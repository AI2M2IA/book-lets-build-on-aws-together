# باب 5: وہ فائلنگ کیبنٹ جو کلاؤڈ میں رہتی ہے

Leo صبح نو بجے EC2 instance صاف کر رہا تھا جب اسے folder ملا۔

دفتر خاموش تھا۔ Maya ابھی نہیں آئی تھی۔ کافی ابھی بن رہی تھی۔ کھڑکی کے باہر، صبح کے مسافر گزر رہے تھے۔ Leo کے headphones لگے تھے اور وہ directories میں اسکرول کر رہا تھا جب وہ رک گیا۔

آٹھ سو فائلیں۔ ان میں سے سب مینو تصاویر۔ ان میں سے سب ایک واحد مشین پر بغیر کسی بیک اپ کے۔

وہ EC2 instance جہاں Nimbus ایپ چلتی تھی بارہ منٹ کے آؤٹیج کے بعد سے ایک بار اپ گریڈ ہو چکا تھا، لیکن تصویری اسٹوریج کبھی منتقل نہیں ہوئی تھی۔ ہر کرسپی arepa، ہر گرل کی ہوئی سالمن پلیٹ، ہر بالکل سجائی گئی سالاد باؤل — ایک واحد ورچوئل مشین پر بیٹھی، جس کے بارے میں وہ پہلے ہی ثابت کر چکے تھے کہ یہ بغیر کسی انتباہ کے نیچے جا سکتی ہے۔

اور اگر وہ مشین کبھی دوبارہ شروع ہو جائے، resize ہو جائے، یا تبدیل ہو جائے؟

غائب۔

"اب تک گاہکوں نے کتنی تصاویر اپ لوڈ کی ہیں؟" Maya نے پوچھا، جب وہ آئی۔

Leo مڑا۔ "تقریباً آٹھ سو۔"

"اور اگر ہم سرور دوبارہ شروع کریں تو ان آٹھ سو تصاویر کا کیا ہوتا ہے؟"

Leo کے بامعنی وقفوں میں سے ایک اور۔

یہ باب اس بارے میں ہے کہ فائلیں کلاؤڈ میں دراصل کہاں سے تعلق رکھتی ہیں۔

**فائلیں "سرور پر" محفوظ کرنے کا مسئلہ**

جب آپ فائلیں براہِ راست کسی EC2 instance پر — اس کے فائل سسٹم کے اندر — محفوظ کرتے ہیں، تو آپ ان فائلوں کو اس مخصوص مشین کے lifecycle سے باندھ دیتے ہیں۔

اس سے کئی مسائل پیدا ہوتے ہیں:

**فطرتاً عارضی۔** EC2 instances کو روکا، terminate، تبدیل کیا جا سکتا ہے۔ ان کی مقامی ڈسک کا مستقل ہونا مقصود نہیں۔ یہ عارضی scratch جگہ ہے۔

**ناکامی کا واحد نقطہ۔** اگر instance ناکام ہو جائے، تو فائلیں اس کے ساتھ چلی جاتی ہیں۔ کوئی ریڈنڈنسی نہیں۔ کوئی بیک اپ نہیں۔ ایک برا صبح اور آٹھ سو مینو تصاویر غائب ہو جاتی ہیں۔

**instances میں شیئر نہیں ہو سکتیں۔** جب آپ ایک دوسرا سرور شامل کرتے ہیں (جو آپ کریں گے، باب 7 میں)، تو وہ پہلے سرور کی ڈسک پر محفوظ فائلیں نہیں دیکھے گا۔ دونوں سرور الگ تھلگ ہیں۔ ایک صارف جو تصویر اپ لوڈ کرتا ہے شاید اسے دیکھے؛ ایک مختلف سرور سے ٹکرانے والا دوسرا صارف شاید نہ دیکھے۔

**کوئی پیمانہ نہیں۔** EC2 ڈسک کی جگہ محدود ہے۔ اگر آپ اسے بھر دیں، تو آپ یا تو اپ لوڈز قبول کرنا بند کر دیتے ہیں یا دباؤ میں اسٹوریج بڑھانے کے لیے بھاگ دوڑ کرتے ہیں۔

Leo نے یہ غور نہیں کیا تھا کہ متعدد سرورز کے ساتھ کیا ہوتا ہے۔ اس نے یہ Priya سے غیر رسمی طور پر ذکر کیا۔

"ٹھہریں — تصویر کا مسئلہ دو سرورز کے ساتھ کیسے کام کرے گا؟" Priya نے پوچھا۔

"تمہارا کیا مطلب ہے؟"

"اگر ہمارے پاس load balancer کے پیچھے Server A اور Server B ہیں،" Priya نے کہا، "اور کوئی گاہک تصویر اپ لوڈ کرتا ہے — اس کی درخواست Server A کو جاتی ہے، ٹھیک ہے؟ تو تصویر Server A کی ڈسک پر محفوظ ہوتی ہے۔ اب اس کی اگلی درخواست Server B کو جاتی ہے۔ Server B کے پاس وہ تصویر نہیں ہے۔ گاہک کو کیا نظر آتا ہے؟"

Leo نے منہ کھولا۔ پھر بند کر لیا۔

"ایک ٹوٹی ہوئی image،" اس نے آخر کار کہا۔

"یا ایک 404 error،" Priya نے کہا۔ "یا، اگر ایپلیکیشن اسے لوڈ کرنے کی کوشش کرے اور crash ہو جائے، تو ایک error صفحہ۔"

اس نے وائٹ بورڈ پر load-balancer منصوبے کا خاکہ بنایا — ایک دوسرا سرور شامل کرنا پہلے ہی roadmap پر تھا۔ جس لمحے یہ ہوتا، ہر تصویر اپ لوڈ ایک سکے کا اچھال بن جاتی: Server A پر اپ لوڈ، ممکنہ طور پر Server B سے پیش، تصویر غائب، گاہک الجھن میں۔

"ہم یہ معلوم کرنے سے پہلے ایک ہفتہ اسے debug کر رہے ہوتے کہ کیا غلط ہے،" Leo نے کہا۔

"کیا ہم نے سوچا ہے کہ جب ہم Auto Scaling آن کریں اور اچانک تین یا چار سرورز ہوں تو کیا ہوگا؟" Priya نے پوچھا۔ "ہم مسلسل تصاویر کھو رہے ہوں گے۔"

یہ bug کی ایک ایسی قسم ہے جو unit tests میں ظاہر نہیں ہوتی۔ یہ صرف production میں ظاہر ہوتی ہے، load کے تحت، جب حقیقی ٹریفک متعدد سرورز میں پھیلی ہو۔ حل یہ ہے کہ فائلیں سرورز پر مکمل طور پر محفوظ کرنا بند کر دیا جائے۔

ایک بہتر ماڈل موجود ہے۔ AWS نے اسے 2006 میں بنایا، اور یہ اب بھی دنیا کی سب سے زیادہ استعمال ہونے والی کلاؤڈ سروسز میں سے ایک ہے۔

**وہ ہارڈ ڈرائیو جو آن لائن رہتی ہے**

ایک ایسی ہارڈ ڈرائیو کا تصور کریں جو انٹرنیٹ پر رہتی ہے — ایک جو اتنی بڑھتی ہے جتنی آپ کو کبھی ضرورت ہو، اور آپ سے صرف اس کا چارج کرتی ہے جو آپ دراصل استعمال کرتے ہیں۔ آپ اسے کبھی provision نہیں کرتے۔ آپ کبھی جگہ ختم ہونے کی فکر نہیں کرتے۔ اگر آپ آج آٹھ سو تصاویر ڈالیں اور اگلے سال اسی لاکھ، تو آپ کی طرف بل کے لائن آئٹم کے سوا کچھ نہیں بدلتا۔

یہی AWS پیش کرتا ہے۔ وہ اسے **Amazon S3** کہتے ہیں — Simple Storage Service۔

S3 AWS کی object اسٹوریج سروس ہے۔ یہ بالکل فائل سسٹم جیسی نہیں، اور بالکل ڈیٹابیس جیسی نہیں۔ یہ فائلیں — جنہیں objects کہتے ہیں — buckets نامی نام زد کنٹینرز میں محفوظ کرتی ہے۔ ماڈل سادہ ہے، اور یہ سادگی ہی اصل بات ہے۔

S3 میں اہم تصور **object** ہے۔

ایک object کوئی بھی فائل ہے: ایک تصویر، ایک ویڈیو، ایک PDF، ایک CSV، ایک بیک اپ، ایک log فائل۔ S3 کو قسم یا ساخت کی پروا نہیں۔ یہ bytes محفوظ کرتا ہے اور جب آپ مانگیں واپس دیتا ہے۔

objects **buckets** کے اندر رہتے ہیں۔ ایک bucket ایک اعلیٰ سطح کے folder کی طرح ہے — S3 کے اندر ایک نام زد کنٹینر جو آپ کے objects رکھتا ہے۔ ہر bucket کا عالمی سطح پر منفرد نام ہوتا ہے (تمام AWS اکاؤنٹس میں کوئی بھی دو buckets ایک نام شیئر نہیں کر سکتیں) اور یہ ایک مخصوص Region میں موجود ہوتی ہے۔

**S3 کیسے کام کرتا ہے**

آپ ایک bucket میں ایک object **اپ لوڈ** کرتے ہیں۔ S3 اسے ایک **key** دیتا ہے — بنیادی طور پر ایک راستے کا نام جیسے `menus/restaurant-001/photo-arepa.jpg`۔ وہ key bucket کے اندر object کو منفرد طور پر شناخت کرتی ہے۔

آپ bucket کے نام اور key کا استعمال کرتے ہوئے object **ڈاؤن لوڈ** (یا حاصل) کرتے ہیں۔

آپ objects کو عوامی طور پر قابلِ رسائی بھی بنا سکتے ہیں — یعنی URL رکھنے والا کوئی بھی انہیں ڈاؤن لوڈ کر سکتا ہے۔ اسی طرح زیادہ تر ویب سائٹس تصاویر پیش کرتی ہیں: تصویر S3 میں محفوظ کریں، اسے عوامی بنائیں، اپنے HTML میں URL embed کریں۔

یا آپ objects نجی رکھتے ہیں — صرف تصدیق شدہ درخواستوں کے لیے قابلِ رسائی۔ یہ گاہک کے ڈیٹا، بیک اپس، اور کسی بھی حساس چیز کے لیے صحیح ماڈل ہے۔

S3 ایک فائل سسٹم نہیں ہے۔ کوئی حقیقی folders نہیں ہیں۔ key نام میں `/` محض ایک روایت ہے — S3 پوری key کو ایک flat string سمجھتا ہے۔ لیکن یہ folders جیسا لگتا ہے اور زیادہ تر اوزار اسے folders کے طور پر پیش کرتے ہیں، اس لیے عمل میں اس امتیاز کی فکر نہ کریں۔

S3 کی چند آپریشنل خصوصیات ہیں جو عمل میں اہم ہیں لیکن تفصیل سے واضح نہیں:

**Object immutability**: S3 objects کو ان کی جگہ پر ترمیم نہیں کیا جاتا۔ اگر آپ کوئی فائل اپڈیٹ کرتے ہیں، تو آپ اسی key کے ساتھ object کا ایک نیا ورژن اپ لوڈ کرتے ہیں۔ S3 پرانے object کو نئے سے بدل دیتا ہے (یا، versioning فعال ہونے کے ساتھ، دونوں رکھتا ہے)۔ ایک ڈیٹابیس کے برعکس جہاں آپ ایک row `UPDATE` کرتے ہیں، S3 objects write-once، read-many ہیں۔ ان text فائلوں اور دستاویزات کے لیے جنہیں آپ اکثر ترمیم کرتے ہیں، یہ ٹھیک ہے — بس نیا ورژن اپ لوڈ کریں۔ بہت بڑی فائلوں کے لیے جہاں آپ صرف مواد کا ایک حصہ اپڈیٹ کرنا چاہتے ہیں، S3 کے object ماڈل کا مطلب ہے کہ آپ ہر بار پوری فائل دوبارہ اپ لوڈ کرتے ہیں۔

**Strong read-after-write consistency**: دسمبر 2020 سے، S3 تمام objects کے لیے strong consistency فراہم کرتا ہے — نئی لکھائیاں بعد کی reads کو فوراً نظر آتی ہیں۔ 2020 سے پہلے، S3 کی کچھ آپریشنز کے لیے eventual consistency تھی، جو ان ایپلیکیشنز میں باریک bugs کا سبب بنتی تھی جو ایک object لکھتیں اور فوراً اسے پڑھنے کی کوشش کرتیں۔ consistency ماڈل کی بہتری نے bugs کی اس قسم کو ختم کر دیا۔

**Object URLs**: ہر S3 object کا ایک URL ہوتا ہے۔ ایک عوامی object کے لیے، یہ ایسا نظر آتا ہے: `https://bucket-name.s3.region.amazonaws.com/key/path`۔ نجی objects کے لیے، آپ pre-signed URLs بنا سکتے ہیں جن میں تصدیقی معلومات شامل ہوتی ہیں اور جو ایک کنفیگر شدہ وقت کے بعد ختم ہو جاتے ہیں۔ دونوں URL فارمیٹ وہ طریقہ ہیں جس سے ایپلیکیشنز اور براؤزرز دراصل objects حاصل کرتے ہیں — کوئی ملکیتی protocol شامل نہیں۔

**بنانے کے لیے کوئی directories نہیں**: چونکہ S3 کے کوئی حقیقی folders نہیں ہیں، اس لیے کوئی directory بنانے کی آپریشنز نہیں ہیں۔ آپ بس ایک object اپ لوڈ کرتے ہیں جس کی key میں راستے کا prefix شامل ہو۔ "folder" console میں خودکار طور پر ظاہر ہوتا ہے جب اس prefix والے objects موجود ہوں، اور خودکار طور پر غائب ہو جاتا ہے جب اس prefix والے تمام objects حذف ہو جائیں۔

**S3 ایک عام ہارڈ ڈرائیو سے کیوں مختلف ہے**

تین چیزیں S3 کو EC2 instance پر فائل اسٹوریج سے بنیادی طور پر مختلف بناتی ہیں:

**پائیداری (Durability)۔** AWS، S3 کو 99.999999999% (گیارہ نائنز) پائیداری کے لیے ڈیزائن کرتا ہے۔ اس کا مطلب ہے کہ اگر آپ ایک کروڑ objects محفوظ کریں، تو آپ ہارڈ ویئر کی ناکامی کی وجہ سے ہر دس ہزار سال میں ایک object کھونے کی توقع کر سکتے ہیں۔ وہ یہ ہر object کی متعدد کاپیاں خودکار طور پر کم از کم تین Availability Zones میں محفوظ کر کے حاصل کرتے ہیں۔

لیکن پائیداری ہارڈ ویئر کی ناکامی سے بچاتی ہے — اس سے نہیں کہ آپ غلطی سے کچھ حذف کر دیں۔ versioning اسی کے لیے ہے۔

**پائیداری** اور **دستیابی** کے درمیان ایک اہم امتیاز ہے۔ پائیداری اس بارے میں ہے کہ آیا آپ کا ڈیٹا ابھی بھی موجود ہے۔ دستیابی اس بارے میں ہے کہ آیا آپ ابھی اس تک رسائی کر سکتے ہیں۔ S3 Standard 99.999999999% پائیداری اور 99.99% دستیابی پیش کرتا ہے۔ پائیداری کا عدد تقریباً ناقابلِ فہم حد تک بلند ہے؛ 99.99% دستیابی کا عدد ایک *ڈیزائن ہدف* ہے — سالانہ تقریباً 52 منٹ کی عدم دستیابی۔ معاہداتی *SLA* دراصل کم ہے (99.9% فی ماہ)، اور اسے نہ پانا آپ کو سروس credits کماتا ہے، uptime نہیں۔ عمل میں، S3 دستیابی دونوں اعداد سے بہت زیادہ ہے — لیکن یہ سمجھنا قابلِ قدر ہے کہ پائیداری اور دستیابی الگ ضمانتیں ہیں، اور ڈیزائن اہداف اور SLAs الگ وعدے ہیں۔

**دستیابی (Availability)۔** S3 کو اس طرح ڈیزائن کیا گیا ہے کہ انفرادی اجزاء کی ناکامی کے باوجود بھی قابلِ رسائی رہے۔ آپ ایک سرور سے نہیں جڑ رہے — آپ ایک تقسیم شدہ نظام سے جڑ رہے ہیں جو ناکامیوں کے گرد راستہ نکالتا ہے۔

**پیمانہ (Scale)۔** S3 بنیادی طور پر لامحدود مقدار میں ڈیٹا رکھتا ہے۔ ایک واحد bucket میں کھربوں objects ہو سکتے ہیں۔ Amazon خود S3 کو ایسے پیمانے پر ڈیٹا محفوظ کرنے کے لیے استعمال کرتا ہے جسے سمجھنا مشکل ہے۔ دنیا کی سب سے بڑی S3 buckets exabytes ڈیٹا رکھتی ہیں — لاکھوں terabytes۔ آپ اس پیمانے کا انتظام نہیں کرتے؛ آپ بس objects اپ لوڈ کرتے ہیں اور S3 نیچے ہر چیز سنبھالتا ہے۔

**لاگت (Cost)۔** S3 Standard اس تحریر کے وقت تقریباً $0.023 فی GB فی ماہ پڑتا ہے۔ Nimbus کی آٹھ سو مینو تصاویر کے لیے، ہر ایک اوسطاً 2MB، یہ 1.6 GB اسٹوریج ہے — تقریباً $0.04 فی ماہ۔ 800,000 تصاویر پر بھی، آپ اسٹوریج کے لیے $37 فی ماہ دیکھ رہے ہیں۔ EBS volume پر اسی اسٹوریج کی لاگت تقریباً $128 فی ماہ ہوتی، ایک مقررہ حد کے ساتھ جس کے لیے مزید شامل کرنے سے پہلے توسیع درکار ہوتی۔ S3 خودکار طور پر بڑھتا ہے اور تناسب سے چارج کرتا ہے۔ EBS کا ایک مقررہ سائز اور ایک مقررہ لاگت ہے۔

**Versioning: انڈو بٹن**

یہاں کچھ ایسا ہے جو Maya نے S3 console ایکسپلور کرتے وقت پایا۔

S3 **versioning** سپورٹ کرتا ہے۔ جب آپ کسی bucket پر versioning فعال کرتے ہیں، تو S3 ہر object کا ہر ورژن رکھتا ہے — بشمول پچھلے ورژن اور حذف شدہ ورژن۔

یہ آپ کی فائلوں کے لیے انڈو بٹن ہے۔

Priya اس پر بھروسہ کرنے سے پہلے اس کا امتحان لینا چاہتی تھی۔ اس نے bucket میں ایک مینو تصویر اپ لوڈ کی، پھر غلط فائل کے ساتھ ایک نیا ورژن اپ لوڈ کیا — ایک بالکل کالی image جو اس نے تیس سیکنڈ میں بنائی۔

اس نے S3 console کھولا، "Show versions" پر click کیا، اور دونوں پائے: خراب ورژن (موجودہ) اور اصل (پچھلا)۔ اس نے پچھلے ورژن کو نئے موجودہ ورژن کے طور پر واپس کاپی کر کے بحال کیا۔

"یہ کام کرتا ہے،" اس نے کہا۔

"وہ تمام ورژن رکھنے کی کتنی لاگت ہے؟" Tom نے پوچھا۔

آپ ہر ورژن کی اسٹوریج کے لیے ادائیگی کرتے ہیں۔ اگر آپ کے پاس بڑی فائلوں کے بہت سے ورژن ہیں، تو یہ جمع ہو جاتا ہے۔ AWS کے پاس **lifecycle policies** ہیں جو ایک مخصوص وقت کے بعد پرانے ورژن خودکار طور پر حذف کر دیتی ہیں — ہم انہیں باب 23 میں کور کرتے ہیں جب ہم لاگت کی اصلاح پر گہرائی سے جاتے ہیں۔

"تو ہم versioning فعال کرتے ہیں لیکن تیس دن کے بعد پرانے ورژن حذف کرنے کے لیے ایک lifecycle قاعدہ طے کرتے ہیں،" Priya نے کہا۔ "اس طرح ہمارے پاس ہر ورژن کو ہمیشہ کے لیے محفوظ کرنے کی ادائیگی کیے بغیر ایک ریکوری window ہوتی ہے۔"

Tom نے عدد لکھ لیا۔ تیس دن کے ورژنز کی اسٹوریج لاگت قابلِ قبول تھی۔

**S3 Event Notifications: فائلیں جو کام کرتی ہیں**

Leo مینو تصاویر کو ایک مختلف زاویے سے دیکھ رہا تھا۔

"ابھی،" اس نے کہا، "جب کوئی ریستوران تصویر اپ لوڈ کرتا ہے، ہم اصل کو پوری resolution پر محفوظ کرتے ہیں۔ ان میں سے کچھ چار ہزار بائی تین ہزار pixels ہیں۔ ہر بار جب کوئی گاہک فون پر مینو صفحہ لوڈ کرتا ہے، ہم ایک چار میگابائٹ image پیش کر رہے ہیں۔"

"اس کی bandwidth میں کتنی لاگت ہے؟" Tom نے پوچھا۔

Leo نے بل پر ڈیٹا منتقلی کے اعداد کھولے۔ جواب تھا "اس سے زیادہ جتنا ہونا چاہیے۔"

S3 کی ایک خصوصیت ہے جسے **Event Notifications** کہتے ہیں۔ جب کسی bucket میں کوئی object اپ لوڈ ہوتا ہے، تو S3 خودکار طور پر کسی دوسری سروس کو متحرک کر سکتا ہے — جیسے Lambda، وہ serverless کمپیوٹنگ سروس جسے ہم باب 20 میں کور کرتے ہیں۔ وہ trigger کسی دستی مداخلت کے بغیر اپ لوڈ کے جواب میں کوڈ چلا سکتا ہے۔

Nimbus کا حل: ہر بار جب کوئی تصویر raw photos bucket میں اپ لوڈ ہوتی ہے، تو ایک S3 Event Notification ایک Lambda function کو متحرک کرتا ہے۔ Lambda function اصل تصویر پڑھتا ہے، ایک 400-pixel-چوڑا thumbnail بناتا ہے، اور اسے ایک processed photos bucket میں محفوظ کرتا ہے۔ گاہک کا سامنا کرنے والی ایپ اصل کے بجائے thumbnail پیش کرتی ہے۔

pipeline:

1. ریستوران 4MB اصل تصویر `nimbus-photos-raw/restaurant-001/arepa.jpg` پر اپ لوڈ کرتا ہے
2. S3 Event Notification فائر کرتا ہے
3. Lambda function اصل پڑھتا ہے، ایک 400x300 thumbnail بناتا ہے
4. Lambda thumbnail کو `nimbus-photos-processed/restaurant-001/arepa.jpg` میں محفوظ کرتا ہے
5. گاہک مینو لوڈ کرتا ہے، ایپ 4MB اصل کے بجائے 40KB thumbnail پیش کرتی ہے

نتیجہ: image bandwidth میں 99% کمی۔ تیز صفحہ لوڈز۔ بل پر ایک چھوٹی ڈیٹا منتقلی کی لائن۔ اصل raw bucket میں محفوظ ہیں، اس لیے اگر Nimbus کبھی اعلیٰ-resolution ورژن بنانا چاہے، تو ماخذ مواد وہاں موجود ہے۔

"یہ خودکار طور پر چلتا ہے؟" Maya نے پوچھا۔

"ہر بار جب کوئی تصویر اپ لوڈ کرتا ہے،" Leo نے کہا۔ "ہم اسے کبھی نہیں چھوتے۔"

یہ پیٹرن — اسٹوریج events سے متحرک event-driven پروسیسنگ — جدید کلاؤڈ آرکیٹیکچر میں سب سے عام اور طاقتور پیٹرنز میں سے ایک ہے۔ ہم اس پر باب 20 میں اچھی طرح دوبارہ آتے ہیں۔

**Cross-Region Replication: جب ایک کاپی کافی نہیں**

Priya نے ہفتے کے آخر میں ایک تعمیل کا سوال اٹھایا۔

"اگر Nimbus EU میں ریستورانوں کو خدمت دینے کے لیے پھیلے،" اس نے کہا، "اور وہ ریستوران تصاویر اپ لوڈ کریں — کیا وہ تصاویر ہماری `us-west-2` bucket میں محفوظ ہوتی ہیں؟"

"ہاں،" Leo نے کہا۔

"اور کیا GDPR کے پاس اس بارے میں کچھ کہنا ہے کہ وہ ڈیٹا کہاں محفوظ ہوتا ہے؟"

ہے۔ GDPR کی ڈیٹا منتقلی کی شقوں کا مطلب ہے کہ EU باشندوں کے بارے میں ذاتی ڈیٹا کو EU کے اندر یا مناسب ڈیٹا تحفظ والے دائرہ اختیار میں اسٹوریج کی ضرورت ہو سکتی ہے۔

S3 کا اس کا جواب **Cross-Region Replication** (CRR) ہے۔ جب آپ کسی bucket پر CRR فعال کرتے ہیں، تو اپ لوڈ کیا گیا ہر نیا object خودکار طور پر کسی اور Region میں ایک bucket میں نقل ہو جاتا ہے۔ آپ source bucket، destination bucket، اور وہ IAM role کنفیگر کرتے ہیں جو S3 کو نقل انجام دینے کی اجازت دیتا ہے۔

جب EU توسیع ہوتی ہے، تو منصوبہ یہ ہے: EU ریستورانوں کی اپ لوڈ کی گئی تصاویر ایک `eu-west-1` bucket میں جائیں گی، اور CRR انہیں ڈیزاسٹر ریکوری کے لیے `eu-central-1` (Frankfurt) میں ایک بیک اپ bucket میں نقل کرے گا۔ EU ڈیٹا EU Regions میں رہتا ہے۔

"اس کی کتنی لاگت ہوگی؟" Tom نے پوچھا۔

Cross-region ڈیٹا منتقلی اور اسٹوریج لاگتیں لاگو ہوتی ہیں — تقریباً source Region سے destination تک فی-GB منتقلی کا ریٹ، نیز نقل شدہ کاپیوں کے لیے اسٹوریج۔ Tom نے Nimbus کے متوقع EU تصویری حجم پر حساب کیا اور طے کیا کہ یہ قابلِ قبول ہوگا۔

"اور اگر کوئی replication pipeline میں توڑ پھوڑ کرنے کی کوشش کرے تو؟" Priya نے پوچھا۔ "وہ IAM role جو نقل انجام دیتا ہے اسے سختی سے محدود ہونا چاہیے — صرف S3 replication actions، صرف مخصوص buckets پر۔"

اس نے وہ ضرورت توسیع کے منصوبے میں لکھ دی۔

**Multipart Upload اور نامکمل اپ لوڈ کا مسئلہ**

Tom نے AWS بل پر ایک غیر متوقع لائن آئٹم پایا۔

"ہم S3 میں اسٹوریج کے لیے ادائیگی کر رہے ہیں،" اس نے کہا، "لیکن مقدار اس سے زیادہ ہے جتنی میں ہماری تصاویر کی تعداد سے توقع کروں گا۔"

Leo نے تفتیش کی۔ اسے S3 Storage Lens رپورٹ میں ایک زمرہ ملا: **incomplete multipart uploads**۔

جب S3 ایک مخصوص سائز سے بڑی فائل اپ لوڈ کرتا ہے، تو یہ **multipart upload** استعمال کرتا ہے: فائل کو حصوں میں تقسیم کیا جاتا ہے، ہر حصہ الگ اپ لوڈ ہوتا ہے، اور پھر حصوں کو حتمی object میں جمع کیا جاتا ہے۔ یہ بڑی اپ لوڈز کو زیادہ قابلِ اعتماد بناتا ہے — اگر ایک حصہ ناکام ہو جائے، تو صرف اس حصے کو دوبارہ آزمانے کی ضرورت ہوتی ہے، پوری فائل کو نہیں۔

لیکن اگر کوئی multipart upload شروع ہو جائے اور پھر ترک ہو جائے — صارف نے براؤزر بند کر دیا، نیٹ ورک گر گیا، ایپلیکیشن crash ہو گئی — تو جزوی حصے S3 میں رہتے ہیں، اسٹوریج چارجز جمع کرتے ہوئے۔ وہ مکمل objects کے طور پر نظر نہیں آتے، لیکن انہیں اسٹوریج کے طور پر bill کیا جا رہا ہوتا ہے۔

"کتنا؟" Tom نے پوچھا۔

"تقریباً $12 ماہانہ،" Leo نے کہا۔ "ان جزوی اپ لوڈز سے جو کبھی مکمل نہیں ہوئیں۔"

حل: ایک S3 **lifecycle قاعدہ** جو سات دن کے بعد نامکمل multipart uploads خودکار طور پر حذف کر دیتا ہے۔ کوئی بھی اپ لوڈ جو ایک ہفتے میں مکمل نہیں ہوئی ترک کر دی جاتی ہے، اور جزوی حصے صاف کر دیے جاتے ہیں۔

Tom نے اسی دوپہر lifecycle قاعدہ شامل کیا۔ $12/ماہ کا چارج چند دنوں میں غائب ہو گیا۔

"یہ $144 سالانہ ہے،" Tom نے اپنی اسپریڈ شیٹ دیکھتے ہوئے کہا۔ "کچھ نہ ہونے کے لیے۔"

"میں نے ایک load test سیٹ اپ کیا تھا جو multipart uploads استعمال کرتا تھا،" Leo نے کہا۔ "اوہ۔" ایک وقفہ۔ "وہ شاید ان میں سے زیادہ تر ہیں۔ میں test مکمل ہونے پر اسے صاف کرنا بھول گیا۔"

Tom نے اسے بہرحال لکھ لیا۔

**رسائی کنٹرول: عوامی بمقابلہ نجی**

ڈیفالٹ طور پر، S3 میں ہر چیز نجی ہے۔ صرف آپ کا AWS اکاؤنٹ اس تک رسائی کر سکتا ہے۔

آپ انفرادی objects کو عوامی بنا سکتے ہیں — جیسے آپ ویب سائٹ کے ملاحظہ کاروں کو مینو تصاویر پیش کریں گے۔ یا آپ سب کچھ نجی رکھ سکتے ہیں اور **pre-signed URLs** بنا سکتے ہیں: وقت کی پابند links جو کسی کو AWS credentials کی ضرورت کے بغیر ایک مخصوص object ڈاؤن لوڈ کرنے دیتے ہیں۔ کسی گاہک کو 24 گھنٹے کے لیے اپنا انوائس ڈاؤن لوڈ کرنے دینے کے لیے بہترین۔

Priya کی اس بارے میں بہت مضبوط رائے تھی۔

"اور اگر کوئی غلط کنفیگر کی گئی bucket کے ذریعے توڑ پھوڑ کرنے کی کوشش کرے تو؟" اس نے کہا۔ "کبھی کسی bucket کو مکمل طور پر عوامی نہ بنائیں جب تک کہ آپ نے شعوری طور پر فیصلہ نہ کر لیا ہو کہ اس میں ہر object پورے انٹرنیٹ کے لیے قابلِ رسائی ہو۔ سب سے عام S3 سیکیورٹی غلطی ایک ایسی bucket کو غلطی سے بے نقاب کرنا ہے جس میں حساس ڈیٹا ہو۔"

AWS کے پاس اب ایک "Block Public Access" سیٹنگ ہے جسے آپ اکاؤنٹ کی سطح پر لاگو کر سکتے ہیں، تمام buckets کو نجی بناتے ہوئے جب تک آپ فی bucket واضح طور پر اسے override نہ کریں۔

اسے فعال کریں۔ ہمیشہ۔

اس کے پیچھے کی تاریخ: اس سے پہلے کہ AWS نے اکاؤنٹ کی سطح کا Block Public Access شامل کیا، سب سے عام S3 سیکیورٹی واقعہ غلطی سے کسی bucket کو عوامی بنانا تھا۔ ایک ڈویلپر نے امتحان کے لیے ایک bucket بنایا، سہولت کے لیے "public" باکس چیک کیا، کچھ فائلیں شامل کیں بشمول چند ان folders سے جن کے بارے میں اس نے نہیں سوچا تھا، اور پھر اسے بھول گیا۔ bucket مہینوں وہاں، عوامی طور پر قابلِ رسائی، بیٹھی رہی۔ چند نمایاں واقعات میں، "بھولی ہوئی test bucket" میں گاہک کا ڈیٹا، اندرونی دستاویزات، یا credentials تھے۔

اکاؤنٹ کی سطح کا Block Public Access اس کے خلاف ایک حفاظتی اقدام ہے۔ حتیٰ کہ اگر کوئی ڈویلپر غلطی سے کسی bucket کو عوامی ہونے کے لیے کنفیگر کرے، تو اکاؤنٹ کی سطح کی سیٹنگ اسے override کر دیتی ہے۔ آپ کو کسی bucket کے عوامی ہونے سے پہلے واضح طور پر اکاؤنٹ کی سطح کی سیٹنگ غیر فعال کرنی ہوگی — جو ایک جان بوجھ کر speed bump بناتا ہے جو حادثات کو روکتا ہے۔

Nimbus کا اکاؤنٹ کی سطح پر Block Public Access فعال تھا۔ تو وہ مینو تصاویر جنہیں عوامی طور پر قابلِ رسائی ہونے کی ضرورت تھی کیسے پیش کی جائیں گی؟ معیاری پیٹرن — جو Nimbus بعد میں، باب 13 میں اپنائے گا — یہ ہے کہ bucket کے سامنے CloudFront جیسا ایک CDN ایک Origin Access Control policy کے ساتھ رکھا جائے: CDN ایک نجی S3 bucket سے objects حاصل کر سکتا ہے، لیکن کوئی bucket تک براہِ راست رسائی نہیں کر سکتا۔ یہ پیٹرن ایک عوامی bucket سے زیادہ محفوظ ہے اور CDN کی caching کو S3 درخواست لاگتیں کم کرنے دیتا ہے۔

"ٹھہریں — لیکن ہم ایسا *کیوں* کریں گے؟" Maya نے پوچھا۔ "تصاویر تو بہرحال عوامی ہیں، تو اگر bucket عوامی ہو تو کیا فرق پڑتا ہے؟"

"کیونکہ ایک عوامی bucket کا مطلب ہے کوئی بھی شمار کر سکتا ہے کہ اس میں کیا ہے،" Priya نے کہا۔ "وہ bucket میں تمام objects کی فہرست بنا سکتے ہیں۔ سامنے CloudFront کے ساتھ، وہ صرف وہ URLs دیکھتے ہیں جو ہم ایپلیکیشن میں بے نقاب کرتے ہیں۔ bucket خود نجی رہتی ہے۔"

Maya نے "enumerate" کو حملہ سطحوں کے اپنے ذہنی ماڈل میں شامل کیا۔

**S3 Storage Classes: تمام ڈیٹا برابر نہیں**

تمام ڈیٹا یکساں رسائی نہیں کیا جاتا۔

آپ کی سب سے مقبول مینو تصاویر فی سیکنڈ درجنوں بار حاصل کی جاتی ہیں۔ تین سال پہلے کے آپ کے logs شاید سال میں ایک بار، اگر کبھی، رسائی کیے جاتے ہیں۔ S3 اسے پہچانتا ہے اور مختلف کارکردگی اور لاگت کے ٹریڈ آفس کے ساتھ مختلف **storage classes** پیش کرتا ہے۔

| اسٹوریج کلاس            | استعمال کا موقع                                | بازیابی          | لاگت                          |
|-------------------------|-----------------------------------------------|------------------|-----------------------------|
| S3 Standard             | کثرت سے رسائی کیا جانے والا ڈیٹا              | فوری             | فی GB زیادہ                  |
| S3 Standard-IA          | کم رسائی، پھر بھی تیز بازیابی درکار            | فوری             | فی GB کم، بازیابی فیس        |
| S3 Glacier Instant      | کبھی کبھار رسائی کیے جانے والے آرکائیوز       | فوری             | بہت کم                       |
| S3 Glacier Flexible     | شاذ و نادر رسائی کیے جانے والے آرکائیوز       | منٹوں سے گھنٹوں  | بہت کم                       |
| S3 Glacier Deep Archive | تعمیل آرکائیوز، تقریباً کبھی رسائی نہیں       | 12 گھنٹوں تک     | سب سے کم                     |

ہم ان پر باب 23 میں گہرائی سے جاتے ہیں۔ ابھی کے لیے: تصور یہ ہے کہ آپ objects کو ان کی عمر اور رسائی کے نمونوں کی بنیاد پر storage classes کے درمیان خودکار طور پر منتقل کر سکتے ہیں، اس ڈیٹا پر نمایاں پیسہ بچاتے ہوئے جسے آپ شاذ و نادر ہی چھوتے ہیں۔

ایک **S3 Intelligent-Tiering** بھی ہے — ایک storage class جو مشاہدہ شدہ رسائی کے نمونوں کی بنیاد پر objects کو frequent-access اور infrequent-access tiers کے درمیان خودکار طور پر منتقل کرتی ہے۔ آپ فی object فی ماہ ایک چھوٹی monitoring فیس ادا کرتے ہیں، اور S3 خودکار طور پر tiering سنبھالتا ہے۔ یہ تب مفید ہے جب آپ کو یقین نہ ہو کہ کون سے objects کثرت سے رسائی کیے جائیں گے اور کون سے نہیں — سروس پیٹرن سیکھتی ہے اور اسی کے مطابق optimize کرتی ہے۔

Tom کا نقطہ نظر زیادہ دستی تھا: "میں جاننا چاہتا ہوں کہ ہر ڈالر کہاں جا رہا ہے۔" اس نے Intelligent-Tiering کے بجائے واضح lifecycle قواعد چنے، کیونکہ واضح قواعد قابلِ پیش گوئی اور قابلِ آڈٹ ہیں۔ Nimbus کی S3 اسٹوریج چلانے کے چھ مہینے بعد، اس کے پاس رسائی کے نمونوں کی واضح تصویر تھی اور وہ lifecycle قواعد طے کر سکتا تھا جو objects کو 30 دن کے بعد Standard-IA اور 180 دن کے بعد Glacier Flexible Retrieval میں منتقل کرتے۔

پہلے سال میں lifecycle management سے کل اسٹوریج بچت: تقریباً $340۔ زندگی بدلنے والی نہیں، لیکن حقیقی — اور یہ پیٹرن کسی بھی سنجیدہ AWS اکاؤنٹ میں درجنوں buckets میں دہرایا جاتا ہے۔

"یہ تقریباً ایک round-trip پرواز ہے،" Maya نے کہا۔

"یہ اچھی انجینیئرنگ پریکٹس ہے،" Tom نے کہا۔ اس نے اسے اسپریڈ شیٹ میں ڈال دیا۔

storage class کے انتخاب میں ایک جال ہے جو بہت سی ٹیموں کو پکڑتا ہے: **کم از کم اسٹوریج مدت**۔ S3 Standard-IA کی کم از کم 30 دن اسٹوریج مدت ہے — اگر آپ کوئی object Standard-IA میں محفوظ کریں اور اسے 15 دن بعد حذف کریں، تو آپ پھر بھی 30 دن کے لیے ادائیگی کرتے ہیں۔ Glacier Flexible Retrieval کی 90 دن کی کم از کم ہے۔ Glacier Deep Archive کی 180 دن کی کم از کم ہے۔

ان objects کے لیے جو کثرت سے حذف ہوتے ہیں یا جن کی عمر کم ہوتی ہے، یہ کم از کم حدیں IA اور Glacier کلاسز کو Standard سے زیادہ مہنگا بناتی ہیں، کم نہیں۔ کسی سستی storage class میں منتقل ہونے سے پہلے، تصدیق کریں کہ objects دراصل وہاں اتنی دیر رہیں گے کہ بچت کم از کم مدت کے جرمانوں سے تجاوز کرے۔

## طاقتیں اور حدود

**S3 کیوں بہترین ہے**:

- گیارہ نائنز پائیداری۔ آپ کا ڈیٹا S3 میں تقریباً کسی بھی دوسرے نظام سے زیادہ محفوظ ہے۔
- لامحدود پیمانہ۔ آپ کو کبھی اسٹوریج provision کرنے کی ضرورت نہیں — یہ بس بڑھتا رہتا ہے۔
- جو یہ فراہم کرتا ہے اس کے لیے انتہائی سستا (فی GB فی ماہ سینٹ کے حصے)۔
- تقریباً ہر دوسری AWS سروس کے ساتھ مقامی انضمام۔
- جامد ویب سائٹ ہوسٹنگ سپورٹ کرتا ہے — آپ براہِ راست S3 سے ایک مکمل جامد ویب سائٹ
  پیش کر سکتے ہیں، کوئی سرور درکار نہیں۔
- Event-driven پروسیسنگ: S3 Event Notifications objects بننے یا حذف ہونے پر خودکار طور پر
  Lambda، SQS، یا SNS کو متحرک کرتے ہیں، polling یا scheduled jobs کے بغیر طاقتور
  پروسیسنگ pipelines کو ممکن بناتے ہوئے۔
- تعمیل ڈیٹا رہائش اور ڈیزاسٹر ریکوری کے لیے Cross-Region Replication۔

**جہاں S3 صحیح انتخاب نہیں**:

- S3 ایک فائل سسٹم نہیں ہے۔ اگر آپ کی ایپلیکیشن کو ایک drive mount کرنے اور اسے ایک
  مقامی ڈسک کی طرح استعمال کرنے کی ضرورت ہو (فائلیں اپنی جگہ پڑھنا، لکھنا، ترمیم کرنا)، تو S3 غلط اوزار ہے۔
  اس کے بجائے EFS (Elastic File System، باب 6) یا EBS استعمال کریں۔
- S3 کی latency ایک مقامی ڈسک سے نمایاں طور پر زیادہ ہے۔ ڈیٹابیسز یا
  ایسی ایپلیکیشنز کے لیے جنہیں تیز، random-access I/O چاہیے، block اسٹوریج (EBS، باب 6)
  مناسب ہے۔
- S3 *میں* ڈیٹا منتقلی bandwidth چارجز سے مفت ہے — لیکن مکمل طور پر مفت نہیں:
  ہر اپ لوڈ ایک PUT درخواست ہے، اور S3 فی درخواست چارج کرتا ہے۔ لاکھوں
  چھوٹے objects اپ لوڈ کرنا اسٹوریج سے زیادہ درخواست فیس میں پڑ سکتا ہے۔ ڈیٹا منتقلی *باہر*
  فی GB پیسہ لیتی ہے۔ دونوں عام billing حیرتیں ہیں — ہم انہیں باب 30 میں حل کرتے ہیں۔
- S3 ایک ڈیٹابیس نہیں ہے۔ آپ key سے objects محفوظ اور حاصل کر سکتے ہیں، لیکن آپ
  ان کے مواد سے objects query نہیں کر سکتے، aggregations نہیں چلا سکتے، یا relational آپریشنز نہیں کر سکتے۔
  اگر آپ کو محفوظ ڈیٹا کے مواد کو query کرنے کی ضرورت ہو (صرف نام سے حاصل کرنے کی نہیں)،
  تو آپ کو ایک ڈیٹابیس یا Athena (باب 26) جیسی سروس کی ضرورت ہے جو SQL کا استعمال کرتے ہوئے
  S3 objects query کر سکے۔
- Object versioning ایسی لاگتیں محفوظ کرتی ہے جو مرکب ہوتی ہیں۔ ہر versioned object کا ہر پچھلا ورژن
  اسٹوریج کے طور پر bill ہوتا ہے۔ پرانے ورژن ختم کرنے والے lifecycle قواعد
  اختیاری نہیں ہیں — وہ versioning فعال والی کسی بھی bucket کے لیے لاگت کے انتظام کی
  حکمتِ عملی کا حصہ ہیں۔

**S3 Objects کیسے encrypt ہوتے ہیں**

"اور اگر کوئی توڑ پھوڑ کرنے کی کوشش کرے تو؟" Priya نے، حسبِ توقع، اس دن پوچھا جب تصاویر live ہوئیں۔ "کیا یہ objects at rest encrypt ہیں؟"

وہ تھے — اور یہ سمجھنے کے قابل ہے، کیونکہ S3 encryption امتحان پر سب سے زیادہ آزمائے جانے والے موضوعات میں سے ایک ہے۔ S3 پر اپ لوڈ کیا گیا ہر object ڈیفالٹ طور پر at rest encrypt ہوتا ہے۔ سوال یہ ہے کہ *key کس کے پاس ہے*:

**SSE-S3 (ڈیفالٹ)**: S3 ہر object کو ان keys سے encrypt کرتا ہے جنہیں S3 خود منظم کرتا ہے، AES-256 استعمال کرتے ہوئے۔ آپ کچھ نہیں کرتے، کچھ کنفیگر نہیں کرتے، کچھ ادا نہیں کرتے۔ جنوری 2023 سے، یہ ہر bucket پر خودکار ہے۔ زیادہ تر ڈیٹا کے لیے، یہ کافی ہے۔

**SSE-KMS**: S3 objects کو ایک KMS key سے encrypt کرتا ہے — یا تو AWS managed `aws/s3` key یا ایک customer managed key جسے آپ کنٹرول کرتے ہیں (باب 16 KMS کو گہرائی سے کور کرتا ہے)۔ آپ کو کیا ملتا ہے: ہر key کے استعمال کا CloudTrail میں ایک audit trail، key policy کے ذریعے بالکل کنٹرول کرنے کی صلاحیت کہ کون decrypt کر سکتا ہے، اور key غیر فعال کر کے رسائی منسوخ کرنے کی صلاحیت۔ آپ کیا ادا کرتے ہیں: فی درخواست KMS API چارجز۔ زیادہ درخواست کی شرحوں پر، **S3 Bucket Keys** فعال کریں — S3 آپ کے KMS key سے ایک قلیل المدتی bucket-سطح کی key اخذ کرتا ہے، KMS API calls (اور لاگت) کو 99% تک کم کرتے ہوئے۔

**SSE-C**: آپ *ہر درخواست کے ساتھ* اپنی encryption key فراہم کرتے ہیں۔ AWS اسے میموری میں استعمال کرتا ہے اور کبھی محفوظ نہیں کرتا۔ ان تنظیموں کے لیے جن کے تعمیل کے قواعد کہتے ہیں کہ AWS کو کبھی key نہیں رکھنی چاہیے۔ آپریشنل طور پر مشکل — key کھو دیں، ڈیٹا کھو دیں۔

امتحانی پیٹرن: "key استعمال کے audit trail کے ساتھ encryption" یا "کنٹرول کریں کہ کون decrypt کر سکتا ہے" → SSE-KMS۔ "کمپنی کو اپنی keys کا انتظام کرنا ہے اور AWS کو انہیں کبھی محفوظ نہیں کرنا چاہیے" → SSE-C۔ "بغیر کسی انتظامی overhead کے encryption at rest" → SSE-S3 (پہلے سے آن)۔

**S3 Object Lock: Write Once, Read Many**

کچھ ڈیٹا کا حذف کرنا *ناممکن* ہونا چاہیے — policy سے محفوظ نہیں، ساختی طور پر ناقابلِ تبدیل۔ مالیاتی trade ریکارڈز، audit logs، قانونی شواہد۔ **S3 Object Lock** objects کو ایک retention مدت کے لیے ناقابلِ حذف اور ناقابلِ ترمیم بناتا ہے، ایڈمنسٹریٹرز کے ذریعے بھی۔ اسے versioning درکار ہے، اور یہ دو modes میں آتا ہے جنہیں امتحان متضاد کرنا پسند کرتا ہے: **governance mode** (ایک خاص permission والے صارفین پھر بھی lock کو bypass کر سکتے ہیں) اور **compliance mode** (کوئی بھی retention کو کم نہیں کر سکتا یا object حذف نہیں کر سکتا — حتیٰ کہ root صارف بھی — جب تک مدت ختم نہ ہو)۔ ریگولیٹری جملے جیسے "WORM storage" یا "SEC Rule 17a-4" compliance mode میں Object Lock کے لیے امتحانی triggers ہیں۔

**S3 Transfer Acceleration: دور سے تیز اپ لوڈز**

جب صارفین دنیا کے دوسری طرف سے کسی bucket میں بڑی فائلیں اپ لوڈ کرتے ہیں، تو سست حصہ bucket کے region تک طویل عوامی-انٹرنیٹ راستہ ہے۔ **S3 Transfer Acceleration** bucket کو ایک خاص endpoint دیتا ہے جو اپ لوڈز کو قریب ترین AWS edge location میں route کرتا ہے، پھر انہیں AWS کے private backbone پر bucket تک لے جاتا ہے۔ امتحانی trigger: "دنیا بھر کے صارفین ایک مرکزی bucket میں بڑی فائلیں اپ لوڈ کرتے ہیں؛ اپ لوڈز سست ہیں" → Transfer Acceleration (اکثر multipart upload کے ساتھ جوڑا گیا)۔ سمت نوٹ کریں: Transfer Acceleration ڈیٹا کو S3 *میں* لانے کے بارے میں ہے؛ CloudFront ڈیٹا کو *باہر* پیش کرنے کے بارے میں ہے۔

ایک اور storage class جاننے کے قابل ہے: **S3 One Zone-IA** — Standard-IA کی طرح لیکن ایک واحد Availability Zone میں محفوظ، تقریباً 20% سستا، کم رسائی کیے جانے والے ڈیٹا کے لیے جسے آپ دوبارہ بنا سکتے ہیں اگر وہ AZ ضائع ہو جائے (thumbnails، دوبارہ بنائی جا سکنے والی رپورٹس)۔ یہ ایک معیاری امتحانی distractor ہے؛ باب 23 storage-class کے پورے دائرے کو کور کرتا ہے۔


## خلاصہ

ایک واحد instance پر آٹھ سو تصاویر مسئلہ تھا۔ S3 نے اسے حل کیا — لیکن S3 فائلیں رکھنے کی جگہ سے زیادہ ہے۔ یہ ایک پائیدار، قابلِ پیمائش، عالمی سطح پر قابلِ رسائی object store ہے جس کا اپنا رسائی ماڈل، storage classes، lifecycle policies، اور event system ہے۔ یہ سمجھنا کہ S3 کس چیز میں اچھا ہے، اور کس میں جان بوجھ کر نہیں، ہر اسٹوریج فیصلے کو شکل دیتا ہے جو ٹیم یہاں سے آگے کرے گی۔

- **Amazon S3** object اسٹوریج ہے — نام زد کنٹینرز (buckets) میں فائلیں (objects)۔ یہ گیارہ نائنز پائیداری کے لیے کم از کم تین Availability Zones میں کاپیاں محفوظ کرتا ہے۔ S3 ایک فائل سسٹم نہیں ہے: شیئر شدہ mounts کے لیے EFS، واحد-instance block اسٹوریج کے لیے EBS استعمال کریں۔
- EC2 instances پر محفوظ فائلیں اس instance کے lifecycle سے بندھی ہوتی ہیں، جب ٹریفک متعدد سرورز میں پھیلتی ہے تو تصویر-غائب bugs پیدا کرتی ہیں۔ S3 اسے کسی بھی instance سے آزاد ہو کر حل کرتا ہے۔
- **Versioning** objects کے پچھلے ورژن محفوظ رکھتی ہے۔ **Lifecycle قواعد** storage classes کے درمیان منتقلیوں کو خودکار کرتے ہیں اور نامکمل multipart uploads صاف کرتے ہیں جو بصورتِ دیگر خاموش billing چارجز جمع کرتے۔
- ڈیفالٹ طور پر، S3 نجی ہے۔ اکاؤنٹ کی سطح پر "Block Public Access" فعال کریں۔ buckets کو براہِ راست عوامی بنانے کے بجائے Origin Access Control کے ساتھ CloudFront کے ذریعے عوامی objects پیش کریں۔
- S3 storage classes آپ کو لاگت کو رسائی کی تعدد سے ملانے دیتے ہیں — لیکن قلیل المدتی objects کو Infrequent Access یا Glacier tiers میں منتقل کرنے سے پہلے کم از کم اسٹوریج مدت کے چارجز پر نظر رکھیں۔

## Exam Tips

*SAA-C03 ڈومین 3 — ٹاسک 3.1 (high-performing storage solutions)*

- **S3 object اسٹوریج ہے، block اسٹوریج نہیں۔** جب کسی امتحانی منظر نامے کو ایک ایسے فائل سسٹم کی ضرورت ہو جسے متعدد سرورز mount کر سکیں، وہ EFS ہے۔ جب اسے ایک واحد EC2 instance کے لیے ایک ڈسک کی ضرورت ہو، وہ EBS ہے۔ جب اسے فائلیں، بیک اپس، images، یا ایسا ڈیٹا محفوظ کرنے کی ضرورت ہو جو HTTP کے ذریعے رسائی کیا جائے — وہ S3 ہے۔
- **گیارہ نائنز پائیداری** کا مطلب ہے کہ S3 خودکار طور پر متعدد AZs میں ڈیٹا نقل کرتا ہے۔ آپ اسے کنفیگر نہیں کرتے — یہ ڈیفالٹ ہے۔
- **S3 Regional ہے**، لیکن عالمی سطح پر قابلِ رسائی۔ buckets ایک مخصوص Region میں موجود ہیں، لیکن آپ انہیں کہیں سے بھی رسائی کر سکتے ہیں۔
- **Pre-signed URLs** نجی objects تک وقت کی پابند رسائی کی اجازت دیتے ہیں۔ عام پیٹرن: آپ کی ایپلیکیشن 15 منٹ کے لیے درست ایک pre-signed URL بناتی ہے، اسے صارف کو دیتی ہے، صارف براہِ راست S3 سے فائل ڈاؤن لوڈ کرتا ہے۔
- **S3 Standard-IA** کی کم از کم اسٹوریج مدت کا چارج (30 دن) ہے۔ اسے ایسے ڈیٹا کے لیے استعمال نہ کریں جسے آپ جلدی حذف کریں گے۔ امتحان جانچتا ہے کہ آیا آپ storage classes کے درمیان ٹریڈ آفس جانتے ہیں۔
- **Storage class فیصلہ درخت**: *کثرت سے رسائی* → S3 Standard؛ *کم رسائی لیکن تیز بازیابی درکار* → S3 Standard-IA؛ *کبھی کبھار رسائی کیا جانے والا آرکائیو* → S3 Glacier Instant Retrieval؛ *شاذ و نادر رسائی کیا جانے والا آرکائیو* → S3 Glacier Flexible Retrieval؛ *تعمیل آرکائیو، تقریباً کبھی رسائی نہیں* → S3 Glacier Deep Archive۔
- **Cross-Region Replication** کے لیے source اور destination دونوں buckets پر versioning فعال ہونا ضروری ہے۔ ڈیزاسٹر ریکوری یا ڈیٹا خودمختاری کے بارے میں امتحانی سوالات اکثر CRR شامل کرتے ہیں۔

## مشقیں

**مشق 1 — یاد کریں**

اپنے الفاظ میں: S3 object کیا ہے؟ S3 bucket کیا ہے؟ EC2 instance کی مقامی ڈسک پر فائلیں محفوظ کرنے کے بجائے S3 میں محفوظ کرنا کیوں بہتر ہے؟

*(اشارہ: سوچیں کہ اگر instance terminate ہو جائے تو EC2 instance پر موجود فائلوں کا کیا ہوتا ہے۔ S3 کیا مختلف کرتا ہے؟)*

**مشق 2 — SAA-C03 منظر نامہ**

*منظر نامہ*: ایک میڈیا کمپنی documentary ویڈیوز بناتی ہے۔ انہیں اصل 4K فوٹیج (پروڈکشن کے دوران کثرت سے رسائی)، ترمیم شدہ فائنل کٹس (تقسیم کے لیے ماہانہ رسائی)، اور آرکائیو ماسٹرز (غیر معینہ مدت تک رکھے جاتے ہیں لیکن تعمیلی مقاصد کے لیے زیادہ سے زیادہ سال میں ایک بار رسائی) محفوظ کرنے کی ضرورت ہے۔ وہ ہر درجے کی رسائی کی ضروریات پوری کرتے ہوئے اسٹوریج لاگتیں کم سے کم کرنا چاہتے ہیں۔

کون سی اسٹوریج حکمتِ عملی ان کی ضروریات کو **بہترین** طریقے سے پورا کرتی ہے؟

A) اصل فوٹیج کو S3 Standard میں، فائنل کٹس کو S3 Standard-IA میں، اور آرکائیوز کو S3 Glacier Deep Archive میں محفوظ کریں  
B) مستقل کارکردگی اور سادگی کے لیے تمام مواد کو S3 Standard میں محفوظ کریں  
C) تیز ترین رسائی کے لیے تمام مواد کو EC2 instance اسٹوریج پر محفوظ کریں  
D) لاگتیں کم سے کم کرنے کے لیے تمام مواد کو S3 Glacier Deep Archive میں محفوظ کریں

**اشارہ 1**: مختلف فائلوں کے مختلف رسائی کے نمونے ہیں۔ S3 مختلف رسائی کی تعدد کے لیے مختلف storage classes پیش کرتا ہے۔ کون سی کلاس "کثرت سے رسائی" سے میل کھاتی ہے؟

**اشارہ 2**: "زیادہ سے زیادہ سال میں ایک بار" رسائی کیے جانے والے آرکائیوز کو فوری بازیابی کی ضرورت نہیں۔ کون سی storage class کم سے کم لاگت پر طویل مدتی archival کے لیے ڈیزائن کی گئی ہے؟

**اشارہ 3**: ہر درجے کی رسائی کی تعدد کو مناسب storage class سے ملائیں۔ کثرت سے رسائی = Standard۔ ماہانہ = Standard-IA۔ سال میں ایک بار = Glacier Deep Archive۔

**جواب**: A

**وضاحت**: یہ حکمتِ عملی درست طریقے سے ہر ڈیٹا درجے کو مناسب S3 storage class سے ملاتی ہے۔ کثرت سے رسائی کی جانے والی اصل فوٹیج بغیر بازیابی فیس کے فوری رسائی کے لیے Standard میں رہتی ہے۔ ماہانہ رسائی کی جانے والی فائنل کٹس Standard-IA میں جاتی ہیں (کم اسٹوریج لاگت، سستی بازیابی فیس)۔ سالانہ ایک بار رسائی کیے جانے والے آرکائیوز کم سے کم ممکنہ اسٹوریج لاگت کے لیے Glacier Deep Archive میں جاتے ہیں۔

**B کیوں نہیں؟** سب کچھ Standard میں محفوظ کرنا سادہ لیکن مہنگا ہے۔

**C کیوں نہیں؟** EC2 instance اسٹوریج عارضی ہے اور طویل مدتی میڈیا اسٹوریج کے لیے موزوں نہیں۔ اگر instance terminate ہو جائے، تو تمام مواد ضائع ہو جاتا ہے۔

**D کیوں نہیں؟** Glacier Deep Archive کی بازیابی کے اوقات 12 گھنٹوں تک ہیں۔ کثرت سے رسائی کی جانے والی پروڈکشن فوٹیج وہاں محفوظ کرنے سے پروڈکشن کام ناممکن ہو جائے گا۔

*SAA-C03 ڈومین 3 — ٹاسک 3.1 / ڈومین 4 — ٹاسک 4.1*

**مشق 3 — آرکیٹیکچر چیلنج** *(اختیاری)*

Nimbus گاہک کی اپ لوڈ کردہ آرڈر تصاویر S3 میں محفوظ کرتا ہے۔ ایک ڈیٹا تحفظ ضابطہ تقاضا کرتا ہے کہ گاہک کی تصاویر 7 سال کے لیے محفوظ کی جانی چاہئیں لیکن اس کے بعد حذف کی جا سکتی ہیں۔ ٹیم پچھلے سالوں کی پرانی تصاویر محفوظ کرنے کی لاگت بھی کم سے کم کرنا چاہتی ہے۔

اس ضرورت کے لیے ایک S3 اسٹوریج حکمتِ عملی ڈیزائن کریں۔ آپ کون سی storage classes استعمال کریں گے، اور آپ ان کے درمیان کب منتقل ہوں گے؟ آپ حذف کرنے کی ضرورت کے بارے میں کیا کریں گے؟

*(اشارہ: lifecycle policies کے بارے میں سوچیں۔ کوئی واحد درست جواب نہیں ہے — لاگت بمقابلہ بازیابی وقت کے ٹریڈ آفس پر استدلال کریں۔)*
