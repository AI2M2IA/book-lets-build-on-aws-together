# باب ۲۱: کوڈ کے لیے شپنگ کنٹینر

"یہ میری مشین پر کام کرتا ہے۔"

Leo نے یہ بات بلند آواز میں کہنا چھوڑ دیا تھا۔ یہ دفاع نہیں تھا — یہ تشخیص تھا۔ اور اس بار تشخیص پروڈکشن EC2 انسٹینس نمبر تین تھی، جسے چھ ہفتے پہلے ایک لائبریری پیچ ملی تھی جس کی کسی نے دستاویز نہیں کی تھی، جو دوسری دو انسٹینسز کو نہیں ملی تھی، اور جو اب ایک بگ کا سبب بن رہی تھی جو صرف وہاں موجود تھی، اس ایک انسٹینس میں، ہر جگہ نادیدہ۔

اس نے گزشتہ رات اسے ڈھونڈنے میں تین گھنٹے گزارے تھے۔

"ہر بار جب ہم ڈیپلوائے کرتے ہیں،" اس نے اگلی صبح کہا، "ہم متعدد انسٹینسز میں ہم آہنگی کرتے ہیں۔ نئی ورژن، مختلف انحصارات۔ اسٹیجنگ میں کام کرتا ہے، پروڈکشن میں ٹوٹ جاتا ہے کیونکہ ماحول الگ ہو گئے ہیں۔"

"کیونکہ کسی نے انسٹینس تین پر پیکج اپڈیٹ کیا دوسروں کو اپڈیٹ کیے بغیر،" Priya نے کہا۔ بے رحمی سے نہیں۔

"مجھے ایک مخصوص ورژن کی ضرورت تھی—"

"میں جانتی ہوں،" اس نے کہا۔ "اور اب انسٹینس تین کی انسٹینس ایک اور دو سے مختلف تاریخ ہے۔ یہ ترتیب کا بہاؤ ہے۔ خاموش رہتا ہے جب تک کہ نہ ہو۔"

Lambda نے Nimbus کی چھوٹی سروسز کے لیے بیکار سرور کا مسئلہ حل کر دیا تھا۔ لیکن مرکزی API — جو تمام آرڈر ٹریفک اٹھاتی تھی — ابھی بھی EC2 پر تھی۔ اور EC2 انسٹینسز، فنکشنز کے برعکس، تاریخ جمع کرتی تھیں۔

"اصل حل کیا ہے؟" Maya نے پوچھا۔

"سرورز کو مستقل چیزیں سمجھنا بند کریں جنہیں آپ ترتیب دیتے ہیں،" Priya نے کہا۔ "انہیں یکجہتی اکائیاں سمجھنا شروع کریں جنہیں آپ بدلتے ہیں۔"

ایک مثال ہے جو یہ اتنی درستگی سے سمجھاتی ہے کہ یہ سافٹ ویئر کنٹینرز کی تقریباً ہر وضاحت میں آتی ہے۔ یہ ۱۹۵۶ سے ہے، اور اس کا سافٹ ویئر سے کوئی تعلق نہیں ہے۔ جواب، جب کسی نے آخرکار پوچھا "مختلف کیریئرز پر بھروسے کے ساتھ سامان بھیجنے کا حل کیا ہے؟"، تھا: کنٹینر کو معیاری بنائیں۔ صرف مواد نہیں، ڈبہ بھیجیں۔

**کنٹینر کیا ہے؟**

ایک **کنٹینر** ایک ہلکا، قابل نقل یونٹ ہے جو آپ کی ایپلی کیشن کو اسے چلانے کے لیے درکار ہر چیز کے ساتھ پیک کرتا ہے: رن ٹائم (Python 3.11، Node.js 20، Java 17)، لائبریریاں اور انحصارات، ترتیب فائلیں، اور ایپلی کیشن کوڈ خود۔

ایک ورچوئل مشین کے برعکس (جو پورے کمپیوٹر کی نقل اتارتی ہے، آپریٹنگ سسٹم کرنل سمیت)، کنٹینر ہوسٹ OS کرنل شیئر کرتا ہے جبکہ باقی سب کو الگ تھلگ رکھتا ہے۔ یہ کنٹینرز کو شروع ہونے میں تیز (سیکنڈ، کبھی کبھی ملی سیکنڈ) اور چھوٹا (گیگا بائٹس نہیں، میگا بائٹس) بناتا ہے۔

سب سے مقبول کنٹینر ٹیکنالوجی **Docker** ہے۔ Docker امیج خاکہ ہے — ایپلی کیشن اور اس کے ماحول کا ایک سنیپ شاٹ۔ Docker کنٹینر اس امیج کی چلتی ہوئی مثال ہے۔

اہم خاصیت: **ناقابل تبدیلی**۔ آج بنایا گیا ایک امیج کسی بھی ہوسٹ پر یکساں طریقے سے چلے گا جو Docker کو سپورٹ کرتا ہو — ایک لیپ ٹاپ، ایک EC2 انسٹینس، ایک مختلف ڈیٹا سینٹر میں سرور۔ ماحول بیک ان ہے۔ ترتیب کا بہاؤ ناممکن ہے۔

"تو EC2 انسٹینس پر کیا انسٹال ہے اس کی فکر کرنے کے بجائے،" Leo نے کہا، "ہم ایک امیج بناتے ہیں جس میں سب کچھ ہوتا ہے۔ امیج ہر جگہ ایک ہی طرح چلتا ہے۔"

"اور اگر آپ اسے مقامی طور پر ٹیسٹ کرنا چاہیں، تو آپ وہی امیج چلاتے ہیں،" Priya نے شامل کیا۔ "مزید 'یہ میری مشین پر کام کرتا ہے' نہیں۔"

**Amazon ECS: آرکیسٹریٹر**

ایک کنٹینر چلانا آسان ہے۔ متعدد ہوسٹس پر درجنوں کنٹینرز چلانا، ان کے درمیان ٹریفک روٹ کرنا، ناکام کنٹینرز کو دوبارہ شروع کرنا، بغیر ڈاؤن ٹائم کے نئی ورژنز ڈیپلوائے کرنا — اس کے لیے ایک **آرکیسٹریٹر** درکار ہے۔

**Amazon ECS (Elastic Container Service)** AWS کی منظم کنٹینر آرکیسٹریشن سروس ہے۔ آپ تعریف کرتے ہیں:

- **کام کی تعریف**: کون سا کنٹینر امیج چلانا ہے، کتنا CPU اور میموری، کیا ماحول متغیر، کون سے پورٹ ظاہر کریں
- **سروس**: کتنی کاپیاں کام چلانی ہیں، ناکامیوں اور ڈیپلوائمنٹ کو کیسے سنبھالنا ہے
- **کلسٹر**: بنیادی کمپیوٹ بنیادی ڈھانچہ

ECS باقی سنبھالتا ہے: کاموں کو دستیاب صلاحیت پر رکھنا، ناکام کاموں کو دوبارہ شروع کرنا، ڈیپلوائمنٹ کے دوران کنکشن ہٹانا، صحت مند کاموں کو لوڈ بیلنسر کے ساتھ رجسٹر کرنا۔

Nimbus کے لیے، API دستی طور پر منظم ڈیپلوائمنٹ کے ساتھ EC2 انسٹینسز سے ECS پر منتقل ہوئی۔ ہر نئی ڈیپلوائمنٹ نے **Amazon ECR (Elastic Container Registry)** — AWS کی منظم کنٹینر رجسٹری — میں ایک نیا Docker امیج پش کیا اور ECS نے اسے صفر ڈاؤن ٹائم کے ساتھ تمام کاموں میں رول آؤٹ کیا۔

**Fargate بمقابلہ EC2 لانچ ٹائپ**

ECS کنٹینرز دو طریقوں سے چلا سکتا ہے:

**EC2 لانچ ٹائپ**: آپ بنیادی EC2 انسٹینسز منظم کرتے ہیں۔ آپ انسٹینسز کو پیچ کرنے، انہیں صحیح سائز دینے، اور یہ یقینی بنانے کے ذمہ دار ہیں کہ آپ کے کنٹینرز کے لیے کافی صلاحیت ہو۔ زیادہ کنٹرول، زیادہ ذمہ داری۔

**Fargate (کنٹینرز کے لیے سرورلیس کمپیوٹ)**: AWS بنیادی بنیادی ڈھانچے کو مکمل طور پر منظم کرتا ہے۔ آپ فی کام CPU اور میموری بتاتے ہیں؛ Fargate خودبخود صحیح صلاحیت فراہم کرتا ہے۔ کوئی EC2 انسٹینسز منظم کرنے کی ضرورت نہیں۔ آپ فی vCPU-سیکنڈ اور میموری کے GB-سیکنڈ کی ادائیگی کرتے ہیں۔

Fargate "سرورلیس کنٹینرز" کا نمونہ ہے — آپ کو سرور منظم کیے بغیر کنٹینرز کا ماحولیاتی تنہائی ملتی ہے۔ قیمت: بنیادی انسٹینس ترتیب پر کم کنٹرول اور تھوڑی زیادہ فی یونٹ لاگت۔

Nimbus کے لیے: API سروس کے لیے Fargate۔ وہ کنٹینرز کے لیے EC2 انسٹینسز منظم نہیں کرنا چاہتے تھے۔

**Amazon EKS: جب آپ کو Kubernetes چاہیے**

**Kubernetes** ایک اوپن سورس کنٹینر آرکیسٹریشن سسٹم ہے — بنیادی طور پر پیمانے پر کنٹینرز منظم کرنے کا صنعتی معیار۔ یہ طاقتور، قابل توسیع، اور پیچیدہ ہے۔

**Amazon EKS (Elastic Kubernetes Service)** AWS کی منظم Kubernetes سروس ہے۔ یہ آپ کے لیے Kubernetes کنٹرول پلین (منظمت کی پرت) چلاتا ہے، جبکہ آپ ورکر نوڈز منظم کرتے ہیں (یا ان کے لیے بھی Fargate استعمال کریں)۔

آپ EKS بمقابلہ ECS کب استعمال کریں؟

**ECS استعمال کریں** اگر:

- آپ بنیادی طور پر AWS پر ہیں اور آسان، زیادہ AWS-مقامی تجربہ چاہتے ہیں
- آپ کی ٹیم کے پاس موجودہ Kubernetes مہارت نہیں ہے
- آپ کم آپریشنل بوجھ چاہتے ہیں

**EKS استعمال کریں** اگر:

- آپ کو Kubernetes-مخصوص خصوصیات چاہیے (Custom Resource Definitions، Helm چارٹس، Kubernetes ماحولیاتی نظام)
- آپ کی ٹیم پہلے سے Kubernetes جانتی ہے
- آپ ایک ہائبرڈ ماحول چلا رہے ہیں (کچھ آن پریمیسز، کچھ AWS میں) اور آرکیسٹریشن کی یکساں پرت چاہتے ہیں
- آپ کے کام کی ضروریات Kubernetes کی توسیعیت سے میل کھاتی ہیں

"ہمیں کون سا استعمال کرنا چاہیے؟" Maya نے پوچھا۔

"ECS،" Priya نے فوراً کہا۔ "ہمارے پاس Kubernetes مہارت نہیں ہے۔ ECS ہر وہ کام کرتا ہے جو ہمیں چاہیے۔ ابھی Kubernetes شامل کرنا کوئی عملی فائدہ نہ ہونے کے ساتھ آپریشنل پیچیدگی شامل کرنا ہوگا۔"

"اگر ہم ECS سے آگے نکل جائیں تو ہم بعد میں EKS میں منتقل ہو سکتے ہیں،" Leo نے شامل کیا۔

یہ ایک درست سینئر جواب ہے: وہ آسان ٹول چنیں جو آپ کی موجودہ ضروریات کے لیے موزوں ہو۔

**کنٹینرز ڈیپلوائمنٹ کو کیسے بدلتے ہیں**

کنٹینرز سے پہلے، Nimbus API کی نئی ورژن ڈیپلوائے کرنے کا مطلب تھا:

1. ہر EC2 انسٹینس پر SSH
2. Git سے تازہ ترین کوڈ کھینچیں
3. انحصارات انسٹال/اپڈیٹ کریں
4. ایپلی کیشن عمل دوبارہ شروع کریں
5. صحت کی تصدیق کریں
6. اگلی انسٹینس پر جائیں

یہ غلطیوں کا شکار اور سست تھا۔ ہم آہنگی درکار تھی۔ اگر مرحلہ ۳ انسٹینس ۴ پر ناکام ہو جائے، تو آپ کے پاس ملی جلی ڈیپلوائمنٹ تھی جہاں کچھ انسٹینسز پرانی ورژن چلا رہی تھیں اور کچھ نئی ورژن چلانے میں ناکام ہو رہی تھیں۔

ECS اور کنٹینرز کے ساتھ:

1. نیا Docker امیج بنائیں (CI/CD پائپ لائن میں خودکار)
2. ECR پر پش کریں
3. ECS سروس کو نئی امیج ورژن استعمال کرنے کے لیے اپڈیٹ کریں

ECS رولنگ ڈیپلوائمنٹ سنبھالتا ہے: نئے امیج کے ساتھ نئے کام شروع کرتا ہے، ان کے صحت مند ہونے کا انتظار کرتا ہے، پھر پرانے کام بند کرتا ہے۔ صفر ڈاؤن ٹائم ڈیپلوائمنٹ، خودکار۔

اگر نئی ورژن صحت جانچ میں ناکام ہو جائے، ECS ڈیپلوائمنٹ روک دیتا ہے اور پرانی ورژن ٹریفک سرو کرتی رہتی ہے۔

## طاقت اور حدود

**کنٹینرز**:

- ماحولیاتی عدم استواری ختم ("یہ میری مشین پر کام کرتا ہے")
- تیز، قابل اعتماد ڈیپلوائمنٹ ممکن
- ناقابل تبدیلی — وہی امیج ہر جگہ یکساں طریقے سے چلتا ہے
- موثر — VMs سے ہلکا، تیزی سے شروع ہوتا ہے

**ECS**:

- AWS-مرکوز کام کے لیے Kubernetes سے آسان
- مضبوط AWS انضمام (IAM، ALB، CloudWatch، Secrets Manager)
- Fargate آپشن EC2 منظمت کو مکمل طور پر ختم کر دیتا ہے

**EKS**:

- مکمل Kubernetes مطابقت — پورا ماحولیاتی نظام استعمال کریں
- ہائبرڈ ماحول یا Kubernetes مہارت والی ٹیموں کے لیے بہتر
- ECS سے زیادہ پیچیدہ سیٹ اپ اور آپریشن

**جہاں پیچیدہ ہو جاتا ہے**:

- کنٹینر امیجز بنانے اور ورژن کرنے کی ضرورت ہے — CI/CD پائپ لائن درکار ہے
- کنٹینرز میں ڈیبگنگ روایتی عمل میں ڈیبگنگ سے مختلف ٹولنگ درکار ہے
- حالت والے کنٹینرز (کنٹینرز میں ڈیٹابیس) محتاط مستقل اسٹوریج ترتیب درکار کرتے ہیں
- کنٹینرز کے درمیان نیٹ ورکنگ (سروس سے سروس مواصلت) کنٹینر نیٹ ورکنگ تصورات کو سمجھنے کی ضرورت ہے

## خلاصہ

- **کنٹینرز** ایپلی کیشن کوڈ، رن ٹائم، اور انحصارات کو ایک ساتھ پیک کرتے ہیں — ہر جگہ یکساں طریقے سے چلتے ہیں۔
- **Docker** معیاری کنٹینر ٹیکنالوجی ہے۔ امیجز خاکے ہیں؛ کنٹینرز چلتی ہوئی مثالیں ہیں۔
- **ECR (Elastic Container Registry)** AWS کی منظم Docker رجسٹری ہے — اپنی امیجز یہاں محفوظ اور ورژن کریں۔
- **ECS (Elastic Container Service)** کنٹینرز آرکیسٹریٹ کرتا ہے۔ آپ کام اور سروسز تعریف کرتے ہیں؛ ECS جگہ اور لائف سائیکل منظم کرتا ہے۔
- **Fargate** کنٹینرز کے لیے سرورلیس کمپیوٹ ہے — کوئی EC2 انسٹینسز منظم کرنے کی ضرورت نہیں۔
- **EKS (Elastic Kubernetes Service)** منظم Kubernetes ہے — ان ٹیموں کے لیے جن کو Kubernetes خصوصیات یا مطابقت کی ضرورت ہے۔
- AWS پر آسانی کے لیے ECS چنیں؛ Kubernetes ماحولیاتی نظام کی مطابقت کے لیے EKS چنیں۔

- **ECS بمقابلہ EKS اشارے**: امتحانی منظرنامے جن میں "Kubernetes،" "Helm،" "موجودہ Kubernetes مہارت،" یا "کثیر کلاؤڈ کنٹینر آرکیسٹریشن" ذکر ہو → EKS۔ باقی سب → ECS۔
- **Fargate بمقابلہ EC2 لانچ ٹائپ**: "کنٹینرز کے لیے EC2 انسٹینسز منظم نہیں کرنا چاہتے،" "سرورلیس کنٹینرز،" "کوئی بنیادی ڈھانچہ منظمت نہیں" → Fargate۔ "مخصوص انسٹینس ٹائپس چاہیے،" "GPU کام،" "باریک بین انسٹینس کنٹرول" → EC2 لانچ ٹائپ۔
- **ECS کام کردار**: EC2 انسٹینس کردار کی طرح، ECS کاموں کے IAM کردار ہیں۔ ہر کام کی مختلف اجازتیں ہو سکتی ہیں۔ امتحانی منظرنامہ: "کنٹینر کو S3 سے پڑھنا ہے" → کام کی تعریف میں IAM کردار منسلک کریں۔
- **ECR امیج اسکیننگ**: ECR معروف کمزوریوں (CVEs) کے لیے کنٹینر امیجز اسکین کر سکتا ہے۔ امتحانی اشارہ: "سیکیورٹی کمزوریوں کے لیے کنٹینرز اسکین کریں" → ECR امیج اسکیننگ۔
- **بلیو/گرین ڈیپلوائمنٹ**: ECS CodeDeploy انضمام کے ذریعے بلیو/گرین ڈیپلوائمنٹ سپورٹ کرتا ہے۔ خودکار رول بیک کے ساتھ صفر ڈاؤن ٹائم ڈیپلوائمنٹ۔ امتحانی پیٹرن: "خودکار رول بیک کے ساتھ بغیر ڈاؤن ٹائم ڈیپلوائے کریں" → ECS + CodeDeploy بلیو/گرین۔
- **ECS سروس آٹو اسکیلنگ**: CPU، میموری، یا حسب ضرورت CloudWatch میٹرکس کی بنیاد پر کاموں کی تعداد پیمانہ بڑھائیں۔ چلتے ہوئے کاموں کی صحیح تعداد تک ٹریفک روٹ کرنے کے لیے ALB کے ساتھ کام کرتا ہے۔

## مشقیں

**مشق ۱ — یاد کریں**

Docker امیج اور Docker کنٹینر کے درمیان فرق سمجھائیں۔ ECS اور ECR کے درمیان فرق سمجھائیں۔

*(اشارہ: امیج کنٹینر سے وہی تعلق ہے جو نسخہ پکے ہوئے کھانے سے ہے۔ ECR امیجز محفوظ کرتا ہے؛ ECS انہیں چلاتا ہے۔)*

**مشق ۲ — امتحانی مشق**

*منظرنامہ*: ایک کمپنی کے پاس مائیکروسروسز ایپلی کیشن ہے جو فی الحال دستی طور پر منظم EC2 انسٹینسز پر چل رہی ہے۔ ٹیم کو غیر مستقل ڈیپلوائمنٹ سے مشکل ہے — مختلف EC2 انسٹینسز کے مختلف لائبریری ورژن ہیں، جو مشکل سے دوبارہ پیدا ہونے والے بگز کا سبب بنتے ہیں۔ وہ بنیادی سرورز منظم کرنے کے آپریشنل بوجھ کو کم کرتے ہوئے ڈیپلوائمنٹ معیاری بنانا چاہتے ہیں۔ ٹیم کے پاس کوئی Kubernetes تجربہ نہیں ہے۔

کون سا حل ان ضروریات کو بہترین طریقے سے پورا کرتا ہے؟

A) EC2 پر AWS Systems Manager Patch Manager کے ساتھ ڈیپلوائے کریں تاکہ انسٹینسز مستقل رہیں  
B) Docker کے ساتھ ایپلی کیشن کنٹینرائز کریں؛ Fargate لانچ ٹائپ کے ساتھ Amazon ECS استعمال کریں  
C) Docker کے ساتھ ایپلی کیشن کنٹینرائز کریں؛ خود منظم نوڈ گروپس کے ساتھ Amazon EKS استعمال کریں  
D) AWS Elastic Beanstalk کا استعمال ڈیپلوائمنٹ اور انسٹینس ترتیب خودبخود منظم کرنے کے لیے کریں

**اشارہ ۱**: کنٹینرز "غیر مستقل ماحول" کا مسئلہ براہ راست حل کرتے ہیں۔ کون سے آپشن کنٹینرز استعمال کرتے ہیں؟

**اشارہ ۲**: "سرورز منظم کرنے کے آپریشنل بوجھ کو کم کریں" → Fargate (کوئی EC2 منظمت نہیں) بمقابلہ خود منظم نوڈز (EC2 ابھی بھی منظم کریں)۔

**اشارہ ۳**: "کوئی Kubernetes تجربہ نہیں" → EKS ECS سے زیادہ آپریشنل پیچیدگی ہے۔

**جواب**: B

**وضاحت**: Docker کے ساتھ کنٹینرائزنگ یقینی بناتی ہے کہ ہر ڈیپلوائمنٹ ایک ہی انحصارات کے ساتھ ایک ہی امیج استعمال کرے — ترتیب کے بہاؤ کو ختم کرتے ہوئے۔ Fargate کے ساتھ ECS مطلب ہے کوئی EC2 انسٹینسز منظم نہیں کرنی۔ ٹیم ایپلی کیشن کوڈ اور کنٹینر تعریفوں پر توجہ دیتی ہے، سرور دیکھ بھال پر نہیں۔ Kubernetes تجربہ نہ ہونے والی ٹیموں کے لیے ECS (EKS نہیں) مناسب ہے۔

**A کیوں نہیں؟** Patch Manager EC2 انسٹینسز کو اپڈیٹ رکھتا ہے لیکن ایپلی کیشنز کے درمیان لائبریری ورژن عدم استواری حل نہیں کرتا۔ بنیادی مسئلہ (مختلف انسٹینسز پر مختلف کوڈ ماحول) باقی رہتا ہے۔

**C کیوں نہیں؟** خود منظم نوڈ گروپس کے ساتھ EKS EC2 انسٹینسز منظم کرنے *اور* Kubernetes سیکھنے کی ضرورت ہے۔ دونوں میں سے کوئی بھی ضروریات کے ساتھ ہم آہنگ نہیں ہے۔

**D کیوں نہیں؟** Elastic Beanstalk EC2 پر ایپلی کیشن ڈیپلوائمنٹ منظم کرتا ہے لیکن کنٹینرز استعمال کیے بغیر بنیادی ماحولیاتی عدم استواری حل نہیں کرتا۔ Beanstalk بطور ڈیفالٹ Docker امیجز استعمال نہیں کرتا (اگرچہ اسے ترتیب دیا جا سکتا ہے)۔

*SAA-C03 ڈومین: لچکدار آرکیٹیکچر ڈیزائن — کام ۲.۱*

**مشق ۳ — آرکیٹیکچر چیلنج** *(اختیاری)*

Nimbus مونولتھک API کو تین مائیکروسروسز میں تقسیم کر رہا ہے: آرڈر سروس، مینو سروس، اور اطلاع سروس۔ ہر سروس کے مختلف پیمانہ بڑھانے کی ضروریات ہیں (آرڈر سروس ٹریفک کے ساتھ پیمانہ بڑھاتی ہے؛ مینو سروس زیادہ تر صرف پڑھنے والی اور مستقر ہے؛ اطلاع سروس میں اچانک ابھار ہیں)۔

ان تین سروسز کے لیے ECS آرکیٹیکچر ڈیزائن کریں۔ سروس سے سروس مواصلت کیسے سنبھالیں گے؟ کیا آپ ایک ECS کلسٹر استعمال کریں گے یا تین؟ ہر سروس کے لیے آٹو اسکیلنگ کیسے مختلف طریقے سے ترتیب دیں گے؟

*(کوئی واحد درست جواب نہیں ہے۔ مقصد ECS پر مائیکروسروسز آرکیٹیکچر کی مشق کرنا ہے۔)*
