# باب 1: جب آپ مالک بھی ہو سکتے ہیں تو کرائے پر کیوں؟

Tom رات سے سوال لے کر بیٹھا تھا۔ اس نے اسے نوٹ بک میں لکھا تھا، پھر کاٹ دیا، پھر دوبارہ لکھا۔

جب Leo اور Priya اگلی صبح آئے — ہاتھ میں کافی، کسی غیر متعلقہ بات پر بحث کرتے ہوئے — Tom پہلے سے وائٹ بورڈ پر کھڑا تھا۔ تیسرا اختیار ابھی بھی وہاں تھا، ہاتھ نہیں لگایا گیا۔ کسی بادل کی شکل، کسی نے بنائی جس نے مان لیا تھا کہ وہ اس کا مطلب نہیں جانتا۔

"مجھے چاہیے کہ کوئی کچھ مجھے سمجھائے،" Tom نے مڑے بغیر کہا۔ "اگر ہم Amazon سے کمپیوٹر کرائے پر لیتے ہیں بجائے اپنے خریدنے کے — تو یہ *سستا* کیوں ہوگا؟"

کمرہ خاموش ہو گیا۔ یہ اس قسم کا سوال تھا جو آسان لگتا ہے اور ہے نہیں۔

"کیونکہ،" Leo نے شروع کیا۔

"نہیں،" Tom نے کہا۔ "میں سمجھنا چاہتا ہوں۔ صرف جواب سننا نہیں چاہتا۔ کرایہ مالکی سے سستا کیوں ہے؟"

**سرور مالک ہونے کا واضح مسئلہ**

تصور کریں کہ آپ ایک ریستوران کھولنے کا فیصلہ کرتے ہیں۔ Nimbus کی قسم نہیں — ایک عام ریستوران۔

آپ کے پہلے گاہک کے آنے سے پہلے، آپ کو میزیں چاہیے ہوں گی۔ کرسیاں۔ ایک باورچی خانہ۔ ایک چولہا۔ پلیٹیں۔ عملہ۔ آپ کو یہ سب پہلے دن چاہیے، چاہے آپ کا پہلا ہفتہ سست ہو، چاہے آپ کا لفظ پھیلنے سے پہلے تین مہینے روزانہ چھ گاہک آئیں۔

جسمانی سرور اسی طرح کام کرتے ہیں۔

اگر Nimbus اپنے سرور خریدتی ہے، تو انہیں وہ مقدار کے لیے خریدنی ہوگی جس کی وہ چوٹی پر توقع کرتے ہیں۔ سب سے مصروف جمعے کی رات جس کا وہ تصور کر سکتے ہیں۔ وہ وائرل لمحہ جہاں کوئی فوڈ بلاگر arepa کے بارے میں پوسٹ کرتا ہے اور دس ہزار لوگ بیک وقت آرڈر دینے کی کوشش کرتے ہیں۔

لیکن زیادہ تر وقت، یہ اتنا مصروف نہیں ہوتا۔ زیادہ تر وقت، وہ سرور وہاں بیٹھے رہتے ہیں، بجلی استعمال کرتے ہیں، تقریباً کچھ نہیں کرتے۔

"ہم ایسی صلاحیت کے لیے ادا کر رہے ہوں گے جو ہم استعمال نہیں کر رہے،" Maya نے کہا۔

"بالکل ٹھیک،" Tom نے کہا، جس نے سب کو حیران کیا کیونکہ وہی وہ تھا جس نے سوال پوچھا تھا۔

**کرائے کا ماڈل**

یہی ہے جو کلاؤڈ کمپیوٹنگ کو مختلف بناتا ہے۔

جب آپ AWS استعمال کرتے ہیں، آپ سرور نہیں خریدتے۔ آپ کمپیوٹنگ طاقت کرائے پر لیتے ہیں، اور صرف وہی ادا کرتے ہیں جو آپ استعمال کرتے ہیں۔ یہ ریستوران کی عمارت مالک ہونے کی بجائے کوئی جگہ کرائے پر لینے کے قریب ہے۔

اسے اس طرح سوچیں۔

اگر آپ کو پچاس لوگوں کے لیے سالگرہ کی پارٹی کرنی ہے، آپ یا تو پچاس لوگوں اور ان کی میزوں اور کرسیوں کے لیے کافی بڑا گھر خرید سکتے ہیں۔ یا آپ ہفتہ کو چار گھنٹے کے لیے ایک جگہ کرائے پر لے سکتے ہیں، بالکل اس جگہ اور وقت کے لیے ادا کریں جس کی آپ کو ضرورت ہے، اور جب پارٹی ختم ہو جائے تو چابیاں واپس کریں۔

جگہ اب بھی وہاں ہے جب آپ کو اس کی ضرورت ہو۔ جب کوئی اور چیز آتی ہے تو یہ دوبارہ دستیاب ہوتی ہے۔ آپ کو عمارت کا مینیجر رکھنا نہیں پڑا۔ آپ نے سال بھر اس کے لیے پراپرٹی ٹیکس ادا نہیں کیا۔

یہی کلاؤڈ ماڈل ہے۔ AWS کے پاس "جگہیں" ہیں۔ آپ جب ضرورت ہو آتے ہیں۔

**لیکن رکیں — اور بھی کچھ ہے**

"ٹھیک ہے،" Leo نے کہا، "لیکن اگر میری جگہ جل جائے تو؟"

اچھا جبلت۔ تاریک، لیکن اچھا۔

جب آپ اپنے سرور مالک ہوتے ہیں تو اس میں ایک خاموش مفروضہ ہے کہ *آپ* انہیں چلتے رکھنے کے ذمہ دار ہیں۔ اگر آپ کے دفتر کا سرور کسی بے ڈھنگے انٹرن سے گر جائے، تو آپ کی ویب سائٹ بند ہے۔ اگر عمارت بجلی کھو دیتی ہے، آپ کی ویب سائٹ بند ہے۔ اگر ہارڈ ڈرائیو فیل ہو جائے — اور ہارڈ ڈرائیوز ہمیشہ بالآخر فیل ہو جاتی ہیں — آپ کی ویب سائٹ بند ہے۔

AWS ڈیٹا سینٹر چلاتا ہے۔ بڑی، پیشہ ورانہ طور پر منظم سہولیات جن میں بیک اپ پاور، ریڈنڈنٹ نیٹ ورک کنیکشن، جسمانی سیکیورٹی، اور انجینیئرز کی ٹیمیں ہیں جن کا واحد کام ان مشینوں کو چلاتے رکھنا ہے۔

آپ صرف کمپیوٹنگ طاقت کرائے پر نہیں لے رہے۔ آپ قابل اعتماد ہونا کرائے پر لے رہے ہیں۔

"اس کی کتنی قیمت ہے؟" Tom نے پوچھا۔

ہم اس تک پہنچیں گے۔ کئی ابواب بعد، جب Tom کی آنکھیں چکرانا بند کر دیں گی۔

**تین چیزیں جو کلاؤڈ مختلف طریقے سے کرتا ہے**

آئیے اسے ٹھوس بنائیں۔ اپنے سرور چلانے اور کلاؤڈ فراہم کنندہ استعمال کرنے کے درمیان تین بنیادی فرق یہ ہیں۔

**1. آپ وہی ادا کرتے ہیں جو آپ استعمال کرتے ہیں۔**

کوئی سرور بے کار نہیں بیٹھا۔ کوئی پیشگی خریداری نہیں۔ اگر Nimbus کو پیر کی صبح صفر آرڈر ملتے ہیں، تو وہ تقریباً کچھ ادا نہیں کرتے۔ اگر نئے سال کی شام وہ مصروف ہو جاتے ہیں، تو AWS کے پاس خودکار طور پر صلاحیت تیار ہے۔

**2. کوئی اور ہارڈ ویئر سنبھالتا ہے۔**

AWS جسمانی مشینوں کی دیکھ بھال کرتا ہے۔ نیٹ ورکنگ کیبلز۔ پاور سپلائیز۔ کولنگ سسٹمز۔ Nimbus اس کے لیے کسی کو نہیں رکھتا۔ وہ اپنی ایپلیکیشن پر توجہ مرکوز کرتے ہیں، نہ کہ اس کے نیچے کے انفراسٹرکچر پر۔

**3. آپ فوری طور پر اسکیل اپ — اور ڈاؤن — کر سکتے ہیں۔**

یہ وہ ہے جسے مکمل طور پر سمجھنے میں تھوڑا وقت لگتا ہے۔ جسمانی سرورز کے ساتھ، اسکیل اپ کا مطلب نیا ہارڈ ویئر آرڈر کرنا، ڈیلیوری کے لیے ہفتوں انتظار کرنا، اسے سیٹ اپ کرنا ہے۔ AWS کے ساتھ، اسکیل اپ کا مطلب ایک بٹن کلک کرنا ہے (یا نظام کو خودبخود یہ کرنے دینا ہے)۔ اور جب آپ کو اضافی صلاحیت کی مزید ضرورت نہیں، آپ واپس اسکیل ڈاؤن کرتے ہیں۔ آپ ادائیگی بند کر دیتے ہیں۔

اس وضاحت کے دوران Priya خاموش تھی۔ اس کا ایک سوال تھا۔

"سیکیورٹی کے بارے میں کیا؟ ڈیٹا محفوظ رکھنے کا ذمہ دار کون ہے؟"

اور یہاں دلچسپ ہو جاتا ہے۔

**مشترکہ ذمہ داری کا ماڈل**

یہ AWS کے تمام سب سے اہم تصورات میں سے ایک ہے۔ ایک بار سمجھنے کے بعد یہ آسان ہے، لیکن یہ بہت سے لوگوں کو الجھاتا ہے — بشمول امتحان میں۔

AWS اور آپ سیکیورٹی کی مشترکہ ذمہ داری اٹھاتے ہیں۔ لیکن ہر فریق مختلف چیزوں کا ذمہ دار ہے۔

**AWS کلاؤڈ *کی* سیکیورٹی کا ذمہ دار ہے۔**

جسمانی ڈیٹا سینٹر۔ ہارڈ ویئر۔ نیٹ ورک انفراسٹرکچر۔ ہائپر وائزر جو ورچوئل مشینیں چلاتے ہیں۔ اگر کوئی AWS ڈیٹا سینٹر میں گھس جائے، تو یہ Amazon کا مسئلہ ہے۔

**آپ کلاؤڈ *میں* سیکیورٹی کے ذمہ دار ہیں۔**

آپ کا ڈیٹا۔ آپ کی ایپلیکیشن۔ آپ کے یوزر اکاؤنٹس اور کس کو کس تک رسائی ہے۔ جو کنفیگریشنز آپ چنتے ہیں۔ اگر کوئی آپ کا پاس ورڈ چراتا ہے اور آپ کے AWS اکاؤنٹ میں لاگ ان ہوتا ہے، تو یہ آپ کا مسئلہ ہے۔

Priya نے آہستہ سر ہلایا۔ "تو وہ عمارت کی حفاظت کرتے ہیں۔ ہم اندر موجود چیزوں کی حفاظت کرتے ہیں۔"

"بالکل ٹھیک،" Maya نے کہا۔

"تو اگر Leo ایک ایسا پورٹ کھول دے جو نہیں کھلنا چاہیے..."

"اب بھی ہمارا مسئلہ ہے،" Maya نے تصدیق کی، Leo کی طرف دیکھتے ہوئے۔

Leo اپنے لیپ ٹاپ پر کچھ ٹائپ کر رہا تھا اور سننے کا بہانہ کر رہا تھا۔

## طاقتیں اور حدود

کوئی اوزار کامل نہیں ہے۔ آئیں دونوں پہلوؤں کے بارے میں ایمانداری سے بات کریں۔

**کلاؤڈ کیوں بہترین ہے**:

- کوئی پیشگی ہارڈ ویئر اخراجات نہیں
- صرف وہی ادا کریں جو آپ استعمال کریں
- دونوں سمتوں میں فوری اسکیل کرتا ہے
- پیشہ ورانہ قابل اعتماد ہونا اور جسمانی سیکیورٹی
- سینکڑوں منظم سروسز (ڈیٹا بیس، قطاریں، مشین لرننگ، اور بہت کچھ) تک رسائی
  خود انہیں بنانے یا برقرار رکھنے کے بغیر

**جہاں یہ پیچیدہ ہو جاتا ہے**:

- اگر آپ دھیان نہ دیں تو اخراجات غیر متوقع ہو سکتے ہیں (Tom کا مستقبل کا کابوس)
- آپ اپنے انفراسٹرکچر کے لیے کسی تیسرے فریق پر انحصار کرتے ہیں — اگر آپ کے علاقے میں AWS کا کوئی آؤٹیج ہو، تو آپ کی سروس بھی متاثر ہوتی ہے
- سیکھنے کی تکلیف ہے۔ AWS کے پاس سینکڑوں سروسز ہیں۔ کون سا استعمال کرنا ہے یہ جاننے کے لیے تجربہ، یا اس جیسی ایک کتاب درکار ہے۔
- کلاؤڈ چھوڑتا ہوا ڈیٹا مہنگا ہو سکتا ہے۔ AWS سے بڑی مقدار میں ڈیٹا نکالنے کے پیسے لگتے ہیں۔ (ہم اسے باب 30 میں دوبارہ دیکھیں گے۔)

"تو ہم کنٹرول سہولت کے بدلے میں ترک کر رہے ہیں،" Tom نے کہا۔

"اور پیشگی لاگت کو جاری لاگت کے بدلے میں،" Maya نے مزید کہا۔

"اور سیکیورٹی کے حوالے سے کسی اور کا مسئلہ اپنے مسئلے کے بدلے میں،" Priya نے کہا۔

"لیکن ہم Leo کے ٹوٹے ہوئے سرور کو Amazon کے بہت-نہ-ٹوٹے ہوئے سرور کے بدلے میں بھی ترک کر رہے ہیں،" Leo نے کہا، جو ظاہراً پوری دیر سن رہا تھا۔

وہ بالکل غلط نہیں تھا۔

## خلاصہ

- کلاؤڈ وہ کمپیوٹنگ طاقت ہے جو آپ مالک ہونے کی بجائے کرائے پر لیتے ہیں۔
- AWS دنیا کا سب سے بڑا کلاؤڈ فراہم کنندہ ہے۔
- بنیادی فائدہ pay-as-you-go اسکیلنگ ہے: آپ صرف وہی ادا کرتے ہیں جو آپ استعمال کرتے ہیں، اور جیسی ضرورت ہو اوپر یا نیچے اسکیل کر سکتے ہیں۔
- AWS جسمانی انفراسٹرکچر سنبھالتا ہے۔ آپ اپنی ایپلیکیشن، اپنا ڈیٹا، اور اپنی کنفیگریشنز سنبھالتے ہیں۔ اس تقسیم کو **مشترکہ ذمہ داری ماڈل** کہتے ہیں۔
- کلاؤڈ ہمیشہ سستا یا آسان نہیں ہوتا — لیکن یہ شروع کرنے کی رکاوٹیں دور کرتا ہے، اور یہ اسکیلنگ کو اس طریقے سے ممکن بناتا ہے جو جسمانی سرور نہیں کر سکتے۔

## Exam Tips

*SAA-C03 ڈومین: کراس ڈومین — کلاؤڈ تصورات کی بنیادیں*

- **مشترکہ ذمہ داری ماڈل** امتحان میں باقاعدگی سے آتا ہے۔ یاد رکھیں: AWS کلاؤڈ *کی* سیکیورٹی کا ذمہ دار ہے (ہارڈ ویئر، ڈیٹا سینٹر، عالمی نیٹ ورک)۔ آپ کلاؤڈ *میں* سیکیورٹی کے ذمہ دار ہیں (ڈیٹا، شناختیں، ایپلیکیشن کنفیگریشن)۔
- **اہم باریکی**: تقسیم سروس کی قسم کے لحاظ سے بدلتی ہے۔ EC2 کے لیے (ایک ورچوئل مشین جسے آپ کنٹرول کرتے ہیں)، *آپ* آپریٹنگ سسٹم کو پیچ کرتے ہیں۔ RDS کے لیے (ایک منظم ڈیٹا بیس)، AWS ڈیٹا بیس انجن کو پیچ کرتا ہے۔ سروس جتنی زیادہ "منظم" ہو، اتنی زیادہ ذمہ داری AWS کی طرف منتقل ہوتی ہے۔ امتحانی منظر نامے کسی واقعے کا بیان کریں گے اور پوچھیں گے کہ ذمہ دار کون ہے — ہمیشہ پوچھیں "یہ سروس کتنی منظم ہے؟"
- کلاؤڈ *فوائد* کے بارے میں سوالات اکثر CapEx بمقابلہ OpEx کا امتحان لیتے ہیں۔ On-premises ہارڈ ویئر سرمایہ اخراجات ہے (CapEx — ایک بار خریدیں، وقت کے ساتھ قیمت کم کریں)۔ کلاؤڈ آپریشنل اخراجات ہے (OpEx — ماہانہ ادائیگی کریں)۔ AWS اخراجات CapEx سے OpEx میں منتقل کرتا ہے۔
- "لچک" — خودکار طور پر اوپر *اور نیچے* اسکیل کرنے کی صلاحیت — ایک بنیادی کلاؤڈ فائدہ ہے۔ آپ اسے امتحان میں "اسکیل ایبلٹی" کے ساتھ جوڑا ہوا دیکھ سکتے ہیں۔ لچک کا مطلب خودکار، مانگ کے مطابق دونوں سمتوں میں اسکیلنگ ہے۔ اسکیل ایبلٹی کا مطلب ہے کہ نظام بڑھ *سکتا* ہے، لیکن ضروری نہیں کہ خودکار طور پر سکڑے۔

## مشقیں

**مشق 1 — یاد کریں**

اپنے الفاظ میں: مشترکہ ذمہ داری ماڈل کی وضاحت کریں۔ کون کس کے لیے ذمہ دار ہے، اور یہ امتیاز کیوں اہم ہے؟

*(اشارہ: Priya کی مشابہت کے بارے میں سوچیں — عمارت کی حفاظت کون کرتا ہے، اور اندر موجود چیزوں کی حفاظت کون کرتا ہے؟)*

**مشق 2 — Exam Practice**

*منظر نامہ*: ایک کمپنی اپنی ویب ایپلیکیشن on-premises ڈیٹا سینٹر سے AWS میں منتقل کر رہی ہے۔ سیکیورٹی ٹیم اپنی ڈیٹا تحفظ پالیسیوں کی تعمیل برقرار رکھنے کے بارے میں فکرمند ہے۔ ایک نیا انجینیئر پوچھتا ہے: "اب جب ہم AWS پر ہیں، کیا Amazon ہماری تمام سیکیورٹی ضروریات سنبھالتا ہے؟"

درج ذیل میں سے کون سا سیکیورٹی ذمہ داریوں کی تقسیم کو **بہترین** طریقے سے بیان کرتا ہے؟

A) AWS ایپلیکیشن کلاؤڈ میں ہوسٹ ہونے کے بعد تمام سیکیورٹی کا مکمل ذمہ دار ہے  
B) گاہک تمام سیکیورٹی کا مکمل ذمہ دار ہے، بشمول جسمانی ڈیٹا سینٹر سیکیورٹی  
C) AWS بنیادی انفراسٹرکچر کی سیکیورٹی کا انتظام کرتا ہے؛ گاہک اپنے ڈیٹا، ایپلیکیشنز، اور کنفیگریشنز کی سیکیورٹی کا انتظام کرتا ہے  
D) سیکیورٹی کی ذمہ داریاں فی اکاؤنٹ مذاکرہ کی جاتی ہیں اور گاہک کے سروس ٹائر پر منحصر ہیں

**اشارہ 1**: سوچیں کہ AWS جسمانی طور پر کیا کنٹرول کرتا ہے بمقابلہ آپ کیا کنٹرول کرتے ہیں۔

**اشارہ 2**: AWS ڈیٹا سینٹر کا مالک ہے۔ آپ نے چنا کہ ان میں کیا رکھنا ہے اور اپنی ایپلیکیشن کو کیسے کنفیگر کرنا ہے۔

**اشارہ 3**: ہم نے اس باب میں ذمہ داریوں کی اس تقسیم کے لیے ایک مخصوص نام متعارف کرایا۔

**جواب**: C

**وضاحت**: AWS مشترکہ ذمہ داری ماڈل سیکیورٹی کو دو ڈومینز میں تقسیم کرتا ہے۔ AWS جسمانی انفراسٹرکچر — ڈیٹا سینٹر، ہارڈ ویئر، اور نیٹ ورکنگ — کو محفوظ کرتا ہے۔ گاہک اس کے اوپر ڈیپلائے کی گئی ہر چیز کو محفوظ کرتا ہے: ان کا ڈیٹا، ان کے رسائی کنٹرول، ان کی ایپلیکیشن کنفیگریشنز، اور ان کی نیٹ ورک سیٹنگز۔

**A کیوں نہیں؟** AWS کبھی بھی گاہک کی ایپلیکیشن سیکیورٹی کی مکمل ذمہ داری نہیں لیتا۔ جیسے ہی آپ کچھ کنفیگر کرتے ہیں، وہ کنفیگریشن آپ کی ذمہ داری بن جاتی ہے۔

**B کیوں نہیں؟** گاہک جسمانی ڈیٹا سینٹر سیکیورٹی کے ذمہ دار نہیں ہیں — یہ بالکل AWS استعمال کرنے کے فوائد میں سے ایک ہے۔

**D کیوں نہیں؟** مشترکہ ذمہ داری ماڈل ایک مقررہ فریم ورک ہے، مذاکرہ کا انتظام نہیں۔

*SAA-C03 ڈومین: کراس ڈومین — کلاؤڈ تصورات / مشترکہ ذمہ داری*

**مشق 3 — آرکیٹیکچر چیلنج** *(اختیاری)*

ایک دوست ایک نئی ایپ لانچ کر رہا ہے اور آپ کی رائے مانگتا ہے۔ وہ دو جسمانی سرور خریدنے (ایک ایپ کے لیے، ایک ڈیٹا بیس کے لیے) یا کلاؤڈ فراہم کنندہ استعمال کرنے کے درمیان فیصلہ کر رہا ہے۔ ان کی متوقع ٹریفک 10-100 یوزرز روزانہ ہے، لیکن تین مہینوں میں ایک لانچ ایونٹ ہے جو ایک ہی دن میں 10,000 یوزرز لا سکتا ہے۔
