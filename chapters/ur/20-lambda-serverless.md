**سرور ہمیشہ جواب نہیں ہوتا**

EC2 انسٹینسز مستقل ہوتی ہیں۔ آپ ایک شروع کریں اور یہ تب تک چلتی ہے جب تک آپ اسے بند نہ کریں — دن کے چوبیس گھنٹے، ہفتے کے سات دن، اصل استعمال سے قطع نظر۔ آپ کے ویب سرور کے لیے (جو ہر وقت ٹریفک سنبھالتا ہے)، یہ درست ہے۔ ای میل سروس کے لیے (جو ای میلوں کی بوچھاڑ بھیجتی ہے اور پھر گھنٹوں بیکار رہتی ہے)، یہ ضیاع ہے۔

Auto Scaling Group ای میل سروس کو غیر پیک اوقات میں ایک انسٹینس تک کم کر سکتا ہے۔ لیکن ایک انسٹینس پھر بھی مسلسل چلتی رہتی ہے۔

کیا ہوگا اگر کوڈ صرف تب چلے جب کام ہو؟

یہی **سرورلیس کمپیوٹنگ** کا بنیادی تصور ہے۔

**AWS Lambda: سرورز کے بغیر کوڈ**

**AWS Lambda** آپ کو واقعات کے جواب میں سرور فراہم یا منظم کیے بغیر کوڈ چلانے کی سہولت دیتا ہے۔ آپ ایک فنکشن اپلوڈ کریں، بتائیں کیا اسے ٹریگر کرتا ہے، اور Lambda اسے تب چلاتا ہے جب ٹریگر لگتا ہے۔

Lambda فنکشن:

- کوئی مستقل حالت نہیں ہوتی (ہر مرتبہ کا چلنا آزاد ہوتا ہے)
- ہر مرتبہ زیادہ سے زیادہ ۱۵ منٹ چلتا ہے
- خودبخود ۰ سے ہزاروں بیک وقت چلانے تک پیمانہ بڑھاتا ہے
- صرف تب بل ہوتا ہے جب چل رہا ہو (فی ۱ ms اجرا کے، اوپر کی طرف گول کر کے، مختص GB میموری فی)

جب کوئی ٹریگر نہیں، Lambda کچھ نہیں چارج کرتا۔ جب ٹریگر لگتے ہیں، Lambda چلتا ہے اور چارج کرتا ہے۔ جب ۱۰٬۰۰۰ ٹریگر بیک وقت لگتے ہیں، Lambda ۱۰٬۰۰۰ بیک وقت چلانے شروع کرتا ہے۔ پیمانہ بڑھنا خودکار اور تقریباً فوری ہے۔

**واقعہ ٹریگرز: Lambda کو کیا جگاتا ہے**

Lambda فنکشن خود نہیں چلتے — یہ واقعات کا جواب دیتے ہیں۔ عام ٹریگرز میں شامل ہیں:

- **SQS قطار**: قطار سے پیغامات پروسیس کریں۔ Lambda قطار کو پول کرتا ہے اور فنکشن کو پیغامات کے گروہوں کے ساتھ بلاتا ہے۔
- **API Gateway**: HTTP درخواست آتی ہے۔ API Gateway Lambda کو ٹریگر کرتا ہے۔ Lambda جواب تیار کرتا ہے۔
- **S3 واقعہ**: S3 میں کوئی فائل اپلوڈ ہوتی ہے۔ Lambda اسے پروسیس کرتا ہے (تصویر کا سائز بدلنا، CSV تجزیہ کرنا، دستاویز تصدیق کرنا)۔
- **SNS**: ایک موضوع پر پیغام شائع ہوتا ہے۔ Lambda کو اطلاع ملتی ہے۔
- **DynamoDB Streams**: DynamoDB میں ریکارڈ تبدیل ہوتا ہے۔ Lambda تبدیلی پروسیس کرتا ہے۔
- **CloudWatch Events (EventBridge)**: ایک شیڈول واقعہ (جیسے cron جاب) مقررہ وقت پر چلتا ہے۔
- **ALB**: لوڈ بیلنسر پر HTTP درخواست پہنچتی ہے۔ Lambda کچھ راستے سنبھال سکتا ہے۔

Nimbus کے لیے، ای میل سروس Lambda فنکشن بن گئی جو اپنی SQS قطار سے ٹریگر ہوتی تھی۔ جب قطار میں پیغام آتا ہے، Lambda پیغام کے مواد کے ساتھ بلایا جاتا ہے، SES (Simple Email Service) کے ذریعے ای میل بھیجتا ہے، اور ختم ہو جاتا ہے۔

صفر سرور۔ صفر بیکار وقت۔ بیکار ہونے پر صفر لاگت۔

**کولڈ سٹارٹ کا مسئلہ**

Lambda فنکشن **اجرائی ماحول** میں چلتے ہیں — چھوٹے، الگ تھلگ کنٹینر۔ جب فنکشن بلایا جاتا ہے:

1. AWS چیک کرتا ہے کہ آیا گرم اجرائی ماحول دستیاب ہے (جو حال ہی میں چلایا گیا ہو)
2. اگر گرم ہو: فنکشن فوری چلتا ہے
3. اگر ٹھنڈا ہو: AWS نیا اجرائی ماحول شروع کرتا ہے — آپ کا کوڈ ڈاؤنلوڈ کرتا ہے، رن ٹائم شروع کرتا ہے، آپ کا ابتدائی کوڈ چلاتا ہے — پھر فنکشن چلاتا ہے

**کولڈ سٹارٹ** رن ٹائم (Java اور .NET میں Python اور Node.js سے زیادہ لمبا کولڈ سٹارٹ ہوتا ہے) اور آپ کے کوڈ پیکج کے سائز کے لحاظ سے ۱۰۰ms سے کئی سیکنڈ تک تاخیر شامل کرتا ہے۔

غیر متزامن پروسیسنگ (ای میل بھیجنا، تصویر کا سائز بدلنا) کے لیے، کولڈ سٹارٹ صارفین کو نظر نہیں آتا۔

متزامن APIs (HTTP درخواستیں جہاں صارف جواب کا انتظار کر رہا ہو) کے لیے، کولڈ سٹارٹ کبھی کبھی سست جوابات کا سبب بن سکتا ہے۔

**تدارک**:

- **Provisioned concurrency**: مخصوص تعداد کے اجرائی ماحول پہلے سے گرم کریں۔ یہ ہمیشہ تیار رہتے ہیں۔ آپ اس کے لیے ادائیگی کرتے ہیں چاہے یہ درخواستیں پروسیس نہ کر رہے ہوں۔
- **چھوٹے پیکج سائز**: چھوٹا کوڈ تیزی سے شروع ہوتا ہے۔
- **وارم-اپ بلاوے**: فنکشنز کو گرم رکھنے کے لیے شیڈول شدہ پنگ (ایک عام لیکن غیر خوبصورت طریقہ)۔
- **صحیح رن ٹائم چنیں**: Python اور Node.js Java سے تیزی سے کولڈ سٹارٹ ہوتے ہیں۔

**Lambda کس چیز میں اچھا ہے (اور کس میں نہیں)**

Lambda ان کاموں کے لیے بہترین ہے:

- **واقعہ سے چلنے والی پروسیسنگ**: واقعات کا جواب دیں (فائل اپلوڈ، قطار پیغامات، شیڈول شدہ کام)
- **مختصر مدت کے کام**: ۱۵ منٹ کے اندر مکمل ہونے والی پروسیسنگ
- **اچانک، غیر متوقع ٹریفک**: Lambda فوری طور پر ۰ سے ہزاروں تک پیمانہ بڑھاتا ہے — پہلے سے کوئی انتظام نہیں
- **غیر معمولی آپریشن**: ایک رپورٹ جو روزانہ رات ۲ بجے چلتی ہے۔ صفائی کا کام جو ہفتہ وار چلتا ہے۔
- **گوند کوڈ**: چھوٹے فنکشن جو سروسز کے درمیان ڈیٹا منتقل کرتے ہیں

Lambda ان کاموں کے لیے ناموزوں ہے:

- **دیر تک چلنے والے عمل**: ۱۵ منٹ کی حد ایک پختہ دیوار ہے
- **حالت والی ایپلی کیشنز**: Lambda فنکشن ڈیزائن سے بے حال ہوتے ہیں — ہر بلاوا آزاد ہوتا ہے
- **زیادہ تھروپٹ، کم تاخیر APIs**: کولڈ سٹارٹ تاخیر کی چوٹیاں پیدا کر سکتا ہے؛ provisioned concurrency اس کو کم کرتا ہے لیکن لاگت بڑھاتا ہے
- **وہ ایپلی کیشنز جن کو مستقل کنکشن چاہیے**: Lambda آسانی سے ڈیٹابیس کنکشن پول برقرار نہیں رکھ سکتا (اگرچہ RDS Proxy جیسے کنکشن پولنگ ٹولز مدد کرتے ہیں)
- **روایتی ویب سرور**: ممکن ہے، لیکن فطری موزوں نہیں

"تو Lambda EC2 کا متبادل نہیں ہے،" Maya نے کہا۔ "یہ مختلف کاموں کے لیے مختلف ٹول ہے۔"

"Nimbus ویب API EC2 یا ECS پر رہتا ہے،" Leo نے تصدیق کی۔ "ای میل سروس، تصویر ری سائزر، رات کا رپورٹ جنریٹر، لاگ کلینر — یہ Lambda پر منتقل ہوتے ہیں۔"

**سرورلیس فلسفہ**

Lambda ایک وسیع تر تصور کا حصہ ہے: **سرورلیس** — ایسی ایپلی کیشنز بنانا جہاں آپ کوئی سرور منظم نہیں کرتے، صرف کوڈ۔

ایک مکمل سرورلیس Nimbus اسٹیک کچھ اس طرح نظر آ سکتی ہے:

- API Gateway + Lambda (EC2 ویب سرور کی بجائے)
- DynamoDB (RDS کی بجائے — بھی سرورلیس، کوئی سرور منظم نہیں)
- S3 (جامد اثاثے — فطری طور پر سرورلیس)
- SNS + SQS (میسجنگ — سرورلیس)
- Lambda (تمام پس منظر پروسیسنگ)

کشش: آپ کوڈ لکھتے ہیں؛ AWS باقی سب منظم کرتا ہے۔ کوئی پیچنگ نہیں، کوئی پیمانہ ترتیب نہیں، کوئی صلاحیت منصوبہ بندی نہیں۔

حقیقت: سرورلیس کی اپنی آپریشنل پیچیدگی ہے — تقسیم شدہ Lambda فنکشنز میں خرابی کا پتا لگانا، کولڈ سٹارٹ منظم کرنا، بیک وقت چلانے کی حدیں سمجھنا۔ یہ آسان نہیں، بس مختلف ہے۔

## طاقت اور حدود

**Lambda کیوں طاقتور ہے**:

- حقیقی ادائیگی-استعمال-کے-مطابق — بیکار ہونے پر صفر لاگت
- بغیر ترتیب کے خودکار پیمانہ بڑھنا
- کوئی سرور پیچ یا برقرار رکھنے کی ضرورت نہیں
- فراخ دل مفت ٹائر (ہر ماہ ۱۰ لاکھ درخواستیں، ہمیشہ کے لیے مفت)
- AWS کے باقی حصے کے ساتھ مضبوط انضمام

**جہاں یہ پیچیدہ ہو جاتا ہے**:

- کولڈ سٹارٹ حقیقی ہیں اور تاخیر سے حساس کام کے لیے احتیاط سے سنبھالنے کی ضرورت ہے
- ۱۵ منٹ کی اجرائی حد دیر تک چلنے والے کاموں کو خارج کرتی ہے
- ڈیبگنگ مشکل ہے — SSH کرنے کے لیے کوئی مستقل سرور نہیں
- بے حال ڈیزائن تمام حالت کو بیرونی بنانے کی ضرورت ہے (ڈیٹابیس، کیش، S3)
- بیک وقت چلانے کی حدیں (بنیادی طور پر فی اکاؤنٹ ۱٬۰۰۰ بیک وقت چلانے) پیمانے پر تھروٹل کر سکتی ہیں
- VPC سے جڑے Lambda فنکشنز میں اضافی تاخیر اور کولڈ سٹارٹ مسائل ہیں

## خلاصہ

- **AWS Lambda** واقعات کے جواب میں سرور منظم کیے بغیر کوڈ چلاتا ہے۔
- **استعمال کے مطابق ادائیگی**: فی بلاوے اور فی ۱ ms اجرا (اوپر کی طرف گول کر کے) بل ہوتا ہے۔ بیکار ہونے پر صفر لاگت۔
- خودبخود ۰ سے ہزاروں بیک وقت چلانے تک پیمانہ بڑھاتا ہے۔
- **کولڈ سٹارٹ**: جب کوئی گرم اجرائی ماحول موجود نہ ہو تو ابتدائی تاخیر۔ provisioned concurrency یا ہلکے رن ٹائم سے کم ہوتی ہے۔
- بہترین برائے: واقعہ سے چلنے والی، مختصر مدت، اچانک، یا غیر معمولی کام۔
- مناسب نہیں: دیر تک چلنے والے کام، حالت والی ایپلی کیشنز، زیادہ تھروپٹ کم تاخیر APIs بغیر provisioned concurrency۔
- **سرورلیس** ایک ڈیزائن فلسفہ ہے — آپ کوڈ منظم کرتے ہیں، بنیادی ڈھانچہ نہیں۔

## امتحانی تجاویز

*SAA-C03 ڈومین: لچکدار آرکیٹیکچر ڈیزائن (ڈومین ۲، کام ۲.۱)*

- **Lambda + S3**: کلاسک پیٹرن — S3 میں فائل اپلوڈ ہونا Lambda کو پروسیسنگ کے لیے ٹریگر کرتا ہے (تھمب نیل بنانا، وائرس اسکین، ڈیٹا تبدیلی)۔ کوئی سرور نہیں چاہیے۔
- **Lambda + SQS**: Lambda SQS کو پول کرتا ہے اور گروہوں میں پروسیس کرتا ہے۔ SQS ری ٹرائی/DLQ میکانیزم فراہم کرتا ہے۔ Lambda پروسیسنگ فراہم کرتا ہے۔
- **Lambda + API Gateway**: سرورلیس HTTP API۔ API Gateway روٹنگ، تصدیق، تھروٹلنگ سنبھالتا ہے۔ Lambda کاروباری منطق سنبھالتا ہے۔
- **کولڈ سٹارٹ اشارے**: "پہلی درخواست پر تاخیر کی چوٹیاں،" "غیر مستقل جواب کے اوقات" → کولڈ سٹارٹ۔ حل: provisioned concurrency (پیسے لگتے ہیں)، چھوٹا پیکج، ہلکا رن ٹائم۔
- **اجرائی حدیں**: زیادہ سے زیادہ ۱۵ منٹ۔ زیادہ سے زیادہ ۱۰GB میموری۔ بنیادی طور پر ۵۱۲MB /tmp عارضی اسٹوریج (۱۰GB تک قابل ترتیب)۔ یہ حدیں امتحانی منظرناموں میں آتی ہیں۔
- **Lambda concurrency**: بنیادی طور پر فی اکاؤنٹ ۱٬۰۰۰ بیک وقت چلانے (بڑھایا جا سکتا ہے)۔ **ریزرو شدہ concurrency**: گارنٹی دیں کہ ایک فنکشن کو مخصوص تعداد کے چلانے ملیں؛ دوسرے فنکشنز کو ان کے استعمال سے روکتا ہے۔ **Provisioned concurrency**: اجرائی ماحول کی تعداد پہلے سے گرم کریں۔
- **واقعہ ماخذ نقشہ سازی**: وہ Lambda خصوصیت جو SQS/DynamoDB Streams/Kinesis کو Lambda سے جوڑتی ہے۔ Lambda ماخذ کو پول کرتا ہے اور ریکارڈ کو گروہوں میں کرتا ہے۔

## مشقیں

**مشق ۱ — یاد کریں**

کولڈ سٹارٹ کا مسئلہ سمجھائیں۔ کس قسم کی ایپلی کیشن میں کولڈ سٹارٹ سب سے زیادہ پریشان کن ہوگا؟ کس قسم میں قابل قبول ہوگا؟

*(اشارہ: ایک ریئل ٹائم API (صارف جواب کا انتظار کر رہا ہے) کو ایک غیر متزامن پس منظر کام (صارف نے پہلے ہی اپنی تصدیق لے لی ہے اور دوسرے کام کر رہا ہے) سے موازنہ کریں۔)*

**مشق ۲ — امتحانی مشق**

*منظرنامہ*: ایک کمپنی S3 بکٹ کے ذریعے اپنے سپلائرز سے پروڈکٹ تصاویر وصول کرتی ہے۔ ہر تصویر کو چار معیاری جہتوں (تھمب نیل، چھوٹا، درمیانہ، بڑا) میں سائز کرنا اور واپس S3 میں محفوظ کرنا ہے۔ حجم غیر متوقع ہے — کچھ دنوں میں ۱۰ تصاویر، کچھ میں ۱۰۰٬۰۰۰۔ پروسیسنگ فی تصویر ۱۰ منٹ کے اندر مکمل ہونی چاہیے۔ لاگت کم سے کم رکھنی ہے۔

کون سی آرکیٹیکچر ان ضروریات کو بہترین طریقے سے پورا کرتی ہے؟

A) S3 بکٹ کی لمبی پولنگ سے نگرانی کرنے والے Auto Scaling Group میں EC2 انسٹینسز  
B) S3 واقعہ اطلاع Lambda فنکشن کو ٹریگر کرتی ہے جو تصاویر کا سائز بدلتا ہے اور نتائج S3 میں محفوظ کرتا ہے  
C) SQS قطار سے ٹریگر شدہ ECS Fargate کام، S3 واقعات قطار میں شائع ہوتے ہیں  
D) ایک مخصوص EC2 انسٹینس جس میں cron جاب ہر منٹ نئی تصاویر کے لیے S3 چیک کرتا ہے

**اشارہ ۱**: غیر متوقع حجم صفر تک پیمانہ کم کرنے کی حمایت کرتا ہے۔ کون سا آپشن یہ کرتا ہے؟

**اشارہ ۲**: فی تصویر ۱۰ منٹ Lambda کی ۱۵ منٹ کی حد کے اندر ہے۔ چیک کریں کہ آیا تصویر ری سائزنگ کا کام Lambda کی قیود میں فٹ ہوتا ہے۔

**اشارہ ۳**: ۲۴/۷ چلنے والی مخصوص EC2 انسٹینس مہنگی ہے اور پیمانہ نہیں بڑھاتی۔

**جواب**: B

**وضاحت**: S3 واقعہ اطلاعات تصویر اپلوڈ ہونے پر Lambda کو ٹریگر کرتی ہیں۔ Lambda تصویر کو چار جہتوں میں سائز کرتا ہے اور نتائج S3 میں محفوظ کرتا ہے۔ Lambda خودبخود ۰ سے ہزاروں بیک وقت چلانے تک پیمانہ بڑھاتا ہے، پہلے سے انتظام کیے بغیر غیر متوقع حجم سنبھالتا ہے۔ جب کوئی تصاویر پروسیس نہیں ہو رہی تو صفر لاگت۔

**A کیوں نہیں؟** ASG میں EC2 صفر تک پیمانہ نہیں کم کرتی — ہمیشہ کم از کم ایک انسٹینس چلتی رہتی ہے۔ S3 کو لمبی پولنگ نیٹو S3 واقعہ میکانیزم نہیں ہے۔ اچانک کام کے لیے Lambda سے زیادہ لاگت۔

**C کیوں نہیں؟** ECS Fargate کام کرتا ہے، لیکن زیادہ پیچیدہ ہے (کنٹینر منظمت، ECR، کام کی تعریفیں درکار) اور اچانک کام کے لیے Lambda سے تھوڑا زیادہ کولڈ سٹارٹ تاخیر ہے۔ اس استعمال کے معاملے میں Lambda آسان ہے۔

**D کیوں نہیں؟** مخصوص EC2 انسٹینس ناکامی کا واحد نقطہ ہے، پیمانہ نہیں بڑھاتی، ۲۴/۷ چلتی ہے، اور cron پر مبنی نقطہ نظر میں ۶۰ سیکنڈ تک کا پتہ لگانے میں تاخیر ہوتی ہے۔

*SAA-C03 ڈومین: لچکدار آرکیٹیکچر ڈیزائن — کام ۲.۱*

**مشق ۳ — آرکیٹیکچر چیلنج** *(اختیاری)*

Nimbus پچھلے دن کے حجم کے لحاظ سے ٹاپ ۱۰ ریستوران کے بارے میں روزانہ صبح ۵ بجے ایک رپورٹ تیار کرنا چاہتا ہے۔ رپورٹ DynamoDB ڈیٹا سے بنتی ہے، PDF کے طور پر فارمیٹ کی جاتی ہے، S3 میں محفوظ کی جاتی ہے، اور تمام ریستوران شراکت داروں کو ای میل کی جاتی ہے۔

اس کے لیے مکمل Lambda پر مبنی پائپ لائن ڈیزائن کریں۔ Lambda کو کیا ٹریگر کرتا ہے؟ اگر PDF بنانے میں ۱۲ منٹ لگیں تو کیا ہوگا؟ اگر ۵٬۰۰۰ ریستوران شراکت دار ہوں اور سب کو ای میل کرنے میں وقت لگے؟ کیا آپ ایک Lambda استعمال کریں گے یا کئی؟

*(کوئی واحد درست جواب نہیں ہے۔ مقصد Lambda کو دیگر سروسز کے ساتھ جوڑنے کی مشق کرنا ہے۔)*
