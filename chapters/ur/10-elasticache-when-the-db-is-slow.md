**غلط پہلی کوشش**

Leo کی پہلی جبلت فی صارف ڈیٹا cache کرنا تھی۔ ہر صارف کا ایک session تھا، اور session ان کا پروفائل لوڈ کرتا تھا: محفوظ پتے، ادائیگی کے طریقے، آرڈر کی تاریخ کا خلاصہ۔ شاید اسے cache کرنے سے چیزیں تیز ہو جائیں۔

اس نے اسے نافذ کیا۔ Redis key فارمیٹ: `user:{userId}:profile`۔ TTL: دس منٹ۔

اس نے لوڈ ٹیسٹ چلایا۔ صفحہ لوڈ چھ ملی سیکنڈ کم ہوا۔

"کیوں نہیں؟"

Leo نے ایک لمحے کے لیے گراف کو گھورا۔ "کیونکہ صارف پروفائل صرف ایک درخواست ہے۔ پھر بھی فی صفحہ چھیالیس DynamoDB calls ہیں۔ اور وہ مینو calls ہیں — browse صفحے پر فی ریستوران ایک۔ میں نے غلط چیز cache کی۔"

یہ caching میں ایک عام غلطی ہے: اس چیز کو بہتر بنانا جو رکاوٹ نہیں ہے۔ صارف پروفائل دو ملی سیکنڈ میں لوڈ ہوتا تھا۔ اتنی تیز چیز کو cache کرنے سے تقریباً کچھ نہیں بچا۔ مینو ڈیٹا — سینتالیس بار لایا گیا، ہر بار چار ملی سیکنڈ لیتا ہوا — اصل مسئلہ تھا۔

"آپ کو فی مینو cache کرنا ہے، فی صارف نہیں،" Priya نے کہا۔ "ریستوران 047 کا مینو ہر اس صارف کے لیے ایک ہی ہے جو اسے براؤز کرتا ہے۔ یہ وہ ڈیٹا ہے جو cache کرنے کے قابل ہے — یہ ہزاروں درخواستوں میں ایک جیسا ہے۔"

فی صارف caches قیمتی ہوتے ہیں جب صارفین کی مہنگی ذاتی نوعیت کی حالت ہو۔ فی entity caches (مینوز، پروڈکٹ کیٹلاگ، config) قیمتی ہوتے ہیں جب ایک ہی ڈیٹا ہزاروں صارفین کو پیش کیا جائے۔ کوڈ لکھنے سے پہلے جان لیں کہ آپ کے پاس کون سا مسئلہ ہے۔

Leo نے cache keys دوبارہ ڈیزائن کیں: `menu:{restaurantId}`۔ فی ریستوران ایک cache entry، اس ریستوران کو براؤز کرنے والے ہر صارف کے ذریعے مشترک۔

اس نے دوبارہ لوڈ ٹیسٹ چلایا۔ صفحہ لوڈ 188 ملی سیکنڈ سے گر کر 12 ملی سیکنڈ ہو گیا۔ یہ وہ بہتری تھی جس کی وہ تلاش میں تھے۔

**ریستوران کی مثال**

ایک ریستوران کی کچن کا تصور کریں۔ ہر بار جب کسی ویٹر کو آج کی خصوصی اشیاء جاننی ہوتی ہیں، وہ پیچھے چلتا ہے، باورچی سے پوچھتا ہے، اور میز پر واپس آتا ہے۔

یہ ٹھیک کام کرتا ہے اگر آپ کے پاس دو ویٹر اور تین میزیں ہیں۔

اب دو سو ویٹر اور ایک ہزار میزیں تصور کریں۔ ان میں سے ہر ایک ایک ہی سوال کے لیے پیچھے جا رہا ہے۔ کچن رکاوٹ بن جاتی ہے۔ باورچی ایک گھنٹے میں چار سو بار ایک ہی سوال کا جواب دے رہا ہے۔

واضح حل: ریستوران کے سامنے ایک بورڈ پر خصوصی اشیاء لکھیں۔ ہر ویٹر بورڈ سے پڑھتا ہے۔ کچن کو آرام ملتا ہے۔ جب خصوصی اشیاء تبدیل ہوں تو بورڈ اپڈیٹ ہوتا ہے۔

وہ بورڈ ایک cache ہے۔

Cache حال ہی میں بازیافت کردہ ڈیٹا کا ایک تیز، مقامی ذخیرہ ہے۔ ایک ہی چیز کو بار بار کسی سست ذریعہ سے لانے کے بجائے، آپ اسے ایک بار لاتے ہیں اور قریب رکھتے ہیں۔

ایک اور مثال ہے جو انجینئرز کو مفید لگتی ہے: لائبریری کا ریزرو شیلف۔ جب کوئی مقبول کتاب واپس جمع ہوتی ہے، تو لائبریرین جانتا ہے کہ اسے جلد دوبارہ مانگا جائے گا، لہٰذا وہ اسے ذخیروں میں رکھنے کے بجائے فرنٹ ڈیسک کے قریب ریزرو شیلف پر رکھ دیتا ہے۔ اگلے قاری کو پوری لائبریری چھاننی نہیں پڑتی — اسے یہ ڈیسک پر ہی مل جاتی ہے۔ ریزرو شیلف کی محدود جگہ ہے۔ اگر یہ بھر جائے، تو پرانی کتابیں نئی کے لیے جگہ بنانے کے لیے واپس ذخیروں میں منتقل ہو جاتی ہیں۔ ایک cache بالکل اسی طرح کام کرتا ہے: کثرت سے رسائی کیا جانے والا ڈیٹا سامنے کے قریب رہتا ہے، شاذ و نادر رسائی کیا جانے والا ڈیٹا جگہ بنانے کے لیے evict ہو جاتا ہے۔

**صرف میموری کیوں نہیں؟**

"کیا ہم صرف ایپلیکیشن کی میموری میں مینو محفوظ نہیں کر سکتے؟" Leo نے پوچھا۔

درست سوال۔

آپ کر سکتے ہیں۔ ایک سنگل سرور ایپلیکیشن کے لیے، in-memory caching ٹھیک کام کرتی ہے۔ لیکن Nimbus ایک لوڈ بیلنسر کے پیچھے، متعدد EC2 انسٹینسز میں چلتا ہے۔ اگر ایک انسٹینس اپنی میموری میں مینو cache کرے، تو دوسری انسٹینسز کے پاس وہ ڈیٹا نہیں ہے۔ وہ ہر ایک الگ caches برقرار رکھتی ہیں۔ جب مینو اپڈیٹ ہوتا ہے، تو آپ کو ان سب کو invalidate کرنا پڑے گا۔

یہ *cache coherence مسئلہ* ہے — متعدد caches کو متسق رکھنا۔

ElastiCache اسے ایک *مرکزی* cache فراہم کر کے حل کرتا ہے جسے آپ کی تمام انسٹینسز شیئر کرتی ہیں۔ ہر سرور کی اپنی میموری رکھنے کے بجائے، ہر سرور ایک ہی cache سے پڑھتا اور لکھتا ہے۔ ایک اپڈیٹ سب تک پہنچ جاتی ہے۔

**ElastiCache سے ملیں**

"رکیں — لیکن ہم *کیوں* اسے اس طرح کریں؟" Maya نے پوچھا۔ "ایک پوری نئی سروس کیوں؟ صرف مزید ڈیٹابیس صلاحیت کیوں نہ شامل کریں؟"

اچھا سوال۔ جواب یہ ہے کہ مزید ڈیٹابیس صلاحیت شامل کرنا — بڑے انسٹینسز، مزید read replicas — بنیادی مسئلہ ٹھیک نہیں کرتا۔ ان سینتالیس صفحہ-لوڈ درخواستوں میں سے ہر ایک پھر بھی وقت اور پیسہ خرچ کرتی ہے، چاہے ایک تیز ڈیٹابیس پر بھی۔ Cache ڈیٹابیس کو تیز نہیں بناتا؛ اس کا مطلب یہ ہے کہ ڈیٹابیس سے ایک ہی سوال بہت کم بار پوچھا جاتا ہے۔ ایسے ڈیٹا کے لیے جو بار بار پڑھا جاتا ہے اور کم ہی بدلتا ہے — جیسے ایک ریستوران کا مینو — cache کا مطلب ہے کہ ڈیٹابیس وہ سوال فی صفحہ لوڈ سینتالیس بار کے بجائے ہر پانچ منٹ میں ایک بار جواب دے سکتا ہے۔

Amazon ElastiCache ایک منیجڈ caching سروس ہے۔ یہ مشہور caching engines — Redis اور Memcached — آپ کو سرورز منظم کیے بغیر چلاتا ہے۔

**Redis** دونوں میں سے زیادہ طاقتور ہے۔ یہ پیچیدہ ڈیٹا structures (strings، lists، sets، hashes، sorted sets)، persistence (ری اسٹارٹ کے بعد ڈیٹا باقی رہتا ہے)، ریپلیکیشن، اور pub/sub messaging سپورٹ کرتا ہے۔ Redis caching سے زیادہ کر سکتا ہے — یہ ایک ہلکے ڈیٹا اسٹور کے طور پر کام کر سکتا ہے۔

**Memcached** آسان ہے۔ خالص key-value caching، افقی طور پر قابل توسیع، کوئی persistence نہیں۔ آسان استعمال کے کیسز کے لیے تیز لیکن کم خصوصیات۔

Nimbus کے لیے: Redis۔ انہیں مینو ڈیٹا (منظم)، session tokens (key-value) cache کرنے کی ضرورت تھی، اور بعد میں وہ "trending restaurants" کی درجہ بندی کے لیے sorted sets چاہتے تھے۔

**عملی طور پر Caching کیسے کام کرتی ہے**

بنیادی caching نمونے کو **cache-aside** (lazy loading بھی کہا جاتا ہے) کہتے ہیں:

1. ایپلیکیشن کو ڈیٹا چاہیے
2. پہلے cache چیک کریں
3. اگر ملا (*cache hit*): فوری طور پر ڈیٹا واپس کریں
4. اگر نہیں ملا (*cache miss*): ڈیٹابیس جائیں، ڈیٹا لیں، اسے cache میں محفوظ کریں، واپس کریں

pseudocode میں:

```
menuData = cache.get("menu:restaurant-047")
if menuData is null:
    menuData = dynamodb.query(TableName="menu", KeyConditionExpression="restaurantId = '047'")
    cache.set("menu:restaurant-047", menuData, ttl=300)  # 5 منٹ کے لیے Cache
return menuData
```

پہلی درخواست ہمیشہ ڈیٹابیس سے ٹکراتی ہے۔ ہر بعد کی درخواست cache سے ٹکراتی ہے۔ cache کے ساتھ، Nimbus کی فی صفحہ لوڈ سینتالیس DynamoDB ریڈز ایک یا دو cache lookups بن جاتی ہیں۔ تیز، سستی، اور قابل توسیع۔

**TTL: آپ کتنی دیر یاد رکھتے ہیں؟**

ہر cache entry کی ایک **Time-To-Live (TTL)** ہوتی ہے: وہ مدت جس کے بعد entry ختم ہو جاتی ہے اور اگلی درخواست تازہ ڈیٹا کے لیے ڈیٹابیس پر واپس جاتی ہے۔

یہ caching کا بنیادی تناؤ ہے: تازگی بمقابلہ کارکردگی۔

- **مختصر TTL (سیکنڈ)**: بہت تازہ ڈیٹا، لیکن بہت سارے cache misses۔ Cache مشکل سے مدد کرتا ہے۔
- **لمبی TTL (گھنٹے یا دن)**: بہت تیز، لیکن ڈیٹا پرانا ہو سکتا ہے۔ صارف کل کا مینو دیکھتا ہے۔

مینو ڈیٹا کے لیے، پانچ منٹ مناسب ہے۔ مینو ہر سیکنڈ نہیں بدلتا۔ اگر کوئی ریستوران اپنا مینو اپڈیٹ کرے، تو صارفین پانچ منٹ تک پرانا ورژن دیکھ سکتے ہیں — قابل قبول۔

Session tokens کے لیے (کیا یہ صارف لاگ ان ہے؟)، چھوٹی TTL سمجھ آتی ہے، یا جب session تبدیل ہو تو آپ فوری طور پر cache اپڈیٹ کرتے ہیں۔

مالی ڈیٹا کے لیے (آرڈر totals، ادائیگی ریکارڈ)، اسے cache نہ کریں — یا اگر کریں، تو رائٹ پر فوری طور پر invalidate کریں۔

آپ سوچ رہے ہوں گے: ایک پوری نئی caching پرت متعارف کرانے کے بجائے صرف مزید ڈیٹابیس صلاحیت کیوں نہ شامل کریں؟ مزید replicas، ایک بڑا انسٹینس — وہ کیوں نہیں؟ جواب یہ ہے کہ اضافی ڈیٹابیس صلاحیت بیک وقت درخواستیں سنبھالنے کی آپ کی صلاحیت کو ضرب دیتی ہے، لیکن یہ درخواستوں کی تعداد کم نہیں کرتی۔ اگر دس ہزار صارف ہر ایک فی صفحہ لوڈ سینتالیس ریڈز trigger کر رہے ہیں، تو ایک دوسرا read replica شامل کرنے کا مطلب صرف یہ ہے کہ ہر replica سینتالیس ہزار کے بجائے تئیس ہزار درخواستیں سنبھالتا ہے — کل کام سکڑتا نہیں۔ Cache فالتو کام کو مکمل طور پر ختم کر دیتا ہے: وہ دس ہزار صارف ایک ہی cache شدہ نتیجہ شیئر کرتے ہیں۔

"کمپیوٹر سائنس میں صرف دو مشکل مسائل ہیں،" Leo نے کسی ایسے شخص کی مشق شدہ فراہمی کے ساتھ اقتباس کیا جس نے یہ پہلے کہا تھا۔ "Cache invalidation اور چیزوں کے نام رکھنا۔"

"Cache invalidation مشکل کیوں ہے؟" Maya نے پوچھا۔

"کیونکہ ڈیٹا *واقعی* کب بدلتا ہے؟ کیا مینو اس لیے بدلا کیونکہ ایک ریستوران پارٹنر نے اسے اپڈیٹ کیا؟ یا کیونکہ ایک cron job چلی؟ یا کیونکہ ایک admin نے ہاتھ سے ترمیم کی؟ ہر وہ جگہ جو ڈیٹا بدل سکتی ہے اسے cache کو بتانا جاننا ضروری ہے۔"

یہی وجہ ہے کہ سینئر انجینئرز ایک caching گفتگو "write paths کیا ہیں؟" سے شروع کرتے ہیں، "آئیں Redis شامل کریں" سے نہیں۔

انہوں نے ایک DynamoDB Streams handler شامل کیا — پچھلے باب سے — جو جب بھی کوئی مینو آئٹم بدلتا، خودبخود cache invalidate کر دیتا، چاہے کسی بھی نظام نے رائٹ trigger کیا ہو۔ ایک handler، تمام write paths کا احاطہ۔

**Cache Eviction: جب بورڈ بھر جائے**

خصوصی اشیاء کے بورڈ کی محدود جگہ ہے۔ جب یہ بھر جائے، تو آپ کو جگہ بنانے کے لیے کچھ مٹانا پڑتا ہے۔

Redis (اور عام طور پر caches) کے پاس *eviction policies* ہیں جو طے کرتی ہیں کہ میموری بھرنے پر کیا ہٹایا جائے:

- **LRU (Least Recently Used)**: وہ آئٹمز ہٹائیں جن تک سب سے لمبے عرصے سے رسائی نہیں کی گئی۔
- **LFU (Least Frequently Used)**: وہ آئٹمز ہٹائیں جن تک سب سے کم رسائی کی جاتی ہے۔
- **allkeys-random**: بے ترتیب eviction۔ آسان، بہترین نہیں۔
- **noeviction**: میموری بھرنے پر ایک ایرر واپس کریں (ایپلیکیشن کو اسے سنبھالنا ہوگا)۔

زیادہ تر ویب ایپلیکیشنز کے لیے: LRU۔ وہ چیزیں جو آپ نے حال ہی میں نہیں دیکھیں وہ شاید کم ضروری ہیں۔

**Cache Stampede کا مسئلہ**

"کیا ہم نے سوچا ہے کہ اگر پورا cache ایک ساتھ خالی ہو جائے تو کیا ہوتا ہے؟" Priya نے پوچھا۔

"یہ کب ہوگا؟" Leo نے کہا۔

"جب آپ ایک نیا ElastiCache cluster deploy کریں۔ جب entries کے ایک بڑے بیچ پر TTL بیک وقت ختم ہو۔ جب آپ bug fix کے بعد refresh پر مجبور کرنے کے لیے cache flush کریں۔"

Leo نے اس پر سوچا۔ "اگر cache خالی ہے، تو ہر درخواست ڈیٹابیس پر جاتی ہے۔ سب ایک ساتھ۔ چند سیکنڈ کے لیے، ڈیٹابیس ہر بیک وقت صارف کا پورا بوجھ سنبھالتا ہے۔"

"اس کے سامنے کوئی cache نہیں۔"

"یہ تکلیف دہ ہوگا۔" Leo نے ڈیٹابیس صلاحیت کی ترتیبات دیکھیں۔ "ہم یقینی طور پر throttle ہو جائیں گے۔"

اسے **cache stampede** (thundering herd بھی کہا جاتا ہے) کہتے ہیں۔ یہ تب ہوتا ہے جب بہت سی cache entries ایک ہی وقت میں ختم ہو جائیں — اکثر اس لیے کہ وہ سب ایک deploy یا cold start کے دوران ایک ہی وقت میں بنائی گئی تھیں — اور cache misses کی اچانک لہر سب بیک وقت ڈیٹابیس سے ٹکراتی ہے۔

تخفیف کی حکمت عملیاں:

**TTL پر Jitter**: ہر مینو entry کو بالکل 300 سیکنڈ پر سیٹ کرنے کے بجائے، بے ترتیب تبدیلی شامل کریں: 270 سے 330 سیکنڈ۔ entries تھوڑے مختلف اوقات پر ختم ہوتی ہیں، cache miss کی لہر کو بیک وقت ٹکرانے کے بجائے ایک منٹ پر پھیلا دیتی ہیں۔

**امکانی جلد expiration**: کسی entry کے ختم ہونے سے پہلے، درخواستوں کا ایک چھوٹا فیصد فعال طور پر اسے refresh کر دیتا ہے۔ یہ entries کو پرانا ہونے سے پہلے تازہ رکھتا ہے، expiration کو کبھی miss بننے سے روکتا ہے۔

**درخواست کا اتحاد (mutex/lock)**: جب cache miss ہو، تو ڈیٹابیس سے ٹکرانے سے پہلے ایک lock حاصل کریں۔ اسی key کے لیے دیگر بیک وقت درخواستیں پہلی درخواست کے مکمل ہونے اور cache دوبارہ بھرنے کا انتظار کرتی ہیں، پھر cache سے پڑھتی ہیں۔ فی cache miss صرف ایک ڈیٹابیس درخواست کی جاتی ہے، اعلیٰ بیک وقتگی کے تحت بھی۔

Nimbus کے لیے، انہوں نے TTL jitter نافذ کی۔ آسان، مؤثر، کوئی اضافی پیچیدگی نہیں۔

```python
import random
TTL_BASE = 300
TTL_JITTER = 30
ttl = TTL_BASE + random.randint(-TTL_JITTER, TTL_JITTER)
cache.set(key, value, ttl=ttl)
```

"کوڈ کی دو لائنیں،" Leo نے کہا۔ "Deploys کے دوران ممکنہ ڈیٹابیس outage کو روکنے کے لیے۔"

"زیادہ تر اعتباریت کی بہتریاں ایسی ہی ہوتی ہیں،" Priya نے کہا۔ "نافذ کرنے میں سستی، یہ سیکھنے میں مہنگی کہ آپ کو ان کی ضرورت تھی۔"

**Redis ڈیٹا Structures: Key-Value سے زیادہ**

جب Nimbus نے "trending restaurants" خصوصیت شامل کی، تو Leo نے ابتدائی طور پر درجہ بندی کو ایک سادہ JSON فہرست کے طور پر محفوظ کیا: `trending:global → ["NIMBUS-047", "NIMBUS-112", ...]`۔

یہ کام کر گئی، لیکن اسے اپڈیٹ کرنا عجیب تھا۔ ایک نیا ریستوران شامل کرنے یا ایک سکور اپڈیٹ کرنے کے لیے، اسے پوری فہرست پڑھنی پڑتی، اسے ایپلیکیشن کوڈ میں ترمیم کرنی پڑتی، اور پوری چیز واپس لکھنی پڑتی۔ analytics pipeline سے بیک وقت رائٹس کے تحت، race conditions کی وجہ سے سکور اوور رائٹ ہو جاتے تھے۔

Priya نے اسے Redis sorted sets کی طرف اشارہ کیا۔

Redis میں ایک **sorted set** members کو منسلک عددی سکورز کے ساتھ محفوظ کرتا ہے۔ Members خودبخود سکور کے لحاظ سے ترتیب دیے جاتے ہیں۔ آپریشنز atomic ہیں — بیک وقت اپڈیٹس سے کوئی race conditions نہیں۔

```
# کسی ریستوران کا سکور شامل/اپڈیٹ کریں
ZADD trending:global 9420 "NIMBUS-047"
ZADD trending:global 8831 "NIMBUS-112"

# سکور کے لحاظ سے ٹاپ 10 ریستوران حاصل کریں (سب سے زیادہ پہلے)
ZREVRANGE trending:global 0 9 WITHSCORES

# کسی ریستوران کا سکور atomically بڑھائیں
ZINCRBY trending:global 50 "NIMBUS-047"
```

analytics Lambda ہر بار آرڈر دیے جانے پر `ZINCRBY` کال کرتا تھا، ریستوران کا سکور بڑھاتا تھا۔ homepage ٹاپ دس حاصل کرنے کے لیے `ZREVRANGE` کال کرتا تھا۔ کوئی locks نہیں، کوئی race conditions نہیں، کوئی read-modify-write چکر نہیں۔

Redis سادہ key-value سے آگے کئی دیگر ڈیٹا structures سپورٹ کرتا ہے:

**Lists**: ترتیب شدہ سلسلے۔ آگے یا پیچھے push کریں۔ queues، حالیہ سرگرمی feeds، log streams کے لیے استعمال کریں۔

**Sets**: بغیر نقل کے غیر ترتیب شدہ مجموعے۔ Union، intersection، difference آپریشنز۔ "کن صارفین نے یہ اطلاع دیکھی ہے؟" یا "کن ریستورانوں کا تعلق اس قسم سے ہے؟" کے لیے استعمال کریں۔

**Hashes**: ایک key کے اندر نامزد فیلڈز۔ منظم اشیاء کے لیے استعمال کریں جہاں آپ پورے object کو دوبارہ لکھے بغیر انفرادی فیلڈز اپڈیٹ کرنا چاہتے ہیں۔

**HyperLogLog**: امکانی cardinality تخمینہ۔ ہر visitor ID محفوظ کیے بغیر کسی صفحے پر منفرد visitors گنیں۔ کمپیکٹ اور تیز۔

**Pub/Sub**: channels پر پیغامات شائع کریں؛ subscribers انہیں real time میں وصول کرتے ہیں۔ سروسز کے درمیان ہلکی real-time اطلاعات کے لیے استعمال کریں۔

"Redis صرف ایک cache نہیں ہے،" Leo نے کہا۔ "یہ ایک ڈیٹا structure سرور ہے۔"

"یہ اس کی سرکاری تفصیل ہے،" Priya نے کہا۔

"میں نے سوچا یہ صرف ایک فینسی dictionary تھا۔"

"اس نے اسی طرح شروع کیا تھا۔"

**Write-Through: دوسرا Caching نمونہ**

Cache-aside (lazy loading) سب سے عام نمونہ ہے۔ لیکن ایک دوسرا بھی ہے جسے جاننا قابل قدر ہے: **write-through**۔

write-through caching میں، ہر بار جب آپ کی ایپلیکیشن ڈیٹابیس میں لکھتی ہے، تو یہ فوری طور پر cache میں بھی لکھتی ہے۔

```python
def update_menu(restaurant_id, menu_data):
    dynamodb.put_item(TableName="menu", Item=menu_data)
    cache.set(f"menu:{restaurant_id}", menu_data, ttl=300)
```

فائدہ: cache ہمیشہ تازہ ترین رہتا ہے۔ رائٹ اور TTL expiry کے درمیان کوئی پرانا ڈیٹا نہیں۔

نقصان: ہر رائٹ دو جگہوں پر جاتی ہے۔ اور آپ cache کو ایسے ڈیٹا سے بھرتے ہیں جو شاید کبھی نہ پڑھا جائے۔ اگر دس ریستوران اپنے مینوز اپڈیٹ کریں لیکن اگلے پانچ منٹ میں صرف دو کو نمایاں ٹریفک ملے، تو آپ نے آٹھ caches کے لیے write-through کام کیا ہے جو ختم ہونے سے پہلے استعمال نہیں ہوں گے۔

"رکیں — لیکن ہم *کیوں* اسے اس طرح کریں؟" Maya نے پوچھا۔ "اگر ہم ہر اپڈیٹ پر cache میں لکھتے ہیں، تو ہم پہلے سے زیادہ کام فی رائٹ کر رہے ہیں۔ یہ کیسے بہتر ہے؟"

"یہ ہمیشہ بہتر نہیں ہے،" Priya نے کہا۔ "Write-through تب سمجھ آتا ہے جب آپ کسی رائٹ کے بعد پرانے ڈیٹا کی کوئی کھڑکی برداشت نہیں کر سکتے۔ Cache-aside ہر رائٹ پر اضافی کام نہ کرنے کے بدلے ایک TTL تک کا پرانا پن قبول کرتا ہے۔"

Nimbus کے لیے: cache-aside صحیح انتخاب تھا۔ مینوز کو لکھنے سے کہیں زیادہ پڑھا جاتا تھا۔ پانچ منٹ کی پرانی کھڑکی قابل قبول تھی۔ ایک مالی trading نظام کے لیے جہاں ہر قیمت کی اپڈیٹ کو فوری طور پر ظاہر کرنا ضروری تھا، write-through زیادہ مناسب ہوگا۔

فیصلہ دو سوالوں پر آتا ہے: آپ کا write-to-read تناسب کیا ہے، اور آپ کسی رائٹ کے بعد پرانی reads کو کتنا برداشت کرتے ہیں؟

**Redis کے لیے ElastiCache: آپ کو کیا منیجڈ ملتا ہے**

RDS کی طرح، ElastiCache ایک اوپن سورس ٹول لیتا ہے اور آپریشنل کام سنبھالتا ہے:

- **خودکار بیک اپ**: شیڈول پر Redis snapshots
- **Multi-AZ ریپلیکیشن**: مختلف AZs میں Primary node + read replicas
- **خودکار failover**: اگر primary Redis node ناکام ہو، تو ایک replica خودبخود ترقی پاتا ہے
- **Cluster mode**: بہت بڑے caches کے لیے متعدد nodes میں افقی sharding
- **خفیہ کاری**: تعمیل کے لیے transit اور at-rest خفیہ کاری
- **VPC انضمام**: Cache آپ کے نجی نیٹ ورک میں چلتا ہے، عوامی طور پر قابل رسائی نہیں

**Cache کی نگرانی**

"کیا ہم نے سوچا ہے کہ جب cache صحیح طریقے سے کام نہ کر رہا ہو تو کیا ہوتا ہے؟" Priya نے Redis تعیناتی کے ایک ہفتے بعد پوچھا۔ "صرف مکمل طور پر ناکام نہیں ہوتا — کام کرتا ہے، لیکن خراب طریقے سے۔ اعلیٰ miss rate۔ اعلیٰ eviction rate۔ Latency بڑھتی ہوئی۔"

"میں محسوس کروں گا جب صفحہ لوڈ کے اوقات بڑھیں،" Leo نے کہا۔

"جس مقام تک ڈیٹابیس پہلے ہی جدوجہد کر رہا ہوگا،" اس نے کہا۔

ElastiCache CloudWatch کے ذریعے میٹرکس ظاہر کرتا ہے۔ وہ جو سب سے زیادہ اہم ہیں:

**CacheHitRate**: cache reads کا فیصد جنہوں نے ایک نتیجہ واپس کیا۔ بہترین طور پر ایک پختہ cache کے لیے 80% سے اوپر۔ گرتا ہوا hit rate اشارہ دیتا ہے کہ آپ کا سب سے زیادہ رسائی کیا جانے والا ڈیٹا cache میں نہیں ہے — یا تو TTLs بہت مختصر ہیں، cache بہت چھوٹا ہے، یا آپ کے رسائی کے نمونے بدل گئے ہیں۔

**CacheMisses**: cache misses کی مطلق گنتی۔ یہاں اچانک اضافے کا مطلب ہے کہ cache مدد نہیں کر رہا اور ڈیٹابیس پورا بوجھ لے رہا ہے۔

**Evictions**: نئی کے لیے جگہ بنانے کے لیے evict کیے گئے cache آئٹمز کی تعداد۔ اعلیٰ eviction rates کا مطلب ہے کہ آپ کا cache آپ کے working set کے لیے بہت چھوٹا ہے۔ آپ کو زیادہ میموری یا زیادہ منتخب caching حکمت عملی کی ضرورت ہے۔

**CurrConnections**: Redis سے موجودہ client کنکشنز۔ بہت زیادہ کنکشنز Redis کی کنکشن حد ختم کر سکتے ہیں۔ ایپلیکیشنز کو ہر درخواست پر نیا کنکشن کھولنے سے بچنے کے لیے connection pooling استعمال کرنی چاہیے۔

**ReplicationLag**: read replica primary سے کتنا پیچھے ہے۔ اگر یہ بڑھے، تو replica reads پرانا ڈیٹا واپس کر سکتی ہیں۔

Leo نے دو CloudWatch alarms سیٹ کیے۔ پہلا: اگر cache hit rate لگاتار پندرہ منٹ تک 70% سے نیچے گرے تو alert کریں — یہ ڈیٹابیس کے محسوس کرنے سے پہلے تفتیش کے قابل ایک مسئلے کا اشارہ دے گا۔ دوسرا: اگر eviction rate فی منٹ 100 evictions سے زیادہ ہو تو alert کریں — یہ اشارہ دے گا کہ cache بہت چھوٹا ہے۔

"دو alarms،" Priya نے ترتیب کا جائزہ لیتے ہوئے کہا۔ "یہ ایک اچھی شروعات ہے۔"

"میں نے ایک dashboard بھی شامل کیا،" Leo نے کہا۔ "Hit rate، miss rate، evictions، latency۔ سب ایک جگہ نظر آتے ہیں۔"

"یہ صفحے کے سست ہونے کا انتظار کرنے سے بہتر ہے۔"

"کافی بہتر،" Leo نے اتفاق کیا۔

**ElastiCache بمقابلہ DAX: DynamoDB کے لیے کون سا Cache؟**

"اگر ہم DynamoDB ڈیٹا cache کر رہے ہیں،" Maya نے پوچھا، "تو ElastiCache کے بجائے DAX کیوں نہ استعمال کریں؟ میں نے اسے دستاویزات میں دیکھا۔"

اچھا سوال۔

**DAX (DynamoDB Accelerator)** DynamoDB کے لیے ایک مقصد کے لیے بنایا گیا in-memory cache ہے۔ یہ client کی سطح پر DynamoDB API calls کو intercept کرتا ہے — آپ کا ایپلیکیشن کوڈ اسی DynamoDB SDK کا استعمال کرتے ہوئے DAX سے بات کرتا ہے۔ Cache misses خودبخود DynamoDB سے لائے جاتے ہیں۔ Cache hits microseconds میں واپس آتی ہیں۔ جب ڈیٹا بدلتا ہے تو invalidation خودبخود سنبھالی جاتی ہے۔

**ElastiCache** ایک عام مقصد کا cache ہے۔ آپ cache keys، TTL منطق، invalidation — سب کچھ خود منظم کرتے ہیں۔ زیادہ کنٹرول، زیادہ ذمہ داری۔

کب کون سا استعمال کریں:

| منظر نامہ | سفارش |
|---|---|
| آپ DynamoDB ریڈز cache کر رہے ہیں اور صفر ایپلیکیشن تبدیلیاں چاہتے ہیں | DAX |
| آپ کو DynamoDB ریڈز پر microsecond latency چاہیے | DAX |
| آپ متعدد ذرائع سے cache کر رہے ہیں (DynamoDB + RDS + بیرونی APIs) | ElastiCache |
| آپ کو Redis ڈیٹا structures چاہئیں (sorted sets، pub/sub، HyperLogLog) | ElastiCache |
| آپ کو باریک TTL کنٹرول اور کسٹم invalidation منطق چاہیے | ElastiCache |
| آپ کو session اسٹوریج، rate limiting، یا distributed locks چاہئیں | ElastiCache |

Nimbus کے لیے: انہوں نے ElastiCache چنا کیونکہ وہ متعدد ذرائع سے ڈیٹا cache کر رہے تھے — مینوز کے لیے DynamoDB، آرڈر کی تاریخ کے خلاصوں کے لیے RDS، ریستوران کی ریٹنگز کے لیے بیرونی APIs۔ DAX صرف DynamoDB کے ساتھ کام کرتا ہے۔ اور انہیں trending درجہ بندی کے لیے Redis sorted sets کی ضرورت تھی۔

"اگر یہ خالصتاً ایک DynamoDB caching مسئلہ ہوتا،" Priya نے کہا، "تو DAX آسان جواب ہوتا۔ ایک سروس، خودکار invalidation، ایک ہی API۔ لیکن ہمارے پاس ایک سے زیادہ ڈیٹا ذریعہ ہے۔"

"تو DAX آسان ہے جب آپ صرف-DynamoDB ہوں،" Maya نے خلاصہ کیا۔ "ElastiCache جب آپ کو پورا ٹول باکس چاہیے۔"

"یہی ٹریڈ آف ہے۔"

### جب Cache ڈیٹا کھویا نہیں جا سکتا: Amazon MemoryDB

"کوئی Redis کو primary ڈیٹابیس کے طور پر کیوں استعمال کرے گا؟" Maya نے پوچھا۔ "کیا یہ cache نہیں ہے؟"

یہ بالکل صحیح سوال ہے۔

Redis کے لیے ElastiCache ایک cache ہے — تیز، in-memory، اور ڈیزائن کے لحاظ سے، سچائی کا ذریعہ نہیں۔ اگر ایک ElastiCache node ناکام ہو جائے، تو ری اسٹارٹ پر cache خالی ہوتا ہے۔ ایپلیکیشنز اسے ڈیٹابیس سے دوبارہ گرم کرتی ہیں۔ یہ ایک cache کے لیے ٹھیک ہے۔

لیکن کچھ استعمال کے کیسز Redis کو cache کے طور پر نہیں بلکہ ایک primary ڈیٹا اسٹور کے طور پر سمجھتے ہیں — session حالت جو ری اسٹارٹ سے بچنی چاہیے، ایک real-time leaderboard جو کھویا نہیں جا سکتا، ایک shopping cart جو ایک AZ ناکامی میں باقی رہنی چاہیے۔ ان استعمال کے کیسز کے لیے، ElastiCache کی بالآخر پائیداری ایک خطرہ ہے۔

**Redis کے لیے Amazon MemoryDB** ایک مکمل طور پر منیجڈ، Redis-مطابقت پذیر، پائیدار in-memory ڈیٹابیس ہے۔ ElastiCache کے برعکس، MemoryDB ایک distributed transaction log استعمال کرتا ہے جو متعدد AZs میں محفوظ ہوتا ہے اور ہر رائٹ کو acknowledge کیے جانے سے پہلے پائیدار بناتا ہے۔ ڈیٹا node ناکامیوں سے بچتا ہے — اس لیے نہیں کہ یہ کسی سست ڈیٹابیس سے دوبارہ چلتا ہے، بلکہ اس لیے کہ یہ کبھی صرف ایک جگہ میں نہیں تھا۔

اہم فرق:

| | Redis کے لیے ElastiCache | Redis کے لیے MemoryDB |
|---|---|---|
| کردار | Cache پرت | Primary ڈیٹابیس |
| پائیداری | ناکامی پر ضمانت نہیں | Multi-AZ transaction log |
| Latency | Microsecond ریڈز اور رائٹس | Microsecond ریڈز، single-digit millisecond رائٹس |

دونوں ایک ہی Redis commands اور ڈیٹا structures سپورٹ کرتے ہیں۔ API ایک ہی ہے۔ پائیداری کی ضمانت ایک ہی نہیں۔

Nimbus کے لیے: ٹیم فی ریستوران real-time آرڈر گنتیوں کو ایک Redis sorted set کے طور پر محفوظ کرنا چاہتی ہے — اور اسے ڈیٹابیس سے دوبارہ بھرے بغیر ایک AZ ناکامی سے بچنا ہے۔ وہ ضرورت — Redis-مطابقت پذیر *اور* پائیدار — MemoryDB کا عین اشارہ ہے۔

"تو ہمیں ناکامی کے بعد اسے دوبارہ گرم نہیں کرنا پڑے گا؟" Leo نے پوچھا۔

"یہی بات ہے،" Priya نے کہا۔ "اگر node ناکام ہو اور واپس آ جائے، تو ڈیٹا موجود ہے۔ transaction log نے اسے رکھا۔"

Leo نے ایک لمحے کے لیے pricing صفحہ کو گھورا۔ "اس پر ElastiCache سے زیادہ خرچ آتا ہے۔"

"ہر وہ چیز جس پر اعتماد قابل قدر ہو، ایسا ہی کرتی ہے،" Priya نے کہا۔

## خوبیاں اور حدود

**Caching کیوں طاقتور ہے**:

- ڈیٹابیس لوڈ کو ڈرامائی طور پر کم کرتا ہے (کم queries، کم لاگت)
- Cache hits کے لیے sub-millisecond ردعمل کے اوقات
- آپ کے ڈیٹابیس کو ٹریفک spikes سے محفوظ رکھتا ہے
- Redis سادہ key-value اسٹور سے زیادہ امیر ڈیٹا structures سپورٹ کرتا ہے
- Cache stampede تخفیف (TTL jitter، coalescing) cold-start اضافوں سے بچاتی ہے

**جہاں Caching پیچیدہ ہو جاتی ہے**:

- Cache invalidation واقعی مشکل ہے — پرانا ڈیٹا bugs پیدا کرتا ہے
- آپریشنل پیچیدگی بڑھاتی ہے (نگرانی کرنے کے لیے ایک اور سروس، ناکامی کا ایک اور نقطہ)
- Cold start مسئلہ: جب آپ تازہ تعینات کریں، تو cache خالی ہوتا ہے — ڈیٹابیس پورا بوجھ لیتا ہے
- Cache stampede: اگر بہت سی entries ایک ساتھ ختم ہو جائیں، تو تمام درخواستیں بیک وقت ڈیٹابیس کو متاثر کرتی ہیں
- ElastiCache nodes مفت نہیں — آپ انہیں بیکار ہونے پر بھی ادائیگی کرتے ہیں

**ElastiCache بمقابلہ DynamoDB DAX**:

اگر آپ خاص طور پر DynamoDB ڈیٹا cache کر رہے ہیں، تو AWS **DAX (DynamoDB Accelerator)** پیش کرتا ہے — DynamoDB کے لیے ایک مقصد کے لیے بنایا گیا in-memory cache۔ DAX آپ کے ایپلیکیشن کوڈ کے لیے شفاف ہے (ایک ہی API)، DynamoDB ریڈ latency کو microseconds تک کم کرتا ہے، اور cache invalidation خودبخود سنبھالتا ہے۔

DAX استعمال کریں جب آپ کی رکاوٹ DynamoDB ریڈز ہوں اور آپ صفر-تبدیلی caching چاہتے ہوں۔ ElastiCache استعمال کریں جب آپ کو کسی بھی ڈیٹا ذریعہ کے لیے ایک عام مقصد کا cache چاہیے، یا جب آپ کو Redis ڈیٹا structures چاہئیں۔

## خلاصہ

سینتالیس ڈیٹابیس calls ایک cache lookup بن گئیں۔ صفحہ 188 ملی سیکنڈ سے 12 پر چلا گیا۔ ایک caching پرت شامل کرنا ان سب سے زیادہ فائدہ مند تبدیلیوں میں سے ایک ہے جو ایک بڑھتی ہوئی ایپلیکیشن کر سکتی ہے — لیکن صرف تب جب cache سوچ سمجھ کر ڈیزائن کیا جائے، اس سوال کے واضح جوابات کے ساتھ کہ "یہ ڈیٹا کب بدلتا ہے؟"

- Cache حال ہی میں بازیافت کردہ ڈیٹا کا ایک تیز ذخیرہ ہے — آپ ایک بار پوچھتے ہیں، جواب یاد رکھتے ہیں۔ ElastiCache AWS کی منیجڈ caching سروس ہے، **Redis** (persistence، پیچیدہ ڈیٹا structures، pub/sub) اور **Memcached** (خالص key-value، افقی اسکیلنگ) سپورٹ کرتی ہے۔
- **Cache-aside نمونہ** (lazy loading): پہلے cache چیک کریں، miss پر ڈیٹابیس پر واپس جائیں۔ **TTL** کنٹرول کرتی ہے کہ ڈیٹا کب تک cache رہے — مختصر TTL کا مطلب زیادہ تازہ ڈیٹا اور زیادہ misses؛ لمبی TTL کا مطلب تیز ردعمل اور ممکنہ پرانا پن۔
- صحیح چیز cache کریں: فی entity ڈیٹا جو بہت سے صارفین میں مشترک ہو، نہ کہ فی صارف ڈیٹا جو ہر session کے لیے منفرد ہو۔ Cache stampede تب ہوتا ہے جب بہت سی entries بیک وقت ختم ہو جائیں — TTL jitter سے اس کی تخفیف کریں۔
- **DAX** صرف-DynamoDB caching کے لیے صحیح انتخاب ہے۔ **ElastiCache** متعدد-ذرائع caching اور Redis ڈیٹا structures کے لیے زیادہ لچکدار ہے۔
- Caching کا سب سے مشکل حصہ invalidation ہے: یہ جاننا کہ ڈیٹا کب بدلتا ہے اور ان تمام کوڈ راستوں میں cache اپڈیٹ کرنا جو اسے لکھتے ہیں۔ ایک cache صرف اتنا ہی قابل اعتماد ہے جتنی اس کی invalidation حکمت عملی۔

## امتحانی نکات

*SAA-C03 ڈومین: اعلیٰ کارکردگی آرکیٹیکچرز ڈیزائن کریں (ڈومین ۳، ٹاسک ۳.۳)*

- **امتحان میں Redis بمقابلہ Memcached**: Redis = persistence، ریپلیکیشن، پیچیدہ structures، pub/sub۔ Memcached = آسان key-value، خالص افقی اسکیلنگ۔ جب منظر نامے میں کہا جائے "cache کردہ ڈیٹا کھو نہیں سکتے"، تو جواب Redis ہے (یہ disk پر persist کرتا ہے)۔
- **ElastiCache استعمال کے کیس کے اشارے**: "ڈیٹابیس رکاوٹ ہے"، "ریڈ-بھاری ورک لوڈ"، "latency کم کریں"، "session اسٹور" — سب ElastiCache کی طرف اشارہ کرتے ہیں۔
- **DAX اشارہ**: "DynamoDB ریڈ latency کم کریں" یا "DynamoDB ریڈز بہت سست ہیں" → DAX، ElastiCache نہیں۔
- **Session management**: ElastiCache Redis صارف session ڈیٹا محفوظ کرنے کے لیے معیاری جواب ہے۔ بے حالت ایپلیکیشن + Redis session اسٹور = مستقل sessions کے ساتھ افقی اسکیلنگ۔
- **Write-through بمقابلہ cache-aside**: Cache-aside (lazy loading) سب سے عام ہے۔ Write-through ہر رائٹ پر cache اپڈیٹ کرتا ہے — کبھی پرانا نہیں، لیکن زیادہ write آپریشنز۔ امتحان انہیں الگ کر سکتا ہے۔
- **Cache eviction policies**: LRU (least recently used) عام ویب ورک لوڈز کے لیے سب سے عام امتحانی جواب ہے۔
- **ElastiCache بمقابلہ MemoryDB:** ElastiCache = cache پرت، تیز، ناکامی پر ڈیٹا کا نقصان قابل قبول۔ MemoryDB = پائیدار in-memory primary ڈیٹابیس، Redis-مطابقت پذیر، multi-AZ transaction log۔ امتحانی trigger: "Redis-compatible AND durable" یا "primary data store in Redis" → MemoryDB، ElastiCache نہیں۔

## مشقیں

**مشق ۱ — یادداشت**

اپنے الفاظ میں: cache invalidation کیا ہے، اور یہ مشکل کیوں ہے؟

*(اشارہ: Nimbus میں ان تمام جگہوں کے بارے میں سوچیں جہاں مینو ڈیٹا اپڈیٹ ہو سکتا ہے — ریستوران پارٹنر پورٹل، ایک admin ٹول، ایک cron job۔ ان میں سے ہر راستے کو cache کے بارے میں جاننا ضروری ہے۔)*

**مشق ۲ — SAA-C03 منظر نامہ**

*منظر نامہ*: ایک ویڈیو streaming platform لاکھوں صارفین کو پیش کرتا ہے۔ دستیاب فلموں کا catalog کم ہی بدلتا ہے (رات کو اپڈیٹ ہوتا ہے)۔ ایپلیکیشن اعلیٰ ڈیٹابیس CPU استعمال محسوس کر رہی ہے کیونکہ ہر صارف کی درخواست catalog query کرتی ہے۔ ٹیم اپڈیٹس کے ایک گھنٹے کے اندر catalog ڈیٹا کو درست رکھتے ہوئے ڈیٹابیس لوڈ کم کرنا چاہتی ہے۔

کون سا حل ان ضروریات کو بہترین طریقے سے پورا کرتا ہے؟

A) لوڈ تقسیم کرنے کے لیے RDS ڈیٹابیس میں read replicas شامل کریں  
B) Catalog کو on-demand capacity کے ساتھ DynamoDB میں منتقل کریں  
C) Catalog ڈیٹا کے لیے 1-گھنٹہ TTL کے ساتھ Redis کے لیے ElastiCache استعمال کریں  
D) زیادہ بیک وقت queries سنبھالنے کے لیے RDS انسٹینس سائز بڑھائیں

**اشارہ ۱**: ڈیٹا ریڈ-بھاری ہے اور کم ہی بدلتا ہے۔ اس کے لیے کون سا نمونہ مثالی ہے؟

**اشارہ ۲**: "ایک گھنٹے کے اندر درست" براہ راست ایک مخصوص cache ترتیب پیرامیٹر میں ترجمہ ہوتا ہے۔

**اشارہ ۳**: مقصد ڈیٹابیس لوڈ کم کرنا ہے، نہ صرف اس میں سے زیادہ سنبھالنا۔

**جواب**: C

**وضاحت**: ایک گھنٹے کی TTL کے ساتھ ElastiCache ہر key کے لیے پہلی درخواست کے بعد catalog ڈیٹا cache کرتا ہے۔ بعد کی درخواستیں ڈیٹابیس کو چھوئے بغیر cache سے واپس آتی ہیں۔ جب رات کی اپڈیٹ چلتی ہے، تو entries ایک گھنٹے کے اندر ختم ہو جاتی ہیں اور اگلی درخواست پر تازہ ڈیٹا لوڈ ہوتا ہے۔

**A کیوں نہیں؟** Read replicas مزید ڈیٹابیس nodes میں ریڈ ٹریفک تقسیم کرتی ہیں لیکن queries کی کل تعداد کم نہیں کرتیں۔ وہ ریڈز کو اسکیل کرنے کے لیے مفید ہیں، کثرت سے دہرائی جانے والی queries سے ڈیٹابیس لوڈ کم کرنے کے لیے نہیں۔

**B کیوں نہیں؟** DynamoDB میں منتقل کرنا بنیادی مسئلہ حل نہیں کرتا — catalog ڈیٹا اب بھی ہر صارف کی درخواست پر ڈیٹابیس (DynamoDB) سے بازیافت ہوگا۔

**D کیوں نہیں؟** انسٹینس کو بڑا کرنا زیادہ بیک وقت queries سنبھالتا ہے لیکن queries کی تعداد کم نہیں کرتا۔ بنیادی ناکارہ مزاجی باقی رہتی ہے۔

*SAA-C03 ڈومین: اعلیٰ کارکردگی آرکیٹیکچرز ڈیزائن کریں — ٹاسک ۳.۳*

**مشق ۳ — آرکیٹیکچر چیلنج** *(اختیاری)*

Nimbus ایک "trending restaurants" خصوصیت شامل کرنا چاہتا ہے: پچھلے 24 گھنٹوں میں آرڈر والیوم کے حساب سے ٹاپ 10 ریستورانوں کی ایک درجہ بندی فہرست، ہر 15 منٹ میں اپڈیٹ ہوتی ہے۔

آپ اسے ElastiCache Redis کے ساتھ کیسے نافذ کریں گے؟ درجہ بندی کے لیے آپ کون سا Redis data structure استعمال کریں گے؟ آپ کی cache TTL کیا ہوگی، اور آپ cache کو بالکل کب اپڈیٹ کریں گے؟

یہ بھی غور کریں: اگر ElastiCache node ناکام ہو جائے تو کیا ہوگا؟ کیا خصوصیت ٹوٹ جائے گی؟ آپ اس ناکامی کے گرد کیسے ڈیزائن کریں گے؟

*(کوئی ایک درست جواب نہیں ہے۔ مقصد cache ڈیزائن اور ناکامی کی سوچ کی مشق کرنا ہے۔)*
