# باب ۹: جب ٹیبل بڑا ہو جاتا ہے

Nimbus کے پہلے ریستوران پارٹنر کے کچن میں صبح دس بجے بھی لہسن اور گرم روٹی کی خوشبو تھی۔ Maya وہاں ایک ڈیمو کے لیے موجود تھی، ایک باورچی کو دیکھ رہی تھی جو ایک تبدیلی درج کرنے کے لیے ایپ پر سوائپ کر رہا تھا — جھینگے کی جگہ مچھلی، عارضی طور پر ختم۔ سوائپ ہوا۔ مینو اپڈیٹ ہو گیا۔ شہر کے کسی اور حصے میں موجود ایک گاہک نے سیکنڈوں میں تبدیلی دیکھ لی۔

یہ جادو کی طرح محسوس ہوا تھا۔

دفتر واپس آ کر، جادو سست ہونا شروع ہو گیا تھا۔

مینو ٹیبل میں 50,000 آئٹمز تھے۔

یہ 287 ریستورانوں میں تھے — پارٹنرز کی تعداد لوڈ-بیلنسر کے دنوں کے سینتالیس سے بڑھ کر ایک سال سے کم میں تقریباً تین سو ہو گئی تھی — ہر ایک کے ساتھ روزانہ کی خصوصی اشیاء، موسمی آئٹمز، اور علاقائی تبدیلیاں۔ کچھ آئٹمز میں ترمیم کنندگان تھے — سائز، مصالحے کی سطح، پروٹین کا انتخاب۔ کچھ میں کومبو ڈیلز تھے جو دوسرے آئٹمز کا حوالہ دیتے تھے۔ کچھ صرف ہفتے کے دنوں، یا صرف دوپہر کے کھانے کے وقت، یا صرف بعض شہروں میں مینو پر ظاہر ہوتے تھے۔

SQL query جو ریستوران کا مکمل مینو بازیافت کرتی تھی 200 ملی سیکنڈ میں واپس آتی تھی۔

اب یہ چار سیکنڈ لے رہی تھی۔

چار سیکنڈ وہ فرق ہے جس کی وجہ سے کوئی آرڈر دیتا ہے اور کوئی ایپ بند کر دیتا ہے۔ Leo نے query پلان چلایا۔ Tom نے index ترتیب دیکھی۔ Priya نے ریڈ ریپلیکا کاؤنٹ بڑھایا۔ ان میں سے کسی سے بھی کوئی معنی خیز فرق نہیں پڑا۔

اور اس نے کمرے کا مزاج بدل دیا۔

---

**پہلی کوشش: زیادہ Indexes**

Leo کے پاس query پلان کھلا تھا۔ اس نے احتیاط سے اس کا سراغ لگایا۔

"مسئلہ یہ join ہے،" اس نے کہا۔ "جب ہم ریستوران کا مینو نکالتے ہیں، تو ہم menu_items ٹیبل کو modifiers ٹیبل سے، پھر combos ٹیبل سے، پھر availability_windows ٹیبل سے جوڑتے ہیں۔ چار ٹیبلز، تین joins، پچاس ہزار قطاریں۔"

اس نے ہر ٹیبل میں `restaurantId` پر ایک index شامل کیا۔ اس نے query دوبارہ چلائی۔ دو سیکنڈ۔ بہتر، لیکن کافی اچھا نہیں۔

Tom نے query hints کے بارے میں کچھ پڑھا تھا۔ اس نے ایک دوپہر اسے ٹھیک کرنے میں گزاری۔ ایک اعشاریہ تین سیکنڈ۔ پھر بھی اچھا نہیں۔

"کیا ہو اگر ہم denormalize کریں؟" Leo نے پوچھا۔ "modifiers کو menu_items ٹیبل پر ہی ایک JSON کالم میں ملا دیں۔ کم joins۔"

انہوں نے یہ آزمایا۔ ٹھیک ایک سیکنڈ۔ یہ پیش رفت محسوس ہوئی۔ Maya نے ریستوران پارٹنرز کو پیغام بھیجا کہ انہوں نے رفتار کا مسئلہ حل کر دیا ہے۔ یہ منگل کا دن تھا۔

جمعرات تک query دوبارہ 2.8 سیکنڈ پر آ گئی۔ ان کا ڈیٹا بڑھ گیا تھا۔ مزید ریستوران شامل ہو گئے تھے۔ فی ریستوران مزید آئٹمز۔ وہ query جو حل شدہ محسوس ہوئی تھی، حل شدہ نہیں تھی۔

"Index کا طریقہ آج کے ڈیٹا کے ساتھ ساتھ چل رہا ہے،" Priya نے کہا۔ "لیکن ہم ہفتے میں چالیس ریستوران شامل کر رہے ہیں۔ اگلی سہ ماہی تک ہمارے پاس دوگنے آئٹمز ہوں گے۔ تب query کیسی نظر آئے گی؟"

"کم از کم تین سیکنڈ،" Leo نے کہا۔ "شاید پانچ۔"

"تو ہم نے اپنے لیے چند ہفتے خرید لیے ہیں۔"

"ہاں۔"

وہ اس کے ساتھ بیٹھے رہے۔ ایک ایسا حل جو ختم ہو جائے، حقیقت میں حل نہیں ہے۔

**دوسری کوشش: Read Replicas**

Priya نے پہلے ہی ایک بار ریڈ ریپلیکا کاؤنٹ بڑھایا تھا۔ اس نے دوبارہ کوشش کی — اب دو ریڈ ریپلیکا، اور ایپلیکیشن ان کے درمیان لوڈ-بیلنس کرتی تھی۔ نظریہ درست تھا: ریڈ ٹریفک پھیلائیں، ہر ریپلیکا کم کام سنبھالے۔

اس سے تھوڑی مدد ملی۔ peak load 2.8 سیکنڈ سے گر کر 2.2 سیکنڈ ہو گیا۔

"یہ اس لیے ہے کہ رکاوٹ ریڈز کی تعداد نہیں ہے،" Tom نے ڈیٹابیس میٹرکس دیکھتے ہوئے کہا۔ "یہ خود query ہے۔ مزید ریپلیکا کا مطلب ہے مزید سرورز وہی سست query چلا رہے ہیں۔ query پھر بھی سست ہے۔"

"اس پر فی مہینہ کتنا خرچ آتا ہے؟" اس نے مزید کہا، کیونکہ وہ ہمیشہ پوچھتا تھا۔ "ایک db.r5.large پر دو اضافی ریڈ ریپلیکا — یہ تقریباً 350 ڈالر فی مہینہ ہے۔ دو سیکنڈ کی بہتری کے لیے۔"

Leo نے replica پینل بند کر دیا۔

"تو زیادہ ہارڈ ویئر خراب query کو ٹھیک نہیں کرتا،" Maya نے کہا۔

"جب کوئی مسئلہ indexing، caching کی کوششوں، اور اضافی ریپلیکا سے بچ جائے،" Leo نے آہستہ آہستہ کہا، "تو شاید مسئلہ ترتیب نہیں ہے۔ شاید یہ نظام کی شکل ہے۔"

یہ ایک طویل گفتگو کا آغاز تھا۔

---

*پچھلے ہفتے، ٹیم نے بالآخر RDS کو قابو میں کر لیا تھا۔ Multi-AZ standby، خودکار بیک اپ، ایک ریڈ ریپلیکا جو رپورٹنگ queries سنبھالتا تھا۔ DBA کا مسئلہ — وہ جو Leo کو رات کو جگاتا تھا — حل ہو گیا تھا۔ منیجڈ ڈیٹابیس کی پرت مستحکم تھی۔ لیکن مستحکم کا مطلب تیز نہیں تھا، اور تیز ہونا اب مسئلہ تھا۔ مینو ٹیبل نے ایسی حدوں سے ٹکرانا شروع کر دیا تھا جنہیں مزید ریپلیکا ٹھیک نہیں کر سکتے تھے۔ ڈیٹا کی شکل خود ہی غلط تھی۔*

---

**ہر چیز ٹیبل میں فٹ کرنے کا مسئلہ**

یہاں ریلیشنل ڈیٹابیسز کا بنیادی تناؤ ہے: انہیں *مقررہ* شکلوں میں *منظم* ڈیٹا محفوظ کرنے کے لیے ڈیزائن کیا گیا ہے۔

اگر ہر مینو آئٹم کے ایک جیسے فیلڈز ہوتے — نام، قیمت، تفصیل، قسم — تو SQL بالکل درست ہوتا۔ آپ کے پاس ایک صاف `menu_items` ٹیبل ہوتا، ہر آئٹم کے لیے قطاریں، اور queries جو سمجھ میں آتیں۔

لیکن حقیقی مینوز اس طرح کام نہیں کرتے۔

ایک آئٹم کا "مصالحے کی سطح" ترمیم کنندہ ہو سکتا ہے۔ دوسرے کا "پروٹین کا انتخاب" ہو سکتا ہے۔ تیسرے میں نیسٹڈ کومبوز ہو سکتے ہیں — "خاندانی کھانا آرڈر کریں اور آپ کو دو مین، دو سائڈز، اور ایک مشروب ملتا ہے۔" ڈیٹا کی ساخت *فی آئٹم* مختلف ہوتی ہے۔

SQL میں، آپ کے پاس دو آپشن ہیں:

**آپشن 1**: ہر ممکنہ ترمیم کنندہ کے لیے ایک کالم بنائیں۔ اس سے ایک بہت چوڑا ٹیبل بنتا ہے جہاں زیادہ تر کالم زیادہ تر وقت خالی ہوتے ہیں۔

**آپشن 2**: ایک الگ modifiers ٹیبل بنائیں اور اسے menu items ٹیبل سے جوڑیں۔ یہ کام کرتا ہے، لیکن پیچیدہ مینوز کے لیے متعدد joins کی ضرورت ہوتی ہے، اور پچاس ہزار آئٹمز کے ساتھ اعلیٰ ریڈ والیوم پر، وہ joins مہنگے ہو جاتے ہیں۔

"ایک تیسرا آپشن ہے،" Priya نے کہا، جو کونے میں خاموشی سے دستاویزات پڑھ رہی تھی۔

اس نے ایک نیا ٹیب کھولا۔ "کیا ہو اگر ڈیٹا کو ٹیبل میں فٹ نہ ہونا پڑے؟"

**ڈیٹا کے بارے میں سوچنے کا ایک مختلف طریقہ**

ریلیشنل ڈیٹابیسز ڈیٹا کو ٹیبلز میں قطاروں کے طور پر محفوظ کرتے ہیں۔ ہر قطار کو ٹیبل کے اسکیما کے مطابق ہونا چاہیے۔ اسکیما پہلے سے طے ہوتا ہے۔

NoSQL ڈیٹابیسز ڈیٹا مختلف طریقے سے محفوظ کرتے ہیں۔ ایک عام طریقہ *document model* ہے: ہر ریکارڈ ایک خود کفیل document (عام طور پر JSON) کے طور پر محفوظ ہوتا ہے، اور ایک ہی collection میں documents کے ایک جیسے فیلڈز ہونا ضروری نہیں۔

document model میں ایک مینو آئٹم اس طرح نظر آ سکتا ہے:

```json
{
  "itemId": "ITEM-001",
  "restaurantId": "NIMBUS-047",
  "name": "Shrimp Arepa",
  "price": 3200,
  "modifiers": [
    { "name": "Spice Level", "options": ["mild", "medium", "hot"] },
    { "name": "Protein", "options": ["shrimp", "fish", "mixed"] }
  ],
  "available": true,
  "seasonalUntil": "2024-03-31"
}
```

ایک اور آئٹم بالکل مختلف نظر آ سکتا ہے:

```json
{
  "itemId": "ITEM-002",
  "restaurantId": "NIMBUS-047",
  "name": "Family Feast",
  "price": 9800,
  "includes": ["ITEM-010", "ITEM-011", "ITEM-015", "ITEM-020"],
  "servings": 4,
  "available": true
}
```

مختلف شکلیں۔ ایک ہی collection۔ کوئی مسئلہ نہیں۔

"تو ڈیٹابیس ٹیبل سے زیادہ فائلنگ سسٹم کی طرح ہے،" Maya نے کہا۔

"بالکل،" Priya نے کہا۔ "آپ کسی بھی drawer میں کوئی بھی document ڈال سکتے ہیں۔ آپ کو document کو مقررہ سائز میں فٹ کرنے کے لیے کاٹنا نہیں پڑتا۔"

**DynamoDB سے ملیں**

Amazon DynamoDB AWS کی منیجڈ NoSQL ڈیٹابیس سروس ہے۔ یہ ڈیٹا کو آئٹمز (قطاریں نہیں) کے طور پر محفوظ کرتا ہے، اور آئٹمز ٹیبلز میں جمع ہوتے ہیں (نام SQL سے ملتا جلتا ہے، لیکن رویہ مختلف ہے)۔

DynamoDB ٹیبل میں ہر آئٹم کا ایک **primary key** ہونا چاہیے، جو اسے منفرد طور پر شناخت کرے۔ باقی سب لچکدار ہے۔

primary key دو شکلوں میں سے ایک ہو سکتی ہے:

**صرف partition key**: ایک واحد attribute جو تمام آئٹمز میں منفرد ہونا چاہیے۔

**partition key + sort key (composite primary key)**: دو attributes جو *مل کر* ایک منفرد مجموعہ بناتے ہیں۔ یہ آپ کو ایک ہی partition key والے متعدد آئٹمز رکھنے دیتا ہے، جو ان کی sort key سے الگ ہوتے ہیں۔

Nimbus کے مینو کے لیے:

- Partition key: `restaurantId`
- Sort key: `itemId`

اس کا مطلب ہے آپ ایک مخصوص ریستوران کے تمام آئٹمز کو مؤثر طریقے سے بازیافت کر سکتے ہیں — DynamoDB کو عین معلوم ہے کہ کس partition میں دیکھنا ہے۔

"اسے partition key کیوں کہتے ہیں؟" Tom نے پوچھا۔

"اور کیا ہو اگر کوئی توڑ کر داخل ہونے کی کوشش کرے؟" Priya نے پوچھا۔ "اگر partition key کا اندازہ لگایا جا سکتا ہے، تو کیا کوئی ایک partition کو رائٹس سے بھر کر جان بوجھ کر hot-spot کی حالت پیدا کر سکتا ہے؟"

"ہاں،" Leo نے کہا۔ "یہ دراصل خراب ڈیزائن شدہ ٹیبلز کے لیے ایک denial-of-service ویکٹر ہے۔ جو اعلیٰ-cardinality keys چننے کی ایک اور وجہ ہے۔"

Priya نے یہ لکھ لیا۔

**DynamoDB داخلی طور پر ڈیٹا کیسے محفوظ کرتا ہے**

DynamoDB کو بہت بڑے سائز تک افقی طور پر اسکیل کرنے کے لیے بنایا گیا ہے۔ یہ *partitioning* کے ذریعے حاصل ہوتا ہے — partition key کی بنیاد پر ڈیٹا کئی جسمانی مشینوں میں تقسیم ہوتا ہے۔

جب آپ کوئی آئٹم لکھتے ہیں، DynamoDB partition key کی قدر کو hash کرتا ہے اور اس hash کو استعمال کر کے طے کرتا ہے کہ کون سی جسمانی partition (اور اس طرح کون سا سرور) آئٹم محفوظ کرے گا۔ جب آپ کوئی آئٹم پڑھتے ہیں، DynamoDB اسے فوری طور پر تلاش کرنے کے لیے وہی حساب لگاتا ہے۔

اسے ایک پوسٹل سسٹم کی طرح سوچیں۔ اگر ہر لفافے پر ایک zip کوڈ ہے، تو پوسٹل سروس یہ معلوم کرنے کے لیے ہر لفافہ نہیں پڑھتی کہ یہ کہاں سے تعلق رکھتا ہے — یہ zip کوڈ کے مطابق ترتیب دیتی ہے۔ DynamoDB partition key hash کے مطابق ترتیب دیتا ہے۔

"رکیں — لیکن ہم *کیوں* اسے اس طرح کریں؟" Maya نے پوچھا۔ "partition key کا انتخاب اتنا اہم کیوں ہے؟ کیا ہم کچھ بھی نہیں چن سکتے؟"

یہ صحیح سوال ہے۔ partition key DynamoDB اسکیما میں سب سے اہم ڈیزائن کا فیصلہ ہے۔ یہاں وجہ ہے:

اگر آپ کم cardinality والی partition key چنتے ہیں — جیسے `available: true/false`، یا `category: "main/side/drink"` — تو آپ کا زیادہ تر ڈیٹا انہی چند partitions پر اترتا ہے۔ DynamoDB اسے "hot partition" کہتا ہے۔ ایک سرور زیادہ تر ٹریفک سنبھالتا ہے۔ یہ اوورلوڈ ہو جاتا ہے۔ DynamoDB درخواستیں throttle کرنا شروع کر دیتا ہے۔ صارف خرابیاں دیکھنا شروع کر دیتے ہیں۔

- **اچھی**: اعلیٰ cardinality، یکساں طور پر تقسیم شدہ قدریں (`restaurantId` بہت سارے ریستورانوں کے ساتھ)
- **بری**: کم cardinality (`true/false`، `category`) — زیادہ تر ڈیٹا چند partitions پر اترتا ہے، "hot spots" بناتا ہے

"تو اگر میں نے `available: true` کو partition key کے طور پر استعمال کیا،" Leo نے آہستہ آہستہ کہا، "تمام دستیاب آئٹمز ایک ہی partition پر ڈھیر ہو جاتے۔"

"اور رات کے کھانے کی بھیڑ میں آپ کا ڈیٹابیس پگھل جاتا،" Priya نے تصدیق کی۔

Leo نے آہستہ آہستہ اپنا لیپ ٹاپ بند کیا۔

**Hot Partition کا واقعہ**

انہیں اسے تصور کرنا نہیں پڑے گا۔ کئی مہینے بعد — DynamoDB پر اپنے دوسرے مہینے کے دوران، اس سے پہلے کہ انہوں نے واقعی اس قاعدے کو اپنے اندر سمو لیا ہوتا — وہ اسے مشکل طریقے سے سیکھیں گے۔

ٹیم نے ایک نئی خصوصیت لانچ کی تھی: ایک "Featured Items" بیج۔ ریستوران پارٹنرز پانچ تک آئٹمز کو featured نشان زد کر سکتے تھے۔ خصوصیت ہر آئٹم پر ایک `featured: true` attribute محفوظ کرتی تھی۔

Leo نے سوچا کہ تمام ریستورانوں میں تمام featured آئٹمز کو query کرنا مفید ہوگا — ہوم پیج پر ایک "trending items" ویجٹ کے لیے۔ اس نے اس query کو سپورٹ کرنے کے لیے ایک secondary index بنایا تھا۔ index نے `featured` کو اپنی partition key کے طور پر استعمال کیا۔

"یہ ٹھیک رہے گا،" اس نے کہا تھا۔ "کتنے featured آئٹمز ہو سکتے ہیں؟"

تقریباً بارہ سو، دو سو چالیس ریستورانوں میں پھیلے ہوئے۔

لیکن "trending items" ویجٹ ہر صفحے پر لوڈ ہوتا تھا۔ ہر صفحہ لوڈ `featured` index کے خلاف ایک query کو trigger کرتا تھا۔ تمام بارہ سو آئٹمز دو partitions پر رہتے تھے — `true` اور `false`۔ `true` partition ہر ہٹ لیتا تھا۔

جمعہ کی شام رات کے کھانے کی بھیڑ۔ آٹھ ہزار بیک وقت صارف۔ سب ہوم پیج لوڈ کر رہے تھے۔

DynamoDB ایرر ریٹ بڑھ کر اٹھارہ فیصد ہو گیا۔ کچھ صارفین کو خالی trending ویجٹ ملا۔ کچھ کو لوڈنگ اسپنرز ملے۔ کچھ کو ایسی خرابیاں ملیں جو آرڈرنگ فلو میں اوپر آ گئیں۔

Leo نے میٹرکس نکالے۔ "index partition throttle ہو رہا ہے،" اس نے کہا۔ "ہم ایک ہی partition پر throughput حد سے ٹکرا رہے ہیں۔"

"کیسے؟" Priya نے پوچھا۔

"`featured` key کی صرف دو قدریں ہیں۔ تمام بارہ سو featured آئٹمز ایک ہی partition پر رہتے ہیں۔ ہر ہوم پیج لوڈ اس partition سے ٹکراتا ہے۔"

انہوں نے تین منٹ کے اندر trending ویجٹ غیر فعال کر دیا۔ ایرر ریٹ صفر پر آ گیا۔

"تو ایک دو-قدر والی partition key نے ہمیں جمعہ کی رات throttle کر دیا،" Tom نے کہا۔

"اس پر ہمیں کتنا خرچ آیا؟"

"آٹھ ہزار صارفین میں تقریباً چالیس منٹ کا کمزور تجربہ،" Priya نے کہا۔ "آمدنی پر اثر، شاید چند سو آرڈرز۔"

"پہلے اپنے رسائی کے نمونے ڈیزائن کریں،" Priya نے کہا۔ "پھر اپنا ڈیٹا ماڈل چنیں۔"

**پیمانے پر پڑھنا اور لکھنا**

DynamoDB فی سیکنڈ لاکھوں درخواستیں سنبھال سکتا ہے۔ لیکن اسے جاننا ضروری ہے کہ کتنی صلاحیت فراہم کرنی ہے۔

دو صلاحیت کے طریقے ہیں:

**Provisioned capacity**: آپ بتاتے ہیں کہ آپ کتنی ریڈ اور رائٹ یونٹس چاہتے ہیں۔ DynamoDB آپ کے لیے وہ صلاحیت محفوظ کرتا ہے اور اس سے زیادہ ٹریفک کو throttle کرتا ہے۔ قابل پیش گوئی لاگت، فی درخواست کم قیمت۔

یونٹس کی درست تعریفیں ہیں، اور امتحان ان سے آپ کے واقف ہونے کی توقع رکھتا ہے: ایک **Read Capacity Unit (RCU)** ایک آئٹم کے 4 KB تک کی فی سیکنڈ ایک strongly consistent ریڈ ہے — یا اسی سائز کی دو eventually consistent ریڈز۔ ایک **Write Capacity Unit (WCU)** ایک آئٹم کے 1 KB تک کی فی سیکنڈ ایک رائٹ ہے۔ بڑے آئٹمز متناسب طور پر زیادہ استعمال کرتے ہیں: ایک 12 KB آئٹم کو strongly consistent پڑھنے پر 3 RCUs لگتے ہیں؛ ایک 3 KB آئٹم لکھنے پر 3 WCUs لگتے ہیں۔

**On-demand capacity**: DynamoDB خودبخود آپ کی اصل ٹریفک کے ساتھ اسکیل ہوتا ہے۔ روٹین صلاحیت کی منصوبہ بندی ضروری نہیں۔ فی درخواست زیادہ لاگت، اور آپریشنل طور پر بہت آسان، اگرچہ ٹیبل کی حالیہ ٹریفک کے نمونے سے بہت آگے اچانک اضافے اگر بہت تیزی سے بڑھیں تو پھر بھی throttling کا سبب بن سکتے ہیں۔

Nimbus کے لیے، مینو اسے لکھنے سے کہیں زیادہ پڑھا جاتا ہے۔ صارف ایپ کھولتا ہے، مینو براؤز کرتا ہے — یہ بہت سی ریڈز ہیں۔ ریستوران پارٹنر اپنا مینو ہفتے میں دو بار اپڈیٹ کرتا ہے — یہ کبھی کبھار رائٹس ہیں۔

"On-demand ابھی کے لیے سمجھ آتا ہے،" Tom نے کہا۔ "ہمیں ابھی تک اپنے ٹریفک کے نمونے معلوم نہیں ہیں۔ under-provision کر کے throttle ہونے سے بہتر ہے کہ فی درخواست زیادہ ادائیگی کریں۔"

بے رغبتی سے بنیادی ڈھانچے کی حکمت۔ Tom کی طرف سے۔ ٹیم باضابطہ طور پر بڑی ہو گئی تھی۔

"اس پر فی مہینہ کتنا خرچ آتا ہے؟" Tom نے pricing کیلکولیٹر کھولتے ہوئے پوچھا۔

"ہمارے موجودہ ریڈ والیوم پر — تقریباً چالیس ہزار ریڈز فی دن — on-demand تقریباً بارہ ڈالر فی مہینہ ہے،" Leo نے کہا۔ "Provisioned، اگر ہم اسے ٹھیک ٹیون کریں، تو چار کے قریب ہے۔ لیکن ہمیں صلاحیت دستی طور پر سیٹ کرنی پڑے گی اور اگر غلط اندازہ لگائیں تو throttling کا خطرہ ہوگا۔"

**مستقل مزاجی: آپ کا ڈیٹا کتنا تازہ ہے؟**

DynamoDB خودبخود متعدد Availability Zones میں ڈیٹا نقل کرتا ہے۔ یہ پائیداری کے لیے بہترین ہے، لیکن اس کا مطلب یہ بھی ہے کہ آپ کو ریڈ مستقل مزاجی کے بارے میں واضح طور پر سوچنا ہوگا۔

جب آپ DynamoDB سے پڑھتے ہیں، آپ کے پاس انتخاب ہے:

**Eventually consistent read**: یہ ڈیفالٹ ہے۔ یہ سستا ہے، اور نتیجہ حال ہی میں مکمل ہونے والی رائٹ سے مختصر طور پر پیچھے ہو سکتا ہے۔

**Strongly consistent read**: ٹیبل یا local secondary index کے خلاف ریڈز کے لیے، DynamoDB کامیاب پچھلی رائٹس سے تازہ ترین کمٹ شدہ قدر واپس کر سکتا ہے۔ اس میں زیادہ ریڈ صلاحیت لگتی ہے اور یہ global secondary indexes کے لیے دستیاب نہیں ہے۔

مینو ڈیٹا کے لیے، eventual consistency ٹھیک ہے۔ ایک ملی سیکنڈ پرانا مینو آئٹم کوئی اہمیت نہیں رکھتا۔

آرڈر کنفرمیشن ڈیٹا کے لیے — "کیا یہ آرڈر دیا جا چکا ہے؟" — آپ strong consistency چاہیں گے۔ صارف کو "دوبارہ کوشش کریں" پیغام نہیں ملنا چاہیے جب ان کا آرڈر ابھی محفوظ ہوا ہو۔

"یہ ایسا ہی ہے جیسے ایپ پر اپنا بینک بیلنس چیک کرنا بمقابلہ بینک کو براہ راست فون کرنا،" Maya نے کہا۔ "ایپ تیس سیکنڈ پیچھے ہو سکتی ہے۔ فون کال ہمیشہ موجودہ ہے۔"

آپ سوچ رہے ہوں گے: اگر DynamoDB خودبخود متعدد AZs میں نقل کرتا ہے، تو consistency کا طریقہ سرے سے کیوں اہم ہے؟ یہاں جواب ہے: ریپلیکیشن میں ایک چھوٹا لیکن غیر صفر وقت لگتا ہے — عام طور پر ملی سیکنڈز۔ ایک eventually consistent ریڈ ایسے replica سے فراہم ہو سکتی ہے جسے ابھی تازہ ترین رائٹ موصول نہیں ہوئی۔ ایک strongly consistent ریڈ ہمیشہ ڈیٹا کی primary کاپی سے رابطہ کرتی ہے۔ زیادہ تر استعمال کے معاملات کے لیے (مینو آئٹمز، پروڈکٹ کیٹلاگ، صارف کے پروفائلز) تاخیر ناقابل محسوس ہوتی ہے۔ ان معاملات کے لیے جہاں ریڈ کے لمحے درستگی اہم ہو (ادائیگی کی تصدیق، انوینٹری کی دستیابی)، آپ strong consistency چاہتے ہیں۔

**Secondary Indexes: Primary Key سے آگے Query کرنا**

کیا ہو اگر آپ کو ڈیٹا تک اس طرح رسائی کی ضرورت ہو جس کی primary key اجازت نہیں دیتی؟

DynamoDB **secondary indexes** سپورٹ کرتا ہے — متبادل keys جو آپ کو مختلف attributes کا استعمال کر کے وہی ڈیٹا query کرنے دیتے ہیں۔

**Local Secondary Index (LSI)**: ٹیبل کی وہی partition key استعمال کرتا ہے، لیکن ایک مختلف sort key۔ اسے ٹیبل بنانے کے وقت پر بیان کرنا ضروری ہے اور بعد میں شامل نہیں کیا جا سکتا۔ ٹیبل کی provisioned صلاحیت کا اشتراک کرتا ہے۔ چونکہ LSIs partition کا اشتراک کرتے ہیں، یہ strongly consistent ریڈز سپورٹ کرتے ہیں۔

**Global Secondary Index (GSI)**: ایک مکمل طور پر الگ index جس کی اپنی partition key اور sort key ہوتی ہے — ٹیبل کی primary key سے مختلف۔ ٹیبل کے موجود ہونے کے بعد شامل یا ہٹایا جا سکتا ہے، جو آپ کو لچک دیتا ہے۔ اس کی اپنی provisioned صلاحیت کی ترتیبات ہوتی ہیں، جو ٹیبل سے الگ ہوتی ہیں۔

Nimbus کے لیے: اگر انہیں قیمت کی رینج کے لحاظ سے آئٹمز query کرنے کی ضرورت ہوتی، تو ایک GSI اسے سپورٹ کر سکتا تھا — لیکن ایک قاعدہ ذہن میں رکھتے ہوئے: ایک partition key صرف *equality* موازنے قبول کرتی ہے، لہٰذا `price` (جس پر آپ رینج کرنا چاہتے ہیں) کو **sort key** ہونا چاہیے، جس میں کسی گروپنگ attribute جیسے category یا `cuisineType#region` کو GSI partition key کے طور پر رکھا جائے۔ یہ بالکل وہی index ہے جو نیچے دیے گئے walkthrough میں بنایا گیا ہے۔

اگر آپ LSI چنتے ہیں، تو آپ کو strong consistency اور مشترکہ صلاحیت ملتی ہے، لیکن آپ ٹیبل بنانے کے وقت اس ڈیزائن میں قید ہو جاتے ہیں؛ اگر آپ GSI چنتے ہیں، تو آپ کو اسے بعد میں شامل کرنے کی لچک اور آزاد اسکیلنگ ملتی ہے، لیکن آپ index کے خلاف strongly consistent ریڈز کرنے کی صلاحیت کھو دیتے ہیں۔

**ایک GSI Query Walkthrough**

Priya نے ایک ٹھوس مثال کے ذریعے بات کی۔ Nimbus ایک "براؤز بائی cuisine" خصوصیت سپورٹ کرنا چاہتا تھا: تمام پارٹنر ریستورانوں میں ایک خاص cuisine قسم کے تمام دستیاب پکوان دکھانا۔

مرکزی ٹیبل میں `restaurantId` partition key کے طور پر اور `itemId` sort key کے طور پر ہے۔ آپ "تمام آئٹمز جہاں cuisineType = Colombian" کو مؤثر طریقے سے query نہیں کر سکتے — اس کے لیے ہر partition میں ایک scan درکار ہوگا۔

انہوں نے ایک GSI بنایا:

- GSI partition key: `cuisineType#region` (مثلاً "Colombian#NYC"، "Mexican#Chicago")
- GSI sort key: `price`

GSI ہر آئٹم کی ایک projection کو نقل کرتا ہے — صرف وہ فیلڈز جو براؤز صفحے کے لیے درکار ہیں — index اسٹوریج میں۔ اب `cuisineType#region = "Colombian#NYC"` کے ساتھ GSI کے خلاف ایک query براہ راست index کے اس partition پر جاتی ہے۔

"صرف `cuisineType` اکیلے کیوں نہیں استعمال کرتے؟" Leo نے پوچھا۔

"کیونکہ cuisineType اکیلے کی cardinality کم ہے،" Priya نے کہا۔ "Colombian، Mexican، Thai — کل بیس قدریں۔ پھر سے hot partitions۔ region شامل کرنے سے ہمیں Colombian#NYC، Colombian#Chicago، Colombian#LA ملتے ہیں۔ زیادہ partitions، بہتر تقسیم۔"

"یہ تھوڑا غیر معیاری لگتا ہے۔"

"یہ ایک معیاری DynamoDB پیٹرن ہے۔ اسے partition key sharding کہتے ہیں۔ کبھی کبھی آپ کو آلے کے ساتھ کام کرنا پڑتا ہے۔"

کوڈ میں GSI query اس طرح نظر آتی تھی:

```python
response = dynamodb.query(
    TableName='menu',
    IndexName='cuisineType-price-index',
    KeyConditionExpression='#ct = :ct AND price BETWEEN :lo AND :hi',
    ExpressionAttributeNames={'#ct': 'cuisineType#region'},
    ExpressionAttributeValues={
        ':ct': {'S': 'Colombian#NYC'},
        ':lo': {'N': '1000'},
        ':hi': {'N': '2500'}
    }
)
```

اس نے نیویارک سٹی کے تمام Colombian پکوان واپس کیے جن کی قیمت $10 اور $25 کے درمیان تھی، قیمت کے لحاظ سے ترتیب دیے گئے، تقریباً 4 ملی سیکنڈ میں۔

"یہ پرانی SQL query سے ایک ہزار گنا تیز ہے،" Leo نے کہا۔

"کیونکہ یہ صرف ایک index کے ایک partition کو چھو رہی ہے،" Priya نے تصدیق کی۔ "ایک جوائنڈ ٹیبل میں ہر قطار کو scan نہیں کر رہی۔"

**DynamoDB Streams: تبدیلیوں پر ردعمل**

"کیا ہم نے سوچا ہے کہ جب کوئی مینو آئٹم اپڈیٹ ہوتا ہے تو کیا ہوتا ہے؟" Priya نے ایک صبح پوچھا۔ "ایک ریستوران پارٹنر قیمت بدلتا ہے۔ ہمیں سرچ index اپڈیٹ کرنا ہے۔ ہمیں ElastiCache entry کو invalidate کرنا ہے" — caching سروس جس سے ہم اگلے باب میں ملیں گے — "اور ہمیں اپنی analytics pipeline کے لیے تبدیلی لاگ کرنی ہے۔"

"ہم یہ سب API handler میں کر سکتے ہیں،" Leo نے کہا۔ "جب رائٹ ہو، تو تمام downstream اپڈیٹس trigger کریں۔"

"اور اگر ان میں سے کوئی ایک ناکام ہو جائے؟"

"تو... ہم دوبارہ کوشش کرتے ہیں۔"

"کیا ہو اگر رائٹ کے بعد لیکن downstream اپڈیٹس سے پہلے EC2 instance کریش ہو جائے؟ ڈیٹا محفوظ ہے، لیکن کسی کو تبدیلی کا علم نہیں۔"

Leo نے اس پر سوچا۔

"ہمیں اپڈیٹ کی ضمانت چاہیے،" اس نے کہا۔ "چاہے ہمارا ایپلیکیشن کوڈ بیچ میں ناکام ہو جائے۔"

یہی وہ ہے جسے **DynamoDB Streams** حل کرتا ہے۔

DynamoDB Streams ایک DynamoDB ٹیبل میں ہر آئٹم کی ترمیم کا ایک وقت کے لحاظ سے ترتیب شدہ لاگ پکڑتا ہے۔ ہر insert، update، اور delete کو ایک event کے طور پر stream میں لکھا جاتا ہے۔ stream events کو 24 گھنٹے تک برقرار رکھتا ہے۔

آپ stream کے ساتھ ایک Lambda function منسلک کر سکتے ہیں۔ ہر بار جب کوئی آئٹم بدلتا ہے، Lambda function کو آئٹم کی پہلے اور بعد کی حالت کے ساتھ invoke کیا جاتا ہے۔ پھر Lambda یہ کر سکتا ہے:

- ایک سرچ index اپڈیٹ کرے (OpenSearch)
- ElastiCache میں ایک cache entry invalidate کرے
- کسی دوسرے نظام کو ایک اطلاع بھیجے
- ایک analytics pipeline کو فیڈ کرے
- تبدیلی کو کسی دوسرے ٹیبل یا ڈیٹابیس میں نقل کرے

اہم فرق: Streams رائٹ کو downstream اثرات سے الگ کر دیتے ہیں۔ DynamoDB رائٹ اس بات سے قطع نظر کامیاب ہوتا ہے کہ Lambda کامیاب ہوتا ہے یا نہیں۔ اگر Lambda ناکام ہو جائے، DynamoDB اسے دوبارہ کوشش کرتا ہے۔ اگر رائٹ کے بعد ایپلیکیشن کریش ہو جائے، تو stream event پھر بھی موجود ہے — Lambda حالات بحال ہونے پر اسے پروسیس کرے گا۔

"تو ہم DynamoDB میں لکھتے ہیں،" Leo نے آہستہ آہستہ کہا، "اور DynamoDB ضمانت دیتا ہے کہ downstream پروسیسنگ بالآخر ہو گی، چاہے ہم کریش ہو جائیں۔"

"بالکل،" Priya نے کہا۔ "یہ امید کرنے کہ آپ کے تمام side effects چلیں گے، اور ڈیٹابیس کے ان کی ضمانت دینے کے درمیان فرق ہے۔"

Nimbus کے لیے، انہوں نے مینو ٹیبل پر DynamoDB Streams کو ایک Lambda سے جوڑا جو مینو آئٹمز بدلنے پر ElastiCache entries کو invalidate کرتا تھا۔ cache ڈیٹابیس کے ساتھ مستقل رہا، خودبخود، invalidation کا انتظام کرنے والے کسی ایپلیکیشن کوڈ کے بغیر۔

"Streams پر کتنا خرچ آتا ہے؟" Tom نے پوچھا۔

"آپ stream سے پڑھنے کے لیے ادائیگی کرتے ہیں — ہر Lambda invocation اس سے پڑھتا ہے۔ ہمارے والیوم پر، شاید دو سے تین ڈالر فی مہینہ۔"

Tom نے اسے مزید سوالات کے بغیر منظور کر لیا۔ اس نے سیکھ لیا تھا کہ کب دو ڈالر فی مہینہ قابل قدر تھے۔

**ٹریڈ آف: DynamoDB کیا نہیں کر سکتا**

NoSQL سختی سے SQL سے بہتر نہیں ہے۔ یہ ایک مختلف کام کے لیے ایک مختلف آلہ ہے۔

DynamoDB کیا چھوڑتا ہے:

**لچکدار queries**: SQL میں، آپ کسی بھی کالم سے فلٹر اور ترتیب دے سکتے ہیں۔ DynamoDB میں، آپ صرف primary key کے ذریعے مؤثر طریقے سے query کر سکتے ہیں۔ من مانی فیلڈز کے ذریعے querying کے لیے ایک *scan* (ٹیبل میں ہر آئٹم پڑھنا) کی ضرورت ہے، جو پیمانے پر مہنگا اور سست ہے۔

**Joins**: DynamoDB joins نہیں کرتا۔ اگر آپ کو دو ٹیبلز سے ڈیٹا چاہیے، تو آپ اپنے ایپلیکیشن کوڈ میں دو الگ ریڈز کرتے ہیں۔

**Transactions**: DynamoDB transactions سپورٹ کرتا ہے، لیکن ریلیشنل ڈیٹابیسز بہت سے کثیر-entity workflows، رپورٹنگ-بھاری نظاموں، اور join-بھاری ڈیزائنوں کے لیے اب بھی زیادہ قدرتی فٹ ہیں۔

**واقفیت**: SQL ٹولنگ، ہنر، اور ذہنی ماڈلز کی دہائیاں براہ راست منتقل نہیں ہوتیں۔

DynamoDB کیا بہترین کرتا ہے:

- key-value اور document رسائی کے نمونے
- بڑے پیمانے (کسی بھی سائز پر single-digit millisecond latency)
- بے سرور، کوئی infrastructure management نہیں
- خودکار اسکیلنگ، multi-AZ ریپلیکیشن، بیک اپ
- ڈیٹا والیوم سے قطع نظر قابل پیش گوئی کارکردگی

"تو قاعدہ یہ ہے،" Maya نے کہا، "DynamoDB استعمال کریں جب آپ *بالکل* جانتے ہوں کہ آپ ڈیٹا تک کیسے رسائی کریں گے۔ SQL استعمال کریں جب آپ ابھی تک نہیں جانتے۔"

Priya نے اثبات میں سر ہلایا۔ "پہلے اپنے رسائی کے نمونے ڈیزائن کریں۔ پھر اپنا ڈیٹابیس چنیں۔"

یہ ان سب سے سینئر باتوں میں سے ایک ہے جو ایک ڈیٹابیس گفتگو سے پیدا ہو سکتی ہے۔

**جب DynamoDB غلط انتخاب ہو**

Tom، جس نے مالی رپورٹنگ ماڈیول سنبھالا تھا، کا ایک سوال تھا۔

"ہم مالی رپورٹنگ بنا رہے ہیں،" اس نے کہا۔ "فی ریستوران ماہانہ آمدنی کے خلاصے، ٹیکس کیلکولیشنز، انوائس کی تاریخ۔ کیا ہم اسے بھی DynamoDB میں ڈال سکتے ہیں؟"

ٹیم نے ایک دوسرے کی طرف دیکھا۔

"رکیں — لیکن ہم *کیوں* اسے اس طرح کریں؟" Maya نے پوچھا، اس سے پہلے کہ Priya پوچھ سکتی۔

Priya مسکرائی۔ Maya عادت اپنا رہی تھی۔

"queries کے بارے میں ہمیں بتاؤ،" Priya نے Tom سے کہا۔

اس نے اسپیک کھولی۔ "ہمیں چاہیے: فی ریستوران کل آمدنی، ہفتے کے لحاظ سے گروپ کی گئی۔ تمام ریستورانوں میں آرڈر کی تعداد کے لحاظ سے بہترین کارکردگی والے آئٹمز۔ cuisine قسم کے لحاظ سے آمدنی کی تقسیم۔ شہر کے لحاظ سے اوسط آرڈر ویلیو۔ پارٹنر رپورٹنگ کے لیے سال بہ سال موازنہ۔"

Leo نے فہرست پڑھی۔ "ان میں سے ہر ایک ایک aggregation ہے۔ Sum، group، average، compare۔"

"DynamoDB میں کوئی aggregation functions نہیں ہیں،" Priya نے کہا۔ "کوئی GROUP BY نہیں۔ کوئی SUM نہیں۔ کوئی AVG نہیں۔ 'اس ہفتے فی ریستوران کل آمدنی' کا جواب دینے کے لیے، آپ کو ہفتے کے ہر آرڈر کو scan کرنا ہوگا، یہ سب ایپلیکیشن میموری میں کھینچنا ہوگا، اور خود اسے حساب کرنا ہوگا۔"

"یہ برا لگتا ہے،" Tom نے کہا۔

"ہمارے پیمانے پر، یہ ہر رپورٹ درخواست کے لیے دسیوں ہزار ریکارڈز میموری میں کھینچے جاتے ہیں۔ یہ سست اور مہنگا ہوگا۔ اور ہر بار جب ہم کوئی نئی رپورٹ کی ضرورت شامل کرتے، ہم نیا scan-and-compute کوڈ لکھ رہے ہوتے۔"

"تو ہم کیا استعمال کریں؟"

"مالی رپورٹنگ کے لیے؟ RDS۔ مناسب indexes کے ساتھ PostgreSQL۔ جو queries آپ نے بیان کیں وہ بالکل وہی ہیں جن کے لیے SQL ڈیزائن کیا گیا تھا۔ یہ دس لائنوں کی SQL ہوں گی۔ یہ دو سو لائنوں کا DynamoDB scan کوڈ ہوں گی۔"

DynamoDB غلط ہے جب:

- آپ پیشگی اپنے رسائی کے نمونے نہیں جانتے (رپورٹنگ فطری طور پر تحقیقاتی ہے)
- آپ کو بڑے ڈیٹا سیٹس میں aggregations (SUM، GROUP BY، COUNT) کی ضرورت ہو
- آپ کے ڈیٹا کے پیچیدہ رشتے ہوں اور آپ کو joins کی ضرورت ہو
- آپ کو ad-hoc query لچک کی ضرورت ہو — ایسے سوالات پوچھنے کے لیے جن کے بارے میں آپ نے ابھی تک نہیں سوچا
- آپ کے ڈیٹا کی بنیادی طور پر ریلیشنل ساخت ہو جو قدرتی طور پر key-value سے میل نہیں کھاتی

"تو انتخاب یہ نہیں ہے کہ 'نئی ٹیکنالوجی بہتر ہے،'" Maya نے کہا۔

"انتخاب یہ ہے کہ 'آپ کے ڈیٹا کی شکل کیا ہے، اور آپ اس تک کیسے رسائی کریں گے،'" Priya نے تصدیق کی۔ "DynamoDB حقیقتاً مینو کے لیے بہتر ہے۔ یہ حقیقتاً مالی رپورٹس کے لیے بدتر ہوگا۔ دونوں بیانات ایک ہی وقت میں سچ ہیں۔"

Tom نے مالی رپورٹنگ PostgreSQL پر بنائی۔ پہلی GROUP BY query جو اس نے لکھی 80 ملی سیکنڈ میں واپس آئی۔ اسے scan کوڈ کی ایک لائن بھی لکھنے کی ضرورت نہیں پڑی۔

**کب کون سا استعمال کریں**

| صورتحال                                                | ان کی طرف رجوع کریں      |
|-------------------------------------------------------|-------------------------|
| منظم ڈیٹا، پیچیدہ queries، رپورٹنگ                     | RDS (PostgreSQL، MySQL) |
| لچکدار ڈیٹا شکلیں، key-based رسائی، بڑے پیمانے          | DynamoDB                |
| پیچیدہ رشتوں کے ساتھ رائٹ-بھاری                         | RDS                     |
| قابل پیش گوئی رسائی کے نمونوں کے ساتھ ریڈ-بھاری          | DynamoDB                |
| آپ کو joins اور aggregates کی ضرورت ہے                  | RDS                     |
| آپ کو لاکھوں req/sec پر ملی سیکنڈ latency کی ضرورت ہے   | DynamoDB                |
| متعدد entities میں Transactions                        | RDS (عام طور پر)        |
| بے سرور / غیر قابل پیش گوئی ٹریفک اضافے                 | DynamoDB on-demand      |
| مالی رپورٹنگ، ad-hoc analytics                          | RDS یا ایک data warehouse |
| Event sourcing، change capture، real-time processing   | DynamoDB + Streams      |

غلط جواب ہمیشہ "ہمیشہ ایک یا دوسرا استعمال کریں" ہوتا ہے۔ Nimbus نے بالآخر دونوں استعمال کیے: آرڈر کی تاریخ اور مالی ریکارڈز کے لیے RDS (منظم، ریلیشنل، رپورٹنگ کی ضرورت ہے)، مینو کے لیے DynamoDB (لچکدار اسکیما، اعلیٰ ریڈ والیوم، ریستوران ID کے ذریعے رسائی)۔

## صحیح ورک لوڈ کے لیے صحیح ڈیٹابیس

چھ مہینے آگے بڑھیں — DynamoDB منتقلی کے ٹھیک سے بیٹھ جانے کے کافی بعد — اور Nimbus کے پاس بورڈ پر تین نئے پروجیکٹ تھے۔ Maya نے ایک منگل کی صبح ٹیم کو ان کے بارے میں بتایا۔

"پہلا: ایک recommendation engine۔ ہم گاہکوں کو ایسے پکوان دکھانا چاہتے ہیں جن کا آرڈر دینے کا امکان ہے، ان کی تاریخ اور ملتے جلتے ذوق والے لوگوں کے آرڈر کی بنیاد پر۔ دوسرا: ہم مینو ڈیٹا کو زیادہ بھرپور مواد سپورٹ کرنے کے لیے منتقل کر رہے ہیں — JSON میں مکمل مینو documents، فی ریستوران مختلف ساخت، لچکدار اسکیما۔ تیسرا: ہم Barato کی خریداری بند کرنے والے ہیں، اور ان کی ڈیٹا ٹیم گاہک کے رویے کے ڈیٹا کے لیے ایک Cassandra cluster چلاتی ہے۔ وہ اسے اپنی pipelines دوبارہ لکھے بغیر AWS پر لانا چاہتے ہیں۔"

تین پروجیکٹ۔ تین بہت مختلف ڈیٹا تقاضے۔ ان میں سے کوئی بھی واضح DynamoDB فٹ نہیں تھا۔

"ان سب کو مختلف ڈیٹابیسز کی ضرورت ہے،" Priya نے کہا۔

"ہمارے پاس DynamoDB ہے،" Leo نے کہا۔

"ہمارے پاس صحیح آلہ چننے کا حق ہے،" Priya نے کہا۔

**Amazon DocumentDB: جب آپ کا ورک لوڈ MongoDB بولتا ہے**

دوسرا پروجیکٹ — بھرپور JSON مینو documents جن کے لچکدار، فی ریستوران اسکیما ہوں — ایک document ڈیٹابیس کو بیان کرتا تھا۔ Nimbus پہلے سے ہی مینو کے لیے DynamoDB کی لچکدار اسکیما استعمال کر رہا تھا، لیکن جیسے جیسے ٹیم نے زیادہ نفیس مینو خصوصیات بنائیں (نیسٹڈ modifiers، وقت پر مبنی قیمت، پیچیدہ combo ساختیں)، DynamoDB کا query ماڈل اپنی حدیں دکھا رہا تھا۔ ٹیم زیادہ بھرپور document queries چاہتی تھی: تمام ایسے مینو آئٹمز تلاش کریں جہاں ایک نیسٹڈ modifier میں ایک مخصوص آپشن ہو، JSON ساخت کے اندر من مانی فیلڈز کے لحاظ سے فلٹر کریں۔

"یہ ایک document ڈیٹابیس پیٹرن ہے،" Priya نے کہا۔ "MongoDB۔"

"ہم MongoDB کو EC2 پر چلا سکتے ہیں،" Leo نے پیش کیا۔

"یا ہم DocumentDB استعمال کر سکتے ہیں،" Priya نے کہا۔

**Amazon DocumentDB** ایک MongoDB-مطابقت پذیر منیجڈ document ڈیٹابیس ہے۔ یہ ڈیٹا کو لچکدار اسکیما کے ساتھ JSON جیسے documents کے طور پر محفوظ کرتا ہے — ایک ہی collection میں مختلف documents کے مختلف فیلڈز ہو سکتے ہیں۔ DocumentDB MongoDB کی query زبان، APIs، اور drivers سپورٹ کرتا ہے۔ اگر آپ کا ورک لوڈ فی الحال MongoDB پر چلتا ہے، تو DocumentDB وہی زبان بولتا ہے۔ منتقلی کا راستہ ایک connection string منتقل کرنا ہے، ایپلیکیشن دوبارہ لکھنا نہیں۔

DocumentDB مکمل طور پر منیجڈ ہے: کوئی patching نہیں، خودکار بیک اپ، Multi-AZ اعلیٰ دستیابی، read replicas، اور اسٹوریج جو آپ کے ڈیٹا کے بڑھنے کے ساتھ خودبخود بڑھتا ہے۔

"تو ہم مینو کو DocumentDB میں منتقل کرتے ہیں،" Leo نے کہا۔ "اور وہ queries جو ہمارے پاس پہلے سے MongoDB syntax میں ہیں بس کام کرتی ہیں؟"

"معمولی مطابقت کی جانچ کے ساتھ، ہاں،" Priya نے تصدیق کی۔ "DocumentDB MongoDB کے زیادہ تر query API کو سپورٹ کرتا ہے۔ مکمل کوریج فرض کرنے سے پہلے مطابقت میٹرکس چیک کریں، لیکن document queries اور aggregations کے لیے، یہ سیدھا ہے۔"

DocumentDB کے لیے امتحان کا اشارہ سادہ ہے: **"MongoDB-compatible"** یا **"document store۔"** اگر کوئی منظر نامہ MongoDB یا document-oriented ڈیٹا کا ذکر کرے، تو DocumentDB منیجڈ AWS جواب ہے۔

**Amazon Neptune: جب رشتے ہی ڈیٹا ہوں**

recommendation engine ایک مشکل تر مسئلہ تھا۔

سوال یہ نہیں تھا کہ "اس گاہک نے کیا آرڈر کیا؟" — وہ ایک سادہ DynamoDB lookup تھا۔ سوال یہ تھا: "کن گاہکوں کے ذوق کے پروفائلز اس گاہک سے ملتے جلتے ہیں، اور ان گاہکوں نے کن پکوانوں کو پسند کیا ہے جنہیں اس گاہک نے ابھی تک نہیں آزمایا؟"

یہ ایک graph مسئلہ ہے۔ ڈیٹا ماڈل قطاروں کا ٹیبل یا documents کا collection نہیں ہے۔ یہ رشتوں کا ایک نیٹ ورک ہے: گاہک پکوانوں سے جڑے ہوئے (آرڈر کیے گئے، ریٹ کیے گئے، دیکھے گئے)، پکوان ریستورانوں اور cuisine اقسام سے جڑے ہوئے، ریستوران محلوں اور شہروں سے جڑے ہوئے۔ تجویز ڈیٹا کے نکات میں نہیں ہے — یہ ان کے درمیان راستوں میں ہے۔

"ہمیں ایک graph ڈیٹابیس کی ضرورت ہے،" Priya نے کہا۔

**Amazon Neptune** ایک مکمل طور پر منیجڈ graph ڈیٹابیس ہے۔ یہ دو graph ماڈل سپورٹ کرتا ہے: **property graph** (Gremlin traversal زبان کے ساتھ query کی گئی) اور **RDF** (SPARQL کے ساتھ query کی گئی)۔ آپ اپنے موجودہ graph اسٹیک یا ٹیم کی ترجیح کی بنیاد پر چنتے ہیں؛ دونوں ایک ہی Neptune بنیادی ڈھانچے پر چلتے ہیں۔

Graph ڈیٹابیسز ان ورک لوڈز کے لیے خاص طور پر بنائی گئی ہیں جہاں ڈیٹا کے نکات کے درمیان رشتے خود ڈیٹا جتنے ہی اہم ہوں: سوشل نیٹ ورکس (کون کس سے جڑا ہے)، recommendation engines (ملتے جلتے صارفین نے کیا پسند کیا)، fraud detection (کن لین دین میں اکاؤنٹس میں مشکوک پیٹرن مشترک ہیں)، اور knowledge graphs (تصورات کیسے جڑے ہیں)۔

Nimbus کے recommendation engine کے لیے: گاہک اور پکوان Neptune میں nodes بن گئے۔ آرڈر events edges بن گئے۔ ایک Gremlin traversal ایک ہی query میں وہ تمام پکوان تلاش کر سکتی تھی جنہیں ملتے جلتے آرڈر کی تاریخ والے گاہکوں نے زیادہ ریٹ کیا تھا، رابطے کی مضبوطی کے لحاظ سے ترتیب دیے گئے — ان پیچیدہ JOIN زنجیروں کے بغیر جو ایک ریلیشنل ڈیٹابیس میں درکار ہوتیں یا ان متعدد round-trip queries کے بغیر جو DynamoDB میں درکار ہوتیں۔

Neptune کے لیے امتحان کا اشارہ: **"social network،" "recommendation engine،" "knowledge graph،" "fraud detection،"** یا **"graph traversal۔"** اگر کوئی منظر نامہ ایسے ڈیٹا کو بیان کرے جہاں رابطے خود ڈیٹا جتنے ہی اہم ہوں، تو Neptune جواب ہے۔

**Amazon Keyspaces: آپریشنز کے بغیر Cassandra**

Barato کی خریداری ایک Cassandra cluster کو تصویر میں لے آئی۔ Cassandra ایک wide-column NoSQL ڈیٹابیس ہے — بہت اعلیٰ رائٹ throughput اور افقی اسکیل ایبلیٹی کے لیے ڈیزائن کیا گیا، عام طور پر time-series ڈیٹا، صارف سرگرمی لاگز، اور IoT telemetry کے لیے استعمال ہوتا ہے۔ Barato ڈیٹا ٹیم نے اسے گاہک کے رویے کو ٹریک کرنے کے لیے استعمال کیا: کن آئٹمز کو دیکھا گیا، کن کو کارٹ میں شامل کیا گیا، کن کو ترک کیا گیا۔

Cassandra کو AWS پر منتقل کرنے کے دو آپشن تھے: اسے EC2 پر چلائیں (cluster کے انتظام، اپ گریڈز، اسکیلنگ کا آپریشنل اوور ہیڈ) یا منیجڈ آپشن استعمال کریں۔

"Amazon Keyspaces،" Priya نے کہا۔

**Amazon Keyspaces** ایک بے سرور، Cassandra-مطابقت پذیر منیجڈ ڈیٹابیس ہے۔ یہ Cassandra Query Language (CQL) سپورٹ کرتا ہے — وہی query زبان جو Barato کی pipelines پہلے سے استعمال کر رہی تھیں۔ MongoDB کے لیے DocumentDB کی طرح، Keyspaces منیجڈ راستہ ہے: ایپلیکیشن کوڈ کو جوں کا توں رکھیں، اسے self-managed cluster کے بجائے ایک Keyspaces endpoint کی طرف اشارہ کریں، اور AWS کو بنیادی ڈھانچہ سنبھالنے دیں۔

Keyspaces ٹریفک کے ساتھ خودبخود اسکیل ہوتا ہے، کسی صلاحیت کی منصوبہ بندی کی ضرورت نہیں، اور بے سرور ہے — آپ ان ریڈز اور رائٹس کے لیے ادائیگی کرتے ہیں جو آپ حقیقتاً انجام دیتے ہیں۔ Barato کے رویے کو ٹریک کرنے والے ڈیٹا کے لیے، یہ صحیح ماڈل تھا: انتہائی متغیر والیوم (رات کے کھانے کی بھیڑ بمقابلہ صبح 3 بجے)، wide-column اسکیما، اعلیٰ رائٹ throughput۔

امتحان کا اشارہ: **"Cassandra-compatible،" "wide-column،" "CQL،"** یا **"Cassandra workload۔"**

**صحیح ڈیٹابیس چننا: ایک حوالہ ٹیبل**

کہانی کے اس مقام تک، Nimbus کا ڈیٹابیس منظر نامہ ساتویں باب جیسا بالکل نہیں رہا تھا۔ ہر ورک لوڈ کے لیے صحیح آلہ:

| Trigger جملہ | ڈیٹابیس |
|---|---|
| "MongoDB-compatible" یا "document store" | DocumentDB |
| "Graph relationships،" "social network،" "recommendation engine" | Neptune |
| "Cassandra-compatible" یا "wide-column" | Keyspaces |
| "Key-value at any scale،" "single-digit millisecond latency" | DynamoDB |
| "Relational + serverless،" "auto-scaling SQL" | Aurora Serverless |
| "Structured data، complex queries، reporting" | RDS (PostgreSQL، MySQL) |

"کیا یہ بڑھتا رہے گا؟" Leo نے فہرست دیکھتے ہوئے پوچھا۔

"ہاں،" Maya نے کہا۔ "کیونکہ مختلف مسائل کی مختلف شکلیں ہوتی ہیں۔ اور غلط شکل استعمال کرنا آپ کو یا تو کارکردگی، ڈویلپر کا وقت، یا دونوں میں خرچ پڑتا ہے۔"

"صحیح سوال یہ نہیں ہے کہ 'ہمیں کون سا ڈیٹابیس استعمال کرنا چاہیے،'" Priya نے مزید کہا۔ "یہ ہے کہ 'ہمارے ڈیٹا کی شکل کیا ہے، اور ہم اس تک کیسے رسائی کریں گے؟' ڈیٹابیس جواب سے نکلتا ہے۔"

یہ سب سے اہم بات تھی جو اس نے دو سال میں ڈیٹابیسز کے بارے میں کہی تھی۔

## خوبیاں اور حدود

**DynamoDB کیوں طاقتور ہے**:

- کسی بھی پیمانے پر single-digit millisecond latency
- مکمل طور پر منیجڈ — کوئی patching نہیں، کوئی ریپلیکیشن سیٹ اپ نہیں، کوئی maintenance windows نہیں
- خودکار multi-AZ ریپلیکیشن (بلٹ ان پائیداری)
- On-demand اسکیلنگ کا مطلب صفر صلاحیت کی منصوبہ بندی ہے
- Lambda، API Gateway، Streams کے ساتھ مقامی انضمام
- Point-in-time recovery (RDS خودکار بیک اپ کی طرح)
- DynamoDB Streams — ہر تبدیلی کو ایک event کے طور پر capture کریں (real-time processing کے لیے مفید)

**جہاں DynamoDB پیچیدہ ہو جاتا ہے**:

- Access pattern ڈیزائن ناقابل سمجھوتہ ہے — غلطیاں واپس کرنا مہنگا ہے
- پیچیدہ queries کے لیے secondary indexes کی ضرورت ہے (لاگت اور پیچیدگی میں اضافہ)
- Scans مہنگے ہیں — پروڈکشن میں ان سے بچیں
- "آئٹم سائز کی حد" 400KB ہے — بڑے آئٹمز کو مختلف اسٹوریج کی ضرورت ہے
- اگر آپ ریڈ/رائٹ یونٹ کے اخراجات نہیں سمجھتے تو pricing آپ کو حیران کر سکتی ہے
- Hot partitions خاموش قاتل ہیں — throttling شروع ہونے تک کوئی خرابیاں نہیں

## خلاصہ

اسکیما کے نئے ڈیزائن میں دو دن اور وائٹ بورڈ کی کافی جگہ لگی تھی۔ NoSQL ڈیٹابیس چننا صرف ایک تکنیکی فیصلہ نہیں ہے — یہ بدل دیتا ہے کہ آپ ڈیٹا کے بارے میں کیسے سوچتے ہیں۔ لیکن نتیجہ ایک ایسا مینو ٹیبل تھا جو سست ہوئے بغیر کسی بھی سائز تک بڑھ سکتا تھا۔ اتنا ہی اہم: ٹیم نے سیکھا کہ DynamoDB کی حدیں کہاں ہیں، اور جب مسئلہ شکل بدلے تو کن خصوصی ڈیٹابیسز کی طرف رجوع کرنا ہے۔

- DynamoDB AWS کی منیجڈ NoSQL ڈیٹابیس سروس ہے۔ آئٹمز لچکدار documents ہیں — کوئی مقررہ اسکیما نہیں۔ ہر آئٹم کا ایک **primary key** ہونا چاہیے: اکیلا partition key، یا partition key + sort key۔ یکساں تقسیم کے لیے partition key چنیں — hot partitions throttling کا سبب بنتے ہیں۔
- **On-demand** صلاحیت خودبخود اسکیل ہوتی ہے؛ **provisioned** صلاحیت قابل پیش گوئی ٹریفک کے لیے سستی ہے۔ **Eventually consistent** ریڈز سستی ہیں؛ **strongly consistent** ریڈز ہمیشہ موجودہ لیکن GSIs پر دستیاب نہیں۔
- **DynamoDB Streams** real time میں item-level تبدیلیاں capture کرتے ہیں — انہیں cache invalidation، search index اپڈیٹس، اور analytics pipelines چلانے کے لیے استعمال کریں۔
- DynamoDB رپورٹنگ، پیچیدہ joins، اور ad-hoc queries کے لیے غلط انتخاب ہے — ان کے لیے RDS استعمال کریں۔
- **DocumentDB** (MongoDB-مطابقت پذیر)، **Neptune** (graph ڈیٹابیس)، اور **Keyspaces** (Cassandra-مطابقت پذیر) ان ورک لوڈز کے لیے AWS منیجڈ متبادل ہیں جو DynamoDB کے key-value ماڈل میں فٹ نہیں ہوتے۔

## امتحانی نکات

*SAA-C03 ڈومین: اعلیٰ کارکردگی آرکیٹیکچرز ڈیزائن کریں (ڈومین ۳، ٹاسک ۳.۳)*

- Partition key قواعد جانیں: **اعلیٰ cardinality، یکساں تقسیم**۔ Hot partitions ایک عام امتحانی جال ہیں۔
- **On-demand بمقابلہ provisioned**: غیر قابل پیش گوئی ٹریفک کے لیے on-demand؛ قابل پیش گوئی ورک لوڈز کے لیے provisioned (Auto Scaling کے ساتھ)۔
- **DynamoDB Streams**: real time میں item-level تبدیلیاں capture کرتا ہے۔ عام امتحانی منظر نامہ: "جب ریکارڈ تبدیل ہو تو Lambda function trigger کریں۔"
- **Global Tables**: عالمی سطح پر تقسیم شدہ ایپلیکیشنز اور ڈیزاسٹر ریکوری کے منظر ناموں کے لیے multi-Region، multi-active ریپلیکیشن۔ امتحان میں، یہ ایک مضبوط اشارہ ہے جب ورک لوڈ کو ایک سے زیادہ Region میں مقامی ریڈز اور رائٹس کی ضرورت ہو۔
- **DynamoDB TTL (Time to Live)**: آئٹمز پر ایک expiration timestamp attribute سیٹ کریں اور DynamoDB انہیں expiry کے بعد خودبخود delete کر دیتا ہے — **بلا قیمت**، کوئی رائٹ صلاحیت استعمال کیے بغیر۔ امتحانی trigger: "session ڈیٹا/عارضی آئٹمز کو کم سے کم قیمت پر N گھنٹوں کے بعد خودبخود ہٹایا جانا چاہیے" → TTL، کبھی ایک شیڈولڈ Lambda scan نہیں۔ expire شدہ آئٹمز archival کے لیے DynamoDB Streams میں بھی بہہ سکتے ہیں۔
- **DAX (DynamoDB Accelerator)**: DynamoDB کے لیے in-memory caching layer۔ ریڈ latency کو milliseconds سے microseconds تک کم کرتا ہے۔ امتحان اسے استعمال کرتا ہے جب RDS read replicas مدد نہیں کریں گے (کیونکہ یہ DynamoDB-specific cache ہے)۔
- **Composite primary key**: partition key + sort key ایک partition کے اندر لچکدار queries کی اجازت دیتا ہے۔ مثال: دو تاریخوں کے درمیان کسی گاہک کے تمام آرڈر بازیافت کریں — `customerId` partition key ہے، `orderDate` sort key ہے۔
- **GSI بمقابلہ LSI**: GSI کو ٹیبل بنانے کے بعد شامل کیا جا سکتا ہے؛ LSI کو نہیں۔ LSI strongly consistent ریڈز سپورٹ کرتا ہے؛ GSI نہیں۔ LSI ٹیبل کی صلاحیت کا اشتراک کرتا ہے؛ GSI کی اپنی ہوتی ہے۔
- جانیں DynamoDB کب استعمال نہ کریں: پیچیدہ joins، ad-hoc reporting، multi-entity transactions → RDS عام طور پر جواب ہے۔
- **مخصوص-مقصد ڈیٹابیس کا انتخاب** — امتحان اکثر ایک منظر نامہ پیش کرتا ہے اور پوچھتا ہے کہ کون سا ڈیٹابیس فٹ ہے۔ اسے اپنے فوری حوالے کے طور پر استعمال کریں: "MongoDB-compatible" → DocumentDB۔ "Graph/social network/recommendation engine/knowledge graph" → Neptune۔ "Cassandra-compatible/wide-column" → Keyspaces۔ "Key-value at any scale/millisecond latency" → DynamoDB۔ "Relational/complex queries/reporting" → RDS یا Aurora۔

**مشق ۲ — SAA-C03 منظر نامہ**

*منظر نامہ*: ایک عالمی gaming کمپنی DynamoDB میں کھلاڑیوں کے پروفائلز محفوظ کرتی ہے۔ ہر پروفائل میں username، level، achievements، اور inventory جیسے فیلڈز شامل ہیں۔ کچھ کھلاڑیوں کے پاس 10 inventory آئٹمز ہیں؛ دوسروں کے پاس چند سو — پروفائلز شکل میں مختلف ہوتے ہیں لیکن ہر ایک آرام سے DynamoDB کی 400KB آئٹم سائز کی حد سے نیچے رہتا ہے۔ کمپنی کو فعال gameplay کے دوران پروفائل تلاش کے لیے single-digit millisecond ریڈ latency کی ضرورت ہے۔

کون سا ڈیزائن طریقہ اس ضرورت کو بہترین طریقے سے سپورٹ کرتا ہے؟

A) `playerId` کو partition key کے طور پر استعمال کر کے DynamoDB استعمال کریں اور پورے پروفائل کو ایک واحد آئٹم کے طور پر محفوظ کریں  
B) ہر region میں read replicas کے ساتھ RDS Aurora میں منتقل کریں  
C) ایک جیسی مہارت والے کھلاڑیوں کو گروپ کرنے کے لیے `level` کو partition key کے طور پر DynamoDB استعمال کریں  
D) sub-millisecond latency حاصل کرنے کے لیے RDS کے سامنے ElastiCache استعمال کریں

**اشارہ ۱**: رسائی کا نمونہ "ID کے ذریعے ایک مخصوص کھلاڑی تلاش کریں" ہے۔ کون سی key اسے مؤثر بناتی ہے؟

**اشارہ ۲**: ایک آپشن ایک خوفناک hot partition بناتا ہے۔ کون سی attribute کی بہت کم cardinality ہے؟

**اشارہ ۳**: DynamoDB پہلے سے ہی مقامی طور پر single-digit millisecond latency فراہم کرتا ہے۔

**جواب**: A

**وضاحت**: `playerId` کو partition key کے طور پر استعمال کرنے سے partitions میں ڈیٹا یکساں طور پر تقسیم ہوتا ہے اور player ID کے ذریعے فوری تلاش ممکن ہوتی ہے — بالکل وہی رسائی کا نمونہ جو بیان کیا گیا ہے۔ DynamoDB کا لچکدار document ماڈل schema تبدیلیوں کے بغیر مختلف inventory سائز سنبھالتا ہے۔

**B کیوں نہیں؟** Read replicas کے ساتھ RDS Aurora پیچیدگی بڑھاتا ہے اور اس قسم کی key-based profile lookup کے لیے gaming پیمانے پر اب بھی قدرتی پہلا انتخاب نہیں ہے۔

**C کیوں نہیں؟** `level` کو partition key کے طور پر استعمال کرنے سے شدید hot partitions بنتے ہیں — زیادہ تر ٹریفک level 1 (نئے کھلاڑی) یا زیادہ سے زیادہ level (فعال تجربہ کار) پر جاتی ہے، دیگر partitions کو بیکار چھوڑ کر۔

**D کیوں نہیں؟** سوال DynamoDB کے بارے میں ہے، RDS نہیں۔ RDS کے سامنے ElastiCache شامل کرنے سے دو نئی سروسز متعارف ہوتی ہیں جب DynamoDB اکیلے مسئلہ حل کرتا ہے۔

*SAA-C03 ڈومین: اعلیٰ کارکردگی آرکیٹیکچرز ڈیزائن کریں — ٹاسک ۳.۳*

**مشق ۳ — آرکیٹیکچر چیلنج** *(اختیاری)*

Nimbus ایک "پسندیدہ" خصوصیت شامل کر رہا ہے: گاہک اپنے پسندیدہ مینو آئٹمز محفوظ کر سکتے ہیں اور انہیں ایک ٹیپ سے دوبارہ آرڈر کر سکتے ہیں۔

اس خصوصیت کے لیے DynamoDB ٹیبل ڈیزائن کریں۔ Partition key کیا ہوگی؟ کیا آپ sort key استعمال کریں گے؟ آئٹم کا ڈھانچہ کیسا نظر آئے گا؟

پھر غور کریں: اگر آپ کو "تمام گاہکوں میں سب سے زیادہ 100 پسندیدہ آئٹمز" دکھانے کی ضرورت ہو تو کیا ہوگا؟ کیا DynamoDB اس کا مؤثر طریقے سے جواب دے سکتا ہے؟ اگر نہیں، تو آپ آرکیٹیکچر میں کیا شامل کریں گے؟

*(کوئی ایک درست جواب نہیں ہے۔ مقصد رسائی کے نمونوں کے لیے ڈیزائن کرنے کی مشق کرنا ہے۔)*
