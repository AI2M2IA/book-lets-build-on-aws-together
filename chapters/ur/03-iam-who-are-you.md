# باب 3: آپ آخر ہیں کون؟

صبح کے نو بجے کے کچھ ہی بعد کا وقت تھا۔ Leo سات بجے سے اپنی میز پر تھا، کافی کی بورڈ کے ساتھ ٹھنڈی ہو چکی تھی۔ دفتر خاموش تھا — Maya ابھی نہیں آئی تھی، Tom ایک کال پر تھا۔ باہر، کوئی لان کاٹ رہا تھا۔

Leo نے کمانڈ ایک بار اور ٹائپ کی۔

ٹرمینل نے دو الفاظ واپس کیے: Access Denied۔

Singapore کا بحران ان کے پیچھے تھا۔ region ٹھیک ہو چکا تھا، سرور us-west-2 میں چل رہا تھا، اور ٹیم مختصر طور پر باصلاحیت محسوس کر رہی تھی۔ وہ احساس نئے مسئلے کے سامنے آنے سے پہلے تقریباً اڑتالیس گھنٹے چلا: Leo production میں deploy نہیں کر سکتا تھا۔ کسی نے اس کی permissions سیٹ اپ نہیں کی تھیں۔ کسی نے کسی کی permissions سیٹ اپ نہیں کی تھیں۔ AWS اکاؤنٹ root سطح پر کھلا پڑا تھا اور باقی ہر جگہ بند تھا، اور کسی نے غور نہیں کیا تھا کیونکہ کسی نے کوشش نہیں کی تھی۔

"میں نے اسے پہلے ہی deploy کر دیا تھا — اوہ،" Leo بڑبڑایا، اپنے ٹرمینل میں پیچھے اسکرول کرتے ہوئے۔ وہ ایک ہفتے سے اس میں deploy کر رہا تھا جسے وہ production سمجھتا تھا۔ وہ staging تھا۔ حقیقی production ماحول کو کبھی چھوا ہی نہیں گیا تھا۔

Maya نے اس کے کندھے کے اوپر سے error message دیکھا۔ "تمہیں یہ permission کس نے دی؟"

Leo مڑا۔ "کون سی permission؟"

"Production میں deploy کرنے کی permission۔ یہ کس نے سیٹ اپ کی؟"

Leo نے AWS console کھولا اور menus میں click کرنا شروع کیا۔ کسی نے نہیں کی تھی۔ کوئی policy نہیں تھی، کوئی role نہیں، کوئی واضح grant نہیں۔ کوئی واضح انکار بھی نہیں تھا — صرف ایک غیر موجودگی تھی۔ Nimbus میں کسی نے کبھی بیٹھ کر اس بارے میں نہیں سوچا تھا کہ کون کیا کر سکتا ہے۔

یہی مسئلہ تھا۔

**Passwords کا مسئلہ**

Passwords کمپیوٹر نظاموں کے لیے ایک برا ماڈل ہیں۔

اس لیے نہیں کہ وہ ہمیشہ کمزور ہوتے ہیں۔ اس لیے کہ وہ binary ہوتے ہیں: یا تو آپ کے پاس password ہے یا نہیں۔ اگر آپ کے پاس ہے، تو آپ وہ سب کچھ کر سکتے ہیں جو اکاؤنٹ کو کرنے کی اجازت ہے۔

یہ کسی ایک صارف کے ذاتی لیپ ٹاپ کے لیے ٹھیک ہے۔ کمپنی کے cloud انفراسٹرکچر کے لیے یہ تباہ کن ہے۔

غور کریں کہ Nimbus کو کیا منظم کرنا ہے: web server، ڈیٹابیس، فائل اسٹوریج، نیٹ ورکنگ، billing alerts، یوزر اکاؤنٹس۔ اگر ہر چیز ایک password سے محفوظ ہو — یا credentials کے ایک ہی سیٹ سے — تو جسے بھی وہ password ملے، اسے سب کچھ مل جاتا ہے۔

اور AWS پر "سب کچھ" کا مطلب ہے ڈیٹابیسز حذف کرنے کی صلاحیت۔ ایسے سرور spin up کرنا جو $50,000 کا بل بنا دیں۔ ہر گاہک کا record exfiltrate کرنا۔ Backup ڈیٹا تباہ کرنا۔

passwords کی binary نوعیت سے ہٹ کر ایک اور مسئلہ ہے: passwords static ہوتے ہیں۔ وہ خودکار طور پر ختم نہیں ہوتے۔ وہ اکثر سروسز میں دوبارہ استعمال ہوتے ہیں۔ وہ لکھ لیے جاتے ہیں۔ وہ "passwords شیئر نہ کریں" کے لیبل والی اسپریڈ شیٹس میں محفوظ ہو جاتے ہیں۔ وہ بہرحال شیئر ہو جاتے ہیں، کیونکہ جب سیکیورٹی میکانزم رگڑ ہو تو سہولت سیکیورٹی کو شکست دے دیتی ہے۔

"shared credentials" کا مسئلہ کوئی کردار کی خامی نہیں ہے۔ یہ ایک نظاموں کا مسئلہ ہے۔ جب کسی کو کسی نظام تک عارضی رسائی دینے کا واحد طریقہ انہیں مستقل password دینا ہو، تو لوگ passwords شیئر کرتے ہیں۔ حل یہ ہے کہ ایک ایسا نظام بنایا جائے جہاں عارضی، محدود رسائی ڈیفالٹ ہو — نہ کہ کوئی ایسا حل جس کے لیے بہادرانہ کوشش درکار ہو۔

یہی IAM کرتا ہے۔ صرف "بہتر passwords" نہیں، بلکہ ایک بنیادی طور پر مختلف ماڈل جہاں رسائی کی تعریف شناخت اور policy سے ہوتی ہے، نہ کہ اس سے کہ کون حروف کی ایک لڑی جانتا ہے۔

Priya نے اسے پُرسکون، تجریدی الفاظ میں بیان نہیں کیا۔ اس نے اسے ایک کہانی کے طور پر بیان کیا۔

**وہ خلاف ورزی جس نے چار گھنٹوں میں $80,000 کا نقصان کیا**

ایک اسٹارٹ اپ کے ایک ڈویلپر نے ایک GitHub Actions ڈیپلائمنٹ اسکرپٹ اپنی عوامی repository میں push کی۔ اسکرپٹ میں AWS credentials environment variables کے طور پر hardcoded تھے — ایک ایسی غلطی جو اتنی عام ہے کہ cloud سیکیورٹی پوسٹ مارٹمز میں اس کا اپنا زمرہ ہے۔ credentials کے پاس کمپنی کے AWS اکاؤنٹ تک مکمل admin رسائی تھی، کیونکہ کسی نے انہیں چھ ماہ پہلے IAM policies سے نمٹنے سے بچنے کے لیے اس طرح کنفیگر کیا تھا۔

credentials فائل میں تقریباً چھ منٹ تھے اس سے پہلے کہ ایک خودکار اسکینر — جو کسی حملہ آور نے چلایا تھا، کسی سیکیورٹی محقق نے نہیں — انہیں ڈھونڈ لیا۔

اسکینر نے credentials کو index کیا، اکاؤنٹ کی permissions کا اندازہ لگایا، اور متعدد regions میں GPU instances spin up کرنا شروع کر دیا۔ GPU instances مہنگے ہوتے ہیں۔ وہ cryptocurrency mining کے لیے بھی مفید ہیں۔ پہلے گھنٹے کے اندر، سینتالیس `p3.8xlarge` instances `us-east-1`، `eu-west-1`، اور `ap-southeast-1` میں چل رہے تھے۔

ایک `p3.8xlarge` تقریباً $12 فی گھنٹہ پڑتا ہے۔ ان میں سے سینتالیس $564 فی گھنٹہ پڑتے ہیں۔

جب تک اسٹارٹ اپ کا billing الرٹ چلا — $1,000 فی دن پر کنفیگر کیا گیا، جسے سخت کرنے کا کسی نے نہیں سوچا تھا — چار گھنٹے گزر چکے تھے۔ بل $2,200 کے قریب پہنچ رہا تھا اور بڑھ رہا تھا۔

جب تک کسی نے سمجھا کہ کیا ہو رہا ہے اور credentials منسوخ کیے، بل ان چند گھنٹوں کے لیے $3,400 تک پہنچ چکا تھا۔ لیکن اصل لاگت بعد میں آئی: آڈٹ نے ظاہر کیا کہ حملہ آور پہلے ہی ہفتوں سے mining کر رہا تھا، خاموشی سے، رات کو، leaked credentials کے ایک دوسرے سیٹ کا استعمال کرتے ہوئے جس پر کسی نے غور نہیں کیا تھا۔ آڈٹ مکمل ہونے تک کل نقصان: $80,000 سے زیادہ۔

"اور وہ بند ہو گئے؟" Tom نے پوچھا۔

"تین ماہ بعد،" Priya نے کہا۔ "سرمایہ کار نکل گئے۔ خلاف ورزی ظاہر ہو گئی۔ پریس کوریج نے fundraising ناممکن بنا دی۔"

کمرہ خاموش تھا۔

"تو متبادل کیا ہے؟" Tom نے پوچھا۔

**تصور: Identity and Access Management**

متبادل ایک ایسا نظام ہے جہاں آپ سب کو ایک ہی چابی نہیں دیتے۔

ایک دفتری عمارت کا تصور کریں جہاں ہر منزل کے مختلف علاقے ہیں، اور ہر ملازم کے پاس ایک keycard ہے جو صرف وہ دروازے کھولتا ہے جنہیں اسے اپنے کام کے لیے چاہیے۔ انٹرن کا keycard تیسری منزل پر کام کرتا ہے۔ اکاؤنٹنٹ کا keycard finance دفتر کھولتا ہے لیکن server room نہیں۔ کوئی ایسے دروازے سے نہیں گزرتا جس سے گزرنے کی اس کی کوئی وجہ نہ ہو۔

یہی وہ ماڈل ہے جو AWS استعمال کرتا ہے۔

AWS اس نظام کو **IAM** کہتا ہے: Identity and Access Management۔

IAM آپ کے پورے cloud اکاؤنٹ کے لیے keycard نظام ہے۔ آپ define کرتے ہیں کہ کون موجود ہے (شناختیں)، انہیں کیا کرنے کی اجازت ہے (permissions)، اور ان permissions کو policies کے ذریعے لاگو کرتے ہیں۔ عمارت کی درجنوں منزلیں ہیں۔ IAM یقینی بناتا ہے کہ ہر شخص صرف ان منزلوں تک پہنچ سکے جن کی اسے ضرورت ہے۔

keycard کی تشبیہ مزید آگے بڑھتی ہے۔ ایک اچھی طرح چلائی جانے والی عمارت میں، آپ کسی بھی لمحے جانتے ہیں کہ کس کو کس تک رسائی ہے۔ آپ ایک رپورٹ پرنٹ کر سکتے ہیں: یہ ہر keycard کے رسائی حقوق ہیں۔ یہ ہے کہ پچھلے 30 دنوں میں server room میں کون رہا ہے۔ یہ وہ cards ہیں جو 90 دنوں میں استعمال نہیں ہوئے (ایک برطرف ملازم کے ایسے card کا ممکنہ اشارہ جسے غیر فعال نہیں کیا گیا)۔

IAM وہی visibility فراہم کرتا ہے۔ IAM کے ذریعے کیا گیا ہر عمل — ہر API call، ہر console login، ہر permission grant — **AWS CloudTrail** میں لاگ ہوتا ہے۔ اگر آپ کو جاننے کی ضرورت ہو کہ منگل کو رات 2 بجے کس نے ڈیٹابیس حذف کیا، تو CloudTrail کے پاس جواب ہے۔ اگر آپ کو کسی آڈیٹر کو ظاہر کرنا ہو کہ صرف مجاز صارفین کو production نظاموں تک رسائی تھی، تو CloudTrail ثبوت فراہم کرتا ہے۔

AWS CloudTrail خودکار طور پر management events کی 90 دن کی تاریخ رکھتا ہے، جو console سے پڑھنے کے قابل ہے۔ لیکن 90 دن کا یہ مسئلہ ہے کہ جب آپ کی سیکیورٹی ٹیم کو پچھلی سہ ماہی کا کچھ آڈٹ کرنے کی ضرورت ہو تو یہ بالکل کافی نہیں ہوتا۔ مستقل، طویل مدتی logging کے لیے — اور alerts کے لیے — آپ کو ایک **Trail** بنانے کی ضرورت ہے، جو تمام events کو ایک S3 bucket میں لکھتا ہے اور CloudWatch Logs میں stream کر سکتا ہے۔ Trail خودکار نہیں ہے؛ یہ کچھ ایسا ہے جسے آپ ایک بار کنفیگر کرتے ہیں اور پھر بھول جاتے ہیں۔ جب تک آپ کو اس کی ضرورت نہ پڑے۔

IAM کے رسائی کنٹرولز اور CloudTrail کی audit logging کا امتزاج وہ ہے جو بڑی تنظیموں کو AWS اکاؤنٹس کو اعتماد کے ساتھ پیمانے پر چلانے دیتا ہے: رسائی کی تعریف اور نفاذ IAM کرتا ہے؛ اس رسائی کے ہر استعمال کو CloudTrail ریکارڈ کرتا ہے۔

**ہسپتال کی تشبیہ**

اس کے بارے میں سوچنے کا یہ ایک دوسرا طریقہ ہے — ایک جو رسائی کے درجہ بندی کو زیادہ بدیہی بناتا ہے۔

ایک ہسپتال کا تصور کریں۔ صرف جسمانی عمارت نہیں، بلکہ لوگوں، کرداروں، اور ڈیٹا کا مکمل تنظیمی ڈھانچہ۔

**استقبالیہ** مریضوں کی اپائنٹمنٹ شیڈولز اور انشورنس کی معلومات دیکھ سکتا ہے۔ وہ مریضوں کو check in اور check out کر سکتے ہیں۔ وہ طبی ریکارڈ تک رسائی نہیں کر سکتے، نسخے میں ترمیم نہیں کر سکتے، جراحی کی تاریخ نہیں دیکھ سکتے۔

**نرس** اپنے وارڈ کے مریضوں کے طبی ریکارڈ تک رسائی کر سکتی ہے۔ وہ ڈاکٹر کے احکامات کے مطابق دوائیاں دے سکتے ہیں۔ وہ دوائیاں تجویز نہیں کر سکتے۔ وہ سرجریوں کی اجازت نہیں دے سکتے۔

**ڈاکٹر** طبی ریکارڈ دیکھ اور ترمیم کر سکتا ہے، نسخے لکھ سکتا ہے، اور ٹیسٹ کا حکم دے سکتا ہے۔ وہ payroll نظام تک رسائی نہیں کر سکتے۔ وہ کسی مخصوص override کے بغیر دوسرے ڈاکٹروں کے نسخوں میں ترمیم نہیں کر سکتے۔

**سرجن** آپریشن روم کے نظاموں تک رسائی کر سکتا ہے۔ ان کے پاس جراحی ریکارڈ کے لیے مخصوص permissions ہیں جن کی زیادہ تر ڈاکٹروں کو ضرورت نہیں۔

**صفائی کا عملہ** فلور پلانز اور کمرے کے شیڈولز تک رسائی کر سکتا ہے۔ وہ کسی مریض کے ڈیٹا تک رسائی نہیں کر سکتے۔

ہسپتال میں ہر شخص کو وہ رسائی ہے جس کی اسے اپنے کام کے لیے ضرورت ہے — اور صرف وہی۔ استقبالیہ کو جراحی رسائی نہیں ہے۔ صفائی کا عملہ مریض کے ریکارڈ نہیں دیکھتا۔ اور اہم بات: اگر صفائی کے عملے کے کسی رکن کا keycard چوری ہو جائے، تو حملہ آور کو صفائی کے شیڈولز ملتے ہیں۔ انہیں مریض کے ریکارڈ نہیں ملتے۔ خلاف ورزی کا blast radius اس تک محدود ہے جس تک وہ keycard رسائی کر سکتا تھا۔

یہی طرح IAM کام کرتا ہے۔ ہر شناخت — ہر صارف، ہر سروس، ہر خودکار عمل — کو بالکل وہ permissions ملتی ہیں جن کی اسے ضرورت ہے۔ اس سے زیادہ کچھ نہیں۔

Tom پیچھے ٹیک لگا کر بیٹھ گیا۔ "تو Leo نرس ہے، اور میں اکاؤنٹنٹ ہوں۔"

"کچھ ایسا ہی،" Priya نے کہا۔ "اور آپ دونوں میں سے کوئی سرجن نہیں ہے۔"

"سرجن کون ہے؟"

"کوئی نہیں، روزمرہ میں،" Priya نے کہا۔ "root اکاؤنٹ سرجن ہے۔ یہ صرف مخصوص، دستاویزی طریقہ کاروں کے لیے باہر آتا ہے۔"

**IAM کے بنیادی اجزا**

IAM کے چار بنیادی تصورات ہیں۔ وہ ایک دوسرے پر بنتے ہیں۔

**Users** انفرادی شناختیں ہیں۔ Maya کا ایک IAM user ہے۔ Tom کا ایک IAM user ہے۔ ہر user کے اپنے credentials ہوتے ہیں — اور اسے صرف وہ permissions ہونی چاہئیں جن کی اسے خاص طور پر ضرورت ہے۔

ایک IAM user کے پاس دو قسم کے credentials ہوتے ہیں: console رسائی کے لیے ایک **password** (AWS web interface میں لاگ ان کرنا) اور CLI یا SDKs کے ذریعے programmatic رسائی کے لیے **access keys** (ایک key ID اور secret key)۔ آپ کو ہمیشہ دونوں کی ضرورت نہیں ہوتی۔ ایک ڈویلپر جو صرف CLI استعمال کرتا ہے اسے console password کی ضرورت نہیں۔ ایک غیر تکنیکی صارف جسے صرف console کی ضرورت ہے اسے access keys کی ضرورت نہیں۔ صرف وہی دیں جو ضروری ہو۔

**Groups** users کے مجموعے ہیں۔ Maya، Tom، Priya، اور Leo کے لیے permissions انفرادی طور پر سیٹ کرنے کے بجائے، آپ developer permissions کے ساتھ ایک "Developers" group بناتے ہیں اور انہیں اس میں شامل کرتے ہیں۔ جب پانچواں شخص شامل ہوتا ہے، آپ اسے group میں شامل کرتے ہیں اور وہ فوراً صحیح permissions وراثت میں لے لیتا ہے۔

groups کا عملی فائدہ قابلِ دیکھ بھال ہونا ہے۔ اگر "Developers" group کو ایک نئی permission چاہیے — مثلاً، ایک نئے S3 bucket تک رسائی — تو آپ اسے group میں ایک بار شامل کرتے ہیں اور تمام ڈویلپرز کے پاس فوراً وہ ہوتی ہے۔ groups کے بغیر، آپ ہر user کو انفرادی طور پر اپڈیٹ کرتے، جو عدم مطابقت کے مواقع پیدا کرتا ہے اور لوگ چھوٹ جاتے ہیں۔

**Roles** عارضی شناختیں ہیں جنہیں کوئی چیز *assume* کر سکتی ہے — ایک شخص، ایک سروس، یا کوئی دوسرا AWS اکاؤنٹ۔ ہم باب 14 میں roles پر گہرائی سے جائیں گے۔ ابھی کے لیے: اگر User ایک مستقل ملازم ہے، تو Role ایک visitor badge ہے۔ یہ ایک مخصوص وقت یا مقصد کے لیے مخصوص رسائی دیتا ہے۔

اس باب کے لیے Roles کا سب سے اہم استعمال: EC2 instances کے لیے IAM Roles۔ جب آپ کسی EC2 instance سے ایک Role منسلک کرتے ہیں، تو اس instance پر چلنے والی ایپلیکیشن Role کی permissions کا استعمال کرتے ہوئے AWS API calls کر سکتی ہے — کہیں بھی کوئی static credentials محفوظ کیے بغیر۔ credentials عارضی ہیں، AWS کی طرف سے خودکار طور پر گھمائے جاتے ہیں، اور Role کی policies تک محدود ہیں۔ یہ "config files میں credentials" کے مسئلے کو مکمل طور پر ختم کر دیتا ہے۔

**Policies** اصل permission کے قواعد ہیں۔ ایک policy ایک دستاویز ہے (اندرونی طور پر JSON میں لکھی جاتی ہے، لیکن آپ کو format یاد کرنے کی ضرورت نہیں) جو کہتی ہے: "اس policy کے حامل کو resource Y پر action X انجام دینے کی ALLOW ہے۔" یا "action Z DENIED ہے۔"

AWS سینکڑوں **managed policies** فراہم کرتا ہے — عام استعمال کے مواقع کے لیے پہلے سے لکھی گئی policies۔ `AmazonS3ReadOnlyAccess` تمام S3 buckets تک read رسائی دیتا ہے۔ `AmazonEC2FullAccess` مکمل EC2 کنٹرول دیتا ہے۔ production استعمال کے لیے، آپ اکثر **customer-managed policies** چاہتے ہیں — وہ policies جو آپ خود لکھتے ہیں، ان resources اور actions تک عین مطابق محدود جن کی آپ کی ایپلیکیشن کو دراصل ضرورت ہے۔

IAM evaluation ماڈل یہ ہے: ڈیفالٹ طور پر، ہر چیز denied ہے۔ Permissions کو واضح طور پر grant کرنا پڑتا ہے۔ اگر کوئی policy یہ نہیں کہتی کہ آپ کچھ کر سکتے ہیں، تو آپ نہیں کر سکتے۔

**Principle of Least Privilege**

لوگوں اور نظاموں کو صرف وہ رسائی دیں جس کی انہیں اپنا کام کرنے کے لیے ضرورت ہے۔ اس سے زیادہ کچھ نہیں۔

Priya نے اسے "principle of least privilege" کہا۔ یہ واضح لگتا ہے۔ عمل میں، زیادہ تر ٹیمیں اسے مسلسل خلاف ورزی کرتی ہیں — بد نیتی سے نہیں، بلکہ سہولت کی وجہ سے۔

"کیا ہم Leo کو admin access دے دیں تاکہ وہ چیزیں تیزی سے deploy کر سکے؟"

نہیں۔

"کیا ہم root اکاؤنٹ ہی ہر چیز کے لیے استعمال کر لیں؟"

بالکل نہیں۔

root اکاؤنٹ آپ کے پورے AWS اکاؤنٹ کی master key ہے۔ یہ کچھ بھی کر سکتا ہے، حتیٰ کہ خود اکاؤنٹ بند کرنا بھی۔ آپ کو اسے ایک بار بنانا چاہیے، multi-factor authentication سیٹ اپ کرنا چاہیے، اور پھر روزمرہ کے کام کے لیے اسے کبھی دوبارہ استعمال نہیں کرنا چاہیے۔

بالکل مٹھی بھر کام ہیں جن کے لیے root اکاؤنٹ درکار ہوتا ہے: اکاؤنٹ کا ای میل پتہ تبدیل کرنا، billing معلومات دیکھنا جو بصورتِ دیگر تفویض نہ کی گئی ہو، اکاؤنٹ بند کرنا، اور چند دیگر انتظامی آپریشنز جنہیں AWS واضح طور پر root تک محدود کرتا ہے۔ باقی ہر چیز کے لیے — users بنانا، انفراسٹرکچر deploy کرنا، ڈیٹابیسز تک رسائی کرنا — آپ IAM users اور roles استعمال کرتے ہیں۔ root اکاؤنٹ عمارت کے مینیجر کے لیے ہے۔ باقی سب کے پاس مناسب keycards ہیں۔

Priya نے اسی دوپہر سب کے لیے الگ IAM users بنائے۔ اس نے Leo کو development ماحول میں deploy کرنے کی permissions دیں۔ Production نہیں۔ Billing نہیں۔ Networking نہیں۔ صرف deployment۔

"یہ restrictive محسوس ہوتا ہے،" Leo نے کہا۔

"اسی سے آپ کو پتہ چلتا ہے کہ یہ صحیح ہے،" Priya نے جواب دیا۔

development بمقابلہ production کی حد پہلی اور سب سے اہم least-privilege لکیر تھی جو Priya نے کھینچی۔ ڈویلپرز کو development میں تیزی سے آگے بڑھنے کی ضرورت تھی: resources بنانا، configurations کا امتحان لینا، غلطیاں کرنا۔ لیکن production مختلف تھا۔ production تبدیلیوں کو سوچا سمجھا، جائزہ لیا گیا، اور ایک کنٹرول شدہ عمل کے ذریعے انجام دیا جانا چاہیے تھا۔ کسی ڈویلپر کو براہِ راست production رسائی دینا انہیں development کی رفتار سے production غلطیاں کرنے کی صلاحیت دینا تھا۔

وقت کے ساتھ، Priya نے ایک ایسا نظام بنایا جہاں production رسائی ایک role assumption عمل کے ذریعے عارضی طور پر دی جاتی تھی: ایک ڈویلپر جسے production تبدیلی کرنی ہوتی، رسائی کی درخواست کرتا، اسے 4 گھنٹے کی window کے لیے ملتی، تبدیلی کرتا، اور رسائی خودکار طور پر ختم ہو جاتی۔ window کو CloudTrail میں لاگ کیا جاتا۔ رسائی ختم ہونے کے بعد استعمال نہیں کی جا سکتی تھی۔ production کی حفاظت رسائی کو مستقل طور پر انکار کر کے نہیں، بلکہ رسائی کو وقت کی پابند اور قابلِ آڈٹ بنا کر کی گئی۔

آپ سوچ رہے ہوں گے: اگر ہر چیز ڈیفالٹ طور پر denied ہے، تو root اکاؤنٹ کے پاس مکمل رسائی کیوں ہے؟ root اکاؤنٹ خاص ہے — یہ IAM کو مکمل طور پر نظرانداز کر دیتا ہے۔ بالکل اسی لیے آپ اسے تالے میں بند رکھتے ہیں۔ AWS میں ہر دوسرا عمل IAM کی evaluation chain سے گزرتا ہے، جہاں ایک غائب Allow ایک Deny کے برابر ہے۔

**Blast Radius: کیوں least privilege کمپنیوں کو بچاتا ہے**

ایک تصور ہے جسے سیکیورٹی انجینیئر credential کے سمجھوتے کے بارے میں سوچنے کے لیے استعمال کرتے ہیں: **blast radius**۔

Blast radius وہ زیادہ سے زیادہ نقصان ہے جو کوئی حملہ آور کر سکتا ہے اگر اسے کوئی خاص credential حاصل ہو جائے۔

AWS اکاؤنٹ کے root credentials والے حملہ آور کا blast radius لامحدود ہوتا ہے۔ وہ ہر resource حذف کر سکتے ہیں، ڈیٹا کا ہر بائٹ exfiltrate کر سکتے ہیں، ہر Region میں GPU instances spin up کر سکتے ہیں، اور اکاؤنٹ بند کر سکتے ہیں۔ credential خود کوئی حدود نہیں رکھتا۔

Leo کے IAM credentials والے حملہ آور — development ماحول میں deploy کرنے اور ایک S3 bucket سے read کرنے تک محدود — کا blast radius بہت چھوٹا ہوتا ہے۔ وہ dev میں deploy کر سکتے ہیں۔ وہ کچھ فائلیں read کر سکتے ہیں۔ وہ production کو نہیں چھو سکتے۔ وہ ڈیٹابیس تک رسائی نہیں کر سکتے۔ وہ billing نہیں دیکھ سکتے۔ وہ GPU instances spin up نہیں کر سکتے۔

پہلے کی خلاف ورزی کی کہانی کا blast radius بڑا تھا کیونکہ ڈویلپر کے credentials admin تھے۔ اگر وہی credentials ان کے اصل کام تک محدود ہوتے — ایک مخصوص ماحول میں deploy کرنا — تو نقصان بہت کم ہوتا۔ حملہ پھر بھی ہو سکتا تھا۔ نتیجہ مختلف ہوتا۔

یہی وجہ ہے کہ least privilege صرف policy نہیں ہے۔ یہ آرکیٹیکچر ہے۔ ہر وہ permission جو آپ نہیں دیتے وہ blast radius ہے جو آپ کے پاس نہیں ہے۔

**جب آپ یہ غلط کرتے ہیں تو کیا ہوتا ہے**

تین منظر نامے، بڑھتی ہوئی شدت کی ترتیب میں:

**منظر نامہ 1**: admin رسائی والا ایک ملازم کمپنی چھوڑ دیتا ہے۔ کوئی اس کا اکاؤنٹ غیر فعال نہیں کرتا۔ تین ماہ بعد، اسے ابھی بھی رسائی حاصل ہے۔ یہ مسلسل ہوتا ہے۔ IAM اسے حل کرتا ہے: آپ user غیر فعال کرتے ہیں۔ فوراً، ہر جگہ۔

یہ سب سے عام IAM failure mode ہے، اور یہ مکمل طور پر قابلِ تدارک ہے۔ زیادہ تر تنظیموں کے پاس جسمانی رسائی منسوخ کرنے کا عمل ہوتا ہے (badge واپس کرنا، لیپ ٹاپ واپس کرنا) لیکن IAM کو نظرانداز کر دیتی ہیں۔ وہ offboarding چیک لسٹ جس میں "IAM user غیر فعال کریں" اور "تمام IAM groups سے ہٹائیں" شامل ہو، کوئی پیچیدہ انجینیئرنگ چیلنج نہیں ہے — یہ عمل کا نظم و ضبط ہے۔ جو ٹیمیں اسے مستقل طور پر کرتی ہیں وہی وہ ہیں جنہیں کبھی پتہ نہیں چلتا کہ کیا ہوتا ہے جب کوئی سابق ملازم ابھی بھی production ڈیٹابیس تک رسائی کر سکتا ہے۔

**منظر نامہ 2**: ایک ڈویلپر کا لیپ ٹاپ سمجھوتہ ہو جاتا ہے۔ حملہ آور کو ایک config فائل میں محفوظ AWS credentials ملتے ہیں جن کے پاس مکمل admin permissions ہیں۔ چونکہ credentials کے پاس وسیع رسائی ہے، حملہ آور کچھ بھی کر سکتا ہے: cryptocurrency mine کرنا، ڈیٹا چرانا، backups حذف کرنا۔ least privilege کے ساتھ: credentials صرف اپنے محدود scope کے لیے کام کرتے ہیں۔ blast radius محدود رہتا ہے۔

config فائل میں credentials کا پیٹرن اس سے زیادہ عام ہے جتنا اسے ہونا چاہیے۔ ڈویلپرز اکثر مقامی development کے لیے AWS credentials `~/.aws/credentials` میں محفوظ کرتے ہیں — جو ٹھیک ہے۔ مسئلہ تب ہوتا ہے جب ان credentials کے پاس sandbox ماحول تک محدود ہونے کے بجائے production سطح کی رسائی ہو۔ development credentials کو ایک development ماحول تک محدود ہونا چاہیے۔ production رسائی کے لیے assume کرنے کے واضح اقدامات درکار ہونے چاہئیں، نہ کہ یہ ہر لیپ ٹاپ پر ہر وقت موجود ہو۔

**منظر نامہ 3**: ایک خراب لکھی گئی ایپلیکیشن غلطی سے AWS credentials اپنے logs میں ظاہر کر دیتی ہے۔ اگر ان credentials کے پاس وسیع رسائی ہے، تو آپ کے پاس ایک تباہ کن خلاف ورزی ہے۔ اگر ان کے پاس محدود رسائی ہے — صرف اس مخصوص S3 bucket تک جس کی ایپلیکیشن کو ضرورت ہے — تو exposure محدود اور قابو میں ہے۔

logs میں ایپلیکیشن credentials کا منظر نامہ باریک ہے۔ یہ اکثر تب ہوتا ہے جب debugging کوڈ مکمل request context لاگ کرتا ہے — بشمول authorization headers — یا جب کوئی error handler تمام environment variables (بشمول `AWS_ACCESS_KEY_ID`) کو ایک log فائل میں serialize کرتا ہے۔ یہاں حفاظتی اقدام EC2 کے لیے IAM Roles ہیں، جو ایپلیکیشن کے ماحول سے static credentials کو مکمل طور پر ختم کر دیتے ہیں۔ اگر کوئی static credentials نہ ہوں، تو وہ logs میں ظاہر نہیں ہو سکتے۔

پیٹرن: رسائی کو کم سے کم تک محدود ہونا چاہیے۔ ہمیشہ۔ اس لیے نہیں کہ آپ اپنے لوگوں پر بھروسہ نہیں کرتے، بلکہ اس لیے کہ آپ کنٹرول نہیں کر سکتے کہ سمجھوتہ شدہ credentials کے ساتھ کیا ہوتا ہے۔

**اگر وسیع رسائی تو سہولت لیکن exposure**

ہمیشہ ٹیموں کو ان کی ضرورت سے زیادہ وسیع رسائی دینے کا لالچ ہوتا ہے — یہ ڈیپلائمنٹس کو تیز کرتا ہے، رگڑ کم کرتا ہے، ان "Access Denied" لمحوں سے بچاتا ہے جو بہاؤ توڑ دیتے ہیں۔ اگر آپ سب کو admin رسائی دیں، تو ڈیپلائمنٹس ہموار ہوتی ہیں اور کوئی بلاک نہیں ہوتا — لیکن جب credentials leak ہوتے ہیں (اور وہ ہوتے ہیں)، تو حملہ آور مکمل admin حقوق وراثت میں لے لیتا ہے۔ ایک سمجھوتہ شدہ لیپ ٹاپ ایک مکمل اکاؤنٹ خلاف ورزی بن جاتا ہے۔ پہلے کم سے کم permission لکھیں۔ صرف اس وقت پھیلائیں جب کچھ ناکام ہو۔ یہ اصول کمپنیوں کو بچاتا ہے۔

**Multi-Factor Authentication: دوسرا تالا**

least privilege کے باوجود، credentials چوری ہو سکتے ہیں۔ Passwords کا اندازہ لگایا جا سکتا ہے، phish کیا جا سکتا ہے، یا leak ہو سکتے ہیں۔ IAM اسے **Multi-Factor Authentication (MFA)** سے حل کرتا ہے۔

MFA ایسی چیز مانگتا ہے جو آپ *جانتے* ہیں (password) ساتھ ہی ایسی چیز جو آپ کے پاس *ہے* (ایک فون، ایک hardware key)۔ اگر کوئی حملہ آور آپ کا password چوری کر بھی لے، وہ آپ کا فون بھی رکھے بغیر لاگ ان نہیں کر سکتا۔

MFA ہر IAM user کے لیے فعال ہونا چاہیے۔ root اکاؤنٹ کے لیے یہ غیر قابلِ مذاکرہ ہے۔

Priya نے دوپہر سب کے لیے اسے سیٹ اپ کرنے میں گزاری۔ یہ ہموار نہیں چلا۔

Leo کی authenticator ایپ نے دو بار غلط اکاؤنٹ register کیا۔ اسے QR code تین بار اسکین کرنا پڑا کیونکہ اس کے لیپ ٹاپ کی گھڑی تھوڑی غیر مطابقت میں تھی، جس کی وجہ سے time-based tokens ناکام ہو رہے تھے۔ تیسری کوشش پر، یہ کام کر گیا۔

"کیا ایپ کے بغیر یہ کرنے کا کوئی طریقہ ہے؟" Leo نے اپنا فون دیکھتے ہوئے پوچھا۔

"Hardware keys،" Priya نے کہا۔ "ایک جسمانی آلہ جو USB میں لگتا ہے۔ ایپ سے زیادہ محفوظ۔ زیادہ مہنگا۔"

"کتنا زیادہ؟"

"تقریباً $50 فی key۔ آپ دو چاہیں گے، اس صورت میں کہ آپ ایک کھو دیں۔"

Tom نے اپنی نوٹ بک میں "فی ڈویلپر $100" لکھا۔

"ہم انہیں خرید رہے ہیں،" Priya نے کہا۔ "کم از کم root اکاؤنٹ کے لیے۔"

Tom نے پوچھا کہ کیا یہ مجموعی طور پر بہت زیادہ رگڑ ہے۔ Priya نے خلاف ورزی کی کہانی دوبارہ کھول دی۔

Tom نے فوراً MFA سیٹ اپ کر لیا۔

"اور اگر کوئی اس منتقلی کے درمیان توڑ پھوڑ کرنے کی کوشش کرے تو؟" Priya نے پوچھا۔ "اس سے پہلے کہ سب کے پاس MFA فعال ہو؟"

کسی کے پاس اچھا جواب نہیں تھا۔ اس نے باقی سب سے پہلے، root اکاؤنٹ کے لیے MFA سیٹ اپ کیا۔

**IAM Access Analyzer: دوسری نظر**

MFA سیٹ اپ مکمل ہونے کے بعد Priya کے پاس ٹیم کو دکھانے کے لیے ایک اور اوزار تھا۔

"یہ خودکار طور پر چلتا ہے،" اس نے ایک نیا console ٹیب کھولتے ہوئے کہا۔

**IAM Access Analyzer** ایک سروس ہے جو آپ کی IAM policies کا مسلسل تجزیہ کرتی ہے اور ایسی کسی بھی چیز کو نشان زد کرتی ہے جو آپ کے اکاؤنٹ سے باہر — یا آپ کی توقع سے باہر — resources تک رسائی دیتی ہے۔

اسے پہلی بار چلانے پر ہی کچھ ملا۔

ایک S3 bucket — جسے Leo نے تین ہفتے پہلے "عارضی" کے طور پر سیٹ اپ کیا تھا اور پھر بھول گیا تھا — کی ایک bucket policy تھی جو عوامی read رسائی کی اجازت دیتی تھی۔ bucket میں کچھ test ڈیٹا فائلیں تھیں، کچھ حساس نہیں۔ لیکن اس میں ایک folder بھی تھا جسے Leo نے `db-backups-staging` کا نام دیا تھا اور import کے عمل کا امتحان لینے کے لیے چند export شدہ SQL فائلوں سے بھرا تھا۔

"کیا ان SQL فائلوں میں کوئی حساس چیز ہے؟" Priya نے پوچھا۔

Leo نے folder کا نام دیکھا۔ پھر اس کے اندر کی فائلیں۔ پھر چھت۔

"میں نے staging ڈیٹابیس export کی،" اس نے کہا۔ "جس میں ابتدائی production گاہک کے ڈیٹا کی کاپیاں ہیں۔"

Priya نے آہستہ سے اپنا لیپ ٹاپ بند کر دیا۔

bucket پانچ منٹ کے اندر private کر دیا گیا۔ Access Analyzer مستقبل کی کسی بھی ایسی policies کے لیے نگرانی جاری رکھتا رہا جو resources کو غیر متوقع طور پر کھول دیں۔

"اسے ایک perimeter alarm کے طور پر سوچیں،" Priya نے کہا۔ "ہر بار جب کوئی غلطی سے کوئی دروازہ کھلا چھوڑ دیتا ہے، یہ ہمیں بتاتا ہے۔"

آپ سوچ رہے ہوں گے: کیا IAM Access Analyzer دستی policy جائزے کی جگہ لے لیتا ہے؟ نہیں۔ یہ ایک پتہ لگانے کا اوزار ہے، روک تھام کا اوزار نہیں۔ یہ آپ کو اس رسائی کے بارے میں بتاتا ہے جو دی گئی ہے — یہ آپ کو نہیں بتا سکتا کہ آیا وہ رسائی جان بوجھ کر تھی۔ "کیا یہ policy درست تھی؟" کا انسانی جائزہ پھر بھی کرنا پڑتا ہے۔ Access Analyzer بس یہ یقینی بناتا ہے کہ کھلی کھڑکیاں نظر سے نہ گزر جائیں۔

## طاقتیں اور حدود

**IAM صحیح اوزار ہے**:

- یہ کنٹرول کرنے کے لیے کہ کون اور کیا ہر AWS resource تک رسائی کر سکتا ہے
- users، services، اور cross-account حدود میں least-privilege نافذ کرنے کے لیے
- نظاموں کے درمیان long-lived credentials شیئر کرنے کی ضرورت ختم کرنے کے لیے
- ہر IAM عمل خودکار طور پر لاگ ہوتا ہے، جو آپ کو ایک audit trail دیتا ہے کہ کس نے کیا اور کب کیا (باب 14 میں کور کیا گیا)
- Cross-account رسائی: Account A میں ایک IAM Role کو Account B میں ایک principal assume کر سکتا ہے، جو credential شیئرنگ کے بغیر AWS اکاؤنٹس کے درمیان resources کی کنٹرول شدہ شیئرنگ کی اجازت دیتا ہے

**جہاں IAM مشکل ہو جاتا ہے**: IAM policies درجنوں roles میں سینکڑوں statements تک بڑھ سکتی ہیں، اور ایک "Access Denied" error کو debug کرنے کے لیے یہ سمجھنا پڑتا ہے کہ ان policies میں سے کون سی مؤثر ہے — ایک ایسا کام جو سننے سے زیادہ مشکل ہے۔ سب سے عام IAM غلطی بہت کم رسائی نہیں — بہت زیادہ ہے۔ "بس اسے چلانے" کے لیے بنائی گئی over-permissive policies سیکیورٹی liabilities بن جاتی ہیں جنہیں بعد میں واپس لینا تکلیف دہ ہوتا ہے۔ پہلے کم سے کم permission لکھیں۔ صرف اس وقت پھیلائیں جب کچھ ناکام ہو۔

IAM کے ساتھ پیمانے پر ایک عملی چیلنج ہے: **policy sprawl**۔ وہ تنظیمیں جو کئی سال سے AWS چلا رہی ہیں اکثر درجنوں یا سینکڑوں custom policies رکھتی ہیں، جن میں سے بہت سی overlap کرتی ہیں، کچھ کبھی استعمال نہیں ہوتیں، اور چند ایسی طریقوں سے ایک دوسرے سے متضاد ہوتی ہیں جن پر کسی نے غور نہیں کیا کیونکہ تضادات صرف edge cases کے لیے اہم ہوتے ہیں۔ AWS **IAM Access Analyzer** (جسے ہم نے اس باب میں متعارف کرایا) اور **IAM policy simulation** اوزار فراہم کرتا ہے تاکہ policies کا آڈٹ اور انہیں منطقی بنایا جا سکے۔ لیکن سب سے مؤثر حکمتِ عملی شروع سے صاف policies بنانا اور باقاعدگی سے آڈٹ کرنا ہے — بجائے اس کے کہ policies جمع ہونے دی جائیں اور بعد میں انہیں سلجھانے کی کوشش کی جائے۔

Priya نے ایک سہ ماہی IAM جائزہ سیٹ اپ کیا: تمام roles اور policies کی فہرست بنائیں، CloudTrail logs کے ذریعے چیک کریں کہ کون سی فعال طور پر استعمال ہو رہی ہیں، کسی بھی غیر استعمال شدہ credentials یا حد سے زیادہ وسیع policies کو ہٹانے یا محدود کرنے کے لیے نشان زد کریں۔ جائزے میں فی سہ ماہی دو گھنٹے لگے اور اپنے پہلے سال میں تین policy مسائل پکڑے۔

"یہ دلچسپ کام نہیں ہے،" اس نے کہا۔ "لیکن رسائی کے جائزے وہ طریقہ ہیں جس سے آپ وہ چیزیں ڈھونڈتے ہیں جو تباہ کن ہوتیں اگر کوئی پہلے انہیں نوٹ کر لیتا۔"

## خلاصہ

Admin123 password علامت تھی۔ بیماری یہ تھی کہ Nimbus کے پاس کوئی رسائی کنٹرول حکمتِ عملی تھی ہی نہیں — ایک شیئر شدہ root credential، کوئی roles نہیں، کوئی policies نہیں، کوئی audit trail نہیں۔ IAM صرف علامت ٹھیک نہیں کرتا؛ یہ ٹیم کو ایک ایسے سوال کا جواب دینے پر مجبور کرتا ہے جس سے وہ بچ رہے تھے: بالکل کون، کیا کرنے کا مجاز ہے؟ اس سوال کا جواب ہر محفوظ AWS آرکیٹیکچر کی بنیاد ہے۔

- **IAM** (Identity and Access Management) وہ طریقہ ہے جس سے آپ کنٹرول کرتے ہیں کہ AWS میں کون کیا کر سکتا ہے۔ بنیادی اجزا ہیں: **Users**، **Groups**، **Roles**، اور **Policies**۔
- ڈیفالٹ طور پر، AWS میں ہر چیز **denied** ہے۔ Permissions کو واضح طور پر grant کرنا پڑتا ہے۔
- **Principle of Least Privilege** کا مطلب ہے ہر شناخت کو صرف وہ رسائی دینا جس کی اسے ضرورت ہے — اگر کوئی credential کبھی سمجھوتہ ہو جائے تو **blast radius** کو کم سے کم کرنا۔
- **root اکاؤنٹ** کچھ بھی کر سکتا ہے، تباہ کن چیزیں بھی۔ اسے MFA کے پیچھے تالے میں بند کریں اور جتنا کم ممکن ہو استعمال کریں۔
- ہر IAM user کے لیے **MFA** فعال کریں۔ غیر قابلِ مذاکرہ — امتحان میں اور production میں۔

## Exam Tips

*SAA-C03 ڈومین 1 — ٹاسک 1.1 (AWS resources تک محفوظ رسائی)*

- **ڈیفالٹ طور پر ہر چیز denied ہے۔** ایک واضح "Allow" درکار ہے۔ اگر کوئی policy کسی action کا ذکر نہیں کرتی، تو وہ action denied ہے۔
- **واضح Deny ہمیشہ جیتتا ہے۔** اگر chain میں کوئی بھی policy کسی action کو deny کرتی ہے، تو اس deny کو chain میں کہیں بھی موجود Allow override نہیں کر سکتا۔ یہ بہت سے امیدواروں کو غافل پکڑتا ہے۔
- **root اکاؤنٹ ≠ IAM admin۔** root اکاؤنٹ IAM سے ایک الگ credential ہے۔ آپ root اکاؤنٹ حذف نہیں کر سکتے۔ آپ اس کے استعمال کو محدود کر *سکتے* ہیں (اور کرنا چاہیے)۔
- **IAM global ہے**، Regional نہیں۔ IAM users، groups، roles، اور policies پورے AWS اکاؤنٹ میں موجود ہوتے ہیں، per-Region نہیں۔
- **Roles AWS سروسز کو رسائی دینے کا ترجیحی طریقہ ہیں۔** اگر کسی EC2 instance کو S3 تک رسائی چاہیے، تو آپ instance سے ایک IAM Role منسلک کرتے ہیں — آپ مشین پر credentials محفوظ نہیں کرتے۔ یہ پیٹرن امتحان میں مسلسل آتا ہے۔
- **IAM Access Analyzer** اس وقت findings پیدا کرتا ہے جب resources اکاؤنٹ سے باہر سے یا تنظیم سے باہر سے قابلِ رسائی ہوں۔ جب کوئی امتحانی منظر نامہ S3 یا KMS تک غیر ارادی بیرونی رسائی کا پتہ لگانے کا ذکر کرے، تو Access Analyzer جواب ہے۔
- **root اکاؤنٹ کے لیے MFA لازمی ہے**، اختیاری نہیں، AWS سیکیورٹی بہترین طریقوں کے سیاق و سباق میں۔ root اکاؤنٹ کو محفوظ کرنے کے بارے میں امتحانی سوالات میں ہمیشہ MFA درست جواب کا حصہ ہوتا ہے۔
- **Permission boundaries** ایک اعلیٰ درجے کی IAM خصوصیت ہے (باب 14 میں کور کی گئی) جو ایک IAM user یا role کی زیادہ سے زیادہ permissions کو محدود کرتی ہے، چاہے ان کی policies زیادہ grant کریں۔ "privilege escalation کو روکنے" یا "زیادہ سے زیادہ permission کی حد طے کرنے" کے بارے میں امتحانی سوالات permission boundaries کی طرف اشارہ کرتے ہیں۔
- **Service Control Policies (SCPs)** تنظیمی سطح کی policies ہیں جو محدود کرتی ہیں کہ ایک AWS Organization کے رکن اکاؤنٹس میں کیا کیا جا سکتا ہے۔ وہ IAM سطح سے اوپر کام کرتی ہیں — حتیٰ کہ ایک اکاؤنٹ ایڈمنسٹریٹر بھی SCP کی طے کردہ حدود سے تجاوز نہیں کر سکتا۔ جب کوئی امتحانی منظر نامہ multi-account سیکیورٹی گورننس شامل کرے، تو SCPs سوچیں۔
- **CloudTrail** تمام IAM API calls ریکارڈ کرتا ہے۔ جب کوئی امتحانی منظر نامہ پوچھے "آپ کیسے آڈٹ کریں گے کہ کن صارفین نے IAM policies میں تبدیلیاں کیں،" تو جواب CloudTrail ہے۔ ہر IAM عمل — ایک user بنانا، ایک policy میں ترمیم کرنا، ایک role assume کرنا — لاگ ہوتا ہے۔ 90 دن کی event تاریخ خودکار اور مفت ہے؛ طویل مدتی برقراری اور alerting کے لیے، آپ کو ایک Trail بنانا ہوگا جو logs کو ایک S3 bucket تک پہنچائے۔

سب سے محفوظ اور آپریشنل طور پر مناسب حل کیا ہے؟

A) Access keys کو کوڈ کے بجائے EC2 instance پر environment variables میں محفوظ کریں  
B) S3 read permissions کے ساتھ ایک dedicated IAM user بنائیں اور credentials development ٹیم کے ساتھ شیئر کریں  
C) مناسب S3 read permissions والا ایک IAM Role براہِ راست EC2 instances سے منسلک کریں

**اشارہ 1**: instance پر کہیں بھی credentials محفوظ کرنے کا مسئلہ یہ ہے کہ credentials leak ہو سکتے ہیں۔ کیا EC2 instance کو credentials بالکل استعمال کیے بغیر رسائی دینے کا کوئی طریقہ ہے؟

**اشارہ 2**: AWS کے پاس ایک میکانزم ہے جہاں سروسز کو static credentials کی ضرورت کے بغیر permissions دی جا سکتی ہیں۔ اس میکانزم کو کیا کہتے ہیں؟

**اشارہ 3**: IAM Roles کو EC2 instances سے منسلک کیا جا سکتا ہے۔ جب ایسا ہوتا ہے، instance خودکار طور پر عارضی credentials وصول کرتا ہے جنہیں AWS گھماتا ہے۔ کوئی static credentials درکار نہیں۔

**جواب**: C

**وضاحت**: ایک EC2 instance سے ایک IAM Role منسلک کرنا درست پیٹرن ہے۔ instance کو EC2 metadata service کے ذریعے عارضی، گھومنے والے credentials خودکار طور پر ملتے ہیں۔ leak، گھمانے، یا غلطی سے کسی repository میں commit کرنے کے لیے کوئی long-lived credentials موجود ہی نہیں ہوتے۔

**A کیوں نہیں؟** EC2 instance پر environment variables پھر بھی leak ہو سکتے ہیں — ایپلیکیشن logs، debugging endpoints، یا اگر instance سمجھوتہ ہو جائے، کے ذریعے۔ Static credentials مسئلہ ہیں، ان کی location نہیں۔

**B کیوں نہیں؟** ایک shared IAM user بنانا اور credentials کسی ٹیم میں تقسیم کرنا least privilege کی خلاف ورزی کرتا ہے اور credential rotation کو ایک ڈراؤنا خواب بنا دیتا ہے۔ اگر ایک شخص چلا جائے، تو آپ shared credentials بدلے بغیر صرف اس کی رسائی آسانی سے منسوخ نہیں کر سکتے۔

**D کیوں نہیں؟** کسی بھی ایپلیکیشن کے لیے root اکاؤنٹ credentials استعمال کرنا ایک شدید سیکیورٹی خلاف ورزی ہے۔ root اکاؤنٹ کے پاس لامحدود رسائی ہوتی ہے اور اس کے credentials کبھی اکاؤنٹ مالک کے کنٹرول سے باہر نہیں جانے چاہئیں۔

*SAA-C03 ڈومین 1 — ٹاسک 1.1 (IAM roles, least privilege)*

**مشق 3 — آرکیٹیکچر چیلنج** *(اختیاری)*

Nimbus اگلے ماہ تین نئے ڈویلپرز onboard کر رہا ہے۔ ہر ایک کو رسائی کی مختلف سطحوں کی ضرورت ہوگی: ایک ڈیٹابیس layer پر کام کرتا ہے، ایک ایپلیکیشن سرورز پر، ایک front-end static فائلوں پر۔ ایک CI/CD pipeline بھی ہے جسے کوڈ deploy کرنا ہے۔

اس منظر نامے کے لیے ایک IAM ڈھانچہ ڈیزائن کریں۔ آپ کون سے users، groups، roles، اور policies بنائیں گے؟ نافذ کرنے کے لیے سب سے اہم least-privilege حد کیا ہوگی؟

*(کوئی واحد درست جواب نہیں ہے۔ سوچیں کہ اگر کوئی ایک شناخت سمجھوتہ ہو جائے تو blast radius کو کیسے کم سے کم کیا جائے۔)*
