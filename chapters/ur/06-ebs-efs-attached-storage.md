# باب 6: وہ ڈسک جو آپ کے پیچھے پیچھے چلتی ہے

Tom کے پاس ایک سرخ قلم تھا اور ایک عادت جو Leo کو گھبراہٹ میں ڈال دیتی تھی۔

ہر ہفتے کی صبح، وہ ایک کافی کے ساتھ بیٹھتا اور کچھ پرنٹ کرتا۔ ای میل نہیں۔ رپورٹس نہیں۔ وہ Nimbus جو چلا رہا تھا اس کی فہرست پرنٹ کرتا اور اسے ایک کھاتے کی طرح پڑھتا، لائن بہ لائن، ہاتھ میں قلم۔ وہ یہ ہفتہ دو سے کر رہا تھا۔ پرنٹر کے گرم ہونے کی آواز ویک اینڈ کا حصہ بن چکی تھی۔

Leo اسے "وہ چیز جو Tom کرتا ہے جو Leo کو محسوس کراتی ہے جیسے اس نے کچھ غلط کیا ہو" کہتا تھا۔

اس ہفتے، Tom نے کچھ دائرے میں گھیرا اور پرنٹ آؤٹ Maya کی میز پر بغیر ایک لفظ کہے چھوڑ دیا۔

اس نے اسے پیر کی صبح پایا۔ ایک دائرہ۔ حاشیے میں ایک نوٹ، تین الفاظ:

*سب کچھ۔ ایک مشین۔*

تصاویر اب S3 میں محفوظ تھیں — وہ مسئلہ حل ہو چکا تھا۔ لیکن ڈیٹابیس ابھی بھی اسی EC2 instance پر تھا جیسے web server۔ آرڈر کی تاریخ، گاہک کے ریکارڈز، دو ماہ کی ٹرانزیکشنز۔ ایپلیکیشن اور اس کے نیچے ہر چیز، ایک واحد ورچوئل ڈسک شیئر کرتی ہوئی۔

"اگر instance crash ہو جائے تو ڈیٹابیس کا کیا ہوتا ہے؟" Maya نے پوچھا، پرنٹ آؤٹ اس کے ہاتھ میں۔

"وہ بھی crash ہو جاتا ہے،" Leo نے کہا۔

"اور ڈیٹا؟"

"اس بات پر منحصر ہے کہ ڈیٹابیس اسے کیسے محفوظ کرتا ہے۔"

وہ "منحصر" ہی مسئلہ تھا۔

**EC2 instances ڈیٹا کیسے محفوظ کرتی ہیں**

جب کوئی EC2 instance چلتی ہے، تو اس کا آپریٹنگ سسٹم ڈسک پر کہیں رہتا ہے۔ اس ڈسک کو **root volume** کہا جاتا ہے۔ ڈیفالٹ طور پر، یہ ایک **EBS volume** ہے — چاہے آپ اس کے بارے میں نہ سوچیں۔

لیکن کچھ اور بھی ہے: EC2 instances کے پاس **instance store** اسٹوریج بھی ہوتی ہے۔

instance store عارضی اسٹوریج ہے جو جسمانی طور پر اس بنیادی ہارڈ ویئر سے منسلک ہے جو آپ کی ورچوئل مشین چلاتا ہے۔ یہ انتہائی تیز ہے — AWS میں تقریباً کسی بھی دوسرے اسٹوریج اختیار سے تیز۔ لیکن اس کے ساتھ ایک شرط ہے۔

instance store **عارضی** ہے۔

جب instance رکتی یا terminate ہوتی ہے، تو instance store کا ڈیٹا ختم ہو جاتا ہے۔ مستقل طور پر۔ بحال نہیں ہو سکتا۔ AWS آپ کو اس کے بارے میں بہت زور سے خبردار نہیں کرتا، اور اسی طرح ٹیمیں اسے دریافت کرتی ہیں: ڈیٹا کھو کر۔

instance store caches، عارضی پروسیسنگ فائلوں، اور scratch جگہ کے لیے مناسب ہے۔ کبھی اس ڈیٹا کے لیے نہیں جس کی آپ کو پروا ہے۔

**EBS: مستقل ڈسک**

ایک ایسی بیرونی ہارڈ ڈرائیو کا تصور کریں جسے آپ اپنی EC2 instance میں لگا سکتے ہیں — ایک جو آپ کے اسے نکالنے پر غائب نہیں ہوتی، اور جسے اگر ضرورت ہو تو آپ کسی مختلف مشین پر منتقل کر سکتے ہیں۔ AWS اسے **EBS** کہتا ہے: Elastic Block Store۔

EBS، EC2 instances کے لیے مستقل block اسٹوریج ہے۔

block اسٹوریج کا مطلب ہے کہ یہ ایک حقیقی ہارڈ ڈرائیو کی طرح برتاؤ کرتا ہے: آپ کا آپریٹنگ سسٹم اس پر فائل سسٹمز بنا سکتا ہے، من مانی positions پر من مانی bytes پڑھ اور لکھ سکتا ہے، اس پر ڈیٹابیسز چلا سکتا ہے، اور اسے بالکل ایک منسلک ڈسک کی طرح برت سکتا ہے۔

اہم خصوصیات:

**مستقل۔** instance store کے برعکس، EBS volumes instance کے رکنے، شروع ہونے، اور حتیٰ کہ instance terminate ہونے (کنفیگریشن کے مطابق) سے بچ جاتے ہیں۔ ڈیٹا volume پر رہتا ہے چاہے کوئی instance اسے استعمال نہ کر رہی ہو۔

یہاں ایک کنفیگریشن باریکی ہے: جب آپ کوئی EC2 instance بناتے ہیں، تو root volume کی ایک سیٹنگ ہوتی ہے جسے "Delete on Termination" کہتے ہیں۔ ڈیفالٹ طور پر، یہ true پر سیٹ ہے — instance terminate ہونے پر root volume حذف ہو جاتا ہے۔ اضافی ڈیٹا volumes کے لیے جو آپ منسلک کرتے ہیں، ڈیفالٹ false ہے — وہ instance terminate ہونے کے بعد برقرار رہتے ہیں۔ آپ دونوں سیٹنگز بدل سکتے ہیں۔ اگر آپ چاہتے ہیں کہ root volume instance terminate ہونے سے بچے (forensic تجزیے یا ڈیٹا ریکوری کے لیے)، تو "Delete on Termination" غیر فعال کریں۔ اگر آپ چاہتے ہیں کہ ڈیٹا volumes خودکار طور پر صاف ہوں، تو اسے فعال کریں۔

**منسلک اور علیحدہ کرنے کے قابل۔** ایک EBS volume کو ایک instance سے علیحدہ کیا جا سکتا ہے اور دوسری سے منسلک کیا جا سکتا ہے۔ اگر آپ کو ڈیٹا منتقل کرنا ہو یا ناکام instance سے بحال کرنا ہو، تو آپ volume علیحدہ کر کے کہیں اور دوبارہ منسلک کر سکتے ہیں۔

علیحدہ-اور-دوبارہ-منسلک کرنے کا workflow ایک snapshot restore سے سست ہے لیکن volume کی صحیح حالت محفوظ رکھتا ہے — تمام غیر committed لکھائیاں، تمام cached ڈیٹا، صحیح فائل سسٹم حالت۔ یہ اسے forensic تجزیے کے لیے مفید بناتا ہے (اصل سسٹم کو boot کیے بغیر volume کو ایک تجزیہ instance سے منسلک کریں) اور ڈیٹا منتقلی کے لیے (snapshot لیے بغیر ڈیٹابیس volume کو ایک بڑے instance پر منتقل کریں)۔

**واحد اٹیچمنٹ (زیادہ تر)۔** ڈیفالٹ طور پر، ایک EBS volume ایک وقت میں بالکل ایک EC2 instance سے منسلک ہوتا ہے۔ ایک واحد instance کے پاس متعدد EBS volumes ہو سکتے ہیں، لیکن ایک واحد EBS volume کو متعدد instances بیک وقت mount نہیں کر سکتیں (ایک استثنا کے ساتھ: EBS Multi-Attach، جس کے محدود استعمال کے مواقع اور اہم پابندیاں ہیں)۔

EBS Multi-Attach io1/io2 (Provisioned IOPS) volumes کو ایک ہی AZ میں متعدد instances سے بیک وقت منسلک ہونے کی اجازت دیتا ہے۔ یہ ایسا لگتا ہے جیسے یہ "shared storage" کا مسئلہ حل کرتا ہے، لیکن اس کے ساتھ سنگین رکاوٹیں آتی ہیں: منسلک instances پر ایپلیکیشنز کو ہم وقت رسائی کو ہم آہنگ کرنے کے قابل ہونا چاہیے — shared فائل سسٹم semantics (lock management، write ordering) EBS فراہم نہیں کرتا۔ عمل میں، EBS Multi-Attach ان clustered ڈیٹابیس ایپلیکیشنز کے لیے استعمال ہوتا ہے جو ہم آہنگی خود سنبھالتی ہیں۔ عام shared فائل رسائی کے لیے، EFS آسان اور زیادہ مناسب ہے۔

EBS کی تشبیہ: ایک بیرونی ہارڈ ڈرائیو جو ایک لیپ ٹاپ میں لگی ہے۔ لیپ ٹاپ (EC2 instance) اسے پڑھ اور لکھ سکتا ہے۔ جب آپ کا کام ہو جائے، تو آپ اسے نکال کر کسی مختلف لیپ ٹاپ میں لگا سکتے ہیں۔

**EBS Volume کی اقسام**

تمام EBS volumes ایک جیسی نہیں ہیں۔ AWS مختلف کارکردگی اور لاگت کے پروفائلز کے ساتھ کئی اقسام پیش کرتا ہے۔

**gp3 (General Purpose SSD)**: زیادہ تر workloads کے لیے ڈیفالٹ انتخاب۔ کارکردگی اور قیمت کا اچھا توازن۔ boot volumes، چھوٹے ڈیٹابیسز، اور development ماحول کے لیے موزوں۔

gp3 کے ڈیفالٹ بننے سے پہلے، **gp2** تھا — اور آپ اسے ابھی بھی عملی دنیا میں دیکھیں گے۔ gp2 volumes اپنی IOPS کارکردگی کو براہِ راست volume کے سائز سے باندھتے ہیں: آپ کو فی gigabyte 3 IOPS ملتے ہیں، زیادہ سے زیادہ 16,000 IOPS تک (جس کے لیے 5,334 GB volume درکار ہوتا ہے)۔ Throughput 250 MB/s پر محدود ہے۔ اس جوڑ کا مطلب ہے کہ gp2 پر، زیادہ IOPS حاصل کرنے کا واحد طریقہ volume کو بڑا بنانا ہے — چاہے آپ کو اضافی جگہ کی ضرورت نہ ہو۔ gp3 نے اس انحصار کو توڑ دیا: یہ سائز سے قطع نظر 3,000 IOPS اور 125 MB/s سے شروع ہوتا ہے، اور آپ کو IOPS اور throughput آزادانہ طور پر، کم لاگت پر کنفیگر کرنے دیتا ہے۔ AWS نئے volumes کے لیے gp3 کی سفارش کرتا ہے، لیکن چونکہ بہت سے موجودہ workloads ابھی بھی gp2 پر چلتے ہیں، آپ کو دونوں جاننے کی ضرورت ہے۔

**io2 (Provisioned IOPS SSD)**: I/O-سے بھرپور workloads کے لیے اعلیٰ کارکردگی کا اختیار۔ آپ بتاتے ہیں کہ آپ کو فی سیکنڈ کتنی I/O آپریشنز (IOPS) چاہئیں، اور AWS اس کارکردگی کی ضمانت دیتا ہے۔ بڑے production ڈیٹابیسز کے لیے موزوں۔

**st1 (Throughput Optimized HDD)**: بڑے sequential reads اور writes کے لیے optimized مقناطیسی اسٹوریج۔ SSD سے کم لاگت، لیکن random I/O کے لیے سست۔ ڈیٹا warehousing اور log پروسیسنگ کے لیے اچھا۔

**sc1 (Cold HDD)**: سب سے سستا EBS اختیار۔ کم رسائی کیے جانے والے ڈیٹا کے لیے۔ کسی بھی وقت-حساس چیز کے لیے موزوں نہیں۔

"gp3 کے مقابلے io2 کتنا زیادہ پڑتا ہے؟" Tom نے اپنی نوٹ بک سے نظر اٹھاتے ہوئے پوچھا۔

Leo نے pricing صفحہ کھولا۔ io2 gp3 کی فی-GB لاگت سے تقریباً تین گنا پڑتا تھا، نیز فی provisioned IOPS ایک الگ چارج۔ Tom نے فرق نوٹ کیا۔ "تو ہم gp3 استعمال کرتے ہیں جب تک ڈیٹابیس کو دراصل کارکردگی کی ضمانت کی ضرورت نہ ہو۔"

امتحان آپ سے تمام اقسام یاد کرنے کا تقاضا نہیں کرتا۔ یہ آپ کی ضروریات کو صحیح قسم سے ملانے کی صلاحیت کا امتحان لیتا ہے: IOPS ضروریات → io2۔ لاگت-حساس sequential workloads → st1۔ عام ویب ایپلیکیشنز → gp3۔

**IOPS بمقابلہ Throughput: امتیاز کیوں اہم ہے**

Tom اگلے منگل EBS volume کے سوال پر واپس آیا، CloudWatch چیک کرنے کے بعد۔

"میں EBS ڈیش بورڈ پر دو میٹرکس دیکھتا ہوں،" اس نے کہا۔ "IOPS اور throughput۔ یہ مختلف چیزیں ہیں؟"

وہ ہیں۔

**IOPS** (Input/Output Operations Per Second) ناپتا ہے کہ ڈسک فی سیکنڈ کتنی read یا write آپریشنز سنبھال سکتی ہے۔ ہر آپریشن عام طور پر چھوٹا ہوتا ہے — 4KB سے 256KB۔ زیادہ IOPS ان ڈیٹابیسز کے لیے اہم ہے جو بہت سی چھوٹی، random reads اور writes کرتے ہیں: انفرادی rows لانا، ریکارڈز اپڈیٹ کرنا، ہم وقت queries سنبھالنا۔

**Throughput** (MB/s میں ناپا گیا) ناپتا ہے کہ فی سیکنڈ کتنا ڈیٹا منتقل ہوتا ہے۔ زیادہ throughput sequential workloads کے لیے اہم ہے: بڑی log فائلیں پڑھنا، streaming analytics، بڑے datasets لوڈ کرنا۔

ایک ڈیٹابیس کو عام طور پر زیادہ IOPS اور کم-سے-معتدل throughput چاہیے۔ بڑی tables اسکین کرنے والے ایک ڈیٹا warehouse کو زیادہ throughput چاہیے اور وہ معتدل IOPS کے ساتھ گزارہ کر سکتا ہے۔

Tom Nimbus ڈیٹابیس کے CloudWatch میٹرکس دیکھ رہا تھا۔ IOPS رات کے کھانے کے رش کے دوران بڑھ رہے تھے — مختصر، random reads جب ایپلیکیشن مینو اشیاء اور آرڈر ڈیٹا لاتی۔ throughput کم تھا۔ پیٹرن ایک ایسے ڈیٹابیس workload سے میل کھاتا تھا جسے بہتر IOPS چاہیے تھا، بہتر throughput نہیں۔

"تو اگر ڈیٹابیس سست ہو جائے،" Tom نے کہا، "تو ہم volume اپ گریڈ کرنے سے پہلے چیک کرتے ہیں کہ یہ IOPS-bound ہے یا throughput-bound؟"

"درست،" Priya نے کہا۔ "gp3 سے io2 پر اپ گریڈ ایک لاگت پر IOPS شامل کرتا ہے۔ اگر مسئلہ throughput ہے، تو وہ اپ گریڈ مدد نہیں کرے گا۔ پہلے میٹرک چیک کریں۔"

یہ بالکل وہی ہے جس سے آپ مہنگے اسٹوریج اپ گریڈز سے بچتے ہیں جو غلط مسئلہ حل کرتے ہیں۔

**EBS Snapshots: بیک اپ**

یہاں کچھ ایسا ہے جو کمپنیوں کو باقاعدگی سے بچاتا ہے۔

ایک **EBS snapshot** ایک EBS volume کا ایک مخصوص-وقت کا بیک اپ ہے، جو S3 میں محفوظ ہوتا ہے (اگرچہ آپ اس تک EBS interface کے ذریعے رسائی کرتے ہیں، براہِ راست S3 کے ذریعے نہیں)۔ snapshots اضافی (incremental) ہیں: پہلا snapshot پورا volume پکڑتا ہے؛ بعد کے snapshots صرف وہی محفوظ کرتے ہیں جو آخری کے بعد بدلا۔

آپ کسی snapshot سے ایک نیا EBS volume بنا سکتے ہیں — ڈیٹابیس کی خرابی، ایک خراب ڈیپلائمنٹ، یا حادثاتی حذف سے پہلے کے ایک نقطے پر بحال کرتے ہوئے۔

آپ کو snapshots خودکار کرنے چاہئیں۔ AWS اس مقصد کے لیے **Amazon Data Lifecycle Manager** فراہم کرتا ہے: ایک policy define کریں (ہر 6 گھنٹے میں ایک snapshot لیں، آخری 7 دن رکھیں)، اور یہ خودکار طور پر چلتا ہے۔

Priya نے یہ ڈیٹابیس کے production میں جانے سے پہلے ہی سیٹ اپ کر لیا تھا۔

Leo نے اس کے بارے میں نہیں سوچا تھا۔

"کیا ہم نے سوچا ہے کہ اگر snapshot کا کام خاموشی سے ناکام ہو جائے تو کیا ہوگا؟" Priya نے پوچھا۔ "اگر policy چلے لیکن snapshots دراصل درست نہ ہوں؟"

انہوں نے اسی دوپہر restore کے عمل کا امتحان لیا۔

Nimbus production ڈیٹابیس کے لیے Priya کی مکمل snapshot بیک اپ policy، جب اس کے پاس اسے ٹھیک سے دستاویز کرنے کا وقت ہو گیا:

- **روزانہ snapshots**، 7 دن کے لیے برقرار۔ یہ عام ریکوری منظر نامے کو کور کرتے ہیں: ایک خراب ڈیپلائمنٹ، ایک حادثاتی حذف، ایک ہفتے کے اندر دریافت ہونے والا خرابی کا واقعہ۔
- **ہفتہ وار snapshots** (ہر اتوار رات 2 بجے لیے گئے)، 30 دن کے لیے برقرار۔ یہ اس منظر نامے کو کور کرتے ہیں جہاں کوئی مسئلہ فوراً پتہ نہ چلے — ایک باریک ڈیٹا خرابی جو صرف ہفتوں بعد محسوس ہوتی ہے۔
- ہفتے میں ایک بار `us-east-1` تک cross-region snapshot کاپی، 30 دن کے لیے برقرار۔ یہ اس منظر نامے کو کور کرتے ہیں جہاں پورا `us-west-2` Region دستیاب نہ ہو اور Nimbus کو ڈیٹابیس کہیں اور دوبارہ تعمیر کرنے کی ضرورت ہو۔

"یہ بہت سارے snapshots لگتے ہیں،" Leo نے کہا۔

"پہلے کے بعد ہر incremental snapshot چھوٹا ہوتا ہے،" Priya نے کہا۔ "آپ صرف وہی محفوظ کر رہے ہوتے ہیں جو بدلا۔ کل اسٹوریج لاگت معمولی ہے۔"

Tom پہلے ہی قیمت دیکھ چکا تھا۔ ایک 50GB ڈیٹابیس کے روزانہ snapshots، 7 دن کے لیے رکھے گئے، نیز 30 دن کے لیے برقرار ہفتہ وار snapshots — تقریباً $3 سے $5 فی ماہ۔ ان کے نہ ہونے کی لاگت، اگر ڈیٹابیس کبھی خراب ہو جاتا، ناقابلِ پیمائش حد تک زیادہ تھی۔

"اور Fast Snapshot Restore؟" Leo نے پوچھا۔ "میں نے یہ اختیار دیکھا تھا جب میں سیٹنگز دیکھ رہا تھا۔"

**Fast Snapshot Restore** (FSR) ایک EBS خصوصیت ہے جو اس I/O کارکردگی کے جرمانے کو ختم کرتی ہے جو عام طور پر اس وقت ہوتا ہے جب آپ پہلی بار ایک restore شدہ snapshot استعمال کرتے ہیں۔ FSR کے بغیر، ایک تازہ restore شدہ EBS volume پہلے چند منٹ یا گھنٹوں کے لیے خراب کارکردگی دکھاتا ہے کیونکہ ڈیٹا S3 سے سستی سے لوڈ ہوتا ہے — reads اس ڈیٹا کے لیے S3 پر جاتی ہیں جو ابھی تک volume پر نہیں کھینچا گیا۔ کسی مخصوص AZ میں کسی snapshot پر FSR فعال کے ساتھ، restore شدہ volume فوراً پوری کارکردگی کے لیے تیار ہوتا ہے۔

FSR اضافی پڑتا ہے — آپ فی snapshot فی AZ فی گھنٹہ ادا کرتے ہیں جب FSR فعال ہو۔ Nimbus کے ڈیزاسٹر ریکوری snapshots کے لیے، کبھی کبھار کا استعمال جاری FSR لاگت کا جواز نہیں بناتا تھا۔ ایک production ڈیٹابیس snapshot کے لیے جسے کسی ہنگامی صورتحال میں منٹوں میں restore اور آپریشنل ہونے کی ضرورت تھی، FSR قابلِ قدر تھا۔

"اس ہفتہ وار snapshot پر FSR فعال کریں جسے ہم دراصل ڈیزاسٹر ریکوری کے لیے استعمال کریں گے،" Priya نے کہا۔ "retention window میں ہر روزانہ snapshot پر اسے فعال نہ کریں۔"

Tom نے لاگت کا حساب اپنی اسپریڈ شیٹ میں شامل کیا۔

**ڈیزاسٹر ریکوری کے لیے Cross-Region Snapshot کاپی**

EBS snapshots اس Region میں رہتے ہیں جہاں وہ بنائے گئے۔ اگر پورا `us-west-2` Region نیچے چلا جائے، تو `us-west-2` میں آپ کے snapshots ناقابلِ رسائی ہیں۔

حل: **cross-region snapshot کاپی**۔ آپ ایک EBS snapshot کو کسی اور Region میں کاپی کر سکتے ہیں، آپ کو ایک قابلِ استعمال بیک اپ دیتے ہوئے چاہے آپ کا بنیادی Region دستیاب نہ ہو۔

AWS Data Lifecycle Manager ایک snapshot policy کے حصے کے طور پر خودکار cross-region کاپی سپورٹ کرتا ہے: `us-west-2` میں ایک روزانہ snapshot لیں، ہفتے میں ایک بار خودکار طور پر اسے `us-east-1` میں کاپی کریں۔ اگر آفت آئے، تو `us-east-1` میں ایک نیا EC2 instance لانچ کریں، cross-region snapshot سے restore کریں، DNS endpoint اپڈیٹ کریں، اور آپریشن جاری رکھیں۔

"یہ ڈیٹابیس کے لیے ہمارا ڈیزاسٹر ریکوری منصوبہ ہے،" Priya نے ٹیم کو policy کی دستاویزات پیش کرتے ہوئے کہا۔ "ایک مکمل multi-region آرکیٹیکچر نہیں — وہ ابھی ہماری ضرورت سے زیادہ پیچیدگی ہے۔ لیکن اگر `us-west-2` مکمل طور پر نیچے چلا جائے، تو ہم دو گھنٹوں کے اندر `us-east-1` میں restore کر سکتے ہیں۔"

"دو گھنٹے کا downtime،" Tom نے کہا۔

"بمقابلہ لامحدود downtime،" Priya نے کہا۔

Tom نے امتیاز تسلیم کیا۔

**EBS Encryption: یہ کہانی کہ آپ in-place کیوں encrypt نہیں کر سکتے**

Nimbus production ڈیٹابیس چھ ہفتے سے چل رہا تھا جب Priya نے کچھ نشان زد کیا۔

"EBS volume encrypt نہیں ہے،" اس نے کہا۔

"کیا ہم اسے encrypt کر سکتے ہیں؟" Leo نے پوچھا۔

"ہاں۔ لیکن in-place نہیں۔"

EBS encryption کے بارے میں بات یہ ہے: آپ کسی موجودہ، غیر encrypt شدہ EBS volume کو براہِ راست encrypt نہیں کر سکتے۔ ڈیٹا پہلے ہی plaintext میں لکھا جا چکا ہے۔ اسے encrypt کرنے کے لیے، آپ کو کرنا ہوگا:

1. غیر encrypt شدہ volume کا ایک snapshot بنائیں
2. snapshot کاپی کریں، کاپی پر encryption فعال کرتے ہوئے
3. encrypt شدہ snapshot سے ایک نیا encrypt شدہ EBS volume بنائیں
4. instance روکیں
5. پرانا غیر encrypt شدہ volume علیحدہ کریں
6. نیا encrypt شدہ volume منسلک کریں
7. instance شروع کریں اور تصدیق کریں کہ سب کچھ کام کرتا ہے

اس عمل کا ایک downtime window ہے — stop، detach، attach، start کا سلسلہ۔ Nimbus کے لیے، ایک چھوٹے ڈیٹابیس کے ساتھ، window تقریباً پندرہ منٹ کا تھا۔ سینکڑوں GB والے ایک بڑے production ڈیٹابیس کے لیے، snapshot اور کاپی کا عمل زیادہ وقت لے سکتا ہے، حالانکہ اصل instance downtime پھر بھی صرف stop/start cycle ہے۔

"ہم بس ایک switch کیوں نہیں دبا سکتے؟" Leo نے پوچھا۔

"کیونکہ ڈسک پر موجود ڈیٹا غیر encrypt شدہ bytes ہے،" Priya نے کہا۔ "AWS انہیں ہر block پڑھے اور دوبارہ لکھے بغیر دوبارہ encrypt نہیں کر سکتا — جو بالکل وہی ہے جو snapshot کاپی کا عمل کرتا ہے۔ یہ source snapshot سے ہر block پڑھتا ہے، ہر ایک کو encrypt کرتا ہے، اور اسے نئے snapshot میں لکھتا ہے۔"

Leo عمل سے گزرا۔ نیا encrypt شدہ volume منسلک ہوا۔ instance واپس آن لائن آیا۔ ڈیٹابیس ایک encrypt شدہ volume پر چل رہا تھا۔

"نئے EBS volumes ڈیفالٹ طور پر encrypt شدہ بنائے جا سکتے ہیں،" Priya نے کہا۔ "ایک اکاؤنٹ-سطح کی سیٹنگ ہے۔ ہر نیا volume خودکار طور پر encrypt ہوتا ہے۔ ہمیں یہ پہلے دن فعال کر دینا چاہیے تھا۔"

اس نے اسے فعال کیا۔ اس نقطے سے آگے، Nimbus AWS اکاؤنٹ میں بنایا گیا ہر EBS volume ڈیفالٹ طور پر encrypt تھا — کوئی اضافی اقدامات درکار نہیں۔

**EFS: مشترکہ فائلنگ کیبنٹ**

EBS ایک instance سے منسلک ایک ڈسک ہے۔ کیا ہو اگر متعدد instances کو بیک وقت ایک ہی فائلوں تک رسائی کی ضرورت ہو؟

آپ کو ایک ایسی چیز چاہیے جیسے دفتر کے مرکز میں فائلنگ کیبنٹ — کوئی بھی چل کر آ سکتا ہے، ایک فائل نکال سکتا ہے، اسے واپس رکھ سکتا ہے، اور اگلا شخص تبدیلی فوراً دیکھ لیتا ہے۔ متعدد لوگ، بیک وقت، ایک ہی اسٹوریج تک رسائی کرتے ہوئے۔

AWS اسے **EFS** کہتا ہے: Elastic File System۔

EFS ایک managed نیٹ ورک فائل سسٹم ہے۔ متعدد EC2 instances ایک ہی وقت میں ایک ہی EFS فائل سسٹم mount کر سکتی ہیں اور shared فائلوں کو پڑھ/لکھ سکتی ہیں۔ یہ وہ اہم صلاحیت ہے جو EBS فراہم نہیں کرتا۔

سادہ الفاظ میں:

EBS ایک بیرونی ہارڈ ڈرائیو ہے جو ایک لیپ ٹاپ میں لگی ہے۔ ایک وقت میں صرف وہی لیپ ٹاپ اسے استعمال کر سکتا ہے۔

EFS دفتر کے مرکز میں فائلنگ کیبنٹ ہے۔ کوئی بھی ٹیم رکن چل کر آ سکتا ہے، ایک دراز کھول سکتا ہے، ایک فائل پڑھ سکتا ہے، کچھ واپس رکھ سکتا ہے۔

**آپ کو EFS کب چاہیے؟**

- جب متعدد EC2 instances کو فائلیں شیئر کرنی ہوں — content management systems، shared
  کنفیگریشن فائلیں، shared میڈیا لائبریریاں
- جب آپ کے پاس ایک افقی طور پر اسکیل کی گئی ایپلیکیشن ہو جہاں تمام instances کو
  ایک ہی ڈیٹا تک رسائی چاہیے
- جب آپ کو ایک مستقل فائل سسٹم چاہیے جو instance کی ناکامیوں سے بچے

EFS کو NFS protocol (خاص طور پر NFSv4) کا استعمال کرتے ہوئے نیٹ ورک پر رسائی کیا جاتا ہے۔ کوئی بھی EC2 instance جس کے پاس EFS mount target تک نیٹ ورک کنیکٹیویٹی ہو اسے mount کر سکتی ہے — بشمول ایک ہی Region کے اندر مختلف AZs میں instances۔ آپ ہر AZ میں mount targets کنفیگر کرتے ہیں، اور instances بہترین کارکردگی کے لیے قریب ترین mount target سے جڑتی ہیں۔

عملی مفہوم: EFS باکس سے باہر AZs میں کام کرتا ہے۔ اگر آپ کے پاس `us-west-2a` اور `us-west-2b` میں web servers ہوں جو دونوں ایک ہی EFS فائل سسٹم mount کرتے ہوں، تو `2a` میں ایک سرور کی لکھی گئی فائل `2b` میں ایک سرور کو فوراً نظر آتی ہے۔ یہ shared فائل سسٹم برتاؤ ہے جو EBS فراہم نہیں کر سکتا۔

**EFS Performance Modes**

EFS کے دو throughput modes ہیں جو sizing کے لیے اہم ہیں:

**Elastic Throughput** (زیادہ تر نئے فائل سسٹمز کے لیے ڈیفالٹ): EFS اصل استعمال کی بنیاد پر throughput کو خودکار طور پر اوپر اور نیچے اسکیل کرتا ہے۔ آپ throughput کی سطح provision نہیں کرتے۔ آپ وہی ادا کرتے ہیں جو آپ استعمال کرتے ہیں۔ یہ متغیر workloads کے لیے صحیح mode ہے جہاں throughput کی ضروریات اتار چڑھاؤ کرتی ہیں — جیسے Nimbus، جہاں پیر کی صبح کی ٹریفک جمعے کی شام سے مختلف ہوتی ہے۔

**Provisioned Throughput**: آپ محفوظ شدہ ڈیٹا سے قطع نظر throughput کی سطح بتاتے ہیں۔ مفید جب آپ کے workload کو مستقل طور پر اعلیٰ throughput چاہیے جو اس سے زیادہ ہو جو محفوظ ڈیٹا حجم Elastic mode میں فراہم کرتا۔ اگر آپ ایک build system چلا رہے ہیں جو فی منٹ دسیوں gigabytes پڑھتا ہے چاہے کتنا بھی محفوظ ہو، تو Provisioned Throughput مناسب ہے۔

ایک تیسرا mode بھی ہے، **Bursting Throughput**، جو اصل EFS برتاؤ ہے اور Elastic دستیاب ہونے سے پہلے بنائے گئے فائل سسٹمز کے لیے ابھی بھی ڈیفالٹ ہے۔ Bursting mode میں، throughput اس بات کے ساتھ اسکیل کرتا ہے کہ آپ کتنا ڈیٹا محفوظ کرتے ہیں: آپ کو فی GB 50 KB/s کی ایک بنیادی لکیر ملتی ہے، نیز burst credits جو اس وقت جمع ہوتے ہیں جب آپ بنیادی لکیر سے نیچے ہوں اور تب خرچ کیے جا سکتے ہیں جب آپ کو زیادہ throughput چاہیے ہو (چھوٹے فائل سسٹمز کے لیے 100 MB/s تک، یا بڑے کے لیے بنیادی لکیر کے ایک ضرب تک)۔ یہ غیر متوقع یا spiky رسائی کے نمونوں والے workloads کے لیے صحیح انتخاب ہے جہاں فائل سسٹم اتنا بڑا ہو کہ معنی خیز burst credits کمائے۔ اگر آپ کا فائل سسٹم چھوٹا ہے اور آپ کا رسائی نمونہ bursty ہے، تو آپ اپنے credits جلدی ختم کر سکتے ہیں — اپنی پوزیشن جاننے کے لیے `BurstCreditBalance` CloudWatch میٹرک دیکھیں۔

Tom کا سوال فوری تھا: "کیا Elastic زیادہ مہنگا ہے؟"

"یہ استعمال کے نمونے پر منحصر ہے،" Leo نے کہا۔ "Elastic کے ساتھ، آپ اس throughput کے لیے ادا کرتے ہیں جو آپ دراصل استعمال کرتے ہیں۔ Provisioned کے ساتھ، آپ اس throughput کے لیے ادا کرتے ہیں جو آپ نے بتایا ہے چاہے آپ اسے استعمال نہ کر رہے ہوں۔"

"تو متغیر workloads کے لیے، Elastic عام طور پر سستا ہے،" Tom نے کہا۔

"عام طور پر،" Priya نے کہا۔ "فیصلہ کرنے سے پہلے CloudWatch میں اپنے اصل throughput نمونے چیک کریں۔"

EFS کے دو performance modes بھی ہیں: **General Purpose** (کم latency، زیادہ تر workloads کے لیے موزوں، ڈیفالٹ) اور **Max I/O** (تھوڑی زیادہ latency کی قیمت پر انتہائی parallelized workloads کے لیے زیادہ throughput)۔ General Purpose استعمال کے بہت بڑے حصے کو سنبھالتا ہے۔ Max I/O ان ایپلیکیشنز کے لیے ڈیزائن کیا گیا جنہیں ہزاروں بیک وقت فائل سسٹم آپریشنز کرنے کی ضرورت ہو — بڑے پیمانے پر میڈیا پروسیسنگ pipelines، بہت سے parallel readers والے scientific computing workflows۔

**EFS بمقابلہ S3:** EFS ایک فائل سسٹم ہے (folders، فائلیں، اجازتیں، locking)۔ S3 object اسٹوریج ہے (اپ لوڈ، ڈاؤن لوڈ، کوئی فائل سسٹم semantics نہیں)۔ EFS، S3 سے بہت زیادہ مہنگا ہے — EFS Standard کے لیے تقریباً $0.30 فی GB فی ماہ بمقابلہ S3 Standard کے لیے $0.023 فی GB فی ماہ۔ ان فائلوں کے لیے S3 استعمال کریں جو پوری محفوظ اور حاصل کی جاتی ہیں۔ ان فائلوں کے لیے EFS استعمال کریں جنہیں ایپلیکیشنز معیاری فائل سسٹم آپریشنز کے ذریعے فعال طور پر پڑھتی اور لکھتی ہیں۔

**اگر EBS تو ایک instance، لیکن اگر EFS تو بہت سی**

EBS/EFS فیصلہ ایک سوال پر آتا ہے: کتنی instances کو بیک وقت اس اسٹوریج تک رسائی کی ضرورت ہے؟

اگر آپ EBS پر ایک افقی طور پر اسکیل کی گئی ایپلیکیشن بناتے ہیں، تو ہر instance کی اپنی ڈسک ہوتی ہے — لیکن جب کوئی صارف instance A پر فائل اپ لوڈ کرتا ہے، تو instance B اسے نہیں دیکھ سکتا۔ یہ ڈیٹابیسز کے لیے ٹھیک ہے (ہر DB کی اپنی ڈسک ہوتی ہے)، لیکن shared مواد کے لیے ٹوٹا ہوا۔ اگر آپ کو shared رسائی چاہیے، تو EFS جواب ہے — لیکن EFS، S3 سے فی GB زیادہ پڑتا ہے، اور random I/O کے لیے EBS سے زیادہ latency رکھتا ہے۔ صحیح انتخاب مکمل طور پر اس پر منحصر ہے کہ آپ کی ایپلیکیشن ڈیٹا کے ساتھ کیا کرتی ہے۔

**صحیح اسٹوریج چننا**

اب تک آپ نے AWS میں تین قسم کی اسٹوریج دیکھی ہے۔ آئیے فیصلے کو واضح کریں۔

| ضرورت                                   | اسٹوریج کی قسم    |
|---------------------------------------|------------------|
| ڈیٹابیس کو مستقل، تیز ڈسک چاہیے        | EBS (gp3 یا io2) |
| متعدد سرورز کو shared فائلیں چاہئیں     | EFS              |
| فائلیں، بیک اپس، images، بڑے objects     | S3               |
| عارضی computation scratch جگہ            | Instance Store   |
| کم سے کم لاگت پر طویل مدتی آرکائیوز    | S3 Glacier       |

آپ سوچ رہے ہوں گے: اگر EFS متعدد instances کو فائلیں شیئر کرنے دیتا ہے، تو اسے ہر چیز کے لیے کیوں نہ استعمال کریں؟ کیونکہ EFS، S3 سے فی GB نمایاں طور پر زیادہ پڑتا ہے، اور random I/O کے لیے مقامی EBS سے زیادہ latency رکھتا ہے۔ یہ shared فائل سسٹم رسائی کے لیے صحیح اوزار ہے — عام فائل اسٹوریج یا ڈیٹابیس اسٹوریج کے لیے نہیں۔

یہ فیصلہ صحیح کرنا اہم ہے۔ جہاں آپ کو EFS چاہیے وہاں S3 استعمال کرنا آپریشنل پیچیدگی بڑھاتا ہے۔ جہاں آپ کو EFS چاہیے وہاں EBS استعمال کرنا اسکیل کرتے وقت ناکامیاں پیدا کرتا ہے۔ جہاں آپ کو استقلال چاہیے وہاں instance store استعمال کرنا ڈیٹا کھو دیتا ہے۔

Priya نے یہ جدول پرنٹ کر کے دیوار پر لگا دی۔

"ہر بار جب ہم کوئی اسٹوریج کی ضرورت شامل کریں،" اس نے کہا، "ہم یہاں سے شروع کرتے ہیں۔"

آئیے فیصلے کو ٹھوس بنانے کے لیے چند حقیقی منظر ناموں سے گزریں:

**منظر نامہ A**: ایک مشین لرننگ training کا کام ایک GPU EC2 instance پر چلتا ہے اور اسے ایک 200GB dataset پڑھنے کی ضرورت ہے۔ کام دن میں ایک بار چلتا ہے اور دو گھنٹے لیتا ہے۔ dataset متعدد تحقیقی ٹیمیں شیئر کرتی ہیں۔

فیصلہ: S3۔ dataset بڑا ہے، فی-کام-ایک-بار-پڑھا جاتا ہے، اور shared ہے۔ S3 سستا، پائیدار، اور کسی بھی EC2 instance یا کسی بھی ٹیم کے اکاؤنٹ سے قابلِ رسائی ہے۔ GPU instance اسے S3 API کے ذریعے پڑھتی ہے۔ یہاں کسی فائل سسٹم کی ضرورت نہیں۔

**منظر نامہ B**: ایک WordPress سائٹ ایک load balancer کے پیچھے چار EC2 instances پر چلتی ہے۔ WordPress plugin فائلیں، theme فائلیں، اور صارف اپ لوڈز کو سرور پر ایک directory میں محفوظ کرتا ہے۔ تمام چار instances کو ایک ہی فائلیں پڑھنی اور لکھنی ہیں۔

فیصلہ: EFS۔ WordPress فائل سسٹم semantics استعمال کرتا ہے — یہ directories بناتا ہے، فائلیں لکھتا ہے، راستے سے فائلیں پڑھتا ہے۔ S3 کو WordPress plugin ماحولیاتی نظام کو دوبارہ لکھنے کی ضرورت ہوگی۔ EFS ایک معیاری NFS فائل سسٹم کے طور پر mount ہوتا ہے، جس کے ساتھ WordPress مقامی طور پر کام کرتا ہے۔

**منظر نامہ C**: ایک PostgreSQL ڈیٹابیس ایک EC2 instance پر چلتا ہے۔ اسے query execution اور index lookups کے لیے تیز random I/O چاہیے۔

فیصلہ: EBS (gp3 یا io2)۔ ڈیٹابیسز کو چھوٹی، random reads اور writes کے لیے کم latency کے ساتھ block اسٹوریج چاہیے۔ S3 بہت سست ہے اور فائل سسٹم semantics سپورٹ نہیں کرتا۔ EFS، random I/O کے لیے EBS سے زیادہ latency رکھتا ہے۔

پیٹرن: فائلوں کے لیے ڈیفالٹ S3 ہے۔ EBS تب شامل کریں جب آپ کو کسی مخصوص instance کے لیے block اسٹوریج چاہیے۔ EFS تب شامل کریں جب متعدد instances کو ایک فائل سسٹم شیئر کرنا ہو۔ instance store صرف عارضی scratch جگہ کے لیے۔

## جب EFS کافی نہ ہو: Amazon FSx

اگلا اسٹوریج سبق کسی آؤٹیج یا وائٹ بورڈ بحث کے طور پر نہیں آیا۔ یہ ایک sales معاہدے کے طور پر آیا — اس قسم کا جس کا Maya portal لانچ ہونے سے پیچھا کر رہی تھی، اس قسم کا جسے بند کرنے میں ایک پوری سہ ماہی کے demos اور follow-up کالز لگیں۔ ریستوران آپریٹر portal لانچ ہونے کے تین ماہ بعد، Nimbus نے اپنا پہلا multi-location کلائنٹ دستخط کیا: Copper Kettle، midwest بھر میں ایک درجن مقامات کا ایک خاندانی گروپ۔ Maya نے ڈیل چلائی تھی۔ Tom نے مالی ماڈل بنایا تھا۔ Leo نے سیاہی خشک ہونے سے پہلے تکنیکی انضمام کی منصوبہ بندی شروع کر دی تھی۔

پھر اس نے Copper Kettle کی IT ٹیم کے infrastructure نوٹس پڑھے۔

"ان کے فائل سرور Windows ہیں،" اس نے کہا۔ "سب کچھ Windows ہے۔ ان کا کچن مینجمنٹ سافٹ ویئر، ان کا HR سسٹم، ان کا scheduling اوزار — یہ سب کچھ Windows فائل سرورز پر shared drives میں لکھتا ہے۔ SMB protocol۔ Active Directory authentication۔"

"کیا ہم انہیں EFS پر منتقل کر سکتے ہیں؟" Maya نے پوچھا۔

Leo نے سر ہلایا۔ "EFS، NFS استعمال کرتا ہے۔ ان کی ایپلیکیشنز SMB بولتی ہیں۔ یہ مختلف protocols ہیں۔ Copper Kettle سافٹ ویئر نہیں جانتا کہ NFS کیا ہے۔ آپ اسے بس ایک EFS mount کی طرف اشارہ نہیں کر سکتے۔"

"تو ہم EFS استعمال نہیں کر سکتے۔"

"اس کے لیے نہیں۔ ایک مختلف سروس ہے۔"

**FSx for Windows File Server: EFS، لیکن Windows کے لیے**

**Amazon FSx for Windows File Server** ایک مکمل managed، Windows-مقامی shared فائل سسٹم ہے۔ یہ SMB (Server Message Block) protocol سپورٹ کرتا ہے — وہی protocol جسے Windows سرورز، Windows ایپلیکیشنز، اور on-premises Windows فائل shares دہائیوں سے استعمال کر رہے ہیں۔ یہ Active Directory کے ساتھ ضم ہوتا ہے، Windows ACLs (فائل-سطح کی اجازتیں) سپورٹ کرتا ہے، اور وہ Windows-مخصوص خصوصیات سپورٹ کرتا ہے جن پر Windows ایپلیکیشنز دراصل انحصار کرتی ہیں۔

اسے EFS کے طور پر سوچیں، لیکن Windows کے لیے — ان تمام Windows-مخصوص خصوصیات کے ساتھ جو آپ کا Active Directory ماحول پہلے ہی توقع کرتا ہے۔ Copper Kettle کچن مینجمنٹ سافٹ ویئر اس سے بالکل ویسے جڑتا جیسے یہ on-premises فائل سرورز سے جڑا تھا۔ ایپلیکیشن نہیں بدلتی۔ protocol نہیں بدلتا۔ ڈیٹا بس Chicago میں کہیں ایک تہہ خانے میں ایک سرور کے بجائے ایک managed AWS سروس پر رہتا ہے۔

Copper Kettle کی منتقلی کے لیے: Leo نے ایک FSx for Windows File Server فائل سسٹم provision کیا، اسے Copper Kettle Active Directory سے جوڑا (AWS Managed Microsoft AD کے ذریعے AWS تک بڑھایا گیا)، اور موجودہ drive letters کو map کیا۔ کچن سافٹ ویئر نے اپنی فائل shares بالکل وہیں پائیں جہاں اس نے توقع کی تھی۔

"یہ ماہانہ کتنا پڑتا ہے؟" Tom نے پوچھا۔

Leo پہلے ہی دیکھ چکا تھا۔ FSx for Windows فی GB اسٹوریج فی ماہ قیمت لگاتا ہے — EFS سے زیادہ مہنگا، S3 سے نمایاں طور پر زیادہ، لیکن ایک درجن مقامات پر Windows فائل سرورز برقرار رکھنے سے کہیں سستا۔ Tom نے عدد بغیر اعتراض لکھ لیا۔

**FSx for Lustre: جب آپ کے ML کام کو سینکڑوں GPUs کھلانے ہوں**

اسی دوران، Leo نے ساتھ ساتھ ایک recommendation engine کا prototype بنانا شروع کر دیا تھا — یہ پیش گوئی کرتے ہوئے کہ کوئی گاہک ماضی کے برتاؤ اور ملتے جلتے گاہکوں کے آرڈرز کی بنیاد پر کون سے پکوان آرڈر کرنے کا امکان رکھتا ہے۔ training ڈیٹا ابھی چھوٹا تھا، لیکن تجربے نے اسے اس بات کی گہرائی میں بھیجا کہ سنجیدہ ML ٹیمیں اپنے ماڈلز کو کیسے کھلاتی ہیں: training کے کام جو ہر دوڑ پر S3 سے سینکڑوں gigabytes پڑھتے ہیں۔

"جو پیٹرن case studies میں بار بار آتا ہے،" اس نے اگلے ٹیم لنچ پر رپورٹ کیا، "وہ training کے کام ہیں جو I/O پر bottleneck ہیں۔ مہنگے GPUs 40% وقت بیکار بیٹھے، ڈیٹا کے اگلے batch کا انتظار کرتے ہوئے۔"

یہ shared فائل اسٹوریج سے ایک مختلف مسئلہ ہے۔ یہ ایک high-performance computing (HPC) مسئلہ ہے: جب آپ کے پاس سینکڑوں processing units ہوں جنہیں سب کو بیک وقت، بہت زیادہ throughput پر، ایک ہی dataset سے ڈیٹا پڑھنے کی ضرورت ہو۔

**Amazon FSx for Lustre** Lustre parallel فائل سسٹم کا ایک مکمل managed نفاذ ہے۔ Lustre بالکل اسی منظر نامے کے لیے خاص طور پر بنایا گیا ہے — انتہائی زیادہ throughput پر، بہت سے بیک وقت clients میں parallel reads۔ یہ S3 کے ساتھ مقامی طور پر ضم ہوتا ہے: آپ FSx for Lustre کو ایک S3 bucket کی طرف اشارہ کرتے ہیں، اور یہ خودکار طور پر اس ڈیٹا کو Lustre فائل سسٹم کے ذریعے دستیاب کرتا ہے۔ training کا کام ایک مقامی mount point سے پڑھتا ہے؛ FSx پسِ پردہ S3 سے ڈیٹا stream کرتا ہے۔

جب آپ کے ML training کام کو بیک وقت سینکڑوں GPUs کو ڈیٹا کھلانے کی ضرورت ہو، تو FSx for Lustre اوزار ہے۔ یہی مالیاتی modeling، genomics workloads، اور video rendering پر لاگو ہوتا ہے — کوئی بھی workload جہاں bottleneck اسٹوریج کی صلاحیت کے بجائے parallel I/O throughput ہو۔

Leo نے جو case study bookmark کی تھی اس نے کہانی دو اعداد میں بتائی: training کام کو FSx for Lustre میں منتقل کرنے کے بعد، GPU استعمال 60% سے 94% تک چڑھ گیا، اور وہ training دوڑ جو چھ گھنٹے لیتی تھی ساڑھے تین گھنٹوں میں مکمل ہو گئی۔ Nimbus کو لمبے عرصے تک اس قسم کی طاقت کی ضرورت نہ ہوگی — لیکن Leo نے پیٹرن اس دن کے لیے فائل کر لیا جب recommendation engine بڑا ہو جائے۔

**دیگر FSx اختیارات**

AWS **FSx for NetApp ONTAP** بھی پیش کرتا ہے — ان اداروں کے لیے جو پہلے ہی on-premises NetApp اسٹوریج چلاتے ہیں اور multi-protocol رسائی (ایک ہی فائل سسٹم سے NFS، SMB، اور iSCSI) چاہتے ہیں — اور **FSx for OpenZFS**، ان workloads کے لیے جنہیں فائل سسٹم سطح پر snapshots اور clones جیسی ZFS-مخصوص خصوصیات چاہئیں۔ دونوں ان تنظیموں کے لیے خصوصی اوزار ہیں جن کے پاس مخصوص موجودہ infrastructure یا ضروریات ہیں۔

زیادہ تر ٹیموں کے لیے، فیصلہ چار FSx variants اور EFS کے درمیان ہوتا ہے۔ سوال ہمیشہ ایک ہی ہوتا ہے: workload کون سا protocol بولتا ہے، اور اسے کن کارکردگی خصوصیات کی ضرورت ہے؟

>
> *SAA-C03 ڈومین: Design High-Performing Architectures (ڈومین 3، ٹاسک 3.1)*
>
> - **FSx for Windows = SMB + Active Directory + Windows workloads**۔ امتحان کے اشارے: "Windows file server"، "SMB protocol"، "Active Directory integration"، "lift-and-shift Windows applications"۔ جب آپ ان میں سے کوئی جملہ دیکھیں، تو FSx for Windows جواب ہے۔

> - **EFS کسی کا متبادل نہیں ہے۔** EFS، Linux workloads کے لیے NFS ہے۔ یہ SMB نہیں بولتا۔ یہ ایک parallel high-performance فائل سسٹم نہیں ہے۔ جہاں FSx چاہیے وہاں EFS استعمال کرنے کا مطلب ہے کہ ایپلیکیشن کام نہیں کرتی (Windows) یا I/O-bottleneck ہوتی ہے (HPC)۔
> - **FSx for NetApp ONTAP اور FSx for OpenZFS** کم ظاہر ہوتے ہیں، لیکن اشارے مخصوص ہیں۔ "موجودہ NetApp/ONTAP اسٹوریج منتقل کریں"، "multi-protocol رسائی (NFS + SMB + iSCSI)"، یا "SnapMirror" → FSx for NetApp ONTAP۔ "ZFS"، "instant snapshots/clones کے ساتھ NFS"، یا "on-premises ZFS فائل سرور منتقل کریں" → FSx for OpenZFS۔
> - فوری حوالہ: "SMB یا Windows file server" → FSx for Windows۔ "Machine learning training یا high-performance computing" → FSx for Lustre۔ "NetApp/multi-protocol" → FSx for ONTAP۔ "ZFS" → FSx for OpenZFS۔

## کلاؤڈ تک کا پل: AWS Storage Gateway

Nimbus کا اب تک کا سب سے بڑا امکانی گاہک — Meridian Kitchen نامی ایک علاقائی چین، تین ریاستوں میں بیس مقامات — ایک ایسے مسئلے کے ساتھ آیا جسے `aws s3 cp` سے حل نہیں کیا جا سکتا تھا۔

Meridian کے پاس برسوں کا آپریشنل ڈیٹا on-premises فائل سرورز پر رہتا تھا۔ recipes، invoices، کچن کی video فوٹیج، supplier معاہدے۔ چند gigabytes نہیں۔ Terabytes۔ اور وہ سافٹ ویئر جو یہ ڈیٹا پیدا اور استعمال کرتا تھا — ان کا کچن مینجمنٹ سسٹم، ان کا invoicing platform، ان کے HR اوزار — یہ سب کچھ NFS یا SMB استعمال کرتے ہوئے مقامی فائل shares میں لکھتا تھا۔ ان ایپلیکیشنز کو دوبارہ لکھنا ممکن نہیں تھا۔ سارا ڈیٹا راتوں رات منتقل کرنا بھی ممکن نہیں تھا۔

"تو ہم ان کا ڈیٹا AWS میں کیسے لانا شروع کریں،" Maya نے پوچھا، "ان سے ایک بھی ایپلیکیشن بدلنے کا کہے بغیر؟"

"بالکل اسی کے لیے ایک سروس ہے،" Priya نے کہا۔ "یہ ان کے ڈیٹا سینٹر میں ایک VM کے طور پر چلتی ہے، ان کے موجودہ سافٹ ویئر کو ایک عام فائل سرور یا اسٹوریج آلے کی طرح نظر آتی ہے، اور خاموشی سے پسِ پردہ سب کچھ AWS میں محفوظ کرتی ہے۔"

وہ سروس **AWS Storage Gateway** ہے: ایک hybrid اسٹوریج سروس جو on-premises ماحول کو AWS اسٹوریج سے جوڑتی ہے۔ یہ آپ کی ایپلیکیشنز کو اسٹوریج ان protocols کا استعمال کرتے ہوئے پیش کرتی ہے جو وہ پہلے ہی سمجھتی ہیں، جبکہ دراصل ڈیٹا کو S3، S3 Glacier، یا EBS snapshots کے طور پر محفوظ کرتی ہے۔

تین gateway اقسام ہیں، ہر ایک ایک مختلف on-premises مسئلہ حل کرتی ہے۔

**File Gateway** on-premises ایپلیکیشنز کو ایک NFS یا SMB interface پیش کرتا ہے۔ gateway میں لکھی گئی فائلیں S3 میں objects کے طور پر محفوظ ہوتی ہیں — لیکن ایپلیکیشن یہ نہیں جانتی۔ یہ ایک فائل سسٹم دیکھتی ہے۔ کثرت سے رسائی کی جانے والی فائلیں کم-latency reads کے لیے مقامی طور پر cache ہوتی ہیں؛ باقی S3 میں رہتی ہیں۔ یہی Meridian کو چاہیے تھا: کچن مینجمنٹ سافٹ ویئر ایک ایسی چیز میں لکھتا ہے جو فائل share کی طرح نظر آتی ہے، اور ڈیٹا S3 میں ختم ہوتا ہے جہاں Nimbus اس کا تجزیہ کر سکتا ہے، اسے بیک اپ کر سکتا ہے، اور اسے تلاش کر سکتا ہے۔

"ٹھہریں — لیکن ہم ایسا *کیوں* کریں گے؟" Maya نے پوچھا۔ "سافٹ ویئر کو بس براہِ راست S3 کی طرف کیوں نہ اشارہ کریں؟"

کیونکہ NFS اور SMB، S3 نہیں ہیں۔ کچن سافٹ ویئر S3 کی API نہیں بولتا۔ یہ فائل راستے کھولتا ہے۔ یہ ایک directory میں bytes لکھتا ہے۔ File Gateway اسے S3 object آپریشنز میں ترجمہ کرتا ہے ایپلیکیشن کو کچھ بدلنے کا پتہ چلے بغیر۔

**Volume Gateway** on-premises سرورز کو iSCSI block اسٹوریج volumes پیش کرتا ہے — وہی interface جو ایک جسمانی ہارڈ ڈرائیو یا SAN آلہ پیش کرے گا۔ اس کے دو modes ہیں: *stored volumes* بنیادی ڈیٹا on-premises رکھتے ہیں اور S3 میں EBS snapshots کے طور پر asynchronous بیک اپس کرتے ہیں (ان on-premises-پہلے workloads کے لیے جو کلاؤڈ بیک اپ بھی چاہتے ہیں)، اور *cached volumes* بنیادی ڈیٹا S3 میں رکھتے ہیں اور کثرت سے رسائی کی جانے والی ڈیٹا on-premises cache رکھتے ہیں (ان تنظیموں کے لیے جو S3 کو بنیادی اسٹوریج کے طور پر برتنے کے لیے تیار ہیں)۔

**Tape Gateway** Veeam، Veritas، یا NetBackup جیسے بیک اپ سافٹ ویئر کو ایک ورچوئل tape library (VTL) پیش کرتا ہے۔ بیک اپ سافٹ ویئر ایک ایسی چیز میں لکھتا ہے جو جسمانی tape cartridges کی طرح نظر آتی ہے۔ وہ ورچوئل tapes S3 میں محفوظ ہوتی ہیں اور S3 Glacier میں archive کی جا سکتی ہیں۔ بیک اپ سافٹ ویئر نہیں بدلتا۔ جسمانی tape robots اور shelves ختم ہو جاتے ہیں۔

"Meridian کی بیک اپ ٹیم Veeam چلاتی ہے،" Leo نے کہا۔ "ان کے پاس اصل جسمانی tapes ہیں۔ Off-site اسٹوریج، rotation شیڈولز، پوری چیز۔"

"Tape Gateway جسمانی tapes کی جگہ لے لیتا ہے،" Priya نے کہا۔ "وہی Veeam کنفیگریشن۔ وہی بیک اپ کام۔ tapes بس ایک rack کے بجائے S3 میں رہتی ہیں۔"

Tom نے off-site tape اسٹوریج کی لاگت دیکھی۔ اس نے وہ ٹیب بغیر تبصرے کے بند کر دیا اور منتقلی کے منصوبے کی منظوری دے دی۔

> **Exam Tip — AWS Storage Gateway**
>
> *SAA-C03 ڈومین: Design High-Performing Architectures (ڈومین 3)*
>
> - **File Gateway = NFS/SMB → S3۔** on-premises ایپلیکیشنز کی لکھی گئی فائلیں S3 objects بن جاتی ہیں۔ کثرت سے رسائی کی جانے والی فائلیں مقامی طور پر cache ہوتی ہیں۔ امتحانی trigger: "on-premises ایپلیکیشن کو بغیر کوڈ تبدیلیوں کے فائلیں S3 میں محفوظ کرنی ہیں۔"
> - **Volume Gateway = iSCSI block اسٹوریج → S3 snapshots۔** Stored mode: بنیادی ڈیٹا on-premises، S3 میں EBS snapshots کے طور پر بیک اپ۔ Cached mode: بنیادی ڈیٹا S3 میں، کثرت سے رسائی کی جانے والی blocks مقامی طور پر cache۔ امتحانی trigger: "on-premises سرور کو کلاؤڈ-backed block اسٹوریج چاہیے۔"
> - **Tape Gateway = VTL → S3/Glacier۔** بیک اپ سافٹ ویئر ورچوئل tapes میں لکھتا ہے؛ tapes S3 میں محفوظ یا Glacier میں archive ہوتی ہیں۔ امتحانی trigger: "بیک اپ سافٹ ویئر بدلے بغیر جسمانی tape بیک اپ infrastructure کی جگہ لیں۔"
> - **اہم امتحانی پیٹرن:** "on-premises ایپلیکیشن کو بغیر کوڈ تبدیلیوں کے کلاؤڈ اسٹوریج چاہیے" → Storage Gateway۔ "tape بیک اپ کی جگہ لیں" → خاص طور پر Tape Gateway۔

## طاقتیں اور حدود

**EBS کی طاقتیں**:

- EC2 کے لیے مستقل، تیز block اسٹوریج
- مخصوص-وقت کے بیک اپ اور ریکوری کے لیے snapshots
- مختلف workloads کے لیے متعدد کارکردگی درجے
- Encryption at rest مقامی طور پر سپورٹ — ڈیفالٹ طور پر اکاؤنٹ-سطح کی encryption فعال کریں

**EBS کی حدود**:

- ایک وقت میں ایک instance سے منسلک (معمولی استثنا کے ساتھ)
- EC2 instance کے ساتھ ایک ہی AZ میں (کسی اور AZ میں کاپی کرنے کے لیے ایک snapshot درکار ہے)
- آپ provision شدہ اسٹوریج کے لیے ادائیگی کرتے ہیں، نہ صرف اس کے لیے جو آپ استعمال کرتے ہیں
- ایک موجودہ غیر encrypt شدہ volume کو encrypt کرنے کے لیے ایک maintenance window کے ساتھ snapshot-copy-restore cycle درکار ہے

**EFS کی طاقتیں**:

- Multi-instance shared فائل سسٹم — مقامی NFS protocol
- خودکار طور پر اسکیل کرتا ہے، آپ صلاحیت provision نہیں کرتے
- ایک Region کے اندر AZs میں قابلِ رسائی
- Elastic Throughput mode خودکار طور پر workload کے مطابق ایڈجسٹ ہوتا ہے

**EFS کی حدود**:

- فی GB S3 سے زیادہ مہنگا
- random I/O کے لیے EBS سے زیادہ latency
- تمام Regions میں دستیاب نہیں

## بڑے پیمانے پر ڈیٹا منتقل کرنا: DataSync اور Snow Family

Storage Gateway on-premises ایپلیکیشنز کو کلاؤڈ اسٹوریج سے *مسلسل جڑا* رکھتا ہے۔ لیکن دو دیگر منتقلی منظر نامے امتحان پر مسلسل ظاہر ہوتے ہیں — اور بالآخر حقیقی منصوبوں میں:

**AWS DataSync** *online bulk منتقلی* کے لیے ہے: on-premises NFS/SMB فائل سرورز (یا دیگر clouds) اور S3، EFS، یا FSx کے درمیان بڑے datasets نیٹ ورک پر منتقل کرنا — ایک بار، یا ایک شیڈول پر۔ یہ parallelization، integrity verification، retries، اور bandwidth throttling سنبھالتا ہے، اور یہ ہاتھ سے بنائے گئے rsync-طرز کے scripts سے تقریباً 10 گنا تیز ہے۔ امتحانی trigger: "on-premises NFS سرور سے Amazon EFS/S3 میں لاکھوں فائلیں منتقل/منتقل کریں" → DataSync۔ (اسے Storage Gateway سے نہ ملائیں، جو *جاری hybrid رسائی* کے لیے ہے، یا DMS سے، جو *ڈیٹابیسز* منتقل کرتا ہے۔)

**AWS Snow Family** اس وقت کے لیے ہے جب نیٹ ورک bottleneck ہو۔ 100 TB کو 100 Mbps لائن پر منتقل کرنے میں تین ماہ سے زیادہ لگتے ہیں؛ ایک ٹرک تیز ہے۔ **Snowball Edge** ایک مضبوط آلہ ہے جسے AWS آپ کو بھیجتا ہے — مقامی طور پر تقریباً 80 TB تک لوڈ کریں، اسے واپس بھیجیں، AWS اسے S3 میں import کرتا ہے۔ **Snowcone** چھوٹا پورٹیبل ورژن تھا (تقریباً 8–14 TB) edge مقامات کے لیے — 2024 کے آخر میں بند کر دیا گیا، حالانکہ یہ پرانے امتحانی سوالات میں ابھی بھی ظاہر ہو سکتا ہے (باب 25 میں reality check دیکھیں)۔ امتحانی حساب کا trigger: جب سوال آپ کو ایک dataset کا سائز اور ایک پتلی یا ناقابلِ اعتماد لنک دے اور سب سے تیز/سب سے عملی منتقلی پوچھے، تو منتقلی کا وقت حساب کریں — اگر یہ ہفتوں یا مہینوں میں ہو، تو جواب Snow Family ہے۔

> **Exam Tip — AWS Backup**
>
> ایک اور سروس جو اس باب کو ایک ساتھ پروتی ہے: **AWS Backup** EBS، EFS، RDS، DynamoDB، FSx، اور Storage Gateway میں بیک اپس کو ایک واحد بیک اپ منصوبے کے ساتھ مرکزی اور خودکار کرتا ہے — شیڈولز، retention، cross-region اور cross-account کاپیاں، اور immutability کے لیے Backup Vault Lock۔ امتحانی trigger: "متعدد AWS سروسز/اکاؤنٹس میں بیک اپس کا مرکزی انتظام کریں" → AWS Backup، فی-سروس scripts نہیں۔


## خلاصہ

Tom کے سرخ قلم نے اصل مسئلہ دائرے میں گھیرا: ایک مشین پر بہت زیادہ۔ اسٹوریج کو EC2 instance سے ہٹانا صرف صلاحیت کے بارے میں نہیں ہے — یہ خدشات کو الگ کرنے کے بارے میں ہے تاکہ ہر پرت کو آزادانہ طور پر منظم، اسکیل، اور محفوظ کیا جا سکے۔ صحیح اسٹوریج کا انتخاب چار سوالوں پر منحصر ہے: اسٹوریج کس چیز کو چاہیے، کتنی چیزوں کو ایک وقت میں چاہیے، یہ کتنی دیر رہتا ہے، اور اس تک کیسے رسائی کی جاتی ہے؟ یہ چار سوال مستقل طور پر صحیح جواب کی طرف لے جاتے ہیں۔

- **EBS** (Elastic Block Store) ایک واحد EC2 instance کے لیے مستقل block اسٹوریج ہے۔ یہ instance کے رکنے سے بچ جاتا ہے اور بیک اپ کے لیے snapshot لیا جا سکتا ہے۔ عام workloads کے لیے gp3 استعمال کریں، زیادہ-IOPS ضروریات کے لیے io2۔ instance store عارضی اور تیز ہے لیکن instance terminate ہونے پر ختم ہو جاتا ہے۔
- **EFS** (Elastic File System) ایک shared نیٹ ورک فائل سسٹم ہے جسے متعدد instances بیک وقت mount کر سکتی ہیں۔ EFS ایک Region کے اندر AZs پر پھیلا ہوتا ہے؛ EBS ایک واحد AZ تک محدود ہے۔
- اسٹوریج کی قسم کو ضرورت سے ملائیں: واحد EC2 ڈیٹابیس → EBS؛ سرورز میں shared فائلیں → EFS؛ objects، میڈیا، بیک اپس → S3؛ آرکائیوز → S3 Glacier۔
- ایک موجودہ EBS volume کو encrypt کرنے کے لیے درکار ہے: snapshot → encrypted کاپی → نیا volume → تبدیلی۔ نئے volumes کے لیے اس سے بچنے کے لیے ڈیفالٹ طور پر اکاؤنٹ-سطح کی encryption فعال کریں۔
- **EBS "Delete on Termination"**: root volumes ڈیفالٹ طور پر instance terminate ہونے پر حذف ہوتے ہیں؛ ڈیٹا volumes ڈیفالٹ طور پر برقرار رہتے ہیں۔ instance lifecycle policies ڈیزائن کرتے وقت دونوں سیٹنگز کا جائزہ لیں۔

## Exam Tips

*SAA-C03 ڈومین 3 — ٹاسک 3.1 (storage solutions)*

- **EBS volumes ایک AZ میں رہتے ہیں۔** انہیں صرف ایک ہی AZ کی instance سے منسلک کیا جا سکتا ہے۔ کسی مختلف AZ میں EBS volume استعمال کرنے کے لیے، آپ ایک snapshot بناتے ہیں اور ہدف AZ میں restore کرتے ہیں۔
- **EBS snapshots incremental ہیں اور S3 میں محفوظ ہیں۔** پہلا snapshot مکمل ہے؛ بعد کے صرف تبدیلیاں محفوظ کرتے ہیں۔ آپ ڈیزاسٹر ریکوری کے لیے snapshots کو دیگر Regions میں کاپی کر سکتے ہیں۔
- **EFS کراس-AZ ہے۔** ایک ہی Region کے اندر مختلف AZs میں متعدد instances ایک ہی EFS فائل سسٹم mount کر سکتی ہیں۔ یہ EBS سے ایک اہم امتیاز ہے۔
- **جب کوئی امتحانی منظر نامہ کہے "shared content کے ساتھ ویب ایپلیکیشن" یا "ایک ہی فائلوں تک رسائی کرنے والی متعدد instances," تو EFS سوچیں۔** جب یہ "database storage" یا "ایک سرور کے لیے مستقل ڈسک" کہے، تو EBS سوچیں۔
- **Instance store ڈیٹا ایک reboot سے بچتا ہے لیکن ایک stop یا termination سے نہیں۔** ایک سوال ایسے ڈیٹا کو بیان کر سکتا ہے جو "instance روکنے کے بعد غائب ہو جاتا ہے" — یہ instance store ہے جو کام کر رہا ہے۔
- **gp3 بمقابلہ io2**: gp3 عام استعمال کے لیے ڈیفالٹ ہے؛ io2 ان workloads کے لیے ہے جنہیں ضمانت شدہ IOPS چاہیے (بڑے ڈیٹابیسز، mission-critical نظام)۔ "IOPS ضروریات" یا "مستقل کم-latency ڈیٹابیس کارکردگی" بیان کرنے والے امتحانی منظر نامے io2 کی طرف اشارہ کرتے ہیں۔
- **gp2 بمقابلہ gp3:** gp2 IOPS سائز سے جڑے ہیں (3 IOPS/GB، 5,334 GB پر زیادہ سے زیادہ 16,000 IOPS)؛ gp3 IOPS سائز سے آزاد ہیں (3,000 base، 2025 کے آخر سے 80,000 تک قابلِ کنفیگر — پرانا مواد، اور ممکنہ طور پر امتحان کا سوال bank، ابھی بھی پچھلی 16,000 کی حد فرض کرتا ہے)۔ امتحانی سوال کا پیٹرن: ایک workload کو اسٹوریج بڑھائے بغیر زیادہ IOPS چاہیے — جواب gp3 یا io2 ہے، gp2 نہیں۔
- **EBS کے لیے Encryption at rest**: آپ ایک موجودہ غیر encrypt شدہ volume کو اس کی جگہ encrypt نہیں کر سکتے — آپ کو snapshot لینا، encrypt شدہ کاپی کرنا، restore کرنا ہوگا۔ غلطی سے غیر encrypt شدہ volumes بنانے سے بچنے کے لیے اکاؤنٹ-سطح کی encryption ڈیفالٹس فعال کریں۔ Encryption KMS keys کا استعمال کرتے ہوئے AES-256 ہے۔
- **Fast Snapshot Restore** تازہ restore شدہ volumes پر کارکردگی کے جرمانے کو ختم کرتا ہے لیکن فی snapshot فی AZ پیسہ لیتا ہے۔ volumes کو "فوراً پوری کارکردگی پر" restore کرنے کے بارے میں امتحانی سوالات FSR کی طرف اشارہ کرتے ہیں۔
- **EFS performance modes**: General Purpose (کم latency، زیادہ تر workloads کے لیے موزوں) بمقابلہ Max I/O (انتہائی parallelized workloads کے لیے زیادہ throughput)۔
- **EFS throughput modes — تین اختیارات:** Bursting (throughput اسٹوریج سائز کے ساتھ اسکیل کرتا ہے، burst credits استعمال کرتا ہے — spiky workloads کے لیے اچھا)، Elastic (خودکار اسکیل، فی استعمال ادائیگی — غیر متوقع workloads کے لیے اچھا)، Provisioned (اسٹوریج سے قطع نظر مقررہ throughput — مستقل زیادہ-throughput ضروریات کے لیے اچھا)۔ امتحان جانچتا ہے کہ آیا آپ جانتے ہیں کہ throughput کب provision کرنا ہے بمقابلہ اسے elastically اسکیل ہونے دینا یا burst credits پر انحصار کرنا۔
- **Cross-region snapshot کاپی**: EBS snapshots کو ڈیزاسٹر ریکوری کے لیے دیگر Regions میں کاپی کیا جا سکتا ہے۔ کاپی شدہ snapshot آزاد ہوتا ہے اور restore کے دوران ڈیٹا منتقلی لاگتیں شامل نہیں کرتا — صرف خود کاپی آپریشن کے دوران۔
- **Storage Gateway کی اقسام:** File Gateway = NFS/SMB → S3 (فائلیں objects بن جاتی ہیں)۔ Volume Gateway = iSCSI block اسٹوریج → S3 snapshots (stored: بنیادی on-prem؛ cached: بنیادی S3 میں)۔ Tape Gateway = VTL → S3/Glacier (جسمانی tapes کی جگہ لیتا ہے)۔ امتحانی trigger: "on-premises ایپ کو بغیر کوڈ تبدیلیوں کے کلاؤڈ اسٹوریج چاہیے" → Storage Gateway۔ "tape بیک اپ کی جگہ لیں" → Tape Gateway۔

## مشقیں

**مشق 1 — یاد کریں**

اپنے الفاظ میں: EBS اور EFS کے درمیان کیا فرق ہے؟ آپ ایک کو دوسرے پر کب ترجیح دیں گے؟

*(اشارہ: اس بارے میں سوچیں کہ آیا ایک instance یا متعدد instances کو ایک ہی وقت میں اسٹوریج تک رسائی کی ضرورت ہے۔)*

**مشق 2 — SAA-C03 منظر نامہ**

*منظر نامہ*: ایک کمپنی ایک load balancer کے پیچھے چار EC2 instances میں ایک ویب ایپلیکیشن چلاتی ہے۔ صارفین پروفائل تصاویر اپ لوڈ کر سکتے ہیں۔ کوئی بھی تصویر اپ لوڈ کے فوراً بعد صارفین کو قابلِ دیکھنا چاہیے، چاہے اسے کسی بھی instance نے سنبھالا ہو۔ تصاویر براؤزرز کو HTTP پر پیش کی جاتی ہیں، کبھی اپنی جگہ ترمیم نہیں کی جاتیں، اور ٹیم سب سے کم آپریشنل overhead کے ساتھ **سب سے زیادہ** لاگت-مؤثر، قابلِ اسکیل حل چاہتی ہے۔

کون سا اسٹوریج حل ان کی ضروریات کو **بہترین** طریقے سے پورا کرتا ہے؟

A) ہر EC2 instance سے ایک EBS gp3 volume منسلک کریں اور ایک cron job کا استعمال کرتے ہوئے فائلوں کو ان کے درمیان sync کریں  
B) تصاویر براہِ راست EC2 instance کے instance store پر محفوظ کریں  
C) Amazon EFS استعمال کریں، تمام چار EC2 instances پر بیک وقت mount کریں  
D) تصاویر S3 میں محفوظ کریں اور انہیں ایپلیکیشن کوڈ سے براہِ راست رسائی کریں

**اشارہ 1**: ضرورت یہ ہے کہ "تمام چار instances کو کوئی بھی تصویر پیش کرنی ہوگی۔" کون سے اختیارات کسی فائل کو تمام instances کے لیے فوراً قابلِ دیکھنا بناتے ہیں؟

**اشارہ 2**: instance store عارضی ہے۔ EBS کو بیک وقت متعدد instances پر mount نہیں کیا جا سکتا۔ یہ اسے محدود کرتا ہے۔

**اشارہ 3**: C اور D دونوں نظریاتی طور پر کام کر سکتے ہیں۔ کون سا اس صورت کے لیے زیادہ مناسب ہے جہاں ایپلیکیشن کو فائل سسٹم آپریشنز بمقابلہ HTTP درخواستوں کے ذریعے تصاویر تک رسائی کرنی ہو؟

**جواب**: D

**وضاحت**: تصاویر S3 میں محفوظ کرنا اور انہیں URL کے ذریعے پیش کرنا ایک ویب ایپلیکیشن کے لیے آرکیٹیکچرل طور پر درست انتخاب ہے۔ اپ لوڈ کی گئی تصاویر فوراً کسی بھی سرور سے (اور کسی بھی براؤزر سے) S3 کے URL کے ذریعے قابلِ رسائی ہیں۔ S3 بالکل اسی استعمال کے موقع کے لیے ڈیزائن کیا گیا ہے: صارف کی اپ لوڈ کردہ فائلیں پیمانے پر اعلیٰ دستیابی اور صفر انتظامی overhead کے ساتھ محفوظ کرنا۔

نوٹ: C (EFS) تکنیکی طور پر کام کرے گا، لیکن S3 ویب ایپلیکیشنز میں صارف کی اپ لوڈ کردہ binary فائلوں کے لیے ترجیحی پیٹرن ہے کیونکہ یہ سستا، زیادہ قابلِ اسکیل ہے، اور ایپلیکیشن کے proxy کے طور پر کام کیے بغیر براہِ راست HTTP پر فائلیں پیش کرتا ہے۔

**A کیوں نہیں؟** cron job کے ذریعے فائلیں sync کرنا race conditions اور consistency کے مسائل پیدا کرتا ہے۔ اپ لوڈز اور اگلے sync کے درمیان، فائلیں دوسری instances پر غائب ہوں گی۔

**B کیوں نہیں؟** instance store ڈیٹا instance رکنے یا terminate ہونے پر ختم ہو جاتا ہے۔ تصاویر غائب ہو جائیں گی۔

**C کیوں نہیں؟** EFS صحیح جواب ہے جب سوال فائل سسٹم semantics کا تقاضا کرے (مثلاً، ایک CMS جو فائلوں کو اپنی جگہ ترمیم کرتا ہے)۔ ویب پر پیش کی جانے والی صارف کی اپ لوڈ کردہ تصاویر کے لیے، S3 آسان، سستا، اور زیادہ مناسب ہے۔

**امتحانی-keyword انتباہ**: حقیقی امتحان پر، سوال کو لفظی پڑھیں۔ اگر یہ کہے "shared **file** storage،" "file system،" "NFS،" یا "POSIX،" تو keyed جواب **EFS** ہے — بیان کردہ ضرورت کو آرکیٹیکچرل ذوق سے override نہ کریں۔ یہ منظر نامہ S3 کی طرف key کرتا ہے کیونکہ یہ HTTP پر لاگت-مؤثر object ترسیل مانگتا ہے، نہ کہ ایک فائل سسٹم۔

*SAA-C03 ڈومین 3 — ٹاسک 3.1*

**مشق 3 — آرکیٹیکچر چیلنج** *(اختیاری)*

Nimbus ایک نئی خصوصیت شامل کر رہا ہے: ریستوران کے مالکان PDF مینوز اپ لوڈ کر سکتے ہیں جو پھر parse ہو کر Nimbus ڈیٹابیس کو آباد کرنے کے لیے استعمال ہوتے ہیں۔ PDF پروسیسنگ کا کام EC2 instances کے ایک fleet پر چلتا ہے جنہیں: (a) اپ لوڈ کی گئی PDF پڑھنی ہے، (b) عارضی پروسیسنگ فائلیں لکھنی ہیں، (c) parse کی گئی output لکھنی ہے۔

آپ ان تین مراحل میں سے ہر ایک کے لیے کون سی اسٹوریج سروسز استعمال کریں گے، اور کیوں؟

*(کوئی واحد درست جواب نہیں ہے۔ ہر مرحلے کی خصوصیات سے اسٹوریج کی قسم کو ملانے پر توجہ دیں۔)*
