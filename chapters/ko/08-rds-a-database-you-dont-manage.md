# 8장: 결코 병에 걸리지 않는 데이터베이스 관리자

새벽 3시에 알림이 왔다.

데이터베이스 서버에 보안 패치가 필요했다 — 재시작이 필요한 종류. 취약점은 실제였고, 패치는 이용 가능했으며, 고객을 방해하지 않고 적용할 수 있는 창은 지금 이었다. 트래픽이 낮은 밤 한중간에.

Priya만 깨어 있었다. 그녀가 패치를 적용하고, 서버를 재시작하고, 애플리케이션이 다시 온라인 상태가 될 때까지 로그를 지켜보다가, 오전 4시 15분에 잠자리에 들었다.

아침에 그녀가 팀에게 무슨 일이 있었는지 말했다. 잠시 침묵이 흘렀다.

"또 그런 일이 생길 거야," Tom이 말했다.

"패치가 있을 때마다 생길 거야," Priya가 말했다. "그리고 항상 패치가 있어. 이걸 더 잘할 방법이 있어야 해."

방법이 있었다. 단지 데이터베이스를 직접 관리해야 한다는 생각을 내려놓아야 했다.

**전통적인 데이터베이스 문제**

EC2 인스턴스에서 직접 데이터베이스를 실행하면, 모든 것에 책임이 있다.

데이터베이스 소프트웨어 설치. 안전하게 설정. 보안 취약점이 발견될 때 패치. 백업 수행. 백업이 실제로 작동하는지 테스트(대부분의 팀이 너무 늦을 때까지 이 단계를 건너뛰는 것). 디스크 공간 모니터링. 이중화를 위한 복제 설정. 기본 서버가 다운될 때를 위한 장애 조치 설정. 쿼리 성능 튜닝. 부하에서 연결 관리.

이 중 어느 것도 애플리케이션이 아니다. 어느 것도 기능을 추가하지 않는다. 모두 전문 지식이 필요하다.

대부분의 개발 팀은 데이터베이스 관리자가 아니다. 이것은 예측 가능한 패턴을 만든다:
데이터베이스가 설치되고, 최소한으로 설정되고, 그런 다음 치명적으로 잘못될 때까지 대부분 잊혀진다.

"우리가 그렇게 한 거야?" Maya가 물었다.

Leo의 답은 침묵이었는데, 그것은 예스와 같았다.

**Amazon RDS: 관리형 데이터베이스**

**Amazon RDS** — Relational Database Service — 는 직접 하지 않아도 되도록 관계형 데이터베이스를 실행하는 운영 부담을 처리한다.

RDS를 사용하면, AWS가 관리한다:

- 데이터베이스 엔진 설치 및 패치
- 자동화된 백업(S3에 저장, 최대 35일 보관)
- 자동화된 장애 조치(기본 서버가 다운되면, 스탠바이가 자동으로 인계)
- 모니터링 및 메트릭
- 저장 시 및 전송 중 암호화
- 스토리지 자동 확장(활성화하면, 가득 찰 때 디스크가 늘어난다)

당신이 관리한다:

- 데이터베이스 스키마(테이블 구조)
- 쿼리 및 애플리케이션 로직
- 데이터베이스에 접근하는 사람
- 데이터베이스를 실행하는 인스턴스 유형
- 매개변수 튜닝(하지만 RDS는 합리적인 기본값을 제공한다)

비유: 결코 병가를 내지 않고, 설정 오류를 하지 않으며, 자동으로 일일 백업을 하고, 문제가 생기면 스스로 고치는 데이터베이스 관리자를 고용하는 것 — 하지만 애플리케이션 로직을 작성하지 않는.

**지원되는 엔진**

RDS는 여러 인기 있는 데이터베이스 엔진을 지원한다:

- **MySQL** — 가장 널리 사용되는 오픈 소스 관계형 데이터베이스
- **PostgreSQL** — 강력하고 확장 가능하며, 복잡한 워크로드에 점점 더 인기
- **MariaDB** — 오픈 소스 MySQL 포크, 완전히 호환
- **Oracle** — 엔터프라이즈급, 레거시 요구사항이 있는 대형 조직에서 사용
- **Microsoft SQL Server** — Windows 중심 환경용
- **Amazon Aurora** — 클라우드용으로 구축된 AWS의 자체 MySQL/PostgreSQL 호환 엔진
  (24장에서 Aurora를 깊이 다룬다)

Nimbus의 경우, 선택은 PostgreSQL이었다. Leo가 알고 있던 것이었고, 관계형 데이터를 잘 처리했다. 엔진 선택은 대부분의 애플리케이션에서 생각보다 덜 중요하다 — 운영 이점은 엔진에 관계없이 적용된다.

**멀티 AZ: 인계하는 스탠바이**

이것이 신뢰성 계산을 완전히 바꾸는 기능이다.

**멀티 AZ 배포**는 RDS가 기본 서버와 다른 가용 영역에 동기적인 스탠바이 인스턴스를 유지한다는 것을 의미한다. 기본 서버에 커밋된 모든 트랜잭션이 커밋이 확인되기 전에 스탠바이에 동기적으로 복제된다.

기본 서버가 실패하면 — 하드웨어 장애, AZ 장애, 소프트웨어 충돌 — RDS가
자동으로 스탠바이로 장애 조치한다. 데이터베이스 엔드포인트의 DNS 레코드가 업데이트된다. 애플리케이션이 새 기본 서버에 재연결한다.

장애 조치는 60-120초가 걸린다. 그 창 동안, 애플리케이션이 연결 오류를 경험한다. 올바르게 작성된 애플리케이션은 이것을 우아하게 처리해야 한다(백오프를 사용한 연결 재시도).

스탠바이는 읽기 복제본이 아니다. 읽기 트래픽을 제공하지 않는다. 그것의 유일한 목적은 인계할 준비가 되어 있는 것이다.

Tom: "멀티 AZ 비용이 얼마나 돼요?"

단일 인스턴스 비용의 약 두 배 — 말 그대로 두 개의 데이터베이스 인스턴스를 실행하기 때문이다. 스탠바이는 기본 서버와 같은 비용이 든다.

Tom: "그리고 기본 서버가 죽으면 무료로 받는 장애 조치 비용은 얼마야?"

그는 금요일 최대 부하 동안 시간당 수익을 추정하여 자신의 질문에 답했다.

그 오후에 멀티 AZ가 활성화되었다.

**자동화된 백업 및 특정 시점 복구**

RDS는 매일 자동화된 백업을 한다. AWS는 이 백업을 S3에 저장한다(RDS에 의해 관리됨 — S3 콘솔에서 직접 보지 않는다). 백업 보관 기간 내 어느 시점으로도 데이터베이스를 복원할 수 있다.

백업은 설정 가능한 **유지 보수 창** 동안 발생한다 — 보통 이른 아침의 낮은 트래픽 기간. 대부분의 엔진 유형에서, 백업이 다운타임을 발생시키지 않는다.

**특정 시점 복구**는 가장 가치 있는 기능 중 하나다: 보관 기간 내 어느 *초*로도 복원할 수 있다. 일일 스냅샷만이 아니라 — *어느 초*든. 이것은 RDS가 일일 백업 외에도 트랜잭션 로그를 지속적으로 아카이브하기 때문에 가능하다.

누군가 오후 2:37에 `DELETE FROM orders WHERE 1=1`을 실수로 실행하면, 오후 2:36으로 복원할 수 있다.

이것을 이해할 때 Leo가 눈에 띄게 안도했다.

"지난달 내가 삭제한 것에서 복구할 수 있었을까요?" 그가 물었다.

"RDS 이전? 아니요," Priya가 말했다. "RDS 이후? 네."

**읽기 복제본: 읽기 트래픽 확장**

멀티 AZ는 가용성에 관한 것이다. **읽기 복제본**은 성능에 관한 것이다.

읽기 복제본은 읽기 쿼리를 제공할 수 있는 기본 데이터베이스의 비동기 복사본이다. 대부분의 RDS 엔진에서 최대 5개의 읽기 복제본을 가질 수 있다(Aurora는 더 많다).

애플리케이션이 읽기 쿼리를 복제본으로, 쓰기 쿼리를 기본 서버로 보내도록 수정된다. 이것이 부하를 분산한다: 기본 서버가 쓰기와 복잡한 트랜잭션을 처리하고; 복제본이 읽기를 처리한다.

핵심 특성:

- 복제는 **비동기적** — 기본 서버와 복제본 사이에 (지연) 차이가 있을 수 있다. 레코드를 쓰고 복제본에서 즉시 읽으면, 아직 보지 못할 수 있다.
- 읽기 복제본은 같은 리전 또는 다른 리전에 있을 수 있다(교차 리전 복제본은 지연을 추가하지만 지리적 배포를 가능하게 한다).
- 재해 시나리오에서 읽기 복제본을 독립 실행형 데이터베이스로 승격할 수 있다.

Nimbus의 경우: 메뉴 조회는 읽기다. 주문 내역은 읽기다. 트래픽의 대다수가 읽기 트래픽이다. 읽기 복제본을 추가하고 읽기를 거기로 라우팅하면 기본 데이터베이스 부하가 크게 줄어든다.

읽기 복제본을 24장에서 Aurora를 논의할 때 더 철저히 다룬다.

**RDS 파라미터 그룹과 옵션 그룹**

시험에 나오는 두 가지 설정 메커니즘:

**파라미터 그룹**은 데이터베이스 엔진 설정을 제어한다 — 최대 연결 수, 쿼리 캐시 크기, 타임아웃 값 같은 것들. RDS는 대부분의 경우에 작동하는 기본 파라미터 그룹을 만든다. 특정 설정을 튜닝해야 할 때 사용자 정의 파라미터 그룹을 만든다.

**옵션 그룹**은 일부 엔진에 대한 추가 기능을 활성화한다 — Oracle의 기본 네트워크 암호화나 SQL Server의 투명 데이터 암호화 같은. 대부분의 오픈 소스 엔진 배포는 사용자 정의 옵션 그룹이 필요하지 않다.

이것들을 암기할 필요가 없다. 데이터베이스 엔진 동작을 사용자 정의하기 위해 존재한다는 것을 알면 된다.

## 장점과 한계

**RDS가 훌륭한 이유**:

- 데이터베이스 소프트웨어 관리의 운영 부담을 없애준다
- 자동화된 백업 및 특정 시점 복구
- 최소 RTO로 자동 장애 조치를 위한 멀티 AZ
- 읽기 트래픽 확장을 위한 읽기 복제본
- 저장 시 및 전송 중 암호화 내장
- 모든 주요 관계형 데이터베이스 엔진 지원

**RDS의 한계**:

- 기본 OS에 접근할 수 없다. 사용자 정의 OS 수준 소프트웨어를 설치하거나 운영 체제 설정을 변경할 수 없다. 데이터베이스에 OS 수준 접근을 요구하는 요구사항이 있다면, 자체 EC2 기반 데이터베이스를 실행해야 할 수 있다.
- RDS는 서버리스가 아니다(예외: Aurora Serverless가 있으며, 24장에서 다룬다). 유휴 상태에서도 실행 중인 인스턴스에 대해 지불한다.
- RDS는 수평으로 샤딩된 데이터베이스를 위해 설계되지 않았다. 쓰기 집약적인 관계형 워크로드의 대규모 확장을 위해, 결국 다른 아키텍처가 필요할 수 있다.
- 비관계형(NoSQL) 데이터 패턴의 경우, DynamoDB(9장)가 더 적절하다.

## 요약

- **Amazon RDS**는 관리형 관계형 데이터베이스 서비스다. AWS가 패치, 백업, 장애 조치, 스토리지 관리를 처리한다. 당신이 스키마, 쿼리, 애플리케이션 로직을 처리한다.
- **멀티 AZ** 배포는 다른 AZ에 동기적인 스탠바이를 유지한다.
  기본 서버가 실패하면 60-120초 내에 자동 장애 조치가 발생한다.
- **자동화된 백업**과 **특정 시점 복구**를 통해 보관 기간 내 어느 초로도 복원할 수 있다.
- **읽기 복제본**은 읽기 트래픽을 제공하는 비동기 복사본으로, 기본 서버의 부하를 줄인다. 복제 지연은 약간 뒤처질 수 있다는 것을 의미한다.
- 관리되는 작업이 있는 관계형 데이터베이스가 필요할 때 RDS를 선택하라. 더 높은 성능이나 서버리스 옵션이 필요할 때 Aurora(24장)를 사용하라.

## 시험 팁

*SAA-C03 도메인 3 — 태스크 3.3 (데이터베이스 솔루션)*

- **멀티 AZ는 고가용성을 위한 것이지, 성능을 위한 것이 아니다.** 스탠바이는 읽기 트래픽을 제공하지 않는다. 읽기 복제본은 성능을 위한 것이다. 이 구분이 자주 테스트된다.
- **멀티 AZ 장애 조치는 자동적이다.** 언제 또는 어떻게 발생하는지 설정하지 않는다. RDS가 기본 서버를 모니터링하고 자동으로 장애 조치를 트리거한다.
- **복제 지연이 중요하다.** 읽기 복제본은 기본 서버보다 약간 뒤처질 수 있다. 방금 쓴 데이터를 읽어야 하는 애플리케이션의 경우, 복제본이 아니라 기본 서버에서 읽어야 한다. 이것을 "쓰기-읽기 일관성"이라고 한다.
- **자동화된 백업은 0-35일 동안 보관된다.** 보관을 0으로 설정하면 자동화된 백업이 비활성화된다. 수동 스냅샷은 삭제할 때까지 무기한 보관된다.
- **RDS 스토리지 자동 확장**은 디스크 가득 참 중단을 방지한다. 활성화하라. 위로만 확장하고, 아래로는 확장하지 않는다. 시험은 이 비대칭성을 알고 있는지 테스트할 수 있다.

*(힌트: 하나는 다운타임으로부터 보호하고; 다른 하나는 읽기 부하에서 성능을 향상시킨다. 서로 다른 문제를 해결하며 함께 사용할 수 있다.)*

**연습 2 — 시험 연습**

*시나리오*: 한 회사가 RDS에서 프로덕션 PostgreSQL 데이터베이스를 실행한다. 하루 종일 실행되는 리포팅 쿼리로 인해 높은 읽기 트래픽을 경험한다. 팀은 또한 데이터베이스 가용성을 걱정한다 — 실패 시나리오에서 몇 분 이상의 다운타임을 감당할 수 없다. 리포팅 워크로드로부터 기본 데이터베이스에 대한 영향을 최소화하길 원한다.

다음 중 두 가지 우려를 가장 잘 해결하는 RDS 기능 조합은?

A) 멀티 AZ를 활성화하고 스탠바이 인스턴스에 대해 모든 쿼리를 실행한다  
B) 장애 조치 보호를 위한 멀티 AZ를 활성화하고 리포팅 쿼리를 위한 읽기 복제본을 만든다  
C) 비용 절감을 위해 멀티 AZ 없이 여러 읽기 복제본을 만든다  
D) 더 많은 수동 스냅샷을 자주 찍고 기본 서버가 실패하면 그것에서 복원한다

**힌트 1**: 두 가지 요구사항은: (1) 실패 시 가용성, (2) 읽기 오프로딩. 어떤 기능이 어떤 요구사항을 해결하는가?

**힌트 2**: 멀티 AZ는 자동 장애 조치를 제공한다. 스탠바이는 읽기 트래픽을 제공하지 않는다. 따라서 멀티 AZ만으로는 읽기 문제를 해결하지 못한다.

**힌트 3**: 읽기 복제본은 읽기 트래픽을 제공한다. 멀티 AZ는 장애 조치를 제공한다. 둘 다 필요하다.

**답**: B

**설명**: 멀티 AZ는 다른 AZ의 스탠바이로 자동 장애 조치를 제공한다 —
가용성 요구사항을 해결한다. 읽기 복제본은 리포팅 쿼리가 기본 데이터베이스에 영향을 미치지 않고 실행되도록 한다 — 성능 요구사항을 해결한다. 두 기능을 동시에 사용할 수 있다.

**왜 A가 아닌가?** 멀티 AZ 스탠바이는 읽기 트래픽을 제공할 수 없다. 직접 쿼리하는 것은 지원되지 않는다.

**왜 C가 아닌가?** 읽기 복제본은 읽기 성능을 돕지만 자동 장애 조치를 제공하지 않는다. 기본 서버가 실패하면, 읽기 복제본을 수동으로 승격해야 한다 — 시간이 걸리고 자동이 아니다.

**왜 D가 아닌가?** 수동 스냅샷은 전체 데이터베이스 복사본을 복원한다 — 대형 데이터베이스의 경우 잠재적으로 몇 시간이 걸리는 훨씬 더 긴 프로세스. 이것은 "몇 분" 다운타임 요구사항을 충족하지 않는다.

*SAA-C03 도메인 3 — 태스크 3.3*

**연습 3 — 아키텍처 과제** *(선택 사항)*

Nimbus는 기존의 자체 관리 PostgreSQL 데이터베이스(EC2 인스턴스에서 실행)를 RDS PostgreSQL로 마이그레이션하는 것을 고려하고 있다. 마이그레이션은 최소한의 다운타임 — 이상적으로는 15분 미만 — 으로 진행해야 한다. 데이터베이스는 200GB다.

어떤 접근 방식을 추천하겠는가? 어떤 AWS 서비스가 마이그레이션에 도움이 될 수 있는가? 프로덕션 트래픽을 전환하기 전에 어떤 위험을 테스트하겠는가?

*(단 하나의 정답은 없다. AWS Database Migration Service, 논리적 복제, 전환 중 데이터 불일치 위험에 대해 생각하라.)*

3일 후, 데이터베이스가 건강했다. 쿼리 시간이 약간 떨어졌지만 충분하지 않았다. 메뉴는 여전히 로드가 느렸다. 22,000개의 아이템. 매번 모두를 반환하는 쿼리.

"문제는 데이터베이스 엔진이 아니야," Priya가 말했다. "데이터 모델이야."
