# 19장: 티켓 머신

티켓 머신은 조용한 혁명이었다. 번호를 뽑고, 호출되기를 기다린다. 줄이 큐가 됐다. 사람들이 앉을 수 있었다. 서비스 카운터가 자체 속도로 작동했다. 아무도 아무도 막지 않았다.

Nimbus에는 문제처럼 느껴지지 않다가 주문이 인기를 얻은 후에 문제로 나타난 것이 있었다.

주문이 들어올 때마다, API 서버가 다음을 해야 했다:

1. 데이터베이스에 주문 저장
2. 레스토랑 태블릿에 알림 전송
3. 고객에게 확인 이메일 전송
4. 레스토랑 분석 대시보드 업데이트
5. 결제를 위한 이벤트 기록

이 모든 것이 API가 고객에게 응답하기 전에 동기적으로 일어나야 했다. 이메일 서비스가 느리면(때로는 그랬다), 고객이 기다렸다. 분석 대시보드가 다운되면(때로는 그랬다), 주문이 실패했다.

"우리는 강하게 결합되어 있어," Priya가 말했다. "하나의 다운스트림 단계가 실패하면, 전체 주문이 실패해."

"주문을 저장하고 즉시 고객에게 확인할 수 있다면," Leo가 말했다. "그리고 나머지는 백그라운드에서 처리하는 거요?"

"그게 큐야," Priya가 말했다.

**델리 카운터 모델**

바쁜 델리 카운터에서, 계산대 직원은 슬라이서가 슬라이싱을 마칠 때까지 기다리지 않고 다음 고객으로 이동한다. 주문을 받고, 주방에 건네고, 다음 사람을 시작한다. 주방이 자체 속도로 주문을 처리한다.

고객이 더 빠른 서비스를 받는다. 주방이 갑작스러운 급증에 압도되지 않는다. 주방이 느린 순간이 있으면, 주문이 오류를 일으키는 대신 큐에 쌓인다.

이것이 **분리**다: 작업을 수락하는 구성 요소를 처리하는 구성 요소에서 분리하는 것.

소프트웨어 시스템에서, 큐는 종종 메시지 브로커다 — 생산자로부터 메시지를 수락하고 소비자에게 배달하는 서비스.

**Amazon SQS: 큐**

**Amazon SQS(Simple Queue Service)**는 AWS의 관리형 메시지 큐 서비스다. 소비자가 처리할 때까지 메시지를 내구성 있게 저장한다.

기본 흐름:

1. **생산자**(API 서버)가 큐에 메시지를 넣는다: `{ "orderId": "ORD-5532", "restaurantId": "47", "items": [...] }`
2. API가 즉시 고객에게 응답한다: "주문이 확인됐습니다!"
3. **소비자**(별도의 작업자 서비스들)가 큐에서 메시지를 읽고 처리한다: 레스토랑 알림 전송, 확인 이메일 전송, 분석 업데이트

고객 경험: 즉시 확인. 다운스트림 처리: 작업자의 속도로 비동기적으로 일어난다.

**SQS 핵심 개념**

**메시지 가시성 타임아웃**: 소비자가 SQS에서 메시지를 읽을 때, 메시지가 다른 소비자에게 보이지 않게 된다(기본값: 30초). 이것이 소비자에게 처리할 시간을 준다. 소비자가 성공적으로 완료하면, 메시지를 삭제한다. 소비자가 충돌하면, 가시성 타임아웃이 만료되고 메시지가 다른 소비자가 재시도할 수 있도록 다시 보이게 된다.

이것이 최소 한 번 배달을 보장한다: 소비자가 처리 중에 실패하더라도, 모든 메시지가 최소 한 번 처리된다.

**Dead-letter 큐(DLQ)**: 메시지가 너무 많이 처리에 실패하면(설정 가능 — 예: 5번 재시도), SQS가 메시지를 dead-letter 큐로 이동한다. DLQ를 검사하여 메시지를 잃지 않고 메시지가 실패하는 이유를 이해한다.

**큐 유형**:

**표준 큐**: 최대 처리량(초당 무제한 메시지). 배달 순서는 최선을 다함(보장 안 됨). 최소 한 번 배달(매우 드물게, 메시지가 두 번 배달될 수 있다).

**FIFO 큐**: 엄격한 선입선출 순서. 정확히 한 번 배달. 배치로 초당 3,000개 메시지, 없이는 300개로 제한. 순서가 중요할 때 사용(금융 거래, 순차적 상태 변경).

Nimbus의 경우, 대부분의 큐가 표준 큐를 사용했다. 결제 큐는 요금이 순서대로 처리되도록 FIFO를 사용했다.

**Amazon SNS: 방송자**

**Amazon SNS(Simple Notification Service)**는 게시/구독(pub/sub) 메시지 서비스다. 하나의 생산자, 하나의 소비자(큐)가 아닌, SNS는 하나의 메시지가 동시에 *많은* 구독자에게 배달되는 것을 지원한다.

모델:

1. **게시자**가 SNS **토픽**에 메시지를 전송한다
2. 해당 토픽의 모든 **구독자**가 동시에 메시지를 받는다(팬 아웃)

구독자는 다음이 될 수 있다:

- SQS 큐(비동기 처리를 위해 큐에 메시지 푸시)
- Lambda 함수(함수를 직접 트리거)
- HTTP/HTTPS 엔드포인트(웹훅 배달)
- 이메일 주소
- SMS(전화번호)

Nimbus의 경우, 주문 들어온 이벤트가 `order-events`라는 SNS 토픽에 게시된다:

- 레스토랑 알림 서비스가 구독(SQS 큐에서 받는다)
- 이메일 서비스가 구독(SQS 큐에서 받는다)
- 분석 서비스가 구독(SQS 큐에서 받는다)
- 결제 서비스가 구독(FIFO SQS 큐에서 받는다)

하나의 주문 이벤트. 네 명의 구독자. 모두 동시에 알림 받음. 각자 자체 속도로 처리.

"그러면 SNS가 발표이고," Maya가 말했다. "SQS가 각 팀이 자신의 속도로 발표를 처리하는 받은 편지함이군요."

"정확히," Leo가 말했다. "SNS/SQS 팬 아웃이 표준 패턴이에요."

**SNS/SQS 팬 아웃 패턴**

이 조합 — 여러 SQS 큐를 피딩하는 SNS 토픽 — 은 AWS에서 가장 중요한 아키텍처 패턴 중 하나다:

```
API 서버
    |
    | 게시
    ↓
SNS 토픽: "order-placed"
    |
    |—————————————————|—————————————————|
    ↓                 ↓                 ↓
SQS 큐            SQS 큐            SQS 큐
(알림)           (이메일 서비스)   (분석)
    |                 |                 |
    ↓                 ↓                 ↓
작업자            작업자            작업자
Lambda/EC2       Lambda/EC2       Lambda/EC2
```

각 큐는 독립적이다. 분석 서비스가 느릴 수 있다 — 큐가 채워지지만, 알림 및 이메일 서비스는 영향 받지 않는다. 분석 서비스가 다운되면, 메시지는 큐에서 다시 올라올 때까지 기다린다. 아무것도 잃지 않는다.

이것이 핵심 속성이다: **독립적 실패**. 하나의 소비자의 문제가 다른 것들에 전파되지 않는다.

**메시지 필터링: 모든 구독자를 위한 모든 메시지가 아니다**

시스템이 성장하면, 모든 구독자가 모든 메시지를 처리하기를 원하지 않는다. 분석 서비스는 완료된 주문만 신경쓰면 결제 처리 실패 메시지를 받아서는 안 된다.

**SNS 메시지 필터링**을 통해 구독자가 필터 정책을 지정할 수 있다 — 특정 속성과 일치하는 메시지만 배달한다.

레스토랑 알림 서비스가 `status = "confirmed"` 필터로 구독한다.

오류 알림 서비스가 `status = "failed"` 필터로 구독한다.

각 구독자가 필요한 것만 받는다.

**SQS vs. SNS를 언제 사용하는가**

**SQS 단독**: 하나의 생산자, 하나의 소비자(또는 같은 큐에 여러 경쟁하는 소비자). 메시지가 한 번 처리되어야 한다, 순서대로(FIFO) 또는 그렇지 않게(표준). 작업자 큐 패턴 — 하나의 큐, 여러 작업자가 소비한다.

**SNS 단독**: 화재-및-망각 알림. 이메일, SMS, 또는 HTTP 엔드포인트로 푸시. 메시지를 큐에 넣을 필요가 없다 — 그냥 알림을 보내고 이동한다.

**SNS + SQS (팬 아웃)**: 하나의 이벤트, 여러 독립적인 소비자. 각 소비자는 자체 큐를 갖고, 독립적으로 처리하며, 독립적으로 실패할 수 있다.

## 장점과 한계

**SQS와 SNS가 강력한 이유**:

- SQS는 내구성 있고 신뢰할 수 있는 메시지 배달을 제공한다 — 메시지는 여러 AZ에 걸쳐 저장된다
- 분리는 생산자 및 소비자 서비스의 독립적인 확장 및 배포를 가능하게 한다
- Dead-letter 큐는 어떤 메시지도 실패 시 자동으로 잃어버리지 않도록 보장한다
- SNS 팬 아웃 패턴은 생산자를 변경하지 않고 새 소비자를 추가하는 것을 허용한다

**복잡해지는 부분**:

- 최소 한 번 배달은 소비자가 *멱등적*이어야 한다는 것을 의미한다 — 같은 메시지를 두 번 처리하면 문제가 없어야 한다(중복 주문, 중복 청구)
- FIFO 큐는 더 비싸고 처리량 제한이 있다
- 여러 큐와 서비스에 걸쳐 실패한 메시지를 디버깅하려면 좋은 로깅 및 관찰 가능성이 필요하다
- 메시지 순서 보장은 제한적 — 여러 서비스에 걸쳐 엄격한 순서가 중요하면, 설계가 복잡해진다

## 요약

- **분리**는 작업을 생성하는 구성 요소를 처리하는 구성 요소에서 분리한다.
- **SQS**는 관리형 큐다. 생산자가 메시지를 보내고; 소비자가 비동기적으로 읽고 처리한다.
- **SQS Standard**: 높은 처리량, 최선을 다한 순서, 최소 한 번 배달.
- **SQS FIFO**: 엄격한 순서, 정확히 한 번 배달, 낮은 처리량.
- **SNS**는 pub/sub 서비스다. 하나의 메시지, 동시에 많은 구독자.
- **SNS + SQS 팬 아웃**: 하나의 이벤트가 여러 독립적인 처리 파이프라인을 트리거하는 표준 패턴.
- **Dead-letter 큐**: 너무 많은 재시도 후 처리에 실패한 메시지를 잡는다.
- **멱등성**: 소비자가 중복 메시지를 안전하게 처리할 수 있도록 설계하라.

## 시험 팁

*SAA-C03 도메인: 탄력적 아키텍처 설계(도메인 2, 태스크 2.1)*

- **SQS Standard vs. FIFO**: 시험은 순서 및 배달 보장으로 구분한다. "순서대로 처리해야 함" → FIFO. "최대 처리량" → Standard.
- **가시성 타임아웃**: 최소 한 번 배달을 위한 핵심 개념. 소비자가 실패하면, 타임아웃 후 메시지가 다시 보인다. 시험 시나리오: "메시지가 두 번 처리됨" → 가시성 타임아웃이 너무 짧다(소비자가 처리하는 데 타임아웃보다 더 오래 걸린다).
- **Dead-letter 큐**: N번 재시도 후 실패한 메시지가 여기로 이동한다. 시험 시나리오: "반복 실패에서도 어떤 메시지도 손실되지 않도록 보장" → DLQ.
- **SNS 팬 아웃**: 하나의 이벤트가 여러 소비자를 트리거해야 하는 경우의 고전적인 시험 패턴. "주문 알림은 이메일, SMS, 인벤토리 업데이트를 동시에 트리거해야 함" → SQS 구독이 있는 SNS 토픽.
- **SQS + Lambda**: Lambda가 SQS 큐를 폴링하고 각 메시지 배치에서 트리거하도록 설정할 수 있다. 시험은 대규모 이벤트 기반 처리를 위해 이것을 사용한다.
- **SQS 롱 폴링**: 소비자가 몇 초마다 폴링(짧은 폴링, API 호출을 낭비)하는 대신, 롱 폴링은 메시지를 최대 20초 기다린다. 비용을 줄이고 거짓 빈 응답을 줄인다.

**힌트 3**: SNS 팬 아웃은 세 가지 다운스트림 서비스 모두가 동시에 이벤트를 받도록 허용한다.

**답**: B

**설명**: API가 데이터베이스에 주문을 저장하고(동기적 — 확인 전에 완료되어야 함) 즉시 확인을 반환한다. 그런 다음 SNS 토픽에 `order-placed` 이벤트를 게시한다. 인벤토리, 이메일, 분석 서비스 각각이 독립적인 SQS 큐를 통해 구독한다. 자체 속도로 처리한다 — 분석이 느리면, 큐가 쌓이지만 다른 서비스는 영향 받지 않는다. 서비스가 실패하면, 메시지는 SQS 큐에 남아 재시도된다; 설정된 수의 실패한 재시도 후 DLQ로 이동한다.

**왜 A가 아닌가?** FIFO 큐는 메시지를 순서대로 처리한다 — 이것은 동기적 느려짐을 해결하지 못한다. 또한, 순차적 처리는 분석이 여전히 이메일을 차단한다.

**왜 C가 아닌가?** "병렬 EC2 인스턴스가 동기적으로 처리"는 여전히 모든 단계가 완료되기 전에 응답하기를 고객이 기다린다는 것을 의미한다. 더 많은 인스턴스를 추가해도 동기적 결합을 해결하지 못한다.

**왜 D가 아닌가?** API Gateway는 API 라우팅과 검증을 가속화하지만, 다운스트림 처리 단계를 분리하지 않는다.

*SAA-C03 도메인: 탄력적 아키텍처 설계 — 태스크 2.1*

**연습 3 — 아키텍처 과제** *(선택 사항)*

Nimbus는 레스토랑 파트너를 위한 알림 시스템을 구축하고 있다. 고객이 주문을 하면, 레스토랑은 다음을 통해 알림을 받아야 한다:

- 태블릿 앱(푸시 알림)
- 주방 디스플레이 시스템(로컬 하드웨어로의 HTTP 웹훅)
- 백업 SMS(태블릿 알림이 실패하면)

태블릿 알림 서비스는 신뢰할 수 있다. 주방 웹훅은 때때로 다운된다(레스토랑이 마감 시간에 하드웨어를 끈다). SMS는 태블릿 알림이 실패하는 경우에만 발송해야 한다.

SNS와 SQS를 사용하는 아키텍처를 설계하라. "태블릿이 실패하면 SMS만"이라는 요구사항을 어떻게 처리하겠는가? 주방 웹훅이 오프라인일 때 태블릿 알림을 막지 않도록 어떻게 보장하겠는가?

*(단 하나의 정답은 없다. 조건부 라우팅으로 팬 아웃 설계를 연습하는 것이 목표다.)*

고객이 주문했다. API가 95밀리초에 응답했다. 확인이 전화기에 즉시 나타났다.

고객은 결코 알아차리지 못했다.

Leo가 버그를 수정하고 분석 서비스가 재시작했을 때, 18분 만에 백로그를 처리했다. 데이터가 손실되지 않았다. DLQ가 비어 있었다.

"이게 분리가 의미하는 거야," Priya가 말했다.

그는 예상치 못하게 저렴하고 예상치 못하게 좋은 것을 발견한 누군가의 표정을 했다.
