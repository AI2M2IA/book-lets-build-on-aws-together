# 23장: 스스로 정렬하는 파일링 시스템

법률 사무소는 활성 사건 파일을 책상에 둔다. 완료된 사건은 파일 캐비닛에 간다. 3년 전 사건은 지하실의 보관 상자에 간다. 10년 전 사건은 무엇이든 2일 걸려 검색하지만 상자당 몇 센트인 오프사이트 아카이브 시설에 간다.

같은 정보, 얼마나 자주 접근하는지에 따라 다른 비용으로 저장된다.

S3는 이것을 자동으로 한다.

Tom이 Nimbus AWS 청구서를 검토하고 있었다. 항목: S3 스토리지. 월 $847.

그가 Leo를 불렀다.

"S3에 4.2테라바이트가 있어요," Leo가 확인 후 말했다.

"무엇이요?"

"레스토랑 사진. 주문 영수증. 분석 내보내기. 18개월 전 백업 스냅샷."

"18개월 전 백업에 마지막으로 누군가 접근한 게 언제야?"

Leo가 접근 로그를 확인했다.

"지난 10월이요," 그가 말했다. "한 번. 백업 형식을 확인하기 위해."

"그러면 우리는 18개월의 백업을 전체 S3 Standard 가격으로 지불하고 있어요."

"네."

Tom이 S3 가격 페이지를 봤다. S3 Standard: GB당 월 $0.023. S3 Glacier Instant Retrieval: GB당 월 $0.004.

계산을 했다. 빠른 계산.

"이 청구서를 상당히 줄일 수 있어요," 그가 말했다. "그냥 이전 데이터를 더 저렴한 스토리지로 이동하면서."

"무엇이 이전 건지 알아야 해요," Leo가 말했다.

"S3가 알아. 마지막 접근 시간을 추적하거든."

**S3 스토리지 클래스: 전체 스펙트럼**

5장에서 S3 Standard를 기본 스토리지 클래스로 소개했다. S3에는 실제로 일곱 가지 스토리지 클래스가 있으며, 각각 다른 접근 패턴을 위해 설계됐다:

**S3 Standard**: 자주 접근하는 데이터를 위해. 낮은 지연(밀리초). 최고 비용. 최소 스토리지 기간 없음. 활성 데이터에 사용: 현재 메뉴 사진, 오늘의 주문, 최근 로그.

**S3 Standard-Infrequent Access(S3 Standard-IA)**: 한 달에 한 번 미만으로 접근하는 데이터를 위해. Standard와 같은 밀리초 검색이지만 더 낮은 스토리지 비용 + GB당 검색 수수료. 접근할 때 즉시 필요하지만 드물게 하는 데이터에 사용: 이전 주문 영수증, 6개월 된 분석 내보내기.

**S3 One Zone-Infrequent Access(S3 One Zone-IA)**: S3 Standard-IA와 같지만 하나의 가용 영역에만 저장됨(세 개 대신). 내구성이 더 낮지만(그 AZ에 재해가 발생하면 데이터가 손실될 수 있음), 20% 더 저렴하다. 잃어버려도 재생성할 수 있는 데이터에 사용: 썸네일 캐시, 임시 처리 출력.

**S3 Glacier Instant Retrieval**: 가끔 필요한 아카이브 데이터. 밀리초 검색. 매우 낮은 스토리지 비용, 더 높은 GB당 검색 비용. 90일 최소 스토리지. 분기별로 또는 그 미만으로 접근하는 데이터에 사용: 분기별 컴플라이언스 보고서, 12개월 된 백업 스냅샷.

**S3 Glacier Flexible Retrieval**: 분~시간 내에 검색되는 딥 아카이브. Glacier Instant Retrieval보다 낮은 비용. 덜 긴박한 아카이브 데이터에 사용.

**S3 Glacier Deep Archive**: 가장 저렴한 옵션. 12시간 내에 검색. 180일 최소 스토리지. 규제 컴플라이언스를 위해 보관해야 하지만 거의 접근되지 않는 데이터에 사용: 7년 세금 기록, 10년 감사 로그.

패턴: 접근 빈도가 감소할수록 비용이 감소하지만 검색 시간이 증가한다(그리고 검색당 비용이 증가한다). 접근 패턴과 일치하는 클래스를 선택하라.

**S3 수명주기 정책: 자동화된 파일링 시스템**

스토리지 클래스 사이에 파일을 수동으로 이동하는 것은 오류가 발생하기 쉽고 시간이 많이 걸린다. S3 **수명주기 정책**이 정의한 규칙을 기반으로 이것을 자동화한다.

수명주기 규칙에는 두 가지 구성 요소가 있다:

**필터**: 규칙이 적용되는 객체(모든 객체, 특정 접두어가 있는 객체, 특정 태그가 있는 객체).

**액션**: 며칠 후에 무엇을 할 것인지.

Nimbus의 주문 영수증을 위한 예시 수명주기 정책:

```
90일 후 S3 Standard-IA로 전환
365일 후 S3 Glacier Instant Retrieval로 전환
2555일 후 S3 Glacier Deep Archive로 전환(7년)
2920일 후 삭제(8년)
```

이 하나의 정책이 보장한다:

- 활성 영수증(< 90일): S3 Standard, 빠른 접근
- 최근 영수증(90-365일): Standard-IA, 저렴하지만 즉시 사용 가능
- 이전 영수증(1-7년): Glacier, 매우 저렴, 드물게 필요함
- 만료된 영수증(> 8년): 자동 삭제

Tom이 예상 절감액을 검토했다: 월 $847에서 약 $220으로.

"그냥... 이전 것이 무엇인지와 어디로 가야 하는지를 정의하는 것만으로요?" 그가 말했다.

"그리고 S3가 자동으로 이동시킨다," Leo가 확인했다. "크론 작업 없음. 수동 마이그레이션 없음. 잊어버리지 않음."

**S3 Intelligent-Tiering: 자기 조직 클래스**

데이터에 얼마나 자주 접근할지 모른다면?

**S3 Intelligent-Tiering**은 각 객체의 접근 패턴을 모니터링하고 자동으로 접근 계층 사이에 이동한다:

- **Frequent Access 계층**: 최근에 접근한 객체를 위해
- **Infrequent Access 계층**: 30일 동안 접근하지 않은 객체
- **Archive Instant Access 계층**: 90일 동안 접근하지 않은 객체
- **Archive Access 계층**: 90-730일 동안 접근하지 않은 객체(선택적)
- **Deep Archive Access 계층**: 180-730일 이상 접근하지 않은 객체(선택적)

S3 Intelligent-Tiering은 객체당 월 소액 모니터링 수수료($0.0025 per 1,000 객체)를 부과하지만, Frequent 및 Infrequent 계층에 대한 검색 수수료가 없다.

다음의 경우 Intelligent-Tiering을 사용하라:

- 접근 패턴이 예측 불가능하거나 시간에 따라 변경될 때
- 쉽게 분류할 수 없는 핫 데이터와 콜드 데이터의 혼합이 있을 때
- 128KB보다 큰 객체(소형 객체는 절감보다 모니터링 수수료가 더 많이 든다)

다음의 경우 명시적 스토리지 클래스(수명주기 정책 포함)를 사용하라:

- 접근 패턴이 예측 가능할 때
- 객체당 모니터링 수수료를 최소화하고 싶을 때
- 객체가 작다(< 128KB)

**Multipart Upload: 대용량 객체를 위해**

S3는 5GB 단일 업로드 제한이 있다. 더 큰 객체의 경우, **멀티파트 업로드**를 사용해야 한다: 객체를 부분으로 나누고, 각각을 병렬로 업로드하고, S3가 조립한다.

이점:

- 더 빠른 업로드(병렬)
- 실패한 업로드 재개 가능(실패한 부분만 다시 업로드)
- 5GB보다 큰 객체에 필요

수명주기 팁: 7일 후 완료되지 않은 멀티파트 업로드를 삭제하는 수명주기 규칙을 설정하라. 업로드가 중간에 실패하고 정리되지 않으면, 그 부분적인 부분이 저장되고 청구된다 — 조립된 객체가 없어도.

Tom은 이 팁을 매우 높이 평가했다.

**S3 복제: 버킷 사이에 데이터 복사**

S3는 하나의 버킷에서 다른 버킷으로 객체를 자동으로 복제할 수 있다:

**동일 리전 복제(SRR)**: 같은 리전 내에서 객체를 복사한다. 컴플라이언스(다른 계정에 별도 복사본 유지), 여러 버킷의 로그 집계, 또는 프로덕션 데이터에서 테스트 환경 생성에 사용.

**교차 리전 복제(CRR)**: 다른 리전으로 객체를 복사한다. 재해 복구(리전 전체에 걸친 데이터 이중화), 컴플라이언스(특정 지리에 있어야 하는 데이터), 글로벌 사용자를 위한 낮은 지연에 사용.

복제는 백업 솔루션이 아니다 — 소스 버킷에서 객체를 삭제하면 복제본에서도 삭제된다(삭제 마커 복제가 비활성화되지 않는 한). 백업에는 AWS Backup이나 버전 관리와 객체 잠금을 사용하라.

**S3 Object Lock: 컴플라이언스를 위한 불변성**

일부 규정은 데이터가 **불변**이어야 한다고 요구한다 — 한 번 쓰면, 지정된 기간 동안 수정하거나 삭제할 수 없다.

**S3 Object Lock**은 WORM(Write Once, Read Many) 스토리지를 구현한다:

**보관 기간**: 지정된 기간 동안 객체를 삭제하거나 덮어쓸 수 없다.

**법적 보류**: 법적 보류가 명시적으로 제거될 때까지 보관 기간에 관계없이 객체를 삭제할 수 없다.

규제 산업에 S3 Object Lock을 사용하라: 금융 레코드(SEC 규칙 17a-4), 의료 레코드(HIPAA), 컴플라이언스 아카이브.

## 장점과 한계

**S3 스토리지 계층이 중요한 이유**:

- 실제로 접근하는 것에 대한 내구성이나 가용성을 희생하지 않고 상당한 비용 절감
- 수명주기 정책이 전체 프로세스를 자동화한다 — 운영 부담 없음
- S3 Intelligent-Tiering은 접근 패턴을 예측할 필요를 제거

**복잡해지는 부분**:

- 최소 스토리지 기간 요금이 Glacier 클래스에 적용된다(Glacier Instant의 경우 90일, Deep Archive의 경우 180일) — 일찍 삭제해도 최소 요금이 발생
- 아카이브된 데이터에 자주 접근하면 검색 수수료가 놀랄 수 있다
- 수명주기 전환은 시간이 걸린다 — 규칙이 트리거된 후 객체가 즉시 이동되지 않는다
- Intelligent-Tiering 모니터링 수수료가 수백만 개의 소형 객체를 가진 버킷에 쌓인다

## 요약

- S3에는 일곱 가지 스토리지 클래스가 있다: Standard, Standard-IA, Intelligent-Tiering, One Zone-IA, Glacier Instant Retrieval, Glacier Flexible Retrieval, Glacier Deep Archive.
- **수명주기 정책**은 나이에 따라 스토리지 클래스 사이의 전환을 자동화한다 — 한 번 정의하면, S3가 영원히 처리한다.
- **S3 Intelligent-Tiering**은 실제 접근 패턴에 따라 자동으로 객체를 계층 사이에 이동한다 — 예측 불가능한 워크로드에 사용.
- **멀티파트 업로드**는 5GB보다 큰 객체에 필요하고 100MB보다 큰 것에 권장된다.
- **S3 복제**(SRR 및 CRR)는 버킷과 리전 전체에 걸쳐 객체를 복사한다 — DR, 컴플라이언스, 집계를 위해.
- **S3 Object Lock**은 컴플라이언스 시나리오를 위한 WORM 스토리지를 제공한다.

## 시험 팁

*SAA-C03 도메인: 비용 최적화 아키텍처 설계(도메인 4, 태스크 4.1)*

- **스토리지 클래스 선택 신호**:
  - "자주 접근됨" → Standard
  - "월에 한 번 접근, 즉시 검색 필요" → Standard-IA
  - "검색 시간 수 시간 허용, 드물게 접근됨" → Glacier Flexible Retrieval
  - "규제 컴플라이언스, 7년+ 보관, 절대 접근 안 됨" → Glacier Deep Archive
  - "알 수 없거나 변경되는 접근 패턴" → Intelligent-Tiering
- **수명주기 정책 시험 패턴**: "데이터가 나이가 들면서 스토리지 비용 자동으로 줄이기," "90일 후 아카이브로 전환" → 수명주기 정책.
- **Intelligent-Tiering 모니터링 수수료**: 객체당 소액 수수료. 많은 수의 소형 객체의 경우, 절감보다 더 비쌀 수 있다. 시험은 이것을 테스트할 수 있다.
- **CRR 요구사항**: 소스와 대상 버킷 모두에서 버전 관리가 활성화되어야 한다. 소스와 대상은 다른 리전에 있어야 한다.
- **S3 Object Lock**: "WORM," "불변," "SEC 17a-4," "삭제하거나 수정할 수 없음" → Object Lock. 거버넌스 모드(관리자가 재정의 가능). 컴플라이언스 모드(루트 포함 누구도 재정의 불가능).
- **Glacier 복원**: Glacier의 객체는 즉시 사용 가능하지 않다. 접근하려면 S3 Standard로 복사본을 "복원"해야 한다. 복원된 복사본은 임시적이다(기간을 설정). 원본은 Glacier에 남아 있다.

## 연습 문제

**연습 1 — 회상**

S3 Standard-IA와 S3 Glacier Instant Retrieval의 차이를 설명하라. 각각을 적합하게 만드는 접근 패턴은 무엇인가?

*(힌트: 데이터에 얼마나 자주 접근하고 접근할 때 얼마나 빨리 필요한지 생각해보라.)*

**연습 2 — 시험 연습**

*시나리오*: 회사가 매일 500GB의 애플리케이션 로그를 생성한다. 로그는 처음 7일 동안 디버깅 및 모니터링을 위해 많이 쿼리된다. 7일 후, 로그가 필요하면 30분 내에 사용 가능해야 한다. 1년 후, 로그는 컴플라이언스를 위해 보관해야 하지만 절대 접근되지 않는다. 회사는 스토리지 비용을 최소화하면서 이러한 요구사항을 충족해야 한다.

다음 중 이 요구사항을 가장 잘 충족하는 S3 수명주기 정책은?

A) S3 Standard에 7일 저장; 7일 후 S3 Glacier Deep Archive로 전환; 365일 후 만료  
B) S3 Standard에 7일 저장; 7일 후 S3 Standard-IA로 전환; 365일 후 S3 Glacier Flexible Retrieval로 전환  
C) 첫날부터 모든 로그를 S3 Intelligent-Tiering에 저장  
D) S3 Standard에 7일 저장; 7일 후 S3 Glacier Instant Retrieval로 전환; 365일 후 S3 Glacier Deep Archive로 전환

**힌트 1**: "30분 내에 사용 가능"은 어떤 스토리지 클래스를 제외하는가?

**힌트 2**: Glacier Deep Archive는 검색에 12시간이 걸린다 — "30분" 요구사항을 충족하지 않는다.

**힌트 3**: 365일 후, 검색 시간이 중요하지 않다(절대 접근 안 됨), 그래서 가장 저렴한 옵션이 적용된다.

**답**: D

**설명**: S3 Standard가 7일 동안 자주 접근하는 것을 처리한다. Glacier Instant Retrieval이 7-365일 동안 밀리초 접근을 제공한다 — "30분" 요구사항을 Standard-IA보다 훨씬 저렴한 비용으로 충족. 365일 후, Glacier Deep Archive가 절대 접근되지 않는 데이터에 가장 저렴한 옵션이다.

**왜 A가 아닌가?** Glacier Deep Archive는 검색에 12시간이 걸린다 — "30분 가용성" 요구사항을 7-365일 기간에 충족하지 않는다.

**왜 B가 아닌가?** Standard-IA가 7일 후 작동하지만, Glacier Instant Retrieval이 훨씬 더 저렴하다. Standard-IA는 자주 접근하지 않는 데이터를 위한 것이 더 적합하다 — 여기서 데이터는 7일 이후 드물게 접근한다.

**왜 C가 아닌가?** Intelligent-Tiering은 모니터링 수수료가 있고 예측 가능한 접근 패턴을 가진 대용량 로그에 명시적 수명주기 규칙만큼 비용 효율적이지 않을 수 있다.

*SAA-C03 도메인: 비용 최적화 아키텍처 설계 — 태스크 4.1*

**연습 3 — 아키텍처 과제** *(선택 사항)*

Nimbus에는 다른 특성을 가진 세 가지 유형의 S3 데이터가 있다:

- 레스토랑 사진: 한 번 업로드되고, 고객이 여러 번 접근하며, 절대 삭제되지 않음
- 주문 영수증: 첫 달에 고객이 접근하고, 세금 목적으로 7년 보관
- 분석 내보내기: 매일 생성되고, 다음 주에 분석되고, 2년 보관

각각을 위한 수명주기 정책을 설계하라. 레스토랑 사진의 경우, Intelligent-Tiering이 의미가 있는가? 주문 영수증의 경우, 1개월~7년 창을 커버하는 스토리지 클래스는 무엇인가? 분석 내보내기의 경우, 다른 접두어에 다른 정책을 적용하기 위해 버킷을 어떻게 구조화하겠는가?

*(단 하나의 정답은 없다. 실제 데이터를 위한 스토리지 계층 선택을 연습하는 것이 목표다.)*
