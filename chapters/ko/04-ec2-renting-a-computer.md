# 챕터 4: 다른 사람의 건물에 있는 컴퓨터

CPU 그래프는 배경 음악이 되어 있었습니다.

Tom의 노트북이 책상 한구석에 열린 채로 놓여 있었고, CloudWatch가 매 분마다 새로고침되며, 가동률 선이 무언가가 열심히 일하고 있음을 뜻하는 기울기로 올라가고 있었습니다. Maya는 사흘 전에 그것을 알아챘고 아무에게도 말하지 않았습니다. 대신 주문 대기열을 지켜보고 있었습니다.

IAM은 자리를 잡았습니다. 자격 증명은 정돈되었습니다. Priya는 모든 것에 MFA를 걸어 두었습니다. 팀은 처음으로, 자신들이 약간은 책임감 있게 행동하고 있다고 느꼈습니다. 하지만 책임감이 Maya가 지켜보던 문제를 해결해 주지는 않았습니다: 주문 대시보드의 숫자가 올라가는 동안 CPU 선도 함께 올라가고 있었습니다.

Nimbus 앱은 Leo가 별생각 없이 시작한 인스턴스에서 돌아가고 있었습니다 — 아무도 리전이 무엇인지 알기 전에 그가 "어딘가에 배포한" 그것이요.

그것은 투자자에게 데모를 보여 주기에는 괜찮았습니다. Maya가 "출시"를 누르고 첫 주에 200건의 가입이 들어왔을 때는 괜찮지 않았습니다 — 매일 47개의 식당이 활발하게 주문을 받고 있었으니까요. Leo의 즉흥적인 인스턴스가 이제 실제 주문, 실제 메뉴, 실제 고객을 처리하고 있었습니다 — 우연히 선택되고, 기본값으로 크기가 정해지고, AWS를 타이핑하며 배워 가던 사람이 구성한 기계가요.

"우리에게는 서버가 필요해요," Maya가 말했습니다. "진짜 서버요. 누군가 실제로 의도를 가지고 고른 서버요."

Tom이 CPU 그래프를 보았습니다. 그 선은 방 건너편에서도 보였습니다.

그것이 그들이 컴퓨터를 임대한다는 것이 실제로 무엇을 의미하는지 살펴보기 시작한 때였습니다.

**아무도 설명하지 않는 추상화**

사람들이 자기 애플리케이션이 "클라우드에서 실행된다"고 말할 때, 보통은 가상 머신에서 실행된다는 뜻입니다 — 전용 하드웨어로 물리적으로 존재하지는 않지만, 모든 면에서 그런 것처럼 동작하는 컴퓨터요.

그 메커니즘은 이렇습니다.

AWS 데이터 센터의 물리적 서버에는 많은 리소스가 있습니다: CPU 코어, 메모리, 디스크, 네트워크 대역폭. AWS는 그 물리적 서버를 가져다 **하이퍼바이저(hypervisor)**라는 소프트웨어를 사용해 나눕니다 — 건물 관리인처럼 물리적 서버의 리소스를 여러 가상 입주자에게 나누어 주는 소프트웨어죠. 하이퍼바이저는 여러 가상 머신을 만드는데, 각각은 자기 전용 CPU, 메모리, 디스크를 가진 것처럼 보이지만 — 실제로는 기반 물리적 하드웨어를 공유합니다.

집을 사는 것이 아니라 큰 건물에서 아파트를 임대하는 것처럼 생각해 보십시오.

건물 소유주(AWS)는 물리적 구조를 유지합니다 — 배관, 전기, 보안. 여러분은 한 세대를 얻습니다. 원하는 대로 꾸밉니다. 매월(또는 매시간) 비용을 냅니다. 더 많은 공간이 필요하면, 더 큰 세대로 이사합니다. 이사를 나가면, 비용 지불을 멈춥니다.

그 가상 머신 임대 각각이 AWS가 **EC2 인스턴스** — Elastic Compute Cloud — 라고 부르는 것입니다.

EC2는 Elastic Compute Cloud의 약자입니다. "elastic(탄력적)" 부분이 중요한데, 거기에 대해서는 다룰 것입니다. 지금은: EC2 인스턴스는 여러분이 시간 단위로 임대하는 컴퓨터입니다. 운영체제, 네트워크 연결, 컴퓨팅 파워를 가집니다. 물리적 서버가 그러듯이 여러분의 애플리케이션을 실행합니다.

**인스턴스 선택하기: 크기가 중요하다**

모든 EC2 인스턴스가 같은 것은 아닙니다. AWS는 수백 가지 인스턴스 유형을 제공하며, 무엇에 최적화되어 있는지에 따라 패밀리로 구성되어 있습니다.

**범용**(예: `t3`, `m6i`): 균형 잡힌 CPU와 메모리. 대부분의 웹 애플리케이션에 좋은 기본 선택입니다. `t3` 패밀리는 버스트 가능형(burstable)입니다 — 낮은 가동률 기간 동안 CPU 크레딧을 축적하고 버스트 동안 그것을 씁니다. 개발 환경과 변동하는 CPU 수요를 가진 워크로드에 훌륭합니다. `m6i` 패밀리는 일관되고 버스트 불가능한 성능을 제공합니다 — 지속적인 CPU 수요를 가진 프로덕션 워크로드에 더 좋습니다.

**컴퓨팅 최적화**(예: `c7g`): 메모리 대비 더 많은 CPU. 비디오 인코딩, 과학적 모델링, 배치 처리에 좋습니다. `c7g`의 "g" 접미사는 인스턴스가 AWS Graviton 프로세서를 사용한다는 뜻입니다 — AWS가 자체 설계한 ARM 기반 칩으로, 많은 워크로드에서 동등한 x86 인스턴스보다 더 나은 가격 대비 성능을 제공합니다.

**메모리 최적화**(예: `r7i`): CPU 대비 더 많은 메모리. 데이터베이스, 캐싱, 인메모리 분석에 좋습니다. 더 많은 데이터를 RAM에 유지함으로써 성능이 극적으로 향상되는 데이터베이스를 돌린다면, R 패밀리가 올바른 출발점입니다.

**스토리지 최적화**(예: `i3`): 고속 로컬 스토리지. 매우 빠른 디스크 I/O가 필요한 데이터 집약적 워크로드에 좋습니다. 이 인스턴스의 로컬 NVMe 스토리지는 EBS보다 상당히 빠릅니다 — 하지만 그것은 또한 일시적(ephemeral)입니다. 임시 데이터에 사용하고, 잃어버릴 수 없는 것에는 사용하지 마십시오.

**가속 컴퓨팅**(예: `p4`): GPU가 부착됨. 머신러닝 훈련과 그래픽 렌더링에 좋습니다. 이 인스턴스는 비쌉니다 — `p3.8xlarge`는 시간당 12달러를 넘습니다 — 하지만 GPU 병렬성의 이점을 보는 워크로드에는 대체재가 없습니다.

각 패밀리에는 크기가 있습니다. `t3.micro`는 가상 CPU 2개와 메모리 1GB를 가집니다. `t3.xlarge`는 가상 CPU 4개와 16GB를 가집니다. `t3.2xlarge`는 다시 두 배가 됩니다. 명명 패턴은 일관됩니다: 접미사는 `nano`, `micro`, `small`, `medium`, `large`, `xlarge`, `2xlarge`, `4xlarge`, `8xlarge`, 그리고 그 너머로 갑니다.

Leo는 `t3.micro`를 선택했었습니다.

"`t3.micro`가 사용자 몇 명을 감당할 수 있어?" Tom이 물었습니다. "그리고 더 큰 건 얼마나 더 비싸?"

"애플리케이션에 따라 다르죠," Leo가 말했습니다. "하지만 이미지 업로드와 데이터베이스 쿼리를 돌리는 동시 사용자 백 명은 아마 아닐 거예요."

"그게 한 달에 얼마나 들어?" Tom이 인스턴스 유형 비교 페이지를 보며 물었습니다.

Leo가 AWS 가격 페이지를 띄웠습니다. t3.micro는 한 달에 약 8달러였습니다. t3.small은 17달러였습니다. t3.medium은 33달러였습니다. t3.large는 약 60달러였습니다. 위로 올라갈수록 격차가 빠르게 벌어졌습니다 — 선형이 아니라, 각 크기 단계마다 대략 두 배가 되었습니다. Tom은 숫자를 적으며, 각 크기 단계가 메모리를 두 배로 늘린다는 점을 — 하지만 신기하게도 CPU 수는 아니라는 점을 — 적어 두었습니다. micro부터 large까지 모든 t3는 같은 2 vCPU를 가졌습니다; 그 수는 xlarge가 되어서야 늘어났습니다. 각 단계가 메모리를 두 배로 늘렸습니다; **CPU 크레딧 기준선(CPU credit baseline)** — 인스턴스가 버스트 크레딧을 소진하지 않고 지속적으로 사용할 수 있는 그 vCPU의 몫 — 도 증가했지만, 모든 단계마다 그런 것은 아니었습니다.

Tom은 화이트보드에 "t3.micro"라고 쓰고 그 옆에 슬픈 얼굴을 그렸습니다.

**적정 크기 조정 대화**

t3.micro는 금요일 밤 트래픽이 그것을 짓뭉개기 전까지 약 한 달을 버텼습니다. Leo는 서둘러 업그레이드했습니다 — 곧장 t3.large로요, 너무 작은 것보다는 너무 큰 것이 더 안전하다는 논리로요. t3.large로 옮긴 지 2주 후, Tom이 무언가를 짚었습니다.

"CPU가 9%예요," 그가 말했습니다. "평균이요. 지난 7일 동안요."

Leo가 CloudWatch 그래프를 보았습니다. 평균 CPU 9%. 금요일 저녁에 어쩌면 35%의 피크. 나머지 시간에는: 간신히 째깍거리는 정도.

"우리는 한 달에 60달러짜리 서버를," Tom이 말했습니다. "용량의 9%로 돌리고 있어요."

"하지만 금요일 피크는요?" Leo가 말했습니다. "여유 공간이 필요해요."

"금요일 피크는 35%를 쳐요," Tom이 말했습니다. "t3.small은 같은 2 vCPU를 가지고 있어요 — 더 작은 건 크레딧 기준선이에요, 약 20% 지속이요. 우리는 평균 9%예요. 그건 우리가 매일 종일 CPU 크레딧을 적립하고, 금요일 밤 몇 시간 동안 그중 일부를 쓴다는 뜻이에요. `CPUCreditBalance` 계산을 확인해 봤어요 — 잔액이 0에 가까워지는 일이 결코 없어요. 한 달에 17달러예요. 여유 공간이 있어요."

Leo가 숫자를 보았습니다. 그래프를 보았습니다. 과도하게 프로비저닝했고 그것을 아는 엔지니어의 불편함을 느꼈습니다.

"하지만 급증이 오면요?" 그가 말했습니다.

"그러면 지표가 아프기 전에 우리에게 알려 줄 거예요," Priya가 말했습니다. "그리고 결국 우리는 Auto Scaling을 설정할 거예요 — 그게 말 그대로 그것의 용도예요. 시스템이 자동으로 인스턴스를 추가할 수 있게 되면 급증에 대비해 수동으로 프로비저닝할 필요가 없어져요."

그들은 t3.small로 줄였습니다. 월 청구서가 40달러 떨어졌습니다. 1년이면 480달러였습니다 — 아무것도 아닌 게 아니죠, 특히 스타트업에게는요. Tom은 2주 동안 이 점을 짚을 기회를 기다려 온 사람의 조용한 만족감으로 그것을 스프레드시트에 기록했습니다.

이 패턴에는 이름이 있습니다: **적정 크기 조정(right-sizing)**. 그것은 상상된 최악의 경우가 아니라 실제 워크로드에 인스턴스 크기를 맞추는 것을 의미합니다. AWS Compute Optimizer와 CloudWatch 지표 같은 AWS 도구는 적정 크기 조정을 추측이 아니라 데이터 기반 결정으로 만듭니다.

**AMI: 당신의 기계의 시작 상태**

EC2 인스턴스를 시작하기 전에, 여러분은 그것의 운영체제와 초기 구성을 선택합니다. AWS에서, 이것은 **Amazon Machine Image**(AMI)라고 불립니다.

AMI는 템플릿입니다. 그것은 다음을 정의합니다:

- 운영체제(Amazon Linux, Ubuntu, Windows Server 등)
- 사전 설치된 소프트웨어
- 초기 디스크 상태

AMI에서 인스턴스를 시작하면, AWS는 그 템플릿의 새 복사본을 여러분만을 위해 만듭니다. 여러분 자신의 AMI를 만들 수도 있습니다 — 서버를 정확히 원하는 방식으로 구성하면, 그 상태를 사용자 정의 AMI로 "저장"하고 그것을 사용해 동일한 서버를 빠르게 시작할 수 있습니다. 이것이 대규모로 일관된 환경을 배포하는 방법입니다.

AMI를 레시피로 생각해 보십시오. 레시피는 요리를 묘사합니다. 레시피를 따를 때마다, 같은 요리를 얻습니다. 요리를 영구적으로 바꾸고 싶다면, 레시피를 업데이트합니다.

AWS는 AMI의 마켓플레이스를 제공합니다 — 일부는 AWS가 유지관리하고(Amazon Linux 2, Amazon Linux 2023), 일부는 주요 Linux 배포판이 유지관리하며(Ubuntu, Red Hat, SUSE), 일부는 타사 공급업체에서 옵니다(사전 구성된 데이터베이스 서버, 보안 장비, 상용 소프트웨어). 대부분의 웹 애플리케이션에는, AWS가 유지관리하는 Amazon Linux AMI나 Ubuntu LTS AMI가 올바른 출발점입니다.

Nimbus를 위해, Leo는 최신 Amazon Linux 2023 베이스에서 시작해 Node.js 런타임, 애플리케이션의 시스템 의존성, 애플리케이션 프로세스를 위한 사전 생성된 서비스 파일을 추가한 사용자 정의 AMI를 만들었습니다. 이 AMI에서 시작된 새 인스턴스는 90초 이내에 트래픽을 처리하기 시작했습니다 — UserData 스크립트를 사용해 모든 것을 처음부터 설치할 때의 4분 부팅 시간보다 상당히 빨랐습니다.

트레이드오프가 있습니다: 사용자 정의 AMI는 유지관리되어야 합니다. 시스템 의존성이나 런타임 버전을 업데이트할 때마다, AMI를 다시 빌드해야 합니다. AMI가 오래되도록 방치하는 팀은 구식 소프트웨어로 인스턴스를 돌리고 있는 자신을 발견합니다 — 보안 위험이죠. Priya는 월간 엔지니어링 체크리스트에 "최신 패키지로 AMI 재빌드"를 넣었습니다.

"AMI를 저장하는 비용은 얼마야?" Tom이 물었습니다.

AMI는 EBS 스냅샷으로 저장됩니다 — AMI의 크기에 대해 EBS 스냅샷 요율(GB당 월 약 0.05달러)을 냅니다. Nimbus 애플리케이션 스택을 가진 일반적인 Amazon Linux AMI는 약 4GB였습니다. GB당 0.05달러로: AMI당 한 달에 0.20달러. 롤백 목적으로 다섯 개의 과거 AMI를 보관하면: 월 1달러. 의미 있는 비용이 아닙니다.

**UserData: 부트스트랩 스크립트**

애플리케이션 코드가 바뀔 때마다 새 AMI를 빌드하는 것을 피하려 할 때 Leo가 발견한, EC2의 구성 옵션이 하나 더 있습니다.

EC2 인스턴스를 시작할 때, **UserData 스크립트** — 인스턴스가 처음 시작될 때 자동으로 실행되는 셸 스크립트 — 를 제공할 수 있습니다. 그것은 인스턴스가 "준비됨"으로 간주되기 전에, 루트로 실행됩니다.

Nimbus의 경우, UserData 스크립트는 대략 이렇게 생겼습니다:

```bash
#!/bin/bash
yum update -y
yum install -y nodejs npm git
git clone https://github.com/nimbus-app/server.git /opt/nimbus
cd /opt/nimbus
npm install
systemctl enable nimbus
systemctl start nimbus
```

그 스크립트는 Node.js를 설치하고, 최신 애플리케이션 코드를 가져오고, 의존성을 설치하고, 애플리케이션 서비스를 시작합니다. 베이스 AMI에서 시작되는 모든 새 인스턴스는 이 스크립트를 실행하고 현재 버전의 애플리케이션이 설치된 채로 올라옵니다 — 자동으로요.

이 접근 방식은 AMI가 단순하게(그저 베이스 OS) 유지되고, UserData가 애플리케이션 설정을 처리한다는 것을 의미합니다. 트레이드오프: UserData 스크립트는 실행하는 데 시간이 걸립니다. 인스턴스가 부팅되어 준비되기까지 3분에서 5분이 걸릴 수 있습니다. 시작 시간이 중요한 애플리케이션 — 새 인스턴스가 빠르게 준비되어야 하는 Auto Scaling — 에는, 애플리케이션을 사용자 정의 AMI에 미리 구워 넣는 것이 부팅 시간을 상당히 줄입니다.

"괜찮을 거예요," Leo가 말했습니다, Priya가 부팅 시간에 대해 물었을 때요.

"부팅 시간이 얼마예요?" 그녀가 물었습니다.

"4분이요."

"그리고 그 4분 동안, 인스턴스는 실행되지만 트래픽을 처리하지는 않는 거죠?"

"네."

"그러니까 갑작스러운 트래픽 급증 동안, 새 인스턴스가 아직 도움이 안 되는 4분이 생길 수 있다는 거네요?"

Leo가 자기 UserData 스크립트를 보았습니다. 그는 사용자 정의 AMI를 빌드하는 방법을 찾아보기 시작했습니다.

**키 페어: 서버에 접근하는 올바른 방법**

지난 챕터의 "Admin123" 재앙을 기억하십니까?

EC2 인스턴스에 로그인하는 올바른 방법은 **키 페어(key pair)**입니다.

키 페어는 암호화 쌍입니다: 공개 키(AWS가 서버에 저장)와 개인 키(여러분이 다운로드하고 비밀로 유지하는 파일). 로그인하려면, 여러분의 개인 키로 SSH — 안전한 프로토콜 — 를 사용합니다. 비밀번호가 없습니다. 개인 키를 잃어버리면, 접근권을 잃습니다. SSH에는 "비밀번호를 잊으셨나요"가 없습니다.

이것이 중요한 이유는 키 페어가 다음과 같기 때문입니다:

- 여러분에게 고유함
- 암호학적으로 추측 불가능함
- AWS가 저장하지 않음(여러분이 개인 키를 보관)
- 취소하기 쉬움(서버에서 키를 삭제하고, 새 쌍을 생성)

Priya는 이미 Nimbus 서버에 키 기반 접근을 설정해 두었습니다. Admin123 서버는 폐기되었습니다. 아무도 그것을 슬퍼하지 않았습니다.

"그리고 누군가 침입하려고 전송 중인 키 페어를 가로채면요?" Priya가 물었습니다. 그녀는 이미 답을 정리해 두었습니다: 개인 키는 결코 네트워크를 통해 이동하지 않습니다. 한 번 다운로드합니다. 로컬에 보관합니다. 그것은 결코 여러분의 기계를 떠나지 않습니다.

**키 페어를 잃어버리면 어떻게 되는가**

Leo는 3주 차에 이 질문을 했습니다, 아직 키 페어를 잃어버리지는 않았지만 그것을 생각하고 있는 사람 특유의 에너지로요.

"개인 키 파일을 잃어버리면, 어떻게 되죠?"

"인스턴스에 대한 SSH 접근을 잃어요," Priya가 말했습니다.

"영구적으로요?"

"꼭 그런 건 아니에요. 하지만 복구 과정이 불쾌해요."

복구 과정: 인스턴스를 중지하고, 그것의 루트 EBS 볼륨을 분리하고, 여러분이 접근권을 *가진* 다른 인스턴스에 그것을 연결하고, 볼륨을 마운트하고, 마운트된 볼륨의 `authorized_keys` 파일에 새 공개 키를 추가하고, 그것을 분리해 원래 인스턴스에 다시 연결하고, 재시작합니다.

이것은 작동합니다. 30분에서 60분이 걸리고 신중한 실행을 요구합니다. 한 단계만 잘못해도 상황을 더 나쁘게 만들 수 있습니다.

대안은, 여러분의 애플리케이션이 루트 볼륨에 중요한 것을 아무것도 저장하지 않는다면(이 책의 조언을 따라 데이터를 S3와 EBS에 저장해 왔기 때문에): 인스턴스를 종료하고 AMI에서 새 인스턴스를 시작합니다. 그렇게 할 때 새 키 페어를 생성합니다.

"개인 키를 안전한 어딘가에 저장하세요," Priya가 말했습니다. "그리고 절대 EC2 인스턴스에는 두지 마세요."

Leo가 `AWS_keys`라고 라벨이 붙은 자기 바탕화면 폴더를 보았습니다. 그런 다음 Priya를. 그런 다음 그 폴더를 자기 암호화된 비밀번호 관리자로 옮겼습니다.

**보안 그룹: 당신의 인스턴스의 방화벽**

EC2 인스턴스가 시작될 때, 그것에는 **보안 그룹(security group)**이 필요합니다 — 어떤 네트워크 트래픽이 그것에 도달할 수 있고 어떤 트래픽을 내보낼 수 있는지를 제어하는 가상 방화벽입니다.

보안 그룹에는 두 세트의 규칙이 있습니다: **인바운드**(들어오는 트래픽)와 **아웃바운드**(나가는 트래픽).

기본적으로, 새 보안 그룹은 모든 인바운드 트래픽을 차단하고 모든 아웃바운드 트래픽을 허용합니다. 특정 소스에 특정 포트를 열기 위해 인바운드 규칙을 추가합니다.

Nimbus 웹 서버를 위해, Priya는 다음과 같이 구성했습니다:

- `0.0.0.0/0`(전체 인터넷)에서 TCP 포트 443(HTTPS) 허용
- `0.0.0.0/0`(전체 인터넷)에서 TCP 포트 80(HTTP) 허용(애플리케이션에서 443으로 리디렉션됨)
- 사무실 IP 주소에서만 TCP 포트 22(SSH) 허용 — 인터넷에서는 아님

"잠깐 — 그런데 *왜* SSH를 사무실 IP로만 제한하죠?" Maya가 물었습니다.

"SSH가 전체 인터넷에 열려 있으면," Priya가 말했습니다. "자동화된 봇이 하루 24시간 자격 증명 조합을 시도하며 포트 22를 두드릴 거예요. 우리 로그가 실패한 시도로 가득 찰 거예요. 그리고 SSH 데몬 자체에 언젠가 취약점이 생기면, 세상의 모든 공격자가 그것을 악용하려 할 수 있어요."

"하지만 Leo가 집에서 로그인해야 하면요?"

"VPN이요," Priya가 말했습니다.

Leo는 이미 VPN을 설정해 두었습니다. 그는 전에 이 질문을 받아 본 사람의 표정을 짓고 있었습니다.

데이터베이스는 여전히 애플리케이션과 같은 기계에 살고 있었습니다 — 하지만 Priya는 그것이 그렇지 않게 될 날을 위해 별도의 보안 그룹을 준비했습니다: 데이터베이스 포트는 웹 서버의 보안 그룹에서 오는 트래픽에만 열림 — 인터넷에서는 아님, (직접 DB 접근을 위한) SSH에서도 아님, 그 밖의 어디에서도 아님. 그동안, 그녀는 공유 인스턴스의 보안 그룹이 데이터베이스 포트를 인터넷에 전혀 노출하지 않도록 확실히 했습니다. 데이터베이스는 그것을 필요로 하는 애플리케이션을 제외한 모든 것에 보이지 않을 것이었습니다.

데이터베이스에 직접 도달하려면, 공격자는 먼저 웹 서버를 침해해야 했습니다. 그것이 방어의 첫 번째 계층이었습니다.

"그리고 두 번째 계층은요?" Tom이 물었습니다.

"데이터베이스를 위한 IAM 인증. 그리고 전송 중 암호화요."

그녀는 둘 다 설정 체크리스트에 추가했습니다.

**EC2 인스턴스 메타데이터와 IMDSv2**

입문 콘텐츠에서는 좀처럼 설명되지 않더라도, 실제로 중요한 EC2 보안 조각이 하나 더 있습니다.

애플리케이션이 EC2 인스턴스에서 실행될 때, 그것은 `http://169.254.169.254/latest/meta-data/`에 있는 특별한 내부 엔드포인트를 쿼리하여 인스턴스에 대한 정보를 검색할 수 있습니다: 인스턴스 ID, 리전, 가용 영역, 그리고 — 결정적으로 — 연결된 IAM 역할과 관련된 임시 IAM 자격 증명.

이것이 EC2 인스턴스의 애플리케이션이 하드코딩된 자격 증명 없이 AWS 서비스를 호출하는 방법입니다. 그것은 메타데이터 서비스에 묻습니다: "지금 어떤 자격 증명을 사용해야 하나요?" 메타데이터 서비스는 만료되고 자동으로 교체되는 임시 자격 증명을 반환합니다.

보안 문제: 이 메타데이터 서비스의 구버전(IMDSv1)은 인스턴스의 어떤 프로세스에서 오는 어떤 요청에도 응답하곤 했습니다. 애플리케이션에 서버 측 요청 위조(SSRF) 취약점 — 공격자가 서버로 하여금 공격자가 선택한 URL을 가져오게 할 수 있는 버그 — 이 있다면, 공격자는 그 취약점을 사용해 `http://169.254.169.254/latest/meta-data/iam/security-credentials/`를 가져와 인스턴스의 IAM 자격 증명을 검색할 수 있었습니다.

이 공격은 실제 침해에 사용되었습니다.

**IMDSv2**(Instance Metadata Service 버전 2)는 메타데이터 서비스가 응답하기 전에 세션 토큰을 요구함으로써 이것을 고칩니다. 토큰은 PUT 요청을 통해 얻습니다. 일반적으로 GET 요청을 사용하는 SSRF 공격은 PUT 단계를 완료할 수 없습니다 — 그래서 토큰을 얻을 수 없고, 메타데이터가 반환되지 않습니다.

"우리 IMDSv2를 활성화해야 하나요?" Leo가 물었습니다.

"이제 새 인스턴스에는 기본값이에요," Priya가 말했습니다. "하지만 기존 인스턴스에는, 직접 옵트인해야 해요."

그녀는 그날 오후 모든 기존 Nimbus 인스턴스에서 그것을 활성화했습니다.

**인스턴스 수명 주기: 영원하지 않다**

이것은 많은 초보자가 놓치는 것입니다.

EC2 인스턴스는 기본적으로 영구적이지 않습니다. 인스턴스를 중지하면, 컴퓨팅 리소스가 해제됩니다. 그것을 다시 시작하면, 다른 물리적 하드웨어에서 실행될 수 있습니다. *인스턴스 자체에*(루트 볼륨에) 저장된 모든 데이터는 중지/시작 주기에서 살아남습니다 — 하지만 퍼블릭 IP 주소는 바뀝니다.

인스턴스를 *종료(terminate)*하면, 그것은 사라집니다. 별도의 스토리지가 연결되어 있지 않은 한(6장에서 다룹니다), 인스턴스의 모든 데이터가 사라집니다.

EC2 인스턴스가 가질 수 있는 네 가지 상태:

**Pending(대기 중)**: 인스턴스가 시작되고 있습니다. 하드웨어가 할당되었지만 부팅을 마치지 못했습니다.

**Running(실행 중)**: 인스턴스가 활성화되어 접근 가능합니다. 여러분은 그것에 대해 비용을 내고 있습니다. 첫 번째 부팅 시, 이것이 UserData 스크립트가 실행되는 시점이기도 합니다.

**Stopping/Stopped(중지 중/중지됨)**: 인스턴스가 종료되었습니다. EBS 루트 볼륨은 보존됩니다. 컴퓨팅에 대해서는 비용을 내지 않지만, 연결된 EBS 스토리지에 대해서는 여전히 비용을 냅니다.

**Shutting-down/Terminated(종료 중/종료됨)**: 인스턴스가 삭제되고 있습니다. EBS 볼륨이 지속되도록 구성하지 않은 한, 그것들의 데이터는 사라집니다.

이 "일시성(ephemerality)"은 사실 버그가 아니라 기능입니다. 그것은 여러분이 서버를 띄우고, 사용하고, 버릴 수 있다는 것을 의미합니다. 그것은 수평 확장을 가능하게 합니다. 하지만 그것은 또한 EC2 인스턴스 *자체에는* 중요한 데이터를 결코 저장해서는 안 된다는 것을 의미합니다.

그러면 데이터는 어디에 사는 걸까요?

별도의 스토리지에요. 다음 두 챕터에서 거기에 도달합니다.

이런 생각이 들 수도 있습니다: 인스턴스가 재시작할 때마다 새 IP 주소를 얻는다면, 여러분의 애플리케이션은 어떻게 안정적인 주소를 유지하는가? AWS에는 Elastic IP라는 해결책이 있습니다 — 여러분이 소유하고 재시작 후에도 동일하게 유지되는 정적 퍼블릭 IP입니다. 비용에 관한 메모: 2024년 2월부터, AWS는 모든 퍼블릭 IPv4 주소에 대해 소액의 시간당 요금을 청구합니다 — Elastic IP(연결되었든 아니든)와 인스턴스의 자동 할당된 퍼블릭 IP 모두에요. 퍼블릭 IPv4는 더 이상 무료가 아니며, 이것은 인스턴스를 로드 밸런서 뒤의 프라이빗 서브넷에 두는 또 하나의 이유입니다.

로드 밸런서 뒤의 애플리케이션 — 모든 프로덕션 웹 애플리케이션의 올바른 아키텍처 — 에는, Elastic IP가 전혀 필요 없습니다. 사용자는 로드 밸런서의 안정적인 DNS 이름에 연결합니다. 로드 밸런서는 VPC 내의 프라이빗 IP 주소로 인스턴스에 연결합니다. 인스턴스는 왔다 갔다 하고, 새 IP를 얻고, 확장되고 축소될 수 있습니다 — 로드 밸런서가 그 모든 것을 투명하게 처리합니다. Elastic IP는 특정 사용 사례를 위한 것입니다: 클라이언트가 IP로 직접 연결하는 서버, 안정적인 주소를 가진 배스천 호스트, 어떤 특정 이유로 로드 밸런서 뒤에 있지 않은 애플리케이션.

Leo는 처음에 Nimbus 웹 서버에 Elastic IP를 사용할 계획이었습니다. Priya는 로드 밸런서가 있으면 웹 서버의 IP 주소가 외부 클라이언트에게 무관하다는 점을 지적했습니다. 로드 밸런서가 안정적인 DNS 이름을 가졌습니다. 그 뒤의 인스턴스는 설계상 일회용이었습니다.

"그러니까 Elastic IP는 규칙이 아니라 예외를 위한 거네요," Leo가 말했습니다.

"맞아요," Priya가 말했습니다. "그리고 그걸 집으려고 하는 자신을 발견하면, 대신 아키텍처에 로드 밸런서가 있어야 하는지 물어보세요."

**"Elastic"이 의미하는 것**

EC2는 Elastic Compute Cloud의 약자라고 말했습니다. 그것의 무엇이 탄력적일까요?

두 가지입니다:

**수직적 탄력성**: 인스턴스의 크기를 바꿀 수 있습니다. 인스턴스를 중지하고, `t3.micro`에서 `t3.xlarge`로 바꾸고, 재시작합니다. 더 많은 CPU와 메모리, 같은 애플리케이션, 같은 설정.

**수평적 탄력성**: 더 많은 인스턴스를 추가할 수 있습니다. 하나의 큰 서버 대신, 로드 밸런서 뒤에서 열 개의 중간 서버를 돌립니다. 트래픽이 떨어지면, 인스턴스를 제거하고 그것에 대한 비용 지불을 멈춥니다.

두 접근 방식 모두 "서버 하나, 너무 많은 트래픽" 문제를 해결합니다. 그것들은 서로 다른 트레이드오프를 가지며, 7장에서 Auto Scaling을 이야기에 추가할 때 탐구합니다.

핵심 통찰: EC2로, 컴퓨팅 파워는 여러분이 *사는* 것이 아니라 *다이얼을 돌리는* 것입니다. 더 필요하다? 다이얼을 올립니다. 덜 필요하다? 내립니다. 그에 맞춰 비용을 냅니다.

Maya가 인스턴스 유형 표를 보았습니다. "그냥 서버를 더 크게 만들 수 있다면, 왜 중간 것 열 개로 번거롭게 해요?"

"왜냐면," Leo가 말했습니다. "하나의 큰 서버도 여전히 하나의 서버니까요. 그게 다운되면, 모든 게 다운돼요. 중간 서버 열 개는 하나가 실패해도 아홉 개가 계속 돌아간다는 뜻이에요."

"그리고," Priya가 덧붙였습니다. "서버를 재시작하지 않고는 더 크게 만들 수 없어요. 작은 것 열 개는 돌아가는 것을 건드리지 않고 더 추가할 수 있다는 뜻이에요."

Tom은 이미 노트에 "재시작 = 다운타임"이라고 적어 두었습니다.

## 강점과 한계

**EC2가 강력한 이유**:

- 완전한 제어. 여러분이 OS, 소프트웨어, 구성을 선택합니다. 그것은 여러분의 컴퓨터입니다.
- 유연한 크기 조정. 모든 사용 사례에 걸친 수백 가지 인스턴스 유형.
- 관리할 하드웨어 없음. AWS가 물리적 계층을 처리합니다.
- Amazon Linux, Windows, Ubuntu AMI에 대해 60초 최소의 초당 과금. (RHEL과 SUSE 같은 일부 상용 Linux AMI는 여전히 시간당 과금됩니다 — AMI의 과금 조건을 확인하십시오.) 인스턴스를 중지하면, 비용 지불을 멈춥니다.
- 모든 것과 함께 작동합니다. EC2는 대부분의 다른 AWS 서비스가 그 위에 구축된 기초입니다.
- 여러 가격 모델(온디맨드, 예약, 스팟)이 예측 가능하거나 유연한 워크로드에 상당한 비용 최적화를
  가능하게 합니다 — 27장에서 자세히 다룹니다.

**복잡해지는 부분**:

- 운영체제를 패치하고 업데이트하는 책임은 여러분에게 있습니다. (공동 책임
  모델 — 이것이 여러분의 몫인 "클라우드 안의" 부분입니다.)
- OS 패치는 선택 사항이 아닙니다. 패치되지 않은 EC2 인스턴스는 클라우드 침해에서 가장 흔한
  공격 벡터 중 하나입니다. AWS Systems Manager Patch Manager가 이것을 자동화할
  수 있습니다 — 하지만 여러분이 그것을 구성하고 모니터링해야 합니다.
- 대규모 EC2 관리는 잠재적으로 수천 대의 기계에 걸쳐 인스턴스 상태, AMI, 보안 패치,
  수명 주기를 관리하는 것을 의미합니다. 그것은 운영 부담입니다.
- EC2가 모든 것에 올바른 답인 것은 아닙니다. 드물게 실행되는 이벤트 기반 코드에는,
  Lambda(20장)가 더 저렴하고 단순합니다. 컨테이너화된
  워크로드에는, ECS와 EKS(21장)가 더 나은 리소스 효율성을 제공합니다.
- 사용하지 않는 인스턴스도 여전히 비용이 듭니다. 인스턴스를 중지하면, 컴퓨팅에 대한 비용 지불을
  멈춥니다 — 하지만 스토리지가 연결되어 있으면, 그것에 대해서는 여전히 비용을 냅니다.

**EC2를-언제-사용하지-않을지 판단**: EC2는 여러분에게 최대의 제어를 줍니다 — 하지만 제어에는 운영 비용이 있습니다. 여러분이 돌리는 모든 EC2 인스턴스는 패치하고, 모니터링하고, 결국 교체해야 하는 무언가입니다. 드물게 실행되는 애플리케이션(Lambda가 더 저렴), 수십 또는 수백 개의 인스턴스로 수평 확장해야 하는 애플리케이션(컨테이너가 더 효율적), 또는 데이터베이스와 기타 관리형 워크로드(RDS, ElastiCache)에는, 완전 관리형 서비스가 적당한 비용 프리미엄으로 상당한 운영 부담을 없앱니다. EC2는 그것이 제공하는 제어가 필요할 때 올바른 선택입니다 — 기본값이 아니라요.

Priya에게는 휴리스틱이 있었습니다: "우리가 필요한 것을 하는 관리형 서비스로 만족할 수 있다면, 관리형 서비스를 쓰세요. 관리형 옵션이 존재하지 않거나 맞지 않을 때 EC2를 쓰세요."

Leo가 처음에 이에 반발했습니다. "하지만 EC2는 우리에게 더 많은 옵션을 줘요."

"옵션은 부담이에요," Priya가 말했습니다. "우리는 모든 옵션이 필요하지 않아요. 우리는 안정적으로 유지관리되는 올바른 구성이 필요해요."

**EC2 배치 그룹: 인스턴스가 어디에 놓이는지 제어하기**

EC2는 여러분에게 인스턴스가 무엇인지 — 그것의 크기, OS, 구성 — 에 대한 제어를 줍니다. 그것은 또한 **배치 그룹(placement groups)**이라는 기능을 통해 인스턴스가 물리적으로 *어디에* 놓이는지에 대한 제한된 제어도 줍니다.

기본적으로, AWS는 가용성을 최대화하기 위해 인스턴스를 물리적 하드웨어에 분산합니다. 하지만 특정 워크로드에는, 그 기본값을 재정의하고 싶을 수 있습니다 — 인스턴스를 더 가까이 두거나, 그것들이 멀리 떨어져 있도록 보장하기 위해서요.

세 가지 배치 그룹 유형:

**Cluster(클러스터)**: 단일 가용 영역 내에서, 일반적으로 같은 물리적 랙이나 인접한 하드웨어에 인스턴스를 가까이 모읍니다. 그 결과는 그룹 내 인스턴스 간의 가장 낮은 네트워크 지연 시간과 가장 높은 네트워크 처리량입니다 — 인스턴스 간 10Gbps 이상의 네트워크 처리량으로요(이것을 배치 그룹과 무관한 인스턴스별 네트워킹 기능인 Enhanced Networking/ENA와 혼동하지 마십시오). 이것은 HPC(고성능 컴퓨팅), 대규모 ML 훈련 작업, 그리고 인스턴스가 서로에게 데이터를 보내는 데 많은 시간을 쓰는 긴밀하게 결합된 병렬 워크로드를 위한 선택입니다. 트레이드오프는 가용성입니다: 기반 하드웨어 세그먼트가 실패하면, 클러스터의 모든 인스턴스가 동시에 영향을 받을 수 있습니다.

**Partition(파티션)**: 인스턴스를 논리적 파티션에 걸쳐 나누는데, 각 파티션은 자기 자신의 하드웨어 세트 — 별도의 랙, 별도의 전력, 별도의 네트워크 스위치 — 에 위치합니다. 한 파티션 내의 인스턴스는 서로 하드웨어를 공유하지만, 파티션은 결코 다른 파티션과 하드웨어를 공유하지 않습니다. 이 설계는 하드웨어 고장의 폭발 반경을 제한합니다: 랙 하나가 다운되면 한 파티션에 영향을 미치지만 다른 것들에는 미치지 않습니다. 파티션 배치 그룹은 대규모 분산 및 복제 워크로드 — Apache Hadoop, Apache Cassandra, Apache Kafka — 를 위해 만들어졌으며, 거기서는 랙 수준 고장이 전체 클러스터를 다운시키지 않을 만큼 충분한 장애 격리를 원합니다.

**Spread(스프레드)**: 각 인스턴스를 완전히 별개의 기반 하드웨어에 배치합니다. 인스턴스 간 최대 격리. 결코 물리적 호스트를 공유해서는 안 되는(단일 하드웨어 고장이 결코 하나 이상을 다운시켜서는 안 되기 때문에) 다섯 개의 중요한 애플리케이션 인스턴스가 있다면, Spread가 답입니다. 한계: **배치 그룹당 가용 영역당 7개 인스턴스**. Spread는 함께 배치되는 것을 견딜 수 없는 적은 수의 중요한 인스턴스를 위해 설계되었으며, 대규모 플릿을 위한 것이 아닙니다.

"그러니까 Cluster는 속도를 위한 거고, Spread는 격리를 위한 거고, Partition은 약간의 클러스터링과 약간의 격리 둘 다 필요한 분산 시스템을 위한 거네요?" Maya가 물었습니다.

"거의 맞아요," Priya가 말했습니다. "Cluster: 인스턴스 간 낮은 지연 시간, 하나의 큰 위험. Spread: 최대 격리, AZ당 7개의 엄격한 한계. Partition: 큰 분산 시스템을 위한 구조화된 격리 — 각 인스턴스가 어느 파티션으로 가는지 여러분이 제어해요."

Nimbus의 현재 아키텍처에는, 이 중 어느 것도 아직 적용되지 않았습니다. 하지만 그것들이 존재한다는 것을 안다는 것은 언제 그것들을 집어야 할지 안다는 것을 의미했습니다 — 그리고 더 당장은, "낮은 노드 간 지연 시간이 필요한 HPC 워크로드"에 관한 시험 문제가 실제로 무엇을 묻는지 안다는 것을요.

## 요약

우연히 시작된 인스턴스는 결코 프로덕션 서버가 될 수 없었습니다. EC2를 제대로 이해하는 것은 단지 용량 문제를 해결한 게 아닙니다 — 그것은 거의 모든 후속 챕터에서 나올 새로운 개념 세트를 도입했습니다. 인스턴스 유형, AMI, 키 페어, 보안 그룹, 적정 크기 조정은 EC2 잡학이 아닙니다; 그것들은 책의 나머지가 그 위에 구축되는 어휘입니다. 여기서 그것들을 배우면 다른 모든 것이 더 잘 이해됩니다.

- **EC2 인스턴스**는 여러분이 AWS에서 임대하는 가상 머신입니다. 인스턴스 유형은 사용 사례별로 구성됩니다: 범용, 컴퓨팅 최적화, 메모리 최적화, 스토리지 최적화. 올바른 패밀리를 고르고 실제 워크로드 지표에 맞춰 적정 크기로 조정하십시오 — 상상된 최악의 경우가 아니라요.
- **AMI**(Amazon Machine Image)는 인스턴스의 OS와 초기 구성을 위한 템플릿입니다. 사용자 정의 AMI는 일관되고 반복 가능한 배포를 가능하게 합니다.
- **키 페어**는 EC2 인스턴스에 접근하는 안전한 방법입니다. **보안 그룹**은 여러분의 인스턴스의 방화벽입니다 — SSH를 알려진 IP로 제한하고 데이터베이스 포트를 애플리케이션의 보안 그룹에만 잠그십시오.
- **IMDSv2**는 인스턴스 메타데이터 서비스로부터의 SSRF 기반 자격 증명 탈취를 방지하기 위해 모든 인스턴스에서 활성화되어야 합니다.
- EC2 인스턴스는 기본적으로 영구적이지 않습니다. 종료된 인스턴스는 로컬 데이터를 잃습니다 — 중요한 데이터는 인스턴스 디스크가 아니라 S3나 EBS에 저장하십시오.

- **EC2에 대한 공동 책임**: 여러분이 OS를 패치하는 책임이 있습니다.
  AWS가 물리적 하드웨어와 하이퍼바이저를 유지관리합니다. 이것은 자주 테스트되는
  구분입니다.
- **인스턴스 패밀리는 시나리오 질문에 중요합니다.** 시나리오가 높은
  메모리 요구 사항(인메모리 캐시, SAP HANA)을 언급하면, 답은 아마
  메모리 최적화 인스턴스를 수반합니다. 배치 처리나 HPC를 언급하면, 컴퓨팅 최적화입니다.
- **중지 ≠ 종료.** 인스턴스를 중지하는 것은 그것을 보존합니다(재시작할 수 있음).
  종료하는 것은 그것을 삭제합니다. 시험 시나리오는 여러분이 이 구분을 아는지 테스트합니다.
- **재시작 시 퍼블릭 IP가 바뀝니다.** 애플리케이션에 안정적인 IP 주소가 필요하면,
  **Elastic IP** — 여러분의 계정과 연결된 채로 유지되는 정적 퍼블릭 IP — 를 사용하십시오.
  2024년 2월부터, AWS는 모든 퍼블릭 IPv4 주소를 시간당 청구합니다 — Elastic IP
  (연결되었든 아니든)와 자동 할당된 퍼블릭 IP 모두요.
- **온디맨드, 예약, 스팟** 가격 모델은 도메인 4에서 많이 테스트됩니다.
  우리는 27장에서 그것들을 다룹니다. 지금은, 온디맨드는 약정 없이 초당
  지불하는 것을 의미한다는 것을 알아 두십시오.
- **보안 그룹은 상태 저장(stateful)입니다.** 한 포트에서 인바운드 트래픽을 허용하면,
  반환 트래픽은 명시적 아웃바운드 규칙 없이 자동으로 허용됩니다. NACL
  (15장에서 다룸)은 상태 비저장(stateless)입니다 — 인바운드와 아웃바운드 규칙 둘 다 필요합니다.
- **배치 그룹:** Cluster = 인스턴스 간 가장 낮은 지연 시간(HPC, ML 훈련 — 하지만 그룹에 대한 단일 장애 지점 위험); Partition = 파티션별 장애 격리를 가진 분산 시스템(Hadoop, Kafka, Cassandra); Spread = 최대 인스턴스 격리, AZ당 최대 7개. 시험 문제 패턴: "긴밀하게 결합된 HPC 워크로드가 노드 간 최대 네트워크 처리량을 필요로 함" → Cluster 배치 그룹.

**연습 2 — SAA-C03 시나리오**

*시나리오*: 한 회사가 높은 트래픽의 웹 애플리케이션을 배포하고 있습니다. 그 애플리케이션은
CPU 집약적인 복잡한 필터링 로직으로 제품 카탈로그 검색을 처리합니다.
팀은 세일 이벤트 동안 상당한 트래픽 급증을 예상합니다. 그들은 올바른 EC2 인스턴스
유형을 선택하고 트래픽 폭증에 대비하고 싶어 합니다.

다음 중 그들의 요구 사항을 가장 잘 충족하는 선택의 조합은 무엇입니까?

A) 일관된 성능을 보장하기 위한 고정된 수의 메모리 최적화 인스턴스  
B) 트래픽 급증을 처리하기 위한 Auto Scaling을 갖춘 컴퓨팅 최적화 인스턴스  
C) 단일 대형 인스턴스 크기의 범용 인스턴스  
D) 제품 카탈로그가 빠른 디스크 접근을 필요로 하므로 스토리지 최적화 인스턴스

**힌트 1**: 워크로드가 "CPU 집약적"으로 묘사되어 있습니다. 어느 인스턴스 패밀리가
CPU에 최적화되어 있습니까?

**힌트 2**: 시나리오는 "세일 이벤트 동안의 트래픽 급증"을 언급합니다. 고정된 수의
인스턴스는 변동하는 트래픽을 효율적으로 처리하지 못합니다. 어떤 AWS 기능이 이것을 처리합니까?

**힌트 3**: 컴퓨팅 최적화 인스턴스는 CPU 집약적 작업을 처리합니다. Auto Scaling은
수요에 따라 인스턴스를 추가하고 제거합니다. 함께 그것들은 두 요구 사항 모두에 답합니다.

**정답**: B

**설명**: 컴퓨팅 최적화 인스턴스(`c` 패밀리 같은)는 CPU 집약적 워크로드에 대해
달러당 더 많은 CPU를 제공합니다. Auto Scaling은 부하에 따라 인스턴스 수를
자동으로 조정합니다 — 세일 이벤트 동안 인스턴스를 추가하고, 트래픽이 정상으로
돌아오면 그것들을 제거합니다. 이 조합은 성능과 비용 둘 다를 최적화합니다.

**왜 A가 아닌가?** 메모리 최적화 인스턴스는 많은 양의 RAM이 필요한
워크로드(데이터베이스, 인메모리 캐시)를 위해 설계되었습니다. 이것은 CPU 바운드 워크로드입니다. 그리고 고정된
인스턴스 수는 과도한 프로비저닝(낭비)이나 부족한 프로비저닝(실패)을 의미합니다.

**왜 C가 아닌가?** 범용 인스턴스는 균형을 위해 약간의 CPU 효율성을 맞바꿉니다.
알려진 CPU 집약적 워크로드에는, 컴퓨팅 최적화가 더 적절합니다. 그리고 단일
대형 인스턴스는 단일 장애 지점입니다.

**왜 D가 아닌가?** 병목은 CPU이지, 디스크 I/O가 아닙니다. 스토리지 최적화 인스턴스는
로컬 스토리지에 매우 높은 처리량이 필요한 워크로드를 위해 설계되었습니다.
