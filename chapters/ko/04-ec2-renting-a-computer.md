# 4장: 다른 사람의 건물에 있는 컴퓨터

Nimbus 앱은 Tom의 노트북에서 실행되고 있었다.

투자자들에게 데모를 보여주기에는 괜찮았다. Maya가 "출시"를 눌렀을 때 첫 주에 200개의 레스토랑이 등록하자 더 이상 괜찮지 않았다. Tom의 노트북은 이제 Tom의 책상 아래에서, 사무실 와이파이로 실행되면서, 전기 히터와 커피 메이커에도 전원을 공급하는 멀티탭에 꽂힌 채 실제 주문, 실제 메뉴, 실제 고객을 처리하고 있었다.

"서버가 필요해," Maya가 말했다. "진짜 서버. 책상 아래가 아닌 어딘가에서 실행되는."

Tom이 노트북을 봤다. 팬 소리가 방 건너편에서도 들렸다.

그게 그들이 컴퓨터를 임대한다는 것이 실제로 무엇을 의미하는지 살펴보기 시작한 때였다.

**아무도 설명하지 않는 추상화**

사람들이 애플리케이션이 "클라우드에서 실행된다"고 말할 때, 보통 가상 머신에서 실행된다는 것을 의미한다 — 전용 하드웨어로 물리적으로 존재하지는 않지만 모든 면에서 그렇게 동작하는 컴퓨터.

메커니즘은 이렇다.

AWS 데이터 센터의 물리적 서버에는 많은 리소스가 있다: CPU 코어, 메모리, 디스크, 네트워크 대역폭. AWS는 **하이퍼바이저**라는 소프트웨어를 사용하여 그 물리적 서버를 나눈다. 하이퍼바이저는 여러 가상 머신을 만들어, 각각이 전용 CPU, 메모리, 디스크를 갖고 있는 것처럼 보이지만 실제로는 기본 물리적 하드웨어를 공유한다.

그 각각의 가상 머신을 AWS는 **EC2 인스턴스**라고 부른다.

EC2는 Elastic Compute Cloud를 의미한다. "탄력적인" 부분이 중요하며, 곧 다루겠다. 지금은: EC2 인스턴스는 시간당 임대하는 컴퓨터다. 운영 체제, 네트워크 연결, 컴퓨팅 파워가 있다. 물리적 서버처럼 애플리케이션을 실행한다.

비유: 큰 건물에서 아파트를 임대하는 것 대 집을 구매하는 것.

건물 소유자(AWS)가 물리적 구조, 배관, 전기, 보안을 유지한다. 당신은 유닛을 얻는다. 원하는 대로 꾸민다. 월별로(또는 시간별로) 지불한다. 더 많은 공간이 필요하면 더 큰 유닛으로 이동한다. 이사를 나가면 지불을 중단한다.

**인스턴스 선택: 크기가 중요하다**

모든 EC2 인스턴스가 같은 것은 아니다. AWS는 최적화된 목적에 따라 패밀리로 구성된 수백 가지 인스턴스 유형을 제공한다.

**범용**(예: `t3`, `m6i`): CPU와 메모리의 균형. 대부분의 웹 애플리케이션에 좋은 기본 선택.

**컴퓨팅 최적화**(예: `c7g`): 메모리에 비해 더 많은 CPU. 비디오 인코딩, 과학 모델링, 배치 처리에 좋다.

**메모리 최적화**(예: `r7i`): CPU에 비해 더 많은 메모리. 데이터베이스, 캐싱, 인메모리 분석에 좋다.

**스토리지 최적화**(예: `i3`): 고속 로컬 스토리지. 매우 빠른 디스크 I/O가 필요한 데이터 집약적 워크로드에 좋다.

**가속 컴퓨팅**(예: `p4`): GPU가 연결됨. 머신 러닝 훈련과 그래픽 렌더링에 좋다.

각 패밀리에는 크기가 있다. `t3.micro`는 2개의 가상 CPU와 1GB 메모리가 있다. `t3.xlarge`는 4개의 가상 CPU와 16GB가 있다. 워크로드에 맞는 크기를 선택한다.

Leo는 `t3.micro`를 선택했다.

"t3.micro가 몇 명의 사용자를 처리할 수 있어요?" Tom이 물었다.

"애플리케이션에 따라 달라요," Leo가 말했다. "하지만 이미지 업로드와 데이터베이스 쿼리를 실행하는 동시 사용자 100명은 아마 안 될 거예요."

Tom이 화이트보드에 "t3.micro"를 적고 옆에 슬픈 얼굴을 그렸다.

**AMI: 머신의 초기 상태**

EC2 인스턴스를 실행하기 전에, 운영 체제와 초기 설정을 선택한다. AWS에서 이것을 **Amazon Machine Image**(AMI)라고 한다.

AMI는 템플릿이다. 다음을 정의한다:

- 운영 체제(Amazon Linux, Ubuntu, Windows Server 등)
- 사전 설치된 소프트웨어
- 초기 디스크 상태

AMI에서 인스턴스를 실행하면, AWS가 당신만을 위한 그 템플릿의 새 복사본을 만든다. 자체 AMI를 만들 수도 있다 — 서버를 원하는 대로 정확히 설정하면, 그 상태를 사용자 정의 AMI로 "저장"하여 빠르게 동일한 서버를 실행하는 데 사용할 수 있다. 이것이 대규모로 일관된 환경을 배포하는 방법이다.

AMI를 요리법으로 생각하라. 요리법이 요리를 설명한다. 요리법을 따를 때마다 같은 요리가 만들어진다. 요리를 영구적으로 바꾸고 싶다면, 요리법을 업데이트한다.

**키 페어: 서버에 접근하는 올바른 방법**

지난 챕터에서 "Admin123" 재앙을 기억하는가?

EC2 인스턴스에 로그인하는 올바른 방법은 **키 페어**를 사용하는 것이다.

키 페어는 암호화 쌍이다: 공개 키(서버에 AWS에 의해 저장됨)와 개인 키(다운로드하고 비밀로 유지하는 파일). 로그인하려면, 개인 키로 SSH — 보안 프로토콜 — 를 사용한다. 비밀번호가 없다. 개인 키를 잃으면, 접근을 잃는다. SSH에는 "비밀번호를 잊었습니다"가 없다.

이것이 중요한 이유는 키 페어가:

- 당신에게 고유하다
- 암호학적으로 추측 불가능하다
- AWS에 저장되지 않는다(당신이 개인 키를 보관한다)
- 취소하기 쉽다(서버에서 키를 삭제하고, 새 쌍을 만든다)

Priya는 Nimbus 서버에 키 기반 접근을 이미 설정했다. Admin123 서버는 폐기되었다. 아무도 슬퍼하지 않았다.

**인스턴스 수명주기: 영원히가 아니다**

이것은 많은 초보자들이 놓치는 것이다.

EC2 인스턴스는 기본적으로 영구적이지 않다. 인스턴스를 중지하면, 컴퓨팅 리소스가 해제된다. 다시 시작하면, 다른 물리적 하드웨어에서 실행될 수 있다. *인스턴스 자체*(루트 볼륨)에 저장된 데이터는 중지/시작 사이클에서 살아남는다 — 하지만 공개 IP 주소가 바뀐다.

인스턴스를 *종료*하면, 사라진다. 별도의 스토리지가 연결되어 있지 않으면(6장에서 다룬다), 인스턴스의 모든 데이터가 사라진다.

이 "일시적" 특성은 실제로 버그가 아니라 기능이다. 서버를 실행하고, 사용하고, 버릴 수 있다는 것을 의미한다. 수평 확장을 가능하게 한다. 하지만 또한 중요한 데이터를 EC2 인스턴스 *위에* 저장해서는 안 된다는 것을 의미한다.

그렇다면 데이터는 어디에 사는가?

별도의 스토리지에. 다음 두 챕터에서 다룬다.

**"탄력적"이 의미하는 것**

EC2가 Elastic Compute Cloud를 의미한다고 했다. 탄력적이라는 게 뭔가?

두 가지:

**수직 탄력성**: 인스턴스의 크기를 변경할 수 있다. 인스턴스를 중지하고, `t3.micro`에서 `t3.xlarge`로 변경하고, 다시 시작한다. 더 많은 CPU와 메모리, 같은 애플리케이션, 같은 설정.

**수평 탄력성**: 더 많은 인스턴스를 추가할 수 있다. 하나의 대형 서버 대신, 로드 밸런서 뒤에 10개의 중간 서버를 실행한다. 트래픽이 감소하면, 인스턴스를 제거하고 지불을 중단한다.

두 접근 방식 모두 "서버 하나, 트래픽 너무 많음" 문제를 해결한다. 서로 다른 트레이드오프가 있으며, 7장에서 Auto Scaling을 이야기에 추가할 때 살펴볼 것이다.

핵심 통찰: EC2에서 컴퓨팅 파워는 *구매*하는 것이 아니라 *조절*하는 것이다. 더 필요하면? 다이얼을 올린다. 덜 필요하면? 다이얼을 내린다. 그에 따라 지불한다.

## 장점과 한계

**EC2가 강력한 이유**:

- 완전한 제어. OS, 소프트웨어, 설정을 선택한다. 당신의 컴퓨터다.
- 유연한 크기 조정. 모든 사용 사례에 걸쳐 수백 가지 인스턴스 유형.
- 관리할 하드웨어가 없다. AWS가 물리적 레이어를 처리한다.
- 초 단위 결제(대부분의 인스턴스 유형). 인스턴스를 중지하면, 지불을 중단한다.
- 모든 것과 작동한다. EC2는 다른 대부분의 AWS 서비스가 구축된 기반이다.

**복잡해지는 부분**:

- 운영 체제를 패치하고 업데이트할 책임이 있다. (공동 책임 모델 — 이것이 당신의 "클라우드 내" 부분이다.)
- 대규모로 EC2를 관리하는 것은 수천 대의 기계에 걸쳐 인스턴스 상태, AMI, 보안 패치, 수명주기를 관리하는 것을 의미한다. 운영 오버헤드다.
- EC2가 모든 것의 올바른 답은 아니다. 드물게 실행되는 이벤트 기반 코드의 경우, Lambda(20장)가 더 저렴하고 단순하다. 컨테이너화된 워크로드의 경우, ECS와 EKS(21장)가 더 나은 리소스 효율을 제공한다.
- 사용하지 않는 인스턴스도 비용이 든다. 인스턴스를 중지하면 컴퓨팅 비용 지불을 중단하지만, 스토리지가 연결되어 있으면 그것에 대한 비용은 계속 낸다.

## 요약

- **EC2 인스턴스**는 AWS에서 임대하는 가상 머신이다. OS, 네트워크
  접근, 컴퓨팅 리소스가 있다.
- 인스턴스 유형은 사용 사례별로 구성된다: 범용, 컴퓨팅 최적화,
  메모리 최적화, 스토리지 최적화, 가속 컴퓨팅. 워크로드에 맞는 올바른 패밀리와 크기를 선택하라.
- **AMI**(Amazon Machine Image)는 인스턴스의 OS와 초기 설정을 위한 템플릿이다. 사용자 정의 AMI는 일관되고 반복 가능한 배포를 가능하게 한다.
- **키 페어**는 EC2 인스턴스에 접근하는 안전한 방법이다. 비밀번호 없음.
- EC2 인스턴스는 기본적으로 영구적이지 않다. 종료된 인스턴스는 데이터를 잃는다.
  중요한 데이터는 별도의 스토리지 서비스에 저장하라.
- "탄력적"은 컴퓨팅을 확장하고 축소할 수 있다는 것을 의미한다 — 수직으로(더 큰 인스턴스)와
  수평으로(더 많은 인스턴스) 모두.

## 시험 팁

*SAA-C03 도메인 3 — 태스크 3.2 (고성능 컴퓨팅 솔루션)*

- **EC2에 대한 공동 책임**: OS를 패치하는 것은 당신의 책임이다.
  AWS는 물리적 하드웨어와 하이퍼바이저를 유지한다. 이것은 자주 테스트되는 구분이다.
- **인스턴스 패밀리는 시나리오 질문에 중요하다.** 시나리오가 높은 메모리 요구사항(인메모리 캐시, SAP HANA)을 언급하면, 답은 메모리 최적화 인스턴스를 포함할 것이다. 배치 처리나 HPC를 언급하면, 컴퓨팅 최적화.
- **중지 ≠ 종료.** 인스턴스를 중지하면 보존된다(재시작 가능).
  종료는 삭제한다. 시험 시나리오는 이 구분을 알고 있는지 테스트한다.
- **재시작 시 공개 IP가 변경된다.** 애플리케이션이 안정적인 IP 주소가 필요하면,
  **Elastic IP** — 계정과 연결된 상태로 유지되는 정적 공개 IP — 를 사용하라.
  이것은 할당하고 사용하지 않으면 비용이 든다.
- **온디맨드, 예약, Spot** 가격 모델은 도메인 4에서 무겁게 테스트된다.
  27장에서 다룬다. 지금은, 온디맨드는 약정 없이 초당 지불을 의미한다는 것만 알아라.

**힌트 1**: 워크로드가 "CPU 집약적"이라고 설명된다. 어떤 인스턴스 패밀리가 CPU에 최적화되어 있는가?

**힌트 2**: 시나리오가 "세일 이벤트 동안 트래픽 급증"을 언급한다. 고정된 수의 인스턴스는 가변적인 트래픽을 효율적으로 처리하지 못한다. 어떤 AWS 기능이 이것을 처리하는가?

**힌트 3**: 컴퓨팅 최적화 인스턴스는 CPU 집약적인 작업을 처리한다. Auto Scaling은 수요에 따라 인스턴스를 추가하고 제거한다. 함께 두 요구사항 모두에 답한다.

**답**: B

**설명**: 컴퓨팅 최적화 인스턴스(`c` 패밀리)는 CPU 집약적인 워크로드에 대해 달러당 더 많은 CPU를 제공한다. Auto Scaling은 부하에 따라 인스턴스 수를 자동으로 조정한다 — 세일 이벤트 동안 인스턴스를 추가하고, 트래픽이 정상으로 돌아오면 제거한다. 이 조합은 성능과 비용 모두를 최적화한다.

**왜 A가 아닌가?** 메모리 최적화 인스턴스는 대량의 RAM이 필요한 워크로드(데이터베이스, 인메모리 캐시)를 위해 설계되었다. 이것은 CPU 바운드 워크로드다. 그리고 고정된 인스턴스 수는 과도 프로비저닝(낭비) 또는 부족 프로비저닝(실패)을 의미한다.

**왜 C가 아닌가?** 범용 인스턴스는 일부 CPU 효율성을 균형을 위해 트레이드한다. 알려진 CPU 집약적인 워크로드의 경우, 컴퓨팅 최적화가 더 적절하다. 그리고 단일 대형 인스턴스는 단일 장애 지점이다.

**왜 D가 아닌가?** 병목은 CPU이지 디스크 I/O가 아니다. 스토리지 최적화 인스턴스는 로컬 스토리지에 매우 높은 처리량이 필요한 워크로드를 위해 설계되었다.
