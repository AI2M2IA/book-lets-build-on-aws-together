# 장 28: 스토리지 청구서의 놀라움

스프레드시트에는 이제 열여섯 개의 탭이 있었다. 톰은 그것을 두 번째 창에 열어 두었다. 어떤 사람들이 장보기 목록을 두는 방식처럼 — 항상 보이고, 항상 쌓여 가는. 그는 EC2를 위한 새 행을 추가하고 (완료, Savings Plan 약정됨) 커서를 다음 줄로 옮겼다.

스토리지.

**요점 정리: EC2 정리 완료, 남은 항목 하나**

27장의 컴퓨트 가격 작업은 EC2 전략을 확정했다: 3년 기간의 시간당 $0.45 Compute Savings Plan, 더하기 야간 배치를 위한 Spot — 기간에 걸쳐 추정 $42,500의 절약. 그 작업은 끝났고, 잘 끝났다. 하지만 그것은 청구서의 한 줄이었다. 톰은 6개월간의 Athena 비용 분석으로부터, 청구서에 여러 줄이 있다는 것 — 그리고 각각이 동일한 정밀 검토를 받을 자격이 있다는 것을 배웠다. S3가 다음이었다: 월 $198, 23장의 라이프사이클 정책 변경 이후 $847에서 이미 개선된 상태였다. 하지만 그의 눈길을 끈 숫자는 페이지 아래쪽에 있었다. EBS: 월 $440.

"저거 높아 보이는데요," 그가 말했다.

레오가 EBS 볼륨 목록을 띄웠다. 인스턴스에 연결된 EBS 볼륨이 47개 있었다. 그리고 어떤 인스턴스에도 연결되지 않은 볼륨이 또 23개 있었다.

"이 23개 볼륨," 톰이 말했다. "이게 뭐죠?"

**고아 볼륨 감사**

레오는 그것들을 하나씩 훑어보기 시작했다. 이것은 빠른 과정이 아니었다 — 볼륨들은 일관되게 라벨이 붙어 있지 않았고, 태그는 제각각이었으며, 일부는 너무 오래전에 생성되어 아무도 그 맥락을 기억하지 못했다. 톰은 의자를 끌어와 지켜보았다.

볼륨 ebs-021a4c. 16개월 전 생성. 태그: "debug-prod-db-snapshot-restore." 크기: 200GB. 마지막 연결: 없음, 또는 연결 기록이 삭제됨.

"저건 기억나요," 레오가 말했다. "데이터베이스 쿼리 문제가 있어서 데이터를 확인하려고 스냅샷을 복원했어요. 확인해 봤더니 거기엔 문제가 없었고, 볼륨 삭제하는 걸 깜빡했죠."

볼륨 ebs-07f38b. 11개월 전 생성. 태그: "load-test-temp." 크기: 400GB.

레오는 잠시 조용했다. "그건 시리즈 시드 피칭 전에 했던 부하 테스트인 것 같아요. 피크 부하를 시뮬레이션하려고 추가 스토리지가 달린 추가 인스턴스를 프로비저닝했는데, 그러고 나서... 그 후에 아무것도 삭제하지 않은 것 같네요."

"이미 배포했는데 — 아," 그가 말했다. "부하 테스트는 임시였어요. 볼륨은 아니었고요."

볼륨 ebs-0ab12c부터 ebs-0ab134까지. 9개월 전 생성된 연속된 볼륨 여덟 개. 태그: "k8s-experiment." 각 100GB, 총 800GB.

"그건 Kubernetes 평가였어요," 프리야가 레오의 어깨너머로 보며 말했다. "ECS로 갈지 EKS로 갈지 마이그레이션 여부를 평가하는 데 3주를 썼죠. EKS가 차점이었어요. 실험 클러스터는 헐었는데 영구 볼륨은 그냥 남겨둔 모양이네요."

톰은 별도의 탭에서 합산하고 있었다. 볼륨별로 숫자가 쌓여 갔다:

- 디버그 복원 볼륨: 4개 볼륨 × 200GB = 800GB
- 부하 테스트 볼륨: 200~400GB 사이 여섯 개 볼륨 — 총 약 1,200GB
- Kubernetes 실험 볼륨: 8개 볼륨 × 100GB = 800GB
- 기타 태그 없는 것: 5개 볼륨 × 다양한 크기 = 약 700GB

총: 연결되지 않은 23개 볼륨에 걸쳐 약 3,500GB.

"이게 월별로 얼마나 들죠?" 톰이 물었다. 답: gp3는 GB당 월 $0.08. 3,500GB × $0.08 = 월 $280.

그는 가장 오래된 생성 날짜를 확인했다. 16개월. 그는 계산기를 꺼냈다.

"이 중 일부는 16개월 동안 비용을 내고 있었어요," 그가 말했다. "일부는 9개월. 전부 평균하면 아마 10개월쯤." 볼륨 23개, 각각 평균 월 $12, 평균 10개월. 그것은 약 $2,760였다. 더 큰 볼륨을 더하니 계산은 총 약 $3,200의 낭비로 나왔다.

"3,200달러," 톰이 말했다. "아무도 쓰지 않던 볼륨에서."

"그리고 청구가 수십 개의 항목에 흩어져 있어서 아무도 알아채지 못했어요," 레오가 말했다. "$3,200짜리 청구 하나가 아니에요. 월 $12나 $50나 $80짜리 청구 23개인데, 각각이 개별적으로는 어떤 경보도 울리지 않을 만큼 충분히 작죠."

톰은 연결되지 않은 23개 볼륨을 모두 삭제했다. 그는 레오, 프리야와 함께 각각에 필요한 데이터가 없음을 확인했다 — 디버그 볼륨은 이후 마이그레이션된 데이터베이스의 오래된 데이터였고, 부하 테스트 데이터는 무관했으며, Kubernetes 실험 볼륨은 비어 있었다. 삭제는 15분이 걸렸다. 다음 달, EBS 청구서는 $440에서 $160로 떨어졌다.

"잠깐 — 근데 *왜* 그런 식으로 하는 거죠?" 톰이 발견 내용을 설명해 줄 때 마야가 물었다. "인스턴스를 종료할 때 볼륨 삭제가 왜 기본값이 아닌가요?"

"볼륨에 따라 달라요," 톰이 말했다. "**루트** 볼륨은 기본적으로 삭제됩니다 — 거기엔 `DeleteOnTermination`이 true예요. 하지만 연결하는 **추가** 데이터 볼륨은 기본적으로 보존됩니다. 거기 있던 데이터가 필요할 수도 있다는 가정이죠. 이 23개 고아는 모두 데이터 볼륨이었어요 — 디버그 세션이나 부하 테스트를 위해 연결됐다가, 인스턴스가 종료될 때 남겨진 거죠."

"그러니까 기본값은 데이터 볼륨에서의 우발적 데이터 손실로부터 보호해 주는 거네요."

"그리고 주의를 기울이지 않으면 돈이 들죠. 이제부터: 추가 데이터 볼륨은 인스턴스가 종료될 때 명시적으로 삭제되거나 — 연결 시 `DeleteOnTermination`을 설정하거나 — 누군가 그것을 유지해야 하는 이유를 문서로 제시하지 않는 한 그렇게 합니다."

"누군가 그 사유를 문서화하는 걸 잊으면 어떻게 되는지 생각해 봤나요?" 프리야가 물었다. "중요한 걸 삭제할 수도 있어요."

"그게 트레이드오프예요," 톰이 말했다. "지금은 트레이드오프가 반대 방향에 있어요 — 모든 걸 유지해야 한다고 가정하고, 그렇지 않을 때도 비용을 내고 있죠. '이 볼륨 유지' 문서화의 규율은 '모든 걸 조용히 유지'라는 현재 기본값보다 덜 위험합니다."

**스토리지 비용 감사**

톰의 EBS 발견은 더 넓은 패턴의 증상이었다: 스토리지 비용은 눈에 보이지 않게 쌓인다. 컴퓨트와 달리 (서버 47대가 실행되면 알아챈다) 스토리지는 조용히 합산된다.

그것을 창고 임대처럼 생각해 보라. 창고 하나를 임대하는 것은 신용카드 명세서에 명확하다. 하지만 프로젝트를 위해 두 번째 창고를 빌리고, 오래된 가구를 위해 세 번째를 빌리고, 안에 뭐가 있는지 다시 확인하러 가지 않는다면 — 청구는 매달 조용히 계속 나타나고, 당신이 무엇을 보관하고 있는지조차 잊어버린 한참 후까지도 그렇다. 클라우드 스토리지도 같은 방식으로 작동한다: 바이트는 거기 앉아 있고, 청구서는 도착하고, 누군가 마침내 문을 열어 더 이상 아무도 필요로 하지 않는 것들로 가득 찬 것을 발견할 때까지 아무도 의문을 제기하지 않는다.

철저한 스토리지 비용 감사는 다음을 살핀다:

**S3**:

- 모든 버킷에 라이프사이클 정책이 마련되어 있는가?
- S3에 오래된 스냅샷(RDS, EBS)이 앉아 있는가?
- 접근 패턴이 불확실한 버킷에 Intelligent-Tiering이 적절한가?
- 접근되지 않는 여러 복사본을 만드는 버전 객체가 있는가?
- 조용히 쌓이는 불완전한 멀티파트 업로드가 있는가?

**EBS**:

- 연결되지 않은 볼륨이 있는가 (사용 중인 실행 인스턴스가 없는)?
- gp3 볼륨이 제대로 구성되어 있는가? (기본 gp3 볼륨은 필요하지 않은 과도한 프로비저닝 처리량/IOPS를 가질 수 있다)
- 필요 이상으로 오래된 스냅샷이 보존되고 있는가?

**RDS**:

- 자동 백업 보존 기간이 적절하게 설정되어 있는가? (길수록 = 더 많은 스토리지 비용)
- 오래된 인스턴스에서 만든 수동 스냅샷이 아직 남아 있는가?
- 데이터베이스 마이그레이션의 읽기 복제본이 아직 실행 중인가?

**EFS**:

- EFS 볼륨이 올바른 스토리지 클래스에 있는가? (Standard vs Infrequent Access)

**S3 버전 관리: 숨겨진 비용**

5장에서 우리는 S3 버전 관리가 객체의 모든 이전 버전을 유지한다고 언급했다. 이것은 안전을 위해서는 훌륭하다. 버전에 대한 라이프사이클 규칙도 함께 두지 않으면 비용 측면에서는 끔찍하다.

버킷에서 버전 관리가 활성화되면, 객체를 덮어쓸 때마다 이전 버전이 보존된다. 시간이 지나면:

- 1일차: 이미지 업로드 (v1)
- 30일차: 이미지 업데이트 (v1은 이제 "비현행(noncurrent)" 버전, v2가 현행)
- 60일차: 이미지 다시 업데이트 (v1과 v2는 비현행, v3가 현행)
- 365일차: v1, v2... v12가 모두 저장됨. 이미지 한 장의 복사본 12개에 대해 비용을 내고 있다.

버전 관리가 왜 오래된 버전을 자동으로 정리하지 않는지 궁금할 수 있다. 답은 의도적이다 — AWS는 당신의 데이터를 자동으로 삭제하고 싶어 하지 않는다. 하지만 그 결과는, 당신이 S3에게 얼마나 오래 보관할지 명시적으로 말할 때까지 모든 버전이 쌓인다는 것이다. 해결책: 비현행 버전에 대한 라이프사이클 규칙.

```
Expire noncurrent versions after 30 days
Delete failed multipart uploads after 7 days
```

톰은 이 규칙들을 모든 버전 관리 버킷에 적용했다. 다음 달, S3 스토리지가 18% 감소했다.

**불완전한 멀티파트 업로드: 보이지 않는 누적**

대부분의 엔지니어가 완전히 놓치는 더 미묘한 S3 비용이 있다: 불완전한 멀티파트 업로드.

S3가 큰 파일을 업로드할 때, 그것을 여러 부분으로 쪼개 각각을 따로 업로드한다. 이것이 멀티파트 업로드 메커니즘이다 — 수백 메가바이트가 넘는 파일에 대해 단일 대형 PUT보다 더 신뢰성이 높다. 하지만 업로드가 시작된 다음 중간에 실패하면 — 네트워크 중단, 클라이언트 충돌, 애플리케이션 버그 — 이미 업로드된 부분들이 S3에 남는다. 그것들은 버킷에서 객체로 보이지 않는다. 어떤 목록에도 나타나지 않는다. 하지만 저장되어 있고, 표준 S3 요금으로 비용이 청구된다.

톰은 S3 콘솔에서 S3 Storage Lens 대시보드를 활성화하고 "incomplete multipart uploads"로 정렬하여 이것을 발견했다. Nimbus는 네 개의 AWS 계정에 걸친 버킷에 340GB의 불완전한 멀티파트 업로드 데이터가 조용히 앉아 있었고, 그중 일부는 1년이 넘었다.

"이게 월별로 얼마나 들죠?" 톰이 물었다. GB당 월 $0.023 × 340GB = 월 $7.82. 개별적으로는 작다. 하지만 아무도 알아채지 못한 채 1년 동안 쌓여 왔다.

해결책: 모든 버킷에 라이프사이클 규칙 추가.

```
AbortIncompleteMultipartUpload:
  DaysAfterInitiation: 7
```

7일 후, 불완전한 멀티파트 업로드는 자동으로 정리된다. 이것은 지속적인 관심 없이 무기한 실행된다.

"그게 전부 꼬박 1년 동안 거기 있었다면 — 실패한 업로드에 쓴 $94쯤 되겠네요," 레오가 말했다.

"실패한 업로드에요," 톰이 확인했다. "성공한 스토리지도 아니고요. 이것이 인프라 낭비의 정의예요."

**EBS: 적정 크기 조정과 gp3 업그레이드**

EBS 볼륨 가격에는 두 가지 구성 요소가 있다:

1. 스토리지 (GB당 월 단위)
2. 프로비저닝된 IOPS와 처리량 (io1/io2를 쓰거나 추가 gp3 성능에 비용을 낼 경우)

**gp3 기회**: 6장에서 우리는 gp3가 현재 기본값이며 gp2보다 저렴하다고 언급했다. Nimbus에 gp3가 가용해지기 전에 (2020년 12월 출시) 생성된 볼륨이 있었다면, 그것들은 아직 gp2일 수 있다.

마이그레이션은 간단하다: AWS 콘솔이나 CLI를 통해 볼륨 유형을 gp2에서 gp3로 수정한다. 다운타임이 필요 없다. 전환 동안 볼륨은 가용 상태를 유지한다. 성능 특성은 동등하거나 더 낫다 — gp3는 3,000 IOPS와 125 MB/s의 기준 처리량을 제공하는데, 이는 더 작은 볼륨에서는 일관되지 않을 수 있었던 gp2의 버스트형 모델과 대비된다.

"잠깐 — 근데 *왜* 그런 식으로 하는 거죠?" 마야가 물었다. "gp3가 더 싸고 적어도 gp2만큼 좋다면, AWS는 왜 그냥 모두를 자동으로 마이그레이션하지 않았나요?"

"AWS는 고객 인프라에 일방적인 변경을 가하지 않거든요," 톰이 말했다. "이로운 변경이라도요. 그 수정이 이론적으로 어떤 워크로드에 부작용을 일으킬 수 있어요. 고객이 그것을 시작해야 합니다. 그래서 수천 개의 팀이 gp3 출시 후 몇 년이 지나도 단지 아무도 찾아보지 않았다는 이유로 여전히 gp2 가격을 내고 있죠."

톰은 토요일 아침에 gp3 마이그레이션을 하기로 결정했다 — EC2 가격 분석에 적용했던 것과 같은 아침의 규율. 조용한 시간. 스탠드업 없음. 오직 AWS 콘솔과 계획뿐.

그는 프로덕션 환경 전반에서 아직 gp2인 볼륨 8개를 식별했다: API 서버 루트 볼륨 네 개, 백그라운드 처리기에 연결된 볼륨 두 개, 그리고 새 배포에 gp3 마이그레이션이 표준 관행이 되기 전에 생성된 레거시 데이터 볼륨 두 개. 합쳐서 총 960 GB였다.

마이그레이션 과정은 볼륨당 단일 API 호출이었다:

```bash
aws ec2 modify-volume \
  --volume-id vol-0a1b2c3d4e5f67890 \
  --volume-type gp3 \
  --iops 3000 \
  --throughput 125
```

`--iops 3000`과 `--throughput 125` 파라미터는 gp3의 기준 기본값과 일치했다. gp2에 대해, 톰은 먼저 CloudWatch 메트릭을 확인했다: 각 볼륨의 평균 IOPS는 200에서 800 사이였다. 그것들 중 어느 것도 gp3가 무료로 제공하는 3,000 IOPS 기준보다 더 필요로 하지 않았다. 처리량도 마찬가지로 여유로웠다 — 125 MB/s 기본값 안에 충분히 들어갔다.

"전환 후에 볼륨이 더 많은 IOPS를 필요로 하면 어떡하죠?" 톰이 마이그레이션 계획을 설명할 때 마야가 물었다.

"gp3 볼륨의 프로비저닝된 IOPS는 언제든 늘릴 수 있어요," 톰이 말했다. "마이그레이션이 아무것도 고정하지 않아요. 3,000 IOPS로 gp3에 갔다가 그게 부족하다는 걸 알게 되면, 볼륨을 다시 수정해서 더 추가하면 됩니다. 수정은 라이브예요 — 다운타임 없음, 언마운트 없음."

"그리고 gp2는 제자리에서 수정할 수 없나요?"

"gp2는 제자리에서 gp3로 수정할 수 있어요. 할 수 없는 건 gp3에서 gp2로 되돌아가는 거예요 — 적어도 쉽게는 안 되고, 그럴 이유도 없죠."

실제 마이그레이션은 8개 볼륨 전부에 걸쳐 첫 명령에서 완료까지 73분이 걸렸다. AWS는 각 볼륨을 마운트되어 사용 중인 상태로 수정했다. API 서버들은 내내 계속 트래픽을 받았다. CloudWatch는 전환 동안 I/O 지연 시간에 어떤 급증도 보이지 않았다 — 전환은 실행 중인 애플리케이션 관점에서 완전히 투명했다.

"그게 '다운타임 필요 없음'이 실제로 어떤 모습인지군요," 톰이 캡처한 전후 메트릭을 보며 레오가 말했다. "저는 '다운타임 없음'이 '짧은 재시작'을 의미한다고 가정했어요. 그건 애플리케이션 관점에서 말 그대로 아무것도 바뀌지 않는다는 뜻이네요."

절약: gp2는 GB당 월 $0.10였고, gp3는 GB당 월 $0.08였다. 960 GB에 대해: 월 $96 대 $76.80. 월간 절약: $19.20. 그 자체로는 변혁적이지 않지만, 그것이 대표하는 규율은 그랬다. 그 시점부터 생성된 모든 새 볼륨은 기본적으로 gp3를 사용했다. 톰이 그날 아침 작성한 조직 규칙: gp2 볼륨 금지. EBS 볼륨을 생성하는 모든 엔지니어는 구체적이고 문서화된 다른 이유가 없는 한 gp3를 사용해야 한다.

**IOPS와 처리량**: gp3 볼륨은 기본적으로 3,000 IOPS와 125 MB/s 처리량을 추가 비용 없이 제공한다. 워크로드가 필요로 하면 더 프로비저닝할 수 있다. 프로비저닝된 성능이 실제로 활용되고 있는지 검토하라.

같은 감사에서, 톰은 10,000 프로비저닝 IOPS를 가진 두 개의 볼륨을 발견했다 — 그가 합류하기 전부터의 레거시 설정으로, 이후 Aurora로 마이그레이션된 데이터베이스에 맞게 크기가 정해진 것이었다. 그는 CloudWatch 메트릭을 확인했다: 실제 평균 IOPS는 1,200이었다. 그는 프로비저닝된 IOPS를 4,000으로 줄였다 (실제 피크보다 위의 안전 여유).

월간 절약: 아무도 쓰지 않던 성능 여유에 대해 비용을 내고 있던 프로비저닝 IOPS 비용 $68.

**스냅샷 라이프사이클**: EBS 스냅샷은 증분적이다 (각 스냅샷은 이전 것 이후의 변경만 저장한다) 하지만 쌓인다. Nimbus 초창기의 오래된 스냅샷이 아직 존재했다. 톰은 30일치 일일 스냅샷을 유지하고 나머지는 삭제했다.

**EFS: 스토리지 클래스와 Intelligent-Tiering 결정**

Amazon EFS에는 자체 스토리지 클래스가 있다:

- **EFS Standard**: 자주 접근되는 파일용. 더 높은 비용.
- **EFS Infrequent Access (IA)**: 30일 동안 접근되지 않은 파일용. Standard보다 92% 저렴.
- **EFS Archive**: 90일 동안 접근되지 않은 파일용. IA보다 더 저렴.

**EFS Intelligent-Tiering**: 접근 패턴에 따라 파일을 스토리지 클래스 간에 자동으로 이동한다.

톰은 EFS 볼륨에서 Intelligent-Tiering을 활성화했다. 6주 후, 파일의 68%가 Infrequent Access로 이동했다. 월간 EFS 비용은 $89에서 $31로 떨어졌다.

하지만 Intelligent-Tiering과 수동 라이프사이클 규칙 사이의 선택은 사소하지 않았다. 톰은 그것을 고민했었다.

"잠깐 — 근데 *왜* 그냥 수동 라이프사이클 규칙을 설정하는 대신 Intelligent-Tiering을 하는 거죠?" 마야가 물었다. "30일 넘은 파일이 접근되지 않는다는 걸 안다면, 그냥 규칙을 설정하고 끝내면 안 되나요?"

"Intelligent-Tiering은 다시 돌아오는 파일을 처리해요," 톰이 말했다. "제가 30일 후 파일을 IA로 옮기는 라이프사이클 규칙을 설정하고, 그런 다음 누군가 IA에 6개월 동안 있던 파일에 접근하면, 그건 IA에 머물러요. Intelligent-Tiering에서는, 접근이 재개되면 파일이 자동으로 Standard로 돌아갑니다. 양방향이에요."

"그럼 언제 라이프사이클 규칙을 선호하나요?"

"접근 패턴이 단방향이라고 확신할 때요. 아카이브 로그 — 그것들은 기록되고, 나이 들고, 컴플라이언스 감사를 위해 한 번 접근됐다가 그 후로는 다시는 접근되지 않아요. 그 패턴에는, 90일 후 Archive로 옮기는 라이프사이클 규칙이 모니터링 오버헤드를 내지 않으니 Intelligent-Tiering보다 싸요."

"모니터링 요금이 있나요?"

"S3 Intelligent-Tiering의 경우, 네, 그래서 우리가 S3 라이프사이클 장에서 소형 객체 경제학을 다뤘죠. EFS의 경우, 결정은 대부분 접근 패턴에 관한 거예요: 파일이 다시 핫해질 수 있다면 Intelligent-Tiering이 더 안전해요. 한 방향으로만 나이 든다면, Archive로 가는 라이프사이클 규칙이 더 싸고 단순하죠."

**S3 비용 할당 태그: 누가 무엇에 쓰는지 찾기**

Nimbus가 성장하면서, 여러 팀이 S3에 데이터를 저장하고 있었다. 분석팀은 자기 버킷이 있었다. 엔지니어링팀은 자기 버킷이 있었다. 레스토랑 데이터팀은 자기 버킷이 있었다.

청구서는 그냥 "S3: $198"만 보여줬다. 팀별 분해가 없었다.

**비용 할당 태그**는 AWS 리소스에 비즈니스 메타데이터(팀, 프로젝트, 환경)를 태깅하고, 그런 다음 AWS Cost Explorer에서 그 태그별로 분해된 비용을 볼 수 있게 한다.

톰은 모든 S3 버킷에 태그를 추가했다:
```
Team: analytics
Environment: production
Project: nimbus-core
```

태깅을 적용한 한 청구 주기 후, 그는 볼 수 있었다: "분석팀의 데이터 레이크는 월 $74. 엔지니어링 백업은 월 $43. 레스토랑 데이터는 월 $81."

이제 그는 그저 집계 숫자를 보는 대신 각 팀과 예산 대화를 할 수 있었다.

**AWS Cost Explorer와 AWS Budgets**

**AWS Cost Explorer**: 서비스, 리전, 태그, 사용 유형별로 과거 및 예측 비용을 시각화한다. 돈이 어디로 가는지 이해하는 데 필수적이다.

**AWS Budgets**: 비용이 임계값을 초과하거나 (초과할 것으로 예측될 때) 알림을 설정한다. 서비스, 리전, 태그, 또는 계정별로 예산을 짤 수 있다.

톰은 세 개의 예산을 설정했다:

1. 총 월간 청구서: 예산 금액의 90%에서 알림
2. EC2 On-Demand: On-Demand 지출이 월 $500를 초과하면 알림 (Savings Plan 간극을 신호)
3. 데이터 전송 아웃: 월 $200에서 알림 (데이터 전송 비용은 예기치 않게 급증할 수 있음)

Budgets는 Slack 채널로 알림을 보냈다. 팀은 월간 청구서에서 발견하는 대신, 한도에 다가가고 있을 때 그것을 보았다.

**모든 줄이 적힌 영수증: 비용 및 사용 보고서**

Cost Explorer는 톰의 질문 대부분에 답했다. 그러다 그것이 답할 수 없는 하나에 부딪혔다: "정확히 어떤 S3 버킷이, 시간별로, 지난 화요일의 급증을 일으켰는가 — 그리고 어떤 태그 아래에서?"

포렌식 수준의 질문을 위해, AWS는 **비용 및 사용 보고서(CUR)** — 이제 **Data Exports**를 통해 제공됨 — 를 제공한다. AWS가 생산하는 가장 상세한 청구 데이터다: 모든 항목, **리소스별, 시간별**, 태그와 함께, 당신이 소유한 S3 버킷으로 전달된다. 그것은 대시보드가 아니다; 원장 그 자체다. 표준 패턴은 그것을 Athena로 쿼리하거나 (컬럼형 포맷으로 떨어진다) 대시보드를 위해 QuickSight에 공급하는 것이다.

시험에서의 분업: **Cost Explorer** = 콘솔에서의 대화형 시각화와 예측. **Budgets** = 임계값 알림. **CUR/Data Exports** = 당신만의 분석을 위해 S3로 전달되는 가장 세분화된 데이터. 질문이 "커스텀 분석을 위한 리소스 수준의 시간별 비용 데이터"라고 하면 — 그것은 CUR이지 Cost Explorer가 아니다.

"우리가 그냥 이걸 절대 안 본다면 어떻게 되는지 생각해 봤나요?" 프리야가 물었다. "이틀 만에 $6,700를 찾았어요. 아직 뭐가 숨어 있을까요?"

"정기 감사요," 그녀가 이어갔다. "월별 Cost Explorer 검토. AWS Trusted Advisor는 연결되지 않은 볼륨과 유휴 리소스를 자동으로 표시해요. 알려진 낭비 패턴의 정리를 자동화하세요: N일보다 오래된 스냅샷 삭제, 연결되지 않은 EBS 볼륨에 알림, 오래된 S3 버전 만료."

**S3 Requester-Pays: 전송 비용 떠넘기기**

스토리지 감사 동안, 톰은 예상하지 못한 상황을 발견했다.

Nimbus의 레스토랑 파트너들은 자기 메뉴 사진 자산을 다운로드해야 했다 — 주문 플랫폼이 고객에게 제공하는 처리되고 크기 조정된 이미지들. 메뉴를 업데이트하는 레스토랑에게, 이것은 50 MB(작은 업데이트)에서 800 MB(전체 시즌 갱신)의 이미지 파일을 다운로드하는 것을 의미했다. 현재, Nimbus는 모든 다운로드에 대해 아웃바운드 데이터 전송 비용을 내고 있었다: S3에서 파트너 위치로 GB당 $0.09.

287개 레스토랑 파트너에, 월평균 한 번의 메뉴 갱신과 평균 200 MB 다운로드로, 계산은: 287 × 0.2GB × $0.09 = 월 $5.17. 현재 규모에서는 유의미하지 않았다.

"2,000개 레스토랑에서는 어떻게 되죠?" 톰이 물었다.

"같은 계산이요," 마야가 말했다. "월 약 $36."

"10,000개 레스토랑이고, 파트너들이 큰 시즌 자산 팩을 다운로드한다면요 — 가령 홀리데이 메뉴 업데이트로 2 GB라고 하면?"

그는 계산했다. 10,000 × 2GB × $0.09 = 월 $1,800의 데이터 전송, 그저 파트너들이 필요한 자산을 다운로드하는 것만으로.

"그건 실재하는 숫자네요," 프리야가 말했다.

"그 청구서가 우리가 시리즈 B를 마무리하려는 바로 그 달에 나타나면 어떻게 되는지 생각해 봤나요?" 프리야가 이어갔다.

"S3 Requester-Pays," 톰이 말했다.

S3에는 Requester-Pays라는 기능이 있다: 버킷에서 활성화되면, 요청을 하는 주체가 — 버킷 소유자가 아니라 — 데이터 전송 및 요청 비용을 낸다. 버킷 소유자는 여전히 스토리지 비용을 낸다. 하지만 버킷에서의 모든 다운로드는 요청자의 AWS 계정에 청구된다.

트레이드오프는 접근성이다. Requester-Pays는 요청자가 유효한 계정을 가진 AWS 고객일 것을 요구한다 — Requester-Pays 버킷에 대한 인증되지 않은 또는 익명 접근은 오류를 반환한다. 다양한 수준의 기술적 정교함을 가진 사업체인 Nimbus의 레스토랑 파트너들에게, 자기 메뉴 자산을 다운로드하기 위해 AWS 계정을 갖도록 요구하는 것은 실현 가능한 모델이 아니었다.

"직접적인 파트너 접근에는 Requester-Pays를 쓸 수 없어요," 마야가 말했다. "우리 파트너 대부분은 사진을 다운로드하려고 AWS 계정을 설정하지 않을 거예요."

"맞아요," 톰이 말했다. "하지만 B2B 통합에는 쓸 수 있어요 — 기술팀과 AWS 계정을 가진 더 큰 체인들. 길모퉁이의 작은 레스토랑이 아니라, 엔지니어링팀이 있고 우리 API와 직접 통합하는 50개 지점 버거 체인 같은 곳. 그 세그먼트에는 Requester-Pays가 합리적이죠."

"그럼 나머지는요?"

"그들에게는 미리 서명된 S3 URL을 사용하는 다운로드 포털을 줘요. 전송은 여전히 AWS를 통하고, 비용은 여전히 우리 거예요 — 하지만 그건 이미 파트너 가격에 반영되어 있죠. Requester-Pays 옵션은 더 큰 파트너를 위한 계약 협상에 넣을 만한 거예요, 오늘 배포할 게 아니라."

톰은 그것을 스프레드시트의 "향후 최적화" 아래에 추가했다: AWS 계정을 가진 엔터프라이즈 파트너를 위한 S3 Requester-Pays. 2,000개 레스토랑에 엔터프라이즈 고객 20%, 월 2 GB 다운로드로: 잠재적으로 파트너에게 떠넘길 수 있는 월 $72. 그 규모에서는 작지만, 자산 팩이 커지면 같은 패턴이 유의미해진다. 파트너 수가 1,000을 초과하거나 엔터프라이즈 파트너들이 더 큰 시즌 패키지를 끌어가기 시작하면 검토하라.

"교훈은 늘 같은 거예요," 톰이 말했다. "규모에 도달하기 전에 규모에서 비용이 어떻게 되는지 알아두는 것. 오늘의 $5 문제가 3년 후의 $1,800 문제예요. 지금 그것을 대비해 설계하는 건 비용이 들지 않아요."

**거버넌스: 자동 삭제 vs 알림만**

자동화 질문은 가장 많은 의견 불일치를 낳은 것이었다.

"연결되지 않은 EBS 볼륨을 14일 후 자동 삭제해야 할까요?" 톰이 물었다. "AWS Config 규칙이 그것들을 표시할 수 있어요. Lambda가 자동으로 삭제할 수 있고요."

"안 돼요," 프리야가 즉시 말했다.

"왜요?"

"자동 삭제는 결국 이유가 있어 연결되지 않았던 무언가를 삭제하게 될 거라서요. 누군가 볼륨을 다른 인스턴스로 옮기려고 분리했는데, 변경이 검토되는 동안 12일째 앉아 있을 수도 있어요. 14일째의 자동 삭제는 그 데이터를 파괴하죠."

"그럼 알림만요?" 톰이 말했다. "알림은 받되 자동으로 삭제하진 않는 거죠."

"알림 먼저요," 프리야가 말했다. "사람이 결정을 내리도록 강제해요. 알림은: '이 볼륨이 14일 동안 연결되지 않았습니다. 필요하면 `keep: true`로 태그하거나, 그렇지 않으면 다음 검토에서 삭제 대상으로 표시됩니다.' 그러면 인간의 결정이 태그의 존재나 부재로 문서화돼요."

"그건 더 느려요," 레오가 말했다.

"더 느리고 데이터를 파괴할 가능성이 더 낮죠," 프리야가 말했다. "우리는 이미 방치로 $3,200를 잃었어요. 자동화로 데이터를 잃은 적은 없고요. 저는 어느 쪽을 유지하고 싶은지 알아요."

톰은 하이브리드에 도달했다: 7일에 자동 알림, 향후 알림을 억제하려면 `keep: true` 태그를 요구, 그리고 태그 없고 연결되지 않은 모든 볼륨에 대한 주간 보고서를 팀이 함께 검토하도록 실행. 자동 삭제는 없음.

**변형: 정리가 절약하는 것보다 더 비쌀 때**

추가 스냅샷의 안전이 필요하다면 유지하라 — 하지만 접근 없이 90일이 넘은 모든 스냅샷은 자기 자리를 벌어야 한다. 트레이드오프는 비대칭적이다: 필요했던 스냅샷을 삭제하는 것은 인시던트의 비용이 들고, 필요 없던 스냅샷을 유지하는 것은 작은 월 요금만 든다. 컴플라이언스에 민감한 데이터의 경우, 오래된 스냅샷을 유지하는 비용은 실재하지만 보통 감사관이 요청할 때 그것이 없는 비용보다는 적다. 14개월 전에 실행된 테스트의 개발 스냅샷이라면, 계산은 반대 방향으로 간다.

접근 패턴이 불확실한 파일에 EFS Intelligent-Tiering을 활성화하면, 자동 계층화가 돈을 절약하고 지속적인 개입이 필요 없다. 파일이 예측 가능하게 아카이브 접근으로 나이 든다면, 직접적인 라이프사이클 규칙이 더 단순하다. 활성화하기 전에 측정하라.

SAA-C03 연결: 시험은 접근 빈도 시나리오가 주어졌을 때 S3 스토리지 클래스(Standard, IA, Glacier) 중에서 선택할 수 있는지를 테스트한다. 같은 논리가 여기에 적용된다 — 올바른 클래스는 데이터가 얼마나 자주 접근되는지에 달려 있다.

**방치의 비용**

톰은 스프레드시트를 만들었다. 그는 Nimbus가 다음에 얼마를 썼는지 계산했다:

- 연결되지 않은 EBS 볼륨 (16개월): $3,200
- 오래된 S3 스냅샷 (발견 및 삭제): $890
- 필요 없는 프로비저닝 IOPS: $816
- gp2에서 gp3 마이그레이션 절약 (더 일찍 했다면, 추정치): 18개월에 걸쳐 $346
- 쌓이는 비현행 S3 버전: $1,340
- 불완전한 멀티파트 업로드: $94

식별된 총 낭비: 18개월에 걸쳐 약 $6,700.

"6,700달러," 마야가 말했다.

"방치에서요," 톰이 말했다. "잘못된 아키텍처 결정에서가 아니라. 정리하지 않은 것에서."

"체계적인 해결책은요?"

"그리고," 톰이 덧붙였다, "비용 위생을 배포 프로세스의 일부로 만들어요. 엔지니어가 EC2 인스턴스를 종료하면, 명시적으로 옵트아웃하지 않는 한 EBS 볼륨이 자동으로 삭제되도록요."

## 강점과 한계

**비용 최적화 규율**:

- 정기 검토는 누적되는 낭비가 유의미해지기 전에 잡아낸다
- 태깅은 책임성을 가능하게 한다 — 팀이 자기 비용을 본다
- 자동 알림은 청구 놀라움을 방지한다
- 라이프사이클 정책과 적정 크기 조정은 종종 한 번 설정하면 잊어도 되는 절약이다

**복잡해지는 지점**:

- 많은 팀이 있는 큰 계정에서 낭비를 식별하려면 중앙화된 도구가 필요하다
- 일부 낭비는 의도적이다 ("만약을 위해" 추가 스냅샷 유지) — 비용/위험 트레이드오프는 판단의 문제다
- gp3 마이그레이션은 신중한 검증이 필요하다 (IOPS와 처리량 기본값이 일부 엣지 케이스에서 gp2 동작과 다를 수 있다)
- 비용 할당 태그는 모든 팀에 걸친 규율이 필요하다 — 일관되지 않은 태깅은 데이터를 불완전하게 만든다
- 자동 삭제 자동화는 스토리지에 위험하다 — 볼륨과 스냅샷에는 알림 후 검토가 더 안전하다

## 요약

스토리지 감사는 이틀이 걸렸다. 그것이 드러낸 낭비 — 보이지 않는 누적 18개월에 걸친 $6,700 — 는 의사결정의 실패라기보다 주의의 실패였다. 의도적으로 잘못 구성된 것은 없었다. 스냅샷, 연결되지 않은 볼륨, 쌓이는 버전 기록, 불완전한 멀티파트 업로드: 각각은 그 당시에는 말이 됐고 그저 다시 들여다보지 않았을 뿐이다. 교훈은 특정 AWS 서비스에 관한 것이 아니었다. 들여다보는 습관을 기르는 것에 관한 것이었다.

- **스토리지 비용은 보이지 않게 쌓인다** — 정기 감사가 필수다.
- **연결되지 않은 EBS 볼륨**은 흔한 낭비의 원천이다. 삭제하라 (또는 인스턴스 종료 시 삭제를 자동화하라).
- **EBS 적정 크기 조정**: gp2를 gp3로 마이그레이션 (일반적으로 20% 절약). 과도한 프로비저닝 IOPS 제거.
- **S3 버전 관리**: 무제한 버전 기록에 비용을 내지 않도록 비현행 버전에 라이프사이클 규칙을 활성화하라.
- **불완전한 멀티파트 업로드**: 모든 버킷에 `AbortIncompleteMultipartUpload` 라이프사이클 규칙을 추가하라. 이것은 종종 간과되고 조용히 쌓인다.
- **EFS Intelligent-Tiering**: 접근 빈도에 따라 파일을 더 낮은 비용의 계층으로 자동 이동한다. 예측 가능한 접근 패턴의 경우, 수동 라이프사이클 규칙이 더 쌀 수 있다.
- **거버넌스**: 연결되지 않은 볼륨에 7~14일 후 알림; 억제하려면 명시적 태깅을 요구. 스토리지 리소스에는 자동 삭제를 피하라.

## 시험 팁

*SAA-C03 도메인: 비용 최적화 아키텍처 설계 (도메인 4, 작업 4.1)*

- **비용 할당 태그**: 청구 콘솔에서 비용 할당을 위한 사용자 정의 태그를 활성화하고; 그런 다음 리소스에 태그를 단다. Cost Explorer는 태그별 분해를 보여준다. 시험 시나리오: "어느 부서가 가장 많은 S3 비용을 발생시키는지 식별" → 비용 할당 태그.
- **AWS Trusted Advisor**: 미활용 EC2 인스턴스, 연결되지 않은 EBS 볼륨, 유휴 로드 밸런서, 기타 낭비를 식별한다. 기본 검사는 무료; 전체 검사는 Business/Enterprise Support가 필요하다.
- **EBS 비용 구성 요소**: 스토리지 (GB당), 프로비저닝 IOPS (io1/io2 또는 추가 gp3인 경우), 처리량 (추가 gp3인 경우). 어떤 구성 요소를 적정 크기 조정할 수 있는지 알아두라.
- **S3 버전 관리 비용**: 비현행 버전은 현행 버전과 같은 요율로 저장되고 청구된다. 비현행 버전을 만료시키는 라이프사이클 규칙은 버전 관리 버킷에서 비용 통제에 핵심적이다.
- **AWS Compute Optimizer**: EC2 활용도를 분석하고 적정 크기 조정된 인스턴스 유형을 추천한다. 시험 신호: "올바른 인스턴스 유형을 선택하여 EC2 비용 절감" → Compute Optimizer.
- **AWS Cost Anomaly Detection**: ML을 사용하여 비정상적인 지출 패턴을 감지한다. 시험 신호: "예기치 않은 비용 증가를 자동으로 감지" → Cost Anomaly Detection.
- **비용 도구 라인업**: 대화형 차트/예측 → Cost Explorer. 임계값 알림 → Budgets. "커스텀 분석을 위해 S3로 전달되는 가장 세분화된, 리소스 수준/시간별 청구 데이터 (Athena/QuickSight)" → **비용 및 사용 보고서 (Data Exports)**.
- **Requester Pays**: "큰 S3 데이터셋을 공유; 소비자가 자기 다운로드 비용을 지불" → S3 Requester Pays (소유자는 스토리지만 계속 지불; 요청자는 AWS 계정으로 인증해야 함).

## 연습문제

**연습문제 1 — 회상**

EC2 인스턴스가 사용하고 있지 않은데도 연결되지 않은 EBS 볼륨이 비용을 발생시키는 이유를 설명하라. 이 낭비를 피하기 위해 엔지니어가 EC2 인스턴스를 종료할 때 어떤 절차를 따라야 하는가?

*(힌트: EBS 볼륨은 물리 디스크에 데이터를 저장하고, 그 디스크는 읽히고 있는지 여부와 상관없이 비용이 든다.)*

**연습문제 2 — SAA-C03 시나리오**

*시나리오*: 한 회사의 AWS 청구서가 6개월에 걸쳐 월 $5,000에서 $9,000로 늘어났지만, 새로운 서비스를 추가하지 않았습니다. 엔지니어링팀은 스토리지 비용이 문제라고 의심합니다. 다음 중 비용 증가를 가장 잘 식별하고 설명할 AWS 도구의 조합은?

A) 누가 새 리소스를 생성했는지 식별하기 위해 API 호출을 검토하는 AWS CloudTrail  
B) 서비스 수준 비용 분해를 위한 AWS Cost Explorer와 유휴 및 연결되지 않은 리소스 감지를 위한 AWS Trusted Advisor  
C) 리소스 활용도를 모니터링하고 비용 경보를 생성하는 Amazon CloudWatch  
D) 모든 리소스와 그 컴플라이언스 상태를 식별하는 AWS Config

**힌트 1**: "비용 증가 식별" → 서비스별 비용 분해를 시각화한다.

**힌트 2**: "유휴 및 연결되지 않은 리소스" → 특정 도구가 이것들을 사전에 식별한다.

**힌트 3**: CloudTrail은 API 호출을 로깅하고; Cost Explorer는 비용 추세를 보여준다. 어느 것이 비용 분석에 더 유용한가?

**정답**: B

**설명**: AWS Cost Explorer는 서비스, 리전, 사용 유형별로 분해된 비용 추세를 보여준다 — 어떤 서비스가 증가를 일으켰는지 식별하기에 완벽하다. AWS Trusted Advisor의 비용 최적화 검사는 연결되지 않은 EBS 볼륨, 유휴 EC2 인스턴스, 미활용 로드 밸런서, 기타 흔한 낭비 원천을 식별한다.

**왜 A가 아닌가?** CloudTrail은 누가 언제 리소스를 생성했는지 로깅하지만, 비용 추세를 직접 보여주거나 낭비를 식별하지 않는다.

**왜 C가 아닌가?** CloudWatch는 리소스 성능(CPU, 메모리)을 모니터링한다 — 적정 크기 조정에는 유용하지만 누적된 스토리지 낭비를 식별하는 데는 아니다.

**왜 D가 아닌가?** AWS Config는 리소스 구성과 컴플라이언스를 추적하지만 비용 분석 도구가 아니다.

*SAA-C03 도메인: 비용 최적화 아키텍처 설계 — 작업 4.1*

**연습문제 3 — 아키텍처 도전** *(선택)*

Nimbus의 S3 청구서는 "backups"라는 라벨이 붙은 버킷에 월 $340를 보여준다. 그 버킷은 버전 관리가 활성화되어 있고 다음을 포함한다:

- 일일 데이터베이스 스냅샷 (그들의 정책에는 7일이면 충분)
- 주간 전체 백업 (3개월 보관)
- 분기별 아카이브 (세금 컴플라이언스를 위해 7년 보관)

이 보존 요구 사항을 충족하면서 비용을 최소화하는 이 버킷의 라이프사이클 정책을 설계하라. 각 데이터 유형은 어떤 스토리지 클래스를 사용해야 하는가? 오래된 버전이 쌓이는 것을 방지하기 위해 버전 관리를 어떻게 처리할 것인가?

*(정답은 단 하나가 아니다. 목표는 라이프사이클 정책 설계를 연습하는 것이다.)*

## 크레딧 후 장면

톰은 비용 감사 결과를 팀에 게시했다.

식별된 낭비: 18개월에 걸쳐 $6,700.
구현된 변경으로 예상되는 연간 절약: $6,200.

그런 다음 그는 맨 아래에 한 줄을 추가했다: "이것은 Savings Plans (연 $14,200)나 S3 라이프사이클 정책 (연 $7,800)으로부터의 절약은 포함하지 않습니다. 결합된 연간 최적화 효과: 약 $28,200."

마야는 그것을 두 번 읽었다.

"그건 거의 주니어 엔지니어 한 명의 연봉이네요," 그녀가 말했다.

"낭비에서요," 톰이 확인했다.

"아니면," 레오가 말했다, "이런 최적화를 더 일찍 했다면 그 주니어 엔지니어를 충당했을 거라는 증거죠."

톰이 그를 바라보았다.

"그게 그것에 대해 생각하는 올바른 방식이에요," 그가 말했다. "비용 최적화는 잘라내는 것에 관한 게 아니에요. 가치를 창출하지 않는 것에 비용을 내지 않는 것에 관한 거죠."

마야는 그 문서를 회사 위키에 고정했다.

다음 장에서: 데이터베이스 계층이 같은 처리를 받고, 톰은 실제로 그가 과소투자하고 있던 한 곳을 발견한다.
