# 장 28: 보관 비용의 놀라움

톰은 EC2에 대한 세이빙 플랜을 제출했습니다. 청구서에서 다음 항목은 S3: $198/월 (장 23의 라이프사이클 정책 변경 이후 $847에서 내려왔습니다).

그런 다음 그는 EBS를 확인했습니다: $440/월.

"이게 좀 높네요," 톰은 말했습니다.

레오가 EBS 볼륨 목록을 불러왔습니다. 47개의 EBS 볼륨이 인스턴스에 연결되어 있었고, 또 다른 23개의 볼륨이 어떤 인스턴스에도 연결되어 있지 않았습니다.

"이 23개의 볼륨," 톰은 말했습니다. "무슨 것들이죠?"

레오가 확인했습니다. 그들은 모두 분리되어 있었으며 현재 사용 중인 인스턴스는 없었습니다. 대부분은 디버깅 목적으로 스크린샷에서 생성되었습니다. 일부는 인스턴스가 종료되었지만 볼륨이 삭제되지 않은 상태였습니다.

"누군가 읽지 않는 23 테라바이트의 보관 비용을 지불하고 있어요," 레오가 말했습니다.

톰은 총량을 확인했습니다: 분리된 2.3 테라바이트의 볼륨.

"분리된 볼륨으로 매달 230달러를 지출하고 있는데, 실제로 사용하지 않는 보관 비용입니다," 톰은 말했습니다. "이런 일이 얼마나 오래 되었을까요?"

레오가 생성 날짜를 확인했습니다. 가장 오래된 볼륨의 날짜는 16개월 전이었습니다.

"3,680달러," 톰은 조용히 말했습니다. "우리는 접근하지 않는 보관 비용으로 3,600달러를 지출했어요."

분리된 볼륨을 삭제했습니다. 다음 달에는 EBS 청구서가 $210로 줄었습니다.

**보관 비용 검토**

톰의 EBS 발견은 더 넓은 패턴의 증상입니다: 보관 비용이 무시되며 누적됩니다. 계산에 대한 것과는 달리(47개 서버가 실행되고 있을 때 알게 됩니다), 보관은 조용히 쌓입니다.

이것을 저장소 단위 임대와 비교해보세요. 하나의 단위를 임대하면 카드 청구서에서 명확하게 나타납니다. 하지만 프로젝트에 두 번째 단위, 몇 가지 오래된 가구에 세 번째 단위를 임대하고 그 안에 무엇이 있는지 확인하지 않으면, 매달 비용이 계속 추가되며, 당신은 실제로 저장하는 것을 완전히 잊어버린 후에도 계속 나타납니다. 클라우드 보관도 마찬가지입니다: 바이트는 거기서 앉아 있고 청구서가 도착하고, 누군가 문을 열고 필요 없는 것들로 가득 찬 것을 발견하기 전까지는 아무도 그것을 의심하지 않습니다.

자세한 보관 비용 검토에는 다음과 같은 항목들이 포함됩니다:

**S3**:

- 모든 버킷에 라이프사이클 정책이 설정되어 있나요?
- 오래된 스크린샷(RDS, EBS)은 S3에 저장되어 있나요?
- 불확실한 접근 패턴을 가진 어떤 버킷에도 인스elligent-Tiering이 적절합니까?
- 버전화된 객체가 여러 번 생성되며 실제로 사용되지 않는 경우는 무엇인가요?

**EBS**:

- 어떤 볼륨이 분리되어 있나요(현재 실행 중인 인스턴스 없음)?
- gp3 볼륨은 적절히 구성되었나요? (기본 gp3 볼륨은 필요 없는 추가된 프로비저닝 트루스피어/IOPS를 포함할 수 있습니다)
- 필요한 것보다 오래된 스크린샷을 유지하고 있나요?

**RDS**:

- 자동 백업 보존 기간이 적절히 설정되어 있나요? (더 긴 기간 = 더 많은 저장 비용)
- 오래된 인스턴스에서 생성된 수동 스크린샷은 아직 남아있나요?
- 데이터베이스 마이그레이션에서 여전히 실행 중인 읽기 복제본은 무엇인가요?

**EFS**:

- EFS 볼륨이 적절한 저장 클래스에 위치되어 있나요? (표준 vs 비주로 접근)

**S3 버전화: 숨겨진 비용**

장 5에서 언급했듯이, S3 버전화는 모든 이전 버전의 객체를 유지합니다. 이것은 안전성 측면에서는 좋지만, 버전 규칙 없이는 비용 측면에서는 매우 나쁘습니다.

버전화가 활성화된 버킷에 대해 시간이 지남에 따라:

- 1일: 이미지 업로드 (v1)
- 30일: 이미지 업데이트 (v1은 "비주로 접근" 버전, v2는 현재 버전)
- 60일: 다시 이미지 업데이트 (v1과 v2는 비주로 접근, v3는 현재 버전)
- 365일: v1, v2... v12가 모두 저장됩니다. 이미지를 12개의 복사본을 지불해야 합니다.

해결책: 비주로 접근 버전에 대한 라이프사이클 규칙 설정.

```
Expire noncurrent versions after 30 days
Delete failed multipart uploads after 7 days
```

소피아는 이 규칙을 모든 버전별 버킷에 적용했습니다. 다음 달에는 S3 저장이 18% 감소했습니다.

**EBS: 적절한 크기 조정과 gp3 업그레이드**

EBS 볼륨 가격은 두 가지 구성 요소로 이루어져 있습니다:

1. **스토리지 (GB당 월 단위)**
2. **프로비저닝된 IOPS와 트래픽량 (io1/io2에 대해 또는 추가 gp3 성능을 위해)**

**gp3 기회**: 제 6장에서 우리는 gp3가 현재 기본 설정이며 가격이 gp2보다 저렴하다는 점을 언급했습니다. Nimbus의 볼륨이 gp3가 출시되기 전에 생성되었을 수 있으며(2020년 12월에 출시됨), 여전히 gp2일 가능성이 있습니다.

소피아는 총 1,200 GB인 12개의 gp2 볼륨을 발견했습니다. 이 볼륨들을 업그레이드하여 즉시 20%의 비용 절감 효과를 얻었으며 성능 저하 없이 진행되었습니다.

**IOPS와 트래픽량**: 기본적으로 3,000 IOPS와 125 MB/s 트래픽량을 제공하는 gp3 볼륨은 추가 비용 없이 사용할 수 있습니다. 필요에 따라 더 많은 프로비저닝도 가능합니다. 실제로 사용되고 있는 프로비저닝된 성능을 검토해 보세요.

소피아는 10,000 프로비저닝된 IOPS를 가진 두 개의 gp3 볼륨을 발견했습니다. 클라우드워치 메트릭을 확인한 결과 실제 평균 IOPS가 1,200이었으므로 프로비저닝된 IOPS를 4,000으로 줄였습니다(실제 최대치보다 안전한 여유를 두었습니다).

월간 절약액: $68.

**스냅샷 라이프사이클**: EBS 스냅샷은 누적형 (각 스냅샷은 이전 스냅샷에 대한 변경 사항만 저장)이지만, 오래된 스냅샷들이 Nimbus 초기부터 존재했습니다. 소피아는 30일마다 한 번씩 생성되는 스냅샷을 유지하고 나머지는 삭제했습니다.

**EFS: 스토리지 클래스**

Amazon EFS에는 다음과 같은 스토리지 클래스가 있습니다:

- **EFS Standard**: 자주 접근하는 파일에 사용. 비용이 높습니다.
- **EFS Infrequent Access (IA)**: 30일 동안 접근되지 않은 파일에 사용. 표준보다 92% 저렴합니다.
- **EFS Archive**: 90일 동안 접근되지 않은 파일에 사용. IA보다 더 저렴합니다.

**EFS Intelligent-Tiering**: 접근 패턴을 기반으로 자동으로 스토리지 클래스를 변경합니다.

소피아는 EFS 볼륨에 인텔리전트-티어링을 활성화했습니다. 6주 후에는 68%의 파일이 Infrequent Access로 이동했습니다. 매월 EFS 비용은 $89에서 $31로 줄었습니다.

**S3 비용 할당 태그: 누가 어떤 비용을 지불하는지 찾기**

 Nimbus가 성장하면서 여러 팀이 S3에 데이터를 저장하고 있었습니다. 분석팀은 자신의 버킷을 사용했고, 엔지니어링 팀은 자신의 버킷을 사용했습니다. 식당 데이터 팀도 자신의 버킷을 사용했습니다.

계산서는 단순히 "S3: $198"만 보여주었으며 팀별로 분할되지 않았습니다.

# 비용 분석과 예산 설정

## AWS 비용 분석 및 예산

### AWS 비용 분석 (AWS Cost Explorer)

AWS 비용 분석은 서비스, 지역, 태그, 사용 유형별로 과거와 예측된 비용을 시각화합니다. 비용이 어디에 들어가는지 이해하는 데 필수적입니다.

### AWS 예산 설정 (AWS Budgets)

예산 설정은 비용이 예산의 90%를 초과할 때 알림을 보내는 기능을 제공합니다. 서비스, 지역, 태그 또는 계정별로 예산을 설정할 수 있습니다.

톰은 세 가지 예산을 설정했습니다:

1. 전체 월간 청구: 예산액의 90% 이상일 때 알림
2. EC2 온디맨드: 매월 500달러를 초과한 비용 발생 시 알림 (저장 계획 격차 신호)
3. 데이터 전송 외부: 매월 200달러를 초과할 때 알림

이 예산들은 슬랙 채널로 보내졌습니다. 팀은 예산을 초과하는 것을 미리 알 수 있었고, 매월 청구서를 확인해야 하는 번거로움을 피했습니다.

## 소홀의 비용

톰은 스프레드시트를 만들었습니다. 그는 니모스가 다음 항목에서 얼마나 지출했는지를 계산했습니다:

- 분리된 EBS 볼륨 (16개월): 3,680달러
- 오래된 S3 스냅샷 (발견하고 삭제한 것): 890달러
- 필요 없는 프로비저닝 IOPS: 816달러
- gp2에서 gp3로의 이동 비용 절약 (만약 더 일찍 진행했다면): 18개월 동안 2,160달러
- 비현행 S3 버전 누적: 1,340달러

총 낭비: 약 8,800달러(18개월간).

"여덟 천팔백 달러," 마야가 말했다.

"소홀함으로 인해 발생한 비용이에요," 톰이 말했다. "잘못된 아키텍처 결정 때문은 아니에요. 단순히 정리하지 않았기 때문이죠."

"시스템적인 해결책은?"

"정기적인 검토가 필요해요," 프리야가 말했다. "월별 AWS 비용 분석 검토. AWS 트러스트 아드바이저는 자동으로 분리된 볼륨과 비활성화 리소스를 표시합니다. 알려진 낭비 패턴을 자동으로 삭제하도록 설정하고, 오래된 스냅샷을 N일 이상 유지하지 않도록 알림을 보내세요."

"그리고," 톰이 덧붙였다, "비용 위생은 배포 프로세스의 일부가 되어야 해요. 엔지니어가 EC2 인스턴스를 종료할 때, EBS 볼륨도 자동으로 삭제되지만 명시적으로 선택하지 않는 한."

**연습 문제 2 — 시험 연습**

*상황*: 회사의 AWS 요금이 6개월 동안 $5,000에서 $9,000/month로 증가했지만 새로운 서비스를 추가하지 않았습니다. 엔지니어링 팀은 저장 공간 비용이 문제일 가능성이 있다고 생각합니다. 다음 중 가장 적합한 AWS 도구는 무엇인가요?

A) AWS CloudTrail를 사용하여 API 호출을 검토하고 새로운 리소스를 생성한 사람을 확인  
B) AWS Cost Explorer를 사용하여 서비스 별 비용 분석 및 AWS Trusted Advisor를 사용하여 비활성화 및 연결되지 않은 리소스를 감지  
C) Amazon CloudWatch를 사용하여 리소스 활용도를 모니터링하고 비용 경보를 생성  
D) AWS Config를 사용하여 모든 리소스와 그 준수 상태를 식별

**힌트 1**: "비용 증가를 확인" → 서비스 별 비용 분석을 시각화합니다.

**힌트 2**: "비활성화 및 연결되지 않은 리소스" → 특정 도구가 이러한 문제를 적극적으로 감지합니다.

**힌트 3**: CloudTrail 로그는 API 호출을 기록하고, Cost Explorer는 비용 추세를 보여줍니다. 어떤 것이 비용 분석에 더 유용한가요?

**답변**: B

**설명**: AWS Cost Explorer는 서비스 별, 지역별, 사용 유형별로 비용 추세를 시각화하여 비용 증가 원인을 식별할 수 있습니다. AWS Trusted Advisor의 비용 최적화 검사는 연결되지 않은 EBS 볼륨, 비활성화된 EC2 인스턴스, 하드웨어 적으로 사용되지 않는 로드 밸런서 등 일반적인 낭비 소스를 식별합니다.

**A는 왜 안될까요?** CloudTrail 로그는 리소스 생성자와 시간을 확인하지만 비용 추세나 낭비를 직접적으로 보여주지 않습니다.

**C는 왜 안될까요?** CloudWatch는 리소스 성능(CPU, 메모리)을 모니터링합니다 — 적정 크기 결정에 유용하지만 저장 공간 누적 낭비를 식별하는 데는 도움이 되지 않습니다.

**D는 왜 안될까요?** AWS Config는 리소스 구성과 준수 상태를 추적하지만 비용 분석 도구가 아닙니다.

**연습 문제 3 — 아키텍처 과제** *(선택사항)*

Nimbus의 S3 요금은 "백업"이라는 라벨이 붙은 버킷에서 $340/month를 보여줍니다. 버킷에는 다음과 같은 내용이 포함되어 있습니다:

- 매일 데이터베이스 스냅샷 (정책에 따라 7일 동안 충분합니다)
- 주별 전체 백업 (3개월간 유지됩니다)
- 분기별 아카이브 (세금 준수를 위해 7년간 유지됩니다)

이 요구사항을 만족하면서 비용을 최소화하기 위한 버킷의 라이프사이클 정책을 설계하세요. 각 유형의 데이터는 어떤 저장 클래스를 사용해야 할까요? 버전 관리에 대해 어떻게 처리할 것인가요?

*(단, 단일 올바른 답변은 없습니다. 목표는 라이프사이클 정책 설계 연습입니다.)*

## 캐치플레이스 장면

톰은 비용 검토 결과를 팀에게 공윈습니다.

식별된 낭비: 18개월 동안 $8,800.
변경을 실시한 후 예상 연간 절약액: $6,200.

그는 하단에 한 줄을 추가했습니다: "이것은 저가 직원의 연봉을 포함하지 않습니다."

"그게 거의 신입 엔지니어의 연봉과 같습니다," 마야가 말했습니다.

"비용 낭비에서," 톰이 확인했습니다.

"혹시," 레오가 말했습니다, "이런 최적화를 더 일찍 하면 그 신입 엔지니어의 연봉을 충당할 수 있었겠죠."

톰은 그에게 시선을 돌렸습니다.

"그렇게 생각하는 것이 옳습니다," 톰이 말했습니다. "비용 최적화는 절약하는 것만이 아닙니다. 가치를 창출하지 않는 것에 대한 비용을 지불하지 않도록 하는 것입니다."

마야는 문서를 회사 위키에 고정했습니다.

다음 장: 데이터베이스 티어도 같은 처리를 받고, 톰은 실제로 투자 부족한 한 곳을 발견하게 됩니다.
