# 21장: 코드를 위한 배송 컨테이너

"내 머신에서는 작동해요."

Leo는 이것을 큰 소리로 말하지 않는 법을 배웠다. 방어가 아니라 진단이었다. 이번에 진단은 프로덕션 EC2 인스턴스 3번이었다. 아무도 문서화하지 않은 라이브러리 패치를 6주 전에 받았고, 다른 두 인스턴스는 받지 않았으며, 다른 곳에서는 보이지 않는 버그를 유발하고 있었다.

그는 전날 밤 세 시간을 추적하는 데 보냈다.

"배포할 때마다," 그가 다음 날 아침 말했다. "여러 인스턴스에 걸쳐 조율한다. 새 버전, 다른 의존성. 스테이징에서는 작동하고, 프로덕션에서는 고장난다. 왜냐하면 환경이 달라졌기 때문이야."

"누군가 다른 것들을 업데이트하지 않고 인스턴스 3에 특정 버전의 패키지를 설치했기 때문이야," Priya가 말했다. 냉담하지 않게.

"필요했어요—"

"알아," 그녀가 말했다. "그리고 이제 인스턴스 3는 인스턴스 1과 2와 다른 히스토리를 갖고 있어. 그게 설정 드리프트야. 그것이 문제가 되기 전까지 조용해."

Lambda가 Nimbus의 소규모 서비스를 위한 유휴 서버 문제를 해결했다. 하지만 핵심 API — 모든 주문 트래픽을 운반하는 — 는 여전히 EC2에 있었다. 그리고 EC2 인스턴스는, Lambda 함수와 달리, 역사를 축적했다.

"실제 해결책은 뭐야?" Maya가 물었다.

"서버를 영구적으로 설정하는 것으로 취급하는 것을 그만해," Priya가 말했다. "그것들을 교체하는 일회용 단위로 취급하기 시작해."

1956년에서 온 비유가 있다. 누군가 "다른 운반자를 통해 물건을 안정적으로 배송하는 해결책은 무엇인가?"라고 물었을 때, 대답은: 컨테이너를 표준화하라. 내용물이 아닌 상자를 배송하라.

**컨테이너란 무엇인가?**

**컨테이너**는 애플리케이션을 실행하는 데 필요한 모든 것을 함께 패키지하는 경량의 포터블 단위다: 런타임(Python 3.11, Node.js 20, Java 17), 라이브러리 및 의존성, 설정 파일, 그리고 애플리케이션 코드 자체.

운영 체제 커널을 에뮬레이트하는 가상 머신과 달리, 컨테이너는 호스트 OS 커널을 공유하면서 다른 모든 것은 격리한다. 이것이 컨테이너를 빠르게 시작하게 하고(초, 때로는 밀리초) 작게 만든다(기가바이트가 아닌 메가바이트).

가장 인기 있는 컨테이너 기술은 **Docker**다. Docker 이미지가 청사진이다 — 애플리케이션과 그 환경의 스냅샷. Docker 컨테이너가 그 이미지의 실행 중인 인스턴스다.

핵심 속성: **불변성**. 오늘 구축된 이미지는 Docker를 지원하는 모든 호스트에서 동일하게 실행된다 — 노트북, EC2 인스턴스, 다른 데이터 센터의 서버. 환경이 구워진다. 설정 드리프트가 불가능하다.

"그러면 EC2 인스턴스에 설치된 것을 걱정하는 대신," Leo가 말했다. "모든 것을 포함하는 이미지를 구축한다. 이미지는 어디서나 같은 방식으로 실행된다."

"그리고 로컬에서 테스트하고 싶다면, 같은 이미지를 실행한다," Priya가 덧붙였다. "'내 머신에서는 작동해' 없음."

**Amazon ECS: 오케스트레이터**

하나의 컨테이너를 실행하는 것은 단순하다. 여러 호스트에 걸쳐 수십 개의 컨테이너를 실행하고, 그것들 사이에 트래픽을 라우팅하고, 실패한 컨테이너를 재시작하고, 다운타임 없이 새 버전을 배포하는 것 — 그것은 **오케스트레이터**가 필요하다.

**Amazon ECS(Elastic Container Service)**는 AWS의 관리형 컨테이너 오케스트레이션 서비스다. 다음을 정의한다:

- **작업 정의**: 실행할 컨테이너 이미지, CPU와 메모리 양, 환경 변수, 노출할 포트
- **서비스**: 실행할 작업의 복사본 수, 실패와 배포를 처리하는 방법
- **클러스터**: 기본 컴퓨팅 인프라

ECS가 나머지를 처리한다: 사용 가능한 용량에 작업 배치, 실패한 작업 재시작, 배포 중 연결 드레인, 로드 밸런서에 정상 작업 등록.

Nimbus의 경우, API가 수동으로 관리되는 배포가 있는 EC2 인스턴스에서 ECS로 이동했다. 각 새 배포는 새 Docker 이미지를 **Amazon ECR(Elastic Container Registry)** — AWS의 관리형 컨테이너 레지스트리 — 에 푸시하고, ECS가 다운타임 없이 모든 작업에 걸쳐 롤아웃했다.

**Fargate vs. EC2 Launch Type**

ECS는 두 가지 모드로 컨테이너를 실행할 수 있다:

**EC2 launch type**: 기본 EC2 인스턴스를 관리한다. 인스턴스 패치, 올바른 크기 조정, 컨테이너를 위한 충분한 용량 보장에 책임이 있다. 더 많은 제어, 더 많은 책임.

**Fargate(컨테이너를 위한 서버리스 컴퓨팅)**: AWS가 기본 인프라를 완전히 관리한다. 작업당 CPU와 메모리를 지정하면; Fargate가 자동으로 올바른 용량을 프로비저닝한다. 관리할 EC2 인스턴스가 없다. vCPU-초 및 GB-초 메모리당 비용을 지불한다.

Fargate는 "서버리스 컨테이너" 모델이다 — 서버를 관리하지 않고 컨테이너의 환경 격리를 얻는다. 트레이드오프: 기본 인스턴스 설정에 대한 제어가 적고 단위당 비용이 약간 더 높다.

Nimbus의 경우: API 서비스를 위한 Fargate. 컨테이너를 위한 EC2 인스턴스를 관리하고 싶지 않았다.

**Amazon EKS: Kubernetes가 필요할 때**

**Kubernetes**는 오픈 소스 컨테이너 오케스트레이션 시스템이다 — 본질적으로 대규모 컨테이너 관리를 위한 산업 표준. 강력하고 확장 가능하며 복잡하다.

**Amazon EKS(Elastic Kubernetes Service)**는 AWS의 관리형 Kubernetes 서비스다. AWS가 Kubernetes 제어 평면(관리 레이어)을 실행하고, 당신이 작업자 노드를 관리하거나(또는 그것들을 위해 Fargate를 사용).

ECS vs. EKS를 언제 사용해야 하는가?

**ECS 사용** 시:

- 주로 AWS에 있고 더 단순하고 AWS 기본적인 경험을 원할 때
- 팀에 기존 Kubernetes 전문 지식이 없을 때
- 운영 오버헤드를 적게 원할 때

**EKS 사용** 시:

- Kubernetes 특화 기능이 필요할 때(사용자 정의 리소스 정의, Helm 차트, Kubernetes 생태계)
- 팀이 이미 Kubernetes를 알 때
- 하이브리드 환경(일부는 온프레미스, 일부는 AWS)을 실행하고 일관된 오케스트레이션 레이어를 원할 때
- 워크로드가 Kubernetes의 확장 가능성과 일치하는 요구사항을 가질 때

"어느 것을 써야 해요?" Maya가 물었다.

"ECS요," Priya가 즉시 말했다. "Kubernetes 전문 지식이 없어요. ECS가 필요한 모든 것을 한다. 지금 Kubernetes를 추가하는 것은 실용적인 이점 없이 운영 복잡성을 추가하는 것이야."

"ECS를 넘어서면 나중에 EKS로 마이그레이션할 수 있어," Leo가 덧붙였다.

이것이 올바른 시니어 답이다: 현재 필요에 맞는 더 단순한 도구를 선택하라.

**컨테이너가 배포를 바꾸는 방법**

컨테이너 이전에, 새 버전의 Nimbus API를 배포하는 것은 다음을 의미했다:

1. 각 EC2 인스턴스에 SSH
2. Git에서 최신 코드 가져오기
3. 의존성 설치/업데이트
4. 애플리케이션 프로세스 재시작
5. 상태 확인
6. 다음 인스턴스로 이동

이것이 오류가 발생하기 쉽고 느렸다. 조율이 필요했다. 4단계가 인스턴스 4에서 실패하면, 일부 인스턴스는 이전 버전을 실행하고 일부는 새 버전 실행에 실패하는 혼합 배포가 있었다.

ECS와 컨테이너를 사용하면:

1. 새 Docker 이미지 구축(CI/CD 파이프라인에서 자동화)
2. ECR에 푸시
3. 새 이미지 버전을 사용하도록 ECS 서비스 업데이트

ECS가 롤링 배포를 처리한다: 새 이미지로 새 작업을 시작하고, 정상이 될 때까지 기다리고, 그런 다음 이전 작업을 중단한다. 제로 다운타임 배포, 자동화.

새 버전이 상태 확인에 실패하면, ECS가 배포를 중단하고 이전 버전이 계속 트래픽을 제공한다.

## 장점과 한계

**컨테이너**:

- 환경 불일치 제거("내 머신에서는 작동해")
- 빠르고 신뢰할 수 있는 배포 가능
- 불변 — 같은 이미지가 어디서나 동일하게 실행
- 효율적 — VM보다 가볍고, 더 빠른 시작

**ECS**:

- AWS 중심 워크로드에 Kubernetes보다 더 단순
- 긴밀한 AWS 통합(IAM, ALB, CloudWatch, Secrets Manager)
- Fargate 옵션이 EC2 관리를 완전히 제거

**EKS**:

- 전체 Kubernetes 호환성 — 전체 생태계 사용
- 하이브리드 환경이나 Kubernetes 전문 지식을 가진 팀에 더 적합
- ECS보다 설정 및 운영이 더 복잡

**복잡해지는 부분**:

- 컨테이너 이미지는 구축되고 버전화되어야 한다 — CI/CD 파이프라인 필요
- 컨테이너 디버깅은 전통적인 프로세스 디버깅과 다른 도구가 필요하다
- 상태가 있는 컨테이너(컨테이너의 데이터베이스)는 신중한 영구 스토리지 설정이 필요하다
- 컨테이너 간 네트워킹(서비스 간 통신)은 컨테이너 네트워킹 개념 이해가 필요하다

## 요약

- **컨테이너**는 애플리케이션 코드, 런타임, 의존성을 함께 패키지한다 — 어디서나 동일하게 실행된다.
- **Docker**는 표준 컨테이너 기술이다. 이미지가 청사진이고; 컨테이너가 실행 중인 인스턴스다.
- **ECR(Elastic Container Registry)**은 AWS의 관리형 Docker 레지스트리다 — 이미지를 여기에 저장하고 버전화한다.
- **ECS(Elastic Container Service)**가 컨테이너를 오케스트레이션한다. 작업과 서비스를 정의하면; ECS가 배치와 수명주기를 관리한다.
- **Fargate**는 컨테이너를 위한 서버리스 컴퓨팅이다 — 관리할 EC2 인스턴스가 없다.
- **EKS(Elastic Kubernetes Service)**는 관리형 Kubernetes다 — Kubernetes 기능이나 호환성이 필요한 팀을 위해.
- AWS에서 단순함을 원하면 ECS를 선택하고; Kubernetes 생태계 호환성을 위해 EKS를 선택하라.

## 시험 팁

*SAA-C03 도메인: 탄력적 아키텍처 설계(도메인 2, 태스크 2.1)*

- **ECS vs. EKS 신호**: "Kubernetes," "Helm," "기존 Kubernetes 전문 지식," 또는 "멀티 클라우드 컨테이너 오케스트레이션"을 언급하는 시험 시나리오 → EKS. 다른 모든 것 → ECS.
- **Fargate vs. EC2 launch type**: "컨테이너를 위한 EC2 인스턴스를 관리하고 싶지 않다," "서버리스 컨테이너," "인프라 관리 없음" → Fargate. "특정 인스턴스 유형 필요," "GPU 워크로드," "세밀한 인스턴스 제어" → EC2 launch type.
- **ECS 작업 역할**: EC2 인스턴스 역할처럼, ECS 작업은 IAM 역할을 갖는다. 각 작업은 다른 권한을 가질 수 있다. 시험 시나리오: "컨테이너가 S3에서 읽어야 함" → 작업 정의에 IAM 역할을 연결하라.
- **ECR 이미지 스캔**: ECR이 알려진 취약성(CVE)에 대해 컨테이너 이미지를 스캔할 수 있다. 시험 신호: "보안 취약성에 대해 컨테이너를 스캔" → ECR 이미지 스캔.
- **블루/그린 배포**: ECS는 CodeDeploy 통합을 통해 블루/그린 배포를 지원한다. 자동 롤백을 포함한 제로 다운타임 배포. 시험 패턴: "자동 롤백과 함께 다운타임 없이 배포" → ECS + CodeDeploy 블루/그린.
- **ECS Service Auto Scaling**: CPU, 메모리, 또는 사용자 정의 CloudWatch 메트릭에 따라 작업 수를 확장. 올바른 수의 실행 중인 작업으로 트래픽을 라우팅하기 위해 ALB와 함께 작동.

**힌트 2**: "서버 관리를 위한 운영 오버헤드 최소화" → Fargate(EC2 관리 없음) vs. 자체 관리 노드(여전히 EC2 관리).

**힌트 3**: "Kubernetes 경험 없음" → EKS는 ECS보다 더 많은 운영 복잡성이다.

**답**: B

**설명**: Docker로 컨테이너화하면 모든 배포가 같은 의존성과 함께 같은 이미지를 사용하도록 보장된다 — 설정 드리프트 제거. Fargate가 있는 ECS는 EC2 인스턴스를 관리하지 않는다는 것을 의미한다. 팀은 서버 유지 보수가 아닌 애플리케이션 코드와 컨테이너 정의에 집중한다. Kubernetes 경험 없이 ECS(EKS 아님)가 적합하다.

**왜 A가 아닌가?** Patch Manager가 EC2 인스턴스를 업데이트하지만 애플리케이션 간의 라이브러리 버전 불일치를 해결하지 않는다. 근본적인 문제(다른 코드 환경)는 남는다.

**왜 C가 아닌가?** 자체 관리 노드 그룹이 있는 EKS는 EC2 인스턴스를 *그리고* Kubernetes를 관리해야 한다. 어느 것도 요구사항과 일치하지 않는다.

**왜 D가 아닌가?** Elastic Beanstalk가 EC2에서 애플리케이션 배포를 관리하지만 기본적으로 컨테이너를 사용하지 않는다. 컨테이너를 사용하도록 설정할 수 있지만, 그 접근이 설명과 일치하지 않는다.

*SAA-C03 도메인: 탄력적 아키텍처 설계 — 태스크 2.1*

**연습 3 — 아키텍처 과제** *(선택 사항)*

Nimbus는 모놀리식 API를 세 마이크로서비스로 분리하고 있다: 주문 서비스, 메뉴 서비스, 알림 서비스. 각 서비스는 다른 확장 요구사항을 갖고 있다(주문 서비스는 트래픽에 따라 확장하고; 메뉴 서비스는 대부분 읽기 전용으로 안정적이며; 알림 서비스는 급격한 버스트를 갖는다).

이 세 서비스의 ECS 아키텍처를 설계하라. 서비스 간 통신을 어떻게 처리하겠는가? 하나의 ECS 클러스터를 사용하겠는가, 아니면 세 개를 사용하겠는가? 각 서비스에 대해 Auto Scaling을 어떻게 다르게 설정하겠는가?

*(단 하나의 정답은 없다. ECS에서 마이크로서비스 아키텍처를 연습하는 것이 목표다.)*

Leo가 잠시 콘솔을 응시했다.
