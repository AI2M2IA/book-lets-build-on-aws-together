# 21장: 코드를 위한 배송 컨테이너

1956년 이전에는, 화물을 배에 싣는 것이 숙련되고 전문화된 협상이었습니다. 모든 배가 다른 화물칸을 가졌습니다. 모든 항구가 다른 크레인을 가졌습니다. 모든 운송업체가 무엇이 어디로 가는지 추적하는 다른 시스템을 가졌습니다. 화물 상자가 트럭에서 부두로, 배로, 부두로, 트럭으로 이동하며 모두가 다르게 다루는 사람들의 사슬을 거쳤습니다. 화물이 분실되었습니다. 화물이 손상되었습니다. 같은 물건이, 두 번 배송되면, 다른 상태로 도착했습니다. 두 번 모두 취급이 달랐기 때문입니다.

누군가 마침내 그것을 명확하게 물었을 때, 답은: 컨테이너를 표준화하라는 것이었습니다. 모든 항구에서 문제를 해결하지 마라. 한 번만, 컨테이너 수준에서 해결하라. 내용물만이 아니라 상자를 배송하라.

표준화된 배송 컨테이너는 단지 배송을 더 빠르게 만든 것만이 아니었습니다. 그것은 배송을 *예측 가능하게* 만들었습니다. 상하이의 컨테이너 내용물은 로테르담에 도착했을 때 정확히 같은 상태였습니다 — 컨테이너가 모든 환적 지점에서 가변성으로부터 그것들을 보호했기 때문입니다.

그것이 Leo가 가진 정확히 같은 문제였습니다. Nimbus API가 모든 "항구"에서 다르게 "적재"되고 있었습니다: 스테이징이 프로덕션과 다르게 배포되었고, 인스턴스 1이 인스턴스 3과 다르게 배포되었으며, 6주간의 문서화되지 않은 변경이 플릿을 예측 불가능하게 만들었습니다.

컨테이너는 Leo를 더 빠른 개발자로 만들지 못할 것입니다. 그것은 배포를 예측 가능하게 만들 것입니다.

---

Lambda 마이그레이션은 소규모 서비스에 대한 EC2 청구서를 줄였습니다. 하지만 핵심 API는 달랐습니다 — 그것은 끊임없이 실행되었고, 모든 주문 트래픽을 운반했으며, 8개월 동안 구성 히스토리를 축적해 왔습니다. Lambda는 유휴 상태를 해결했습니다. 컨테이너는 불일치를 해결할 것입니다.

핵심 API는 유휴 상태가 아니었습니다; 그것은 Lambda로 옮길 수 없었습니다. 하지만 그것에는 다른 문제가 있었습니다: 그것을 실행하는 EC2 인스턴스들이 서로 갈라져 있었습니다.

---

Leo는 "내 머신에서는 작동해요"를 큰 소리로 말하지 않는 법을 배웠습니다. 그것은 방어가 아니었습니다 — 그것은 진단이었습니다. 그리고 이번의 진단은 프로덕션 EC2 인스턴스 3번이었는데, 그것은 6주 전에 아무도 문서화하지 않은 라이브러리 패치를 받았고, 다른 두 인스턴스는 받지 않았으며, 이제 거기, 그 하나의 인스턴스에만 존재하고 다른 곳 어디에서도 보이지 않는 버그를 유발하고 있었습니다.

그는 전날 밤 세 시간을 그것을 추적하는 데 보냈습니다.

"배포할 때마다," 그가 다음날 아침 말했습니다, "우리는 여러 인스턴스에 걸쳐 조율해요. 새 버전, 다른 종속성. 스테이징에서는 작동하고, 프로덕션에서는 고장나요. 환경이 갈라졌기 때문이에요."

"누군가 다른 것들을 업데이트하지 않고 인스턴스 3에 패키지를 업데이트했기 때문이지," Priya가 말했습니다. 모질지 않게요.

"특정 버전이 필요했어요—"

"알아," 그녀가 말했습니다. "그리고 이제 인스턴스 3은 인스턴스 1, 2와 다른 히스토리를 가졌어. 그게 구성 드리프트야. 문제가 되기 전까지는 조용해."

"실제 해결책이 뭐예요?" Maya가 물었습니다.

"서버를 네가 구성하는 영구적인 것으로 취급하는 걸 멈춰," Priya가 말했습니다. "그것들을 교체하는 일회용 단위로 취급하기 시작해."

**컨테이너란 무엇인가?**

"배송 컨테이너처럼 생각하세요," Leo가 마커를 집으며 말했습니다. "컨테이너는 자신이 어떤 배에 있는지 신경 쓰지 않아요. 배는 컨테이너 안에 뭐가 있는지 신경 쓰지 않아요. 그들은 치수와 잠금 메커니즘에 합의했어요. 다른 모든 건 상자 안에 있어요."

**컨테이너**는 애플리케이션을 그것이 실행하는 데 필요한 모든 것과 함께 패키징하는 경량의 휴대 가능한 단위입니다: 런타임(Python 3.11, Node.js 20, Java 17), 라이브러리와 종속성, 구성 파일, 그리고 애플리케이션 코드 자체.

운영 체제 커널을 포함한 전체 컴퓨터를 에뮬레이트하는 가상 머신과 달리, 컨테이너는 다른 모든 것을 격리한 채로 호스트 OS 커널을 공유합니다. 이것이 컨테이너를 시작이 빠르고(초, 때로는 밀리초) 작게(기가바이트가 아니라 메가바이트) 만듭니다.

가장 인기 있는 컨테이너 기술은 **Docker**입니다. Docker 이미지는 청사진입니다 — 애플리케이션과 그 환경의 스냅샷. Docker 컨테이너는 그 이미지의 실행 중인 인스턴스입니다.

핵심 속성: **불변성**. 오늘 빌드된 이미지는 Docker를 지원하는 모든 호스트에서 동일하게 실행됩니다 — 노트북, EC2 인스턴스, 다른 데이터 센터의 서버. 환경이 구워져 있습니다. 구성 드리프트가 불가능합니다.

"그러니까 EC2 인스턴스에 무엇이 설치되어 있는지 걱정하는 대신," Leo가 말했습니다, "모든 것을 가진 이미지를 빌드해요. 이미지는 어디서나 같은 방식으로 실행돼요."

"그리고 로컬에서 테스트해야 하면, 같은 이미지를 실행하면 돼요," Priya가 덧붙였습니다. "더 이상 '내 머신에서는 작동해'가 없어요."

**Docker 이미지 빌드 및 ECR에 푸시하기**

어떤 오케스트레이터가 컨테이너를 관리할 수 있기 전에, Leo는 그것을 빌드하고 ECS가 가져올 수 있는 어딘가에 저장해야 했습니다.

그가 Dockerfile을 작성했습니다:

```dockerfile
FROM python:3.11-slim

WORKDIR /app

COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

COPY . .

EXPOSE 8000
CMD ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8000"]
```

핵심 라인: `FROM python:3.11-slim`. Python 3.9가 아닙니다. Python 3.10이 아닙니다. 3.11 — 팀이 합의한 특정 버전, 이미지에 구워졌습니다. 이 이미지를 실행하는 모든 인스턴스가 정확히 Python 3.11을 사용할 것입니다. decimal 모듈 반올림 동작이 어디서나 동일할 것입니다.

그가 이미지를 로컬에서 빌드했습니다: `docker build -t nimbus-api:1.0.0 .`

빌드가 4분 걸렸습니다. Docker가 베이스 이미지를 가져오고, 종속성을 설치하고, 애플리케이션 코드를 복사하고, `nimbus-api:1.0.0`으로 태그된 이미지를 만들었습니다.

그가 그것을 로컬에서 실행했습니다: `docker run -p 8000:8000 nimbus-api:1.0.0`

API가 시작되었습니다. 같은 포트, 프로덕션 서버와 같은 동작 — 환경이 동일했기 때문입니다.

그러고 나서 그가 그것을 ECR에 푸시했습니다:

```bash
# Docker를 ECR에 인증
aws ecr get-login-password --region us-west-2 |   docker login --username AWS --password-stdin   123456789012.dkr.ecr.us-west-2.amazonaws.com

# ECR을 위해 이미지에 태그 지정
docker tag nimbus-api:1.0.0   123456789012.dkr.ecr.us-west-2.amazonaws.com/nimbus-api:1.0.0

# 푸시
docker push 123456789012.dkr.ecr.us-west-2.amazonaws.com/nimbus-api:1.0.0
```

푸시가 2분 걸렸습니다. ECR이 이미지를 저장하고, 즉시 이미지 스캔을 트리거하고, 5분 이내에 결과를 보고했습니다.

**Amazon ECS: 오케스트레이터**

하나의 컨테이너를 실행하는 것은 단순합니다. 여러 호스트에 걸쳐 수십 개의 컨테이너를 실행하고, 그들 사이에 트래픽을 라우팅하고, 실패한 컨테이너를 재시작하고, 다운타임 없이 새 버전을 배포하는 것 — 그것은 **오케스트레이터**가 필요합니다.

**Amazon ECS(Elastic Container Service)**는 AWS의 관리형 컨테이너 오케스트레이션 서비스입니다. 다음을 정의합니다:

- **태스크 정의**: 어떤 컨테이너 이미지를 실행할지, 얼마나 많은 CPU와 메모리, 어떤 환경 변수, 어떤 포트를 노출할지
- **서비스**: 태스크의 사본을 몇 개 실행할지, 실패와 배포를 어떻게 처리할지
- **클러스터**: 기반 컴퓨팅 인프라

ECS가 나머지를 처리합니다: 사용 가능한 용량에 태스크 배치, 실패한 태스크 재시작, 배포 중 연결 드레인, 정상 태스크를 로드 밸런서에 등록.

Nimbus의 경우, API가 수동으로 관리되는 배포를 가진 EC2 인스턴스에서 ECS로 이동했습니다. 각 새 배포가 새 Docker 이미지를 **Amazon ECR(Elastic Container Registry)** — AWS의 관리형 컨테이너 레지스트리 — 에 푸시했고, ECS가 그것을 모든 태스크에 걸쳐 제로 다운타임으로 롤아웃했습니다.

**Fargate vs EC2 Launch Type**

ECS는 두 가지 모드로 컨테이너를 실행할 수 있습니다:

**EC2 launch type**: 기반 EC2 인스턴스를 여러분이 관리합니다. 인스턴스 패치, 적절한 크기 조정, 컨테이너를 위한 충분한 용량 보장에 대한 책임이 있습니다. 더 많은 제어, 더 많은 책임.

**Fargate(컨테이너를 위한 서버리스 컴퓨팅)**: AWS가 기반 인프라를 완전히 관리합니다. 태스크당 CPU와 메모리를 지정하면; Fargate가 적절한 용량을 자동으로 프로비저닝합니다. 관리할 EC2 인스턴스 없음. vCPU-초와 메모리 GB-초당 지불합니다.

Fargate는 "서버리스 컨테이너" 모델입니다 — 서버를 관리하지 않고 컨테이너의 환경 격리를 얻습니다. 절충안: 기반 인스턴스 구성에 대한 제어가 적고 단위당 비용이 약간 더 높습니다.

"그게 월 얼마나 들죠?" Tom이 가격 계산기를 불러오며 물었습니다. "Fargate 대 EC2 launch type — 실제 숫자를 보고 싶어요."

Leo의 직감 추정 — 모두가 가지고 다니는 것 — 은 Fargate가 더 비쌀 것이라는 것이었습니다. 서버리스 편의, 프리미엄 가격. 그는 EC2보다 아마 20~30% 정도 위일 것이라고 짐작했습니다.

"실제 숫자를 돌려봐," Tom이 말했습니다. 그게 Tom이었으니까요.

Nimbus API 서비스는 3개 태스크를 실행했고, 각각 0.5 vCPU와 1GB 메모리가 필요했으며, 24시간 내내였습니다:

**Fargate**: vCPU-시간당 $0.04048 × 0.5 × 3 × 720시간 = CPU에 대해 월 $43.72. GB-시간당 $0.004445 × 1 × 3 × 720 = 메모리에 대해 월 $9.60. 총: 월 $53.32.

**EC2 launch type**(시간당 $0.0416의 t3.medium × 3): $0.0416 × 3 × 720 = 월 $89.86.

"잠깐," Tom이 말했습니다. "Fargate가 더 싸요?"

"이 크기에서는, 네," Leo가 말했습니다. "Fargate는 할당한 것에 정확히 요금을 부과해요. EC2 인스턴스는 오버헤드가 있어요 — OS와 ECS 에이전트가 컨테이너가 시작되기도 전에 일부 CPU와 메모리를 소비해요. t3.medium은 2 vCPU와 4GB를 주지만, 우리는 컨테이너당 0.5 vCPU와 1GB를 사용해요. 나머지는 낭비돼요."

"하지만 EC2 launch type은 여러 태스크를 한 인스턴스에 채울 수 있게 해줘요."

"네. 더 큰 규모에서는, 신중한 빈 패킹으로, EC2 launch type이 더 저렴해져요. 우리 규모에서는 — 세 개 태스크 — Fargate가 이겨요."

Tom이 이것을 적었습니다.

Nimbus의 경우: API 서비스에 Fargate. 그들은 컨테이너를 위한 EC2 인스턴스를 관리하고 싶지 않았습니다.

Fargate로 컨테이너화하면, 모든 EC2 관리 오버헤드를 제거합니다 — 하지만 인스턴스 유형을 커스터마이징하는 능력을 포기하게 되는데, 이것은 GPU 워크로드나 특수 네트워킹에 중요합니다. AWS 네이티브 단순성을 위해 ECS를 선택하면, 긴밀한 IAM과 ALB 통합을 얻습니다 — 하지만 Kubernetes 생태계에서 차단되어, 나중에 멀티 클라우드 이식성이 필요하면 재설계가 필요합니다.

**Amazon EKS: Kubernetes가 필요할 때**

**Kubernetes**는 오픈 소스 컨테이너 오케스트레이션 시스템입니다 — 본질적으로 대규모 컨테이너 관리를 위한 업계 표준. 그것은 강력하고, 확장 가능하며, 복잡합니다.

**Amazon EKS(Elastic Kubernetes Service)**는 AWS의 관리형 Kubernetes 서비스입니다. 그것은 Kubernetes 제어 평면(관리 레이어)을 여러분을 위해 실행하고, 여러분은 작업자 노드를 관리합니다(또는 그것들을 위해서도 Fargate를 사용합니다).

여러분은 궁금해할지 모릅니다: Kubernetes가 업계 표준이고 모든 채용 공고가 그것을 언급한다면, 왜 그냥 그것을 쓰지 않죠? 왜냐하면 "업계 표준"은 전담 플랫폼 팀을 가진 대기업이 사용하는 것을 설명하기 때문입니다. 음식 주문 앱을 만드는 6명 팀에게, Kubernetes는 지금 당장 실용적 이익 없이 운영 복잡성을 추가합니다. 복잡성은 실재합니다; 이익은 이 규모에서는 이론적입니다.

Kubernetes는 대부분의 팀이 필요로 하지 않는 복잡성 수준에서 가치를 제공합니다: 내부 플랫폼 구축을 위한 커스텀 리소스 정의, 고급 스케줄링 제약, 세밀한 배포 제어를 위한 파드 중단 예산, 그리고 수백 개의 마이크로서비스 사이의 트래픽 관리를 위한 서비스 메시 통합. 이것들은 진정한 기능입니다. 그것들은 또한 Nimbus 규모의 스타트업이 결코 사용하지 않을 기능이기도 합니다.

여기서의 엔지니어링 원칙은 때때로 YAGNI라고 불립니다: You Aren't Gonna Need It(필요하지 않을 거야). ECS는 Nimbus에게 현재 필요한 모든 것을 줍니다. EKS는 그들에게 필요한 것보다 더 많은 것을, 더하기 상당한 학습 곡선과 운영 오버헤드를 줍니다. "나중에 유용할 거야"는 지금 복잡성을 추가하는 좋은 이유가 아닙니다.

언제 EKS를 ECS 대신 사용해야 할까요?

**ECS 사용** 시:

- 주로 AWS에 있고 더 단순하고 더 AWS 네이티브한 경험을 원할 때
- 팀에 기존 Kubernetes 전문성이 없을 때
- 운영 오버헤드를 적게 원할 때

**EKS 사용** 시:

- Kubernetes 특화 기능(커스텀 리소스 정의, Helm 차트, Kubernetes 생태계)이 필요할 때
- 팀이 이미 Kubernetes를 알 때
- 하이브리드 환경(일부는 온프레미스, 일부는 AWS)을 실행하고 일관된 오케스트레이션 레이어를 원할 때
- 워크로드가 Kubernetes의 확장성과 일치하는 요구사항을 가질 때

**컨테이너 네트워킹: 일시적 IP와 서비스 디스커버리**

컨테이너로 이동할 때 팀을 당황하게 하는 한 가지: 컨테이너의 IP 주소가 재시작될 때마다 바뀝니다.

EC2 세계에서, 인스턴스는 상대적으로 안정적인 프라이빗 IP를 가졌습니다. 여러분은 (그러면 안 되지만) 그것들을 구성 파일에 하드코딩할 수 있었습니다. 서비스가 서로를 IP로 알았습니다.

컨테이너 세계에서, ECS의 각 태스크는 시작될 때 VPC 서브넷에서 IP를 받습니다. 그것이 중지되고 새 태스크가 시작될 때(배포나 재시작의 일부로), 그 새 태스크는 다른 IP를 받습니다.

"서비스가 `10.0.1.45`를 호출하도록 하드코딩되어 있는데 그 컨테이너가 `10.0.1.82`로 교체되면 어떻게 되죠?" Priya가 물었습니다. "호출하는 서비스가 아무것도 없는 곳에 도달하기 시작해요."

이것이 컨테이너 환경에서 서비스 디스커버리가 중요한 이유입니다. ECS + Application Load Balancer가 이것을 자동으로 처리합니다: ALB의 DNS 이름은 안정적입니다; ECS가 정상 태스크를 대상 그룹에 등록합니다; ALB가 현재 정상인 어떤 태스크로든 라우팅합니다. 호출하는 서비스는 개별 컨테이너 IP가 아니라 ALB DNS 이름에 통신합니다.

내부 서비스 간 통신(사용자 대면이 아닌)의 경우, **AWS Cloud Map**이 서비스 디스커버리를 제공합니다: 각 ECS 서비스가 Cloud Map에 등록되고, 이것이 안정적인 DNS 이름을 제공합니다. 주문 서비스가 `http://notification.nimbus.local:8080`을 호출하면, Cloud Map이 그것을 알림 서비스의 현재 정상인 어떤 태스크로든 해석합니다.

"그러니까 컨테이너가 IP가 아니라 DNS 이름을 통해 서로 통신하는 거네요?" Leo가 확인했습니다.

"맞아요. IP는 일시적이에요. DNS 이름이 계약이에요."

**비밀 주입: 환경 변수에 비밀 없음**

원래의 EC2 배포에는 Priya가 몇 달 동안 지적해 온 문제가 있었습니다: 비밀(데이터베이스 비밀번호, API 키, SES 자격 증명)이 배포 스크립트를 통해 설정되어 EC2 인스턴스의 환경 변수에 저장되었습니다.

환경 변수는 인스턴스에서 실행되는 모든 프로세스가 접근할 수 있습니다. 그것들은 디버깅 도구에, 일부 충돌 보고서에, 프로세스 목록에 나타납니다. 그것들은 또한 그것들을 로그하면 CloudWatch에서 보입니다(일부 개발 도구가 기본적으로 그렇게 합니다).

컨테이너는 이것을 자동으로 해결하지 않습니다 — 여러분은 여전히 ECS 태스크 정의에서 비밀을 환경 변수로 전달할 수 있습니다. 그리고 ECS 태스크 정의는 AWS 콘솔에 저장되어, ECS 액세스를 가진 누구에게나 보입니다.

올바른 패턴: **AWS Secrets Manager + ECS 태스크 정의 통합**.

데이터베이스 비밀번호를 태스크 정의에 저장하는 대신:

```json
"secrets": [
  {
    "name": "DB_PASSWORD",
    "valueFrom": "arn:aws:secretsmanager:us-west-2:123456789012:secret:nimbus/prod/db-password"
  }
]
```

ECS가 태스크 시작 시점에 Secrets Manager에서 비밀을 검색하여 환경 변수로 컨테이너에 주입합니다. 비밀 값은 결코 태스크 정의에 저장되지 않습니다 — 오직 Secrets Manager 비밀의 ARN만요. 컨테이너가 런타임에 값을 받습니다. Secrets Manager가 태스크 정의를 변경하지 않고 값을 교체할 수 있습니다.

"그러면 누군가 태스크 정의를 읽으면요?" Priya가 물었습니다. "그들은 Secrets Manager ARN을 보겠지만, 값은 못 봐요."

"그리고 올바른 IAM 권한 없이는," Leo가 확인했습니다, "Secrets Manager에서 값도 검색할 수 없어요."

"그게 설계야," Priya가 말했습니다. "태스크의 실행 역할이 그 특정 비밀을 읽을 권한을 가져. 다른 건 없어. 태스크 정의를 손상시키면 비밀번호가 아니라 ARN을 얻을 뿐이야."

"우리가 어느 걸 써야 해요?" Maya가 물었습니다. "그리고 왜 Kubernetes는 안 돼요? 모든 채용 공고에 있어요. 모든 컨퍼런스 발표에요."

"ECS," Priya가 즉시 말했습니다. "우리는 Kubernetes 전문성이 없어. ECS가 우리가 필요한 모든 걸 해. 지금 Kubernetes를 추가하는 건 실용적 이익 없이 운영 복잡성을 추가하는 거야."

지난 회사에서 Kubernetes 클러스터를 운영했던 Soo-Jin이 고개를 끄덕였습니다. "그 호출기를 들고 다녔어요. 필요해지기 전까지는 원하지 않을 거예요."

"ECS를 넘어서 성장하면 나중에 언제든 EKS로 마이그레이션할 수 있어요," Leo가 덧붙였습니다.

이것이 올바른 시니어 답입니다: 현재 필요에 맞는 더 단순한 도구를 선택하라.

**ECR: 이미지 보안**

"그러면 누군가 취약한 베이스 이미지를 통해 침입하려 하면 어떻게 되죠?" Priya가 물었습니다. "누군가 알려진 CVE가 있는 오래된 이미지를 가져와서 애플리케이션 컨테이너에 발판을 마련하는 데 사용하면요?"

그것은 프로덕션에 어떤 컨테이너를 배포하기 전에 던질 옳은 질문이었습니다.

**Amazon ECR(Elastic Container Registry)**은 여러분의 Docker 이미지를 저장하고 배포 전에 알려진 취약점에 대해 그것들을 스캔할 수 있습니다. ECR 이미지 스캔은 알려진 CVE(Common Vulnerabilities and Exposures) 데이터베이스에 대해 이미지를 확인하고 심각도별로 문제를 표시합니다.

Priya가 작성한 정책: CRITICAL 심각도 CVE가 있는 어떤 이미지도 프로덕션에 배포되지 않을 것. CI/CD 파이프라인이 ECS 서비스를 업데이트하기 전에 스캔 결과를 확인할 것입니다. 치명적 취약점이 발견되면, 파이프라인이 실패하고 팀에 알릴 것입니다.

"그건 편집증이 아니야," Priya가 말했습니다. "그건 그저 배포 전에 확인을 하는 거야."

**컨테이너가 배포를 바꾸는 방법**

컨테이너 이전에, Nimbus API의 새 버전을 배포하는 것은 다음을 의미했습니다:

1. 각 EC2 인스턴스에 SSH
2. Git에서 최신 코드 가져오기
3. 종속성 설치/업데이트
4. 애플리케이션 프로세스 재시작
5. 상태 확인
6. 다음 인스턴스로 이동

이것은 오류가 발생하기 쉽고 느렸습니다. 조율이 필요했습니다. 인스턴스 4에서 3단계가 실패하면, 일부 인스턴스는 이전 버전을 실행하고 일부는 새 버전 실행에 실패하는 혼합 배포가 생겼습니다.

ECS와 컨테이너를 사용하면:

1. 새 Docker 이미지 빌드(CI/CD 파이프라인에서 자동화됨)
2. ECR에 푸시
3. 새 이미지 버전을 사용하도록 ECS 서비스 업데이트

ECS가 롤링 배포를 처리합니다: 새 이미지로 새 태스크를 시작하고, 그것들이 정상이 될 때까지 기다린 다음, 이전 태스크를 중지합니다. 제로 다운타임 배포, 자동화됨.

새 버전이 상태 확인에 실패하면, ECS가 배포를 중지하고 이전 버전이 계속 트래픽을 처리합니다.

**배포 최소 구성: 상태 확인**

컨테이너 배포의 전체 안전성은 상태 확인이 실제로 작동하는지에 달려 있습니다.

ECS는 두 가지 유형의 상태 확인을 사용합니다:

**컨테이너 수준 상태 확인**: Dockerfile이나 태스크 정의에 정의됩니다. 애플리케이션이 응답하는지 확인하기 위해 컨테이너 내부에서 실행됩니다.

```dockerfile
HEALTHCHECK --interval=30s --timeout=5s --retries=3   CMD curl -f http://localhost:8000/health || exit 1
```

**ALB 대상 그룹 상태 확인**: 로드 밸런서가 주기적으로 상태 엔드포인트로 HTTP 요청을 보냅니다. 상태 확인에 실패한 태스크는 대상 그룹에서 제거됩니다.

어느 상태 확인도 제대로 구성되지 않으면, ECS는 모든 태스크를 정상으로 간주합니다 — 그리고 중단 없이 고장난 이미지를 배포할 것입니다. 이것이 가장 흔한 컨테이너 배포 실수입니다.

"상태 확인 엔드포인트가 내부 정보를 누출할 수 있나요?" Priya가 물었습니다.

`/health`의 상태 확인 엔드포인트는 오직 다음만 반환했습니다: `{"status": "ok"}`. 버전 번호 없음, 종속성 상태 없음, 내부 구성 없음. 상태 응답의 어떤 정보든 애플리케이션을 매핑하는 누군가에게 유용할 수 있습니다. 상태 엔드포인트를 최소한으로 유지하십시오.

상세한 내부 상태(데이터베이스 연결성, 종속성 확인)의 경우, 별도의 인증된 `/health/detail` 엔드포인트를 사용하십시오 — VPC 내부에서만 접근 가능합니다.

**구조화된 로깅: 실행 중인 컨테이너로의 유일한 창**

EC2에서, 무언가가 잘못되면 SSH로 들어갑니다. 로그 파일을 tail합니다. 프로세스 테이블을 봅니다. 디스크 사용량을 확인합니다. 여기저기 찔러봅니다.

컨테이너에는, SSH가 없습니다. 컨테이너는 일시적입니다 — 그것은 클러스터의 어떤 호스트에서든 실행 중일 수 있고, ECS가 상태 확인에 실패하면 경고 없이 그것을 교체할 것입니다. 여러분이 SSH로 들어가는 것을 생각할 때쯤이면, 검사하고 싶었던 컨테이너가 더 이상 존재하지 않을 수 있습니다.

로그는 컨테이너화된 환경에서 디버깅 편의가 아닙니다. 그것들은 무언가가 일어났다는 유일한 증거입니다.

"그러면 컨테이너가 조용히 실패하고 우리에게 로그가 없으면 어떻게 되죠?" Priya가 컨테이너 아키텍처 검토 중에 물었습니다. "태스크가 코드 1로 종료될 수 있고 로그가 종료 전에 포착되지 않았다면 원인을 결코 모를 수 있어요."

이것은 가정이 아닙니다. 그것은 첫 컨테이너 배포에서, 일관되게 일어납니다.

올바른 패턴: 모든 컨테이너가 `awslogs` 로그 드라이버를 사용해 구조화된 로그를 **Amazon CloudWatch Logs**로 보내도록 구성하는 것. ECS가 전송을 자동으로 처리합니다 — 설치할 로그 에이전트 없음, 필요한 사이드카 컨테이너 없음.

태스크 정의에서:

```json
"logConfiguration": {
  "logDriver": "awslogs",
  "options": {
    "awslogs-group": "/ecs/nimbus-api",
    "awslogs-region": "us-west-2",
    "awslogs-stream-prefix": "ecs"
  }
}
```

컨테이너 내부에서 stdout이나 stderr에 쓰인 모든 줄이 포착되어 로그 그룹 `/ecs/nimbus-api`로 보내지며, 태스크 ID별로 정리됩니다. ECS가 각 태스크에 대해 새 로그 스트림을 생성하므로, 실패한 특정 컨테이너의 로그를 찾을 수 있습니다 — 그것이 교체된 후에도요.

태스크 실행 역할은 CloudWatch Logs에 쓸 권한이 필요합니다. 그것 없이는, 로그 드라이버가 조용히 실패하고 모든 로그 출력이 손실됩니다.

**구조화된 로그 vs 일반 텍스트**: 일반 텍스트 로그("Order 7741 placed")는 grep이 필요합니다. 구조화된 JSON 로그(`{"event": "order_placed", "order_id": "7741", "restaurant_id": "47", "amount": 3200}`)는 SQL과 유사한 구문을 사용해 CloudWatch Logs Insights로 쿼리할 수 있습니다:

```
fields @timestamp, event, order_id, restaurant_id
| filter event = "order_placed"
| stats count(*) by restaurant_id
| sort count desc
| limit 10
```

그 쿼리는 로그 그룹에 직접 실행됩니다. 데이터베이스 없음. 데이터 파이프라인 없음. ETL 작업 없음. 답이 몇 초 안에 거기 있습니다.

이것은 26장에서 구축할 분석 데이터 레이크를 대체하지 않습니다. 그것은 운영 질문에 답합니다 — "지난 30분 동안 레스토랑 47에서 온 주문이 몇 개?" — 사건 한복판에서, Athena 쿼리를 실행할 시간이 없을 때요.

**CloudWatch Container Insights**

**Container Insights**는 컨테이너 수준 지표 — CPU, 메모리, 네트워크 I/O, 스토리지 I/O — 를 ECS 클러스터, 서비스, 태스크별로 수집하고 집계하는 CloudWatch 기능입니다. EC2 수준 지표(호스트는 어떤가?) 대신, 태스크 수준 지표(이 특정 ECS 서비스는 어떤가?)를 봅니다.

ECS 클러스터에서 하나의 설정으로 활성화합니다:

```bash
aws ecs update-cluster-settings \
  --cluster nimbus-production \
  --settings name=containerInsights,value=enabled
```

활성화 후:

- 서비스당 대시보드를 봅니다: 태스크 수, CPU 사용률, 메모리 사용률
- 태스크 수준 CPU에 알람을 걸 수 있습니다(훨씬 더 무딘 신호인 EC2 호스트 CPU가 아니라)
- 메모리 급증을 로그 이벤트와 상관시킬 수 있습니다 — 태스크 메모리가 14:22에 95%로 올랐고; 로그가 정확히 14:21에 레스토랑 47의 메뉴 임포트로 인한 인바운드 요청 급증을 보여줍니다

"그게 월 얼마나 들죠?" Tom이 물었습니다.

Container Insights는 그것이 생성하는 커스텀 지표와 로그 스토리지에 요금을 부과합니다. Nimbus의 규모(세 개 서비스, 각각 3~6개 태스크)에서, 이것은 약 월 $12였습니다 — 태스크 수준 운영 가시성에 대한 합리적인 거래.

Leo가 그날 안에 그것을 활성화했습니다.

태스크가 처음으로 상태 확인에 실패하고 ECS에 의해 교체되었을 때, Container Insights 대시보드가 이벤트를 자동으로 포착했습니다: 태스크 ID, 시작 시간, 실패 시간, 종료 코드. 그 태스크의 CloudWatch 로그 스트림이 종료 전 출력의 마지막 40줄을 보존했습니다 — 그것은 새 레스토랑 파트너의 잘못된 형식의 메뉴 JSON에 의해 트리거된 잡히지 않은 예외를 보여주었습니다.

Container Insights와 구조화된 로깅 없이는: 오류율의 신비로운 급증, 더 이상 실패한 태스크를 실행하지 않는 호스트로 SSH가 필요한 조사, 45분의 추측.

그것들과 함께: CloudWatch 대시보드의 로그 스트림 링크, 정확한 예외, 레스토랑 ID, 문제의 필드 — 5분 미만.

"SSH 없음," Leo가 사후 분석을 검토하며 말했습니다. "조사할 다운타임 없음. 로그가 일을 했어요."

"로그는 오직 일을 해," Priya가 말했습니다, "네가 그것들이 포착되도록 구성했을 때만."


**컨테이너가 잘못된 선택일 때**

"잠깐 — 그런데 *왜* 모든 것을 컨테이너화하지 않죠?" Maya가 물었습니다. "방금 컨테이너가 모든 구성 드리프트 문제를 해결한다고 저를 설득했잖아요. 왜 모든 단일 서비스를 컨테이너로 실행하지 않죠?"

그것은 그녀가 Lambda에 대해 물었던 같은 질문이었습니다. 답은 비슷했습니다.

컨테이너는 운영 요구사항을 추가합니다: 컨테이너 레지스트리(ECR), 이미지를 빌드하고 푸시하는 CI/CD 파이프라인, 오케스트레이터(ECS), 인스턴스 수준이 아니라 태스크 수준 가시성을 위해 구성된 모니터링, 그리고 Docker와 이미지 버전 관리를 이해하는 팀이 필요합니다.

EC2에서 이미 잘 작동하고, 안정적이며, 구성 드리프트로 고통받지 않는 서비스의 경우, 그것을 컨테이너화하는 비용이 이익을 초과할 수 있습니다.

컨테이너가 잘못된 선택인 특정 경우:

**컨테이너 이동성을 위해 만들어지지 않은 상태가 있는 서비스**: 컨테이너의 데이터베이스는 신중한 영구 볼륨 관리가 필요합니다. 컨테이너에서 데이터베이스를 실행하는 대부분의 팀은 이 복잡성을 만난 후 결국 그것들을 관리형 서비스(RDS, ElastiCache)로 다시 옮깁니다.

**특수 하드웨어 요구사항이 있는 서비스**: GPU 워크로드, 특정 네트워크 인터페이스 구성, 또는 FPGA 기반 처리는 특정 하드웨어를 가진 EC2 인스턴스가 필요합니다. 컨테이너는 이것을 바꾸지 않습니다 — 여전히 EC2 launch type을, 그저 위에 컨테이너를 얹어 사용할 것이고, 컨테이너 추상화는 이익 없이 복잡성을 추가합니다.

**매우 단순한 스크립트와 작업**: 일주일에 한 번 실행되고 종속성 드리프트 문제가 없는 40줄짜리 Python 스크립트. 이것을 위해 Docker, ECR, ECS 태스크 정의, CI/CD 파이프라인을 추가하는 것은 균형이 맞지 않습니다. Lambda가 더 단순합니다. 일반 EC2 크론 작업이 더 단순할 수도 있습니다.

"원칙은," Leo가 말했습니다, "항상과 같아요: 도구를 문제에 맞추세요. 컨테이너는 구성 드리프트와 배포 일관성을 해결해요. 그 문제가 없다면, 컨테이너가 필요 없어요."

## AWS Batch: 대규모 작업을 위한 컨테이너

ECS와 EKS는 장기 실행 서비스를 위해 설계되었습니다 — 끊임없이 실행되고, 요청을 받고, 트래픽에 따라 확장되는 애플리케이션. 하지만 일부 워크로드는 다릅니다: 그것들은 고정된 기간 동안 실행되고, 정의된 데이터셋을 처리하고, 그러고 나서 중지됩니다. 수백 개의 레스토랑에 대한 월말 청구서 생성. 머신러닝 훈련 작업 실행. 야간 분석 내보내기 처리.

이런 워크로드의 경우, 서비스를 원하지 않습니다 — 작업(job)을 원합니다.

**AWS Batch**는 어떤 규모에서든 배치 컴퓨팅 작업을 실행하는 완전 관리형 서비스입니다. 작업을 Docker 컨테이너(ECS가 사용하는 같은 컨테이너 형식)로 정의하면, Batch가 나머지를 처리합니다: EC2 또는 Fargate 컴퓨팅 프로비저닝, 작업을 큐로 스케줄링, 작업이 도착하면 용량을 확장하고 완료되면 다시 0으로.

핵심 개념:

- **작업 정의:** Docker 컨테이너, 리소스 요구사항(vCPU, 메모리), 실행할 명령
- **작업 큐:** 제출된 작업이 실행 전에 기다리는 곳; 각 큐는 하나 이상의 컴퓨팅 환경과 연결됩니다
- **컴퓨팅 환경:** 기반 EC2 또는 Fargate 용량. 최대 90% 비용 절감을 위해 스팟 인스턴스를 사용할 수 있습니다 — Batch가 중단과 재시도를 자동으로 처리합니다

"잠깐 — 그런데 *왜* 그냥 ECS 태스크를 실행하는 대신 Batch를 쓰죠?" Maya가 물었습니다.

"왜냐하면 ECS 서비스는 항상 켜져 있기 때문이에요," Leo가 말했습니다. "그건 요청을 기다려요. Batch 작업은 실행되고, 끝나고, Batch가 컴퓨팅을 다시 0으로 축소해요. 실행 사이에는 아무 비용도 안 내요."

Tom이 가격 페이지에서 고개를 들었습니다. "그리고 스팟 인스턴스는요?"

"Batch는 스팟에서 실행할 수 있어요. 스팟 인스턴스가 작업 중에 회수되면, Batch가 자동으로 재시도해요. 45분짜리 청구서 작업에는, 그게 괜찮아요."

**vs ECS/EKS:** ECS/EKS는 서비스를 실행합니다 — 항상 켜져 있고, 요청 기반. Batch는 작업을 실행합니다 — 유한한 기간, 데이터 기반, 유휴 시 0으로 확장.

**vs Lambda:** Lambda는 15분 타임아웃이 있습니다. Batch 작업은 몇 시간 또는 며칠 실행될 수 있습니다.

Nimbus 맥락: 야간 청구서 생성 작업은 수백 개의 레스토랑 파트너에 대해 45분이 걸립니다. Lambda는 15분에 타임아웃됩니다. 항상 켜져 있는 ECS 서비스는 하루 23시간 돈을 낭비합니다. Batch는 스팟 인스턴스에서 작업을 실행하고, 38분에 끝내고, $1.20이 들고, 종료됩니다.

"그건 옛날 스크립트가 끝나기를 기다리면서 산 커피보다 싸요," Leo가 말했습니다.

"그리고 관리할 EC2가 없어요," Priya가 덧붙였습니다. "Batch가 그것을 프로비저닝하고, 실행하고, 종료해요."

## 장점과 한계

**컨테이너**:

- 환경 불일치 제거("내 머신에서는 작동해")
- 빠르고 신뢰할 수 있는 배포 가능
- 불변 — 같은 이미지가 어디서나 동일하게 실행됨
- 효율적 — VM보다 가볍고, 더 빠른 시작

**ECS**:

- AWS 중심 워크로드에 Kubernetes보다 더 단순
- 긴밀한 AWS 통합(IAM, ALB, CloudWatch, Secrets Manager)
- Fargate 옵션이 EC2 관리를 완전히 제거

**EKS**:

- 완전한 Kubernetes 호환성 — 전체 생태계 사용
- 하이브리드 환경이나 Kubernetes 전문성을 가진 팀에 더 적합
- ECS보다 설정과 운영이 더 복잡

**복잡해지는 부분**:

- 컨테이너 이미지는 빌드되고 버전화되어야 합니다 — CI/CD 파이프라인 필요
- 컨테이너 디버깅은 전통적 프로세스 디버깅과 다른 도구가 필요합니다
- 상태가 있는 컨테이너(컨테이너의 데이터베이스)는 신중한 영구 스토리지 구성이 필요합니다
- 컨테이너 간 네트워킹(서비스 간 통신)은 컨테이너 네트워킹 개념의 이해가 필요합니다

## 요약

Lambda는 유휴 컴퓨팅을 무료로 만들었습니다. 컨테이너는 배포를 결정론적으로 만들었습니다. 함께, 그것들은 성장하는 엔지니어링 팀에게 가장 흔한 운영 고통의 원인 두 가지를 해결했습니다.

- **컨테이너**는 애플리케이션 코드, 런타임, 종속성을 함께 패키징합니다 — 어디서나 동일하게 실행됩니다.
- **Docker**는 표준 컨테이너 기술입니다. 이미지는 청사진입니다; 컨테이너는 실행 중인 인스턴스입니다.
- **ECR(Elastic Container Registry)**은 AWS의 관리형 Docker 레지스트리입니다 — 여기서 이미지를 저장하고, 버전화하고, 스캔하십시오. 배포 전에 CVE를 잡기 위해 이미지 스캔을 활성화하십시오.
- **ECS(Elastic Container Service)**는 컨테이너를 오케스트레이션합니다. 태스크와 서비스를 정의하면; ECS가 배치와 수명 주기를 관리합니다.
- **Fargate**는 컨테이너를 위한 서버리스 컴퓨팅입니다 — 관리할 EC2 인스턴스 없음. EC2 오버헤드 제거로 인해 작은 규모에서 종종 EC2 launch type보다 저렴합니다. 신중한 태스크 빈 패킹이 있는 더 큰 규모에서는, EC2 launch type이 더 비용 효율적이 될 수 있습니다.
- **EKS(Elastic Kubernetes Service)**는 관리형 Kubernetes입니다 — Kubernetes 기능이나 호환성이 필요한 팀을 위해.
- **Secrets Manager 통합**: 태스크 정의를 통해 시작 시점에 비밀을 컨테이너에 주입하십시오 — 비밀 값을 환경 변수나 태스크 정의에 직접 저장하지 마십시오.
- **서비스 디스커버리**: 컨테이너 IP는 일시적입니다. 안정적인 서비스 주소 지정을 위해 ALB DNS 이름이나 Cloud Map을 사용하십시오.
- AWS에서 단순성을 위해 ECS를 선택하고; Kubernetes 생태계 호환성을 위해 EKS를 선택하십시오.

## 시험 팁

*SAA-C03 도메인: 탄력적 아키텍처 설계(도메인 2, 태스크 2.1)*

- **ECS vs EKS 신호**: "Kubernetes," "Helm," "기존 Kubernetes 전문성," 또는 "멀티 클라우드 컨테이너 오케스트레이션"을 언급하는 시험 시나리오 → EKS. 다른 모든 것 → ECS.
- **Fargate vs EC2 launch type**: "컨테이너를 위한 EC2 인스턴스를 관리하고 싶지 않음," "서버리스 컨테이너," "인프라 관리 없음" → Fargate. "특정 인스턴스 유형 필요," "GPU 워크로드," "세밀한 인스턴스 제어" → EC2 launch type.
- **태스크 역할 vs 태스크 실행 역할** — 실제 시험 구별 요소. **태스크 실행 역할**은 여러분의 코드 전후와 주변에서 태스크를 대신해 ECS *에이전트*가 사용합니다: ECR에서 이미지 가져오기, Secrets Manager에서 비밀 가져오기, CloudWatch에 로그 쓰기. **태스크 역할**은 *컨테이너 내부의 여러분의 애플리케이션 코드*가 AWS 서비스를 호출하는 데 사용하는 것입니다: S3에서 읽기, DynamoDB에 쓰기 — EC2 인스턴스 역할과 같지만, 태스크별이라, 각 태스크가 다른 권한을 가질 수 있습니다. "컨테이너가 S3에서 읽어야 함" → **태스크 역할**(태스크 정의에 연결됨). "태스크가 이미지를 가져오지 못함 / 비밀을 가져올 수 없음" → **실행 역할**에 권한이 없음.
- **Fargate Spot**: 2분 중단 경고와 함께 최대 ~70% 할인된 여유 용량에서 장애 허용 컨테이너를 실행 — Fargate의 EC2 Spot 등가물, 용량 공급자를 통해 구성. 시험 트리거: "인스턴스를 관리하지 않고 가장 낮은 비용으로 중단 허용 컨테이너 실행" → Fargate Spot.
- **ECR 이미지 스캔**: ECR이 알려진 취약점(CVE)에 대해 컨테이너 이미지를 스캔할 수 있습니다. 시험 신호: "보안 취약점에 대해 컨테이너 스캔" → ECR 이미지 스캔.
- **블루/그린 배포**: ECS는 CodeDeploy 통합을 통해 블루/그린 배포를 지원합니다. 자동 롤백과 함께 제로 다운타임 배포. 시험 패턴: "자동 롤백과 함께 다운타임 없이 배포" → ECS + CodeDeploy 블루/그린.
- **Secrets Manager 통합**: 시험 신호: "태스크 정의에 값을 저장하지 않고 컨테이너에 비밀 주입" → Secrets Manager ARN을 참조하는 태스크 정의의 `secrets` 필드 사용. 태스크 실행 역할은 `secretsmanager:GetSecretValue` 권한이 필요합니다.
- **ECS Service Auto Scaling**: CPU, 메모리, 또는 커스텀 CloudWatch 지표에 기반해 태스크 수를 확장합니다. 올바른 수의 실행 중인 태스크로 트래픽을 라우팅하기 위해 ALB와 함께 작동합니다.
- **AWS Batch:** Docker 컨테이너를 위한 관리형 배치 컴퓨팅. 작업 큐 → 컴퓨팅 환경(EC2 또는 Fargate, 스팟 지원). 사용할 때: Lambda 타임아웃이 너무 짧을 때, 유한한 작업에 ECS 서비스가 낭비적일 때. 시험 트리거: "대규모 배치 처리" 또는 "몇 시간 실행되는 작업" → AWS Batch.

## 연습 문제

**연습 1 — 회상**

Docker 이미지와 Docker 컨테이너의 차이를 설명하십시오. ECS와 ECR의 차이를 설명하십시오.

*(힌트: 이미지가 컨테이너에 대해 갖는 관계는 레시피가 요리된 요리에 대해 갖는 관계와 같습니다. ECR은 이미지를 저장합니다; ECS는 그것들을 실행합니다.)*

**연습 2 — SAA-C03 시나리오**

*시나리오*: 회사가 현재 수동으로 관리되는 EC2 인스턴스에서 실행 중인 마이크로서비스 애플리케이션을 가지고 있습니다. 팀은 일관되지 않은 배포로 고생하고 있습니다 — 다른 EC2 인스턴스가 다른 라이브러리 버전을 가져, 재현하기 어려운 버그를 유발합니다. 그들은 기반 서버 관리를 위한 운영 오버헤드를 최소화하면서 배포를 표준화하기를 원합니다. 팀에는 Kubernetes 경험이 없습니다.

이 요구사항을 가장 잘 충족하는 솔루션은 무엇입니까?

A) Docker로 애플리케이션을 컨테이너화; Fargate launch type으로 Amazon ECS 사용  
B) 인스턴스를 일관되게 유지하기 위해 AWS Systems Manager Patch Manager와 함께 EC2에 배포  
C) Docker로 애플리케이션을 컨테이너화; 자체 관리 노드 그룹으로 Amazon EKS 사용  
D) 배포와 인스턴스 구성을 자동으로 관리하기 위해 AWS Elastic Beanstalk 사용

**힌트 1**: 컨테이너는 "일관되지 않은 환경" 문제를 직접 해결합니다. 어떤 옵션이 컨테이너를 사용합니까?

**힌트 2**: "서버 관리를 위한 운영 오버헤드 최소화" → Fargate(EC2 관리 없음) vs 자체 관리 노드(여전히 EC2 관리).

**힌트 3**: "Kubernetes 경험 없음" → EKS는 ECS보다 더 많은 운영 복잡성입니다.

**정답**: A

**설명**: Docker로 컨테이너화하면 모든 배포가 같은 종속성을 가진 같은 이미지를 사용하도록 보장합니다 — 구성 드리프트를 제거합니다. Fargate가 있는 ECS는 관리할 EC2 인스턴스가 없다는 것을 의미합니다. 팀은 서버 유지 보수가 아니라 애플리케이션 코드와 컨테이너 정의에 집중합니다. ECS(EKS가 아니라)가 Kubernetes 경험이 없는 팀에 적합합니다.

**왜 B가 아닌가?** Patch Manager는 EC2 인스턴스를 최신으로 유지하지만 애플리케이션 간 라이브러리 버전 불일치를 해결하지 않습니다. 근본적인 문제(다른 인스턴스의 다른 코드 환경)가 남습니다.

**왜 C가 아닌가?** 자체 관리 노드 그룹이 있는 EKS는 EC2 인스턴스를 관리하는 것 *그리고* Kubernetes를 배우는 것이 필요합니다. 어느 것도 요구사항과 맞지 않습니다.

**왜 D가 아닌가?** Elastic Beanstalk는 EC2에서 애플리케이션 배포를 관리하지만 컨테이너가 사용되지 않는 한 근본적인 환경 불일치를 해결하지 않습니다. Beanstalk는 기본적으로 Docker 이미지를 사용하지 않습니다(사용하도록 구성할 수는 있지만).

*SAA-C03 도메인: 탄력적 아키텍처 설계 — 태스크 2.1*

**연습 3 — 아키텍처 과제** *(선택 사항)*

Nimbus가 모놀리식 API를 세 개의 마이크로서비스로 분리하고 있습니다: 주문 서비스, 메뉴 서비스, 알림 서비스. 각 서비스는 다른 확장 요구사항을 가집니다(주문 서비스는 트래픽에 따라 확장하고; 메뉴 서비스는 대부분 읽기 전용이고 안정적이며; 알림 서비스는 뾰족한 버스트를 가집니다).

이 세 서비스를 위한 ECS 아키텍처를 설계하십시오. 서비스 간 통신을 어떻게 처리하겠습니까? 하나의 ECS 클러스터를 사용하겠습니까, 아니면 세 개를 사용하겠습니까? 각 서비스에 대해 Auto Scaling을 어떻게 다르게 구성하겠습니까?

고려하십시오: 메뉴 서비스는 읽기가 많고 60초 동안 오래된 데이터를 제공할 수 있습니다 — 그 앞에 캐싱을 추가하겠습니까? 알림 서비스는 금요일 저녁에 버스트 확장을 심하게 합니다 — Fargate 최소 용량을 1로, 최대를 20으로 설정하겠습니까? 축소 이벤트 중 진행 중인 알림은 어떻게 됩니까?

*(단 하나의 정답은 없습니다. 목표는 ECS에서 마이크로서비스 아키텍처를 연습하는 것입니다.)*
