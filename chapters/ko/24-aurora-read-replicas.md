# 24장: 당신과 함께 성장하는 데이터베이스

Tom의 비용 검토가 데이터베이스 계층에서 예상치 못한 것을 발견했다.

Nimbus는 RDS PostgreSQL을 실행하고 있었다: 멀티 AZ, db.r6g.large 인스턴스. 월 $340.

"높은 것 같은데요," Tom이 말했다. "하지만 비교할 것이 없어요."

Leo가 성능 메트릭을 열었다. 데이터베이스 CPU가 금요일 저녁 러시 동안 85%로 급등했다. 읽기 쿼리가 큐에 쌓였다. P95 쿼리 지연이 6개월 동안 두 배가 됐다.

"데이터베이스가 병목이야," 그가 말했다. "트래픽이 성장했어. 데이터베이스는 그에 따라 확장되지 않았어."

"그냥 인스턴스를 더 크게 만들 수 없나요?" Maya가 물었다.

"그럴 수 있어요," Leo가 말했다. "그게 수직 확장이야. r6g.large에서 r6g.xlarge로 이동해요. 더 많은 CPU, 더 많은 메모리. 더 비싸지고 시간을 벌어요."

"하지만 근본적인 문제를 고치지 않아요," Priya가 말했다. "결국 가장 큰 인스턴스에 도달하면 다른 접근이 필요해요."

"두 가지 접근이 있어요," Leo가 말했다. "읽기 복제본, 또는 Aurora."

"차이가 뭐야?"

좋은 질문이다. 이 챕터의 나머지가 답이다.

많은 사서와 하나의 사서가 있는 바쁜 도서관을 생각하라. 하나의 사서가 책 체크인도 하고 후원자 질문에도 답한다. 도서관이 인기를 얻으면, 줄이 형성된다. 수정: 더 많은 사서를 채용하지만 질문에 답하기 위해서만. 체크인은 여전히 원래 책상을 통해 간다. 읽기 복제본이 그것이다: 읽기를 처리하는 추가 용량이지만, 모든 쓰기는 여전히 하나의 권위 있는 소스를 통해 간다. Aurora는 한 걸음 더 나아가, 모든 사서가 같은 선반을 공유하고 지연 없이 항상 같은 책을 볼 수 있도록 선반 시스템 자체를 재설계한다.

**읽기 복제본: 읽기 트래픽 배분**

대부분의 웹 애플리케이션은 쓰는 것보다 훨씬 자주 데이터를 읽는다. 메뉴를 탐색하는 고객은 수십 개의 SELECT 쿼리를 만든다. 주문하는 것은 몇 개의 INSERT/UPDATE 쿼리를 만든다. 비율은 보통 10:1 이상이다.

**읽기 복제본**은 기본 서버에서 모든 쓰기의 복사본을 받고 SELECT 쿼리에 사용 가능하게 만드는 추가 RDS 인스턴스다.

작동 방식:

1. 애플리케이션 쓰기(INSERT, UPDATE, DELETE)가 기본 데이터베이스로 간다
2. 기본 서버가 비동기적으로 읽기 복제본에 그 변경을 복제한다
3. 애플리케이션 읽기(SELECT)가 읽기 복제본에 분산된다
4. 읽기 복제본이 부하를 공유한다 — 각각이 총 읽기 트래픽의 일부를 처리한다

결과: 기본 데이터베이스가 쓰기만(그리고 선택적으로 일부 읽기) 처리한다. 읽기 복제본이 읽기 부하를 처리한다. 10:1 읽기/쓰기 비율에서, 하나의 읽기 복제본을 추가하면 기본 서버의 총 부하가 대략 절반이 된다.

**중요한 한계**: 복제는 **비동기적**이다. 기본 서버와 복제본 사이에 복제 지연이 있다 — 보통 밀리초이지만 부하에서 초가 될 수 있다. 레코드를 쓰고 즉시 복제본에서 읽으면 아직 보지 못할 수 있다. 대부분의 읽기(메뉴 탐색, 주문 내역 보기)에는 허용 가능하다. "내 주문이 방금 완료됐나?" — 기본 서버에서 읽어야 한다.

**읽기 복제본: 세부 사항**

- 기본 RDS 인스턴스당 최대 5개의 읽기 복제본을 가질 수 있다
- 읽기 복제본은 같은 리전이나 다른 리전에 있을 수 있다(교차 리전 복제본)
- 읽기 복제본은 스스로 읽기 복제본을 가질 수 있다(체인)
- 읽기 복제본은 별도의 엔드포인트다 — 애플리케이션이 복제본 엔드포인트로 읽기를 직접 보내야 한다
- 재해 시나리오에서 읽기 복제본을 독립 실행형 데이터베이스로 승격할 수 있다

Nimbus의 경우, Leo가 하나의 읽기 복제본을 추가했다. 그는 다음을 위해 애플리케이션을 업데이트했다:

- 쓰기 작업 → 기본 엔드포인트
- 메뉴 탐색, 주문 내역 → 복제본 엔드포인트

최대 기본 서버 CPU가 85%에서 41%로 떨어졌다.

Tom이 비용을 봤다: 같은 인스턴스 유형의 읽기 복제본은 기본 서버와 같은 비용이다. $340/월에서 $680/월로.

"우리는 부하를 대략 절반으로 줄이기 위해 비용을 두 배로 했어요," Tom이 말했다.

"그래요. 하지만 대안은 더 비싼 인스턴스 유형으로 이동하는 것이었어요. 더 비싸지고 읽기 부하를 배분하지 않아요."

Tom이 계산을 했다. 그가 마지못해 고개를 끄덕였다.

"Aurora가 뭔가요?" 그가 물었다.

**Amazon Aurora: 데이터베이스 엔진 재고**

Aurora는 MySQL 및 PostgreSQL과 호환되는 AWS의 독자적인 관계형 데이터베이스 엔진이다. 클라우드 워크로드를 위해 처음부터 설계되어 관계형 데이터베이스의 스토리지 레이어가 작동하는 방식을 재구상했다.

전통적인 RDS 설정(MySQL, PostgreSQL)에서, 스토리지와 컴퓨팅이 긴밀하게 결합되어 있다. 데이터베이스 엔진이 데이터 파일을 관리한다. 복제가 기본 서버에서 복제본으로 데이터를 복사한다. 복제본이 모든 쓰기 작업을 다시 실행해야 한다.

Aurora는 스토리지와 컴퓨팅을 분리한다. 여섯 개의 복사본에서 세 개의 가용 영역에 걸쳐 데이터를 자동으로 복제하는 분산되고 내고장성 스토리지 레이어를 사용한다. 컴퓨팅 레이어(데이터베이스 인스턴스)가 이 스토리지 레이어 위에 앉는다.

**이것이 바꾸는 것**:

**읽기 복제본**: Aurora 복제본은 데이터를 복제할 필요가 없다 — 이미 같은 스토리지 레이어를 공유한다. 이것은 다음을 의미한다:

- 최대 15개의 읽기 복제본(일반 RDS의 5개 vs.)
- 복제 지연이 보통 100밀리초 미만(부하에서 RDS의 경우 초 vs.)
- 복제본이 30초 미만에 기본 서버로 승격될 수 있다(몇 분 vs.)

**장애 조치**: 복제본이 스토리지를 공유하기 때문에, 장애 조치가 훨씬 빠르다 — 승격은 데이터 전송을 포함하지 않고, 쓰기를 리디렉션하는 것이다.

**스토리지**: Aurora는 10GB 증분으로 최대 128TB까지 스토리지를 자동으로 확장한다. 스토리지를 미리 프로비저닝할 필요가 없다.

**성능**: Aurora는 동등한 인스턴스 유형에서 표준 MySQL보다 5배 처리량, 표준 PostgreSQL보다 3배를 주장한다.

**Aurora 가격: Tom의 질문**

"비용이 얼마나 돼요?" Tom이 물었다.

Aurora 가격은 RDS와 다르다:

**인스턴스 가격**: 유형별로 RDS 인스턴스 가격과 유사하다.

**스토리지 가격**: GB당 월 $0.10(저장된 양에 대해 지불, 자동으로 확장).

**I/O 가격**: Aurora는 스토리지에 대한 읽기/쓰기당 요금을 부과한다. 쓰기 집약적인 워크로드에서 상당할 수 있다.

"잠깐," Tom이 말했다. "I/O에 별도로 지불하고 있는 거예요?"

"Aurora Serverless v2와 Aurora I/O-Optimized가 이 가격 모델을 바꿔요," Leo가 말했다. "Aurora I/O-Optimized는 I/O 수수료가 없지만 스토리지와 인스턴스 가격이 더 높다. I/O 집약적인 워크로드에 더 좋아요."

Tom이 트레이드오프를 봤다. 읽기 집약적인(대량의 메뉴 쿼리, 적은 쓰기) Nimbus의 경우, Aurora I/O-Optimized는 더 많은 비용이 들 수 있다. 표준 Aurora 가격이 적합할 수 있다.

이것이 시니어 엔지니어가 내리는 실제 비용 결정이다: 올바르게 선택하려면 워크로드의 I/O 패턴을 알아야 한다.

**Aurora Serverless: 인스턴스 크기 생각 없이 확장**

**Aurora Serverless v2**는 실제 데이터베이스 부하에 따라 컴퓨팅 용량을 자동으로 확장하는 설정이다. 고정된 인스턴스 크기(db.r6g.large)를 선택하는 대신, Aurora Capacity Units(ACU)의 최소값과 최대값을 설정한다.

Aurora Serverless v2:

- 부하가 증가할 때 초 내에 확장
- 유휴 기간에 거의 제로로 축소
- 비용: ACU-시간당 $0.12(더하기 스토리지 및 I/O)

가변 트래픽을 가진 워크로드 — Nimbus의 금요일 급증 vs. 월요일 아침 조용 — 에서, Serverless v2는 비수요 기간에 비용을 줄이고 피크를 사전 프로비저닝 없이 처리한다.

"금요일 급증 동안," Leo가 말했다. "Aurora가 자동으로 부하를 처리하기 위해 확장한다. 일요일 아침에 트래픽이 거의 없으면 최소로 다시 축소한다."

"그리고 사용하는 용량만 지불하는 거죠," Tom이 말했다.

"정확히."

Tom이 예상대로 찾고 있었던 것을 발견한 표정을 지었다.

**Aurora 글로벌 데이터베이스: 멀티 리전 읽기**

**Aurora 글로벌 데이터베이스**는 여러 AWS 리전에 걸쳐 Aurora를 확장한다:

- **하나의 기본 리전**이 모든 쓰기를 처리
- **최대 다섯 개의 보조 리전**이 일반적으로 <1초의 복제 지연으로 읽기를 제공
- 보조 리전은 DR 시나리오에서 1분 내에 기본 서버로 승격될 수 있다

Nimbus의 글로벌 확장을 위해, Aurora 글로벌 데이터베이스는 런던의 레스토랑 파트너가 미국 기본 서버에서의 교차 대서양 지연 없이 EU 읽기 복제본에서 자신의 메뉴를 쿼리할 수 있게 한다.

**RDS vs. Aurora: 각각을 언제 선택하는가**

| 요소 | RDS (PostgreSQL/MySQL) | Aurora |
|---|---|---|
| 비용 | 소형 워크로드에 더 낮음 | 더 높은 기본, 하지만 더 잘 확장됨 |
| 호환성 | 완전 | MySQL/PostgreSQL 호환(일부 차이점) |
| 최대 복제본 | 5 | 15 |
| 복제 지연 | 초가 될 수 있음 | 보통 <100ms |
| 스토리지 | 고정 프로비저닝 | 128TB까지 자동 확장 |
| 장애 조치 시간 | 60-120초 | <30초 |
| 서버리스 옵션 | 제한적 | Aurora Serverless v2 |
| 적합한 경우 | 안정적이고 예측 가능한 워크로드 | 가변 트래픽, 높은 읽기 볼륨, 빠른 장애 조치 필요 |

## 장점과 한계

**Aurora 장점**:

- 표준 RDS보다 훨씬 빠른 장애 조치
- 최소 지연으로 최대 15개의 읽기 복제본
- 자동 확장 스토리지
- 가변 워크로드를 위한 Serverless v2
- 멀티 리전 배포를 위한 글로벌 데이터베이스

**Aurora 한계**:

- 소형의 안정적인 워크로드에 더 높은 비용
- I/O 가격이 쓰기 집약적인 워크로드에 상당할 수 있다(I/O-Optimized 사용)
- 마이너 MySQL/PostgreSQL 호환성 차이가 코드 변경이 필요할 수 있다
- Serverless v2 콜드 스타트(거의 제로에서)가 지연 급증을 유발할 수 있다

## 요약

- **읽기 복제본**은 기본 서버에서 읽기 트래픽을 배분한다. 비동기 복제 — 약간의 지연이 대부분의 읽기에 허용 가능하다.
- **Aurora**는 스토리지 레이어를 재구상한다: 분산되고, 복제본에 걸쳐 공유되며, 자동 확장.
- Aurora 제공: 15개의 읽기 복제본, <100ms 복제 지연, <30초 장애 조치, 128TB까지 자동 확장 스토리지.
- **Aurora Serverless v2**: 부하에 따라 컴퓨팅 용량을 자동 확장. 가변 트래픽에 좋다.
- **Aurora 글로벌 데이터베이스**: 하나의 리전에 기본 서버, 최대 다섯 개의 리전에 읽기 복제본.
- 더 소형이고 안정적이며 예측 가능한 워크로드에는 RDS를 선택하라. 규모, 빠른 장애 조치, 또는 가변 트래픽 처리가 필요할 때는 Aurora를 선택하라.

## 시험 팁

*SAA-C03 도메인: 고성능 아키텍처 설계(도메인 3, 태스크 3.3)*

- **Aurora 복제본 vs. RDS 읽기 복제본**: Aurora 복제본은 스토리지를 공유한다(거의 제로 지연, <30초 장애 조치). RDS 읽기 복제본은 데이터를 복제한다(지연 가능, 장애 조치에 분이 걸린다).
- **Aurora Serverless v2**: "데이터베이스 용량 자동 확장," "예측 불가능하거나 스파이크하는 데이터베이스 트래픽," "제로로 축소" → Aurora Serverless v2.
- **Aurora 글로벌 데이터베이스**: "멀티 리전 데이터베이스," "미국 기본 서버에서 EU의 낮은 지연으로 읽기," "지역 장애 조치를 위한 RTO < 1분" → Aurora 글로벌 데이터베이스.
- **장애 조치 타이밍**: Aurora < 30초. RDS 멀티 AZ 60-120초. 둘 다 알아라.
- **Aurora I/O-Optimized**: 더 높은 스토리지 및 인스턴스 비용, I/O당 요금 없음. I/O 비용이 지배할 때(쓰기 집약적) 사용. 표준 Aurora: 더 낮은 스토리지 비용, I/O당 지불. 읽기 집약적 사용.
- **Aurora Backtrack**: 전체 백업 스냅샷을 복원하지 않고 데이터베이스를 특정 시점으로 되감기. MySQL 호환 Aurora에만 사용 가능. 시험 신호: "실수로 데이터 삭제, 전체 백업을 복원하지 않고 빠르게 복구해야 함."

## 연습 문제

**연습 1 — 회상**

Aurora와 표준 RDS 읽기 복제본의 차이를 설명하라. Aurora의 복제 지연이 일반적으로 낮은 이유는 무엇인가?

*(힌트: 핵심 차이는 공유 스토리지 vs. 데이터 복제다. 쓰기가 도착할 때 각 복제본이 해야 하는 일에 대해 생각해보라.)*

**연습 2 — 시험 연습**

*시나리오*: 소셜 미디어 플랫폼의 MySQL 데이터베이스가 증가하는 트래픽으로 높은 읽기 지연을 경험하고 있다. 애플리케이션이 읽기 집약적이다(95% 읽기, 5% 쓰기). 팀은 트래픽 급증 중에도 읽기 지연이 일관적이어야 한다. 최소 다운타임(목표 RTO < 30초)으로 자동 장애 조치가 필요하다. 데이터 볼륨이 예측 불가능하게 증가하고 있다.

다음 중 이 요구사항을 가장 잘 충족하는 데이터베이스 솔루션은?

A) RDS MySQL 멀티 AZ와 다섯 개의 읽기 복제본  
B) Aurora MySQL과 Aurora Replicas 및 Aurora Serverless v2  
C) 더 큰 인스턴스 유형(수직 확장)이 있는 RDS MySQL  
D) 읽기 캐싱을 위해 RDS 앞에 ElastiCache를 추가

**힌트 1**: "RTO < 30초" — 어떤 서비스가 이것을 달성하는가? 각 옵션의 장애 조치 타이밍을 확인하라.

**힌트 2**: "급증 중 일관된 읽기 지연" — 어떤 서비스의 복제본이 잠재적인 초 지연 vs. 거의 제로 지연을 갖는가?

**힌트 3**: "예측 불가능하게 증가하는 데이터 볼륨" — 어떤 서비스가 스토리지를 자동으로 확장하는가?

**답**: B

**설명**: Aurora MySQL과 Aurora Replicas는 일관된 읽기 성능을 위해 밀리초(초가 아닌) 복제 지연을 제공한다. Aurora Serverless v2는 트래픽 급증 중 과도 프로비저닝 없이 컴퓨팅을 자동 확장한다. Aurora 스토리지가 데이터 증가에 따라 자동으로 확장된다. Aurora 장애 조치(복제본 승격)가 30초 미만에 완료된다 — RTO 요구사항을 충족한다.

**왜 A가 아닌가?** RDS 멀티 AZ 장애 조치는 60-120초가 걸린다 — RTO < 30초를 충족하지 않는다. 표준 RDS 읽기 복제 지연은 부하에서 초가 될 수 있다 — "일관된" 읽기 지연이 보장하기 더 어렵다.

**왜 C가 아닌가?** 수직 확장(더 큰 인스턴스)은 용량을 증가시키지만 읽기 부하를 배분하지 않는다. 데이터베이스는 여전히 읽기를 위한 단일 장애 지점이다.

**왜 D가 아닌가?** DynamoDB가 아닌 MySQL 데이터베이스를 위한 ElastiCache 추가는 RDS 앞에 두 개의 새 서비스를 도입한다. DynamoDB만이 DAX를 갖고 있다; 일반 RDS를 위해, ElastiCache는 도움이 되지만 근본적인 문제(읽기 복제 및 장애 조치 속도)를 해결하지 않는다.

*SAA-C03 도메인: 고성능 아키텍처 설계 — 태스크 3.3*

**연습 3 — 아키텍처 과제** *(선택 사항)*

Nimbus가 글로벌 확장을 설계하고 있다. 서부 해안, 독일, 호주의 레스토랑 파트너가 교차 리전 지연 없이 자신의 주문 데이터를 빠르게 보기를 원한다. 하지만, 모든 쓰기는 일관성을 유지하기 위해 단일 미국 동부 기본 서버를 통해 가야 한다.

Aurora를 사용하는 데이터베이스 아키텍처를 설계하라. 글로벌 데이터베이스를 어떻게 구조화하겠는가? 미국 동부 기본 서버가 다운되면 어떻게 되는가? 승격 프로세스를 어떻게 처리하겠는가?

*(단 하나의 정답은 없다. 멀티 리전 데이터베이스 설계를 연습하는 것이 목표다.)*

## 포스트 크레딧 장면

Leo가 Aurora Serverless v2로 마이그레이션했다.

금요일 급증이 왔다가 갔다. CPU가 결코 60%를 초과하지 않았다. 쿼리 지연이 일관성 있게 유지됐다. Aurora가 부하를 처리하기 위해 자동으로 확장했다가, 러시 후 다시 축소했다.

"이것이 지난 금요일과 비교하여 얼마나 비용이 들었어요?" Tom이 월요일 아침 물었다.

Leo가 결제 탐색기를 열었다. "금요일 최대 시 $0.89/시간으로 피크. 토요일 아침이 $0.11/시간."

Tom이 아무 말도 하지 않았다.

"이전 설정은 부하에 관계없이 고정 $0.47/시간이었어요," Leo가 덧붙였다.

"그러면 급증 중에 이전보다 더 많이 지불했어요," Tom이 말했다.

"네. 하지만 비수요 기간에 훨씬 덜. 주 전체 순 비용이 낮아요."

Tom이 계산했다. 그런 다음 고개를 끄덕였다.

"여기에 교훈이 있어요," 그가 말했다. "'더 저렴한가?'가 올바른 질문이 아니야. '실제 사용 패턴에 더 저렴한가?'야."

"그게," 맞은편에서 Priya가 말했다. "시니어 엔지니어의 본능이야."

Tom이 약간 놀란 것처럼 보였다.
