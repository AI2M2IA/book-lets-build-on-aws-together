# 24장: 당신과 함께 성장하는 데이터베이스

두 개의 선반과 한 명의 사서로 시작한 도서관을 상상해보십시오. 그것은, 한동안, 충분했습니다. 사서는 모든 것이 어디 있는지 알았습니다. 요청이 빠르게 답해졌습니다. 그러고 나서 도서관이 성장했습니다: 열 개의 선반, 스무 개, 마흔 개. 같은 사서, 같은 데스크, 같은 카드 목록. 이제 무언가를 찾는 데 기다림이 필요합니다. 사서가 느린 것이 아닙니다 — 그저 한 사람이 원래 속도로 서비스할 수 있는 것보다 더 많은 도서관이 있을 뿐입니다.

해결책은 더 빠른 사서가 아닙니다. 그것은 다른 종류의 도서관입니다.

---

S3 비용 절감 후, Tom이 검토를 계속했습니다. 데이터베이스 계층은 다른 종류의 문제였습니다 — 잘못된 스토리지 클래스에 있는 유휴 데이터가 아니라, 6개월간의 트래픽 성장의 부하 아래에서 적극적으로 고전하고 있는 시스템.

---

숫자는 편안하지 않았습니다.

Nimbus는 RDS PostgreSQL을 실행하고 있었습니다: 멀티 AZ, db.r6g.large 인스턴스. 월 $340.

Leo가 CloudWatch 지표 대시보드를 불러왔습니다. 숫자에 패턴이 있었습니다.

**DatabaseConnections**: 금요일 피크 동안 최대 200개 중 198개. 포화에서 두 연결. 200에서, 새 연결 시도가 "too many connections"로 실패할 것입니다 — 저녁을 주문하는 고객에게 HTTP 500으로 드러날 오류.

**CPUUtilization**: 금요일 저녁 러시 동안 89% 피크. 인스턴스는 급증을 처리하도록 설계되었습니다 — db.r6g.large는 2 vCPU와 16 GB 메모리를 가집니다 — 하지만 지속된 89% CPU는 피크 시간이 도착하기도 전에 데이터베이스가 용량에 도달했다는 것을 의미했습니다.

**ReadLatency**: P95 840밀리초. 6개월 전에는, 180ms였습니다. 저하가 점진적이었습니다 — 주당 10~20ms — 재앙적이 될 때까지 보이지 않았습니다. Tom의 검토 전 주에, P99 지연이 꼬박 1초를 넘었습니다. 레스토랑 메뉴를 클릭하는 고객이 페이지가 로드되기를 1초 넘게 기다리고 있었습니다.

**FreeStorageSpace**: 프로비저닝된 스토리지의 18% 남음. 현재 성장률로, 데이터베이스가 약 11주 안에 프로비저닝된 스토리지가 떨어질 것입니다.

"이것들 각각은 따로따로는 해결 가능해요," Leo가 대시보드를 보며 말했습니다. "하지만 우리는 네 개를 한꺼번에 가지고 있어요."

연결 수 급증은 애플리케이션의 연결 풀링 문제를 가리켰습니다 — 너무 많은 ECS 태스크가 자체 데이터베이스 연결을 여는 것. CPU 문제는 비싼 쿼리를 가리켰습니다. 지연 문제와 CPU 문제는 거의 확실히 같은 문제였습니다: 너무 자주 실행되는 느린 쿼리.

"잠깐 — 그런데 *왜* 우리가 198개 연결에 있죠?" Maya가 물었습니다. "우리는 세 개의 ECS 태스크가 있어요. 어떻게 거의 200개의 데이터베이스 연결이 있죠?"

각 ECS 태스크가 기본 풀 크기 5개 연결에 오버플로 10개를 더한 SQLAlchemy를 사용했습니다. 세 태스크 × 잠재적 15개 연결 = 애플리케이션에서 45개 연결. 다른 153개는 분석 Lambda 함수, 백그라운드 작업 작업자, Glue ETL 작업, 베스천 호스트를 통한 개발 팀의 로컬 연결, 그리고 오래된 버전의 코드에 의해 열렸지만 제대로 닫히지 않은 여러 연결에서 왔습니다.

"연결 수 문제는," Leo가 말했습니다, "실제로 데이터베이스 문제처럼 보이는 애플리케이션 문제예요." 그가 작업 목록에 PgBouncer(연결 풀러)를 추가했습니다 — 하지만 즉각적인 병목은 느린 쿼리였습니다.

데이터베이스 CPU가 금요일 저녁 러시 동안 89%로 급증하고 있었습니다. 읽기 쿼리가 큐에 들어가고 있었습니다. P95 쿼리 지연이 6개월에 걸쳐 두 배가 되었습니다.

"데이터베이스가 병목이에요," 그가 말했습니다. "트래픽이 성장했어요. 데이터베이스가 그것과 함께 확장되지 않았어요."

"그냥 인스턴스를 더 크게 만들 수 없나요?" Maya가 물었습니다. "잠깐 — 그런데 *왜* 우리가 모든 읽기와 쓰기를 처리하는 단일 데이터베이스를 가지고 있죠? 왜 처음부터 이것을 분산하지 않았죠?"

"할 수 있어요," Leo가 말했습니다. "그게 수직 확장이에요. r6g.large에서 r6g.xlarge로 옮겨요. 더 많은 CPU, 더 많은 메모리. 더 비싸겠지만 시간을 벌어줄 거예요."

"하지만 그게 근본 문제를 고치지 않아요," Priya가 말했습니다. "결국 가장 큰 인스턴스에 부딪히고 다른 접근법이 필요할 거예요. 그리고 쓰기가 실수로 읽기 복제본으로 가면 어떻게 되는지 생각해봤어요? 복제본이 그것을 거부하고 주문이 조용히 실패해요."

"두 가지 접근법이 있어요," Leo가 말했습니다. "읽기 복제본, 아니면 Aurora."

"차이가 뭐예요?"

"도서관처럼 생각하세요," Leo가 마커를 집으며 말했습니다. "책을 입고하고 이용자 질문에 답하는 한 명의 사서. 도서관이 인기를 얻으면, 줄이 생겨요. 해결책: 더 많은 사서를 고용하되 — 오직 질문에 답하기 위해서만요. 입고는 여전히 원래 데스크를 거쳐요."

"그게 읽기 복제본이에요," Priya가 말했습니다.

"정확해요. Aurora는 한 걸음 더 나아가요 — 그것은 선반 시스템 자체를 재설계해서 모든 사서가 같은 선반을 공유하고 항상 같은 책을 보게, 지연 없이요. 업데이트가 한 데스크에서 다른 데스크로 흘러내리기를 기다릴 필요가 없어요."

**읽기 복제본: 읽기 트래픽 분산**

대부분의 웹 애플리케이션은 데이터를 쓰는 것보다 훨씬 더 자주 읽습니다. 메뉴를 둘러보는 고객은 수십 개의 SELECT 쿼리를 합니다. 주문을 하는 것은 몇 개의 INSERT/UPDATE 쿼리를 합니다. 비율은 일반적으로 10:1 이상입니다.

**읽기 복제본**은 기본 서버로부터 모든 쓰기의 사본을 받고 그 쓰기를 SELECT 쿼리에 사용 가능하게 만드는 추가 RDS 인스턴스입니다.

작동 방식:

1. 애플리케이션 쓰기(INSERT, UPDATE, DELETE)가 기본 데이터베이스로 갑니다
2. 기본 서버가 그 변경을 읽기 복제본에 비동기적으로 복제합니다
3. 애플리케이션 읽기(SELECT)가 읽기 복제본에 걸쳐 분산됩니다
4. 읽기 복제본이 부하를 공유합니다 — 각각이 전체 읽기 트래픽의 일부를 처리합니다

결과: 기본 데이터베이스가 오직 쓰기만(그리고 선택적으로 일부 읽기) 처리합니다. 읽기 복제본이 읽기 부하를 처리합니다. 10:1 읽기/쓰기 비율의 경우, 읽기 복제본 하나를 추가하면 기본 서버의 총 부하가 대략 절반이 됩니다.

**중요한 한계**: 복제는 **비동기적**입니다. 복제 지연이 있습니다 — 일반적으로 밀리초이지만, 부하 시 초가 될 수 있습니다. 복제본에서의 읽기는 기본 서버보다 약간 뒤처진 데이터를 볼 수 있습니다. 대부분의 읽기(메뉴 둘러보기, 주문 기록 보기)의 경우, 이것은 수용 가능합니다. "내 주문이 방금 통과됐나?"의 경우 — 기본 서버에서 읽으십시오.

**읽기 복제본: 세부 사항**

- 기본 RDS 인스턴스당 최대 15개의 읽기 복제본을 가질 수 있습니다(MySQL, PostgreSQL, MariaDB)
- 읽기 복제본은 같은 리전이나 다른 리전에 있을 수 있습니다(교차 리전 복제본)
- 읽기 복제본은 그 자체로 읽기 복제본을 가질 수 있습니다(체이닝)
- 읽기 복제본은 별도의 엔드포인트입니다 — 애플리케이션이 읽기를 복제본 엔드포인트로 보내야 합니다
- 읽기 복제본은 독립형 데이터베이스로 승격될 수 있습니다(DR에 유용)

Nimbus의 경우, Leo가 읽기 복제본 하나를 추가했습니다. "괜찮을 거예요," 그가 Priya가 트래픽을 전환하기 전에 애플리케이션의 읽기/쓰기 라우팅 로직을 테스트했는지 물었을 때 말했습니다. 그는 하지 않았습니다. 그가 다음 40분을 쓰기가 읽기 복제본 엔드포인트로 가지 않는다는 것을 검증하는 데 보냈습니다.

그가 애플리케이션을 업데이트했습니다:

- 쓰기 작업 → 기본 엔드포인트
- 메뉴 둘러보기, 주문 기록 → 복제본 엔드포인트

기본 서버의 CPU가 피크에서 89%에서 41%로 떨어졌습니다.

**읽기 후 쓰기 일관성 문제**

읽기 복제본을 활성화한 지 3일 후, 지원 티켓이 도착했습니다. 레스토랑 파트너가 메뉴를 업데이트하고 — 단종된 항목을 제거하고 — 그러고 나서 그것이 제거되었는지 확인하려고 전화했습니다. 고객 서비스 담당자가 Nimbus 인터페이스에서 메뉴를 불러왔습니다. 항목이 여전히 거기 있었습니다.

20초 후, 그것이 사라졌습니다.

비동기 복제 지연. 쓰기(DELETE 메뉴 항목)가 기본 서버로 갔습니다. 고객 서비스 담당자의 읽기가 아직 변경을 받지 않은 복제본으로 갔습니다. 복제본이 그 순간 15초 뒤처져 있었습니다 — 비정상적이지 않지만, 눈에 보였습니다.

"그러면 누군가 최종 일관성 창을 통해 침입을 시도하면 어떻게 되죠?" Priya가 물었습니다. "아니면 그냥 — 방금 삭제된 메뉴 항목에 대해 주문이 들어오면요? 우리가 고객에게 청구하고 레스토랑이 그 항목을 가지고 있지 않을 거예요."

이것은 단지 UX 짜증이 아니라, 실제 일관성 우려였습니다.

해결책: 어떤 읽기가 일관성 요구사항을 가지는지 식별하고 그것들을 기본 서버로 라우팅하는 것.

**복제본으로 갈 수 있는 읽기**(최종 일관성이 괜찮음):
- 레스토랑의 메뉴를 둘러보는 고객(1~2초 오래됨은 감지할 수 없음)
- 주문 기록 쿼리(1분 전 주문 기록을 보는 사용자)
- 분석 유형 읽기(이번 주 상위 레스토랑)

**기본 서버로 가야 하는 읽기**(읽기 후 쓰기 일관성 필요):
- 쓰기 직후, 애플리케이션이 쓰기가 성공했는지 확인해야 할 때
- 주문 직후 주문 상태 읽기
- 레스토랑 관리 인터페이스에 의해 트리거된 메뉴 읽기(레스토랑이 방금 메뉴를 변경함)

애플리케이션이 데이터베이스 연결 계층에 라우팅 힌트를 추가했습니다: 요청이 레스토랑 관리 대시보드에서 왔으면, 기본 서버로 라우팅. 그것이 둘러보는 고객에게서 왔으면, 복제본으로 라우팅. `X-Read-Consistency: strong` HTTP 헤더가 신호 역할을 했습니다.

"그렇게 어렵지 않아요," Leo가 말했습니다. "그저 어떤 읽기가 그것을 필요로 하는지 알아야 해요."

"그리고 그것을 문서화해야 해요," Priya가 말했습니다. "그래야 새 엔드포인트를 추가하는 다음 사람이 어떤 풀을 사용할지 알아요."

"그게 월 얼마나 들죠?" Tom이 물었습니다. 그것은 어떤 새 서비스에 대해서든 그의 표준 시작 질문이었습니다.

같은 인스턴스 유형의 읽기 복제본은 기본 서버와 같은 비용이 듭니다. 월 $340에서 월 $680로.

"우리가 부하를 대략 절반으로 하려고 비용을 두 배로 했네요," Tom이 말했습니다.

"네. 하지만 대안은 더 큰 인스턴스 유형으로 옮기는 것이었는데, 그것도 더 비싸고 읽기 부하를 분산하지 않을 거예요."

Tom이 계산했습니다. 그가 마지못해 고개를 끄덕였습니다.

"기본 서버가 실패하면요?" Maya가 Tom이 Aurora로 전환하기 전에 물었습니다. "읽기 복제본은 어떻게 되죠?"

Leo가 복제본 승격을 설명했습니다.

**기본 RDS 인스턴스가 실패하면**, AWS가 멀티 AZ 구성의 스탠바이 복제본(다른 종류의 복제본 — 읽기 복제본이 아니라 동기 스탠바이)으로 자동으로 장애 조치합니다. 멀티 AZ 스탠바이가 새 기본 서버가 됩니다. 읽기 복제본은 이제 새 기본 서버로부터 복제하면서 계속 읽기를 제공합니다. 애플리케이션 관점에서, 기본 엔드포인트 DNS가 이전 스탠바이를 가리키도록 바뀌고, 애플리케이션이 재연결합니다.

장애 조치는 RDS PostgreSQL의 경우 일반적으로 60~120초가 걸립니다. 그 창 동안, 쓰기가 실패합니다.

**읽기 복제본 승격**은 별도의 작업입니다 — 그리고 별도의 시나리오입니다. 읽기 복제본을 가져와 독립적이고 쓰기 가능한 데이터베이스로 만들고 싶다면(DR을 위해, 새 리전으로의 마이그레이션을 위해, 또는 기본 서버가 사라져서 멀티 AZ 장애 조치를 기다리는 대신 승격해야 하기 때문에), 읽기 복제본을 독립형 기본 서버로 승격할 수 있습니다. 승격은 몇 분이 걸리고, 그 후 복제본은 더 이상 원래 기본 서버로부터 복제하지 않습니다 — 그것은 자체 데이터베이스입니다.

"us-west-2 기본 서버가 완전히 다운되면 어떻게 되는지 생각해봤어요?" Priya가 물었습니다. "단지 멀티 AZ 스탠바이로의 장애 조치가 아니라 — 전체 리전이요."

"리전이 실패하면," Leo가 말했습니다, "멀티 AZ 스탠바이도 us-west-2에 있어요. 둘 다 함께 실패해요."

"그러니까 진정한 지역 DR 시나리오를 위해서는," Tom이 말했습니다, "우리가 승격할 수 있는 us-east-1의 읽기 복제본이 필요하겠네요."

"네. 교차 리전 읽기 복제본. 우리는 아직 하나도 없어요."

"그게 월 얼마나 들죠?" Tom이 물었습니다. 그는 이미 답이 결정을 포함할 것을 알고 있었습니다.

us-east-1의 db.r6g.large의 교차 리전 읽기 복제본: 월 $340(같은 인스턴스 비용). 더하기 복제를 위한 교차 리전 데이터 전송: Nimbus의 쓰기 볼륨에서 미미함. 총: DR 복제본에 대해 약 월 $350.

"그건 연간 $4,200이에요," Tom이 말했습니다, "10년 동안 AWS 리전에 다섯 번 미만 일어난 시나리오로부터 보호하기 위해서요."

"그리고 지역 이벤트 동안 Nimbus가 24시간 다운되는 비용은요?" Priya가 물었습니다.

Tom이 계산했습니다. 그는 소리 내어 답하지 않았습니다. 하지만 그가 DR 백로그에 "교차 리전 읽기 복제본"을 추가했습니다.

"Aurora가 뭐예요?" 그가 물었습니다.

**Amazon Aurora: 데이터베이스 엔진 재고하기**

Aurora는 AWS의 독점 관계형 데이터베이스 엔진으로, MySQL과 PostgreSQL과 호환됩니다. 그것은 클라우드 워크로드를 위해 처음부터 설계되어, 관계형 데이터베이스의 스토리지 계층이 작동하는 방식을 재상상했습니다.

전통적인 RDS 설정(MySQL, PostgreSQL)에서, 스토리지와 컴퓨팅이 긴밀하게 결합됩니다. 데이터베이스 엔진이 데이터 파일을 관리합니다. 복제가 기본 서버에서 복제본으로 데이터를 복사합니다. 복제본이 모든 쓰기 작업을 다시 실행해야 합니다.

이것이 복제 속도에 천장을 만듭니다: 복제본은 복제 로그를 처리할 수 있는 만큼 빠르게만 쓰기를 적용할 수 있습니다. 쓰기가 많은 기간 동안 — 대량 임포트, 플래시 세일, 배치 업데이트 — 복제본이 뒤처질 수 있습니다. 복제 지연은 구현의 결함이 아닙니다; 그것은 아키텍처의 결과입니다.

Priya가 Leo가 읽기 복제본을 제안했을 때 이것을 즉시 지적했습니다. "그리고 금요일 러시 동안 복제 지연이 30초로 급증하면 어떻게 되는지 생각해봤어요? 복제본이 30초 뒤처져요. 고객이 주문을 하고, 주방 슬롯이 기본 서버에 예약되지만, 복제본을 쿼리하는 두 번째 고객이 예약을 보지 못해요. 두 주문, 한 슬롯."

"그건 인벤토리 일관성 문제예요," Leo가 말했습니다.

"그게 정확히 인벤토리 일관성 문제예요," Priya가 확인했습니다. "그것이 인벤토리 읽기 — '이 항목이 아직 사용 가능한가?' — 가 기본 서버로 가야 하는 이유예요."

Aurora의 아키텍처가 지연을 직접 다룹니다.

Aurora는 스토리지를 컴퓨팅에서 분리합니다. 그것은 데이터를 세 개의 가용 영역에 걸쳐 여섯 개 사본으로 자동으로 복제하는 분산되고 장애 허용적인 스토리지 계층을 사용합니다. 컴퓨팅 계층(데이터베이스 인스턴스)이 이 스토리지 계층 위에 앉습니다.

**이것이 바꾸는 것**:

**읽기 복제본**: Aurora 복제본은 데이터를 복제할 필요가 없습니다 — 그것들은 이미 같은 스토리지 계층을 공유합니다. 이것은 다음을 의미합니다:

- 스토리지 볼륨을 공유하는 최대 15개의 Aurora 복제본(일반 RDS도 최대 15개의 읽기 복제본을 허용하지만, 각각이 전체 데이터 사본임)
- 복제 지연이 일반적으로 100밀리초 미만(부하 시 RDS의 초에 비해)
- 복제본이 30초 미만에 기본 서버로 승격될 수 있음(분에 비해)

**장애 조치**: 복제본이 스토리지를 공유하기 때문에, 장애 조치가 훨씬 빠릅니다 — 승격이 데이터 전송을 포함하지 않고, 그저 쓰기를 리디렉션합니다.

**스토리지**: Aurora가 10GB 단위로 스토리지를 자동으로 확장하며, 최대 128 TiB(최근 엔진 버전에서 256 TiB)까지입니다. 스토리지를 미리 프로비저닝하지 않습니다.

**성능**: Aurora는 동등한 인스턴스 유형에 대해 표준 MySQL의 5배 처리량, 표준 PostgreSQL의 3배를 주장합니다.

여러분은 궁금해할지 모릅니다: 모든 복제본이 같은 스토리지를 공유한다면, 그 스토리지가 단일 장애 지점이 되지 않나요? Aurora의 스토리지 계층은 데이터를 세 개의 가용 영역에 걸쳐 여섯 개 사본으로 자동으로 복제합니다. 스토리지 자체가 어떤 단일 RDS 멀티 AZ 설정보다 더 탄력적입니다 — 그것은 데이터 손실 제로와 필요한 장애 조치 없이 전체 AZ의 손실을 견디도록 설계되었습니다.

두 번째 흔한 질문: Aurora가 MySQL/PostgreSQL 호환이라면, 애플리케이션 코드를 변경하지 않고 RDS PostgreSQL에서 Aurora PostgreSQL로 마이그레이션할 수 있나요? 거의요. Aurora PostgreSQL 호환성은 Aurora가 PostgreSQL 와이어 프로토콜을 구현하고 PostgreSQL SQL 구문과 기능의 대다수를 지원한다는 것을 의미합니다. 대부분의 애플리케이션이 코드 변경 제로로 마이그레이션합니다. 엣지 케이스: 소수의 PostgreSQL 확장이 Aurora에서 사용 불가능하고, 일부 시스템 카탈로그 쿼리가 다른 값을 반환하며, 특정 관리 작업이 다릅니다. 프로덕션 마이그레이션의 경우, 쓰기를 전환하기 전에 병렬 읽기 트래픽으로 테스트하십시오.

Nimbus의 경우, RDS PostgreSQL에서 Aurora PostgreSQL로의 마이그레이션이 오후 하루 걸렸습니다. 애플리케이션이 Aurora 엔드포인트를 가리켰습니다. 메뉴 쿼리가 — Leo가 Performance Insights가 데이터베이스 부하의 최상위 소비자로 가리킨 인덱스를 추가한 후 — 620ms 대신 4ms에 실행되었습니다. 연결 풀이 더 이상 200개 중 198개에 도달하지 않았습니다. P95 지연이 28ms로 떨어졌습니다.

"그건 다른 데이터베이스 엔진이에요," Leo가 말했습니다, "애플리케이션이 같은 데이터베이스 엔진이라고 생각하는."

"그리고 흥미로운 부분은요?" Maya가 물었습니다.

"빠른 데이터베이스 복제요."

"기록했어요," Sam이 방 건너편에서 조용히 말하며, 이미 타이핑하고 있었습니다. Sam은 Leo의 일에서 데이터베이스 작업의 일부를 덜기 위해 몇 주 전에 팀에 합류한 백엔드 엔지니어였습니다. 아무도 그가 무엇을 하고 있는지 묻지 않았습니다.

**Aurora 가격: Tom 질문**

Aurora 가격은 RDS와 다릅니다:

**인스턴스 가격**: 유형별 RDS 인스턴스 가격과 유사함.

**스토리지 가격**: GB당 월 $0.10(저장된 것에 지불, 자동으로 확장됨).

**I/O 가격**: Aurora는 I/O 요청당(스토리지에 대한 읽기/쓰기) 요금을 부과합니다. 이것은 쓰기가 많은 워크로드에 상당할 수 있습니다.

"잠깐," Tom이 말했습니다. "우리가 I/O에 별도로 지불하는 거예요?"

"Aurora Serverless v2와 Aurora I/O-Optimized가 이 가격 모델을 바꿔요," Leo가 말했습니다. "Aurora I/O-Optimized는 I/O 요금을 부과하지 않지만 더 높은 스토리지와 인스턴스 가격을 부과해요. I/O가 많은 워크로드에 더 좋아요."

Tom이 절충안을 보았습니다. 읽기가 많은(많은 메뉴 쿼리, 적은 쓰기) Nimbus의 경우, Aurora I/O-Optimized가 더 비쌀 수 있었습니다. 표준 Aurora 가격이 적절할 수 있었습니다.

유용한 경험칙: I/O 요금이 총 Aurora 청구서의 대략 25%를 초과하면, I/O-Optimized가 더 저렴할 가능성이 높습니다. Nimbus의 읽기가 많은 워크로드의 경우, I/O 요금이 낮았습니다 — 표준 가격이 적용됩니다. 이벤트 로깅 시스템 같은 쓰기가 많은 워크로드의 경우, I/O-Optimized가 비용을 상당히 줄일 수 있습니다.

이것은 시니어 엔지니어가 내리는 실제 비용 결정입니다: 올바르게 선택하려면 워크로드의 I/O 패턴을 알아야 합니다.

워크로드가 작고, 안정적이고, 예측 가능하다면, RDS PostgreSQL이 더 단순하고 의미 있게 더 저렴합니다 — 하지만 트래픽이 예측 불가능하거나, 데이터 볼륨이 미리 프로비저닝할 수 있는 것을 넘어 성장하고 있거나, 30초 미만의 자동 장애 조치가 필요하다면, Aurora의 공유 스토리지 모델이 더 높은 기본 비용을 정당화합니다.

**Aurora Serverless: 인스턴스를 생각하지 않고 확장하기**

**Aurora Serverless v2**는 실제 데이터베이스 부하에 기반해 컴퓨팅 용량을 자동으로 확장하는 구성입니다. 고정된 인스턴스 크기(db.r6g.large)를 선택하는 대신, Aurora Capacity Unit(ACU)으로 최소 및 최대 용량을 설정합니다.

Aurora Serverless v2:

- 부하가 증가하면 초 단위로 확장
- 유휴 기간 동안 축소 — 그리고 2024년 말부터, 연결이 없을 때 0 ACU까지 자동 일시 중지할 수 있음(재개는 ~15초 걸림; 자동 일시 중지는 RDS Proxy나 다른 연결 유지 프록시와 함께 작동하지 않음)
- 비용: ACU-시간당 $0.12(더하기 스토리지와 I/O)

가변 트래픽이 있는 워크로드의 경우 — Nimbus의 금요일 급증 대 월요일 아침 조용함 — Serverless v2가 비수요 기간 동안 비용을 줄이고 사전 프로비저닝 없이 피크를 처리합니다.

"그러니까 금요일 급증 동안," Leo가 말했습니다, "Aurora가 자동으로 확장돼요. 거의 트래픽이 없는 일요일 아침에, 그것이 다시 최소치로 축소돼요."

"그리고 우리는 사용하는 용량에 대해서만 지불해요," Tom이 말했습니다.

"맞아요."

Aurora Serverless v2에서 한 달 후, Leo가 지난주의 ACU(Aurora Capacity Unit) 그래프를 불러왔습니다.

그래프가 두 개의 뚜렷한 패턴을 보여주었습니다. 주중에, 데이터베이스가 2~4 ACU로 실행되었습니다 — 백그라운드 쿼리, ECS 상태 확인, Glue ETL 작업, 개발 테스트의 조용한 웅성거림. 금요일 저녁 18:00와 22:00 사이에, ACU 수가 올랐습니다:

```
Friday 18:00  → 6 ACUs
Friday 19:00  → 14 ACUs
Friday 19:45  → 26 ACUs  (피크 — NFL 킥오프 전 피자 주문 급증)
Friday 20:30  → 18 ACUs
Friday 21:00  → 12 ACUs
Friday 22:30  → 4 ACUs
Saturday 02:00 → 2 ACUs  (최소)
```

확장이 거의 즉각적이었습니다 — Aurora Serverless v2는 0.5 ACU 단위로 확장하고, 새 RDS 인스턴스를 프로비저닝하는 데 필요한 분이 아니라 초 단위로 용량을 추가할 수 있습니다.

"그 금요일 피크가 얼마나 들었어요?" Tom이 물었습니다.

ACU-시간당 $0.12로: 금요일 피크는 평균 18 ACU로 4시간 → 피크 기간에 $8.64. 나머지 주는 평균 3 ACU × 164시간 × $0.12 = $59.04. 주 총: $67.68.

금요일 피크를 처리하는 동등한 프로비저닝된 인스턴스(db.r6g.xlarge, 4 vCPU, 32 GB)는 $0.937/시간 × 168시간 = **주에 $157.42**가 들 것입니다 — 금요일의 피크가 실제로 발생하든 안 하든요.

"Serverless v2는 주에 $67이에요. 피크에 맞춰 크기가 정해진 프로비저닝된 인스턴스는 $157이에요," Tom이 말했습니다. "그건 57% 감소예요."

"금요일에 네 시간 동안 정당하게 26 ACU를 사용하고 나머지 주는 2 ACU를 사용하는 데이터베이스에서요," Leo가 말했습니다. "데이터베이스가 일주일 내내 일관된 높은 부하로 실행되면, 프로비저닝된 인스턴스가 더 저렴해요. 절감은 가변성에서 나와요."

Tom이 천천히 고개를 끄덕였습니다. 그가 노트의 패턴에 이것을 추가하고 있었습니다: 이번 분기의 모든 절감 이야기가 같은 모양을 가졌습니다. 필요할지도 모르는 것이 아니라, 사용하는 것에 대해 지불합니다. S3 수명 주기 정책이 각 객체가 정당화하는 스토리지 클래스에 대해서만 지불했습니다. Lambda가 호출 시간에 대해서만 지불했습니다. Fargate가 태스크 CPU와 메모리에 대해서만 지불했습니다. Aurora Serverless v2가 데이터베이스가 실제로 소비한 ACU에 대해서만 지불했습니다.

Tom은 정확히 찾고 있던 것을 발견한 사람의 표정을 했습니다.

**나쁜 마이그레이션에서 복구하기: 클론, PITR, 그리고 실행 취소 버튼**

Aurora로 옮긴 지 2주 후, Sam이 프로덕션에서 데이터베이스 마이그레이션 스크립트를 실행했습니다. 스크립트는 `menu_items` 테이블에서 `legacy_menu_format` 열을 제거하기로 되어 있었습니다. 그가 포함했다고 생각한 WHERE 절 없이 그것을 실행했습니다.

결과는 열을 제거하는 것이 아니었습니다. 그것은 `menu_items` 테이블에서 40,000개 행을 지운 DELETE 문이었습니다 — 약 200개 레스토랑 분량의 메뉴 데이터가, 사라졌습니다.

알림이 30초 이내에 발사되었습니다. 주문 실패가 급증했습니다. 메뉴 서비스가 200개 레스토랑에 대해 빈 결과를 반환하기 시작했습니다.

"WHERE 절이 있어야 했어요," Sam이 콘솔을 응시하며 말했습니다.

전통적인 복구 경로: 가장 최근 자동 백업 스냅샷에서 복원. 자동 백업은 24시간마다 한 번 실행되고, 전체 복원-및-교체는 20~40분이 걸릴 것입니다 — 그동안 영향받은 200개만이 아니라 *모든* 레스토랑이 어두워질 것이고 — 백업 이후 들어온 모든 주문이 손실될 것입니다.

Leo는 그것을 하지 않았습니다. 표준 RDS처럼, Aurora는 **시점 복구(PITR, point-in-time recovery)**를 위해 연속 백업을 유지합니다 — 마지막 야간 스냅샷뿐만 아니라 백업 보존 창 내의 어떤 초로든 클러스터를 복원할 수 있습니다. 그리고 중요하게도, 복원이 *새* 클러스터를 생성합니다; 복구하는 동안 프로덕션이 가동 상태로 유지됩니다.

```bash
aws rds restore-db-cluster-to-point-in-time \
  --db-cluster-identifier nimbus-aurora-recovery \
  --source-db-cluster-identifier nimbus-aurora-cluster \
  --restore-to-time 2024-06-14T15:42:00Z
```

타임스탬프: 15:42:00Z — Sam이 마이그레이션 스크립트를 실행하기 4분 전. 복구 클러스터가 가동되는 동안, 나머지 프로덕션이 영향받지 않은 레스토랑을 계속 제공했습니다. 그것이 사용 가능해지자, Leo가 복구 클러스터에서 영향받은 200개 레스토랑의 `menu_items` 행을 덤프하고 그것들을 프로덕션에 다시 삽입했습니다. 알림에서 완전히 복원된 메뉴까지의 총 시간: 40분 약간 미만 — 그리고 그가 전체 데이터베이스를 교체하는 대신 행을 외과적으로 수리했기 때문에, 15:42 이후 들어온 어떤 주문도 손실되지 않았습니다. 복구 클러스터는 그 후 삭제되었습니다; 그것은 목적을 달성했습니다.

"우리가 뭘 잃었어요?" Maya가 물었습니다.

잠깐 비어 있던 메뉴에 대해 들어온 여섯 개의 주문이 결제에서 실패했습니다 — 그것들 모두가 SQS 큐에 있었고 다시 재생될 수 있었습니다. 어떤 고객 데이터도 영구적으로 손실되지 않았습니다.

"그리고 여기가 **빠른 데이터베이스 복제**가 들어오는 곳이에요," Leo가 그 후 팀을 모으며 말했습니다. Aurora는 데이터베이스 크기와 관계없이 몇 분 안에 클러스터의 **클론(clone)**을 생성할 수 있습니다, copy-on-write를 사용해서요: 클론이 원본의 스토리지 계층을 공유하고 오직 새로운 또는 변경된 페이지만 추가 공간을 소비합니다. 현재 프로덕션 데이터베이스의 클론은 저렴하고, 빠르고, 완전히 격리됩니다 — 클론에 대한 쓰기는 결코 프로덕션을 건드리지 않습니다.

"즉," Priya가 Sam을 보며 말했습니다, "마이그레이션 스크립트가 프로덕션에서 실행되기 전에 프로덕션 데이터의 클론에 대해 테스트되는 거예요. 그게 새 규칙이에요."

Sam이 고개를 끄덕였습니다. 그는 이미 그것을 포스트잇에 적었습니다.

한 가지 도구가 더 이 그림에 속합니다. Aurora MySQL — Aurora PostgreSQL이 아니라 — 에는 **Aurora Backtrack**이 있습니다: 새 클러스터로 복원하지 않고 클러스터를 특정 시점으로 *제자리에서* 되감는 기능. Nimbus의 클러스터가 Aurora MySQL이었다면, Leo가 3분 미만에 그것을 15:42로 백트랙할 수 있었을 것입니다 — 다만 전체 클러스터를 되감으면 삭제 후 쓰인 소수의 정당한 주문도 롤백되었을 텐데, 외과적 PITR 접근법은 그것들을 보존했습니다.

"그러면 누군가 Backtrack을 사용해서 침입을 시도하면 — 아니면 시점 복원을요? 공격자가 감사 로그나 규정 준수 데이터를 되감을 수 있나요?" Priya가 물었습니다.

Backtrack은 `rds:BacktrackDBCluster` API 권한이 필요하고, 복원은 `rds:RestoreDBClusterToPointInTime`이 필요합니다 — 정상 데이터베이스 작업과 별도의 IAM 동작. 표준 애플리케이션 역할은 이 권한이 없습니다. 그것들을 허용하는 명시적 IAM 정책을 가진 운영 팀만이 그것들을 사용할 수 있습니다. 그녀가 이것을 IAM 권한 검토 체크리스트에 추가했습니다.

중요한 주의 사항: Aurora Backtrack은 PostgreSQL이 아니라 Aurora MySQL 호환 클러스터에만 사용 가능합니다. Backtrack 창은 클러스터 생성 시 구성됩니다(1시간에서 72시간, 백트랙 창 시간당 요금). 그리고 Backtrack은 전체 클러스터에 영향을 미칩니다 — 한 테이블이나 한 행 집합을 백트랙할 수 없습니다. 외과적 행 수준 복구의 경우 — 어느 엔진에서든 — Leo가 사용한 임시 클러스터로의 PITR 접근법이 도구입니다.

**Aurora Global Database: 멀티 리전 읽기**

**Aurora Global Database**는 Aurora를 여러 AWS 리전에 걸쳐 확장합니다:

- **하나의 기본 리전**이 모든 쓰기를 처리합니다
- **최대 다섯 개의 보조 리전**이 일반적으로 1초 미만의 복제 지연으로 읽기를 제공합니다
- 보조 리전이 1분 미만에 기본 서버로 승격될 수 있습니다(DR 시나리오용)

Nimbus의 글로벌 확장의 경우, Aurora Global Database가 런던의 레스토랑 파트너가 EU 읽기 복제본에서 로컬 메뉴를 쿼리하게 하는 동안, 모든 주문(쓰기)은 여전히 US 기본 서버를 거칩니다.

**RDS vs Aurora: 각각을 언제 선택하는가**

| 요소 | RDS(PostgreSQL/MySQL) | Aurora |
|-------------------|-------------------------------|------------------------------------------------------------|
| 비용 | 작은 워크로드에 더 낮음 | 더 높은 기본, 하지만 더 잘 확장됨 |
| 호환성 | 완전 | MySQL/PostgreSQL 호환(사소한 차이 있음) |
| 최대 복제본 | 15(각각 전체 데이터 사본) | 15(공유 스토리지 볼륨) |
| 복제본 지연 | 초가 될 수 있음 | 보통 100ms 미만 |
| 스토리지 | 고정 프로비저닝 | 128 TiB까지 자동 확장(최근 버전에서 256 TiB) |
| 장애 조치 시간 | 60~120초 | 30초 미만 |
| 서버리스 옵션 | 제한적 | Aurora Serverless v2 |
| 가장 적합 | 안정적, 예측 가능한 워크로드 | 가변 트래픽, 높은 읽기 볼륨, 빠른 장애 조치 필요 |

**관계형을 넘어: 목적 특화 패밀리**

9장에서 DocumentDB(MongoDB 호환 문서), Neptune(그래프 관계), Keyspaces(Cassandra 호환 와이드 컬럼)를 소개했고, 10장에서 MemoryDB(내구성 있는 Redis 호환 기본 데이터베이스)를 소개했습니다. 두 개의 이름이 더 패밀리를 완성합니다 — 그것들에 대한 깊이가 필요하지 않고, 그저 어떤 데이터 모양이 어떤 엔진을 가리키는지 인식하는 능력만 있으면 됩니다. 그것들이 답 옵션으로 끊임없이 나타나기 때문입니다:

- **Amazon Timestream**: **시계열** 데이터 — 센서 판독값, 지표, 텔레메트리. 시험 신호: "시간에 따른 IoT 측정." (현실 세계에서 현재 제공은 Timestream for InfluxDB입니다; 원래의 "LiveAnalytics" 종류는 2025년에 신규 고객에게 닫혔습니다.)
- **Amazon QLDB**: 오래된 질문에서 여전히 "불변의, 암호학적으로 검증 가능한 원장"으로 그것을 만날 수 있습니다. AWS가 2025년에 QLDB를 중단했습니다(대신 Aurora PostgreSQL을 권장) — 그것을 빌딩 블록이 아니라 레거시 방해 요소로 취급하십시오.

화이트보드에 적을 가치가 있는 규칙: **관계형 행 → RDS/Aurora; 대규모 키-값 → DynamoDB; 문서 → DocumentDB; 관계 → Neptune; 시간 → Timestream; Cassandra → Keyspaces; 내구성 있는 Redis → MemoryDB.** 모양을 맞추면, 질문이 스스로 답합니다.

## 장점과 한계

**Aurora 강점**:

- 표준 RDS보다 상당히 빠른 장애 조치
- 최소 지연으로 최대 15개 읽기 복제본
- 자동 확장 스토리지
- 가변 워크로드를 위한 Serverless v2
- 멀티 리전 배포를 위한 Global Database

**Aurora 한계**:

- 작고 안정적인 워크로드에 더 높은 비용
- I/O 가격이 쓰기가 많은 워크로드에 상당할 수 있음(이를 위해 I/O-Optimized 사용)
- 사소한 MySQL/PostgreSQL 호환성 차이가 코드 변경을 요구할 수 있음
- 자동 일시 중지에서의 Serverless v2 재개(~15초)와 빠른 확장이 지연 급증을 유발할 수 있음

## 요약

23장의 S3 수명 주기 작업은 데이터를 올바른 스토리지 계층으로 옮겨 비용을 줄였습니다. Aurora는 컴퓨팅에 대해 동등한 것을 합니다: 피크 부하에 맞춰 프로비저닝하고 항상 그것에 대해 지불하는 대신, Serverless v2가 수요에 맞춰 확장합니다.

- **읽기 복제본**은 기본 서버로부터 읽기 트래픽을 분산합니다. 비동기 복제 — 대부분의 읽기에 약간의 지연이 수용 가능함. 쓰기 일관성이 필요한 읽기(쓰기 직후 읽기, 관리 인터페이스 읽기)는 복제본이 아니라 기본 서버로 라우팅하십시오.
- **Aurora**는 스토리지 계층을 재상상합니다: 분산되고, 복제본 전체에 공유되며, 자동 확장됩니다.
- Aurora가 제공: 15개 읽기 복제본, 100ms 미만 복제본 지연, 30초 미만 장애 조치, 최대 128 TiB(최근 버전에서 256 TiB) 자동 확장 스토리지.
- **Performance Insights**: 어떻게 확장할지 결정하기 전에 데이터베이스 부하를 일으키는 특정 SQL 쿼리를 식별합니다. 누락된 인덱스가 더 큰 인스턴스의 필요를 제거할 수 있습니다.
- **CloudWatch 데이터베이스 지표**: DatabaseConnections(포화에 가까움은 애플리케이션 연결 풀링이 깨졌음을 의미), CPUUtilization(지속된 높은 CPU는 비싼 쿼리를 의미), ReadLatency(시간에 따른 저하는 종종 누락된 인덱스를 가진 커지는 테이블).
- **Aurora Serverless v2**: 0.5 ACU 단위로 컴퓨팅을 자동 확장합니다. ACU-시간당 청구됨. 피크와 비피크 사이 높은 가변성을 가진 워크로드에 프로비저닝된 인스턴스보다 상당히 저렴합니다.
- **시점 복구(PITR)**: Aurora 클러스터를 백업 보존 창 내의 어떤 초로든 복원 — *새* 클러스터로, 그래서 손실된 행을 외과적으로 복사하는 동안 프로덕션이 가동 상태로 유지됩니다.
- **빠른 데이터베이스 복제**: 크기와 관계없이 몇 분 안에 클러스터의 copy-on-write 클론. 저렴하고, 격리됨 — 프로덕션에서 실행되기 전에 프로덕션 데이터에 대해 마이그레이션을 테스트하는 데 사용하십시오.
- **Aurora Backtrack**(MySQL 호환 전용 — PostgreSQL 아님): 백업에서 복원하지 않고 클러스터를 제자리에서 시점으로 되감습니다. 최대 72시간 창에 사용 가능. `rds:BacktrackDBCluster` IAM 권한이 필요함 — 운영 팀으로 제한.
- **Aurora Global Database**: 한 리전의 기본, 최대 다섯 리전의 읽기 복제본.
- **읽기 복제본 승격**: 교차 리전 읽기 복제본이 지역 DR을 위해 독립형 기본 서버로 승격될 수 있습니다. DR 이익을 두 번째 전체 인스턴스 실행 비용과 견주십시오.
- 더 작고, 안정적이고, 예측 가능한 워크로드에는 RDS를 선택하십시오. 규모, 빠른 장애 조치, 또는 가변 트래픽 처리가 필요할 때 Aurora를 선택하십시오.

## 시험 팁

*SAA-C03 도메인: 고성능 아키텍처 설계(도메인 3, 태스크 3.3)*

- **Aurora 복제본 vs RDS 읽기 복제본**: Aurora 복제본은 스토리지를 공유합니다(거의 제로 지연, 30초 미만 장애 조치). RDS 읽기 복제본은 데이터를 복제합니다(지연 가능, 장애 조치에 분).
- **Aurora Serverless v2**: "데이터베이스 용량 자동 확장," "예측 불가능하거나 뾰족한 데이터베이스 트래픽" → Aurora Serverless v2. 주의: 역사적으로 Serverless **v1**만 제로로 확장했습니다; v2의 최소치는 2024년 말까지 0.5 ACU였는데, 그때 v2가 0 ACU로의 자동 일시 중지를 얻었습니다. 오래된 시험 문제는 여전히 v2가 제로로 확장할 수 없다고 가정할 수 있습니다.
- **Aurora Global Database**: "멀티 리전 데이터베이스," "US 기본에서 낮은 지연으로 EU에서 읽기," "지역 장애 조치에 대해 RTO < 1분" → Aurora Global Database.
- **장애 조치 타이밍**: Aurora < 30초. RDS 멀티 AZ 60~120초. 둘 다 알아두십시오.
- **데이터 모양별 목적 특화 데이터베이스**: "소셜 그래프 / 추천 / 사기 링" → Neptune. "MongoDB" → DocumentDB. "Cassandra" → Keyspaces. "시계열 / IoT 텔레메트리" → Timestream. "Redis 호환 *기본* 데이터베이스(내구성 있는)" → MemoryDB(ElastiCache = 캐시에 비해). "불변 암호학적 원장" → 오래된 질문에서 QLDB(2025년 중단).
- **Aurora I/O-Optimized**: 더 높은 스토리지와 인스턴스 비용, I/O당 요금 없음. I/O 비용이 지배할 때(쓰기가 많음) 사용. 표준 Aurora: 더 낮은 스토리지 비용, I/O당 지불. 읽기가 많은 경우에 사용.
- **Aurora Backtrack**: 백업 스냅샷에서 복원하지 않고 데이터베이스를 특정 시점으로 제자리에서 되감습니다. MySQL 호환 Aurora에만 사용 가능 — Aurora PostgreSQL의 경우, 답은 시점 복원(새 클러스터로) 또는 빠른 클론입니다. 시험 신호: "실수로 데이터를 삭제, 전체 백업을 복원하지 않고 빠르게 복구 필요" + MySQL → Backtrack.
- **Aurora 빠른 데이터베이스 복제**: 데이터베이스 크기와 관계없이 몇 분 안에 copy-on-write 클론. 시험 신호: "프로덕션 데이터의 사본에 대해 빠르고 저렴하게 테스트" → 스냅샷 복원이 아니라 클론.

## 연습 문제

**연습 1 — 회상**

Aurora와 표준 RDS 읽기 복제본의 차이를 설명하십시오. 왜 Aurora의 복제 지연이 일반적으로 더 낮습니까?

*(힌트: 핵심 차이는 공유 스토리지 대 데이터 복제입니다. 쓰기가 도착할 때 각 복제본이 무엇을 해야 하는지 생각해보십시오.)*

**연습 2 — SAA-C03 시나리오**

*시나리오*: 소셜 미디어 플랫폼의 MySQL 데이터베이스가 증가하는 트래픽으로 인해 높은 읽기 지연을 경험하고 있습니다. 애플리케이션은 읽기가 많습니다(95% 읽기, 5% 쓰기). 팀은 트래픽 급증 동안에도 읽기 지연이 일관적이기를 필요로 합니다. 그들은 최소 다운타임으로 자동 장애 조치가 필요합니다(목표 RTO < 30초). 데이터 볼륨이 예측 불가능하게 성장하고 있습니다.

이 요구사항을 가장 잘 충족하는 데이터베이스 솔루션은 무엇입니까?

A) 다섯 개의 읽기 복제본이 있는 RDS MySQL 멀티 AZ  
B) Aurora 복제본과 Aurora Serverless v2가 있는 Aurora MySQL  
C) 더 큰 인스턴스 유형의 RDS MySQL(수직 확장)  
D) 읽기 캐싱을 위한 DynamoDB DAX가 있는 DynamoDB

**힌트 1**: "RTO < 30초" — 어떤 서비스가 이를 달성합니까? 각 옵션의 장애 조치 타이밍을 확인하십시오.

**힌트 2**: "급증 동안 일관된 읽기 지연" — 어떤 서비스의 복제본이 잠재적 몇 초의 지연 대 거의 제로 지연을 가집니까?

**힌트 3**: "예측 불가능하게 성장하는 데이터 볼륨" — 어떤 서비스가 스토리지를 자동 확장합니까?

**정답**: B

**설명**: Aurora 복제본이 있는 Aurora MySQL은 부하 아래에서 일관된 읽기 성능을 위해 거의 제로의 복제 지연(초가 아니라 밀리초)을 제공합니다. Aurora Serverless v2가 과잉 프로비저닝 없이 트래픽 급증 동안 컴퓨팅을 자동 확장합니다. Aurora 스토리지가 데이터가 성장하면서 자동 확장합니다. Aurora 장애 조치(복제본의 승격)가 30초 미만에 완료됩니다 — RTO 요구사항을 충족합니다.

**왜 A가 아닌가?** RDS 멀티 AZ 장애 조치는 60~120초가 걸립니다 — RTO < 30초를 충족하지 않습니다. 표준 RDS 읽기 복제본 지연이 부하 아래에서 몇 초에 도달할 수 있습니다 — "일관된" 읽기 지연을 보장하기 더 어렵습니다.

**왜 C가 아닌가?** 수직 확장(더 큰 인스턴스)은 용량을 늘리지만 읽기 부하를 분산하지 않습니다. 데이터베이스가 읽기에 대한 단일 장애 지점으로 남습니다.

**왜 D가 아닌가?** DynamoDB는 NoSQL입니다 — MySQL에서 DynamoDB로 마이그레이션하는 것은 데이터 모델과 애플리케이션 쿼리를 재설계하는 것이 필요하며, 이것은 이 성능 개선 작업의 범위를 훨씬 넘어섭니다.

*SAA-C03 도메인: 고성능 아키텍처 설계 — 태스크 3.3*
