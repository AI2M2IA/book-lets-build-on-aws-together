# 6장: 당신을 따라다니는 디스크

Tom에게는 빨간 펜과 Leo를 불안하게 만드는 습관이 있었다.

매주 토요일 아침, Tom은 AWS 콘솔 요약 — 실행 중인 인스턴스, 스토리지 볼륨, 연결된 디스크 — 을 출력하고 한 줄씩 살펴봤다. 그는 2주차부터 이렇게 해왔다. 그는 그것을 "원장"이라고 불렀다. Leo는 그것을 "Tom이 하는 그 일, Leo가 뭔가 잘못했다는 느낌을 주는"이라고 불렀다.

그 토요일, Tom은 무언가에 동그라미를 치고 한 마디도 하지 않고 Maya의 책상에 프린트물을 올려놓았다.

그녀는 월요일 아침에 발견했다. 동그라미 하나. 여백에 세 단어 메모:

*모든 것. 하나의 머신.*

웹 서버. 데이터베이스. 모든 고객 레코드. 두 달치 주문 내역. 이 모든 것이 단일 EC2 인스턴스에서 실행되고 있었다.

"인스턴스가 충돌하면 데이터베이스에 무슨 일이 일어나요?" Maya가 프린트물을 손에 들고 물었다.

"그것도 충돌해요," Leo가 말했다.

"그리고 데이터는요?"

"데이터베이스가 그걸 어떻게 저장하느냐에 달려 있어요."

그 "달려 있어요"가 문제였다.

**EC2 인스턴스가 데이터를 저장하는 방법**

EC2 인스턴스가 실행될 때, 운영 체제는 어딘가의 디스크에 산다. 그 디스크를 **루트 볼륨**이라고 한다. 기본적으로, 이것은 **EBS 볼륨**이다 — 생각하지 않더라도.

하지만 다른 것도 있다: EC2 인스턴스에는 **인스턴스 스토어** 스토리지도 있다.

인스턴스 스토어는 가상 머신을 실행하는 기본 하드웨어에 물리적으로 연결된 임시 스토리지다. 매우 빠르다 — AWS의 거의 모든 다른 스토리지 옵션보다 빠르다. 하지만 문제가 있다.

인스턴스 스토어는 **일시적**이다.

인스턴스가 중지되거나 종료되면, 인스턴스 스토어 데이터가 사라진다. 영구적으로. 복구 불가능하다. AWS는 이에 대해 크게 경고하지 않는데, 팀이 그것을 발견하는 방법이다: 데이터를 잃음으로써.

인스턴스 스토어는 캐시, 임시 처리 파일, 스크래치 공간에 적합하다. 중요한 데이터에는 절대 안 된다.

**EBS: 영구 디스크**

**Amazon EBS** — Elastic Block Store — 는 EC2 인스턴스를 위한 영구 블록 스토리지다.

블록 스토리지는 실제 하드 드라이브처럼 동작한다는 것을 의미한다: 운영 체제가 파일시스템을 만들고, 임의 위치에서 임의 바이트를 읽고 쓸 수 있으며, 데이터베이스를 실행하고, 연결된 디스크처럼 정확히 처리할 수 있다.

핵심 속성:

**영구적.** 인스턴스 스토어와 달리, EBS 볼륨은 인스턴스 중지, 시작, 심지어 인스턴스 종료(설정에 따라)에서도 살아남는다. 아무 인스턴스도 사용하지 않아도 볼륨의 데이터는 남는다.

**연결 및 분리 가능.** EBS 볼륨은 하나의 인스턴스에서 분리하고 다른 인스턴스에 연결할 수 있다. 실패한 인스턴스에서 데이터를 마이그레이션하거나 복구해야 하는 경우, 볼륨을 분리하고 다른 곳에 재연결할 수 있다.

**단일 연결(대부분).** 기본적으로, EBS 볼륨은 정확히 하나의 EC2 인스턴스에 한 번에 연결된다. 단일 인스턴스가 여러 EBS 볼륨을 가질 수 있지만, 단일 EBS 볼륨은 동시에 여러 인스턴스에 마운트될 수 없다(하나의 예외: EBS Multi-Attach, 제한된 사용 사례와 중요한 제한이 있다).

비유: EBS는 노트북에 꽂는 외장 하드 드라이브다. 노트북(EC2 인스턴스)이 읽고 쓸 수 있다. 완료되면, 꽂은 것을 빼고 다른 노트북에 꽂을 수 있다.

**EBS 볼륨 유형**

모든 EBS 볼륨이 같은 것은 아니다. AWS는 서로 다른 성능과 비용 프로파일을 가진 여러 유형을 제공한다.

**gp3(범용 SSD)**: 대부분의 워크로드를 위한 기본 선택. 성능과 가격의 좋은 균형. 부트 볼륨, 소형 데이터베이스, 개발 환경에 적합.

**io2(프로비저닝된 IOPS SSD)**: I/O 집약적인 워크로드를 위한 고성능 옵션. 필요한 초당 I/O 작업 수(IOPS)를 지정하면 AWS가 그 성능을 보장한다. 대형 프로덕션 데이터베이스에 적합.

**st1(처리량 최적화 HDD)**: 대용량 순차 읽기와 쓰기에 최적화된 자기 스토리지. SSD보다 저렴하지만 랜덤 I/O는 더 느리다. 데이터 웨어하우징과 로그 처리에 좋다.

**sc1(콜드 HDD)**: 가장 저렴한 EBS 옵션. 비정기적으로 접근하는 데이터용. 시간에 민감한 것에는 적합하지 않다.

시험에서 모든 유형을 암기할 필요가 없다. IOPS 요구사항 → io2. 비용에 민감한 순차 워크로드 → st1. 일반 웹 애플리케이션 → gp3로 요구사항을 올바른 유형과 매치하는 능력을 테스트한다.

**EBS 스냅샷: 백업**

여기에 정기적으로 회사를 구하는 것이 있다.

**EBS 스냅샷**은 S3에 저장된 EBS 볼륨의 특정 시점 백업이다(EBS 인터페이스를 통해 접근하지만, S3를 통해 직접은 아니다). 스냅샷은 증분적이다: 첫 번째 스냅샷은 전체 볼륨을 캡처하고; 후속 스냅샷은 마지막 이후 변경된 것만 저장한다.

스냅샷에서 새 EBS 볼륨을 만들 수 있다 — 데이터베이스 손상, 나쁜 배포, 또는 우발적인 삭제 이전의 특정 시점으로 복원한다.

스냅샷을 자동화해야 한다. AWS는 이를 위해 **Amazon Data Lifecycle Manager**를 제공한다: 정책을 정의하고(6시간마다 스냅샷 찍기, 마지막 7일 유지), 자동으로 실행된다.

Priya는 데이터베이스가 프로덕션에 들어가기 전에 이것을 설정했다.

Leo는 그것에 대해 생각하지 않았다.

**EFS: 공유 파일 캐비닛**

EBS는 하나의 인스턴스에 연결된 디스크다. 여러 인스턴스가 동시에 같은 파일에 접근해야 한다면?

**Amazon EFS** — Elastic File System — 가 등장한다.

EFS는 관리형 네트워크 파일시스템이다. 여러 EC2 인스턴스가 동시에 같은 EFS 파일시스템을 마운트하고 공유 파일을 읽고 쓸 수 있다. 이것이 EBS가 제공하지 않는 핵심 기능이다.

이렇게 생각하라:

EBS는 하나의 노트북에 꽂힌 외장 하드 드라이브다. 그 노트북만 한 번에 사용할 수 있다.

EFS는 사무실 중앙의 파일 캐비닛이다. 팀원 누구나 걸어와서 서랍을 열고 파일을 읽고 뭔가를 돌려놓을 수 있다. 여러 사람이, 동시에, 같은 스토리지에 접근하는.

**EFS가 필요한 경우**:

- 여러 EC2 인스턴스가 파일을 공유해야 할 때 — 콘텐츠 관리 시스템, 공유 설정 파일, 공유 미디어 라이브러리
- 모든 인스턴스가 같은 데이터에 접근해야 하는 수평 확장된 애플리케이션이 있을 때
- 인스턴스 실패에서 살아남는 영구 파일시스템이 필요할 때

**EFS vs. S3:** EFS는 파일시스템이다(폴더, 파일, 권한, 잠금). S3는 객체 스토리지다(업로드, 다운로드, 파일시스템 시맨틱 없음). EFS는 S3보다 훨씬 비싸다. 전체적으로 저장하고 검색하는 파일에는 S3를 사용하라. 애플리케이션이 표준 파일시스템 작업을 통해 능동적으로 읽고 쓰는 파일에는 EFS를 사용하라.

**올바른 스토리지 선택**

이제 AWS에서 세 가지 유형의 스토리지를 봤다. 결정을 명확하게 만들어보자.

| 필요 | 스토리지 유형 |
|---|---|
| 데이터베이스에 영구적이고 빠른 디스크 필요 | EBS (gp3 또는 io2) |
| 여러 서버가 공유 파일 필요 | EFS |
| 파일, 백업, 이미지, 대용량 객체 | S3 |
| 임시 계산 스크래치 공간 | 인스턴스 스토어 |
| 최소 비용의 장기 아카이브 | S3 Glacier |

이 결정을 올바르게 하는 것이 중요하다. EFS가 필요한 곳에 S3를 사용하면 운영 복잡성이 추가된다. EFS가 필요한 곳에 EBS를 사용하면 확장할 때 실패가 발생한다. 영구성이 필요한 곳에 인스턴스 스토어를 사용하면 데이터를 잃는다.

Priya는 이 표를 출력하여 벽에 붙였다.

"스토리지 요구사항을 추가할 때마다," 그녀가 말했다. "여기서 시작해."

## 장점과 한계

**EBS 장점**:

- EC2를 위한 영구적이고 빠른 블록 스토리지
- 특정 시점 백업 및 복구를 위한 스냅샷
- 다양한 워크로드를 위한 여러 성능 계층
- 기본적으로 저장 시 암호화 지원

**EBS 한계**:

- 한 번에 하나의 인스턴스에만 연결(소수의 예외)
- EC2 인스턴스와 같은 AZ에 있음(다른 AZ로 복사하려면 스냅샷 필요)
- 사용한 것이 아니라 프로비저닝된 스토리지 비용 지불

**EFS 장점**:

- 멀티 인스턴스 공유 파일시스템 — 기본 NFS 프로토콜
- 자동으로 확장, 용량 프로비저닝 불필요
- 리전 내 AZ 전체에서 접근 가능

**EFS 한계**:

- GB당 S3보다 비쌈
- 랜덤 I/O의 경우 EBS보다 더 높은 지연 시간
- 모든 리전에서 사용 가능하지 않음

## 요약

- **인스턴스 스토어**는 호스트에 물리적으로 연결된 임시적이고 빠른 스토리지다.
  인스턴스가 중지되거나 종료되면 데이터가 사라진다. 스크래치 공간에만 사용.
- **EBS**(Elastic Block Store)는 단일 EC2 인스턴스를 위한 영구 블록 스토리지다.
  인스턴스 중지에서 살아남는다. 백업을 위해 스냅샷을 만들 수 있다. 올바른
  볼륨 유형을 선택하라(일반용 gp3, 높은 IOPS 요구사항의 경우 io2).
- **EFS**(Elastic File System)는 여러 인스턴스가 동시에 마운트할 수 있는 공유 네트워크 파일시스템이다. 여러 서버가 같은 파일에 접근해야 할 때 사용하라.
- 스토리지 유형을 요구사항에 매치하라: 데이터베이스 → EBS; 공유 파일 → EFS;
  객체/백업 → S3; 아카이브 → S3 Glacier.

## 시험 팁

*SAA-C03 도메인 3 — 태스크 3.1 (스토리지 솔루션)*

- **EBS 볼륨은 하나의 AZ에 있다.** 같은 AZ의 인스턴스에만 연결할 수 있다. 다른 AZ에서 EBS 볼륨을 사용하려면, 스냅샷을 만들고 대상 AZ에서 복원한다.
- **EBS 스냅샷은 증분적이고 S3에 저장된다.** 첫 번째 스냅샷은 전체적이고;
  후속 스냅샷은 변경 사항만 저장한다. 재해 복구를 위해 스냅샷을 다른 리전으로 복사할 수 있다.
- **EFS는 교차 AZ다.** 같은 리전 내 다른 AZ의 여러 인스턴스가 같은 EFS 파일시스템을 마운트할 수 있다. 이것이 EBS와의 핵심 차별화 요소다.
- **시험 시나리오가 "공유 콘텐츠가 있는 웹 애플리케이션" 또는 "같은 파일에 접근하는 여러 인스턴스"라고 말하면, EFS를 생각하라.** "데이터베이스 스토리지" 또는 "하나의 서버를 위한 영구 디스크"라고 하면, EBS를 생각하라.
- **인스턴스 스토어 데이터는 재부팅에서 살아남지만 중지나 종료에서는 아니다.** 질문이 "인스턴스가 중지된 후 데이터가 사라진다"고 설명하면 — 그것이 인스턴스 스토어가 작동하는 것이다.

## 연습 문제

**연습 1 — 회상**

자신의 말로: EBS와 EFS의 차이는 무엇인가? 각각을 언제 선택하겠는가?

*(힌트: 동시에 하나의 인스턴스 또는 여러 인스턴스가 스토리지에 접근해야 하는지 생각해보라.)*

**연습 2 — 시험 연습**

*시나리오*: 한 회사가 로드 밸런서 뒤에 네 개의 EC2 인스턴스에서 웹 애플리케이션을 실행한다. 사용자가 프로필 사진을 업로드할 수 있다. 네 개의 인스턴스 모두 업로드를 처리한 인스턴스에 관계없이 업로드 후 즉시 모든 사용자의 사진을 제공할 수 있어야 한다. 팀은 영구적이고 공유된 파일 스토리지가 필요하다.

다음 중 요구사항을 가장 잘 충족하는 스토리지 솔루션은?

A) 각 EC2 인스턴스에 EBS gp3 볼륨을 연결하고 cron 작업을 사용하여 파일을 동기화한다  
B) EC2 인스턴스의 인스턴스 스토어에 직접 사진을 저장한다  
C) 모든 네 개의 EC2 인스턴스에 동시에 마운트된 Amazon EFS를 사용한다  
D) S3에 사진을 저장하고 애플리케이션 코드에서 직접 접근한다

**힌트 1**: 요구사항은 "네 개의 인스턴스 모두 모든 사진을 제공해야 한다"이다. 어떤 옵션이 모든 인스턴스에서 파일을 즉시 볼 수 있게 만드는가?

**힌트 2**: 인스턴스 스토어는 일시적이다. EBS는 동시에 여러 인스턴스에 마운트될 수 없다. 그게 범위를 좁힌다.

**힌트 3**: C와 D 모두 이론적으로 작동할 수 있다. 애플리케이션이 파일시스템 작업 vs. HTTP 요청을 통해 사진에 접근해야 하는 경우 어느 것이 더 적합한가?

**답**: D

**설명**: S3에 사진을 저장하고 URL을 통해 제공하는 것이 아키텍처적으로
올바른 선택이다. 업로드된 사진은 모든 서버(그리고 모든 브라우저)에서 S3의 URL을 통해 즉시 접근 가능하다. S3는 정확히 이 사용 사례를 위해 설계되었다: 고가용성으로 사용자가 업로드한 파일을 대규모로 저장하고 제로 관리 오버헤드.

참고: C(EFS)도 기술적으로 작동하지만, S3는 웹 애플리케이션에서 사용자가 업로드한 바이너리 파일에 선호하는 패턴이다. 애플리케이션이 프록시 역할을 하지 않고 HTTP를 통해 직접 파일을 제공하기 때문에 더 저렴하고, 더 확장 가능하다.

**왜 A가 아닌가?** cron 작업을 통해 파일을 동기화하면 경쟁 조건과 일관성
문제가 생긴다. 업로드와 다음 동기화 사이에, 파일은 다른 인스턴스에서 누락된다.

**왜 B가 아닌가?** 인스턴스 스토어 데이터는 인스턴스가 중지되거나 종료될 때 사라진다.
사진이 사라진다.

**왜 C가 아닌가?** EFS는 애플리케이션이 파일을 제자리에서 수정하는 파일시스템 시맨틱이 필요한 경우(예: CMS) 올바른 답이다. 웹을 통해 제공되는 사용자가 업로드한 사진의 경우, S3는 더 단순하고, 저렴하며, 더 적합하다.

*SAA-C03 도메인 3 — 태스크 3.1*

**연습 3 — 아키텍처 과제** *(선택 사항)*

Nimbus는 새 기능을 추가하고 있다: 레스토랑 소유자가 PDF 메뉴를 업로드할 수 있고, 그런 다음 파싱하여 Nimbus 데이터베이스를 채운다. PDF 처리 작업은 EC2 인스턴스 플리트에서 실행되며 다음이 필요하다: (a) 업로드된 PDF 읽기, (b) 임시 처리 파일 쓰기, (c) 파싱된 출력 쓰기.

이 세 단계 각각에 어떤 스토리지 서비스를 사용하겠으며, 왜인가?

## 포스트 크레딧 장면

그 오후에, Nimbus는 스토리지를 적절히 분리했다. 데이터베이스는 자동화된 스냅샷이 있는 자체 EBS 볼륨을 얻었다. 메뉴 사진이 S3로 이동했다. EC2 인스턴스가 마침내 숨을 쉴 공간이 생겼다.

Leo가 부하 테스트를 실행했다. 사이트가 200명의 동시 사용자를 처리하며 문제가 없었다.

Tom이 청구서를 봤다. EBS 볼륨이 월 $8를 추가하고 있었다. 그가 적어 두었다.

"이 청구서에 계속 추가되고 있어," 그가 말했다. "언제 균형이 맞춰지지?"

"중단이 없을 때," Maya가 말했다. "모든 중단은 예방보다 더 많은 비용이 들어."

Tom은 납득하지 못한 것 같았다. 결국은 납득할 것이다.

3일 후, 플랫폼에 있는 레스토랑 소유자가 주문을 하려다가 오류가 났다. Maya가 로그를 확인했다.

데이터베이스는 거기 있었다. 애플리케이션은 실행 중이었다. 하지만 20명의 동시 사용자가 메뉴를 읽으려고 했고, 각자 데이터베이스에 접근하고 있었다.

"모든 페이지 로드가 데이터베이스 쿼리야," Leo가 말했다. "매번 하나씩."

Priya가 이미 무언가를 검색하고 있었다.

다음 챕터에서: 서버가 처리할 수 있는 것보다 더 많은 고객이 도착할 때 무슨 일이 일어나는가.
