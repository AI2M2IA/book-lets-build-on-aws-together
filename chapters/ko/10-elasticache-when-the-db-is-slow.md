# 10장: 데이터베이스가 너무 느릴 때

페이지 로드 메트릭이 화면에 열려 있었다. Leo는 아무 말도 하지 않고 20분 동안 그것들을 보고 있었다.

페이지 로드당 47개의 DynamoDB 요청. 데이터를 검색하는 데만 188밀리초 — 브라우저가 픽셀 하나를 렌더링하기 전에.

그는 계산을 했었다. 금요일 저녁 동시 사용자 만 명, 각각 약 1분에 한 번씩 탐색 페이지를 로드: 분당 사십칠만 번의 DynamoDB 읽기. 비용이 실제였다. 하지만 지연 시간이 실제 문제였다. Nimbus 탐색 페이지를 여는 사용자는 무언가 나타나기 전에 거의 200밀리초를 기다렸다 — 그리고 그것은 빠른 연결에서였다.

---

*그 전 주, DynamoDB 스키마 재설계가 효과를 봤었다. 메뉴 테이블은 이제 유연했다 — 어느 레스토랑이든 어느 수정자든, 어느 콤보 구조든, 어느 계절 변형이든 추가할 수 있었다. 개별 조회의 성능은 훌륭했다. 하지만 페이지당 마흔일곱 번 곱해진 훌륭한 개별 조회는, 여전히 느린 페이지로 합산됐다. DynamoDB 문제는 해결됐다. 새로운 문제가 그 자리를 차지했다.*

---

"데이터베이스가 요청당 4밀리초에 응답하고 있어," Leo가 말했다. "그게 실제로 빠른 거야. DynamoDB가 할 일을 하고 있어."

"그럼 페이지가 왜 느려?" Maya가 물었다.

"페이지 로드당 47번 호출하고 있기 때문이야," Priya가 말했다. "문제는 데이터베이스가 아니야. 문제는 우리가 그것과 너무 많이 이야기하고 있다는 거야."

Tom이 앞으로 몸을 기울였다. 문제가 곧 비용 대화가 되려는 표정을 지으며. "그러면 해결책은 덜 이야기하는 것?"

"덜 이야기하고. 더 기억하고."

---

**잘못된 첫 번째 시도**

Leo의 첫 본능은 사용자별 데이터를 캐시하는 것이었다. 각 사용자는 세션을 가졌고, 세션이 그들의 프로필을 로드했다: 저장된 주소, 결제 방법, 주문 내역 요약. 어쩌면 그것을 캐시하면 속도가 빨라질 것이다.

그는 그것을 구현했다. Redis 키 형식: `user:{userId}:profile`. TTL: 10분.

그는 부하 테스트를 실행했다. 페이지 로드가 6밀리초 떨어졌다.

"별로 많지 않네," Tom이 관찰했다.

"응," Leo가 말했다.

"왜 안 돼?"

Leo가 잠시 그래프를 바라봤다. "사용자 프로필은 하나의 요청뿐이니까. 페이지당 여전히 마흔여섯 번의 DynamoDB 호출이 있어. 그리고 그것들은 메뉴 호출이야 — 탐색 페이지의 레스토랑당 하나씩. 나는 잘못된 것을 캐시했어."

이것은 캐싱에서 흔한 실수다: 병목이 아닌 것을 최적화하기. 사용자 프로필은 2밀리초에 로드됐다. 그렇게 빠른 것을 캐시하는 것은 거의 아무것도 절약하지 못했다. 메뉴 데이터 — 마흔일곱 번 가져오고, 각각 4밀리초가 걸리는 — 가 실제 문제였다.

"사용자별이 아니라 메뉴별로 캐시해야 해," Priya가 말했다. "레스토랑 047의 메뉴는 그것을 탐색하는 모든 사용자에게 같아. 그게 캐시할 가치가 있는 데이터야 — 수천 개의 요청에 걸쳐 동일하니까."

사용자별 캐시는 사용자가 비싼 개인화된 상태를 가질 때 가치가 있다. 엔티티별 캐시(메뉴, 제품 카탈로그, 설정)는 같은 데이터가 수천 명의 사용자에게 제공될 때 가치가 있다. 코드를 작성하기 전에 어떤 문제를 가졌는지 알라.

Leo는 캐시 키를 재설계했다: `menu:{restaurantId}`. 레스토랑당 하나의 캐시 엔트리, 그 레스토랑을 탐색하는 모든 사용자가 공유한다.

그는 부하 테스트를 다시 실행했다. 페이지 로드가 188밀리초에서 12밀리초로 떨어졌다. 그것이 그들이 찾고 있던 개선이었다.

---

**레스토랑 비유**

레스토랑의 주방을 상상해보라. 웨이터가 오늘의 특선 메뉴를 알아야 할 때마다, 뒤로 걸어가서, 주방장에게 묻고, 테이블로 돌아온다.

웨이터가 두 명이고 테이블이 세 개라면 잘 작동한다.

이제 웨이터가 이백 명이고 테이블이 천 개라고 상상해보라. 그들 모두가 같은 질문을 위해 뒤로 걸어간다. 주방이 병목이 된다. 주방장이 매시간 같은 질문에 사백 번 답하고 있다.

명백한 해결책: 특선 메뉴를 레스토랑 앞쪽 보드에 적어놓는다. 모든 웨이터가 보드에서 읽는다. 주방이 휴식을 취한다. 특선이 바뀌면 보드가 업데이트된다.

그 보드가 캐시다.

캐시는 최근에 검색된 데이터의 빠르고 로컬한 저장소다. 느린 소스에서 반복적으로 같은 것을 가져오는 대신, 한 번 가져와서 가까이 두는 것이다.

엔지니어가 유용하다고 느끼는 또 다른 비유가 있다: 도서관 예약 선반. 인기 있는 책이 반납되면, 사서는 그것이 곧 다시 요청될 것을 알고, 그래서 서가에 꽂는 대신 안내 데스크 근처의 예약 선반에 둔다. 다음 이용자는 도서관 전체를 걸을 필요가 없다 — 데스크에서 바로 그것을 찾는다. 예약 선반은 공간이 제한되어 있다. 가득 차면, 더 오래된 책이 새것을 위한 공간을 만들기 위해 서가로 다시 옮겨진다. 캐시는 동일하게 작동한다: 자주 접근되는 데이터는 앞쪽에 머물고, 드물게 접근되는 데이터는 공간을 만들기 위해 제거된다.

**왜 그냥 메모리를 사용하지 않는가?**

"애플리케이션의 메모리에 메뉴를 저장할 수 없어요?" Leo가 물었다.

유효한 질문.

할 수 있다. 단일 서버 애플리케이션의 경우, 인메모리 캐싱이 잘 작동한다. 하지만 Nimbus는 로드 밸런서 뒤에서, 여러 EC2 인스턴스에 걸쳐 실행된다. 하나의 인스턴스가 메모리에 메뉴를 캐시하면, 다른 인스턴스에는 그 데이터가 없다. 각각이 별도의 캐시를 유지한다. 메뉴가 업데이트될 때, 그것들 모두를 무효화해야 한다.

이것이 *캐시 일관성 문제*다 — 여러 캐시를 일관되게 유지하는 것.

ElastiCache는 모든 인스턴스가 공유하는 *중앙 집중식* 캐시를 제공하여 이것을 해결한다. 모든 서버가 자체 메모리를 갖는 것 대신, 모든 서버가 같은 캐시에서 읽고 쓴다. 하나의 업데이트가 모두에게 전파된다.

**ElastiCache 소개**

"잠깐 — 그런데 *왜* 그렇게 하는 거죠?" Maya가 물었다. "왜 완전히 새로운 서비스죠? 왜 그냥 데이터베이스 용량을 추가하지 않죠?"

좋은 질문. 답은 데이터베이스 용량을 추가하는 것 — 더 큰 인스턴스, 더 많은 읽기 복제본 — 이 근본적인 문제를 고치지 않는다는 것이다. 그 마흔일곱 개의 페이지 로드 요청 각각이 더 빠른 데이터베이스에서도 여전히 시간과 돈을 비용으로 한다. 캐시는 데이터베이스를 더 빠르게 만들지 않는다; 그것은 데이터베이스가 같은 질문을 훨씬 덜 자주 받게 된다는 것을 의미한다. 반복적으로 읽히고 드물게 바뀌는 데이터 — 레스토랑의 메뉴 같은 — 의 경우, 캐시는 데이터베이스가 그 질문에 페이지 로드당 마흔일곱 번 대신 5분마다 한 번 답할 수도 있다는 것을 의미한다.

Amazon ElastiCache는 관리형 캐싱 서비스다. 서버를 관리할 필요 없이 인기 있는 캐싱 엔진 — Redis와 Memcached — 을 실행한다.

**Redis**는 둘 중 더 강력하다. 복잡한 데이터 구조(문자열, 리스트, 셋, 해시, 정렬된 셋), 영속성(데이터가 재시작에서 살아남는다), 복제, pub/sub 메시징을 지원한다. Redis는 캐싱보다 더 많은 것을 할 수 있다 — 가벼운 데이터 저장소로 기능할 수 있다.

**Memcached**는 더 단순하다. 순수 키-값 캐싱, 수평 확장 가능, 영속성 없음. 더 단순한 사용 사례에는 더 빠르지만 기능이 적다.

Nimbus의 경우: Redis. 그들은 메뉴 데이터(구조화됨), 세션 토큰(키-값)을 캐시해야 했고, 나중에 "트렌딩 레스토랑" 랭킹을 위해 정렬된 셋이 필요할 것이다.

**실제로 캐싱이 작동하는 방법**

기본 캐싱 패턴을 **캐시-어사이드**(게으른 로딩이라고도 함)라고 한다:

1. 애플리케이션이 데이터를 필요로 함
2. 먼저 캐시를 확인
3. 찾으면 (*캐시 히트*): 즉시 데이터를 반환
4. 찾지 못하면 (*캐시 미스*): 데이터베이스로 가서, 데이터를 가져오고, 캐시에 저장하고, 반환

의사 코드로:

```
menuData = cache.get("menu:restaurant-047")
if menuData is null:
    menuData = dynamodb.query(TableName="menu", KeyConditionExpression="restaurantId = '047'")
    cache.set("menu:restaurant-047", menuData, ttl=300)  # 5분 동안 캐시
return menuData
```

첫 번째 요청은 항상 데이터베이스에 접근한다. 모든 후속 요청은 캐시에 접근한다. 캐시를 사용하면, Nimbus의 페이지 로드당 마흔일곱 번의 DynamoDB 읽기가 하나 또는 두 번의 캐시 조회가 된다. 빠르고, 저렴하고, 확장 가능하다.

**TTL: 얼마나 오래 기억하는가?**

모든 캐시 엔트리에는 **TTL(Time-To-Live)**이 있다: 엔트리가 만료되고 다음 요청이 신선한 데이터를 위해 데이터베이스로 돌아가기 전까지의 기간.

이것이 캐싱의 핵심 긴장감이다: 신선도 vs. 성능.

- **짧은 TTL(초)**: 매우 신선한 데이터, 하지만 많은 캐시 미스. 캐시가 거의 도움이 안 된다.
- **긴 TTL(시간 또는 일)**: 매우 빠르지만, 데이터가 오래될 수 있다. 고객이 어제 메뉴를 본다.

메뉴 데이터의 경우, 5분이 합리적이다. 메뉴는 매초 바뀌지 않는다. 레스토랑이 메뉴를 업데이트하면, 고객이 최대 5분 동안 이전 버전을 볼 수 있다 — 허용 가능하다.

세션 토큰(이 사용자가 로그인되어 있는가?)의 경우, 더 짧은 TTL이 의미가 있거나, 세션이 변경될 때 즉시 캐시를 업데이트한다.

재무 데이터(주문 합계, 결제 레코드)의 경우, 캐시하지 않는다 — 또는 캐시한다면, 쓰기 시 즉시 무효화한다.

여러분은 궁금할 것이다: 완전히 새로운 캐싱 레이어를 도입하는 대신 왜 그냥 데이터베이스 용량을 추가하지 않는가? 더 많은 복제본, 더 큰 인스턴스 — 왜 그게 아닌가? 답은 추가 데이터베이스 용량이 동시 요청을 처리하는 능력을 배가시키지만, 요청 수를 줄이지는 않는다는 것이다. 만 명의 사용자가 각각 페이지 로드당 마흔일곱 번의 읽기를 트리거한다면, 두 번째 읽기 복제본을 추가하는 것은 각 복제본이 사만칠천 개 대신 이만삼천 개의 요청을 처리한다는 것을 의미할 뿐이다 — 총 작업은 줄어들지 않는다. 캐시는 중복 작업을 완전히 제거한다: 그 만 명의 사용자가 같은 캐시된 결과를 공유한다.

"컴퓨터 과학에는 두 가지 어려운 문제만 있어," Leo가 전에 말한 적 있는 사람의 연습된 전달로 인용했다. "캐시 무효화와 이름 짓기."

"왜 캐시 무효화가 어려워요?" Maya가 물었다.

"데이터가 *실제로* 언제 변경되는가? 레스토랑 파트너가 메뉴를 업데이트했기 때문에 변경됐나? 아니면 크론 작업이 실행됐기 때문에? 아니면 관리자가 수동으로 편집했기 때문에? 데이터를 변경할 수 있는 모든 곳이 캐시에게 알려야 한다는 것을 알아야 해."

이것이 시니어 엔지니어가 "Redis를 추가하자" 대신 "쓰기 경로는 무엇인가?"로 캐싱 대화를 시작하는 이유다.

---

**캐시 무효화 이야기**

그들은 레스토랑 파트너가 처음 불평했을 때 캐시 무효화가 얼마나 어려운지 알게 됐다.

레스토랑 112 — 이스트사이드의 콜롬비아 음식점 — 가 목요일 오후에 가격을 업데이트했었다. 그들은 아레파를 8달러에서 9달러로 올렸다. 그들은 20분 후 Nimbus 지원팀에 전화했다.

"우리 메뉴가 여전히 이전 가격을 보여줘요," 주인이 말했다. "고객들이 8달러에 주문하고 있어요. 이제 그 가격을 지켜야 해요."

Priya가 버그를 추적하는 동안 Tom이 손실을 계산했다. 그 20분 동안 들어온 모든 주문이 8달러를 청구했다. 레스토랑은 9달러를 원했었다. Nimbus가 차액을 흡수해야 할 것이다.

5분 TTL은 오래전에 만료됐어야 했다. 20분이 지났다. Priya가 코드를 꺼냈다.

캐시 키는 `menu:restaurant-112`였다. 그것은 300초 TTL로 설정됐었다. 그녀는 그것이 마지막으로 쓰여진 때를 확인했다.

"오후 2시 3분에 설정됐어," 그녀가 말했다. "22분 전."

"하지만 TTL은 5분이잖아," Leo가 말했다.

"TTL은 처음 캐시된 때부터 5분이야. 하지만 캐시에 접근한 모든 요청이 TTL을 새로 고치고 있었어. 캐시 엔트리가 들어오는 요청에 의해 몇 초마다 건드려지고 있었고, TTL이 재설정되고 있었어."

"그래서 절대 만료되지 않았네."

"이 구현에서는 아니야. 우리는 모든 캐시 읽기에서 TTL을 설정했어. 슬라이딩 윈도우. 누군가 그것에 접근하는 한 엔트리가 살아 있었어."

수정: 쓰기 시에만 설정되고, 읽기 시 절대 연장되지 않는 고정 TTL을 사용한다. 엔트리는 얼마나 많이 읽히든 상관없이, 저장된 후 정확히 5분에 만료된다. 레스토랑이 메뉴를 업데이트하면, 이전 엔트리가 5분 내에 만료되고 다음 요청이 신선한 데이터를 가져왔다.

"그리고 레스토랑이 가격을 업데이트하고 즉시 반영되어야 하는 경우는?" Tom이 물었다.

"능동적 무효화," Priya가 말했다. "레스토랑 파트너 포털이 업데이트를 제출하면, API가 반환하기 전에 `cache.delete('menu:restaurant-112')`를 호출해. 다음 요청이 즉시 신선한 데이터를 가져와."

"하지만 그건 포털이 캐시에 대해 알아야 한다는 거잖아."

"데이터베이스로 가는 모든 쓰기 경로가 캐시에 대해 알아야 해. 그게 Leo가 아까 말한 거야. 이제 우리가 그것을 겪었지."

"제가 이미 배포했어요 — 아." Leo는 포털에 무효화를 구현했지만 관리자 편집 인터페이스를 잊었다. 2주 후, 관리자가 내부 대시보드를 통해 메뉴를 업데이트했고, 이전 가격이 5분 동안 캐시에 지속됐다. 같은 사고의 더 작은 버전.

그들은 DynamoDB Streams 핸들러 — 이전 챕터에서 — 를 추가했는데, 그것은 어떤 시스템이 쓰기를 트리거했든 상관없이 메뉴 아이템이 변경될 때마다 자동으로 캐시를 무효화했다. 하나의 핸들러, 모든 쓰기 경로 커버.

**캐시 제거: 보드가 가득 찰 때**

특선 메뉴 보드는 공간이 제한되어 있다. 가득 차면, 새 것을 위한 공간을 만들기 위해 무언가를 지워야 한다.

Redis(그리고 일반적으로 캐시)는 메모리가 가득 찰 때 무엇을 제거할지를 결정하는 *제거 정책*을 갖고 있다:

- **LRU (가장 최근에 사용되지 않은)**: 가장 오랜 시간 동안 접근하지 않은 아이템을 제거한다.
- **LFU (가장 적게 사용된)**: 가장 적게 접근하는 아이템을 제거한다.
- **allkeys-random**: 무작위 제거. 간단하지만 최적이 아니다.
- **noeviction**: 메모리가 가득 찰 때 오류를 반환한다(애플리케이션이 이것을 처리해야 한다).

대부분의 웹 애플리케이션에는: LRU. 최근에 보지 않은 것은 아마도 덜 필요하다.

**캐시 스탬피드 문제**

"전체 캐시가 한 번에 비어버리면 무슨 일이 일어나는지 생각해봤어?" Priya가 물었다.

"그게 언제 일어나는데?" Leo가 말했다.

"새 ElastiCache 클러스터를 배포할 때. 큰 배치의 엔트리에 대한 TTL이 동시에 만료될 때. 버그 수정 후 새로 고침을 강제하기 위해 캐시를 플러시할 때."

Leo가 그것을 곰곰이 생각했다. "캐시가 비어 있으면, 모든 요청이 데이터베이스로 가. 한 번에 전부. 몇 초 동안, 데이터베이스가 모든 동시 사용자의 전체 부하를 처리해."

"그 앞에 캐시 없이."

"그건 아프겠는데." Leo가 데이터베이스 용량 설정을 봤다. "확실히 스로틀될 거야."

이것을 **캐시 스탬피드**(천둥 무리라고도 함)라고 한다. 많은 캐시 엔트리가 같은 시간에 만료될 때 — 종종 배포나 콜드 스타트 중에 그것들이 모두 같은 시간에 생성됐기 때문에 — 발생하며, 갑작스러운 캐시 미스의 물결이 모두 동시에 데이터베이스에 부딪친다.

완화 전략:

**TTL의 지터**: 모든 메뉴 엔트리를 정확히 300초로 설정하는 대신, 무작위 변동을 추가한다: 270초에서 330초. 엔트리가 약간 다른 시간에 만료되어, 캐시 미스 물결을 동시에 부딪치는 대신 1분에 걸쳐 분산시킨다.

**확률적 조기 만료**: 엔트리가 만료되기 전에, 작은 비율의 요청이 능동적으로 그것을 새로 고친다. 이것은 엔트리가 오래되기 전에 신선하게 유지하여, 만료가 결코 미스가 되지 않도록 방지한다.

**요청 병합(뮤텍스/락)**: 캐시 미스가 발생하면, 데이터베이스에 부딪치기 전에 락을 획득한다. 같은 키에 대한 다른 동시 요청은 첫 번째 요청이 완료되고 캐시를 다시 채울 때까지 기다린 다음, 캐시에서 읽는다. 높은 동시성에서도, 캐시 미스당 단 하나의 데이터베이스 요청만 이루어진다.

Nimbus의 경우, 그들은 TTL 지터를 구현했다. 간단하고, 효과적이고, 추가 복잡성 없음.

```python
import random
TTL_BASE = 300
TTL_JITTER = 30
ttl = TTL_BASE + random.randint(-TTL_JITTER, TTL_JITTER)
cache.set(key, value, ttl=ttl)
```

"코드 두 줄," Leo가 말했다. "배포 중 잠재적 데이터베이스 중단을 방지하기 위해."

"대부분의 안정성 개선이 그래," Priya가 말했다. "구현하기는 저렴하고, 필요했다는 것을 배우기는 비싸지."

**Redis 데이터 구조: 키-값 이상**

Nimbus가 "트렌딩 레스토랑" 기능을 추가했을 때, Leo는 처음에 랭킹을 평범한 JSON 리스트로 저장했다: `trending:global → ["NIMBUS-047", "NIMBUS-112", ...]`.

작동했지만, 그것을 업데이트하는 것은 어색했다. 새 레스토랑을 추가하거나 점수를 업데이트하려면, 전체 리스트를 읽고, 애플리케이션 코드에서 수정하고, 전체를 다시 써야 했다. 분석 파이프라인의 동시 쓰기에서, 경합 조건이 점수를 덮어쓰게 만들었다.

Priya가 그를 Redis 정렬된 셋으로 안내했다.

Redis의 **정렬된 셋**은 연관된 숫자 점수와 함께 멤버를 저장한다. 멤버는 점수에 따라 자동으로 정렬된다. 연산은 원자적이다 — 동시 업데이트로부터의 경합 조건이 없다.

```
# 레스토랑의 점수 추가/업데이트
ZADD trending:global 9420 "NIMBUS-047"
ZADD trending:global 8831 "NIMBUS-112"

# 점수 기준 상위 10개 레스토랑 가져오기(높은 순)
ZREVRANGE trending:global 0 9 WITHSCORES

# 레스토랑의 점수를 원자적으로 증가
ZINCRBY trending:global 50 "NIMBUS-047"
```

분석 Lambda는 주문이 들어올 때마다 `ZINCRBY`를 호출하여 레스토랑의 점수를 증가시켰다. 홈페이지는 상위 열 개를 가져오기 위해 `ZREVRANGE`를 호출했다. 락 없음, 경합 조건 없음, 읽기-수정-쓰기 사이클 없음.

Redis는 단순한 키-값 외에 여러 다른 데이터 구조를 지원한다:

**리스트**: 순서가 있는 시퀀스. 앞이나 뒤로 푸시. 큐, 최근 활동 피드, 로그 스트림에 사용.

**셋**: 중복이 없는 순서 없는 컬렉션. 합집합, 교집합, 차집합 연산. "어떤 사용자가 이 알림을 봤는가?" 또는 "어떤 레스토랑이 이 카테고리에 있는가?"에 사용.

**해시**: 키 안의 명명된 필드. 전체 객체를 다시 쓰지 않고 개별 필드를 업데이트하고 싶은 구조화된 객체에 사용.

**HyperLogLog**: 확률적 카디널리티 추정. 모든 방문자 ID를 저장하지 않고 페이지의 고유 방문자를 센다. 작고 빠르다.

**Pub/Sub**: 채널에 메시지를 게시; 구독자가 실시간으로 그것들을 받는다. 서비스 간 가벼운 실시간 알림에 사용.

"Redis는 단지 캐시가 아니야," Leo가 말했다. "데이터 구조 서버야."

"그게 그것의 공식 설명이야," Priya가 말했다.

"나는 그냥 멋진 사전인 줄 알았어."

"그렇게 시작했지."

**쓰기-스루: 다른 캐싱 패턴**

캐시-어사이드(게으른 로딩)가 가장 흔한 패턴이다. 하지만 알아둘 가치가 있는 두 번째 것이 있다: **쓰기-스루**.

쓰기-스루 캐싱에서는, 애플리케이션이 데이터베이스에 쓸 때마다, 즉시 캐시에도 쓴다.

```python
def update_menu(restaurant_id, menu_data):
    dynamodb.put_item(TableName="menu", Item=menu_data)
    cache.set(f"menu:{restaurant_id}", menu_data, ttl=300)
```

장점: 캐시가 항상 최신이다. 쓰기와 TTL 만료 사이에 오래된 데이터가 없다.

단점: 모든 쓰기가 두 곳으로 간다. 그리고 절대 읽히지 않을 수도 있는 데이터로 캐시를 채운다. 열 개의 레스토랑이 메뉴를 업데이트하지만 그중 두 개만 다음 5분 동안 상당한 트래픽을 받는다면, 만료되기 전에 사용되지 않을 여덟 개의 캐시에 대해 쓰기-스루 작업을 한 것이다.

"잠깐 — 그런데 *왜* 그렇게 하는 거죠?" Maya가 물었다. "모든 업데이트에서 캐시에 쓴다면, 이전보다 쓰기당 더 많은 작업을 하는 거잖아요. 그게 어떻게 더 나은 거죠?"

"항상 더 나은 건 아니야," Priya가 말했다. "쓰기-스루는 쓰기 후 오래된 데이터의 어떤 윈도우도 용납할 수 없을 때 의미가 있어. 캐시-어사이드는 모든 쓰기에서 추가 작업을 하지 않는 대가로 최대 한 번의 TTL만큼의 오래됨을 받아들여."

Nimbus의 경우: 캐시-어사이드가 올바른 선택이었다. 메뉴는 쓰여지는 것보다 훨씬 자주 읽혔다. 5분 오래됨 윈도우는 허용 가능했다. 모든 가격 업데이트가 즉시 반영되어야 하는 금융 거래 시스템의 경우, 쓰기-스루가 더 적절할 것이다.

결정은 두 가지 질문으로 귀결된다: 쓰기 대 읽기 비율은 무엇인가, 그리고 쓰기 후 오래된 읽기에 얼마나 관대한가?

**ElastiCache for Redis: 관리되는 것**

RDS처럼, ElastiCache는 오픈 소스 도구를 가져다가 운영 작업을 처리한다:

- **자동화된 백업**: 일정에 따라 Redis 스냅샷
- **멀티 AZ 복제**: 다른 AZ에 기본 노드 + 읽기 복제본
- **자동 장애 조치**: 기본 Redis 노드가 실패하면, 복제본이 자동으로 승격
- **클러스터 모드**: 매우 큰 캐시를 위한 여러 노드에 걸친 수평 샤딩
- **암호화**: 컴플라이언스를 위한 전송 중 및 저장 중 암호화
- **VPC 통합**: 캐시가 공개적으로 접근 가능하지 않은 프라이빗 네트워크에서 실행

"그게 한 달에 얼마나 들어?" Tom이 물었다.

"우리가 대체하는 DynamoDB 읽기보다 적어," Leo가 말했다. "한 달에 약 200달러."

Leo가 가격 페이지를 열었다. 그는 이미 계산을 했었지만, Tom에게 그것을 설명했다.

`cache.t3.micro` — 가장 작은 노드 — 는 한 달에 약 12달러였다. 0.5GB의 메모리를 가졌다. 몇백 개의 캐시 키를 가진 작은 애플리케이션에 충분했다.

`cache.r6g.large` — Nimbus의 트래픽에 적합한 티어 — 는 13GB의 메모리를 가졌고 한 달에 약 140달러였다. 비교하자면, Nimbus는 캐싱 전에 DynamoDB 읽기에 한 달에 대략 400달러를 쓰고 있었다. 캐싱 후, 그 읽기는 약 89퍼센트 떨어졌다. 계산은 DynamoDB 읽기에서 한 달에 대략 356달러 절약, 빼기 ElastiCache에 쓴 140달러 — 한 달에 약 216달러의 순 절약으로 나왔다.

Tom의 표정이 회의적에서 만족스러운 것으로 바뀌었다. "확장하기 전에 숫자를 제대로 돌려봐, 하지만 그게 맞아." 그는 그것을 적었다.

"그리고 누군가 침입하려 하면?" Priya가 말했다. "캐시에 세션 토큰이 있을 수 있어. 사용자 데이터도. Redis 인스턴스에 인증 토큰이 필요하고 공개 접근이 없어야 해."

"프라이빗 서브넷에 있을 거야," Leo가 말했다.

"좋아. 하지만 '괜찮을 거야'는 보안 자세가 아니야," 그녀가 말했다. "인증 토큰. 전송 중 암호화. VPC 전용."

Leo가 고개를 끄덕였다. 그녀가 옳았다.

**캐시 모니터링**

"캐시가 올바르게 작동하지 않을 때 무슨 일이 일어나는지 생각해봤어?" Redis 배포 일주일 후 Priya가 물었다. "완전히 실패하는 것뿐만 아니라 — 작동하지만, 형편없이. 높은 미스율. 높은 제거율. 지연 시간이 슬금슬금 올라가는 것."

"페이지 로드 시간이 증가하면 알아차릴 거야," Leo가 말했다.

"그 시점에는 데이터베이스가 이미 고생하고 있어," 그녀가 말했다.

ElastiCache는 CloudWatch를 통해 메트릭을 노출한다. 가장 중요한 것들:

**CacheHitRate**: 결과를 반환한 캐시 읽기의 비율. 성숙한 캐시의 경우 이상적으로 80% 이상. 떨어지는 히트율은 가장 많이 접근되는 데이터가 캐시에 없다는 신호다 — TTL이 너무 짧거나, 캐시가 너무 작거나, 접근 패턴이 바뀌었다.

**CacheMisses**: 캐시 미스의 절대 수. 여기서 갑작스러운 급증은 캐시가 도움이 되지 않고 데이터베이스가 전체 부하를 받고 있다는 것을 의미한다.

**Evictions**: 새것을 위한 공간을 만들기 위해 제거된 캐시 아이템의 수. 높은 제거율은 캐시가 작업 세트에 비해 너무 작다는 것을 의미한다. 더 많은 메모리나 더 선택적인 캐싱 전략이 필요하다.

**CurrConnections**: Redis에 대한 현재 클라이언트 연결. 너무 많은 연결은 Redis의 연결 한계를 소진할 수 있다. 애플리케이션은 모든 요청에서 새 연결을 여는 것을 피하기 위해 연결 풀링을 사용해야 한다.

**ReplicationLag**: 읽기 복제본이 기본에서 얼마나 뒤처져 있는지. 이것이 커지면, 복제본 읽기가 오래된 데이터를 반환할 수 있다.

Leo는 두 개의 CloudWatch 알람을 설정했다. 첫째: 캐시 히트율이 15분 연속 70% 아래로 떨어지면 알림 — 그것은 데이터베이스가 느끼기 전에 조사할 가치가 있는 문제를 신호한다. 둘째: 제거율이 분당 100회 제거를 초과하면 알림 — 그것은 캐시가 작게 설계됐다는 것을 신호한다.

"알람 두 개," Priya가 설정을 검토하며 말했다. "좋은 시작이야."

"대시보드도 추가했어," Leo가 말했다. "히트율, 미스율, 제거, 지연 시간. 전부 한 곳에서 보여."

"페이지가 느려지기를 기다리는 것보다 낫네."

"상당히 낫지," Leo가 동의했다.

**ElastiCache vs DAX: DynamoDB에 어떤 캐시?**

"우리가 DynamoDB 데이터를 캐시한다면," Maya가 물었다. "왜 ElastiCache 대신 DAX를 사용하지 않죠? 문서에서 봤어요."

좋은 질문.

**DAX (DynamoDB Accelerator)**는 DynamoDB를 위한 목적 구축 인메모리 캐시다. 클라이언트 수준에서 DynamoDB API 호출을 가로챈다 — 애플리케이션 코드가 같은 DynamoDB SDK를 사용하여 DAX와 이야기한다. 캐시 미스는 DynamoDB에서 자동으로 가져온다. 캐시 히트는 마이크로초에 반환된다. 무효화는 데이터가 변경될 때 자동으로 처리된다.

**ElastiCache**는 범용 캐시다. 캐시 키, TTL 로직, 무효화 — 그 전부를 관리한다. 더 많은 제어, 더 많은 책임.

각각을 언제 사용하는가:

| 시나리오 | 권장 |
|---|---|
| DynamoDB 읽기를 캐시하고 애플리케이션 변경을 원하지 않음 | DAX |
| DynamoDB 읽기에 마이크로초 지연 시간이 필요함 | DAX |
| 여러 소스에서 캐시함(DynamoDB + RDS + 외부 API) | ElastiCache |
| Redis 데이터 구조가 필요함(정렬된 셋, pub/sub, HyperLogLog) | ElastiCache |
| 세밀한 TTL 제어와 사용자 정의 무효화 로직이 필요함 | ElastiCache |
| 세션 저장소, 속도 제한, 또는 분산 락이 필요함 | ElastiCache |

Nimbus의 경우: 그들은 여러 소스에서 데이터를 캐시하고 있었기 때문에 ElastiCache를 선택했다 — 메뉴에는 DynamoDB, 주문 내역 요약에는 RDS, 레스토랑 평점에는 외부 API. DAX는 DynamoDB에서만 작동한다. 그리고 그들은 트렌딩 랭킹을 위해 Redis 정렬된 셋이 필요했다.

"순전히 DynamoDB 캐싱 문제였다면," Priya가 말했다. "DAX가 더 간단한 답이었을 거야. 하나의 서비스, 자동 무효화, 같은 API. 하지만 우리는 하나 이상의 데이터 소스를 가졌어."

"그러니까 DynamoDB만 쓸 때는 DAX가 더 간단하고," Maya가 요약했다. "전체 도구 상자가 필요할 때는 ElastiCache네요."

"그게 트레이드오프야."

### 캐시 데이터를 잃을 수 없을 때: Amazon MemoryDB

"왜 누군가 Redis를 기본 데이터베이스로 사용하죠?" Maya가 물었다. "그건 캐시 아닌가요?"

그게 정확히 올바른 질문이다.

ElastiCache for Redis는 캐시다 — 빠르고, 인메모리이며, 설계상 진실의 원천이 아니다. ElastiCache 노드가 실패하면, 재시작 시 캐시가 비어 있다. 애플리케이션이 데이터베이스에서 그것을 다시 워밍한다. 캐시에는 괜찮다.

하지만 일부 사용 사례는 Redis를 캐시가 아니라 기본 데이터 저장소로 취급한다 — 재시작에서 살아남아야 하는 세션 상태, 잃을 수 없는 실시간 리더보드, AZ 실패에 걸쳐 지속되어야 하는 장바구니. 이런 사용 사례에서는, ElastiCache의 최종 내구성이 위험이다.

**Amazon MemoryDB for Redis**는 완전 관리형, Redis 호환, 내구성 있는 인메모리 데이터베이스다. ElastiCache와 달리, MemoryDB는 여러 AZ에 걸쳐 저장된 분산 트랜잭션 로그를 사용하여 모든 쓰기를 승인되기 전에 내구성 있게 만든다. 데이터는 노드 실패에서 살아남는다 — 더 느린 데이터베이스에서 재생하기 때문이 아니라, 결코 한 곳에만 있지 않았기 때문에.

핵심 구분:

| | ElastiCache for Redis | MemoryDB for Redis |
|---|---|---|
| 역할 | 캐시 레이어 | 기본 데이터베이스 |
| 내구성 | 실패 시 보장되지 않음 | 멀티 AZ 트랜잭션 로그 |
| 지연 시간 | 마이크로초 읽기 및 쓰기 | 마이크로초 읽기, 한 자리 수 밀리초 쓰기 |

둘 다 같은 Redis 명령과 데이터 구조를 지원한다. API는 같다. 내구성 보장은 같지 않다.

Nimbus의 경우: 팀은 실시간 레스토랑별 주문 수를 Redis 정렬된 셋으로 저장하고 싶어 한다 — 그리고 그것은 데이터베이스에서 다시 시드하지 않고 AZ 실패에서 살아남아야 한다. 그 요구사항 — Redis 호환 *그리고* 내구성 있음 — 이 MemoryDB에 대한 정확한 신호다.

"그러면 실패 후 그것을 다시 워밍할 필요가 없어요?" Leo가 물었다.

"그게 요점이야," Priya가 말했다. "노드가 실패하고 돌아오면, 데이터가 거기 있어. 트랜잭션 로그가 그것을 지켰어."

Leo가 잠시 가격 페이지를 바라봤다. "ElastiCache보다 비싸네요."

"믿을 가치가 있는 모든 것이 그래," Priya가 말했다.

## 장점과 한계

**캐싱이 강력한 이유**:

- 데이터베이스 부하를 극적으로 줄인다(쿼리 더 적음, 비용 더 낮음)
- 캐시 히트에 서브 밀리초 응답 시간
- 트래픽 급증으로부터 데이터베이스를 보호한다
- Redis는 단순한 키-값 저장소보다 더 풍부한 데이터 구조를 지원한다
- 캐시 스탬피드 완화(TTL 지터, 병합)는 콜드 스타트 급증으로부터 보호한다

**캐싱이 복잡해지는 경우**:

- 캐시 무효화는 진정으로 어렵다 — 오래된 데이터가 버그를 유발한다
- 운영 복잡성을 추가한다(모니터링할 서비스 하나 더, 실패 지점 하나 더)
- 콜드 스타트 문제: 새로 배포하면, 캐시가 비어 있다 — 데이터베이스가 전체 부하를 받는다
- 캐시 스탬피드: 많은 엔트리가 한 번에 만료되면, 모든 요청이 동시에 데이터베이스에 접근한다
- ElastiCache 노드는 무료가 아니다 — 유휴 상태에서도 비용이 든다

**ElastiCache vs DynamoDB DAX**:

DynamoDB 데이터를 구체적으로 캐시하는 경우, AWS는 **DAX (DynamoDB Accelerator)** — DynamoDB를 위한 목적 구축 인메모리 캐시를 제공한다. DAX는 애플리케이션 코드에 투명하고(같은 API), DynamoDB 읽기 지연을 마이크로초로 줄이고, 캐시 무효화를 자동으로 처리한다.

병목이 DynamoDB 읽기이고 변경 없는 캐싱을 원할 때 DAX를 사용하라. 모든 데이터 소스를 위한 범용 캐시가 필요하거나, Redis 데이터 구조가 필요할 때 ElastiCache를 사용하라.

## 요약

마흔일곱 번의 데이터베이스 호출이 하나의 캐시 조회가 되었다. 페이지가 188밀리초에서 12로 갔다. 캐싱 레이어를 추가하는 것은 성장하는 애플리케이션이 할 수 있는 가장 큰 레버리지를 가진 변경 중 하나다 — 하지만 캐시가 "이 데이터는 언제 변경되는가?"라는 질문에 대한 명확한 답을 가지고 신중하게 설계됐을 때만.

- 캐시는 최근에 검색된 데이터의 빠른 저장소다 — 한 번 물어보고, 답을 기억한다. ElastiCache는 AWS의 관리형 캐싱 서비스로, **Redis**(영속성, 복잡한 데이터 구조, pub/sub)와 **Memcached**(순수 키-값, 수평 확장)를 지원한다.
- **캐시-어사이드 패턴**(게으른 로딩): 먼저 캐시를 확인하고, 미스 시 데이터베이스로 폴백. **TTL**은 데이터가 얼마나 오래 캐시되는지를 제어한다 — 짧은 TTL은 더 신선한 데이터와 더 많은 미스를 의미하고; 긴 TTL은 더 빠른 응답과 잠재적 오래됨을 의미한다.
- 올바른 것을 캐시하라: 각 세션에 고유한 사용자별 데이터가 아니라, 많은 사용자에 걸쳐 공유되는 엔티티별 데이터. 캐시 스탬피드는 많은 엔트리가 동시에 만료될 때 발생한다 — TTL 지터로 완화하라.
- **DAX**는 DynamoDB 전용 캐싱에 올바른 선택이다. **ElastiCache**는 다중 소스 캐싱과 Redis 데이터 구조에 더 유연하다.
- 캐싱의 가장 어려운 부분은 무효화다: 데이터가 언제 변경되는지 알고 그것을 쓰는 모든 코드 경로에 걸쳐 캐시를 업데이트하는 것. 캐시는 그것의 무효화 전략만큼만 신뢰할 수 있다.

## 시험 팁

*SAA-C03 도메인: 고성능 아키텍처 설계(도메인 3, 태스크 3.3)*

- **시험에서 Redis vs Memcached**: Redis = 영속성, 복제, 복잡한 구조, pub/sub. Memcached = 단순 키-값, 순수 수평 확장. 시나리오가 "캐시된 데이터를 잃을 수 없다"고 언급하면, 답은 Redis다(디스크에 영속된다).
- **ElastiCache 사용 사례 신호**: "데이터베이스가 병목", "읽기 집약적 워크로드", "지연 시간 줄이기", "세션 저장소" — 모두 ElastiCache를 가리킨다.
- **DAX 신호**: "DynamoDB 읽기 지연 줄이기" 또는 "DynamoDB 읽기가 너무 느림" → DAX, ElastiCache 아님.
- **세션 관리**: ElastiCache Redis가 사용자 세션 데이터를 저장하는 표준 답이다. 무상태 애플리케이션 + Redis 세션 저장소 = 일관된 세션을 가진 수평 확장.
- **쓰기-스루 vs. 캐시-어사이드**: 캐시-어사이드(게으른 로딩)가 가장 흔하다. 쓰기-스루는 모든 쓰기에서 캐시를 업데이트한다 — 결코 오래되지 않지만, 더 많은 쓰기 작업. 시험이 그것들을 구분할 수 있다.
- **캐시 제거 정책**: LRU(가장 최근에 사용되지 않은)가 일반 웹 워크로드에 대한 가장 흔한 시험 답이다.
- **ElastiCache vs. MemoryDB**: ElastiCache = 캐시 레이어, 빠름, 실패 시 데이터 손실 허용 가능. MemoryDB = 내구성 있는 인메모리 기본 데이터베이스, Redis 호환, 멀티 AZ 트랜잭션 로그. 시험 트리거: "Redis 호환 그리고 내구성 있음" 또는 "Redis의 기본 데이터 저장소" → MemoryDB, ElastiCache 아님.

**힌트 3**: 목표는 데이터베이스 부하를 줄이는 것이지, 더 많이 처리하는 것이 아니다.

**정답**: C

**설명**: ElastiCache에 1시간 TTL을 가진 카탈로그 데이터를 캐시하면 키당 첫 번째 요청 후 후속 요청이 데이터베이스를 건드리지 않고 캐시에서 반환된다. 밤마다 업데이트가 실행되면, 엔트리가 1시간 내에 만료되고 신선한 데이터가 다음 요청에서 로드된다.

**왜 A가 아닌가?** 읽기 복제본은 읽기 트래픽을 더 많은 데이터베이스 노드에 배분하지만 총 쿼리 수를 줄이지 않는다. 읽기를 확장하는 데 유용하지, 자주 반복되는 쿼리에서 데이터베이스 부하를 줄이는 데는 아니다.

**왜 B가 아닌가?** DynamoDB로 마이그레이션해도 근본적인 문제를 해결하지 않는다 — 카탈로그 데이터는 모든 사용자 요청에서 데이터베이스(DynamoDB)에서 여전히 가져올 것이다.

**왜 D가 아닌가?** 인스턴스를 확장하면 더 많은 동시 쿼리를 처리하지만 쿼리 수를 줄이지 않는다. 근본적인 비효율성이 남는다.

*SAA-C03 도메인: 고성능 아키텍처 설계 — 태스크 3.3*

**연습 3 — 아키텍처 과제** *(선택 사항)*

Nimbus는 "트렌딩 레스토랑" 기능을 추가하길 원한다: 지난 24시간 동안 주문량 기준으로 상위 10개 레스토랑의 순위 목록, 15분마다 업데이트.

ElastiCache Redis로 이것을 어떻게 구현하겠는가? 어떤 Redis 데이터 구조를 순위에 사용하겠는가? 캐시 TTL이 무엇이고, 정확히 언제 캐시를 업데이트하겠는가?

## 포스트 크레딧 장면

"제가 이미 배포했어요 — 아." Leo는 연결 풀 설정을 업데이트하기 전에 Redis 통합을 프로덕션에 푸시했다. 부하 중에, 애플리케이션이 너무 많은 Redis 연결을 열고 있었다. 그는 그것을 롤백하고 올바른 설정으로 다시 배포해야 했다.

Leo가 메뉴를 위한 Redis 캐싱을 추가했다. 페이지 로드 시간이 188밀리초에서 12밀리초로 떨어졌다.

마흔일곱 번의 DynamoDB 호출이 하나의 Redis 조회가 되었다. 그 호출은 0.8밀리초였다.

그는 월요일 스탠드업에서 이것을 발표했다.

"잘했어," Priya가 노트북에서 눈을 들지 않고 말했다.

"감사합니다," Leo가 말했다.

"Redis 인증 토큰을 마지막으로 언제 교체했어?"

Leo가 메모를 봤다. "설정한 것 같지 않아요."

"그러면 캐시가 인증되지 않았네."

"VPC 안에 있어요."

"침해된 모든 다른 것들도 마찬가지야." 그녀가 마침내 고개를 들었다. "Leo의 노트북이 감염되고 누군가 VPC로 피벗하면, 캐시에 비밀번호가 없어."

Leo가 그녀를 바라봤다.

"인증 토큰을 설정할게요," 그가 말했다.
