# 25장: 프라이빗 고속도로

잠깐 일어나서 손을 흔들어 보라.

데이터 이동에 대해 이야기하려 한다. AWS 내의 서비스 간이 아니라 실제 세계와 AWS 사이 — 사무실과 클라우드 인프라 사이, 대륙 사이.

Nimbus의 인프라 팀(이제 엔지니어 네 명)은 시애틀의 공유 사무실에서 근무했다. 그들은 관리하는 AWS 인프라에 접근해야 했다. 일부 작업은 VPC의 리소스에 연결이 필요했다.

현재 그들은 노트북의 VPN을 사용하여 공개 서브넷의 배스천 호스트에 접근하고, 거기서 리소스에 SSH했다.

작동했다. 느렸다. VPN 연결은 공개 인터넷을 통해 라우팅됐다: 시애틀 → 교차 국가 광섬유 → 여러 운반자 홉 → us-east-1. 각 왕복은 80밀리초 이상.

"일상적인 SSH의 경우, 그건 허용 가능해요," Leo가 말했다. "하지만 우리는 분석 데이터베이스를 이동하려 한다. 이전 주문 데이터 4테라바이트. 이 연결을 통해, 마이그레이션이 몇 주 걸릴 거야."

"더 나은 연결이 필요해요," Maya가 말했다.

"프라이빗 연결," Priya가 덧붙였다. "공개 인터넷을 통하지 않는."

직장까지 출근하는 것처럼 생각하라. Site-to-Site VPN은 공공 도로에서 운전하는 것과 같다: 자동차 문을 잠그지만(암호화), 모든 사람과 같은 차선을 공유하며, 교통 정체가 예측할 수 없게 느리게 만든다. Direct Connect는 전용 프라이빗 차선을 임대하는 것과 같다 — 공유 트래픽 없음, 일관된 속도, 더 높은 월 통행료. 대부분의 날 공공 도로가 괜찮다. 빠듯한 일정에 귀중한 화물 트럭을 이동시킬 때, 프라이빗 차선에 지불한다.

**AWS Site-to-Site VPN: 빠른 옵션**

**AWS Site-to-Site VPN**은 공개 인터넷을 통해 온프레미스 네트워크와 VPC 사이에 암호화된 터널을 만든다.

설정:

1. VPC에 연결된 Virtual Private Gateway(VGW)를 만든다
2. 온프레미스 라우터를 나타내는 Customer Gateway를 만든다
3. 그것들 사이에 두 개의 VPN 터널을 수립한다(이중화를 위해)

트래픽이 암호화된다(AES-256). 공개 인터넷을 통해 이동하며, 지연이 인터넷 조건에 따라 달라진다. AWS가 자동으로 이중화를 위해 두 개의 터널을 제공한다 — 하나의 터널에 문제가 생기면 트래픽이 다른 것으로 이동한다.

**Site-to-Site VPN을 사용하는 경우**:

- 빠른 설정(분~시간)
- 비용 효율적(VPN 연결당 $0.05/시간)
- 터널당 최대 1.25 Gbps 대역폭
- 사용 사례에 인터넷 지연이 허용 가능할 때

Nimbus의 4TB 마이그레이션의 경우, 인터넷 기반 VPN은 최대 1.25 Gbps에서: 4TB / 1.25 Gbps ≈ 최소 7시간이 걸릴 것이다. 실제 세계 오버헤드는 12-20시간에 더 가깝다. 허용 가능하지만, 공개 인터넷 경로의 혼잡이 예측 불가능하게 만든다.

"다른 옵션은요?" Tom이 물었다.

**AWS Direct Connect: 전용 라인**

**AWS Direct Connect**는 위치(또는 코로케이션 시설)와 AWS 사이에 전용 프라이빗 네트워크 연결을 수립한다. 트래픽이 절대 공개 인터넷을 건드리지 않는다.

Direct Connect는 물리적 연결이다 — 네트워크에서 AWS Direct Connect 위치로의 광섬유 라인. AWS가 자신들의 측에 포트를 제공하는 동안 물리적 회로를 수립하기 위해 통신 공급업체와 협력한다.

**이점**:

- 일관되고 예측 가능한 지연(공개 인터넷 분산 없음)
- 50 Mbps에서 100 Gbps까지 속도
- 인터넷보다 낮은 데이터 전송 비용(Direct Connect 데이터 전송률이 표준 AWS 데이터 전송 아웃 비율보다 저렴)
- 더 안전(프라이빗 회로, 공개 인터넷 아님)

**트레이드오프**:

- 설정에 수 주에서 수 개월이 걸린다(물리적 인프라 프로비저닝)
- VPN보다 훨씬 더 높은 비용($0.025-0.30/시간 포트당, 더하기 통신 회로 비용 — 종종 월 최소 $500-1000+)
- 내장 이중화 없음(직접 이중 회로를 수립한다)
- 지리적으로 분산된 사무실에 여러 회로 없이는 적합하지 않음

Nimbus의 경우: Direct Connect는 현재 크기에 과잉이었다. 하지만 상당한 데이터 전송 볼륨이나 프라이빗 네트워크 연결에 대한 컴플라이언스 요구사항이 있는 기업에게는 Direct Connect가 그 자체 비용을 지불한다.

**호스팅 연결: 중간 지점**

모든 조직이 100 Gbps 전용 광섬유 회로를 약정할 수 있는 것은 아니다. **Direct Connect 호스팅 연결**을 통해 AWS Direct Connect 파트너(승인된 통신업체)가 다른 고객과 공유하는 서브-1Gbps 연결을 프로비저닝할 수 있다.

설정이 더 빠르고(수 주, 수 개월이 아닌) 전용 연결보다 비용이 적다. 트레이드오프: 공유 용량은 덜 일관된 처리량을 의미한다.

Nimbus(성장하면서): 파트너를 통한 호스팅 500 Mbps 연결이 합리적인 가격으로 프라이빗 연결을 제공할 것이다.

**AWS Transit Gateway: VPC를 위한 허브-앤-스포크**

Nimbus가 성장하면서, 여러 VPC를 축적하게 된다: 프로덕션 VPC, 스테이징 VPC, 분석 VPC, 보안 도구 VPC.

신중한 계획 없이, 이 VPC들을 연결하는 것은 전체 메시의 VPC 피어링 연결이 필요하다. VPC 4개의 경우: 6개의 피어링 연결. VPC 10개의 경우: 45개. VPC 20개의 경우: 190개. 이것이 확장되지 않는다.

**AWS Transit Gateway**는 여러 VPC와 온프레미스 네트워크를 연결하는 네트워크 허브다. 피어링 연결의 메시 대신, 각 VPC가 Transit Gateway에 연결된다. Transit Gateway가 그것들 사이에 트래픽을 라우팅한다.

```
온프레미스 ──── Direct Connect ──┐
                                  │
프로덕션 VPC ───────────────── Transit Gateway
스테이징 VPC ──────────────────── Transit Gateway
분석 VPC ─────────────────────── Transit Gateway
보안 VPC ──────────────────────── Transit Gateway
```

**전이적 라우팅**: VPC A와 VPC B가 모두 Transit Gateway에 연결되면, 그것들은 직접 피어링 없이 통신할 수 있다. Transit Gateway가 라우팅을 처리한다. VPC 피어링과 달리(전이적이지 않은), Transit Gateway는 허브-앤-스포크 토폴로지를 가능하게 한다.

**Transit Gateway 비용**: VPC 또는 VPN/Direct Connect 연결 첨부당 더하기 처리된 GB당 요금. 대규모에서, 단순함을 위해 가치가 있다.

**VPC 엔드포인트: AWS 서비스에 대한 프라이빗 접근**

미묘한 비용 및 보안 문제: EC2 인스턴스(프라이빗 서브넷에서)가 S3 API를 호출할 때, 그 트래픽이 NAT 게이트웨이를 통해 라우팅된다(S3의 공개 엔드포인트가 있는 인터넷에 도달하기 위해). NAT 게이트웨이 처리 비용을 지불한다.

**VPC 엔드포인트**를 통해 VPC의 리소스가 공개 인터넷을 통하지 않고 — 그리고 NAT 게이트웨이 없이 — AWS 서비스와 비공개로 통신할 수 있다.

두 가지 유형:

**게이트웨이 엔드포인트**(무료): S3 및 DynamoDB를 위해. 라우팅 테이블에 S3 또는 DynamoDB 트래픽을 인터넷이 아닌 엔드포인트로 보내는 경로를 추가한다. 무료로 만들고; 무료로 사용.

**인터페이스 엔드포인트**(가격 있음): 다른 AWS 서비스(SQS, SNS, Secrets Manager, SSM 등)를 위해. 프라이빗 IP를 가진 서브넷에 ENI(Elastic Network Interface)를 만든다. 서비스로의 트래픽이 이 프라이빗 IP를 사용한다. AZ당 ~$0.01/시간 더하기 데이터 처리 비용.

Tom은 그것들이 무료라는 것을 배운 후 즉시 S3와 DynamoDB를 위한 게이트웨이 엔드포인트를 만들었다. NAT 게이트웨이 데이터 처리 수수료가 30% 떨어졌다.

**AWS Global Accelerator: 엣지에서 라우팅**

Nimbus가 us-east-1(버지니아)에서 서부 해안 사용자에게 서비스를 제공할 때, 지연이 80ms였다. 서버가 금지적으로 멀어서가 아니라, 시애틀과 버지니아 사이의 공개 인터넷 라우팅이 최적이 아니어서였다. 여러 운반자를 통해 튀어 다녔다.

**AWS Global Accelerator**는 AWS의 프라이빗 백본 네트워크(CloudFront를 구동하는 같은 인프라)를 사용하여 사용자와 AWS 애플리케이션 사이에 트래픽을 라우팅한다. 공개 인터넷 라우팅 대신, 트래픽이 가장 가까운 엣지 로케이션에서 AWS 네트워크에 들어가고 최적화된 프라이빗 경로를 통해 이동한다.

Nimbus의 경우, 시애틀 사용자는:

- **Global Accelerator 없이**: 공개 인터넷 운반자를 통해 ~80ms로 라우팅
- **Global Accelerator를 통해**: 시애틀의 가장 가까운 AWS 엣지를 타격 → AWS 백본을 통해 이동 → us-east-1에 도착 → ~45ms

Global Accelerator는 콘텐츠를 캐시하지 않는다(그게 CloudFront다). 동적 요청을 위한 네트워크 경로를 최적화한다.

**Global Accelerator vs. CloudFront를 언제 사용하는가**:

- CloudFront: 정적 및 캐시 가능한 콘텐츠, CDN 사용 사례
- Global Accelerator: 동적 콘텐츠, 비HTTP 프로토콜(UDP, 게이밍, IoT), 또는 정적 Anycast IP 주소가 필요할 때

## 장점과 한계

**Site-to-Site VPN**:

- 빠른 설정, 낮은 비용
- 공개 인터넷 경로는 가변 지연을 의미
- 제한된 대역폭 최대값

**Direct Connect**:

- 일관되고 프라이빗, 높은 대역폭
- 설정이 느리고, 상당한 반복 비용
- 물리적 회로는 단일 장애 지점(이중화를 추가)

**Transit Gateway**:

- 멀티 VPC 연결을 극적으로 단순화
- 전이적 라우팅(VPC 피어링과 달리)
- 많은 첨부로 비용이 쌓인다

**VPC 엔드포인트**:

- S3/DynamoDB에 대한 보안 및 비용 이점(무료 게이트웨이 엔드포인트)
- AWS 서비스 트래픽을 위한 NAT 게이트웨이 비용 제거

**Global Accelerator**:

- 전 세계 사용자를 위한 동적 애플리케이션 지연 향상
- 고정 Anycast IP(CloudFront의 동적 IP와 달리)
- 추가 비용(가속기당 $0.025/시간 + 데이터 전송)

## 요약

- **Site-to-Site VPN**: 공개 인터넷을 통한 온프레미스와 VPC 사이의 암호화된 터널. 빠른 설정, 낮은 비용, 가변 지연.
- **Direct Connect**: AWS에 대한 프라이빗 전용 광섬유 연결. 예측 가능한 지연, 더 높은 대역폭, 설정에 수 주, 상당한 비용.
- **Transit Gateway**: VPC 및 온프레미스 연결을 위한 허브. 전이적 라우팅을 가능하게 한다. 수백 개의 연결로 확장된다.
- **VPC 엔드포인트**: NAT 게이트웨이 없이 AWS 서비스에 대한 프라이빗 접근. 게이트웨이 엔드포인트(S3, DynamoDB)는 무료.
- **Global Accelerator**: AWS 백본을 통해 글로벌 사용자를 위한 동적 트래픽을 라우팅하여 지연 감소.

## 시험 팁

*SAA-C03 도메인: 고성능 아키텍처 설계(도메인 3, 태스크 3.4)*

- **VPN vs. Direct Connect 신호**: VPN = "VPC에 트래픽 암호화," "빠른 설정," "비용 민감." Direct Connect = "일관된 낮은 지연," "대용량 데이터 전송," "프라이빗 연결," "프라이빗 네트워크를 요구하는 컴플라이언스."
- **Transit Gateway vs. VPC 피어링**: 피어링은 비전이적(A→B→C는 A→C를 허용하지 않는다). Transit Gateway는 전이적. "통신이 필요한 많은 VPC" → Transit Gateway.
- **VPC 게이트웨이 엔드포인트**: 무료. S3와 DynamoDB만. 라우팅 테이블 변경. 추가 비용 없음. 시험 시나리오: "프라이빗 서브넷에서의 S3 접근을 위한 데이터 전송 비용 절감" → 게이트웨이 엔드포인트.
- **Global Accelerator vs. CloudFront**: 가속기 = 동적 콘텐츠, 비HTTP, 정적 IP, 네트워크 최적화. CloudFront = 캐싱, HTTP 콘텐츠, CDN.
- **Direct Connect + VPN**: VPN을 Direct Connect 연결의 백업으로 사용할 수 있다. Direct Connect 회로가 실패하면, 트래픽이 VPN으로 장애 조치된다. VPN만보다 더 비싸지만 Direct Connect만보다 더 신뢰할 수 있다.
- **Direct Connect Gateway**: 단일 Direct Connect 회로를 여러 리전이나 계정의 여러 VPC에 연결한다. 없으면, Direct Connect 회로가 하나의 리전의 하나의 VGW에 연결된다.

C) 다른 인터넷 공급업체를 통한 두 개의 Site-to-Site VPN 연결  
D) Direct Connect Gateway가 있는 Direct Connect 호스팅 연결

**힌트 1**: "공개 인터넷을 통과해서는 안 됨" — VPN 트래픽은 공개 인터넷을 통해 간다(암호화되더라도). Direct Connect만이 프라이빗이다.

**힌트 2**: "일관되고 예측 가능한 지연" — 공개 인터넷 VPN 성능이 달라진다. Direct Connect가 일관적이다.

**힌트 3**: "백업 연결" — Direct Connect가 기본 서버일 때 권장 접근은 무엇인가?

**답**: B

**설명**: Direct Connect는 공개 인터넷을 통과하지 않는 프라이빗 전용 연결을 제공하고 — 프라이버시와 지연 요구사항을 충족한다. Site-to-Site VPN이 백업으로 이중화를 제공한다: Direct Connect 회로가 실패하면, 트래픽이 암호화된 VPN으로 장애 조치된다. 이것이 Direct Connect를 위한 표준 HA 패턴이다.

**왜 A가 아닌가?** Site-to-Site VPN 트래픽은 공개 인터넷을 통과한다 — "공개 인터넷을 통과해서는 안 됨" 요구사항을 위반한다.

**왜 C가 아닌가?** 다른 ISP를 통한 두 개의 VPN 연결은 여전히 공개 인터넷을 통과한다, 암호화되더라도. 프라이빗 네트워크 요구사항을 충족하지 않는다.

**왜 D가 아닌가?** 호스팅 연결은 Direct Connect 연결을 제공하지만 옵션 D는 백업을 포함하지 않는다. 백업 없는 단일 Direct Connect는 단일 장애 지점이다 — 물리적 광섬유를 자를 수 있다.
