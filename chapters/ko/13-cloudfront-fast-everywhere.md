# 13장: 어디서나 빠르게

오리건의 서버에서 보스턴의 전화기로 이동하는 사진은 약 4,100킬로미터의 광섬유 케이블을 가로지른다. 빛의 속도의 3분의 2로, 그것은 약 25밀리초의 순수한 물리학이다 — 피할 수 없고, 협상 불가능하며, 우주의 법칙에 새겨져 있다.

그런 다음 왕복을 추가하라. 처리 시간을 추가하라. 브라우저가 아직 렌더링을 시작하지 않았는데 이미 80밀리초가 지나갔다.

---

*`eatnimbus.com`이 라이브였고 도메인 이름이 진짜였다. 사용자가 앱을 찾을 수 있었다. 하지만 그것을 찾는 것은 즐기는 것과 같지 않았다. Tom이 여러 도시에서 지연 시간 측정을 실행하고 있었고, 동부 해안과 남미의 수치가 좋지 않았다. 도메인 이름 문제는 해결됐다. 물리학 문제는 아니었다.*

---

`eatnimbus.com`이 라이브였다. Leo가 동부 해안 사용자의 지연 시간 메트릭을 확인했다: 요청당 80-100밀리초. 그 수치가 작게 들릴 수 있지만, 쌓인다.

메뉴 로드: 90ms. 레스토랑 목록 로드: 80ms. 레스토랑 사진 로드: 200ms(이미지는 크다). 사용자가 주문을 할 수 있기 전의 총 시간: 좋은 연결에서도 반초 이상.

"물리학이 문제야," Leo가 말했다. "서버가 오리건에 있어. 성장은 동부 해안에 있고 — 그리고 상파울루에."

"그러면 서버를 동부 해안으로 이동시켜," Tom이 말했다.

"돈이 들어요."

"그게 한 달에 얼마나 들지?" Tom이 물었다.

"us-east-1에서 우리 인프라의 완전한 복제본을 실행하는 거? 아마 현재 비용의 세 배. 그리고 완전히 새로운 문제를 만들어요: 서부 해안 데이터베이스와 동부 해안 데이터베이스를 동기화 상태로 유지하는 것."

Priya가 노트북에서 고개를 들었다. "아니면 서버를 이동시키지 않아. *콘텐츠*를 이동시키는 거지."

Maya가 고개를 들었다. "차이가 뭐예요? 콘텐츠가 서버에 있고, 서버가 오리건에 있으면, 콘텐츠가 오리건에 있는 거잖아요."

"페이지가 전달하는 대부분은 정적이야," Priya가 말했다. "이미지, 스타일시트, JavaScript 파일, 폰트. 그것들은 모든 사용자에게 같아. 그것들은 데이터베이스에서 오지 않아. S3에 살아. 그리고 S3 객체는 어디서든 제공될 수 있어."

"그러면 그것들을 사용자에게 더 가까운 서버에 복사해요?"

"서비스가 그것을 우리를 위해 관리하게 해. 하나의 진실의 원천. 필요한 모든 곳에 복사본."

Tom은 이미 가격 페이지를 열었다. 그는 Priya가 설명을 끝내기 전에 계산하고 있었다.

**사전 비축 창고 비유**

소매업체로서의 Amazon을 상상해보라, 클라우드 회사가 아닌. 그들에게는 한 위치에 모든 제품을 갖춘 하나의 거대한 창고가 있다. 그 하나의 창고에서 모든 주문을 배송하면, 먼 도시의 고객들이 며칠을 기다릴 것이다.

대신, Amazon은 주요 인구 중심지 근처에 주문 처리 센터를 갖고 있다. 제품이 인기 있으면, 그 로컬 창고에 미리 비축한다. 시애틀의 고객이 책을 주문하면, 전국을 가로질러서가 아니라 로컬 주문 처리 센터에서 배송된다.

이것이 **콘텐츠 전송 네트워크(CDN)**다: 사용자 가까이에 콘텐츠의 복사본을 캐시하는 지리적으로 배포된 서버 네트워크.

보스턴의 사용자가 홈페이지를 요청하면, CDN이 보스턴의 서버에서 그것을 제공한다. 오리건이 아니라. 요청이 절대 국가를 가로지르지 않는다.

**CloudFront 소개**

Amazon CloudFront는 AWS의 CDN이다. **엣지 로케이션** — 세계 전역 도시에 위치한 캐싱 서버 — 의 글로벌 네트워크를 통해 운영된다. 이 글을 쓰는 시점에, 100개 이상의 도시에 750개 이상의 접속 지점이 있다.

CloudFront를 설정할 때, **오리진**을 지정한다: 실제 콘텐츠의 소스. 오리진은 다음이 될 수 있다:

- S3 버킷(정적 파일: 이미지, CSS, JavaScript, PDF)
- Application Load Balancer(애플리케이션의 동적 콘텐츠)
- EC2 인스턴스
- 인터넷 어디의 HTTP 서버

CloudFront가 오리진 앞에 앉는다. 요청이 가장 가까운 엣지 로케이션에 들어온다. 엣지에 캐시된 콘텐츠가 있으면, 즉시 반환한다. 없으면(*캐시 미스*), 오리진에서 가져오고, 캐시하고, 반환한다.

**CloudFront 캐싱 작동 방식**

어떤 콘텐츠의 첫 번째 요청은 항상 캐시 미스다 — 오리진으로 간다. 모든 후속 요청은 엣지 로케이션의 캐시에 접근한다.

Nimbus의 경우, 메뉴 사진이 완벽한 CloudFront 후보다. 레스토랑 사진은 드물게 변경된다(레스토랑이 프로필을 업데이트할 때 정도). CloudFront를 사용하면:

1. 보스턴의 사용자가 `images.eatnimbus.com/restaurant-047/photo.jpg`를 요청
2. CloudFront가 보스턴의 엣지 로케이션을 확인 — 아직 캐시되지 않음(캐시 미스)
3. CloudFront가 us-west-2의 S3에서 가져옴(~80ms)
4. CloudFront가 사진을 보스턴 엣지 로케이션에 저장
5. 보스턴의 다음 사용자가 같은 사진을 요청
6. CloudFront가 로컬 엣지 캐시에서 제공(~5ms)

첫 번째 요청에는 동일한 80ms 페널티. 하지만 같은 도시에서의 천 번째 요청은 5밀리초.

**Cache-Control 헤더**와 CloudFront의 **TTL 설정**은 콘텐츠가 엣지에 얼마나 오래 캐시되는지를 결정한다. 이미지 파일은 몇 시간 또는 며칠 동안 캐시될 수 있다. 더 자주 변경되는 HTML 페이지는 몇 분 또는 몇 초 동안 캐시될 수 있다.

여러분은 궁금할 것이다: CDN을 사용하는 대신 왜 전체 애플리케이션을 여러 리전에 호스팅하지 않는가? 데이터가 오리건에 있다면, 왜 뉴욕, 도쿄, 상파울루에 완전한 복사본을 두지 않는가? 그럴 수 있다. 하지만 그것은 여러 데이터베이스를 동기화하고, 리전에 걸쳐 배포를 동시에 관리하고, 리전이 불일치하는 스플릿-브레인 시나리오를 처리하는 것을 의미한다. CDN은 정적 및 준정적 콘텐츠에 훨씬 더 간단한 답이다: 하나의 오리진, 엣지의 많은 캐시된 복사본. 사용자 가까이에서 컴퓨트나 데이터베이스 연산이 정말로 필요할 때만 멀티 리전 복잡성을 추가한다 — 대부분의 콘텐츠에는, 엣지 캐싱으로 충분하다.

"잠깐 — 그런데 *왜* 그렇게 하는 거죠?" Maya가 물었다. "왜 오리건에 더 큰 ElastiCache 클러스터를 추가하는 대신 엣지에 캐시를 두죠?"

"물리학이 여전히 문제니까," Priya가 말했다. "오리건이 1밀리초에 응답하더라도, 그 응답은 여전히 보스턴으로 이동해야 해. 왕복 시간이 최소 70밀리초야 — 빛의 속도는 우리 서버가 얼마나 빠른지 신경 쓰지 않아. 엣지 캐싱은 답을 질문에 더 가깝게 옮겨."

**동적 콘텐츠: 캐싱 이상의 CloudFront**

"하지만 우리 API 응답은요?" Leo가 물었다. "그것들은 동적이야 — 사용자마다, 요청마다 바뀌어. 주문 내역 페이지는 캐시할 수 없잖아."

맞다. 하지만 CloudFront는 여전히 동적 콘텐츠를 돕는다.

콘텐츠가 캐시될 수 없더라도, CloudFront는 엣지 로케이션에서 오리진으로의 요청을 AWS의 프라이빗 백본 네트워크 — 전 세계 AWS 인프라를 연결하는 고속 광섬유 — 를 통해 라우팅한다. 이것이 트래픽이 여러 운반자를 통해 튀어 다닐 수 있는 공개 인터넷을 통해 라우팅하는 것보다 더 빠르고 안정적이다.

결과: 동적 요청은 CloudFront를 통해 공개 인터넷을 통해 직접 오리진으로 가는 것보다 여전히 20-40% 더 빠르다. 캐싱 때문이 아니라, 네트워크 경로 때문에.

"말이 안 되는데요," Maya가 말했다. "API 응답이 여전히 오리건에서 엣지로, 그런 다음 보스턴으로 이동해야 한다면, 그게 오리건에서 보스턴으로 직접 가는 것보다 어떻게 더 빠르죠?"

"두 가지 이유," Priya가 말했다. "첫째, AWS의 프라이빗 백본이 공개 인터넷보다 더 빠르고 안정적이야. 공개 인터넷 트래픽은 여러 운반자를 통해 라우팅되고, 각각이 자체 지연 시간과 변동성을 추가해. 백본은 직접적이고, 낮은 지연 시간의 광섬유야. 둘째, SSL 종료가 엣지에서 일어나. 사용자가 가장 가까운 CloudFront 엣지 로케이션에 TLS 연결을 설정해 — 핸드셰이크가 빨라. 그런 다음 CloudFront가 오리진으로 지속적이고 사전 설정된 연결을 유지해. 하나의 장거리 연결 대신 두 개의 단거리 연결."

"그러니까 캐시되지 않은 콘텐츠에도, CloudFront가 연결 오버헤드에서 시간을 깎네요," Leo가 말했다.

"보통 10에서 40퍼센트. 캐싱만큼 극적이지는 않아. 하지만 실제야."

추가로, CloudFront는 다음을 제공한다:

**SSL/TLS 종료**: CloudFront가 엣지에서 HTTPS를 처리한다. 사용자와 CloudFront 사이의 연결이 암호화된다. CloudFront는 내부적으로 HTTP(오리진 부하 줄이기)나 HTTPS(엔드-투-엔드 암호화)로 오리진에 연결할 수 있다.

**DDoS 보호**: CloudFront는 AWS Shield Standard와 통합된다. 수백 개의 엣지 로케이션에 걸쳐 분산된 트래픽은 공격이 오리진을 강타하는 대신 엣지에서 흡수된다는 것을 의미한다.

**지오 제한**: 특정 국가에서의 접근을 차단. Nimbus가 특정 시장에서만 운영하도록 허가되었다면, CloudFront가 요청이 서버에 도달하기 전에 엣지에서 그것을 시행할 수 있다.

**그리고 누군가 CDN을 통해 침입하려 하면?** Priya가 물었다. "캐시 포이즈닝 — 누군가 엣지 캐시에 나쁜 콘텐츠를 주입하면?"

"CloudFront에는 캐시 키 제어가 있어요," Leo가 말했다. "두 요청이 같은 캐시된 응답을 받는지를 결정하는 속성을 정확히 정의해요. 헤더, 쿼리 문자열, 쿠키. 공격자는 정확한 캐시 키를 일치시키지 않고는 다른 캐시된 응답을 주입할 수 없어요."

"그리고 Origin Access Control은 S3 버킷이 CloudFront를 통해 오지 않는 것은 아무것도 제공하지 않는다는 것을 의미해," Priya가 말했다. "두 개 대신 하나의 공격 표면."

**CloudFront 동작: 세밀한 캐싱 규칙**

CloudFront 배포는 URL 패턴을 기반으로 한 라우팅 규칙인 여러 **동작**을 가질 수 있다.

Nimbus의 경우:

- `/images/*` → 엣지에서 7일 동안 캐시(사진은 자주 변경되지 않는다)
- `/static/*` → 엣지에서 30일 동안 캐시(버전화된 파일명을 가진 CSS와 JavaScript)
- `/api/*` → 캐시하지 않음; 로드 밸런서로 직접 전달
- `/*` → 5분 동안 캐시(HTML 페이지)

이것이 CloudFront를 스마트하게 만든다: 안정적인 것을 공격적으로 캐시하고, 동적인 것을 통과시킨다.

동작은 가장 구체적인 것에서 가장 덜 구체적인 것으로 일치된다. `/images/hero.jpg`는 `/*`에 일치하기 전에 `/images/*`에 일치한다. 맨 아래의 포괄 `/*`이 기본값이다 — 더 구체적인 패턴에 일치하지 않는 모든 것에 적용된다.

"인증된 사용자와 인증되지 않은 사용자에 대해 다른 캐싱을 원하면?" Priya가 물었다. "같은 URL이 사용자가 로그인됐는지에 따라 다른 콘텐츠를 반환할 수 있어."

"그러면 캐시 키에 세션 쿠키를 포함해," Leo가 말했다. "하지만 그건 모든 로그인된 사용자가 자체 캐시 엔트리를 받는다는 거야. 인증된 콘텐츠에 대해 히트율이 붕괴해."

"그게 인증된 콘텐츠를 공개 콘텐츠로부터 URL 수준에서 분리하는 이유야," Priya가 말했다. "인증이 필요한 모든 것은 `/app/*`로 가고 캐시되지 않아. 공개 콘텐츠는 `/browse/*`로 가고 공격적으로 캐시돼. 하나의 명확한 경계."

교훈: CloudFront는 URL 구조가 캐싱 의도를 반영할 때 가장 잘 작동한다. 완전히 공개적이고 정적인 데이터를 가리키는 URL은 개인화되고 동적인 데이터를 반환하는 URL과 다르게 보여야 한다. 그것들이 CloudFront에 같게 보이면, 캐시가 망가지거나 잘못된 콘텐츠가 제공된다.

Leo가 주말에 Nimbus URL 스킴을 재구조화했다. 탐색 엔드포인트가 `/browse/`로 이동했다. API 엔드포인트가 `/api/`로 이동했다. 인증된 앱 UI가 `/app/`로 이동했다. 세 개의 동작, 세 개의 명확한 캐싱 정책, 모호함 제로.

"좀 리팩토링이네요," 그가 말했다.

"올바른 구조야," Priya가 말했다. "결국 필요했을 거야."

**Origin Access Control: CloudFront로 S3 보안**

S3 버킷에 CloudFront를 통해서만 제공되어야 하는(직접이 아닌) 비공개 콘텐츠가 포함되어 있다면, **Origin Access Control(OAC)**을 사용하여 S3가 CloudFront에서 오지 않는 요청을 거부하도록 할 수 있다.

이렇게:

- `d1234abcd.cloudfront.net/image.jpg` → 제공됨(CloudFront가 권한을 갖고 있다)
- `nimbus-assets.s3.amazonaws.com/image.jpg` → 차단됨(직접 S3 접근 거부됨)

콘텐츠는 캐시 규칙과 보안 설정이 적용된 배포를 통해서만 접근 가능하다.

**오래된 사진 사고**

레스토랑 112 — 이스트사이드의 콜롬비아 음식점 — 가 목요일 아침 지원팀에 이메일을 보냈다. 고객이 주인이 이틀 전에 새것을 업로드했는데도 레스토랑의 히어로 사진이 여전히 이전 가게 정면을 보여준다고 불평했다.

Leo가 CloudFront 배포 설정을 열었다.

`/images/*`에 대한 동작은 TTL이 7일이었다. 레스토랑 파트너 포털이 이틀 전에 새 사진을 업로드하여, 같은 S3 키 경로의 파일을 교체했다: `restaurant-112/hero.jpg`. 이전 파일은 S3에서 사라졌다. 하지만 CloudFront는 지난 7일 내에 그것을 가져온 모든 엣지 로케이션에서 여전히 캐시에서 그것을 제공하고 있었다.

"우리가 오리진에서 콘텐츠를 바꿨어요," Leo가 말했다. "하지만 CloudFront는 그것을 몰라요. 캐시된 복사본을 갖고 있고 7일 동안 확인하지 않을 거예요."

"제가 이미 배포했어요 — 아." 그는 S3 파일을 교체하면 CloudFront 캐시가 자동으로 새로 고쳐질 것이라고 가정했다. 그렇지 않다. CloudFront에는 S3 키의 콘텐츠가 바뀌었다는 것을 감지할 메커니즘이 없다 — 단순히 TTL이 만료될 때까지 캐시한 것을 제공한다.

두 가지 옵션:

**옵션 하나: 무효화.** CloudFront에 `/images/restaurant-112/hero.jpg`에 대한 무효화 요청을 보낸다. CloudFront가 모든 엣지 로케이션에서 그 경로를 오래된 것으로 표시한다. 그 경로에 대한 다음 요청이 S3에서 신선한 콘텐츠를 가져온다. 비용: 매달 처음 1,000개의 무효화 경로는 각각 무료; 그 이상은, *경로당* $0.005. 하나의 파일에는, 무료. 대량 업데이트 중 수천 개의 파일을 무효화하는 데는, 비용이 쌓인다.

**옵션 둘: 버전화된 파일명.** `hero.jpg` 대신, 파일 이름을 `hero-v2.jpg`로 한다. 데이터베이스의 참조를 업데이트한다. CloudFront에 `hero-v2.jpg`에 대한 캐시된 엔트리가 없다 — 첫 번째 요청이 S3에서 그것을 가져오고, 사용자가 즉시 그것을 본다. 이전 `hero.jpg`는 캐시된 채로 남지만 더 이상 어디에서도 참조되지 않는다. 7일 후 자연스럽게 만료된다.

"사용자가 업로드한 콘텐츠에는," Priya가 말했다. "버전화된 이름이 올바른 패턴이야. 파일명에 해시나 타임스탬프를 추가해. 모든 새 업로드가 새 캐시 엔트리야. 무효화 비용 없음, 오래된 콘텐츠 없음."

Leo가 파트너 포털을 업데이트했다. 새 업로드는 이제 `hero-{timestamp}.jpg`로 저장될 것이다. 데이터베이스 레코드가 새 경로로 업데이트됐다. 이전 캐시된 경로는 무관했다.

"배포 케이스는요?" Maya가 물었다. "앱의 새 버전을 푸시하고 JavaScript가 바뀔 때."

"같은 원칙," Priya가 말했다. "Webpack 같은 빌드 도구는 해시된 파일명을 출력해: `app.a3b9c2d4.js`. 새 버전을 배포하면 해시가 바뀌어: `app.f7e1b3c5.js`. CloudFront가 둘 다 캐시에서 제공해 — 이전 사용자는 이전 파일을, 새 사용자는 새 파일을 받아. 무효화 없음, 조율 문제 없음."

"HTML 페이지가 현재 해시를 참조해요," Leo가 말했다. "그래서 새 사용자가 새 JS 해시를 가진 새 HTML을 받고, CDN이 올바른 파일을 제공해요."

"표준 관행이야," Priya가 확인했다.

**실제 수치로 본 지연 시간**

Tom이 세 도시에서 지연 시간 측정을 실행하고 있었다.

| 위치 | CloudFront 없이 | CloudFront 있이 | 개선 |
|---|---|---|---|
| 시애틀 | 15ms | 12ms | 20% |
| 뉴욕 | 80ms | 10ms | 88% |
| 상파울루 | 290ms | 35ms | 88% |
| 도쿄 | 260ms | 28ms | 89% |

"개선은 물리학 문제가 가장 나쁜 곳에서 가장 커," Tom이 관찰했다. "상파울루에서 오리건은 200밀리초가 넘어. 그건 4분의 1초가 넘어, 단지 대화를 시작하는 데."

"그리고 콘텐츠는 두 번째에는 절대 상파울루에 도달하지 않아," Leo가 말했다. "상파울루의 첫 번째 사용자가 오리건에서 가져와서 로컬에 캐시해. 그 후의 모든 사용자가 35밀리초를 받아."

"상파울루의 첫 번째 사용자가 비용을 치르네," Tom이 말했다. "다른 모든 사람이 이득을 보고."

"그게 CDN이 작동하는 방식이야," Priya가 말했다. "첫 번째 요청이 캐시를 채워. 그 후의 모든 캐시 히트는 거의 무료야."

글로벌 제품에 대한 함의는 상당하다. CloudFront 없이, 히어로 이미지에 260밀리초를 기다리는 도쿄의 사용자는 물리학 때문에 기다리는 것이다 — 광섬유 케이블과 빛의 속도. CloudFront로, 그 이미지의 복사본을 도쿄에 두면, 물리학 문제가 본질적으로 사라진다.

**여러 오리진: ALB와 S3 함께**

"우리 이미지는 S3에, API는 로드 밸런서에 있어요," Maya가 말했다. "두 개의 CloudFront 배포가 필요해요?"

"아니," Leo가 말했다. "하나의 배포, 여러 오리진."

단일 CloudFront 배포가 다른 URL 패턴을 다른 오리진으로 라우팅할 수 있다. 이것이 멀티 오리진 패턴이다:

```
eatnimbus.com/*         → 오리진: us-west-2의 ALB (동적 콘텐츠)
eatnimbus.com/images/*  → 오리진: S3 버킷 (정적 이미지)
eatnimbus.com/static/*  → 오리진: S3 버킷 (CSS, JS, 폰트)
```

CloudFront는 동작을 구체성 순서로 평가한다. `/images/hero.jpg`에 대한 요청은 `/images/*` 동작에 일치하고 S3로 간다. `/api/orders`에 대한 요청은 `/*` 포괄에 일치하고 ALB로 간다.

이점: 하나의 도메인, 하나의 SSL 인증서, 하나의 CloudFront 배포, 여러 백엔드. 사용자는 통합된 도메인을 본다. 라우팅이 그들에게 보이지 않는다.

운영 세부사항이자 보장된 시험 사실이기도 한 것: 그 SSL 인증서는 AWS Certificate Manager(ACM)에서 오고, **CloudFront가 사용하는 인증서는 `us-east-1`에서 요청되거나 가져와져야 한다** — 오리진이 어디 사는지와 무관하게. CloudFront는 컨트롤 플레인이 us-east-1에 사는 글로벌 서비스다; us-west-2에 있는 인증서는 그냥 배포의 드롭다운에 나타나지 않는다. (ALB 같은 리전 서비스의 경우, 인증서는 ALB 자체 리전에 산다.)

"그리고 ALB는 공개 facing이 아니죠?" Priya가 물었다.

"CloudFront만 ALB와 통신해요," Leo가 말했다. "ALB의 보안 그룹을 CloudFront의 관리형 접두사 목록으로 제한해요. 인터넷에서 ALB로의 직접 연결은 차단돼요."

"그러니까 애플리케이션에 도달하는 유일한 방법은 CloudFront를 통하는 거네."

"그건 WAF 규칙, SSL 종료, DDoS 보호가 우리에게 도달하기 전에 모든 트래픽에 적용된다는 거예요."

**CloudFront Functions vs Lambda@Edge**

"엣지에서 URL을 다시 작성해야 한다면 무엇을 할지 생각해봤어?" Priya가 물었다. "또는 모든 응답에 보안 헤더를 추가하는 것?"

"그걸 애플리케이션에서 할 수 없어요?" Leo가 물었다.

"할 수 있어. 하지만 그것이 엣지에서 일어나면 — CloudFront가 캐시에서 제공하기 전에 — 오리진으로의 왕복을 절약해."

CloudFront는 엣지에서 코드를 실행하기 위한 두 가지 메커니즘을 지원한다:

**CloudFront Functions**는 모든 엣지 로케이션에서 실행되는 가벼운 JavaScript 함수다. 서브 밀리초 시간에 실행되고, 초당 수백만 요청을 처리하며, 간단한 변환을 위해 설계됐다: URL 다시 쓰기, 헤더 조작, 쿼리 문자열 정규화, 간단한 리디렉션. 뷰어 요청과 뷰어 응답(사용자 관점에서 캐시 전후)에서 실행될 수 있다. 네트워크 호출을 할 수 없다. 비용: 백만 호출당 $0.10.

**Lambda@Edge**는 실제 Lambda 함수를 CloudFront의 리전 엣지 로케이션(모든 pop이 아니라, 전 세계 수십 개의 주요 곳)에서 실행한다. Lambda@Edge는 네트워크 호출을 하고, 데이터베이스에 접근하고, 동적 응답을 생성하고, 복잡한 인증 로직을 할 수 있다. 뷰어 요청, 오리진 요청, 오리진 응답, 뷰어 응답에서 실행된다 — 요청 수명 주기에서 네 개의 개입 지점을 준다. 비용: CloudFront Functions보다 높음, 요청과 기간당 청구.

정신 모델:

| 사용 사례 | 도구 |
|---|---|
| `/old-path`를 `/new-path`로 다시 쓰기 | CloudFront Functions |
| `Strict-Transport-Security` 헤더 추가 | CloudFront Functions |
| 캐시 조회 전 쿼리 문자열 정규화 | CloudFront Functions |
| A/B 테스트: 뷰어 요청에 테스트 쿠키 할당 | CloudFront Functions |
| A/B 테스트: 사용자의 10%를 다른 오리진으로 라우팅 | Lambda@Edge (오리진 요청 — CloudFront Functions는 오리진을 바꿀 수 없음) |
| JWT 토큰 인증(암호 라이브러리 필요) | Lambda@Edge |
| 엣지에서 데이터베이스로부터 개인화된 콘텐츠 가져오기 | Lambda@Edge |
| 엣지에서 온디맨드로 이미지 썸네일 생성 | Lambda@Edge |

Nimbus의 경우: 그들은 CloudFront Function을 사용하여 모든 응답에 보안 헤더를 추가했다 — `Strict-Transport-Security`, `X-Content-Type-Options`, `X-Frame-Options`. 스물네 줄의 JavaScript. 서브 밀리초 실행. 오리진 왕복 불필요.

"그 함수를 작성하는 것보다," Leo가 말했다. "주니어 엔지니어에게 헤더를 설명하는 게 더 오래 걸릴 거예요."

**가격 클래스: 어떤 엣지 로케이션을 선택할지**

"이게 대규모에서 얼마나 드는지 생각해봤어?" Tom이 CloudFront 가격 페이지를 스크롤하며 물었다.

"그게 한 달에 얼마나 들지?"는 여기서 기술적으로 두 가지 질문이었다. 첫째: CloudFront가 무엇을 청구하는가? 둘째: 세계의 모든 엣지 로케이션이 필요한가?

CloudFront 데이터 전송 가격은 리전에 따라 다르다. 북미와 유럽의 엣지 로케이션에서 제공되는 트래픽이 가장 저렴하다. 남미, 아시아 태평양, 호주, 인도의 트래픽은 더 비싸다 — 거기 인프라가 더 비싸기 때문에.

AWS는 배포에 대해 **가격 클래스**를 선택하게 한다:

- **가격 클래스 All**: 전 세계 모든 엣지 로케이션을 사용. 어디서나 최고의 성능. 북미와 유럽 외 리전에 대해 가장 높은 데이터 전송 비용.
- **가격 클래스 200**: 대부분의 엣지 로케이션(북미, 유럽, 아시아, 중동, 아프리카)을 사용. 가장 비싼 남미와 일부 오세아니아 로케이션을 제외.
- **가격 클래스 100**: 북미와 유럽 엣지 로케이션만 사용. 가장 저렴. 상파울루, 도쿄, 시드니의 사용자도 여전히 제공받지만 — 가장 가까운 곳이 아니라 북미나 유럽 엣지에서.

"그러면 가격 클래스 100을 선택하면," Tom이 말했다. "상파울루의 사용자가... 마이애미? 뉴욕?에서 제공받겠네요."

"가장 가까운 포함된 엣지가 어디든. 오리건으로 직접 230밀리초 대신 아마 50밀리초," Priya가 말했다. "여전히 의미 있는 개선. 가격 클래스 All만큼 좋지는 않아."

"그리고 비용 차이는?"

"남미에서의 데이터 전송은 북미의 약 두 배 비용이야. 아직 트래픽을 구축 중인 스타트업에는, 가격 클래스 200이 합리적인 타협이야 — 가격 클래스 All보다 낮은 비용으로 아시아와 유럽을 얻고, 대부분의 사용자가 커버돼."

"200으로 시작해," Tom이 말했다. "각 리전의 실제 트래픽 데이터가 있으면, All이 가치 있는지 결정할 거야."

올바른 가격 클래스는 사용자가 어디 있는지에 달려 있다. 남미에 사용자가 없으면, 남미 엣지 로케이션에 지불하는 것은 순수 비용이다. 수익의 20퍼센트가 브라질에서 오면, 가격 클래스 All의 성능 개선이 아마 스스로 값을 한다.

**캐시 키 설계**

"두 다른 사용자가 같은 URL을 요청하지만 다른 콘텐츠를 받으면 무슨 일이 일어나는지 생각해봤어?" Priya가 물었다.

Leo가 그것에 대해 생각했다. "개인화된 페이지."

"또는 언어별 페이지. 또는 모바일 대 데스크톱 버전. 또는 쿠키에 따라 다른 페이지."

기본으로, CloudFront는 URL 경로만 캐시 키로 사용한다. `/browse`에 대한 두 요청은 사용자의 언어 선호, 기기 유형, 또는 세션 쿠키와 무관하게 같은 캐시된 응답을 받는다.

애플리케이션이 쿼리 문자열, 헤더, 또는 쿠키를 기반으로 다른 콘텐츠를 제공하고 — 그 변형을 CloudFront가 별도로 캐시하길 원한다면 — 그 속성을 **캐시 키**에 포함해야 한다.

Nimbus의 경우:

- `/browse?city=miami`는 `/browse?city=boston`과 별도로 캐시되어야 한다 — 다른 레스토랑 목록. 쿼리 문자열을 캐시 키에 포함.
- 모바일 사용자가 다른 레이아웃을 받을 수 있다. 정규화된 기기 유형(`User-Agent` 헤더에서 파생)을 캐시 키에 포함.
- `Accept-Language` 헤더가 페이지가 어떤 언어로 렌더링되는지를 결정한다. 그것을 캐시 키에 포함.

하지만 조심하라. 추가하는 모든 캐시 키 속성이 더 많은 캐시 변형을 만든다. 전체 `User-Agent` 문자열(브라우저 버전, OS 버전, 패치 수준에 따라 다른)을 포함하면, 사실상 캐싱을 망친다 — 모든 사용자가 약간 다른 User-Agent를 가지므로, 모든 요청이 캐시 미스다.

규율: 캐싱 전에 정규화하라. "iPhone 15 Pro Safari 17.4.1"을 "mobile"로 줄여라. 모든 허용된 언어를 실제로 지원하는 두세 개로 줄여라. 응답을 진정으로 바꾸는 것만 포함하라.

"캐시 키가 더 구체적일수록," Leo가 말했다. "히트율이 더 나빠져요."

"그리고 더 일반적일수록," Priya가 말했다. "잘못된 사용자에게 잘못된 콘텐츠를 제공할 가능성이 더 높아져."

"그러니까 캐시 키 설계는 캐싱의 다른 모든 것과 같은 트레이드오프네요."

"응," Priya가 말했다. "항상 같은 트레이드오프야."

## CloudFront가 답이 아닐 때: Global Accelerator

Nimbus 모바일 앱에는 Tom이 두 달 동안 조용히 지켜본 기능이 있었다: 실시간 주문 상태. 고객이 주문을 하면, 앱이 WebSocket을 통해 연결을 유지하고 주방의 주문 관리 화면이 실시간으로 업데이트됐다. 새로고침 버튼 없음. 폴링 없음. 주방이 아이템을 준비됨으로 표시하는 순간 업데이트를 푸시하는 라이브 연결.

"이게 WebSocket을 사용하고 있어요," Tom이 어느 아침 지연 시간 메트릭을 보며 말했다. "상파울루의 사용자에서, 연결 설정이 340밀리초가 걸려요. 뭔가 잘못됐어요."

"CloudFront는 WebSocket 연결을 캐시하지 않아요," Leo가 말했다. "그것들을 프록시해요 — 오리진으로 통과시켜요. 캐싱 이점 없음."

"맞아요. 그럼 왜 여전히 느려요?"

"WebSocket이 여전히 상파울루에서 오리건의 우리 서버로 공개 인터넷을 통해 이동하기 때문이에요," Leo가 말했다. "CloudFront가 도움이 돼요. TLS 핸드셰이크를 엣지에서 종료하고 그런 다음 AWS의 백본을 오리진으로 사용하니까요. 하지만 지속적인 WebSocket 연결의 경우, 그건 여전히 장거리 연결이에요."

"정확히 이 문제를 위한 서비스가 있어," Priya가 말했다.

**AWS Global Accelerator**는 CDN이 아니다. 아무것도 캐시하지 않는다. 엣지 로케이션에서 콘텐츠를 제공하지 않는다. 그것이 하는 일은 모든 AWS 엣지 로케이션에서 동시에 전 세계적으로 광고되는 두 개의 정적 Anycast IP 주소를 주는 것 — 그런 다음 사용자의 트래픽을 공개 인터넷 대신 AWS의 프라이빗 백본을 통해 라우팅하는 것이다.

상파울루의 고객이 Nimbus 앱을 열면, 그들의 기기가 가장 가까운 AWS 엣지 로케이션(상파울루 자체에 있을 수도)에 연결한다. 그 엣지 로케이션에서, 트래픽이 AWS의 프라이빗하고, 모니터링되고, 최적화된 광섬유 네트워크를 통해 오리건의 Nimbus 서버로 이동한다 — 패킷이 예측 불가능한 운반자와 라우팅 홉을 통해 튀어 다니는 공개 인터넷을 통해서가 아니라.

공개 인터넷은 지연 시간을 위해 설계되지 않았다. 복원력을 위해 설계됐다 — 패킷이 사용 가능한 어떤 경로든 취할 수 있다. AWS의 백본은 다르게 설계됐다: 직접적이고, 낮은 혼잡이며, AWS의 운영 제어 하에 있다.

Tom이 차이를 벤치마크했다.

| 경로 | 지연 시간 (상파울루에서 오리건) |
|---|---|
| 공개 인터넷 | 340ms |
| Global Accelerator를 통해 | 180ms |

47% 감소. 캐싱에서가 아니라 — 더 나은 네트워크 경로에서.

"그럼 왜 모든 것에 CloudFront를 쓰지 않죠?" Maya가 물었다. "CloudFront가 이미 동적 콘텐츠를 위해 AWS의 백본을 통해 라우팅하잖아요."

"CloudFront는 HTTP와 HTTPS만이야," Priya가 말했다. "WebSocket이 CloudFront와 작동하지만, HTTP 업그레이드를 통해서만. 그리고 우리 프로토콜 중 일부 — 예를 들어 IoT 센서 데이터 — 는 순수 TCP나 UDP야. CloudFront는 그것들을 처리하지 않아. Global Accelerator는 프로토콜에 무관해. TCP, UDP, WebSocket, 뭐든. HTTP 요청이 아니라 패킷을 옮겨."

Priya가 보안 문서에 기록한 또 다른 차이가 있었다.

"Global Accelerator는 우리에게 두 개의 정적 Anycast IP를 줘," 그녀가 말했다. "그 IP는 절대 바뀌지 않아. 그건 우리 보안 정책에 그것들을 추가하고, 파트너 화이트리스트에 추가하고, 방화벽 규칙에 추가할 수 있다는 거야. CloudFront의 IP 주소는 시간에 따라 바뀌어 — AWS가 관리하고 고정되지 않아."

"장애 조치는요?" Leo가 물었다.

"즉시," Priya가 말했다. "우리 us-west-2 애플리케이션에 문제가 있으면, Global Accelerator가 사용자가 연결하는 IP 주소를 바꾸지 않고 30초 미만에 us-east-1의 백업으로 트래픽을 이동시킬 수 있어. Route 53을 통한 DNS 장애 조치는 TTL에 따라 60-300초가 걸려. Global Accelerator가 더 빨라."

**CloudFront vs. Global Accelerator — 정신 모델:**

CloudFront는 캐싱으로 전송을 향상시킨다. HTTP/HTTPS를 위해 만들어졌고 콘텐츠가 사용자 가까이 캐시될 수 있을 때 이점이 가장 크다 — 정적 파일, 이미지, JavaScript. 콘텐츠가 캐시될 수 없을 때, CloudFront가 여전히 백본 라우팅을 통해 돕지만, 개선이 더 작다.

Global Accelerator는 라우팅으로 전송을 향상시킨다. 콘텐츠를 옮기지 않는다. 아무것도 캐시하지 않는다. 이점이 모든 패킷에 적용된다 — 캐시되든 아니든, HTTP든 아니든, 정적이든 동적이든. 두 개의 정적 IP가 전 세계적으로 작동한다. 장애 조치가 거의 즉각적이다. CloudFront가 충분하지 않은 사용 사례 — 실시간 WebSocket, UDP 기반 프로토콜, 비-HTTP 트래픽, 고정 IP가 필요한 글로벌 애플리케이션 — 가 Global Accelerator가 올바른 도구인 곳이다.

Tom이 실시간 주문 상태 기능을 위해 Global Accelerator 엔드포인트에 연결하도록 Nimbus 모바일 앱을 업데이트했다. 상파울루에서 WebSocket 연결 설정이 340ms에서 180ms로 떨어졌다. 주방 업데이트가 여전히 즉각적으로 느껴졌다 — 이제, 북미 외 사용자에게, 실제로 그랬기 때문이다.

## 장점과 한계

**CloudFront가 강력한 이유**:

- 100개 이상의 도시에 750개 이상의 접속 지점 — 대부분의 사용자가 <20ms 떨어진 곳에서 콘텐츠를 얻는다
- 첫 번째 캐시 후 한 자리 수 밀리초에 정적 콘텐츠 제공
- 오리진 부하를 크게 줄인다(반복 트래픽이 절대 서버를 건드리지 않는다)
- AWS Shield, WAF, Certificate Manager와 통합
- 용량 계획 불필요 — CloudFront가 자동으로 확장
- 멀티 오리진 배포가 하나의 도메인에서 다른 경로를 다른 백엔드로 라우팅
- CloudFront Functions가 서브 밀리초 지연 시간에 가벼운 엣지 로직을 처리

**복잡해지는 부분**:

- 캐시된 콘텐츠가 오래될 수 있다 — 캐시 무효화는 비용이 든다(매달 처음 1,000개 무료 경로 후 경로당 $0.005). 대신 버전화된 파일명을 사용하라.
- Cache-Control 헤더가 오리진에서 올바르게 설정되어야 한다 — 실수가 오래된 콘텐츠를 유발한다
- 동적 콘텐츠는 라우팅 최적화의 이점을 얻지만 캐싱의 이점은 얻지 못한다
- 캐시 동작(어디서, 얼마나 오래 캐시됨)을 디버깅하려면 여러 레이어 이해가 필요하다: 오리진 헤더, CloudFront TTL 설정, 동작 규칙
- CloudFront를 통한 데이터 전송은 비용이 들지만, 표준 데이터 전송보다 적다
- 캐시 키 설계는 신중한 생각이 필요하다 — 너무 구체적이면 캐싱을 망치고, 너무 일반적이면 잘못된 콘텐츠를 제공한다

## 요약

CloudFront는 물리학을 바꾸지 않았다. 빛은 여전히 같은 속도로 이동한다. 하지만 답이 사는 곳을 바꿨다 — 그리고 대부분의 사용자에게, 답은 이제 수백 밀리초가 아니라 몇 밀리초 떨어진 곳에 있었다. 배포 후 캐시 히트율: 83%. 그것은 백만 건의 요청 중 83만 건이 오리진 서버에 전혀 도달하지 않았다는 것을 의미했다. 상파울루의 사용자가 290밀리초에서 35밀리초로 갔다. 도쿄의 사용자가 260에서 28로.

- **CDN**은 사용자 가까이 엣지 로케이션에 콘텐츠의 복사본을 캐시한다 — 지연 시간과 오리진 부하를 줄인다.
- **CloudFront**는 AWS의 CDN으로, 전 세계 750개 이상의 접속 지점이 있다.
- 캐시 미스는 **오리진**(S3, ALB, EC2)에서 가져온다. 캐시 히트는 엣지에서 제공된다 — 수백 밀리초가 아닌 밀리초.
- **동작**을 통해 다른 URL 패턴에 다른 캐싱 규칙을 설정할 수 있다. 하나의 배포가 `/images/*`를 S3에서, `/*`를 ALB에서 제공할 수 있다.
- 동적 콘텐츠는 캐시되지 않지만, CloudFront는 여전히 AWS의 프라이빗 백본 네트워크를 통해 성능을 향상시킨다.
- 무효화 대신 버전화된 파일명(예: `hero-v2.jpg`)을 사용하여 **오래된 콘텐츠를 피하라** — 더 저렴하고 더 안정적이다.
- **CloudFront Functions**는 가벼운 엣지 로직(헤더 조작, URL 다시 쓰기)을 서브 밀리초 속도로 처리한다. **Lambda@Edge**는 네트워크 호출이 필요한 더 무거운 처리를 처리한다.
- **가격 클래스**를 통해 어떤 엣지 로케이션이 트래픽을 제공하는지를 — 따라서 데이터 전송 비용을 — 제어할 수 있다.
- **캐시 키 설계**는 어떤 요청 속성이 별도의 캐시된 변형을 만드는지를 결정한다. 더 구체적인 키 = 낮은 히트율. 덜 구체적 = 잘못된 콘텐츠를 제공할 위험.

## 시험 팁

*SAA-C03 도메인: 고성능 아키텍처 설계(도메인 3, 태스크 3.4)*

- **CloudFront + S3**: 전 세계적으로 정적 웹사이트를 제공하기 위한 고전적인 시험 패턴. S3 버킷을 오리진으로, CloudFront를 CDN으로, 직접 S3 접근을 방지하기 위한 Origin Access Control.
- **엣지 로케이션 vs. 리전 vs. AZ**: 엣지 로케이션이 더 많고 캐싱/CDN 목적으로만 존재한다. AZ(컴퓨팅을 실행하는)와 같지 않다.
- **캐시 무효화**: CloudFront가 신선한 콘텐츠를 강제로 가져오도록 `/images/*` 무효화를 만든다. 비용이 든다 — 시험은 비용 효율적인 대안을 물을 수 있다: 버전화된 URL(`image.jpg` 대신 `image-v2.jpg`)이 자연스럽게 캐시를 우회한다.
- **TTL 제어**: 오리진의 `Cache-Control: max-age=3600`은 1시간 캐시 TTL을 설정한다. CloudFront가 이 헤더를 따른다. 최소 TTL, 최대 TTL, 기본 TTL도 배포 동작에서 설정할 수 있다.
- **CloudFront Functions vs. Lambda@Edge**: CloudFront Functions는 가벼운 요청/응답 조작을 위해 엣지에서 실행된다(서브 밀리초). Lambda@Edge는 더 무거운 처리를 위해 리전 엣지 로케이션에서 Lambda 코드를 실행한다. 시험은 사용 사례 복잡성으로 그것들을 구분한다. CloudFront Functions는 네트워크 호출을 할 수 없다; Lambda@Edge는 할 수 있다.
- **서명된 URL과 서명된 쿠키**: CloudFront를 통해 콘텐츠에 접근할 수 있는 사람을 제어한다. 서명된 URL은 특정 파일에 접근 권한을 제공하고; 서명된 쿠키는 여러 파일에 접근 권한을 제공한다. 시험은 "유료 구독자 콘텐츠"에 이것들을 사용한다.
- **가격 클래스**: 시험은 글로벌 청중 대 북미/유럽 청중에 대해 어떤 가격 클래스를 선택할지 물을 수 있다. 가격 클래스 All = 최고 성능, 최고 비용. 가격 클래스 100 = 북미와 유럽만, 최저 비용.
- **캐시 키**: 기본 캐시 키는 URL이다. 쿼리 문자열, 헤더, 또는 쿠키를 캐시 키에 추가하면 별도의 캐시된 변형을 만든다 — 하지만 캐시 미스율을 높인다. 시험은 콘텐츠가 쿼리 매개변수로 다른 시나리오를 제시하고 캐싱을 어떻게 설정할지 물을 수 있다.
- **오리진 장애 조치**: CloudFront는 기본과 보조 오리진을 가진 오리진 그룹을 지원한다. 기본 오리진이 5xx 오류를 반환하면, CloudFront가 자동으로 보조로 재시도한다. Route 53 장애 조치와 다르다 — 이것은 단일 CloudFront 배포 내에 있다.
- **멀티 오리진 동작**: 단일 배포가 `/images/*`를 S3로, `/*`를 ALB로 라우팅할 수 있다. 시험은 이것을 "두 배포 없이 하나의 도메인에서 정적 및 동적 콘텐츠를 제공하는 방법"으로 제시할 수 있다.
- **CloudFront vs. Global Accelerator**: CloudFront = HTTP/HTTPS CDN, 엣지 로케이션에 콘텐츠 캐시, 오리진 부하 감소, 정적 및 캐시 가능 콘텐츠에 최적. Global Accelerator = 모든 TCP/UDP 프로토콜, 아무것도 캐시 안 함, AWS의 프라이빗 백본을 통해 트래픽 라우팅, 2개의 정적 Anycast IP 제공, 거의 즉각적인 리전 장애 조치 지원. 시험 트리거: "비-HTTP 트래픽의 지연 시간 개선" 또는 "글로벌 애플리케이션을 위한 정적 IP" 또는 "글로벌 사용자를 위한 WebSocket 성능" 또는 "DNS보다 빠른 리전 장애 조치" → Global Accelerator. "낮은 지연 시간으로 전 세계적으로 정적 파일 제공" → CloudFront.

## 연습 문제

**연습 1 — 회상**

CloudFront 캐시 히트와 캐시 미스의 차이를 설명하라. 각 경우에 무슨 일이 일어나는가?

*(힌트: 콘텐츠가 어디서 오는지, 두 경우에 응답 시간이 어떻게 다른지 생각해보라.)*

**연습 2 — SAA-C03 시나리오**

*시나리오*: 소프트웨어 회사가 S3 버킷에서 전 세계 고객에게 대용량 설치 파일(각 ~2GB)을 배포한다. 아시아 고객의 다운로드 속도가 느리다. 팀은 S3 버킷을 여러 리전에 복제하지 않고 성능을 향상시키길 원한다. 또한 결제 고객만 설치 파일을 다운로드할 수 있도록 해야 한다.

다음 중 이 요구사항을 가장 잘 충족하는 솔루션은?

A) 버킷에서 S3 Transfer Acceleration을 활성화하고 결제 고객을 위한 사전 서명된 URL 생성  
B) S3 버킷을 오리진으로 사용하는 CloudFront를 사용하고, Origin Access Control을 활성화하고, 결제 고객에게 CloudFront Signed URL 사용  
C) 각 AWS 리전에 S3 버킷을 만들고 가장 가까운 버킷으로 고객을 안내하기 위해 Route 53 지리적 위치 라우팅 사용  
D) 각 리전에 설치 파일을 제공하는 EC2 인스턴스가 있는 Application Load Balancer 사용

**힌트 1**: 요구사항은 버킷을 복제하지 않고 전 세계 성능을 향상시키는 것이다. 어떤 옵션이 여러 버킷을 필요로 하지 않는가?

**힌트 2**: CloudFront를 통해 콘텐츠에 접근할 수 있는 사람을 구체적으로 제어하는 어떤 서비스인가?

**힌트 3**: S3 Transfer Acceleration은 S3로의 장거리 업로드에 최적화되어 있다. 전 세계 최종 사용자에게 S3에서 콘텐츠를 *배포*하는 것을 위해, CloudFront가 올바른 도구다.

**정답**: B

**설명**: CloudFront는 첫 번째 다운로드 후 전 세계적으로 엣지 로케이션에 설치 파일을 캐시한다. 같은 리전에서의 후속 다운로드는 엣지에서 온다 — us-west-2의 S3에서 태평양을 가로지르는 것보다 훨씬 빠르다. Origin Access Control은 S3 버킷이 CloudFront를 통해서만 접근 가능하도록 한다. 서명된 URL은 결제 고객에게 접근을 제한한다.

**왜 A가 아닌가?** S3 Transfer Acceleration은 S3*으로의* 장거리 업로드에 최적화되어 있다 — 전 세계 대상에게 S3*에서* 콘텐츠를 배포하는 것이 아니다. 그것을 위해서는, CloudFront가 올바른 도구다. 사전 서명된 URL은 접근을 제어하지만 전 세계 성능을 향상시키지 않는다.

**왜 C가 아닌가?** 리전당 S3 버킷을 만드는 것은 성능을 위해 작동하지만 복제를 피하라는 요구사항에 모순된다. 또한 버킷 전체에 걸쳐 데이터 동기화 전략이 필요하다.

**왜 D가 아닌가?** 각 리전에 EC2 인스턴스 뒤의 로드 밸런서는 CloudFront보다 훨씬 더 비싸고 여러 리전의 서버 관리가 필요하다.

*SAA-C03 도메인: 고성능 아키텍처 설계 — 태스크 3.4*
