# 13장: 어디서나 빠르게

버지니아에서 시애틀의 전화기로 이동하는 사진은 약 4,400킬로미터의 광섬유 케이블을 가로지른다. 빛의 속도의 3분의 2로, 그것은 어느 것도 피할 수 없는 순수한 물리학으로 약 25밀리초다.

그런 다음 왕복을 추가하라. 처리 시간을 추가하라. 브라우저가 아직 렌더링을 시작하지 않았는데 이미 80밀리초가 지나갔다.

`eatnimbus.com`이 라이브였다. Leo가 서부 해안 사용자의 지연 시간 메트릭을 확인했다: 요청당 80-100밀리초. 그 수치가 작게 들릴 수 있지만, 복잡하다.

메뉴 로드: 90ms. 레스토랑 목록 로드: 80ms. 레스토랑 사진 로드: 200ms(이미지는 크다). 사용자가 주문을 할 수 있기 전의 총 시간: 좋은 연결에서도 반초 이상.

"물리학이 문제야," Leo가 말했다. "서버가 버지니아에 있어. 사용자는 서부 해안에 있고."

"그러면 서버를 서부 해안으로 이동시켜," Tom이 말했다.

"돈이 들어요."

"얼마나?"

"많이요. 그리고 완전히 새로운 문제를 만들어요: 동부 해안 데이터베이스와 서부 해안 데이터베이스를 동기화 상태로 유지하는 것."

Priya가 노트북에서 고개를 들었다. "아니면 서버를 이동시키지 않아요. *콘텐츠*를 이동시키는 거죠."

**사전 비축 창고 비유**

소매업체로서의 Amazon을 상상해보라, 클라우드 회사가 아닌. 그들에게는 모든 제품을 갖춘 하나의 거대한 창고가 있다. 그 하나의 창고에서 모든 주문을 배송하면, 먼 도시의 고객들이 며칠을 기다릴 것이다.

대신, Amazon은 주요 인구 중심지 근처에 주문 처리 센터를 갖고 있다. 제품이 인기 있으면, 그 로컬 창고에 미리 비축한다. 시애틀의 고객이 책을 주문하면, 버지니아에서가 아니라 로컬 주문 처리 센터에서 배송된다.

이것이 **콘텐츠 전송 네트워크(CDN)**다: 사용자 가까이에 콘텐츠의 복사본을 캐시하는 지리적으로 배포된 서버 네트워크.

시애틀의 사용자가 홈페이지를 요청하면, CDN이 시애틀의 서버에서 그것을 제공한다. 버지니아가 아니라. 요청이 국가를 가로지르지 않는다.

**CloudFront 소개**

Amazon CloudFront는 AWS의 CDN이다. **엣지 로케이션** — 세계 전역 도시에 위치한 캐싱 서버 — 의 글로벌 네트워크를 통해 운영된다. 이 글을 쓰는 시점에, 90개 이상의 도시에 500개 이상의 엣지 로케이션이 있다.

CloudFront를 설정할 때, **오리진**을 지정한다: 실제 콘텐츠의 소스. 오리진은 다음이 될 수 있다:

- S3 버킷(정적 파일: 이미지, CSS, JavaScript, PDF)
- Application Load Balancer(애플리케이션의 동적 콘텐츠)
- EC2 인스턴스
- 인터넷 어디의 HTTP 서버

CloudFront가 오리진 앞에 앉는다. 요청이 가장 가까운 엣지 로케이션에 들어온다. 엣지에 캐시된 콘텐츠가 있으면, 즉시 반환한다. 없으면(*캐시 미스*), 오리진에서 가져오고, 캐시하고, 반환한다.

**CloudFront 캐싱 작동 방식**

어떤 콘텐츠의 첫 번째 요청은 항상 캐시 미스다 — 오리진으로 간다. 모든 후속 요청은 엣지 로케이션의 캐시에 접근한다.

Nimbus의 경우, 메뉴 사진이 완벽한 CloudFront 후보다. 레스토랑 사진은 드물게 변경된다(레스토랑이 프로필을 업데이트할 때 정도). CloudFront를 사용하면:

1. 시애틀의 사용자가 `images.eatnimbus.com/restaurant-047/photo.jpg`를 요청
2. CloudFront가 시애틀의 엣지 로케이션을 확인 — 아직 캐시되지 않음(캐시 미스)
3. CloudFront가 us-east-1의 S3에서 가져옴(~80ms)
4. CloudFront가 사진을 시애틀 엣지 로케이션에 저장
5. 시애틀의 다음 사용자가 같은 사진을 요청
6. CloudFront가 로컬 엣지 캐시에서 제공(~5ms)

첫 번째 요청에는 동일한 80ms 페널티. 하지만 같은 도시에서의 1,000번째 요청은 5밀리초.

**Cache-Control 헤더**와 CloudFront의 **TTL 설정**은 콘텐츠가 엣지에 얼마나 오래 캐시되는지를 결정한다. 이미지 파일은 몇 시간 또는 며칠 동안 캐시될 수 있다. 더 자주 변경되는 HTML 페이지는 몇 분 또는 몇 초 동안 캐시될 수 있다.

**동적 콘텐츠: 캐싱 이상의 CloudFront**

"하지만 우리 API 응답은요?" Leo가 물었다. "그것들은 동적이야 — 사용자마다, 요청마다 바뀌어. 주문 내역 페이지는 캐시할 수 없잖아."

맞다. 하지만 CloudFront는 여전히 동적 콘텐츠를 돕는다.

콘텐츠가 캐시될 수 없더라도, CloudFront는 엣지 로케이션에서 오리진으로의 요청을 AWS의 프라이빗 백본 네트워크 — 전 세계 AWS 인프라를 연결하는 고속 광섬유 — 를 통해 라우팅한다. 이것이 트래픽이 여러 운반자를 통해 튀어 다닐 수 있는 공개 인터넷을 통해 라우팅하는 것보다 더 빠르고 안정적이다.

결과: 동적 요청은 CloudFront를 통해 공개 인터넷을 통해 직접 오리진으로 가는 것보다 여전히 20-40% 더 빠르다. 캐싱 때문이 아니라, 네트워크 경로 때문에.

추가로, CloudFront는 다음을 제공한다:

**SSL/TLS 종료**: CloudFront가 엣지에서 HTTPS를 처리한다. 사용자와 CloudFront 사이의 연결이 암호화된다. CloudFront는 내부적으로 HTTP(오리진 부하 줄이기)나 HTTPS(엔드-투-엔드 암호화)로 오리진에 연결할 수 있다.

**DDoS 보호**: CloudFront는 AWS Shield Standard와 통합된다. 수백 개의 엣지 로케이션에 걸쳐 분산된 트래픽은 공격이 오리진을 강타하는 대신 엣지에서 흡수된다는 것을 의미한다.

**지오 제한**: 특정 국가에서의 접근을 차단. Nimbus가 특정 시장에서만 운영하도록 허가되었다면, CloudFront가 요청이 서버에 도달하기 전에 엣지에서 그것을 시행할 수 있다.

**CloudFront 동작: 세밀한 캐싱 규칙**

CloudFront 배포는 URL 패턴을 기반으로 한 라우팅 규칙인 여러 **동작**을 가질 수 있다.

Nimbus의 경우:

- `/images/*` → 엣지에서 7일 동안 캐시(사진은 자주 변경되지 않는다)
- `/static/*` → 엣지에서 30일 동안 캐시(버전화된 파일명을 가진 CSS와 JavaScript)
- `/api/*` → 캐시하지 않음; 로드 밸런서로 직접 전달
- `/*` → 5분 동안 캐시(HTML 페이지)

이것이 CloudFront를 스마트하게 만든다: 안정적인 것을 공격적으로 캐시하고, 동적인 것을 통과시킨다.

**Origin Access Control: CloudFront로 S3 보안**

S3 버킷에 CloudFront를 통해서만 제공되어야 하는(직접이 아닌) 비공개 콘텐츠가 포함되어 있다면, **Origin Access Control(OAC)**을 사용하여 S3가 CloudFront에서 오지 않는 요청을 거부하도록 할 수 있다.

이렇게:

- `d1234abcd.cloudfront.net/image.jpg` 제공됨(CloudFront가 권한을 갖고 있다)
- `nimbus-assets.s3.amazonaws.com/image.jpg` 차단됨(직접 S3 접근 거부됨)

콘텐츠는 캐시 규칙과 보안 설정이 적용된 배포를 통해서만 접근 가능하다.

## 장점과 한계

**CloudFront가 강력한 이유**:

- 90개 이상의 도시에 엣지 로케이션 — 대부분의 사용자가 <20ms 내에 콘텐츠를 얻는다
- 첫 번째 캐시 후 한 자리 수 밀리초에 정적 콘텐츠 제공
- 반복 트래픽이 절대 서버를 건드리지 않아 오리진 부하를 크게 줄인다
- AWS Shield, WAF, Certificate Manager와 통합
- 용량 계획 불필요 — CloudFront가 자동으로 확장

**복잡해지는 부분**:

- 캐시된 콘텐츠가 오래될 수 있다 — 캐시 무효화는 비용이 든다(1,000개 경로당 $0.005)
- Cache-Control 헤더가 오리진에서 올바르게 설정되어야 한다 — 실수가 오래된 콘텐츠를 유발한다
- 동적 콘텐츠는 라우팅 최적화의 이점을 얻지만 캐싱의 이점은 얻지 못한다
- 캐시 동작(어디서, 얼마나 오래 캐시됨)을 디버깅하려면 여러 레이어 이해가 필요하다: 오리진 헤더, CloudFront TTL 설정, 동작 규칙
- CloudFront를 통한 데이터 전송은 비용이 들지만, 표준 데이터 전송보다 적다

## 요약

- **CDN**은 사용자 가까이 엣지 로케이션에 콘텐츠의 복사본을 캐시하여 지연 시간과 오리진 부하를 줄인다.
- **CloudFront**는 AWS의 CDN으로, 전 세계 500개 이상의 엣지 로케이션이 있다.
- 캐시 미스는 **오리진**(S3, ALB, EC2)에서 가져온다. 캐시 히트는 엣지에서 제공된다 — 수백 밀리초가 아닌 밀리초.
- **동작**을 통해 URL 패턴에 따라 다른 캐싱 규칙을 설정할 수 있다.
- 동적 콘텐츠는 캐시되지 않지만, CloudFront는 여전히 AWS의 프라이빗 백본 네트워크를 통해 성능을 향상시킨다.
- **Origin Access Control**은 직접 S3 접근을 제한한다 — 콘텐츠는 CloudFront를 통해서만 제공된다.
- Shield(DDoS), WAF(애플리케이션 방화벽), ACM(SSL 인증서)과 통합.

## 시험 팁

*SAA-C03 도메인: 고성능 아키텍처 설계(도메인 3, 태스크 3.4)*

- **CloudFront + S3**: 전 세계적으로 정적 웹사이트를 제공하기 위한 고전적인 시험 패턴. S3 버킷을 오리진으로, CloudFront를 CDN으로, 직접 S3 접근을 방지하기 위한 Origin Access Control.
- **엣지 로케이션 vs. 리전 vs. AZ**: 엣지 로케이션이 더 많고 캐싱/CDN 목적으로만 존재한다. AZ(컴퓨팅을 실행하는)와 같지 않다.
- **캐시 무효화**: CloudFront가 신선한 콘텐츠를 강제로 가져오도록 `/images/*` 무효화를 만든다. 비용이 든다 — 시험은 비용 효율적인 대안을 물을 수 있다: 버전화된 URL(`image.jpg` 대신 `image-v2.jpg`)이 자연스럽게 캐시를 우회한다.
- **TTL 제어**: 오리진의 `Cache-Control: max-age=3600`은 1시간 캐시 TTL을 설정한다. CloudFront가 이 헤더를 따른다.
- **CloudFront Functions vs. Lambda@Edge**: CloudFront Functions는 가벼운 요청/응답 조작을 위해 엣지에서 실행된다(서브 밀리초). Lambda@Edge는 더 무거운 처리를 위해 엣지 로케이션에서 Lambda 코드를 실행한다. 시험은 사용 사례 복잡성으로 그것들을 구분한다.
- **서명된 URL과 서명된 쿠키**: CloudFront를 통해 콘텐츠에 접근할 수 있는 사람을 제어한다. 서명된 URL은 특정 파일에 접근 권한을 제공하고; 서명된 쿠키는 여러 파일에 접근 권한을 제공한다. 시험은 "유료 구독자 콘텐츠"에 이것들을 사용한다.

**연습 1 — 회상**

CloudFront 캐시 히트와 캐시 미스의 차이를 설명하라. 각 경우에 무슨 일이 일어나는가?

**연습 2 — 시험 연습**

*시나리오*: 소프트웨어 회사가 S3 버킷에서 전 세계 고객에게 대용량 설치 파일(각 ~2GB)을 배포한다. 아시아 고객의 다운로드 속도가 느리다. 팀은 S3 버킷을 여러 리전에 복제하지 않고 성능을 향상시키길 원한다. 또한 결제 고객만 설치 파일을 다운로드할 수 있도록 해야 한다.

다음 중 이 요구사항을 가장 잘 충족하는 솔루션은?

A) 버킷에서 S3 Transfer Acceleration을 활성화하고 결제 고객을 위한 사전 서명된 URL 생성  
B) S3 버킷을 오리진으로 사용하는 CloudFront를 사용하고, Origin Access Control을 활성화하고, 결제 고객에게 CloudFront Signed URL 사용  
C) 각 AWS 리전에 S3 버킷을 만들고 가장 가까운 버킷으로 고객을 안내하기 위해 Route 53 지리적 위치 라우팅 사용  
D) 각 리전에 설치 파일을 제공하는 EC2 인스턴스가 있는 Application Load Balancer 사용

**힌트 1**: 요구사항은 버킷을 복제하지 않고 전 세계 성능을 향상시키는 것이다. 어떤 옵션이 여러 버킷을 필요로 하지 않는가?

**힌트 2**: CloudFront를 통해 콘텐츠에 접근할 수 있는 사람을 구체적으로 제어하는 어떤 서비스인가?

**힌트 3**: S3 Transfer Acceleration은 S3로의 장거리 업로드에 최적화되어 있다. 전 세계 최종 사용자에게 S3에서 콘텐츠를 *배포*하는 것을 위해, CloudFront가 올바른 도구다.

**답**: B

**설명**: CloudFront는 전 세계적으로 엣지 로케이션에 설치 파일을 캐시한다. Origin Access Control은 S3 버킷이 CloudFront를 통해서만 접근 가능하도록 한다. 서명된 URL은 결제 고객에게 접근을 제한한다.

**왜 A가 아닌가?** S3 Transfer Acceleration은 S3*으로의* 장거리 업로드에 최적화되어 있다 — 전 세계 대상에게 S3*에서* 콘텐츠를 배포하는 것이 아니다. 사전 서명된 URL은 접근을 제어하지만 전 세계 성능을 향상시키지 않는다.

**왜 C가 아닌가?** 리전당 S3 버킷을 만드는 것은 성능을 위해 작동하지만 복제 없이 라는 요구사항에 모순된다. 또한 버킷 전체에 걸쳐 데이터 동기화 전략이 필요하다.

**왜 D가 아닌가?** 각 리전에 EC2 인스턴스 뒤의 로드 밸런서는 CloudFront보다 훨씬 더 비싸고 여러 리전의 서버 관리가 필요하다.

**연습 3 — 아키텍처 과제** *(선택 사항)*

Nimbus는 비디오 콘텐츠를 추가하길 원한다 — 레스토랑 파트너의 짧은 요리 튜토리얼 비디오. 비디오는 50-500MB가 될 수 있다. 같은 비디오가 게시 후 몇 시간 내에 같은 도시의 수천 명의 사용자에게 시청될 것으로 예상한다.

스토리지와 전송 아키텍처를 설계하라. S3와 CloudFront를 사용하겠는가? 비디오가 캐시되기 전의 첫 번째 요청(콜드 스타트)을 처리하여 지연을 최소화하려면 어떻게 하겠는가? 게시 후 변경되지 않는 비디오에 어떤 캐시 TTL을 설정하겠는가?

## 포스트 크레딧 장면

Priya가 배포 후 CloudFront 메트릭을 지켜봤다.

캐시 히트율: 83%.

"그게 무슨 뜻이야요?" Tom이 물었다.

"우리 사용자의 83%가 us-east-1이 아닌 가까운 엣지 로케이션에서 콘텐츠를 얻고 있다는 거야."

"나머지 17%는요?"

"첫 번째 요청들. 그 엣지 로케이션에서 아직 캐시되지 않은 콘텐츠."

Tom이 메트릭을 응시했다. "그러면 하루에 거의 백만 건의 요청을 CloudFront 엣지 노드에서 제공하고 있어요. 그리고 그 중 170,000개만 실제로 서버에 접근하는 거군요."

"응."

"CloudFront가 없었다면, 서버가 백만 건을 처리해야 했을 거예요."

"각각 전 세계 사용자에게 140-160밀리초씩."

Tom이 뒤로 기대었다. Maya가 그것을 알아봤다 — 실시간으로 비용을 재계산하는 사람의 표정.

"이건 가치가 있어요," 그가 말했다.

Maya가 이미 노트북에 있었다. "다음 주에 플랫폼 팀에서 Soo-Jin과 보안 전문이었던 Rafael이 합류해요. 첫날 전에 IAM에 대한 온보딩을 원해요."

"IAM 고급이요?" Leo가 물었다.

"역할, 정책, 교차 계정 접근. 진짜 내용."
