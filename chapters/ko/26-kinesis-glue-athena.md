# 26장: 모든 것을 이해하기

데이터는 원시적이다: 타임스탬프, 클릭, 이벤트, 숫자. 정보는 데이터가 구성되고, 처리되고, 맥락을 부여받을 때 얻는 것이다. 두 사이의 간격이 이 챕터가 사는 곳이다.

그리고 성장하는 시스템에서, 그 간격은 비용이 빠르게 된다.

Nimbus는 엄청난 양의 데이터를 생성하고 있었다. 모든 주문: 기록됨. 모든 메뉴 보기: 로그됨. 모든 레스토랑 업데이트: 캡처됨. 모든 고객 상호 작용: 추적됨.

Tom에게는 질문이 있었다.

"금요일 가장 바쁜 주문 시간이 언제야?"

Leo가 그를 봤다. "그건 우리 대시보드에 없어요."

"추가할 수 있어?"

"데이터가 DynamoDB에 있어요. 그리고 CloudWatch 로그에. 그리고 분석 내보내기 작업의 S3에서." Leo가 멈췄다. "세 곳에 다른 형식으로."

Maya가 덧붙였다: "그리고 분석 내보내기는 밤에 한 번만 실행돼. 금요일 데이터를 원하면, 토요일 아침까지 기다려야 해."

Tom이 화면을 봤다. "그러면 데이터가 있는데. 그냥 사용할 수 없는 거네."

그 문장이 현대 분석의 절반을 설명한다.

이것이 데이터 엔지니어링 문제다: 데이터가 있지만 필요할 때 분석할 수 있는 형태가 아니다.

**세 가지 다른 문제**

Nimbus의 데이터 문제는 세 가지 차원이 있었다:

**실시간 스트리밍**: 지금 주문이 들어오고 있다. 분당 주문 속도의 라이브 대시보드를 보길 원한다 — 리전별, 레스토랑별. 데이터가 도착하면서 처리되어야 한다.

**데이터 변환**: 데이터가 다양한 시스템에서 S3에 다른 형식(JSON, CSV, Parquet)으로 있다. 분석하기 전에 표준화해야 한다 — 같은 스키마, 같은 형식, 정리됨, 참조 데이터와 조인됨.

**임시 분석**: 데이터가 구성되면, 먼저 데이터베이스에 로드하지 않고 SQL 쿼리를 실행하고 싶다. "지난 30일 동안 매출로 상위 10개 레스토랑을 알려줘." 데이터베이스에 데이터를 로드하지 않고.

이것들은 각각 별개의 문제다. AWS는 각각을 위한 전용 서비스가 있다:

- **Amazon Kinesis**: 실시간 스트리밍 데이터
- **AWS Glue**: 데이터 변환 및 카탈로그
- **Amazon Athena**: S3에서 서버리스 SQL 쿼리

**Amazon Kinesis: 실시간 티커 테이프**

**Amazon Kinesis Data Streams**는 실시간 데이터 스트리밍 서비스다. 생산자가 스트림에 데이터 레코드를 보낸다. 여러 소비자가 각자의 속도로 동시에 스트림에서 읽을 수 있다.

티커 테이프 기계처럼 생각하라: 가격이 지속적으로 인쇄되고, 누구든지 테이프를 읽을 수 있으며, 테이프가 개별 독자를 위해 느려지지 않는다.

Nimbus의 경우, 주문이 들어올 때, 애플리케이션이 Kinesis 스트림에 이벤트를 게시한다: `{ "orderId": "ORD-7741", "restaurantId": "47", "total": 3200, "timestamp": "...", "region": "us-west-2" }`.

이 스트림의 소비자:

- 실시간 대시보드(이벤트가 도착하면서 읽고, 메트릭을 업데이트)
- 사기 감지 Lambda(비정상적인 주문 패턴을 찾음)
- 영구 저장을 위한 S3로의 스트림

**Kinesis Data Streams 개념**:

- **샤드**: 용량의 기본 단위. 하나의 샤드는 1MB/s 쓰기, 2MB/s 읽기를 처리한다.
- **보관 기간**: 데이터가 24시간(기본) ~ 7일 동안 스트림에 남아 있다.
- **시퀀스 번호**: 각 레코드에 시퀀스 번호가 있다. 소비자가 스트림에서 자신의 위치를 추적한다.

**Amazon Data Firehose**(이전 **Kinesis Data Firehose**): S3, Redshift, OpenSearch 같은 대상 사이의 관리형 배달 서비스. 데이터를 자동으로 버퍼링, 압축, 변환, 배달한다.

Nimbus의 경우: Kinesis Data Streams → Amazon Data Firehose → S3(Parquet 형식, 압축됨, 날짜별 파티션됨).

**AWS Glue: 번역가**

S3의 데이터는 원시적이다. 효율적으로 분석하기 전에 다음이 필요하다:

- 거기에 무엇이 있고 스키마가 무엇인지 발견(어떤 열, 어떤 유형)
- 일관된 형식으로 변환
- 다른 데이터셋과 조인
- 불량 레코드, 스키마 변경, 누락 값 처리

**AWS Glue**는 완전히 관리되는 ETL(Extract, Transform, Load) 서비스다. 두 가지 주요 구성 요소가 있다:

**Glue Data Catalog**: S3 데이터를 설명하는 메타데이터 저장소 — 어떤 테이블이 있는지, 어떤 열이 있는지, 데이터 파일이 어디에 있는지. 데이터 레이크를 위한 카드 카탈로그 같다.

**Glue Crawlers**: S3를 스캔하고, 스키마를 추론하고, Data Catalog를 채우는 자동화된 에이전트. S3 버킷에서 크롤러를 실행하면 10분 후에 모든 테이블의 카탈로그가 있다.

**Glue Jobs**: 실제 변환을 수행하는 서버리스 Spark/Python 작업. 변환 로직을 작성하거나(또는 Glue의 시각적 ETL 도구 사용), Glue가 관리된 인프라에서 실행한다.

Nimbus의 경우:

1. Glue Crawler가 S3의 주문 데이터를 스캔 → Glue Data Catalog에 테이블 정의 생성
2. Glue Job이 원시 JSON 주문 이벤트를 깔끔하고, 파티션된 Parquet 형식으로 변환
3. 변환된 데이터가 쿼리 최적화된 레이아웃으로 S3에 다시 기록

**Amazon Athena: 사서**

**Amazon Athena**는 S3 데이터에서 직접 SQL 쿼리를 실행하는 서버리스 대화형 쿼리 서비스다. 프로비저닝할 데이터베이스 없고, 로드할 데이터 없음. 테이블을 정의하거나(또는 Glue Data Catalog 사용), SQL을 작성하면, Athena가 S3 파일에 대해 쿼리를 실행한다.

```sql
SELECT 
    restaurant_id,
    COUNT(*) as order_count,
    SUM(total) as revenue
FROM orders
WHERE year='2024' AND month='01'
GROUP BY restaurant_id
ORDER BY revenue DESC
LIMIT 10;
```

Athena 가격은 쿼리가 얼마나 많은 데이터를 스캔하는지를 기반으로 한다. 많은 리전에서 표준 SQL 쿼리는 스캔된 테라바이트당 $5부터 시작한다. Parquet 형식(컬럼형)을 파티션 프루닝(`WHERE year='2024' AND month='01'`)과 함께 사용하면 Athena가 필요한 파일만 스캔하며, 비용을 극적으로 줄인다.

"30일간의 데이터에 이 쿼리를 실행할 수 있어요," Leo가 말했다. "그리고 잘 저장하면 놀랍도록 낮은 비용이 될 수 있어요."

"우리가 생각할 수 있는 임의의 질문에 대해요?" Tom이 물었다.

"SQL로 표현할 수 있는 모든 질문, S3에 저장한 모든 데이터에 대해요."

Tom이 버려온 모든 데이터의 가치를 실시간으로 재계산하는 표정을 지었다.

**데이터 레이크 아키텍처**

이 세 가지 서비스는 **데이터 레이크 아키텍처** — 모든 데이터를 위한 중앙 집중식 S3 저장소, 처리하고 쿼리하는 도구와 함께 — 를 형성한다:

```
애플리케이션(주문, 메뉴, 이벤트)
    |
    | 실시간 이벤트
    ↓
Kinesis Data Streams ──→ Amazon Data Firehose ──→ S3 (원시)
                                                   |
                                                   | Glue Crawler가 스키마 발견
                                                   ↓
                                              Glue Data Catalog
                                                   |
                                                   | Glue Jobs가 변환
                                                   ↓
                                              S3 (깔끔함, Parquet, 파티션됨)
                                                   |
                                                   | SQL 쿼리
                                                   ↓
                                              Amazon Athena
                                                   |
                                                   ↓
                                          비즈니스 인텔리전스 도구
                                       (QuickSight, Tableau 등)
```

원시 데이터는 항상 보존된다(원래 S3 버킷에). 변환된 데이터는 Athena를 통해 쿼리 가능하다. 새 질문은 항상 원시 데이터에서 새 Glue 작업을 실행하여 답할 수 있다.

**Amazon Redshift: Athena로 충분하지 않을 때**

일부 사용 사례에서 Athena가 너무 느리거나 너무 비싸다:

- 많은 조인이 있는 매우 복잡한 쿼리
- 같은 쿼리를 하루에 수천 번 실행하는 대시보드
- 구조화된 데이터에서 머신 러닝
- BI 도구를 위한 서브 초 응답 시간 요구사항

**Amazon Redshift**는 완전히 관리되는 데이터 웨어하우스다: 대규모 반복적인 분석 워크로드를 위해 설계된 컬럼형 분석 데이터베이스. S3에 있는 데이터를 쿼리하는 Athena와 달리, Redshift는 데이터를 최적화된 웨어하우스 스토리지에 로드하고 쿼리 최적화, 정렬 전략, 배포 전략을 사용하여 복잡한 분석을 가속화한다.

Redshift는 비용(프로비저닝된 용량)과 데이터를 쿼리하기 전에 로드해야 하는 요구사항을 대가로 복잡한 분석 쿼리에 훨씬 빠르다.

**Redshift Serverless**가 용량 계획 부담을 없긴다 — 쿼리하면, Redshift가 확장한다. 비용은 쿼리당.

현재 Nimbus의 규모에서: Athena로 충분하다. 5배의 데이터 볼륨과 BI 도구가 하루에 수백 번 같은 대시보드를 쿼리하는 경우, Redshift가 비용 효율적이 된다.

## 장점과 한계

**Kinesis Data Streams**: 데이터가 지속적으로 도착하고 순서가 중요할 때 — 클릭스트림, 금융 거래, IoT 원격 측정 — Kinesis를 사용하라. Kinesis는 샤드 내에서 레코드 순서를 유지하고 설정된 보관 창 동안 재생을 허용한다. SQS와 근본적으로 다르다. 순서가 중요하지 않고 재생이 필요 없는 간단한 작업 큐의 경우, SQS가 더 단순한 선택이다.

**AWS Glue**: Glue는 전통적인 ETL 클러스터의 인프라를 없앤다. 변환 로직을 작성하면; AWS가 Spark 환경을 관리한다. 변환이 복잡하거나 데이터 볼륨이 클 때 가치가 있다. 한계는 비용과 콜드 스타트다 — Glue 작업에는 수 분의 시작 지연이 있어, 거의 실시간 변환에는 부적합하다. 단순한 파일 형식 변환(CSV에서 Parquet)의 경우, Glue의 오버헤드가 Lambda 함수나 가벼운 스크립트보다 가치 없을 수 있다.

**Amazon Athena**: Athena로 표준 SQL과 인프라 없이 S3 데이터를 쿼리할 수 있다. 중요한 제약은 비용이다: Athena는 스캔된 데이터 테라바이트당 요금을 부과한다. 전체를 스캔하는 10TB 테이블에 대한 쿼리는 Parquet 형식, 파티션된 테이블에서 200GB를 스캔하는 동일한 쿼리보다 훨씬 더 많은 비용이 든다. 항상 컬럼형 형식(Parquet 또는 ORC)을 사용하고 프로덕션에서 Athena를 실행하기 전에 데이터를 파티션하라. 이러한 최적화 없이, Athena 청구서가 놀랄 수 있다.

## 요약

- **Amazon Kinesis**: 실시간 데이터 스트리밍. 생산자가 레코드를 쓰고; 소비자가 자신의 속도로 읽는다. Amazon Data Firehose는 스트리밍 데이터를 S3, Redshift, 다른 대상으로 덜 운영 작업으로 배달할 수 있다.
- **AWS Glue**: ETL 및 데이터 카탈로그. Crawlers가 스키마를 발견하고; Jobs가 데이터를 변환하고; Data Catalog가 데이터를 Athena와 다른 도구가 발견할 수 있게 한다.
- **Amazon Athena**: S3에서 서버리스 SQL. 표준 SQL을 사용하여 S3의 모든 데이터를 쿼리한다. 스캔된 TB당 가격 — 비용을 최소화하기 위해 Parquet과 파티셔닝을 사용하라.
- **Amazon Redshift**: 높은 성능 분석을 위한 관리형 데이터 웨어하우스. 데이터를 로드하고, 반복적인 분석 쿼리에 최적화하고, 웨어하우스 규모로 빠르게 쿼리한다.
- **데이터 레이크 패턴**: S3로 원시 데이터 → Glue가 변환 → Athena가 쿼리 → BI 도구가 시각화.

## 시험 팁

*SAA-C03 도메인: 고성능 아키텍처 설계(도메인 3, 태스크 3.5)*

- **Kinesis vs. SQS**: Kinesis = 순서가 있고, 실시간 스트리밍, 여러 소비자, 보관 창 내 재생. SQS = 작업 큐, 소비 시 각 메시지 삭제. "여러 소비자가 동시에 같은 스트림을 읽기" → Kinesis. "메시지당 하나의 작업자" → SQS.
- **Athena 시험 신호**: "S3에서 서버리스 SQL," "데이터베이스에 로드하지 않고 S3 데이터 분석," "쿼리당 지불" → Athena.
- **Athena 비용 최적화**: 컬럼형 형식(Parquet 또는 ORC) + 파티셔닝이 스캔된 데이터를 극적으로 줄이고 따라서 비용도 줄인다. 시험은 Athena 비용 줄이는 방법을 물을 수 있다.
- **Glue Crawler**: "S3 데이터의 스키마를 자동으로 발견" → Glue Crawler.
- **Amazon Data Firehose**: "소비자를 관리하지 않고 스트리밍 데이터를 S3/Redshift/OpenSearch에 자동으로 로드" → Amazon Data Firehose. 이전 자료에서 아직 Kinesis Data Firehose라고 부를 수 있다.
- **Redshift vs. Athena**: 같은 데이터셋에서 고빈도 복잡한 쿼리(BI 대시보드)에는 Redshift. 자주 변경되는 S3 데이터에서 임시 쿼리에는 Athena.
- **EMR (Elastic MapReduce)**: AWS 관리형 Hadoop/Spark 클러스터. "기존 Hadoop/Spark 워크로드" 또는 "사용자 정의 데이터 처리 프레임워크"가 언급될 때 시험이 사용. Glue가 대부분의 사용 사례에 대한 관리형 대안이다.

**연습 2 — 시험 연습**

*시나리오*: 라이드쉐어링 회사가 여행 데이터를 분석하길 원한다. 하루에 100만 건의 여행이 완료된다. 여행 레코드가 JSON 파일(각 약 2KB)로 S3에 저장된다. 분석 팀은 "지난주 도시별 평균 여행 시간" 같은 임시 SQL 쿼리를 실행하고 싶다. 쿼리는 2분 내에 완료되어야 한다. 스토리지 비용을 최소화해야 한다. 팀은 주당 20-30개의 쿼리를 실행할 것이다.

다음 중 이 요구사항을 가장 잘 충족하는 아키텍처는?

A) 매일 RDS PostgreSQL에 여행 데이터 로드; 표준 SQL로 쿼리  
B) JSON을 날짜와 도시별로 파티션된 Parquet 형식으로 변환하기 위해 AWS Glue 사용; Amazon Athena로 쿼리  
C) Amazon Data Firehose를 사용하여 Amazon Redshift에 여행 데이터 배달; Redshift로 쿼리  
D) DynamoDB에 여행 데이터 로드하고 SQL 쿼리에 PartiQL 사용

**힌트 1**: 주당 20-30개의 쿼리는 낮은 빈도다. 가격에 어떤 서비스가 가장 비용 효율적인가?

**힌트 2**: Parquet 형식 + 파티셔닝이 Athena가 스캔하는 데이터를 극적으로 줄인다 — 따라서 비용도.

**힌트 3**: 100만 건 여행 × 2KB = 하루 ~2GB. 주간 ~14GB. 스캔된 TB당 $5의 Athena에서, 최적화 없이도 저렴하다.

**답**: B

**설명**: Glue가 JSON을 Parquet(컬럼형 형식이 스캔된 데이터를 극적으로 줄임)으로 변환하고 날짜와 도시별로 파티션된다(파티션 프루닝이 "지난주" 쿼리가 7일의 파티션만 스캔함). Athena가 표준 SQL로 S3에서 직접 쿼리한다. 주당 20-30개의 쿼리의 경우, 쿼리당 지불 Athena가 항상 실행 중인 Redshift보다 극도로 비용 효율적이다.

**왜 A가 아닌가?** 매일 RDS에 2GB의 데이터를 로드하고, 그런 다음 쿼리하면 24/7 실행되는 데이터베이스 인스턴스가 필요하다. 주당 20-30개의 쿼리에 대해 이것이 과도하게 엔지니어링되고 비싸다.

**왜 C가 아닌가?** Redshift는 고빈도 쿼리(하루에 같은 데이터셋에서 수백 개)에 비용 효율적이다. 주당 20-30개의 쿼리에 대해, 항상 켜진 Redshift 클러스터는 Athena의 쿼리당 가격보다 훨씬 더 많은 비용이 든다.

**왜 D가 아닌가?** DynamoDB는 키-값/문서 저장소로 키 기반 접근에 최적화되어 있지 임시 분석 쿼리가 아니다. DynamoDB에서 PartiQL은 설명된 종류의 GROUP BY 집계를 지원하지 않는다.

*SAA-C03 도메인: 고성능 아키텍처 설계 — 태스크 3.5*

**연습 3 — 아키텍처 과제** *(선택 사항)*

Nimbus는 주문을 위한 실시간 사기 감지 시스템을 구축하길 원한다. 시스템은 다음을 해야 한다:

- 60초 내에 같은 계정에서 5번 이상 주문 감지
- 30일 미만의 새 계정에서 $500 이상의 주문 플래그
- 플래그된 주문을 사람 검토 큐에 보내기

아키텍처를 설계하라. Kinesis가 무엇을 제공하는가? 사기 로직은 어디서 실행되는가? "같은 계정, 60초 창"을 어떻게 상관시키는가? 어떤 서비스가 플래그된 주문을 받는가?

*(단 하나의 정답은 없다. 실시간 스트리밍 아키텍처 설계를 연습하는 것이 목표다.)*

## 포스트 크레딧 장면

Tom이 첫 번째 Athena 쿼리를 실행했다.

"지난 분기 매출로 상위 10개 레스토랑," 그가 말했다.

12초 후, 결과가 나타났다.

그가 그것들을 응시했다.

"레스토랑 47번이 1위야," 그가 말했다. Maya의 가족 레스토랑이었다 — Nimbus가 시작된 곳, 전화가 항상 바빠서 주문을 잃던 때.

"물론이죠," Maya가 말했다. "아레파가 그 정도로 좋아요."

Tom이 다른 쿼리를 실행했다. 그리고 또 다른. 각각 초 안에, 각각 몇 분의 1센트 비용.

한 시간 후, 그는 이전에 결코 갖지 못했던 방식으로 Nimbus의 사업의 완전한 그림을 갖고 있었다. 어떤 레스토랑 카테고리가 가장 빠르게 성장했는지. 어떤 고객 코호트가 가장 오래 유지됐는지. 어떤 메뉴 아이템이 가장 많은 반복 주문을 이끌었는지.

"왜 이걸 더 일찍 구축하지 않았어?" 그가 물었다.

"데이터가 있었어요," Leo가 말했다. "그냥 사용할 파이프라인이 없었을 뿐이에요."

"데이터는 항상 거기에 있었어," Maya가 조용히 말했다. "그냥 볼 수가 없었을 뿐이야."

다음 챕터에서: 사업을 명확하게 볼 수 있게 됐으니, 그것을 운영하는 인프라 비용을 더 효율적으로 지불하는 방법에 대해 이야기하자.
