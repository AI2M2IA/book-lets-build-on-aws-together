**세 가지 다른 문제**

Nimbus의 데이터 문제에는 세 가지 차원이 있었습니다:

**실시간 스트리밍**: 주문이 지금 들어오고 있습니다. 주문 속도의 실시간 대시보드를 보고 싶습니다 — 분당 몇 개, 리전별, 레스토랑별. 데이터가 도착하는 대로 처리되어야 합니다.

**데이터 변환**: 데이터가 다양한 시스템에서 나와 다른 형식(JSON, CSV, Parquet)으로 S3에 있습니다. 그것을 분석하기 전에, 그것을 정규화해야 합니다 — 같은 스키마, 같은 형식, 정리됨, 참조 데이터와 조인됨.

**임시 분석**: 데이터가 정리되면, 먼저 데이터베이스에 로드하지 않고 그것에 대해 SQL 쿼리를 실행하고 싶습니다. "지난 30일에 매출 기준 상위 10개 레스토랑을 줘." 데이터를 데이터베이스에 로드하지 않고요.

이것들 각각이 별개의 문제입니다. AWS에는 각각에 대한 전용 서비스가 있습니다.

**실시간 스트림: 데이터를 위한 티커 테이프**

티커 테이프 기계를 상상해보십시오 — 주가를 연속적인 종이 두루마리에 인쇄하던 종류. 가격이 변하는 대로 인쇄되었습니다. 현재 가격을 원하는 모두가 테이프를 읽을 수 있었습니다. 아무도 다른 사람을 기다릴 필요가 없었습니다; 테이프가 얼마나 많은 사람이 읽고 있든 관계없이 계속 인쇄되었습니다.

그것이 실시간 데이터 스트리밍의 모델입니다. 생산자가 데이터를 일어나는 대로 보냅니다. 여러 소비자가 스트림을 동시에 읽을 수 있고, 각자 자체 속도로, 각자 전체 그림을 얻습니다.

**Amazon Kinesis Data Streams**가 Nimbus를 위한 그 기계입니다. 주문이 들어오면, 애플리케이션이 Kinesis 스트림에 이벤트를 게시합니다: `{ "orderId": "ORD-7741", "restaurantId": "47", "total": 3200, "timestamp": "...", "region": "us-west-2" }`.

이 스트림의 소비자:

- 실시간 대시보드(이벤트가 도착하는 대로 읽고, 지표를 업데이트)
- 사기 탐지 Lambda(비정상적인 주문 패턴을 찾음)
- 영구 저장을 위한 S3로의 스트림

**Kinesis Data Streams 개념**:

- **샤드(Shard)**: 용량의 기본 단위. 하나의 샤드가 쓰기 1 MB/s, 읽기 2 MB/s를 처리합니다.
- **보존 기간**: 데이터가 스트림에 24시간(기본) 머물며, Extended Data Retention으로 **365일**(1년)까지 연장 가능.
- **시퀀스 번호**: 각 레코드에 시퀀스 번호가 있습니다. 소비자가 스트림에서의 위치를 추적합니다.

**Amazon Data Firehose**(이전의 **Kinesis Data Firehose**): 스트리밍 생산자와 S3, Redshift, OpenSearch 같은 대상 사이의 관리형 배달 서비스. 그것이 데이터를 자동으로 버퍼링, 압축, 변환, 배달합니다.

Nimbus의 경우: Kinesis Data Streams → Amazon Data Firehose → S3(Parquet 형식, 압축됨, 날짜별 파티셔닝됨).

"이미 배포했어요 — 아." Leo가 먼저 쓰기 처리량을 계산하지 않고 샤드 수를 하나로 설정했습니다. Nimbus의 주문량에서, 하나의 샤드가 괜찮았습니다. 그가 누군가 그가 추측했다는 것을 알아차리기 전에 이것을 확인했습니다.

**번역기: 원시 데이터를 이해하기**

S3의 데이터는 원시입니다. 그것을 효율적으로 분석하기 전에, 거기 무엇이 있는지 발견하고, 그것을 일관된 형식으로 변환하고, 다른 데이터셋을 함께 조인하고, 나쁜 레코드와 누락된 값을 처리해야 합니다.

그것이 전용 번역 레이어를 위한 작업입니다.

**AWS Glue**는 완전 관리형 ETL(Extract, Transform, Load) 서비스입니다. 그것에는 두 가지 주요 구성 요소가 있습니다:

**Glue Data Catalog**: S3 데이터를 설명하는 메타데이터 저장소 — 어떤 테이블이 존재하는지, 어떤 열을 가지는지, 데이터 파일이 어디 있는지. 그것은 여러분의 데이터 레이크를 위한 카드 목록 같습니다.

**Glue Crawlers**: S3를 스캔하고, 스키마를 추론하고, Data Catalog를 채우는 자동화된 에이전트. S3 버킷에서 크롤러를 실행하면 10분 후에 모든 테이블의 카탈로그를 갖게 됩니다.

**Glue Jobs**: 실제 변환을 수행하는 서버리스 Spark/Python 작업. 변환 로직을 작성하거나(또는 Glue의 시각적 ETL 도구를 사용), Glue가 그것을 관리형 인프라에서 실행합니다.

Nimbus의 경우:

1. Glue Crawler가 S3의 주문 데이터를 스캔 → Glue Data Catalog에 테이블 정의를 생성
2. Glue Job이 원시 JSON 주문 이벤트를 깨끗하고, 파티셔닝된 Parquet 형식으로 변환
3. 변환된 데이터가 쿼리 최적화된 레이아웃으로 S3에 다시 쓰임

**ETL이 깨질 때: 스키마 진화 문제**

Glue 파이프라인이 처음 3주 동안 깔끔하게 실행되었습니다. 그러고 나서 레스토랑 파트너 #412가 메뉴 내보내기에 새 필드를 추가했습니다: `allergen_tags`. 필드가 문자열 배열이었고 — `["gluten", "dairy", "nuts"]` — 레스토랑의 야간 데이터 내보내기에 나타났습니다.

Glue 작업의 스키마가 엄격했습니다. 그것이 주문 JSON에서 특정 필드를 기대하도록 작성되었습니다. 그것이 `allergen_tags` — 스키마에 없는 필드 — 를 만났을 때, Glue 작업이 실패했습니다.

47개 레스토랑(모두 파트너 #412와 같은 메뉴 내보내기 형식을 사용)의 여섯 시간치 주문 데이터가 처리되지 않고 S3에 쌓였습니다. 어젯밤의 주문을 아침까지 쿼리 가능하게 만들기로 되어 있던 야간 Glue 실행이 대신 새벽 2시 47분에 멈추고 CloudWatch에 실패 레코드를 썼습니다.

Tom이 오전 9시에 Athena 쿼리를 실행하려 했을 때 그것을 발견했고 이전 12시간에 대해 `0 rows returned`를 받았습니다.

"ETL이 소스 데이터가 바뀌어서 깨졌어요?" Maya가 Leo가 무슨 일이 일어났는지 설명하자 물었습니다.

"ETL이 ETL이 스키마 변경을 처리하는 법을 몰라서 깨졌어요," Leo가 말했습니다. "우리가 정확히 이 필드들을 기대하는 엄격한 작업을 작성했어요. 새 필드가 나타났을 때, 그것이 당황했어요."

"그러면 누군가 스키마 변경을 통해 침입을 시도하면 어떻게 되죠?" Priya가 물었습니다. "악의적인 레스토랑 파트너가 파이프라인을 충돌시키려고 의도적으로 예상치 못한 필드를 제출하는 거요?"

질문이 고려할 가치가 있었습니다. 예상치 못한 입력에 충돌하는 ETL 파이프라인은 서비스 거부 벡터입니다: 비정상적인 데이터 형식을 제출하고, 파이프라인을 충돌시키면, 그 레스토랑(그리고 그 형식을 공유하는 다른 모든 레스토랑)이 처리를 멈춥니다.

해결책에는 두 부분이 있었습니다:

**Glue 스키마 진화**: Glue의 동적 프레임이 스키마 진화를 지원합니다 — 기대 스키마에 없는 필드가 실패를 일으키는 대신 통과됩니다. 작업 스크립트에서 DataFrame 대신 DynamicFrame을 사용하고, 추가 옵션에 `mergeSchema`를 설정하여 활성화합니다. 새 필드가 다음 크롤러 실행에서 스키마에 자동으로 추가됩니다.

```python
# 이전 (엄격, 새 필드에 깨짐)
datasource = glueContext.create_dynamic_frame.from_catalog(
    database="nimbus_db",
    table_name="orders"
)

# 이후 (스키마 진화 활성화)
datasource = glueContext.create_dynamic_frame.from_catalog(
    database="nimbus_db",
    table_name="orders",
    additional_options={"mergeSchema": "true"}
)
```

**Glue 작업 알림**: 파이프라인 실패가 Tom이 알아차리기 전 약 여섯 시간 동안 조용했습니다. Glue 작업 실행 상태(`FAILED`)에 대한 CloudWatch 알람이 온콜 엔지니어에게 5분 이내에 알렸을 것입니다. 알람 비용: 월 10센트 — 사실상 무료(지표 자체가 비용이 없고, 처음 열 개 알람이 무료 계층에 들어감).

"여섯 시간치 데이터가 S3에 처리되지 않고 앉아 있었어요," Leo가 따라잡기 위해 Glue 작업을 수동으로 다시 실행한 후 말했습니다. "아무것도 손실되지 않았어요 — 하지만 분석이 그만큼 뒤처졌어요. 우리가 알람을 가졌다면, 지연이 30분이었을 거예요."

더 넓은 교훈: 외부 데이터를 처리하는 ETL 파이프라인은 스키마 변경을 우아하게 처리해야 합니다. 외부 파트너 — 레스토랑, 결제 제공자, 배달 서비스 — 가 데이터 형식을 바꿀 것입니다. 파이프라인이 그 변경에 깨지기 쉬워서는 안 됩니다.

**쿼리 레이어: S3에 직접 SQL**

이제 데이터가 S3에, Parquet 형식으로, 날짜별로 파티셔닝되어 있었습니다. 마지막 조각: 먼저 데이터베이스에 로드하지 않고 그것에 질문을 하는 방법.

**Amazon Athena**는 S3 데이터에 직접 SQL 쿼리를 실행하는 서버리스, 대화형 쿼리 서비스입니다. 프로비저닝할 데이터베이스 없음, 로드할 데이터 없음. 테이블을 정의하거나(또는 Glue Data Catalog를 사용), SQL을 작성하면, Athena가 S3 파일에 대해 쿼리를 실행합니다.

```sql
SELECT 
    restaurant_id,
    COUNT(*) as order_count,
    SUM(total) as revenue
FROM orders
WHERE year='2024' AND month='09'
GROUP BY restaurant_id
ORDER BY revenue DESC
LIMIT 10;
```

Athena 가격은 쿼리가 스캔하는 데이터 양에 기반합니다. us-east-1, us-west-2, 그리고 대부분의 주요 리전에서, 표준 SQL 쿼리는 스캔된 테라바이트당 $5입니다. Parquet 형식(컬럼형)을 파티션 프루닝(`WHERE year='2024' AND month='09'`)과 함께 사용하면 Athena가 필요한 파일만 스캔하며, 이것이 비용을 극적으로 줄입니다.

"우리가 30일치 데이터에 대해 이 쿼리를 실행할 수 있어요," Leo가 말했습니다, "그리고 우리가 그것을 잘 저장하면 놀랍도록 적게 들 수 있어요."

"어떻게 그렇게 적게 들 수 있죠?" Maya가 물었습니다. "테라바이트의 데이터를 스캔하면, 그게 어떻게 비싸지 않죠?"

Leo가 Parquet을 설명했습니다. 행 기반 형식(JSON, CSV)에서, 스무 개 중 두 개의 열을 찾는 쿼리가 스무 개 모두를 읽어야 합니다. Parquet 같은 컬럼형 형식에서, 그것이 필요한 두 개만 읽습니다. 50TB 데이터셋의 경우, 잘 최적화된 쿼리가 200GB를 스캔할 수 있습니다. $5/TB에서, 그건 1달러입니다.

"그러면 누군가 실수로 전체 테이블을 쿼리하면요?" Maya가 밀어붙였습니다.

"그게 진짜 비용 위험이에요," Leo가 말했습니다.

여러분은 궁금해할지 모릅니다: Athena가 스캔된 테라바이트당 요금을 부과한다면, 잘못 작성된 한 쿼리가 큰 예상치 못한 청구서를 생성할 수 있나요? 그렇습니다 — 그리고 이것이 실제 프로덕션 환경에서 일어납니다. 50TB의 최적화되지 않은 테이블에 대한 쿼리가 전체 월 S3 청구서보다 더 들 수 있습니다. 이것이 Parquet 형식과 파티셔닝이 선택적 최적화가 아닌 이유입니다 — 그것들은 비용 통제입니다. Athena는 또한 단일 쿼리가 스캔할 수 있는 데이터 양을 제한하는 워크그룹 쿼리 스캔 제한을 지원합니다.

"우리가 생각할 수 있는 어떤 임의의 질문에 대해서든요?" Tom이 물었습니다.

"우리가 SQL로 표현할 수 있는 어떤 질문이든, 우리가 S3에 저장한 어떤 데이터에 대해서든."

Tom이 Leo의 노트북에 앉아 첫 쿼리를 작성했습니다:

```sql
SELECT
    r.restaurant_id,
    r.restaurant_name,
    AVG(EXTRACT(EPOCH FROM (o.confirmed_at - o.notification_sent_at)) / 60) 
        AS avg_confirmation_minutes,
    COUNT(DISTINCT c.customer_id) AS unique_customers,
    COUNT(DISTINCT CASE WHEN c.order_count > 1 THEN c.customer_id END) 
        AS returning_customers,
    ROUND(
        COUNT(DISTINCT CASE WHEN c.order_count > 1 THEN c.customer_id END) * 100.0 /
        NULLIF(COUNT(DISTINCT c.customer_id), 0),
        2
    ) AS reorder_rate_pct
FROM orders o
JOIN restaurants r ON r.restaurant_id = o.restaurant_id
JOIN (
    SELECT customer_id, restaurant_id, COUNT(*) AS order_count
    FROM orders
    WHERE year >= '2024'
    GROUP BY customer_id, restaurant_id
) c ON c.customer_id = o.customer_id AND c.restaurant_id = o.restaurant_id
WHERE o.year = '2024'
  AND o.status = 'delivered'
GROUP BY r.restaurant_id, r.restaurant_name
ORDER BY avg_confirmation_minutes ASC
LIMIT 20;
```

쿼리가 11초 동안 실행되었습니다. 결과: 20개 레스토랑, 가장 빠른 평균 확인 시간으로 정렬되고, 옆에 그들의 재주문율과 함께.

Tom이 출력을 응시했습니다.

가장 빠르게 확인하는 레스토랑 — 평균 3~4분 이내에 주문을 인정하고 확인한 곳 — 이 평균 41%의 재주문율을 가졌습니다. 가장 느리게 확인하는 레스토랑(평균 확인 시간 18~22분)이 13%의 재주문율을 가졌습니다.

"빠르게 확인하는 레스토랑이 세 배의 반복 비즈니스를 얻네요," Tom이 말했습니다.

"그건 엄청난 격차예요," Maya가 말했습니다. "왜 확인 속도가 재주문율에 그렇게 많이 영향을 미치죠?"

"왜냐하면 고객이 주문을 하고 거기 앉아 전화기를 보고 있었기 때문이에요," Leo가 말했습니다. "확인이 3분에 오면, 그들이 확실하다고 느껴요. 그것이 22분에 — 또는 결코 — 오면, 그들이 불안해요. 음식이 잘 도착해도, 그 불안이 제품 실패예요."

"이건 제품 통찰이에요," Maya가 말했습니다. "단지 분석 통찰이 아니라요. 우리가 레스토랑에게 카테고리 평균과 비교한 그들의 확인 시간 벤치마크를 보여줘야 해요."

Athena 쿼리가 1.2 GB의 데이터를 스캔했습니다(Parquet 형식의 두 달치 주문, 연도와 월별로 파티셔닝됨). 비용: $0.006.

반 센트. Nimbus가 레스토랑 온보딩을 설계하는 방식을 바꿀 비즈니스 통찰을 위해 — 어떤 레스토랑을 성공 코칭을 위해 우선시할지, 파트너 SLA의 일부로 어떤 확인 시간 목표를 설정할지.

Tom이 그들이 버려온 모든 데이터의 가치를 재계산하는 사람의 표정을 했습니다.

"그러면 누군가 쿼리 레이어를 통해 침입을 시도하면 어떻게 되죠?" Priya가 물었습니다. "아니면 그냥 원시 주문 데이터에서 고객 주소를 실수로 내보내는 분석가요? 고객 PII, 주문 기록, 금융 기록 — 누가 어떤 테이블이 보이기라도 하는지 제어하죠?"

그녀가 질문을 마치기 전에, Leo도 운영 문제를 깨달았습니다: 한 팀이 단일 쿼리에서 $500 Athena 청구서를 생성하는 재앙적인 전체 테이블 스캔을 실행하는 것을 어떻게 멈추죠?

**Athena 워크그룹**이 두 문제를 동시에 해결합니다.

워크그룹은 Athena 사용자를 그룹화하고 공유 설정을 적용하는 명명된 구성입니다: 쿼리 결과 위치, 암호화, 그리고 — 중요하게 — 쿼리당 데이터 스캔 제한.

```
워크그룹: analytics-team
  쿼리 스캔 제한: 쿼리당 10 GB
  제한 초과 시 동작: 쿼리 취소

워크그룹: engineering-team
  쿼리 스캔 제한: 쿼리당 100 GB
  제한 초과 시 동작: 경고만

워크그룹: finance-reports
  쿼리 스캔 제한: 쿼리당 1 GB
  제한 초과 시 동작: 쿼리 취소
```

`analytics-team` 워크그룹의 분석가가 실수로 50TB의 데이터를 스캔하고 $250 Athena 요금을 생성할 수 없습니다. 쿼리가 10GB의 스캔된 데이터를 초과할 때 취소됩니다. 분석가가 오류 메시지를 보고 파티션 필터를 추가해야 한다는 것을 압니다.

워크그룹은 또한 팀별로 별도의 결과 위치를 강제합니다: 엔지니어링 팀의 쿼리 결과가 `s3://nimbus-query-results/engineering/`로 갑니다; 재무 팀의 결과가 `s3://nimbus-query-results/finance/`로 갑니다. 팀 간 쿼리 결과 액세스 없음.

IAM이 어떤 사용자가 어떤 워크그룹을 사용할 수 있는지 제어합니다. 자동화된 보고서를 실행하는 Lambda 함수가 `finance-reports` 워크그룹(엄격하게 제한됨)을 사용합니다. 프로덕션 문제를 디버깅하는 엔지니어가 `engineering-team` 워크그룹(더 넓은 제한, 취소가 아니라 경고)을 사용합니다. 원시 이벤트 테이블(고객 PII를 포함)에 대한 액세스가 Glue Data Catalog 테이블에 대한 IAM 조건을 통해 `engineering-team` 워크그룹으로 제한됩니다.

"그건 단지 비용 통제가 아니에요," Priya가 말했습니다. "그건 액세스 통제예요. 워크그룹이 강제 지점이에요."

그것이 그녀의 질문에 완전히 답했습니다. 액세스 통제를 건너뛰는 모든 데이터 파이프라인 논의가 결국 규정 준수 사건이 됩니다 — 그리고 여기서, 분석 팀은 집계된 주문 테이블만 보았고, 고객 PII가 있는 원시 이벤트는 명시적 IAM 인증 뒤에 머물렀습니다. Glue Data Catalog는 단지 스키마 디렉토리가 아니었습니다. 그것은 액세스 통제 경계였습니다.

"그건 추가 작업이 아니에요," Priya가 말했습니다. "그게 설계예요."

**데이터 레이크 아키텍처**

이 세 서비스가 **데이터 레이크 아키텍처**라고 불리는 것으로 결합됩니다 — 모든 데이터를 위한 중앙 집중식 S3 저장소, 그것을 처리하고 쿼리하는 도구와 함께:

```
Applications (orders, menus, events)
    |
    | Real-time events
    ↓
Kinesis Data Streams ──→ Amazon Data Firehose ──→ S3 (raw)
                                                   |
                                                   | Glue Crawler discovers schema
                                                   ↓
                                              Glue Data Catalog
                                                   |
                                                   | Glue Jobs transform
                                                   ↓
                                              S3 (clean, Parquet, partitioned)
                                                   |
                                                   | SQL queries
                                                   ↓
                                              Amazon Athena
                                                   |
                                                   ↓
                                          Business Intelligence Tools
                                       (QuickSight, Tableau, etc.)
```

원시 데이터는 항상 보존됩니다(원래 S3 버킷에). 변환된 데이터는 Athena를 통해 쿼리 가능합니다. 새 질문은 항상 원시 데이터에 새 Glue 작업을 실행하여 답할 수 있습니다.

**Amazon Redshift: Athena로 충분하지 않을 때**

일부 사용 사례에서, Athena가 너무 느리거나 너무 비쌉니다:

- 많은 조인이 있는 매우 복잡한 쿼리
- 하루에 같은 쿼리를 수천 번 실행하는 대시보드
- 구조화된 데이터에 대한 머신러닝
- BI 도구를 위한 1초 미만 응답 시간 요구사항

**Amazon Redshift**는 완전 관리형 데이터 웨어하우스입니다: 크고, 반복적인 분석 워크로드를 위해 설계된 컬럼형 분석 데이터베이스. 데이터가 S3에 사는 곳에서 쿼리하는 Athena와 달리, Redshift는 데이터를 최적화된 웨어하우스 스토리지에 로드하고 쿼리 최적화, 정렬 전략, 분산 전략을 사용해 복잡한 분석을 가속합니다.

데이터 볼륨이 작고 쿼리가 드물게(주별 또는 월별) 실행되면, 잘 정리된 S3 데이터를 가진 Athena가 충분하고 거의 무료입니다 — 하지만 같은 분석 대시보드를 하루에 수백 번 실행하면, Redshift의 사전 최적화된 컬럼형 스토리지가 더 빠르고 궁극적으로 더 비용 효율적입니다, 데이터를 미리 로드하기를 요구함에도 불구하고요.

Redshift는 비용(프로비저닝된 용량)과 쿼리 전에 데이터를 로드해야 하는 요구사항을 대가로 복잡한 분석 쿼리에 상당히 빠릅니다.

**Redshift Serverless**가 용량 계획 부담을 제거합니다 — 쿼리하면, Redshift가 확장합니다. 비용은 실제로 사용된 컴퓨팅 용량에 기반하며, **RPU-시간**으로 측정되고 초당 청구되며(활성화당 60초 최소), 더하기 관리형 스토리지 GB-월당 — 그리고 웨어하우스가 유휴 상태일 때 컴퓨팅에 대해 아무것도 안 냅니다. (Athena가 쿼리당 가격이 책정되는 것입니다: 스캔된 TB당 $5.)

현재 규모의 Nimbus의 경우: Athena가 충분합니다. 데이터 볼륨의 다섯 배와 BI 도구가 같은 대시보드를 하루에 수백 번 쿼리하면, Redshift가 비용 효율적이 될 것입니다.

**Athena가 잘못된 도구일 때**

"그러면 함정이 뭐예요?" Maya가 물었습니다. "왜 모든 것에 Athena를 쓰지 않죠? 그건 서버리스, 쿼리당 지불, 인프라 없음 — 완벽하게 들려요."

Athena가 옳은 답이 아닌 경우:

**고빈도 대시보드**: 30초마다 새로 고치고 분당 50개 쿼리를 실행하는 고객 대면 분석 대시보드는 좋은 Athena 사용 사례가 아닙니다. 스캔된 $5/TB에서, 그 쿼리가 그 빈도에서 비용 효율적이려면 극도로 잘 최적화되어야 합니다. Redshift나 사전 집계된 데이터베이스(심지어 RDS)가 1초 미만 응답 시간 요구사항이 있는 대시보드에 더 적절합니다.

**낮은 지연 요구사항이 있는 운영 쿼리**: 고객 서비스 담당자가 500ms 미만에 특정 주문을 찾아야 한다면, Athena는 도구가 아닙니다 — DynamoDB 조회나 RDS 쿼리입니다. Athena는 운영 지연이 아니라 분석 처리량에 최적화되어 있습니다. 작은 데이터셋에 대한 잘 조정된 Athena 쿼리조차도 1~3초의 콜드 스타트 오버헤드가 있습니다.

**트랜잭션 시스템**: Athena는 읽기 전용입니다. Athena에서 레코드를 INSERT, UPDATE, DELETE할 수 없습니다(자체 복잡성을 가진 Lake Formation이나 Iceberg 테이블 형식 같은 특정 통합을 제외하고). 운영 쓰기 워크로드의 경우, 트랜잭션 데이터베이스를 사용하십시오.

**매우 작고, 자주 변하는 데이터셋**: 데이터셋이 매분 변하고 1GB뿐이라면, 그것을 RDS나 DynamoDB에 로드하고 거기서 쿼리하는 것이 오래되었을 수 있는 S3 파일에 대해 Athena 쿼리를 실행하는 것보다 더 단순하고 빠릅니다. Athena는 쿼리 시점의 S3 파일을 쿼리합니다 — 파일이 2분 전에 쓰였다면, 그것이 여러분이 얻는 신선도입니다.

나타나는 패턴: Athena는 S3 데이터에 대한 대규모, 드문, 임시 분석 쿼리에 훌륭합니다. 운영적, 트랜잭션적, 또는 1초 미만 지연이 필요한 어떤 것에 대해서는, 적절한 운영 데이터베이스를 사용하십시오.

**Kinesis vs SQS: 혼란 정리하기**

이것이 모든 데이터 아키텍처 논의에서 나오는 질문입니다. Kinesis와 SQS 둘 다 메시지를 다룹니다. 각각을 언제 사용하죠?

혼란은 표면 수준의 유사성에서 옵니다: 둘 다 생산자로부터 메시지를 받습니다. 둘 다 그 메시지를 소비자에게 배달합니다. 둘 다 관리형 AWS 서비스입니다. 하지만 그것들의 데이터 모델이 근본적으로 다릅니다.

**SQS(Simple Queue Service)**는 작업 큐입니다. 메시지를 넣습니다. 한 소비자가 그것을 꺼내 처리합니다. 처리가 완료되면, 메시지가 삭제됩니다. 열 개의 소비자가 있으면, 각 메시지가 그중 정확히 하나로 갑니다. 메시지가 소비 후 사라집니다.

**Kinesis Data Streams**는 로그입니다. 레코드를 넣습니다. 모든 소비자가 모든 레코드를 읽습니다. 소비자 A가 그것들 모두를 읽습니다. 소비자 B도 그것들 모두를, 자체 속도로 읽습니다. 어느 소비자도 레코드를 삭제하지 않습니다 — 그것이 보존 기간이 만료될 때까지 스트림에 머뭅니다. 언제든 세 번째 소비자를 추가할 수 있고, 그것이 스트림의 처음부터(보존 창 내에서) 읽을 수 있습니다.

"언제 실제로 모든 소비자가 모든 메시지를 보기를 원하죠?" Maya가 물었습니다.

답은 Kinesis가 빛나는 사용 사례입니다:

**실시간 대시보드 + 사기 탐지 + S3 아카이브**: 세 개 모두 같은 주문 이벤트 스트림을 동시에 소비합니다. SQS를 사용하면, 세 개의 별도 큐에 게시해야 합니다 — 그리고 게시하는 사람이 세 소비자 모두에 대해 알아야 합니다. Kinesis로, 생산자가 한 번 게시합니다; 어떤 수의 소비자든 독립적으로 읽을 수 있습니다.

**재생**: 소비자가 2시간 동안 실패합니다(Lambda 동시성 제한에 도달, 다운스트림 서비스 다운). SQS로, 그 메시지들이 이미 삭제되었습니다(또는 정의된 가시성 타임아웃이 있음). Kinesis로, 소비자가 마지막 체크포인트에서 재개하고 놓친 2시간치 레코드를 처리합니다. 데이터가 스트림에 보존되었습니다(Extended Data Retention으로 최대 365일).

**샤드 내 순서**: 같은 파티션 키를 가진 레코드가 항상 같은 샤드로 가서, 순서를 보존합니다. 심볼 `AMZN`의 모든 거래가 순서대로 처리되어야 하는 주식 거래 시스템의 경우, Kinesis가 이것을 보장합니다. SQS FIFO는 그룹별 순서를 제공하지만 더 낮은 처리량에서입니다(표준 모드에서 배치로 큐당 초당 최대 3,000개 메시지 — 고처리량 모드가 이를 초당 수만 개로 높임 — 대 Kinesis의 샤드당 1 MB/s 또는 초당 1,000개 레코드, 필요한 만큼 많은 샤드로 곱함).

결정적 질문: **모든 메시지가 정확히 한 소비자에 의해 소비되고 그러고 나서 버려져야 하는가?** → SQS. **각 메시지가 여러 소비자에 의해 독립적으로 보여야 하는가, 또는 재생 능력이 필요한가?** → Kinesis.

Nimbus의 실시간 대시보드의 경우: Kinesis. 여러 소비자(대시보드, 사기 탐지, S3 아카이브)가 모두 같은 스트림을 읽음.

Nimbus의 주문 처리 큐의 경우(주문 접수 → 하나의 ECS 태스크가 그것을 처리): SQS. 한 소비자, 재생 필요 없음, 팬 아웃 필요 없음.

## 데이터 시각화: Amazon QuickSight

Athena가 데이터를 쿼리합니다. Glue가 그것을 준비합니다. 하지만 어느 시점에 누군가 차트를 봐야 합니다 — 그리고 콘솔에서 SQL 쿼리를 실행해서가 아니라요.

"우리가 정말 그것을 위한 또 다른 서비스가 필요해요?" Maya가 물었습니다. "Athena 결과를 스프레드시트로 그냥 내보낼 수 없나요?"

"한 쿼리에는, 그래요," Tom이 말했습니다. 그는 이미 이것을 시도해 본 사람의 표정을 했습니다. "전체 팀과 공유하고 싶은 대시보드에는, 그게 매일 아침 새 스프레드시트예요."

**Amazon QuickSight**는 AWS의 관리형 비즈니스 인텔리전스(BI) 서비스입니다. 그것이 Athena, S3, RDS, Redshift, 그리고 다른 소스에 직접 연결하고, 별도의 BI 서버 없이 대시보드와 시각화를 구축하게 합니다.

핵심 기능:

- **SPICE**(Super-fast, Parallel, In-memory Calculation Engine): QuickSight가 모든 대시보드 로드에서 Athena를 다시 쿼리하지 않고 대규모에서 1초 미만 쿼리 성능을 위해 데이터셋을 인메모리 엔진으로 임포트할 수 있습니다
- **ML Insights:** 이상 탐지와 예측이 내장됨 — 데이터 과학 필요 없음
- **임베디드 대시보드:** URL을 통해 QuickSight 대시보드를 여러분 자신의 웹 애플리케이션에 임베드할 수 있습니다

Tom이 QuickSight를 Athena 데이터 소스에 연결하고 오후 안에 일일 주문, 레스토랑별 매출, 전환 퍼널을 보여주는 작동하는 대시보드를 가졌습니다.

"그게 월 얼마나 들죠?" 그가 물었습니다 — 그러고 나서 다른 누가 답하기 전에 자신의 질문에 답했습니다. "QuickSight가 작성자당 — 대시보드를 구축하는 사람들 — 약 월 $24, 그리고 독자당 월 $3예요. 우리가 그것을 사용할 네 명이 있어요."

"그러니까 월 약 백 달러네요," Maya가 말했습니다.

"그렇지 않으면 별도의 분석 서버 실행이 필요할 BI 서비스를 위해서요," Priya가 말했습니다. "네."

Tom이 대시보드를 게시했습니다. 다음 아침, Athena 쿼리를 실행하는 대신, 전체 팀이 URL을 열었습니다.

> **시험 팁 — QuickSight**
>
> QuickSight는 AWS의 관리형 BI 및 시각화 서비스입니다. Athena, S3, Redshift, RDS에 연결합니다. SPICE는 반복적인 대시보드 쿼리를 가속하는 인메모리 쿼리 엔진입니다. 시험 트리거: "AWS의 비즈니스 인텔리전스 대시보드" 또는 "Athena/Redshift의 데이터 시각화" → QuickSight.

## 레이크 거버넌스: AWS Lake Formation

Nimbus의 데이터 레이크가 성장하면서, 데이터 액세스가 거버넌스 문제가 되었습니다.

"누가 원시 거래 로그를 쿼리할 수 있죠?" Priya가 다음 아키텍처 검토에서 물었습니다. "누가 고객 PII를 볼 수 있죠? 누가 재무 요약 테이블에 액세스할 수 있죠?"

"엔지니어링이 전체 액세스를 가져요," Leo가 말했습니다. "분석 팀이 집계된 테이블에 액세스를 가져요. 재무가 매출 테이블에 액세스를 가져요."

"어디에 구성되어 있죠?"

Leo가 멈췄습니다. "음... 몇 개의 다른 장소에요. S3 버킷 정책, IAM 정책, Glue 카탈로그 권한."

"세 개의 별도 시스템, 모두 일관되어야 하는," Priya가 말했습니다. "우리가 새 분석가를 추가하면 어떻게 되죠? 또는 특정 열 — 예를 들어, 고객 전화번호 — 에 대한 액세스를 분석 팀에서 제한하기로 결정하면요?"

그 질문이 격차를 드러냈습니다. S3 버킷 정책, IAM, Glue Data Catalog에 걸쳐 동시에 세밀한 데이터 액세스를 관리하는 것이 깨지기 쉬웠습니다.

**AWS Lake Formation**은 데이터 레이크에 대한 액세스 통제를 중앙 집중화하는 관리형 서비스입니다. 버킷 정책, IAM 정책, Glue 카탈로그 권한을 별도로 관리하는 대신, Lake Formation이 데이터에 대한 열 수준, 행 수준, 테이블 수준 권한을 부여할 단일 장소를 제공합니다.

핵심 기능:

- S3와 Glue Data Catalog 위에 앉음 — 데이터 마이그레이션 필요 없음
- **세밀한 액세스 통제:** 특정 사용자나 역할에게 특정 테이블, 열, 또는 심지어 필터링된 행에 대한 액세스를 부여 — S3 데이터에 대한 데이터베이스 수준 권한의 등가물
- **데이터 필터링:** 사용자가 Athena를 통해 Lake Formation 관리 테이블을 쿼리하면, Lake Formation이 그들이 볼 수 없는 열이나 행을 자동으로 필터링함

Priya가 세 개의 권한 계층으로 Lake Formation을 설정했고, Rafael이 열 수준 규칙을 작성했습니다: 엔지니어링 역할이 모든 테이블과 모든 열을 보았습니다. 분석 역할이 집계된 주문 테이블을 보았지만 고객 PII 열은 보지 못했습니다. 재무 역할이 고객 식별자가 마스킹된 매출 테이블을 보았습니다.

"그러니까 분석가가 같은 Athena 쿼리를 실행해요," Leo가 확인했습니다. "하지만 Lake Formation이 그것을 가로채서 그들이 볼 권한이 없는 열을 제거해요?"

"맞아요. 필터링이 자동이에요. 분석가가 그것이 일어나고 있다는 것을 알 필요가 없어요 — 그리고 그들이 원시 S3 파일을 직접 쿼리해서 그것을 우회할 수 없어요, Lake Formation이 카탈로그 수준에서 액세스를 통제하기 때문이에요."

"그건 추가 작업이 아니에요," Priya가 말했습니다. "그게 설계예요."

> **시험 팁 — Lake Formation**
>
> Lake Formation은 S3와 Glue Data Catalog 위에 구축된 데이터 레이크에 대한 액세스 통제를 중앙 집중화합니다. 테이블, 열, 행 수준에서 세밀한 권한을 지원합니다. 시험 트리거: "S3 데이터 레이크의 특정 열에 대한 액세스 제한" 또는 "데이터 레이크 거버넌스 중앙 집중화" → Lake Formation. 원시 IAM과의 핵심 구별: Lake Formation이 IAM 정책 단독으로 표현할 수 없는 열 및 행 수준 필터링을 강제합니다.

## 장점과 한계

**Kinesis Data Streams**: 데이터가 지속적으로 도착하고 순서가 중요할 때 Kinesis를 사용하십시오 — 클릭스트림, 금융 거래, IoT 텔레메트리. Kinesis가 샤드 내 레코드 순서를 보존하고 구성된 보존 창(기본 24시간, Extended Data Retention으로 최대 365일) 동안 재생을 허용하며, 이것이 그것을 SQS와 근본적으로 다르게 만듭니다. 절충안은 운영 복잡성입니다: 프로비저닝된 모드에서, 샤드 용량과 소비자 동작을 관리합니다. 순서가 중요하지 않고 재생이 필요 없는 단순한 작업 큐의 경우, SQS가 더 단순한 선택입니다.

**AWS Glue**: Glue가 전통적인 ETL 클러스터의 인프라를 제거합니다. 변환 로직을 작성하면; AWS가 Spark 환경을 관리합니다. 이것은 변환이 복잡하거나 데이터 볼륨이 클 때 가치 있습니다. 한계는 비용과 콜드 스타트입니다 — Glue 작업이 몇 분의 시작 지연이 있어, 거의 실시간 변환에 부적합하게 만듭니다. 단순한 파일 형식 변환(CSV에서 Parquet)의 경우, Glue의 오버헤드가 Lambda 함수나 경량 스크립트에 비해 그만한 가치가 없을 수 있습니다.

**Amazon Athena**: Athena가 표준 SQL로 그리고 관리할 인프라 없이 S3 데이터를 쿼리하게 합니다. 핵심 제약은 비용입니다: Athena가 스캔된 데이터 테라바이트당 요금을 부과합니다. 전체를 스캔하는 10 TB 테이블에 대한 쿼리가 200 GB를 스캔하는 Parquet 형식, 파티셔닝된 테이블에 대한 같은 쿼리보다 상당히 더 많이 듭니다. 프로덕션에서 Athena를 실행하기 전에 항상 컬럼형 형식(Parquet 또는 ORC)을 사용하고 데이터를 파티셔닝하십시오. 이 최적화 없이는, Athena 청구서가 여러분을 놀라게 할 수 있습니다.

## 요약

25장의 네트워크 작업이 Nimbus의 데이터 파이프라인을 가능하게 했습니다. 이 챕터는 그 파이프라인이 무엇을 위한 것인지입니다: Nimbus가 생성해 온 모든 데이터를 실제로 보이고 실행 가능하게 만드는 것.

- **Amazon Kinesis**: 실시간 데이터 스트리밍. 생산자가 레코드를 쓰고; 소비자가 자체 속도로 읽습니다. Amazon Data Firehose가 그러고 나서 더 적은 운영 작업으로 스트리밍 데이터를 S3, Redshift, 그리고 다른 대상으로 배달할 수 있습니다.
- **AWS Glue**: ETL과 데이터 카탈로깅. 크롤러가 스키마를 발견하고; 작업이 데이터를 변환하고; Data Catalog가 Athena와 다른 도구에 데이터를 발견 가능하게 만듭니다.
- **Amazon Athena**: S3에 대한 서버리스 SQL. 표준 SQL을 사용해 S3의 어떤 데이터든 쿼리합니다. 스캔된 TB당 가격 책정 — 비용을 최소화하기 위해 Parquet과 파티셔닝을 사용하십시오.
- **Amazon Redshift**: 고성능 분석을 위한 관리형 데이터 웨어하우스. 데이터를 로드하고, 반복적인 분석 쿼리를 위해 최적화하고, 웨어하우스 규모에서 빠르게 쿼리합니다.
- **데이터 레이크 패턴**: 원시 데이터를 S3로 → Glue가 그것을 변환 → Athena가 그것을 쿼리 → BI 도구가 그것을 시각화.
- **Glue 스키마 진화**: 외부 데이터를 처리하는 ETL 파이프라인은 스키마 변경을 우아하게 처리해야 합니다. 업스트림 데이터가 새 필드를 추가할 때 파이프라인 실패를 피하기 위해 `mergeSchema: true`와 함께 DynamicFrame을 사용하십시오.
- **Athena 워크그룹**: 팀별 데이터 스캔 제한과 결과 위치. 하나의 구성에 비용 통제와 액세스 통제. 모든 다중 팀 Athena 배포에 필요함.
- **Kinesis vs SQS**: 여러 소비자로의 팬 아웃과 재생 능력에는 Kinesis. 단순한 작업 큐에는 SQS Standard; 순서가 정해지고, 중복 제거된 작업 처리에는 SQS FIFO. 결정 질문: 모든 소비자가 모든 메시지를 봐야 하는가, 또는 각 메시지가 한 소비자로 가는가?
- **Athena가 잘못된 때**: 고빈도 대시보드(Redshift 사용), 운영 쿼리(RDS나 DynamoDB 사용), 매우 작고 자주 변하는 데이터셋(그냥 데이터베이스 사용).
- **Amazon QuickSight**: AWS의 관리형 BI 서비스. Athena, S3, Redshift, RDS에 연결해 별도의 BI 서버를 실행하지 않고 대시보드를 구축합니다. SPICE는 반복적인 대시보드 쿼리를 가속하는 인메모리 엔진입니다.
- **AWS Lake Formation**: S3 + Glue Data Catalog의 데이터 레이크에 대한 중앙 집중식 액세스 통제. 열 수준, 행 수준, 테이블 수준 권한을 가능하게 함 — IAM 단독으로 표현할 수 없는 세밀한 데이터 거버넌스.

## 시험 팁

*SAA-C03 도메인: 고성능 아키텍처 설계(도메인 3, 태스크 3.5)*

- **Kinesis vs SQS**: Kinesis = 순서가 정해진, 실시간 스트리밍, 여러 소비자, 보존 창 내 재생(기본 24시간, 최대 365일). SQS = 작업 큐, 각 메시지가 한 번 처리됨. "여러 소비자가 같은 스트림을 동시에 읽음" → Kinesis. "메시지당 한 작업자" → SQS.
- **Athena 시험 신호**: "S3에 대한 서버리스 SQL," "데이터베이스에 로드하지 않고 S3 데이터 분석," "쿼리당 지불" → Athena.
- **Athena 비용 최적화**: 컬럼형 형식(Parquet 또는 ORC) + 파티셔닝이 스캔된 데이터와 비용을 극적으로 줄입니다. 시험이 Athena 비용을 줄이는 법을 물을 수 있습니다.
- **Athena 가격**: 스캔된 TB당 $5(us-east-1, us-west-2, 그리고 대부분의 주요 리전). 비용이 반환된 데이터가 아니라 스캔된 데이터에 계산됨 — 프로덕션 쿼리를 실행하기 전에 항상 스토리지 형식을 최적화하십시오.
- **Glue Crawler**: "S3 데이터의 스키마 자동 발견" → Glue Crawler.
- **Amazon Data Firehose**: "소비자를 관리하지 않고 스트리밍 데이터를 S3/Redshift/OpenSearch로 자동 로드" → Amazon Data Firehose. 오래된 자료가 여전히 그것을 Kinesis Data Firehose라고 부를 수 있습니다.
- **Redshift vs Athena**: 고정 데이터셋에 대한 고빈도, 복잡한 쿼리(BI 대시보드)에는 Redshift. 자주 변하는 S3 데이터에 대한 임시 쿼리에는 Athena.
- **EMR(Elastic MapReduce)**: AWS 관리형 Hadoop/Spark 클러스터. 시험이 "기존 Hadoop/Spark 워크로드" 또는 "커스텀 데이터 처리 프레임워크"가 언급될 때 이것을 사용합니다. Glue가 대부분의 사용 사례에 관리형 대안입니다.
- **QuickSight:** AWS 관리형 BI 및 시각화. Athena, S3, Redshift, RDS에 연결. SPICE = 빠른 반복 쿼리를 위한 인메모리 엔진. 시험 트리거: "AWS의 비즈니스 인텔리전스 대시보드" → QuickSight.
- **Lake Formation:** 데이터 레이크(S3 + Glue Data Catalog)에 대한 중앙 집중식 액세스 통제. 세밀한 권한: 테이블, 열, 행 수준. 시험 트리거: "S3 데이터 레이크의 특정 열에 대한 액세스 제한" 또는 "데이터 레이크 거버넌스 중앙 집중화" → Lake Formation.

## 연습 문제

**연습 1 — 회상**

Amazon Kinesis와 Amazon SQS의 차이를 설명하십시오. 어떤 때 각각을 사용하겠습니까?

*(힌트: 얼마나 많은 소비자가 같은 데이터를 읽을 수 있는지, 메시지가 읽은 후 삭제되는지, 그리고 순서가 중요한지 생각해보십시오.)*

**연습 2 — SAA-C03 시나리오**

*시나리오*: 차량 공유 회사가 트립 데이터를 분석하고 싶어합니다. 매일 100만 트립이 완료됩니다. 트립 레코드가 JSON 파일(각각 약 2KB)로 S3에 저장됩니다. 분석 팀이 "지난주 도시별 평균 트립 시간" 같은 임시 SQL 쿼리를 실행하고 싶어합니다. 쿼리가 2분 미만에 완료되어야 합니다. 스토리지 비용이 최소화되어야 합니다. 팀이 주당 20~30개 쿼리를 실행할 것입니다.

이 요구사항을 가장 잘 충족하는 아키텍처는 무엇입니까?

A) AWS Glue를 사용해 JSON을 날짜와 도시별로 파티셔닝된 Parquet 형식으로 변환; Amazon Athena로 쿼리  
B) 매일 트립 데이터를 RDS PostgreSQL에 로드; 표준 SQL을 사용해 쿼리  
C) Amazon Data Firehose를 사용해 트립 데이터를 Amazon Redshift로 배달; Redshift로 쿼리  
D) 트립 데이터를 DynamoDB에 로드하고 SQL 쿼리를 위해 PartiQL 사용

**힌트 1**: 주당 20~30개 쿼리는 낮은 빈도입니다. 어떤 서비스가 가끔의 쿼리에 가장 비용 효율적입니까?

**힌트 2**: Parquet 형식 + 파티셔닝이 Athena에 의해 스캔된 데이터를 — 따라서 비용을 — 극적으로 줄입니다.

**힌트 3**: 100만 트립 × 2KB = 하루에 ~2GB. 일주일에 걸쳐, ~14GB. Athena의 $5/TB에서, 최적화 없이도, 이것은 감당 가능합니다.

**정답**: A

**설명**: Glue가 JSON을 Parquet으로 변환하고(컬럼형 형식이 스캔된 데이터를 극적으로 줄임) 날짜와 도시별로 파티셔닝합니다(파티션 프루닝은 "지난주" 쿼리가 7일의 파티션만 스캔한다는 것을 의미). Athena가 표준 SQL로 S3를 직접 쿼리합니다. 주당 20~30개 쿼리의 경우, 쿼리당 지불 Athena가 항상 실행되는 Redshift에 비해 극도로 비용 효율적입니다.

**왜 B가 아닌가?** 매일 2GB의 데이터를 RDS에 로드하고, 그러고 나서 쿼리하는 것은 24시간 내내 실행되는 데이터베이스 인스턴스가 필요합니다. 주당 20~30개 쿼리의 경우, 이것은 대단히 과잉 설계되고 비쌉니다.

**왜 C가 아닌가?** Redshift는 고빈도 쿼리(같은 데이터셋에 대해 하루에 수백 개)에 비용 효율적입니다. 주당 20~30개 쿼리의 경우, 항상 켜진 Redshift 클러스터가 Athena의 쿼리당 가격보다 훨씬 더 많이 듭니다.

**왜 D가 아닌가?** DynamoDB는 임시 분석 쿼리가 아니라 키 기반 액세스에 최적화된 키-값/문서 저장소입니다. DynamoDB의 PartiQL은 설명된 종류의 GROUP BY 집계를 지원하지 않습니다.

*SAA-C03 도메인: 고성능 아키텍처 설계 — 태스크 3.5*

## 포스트 크레딧 장면

Tom이 첫 Athena 쿼리를 실행했습니다.

"지난 분기 매출 기준 상위 10개 레스토랑," 그가 말했습니다.

12초 후, 결과가 나타났습니다.

그가 그것들을 응시했습니다.

"레스토랑 47이 첫 번째였어요," 그가 말했습니다. 그것은 Maya 가족의 레스토랑이었습니다 — Nimbus가 시작된 곳.

"당연하죠," Maya가 말했습니다. "Arepa가 그렇게 맛있어요."

Tom이 또 다른 쿼리를 실행했습니다. 그리고 또 다른. "그게 월 얼마나 들죠?" Tom이 Leo가 뭐라고 말하기 전에 물었습니다. Leo가 쿼리 스캔 기록을 확인했습니다. 세 개 쿼리, 총 스캔된 데이터: 1.2GB. 비용: 1센트 미만.

한 시간 후, Tom이 이전에 가져본 적 없는 방식으로 Nimbus 비즈니스의 완전한 그림을 가졌습니다. 어떤 레스토랑 카테고리가 가장 빠르게 성장했는지. 어떤 고객 코호트가 가장 오래 유지되었는지. 어떤 메뉴 항목이 가장 많은 반복 주문을 이끌었는지.

"왜 우리가 이걸 더 일찍 안 만들었죠?" 그가 물었습니다.

"우리가 데이터를 가지고 있었어요," Leo가 말했습니다. "우리가 그저 그것을 사용할 파이프라인이 없었을 뿐이에요."

"데이터가 항상 거기 있었어요," Maya가 조용히 말했습니다. "우리가 그저 그것을 볼 수 없었어요."

다음 챕터에서: 이제 우리가 비즈니스를 명확하게 볼 수 있으니, 그것을 실행하는 인프라에 어떻게 더 효율적으로 비용을 지불할지 이야기해봅시다.
