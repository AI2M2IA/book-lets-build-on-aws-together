**세 가지 위협 카테고리**

클라우드 애플리케이션에 대한 보안 위협은 일반적으로 세 가지 카테고리로 나눈다:

**볼륨 공격(DDoS)**: 공격자가 애플리케이션이 정상 사용자에게 응답할 수 없을 만큼 많은 트래픽을 보낸다. 공격은 수백만 개의 HTTP 요청이거나, 서버의 연결 테이블을 소진시키도록 설계된 TCP SYN 패킷 홍수일 수 있다.

**애플리케이션 공격(익스플로잇)**: 공격자가 애플리케이션의 약점을 악용하도록 설계된 특별히 제작된 요청을 보낸다 — SQL 인젝션, 교차 사이트 스크립팅, 파서를 충돌시키는 잘못된 입력.

**행동 이상(정찰 및 침해)**: 일어나서는 안 되는 API 호출(누군가 새벽 3시에 전체 사용자 데이터베이스를 쿼리), 비정상적인 IAM 활동(새 국가에서 사용되는 자격증명), 또는 예상치 못한 대상으로의 네트워크 트래픽.

AWS는 각각에 대한 전용 서비스가 있다:

- **AWS Shield**: DDoS 보호
- **AWS WAF**: 애플리케이션 레이어 보호
- **Amazon GuardDuty**: 행동 위협 감지

**AWS Shield: DDoS 흡수기**

**AWS Shield Standard**는 추가 요금 없이 모든 AWS 고객에게 자동으로 활성화된다. 가장 흔한 레이어 3(네트워크) 및 레이어 4(전송) DDoS 공격으로부터 보호한다 — SYN 홍수, UDP 홍수, DNS 증폭 공격.

CloudFront, Route 53, Elastic Load Balancing은 AWS 네트워크의 엣지에 앉아 있다. DDoS 공격이 애플리케이션을 타겟으로 할 때, 이 관리형 서비스들을 먼저 타격한다. AWS의 네트워크 인프라가 그것이 EC2 인스턴스에 도달하기 전에 공격을 흡수한다.

**AWS Shield Advanced**는 프리미엄 계층(조직당 월 $3,000, 1년 약정)이다. 별도의 구독이다 — 어떤 AWS Support 플랜에도 *포함되지 않는다*. 다음을 추가한다:

- EC2, ELB, CloudFront, Global Accelerator, Route 53에 대한 보호
- 거의 실시간 공격 알림
- AWS Shield Response Team(SRT)에 대한 접근 — 공격 대응을 도울 수 있는 보안 엔지니어(SRT 참여는 추가로 Business나 Enterprise Support 플랜을 요구한다)
- 비용 보호: 공격이 청구서를 급등시키면, AWS가 급등 비용을 크레딧으로 제공
- 레이어 7(애플리케이션 레이어)에서 강화된 DDoS 감지 및 완화

"그게 한 달에 얼마나 들어?" Tom이 물었다.

**DDoS 사건: Shield가 작동하는 모습**

Leo가 CloudFront 메트릭을 먼저 봤다. "요청 속도가 60배 올랐어요. 응답 시간이 급등하고 있어요."

Priya가 CloudWatch 메트릭을 나란히 열었다: 엣지에서 연결 시도가 수직으로 오르고, 실제로 오리진에 도달하는 요청은 — 평평하다. "Shield Standard가 그걸 먹고 있어," 그녀가 말했다. 경고도, 대시보드 이벤트도, 알림도 없었다. Shield Standard는 조용히 작동한다: 항상 켜져 있고, 무료이며, **공격 가시성을 주지 않는다** — 이벤트 콘솔도, 알림도, DDoS 대응 팀도 없다. (그 가시성 — 거의 실시간 공격 대시보드와 경고 — 이 정확히 Shield *Advanced*가 파는 것이다.) Priya가 공격을 볼 수 있는 유일한 방법은 자신의 CloudWatch 메트릭을 통해서였다.

Shield Standard가 SYN 홍수를 자동으로 감지하고 첫 2분 내에 완화를 시작했다. 공격 트래픽이 전 세계 CloudFront의 엣지 노드에서 흡수되고 있었다 — 합법적인 콘텐츠를 제공한 동일한 750개 이상의 접속 지점이 공격 볼륨도 흡수했다.

**AWS WAF: 애플리케이션 필터**

**AWS WAF(Web Application Firewall)**는 HTTP 레이어에서 운영된다 — 웹 요청의 내용을 애플리케이션에 도달하기 전에 검사한다.

WAF는 무엇을 허용하고, 차단하거나, 계산할지를 정의하는 규칙 세트인 **웹 ACL(Access Control Lists)**로 설정된다.

WAF는 다음에 연결할 수 있다:

- CloudFront 배포(전 세계적으로 엣지에서 요청 검사)
- Application Load Balancer(리전 수준에서 요청 검사)
- API Gateway
- AWS AppSync

**WAF 관리 규칙**: AWS와 타사 공급업체가 사전 구축된 규칙 세트를 게시한다:

- **AWS 관리 규칙 - 핵심 규칙 세트**: 동반 규칙 그룹(SQL 데이터베이스, 알려진 나쁜 입력)과 함께, OWASP 상위 10개 취약점(SQL 인젝션, XSS, 명령 인젝션, 경로 탐색 등)을 다룬다
- **AWS 관리 규칙 - 알려진 나쁜 입력**: 알려진 공격 패턴과 일치하는 요청 차단
- **AWS 관리 규칙 - Amazon IP 평판 목록**: 봇넷 및 스캐너와 연관된 것으로 알려진 IP 차단
- **AWS 관리 규칙 - 봇 제어**: 봇 트래픽 식별 및 관리

사용자 정의 규칙도 만들 수 있다:

- "'sqlmap'을 포함하는 User-Agent 헤더가 있는 모든 요청 차단"(일반적인 SQL 인젝션 스캐너)
- "속도 제한: IP당 5분당 1000개 요청 이상 허용하지 않음"
- "파라미터 값에 `<script>`를 포함하는 요청 차단"

Nimbus의 경우, 실용적인 설정: CloudFront 배포에 핵심 규칙 세트가 활성화된 WAF. 이것이 가장 흔한 공격 패턴을 요청이 EC2 인스턴스에 절대 도달하기 전에 차단한다.

여러분은 궁금할 것이다: WAF가 알려진 공격 패턴을 차단한다면, WAF가 모르는 새 공격 패턴이 나타나면 무슨 일이 일어나는가? WAF 관리 규칙 세트는 새 위협이 나타나면서 AWS와 타사 공급업체에 의해 업데이트된다 — 규칙을 수동으로 업데이트할 필요가 없다. 하지만 WAF가 근본적으로 알려진 패턴에 반응적이라는 것은 옳다. 새롭고 참신한 공격 기법은 아직 존재하지 않는 규칙에 의해 차단되지 않을 것이다. 이것이 GuardDuty가 WAF와 함께 존재하는 이유다: WAF가 정문을 필터링하고, GuardDuty가 집 안의 비정상적인 행동을 감시한다. 새 공격 유형이 WAF를 통과할 수 있지만, GuardDuty가 여전히 그것이 일으키는 이상 활동을 플래그할 수 있다 — 비정상적인 API 호출, 예상치 못한 네트워크 대상, 기준선과 일치하지 않는 접근 패턴.

**WAF가 잘못된 긍정을 일으키면 무슨 일이 일어나는지 생각해봤어?** Priya가 물었다. "핵심 규칙 세트에 의해 차단되는 합법적인 사용자의 요청?"

"WAF에는 'Count' 모드가 있어요," Leo가 말했다. "차단하는 대신, 일치하는 요청을 그냥 계산해요. 먼저 Count 모드로 실행하고, 무엇을 차단했을지 검토하고, 잘못된 긍정이 없는지 검증하고, 그런 다음 Block으로 전환해요."

"좋아," Priya가 말했다. "Count 모드로 시작해."

**WAF 규칙 만들기: 속도 제한 이야기**

WAF를 Count 모드로 활성화한 2주 후, Priya가 로그를 검토했다. 핵심 규칙 세트 발견 사항이 깨끗했다 — 합법적인 트래픽에 잘못된 긍정 없음, 자동화 스캐너에서의 소수의 차단된 SQL 인젝션 시도.

하지만 그녀는 핵심 규칙 세트가 플래그하지 않는 패턴을 알아챘다: 하나의 IP 주소가 5분 동안 `/api/search`에 847개의 요청을 했다. 모든 요청이 구조적으로 유효했다. 하지만 5분에 847개의 검색은 사람이 아니었다.

"가격 스크레이퍼," 그녀가 말했다. "누군가 경쟁 가격 데이터베이스를 만들기 위해 우리 레스토랑 검색을 자동으로 쿼리하고 있어."

"우리가 신경 써요?" Leo가 물었다.

"우리 컴퓨트 리소스를 사용하고 우리 서비스 약관에 위배돼," Tom이 말했다.

"신경 써," Priya가 확인했다.

그녀가 사용자 정의 WAF 속도 기반 규칙을 만들었다:

```
규칙 이름: RateLimitSearchAPI
규칙 유형: 속도 기반 규칙
속도 제한: IP 주소당 100개 요청
평가 윈도우: 5분 (설정 가능: 1, 2, 5, 또는 10분)
범위 축소 문장: URI 경로가 /api/search로 시작
액션: 차단
```

범위 축소 문장이 중요하다 — 속도 제한이 `/api/search`에만 적용된다. 다른 엔드포인트로의 합법적인 API 트래픽은 영향받지 않는다. 그리고 차단이 어떻게 작동하는지 유의하라: 고정된 "처벌" 기간이 없다 — WAF가 각 IP의 요청 속도를 지속적으로 재평가하고, 속도가 제한 위에 머무는 동안 차단하고, 속도가 다시 아래로 떨어지면(보통 몇 초 내에) 차단을 해제한다.

그녀가 먼저 Count 모드로 설정했다. 24시간 실행했다. 규칙을 발동시킨 유일한 IP는 스크레이퍼였다. 어떤 합법적인 사용자도 5분 동안 검색 엔드포인트에 12개 이상의 요청을 보낸 적이 없었다.

그녀가 Block 모드로 전환했다. 스크레이퍼의 다음 요청이 403을 받았다. 다른 IP로 전환했다. 속도 제한이 그것도 잡았다.

"결국 우회할 거예요," Leo가 말했다. "더 많은 IP에 분산해서."

"그 시점에 그들은 더 많은 인프라를 사용하고, 더 많이 지불하고, 더 적은 데이터를 얻어," Priya가 말했다. "우리는 그들을 완전히 멈출 필요가 없어. 가치가 없을 만큼 비싸게 만들면 돼."

"그게 한 달에 얼마나 들어?" Tom이 물었다.

WAF 가격은 웹 ACL당 월별, 규칙당 월별, 백만 요청당이다. Nimbus 설정 — CloudFront에 하나의 웹 ACL, 다섯 개의 규칙 — 의 경우, 약 월 $15 더하기 요청 요금.

Tom이 즉시 승인했다.

**Amazon GuardDuty: 행동 분석가**

"잠깐 — 그런데 *왜* 그렇게 하는 거죠?" Maya가 물었다. "WAF가 공격을 차단하고 Shield가 홍수를 흡수한다면, 왜 세 번째 서비스가 필요해요? GuardDuty가 실제로 무엇을 감시하죠?"

WAF와 Shield는 필터다 — 나쁜 트래픽이 애플리케이션에 도달하기 전에 가로챈다. GuardDuty는 트래픽이 도착한 후 무슨 일이 일어나는지 감시한다. 인프라가 무엇을 하고 있는지를 본다: 어떤 IAM 자격증명이 사용되고 있는지, 인스턴스가 어떤 도메인에 접촉하고 있는지, 새벽 3시에 어떤 API 호출이 일어나고 있는지. 합법적으로 보이는 요청을 통해 정문을 통과한 공격자는 WAF에 의해 멈추지 않을 것이다 — 하지만 GuardDuty가 같은 자격증명이 갑자기 루마니아에서 API 호출을 하고 있다는 것을 알아챌 것이다.

GuardDuty는 Shield와 WAF와 근본적으로 다르다. 공격을 차단하지 않는다 — **비정상적인 행동을 감지**한다.

GuardDuty는 위협을 감지하기 위해 여러 활동 스트림을 지속적으로 분석한다: **CloudTrail 관리 및 데이터 이벤트**(API 호출과 액션), **VPC 흐름 로그**(네트워크 트래픽 패턴), **DNS 쿼리 로그**(도메인 조회). 이것이 GuardDuty가 항상 의존해온 세 가지 기초 소스다:

- **AWS CloudTrail 로그**: IAM 변경, API 호출, 콘솔 로그인
- **VPC 흐름 로그**: VPC 내의 네트워크 트래픽 패턴
- **DNS 쿼리 로그**: 인스턴스가 해석하는 것(알려진 맬웨어가 종종 특정 C2 도메인을 해석한다)

하지만 GuardDuty는 이 세 가지를 훨씬 넘어 크게 확장됐다. AWS는 선택적 추가 기능을 **보호 플랜**이라고 부른다 — S3 Protection, EKS Protection, RDS Protection, Lambda Protection, Runtime Monitoring, Malware Protection — 각각 개별적으로 활성화된다. 어떤 것을 활성화하느냐에 따라, GuardDuty는 또한 **S3 데이터 이벤트**(버킷에 대한 비정상적인 접근 패턴), **EKS 감사 로그 및 런타임 활동**(실행 중인 컨테이너 내부의 악성 행동), **RDS 로그인 이벤트**(비정상적인 데이터베이스 로그인 시도), **Lambda 네트워크 트래픽**(예상치 못한 외부 대상을 호출하는 함수), **ECS/EC2 런타임 행동**, **맬웨어를 위해 스캔되는 EBS 볼륨**을 분석할 수 있다. 시험을 위해, 세 가지 핵심 소스를 외워라; 보호 플랜은 특정 위협 감지 컨텍스트에 대한 시나리오에 나타난다 — "RDS에 대한 비정상적인 로그인 시도 감지" 또는 "실행 중인 컨테이너 내부의 악성 행동 식별"은 GuardDuty의 선택적 보호 플랜을 생각하라는 신호다.

머신 러닝 모델이 기준에서 벗어나는 패턴을 식별한다. GuardDuty가 이상을 감지하면 **발견** — 분류된 경고 — 를 생성한다.

GuardDuty가 감지할 수 있는 예시:

- 인식할 수 없는 IP 주소(이전에 사용한 적 없는 국가)에서 로그인하는 IAM 사용자
- Tor 종료 노드에서 이루어지는 API 호출
- 알려진 암호화폐 채굴 풀과 통신하는 EC2 인스턴스
- 비정상적으로 높은 API 호출 볼륨(자격증명 남용 또는 스캔)
- 악성 활동으로 플래그된 IP 주소에 의해 접근되는 S3 버킷
- 맬웨어 명령-및-제어와 연관된 것으로 알려진 도메인으로의 아웃바운드 트래픽

"이것이 루마니아 IP를 잡았을 것이에요," Leo가 조용히 말했다.

"GuardDuty가 활성화됐다면, 새벽 2시에 인식할 수 없는 외부 IP로 아웃바운드 연결을 하는 EC2 인스턴스에 플래그를 세웠을 거예요," Priya가 확인했다.

**다섯 가지 GuardDuty 발견 유형과 할 일**

Priya가 가장 흔한 다섯 가지 GuardDuty 발견에 대한 런북을 만들었다. 발견이 발화하면, 팀이 그것이 무엇을 의미하고 무엇을 해야 하는지 즉시 안다.

**1. UnauthorizedAccess:IAMUser/ConsoleLoginSuccess.B**

IAM 사용자가 이 계정에 대해 이전에 보지 못한 IP 주소에서, 또는 이전 로그인과 일치하지 않는 지리적 위치에서 AWS 콘솔에 성공적으로 로그인했다.

대응: 사용자에게 로그인을 시작했는지 확인한다. 하지 않았다면 — 또는 연락할 수 없으면 — 즉시: 사용자의 액세스 키와 콘솔 비밀번호를 비활성화하고, 활성 세션을 취소하고, 그 사용자가 지난 24시간 동안 한 모든 것의 CloudTrail 감사를 시작한다. 이 발견은 종종 자격증명 남용에 선행한다.

**2. CryptoCurrency:EC2/BitcoinTool.B**

EC2 인스턴스가 암호화폐 채굴 풀과 연관된 IP 주소나 도메인 이름을 쿼리하고 있다. 이것은 거의 항상 EC2 인스턴스가 침해되어 채굴 봇으로 사용된 결과다.

대응: 인스턴스를 즉시 격리한다 — 배스천 호스트를 제외한 모든 인바운드 및 아웃바운드 트래픽을 차단하도록 보안 그룹을 수정한다. EBS 볼륨의 포렌식 스냅샷을 찍는다. 그런 다음 인스턴스를 종료하고 깨끗한 AMI에서 교체를 시작한다.

**3. Recon:EC2/PortProbeUnprotectedPort**

EC2 인스턴스에 알려진 스캐너나 Tor 종료 노드에서 탐색되고 있는 인터넷에 열린 포트가 있다. GuardDuty가 흐름 로그에서 외부 소스에서 접근 가능한 것으로 나타나는 포트를 플래그한다.

대응: 보안 그룹 규칙을 검토한다. 포트가 의도적으로 열려 있으면, 메모와 함께 발견을 해결됨으로 표시한다. 의도적이지 않으면, 즉시 포트를 닫는다. 그 포트를 통해 발생했을 수 있는 어떤 접근이든 CloudTrail을 확인한다.

**4. Trojan:EC2/BlackholeTraffic**

EC2 인스턴스가 "블랙홀"로 식별된 IP 주소 — 맬웨어 명령-및-제어 인프라와 연관된 대상 — 와 통신하려 하고 있다. 이 IP로의 트래픽은 인스턴스가 감염되어 집에 전화하려 하고 있다는 것을 시사한다.

대응: CryptoCurrency 발견과 동일 — 격리, 스냅샷, 교체. 이 발견은 인스턴스의 활성 맬웨어를 나타낸다. 인스턴스를 제자리에서 청소하려 하지 마라; 깨끗한 AMI에서 새것을 만든다.

**5. Policy:S3/BucketBlockPublicAccessDisabled**

누군가 S3 버킷에서 Block Public Access 설정을 비활성화했다. 이것은 버킷이 공개적이라는 것을 의미하지 않는다 — 우연한 공개 노출을 방지하는 안전 메커니즘이 그 버킷에 대해 꺼졌다는 것을 의미한다. 이것은 종종 우연히 또는 잘못 설정된 배포의 일부로 이루어진다.

대응: 누가 변경을 했는지 조사한다(CloudTrail에 API 호출이 있을 것이다). 비활성화되어야 하는 문서화된 이유가 없는 한 Block Public Access를 다시 활성화한다. 이 발견이 미래에 발생하는 것을 방지하기 위해 계정 수준 Block Public Access 설정을 활성화하는 것을 고려한다.

"GuardDuty 발견에 대해 가장 중요한 것은," Priya가 말했다. "그것들이 경고가 아니라 — 가설이라는 거야. 각 발견이 '이 패턴이 비정상적으로 보인다'고 말해. 검증하고, 조사하고, 대응해. 일부는 잘못된 긍정일 거야. 대부분은 아닐 거고."

"우선순위를 어떻게 정해요?" Rafael이 물었다.

"GuardDuty가 심각도 수준을 할당해: 낮음, 중간, 높음. 높은 심각도 발견은 당일 대응이 필요해. 트로이 목마와 자격증명 침해 발견은 항상 높음이야. 포트 탐색 발견은 중간이나 낮음일 수 있어. 높음으로 시작해서 내려가."

"비용이 얼마나 들어?" Tom이 물었다.

GuardDuty 가격은 분석된 로그 볼륨을 기반으로 한다 — CloudTrail 이벤트, VPC 흐름 데이터, DNS 쿼리. 소~중간 규모 애플리케이션의 경우, 보통 월 $50-150. 대규모에서도 인프라 비용의 작은 부분이다.

Tom이 콘솔을 열고 활성화했다.

"괜찮을 거예요," Leo가 말했다. "그냥 모니터링이에요. 뭔가를 망가뜨리지 않아요."

"제가 이미 배포했어요," Leo가 덧붙였다 — 그러고는 GuardDuty 대시보드를 확인했다. "아. 샘플 발견만 있어요. 진짜는 시간이 좀 걸려요."

"GuardDuty는 정상이 어떻게 생겼는지의 기준선을 구축하는 데 시간이 필요해," Priya가 말했다. "며칠 줘. 첫 진짜 발견이 도착할 거야 — 항상 그래."

그녀가 그것에 대해 옳은 것으로 드러났다. 하지만 첫 발견은 이 챕터 끝의 이야기다.

**세 서비스 연결**

Shield, WAF, GuardDuty는 다른 레이어에서 작동하며 서로를 보완한다:

| 서비스     | 레이어                    | 무엇으로부터 보호                            | 액션                               |
|------------|---------------------------|---------------------------------------------|------------------------------------|
| AWS Shield | 네트워크/전송 (L3/L4)     | DDoS 홍수                                    | 공격 흡수/완화                     |
| AWS WAF    | 애플리케이션 (L7)         | OWASP 상위 10개, 봇, 스크레이퍼             | 요청 허용, 차단, 또는 계산         |
| GuardDuty  | 행동 (모든 로그)          | 이상, 침해된 자격증명, 맬웨어               | 감지 및 경고                       |

Shield가 홍수를 막는다. WAF가 물을 필터링한다. GuardDuty가 비정상적인 흐름 패턴을 위해 배관을 감시한다. Macie가 저수지에 저장된 것을 감사한다. Security Hub가 모든 대시보드를 한 번에 볼 수 있는 관제실이다.

각각의 실패 모드가 왜 모두가 필요한지 설명한다:

- 50Gbps SYN 홍수는 웹 요청이 아니다. WAF가 그것을 검사할 수 없다. GuardDuty가 연관된 CloudTrail 이벤트를 알아챌 수 있다. Shield가 그것을 막는다.
- 단일 SQL 인젝션 요청은 홍수가 아니다. Shield가 그것을 무시한다. GuardDuty는 HTTP 요청의 내용을 모른다. WAF가 그것을 잡는다.
- 자신의 자격증명을 사용하여 데이터를 천천히 유출하는 합법적인 AWS 사용자 — DDoS 없음, 인젝션 없음, 유효한 HTTP — Shield와 WAF가 비정상적인 것을 아무것도 보지 못한다. GuardDuty가 자격증명이 새벽 3시에 새 국가에서 사용되고 있다는 것을 알아챈다.
- 우연히 고객 데이터를 공개 접근 가능 버킷에 업로드하는 개발자는 비정상적인 행동을 전혀 생성하지 않는다. GuardDuty가 플래그할 것이 없다. Macie가 버킷을 스캔하고 PII를 찾는다.

각 서비스에 맹점이 있다. 조합이 그 맹점을 커버한다.

**CloudTrail: 기반**

세 서비스 모두 로그에 의존한다. **AWS CloudTrail**은 AWS 계정의 모든 API 호출을 캡처하는 로깅 서비스다 — 누가 무엇을, 언제, 어디서, 어떤 결과로 호출했는지.

CloudTrail은 콘솔에서 90일 히스토리에 대해 기본으로 활성화된다. 장기간 로그를 보관하려면:

1. S3 버킷에 기록하는 추적을 만든다
2. 선택적으로, 실시간 경고를 위해 CloudWatch Logs로 보낸다
3. 로그 파일 유효성 검사를 활성화한다(로그가 변조됐는지 감지하기 위해)

GuardDuty, AWS Config, Security Hub, IAM Access Analyzer 모두 CloudTrail에서 읽는다. CloudTrail 로그 없이는 이 서비스들이 분석할 것이 없다.

"누군가 CloudTrail을 비활성화하려 하면?" Priya가 물었다. "공격자가 관리자 접근을 얻으면, 첫 액션이 로깅을 비활성화하는 것 — 흔적을 덮는 것 — 일 수 있어."

"그게 14장의 SCP가 방지하는 거예요," Leo가 말했다. "이 계정의 누구도 CloudTrail을 비활성화할 수 없어요, 관리자조차도."

"그리고 그들이 어떻게든 했다면?"

"Security Hub가 발견을 생성할 거예요. CloudTrail이 설정 변경 시 SNS에 알림을 보내요. 어떤 CloudTrail 수정의 2분 내에 경고를 받아요."

"그리고 GuardDuty가 그 API 호출을 플래그할 거예요," Rafael이 덧붙였다. "비정상적인 IAM 액션으로 — 로깅 비활성화는 정상 운영 활동이 아니니까요."

가장 중요한 보안 액션 중 하나에 대한 여러 레이어의 감지: 로그 변조. 이것은 우연이 아니었다. Priya가 의도적으로 설계했다.

"심층 방어가 모니터링 레이어에도 적용돼," 그녀가 말했다. "단지 애플리케이션 레이어만이 아니라."

**Amazon Macie: S3의 민감한 데이터**

"누군가 우연히 고객 신용카드 번호가 있는 파일을 S3에 업로드하면 무슨 일이 일어나는지 생각해봤어?" Priya가 물었다. "악의적으로가 아니라 — 그냥 개발자가 디버깅을 위해 데이터를 내보내고 잘못된 파일을 업로드하면?"

"우리가 절대 모를 거예요," Leo가 말했다.

"정확히. 우리에게 Macie가 없는 한."

**Amazon Macie**는 머신 러닝을 사용하여 S3의 민감한 데이터를 자동으로 발견하고 보호하는 데이터 보안 서비스다. 지속적으로 S3 버킷을 스캔하고 다음을 식별한다:

- PII(개인 식별 정보): 이름, 이메일 주소, 전화번호, 생년월일
- 재무 데이터: 신용카드 번호, 은행 계좌 번호
- 자격증명: 파일에 포함된 비밀번호, 액세스 키, 프라이빗 키
- 건강 정보: 환자 레코드, 진단

Macie는 민감한 데이터를 있어서는 안 되는 곳에서 감지하거나 — S3 버킷에 과도하게 허용적인 접근 설정이 있을 때 발견을 생성한다.

"이게 GuardDuty와 같은 거예요?" Maya가 물었다.

"다른 목적," Priya가 말했다. "GuardDuty는 행동을 감시해 — 어떤 액션이 취해지고 있는지, 그 액션이 이상하게 보이는지. Macie는 데이터를 감시해 — 어떤 콘텐츠가 저장되어 있는지, 그 콘텐츠가 민감한지. GuardDuty가 비정상적인 API 호출을 하는 EC2 인스턴스를 플래그할 거야. Macie가 신용카드 번호를 포함하는 S3 버킷을 플래그할 거야."

"그러니까 GuardDuty가 행동 분석가이고," Leo가 말했다. "Macie가 데이터 감사자네요."

"정확히. 둘 다 필요해. 합법적으로 보이는 API 호출을 통해 데이터를 유출하는 공격자가 비정상적인 API 패턴으로 GuardDuty에 의해 플래그될 수 있어. 하지만 직원이 만 명의 고객 레코드가 있는 파일을 개발 버킷에 업로드하면, 감지할 비정상적인 행동이 없어 — 그냥 잘못된 곳의 민감한 데이터야. Macie가 그것을 잡아."

Nimbus의 경우, Macie의 가장 즉각적인 가치는 `nimbus-debug-exports` 버킷 — 개발자가 디버깅을 위해 데이터를 덤프하는 데 사용한 버킷 — 에 있었다. Macie가 고객 이름과 배달 주소가 있는 주문 내역을 포함하는 세 개의 파일을 찾았다. 결제 데이터는 아니지만, 암호화되지 않은 개발 버킷에 있어서는 안 되는 개인 데이터.

파일이 제거됐다. 정책이 추가됐다: 디버그 버킷이 합성 테스트 데이터로만 제한됐다. 실제 고객 데이터는 프로덕션 외의 어떤 환경으로 내보내려면 Priya의 승인이 필요했다.

"그게 한 달에 얼마나 들어?" Tom이 물었다.

Macie는 월별 평가된 S3 버킷 수와 스캔된 데이터 볼륨을 기반으로 청구한다. 적당한 수의 버킷을 가진 스타트업의 경우, 약 월 $10-50. 처음 30일은 무료.

Tom이 점심 전에 활성화했다.

---

**AWS Security Hub: 대시보드**

여러 AWS 계정을 실행하거나 보안 발견의 통합된 뷰가 필요하다면, **AWS Security Hub**가 GuardDuty, Inspector(취약성 평가), Macie(데이터 프라이버시), Config, Firewall Manager의 발견을 단일 대시보드에 집계한다.

또한 보안 모범 사례(AWS Foundational Security Best Practices 표준)와 CIS AWS Foundations Benchmark에 대해 설정을 확인한다.

Security Hub는 "다섯 개의 다른 콘솔 사이를 전환하지 않고 어떻게 한 곳에서 모든 보안 발견을 보는가?"에 대한 답이다. GuardDuty가 발견을 생성하면, GuardDuty와 Security Hub에 나타난다. Macie가 S3 버킷에서 민감한 데이터를 찾으면, Macie와 Security Hub에 나타난다. Config 규칙이 잘못된 설정을 감지하면, Config와 Security Hub에 나타난다.

단일 계정 팀의 경우, Security Hub는 한계 가치를 더한다 — 확인할 또 다른 콘솔이다. 그 힘은 대규모에서 나타난다: 세 계정, 열 계정, 오십 계정. 모든 계정의 모든 발견이 관리 계정의 Security Hub에 집계된다. 한 팀이 하나의 대시보드를 모니터링한다. 하나의 경고 세트. 계정별 로그 확인 없음.

Nimbus의 경우: Security Hub는 아직 필요하지 않았다. 세 개의 계정(개발, 스테이징, 프로덕션)으로 성장하면, 필수적이 될 것이다.

"지금 설정해," Soo-Jin이 세 번째 주에 말했다. "활성화하는 데 15분 걸려. 더 일찍 했기를 바라는 데 3개월 걸려."

그들이 활성화했다.

**Amazon Inspector: 취약성 평가**

Macie를 활성화한 일주일 후, Nimbus 프로덕션 플릿 전체에서 실행되는 OpenSSL 버전에 대한 CVE가 게시됐다. Priya가 커피를 마시며 권고문을 읽었다.

"우리 인스턴스 중 어떤 것이 영향받는지 알아야 해," 그녀가 말했다.

"수동 스캔을 실행할 수 있어요," Leo가 말했다.

"아홉 개의 인스턴스에는, 그래. 아흔 개는? 컨테이너는?" Priya가 Inspector 콘솔을 열었다. "이게 Inspector가 있는 이유야."

**Amazon Inspector**는 자동화된 취약성 평가 서비스다. GuardDuty가 행동을 감시하는 — 인프라가 지금 무엇을 하고 있는지 — 곳에서, Inspector는 악용될 수 있는 무엇이 존재하는지를 본다.

- **EC2 인스턴스:** Inspector가 운영 체제와 설치된 패키지를 NVD(National Vulnerability Database) — 알려진 CVE의 권위 있는 카탈로그 — 에 대해 스캔한다. OpenSSL 1.1.1을 실행하고 있고 CVE가 그 버전을 타겟으로 하면, Inspector가 그것을 플래그한다.
- **ECR 컨테이너 이미지:** Inspector가 배포되기 전에 Elastic Container Registry의 컨테이너 이미지를 스캔한다. 베이스 이미지의 취약한 패키지가 컨테이너가 프로덕션에서 실행되기 전에 발견으로 나타난다.
- **Lambda 함수 패키지:** Inspector가 Lambda 함수에 번들된 의존성 — Python 패키지, Node 모듈, Java 의존성 — 을 알려진 취약점에 대해 분석한다.

일회성 스캔과의 결정적 차이: Inspector가 **지속적으로** 실행된다. 활성화할 때 인스턴스를 한 번 확인하고 깨끗하다고 선언하는 것이 아니다. 새 CVE가 게시되면, Inspector가 자동으로 기존 리소스를 새 취약점에 대해 재평가한다. EC2 인스턴스가 바뀌면 — 새 패키지 설치, AMI 업데이트 — Inspector가 그것을 다시 스캔한다. Priya의 EC2 플릿이 Inspector를 활성화한 몇 분 내에 OpenSSL CVE로 플래그됐다. 그녀가 스캔하라고 요청해서가 아니라, 그것이 그것이 하는 일이기 때문이다.

발견은 심각도 등급이 매겨진다: 치명적, 높음, 중간, 낮음, 정보. GuardDuty와 Macie 발견과 함께 Security Hub로 흐른다. 하나의 대시보드. 세 가지 렌즈 모두.

"세 인스턴스가 영향받았어요," Leo가 Inspector 발견을 읽으며 말했다. "다른 여섯 개는 패치된 버전에 있어요."

"이번 주에 그 세 개를 패치해," Priya가 말했다.

"컨테이너 이미지는요?"

Priya가 Inspector ECR 발견을 봤다. 컨테이너 레지스트리의 두 베이스 이미지에 알려진 취약점이 있었다 — 그 이후로 패치된 패키지의 이전 버전. 그녀가 재빌드를 위해 그것들을 태그했다.

"중요한 것은," Priya가 말했다. "우리가 이것을 악용되기 전에 발견했다는 거야. 후가 아니라."

**세 렌즈 모델**

GuardDuty, Inspector, Macie는 각각 다른 것을 감시한다:

- **GuardDuty**는 행동적이다. *지금 무엇이 일어나고 있고 잘못되어 보이는가?*를 묻는다. 예상치 못한 위치에서의 API 호출, 명령-및-제어 서버에 접촉하는 EC2 인스턴스, 비정상적인 시간에 사용되는 자격증명. 활성 위협과 이상을 잡는다.
- **Inspector**는 구조적이다. *우리 환경에 악용될 수 있는 무엇이 존재하는가?*를 묻는다. 패치되지 않은 패키지, 취약한 의존성, 오래된 런타임. 공격을 가능하게 하는 조건을 잡는다.
- **Macie**는 데이터에 관한 것이다. *있어서는 안 되는 어떤 민감한 정보가 우리 S3 버킷에 앉아 있는가?*를 묻는다. PII, 재무 레코드, 파일에 남겨진 자격증명. 비정상적인 행동을 생성하지 않는 노출을 잡는다 — 그냥 잘못된 곳의 데이터.

알려진 CVE를 포함하는 침해는 세 가지 모두에 나타날 수 있다: Inspector가 공격 전에 취약점을 플래그했을 것이다. GuardDuty가 공격 중 비정상적인 행동을 플래그할 것이다. Macie가 S3에 도착한 후 유출된 데이터를 플래그할 것이다.

세 가지 다른 렌즈, 세 가지 다른 시간 지평, 어느 것도 다른 것을 대체하지 않는다.

**AWS Network Firewall: 트래픽 검사기**

도구 상자가 닫히기 전에 한 명의 전문가가 더 언급될 가치가 있다. 보안 그룹과 NACL(15장)은 IP, 포트, 프로토콜로 트래픽을 필터링한다 — *누가* *무엇*과 통신할 수 있는지 말할 수 있지만, 대화 안을 들여다볼 수 없다. **AWS Network Firewall**은 VPC 수준에 배포하는 관리형, 상태가 있는 방화벽이다. 심층 패킷 검사를 수행한다: 도메인 이름으로 필터링(`*.eatnimbus.com`과 패키지 저장소로만 아웃바운드 허용), 침입 시그니처와 일치하는 트래픽 차단(IDS/IPS, Suricata 규칙과 호환), 포트 번호가 괜찮아 보여서 보안 그룹이 그냥 통과시킬 흐름 검사.

"그러니까 두뇌가 있는 보안 그룹이네요," Leo가 말했다.

"방화벽 공급업체에서 살 어플라이언스야," Priya가 말했다. "관리되고, 자동 확장되며, VPC 안팎의 모든 트래픽이 그것을 통해 라우팅되도록 자체 서브넷에 배포되는 것만 빼고."

시험 신호: "도메인 이름이나 페이로드로 트래픽 검사 또는 필터링," "VPC를 위한 침입 탐지/방지(IDS/IPS)," 또는 "아웃바운드 트래픽을 위한 중앙 집중식 이그레스 필터링" → Network Firewall. 보안 그룹과 NACL은 포트와 IP로 인스턴스 수준 및 서브넷 수준 허용/거부에 대한 답이다; Network Firewall은 질문이 트래픽 *안의* 검사를 요구할 때의 답이다. 그리고 질문이 WAF 규칙, Shield Advanced, 보안 그룹, *그리고* Network Firewall 정책을 많은 계정에 걸쳐 일관되게 관리하는 방법을 물으면 — 그것이 **AWS Firewall Manager**, 위에 있는 정책 관리 레이어다.

## 장점과 한계

**AWS Shield**:

- Standard: 무료이고 자동 — 사용하지 않을 이유가 없다
- Advanced: 프로필이 높은 타겟에 훌륭함; 소형 팀에는 비쌈
- Standard가 레이어 3/4 공격(SYN 홍수, UDP 홍수, DNS 증폭)을 자동으로 흡수한다
- Advanced가 레이어 7 보호, 실시간 알림, Shield Response Team을 추가한다

**AWS WAF**:

- 관리형 규칙 그룹이 설정을 크게 단순화한다 — 몇 번의 클릭으로 OWASP 상위 10개 보호
- 사용자 정의 규칙은 HTTP 공격 패턴 이해 필요
- 속도 제한은 종종 간과되는 강력한 기능 — 스크레이퍼와 무차별 대입에 효과적
- WAF는 보안 애플리케이션 코드를 대체하지 않는다 — 심층 방어 레이어다
- Count 모드로 시작하고, 검증하고, 그런 다음 Block으로 전환하라

**GuardDuty**:

- 활성화하기 매우 낮은 노력(몇 번의 클릭, 30일 무료 체험)
- 발견은 사람의 검토와 대응이 필요하다 — GuardDuty가 감지하지, 고치지 않는다
- 잘못된 긍정이 발생한다 — 일부 정상 활동이 ML 모델에게 이상하게 보인다
- 심각도 수준(낮음/중간/높음)이 대응 우선순위를 정하는 데 도움이 된다
- 자동화된 대응 워크플로우를 위해 Security Hub, EventBridge, Lambda와 통합된다

**Amazon Inspector**:

- 지속적이고 자동화된 취약성 스캔 — 일회성 확인이 아니다
- 새 CVE가 게시되거나 리소스가 바뀌면 자동으로 재스캔
- EC2 인스턴스(OS 및 애플리케이션 패키지), ECR 컨테이너 이미지, Lambda 함수 패키지를 다룬다
- 발견이 Security Hub로 흐른다; 심각도 등급이 패치 우선순위를 정하는 데 도움이 된다
- 공격을 차단하지 않는다 — 공격을 가능하게 하는 조건을 표면화한다

**Amazon Macie**:

- S3의 민감한 데이터(PII, 자격증명, 재무 데이터)를 자동으로 발견한다
- 비정상적인 행동 패턴이 없는 데이터 노출을 잡는다 — GuardDuty가 놓칠 것
- 30일 무료 체험; 그 후 버킷당 월별 지불
- 많은 S3 버킷과 다양한 민감도 수준을 가진 팀에 가장 가치 있음

**AWS Security Hub**:

- GuardDuty, Macie, Inspector, Config, Firewall Manager의 발견을 집계한다
- 보안 벤치마크(CIS, NIST, PCI-DSS)에 대해 설정을 확인한다
- 멀티 계정 규모에서 가장 가치 있음
- 하나의 계정만 있더라도 일찍 활성화하라 — 발견 히스토리가 누적된다

## 요약

다섯 개의 서비스, 다섯 개의 레이어. 각각이 다른 종류의 위협을 해결하고 — 어느 것도 다른 것을 대체하지 않는다. DDoS 공격은 WAF와 GuardDuty를 우회한다. SQL 인젝션 시도는 Shield를 우회한다. 천천히 신중하게 사용되는 침해된 자격증명은 Shield와 WAF를 완전히 우회할 수 있다 — 하지만 GuardDuty가 이상을 볼 것이다. 우연히 고객 PII를 디버그 S3 버킷에 업로드하는 개발자는 세 가지 모두를 우회한다 — 하지만 Macie가 그것을 잡는다.

- **AWS Shield Standard**: 무료, 자동 레이어 3/4 DDoS 보호. 항상 켜져 있다. 50Gbps SYN 홍수를 Nimbus 로드 밸런서에 도달하기 전에 흡수했다.
- **AWS Shield Advanced**: SRT 접근과 비용 보호가 있는 프리미엄 DDoS 보호. 엔터프라이즈 사용 사례.
- **AWS WAF**: 애플리케이션 레이어 방화벽. HTTP 요청 검사 및 필터링. CloudFront, ALB, 또는 API Gateway에 연결. OWASP 상위 10개 보호를 위해 관리형 규칙 그룹 사용. 스크레이퍼 방어를 위한 속도 기반 규칙.
- **Amazon GuardDuty**: 행동 위협 감지. 핵심 데이터 소스: CloudTrail 이벤트, VPC 흐름 로그, DNS 로그. 선택적 확장 보호가 S3 이벤트, EKS/ECS 런타임 모니터링, RDS 로그인 이벤트, Lambda 네트워크 활동을 추가한다. 비정상적인 활동에 대한 분류된 발견을 생성한다. 다섯 가지 핵심 발견 유형: UnauthorizedAccess(콘솔 로그인), CryptoCurrency(채굴), Recon(포트 탐색), Trojan(C2 트래픽), Policy(S3 잘못된 설정).
- **Amazon Inspector**: 자동화된 취약성 평가. EC2 인스턴스, ECR 컨테이너 이미지, Lambda 함수 패키지를 알려진 CVE에 대해 스캔한다. 지속적으로 실행되고 새 취약점이 게시되면 재평가한다. 발견이 Security Hub로 흐른다.
- **Amazon Macie**: S3의 민감한 데이터 발견. PII, 자격증명, 재무 데이터를 감지한다. 비정상적인 행동 패턴이 없는 노출을 잡는다.
- **AWS Security Hub**: 모든 보안 서비스의 발견을 하나의 대시보드에 집계한다. 여러 계정에 걸친 중앙 집중식 모니터링을 가능하게 한다.
- **CloudTrail**: 모든 AWS 보안 로깅의 기반. 장기 보관을 위해 S3에 기록하는 추적을 활성화하라. 모든 보안 서비스가 그것에서 읽는다.

## 시험 팁

*SAA-C03 도메인: 보안 아키텍처 설계(도메인 1, 태스크 1.2)*

- **Shield Standard vs. Advanced**: Standard는 무료이고 자동이다. Advanced는 비용이 들고 SRT, 비용 보호, 더 나은 감지를 추가한다. Advanced에 대한 시험 신호: "대규모 DDoS," "공격 중 SLA 보장," "DDoS 관련 비용 급등으로부터 재무적 보호."
- **WAF 사용 사례 신호**: "SQL 인젝션 차단," "교차 사이트 스크립팅 차단," "API 호출 속도 제한," "특정 사용자 에이전트 차단," "OWASP 상위 10개 보호" → WAF.
- **GuardDuty 신호**: "비정상적인 API 활동 감지," "침해된 자격증명 식별," "비정상적인 EC2 네트워크 연결 플래그," "위협 인텔리전스" → GuardDuty.
- **WAF 연결**: CloudFront(전 세계), ALB(리전), API Gateway(리전), AppSync에 연결할 수 있다.
- **GuardDuty 데이터 소스**: 세 가지 핵심 소스 — CloudTrail 이벤트, VPC 흐름 로그, DNS 로그. 확장 선택적 소스는 S3 데이터 이벤트, EKS 감사 로그, RDS 로그인 이벤트, Lambda 네트워크 활동, ECS 런타임을 포함한다. 시험은 특정 감지 시나리오와 관련된 데이터 소스를 물을 수 있다: "비정상적인 RDS 로그인" → GuardDuty RDS Protection; "컨테이너 런타임 위협" → GuardDuty EKS/ECS Runtime Monitoring.
- **Macie vs GuardDuty**: 이것이 흔한 시험 함정이다. **Macie**는 ML을 사용하여 S3에서 민감한 데이터(PII, 자격증명, 재무 데이터)를 감지한다. **GuardDuty**는 행동에서 위협과 이상을 감지한다. Macie는 콘텐츠에 관한 것이다. GuardDuty는 행동에 관한 것이다.
- **Inspector vs. GuardDuty vs. Macie**: 세 가지 다른 렌즈, 어느 것도 다른 것을 대체하지 않는다. **Inspector** = 취약성 스캔 — EC2 인스턴스, ECR의 컨테이너 이미지, Lambda 함수 패키지의 CVE. 지속적으로 실행되고 새 CVE가 게시되면 재스캔한다. **GuardDuty** = 행동 위협 감지 — 지금 무엇이 일어나고 있고 이상하게 보이는가. **Macie** = S3의 민감한 데이터 발견 — 있어서는 안 되는 PII, 자격증명, 재무 데이터. 시험 트리거: "EC2의 패치되지 않은 취약점 식별" 또는 "CVE에 대한 컨테이너 이미지 스캔" → Inspector. "비정상적인 API 호출이나 침해된 자격증명 감지" → GuardDuty. "S3에서 PII나 민감한 데이터 찾기" → Macie.
- **Security Hub**: 여러 서비스와 계정의 보안 발견을 집계한다. 시험 시나리오: "회사가 여러 AWS 계정이 있고 모든 보안 발견의 단일 뷰를 원함" → Security Hub.
- **WAF의 속도 기반 규칙**: 시간 윈도우 내에서 IP당 요청을 제한하는 데 사용. 핵심 규칙 세트(공격 패턴을 일치시키는)와 다르다. 시험은 "무차별 대입 로그인 시도 방지" 또는 "스크레이핑 완화"에 속도 기반 규칙을 사용한다.
- **CloudTrail + GuardDuty + Security Hub**: 이 셋이 함께 AWS 보안 관찰 가능성의 핵심을 형성한다. CloudTrail을 먼저 활성화하고(GuardDuty와 Security Hub가 그것에 의존), 그런 다음 GuardDuty, 그런 다음 발견을 집계하기 위해 Security Hub.

## 연습 문제

**연습 1 — 회상**

AWS WAF와 Amazon GuardDuty의 차이를 설명하라. 각 서비스는 무엇으로부터 보호하며, 각각은 어떤 레이어에서 운영되는가?

*(힌트: WAF를 들어오는 요청에 대한 필터로, GuardDuty를 로그를 감시하는 행동 분석가로 생각하라.)*

**연습 2 — SAA-C03 시나리오**

*시나리오*: 소매 회사의 웹사이트가 시간당 수백만 개의 요청을 제품 검색 API에 보내는 봇넷의 타겟이 되고 있다. 요청이 합법적으로 보인다(유효한 User-Agent 문자열, 유효한 세션 쿠키) 하지만 구매로 이어지지 않는다 — 제품 가격을 스크레이핑하고 있다. 공격이 정상 고객이 느린 응답 시간을 경험하게 하고 있다.

다음 중 이 위협을 가장 잘 해결하는 서비스 조합은?

A) 속도 제한 규칙이 있는 AWS WAF와 CloudFront  
B) AWS Shield Advanced와 CloudFront  
C) Amazon GuardDuty와 AWS Shield Standard  
D) 봇넷의 IP 범위를 차단하는 네트워크 ACL

**힌트 1**: 요청이 HTTP 레이어(애플리케이션 레이어)에 있다. 어떤 서비스가 HTTP 레이어에서 운영되는가?

**힌트 2**: 봇넷은 많은 다른 IP 주소를 사용한다 — NACL 수준에서 특정 IP 범위를 차단하는 것은 대형 봇넷에 비효율적이다.

**힌트 3**: IP 주소당 속도 제한은 완전히 차단할 수 없더라도 스크레이핑을 늦출 수 있다.

**정답**: A

**설명**: AWS WAF는 IP 주소당 요청을 속도 제한하여 어떤 단일 소스에서의 고볼륨 스크레이핑의 영향을 줄일 수 있다. CloudFront는 들어오는 트래픽을 AWS의 엣지 네트워크에 걸쳐 배포하여 볼륨을 흡수하고 오리진을 보호한다. WAF 규칙은 또한 요청 패턴(동일한 API 엔드포인트로의 빠른 순차 요청)을 일치시켜 스크레이핑 행동을 식별할 수 있다.

**왜 B가 아닌가?** Shield Advanced는 DDoS 홍수(레이어 3/4)로부터 보호한다. 시나리오는 애플리케이션 레이어 스크레이핑(레이어 7 HTTP 요청)을 설명하는데, Shield는 검사하지 않는다.

**왜 C가 아닌가?** GuardDuty는 AWS 계정 행동의 이상을 감지한다 — 들어오는 HTTP 요청을 차단하지 않는다. Shield Standard는 애플리케이션 레이어 공격을 처리하지 않는다.

**왜 D가 아닌가?** 대형 봇넷은 분산된 소스에서 수천 개의 IP 주소를 사용한다. 특정 범위를 차단하는 것은 정교한 봇넷에 실패하는 두더지 잡기 접근 방식이다.

*SAA-C03 도메인: 보안 아키텍처 설계 — 태스크 1.2*

**연습 3 — 아키텍처 과제** *(선택 사항)*

Nimbus는 신용카드 데이터를 처리하기 위한 준비를 할 때 위협 모델을 고려하고 있다. PCI-DSS 컴플라이언스 검토에는 다음이 필요하다:

- 네트워크 레이어 DDoS 공격으로부터 보호
- 알려진 웹 익스플로잇에 대한 애플리케이션 레이어 필터링
- 모든 API 호출을 변조 방지 장기 저장소에 기록
- 결제 서비스에 대한 비정상적인 접근 패턴 감지

각 요구사항을 특정 AWS 서비스나 설정에 매핑하라. Shield Standard가 충분한가, 아니면 PCI-DSS 컨텍스트가 Advanced를 제안하는가? WAF를 어디에 연결하겠는가?

*(단 하나의 정답은 없다. 목표는 컴플라이언스 요구사항을 AWS 서비스에 매핑하는 것을 연습하는 것이다.)*

## 포스트 크레딧 장면

GuardDuty가 활성화됐다.

48시간 후, 첫 번째 발견이 생성됐다: *"EC2 인스턴스 i-0abc123이 알려진 Tor 종료 노드와 통신하고 있습니다."*

Leo가 인스턴스 ID를 봤다.

"그건 내부 모니터링 인스턴스예요," 그가 말했다. "네트워크 진단을 실행하기 위해 설정한 거예요."

"Tor 종료 노드와 통신해야 하나요?"

"아니요." 그가 멈췄다. "왜 그럴까요?"

그가 인스턴스를 열었다. 누군가 그것에 도구를 설치했다 — 알고 보니 익명화된 데이터 수집을 위해 Tor 인프라와도 통신하는 합법적인 오픈 소스 네트워크 스캐너.

"그러면 도구가 집에 전화하고 있었던 거네," Priya가 말했다.

"내 지식 없이," Leo가 확인했다.

"그게 공급망 위험이야. 당신이 승인하지 않은 일들을 하는 의존성."

Leo가 도구를 제거했다. 설치하기 전에 모든 타사 도구를 검토하는 프로세스를 설정했다.

"이게 이제 우리가 있는 편집증 수준인가요?" Maya가 물었다.

"예," Priya가 말했다.

"항상 이 수준에 있어야 했나요?" Maya가 물었다.

"또 예," Priya가 말했다.
