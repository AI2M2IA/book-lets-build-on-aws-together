# 장 30: 숨겨진 비용

톰은 회의실에 세 개의 열이 있는 화이트보드를 두고 있었다: 컴퓨트, 스토리지, 네트워킹. 처음 두 개는 채워져 있었다 — 숫자, 날짜, 완료된 최적화의 이름들. 그는 세 번째 열에 무언가를 쓰기 전에 잠시 화이트보드 앞에 섰다. AWS 청구서의 네트워킹 줄들은 다른 것들과 달리 페이지 곳곳에 흩어져 있었다. 각각은 다른 이름, 다른 단위, 돈이 빠져나가는 이유에 대한 다른 정당화를 가지고 있었다.

그는 마커의 뚜껑을 열었다.

**요점 정리: 청구서의 마지막 미지수**

데이터베이스 감사는 톰이 적극적으로 작업해 온 마지막 주요 항목을 마무리했다 — 월 $491 회수, 연 $5,892. EC2 Savings Plans, S3 라이프사이클 정책, 스토리지 정리를 더하면, 누적 총합은 석 달간의 작업에 걸쳐 연 $34,092의 절약이었다. 하지만 톰은 데이터베이스 심층 분석 동안, 한 카테고리가 거의 검토되지 않았다는 것을 알아챘다. 스토리지 비용은 한 줄로 나타났다: "S3: $198." 컴퓨트 비용은 한 줄로 나타났다: "EC2: $2,340" — 27장의 Savings Plan 할인이 적용되기 전. 네트워킹 비용은 "Data Transfer Out", "NAT Gateway Processing", "VPC Peering Data Transfer", "CloudFront Data Transfer" 같은 이름으로 십여 개의 항목에 흩어져 있었다. 그는 그것들을 합산하여 합계를 본 적이 없었다. 그것이 오늘의 작업이었다.

톰은 청구서를 띄웠다. 데이터 전송 섹션을 찾았다. 모든 항목을 합산했다.

AWS의 네트워킹 비용은 도시의 통행료 시스템과 같다: 도시로 들어가는 것은 무료지만, 바깥으로 나가며 지나는 모든 터널은 돈이 들고, 동네 사이를 운전하는 것도 약간 든다. 대부분의 사람들은 월말에 청구서를 받고 줄곧 무료 지상 도로가 있었는데 매일 터널을 이용해 왔다는 것을 깨달을 때까지 통행료를 생각하지 않는다. 이 장의 목표는 모든 톨게이트를 이해하는 것 — 그리고 어느 것이 낼 가치가 있는지 결정하는 것이다.

월 $847.

"우리는 데이터 전송에 월 $847를 쓰고 있어요," 그가 말했다.

"그게 많은 건가요?" 레오가 물었다.

"최적화하기 전 우리 S3 청구서와 정확히 같은 액수예요. 그리고 저는 우리에게 이 규모의 데이터 전송 청구서가 있다는 것조차 몰랐어요."

마야가 건너다봤다. "데이터 전송이 정확히 뭐죠?"

"바이트를 이리저리 옮기는 것에 AWS가 청구하는 거예요. AWS로 들어오는 바이트: 보통 무료. AWS에서 인터넷으로 나가는 바이트: 청구됨. 다른 리전의 서비스 간 바이트: 청구됨. NAT Gateway를 통과하는 바이트: 청구됨."

"분해해 줄 수 있나요?"

톰은 할 수 있었다. 하지만 이번에는 청구 콘솔에서 멈추지 않았다. 그는 모든 VPC에 걸쳐 VPC Flow Logs를 활성화하고 그것들을 CloudWatch Logs Insights에 공급했다. 이것은 그가 실제 트래픽 흐름을 쿼리할 수 있게 했다 — 그저 달러 금액이 아니라, 어떤 소스가 어디로 데이터를 보내고 있는지, 그리고 얼마나.

쿼리는 실행에 2분이 걸렸다. 그가 곧 끌어올 로그 소스 하나와 결합하니, 출력은 행동을 취하기에 충분히 구체적이었다.

**트래픽 분석: 실제로 청구서를 발생시키는 것**

볼륨 기준 상위 다섯 개 트래픽 흐름, 순서대로:

1. EC2 애플리케이션 서버 → NAT Gateway → AWS 서비스 (SSM, Secrets Manager, CloudWatch, SQS): 월 3.9TB
2. EC2 애플리케이션 서버 → NAT Gateway → 외부 API: 월 1.3TB
3. Aurora 읽기 엔드포인트 → EC2 애플리케이션 서버 (교차 AZ): 월 0.4TB
4. 분석 파이프라인 → us-east-1의 S3 버킷 (교차 리전): 월 0.3TB
5. CloudFront → S3 오리진 (캐시 미스): 월 0.2TB

처음 네 개는 Flow Logs에서 바로 나왔다. 다섯 번째는 그럴 수 없었다: VPC Flow Logs는 당신의 VPC 안의 네트워크 인터페이스를 통과하는 트래픽만 보고, S3에서 가져오는 CloudFront 캐시 미스는 VPC를 전혀 건드리지 않는다 — 그것은 CloudFront가 S3와 직접 대화하는 것이다. 그 흐름에 대해, 톰은 CloudFront의 표준 액세스 로그를 끌어와 `x-edge-result-type` 필드로 필터링했다: `Miss`로 표시된 모든 항목은 CloudFront가 오리진에서 가져와야 했던 요청이고, 바이트를 합산하니 0.2TB가 나왔다. 하나의 청구서, 두 개의 도구 — 각각은 다른 것이 보는 것에 대해 눈먼.

"네 번째 흐름," 프리야가 말했다. "왜 우리 분석 파이프라인이 us-east-1의 버킷과 대화하고 있죠?"

레오는 톰이 알아보는 표정을 짓고 있었다.

"이미 배포했는데 — 아," 레오가 말했다. "6개월 전에 우리 분석 파이프라인이 여러 리전으로 병렬로 팬아웃할 수 있는지 테스트하고 있었어요. us-east-1에 테스트 버킷을 띄우고, 파이프라인을 거기로 향하게 하고, 일주일 동안 실행했죠. 테스트는 끝났는데 파이프라인 설정에서 us-east-1 대상을 제거하는 걸 깜빡했어요."

"그러니까 다섯 달 동안," 톰이 말했다, "우리는 모든 분석 결과의 복사본을 버지니아의 버킷에 쓰고 있었네요."

"이게 월별로 얼마나 들죠?" 톰이 물었다.

us-west-2에서 us-east-1로의 교차 리전 전송: GB당 $0.02. 월 300GB = 전송에 월 $6. 더하기 us-east-1의 중복 데이터에 대한 S3 스토리지: 300GB × 5개월 × GB당 $0.023 = 저장된 데이터로 $34.50.

"크진 않네요," 레오가 말했다.

"월별로는 크지 않죠," 톰이 말했다. "하지만 다섯 달 동안 실행되고 있었고 아무도 몰랐어요. 의도하지 않은 비용이죠. 질문은 $6가 중요한지가 아니에요 — 모든 달러가 왜 쓰이고 있는지 우리가 아는지예요."

레오는 us-east-1 테스트 버킷을 삭제하고 파이프라인 설정에서 대상을 제거했다.

흐름 로그 출력에서 가장 실행 가능한 발견은 첫 번째 흐름이었다: EC2 애플리케이션 서버가 NAT Gateway를 통해 AWS 서비스를 호출하는 것.

톰은 CloudWatch Logs Insights 쿼리의 특정 로그 항목을 끌어와, AWS 서비스 IP 범위로 향하는 트래픽만 표시하도록 필터링했다:

```
fields @timestamp, srcAddr, dstAddr, bytes, protocol
| filter dstAddr like "52.94." or dstAddr like "54.239." or dstAddr like "52.46."
| stats sum(bytes) as totalBytes by srcAddr, dstAddr
| sort totalBytes desc
| limit 20
```

출력은 그가 예상하지 못한 것을 보여줬다: 월 약 300 GB의 동일 리전 S3 트래픽 — 레오의 us-east-1 버킷으로의 교차 리전 흐름과는 별개로 — 이 NAT Gateway를 통과하고 있었다. 하지만 톰은 몇 달 전에 이미 S3 Gateway Endpoint를 구성했었다.

"우리한테 S3 Gateway Endpoint가 있잖아요," 레오가 말했다. "왜 S3 트래픽이 아직 NAT를 통과하죠?"

톰은 라우팅 테이블을 봤다. Gateway Endpoint는 구성되어 있었다 — 하지만 애플리케이션 VPC에만. 분석 파이프라인은 9개월 전 데이터 격리를 위해 생성된 별도의 VPC에서 실행됐다. 그 VPC에는 S3 Gateway Endpoint가 없었다. 분석 파이프라인의 EC2 인스턴스로부터의 모든 S3 호출은 그 VPC의 NAT Gateway를 통해 라우팅됐다.

"0.3TB의 분석 파이프라인 트래픽 × GB당 $0.045 = 월 $13.50," 톰이 말했다. "그저 두 번째 VPC에 빠진 엔드포인트 때문에요."

"엔드포인트를 추가하는 데 얼마나 들죠?" 레오가 물었다.

"0원이요," 톰이 말했다. "S3 Gateway Endpoint는 무료예요. 라우팅 테이블 항목 하나죠."

분석 VPC에 Gateway Endpoint를 추가하는 것은 4분이 걸리고 월간 NAT Gateway 요금에서 $13.50를 깎을 것이다 — 작은 절대 숫자지만, 발견은 원칙이었다. 그들은 한 VPC에 비용 통제를 추가했고 두 번째를 만들 때 그것을 복제하는 걸 잊었다. 일관성은 지식뿐만 아니라 프로세스를 요구했다.

톰은 배포 체크리스트에 추가했다: 새 VPC를 생성할 때, 워크로드를 연결하기 전에 S3와 DynamoDB Gateway Endpoint를 추가하라.

흐름 로그의 두 번째 특정 발견은 더 비쌌다. 주문 알림 시스템을 실행하는 Lambda 함수들의 트래픽 — 레스토랑 구성 파일을 읽기 위한 S3 접근 — 이 S3 엔드포인트 대신 NAT Gateway를 통과하고 있었다. Lambda 함수들은 (RDS 접근을 위해) VPC 안에서 실행됐고, VPC의 S3 엔드포인트는 애플리케이션 서브넷의 EC2 인스턴스에만 구성되어 있었다. Lambda 서브넷의 Lambda 함수들은 NAT를 통해 라우팅되고 있었다.

"잠깐 — 근데 *왜* 그런 식으로 하는 거죠?" 마야가 물었다. "우리한테 엔드포인트가 있잖아요. 왜 Lambda가 그걸 안 쓰죠?"

"VPC Gateway Endpoint는 라우팅 테이블에 근거해 서브넷별로 적용돼요," 톰이 말했다. "Lambda 함수들은 자체 라우팅 테이블이 있는 자기 서브넷에 있어요. 그 라우팅 테이블에 엔드포인트 경로가 없었어요. 제가 애플리케이션 서브넷에는 추가했는데, Lambda 서브넷을 놓쳤죠."

Lambda 서브넷 라우팅 테이블에 S3 엔드포인트 경로를 추가하면 무료여야 했던 S3 호출에 청구되고 있던 NAT Gateway 처리 요금에서 월 $41를 더 절약할 것이다.

흐름 로그 분석은 그 값을 했다. 세 시간의 쿼리 시간, 세 가지 구체적인 발견: 잊혀진 분석 VPC 엔드포인트 (월 $13.50), Lambda 서브넷 라우팅 간극 (월 $41), 그리고 Interface Endpoint 결정의 기초가 된 원래의 큰 발견. 흐름 로그 분석으로 식별된 총 추가 월간 절약: $54.50, 분석이 이미 드러낸 Interface Endpoint의 $78 위에. 그 두 개의 더 작은 수정은 다음 스프린트의 백로그로 갔다; 이 장 끝의 절약 표는 출시된 것만 센다.

"교훈은 VPC 엔드포인트가 일회성 구성이 아니라는 거예요," 톰이 말했다. "모든 새 VPC, 모든 새 서브넷, 모든 새 워크로드 유형은 같은 확인을 요구해요. 프라이빗 서브넷의 모든 것의 기본값은 NAT를 통해 라우팅하는 거예요. 확인은: 이 워크로드가 S3, DynamoDB, 또는 고트래픽 AWS 서비스 중 어느 것이라도 호출하는가? 그렇다면, 엔드포인트 경로가 있는가?"

"그 확인을 자동화하는 걸 생각해 봤나요?" 프리야가 물었다. "S3 엔드포인트 경로 없이 프라이빗 서브넷이 생성되면 알리는 AWS Config 규칙요?"

"목록에 있어요," 톰이 말했다. "고아 볼륨 알림 바로 다음에요."


그리고 그것으로, 톰은 분석을 시작하게 한 질문에 대한 답을 얻었다. 네트워킹 비용은 단일 문제가 아니었다. 그것들은 다섯 가지 다른 문제였고, 각각 다른 해결책을 가지고 있었다.

**AWS가 데이터 전송에 청구하는 방식**

AWS의 데이터 전송 가격은 비대칭적이다:

**AWS로 (인바운드)**: 무료. 원하는 만큼 데이터를 업로드할 수 있다.

**AWS에서 인터넷으로 (아웃바운드)**: 청구됨. 첫 100GB/월은 무료. 그 후:

- 첫 10TB/월에 대해 GB당 $0.09 (미국 리전)
- 다음 40TB에 대해 GB당 $0.085
- 더 높은 볼륨에서는 더 낮음

**같은 가용 영역 내**: 무료. 같은 AZ에서 서로 대화하는 EC2 인스턴스는 아무것도 내지 않는다.

**가용 영역 간 (같은 리전)**: 각 방향으로 GB당 $0.01. 작지만 실재하는 비용.

**리전 간**: 리전에 따라 GB당 $0.02~0.08. 교차 리전 트래픽은 상당히 더 비싸다.

**NAT Gateway**: 처리된 GB당 $0.045. 프라이빗 EC2 인스턴스가 인터넷에 도달하기 위해 NAT Gateway를 통해 보내는 모든 바이트 — 그리고 돌아오는 모든 바이트 — 가 청구된다.

**CloudFront**: 직접 AWS-인터넷 전송보다 낮은 데이터 전송 요율. 첫 10TB에 대해 GB당 $0.085 (직접 데이터 전송 아웃보다 약간 적음). CloudFront는 엣지 캐싱이 오리진이 데이터를 덜 자주 제공한다는 것을 의미하므로 종종 총 전송 비용을 줄인다.

**톰의 분해**

"이게 월별로 얼마나 들죠?" 톰이 각 항목에 대해 차례로 물었다. 그는 그것들을 스프레드시트의 별도 탭에 추가했다 — 월간 총합이 아니라, 분류된 각 카테고리. 총합은 청구서의 어느 부분이 어떤 종류의 비용인지 이해하는 것보다 덜 유용했다.

모든 항목을 분류한 후:

**인터넷으로의 아웃바운드 데이터**: 월 $214

- 전 세계 고객에게 가는 API 응답
- CloudFront를 우회하여 여전히 S3와 ALB에서 클라이언트로 직접 제공되는 자산 (캐시 채움 자체 — CloudFront가 AWS 오리진에서 가져오는 것 — 은 무료다: AWS는 오리진-CloudFront 전송을 면제한다)

**NAT Gateway 처리**: 월 $289

- 외부 API를 호출하는 애플리케이션 서버 (결제 처리기, 이메일 서비스, 지도 데이터)
- NAT Gateway를 통과하는 DynamoDB 호출 (일부 테이블에 VPC 엔드포인트가 설정되기 전)

**교차 AZ 데이터 전송**: 월 $178

- 로드 밸런서에서 EC2 인스턴스로 (로드 밸런서는 한 AZ에, 일부 인스턴스는 다른 AZ에)
- 애플리케이션 서버에서 RDS 읽기 복제본으로 (다른 AZ에)

**교차 리전 데이터 전송**: 월 $166

- Aurora Global Database 복제 (프라이머리는 us-west-2, 읽기는 us-east-1)
- 백업을 위한 S3 교차 리전 복제
- 레오의 잊혀진 테스트 파이프라인 (이 총합 중 월 $6)

**NAT Gateway: 가장 큰 놀라움**

월 $289의 NAT Gateway 처리 요금이 가장 큰 항목이었다. 그리고 VPC Flow Log 분석이 그것을 구체화했다: 최대 소비자는 NAT Gateway를 통해 AWS 서비스 API (SSM, Secrets Manager, CloudWatch Logs)를 호출하는 애플리케이션 서버였다.

11장에서, 톰은 S3와 DynamoDB를 위한 VPC Gateway Endpoint를 설정했었다. 그것들은 무료였다. 하지만 그는 여러 다른 서비스를 위한 Interface Endpoint 설정을 놓쳤다:

- 패치 관리를 위한 Systems Manager (SSM)
- 자격 증명 검색을 위한 Secrets Manager
- 메트릭 및 로그 전송을 위한 CloudWatch
- 메시지 폴링을 위한 SQS

프라이빗 EC2 인스턴스에서 이 서비스들로의 모든 호출이 NAT Gateway를 통과하고 있었다. 각 호출은 GB당 $0.045가 청구됐다.

당신이 이미 AWS의 네트워크 안에 있는데 왜 AWS가 NAT Gateway를 통과하는 트래픽에 청구하는지 궁금할 수 있다. 답은 NAT Gateway 자체가 관리형 서비스라는 것이다 — 그것을 운영하는 데 돈이 들고, AWS는 그 비용을 기가바이트당 전가한다. VPC 엔드포인트는 중간상을 제거하고, 그것이 청구서를 줄이는 이유다.

"잠깐 — 근데 *왜* 그런 식으로 하는 거죠?" 톰이 숫자를 보여줄 때 마야가 물었다. "우리는 S3와 DynamoDB를 위한 Gateway Endpoint를 설정했잖아요. 왜 SSM과 CloudWatch에는 같은 걸 하지 않았죠?"

"Gateway Endpoint는 S3와 DynamoDB에만 사용 가능해요," 톰이 말했다. "나머지 모든 것 — SSM, Secrets Manager, SQS — 은 Interface Endpoint가 필요해요. 무료는 아니지만, 우리가 생성하는 볼륨에서는 NAT를 통해 라우팅하는 것보다 싸요."

이 서비스들을 위한 **Interface Endpoint**: AZ당 시간당 $0.01 + 처리된 데이터 GB당 $0.01.

Nimbus의 볼륨에서, SSM Interface Endpoint는 월 약 $25 (시간당 요금 더하기 GB당 처리)가 들고 NAT Gateway 요금에서 월 약 $45를 절약할 것이다 (SSM이 패치 관리와 파라미터 스토어 호출에 상당한 데이터 볼륨을 생성하기 때문에).

엔드포인트 비용과 절약은 서비스와 볼륨에 따라 달랐다. 톰은 네 개의 고트래픽 서비스를 위한 Interface Endpoint 설정 — 각각 두 AZ, 더하기 그것들이 운반할 3.9TB에 대한 GB당 $0.01 처리 — 이 총 월 약 $97가 들고 NAT Gateway 처리에서 월 약 $176를 절약할 것이라고 계산했다.

순 절약: 엔드포인트 설정만으로 월 $78.

"그리고 누군가 침입하려고 하면요?" VPC 엔드포인트 대화가 구현으로 넘어갈 때 프리야가 말했다. "VPC 엔드포인트는 트래픽이 공공 인터넷을 절대 건드리지 않는다는 것을 의미해요 — 그건 비용만이 아니라 위협 표면 감소죠. 우리는 보안 이점만으로도 이걸 했어야 해요."

"동의해요," 톰이 말했다. "비용 절약은 보너스예요."

레오는 NAT를 통해 라우팅되고 있던 서비스 목록을 봤다. "VPC 엔드포인트가 있는지 확인하지 않고 CloudWatch 로깅 엔드포인트를 설정했을 수도 있어요," 그가 말했다. "지금은 괜찮을 거예요 — 하지만 네, 그게 6개월 동안 NAT를 통과하고 있었네요."

"그것도 목록에 있어요," 톰이 말했다. "CloudWatch는 우리가 고치는 네 개 중 하나예요."

**PrivateLink 계산: 언제 말이 되는가**

아키텍처가 성장하면서 떠오르는 이 대화의 더 복잡한 버전이 있다: 다른 AWS 고객이 호스팅하는 서비스 (또는 다른 VPC의 당신 자신의 서비스)에 프라이빗 연결을 제공하기 위해 AWS PrivateLink를 사용하는 것.

PrivateLink Interface Endpoint는 AZ당 시간당 $0.01 더하기 GB당 $0.01이 든다. 엔드포인트를 통해 월 1TB의 트래픽을 생성하는 서비스의 경우:

- PrivateLink 비용: $0.01 × 2 AZ × 730 시간 + $0.01 × 1,000GB = $14.60 + $10 = 월 $24.60
- 대신 같은 트래픽을 기존 NAT Gateway를 통해 라우팅: $0.045 × 1,000GB = 월 $45의 증분 처리 요금

비교는 *증분적*인데, NAT Gateway는 어느 쪽이든 남기 때문이다 — 그것은 여전히 나머지 인터넷 향 트래픽을 제공하므로, 이 한 서비스가 엔드포인트로 이동할 때 그 시간당 비용 ($0.045 × 2 × 730 = $65.70)은 사라지지 않는다. 이 트래픽 볼륨에서, PrivateLink는 월 약 $20를 절약한다. 손익분기점은 대략 월 420GB다 — 그 아래에서는 엔드포인트 자체의 시간당 비용이 NAT 처리 대비 GB당 절약을 능가한다.

"잠깐 — 근데 *왜* 그냥 VPN이나 피어링 대신 PrivateLink를 쓰죠?" 마야가 물었다.

"VPC Peering은 더 단순하고 리전 내 전송에는 무료예요," 톰이 말했다. "하지만 피어링은 VPC 간에 완전히 라우팅된 연결을 만들어요 — VPC A의 무엇이든 잠재적으로 VPC B의 무엇에든 도달할 수 있죠. PrivateLink는 더 외과적이에요. 엔드포인트는 전체 네트워크 경로가 아니라 특정 서비스를 노출해요. 보안을 의식하는 아키텍처에는, 그 특정성이 중요하죠."

"그리고 누군가 피어링된 VPC에 침입하려고 하면요?" 프리야가 물었다. "완전한 피어링은 한 VPC의 손상된 인스턴스가 피어링된 VPC의 모든 인스턴스로 가는 경로를 가진다는 것을 의미해요."

"그게 서드파티 서비스나 별도 팀이 소유한 서비스에 연결할 때 피어링보다 PrivateLink를 쓰는 논거예요," 톰이 말했다. "신뢰된 사내 VPC에는 피어링. 최소 노출 연결을 원하는 모든 것에는 PrivateLink."

**교차 AZ 트래픽: 아키텍처 질문**

월 $178의 교차 AZ 데이터 전송은 더 까다로웠다.

그중 일부는 불가피했다: 로드 밸런서는 트래픽을 AZ에 걸쳐 분배하므로, 일부 요청은 한 AZ에서 시작되고 로드 밸런서가 그것들을 다른 AZ의 인스턴스로 전달한다.

그중 일부는 최적화 가능했다: 애플리케이션은 RDS 프라이머리 (us-west-2a)에 쓰고 읽기 복제본 (us-west-2b)에서 읽도록 구성되어 있었다. 모든 읽기 쿼리가 AZ 경계를 넘었다.

읽기의 경우, 한 가지 해결책: 애플리케이션이 요청 인스턴스와 같은 AZ의 읽기 복제본을 선호하도록 구성. 각 AZ가 자체 읽기 복제본을 가진다. 트래픽이 로컬에 머문다.

트레이드오프: 더 많은 읽기 복제본 = 더 많은 비용. 교차 AZ 트래픽 비용이 월 $50이고 추가 읽기 복제본이 월 $190이라면, AZ 로컬 최적화는 본전을 못 뽑는다.

톰은 계산했다: 그들의 현재 쿼리 볼륨에서, 교차 AZ 트래픽은 $178 중 월 $31에 불과했다. 복제본을 추가할 가치가 없었다.

다른 교차 AZ 비용은 로드 밸런서 라우팅과 서비스 간 통신이었다 — 현재 아키텍처 수준에서는 대체로 불가피했다.

"이건 비용을 이해한다고 해서 그것을 고쳐야 하는 건 아닌 경우 중 하나예요," 톰이 말했다.

"교차 AZ 트래픽을 완전히 없애는 데 얼마나 들죠?" 마야가 물었다.

"모든 걸 한 AZ에 두는 건 Multi-AZ의 목적을 무산시켜요. 그건 고가용성을 잃는 대가로 월 $31의 절약이죠."

"그럼 그냥 두죠," 그녀가 말했다.

"그냥 둬요."

**S3 Select: 쿼리에서 데이터 전송 줄이기**

분석 파이프라인을 검토하는 동안, 톰은 분석팀이 큰 S3 파일을 쿼리하는 방식에 특정한 또 다른 최적화를 발견했다.

패턴: 매일 아침, 분석 작업이 S3에서 500MB Parquet 파일을 다운로드하여 레스토랑별 주문 데이터를 위해 인메모리로 필터링했다. 파일의 약 95%가 다운로드 후 버려졌다.

**S3 Select**는 파일 전체를 다운로드하여 애플리케이션에서 필터링하는 대신, S3 객체 (CSV, JSON, Parquet)에서 필요한 행과 열만 검색할 수 있게 한다.

> **중요 업데이트**: 2024년 중반, AWS는 신규 고객에게 S3 Select 제공을 중단했다 — 기존 사용자는 유지하지만, 신규 아키텍처에는 막다른 길이다. 이 섹션이 가르치는 원칙 (스토리지 계층에서 필터링하라, 파일 전체를 보내지 마라)은 시대를 초월한다; 그것을 위한 현대적 도구는 **Amazon Athena** (S3 위의 직접 SQL, S3 Select에 결코 없었던 조인과 집계 포함)다. **S3 Object Lambda**는, 한때 다른 대안이었는데, S3 Select를 따라 레거시 상태가 되었다: 2025년 11월 7일 기준 신규 고객에게도 닫혔다 (기존 워크로드는 계속 실행됨). 현재 시험에서, "S3에서 제자리에 데이터 쿼리"는 Athena를 가리킨다. 아래 이야기는 *추론* — 먼저 측정하고, 필터를 데이터로 옮겨라 — 이 교훈이기 때문에 보존된다.

S3 Select 없이:
```python
# 500MB 파일 다운로드, 메모리에서 처리
data = s3.get_object(Bucket='analytics', Key='orders-2024.csv')
df = pd.read_csv(data['Body'])
result = df[df['restaurant_id'] == '47'][['order_id', 'total']]
```

S3 Select로:
```python
# S3가 먼저 필터링하게 하고, 매칭되는 행만 전송 (500MB 대신 ~2MB)
response = s3.select_object_content(
    Bucket='analytics',
    Key='orders-2024.csv',
    Expression="SELECT order_id, total FROM S3Object WHERE restaurant_id = '47'"
)
```

S3 Select는 S3에서 애플리케이션으로 옮겨지는 데이터를 줄인다. 선택적 쿼리를 가진 큰 파일의 경우, 이것은 데이터 볼륨에서 10~100배 감소일 수 있다 — 그리고, 분석 인스턴스가 버킷과 같은 리전에서 실행되므로, 이득은 전송 청구서가 아니라 (동일 리전 S3-EC2 전송은 무료다): 즉시 버릴 데이터를 다운로드하고 필터링하는 데 쓰는 컴퓨트, 메모리, 시간이다.

톰은 그것을 분석팀에 제기했다. 그들은 처음에 반발했다.

"우리는 이미 pandas 쓰는 법을 알아요," 한 분석가가 말했다.

"이건 pandas에 관한 게 아니에요," 톰이 말했다. "2MB의 데이터를 얻으려고 500MB를 다운로드하고 있다는 사실에 관한 거예요. 다운로드 자체는 무료예요 — 같은 리전 — 하지만 인스턴스는 아니죠. 여러분은 이걸 모든 레스토랑에 대해 실행해요: 287개 레스토랑, 287개 쿼리, 매일 밤 140GB를 끌어와 pandas에서 필터링하죠. 그게 분석 박스를 두 시간 동안 바쁘게 만드는 거고 — 그게 그게 xlarge인 이유예요."

"그럼 S3 Select는요?"

"S3 Select는 스캔된 GB당 $0.002, 반환된 GB당 $0.0007를 청구해요 — 쿼리당 약 0.1센트. 그 대가로, 인스턴스는 매일 밤 140GB 대신 600MB를 받고, 작업은 몇 분 만에 끝나고, 박스는 크기를 낮출 수 있어요."

"그건 월 $450인데요," 분석가가 인스턴스 계산을 한 후 말했다 — 인스턴스의 시간당 요율과 그것이 갈아대며 보낸 시간으로부터의 봉투 뒷면 추정.

"그게 제가 여기 있는 이유예요," 톰이 말했다. 실제 숫자는 더 낮은 것으로 드러나게 된다 — 톰이 나중에 야간 작업에 귀속되는 실제 컴퓨트 지출을 끌어왔을 때, 그것은 $450가 아니라 월 $202였다. 냅킨 계산은 문제를 찾고; 측정은 그 크기를 정한다.

톰은 분석팀을 대화에 끌어들이기 전에 먼저 레오에게 제기했다. 그는 레오가 반발할 것을 알았고, 그것이 방 차원의 토론이 되기 전에 그 반발을 이해하고 싶었다.

"S3 Select는 분석 파이프라인 쿼리에서 월 $180를 절약할 거예요," 톰이 말했다.

"그건 모든 쿼리를 다시 작성해야 해요," 레오가 말했다.

"데이터 접근 패턴을 '다운로드하고 필터링'에서 'S3 Select API를 통해 쿼리'로 바꿔야 하는 거예요."

"그게 다시 작성이죠."

"클라이언트 라이브러리 호출의 변경이에요," 톰이 말했다. "쿼리 로직 — 필터링 표현식 — 은 그대로예요. 바뀌는 건 필터링이 어디서 일어나는지죠. 현재: EC2. S3 Select로: S3."

"S3 Select 문서를 읽어봤어요," 레오가 말했다. "조인을 할 수 없어요. 기본 SUM과 COUNT보다 복잡한 집계를 할 수 없죠. 우리 분석 쿼리 중 일부는 그것보다 정교해요."

"알아요," 톰이 말했다. "그래서 모든 쿼리에 S3 Select를 제안하는 게 아니에요. 레스토랑별 일일 요약 쿼리에 제안하는 거예요. 그게 restaurant_id로 필터링되어 두 열을 끌어오는 500MB Parquet 파일이죠. 그 쿼리는 순수한 필터-앤-프로젝트예요. S3 Select는 그 경우에 정확히 맞는 도구예요."

레오는 잠시 조용했다. 그는 문제의 쿼리를 띄웠다.

```python
# 현재: 500MB 다운로드, 메모리에서 필터링
df = pd.read_parquet('s3://analytics/orders-2024.parquet')
result = df[df['restaurant_id'] == restaurant_id][['order_id', 'total', 'timestamp']]
```

"S3 Select 버전은 뭐가 될까요 — select_object_content 호출요?"

"네," 톰이 말했다. "read_parquet 호출을 WHERE 절을 S3로 밀어내는 select_object_content 호출로 교체하는 거예요. 결과는 이미 필터링되어 돌아오죠. 전체 Parquet 파일 대신 매칭되는 레코드 스트림을 받아요."

**"의도된 비용 vs 의도하지 않은 비용"**

3주간의 네트워킹 분석 끝에, 톰은 전체 분해를 팀에 다시 가져왔다. 그는 스프레드시트에 새 열을 가지고 있었다: "의도됨?" 각 항목에 대해 예 또는 아니오로.

"그게 제가 지금 쓰는 프레임이에요," 그가 말했다. "그저 '얼마나 드는가'가 아니라 '우리가 이걸 쓰기로 결정했는가'요."

"의도된 비용이 뭐죠?" 마야가 물었다.

"Aurora Global Database 복제요. 우리는 동부 해안에 레스토랑 파트너가 있어서 us-east-1로 복제하기로 결정했어요. 그게 교차 리전 복제로 월 $120 — DR 계획 시절의 봉투 뒷면 추정의 대략 두 배예요. 우리는 특정 이유로 그 비용을 선택했어요."

"그리고 의도하지 않은 건요?"

"테스트가 끝난 후 다섯 달 동안 us-east-1에 쓰던 레오의 분석 파이프라인이요. 아무도 그걸 선택하지 않았어요. 아무도 지켜보지 않았기 때문에 일어나고 있었죠."

"그리고 AWS 서비스 호출에 대한 NAT Gateway 요금은요?"

"그 중간 어딘가예요," 톰이 말했다. "우리는 SSM을 NAT Gateway를 통해 라우팅하기로 명시적으로 결정하지 않았어요 — 그게 기본값이었죠. 우리는 더 싼 옵션이 있다는 걸 몰랐어요. 그게 의도된 건가요? 우리는 선택을 했지만, 우리가 뭘 선택하는지 몰랐을 뿐이에요."

"그게 가장 위험한 카테고리예요," 프리야가 말했다. "당신이 내리는 줄 모르는 결정들."

"그게 VPC Flow Logs 분석이 중요한 이유예요," 톰이 말했다. "그건 보이지 않는 걸 보이게 만들어요. 경계를 넘는 모든 바이트가 이제 우리가 추적할 수 있는 이야기를 가지고 있어요."

"이게 다시 흘러가게 두면 어떻게 되는지 생각해 봤나요?" 프리야가 물었다. "우리는 일회성 분석을 했어요. 6개월 후, 레오는 어딘가에 또 다른 테스트 버킷을 만들어 놨을 거예요."

"제가 바로 여기 있을게요," 레오가 말했다. "다음번엔 eu-west-1에서 할게요. 그럼 적어도 GB당 더 비싸서 더 빨리 알아챌 거예요."

"월간 VPC Flow Log 검토요," 톰이 말했다. "분기별 비용 검토에 추가할게요. 새 교차 리전 흐름이나 NAT Gateway 급증을 보면, 다음 청구서 전에 추적해요."

**변형: 받아들이는 트레이드오프**

모든 것을 단일 가용 영역에서 실행하여 교차 AZ 트래픽을 없애면, Nimbus의 현재 볼륨에서 월 약 $31를 절약한다 — 하지만 인시던트 위험에서 그보다 훨씬 더 가치 있는 Multi-AZ 중복성을 잃는다. 성숙한 비용 대화는 항상 절약을 찾는 것에 관한 게 아니다; 때로는 당신이 정확히 무엇에 비용을 내고 있는지 이해하고 그것이 가치 있다고 결정하는 것에 관한 것이다.

교차 AZ 요금은 회복력의 가격이다. 일부 네트워킹 비용은 비효율이 아니라 아키텍처 약정이다.

SAA-C03 연결: 시험은 "비용 최적화"가 중복성을 제거할 시나리오를 자주 제시한다. 올바른 답은 보통 중복성을 보존하고 다른 곳에서 최적화하는 것이다 — 낭비와 신뢰성의 비용 사이의 차이를 알라.

**CloudFront: 데이터 전송 할인**

여기 직관에 반하는 사실이 있다: CloudFront를 통해 데이터를 제공하는 것은 일반적으로 EC2나 S3에서 직접 제공하는 것보다 싸다.

**직접 EC2-인터넷**: GB당 $0.09
**CloudFront-인터넷**: GB당 $0.085 (약간 더 싸다)

하지만 진짜 절약은 GB당 요율이 아니다 — CloudFront가 엣지 위치에 데이터를 캐시한다는 것이다. 1,000명의 사용자가 같은 메뉴 사진을 요청하면:

- **CloudFront 없이**: 1,000개 요청이 S3에서 인터넷으로 직접 나간다 × 사진 크기 × GB당 $0.09
- **CloudFront로**: 클라이언트는 CloudFront 요율 (GB당 $0.085)로 엣지에서 사진을 받고, 캐시 채움 — CloudFront가 1번의 미스에서 S3에서 가져오는 것 — 은 **무료**다 (AWS는 오리진-CloudFront 전송을 면제한다; 당신은 오리진 GET 요청만 낸다)

83% 캐시 적중률 (13장에서)을 가진 Nimbus의 경우, 요청의 83%가 오리진을 전혀 건드리지 않았다 — 더 적은 오리진 요청, 더 적은 오리진 부하, 그리고 S3의 인터넷 요율 대신 엣지 요율로 청구되는 모든 바이트.

"CloudFront는 그저 성능을 위한 CDN이 아니에요," 톰이 말했다. "데이터 전송을 위한 비용 최적화이기도 하죠."

레오가 생각에 잠긴 표정을 지었다. "지연 시간에 민감하지 않은 자산이라도 모든 정적 콘텐츠 전달을 CloudFront를 통해 옮겨야겠네요."

"맞아요. 사용자가 AWS에서 다운로드하는 거라면, CloudFront를 통과해야 해요."

## 강점과 한계

**NAT Gateway 비용**:

- NAT Gateway를 통한 큰 데이터 볼륨은 빠르게 쌓인다
- VPC 엔드포인트는 일부 NAT 비용을 완전히 제거한다
- 프라이빗 인스턴스가 어떤 서비스를 호출하는지, 엔드포인트가 사용 가능한지 검토하라

**비용을 위한 CloudFront**:

- 캐시 적중률이 비용 절약을 직접 결정한다
- 높은 캐시 적중률 = 더 적은 오리진 요청과 더 적은 오리진 부하, 더하기 CloudFront의 더 싼 뷰어 측 요율로 청구되는 더 많은 바이트 (AWS 오리진에서 CloudFront로의 전송은 전혀 청구되지 않는다)
- 모든 정적 자산 전달을 CloudFront를 통해 옮겨라

**교차 AZ 트레이드오프**:

- 교차 AZ 트래픽을 없애는 것은 보통 절약보다 더 많은 비용이 드는 아키텍처 변경을 요구한다
- 최적화하기 전에 신중하게 계산하라

**S3 Select** (레거시 — 2024년 이래 신규 고객에게 사용 불가; 대신 Athena를 사용하라. S3 Object Lambda도 이제 레거시다 — 2025년 11월 기준 신규 고객에게 닫힘, 기존 워크로드는 영향 없음):

- 원칙은 유효하다: 큰 S3 객체를 다운로드하는 대신 스토리지 계층에서 필터링하라 — 절약은 컴퓨트 시간, 인스턴스 크기, 작업 지속 시간에서 나타난다 (동일 리전 S3 전송은 이미 무료다)
- 파일 전체가 필요할 때는 도움이 되지 않는다

## 요약

톰은 화이트보드의 숫자와 청구서의 마지막 미지수가 실제로 무엇이었는지에 대한 더 명확한 이해로 네트워킹 분석을 마무리했다. 월 $847의 네트워킹 비용은 무능의 미스터리가 아니었다 — 그것은 가용 영역을 가로지르고, 글로벌 사용자를 제공하고, 리전에 걸쳐 데이터를 복제하는 분산 시스템의 예상된 비용이었다. 그중 대부분은 낼 가치가 있었다. 일부는 아니었다. 핵심 진전은 어느 것이 어느 것인지 구별할 수 있게 된 것이었다.

- AWS는 **아웃바운드 데이터** (인터넷: ~GB당 $0.09), **교차 AZ 트래픽** (각 방향 GB당 $0.01), **교차 리전 트래픽** (GB당 $0.02~0.08), 그리고 **NAT Gateway 처리** (GB당 $0.045)에 청구한다.
- **인바운드 데이터**는 무료다. **동일 AZ 트래픽**은 무료다.
- **VPC Flow Logs**는 당신의 VPC 안의 어떤 특정 트래픽 흐름이 각 카테고리의 비용을 생성하는지 드러낸다 — 표적 최적화에 필수적이다. VPC 네트워크 인터페이스를 절대 넘지 않는 흐름 (CloudFront가 S3 오리진에서 가져오는 것 같은)은 자체 도구가 필요하다: CloudFront 표준 로그나 S3 서버 액세스 로그.
- **VPC Gateway Endpoint** (S3, DynamoDB): 무료. 이 서비스들의 NAT Gateway 비용을 제거한다.
- **VPC Interface Endpoint**: 시간당 더하기 GB당 가격. 고볼륨 서비스에는 NAT Gateway보다 싸다.
- **CloudFront**는 직접 EC2-인터넷보다 낮은 요율로 데이터를 제공하고 캐싱을 통해 오리진 전송 볼륨을 극적으로 줄인다.
- 핵심 질문은 그저 "얼마나"가 아니라 "이 비용이 의도된 것인가?"다. 의도하지 않은 비용 — 잊혀진 테스트 파이프라인, NAT를 통한 기본 라우팅 — 이 진짜 절약이 숨는 곳이다.

## 시험 팁

*SAA-C03 도메인: 비용 최적화 아키텍처 설계 (도메인 4, 작업 4.4)*

- **NAT Gateway vs VPC 엔드포인트**: 시험 시나리오: "프라이빗 서브넷의 EC2가 자주 S3/DynamoDB를 호출함 — NAT Gateway 비용을 줄이는 방법?" → VPC Gateway Endpoint (S3와 DynamoDB에 무료).
- **데이터 전송 가격 규칙**:
  - AWS로: 무료
  - 동일 AZ: 무료
  - 교차 AZ: 청구됨
  - 교차 리전: 청구됨 (높은 요율)
  - 인터넷: 청구됨 (상당한 요율)
- **비용 최적화로서의 CloudFront**: "글로벌 콘텐츠 전달을 위한 데이터 전송 비용 절감" → CloudFront. 캐시 계층이 오리진 요청을 줄인다.
- **S3 Transfer Acceleration**: CloudFront 엣지 위치를 사용하여 S3로의 업로드를 *가속*한다. 표준 S3보다 높은 비용. 지리적으로 먼 위치에서 큰 파일을 업로드하는 고객에게 사용하라.
- **교차 리전 복제 비용**: 리전에 걸쳐 데이터를 복제하는 것은 데이터 전송 요금을 발생시킨다. S3 CRR의 경우, 데이터 전송 아웃 요율과 S3 요청 비용을 모두 낸다.
- **PrivateLink (VPC Interface Endpoint)**: AWS 서비스와 다른 AWS 고객이 호스팅하는 서비스에 프라이빗 연결을 제공한다. NAT를 통하는 것보다 더 안전하고, 고볼륨 서비스에는 종종 더 싸다. NAT Gateway 처리 대비 손익분기는 대략 월 420GB다 (엔드포인트 자체의 AZ당 시간당 비용을 세고, NAT Gateway가 다른 트래픽을 위해 남는다고 가정).

## 연습문제

**연습문제 1 — 회상**

VPC Gateway Endpoint와 VPC Interface Endpoint의 차이를 설명하라. 각각은 어떤 AWS 서비스에 사용 가능하고, 각각의 비용은 무엇인가?

*(힌트: Gateway Endpoint는 무료지만 S3와 DynamoDB에만. Interface Endpoint는 시간당 비용이 들지만 대부분의 다른 AWS 서비스에 작동한다.)*

**연습문제 2 — SAA-C03 시나리오**

*시나리오*: 한 회사의 애플리케이션이 프라이빗 서브넷의 EC2 인스턴스에서 실행됩니다. 인스턴스는 Amazon SQS와 Amazon S3에 잦은 API 호출을 합니다. 현재, 모든 트래픽은 NAT Gateway를 통해 나갑니다. 팀은 NAT Gateway 비용을 줄이고 싶습니다. 데이터 보안이 유지되어야 합니다 — 어떤 트래픽도 공공 인터넷을 통과해서는 안 됩니다.

다음 중 최소의 지속 비용으로 이 요구 사항을 가장 잘 충족하는 접근법은?

A) SQS를 위한 Gateway Endpoint와 S3를 위한 Gateway Endpoint 생성  
B) SQS와 S3 둘 다를 위한 Interface Endpoint 생성  
C) SQS를 위한 Interface Endpoint와 S3를 위한 Gateway Endpoint 생성  
D) NAT Gateway를 제거하고 API 호출에 인터넷 게이트웨이를 직접 사용

**힌트 1**: Gateway Endpoint는 S3와 DynamoDB에만 사용 가능하다.

**힌트 2**: Interface Endpoint는 SQS와 많은 다른 서비스에 사용 가능하다 (하지만 비용이 든다).

**힌트 3**: 프라이빗 서브넷 라우팅 테이블의 인터넷 게이트웨이는 그것을 퍼블릭 서브넷으로 만든다 — 보안 요구 사항 위반.

**정답**: C

**설명**: S3는 Gateway Endpoint (무료)를 사용한다. SQS는 Interface Endpoint (유료)를 요구한다. 이 조합은 두 서비스 모두에 대한 NAT Gateway 데이터 처리 비용을 제거한다. 모든 트래픽은 AWS의 프라이빗 네트워크 안에 남는다 — 공공 인터넷 통과 없음.

**왜 A가 아닌가?** Gateway Endpoint는 SQS에 사용할 수 없다. S3와 DynamoDB만 Gateway Endpoint를 가진다.

**왜 B가 아닌가?** 이것이 작동하기는 하지만, S3에 (무료 Gateway Endpoint 대신) Interface Endpoint를 사용하는 것은 불필요한 시간당 요금을 발생시킨다. S3와 DynamoDB에는 항상 무료 Gateway Endpoint를 사용하라.

**왜 D가 아닌가?** 프라이빗 서브넷에서 인터넷 게이트웨이로의 경로를 추가하는 것은 그것을 퍼블릭 서브넷으로 만든다. 프라이빗 서브넷의 EC2 인스턴스는 보통 Elastic IP가 없어서, 추가 변경 없이는 실제로 인터넷 게이트웨이를 통해 라우팅할 수 없다 — 그리고 그렇게 하는 것은 그것들을 인바운드 인터넷 트래픽에 노출시킨다.

*SAA-C03 도메인: 비용 최적화 아키텍처 설계 — 작업 4.4*

**연습문제 3 — 아키텍처 도전** *(선택)*

Nimbus의 동부 해안 사용자가 상당한 트래픽을 생성한다. 애플리케이션은 그들을 us-west-2 (오레곤)에서 제공한다. 현재:

- API 응답은 us-west-2 EC2 인스턴스에서 동부 해안 사용자에게 직접 간다 (~80ms, GB당 $0.09)
- 메뉴 사진은 S3 us-west-2에서 보스턴의 CloudFront 엣지를 통해 간다 (캐싱 후 ~8ms)

팀은 API 지연 시간을 줄이기 위해 동부 해안 사용자를 위한 두 번째 애플리케이션 리전을 us-east-1 (북부 버지니아)에 추가하는 것을 고려하고 있다.

이 변경의 데이터 전송 비용을 분석하라. 이중 리전 설정은 어떤 새 교차 리전 데이터 전송 비용을 발생시키는가? Route 53 지연 시간 기반 라우팅은 총 전송 비용을 줄이는가 늘리는가? 어떤 조건 (트래픽 볼륨, 지연 시간 민감도)에서 이중 리전 설정이 본전을 뽑는가?

*(정답은 단 하나가 아니다. 목표는 멀티 리전 비용-편익 분석을 연습하는 것이다.)*

## 크레딧 후 장면

톰은 네트워킹 분석을 마무리했다.

석 달간의 총 최적화 프로젝트 효과:

- EC2 Savings Plans: -연 $14,200
- S3 라이프사이클 정책: -연 $7,800
- 스토리지 (S3 + EBS): -연 $6,200
- 데이터베이스 계층: -연 $5,892
- 네트워킹: -연 $1,812
- **총합: -연 $35,904**

그는 그것을 회의실의 화이트보드에 적었다.

레오가 그것을 응시했다. "3만 5천."

"그리고 잔돈," 톰이 말했다.

"연간으로."

"연간으로."

프리야가 계산을 했다. "그건 우리가 가치를 창출하지 않는 것들에 쓰고 있던 월 $2,992예요."

"전부는 아니에요," 톰이 정정했다. "그중 일부는 우리가 가치를 얻고 있던 것이었지만, 너무 많이 내고 있던 거예요. Savings Plans — 우리는 정확히 같은 EC2 용량을 얻고 있었어요, 그저 더 나은 가격에."

마야가 오랫동안 화이트보드 앞에 섰다.

"우리가 Nimbus를 시작했을 때," 그녀가 말했다, "모든 달러가 중요했어요. 우리는 첫 EC2 인스턴스를 겨우 감당할 수 있었죠."

"네," 톰이 말했다.

"그리고 어느 순간부터, 우리는 달러를 그렇게 주의 깊게 지켜보는 걸 멈췄어요."

"성장이 그렇게 만들죠," 프리야가 말했다. "초점이 최적화가 아니라 구축으로 옮겨가요."

"둘 다 중요해요," 마야가 말했다. "둘 다, 항상. 이걸 위키에 추가하세요. 그리고 비용에 대한 분기별 검토를 설정하세요."

톰은 이미 자기 캘린더를 열고 있었다.

다음 몇 장에서: 우리는 개별 서비스에서 줌아웃하여 아키텍트처럼 생각하기 시작한다.
