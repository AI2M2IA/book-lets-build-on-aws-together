# 5장: 클라우드에 사는 파일 캐비닛

Leo는 Nimbus가 업로드된 메뉴 사진을 EC2 인스턴스에 직접 저장하고 있다는 것을 깨달았다.
고객이 업로드하는 모든 사진 — 바삭한 arepa, 구운 연어 플레이트, 완벽하게 담긴 샐러드 그릇 — 이 단일 가상 머신에 앉아 있었다.

그 머신이 언제든 재시작되거나, 크기 조정되거나, 교체된다면?

사라진다.

"고객이 지금까지 업로드한 사진이 몇 장이야?" Maya가 물었다.

Leo가 콘솔을 열었다. "약 800장이요."

"그리고 서버를 재시작하면 그 800장의 사진에 무슨 일이 일어나?"

Leo의 또 다른 의미 있는 멈춤.

이 챕터는 파일이 클라우드에서 실제로 어디에 속하는지에 관한 것이다.

**"서버에" 파일을 저장하는 문제**

EC2 인스턴스의 파일시스템 안에 직접 파일을 저장하면 — 그 특정 머신의 수명주기에 파일을 묶는 것이다.

이것은 여러 문제를 만든다:

**본질적으로 일시적이다.** EC2 인스턴스는 중지, 종료, 교체될 수 있다. 로컬 디스크는 영구적으로 유지되도록 설계되지 않았다. 임시 스크래치 공간이다.

**단일 장애 지점이다.** 인스턴스가 실패하면, 파일도 함께 사라진다. 이중화 없음. 백업 없음. 하나의 나쁜 아침에 800장의 메뉴 사진이 사라진다.

**인스턴스 간에 공유할 수 없다.** 두 번째 서버를 추가할 때(7장에서 할 것이다), 첫 번째 서버의 디스크에 저장된 파일을 볼 수 없다. 두 서버는 격리되어 있다. 사진을 업로드한 사용자는 볼 수 있지만; 다른 서버에 접근하는 다른 사용자는 못 볼 수 있다.

**확장이 없다.** EC2 디스크 공간은 유한하다. 가득 차면, 업로드 수락을 중단하거나 압박 속에서 스토리지를 확장하기 위해 허둥댄다.

더 나은 모델이 있다. AWS는 2006년에 그것을 만들었고, 여전히 세계에서 가장 널리 사용되는 클라우드 서비스 중 하나다.

**Amazon S3: 온라인에 사는 하드 드라이브**

**Amazon S3** — Simple Storage Service — 는 AWS의 객체 스토리지 서비스다.

인터넷에 사는 하드 드라이브로 생각하라. 무한한 하드 드라이브. 단일 데이터 센터 손실이 파일을 잃지 않도록 최소 세 개의 가용 영역에 모든 객체의 여러 복사본을 자동으로 백업하는.

S3의 핵심 개념은 **객체**다.

객체는 모든 파일이다: 사진, 비디오, PDF, CSV, 백업, 로그 파일. S3는 유형이나 구조를 신경쓰지 않는다. 바이트를 저장하고 요청할 때 돌려준다.

객체는 **버킷** 안에 산다. 버킷은 최상위 폴더 같다 — 객체를 담는 S3 안의 이름이 있는 컨테이너. 각 버킷은 전 세계적으로 고유한 이름을 갖고(모든 AWS 계정에 걸쳐 두 버킷이 이름을 공유할 수 없다) 특정 리전에 존재한다.

**S3 작동 방식**

모델이 단순하고, 그 단순함이 요점이다.

버킷에 객체를 **업로드**한다. S3가 **키** — 기본적으로 `menus/restaurant-001/photo-arepa.jpg` 같은 경로명 — 를 부여한다. 그 키가 버킷 내에서 객체를 고유하게 식별한다.

버킷 이름과 키를 사용하여 객체를 **다운로드**(또는 검색)한다.

객체를 공개적으로 접근 가능하게 만들 수도 있다 — URL을 가진 누구든지 다운로드할 수 있다는 것을 의미한다. 이것이 대부분의 웹사이트가 이미지를 제공하는 방법이다: S3에 이미지를 저장하고, 공개적으로 만들고, HTML에 URL을 포함한다.

아니면 객체를 비공개로 유지한다 — 인증된 요청만 접근 가능하다. 이것이 고객 데이터, 백업, 민감한 것에 올바른 모델이다.

S3는 파일시스템이 아니다. 진짜 폴더가 없다. 키 이름의 `/`는 그냥 관례다 — S3는 전체 키를 평평한 문자열로 처리한다. 하지만 폴더처럼 보이고 대부분의 도구는 폴더로 표시하므로, 실제로는 이 구분을 걱정하지 마라.

**S3가 일반 하드 드라이브와 다른 이유**

세 가지가 S3를 EC2 인스턴스의 파일 스토리지와 근본적으로 다르게 만든다:

**내구성.** AWS는 S3를 99.999999999%(열한 개의 9) 내구성으로 설계한다. 이는 1천만 개의 객체를 저장하면, 하드웨어 장애로 인해 1만 년에 하나의 객체를 잃을 것으로 예상할 수 있다는 것을 의미한다. 모든 객체의 여러 복사본을 최소 세 개의 가용 영역에 자동으로 저장하여 이를 달성한다.

**가용성.** S3는 개별 구성 요소가 실패해도 접근 가능하도록 설계되었다. 하나의 서버에 연결하는 게 아니라 — 장애를 우회하는 분산 시스템에 연결하는 것이다.

**규모.** S3는 본질적으로 무제한의 데이터를 보유한다. 단일 버킷이 수조 개의 객체를 보유할 수 있다. Amazon 자체가 상상하기 어려운 규모로 데이터를 저장하기 위해 S3를 사용한다.

**버전 관리: 실행 취소 버튼**

S3 콘솔을 탐색하던 Maya가 발견한 것이 있다.

S3는 **버전 관리**를 지원한다. 버킷에서 버전 관리를 활성화하면, S3는 모든 객체의 모든 버전을 유지한다 — 이전 버전과 삭제된 버전을 포함하여.

이것이 파일의 실행 취소 버튼이다.

실수로 이전 것을 덮어쓰는 새 메뉴 사진을 업로드했는가? 이전 버전이 여전히 거기에 있다. 실수로 파일을 삭제했는가? 복구 가능하다. 모든 파일을 암호화된 쓰레기로 덮어쓰는 랜섬웨어에 맞았는가? 버전 관리를 사용하면, 공격 이전으로 복원한다.

"그 모든 버전을 유지하는 데 얼마나 드나요?" Tom이 물었다.

모든 버전의 스토리지 비용을 지불한다. 대용량 파일의 많은 버전이 있으면, 비용이 쌓인다. AWS는 특정 시간이 지난 후 이전 버전을 자동으로 삭제하는 **수명주기 정책**을 갖고 있다 — 비용 최적화를 깊이 다루는 23장에서 다룬다.

**접근 제어: 공개 vs. 비공개**

기본적으로, S3의 모든 것은 비공개다. AWS 계정만 접근할 수 있다.

개별 객체를 공개적으로 만들 수 있다 — 웹사이트 방문자에게 메뉴 이미지를 제공하는 방법이다. 아니면 모든 것을 비공개로 유지하고 **사전 서명된 URL**을 생성할 수 있다: AWS 자격증명 없이 특정 객체를 다운로드할 수 있는 시간 제한 링크. 고객이 24시간 동안 영수증을 다운로드하도록 하는 데 완벽하다.

Priya는 이에 대해 매우 강한 의견을 갖고 있었다.

"의도적으로 전체 인터넷에 모든 객체를 접근 가능하게 만들기로 결정하지 않는 한 버킷을 완전히 공개로 만들지 마세요," 그녀가 말했다. "가장 흔한 S3 보안 실수는 민감한 데이터를 포함하는 버킷을 우연히 노출하는 것이다."

AWS는 이제 계정 수준에서 적용할 수 있는 "공개 접근 차단" 설정이 있어, 버킷별로 명시적으로 재정의하지 않는 한 모든 버킷을 비공개로 강제한다.

항상 활성화하라.

**S3 스토리지 클래스: 모든 데이터가 동등하지 않다**

모든 데이터가 동등하게 접근되지 않는다.

가장 인기 있는 메뉴 사진은 초당 수십 번 가져온다. 3년 전 로그는 일 년에 한 번, 있다면, 접근된다. S3는 이것을 인식하고 서로 다른 성능과 비용 트레이드오프를 가진 서로 다른 **스토리지 클래스**를 제공한다.

| 스토리지 클래스 | 사용 사례 | 검색 | 비용 |
|---|---|---|---|
| S3 Standard | 자주 접근하는 데이터 | 즉시 | GB당 높음 |
| S3 Standard-IA | 비정기 접근이지만 빠른 검색이 필요 | 즉시 | GB당 낮음, 검색 수수료 |
| S3 Glacier Instant | 가끔 접근하는 아카이브 | 즉시 | 훨씬 낮음 |
| S3 Glacier Flexible | 드물게 접근하는 아카이브 | 분~시간 | 매우 낮음 |
| S3 Glacier Deep Archive | 컴플라이언스 아카이브, 거의 접근 안 함 | 최대 12시간 | 최저 |

23장에서 이것들을 깊이 다룬다. 지금은: 개념은 접근 패턴과 나이에 따라 스토리지 클래스 간에 객체를 자동으로 이동하여, 거의 건드리지 않는 데이터에 상당한 비용을 절감할 수 있다는 것이다.

## 장점과 한계

**S3가 훌륭한 이유**:

- 열한 개의 9 내구성. 데이터는 거의 모든 다른 시스템보다 S3에서 더 안전하다.
- 무제한 규모. 스토리지를 프로비저닝할 필요가 없다 — 그냥 늘어난다.
- 제공하는 것에 비해 매우 저렴하다(GB당 월 몇 분의 1센트).
- 거의 모든 다른 AWS 서비스와 기본 통합.
- 정적 웹사이트 호스팅 지원 — 서버 없이 S3에서 직접 완전한 정적 웹사이트를 제공할 수 있다.

**S3가 올바른 선택이 아닌 경우**:

- S3는 파일시스템이 아니다. 애플리케이션이 드라이브를 마운트하고 로컬 디스크처럼 사용해야 하는 경우(읽기, 쓰기, 파일 수정), S3는 잘못된 도구다.
  EFS(Elastic File System, 6장) 또는 EBS를 대신 사용하라.
- S3는 로컬 디스크보다 눈에 띄게 더 높은 지연 시간이 있다. 빠른 랜덤 액세스 I/O가 필요한 데이터베이스나 애플리케이션의 경우, 블록 스토리지(EBS, 6장)가 적절하다.
- S3로의 대용량 데이터 전송은 무료다. S3 *밖으로의* 대용량 데이터 전송은 돈이 든다.
  이것은 흔한 결제 놀라움이다 — 30장에서 다룬다.

## 요약

- **Amazon S3**는 객체 스토리지다 — 이름이 있는 컨테이너(버킷이라고 불리는)에 파일(객체라고 불리는)을 저장하는 곳.
- S3는 모든 객체의 복사본을 최소 세 개의 가용 영역에 자동으로 저장하여 열한 개의 9 내구성을 위해 설계되었다.
- EC2 인스턴스에 저장된 파일은 그 인스턴스의 수명주기에 묶여 있다. 중요한 파일은 서버가 아닌 S3에 속한다.
- **버전 관리**는 객체의 이전 버전을 보존한다 — 실행 취소 버튼.
- 기본적으로, S3는 비공개다. 계정 수준에서 "공개 접근 차단"을 활성화하라.
- S3에는 서로 다른 접근 패턴과 비용을 위한 여러 **스토리지 클래스**가 있다.
  비정기 접근 클래스는 훨씬 저렴하지만 검색 수수료가 있다.

## 시험 팁

*SAA-C03 도메인 3 — 태스크 3.1 (고성능 스토리지 솔루션)*

- **S3는 객체 스토리지이지, 블록 스토리지가 아니다.** 시험 시나리오가 여러 서버가 마운트할 수 있는 파일시스템이 필요하면, 그것은 EFS다. 단일 EC2 인스턴스를 위한 디스크가 필요하면, 그것은 EBS다. 파일, 백업, 이미지, 또는 HTTP를 통해 접근하는 데이터를 저장해야 하면 — 그것이 S3다.
- **열한 개의 9 내구성**은 S3가 여러 AZ에 데이터를 자동으로 복제한다는 것을 의미한다.
  이것을 설정하지 않는다 — 기본값이다.
- **S3는 리전별**이지만, 전 세계적으로 접근 가능하다. 버킷은 특정 리전에 존재하지만, 어디서나 접근할 수 있다.
- **사전 서명된 URL**은 비공개 객체에 시간 제한 접근을 허용한다. 일반적인 패턴:
  애플리케이션이 15분 동안 유효한 사전 서명된 URL을 생성하고, 사용자에게 제공하며, 사용자가 S3에서 직접 파일을 다운로드한다.
- **S3 Standard-IA**에는 최소 스토리지 기간 요금(30일)이 있다. 빠르게 삭제할 데이터에는 사용하지 마라. 시험은 스토리지 클래스 간 트레이드오프를 알고 있는지 테스트한다.
- **스토리지 클래스 의사결정 트리**: *자주 접근함* → S3 Standard; *비정기적으로 접근하지만 빠른 검색이 필요함* → S3 Standard-IA; *가끔 접근하는 아카이브* → S3 Glacier Instant Retrieval; *드물게 접근하는 아카이브* → S3 Glacier Flexible Retrieval; *컴플라이언스 아카이브, 거의 접근 안 함* → S3 Glacier Deep Archive. 시나리오가 "비용 최적화"와 "비정기 접근"을 언급할 때, Standard-IA가 거의 항상 답이다. "컴플라이언스"나 "7년 보관"을 언급할 때, Glacier Deep Archive를 생각하라.

## 연습 문제

**연습 1 — 회상**

자신의 말로: S3 객체가 무엇인가? S3 버킷이 무엇인가? S3에 파일을 저장하는 것이 EC2 인스턴스의 로컬 디스크에 저장하는 것보다 나은 이유는 무엇인가?

*(힌트: EC2 인스턴스가 종료되면 파일에 무슨 일이 일어나는지 생각해보라. S3는 무엇을 다르게 하는가?)*

**연습 2 — 시험 연습**

*시나리오*: 미디어 회사가 다큐멘터리 비디오를 제작한다. 원본 4K 영상(제작 중 자주 접근), 편집된 최종 컷(배포를 위해 월별 접근), 아카이브 마스터(무기한 보관하지만 컴플라이언스 목적으로 최대 일 년에 한 번 접근)를 저장해야 한다. 각 계층의 접근 요구사항을 충족하면서 스토리지 비용을 최소화하기를 원한다.

다음 중 요구사항을 가장 잘 충족하는 스토리지 전략은?

A) 일관된 성능과 단순함을 위해 모든 콘텐츠를 S3 Standard에 저장  
B) 원본 영상은 S3 Standard에, 최종 컷은 S3 Standard-IA에, 아카이브는
   S3 Glacier Deep Archive에 저장  
C) 가장 빠른 접근을 위해 모든 콘텐츠를 EC2 인스턴스 스토리지에 저장  
D) 비용 최소화를 위해 모든 콘텐츠를 S3 Glacier Deep Archive에 저장

**힌트 1**: 서로 다른 파일은 서로 다른 접근 패턴을 갖는다. S3는 서로 다른 접근 빈도를 위한 서로 다른 스토리지 클래스를 제공한다. 어떤 클래스가 "자주 접근함"과 일치하는가?

**힌트 2**: "최대 일 년에 한 번" 접근하는 아카이브는 즉시 검색이 필요하지 않다. 어떤 스토리지 클래스가 최소 비용으로 장기 아카이브를 위해 설계되었는가?

**힌트 3**: 각 계층의 접근 빈도를 적절한 스토리지 클래스와 매치하라.
자주 접근함 = Standard. 월별 = Standard-IA. 일 년에 한 번 = Glacier Deep Archive.

**답**: B

**설명**: 이 전략은 각 데이터 계층을 적절한
S3 스토리지 클래스와 올바르게 매치한다. 자주 접근하는 원본 영상은 검색 수수료 없이 즉시 접근을 위해 Standard에 남는다. 월별 접근하는 최종 컷은 Standard-IA로 이동(더 낮은 스토리지 비용, 합리적인 검색 수수료). 일 년에 한 번 접근하는 아카이브는 가능한 가장 낮은 스토리지 비용을 위해 Glacier Deep Archive로 이동한다.

**왜 A가 아닌가?** 모든 것을 Standard에 저장하는 것은 간단하지만 비싸다. 거의 접근하지 않는 아카이브 콘텐츠에 프리미엄 가격을 지불하는 것이다.

**왜 C가 아닌가?** EC2 인스턴스 스토리지는 일시적이고 장기 미디어 스토리지에 적합하지 않다. 인스턴스가 종료되면, 모든 콘텐츠가 사라진다.

**왜 D가 아닌가?** Glacier Deep Archive는 최대 12시간의 검색 시간이 있다. 자주 접근하는 제작 영상을 거기에 저장하면 제작 작업이 불가능해진다.
