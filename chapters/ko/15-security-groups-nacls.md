**두 레이어의 네트워크 보안**

VPC에서, 네트워크 트래픽을 제어하는 두 가지 별개의 도구가 있다:

**보안 그룹**: 개별 리소스(EC2 인스턴스, RDS 데이터베이스, 로드 밸런서, VPC의 Lambda 함수)에 연결된 가상 방화벽. 리소스 수준에서 운영된다.

**네트워크 ACL(NACL)**: 서브넷에 연결된 방화벽 규칙. 서브넷 경계에서 운영된다 — 트래픽이 해당 서브넷의 모든 리소스에 도달하기 전에.

둘 다 이해하려면 하나의 중요한 차이를 이해해야 한다: **상태가 있는 vs. 무상태**.

**상태가 있는: 보안 그룹**

보안 그룹은 **상태가 있다**.

특정 포트의 인바운드 트래픽을 허용하면, 응답 트래픽이 아웃바운드에 대한 명시적 규칙이 없더라도 자동으로 아웃바운드가 허용된다.

특정 대상으로의 아웃바운드 트래픽을 허용하면, 돌아오는 응답이 자동으로 허용된다.

사무실 건물의 상태가 있는 경비를 생각하라. 들어가려면 배지를 보여준다. 나중에 걸어 나온다. 경비는 나가는 길에 다시 확인할 필요가 없다 — 시스템은 당신이 들어갔다는 것을 알고, 나가도록 허용된다.

**Nimbus API EC2 인스턴스의 보안 그룹 규칙:**

- **인바운드 — TCP 8080 — 로드 밸런서 SG에서** → ALB에서 API 트래픽 수락
- **인바운드 — TCP 22 — 배스천 호스트 SG에서** → 배스천에서만 SSH
- **아웃바운드 — TCP 5432 — RDS SG로** → PostgreSQL에 연결
- **아웃바운드 — TCP 6379 — ElastiCache SG로** → Redis에 연결
- **아웃바운드 — TCP 443 — 0.0.0.0/0으로** → 외부 API로 HTTPS

참고: 포트 8080에 대한 명시적 아웃바운드 규칙이 없다. 인바운드 규칙이 상태가 있다 — 응답 트래픽(로드 밸런서에 대한 API의 응답)이 자동으로 허용된다.

또한 참고: 보안 그룹 규칙은 IP 주소가 아닌 *다른 보안 그룹*을 참조한다. "로드 밸런서 보안 그룹에서 인바운드 허용"은 "이 보안 그룹이 연결된 모든 리소스에서 트래픽을 허용한다"를 의미한다. 이것이 IP 주소를 추적하는 것보다 더 유연하고 유지 관리하기 쉽다.

**기본 동작:**

- 기본적으로 모든 인바운드 트래픽이 거부됨
- 기본적으로 모든 아웃바운드 트래픽이 허용됨
- 모든 규칙이 평가됨(보안 그룹은 순서가 있는 규칙이 없다 — 일치하는 모든 규칙이 적용됨)
- 보안 그룹은 트래픽을 **허용**만 할 수 있다 — 명시적 거부 규칙을 만들 수 없다

**무상태: 네트워크 ACL**

NACL은 **무상태**다.

포트 8080에서 인바운드 트래픽을 허용하면, 인바운드만 커버된다. 응답(임시 포트의 아웃바운드 트래픽)은 아웃바운드 규칙으로 명시적으로 허용해야 한다.

금속 탐지기처럼 생각하라. 들어올 때 통과한다. 금속 탐지기는 당신이 이미 통과했다는 것을 모른다 — 나갈 때도 다시 통과해야 한다.

**NACL 규칙은 번호가 있고 순서대로 평가된다.** 먼저 일치하는 규칙이 이긴다. 규칙 100이 규칙 200보다 먼저 평가된다. 규칙 100이 트래픽을 거부하고 규칙 200이 허용하면, 트래픽이 거부된다.

NACL은 트래픽을 명시적으로 **거부**할 수 있다 — 허용만 할 수 있는 보안 그룹과 달리. 이것이 특정 IP 범위를 차단하는 데 유용하다.

**기본 NACL 동작:**

- (VPC와 함께 만들어진) 기본 NACL은 모든 인바운드 및 아웃바운드 트래픽을 허용한다
- 사용자 정의 NACL은 기본적으로 모든 트래픽을 거부한다(원하는 것을 명시적으로 허용해야 한다)

**공개 서브넷의 NACL(단순화):**

*인바운드 규칙(순서대로 평가됨 — 첫 번째 일치가 이긴다):*

- 규칙 100: TCP 443, 0.0.0.0/0에서 → **허용** (HTTPS)
- 규칙 110: TCP 80, 0.0.0.0/0에서 → **허용** (HTTP)
- 규칙 120: TCP 1024–65535, 0.0.0.0/0에서 → **허용** (임시 반환 포트)
- 규칙 \*: 모든 트래픽 → **거부**

*아웃바운드 규칙:*

- 규칙 100: TCP 443, 0.0.0.0/0으로 → **허용** (HTTPS)
- 규칙 110: TCP 80, 0.0.0.0/0으로 → **허용** (HTTP)
- 규칙 120: TCP 1024–65535, 0.0.0.0/0으로 → **허용** (임시 반환 포트)
- 규칙 \*: 모든 트래픽 → **거부**

규칙 120(포트 1024-65535)은 임시 포트를 허용한다 — TCP 응답 트래픽에 사용되는 임시 높은 번호의 포트. NACL이 무상태이기 때문에, 명시적으로 아웃바운드를 허용해야 한다, 그렇지 않으면 서버의 응답이 통과하지 못한다.

**각각을 언제 사용하는가**

"잠깐 — 그런데 *왜* 그렇게 하는 거죠?" Maya가 물었다. "보안 그룹이 이미 작동한다면, 왜 두 개의 별개 도구 — 보안 그룹 *그리고* NACL — 을 가져요? 추가 복잡성의 요점이 뭐죠?"

답은 그것들이 다른 수준에서 운영되고 다른 기능을 가진다는 것이다. 보안 그룹은 개별 리소스를 보호하고 트래픽을 허용만 할 수 있다. NACL은 전체 서브넷을 보호하고 명시적으로 거부할 수 있다. 둘 다 가지면 리소스 수준에서 세밀한 허용 규칙을, 서브넷 수준에서 광범위한 거부 규칙을 적용할 수 있다 — 하나가 다른 것을 방해하지 않고.

**보안 그룹**을 주요 접근 제어 레이어로 사용하라. 관리하기 쉽고, 상태가 있으며(임시 포트를 잊어서 우연히 차단할 가능성 적음), 다른 보안 그룹 참조를 지원한다.

**NACL**을 서브넷 수준 제어에 특히 다음 경우에 사용하라:

- **명시적 거부 규칙**: 특정 IP 주소나 범위가 전체 서브넷에 도달하는 것을 차단
- **긴급 차단**: IP가 활발히 공격하고 있다 — 리소스에 도달하기 전에 전체 서브넷을 차단하기 위해 NACL 거부 규칙 추가

여러분은 궁금할 것이다: 보안 그룹이 상태가 있고 기본적으로 모든 인바운드를 차단한다면, 언제 실제로 NACL이 필요한가? 보안 그룹이 대부분의 경우를 잘 처리한다. 하지만 그것이 할 수 없는 한 가지가 있다: 명시적으로 거부하기. 보안 그룹은 트래픽을 허용만 할 수 있다 — 규칙이 일치하지 않으면, 트래픽이 기본적으로 거부된다. "이 특정 IP를 차단"이라고 말하는 규칙을 추가할 수 없다. 그것을 위해서는, NACL이 필요하다: 특정 주소 범위를 서브넷의 어느 리소스에 도달하기 전에 멈추는 번호가 있는 거부 규칙. NACL은 긴급 대응(활성 공격자 차단)과 개별 리소스 설정에 의존해서는 안 되는 서브넷 수준 경계를 시행하는 데 가장 유용하다.

"그러면 보안 그룹이 세밀한 제어이고," Maya가 말했다. "NACL이 광범위한 획이군요?"

"보안 그룹은 개별 리소스를 보호해," Priya가 확인했다. "NACL은 전체 서브넷을 보호해. IP가 네트워크의 어느 것에도 도달하는 것을 막고 싶을 때는 NACL. 로드 밸런서만 API 서버에 도달하도록 허용하고 싶을 때는 보안 그룹."

"공격자가 다른 IP로 돌아오면 무슨 일이 일어나는지 생각해봤어?" Priya가 말했다. "NACL이 하나의 범위를 차단해. 그들이 다른 것으로 이동해."

"그게 GuardDuty가 있는 이유예요," Leo가 말했다. "행동 탐지. 같은 스크립트가 새 IP에서 실행되면, 트래픽 패턴이 같게 보여요."

"거기 갈 거야," Priya가 말했다. "먼저 할 것부터."

"이 모든 게 한 달에 얼마나 들어?" Tom이 물었다.

보안 그룹과 NACL 자체는 무료다. AWS는 보안 그룹의 수, 규칙의 수, 또는 NACL 항목의 수에 대해 청구하지 않는다. 비용 고려는 간접적이다: 더 엄격한 아웃바운드 보안 그룹 규칙은 NAT 게이트웨이를 통해 더 적은 트래픽을 라우팅할 수 있어, 데이터 처리 요금을 줄인다.

"그러니까 보안 제어는 무료네요," Rafael이 말했다. "비용은 그것들을 지원하는 인프라고요."

"맞아. 고가용성을 위한 NAT 게이트웨이. 그렇지 않으면 NAT를 통과할 서비스를 위한 인터페이스 VPC 엔드포인트. 그것들은 비용이 있어. 보안 그룹 규칙 자체는 없어."

```
CloudFront + Shield (DDoS 흡수)
  ↓
WAF (애플리케이션 계층 필터링)
  ↓
인터넷 게이트웨이
  ↓
공개 서브넷의 NACL (서브넷 수준 규칙, 긴급 차단)
  ↓
ALB 보안 그룹 (어디서든 HTTPS)
  ↓
프라이빗 앱 서브넷의 NACL
  ↓
EC2 API 보안 그룹 (ALB SG에서만 포트 8080)
  ↓
프라이빗 데이터 서브넷의 NACL
  ↓
RDS 보안 그룹 (API SG에서만 포트 5432)
```

"각 레이어가 이전 것이 실패할 수 있다고 가정해," 그녀가 말했다. "데이터베이스는 네트워크 레이어가 공격자를 멈췄다고 신뢰하지 않아. EC2 인스턴스는 ALB가 공격자를 멈췄다고 신뢰하지 않아. 각 레이어가 자체 규칙을 독립적으로 시행해."

"심층 방어," Maya가 말했다.

"심층 방어. 하나의 레이어를 통과하는 공격자가 여전히 다음 것을 마주해. 어떤 단일 잘못된 설정도 치명적이지 않아. 하나의 레이어가 실패하고, 다른 것들이 버틴다는 거야."

Leo가 다이어그램을 봤다. 공격자가 하나의 EC2 인스턴스를 침해했다. 그들은 자격증명 레이어를 통과했다. 하지만 모든 후속 레이어가 버텼다.

그것이 실제로 심층 방어가 보이는 모습이었다.

**사건: 레이어들이 잡아낸 것**

루마니아 IP 공격으로 돌아가서:

**일어난 일**: 공격자가 침해된 배포 키를 사용하여 하나의 EC2 인스턴스에 스캔 스크립트를 업로드했다. 스크립트가 다른 서비스에 연결하려 했다.

**무엇이 그들을 막았나**:

- RDS 보안 그룹은 API EC2 보안 그룹에서만 포트 5432에서 인바운드를 허용했다. 스크립트는 올바른 보안 그룹을 연결하지 않았기 때문에 스캔 도구에서 데이터베이스에 접근할 수 없었다.
- ElastiCache 보안 그룹은 API EC2 보안 그룹에서만 포트 6379에서 인바운드를 허용했다.
- 다른 EC2 인스턴스는 배스천 호스트 보안 그룹에서만 SSH를 허용했다.

**무엇이 그들을 막지 못했나**: 

- EC2 인스턴스의 아웃바운드 규칙은 0.0.0.0/0으로 HTTPS를 허용했다(패키지 다운로드에 필요). 스크립트가 이것을 사용하여 공격자의 서버에 아웃바운드 연결을 만들었다.

사건 후, Priya가 추가했다:

- 루마니아 IP 범위를 차단하는 NACL 규칙
- EC2 인스턴스의 더 제한적인 아웃바운드 규칙(특정 알려진-좋은 대상만 허용)
- 모든 인스턴스에서 **IMDSv2가 강제됐는지**(`HttpTokens=required`) 확인 — 스크립트가 인스턴스 *위에서* 실행됐다는 것은 인스턴스 역할의 임시 자격증명을 위해 메타데이터 서비스를 쿼리할 수 있었다는 것을 의미했다. IMDSv2는 4장에서 활성화됐었다; Priya는 그것이 여전히 어디에나 요구되는지 검증했다. 코드 실행을 가진 공격자 더하기 IMDSv1은 도난당한 AWS 자격증명과 같기 때문이다.

**흐름 로그 읽기: Priya가 본 것**

조사는 VPC 흐름 로그로 시작됐다. Priya가 CloudWatch Logs Insights를 열고 지난 48시간에 대한 흐름 로그 그룹에 대해 쿼리를 실행했다:

```
fields @timestamp, srcAddr, dstAddr, srcPort, dstPort, action
| filter srcAddr = "10.0.10.7"
| filter action = "REJECT"
| sort @timestamp asc
```

`10.0.10.7`은 침해된 EC2 인스턴스였다. REJECT 필터는 차단된 연결 시도를 보여줬다.

결과:

```
10.0.10.7 → 10.0.10.8  port 22    REJECT   # 다른 EC2 인스턴스 — SSH 차단
10.0.10.7 → 10.0.10.9  port 22    REJECT   # 또 다른 EC2 — SSH 차단
10.0.10.7 → 10.0.20.8  port 5432  REJECT   # RDS — 보안 그룹에 의해 차단
10.0.10.7 → 10.0.20.9  port 5432  REJECT   # RDS 복제본 — 차단
10.0.10.7 → 10.0.20.11 port 6379  REJECT   # Redis — 차단
```

스캔이 모든 내부 서비스를 타격했다. 모든 시도가 거부됐다. 보안 그룹 설계가 버텼다.

하지만 아웃바운드 ACCEPT 항목도 있었다:

```
10.0.10.7 → 185.220.101.55  port 443  ACCEPT   2847 bytes
```

그것이 데이터 유출 시도였다 — HTTPS를 통해 루마니아 IP로 보내진 2.8킬로바이트. 보안 그룹이 합법적인 패키지 다운로드를 위해 HTTPS 아웃바운드를 허용했다. 공격자가 그 규칙을 사용했다.

"보안 그룹이 측면 이동을 멈췄어," Priya가 팀에게 로그를 안내하며 말했다. "하지만 아웃바운드 규칙이 너무 허용적이었어. 우리가 어떤 대상으로든 HTTPS를 허용했어. HTTPS를 알려진 AWS 엔드포인트 — CloudWatch, Secrets Manager, S3 — 와 패키지 저장소 CDN에만 허용해야 해."

그녀가 업데이트된 보안 그룹 아웃바운드 규칙을 보여줬다:

```
TCP 443 → pl-63a5400a (AWS S3 게이트웨이 엔드포인트 접두사 목록)
TCP 443 → pl-02cd2c6b (AWS CloudWatch Logs)
TCP 443 → 54.239.0.0/18 (AWS 패키지 저장소 — 시간에 따라 좁혀짐)
```

"그게 일반 HTTPS 아웃바운드 규칙을 제거해. 아웃바운드 HTTPS가 이제 알려진-좋은 대상으로만 가."

"타사 API를 호출하는 Lambda 함수는요?" Leo가 물었다.

"그것들은 자체 전용 아웃바운드 규칙을 가진 NAT 게이트웨이를 통해 가," Priya가 말했다. "Lambda는 EC2 보안 그룹을 사용하지 않아. 다른 네트워크 인터페이스, 다른 규칙 세트."

**무상태 디버깅 이야기**

사건 2주 후, Rafael — 여전히 첫 달 — 이 새 데이터 파이프라인을 설정하는 것을 돕고 있었다. 그것은 EC2에서 실행되는 내부 API를 호출해야 하는 VPC의 Lambda 함수를 포함했다.

Lambda 함수가 타임아웃됐다. 모든 호출이 타임아웃됐다.

Rafael이 보안 그룹을 확인했다. Lambda 보안 그룹에는 EC2 보안 그룹으로 TCP 8080에 대한 아웃바운드 규칙이 있었다. EC2 보안 그룹에는 Lambda 보안 그룹에서 TCP 8080에 대한 인바운드 규칙이 있었다. 규칙이 올바르게 보였다.

그가 Leo에게 돌아섰다. "보안 그룹이 괜찮아 보여요. 왜 타임아웃되죠?"

Leo가 서브넷 설정을 봤다. Lambda 함수는 프라이빗 서브넷에 있었다. 서브넷에는 Priya가 보안 강화 중 적용한 사용자 정의 NACL이 있었다.

그가 NACL 아웃바운드 규칙을 봤다:

```
규칙 100: TCP 443  → 0.0.0.0/0  ALLOW
규칙 110: TCP 5432 → 10.0.20.0/24 ALLOW
규칙 *:   All      → 0.0.0.0/0  DENY
```

"NACL이 HTTPS 아웃바운드와 PostgreSQL 아웃바운드를 허용해," Leo가 말했다. "TCP 8080 아웃바운드를 허용하지 않아."

"보안 그룹이 허용하는데요," Rafael이 말했다.

"NACL은 안 해. 그리고 NACL은 무상태야. Lambda 함수의 보안 그룹이 아웃바운드 연결을 허용하더라도, 서브넷 경계의 NACL이 여전히 아웃바운드 트래픽을 평가해. NACL이 Lambda의 호출을 서브넷을 떠나기 전에 차단하고 있어."

"하지만 NACL에 TCP 8080 아웃바운드를 ALLOW로 추가하면—"

"임시 포트 인바운드도 ALLOW를 추가해야 해," Leo가 말했다. "EC2 인스턴스로부터의 응답은 1024와 65535 사이의 무작위 포트로 돌아와. NACL의 인바운드 규칙이 그것들을 허용하지 않으면, 응답이 돌아오는 길에 차단돼."

Rafael이 NACL을 업데이트했다:

```
규칙 100:  TCP 443       → 0.0.0.0/0      ALLOW  (아웃바운드)
규칙 105:  TCP 8080      → 10.0.10.0/24   ALLOW  (EC2 서브넷으로 아웃바운드)
규칙 110:  TCP 5432      → 10.0.20.0/24   ALLOW  (DB 서브넷으로 아웃바운드)
규칙 *:    All           → 0.0.0.0/0      DENY
```

그리고 인바운드 측에서:

```
규칙 100:  TCP 1024-65535 from 10.0.10.0/24  ALLOW  (EC2에서 반환 트래픽)
규칙 *:    All                               DENY
```

Lambda 함수가 즉시 연결됐다.

"이게 사람들이 NACL을 싫어하는 이유예요," Rafael이 말했다.

"이게 네가 그것들을 이해해야 하는 이유야," Priya가 말했다. "그것들이 만드는 버그는 정확히 그것들이 방지하도록 설계된 버그야 — 예상치 못한 트래픽 흐름. 무상태 모델을 이해하는 것이 연결이 신비롭게 실패할 때 정확히 어디를 봐야 하는지 알려줘."

"보안 그룹 상태가 있는 — 반환 트래픽 자동. NACL 무상태 — 반환 트래픽이 명시적 규칙 필요," Rafael이 반복했다.

"네가 생각하는 방식의 일부가 될 때까지 말해," Priya가 말했다.

**NACL 긴급 차단: /24 규칙**

공격자의 소스 IP 범위를 식별한 후, Priya의 대응은 즉각적이었다: NACL 거부 규칙 추가.

하지만 그녀는 단일 IP만 차단하지 않았다. 공격자가 운영하는 전체 `/24` — 256개 주소 서브넷 — 을 차단했다.

"왜 전체 /24요?" Leo가 물었다.

"개별 IP 차단이 지는 게임이니까. 공격자는 범위 내의 여러 IP를 사용하고, 하나가 차단되면 그것들을 돌려가며 써. /24를 차단하는 게 더 어렵게 만들어 — 그들이 다른 주소 블록으로 이동해야 하는데, 그게 시간과 노력을 비용으로 해."

NACL 규칙:

```
규칙 90:  ALL from 185.220.101.0/24 → DENY
```

규칙 90은 어떤 허용 규칙(규칙 100에서 시작)보다 먼저 평가된다. 전체 범위가 어떤 허용 규칙이 고려되기 전에 차단된다.

"그리고 이게 서브넷의 모든 리소스에 적용돼요?" Leo가 물었다.

"모든 리소스. 그게 NACL의 요점이야 — 트래픽이 어떤 개별 리소스의 보안 그룹에 도달하기 전에 적용돼. 규칙 90의 NACL 거부는 패킷이 보안 그룹 평가에 절대 도달하지 못한다는 거야."

"이걸 보안 그룹으로 대신 할 수 있어요?"

"아니. 보안 그룹은 트래픽을 허용만 할 수 있어. 거부 규칙이 없어. 특정 IP가 서브넷의 어느 리소스에 도달하는 것을 차단하고 싶으면, NACL이 유일한 옵션이야."

이것이 NACL 거부 규칙의 주요 사용 사례다: 활성 공격에 대한 긴급 대응. 보안 그룹이 주요 제어 메커니즘이다. NACL은 비상 브레이크다.

**보안 그룹 설계 패턴: ID로 참조**

"우리 EC2 인스턴스가 교체될 때 무슨 일이 일어나는지 생각해봤어?" Priya가 물었다. "Auto Scaling이 이전 인스턴스를 종료하고 새것을 시작해. 새 인스턴스가 새 프라이빗 IP 주소를 받아."

"보안 그룹 규칙이 IP 주소를 참조하면," Leo가 천천히 말했다. "인스턴스가 교체될 때마다 규칙을 업데이트해야 하겠네요."

"정확히. 그게 인트라-VPC 트래픽에 대한 보안 그룹 규칙에서 IP 주소를 참조하지 않는 이유야."

보안 그룹은 IP 주소 대신 다른 보안 그룹을 참조할 수 있다. 규칙이 "로드 밸런서 보안 그룹에서 인바운드 허용"이라고 말하면, "로드 밸런서 보안 그룹이 연결된 모든 리소스에서 트래픽을 허용한다"를 의미한다. Auto Scaling이 각각 새 IP를 가진 천 개의 새 인스턴스를 시작할 수 있고, 규칙은 유효하게 남는다.

Nimbus 보안 그룹 구조:

```
nimbus-alb-sg (로드 밸런서)
  - 인바운드: 0.0.0.0/0에서 TCP 443
  - 인바운드: 0.0.0.0/0에서 TCP 80

nimbus-api-sg (EC2 API 인스턴스)
  - 인바운드: nimbus-alb-sg에서 TCP 8080
  - 인바운드: nimbus-bastion-sg에서 TCP 22
  - 아웃바운드: nimbus-rds-sg로 TCP 5432
  - 아웃바운드: nimbus-redis-sg로 TCP 6379

nimbus-rds-sg (RDS)
  - 인바운드: nimbus-api-sg에서 TCP 5432

nimbus-redis-sg (ElastiCache)
  - 인바운드: nimbus-api-sg에서 TCP 6379

nimbus-bastion-sg (배스천 호스트)
  - 인바운드: <사무실 VPN IP>에서 TCP 22
```

내부 트래픽에 IP 주소 없음. 보안 그룹 ID만. 인스턴스가 교체되면, 보안 그룹 멤버십이 새 인스턴스로 자동으로 전송된다.

"그리고 우리가 계획하는 마이크로서비스는요?" Rafael이 물었다. "결국 열두 개의 서비스를 가질 거예요. 각각이 일부 다른 것과 통신해야 하지만, 모든 다른 것은 아니에요."

"각 서비스가 자체 보안 그룹을 받아," Priya가 말했다. "서비스 A의 보안 그룹이 서비스 A가 호출하도록 허용된 모든 서비스의 인바운드 규칙에서 참조돼. 통신해서는 안 되는 서비스는 그냥 서로의 보안 그룹을 참조하지 않아."

이것이 마이크로서비스를 위한 **허브-앤-스포크 보안 그룹 패턴**이다. 공유 데이터베이스 보안 그룹이 다섯 개의 다른 서비스 보안 그룹에서 인바운드 규칙을 가진다. 여섯 번째 서비스가 데이터베이스 접근이 필요하면, 그것의 보안 그룹을 데이터베이스의 인바운드 규칙에 추가한다. 접근을 제거해야 하면, 참조를 제거한다. IP 관리 없음. 사용 중단된 서버를 가리키는 오래된 규칙 없음.

"보안 그룹이 신원이야," Priya가 말했다. "IP 주소는 스케줄링의 우연이야."

**최소 권한 방화벽: 규율**

"아웃바운드 규칙에 대한 올바른 자세가 무엇인지 생각해봤어?" 사건 후 검토 중 Priya가 물었다.

강화 후 Nimbus API 보안 그룹 아웃바운드 규칙:

```

TCP 443  → s3.amazonaws.com 접두사 목록    (S3 게이트웨이 엔드포인트)
TCP 443  → secretsmanager 엔드포인트       (Secrets Manager)
TCP 443  → logs 엔드포인트                  (CloudWatch Logs)
```

"모든 아웃바운드 허용" 없음. 모든 대상이 명명됨.

"이건 유지 관리가 많네요," Leo가 말했다.

## 장점과 한계

**보안 그룹**:

- 상태가 있음(임시 포트 골치 없음)
- 다른 보안 그룹 참조 가능(IP보다 더 유연)
- 허용 규칙만 — 명시적 거부 없음
- 리소스 수준에서 운영 — 세밀
- 규칙이 즉시 적용 — 순서 없음, 우선순위 없음
- 여러 보안 그룹이 하나의 리소스에 연결될 수 있음 — 모든 규칙이 결합됨

**NACL**:

- 무상태(임시 포트를 포함한 양 방향에 대한 명시적 규칙 필요)
- 명시적으로 거부 가능 — 알려진-나쁜 IP 차단에 유용
- 서브넷 수준에서 운영 — 더 광범위한 획
- 번호가 있는 규칙 순서대로 평가 — 예측 가능하지만 신중한 관리 필요
- 트래픽이 서브넷의 어느 리소스에 도달하기 전에 적용 — 첫 번째 방어선
- 전체 서브넷에 걸친 긴급 IP 차단에 효과적

**각 도구가 맞는 곳**:

기본적으로 모든 것에 보안 그룹을 사용하라. 명시적 거부 규칙이 필요할 때 NACL을 추가하라 — IP 범위 차단, 개별 리소스 설정과 무관하게 서브넷 수준에서 포트 차단, 또는 데이터 서브넷이 특정 소스에서 절대 트래픽을 받지 못하도록 시행. NACL은 보안 그룹의 대체가 아니다; 보안 그룹의 허용 전용 설계가 불충분한 상황을 위한 보충이다.

## 요약

루마니아 IP 사건은 이미 자리 잡은 보안 제어에 의해 억제됐다 — 운으로가 아니라, 설계로. 보안 그룹이 VPC 내 측면 이동을 방지했다. 사건 후, NACL이 서브넷 경계에서 공격자의 IP 범위를 명시적으로 차단하는 능력을 추가했다. VPC 흐름 로그가 공격을 보이게 만들었다. 두 도구, 두 레이어, 두 다른 일 — 무슨 일이 일어났는지 증명하는 로깅과 함께.

- **보안 그룹**은 개별 리소스를 위한 상태가 있는 가상 방화벽이다. 허용 규칙만. 모든 규칙이 동시에 평가됨.
- **NACL**은 전체 서브넷을 위한 무상태 방화벽이다. 허용 및 거부 규칙. 번호 순서대로 규칙 평가 — 첫 번째 일치가 이긴다.
- **상태가 있는**은 응답 트래픽이 자동으로 허용된다는 것을 의미한다. **무상태**는 임시 반환 포트를 포함한 양 방향 트래픽을 명시적으로 허용해야 한다는 것을 의미한다.
- 보안 그룹이 주요 접근 제어 레이어다. NACL은 서브넷 수준 재정의다 — 특히 긴급 차단을 위한.
- NACL이 인바운드 트래픽을 허용할 때, TCP 응답이 통과하도록 아웃바운드 임시 포트(1024-65535)도 허용해야 한다.
- 인트라-VPC 트래픽에는 IP 주소가 아닌 **ID로 보안 그룹을 참조하라**. Auto Scaling이 인스턴스를 교체한다; 보안 그룹 멤버십이 자동으로 전송된다.
- EC2 인스턴스의 **특정 아웃바운드 규칙**은 침해된 인스턴스가 할 수 있는 것을 제한한다 — 최소 권한 방화벽.
- 보안 그룹과 NACL이 실제로 무엇을 하는지 보기 위해 흐름 로그를 사용하라. 규칙은 이론이다. 로그는 증거다.

## 시험 팁

*SAA-C03 도메인: 보안 아키텍처 설계(도메인 1, 태스크 1.2)*

- **상태가 있는 vs. 무상태**: 이 구분이 이 챕터에서 가장 많이 테스트되는 개념이다. 보안 그룹 = 상태가 있는 = 응답 자동 허용. NACL = 무상태 = 명시적으로 응답 트래픽 허용 필요.
- **보안 그룹 규칙**: 명시적 거부 없음. 인스턴스에 여러 보안 그룹이 연결되면, 모든 규칙의 합집합이 적용된다. 모든 일치하는 규칙이 동시에 평가됨.
- **NACL 규칙 순서**: 규칙은 가장 낮은 번호에서 가장 높은 번호로 평가된다. 규칙 100이 200보다 먼저. 첫 번째 일치가 이긴다. 맨 아래의 `*`(별표) 규칙이 암묵적 거부다. 규칙 90에 거부 규칙을 추가하면 규칙 100의 어떤 허용 규칙보다 먼저 차단한다.
- **임시 포트**: 고전적인 NACL 실수는 아웃바운드 포트 1024-65535를 허용하는 것을 잊는 것이다. NACL이 인바운드 HTTP(포트 80)를 허용하지만 아웃바운드 임시 포트를 허용하지 않으면, 사용자는 요청을 보낼 수 있지만 응답을 절대 받을 수 없다. 이것이 가장 흔한 NACL 시험 시나리오다.
- **보안 그룹 참조**: 다른 보안 그룹(IP만이 아닌)에서 트래픽을 허용할 수 있다. 인트라-VPC 트래픽에 권장되는 패턴이다. 시험은 EC2 접근을 제한하는 올바른 답으로 "ALB 보안 그룹에서 인바운드 허용"을 자주 사용한다.
- **기본 NACL vs. 사용자 정의 NACL**: 기본 NACL은 모든 트래픽을 허용한다. (만드는) 사용자 정의 NACL은 기본적으로 모든 트래픽을 거부한다. 시험 시나리오: "새 NACL을 만들었는데 이제 트래픽이 차단됨" → 허용 규칙 누락을 확인하라.
- **공격자의 IP 차단**: 보안 그룹은 특정 IP를 차단할 수 없다(허용만). NACL은 특정 IP나 CIDR을 명시적으로 거부할 수 있다. 시험 시나리오: "특정 IP가 서브넷의 어느 리소스에 도달하는 것을 차단" → NACL 거부 규칙.
- **연결 실패 디버깅**: 순서를 확인하라: 소스의 보안 그룹(아웃바운드) → 대상의 보안 그룹(인바운드) → 소스 서브넷의 NACL(아웃바운드 + 임시 포트) → 대상 서브넷의 NACL(인바운드). 대부분의 시험 연결 실패는 누락된 NACL 아웃바운드 규칙이나 누락된 임시 포트 허용으로 인한 것이다.
- **여러 서브넷과 NACL**: 하나의 NACL이 그것과 연결된 모든 서브넷에 적용된다. 하나의 서브넷은 하나의 NACL과만 연결될 수 있다. 시험은 특정 서브넷의 트래픽이 영향받을 때 어떤 NACL을 업데이트할지 물을 수 있다.

## 연습 문제

**연습 1 — 회상**

개발자가 포트 443에서 트래픽을 허용하는 인바운드 규칙을 보안 그룹에 추가했다. 서버의 응답을 허용하는 아웃바운드 규칙도 추가해야 하는가? 왜 또는 왜 아닌가?

대신 NACL에 포트 443에서 트래픽을 허용하는 인바운드 규칙을 추가하면, 아웃바운드 규칙을 추가해야 하는가? 왜 또는 왜 아닌가?

**힌트**: 챕터의 비유를 되돌아보라 — 각각이 당신을 들여보낸 것을 기억하는 보안 경비인가, 아니면 나가는 길에 다시 통과해야 하는 금속 탐지기인가?

**연습 2 — SAA-C03 시나리오**

*시나리오*: 회사가 공개 서브넷의 EC2 인스턴스에서 웹 애플리케이션을 실행한다. 애플리케이션은 인터넷에서 HTTPS 트래픽(포트 443)을 수락한다. 사용자가 애플리케이션에 연결할 수 있지만 응답을 받을 수 없다고 보고한다 — 요청이 멈추고 타임아웃된다.

EC2 보안 그룹에는 0.0.0.0/0에서 TCP 443을 허용하는 인바운드 규칙이 있다. 서브넷의 NACL에는 0.0.0.0/0에서 TCP 443을 허용하는 인바운드 규칙(규칙 100)과 0.0.0.0/0으로 TCP 443을 허용하는 아웃바운드 규칙(규칙 100)이 있다.

문제의 가장 가능성 있는 원인은 무엇인가?

A) 보안 그룹에 TCP 443에 대한 아웃바운드 규칙이 없다  
B) EC2 인스턴스에 Elastic IP 주소가 없다  
C) 보안 그룹에 임시 포트에 대한 인바운드 규칙이 없다  
D) NACL에 임시 포트(1024-65535)를 허용하는 아웃바운드 규칙이 없다

**힌트 1**: 보안 그룹은 상태가 있다 — 응답을 자동으로 허용한다. NACL은 무상태다 — 허용하지 않는다.

**힌트 2**: 브라우저가 포트 443의 웹 서버에 연결될 때, 서버의 응답은 포트 443이 아닌 무작위 임시 포트(1024-65535)로 여행한다.

**힌트 3**: NACL에는 443을 위한 아웃바운드 규칙이 있지만, 응답은 포트 443으로 가지 않는다.

**정답**: D

**설명**: NACL은 무상태다. 사용자가 포트 443의 서버에 연결할 때, 서버의 TCP 응답은 임시 포트(1024-65535에서 무작위로 선택)로 여행한다. NACL 아웃바운드 규칙은 포트 443만 허용하므로, 응답은 기본 거부 규칙에 의해 차단된다. TCP 1024-65535를 허용하는 아웃바운드 NACL 규칙을 추가하면 수정된다.

**왜 A가 아닌가?** 보안 그룹은 상태가 있다 — 응답 트래픽은 아웃바운드 규칙에 관계없이 자동으로 허용된다. 아웃바운드 보안 그룹 규칙이 필요하지 않다.

**왜 B가 아닌가?** Elastic IP는 인스턴스가 공개 IP를 갖는지 여부에 영향을 미치지, 수립된 연결이 응답을 받을 수 있는지 여부에 영향을 미치지 않는다.

**왜 C가 아닌가?** 임시 포트는 아웃바운드 응답 트래픽을 위한 것이지, 인바운드가 아니다. 사용자로부터의 인바운드 연결은 이미 허용된 포트 443으로 들어온다.

*SAA-C03 도메인: 보안 아키텍처 설계 — 태스크 1.2*
