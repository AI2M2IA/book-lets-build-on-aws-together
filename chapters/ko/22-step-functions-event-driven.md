# 22장: 스스로 실행되는 순서도

Nimbus의 주문 확인에는 순서대로 다섯 가지가 일어나야 했다: 카드 청구, 확인 이메일 전송, 레스토랑 알림, 인벤토리 업데이트, 회계를 위한 거래 기록. 3단계가 실패하면 — 레스토랑 알림이 타임아웃되면 — 1단계와 2단계는 이미 일어났다. 고객은 청구되었다. 이메일이 발송됐다. 하지만 레스토랑은 주문이 존재한다는 것을 몰랐다.

Leo는 이 버그의 카테고리에 이름이 있었다: 부분적 성공. "모든 것이 작동했어," 그가 말했다. "중요한 부분을 제외하고."

"지난 2주에 이런 일이 몇 번 있었어요?" Maya가 물었다.

"11번. 우리가 대부분을 레스토랑에 화난 전화를 통해 발견했어. 두 개는 로그에서 사후에 발견했어."

"그러면 우리는 조율이 없어," Priya가 말했다. "다섯 단계가 순서가 보장 없이 스크립트로 실행되고 있어."

"또는 모두 완료됐다는 것을."

"또는 어느 것이 실패했는지 우리가 알 수 있다는 것도."

Leo가 프로젝터에 코드를 열었다. 50줄짜리 Python 함수였다: 다섯 개의 순차적인 API 호출, 전체 주변에 하나의 try/except 블록. "여기서 무언가가 예외를 발생시키면, 500을 받고 고객은 오류를 본다. 하지만 청구와 이메일은 롤백되지 않아."

"워크플로우가 필요해요," Maya가 말했다. "각 단계를 추적하는 것."

**AWS Step Functions: 워크플로우 오케스트레이션**

**AWS Step Functions**는 애플리케이션의 단계를 시각적 워크플로우로 조율하는 서버리스 오케스트레이션 서비스다. 각 단계는 **상태 머신**의 **상태**다.

아래로 실행되다가 충돌하는 Python 스크립트 대신, 워크플로우를 JSON/YAML 상태 머신으로 정의한다:

```json
{
  "StartAt": "ValidateLicense",
  "States": {
    "ValidateLicense": {
      "Type": "Task",
      "Resource": "arn:aws:lambda:us-east-1:123456789012:function:validate-license",
      "Next": "ImportMenu",
      "Catch": [{"ErrorEquals": ["*"], "Next": "OnboardingFailed"}]
    },
    "ImportMenu": {
      "Type": "Task",
      "Resource": "arn:aws:lambda:us-east-1:123456789012:function:import-menu",
      "Next": "SetupPayments",
      "Retry": [{"ErrorEquals": ["*"], "MaxAttempts": 3, "IntervalSeconds": 5}]
    },
    ...
  }
}
```

각 상태는 다음을 할 수 있다:

- **Lambda 함수 실행**(가장 흔한 패턴)
- **ECS 작업 실행**(더 장기 실행 작업을 위해)
- **특정 시간** 또는 **이벤트 대기**(외부에서 무언가가 일어날 때까지 워크플로우 일시 정지)
- **조건에 따라 경로 선택**(if/else 로직)
- **병렬 브랜치 실행**(동시에)
- **실패 시 재시도**(설정 가능한 백오프)
- **오류 잡기**(오류 처리 상태로 라우팅)

Step Functions가 실행 상태를 내구성 있게 관리한다. 3단계가 실패하면, 실행이 3단계에서 일시 정지된다. 콘솔에서 실패한 실행을 검사하고, 문제를 수정하고, 3단계에서 다시 시작할 수 있다 — 1단계와 2단계를 반복하지 않고.

**상태 유형: 구성 요소**

**Task**: 액션 실행 — Lambda 함수 호출, ECS 작업 시작, API 호출. 여기서 실제 작업이 일어난다.

**Choice**: 입력 데이터의 조건에 따라 분기. 코드의 if/else처럼.

**Parallel**: 여러 브랜치를 동시에 실행하고 모두 완료될 때까지 기다린다.

**Map**: 목록의 각 항목에 상태 세트를 적용한다. 50개의 레스토랑 메뉴 항목을 병렬로 처리한다.

**Wait**: 지정된 시간 또는 타임스탬프까지 일시 정지한다. 예약된 지연에 유용하다.

**Pass**: 작업 없이 입력을 출력으로 전달한다. 데이터 변환 및 테스트에 사용된다.

**Succeed/Fail**: 실행을 종료하는 터미널 상태.

레스토랑 온보딩을 위해, Leo가 워크플로우를 설계했다:

1. ValidateLicense (Task → Lambda)
2. ImportMenu (Task → Lambda, 3번 재시도)
3. 병렬 브랜치:
   a. SetupPayments (Task → Lambda)
   b. CreateIAMRole (Task → Lambda)
4. SendWelcomeEmail (Task → Lambda, 병렬 완료 대기)
5. NotifySalesTeam (Task → Lambda)

3a와 3b 단계는 병렬로 실행된다 — 서로 의존하지 않고, 동시에 실행하면 시간이 절약된다.

**Standard vs. Express 워크플로우**

Step Functions는 두 가지 워크플로우 유형을 제공한다:

**Standard 워크플로우**:

- 최대 기간: 1년
- 실행이 내구성이 있다 — 상태가 영속되며, 검사하고 감사할 수 있다
- 최소 한 번 실행(각 작업이 최소 한 번 실행된다)
- 상태 전환당 가격
- 장기 실행, 중요한 워크플로우에 가장 적합(주문 처리, 온보딩, 결제 흐름)

**Express 워크플로우**:

- 최대 기간: 5분
- 더 높은 처리량 — 초당 최대 100,000
- 최소 한 번 또는 최대 한 번(설정 가능)
- 기간당 가격(Lambda처럼)
- 높은 볼륨, 짧은 기간 워크플로우에 가장 적합(실시간 이벤트 처리, IoT 데이터 수집)

Nimbus의 레스토랑 온보딩: Standard(중요하고, 내구성이 있으며, 수동 단계가 포함되면 시간이 걸릴 수 있다).

Nimbus의 실시간 주문 상태 업데이트: Express(높은 볼륨, 짧은 기간, 덜 중요).

**이벤트 기반 아키텍처: 더 큰 그림**

Step Functions는 더 큰 패턴의 한 부분이다: **이벤트 기반 아키텍처**. 서비스가 서로 직접 호출하는(강한 결합) 대신, 서비스가 이벤트를 발산하고 다른 서비스가 그 이벤트에 반응한다.

이 책 전체에서 이것을 봤다:

- 주문 들어옴 → SNS가 이벤트 발행 → SQS 큐가 소비자에게 배달
- S3 파일 업로드됨 → Lambda 처리를 위해 트리거됨
- DynamoDB 레코드 변경됨 → DynamoDB Streams → Lambda가 캐시 업데이트

**Amazon EventBridge**(이전 CloudWatch Events)는 이 패턴을 위한 고급 이벤트 버스다. 규칙에 따라 AWS 서비스와 자체 애플리케이션의 이벤트를 타겟(Lambda, SQS, Step Functions 등)으로 라우팅한다.

EventBridge는 아키텍처 수준에서 느슨한 결합을 허용한다: 주문 서비스가 `order.placed` 이벤트를 누가 듣고 있는지 모르고 발행한다. 분석 서비스, 알림 서비스, 로열티 포인트 서비스가 모두 독립적으로 듣는다. 새 리스너를 추가해도 주문 서비스를 바꿀 필요가 없다.

**Step Functions가 올바른 도구인 경우**

Step Functions는 다음이 있을 때 탁월하다:

**단계 전체에 걸쳐 진행을 추적해야 하는 다중 단계 워크플로우**

**루프 내 사람 프로세스** — Step Functions는 외부 이벤트(사람이 무언가를 승인하는 것처럼)를 무기한 기다렸다가 계속할 수 있다

**대규모 오류 처리** — 많은 단계에 걸쳐 내장된 재시도, 잡기, 폴백 로직

**감사 가능한 프로세스** — 모든 실행이 모든 상태 전환을 기록한다. 무엇이 언제 일어났는지 정확히 볼 수 있다

**복잡한 병렬 또는 순차 로직** — 시각적 워크플로우가 동등한 코드보다 추론하기 쉽다

Step Functions는 간단한 두 단계 프로세스에는 과잉이다. 조율 자체가 가치 있고 실패 시나리오가 중요할 때 사용하라.

## 장점과 한계

**Step Functions가 강력한 이유**:

- 시각적 실행 내역 — 워크플로우가 어디에 있는지(또는 실패했는지) 정확히 볼 수 있다
- 내장 재시도 및 오류 처리 — 사용자 정의 재시도 코드 없음
- 내구성 있는 상태 — 실행이 서비스 재시작 및 중단에서 살아남는다
- 200개 이상의 AWS 서비스와 직접 통합(Lambda만이 아닌)
- 시각적 워크플로우가 자기 문서화

**복잡해지는 부분**:

- Standard 워크플로우는 상태 전환당 가격이 매겨진다 — 많은 상태를 가진 복잡한 워크플로우가 대규모에서 비쌀 수 있다
- ASL(Amazon States Language) JSON 형식에는 학습 곡선이 있다
- 최대 페이로드 크기는 256KB — 대용량 데이터는 직접 워크플로우를 통해서가 아닌 S3 참조를 통해 전달해야 한다
- 많은 수동 단계가 있는 장기 실행 워크플로우는 신중한 타임아웃 설정이 필요하다

## 요약

- **Step Functions**는 다중 단계 워크플로우를 상태 머신으로 오케스트레이션한다.
- 각 **상태**는 Lambda 함수를 실행하고, ECS 작업을 실행하고, 기다리거나, 분기하거나, 병렬 단계를 실행할 수 있다.
- **재시도 및 잡기**는 각 상태에 내장되어 있다 — 사용자 정의 재시도 코드 없음.
- **Standard 워크플로우**: 장기 실행(최대 1년), 내구성 있음, 최소 한 번. 중요한 비즈니스 프로세스를 위해.
- **Express 워크플로우**: 짧은 기간(최대 5분), 높은 처리량. 높은 볼륨 이벤트 처리를 위해.
- **이벤트 기반 아키텍처**는 SNS, SQS, Lambda, EventBridge 같은 서비스를 사용하여 직접 호출 대신 이벤트 주변으로 시스템을 분리한다.
- 조율 자체가 복잡하고 감사 가능성이 중요할 때 Step Functions를 사용하라.

## 시험 팁

*SAA-C03 도메인: 탄력적 아키텍처 설계(도메인 2, 태스크 2.1)*

- **Step Functions 사용 사례 신호**: "여러 Lambda 함수 오케스트레이션," "재시도 및 오류 처리가 있는 워크플로우," "자동화된 워크플로우의 사람 승인 단계," "각 워크플로우 단계의 감사 추적" → Step Functions.
- **Standard vs. Express**: 장기 실행, 감사 가능, 비즈니스 중요 워크플로우에는 Standard. 높은 처리량, 짧은 기간 이벤트 처리에는 Express.
- **SQS vs. Step Functions**: 단순한 작업 큐(생산자/소비자)에는 SQS. 복잡한 로직, 재시도, 상태 추적이 있는 다중 단계 워크플로우에는 Step Functions.
- **EventBridge 신호**: "AWS 서비스에서 타겟으로 이벤트 라우팅," "서비스 간 이벤트 기반 통합," "Lambda 함수 스케줄링" → EventBridge(이전 CloudWatch Events).
- **콜백 패턴**: Step Functions는 실행을 일시 정지하고 외부 콜백(작업 토큰)을 기다릴 수 있다. 완료되면 작업자가 콜백한다. Lambda의 15분 제한이 필요하지 않은 장기 실행 ECS 작업에 유용하다.
- **직접 SDK 통합**: Step Functions는 Lambda를 통하지 않고 AWS 서비스(DynamoDB, S3, SQS 등)를 직접 호출할 수 있다. 단순한 서비스 호출을 위한 비용과 지연을 줄인다.

## 연습 문제

**연습 1 — 회상**

Step Functions가 다중 단계 워크플로우에 왜 유용한지 설명하라. 단순히 다른 Lambda 함수를 호출하는 Lambda 함수와 비교하여 무엇을 제공하는가?

*(힌트: 두 접근 방식에서 5단계 중 3단계가 실패할 때 어떤 일이 일어나는지 생각해보라. 무엇이 일어났는지 어떻게 알 수 있는가? 3단계만 재시도하려면 어떻게 해야 하는가?)*

**연습 2 — 시험 연습**

*시나리오*: 금융 서비스 회사가 여러 단계로 대출 신청을 처리한다: 신용 확인, 소득 확인, 문서 유효성 검사, 심사자 검토(수동), 결정 알림. 각 단계는 초(신용 확인)에서 며칠(심사자 검토)까지 걸릴 수 있다. 회사는 컴플라이언스를 위해 모든 단계의 전체 감사 추적이 필요하다. 실패한 자동화 단계는 자동으로 재시도해야 하고; 수동 단계는 사람의 결정을 기다리며 일시 정지해야 한다.

이 요구사항을 가장 잘 충족하는 서비스는?

A) 각 단계 사이에 SQS 큐가 있는 Lambda 함수로 체인  
B) 심사자 검토 단계를 위한 Wait for callback 패턴이 있는 AWS Step Functions Standard 워크플로우  
C) 자동화된 단계를 위한 AWS Step Functions Express 워크플로우와 수동 단계를 위한 SQS FIFO  
D) 각 단계를 위한 Lambda 함수로 이벤트 규칙을 라우팅하는 Amazon EventBridge

**힌트 1**: "며칠까지" 기간 — 어떤 Step Functions 유형이 이것을 지원하는가?

**힌트 2**: "사람의 결정을 기다린다" — 어떤 Step Functions 패턴이 이를 위해 설계됐는가?

**힌트 3**: "컴플라이언스를 위한 전체 감사 추적" — 어떤 서비스가 호출당 상태 내역을 제공하는가?

**답**: B

**설명**: Step Functions Standard 워크플로우는 최대 1년 실행할 수 있어, 며칠 걸리는 심사자 검토 단계를 지원한다. Wait for callback 패턴은 작업 토큰으로 심사자 단계에서 실행을 일시 정지한다; 심사자가 결정을 내리면, 토큰으로 콜백하여 워크플로우를 계속한다. Standard 워크플로우는 모든 상태 전환을 기록한다 — 컴플라이언스를 위한 전체 감사 추적.

**왜 A가 아닌가?** SQS를 통해 체인된 Lambda는 내장된 상태 추적이나 감사 추적을 제공하지 않는다. 실패한 단계는 사용자 정의 재시도 로직이 필요하다. 특정 실패한 단계에서 재시작하는 것은 사용자 정의 구현이 필요하다.

**왜 C가 아닌가?** Express 워크플로우는 최대 5분 기간이 있다 — 며칠 걸릴 수 있는 단계와 호환되지 않는다.

**왜 D가 아닌가?** EventBridge는 서비스 사이에 이벤트를 라우팅하지만 워크플로우 상태를 유지하거나 내장된 재시도/감사를 제공하지 않는다. 이것만으로 구축하려면 사용자 정의 상태 관리가 필요하다.

*SAA-C03 도메인: 탄력적 아키텍처 설계 — 태스크 2.1*

**연습 3 — 아키텍처 과제** *(선택 사항)*

Nimbus는 음식 품질 분쟁 해결 프로세스를 구축하고 있다. 고객이 나쁜 경험을 보고할 때:

1. 보고서가 자동으로 유효성 검사된다(주문이 존재하는지, 최근 것인지 확인)
2. 레스토랑이 자동으로 알림을 받는다
3. Nimbus 지원 에이전트가 불만을 검토한다(수동 단계 — 1-3 영업일 걸릴 수 있다)
4. 에이전트의 결정에 따라: 환불 발행(Lambda → 결제 프로세서) OR 사과 쿠폰 전송(Lambda → 쿠폰 서비스) OR 관리자에게 에스컬레이션(Step Functions 하위 워크플로우)
5. 고객이 결과 알림을 받는다

이것을 Step Functions 워크플로우로 설계하라. 각 단계를 처리하는 상태 유형은 무엇인가? 1-3일 대기를 어떻게 처리하겠는가? 4단계의 분기를 어떻게 모델링하겠는가?

*(단 하나의 정답은 없다. Step Functions 상태 설계를 연습하는 것이 목표다.)*

## 포스트 크레딧 장면

레스토랑 온보딩 워크플로우가 라이브였다.

다음 달에, 12개의 새 레스토랑 파트너가 온보딩했다. 두 개에서 결제 처리 단계(3단계)에서 실패했다. 두 경우 모두, Step Functions가 정확한 오류를 캡처하고, 실행 상태를 저장하고, Nimbus 팀에 알림을 보냈다.

Leo가 근본 원인(결제 공급자의 잘못 설정된 API 키)을 수정하고 두 실행을 3단계에서 재시도했다. 실행이 각각 23초 안에 완료되어 실패한 정확한 위치에서 다시 시작됐다.

어떤 레스토랑도 다시 임포트할 필요가 없었다. IAM 역할이 두 번 생성되지 않았다. 중복 환영 이메일이 발송되지 않았다.

"Step Functions 이전에는," Leo가 Maya에게 말했다. "각 레스토랑에 대해 무엇이 완료됐고 완료되지 않았는지 수동으로 추적하고, 누락된 단계를 수동으로 다시 실행해야 했을 거야."

"그리고 이제?"

"콘솔에서 재시도를 클릭한다. 시스템이 무엇이 완료됐는지 안다."

Maya가 이것에 대해 생각했다.

"그건 단순히 기술적 향상이 아니야," 그녀가 말했다. "그건 확장되는 프로세스와 그렇지 않는 것의 차이야."
