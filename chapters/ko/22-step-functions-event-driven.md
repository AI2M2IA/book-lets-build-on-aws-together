# 22장: 스스로 실행되는 순서도

Leo는 한 시간 동안 같은 로그 파일을 응시하고 있었습니다. 스택 추적은 개별적으로는 충분히 명확했지만, 그것들에 걸친 패턴 — 한 단계가 조용히 실패하고 다음 단계가 어쨌든 실행되는 방식 — 은 그가 보는 데 잠시 걸렸습니다. 그가 마침내 뒤로 기대고, 커피를 내려놓고, 메모장에 한 단어를 썼습니다: *조율*.

공연 도중에 지휘대에서 내려오는 지휘자를 상상해보십시오. 오케스트라는 계속 연주합니다 — 하지만 47마디에서 금관악기를 들여올 사람이 없고, 피날레 전의 침묵을 큐로 신호할 사람이 없습니다. 개별 연주자는 자신의 파트를 올바르게 연주합니다. 공연은 여전히 무너집니다. 파트들이 아무도 관리하지 않는 조율에 의존하기 때문입니다.

그것이 Leo가 주문 확인 코드에서 발견한 문제였습니다. 개별 단계의 버그가 아닙니다. 조율 실패입니다.

---

컨테이너는 올바르게 실행되고 깔끔하게 배포되고 있었습니다. ECS 배포 파이프라인은 탄탄했습니다. 하지만 애플리케이션 코드 내부에는, 몇 주 동안 다른 종류의 실패가 쌓이고 있었습니다. 컨테이너는 괜찮았습니다. 그중 하나 안의 로직은 그렇지 않았습니다.

Leo는 로그에서 그 패턴을 추적해 왔지만 발생 횟수를 셀 때까지는 그것을 이해하지 못했습니다.

11번. 2주 동안에요.

---

Nimbus의 주문 확인에는 다섯 가지가 순서대로 일어나야 했습니다: 카드 청구, 확인 이메일 전송, 레스토랑 알림, 인벤토리 업데이트, 회계를 위한 거래 기록.

Leo가 원래의 주문 확인 함수를 작성했을 때, 그는 전체를 하나의 `try/except` 블록으로 감싸고 "괜찮을 거예요 — 로그에서 오류를 잡을게요"라고 말했습니다. 그게 8개월 전이었습니다.

괜찮지 않았습니다.

3단계가 실패하면 — 레스토랑 알림이 타임아웃되면 — 1단계와 2단계는 이미 일어났습니다. 고객이 청구되었습니다. 이메일이 전송되었습니다. 하지만 레스토랑은 주문이 존재한다는 것을 몰랐습니다.

Leo는 이 범주의 버그에 이름이 있었습니다: 부분적 성공. "모든 게 작동했어요," 그가 말했습니다. "중요했던 부분만 빼고요."

"이런 일이 몇 번이나 일어났어요?" Maya가 물었습니다.

"지난 2주 동안 11번이요. 우리가 대부분을 레스토랑으로 온 화난 전화에서 잡았어요. 두 개는 사후에 로그에서 찾았어요."

"그러니까 우리는 조율이 없어요," Priya가 말했습니다. "다섯 단계가, 스크립트로 실행되면서, 그것들이 모두 완료된다는 보장이 없어요. 그리고 누군가 2단계 동안 침입을 시도하면 어떻게 되죠 — 청구가 통과한 후 레스토랑이 알림을 받기 전에요? 우리는 이미 레스토랑이 가지고 있지 않은 주문에 대해 고객에게 청구했어요."

"또는 그것들이 올바른 순서로 완료된다는 것도요."

"또는 우리가 어느 것이 실패했는지 안다는 것도요."

Leo가 프로젝터에 코드를 불러왔습니다. 그것은 Python 함수였습니다: 50줄, 다섯 개의 순차적 API 호출, 전체를 둘러싼 하나의 try/except 블록.

"우리는 워크플로가 필요해요," Maya가 말했습니다. "각 단계를 추적하는 무언가요. 잠깐 — 그런데 *왜* 그냥 기존 Python 함수에 더 나은 오류 처리를 추가할 수 없죠? 왜 완전히 새로운 서비스가 필요하죠?"

"왜냐하면 더 나은 오류 처리도 어느 지점에서든 실패할 수 있는 단일 프로세스에서 실행되기 때문이에요," Leo가 말했습니다. "서버가 실행 도중에 재시작하면, 오류 처리도 그것과 함께 재시작해요. Step Functions는 상태를 외부에 영속화해요."

제조 체크리스트를 생각해보십시오 — 각 작업대가 다음으로 넘기기 전에 완료를 확인하고, 무언가가 실패하면 전체 라인이 그 위치를 유지하는 것. 라인이 처음부터 재시작하지 않습니다. 그것은 실패한 정확한 작업대에서 재개합니다. 그 작업대의 상태가 기록됩니다. 그 이전의 단계들은 완료되었고 반복되지 않습니다. 그 이후의 단계들은 문제가 해결될 때까지 기다립니다.

그것이 주문 확인 흐름이 필요로 했던 것입니다. 문제 주위의 더 많은 코드가 아닙니다. 문제를 관리하도록 설계된 시스템입니다.

**AWS Step Functions: 워크플로 오케스트레이션**

**AWS Step Functions**는 애플리케이션의 단계들을 시각적 워크플로로 조율하는 서버리스 오케스트레이션 서비스입니다. 각 단계는 **상태 머신(state machine)**의 **상태(state)**입니다.

위에서 아래로 실행되다가 충돌하는 Python 스크립트 대신, 워크플로를 JSON/YAML 상태 머신으로 정의합니다:

```json
{
  "StartAt": "ValidateLicense",
  "States": {
    "ValidateLicense": {
      "Type": "Task",
      "Resource": "arn:aws:lambda:us-west-2:123456789012:function:validate-license",
      "Next": "ImportMenu",
      "Catch": [{"ErrorEquals": ["States.ALL"], "Next": "OnboardingFailed"}]
    },
    "ImportMenu": {
      "Type": "Task",
      "Resource": "arn:aws:lambda:us-west-2:123456789012:function:import-menu",
      "Next": "SetupPayments",
      "Retry": [{"ErrorEquals": ["States.ALL"], "MaxAttempts": 3, "IntervalSeconds": 5}]
    },
    ...
  }
}
```

각 상태는 다음을 할 수 있습니다:

- **Lambda 함수 실행**(가장 흔한 패턴)
- **ECS 태스크 실행**(더 오래 실행되는 작업용)
- 특정 **시간** 또는 **이벤트**를 기다림(외부에서 무언가가 일어날 때까지 워크플로 일시 중지)
- 조건에 기반해 **경로 선택**(if/else 로직)
- **병렬 분기**를 동시에 실행
- 구성 가능한 백오프로 **실패 시 재시도**
- **오류를 잡아** 오류 처리 상태로 라우팅

Step Functions는 실행 상태를 내구성 있게 관리합니다. 3단계가 실패하면, 실행이 3단계에서 일시 중지됩니다. 콘솔에서 실패한 실행을 검사하고, 문제를 고치고, 3단계부터 재시작할 수 있습니다 — 1단계와 2단계를 반복하지 않고요.

여러분은 궁금해할지 모릅니다: Lambda 함수에 그냥 재시도 로직을 작성할 수 없나요? 그럴 수 있습니다 — 하지만 그러면 실패 추적, 상태 영속화, 감사 로깅도 코드로 작성하게 됩니다. 그리고 7단계 중 3단계가 실패하면, 어떤 레스토랑이 처리되고 있었는지, 그 전에 무엇이 일어났는지, 어디서 재개할지 알아야 합니다. Step Functions가 그 모든 것을 합니다.

**Nimbus 주문 흐름: 주석이 달린 상태 머신**

여기 Nimbus가 주문 확인을 위해 구축한 실제 Step Functions 상태 머신의 단순화된 버전이 있습니다 — 각 부분이 무엇을 하는지 볼 수 있도록 주석이 달려 있습니다:

```json
{
  "Comment": "Nimbus order confirmation workflow",
  "StartAt": "ChargeCard",
  "States": {
    "ChargeCard": {
      "Type": "Task",
      "Resource": "arn:aws:lambda:us-west-2:123456789012:function:charge-card",
      "Next": "SendConfirmationEmail",
      "Retry": [
        {
          "ErrorEquals": ["PaymentRetryableError"],
          "MaxAttempts": 2,
          "IntervalSeconds": 3,
          "BackoffRate": 2.0
        }
      ],
      "Catch": [
        {
          "ErrorEquals": ["PaymentDeclinedError"],
          "Next": "NotifyCustomerOfDecline"
        },
        {
          "ErrorEquals": ["States.ALL"],
          "Next": "ChargeCardFailed"
        }
      ]
    },
    "SendConfirmationEmail": {
      "Type": "Task",
      "Resource": "arn:aws:lambda:us-west-2:123456789012:function:send-confirmation-email",
      "Next": "NotifyRestaurant",
      "Retry": [
        {
          "ErrorEquals": ["States.ALL"],
          "MaxAttempts": 3,
          "IntervalSeconds": 5
        }
      ]
    },
    "NotifyRestaurant": {
      "Type": "Task",
      "Resource": "arn:aws:lambda:us-west-2:123456789012:function:notify-restaurant",
      "Next": "UpdateInventory",
      "Retry": [
        {
          "ErrorEquals": ["States.ALL"],
          "MaxAttempts": 3,
          "IntervalSeconds": 10,
          "BackoffRate": 2.0
        }
      ],
      "Catch": [
        {
          "ErrorEquals": ["States.ALL"],
          "Next": "RestaurantNotificationFailed"
        }
      ]
    },
    "UpdateInventory": {
      "Type": "Task",
      "Resource": "arn:aws:lambda:us-west-2:123456789012:function:update-inventory",
      "Next": "LogTransaction",
      "Retry": [{"ErrorEquals": ["States.ALL"], "MaxAttempts": 2}]
    },
    "LogTransaction": {
      "Type": "Task",
      "Resource": "arn:aws:lambda:us-west-2:123456789012:function:log-transaction",
      "End": true
    },
    "NotifyCustomerOfDecline": {
      "Type": "Task",
      "Resource": "arn:aws:lambda:us-west-2:123456789012:function:notify-decline",
      "End": true
    },
    "ChargeCardFailed": {
      "Type": "Fail",
      "Error": "ChargeCardFailed",
      "Cause": "Card charge failed after retries"
    },
    "RestaurantNotificationFailed": {
      "Type": "Task",
      "Resource": "arn:aws:lambda:us-west-2:123456789012:function:alert-support",
      "Comment": "Alert support team — order charged but restaurant not notified",
      "End": true
    }
  }
}
```

주목할 몇 가지:

**`ChargeCard`에는 두 개의 Catch 절이 있습니다.** 하나는 `PaymentDeclinedError`(알려진, 예상된 실패 — 카드가 거절되었지, 시스템 오류가 아님)용이고 하나는 `States.ALL`(다른 모든 것 — 시스템 중단, 타임아웃, 예상치 못한 예외)용입니다. 그것들은 다른 것을 의미하기 때문에 다른 상태로 라우팅됩니다.

**`NotifyRestaurant`에는 `RestaurantNotificationFailed`로 라우팅되는 Catch가 있습니다.** 이것이 11건의 사건을 일으킨 버그입니다. 옛날 Python 스크립트에는, 동등한 것이 없었습니다 — 알림이 실패하면, 함수가 조용히 충돌하거나 오류를 로그하고 계속했습니다. Step Functions는 실패 경로를 명시적으로 만듭니다: 그것은 특정한 어딘가로 가고, 그 어딘가가 누군가 전화를 해야 하기 전에 지원 팀에 알립니다.

**모든 Task에 Retry가 있습니다.** 이메일 서비스에 일시적 타임아웃이 있으면, 그것은 증가하는 백오프로, 세 번, 자동으로 재시도합니다. 고객은 이것을 결코 보지 못합니다. 주문은 손실되지 않습니다.

**흐름은 스크립트가 아니라 그래프입니다.** `NotifyRestaurant`가 영구적으로 실패하면(재시도 후), 실행이 `UpdateInventory`로 계속되지 않습니다. 워크플로가 `RestaurantNotificationFailed`에서 멈춥니다. 주문에 대해 모르는 레스토랑에 대해 인벤토리가 업데이트되지 않습니다. 이것이 올바른 동작입니다.

"잠깐 — 그런데 *왜* 결제 거절 대 시스템 오류에 대해 별도의 실패 경로가 필요하죠?" Maya가 물었습니다.

"왜냐하면 그것들은 완전히 다른 대응을 요구하기 때문이에요," Leo가 말했습니다. "거절된 카드는 우리가 고객에게 이메일을 보내고 다시 시도하라고 요청한다는 의미예요. 청구 함수의 시스템 오류는 Lambda 함수가 왜 실패하는지 엔지니어가 조사해야 한다는 의미예요. 같은 관찰 가능한 결과 — 주문이 통과되지 않았다 — 지만 완전히 다른 해결책이에요."

**상태 유형: 빌딩 블록**

**Task**: 동작을 실행합니다 — Lambda 함수 호출, ECS 태스크 시작, API 호출. 여기서 실제 작업이 일어납니다.

**Choice**: 입력 데이터의 조건에 기반해 분기합니다. 코드의 if/else 같습니다.

**Parallel**: 여러 분기를 동시에 실행하고 모두 완료될 때까지 기다립니다.

**Map**: 목록의 각 항목에 상태 집합을 적용합니다. 50개의 레스토랑 메뉴 항목을 병렬로 처리합니다.

Nimbus가 레스토랑의 메뉴를 임포트할 때, 메뉴는 8개에서 200개까지의 항목을 포함할 수 있었습니다. 각 항목에 대해, 임포트 프로세스는 다음을 해야 했습니다: 형식 검증, 알레르겐 데이터 확인, 사진 크기 조정, DynamoDB에 레코드 쓰기.

Map 상태 없이는, 이것이 항목을 순차적으로 처리하는 단일 Lambda였을 것입니다 — 200개 항목 × 항목당 200ms = 40초의 처리 시간. Map 상태로, Step Functions가 처리 상태의 동시 실행을 시작하고 — 구성된 동시성 제한까지 — 그것들 모두가 완료될 때까지 기다립니다. 같은 200개 항목이 5초 미만에 끝날 수 있습니다.

**Wait**: 지정된 시간 또는 타임스탬프까지 일시 중지합니다. 예약된 지연에 유용합니다.

**Pass**: 작업을 하지 않고 입력을 출력으로 전달합니다. 데이터 변환과 테스트에 사용됩니다.

**Succeed/Fail**: 실행을 끝내는 종료 상태.

레스토랑 온보딩의 경우, Leo가 워크플로를 설계했습니다:

1. ValidateLicense(Task → Lambda)
2. ImportMenu(Task → Lambda, 3회 재시도)
3. 병렬 분기:
   a. SetupPayments(Task → Lambda)
   b. CreateIAMRole(Task → Lambda)
4. SendWelcomeEmail(Task → Lambda, 병렬이 완료될 때까지 대기)
5. NotifySalesTeam(Task → Lambda)

3a와 3b 단계는 병렬로 실행됩니다 — 그것들은 서로 의존하지 않고, 동시에 실행하면 시간을 절약합니다.

첫 레스토랑 코호트가 온보딩을 완료한 후, 규정 준수 요구사항이 나타났습니다: 레스토랑 파트너가 가동되기 전에, Nimbus 계정 관리자가 라이선스 문서를 수동으로 검토하고 승인해야 했습니다. 이것은 1~3 영업일이 걸릴 수 있었습니다.

"그러면 그 창 동안 누군가 침입을 시도하면 어떻게 되죠?" Priya가 물었습니다. "레스토랑이 부분적으로 구성되어 있고 — 결제 계정이 생성되었지만 아직 승인되지 않음 — 누군가 대기 상태를 발견하면, 반쯤 열린 구성을 악용하려 할 수 있어요."

더 실용적으로: 사람을 기다리며 Step Functions 워크플로를 3일 동안 어떻게 일시 중지합니까?

답은 **태스크 토큰을 사용한 콜백 패턴**입니다.

`ValidateLicense`가 실행될 때, 자동으로 완료하는 대신, 세 가지를 하는 Lambda를 호출합니다:

1. 계정 관리자에게 레스토랑의 문서와 함께 이메일을 보냅니다
2. **태스크 토큰**(Step Functions가 이 특정 실행과 상태에 대해 생성하는 고유 식별자)을 그 대기 중인 검토와 연결하여 데이터베이스에 기록합니다
3. `.waitForTaskToken`과 함께 Step Functions로 반환합니다 — 이것은 Step Functions에게 이 상태에서 실행을 무기한 일시 중지하라고 알립니다

Step Functions가 실행을 주차시킵니다. 다른 어떤 것도 차단되지 않습니다 — 어떤 서버도 기다리며 앉아 있지 않습니다. 상태 머신은 그저 기다리며, 어떤 컴퓨팅 리소스도 소비하지 않습니다.

3일 후, 계정 관리자가 내부 관리 도구에서 "승인"을 클릭합니다. 관리 도구가 데이터베이스에서 태스크 토큰을 조회하고 호출합니다:

```python
stepfunctions.send_task_success(
    taskToken=token,
    output=json.dumps({"approved": True, "reviewedBy": "dana.cole@eatnimbus.com"})
)
```

Step Functions가 재개합니다. 실행이 2단계(`ImportMenu`)부터 계속되며, 검토자의 정보가 워크플로 상태에서 사용 가능합니다.

"실행이 3일 동안 일시 중지되었어요," Leo가 말했습니다, "그리고 제가 그것을 승인했을 때 일어난 유일한 것은 하나의 API 호출이었어요."

"그러면 계정 관리자가 그것을 거부하면요?" Maya가 물었습니다.

"대신 `send_task_failure`를 호출해요. 상태 머신이 그것을 잡아서 레스토랑 파트너에게 이메일을 보내는 `NotifyRejection` 상태로 라우팅해요."

Step Functions는 폴링하지 않습니다. 재시도하지 않습니다. 타임아웃되지 않습니다(하트비트 타임아웃을 설정하지 않는 한). 그것은 단지 콜백이 도착할 때까지 기다린 다음, 계속합니다. 이것은 데이터베이스나 큐를 폴링하는 것과 근본적으로 다릅니다 — 그리고 그것이 Step Functions가 자동 단계와 수동 단계를 섞는 워크플로에 잘 맞는 이유입니다.

**Standard vs Express 워크플로**

Step Functions는 두 가지 워크플로 유형을 제공합니다:

**Standard 워크플로**:

- 최대 기간: 1년
- 실행이 내구성 있음 — 상태가 영속화되고, 검사 및 감사 가능
- 정확히 한 번 실행(Retry를 구성하지 않는 한 태스크가 한 번 이상 실행되지 않음)
- 상태 전환당 요금
- 장기 실행, 중요한 워크플로(주문 처리, 온보딩, 결제 흐름)에 가장 적합

**Express 워크플로**:

- 최대 기간: 5분
- 더 높은 처리량 — 초당 최대 100,000개
- 최소 한 번 실행(비동기) 또는 최대 한 번(동기) — 태스크를 멱등적으로 설계
- 기간당 요금(Lambda처럼)
- 대량, 단기 워크플로(실시간 이벤트 처리, IoT 데이터 수집)에 가장 적합

"그게 월 얼마나 들죠?" Tom이 가격 페이지를 불러오며 물었습니다. "Standard의 경우 상태 전환당 — 단계가 많으면 그게 쌓여요."

Leo가 계산을 짚어 나갔습니다. 레스토랑 온보딩 워크플로의 경우(실행당 여섯 개 태스크 상태, 대략 월 12~15개 신규 레스토랑): 백 개 미만의 상태 전환 — 1센트 미만이고, 전적으로 월 4,000회 전환 무료 계층 안에 있어서, 사실상 $0. 전체 Nimbus 트래픽에서의 주문 확인 워크플로의 경우: 더 의미 있지만, 여전히 월 11건의 부분적 성공을 수동으로 디버깅하는 비용보다 훨씬 적습니다.

"디버깅 시간이 숨은 비용이에요," Leo가 말했습니다.

"그게 항상 숨은 비용이에요," Tom이 말했습니다.

Tom이 숫자를 더 신중하게 돌렸습니다. 그게 Tom이었으니까요.

**Nimbus의 주문 확인 흐름에 대한 Standard 워크플로 비용**: 해피 패스에서 주문당 다섯 개 상태, 상태 전환당 $0.000025. 다섯 개 상태 전환 × $0.000025 × 월 15,000 주문 = **월 $1.88**. 주문량의 열 배에서: 월 약 $19. 한 건의 부분적 성공 사건에 대한 디버깅 비용(지원 엔지니어 시간 24분)이 월 Step Functions 청구서를 여러 배 초과했습니다.

비교는 누군가 고빈도 분석 이벤트에 Standard 워크플로를 사용하자고 제안하면 중요해집니다. Nimbus가 모든 원시 클릭스트림 이벤트 — 모든 메뉴 페이지 조회, 모든 스크롤, 모든 검색 — 를 처리하기 위해 Step Functions를 사용하고 싶다고 가정해보십시오. 그것은 현재 규모에서 하루에 대략 800,000개 이벤트입니다. 각 이벤트에 대한 다섯 개 상태 Standard 워크플로: 800,000 × 5 × $0.000025 × 30일 = **월 $3,000**. 그것은 분석 파이프라인에 진짜 돈입니다.

같은 볼륨에 대한 Express 워크플로: 상태 전환당이 아니라 요청당 더하기 기간으로 요금이 부과됩니다. 월 2,400만 실행은 백만 요청당 $1.00 = $24. 기간: 2,400만 × 64MB 청구 최소치에서 500ms ≈ 208 GB-시간 × $0.06 = $12.50. 총 ≈ **월 $36.50** — Standard의 $3,000보다 거의 두 자릿수 더 저렴합니다.

"그러니까 워크플로의 유형은 단지 아키텍처 결정이 아니에요," Tom이 말했습니다. "그건 비용 결정이에요. 같은 수의 상태가 어느 워크플로 유형을 사용하느냐에 따라 거의 백 배 더 들 수 있어요."

"그리고 어느 것이 더 나은지는 전적으로 워크플로가 무엇을 하느냐에 달려 있어요," Leo가 말했습니다. "주문 확인: Standard. 그건 중요하고, 의미 있는 실패 경로가 있고, 우리는 감사 추적을 원해요. 분석 이벤트 처리: Express. 그건 대량이고, 단기이며, 우리는 모든 페이지 조회에 대해 90일 실행 히스토리가 필요 없어요."

프로세스가 두 단계이고 감사 추적이 필요 없다면, 단순한 Lambda 함수가 더 저렴하고 JSON 상태 머신 구문이 필요 없습니다 — 하지만 어떤 단계든 독립적으로 실패할 수 있고 이전 단계를 반복하지 않고 재시도되거나 재시작되어야 한다면, Step Functions가 줄어든 디버깅과 수동 해결로 그 비용을 회수합니다.

Nimbus의 레스토랑 온보딩의 경우: Standard(중요하고, 내구성 있으며, 수동 단계가 관련되면 몇 시간이 걸릴 수 있음).

Nimbus의 실시간 주문 상태 업데이트의 경우: Express(대량, 단기, 덜 중요함).

**이벤트 기반 아키텍처: 더 큰 그림**

Step Functions는 더 큰 패턴의 한 조각입니다: **이벤트 기반 아키텍처(event-driven architecture)**. 서비스가 서로를 직접 호출하는 대신(긴밀한 결합), 서비스가 이벤트를 방출하고, 다른 서비스가 그 이벤트에 반응합니다.

우리는 이것을 책 전체에서 봐 왔습니다:

- 주문 접수 → SNS가 이벤트 게시 → SQS 큐가 소비자에게 전달
- S3 파일 업로드 → 그것을 처리하기 위해 Lambda 트리거
- DynamoDB 레코드 변경 → DynamoDB Streams → Lambda가 캐시 업데이트

**Amazon EventBridge**(이전의 CloudWatch Events)는 이 패턴을 위한 고급 이벤트 버스입니다. 그것은 규칙에 기반해 AWS 서비스와 여러분 자신의 애플리케이션의 이벤트를 대상(Lambda, SQS, Step Functions 등)으로 라우팅합니다.

EventBridge는 아키텍처 수준에서 느슨한 결합을 허용합니다: 주문 서비스가 누가 듣고 있는지 모르고 `order.placed` 이벤트를 게시합니다. 분석 서비스, 알림 서비스, 로열티 포인트 서비스가 모두 독립적으로 듣습니다. 새 리스너를 추가하는 것은 주문 서비스를 변경할 필요가 없습니다.

EventBridge는 또한 수십 개의 AWS 서비스와 **이벤트 소스**로서 네이티브로 통합됩니다. CloudTrail API 호출이 패턴과 일치하면, EventBridge가 규칙을 발사할 수 있습니다. EC2 인스턴스가 상태를 변경하면, EventBridge가 Lambda를 트리거할 수 있습니다. RDS 인스턴스가 장애 조치하면, EventBridge가 온콜 엔지니어에게 알릴 수 있습니다. 전체 AWS 제어 평면을 이벤트 스트림으로 취급할 수 있습니다.

Nimbus의 경우, 특히 유용한 EventBridge 규칙: 새 이미지가 ECR에 푸시될 때마다 Lambda를 트리거합니다. Lambda가 이미지 스캔 결과를 확인하고 HIGH 또는 CRITICAL CVE가 발견되면 엔지니어링 Slack 채널에 게시합니다 — 누군가 이미지를 배포하기 전에요. 이것은 ECR의 보안 스캐닝(21장에서)과 EventBridge의 이벤트 라우팅을 자동화된 보안 게이트로 결합합니다.

이벤트 기반 아키텍처의 원칙은 Step Functions의 재시도 로직과 같습니다: 실패를 조용하고 삼켜지는 것이 아니라 명시적이고 라우팅되게 만드는 것. 이벤트를 통해 통신하는 서비스는 우아하게 실패합니다 — `OrderConfirmed` 이벤트가 발사될 때 로열티 포인트 Lambda가 다운되어 있으면, EventBridge가 배달을 재시도하거나 dead-letter 큐로 보낼 수 있습니다. 주문 확인 자체는 영향받지 않습니다. 분리가 복원력입니다.

**EventBridge: 부수 효과를 주 흐름에서 분리하기**

주문 확인 상태 머신이 깔끔하게 실행되고 있은 후, Maya가 다음 아키텍처 검토에서 질문을 제기했습니다.

"주문이 확인될 때 로열티 포인트를 추가하고 싶어요. 고객이 쓴 1달러당 1포인트를 받아요. 그게 상태 머신의 어디에 들어가죠?"

Leo의 첫 본능: `LogTransaction` 후에 `GrantLoyaltyPoints` 상태를 추가하는 것.

Priya의 대응: "그러면 추천 보너스를 추가할 때는요? 그리고 주문 후 설문조사는요? 그리고 레스토랑 평가 요청은요? 각각이 임계 경로에 상태를 추가해요. 로열티 포인트 Lambda가 실패하면, 전체 주문 확인이 실패해요."

"주문 확인 흐름은 한 가지를 해야 해요," 그녀가 말했습니다. "주문을 확인하는 것. 다른 모든 건 부수 효과예요."

이것이 주 워크플로에서 부수 효과를 느슨하게 결합하는 메커니즘으로서 **Amazon EventBridge**에 대한 아키텍처적 논거입니다.

수정된 접근법: `LogTransaction` 상태가 성공적으로 완료되면, Lambda가 EventBridge에 이벤트를 게시합니다:

```json
{
  "source": "nimbus.orders",
  "detail-type": "OrderConfirmed",
  "detail": {
    "orderId": "ORD-8812",
    "customerId": "CUST-441",
    "restaurantId": "94",
    "total": 3200,
    "timestamp": "2024-03-15T14:23:43Z"
  }
}
```

그러면 EventBridge 규칙이 그 이벤트를 독립적인 대상으로 라우팅합니다:

- **규칙 1**: `OrderConfirmed` → 로열티 포인트 Lambda($32 주문에 대해 32포인트 부여)
- **규칙 2**: `OrderConfirmed` → 주문 후 설문조사 Lambda(배달 2시간 후 설문조사 큐에 추가)
- **규칙 3**: `OrderConfirmed` → 분석 Kinesis 스트림(실시간 대시보드에 공급)

각 규칙은 독립적입니다. 로열티 포인트 Lambda가 설문조사 큐에 영향을 주지 않고 실패할 수 있습니다. 분석 파이프라인이 로열티 시스템을 차단하지 않고 뒤처질 수 있습니다. 새 부수 효과(레스토랑 평가 요청, 캐시백 알림)를 추가하는 것은 새 EventBridge 규칙을 만드는 것이 필요합니다 — 상태 머신을 수정하는 것이 아니라요.

"그러면 누군가 EventBridge 규칙을 통해 침입을 시도하면 어떻게 되죠?" Priya가 물었습니다. "이벤트가 고객 PII를 포함하면, 그것을 받는 모든 Lambda가 이제 PII 액세스 지점이 돼요."

이벤트는 신중하게 설계되었습니다: 이름, 주소, 또는 결제 세부 정보가 아니라 오직 ID만. 고객 데이터가 필요한 어떤 Lambda든 고객 ID를 사용해 데이터베이스에서 그것을 조회할 것입니다 — 무엇에 액세스할 수 있는지 제어하는 자체 IAM 권한과 함께요.

"이벤트는 신호예요," Priya가 말했습니다. "데이터 덤프가 아니라요."

**Step Functions가 올바른 도구일 때**

Step Functions는 다음을 가질 때 탁월합니다:

**다단계 워크플로** — 단계에 걸쳐 진행 상황을 추적해야 함

**휴먼 인 더 루프 프로세스** — Step Functions는 외부 이벤트(누군가 무언가를 승인하는 것 같은)를 무기한 기다린 다음 계속할 수 있음

**대규모 오류 처리** — 많은 단계에 걸친 내장 재시도, 캐치, 폴백 로직

**감사 가능한 프로세스** — 모든 실행이 모든 상태 전환을 기록함. 정확히 무엇이 일어났고 언제인지 볼 수 있음.

**복잡한 병렬 또는 순차 로직** — 시각적 워크플로가 동등한 코드보다 추론하기 쉽게 만듦

Step Functions는 단순한 두 단계 프로세스에는 과합니다. 조율 자체가 가치 있고 실패 시나리오가 중요할 때 사용하십시오.

**Step Functions가 잘못된 도구일 때**

"잠깐 — 그런데 *왜* 모든 것에 Step Functions를 쓰지 않죠?" Maya가 설계 세션 끝에 물었습니다. "우리는 레스토랑 온보딩 워크플로를 구축했어요. 주문 확인 흐름이 있어요. 왜 모든 것을 상태 머신으로 변환하지 않죠?"

정직한 답: 왜냐하면 Step Functions가 모든 워크플로가 정당화하지 않는 오버헤드를 추가하기 때문입니다.

**단순한 두 단계 프로세스**: 두 번째 Lambda를 호출해서 업로드된 파일을 처리하는 Lambda가 있다면, 상태 머신의 조율 오버헤드는 운영 이익만큼의 가치가 없습니다. 단일 함수 내에서 순차적으로 호출되는 두 Lambda가 더 단순하고, 테스트하기 쉽고, 상태 전환당 비용이 없습니다.

**초고빈도, 1초 미만 워크플로**: Standard 워크플로는 대량에서 누적되는 사소하지 않은 상태 전환당 비용을 가집니다(위의 분석 예에서 보았듯이). Express 워크플로가 비용 문제를 해결하지만 내구성 있는 상태 히스토리를 제공하지 않습니다. 매우 짧은 기간의 매우 높은 빈도에서, SQS 더하기 Lambda(19장의 패턴)가 어느 Step Functions 유형보다 더 단순하고 저렴합니다.

**조율 없는 순수한 팬 아웃**: 같은 이벤트를 스무 명의 소비자에게 보내야 하고 각각의 결과에 신경 쓰지 않는다면, SNS가 도구입니다. Step Functions는 필요 없고 불필요하게 비용을 지불할 상태 추적을 추가합니다.

**실시간 동기 사용자 상호작용**: Step Functions 실행은 비동기적입니다. 사용자가 결제 화면에서 500ms 미만의 동기 응답을 기다리고 있다면, Step Functions Standard 워크플로는 이를 위해 설계되지 않았습니다(Express 워크플로는 동기적으로 호출될 수 있지만, 지연 오버헤드가 여전히 직접 Lambda 호출보다 높습니다). 동기 사용자 대면 흐름의 경우, 잘 설계된 오류 처리가 있는 Lambda + API Gateway가 종종 더 적절합니다.

원칙: 단계의 *조율*이 그 자체로 복잡할 때 — 단계가 독립적으로 실패할 수 있을 때, 이전 것을 반복하지 않고 개별 단계를 재시도해야 할 때, 실행 히스토리가 규정 준수나 디버깅 가치가 있을 때, 또는 워크플로가 며칠 걸릴 수 있는 사람 승인 단계를 포함할 때 Step Functions를 사용하십시오. 단일 함수로 잘 작동하는 단순한 순차 로직에 오케스트레이션 오버헤드를 추가하기 위해 그것을 사용하지 마십시오.

## 장점과 한계

**Step Functions가 강력한 이유**:

- 시각적 실행 히스토리 — 워크플로가 정확히 어디에 있는지(또는 실패했는지) 봅니다
- 내장 재시도와 오류 처리 — 커스텀 재시도 코드 없음
- 내구성 있는 상태 — 실행이 서비스 재시작과 중단을 견딥니다
- 200개 이상의 AWS 서비스와의 직접 통합(Lambda만이 아니라)
- 시각적 워크플로가 자체 문서화됩니다
- 콜백 패턴이 컴퓨팅을 소비하지 않고 사람 행동을 무기한 기다리는 것을 가능하게 합니다

**복잡해지는 부분**:

- Standard 워크플로는 상태 전환당 요금이 부과됩니다 — 많은 상태를 가진 복잡한 워크플로는 대규모에서 비싸질 수 있습니다
- ASL(Amazon States Language) JSON 형식은 학습 곡선이 있습니다
- 최대 페이로드 크기는 256KB입니다 — 큰 데이터는 워크플로를 통해 직접이 아니라 S3 참조를 통해 전달되어야 합니다
- 많은 수동 단계를 가진 장기 실행 워크플로는 신중한 타임아웃 구성이 필요합니다
- ASL 오류 디버깅은 실행을 돌리는 것이 필요합니다; 실제 서비스만큼 유능한 로컬 에뮬레이터가 없습니다
- IAM 권한은 상태 머신이 호출하는 각 리소스에 대해 별도로 부여되어야 합니다 — 한 권한을 잊으면 런타임에 혼란스러운 오류가 발생합니다

## 요약

21장의 컨테이너는 배포를 신뢰할 수 있게 만들었습니다. Step Functions는 다단계 비즈니스 프로세스를 신뢰할 수 있게 만듭니다 — "핸드오프 위험 제거"라는 같은 원칙이 애플리케이션 로직에 적용된 것입니다.

- **Step Functions**는 다단계 워크플로를 상태 머신으로 오케스트레이션합니다.
- 각 **상태**는 Lambda 함수를 실행하거나, ECS 태스크를 실행하거나, 기다리거나, 분기하거나, 병렬 단계를 실행할 수 있습니다.
- **Retry와 Catch**가 각 상태에 내장되어 있습니다 — 커스텀 재시도 코드가 필요 없습니다.
- **Standard 워크플로**: 장기 실행(최대 1년), 내구성 있음, 정확히 한 번. 중요한 비즈니스 프로세스용.
- **Express 워크플로**: 단기(최대 5분), 고처리량. 대량 이벤트 처리용.
- **태스크 토큰을 사용한 콜백 패턴**: 외부 이벤트나 사람 행동을 기다리며 워크플로를 무기한 일시 중지; 하나의 API 호출로 재개.
- **Map 상태**: 항목 목록을 동시에 처리 — 순차 루프를 병렬 팬 아웃으로 대체.
- **직접 SDK 통합**: Lambda 래퍼 없이 상태에서 DynamoDB, S3, SQS, 그리고 200개 이상의 AWS 서비스를 직접 호출.
- **EventBridge**: 부수 효과를 주 워크플로에서 분리 — 하나의 이벤트를 게시하고, 독립적인 규칙이 그것을 핵심 상태 머신을 수정하지 않고 로열티 포인트, 분석, 설문조사 서비스로 라우팅하게 함.
- **Standard vs Express 비용**: 상태 전환당 $0.000025의 Standard는 저용량 중요 워크플로에 잘 작동합니다(Nimbus의 주문 확인은 월 $1.88). 요청당 더하기 기간 가격의 Express는 Standard가 수십 배 더 들 고빈도 이벤트에 적절합니다(Nimbus의 클릭스트림 계산에서 ~80배).
- **이벤트 기반 아키텍처**는 직접 호출이 아니라 이벤트를 중심으로 시스템을 분리하기 위해 SNS, SQS, Lambda, EventBridge 같은 서비스를 사용합니다.
- 단계의 조율이 그 자체로 복잡하고 감사 가능성이 중요할 때 Step Functions를 사용하십시오. 단순한 두 단계 시퀀스, 초고빈도 워크플로, 순수한 팬 아웃, 또는 동기 사용자 대면 흐름에는 사용하지 마십시오.

## 시험 팁

*SAA-C03 도메인: 탄력적 아키텍처 설계(도메인 2, 태스크 2.1)*

- **Step Functions 사용 사례 신호**: "여러 Lambda 함수 오케스트레이션," "재시도와 오류 처리가 있는 워크플로," "자동화된 워크플로의 사람 승인 단계," "각 워크플로 단계의 감사 추적" → Step Functions.
- **Standard vs Express**: 장기 실행, 감사 가능, 비즈니스 중요 워크플로에는 Standard. 고처리량, 단기 이벤트 처리에는 Express.
- **SQS vs Step Functions**: 단순한 작업 큐(생산자/소비자)에는 SQS. 복잡한 로직, 재시도, 상태 추적이 있는 다단계 워크플로에는 Step Functions.
- **EventBridge 신호**: "AWS 서비스의 이벤트를 대상으로 라우팅," "서비스 간 이벤트 기반 통합," "Lambda 함수 예약" → EventBridge(이전의 CloudWatch Events).
- **콜백 패턴**: Step Functions는 실행을 일시 중지하고 외부 콜백(태스크 토큰)을 기다릴 수 있습니다. 작업자가 완료되면 콜백합니다. Lambda의 15분 제한을 원하지 않는 장기 실행 ECS 태스크에 유용합니다.
- **직접 SDK 통합**: Step Functions는 Lambda를 거치지 않고 AWS 서비스(DynamoDB, S3, SQS 등)를 직접 호출할 수 있습니다. 단순한 서비스 호출의 비용과 지연을 줄입니다. 예를 들어, DynamoDB에 주문 레코드를 쓰는 것은 Lambda 함수 없이 상태 머신에서 직접 SDK 호출일 수 있습니다: `"Resource": "arn:aws:states:::dynamodb:putItem"`. 이것은 Lambda 콜드 스타트, Lambda 실행 비용, 그리고 그저 `dynamodb.put_item(...)`을 호출하고 반환하는 코드를 제거합니다.

## 연습 문제

**연습 1 — 회상**

Step Functions가 다단계 워크플로에 유용한 이유를 설명하십시오. 다른 Lambda 함수를 호출하는 단순한 Lambda 함수가 제공하지 않는 것을 그것이 무엇을 제공합니까?

*(힌트: 각 접근법에서 5단계 중 3단계가 실패하면 어떻게 되는지 생각해보십시오. 무엇이 일어났는지 어떻게 압니까? 3단계만 어떻게 재시도합니까?)*

**연습 2 — SAA-C03 시나리오**

*시나리오*: 금융 서비스 회사가 여러 단계로 대출 신청을 처리합니다: 신용 확인, 소득 검증, 문서 검증, 인수 심사(수동), 결정 통보. 각 단계는 초(신용 확인)에서 며칠(인수 심사)까지 걸릴 수 있습니다. 회사는 규정 준수를 위해 모든 단계의 완전한 감사 추적이 필요합니다. 실패한 자동 단계는 자동으로 재시도되어야 합니다; 수동 단계는 일시 중지하고 사람의 결정을 기다려야 합니다.

이 요구사항을 가장 잘 충족하는 서비스는 무엇입니까?

A) 각 단계 사이에 SQS 큐로 함께 체이닝된 AWS Lambda 함수  
B) 인수 심사 단계를 위한 콜백 대기 패턴이 있는 AWS Step Functions Standard 워크플로  
C) 자동 단계를 위한 AWS Step Functions Express 워크플로와 수동 단계를 위한 SQS FIFO  
D) 각 단계에 대해 Lambda 함수 사이를 라우팅하는 이벤트 규칙이 있는 Amazon EventBridge

**힌트 1**: "며칠까지" 기간 — 어떤 Step Functions 유형이 이를 지원합니까?

**힌트 2**: "사람의 결정을 기다림" — 어떤 Step Functions 패턴이 이를 위해 설계되었습니까?

**힌트 3**: "규정 준수를 위한 완전한 감사 추적" — 어떤 서비스가 실행별 상태 히스토리를 제공합니까?

**정답**: B

**설명**: Step Functions Standard 워크플로는 최대 1년 실행될 수 있어, 며칠 걸리는 인수 심사 단계를 지원합니다. 콜백 대기 패턴은 태스크 토큰으로 인수 심사 단계에서 실행을 일시 중지합니다; 인수자가 결정을 내리면, 그들이 토큰과 함께 콜백하여 워크플로를 계속합니다. Standard 워크플로는 모든 상태 전환을 기록합니다 — 규정 준수를 위한 완전한 감사 추적.

**왜 A가 아닌가?** SQS로 체이닝된 Lambda는 내장 상태 추적이나 감사 추적을 제공하지 않습니다. 실패한 단계는 커스텀 재시도 로직이 필요합니다. 특정 실패 단계에서 재시작하는 것은 커스텀 구현이 필요합니다.

**왜 C가 아닌가?** Express 워크플로는 최대 5분 기간입니다 — 며칠 걸릴 수 있는 단계와 호환되지 않습니다.

**왜 D가 아닌가?** EventBridge는 서비스 간 이벤트를 라우팅하지만 워크플로 상태를 유지하거나 내장 재시도/감사를 제공하지 않습니다. EventBridge만으로 이것을 구축하는 것은 커스텀 상태 관리가 필요합니다.

*SAA-C03 도메인: 탄력적 아키텍처 설계 — 태스크 2.1*

**연습 3 — 아키텍처 과제** *(선택 사항)*

Nimbus가 음식 품질 분쟁 해결 프로세스를 구축하고 있습니다. 고객이 나쁜 경험을 보고하면:

1. 보고가 자동으로 검증됩니다(주문이 존재하는지, 충분히 최근인지 확인)
2. 레스토랑이 자동으로 알림을 받습니다
3. Nimbus 지원 담당자가 불만을 검토합니다(수동 단계 — 1~3 영업일이 걸릴 수 있음)
4. 담당자의 결정에 기반해: 환불 발행(Lambda → 결제 처리자) 또는 사과 쿠폰 발송(Lambda → 쿠폰 서비스) 또는 경영진에 에스컬레이션(Step Functions 하위 워크플로)
5. 고객이 결과를 통보받습니다

이것을 Step Functions 워크플로로 설계하십시오. 어떤 상태 유형이 각 단계를 처리합니까? 1~3일 대기를 어떻게 처리하겠습니까? 4단계의 분기를 어떻게 모델링하겠습니까?

*(단 하나의 정답은 없습니다. 목표는 Step Functions 상태 설계를 연습하는 것입니다.)*

**확장**: 상태 머신이 (어느 분기든) 완료된 후, 그것이 EventBridge에 `OrderDisputeResolved` 이벤트를 게시합니다. 어떤 부수 효과가 이 이벤트를 들을 수 있습니까? 고려하십시오: 레스토랑의 평가 시스템, 고객의 로열티 포인트(환불이 포인트를 차감할 수 있음), 분석 파이프라인(분쟁률은 핵심 레스토랑 품질 지표임), 고객 지원 팀의 SLA 추적 대시보드. 여기서 EventBridge를 사용하는 것이 어떻게 분쟁 상태 머신이 종속성 거미가 되는 것을 막습니까?

## 포스트 크레딧 장면

레스토랑 온보딩 워크플로가 라이브였습니다.

다음 달에 걸쳐, 12개의 새 레스토랑 파트너가 온보딩했습니다. 두 개가 결제 처리 단계(3단계) 동안 실패했습니다. 두 경우 모두, Step Functions가 정확한 오류를 포착하고, 실행의 상태를 저장하고, Nimbus 팀에 알림을 보냈습니다.

Leo가 근본 원인(결제 제공자의 잘못 구성된 API 키)을 고치고 두 실행을 3단계부터 재시도했습니다. 실행이 각각 23초에 완료되며, 정확히 실패한 곳에서부터 이어받았습니다.

어떤 레스토랑도 다시 임포트될 필요가 없었습니다. 어떤 IAM 역할도 두 번 생성되지 않았습니다. 어떤 중복 환영 이메일도 전송되지 않았습니다.

"Step Functions 이전에는," Leo가 Maya에게 말했습니다, "이건 누군가 각 레스토랑에 대해 무엇이 완료되었고 안 되었는지 수동으로 추적하고, 누락된 단계를 수동으로 다시 실행해야 했을 거예요."

"그리고 이제는?"

"이제 콘솔에서 재시도를 클릭해요. 시스템이 무엇이 완료되었는지 알아요."

Maya가 이것에 대해 생각했습니다.

"그건 단지 기술적 개선이 아니에요," 그녀가 말했습니다. "그건 확장되는 프로세스와 그렇지 않은 프로세스의 차이예요."
