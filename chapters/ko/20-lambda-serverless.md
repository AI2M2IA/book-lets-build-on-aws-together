# 20장: 프리랜서 모델

주문 알림 함수는 주문당 정확히 한 번 실행됐다. 주문 사이에는 아무것도 하지 않았다. 화요일에 17시간 동안 주문이 없었다. 그 17시간 동안, 함수는 아무 비용도 들지 않았다. 1센트도 아니다. 유휴 서버 없음, 대기 인스턴스 없음, 사용되지 않는 예약 용량 없음. 함수가 존재했다. 그냥 실행되지 않았을 뿐이다.

SNS/SQS 팬 아웃이 작동하고 있었다. 분석 서비스, 알림 서비스, 이메일 서비스가 각자의 SQS 큐에서 소비하고 있었다.

하지만 Priya가 뭔가를 알아챘다.

"이메일 서비스," 그녀가 말했다. "시간당 얼마나 많은 이메일을 보내요?"

Leo가 메트릭을 확인했다. "평균 400개. 금요일 저녁 최대 약 1,200개."

"그리고 이메일 서비스를 실행하는 EC2 인스턴스 — 얼마나 오래 실행되나요?"

"항상. 24/7."

"새벽 3시에 이메일을 0개 보낼 때도요?"

침묵.

더 많은 침묵.

**서버가 항상 답은 아니다**

EC2 인스턴스는 영구적이다. 중지할 때까지 실행된다 — 하루 24시간, 주 7일, 실제 사용에 관계없이. 모든 시간에 트래픽을 처리하는 웹 서버의 경우, 맞다. 드물게 이메일을 보내고 몇 시간 유휴 상태인 이메일 서비스의 경우, 낭비다.

Auto Scaling Group은 이메일 서비스를 비수요 시간에 하나의 인스턴스로 축소할 수 있다. 하지만 하나의 인스턴스는 여전히 계속 실행된다.

작업이 있을 때만 코드가 실행된다면 어떨까?

이것이 **서버리스 컴퓨팅**의 전제다.

**AWS Lambda: 서버 없는 코드**

**AWS Lambda**는 서버를 프로비저닝하거나 관리하지 않고 이벤트에 대응하여 코드를 실행하게 한다. 함수를 업로드하고, 무엇이 트리거하는지 지정하면, Lambda가 트리거가 발생할 때 실행한다.

Lambda 함수:

- 영구적인 상태가 없다(각 호출은 독립적)
- 호출당 최대 15분 실행된다
- 0에서 수천 개의 동시 호출까지 자동으로 확장된다
- 실행 중일 때만 청구된다(1ms 실행당, 반올림, GB 메모리 할당당)

트리거가 없으면, Lambda는 아무것도 비용이 들지 않는다. 트리거가 발생하면, Lambda가 실행되고 청구된다. 10,000개의 트리거가 동시에 발생하면, Lambda는 10,000개의 동시 호출을 실행한다. 확장은 자동이고 거의 즉각적이다.

**이벤트 트리거: Lambda를 깨우는 것**

Lambda 함수는 스스로 실행되지 않는다 — 이벤트에 대응한다. 일반적인 트리거에는 다음이 포함된다:

- **SQS 큐**: 큐에서 메시지를 처리한다. Lambda가 큐를 폴링하고 메시지 배치로 함수를 호출한다.
- **API Gateway**: HTTP 요청이 들어온다. API Gateway가 Lambda를 트리거한다. Lambda가 응답을 생성한다.
- **S3 이벤트**: 파일이 S3에 업로드된다. Lambda가 그것을 처리한다(이미지 크기 조정, CSV 파싱, 문서 검증).
- **SNS**: 메시지가 토픽에 게시된다. Lambda가 알림을 받는다.
- **DynamoDB Streams**: DynamoDB의 레코드가 변경된다. Lambda가 변경을 처리한다.
- **CloudWatch Events(EventBridge)**: 예약된 이벤트(크론 작업처럼)가 정의된 시간에 실행된다.
- **ALB**: HTTP 요청이 로드 밸런서에 도착한다. Lambda가 특정 경로를 처리할 수 있다.

Nimbus의 경우, 이메일 서비스가 SQS 큐에서 트리거된 Lambda 함수가 됐다. 큐에 메시지가 도착하면, Lambda가 메시지 내용으로 호출되고, SES(Simple Email Service)를 통해 이메일을 보내고, 종료된다.

서버 없음. 유휴 시간 없음. 유휴 시 비용 없음.

**콜드 스타트 문제**

Lambda 함수는 **실행 환경** — 작고 격리된 컨테이너에서 실행된다. 함수가 호출될 때:

1. AWS가 웜 실행 환경이 사용 가능한지 확인한다(최근 호출을 처리한 것)
2. 웜이면: 함수가 즉시 실행된다
3. 콜드이면: AWS가 새 실행 환경을 초기화한다 — 코드를 다운로드하고, 런타임을 시작하고, 초기화 코드를 실행한 다음 — 함수를 실행한다

**콜드 스타트**는 런타임(Java와 .NET은 Python과 Node.js보다 더 긴 콜드 스타트를 갖는다)과 코드 패키지의 크기에 따라 100ms에서 수 초의 지연을 추가한다.

비동기 처리(이메일 전송, 이미지 크기 조정)의 경우, 콜드 스타트는 사용자에게 보이지 않는다.

응답을 기다리는 동기 API(HTTP 요청)의 경우, 콜드 스타트는 때때로 느린 응답을 유발할 수 있다.

**완화 방법**:

- **프로비저닝된 동시성**: 지정된 수의 실행 환경을 미리 예열. 처리 요청을 기다리지 않아도 항상 준비됨. 이 비용은 심지어 요청을 처리하지 않을 때도 지불한다.
- **더 작은 패키지 크기**: 더 작은 코드가 더 빠르게 초기화된다.
- **웜업 호출**: 함수를 웜하게 유지하기 위한 예약된 핑(일반적이지만 우아하지 않은 접근).
- **올바른 런타임 선택**: Python과 Node.js가 Java보다 더 빨리 콜드 스타트된다.

**Lambda 가격: Tom이 웃은 이유**

Lambda 가격에는 두 가지 구성 요소가 있다:

1. **요청 요금**: 백만 호출당 $0.20
2. **기간 요금**: GB-초당 $0.0000166667(메모리 할당 × 실행 초)

월간 첫 백만 요청은 무료다(항상, 첫 해만이 아니라).

Tom이 이메일 서비스를 위한 계산을 했다:

- 하루 1,200개 이메일 × 30일 = 월 36,000 호출
- 각 호출은 256MB 메모리로 ~2초 걸린다
- 기간: 36,000 × 2 × 0.25GB × $0.0000166667 = $0.30/월
- 요청: 36,000 << 1,000,000(무료 계층) = $0.00/월

이메일 서비스를 위한 EC2 인스턴스: 월 $18.

Tom이 잠시 조용했다. 그런 다음: "이것을 모든 것에 해야 해요."

**Lambda가 잘하는 것(그리고 못하는 것)**

Lambda는 다음에 훌륭하다:

- **이벤트 기반 처리**: 이벤트에 대응(파일 업로드, 큐 메시지, 예약된 작업)
- **짧은 실행 작업**: 15분 내에 잘 완료되는 처리
- **스파이크하고 예측 불가능한 트래픽**: Lambda는 0에서 수천으로 즉시 확장된다 — 사전 프로비저닝 없음
- **비정기적 작업**: 매일 새벽 2시에 실행되는 보고서. 매주 실행되는 정리 작업.
- **글루 코드**: 서비스 사이에 데이터를 이동하는 작은 함수

Lambda는 다음에 좋지 않다:

- **장기 실행 프로세스**: 15분 제한이 고정 벽이다
- **상태가 있는 애플리케이션**: Lambda 함수는 설계상 무상태다 — 각 호출은 독립적
- **높은 처리량, 낮은 지연 API**: 콜드 스타트는 지연 급증을 유발할 수 있다; 프로비저닝된 동시성이 이를 완화하지만 비용을 추가한다
- **영구적 연결이 필요한 애플리케이션**: Lambda는 쉽게 장기 데이터베이스 연결 풀을 유지할 수 없다(RDS Proxy 같은 연결 풀링 도구가 도움이 되지만)
- **전통적인 웹 서버**: 가능하지만, 자연스러운 적합이 아니다

"그러면 Lambda는 EC2의 교체가 아니야," Maya가 말했다. "다른 작업을 위한 다른 도구야."

"Nimbus 웹 API는 EC2나 ECS에 남는다," Leo가 확인했다. "이메일 서비스, 이미지 리사이저, 야간 보고서 생성기, 로그 클리너 — 그것들이 Lambda로 이동한다."

**서버리스 철학**

Lambda는 더 넓은 개념의 일부다: **서버리스** — 서버가 아닌 코드만 관리하는 애플리케이션 구축.

완전한 서버리스 Nimbus 스택은 이렇게 보일 수 있다:

- API Gateway + Lambda (웹 서버가 있는 EC2 대신)
- DynamoDB (RDS 대신 — 또한 서버리스, 서버 관리 없음)
- S3 (정적 자산 — 본질적으로 서버리스)
- SNS + SQS (메시징 — 서버리스)
- Lambda (모든 백그라운드 처리)

매력: 코드를 작성하면; AWS가 다른 모든 것을 관리한다. 패치 없음, 확장 설정 없음, 용량 계획 없음.

현실: 서버리스는 자체적인 운영 복잡성을 갖는다 — 분산 Lambda 함수 디버깅, 콜드 스타트 관리, 동시성 제한 이해. 더 단순하지 않고, 다를 뿐이다.

## 장점과 한계

**Lambda가 강력한 이유**:

- 진정한 사용당 지불 — 유휴 시 비용 없음
- 설정 없이 자동 확장
- 패치하거나 유지 보수할 서버 없음
- 관대한 무료 계층(월 백만 요청, 영원히 무료)
- AWS 나머지와 긴밀한 통합

**복잡해지는 부분**:

- 콜드 스타트는 실제이며 지연 민감 워크로드에 주의 깊은 처리가 필요하다
- 15분 실행 제한이 장기 실행 작업을 제외한다
- 디버깅이 더 어렵다 — SSH할 영구 서버가 없다
- 무상태 설계는 모든 상태를 외부화해야 한다(데이터베이스, 캐시, S3)
- 동시성 제한(계정당 기본 1,000 동시 호출)이 대규모에서 스로틀할 수 있다
- VPC 연결 Lambda 함수는 추가 지연 및 콜드 스타트 문제가 있다

## 요약

- **AWS Lambda**는 서버를 관리하지 않고 이벤트에 대응하여 코드를 실행한다.
- **사용당 지불**: 호출당 및 1ms 실행당(반올림) 청구. 유휴 시 비용 없음.
- 0에서 수천 개의 동시 호출까지 자동으로 확장한다.
- **콜드 스타트**: 웜 실행 환경이 없을 때 초기화 지연. 프로비저닝된 동시성 또는 경량 런타임으로 완화된다.
- 이벤트 기반, 단기 실행, 스파이크, 또는 비정기적 워크로드에 가장 적합.
- 장기 실행 작업, 상태가 있는 애플리케이션, 프로비저닝된 동시성 없는 높은 처리량 낮은 지연 API에는 적합하지 않음.
- **서버리스**는 설계 철학이다 — 인프라가 아닌 코드를 관리한다.

## 시험 팁

*SAA-C03 도메인: 탄력적 아키텍처 설계(도메인 2, 태스크 2.1)*

- **Lambda + S3**: 고전적인 패턴 — S3에 파일이 업로드됨이 처리를 위해 Lambda를 트리거한다(썸네일 생성, 바이러스 스캔, 데이터 변환). 서버 필요 없음.
- **Lambda + SQS**: Lambda가 SQS를 폴링하고 배치로 처리한다. SQS가 재시도/DLQ 메커니즘을 제공한다. Lambda가 처리를 제공한다.
- **Lambda + API Gateway**: 서버리스 HTTP API. API Gateway가 라우팅, 인증, 스로틀링을 처리한다. Lambda가 비즈니스 로직을 처리한다.
- **콜드 스타트 신호**: "첫 번째 요청에서 지연 급증," "일관되지 않은 응답 시간" → 콜드 스타트. 해결책: 프로비저닝된 동시성(비용이 든다), 더 작은 패키지, 더 가벼운 런타임.
- **실행 제한**: 최대 15분. 최대 10GB 메모리. 기본 512MB /tmp 임시 스토리지(최대 10GB까지 설정 가능). 이 제한들이 시험 시나리오에 나타난다.
- **Lambda 동시성**: 기본 계정당 1,000 동시 실행(늘릴 수 있다). **예약된 동시성**: 함수가 특정 수의 실행을 받도록 보장; 다른 함수가 소비하는 것을 방지한다. **프로비저닝된 동시성**: 실행 환경을 미리 예열.
- **이벤트 소스 매핑**: SQS/DynamoDB Streams/Kinesis를 Lambda에 연결하는 Lambda 기능. Lambda가 소스를 폴링하고 레코드를 배치한다.

D) 새 이미지를 위해 1분마다 S3를 확인하는 크론 작업이 있는 전용 EC2 인스턴스

**힌트 1**: 예측 불가능한 볼륨은 제로로 확장하는 것을 선호한다. 어떤 옵션이 그것을 하는가?

**힌트 2**: 이미지당 10분이 Lambda의 15분 제한 내에 있다. 이미지 크기 조정 작업이 Lambda의 제약에 맞는지 확인하라.

**힌트 3**: 24/7 실행되는 전용 EC2 인스턴스는 비싸고 확장되지 않는다.

**답**: B

**설명**: S3 이벤트 알림이 이미지가 업로드될 때 Lambda를 트리거한다. Lambda가 이미지를 네 가지 크기로 조정하고 결과를 S3에 저장한다. Lambda는 수천 개의 동시 호출까지 자동으로 확장하여 예측 불가능한 볼륨을 사전 프로비저닝 없이 처리한다. 이미지를 처리하지 않을 때 비용 없음.

**왜 A가 아닌가?** ASG의 EC2는 제로로 확장되지 않는다 — 최소 하나의 인스턴스가 항상 실행된다. S3를 롱 폴링하는 것은 기본 S3 이벤트 메커니즘이 아니다. 스파이크 워크로드에 Lambda보다 높은 비용.

**왜 C가 아닌가?** ECS Fargate는 작동하지만, 컨테이너 관리(ECR, 작업 정의)가 더 복잡하고 이 사용 사례에서 스파이크 워크로드에 Lambda보다 약간 더 높은 콜드 스타트 지연을 갖는다. Lambda가 이 사용 사례에 더 단순하다.

**왜 D가 아닌가?** 전용 EC2 인스턴스는 단일 장애 지점이고, 확장되지 않으며, 24/7 실행되며, 크론 기반 접근은 최대 60초의 감지 지연이 있다.

*SAA-C03 도메인: 탄력적 아키텍처 설계 — 태스크 2.1*

**연습 3 — 아키텍처 과제** *(선택 사항)*

Nimbus는 이전 날의 상위 10개 레스토랑을 주문량 기준으로 매일 새벽 5시에 일일 보고서를 생성하길 원한다. 보고서는 DynamoDB 데이터에서 생성되고, PDF로 포맷되어, S3에 저장되고, 모든 레스토랑 파트너에게 이메일로 전송된다.

이를 위한 전체 Lambda 기반 파이프라인을 설계하라. Lambda를 무엇이 트리거하는가? PDF 생성이 12분이 걸리면 어떻게 되는가? 5,000개의 레스토랑 파트너에게 이메일을 보내는 데 시간이 걸린다면? 하나의 Lambda를 사용하겠는가, 아니면 여러 개를 사용하겠는가?

*(단 하나의 정답은 없다. Lambda를 다른 서비스와 함께 구성하는 것을 연습하는 것이 목표다.)*
