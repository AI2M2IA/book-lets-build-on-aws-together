# 20장: 프리랜서 모델

조용한 수요일 오후였습니다. Priya가 모처럼 헤드폰을 벗었고, 사무실에는 모두가 집중하고 있지만 아무도 당황하지 않고 있음을 의미하는 그런 낮은 웅성거림이 있었습니다. Leo는 한 화면에 비용 대시보드를, 다른 화면에 EC2 인스턴스 목록을 열어두고 있었습니다.

온콜로 일하는 프리랜서를 생각해보십시오. 그들은 9시부터 5시까지 책상에 앉아 있지 않습니다. 그들은 기다립니다. 전화가 울리면, 일을 하고, 청구서를 보내고, 다시 기다리는 상태로 돌아갑니다. 일이 없으면, 비용도 없습니다. 요청이 폭주하면, 모든 것을 동시에 처리합니다. 여러분은 실제로 일한 시간에 대해서만 지불합니다 — 그들이 대기하며 보낸 시간이 아니라요.

그것이 이 챕터가 다루는 모델입니다.

여기에 붙잡아둘 만한 미묘함이 있습니다. 전통적인 모델은: 직원을 고용하고, 8시간에 대해 지불하고, 가변적인 산출물을 얻는 것입니다. 프리랜서 모델은: 전화가 울릴 때만 지불하고, 요청된 것을 정확히 얻는 것입니다. 예측 가능하고 일정한 수요를 가진 회사에게는, 직원 모델이 더 효율적입니다 — 전화가 끊임없이 울릴 것을 알기에, 시간당 지불이 동등하고 참여와 해제의 오버헤드가 없습니다. 가변적이고, 뾰족하거나, 드문 수요를 가진 회사에게는, 프리랜서 모델이 극적으로 더 저렴합니다.

AWS는 컴퓨팅에 대해 그 모델을 제공합니다 — 그리고 그것이 말이 되는지는 여러분의 수요 패턴에 달려 있습니다. 첫 번째 질문은 결코 "이 모델이 좋은가?"가 아니라 "내 워크로드가 실제로 어떤 모습인가?"입니다.

스타트업보다 큰 대부분의 워크로드의 경우: 혼합. 일부는 끊임없이 실행됩니다(API 서버, 데이터베이스). 일부는 트리거될 때만 실행됩니다(이벤트 처리, 보고서 생성, 이미지 크기 조정). 프리랜서 모델은 두 번째 범주를 위한 것입니다 — 그리고 Nimbus는 자신의 청구서 중 얼마나 많은 부분이 거기에 속하는지 막 발견하려 하고 있었습니다.

---

SQS/SNS 팬 아웃은 주문 흐름을 분리했지만, 그 큐들을 소비하는 작업자들은 여전히 시간당 요금을 부과하는 EC2 인스턴스에서 실행되었습니다 — 그들이 실제로 보낸 이메일 수와 관계없이요. 아키텍처는 옳았습니다. 비용 모델에는 여전히 누수가 있었습니다.

Priya가 먼저 그것을 알아챘습니다.

"이메일 서비스," 그녀가 말했습니다. "하루에 이메일을 몇 개 보내죠?"

Leo가 지표를 확인했습니다. "평균 하루 400개. 금요일 밤에 피크 약 1,200개."

"그리고 이메일 서비스를 실행하는 EC2 인스턴스 — 얼마나 오래 실행되나요?"

"항상요. 24시간 내내요."

"새벽 3시에 이메일을 0개 보낼 때도요?"

침묵.

Leo가 이메일 서비스 EC2 인스턴스의 CloudWatch CPU 그래프를 불러왔습니다. 그래프는 18시간의 연속 작동을 보여주었습니다. 금요일 피크에서: CPU 38%, 이메일 폭주를 처리. 자정 이후: CPU가 3%로 떨어졌습니다. 점심 주문이 시작될 때까지 거기 머물렀습니다.

18시간 내내 3% CPU. 인스턴스가 실행되고 있었습니다. 청구되고 있었습니다. 의미 있는 일은 아무것도 하고 있지 않았습니다.

"우리는 컴퓨터가 거기 앉아서 아무것도 안 하는 데 돈을 지불하고 있어요," Leo가 말했습니다.

"하루에 몇 시간이나요?"

더 많은 침묵.

"약 18시간이요."

Tom이 이제 매우 주의를 기울이고 있었습니다.

"그리고 이메일 서비스만이 아니에요," Priya가 덧붙였습니다. "레스토랑 사진을 위한 이미지 크기 조정 서비스는 대부분의 시간에 1% CPU로 실행돼요. 레스토랑이 새 메뉴를 업로드할 때만 급증해요. 그게, 뭐, 레스토랑당 하루에 몇 번 일어나죠?"

"맞아요," Leo가 확인했습니다.

"임시 파일을 삭제하는 야간 정리 작업 — 그건 새벽 2시에 4분간 실행되고 그러고 나서 23시간 56분 동안 완전히 유휴 상태로 앉아 있어요."

"그것도 맞아요."

패턴은 Nimbus의 모든 작은 서비스에 걸쳐 동일했습니다: 하루 24시간 비용을 지불한 컴퓨팅이 그중 일부에만 사용되는 것.

**서버가 항상 답은 아니다**

EC2 인스턴스는 영구적입니다. 하나를 시작하면 중지할 때까지 실행됩니다 — 하루 24시간, 주 7일, 실제 사용과 관계없이요. 모든 시간에 트래픽을 처리하는 웹 서버의 경우, 그것이 옳습니다. 이메일을 폭주로 보내고 그러고 나서 몇 시간 동안 유휴 상태인 이메일 서비스의 경우, 그것은 낭비입니다.

Auto Scaling Group은 비수요 시간에 이메일 서비스를 하나의 인스턴스로 축소할 수 있습니다. 하지만 하나의 인스턴스는 여전히 끊임없이 실행됩니다.

이것이 청구서를 볼 때 Tom이 계속 돌아오던 질문입니다: 각 서비스가 3% CPU의 그 18시간 동안 실제로 무엇을 하고 있었나? 기술적으로는, 아무것도 아닌 건 아닙니다 — 인스턴스는 대기하고, 이벤트를 확인하고, 상태를 유지하고 있었습니다. 하지만 비즈니스 관점에서는: 아무것도. 서비스는 가치를 전달하고 있지 않았습니다. 청구되고 있었습니다.

대부분의 시간에 진정으로 유휴 상태인 워크로드의 경우, 항상 켜져 있는 EC2 인스턴스는 주말에만 방문하는 아파트에 임대료를 내는 것입니다. 아파트는 여러분의 것이고; 임대료는 멈추지 않습니다.

프리랜서 모델은 이것을 완전히 해결합니다. 코드가 존재합니다. 그저 실행할 이유가 있기 전까지는 실행되지 않을 뿐입니다. 유휴 비용 없음. 예약 용량 없음. 전화 옆에서 대기하는 서버 없음.

그것이 **서버리스 컴퓨팅**의 전제입니다.

**AWS Lambda: 서버 없는 코드**

**AWS Lambda**는 서버를 프로비저닝하거나 관리하지 않고 이벤트에 대응하여 코드를 실행하게 해줍니다. 함수를 업로드하고, 무엇이 그것을 트리거하는지 지정하면, Lambda가 트리거가 발사될 때 그것을 실행합니다.

Lambda 함수:

- 영구적인 상태가 없습니다(각 호출은 독립적)
- 호출당 최대 15분 실행됩니다
- 0에서 수천 개의 동시 호출까지 자동으로 확장됩니다
- 실행 중일 때만 청구됩니다(실행 1ms당, 올림, 할당된 메모리 GB당)

트리거가 없으면, Lambda는 아무 비용도 들지 않습니다. 트리거가 발사되면, Lambda가 실행되고 청구됩니다. 10,000개의 트리거가 동시에 발사되면, Lambda는 10,000개의 동시 호출을 실행합니다. 확장은 자동이고 거의 즉각적입니다.

**이벤트 트리거: Lambda를 깨우는 것**

Lambda 함수는 스스로 실행되지 않습니다 — 그것들은 이벤트에 대응합니다. 일반적인 트리거에는 다음이 포함됩니다:

- **SQS 큐**: 큐에서 메시지를 처리합니다. Lambda가 큐를 폴링하고 메시지 배치로 함수를 호출합니다.
- **API Gateway**: HTTP 요청이 들어옵니다. API Gateway가 Lambda를 트리거합니다. Lambda가 응답을 생성합니다.
- **S3 이벤트**: 파일이 S3에 업로드됩니다. Lambda가 그것을 처리합니다(이미지 크기 조정, CSV 파싱, 문서 검증).
- **SNS**: 메시지가 토픽에 게시됩니다. Lambda가 알림을 받습니다.
- **DynamoDB Streams**: DynamoDB의 레코드가 변경됩니다. Lambda가 변경을 처리합니다.
- **CloudWatch Events(EventBridge)**: 예약된 이벤트(크론 작업 같은)가 정의된 시간에 실행됩니다.
- **ALB**: HTTP 요청이 로드 밸런서에 도착합니다. Lambda가 특정 경로를 처리할 수 있습니다.

Nimbus의 경우, 이메일 서비스가 자체 SQS 큐에 의해 트리거되는 Lambda 함수가 되었습니다. 큐에 메시지가 도착하면, Lambda가 메시지 내용으로 호출되고, SES(Simple Email Service)를 통해 이메일을 보내고, 종료됩니다.

서버 제로. 유휴 시간 제로. 유휴 시 비용 제로.

Lambda + SQS 패턴은 내재화할 가치가 있습니다: SQS가 큐, 내구성, 재시도 로직, DLQ를 처리합니다. Lambda가 처리를 다룹니다. 여러분은 SQS의 분리 이점을 Lambda의 제로로 확장하는 경제성과 함께 얻습니다. 어느 서비스도 다른 것의 일을 하지 않습니다. 그것들은 깔끔하게 구성됩니다.

"큐에 잘못된 형식의 메시지가 있으면 어떻게 되죠?" Priya가 물었습니다. "나쁜 입력이 계정의 다른 함수에 영향을 미치는 방식으로 Lambda를 충돌시킬 수 있나요?"

Lambda 호출은 서로 격리되어 있습니다. 충돌하는 함수가 다른 함수에 영향을 미치지 않습니다. 잘못된 형식의 메시지에서 처리되지 않은 예외를 던지는 Lambda: 메시지가 큐로 돌아가고, 구성된 한계까지 재시도되고, 그러고 나서 DLQ로 이동합니다. Lambda 자체는 다음 메시지를 위해 계속 사용 가능한 상태로 남습니다. Lambda 핸들러 내부의 입력 검증은 여전히 중요합니다 — 처리를 시도하기 전에 잘못된 형식의 데이터를 잡기 위해 — 하지만 하나의 나쁜 메시지가 함수를 무너뜨릴 수는 없습니다.

**콜드 스타트 문제**

Lambda 함수는 **실행 환경** — 작고 격리된 컨테이너에서 실행됩니다. 함수가 호출될 때:

1. AWS가 웜 실행 환경(최근 호출을 처리한 것)이 사용 가능한지 확인합니다
2. 웜이면: 함수가 즉시 실행됩니다
3. 콜드이면: AWS가 새 실행 환경을 초기화합니다 — 코드를 다운로드하고, 런타임을 시작하고, 초기화 코드를 실행한 다음 — 함수를 실행합니다

**콜드 스타트**는 런타임(Java와 .NET은 Python과 Node.js보다 더 긴 콜드 스타트를 갖습니다)과 코드 패키지의 크기에 따라 100ms에서 수 초의 지연을 추가합니다.

여러분은 궁금해할지 모릅니다: Lambda가 매번 처음부터 시작한다면, 그것이 이미 실행 중인 서버보다 더 느리게 만들지 않나요? 그렇습니다 — 때때로요. 그것이 콜드 스타트 문제이며, 시간에 민감한 사용자 대면 API에 중요합니다. 사용자가 이미 확인을 받은 백그라운드 작업에는 전혀 중요하지 않습니다. 백그라운드에서 실행되는 이메일 서비스의 200ms 콜드 스타트는 누구에게도 보이지 않습니다.

비동기 처리(이메일 전송, 이미지 크기 조정)의 경우, 콜드 스타트는 사용자에게 보이지 않습니다.

동기 API(사용자가 응답을 기다리는 HTTP 요청)의 경우, 콜드 스타트는 때때로 느린 응답을 유발할 수 있습니다.

**완화 방법**:

- **프로비저닝된 동시성**: 지정된 수의 실행 환경을 미리 예열합니다. 그것들은 항상 준비되어 있습니다. 그것들이 요청을 처리하지 않을 때조차 이에 대해 지불합니다.
- **더 작은 패키지 크기**: 더 작은 코드가 더 빠르게 초기화됩니다.
- **웜업 호출**: 함수를 웜하게 유지하기 위한 예약된 핑(일반적이지만 우아하지 않은 접근법).
- **올바른 런타임 선택**: Python과 Node.js가 Java보다 더 빠르게 콜드 스타트됩니다.

**실제 콜드 스타트 조사**

Lambda 마이그레이션 2주 후, Leo가 레스토랑 파트너로부터 Slack 메시지를 받았습니다: "주문 확인이 가끔 3초가 걸려요. 보통은 빨라요. 무슨 일이죠?"

Leo가 Lambda 함수의 CloudWatch 지표를 불러왔습니다. "Duration" 그래프에서, 그는 패턴을 볼 수 있었습니다: 15~20분 이상의 간격 후 첫 호출은 2,800~3,200밀리초로 급증하곤 했습니다. 이후 호출: 180~220밀리초.

전형적인 콜드 스타트.

그가 3초 호출 중 하나의 X-Ray 추적을 꺼냈습니다. 타임라인이 그것을 명확히 보여주었습니다:

- 초기화 단계: 2,640ms(함수 코드 다운로드, Node.js 런타임 시작, 모듈 수준 초기화 코드 실행)
- 핸들러 함수 실행: 290ms

초기화 단계가 문제였습니다. 그가 초기화 코드를 살펴봤습니다. 함수가 큰 SDK를 임포트하고, 데이터베이스 연결을 초기화하고, AWS Secrets Manager에서 구성을 로드하고 있었습니다 — 모두 시작 시에요.

"이 초기화의 일부는 실행 환경당 한 번만 일어나면 돼요," Leo가 말했습니다. "하지만 모든 콜드 스타트에서 일어나고 있어요."

그가 데이터베이스 연결을 핸들러 함수 밖에서 초기화하도록(웜 호출 전체에서 재사용되도록) Lambda 코드를 재구성하고 사용하지 않는 SDK 모듈을 제거하여 패키지 크기를 줄였습니다. 또한 전체 AWS SDK를 번들링하는 것에서 필요한 특정 서비스만 임포트하는 것으로 전환했습니다.

최적화 후:

- 콜드 스타트 기간: 1,100ms(여전히 존재하지만, 덜 심각)
- 웜 호출: 165ms

1.1초 콜드 스타트는 여전히 가끔 일어났습니다. 이메일 서비스의 경우(비동기, 사용자 대면 지연이 보이지 않음), 이것은 수용 가능했습니다. 레스토랑 알림 Lambda의 경우(고객 대면, 태블릿에서 주문), Priya가 프로비저닝된 동시성을 밀어붙였습니다: 항상 준비된 두 개의 미리 예열된 환경.

"그게 월 얼마나 들죠?" Tom이 물었습니다.

256MB의 프로비저닝된 동시성 환경 두 개: 월 약 $5.40. 지연 급증이 멈췄습니다.

**Lambda 가격: Tom이 웃은 이유**

Lambda 가격에는 두 가지 구성 요소가 있습니다:

1. **요청 요금**: 백만 호출당 $0.20
2. **기간 요금**: GB-초당 $0.0000166667(할당된 메모리 × 실행 초)

월간 첫 백만 요청은 무료입니다(항상, 첫 해에만이 아니라).

"그게 월 얼마나 들죠?" Tom이 Leo가 계산기를 열기도 전에 물었습니다.

Tom이 이메일 서비스에 대한 계산을 직접 했습니다:

- 매일이 금요일이라고 가정 — 최악의 경우: 하루 1,200개 이메일 × 30일 = 월 36,000 호출
- 각 호출은 256MB 메모리로 ~2초 걸림
- 기간: 36,000 × 2 × 0.25GB × $0.0000166667 = $0.30/월
- 요청: 36,000 << 1,000,000(무료 계층) = $0.00/월

"그리고 그 18,000 GB-초는 항상 무료인 400,000 GB-초의 기간 내에 잘 들어가요," Tom이 덧붙였습니다. "그러니까 실제 요금은 0일 거예요. 하지만 저는 일부러 무료 계층을 무시하고 있어요 — 실제 단위 비용을 알고 싶어요."

이메일 서비스를 위한 EC2 인스턴스: 월 $18.

"이미 배포했어요 — 아." Leo가 멈췄습니다. 그는 DLQ 구성을 마치기 전에 이메일 서비스 Lambda를 프로덕션에 푸시했습니다. "5분만 주세요."

Tom이 잠시 조용했습니다. 그러고 나서: "이걸 모든 것에 해야 해요."

**Lambda가 잘하는 것(그리고 잘 못하는 것)**

"잠깐 — 그런데 *왜* 그러면 모든 것에 그냥 Lambda를 쓰지 않죠?" Maya가 물었습니다. "더 저렴하고 자동으로 확장된다면, 함정이 뭐죠?"

"15분 제한이요," Leo가 말했습니다. "그리고 사용자 대면인 것에 대한 콜드 스타트요. 그리고 무상태성 — 호출 사이에 메모리에 아무것도 유지할 수 없어요."

워크로드가 뾰족하고, 이벤트 기반이며, 15분 안에 완료된다면, Lambda는 항상 켜져 있는 EC2 인스턴스의 일부 비용이 들 것입니다 — 하지만 워크로드가 15분 제한에 접근하거나 초과하는 장기 실행 데이터 처리 작업이라면, Lambda는 잘못된 도구이고 ECS, Batch, 또는 EC2 기반 접근법이 필요할 것입니다.

Lambda는 다음에 훌륭합니다:

- **이벤트 기반 처리**: 이벤트에 대응(파일 업로드, 큐 메시지, 예약된 작업)
- **단기 실행 작업**: 15분 내에 잘 완료되는 처리
- **뾰족하고, 예측 불가능한 트래픽**: Lambda가 0에서 수천으로 즉시 확장됩니다 — 사전 프로비저닝 없음
- **드문 작업**: 매일 새벽 2시에 실행되는 보고서. 매주 실행되는 정리 작업.
- **글루 코드**: 서비스 사이에 데이터를 이동하는 작은 함수

여러분은 궁금해할지 모릅니다: 10,000개의 이벤트가 갑작스럽게 동시에 도착하면 Lambda의 확장은 어떻게 되나요? Lambda의 기본 동시성 제한은 계정당 1,000개의 동시 실행입니다. 10,000개의 이벤트가 한 번에 도착하면, 최대 1,000개의 호출이 즉시 실행됩니다; 나머지는 SQS 큐에서 기다리고(SQS를 통해 트리거된 경우) 용량이 비워지면서 처리됩니다. 이것은 보통 큐 기반 처리에 괜찮습니다. 지연에 민감한 사용 사례의 경우, Lambda의 버스트 제한(새 동시 실행이 추가되는 초기 속도)이 갑작스러운 급증 동안 잠깐의 스로틀링을 유발할 수 있습니다 — 프로비저닝된 동시성이 용량을 미리 할당함으로써 이를 비껴갑니다.

현재 규모의 Nimbus 이메일 서비스의 경우, 1,000개의 동시 호출은 그들이 결코 필요로 할 것보다 훨씬 더 많았습니다. 하지만 그것에 부딪히기 전에 알아둘 만한 옳은 제약입니다.

Lambda는 다음에 좋지 않습니다:

- **장기 실행 프로세스**: 15분 제한이 단단한 벽입니다
- **상태가 있는 애플리케이션**: Lambda 함수는 설계상 무상태입니다 — 각 호출은 독립적
- **고처리량, 저지연 API**: 콜드 스타트가 지연 급증을 유발할 수 있습니다; 프로비저닝된 동시성이 이를 완화하지만 비용을 추가합니다
- **영구적 연결이 필요한 애플리케이션**: Lambda는 장기간 살아 있는 데이터베이스 연결 풀을 쉽게 유지할 수 없습니다(RDS Proxy 같은 연결 풀링 도구가 도움이 되지만)
- **전통적인 웹 서버**: 가능하지만, 자연스러운 적합은 아닙니다

**15분 벽: Lambda가 잘못된 도구일 때**

마이그레이션 3주 후, Leo가 워크로드 하나를 더 Lambda로 옮기려 했습니다: 야간 분석 보고서 생성기. 그것은 데이터베이스에서 주문 데이터를 가져와, 레스토랑 메타데이터와 조인하고, 통계를 계산하고, PDF를 생성했습니다.

첫날 밤, Lambda 호출이 타임아웃 오류로 실패했습니다.

"보고서 생성이 17분 걸렸어요," Leo가 다음날 아침 말했습니다.

"Lambda의 최대치는 15예요," Priya가 말했습니다.

"네. 이제 그걸 알아요."

그는 평균 처리 시간(8분)을 확인하고 Lambda가 작동할 것이라고 가정했습니다. 그는 꼬리를 확인하지 않았습니다 — 데이터 볼륨이 더 높고 쿼리가 더 오래 걸린 밤들을요. 그런 밤에는, 15분이 충분하지 않았습니다.

"그러면 보고서는 그냥... 생성 안 되는 거예요?" Maya가 물었습니다.

"맞아요. 오류 알림 없음. 부분 보고서 없음. 그냥 침묵."

"이미 배포했어요 — 아," Leo가 말했습니다.

이것은 Lambda가 우아하지 않게 실패하는 특정한 방식 중 하나였습니다: 타임아웃이 출력을 내지 않고, 애플리케이션에 오류 메시지도 없고, 그냥 CloudWatch 오류 로그만 냅니다. Lambda 타임아웃 오류를 특별히 모니터링하지 않으면, 며칠 동안 알아차리지 못할 수 있습니다.

해결책: 보고서 생성기를 ECS Fargate로 옮기는 것 — 서버를 관리하지 않는 컨테이너; 다음 챕터 — 그것은 시간 제한이 없습니다. Lambda는 가끔이라도 15분을 초과할 수 있는 워크로드에는 잘못된 도구였습니다. 교훈은 "Lambda가 나쁘다"가 아니었습니다. 교훈은 "Lambda는 그것의 제약 안에 맞는 워크로드에 옳은 도구이고 — 그렇지 않을 때 놀라운 실패의 원천이다"였습니다.

**RDS Proxy: Lambda를 위한 연결 풀링**

Lambda의 무상태 본성은 특정한 데이터베이스 문제를 만듭니다.

EC2 인스턴스가 RDS에 연결할 때, 그것은 영구적인 연결 풀을 유지합니다. 애플리케이션이 풀에서 연결을 재사용합니다. RDS는, 말하자면, 200개의 동시 연결을 처리할 수 있습니다.

Lambda가 500개의 동시 호출을 처리할 때, 각 호출이 자신의 데이터베이스 연결을 열려고 시도합니다. 그것은 500개의 새 연결입니다 — 200개를 지원하는 데이터베이스를 압도합니다.

**Amazon RDS Proxy**는 Lambda 함수와 RDS 사이에 앉아, 영구적인 연결 풀을 유지하고 Lambda의 단명 연결을 그것을 통해 다중화합니다.

다음 대신: Lambda 호출 → 새 RDS 연결(500개의 동시 호출 각각에 대해)

RDS Proxy와 함께: Lambda 호출 → RDS Proxy → 20개의 영구적인 RDS 연결 풀

"프록시는 RDS 자격 증명이 필요해요," Priya가 말했습니다. "그것들은 어디에 사나요? 그것이 저장하나요?"

RDS Proxy는 자격 증명을 Secrets Manager에 저장하고 자동으로 교체합니다. Lambda 함수의 IAM 역할은 그것에게 RDS 자격 증명에 직접이 아니라 프록시에 대한 액세스를 부여합니다(IAM 인증 사용). 자격 증명은 결코 Lambda 코드에 노출되지 않습니다.

"그러니까 Lambda 함수가 IAM을 통해 인증하고," Leo가 확인했습니다, "프록시가 실제 데이터베이스 자격 증명을 처리하는군요."

Nimbus의 주문 처리 Lambda(주문 검증을 위해 RDS를 쿼리하는 것)의 경우, RDS Proxy가 피크 금요일 트래픽 동안 연결 풀 고갈을 제거했습니다.

**Lambda Layers: 공유 종속성**

이메일 서비스 Lambda, 알림 Lambda, 보고서 Lambda 모두 같은 내부 라이브러리 코드를 공유했습니다: 통화 포맷팅, 입력 정제, 표준 형식으로 로깅을 위한 유틸리티 함수.

Lambda Layers 없이는, 그 공유 코드가 각 함수의 배포 패키지에 번들링되어야 했습니다. 세 개의 함수, 같은 2MB 라이브러리의 세 개 사본. 라이브러리가 업데이트되면, 세 함수 모두 새 배포가 필요했습니다.

**Lambda Layers**는 Lambda 함수가 런타임에 참조할 수 있는 별도의 패키지입니다. 공유 라이브러리가 레이어로 추출되었습니다. 세 함수가 레이어를 참조했습니다. 공유 라이브러리 업데이트는 레이어 버전을 업데이트하는 것을 의미했습니다 — 세 함수를 모두 재배포하는 것이 아니라요.

추가 이점: 더 작은 개별 함수 패키지는 더 빠른 콜드 스타트를 의미합니다.

"레이어가 바꾸지 않는 한 가지: 실행 역할," Priya가 말했습니다. "Lambda가 너무 넓은 권한을 가지면, 손상된 함수가 계정의 모든 것에 액세스할 수 있어요."

"EC2 역할과 같은 원칙이에요," Leo가 말했습니다. "최소 권한. 각 Lambda는 실제로 필요한 권한만 받아요."

"그러니까 Lambda는 EC2의 대체물이 아니에요," Maya가 말했습니다. "다른 작업을 위한 다른 도구예요."

"Nimbus 웹 API는 EC2 또는 ECS에 남아요," Leo가 확인했습니다. "이메일 서비스, 이미지 리사이저, 야간 보고서 생성기, 로그 클리너 — 그것들은 Lambda로 이동해요."

**서버리스 철학**

Lambda는 더 넓은 개념의 일부입니다: **서버리스** — 서버를 관리하지 않고 코드만 관리하는 애플리케이션을 구축하는 것.

완전한 서버리스 Nimbus 스택은 이렇게 보일 수 있습니다:

- API Gateway + Lambda(웹 서버가 있는 EC2 대신)
- DynamoDB(RDS 대신 — 또한 서버리스, 서버 관리 없음)
- S3(정적 자산 — 본질적으로 서버리스)
- SNS + SQS(메시징 — 서버리스)
- Lambda(모든 백그라운드 처리)

매력: 코드를 작성하면; AWS가 다른 모든 것을 관리합니다. 패치 없음, 확장 구성 없음, 용량 계획 없음.

## Amazon API Gateway

Lambda 트리거 목록이 API Gateway를 간단히 언급했습니다: HTTP 요청이 들어오고, API Gateway가 Lambda를 트리거합니다. 그것은 정확하지만, API Gateway가 실제로 무엇인지를 과소평가합니다.

"잠깐 — 그런데 *왜* Lambda 앞에 API Gateway를 두죠?" Maya가 물었습니다. "Lambda가 그냥 HTTP 요청을 직접 받을 수 없나요?"

Lambda는 함수 URL — 단순하고 직접적인 HTTPS 엔드포인트 — 을 통해 HTTP 요청을 받을 수 있습니다. 하지만 그것은 라우팅, 인증, 스로틀링, 캐싱, 또는 요청 변환을 처리하지 않습니다. 프로덕션 API의 경우, 그 관심사들은 백엔드가 Lambda이든 EC2이든 관계없이 존재합니다.

**Amazon API Gateway**는 어떤 규모에서든 API를 생성, 배포, 관리하기 위한 완전 관리형 서비스입니다. 그것은 트래픽 관리, 인증, 스로틀링, 캐싱, 모니터링을 처리하여 여러분의 Lambda 함수(또는 EC2, 또는 모든 HTTP 백엔드)가 그것들을 직접 구현하지 않아도 되게 합니다.

**세 가지 API 유형:**

**REST API**는 가장 기능이 풍부한 옵션입니다. 그것은 요청 및 응답 변환, 응답 캐싱, API 키에 연결된 사용 계획, 그리고 모든 인증 유형을 지원합니다. API Gateway를 언급하는 대부분의 SAA-C03 시험 문제는 REST API를 포함합니다.

**HTTP API**는 더 단순하고 더 저렴합니다 — REST API보다 대략 70% 적은 비용. 그것은 Lambda 백엔드와 HTTP 프록시를 위해 설계되었습니다. OIDC와 OAuth 2.0 인증을 지원하지만 요청 변환이나 캐싱은 지원하지 않습니다. REST API의 고급 기능이 필요 없다면, HTTP API가 옳은 선택입니다.

**WebSocket API**는 영구적인 양방향 연결을 관리합니다. API Gateway가 연결 수명 주기를 처리하고 메시지 내용에 기반해 Lambda로 메시지를 라우팅합니다. Lambda 함수는 소켓 상태를 관리할 필요가 없습니다 — API Gateway가 그것을 합니다.

**인증 옵션**(시험이 테스트하는 것들):

**Cognito 사용자 풀 인증자**는 Cognito 사용자 풀의 JWT를 검증합니다. Lambda가 필요 없습니다. API Gateway가 토큰 자체를 확인합니다. 그것이 유효하면, 요청이 통과합니다.

**Lambda 인증자**는 토큰을 검증하기 위해 여러분 자신의 Lambda 함수를 실행합니다 — 커스텀 JWT, 서드파티 자격 증명 공급자의 OAuth 토큰, 독점 형식의 API 키. Lambda가 IAM 정책을 반환합니다. 정책이 동작을 허용하면, 요청이 진행됩니다.

**API 키**는 요청 헤더에 전달되는 단순한 키입니다. API 키는 인증이 아니라 클라이언트별 속도 제한을 위한 것입니다. 그것들을 보안 메커니즘으로 사용하지 마십시오 — 그것들은 비밀이 아니라, 식별자입니다.

**스로틀링과 사용 계획:**

기본적으로, API Gateway는 계정 수준에서 초당 10,000개의 요청을 허용하고(소프트 제한), 5,000개의 버스트를 허용합니다. 그것을 초과하면 클라이언트가 `429 Too Many Requests`를 받습니다 — 여러분의 백엔드는 그것을 느끼지조차 않습니다. 클라이언트별 제한이 필요할 때, 사용 계획을 만듭니다: 그것을 API 키에 첨부하고, 요청 속도와 일일 또는 월간 할당량을 설정합니다. 한 클라이언트의 버스트가 다른 클라이언트의 할당을 소비하지 않습니다.

기억할 만한 두 숫자: 최대 페이로드는 **10 MB**이고, 기본 통합 타임아웃은 **29초**입니다 — 백엔드가 더 오래 걸리면, 게이트웨이가 포기합니다. (2024년부터, 그 타임아웃은 할당량 증가를 통해 리전 및 프라이빗 REST API에 대해 29초를 넘어 상향될 수 있습니다 — 하지만 29초 기본값이 여전히 시험이 기대하는 것입니다.) API Gateway는 장기 실행 작업이 아니라 요청/응답 API를 위한 것입니다; 그런 작업의 경우, 작업을 SQS나 Step Functions에 넘기고 즉시 응답하십시오.

"이게 월 얼마나 들죠?" Tom이 물었습니다.

REST API의 경우: 백만 API 호출당 $3.50, 더하기 데이터 전송 GB당 $0.09. 소규모에서 중규모 트래픽의 경우, 본질적으로 무료입니다. 대량 API의 경우, HTTP API의 더 낮은 가격대가 의미 있어집니다.

Leo가 그가 앞서 쓴 Lambda 트리거 목록을 가리켰습니다. "그러니까 API Gateway는 그냥 Lambda를 트리거하는 방법이 아니에요. 그것은 Lambda를 진짜 API처럼 느끼게 만드는 거예요."

"Lambda 함수가 비즈니스 로직을 처리해요," Priya가 말했습니다. "API Gateway가 그 앞의 모든 것을 처리해요 — 라우팅, 인증, 스로틀링, 모니터링. 각각이 한 가지를 해요."

"그러면 누군가 API Gateway를 우회해서 Lambda를 직접 호출하려 하면 어떻게 되죠?"

"Lambda 실행 정책이 API Gateway로부터의 호출만 허용해요," Priya가 말했습니다. "Lambda의 리소스 기반 정책이 다른 모든 것을 거부해요."

현실: 서버리스는 자체적인 운영 복잡성을 갖습니다 — 분산 Lambda 함수 디버깅, 콜드 스타트 관리, 동시성 제한 이해. 그것은 더 단순하지 않고, 그저 다를 뿐입니다.

"잠깐 — 그런데 *왜* 서버리스가 '더 단순하지 않죠'?" Maya가 물었습니다. "전체 홍보는 그것이 운영 부담을 제거한다는 거잖아요."

"그것은 일부 운영 부담을 제거해요," Leo가 말했습니다. "인프라 프로비저닝, 패치, 확장 구성 — 그것들은 사라져요. 남는 것은 다른 거예요: 콜드 스타트 관리, SSH할 수 없는 함수 전체의 분산 추적, 동시성 제한, 함수 버전과 별칭 관리, 레이어 업데이트가 어떻게 전파되는지 이해하기, 15분 타임아웃을 우아하게 다루기."

"그러니까 부담이 이동하는 거네요," Priya가 말했습니다. "인프라 운영에서 함수 운영으로."

"네. 많은 워크로드 — 특히 이벤트 기반, 작은, 뾰족한 것 — 의 경우, 그게 더 나은 거래예요. 엔지니어가 상호작용하고 디버깅해야 하는 장기 실행 애플리케이션 서버의 경우, EC2나 컨테이너가 종종 옳은 선택으로 남아요."

여러분은 궁금해할지 모릅니다: 서버리스가 미래이고, 결국 모든 것이 Lambda로 옮겨가야 하나요? 정직한 답은 워크로드에 달려 있다는 것입니다. 서버리스는 이벤트 기반 처리를 지배해 왔습니다. HTTP API(API Gateway + Lambda를 통해)에서 상당한 진전을 이뤘습니다. 그것은 항상 켜져 있는 애플리케이션 서버, 장기 실행 배치 처리, 또는 상태가 있는 서비스를 대체하지 않았습니다 — 그리고 아마 그러지 않을 것입니다. 그 사용 사례들이 Lambda의 모델에서 이익을 얻지 못하기 때문입니다. 옳은 도구 질문은 결코 사라지지 않습니다; 그것은 그저 시간이 지나면서 다른 옵션에 적용될 뿐입니다.

## 장점과 한계

**Lambda가 강력한 이유**:

- 진정한 사용당 지불 — 유휴 시 비용 제로
- 구성 없는 자동 확장
- 패치하거나 유지 보수할 서버 없음
- 관대한 무료 계층(월 백만 요청, 영원히 무료)
- AWS 나머지와의 긴밀한 통합
- RDS Proxy와 Lambda Layers는 가장 흔한 Lambda 고충점 두 가지(연결 풀링과 코드 공유)를 아키텍처 변경 없이 해결합니다

**복잡해지는 부분**:

- 콜드 스타트는 실재하며 지연에 민감한 워크로드에 주의 깊은 처리가 필요합니다
- 15분 실행 제한이 장기 실행 작업을 제외합니다
- 디버깅이 더 어렵습니다 — SSH할 영구 서버가 없습니다
- 무상태 설계는 모든 상태를 외부화해야 합니다(데이터베이스, 캐시, S3)
- 동시성 제한(계정당 기본 1,000 동시 호출)이 대규모에서 스로틀할 수 있습니다
- VPC 연결 Lambda 함수는 추가 지연과 콜드 스타트 문제를 갖습니다

**SSH 없이 Lambda 모니터링하기**

Lambda 함수에서 무언가가 처음 고장났을 때, Leo의 본능은 SSH로 들어가 프로세스를 보는 것이었습니다. SSH로 들어갈 프로세스가 없습니다. Lambda의 실행 환경은 일시적이고 접근 불가능합니다.

Lambda 디버깅은 다른 도구 모음을 배우는 것을 요구합니다:

**CloudWatch Logs**: 모든 Lambda 호출이 그것의 stdout/stderr를 CloudWatch 로그 그룹에 씁니다. 구조화된 로깅(JSON 형식)이 이것들을 필터링 가능하게 만듭니다. 가장 유용한 필드: 함수 이름, 호출 ID, 기간, 오류 유형, 그리고 여러분의 커스텀 상관관계 ID.

**CloudWatch Metrics**: Lambda가 Invocations, Duration, Errors, Throttles, ConcurrentExecutions 지표를 자동으로 게시합니다. Errors와 Throttles에 알람을 설정하는 것은 어떤 Lambda 배포에서든 첫날이어야 합니다.

**AWS X-Ray**: Lambda를 위한 분산 추적. 작은 오버헤드(호출당 2~5ms)를 추가하지만 함수 내부에서 시간이 어디에 쓰이는지의 플레임 그래프를 제공합니다. 콜드 스타트 분석에 필수적입니다 — X-Ray가 핸들러 단계와 별도로 초기화 단계를 보여줍니다.

**Lambda Insights**: Lambda를 위한 향상된 모니터링, CloudWatch Lambda Insights를 통해 사용 가능. 표준 지표에 메모리 사용량, CPU 시간, 초기화 기간을 추가합니다. 약간의 추가 비용이 들지만 프로덕션 함수에는 그만한 가치가 있습니다.

"그러면 누군가 실행 환경을 통해 침입하려 하면 어떻게 되죠?" Priya가 물었습니다. "Lambda 함수는 격리된 컨테이너에서 실행되지만, 종속성에 취약점이 있으면, 공격자가 우리 Lambda 내부에서 코드 실행을 얻을 수 있나요?"

완화 방법: 종속성을 최소한으로 그리고 최신으로 유지하고(콜드 스타트 분석이 이미 Leo가 패키지 크기를 줄이도록 밀어붙였습니다), 공유 라이브러리를 버전화하기 위해 Lambda Layers를 사용하고, Lambda 실행 역할에 최소 필요 권한을 부여합니다. 함수가 하나의 특정 S3 버킷에만 쓸 수 있고 하나의 특정 DynamoDB 테이블만 쿼리할 수 있다면, 손상된 함수의 폭발 반경은 정확히 그것으로 제한됩니다.

"Lambda 실행 역할에 대한 최소 권한은 선택 사항이 아니에요," Priya가 말했습니다. "그것은 무언가가 잘못될 때 피해를 제한하는 거예요."

그녀가 옳았습니다. 그리고 대부분의 보안 조언처럼, 그것은 또한 그저 좋은 엔지니어링이기도 했습니다.

## 요약

19장의 SQS/SNS 아키텍처는 작업을 수락하는 것과 그것을 처리하는 것의 관심사를 분리했습니다. Lambda는 그것을 더 멀리 가져갑니다: 그것은 작업을 처리하는 것과 그것을 할 용량에 대해 지불하는 것의 관심사를 분리합니다.

- **AWS Lambda**는 서버를 관리하지 않고 이벤트에 대응하여 코드를 실행합니다.
- **사용당 지불**: 호출당 및 실행 1ms당(올림) 청구. 유휴 시 비용 제로.
- 0에서 수천 개의 동시 호출까지 자동으로 확장합니다.
- **콜드 스타트**: 웜 실행 환경이 없을 때 초기화 지연. 프로비저닝된 동시성 또는 경량 런타임으로 완화됨.
- **Lambda Layers**: 여러 함수가 참조할 수 있는 공유 코드 패키지로, 중복과 패키지 크기를 줄입니다.
- **RDS Proxy**: Lambda와 RDS 사이에 영구적인 데이터베이스 연결 풀을 유지하여 Lambda의 연결 고갈 문제를 해결합니다.
- **모니터링**: CloudWatch Logs, Metrics, X-Ray 추적, Lambda Insights를 사용하십시오 — SSH할 서버가 없습니다.
- 다음에 가장 적합: 이벤트 기반, 단기 실행, 뾰족한, 또는 드문 워크로드.
- 다음에는 이상적이지 않음: 장기 실행 작업(15분 단단한 제한), 상태가 있는 애플리케이션, 프로비저닝된 동시성 없는 고처리량 저지연 API.
- **서버리스**는 설계 철학입니다 — 인프라가 아니라 코드를 관리합니다. 운영 복잡성은 이동하지, 사라지지 않습니다.

## 시험 팁

*SAA-C03 도메인: 탄력적 아키텍처 설계(도메인 2, 태스크 2.1)*

- **Lambda + S3**: 고전적 패턴 — S3에 업로드된 파일이 처리(썸네일 생성, 바이러스 스캔, 데이터 변환)를 위해 Lambda를 트리거합니다. 서버 필요 없음.
- **Lambda + SQS**: Lambda가 SQS를 폴링하고 배치를 처리합니다. SQS가 재시도/DLQ 메커니즘을 제공합니다. Lambda가 처리를 제공합니다.
- **Lambda + API Gateway**: 서버리스 HTTP API. API Gateway가 라우팅, 인증, 스로틀링을 처리합니다. Lambda가 비즈니스 로직을 처리합니다.
- **API Gateway 유형:** REST API = 전체 기능, 요청 변환, 캐싱, 사용 계획. HTTP API = 더 단순, 더 저렴, OIDC/OAuth만. WebSocket API = 영구적 양방향 연결. **인증:** Cognito 인증자 = Cognito JWT를 네이티브로 검증. Lambda 인증자 = 커스텀 토큰 검증 로직. API 키 = 클라이언트별 속도 제한(인증 아님). 시험 트리거: "서버리스 REST API" → API Gateway + Lambda.
- **콜드 스타트 신호**: "첫 요청에서 지연 급증," "일관되지 않은 응답 시간" → 콜드 스타트. 해결책: 프로비저닝된 동시성(비용이 듦), 더 작은 패키지, 더 가벼운 런타임.
- **실행 제한**: 최대 15분. 최대 10GB 메모리. 기본 512MB /tmp 임시 스토리지(최대 10GB까지 구성 가능). 이 제한들이 시험 시나리오에 나타납니다.
- **Lambda 타임아웃 오류는 조용함**: Lambda 함수가 타임아웃되면, CloudWatch 오류를 내지만 애플리케이션 수준 오류 응답은 내지 않습니다. CloudWatch Lambda 타임아웃 오류를 명시적으로 모니터링하십시오. 이것이 Leo의 17분 보고서 생성기가 어떤 애플리케이션 수준 알람도 없이 첫날 밤에 실패한 방식입니다.
- **VPC Lambda 콜드 스타트**: VPC 내부의 Lambda 함수는 추가 콜드 스타트 지연(ENI 프로비저닝)을 갖습니다. AWS가 Hyperplane ENI로 이를 크게 개선했지만, VPC Lambda 콜드 스타트는 여전히 비VPC보다 느립니다. VPC 리소스가 필요 없는(즉, RDS, ElastiCache, 또는 다른 VPC 전용 리소스에 연결하지 않는) Lambda 함수에는 VPC를 피하십시오.
- **Lambda 동시성**: 계정당 기본 1,000 동시 실행(늘릴 수 있음). **예약된 동시성**: 함수가 특정 수의 실행을 받도록 보장합니다; 다른 함수가 그것들을 소비하는 것을 방지합니다. **프로비저닝된 동시성**: 다수의 실행 환경을 미리 예열합니다.
- **이벤트 소스 매핑**: SQS/DynamoDB Streams/Kinesis를 Lambda에 연결하는 Lambda 기능. Lambda가 소스를 폴링하고 레코드를 배치합니다.
- **계정 제한에 부딪힘**: "애플리케이션이 확장하면서 스로틀됨 / LimitExceeded" → **Service Quotas**에서 제한을 확인하고 거기서 증가를 요청하십시오(Lambda 동시성 같은 많은 할당량이 조정 가능합니다; 일부는 단단한 제한입니다).
- **RDS Proxy**: 시험 신호: "Lambda 함수가 너무 많은 데이터베이스 연결을 일으킴," "Lambda로 인한 연결 풀 고갈." → RDS Proxy가 영구적 연결을 유지하고 Lambda의 단명 연결을 다중화합니다.
- **Lambda Layers**: 시험 신호: "여러 Lambda 함수에 걸쳐 코드 공유," "배포 패키지 크기 줄이기" → Lambda Layers.
- **Lambda + X-Ray**: Lambda를 위한 분산 추적. 시험 시나리오: "여러 Lambda 함수와 서비스에 걸쳐 요청 추적" → Lambda에서 X-Ray 추적 활성화.
- **Lambda Destinations:** 비동기 Lambda 호출의 경우, 성공과 실패 결과 모두에 대해 Destination을 구성할 수 있습니다. 성공 결과를 SQS, SNS, EventBridge, 또는 다른 Lambda 함수로 보냅니다. 실패를 알림을 위해 SQS나 SNS로 보냅니다. 이것은 실패만이 아니라 성공과 실패 모두를 포착하기 때문에 비동기 호출에 대해 DLQ보다 선호되는 대안입니다. 시험 신호: "성공한 Lambda 결과를 다른 서비스로 라우팅" 또는 "비동기 Lambda로부터 성공과 실패 결과 모두 포착" → Lambda Destinations. "비동기 호출에 대해 실패한 메시지만 포착" → DLQ도 여전히 유효하지만 Destinations가 더 완전한 솔루션입니다.

**연습 2 — SAA-C03 시나리오**

*시나리오*: 회사가 S3 버킷을 통해 공급업체로부터 제품 이미지를 받습니다. 각 이미지는 네 가지 표준 크기(썸네일, 소형, 중형, 대형)로 크기 조정되어 S3에 다시 저장되어야 합니다. 볼륨이 예측 불가능합니다 — 어떤 날은 10개 이미지, 어떤 날은 100,000개. 처리는 이미지당 10분 내에 완료되어야 합니다. 비용이 최소화되어야 합니다.

이 요구사항을 가장 잘 충족하는 아키텍처는 무엇입니까?

A) S3 버킷을 롱 폴링으로 모니터링하는 Auto Scaling Group의 EC2 인스턴스  
B) 새 이미지를 위해 매분 S3를 확인하는 크론 작업이 있는 전용 EC2 인스턴스  
C) SQS 큐에 의해 트리거되는 ECS Fargate 태스크, S3 이벤트가 큐에 게시  
D) 이미지를 크기 조정하고 결과를 S3에 저장하는 Lambda 함수를 트리거하는 S3 이벤트 알림

**힌트 1**: 예측 불가능한 볼륨은 제로로 확장하는 것을 선호합니다. 어떤 옵션이 그것을 합니까?

**힌트 2**: 이미지당 10분은 Lambda의 15분 제한 내에 있습니다. 이미지 크기 조정 작업이 Lambda의 제약에 맞는지 확인하십시오.

**힌트 3**: 24시간 내내 실행되는 전용 EC2 인스턴스는 비싸고 확장되지 않습니다.

**정답**: D

**설명**: S3 이벤트 알림이 이미지가 업로드될 때 Lambda를 트리거합니다. Lambda가 이미지를 네 가지 크기로 조정하고 결과를 S3에 저장합니다. Lambda는 0에서 수천 개의 동시 호출까지 자동으로 확장하여 사전 프로비저닝 없이 예측 불가능한 볼륨을 처리합니다. 이미지를 처리하지 않을 때 비용 제로.

**왜 A가 아닌가?** ASG의 EC2는 제로로 확장되지 않습니다 — 최소 하나의 인스턴스가 항상 실행됩니다. S3를 롱 폴링하는 것은 네이티브 S3 이벤트 메커니즘이 아닙니다. 뾰족한 워크로드에 대해 Lambda보다 높은 비용.

**왜 B가 아닌가?** 전용 EC2 인스턴스는 단일 장애 지점이고, 확장되지 않으며, 24시간 내내 실행되며, 크론 기반 접근법은 최대 60초의 감지 지연이 있습니다.

**왜 C가 아닌가?** ECS Fargate는 작동하지만, 더 복잡하고(컨테이너 관리, ECR, 태스크 정의 필요) Fargate 태스크 시작은 수십 초에서 분이 걸립니다 — Lambda 콜드 스타트보다 훨씬 느립니다 — 뾰족한, 이벤트 기반 작업에 부적합하게 만듭니다. Lambda가 이 사용 사례에 더 단순합니다.

*SAA-C03 도메인: 탄력적 아키텍처 설계 — 태스크 2.1*

**연습 3 — 아키텍처 과제** *(선택 사항)*

Nimbus는 이전 날의 주문량 기준 상위 10개 레스토랑이 담긴 일일 보고서를 새벽 5시에 생성하기를 원합니다. 보고서는 DynamoDB 데이터에서 생성되어, PDF로 포맷되고, S3에 저장되고, 모든 레스토랑 파트너에게 이메일로 전송됩니다.

또한 고려하십시오: Lambda가 5,000개 중 4,500개의 레스토랑 이메일을 처리한 후 14분에 타임아웃되면 어떻게 됩니까? Lambda가 재시도될 때 중복 이메일을 보내는 것을 어떻게 피합니까? 이 Lambda는 어떤 IAM 권한이 필요하며, 최소 필요 집합은 무엇입니까?
