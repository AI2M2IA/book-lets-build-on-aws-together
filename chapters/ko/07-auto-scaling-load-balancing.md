# 7장: 바빠지면 커지는 레스토랑

오류율이 12%를 넘은 것은 금요일 저녁 7시 43분이었다.

Tom이 먼저 알아챘는데 Tom은 항상 먼저 알아챘다. 그는 다른 사람들이 소셜 미디어를 확인하듯 — 반사적으로, 지속적으로, 의도하지 않고 — 새로고침하는 CloudWatch 대시보드 탭을 열어두고 있었다.

"Leo," 그가 말했다.

Leo는 이미 보고 있었다. 응답 시간: 오르고 있다. 큐에 쌓인 요청: 오르고 있다. 단일 EC2 인스턴스 — 지난달 업그레이드한 더 큰 것조차 — 가 CPU 94%였다.

"고객들을 돌려보내고 있어," Tom이 말했다.

"돌려보내는 게 아니야," Leo가 말했다. "서버가 그러는 거야."

"같은 거야."

그랬다. 그리고 3주 동안 매주 금요일마다 그래왔다. Nimbus는 스토리지 위기에서 살아남았다 — 데이터베이스는 자체 디스크를 갖고, 사진은 S3에 있었다 — 하지만 안정적인 것과 확장 가능한 것은 완전히 다른 문제다. 시스템이 작동했다. 그냥 성장하지 않았을 뿐이다.

팀은 가변 부하를 자동으로 처리하는 시스템이 필요했다. 최악의 경우를 위해 충분한 서버를 사서 조용한 시간에 돈을 낭비하는 것도 아니고. 트래픽 급증이 발생할 때 수동으로 허둥대는 것도 아니었다.

이를 위한 패턴이 있다. AWS에는 두 가지 서비스가 이를 구현한다.

**개념: 수평 확장**

시스템이 더 많은 부하를 처리하게 하는 두 가지 방법이 있다.

**수직 확장**은 단일 서버를 더 크게 만드는 것을 의미한다. 더 많은 CPU. 더 많은 RAM.
4장에서 `t3.micro`에서 `t3.large`로 업그레이드할 때 이것을 했다. 도움이 된다.
하지만 한계가 있다: 얼마나 크게 갈 수 있는지 제한이 있고, 크기 조정하려면 인스턴스를 재시작해야 하며, 여전히 단일 장애 지점이 있다.

**수평 확장**은 더 많은 서버를 추가하는 것을 의미한다. 하나의 대형 서버 대신,
다섯 개의 중간 서버를 실행한다. 트래픽이 감소하면 두 개를 실행한다. 급증하면 열 개를 실행한다.

수평 확장은 수직 확장이 갖지 않는 장점이 있다:

- 단일 장애 지점 없음. 하나의 서버가 죽으면, 나머지가 계속 제공한다.
- 용량을 추가하기 위해 재시작 불필요.
- 사용한 것만 지불 — 필요할 때 서버를 추가하고, 필요 없을 때 제거한다.
- 선형 확장: 서버 두 배, 처리량 대략 두 배.

문제: 여러 서버가 있으면, 사용자는 어느 것과 통신해야 하는지 어떻게 알아야 하는가?

**Application Load Balancer: 문 하나, 방 여러 개**

**Application Load Balancer**(ALB)는 애플리케이션의 앞문이다.

사용자가 로드 밸런서에 연결한다. 로드 밸런서가 들어오는 요청을 EC2 인스턴스 플리트에 걸쳐 배포한다. 각 사용자는 하나의 주소(로드 밸런서의 URL)를 본다. 그 주소 뒤에서, 요청은 실행 중인 서버가 몇 개이든 걸쳐 분산된다.

큰 레스토랑의 안내 데스크 같다고 생각하라. 손님이 도착하면 안내원이 이용 가능한 테이블로 안내한다. 안내원은 어떤 테이블이 바쁘고 어떤 것이 비어 있는지 알고 있다. 손님은 테이블이 몇 개인지 알 필요가 없다 — 그냥 들어오면 안내원이 배분을 처리한다.

ALB는 웹 요청으로 이것을 한다. 들어오는 각 HTTP 요청을 받아 어떤 EC2 인스턴스(**타겟**이라고 부른다)가 처리해야 하는지를 다음과 같은 요소를 기반으로 결정한다:

- 라운드 로빈(각 서버가 순서대로 차례를 갖는다)
- 최소 미해결 요청(가장 적은 진행 중인 요청을 가진 서버가 다음 요청을 받는다)
- 상태 — 정상 타겟만 트래픽을 받는다

**상태 확인**이 필수적이다. ALB는 각 타겟에 정기적으로 테스트 요청을 보낸다.
타겟이 올바르게 응답하지 않으면, ALB는 그것을 비정상으로 표시하고 트래픽 전송을 중단한다. 타겟이 복구되면, 트래픽이 재개된다.

이것은 자동이다. 상태 확인 매개변수를 설정하면; ALB가 그것을 시행한다.

**Auto Scaling: 더 많은 테이블을 여는 레스토랑**

ALB는 기존 서버에 트래픽을 배분한다. 더 많이 필요할 때 서버를 추가하지는 않는다.

**Auto Scaling**이 한다.

**Auto Scaling Group**(ASG)은 AWS에 다음을 말하는 설정이다:

- 항상 실행해야 하는 최소 인스턴스 수
- 허용되는 최대 인스턴스 수
- 확장(인스턴스 추가) 또는 축소(제거) 조건

확장 조건을 **정책**이라고 한다. 가장 흔한 유형:

**타겟 추적**: "평균 CPU 사용률을 70%로 유지하라." 평균 CPU가 70%를 초과하면, AWS가 새 인스턴스를 실행한다. 아래로 떨어지면, 인스턴스가 종료된다.

이것은 자동이다. 누구도 메트릭을 지켜볼 필요가 없다. 누구도 수동으로 서버를 실행할 필요가 없다. 시스템이 실시간으로 부하에 반응한다.

Priya는 처음으로 금요일 러시 동안 이것이 라이브로 일어나는 것을 지켜봤다. 서버 수가 15분에 걸쳐 2에서 5로 증가했다가, 러시 후에 다시 2로 돌아왔다.

"저건," 그녀가 말했다, "정말 인상적이다."

Tom은 대신 비용 그래프를 보고 있었다. 청구서가 러시 동안 증가하다가 이후 감소했다. "우리가 사용한 것만 지불했어," 그가 똑같이 인상받은 듯 말했다.

**ALB와 ASG가 함께 작동하는 방법**

두 서비스는 함께 사용되도록 설계되었다.

ALB를 앞에 배치한다. ALB는 **타겟 그룹** — 트래픽을 받아야 하는 인스턴스의 컬렉션 — 을 가리킨다. Auto Scaling Group이 그 인스턴스들을 관리한다: 확장 시 타겟 그룹에 추가하고, 축소 시 제거한다.

흐름:

1. 트래픽이 ALB에 도착
2. ALB가 정상 타겟에 요청 배분
3. 그 타겟에서 CPU/부하가 올라감
4. ASG가 부하 증가를 감지, 새 인스턴스 실행
5. 새 인스턴스가 상태 확인을 통과, ALB에 등록됨
6. ALB가 그것들에 트래픽 전송 시작
7. 부하가 감소, ASG가 추가 인스턴스 종료
8. ALB가 종료된 인스턴스에 트래픽 전송 중단

인간 개입 없이 이것이 일어난다.

**Launch Template: 새 인스턴스를 위한 청사진**

ASG가 새 인스턴스를 실행할 때, 무엇을 실행할지 알아야 한다. 이것은 **Launch Template**에 정의된다 — AMI, 인스턴스 유형, 적용할 보안 그룹, 모든 사용자 데이터(인스턴스가 부팅할 때 실행되는 시작 스크립트).

일반적인 패턴: 애플리케이션을 사용자 정의 AMI에 구축한다(4장 참조).
ASG가 새 인스턴스가 필요하면, 그 AMI를 실행한다. 새 인스턴스는 이미 설치된 애플리케이션으로 부팅된다. 수동 설정 불필요.

더 동적인 환경의 경우, 시작 시 최신 버전의 코드를 가져와서 설치하는 **사용자 데이터 스크립트**를 사용할 수도 있다. 이것은 더 유연하지만 부팅하는 데 더 오래 걸린다.

올바른 선택은 인스턴스가 부팅하는 데 얼마나 걸려야 하는지와 애플리케이션이 얼마나 자주 변경되는지에 달려 있다.

**스티키 세션: 미묘한 문제**

처음 로드 밸런싱을 구현할 때 많은 팀을 넘어뜨리는 것이 있다.

일부 웹 애플리케이션은 세션 데이터 — 로그인 상태, 쇼핑 카트 내용 — 를 서버 자체(메모리나 로컬 디스크에)에 저장한다. 서버 하나로는 잘 작동한다.
여러 서버로는 고장난다.

사용자가 로그인한다. 요청이 서버 A로 간다. 서버 A가 세션을 저장한다. 다음 요청이 서버 B로 간다. 서버 B에 세션이 없다. 사용자가 로그아웃된 것처럼 보인다.

이것은 두 가지 방법으로 해결할 수 있다:

**스티키 세션**(또는 세션 친화성): 같은 사용자의 요청을 항상 같은 서버로 보내도록 ALB를 설정한다. 이것은 단기 수정이다. 로드 밸런싱을 약화시키고(일부 서버가 "스티키" 사용자를 더 많이 받는다) 인스턴스가 종료될 때 문제가 생긴다.

**무상태 애플리케이션 설계**: 세션 데이터를 외부에 저장 — 데이터베이스나 ElastiCache 같은 캐시에(10장). 각 서버가 외부 저장소에서 모든 사용자의 세션을 재구성할 수 있다. 서버가 상호 교환 가능해진다. 이것이 수평 확장 가능한 애플리케이션에 올바른 접근 방식이다.

Priya는 이것을 "멀티 서버로 갈 때 하는 가장 중요한 아키텍처 결정"이라고 불렀다. 그녀가 옳다. 10장에서 다시 만난다.

**로드 밸런서 유형**

AWS는 각각 서로 다른 트래픽에 맞는 세 가지 유형의 로드 밸런서를 제공한다:

**Application Load Balancer(ALB)**: HTTP 및 HTTPS 트래픽. 레이어 7(HTTP를 이해한다). URL 경로(`/api`는 한 그룹으로, `/static`은 다른 그룹으로), 호스트 헤더, 쿼리 파라미터를 기반으로 라우팅할 수 있다. 이것이 대부분의 웹 애플리케이션이 사용하는 것이다.

**Network Load Balancer(NLB)**: TCP, UDP, TLS 트래픽. 레이어 4(HTTP를 이해하지 못한다). 매우 높은 성능, 초당 수백만 요청, 매우 낮은 지연 시간. HTTP를 처리하지 않거나 원시 속도가 필요할 때 사용하라.

**Gateway Load Balancer(GWLB)**: 타사 가상 네트워크 어플라이언스(방화벽, 침입 감지)를 통해 트래픽을 라우팅하기 위한 것. 주니어 수준에서는 드물게 필요할 것이다.

Nimbus를 위해(그리고 대부분의 웹 애플리케이션을 위해), ALB가 올바른 선택이다.

## 장점과 한계

**ALB + Auto Scaling이 강력한 이유**:

- 제로 다운타임 확장(기존 연결을 중단하지 않고 인스턴스가 추가/제거됨)
- 자동 장애 조치(비정상 인스턴스가 자동으로 트래픽에서 제거됨)
- 비용 효율성(실행 중인 인스턴스에만 지불)
- 단일 장애 지점 없음 — 여러 AZ에 걸쳐 여러 인스턴스

**복잡해지는 부분**:

- 상태가 있는 애플리케이션은 특별한 처리가 필요하다(스티키 세션 또는 외부 상태)
- 확장에 시간이 걸린다 — 트래픽이 즉시 급증하면, 새 인스턴스가 준비되기 전에 지연이 있다. **예약된 확장**(알려진 이벤트 전에 미리 확장) 또는 더 큰 최소 인스턴스 수로 이를 완화할 수 있다
- 더 많은 이동 부품은 모니터링하고 디버깅할 것이 더 많다는 것을 의미한다
- 일부 애플리케이션은 수평으로 쉽게 확장할 수 없다(데이터베이스, 특정 레거시 시스템). 수평 확장은 무상태 계층에 가장 잘 작동한다.

## 요약

- **수평 확장**(더 많은 서버 추가)은 단일 장애 지점을 없애고
  탄력적인 비용을 허용하기 때문에 수직 확장(하나의 서버를 더 크게 만들기)보다 선호된다.
- **Application Load Balancer(ALB)**는 들어오는 HTTP/HTTPS 트래픽을
  여러 EC2 타겟에 배분한다. 상태 확인을 수행하고 정상 인스턴스에만 라우팅한다.
- **Auto Scaling Group(ASG)**은 정의된 확장 정책(예: 타겟 CPU 사용률)에 따라 EC2 인스턴스 수를 자동으로 조정한다.
- ALB와 ASG는 함께 작동한다: ASG가 플리트를 관리하고, ALB가 그것에 걸쳐 트래픽을 배분한다.
- 상태가 있는 애플리케이션은 스티키 세션(단기 수정)을 사용하거나
  상태를 외부화(올바른 장기 설계)해야 한다.
- HTTP 트래픽에는 ALB를 사용하라. 원시 TCP/UDP 성능에는 NLB를 사용하라.

## 시험 팁

*SAA-C03 도메인 2 — 태스크 2.1 (확장 가능한 아키텍처) / 도메인 3 — 태스크 3.2*

- **ASG 상태 확인은 EC2 또는 ALB에서 올 수 있다.** EC2 상태 확인은 인스턴스가 실행 중인지만 감지한다. ALB 상태 확인은 애플리케이션이 올바르게 응답하는지 감지한다. ALB 상태 확인이 더 철저하며 웹 애플리케이션에 선호된다.
- **타겟 추적 확장이 확장 정책에 대한 가장 흔한 시험 답이다.** 단순 확장(알람이 발생하면 N개 인스턴스 추가)은 더 오래되고 덜 적응적이다.
- **확장 아웃은 빠르고; 축소는 느리다.** AWS는 활성 연결을 중단하지 않기 위해 축소 중에 인스턴스를 점진적으로 종료한다 — ALB의 **등록 해제 지연** 설정에 의해 제어되는 동작.
- **최소 인스턴스 수가 복원력 바닥이다.** 최소 = 1로 설정하고 그 인스턴스가 실패하면, ASG가 반응하기 전에 애플리케이션이 다운된다. 진정한 복원력을 위해 최소 ≥ 2로 설정하고 AZ 전체에 분산하라.
- **ALB는 AZ 전체에 트래픽을 자동으로 배분할 수 있다.** 교차 영역 로드 밸런싱이 활성화되면, 각 ALB 노드는 AZ와 관계없이 등록된 모든 타겟에 걸쳐 요청을 균등하게 배분한다. 이것은 AZ 인스턴스 수가 다를 때 균형 있는 부하를 위해 중요하다.

## 연습 문제

**연습 1 — 회상**

자신의 말로: Application Load Balancer와 Auto Scaling Group의 차이는 무엇인가? 각각이 어떤 문제를 해결하고, 왜 일반적으로 함께 사용하는가?

*(힌트: 하나는 이미 존재하는 트래픽을 배분하고; 다른 하나는 얼마나 많은 용량이 있는지 조정한다.)*

**연습 2 — 시험 연습**

*시나리오*: 소매 회사의 전자상거래 웹사이트가 매우 가변적인 트래픽을 경험한다: 주중에는 낮은 트래픽, 주말과 플래시 세일 이벤트 동안 대규모 급증. 그들은 조용한 기간 동안 사용하지 않는 용량을 유지하지 않고 애플리케이션이 최대 부하를 처리하길 원한다. 애플리케이션은 현재 서버 메모리에 세션 데이터를 저장한다.

다음 중 확장성 요구사항을 가장 잘 해결하는 아키텍처 변경은?

A) 최대 트래픽을 처리할 수 있는 단일 매우 큰 EC2 인스턴스로 업그레이드  
B) ALB가 있는 여러 EC2 인스턴스와 Auto Scaling Group을 배포하고,
   세션 스토리지를 ElastiCache로 외부화  
C) 스티키 세션이 활성화된 ALB 뒤에 여러 EC2 인스턴스를 배포  
D) 각 예상 트래픽 급증 전에 수동으로 EC2 인스턴스를 추가하고 이후 종료

**힌트 1**: "사용하지 않는 용량을 유지하지 않고"는 자동 확장이 필요하다는 것을 의미한다. 고정된 대형 인스턴스나 수동 관리가 아니라.

**힌트 2**: 서버 메모리의 세션 스토리지는 멀티 인스턴스 배포에 문제다. 어떤 옵션이 이것을 해결하는가?

**힌트 3**: 옵션 C는 스티키 세션을 사용한다 — 그것은 해결책이 아니라 해결책이다.
어떤 옵션이 확장과 세션 스토리지 문제 모두를 올바르게 해결하는가?

**답**: B

**설명**: Auto Scaling Group이 있는 ALB는 자동으로 탄력적인 확장을 제공한다
— 급증 동안 인스턴스가 추가되고 조용한 기간 동안 제거된다. 세션 스토리지를 ElastiCache(외부 캐시)로 이동하면 애플리케이션이 무상태가 된다: 모든 인스턴스가 모든 사용자의 요청을 처리할 수 있고, ALB가 트래픽을 자유롭게 배분할 수 있다.
이것이 아키텍처적으로 올바른 솔루션이다.

**왜 A가 아닌가?** 아무리 크더라도 단일 대형 인스턴스는 여전히 단일 장애 지점이다. 또한 조용한 기간에 용량 대부분이 사용되지 않아 돈을 낭비한다.

**왜 C가 아닌가?** 스티키 세션은 사용자를 같은 인스턴스로 라우팅하여 부분적으로 세션 문제를 완화하지만 로드 밸런싱을 약화시킨다. 그 인스턴스가 종료되면(축소 중이나 실패 시), 사용자는 어쨌든 세션을 잃는다.

**왜 D가 아닌가?** 수동 확장은 트래픽 급증을 올바르게 예측하고 미리 행동하는 누군가를 필요로 한다. 느리고, 오류가 발생하기 쉬우며, 노동 집약적이다. Auto Scaling이 이것을 자동으로 처리한다.

## 포스트 크레딧 장면

Auto Scaling과 ALB를 배포한 첫 번째 금요일에, 팀이 함께 메트릭을 지켜봤다.

오후 7시 15분: 두 개 인스턴스 실행. 정상 부하.
오후 7시 45분: 부하가 오른다. Auto Scaling이 두 개 인스턴스를 더 실행한다.
오후 8시: 네 개 인스턴스가 최대 부하를 처리한다. 응답 시간 안정적.
오후 9시 30분: 부하가 떨어진다. Auto Scaling이 두 개 인스턴스를 종료한다.
오후 9시 45분: 다시 두 개 인스턴스.

사이트는 한 번도 다운되지 않았다. 단 한 번도.

Leo가 놓친 실패를 찾을 것처럼 메트릭 페이지를 세 번 새로고침했다.

"아무것도 고장나지 않아서 약간 실망스럽다는 게 이상한 건가요?" 그가 말했다.

"응," Priya가 말했다.

Tom은 청구서를 보고 있었다. 비용이 트래픽을 거의 완벽하게 추적했다. "사용한 것만 정확히 지불했어," 그가 말했다. "더도 덜도 아니고."

진심으로 놀란 것처럼 들렸다.

다음 날 아침, Maya가 에러 로그에서 새 문제를 발견했다. 중단이 아니었다 — 더 나빴다.

"우리 데이터베이스," 그녀가 말했다. "평균 쿼리 시간이 8초야."

8초. 레스토랑 주문 앱에서.

"누군가 메뉴를 로드할 때마다, 페이지를 만들기 위해 데이터베이스의 모든 아이템을 쿼리하고 있어," Leo가 말했다. "그리고 우리는 이제 47개 레스토랑이야."

"총 메뉴 아이템이 몇 개야?" Tom이 물었다.

Leo가 쿼리를 실행했다.

"약 22,000개."
