# 第3章：你究竟是谁？

刚过早上九点。Leo 从七点起就坐在桌前，咖啡放在键盘旁，已经凉了。办公室很安静——Maya 还没到，Tom 在打电话。窗外，有人在修剪草坪。

Leo 又输入了一遍那条命令。

终端返回了两个词：拒绝访问（Access Denied）。

新加坡危机已经过去。区域改对了，服务器在 us-west-2 运行着，团队短暂地感到了一阵胜任感。这种感觉持续了大约四十八小时，然后新问题浮出了水面：Leo 无法部署到生产环境。没有人设置过他的权限。没有人设置过任何人的权限。这个 AWS 账户在 root 层面门户大开，在其他所有地方却锁得死死的，而没有人注意到，因为没有人试过。

"我已经把它部署上去了——哦，" Leo 嘟囔着，往回翻看终端记录。一周以来，他一直在向他以为是生产环境的地方部署。那是预发布环境（staging）。真正的生产环境从来没被碰过。

Maya 从他肩后看着错误信息。"谁给了你那个权限？"

Leo 转过身。"什么权限？"

"部署到生产环境的权限。谁设置的？"

Leo 打开了 AWS 控制台，开始点击菜单。没有人设置。没有策略，没有角色，没有明确的授权。也没有明确的拒绝——只是一片空白。Nimbus 没有人曾经坐下来思考过谁可以做什么。

这就是问题所在。

**密码的问题**

密码对计算机系统来说是一个糟糕的模型。

不是因为它们总是很弱。而是因为它们是二元的：你要么有密码，要么没有。如果你有，你可以做该账户被允许做的任何事情。

对于个人笔记本上的单个用户来说，这还好。对于公司的云基础设施来说，这是灾难性的。

考虑 Nimbus 需要管理的内容：Web 服务器、数据库、文件存储、网络、账单提醒、用户账户。如果所有这些都由一个密码保护——或者哪怕是一组凭证——那么任何得到那个密码的人就得到了一切。

而在 AWS 上的"一切"意味着删除数据库的能力。启动会产生 5 万美元账单的服务器。泄露每一条客户记录。销毁备份数据。

除了密码的二元性之外还有另一个问题：密码是静态的。它们不会自动过期。它们经常在多个服务之间重复使用。它们会被写下来。它们会被存进标着"密码 请勿分享"的电子表格里。它们还是会被分享，因为当安全机制成为阻力时，便利会战胜安全。

"共享凭证"的问题不是性格缺陷。这是一个系统问题。当授予某人对系统的临时访问的唯一办法是把永久密码给他们时，人们就会分享密码。解决方案是构建一个把临时的、限定范围的访问作为默认的系统——而不是一个需要英雄式努力才能实现的变通办法。

这就是 IAM 所做的。不只是"更好的密码"，而是一个根本不同的模型：访问由身份和策略定义，而不是由谁知道一串字符来定义。

Priya 并没有以冷静、抽象的方式描述这些。她把它讲成了一个故事。

**四小时烧掉 8 万美元的泄露事件**

一家初创公司的开发者把一个 GitHub Actions 部署脚本推送到了他们的公开仓库。脚本里以环境变量的形式硬编码了 AWS 凭证——这个错误常见到在云安全事故复盘中拥有自己的专属类别。这些凭证拥有该公司 AWS 账户的完整管理员权限，因为六个月前有人为了不想跟 IAM 策略打交道而把它们配置成了那样。

凭证在文件里待了大约六分钟，就被一个自动扫描器发现了——运行扫描器的是攻击者，不是安全研究员。

扫描器收录了这些凭证，评估了账户权限，然后开始在多个区域启动 GPU 实例。GPU 实例很贵。它们也很适合用来挖加密货币。第一个小时内，四十七台 `p3.8xlarge` 实例已经在 `us-east-1`、`eu-west-1` 和 `ap-southeast-1` 运行起来了。

一台 `p3.8xlarge` 每小时约 12 美元。四十七台每小时就是 564 美元。

等到这家初创公司的账单告警触发——告警设在每天 1,000 美元，没有人想过要把阈值调紧——四个小时已经过去了。账单逼近 2,200 美元并且还在攀升。

等到有人弄明白发生了什么并吊销了凭证，那几个小时的账单已经达到 3,400 美元。但真正的代价在后面：审计发现，攻击者其实已经悄悄地、趁夜里挖矿挖了好几个星期，用的是第二组没人注意到的泄露凭证。审计完成时的总损失：超过 8 万美元。

"然后他们倒闭了？" Tom 问。

"三个月后，" Priya 说。"投资人撤资了。泄露事件被披露。媒体报道让融资变得不可能。"

房间里一片安静。

"那么替代方案是什么？" Tom 问。

**概念：身份和访问管理**

替代方案是一个不给每个人同一把钥匙的系统。

想象一栋办公楼，每层楼都有不同的区域，每个员工都有一张只能打开其工作所需的门的门禁卡。实习生的门禁卡在三楼有效。会计的门禁卡能打开财务办公室，但打不开服务器机房。没有人会穿过一扇自己没有理由穿过的门。

这就是 AWS 使用的模型。

AWS 把这个系统称为 **IAM**：身份和访问管理（Identity and Access Management）。

IAM 是你整个云账户的门禁卡系统。你定义谁存在（身份），他们被允许做什么（权限），并通过策略来应用这些权限。这栋大楼有几十层。IAM 确保每个人只能到达他们需要到达的楼层。

门禁卡的类比还可以延伸。在一栋管理良好的大楼里，你随时都知道谁拥有对什么的访问权。你可以打印一份报告：这是每张门禁卡的访问权限。这是过去 30 天进过服务器机房的人。这是 90 天没有使用过的卡（可能意味着某个已离职员工的卡没有被停用）。

IAM 提供同样的可见性。通过 IAM 进行的每一次操作——每一次 API 调用、每一次控制台登录、每一次权限授予——都会被记录在 **AWS CloudTrail** 中。如果你需要知道是谁在某个周二的凌晨 2 点删除了数据库，CloudTrail 有答案。如果你需要向审计员证明只有获授权的用户能访问生产系统，CloudTrail 提供证据。

AWS CloudTrail 会自动保留 90 天的管理事件历史，可以从控制台读取。但当你的安全团队需要审计上个季度的某件事时，90 天总会显得不太够用。要实现持久的、长期的日志记录——以及告警——你需要创建一个 **Trail**（跟踪），它会把所有事件写入一个 S3 存储桶，并可以流式传输到 CloudWatch Logs。Trail 不是自动的；它是你配置一次然后就忘掉的东西。直到你需要它的那一天。

IAM 的访问控制与 CloudTrail 的审计日志相结合，正是大型组织得以放心地大规模运行 AWS 账户的原因：访问由 IAM 定义和执行；对该访问权的每一次行使都由 CloudTrail 记录在案。

**医院类比**

这里是理解它的第二种方式——一种让访问层级更直观的方式。

想象一家医院。不只是物理建筑，而是由人员、角色和数据构成的完整组织结构。

**前台接待员**可以看到患者的预约日程和保险信息。他们可以为患者办理入院和出院。他们不能访问病历，不能修改处方，不能查看手术史。

**护士**可以访问本病区患者的病历。他们可以按医嘱给药。他们不能开处方。他们不能批准手术。

**医生**可以查看和修改病历、开处方、安排检查。他们不能访问工资系统。没有特定的越权授权，他们不能修改其他医生的处方。

**外科医生**可以访问手术室系统。他们对手术记录拥有大多数医生不需要的特定权限。

**保洁人员**可以访问楼层平面图和房间日程。他们不能访问任何患者数据。

医院里的每个人都拥有其工作所需的访问权——仅此而已。前台接待员没有手术权限。保洁人员看不到患者病历。而至关重要的是：如果一名保洁人员的门禁卡被偷，攻击者拿到的是保洁日程表。他们拿不到患者病历。这次泄露的爆炸半径被限制在那张门禁卡所能访问的范围之内。

IAM 就是这样工作的。每个身份——每个用户、每个服务、每个自动化流程——都得到它恰好需要的权限。不多一分。

Tom 向后靠了靠。"所以 Leo 是护士，我是会计。"

"差不多吧，" Priya 说。"而且你们俩谁都不是外科医生。"

"那谁是外科医生？"

"日常工作里，没有人是，" Priya 说。"root 账户才是外科医生。它只在特定的、有记录的手术中才出场。"

**IAM 的构建模块**

IAM 有四个核心概念。它们相互叠加。

**用户**（User）是个人身份。Maya 有一个 IAM 用户。Tom 有一个 IAM 用户。每个用户都有自己的凭证——并且只应该拥有他们特别需要的权限。

一个 IAM 用户有两类凭证：用于控制台访问（登录 AWS 网页界面）的**密码**，以及用于通过 CLI 或 SDK 进行编程访问的**访问密钥**（一个密钥 ID 和一个私有密钥）。你并不总是两者都需要。一个只用 CLI 的开发者不需要控制台密码。一个只需要控制台的非技术用户不需要访问密钥。只授予所需的。

**组**（Group）是用户的集合。与其单独为 Maya、Tom、Priya 和 Leo 设置权限，你可以创建一个带有开发者权限的"开发者"组并将他们添加进去。当第五个人加入时，你把他们添加到组中，他们立即继承正确的权限。

组的实际好处是可维护性。如果"开发者"组需要一项新权限——比如对某个新 S3 存储桶的访问——你把它加到组里一次，所有开发者立刻就都拥有了。没有组的话，你得逐个更新每个用户，这会制造不一致的机会，也会漏掉人。

**角色**（Role）是可以被某个事物*代入*（assume）的临时身份——一个人、一个服务或另一个 AWS 账户。我们将在第14章深入讨论角色。现在：如果用户是永久员工，角色就是访客徽章。它为特定的时间或目的授予特定的访问权限。

对本章来说，角色最重要的用途是：用于 EC2 实例的 IAM 角色。当你把一个角色附加到一台 EC2 实例时，运行在该实例上的应用程序就能使用该角色的权限发起 AWS API 调用——而不需要在任何地方存储任何静态凭证。这些凭证是临时的，由 AWS 自动轮换，并且范围被限定在该角色的策略之内。这彻底消除了"凭证写在配置文件里"的问题。

**策略**（Policy）是实际的权限规则。策略是一个文档（内部用 JSON 编写，但你不需要记住格式），它说："这个策略的持有者被**允许**对资源 Y 执行操作 X。"或者"**拒绝**操作 Z。"

AWS 提供了数百个**托管策略**（managed policy）——为常见用例预先写好的策略。`AmazonS3ReadOnlyAccess` 授予对所有 S3 存储桶的读取权限。`AmazonEC2FullAccess` 授予对 EC2 的完全控制。在生产环境中，你通常需要**客户管理的策略**（customer-managed policy）——你自己编写的、精确限定到应用程序实际所需资源和操作的策略。

IAM 的评估模型是：默认情况下，一切都被拒绝。权限必须明确授予。如果策略没有说你可以做某事，你就不能做。

**最小权限原则**

只给人员和系统他们工作所需的访问权限。不要更多。

Priya 称之为"最小权限原则"。这听起来很明显。在实践中，大多数团队不断违反它——不是出于恶意，而是出于便利。

"我们能不能给 Leo 管理员访问权限，这样他可以更快地部署东西？"

不。

"我们能不能对所有事情都使用 root 账户？"

绝对不行。

root 账户是你整个 AWS 账户的主密钥。它可以做任何事情，包括关闭账户本身。你应该创建一次，设置多因素身份验证，然后再也不为日常工作使用它。

只有屈指可数的几项任务需要 root 账户：更改账户电子邮件地址、查看未以其他方式委派的账单信息、关闭账户，以及少数几项 AWS 明确限定只能由 root 执行的管理操作。对于其他一切——创建用户、部署基础设施、访问数据库——你使用 IAM 用户和角色。root 账户是给大楼管理员的。其他所有人都有各自合适的门禁卡。

那天下午，Priya 为每个人创建了单独的 IAM 用户。她给了 Leo 部署到开发环境的权限。不是生产环境。不是账单。不是网络。只是部署。

"感觉很受限制，" Leo 说。

"这就是你知道它做对了的方式，" Priya 回答道。

开发与生产之间的边界，是 Priya 画下的第一条、也是最重要的一条最小权限分界线。开发者在开发环境里需要快速行动：创建资源、测试配置、犯错误。但生产环境不同。生产变更需要是深思熟虑的、经过评审的，并通过受控流程执行的。给开发者直接的生产访问权，等于给了他们以开发速度犯生产错误的能力。

随着时间推移，Priya 建立了一套系统：生产访问权通过角色代入流程临时授予——需要做生产变更的开发者申请访问，获得一个 4 小时的窗口，完成变更，访问权自动过期。窗口期间的一切都记录在 CloudTrail 里。访问权过期后无法再使用。生产环境受到的保护不是靠永久性地拒绝访问，而是靠让访问有时限、可审计。

你也许会好奇：既然一切默认被拒绝，为什么 root 账户拥有完全访问权？root 账户很特殊——它完全绕过了 IAM。这恰恰就是你要把它锁起来的原因。AWS 中的其他每一个操作都要经过 IAM 的评估链，在那里，缺少一条 Allow 就等同于一条 Deny。

**爆炸半径：为什么最小权限能拯救公司**

安全工程师在思考凭证泄露时会使用一个概念：**爆炸半径**（blast radius）。

爆炸半径是攻击者获得某个凭证后所能造成的最大破坏。

掌握了一个 AWS 账户 root 凭证的攻击者，拥有无限的爆炸半径。他们可以删除每一个资源，窃取每一个字节的数据，在每一个区域启动 GPU 实例，并关闭账户。这个凭证本身不含任何限制。

掌握了 Leo 的 IAM 凭证——其范围被限定为部署到开发环境和读取一个 S3 存储桶——的攻击者，爆炸半径微乎其微。他们可以向开发环境部署。他们可以读一些文件。他们碰不到生产环境。他们访问不了数据库。他们看不到账单。他们启动不了 GPU 实例。

前面那个泄露故事之所以爆炸半径巨大，是因为那名开发者的凭证是管理员权限。如果同样的凭证被限定到他们的实际工作——向某一个特定环境部署——损失会小得多。攻击或许仍会发生。结局会截然不同。

这就是为什么最小权限不只是一项制度。它是架构。你没有授予的每一项权限，都是你不必承担的爆炸半径。

**当你搞错这些时会发生什么**

三个场景，按严重程度递增：

**场景 1**：一个拥有管理员访问权限的员工离开了公司。没有人停用他们的账户。三个月后，他们仍然有访问权限。这种情况经常发生。IAM 解决了这个问题：你停用用户。立即生效，处处生效。

这是最常见的 IAM 失败模式，而且完全可以预防。大多数组织都有撤销物理访问的流程（交还工牌、交还笔记本电脑），却忽略了 IAM。把"停用 IAM 用户"和"从所有 IAM 组中移除"写进离职清单，不是什么复杂的工程挑战——这是流程纪律。那些始终如一地执行它的团队，永远不会有机会知道当一名前员工仍能访问生产数据库时会发生什么。

**场景 2**：一个开发者的笔记本电脑被入侵。攻击者在配置文件中发现了具有完整管理员权限的 AWS 凭证。因为凭证有广泛的访问权限，攻击者可以做任何事情：挖加密货币、窃取数据、删除备份。有了最小权限：凭证只在其有限范围内有效。爆炸半径被控制住了。

凭证放在配置文件里的模式比它应有的程度更常见。开发者经常把 AWS 凭证存在 `~/.aws/credentials` 里用于本地开发——这没问题。问题在于那些凭证拥有生产级别的访问权，而不是被限定在沙盒环境。开发凭证应该被限定在开发环境。生产访问应该需要明确的代入步骤才能获得，而不是时时刻刻存在于每一台笔记本电脑上。

**场景 3**：一个写得不好的应用程序不小心在其日志中暴露了 AWS 凭证。如果这些凭证有广泛的访问权限，你就有了灾难性的泄露。如果它们的访问权很窄——只能访问应用程序需要的那个特定 S3 存储桶——暴露就是有限的、可控的。

应用程序凭证出现在日志里的场景很隐蔽。它通常发生在调试代码记录了完整的请求上下文——包括授权头——的时候，或者错误处理器把所有环境变量（包括 `AWS_ACCESS_KEY_ID`）序列化到日志文件里的时候。这里的防护手段就是用于 EC2 的 IAM 角色，它把静态凭证从应用环境中彻底消除。如果根本没有静态凭证，它们就不可能出现在日志里。

模式：访问应该被限定在最小范围内。始终如此。不是因为你不信任你的人，而是因为你无法控制泄露的凭证会发生什么。

**选择宽泛的访问权，就选择了便利，但也选择了暴露**

总有一种诱惑，让人想给团队比所需更宽的访问权——这让部署更快，减少摩擦，避免打断心流的"拒绝访问"时刻。如果你给所有人管理员权限，那么部署确实顺畅，没有人会被卡住——但当凭证泄露时（它们会泄露的），攻击者就继承了完整的管理员权利。一台被入侵的笔记本电脑就变成了整个账户的沦陷。先写最小权限。只在某件事失败时才扩展。这条规则能拯救公司。

**多因素身份验证：第二把锁**

即使有最小权限，凭证也可能被盗。密码可以被猜测、钓鱼或泄露。IAM 通过**多因素身份验证（MFA）**解决了这个问题。

MFA 需要你*知道*的东西（密码）加上你*拥有*的东西（手机、硬件密钥）。即使攻击者盗取了你的密码，他们也无法在没有你的手机的情况下登录。

MFA 应该为每个 IAM 用户启用。对于 root 账户，这是不可协商的。

Priya 花了一下午为每个人设置它。过程并不顺利。

Leo 的身份验证器应用两次注册到了错误的账户。他不得不扫了三次二维码，因为他笔记本电脑上的时钟略微不同步，导致基于时间的令牌验证失败。第三次尝试，终于成功了。

"有没有不用这个应用的办法？" Leo 看着手机问。

"硬件密钥，" Priya 说。"一种插进 USB 的物理设备。比应用更安全。也更贵。"

"贵多少？"

"每把大约 50 美元。你需要两把，以防丢失一把。"

Tom 在笔记本里写下"每位开发者 100 美元"。

"我们要买，" Priya 说。"至少为 root 账户买。"

Tom 问这一切是不是摩擦太大了。Priya 再次调出了那个泄露事件的故事。

Tom 立即设置了 MFA。

"那如果在我们过渡的过程中——在所有人都启用 MFA 之前——有人试图入侵怎么办？" Priya 问。

没有人有好答案。她最先为 root 账户设置了 MFA，先于其他任何人。

**IAM Access Analyzer：第二双眼睛**

MFA 设置完成后，Priya 还有一个工具要展示给团队。

"这个是自动运行的，" 她说着，打开了一个新的控制台标签页。

**IAM Access Analyzer** 是一项持续分析你的 IAM 策略的服务，它会标记任何将访问权授予你账户之外——或超出你预期范围——的资源的策略。

第一次运行它就发现了东西。

一个 S3 存储桶——Leo 三周前作为"临时用途"建好然后就忘了的——有一条允许公开读取的存储桶策略。桶里有一些测试数据文件，没什么敏感的。但里面还有一个 Leo 命名为 `db-backups-staging` 的文件夹，他往里面放了几个导出的 SQL 文件，用来测试导入流程。

"那些 SQL 文件里有敏感内容吗？" Priya 问。

Leo 看了看文件夹名。又看了看里面的文件。然后看向天花板。

"我导出的是预发布数据库，" 他说。"而它里面有早期生产环境客户数据的副本。"

Priya 缓缓合上了她的笔记本电脑。

五分钟之内，那个存储桶被设为了私有。Access Analyzer 继续监控，留意未来任何意外开放资源的策略。

"把它当作一套周界警报，" Priya 说。"每次有人不小心忘了关门，它都会告诉我们。"

你也许会好奇：IAM Access Analyzer 能取代人工策略评审吗？不能。它是检测工具，不是预防工具。它告诉你哪些访问权已经被授予——它无法告诉你那个授予是否出于本意。"这条策略对不对？"的人工评审仍然必须进行。Access Analyzer 只是确保敞开的窗户不会无人察觉。

## 优势与局限性

**IAM 适合**：

- 控制谁和什么可以访问每一个 AWS 资源
- 在用户、服务和跨账户边界上实施最小权限
- 消除系统之间共享长期凭证的需要
- 每一次 IAM 操作都会被自动记录，为你提供谁在何时做了什么的审计跟踪（第14章详述）
- 跨账户访问：账户 A 中的 IAM 角色可以被账户 B 中的主体代入，从而在不共享凭证的情况下，实现 AWS 账户之间受控的资源共享

**IAM 变得困难的地方**：IAM 策略可能在几十个角色中增长到数百条语句，而调试一个"拒绝访问"错误需要弄清这些策略中哪一条才是实际生效的——这项任务比听起来更难。最常见的 IAM 错误不是访问权太少——而是太多。为了"先让它跑起来"而创建的过于宽松的策略会变成安全隐患，事后回滚起来很痛苦。先写最小权限。只在某件事失败时才扩展。

IAM 在规模化时还有一个现实的挑战：**策略蔓延**（policy sprawl）。运行 AWS 多年的组织往往积累了几十甚至几百条自定义策略，其中许多相互重叠，有些从未被使用，还有少数几条以没有人注意到的方式相互矛盾——因为这些矛盾只在边缘情况下才显现。AWS 提供了 **IAM Access Analyzer**（我们已在本章介绍）和 **IAM 策略模拟**工具来帮助审计和梳理策略。但最有效的策略是从一开始就构建干净的策略并定期审计——而不是任由策略堆积，事后再试图解开乱麻。

Priya 建立了一套季度 IAM 评审制度：列出所有角色和策略，通过 CloudTrail 日志检查哪些正在被实际使用，把任何未使用的凭证或过于宽泛的策略标记出来，予以删除或收紧。评审每季度花两个小时，第一年就抓出了三个策略问题。

"这不是什么令人兴奋的工作，" 她说。"但访问评审正是你抢在别人之前发现那些本会酿成灾难的东西的方式。"

## 摘要

Admin123 这个密码只是症状。病根是 Nimbus 完全没有访问控制策略——一个共享的 root 凭证，没有角色，没有策略，没有审计跟踪。IAM 不只是治标；它迫使团队回答一个他们一直在回避的问题：到底谁被允许做什么？这个问题的答案，是每一个安全的 AWS 架构的基石。

- **IAM**（身份和访问管理）是你控制谁可以在 AWS 中做什么的方式。核心构建模块是：**用户**、**组**、**角色**和**策略**。
- 默认情况下，AWS 中的一切都被**拒绝**。权限必须明确授予。
- **最小权限原则**意味着只给每个身份它需要的访问权限——从而在凭证一旦泄露时把**爆炸半径**降到最小。
- **root 账户**可以做任何事情，包括灾难性的事情。用 MFA 把它锁起来，尽量少使用。
- 为每个 IAM 用户启用 **MFA**。不可协商——在考试中和在生产环境中都是。

## 考试技巧

*SAA-C03 领域1——任务1.1（安全访问 AWS 资源）*

- **默认情况下一切都被拒绝。** 需要显式的"允许（Allow）"。如果策略没有提到某个操作，该操作就被拒绝。
- **显式拒绝（Explicit Deny）始终胜出。** 如果链中的任何策略拒绝某个操作，该拒绝无法被链中其他任何地方的允许覆盖。这让很多考生措手不及。
- **root 账户 ≠ IAM 管理员。** root 账户是与 IAM 分开的凭证。你无法删除 root 账户。你*可以*（也应该）限制其使用时机。
- **IAM 是全局的**，不是按区域的。IAM 用户、组、角色和策略在整个 AWS 账户范围内存在，而不是每个区域各有一套。
- **角色是授予 AWS 服务访问权限的首选方式。** 如果一个 EC2 实例需要访问 S3，你为该实例附加一个 IAM 角色——你不在机器上存储凭证。这种模式在考试中经常出现。
- **IAM Access Analyzer** 会在资源可被账户外部或组织外部访问时生成检测结果。当考试场景提到检测对 S3 或 KMS 的意外外部访问时，Access Analyzer 就是答案。
- 在 AWS 安全最佳实践的语境下，**为 root 账户启用 MFA 是强制性的**，不是可选的。关于保护 root 账户的考题，正确答案中总会包含 MFA。
- **权限边界（Permission boundaries）**是一项高级 IAM 功能（第14章详述），它限定一个 IAM 用户或角色所能拥有的最大权限，即使其策略授予了更多。关于"防止权限提升"或"设置权限上限"的考题指向权限边界。
- **服务控制策略（SCP）**是组织层面的策略，限制 AWS Organization 成员账户中可以执行的操作。它们作用于 IAM 层之上——即使是账户管理员也无法超越 SCP 设定的限制。当考试场景涉及多账户安全治理时，想到 SCP。
- **CloudTrail** 记录所有 IAM API 调用。当考题问"如何审计哪些用户修改了 IAM 策略"时，答案是 CloudTrail。每一次 IAM 操作——创建用户、修改策略、代入角色——都会被记录。90 天的事件历史是自动且免费的；要实现长期保留和告警，你必须创建一个把日志投递到 S3 存储桶的 Trail。

**练习 2——SAA-C03 情景题**

*场景*：一家公司在 EC2 实例上运行一个 Web 应用程序，需要从 S3 存储桶读取文件。一名初级开发者建议直接在 EC2 实例的应用程序代码中存储 AWS 访问密钥。安全团队提出了异议。

什么是*最安全*、操作上最合适的解决方案？

A) 将访问密钥存储在 EC2 实例的环境变量中，而不是代码中  
B) 创建一个具有 S3 读取权限的专用 IAM 用户，并与开发团队共享凭证  
C) 将具有适当 S3 读取权限的 IAM 角色直接附加到 EC2 实例  
D) 使用 root 账户凭证让应用程序完全访问所有 AWS 资源

**提示 1**：在实例上的任何地方存储凭证的问题是凭证可能泄露。有没有一种方法可以在根本不使用凭证的情况下给 EC2 实例授予访问权限？

**提示 2**：AWS 有一种机制，可以在不需要静态凭证的情况下向服务授予权限。那个机制叫什么？

**提示 3**：IAM 角色可以附加到 EC2 实例。附加之后，实例会自动接收由 AWS 轮换的临时凭证。不需要静态凭证。

**答案**：C

**解析**：将 IAM 角色附加到 EC2 实例是正确的模式。实例通过 EC2 元数据服务自动获得临时的、轮换的凭证。没有长期凭证可以泄露、轮换或意外提交到代码仓库。

**为什么不是 A？** EC2 实例上的环境变量仍然可能泄露——通过应用程序日志、调试端点，或在实例被入侵时。静态凭证才是问题所在，而不是它们存放的位置。

**为什么不是 B？** 创建共享 IAM 用户并向团队分发凭证违反了最小权限原则，并使凭证轮换成为噩梦。如果一个人离开，你无法在不更改共享凭证的情况下轻松撤销只属于他们的访问权限。

**为什么不是 D？** 将 root 账户凭证用于任何应用程序都是严重的安全违规。root 账户拥有无限的访问权限，其凭证永远不应离开账户所有者的控制。
