# 第3章：你究竟是谁？

Leo 按下了部署按钮。

终端返回了两个字：拒绝访问。

他再试了一次。结果相同。他在 Nimbus 工作了三周，第一天就获得了 AWS 账户访问权限，一直在没有任何麻烦的情况下向测试环境部署。但这是生产环境。显然，生产环境是不同的。

Maya 从他肩后看着错误信息。"谁给了你那个权限？"

Leo 转过身。"什么权限？"

"部署到生产环境的权限。谁设置的？"

Leo 打开了 AWS 控制台，开始点击菜单。没有人设置。没有策略，没有角色，没有明确的授权。也没有明确的拒绝——只是一片空白。Nimbus 没有人曾经坐下来思考过谁可以做什么。

这就是问题所在。

**密码的问题**

密码对计算机系统来说是一个糟糕的模型。

不是因为它们总是很弱。而是因为它们是二元的：你要么有密码，要么没有。如果你有，你可以做该账户被允许做的任何事情。

对于个人笔记本上的单个用户来说，这还好。对于公司的云基础设施来说，这是灾难性的。

考虑 Nimbus 需要管理的内容：Web 服务器、数据库、文件存储、网络、账单提醒、用户账户。如果所有这些都由一个密码保护——或者甚至一组凭证——那么任何得到那个密码的人就得到了一切。

而在 AWS 上的"一切"意味着删除数据库的能力。启动会产生 5 万美元账单的服务器。泄露每一条客户记录。销毁备份数据。

Priya 并没有以冷静、抽象的方式描述这些。她用一个故事来描述：一家初创公司发生了数据泄露，攻击者在24小时内通过在他们账户上挖矿产生了8万美元的 AWS 账单，三个月后公司倒闭了。

房间里变得安静。

"那么替代方案是什么？" Tom 问。

**概念：身份和访问管理**

替代方案是一个系统，在这个系统中你不给每个人相同的钥匙。你给每个人——以及每个服务——精确地他们需要的访问权限。仅此而已，不多不少。

在 AWS 中，这个系统被称为 **IAM**：身份和访问管理。

把 IAM 想象成一栋大型办公楼中的门禁卡系统。

大楼有几十层楼。服务器室在12层。财务办公室在8层。CEO 的套房在20层。每个员工都有一张门禁卡，但每张卡只能打开该员工工作所需要打开的门。实习生无法刷卡进入服务器室。会计员无法在下班后进入行政楼层。

IAM 以相同的方式工作。你定义谁存在（身份），他们被允许做什么（权限），并通过策略应用这些权限。

**IAM 的构建模块**

IAM 有四个核心概念。它们相互叠加。

**用户**是个人身份。Maya 有一个 IAM 用户。Tom 有一个 IAM 用户。每个用户都有自己的凭证——并且只应该拥有他们特别需要的权限。

**组**是用户的集合。与其单独为 Maya、Tom、Priya 和 Leo 设置权限，你可以创建一个带有开发者权限的"开发者"组并将他们添加进去。当第五个人加入时，你把他们添加到组中，他们立即继承正确的权限。

**角色**是可以被某人*承担*的临时身份——一个人、一个服务或另一个 AWS 账户。我们将在第14章深入讨论角色。现在：如果用户是永久员工，角色就是访客徽章。它在特定时间或目的内授予特定访问权限。

**策略**是实际的权限规则。策略是一个文档（内部用 JSON 编写，但你不需要记住格式），它说："这个策略的持有者被**允许**对资源 Y 执行操作 X。"或者"**拒绝**操作 Z。"

IAM 评估模型是：默认情况下，一切都被拒绝。权限必须明确授予。如果策略没有说你可以做某事，你就不能做。

**最小权限原则**

这是所有安全中最重要的概念，不仅仅是 IAM。

**只给人员和系统他们工作所需的访问权限。不要更多。**

Priya 称之为"最小权限原则"。这听起来很明显。在实践中，大多数团队不断违反它——不是出于恶意，而是出于便利。

"我们能不能给 Leo 管理员访问权限，这样他可以更快地部署东西？"

不。

"我们能不能对所有事情都使用根账户？"

绝对不行。

根账户是你整个 AWS 账户的主密钥。它可以做任何事情，包括关闭账户本身。你应该创建一次，设置多因素身份验证，然后再也不为日常工作使用它。

那天下午，Priya 为每个人创建了单独的 IAM 用户。她给了 Leo 部署到开发环境的权限。不是生产环境。不是账单。不是网络。只是部署。

"感觉很有限制，" Leo 说。

"这就是你知道它是正确的方式，" Priya 回答道。

**当你搞错这些时会发生什么**

三个场景，按严重程度递增：

**场景 1**：一个拥有管理员访问权限的员工离开了公司。没有人停用他们的账户。三个月后，他们仍然有访问权限。这种情况经常发生。IAM 解决了这个问题：你停用用户。立即，无处不在。

**场景 2**：一个开发者的笔记本电脑被入侵。攻击者在配置文件中发现了具有完整管理员权限的 AWS 凭证。因为凭证有广泛的访问权限，攻击者可以做任何事情：挖矿、窃取数据、删除备份。有了最小权限：凭证只适用于其有限范围。爆炸半径被控制住了。

**场景 3**：一个写得不好的应用程序不小心在其日志中暴露了 AWS 凭证。如果这些凭证有广泛的访问权限，你就有了灾难性的泄露。如果它们有窄的访问权限——只访问应用程序需要的特定 S3 桶——暴露是有限的、可控的。

模式：访问应该被限定在最小范围内。始终如此。不是因为你不信任你的人，而是因为你无法控制被盗凭证会发生什么。

**多因素身份验证：第二把锁**

在我们结束这一章之前，再介绍一个概念。

即使有最小权限，凭证也可能被盗。密码可以被猜测、钓鱼或泄露。IAM 通过**多因素身份验证（MFA）**解决了这个问题。

MFA 需要你*知道*的东西（密码）加上你*拥有*的东西（手机、硬件密钥）。即使攻击者盗取了你的密码，他们也无法在没有你的手机的情况下登录。

MFA 应该为每个 IAM 用户启用。对于根账户，这是不可协商的。

Priya 花了整个下午为每个人设置它。

Tom 问这是否太麻烦了。Priya 再次展示了那个泄露事件的故事。

Tom 立即设置了 MFA。

## 优势与局限性

**IAM 适合**：控制谁和什么可以访问每个 AWS 资源；在用户、服务和跨账户边界上实施最小权限；通过 CloudTrail 集成生成每次 API 调用的审计跟踪；消除系统之间共享长期凭证的需要。

**IAM 变得困难的地方**：IAM 策略可能会在几十个角色中增长到数百个语句，调试"拒绝访问"错误需要理解哪个策略是有效的——这是一项比听起来更难的任务。最常见的 IAM 错误不是访问权限太少——而是太多。为了"让它工作"而创建的过于宽松的策略成为安全隐患，事后很难回滚。先写最小权限。只在出现问题时才扩展。

## 摘要

- **IAM**（身份和访问管理）是你控制谁可以在 AWS 中做什么的方式。
- 核心构建模块是：**用户**（个人）、**组**（用户集合）、**角色**（临时身份）和**策略**（权限规则）。
- 默认情况下，AWS 中的一切都被**拒绝**。权限必须明确授予。
- **最小权限原则**意味着只给每个身份它需要的访问权限。不要更多。
- **根账户**可以做任何事情，包括灾难性的事情。用 MFA 锁定它，尽量少使用。
- 为每个 IAM 用户启用 **MFA**。不可协商。

## 考试技巧

*SAA-C03 领域1——任务1.1（安全访问 AWS 资源）*

- **默认情况下一切都被拒绝。** 需要显式的"允许"。如果策略没有提到某个操作，该操作就被拒绝。
- **显式拒绝始终胜出。** 如果链中的任何策略拒绝某个操作，该拒绝无法被链中其他地方的允许覆盖。这让很多考生措手不及。
- **根账户 ≠ IAM 管理员。** 根账户是与 IAM 分开的凭证。你无法删除根账户。你*可以*（也应该）限制其使用时机。
- **IAM 是全局的**，不是按区域的。IAM 用户、组、角色和策略在整个 AWS 账户中存在，而不是每个区域各有一套。
- **角色是授予 AWS 服务访问权限的首选方式。** 如果一个 EC2 实例需要访问 S3，你为该实例附加一个 IAM 角色——你不在机器上存储凭证。这种模式在考试中经常出现。

**练习 2——考试练习**

*场景*：一家公司在 EC2 实例上运行一个 Web 应用程序，需要从 S3 桶读取文件。一名初级开发者建议直接在 EC2 实例的应用程序代码中存储 AWS 访问密钥。安全团队提出了异议。

什么是*最安全*、操作上最合适的解决方案？

A) 将访问密钥存储在 EC2 实例的环境变量中，而不是代码中  
B) 创建一个具有 S3 读取权限的专用 IAM 用户，并与开发团队共享凭证  
C) 将具有适当 S3 读取权限的 IAM 角色直接附加到 EC2 实例  
D) 使用根账户凭证让应用程序完全访问所有 AWS 资源

**提示 1**：在实例上的任何地方存储凭证的问题是凭证可能泄露。有没有一种方法可以在根本不使用凭证的情况下给 EC2 实例授予访问权限？

**提示 2**：AWS 有一种机制，服务可以在不需要静态凭证的情况下被授予权限。那个机制叫什么？

**提示 3**：IAM 角色可以附加到 EC2 实例。当它们附加时，实例通过 EC2 元数据服务自动接收 AWS 轮换的临时凭证。不需要静态凭证。

**答案**：C

**解析**：将 IAM 角色附加到 EC2 实例是正确的模式。实例通过 EC2 元数据服务自动获得临时的、轮换的凭证。没有长期凭证可以泄露、轮换或意外提交到代码仓库。

**为什么不是 A？** EC2 实例上的环境变量仍然可以泄露——通过应用程序日志、调试端点或如果实例被入侵。静态凭证是问题所在，而不是它们的位置。

**为什么不是 B？** 创建共享 IAM 用户并向团队分发凭证违反了最小权限原则，并使凭证轮换成为噩梦。如果一个人离开，你无法轻松撤销只属于他们的访问权限，而不更改共享凭证。

**为什么不是 D？** 将根账户凭证用于任何应用程序是严重的安全违规。根账户有无限访问权限，其凭证不应该离开账户所有者的控制。
