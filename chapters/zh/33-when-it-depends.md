# 第三十三章：视情况而定

在本章之前，做一次最后的深呼吸。

你已经到达了书的末尾。这既是一个结论，也是一个开始——最后一章，也是你独立做架构决策的第一天。

本章只有一个任务：对没有人足够清楚地告诉你的事情保持诚实。

**问题**

在几乎每一次架构讨论结束时，有人最终会问："正确答案是什么？"

软件工程中最有用、最令人沮丧、最诚实、最被误解的答案是：

**视情况而定。**

不是因为问题无法回答。不是因为专家在回避。而是因为正确答案真正地、结构性地取决于问题中没有的背景。

本章是关于学习正确地说"视情况而定"——这意味着能够完成这句话。

想象一个被问到"手术是正确的治疗方法吗？"的医生。一个坏医生不检查患者就说是或不是。一个好医生说："视情况而定——取决于诊断、患者的年龄、他们的其他状况以及如果我们等待会发生什么。"答案不是回避。而是精确。"视情况而定"后跟着一个完整的句子是医生——或架构师——所能说的最有用的话。

**Nimbus 的结局**

两年后的开始。Maya 站在西雅图的一个会议室里，向一屋子的风险投资人做报告。

Nimbus 已经成长：947 家餐厅合作伙伴。每天 18,000 个订单。每月 GMV $210 万。三个城市已上线，两个更多即将推出。跨两个时区的十四名工程师团队。

投资人有问题。其中一人——基金的技术合伙人——向前倾身。

"你用什么数据库？"他问。

Maya 毫不犹豫。

"订单和客户数据：Aurora PostgreSQL。菜单目录：DynamoDB。会话管理和缓存：ElastiCache Redis。分析：基于 S3 Parquet 文件的 Athena，加上 Redshift 用于高频仪表板查询。"

他点点头。"为什么订单使用 Aurora 而不是 DynamoDB？"

"因为订单有复杂的关系结构——它们引用菜单项、客户账户、餐厅地址、支付方式。我们需要跨多个实体的事务一致性。关系数据库是正确的工具。DynamoDB 的优势是高吞吐量的基于键的访问和灵活的模式，这正是菜单目录的访问模式。"

他记下了什么。"扩展呢？你说每天 18,000 个订单。平均每分钟约 12 个。你是如何为峰值设计的？"

"周五晚餐高峰约是平均的 25 倍。我们用 ECS 水平扩展，Aurora Serverless v2 自动处理突发。CloudFront 吸收静态内容负载。API 是无状态的，所以水平扩展是干净的。"

"如果 Aurora Serverless v2 扩展不够快怎么办？"

"我们有负载测试结果。Aurora Serverless v2 的扩展时间不到 10 秒。我们平均的周五高峰从基线开始的增长速度需要 8 分钟。我们对余量感到满意。"

技术合伙人看了看其他投资人。"她了解自己的系统。"

**"视情况而定"下面的四个问题**

每一个架构权衡都可以归结为四个基本问题。不是每个问题对每个决策都同等重要，但四个问题始终都在发挥作用：

**1. 访问模式是什么？**

数据如何写入和读取？以什么频率？由多少并发用户？以什么顺序？通过什么键？

这个问题在最基本的层面上决定了技术选择。DynamoDB 与 Aurora 与 Redshift 与 Athena——正确答案几乎完全取决于访问模式。

**2. 规模是什么？**

不只是现在——12 个月后，5 年后。规模改变了正确答案。在每天 100 次请求时有效的在 1 亿次时会崩溃。在 10 个用户时是过度设计的在 10,000 个用户时是必要的。

规模不只是流量。它是团队规模（架构必须能被你拥有的团队维护）。它是数据量。它是地理覆盖范围。

**3. 失败后果是什么？**

如果这个崩溃了，会怎样？用户看到一个慢页面？订单失败？钱转移不正确？某人的医疗记录变得无法访问？

后果决定了你在可靠性上投入多少。慢菜单页面可以接受最终一致性。失败的支付需要同步写入和明确确认。

**4. 成本约束是什么？**

不只是钱——还有运维复杂性（它本身就是一种成本）。技术上优越于更简单解决方案的解决方案可能对于四人团队来说维护成本太高。

**"视情况而定"：如何完成这个句子**

正确说"视情况而定"的方式是立即完成它：

*"我们应该使用 DynamoDB 还是 Aurora？"*

"视情况而定访问模式。如果你需要灵活模式的高吞吐量基于键的查找，选 DynamoDB。如果你需要跨相关实体的事务一致性和复杂查询，选 Aurora。"

*"我们应该使用 Lambda 还是 EC2？"*

"视情况而定工作负载特性。Lambda 用于事件驱动、短时运行、可变工作负载，其中零空闲成本很重要。EC2 或 ECS 用于持久、有状态或长时运行的进程，其中可预测性能比空闲成本更重要。"

*"我们应该使用 Multi-AZ 还是 Multi-Region？"*

"视情况而定你的 RTO/RPO 要求和你的威胁模型。Multi-AZ 防止 AZ 故障（最常见的 AWS 故障模式），为 RDS 提供 RPO ~0 和 RTO ~60 秒。Multi-Region 防止区域故障（罕见）并为全球分布的用户提供服务。如果你需要从区域性灾难中不到一分钟的故障转移，使用 Multi-Region。如果 AZ 弹性已经足够，Multi-AZ 更简单且更便宜。"

"视情况而定"不是答案的结束。它是真正答案的开始。

**不变的模式**

虽然特定的技术选择在演变——新服务发布，定价变化，更好的替代方案出现——但一些基本模式已经几十年保持稳定：

**关注点分离**：做不同事情的组件应该是独立的。一个的变化不应该要求另一个的变化。这就是为什么你用 SQS 解耦，而不是直接调用。为什么你用 S3 存储对象，而不是数据库。为什么 Web 层和数据库层是分开的。

**深度防御**：没有单一的安全控制是足够的。你有 IAM、安全组、NACL、WAF、GuardDuty、Secrets Manager、KMS。如果一层失败，下一层会捕获它。

**为你使用时付费**：云的基本经济原则。Lambda 扩展到零。竞价实例使用空闲容量。S3 生命周期策略将冷数据移到更便宜的存储。DynamoDB 按需按请求收费。模式不同；原则相同。

**针对最可能的失败进行优化**：Multi-AZ 优先（AZ 故障会发生）。跨区域灾难恢复其次（区域故障更罕见）。AZ 内冗余（多个实例）先于跨区域复杂性。为现实的失败构建，而非灾难性但不太可能的失败。

**优化之前先测量**：Tom 的方法——调出 CloudWatch 指标，了解实际模式，然后做决策——比基于假设的过早优化更有价值。

**这本书无法教你的**

让我们对局限性保持直接。

这本书教了你：

- 每个主要 AWS 服务是什么
- 使它们直观的类比
- 替代方案之间的权衡
- SAA-C03 所需的考试知识
- 思考架构决策的框架

这本书无法教你：

- **生产直觉**：那种感觉说"这在负载下会变得奇怪"的直觉，在你看到它发生之前。这来自于操作真实系统。
- **压力下的技术判断**：在系统宕机且信息不完整的凌晨 3 点决定该做什么。这来自于事故。
- **利益相关者直觉**：知道何时因为技术成本太高而推回业务需求。这来自于对技术和业务两方面的经验。
- **特定背景下的正确问题**：Carlos 能提出正确的问题是因为他见过类似问题几十次。这种知识是赚来的，不是读来的。

你还没有完成学习。你才刚刚开始。

**考试不是目的地**

你拿起这本书是为了准备 AWS Solutions Architect Associate 考试。这是合理的。SAA-C03 认证是真实的、有价值的，并且会打开大门。

但考试测试知识和模式识别。它不测试判断。它不测试运维经验。它不测试当你构建的架构在周五晚上 11 点停止工作时你会做什么。

认证是一个入门凭证。当你通过考试时，你会知道 AWS 服务如何工作以及它们如何结合。你会有一个思考架构的框架。你还没有做过。

考试后的下一步：构建一些真实的东西。部署它。运营它。看着它失败。修复它。在一个服务中耗尽钱然后把成本转移到其他地方。在半夜被叫醒，在信息不足的情况下做出决定。

这就是这本书中的知识如何变成判断的。

**Maya 的最终答案**

在投资人会议结束时，技术合伙人又有一个问题。

"如果你今天重新开始，知道你现在所知道的，你会做什么不同？"

Maya 考虑了片刻。

"我会从第一天就使用基础设施即代码，"她说，"Leo 手动部署了第一台 EC2 实例。我们花了六个月把所有东西迁移到 Terraform。那是花了我们实际时间的六个月技术债务。"

"还有什么？"

"我会更保守地选择早期的托管服务。我们在使用 DynamoDB 时，一个简单的 RDS 数据库本可以几个月内就够用。DynamoDB 访问模式设计需要我们还没有的经验思维。我们重新设计了模式两次。"

"所以早期更简单更好？"

"更简单*始终*更好。问题始终是：解决实际问题的最简单的事情是什么，而不是预期的未来问题？我们添加了复杂性来解决我们还没有的问题。有些复杂性导致了自己的问题。"

技术合伙人记下了这些。

"最后一个问题，"他说，"你知道的关于在 AWS 上构建最重要的事情，是在你开始时不知道的？"

Maya 想着这两年。事故。成本审查。Well-Architected 审查。在压力下做出的架构决策以及仔细做出的决策。他们做对的和不得不重做的。

"云不能解决架构问题，"她说，"它放大了它们。在本地部署上的一个糟糕决策可能会花费你一周时间。在云上的一个糟糕决策可能会每月花费你钱，在规模上，直到有人注意到。"

她停顿了一下。

"云使好的决策规模化。坏的决策也一样。"

**结语**

你学到了很多。AWS 服务。权衡。模式。

现在用它做些什么。

构建一些东西。故意犯错误。阅读事后分析报告（它们是公开的——AWS、Cloudflare、GitHub、Stripe 都会发布）。与在你最薄弱的地方比你更好的团队合作。

SAA-C03 考试将测试你是否知道材料。你的职业将测试你是否能应用它。

两者都值得做。两者都不是最终目的地。

在这个领域没有最终目的地。只有下一个问题，下一个决定，以及提出下一个正确问题的习惯。

祝你好运。

## 总结

- **"视情况而定"是答案的开始**，而非结束。始终完成这个句子，加上它取决于的条件。
- 每个架构权衡下面的四个问题：访问模式、规模、失败后果、成本约束。
- 持久的模式：关注点分离、深度防御、为使用时付费、针对可能的失败进行优化、优化前先测量。
- **云放大决策**——好的和坏的。在本地部署上的糟糕决策花费一周；在云上的糟糕决策每月在规模上复利。
- SAA-C03 认证测试知识和模式识别。生产经验将这些知识转化为判断。

## 考试技巧

*SAA-C03 领域：跨领域 — 所有领域*

本章结束了本书的考试内容。在参加考试之前：

**审查你最不自信的服务**：

- 对大多数人来说：Kinesis 与 SQS（流与队列的区别）
- VPC 网络（路由表、子网、NAT Gateway、Internet Gateway）
- IAM 策略评估逻辑（明确拒绝 > 明确允许 > 隐式拒绝）
- 存储类选择（了解所有六个 S3 存储类及其权衡）
- RDS 与 Aurora 与 DynamoDB 用于特定用例

**了解考试的典型场景结构**：

SAA-C03 提出业务需求（"公司需要 99.99% 的可用性"），要求你确定满足它的架构。始终阅读需求，识别关键约束，然后排除不满足它的选项。

**练习干扰项识别**：

考试上的每个错误答案都有特定的错误原因。学习识别每个错误答案为什么是错的比记忆正确答案更有价值。

**考试奖励模式识别**：

- "解耦" → SQS/SNS
- "无服务器" → Lambda、DynamoDB、Aurora Serverless
- "全球低延迟" → CloudFront、Global Accelerator、Global DynamoDB、Aurora Global
- "合规/审计" → CloudTrail、Config、Security Hub、Macie
- "成本优化" → 竞价实例、Savings Plans、生命周期策略、正确调整大小

**你已经准备好了**。不是因为这本书涵盖了所有内容——没有什么能做到。而是因为你对原则的理解已经足够深入，可以在你不立即认出确切场景时推理出答案。
