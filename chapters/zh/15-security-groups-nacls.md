# 第15章：门口的卫兵

来自 Nimbus 第一版的旧部署密钥仍然处于活跃状态。它上周进行了三次 API 调用。Leo 不知道是什么调用了它们。

Priya 调出了 VPC 流量日志——显示进出 VPC 的每个连接的网络流量记录。

"周二凌晨2:17，" 她说，"有一个从运行旧 API 的 EC2 实例到罗马尼亚一个 IP 地址的出站连接。"

"那不是我们的基础设施，" Leo 说。

"不是。"

"所以有人在我们的 EC2 实例上。"

"或者某个东西。"

他们追踪了回来：旧部署密钥被用来向 EC2 实例上传一个小脚本。那个脚本尝试扫描相邻服务器上的端口。大多数扫描失败了。

"安全组阻止了它们，" Priya 说。"攻击者进入了一个 EC2 实例。他们无法访问其他实例，因为安全组只允许来自负载均衡器的流量。"

"所以损害被控制住了。"

"因为我们有正确配置的安全组。想象一下如果我们把5432端口对账户中任何 EC2 实例开放会怎样。"

Leo 不需要想象。他在原始设置中见过那种配置。

**两层网络安全**

在 VPC 中，你有两种不同的工具来控制资源级别的网络流量：

**安全组**：附加到单个资源（EC2 实例、RDS 数据库、负载均衡器、VPC 中的 Lambda 函数）的虚拟防火墙。它们在资源级别操作。

**网络 ACL（NACL）**：附加到子网的防火墙规则。它们在子网边界操作——在流量到达该子网中的任何资源之前。

理解两者都需要理解一个关键区别：**有状态 vs 无状态**。

**有状态：安全组**

安全组是**有状态的**。

当你允许特定端口上的入站流量时，响应流量会自动允许出去，即使没有明确的出站规则。

当你允许到目的地的出站流量时，回来的响应自动被允许进入。

把它想象成一个有状态的办公楼安全卫士。你刷徽章进入。你后来走出去。警卫不需要再次检查你——系统知道你被放进去了，你被允许离开。

**Nimbus API EC2 实例的安全组规则：**

- **入站——TCP 8080——来自负载均衡器安全组** → 接受来自 ALB 的 API 流量
- **入站——TCP 22——来自堡垒主机安全组** → 只从堡垒主机 SSH
- **出站——TCP 5432——到 RDS 安全组** → 连接到 PostgreSQL
- **出站——TCP 6379——到 ElastiCache 安全组** → 连接到 Redis
- **出站——TCP 443——到 0.0.0.0/0** → HTTPS 到外部 API

注意：没有端口8080的明确出站规则。入站规则是有状态的——响应流量（API 对负载均衡器的回复）被自动允许。

还要注意：安全组规则引用*其他安全组*，而不是 IP 地址。"允许来自负载均衡器安全组的入站"意味着"允许来自附加了这个安全组的任何资源的流量"。这比追踪 IP 地址更灵活、更易于维护。

**默认行为：**

- 默认情况下，所有入站流量被拒绝
- 默认情况下，所有出站流量被允许
- 所有规则都被评估（安全组没有有序规则——所有匹配的规则都适用）
- 安全组只能**允许**流量——你不能创建明确的拒绝规则

**无状态：网络 ACL**

NACL 是**无状态的**。

当你允许端口8080上的入站流量时，这只涵盖入站。响应（临时端口上的出站流量）必须用出站规则明确允许。

把它想象成金属探测器。你通过进门时要经过它。金属探测器不知道你已经通过了——你出去时也要再次通过。

**NACL 规则按数字排序并按序评估。** 第一个匹配的规则获胜。规则100在规则200之前评估。如果规则100拒绝流量而规则200允许它，流量被拒绝。

NACL 可以明确**拒绝**流量——不像安全组只能允许。这使它们对阻止特定 IP 范围很有用。

**默认 NACL 行为：**

- 默认 NACL（随你的 VPC 创建）允许所有入站和出站流量
- 自定义 NACL 默认拒绝所有流量（你必须明确允许你想要的）

**公共子网的 NACL（简化版）：**

*入站规则（按序评估——第一个匹配获胜）：*

- 规则 100：TCP 443，来自 0.0.0.0/0 → **允许**（HTTPS）
- 规则 110：TCP 80，来自 0.0.0.0/0 → **允许**（HTTP）
- 规则 120：TCP 1024–65535，来自 0.0.0.0/0 → **允许**（临时返回端口）
- 规则 \*：所有流量 → **拒绝**

*出站规则：*

- 规则 100：TCP 443，到 0.0.0.0/0 → **允许**（HTTPS）
- 规则 110：TCP 80，到 0.0.0.0/0 → **允许**（HTTP）
- 规则 120：TCP 1024–65535，到 0.0.0.0/0 → **允许**（临时返回端口）
- 规则 \*：所有流量 → **拒绝**

规则120（端口1024-65535）允许临时端口——用于 TCP 响应流量的临时高编号端口。因为 NACL 是无状态的，你必须明确允许这些出站，否则你服务器的响应无法通过。

**何时使用哪种**

使用**安全组**作为主要的访问控制层。它们更易于管理，有状态（忘记临时端口不会造成意外阻塞），并支持引用其他安全组。

使用 **NACL** 进行子网级别的控制，特别是：

- **明确拒绝规则**：阻止特定 IP 地址或范围访问整个子网
- **紧急阻止**：一个 IP 正在积极攻击——在 NACL 添加拒绝规则，在它到达任何资源之前阻止整个子网

"所以安全组是精细控制，" Maya 说，"NACL 是大范围手段？"

"安全组保护单个资源，" Priya 确认道。"NACL 保护整个子网。当你想阻止一个 IP 访问你网络中的任何东西时，用 NACL。当你只想允许负载均衡器访问 API 服务器时，用安全组。"

**事件：各层防止了什么**

回到罗马尼亚 IP 攻击：

**发生了什么**：攻击者使用被盗的部署密钥向一个 EC2 实例上传了一个扫描脚本。那个脚本尝试连接到其他服务。

**什么阻止了他们**：

- RDS 安全组只允许来自 API EC2 安全组的5432端口入站。扫描工具无法访问数据库——它没有附加正确的安全组。
- ElastiCache 安全组只允许来自 API EC2 安全组的6379端口入站。
- 其他 EC2 实例只允许来自堡垒主机安全组的 SSH。

**什么没有阻止他们**：

- EC2 实例的出站规则允许 HTTPS 到 0.0.0.0/0（包下载所需）。脚本用这个向攻击者的服务器建立了出站连接。

事件后，Priya 添加了：

- 阻止罗马尼亚 IP 范围的 NACL 规则
- EC2 实例上更严格的出站规则（只允许特定的已知目标）

## 优势与局限性

**安全组**：

- 有状态（没有临时端口麻烦）
- 可以引用其他安全组（比 IP 更灵活）
- 只有允许规则——没有明确拒绝
- 在资源级别操作——细粒度

**NACL**：

- 无状态（需要包括临时端口在内的两个方向的明确规则）
- 可以明确拒绝——对阻止已知恶意 IP 有用
- 在子网级别操作——更大的范围
- 按数字排序评估的规则——可预测但需要仔细管理

## 摘要

- **安全组**是单个资源的有状态虚拟防火墙。只有允许规则。所有规则都被评估。
- **NACL** 是整个子网的无状态防火墙。允许和拒绝规则。按数字顺序评估规则。
- **有状态**意味着响应流量自动被允许。**无状态**意味着你必须明确允许两个方向的流量。
- 安全组是你的主要访问控制层。NACL 是子网级别控制和明确阻止的额外层。
- 当 NACL 允许入站流量时，你还必须允许出站临时端口（1024-65535），以便 TCP 响应通过。
- 安全组可以相互引用——允许"来自负载均衡器安全组"的流量比追踪 IP 地址更易维护。

## 考试技巧

*SAA-C03 领域：设计安全架构（领域1，任务1.2）*

- **有状态 vs 无状态**：这个区别是本章最常被测试的概念。安全组 = 有状态 = 响应自动被允许。NACL = 无状态 = 必须明确允许响应流量。
- **安全组规则**：没有明确拒绝。当多个安全组附加到实例时，所有规则的并集适用。所有匹配的规则都被评估。
- **NACL 规则顺序**：规则从最低数字到最高数字评估。规则100在200之前。第一个匹配获胜。底部的 `*`（星号）规则是隐式拒绝。
- **临时端口**：经典的 NACL 错误是忘记允许端口1024-65535的出站。如果你的 NACL 允许入站 HTTP（端口80）但不允许出站临时端口，用户可以发送请求但永远收不到响应。
- **安全组引用**：你可以允许来自另一个安全组（而不只是 IP）的流量。这是 VPC 内部流量推荐的模式。
- **默认 NACL vs 自定义 NACL**：默认 NACL 允许所有流量。你创建的自定义 NACL 默认拒绝所有流量。考试场景："创建了新 NACL 现在流量被阻止了" → 检查缺少的允许规则。

## 练习

**练习 1——回忆**

一名开发者向安全组添加了一条允许443端口流量的入站规则。她还需要添加一条出站规则来允许服务器的响应吗？为什么？

如果她向 NACL 添加一条允许443端口流量的入站规则，她需要添加出站规则吗？为什么？

**练习 2——考试练习**

*场景*：一家公司在公共子网的 EC2 实例上运行 Web 应用程序。应用程序接受来自互联网的 HTTPS 流量（端口443）。用户报告他们可以连接到应用程序，但无法收到响应——请求挂起并超时。

EC2 安全组有一条允许来自 0.0.0.0/0 的 TCP 443 入站规则。子网的 NACL 有一条入站规则（规则100）允许来自 0.0.0.0/0 的 TCP 443，以及一条出站规则（规则100）允许到 0.0.0.0/0 的 TCP 443。

问题最可能的原因是什么？

A) 安全组缺少 TCP 443 的出站规则  
B) NACL 缺少允许临时端口（1024-65535）的出站规则  
C) 安全组缺少临时端口的入站规则  
D) EC2 实例没有弹性 IP 地址

**提示 1**：安全组是有状态的——它们自动允许响应。NACL 是无状态的——它们不允许。

**提示 2**：当浏览器在端口443上连接到 Web 服务器时，服务器的响应通过一个随机临时端口（1024-65535）传回，而不是端口443。

**提示 3**：NACL 有端口443的出站规则，但响应不是到端口443的。

**答案**：B

**解析**：NACL 是无状态的。当用户在端口443上连接到服务器时，服务器的 TCP 响应通过临时端口（从1024-65535中随机选择）传回。NACL 出站规则只允许端口443，所以响应被默认拒绝规则阻止。添加允许 TCP 1024-65535 的 NACL 出站规则可以解决这个问题。

**为什么不是 A？** 安全组是有状态的——无论出站规则如何，响应流量都会自动被允许。不需要出站安全组规则。

**为什么不是 C？** 临时端口用于出站响应流量，而不是入站。来自用户的入站连接在端口443上进来，这已经被允许了。

**为什么不是 D？** 弹性 IP 影响实例是否有公网 IP，而不是已建立连接是否能收到响应。
