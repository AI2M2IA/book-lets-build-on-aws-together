# 第15章：门口的卫兵

**两层网络安全**

在 VPC 中，你有两种不同的工具来控制网络流量：

**安全组**：附加到单个资源（EC2 实例、RDS 数据库、负载均衡器、VPC 中的 Lambda 函数）上的虚拟防火墙。它们在资源级别运作。

**网络 ACL（NACL）**：附加到子网上的防火墙规则。它们在子网边界运作——在流量到达该子网中的任何资源之前。

理解这两者，都需要先理解一个关键区别：**有状态 vs 无状态**。

**有状态：安全组**

安全组是**有状态的**。

当你允许某个特定端口上的入站流量时，响应流量会被自动放行出去，即使没有针对它的显式出站规则。

当你允许去往某个目的地的出站流量时，返回的响应会被自动放行进来。

把它想象成办公楼里一位有状态的保安。你刷工牌进门。稍后你走出去。保安不需要在你出门时再查一遍——系统知道你是被放进来的，你被允许离开。

**Nimbus API EC2 实例的安全组规则：**

- **入站——TCP 8080——来自负载均衡器 SG** → 接受来自 ALB 的 API 流量
- **入站——TCP 22——来自堡垒主机 SG** → 只允许从堡垒主机 SSH
- **出站——TCP 5432——到 RDS SG** → 连接 PostgreSQL
- **出站——TCP 6379——到 ElastiCache SG** → 连接 Redis
- **出站——TCP 443——到 0.0.0.0/0** → HTTPS 访问外部 API

注意：没有针对 8080 端口的显式出站规则。入站规则是有状态的——响应流量（API 对负载均衡器的回复）被自动放行。

还要注意：安全组规则引用的是*其他安全组*，而不是 IP 地址。"允许来自负载均衡器安全组的入站"意味着"允许来自任何附加了该安全组的资源的流量"。这比追踪 IP 地址更灵活、更易于维护。

**默认行为：**

- 默认情况下，所有入站流量被拒绝
- 默认情况下，所有出站流量被允许
- 所有规则都会被评估（安全组没有有序规则——所有匹配的规则都适用）
- 安全组只能**允许**流量——你无法创建显式拒绝规则

**无状态：网络 ACL**

NACL 是**无状态的**。

当你允许 8080 端口上的入站流量时，那只覆盖入站。响应（临时端口上的出站流量）必须用一条出站规则显式允许。

把它想象成金属探测器。你进门时要通过它。金属探测器不知道你已经通过过——你出去时还得再过一遍。

**NACL 规则带编号，按顺序评估。**第一条匹配的规则获胜。规则 100 在规则 200 之前评估。如果规则 100 拒绝某流量而规则 200 允许它，该流量被拒绝。

NACL 可以显式**拒绝**流量——不像只能允许的安全组。这让它们在阻止特定 IP 范围时很有用。

**默认 NACL 行为：**

- 默认 NACL（随你的 VPC 一起创建）允许所有入站和出站流量
- 自定义 NACL 默认拒绝所有流量（你必须显式允许你想要的）

**公有子网的 NACL（简化版）：**

*入站规则（按顺序评估——首个匹配获胜）：*

- 规则 100：TCP 443，来自 0.0.0.0/0 → **允许**（HTTPS）
- 规则 110：TCP 80，来自 0.0.0.0/0 → **允许**（HTTP）
- 规则 120：TCP 1024–65535，来自 0.0.0.0/0 → **允许**（临时返回端口）
- 规则 \*：所有流量 → **拒绝**

*出站规则：*

- 规则 100：TCP 443，到 0.0.0.0/0 → **允许**（HTTPS）
- 规则 110：TCP 80，到 0.0.0.0/0 → **允许**（HTTP）
- 规则 120：TCP 1024–65535，到 0.0.0.0/0 → **允许**（临时返回端口）
- 规则 \*：所有流量 → **拒绝**

规则 120（端口 1024-65535）允许的是临时端口——TCP 响应流量使用的临时高编号端口。因为 NACL 是无状态的，你必须显式允许这些端口的出站，否则你服务器的响应就出不去。

**何时用哪个**

"等等——*为什么*要这么做？"Maya 问。"如果安全组已经够用了，为什么要有两个独立的工具——安全组*和* NACL？这额外的复杂性图什么？"

答案是它们运作在不同层级，能力也不同。安全组保护单个资源，并且只能允许流量。NACL 保护整个子网，并且可以显式拒绝。两者并存意味着你可以在资源级别施加精细的允许规则，在子网级别施加大范围的拒绝规则——彼此互不干扰。

把**安全组**用作访问控制的主要层。它们更易于管理、有状态（不会因为忘记临时端口而意外阻断流量），并且支持引用其他安全组。

把 **NACL** 用于子网级别的控制，尤其是：

- **显式拒绝规则**：阻止某个特定 IP 地址或范围触及整个子网
- **紧急阻断**：某个 IP 正在主动攻击——添加一条 NACL 拒绝规则，在它触及任何资源之前把整个子网封住

你可能会想：如果安全组是有状态的，而且默认阻止所有入站，那什么时候才真正需要 NACL？安全组确实能很好地处理大多数情况。但有一件事它做不到：显式拒绝。安全组只能允许流量——如果没有规则匹配，流量默认被拒绝。你无法添加一条说"阻止这个特定 IP"的规则。为此你需要 NACL：一条带编号的拒绝规则，在特定地址范围触及子网中任何资源之前把它拦下。NACL 最有用的场景是应急响应（阻止正在进行的攻击者）以及强制执行不应依赖于单个资源配置的子网级边界。

"所以安全组是精细控制，"Maya 说，"NACL 是大开大合？"

"安全组保护单个资源，"Priya 确认道。"NACL 保护整个子网。当你想阻止某个 IP 触及你网络中的任何东西时，用 NACL。当你只想让负载均衡器能访问 API 服务器时，用安全组。"

"我们想过攻击者换一个 IP 卷土重来会怎样吗？"Priya 说。"NACL 封了一个网段。他们换到另一个。"

"那就是 GuardDuty 的用武之地，"Leo 说。"行为检测。如果同样的脚本从一个新 IP 运行，流量模式看起来还是一样的。"

"我们会走到那一步的，"Priya 说。"先做眼前的事。"

"这些每月总共要花多少钱？"Tom 问。

安全组和 NACL 本身是免费的。AWS 不按安全组数量、规则数量或 NACL 条目数量收费。成本考量是间接的：更紧的出站安全组规则可能让更少的流量经过 NAT 网关，从而减少数据处理费用。

"所以安全控制是免费的，"Rafael 说。"成本在于支撑它们的基础设施。"

"正确。为高可用而设的 NAT 网关。为那些否则要走 NAT 的服务而设的接口型 VPC 端点。那些有成本。安全组规则本身没有。"

**整合起来：分层防御**

事件之后，Priya 在白板上画出了 Nimbus 的防御层次：

```
Internet
  ↓
CloudFront + Shield (DDoS absorption)
  ↓
WAF (application-layer filtering)
  ↓
Internet Gateway
  ↓
NACL on public subnet (subnet-level rules, emergency blocking)
  ↓
ALB Security Group (HTTPS from anywhere)
  ↓
NACL on private app subnet
  ↓
EC2 API Security Group (port 8080 from ALB SG only)
  ↓
NACL on private data subnet
  ↓
RDS Security Group (port 5432 from API SG only)
```

"每一层都假设前一层可能失效，"她说。"数据库不信任网络层已经拦住了攻击者。EC2 实例不信任 ALB 已经拦住了攻击者。每一层独立执行自己的规则。"

"纵深防御，"Maya 说。

"纵深防御。穿过一层的攻击者仍然要面对下一层。没有任何一个错误配置是灾难性的。它意味着一层失守，其他层依然顶住。"

Leo 看着图。攻击者攻陷了一台 EC2 实例。他们穿过了凭证那一层。但之后的每一层都顶住了。

这就是纵深防御在实践中的样子。

**这次事件：各层拦住了什么**

回到罗马尼亚 IP 攻击：

**发生了什么**：攻击者用失窃的部署密钥向一台 EC2 实例上传了一个扫描脚本。脚本试图连接其他服务。

**什么拦住了他们**：

- RDS 安全组只允许来自 API EC2 安全组的 5432 端口入站。脚本无法用一个扫描工具够到数据库——它并没有挂上正确的安全组。
- ElastiCache 安全组只允许来自 API EC2 安全组的 6379 端口入站。
- 其他 EC2 实例只允许来自堡垒主机安全组的 SSH。

**什么没有拦住他们**：

- EC2 实例的出站规则允许 HTTPS 到 0.0.0.0/0（下载软件包所需）。脚本利用这一点向攻击者的服务器建立了出站连接。

事件之后，Priya 添加了：

- 一条阻止罗马尼亚 IP 范围的 NACL 规则
- EC2 实例上更严格的出站规则（只允许特定的已知良好目的地）
- 一项检查：每台实例上都**强制启用了 IMDSv2**（`HttpTokens=required`）——那个脚本是*在*实例上运行的，意味着它本可以向元数据服务查询实例角色的临时凭证。IMDSv2 早在第4章就启用了；Priya 验证了它在所有地方仍然是必需项，因为攻击者拿到代码执行权再加上 IMDSv1，就等于被盗的 AWS 凭证。

**读流日志：Priya 看到了什么**

调查从 VPC 流日志开始。Priya 打开 CloudWatch Logs Insights，对过去 48 小时的流日志组运行了一个查询：

```
fields @timestamp, srcAddr, dstAddr, srcPort, dstPort, action
| filter srcAddr = "10.0.10.7"
| filter action = "REJECT"
| sort @timestamp asc
```

`10.0.10.7` 就是被攻陷的 EC2 实例。REJECT 过滤器展示了被阻止的连接尝试。

结果：

```
10.0.10.7 → 10.0.10.8  port 22    REJECT   # Other EC2 instance — SSH blocked
10.0.10.7 → 10.0.10.9  port 22    REJECT   # Another EC2 — SSH blocked
10.0.10.7 → 10.0.20.8  port 5432  REJECT   # RDS — blocked by security group
10.0.10.7 → 10.0.20.9  port 5432  REJECT   # RDS replica — blocked
10.0.10.7 → 10.0.20.11 port 6379  REJECT   # Redis — blocked
```

扫描打到了每一个内部服务。每一次尝试都被拒绝了。安全组设计顶住了。

但日志里还有一条出站的 ACCEPT 记录：

```
10.0.10.7 → 185.220.101.55  port 443  ACCEPT   2847 bytes
```

那就是数据外泄的尝试——2.8 KB 数据通过 HTTPS 发往了那个罗马尼亚 IP。安全组为合法的软件包下载允许了 HTTPS 出站。攻击者利用了那条规则。

"安全组拦住了横向移动，"Priya 带着团队过日志时说。"但出站规则太宽松了。我们允许了到任何目的地的 HTTPS。我们应该只允许 HTTPS 到已知的 AWS 端点——CloudWatch、Secrets Manager、S3——以及软件包仓库的 CDN。"

她展示了更新后的安全组出站规则：

```
TCP 443 → pl-63a5400a (AWS S3 gateway endpoint prefix list)
TCP 443 → pl-02cd2c6b (AWS CloudWatch Logs)
TCP 443 → 54.239.0.0/18 (AWS package repos — narrows over time)
```

"这就消灭了那条泛用的 HTTPS 出站规则。出站 HTTPS 现在只去往已知良好的目的地。"

"那调用第三方 API 的 Lambda 函数呢？"Leo 问。

"那些走 NAT 网关，NAT 网关有自己专门的出站规则，"Priya 说。"Lambda 不使用 EC2 的安全组。不同的网络接口，不同的规则集。"

**无状态调试的故事**

事件两周后，Rafael——还在他入职的第一个月——在帮忙搭建一条新的数据管道。它涉及一个位于 VPC 中的 Lambda 函数，需要调用一个运行在 EC2 上的内部 API。

Lambda 函数超时了。每一次调用都超时。

Rafael 检查了安全组。Lambda 的安全组有一条到 EC2 安全组的 TCP 8080 出站规则。EC2 的安全组有一条来自 Lambda 安全组的 TCP 8080 入站规则。规则看起来是正确的。

他转向 Leo。"安全组看起来没问题。为什么还是超时？"

Leo 看了看子网配置。Lambda 函数在一个私有子网里。这个子网挂着 Priya 在安全加固期间应用的一个自定义 NACL。

他查看了 NACL 的出站规则：

```
Rule 100: TCP 443  → 0.0.0.0/0  ALLOW
Rule 110: TCP 5432 → 10.0.20.0/24 ALLOW
Rule *:   All      → 0.0.0.0/0  DENY
```

"NACL 允许 HTTPS 出站和 PostgreSQL 出站，"Leo 说。"它不允许 TCP 8080 出站。"

"安全组允许了啊，"Rafael 说。

"NACL 没有。而且 NACL 是无状态的。即使 Lambda 函数的安全组允许这条出站连接，子网边界上的 NACL 仍然会评估出站流量。NACL 在 Lambda 的调用离开子网之前就把它拦下了。"

"那如果我在 NACL 上给 TCP 8080 出站加一条 ALLOW——"

"你还需要给入站的临时端口加一条 ALLOW，"Leo 说。"EC2 实例的响应会从 1024 到 65535 之间的一个随机端口返回。如果 NACL 的入站规则不允许那些端口，响应在回程上就被拦住了。"

Rafael 更新了 NACL：

```
Rule 100:  TCP 443       → 0.0.0.0/0      ALLOW  (outbound)
Rule 105:  TCP 8080      → 10.0.10.0/24   ALLOW  (outbound to EC2 subnet)
Rule 110:  TCP 5432      → 10.0.20.0/24   ALLOW  (outbound to DB subnet)
Rule *:    All           → 0.0.0.0/0      DENY
```

入站这一侧：

```
Rule 100:  TCP 1024-65535 from 10.0.10.0/24  ALLOW  (return traffic from EC2)
Rule *:    All                               DENY
```

Lambda 函数立刻连上了。

"这就是为什么人们讨厌 NACL，"Rafael 说。

"这就是为什么你需要理解它们，"Priya 说。"它们制造的 bug，恰恰就是它们被设计来防止的东西——预期之外的流量。理解了无状态模型，当一条连接莫名失败时，你就确切知道该往哪里看。"

"安全组有状态——返回流量自动放行。NACL 无状态——返回流量需要显式规则，"Rafael 重复道。

"念到它成为你思维的一部分为止，"Priya 说。

**NACL 紧急阻断：/24 法则**

确认了攻击者的源 IP 范围之后，Priya 的响应是立即的：添加一条 NACL 拒绝规则。

但她没有只封那一个 IP。她封掉了整个 `/24`——攻击者活动所在的那个 256 地址的网段。

"为什么封整个 /24？"Leo 问。

"因为逐个封 IP 是一场必输的游戏。攻击者在一个网段内使用多个 IP，一个被封就轮换到下一个。封掉 /24 让事情变难——他们得换到一个不同的地址块，那要花他们时间和精力。"

那条 NACL 规则：

```
Rule 90:  ALL from 185.220.101.0/24 → DENY
```

规则 90 在任何允许规则（从规则 100 开始）之前评估。整个范围在任何允许规则被考虑之前就被封掉了。

"这适用于子网中的每一个资源？"Leo 问。

"每一个资源。这正是 NACL 的意义所在——它在流量到达任何单个资源的安全组之前生效。规则 90 上的 NACL 拒绝，意味着数据包根本走不到安全组评估那一步。"

"我们能用安全组代替吗？"

"不能。安全组只能允许流量。没有拒绝规则。如果你想阻止某个特定 IP 触及子网中的任何资源，NACL 是唯一选项。"

这就是 NACL 拒绝规则的首要使用场景：对正在进行的攻击的应急响应。安全组是主要的控制机制。NACL 是紧急刹车。

---

**安全组设计模式：按 ID 引用**

"我们想过当 EC2 实例被替换时会发生什么吗？"Priya 问。"Auto Scaling 终止旧实例并启动新实例。新实例会拿到新的私有 IP 地址。"

"如果安全组规则引用 IP 地址，"Leo 慢慢说，"那每次实例被替换我们都得更新规则。"

"完全正确。这就是为什么 VPC 内部流量的安全组规则不引用 IP 地址。"

安全组可以引用其他安全组，而不是 IP 地址。当一条规则说"允许来自负载均衡器安全组的入站"时，它的意思是"允许来自任何附加了负载均衡器安全组的资源的流量"。Auto Scaling 可以启动一千台各有新 IP 的新实例，这条规则依然有效。

Nimbus 的安全组结构：

```
nimbus-alb-sg (Load Balancer)
  - Inbound: TCP 443 from 0.0.0.0/0
  - Inbound: TCP 80 from 0.0.0.0/0

nimbus-api-sg (EC2 API instances)
  - Inbound: TCP 8080 from nimbus-alb-sg
  - Inbound: TCP 22 from nimbus-bastion-sg
  - Outbound: TCP 5432 to nimbus-rds-sg
  - Outbound: TCP 6379 to nimbus-redis-sg

nimbus-rds-sg (RDS)
  - Inbound: TCP 5432 from nimbus-api-sg

nimbus-redis-sg (ElastiCache)
  - Inbound: TCP 6379 from nimbus-api-sg

nimbus-bastion-sg (Bastion Host)
  - Inbound: TCP 22 from <office VPN IP>
```

内部流量没有任何 IP 地址。只有安全组 ID。实例被替换时，安全组成员资格会自动转移到新实例上。

"那我们计划中的微服务呢？"Rafael 问。"我们最终会有十几个服务。每个服务需要和某几个服务通信，但不是所有服务。"

"每个服务有自己的安全组，"Priya 说。"服务 A 的安全组会被引用在每一个服务 A 被允许调用的服务的入站规则里。不应该互相通信的服务，干脆不引用彼此的安全组。"

这就是微服务的**中心辐射型（hub-and-spoke）安全组模式**。一个共享数据库的安全组，入站规则里引用着五个不同服务的安全组。如果第六个服务需要访问数据库，你就把它的安全组加进数据库的入站规则。如果要移除访问权限，你就移除那个引用。没有 IP 管理。没有指向已下线服务器的过期规则。

"安全组才是身份，"Priya 说。"IP 地址只是调度的偶然产物。"

---

**最小权限防火墙：纪律**

"我们想过出站规则的正确姿态是什么吗？"Priya 在事后复盘时问。

大多数团队把 EC2 安全组的出站规则留在默认值：允许所有出站。这很方便——应用程序可以调用任何东西——但这不是最小权限。

Priya 的原则：出站规则应该和入站规则一样具体。

加固之后的 Nimbus API 安全组出站规则：

```
TCP 5432 → nimbus-rds-sg       (PostgreSQL to RDS)
TCP 6379 → nimbus-redis-sg     (Redis to ElastiCache)
TCP 443  → s3.amazonaws.com prefix list    (S3 gateway endpoint)
TCP 443  → secretsmanager endpoint         (Secrets Manager)
TCP 443  → logs endpoint                   (CloudWatch Logs)
```

没有"允许所有出站"。每一个目的地都被指名道姓。

"这维护起来工作量不小，"Leo 说。

"是比全部允许多一些维护，"Priya 承认。"但比一次数据泄露的善后少得多。攻陷那台 EC2 实例的攻击者，如果出站规则是敞开的，本可以外泄更多数据。他们用了那条 HTTPS 到任何地方的规则，就因为它在那儿。"

"而有了具体的出站规则，即使一台实例被攻陷，也只能把数据发往被批准的目的地。"

"完全正确。安全组成了遏制的最后一道防线，而不只是防御的第一道。"

## 优势与局限性

**安全组**：

- 有状态（没有临时端口的麻烦）
- 可以引用其他安全组（比 IP 更灵活）
- 只有允许规则——没有显式拒绝
- 在资源级别运作——粒度细
- 规则立即生效——没有顺序、没有优先级
- 一个资源可以附加多个安全组——所有规则合并生效

**NACL**：

- 无状态（需要包括临时端口在内的双向显式规则）
- 可以显式拒绝——对阻止已知恶意 IP 有用
- 在子网级别运作——范围更大
- 带编号的规则按顺序评估——可预测，但需要仔细管理
- 在流量到达子网中任何资源之前生效——第一道防线
- 对整个子网范围的紧急 IP 阻断很有效

**各工具的适用位置**：

默认情况下，一切都用安全组。当你需要显式拒绝规则时再加 NACL——封禁某个 IP 范围、在子网级别封禁某个端口而不依赖于单个资源的配置、或强制规定一个数据子网永远不能接收来自某个特定来源的流量。NACL 不是安全组的替代品；它是当安全组"只能允许"的设计不够用时的补充。

## 摘要

罗马尼亚 IP 事件被早已就位的安全控制遏制了——不是靠运气，而是靠设计。安全组阻止了 VPC 内部的横向移动。事件之后，NACL 增加了在子网边界显式封禁攻击者 IP 范围的能力。VPC 流日志让攻击变得可见。两个工具，两个层级，两份不同的工作——再加上能证明发生了什么的日志。

- **安全组**是单个资源的有状态虚拟防火墙。只有允许规则。所有规则同时评估。
- **NACL** 是整个子网的无状态防火墙。允许和拒绝规则。规则按编号顺序评估——首个匹配获胜。
- **有状态**意味着响应流量自动被放行。**无状态**意味着你必须显式允许双向流量，包括临时返回端口。
- 安全组是你的主要访问控制层。NACL 是子网级别的覆盖手段——尤其用于紧急阻断。
- 当 NACL 允许入站流量时，你还必须允许出站的临时端口（1024-65535），TCP 响应才能通过。
- 对于 VPC 内部流量，**按 ID 引用安全组**，而不是 IP 地址。Auto Scaling 替换实例；安全组成员资格自动转移。
- EC2 实例上的**具体出站规则**限制了一台被攻陷的实例能做什么——最小权限防火墙。
- 用流日志去看安全组和 NACL 实际在做什么。规则是理论。日志是证据。

## 考试技巧

*SAA-C03 领域：设计安全架构（领域1，任务1.2）*

- **有状态 vs 无状态**：这个区别是本章被考查得最多的概念。安全组 = 有状态 = 响应自动放行。NACL = 无状态 = 必须显式允许响应流量。
- **安全组规则**：没有显式拒绝。当一个实例附加了多个安全组时，所有规则的并集生效。所有匹配的规则同时被评估。
- **NACL 规则顺序**：规则从最小编号到最大编号评估。规则 100 在 200 之前。首个匹配获胜。底部的 `*`（星号）规则是隐式拒绝。在规则 90 加一条拒绝规则，会在 100 上的任何允许规则之前拦截。
- **临时端口**：经典的 NACL 错误是忘记允许 1024-65535 端口的出站。如果你的 NACL 允许入站 HTTP（端口 80）但不允许出站临时端口，用户能发送请求却永远收不到响应。这是最常见的 NACL 考试场景。
- **安全组引用**：你可以允许来自另一个安全组（而不只是某个 IP）的流量。这是 VPC 内部流量的推荐模式。考试经常把"允许来自 ALB 安全组的入站"作为限制 EC2 访问的正确答案。
- **默认 NACL vs 自定义 NACL**：默认 NACL 允许所有流量。自定义 NACL（你自己创建的）默认拒绝所有流量。考试场景："创建了一个新 NACL，现在流量被阻断了" → 检查缺失的允许规则。
- **封禁攻击者的 IP**：安全组无法封禁特定 IP（只能允许）。NACL 可以显式拒绝某个特定 IP 或 CIDR。考试场景："阻止某个特定 IP 触及子网中的任何资源" → NACL 拒绝规则。
- **调试连接失败**：按顺序检查：源端安全组（出站）→ 目标端安全组（入站）→ 源子网的 NACL（出站 + 临时端口）→ 目标子网的 NACL（入站）。考试里大多数连接失败是缺失的 NACL 出站规则或缺失的临时端口许可造成的。
- **多个子网与 NACL**：一个 NACL 适用于所有与之关联的子网。一个子网只能关联一个 NACL。考试可能会问，当某个特定子网的流量受影响时该更新哪个 NACL。

## 练习

**练习 1——回忆**

一名开发者向安全组添加了一条允许 443 端口流量的入站规则。她还需要添加一条出站规则来允许服务器的响应吗？为什么？

如果她改为向 NACL 添加一条允许 443 端口流量的入站规则，她需要添加出站规则吗？为什么？

**提示**：回想本章的类比——每一个分别是记得放你进来的保安，还是出门时还得再过一遍的金属探测器？

**练习 2——SAA-C03 场景**

*场景*：一家公司在公有子网的 EC2 实例上运行 Web 应用程序。应用程序接受来自互联网的 HTTPS 流量（端口 443）。用户反馈说他们能连上应用程序，但收不到响应——请求挂起并超时。

EC2 安全组有一条允许来自 0.0.0.0/0 的 TCP 443 入站规则。子网的 NACL 有一条入站规则（规则 100）允许来自 0.0.0.0/0 的 TCP 443，以及一条出站规则（规则 100）允许到 0.0.0.0/0 的 TCP 443。

问题最可能的原因是什么？

A) 安全组缺少 TCP 443 的出站规则  
B) EC2 实例没有弹性 IP 地址  
C) 安全组缺少临时端口的入站规则  
D) NACL 缺少允许临时端口（1024-65535）的出站规则

**提示 1**：安全组是有状态的——它们自动放行响应。NACL 是无状态的——它们不会。

**提示 2**：当浏览器在 443 端口连接 Web 服务器时，服务器的响应是从一个随机的临时端口（1024-65535）返回的，而不是 443 端口。

**提示 3**：NACL 有针对 443 的出站规则，但响应去的不是 443 端口。

**答案**：D

**解析**：NACL 是无状态的。当用户在 443 端口连接服务器时，服务器的 TCP 响应从一个临时端口（从 1024-65535 中随机选取）返回。NACL 的出站规则只允许 443 端口，所以响应被默认拒绝规则拦下。添加一条允许 TCP 1024-65535 的 NACL 出站规则就能修复这个问题。

**为什么不是 A？** 安全组是有状态的——不管出站规则如何，响应流量都会被自动放行。不需要出站安全组规则。

**为什么不是 B？** 弹性 IP 影响的是实例是否拥有公网 IP，而不是已建立的连接能否收到响应。

**为什么不是 C？** 临时端口用于出站的响应流量，不是入站。来自用户的入站连接走的是 443 端口，而它已经被允许了。
