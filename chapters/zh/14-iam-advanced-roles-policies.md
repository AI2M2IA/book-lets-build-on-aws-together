# 第14章：谁被允许做什么

Tom 打开了一个文本文件，访问密钥已经准备好可以粘贴了。

"EC2 实例需要从 S3 读取配置文件。我要把凭证放在服务器配置里。"

她看了看屏幕一会儿。"关掉那个文件。"

"我只是想——"

"如果有人进入那个服务器，" 她说，"他们就能得到那些密钥。而那些密钥能触及 IAM 用户被允许触及的一切。这很可能不只是 S3。"

Tom 关掉了文件。

"有一个更好的方法，" 她说。"服务器本身可以有一个角色。把它想象成职位头衔——实例不需要凭证，因为系统已经知道它是什么，以及它被允许做什么。"

Tom 看起来很怀疑。"所以服务器自己验证身份？"

"是的。没有密码。没有配置文件里的密钥。没有任何可能被意外提交到 git 的东西。"

最后那点打中了要害。Tom 两周前在 git 历史里找到了一个数据库密码。他打开了一个新的浏览器标签。

**重新审视 IAM：全貌**

第3章介绍了 IAM：用户、组、角色和策略。现在是时候深入了。

IAM 策略是 JSON 文档，指定对哪些资源允许或拒绝哪些操作。它们看起来是这样的：

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": [
        "s3:GetObject",
        "s3:PutObject"
      ],
      "Resource": "arn:aws:s3:::nimbus-assets/*"
    }
  ]
}
```

这个策略允许在 `nimbus-assets` 桶中读写对象，仅此而已。不是删除。不是列出桶。不是任何其他 S3 操作。不是任何其他 AWS 服务。

这是正确的授权方式：特定操作，特定资源。

**"管理员访问"的问题**

像 `AdministratorAccess` 这样的 AWS 托管策略是为了快速上手而设计的。它们不是为有真实团队成员的生产系统而设计的。

`AdministratorAccess` 授予对每个资源的每个操作。如果拥有这个策略的团队成员犯了错误——意外删除了 S3 桶、终止了错误的 EC2 实例、更改了安全组规则——AWS 无法阻止他们。权限已经被授予了。

如果团队成员的凭证被盗（钓鱼攻击、泄露的访问密钥、笔记本被盗），攻击者就对你的 AWS 账户中的一切拥有管理员访问权限。

"那 Soo-Jin 应该有什么？" Leo 问。

"Soo-Jin 需要做什么？" Priya 反问。

"部署 API。查看日志。别的没有了。"

"那她就得到：推送到代码流水线的能力、CloudWatch 日志的读取权限，以及别的什么都没有。"

"那……非常具体。"

"是的。这就是重点所在。"

**IAM 角色：服务的身份**

第3章将角色介绍为 EC2 实例访问 AWS 服务而无需存储凭证的方式。让我们使这具体化。

运行 Nimbus API 的 EC2 实例需要：

- 从 DynamoDB 读取（菜单）
- 写入 DynamoDB（订单）
- 将对象放入 S3（收据、上传）
- 将日志写入 CloudWatch
- 从 Secrets Manager 读取机密

与其创建一个有访问密钥的用户并将该密钥存储在 EC2 实例上（这是安全噩梦——访问密钥可以被任何有 SSH 访问权限的人读取），你为 EC2 实例创建一个具有这些确切权限的 **IAM 角色**。

EC2 实例自动承担该角色。AWS 通过实例元数据服务提供临时凭证。凭证自动轮换。没有访问密钥可以泄露。

"如果有人入侵了 EC2 实例呢？" Leo 问。

"他们可以做 EC2 角色允许的事，" Priya 说。"也就是读取菜单、写入订单和发送日志。他们不能删除 S3 桶。他们不能终止 EC2 实例。他们不能触碰 IAM。"

"因为 EC2 角色没有那些权限。"

"完全正确。"

**角色承担：服务如何成为其他服务**

角色可以被以下对象承担：

- **AWS 服务**（EC2、Lambda、ECS 任务等）
- **你自己账户中的 IAM 用户**（角色提升——你为特定任务承担具有更多权限的角色）
- **其他 AWS 账户中的 IAM 用户**（跨账户访问——另一个组织的账户可以承担你账户中的角色）
- **外部身份提供商**（Google、Active Directory、Okta——为人类用户提供联合访问）

最后一个模式——**身份联合**——是大型组织授予员工 AWS 访问权限而无需为每个人创建单独的 IAM 用户的方式。你公司的 Active Directory 有你的凭证。当你登录 AWS 时，你对 Active Directory 进行身份验证，AWS 授予你一个角色。

**权限边界：限制角色可以授予什么**

这里有一个微妙但重要的问题：默认情况下，IAM 不阻止用户授予他们目前没有的权限。

如果 Soo-Jin 有 `iam:CreatePolicy` 和 `iam:AttachUserPolicy`，她可以创建一个授予 S3 写入访问权限的策略，并将其附加到自己——即使她现有的策略只允许 S3 读取。这类漏洞称为**权限提升**，这正是为什么存在权限边界。

但如果你想将 IAM 权限创建委托给团队负责人，同时确保他们不能授予超出你预期的权限呢？

**权限边界**设置可以授予身份的最大权限。即使身份附加的策略更广泛，有效权限也受到权限边界的限制。

示例：你给团队负责人一个允许他们创建 IAM 角色的策略。但你附加了一个权限边界，说明"这个团队负责人创建的角色永远不能有 S3 删除访问权限"。即使团队负责人创建了一个具有完整 S3 访问权限的角色，边界也阻止 S3 删除生效。

这是一个高级概念，但它出现在考试中，反映了组织如何在规模上委托 IAM 管理。

**IAM Access Analyzer：审计权限**

Priya 花了两天时间审查团队的 IAM 设置。她发现：

- Leo 的个人用户有管理员访问权限（如前所述）
- 一个旧 Lambda 函数有读取所有 S3 桶的权限（测试遗留下来的）
- 一个服务角色对不再存在的 DynamoDB 表有写入权限

这是正常的。IAM 配置会随时间积累杂质。

**IAM Access Analyzer** 是一个 AWS 服务，自动识别与外部实体共享的资源（S3 桶、IAM 角色、KMS 密钥、Lambda 函数）。它还识别过于宽松的策略。

定期的 IAM 审计应该是你运营的一部分。权限会增长；它们很少自然收缩。Access Analyzer 帮助让不可见的东西可见。

**服务控制策略：组织级别的护栏**

如果你的 AWS 环境成长为多个账户（大型团队的常见模式——开发账户、测试账户、生产账户），**AWS Organizations** 让你从中央账户管理它们。

在 Organizations 中，**服务控制策略（SCP）**应用影响账户中*每个* IAM 实体的护栏，包括管理员。

示例 SCP："开发账户中的任何人都不能在 eu-west-1 区域创建 EC2 实例。"

即使有人在开发账户中拥有管理员访问权限，他们也无法违反这个 SCP。它在组织级别强制执行，高于账户级别。

SCP 不授予权限——它们限制权限。它们定义账户中任何 IAM 实体可以拥有的最大权限。

## 优势与局限性

**为什么 IAM 角色和最小权限很重要**：

- 当凭证被盗时限制爆炸半径
- 要求攻击者通过多个系统升级，而不是立即获得完全访问权限
- 提供审计跟踪——CloudTrail 记录哪个角色做了什么
- 强制对访问做出有意识的决定——"这个服务实际需要什么？"

**事情变得复杂的地方**：

- 编写精确的 IAM 策略需要理解每个服务的操作/资源模型（每个服务有几十个操作）
- 过于严格的策略会破坏应用程序——跨多个服务调试"拒绝访问"错误很耗时
- IAM 以轻微延迟传播变化（通常几秒钟，有时更多）——可能导致令人困惑的时序问题
- 跨账户角色需要仔细的信任策略配置

## 摘要

- 在生产中避免**管理员访问**——它用于设置，不用于操作。
- IAM 策略指定**效果**、**操作**和**资源**——对这三者都要具体。
- 将策略附加到**组**（针对人）和**角色**（针对服务）。
- EC2 实例、Lambda 函数和其他 AWS 服务应该使用 **IAM 角色**，而不是访问密钥。
- **权限边界**限制任何身份可以拥有的最大权限，无论附加的策略如何。
- **SCP**（服务控制策略）应用全组织范围的限制，即使管理员也无法覆盖。
- **IAM Access Analyzer** 识别过于宽松的策略和对资源的外部访问。

## 考试技巧

*SAA-C03 领域：设计安全架构（领域1，任务1.1）*

- **EC2 的 IAM 角色**：当 EC2 需要访问 S3、DynamoDB、Secrets Manager 或任何 AWS 服务时的标准答案。永远不要在实例上存储访问密钥。
- **策略评估逻辑**：当 IAM 评估请求时，它使用显式允许/拒绝层次结构。显式**拒绝**始终胜出，即使在链中其他地方有显式允许。默认值是拒绝。
- **权限边界**：用于委托 IAM 管理。考试场景："允许开发者为他们的 Lambda 函数创建角色，但阻止他们授予超出他们自己所拥有的权限。" → 权限边界。
- **SCP 不授予权限**：它们只是限制。如果 SCP 允许 S3 但 IAM 策略拒绝它，S3 被拒绝。如果 SCP 拒绝 S3 但 IAM 策略允许它，S3 被拒绝。
- **基于资源的策略**：某些 AWS 服务（S3、SQS、Lambda）有基于资源的策略——附加到资源而不是身份的权限。这些与 IAM 策略一起工作。
- **跨账户访问**：账户 A 中的 IAM 角色，带有允许账户 B 承担它的信任策略。账户 B 的用户/角色然后使用 `sts:AssumeRole` 获取账户 A 中的临时凭证。
- **IAM 用户 vs 联合访问**：对于大型组织，联合访问（通过 IAM Identity Center 或直接与 IdP 联合）优于单独的 IAM 用户。

**练习 2——考试练习**

*场景*：一个 Lambda 函数需要从 S3 桶读取，并向 DynamoDB 表写入。一个开发者为了在开发期间方便，给了 Lambda 函数 `AdministratorAccess` 角色。在移到生产之前，安全团队希望遵循最小权限原则。

以下哪个是*最佳*方法？

A) 创建一个新的具有 S3 读取和 DynamoDB 写入权限的 IAM 用户；生成访问密钥；将密钥存储在 Lambda 环境变量中  
B) 向 Lambda 函数的执行角色附加一个内联策略，在特定桶上授予 `s3:GetObject`，在特定表上授予 `dynamodb:PutItem`  
C) 保留 `AdministratorAccess` 但添加一个阻止除 S3 和 DynamoDB 之外所有操作的 SCP  
D) 创建一个具有 S3 读取和 DynamoDB 写入权限的 IAM 组，并将 Lambda 函数添加到该组

**提示 1**：Lambda 函数使用执行角色，而不是访问密钥。哪个选项尊重这一点？

**提示 2**：最小权限意味着对特定资源的特定操作，而不是宽泛策略。

**提示 3**：IAM 组包含用户，不包含 Lambda 函数。

**答案**：B

**解析**：Lambda 执行角色应该只拥有函数需要的特定权限。范围限定在特定操作（`s3:GetObject`）和特定资源（桶 ARN、DynamoDB 表 ARN）上的内联策略是最小权限的实现。

**为什么不是 A？** 在 Lambda 环境变量中存储访问密钥是安全反模式——任何有 Lambda 控制台访问权限的人或通过执行上下文都可以读取这些密钥。Lambda 函数通过 IAM 使用临时凭证的执行角色。

**为什么不是 C？** SCP 在组织/账户级别应用，不作为每个函数的权限控制。带 SCP 的 AdministratorAccess 是错误的层级。

**为什么不是 D？** Lambda 函数不能添加到 IAM 组。组只针对 IAM 用户。
