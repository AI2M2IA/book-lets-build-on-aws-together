# 第6章：跟着你走的磁盘

Tom 有一支红笔，还有一个让 Leo 紧张的习惯。

每个周六早上，他端着一杯咖啡坐下来，打印点什么。不是邮件。不是报告。他打印的是 Nimbus 正在运行的东西的清单，然后像查账本一样逐行阅读，笔握在手里。他从第二周就开始这样做了。打印机预热的声音已经成了周末的一部分。

Leo 称之为"Tom 做的那件让 Leo 觉得自己犯了什么错的事"。

那个周六，Tom 圈了点什么，然后一句话不说地把打印件留在了 Maya 的桌子上。

她周一早上发现了它。一个圆圈。页边一条批注，寥寥数字：

*全部。一台机器。*

照片现在安全地待在 S3 里了——那个问题已经解决。但数据库仍然和 Web 服务器在同一台 EC2 实例上。订单历史、客户记录、两个月的交易数据。应用程序和它底下的一切，共用一块虚拟磁盘。

"如果实例崩溃，数据库会怎样？" Maya 手里拿着打印件问。

"也跟着崩溃，" Leo 说。

"那数据呢？"

"取决于数据库怎么存储它。"

那个"取决于"就是问题所在。

**EC2 实例如何存储数据**

当 EC2 实例运行时，它的操作系统存放在某块磁盘上。那块磁盘称为**根卷**。默认情况下，这是一个 **EBS 卷**——即使你从来没想过它。

但还有另一种东西：EC2 实例还有**实例存储**（instance store）。

实例存储是物理连接在运行你的虚拟机的底层硬件上的临时存储。它极快——比 AWS 中几乎任何其他存储选项都快。但它有一个陷阱。

实例存储是**临时的**。

当实例停止或被终止时，实例存储的数据就没了。永久地。无法恢复。AWS 对这一点的警告并不响亮，所以团队往往是这样发现它的：靠丢数据。

实例存储适用于缓存、临时处理文件和暂存空间。绝不要放你在乎的数据。

**EBS：持久磁盘**

想象一块可以插到你的 EC2 实例上的外置硬盘——拔掉它它也不会消失，需要的话还能把它移到另一台机器上。AWS 把它叫做 **EBS**：Elastic Block Store（弹性块存储）。

EBS 是面向 EC2 实例的持久块存储。

块存储意味着它的行为像一块真正的硬盘：你的操作系统可以在上面创建文件系统，在任意位置读写任意字节，在上面运行数据库，把它完全当作一块挂接的磁盘来对待。

关键属性：

**持久。** 与实例存储不同，EBS 卷能在实例停止、启动，甚至实例终止后存活（取决于配置）。即使没有实例在使用它，数据也留在卷上。

这里有一个配置细节：当你创建 EC2 实例时，根卷有一个叫"终止时删除"（Delete on Termination）的设置。默认情况下它是 true——实例被终止时根卷会被删除。而对于你额外挂接的数据卷，默认值是 false——实例被终止后它们会保留下来。两个设置都可以更改。如果你想让根卷在实例终止后保留（用于取证分析或数据恢复），就关闭"终止时删除"。如果你想让数据卷被自动清理，就开启它。

**可挂接、可分离。** EBS 卷可以从一个实例分离，再挂接到另一个实例。如果你需要迁移数据或从一台故障实例中恢复，你可以分离卷，然后在别处重新挂接。

分离-重挂的流程比快照恢复慢，但它保留了卷的精确状态——所有未提交的写入、所有缓存数据、确切的文件系统状态。这使它适用于取证分析（把卷挂到一台分析实例上，而不启动原系统）和数据迁移（把数据库卷移到一台更大的实例上，而无需做快照）。

**单一挂接（基本上）。** 默认情况下，一个 EBS 卷同一时间只挂接在一台 EC2 实例上。一台实例可以有多个 EBS 卷，但一个 EBS 卷不能同时被多台实例挂载（有一个例外：EBS 多重挂接，它的适用场景有限且限制很多）。

EBS 多重挂接允许 io1/io2（预置 IOPS）卷同时挂接到同一可用区内的多台实例。这听起来像是解决了"共享存储"问题，但它带有严格的约束：挂接实例上的应用程序必须能自行协调并发访问——共享文件系统语义（锁管理、写入顺序）EBS 是不提供的。在实践中，EBS 多重挂接用于那些自行处理协调的集群化数据库应用。对于通用的共享文件访问，EFS 更简单、更合适。

EBS 的类比：一块插在一台笔记本电脑上的外置硬盘。笔记本（EC2 实例）可以读写它。用完之后，你可以拔下它，插到另一台笔记本上。

**EBS 卷类型**

并非所有 EBS 卷都相同。AWS 提供几种性能和成本特征各异的类型。

**gp3（通用型 SSD）**：大多数工作负载的默认选择。性能和价格的良好平衡。适用于启动卷、小型数据库和开发环境。

在 gp3 成为默认之前，还有 **gp2**——你在现实环境中仍会遇到它。gp2 卷的 IOPS 性能直接与卷大小挂钩：每 GB 给你 3 IOPS，上限 16,000 IOPS（需要一个 5,334 GB 的卷才能达到）。吞吐量上限为 250 MB/s。这种耦合意味着在 gp2 上，要获得更多 IOPS 的唯一办法是把卷做得更大——即使你并不需要多出来的空间。gp3 打破了这种依赖：无论大小，它起步就是 3,000 IOPS 和 125 MB/s，并允许独立配置 IOPS 和吞吐量，而且价格更低。AWS 建议新卷使用 gp3，但由于许多现有工作负载仍在 gp2 上运行，两者你都得了解。

**io2（预置 IOPS SSD）**：面向 I/O 密集型工作负载的高性能选项。你指定需要多少每秒 I/O 操作数（IOPS），AWS 保证该性能。适用于大型生产数据库。

**st1（吞吐量优化型 HDD）**：针对大型顺序读写优化的磁性存储。比 SSD 便宜，但随机 I/O 更慢。适用于数据仓库和日志处理。

**sc1（冷 HDD）**：最便宜的 EBS 选项。用于不频繁访问的数据。不适用于任何时间敏感的场景。

"io2 比 gp3 贵多少？" Tom 从笔记本上抬起头问。

Leo 调出了定价页面。io2 每 GB 的费用大约是 gp3 的三倍，另外还要按预置的 IOPS 单独收费。Tom 记下了差距。"那我们就先用 gp3，等数据库真正需要性能保证的时候再说。"

考试不要求你背下所有类型。它考的是你把需求匹配到正确类型的能力：IOPS 需求 → io2。对成本敏感的顺序工作负载 → st1。一般 Web 应用程序 → gp3。

**IOPS 与吞吐量：为什么这个区分很重要**

接下来那个周二，Tom 查看完 CloudWatch 后又回到了 EBS 卷的问题上。

"我在 EBS 仪表盘上看到两个指标，" 他说。"IOPS 和吞吐量。它们是两回事？"

是的。

**IOPS**（每秒输入/输出操作数）衡量磁盘每秒能处理多少次读或写操作。每次操作通常很小——4KB 到 256KB。高 IOPS 对那些做大量小型随机读写的数据库很重要：获取单条记录、更新记录、处理并发查询。

**吞吐量**（以 MB/s 计）衡量每秒移动多少数据。高吞吐量对顺序型工作负载很重要：读取大型日志文件、流式分析、加载大型数据集。

数据库通常需要高 IOPS、中低吞吐量。扫描大表的数据仓库需要高吞吐量，IOPS 适中即可。

Tom 一直在观察 Nimbus 数据库的 CloudWatch 指标。晚餐高峰时段 IOPS 出现尖峰——应用程序获取菜单项和订单数据时产生的短促随机读取。吞吐量很低。这个模式吻合一个需要更好 IOPS、而不是更好吞吐量的数据库工作负载。

"所以如果数据库变慢，" Tom 说，"我们要在升级卷之前先查清是 IOPS 受限还是吞吐量受限？"

"对，" Priya 说。"从 gp3 升到 io2 是花钱买 IOPS。如果问题在吞吐量，这次升级帮不上忙。先看指标。"

这正是避免花大价钱做存储升级却解决了错误问题的方法。

**EBS 快照：备份**

这是一个经常拯救公司的东西。

**EBS 快照**是一个 EBS 卷在某个时间点的备份，存储在 S3 中（不过你通过 EBS 界面访问它，而不是直接通过 S3）。快照是增量的：第一个快照捕获完整的卷；后续快照只存储自上一次以来变化的内容。

你可以从快照创建一个新的 EBS 卷——恢复到数据库损坏、错误部署或意外删除之前的某个时间点。

你应该把快照自动化。AWS 为此提供了 **Amazon Data Lifecycle Manager**：定义一条策略（每 6 小时拍一次快照，保留最近 7 天），它就会自动运行。

Priya 在数据库投入生产之前就把这个配好了。

Leo 没想到过这件事。

"我们想过快照任务悄无声息地失败会怎样吗？" Priya 问。"如果策略在跑，但快照其实是无效的呢？"

他们当天下午就测试了恢复流程。

Priya 为 Nimbus 生产数据库制定的完整快照备份策略，在她有时间正式写成文档之后是这样的：

- **每日快照**，保留 7 天。覆盖常规恢复场景：一次错误的部署、一次意外删除、一周之内发现的数据损坏事件。
- **每周快照**（每周日凌晨 2 点执行），保留 30 天。覆盖问题没有被立即发现的场景——几周之后才注意到的细微数据损坏。
- 跨区域快照复制到 `us-east-1`，每周一次，保留 30 天。覆盖整个 `us-west-2` 区域不可用、Nimbus 需要在别处重建数据库的场景。

"快照好像有点多，" Leo 说。

"第一个之后的每个增量快照都很小，" Priya 说。"你只存变化的部分。总存储费用不高。"

Tom 已经查过价格了。一个 50GB 数据库的每日快照保留 7 天，加上保留 30 天的每周快照——大约每月 3 到 5 美元。而万一数据库哪天损坏了，没有它们的代价高到无法估量。

"那快速快照还原呢？" Leo 问。"我看设置的时候看到过那个选项。"

**快速快照还原**（Fast Snapshot Restore，FSR）是 EBS 的一项功能，它消除了首次使用刚还原的快照时通常出现的 I/O 性能损失。没有 FSR，新还原的 EBS 卷在最初的几分钟到几小时里性能很差，因为数据是从 S3 惰性加载的——尚未拉取到卷上的数据，读取时要去访问 S3。在某个可用区对一份快照启用 FSR 后，还原出来的卷立刻就具备完整性能。

FSR 要额外收费——你按"每份快照、每个可用区、每小时启用"来付费。对 Nimbus 的灾难恢复快照而言，偶尔的使用撑不起 FSR 的持续费用。但对于一份在紧急情况下需要在几分钟内还原并投入运行的生产数据库快照来说，FSR 物有所值。

"在我们真正会用于灾难恢复的那份每周快照上启用 FSR，" Priya 说。"不要在保留窗口内的每个每日快照上都开。"

Tom 把这笔成本核算加进了他的电子表格。

**用于灾难恢复的跨区域快照复制**

EBS 快照存放在创建它们的区域里。如果整个 `us-west-2` 区域宕机，你在 `us-west-2` 的快照就无法访问。

解决方案：**跨区域快照复制**。你可以把一份 EBS 快照复制到另一个区域，这样即使主区域不可用，你也有一份可用的备份。

AWS Data Lifecycle Manager 支持把自动化的跨区域复制作为快照策略的一部分：在 `us-west-2` 每天拍一次快照，每周自动复制一次到 `us-east-1`。灾难来临时，在 `us-east-1` 启动一台新 EC2 实例，从跨区域快照恢复，更新 DNS 端点，继续运营。

"这就是我们数据库的灾难恢复计划，" Priya 向团队展示策略文档时说。"不是完整的多区域架构——那超出了我们现在需要的复杂度。但如果 `us-west-2` 彻底宕掉，我们能在两小时内在 `us-east-1` 恢复。"

"两小时的停机时间，" Tom 说。

"对比无限长的停机时间，" Priya 说。

Tom 承认了这个区别。

**EBS 加密：为什么不能原地加密的故事**

Nimbus 生产数据库运行了六周时，Priya 发现了一个问题。

"这个 EBS 卷没有加密，" 她说。

"我们能给它加密吗？" Leo 问。

"能。但不能原地加密。"

EBS 加密的关键在于：你不能直接加密一个已存在的、未加密的 EBS 卷。数据已经以明文写在上面了。要加密它，你必须：

1. 给未加密的卷创建一份快照
2. 复制该快照，并在副本上启用加密
3. 从加密快照创建一个新的加密 EBS 卷
4. 停止实例
5. 分离旧的未加密卷
6. 挂接新的加密卷
7. 启动实例，验证一切正常

这个流程有一个停机窗口——停止、分离、挂接、启动这一串操作。对 Nimbus 这种小数据库来说，窗口约为十五分钟。对于几百 GB 的大型生产数据库，快照和复制过程会花更长时间，不过实际的实例停机时间仍然只是停止/启动那一段。

"为什么不能直接拨个开关？" Leo 问。

"因为磁盘上已有的数据是未加密的字节，" Priya 说。"AWS 不读取并重写每一个块就没法重新加密它们——而这正是快照复制流程做的事。它从源快照读取每一个块，逐个加密，再写入新快照。"

Leo 走完了这套流程。新的加密卷挂接好了。实例重新上线。数据库跑在了一个加密卷上。

"新建的 EBS 卷可以默认加密，" Priya 说。"有一个账户级设置。每个新卷都会自动加密。我们本应该在第一天就把它打开。"

她打开了它。从那时起，Nimbus AWS 账户中创建的每一个 EBS 卷都默认加密——不需要任何额外步骤。

**EFS：共享文件柜**

EBS 是连接到一台实例的磁盘。如果多台实例需要同时访问相同的文件怎么办？

你需要的是类似办公室中央那个文件柜的东西——任何人都可以走过去，抽出一份文件，放回去，下一个人立刻看到变化。多个人，同时，访问同一份存储。

AWS 把它叫做 **EFS**：Elastic File System（弹性文件系统）。

EFS 是一个托管的网络文件系统。多台 EC2 实例可以同时挂载同一个 EFS 文件系统，并对共享文件进行读写。这是 EBS 不提供的关键能力。

说白了：

EBS 是插在一台笔记本上的外置硬盘。同一时间只有那台笔记本能用它。

EFS 是办公室中央的文件柜。任何团队成员都可以走过去，拉开抽屉，读一份文件，放回点东西。

**什么时候需要 EFS？**

- 当多台 EC2 实例需要共享文件时——内容管理系统、共享配置文件、共享媒体库
- 当你有一个水平扩展的应用程序、所有实例都需要访问相同数据时
- 当你需要一个能在实例故障后幸存的持久文件系统时

EFS 通过网络以 NFS 协议（具体是 NFSv4）访问。任何与 EFS 挂载目标有网络连通的 EC2 实例都能挂载它——包括同一区域内不同可用区的实例。你在每个可用区配置挂载目标，实例连接到最近的挂载目标以获得最佳性能。

实际意义是：EFS 开箱即用地跨可用区工作。如果你在 `us-west-2a` 和 `us-west-2b` 的 Web 服务器都挂载着同一个 EFS 文件系统，`2a` 里的服务器写入的文件，`2b` 里的服务器立刻可见。这就是 EBS 无法提供的共享文件系统行为。

**EFS 性能模式**

EFS 有两种与容量规划相关的吞吐量模式：

**弹性吞吐量**（Elastic Throughput，大多数新文件系统的默认值）：EFS 根据实际使用量自动上下调整吞吐量。你不需要预置吞吐量水平。用多少付多少。对于吞吐量需求波动的可变工作负载——比如 Nimbus，周一早上的流量和周五晚上的流量截然不同——这是正确的模式。

**预置吞吐量**（Provisioned Throughput）：你指定吞吐量水平，与存储的数据量无关。当你的工作负载需要持续的高吞吐量、超出弹性模式下存储数据量所能提供的水平时，它很有用。如果你运行的构建系统无论存了多少数据每分钟都要读几十 GB，预置吞吐量就是合适的。

还有第三种模式，**突增吞吐量**（Bursting Throughput），它是 EFS 最初的行为方式，对于在弹性模式推出之前创建的文件系统仍然是默认值。在突增模式下，吞吐量随你存储的数据量扩展：每 GB 给你 50 KB/s 的基线，外加突增积分——当你低于基线时积累，需要更高吞吐量时消耗（小型文件系统最高可达 100 MB/s，大型文件系统可达基线的若干倍）。对于访问模式不可预测或有尖峰、且文件系统足够大、能攒下可观突增积分的工作负载来说，它是正确的选择。如果你的文件系统很小、访问模式又有突发性，你可能很快烧光积分——盯住 CloudWatch 的 `BurstCreditBalance` 指标，随时掌握自己的位置。

Tom 的问题脱口而出："弹性模式更贵吗？"

"取决于使用模式，" Leo 说。"用弹性模式，你为实际消耗的吞吐量付费。用预置模式，即使你没在用，也要为你指定的吞吐量付费。"

"所以对可变工作负载来说，弹性通常更便宜，" Tom 说。

"通常，" Priya 说。"做决定之前先去 CloudWatch 查一下你的实际吞吐量模式。"

EFS 还有两种性能模式：**通用模式**（General Purpose，低延迟，适合大多数工作负载，是默认值）和 **Max I/O**（为高度并行的工作负载提供更高吞吐量，代价是延迟略高）。通用模式能应对绝大多数使用场景。Max I/O 是为那些需要同时进行成千上万次文件系统操作的应用设计的——大规模媒体处理流水线、有大量并行读取者的科学计算工作流。

**EFS 与 S3 的区别：** EFS 是文件系统（文件夹、文件、权限、锁）。S3 是对象存储（上传、下载，没有文件系统语义）。EFS 比 S3 贵得多——EFS 标准约为每 GB 每月 0.30 美元，而 S3 标准是每 GB 每月 0.023 美元。对于整存整取的文件用 S3。对于应用程序通过标准文件系统操作频繁读写的文件用 EFS。

**EBS 对应一台实例，EFS 对应多台**

EBS/EFS 的抉择归结为一个问题：有多少台实例需要同时访问这份存储？

如果你在 EBS 上构建一个水平扩展的应用，那么每台实例都有自己的磁盘——但当用户向实例 A 上传文件时，实例 B 看不见它。这对数据库没问题（每个数据库有自己的磁盘），但对共享内容来说是坏的。如果你需要共享访问，答案是 EFS——但 EFS 每 GB 比 S3 贵，随机 I/O 的延迟又比 EBS 高。正确的选择完全取决于你的应用程序怎么使用这些数据。

**选择正确的存储**

到这里你已经见过 AWS 中的三种存储类型。让我们把决策说得干脆利落。

| 需求 | 存储类型 |
|---------------------------------------|------------------|
| 数据库需要持久、快速的磁盘 | EBS（gp3 或 io2） |
| 多台服务器需要共享文件 | EFS |
| 文件、备份、图片、大型对象 | S3 |
| 临时计算暂存空间 | 实例存储 |
| 最低成本的长期归档 | S3 Glacier |

你可能会想：既然 EFS 能让多台实例共享文件，为什么不干脆什么都用它？因为 EFS 每 GB 的费用显著高于 S3，而它的随机 I/O 延迟又比本地 EBS 高。它是共享文件系统访问的正确工具——不是通用文件存储或数据库存储的工具。

做对这个决定很重要。在需要 EFS 的地方用 S3 会增加运营复杂性。在需要 EFS 的地方用 EBS 会在你扩展时引发故障。在需要持久性的地方用实例存储会丢数据。

Priya 把这张表打印出来，贴在了墙上。

"每次我们新增一个存储需求，" 她说，"都从这里开始。"

我们走几个真实场景，把这个决策落到实处：

**场景 A**：一个机器学习训练任务运行在一台 GPU EC2 实例上，需要读取一个 200GB 的数据集。任务每天跑一次，耗时两小时。数据集由多个研究团队共享。

决策：S3。数据集很大、每次任务读一遍、需要共享。S3 便宜、持久，任何 EC2 实例或任何团队的账户都能访问。GPU 实例通过 S3 API 读取它。这里不需要文件系统。

**场景 B**：一个 WordPress 站点运行在负载均衡器后面的四台 EC2 实例上。WordPress 把插件文件、主题文件和用户上传内容存放在服务器上的某个目录里。四台实例都需要读写相同的文件。

决策：EFS。WordPress 使用文件系统语义——它创建目录、写文件、按路径读文件。改用 S3 意味着要重写 WordPress 的插件生态。EFS 以标准 NFS 文件系统的形式挂载，WordPress 天生就能跟它配合。

**场景 C**：一个 PostgreSQL 数据库运行在一台 EC2 实例上。它的查询执行和索引查找需要快速的随机 I/O。

决策：EBS（gp3 或 io2）。数据库需要低延迟的块存储来支撑小型随机读写。S3 太慢，也不支持文件系统语义。EFS 的随机 I/O 延迟高于 EBS。

规律是：文件的默认选择是 S3。当某台特定实例需要块存储时加 EBS。当多台实例需要共享文件系统时加 EFS。实例存储只用于临时暂存空间。

## 当 EFS 不够用时：Amazon FSx

下一堂存储课不是以一次故障或一场白板辩论的形式到来的。它以一份销售合同的形式到来——那种 Maya 自门户上线以来一直在追的合同，那种花了整整一个季度的演示和跟进电话才签下来的合同。餐厅运营者门户上线三个月后，Nimbus 签下了第一个多门店客户：Copper Kettle，一家家族经营的连锁集团，在中西部有十几家门店。Maya 主导了这笔交易。Tom 搭好了财务模型。Leo 在墨迹未干之前就开始规划技术集成了。

然后他读到了 Copper Kettle IT 团队提供的基础设施说明。

"他们的文件服务器是 Windows 的，" 他说。"全是 Windows。他们的后厨管理软件、HR 系统、排班工具——所有这些都往 Windows 文件服务器上的共享盘里写。SMB 协议。Active Directory 身份验证。"

"我们能把它们搬到 EFS 上吗？" Maya 问。

Leo 摇了摇头。"EFS 用的是 NFS。他们的应用说的是 SMB。这是两种不同的协议。Copper Kettle 的软件根本不知道 NFS 是什么。你不能直接把它指向一个 EFS 挂载点。"

"所以我们用不了 EFS。"

"这件事上用不了。有另外一个服务。"

**FSx for Windows File Server：Windows 版的 EFS**

**Amazon FSx for Windows File Server** 是一个完全托管的、Windows 原生的共享文件系统。它支持 SMB（Server Message Block）协议——Windows 服务器、Windows 应用程序和本地 Windows 文件共享几十年来一直在用的协议。它与 Active Directory 集成，支持 Windows ACL（文件级权限），并支持 Windows 应用程序真正依赖的那些 Windows 专有特性。

可以把它理解为 EFS，但面向 Windows——带着你的 Active Directory 环境早已习以为常的全部 Windows 专有特性。Copper Kettle 的后厨管理软件连接它的方式，会和当初连接本地文件服务器一模一样。应用程序不变。协议不变。数据只是从芝加哥某处地下室里的一台服务器，搬到了一个托管的 AWS 服务上。

针对 Copper Kettle 的迁移：Leo 创建了一个 FSx for Windows File Server 文件系统，把它接入 Copper Kettle 的 Active Directory（通过 AWS Managed Microsoft AD 延伸到 AWS），并映射了原有的盘符。后厨软件在它预期的位置原封不动地找到了它的文件共享。

"那个每月多少钱？" Tom 问。

Leo 已经查过了。FSx for Windows 按每 GB 存储每月计价——比 EFS 贵，比 S3 贵得多，但比在十几个门店各自维护 Windows 文件服务器便宜太多。Tom 没有异议地把数字记了下来。

**FSx for Lustre：当你的 ML 任务要喂饱几百块 GPU 时**

与此同时，Leo 已经开始在业余时间给一个推荐引擎做原型——根据顾客的历史行为以及相似顾客的点单，预测他们可能想点什么菜。训练数据还很小，但这个实验把他带进了一个兔子洞：认真做 ML 的团队是怎么给模型喂数据的——每次运行都要从 S3 读取数百 GB 的训练任务。

"案例研究里反复出现的模式，" 他在下一次团队午餐上汇报说，"是训练任务被 I/O 卡住。昂贵的 GPU 有 40% 的时间在空转，等下一批数据。"

这和共享文件存储是两个不同的问题。这是一个高性能计算（HPC）问题：当你有几百个处理单元都需要同时、以极高吞吐量、从同一个数据集读取数据时。

**Amazon FSx for Lustre** 是 Lustre 并行文件系统的完全托管实现。Lustre 正是为这种场景而生——跨大量并发客户端、以极高吞吐量进行并行读取。它与 S3 原生集成：你把 FSx for Lustre 指向一个 S3 桶，它就自动让那些数据通过 Lustre 文件系统可用。训练任务从一个本地挂载点读取；FSx 在幕后从 S3 流式拉取数据。

当你的 ML 训练任务需要同时给几百块 GPU 喂数据时，FSx for Lustre 就是那个工具。金融建模、基因组学工作负载和视频渲染也一样——任何瓶颈在并行 I/O 吞吐量、而不是存储容量的工作负载。

Leo 收藏的那篇案例研究用两个数字讲完了整个故事：训练任务迁移到 FSx for Lustre 后，GPU 利用率从 60% 升到 94%，原本要跑六小时的训练在三个半小时内完成。Nimbus 在很长一段时间里都用不上那种马力——但 Leo 把这个模式归了档，留给推荐引擎长大成人的那一天。

**其他 FSx 选项**

AWS 还提供 **FSx for NetApp ONTAP**——面向那些本地已经运行 NetApp 存储、想要多协议访问（同一个文件系统同时提供 NFS、SMB 和 iSCSI）的企业——以及 **FSx for OpenZFS**，面向需要文件系统级 ZFS 专有特性（如快照和克隆）的工作负载。两者都是面向拥有特定既有基础设施或需求的组织的专门工具。

对大多数团队来说，决策是在四种 FSx 变体和 EFS 之间做。问题永远是同一个：这个工作负载说什么协议，它需要什么样的性能特征？

> **考试技巧——Amazon FSx**
>
> *SAA-C03 领域：设计高性能架构（领域3，任务3.1）*
>
> - **FSx for Windows = SMB + Active Directory + Windows 工作负载**。考试信号："Windows 文件服务器"、"SMB 协议"、"Active Directory 集成"、"直接迁移（lift-and-shift）Windows 应用"。看到这些措辞中的任何一个，答案就是 FSx for Windows。
> - **FSx for Lustre = HPC + ML 训练 + 并行 I/O + S3 集成**。考试信号："机器学习训练"、"高性能计算"、"HPC"、"并行文件系统"、"I/O 密集型工作负载"、"GPU 集群"、"将文件系统与 S3 集成"。看到这些措辞，答案就是 FSx for Lustre。
> - **EFS 不是这两者的替代品。** EFS 是面向 Linux 工作负载的 NFS。它不会说 SMB。它也不是并行高性能文件系统。在需要 FSx 的地方用 EFS，意味着应用程序跑不起来（Windows），或者被 I/O 卡死（HPC）。
> - **FSx for NetApp ONTAP 和 FSx for OpenZFS** 出现的频率较低，但信号很有辨识度。"迁移现有的 NetApp/ONTAP 存储"、"多协议访问（NFS + SMB + iSCSI）"或"SnapMirror" → FSx for NetApp ONTAP。"ZFS"、"带即时快照/克隆的 NFS"或"迁移本地 ZFS 文件服务器" → FSx for OpenZFS。
> - 速查："SMB 或 Windows 文件服务器" → FSx for Windows。"机器学习训练或高性能计算" → FSx for Lustre。"NetApp/多协议" → FSx for ONTAP。"ZFS" → FSx for OpenZFS。

## 通往云端的桥梁：AWS Storage Gateway

Nimbus 迄今为止最大的潜在客户——一家名叫 Meridian Kitchen 的区域连锁，横跨三个州、二十家门店——带来了一个 `aws s3 cp` 解决不了的问题。

Meridian 多年的运营数据都存放在本地文件服务器上。菜谱、发票、后厨监控录像、供应商合同。不是几个 GB。是几个 TB。而产生和消费这些数据的软件——他们的后厨管理系统、开票平台、HR 工具——全都通过 NFS 或 SMB 往本地文件共享里写。重写那些应用程序不现实。一夜之间搬走所有数据也不现实。

"那我们怎么开始把他们的数据弄进 AWS，" Maya 问，"又不让他们改动任何一个应用程序？"

"正好有个服务就是干这个的，" Priya 说。"它以虚拟机的形式跑在他们的数据中心里，在他们现有软件眼里就是一台普通的文件服务器或存储设备，背地里悄悄把所有东西存进 AWS。"

那个服务就是 **AWS Storage Gateway**：一个把本地环境连接到 AWS 存储的混合存储服务。它用应用程序已经理解的协议向它们提供存储，而实际上把数据持久化到 S3、S3 Glacier，或者以 EBS 快照的形式保存。

它有三种网关类型，各自解决一种不同的本地问题。

**文件网关**（File Gateway）向本地应用程序提供 NFS 或 SMB 接口。写入网关的文件以对象的形式存储在 S3 中——但应用程序不知道这一点。它看到的是一个文件系统。频繁访问的文件在本地缓存以实现低延迟读取；其余的住在 S3 里。这正是 Meridian 需要的：后厨管理软件往一个看起来像文件共享的地方写，数据最终落到 S3，Nimbus 可以在那里分析、备份和检索它。

"等等——可是*为什么*要那样做？" Maya 问。"为什么不直接把软件指向 S3？"

因为 NFS 和 SMB 不是 S3。后厨软件不会说 S3 的 API。它打开的是文件路径。它往目录里写字节。文件网关把这些翻译成 S3 对象操作，而应用程序对发生的变化一无所知。

**卷网关**（Volume Gateway）向本地服务器提供 iSCSI 块存储卷——和一块物理硬盘或 SAN 设备提供的接口一模一样。它有两种模式：*存储卷*（stored volumes）把主数据留在本地，异步备份到 S3 作为 EBS 快照（适合本地优先、同时想要云备份的工作负载）；*缓存卷*（cached volumes）把主数据放在 S3，频繁访问的数据缓存在本地（适合已经准备好把 S3 当作主存储的组织）。

**磁带网关**（Tape Gateway）向 Veeam、Veritas 或 NetBackup 之类的备份软件提供一个虚拟磁带库（VTL）。备份软件往看起来像物理磁带盒的东西里写。那些虚拟磁带存储在 S3 中，并可归档到 S3 Glacier。备份软件不用改。物理磁带机器人和磁带架则可以退役了。

"Meridian 的备份团队用的是 Veeam，" Leo 说。"他们有真正的物理磁带。异地存放、轮换计划，整套流程。"

"磁带网关替换的就是物理磁带，" Priya 说。"同样的 Veeam 配置。同样的备份任务。磁带只是住进了 S3，而不是机架里。"

Tom 查了一下异地磁带存放的费用。他一言不发地关掉了那个标签页，批准了迁移计划。

> **考试技巧——AWS Storage Gateway**
>
> *SAA-C03 领域：设计高性能架构（领域3）*
>
> - **文件网关 = NFS/SMB → S3。** 本地应用程序写入的文件变成 S3 对象。频繁访问的文件在本地缓存。考试触发词："本地应用程序需要在不改代码的情况下把文件存进 S3"。
> - **卷网关 = iSCSI 块存储 → S3 快照。** 存储模式：主数据在本地，以 EBS 快照形式备份到 S3。缓存模式：主数据在 S3，频繁访问的块在本地缓存。考试触发词："本地服务器需要有云端支撑的块存储"。
> - **磁带网关 = VTL → S3/Glacier。** 备份软件写入虚拟磁带；磁带存储在 S3 或归档到 Glacier。考试触发词："在不更换备份软件的情况下替换物理磁带备份基础设施"。
> - **关键考试模式：**"本地应用程序需要云存储且不改代码" → Storage Gateway。"替换磁带备份" → 具体指磁带网关。

## 优势与局限性

**EBS 优势**：

- 面向 EC2 的持久、快速的块存储
- 快照可用于时间点备份和恢复
- 多种性能层级适配不同工作负载
- 原生支持静态加密——请启用账户级默认加密

**EBS 局限性**：

- 同一时间只能挂接到一台实例（有少数例外）
- 与 EC2 实例必须在同一可用区（复制到另一个可用区需要快照）
- 你为预置的存储付费，而不仅仅是实际使用的部分
- 加密一个已存在的未加密卷需要"快照-复制-还原"流程，并伴随一个维护窗口

**EFS 优势**：

- 多实例共享文件系统——原生 NFS 协议
- 自动扩展，你不需要预置容量
- 在区域内跨可用区可访问
- 弹性吞吐量模式自动适配工作负载

**EFS 局限性**：

- 每 GB 比 S3 贵
- 随机 I/O 的延迟高于 EBS
- 并非在所有区域可用

## 批量搬运数据：DataSync 与 Snow 家族

Storage Gateway 让本地应用程序与云存储*持续连接*。但还有两种迁移场景在考试中反复出现——并且终有一天会出现在真实项目里：

**AWS DataSync** 用于*在线批量传输*：通过网络在本地 NFS/SMB 文件服务器（或其他云）与 S3、EFS 或 FSx 之间搬运大型数据集——一次性，或按计划执行。它处理并行化、完整性校验、重试和带宽限速，速度大约是手搓 rsync 式脚本的 10 倍。考试触发词："把数百万个文件从本地 NFS 服务器迁移/传输到 Amazon EFS/S3" → DataSync。（别把它和 Storage Gateway 混淆——后者用于*持续的混合访问*；也别和 DMS 混淆——后者迁移的是*数据库*。）

**AWS Snow 家族**用于网络本身就是瓶颈的情况。通过一条 100 Mbps 的线路搬 100 TB 要花三个多月；卡车更快。**Snowball Edge** 是 AWS 寄给你的一台加固型设备——在本地装入最多约 80 TB，寄回去，AWS 把数据导入 S3。**Snowcone** 曾是小型便携版（约 8–14 TB），面向边缘场所——已于 2024 年底停产，不过它仍可能出现在较旧的考题中（见第25章的现实核查）。考试算术触发：当题干给出数据集大小和一条细弱或不可靠的链路，并问最快/最实际的迁移方式时，算一下传输时间——如果是数周或数月，答案就是 Snow 家族。

> **考试技巧——AWS Backup**
>
> 还有一个把本章串起来的服务：**AWS Backup** 用一个备份计划集中并自动化跨 EBS、EFS、RDS、DynamoDB、FSx 和 Storage Gateway 的备份——计划、保留策略、跨区域和跨账户复制，以及实现不可变性的 Backup Vault Lock。考试触发词："集中管理跨多个 AWS 服务/账户的备份" → AWS Backup，而不是逐服务写脚本。


## 摘要

Tom 的红笔圈出了真正的问题：太多东西挤在一台机器上。把存储搬离 EC2 实例不只是容量问题——它是关注点分离，让每一层都可以独立地管理、扩展和加固。正确的存储选择取决于四个问题：什么东西需要这份存储、同时有多少东西需要它、它要活多久、它是怎么被访问的？这四个问题总能一致地指向正确答案。

- **EBS**（弹性块存储）是面向单台 EC2 实例的持久块存储。它能在实例停止后存活，并可以做快照备份。通用工作负载用 gp3，高 IOPS 需求用 io2。实例存储临时而快速，但实例终止时数据丢失。
- **EFS**（弹性文件系统）是多台实例可以同时挂载的共享网络文件系统。EFS 跨越一个区域内的多个可用区；EBS 被限制在单个可用区内。
- 把存储类型匹配到需求：单台 EC2 的数据库 → EBS；跨服务器共享文件 → EFS；对象、媒体、备份 → S3；归档 → S3 Glacier。
- 加密一个已存在的 EBS 卷需要：快照 → 加密复制 → 新卷 → 替换。启用账户级默认加密，让新卷免去这一切。
- **EBS 的"终止时删除"**：根卷默认随实例终止而删除；数据卷默认保留。在设计实例生命周期策略时，两个设置都要检查。

## 考试技巧

*SAA-C03 领域3——任务3.1（存储解决方案）*

- **EBS 卷存在于一个可用区中。** 它们只能挂接到同一可用区的实例。要在不同可用区使用一个 EBS 卷，你需要创建快照并在目标可用区还原它。
- **EBS 快照是增量的，存储在 S3 中。** 第一个快照是完整的；后续的只存储变化。你可以把快照复制到其他区域用于灾难恢复。
- **EFS 是跨可用区的。** 同一区域内不同可用区的多台实例可以挂载同一个 EFS 文件系统。这是与 EBS 的关键区别。
- **当考试场景说"带共享内容的 Web 应用程序"或"多个实例访问相同文件"时，想到 EFS。** 当它说"数据库存储"或"单台服务器的持久磁盘"时，想到 EBS。
- **实例存储的数据能在重启后存活，但停止或终止后不行。** 题目可能描述"实例停止后消失的数据"——那就是实例存储在起作用。
- **gp3 与 io2**：gp3 是通用场景的默认选择；io2 用于需要 IOPS 保证的工作负载（大型数据库、关键任务系统）。描述"IOPS 需求"或"稳定的低延迟数据库性能"的考试场景指向 io2。
- **gp2 与 gp3：** gp2 的 IOPS 与容量绑定（3 IOPS/GB，最高 16,000 IOPS，需 5,334 GB）；gp3 的 IOPS 与容量无关（基线 3,000，自 2025 年底起可配置到最高 80,000——旧资料以及考试题库可能仍按之前的 16,000 上限）。考题套路：某工作负载需要更多 IOPS 但不想增加存储——答案是 gp3 或 io2，不是 gp2。
- **EBS 的静态加密**：你不能原地加密一个已存在的未加密卷——必须快照、加密复制、还原。启用账户级默认加密，避免意外创建未加密的卷。加密采用 AES-256，使用 KMS 密钥。
- **快速快照还原**消除新还原卷的性能损失，但按"每份快照、每个可用区"收费。关于"立即以完整性能"还原卷的考题指向 FSR。
- **EFS 性能模式**：通用模式（低延迟，适合大多数工作负载）与 Max I/O（为高度并行的工作负载提供更高吞吐量）。
- **EFS 吞吐量模式——三个选项：** 突增（吞吐量随存储大小扩展，使用突增积分——适合有尖峰的工作负载）、弹性（自动扩缩、按使用付费——适合不可预测的工作负载）、预置（与存储无关的固定吞吐量——适合持续的高吞吐量需求）。考试测试你是否知道何时该预置吞吐量、何时让它弹性扩展或依赖突增积分。
- **跨区域快照复制**：EBS 快照可以复制到其他区域用于灾难恢复。复制出来的快照是独立的，还原时不产生数据传输费——只有复制操作本身产生。
- **Storage Gateway 类型：** 文件网关 = NFS/SMB → S3（文件变成对象）。卷网关 = iSCSI 块存储 → S3 快照（存储模式：主数据在本地；缓存模式：主数据在 S3）。磁带网关 = VTL → S3/Glacier（替换物理磁带）。考试触发词："本地应用需要云存储且不改代码" → Storage Gateway。"替换磁带备份" → 磁带网关。

**练习 2——SAA-C03 场景题**

*场景*：一家公司在负载均衡器后面的四台 EC2 实例上运行一个 Web 应用程序。用户可以上传个人资料照片。任何照片在上传后必须立即可被用户查看，无论哪台实例处理了上传。照片通过 HTTP 提供给浏览器、从不就地修改，团队想要**最具**成本效益、可扩展、运营开销最小的方案。

哪种存储解决方案**最能**满足他们的需求？

A) 为每台 EC2 实例挂接一个 EBS gp3 卷，并用 cron 任务在它们之间同步文件  
B) 把照片直接存储在 EC2 实例的实例存储上  
C) 使用 Amazon EFS，同时挂载在所有四台 EC2 实例上  
D) 把照片存储在 S3 中，并直接从应用程序代码访问它们

**提示 1**：需求是"所有四台实例必须能提供任何照片"。哪些选项能让一个文件立即对所有实例可见？

**提示 2**：实例存储是临时的。EBS 不能同时挂载在多台实例上。这缩小了范围。

**提示 3**：C 和 D 理论上都行得通。当应用程序需要通过文件系统操作访问照片，还是通过 HTTP 请求访问照片时，哪种更合适？

**答案**：D

**解析**：把照片存储在 S3 中并通过 URL 提供，是 Web 应用程序在架构上的正确选择。上传的照片可以从任何服务器（以及任何浏览器）通过 S3 的 URL 立即访问。S3 正是为这个使用场景设计的：以高可用性和零管理开销大规模存储用户上传的文件。

注意：C（EFS）在技术上也能工作，但对于 Web 应用程序中用户上传的二进制文件，S3 是首选模式，因为它更便宜、更具可扩展性，并能直接通过 HTTP 提供文件，无需应用程序充当代理。

**为什么不是 A？** 通过 cron 任务同步文件会造成竞争条件和一致性问题。在上传与下一次同步之间，文件在其他实例上是缺失的。

**为什么不是 B？** 实例存储的数据在实例停止或终止时丢失。照片会消失。

**为什么不是 C？** 当题目要求文件系统语义时（例如，就地修改文件的 CMS），EFS 才是正确答案。对于通过 Web 提供的用户上传照片，S3 更简单、更便宜、更合适。

**考试关键词警告**：在真实考试中，要按字面意思读题干。如果它说"共享**文件**存储"、"文件系统"、"NFS"或"POSIX"，标准答案就是 **EFS**——不要用架构品味去推翻题目明示的需求。本场景的答案锁定 S3，是因为它要求的是通过 HTTP 进行成本高效的对象分发，而不是一个文件系统。
