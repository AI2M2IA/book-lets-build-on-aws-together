# 第6章：跟着你走的磁盘

Tom 有一支红笔，还有一个让 Leo 紧张的习惯。

每个周六早上，Tom 打印出 AWS 控制台摘要——运行中的实例、存储卷、附加的磁盘——然后逐行检查。他从第二周就开始这样做了。他称之为"账本"。Leo 称之为"Tom 做的那件让 Leo 觉得自己犯了什么错的事"。

那个周六，Tom 圈了什么，然后把打印件放在 Maya 的桌子上，一句话也没说。

她周一早上找到了它。一个圆圈。页边写着三个字：

*全部。一台机器。*

Web 服务器。数据库。所有客户记录。两个月的订单历史。全都运行在单个 EC2 实例上。

"如果实例崩溃，数据库会怎样？" Maya 手拿打印件问道。

"也会崩溃，" Leo 说。

"那数据呢？"

"取决于数据库如何存储它。"

那个"取决于"就是问题所在。

**EC2 实例如何存储数据**

当 EC2 实例运行时，其操作系统存放在某处的磁盘上。那个磁盘称为**根卷**。默认情况下，这是一个 **EBS 卷**——即使你没有想到它的时候也是如此。

但还有另一种：EC2 实例也有**实例存储**。

实例存储是物理连接到运行你的虚拟机底层硬件上的临时存储。它极快——比 AWS 中几乎任何其他存储选项都快。但它有一个缺陷。

实例存储是**临时的**。

当实例停止或终止时，实例存储数据就消失了。永久消失。无法恢复。AWS 不会非常大声地警告你这一点，这就是团队是如何发现的：通过丢失数据。

实例存储适用于缓存、临时处理文件和暂存空间。绝不适用于你关心的数据。

**EBS：持久磁盘**

**Amazon EBS**——弹性块存储——是 EC2 实例的持久块存储。

块存储意味着它的行为像真正的硬盘：你的操作系统可以在上面创建文件系统，在任意位置读写任意字节，运行数据库，并把它完全当作连接的磁盘来使用。

关键属性：

**持久性。** 与实例存储不同，EBS 卷在实例停止、启动，甚至实例终止后仍然存在（取决于配置）。即使没有实例在使用，数据仍然留在卷上。

**可连接和可拆卸。** EBS 卷可以从一个实例拆卸，然后连接到另一个实例。如果你需要迁移数据或从失败的实例中恢复，你可以拆卸卷并在其他地方重新连接。

**单个连接（大多数情况）。** 默认情况下，EBS 卷一次只连接到一个 EC2 实例。一个实例可以有多个 EBS 卷，但一个 EBS 卷不能同时被多个实例挂载（有一个例外：EBS 多重连接，有有限的使用场景和重要限制）。

类比：EBS 是一个插入笔记本电脑的外置硬盘。笔记本（EC2 实例）可以读写它。当你完成后，你可以拔下它，插入另一台笔记本。

**EBS 卷类型**

并非所有 EBS 卷都相同。AWS 提供几种具有不同性能和成本特征的类型。

**gp3（通用 SSD）**：大多数工作负载的默认选择。性能和价格的良好平衡。适用于启动卷、小型数据库和开发环境。

**io2（预置 IOPS SSD）**：I/O 密集型工作负载的高性能选项。你指定需要多少 I/O 操作/秒（IOPS），AWS 保证该性能。适用于大型生产数据库。

**st1（吞吐量优化 HDD）**：针对大型顺序读写优化的磁性存储。比 SSD 便宜，但随机 I/O 更慢。适用于数据仓库和日志处理。

**sc1（冷 HDD）**：最便宜的 EBS 选项。用于不频繁访问的数据。不适用于任何时间敏感的场景。

考试不要求你记住所有类型。它确实测试你是否能将需求与正确类型匹配：IOPS 需求 → io2。对成本敏感的顺序工作负载 → st1。一般 Web 应用程序 → gp3。

**EBS 快照：备份**

这是一个经常拯救公司的东西。

**EBS 快照**是存储在 S3 中的 EBS 卷的时间点备份（尽管你通过 EBS 界面访问它，而不是直接通过 S3）。快照是增量的：第一个快照捕获完整的卷；后续快照只存储自上次快照以来的变化内容。

你可以从快照创建新的 EBS 卷——恢复到数据库损坏、部署错误或意外删除之前的某个时间点。

你应该自动化快照。AWS 为此提供了 **Amazon 数据生命周期管理器**：定义一个策略（每6小时拍摄一次快照，保留最近7天），它会自动运行。

Priya 在数据库投入生产之前就设置了这个。

Leo 没有想到这一点。

**EFS：共享文件柜**

EBS 是连接到一个实例的磁盘。如果多个实例需要同时访问相同的文件怎么办？

进入 **Amazon EFS**——弹性文件系统。

EFS 是一个托管网络文件系统。多个 EC2 实例可以同时挂载相同的 EFS 文件系统，并读写共享文件。这是 EBS 不提供的关键能力。

这样想：

EBS 是插入一台笔记本的外置硬盘。一次只有那台笔记本可以使用它。

EFS 是办公室中央的文件柜。任何团队成员都可以走过来，打开抽屉，阅读文件，放回东西。多人同时访问相同的存储。

**什么时候你需要 EFS？**

- 当多个 EC2 实例需要共享文件时——内容管理系统、共享配置文件、共享媒体库
- 当你有水平扩展的应用程序，所有实例都需要访问相同数据时
- 当你需要在实例故障后仍然存在的持久文件系统时

**EFS 与 S3 的区别：** EFS 是文件系统（文件夹、文件、权限、锁定）。S3 是对象存储（上传、下载，没有文件系统语义）。EFS 比 S3 贵得多。对于整体存储和检索的文件，使用 S3。对于应用程序通过标准文件系统操作主动读写的文件，使用 EFS。

**选择正确的存储**

到现在你已经看到了 AWS 中的三种存储类型。让我们把决策说清楚。

| 需求 | 存储类型 |
|---|---|
| 数据库需要持久、快速的磁盘 | EBS（gp3 或 io2） |
| 多台服务器需要共享文件 | EFS |
| 文件、备份、图片、大型对象 | S3 |
| 临时计算暂存空间 | 实例存储 |
| 最低成本的长期归档 | S3 Glacier |

做对这个决定很重要。在你需要 EFS 的地方使用 S3 会增加运营复杂性。在你需要 EFS 的地方使用 EBS 会在你扩展时导致故障。在你需要持久性的地方使用实例存储会丢失数据。

Priya 打印了这张表，贴在了墙上。

"每次我们添加存储需求，" 她说，"我们都从这里开始。"

## 优势与局限性

**EBS 优势**：

- EC2 的持久、快速块存储
- 用于时间点备份和恢复的快照
- 适用于不同工作负载的多种性能层级
- 原生支持静态加密

**EBS 局限性**：

- 一次只能连接到一个实例（有少数例外）
- 与 EC2 实例在同一 AZ（复制到另一个 AZ 需要快照）
- 你为预置的存储付费，而不仅仅是你使用的部分

**EFS 优势**：

- 多实例共享文件系统——原生 NFS 协议
- 自动扩展，你不需要规划容量
- 在区域内跨 AZ 可访问

**EFS 局限性**：

- 每 GB 比 S3 更贵
- 随机 I/O 延迟比 EBS 高
- 并非在所有区域可用

## 摘要

- **实例存储**是物理连接到主机的临时、快速存储。当实例停止或终止时，数据丢失。仅用于暂存空间。
- **EBS**（弹性块存储）是单个 EC2 实例的持久块存储。它在实例停止后仍然存在。它可以快照备份。选择正确的卷类型（gp3 用于通用，io2 用于高 IOPS 要求）。
- **EFS**（弹性文件系统）是多个实例可以同时挂载的共享网络文件系统。当多台服务器需要访问相同文件时使用它。
- 将存储类型与需求匹配：数据库 → EBS；共享文件 → EFS；对象/备份 → S3；归档 → S3 Glacier。

## 考试技巧

*SAA-C03 领域3——任务3.1（存储解决方案）*

- **EBS 卷存在于一个 AZ 中。** 它们只能连接到同一 AZ 的实例。要在不同 AZ 使用 EBS 卷，你创建快照并在目标 AZ 中恢复它。
- **EBS 快照是增量的并存储在 S3 中。** 第一个快照是完整的；后续的只存储变化。你可以将快照复制到其他区域用于灾难恢复。
- **EFS 是跨 AZ 的。** 同一区域不同 AZ 中的多个实例可以挂载相同的 EFS 文件系统。这是与 EBS 的关键区别。
- **当考试场景说"带有共享内容的 Web 应用程序"或"多个实例访问相同文件"时，想到 EFS。** 当它说"数据库存储"或"单个服务器的持久磁盘"时，想到 EBS。
- **实例存储数据在重启后存活，但在停止或终止后不会存活。** 题目可能描述"实例停止后消失的数据"——那就是实例存储在起作用。

**练习 2——考试练习**

*场景*：一家公司在负载均衡器后面的四个 EC2 实例上运行一个 Web 应用程序。用户可以上传个人资料照片。所有四个实例必须能够在照片上传后立即为任何用户提供照片，无论哪个实例处理了上传。团队需要持久、共享的文件存储。

哪种存储解决方案*最能*满足他们的需求？

A) 为每个 EC2 实例附加 EBS gp3 卷，并使用 cron 任务在它们之间同步文件  
B) 将照片直接存储在 EC2 实例的实例存储上  
C) 使用 Amazon EFS，同时挂载在所有四个 EC2 实例上  
D) 将照片存储在 S3 中，并直接从应用程序代码访问它们

**提示 1**：需求是"所有四个实例必须提供任何照片"。哪些选项让文件立即对所有实例可见？

**提示 2**：实例存储是临时的。EBS 不能同时挂载在多个实例上。这缩小了范围。

**提示 3**：C 和 D 理论上都可以工作。哪种更适合应用程序需要通过文件系统操作访问照片与通过 HTTP 请求访问照片的情况？

**答案**：D

**解析**：将照片存储在 S3 中并通过 URL 提供它们是 Web 应用程序在架构上正确的选择。上传的照片可以从任何服务器（以及任何浏览器）通过 S3 的 URL 立即访问。S3 正是为这个使用场景设计的：以高可用性和零管理开销在规模上存储用户上传的文件。

注意：C（EFS）在技术上也可以工作，但 S3 是 Web 应用程序用于用户上传二进制文件的首选模式，因为它更便宜、更具可扩展性，并且直接通过 HTTP 提供文件，而不需要应用程序充当代理。

**为什么不是 A？** 通过 cron 任务同步文件会造成竞争条件和一致性问题。在上传和下次同步之间，文件在其他实例上会丢失。

**为什么不是 B？** 实例存储数据在实例停止或终止时丢失。照片会消失。

**为什么不是 C？** 如果应用程序需要文件系统语义（例如，就地修改文件的 CMS），EFS 是正确答案。对于通过 Web 提供的用户上传照片，S3 更简单、更便宜、更合适。

那天下午，Nimbus 正确地分离了存储。数据库有了自己的 EBS 卷，并有自动快照。菜单照片移到了 S3。EC2 实例终于可以轻松运转了。
