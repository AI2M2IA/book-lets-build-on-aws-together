# 第2章：你的服务器在世界的哪里？

站起来。如果附近有窗户，走过去看看。

向外看。不管你看到什么——建筑、树木、停车场、某人的后院——这些都不是你的数据所在的地方。你的数据在完全不同的地方。可能是你从来没去过的地方。

这不是问题。但理解*在哪里*会让数量惊人的事情豁然开朗。

白板讨论之后，决定已经做出：Nimbus 将使用 AWS。云就是答案。但"云"最终是一个位于特定位置的特定事物——而 Leo 在无意之间选择了那个位置。

第二天早上，Maya 注意到服务器在新加坡。

"为什么是新加坡？" 她问。

"那是默认的，" Leo 说。

Tom 从他的咖啡上抬起眼。"当我们所有的客户都在西海岸时，在新加坡运行一台服务器要多少钱？"

Leo 没有答案。

Priya 已经有了另一个顾虑。"而且谁知道那些数据正在经过哪些司法管辖区？"

这一章是关于修正那个决定——以及理解为什么这很重要。

**"某处"的问题**

当你使用 AWS，你不是在使用一个数据中心。你在使用一个遍布全球的数据中心网络。AWS 在数十个国家都有基础设施。

这是一个特性，而不仅仅是一个事实。但这意味着你必须做出选择：你想让你的基础设施在*哪里*运行？

这个选择之所以重要，有三个原因：

**性能。** 你的服务器离用户越近，响应速度越快。物理定律是不可协商的。数据在光纤电缆中以大约三分之二光速传播。从西雅图到新加坡的一次往返仅在传输过程中就需要大约 170 毫秒——还没算上你的应用程序做任何事情。同样的请求从西雅图到俄勒冈（`us-west-2`）大约需要 20 毫秒。这个差距不是四舍五入的误差。对于一个客户期望页面瞬间响应的餐厅订餐应用来说——而且一个页面会触发多次往返——每次往返 170 毫秒的基础延迟，就是一个快速产品与一个迟钝产品之间的差别。

Tom 掏出手机，打开 Nimbus 应用，加载了一个餐厅页面。他用秒表应用计了时。

"差不多三秒，" 他说。

Leo 查看了服务器日志中的延迟分解。仅仅是到新加坡的往返——与数据库查询毫无关系——就给每个请求增加了大约 170 毫秒，而这个应用每个页面要做多次往返。

"那如果我们把服务器搬到俄勒冈呢？" Tom 问。

"二十毫秒，" Leo 说。"也许更少。"

"这每个月要花多少钱？"

价格差距只有几个百分点。不是零，但不是主要变量。当天下午，他们就把服务器迁移到了 `us-west-2`。

"我已经把监控代理部署到新加坡那台实例上了，" Leo 半自言自语地说。"哦。" 他顿了顿。"我改在俄勒冈装一遍。"

**合规性。** 某些行业对数据可以存储在哪里有法律规定。美国医疗数据可能需要留在国内。金融数据可能需要保留在特定地区。选错区域可能造成法律问题。

Priya 在没人要求的情况下就调研过这个问题。

"GDPR，" 第二天早上的站会上，她从笔记中抬起头来说。"如果 Nimbus 哪天服务了欧盟的客户——哪怕只有一个客户——关于他们的个人数据可能就必须留在欧盟境内，或者留在具有同等保护水平的国家。这不是可选项。这是法律。"

"我们是一个餐厅订餐应用，" Leo 说。"在加利福尼亚。"

"目前是，" Priya 说。"我们有没有想过，如果十八个月后我们扩张到欧洲，然后发现我们已经把欧洲客户的数据在俄勒冈存了一年半，会发生什么？"

一阵停顿。

"到时候再改，" Leo 说。

"数据驻留违规是没法追溯性修复的，" Priya 说。"违规已经发生了。"

她并不是在夸张。GDPR 的罚款最高可达年度全球营收的 4%。美国医疗领域的 HIPAA 违规每年每个违规类别的罚款可超过 200 万美元。这些不是假设——这正是大型企业的云决策从合规映射、而不是从基础设施配置开始的原因。

对 Nimbus 来说，眼下的监管风险敞口很低：美国客户，没有医疗数据，没有金融服务。但为一家打算成长的企业选择区域，意味着要把成长考虑在内地去选。

**灾难恢复能力。** 如果一个地点发生停电、地震或网络故障，你希望你的系统能够存活下来。将基础设施分散在多个地点是抵御本地灾难的方式。

**AWS 如何组织其基础设施**

AWS 将其全球基础设施分为三个嵌套概念。把它们想象成俄罗斯套娃，从最大到最小：一个大娃娃打开露出一个中娃娃，中娃娃打开又露出一个小娃娃。每一层都嵌套在另一层之内。

最外层的娃娃就是 AWS 所说的**区域**（Region）。区域里面是一组**可用区**（Availability Zone）。而散布在全球各地、独立于这两者之外的，是**边缘节点**（Edge Location）。

让我们一一打开。

**区域：大盒子**

**区域**是 AWS 拥有数据中心集群的地理区域。每个区域以其位置命名：`us-west-2` 是俄勒冈州，`us-east-1` 是北弗吉尼亚，`eu-west-1` 是爱尔兰，`ap-southeast-1` 是新加坡——Leo 的服务器就藏在那里。

全球有近 40 个区域，AWS 还在定期添加更多。随着 AWS 的扩张，这份名单还在不断变长：北美、南美、欧洲、中东、亚太和非洲都有区域。每个新区域通常会在开放前数月公布，启用时至少包含三个可用区，而要等所有 AWS 服务在该区域可用，则需要几年时间。

每个区域完全独立。`us-west-2` 中的数据会留在 `us-west-2`，除非你明确移动它。这对合规性和弹性至关重要——一个区域的重大中断不会自动影响其他区域。一场扰乱北弗吉尼亚电网的事件不会影响俄勒冈。爱尔兰的一场自然灾害不会影响新加坡。在物理基础设施层面，区域之间是真正相互隔离的。

这种独立性如此彻底，以至于当一个区域发生重大中断时，连 AWS 管理控制台都可能加载缓慢——因为控制台本身也运行在 AWS 基础设施上。这一点值得知道：在真实的 AWS 事故期间，你恰恰可能在最需要监控工具的时候发现它们难以访问。这也是有经验的团队会在 AWS 控制台之外独立监控自己服务的部分原因。

"所以我们应该为 Nimbus 选择 `us-west-2`？" Tom 问。

是的。对于一家面向西海岸客户的美国企业，是的。更低的延迟，你的用户响应更快。

"它比新加坡贵多少？" Tom 补充道。

区域间定价有所不同——通常相差几个百分点。正确区域带来的性能和合规优势值得这一点微小的价格差异。

**Nimbus 差点搞错的区域选择之争**

在团队敲定 `us-west-2` 之前，曾有过一场短暂的争论：`us-east-1`（北弗吉尼亚）是不是更合理。它是最老的区域，最大的区域，AWS 首先发布新服务的区域。在大多数定价页面上它也是最便宜的区域。Tom 喜欢这一点。

"但我们的用户在加利福尼亚、俄勒冈和华盛顿，" Maya 说。"为什么要把服务器放在国家的另一头？"

"更便宜，" Tom 说。"而且可用的服务更多。"

"等等——可我们*为什么*要那样做？" Maya 说。"我们的用户在西海岸。我们的服务器就该在西海岸。价格差是多少，百分之六？百分之七？我们因额外延迟而流失客户的损失，会超过我们在计算账单上省下的钱。"

她说得对。一个工作负载的正确区域，就是离最重要的那批用户最近的区域——除非合规、服务可用性或成本差异能为别的取舍提供正当理由。对 Nimbus 来说，这些理由一条也不成立。

这是一个感觉很小、实际不小的决定。那些因为"它是默认的"而选择 `us-east-1`、然后从东海岸服务西海岸用户的团队，是在白白浪费真实的性能。AWS 控制台默认 `us-east-1` 是出于历史原因。那不是一个推荐。

**可用区：真正的冗余**

这里开始变得有趣了。

每个区域不是一个单一的数据中心。它是多个物理上彼此独立的数据中心组成的集群，这些数据中心称为**可用区**（Availability Zone，简称 AZ）。

俄勒冈（`us-west-2`）有四个可用区：`us-west-2a`、`us-west-2b`、`us-west-2c`、`us-west-2d`。这些都是真实的建筑，相互之间隔着有意义的距离——远到足以使其中一个发生火灾、洪水或停电不会影响其他的，但近到足以使它们之间的网络极快（个位数毫秒延迟）。

"有意义的距离"到底有多远？AWS 不公布精确坐标，但独立研究者估计，同一区域内的可用区之间通常相隔几十英里——远到足以处于不同的电网和不同的光纤路径上，又不至于远到让光速成为同步复制的限制因素。

这种分隔是刻意为之的，也很重要。如果两个可用区共用同一座变电站，一次变电站故障就会同时击垮两个可用区——冗余荡然无存。物理上的分隔确保了共因故障（那种波及整个地理区域的故障）真正成为罕见事件，而不是可预见的风险。

正是这种架构，让 AWS 的可靠性达到了任何单一数据中心都无法比拟的程度。

Priya 向前倾。"所以如果我们的应用程序跨两个可用区运行，其中一个宕机——"

"另一个继续运行，" Maya 接道。

"完全正确。"

Leo 一直在默默听着："我把所有东西都部署在一个 AZ 里了。"

"是的，" Priya 说。"我们注意到了。"

将你的应用程序分散到多个 AZ 的概念——称为**多 AZ 部署**——是 AWS 中最重要的弹性模式之一。我们在第18章深入讨论它。现在，理解 AZ 的存在正是为了使这成为可能。

有一个细微之处值得了解：AZ 的名称（`us-west-2a`、`us-west-2b` 等）在不同 AWS 账户之间并不一致。在你账户中显示为 `us-west-2a` 的，可能与同事账户中显示为 `us-west-2a` 的不是同一个物理数据中心。AWS 随机化这个映射，以防止所有客户在默认选"a"时都部署到同一个物理可用区。如果你需要与另一个账户协调你们位于哪个物理可用区（比如为了低延迟的跨账户通信），AWS 提供了 AZ ID——在所有账户中都映射到同一物理位置的稳定标识符。带名字的可用区（`2a`、`2b`）是相对于账户的。AZ ID（`usw2-az1`、`usw2-az2`）是物理的。考试偶尔会考这个区别。

**一次 AZ 故障究竟是什么样子**

这不是抽象的。让我带你走一遍真实的时间线。

某个周二下午 2 点 47 分。为 `us-west-2b` 供电的一台变压器发生电气故障，导致那个数据中心断电。这一事件无法预测。

如果 Nimbus 完全运行在 `us-west-2b`：
- 下午 2:47：EC2 实例断电。数据库服务器断电。
- 下午 2:47：发往 Nimbus 应用的请求开始因连接超时而失败。
- 下午 2:47：Tom 的监控告警触发。
- 下午 2:50：Leo 开始恢复流程。他在 `us-west-2a` 启动一台新的 EC2 实例。
- 下午 3:05：数据库通过快照恢复重新上线。
- 下午 3:12：应用程序被重新配置，指向新的数据库端点。
- 下午 3:20：Nimbus 重新开始处理流量。

那是 33 分钟的停机。如果发生在周五晚餐时段，33 分钟可能意味着数千美元的订单损失，以及那种不会出现在事故报告里的声誉损害。

如果 Nimbus 以正确的多 AZ 部署跨 `us-west-2a` 和 `us-west-2b` 运行：
- 下午 2:47：`us-west-2b` 中的 EC2 实例断电。
- 下午 2:47：Application Load Balancer 通过健康检查检测到不健康的实例。
- 下午 2:47：ALB 自动停止把流量路由到故障实例。
- 下午 2:47：流量继续流向 `us-west-2a` 中的实例。
- 下午 2:48：Auto Scaling 组启动一台替换实例。
- 下午 2:55：替换实例通过健康检查，重新加入机群。

停机时间：零。客户影响：接近零。Tom 的监控会触发，但 Leo 要做的是"观察并确认恢复已完成"，而不是"手动重建一切"。

这就是多 AZ 与单 AZ 之间的差别。AZ 边界正是 AWS 的冗余设计转化为你的应用弹性的地方。

**多 AZ 的可靠性数学**

AWS 把每个可用区设计为彼此独立——不只是物理上独立，还有各自独立的电力、冷却和网络。同一区域内两个可用区同时故障的概率被设计得极低。

如果单个可用区的可用性为 99.9%（每年约 8.7 小时停机），那么把故障视为独立事件的双 AZ 架构，针对同一种故障模式的可用性约为 99.9999%——每年因 AZ 故障导致的停机约 31 秒。

实践中，大多数应用程序的限制因素并不是 AZ 的可用性，而是应用代码、部署流程和数据库。但这道数学题说明了为什么多 AZ 是标准基线：跨两个可用区运行的成本不高；可用性的提升却很大。

**边缘节点：到处都快**

AZ 解决了弹性问题。它们没有解决向远离你主区域的城市中的用户快速提供内容的问题。

进入**边缘节点**。

边缘节点是小型、轻量级的基础设施点——超过 750 个接入点（points of presence），散布在全球 100 多个城市。它们不是完整的数据中心——它们无法运行你的应用程序。
它们*能*做的是在离你用户近的地方缓存内容。

想象一张存储在弗吉尼亚服务器上的菜单图片。每次东京的人想看它，请求就要穿越太平洋再回来。有了边缘节点，AWS 可以在东京存储该文件的副本，并在本地提供——毫秒级而不是数百毫秒。

这是 CloudFront（AWS 的内容分发网络）的骨干。我们在第13章深入研究 CloudFront。现在：边缘节点是关于静态内容的速度。

你也许会好奇：既然边缘节点缓存内容，它们也会永久存储你的数据吗？不会。边缘节点持有内容的临时副本以便更快地提供——原始内容永远存放在你的区域里。如果缓存过期或内容发生变化，边缘节点会从源头获取一份新副本。

边缘节点网络与区域和可用区的结构是分离的。当你思考应用程序*在哪里运行*时，你思考的是区域和可用区。当你思考内容如何*快速*到达用户时，你思考的是边缘节点和 CloudFront。它们解决不同的问题，运作在不同的层面。

AWS 还有一个相关的概念叫**区域边缘缓存**（Regional Edge Cache）——位于你的区域和边缘节点之间的更大型缓存节点。如果某个城市的边缘节点没有某个文件的缓存副本，它会从区域边缘缓存获取，而不是一路回到你的区域。这降低了源站的负载，并提高了冷门内容的缓存命中率。你不会直接配置区域边缘缓存——它们是 CloudFront 基础设施中自动运作的一部分。

对 Nimbus 的实际意义是：当团队在第13章加上 CloudFront 之后，过去每次请求都要从俄勒冈跑到客户浏览器的菜单图片，将改为从最近的边缘节点提供——德克萨斯的客户走达拉斯，佐治亚的客户走亚特兰大，伊利诺伊的客户走芝加哥。芝加哥的用户从 300 英里外、而不是 2,000 英里外的服务器获取菜单图片。这个差距是可测量的，也是有意义的。

**关于缓存副本的一点提醒**

关于边缘节点，有一个细节现在就值得指出，尽管完整的故事属于第13章：缓存副本是一份*副本*，而副本是会过时的。如果原始内容在你的区域里发生了变化，边缘节点可能还会继续提供旧版本一段时间。会持续多久、你能对此做什么，正是 CDN 提供给你的那类控制手段——也正是 Nimbus 真正部署 CloudFront 时团队要纠结的问题。现在，只需记住这一点：内容可以离用户很近，而"近"有时意味着"略微过时"。

**选择区域：高级工程师的清单**

如果 Nimbus 有一天扩展到服务墨西哥和哥伦比亚的用户——我们将在本章的练习中演练这个场景——区域决策并非随意的。以下是思考方式：

**1. 你的用户在哪里？**

从这里开始。选择最靠近大多数用户的区域。延迟是区域选择最直接、最可衡量的影响。

用户与服务器之间的物理距离的重要性容易被低估。到新加坡 170 毫秒的往返与到俄勒冈 20 毫秒的往返，不是一个抽象的性能指标——而是一个页面感觉瞬间响应与感觉迟钝之间的差别。在带有额外无线电延迟的移动设备上，新加坡的代价还会进一步叠加。对于圣何塞的用户来说，在你考虑任何其他因素之前，`us-west-2`（俄勒冈）就已经是正确的区域。

**2. 是否有合规要求？**

医疗、金融和政府工作负载通常有严格的数据驻留规则。在选择前了解你的监管环境。GDPR 要求欧盟居民的个人数据存储在具有充分数据保护的司法管辖区——要么是欧盟本身，要么是获得充分性认定的国家。HIPAA 要求对美国医疗数据采取有据可查的保障措施。这些不是可以日后再议的可选项。

实践中：在为任何受监管的工作负载选择区域之前，先和你的法务团队谈。AWS 为每个区域维护着详尽的合规文档，包括 SOC 2、ISO 27001、PCI DSS 等认证以及 HIPAA 资格。但认证只告诉你 AWS 做了什么；你的法务团队才能告诉你这对你的具体监管环境是否足够。

**3. 你需要哪些服务？**

并非每个 AWS 服务都在每个区域可用。新服务首先在 `us-east-1` 推出。如果你需要特定服务，请验证你的目标区域是否支持它。

对于本书涉及的服务来说，这不太成问题——所有主要服务都已广泛可用——但对于较新的服务、专门硬件（某些 GPU 实例类型只存在于特定区域），以及 AWS GovCloud（一个为有特定监管要求的美国政府工作负载设计的独立区域）来说，这很重要。

**4. 定价是多少？**

不同区域的价格有所不同。`us-east-1`（北弗吉尼亚）由于其规模和历史，往往是最便宜的。南美洲稍贵一些。在最终确定之前检查 AWS 定价页面。

价格差异通常很小——热门区域之间相差几个到十个百分点。它很少是决定性因素。但对于运行数千台实例的成本敏感型工作负载，哪怕 5% 的价格差异也会随时间累积。Tom 会去查这个数字并把它纳入考量，就像 Tom 查所有数字并把它们纳入考量一样。

**5. 你是否需要多区域？**

对于大多数应用程序，一个区域内的多个 AZ 就已经是足够的弹性。对于连区域级中断都不可接受的关键应用程序，你才需要做多区域设计——但那是一项重大的架构承诺。不要投机性地去做。

"我们什么时候才该加第二个区域，规则是什么？" Leo 问。

"当我们有一条成文的需求写着'即使整个 AWS 区域不可用也必须保持运行'的时候，" Priya 说。"不是'有了会很好'。是一条具体的需求，带着具体的商业理由，而且我们已经把它和复杂性、成本放在天平上称过了。"

"实践中那是什么样子？"

"一份要求 99.99% 正常运行时间的客户合同 SLA。一项要求地理冗余的监管规定。一个我们真的能用营收数字量化的'区域整体失效'场景。而不是单纯的'万一 us-west-2 挂了怎么办'。"

Leo 看了看 Nimbus 目前的架构。他们还在单个可用区上。

"先做多 AZ，" 他说。

"先做多 AZ，" Priya 确认道。

**没人谈论的局限性**

区域很强大，但它们造成了一个重要的张力。

在多个区域运行真的很难。

区域之间的数据复制有延迟。保持两个区域同步——使区域 A 中的事务立即在区域 B 中可见——是分布式系统中最难的问题之一。AWS 提供了相应的工具，但这需要花钱并增加运营复杂性。

大多数应用程序应该从一个区域、多个 AZ 开始，只有在出现明确需求时才扩展到多区域：监管强制要求、要求近乎零区域停机时间的合同 SLA，或者真正分布在各大洲的用户群。

跨区域复制数据会增加成本——跨区域数据传输是 AWS 账单上被低估得最厉害的项目之一。它也增加了运营复杂性：每一次必须跨区域保持一致的写入都会增加延迟。

影响真实应用程序的大多数故障都不是跨区域的大灾难。它们是区域内的问题，比如配置错误的安全组或一次搞砸的部署。那种戏剧性的"整个区域宕掉"的场景之所以能上头条，恰恰因为它罕见。先在多 AZ 上投入，再考虑多区域。当业务理由清晰时再添加多区域。

给出一些具体数字：在 AWS 的历史上，重大的单区域事件只有少数几次。完整的区域级中断确实不常见。AZ 级事件——影响区域内单个数据中心的短暂中断——则没那么罕见，而它们正是多 AZ 部署被设计来吸收的故障。AZ 事件相对于区域事件的发生频率大约高一个数量级。把架构精力优先花在更常见的故障模式上，才是理性的选择。

过早的多区域架构，是初级工程师开始感到自信时最常见、最昂贵的错误之一。

Tom 点了点头。"所以我们不会只因为能做就去做多区域。"

"直到我们需要的时候，" Maya 说。"而且到我们需要的时候，我们会知道的。"

"我们怎么会知道？" Leo 问。

"当你的架构评审文档里有一条需求写着'必须能在区域级中断中存活'的时候，" Priya 说。"我们有没有想过，在我们连多 AZ 都还没搭好的时候，如果整个 AZ 宕掉会发生什么？我们应该先解决那个问题。在那之前：多 AZ。"

你也许会好奇：在真正需要之前，如何验证你的多 AZ 部署确实有效？你去测试它。AWS 提供了一个叫 **AWS Fault Injection Service（FIS）** 的工具——前身是 Fault Injection Simulator——它可以针对你正在运行的架构模拟 AZ 故障、实例终止和其他故障条件——让你能以受控的方式观察系统在故障条件下的行为，而不是在真实事故中才发现这些行为。测试你的弹性架构和构建它同样重要。Priya 读到这个工具之后，立刻把"故障注入测试"写进了季度架构评审日历。

## 当 AWS 来到你身边：Outposts 与 Wavelength

区域和可用区覆盖了整个世界——但并非每个问题都能靠把数据搬进 AWS 来解决。有些工作负载必须留在本地：需要亚毫秒级延迟的制造车间系统、有数据驻留要求的医疗应用、位于没有可靠互联网的门店里的零售收银系统。为此，AWS 把自己的基础设施延伸到了客户所在的位置。

"等等——如果我们以后和一家医院系统合作呢？" Priya 问。"他们的患者监护软件实在无法容忍一次云端往返。而且数据在法律上可能根本不允许离开那栋楼。"

Maya 调出了 AWS 文档。两个服务反复出现。

**AWS Outposts**

一整机柜由 AWS 完全托管的 AWS 硬件，安装在你自己的数据中心或托管设施里。Outposts 运行与 AWS 云相同的 AWS 基础设施、服务、API 和工具——EC2、EBS、RDS、EKS、S3 on Outposts——但物理上位于你的建筑里。

适用场景：对延迟敏感的制造业工作负载、数据必须物理留在特定位置的数据驻留要求、需要 AWS API 但无法容忍与公有云连接中断的应用程序。

关键点：Outposts 仍由 AWS 管理。AWS 负责安装、打补丁和监控。你提供机柜空间和电力。API 和工具与公有云完全一致——同样的 CloudFormation 模板、同样的 IAM 策略、同样的 CLI 命令。考试中的区分点在于物理位置，而不是运维模式。

"所以它是 AWS，但在我们客户的楼里，" Leo 说。

"完全正确，" Maya 说。"同样的 API。不同的邮编。"

**AWS Wavelength**

部署在电信运营商 5G 网络内部的 AWS 基础设施。Wavelength 区位于 5G 网络边缘，物理上靠近移动用户，使移动应用能够实现个位数毫秒级延迟。

适用场景：实时游戏、AR/VR、自动驾驶汽车遥测、5G 边缘的实时视频处理。

"那个不是给医院用的，" Tom 说。"那是给打造下一代多人手游的人用的。"

"或者自动驾驶汽车的遥测，" Priya 说。"任何移动设备需要与服务器通信、而 50 毫秒都嫌太慢的场景。"

**区别在于：** Outposts 把 AWS 带进你的数据中心——你的建筑、你的机柜、你的电力。Wavelength 把 AWS 带到电信网络边缘——与 5G 无线基础设施物理同址，紧邻那些从不接触你私有网络的移动用户。

**AWS Local Zones**

这个家族里还有第三个兄弟——而且在考试中，它是三者里被考得最频繁的。**Local Zones**（本地区）是部署在没有完整区域的大都市圈里的 AWS 基础设施——洛杉矶、休斯顿、迈阿密、拉各斯，以及其他数十座城市。一个 Local Zone 是某个父区域的延伸：你可以*就在那座城市里*运行 EC2、EBS 和一部分其他服务，为该市用户获得个位数毫秒级延迟，而其余一切（以及所有管理功能）都留在父区域。

要背下的模式——三个"边缘计算"兄弟，三个触发词：

- "对**特定城市/都市圈内**的终端用户实现个位数毫秒级延迟" → **Local Zones**
- "为 **5G 移动设备**提供超低延迟" → **Wavelength**
- "在**我们自己的数据中心里**运行 AWS 服务 / 数据必须留在本地" → **Outposts**

三者都不是典型 Web 应用的答案。它们在 SAA-C03 考试中都以模式匹配陷阱的形式出现：触发词才是关键。

## 优势与局限性

**在以下情况使用多区域和多 AZ 设计**：你的应用程序在多个地理位置有用户且延迟很重要；你的 SLA 要求 99.99% 或更高的可用性；监管要求数据驻留在特定区域；你需要 RTO 在一小时以内的灾难恢复。

**权衡是真实的**：在多个区域运行能为你提供抵御区域级中断的冗余——但代价是显著的成本和复杂性。

记住本章前面的成本警告：每一个在区域之间移动的字节都要花钱。在写入必须保持一致的双活（active-active）多区域架构中，你是在持续不断地支付这笔成本。

运营复杂性也会随之放大。在一个区域里排查事故已经很难。排查一起分布式的、跨区域的事故——同一个请求触及了两个大洲的基础设施——则完全是另一种难。

**大多数应用程序的正确演进路径**：从单个区域加多个可用区开始。这能让你以多区域架构复杂性的一小部分为代价，获得对真实发生的故障——AZ 级中断、硬件故障、电力事件——的抵御能力。当一条具体的、成文的需求使其成为必要时，再添加多区域。在那之前不要。

过早跳到多区域的团队的常见模式是：管理两个区域的复杂性会引入它自己的故障模式——数据同步缺陷、脑裂场景、不一致的部署。本来为防止故障而设计的弹性架构，有时反而引入了在更简单的设计中根本不会存在的新型故障。

Priya 有一份文档，她称之为"复杂性预算"。其理念是：每一个增加运营复杂性的架构决策都有成本，而组织管理这种复杂性的能力是有限的。在你还没有掌握单区域可靠性之前，就把复杂性预算花在多区域架构上，是一笔糟糕的投资。复杂性应该花在你实际面对的故障模式上，而不是那些能编出精彩灾备故事的故障模式上。

"我们有一个区域、一个 AZ，还有一个 Leo 每次执行都提心吊胆的部署流程，" Priya 说。"正确的下一步是多 AZ，不是多区域。"

Tom 在笔记本里写下了"复杂性预算"。在接下来的两年里，他会经常使用这个词。

## 摘要

Leo 的新加坡事故最终成了一堂有用的课——不是因为它造成了持久的损害，而是因为它迫使团队去理解一件通常被跳过的事情：你的基础设施在哪里运行，不是一个无关紧要的装饰性决定。物理定律是不可协商的。每次往返 170 毫秒的基础延迟，就是一个快速产品与一个迟钝产品之间的差别；而关于数据存放地点的合规规则，可不管你搬得有多快。

- AWS 将其全球基础设施组织为**区域**、**可用区**和**边缘节点**。
- **区域**是数据中心的地理集群。每个区域是隔离的——数据留在区域内，除非你明确移动它。
- **可用区**是区域内物理上独立的数据中心，通过低延迟网络连接。跨多个 AZ 部署是应对本地故障的标准方式。
- 根据用户位置、合规要求、服务可用性和价格选择你的区域——按此顺序。
- 多 AZ 是标准的弹性基线。多区域适用于有特定、成文需求的关键工作负载——不是默认起点。

## 考试技巧

*SAA-C03 领域1——任务1.1 / 领域2——任务2.2*

- **区域默认是隔离的。** 除非你配置，否则数据不会在区域之间复制。这对数据主权和合规场景很重要。
- **AZ 是大多数题目的弹性单位。** 当考试问如何在数据中心故障中存活时，答案涉及一个区域内的多个 AZ。
- **多区域用于应对区域级中断。** 如果场景说"即使整个 AWS 区域失败也必须保持运行"，答案涉及多区域架构。
- **边缘节点 ≠ AZ。** 边缘节点缓存内容——它们不能运行你的应用程序服务器。不要将它们与数据中心混淆。
- 考试经常测试合规与区域选择之间的关系。如果场景提到数据驻留要求，区域选择是答案的一部分。
- 考试中的 **GDPR 与数据驻留**场景通常指向把数据保留在特定区域内，并确保跨区域复制被禁用或受到控制。
- **Outposts vs Wavelength vs Local Zones：** Outposts = 放在你数据中心里的 AWS 机柜（本地部署、数据驻留、本地低延迟）。Wavelength = 位于 5G 网络边缘的 AWS（移动用户、超低延迟）。Local Zones = 没有完整区域的都市圈里的 AWS 算力。考试触发词："在你自己的设施中运行 AWS" → Outposts。"为 5G 移动用户提供超低延迟" → Wavelength。"对特定城市的用户实现个位数毫秒级延迟" → Local Zones。

**练习 2——SAA-C03 情景题**

*场景*：一家美国医疗公司必须将所有患者数据存储在单个 AWS 区域内，以符合内部数据驻留政策。他们正在西海岸设计一个新的云应用程序，并希望在不将数据移到另一个区域的情况下最大限度地提高弹性。

哪种配置*最能*满足他们的需求？

A) 在 `us-east-1` 部署，并在俄勒冈使用 CloudFront 边缘节点更快地提供内容  
B) 在 `us-west-2` 的单个可用区部署以最小化成本  
C) 在包括 `us-west-2` 和 `us-east-1` 的多个区域部署，并进行跨区域数据复制  
D) 在 `us-west-2`（俄勒冈）跨多个可用区部署

**提示 1**：该政策意味着数据必须保留在单个区域内。哪些选项将数据移到了另一个区域？

**提示 2**：在将数据保留在 `us-west-2` 的选项中，哪个提供了最多的弹性？

**提示 3**：单个区域内的多个 AZ 提供弹性，而不会跨越区域边界。

**答案**：D

**解析**：`us-west-2` 将所有数据保留在单个区域内，满足政策要求。在该区域内跨多个 AZ 部署可以抵御数据中心故障，而不必将数据移到另一个区域。这是合规性和弹性的正确平衡。

**为什么不是 A？** 选项 A 部署在 `us-east-1`，远离西海岸用户——而且 CloudFront 会在所选区域之外的边缘节点缓存与患者相关的内容，违反了驻留政策。

**为什么不是 B？** 单个 AZ 没有弹性。如果该 AZ 经历中断，应用程序将完全失败。

**为什么不是 C？** 复制到 `us-east-1` 会将患者数据移到东海岸，直接违反了单区域要求。
