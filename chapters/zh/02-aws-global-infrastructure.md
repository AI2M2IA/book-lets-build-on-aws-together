# 第2章：你的服务器在世界的哪里？

站起来。如果附近有窗户，走过去看看。

向外看。不管你看到什么——建筑、树木、停车场、某人的后院——这些都不是你的数据所在的地方。你的数据在完全不同的地方。可能是你从来没去过的地方。

这不是问题。但理解*在哪里*会让许多事情豁然开朗。

上一章，Leo 在晚上11点创建了一个 AWS 账户，并在某处启动了一台服务器。某处——这是关键词——他不确定自己选择了世界的哪个部分，因为他不是有意识地选择的。

第二天早上，Maya 注意到服务器在新加坡。

"为什么是新加坡？" 她问。

"那是默认的，" Leo 说。

Tom 从他的咖啡上抬起眼。"当我们所有的客户都在西海岸时，在新加坡运行一台服务器要多少钱？"

Leo 没有答案。

Priya 已经有了："而且还更慢。每个请求都要跨越半个地球。"

这一章是关于修正那个决定——以及理解为什么这很重要。

**"某处"的问题**

当你使用 AWS，你不是在使用一个数据中心。你在使用一个遍布全球的数据中心网络。AWS 在数十个国家都有基础设施。

这是一个特性，而不仅仅是一个事实。但这意味着你必须做出选择：你想让你的基础设施在*哪里*运行？

这个选择之所以重要，有三个原因：

**性能。** 你的服务器离用户越近，响应速度越快。物理定律是不可协商的。数据在光纤电缆中以大约三分之二光速传播。从西雅图到新加坡的请求仅在传输过程中就需要大约300毫秒——还没有算上你的应用程序做任何事情之前。

**合规性。** 某些行业对数据可以存储在哪里有法律规定。美国医疗数据可能需要留在国内。金融数据可能需要保留在特定地区。选错区域可能造成法律问题。

**灾难恢复能力。** 如果一个地点发生停电、地震或网络故障，你希望你的系统能够存活下来。将基础设施分散在多个地点是抵御本地灾难的方式。

**AWS 如何组织其基础设施**

AWS 将其全球基础设施分为三个嵌套概念。把它们想象成俄罗斯套娃，从最大到最小。

**区域 → 可用区 → 边缘节点**

让我们一一打开。

**区域：大盒子**

**区域**是 AWS 拥有数据中心集群的地理区域。每个区域以其位置命名：`us-west-2` 是俄勒冈州，`us-east-1` 是北弗吉尼亚，`eu-west-1` 是爱尔兰，`ap-southeast-1` 是新加坡——Leo 的服务器就藏在那里。

全球有超过30个区域，AWS 还在定期添加更多。

每个区域完全独立。`us-west-2` 中的数据会留在 `us-west-2`，除非你明确移动它。这对合规性和弹性至关重要——一个区域的重大中断不会自动影响其他区域。

"所以我们应该为 Nimbus 选择 `us-west-2`？" Tom 问。

是的。对于一家服务西海岸客户的美国企业，是的。更低的延迟，你的用户响应更快。

"它比新加坡贵多少？" Tom 补充道。

区域间定价有所不同——通常相差几个百分点。正确区域带来的性能和合规优势值得这一点微小的价格差异。

**可用区：真正的冗余**

这里开始变得有趣了。

每个区域不是一个单一的数据中心。它是多个物理上独立的数据中心集群，称为**可用区**（或 AZ）。

俄勒冈（`us-west-2`）有四个可用区：`us-west-2a`、`us-west-2b`、`us-west-2c`、`us-west-2d`。这些都是真实的建筑，相互之间有足够的距离——远到足以使某一个发生火灾、洪水或停电不会影响其他的，但近到足以使它们之间的网络极快（个位数毫秒延迟）。

这就是让 AWS 的可靠性达到任何单一数据中心都无法比拟程度的架构。

Priya 向前倾。"所以如果我们的应用程序跨两个可用区运行，其中一个宕机——"

"另一个继续运行，" Maya 接道。

"完全正确。"

Leo 一直在默默听着："我把所有东西都部署在一个 AZ 里了。"

"是的，" Priya 说。"我们注意到了。"

将你的应用程序分散到多个 AZ 的概念——称为**多 AZ 部署**——是 AWS 中最重要的弹性模式之一。我们在第18章深入讨论它。现在，理解 AZ 的存在正是为了使这成为可能。

**边缘节点：到处都快**

AZ 解决了弹性问题。它们没有解决向远离你主要区域的城市中用户快速提供内容的问题。

进入**边缘节点**。

边缘节点是散布在全球400多个城市的小型轻量级基础设施点。它们不是完整的数据中心——它们无法运行你的应用程序。它们*能*做的是在离你用户近的地方缓存内容。

想象一张存储在弗吉尼亚服务器上的菜单图片。每次东京的人想看它，请求就要穿越太平洋再回来。有了边缘节点，AWS 可以在东京存储该文件的副本，并在本地提供——毫秒级而不是数百毫秒。

这是 CloudFront（AWS 的内容分发网络）的骨干。我们在第13章深入研究 CloudFront。现在：边缘节点是关于静态内容的速度。

**选择区域：高级工程师的清单**

当 Nimbus 扩展到服务墨西哥和哥伦比亚的用户时（发生在第12章），区域决策并非随意的。以下是思考方式：

**1. 你的用户在哪里？**

从这里开始。选择最靠近大多数用户的区域。延迟是区域选择最直接、最可衡量的影响。

**2. 是否有合规要求？**

医疗、金融和政府工作负载通常有严格的数据驻留规则。在选择前了解你的监管环境。

**3. 你需要哪些服务？**

并非每个 AWS 服务都在每个区域可用。新服务首先在 `us-east-1` 推出。如果你需要特定服务，请验证你的目标区域是否支持它。

**4. 定价是多少？**

区域的价格有所不同。`us-east-1`（北弗吉尼亚）由于其规模和历史，往往是最便宜的。南美洲稍贵一些。在确定之前检查 AWS 定价页面。

**5. 你是否需要多区域？**

对于大多数应用程序，一个区域内的多个 AZ 就足够了。对于即使区域中断也不可接受的关键应用程序，你才需要多区域设计——但这是一个重大的架构承诺。不要做出投机性的决定。

**没人谈论的局限性**

区域很强大，但它们造成了一个重要的张力。

在多个区域运行真的很难。

区域之间的数据复制有延迟。保持两个区域同步——使区域 A 中的事务立即在区域 B 中可见——是分布式系统中最难的问题之一。AWS 提供了相应的工具，但这需要花钱并增加运营复杂性。

大多数应用程序应该从一个区域开始，配置多个 AZ，只有在有明确需求时才扩展到多区域：监管要求、要求近乎零区域停机时间的合同 SLA，或者用户基础真正分布在各大洲。

过早的多区域架构是初级工程师开始感到自信时最常见、最昂贵的错误之一。

Tom 点了点头。"所以我们不只是因为能做就去做多区域。"

"直到我们需要的时候，" Maya 说。"我们会知道什么时候需要的。"

"我们怎么会知道？" Leo 问。

"当你的架构评审文档中有一个要求说'必须能在区域中断时存活，'" Priya 说。"在那之前：多 AZ。"

## 优势与局限性

**在以下情况使用多区域和多 AZ 设计**：你的应用程序在多个地理位置有用户，延迟很重要；你的 SLA 要求99.99%或更高的可用性；法规要求数据驻留在特定区域；你需要 RTO 在一小时以内的灾难恢复。

**权衡是真实的**：在区域之间复制数据会增加成本——跨区域数据传输是 AWS 账单上被低估最多的项目之一。这也增加了运营复杂性：每次必须在区域间保持一致的写入都会增加延迟。影响真实应用程序的大多数故障都不是跨区域灾难——它们是区域内问题，比如配置错误的安全组或部署失败。在多区域之前先投资于多 AZ。当业务案例明确时再添加多区域。

## 摘要

- AWS 将其全球基础设施组织为**区域**、**可用区**和**边缘节点**。
- **区域**是数据中心的地理集群。每个区域是隔离的——数据留在区域内，除非你明确移动它。
- **可用区**是区域内物理上独立的数据中心，通过低延迟网络连接。跨多个 AZ 部署是应对本地故障的标准方式。
- **边缘节点**将内容缓存在全球用户附近。它们驱动 CloudFront。
- 根据用户位置、合规要求、服务可用性和价格选择你的区域——按此顺序。
- 多 AZ 是标准的弹性基线。多区域适用于有特定、有据可查要求的关键工作负载——不是默认起点。

## 考试技巧

*SAA-C03 领域1——任务1.1 / 领域2——任务2.2*

- **区域默认是隔离的。** 除非你配置，否则数据不会在区域之间复制。这对数据主权和合规场景很重要。
- **AZ 是大多数问题的弹性单位。** 当考试问如何在数据中心故障中存活时，答案涉及一个区域内的多个 AZ。
- **多区域用于应对区域中断。** 如果场景说"即使整个 AWS 区域失败也必须保持运行"，答案涉及多区域架构。
- **边缘节点 ≠ AZ。** 边缘节点缓存内容——它们不能运行你的应用程序服务器。不要将它们与数据中心混淆。
- 考试经常测试合规与区域选择之间的关系。如果场景提到数据驻留要求，区域选择是答案的一部分。

**练习 2——考试练习**

*场景*：一家美国医疗公司必须将所有患者数据存储在单个 AWS 区域内，以符合内部数据驻留政策。他们正在西海岸设计一个新的云应用程序，并希望在不将数据移到另一个区域的情况下最大限度地提高弹性。

哪种配置*最能*满足他们的需求？

A) 在 `us-east-1` 部署，并在俄勒冈使用 CloudFront 边缘节点更快地提供内容  
B) 在 `us-west-2`（俄勒冈）跨多个可用区部署  
C) 在包括 `us-west-2` 和 `us-east-1` 的多个区域部署，并进行跨区域数据复制  
D) 在 `us-west-2` 的单个可用区部署以最小化成本

**提示 1**：该政策意味着数据必须保留在单个区域内。哪些选项将数据移到了另一个区域？

**提示 2**：在将数据保留在 `us-west-2` 的选项中，哪个提供了最多的弹性？

**提示 3**：单个区域内的多个 AZ 提供弹性，而不会跨越区域边界。

**答案**：B

**解析**：`us-west-2` 将所有数据保留在单个区域内，满足政策要求。在该区域内跨多个 AZ 部署可以抵御数据中心故障，而不必将数据移到另一个区域。这是合规性和弹性的正确平衡。

**为什么不是 A？** CloudFront 在全球边缘节点缓存内容——数据会从 `us-west-2` 物理移出，违反了驻留政策。

**为什么不是 C？** 复制到 `us-east-1` 会将患者数据移到东海岸，直接违反了单区域要求。

**为什么不是 D？** 单个 AZ 没有弹性。如果该 AZ 经历中断，应用程序将完全失败。
