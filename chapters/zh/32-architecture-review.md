# 第三十二章：捍卫方案

Well-Architected 评审之后几周，Carlos 又回来了。这次笔记本电脑一直留在他的包里；他拿起一支白板笔，向房间里的每个人打了招呼，在白板旁找了个位置，拔开了笔帽。

"给我讲讲 Nimbus，"他说。仿佛他从未听说过它。

**回顾：从评审到清算**

第 31 章的 Well-Architected 评审揭示了三个高风险发现，也让 Maya 越来越清楚地意识到：团队做出的决策与他们*认真思考过*的决策之间存在差距。框架给了他们描述这个差距的词汇。但框架给不了他们的，是实时弥合差距的实践——在功能上线之前，而不是之后。这正是 Carlos 此行的目的。Maya 特意邀请他，是因为 Nimbus 即将构建一个重要的东西，她希望在第一行生产代码写下之前，先经受一次结构化的挑战。

一次好的架构审查就像飞行员的起飞前检查清单。飞机可能看起来完全准备好飞行了——发动机运转，燃油满载，乘客已登机。但检查清单之所以存在，是因为有经验的飞行员知道，最有可能导致问题的事情，恰恰是那些一直感觉正常、直到出事才暴露的事情。检查清单并不意味着飞行员不知道自己在做什么。它意味着他们已经内化了一个道理：即使是专家，跳过结构化流程时也会遗漏东西。

**架构师的第一步**

接下来发生的事情让团队感到意外。

Maya 开始描述系统——EC2 实例、Aurora、CloudFront、ElastiCache、DynamoDB 用于菜单、带私有子网的 VPC……

Carlos 轻轻地打断了她。

"从业务开始，"他说，"不是技术。"

她停顿了一下。然后："Nimbus 是一个餐厅订餐平台。我们有 287 家餐厅合作伙伴。我们每天处理约 4,200 个订单。平均订单价值 $34。我们按季度环比增长 18%。"

"好。Nimbus 必须做到的最重要的事情是什么？"

"处理订单，"Leo 说。

"具体一点，"Carlos 追问。

"订单必须在下单后五秒内到达餐厅，"Priya 说，"否则厨房会错过时间窗口。"

"如果没能做到会怎样？"

"餐厅会出错。客户会拿到错误的食物，或者等待太长时间。他们会投诉。我们会失去一个餐厅合作伙伴。"

"那么这个五秒的 SLA，"Carlos 说，"不是技术目标。而是业务生存要求。"

沉默。

"这，"他说，"就是为什么架构对话必须从业务需求开始。技术处在约束条件的下游。"

**架构审查结构**

一次真正的架构审查——在你构建重要的东西之前，或者在评估是否要扩展时进行的那种——有一个结构。

Carlos 把它写在白板上：

**1. 理解约束**

什么必须成立？什么绝对不能发生？（不是"我们想要什么"。哪些是不可协商的？）

**2. 理解未知数**

我们不知道什么？我们在哪里做了假设？如果这些假设是错的会怎样？

**3. 评估选项**

现实的替代方案有哪些？每个方案的权衡是什么？

**4. 识别失效模式**

这个系统会怎样崩溃？每个失效模式触发时的事件序列是什么？

**5. 验证监控**

你如何知道出了问题？在用户告诉你之前？

**6. 定义操作手册**

当这个系统在凌晨 3 点崩溃时，值班的人该做什么？

这不是一个要机械遵循的清单。它是一个思维框架。目标是确保重要的问题在你进入生产*之前*就被提出来。

**运行审查：Nimbus 的新功能**

Carlos 受邀的具体原因，是 Nimbus 即将构建一些新东西。

**功能**："Nimbus Instant"——15 分钟送达保证。如果合作伙伴餐厅每周超过一次未能达到 15 分钟的时间窗口，Nimbus 将自动退款给客户。

"带我过一遍技术需求，"Carlos 说。

Priya 开始了。"我们需要从下单到送达的实时追踪。我们需要将实际送达时间与 15 分钟 SLA 进行比较。我们需要自动触发退款。"

"追踪数据的延迟要求是什么？"

"近实时。客户在手机上看到状态更新。"

"多长时间以内？"

"大概 5 秒钟吧。"

"大概？"

"5 秒以内。这是产品需求。"

"好。那么事件流用 Kinesis。如果 Kinesis 延迟了，失效模式是什么？"

"状态更新到达客户那里会迟。"

"这可以接受吗？"

"迟 10 秒？大概可以。迟 60 秒？不行。"

"那追踪系统的 SLA 是什么？"

Priya 看了看 Leo。"我们还没有定。"

Carlos 在白板上写下：*未知：追踪 SLA。*

"这很重要，"他说，"因为 SLA 决定基础设施设计。如果你的 SLA 是 5 秒，你需要的解决方案和 60 秒时是不一样的。"

"等等——可*为什么*要那样做？"Maya 问。"为什么不直接用轮询机制，让应用每隔几秒检查一次，而非实时推送？"

"延迟和成本，"Carlos 说。"轮询方式在规模化时——比如说 10,000 个活跃订单，每个应用每 5 秒轮询一次——就是每秒 2,000 个请求，也就是每分钟 120,000 个请求。通过 Kinesis 的推送模型只在状态变化时才传递更新。请求更少，延迟更低，而且从事件日志中审计 SLA 承诺也更容易。轮询在小规模下行得通。在 Nimbus 正在迈向的规模下，推送才是正确的基础。"

Carlos 解释的过程中，Leo 一直没说话。然后："我本来打算用 WebSocket 来构建这个。"

Carlos 看着他。"讲给我听。"

"每个订单建立一个 WebSocket 连接。下单时客户端连接。服务器在状态变化时推送——已确认、备餐中、配送中、已送达。没有轮询，低延迟，模型简单。"

"由什么来维护 WebSocket 连接？"

"一个 API Gateway WebSocket 端点。Lambda 函数处理连接和消息事件。DynamoDB 存储连接 ID。"

Carlos 把它写在白板上。"那当客户端的网络断开 15 秒时，失效模式是什么？"

"连接被终止。客户端重连，并请求当前状态。"

"从哪里请求？"

"从……Lambda 处理程序，它从 DynamoDB 读取。"

"所以你同时有一条推送路径和一条拉取路径，"Carlos 说。"WebSocket 推送是正常路径。DynamoDB 读取是恢复路径。你如何确保在客户注意到状态过期之前，连接已经重新建立？"

Leo 想了想。"客户端检测到断开，几秒内就会重连。重连逻辑很直接。"

"在 10,000 个订单同时活跃的情况下——这是 Nimbus 正在迈向的规模——那是多少个并发 WebSocket 连接？"

"10,000 个。"

"API Gateway WebSocket 每个账户的默认配额是每秒 500 个**新连接**，"Carlos 说。"不是并发连接数——是连接*速率*。10,000 个稳定连接没问题。问题在于重连风暴：当一次网络抖动同时掉线几千个客户端，它们在同样的两秒钟内全部重连时，你会撞上这个速率配额，重连恰恰在用户最关注的时候开始失败。你可以申请提额，但这是一个随着增长会反复触碰的配额。另外：API Gateway WebSocket 的收费是每百万连接分钟 $0.25，外加每百万条消息 $1.00。在每天 10,000 个订单、平均 40 分钟追踪窗口的情况下，每天只有约 400,000 连接分钟——几分钱的事。在 10,000 个订单同时活跃时，那就是另一个量级了。"

"那也不算多，"Leo 说。

"在 10,000 个活跃订单的规模下确实不多，"Carlos 说。"在那个规模下，算上连接分钟和消息费用，大约每月 $150。成本不是这里反对 WebSocket 的理由。重连风暴下的连接速率配额，以及连接状态管理，才是。"

"所以 WebSocket 在规模化时会变复杂，"Maya 说。

"如果你为此做了架构设计，它们在规模化时是可以管理的，"Carlos 说。"它没有错——只是一组不同的权衡。现在让我给你们看看轮询的替代方案。"

他画出了第二个选项。

"轮询：客户端每 5 秒向 `/orders/{order_id}/status` 发送一个 GET 请求。后端从 DynamoDB 读取。返回当前状态。"

"那是很多请求，"Priya 说。

"10,000 个活跃订单 × 每 5 秒 1 次轮询 = 每秒 2,000 个请求。你的 API 需要处理 2,000 RPS。DynamoDB 自动扩缩。API Gateway 扛得住负载。成本呢：2,000 RPS × 3,600 秒 × 24 小时 × 30 天 = 每月 51.8 亿个请求。API Gateway REST API 定价：每百万请求 $3.50 = 每月 $18,130。"

房间里安静了。

"这在规模化时不是一个可行的选项，"Tom 说。

"正确，"Carlos 说。"5 秒间隔的轮询是实现最简单的方案，也是规模化时最昂贵的方案。它产生的负载还与活跃连接数成正比，而不是与状态变化数成正比。如果一个订单在'备餐中'状态停留 20 分钟，轮询会产生 240 个全部返回相同状态的请求。这是浪费。"

"那 Kinesis 呢？"Maya 问。

"Kinesis 每次状态变化只产生一个事件。订单确认：一个事件。厨房接单：一个事件。骑手取餐：一个事件。送达：一个事件。每个订单四个事件，与每个状态持续多久无关。消费者——你的后端——从 Kinesis 流中读取，再通过你选择的任何投递机制将更新推送给客户端。"

"但客户端仍然需要一种接收推送的方式，"Leo 说。

"是的。最后一公里的投递可以用 Server-Sent Events、长轮询端点，或者 WebSocket。Kinesis 为你的后端处理可靠、有序、可重放的事件流。客户端投递机制是一个独立的决策。关键优势在于：Kinesis 将事件源与消费者解耦。送达追踪系统、退款系统、餐厅通知系统和客户状态展示，全部独立地从同一条 Kinesis 流中消费。"

"所以这不是用 Kinesis 取代 WebSocket，"Maya 说。"而是 Kinesis 加上一个更轻量的客户端投递机制。"

"正是。权衡分析如下："

他写了下来：

| 选项 | 延迟 | 成本（500 / 1 万活跃订单） | 复杂度 |
|---|---|---|---|
| 仅 WebSocket | ~50ms | 每月 $8 / $150 | 中 |
| 轮询（5 秒） | 0–5 秒 | 每月 $906 / $18,130 | 低 |
| Kinesis + SSE | ~200ms | 每月 $8 / $75 | 中高 |

"轮询选项被成本淘汰了，"Carlos 说。"WebSocket 可行，但在规模化时需要做连接管理。Kinesis 加 Server-Sent Events 的延迟略高，成本相当——它给你换来的，是退款系统所需的持久、可重放的事件日志，以及解耦的消费者。"

"等等——可*为什么*要那样做？"Maya 问。"如果 WebSocket 延迟更低，为什么要接受 Kinesis 加 SSE 的更高延迟？"

"对一个盯着配送状态更新的客户来说，200ms 和 50ms 的差别能感知到吗？"Carlos 问。

"不能，"她说。

"那么这个延迟差异就在感知阈值以下。一万个活跃订单时的成本差异也不大——每月 $75 对 $150。架构上的差异才是真正的论据：Kinesis 给你一个持久、可重放的事件日志——退款审计跟踪正需要它——并且解耦了你的追踪消费者。WebSocket 则意味着你以后还要重新构建这层解耦。"

Leo 看着那张表。"我们差点就把 WebSocket 版本上线了。"

"它本来也能用，"Carlos 说。"这是需要理解的重点。WebSocket 本来能用。架构中的问题很少是'这能用吗？'。问题是'随着增长它的代价是什么，以及我们以后必须重建什么？'"


**架构师提出的问题**

在接下来的两个小时里，Carlos 引导团队完成了审查。他的部分问题：

**关于数据存储**：

"在履约过程中，订单状态存储在哪里？如果应用程序在配送途中崩溃，恢复过程是什么？你能仅从事件重建状态吗？"

**关于退款机制**：

"退款是自动触发的。什么机制阻止退款被发放两次？如果支付处理器超时，你不确定退款是否被接受，怎么办？"

**关于送达追踪**：

"你们依赖骑手的 GPS 数据。如果 GPS 信号丢失 90 秒会怎样？你们如何区分'GPS 丢失'、'配送进行中'和'配送出问题'？"

**关于失效处理**：

"如果退款服务宕机，订单还能正常进行吗？客户还能拿到食物吗？系统部分失效时的用户体验是什么？"

**关于可观测性**：

"你们现在如何知道有多少订单当前距离 15 分钟 SLA 只剩 5 分钟以内？如果这个数字飙升，谁会收到通知？"

每个问题都揭示了团队在不自知的情况下做出的一个假设。

"我已经部署了——哦，"Leo 说。"退款端点。我本来打算直接调用支付 API。我们没考虑过调用两次的情况。"他停顿了一下。"所以如果第一次调用成功了，但我们的确认在传输中丢失，我们再调用一次，客户就会收到两笔退款。"

"我们有没有想过，如果支付 API 接受了第一次调用，但我们的确认在传输中丢失，会发生什么？"Priya 问。

"这就是幂等性，"Carlos 说。

"幂等性密钥——每次退款尝试一个唯一 ID，在调用支付 API 之前存储到数据库里，"Priya 说。"如果我们用同一个密钥调用两次，支付 API 会忽略第二次调用。"

"这意味着，"Carlos 补充说，"你们需要一个用于退款操作的持久状态存储，而不只是队列里的一个事件。"


"我们讨论过的监控，"Carlos 说，"全是基础设施监控。CPU。连接数。Kinesis 延迟。这些很重要——但它们不是能告诉你 Nimbus Instant 是否正常工作的监控。"

"那能告诉我们它正常工作的监控是什么？"Maya 问。

"每家餐厅的 P95 确认时间。在第 95 百分位上，从下单到餐厅确认需要多久——按每个餐厅合作伙伴分别度量？"

"我们没有这个指标，"Priya 说。

"这就是那个缺口，"Carlos 说。"你可以有完美的基础设施——CloudWatch 每个告警都是绿色的——但仍然有一个餐厅合作伙伴，由于平板软件的一个 bug，确认延迟已经恶化了三周。基础设施没问题。业务 SLA 却正在被违反。而你要等到餐厅打电话来投诉才会知道。"

"我们怎么采集这个指标？"Leo 问。

"每次收到订单确认时，发出一个自定义 CloudWatch 指标，或者推送到你们的分析管道。给下单时间打时间戳。给确认时间打时间戳。计算差值。带上 `restaurant_id` 标签发出去。构建一个 CloudWatch 仪表板，按餐厅展示过去 7 天滚动窗口的 p95 确认时间。"

"当它恶化时告警？"Tom 问。

"当某家餐厅的 p95 超过 90 秒且持续超过 5 分钟时告警，"Carlos 说。"那是一个值得主动联系对方的异常，而不是坐等投诉的情形。"

"这就是监控基础设施和监控产品的区别，"Priya 说。

"正是，"Carlos 说。"基础设施监控告诉你系统是否健康。业务级监控告诉你客户是否正在体验到你向他们承诺的东西。两者你都需要。大多数团队只有前者。"

Maya 把它加进了 ADR 附录：除了基础设施健康指标外，还要追踪每家餐厅的 p95 确认时间。告警阈值由产品团队与餐厅成功团队协商确定。

"这也是成本监控与业务监控交汇的地方，"Tom 说。"如果我们的确认延迟在周五晚间对一部分餐厅出现飙升，根本原因可能是 Lambda 冷启动恰好命中了这些餐厅在 Kinesis 里的分片。业务指标揭示症状。基础设施指标揭示原因。"

"而且解决方案可能不是更多的基础设施，"Carlos 说。"可能是给特定 Lambda 函数配置预置并发。或者是分片再平衡。或者是餐厅确认端点里的一个 bug。在你同时拥有两层可观测性之前，你无法知道是哪一个。"

"我们有没有想过，如果我们修好了基础设施，业务指标还是没有改善，会怎样？"Priya 问。

"那么根本原因就不在基础设施里，"Carlos 说。"这是很有价值的信息。没有业务指标，你会一直追逐基础设施层面的改进，而问题其实在别处。"


"当我们同时追踪 500 个并发配送时，这个每月要花多少钱？"Tom 问。"状态存储、Kinesis 流、处理事件的 Lambda 函数？"

Carlos 点点头。"这正是现在该问的问题——在你设计的时候，而不是在你建好之后。"

这就是在结构化审查中会浮现的那类架构细节——而在你埋头构建时，它们往往不会浮现。

**架构决策记录**

审查结束后，Carlos 建议团队用**架构决策记录（ADR）**来记录他们的决策——简短的文档，捕获：

- **做出了什么决策**
- **考虑了哪些替代方案**
- **为什么做出这个决策（当时的背景和约束）**
- **权衡是什么**
- **什么会让我们重新审视这个决策**

你可能会想：ADR 必须是正式文档吗？不必。如果你的团队在 Slack 里工作，一个 ADR 也可以是 Slack 帖子里的一个段落。格式无关紧要。在继续前进之前，把你决定了什么、为什么这么决定写下来——这个动作本身才是建立组织记忆的关键。

"ADR 是为你未来的自己准备的，"Carlos 说。"18 个月后，你会看着一段架构，想知道当初为什么这么做。如果你有 ADR，你会理解当时的背景。如果没有，你要么不动它（因为你不敢碰），要么改掉它（因为你不理解当初为什么这么做）。"

Leo 那天下午写了第一份 ADR：使用 Kinesis 处理送达追踪事件的决策，包含背景、考虑过的替代方案（SQS、EventBridge、轮询）以及各项权衡。

Carlos 看了 Leo 起草的 ADR。他三十秒就读完了。然后说："把 ADR-007 给大家看看。"

Leo 把它投影了出来。

**ADR-007：送达追踪事件基础设施**

**日期**：2025-03-14
**状态**：已接受
**作者**：Leo（由 Carlos、Priya 评审）

---

**问题**

Nimbus Instant 需要实时的配送状态追踪。订单必须更新状态（已确认 → 备餐中 → 配送中 → 已送达），并在状态变化后 5 秒内将更新呈现到客户的移动应用上。退款系统还需要一份可审计、可重放的配送事件日志，用于判定 SLA 是否达标。

---

**考虑过的选项**

**选项 1：API Gateway WebSocket + DynamoDB 状态**
- 客户端为每个订单维护一个 WebSocket 连接
- 后端通过打开的连接推送状态变化
- 重连时，客户端从 DynamoDB 拉取当前状态
- 规模化时的预估成本（1 万个同时活跃订单）：约每月 $150
- 弱点：规模化时的连接限额管理；没有内置的可重放能力供审计使用

**选项 2：客户端轮询（5 秒间隔）**
- 客户端每 5 秒轮询 `/orders/{order_id}/status`
- 后端在每次轮询时从 DynamoDB 读取
- 实现最简单
- 规模化时的预估成本（1 万个同时活跃订单）：每月 $18,130
- 因成本被淘汰

**选项 3：Kinesis Data Streams + Server-Sent Events**
- 配送状态变化发布到 Kinesis 流，按吞吐量确定容量：单个分片可摄入 1 MB/s 或 1,000 条记录/s。在 1 万个活跃订单（每个订单约 4 个状态变化事件，小型 JSON 载荷）的情况下，峰值写入速率约为 40-50 个事件/s——一个分片就够。预置 3 个分片以分散分区并为消费者留余量。
- SSE 端点订阅分配给订单分区的 Kinesis 分片
- 客户端接收 SSE 事件；使用标准 EventSource API 自动重连
- 规模化时的预估成本（1 万个同时活跃订单）：约每月 $75
- 提供持久、可重放的事件日志；解耦所有消费者

---

**决策**

选项 3：Kinesis Data Streams + SSE。

理由：规模化时成本优势显著；Kinesis 事件日志满足退款审计要求，无需另行实现审计跟踪；规模化时 SSE 的重连处理比 WebSocket 的连接管理更简单。

---

**后果**

- *正面*：退款系统、餐厅通知系统和客户应用全部独立地从同一条 Kinesis 流中消费。新增消费者无需修改生产者。
- *正面*：事件最多可重放 7 天（这是我们配置的扩展保留期；Kinesis 支持最长 365 天，需额外付费）。如果退款处理 Lambda 失败，它可以重放漏掉的事件。
- *负面*：SSE 延迟（~200ms）高于 WebSocket 延迟（~50ms）。可以接受，因为这一差异低于客户对状态更新的感知阈值。
- *负面*：Kinesis 预置模式定价随分片小时数增长，扩展保留期会让每分片成本大约翻倍。吞吐量余量很大（单分片可摄入 1,000 条记录/s），但当消费者数量和每消费者读取负载增长到日活跃订单超过约 5 万时，分片数量——以及重新分片/消费者扇出策略——将需要重新审视。

**什么会让我们重新审视这个决策**：如果订单量增长到新的规模下 Kinesis 分片成本超过 WebSocket 成本，或者 200ms 的 SSE 延迟成为产品差异化问题。

---

"重新审视的触发条件，"Carlos 说。"每个决策都存在让它变成错误决策的条件。把这些条件写下来，意味着它们出现时你能认出来。"

"而不是在事后复盘里才发现它们，"Priya 说。

Leo 一直在记笔记。"这份 ADR 在做两件事，"他说。"它记录了我们决定了什么。它还记录了如果情况变化，我们接下来需要决定什么。"

"这就是让一份 ADR 在十八个月后仍然有用的东西，"Carlos 说。"不是决策本身——决策会过时。是推理过程。推理告诉你这个决策是否应该被重新审视，哪怕这个决策仍然有效。"


**什么是架构师**

会议结束时，Maya 问了 Carlos 最初的那个问题："做架构决策和像架构师一样思考有什么区别？"

他想了想。

"架构师懂的技术并不比高级工程师多，"他说。"一个好的架构师对最新框架的了解可能还少一点。但架构师有一组不同的默认问题。"

"什么意思？"

"当你作为高级工程师看一个新功能时，你的第一批问题通常是：'我们要构建什么？它怎么工作？做这件事最好的库是什么？'当架构师看同一个功能时，第一批问题是：'这解决了什么问题？流量翻倍时什么会首先崩溃？我们如何知道它什么时候降级了？支付处理器变慢时用户体验到的是什么？'"

"架构师询问的是系统在压力下的情况，"Leo 说。

"以及每种失效的业务后果，"Priya 补充道。

"还有，"Tom 说，"这个东西规模化之后账单会怎样。"

Carlos 点点头。"你们所有人都已经在这样做了。从第 1 章开始就在做了。高级工程师和架构师的区别不是一张认证或一个头衔。而是提出下一个问题的习惯——那个揭示你还没想到的事情的问题。"

**变体：当架构审查增加风险而不是消除风险时**

如果你的审查被当作审批关卡而不是学习过程，团队就会开始隐藏设计选择来规避延误——而失效模式依然存在，只是没有被记录下来。一个拖慢交付却不提升质量的架构审查，比没有审查更糟。

如果退款服务的幂等性问题被当作功能上线的一次意外延误，而不是一次必要的发现，Leo 就会把原始端点上线，双重退款迟早会发生，而团队将从一位愤怒的客户那里得知此事。审查在修复成本只是一天工作量、而不是一次回滚的时候，把问题暴露了出来。

审查的价值，与团队愿意让它改变设计的程度成正比。

## 优势与局限

**架构审查**：

- 在进入生产之前捕获失效模式
- 在往往各自掌握孤立知识的团队成员之间建立共同理解
- 生成多年持续产生回报的文档（ADR）
- 以有益的方式放慢决策——没有审查的"快速行动"，就是"快速行动，撞上你没看见的墙"

**复杂性所在**：

- 需要有足够技能提出正确问题的人——审查的质量取决于审查者的水平
- 如果被当作打勾的复选框而不是对话，可能会变得官僚化
- 某些架构决策确实不需要完整的审查——知道哪些需要，本身就是一种架构技能
- 输出物（ADR、图表、决策日志）必须随系统演进而持续维护

## 总结

与 Carlos 的审查用了两个小时，产出了三份 ADR、一份在功能开工前需要解决的六个未知数的清单，以及一项架构变更（幂等性状态存储）——后者如果在上线后再补会非常痛苦。起飞前检查清单的比喻贯穿始终：没有发现什么灾难性的东西，但有几个日后会引发问题的隐患，在还容易修复的时候就被发现并记录了下来。

- 架构审查从**业务需求开始，而非技术**。
- 审查结构：约束 → 未知数 → 选项 → 失效模式 → 监控 → 操作手册。
- 架构师问：什么首先崩溃？我们如何知道它降级了？失效期间的用户体验是什么？规模化时的成本是什么？
- **架构决策记录（ADR）**捕获决定了什么、为什么决定，以及什么会导致重新考虑。
- 像架构师一样思考是一种习惯：提出下一个问题，尤其是关于失效模式、业务后果和规模经济的问题。

## 考试技巧

*SAA-C03 领域：跨领域 — 架构推理*

本章与其说是关于特定考试主题，不如说是关于考试所测试的思维方式。

- **SAA-C03 场景**几乎总是先描述一个业务约束（"公司无法承受超过 1 小时的停机"），然后要求你选择满足它的架构。练习把业务约束翻译成技术需求。
- **失效模式思维**：许多考试题描述一个系统，然后问某个组件失效时会发生什么。为你遇到的架构练习问"什么首先崩溃？"。
- **权衡思维**：考试很少有"完美"答案。它要的是在一组约束下的*最佳*答案。要习惯于"这个选项在这些特定要求下是正确的，尽管在不同要求下另一个选项会更好"。
- **架构决策记录**：不是 AWS 服务，而是反映 Well-Architected Framework 卓越运营支柱的一项最佳实践。
- **Kinesis 用于实时事件流**：本章的 Nimbus Instant 功能用 Kinesis 做配送事件流。考试信号："实时事件摄入与有序处理" → Kinesis Data Streams。"解耦组件、至少一次投递" → SQS。知道何时该用哪一个，是一个反复出现的考试模式。
- **幂等性作为可考的模式**：SAA-C03 经常考分布式系统中的幂等性。核心模式：在调用外部系统之前生成一个唯一的幂等性密钥；持久化该密钥和结果；重试时，先检查是否已存在该密钥，再决定是否重新执行。如果已存在，直接返回之前存储的结果而不重新执行。这可以防止网络超时后的重试造成重复扣款、重复发送和重复的状态变更。考试信号："防止服务调用重试时的重复操作"或"确保支付事件的恰好一次处理" → 幂等性密钥存储在 DynamoDB 中并使用条件写入。
- **Server-Sent Events 与 WebSocket 的对比**：SSE 是单向的（服务器到客户端），使用标准 HTTP，并通过 EventSource API 自动重连。WebSocket 是双向的，需要连接管理，适用于客户端也需要向服务器推送数据的场景。对于配送状态更新（仅服务器到客户端），规模化时 SSE 比 WebSocket 更简单也更便宜。

**练习 2 — SAA-C03 场景**

*场景*：一家公司正在构建一个在线广告的实时竞价管理系统。竞价必须在 100 毫秒内完成评估并响应。系统在峰值时每秒处理 100 万次竞价。如果竞价系统宕机，公司就会损失广告收入。公司的数据库团队提议使用带 10 个读副本的 RDS Aurora。解决方案架构师必须先评估该提案是否在根本上可行，然后再审视它的次要特性。

架构师应该首先提出哪个关切？

A) 10 个 Aurora 读副本的成本对预算来说太高  
B) Aurora 读副本存在复制延迟，可能引发一致性问题  
C) Aurora 的典型查询延迟 1-5ms 可能无法满足 100ms 响应 SLA  
D) RDS Aurora 在此延迟要求下不支持每秒 100 万次请求的事务量

**提示 1**：主要约束是 100ms 总响应时间、每秒 100 万次请求。这些关切中，哪一个一旦成立，就会让该提案无论怎样解决其余三项都行不通？

**提示 2**：Aurora 查询延迟通常为 1-5ms。数据库查询占 1-5ms，留给网络、应用逻辑和序列化的还有 95-99ms。100ms 的约束有风险吗？

**提示 3**：Aurora 可以处理高 IOPS，但每秒 100 万次请求是一个非同寻常的速率。在那个规模下，架构会发生什么？

**答案**：D

**解释**：尽管 Aurora 性能很高，但每秒 100 万次请求、总响应时间 100ms 是一个极端要求——它是决定该提案能否成立的架构性阻断点。架构师应该首先质疑 Aurora（或任何关系数据库）能否在这种规模和延迟下充当主要查找系统。这类系统通常使用内存数据存储（Redis）或专门的低延迟数据库，而不是带完整 SQL 语义的关系数据库。仅就 Aurora 查询而言，100ms 的 SLA 是可以达到的，但 100 万 RPS 与 100ms 总 SLA 的组合超出了典型的 Aurora 吞吐特性。"首先"意味着先论可行性，再谈打磨：如果引擎撑不住这个负载，关于该提案的其他一切关切都是空谈。

**为什么不是 A？** 成本是一个合理的关切，但首要关切应该是该架构在规定要求下是否技术可行。

**为什么不是 B？** 复制延迟是该提案真实存在但*次要*的特性——是架构可行之后再去调优的属性。Aurora 副本延迟通常 <100ms，对大多数用例可以接受；如果首先提出它，就等于在讨论一个根本撑不住所需吞吐量的系统的一致性行为。可行性问题（D）将其包含在内。

**为什么不是 C？** Aurora 1-5ms 的延迟对数据库查询部分而言远在 100ms SLA 之内。这不是首要关切。
