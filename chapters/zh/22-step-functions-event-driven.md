# 第二十二章：自己运行的流程图

Nimbus 的订单确认需要五件事按顺序发生：扣款、发送确认邮件、通知餐厅、更新库存以及记录交易以供财务使用。如果第三步失败——如果餐厅通知超时——第一步和第二步已经完成了。客户已被扣款。邮件已发送。但餐厅不知道订单的存在。

Leo 给这类 bug 起了个名字：部分成功。"一切正常，"他说，"除了那个重要的部分。"

"这种情况发生了多少次？"Maya 问。

"过去两周十一次。我们大部分是从餐厅愤怒的电话中发现的。有两次是事后在日志中发现的。"

"所以我们没有协调，"Priya 说，"五个步骤，作为脚本运行，没有保证它们全部完成。"

"或者按正确顺序完成。"

"或者我们知道哪个失败了。"

Leo 把代码投影到屏幕上。这是一个 Python 函数：五十行，五个连续的 API 调用，整个函数外只有一个 try/except 块。"如果这里有任何内容抛出异常，我们得到一个 500 错误，客户看到一个错误。但扣款和邮件不会回滚。"

"我们需要一个工作流，"Maya 说，"能追踪每个步骤的东西。"

**AWS Step Functions：编排工作流**

**AWS Step Functions** 是一个无服务器编排服务，将应用程序的步骤协调为可视化工作流。每个步骤是**状态机**中的一个**状态**。

不是从上到下运行并崩溃的 Python 脚本，而是将工作流定义为 JSON/YAML 状态机：

```json
{
  "StartAt": "ValidateLicense",
  "States": {
    "ValidateLicense": {
      "Type": "Task",
      "Resource": "arn:aws:lambda:us-east-1:123456789012:function:validate-license",
      "Next": "ImportMenu",
      "Catch": [{"ErrorEquals": ["*"], "Next": "OnboardingFailed"}]
    },
    "ImportMenu": {
      "Type": "Task",
      "Resource": "arn:aws:lambda:us-east-1:123456789012:function:import-menu",
      "Next": "SetupPayments",
      "Retry": [{"ErrorEquals": ["*"], "MaxAttempts": 3, "IntervalSeconds": 5}]
    },
    ...
  }
}
```

每个状态可以：

- **执行 Lambda 函数**（最常见的模式）
- **执行 ECS 任务**（用于较长时间运行的工作）
- **等待特定时间**或**事件**（暂停工作流，直到外部事件发生）
- **基于条件选择路径**（if/else 逻辑）
- **并行运行多个分支**
- **失败时重试**，可配置退避
- **捕获错误**并路由到错误处理状态

Step Functions 持久地管理执行状态。如果第 3 步失败，执行在第 3 步暂停。你可以在控制台中检查失败的执行，修复问题，然后从第 3 步重新启动——无需重复第 1 步和第 2 步。

**状态类型：构建块**

**Task**：执行操作——调用 Lambda 函数、启动 ECS 任务、调用 API。这是真正的工作发生的地方。

**Choice**：根据输入数据中的条件进行分支。类似代码中的 if/else。

**Parallel**：同时运行多个分支并等待全部完成。

**Map**：对列表中的每个项目应用一组状态。并行处理 50 个餐厅菜单项目。

**Wait**：暂停指定时间或直到时间戳。对计划延迟很有用。

**Pass**：将输入传递给输出而不做任何工作。用于数据转换和测试。

**Succeed/Fail**：终止执行的终止状态。

对于餐厅入驻，Leo 设计了一个工作流：

1. ValidateLicense（Task → Lambda）
2. ImportMenu（Task → Lambda，重试 3 次）
3. 并行分支：
   a. SetupPayments（Task → Lambda）
   b. CreateIAMRole（Task → Lambda）
4. SendWelcomeEmail（Task → Lambda，等待并行完成）
5. NotifySalesTeam（Task → Lambda）

步骤 3a 和 3b 并行运行——它们相互不依赖，同时运行节省时间。

**标准工作流与快速工作流**

Step Functions 提供两种工作流类型：

**标准工作流**：

- 最长持续时间：1 年
- 执行是持久的——状态被持久化，可以检查和审计
- 至少一次执行（每个任务至少运行一次）
- 按状态转换计费
- 最适合长期运行的重要工作流（订单处理、入驻、支付流程）

**快速工作流**：

- 最长持续时间：5 分钟
- 更高吞吐量——每秒最多 100,000 次
- 至少一次或至多一次（可配置）
- 按持续时间计费（类似 Lambda）
- 最适合高量、短持续时间的工作流（实时事件处理、IoT 数据摄取）

对于 Nimbus 的餐厅入驻：标准工作流（它很重要，持久，如果涉及手动步骤可能需要几个小时）。

对于 Nimbus 的实时订单状态更新：快速工作流（高量、短持续时间、不那么关键）。

**事件驱动架构：更大的图景**

Step Functions 是一个更大模式的一部分：**事件驱动架构**。不是服务直接互相调用（紧耦合），而是服务发出事件，其他服务对这些事件做出响应。

我们在本书中看到了这一点：

- 下单 → SNS 发布事件 → SQS 队列传递给消费者
- S3 文件上传 → Lambda 被触发处理它
- DynamoDB 记录变更 → DynamoDB Streams → Lambda 更新缓存

**Amazon EventBridge**（以前称为 CloudWatch Events）是这种模式的高级事件总线。它根据规则将来自 AWS 服务和你自己的应用程序的事件路由到目标（Lambda、SQS、Step Functions 等）。

EventBridge 允许在架构层面进行松耦合：订单服务发布 `order.placed` 事件而不知道谁在监听。分析服务、通知服务和积分服务都独立地监听。添加新的监听器不需要更改订单服务。

**Step Functions 是正确工具的时机**

Step Functions 在以下情况下表现出色：

**需要跨步骤追踪进度的多步骤工作流**

**涉及人工的流程**——Step Functions 可以无限期地等待外部事件（比如人类批准某事），然后继续

**大规模错误处理**——在许多步骤中内置重试、捕获和回退逻辑

**可审计的流程**——每次执行记录每次状态转换。你可以准确地看到发生了什么以及何时发生的。

**复杂的并行或顺序逻辑**——可视化工作流使推理比等效代码更容易

Step Functions 对于简单的两步流程来说是过度设计。当协调本身有价值且失败场景重要时使用它。

## 优势与局限

**Step Functions 的强大之处**：

- 可视化执行历史——准确看到工作流在哪里（或在哪里失败）
- 内置重试和错误处理——无需自定义重试代码
- 持久状态——执行在服务重启和中断后仍然存活
- 与 200 多个 AWS 服务的直接集成（不只是 Lambda）
- 可视化工作流自我记录

**复杂性所在**：

- 标准工作流按状态转换计费——具有许多状态的复杂工作流在规模扩大时可能变得昂贵
- ASL（Amazon States Language）JSON 格式有学习曲线
- 最大有效载荷大小为 256KB——大型数据必须通过 S3 引用传递，而不是直接通过工作流
- 具有许多手动步骤的长期运行工作流需要仔细的超时配置

## 总结

- **Step Functions** 将多步骤工作流编排为状态机。
- 每个**状态**可以运行 Lambda 函数、执行 ECS 任务、等待、分支或运行并行步骤。
- **重试和捕获**内置于每个状态——不需要自定义重试代码。
- **标准工作流**：长期运行（最长 1 年），持久，至少一次。用于关键业务流程。
- **快速工作流**：短持续时间（最长 5 分钟），高吞吐量。用于高量事件处理。
- **事件驱动架构**使用 SNS、SQS、Lambda 和 EventBridge 等服务，围绕事件而非直接调用将系统解耦。
- 当步骤的协调本身很复杂且可审计性很重要时，使用 Step Functions。

## 考试技巧

*SAA-C03 领域：设计弹性架构（领域 2，任务 2.1）*

- **Step Functions 用例信号**："编排多个 Lambda 函数"、"具有重试和错误处理的工作流"、"自动化工作流中的人工审批步骤"、"每个工作流步骤的审计跟踪"→ Step Functions。
- **标准与快速对比**：标准工作流用于长期运行、可审计、关键业务工作流。快速工作流用于高吞吐量、短持续时间的事件处理。
- **SQS 与 Step Functions**：SQS 用于简单的任务队列（生产者/消费者）。Step Functions 用于具有复杂逻辑、重试和状态追踪的多步骤工作流。
- **EventBridge 信号**："将 AWS 服务的事件路由到目标"、"服务之间的事件驱动集成"、"调度 Lambda 函数"→ EventBridge（以前称为 CloudWatch Events）。
- **回调模式**：Step Functions 可以暂停执行并等待外部回调（任务令牌）。工作完成时，worker 使用令牌回调。对于不想受到 Lambda 15 分钟限制的长时间运行 ECS 任务很有用。
- **直接 SDK 集成**：Step Functions 可以直接调用 AWS 服务（DynamoDB、S3、SQS 等），而无需通过 Lambda。减少简单服务调用的成本和延迟。

**练习 2 — 考试练习**

*场景*：一家金融服务公司以多个步骤处理贷款申请：信用检查、收入验证、文件验证、承销商审查（手动），以及决定通知。每个步骤可能需要从几秒（信用检查）到几天（承销商审查）。公司需要每个步骤的完整审计跟踪以满足合规要求。失败的自动步骤必须自动重试；手动步骤必须暂停并等待人工决定。

哪种服务最符合这些要求？

A) AWS Lambda 函数通过 SQS 队列链接，每个步骤之间有一个队列  
B) AWS Step Functions 标准工作流，对承销商审查步骤使用等待回调模式  
C) AWS Step Functions 快速工作流用于自动步骤，SQS FIFO 用于手动步骤  
D) Amazon EventBridge，使用事件规则在 Lambda 函数之间路由每个步骤

**提示 1**："最长几天"的持续时间——哪种 Step Functions 类型支持这个？

**提示 2**："等待人工决定"——哪种 Step Functions 模式是为此设计的？

**提示 3**："用于合规的完整审计跟踪"——哪种服务提供每次执行的状态历史？

**答案**：B

**解释**：Step Functions 标准工作流可以运行最长 1 年，支持可能持续数天的承销商审查步骤。等待回调模式在承销商步骤处暂停执行并附带任务令牌；当承销商做出决定时，他们用令牌回调以继续工作流。标准工作流记录每次状态转换——合规所需的完整审计跟踪。

**为什么不选 A？** 通过 SQS 链接的 Lambda 不提供内置的状态跟踪或审计跟踪。失败的步骤需要自定义重试逻辑。从特定失败步骤重新启动需要自定义实现。

**为什么不选 C？** 快速工作流最长持续时间为 5 分钟——与可能需要几天的步骤不兼容。

**为什么不选 D？** EventBridge 在服务之间路由事件，但不维护工作流状态或提供内置重试/审计。仅在 EventBridge 上构建这个需要自定义状态管理。

## 片尾彩蛋

餐厅入驻工作流上线了。

接下来的一个月，12 家新餐厅合作伙伴完成了入驻。其中两家在支付处理步骤（第 3 步）中出现了失败。在两种情况下，Step Functions 都捕获了确切的错误，保存了执行状态，并向 Nimbus 团队发送了警报。

Leo 修复了根本原因（支付提供商 API 密钥配置错误），并从第 3 步重试了两次执行。每次执行在 23 秒内完成，从它们失败的确切位置恢复。

没有餐厅需要重新导入。没有 IAM 角色被重复创建。没有重复的欢迎邮件被发送。

"现在呢？"
