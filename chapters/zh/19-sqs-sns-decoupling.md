# 第19章：票务机器

票务机器是一场悄无声息的革命。取一个号码，等待叫号。排队变成了队列。人们可以坐下。服务台以自己的节奏工作。没有人阻塞任何人。

Nimbus 有一个问题，直到订单变得热门才显现出来。

每次下单，API 服务器必须：

1. 将订单保存到数据库
2. 向餐厅的平板电脑发送通知
3. 向顾客发送确认邮件
4. 更新餐厅的分析仪表板
5. 记录事件用于计费

所有这些都必须在 API 响应顾客之前同步发生。如果邮件服务很慢（有时确实如此），顾客要等。如果分析仪表板宕机（有时确实如此），订单失败了。

"我们是紧密耦合的，" Priya 说。"如果任何下游步骤失败，整个订单都失败了。"

"如果我们可以保存订单，立即确认给顾客，" Leo 说，"然后在后台处理其余的呢？"

"那就是一个队列，" Priya 说。

**熟食柜台模型**

在一个繁忙的熟食柜台，收银台的人不会等切肉的人切完再接待下一位顾客。他们接受订单，把它交给厨房，然后开始服务下一位顾客。厨房按自己的节奏处理订单。

顾客获得了更快的服务。厨房不会被突然的爆发压垮。如果厨房有慢的时候，订单会堆积在队列中，而不是在收银台造成错误。

这就是**解耦**：将接受工作的组件与处理工作的组件分开。

在软件系统中，队列通常是消息代理——一个从生产者接受消息并将其传递给消费者的服务。

**Amazon SQS：队列**

**Amazon SQS（简单队列服务）**是 AWS 的托管消息队列服务。它持久存储消息，直到消费者处理它们。

基本流程：

1. **生产者**（API 服务器）向队列放置消息：`{ "orderId": "ORD-5532", "restaurantId": "47", "items": [...] }`
2. API 立即回应顾客："订单已确认！"
3. **消费者**（独立的工作者服务）从队列读取消息并处理它们：发送餐厅通知、发送确认邮件、更新分析

顾客体验：即时确认。下游处理：异步发生，以工作者的节奏进行。

**SQS 关键概念**

**消息可见性超时**：当消费者从 SQS 读取消息时，消息对其他消费者变得*不可见*一段时间（默认：30秒）。这给消费者时间来处理它。如果消费者成功完成，它删除消息。如果消费者崩溃，可见性超时到期，消息再次对另一个消费者可见以重试。

这确保了至少一次传递：每条消息至少会被处理一次，即使消费者在处理中途失败。

**死信队列（DLQ）**：如果消息处理失败太多次（可配置——例如5次重试），SQS 将其移到死信队列。你检查 DLQ 以了解消息失败的原因，而不会丢失它们。

**队列类型**：

**标准队列**：最大吞吐量（每秒无限消息）。传递顺序是尽力而为（不保证）。至少一次传递（很少情况下，消息可能被传递两次）。

**FIFO 队列**：严格的先进先出排序。恰好一次传递。带批处理每秒最多3,000条消息，不带每秒最多300条。在顺序很重要时使用（金融交易、顺序状态更改）。

对于 Nimbus，大多数队列使用标准队列。计费队列使用 FIFO 以确保费用按顺序处理。

**Amazon SNS：广播者**

**Amazon SNS（简单通知服务）**是一种发布/订阅（pub/sub）消息服务。与一个生产者、一个消费者（队列）不同，SNS 支持一条消息同时传递给*多个*订阅者。

模型：

1. **发布者**向 SNS **主题**发送消息
2. 该主题的所有**订阅者**同时接收消息（扇出）

订阅者可以是：

- SQS 队列（将消息推送到队列进行异步处理）
- Lambda 函数（直接触发函数）
- HTTP/HTTPS 端点（Webhook 传递）
- 电子邮件地址
- SMS（手机号码）

对于 Nimbus，订单下达事件被发布到名为 `order-events` 的 SNS 主题：

- 餐厅通知服务订阅（在其 SQS 队列上接收）
- 邮件服务订阅（在其 SQS 队列上接收）
- 分析服务订阅（在其 SQS 队列上接收）
- 计费服务订阅（在其 FIFO SQS 队列上接收）

一个订单事件。四个订阅者。全部同时通知。每个以自己的节奏处理。

"所以 SNS 是公告，" Maya 说，"SQS 是每个团队以自己的速度处理公告的收件箱。"

"完全正确，" Leo 说。"SNS/SQS 扇出是标准模式。"

**SNS/SQS 扇出模式**

这种组合——SNS 主题提供给多个 SQS 队列——是 AWS 中最重要的架构模式之一：

```
API 服务器
    |
    | 发布到
    ↓
SNS 主题："order-placed"
    |
    |——————————————|——————————————|
    ↓              ↓              ↓
SQS 队列       SQS 队列       SQS 队列
（通知）       （邮件服务）   （分析）
    |              |              |
    ↓              ↓              ↓
工作者         工作者         工作者
Lambda/EC2    Lambda/EC2    Lambda/EC2
```

每个队列是独立的。分析服务可以很慢——它的队列堆积，但通知和邮件服务不受影响。如果分析服务宕机，它的消息在队列中等待，直到它恢复。什么都没有丢失。

这是关键属性：**独立失败**。一个消费者中的问题不会传播到其他消费者。

**消息过滤：不是每个订阅者都需要每条消息**

随着系统的增长，你不希望每个订阅者处理每条消息。如果分析服务只关心已完成的订单，它不应该接收关于失败支付处理的消息。

**SNS 消息过滤**让订阅者指定过滤策略——只传递与某些属性匹配的消息。

餐厅通知服务以过滤条件订阅：只有 `status = "confirmed"` 的消息。

错误告警服务以过滤条件订阅：只有 `status = "failed"` 的消息。

每个订阅者只得到它需要的。

**何时使用 SQS vs SNS**

**只用 SQS**：一个生产者，一个消费者（或同一队列上的多个竞争消费者）。消息需要只处理一次，按顺序（FIFO）或不按顺序（标准）。工作者队列模式——一个队列，多个工作者从中消费。

**只用 SNS**：即发即忘通知。推送到电子邮件、SMS 或 HTTP 端点。不需要排队消息——只是通知然后继续。

**SNS + SQS（扇出）**：一个事件，多个独立消费者。每个消费者都有自己的队列，独立处理，独立失败。

## 优势与局限性

**为什么 SQS 和 SNS 很强大**：

- SQS 提供持久、可靠的消息传递——消息存储在多个 AZ 中
- 解耦使生产者和消费者服务的独立扩展和部署成为可能
- 死信队列确保没有消息在失败时无声地丢失
- SNS 扇出模式允许在不改变生产者的情况下添加新消费者

**事情变得复杂的地方**：

- 至少一次传递意味着消费者必须是*幂等的*——两次处理同一消息不应该造成问题（重复订单、重复费用）
- FIFO 队列更贵，有吞吐量限制
- 跨多个队列和服务调试失败的消息需要良好的日志和可观测性
- 消息排序保证是有限的——如果跨多个服务的严格排序很重要，设计会变得复杂

## 摘要

- **解耦**将产生工作的组件与处理工作的组件分开。
- **SQS** 是托管队列。生产者发送消息；消费者异步读取和处理它们。
- **SQS 标准**：高吞吐量，尽力而为的排序，至少一次传递。
- **SQS FIFO**：严格排序，恰好一次传递，较低的吞吐量。
- **SNS** 是 pub/sub 服务。一条消息，多个订阅者同时接收。
- **SNS + SQS 扇出**：一个事件触发多个独立处理管道的标准模式。
- **死信队列**：捕获失败处理太多次后的消息。
- **幂等性**：设计消费者以安全地处理重复消息。

## 考试技巧

*SAA-C03 领域：设计弹性架构（领域2，任务2.1）*

- **SQS 标准 vs FIFO**：考试按排序和传递保证区分。"必须按顺序处理" → FIFO。"最大吞吐量" → 标准。
- **可见性超时**：至少一次传递的关键概念。如果消费者失败，消息在超时后再次可见。考试场景："消息被处理了两次" → 可见性超时太短（消费者处理时间超过超时）。
- **死信队列**：N 次重试失败后的消息被移到这里。考试场景："确保没有消息丢失，即使处理反复失败" → DLQ。
- **SNS 扇出**：一个事件触发多个消费者的经典考试模式。"下单通知必须同时触发邮件、短信和库存更新" → 带 SQS 订阅的 SNS 主题。
- **SQS + Lambda**：Lambda 可以配置为轮询 SQS 队列，并在每批消息上触发。考试将这用于大规模的事件驱动处理。
- **SQS 长轮询**：消费者不是每隔几秒轮询（短轮询，浪费 API 调用），而是长轮询等待最多20秒消息。降低成本和假空响应。

**练习 2——考试练习**

*场景*：一个电商平台每小时处理10,000个订单。当下订单时，系统必须：（1）将订单存储到数据库，（2）扣除库存，（3）发送确认邮件，（4）更新分析仪表板。目前，所有四个步骤同步发生——如果分析服务很慢，顾客要等。团队希望改善面向顾客的响应时间，同时确保没有订单丢失。

哪种架构*最能*解决这个需求？

A) 使用 SQS FIFO 队列顺序处理所有四个步骤  
B) 让 API 保存订单，立即确认给顾客；向 SNS 主题发布事件；让库存、邮件和分析服务通过 SQS 队列订阅  
C) 使用并行的 EC2 实例同步处理每个步骤  
D) 使用带请求验证的 API Gateway 加速订单处理

**提示 1**：顾客确认应该是即时的。哪些步骤必须在响应之前发生，哪些可以在之后发生？

**提示 2**：分析服务很慢不应该影响邮件或库存服务。

**提示 3**：SNS 扇出允许所有三个下游服务同时接收事件。

**答案**：B

**解析**：API 将订单保存到数据库（同步——必须在确认之前完成），并立即返回确认。然后它向 SNS 主题发布 `order-placed` 事件。库存、邮件和分析服务各自通过独立的 SQS 队列订阅。它们以自己的节奏处理——如果分析很慢，它的队列增长，但其他服务不受影响。如果任何服务失败，其消息保留在 SQS 队列中并被重试；在配置的失败重试次数后，它们被移到 DLQ。

**为什么不是 A？** FIFO 队列顺序处理消息——这不能解决同步慢速问题。而且顺序处理意味着分析很慢仍然会阻塞邮件。

**为什么不是 C？** "并行 EC2 实例同步处理"仍然需要所有步骤完成才能响应顾客。添加实例不能解决同步耦合。

**为什么不是 D？** API Gateway 加速 API 路由和验证，但不解耦下游处理步骤。
