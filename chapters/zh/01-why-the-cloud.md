# 第1章：有得买，为何要租？

笔记本摊在桌上，Tom 已经把同一行字划掉了三次。

他熬到很晚。那个问题不肯放过他。午夜前后，他把问题完整地写了下来，然后画了下划线，又画了个方框框住它，最后划掉了，因为写下来并没有让它变得更清楚。他在页边空白处又写了一遍。

当 Leo 和 Priya 第二天早上到来——手里端着咖啡，争论着某件无关的事情——Tom 已经站在白板前了。第三个选项还在那里，没有人动过。一朵云的形状，由一个承认自己不知道它是什么意思的人画的。

餐厅的订餐问题让某种真实的东西清晰起来。Maya 已经宣布云是前进的方向。那个决定已经定了。剩下的是 Tom 摆脱不掉的那个问题，就躺在他笔记本的页边上：如果租是答案，那它为什么会比买更便宜？

"我需要有人给我解释一件事，" Tom 说，没有转身。"如果我们从亚马逊租用计算机而不是购买自己的——为什么那会*更便宜*？"

房间里安静下来。这是一个听起来简单却并不简单的问题。

"因为，" Leo 开口道。

"不，" Tom 说。"我想要理解它。不只是听到答案。为什么租比买便宜？"

Leo 坐了下来。他把咖啡放在桌上。他真的认真思考了一下。

"因为，" 他又开口了，这次更加谨慎，"我们买服务器是为了最坏的情况买的。最繁忙的周五晚上、病毒式爆红的时刻、产品发布活动。但大多数时候，没有那么忙。"

"对，" Tom 说。"继续。"

"所以我们会为没有使用的容量付费。每一个安静的周二。每一个周一早上。我们会有一台服务器摆在那里，消耗着电力，几乎什么都不做。"

"那如果我们改成租呢？"

"我们为使用的部分付费，" Leo 说。"清闲的时候，我们几乎不付钱。繁忙的时候，我们多付一些。但我们永远不会为只是闲置在那里的容量付钱。"

Tom 看起来很满意。不是因为这个答案对他来说是新的——他前一天晚上就已经想明白了。而是因为把它大声说出来让它变得真实。他拿起笔记本，最后一次划掉了那个问题。

这就是基础。本章其余的一切都建立在它之上。

**拥有服务器的显而易见的问题**

想象一下你决定开一家餐厅。不是 Nimbus 那种——一家普通的餐厅。

在第一位顾客走进来之前，你需要桌子。椅子。厨房。炉子。盘子。员工。你在第一天就需要这一切，即使你的第一周很冷清，即使你花了三个月时间每天只有六位顾客，还没等到口口相传。

物理服务器也是如此。

如果 Nimbus 购买自己的服务器，他们必须按预期的峰值来买。他们能想象到的最繁忙的周五晚上。一个美食博主发帖介绍玉米饼、一万人同时尝试下单的那种病毒式时刻。

但大多数时候，没有那么忙。大多数时候，那些服务器就在那里，消耗着电力，几乎什么都不做。

"我们要为没有使用的容量付费，" Maya 说。

"完全正确，" Tom 说，这让所有人都感到惊讶，因为他才是那个问问题的人。

**硬件的真实成本：Tom 的电子表格**

等到团队开会时，Tom 已经搭好了一个像样的成本模型。他带大家过了一遍。

他确实查过真实硬件的价格。一台 Dell PowerEdge R550——一台能承载数百名并发用户的中端服务器——配置好足以运行生产级 Web 应用所需的内存和存储后，价格约为 8,000 美元。这只是一台服务器。为了冗余（让单台故障不至于击垮整个系统），你至少需要两台。还没开始运营，就要先花一万六千美元。

白板上 2,000 美元的估算是乐观的。生产级硬件更贵。你需要足够的内存让应用程序和数据库同时运行。你需要 RAID 来实现存储冗余。你需要一块快到能承受真实流量的网卡。等你把一台真正的生产服务器配置完，8,000 美元这个数字一点也不夸张。

"两台服务器：16,000 美元，" Tom 说着写了下来。

然后是持续性成本。电力：一台 24/7 运行、功耗 400 瓦的服务器每年大约消耗 3,500 千瓦时。按每千瓦时 0.12 美元计算，每台服务器每年大约 420 美元。乘以二：仅电费一项每年就是 840 美元。

然后是互联网。一条快到能承受真实流量的商用线路——不是餐厅目前用的家用 Wi-Fi，而是带服务等级协议的商用级对称光纤——每月要 200 到 400 美元。也就是每年 2,400 到 4,800 美元。

然后是硬件生命周期。服务器能用三到五年，之后就会变得太慢或太不可靠，无法承载生产工作负载。到了第四年之后，你跑的硬件已经无法针对某些漏洞打补丁，服务器厂商也不再提供支持。所以你要把前期成本摊销：16,000 美元摊到四年，就是每年 4,000 美元的资本折旧。

然后是没人写下来的那些成本：一台 UPS（不间断电源）电池备份，用于熬过短暂停电，大约 400 美元。一台可管理网络交换机，300 美元。一台具备完善安全功能的防火墙设备，500 到 2,000 美元。架子上备着的硬盘，应对不可避免的故障，200 美元。散热——如果服务器放在餐厅的后台办公室里，就得有人考虑它们产生的热量，这意味着要么装一条专用空调线路，要么收到一张意外的电费账单。

全部加起来：每年大约 8,000 到 12,000 美元的资本折旧和持续性成本，这还不包括请人维护、配置或修理硬件的费用。而"维护"不只是账单上的一个条目——它是一项专业能力要求。你要么雇一个懂得运维服务器的人，要么你自己就是那个凌晨 2 点出了问题要爬起来处理的人。

"而且当它坏掉的时候，" Tom 说，"我们不知道怎么修。我们得按紧急费率付钱请人。在我们等人来的时候，餐厅的系统是黑着的。"

"对比一下 AWS，" Tom 说。他调出了 EC2 的定价页面。一个 `t3.medium` 实例——对 Nimbus 起步阶段的工作负载来说算力足够——每月约 30 美元。两台用于冗余，每月 60 美元，即每年 720 美元。

每年 4,000 美元的折旧，对比 720 美元。差距悬殊。即便在 AWS 上加上网络、数据传输和一项托管数据库服务，初创规模工作负载的云账单也只是物理硬件成本的一小部分。

"但是，" Tom 说——因为 Tom 总有一个但是——"我们也应该诚实地说说，什么时候事情就不再这么一目了然了。"

他说得对。在巨大的规模下——数千台服务器、持续的高利用率——经济账会发生变化。一家全天候以 90% 利用率运行 5,000 台服务器的公司，可能会发现在那样的体量下，自有硬件的单位成本比租用更低。大公司有时会达到这个临界点。初创公司几乎从来不会。对于一家增长不可预测、没有硬件专长、规模充满不确定性的初创公司来说，上云的账是显而易见的。

**租赁模式**

这就是云计算与众不同的地方。

当你使用 AWS，你不买服务器。你租用计算能力，而且只为你使用的部分付费。这更像是租用场地，而不是拥有一栋餐厅建筑。

这样想想看。

如果你需要为五十个人举办一场生日派对，你可以买一栋足够容纳五十个人、他们的桌子和椅子的房子。或者你可以在周六租用一个场地四个小时，只为你需要的空间和时间付费，派对结束后把钥匙还回去。

那个场地在你需要的时候还在那里。当有其他事情时它又可以使用了。你不必雇用一个建筑管理员。你不必为它缴一整年的房产税。

但这里有一个类比没能完全捕捉到的部分：在 AWS 上，"场地"可以随你的派对扩大或缩小。如果来了五十个人，然后又有两百人意外到场，场地会自动扩展来容纳他们。如果派对提前结束，场地会收缩，你立刻不再为多余的空间付钱。

没有哪个场地租赁是这样运作的。云计算就是。

这就是云模式。AWS 有"场地"。你需要的时候就去。

还有第二个类比，它触及了这幅图景的另一个侧面。

想象你是一家需要专业摄影的初创公司。你可以雇一名全职摄影师——工资、设备、福利、办公位，整套配置。或者你可以在需要时按小时雇摄影师，为完成的工作付费，拍摄结束后让他们离开。

按需雇用的摄影师每小时的费用比全职的高。但除非你每天每小时都需要摄影，否则按需模式的总成本会大幅降低。而且你还能为不同的工作雇不同的专家——拍证件照请人像摄影师，拍商品图请产品摄影师——而无需同时维持两个人的编制。

云计算具有同样的专业化经济学。AWS 为基础设施的每一层都维持着专家团队：网络工程师、数据库管理员、安全研究员、硬件采购专家。你按小时获取他们专业能力的产出——一个可靠的数据库、一个安全的网络、一台配置妥当的服务器——而无需自己雇用其中任何一位专家。

你也许会好奇：如果按小时租比按台买单价更高，这笔经济账是怎么算得过来的？答案是利用率。你自己拥有的物理服务器在清闲的周二只有 9% 的 CPU 使用率。而你按实际需要的小时数租用的云服务器，运行在工作负载所要求的任何利用率上，工作负载停了，你就停止付费。你为实际使用的小时数支付的总额，少于让一台服务器在角落里闲置所要支付的总额。

**但等等——还有更多**

"好，" Leo 说，"但如果我的场地烧掉了呢？"

很好的直觉。阴暗，但很好。

当你拥有自己的服务器时，一个隐含的假设是*你*要负责保持它们运行。如果你办公室里的服务器被一个笨手笨脚的实习生撞倒，你的网站就宕机了。如果大楼停电，你的网站就宕机了。如果硬盘坏了——硬盘最终总会坏的——你的网站就宕机了。

AWS 运营数据中心。巨大的、专业管理的设施，配有备用电源、冗余网络连接、物理安全，以及唯一工作就是让这些机器保持运行的工程师团队。他们有冗余的电源供应。他们有备用发电机。他们有来自多家供应商的冗余网络连接。他们的物理安保水平是大多数办公楼望尘莫及的。

你不仅仅是在租用计算能力。你在租用可靠性。

"那要多少钱？" Tom 问。

我们会谈到这个。定价自成一章，而且它配得上单独一章。

**云的三点不同之处**

让我们具体说明。以下是运行自己的服务器与使用云提供商的三个核心区别。

**1. 你为使用的部分付费。**

没有服务器闲置。没有预先购买。如果 Nimbus 在周一早上没有任何订单，他们几乎不需要付费。如果他们在新年前夜被订单淹没，AWS 会自动准备好容量。

这种模式以固定基础设施无法做到的方式让成本与价值相匹配。当你的成本跟随你的营收变动时，财务规划就变得简单了。

在会计上有一个术语描述这件事：从资本支出转向运营支出。CapEx 是一次性的前期购买，随时间折旧——比如买那台 Dell PowerEdge。OpEx 是按使用持续支付的开销——比如 AWS 账单。对于资本有限、收入不确定的初创公司来说，OpEx 明显更可取。你不会把 16,000 美元押在一个你无法确定的需求预测上。

"我们每一块没花在硬件上的钱，" Tom 说，"都是可以花在真正构建产品上的钱。"

这不是一个微不足道的论点。Tom 算出来的前期硬件成本——两台生产级服务器 16,000 美元——正是那种会让投资人提出尴尬问题、迫使创始人对资金跑道做艰难抉择的资本支出。

**2. 别人处理硬件。**

AWS 维护物理机器。网络线缆。电源供应。冷却系统。Nimbus 不需要雇人做这些。他们专注于自己的应用程序，而不是它底下的基础设施。

这一点值得停下来想一想。运行物理数据中心基础设施所需的专业知识是实打实的。冷却系统、电源管理、硬件更换计划、网络冗余——这些都是各自独立的专业领域。通过使用 AWS，Nimbus 无需为此招人就能获得这些专业能力。

一名具备妥善维护生产服务器技能的系统管理员，年薪在 8 万到 13 万美元之间。一支能处理硬件故障、操作系统级安全、网络配置和存储管理的团队成本更高。AWS 的服务费用只是其中的一小部分——而且运维专业能力已经包含在服务里了。

这就是 AWS 明确提出的规模经济论证。因为 AWS 同时为成千上万的客户运行基础设施，维持这种专业能力的单位成本被分摊到了所有客户身上。每个客户都能以一笔小得多的账单，获得世界级的基础设施运维——如果他们自己从零搭建，成本会高出许多倍。

**3. 你可以即时扩展——也可以即时缩减。**

这一点需要一段时间才能完全体会。使用物理服务器，扩展意味着订购新硬件，等待数周交货，然后进行安装。使用 AWS，扩展意味着点击一个按钮（或者让系统自动执行）。当你不再需要额外容量时，你缩减规模。你停止付费。

"也可以缩减"这部分被低估了。在物理硬件上缩减规模，意味着你仍然拥有那些硬件，仍然付电费，仍然维护系统。你只是拥有了超过所需的东西。在云上，缩减是真实的——资源消失了，成本也随之消失。

Leo 把这形容为"感觉像作弊的部分"。他花了多年时间与固定容量的系统周旋——仔细估算需要多大的服务器，保守地做配置，盯着容量表，而且有时往两个方向都估错。一想到他可以加一台服务器，在周五晚上用它四个小时，然后把它移除——只为那四个小时付费——这感觉不对劲，就像那些好得不像真的的事情给人的感觉一样。

它不是好得不像真的。它就是商业模式本身。AWS 在你使用他们的基础设施时赚钱。他们有充分的动力让这种使用尽可能没有摩擦。

Priya 在这段解释过程中一直保持安静。她有一个问题。

"那如果有人试图入侵呢？那是谁的问题？"

这就是有趣的地方了。

**共同责任模型**

这是整个 AWS 中最重要的概念之一。一旦理解了它就很简单，但它让很多人绊倒——包括在考试中。

AWS 和你共同承担安全责任。但每一方对不同的事情负责。

**AWS 负责云*本身*的安全。**

物理数据中心。硬件。网络基础设施。运行虚拟机的虚拟机管理程序（hypervisor）。如果有人闯入 AWS 数据中心，那是亚马逊的问题。如果一块物理磁盘故障导致数据损坏，那是亚马逊的问题。如果可用区之间的网络基础设施被攻破，那是亚马逊的问题。

**你负责云*内部*的安全。**

你的数据。你的应用程序。你的用户账户以及谁有权访问什么。你选择的配置。如果有人盗取你的密码并登录你的 AWS 账户，那是你的问题。如果你把一个数据库错误配置成可公开访问，那是你的问题。如果你的应用程序存在允许 SQL 注入的漏洞，那是你的问题。

Priya 慢慢点了点头。"所以他们保护建筑。我们保护里面的东西。"

"完全正确，" Maya 说。

"所以如果 Leo 打开了一个不该打开的端口……"

"还是我们的问题，" Maya 确认道，看向 Leo。

Leo 已经在他的笔记本上打着什么，假装没有听到。

你也许会好奇：这是否意味着 AWS 永远不用为数据泄露负责？只有当泄露发生在物理层或基础设施层时——数据中心被攻破、硬件故障、虚拟机管理程序本身的漏洞——AWS 才负责。由配置错误的应用程序、弱密码或设置不当的访问控制导致的泄露，永远是客户的责任，无论云提供商有多大、声誉多好。

**机场类比**

这里是理解共同责任模型的第二种方式，因为它在考试中出现得足够频繁，值得从两个角度来讲。

想象一座机场。

机场运营方负责场地的安全——跑道、航站楼、围栏、安检通道，以及当有人未经授权出现在燃油库附近时的处置。

但一旦进入机场内部，每家航空公司都要为自己的运营负责：自己的飞机维护、自己的机组流程、自己的乘客名单。如果一家航空公司弄丢了乘客的行李，或者一名飞行员跳过了检查清单，那不是机场的错。场地是安全的。是在场地内运营的航空公司做出了糟糕的选择。

AWS 是机场。你是在其中运营的航空公司。AWS 保障物理结构和核心基础设施的安全。你保障你的数据、你的访问控制和你的应用决策的安全。

这个类比之所以重要，是因为它厘清了出问题时责任线在哪里。"我们在 AWS 上，所以那是他们的问题"在考试中永远是错误答案，在现实世界中也几乎总是错误答案。

**服务类型很重要**

现在还有一个值得了解的细节，尽管我们会在全书中反复回到它。

责任的划分会随着服务的托管程度而移动。

对于 EC2——你控制的虚拟机——你负责给操作系统打补丁。AWS 提供物理机器和虚拟机管理程序。操作系统以上的一切都是你的。

对于 RDS——我们将在第 8 章讲到的托管数据库服务——AWS 负责给数据库引擎本身打补丁。你不管理操作系统。你的责任缩小到数据库的配置、其中的数据，以及谁有权访问。

对于 S3——文件存储服务——AWS 完全管理基础设施。你的责任是访问控制（谁可以读写你的存储桶）和数据本身。

服务越托管，越多的责任就转移给 AWS。这是一个关键的考试规律：当题目问某件事由谁负责时，先问"这个服务的托管程度有多高？"

**选择云，就选择了便利，但放弃了控制**

云模式提供了真实的优势：无需管理硬件、成本有弹性、即时扩展。但这也意味着要交换掉某些东西。

如果你把基础设施迁移到云上，那么你获得了灵活性，降低了前期资本成本——但你放弃了对底层机器的完全控制。你无法亲手检查它们。你无法保证它们位于数据中心的哪个位置。你依赖 AWS 的正常运行时间、AWS 的维护窗口，以及当基础设施层面出问题时 AWS 的事故响应。对大多数团队来说，这是一笔极好的交易。对某些受监管的行业来说，这需要细致的文档记录和 AWS 的合规认证。在交换之前，先弄清你在交换什么。

## 优势与局限性

没有工具是完美的。让我们对两面都坦诚。

**为什么云很棒**：

- 无前期硬件成本
- 只为使用的部分付费
- 在两个方向上即时扩展
- 专业的可靠性和物理安全
- 访问数百种托管服务（数据库、队列、机器学习等），无需自己构建或维护
- 全球覆盖：部署到一个新的地理区域只是一次配置变更，而不是一个硬件采购流程

**事情变得复杂的地方**：

- 如果你不注意，成本可能难以预测（Tom 未来的噩梦）
- 你依赖第三方提供基础设施——如果 AWS 在你所在的区域出现故障，你的服务也会受到影响
- 有一个学习曲线。AWS 有数百个服务。知道使用哪个需要经验，或者像这本书一样的参考资料。
- 数据离开云可能很昂贵。从 AWS 移出大量数据需要花钱。（我们将在第30章重新讨论这个问题。）
- 对于更高层级的服务，供应商锁定是真实存在的。使用托管的 AWS 数据库起步容易，离开却更难。你使用的 AWS 专有服务越多，你对 AWS 生态系统及其定价的绑定就越深。

"所以我们在用控制换取便利，" Tom 说。

"还在用前期成本换取持续成本，" Maya 补充道。

"还在把别人的问题换成我们自己的问题，在安全方面，" Priya 说。

"但我们也在用 Leo 那台坏掉的服务器换成亚马逊那台非常不坏的服务器，" Leo 说，显然他一直在听。

他也没说错。

Tom 还有一个顾虑。

"如果我们把一切都建在 AWS 上，而 AWS 三年后涨价，我们可没法把数据库搬回餐厅的后屋。"

"没错，" Maya 说。"但亚马逊的价格走势总体上是向下的——自 2006 年以来，他们已经降价超过 100 次。锁定的风险是真实的，但历史上发生突然涨价的实际风险很低。"

"总体上，" Tom 说。他把这记了下来。他会在未来某个周六的早晨，带着一支红笔和一杯咖啡，重新审视这笔账——就像他重新审视他所有的账一样。

**什么时候本地部署才是正确的选择**

在 Nimbus 的比较中，云明显获胜。但智识上的诚实要求我们说清楚它什么时候不会赢。

**拥有稳定、可预测工作负载的大公司**有时会发现，一旦利用率持续居高，自有硬件在成本上就能与租用相抗衡。如果你全天候以 80% 的利用率运行数千台服务器，所有权的经济账与流量多变的初创公司截然不同。云的按使用付费模式在利用率波动时优势最大。当利用率稳定且高企时，所有权的单位经济性可以与之竞争。这就是为什么一些大型企业采用混合架构：波动的工作负载放云上，稳定的工作负载放本地。

**有严格数据本地化要求的受监管数据环境**可能别无选择，只能本地部署。政府的涉密计算环境——处理涉密国家安全信息的系统——不能使用商业云提供商。数据不能离开受物理管控的设施。某些司法管辖区的金融系统也有类似要求。处理特定类别数据的医疗机构，可能面临商业云认证无法完全满足的要求。在这些情形下，本地部署不是一种偏好；它是一项强制规定。

**对极低延迟、物理邻近性的要求**构成了第三类。一些金融交易系统需要应用程序与交易所撮合引擎之间亚毫秒级的延迟。与交易所同处一个物理数据中心的托管——通过直连光纤——能达到任何云区域都无法企及的延迟。一些科学仪器——粒子加速器、地震监测网络、射电望远镜——产生的数据必须先在本地处理，传输才具有可行性。这些是真实存在的、需要与硬件物理邻近的用例。

**已有的长期合同**是最平淡无奇、却往往最切身相关的约束。一家在 2022 年签了五年期数据中心租约的公司负有合同义务。在租约到期前迁移上云有真实的代价——剩余的租金——这会显著改变这笔经济账。架构决策不是在真空中发生的。它们发生在拥有既有合同、既有硬件折旧计划和既有员工技能的组织里。

"这些情况有哪个适用于我们吗？" Maya 问。

"没有，" Tom 说。"我们没有硬件。没有合同。没有监管强制要求。而且团队没有任何服务器管理经验。"

"那就是云了。"

"那就是云了。但知道它什么时候不是答案，也是知道自己在做什么的一部分。"

这些本地部署的例外情况没有一条适用于 Nimbus。但它们是真实的，一名优秀的云架构师知道何时该说"在这里，云不是正确答案"。目标不是做云的鼓吹者。目标是做对。

## 摘要

Tom 摆脱不掉的那个问题——为什么租比买便宜？——最后证明既有一个简单的答案，也有一个复杂的答案。简单的答案是利用率：你不再为清闲的周二里闲置的容量付费。复杂的答案则涉及共同责任模型、CapEx 与 OpEx 之间的权衡，以及几种云确实是错误选择的诚实情形。Tom 提出这个问题是对的。这个答案改变了团队对之后一切事情的思考方式。

- 核心优势是按使用付费的扩展：你只为使用的部分付费，可以根据需要扩展或缩减。
- Tom 的成本比较清楚地展示了硬件经济账：两个 EC2 实例每年 720 美元，对比同等物理硬件每年 8,000–12,000 美元，这还不算维护费用。
- AWS 处理物理基础设施。你处理你的应用程序、你的数据和你的配置。这种分工被称为**共同责任模型**。
- 共同责任模型会随服务类型而移动——服务越托管，AWS 承担的责任越多。
- 云并不总是更便宜或更简单——但它消除了起步的障碍，并以物理服务器无法比拟的方式使扩展成为可能。

## 考试技巧

*SAA-C03 考试领域：跨领域——云概念基础*

- **共同责任模型**在考试中经常出现。记住：AWS 负责云*本身*的安全（硬件、数据中心、全球网络）。你负责云*内部*的安全（数据、身份、应用程序配置）。
- **关键细节**：分工会根据服务类型而变化。对于 EC2（你控制的虚拟机），*你*来给操作系统打补丁。对于 RDS（托管数据库），AWS 给数据库引擎打补丁。服务越"托管"，就有越多责任转移给 AWS。考试场景会描述一个事件，并问谁应该负责——始终先问"这个服务的托管程度有多高？"
- 关于云*优势*的问题通常测试 CapEx 与 OpEx 的区别。本地硬件是资本支出（CapEx——一次购买，随时间折旧）。云是运营支出（OpEx——每月付费）。AWS 将成本从 CapEx 转移到 OpEx。
- "弹性"——自动向上*和*向下扩展的能力——是核心云优势。你可能会在考试中看到它与"可扩展性"配对。弹性意味着自动、由需求驱动的双向扩展。可扩展性意味着系统*可以*增长，但不一定自动缩减。
- 考试可能描述一家公司正在从"购买服务器"转向"云"的场景。正确的表述框架是：从 CapEx 转向 OpEx、消除前期成本、获得弹性，并将基础设施责任转移给云提供商。

**练习 2——SAA-C03 情景题**

*场景*：一家公司正在将其 Web 应用程序从本地数据中心迁移到 AWS。安全团队担心维护其数据保护政策的合规性。一名新工程师问："既然我们在 AWS 上了，亚马逊是否处理我们所有的安全要求？"

以下哪项*最能*描述安全责任的划分？

A) 应用程序一旦托管在云中，AWS 就完全负责所有安全  
B) 客户完全负责所有安全，包括物理数据中心安全  
C) AWS 管理底层基础设施的安全；客户管理其数据、应用程序和配置的安全  
D) 安全责任按账户协商，取决于客户的服务层级

**提示 1**：想想 AWS 物理控制的内容与你控制的内容。

**提示 2**：AWS 拥有数据中心。是你选择放什么进去，以及如何配置你的应用程序。

**提示 3**：我们在本章中为这种责任划分引入了一个特定名称。

**答案**：C

**解析**：AWS 共同责任模型将安全分为两个领域。AWS 保护物理基础设施——数据中心、硬件和网络。客户保护他们在其上部署的一切：他们的数据、他们的访问控制、他们的应用程序配置和网络设置。

**为什么不是 A？** AWS 从不对客户应用程序安全承担全部责任。一旦你配置了什么，那个配置就是你要管理的。

**为什么不是 B？** 客户不负责物理数据中心安全——这正是使用 AWS 的优势之一。

**为什么不是 D？** 共同责任模型是一个固定框架，不是协商安排。
