# 第1章：有得买，为何要租？

Tom 从前一天晚上开始就一直揣着那个问题。他把它写在笔记本上，又划掉，再写了一遍。

当 Leo 和 Priya 第二天早上到来——手里端着咖啡，争论着某件无关紧要的事情——Tom 已经站在白板前了。第三个选项还在那里，没有人动过。一朵云的形状，由一个承认自己不知道它是什么意思的人画的。

"我需要有人给我解释一件事，" Tom 说，没有转身。"如果我们从亚马逊租用计算机而不是购买自己的——为什么那会*更便宜*？"

房间里安静下来。这是一个听起来简单却并不简单的问题。

"因为，" Leo 开口道。

"不，" Tom 说。"我想要理解它。不只是听到答案。为什么租比买便宜？"

**拥有服务器的显而易见的问题**

想象一下你决定开一家餐厅。不是 Nimbus 那种——一家普通的餐厅。

在第一位顾客走进来之前，你需要桌子、椅子、厨房、炉子、盘子和员工。你在第一天就需要这一切，即使你的第一周很冷清，即使你花了三个月时间每天只有六位顾客，还没等到口口相传。

物理服务器也是如此。

如果 Nimbus 购买自己的服务器，他们必须为预期的峰值购买。他们能想象到的最繁忙的周五晚上。一个美食博主发帖介绍玉米饼，一万人同时尝试下单的那种病毒式时刻。

但大多数时候，没有那么忙。大多数时候，那些服务器就在那里，消耗着电力，几乎什么都不做。

"我们要为没有使用的容量付费，" Maya 说。

"完全正确，" Tom 说，这让所有人都感到惊讶，因为他才是那个问问题的人。

**租赁模式**

这就是云计算与众不同的地方。

当你使用 AWS，你不买服务器。你租用计算能力，你只为你使用的部分付费。这更像是租用场地而不是拥有一栋餐厅建筑。

这样想想看。

如果你需要为五十个人举办一场生日派对，你可以购买一栋足够容纳五十个人、他们的桌子和椅子的房子。或者你可以在周六租用一个场地四个小时，只为你需要的空间和时间付费，派对结束后把钥匙还回去。

那个场地在你需要的时候还在那里。当有其他事情时它又可以使用了。你不必雇用一个建筑管理员。你不必为它缴一整年的房产税。

这就是云模式。AWS 有"场地"。你需要的时候就去。

**但等等——还有更多**

"好，" Leo 说，"但如果我的场地烧掉了呢？"

很好的直觉。阴暗，但很好。

当你拥有自己的服务器时，一个隐含的假设是*你*要负责保持它们运行。如果你办公室里的服务器被一个笨手笨脚的实习生撞倒，你的网站就宕机了。如果大楼停电，你的网站就宕机了。如果硬盘坏了——硬盘最终总会坏的——你的网站就宕机了。

AWS 运营数据中心。巨大的、专业管理的设施，配有备用电源、冗余网络连接、物理安全，以及唯一工作就是让这些机器保持运行的工程师团队。

你不仅仅是在租用计算能力。你在租用可靠性。

"那要多少钱？" Tom 问。

我们会谈到这个。许多章节之后，当 Tom 的眼睛不会因此变得呆滞的时候。

**云的三点不同之处**

让我们具体说明。以下是运行自己的服务器与使用云提供商的三个核心区别。

**1. 你为使用的部分付费。**

没有服务器闲置。没有预先购买。如果 Nimbus 在周一早上没有任何订单，他们几乎不需要付费。如果他们在新年前夜被订单淹没，AWS 会自动准备好容量。

**2. 别人处理硬件。**

AWS 维护物理机器、网络线缆、电源供应和冷却系统。Nimbus 不需要雇人做这些。他们专注于自己的应用程序，而不是底层基础设施。

**3. 你可以随时扩展——也可以随时缩减。**

这一点需要一段时间才能完全体会。使用物理服务器，扩展意味着订购新硬件，等待数周交货，然后进行安装。使用 AWS，扩展意味着点击一个按钮（或者让系统自动执行）。当你不再需要额外容量时，你缩减规模。你停止付费。

Priya 在这段解释过程中一直保持安静。她有一个问题。

"安全性呢？谁负责保护数据安全？"

这就是有趣的地方了。

**共同责任模型**

这是整个 AWS 中最重要的概念之一。一旦理解了它就很简单，但它让很多人绊倒——包括在考试中。

AWS 和你共同承担安全责任。但每一方对不同的事情负责。

**AWS 负责云*本身*的安全。**

物理数据中心、硬件、网络基础设施、运行虚拟机的管理程序。如果有人闯入 AWS 数据中心，那是亚马逊的问题。

**你负责云*内部*的安全。**

你的数据、你的应用程序、你的用户账户以及谁有权访问什么。你选择的配置。如果有人盗取你的密码并登录你的 AWS 账户，那是你的问题。

Priya 慢慢点了点头。"所以他们保护建筑。我们保护里面的东西。"

"完全正确，" Maya 说。

"所以如果 Leo 打开了一个不该打开的端口……"

"还是我们的问题，" Maya 确认道，看向 Leo。

Leo 已经在他的笔记本上打着什么，假装没有听到。

## 优势与局限性

没有工具是完美的。让我们对两面都坦诚。

**为什么云很棒**：

- 无前期硬件成本
- 只为使用的部分付费
- 在两个方向上即时扩展
- 专业的可靠性和物理安全
- 访问数百种托管服务（数据库、队列、机器学习等），无需自己构建或维护

**事情变得复杂的地方**：

- 如果你不注意，成本可能难以预测（Tom 未来的噩梦）
- 你依赖第三方提供基础设施——如果 AWS 在你的地区出现故障，你的服务也会受到影响
- 有一个学习曲线。AWS 有数百个服务。知道使用哪个需要经验，或者像这本书一样的参考资料
- 数据离开云可能很昂贵。从 AWS 移出大量数据需要花钱。（我们将在第30章重新讨论这个问题。）

"所以我们在用便利换取控制，" Tom 说。

"还在用前期成本换取持续成本，" Maya 补充道。

"还在把别人的问题换成我们自己的问题，在安全方面，" Priya 说。

"但我们也在用 Leo 破损的服务器换成亚马逊非常稳定的服务器，" Leo 说，显然一直在听。

他也没说错。

## 摘要

- 云是你租而不是买的计算能力。
- AWS 是世界上最大的云提供商。
- 核心优势是按使用付费的扩展：你只为使用的部分付费，可以根据需要扩展或缩减。
- AWS 处理物理基础设施。你处理你的应用程序、你的数据和你的配置。这种分工被称为**共同责任模型**。
- 云并不总是更便宜或更简单——但它消除了起步的障碍，并以物理服务器无法比拟的方式使扩展成为可能。

## 考试技巧

*SAA-C03 考试领域：跨领域——云概念基础*

- **共同责任模型**在考试中经常出现。记住：AWS 负责云*本身*的安全（硬件、数据中心、全球网络）。你负责云*内部*的安全（数据、身份、应用程序配置）。
- **关键细节**：分工会根据服务类型而变化。对于 EC2（你控制的虚拟机），*你*来给操作系统打补丁。对于 RDS（托管数据库），AWS 给数据库引擎打补丁。服务越"托管"，就有越多责任转移给 AWS。考试场景会描述一个事件，并问谁应该负责——始终问"这个服务有多托管？"
- 关于云*优势*的问题通常测试 CapEx 与 OpEx 的区别。本地硬件是资本支出（CapEx——一次购买，随时间折旧）。云是运营支出（OpEx——每月付费）。AWS 将成本从 CapEx 转移到 OpEx。
- "弹性"——自动向上*和*向下扩展的能力——是核心云优势。你可能会在考试中看到它与"可扩展性"配对。弹性意味着自动、由需求驱动的双向扩展。可扩展性意味着系统*可以*增长，但不一定自动缩减。

## 练习

**练习 1——回忆**

用你自己的话：解释共同责任模型。谁负责什么，为什么这种区分很重要？

*（提示：想想 Priya 的类比——谁保护建筑，谁保护里面的东西。）*

**练习 2——考试练习**

*场景*：一家公司正在将其 Web 应用程序从本地数据中心迁移到 AWS。安全团队担心维护其数据保护政策的合规性。一名新工程师问："既然我们在 AWS 上了，亚马逊是否处理我们所有的安全要求？"

以下哪项*最能*描述安全责任的划分？

A) AWS 一旦应用程序托管在云中，就完全负责所有安全  
B) 客户完全负责所有安全，包括物理数据中心安全  
C) AWS 管理底层基础设施的安全；客户管理其数据、应用程序和配置的安全  
D) 安全责任按账户协商，取决于客户的服务层级

**提示 1**：想想 AWS 物理控制的内容与你控制的内容。

**提示 2**：AWS 拥有数据中心。你选择放什么进去，以及如何配置你的应用程序。

**提示 3**：我们在本章中为这种责任划分引入了一个特定名称。

**答案**：C

**解析**：AWS 共同责任模型将安全分为两个领域。AWS 保护物理基础设施——数据中心、硬件和网络。客户保护他们在其上部署的一切：他们的数据、他们的访问控制、他们的应用程序配置和网络设置。

**为什么不是 A？** AWS 从不对客户应用程序安全承担全部责任。一旦你配置了什么，那个配置就是你的责任。

**为什么不是 B？** 客户不负责物理数据中心安全——这正是使用 AWS 的优势之一。

**为什么不是 D？** 共同责任模型是一个固定框架，不是协商安排。
