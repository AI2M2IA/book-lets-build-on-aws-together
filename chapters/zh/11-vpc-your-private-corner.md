# 第11章：云端你的私人角落

Priya 手里拿着一张有画的纸。

这不是一张复杂的图。一个矩形，标着"AWS"。矩形内部，一堆方框：EC2 实例、RDS 数据库、ElastiCache 集群。所有东西都通过线连接到其他所有东西。矩形外面，一个单独的标签："互联网"。

她把它放在桌子中央。

"这是我们现在的状态，" 她说。"我们的数据库有一个公网 IP 地址。我们的缓存层可以从互联网访问。我们的 EC2 实例全部在同一个扁平网络上。"

"这看起来没问题，" Leo 说。"我们有安全组。"

"你配置的安全组，" Priya 说。"在深夜。在初始设置期间。"

Leo 什么也没说。

"我不是在批评配置，" 她说。"我是说，当所有东西都在扁平的公共网络上时，一次错误配置就是工作系统和可以被互联网上所有人访问的系统之间的差异。"

她拿起一支红色记号笔，在数据库周围画了一个圆圈。

"这不应该可以从互联网访问。一点都不。不通过安全组规则，不通过加固配置。它应该在结构上不可达。"

"我们需要谈谈网络架构，" Maya 说。

"三个月前我们就需要谈了，" Priya 说。"但现在也好。"

团队几周来第一次围着白板聚集。

**开放停车场的问题**

想象一个巨大的公共停车场。一万辆车。任何车都可以停在任何地方。区域之间没有隔离，没有闸门，没有预留区域。

这就是开放网络。每个服务都可以访问其他每个服务。你的 Web 服务器可以与你的数据库通信。你的数据库可以访问互联网。你的缓存层可以从任何地方接收连接。

当所有东西都可以与所有东西通信时，一次入侵就会影响所有东西。

"所以如果有人闯入停车场，" Tom 说，"他们可以进入任何一辆车。"

"然后从任何一辆车，驱车到任何地方，" Priya 确认道。"我们想要围栏。我们想要锁着的大门。我们想要区域。"

VPC 就是你在 AWS 中构建这些区域的方式。

**什么是 VPC？**

**虚拟私有云（VPC）**是 AWS 云中逻辑隔离的部分——一个你定义的私有网络，默认情况下只有你的资源可以访问。

把它想象成巨大公共停车场内一块围起来的私人场地。你的场地有自己的规则：谁可以进入，谁可以出去，各个区域之间有什么路线。

当你创建 VPC 时，你定义：

**一个 CIDR 块**：网络内可用的 IP 地址范围。例如，`10.0.0.0/16` 给你65536个可能的 IP 地址（10.0.0.0 到 10.0.255.255）。

**子网**：VPC 的细分，每个被分配你的 IP 地址范围的一部分，并与特定的可用区关联。

**路由表**：决定网络流量去哪里的规则。

**互联网网关**：你的 VPC 和公共互联网之间的连接。

**子网：公共 vs 私有**

并非所有资源都应该公开访问。

你的 Web 服务器需要接受来自互联网的流量——用户的浏览器需要访问它。

你的数据库*永远不应该*接受来自互联网的流量——只有你的 Web 服务器应该能与它通信。

这就是子网发挥作用的地方。

**公共子网**连接到互联网网关，可以有带公网 IP 地址的资源。流量可以双向流向互联网。

**私有子网**没有直接的互联网连接。私有子网中的资源只能与你 VPC 中的其他资源通信（除非你设置了特定的出站路由）。它们没有公网 IP 地址。

对于 Nimbus，设计变得清晰了：

```
互联网
    |
互联网网关
    |
公共子网（AZ-a）     公共子网（AZ-b）
  [负载均衡器]         [负载均衡器]
    |                      |
私有子网（AZ-a）     私有子网（AZ-b）
  [EC2 实例]           [EC2 实例]
    |                      |
私有子网（AZ-a）     私有子网（AZ-b）
  [RDS 主节点]         [RDS 备用节点]
  [ElastiCache]        [ElastiCache]
```

负载均衡器面向公众——它需要接收来自互联网的流量。EC2 实例是私有的——它们只接收来自负载均衡器的流量。数据库是私有的——它们只接收来自 EC2 实例的流量。

"所以要访问数据库，" Tom 说，"有人必须通过负载均衡器，然后通过 EC2 实例，然后通过数据库安全组？"

"三层，" Priya 确认道。"深度防御。"

**NAT 网关：仍然能下载东西的私有子网**

私有子网无法访问互联网。但有时它们需要。你的 EC2 实例需要下载软件更新。你的应用程序需要调用外部 API。

这就是 **NAT 网关**（网络地址转换）的作用。

NAT 网关位于公共子网中。私有子网中的资源可以将出站流量发送到 NAT 网关，NAT 网关将其中继到互联网——但互联网无法主动发起连接。

这就像一扇单向旋转门。你可以出去。外面的人无法进来。

"NAT 网关要多少钱？" Tom 问。

这个问题没有让任何人感到惊讶。

NAT 网关定价有两个组成部分：每个 NAT 网关的小时费用，加上每 GB 的数据处理费。这可能出乎意料地累积（第30章详细介绍）。现在：不要使用比你需要的更多的 NAT 网关，并且要意识到大量出站数据会出现在你的账单上。

**路由表：流量如何找到它的路**

每个子网都有一个**路由表**，告诉流量去哪里。

典型的公共子网路由表看起来像这样：

| 目的地 | 目标 |
|---|---|
| 10.0.0.0/16 | 本地 |
| 0.0.0.0/0 | igw-xxxx（互联网网关） |

第一条规则：到你 VPC 范围内任何 IP 的流量保持本地。第二条规则：所有其他流量（`0.0.0.0/0` 意味着"所有"）去到互联网网关。

私有子网路由表：

| 目的地 | 目标 |
|---|---|
| 10.0.0.0/16 | 本地 |
| 0.0.0.0/0 | nat-xxxx（NAT 网关） |

私有子网流量保持本地或通过 NAT 网关出去。没有直接到互联网网关的路由。

**安全组与 NACL（预览）**

在 VPC 内部，你有两个工具来在资源级别控制流量：

**安全组**（第15章深入介绍）作为单个资源——EC2 实例、RDS 实例、负载均衡器——的虚拟防火墙。它们是*有状态的*：如果流量被允许进入，响应流量会自动允许出去。

**网络 ACL（NACL）**在子网级别运行，是*无状态的*：你必须分别明确允许入站和出站流量。

对于大多数使用场景，安全组就足够了。当你需要子网级别的控制时，NACL 增加了一个额外层——例如，阻止特定 IP 范围访问整个子网。

"安全组在实例级别，" Leo 在白板上写道。"NACL 在子网级别。"

"并且永远不要让端口22对 0.0.0.0/0 开放，" Priya 补充道，看向 Leo。

"那是一次，" Leo 说。

"永远都是恰好一次，" Priya 说，"直到不是的时候。"

**VPC 对等：连接私有网络**

如果 Nimbus 成长为多个 VPC 会怎么样？（这会发生的。团队变大。服务被隔离到独立的账户中。）

**VPC 对等**让两个 VPC 私下通信，就像它们在同一个网络上一样。流量不会离开 AWS 的私有网络。

重要限制：

- VPC 对等不是传递性的。如果 VPC A 与 VPC B 对等，VPC B 与 VPC C 对等，A 和 C 无法通信——除非你添加直接的 A-C 对等。
- 对等的 VPC 之间的 CIDR 块不能重叠。

对于有很多 VPC 的更大架构，**AWS Transit Gateway**（第25章）处理传递性路由，而不需要完整的对等连接网格。

## 优势与局限性

**为什么 VPC 设计很重要**：

- 网络隔离是深度防御——突破一层不意味着入侵所有层
- 私有子网显著减少攻击面
- 路由表和安全组对流量给予精确控制
- VPC 与所有 AWS 网络服务集成（Direct Connect、VPN、Transit Gateway）

**事情变得复杂的地方**：

- VPC 设计需要预先规划——CIDR 块之后很难更改
- 太多小型 VPC 会产生对等复杂性（n 的平方问题）
- 在 VPC 中调试网络问题需要同时理解路由表、安全组、NACL 和子网关联
- NAT 网关成本在规模化时可能让你大吃一惊（每 GB 处理费）

## 摘要

- **VPC** 是 AWS 中逻辑隔离的私有网络——公共云内你围起来的场地。
- **子网**按可用区划分你的 VPC。公共子网连接到互联网网关；私有子网不连接。
- 将面向互联网的资源（负载均衡器）放在公共子网中。将其他所有东西（EC2、数据库、缓存）放在私有子网中。
- **路由表**控制流量的流向。每个子网都有一个。
- **NAT 网关**（在公共子网中）让私有资源发起出站互联网连接，而不接受入站连接。
- **VPC 对等**私密地连接两个 VPC。不是传递性的——对于大规模连接，使用 Transit Gateway。
- **安全组**保护单个资源（有状态）。**NACL** 保护整个子网（无状态）。

## 考试技巧

*SAA-C03 领域：设计安全架构（领域1，任务1.2）*

- **公共 vs 私有子网**：区别在于路由表。公共子网有到互联网网关的路由。私有子网没有。
- **NAT 网关放置**：始终在*公共*子网中。私有子网资源将出站流量路由到它。
- **NAT 的高可用性**：每个 AZ 创建一个 NAT 网关。如果你在 AZ-a 有一个 NAT 网关，AZ-b 的实例通过它路由，AZ-a 的失败也会导致 AZ-b 的互联网访问中断。
- **VPC 对等不是传递性的**：考试会描述三个 VPC，并问它们是否可以通过中间的那个通信——答案是不行，除非有直接对等或 Transit Gateway。
- **CIDR 重叠**：对等的 VPC 不能有重叠的 CIDR 块。经典考试陷阱。
- **堡垒主机（跳转机）**：要 SSH 进入私有 EC2 实例，你需要公共子网中的堡垒主机。堡垒主机是唯一有公网 IP 的机器；私有实例只接受来自堡垒主机安全组的 SSH。
- **VPC 端点**：允许私有资源访问 AWS 服务（S3、DynamoDB）而不通过 NAT 网关。两种类型：**网关端点**（S3、DynamoDB——免费）和**接口端点**（其他服务——按小时计费加数据费）。

**练习 2——考试练习**

*场景*：一家公司正在 AWS 上设计三层 Web 应用程序。Web 层（ALB + EC2）必须接受互联网流量。应用层（EC2）必须只接受来自 Web 层的流量。数据库层（RDS）必须只接受来自应用层的流量。应用层 EC2 实例需要从互联网下载软件包。解决方案必须高度可用。

哪种架构*最能*满足这些需求？

A) 所有层都在公共子网；安全组限制层间流量  
B) Web 层在公共子网；应用和数据库层在私有子网；一个 NAT 网关在公共子网  
C) Web 层在公共子网；应用和数据库层在私有子网；每个 AZ 一个 NAT 网关  
D) 所有层都在私有子网；互联网网关为所有层提供双向互联网访问

**提示 1**："高度可用"意味着没有单点故障。哪个选项引入了 NAT 网关作为单点故障？

**提示 2**：如果 NAT 网关的 AZ 宕机，哪些实例会失去互联网访问？

**提示 3**：仔细阅读需求——应用层需要*出站*互联网访问，而不是入站。

**答案**：C

**解析**：Web 层在公共子网提供通过 ALB 的面向互联网的访问。应用和数据库层在私有子网确保它们无法直接从互联网访问。每个 AZ 一个 NAT 网关（每个公共子网一个）为私有子网实例提供高可用的出站互联网访问——如果一个 AZ 失败，另一个 AZ 的 NAT 网关继续服务流量。

**为什么不是 A？** 所有层都在公共子网会直接将应用程序和数据库暴露在互联网上，破坏了分层安全模型的目的。

**为什么不是 B？** 单个 AZ 中的一个 NAT 网关是单点故障。如果那个 AZ 的 NAT 网关失败，所有私有实例都会失去出站互联网访问。

**为什么不是 D？** 互联网网关提供双向连接——带有到互联网网关路由的私有子网实际上是公共子网。
