# 第二十一章：代码的运输集装箱

"在我的机器上可以运行。"

Leo 已经学会了不要大声说出这句话。这不是辩解——这是诊断。这次的诊断对象是生产环境中的第三台 EC2 实例，它在六周前收到了一个没有人记录的库补丁，另外两台实例没有收到这个补丁，而这个补丁现在导致了一个只存在于那台实例上的 bug，在其他地方是不可见的。

他花了昨晚三个小时才找到它。

"每次我们部署，"第二天早上他说，"我们都要在多个实例之间协调。新版本，不同的依赖项。在测试环境工作，在生产环境出问题，因为环境已经漂移了。"

"因为有人在第三台实例上更新了包，而没有更新其他实例，"Priya 说，语气不含责备。

"我需要一个特定版本的——"

"我知道，"她说，"现在第三台实例与第一台和第二台有了不同的历史。这就是配置漂移。它悄无声息，直到不再悄无声息。"

Lambda 已经解决了 Nimbus 较小服务的空闲服务器问题。但核心 API——承载所有订单流量的那个——仍然在 EC2 上。而 EC2 实例，与函数不同，会积累历史。

"真正的解决方案是什么？"Maya 问。

"停止将服务器视为你配置的永久性事物，"Priya 说，"开始将它们视为你替换的一次性单元。"

有一个类比能如此精准地解释这一点，以至于它几乎出现在每一个关于软件容器的解释中。它来自 1956 年，与软件毫无关系。当有人终于问"跨不同运输工具可靠运输货物的解决方案是什么？"时，答案是：标准化集装箱。运输箱子，而不仅仅是箱子里的内容。

**什么是容器？**

**容器**是一个轻量级、可移植的单元，将你的应用程序与运行所需的一切打包在一起：运行时（Python 3.11、Node.js 20、Java 17）、库和依赖项、配置文件以及应用程序代码本身。

与虚拟机（模拟包括操作系统内核在内的整台计算机）不同，容器共享宿主机操作系统内核，同时保持其他所有内容的隔离。这使得容器启动迅速（秒级，有时是毫秒级）且体积小（兆字节，而非千兆字节）。

最流行的容器技术是 **Docker**。Docker 镜像是蓝图——应用程序及其环境的快照。Docker 容器是该镜像的一个运行实例。

关键属性：**不可变性**。今天构建的镜像将在任何支持 Docker 的主机上以完全相同的方式运行——无论是笔记本电脑、EC2 实例，还是不同数据中心的服务器。环境被烘焙进去了。配置漂移是不可能的。

"所以不用担心 EC2 实例上安装了什么，"Leo 说，"我们构建一个包含所有内容的镜像。这个镜像在任何地方都以相同的方式运行。"

"如果你需要在本地测试，你运行相同的镜像，"Priya 补充道，"不再有'在我的机器上可以运行'。"

**Amazon ECS：编排器**

运行一个容器很简单。在多台主机上运行数十个容器、在它们之间路由流量、重启失败的容器、在不停机的情况下部署新版本——这需要一个**编排器**。

**Amazon ECS（Elastic Container Service）** 是 AWS 的托管容器编排服务。你定义：

- **任务定义**：运行哪个容器镜像、分配多少 CPU 和内存、设置哪些环境变量、暴露哪些端口
- **服务**：运行多少份任务副本、如何处理故障和部署
- **集群**：底层计算基础设施

ECS 处理其余部分：在可用容量上放置任务、重启失败的任务、在部署期间耗尽连接、将健康任务注册到负载均衡器。

对于 Nimbus，API 从使用手动管理部署的 EC2 实例迁移到了 ECS。每次新部署都会将新的 Docker 镜像推送到 **Amazon ECR（Elastic Container Registry）**——AWS 的托管容器注册表——ECS 以零停机时间在所有任务中滚动更新。

**Fargate 与 EC2 启动类型**

ECS 可以以两种模式运行容器：

**EC2 启动类型**：你管理底层 EC2 实例。你负责修补实例、合理调整实例大小，并确保容器有足够的容量。控制更多，责任也更多。

**Fargate（容器的无服务器计算）**：AWS 完全管理底层基础设施。你指定每个任务的 CPU 和内存；Fargate 自动提供合适的容量。无需管理 EC2 实例。按 vCPU-秒和 GB-秒内存计费。

Fargate 是"无服务器容器"模式——你获得容器的环境隔离，而无需管理服务器。权衡是：对底层实例配置的控制较少，单位成本略高。

对于 Nimbus：API 服务使用 Fargate。他们不想为容器管理 EC2 实例。

**Amazon EKS：当你需要 Kubernetes 时**

**Kubernetes** 是一个开源容器编排系统——本质上是大规模管理容器的行业标准。它功能强大、可扩展，也很复杂。

**Amazon EKS（Elastic Kubernetes Service）** 是 AWS 的托管 Kubernetes 服务。它为你运行 Kubernetes 控制平面（管理层），而你管理工作节点（或者也使用 Fargate）。

何时应该使用 EKS 而不是 ECS？

**使用 ECS** 当：

- 你主要在 AWS 上，想要更简单、更原生 AWS 的体验
- 你的团队没有现有的 Kubernetes 专业知识
- 你想要更少的运维开销

**使用 EKS** 当：

- 你需要 Kubernetes 特定功能（自定义资源定义、Helm charts、Kubernetes 生态系统）
- 你的团队已经了解 Kubernetes
- 你在混合环境中运行（部分在本地，部分在 AWS），想要一致的编排层
- 你的工作负载有符合 Kubernetes 可扩展性的需求

"我们应该用哪个？"Maya 问。

"ECS，"Priya 立即说，"我们没有 Kubernetes 专业知识。ECS 能满足我们所有需求。现在添加 Kubernetes 只会增加运维复杂性而没有实际收益。"

"我们以后总可以在超出 ECS 能力时迁移到 EKS，"Leo 补充道。

这是一个正确的高级答案：选择适合当前需求的更简单的工具。

**容器如何改变部署**

在容器出现之前，部署新版本的 Nimbus API 意味着：

1. SSH 进入每台 EC2 实例
2. 从 Git 拉取最新代码
3. 安装/更新依赖项
4. 重启应用程序进程
5. 验证健康状态
6. 转到下一台实例

这很容易出错且缓慢。它需要协调。如果第 3 步在第 4 台实例上失败，你会得到一个混合部署，有些实例运行旧版本，有些无法运行新版本。

使用 ECS 和容器：

1. 构建新的 Docker 镜像（在 CI/CD 流水线中自动化）
2. 推送到 ECR
3. 更新 ECS 服务以使用新的镜像版本

ECS 处理滚动部署：启动带有新镜像的新任务，等待它们通过健康检查，然后停止旧任务。零停机时间部署，自动化。

如果新版本健康检查失败，ECS 停止部署，旧版本继续提供流量服务。

## 优势与局限

**容器**：

- 消除环境不一致性（"在我的机器上可以运行"）
- 实现快速、可靠的部署
- 不可变——相同的镜像在任何地方以相同方式运行
- 高效——比虚拟机更轻量，启动更快

**ECS**：

- 对于以 AWS 为中心的工作负载比 Kubernetes 更简单
- 与 AWS 紧密集成（IAM、ALB、CloudWatch、Secrets Manager）
- Fargate 选项完全消除了 EC2 管理

**EKS**：

- 完整的 Kubernetes 兼容性——使用整个生态系统
- 更适合混合环境或具有 Kubernetes 专业知识的团队
- 比 ECS 设置和运维更复杂

**复杂性所在**：

- 容器镜像必须构建和版本化——需要 CI/CD 流水线
- 调试容器需要与调试传统进程不同的工具
- 有状态容器（容器中的数据库）需要仔细的持久存储配置
- 容器间网络（服务到服务的通信）需要了解容器网络概念

## 总结

- **容器**将应用程序代码、运行时和依赖项打包在一起——在任何地方都以相同方式运行。
- **Docker** 是标准容器技术。镜像是蓝图；容器是运行实例。
- **ECR（Elastic Container Registry）** 是 AWS 的托管 Docker 注册表——在这里存储和版本化你的镜像。
- **ECS（Elastic Container Service）** 编排容器。你定义任务和服务；ECS 管理放置和生命周期。
- **Fargate** 是容器的无服务器计算——无需管理 EC2 实例。
- **EKS（Elastic Kubernetes Service）** 是托管 Kubernetes——适合需要 Kubernetes 功能或兼容性的团队。
- 在 AWS 上选择 ECS 以求简单；选择 EKS 以获得 Kubernetes 生态系统兼容性。

## 考试技巧

*SAA-C03 领域：设计弹性架构（领域 2，任务 2.1）*

- **ECS 与 EKS 信号**：提到"Kubernetes"、"Helm"、"现有 Kubernetes 专业知识"或"多云容器编排"的考试场景 → EKS。其他情况 → ECS。
- **Fargate 与 EC2 启动类型**："不想为容器管理 EC2 实例"、"无服务器容器"、"无基础设施管理"→ Fargate。"需要特定实例类型"、"GPU 工作负载"、"精细实例控制"→ EC2 启动类型。
- **ECS 任务角色**：与 EC2 实例角色类似，ECS 任务有 IAM 角色。每个任务可以有不同的权限。考试场景："容器需要从 S3 读取"→ 将 IAM 角色附加到任务定义。
- **ECR 镜像扫描**：ECR 可以扫描容器镜像以查找已知漏洞（CVE）。考试信号："扫描容器的安全漏洞"→ ECR 镜像扫描。
- **蓝/绿部署**：ECS 通过 CodeDeploy 集成支持蓝/绿部署。具有自动回滚的零停机部署。考试模式："无停机部署，具有自动回滚"→ ECS + CodeDeploy 蓝/绿。
- **ECS Service Auto Scaling**：根据 CPU、内存或自定义 CloudWatch 指标扩展任务数量。与 ALB 配合工作，将流量路由到正确数量的运行任务。

**练习 1 — 回顾**

解释 Docker 镜像和 Docker 容器之间的区别。解释 ECS 和 ECR 之间的区别。

*（提示：镜像之于容器，就像食谱之于烹饪好的菜肴。ECR 存储镜像；ECS 运行它们。）*

**练习 2 — 考试练习**

*场景*：一家公司有一个目前在手动管理的 EC2 实例上运行的微服务应用。团队在不一致的部署中挣扎——不同的 EC2 实例有不同的库版本，导致难以复现的 bug。他们希望在最大限度减少管理底层服务器的运维开销的同时，标准化部署。团队没有 Kubernetes 经验。

哪种解决方案最符合这些要求？

A) 在 EC2 上部署，使用 AWS Systems Manager Patch Manager 保持实例一致  
B) 使用 Docker 容器化应用程序；使用 Amazon ECS 搭配 Fargate 启动类型  
C) 使用 Docker 容器化应用程序；使用 Amazon EKS 搭配自管理节点组  
D) 使用 AWS Elastic Beanstalk 自动管理部署和实例配置

**提示 1**：容器直接解决"环境不一致"问题。哪些选项使用容器？

**提示 2**："最大限度减少管理服务器的运维开销"→ Fargate（无 EC2 管理）对比自管理节点（仍需管理 EC2）。

**提示 3**："没有 Kubernetes 经验"→ EKS 比 ECS 有更多的运维复杂性。

**答案**：B

**解释**：使用 Docker 容器化确保每次部署都使用具有相同依赖项的相同镜像——消除配置漂移。使用 Fargate 的 ECS 意味着不需要管理 EC2 实例。团队专注于应用程序代码和容器定义，而非服务器维护。ECS（而非 EKS）适合没有 Kubernetes 经验的团队。

**为什么不选 A？** Patch Manager 保持 EC2 实例更新，但并不能解决应用程序之间的库版本不一致问题。根本问题（不同实例上不同的代码环境）仍然存在。

**为什么不选 C？** 使用自管理节点组的 EKS 需要管理 EC2 实例*并且*学习 Kubernetes。两者都不符合要求。

**为什么不选 D？** Elastic Beanstalk 在 EC2 上管理应用程序部署，但除非使用容器，否则无法解决根本的环境不一致问题。默认情况下，Beanstalk 不使用 Docker 镜像（尽管可以配置使用）。

## 片尾彩蛋

第一次容器部署完美无缺。

新版本的 API：零停机时间。ECS 滚动更新，健康检查通过，旧任务耗尽，新任务接管。Leo 盯着控制台中的任务状态，带着一种近乎难以置信的神情。

"它就这样工作了，"他说。

"这就是重点，"Priya 说。

"没有 SSH。没有停机。没有'等待它重启'。"

"镜像就是部署工件，"她说，"环境是不可变的。部署过程是声明式的。这就是软件应该被交付的方式。"

Leo 又盯着控制台看了一会儿。

"我花了三年协调 EC2 部署，"他说，"协调 SSH 脚本。编写部署手册。"

"你在解决一个问题，"Priya 说，"而容器在设计上就解决了这个问题。"

此后他没有再说什么。但第二天早上，他开始编写容器构建过程的文档，这样其他人就不必花三年时间才能弄清楚了。
