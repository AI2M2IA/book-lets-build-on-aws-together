# 第二十一章：代码的运输集装箱

在 1956 年之前，把货物装上船是一场需要专门技能的谈判。每艘船的货舱都不一样。每个港口的起重机都不一样。每家承运商追踪货物去向的系统也各不相同。一箱货物从卡车到码头到轮船再到码头到卡车，要经过一连串处理方式各异的人手。货物会丢失。货物会损坏。同样的货物运两次，到达时状况却不同，因为两次的搬运方式不一样。

当终于有人把问题问清楚时，答案是：把集装箱标准化。不要在每个港口分别解决问题。在集装箱这一层一次性解决。运输箱子，而不仅仅是箱子里的内容。

标准化的集装箱不只是让运输变快了。它让运输变得*可预测*。一个集装箱在上海装入的货物，抵达鹿特丹时状况完全相同——因为集装箱在每个中转点都保护货物免受不确定性的影响。

这正是 Leo 面临的同一个问题。Nimbus API 在每个"港口"被以不同的方式"装载"：预发布环境的部署方式与生产环境不同，一号实例的部署方式与三号实例不同，六周未记录在案的变更让整个机群变得不可预测。

容器不会让 Leo 写代码更快。它会让部署变得可预测。

---

Lambda 迁移降低了较小服务的 EC2 账单。但核心 API 不一样——它持续运行，承载着全部订单流量，而且已经积累了八个月的配置历史。Lambda 解决的是空闲问题。容器要解决的是不一致问题。

核心 API 并不空闲；它无法迁移到 Lambda。但它有一个不同的问题：运行它的那些 EC2 实例已经彼此分化了。

---

Leo 已经学会了不要大声说出"在我的机器上可以运行"。这不是辩解——这是诊断。而这次的诊断对象是生产环境的三号 EC2 实例：六周前它收到了一个没有人记录的库补丁，另外两台实例没有收到，而那个补丁现在导致了一个只存在于那里、只在那一台实例上、在其他任何地方都不可见的 bug。

他前一天晚上花了三个小时才追踪到它。

"每次我们部署，"第二天早上他说，"我们都要在多个实例之间协调。新版本，不同的依赖项。在预发布环境正常，到生产环境就坏，因为环境已经分化了。"

"因为有人在三号实例上更新了一个包，而没有更新其他实例，"Priya 说。语气并不刻薄。

"我当时需要一个特定版本的——"

"我知道，"她说，"现在三号实例的历史和一号、二号不一样了。这就是配置漂移。它悄无声息，直到不再悄无声息。"

"真正的解决方案是什么？"Maya 问。

"停止把服务器当成需要你配置的永久性物件，"Priya 说，"开始把它们当成可以随时替换的一次性单元。"

**什么是容器？**

"把它想象成一个运输集装箱，"Leo 抓起一支马克笔说，"集装箱不在乎自己在哪艘船上。船也不在乎集装箱里装的是什么。它们就尺寸和锁紧机制达成了一致。其余的一切都在箱子里面。"

**容器**是一个轻量级、可移植的单元，将你的应用程序与运行所需的一切打包在一起：运行时（Python 3.11、Node.js 20、Java 17）、库和依赖项、配置文件，以及应用程序代码本身。

与虚拟机（模拟包括操作系统内核在内的整台计算机）不同，容器共享宿主机操作系统内核，同时保持其他所有内容的隔离。这使得容器启动迅速（秒级，有时是毫秒级）且体积小（兆字节，而非千兆字节）。

最流行的容器技术是 **Docker**。Docker 镜像是蓝图——应用程序及其环境的快照。Docker 容器是该镜像的一个运行实例。

关键属性：**不可变性**。今天构建的镜像将在任何支持 Docker 的主机上以完全相同的方式运行——无论是笔记本电脑、EC2 实例，还是不同数据中心的服务器。环境被烘焙进去了。配置漂移是不可能的。

"所以不用担心 EC2 实例上安装了什么，"Leo 说，"我们构建一个包含所有内容的镜像。这个镜像在任何地方都以相同的方式运行。"

"而且如果你需要在本地测试，你运行的是同一个镜像，"Priya 补充道，"不再有'在我的机器上可以运行'。"

**构建 Docker 镜像并推送到 ECR**

在任何编排器能够管理容器之前，Leo 必须先构建它，并把它存放在 ECS 能够拉取的地方。

他写了 Dockerfile：

```dockerfile
FROM python:3.11-slim

WORKDIR /app

COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

COPY . .

EXPOSE 8000
CMD ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8000"]
```

关键的一行：`FROM python:3.11-slim`。不是 Python 3.9。不是 Python 3.10。是 3.11——团队一致同意的特定版本，烘焙进了镜像。每一台运行这个镜像的实例都会精确地使用 Python 3.11。decimal 模块的舍入行为在任何地方都会完全一致。

他在本地构建了镜像：`docker build -t nimbus-api:1.0.0 .`

构建耗时 4 分钟。Docker 拉取了基础镜像，安装了依赖，复制了应用程序代码，并生成了一个标记为 `nimbus-api:1.0.0` 的镜像。

他在本地运行了它：`docker run -p 8000:8000 nimbus-api:1.0.0`

API 启动了。端口相同，行为与生产服务器一致——因为环境完全相同。

然后他把它推送到 ECR：

```bash
# Authenticate Docker to ECR
aws ecr get-login-password --region us-west-2 |   docker login --username AWS --password-stdin   123456789012.dkr.ecr.us-west-2.amazonaws.com

# Tag the image for ECR
docker tag nimbus-api:1.0.0   123456789012.dkr.ecr.us-west-2.amazonaws.com/nimbus-api:1.0.0

# Push
docker push 123456789012.dkr.ecr.us-west-2.amazonaws.com/nimbus-api:1.0.0
```

推送耗时 2 分钟。ECR 存储了镜像，随即触发了一次镜像扫描，并在 5 分钟内报告了结果。

**Amazon ECS：编排器**

运行一个容器很简单。在多台主机上运行数十个容器、在它们之间路由流量、重启失败的容器、在不停机的情况下部署新版本——这需要一个**编排器**。

**Amazon ECS（Elastic Container Service）** 是 AWS 的托管容器编排服务。你定义：

- **任务定义**：运行哪个容器镜像、分配多少 CPU 和内存、设置哪些环境变量、暴露哪些端口
- **服务**：运行多少份任务副本、如何处理故障和部署
- **集群**：底层计算基础设施

ECS 处理其余部分：把任务安置到可用容量上、重启失败的任务、在部署期间排空连接、把健康的任务注册到负载均衡器。

对于 Nimbus，API 从使用手动管理部署的 EC2 实例迁移到了 ECS。每次新部署都会把新的 Docker 镜像推送到 **Amazon ECR（Elastic Container Registry）**——AWS 的托管容器注册表——ECS 以零停机时间在所有任务中滚动更新。

**Fargate 与 EC2 启动类型**

ECS 可以以两种模式运行容器：

**EC2 启动类型**：你管理底层 EC2 实例。你负责给实例打补丁、合理调整实例大小，并确保容器有足够的容量。控制更多，责任也更多。

**Fargate（容器的无服务器计算）**：AWS 完全管理底层基础设施。你指定每个任务的 CPU 和内存；Fargate 自动提供合适的容量。无需管理 EC2 实例。按 vCPU-秒和 GB-秒内存计费。

Fargate 是"无服务器容器"模式——你获得容器的环境隔离，而无需管理服务器。权衡是：对底层实例配置的控制较少，单位成本略高。

"这每个月要花多少钱？"Tom 一边问一边打开定价计算器，"Fargate 对比 EC2 启动类型——我要看到真实的数字。"

Leo 的直觉估计——每个人脑子里都揣着的那种——是 Fargate 会更贵。无服务器的便利性，溢价的价格。他猜测大概比 EC2 贵百分之二十到三十。

"算一下真实的数字，"Tom 说，因为 Tom 就是这样的人。

Nimbus 的 API 服务运行 3 个任务，每个需要 0.5 vCPU 和 1GB 内存，24/7 运行：

**Fargate**：$0.04048/vCPU-小时 × 0.5 × 3 × 720 小时 = CPU 每月 $43.72。$0.004445/GB-小时 × 1 × 3 × 720 = 内存每月 $9.60。总计：每月 $53.32。

**EC2 启动类型**（3 × t3.medium，单价 $0.0416/小时）：$0.0416 × 3 × 720 = 每月 $89.86。

"等等，"Tom 说，"Fargate 更便宜？"

"在这个规模下，是的，"Leo 说，"Fargate 精确地按你分配的量收费。EC2 实例有开销——在你的容器还没启动之前，操作系统和 ECS 代理就已经消耗了一部分 CPU 和内存。一台 t3.medium 提供 2 vCPU 和 4GB，但每个容器只用 0.5 vCPU 和 1GB。剩下的都浪费了。"

"但 EC2 启动类型可以让你把多个任务塞进一台实例。"

"是的。在更大的规模下，通过精心的装箱优化，EC2 启动类型会变得更便宜。在我们的规模——三个任务——Fargate 赢。"

Tom 把这个记了下来。

对于 Nimbus：API 服务使用 Fargate。他们不想为容器管理 EC2 实例。

如果你用 Fargate 进行容器化，你消除了所有 EC2 管理开销——但你放弃了自定义实例类型的能力，这对 GPU 工作负载或专门的网络配置很重要。如果你为了 AWS 原生的简洁性选择 ECS，你获得了与 IAM 和 ALB 的紧密集成——但你被挡在了 Kubernetes 生态系统之外，如果以后需要多云可移植性，就需要重新架构。

**Amazon EKS：当你需要 Kubernetes 时**

**Kubernetes** 是一个开源容器编排系统——本质上是大规模管理容器的行业标准。它功能强大、可扩展，也很复杂。

**Amazon EKS（Elastic Kubernetes Service）** 是 AWS 的托管 Kubernetes 服务。它为你运行 Kubernetes 控制平面（管理层），而你管理工作节点（或者工作节点也用 Fargate）。

你可能会想：既然 Kubernetes 是行业标准，每个招聘启事都会提到它，我们为什么不直接用它呢？因为"行业标准"描述的是拥有专职平台团队的大公司在用什么。对于一个六人团队开发一款订餐应用来说，Kubernetes 增加了运维复杂性，眼下却没有任何实际收益。复杂性是真实的；收益在这个规模下只是理论上的。

Kubernetes 提供价值的层次，是大多数团队不需要的复杂度：用于构建内部平台的自定义资源定义、高级调度约束、用于细粒度部署控制的 Pod 中断预算，以及用于在数百个微服务之间管理流量的服务网格集成。这些是真实存在的能力。但它们也是 Nimbus 这种规模的初创公司永远用不上的能力。

这里的工程原则有时被称为 YAGNI：You Aren't Gonna Need It（你不会需要它）。ECS 给了 Nimbus 当前需要的一切。EKS 给了他们超出需要的东西，外加一条陡峭的学习曲线和可观的运维开销。"以后会有用"不是现在就增加复杂性的好理由。

何时应该使用 EKS 而不是 ECS？

**使用 ECS** 当：

- 你主要在 AWS 上，想要更简单、更 AWS 原生的体验
- 你的团队没有现成的 Kubernetes 专业知识
- 你想要更少的运维开销

**使用 EKS** 当：

- 你需要 Kubernetes 特有的功能（自定义资源定义、Helm charts、Kubernetes 生态系统）
- 你的团队已经了解 Kubernetes
- 你在混合环境中运行（部分在本地，部分在 AWS），想要一致的编排层
- 你的工作负载有与 Kubernetes 可扩展性相匹配的需求

**容器网络：临时 IP 与服务发现**

迁移到容器时有一件事会让团队措手不及：容器的 IP 地址每次重启都会改变。

在 EC2 的世界里，实例拥有相对稳定的私有 IP。你可以（尽管你不应该）把它们硬编码在配置文件里。服务之间通过 IP 互相认识。

在容器的世界里，ECS 中的每个任务启动时从 VPC 子网获取一个 IP。当它停止、新任务启动时（作为部署或重启的一部分），新任务会获得一个不同的 IP。

"如果某个服务被硬编码为调用 `10.0.1.45`，而那个容器被替换成了 `10.0.1.82`，会怎样？"Priya 问，"调用方就开始打空炮了。"

这就是为什么服务发现在容器环境中很重要。ECS + Application Load Balancer 自动处理这件事：ALB 的 DNS 名称是稳定的；ECS 把健康的任务注册到目标组；ALB 把流量路由到当前健康的任意任务。调用方与 ALB 的 DNS 名称对话，而不是与单个容器的 IP 对话。

对于内部服务间通信（非面向用户的），**AWS Cloud Map** 提供服务发现：每个 ECS 服务向 Cloud Map 注册，由它提供一个稳定的 DNS 名称。订单服务调用 `http://notification.nimbus.local:8080`，Cloud Map 把它解析到通知服务中当前健康的那些任务。

"所以容器之间通过 DNS 名称对话，而不是 IP？"Leo 确认道。

"没错。IP 是临时的。DNS 名称才是契约。"

**机密注入：不要把机密放在环境变量里**

最初的 EC2 部署有一个 Priya 已经提了好几个月的问题：机密（数据库密码、API 密钥、SES 凭证）以环境变量的形式存储在 EC2 实例上，由部署脚本设置。

环境变量对实例上运行的任何进程都是可访问的。它们会出现在调试工具里、某些崩溃报告里，以及进程列表里。如果你把它们记进日志（某些开发工具默认就会这么做），它们还会出现在 CloudWatch 里。

容器并不会自动解决这个问题——你仍然可以在 ECS 任务定义中以环境变量的形式传递机密。而 ECS 任务定义存储在 AWS 控制台中，任何有 ECS 访问权限的人都能看到。

正确的模式：**AWS Secrets Manager + ECS 任务定义集成**。

不要把数据库密码存在任务定义里，而是：

```json
"secrets": [
  {
    "name": "DB_PASSWORD",
    "valueFrom": "arn:aws:secretsmanager:us-west-2:123456789012:secret:nimbus/prod/db-password"
  }
]
```

ECS 在任务启动时从 Secrets Manager 获取机密，并将其作为环境变量注入容器。机密的值从不存储在任务定义中——任务定义里只有 Secrets Manager 机密的 ARN。容器在运行时收到值。Secrets Manager 可以在不更改任务定义的情况下轮换值。

"那如果有人读取任务定义呢？"Priya 问，"他们会看到 Secrets Manager 的 ARN，但看不到值。"

"而且没有正确的 IAM 权限，"Leo 确认道，"他们也无法从 Secrets Manager 取回那个值。"

"这就是设计意图，"Priya 说，"任务的执行角色只有读取那一个特定机密的权限。除此之外什么都没有。攻破任务定义得到的是一个 ARN，不是一个密码。" 

"我们应该用哪个？"Maya 问，"还有，为什么不用 Kubernetes？每个职位描述里都有它。每个大会演讲里都有它。"

"ECS，"Priya 立刻说，"我们没有 Kubernetes 专业知识。ECS 能满足我们所有需求。现在引入 Kubernetes 只会增加运维复杂性，却没有任何实际收益。"

曾在上一家公司运维过 Kubernetes 集群的 Soo-Jin 点了点头。"我背过那个值班传呼机。在真正需要它之前，你不会想要它的。"

"如果以后超出了 ECS 的能力，我们随时可以迁移到 EKS，"Leo 补充道。

这是一个正确的资深工程师答案：选择适合当前需求的更简单的工具。

**ECR：保护你的镜像**

"那如果有人试图通过一个有漏洞的基础镜像入侵呢？"Priya 问，"有人抓取一个带有已知 CVE 的旧镜像，用它在应用容器里获得立足点？"

在把任何容器部署到生产环境之前，这正是该问的问题。

**Amazon ECR（Elastic Container Registry）** 存储你的 Docker 镜像，并可以在部署前扫描它们的已知漏洞。ECR 镜像扫描会将镜像与已知 CVE（Common Vulnerabilities and Exposures，公共漏洞和暴露）数据库进行比对，并按严重程度标记问题。

Priya 制定的策略：任何带有 CRITICAL（严重）级别 CVE 的镜像都不得部署到生产环境。CI/CD 流水线会在更新 ECS 服务之前检查扫描结果。如果发现严重漏洞，流水线就会失败并向团队告警。

"这不是偏执，"Priya 说，"这只是在部署前加一道检查。"

**容器如何改变部署**

在容器出现之前，部署新版本的 Nimbus API 意味着：

1. SSH 进入每台 EC2 实例
2. 从 Git 拉取最新代码
3. 安装/更新依赖项
4. 重启应用程序进程
5. 验证健康状态
6. 转到下一台实例

这很容易出错且缓慢。它需要协调。如果第 3 步在第 4 台实例上失败，你会得到一个混合部署：有些实例运行旧版本，有些无法运行新版本。

使用 ECS 和容器：

1. 构建新的 Docker 镜像（在 CI/CD 流水线中自动化）
2. 推送到 ECR
3. 更新 ECS 服务以使用新的镜像版本

ECS 处理滚动部署：启动带有新镜像的新任务，等待它们通过健康检查，然后停止旧任务。零停机部署，全自动。

如果新版本健康检查失败，ECS 停止部署，旧版本继续提供流量服务。

**部署的最低配置要求：健康检查**

容器部署的全部安全性都取决于健康检查是否真正在工作。

ECS 使用两类健康检查：

**容器级健康检查**：在 Dockerfile 或任务定义中定义。在容器内部运行，验证应用程序是否在响应。

```dockerfile
HEALTHCHECK --interval=30s --timeout=5s --retries=3   CMD curl -f http://localhost:8000/health || exit 1
```

**ALB 目标组健康检查**：负载均衡器定期向健康检查端点发送 HTTP 请求。未通过健康检查的任务会被从目标组中移除。

如果两类健康检查都没有正确配置，ECS 会认为每个任务都是健康的——并且会毫不停顿地部署一个坏掉的镜像。这是最常见的容器部署错误。

"健康检查端点会不会泄露内部信息？"Priya 问。

`/health` 处的健康检查端点只返回：`{"status": "ok"}`。没有版本号，没有依赖项状态，没有内部配置。健康响应中的任何信息都可能对试图测绘应用程序的人有用。让健康端点保持最简。

对于详细的内部健康状态（数据库连通性、依赖检查），使用一个单独的、需要认证的 `/health/detail` 端点——仅可从 VPC 内部访问。

**结构化日志：窥探运行中容器的唯一窗口**

在 EC2 上，出了问题你就 SSH 进去。你 tail 日志文件。你看进程表。你检查磁盘使用情况。你四处摸索。

在容器里，没有 SSH。容器是短暂的——它可能运行在集群中的任意一台主机上，而且一旦健康检查失败，ECS 会毫无预警地替换它。等你想到要 SSH 进去时，你想检查的那个容器可能已经不存在了。

在容器化环境中，日志不是一种调试便利。它们是事情发生过的唯一证据。

"那如果一个容器悄无声息地失败了，而我们没有日志呢？"Priya 在容器架构评审时问，"一个任务可能以退出码 1 退出，而如果日志在它终止前没有被捕获，我们永远不会知道原因。"

这不是假设。这种事在第一次容器部署时屡屡发生。

正确的模式：使用 `awslogs` 日志驱动，把每个容器配置为向 **Amazon CloudWatch Logs** 发送结构化日志。ECS 自动处理日志投递——不需要安装日志代理，不需要 sidecar 容器。

在任务定义中：

```json
"logConfiguration": {
  "logDriver": "awslogs",
  "options": {
    "awslogs-group": "/ecs/nimbus-api",
    "awslogs-region": "us-west-2",
    "awslogs-stream-prefix": "ecs"
  }
}
```

容器内写到 stdout 或 stderr 的每一行都会被捕获并发送到日志组 `/ecs/nimbus-api`，按任务 ID 组织。ECS 为每个任务创建一个新的日志流，因此你可以找到那个具体失败的容器的日志——即使它已经被替换了。

任务执行角色需要写入 CloudWatch Logs 的权限。没有它，日志驱动会静默失败，所有日志输出都会丢失。

**结构化日志与纯文本对比**：纯文本日志（"Order 7741 placed"）需要 grep。结构化 JSON 日志（`{"event": "order_placed", "order_id": "7741", "restaurant_id": "47", "amount": 3200}`）可以用 CloudWatch Logs Insights 以一种类似 SQL 的语法查询：

```
fields @timestamp, event, order_id, restaurant_id
| filter event = "order_placed"
| stats count(*) by restaurant_id
| sort count desc
| limit 10
```

这个查询直接在日志组上运行。不需要数据库。不需要数据管道。不需要 ETL 任务。答案几秒钟内就出来了。

这并不能取代我们将在第 26 章构建的分析数据湖。它回答的是运维问题——"过去 30 分钟里 47 号餐厅有多少订单？"——在事故处理的当口，在你没时间跑 Athena 查询的时候。

**CloudWatch Container Insights**

**Container Insights** 是 CloudWatch 的一项功能，它按 ECS 集群、服务和任务收集并聚合容器级指标——CPU、内存、网络 I/O、存储 I/O。你看到的不再是 EC2 级别的指标（这台主机怎么样？），而是任务级别的指标（这个具体的 ECS 服务怎么样？）。

在 ECS 集群上用一项设置就能启用：

```bash
aws ecs update-cluster-settings \
  --cluster nimbus-production \
  --settings name=containerInsights,value=enabled
```

启用之后：

- 你看到每个服务的仪表板：任务数量、CPU 利用率、内存利用率
- 你可以基于任务级 CPU 设置告警（而不是 EC2 主机 CPU，那是一个钝得多的信号）
- 你可以把内存峰值与日志事件关联起来——任务内存在 14:22 攀升到 95%；日志显示恰好在 14:21，来自 47 号餐厅菜单导入的入站请求出现了一个峰值

"这每个月要花多少钱？"Tom 问。

Container Insights 对它产生的自定义指标和日志存储收费。在 Nimbus 的规模（三个服务，每个 3-6 个任务），大约是每月 $12——用来换取任务级的运维可见性，这是一笔划算的交易。

Leo 当天就把它启用了。

第一次有任务健康检查失败并被 ECS 替换时，Container Insights 仪表板自动捕获了该事件：任务 ID、启动时间、失败时间、退出码。该任务的 CloudWatch 日志流保留了终止前的最后 40 行输出——它们显示了一个未捕获的异常，由一家新餐厅合作伙伴格式错误的菜单 JSON 触发。

没有 Container Insights 和结构化日志：错误率神秘飙升，调查需要 SSH 到一台早已不再运行那个失败任务的主机，45 分钟的瞎猜。

有了它们：CloudWatch 仪表板里的一个日志流链接、确切的异常、餐厅 ID、出问题的字段——不到五分钟搞定。

"没有 SSH，"Leo 在评审事后复盘时说，"不用停机调查。日志把活儿干了。"

"日志能把活儿干了，"Priya 说，"前提是你配置了让它们被捕获。"


**当容器是错误的选择**

"等等——可是*为什么*我们不把所有东西都容器化呢？"Maya 问，"你们刚刚让我相信容器解决了所有配置漂移问题。为什么不把每一个服务都跑在容器里？"

这和她当初问 Lambda 的问题一样。答案也类似。

容器带来了运维方面的要求：你需要一个容器注册表（ECR）、一条构建并推送镜像的 CI/CD 流水线、一个编排器（ECS）、配置成任务级而非实例级可见性的监控，以及一个理解 Docker 和镜像版本管理的团队。

对于一个已经在 EC2 上运行良好、稳定、没有受配置漂移之苦的服务，容器化的成本可能超过收益。

容器是错误选择的具体情形：

**并非为容器可移动性而构建的有状态服务**：容器中的数据库需要小心翼翼的持久卷管理。大多数把数据库跑在容器里的团队，在领教过这种复杂性之后，最终都把它们迁回了托管服务（RDS、ElastiCache）。

**有专门硬件需求的服务**：GPU 工作负载、特定的网络接口配置或基于 FPGA 的处理，需要带特定硬件的 EC2 实例。容器改变不了这一点——你仍然要用 EC2 启动类型，只是在上面套了一层容器，而容器这层抽象只增加了复杂性，没带来好处。

**非常简单的脚本和任务**：一个每周运行一次、没有依赖漂移问题的 40 行 Python 脚本。为它加上 Docker、ECR、ECS 任务定义和一条 CI/CD 流水线，未免小题大做。Lambda 更简单。一个普通的 EC2 定时任务可能还要更简单。

"原则，"Leo 说，"和往常一样：让工具匹配问题。容器解决的是配置漂移和部署一致性。如果你没有这个问题，你就不需要容器。"

## AWS Batch：面向大规模任务的容器

ECS 和 EKS 是为长时间运行的服务设计的——持续运行、接受请求、随流量扩展的应用。但有些工作负载不一样：它们运行一段固定的时长，处理一个确定的数据集，然后停止。为数百家餐厅生成月末发票。运行一个机器学习训练任务。处理一份夜间分析导出。

对于这类工作负载，你想要的不是一个服务——而是一个任务（job）。

**AWS Batch** 是一项完全托管的服务，能以任意规模运行批量计算任务。你把任务定义为一个 Docker 容器（与 ECS 使用的容器格式相同），其余交给 Batch 处理：预置 EC2 或 Fargate 计算资源、把任务调度进队列、任务到来时扩容、完成后缩回零。

关键概念：

- **任务定义（Job definition）：** Docker 容器、资源需求（vCPU、内存）以及要运行的命令
- **任务队列（Job queue）：** 已提交的任务在运行前等待的地方；每个队列关联一个或多个计算环境
- **计算环境（Compute environment）：** 底层的 EC2 或 Fargate 容量。可以使用 Spot 实例节省最多 90% 的成本——Batch 自动处理中断和重试

"等等——可是*为什么*要用 Batch，而不是直接跑一个 ECS 任务？"Maya 问。

"因为 ECS 服务是常驻的，"Leo 说，"它等待请求。Batch 任务运行、结束，然后 Batch 把计算资源缩回零。两次运行之间你什么都不用付。"

Tom 从定价页面抬起头来。"那 Spot 实例呢？"

"Batch 可以跑在 Spot 上。如果 Spot 实例在任务中途被回收，Batch 会自动重试。对一个 45 分钟的发票任务来说，这没问题。"

**与 ECS/EKS 对比：** ECS/EKS 运行服务——常驻、由请求驱动。Batch 运行任务——有限时长、由数据驱动、空闲时缩到零。

**与 Lambda 对比：** Lambda 有 15 分钟的超时限制。Batch 任务可以运行数小时甚至数天。

Nimbus 的语境：夜间发票生成任务为数百家餐厅合作伙伴运行，耗时 45 分钟。Lambda 在 15 分钟就超时了。一个常驻的 ECS 服务一天有 23 个小时在浪费钱。Batch 把这个任务跑在 Spot 实例上，38 分钟完成，花费 $1.20，然后关机。

"这比我等旧脚本跑完时买的那杯咖啡还便宜，"Leo 说。

"而且没有 EC2 要管理，"Priya 补充道，"Batch 预置它、运行它、终止它。"

## 优势与局限

**容器**：

- 消除环境不一致性（"在我的机器上可以运行"）
- 实现快速、可靠的部署
- 不可变——相同的镜像在任何地方以相同方式运行
- 高效——比虚拟机更轻量，启动更快

**ECS**：

- 对于以 AWS 为中心的工作负载比 Kubernetes 更简单
- 与 AWS 紧密集成（IAM、ALB、CloudWatch、Secrets Manager）
- Fargate 选项完全消除了 EC2 管理

**EKS**：

- 完整的 Kubernetes 兼容性——可以使用整个生态系统
- 更适合混合环境或具有 Kubernetes 专业知识的团队
- 比 ECS 设置和运维更复杂

**复杂性所在**：

- 容器镜像必须构建和版本化——需要 CI/CD 流水线
- 调试容器需要与调试传统进程不同的工具
- 有状态容器（容器中的数据库）需要仔细的持久存储配置
- 容器间网络（服务到服务的通信）需要了解容器网络概念

## 总结

Lambda 让空闲计算免费了。容器让部署变得确定了。两者合在一起，解决了成长中的工程团队最常见的两大运维痛点。

- **容器**将应用程序代码、运行时和依赖项打包在一起——在任何地方都以相同方式运行。
- **Docker** 是标准容器技术。镜像是蓝图；容器是运行实例。
- **ECR（Elastic Container Registry）** 是 AWS 的托管 Docker 注册表——在这里存储、版本化并扫描你的镜像。启用镜像扫描，在部署前捕获 CVE。
- **ECS（Elastic Container Service）** 编排容器。你定义任务和服务；ECS 管理放置和生命周期。
- **Fargate** 是容器的无服务器计算——无需管理 EC2 实例。在小规模下通常比 EC2 启动类型更便宜，因为消除了 EC2 的开销。在更大的规模下，通过精心的任务装箱优化，EC2 启动类型可能更具成本效益。
- **EKS（Elastic Kubernetes Service）** 是托管 Kubernetes——适合需要 Kubernetes 功能或兼容性的团队。
- **Secrets Manager 集成**：通过任务定义在启动时把机密注入容器——不要把机密的值直接存在环境变量或任务定义里。
- **服务发现**：容器 IP 是临时的。使用 ALB DNS 名称或 Cloud Map 进行稳定的服务寻址。
- 在 AWS 上选择 ECS 以求简单；选择 EKS 以获得 Kubernetes 生态系统兼容性。

## 考试技巧

*SAA-C03 领域：设计弹性架构（领域 2，任务 2.1）*

- **ECS 与 EKS 信号**：提到"Kubernetes"、"Helm"、"现有 Kubernetes 专业知识"或"多云容器编排"的考试场景 → EKS。其他情况 → ECS。
- **Fargate 与 EC2 启动类型**："不想为容器管理 EC2 实例"、"无服务器容器"、"无基础设施管理"→ Fargate。"需要特定实例类型"、"GPU 工作负载"、"精细实例控制"→ EC2 启动类型。
- **任务角色与任务执行角色** ——一个真实的考试区分点。**任务执行角色**由 ECS *代理*代表任务使用，作用于你的代码之前和周边：从 ECR 拉取镜像、从 Secrets Manager 获取机密、向 CloudWatch 写日志。**任务角色**是*容器内你的应用程序代码*调用 AWS 服务时使用的：从 S3 读取、向 DynamoDB 写入——类似 EC2 实例角色，但按任务划分，因此每个任务可以有不同的权限。"容器需要从 S3 读取"→ **任务角色**（在任务定义中附加）。"任务拉取镜像失败 / 无法获取机密"→ **执行角色**缺少权限。
- **Fargate Spot**：在空闲容量上运行容错容器，最高可节省约 70%，并有两分钟的中断警告——它是 Fargate 版的 EC2 Spot，通过容量提供程序配置。考试信号："在不管理实例的情况下，以最低成本运行可容忍中断的容器"→ Fargate Spot。
- **ECR 镜像扫描**：ECR 可以扫描容器镜像以查找已知漏洞（CVE）。考试信号："扫描容器的安全漏洞"→ ECR 镜像扫描。
- **蓝/绿部署**：ECS 通过 CodeDeploy 集成支持蓝/绿部署。具有自动回滚的零停机部署。考试模式："无停机部署，具有自动回滚"→ ECS + CodeDeploy 蓝/绿。
- **Secrets Manager 集成**：考试信号："在不把值存进任务定义的情况下向容器注入机密"→ 在任务定义中使用 `secrets` 字段引用 Secrets Manager 的 ARN。任务执行角色需要 `secretsmanager:GetSecretValue` 权限。
- **ECS Service Auto Scaling**：根据 CPU、内存或自定义 CloudWatch 指标扩展任务数量。与 ALB 配合工作，把流量路由到数量合适的运行中任务。
- **AWS Batch：** 面向 Docker 容器的托管批量计算。任务队列 → 计算环境（EC2 或 Fargate，支持 Spot）。使用场景：Lambda 超时太短，而为有限时长的任务跑一个 ECS 服务太浪费。考试信号："大规模批处理"或"运行数小时的任务"→ AWS Batch。

**练习 2 — SAA-C03 场景**

*场景*：一家公司有一个目前在手动管理的 EC2 实例上运行的微服务应用。团队饱受部署不一致之苦——不同的 EC2 实例有不同的库版本，导致难以复现的 bug。他们希望在最大限度减少管理底层服务器的运维开销的同时，实现部署标准化。团队没有 Kubernetes 经验。

哪种解决方案最符合这些要求？

A) 使用 Docker 容器化应用程序；使用 Amazon ECS 搭配 Fargate 启动类型  
B) 在 EC2 上部署，使用 AWS Systems Manager Patch Manager 保持实例一致  
C) 使用 Docker 容器化应用程序；使用 Amazon EKS 搭配自管理节点组  
D) 使用 AWS Elastic Beanstalk 自动管理部署和实例配置

**提示 1**：容器直接解决"环境不一致"问题。哪些选项使用容器？

**提示 2**："最大限度减少管理服务器的运维开销"→ Fargate（无 EC2 管理）对比自管理节点（仍需管理 EC2）。

**提示 3**："没有 Kubernetes 经验"→ EKS 比 ECS 有更多的运维复杂性。

**答案**：A

**解释**：使用 Docker 容器化确保每次部署都使用具有相同依赖项的相同镜像——消除配置漂移。使用 Fargate 的 ECS 意味着没有 EC2 实例需要管理。团队专注于应用程序代码和容器定义，而非服务器维护。对于没有 Kubernetes 经验的团队，ECS（而非 EKS）才是合适的。

**为什么不选 B？** Patch Manager 让 EC2 实例保持更新，但并不能解决应用程序之间的库版本不一致问题。根本问题（不同实例上不同的代码环境）依然存在。

**为什么不选 C？** 使用自管理节点组的 EKS 需要管理 EC2 实例*并且*学习 Kubernetes。两者都不符合要求。

**为什么不选 D？** Elastic Beanstalk 在 EC2 上管理应用程序部署，但除非使用容器，否则无法解决根本的环境不一致问题。默认情况下，Beanstalk 不使用 Docker 镜像（尽管可以配置使用）。

容器就是对这一切的回答。不是因为它新颖有趣。而是因为它让那个问题再也无从问起。
