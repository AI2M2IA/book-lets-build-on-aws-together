# 第12章：互联网如何找到你

Nimbus 在运行了。负载均衡器有一个公网 IP。EC2 实例有私网 IP。数据库被锁在私有子网中。Priya 对着网络图表示满意地点了点头。

Tom 看了看负载均衡器的 URL：`nimbus-alb-123456789.us-east-1.elb.amazonaws.com`。

"这是顾客要在浏览器里输入的内容？" 他问。

"这是 AWS 自动分配的，" Maya 说。

"我不打算把这个印在名片上。"

"我也不打算。"

他们需要一个域名。他们从一个域名注册商那里购买了 `eatnimbus.com`。现在他们需要将这个名字连接到他们的 AWS 基础设施。

"互联网怎么知道 `eatnimbus.com` 是指 us-east-1 中的负载均衡器？" Leo 问。

问得好，Leo。

**电话本类比**

在智能手机之前，每个城市都有一本电话本。如果你想联系"Mario's Pizza"，你不需要记住他们的电话号码——你查找名字，得到号码，然后打电话。

互联网有自己的电话本：**域名系统（DNS）**。

DNS 将人类可读的名称（如 `eatnimbus.com`）转换为机器可读的 IP 地址（如 `203.0.113.42`）。每次你访问一个网站，你的计算机都悄悄地在 DNS 中查找域名，得到要连接的 IP 地址。

如果你更改了服务器的 IP 地址，你就更新 DNS 记录——就像在电话本里更改你的号码——互联网就能在你的新位置找到你。

**认识 Route 53**

Amazon Route 53 是 AWS 的托管 DNS 服务。它之所以叫 Route 53，是因为53端口是标准的 DNS 端口。（有时 AWS 的命名方式很直接。）

Route 53 做几件事：

**域名注册**：你可以直接通过 Route 53 购买域名。

**DNS 托管（托管区域）**：你为你的域名创建一个*托管区域*，Route 53 管理告诉世界在哪里找到你的 DNS 记录。

**健康检查**：Route 53 可以监控你的端点，并将流量从不健康的端点路由到其他地方。

**流量路由策略**：Route 53 支持多种超越简单 DNS 的路由策略——加权、基于延迟、地理位置、故障转移。

**DNS 记录：电话本条目**

DNS 记录将名称映射到目标。最常见的类型：

**A 记录**：将名称映射到 IPv4 地址。
`eatnimbus.com → 203.0.113.42`

**AAAA 记录**：将名称映射到 IPv6 地址。

**CNAME 记录**：将名称映射到另一个名称（别名）。
`www.eatnimbus.com → eatnimbus.com`

**MX 记录**：指定哪些服务器处理该域名的电子邮件。

**TXT 记录**：存储任意文本。常用于域名验证（证明你拥有该域名）和电子邮件身份验证（SPF、DKIM）。

对于 Nimbus，主要设置：

- `eatnimbus.com` → 指向负载均衡器 IP 的 A 记录
- `www.eatnimbus.com` → 指向 `eatnimbus.com` 的 CNAME
- `api.eatnimbus.com` → 指向 API 负载均衡器的 A 记录

"等等，" Tom 说。"负载均衡器的 IP 可能会变化。AWS 文档里这么说的。"

说得好，Tom。

**别名记录：AWS 对动态 IP 的解决方案**

负载均衡器、CloudFront 发行版和 S3 网站有 DNS 名称，而没有静态 IP 地址。底层 IP 可能会变化。

如果你创建一个 CNAME 指向负载均衡器的 DNS 名称，它可以工作——但由于 DNS 标准的限制，你无法对根域名（没有 `www` 的 `eatnimbus.com`）使用 CNAME。

Route 53 通过**别名记录**解决了这个问题——这是 DNS 的 AWS 专有扩展。别名记录将名称直接映射到 AWS 资源（负载均衡器、CloudFront 发行版、S3 网站），Route 53 自动处理动态 IP 解析。别名记录可以在根域名级别使用。而且与对外部服务的常规 DNS 查询不同，对 AWS 资源的别名记录查询是免费的。

"所以我们为 `eatnimbus.com` 使用别名记录指向负载均衡器，" Leo 确认道。

"Route 53 在任何特定时刻处理负载均衡器使用的任何 IP，" Priya 补充道。

"免费，" Tom 说，突然非常感兴趣。

**路由策略：不仅仅是"它在哪里？"**

这就是 Route 53 变得有趣的地方。DNS 不只是一个查找服务——它可以是一个流量管理工具。

**简单路由**：一条记录，一个目标。标准 DNS。

**加权路由**：按权重在多个目标之间分配流量。在迁移期间将90%的流量发送到新服务器，10%发送到旧服务器。调整权重，直到你对新服务器有信心，然后切换到100%。

**基于延迟的路由**：将用户路由到延迟最低的 AWS 区域。西雅图的用户被路由到 `us-west-2`。东京的用户被路由到 `ap-northeast-1`。相同的域名，不同的目的地。

**地理位置路由**：根据用户的地理位置进行路由。所有欧洲用户去 `eu-west-1`。所有北美用户去 `us-east-1`。用于数据主权（将欧盟用户数据保留在欧盟区域）或内容定制（语言、货币）。

**故障转移路由**：指定主要和次要端点。如果主要端点未通过 Route 53 的健康检查，流量会自动重定向到次要端点。这是灾难恢复的 DNS 层。

**多值应答路由**：为查询返回最多八个健康的 IP 地址，让客户端选择。一种简单的替代方案，可以在多台服务器之间分配流量，而无需负载均衡器。

"所以 Route 53 不只是一本电话本，" Maya 说。"它是一本聪明的电话本，可以根据你的位置路由电话。"

"并且如果号码不健康就断开连接，" Priya 补充道。

**健康检查：绕开故障路由**

Route 53 可以用健康检查监控你的端点。如果端点失败，Route 53 可以：

- 从 DNS 响应中删除它（停止向那里发送流量）
- 触发到备份端点的故障转移
- 通过 CloudWatch 发送警报

健康检查是 DNS 路由和实际应用程序健康之间的链接。在故障转移配置中：Route 53 每30秒监控主要端点。如果三次连续检查失败，Route 53 开始返回次要端点的地址。

这不是即时的——DNS 有传播时间。一旦 Route 53 更改了 DNS 记录，世界各地的 DNS 解析器需要接收到这个变化，根据 TTL 设置，这可能需要几秒到几分钟。

**TTL：DNS 缓存**

DNS 响应在多个层面被缓存——在你的路由器、你的 ISP、你的浏览器中。DNS 记录上的 **TTL（生存时间）**告诉缓存在再次检查之前要记住答案多长时间。

高 TTL（1小时或更多）：DNS 查询更少，Route 53 上的负载更小，但变更传播更慢。

低 TTL（60秒或更少）：变更传播更快，但需要更多 DNS 查询。

在计划的迁移之前（更新 DNS 指向新服务器），提前一天将 TTL 降低到60秒。然后当你做出更改时，它大约在一分钟内传播。迁移后，将其提高回正常值。

"如果我们只是在迁移期间而不是之前降低它，" Leo 慢慢说，"旧的 TTL 意味着一些用户会看到旧服务器达一个小时。"

"完全正确，" Priya 说。"DNS 迁移需要在迁移之前进行规划，而不只是在迁移期间。"

## 优势与局限性

**Route 53 适合的情况**：完全在 AWS 内注册和管理域名；根据延迟、地理位置或跨多个端点的加权分布路由流量；基于健康检查的区域间或主备端点之间的故障转移；通过别名记录将 DNS 与其他 AWS 服务集成。

**Route 53 不是你需要的东西的情况**：Route 53 是一个 DNS 服务，不是负载均衡器。如果你需要在区域内的多台服务器或容器之间分配流量，使用应用负载均衡器——Route 53 无法像负载均衡器那样在连接级别进行加权轮询。基于延迟的跨区域路由增加了成本和运营复杂性，只有在你的用户真正全球分布且毫秒对转化率有影响时才有意义。对于大多数单区域应用程序，一条指向 ALB 的 A 记录就是你需要的全部 Route 53 配置。

## 摘要

- **DNS** 将域名转换为 IP 地址——互联网的电话本。
- **Route 53** 是 AWS 的托管 DNS 服务：域名注册、DNS 托管、健康检查和路由策略。
- **A 记录**将名称映射到 IPv4 地址。**CNAME** 将名称映射到其他名称。**别名记录**将名称映射到 AWS 资源（负载均衡器、CloudFront、S3）。
- 对根域名和具有动态 IP 的资源使用别名记录（而不是 CNAME）。
- 路由策略超越了简单 DNS：**加权**（流量分割）、**基于延迟**（性能）、**地理位置**（数据主权）、**故障转移**（灾难恢复）。
- **健康检查**监控端点，自动从 DNS 响应中删除不健康的目标。
- 在迁移之前提前规划 TTL 变更——提前降低 TTL，使变更快速传播。

## 考试技巧

*SAA-C03 领域：设计高性能架构（领域3，任务3.4）*

- **别名 vs CNAME**：别名记录可以在根域名使用；CNAME 不行。对 AWS 资源的别名记录查询是免费的；CNAME DNS 查询是收费的。当考试询问将根域名映射到负载均衡器时 → 别名记录。
- **路由策略使用案例**（常见考试场景）：
  - "逐步将流量迁移到新版本" → 加权路由
  - "将用户路由到最近的 AWS 区域" → 基于延迟的路由
  - "将欧盟用户数据保留在欧盟区域" → 地理位置路由
  - "当主节点宕机时自动 DNS 故障转移" → 带健康检查的故障转移路由
- **Route 53 健康检查**：可以检查 HTTP/HTTPS/TCP 端点，可以触发 CloudWatch 警报。考试在灾难恢复场景中使用这些。
- **TTL 和传播**：了解 TTL 控制 DNS 解析器缓存记录的时长。短 TTL = 更快的变更。考试场景："团队更新了 DNS 但用户仍然访问旧服务器" → TTL 太高。
- **私有托管区域**：Route 53 可以创建只在 VPC 内部解析的 DNS 记录。考试将其用于内部服务发现（例如 `database.internal` 解析为私有 RDS 端点）。
- Route 53 是**全局的**——它不部署在某个区域。创建托管区域时不需要选择区域。

**练习 2——考试练习**

*场景*：一家媒体公司从两个 AWS 区域运营网站：`us-east-1`（主）和 `eu-west-1`（次）。团队希望在主区域变得不可用时，流量自动路由到 `eu-west-1`。公司还希望在不实际关闭主区域的情况下验证此故障转移机制是否正常工作。

哪种 Route 53 配置*最能*满足这些需求？

A) 加权路由，`us-east-1` 权重100%，`eu-west-1` 权重0%  
B) 基于延迟的路由，在两个端点上有健康检查  
C) 故障转移路由，在主端点上有健康检查，次要记录指向 `eu-west-1`  
D) 地理位置路由，北美指向 `us-east-1`，欧洲指向 `eu-west-1`

**提示 1**：需求是当主节点宕机时自动故障转移。哪种路由策略正是为此设计的？

**提示 2**："不关闭主区域测试"——健康检查可以手动设置为"不健康"进行测试。

**提示 3**：基于延迟的路由优化速度，不是故障转移。

**答案**：C

**解析**：故障转移路由正是为这种使用案例设计的。主记录指向 `us-east-1` 并有健康检查。次要记录指向 `eu-west-1`。如果健康检查失败，Route 53 自动返回次要记录。健康检查可以手动强制失败进行测试，而不会实际中断主区域。

**为什么不是 A？** 权重路由100%/0% 实际上是静态的——当主节点失败时它不会自动切换。

**为什么不是 B？** 基于延迟的路由为每个用户选择最快的端点。它不会自动根据健康状况排除某个区域——如果延迟更优，它仍然会路由一些流量到不健康的 `us-east-1`。

**为什么不是 D？** 地理位置路由按用户位置路由，而不是端点健康状况。即使 `us-east-1` 宕机，欧洲用户也会被困在 `eu-west-1`，而北美用户即使 `us-east-1` 宕机也不会故障转移到 `eu-west-1`。
