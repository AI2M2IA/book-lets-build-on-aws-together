# 第13章：到处都快

一张照片从弗吉尼亚的服务器传输到西雅图的手机，需要穿越大约4400公里的光纤电缆。以三分之二光速计算，这大约是25毫秒的纯物理延迟——不可避免、不可协商，烙印在宇宙定律中。

再加上往返时间。再加上处理时间。浏览器还没开始渲染，80毫秒已经过去了。

`eatnimbus.com` 上线了。Leo 检查了西海岸用户的延迟指标：每次请求80-100毫秒。这听起来很小，但它会累积。

加载菜单：90毫秒。加载餐厅列表：80毫秒。加载餐厅照片：200毫秒（图片很大）。用户能够下单之前的总时间：网络连接良好的情况下超过半秒。

"物理是问题所在，" Leo 说。"服务器在弗吉尼亚。用户在西海岸。"

"那就把服务器移到西海岸，" Tom 说。

"那要花钱。"

"多少钱？"

"很多。而且会带来一个全新的问题：让东海岸数据库和西海岸数据库保持同步。"

Priya 从她的笔记本上抬起头。"或者我们不移动服务器。我们移动*内容*。"

**预存仓库类比**

想象亚马逊这家零售商，不是云公司。他们在一个地方有一个巨大的仓库，里面有每一件产品。如果他们从那一个仓库发出每个订单，在遥远城市的客户要等好几天。

相反，亚马逊在主要人口中心附近设有配送中心。当一个产品很受欢迎时，他们预先在那些本地仓库备货。西雅图的客户订购一本书，它从本地配送中心发货——不是从弗吉尼亚。

这就是**内容分发网络（CDN）**：一个地理分布的服务器网络，将你内容的副本缓存在靠近用户的地方。

当西雅图的用户请求你的主页时，CDN 从西雅图的服务器提供。不是弗吉尼亚。请求从未跨越整个国家。

**认识 CloudFront**

Amazon CloudFront 是 AWS 的 CDN。它通过一个遍布全球城市的**边缘节点**网络运行——截至本文撰写时，有90多个城市中超过500个边缘节点。

当你配置 CloudFront 时，你指定一个**源**：你实际内容的来源。你的源可能是：

- S3 桶（静态文件：图片、CSS、JavaScript、PDF）
- 应用负载均衡器（来自你应用程序的动态内容）
- EC2 实例
- 互联网上任何地方的 HTTP 服务器

CloudFront 坐在你的源前面。请求在最近的边缘节点进入。如果边缘节点缓存了内容，它立即返回。如果没有（*缓存未命中*），它从你的源获取，缓存，然后返回。

**CloudFront 缓存如何工作**

任何内容的第一个请求总是缓存未命中——它去到源。每个后续请求都命中边缘节点的缓存。

对于 Nimbus，菜单照片是完美的 CloudFront 候选。餐厅照片变化不频繁（可能在餐厅更新他们的资料时才更新）。有了 CloudFront：

1. 西雅图的用户请求 `images.eatnimbus.com/restaurant-047/photo.jpg`
2. CloudFront 检查西雅图的边缘节点——还没有缓存（缓存未命中）
3. CloudFront 从 us-east-1 的 S3 获取（约80毫秒）
4. CloudFront 将照片存储在西雅图的边缘缓存中
5. 西雅图的下一个用户请求同一张照片
6. CloudFront 从本地边缘缓存提供（约5毫秒）

第一个请求同样受到80毫秒的惩罚。但来自同一城市的第一千个请求只需要5毫秒。

**Cache-Control 头**和 CloudFront 中的 **TTL 设置**决定内容在边缘缓存的时间。图片文件可以缓存数小时或数天。HTML 页面（更频繁变化）可能缓存几分钟或几秒钟。

**动态内容：CloudFront 不只是用来缓存**

"但我们的 API 响应呢？" Leo 问。"那些是动态的——它们因用户、因请求而异。你无法缓存一个订单历史页面。"

没错。但 CloudFront 对动态内容仍然有帮助。

即使内容无法缓存，CloudFront 也通过 AWS 的私有骨干网络——全球连接 AWS 基础设施的高速光纤——将请求从边缘节点路由到源。这比在公共互联网上路由更快、更可靠，因为公共互联网的流量可能在多个运营商之间跳转。

结果：即使是动态请求，通过 CloudFront 也比直接访问公网上的源快20-40%。不是因为缓存，而是因为网络路径。

此外，CloudFront 还提供：

**SSL/TLS 终止**：CloudFront 在边缘处理 HTTPS。用户和 CloudFront 之间的连接是加密的。CloudFront 可以通过内部 HTTP 连接到你的源（减少源的负载）或 HTTPS（用于端到端加密）。

**DDoS 保护**：CloudFront 与 AWS Shield 标准版集成。分散在数百个边缘节点的流量意味着攻击被边缘吸收，而不是直接打击你的源。

**地理限制**：阻止特定国家的访问。如果 Nimbus 只在某些市场有运营许可证，CloudFront 可以在边缘执行这一限制，请求甚至不会到达你的服务器。

**CloudFront 行为：精细的缓存规则**

CloudFront 发行版可以有多个**行为**——基于 URL 模式的路由规则。

对于 Nimbus：

- `/images/*` → 在边缘缓存7天（照片不经常变化）
- `/static/*` → 在边缘缓存30天（带版本文件名的 CSS 和 JavaScript）
- `/api/*` → 不缓存；直接转发到负载均衡器
- `/*` → 缓存5分钟（HTML 页面）

这让 CloudFront 变得聪明：积极缓存稳定的内容，直通动态的内容。

**源访问控制：用 CloudFront 保护 S3**

如果你的 S3 桶包含只应通过 CloudFront 提供的私有内容（而不是直接访问），你可以使用**源访问控制（OAC）**来确保 S3 拒绝不来自 CloudFront 的请求。

这样：

- `d1234abcd.cloudfront.net/image.jpg` — 提供（CloudFront 有权限）
- `nimbus-assets.s3.amazonaws.com/image.jpg` — 阻止（直接 S3 访问被拒绝）

你的内容只能通过你的发行版访问，应用你的缓存规则和安全设置。

## 优势与局限性

**CloudFront 为什么强大**：

- 90多个城市的边缘节点——大多数用户从小于20毫秒的距离获取内容
- 第一次缓存后静态内容在个位数毫秒内提供
- 显著减少源的负载（重复流量永远不会到达你的服务器）
- 与 AWS Shield、WAF 和 Certificate Manager 集成
- 不需要容量规划——CloudFront 自动扩展

**事情变得复杂的地方**：

- 缓存的内容可能过时——使缓存失效需要花钱（每1000个路径0.005美元）
- Cache-Control 头必须在源正确设置——错误会导致内容过时
- 动态内容受益于路由优化，但不受益于缓存
- 调试缓存行为（什么在哪里缓存、缓存多长时间）需要理解多个层面：源头部、CloudFront TTL 设置、行为规则
- 通过 CloudFront 传出的数据传输是要收费的，尽管比标准数据传输费用低

## 摘要

- **CDN** 在靠近用户的边缘节点缓存你内容的副本——减少延迟和源的负载。
- **CloudFront** 是 AWS 的 CDN，有全球500多个边缘节点。
- 缓存未命中从**源**获取（S3、ALB、EC2）。缓存命中从边缘提供——毫秒级，而不是数百毫秒。
- **行为**让你为不同的 URL 模式设置不同的缓存规则。
- 动态内容不被缓存，但 CloudFront 通过 AWS 的私有骨干网络仍然提高了性能。
- **源访问控制**限制直接 S3 访问——内容只能通过 CloudFront 提供。
- 与 Shield（DDoS）、WAF（应用防火墙）和 ACM（SSL 证书）集成。

## 考试技巧

*SAA-C03 领域：设计高性能架构（领域3，任务3.4）*

- **CloudFront + S3**：全球提供静态网站的经典考试模式。S3 桶作为源，CloudFront 作为 CDN，源访问控制防止直接 S3 访问。
- **边缘节点 vs 区域 vs AZ**：边缘节点更多，只用于缓存/CDN 目的。它们与 AZ（运行你计算的地方）不同。
- **缓存失效**：创建 `/images/*` 失效来强制 CloudFront 获取新内容。要收费——考试可能要求成本效益的替代方案：版本化 URL（`image-v2.jpg` 而不是 `image.jpg`），自然绕过缓存。
- **TTL 控制**：源的 `Cache-Control: max-age=3600` 设置1小时的缓存 TTL。CloudFront 遵循这些头。
- **CloudFront Functions vs Lambda@Edge**：CloudFront Functions 在边缘运行，用于轻量级请求/响应操作（亚毫秒）。Lambda@Edge 在边缘节点运行你的 Lambda 代码，用于更重的处理。考试按使用案例复杂性区分它们。
- **签名 URL 和签名 Cookie**：控制谁可以通过 CloudFront 访问内容。签名 URL 给予对特定文件的访问权限；签名 Cookie 给予对多个文件的访问权限。考试将这些用于"付费订阅内容"。

**练习 2——考试练习**

*场景*：一家软件公司向全球客户从 S3 桶分发大型安装文件（每个约2GB）。亚洲客户的下载速度很慢。团队希望在不将 S3 桶复制到多个区域的情况下改善性能。他们还需要确保只有付费客户才能下载安装文件。

哪种解决方案*最能*满足这些需求？

A) 在桶上启用 S3 传输加速，并为付费客户生成预签名 URL  
B) 使用 CloudFront，以 S3 桶为源，启用源访问控制，并为付费客户使用 CloudFront 签名 URL  
C) 在每个 AWS 区域创建一个 S3 桶，并使用 Route 53 地理位置路由将客户引导到最近的桶  
D) 在每个区域使用带 EC2 实例的应用负载均衡器来提供安装文件

**提示 1**：需求是在*不*复制桶的情况下改善全球性能。哪个选项不需要多个桶？

**提示 2**：哪个服务专门控制谁可以访问通过 CloudFront 提供的内容？

**提示 3**：S3 传输加速针对长距离*上传*到 S3 进行了优化。用于*从* S3 全球分发内容给最终用户，CloudFront 是正确的工具。

**答案**：B

**解析**：CloudFront 在首次下载后在全球边缘节点缓存安装文件。同一区域的后续下载来自边缘——比从 us-east-1 的 S3 跨越太平洋快得多。源访问控制确保 S3 桶只能通过 CloudFront 访问。签名 URL 将访问限制为付费客户。

**为什么不是 A？** S3 传输加速针对长距离*上传*到 S3 进行了优化——不是*从* S3 向全球受众分发内容。对此，CloudFront 是正确的工具。预签名 URL 控制访问，但不改善全球性能。

**为什么不是 C？** 在每个区域创建 S3 桶对性能确实有效，但违反了避免复制的需求。它还需要跨桶的数据同步策略。

**为什么不是 D？** 在每个区域用 EC2 实例的负载均衡器比 CloudFront 昂贵得多，而且需要在多个区域管理服务器。

Priya 在部署后观察 CloudFront 指标。

缓存命中率：83%。

"那意味着什么？" Tom 问。

"意味着83%的用户从靠近他们的边缘节点获取内容，而不是从 us-east-1。"
