**预存仓库类比**

想象亚马逊这家零售商，不是那家云公司。他们在一个地方有一个巨大的仓库，里面有每一件产品。如果他们从那一个仓库发出每个订单，遥远城市的客户要等好几天。

相反，亚马逊在主要人口中心附近设有配送中心。当一个产品很受欢迎时，他们会预先在那些本地仓库备货。西雅图的客户订购一本书时，它从本地配送中心发货——而不是从大陆另一端。

这就是**内容分发网络（CDN）**：一个地理分布的服务器网络，把你内容的副本缓存在靠近用户的地方。

当波士顿的用户请求你的主页时，CDN 从波士顿的服务器提供它。不是俄勒冈。请求从未跨越整个国家。

**认识 CloudFront**

Amazon CloudFront 是 AWS 的 CDN。它通过一个全球**边缘节点**网络运行——部署在世界各地城市的缓存服务器。截至本文撰写时，在 100 多个城市有超过 750 个接入点。

当你配置 CloudFront 时，你指定一个**源（origin）**：你实际内容的来源。你的源可能是：

- 一个 S3 桶（静态文件：图片、CSS、JavaScript、PDF）
- 一个应用负载均衡器（来自你应用程序的动态内容）
- 一个 EC2 实例
- 互联网上任何地方的 HTTP 服务器

CloudFront 坐在你的源前面。请求在最近的边缘节点进入。如果边缘节点缓存了内容，它立即返回。如果没有（*缓存未命中*），它从你的源获取，缓存，然后返回。

**CloudFront 缓存如何工作**

任何一份内容的第一个请求总是缓存未命中——它会去到源。之后的每个请求都命中边缘节点的缓存。

对于 Nimbus，菜单照片是完美的 CloudFront 候选。餐厅照片变化不频繁（可能在餐厅更新资料时才更新）。有了 CloudFront：

1. 波士顿的用户请求 `images.eatnimbus.com/restaurant-047/photo.jpg`
2. CloudFront 检查波士顿的边缘节点——还没有缓存（缓存未命中）
3. CloudFront 从 us-west-2 的 S3 获取（约 80 毫秒）
4. CloudFront 把照片存储在波士顿的边缘节点
5. 波士顿的下一个用户请求同一张照片
6. CloudFront 从本地边缘缓存提供（约 5 毫秒）

第一个请求同样承受 80 毫秒的代价。但来自同一城市的第一千个请求只需要 5 毫秒。

CloudFront 中的 **Cache-Control 头**和 **TTL 设置**决定内容在边缘缓存多长时间。图片文件可以缓存数小时或数天。HTML 页面（变化更频繁）可能缓存几分钟或几秒钟。

你可能会想：为什么不干脆把整个应用程序托管在多个区域，而要用 CDN？如果数据在俄勒冈，为什么不在纽约、东京和圣保罗各放一份完整副本？可以。但那意味着要让多个数据库保持同步，要同时管理跨区域的部署，要处理区域之间意见不一致的脑裂场景。对于静态和半静态内容，CDN 是一个简单得多的答案：一个源，许多在边缘的缓存副本。只有当你真正需要在用户附近进行计算或数据库操作时，才去引入多区域的复杂性——对大多数内容来说，边缘缓存就够了。

"等等——*为什么*要这么做？"Maya 问。"为什么把缓存放在边缘，而不是在俄勒冈加一个更大的 ElastiCache 集群？"

"因为物理仍然是问题所在，"Priya 说。"即使俄勒冈在一毫秒内响应，那个响应仍然得传到波士顿。往返时间最少 70 毫秒——光速可不管我们的服务器有多快。边缘缓存把答案移到了问题的旁边。"

**动态内容：CloudFront 不只是用来缓存**

"但我们的 API 响应呢？"Leo 问。"那些是动态的——它们因用户、因请求而异。你没法缓存一个订单历史页面。"

没错。但 CloudFront 对动态内容仍然有帮助。

即使内容无法缓存，CloudFront 也会把请求从边缘节点经由 AWS 的私有骨干网络——全球连接 AWS 基础设施的高速光纤——路由到源。这比经由公共互联网路由更快、更可靠，因为公共互联网的流量可能在多个运营商之间跳转。

结果：动态请求通过 CloudFront 仍然比经公共互联网直连源快 20-40%。不是因为缓存，而是因为网络路径。

"这说不通啊，"Maya 说。"如果 API 响应仍然得从俄勒冈传到边缘再传到波士顿，那怎么会比从俄勒冈直接到波士顿更快？"

"两个原因，"Priya 说。"第一，AWS 的私有骨干网比公共互联网更快、更可靠。公共互联网流量要经过多个运营商，每个都增加自己的延迟和不确定性。骨干网是直达的低延迟光纤。第二，SSL 终止发生在边缘。用户与最近的 CloudFront 边缘节点建立 TLS 连接——握手很快。然后 CloudFront 维护一条到源的持久的、预先建立的连接。两条短距离连接，而不是一条长距离连接。"

"所以即使对于不缓存的内容，CloudFront 也能从连接开销上省下时间，"Leo 说。

"通常是百分之十到四十。没有缓存那么戏剧化。但是实打实的。"

此外，CloudFront 还提供：

**SSL/TLS 终止**：CloudFront 在边缘处理 HTTPS。用户和 CloudFront 之间的连接是加密的。CloudFront 可以在内部通过 HTTP 连接到你的源（减少源的负载），或者通过 HTTPS（用于端到端加密）。

**DDoS 防护**：CloudFront 与 AWS Shield Standard 集成。流量分散在数百个边缘节点上，意味着攻击在边缘被吸收，而不是猛击你的源。

**地理限制**：阻止来自特定国家的访问。如果 Nimbus 只在某些市场有运营许可，CloudFront 可以在边缘执行这一限制，请求根本不会到达你的服务器。

**那如果有人试图通过 CDN 闯进来呢？**Priya 问。"缓存投毒——如果有人设法把恶意内容注入边缘缓存怎么办？"

"CloudFront 有缓存键控制，"Leo 说。"你精确定义哪些属性决定两个请求是否得到同一份缓存响应。请求头、查询字符串、Cookie。攻击者无法在不匹配确切缓存键的情况下注入一份不同的缓存响应。"

"而且 Origin Access Control 意味着 S3 桶不会响应任何不经过 CloudFront 的请求，"Priya 说。"一个攻击面，而不是两个。"

**CloudFront 行为：精细的缓存规则**

一个 CloudFront 分配可以有多个**行为（behaviors）**——基于 URL 模式的路由规则。

对于 Nimbus：

- `/images/*` → 在边缘缓存 7 天（照片不常变化）
- `/static/*` → 在边缘缓存 30 天（带版本化文件名的 CSS 和 JavaScript）
- `/api/*` → 不缓存；直接转发到负载均衡器
- `/*` → 缓存 5 分钟（HTML 页面）

这让 CloudFront 变得聪明：积极缓存稳定的内容，直通动态的内容。

行为按照从最具体到最不具体的顺序进行匹配。`/images/hero.jpg` 会先匹配 `/images/*`，然后才会匹配 `/*`。最底部的兜底规则 `/*` 是默认值——它适用于任何没有匹配到更具体模式的请求。

"如果我们想对已登录用户和未登录用户使用不同的缓存策略呢？"Priya 问。"同一个 URL 可能根据用户是否登录返回不同的内容。"

"那你就把会话 Cookie 包含进缓存键里，"Leo 说。"但那意味着每个登录用户都有自己的缓存条目。对于需要认证的内容，你的命中率会崩盘。"

"这就是为什么要在 URL 层面把认证内容和公开内容分开，"Priya 说。"任何需要认证的东西都放在 `/app/*` 下，不缓存。公开内容放在 `/browse/*` 下，积极缓存。一条清晰的边界。"

教训：当你的 URL 结构反映缓存意图时，CloudFront 工作得最好。指向完全公开静态数据的 URL，看起来应该和返回个性化动态数据的 URL 不一样。如果它们在 CloudFront 眼里长得一样，那要么缓存失效了，要么会把错误的内容提供给错误的人。

Leo 花了一个周末重构了 Nimbus 的 URL 方案。浏览端点移到了 `/browse/`。API 端点移到了 `/api/`。认证后的应用界面移到了 `/app/`。三个行为，三条清晰的缓存策略，零歧义。

"这算是一次不小的重构，"他说。

"这是正确的结构，"Priya 说。"你迟早会需要它。"

**Origin Access Control：用 CloudFront 保护 S3**

如果你的 S3 桶包含只应通过 CloudFront 提供（而不能被直接访问）的私有内容，你可以使用 **Origin Access Control（OAC）**来确保 S3 拒绝不是来自 CloudFront 的请求。

这样：

- `d1234abcd.cloudfront.net/image.jpg` → 提供（CloudFront 有权限）
- `nimbus-assets.s3.amazonaws.com/image.jpg` → 阻止（直接 S3 访问被拒绝）

你的内容只能通过你的分配访问，你的缓存规则和安全设置都会生效。

**过期照片事件**

112 号餐厅——东区那家哥伦比亚餐厅——在一个周四早上给客服发了邮件。一位顾客抱怨说，餐厅的主图照片仍然显示的是旧店面，尽管店主两天前已经上传了新照片。

Leo 调出了 CloudFront 分配的设置。

`/images/*` 的行为设置了 7 天的 TTL。餐厅合作伙伴门户两天前上传了新照片，替换了同一个 S3 键路径下的文件：`restaurant-112/hero.jpg`。旧文件已经从 S3 上消失了。但 CloudFront 仍然在过去 7 天内取过这个文件的每个边缘节点上从缓存提供它。

"我们在源头改了内容，"Leo 说。"但 CloudFront 不知道。它有一份缓存副本，而且接下来七天都不会去检查。"

"我已经部署了——哦。"他原本以为替换 S3 文件会自动刷新 CloudFront 缓存。并不会。CloudFront 没有任何机制能检测到某个 S3 键上的内容发生了变化——它只是一直提供它缓存的东西，直到 TTL 过期。

两个选项：

**选项一：失效（Invalidation）。**向 CloudFront 发送针对 `/images/restaurant-112/hero.jpg` 的失效请求。CloudFront 在所有边缘节点把那个路径标记为过期。下一个针对该路径的请求会从 S3 获取新内容。费用：每月前 1,000 个失效路径免费；超过之后，*每个路径* 0.005 美元。对一个文件来说，免费。但在批量更新中让数千个文件失效，成本会累积起来。

**选项二：版本化文件名。**不叫 `hero.jpg`，而把文件命名为 `hero-v2.jpg`。更新数据库中的引用。CloudFront 没有 `hero-v2.jpg` 的缓存条目——第一个请求会从 S3 获取它，用户立即看到新图。旧的 `hero.jpg` 仍然在缓存中，但已经没有任何地方引用它了。它会在七天后自然过期。

"对于用户上传的内容，"Priya 说，"版本化命名是正确的模式。在文件名里加上哈希或时间戳。每次新上传都是一个新的缓存条目。没有失效成本，没有过期内容。"

Leo 更新了合作伙伴门户。新上传的文件现在会存储为 `hero-{timestamp}.jpg`。数据库记录会更新为新路径。旧的缓存路径就无关紧要了。

"那部署的情况呢？"Maya 问。"当我们推送新版本的应用、JavaScript 发生变化时？"

"同样的原则，"Priya 说。"像 Webpack 这样的构建工具会输出带哈希的文件名：`app.a3b9c2d4.js`。部署新版本时哈希会变：`app.f7e1b3c5.js`。CloudFront 从缓存里同时提供两个——老用户拿到旧文件，新用户拿到新文件。没有失效操作，没有协调问题。"

"HTML 页面引用当前的哈希，"Leo 说。"所以新用户得到带新 JS 哈希的新 HTML，CDN 提供正确的文件。"

"标准做法，"Priya 确认道。

**用真实数字看延迟**

Tom 一直在从三个城市进行延迟测量。

| 地点 | 不用 CloudFront | 使用 CloudFront | 改善 |
|---|---|---|---|
| 西雅图 | 15ms | 12ms | 20% |
| 纽约 | 80ms | 10ms | 88% |
| 圣保罗 | 290ms | 35ms | 88% |
| 东京 | 260ms | 28ms | 89% |

"物理问题最严重的地方，改善也最大，"Tom 观察道。"圣保罗到俄勒冈要两百多毫秒。光是开始对话就要超过四分之一秒。"

"而且第二次之后，内容根本不需要再跑到圣保罗去取，"Leo 说。"圣保罗的第一个用户从俄勒冈获取并在本地缓存。之后的每个用户都是三十五毫秒。"

"圣保罗的第一个用户承担成本，"Tom 说。"其他所有人受益。"

"这就是 CDN 的工作方式，"Priya 说。"第一个请求填充缓存。之后每次缓存命中几乎是免费的。"

这对全球化产品的意义重大。没有 CloudFront，东京的用户要为你的主图等待 260 毫秒——因为物理：光纤电缆和光速。有了 CloudFront，你把那张图片的副本放在东京，物理问题基本上就消失了。

**多个源：ALB 和 S3 一起用**

"我们的图片在 S3 上，API 在负载均衡器上，"Maya 说。"我们需要两个 CloudFront 分配吗？"

"不需要，"Leo 说。"一个分配，多个源。"

单个 CloudFront 分配可以把不同的 URL 模式路由到不同的源。这就是多源模式：

```
eatnimbus.com/*         → Origin: ALB in us-west-2 (dynamic content)
eatnimbus.com/images/*  → Origin: S3 bucket (static images)
eatnimbus.com/static/*  → Origin: S3 bucket (CSS, JS, fonts)
```

CloudFront 按照具体程度的顺序评估行为。请求 `/images/hero.jpg` 匹配 `/images/*` 行为，去往 S3。请求 `/api/orders` 匹配兜底的 `/*`，去往 ALB。

好处：一个域名，一张 SSL 证书，一个 CloudFront 分配，多个后端。用户看到的是一个统一的域名。路由对他们是不可见的。

有一个运维细节同时也是必考事实：那张 SSL 证书来自 AWS Certificate Manager（ACM），而**供 CloudFront 使用的证书必须在 `us-east-1` 申请或导入**——无论你的源在哪里。CloudFront 是一个控制平面位于 us-east-1 的全局服务；放在 us-west-2 的证书根本不会出现在分配的下拉列表里。（对于 ALB 这样的区域性服务，证书放在 ALB 自己所在的区域。）

"那 ALB 不直接面向公网？"Priya 问。

"只有 CloudFront 跟 ALB 对话，"Leo 说。"我们把 ALB 的安全组限制为 CloudFront 的托管前缀列表。来自互联网的对 ALB 的直接连接被阻止。"

"所以到达应用程序的唯一途径是通过 CloudFront。"

"这意味着 WAF 规则、SSL 终止和 DDoS 防护在流量到达我们之前就已经对全部流量生效。"

**CloudFront Functions vs Lambda@Edge**

"我们想过如果需要在边缘重写 URL 该怎么办吗？"Priya 问。"或者给每个响应添加一个安全头？"

"我们不能在应用程序里做吗？"Leo 问。

"可以。但如果它发生在边缘——在 CloudFront 从缓存提供之前——我们就省下了一次到源的往返。"

CloudFront 支持两种在边缘运行代码的机制：

**CloudFront Functions** 是在每个边缘节点运行的轻量级 JavaScript 函数。它们在亚毫秒时间内执行，每秒处理数百万个请求，专为简单转换设计：URL 重写、头操作、查询字符串规范化、简单重定向。它们可以在查看者请求和查看者响应上运行（从用户的角度看，就是缓存之前和之后）。它们不能发起网络调用。费用：每百万次调用 0.10 美元。

**Lambda@Edge** 在 CloudFront 的区域性边缘节点（不是每个接入点，而是全球数十个主要节点）运行真正的 Lambda 函数。Lambda@Edge 可以发起网络调用、访问数据库、生成动态响应、做复杂的认证逻辑。它可以在查看者请求、源请求、源响应和查看者响应上运行——在请求生命周期中给你四个介入点。费用：高于 CloudFront Functions，按请求次数和时长计费。

心智模型：

| 使用案例 | 工具 |
|---|---|
| 把 `/old-path` 重写为 `/new-path` | CloudFront Functions |
| 添加 `Strict-Transport-Security` 头 | CloudFront Functions |
| 在缓存查找之前规范化查询字符串 | CloudFront Functions |
| A/B 测试：在查看者请求上分配测试 Cookie | CloudFront Functions |
| A/B 测试：把 10% 的用户路由到不同的源 | Lambda@Edge（源请求——CloudFront Functions 无法更改源） |
| 验证 JWT 令牌（需要加密库） | Lambda@Edge |
| 在边缘从数据库获取个性化内容 | Lambda@Edge |
| 在边缘按需生成图片缩略图 | Lambda@Edge |

对于 Nimbus：他们用一个 CloudFront Function 给每个响应添加安全头——`Strict-Transport-Security`、`X-Content-Type-Options`、`X-Frame-Options`。二十几行 JavaScript。亚毫秒执行。不需要到源的往返。

**价格等级：选择哪些边缘节点**

"我们想过这个东西在规模上来之后要花多少钱吗？"Tom 一边滚动 CloudFront 定价页面一边问。

"那每月要花多少钱？"在这里其实是两个问题。第一个：CloudFront 怎么收费？第二个：你需要全世界的每个边缘节点吗？

CloudFront 的数据传输定价因区域而异。从北美和欧洲的边缘节点提供的流量最便宜。从南美、亚太、澳大利亚和印度的流量更贵——因为那里的基础设施成本更高。

AWS 让你为分配选择一个**价格等级（price class）**：

- **Price Class All**：使用全球所有边缘节点。到处都是最佳性能。北美和欧洲之外区域的数据传输成本最高。
- **Price Class 200**：使用大多数边缘节点（北美、欧洲、亚洲、中东、非洲）。排除最昂贵的南美节点和部分大洋洲节点。
- **Price Class 100**：只使用北美和欧洲的边缘节点。最便宜。圣保罗、东京和悉尼的用户仍然能得到服务——但是来自北美或欧洲的边缘节点，而不是离他们最近的那个。

"所以如果我们选 Price Class 100，"Tom 说，"圣保罗的用户会从……迈阿密？纽约？得到服务？"

"从最近的被包含的边缘节点。可能是 50 毫秒，而不是直连俄勒冈的 230 毫秒，"Priya 说。"仍然是有意义的改善。但不如 Price Class All 好。"

"那成本差异呢？"

"南美的数据传出成本大约是北美的两倍。对于一家还在积累流量的初创公司，Price Class 200 是一个合理的折中——你以低于 Price Class All 的成本拿到了亚洲和欧洲，而且大多数用户都被覆盖了。"

"先从 200 开始，"Tom 说。"等我们有了每个区域的真实流量数据，再决定 All 值不值。"

正确的价格等级取决于你的用户在哪里。如果你在南美没有用户，为南美边缘节点付费就是纯粹的成本。如果你百分之二十的收入来自巴西，Price Class All 带来的性能提升大概率能收回成本。

**缓存键设计**

"我们想过两个不同用户请求同一个 URL 却得到不同内容时会发生什么吗？"Priya 问。

Leo 想了想。"个性化页面。"

"或者特定语言的页面。或者移动端和桌面端的版本。或者因 Cookie 而异的页面。"

默认情况下，CloudFront 只使用 URL 路径作为缓存键。两个对 `/browse` 的请求会得到同一份缓存响应，不管用户的语言偏好、设备类型或会话 Cookie 是什么。

如果你的应用程序根据查询字符串、请求头或 Cookie 提供不同的内容——并且你希望 CloudFront 分别缓存这些变体——你需要把这些属性包含进**缓存键**。

对于 Nimbus：

- `/browse?city=miami` 应该和 `/browse?city=boston` 分开缓存——不同的餐厅列表。把查询字符串包含进缓存键。
- 移动用户可能得到不同的布局。把一个规范化后的设备类型（从 `User-Agent` 头推导）包含进缓存键。
- `Accept-Language` 头决定页面用哪种语言渲染。把它包含进缓存键。

但要小心。你添加的每个缓存键属性都会产生更多的缓存变体。如果你包含完整的 `User-Agent` 字符串（它随浏览器版本、操作系统版本和补丁级别而变化），你实际上就破坏了缓存——每个用户的 User-Agent 都略有不同，于是每个请求都是缓存未命中。

纪律是：先规范化再缓存。把"iPhone 15 Pro Safari 17.4.1"简化为"mobile"。把所有接受的语言简化为你实际支持的两三种。只包含真正会改变响应的东西。

"你的缓存键越具体，"Leo 说，"命中率就越差。"

"而越泛化，"Priya 说，"就越可能把错误的内容提供给错误的用户。"

"所以缓存键设计和缓存里的其他一切是同一种权衡。"

"是的，"Priya 说。"永远是同一种权衡。"

## 当 CloudFront 不是答案时：Global Accelerator

Nimbus 移动应用有一个 Tom 默默观察了两个月的功能：实时订单状态。当顾客下单后，应用通过 WebSocket 保持连接，厨房的订单管理屏幕实时更新。没有刷新按钮。没有轮询。一条活跃的连接，在厨房标记某个菜品就绪的瞬间推送更新。

"这是用 WebSocket 做的，"一天早上，Tom 看着延迟指标说。"圣保罗用户的连接建立要 340 毫秒。不对劲。"

"CloudFront 不缓存 WebSocket 连接，"Leo 说。"它代理它们——直通到源。没有缓存收益。"

"对。那为什么还是慢？"

"因为 WebSocket 仍然要经由公共互联网从圣保罗连到我们在俄勒冈的服务器，"Leo 说。"CloudFront 是有帮助的，因为它在边缘终止 TLS 握手，然后走 AWS 骨干网到源。但对于一条持久的 WebSocket 连接，那仍然是一条长距离连接。"

"有一个服务正是为这个问题而生，"Priya 说。

**AWS Global Accelerator** 不是 CDN。它什么都不缓存。它不从边缘节点提供内容。它做的是给你两个静态 Anycast IP 地址，这些地址同时从所有 AWS 边缘节点向全球通告——然后让你用户的流量走 AWS 的私有骨干网，而不是公共互联网。

当圣保罗的一位顾客打开 Nimbus 应用时，他们的设备连接到最近的 AWS 边缘节点（可能就在圣保罗本地）。从那个边缘节点开始，流量经由 AWS 私有的、受监控的、经过优化的光纤网络传输到 Nimbus 在俄勒冈的服务器——而不是经由公共互联网，在那里数据包要在不可预测的运营商和路由跳数之间弹跳。

公共互联网不是为延迟设计的。它是为韧性设计的——数据包可以走任何可用路径。AWS 的骨干网设计思路不同：直达、低拥塞、处于 AWS 的运维控制之下。

Tom 对比测试了差异。

| 路由 | 延迟（圣保罗到俄勒冈） |
|---|---|
| 公共互联网 | 340ms |
| 经由 Global Accelerator | 180ms |

减少了 47%。不是来自缓存——来自一条更好的网络路径。

"那我们为什么不干脆把所有东西都用 CloudFront？"Maya 问。"CloudFront 对动态内容已经走 AWS 骨干网了。"

"CloudFront 只支持 HTTP 和 HTTPS，"Priya 说。"WebSocket 能配合 CloudFront 工作，但只能通过 HTTP 升级。而我们的一些协议——比如 IoT 传感器数据——是纯 TCP 或 UDP。CloudFront 不处理那些。Global Accelerator 是协议无关的。TCP、UDP、WebSocket，什么都行。它搬运的是数据包，不是 HTTP 请求。"

还有一个差异，Priya 记在了她的安全文档里。

"Global Accelerator 给我们两个静态 Anycast IP，"她说。"这些 IP 永远不变。这意味着我们可以把它们写进安全策略，加进合作伙伴的白名单，加进防火墙规则。CloudFront 的 IP 地址会随时间变化——它们由 AWS 管理，不是固定的。"

"故障转移呢？"Leo 问。

"即时，"Priya 说。"如果我们 us-west-2 的应用出了问题，Global Accelerator 可以在 30 秒之内把流量切到 us-east-1 的备用部署——而用户连接的 IP 地址不变。通过 Route 53 的 DNS 故障转移要 60-300 秒，取决于 TTL。Global Accelerator 更快。"

**CloudFront vs Global Accelerator——心智模型：**

CloudFront 通过缓存改善交付。它为 HTTP/HTTPS 而生，当内容可以缓存在用户附近时收益最大——静态文件、图片、JavaScript。当内容无法缓存时，CloudFront 仍然通过骨干网路由有所帮助，但改善幅度较小。

Global Accelerator 通过路由改善交付。它不搬运内容。它什么都不缓存。收益适用于每一个数据包——无论缓存与否、是不是 HTTP、静态还是动态。两个静态 IP 全球通用。故障转移近乎即时。CloudFront 不够用的使用案例——实时 WebSocket、基于 UDP 的协议、非 HTTP 流量、需要固定 IP 的全球应用——正是 Global Accelerator 大显身手的地方。

Tom 更新了 Nimbus 移动应用，让实时订单状态功能连接到 Global Accelerator 端点。圣保罗的 WebSocket 连接建立时间从 340 毫秒降到了 180 毫秒。厨房的更新依然感觉是即时的——因为现在，对北美以外的用户来说，它们真的是即时的。

## 优势与局限性

**CloudFront 为什么强大**：

- 100 多个城市里超过 750 个接入点——大多数用户从不到 20 毫秒的距离获取内容
- 第一次缓存之后，静态内容在个位数毫秒内送达
- 显著减少源的负载（重复流量永远不会到达你的服务器）
- 与 AWS Shield、WAF 和 Certificate Manager 集成
- 不需要容量规划——CloudFront 自动扩展
- 多源分配可以从一个域名把不同路径路由到不同后端
- CloudFront Functions 以亚毫秒延迟处理轻量级边缘逻辑

**事情变得复杂的地方**：

- 缓存的内容可能过时——让缓存失效要花钱（每月前 1,000 个免费路径之后，每个路径 0.005 美元）。改用版本化文件名。
- Cache-Control 头必须在源正确设置——出错会导致内容过期
- 动态内容受益于路由优化，但不受益于缓存
- 调试缓存行为（什么内容缓存在哪里、缓存多久）需要理解多个层面：源的头、CloudFront TTL 设置、行为规则
- 通过 CloudFront 的数据传出要收费，不过低于标准数据传输费用
- 缓存键设计需要仔细斟酌——太具体会破坏缓存，太泛化会提供错误内容

## 摘要

CloudFront 没有改变物理。光仍然以同样的速度传播。但它改变了答案存放的位置——对大多数用户来说，答案现在只有几毫秒之遥，而不是几百毫秒。部署后的缓存命中率：83%。这意味着每一百万个请求中有 83 万个根本不会到达源服务器。圣保罗的用户从 290 毫秒降到了 35 毫秒。东京的用户从 260 降到了 28。

- **CDN** 在靠近用户的边缘节点缓存你内容的副本——减少延迟和源的负载。
- **CloudFront** 是 AWS 的 CDN，全球有 750 多个接入点。
- 缓存未命中从**源**获取（S3、ALB、EC2）。缓存命中从边缘提供——毫秒级，而不是数百毫秒。
- **行为**让你为不同的 URL 模式设置不同的缓存规则。一个分配可以从 S3 提供 `/images/*`，从 ALB 提供 `/*`。
- 动态内容不被缓存，但 CloudFront 通过 AWS 的私有骨干网络仍然提升了性能。
- 用版本化文件名（如 `hero-v2.jpg`）代替失效操作来**避免过期内容**——更便宜也更可靠。
- **CloudFront Functions** 以亚毫秒速度处理轻量级边缘逻辑（头操作、URL 重写）。**Lambda@Edge** 处理需要网络调用的更重的处理。
- **价格等级**让你控制哪些边缘节点为你的流量服务——也就控制了你的数据传输成本。
- **缓存键设计**决定哪些请求属性会产生独立的缓存变体。键越具体 = 命中率越低。键越泛化 = 提供错误内容的风险越高。

## 考试技巧

*SAA-C03 领域：设计高性能架构（领域3，任务3.4）*

- **CloudFront + S3**：全球提供静态网站的经典考试模式。S3 桶作为源，CloudFront 作为 CDN，Origin Access Control 防止直接访问 S3。
- **边缘节点 vs 区域 vs AZ**：边缘节点数量更多，只为缓存/CDN 目的而存在。它们和 AZ（运行你的计算的地方）不是一回事。
- **缓存失效**：创建 `/images/*` 失效来强制 CloudFront 获取新内容。要收费——考试可能要求更具成本效益的替代方案：版本化 URL（`image-v2.jpg` 而不是 `image.jpg`），自然绕过缓存。
- **TTL 控制**：源上的 `Cache-Control: max-age=3600` 设置 1 小时的缓存 TTL。CloudFront 遵循这些头。最小 TTL、最大 TTL 和默认 TTL 也可以在分配的行为里设置。
- **CloudFront Functions vs Lambda@Edge**：CloudFront Functions 在边缘运行，用于轻量级请求/响应操作（亚毫秒）。Lambda@Edge 在区域性边缘节点运行你的 Lambda 代码，用于更重的处理。考试按使用案例的复杂程度区分它们。CloudFront Functions 不能发起网络调用；Lambda@Edge 可以。
- **签名 URL 和签名 Cookie**：控制谁可以通过 CloudFront 访问内容。签名 URL 授予对特定文件的访问；签名 Cookie 授予对多个文件的访问。考试把这些用于"付费订阅内容"。
- **价格等级**：考试可能问面向全球受众和面向北美/欧洲受众分别该选哪个价格等级。Price Class All = 最佳性能、最高成本。Price Class 100 = 只有北美和欧洲、成本最低。
- **缓存键**：默认缓存键是 URL。把查询字符串、请求头或 Cookie 加进缓存键会产生独立的缓存变体——但会提高缓存未命中率。考试可能给出内容因某个查询参数而异的场景，问该如何配置缓存。
- **源故障转移**：CloudFront 支持包含主源和备源的源组（origin group）。如果主源返回 5xx 错误，CloudFront 自动用备源重试。和 Route 53 故障转移不同——这发生在单个 CloudFront 分配内部。
- **多源行为**：单个分配可以把 `/images/*` 路由到 S3、把 `/*` 路由到 ALB。考试可能把它表述为"如何在不建两个分配的情况下从一个域名提供静态和动态内容"。
- **CloudFront vs Global Accelerator：**CloudFront = HTTP/HTTPS CDN，在边缘节点缓存内容，减少源负载，最适合静态和可缓存内容。Global Accelerator = 任何 TCP/UDP 协议，什么都不缓存，让流量走 AWS 私有骨干网，提供 2 个静态 Anycast IP，支持近乎即时的区域故障转移。考试触发词："改善非 HTTP 流量的延迟"或"全球应用需要静态 IP"或"全球用户的 WebSocket 性能"或"比 DNS 更快的区域故障转移" → Global Accelerator。"以低延迟向全球提供静态文件" → CloudFront。

哪种解决方案最能满足这些需求？

A) 在桶上启用 S3 Transfer Acceleration，并为付费客户生成预签名 URL  
B) 使用 CloudFront，以 S3 桶为源，启用 Origin Access Control，并为付费客户使用 CloudFront 签名 URL  
C) 在每个 AWS 区域创建一个 S3 桶，并使用 Route 53 地理位置路由把客户引导到最近的桶  
D) 在每个区域使用带 EC2 实例的应用负载均衡器来提供安装文件

**提示 1**：需求是在*不*复制桶的情况下改善全球性能。哪个选项不需要多个桶？

**提示 2**：哪个机制专门控制谁可以访问通过 CloudFront 提供的内容？

**提示 3**：S3 Transfer Acceleration 针对长距离*上传*到 S3 进行了优化。要把内容*从* S3 分发给全球最终用户，CloudFront 才是正确的工具。

**答案**：B

**解析**：CloudFront 在首次下载后在全球边缘节点缓存安装文件。同一区域的后续下载来自边缘——比从 us-west-2 的 S3 跨越太平洋快得多。Origin Access Control 确保 S3 桶只能通过 CloudFront 访问。签名 URL 把访问限制为付费客户。

**为什么不是 A？** S3 Transfer Acceleration 针对长距离*上传到* S3 进行了优化——不是把内容*从* S3 分发给全球受众。对此，CloudFront 是正确的工具。预签名 URL 控制访问，但不改善全球性能。

**为什么不是 C？** 在每个区域创建 S3 桶对性能确实有效，但违背了避免复制的需求。它还需要跨桶的数据同步策略。

**为什么不是 D？** 在每个区域用负载均衡器加 EC2 实例比 CloudFront 昂贵得多，而且需要在多个区域管理服务器。
