**流量分析：账单到底是什么产生的**

"教训是，VPC 端点不是一次性的配置，"Tom 说，"每一个新 VPC、每一个新子网、每一种新的工作负载类型都需要做同样的检查。私有子网里任何东西的默认行为都是经由 NAT 路由。检查项是：这个工作负载是否会调用 S3、DynamoDB 或任何高流量的 AWS 服务？如果是，它有端点路由吗？"

至此，Tom 得到了开启这次分析的那个问题的答案。网络成本不是一个单一的问题。它是五个不同的问题，每个都有不同的解法。

**AWS 如何对数据传输收费**

AWS 的数据传输定价是不对称的：

**进入 AWS（入站）**：免费。你想上传多少数据都可以。

**从 AWS 出到互联网（出站）**：收费。每月前 100GB 免费。之后：

- 每月前 10TB 为 $0.09/GB（美国区域）
- 接下来 40TB 为 $0.085/GB
- 用量更高时费率更低

**同一可用区内**：免费。同一个 AZ 中的 EC2 实例相互通信不花一分钱。

**可用区之间（同一区域）**：每个方向 $0.01/GB。一笔小但真实存在的成本。

**区域之间**：$0.02-0.08/GB，取决于区域。跨区域流量明显更贵。

**NAT Gateway**：处理费 $0.045/GB。你的私有 EC2 实例经由 NAT Gateway 发往互联网的每一个字节——以及回来的每一个字节——都要收费。

**CloudFront**：数据传输费率低于 AWS 直连互联网。前 10TB 为 $0.085/GB（略低于直接数据传出）。CloudFront 通常会降低总传输成本，因为它的边缘缓存意味着源站提供数据的频率更低。

**NAT Gateway：最大的意外**

每月 $289 的 NAT Gateway 处理费是最大的一项。而 VPC Flow Log 分析把它具体化了：最大的消耗方是应用服务器经由 NAT Gateway 调用 AWS 服务 API（SSM、Secrets Manager、CloudWatch Logs）。

在第 11 章，Tom 为 S3 和 DynamoDB 设置了 VPC Gateway Endpoints。这些是免费的。但他漏掉了为其他几个服务设置 Interface Endpoints：

- 用于补丁管理的 Systems Manager（SSM）
- 用于凭证检索的 Secrets Manager
- 用于指标和日志传输的 CloudWatch
- 用于消息轮询的 SQS

私有 EC2 实例对这些服务的每一次调用都在走 NAT Gateway。每次调用按 $0.045/GB 收费。

你可能会好奇：既然已经在 AWS 的网络内部了，为什么 AWS 还要对经过 NAT Gateway 的流量收费？答案是，NAT Gateway 本身是一项托管服务——运行它要花钱，AWS 按每 GB 把这个成本转嫁出来。VPC Endpoints 砍掉了中间商，这就是它们能降低账单的原因。

"等等——但我们*为什么*会那样做？"Tom 展示数字时，Maya 问，"我们给 S3 和 DynamoDB 设了 Gateway Endpoints。为什么没给 SSM 和 CloudWatch 做同样的事？"

"Gateway Endpoints 只对 S3 和 DynamoDB 可用，"Tom 说，"其他的一切——SSM、Secrets Manager、SQS——都需要 Interface Endpoints。它们不免费，但在我们产生的流量规模下，比走 NAT 更便宜。"

这些服务的 **Interface Endpoints**：每个 AZ 每小时 $0.01 + 数据处理每 GB $0.01。

按 Nimbus 的流量，SSM Interface Endpoint 的成本约为每月 $25（小时费加按 GB 的处理费），能省下约每月 $45 的 NAT Gateway 费用（因为 SSM 的补丁管理和参数存储调用会产生可观的数据量）。

端点的成本和节省因服务和流量而异。Tom 算出，为四个高流量服务设置 Interface Endpoints——每个跨两个 AZ，加上它们承载的 3.9TB 流量按 $0.01/GB 的处理费——总成本约每月 $97，能省下约每月 $176 的 NAT Gateway 处理费。

净节省：仅端点设置一项就是每月 $78。

"那要是有人想入侵呢？"当 VPC 端点的讨论转向实施时，Priya 说，"VPC 端点意味着流量根本不接触公共互联网——这不只是成本，这是攻击面的缩减。光为了安全收益我们就早该这么做了。"

"同意，"Tom 说，"成本节省是附赠的。"

Leo 看着那份一直在走 NAT 的服务清单。"我当时设置 CloudWatch 日志端点的时候，可能没检查它有没有对应的 VPC 端点，"他说，"眼下倒是没事——但没错，它走 NAT 已经走了六个月了。"

"已经在清单上了，"Tom 说，"CloudWatch 是我们要修的四个之一。"

**PrivateLink 的计算：什么时候划算**

随着架构的成长，这场对话还有一个更复杂的版本会出现：使用 AWS PrivateLink 为其他 AWS 客户托管的服务（或你自己在其他 VPC 中的服务）提供私有连接。

PrivateLink Interface Endpoints 的费用是每个 AZ 每小时 $0.01，外加每 GB $0.01。对于一个每月经端点产生 1TB 流量的服务：

- PrivateLink 成本：$0.01 × 2 个 AZ × 730 小时 + $0.01 × 1,000GB = $14.60 + $10 = 每月 $24.60
- 同样的流量改走现有 NAT Gateway：$0.045 × 1,000GB = 每月 $45 的增量处理费

这个比较看的是*增量*，因为 NAT Gateway 无论如何都会留着——它还要服务其余的互联网流量，所以它的小时费（$0.045 × 2 × 730 = $65.70）不会因为这一个服务搬到端点上就消失。在这个流量规模下，PrivateLink 大约每月省 $20。盈亏平衡点大约是每月 420GB——低于这个量，端点自身的小时费就会盖过相对 NAT 处理费的按 GB 节省。

"等等——但我们*为什么*要用 PrivateLink，而不是直接用 VPN 或对等连接？"Maya 问。

"VPC Peering 更简单，区域内传输还免费，"Tom 说，"但对等连接在 VPC 之间建立的是一条全路由的通道——VPC A 里的任何东西都有可能触达 VPC B 里的任何东西。PrivateLink 更精准。端点暴露的是一个特定的服务，而不是一条完整的网络路由。对注重安全的架构来说，这种精确性很重要。"

"那要是有人想入侵一个对等的 VPC 呢？"Priya 问，"完全对等意味着一个 VPC 里被攻陷的实例拥有通往对等 VPC 里每一台实例的路由。"

"这就是在连接第三方服务或别的团队拥有的服务时，PrivateLink 优于对等连接的理由，"Tom 说，"公司内部互信的 VPC 用 Peering。任何你想要最小暴露面连接的场景用 PrivateLink。"

**跨 AZ 流量：一个架构问题**

每月 $178 的跨 AZ 数据传输更棘手。

其中一部分不可避免：负载均衡器把流量分配到各个 AZ，所以有些请求来自一个 AZ，负载均衡器把它们转发到另一个 AZ 的实例。

另一部分可以优化：应用程序被配置为写入 RDS 主库（在 us-west-2a），从读副本读取（在 us-west-2b）。每一次读查询都跨越 AZ 边界。

针对读取，一个解法是：把应用配置为优先使用与发起请求的实例处于同一 AZ 的读副本。每个 AZ 配自己的读副本。流量留在本地。

取舍在于：更多读副本 = 更多成本。如果跨 AZ 流量成本是每月 $50，而一个额外的读副本要每月 $190，AZ 本地化优化就不划算。

Tom 算了一下：在他们当前的查询量下，跨 AZ 流量在 $178 中只占 $31。不值得为此添加副本。

其余的跨 AZ 成本是负载均衡器路由和服务间通信——在当前架构层面基本上不可避免。

"这就是那种'理解了成本并不意味着你就该修它'的情况，"Tom 说。

"完全消除跨 AZ 流量要付出什么代价？"Maya 问。

"把一切都放进一个 AZ，那就违背了 Multi-AZ 的初衷。等于用失去高可用换每月 $31 的节省。"

"那我们就不动它，"她说。

"我们不动它。"

**S3 Select：减少查询中的数据传输**

在审查分析流水线时，Tom 发现了另一项优化，专门针对分析团队查询大型 S3 文件的方式。

模式是这样的：每天早晨，一个分析任务从 S3 下载一个 500MB 的 Parquet 文件，在内存中过滤出特定餐厅的订单数据。文件下载下来后，大约 95% 被直接丢弃。

**S3 Select** 允许你从一个 S3 对象（CSV、JSON、Parquet）中只检索你需要的行和列，而不是把整个文件下载到应用程序里再过滤。

> **重要更新**：2024 年年中，AWS 停止向新客户提供 S3 Select——现有用户可以继续使用，但对新架构来说它是条死路。本节教的原则（在存储层过滤，不要搬运整个文件）是不过时的；当下实现它的工具是 **Amazon Athena**（直接在 S3 上跑 SQL，包括 S3 Select 从未支持过的联接和聚合）。**S3 Object Lambda** 曾是另一个替代方案，如今也步了 S3 Select 的后尘进入遗留状态：自 2025 年 11 月 7 日起对新客户关闭（现有工作负载继续运行）。在当前的考试中，"就地查询 S3 上的数据"指向的是 Athena。下面的故事之所以保留，是因为其中的*推理*——先测量，再把过滤器移到数据那边——才是真正的课。

没有 S3 Select：
```python
# 下载 500MB 文件，在内存中处理
data = s3.get_object(Bucket='analytics', Key='orders-2024.csv')
df = pd.read_csv(data['Body'])
result = df[df['restaurant_id'] == '47'][['order_id', 'total']]
```

有 S3 Select：
```python
# 让 S3 先过滤，只传输匹配的行（约 2MB 而不是 500MB）
response = s3.select_object_content(
    Bucket='analytics',
    Key='orders-2024.csv',
    Expression="SELECT order_id, total FROM S3Object WHERE restaurant_id = '47'"
)
```

S3 Select 减少了从 S3 进入你应用程序的数据量。对于带选择性查询的大文件，这可以把数据量缩减 10-100 倍——而且，由于分析实例与存储桶运行在同一区域，赢的不是传输账单（同区域 S3 到 EC2 的传输是免费的）：赢的是花在下载和过滤那些马上就要扔掉的数据上的计算、内存和时间。

**变体：你选择接受的取舍**

如果你通过把一切都跑在单个可用区里来消除跨 AZ 流量，在 Nimbus 当前的流量下大约能省每月 $31——但你失去的 Multi-AZ 冗余，以事故风险计远比这值钱。成熟的成本对话并不总是关于寻找节省；有时它是关于确切理解你在为什么付费，并决定它值得。

跨 AZ 费用是韧性的价格。有些网络成本是架构上的承诺，而不是低效。

与 SAA-C03 的关联：考试经常给出"成本优化"会消除某项冗余的场景。正确答案通常是保留冗余、在别处优化——要分清浪费与可靠性的成本。

**CloudFront：数据传输的折扣**

这里有一个反直觉的事实：通过 CloudFront 提供数据，通常比直接从 EC2 或 S3 提供更便宜。

**EC2 直连互联网**：$0.09/GB
**CloudFront 到互联网**：$0.085/GB（略便宜）

但真正的节省不在每 GB 的费率——而在于 CloudFront 在边缘节点缓存数据。如果 1,000 个用户请求同一张菜单照片：

- **没有 CloudFront**：1,000 个请求直接从 S3 出到互联网 × 照片大小 × $0.09/GB
- **有 CloudFront**：客户端按 CloudFront 的费率（$0.085/GB）从边缘获取照片，而缓存填充——那 1 次未命中时 CloudFront 从 S3 取数据——是**免费的**（AWS 免除源站到 CloudFront 的传输费；你只为源站的 GET 请求付费）

对于缓存命中率 83% 的 Nimbus（来自第 13 章），83% 的请求根本没碰到源站——更少的回源请求、更低的源站负载，而且每一个字节都按边缘费率计费，而不是 S3 的互联网费率。

"CloudFront 不只是一个为性能而生的 CDN，"Tom 说，"它也是数据传输上的成本优化。"

Leo 若有所思。"我们应该把所有静态内容分发都搬到 CloudFront 上，哪怕是对延迟不敏感的资源。"

"正确。只要用户在从 AWS 下载它，它就应该走 CloudFront。"

**完整的网络优化**

经过三周的分析和实施：

| 成本项目                                  | 之前   | 之后    | 每月节省 |
|--------------------------------------------|----------|----------|----------------|
| NAT Gateway（Interface Endpoints）          | $289     | $211     | $78            |
| CloudFront 优化（迁移更多资源） | $214     | $147     | $67            |
| 跨 AZ 流量（接受现状）          | $178     | $178     | $0             |
| 跨区域流量（Leo 的测试桶）   | $166     | $160     | $6             |
| **总计**                                  | **$847** | **$696** | **每月 $151** |

每月 $151，每年 $1,812 的网络节省。和计算、存储相比不算大，但有意义。

更重要的是：Tom 现在理解了网络账单的每一行。他能解释每一项成本，并且有意识地决定了哪些要优化、哪些要接受。有意成本与无意成本之间的区别，如今已经明确并记录在案。

## 优势与局限

**NAT Gateway 成本**：

- 经过 NAT Gateway 的大流量会迅速累积
- VPC Endpoints 能彻底消除部分 NAT 成本
- 检查你的私有实例调用哪些服务，以及是否有对应的端点可用

**用 CloudFront 降成本**：

- 缓存命中率直接决定成本节省
- 高缓存命中率 = 更少的回源请求和更低的源站负载，加上更多字节按 CloudFront 更便宜的访问者侧费率计费（来自 AWS 源站的源站到 CloudFront 传输完全不收费）
- 把所有静态资源分发都迁移到 CloudFront

**跨 AZ 取舍**：

- 消除跨 AZ 流量通常需要做成本高于节省的架构变更
- 优化之前仔细算账

**S3 Select**（遗留——自 2024 年起对新客户不可用；改用 Athena。S3 Object Lambda 现在也是遗留状态——自 2025 年 11 月起对新客户关闭，现有工作负载不受影响）：

- 原则依然成立：在存储层过滤，而不是下载大型 S3 对象——节省体现在计算时间、实例规格和任务时长上（同区域 S3 传输本来就免费）
- 当你确实需要整个文件时帮不上忙

## 总结

Tom 用白板上的一个数字结束了网络分析，也对账单上最后那个未知数到底是什么有了更清晰的理解。每月 $847 的网络成本并不是一桩无能造成的悬案——它是一个横跨可用区、服务全球用户、跨区域复制数据的分布式系统的预期成本。其中大部分值得付。一部分不值得。关键的进步在于能分辨出哪个是哪个。

- AWS 对**出站数据**（互联网：约 $0.09/GB）、**跨 AZ 流量**（每个方向 $0.01/GB）、**跨区域流量**（$0.02-0.08/GB）和 **NAT Gateway 处理**（$0.045/GB）收费。
- **入站数据**免费。**同 AZ 流量**免费。
- **VPC Flow Logs** 能揭示 VPC 内部具体哪些流量流向在产生各类成本——精准优化的必备工具。从不穿过 VPC 网络接口的流向（比如 CloudFront 从 S3 源站取数据）需要它们自己的测量仪器：CloudFront 标准日志或 S3 服务器访问日志。
- **VPC Gateway Endpoints**（S3、DynamoDB）：免费。消除这些服务的 NAT Gateway 成本。
- **VPC Interface Endpoints**：按小时加按 GB 计费。对高流量服务比 NAT Gateway 便宜。
- **CloudFront** 以低于 EC2 直连互联网的费率提供数据，并通过缓存大幅减少回源传输量。
- 关键问题不只是"花了多少"，而是"这笔成本是有意的吗？"无意的成本——被遗忘的测试流水线、默认走 NAT 的路由——才是真正的节省所藏身的地方。

## 考试技巧

*SAA-C03 领域：设计成本优化架构（领域 4，任务 4.4）*

- **NAT Gateway 与 VPC Endpoints**：考试场景："私有子网中的 EC2 频繁调用 S3/DynamoDB——如何降低 NAT Gateway 成本？"→ VPC Gateway Endpoints（S3 和 DynamoDB 免费）。
- **数据传输定价规则**：
  - 进入 AWS：免费
  - 同 AZ：免费
  - 跨 AZ：收费
  - 跨区域：收费（费率更高）
  - 互联网：收费（费率可观）
- **CloudFront 作为成本优化**："降低全球内容分发的数据传输成本"→ CloudFront。缓存层减少回源请求。
- **S3 Transfer Acceleration**：利用 CloudFront 边缘节点加速*上传到* S3。成本高于标准 S3。用于从地理上遥远的位置上传大文件的客户。
- **跨区域复制成本**：跨区域复制数据会产生数据传输费。对于 S3 CRR，你要同时支付数据传出费率和 S3 请求费用。
- **PrivateLink（VPC Interface Endpoints）**：提供到 AWS 服务以及其他 AWS 客户托管服务的私有连接。比走 NAT 更安全，对高流量服务通常更便宜。相对于 NAT Gateway 处理费的盈亏平衡点约为每月 420GB（计入端点自身按 AZ 的小时费，并假设 NAT Gateway 为其他流量继续保留）。

*（提示：Gateway Endpoints 免费，但只适用于 S3 和 DynamoDB。Interface Endpoints 按小时收费，但适用于大多数其他 AWS 服务。）*

**练习 2 — SAA-C03 场景题**

*场景*：一家公司的应用程序运行在私有子网中的 EC2 实例上。这些实例频繁调用 Amazon SQS 和 Amazon S3 的 API。目前，所有流量都经由一个 NAT Gateway 流出。团队希望降低 NAT Gateway 成本。必须保障数据安全——任何流量都不得经过公共互联网。

哪种方案能以最低的持续成本最好地满足这些要求？

A) 为 SQS 创建一个 Gateway Endpoint，为 S3 创建一个 Gateway Endpoint  
B) 为 SQS 和 S3 都创建 Interface Endpoints  
C) 为 SQS 创建一个 Interface Endpoint，为 S3 创建一个 Gateway Endpoint  
D) 移除 NAT Gateway，直接使用 Internet Gateway 进行 API 调用

**提示 1**：Gateway Endpoints 只适用于 S3 和 DynamoDB。

**提示 2**：Interface Endpoints 适用于 SQS 及许多其他服务（但要花钱）。

**提示 3**：在私有子网的路由表里加一条 Internet Gateway 路由会让它变成公有子网——违反安全要求。

**答案**：C

**解释**：S3 使用 Gateway Endpoint（免费）。SQS 需要 Interface Endpoint（计费）。这个组合消除了两个服务的 NAT Gateway 数据处理费。所有流量都留在 AWS 的私有网络内——不经过公共互联网。

**为什么不是 A？** Gateway Endpoints 不支持 SQS。只有 S3 和 DynamoDB 有 Gateway Endpoints。

**为什么不是 B？** 虽然可行，但为 S3 使用 Interface Endpoint（而不是免费的 Gateway Endpoint）会产生不必要的小时费用。S3 和 DynamoDB 永远使用免费的 Gateway Endpoint。

**为什么不是 D？** 从私有子网添加一条通往 Internet Gateway 的路由会让它变成公有子网。私有子网中的 EC2 实例通常没有弹性 IP，所以不做额外更改它们实际上无法经由 Internet Gateway 路由——而这样做会把它们暴露给入站的互联网流量。
