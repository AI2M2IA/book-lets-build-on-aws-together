# 第7章：越忙越大的餐厅

那是一个周五晚上7点43分，错误率超过了12%。

Tom 首先注意到了，因为 Tom 总是最先注意到。他打开了 CloudWatch 仪表板的一个标签，像其他人刷社交媒体一样——反射性地、不断地、几乎没有刻意而为。

"Leo，" 他说。

Leo 已经在看了。响应时间：上升中。排队请求：上升中。单个 EC2 实例——甚至是上个月他们升级的那个更大的实例——CPU 使用率达到了94%。

"我们在拒绝顾客，" Tom 说。

"我们没有在拒绝他们，" Leo 说。"是服务器在拒绝。"

"这是一回事。"

确实是。而且这每个周五已经发生三周了。Nimbus 已经度过了存储危机——数据库有了自己的磁盘，照片住在 S3 里——但稳定和可扩展是完全不同的问题。系统在工作。它只是不能增长。

团队需要他们的系统自动处理可变负载。而不是为最坏的情况购买足够的服务器，在安静时期浪费钱。也不是在流量峰值到来时手动应急。

有一个解决这个问题的模式。AWS 有两个服务来实现它。

**概念：水平扩展**

让系统处理更多负载有两种方法。

**垂直扩展**意味着让单台服务器变大。更多 CPU。更多 RAM。我们在第4章升级 `t3.micro` 到 `t3.large` 时就这样做了。这有帮助。但它有限制：你能做的只有这么大，实例必须重启才能调整大小，而且你仍然有单点故障。

**水平扩展**意味着添加更多服务器。不是一台大服务器，而是运行五台中等服务器。当流量下降时，运行两台。当流量激增时，运行十台。

水平扩展有垂直扩展没有的优势：

- 没有单点故障。如果一台服务器挂了，其他服务器继续提供服务。
- 添加容量不需要重启。
- 只为使用的部分付费——需要时添加服务器，不需要时删除。
- 线性扩展：双倍的服务器，大约双倍的吞吐量。

问题是：如果你有多台服务器，用户如何知道与哪台通信？

**应用负载均衡器：一扇门，多个房间**

**应用负载均衡器**（ALB）是你应用程序的前门。

用户连接到负载均衡器。负载均衡器将传入请求分发到你的 EC2 实例集群。每个用户看到一个地址（负载均衡器的 URL）。在那个地址背后，请求被分散到所有正在运行的服务器上。

把它想象成一家大型餐厅的领位台。就餐者到来，领位引导他们到可用的桌子。领位知道哪张桌子很忙，哪张是空的。就餐者不需要知道有多少张桌子——他们只是走进来，领位处理分配。

ALB 对 Web 请求这样做。它接收每个传入的 HTTP 请求，并根据以下因素决定哪个 EC2 实例（称为**目标**）应该处理它：

- 轮询（每台服务器依次轮流）
- 最少未完成请求（正在处理请求最少的服务器接收下一个请求）
- 健康状况——只有健康的目标才接收流量

**健康检查**至关重要。ALB 定期向每个目标发送测试请求。如果目标没有正确响应，ALB 将其标记为不健康，并停止向其发送流量。当目标恢复时，流量恢复。

这是自动的。你配置健康检查参数；ALB 执行它们。

**自动扩展：开更多桌子的餐厅**

ALB 将流量分发到你现有的服务器。但当你需要更多时，它不会添加服务器。

**自动扩展**做到了这一点。

**自动扩展组**（ASG）是一个配置，告诉 AWS：

- 始终运行的最少实例数
- 允许的最大实例数
- 扩展（添加实例）或缩减（删除实例）的条件

扩展条件称为**策略**。最常见的类型：

**目标跟踪**：保持平均 CPU 使用率在70%。当平均 CPU 超过70%时，AWS 启动新实例。当它降低时，实例被终止。

这是自动的。没有人需要盯着指标。没有人需要手动启动服务器。系统实时响应负载。

Priya 第一次在周五晚高峰时实时观看这一过程。服务器数量在十五分钟内从2个增加到5个，然后在高峰后恢复到2个。

"那，" 她说，"确实令人印象深刻。"

Tom 在看成本图。账单在高峰期增加，之后下降。"我们只为使用的部分付费，" 他说，同样印象深刻。

**ALB 和 ASG 如何协同工作**

这两个服务被设计为一起使用。

你把 ALB 放在前面。ALB 指向一个**目标组**——应该接收流量的实例集合。自动扩展组管理这些实例：在扩展时将它们添加到目标组，在缩减时删除它们。

流程：

1. 流量到达 ALB
2. ALB 将请求分发到健康的目标
3. 这些目标上的 CPU/负载上升
4. ASG 检测到负载增加，启动新实例
5. 新实例通过健康检查，被注册到 ALB
6. ALB 开始向它们发送流量
7. 负载下降，ASG 终止多余的实例
8. ALB 停止向终止的实例发送流量

这无需任何人工干预即可发生。

**启动模板：新实例的蓝图**

当 ASG 启动新实例时，它需要知道启动什么。这在**启动模板**中定义——一个 AMI、一种实例类型、要应用的安全组，以及任何用户数据（实例启动时运行的启动脚本）。

常见模式：你将应用程序构建到自定义 AMI 中（见第4章）。当 ASG 需要新实例时，它启动那个 AMI。新实例在启动时已经安装了你的应用程序。无需手动设置。

对于更动态的环境，你也可以使用**用户数据脚本**，在启动时拉取并安装你代码的最新版本。这更灵活但启动时间更长。

正确的选择取决于你的实例需要多长时间启动以及你的应用程序更新频率。

**粘性会话：一个微妙的问题**

这里有一些在第一次实施负载均衡时会让很多团队绊倒的东西。

一些 Web 应用程序在服务器本身上存储会话数据——登录状态、购物车内容——（在内存或本地磁盘中）。这在一台服务器上可以正常工作。有多台服务器时就会崩溃。

用户登录。请求去到服务器 A。服务器 A 存储了会话。下一个请求去到服务器 B。服务器 B 没有会话。用户看起来像是登出了。

这可以通过两种方式解决：

**粘性会话**（或会话亲和性）：配置 ALB 总是将来自同一用户的请求发送到同一台服务器。这是短期修复。它破坏了负载均衡（一些服务器获得了更多的"粘性"用户），并在实例被终止时造成问题。

**无状态应用程序设计**：在外部存储会话数据——在数据库或像 ElastiCache（第10章）这样的缓存中。每台服务器都可以从外部存储重建任何用户的会话。服务器变得可以互换。这是水平可扩展应用程序的正确方法。

Priya 称之为"你进行多服务器部署时做出的最重要的架构决策"。她说得对。我们在第10章再次遇到这个问题。

**负载均衡器类型**

AWS 提供三种类型的负载均衡器，每种适用于不同的流量：

**应用负载均衡器（ALB）**：HTTP 和 HTTPS 流量。第7层（理解 HTTP）。可以根据 URL 路径（`/api` 到一个组，`/static` 到另一个组）、主机头和查询参数进行路由。这是大多数 Web 应用程序使用的。

**网络负载均衡器（NLB）**：TCP、UDP 和 TLS 流量。第4层（不理解 HTTP）。极高性能，每秒数百万个请求，非常低的延迟。当你需要原始速度或不处理 HTTP 时使用。

**网关负载均衡器（GWLB）**：用于通过第三方虚拟网络设备（防火墙、入侵检测）路由流量。在初级水平上你很少需要这个。

对于 Nimbus（以及大多数 Web 应用程序），ALB 是正确的选择。

## 优势与局限性

**为什么 ALB + 自动扩展很强大**：

- 零停机时间扩展（实例的添加/删除不会中断现有连接）
- 自动故障转移（不健康的实例自动从流量中移除）
- 成本效率（只为运行的实例付费）
- 没有单点故障——跨多个 AZ 的多个实例

**事情变得复杂的地方**：

- 有状态的应用程序需要特殊处理（粘性会话或外部状态）
- 扩展需要时间——如果流量瞬间激增，新实例准备好之前会有延迟。你可以通过**计划扩展**（在已知事件之前预先扩展）或更大的最小实例数来缓解这一问题
- 更多活动部件意味着需要监控和调试的内容更多
- 一些应用程序不能轻松地水平扩展（数据库、某些遗留系统）。水平扩展最适合无状态层。

## 摘要

- **水平扩展**（添加更多服务器）优于垂直扩展（让一台服务器变大），因为它消除了单点故障并允许弹性成本。
- **应用负载均衡器（ALB）** 将传入的 HTTP/HTTPS 流量分发到多个 EC2 目标。它执行健康检查，只向健康的实例路由。
- **自动扩展组（ASG）** 根据定义的扩展策略（例如目标 CPU 使用率）自动调整 EC2 实例数量。
- ALB 和 ASG 协同工作：ASG 管理集群，ALB 在其中分发流量。
- 有状态的应用程序必须使用粘性会话（短期修复）或外部化状态（正确的长期设计）。
- 对于 HTTP 流量，使用 ALB。对于原始 TCP/UDP 性能，使用 NLB。

## 考试技巧

*SAA-C03 领域2——任务2.1（可扩展架构）/ 领域3——任务3.2*

- **ASG 健康检查可以来自 EC2 或 ALB。** EC2 健康检查只检测实例是否在运行。ALB 健康检查检测应用程序是否正确响应。ALB 健康检查更彻底，应该作为 Web 应用程序的首选。
- **目标跟踪扩展是扩展策略最常见的考试答案。** 简单扩展（警报触发时添加 N 个实例）更老，适应性较差。
- **扩展快；缩减慢。** AWS 在缩减期间逐步终止实例，以避免中断活跃连接——这是由 ALB 的**注销延迟**设置控制的行为。
- **最小实例数是你的弹性底限。** 如果你设置最小值 = 1，那个实例失败时，你的应用程序在 ASG 能够响应之前就宕机了。将最小值设置为 ≥ 2，并跨 AZ 分布，以获得真正的弹性。
- **ALB 可以跨 AZ 自动分发流量。** 启用跨区域负载均衡后，每个 ALB 节点在所有注册的目标之间均匀分发请求，无论 AZ 如何。这对于当 AZ 实例数量不同时平衡负载很重要。

**练习 2——考试练习**

*场景*：一家零售公司的电商网站流量非常不稳定：工作日流量低，周末和闪购活动期间流量大增。他们希望他们的应用程序能够处理峰值负载，而不在安静时期维护未使用的容量。应用程序目前在服务器内存中存储会话数据。

哪种架构变更*最能*满足他们的可扩展性需求？

A) 升级到可以处理峰值流量的单个非常大的 EC2 实例  
B) 在带有自动扩展组的 ALB 后部署多个 EC2 实例，并将会话存储外部化到 ElastiCache  
C) 在启用粘性会话的 ALB 后部署多个 EC2 实例  
D) 在每次预期的流量峰值之前手动添加 EC2 实例，之后终止它们

**提示 1**："不维护未使用的容量"意味着你需要自动扩展，而不是固定的大型实例或手动管理。

**提示 2**：服务器内存中的会话存储对多实例部署是个问题。哪些选项解决了这个问题？

**提示 3**：选项 C 使用粘性会话——这是一种变通方法，而非解决方案。哪个选项同时正确解决了扩展和会话存储问题？

**答案**：B

**解析**：带有自动扩展组的 ALB 提供自动弹性扩展——在峰值期间添加实例，在安静时期删除它们。将会话存储移到 ElastiCache（外部缓存）使应用程序变为无状态：任何实例都可以处理任何用户的请求，ALB 可以自由分发流量。这是架构上正确的解决方案。

**为什么不是 A？** 无论多大的单个实例仍然是单点故障。它在安静时期也浪费钱，因为大部分容量闲置。

**为什么不是 C？** 粘性会话将用户路由到同一实例，这在一定程度上缓解了会话问题，但破坏了负载均衡。如果那个实例被终止（在缩减或故障期间），用户无论如何都会丢失会话。

**为什么不是 D？** 手动扩展需要有人正确预测流量峰值并提前行动。这很慢、容易出错、劳动密集。自动扩展自动处理这一切。

## 彩蛋场景

部署了自动扩展和 ALB 后的第一个周五，团队一起看着指标。

晚上7:15：两个实例在运行。正常负载。
晚上7:45：负载上升。自动扩展启动了两个新实例。
晚上8:00：四个实例处理峰值。响应时间稳定。
晚上9:30：负载下降。自动扩展终止了两个实例。
晚上9:45：恢复到两个实例。

网站从未宕机。一次都没有。

Leo 刷新了三次指标页面，好像他预期会发现他错过的故障。

"有点奇怪，我对什么都没有出问题感到有点失望，对吧？" 他说。

"是的，" Priya 说。

Tom 在看账单。成本几乎完美地追踪了流量。"我们恰好为使用的部分付费，" 他说。"不多不少。"

他听起来真的很惊讶。

第二天早上，Maya 在错误日志中发现了一个新问题。不是宕机——更糟。

八秒。对于一个餐厅订购应用。

"每次有人加载菜单，我们就查询数据库中的每一个菜品来构建页面，" Leo 说。"我们现在有四十七家餐厅了。"

"总共有多少道菜？" Tom 问。

"大约两万两千道。"
