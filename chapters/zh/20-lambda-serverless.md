# 第二十章：自由职业者模式

那是一个安静的周三下午。Priya 难得摘下了耳机，办公室里弥漫着那种低沉的嗡嗡声——意味着每个人都在专注工作，但没有人在恐慌。Leo 一块屏幕上开着成本仪表板，另一块屏幕上是 EC2 实例列表。

想象一位随叫随到的自由职业者。他们不会朝九晚五地坐在办公桌前。他们在等待。电话铃响，他们干活，发出账单，然后继续等待。没有工作，就没有费用。一波请求涌来，他们同时全部处理。你只为实际工作的小时数付费——而不是他们待命的小时数。

这就是本章要讲的模式。

这里有一个值得记住的微妙之处。传统模式是：雇一名员工，支付 8 小时工资，获得不确定的产出。自由职业者模式是：只在电话铃响时付费，获得恰好所要求的成果。对于需求可预测、持续稳定的公司，员工模式更高效——你知道电话会持续不断地响，所以按小时付费是等价的，而且没有接活和收尾的额外开销。对于需求多变、突发或不频繁的公司，自由职业者模式要便宜得多。

AWS 为计算提供了这种模式——它是否合理取决于你的需求模式。第一个问题从来不是"这个模式好吗？"而是"我的工作负载实际上是什么样的？"

对于大多数比初创公司更大的工作负载来说：是一种混合。有些东西持续运行（API 服务器、数据库）。有些东西只在被触发时运行（事件处理、报告生成、图片缩放）。自由职业者模式适用于第二类——而 Nimbus 即将发现，账单里有多少属于这一类。

SQS/SNS 扇出已经解耦了订单流，但消费这些队列的工作进程仍然运行在按小时计费的 EC2 实例上——无论它们实际发送了多少封邮件。架构是对的；成本模型仍有一个漏洞。

"一直都在。24/7 全天候。"

"即使凌晨三点我们一封邮件都不发的时候？"

Leo 调出了电子邮件服务 EC2 实例的 CloudWatch CPU 图表。图表显示了 18 个小时的持续运行。周五高峰时：CPU 为 38%，正在处理邮件高峰。午夜之后：CPU 降到 3%。一直保持到午餐订单开始进来。

连续 18 个小时 3% 的 CPU。实例在运行。它在计费。它没有做任何有意义的事情。

"我们在为一台坐在那里什么都不做的电脑付钱，"Leo 说。

"一天有多少小时是这样？"

更深的沉默。

"大约 18 小时。"

Tom 现在全神贯注。

"是的，"Leo 确认。

"也是的。"

Nimbus 所有较小的服务都呈现同样的模式：为每天 24 小时的计算付费，实际只使用其中一小部分。

**服务器并非总是答案**

EC2 实例是永久性的。你启动一台，它就会一直运行，直到你停止它——每天 24 小时，每周 7 天，无论实际使用情况如何。对于你的 Web 服务器（它全天处理流量），这是正确的。对于电子邮件服务（它突发性地发送邮件，然后闲置数小时），这就是一种浪费。

Auto Scaling Group 可以在非高峰期将电子邮件服务缩减到一个实例。但一个实例仍然持续运行。

这是 Tom 看账单时反复回到的问题：在那 18 个小时 3% CPU 的时间里，每个服务实际上在做什么？严格说来不是什么都没做——实例在等待、检查事件、维护自身状态。但从业务角度看：什么都没做。服务没有创造价值。它在计费。

对于大部分时间确实处于闲置状态的工作负载，一台始终在线的 EC2 实例就像为一套你只在周末才去的公寓付租金。公寓是你的；租金不会停。

自由职业者模式彻底解决了这个问题。代码存在。它只是在有理由运行之前不运行。没有空闲成本。没有预留容量。没有守着电话等待的服务器。

这就是**无服务器计算**的前提。

**AWS Lambda：无需服务器的代码**

**AWS Lambda** 让你在事件响应中运行代码，无需预置或管理服务器。你上传一个函数，指定触发它的条件，Lambda 在触发器触发时运行它。

Lambda 函数：

- 没有持久状态（每次调用相互独立）
- 每次调用最多运行 15 分钟
- 从 0 自动扩展到数千个并发调用
- 仅在运行时计费（按每 1 毫秒执行时间计费，向上取整，按分配的 GB 内存计算）

当没有触发器时，Lambda 不产生任何费用。当触发器触发时，Lambda 运行并计费。当 10,000 个触发器同时触发时，Lambda 运行 10,000 个并发调用。扩展是自动且近乎即时的。

**事件触发器：唤醒 Lambda 的条件**

Lambda 函数不会自行运行——它们响应事件。常见触发器包括：

- **SQS 队列**：从队列中处理消息。Lambda 轮询队列并以批量消息调用函数。
- **API Gateway**：HTTP 请求进入。API Gateway 触发 Lambda。Lambda 生成响应。
- **S3 事件**：文件上传至 S3。Lambda 处理它（调整图片大小、解析 CSV、验证文档）。
- **SNS**：消息发布到主题。Lambda 收到通知。
- **DynamoDB Streams**：DynamoDB 中的记录发生变化。Lambda 处理该变化。
- **CloudWatch Events（EventBridge）**：预定事件（如定时任务）在指定时间运行。
- **ALB**：HTTP 请求到达负载均衡器。Lambda 可以处理特定路由。

对于 Nimbus，电子邮件服务变成了一个由其 SQS 队列触发的 Lambda 函数。当消息到达队列时，Lambda 被调用并获取消息内容，通过 SES（Simple Email Service）发送邮件，然后退出。

零服务器。零空闲时间。空闲时零费用。

Lambda + SQS 这个模式值得内化于心：SQS 负责队列、持久性、重试逻辑和 DLQ。Lambda 负责处理。你既获得了 SQS 的解耦优势，又获得了 Lambda 缩容到零的经济性。两个服务互不越界。它们干净地组合在一起。

"队列里出现格式错误的消息会怎样？"Priya 问，"糟糕的输入会不会让 Lambda 崩溃，进而影响账户中的其他函数？"

Lambda 的调用是彼此隔离的。一个崩溃的函数不会影响其他函数。一个 Lambda 在遇到格式错误的消息时抛出未处理的异常：消息回到队列，重试到配置的上限，然后转移到 DLQ。Lambda 本身对下一条消息仍然可用。在 Lambda 处理程序内部进行输入验证仍然很重要——在尝试处理之前捕获格式错误的数据——但单条坏消息无法搞垮整个函数。

**冷启动问题**

Lambda 函数在**执行环境**中运行——小型隔离容器。当函数被调用时：

1. AWS 检查是否有可用的热执行环境（最近处理过调用的环境）
2. 如果是热环境：函数立即运行
3. 如果是冷环境：AWS 初始化一个新执行环境——下载你的代码，启动运行时，运行你的初始化代码——然后运行函数

**冷启动**会增加 100 毫秒到几秒的延迟，具体取决于运行时（Java 和 .NET 的冷启动时间比 Python 和 Node.js 更长）以及代码包的大小。

你可能会想：如果 Lambda 每次都从零开始，那它不就比一台已经在运行的服务器更慢吗？是的——有时候。这就是冷启动问题，它对时间敏感的面向用户的 API 很重要。但对于用户已经收到确认的后台任务来说，它完全无关紧要。后台运行的电子邮件服务上 200 毫秒的冷启动，对任何人都是不可见的。

对于异步处理（发送邮件、调整图片大小），冷启动对用户不可见。

对于同步 API（用户等待响应的 HTTP 请求），冷启动可能导致偶发性的响应缓慢。

**缓解方法**：

- **预置并发**：预热指定数量的执行环境。它们始终准备就绪。即使不处理请求，你也要为此付费。
- **更小的包大小**：更小的代码初始化更快。
- **预热调用**：定期 ping 以保持函数温热（这是一种常见但不够优雅的方法）。
- **选择合适的运行时**：Python 和 Node.js 的冷启动比 Java 更快。

**一次真实的冷启动排查**

Lambda 迁移两周后，Leo 收到一位餐厅合作伙伴的 Slack 消息："订单确认有时要 3 秒。通常很快。发生了什么？"

Leo 调出了该 Lambda 函数的 CloudWatch 指标。在"Duration"图表中，他看到了一个规律：任何超过 15-20 分钟的间隔之后的第一次调用都会飙升到 2,800-3,200 毫秒。后续调用：180-220 毫秒。

经典的冷启动。

他调出了一次 3 秒调用的 X-Ray 追踪。时间线清楚地显示了问题：

- 初始化阶段：2,640 毫秒（下载函数代码、启动 Node.js 运行时、运行模块级初始化代码）
- 处理程序函数执行：290 毫秒

初始化阶段是问题所在。他查看了初始化代码。函数在启动时导入了一个庞大的 SDK、初始化数据库连接，并从 AWS Secrets Manager 加载配置——全部在启动时进行。

"其中一些初始化只需要在每个执行环境中发生一次，"Leo 说，"但现在每次冷启动都在发生。"

他重构了 Lambda 代码，把数据库连接的初始化放到处理程序函数之外（这样它在热调用之间可以复用），并通过移除未使用的 SDK 模块缩减了包的大小。他还从打包整个 AWS SDK 改为只导入他实际需要的特定服务。

优化之后：

- 冷启动时长：1,100 毫秒（仍然存在，但没那么严重了）
- 热调用：165 毫秒

那 1.1 秒的冷启动偶尔还是会发生。对于电子邮件服务（异步，面向用户的延迟不可见），这是可以接受的。对于餐厅通知 Lambda（面向客户，从平板上下单），Priya 力推预置并发：两个预热好的执行环境随时待命。

"这每个月要花多少钱？"Tom 问。

两个 256MB 的预置并发执行环境：每月约 $5.40。延迟峰值消失了。

**Lambda 定价：Tom 为何微笑**

Lambda 定价有两个组成部分：

1. **请求费用**：每百万次调用 $0.20
2. **时长费用**：每 GB-秒 $0.0000166667（分配的内存 × 运行秒数）

每月前一百万次请求免费（永久免费，不只是第一年）。

"这每个月要花多少钱？"Tom 在 Leo 打开计算器之前就问了。

Tom 亲自为电子邮件服务做了计算：

- 假设每天都是周五——最坏情况：每天 1,200 封邮件 × 30 天 = 每月 36,000 次调用
- 每次调用约 2 秒，内存为 256MB
- 时长：36,000 × 2 × 0.25GB × $0.0000166667 = 每月 $0.30
- 请求：36,000 << 1,000,000（免费额度）= $0.00/月

"而且那 18,000 GB-秒远在永久免费的 400,000 GB-秒时长额度之内，"Tom 补充道，"所以实际费用会是零。但我是故意忽略免费额度的——我想知道真实的单位成本。"

电子邮件服务的 EC2 实例：$18/月。

"我已经部署上线了——哦。"Leo 把话咽了回去。他在完成 DLQ 配置之前就把电子邮件服务的 Lambda 推到了生产环境。"给我五分钟。"

Tom 沉默了片刻。然后说："我们应该把所有东西都这样做。"

**Lambda 擅长的（以及不擅长的）**

"等等——可是*为什么*我们不干脆把所有东西都用 Lambda 呢？"Maya 问，"如果它更便宜还能自动扩展，代价在哪里？"

"15 分钟的限制，"Leo 说，"还有面向用户的任何东西都会有冷启动。还有无状态性——你不能在两次调用之间在内存里保留任何东西。"

如果你的工作负载是突发性的、事件驱动的、能在 15 分钟内完成的，Lambda 的成本只是始终在线的 EC2 实例的一个零头——但如果你的工作负载是一个接近或超过 15 分钟限制的长时间运行的数据处理任务，Lambda 就是错误的工具，你需要 ECS、Batch 或基于 EC2 的方案。

Lambda 非常适合：

- **事件驱动处理**：响应事件（文件上传、队列消息、定时任务）
- **短期任务**：在 15 分钟内能从容完成的处理
- **突发性、不可预测的流量**：Lambda 从 0 瞬间扩展到数千——无需预先配置
- **不频繁的操作**：每天凌晨两点运行一次的报告。每周运行一次的清理任务。
- **粘合代码**：在服务之间移动数据的小函数

你可能会想：当 10,000 个事件突然同时到达时，Lambda 的扩展会怎样？Lambda 的默认并发限制是每账户 1,000 个并发执行。如果 10,000 个事件同时到达，最多 1,000 个调用立即运行；其余的在 SQS 队列中等待（如果是通过 SQS 触发的），并在容量释放时被处理。对于基于队列的处理，这通常没问题。对于延迟敏感的用例，Lambda 的突发限制（新增并发执行的初始速率）可能在突然的流量峰值期间造成短暂的节流——预置并发通过预先分配容量绕开了这个问题。

对于 Nimbus 当前规模的电子邮件服务，1,000 个并发调用远超他们的任何需求。但这是在撞上它之前就该了解的约束。

Lambda 不适合：

- **长时间运行的进程**：15 分钟限制是一堵硬墙
- **有状态应用**：Lambda 函数按设计是无状态的——每次调用相互独立
- **高吞吐量、低延迟 API**：冷启动可能导致延迟峰值；预置并发可以缓解这个问题，但会增加成本
- **需要持久连接的应用**：Lambda 难以维护长期数据库连接池（尽管 RDS Proxy 等连接池工具有所帮助）
- **传统 Web 服务器**：可以，但并非自然适配

**15 分钟之墙：当 Lambda 是错误的工具**

迁移三周后，Leo 试图把又一个工作负载迁移到 Lambda：夜间分析报告生成器。它从数据库拉取订单数据，与餐厅元数据进行关联，计算统计数据，并生成一份 PDF。

第一晚，Lambda 调用就因超时错误失败了。

"报告生成花了 17 分钟，"第二天早上 Leo 说。

"Lambda 的上限是 15 分钟，"Priya 说。

"是的。我现在知道了。"

他检查过平均处理时间（8 分钟），就假设 Lambda 能行。他没有检查尾部情况——那些数据量更大、查询耗时更长的夜晚。在那些夜晚，15 分钟不够用。

"所以报告就……没有生成？"Maya 问。

"没错。没有错误通知。没有部分报告。只有沉默。"

"我已经部署上线了——哦，"Leo 说。

这正是 Lambda 不优雅失败的具体方式之一：超时不产生任何输出，应用程序里没有错误消息，只有一条 CloudWatch 错误日志。如果你没有专门监控 Lambda 超时错误，可能好几天都不会察觉。

修复方案：把报告生成器迁移到 ECS Fargate——无需管理服务器的容器；下一章——它没有时间限制。对于哪怕偶尔可能超过 15 分钟的工作负载，Lambda 就是错误的工具。教训不是"Lambda 不好"。教训是"对于符合其约束的工作负载，Lambda 是正确的工具——当不符合时，它就是出人意料的故障源"。

**RDS Proxy：为 Lambda 提供连接池**

Lambda 的无状态特性带来了一个特定的数据库问题。

当一台 EC2 实例连接到 RDS 时，它维护一个持久连接池。应用程序复用池中的连接。RDS 能处理比如说 200 个同时连接。

当 Lambda 处理 500 个同时调用时，每个调用都试图打开自己的数据库连接。这就是 500 个新连接——压垮一个只支持 200 个连接的数据库。

**Amazon RDS Proxy** 位于 Lambda 函数和 RDS 之间，维护一个持久连接池，并将 Lambda 的短生命周期连接多路复用到这个池上。

不再是：Lambda 调用 → 新的 RDS 连接（500 个并发调用各开一个）

有了 RDS Proxy：Lambda 调用 → RDS Proxy → 由 20 个持久 RDS 连接组成的连接池

"代理需要 RDS 凭证，"Priya 说，"这些凭证放在哪里？它会存储它们吗？"

RDS Proxy 把凭证存储在 Secrets Manager 中并自动轮换。Lambda 函数的 IAM 角色授予它访问代理的权限（使用 IAM 身份验证），而不是直接访问 RDS 凭证。凭证从不暴露给 Lambda 代码。

"所以 Lambda 函数通过 IAM 进行身份验证，"Leo 确认道，"由代理来处理实际的数据库凭证。"

对于 Nimbus 的订单处理 Lambda（那个查询 RDS 进行订单验证的函数），RDS Proxy 消除了周五高峰流量期间的连接池耗尽问题。

**Lambda Layers：共享依赖**

电子邮件服务 Lambda、通知 Lambda 和报告 Lambda 都共享同一套内部库代码：格式化货币、净化输入、按标准格式记录日志的工具函数。

没有 Lambda Layers，那些共享代码必须打包进每个函数的部署包里。三个函数，三份同样的 2MB 库。库一更新，三个函数都需要重新部署。

**Lambda Layers** 是 Lambda 函数可以在运行时引用的独立包。共享库被提取到一个层中。三个函数引用这个层。共享库的更新意味着更新层的版本——而不是重新部署三个函数。

额外的好处：更小的单个函数包意味着更快的冷启动。

"有一件事层改变不了：执行角色，"Priya 说，"如果一个 Lambda 的权限过宽，一个被攻破的函数就能访问账户里的一切。"

"和 EC2 角色是同一个原则，"Leo 说，"最小权限。每个 Lambda 只获得它实际需要的权限。"

"所以 Lambda 并不是 EC2 的替代品，"Maya 说，"它是针对不同任务的不同工具。"

"Nimbus 的 Web API 仍然留在 EC2 或 ECS 上，"Leo 确认道，"电子邮件服务、图片缩放程序、夜间报告生成器、日志清理器——这些迁移到 Lambda。"

**无服务器理念**

Lambda 是一个更广泛概念的一部分：**无服务器**——构建无需管理服务器、只管理代码的应用程序。

一个完全无服务器的 Nimbus 技术栈可能看起来像这样：

- API Gateway + Lambda（代替带 Web 服务器的 EC2）
- DynamoDB（代替 RDS——同样无服务器，无需管理服务器）
- S3（静态资源——本质上是无服务器的）
- SNS + SQS（消息传递——无服务器）
- Lambda（所有后台处理）

吸引力在于：你编写代码；AWS 管理其他一切。无需打补丁，无需扩展配置，无需容量规划。

## Amazon API Gateway

Lambda 触发器列表里简要提到了 API Gateway：HTTP 请求进入，API Gateway 触发 Lambda。这没有错，但低估了 API Gateway 真正的能耐。

"等等——可是*为什么*要在 Lambda 前面放一个 API Gateway？"Maya 问，"Lambda 不能直接接收 HTTP 请求吗？"

Lambda 可以通过函数 URL 接收 HTTP 请求——一个简单、直接的 HTTPS 端点。但它不处理路由、授权、限流、缓存或请求转换。对于一个生产级 API，无论你的后端是 Lambda 还是 EC2，这些关注点都同样存在。

**Amazon API Gateway** 是一项完全托管的服务，用于在任意规模下创建、部署和管理 API。它处理流量管理、授权、限流、缓存和监控，让你的 Lambda 函数（或 EC2，或任何 HTTP 后端）不必自己实现这些功能。

**三种 API 类型：**

**REST API** 是功能最丰富的选项。它支持请求和响应转换、响应缓存、绑定到 API 密钥的使用计划，以及所有的授权类型。大多数提到 API Gateway 的 SAA-C03 考题涉及的都是 REST API。

**HTTP API** 更简单也更便宜——成本比 REST API 低约 70%。它专为 Lambda 后端和 HTTP 代理设计。它支持 OIDC 和 OAuth 2.0 授权，但不支持请求转换或缓存。如果你不需要 REST API 的高级功能，HTTP API 是正确的选择。

**WebSocket API** 管理持久的双向连接。API Gateway 处理连接的生命周期，并根据消息内容将消息路由到 Lambda。Lambda 函数不需要管理套接字状态——API Gateway 负责这件事。

**授权选项**（考试会考的那些）：

**Cognito 用户池授权方**验证来自 Cognito User Pool 的 JWT。不需要 Lambda。API Gateway 自己检查令牌。如果有效，请求就放行。

**Lambda 授权方**运行你自己的 Lambda 函数来验证令牌——自定义 JWT、来自第三方身份提供商的 OAuth 令牌、专有格式的 API 密钥。该 Lambda 返回一个 IAM 策略。如果策略允许该操作，请求就继续。

**API 密钥**是在请求头中传递的简单密钥。API 密钥用于按客户端进行速率限制，而不是用于身份验证。不要把它们当作安全机制——它们不是机密，而是标识符。

**限流与使用计划：**

默认情况下，API Gateway 在账户级别允许每秒 10,000 个请求（软限制），突发上限 5,000。超过限制时，客户端会收到 `429 Too Many Requests`——你的后端甚至毫无感觉。当你需要按客户端限制时，可以创建一个使用计划：把它绑定到一个 API 密钥，设置请求速率和每日或每月配额。一个客户端的突发流量不会消耗另一个客户端的配额。

有两个数字值得记住：最大负载是 **10 MB**，默认集成超时是 **29 秒**——如果你的后端耗时更长，网关就会放弃。（自 2024 年起，Regional 和私有 REST API 可以通过配额提升把这个超时调高到 29 秒以上——但考试预期的仍然是 29 秒的默认值。）API Gateway 适用于请求/响应式 API，不适用于长时间运行的任务；对于后者，把工作交给 SQS 或 Step Functions 并立即回复。

"这每个月要花多少钱？"Tom 问。

对于 REST API：每百万次 API 调用 $3.50，外加每 GB 数据传输 $0.09。对于中小流量，它基本上是免费的。对于大流量 API，HTTP API 更低的价格就变得有意义了。

Leo 指着他早些时候写下的 Lambda 触发器列表。"所以 API Gateway 不只是触发 Lambda 的一种方式。它是让 Lambda 用起来像一个真正的 API 的东西。"

"Lambda 函数处理业务逻辑，"Priya 说，"API Gateway 处理它前面的一切——路由、认证、限流、监控。各司其职。"

"那如果有人试图绕过 API Gateway 直接调用 Lambda 呢？"

"Lambda 的执行策略只允许来自 API Gateway 的调用，"Priya 说，"Lambda 上的基于资源的策略拒绝其他一切。"

现实是：无服务器有其自身的运维复杂性——调试分布式 Lambda 函数、管理冷启动、理解并发限制。它并不更简单，只是不同。

"等等——可是*为什么*无服务器'并不更简单'？"Maya 问，"它的卖点不就是消除运维负担吗？"

"它消除了一部分运维负担，"Leo 说，"基础设施预置、打补丁、扩展配置——这些消失了。剩下的是另一类：冷启动管理、对无法 SSH 进入的函数进行分布式追踪、并发限制、管理函数版本和别名、理解层更新如何传播、优雅地应对 15 分钟超时。"

"所以负担转移了，"Priya 说，"从基础设施运维转移到了函数运维。"

"是的。对于很多工作负载——尤其是事件驱动的、小型的、突发性的——这是一笔更划算的交易。对于工程师需要与之交互和调试的长时间运行的应用服务器，EC2 或容器往往仍然是正确的选择。"

你可能会想：无服务器是未来吗？所有东西最终都应该迁移到 Lambda 吗？诚实的答案是：取决于工作负载。无服务器已经统治了事件驱动处理。它在 HTTP API 领域（通过 API Gateway + Lambda）取得了显著进展。它没有取代始终在线的应用服务器、长时间运行的批处理或有状态服务——而且很可能不会，因为那些用例从 Lambda 的模型中得不到好处。"正确的工具"这个问题永远不会消失；它只是随着时间推移应用于不同的选项。

## 优势与局限

**Lambda 的强大之处**：

- 真正的按使用付费——空闲时零费用
- 无需配置的自动扩展
- 没有需要打补丁或维护的服务器
- 慷慨的免费额度（每月一百万次请求，永久免费）
- 与其他 AWS 服务的紧密集成
- RDS Proxy 和 Lambda Layers 解决了 Lambda 最常见的两个痛点（连接池和代码共享），且无需架构层面的改动

**复杂性所在**：

- 冷启动是真实存在的，对于延迟敏感的工作负载需要仔细处理
- 15 分钟执行限制排除了长时间运行的任务
- 调试更困难——没有持久服务器可以 SSH 进入
- 无状态设计要求将所有状态外部化（数据库、缓存、S3）
- 并发限制（每账户默认 1,000 个并发调用）可能在规模扩大时造成节流
- 连接到 VPC 的 Lambda 函数会有额外的延迟和冷启动问题

**没有 SSH 的 Lambda 监控**

第一次 Lambda 函数出问题时，Leo 的本能反应是 SSH 进去看进程。可没有进程可以 SSH 进去。Lambda 的执行环境是短暂且无法访问的。

调试 Lambda 需要学习一套不同的工具：

**CloudWatch Logs**：每次 Lambda 调用都会把它的 stdout/stderr 写入一个 CloudWatch Log Group。结构化日志（JSON 格式）让这些日志可以被筛选。最有用的字段：函数名、调用 ID、时长、错误类型，以及你自定义的关联 ID。

**CloudWatch Metrics**：Lambda 自动发布 Invocations、Duration、Errors、Throttles 和 ConcurrentExecutions 指标。在 Errors 和 Throttles 上设置告警应该是任何 Lambda 部署第一天就做的事。

**AWS X-Ray**：Lambda 的分布式追踪。会增加一点开销（每次调用 2-5 毫秒），但能给你一张展示函数内部时间消耗的火焰图。对冷启动分析至关重要——X-Ray 把初始化阶段与处理程序阶段分开显示。

**Lambda Insights**：Lambda 的增强监控，通过 CloudWatch Lambda Insights 提供。在标准指标之上增加了内存使用、CPU 时间和初始化时长。会稍微多花一点钱，但对生产函数来说值得。

"那如果有人试图通过执行环境入侵呢？"Priya 问，"Lambda 函数运行在隔离的容器里，但如果某个依赖有漏洞，攻击者能不能在我们的 Lambda 里获得代码执行权限？"

缓解措施：保持依赖最小化并及时更新（冷启动分析已经促使 Leo 缩减了包的大小），用 Lambda Layers 对共享库进行版本管理，并为 Lambda 执行角色授予所需的最小权限。如果函数只能写一个特定的 S3 桶、只能查询一个特定的 DynamoDB 表，那么一个被攻破的函数的爆炸半径就被限制在恰好这个范围内。

"Lambda 执行角色的最小权限不是可选项，"Priya 说，"它决定了出问题时损害有多大。"

她说得对。而且和大多数安全建议一样，这同时也是好的工程实践。

## 总结

第 19 章的 SQS/SNS 架构把接收工作和处理工作这两个关注点分开了。Lambda 更进一步：它把处理工作和为处理能力付费这两个关注点也分开了。

- **AWS Lambda** 在不管理服务器的情况下响应事件运行代码。
- **按使用付费**：按调用次数和每 1 毫秒执行时间计费（向上取整）。空闲时零费用。
- 从 0 到数千个并发调用自动扩展。
- **冷启动**：当不存在热执行环境时的初始化延迟。可通过预置并发或轻量级运行时来缓解。
- **Lambda Layers**：多个函数可以引用的共享代码包，减少重复并缩小包体积。
- **RDS Proxy**：通过在 Lambda 与 RDS 之间维护持久数据库连接池，解决 Lambda 的连接耗尽问题。
- **监控**：使用 CloudWatch Logs、Metrics、X-Ray 追踪和 Lambda Insights——没有服务器可以 SSH 进去。
- 最适合：事件驱动、短时运行、突发性或不频繁的工作负载。
- 不理想用于：长时间运行的任务（15 分钟硬性限制）、有状态应用、没有预置并发的高吞吐量低延迟 API。
- **无服务器**是一种设计理念——你管理代码，而非基础设施。运维复杂性是转移了，而不是消失了。

## 考试技巧

*SAA-C03 领域：设计弹性架构（领域 2，任务 2.1）*

- **Lambda + S3**：经典模式——文件上传到 S3 触发 Lambda 进行处理（缩略图生成、病毒扫描、数据转换）。无需服务器。
- **Lambda + SQS**：Lambda 轮询 SQS 并处理批量消息。SQS 提供重试/DLQ 机制。Lambda 提供处理。
- **Lambda + API Gateway**：无服务器 HTTP API。API Gateway 处理路由、身份验证、限流。Lambda 处理业务逻辑。
- **API Gateway 类型：** REST API = 全功能、请求转换、缓存、使用计划。HTTP API = 更简单、更便宜、仅支持 OIDC/OAuth。WebSocket API = 持久双向连接。**授权：** Cognito 授权方 = 原生验证 Cognito JWT。Lambda 授权方 = 自定义令牌验证逻辑。API 密钥 = 按客户端速率限制（不是身份验证）。考试信号："无服务器 REST API"→ API Gateway + Lambda。
- **冷启动信号**："首次请求时延迟峰值"、"响应时间不一致"→ 冷启动。解决方案：预置并发（需要付费）、更小的包、更轻量的运行时。
- **执行限制**：最长 15 分钟。最大内存 10GB。默认 /tmp 临时存储 512MB（最高可配置到 10GB）。这些限制会出现在考试场景中。
- **Lambda 超时错误是无声的**：如果 Lambda 函数超时，它会产生一条 CloudWatch 错误，但不会产生应用层的错误响应。要专门监控 CloudWatch 的 Lambda 超时错误。这正是 Leo 那个 17 分钟的报告生成器第一晚失败时没有触发任何应用层告警的原因。
- **VPC Lambda 冷启动**：VPC 内的 Lambda 函数有额外的冷启动延迟（ENI 预置）。AWS 通过 Hyperplane ENI 大幅改善了这一点，但 VPC Lambda 的冷启动仍然比非 VPC 的慢。对于不需要 VPC 资源的 Lambda 函数（即不连接 RDS、ElastiCache 或其他仅限 VPC 的资源），避免使用 VPC。
- **Lambda 并发**：默认每账户 1,000 个并发执行（可以增加）。**预留并发**：保证函数获得特定数量的执行量；防止其他函数消耗它们。**预置并发**：预热一定数量的执行环境。
- **事件源映射**：将 SQS/DynamoDB Streams/Kinesis 连接到 Lambda 的 Lambda 功能。Lambda 轮询源并批量处理记录。
- **撞上账户限制**："应用在扩展时被节流 / 出现 LimitExceeded"→ 在 **Service Quotas** 中检查该限制并在那里申请提升（许多配额——如 Lambda 并发——是可调整的；有些是硬性限制）。
- **RDS Proxy**：考试信号："Lambda 函数导致数据库连接过多"、"Lambda 引起连接池耗尽"。→ RDS Proxy 维护持久连接并将 Lambda 的短生命周期连接多路复用到这些连接上。
- **Lambda Layers**：考试信号："在多个 Lambda 函数之间共享代码"、"缩小部署包体积"→ Lambda Layers。
- **Lambda + X-Ray**：Lambda 的分布式追踪。考试场景："跨多个 Lambda 函数和服务追踪请求"→ 在 Lambda 上启用 X-Ray 追踪。
- **Lambda Destinations：** 对于异步 Lambda 调用，你可以为成功和失败两种结果分别配置一个 Destination。把成功结果发送到 SQS、SNS、EventBridge 或另一个 Lambda 函数。把失败发送到 SQS 或 SNS 以便告警。对于异步调用，这是优于 DLQ 的首选替代方案，因为它同时捕获成功和失败，而不仅仅是失败。考试信号："把 Lambda 的成功结果路由到另一个服务"或"捕获异步 Lambda 的成功和失败两种结果"→ Lambda Destinations。"仅捕获异步调用的失败消息"→ DLQ 仍然有效，但 Destinations 是更完整的方案。

**练习 2 — SAA-C03 场景**

*场景*：一家公司通过 S3 桶接收供应商发来的产品图片。每张图片需要调整为四种标准尺寸（缩略图、小、中、大）并存回 S3。数量不可预测——有时一天 10 张，有时一天 100,000 张。每张图片的处理必须在 10 分钟内完成。成本必须最小化。

哪种架构最符合这些要求？

A) EC2 实例在 Auto Scaling Group 中通过长轮询监控 S3 桶  
B) 一台专用 EC2 实例使用定时任务每分钟检查 S3 上的新图片  
C) ECS Fargate 任务由 SQS 队列触发，S3 事件发布到队列  
D) S3 事件通知触发 Lambda 函数调整图片大小并将结果存储到 S3

**提示 1**：不可预测的数量有利于缩容到零。哪个选项可以做到这一点？

**提示 2**：每张图片 10 分钟在 Lambda 的 15 分钟限制之内。检查图片缩放工作是否符合 Lambda 的限制。

**提示 3**：全天候运行的专用 EC2 实例成本高且不可扩展。

**答案**：D

**解释**：S3 事件通知在图片上传时触发 Lambda。Lambda 将图片调整为四种尺寸并将结果存储在 S3 中。Lambda 自动从 0 扩展到数千个并发调用，无需预先配置即可处理不可预测的数量。没有图片在处理时零成本。

**为什么不选 A？** ASG 中的 EC2 无法缩容到零——至少有一个实例始终在运行。长轮询 S3 不是原生的 S3 事件机制。对于突发性工作负载，成本高于 Lambda。

**为什么不选 B？** 专用 EC2 实例是单点故障，不可扩展，全天候运行，而且基于定时任务的方法有最多 60 秒的检测延迟。

**为什么不选 C？** ECS Fargate 可以工作，但更复杂（需要容器管理、ECR、任务定义），而且 Fargate 任务的启动需要几十秒到几分钟——远慢于 Lambda 的冷启动——这使它不适合突发性的事件驱动工作。对于这个用例，Lambda 更简单。

"那 $5.47 大部分是通知 Lambda 上的预置并发——那东西不管运不运行都计费。图片缩放程序、清理任务和其余的都落在免费额度之内。"
