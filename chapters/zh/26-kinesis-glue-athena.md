# 第二十六章：理解一切

数据是原始的：时间戳、点击、事件、数字。信息是当数据被组织、处理并赋予上下文后你得到的东西。两者之间的差距就是本章所在的地方。

在不断增长的系统中，这个差距很快就会变得昂贵。

Nimbus 正在产生大量数据。每一个订单：已记录。每一次菜单查看：已记录。每一次餐厅更新：已捕获。每一次客户互动：已追踪。

Tom 有一个问题。

"周五最繁忙的下单时间是什么时候？"

Leo 看着他。"这不在我们的仪表板上。"

"我们能添加吗？"

"数据在 DynamoDB 里。还在 CloudWatch 日志里。还在分析导出任务导出到 S3 的数据里。"Leo 停顿了一下，"在三个不同的地方，以三种不同的格式。"

Maya 补充道："分析导出只在每晚运行一次。如果你想要周五的数据，你得等到周六早上。"

Tom 看着屏幕。"所以我们有数据。我们就是无法使用它。"

这句话描述了现代分析的一半问题。

这就是数据工程问题：你有数据，但它不是你在需要时可以分析的形式。

**三个不同的问题**

Nimbus 的数据问题有三个维度：

**实时流处理**：订单正在现在被下单。你想要看到订单速度的实时仪表板——每分钟多少订单，按区域、按餐厅。数据需要在到达时被处理。

**数据转换**：数据以各种格式（JSON、CSV、Parquet）从不同系统存储在 S3 中。在你可以有效分析它之前，你需要对它进行规范化——相同的模式、相同的格式、已清理、与参考数据联接。

**临时分析**：一旦数据组织好，你想要对它运行 SQL 查询，而不需要先将其加载到数据库中。"给我过去 30 天按收入排名的前 10 家餐厅。"不需要将数据加载到数据库中。

每个问题都是一个不同的挑战。AWS 为每个问题提供了专用的服务：

- **Amazon Kinesis**：实时流数据
- **AWS Glue**：数据转换和编目
- **Amazon Athena**：S3 上的无服务器 SQL 查询

**Amazon Kinesis：实时股票报价机**

**Amazon Kinesis Data Streams** 是一个实时数据流服务。生产者将数据记录发送到流中。多个消费者可以同时从流中读取，每个都以自己的速度。

想象一台股票报价机：价格不断打印出来，每个人都可以读取纸带，纸带不会因为任何单个读者而减慢速度。

对于 Nimbus，当下单时，应用程序发布一个事件到 Kinesis 流：`{ "orderId": "ORD-7741", "restaurantId": "47", "total": 3200, "timestamp": "...", "region": "us-west-2" }`。

此流的消费者：

- 实时仪表板（在事件到达时读取，更新指标）
- 欺诈检测 Lambda（查找异常订单模式）
- 用于永久存储的流到 S3

**Kinesis Data Streams 概念**：

- **分片**：容量的基本单位。一个分片处理 1 MB/s 写入，2 MB/s 读取。
- **保留期**：数据在流中保留 24 小时（默认）到 7 天。
- **序列号**：每条记录都有一个序列号。消费者追踪其在流中的位置。

**Amazon Data Firehose**（以前称为 **Kinesis Data Firehose**）：在流式生产者和 S3、Redshift、OpenSearch 等目的地之间的托管传递服务。它自动缓冲、压缩、转换和传递数据。

对于 Nimbus：Kinesis Data Streams → Amazon Data Firehose → S3（Parquet 格式，压缩，按日期分区）。

**AWS Glue：翻译器**

S3 中的数据是原始的。在你能有效分析它之前，你需要：

- 发现那里有什么及其模式（有哪些列，什么类型）
- 将其转换为一致的格式
- 将不同数据集联接在一起
- 处理错误记录、模式变更、缺失值

**AWS Glue** 是一个完全托管的 ETL（提取、转换、加载）服务。它有两个主要组件：

**Glue Data Catalog**：描述你的 S3 数据的元数据存储——存在哪些表、它们有哪些列、数据文件在哪里。它就像数据湖的图书馆目录卡。

**Glue 爬虫**：自动代理，扫描 S3、推断模式并填充 Data Catalog。在你的 S3 桶上运行爬虫，10 分钟后你就有了所有表的目录。

**Glue 作业**：执行实际转换的无服务器 Spark/Python 作业。你编写转换逻辑（或使用 Glue 的可视化 ETL 工具），Glue 在托管基础设施上运行它。

对于 Nimbus：

1. Glue 爬虫扫描 S3 中的订单数据 → 在 Glue Data Catalog 中创建表定义
2. Glue 作业将原始 JSON 订单事件转换为干净的、分区的 Parquet 格式
3. 转换后的数据以查询优化的布局写回 S3

**Amazon Athena：图书馆员**

**Amazon Athena** 是一个无服务器、交互式查询服务，直接在 S3 数据上运行 SQL 查询。没有需要配置的数据库，没有需要加载的数据。你定义一个表（或使用 Glue Data Catalog），编写 SQL，Athena 对 S3 文件执行查询。

```sql
SELECT 
    restaurant_id,
    COUNT(*) as order_count,
    SUM(total) as revenue
FROM orders
WHERE year='2024' AND month='01'
GROUP BY restaurant_id
ORDER BY revenue DESC
LIMIT 10;
```

Athena 的定价基于查询扫描的数据量。在许多区域，标准 SQL 查询起始价格为每太字节扫描 $5。使用 Parquet 格式（列式）和分区修剪（`WHERE year='2024' AND month='01'`）意味着 Athena 只扫描它需要的文件，这大幅降低了成本。

"我们可以对 30 天的数据运行这个查询，"Leo 说，"如果存储方式正确，成本可能出乎意料地低。"

"对我们能想到的任意问题？"Tom 问。

"任何我们能用 SQL 表达的问题，针对任何我们存储在 S3 中的数据。"

Tom 有一种正在重新计算他一直在丢弃的所有数据价值的表情。

**数据湖架构**

这三个服务结合成所谓的**数据湖架构**——一个集中的 S3 存储库，包含你所有的数据，以及用于处理和查询它的工具：

```
应用程序（订单、菜单、事件）
    |
    | 实时事件
    ↓
Kinesis Data Streams ──→ Amazon Data Firehose ──→ S3（原始）
                                                   |
                                                   | Glue 爬虫发现模式
                                                   ↓
                                              Glue Data Catalog
                                                   |
                                                   | Glue 作业转换
                                                   ↓
                                              S3（干净、Parquet、分区）
                                                   |
                                                   | SQL 查询
                                                   ↓
                                              Amazon Athena
                                                   |
                                                   ↓
                                          商业智能工具
                                       （QuickSight、Tableau 等）
```

原始数据始终保留（在原始 S3 桶中）。转换后的数据可以通过 Athena 查询。新问题总是可以通过在原始数据上运行新的 Glue 作业来回答。

**Amazon Redshift：当 Athena 不够用时**

对于某些用例，Athena 太慢或太贵：

- 具有多个联接的非常复杂的查询
- 每天运行相同查询数千次的仪表板
- 结构化数据的机器学习
- BI 工具的亚秒级响应时间要求

**Amazon Redshift** 是一个完全托管的数据仓库：一个为大型、重复分析工作负载设计的列式分析数据库。与在 S3 中原地查询数据的 Athena 不同，Redshift 将数据加载到优化的仓库存储中，并使用查询优化、排序策略和分布策略来加速复杂分析。

Redshift 对于复杂分析查询明显更快，代价是成本（预置容量）和在查询前加载数据的要求。

**Redshift Serverless** 消除了容量规划负担——你查询，Redshift 扩展。成本按查询计算。

对于 Nimbus 目前的规模：Athena 已经足够。当数据量达到五倍且 BI 工具每天对相同仪表板查询数百次时，Redshift 将变得具有成本效益。

## 优势与局限

**Kinesis Data Streams**：当你的数据连续到达且顺序很重要时使用 Kinesis——点击流、金融交易、IoT 遥测。Kinesis 在分片内保留记录顺序，并允许在配置的保留窗口内重播，这使它与 SQS 有根本性的不同。代价是运维复杂性：在预置模式下，你管理分片容量和消费者行为。对于顺序无关紧要且不需要重播的简单任务队列，SQS 是更简单的选择。

**AWS Glue**：Glue 消除了传统 ETL 集群的基础设施。你编写转换逻辑；AWS 管理 Spark 环境。当转换复杂或数据量很大时，这非常有价值。限制是成本和冷启动——Glue 作业有几分钟的启动延迟，使它们不适合近实时转换。对于简单的文件格式转换（CSV 到 Parquet），与 Lambda 函数或轻量级脚本相比，Glue 的开销可能不值得。

**Amazon Athena**：Athena 允许你使用标准 SQL 查询 S3 数据，无需管理基础设施。关键限制是成本：Athena 按扫描的数据量收费。对未格式化的 10TB 表运行的查询成本明显高于对仅扫描 200GB 的 Parquet 格式、分区表运行的相同查询。在生产中运行 Athena 之前，始终使用列式格式（Parquet 或 ORC）并对数据进行分区。没有这些优化，Athena 账单可能会让你意外。

## 总结

- **Amazon Kinesis**：实时数据流。生产者写入记录；消费者以自己的速度读取。Amazon Data Firehose 然后可以将流数据传递到 S3、Redshift 和其他目的地，减少运维工作。
- **AWS Glue**：ETL 和数据编目。爬虫发现模式；作业转换数据；Data Catalog 使数据可被 Athena 和其他工具发现。
- **Amazon Athena**：S3 上的无服务器 SQL。使用标准 SQL 查询 S3 中的任何数据。按扫描的 TB 计费——使用 Parquet 和分区来最小化成本。
- **Amazon Redshift**：托管数据仓库，用于高性能分析。将数据加载进来，为重复的分析查询优化，快速在仓库规模上查询。
- **数据湖模式**：原始数据到 S3 → Glue 转换 → Athena 查询 → BI 工具可视化。

## 考试技巧

*SAA-C03 领域：设计高性能架构（领域 3，任务 3.5）*

- **Kinesis 与 SQS**：Kinesis = 有序、实时流、多个消费者、在保留窗口内重播。SQS = 任务队列，每条消息处理一次。"多个消费者同时读取同一流" → Kinesis。"每条消息一个工作器" → SQS。
- **Athena 考试信号**："S3 上的无服务器 SQL"、"在不将数据加载到数据库的情况下分析 S3 数据"、"按查询付费" → Athena。
- **Athena 成本优化**：列式格式（Parquet 或 ORC）+ 分区大幅减少扫描数据量和成本。考试可能会问如何降低 Athena 成本。
- **Glue 爬虫**："自动发现 S3 数据的模式" → Glue 爬虫。
- **Amazon Data Firehose**："自动将流数据加载到 S3/Redshift/OpenSearch，无需管理消费者" → Amazon Data Firehose。旧材料可能仍称其为 Kinesis Data Firehose。
- **Redshift 与 Athena**：Redshift 用于对固定数据集的高频、复杂查询（BI 仪表板）。Athena 用于对频繁变化的 S3 数据的临时查询。
- **EMR（Elastic MapReduce）**：AWS 托管的 Hadoop/Spark 集群。当提到"现有 Hadoop/Spark 工作负载"或"自定义数据处理框架"时，考试会使用这个。Glue 是大多数用例的托管替代方案。

**练习 2 — 考试练习**

*场景*：一家共享出行公司想要分析行程数据。每天完成 100 万次行程。行程记录以 JSON 文件存储在 S3 中（每条约 2KB）。分析团队想要运行临时 SQL 查询，如"上周按城市的平均行程时长"。查询应在 2 分钟内完成。存储成本应最小化。团队每周运行 20-30 次查询。

哪种架构最符合这些要求？

A) 每天将行程数据加载到 RDS PostgreSQL；使用标准 SQL 查询  
B) 使用 AWS Glue 将 JSON 转换为按日期和城市分区的 Parquet 格式；使用 Amazon Athena 查询  
C) 使用 Amazon Data Firehose 将行程数据传递到 Amazon Redshift；使用 Redshift 查询  
D) 将行程数据加载到 DynamoDB 并使用 PartiQL 进行 SQL 查询

**提示 1**：每周 20-30 次查询频率很低。哪种服务对于偶尔查询最具成本效益？

**提示 2**：Parquet 格式 + 分区大幅减少 Athena 扫描的数据量——因此降低成本。

**提示 3**：每天 100 万次行程 × 2KB = 约 2GB。一周约 14GB。按 Athena $5/TB，即使没有优化，这也是负担得起的。

**答案**：B

**解释**：Glue 将 JSON 转换为 Parquet（列式格式大幅减少扫描数据），按日期和城市分区（分区修剪意味着"上周"查询只扫描 7 天的分区）。Athena 使用标准 SQL 直接查询 S3。对于每周 20-30 次查询，按查询付费的 Athena 比始终运行的 Redshift 极具成本效益。

**为什么不选 A？** 每天将 2GB 数据加载到 RDS，然后查询，需要全天候运行的数据库实例。对于每周 20-30 次查询，这是严重过度设计且昂贵的。

**为什么不选 C？** Redshift 对于每天对同一数据集的高频查询（数百次）具有成本效益。对于每周 20-30 次查询，始终运行的 Redshift 集群的成本远高于 Athena 的按查询定价。

**为什么不选 D？** DynamoDB 是一个针对基于键的访问优化的键值/文档存储，而非临时分析查询。DynamoDB 上的 PartiQL 不支持所描述的 GROUP BY 聚合类型。

Tom 运行了第一个 Athena 查询。

"上季度按收入排名的前 10 家餐厅，"他说。

12 秒后，结果出现了。

他盯着它们看。
