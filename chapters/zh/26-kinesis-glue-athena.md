**三个不同的问题**

Nimbus 的数据问题有三个维度：

**实时流处理**：订单此时此刻正在产生。你想看到一个订单速度的实时仪表板——每分钟多少单，按区域、按餐厅。数据需要在到达时被处理。

**数据转换**：数据来自各个系统，以不同的格式（JSON、CSV、Parquet）存放在 S3 中。在分析之前，你需要先对它进行规范化——相同的模式、相同的格式、清理干净、与参考数据联接。

**临时分析**：数据组织好之后，你想直接对它运行 SQL 查询，而不必先把数据加载进数据库。"给我过去 30 天按收入排名的前 10 家餐厅。"不需要把数据加载到数据库中。

每一个都是独立的问题。AWS 为每个问题都提供了专门的服务。

**实时流：数据的股票报价机**

想象一台股票报价机——那种把股价打印在连续纸卷上的机器。价格一变动就被打印出来。任何想知道当前价格的人都可以读纸带。没有人需要等别人；无论有多少人在读，纸带都照常打印。

这就是实时数据流的模型。生产者在事件发生时发送数据。多个消费者可以同时读取流，各自按自己的节奏，各自获得完整的画面。

**Amazon Kinesis Data Streams** 就是 Nimbus 的这台机器。当有订单下达时，应用程序向 Kinesis 流发布一个事件：`{ "orderId": "ORD-7741", "restaurantId": "47", "total": 3200, "timestamp": "...", "region": "us-west-2" }`。

这个流的消费者：

- 实时仪表板（在事件到达时读取，更新指标）
- 欺诈检测 Lambda（查找异常订单模式）
- 一条流向 S3 的持久化存储通道

**Kinesis Data Streams 概念**：

- **分片（Shard）**：容量的基本单位。一个分片处理 1 MB/s 写入，2 MB/s 读取。
- **保留期**：数据在流中保留 24 小时（默认），通过 Extended Data Retention（扩展数据保留）可延长至 **365 天**（1 年）。
- **序列号**：每条记录都有一个序列号。消费者借此追踪自己在流中的位置。

**Amazon Data Firehose**（前身为 **Kinesis Data Firehose**）：介于流式生产者与 S3、Redshift、OpenSearch 等目的地之间的托管传递服务。它自动完成缓冲、压缩、转换和传递。

对于 Nimbus：Kinesis Data Streams → Amazon Data Firehose → S3（Parquet 格式，已压缩，按日期分区）。

"我已经部署好了——哦。"Leo 没有先计算写入吞吐量就把分片数设成了一。以 Nimbus 的订单量，一个分片足够了。他在别人发现自己是靠猜的之前确认了这一点。

**翻译器：让原始数据有意义**

S3 中的数据是原始的。要想高效地分析它，你需要先弄清楚里面有什么，把它转换成一致的格式，把不同的数据集联接到一起，并处理坏记录和缺失值。

这是专门的翻译层该干的活。

**AWS Glue** 是一个完全托管的 ETL（提取、转换、加载）服务。它有两个主要组件：

**Glue Data Catalog**：描述你的 S3 数据的元数据存储——存在哪些表、它们有哪些列、数据文件在哪里。它就像数据湖的图书馆卡片目录。

**Glue 爬虫（Crawlers）**：自动代理，负责扫描 S3、推断模式并填充 Data Catalog。在你的 S3 桶上运行一次爬虫，10 分钟后你就拥有了所有表的目录。

**Glue 作业（Jobs）**：执行实际转换的无服务器 Spark/Python 作业。你编写转换逻辑（或使用 Glue 的可视化 ETL 工具），Glue 在托管基础设施上运行它。

对于 Nimbus：

1. Glue 爬虫扫描 S3 中的订单数据 → 在 Glue Data Catalog 中创建表定义
2. Glue 作业把原始 JSON 订单事件转换成干净的、分区的 Parquet 格式
3. 转换后的数据以查询优化的布局写回 S3

**当 ETL 崩溃时：模式演进问题**

Glue 管道在最初的三周里运行得干干净净。然后，餐厅合作伙伴 #412 在他们的菜单导出中加了一个新字段：`allergen_tags`。这个字段是一个字符串数组——`["gluten", "dairy", "nuts"]`——出现在这家餐厅的每晚数据导出里。

Glue 作业的模式是严格的。它被写成只接受订单 JSON 中的特定字段。当它遇到 `allergen_tags` 这个不在模式中的字段时，Glue 作业失败了。

来自 47 家餐厅（它们都使用与合作伙伴 #412 相同的菜单导出格式）的六个小时的订单数据堆积在 S3 中，没有被处理。本该让昨晚的订单在早晨可供查询的夜间 Glue 任务，在凌晨 2:47 停了下来，并向 CloudWatch 写入了一条失败记录。

Tom 是在早上 9 点尝试运行一个 Athena 查询、却发现过去 12 小时的数据返回 `0 rows returned` 时才发现的。

"ETL 因为源数据变了就崩溃了？"Leo 解释完事情经过后，Maya 问。

"ETL 崩溃是因为它不知道如何处理模式变更，"Leo 说，"我们写了一个严格的作业，要求字段必须恰好是这些。当一个新字段出现时，它就慌了。"

"那如果有人试图通过模式变更搞破坏呢？"Priya 问，"一个恶意的餐厅合作伙伴故意提交意料之外的字段来搞垮管道？"

这个问题值得认真考虑。一个遇到意外输入就崩溃的 ETL 管道本身就是一个拒绝服务攻击的入口：提交一种不寻常的数据格式，搞垮管道，于是这家餐厅（以及所有共用该格式的餐厅）的处理全部停摆。

修复方案分两部分：

**Glue 模式演进**：Glue 的动态帧支持模式演进——不在预期模式中的字段会被透传，而不是导致失败。启用方式是在作业脚本中使用 DynamicFrames 而不是 DataFrames，并在附加选项中设置 `mergeSchema`。新字段会在下一次爬虫运行时自动添加到模式中。

```python
# Before (strict, breaks on new fields)
datasource = glueContext.create_dynamic_frame.from_catalog(
    database="nimbus_db",
    table_name="orders"
)

# After (schema evolution enabled)
datasource = glueContext.create_dynamic_frame.from_catalog(
    database="nimbus_db",
    table_name="orders",
    additional_options={"mergeSchema": "true"}
)
```

**Glue 作业告警**：管道故障在 Tom 发现之前悄无声息地持续了大约六个小时。针对 Glue 作业运行状态（`FAILED`）的 CloudWatch 告警本可以在 5 分钟内通知值班工程师。这个告警的成本：每月一毛钱——实际上等于免费（指标本身不收费，且前十个告警在免费套餐范围内）。

"六个小时的数据在 S3 里没人处理，"Leo 在手动重跑 Glue 作业补上进度后说，"什么也没丢——但分析数据就落后了那么久。如果我们有那个告警，延迟会是 30 分钟。"

更广泛的教训是：处理外部数据的 ETL 管道必须能够优雅地处理模式变更。外部合作伙伴——餐厅、支付服务商、配送服务——一定会改变他们的数据格式。管道决不能对这些变化如此脆弱。

**查询层：直接在 S3 上跑 SQL**

现在数据已经在 S3 里了，是 Parquet 格式，按日期分区。最后一块拼图：一种无需先把数据加载进数据库就能对它提问的方式。

**Amazon Athena** 是一个无服务器的交互式查询服务，直接对 S3 数据运行 SQL 查询。不需要预置数据库，不需要加载数据。你定义一个表（或使用 Glue Data Catalog），写 SQL，Athena 就对 S3 文件执行查询。

```sql
SELECT 
    restaurant_id,
    COUNT(*) as order_count,
    SUM(total) as revenue
FROM orders
WHERE year='2024' AND month='09'
GROUP BY restaurant_id
ORDER BY revenue DESC
LIMIT 10;
```

Athena 的定价基于查询扫描的数据量。在 us-east-1、us-west-2 以及大多数主要区域，标准 SQL 查询每扫描一太字节数据收费 $5。使用 Parquet 格式（列式）配合分区修剪（`WHERE year='2024' AND month='09'`），意味着 Athena 只扫描它需要的文件，从而大幅降低成本。

"我们可以对 30 天的数据运行这个查询，"Leo 说，"如果存储方式得当，成本可能低得出人意料。"

"它怎么能这么便宜？"Maya 问，"如果它扫描的是太字节级的数据，怎么会不贵？"

Leo 解释了 Parquet。在基于行的格式（JSON、CSV）中，一个只需要二十列中两列的查询不得不读完全部二十列。在像 Parquet 这样的列式格式中，它只读需要的那两列。对于一个 50TB 的数据集，一个优化良好的查询可能只扫描 200GB。按 $5/TB 计算，那是一美元。

"那如果有人不小心查了整张表呢？"Maya 追问。

"那才是真正的成本风险，"Leo 说。

你也许会想：既然 Athena 按扫描的太字节数收费，一条写得很糟的查询会不会产生一笔意外的大账单？会——而且这种事在真实的生产环境中确实会发生。一条针对未优化的 50TB 表的查询，花费可能超过你整个月的 S3 账单。这就是为什么 Parquet 格式和分区不是可选的优化——它们本身就是成本控制手段。Athena 还支持工作组（workgroup）查询扫描限额，为单条查询允许扫描的数据量设置上限。

"对我们能想到的任意问题都行？"Tom 问。

"任何我们能用 SQL 表达的问题，针对任何我们存储在 S3 中的数据。"

Tom 在 Leo 的笔记本电脑前坐下，写下了第一条查询：

```sql
SELECT
    r.restaurant_id,
    r.restaurant_name,
    AVG(EXTRACT(EPOCH FROM (o.confirmed_at - o.notification_sent_at)) / 60) 
        AS avg_confirmation_minutes,
    COUNT(DISTINCT c.customer_id) AS unique_customers,
    COUNT(DISTINCT CASE WHEN c.order_count > 1 THEN c.customer_id END) 
        AS returning_customers,
    ROUND(
        COUNT(DISTINCT CASE WHEN c.order_count > 1 THEN c.customer_id END) * 100.0 /
        NULLIF(COUNT(DISTINCT c.customer_id), 0),
        2
    ) AS reorder_rate_pct
FROM orders o
JOIN restaurants r ON r.restaurant_id = o.restaurant_id
JOIN (
    SELECT customer_id, restaurant_id, COUNT(*) AS order_count
    FROM orders
    WHERE year >= '2024'
    GROUP BY customer_id, restaurant_id
) c ON c.customer_id = o.customer_id AND c.restaurant_id = o.restaurant_id
WHERE o.year = '2024'
  AND o.status = 'delivered'
GROUP BY r.restaurant_id, r.restaurant_name
ORDER BY avg_confirmation_minutes ASC
LIMIT 20;
```

查询运行了 11 秒。结果：20 家餐厅，按平均确认时间从快到慢排序，复购率并列展示。

Tom 盯着输出结果。

确认最快的那些餐厅——平均在 3-4 分钟内确认订单——平均复购率是 41%。确认最慢的餐厅（平均确认时间 18-22 分钟）复购率是 13%。

"确认快的餐厅获得了三倍的回头客生意，"Tom 说。

"这个差距太大了，"Maya 说，"为什么确认速度会对复购率影响这么大？"

"因为顾客下了单之后就坐在那儿盯着手机，"Leo 说，"如果确认在 3 分钟内到来，他们就感到踏实。如果 22 分钟才到——或者根本不来——他们就会焦虑。焦虑本身就是产品的失败，哪怕食物最后好好地送到了。"

"这是一个产品洞察，"Maya 说，"不只是一个分析洞察。我们应该把餐厅的确认时长基准跟品类平均值做对比展示给他们看。"

那条 Athena 查询扫描了 1.2 GB 的数据（两个月的订单，Parquet 格式，按年和月分区）。成本：$0.006。

半美分。换来的是一个商业洞察，它改变了 Nimbus 设计餐厅入驻流程的方式——优先为哪些餐厅安排成功辅导、在合作伙伴 SLA 中设定怎样的确认时间目标。

Tom 的表情，像是一个正在重新计算自己一直在白白扔掉的所有数据有多值钱的人。

"那如果有人试图从查询层入侵呢？"Priya 问，"或者只是某个分析师不小心从原始订单数据里导出了客户地址？客户 PII、订单历史、财务记录——到底谁来控制哪些表是可见的？"

她话音未落，Leo 也意识到了运维层面的问题：怎样阻止某个团队跑一条灾难性的全表扫描，一条查询就产生 $500 的 Athena 账单？

**Athena 工作组（Workgroups）**同时解决了这两个问题。

工作组是一种命名配置，它把 Athena 用户分组并应用共享设置：查询结果位置、加密，以及——关键的——按查询的数据扫描限额。

```
Workgroup: analytics-team
  Query scan limit: 10 GB per query
  Action on limit exceeded: Cancel query

Workgroup: engineering-team
  Query scan limit: 100 GB per query
  Action on limit exceeded: Warn only

Workgroup: finance-reports
  Query scan limit: 1 GB per query
  Action on limit exceeded: Cancel query
```

`analytics-team` 工作组里的分析师无法不小心扫描 50TB 数据并产生 $250 的 Athena 费用。一旦查询将超出 10GB 的数据扫描量，它就会被取消。分析师看到一条错误消息，就知道自己需要加上分区过滤条件。

工作组还为每个团队强制使用独立的结果位置：工程团队的查询结果写到 `s3://nimbus-query-results/engineering/`；财务团队的结果写到 `s3://nimbus-query-results/finance/`。团队之间无法互相访问查询结果。

IAM 控制哪些用户可以使用哪个工作组。运行自动化报表的 Lambda 函数使用 `finance-reports` 工作组（限额收得很紧）。排查生产问题的工程师使用 `engineering-team` 工作组（限额更宽，只警告不取消）。包含客户 PII 的原始事件表，则通过 Glue Data Catalog 表上的 IAM 条件限定为只有 `engineering-team` 工作组可以访问。

"这不只是成本控制，"Priya 说，"这是访问控制。工作组就是执行点。"

这完整地回答了她的问题。任何跳过访问控制的数据管道讨论，最终都会演变成一起合规事故——而在这里，分析团队只能看到聚合后的订单表，包含客户 PII 的原始事件则始终被挡在一道明确的 IAM 授权之后。Glue Data Catalog 不只是一个模式目录。它是一道访问控制边界。

"这不是额外的工作，"Priya 说，"这本身就是设计。"

**数据湖架构**

这三个服务组合成了所谓的**数据湖架构**——一个集中存放所有数据的 S3 仓库，外加处理和查询它的工具：

```
应用程序（订单、菜单、事件）
    |
    | 实时事件
    ↓
Kinesis Data Streams ──→ Amazon Data Firehose ──→ S3（原始）
                                                   |
                                                   | Glue 爬虫发现模式
                                                   ↓
                                              Glue Data Catalog
                                                   |
                                                   | Glue 作业转换
                                                   ↓
                                              S3（干净、Parquet、分区）
                                                   |
                                                   | SQL 查询
                                                   ↓
                                              Amazon Athena
                                                   |
                                                   ↓
                                          商业智能工具
                                       （QuickSight、Tableau 等）
```

原始数据始终保留（在原始的 S3 桶中）。转换后的数据可以通过 Athena 查询。新的问题总是可以通过在原始数据上运行新的 Glue 作业来回答。

**Amazon Redshift：当 Athena 不够用时**

对于某些用例，Athena 太慢或太贵：

- 包含大量联接的非常复杂的查询
- 每天把同一条查询跑数千次的仪表板
- 针对结构化数据的机器学习
- BI 工具的亚秒级响应时间要求

**Amazon Redshift** 是一个完全托管的数据仓库：一个为大型、重复性分析工作负载设计的列式分析数据库。与在 S3 中原地查询数据的 Athena 不同，Redshift 把数据加载进优化的仓库存储，并利用查询优化、排序策略和分布策略来加速复杂分析。

如果你的数据量不大、查询频率也低（每周或每月），那么 Athena 配上组织良好的 S3 数据就足够了，而且几乎免费——但如果你每天把同样的分析仪表板跑上几百次，Redshift 预先优化的列式存储会更快，并且尽管它要求提前加载数据，最终反而更具成本效益。

Redshift 在复杂分析查询上明显更快，代价是成本（预置容量）以及查询前必须先加载数据。

**Redshift Serverless** 免去了容量规划的负担——你只管查询，Redshift 负责伸缩。成本基于实际使用的计算容量，以 **RPU 小时**计量并按秒计费（每次激活有 60 秒的最低计费时长），外加按 GB·月计费的托管存储——仓库闲置时计算部分分文不收。（按查询计价的是 Athena：每扫描 1 TB 收 $5。）

对于 Nimbus 目前的规模：Athena 足够了。当数据量达到现在的五倍、且 BI 工具每天对相同的仪表板查询数百次时，Redshift 才会变得具有成本效益。

**当 Athena 是错误的工具时**

"那代价是什么？"Maya 问，"我们为什么不把 Athena 用在所有事情上？无服务器、按查询付费、零基础设施——听起来很完美啊。"

Athena 不是正确答案的几种情形：

**高频仪表板**：一个每 30 秒刷新一次、每分钟跑 50 条查询的面向客户的分析仪表板，不是好的 Athena 用例。按 $5/TB 扫描计费，这些查询必须优化到极致才能在这种频率下保持成本可控。对于有亚秒级响应时间要求的仪表板，Redshift 或者一个预聚合的数据库（哪怕是 RDS）更合适。

**低延迟要求的运营类查询**：如果客服坐席需要在 500 毫秒内查到某个具体订单，Athena 不是合适的工具——DynamoDB 查找或一条 RDS 查询才是。Athena 为分析吞吐量优化，而不是为运营延迟优化。即使是针对小数据集的、调优良好的 Athena 查询，也有 1-3 秒的冷启动开销。

**事务系统**：Athena 是只读的。你不能在 Athena 中 INSERT、UPDATE 或 DELETE 记录（除非通过 Lake Formation 或 Iceberg 表格式等特定集成，而它们自有其复杂性）。对于运营类的写入工作负载，请使用事务型数据库。

**非常小且频繁变化的数据集**：如果你的数据集每分钟都在变、总共也只有 1GB，那么把它加载进 RDS 或 DynamoDB 再查询，比对可能已经过时的 S3 文件运行 Athena 查询更简单也更快。Athena 查询的是查询发起那一刻的 S3 文件——如果文件是 2 分钟前写入的，你得到的新鲜度就是这样。

由此浮现出的模式是：Athena 非常适合针对 S3 数据的大规模、低频次、临时性的分析查询。任何运营性、事务性或要求亚秒级延迟的场景，都应该使用相应的运营数据库。

**Kinesis 与 SQS：澄清困惑**

这是每一场数据架构讨论中都会冒出来的问题。Kinesis 和 SQS 都和消息打交道。各自什么时候用？

困惑来自表面上的相似：两者都接收来自生产者的消息。两者都把消息送达消费者。两者都是 AWS 托管服务。但它们的数据模型有着根本性的不同。

**SQS（Simple Queue Service）**是一个任务队列。你放进一条消息。一个消费者把它取出来处理。处理完成后，消息被删除。如果你有十个消费者，每条消息恰好交给其中一个。消息一经消费就没了。

**Kinesis Data Streams** 是一份日志。你放进一条记录。每个消费者都能读到每条记录。消费者 A 读全部记录。消费者 B 也读全部记录，按它自己的节奏。任何一个消费者都不会删除记录——记录一直留在流中，直到保留期到期。你可以随时增加第三个消费者，它还可以从流的起点（保留窗口之内）开始读。

"什么情况下你会真的希望每个消费者都看到每条消息？"Maya 问。

答案就是 Kinesis 大放异彩的用例：

**实时仪表板 + 欺诈检测 + S3 归档**：三者同时消费同一条订单事件流。如果用 SQS，你得发布到三个独立的队列——而且发布方必须知道所有三个消费者的存在。用 Kinesis，生产者只发布一次；任意数量的消费者都可以独立读取。

**重播**：某个消费者宕了 2 小时（撞上 Lambda 并发上限，或下游服务挂了）。用 SQS，那些消息早已被删除（或者只有一个有限的可见性超时）。用 Kinesis，消费者从上一个检查点恢复，把错过的 2 小时记录补处理完。数据一直保留在流中（通过 Extended Data Retention 最长可达 365 天）。

**分片内有序**：相同分区键的记录总是落到同一个分片，从而保持顺序。对于一个需要把代码为 `AMZN` 的全部交易按顺序处理的股票交易系统，Kinesis 能保证这一点。SQS FIFO 提供按组的有序性，但吞吐量更低（标准模式下配合批处理每个队列最高 3,000 条消息/秒——高吞吐模式可提升到数万条——而 Kinesis 每个分片是 1 MB/s 或 1,000 条记录/秒，且可以按需要乘上任意多个分片）。

决定性的问题是：**每条消息是否只需要被恰好一个消费者消费然后丢弃？** → SQS。**每条消息是否需要被多个消费者独立看到，或者你是否需要重播能力？** → Kinesis。

对于 Nimbus 的实时仪表板：Kinesis。多个消费者（仪表板、欺诈检测、S3 归档）同时读取同一条流。

对于 Nimbus 的订单处理队列（一个订单下达 → 一个 ECS 任务处理它）：SQS。单个消费者，不需要重播，不需要扇出。

## 数据可视化：Amazon QuickSight

Athena 负责查询数据。Glue 负责准备数据。但总有人需要在某个时刻看到一张图表——而且不是靠在控制台里跑 SQL 查询。

"我们真的还需要再加一个服务吗？"Maya 问，"我就不能把 Athena 的结果导出到电子表格里吗？"

"查一次的话，可以，"Tom 说。他一脸早就试过的表情。"但要做一个跟全团队共享的仪表板，那就是每天早上一张新表格。"

**Amazon QuickSight** 是 AWS 的托管商业智能（BI）服务。它直接连接 Athena、S3、RDS、Redshift 等数据源，让你无需单独的 BI 服务器就能构建仪表板和可视化。

关键特性：

- **SPICE**（Super-fast, Parallel, In-memory Calculation Engine，超高速并行内存计算引擎）：QuickSight 可以把数据集导入它的内存引擎，实现大规模下亚秒级的查询性能，而不必每次加载仪表板都重新查询 Athena
- **ML Insights：**内置异常检测和预测——不需要数据科学背景
- **嵌入式仪表板：**你可以通过 URL 把 QuickSight 仪表板嵌入到自己的 Web 应用中

Tom 把 QuickSight 连上了 Athena 数据源，一个下午就做出了一个可用的仪表板，显示每日订单、各餐厅收入和转化漏斗。

"这个每月多少钱？"他问——然后不等别人开口就自己回答了。"QuickSight 大约是每位作者（构建仪表板的人）每月 $24，每位读者每月 $3。我们有四个人会用它。"

"所以一个月一百美元左右，"Maya 说。

"换来一个本来需要单独运行一台分析服务器的 BI 服务，"Priya 说，"是的。"

Tom 发布了仪表板。第二天早上，全团队不再跑 Athena 查询，而是打开了一个 URL。

> **考试技巧 — QuickSight**
>
> QuickSight 是 AWS 的托管 BI 与可视化服务。连接 Athena、S3、Redshift、RDS。SPICE 是为重复性仪表板查询提速的内存查询引擎。考试触发词："AWS 上的商业智能仪表板"或"可视化来自 Athena/Redshift 的数据" → QuickSight。

## 治理数据湖：AWS Lake Formation

随着 Nimbus 数据湖的增长，数据访问成了一个治理问题。

"谁可以查询原始交易日志？"在下一次架构评审上，Priya 问，"谁能看到客户 PII？谁能访问财务汇总表？"

"工程团队有完全访问权限，"Leo 说，"分析团队可以访问聚合表。财务可以访问收入表。"

"配置在哪儿？"

Leo 停顿了一下。"在……几个不同的地方。S3 桶策略、IAM 策略、Glue 目录权限。"

"三个独立的系统，而且它们必须保持一致，"Priya 说，"那我们新增一名分析师时会怎样？或者当我们决定对分析团队限制某一特定列——比如客户电话号码——的访问时呢？"

这个问题暴露了缺口。同时在 S3 桶策略、IAM 和 Glue Data Catalog 之间管理细粒度的数据访问，是脆弱的。

**AWS Lake Formation** 是一个为数据湖集中管理访问控制的托管服务。你不再需要分别管理桶策略、IAM 策略和 Glue 目录权限，Lake Formation 提供了一个统一的地方，对你的数据授予列级、行级和表级权限。

关键特性：

- 建立在 S3 和 Glue Data Catalog 之上——不需要迁移数据
- **细粒度访问控制：**把对特定表、特定列、甚至经过过滤的行的访问权授予特定的用户或角色——相当于在 S3 数据上实现数据库级别的权限
- **数据过滤：**当用户通过 Athena 查询一张由 Lake Formation 治理的表时，Lake Formation 会自动滤掉他们无权查看的列或行

Priya 用 Lake Formation 搭建了三个权限层级，Rafael 负责起草列级规则：工程角色看到所有表和所有列。分析角色看到聚合后的订单表，但看不到客户 PII 列。财务角色看到收入表，其中客户标识符被打码。

"所以分析师跑的还是同一条 Athena 查询，"Leo 确认道，"但 Lake Formation 会拦截它，把他们无权查看的列剥掉？"

"正确。过滤是自动的。分析师甚至不需要知道这件事在发生——而且他们也没法绕过去直接查原始的 S3 文件，因为 Lake Formation 在目录层面控制着访问。"

"这不是额外的工作，"Priya 说，"这本身就是设计。"

> **考试技巧 — Lake Formation**
>
> Lake Formation 为构建在 S3 和 Glue Data Catalog 之上的数据湖集中管理访问控制。支持表级、列级和行级的细粒度权限。考试触发词："限制对 S3 数据湖中特定列的访问"或"集中数据湖治理" → Lake Formation。与纯 IAM 的关键区别：Lake Formation 能强制执行 IAM 策略本身无法表达的列级与行级过滤。

## 优势与局限

**Kinesis Data Streams**：当数据连续到达且顺序很重要时使用 Kinesis——点击流、金融交易、IoT 遥测。Kinesis 在分片内保持记录顺序，并允许在配置的保留窗口内重播（默认 24 小时，通过 Extended Data Retention 最长 365 天），这使它与 SQS 有着根本性的不同。代价是运维复杂性：在预置模式下，分片容量和消费者行为都由你来管理。对于顺序无关紧要、也不需要重播的简单任务队列，SQS 是更简单的选择。

**AWS Glue**：Glue 消除了传统 ETL 集群的基础设施。你写转换逻辑；AWS 管理 Spark 环境。当转换复杂或数据量很大时，这非常有价值。局限在于成本和冷启动——Glue 作业有几分钟的启动延迟，因此不适合近实时转换。对于简单的文件格式转换（CSV 到 Parquet），相比一个 Lambda 函数或一段轻量脚本，Glue 的开销可能并不划算。

**Amazon Athena**：Athena 让你用标准 SQL 查询 S3 数据，没有任何需要管理的基础设施。关键约束是成本：Athena 按扫描的太字节数收费。一条把 10 TB 的表整个扫一遍的查询，花费会显著高于同一条只扫描 200 GB 的、针对 Parquet 格式分区表的查询。在生产环境中运行 Athena 之前，务必使用列式格式（Parquet 或 ORC）并对数据进行分区。没有这些优化，Athena 账单可能让你大吃一惊。

## 总结

第二十五章的网络工作让 Nimbus 的数据管道成为可能。本章讲的就是这条管道的用途：把 Nimbus 一直在生成的所有数据真正变得可见、可用。

- **Amazon Kinesis**：实时数据流。生产者写入记录；消费者按自己的节奏读取。Amazon Data Firehose 随后可以把流数据传递到 S3、Redshift 和其他目的地，运维工作更少。
- **AWS Glue**：ETL 与数据编目。爬虫发现模式；作业转换数据；Data Catalog 使数据能被 Athena 和其他工具发现。
- **Amazon Athena**：S3 上的无服务器 SQL。用标准 SQL 查询 S3 中的任何数据。按扫描的 TB 计费——使用 Parquet 和分区把成本降到最低。
- **Amazon Redshift**：面向高性能分析的托管数据仓库。把数据加载进来，为重复性分析查询做优化，在仓库规模上快速查询。
- **数据湖模式**：原始数据进 S3 → Glue 转换 → Athena 查询 → BI 工具可视化。
- **Glue 模式演进**：处理外部数据的 ETL 管道必须优雅地处理模式变更。使用 DynamicFrames 并设置 `mergeSchema: true`，避免上游数据增加新字段时管道崩溃。
- **Athena 工作组**：按团队设置数据扫描限额和结果位置。成本控制与访问控制集于一处配置。任何多团队的 Athena 部署都不可或缺。
- **Kinesis 与 SQS**：Kinesis 用于扇出给多个消费者以及重播能力。SQS Standard 用于简单的任务队列；SQS FIFO 用于有序、去重的任务处理。决定性问题：是每个消费者都需要看到每条消息，还是每条消息只交给一个消费者？
- **Athena 不适用的场景**：高频仪表板（用 Redshift）、运营类查询（用 RDS 或 DynamoDB）、非常小且频繁变化的数据集（直接用数据库）。
- **Amazon QuickSight**：AWS 的托管 BI 服务。连接 Athena、S3、Redshift 和 RDS 来构建仪表板，无需单独运行 BI 服务器。SPICE 是为重复性仪表板查询提速的内存引擎。
- **AWS Lake Formation**：为 S3 + Glue Data Catalog 上的数据湖集中管理访问控制。支持列级、行级和表级权限——这是仅靠 IAM 无法表达的细粒度数据治理。

## 考试技巧

*SAA-C03 领域：设计高性能架构（领域 3，任务 3.5）*

- **Kinesis 与 SQS**：Kinesis = 有序、实时流、多个消费者、在保留窗口内重播（默认 24 小时，最长 365 天）。SQS = 任务队列，每条消息处理一次。"多个消费者同时读取同一条流" → Kinesis。"每条消息一个工作器" → SQS。
- **Athena 考试信号**："S3 上的无服务器 SQL"、"在不把数据加载进数据库的情况下分析 S3 数据"、"按查询付费" → Athena。
- **Athena 成本优化**：列式格式（Parquet 或 ORC）+ 分区可大幅减少扫描数据量和成本。考试可能会问如何降低 Athena 成本。
- **Athena 定价**：每扫描 1 TB 收 $5（us-east-1、us-west-2 及大多数主要区域）。费用按扫描的数据量计算，而不是返回的数据量——在跑生产查询之前，务必先优化存储格式。
- **Glue 爬虫**："自动发现 S3 数据的模式" → Glue 爬虫。
- **Amazon Data Firehose**："自动把流数据加载到 S3/Redshift/OpenSearch，无需管理消费者" → Amazon Data Firehose。旧资料可能仍称其为 Kinesis Data Firehose。
- **Redshift 与 Athena**：Redshift 用于对固定数据集的高频、复杂查询（BI 仪表板）。Athena 用于对频繁变化的 S3 数据的临时查询。
- **EMR（Elastic MapReduce）**：AWS 托管的 Hadoop/Spark 集群。当题目提到"现有 Hadoop/Spark 工作负载"或"自定义数据处理框架"时，考试指向它。对于大多数用例，Glue 是托管替代方案。
- **QuickSight：**AWS 托管的 BI 与可视化。连接 Athena、S3、Redshift、RDS。SPICE = 加速重复查询的内存引擎。考试触发词："AWS 上的商业智能仪表板" → QuickSight。
- **Lake Formation：**数据湖（S3 + Glue Data Catalog）的集中访问控制。细粒度权限：表级、列级和行级。考试触发词："限制对 S3 数据湖中特定列的访问"或"集中数据湖治理" → Lake Formation。

## 练习

**练习 1 — 回顾**

解释 Amazon Kinesis 和 Amazon SQS 之间的区别。各自在什么情况下使用？

*（提示：思考有多少消费者可以读取同一份数据、消息在读取后是否被删除、以及顺序是否重要。）*

**练习 2 — SAA-C03 场景题**

*场景*：一家共享出行公司想要分析行程数据。每天完成 100 万次行程。行程记录以 JSON 文件形式存储在 S3 中（每条约 2KB）。分析团队想运行临时 SQL 查询，比如"上周各城市的平均行程时长"。查询应在 2 分钟内完成。存储成本应最小化。团队每周运行 20-30 次查询。

哪种架构最符合这些要求？

A) 使用 AWS Glue 将 JSON 转换为按日期和城市分区的 Parquet 格式；使用 Amazon Athena 查询  
B) 每天将行程数据加载到 RDS PostgreSQL；使用标准 SQL 查询  
C) 使用 Amazon Data Firehose 将行程数据传递到 Amazon Redshift；使用 Redshift 查询  
D) 将行程数据加载到 DynamoDB 并使用 PartiQL 进行 SQL 查询

**提示 1**：每周 20-30 次查询是低频。哪种服务对偶发查询最具成本效益？

**提示 2**：Parquet 格式 + 分区可以大幅减少 Athena 扫描的数据量——从而降低成本。

**提示 3**：每天 100 万次行程 × 2KB = 约 2GB。一周约 14GB。按 Athena $5/TB 计算，即使不做优化也负担得起。

**答案**：A

**解释**：Glue 把 JSON 转换为 Parquet（列式格式大幅减少扫描的数据量），并按日期和城市分区（分区修剪意味着"上周"的查询只扫描 7 天的分区）。Athena 用标准 SQL 直接查询 S3。对于每周 20-30 次查询，按查询付费的 Athena 相比始终运行的 Redshift 极具成本效益。

**为什么不是 B？** 每天向 RDS 加载 2GB 数据再查询，需要一台全天候运行的数据库实例。对于每周 20-30 次查询，这严重过度设计且昂贵。

**为什么不是 C？** Redshift 在高频查询（每天对同一数据集查询数百次）时才具有成本效益。对于每周 20-30 次查询，始终在线的 Redshift 集群成本远高于 Athena 的按查询定价。

**为什么不是 D？** DynamoDB 是为基于键的访问而优化的键值/文档存储，不适合临时分析查询。DynamoDB 上的 PartiQL 不支持题目所描述的那种 GROUP BY 聚合。
