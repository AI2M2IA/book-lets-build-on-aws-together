# 第9章：当表变得很大时

菜单表有5万个菜品。

这是跨287家餐厅的菜品，每家都有每日特价、季节性菜品和地区变体。一些菜品有修改选项——大小、辣度、蛋白质选择。一些有引用其他菜品的套餐组合。一些只在工作日、或只在午餐时间、或只在某些城市的菜单上出现。

检索一家餐厅完整菜单的 SQL 查询曾经在200毫秒内返回。

现在需要四秒钟。

四秒钟是某人下单和某人关掉应用程序之间的差距。Leo 已经分析了查询计划。Tom 已经查看了索引配置。Priya 已经增加了只读副本数量。这些都没有产生有意义的区别。

这改变了房间里的气氛。

当一个问题在索引优化、缓存尝试和一个额外的副本之后仍然存在时，人们就停止假设解决方案会是聪明的了。

有时候，解决方案是系统的形状是错误的。

"问题，" Leo 说，"是数据的形状。SQL 希望一切都在行和列里。我们的菜单没有固定的形状。"

这是更长对话的开始。

**把一切都塞进表里的问题**

这是关系数据库的核心张力：它们被设计为以*固定*形状存储*结构化*数据。

如果每个菜单项都有相同的字段——名称、价格、描述、类别——SQL 会完美无缺。你会有一个整洁的 `menu_items` 表，每个菜品一行，查询也很合理。

但真实的菜单不是这样工作的。

一个菜品可能有"辣度"修改选项。另一个可能有"蛋白质选择"。第三个可能有嵌套的套餐组合——"点家庭餐，你就能得到两个主菜、两个配菜和一杯饮料"。*每个菜品*的数据结构都不同。

在 SQL 中，你有两个选择：

**选项1**：为每个可能的修改选项创建一列。这产生一个很宽的表，大多数时候大多数列都是空的。

**选项2**：创建一个单独的修改选项表，并将其与菜品表连接。这可以工作，但复杂的菜单需要多次连接，在有五万个菜品和高读取量的情况下，这些连接变得很昂贵。

"还有第三个选项，" Priya 说，她一直在角落里默默阅读文档。

她拉出了一个新标签。"如果数据不需要放进表里呢？"

**一种不同的数据思考方式**

关系数据库将数据存储为表中的行。每行必须符合表的架构。架构是预先商定好的。

NoSQL 数据库以不同的方式存储数据。一种常见方法是*文档模型*：每条记录作为独立的文档（通常是 JSON）存储，同一集合中的文档不必拥有相同的字段。

文档模型中的菜单项可能看起来是这样的：

```json
{
  "itemId": "ITEM-001",
  "restaurantId": "NIMBUS-047",
  "name": "Shrimp Arepa",
  "price": 3200,
  "modifiers": [
    { "name": "Spice Level", "options": ["mild", "medium", "hot"] },
    { "name": "Protein", "options": ["shrimp", "fish", "mixed"] }
  ],
  "available": true,
  "seasonalUntil": "2024-03-31"
}
```

另一个菜品可能看起来完全不同：

```json
{
  "itemId": "ITEM-002",
  "restaurantId": "NIMBUS-047",
  "name": "Family Feast",
  "price": 9800,
  "includes": ["ITEM-010", "ITEM-011", "ITEM-015", "ITEM-020"],
  "servings": 4,
  "available": true
}
```

不同的形状。相同的集合。没有问题。

"所以数据库更像是一个文件系统而不是一张表，" Maya 说。

"完全正确，" Priya 说。"你可以把任何文档放进任何抽屉。你不需要把文档剪裁成固定的大小。"

**认识 DynamoDB**

Amazon DynamoDB 是 AWS 的托管 NoSQL 数据库服务。它以项目（而不是行）的形式存储数据，项目被收集到表中（命名与 SQL 相似，但行为不同）。

DynamoDB 表中的每个项目必须有一个**主键**，唯一标识它。其他所有内容都是灵活的。

主键可以是以下两种形式之一：

**仅分区键**：必须在所有项目中唯一的单个属性。

**分区键 + 排序键（复合主键）**：两个属性共同形成唯一组合。这允许你拥有多个具有相同分区键、由其排序键区分的项目。

对于 Nimbus 的菜单：

- 分区键：`restaurantId`
- 排序键：`itemId`

这意味着你可以高效地检索特定餐厅的所有菜品——DynamoDB 精确地知道要查找哪个分区。

"为什么叫分区键？" Tom 问。

**DynamoDB 如何内部存储数据**

DynamoDB 被构建为水平扩展到巨大规模。它通过*分区*实现这一点——数据根据分区键在许多物理机器上分散。

当你写入一个项目时，DynamoDB 对分区键值进行哈希，并使用该哈希来确定哪个物理分区（从而哪台服务器）存储该项目。当你读取一个项目时，DynamoDB 进行相同的计算，立即找到它。

把它想象成邮政系统。如果每个信封都有邮政编码，邮政服务不需要读取每个信封来判断它属于哪里——它按邮政编码排序。DynamoDB 按分区键哈希排序。

这就是为什么选择好的分区键很重要：

- **好的**：高基数、均匀分布的值（`restaurantId`，有很多餐厅）
- **不好的**：低基数（`true/false`、`category`）——大多数数据堆积在几个分区上，造成"热点"

热点意味着一个分区获得了大部分流量。那个分区成为瓶颈。DynamoDB 开始限制请求。用户开始看到错误。

"所以如果我把 `available: true` 用作分区键，" Leo 慢慢说，"所有可用菜品都会堆积在同一个分区上。"

"你的数据库会在晚餐高峰时崩溃，" Priya 确认道。

Leo 慢慢地关上了他的笔记本电脑。

**大规模读写**

DynamoDB 可以每秒处理数百万个请求。但它需要知道要配置多少容量。

有两种容量模式：

**预置容量**：你指定需要多少读写单位。DynamoDB 为你保留该容量，并限制超出的流量。成本可预测，每次请求的价格更低。

**按需容量**：DynamoDB 随你的实际流量自动扩展。不需要日常容量规划。每次请求成本更高，操作上也更简单，不过超出表近期流量模式很多的突发尖峰仍然可能导致限流。

对于 Nimbus，菜单的读取频率远高于写入。顾客打开应用程序，浏览菜单——这是很多读操作。餐厅合作伙伴每周更新两次菜单——这是偶尔的写操作。

"按需模式现在有意义，" Tom 说。"我们还不知道我们的流量模式。为每次请求多付一点，比配置不足被限流要好。"

心存疑虑的基础设施智慧。来自 Tom。团队确实已经成长了。

**一致性：你的数据有多新鲜？**

DynamoDB 自动在多个可用区复制数据。这对持久性很好，但也意味着你需要清楚地思考读取一致性。

从 DynamoDB 读取时，你有一个选择：

**最终一致读**：这是默认值。它更便宜，结果可能在最近完成的写入后短暂落后。

**强一致读**：对于针对表或本地二级索引的读取，DynamoDB 可以返回成功先前写入的最新提交值。这需要更多读取容量，对全局二级索引不可用。

对于菜单数据，最终一致性就好了。稍微过时一毫秒的菜品无关紧要。

对于订单确认数据——"这个订单已经下了吗？"——你会希望强一致性。顾客在他们的订单刚保存时不应该看到"再试一次"的消息。

"就像在应用程序上查看银行余额和直接打电话给银行的区别，" Maya 说。"应用程序可能落后三十秒。电话永远是最新的。"

**权衡：DynamoDB 不能做什么**

NoSQL 并不严格优于 SQL。这是一种适用于不同工作的不同工具。

DynamoDB 放弃了什么：

**灵活查询**：在 SQL 中，你可以按任何列过滤和排序。在 DynamoDB 中，你只能通过主键高效查询。按任意字段查询需要*扫描*（读取表中的每个项目），这在大规模下既昂贵又缓慢。

**连接**：DynamoDB 不做连接。如果你需要来自两个表的数据，你在应用程序代码中进行两次单独的读取。

**事务**：DynamoDB 支持事务，但关系数据库对于许多多实体工作流、报告密集型系统和连接密集型设计仍然更自然。

**熟悉度**：几十年的 SQL 工具、技能和思维模型不能直接转移。

DynamoDB 擅长什么：

- 键值和文档访问模式
- 大规模（任何规模下的个位数毫秒延迟）
- 无服务器，无基础设施管理
- 自动扩展、多 AZ 复制、备份
- 无论数据量多大，性能可预测

"所以规则是，" Maya 说，"当你确切地知道*如何*访问数据时使用 DynamoDB。当你还不知道时使用 SQL。"

Priya 点了点头。"先设计你的访问模式。然后选择你的数据库。"

这是数据库对话能产生的最高级别的输出之一。

**何时使用哪种**

| 情况 | 选择 |
|---|---|
| 结构化数据、复杂查询、报告 | RDS（PostgreSQL、MySQL） |
| 灵活的数据形状、基于键的访问、大规模 | DynamoDB |
| 写入密集、有复杂关系 | RDS |
| 读取密集、有可预测的访问模式 | DynamoDB |
| 你需要连接和聚合 | RDS |
| 你需要每秒百万次请求的毫秒级延迟 | DynamoDB |
| 跨多个实体的事务 | RDS（通常） |
| 无服务器/不可预测的流量峰值 | DynamoDB 按需 |

错误答案永远是"始终使用其中一个或另一个"。Nimbus 最终使用了两种：RDS 用于订单历史和财务记录（结构化、关系型、需要报告），DynamoDB 用于菜单（灵活架构、高读取量、按餐厅 ID 访问）。

## 优势与局限性

**DynamoDB 为什么强大**：

- 任何规模下的个位数毫秒延迟
- 完全托管——无需打补丁、无需设置复制、无需维护窗口
- 自动多 AZ 复制（内置持久性）
- 按需扩展意味着零容量规划
- 与 Lambda、API Gateway、Streams 原生集成
- 时间点恢复（类似于 RDS 自动备份）
- DynamoDB Streams——将每次变化捕获为事件（对实时处理很有用）

**DynamoDB 变得复杂的地方**：

- 访问模式设计是不可协商的——错误代价高昂且难以撤销
- 复杂查询需要二级索引（增加成本和复杂性）
- 扫描很昂贵——在生产中避免使用
- "项目大小限制"是400KB——大型项目需要不同的存储
- 如果你不了解读/写单位成本，定价可能会让你大吃一惊

## 摘要

- DynamoDB 是 AWS 的托管 NoSQL 数据库服务。
- 项目以灵活文档的形式存储——不需要固定架构。
- 每个项目必须有一个**主键**：单独的分区键，或分区键 + 排序键。
- 分区键决定哪个物理分区存储该项目。为了均匀分布而选择它。
- **按需**容量自动扩展；**预置**容量在流量可预测时更便宜。
- **最终一致**读更便宜更快。**强一致**读始终是最新的。
- DynamoDB 在大规模的基于键的访问方面表现出色。它在自由查询和连接方面表现不佳。
- 关系数据使用 RDS。文档/键值数据使用 DynamoDB。当情况需要时两者都用。

## 考试技巧

*SAA-C03 领域：设计高性能架构（领域3，任务3.3）*

- 了解分区键规则：**高基数、均匀分布**。热点分区是常见的考试陷阱。
- **按需 vs 预置**：对于不可预测的流量使用按需；对于可预测的工作负载使用预置（带自动扩展）。
- **DynamoDB Streams**：实时捕获项目级变化。常见考试场景："当记录变化时触发 Lambda 函数"。
- **Global Tables**：多区域、多活动复制，用于全球分布式应用程序和灾难恢复场景。在考试中，当工作负载需要在多个区域进行本地读写时，这是一个强烈信号。
- **DAX（DynamoDB Accelerator）**：DynamoDB 的内存缓存层。将读取延迟从毫秒降低到微秒。考试在 RDS 只读副本不适用时使用这个（因为它是 DynamoDB 专用缓存）。
- **复合主键**：分区键 + 排序键允许在分区内进行灵活查询。示例：检索两个日期之间客户的所有订单——`customerId` 是分区键，`orderDate` 是排序键。
- 了解何时*不*使用 DynamoDB：复杂连接、自由报告、多实体事务 → RDS 通常是答案。

**练习 2——考试练习**

*场景*：一家全球游戏公司在 DynamoDB 中存储玩家资料。每个资料包含用户名、等级、成就和物品栏等字段。一些玩家有10个物品；其他人有5000个自定义配置。公司需要在活跃游戏过程中进行资料查找时有个位数毫秒的读取延迟。

哪种设计方法*最能*支持这个需求？

A) 迁移到在每个地区有只读副本的 RDS Aurora  
B) 使用 DynamoDB，以 `playerId` 作为分区键，将整个资料存储为单个项目  
C) 使用 DynamoDB，以 `level` 作为分区键，将相似技能的玩家分组  
D) 在 RDS 前面使用 ElastiCache 以实现亚毫秒延迟

**提示 1**：访问模式是"按 ID 查找特定玩家"。哪个键使这变得高效？

**提示 2**：一个选项会产生可怕的热点分区。哪个属性的基数非常低？

**提示 3**：DynamoDB 已经原生提供个位数毫秒的延迟。

**答案**：B

**解析**：使用 `playerId` 作为分区键可以将数据均匀分布在各个分区上，并支持按玩家 ID 即时查找——正是所描述的访问模式。DynamoDB 的灵活文档模型无需架构更改就能处理不同的物品栏大小。

**为什么不是 A？** 带只读副本的 RDS Aurora 增加了复杂性，对于这种基于键的资料查找在游戏规模上仍然不是首选。

**为什么不是 C？** 使用 `level` 作为分区键会产生严重的热点分区——大多数流量流向等级1（新玩家）或最高等级（活跃老玩家），其他分区处于闲置状态。

**为什么不是 D？** 问题描述的是 DynamoDB，不是 RDS。在 RDS 前面添加 ElastiCache 引入了两个新服务，而 DynamoDB 单独就能解决这个问题。
