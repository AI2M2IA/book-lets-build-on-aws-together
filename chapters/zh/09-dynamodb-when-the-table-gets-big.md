**把一切都塞进表里的问题**

这是关系数据库的核心张力：它们被设计为以*固定*的形状存储*结构化*数据。

如果每个菜单项都有相同的字段——名称、价格、描述、类别——SQL 会完美无缺。你会有一张整洁的 `menu_items` 表，每个菜品一行，查询也清晰合理。

但真实的菜单不是这样的。

一个菜品可能有"辣度"修改选项。另一个可能有"蛋白质选择"。第三个可能有嵌套的套餐组合——"点家庭餐，你就能得到两个主菜、两个配菜和一杯饮料"。数据的结构是*随菜品而变*的。

在 SQL 中，你有两个选择：

**选项1**：为每个可能的修改选项创建一列。这会产生一张非常宽的表，大多数时候大多数列都是空的。

**选项2**：创建一张单独的修改选项表，并把它与菜品表连接。这可以工作，但复杂的菜单需要多次连接，而在五万个菜品和高读取量的情况下，这些连接变得很昂贵。

"还有第三个选项，" Priya 说，她一直在角落里安静地读文档。

她打开了一个新标签页。"如果数据根本不需要放进表里呢？"

**一种不同的数据思考方式**

关系数据库把数据存储为表中的行。每行必须符合表的架构。架构是预先商定好的。

NoSQL 数据库以不同的方式存储数据。一种常见方法是*文档模型*：每条记录作为一个自包含的文档（通常是 JSON）存储，同一集合中的文档不必拥有相同的字段。

文档模型中的菜单项可能是这样的：

```json
{
  "itemId": "ITEM-001",
  "restaurantId": "NIMBUS-047",
  "name": "Shrimp Arepa",
  "price": 3200,
  "modifiers": [
    { "name": "Spice Level", "options": ["mild", "medium", "hot"] },
    { "name": "Protein", "options": ["shrimp", "fish", "mixed"] }
  ],
  "available": true,
  "seasonalUntil": "2024-03-31"
}
```

另一个菜品可能看起来完全不同：

```json
{
  "itemId": "ITEM-002",
  "restaurantId": "NIMBUS-047",
  "name": "Family Feast",
  "price": 9800,
  "includes": ["ITEM-010", "ITEM-011", "ITEM-015", "ITEM-020"],
  "servings": 4,
  "available": true
}
```

不同的形状。同一个集合。没有问题。

"所以这个数据库更像一个文件归档系统，而不是一张表，" Maya 说。

"完全正确，" Priya 说。"你可以把任何文档放进任何抽屉。你不需要把文档裁剪成固定的尺寸。"

**认识 DynamoDB**

Amazon DynamoDB 是 AWS 的托管 NoSQL 数据库服务。它以项目（item，而不是行）的形式存储数据，项目被收集到表中（命名与 SQL 相似，但行为不同）。

DynamoDB 表中的每个项目都必须有一个**主键**，用来唯一标识它。其余一切都是灵活的。

主键可以是两种形式之一：

**仅分区键**：一个在所有项目中必须唯一的单一属性。

**分区键 + 排序键（复合主键）**：两个属性*合在一起*构成唯一组合。这允许你拥有多个分区键相同、由排序键加以区分的项目。

对于 Nimbus 的菜单：

- 分区键：`restaurantId`
- 排序键：`itemId`

这意味着你可以高效地检索某家餐厅的所有菜品——DynamoDB 精确地知道该去哪个分区查找。

"为什么叫分区键？" Tom 问。

"那如果有人试图入侵呢？" Priya 问。"如果分区键是可猜测的，有人能不能用写入请求轰炸某一个分区，故意制造热点状况？"

"能，" Leo 说。"对设计糟糕的表来说，这实际上是一个拒绝服务的攻击途径。这又多了一条选择高基数键的理由。"

Priya 把这条记了下来。

**DynamoDB 内部如何存储数据**

DynamoDB 被构建为可以水平扩展到巨大的规模。它通过*分区*来实现这一点——数据根据分区键被拆分到许多物理机器上。

当你写入一个项目时，DynamoDB 对分区键的值进行哈希，并用这个哈希来决定哪个物理分区（从而哪台服务器）存储该项目。当你读取一个项目时，DynamoDB 做同样的计算，立刻找到它。

把它想象成邮政系统。如果每个信封上都有邮政编码，邮政服务就不需要读每一个信封来判断它该去哪里——它按邮政编码分拣。DynamoDB 按分区键哈希分拣。

"等等——可是*为什么*要那样做？" Maya 问。"为什么分区键的选择这么重要？我们不能随便挑一个吗？"

这正是该问的问题。分区键是 DynamoDB 架构设计中最重要的单一决策。原因在这里：

如果你选择了一个低基数的分区键——比如 `available: true/false`，或者 `category: "main/side/drink"`——你的大部分数据就会落在同样的少数几个分区上。DynamoDB 把这叫做"热分区"。一台服务器要处理大部分流量。它会过载。DynamoDB 开始限流请求。用户开始看到错误。

- **好的**：高基数、分布均匀的值（有很多餐厅的 `restaurantId`）
- **不好的**：低基数（`true/false`、`category`）——大多数数据落在少数分区上，制造"热点"

"所以如果我把 `available: true` 用作分区键，" Leo 缓缓地说，"所有可售菜品都会堆在同一个分区上。"

"然后你的数据库会在晚餐高峰时融化，" Priya 确认道。

Leo 慢慢地合上了他的笔记本电脑。

**大规模读写**

DynamoDB 可以每秒处理数百万个请求。但它需要知道要预置多少容量。

有两种容量模式：

**预置容量**：你指定需要多少读取和写入单位。DynamoDB 为你保留这些容量，并对超出部分的流量进行限流。成本可预测，单次请求价格更低。

这些单位有精确的定义，而且考试要求你掌握它们：一个**读取容量单位（RCU）**是每秒一次对不超过 4 KB 项目的强一致读取——或两次同样大小的最终一致读取。一个**写入容量单位（WCU）**是每秒一次对不超过 1 KB 项目的写入。更大的项目按比例消耗更多：强一致地读取一个 12 KB 的项目消耗 3 个 RCU；写入一个 3 KB 的项目消耗 3 个 WCU。

**按需容量**：DynamoDB 随你的实际流量自动扩展。不需要日常容量规划。单次请求成本更高，但操作上简单得多——不过，远超出表近期流量模式的突发尖峰，如果攀升太快，仍然可能导致限流。

对于 Nimbus，菜单的读取频率远高于写入。顾客打开应用、浏览菜单——这是很多次读取。餐厅合作伙伴每周更新两次菜单——这是偶尔的写入。

"按需模式现在是合理的，" Tom 说。"我们还不了解自己的流量模式。每次请求多付一点，也比容量配少了被限流要好。"

带着几分不情愿的基础设施智慧。出自 Tom 之口。团队算是正式成长了。

"这每个月要花多少钱？" Tom 问，调出了价格计算器。

"按我们当前的读取量——每天大约四万次读取——按需模式每月大约十二美元，" Leo 说。"预置模式，如果调得好，接近四美元。但我们得手动设置容量，猜错了就有被限流的风险。"

Tom 把两个数字都记了下来。他总是把数字记下来。

**一致性：你的数据有多新鲜？**

DynamoDB 自动在多个可用区之间复制数据。这对持久性很好，但也意味着你需要清楚地思考读取一致性。

从 DynamoDB 读取时，你有一个选择：

**最终一致读取**：这是默认值。它更便宜，结果可能短暂地落后于刚刚完成的写入。

**强一致读取**：对于针对表或本地二级索引的读取，DynamoDB 可以返回此前成功写入的最新已提交值。这会消耗更多读取容量，并且不适用于全局二级索引。

对于菜单数据，最终一致性就够了。一个过时一毫秒的菜品无关紧要。

对于订单确认数据——"这个订单下成功了吗？"——你会想要强一致性。顾客的订单刚刚被保存时，不应该看到"请重试"的提示。

"就像在应用上查银行余额和直接给银行打电话的区别，" Maya 说。"应用可能落后三十秒。电话永远是最新的。"

你可能想知道：既然 DynamoDB 自动跨多个 AZ 复制，一致性模式到底为什么还重要？答案是：复制需要一段虽小但非零的时间——通常是几毫秒。一次最终一致读取可能由一个尚未收到最新写入的副本来响应。而强一致读取总是访问数据的主副本。对大多数用例（菜单项、商品目录、用户资料）来说，这点滞后是无法察觉的。而对于读取那一刻正确性至关重要的用例（支付确认、库存可用性），你需要强一致性。

**二级索引：超越主键的查询**

如果你需要以主键所不允许的方式访问数据，怎么办？

DynamoDB 支持**二级索引**——让你能用不同属性查询同一份数据的备用键。

**本地二级索引（LSI）**：使用与表相同的分区键，但排序键不同。必须在创建表时定义，之后不能再添加。共享表的预置容量。由于 LSI 共享分区，它支持强一致读取。

**全局二级索引（GSI）**：一个完全独立的索引，有自己的分区键和排序键——与表的主键不同。可以在表已经存在之后添加或删除，这给了你灵活性。拥有自己独立于表的预置容量设置。

对于 Nimbus：如果他们需要按价格区间查询菜品，GSI 可以支持——但要记住一条规则：分区键只接受*相等*比较，所以 `price`（你想做范围查询的字段）必须是**排序键**，而 GSI 的分区键则用一个分组属性，比如类别或 `cuisineType#region`。下面的实例演练里构建的正是这个索引。

如果你选择 LSI，那么你获得强一致性和共享容量，但你在建表时就被锁死在那个设计里；如果你选择 GSI，那么你获得事后添加的灵活性和独立的扩展能力，但你失去了对索引做强一致读取的能力。

**一次 GSI 查询演练**

Priya 演练了一个具体的例子。Nimbus 想支持"按菜系浏览"功能：展示所有合作餐厅中某个特定菜系的全部可售菜品。

主表以 `restaurantId` 为分区键、`itemId` 为排序键。你无法高效地查询"所有 cuisineType = Colombian 的菜品"——那需要扫描每一个分区。

他们创建了一个 GSI：

- GSI 分区键：`cuisineType#region`（例如 "Colombian#NYC"、"Mexican#Chicago"）
- GSI 排序键：`price`

GSI 会把每个项目的一份投影——只包含浏览页所需的字段——复制到索引存储中。现在，对 GSI 发起的 `cuisineType#region = "Colombian#NYC"` 查询会直达索引的那一个分区。

"为什么不直接只用 `cuisineType`？" Leo 问。

"因为 cuisineType 单独使用基数太低，" Priya 说。"Colombian、Mexican、Thai——总共二十个值。又是热分区。把地区拼接上去，我们就有了 Colombian#NYC、Colombian#Chicago、Colombian#LA。更多分区，更好的分布。"

"这感觉有点像在打补丁。"

"这是一个标准的 DynamoDB 模式。叫做分区键分片（partition key sharding）。有时候你得顺着工具的脾气来。"

代码里的 GSI 查询是这样的：

```python
response = dynamodb.query(
    TableName='menu',
    IndexName='cuisineType-price-index',
    KeyConditionExpression='#ct = :ct AND price BETWEEN :lo AND :hi',
    ExpressionAttributeNames={'#ct': 'cuisineType#region'},
    ExpressionAttributeValues={
        ':ct': {'S': 'Colombian#NYC'},
        ':lo': {'N': '1000'},
        ':hi': {'N': '2500'}
    }
)
```

这条查询返回了纽约市所有价格在 $10 到 $25 之间的哥伦比亚菜，按价格排序，耗时大约4毫秒。

"这比原来的 SQL 查询快了一千倍，" Leo 说。

"因为它只触碰了一个索引的一个分区，" Priya 确认道。"而不是扫描一张连接表里的每一行。"

---

**DynamoDB Streams：对变化做出反应**

"我们想过菜单项被更新时会发生什么吗？" 一天早上 Priya 问。"餐厅合作伙伴改了一个价格。我们需要更新搜索索引。我们需要让 ElastiCache 里的条目失效"——这是我们下一章要认识的缓存服务——"我们还需要把这次变更记录到分析管道里。"

"我们可以在 API 处理程序里把这些全做了，" Leo 说。"写入发生时，触发所有下游更新。"

"那如果其中一个失败了呢？"

"那……我们重试。"

"如果 EC2 实例在写入之后、下游更新之前崩溃了呢？数据保存了，但没有任何东西知道这次变更。"

Leo 想了想。

"我们需要让更新是有保证的，" 他说。"即使我们的应用代码在中途失败。"

这正是 **DynamoDB Streams** 解决的问题。

DynamoDB Streams 捕获 DynamoDB 表中每一次项目修改的按时间排序的日志。每一次插入、更新和删除都会作为一个事件写入流中。流会把事件保留24小时。

你可以把一个 Lambda 函数挂到流上。每当一个项目发生变化，Lambda 函数就会被调用，并收到该项目变化前后的状态。这个 Lambda 接下来可以：

- 更新搜索索引（OpenSearch）
- 让 ElastiCache 中的缓存条目失效
- 向另一个系统发送通知
- 喂给分析管道
- 把变更复制到另一张表或另一个数据库

关键的区别在于：Streams 把写入和下游影响解耦了。DynamoDB 的写入成功与否，独立于 Lambda 成功与否。如果 Lambda 失败，DynamoDB 会重试它。如果应用程序在写入后崩溃，流事件仍然在那里——等系统恢复后 Lambda 会处理它。

"所以我们写入 DynamoDB，" Leo 缓缓地说，"DynamoDB 保证下游处理最终会发生，即使我们崩溃了。"

"完全正确，" Priya 说。"这就是'指望你的所有副作用都能跑完'和'让数据库为它们提供保证'之间的差别。"

对于 Nimbus，他们把菜单表的 DynamoDB Streams 接到了一个 Lambda 上，当菜单项变化时让 ElastiCache 条目失效。缓存自动与数据库保持一致，不需要任何应用代码来管理失效。

"Streams 要花多少钱？" Tom 问。

"按从流读取付费——每次 Lambda 调用都会从流读取。按我们的量，大概每月两到三美元。"

Tom 没再多问就批准了。他已经学会了判断什么时候每月两美元是值得的。

**权衡：DynamoDB 不能做什么**

NoSQL 并不绝对优于 SQL。它是适用于不同工作的不同工具。

DynamoDB 放弃了什么：

**灵活查询**：在 SQL 中，你可以按任何列过滤和排序。在 DynamoDB 中，你只能通过主键高效查询。按任意字段查询需要*扫描*（读取表中的每一个项目），这在大规模下既昂贵又缓慢。

**连接**：DynamoDB 不做连接。如果你需要来自两张表的数据，你要在应用代码中做两次单独的读取。

**事务**：DynamoDB 支持事务，但对于许多多实体工作流、报表密集型系统和连接密集型设计，关系数据库仍然是更自然的选择。

**熟悉度**：几十年积累的 SQL 工具、技能和思维模型无法直接迁移。

DynamoDB 擅长什么：

- 键值和文档访问模式
- 超大规模（任何规模下的个位数毫秒延迟）
- 无服务器，无基础设施管理
- 自动扩展、多 AZ 复制、备份
- 无论数据量多大，性能都可预测

"所以规则是，" Maya 说，"当你*确切*知道会如何访问数据时，用 DynamoDB。当你还不知道时，用 SQL。"

Priya 点了点头。"先设计你的访问模式。再选择你的数据库。"

这是一场数据库对话所能产出的最资深的结论之一。

---

**当 DynamoDB 是错误的选择时**

接手了财务报表模块的 Tom 有一个问题。

"我们正在搭建财务报表，" 他说。"每家餐厅的月度收入汇总、税务计算、发票历史。这些也能放进 DynamoDB 吗？"

团队成员面面相觑。

"等等——可是*为什么*要那样做？" Maya 抢在 Priya 之前问了出来。

Priya 笑了。Maya 正在养成这个习惯。

"把查询过一遍给我们听，" Priya 对 Tom 说。

他调出了需求文档。"我们需要：每家餐厅的总收入，按周分组。按订单数排名的最佳菜品，跨所有餐厅。按菜系类型细分的收入。按城市统计的平均订单金额。用于合作伙伴报告的同比对比。"

Leo 读了这份清单。"每一条都是聚合。求和、分组、平均、对比。"

"DynamoDB 没有聚合函数，" Priya 说。"没有 GROUP BY。没有 SUM。没有 AVG。要回答'这家餐厅本周的总收入'，你得扫描这一周的每一个订单，全部拉进应用内存，自己算。"

"听起来很糟糕，" Tom 说。

"以我们的规模，那是每次报表请求都要把数万条记录拉进内存。既慢又贵。而且每次新增一个报表需求，我们都要写新的扫描加计算的代码。"

"那我们用什么？"

"财务报表？RDS。配好索引的 PostgreSQL。你描述的那些查询正是 SQL 为之设计的东西。它们会是十行 SQL。换成 DynamoDB 扫描代码会是两百行。"

DynamoDB 在以下情况下是错的：

- 你无法提前知道访问模式（报表本质上是探索性的）
- 你需要对大型数据集做聚合（SUM、GROUP BY、COUNT）
- 你的数据有复杂的关系，需要连接
- 你需要随时提出临时查询的灵活性——问那些你还没想到的问题
- 你的数据本质上是关系型结构，无法自然映射到键值模型

"所以这个选择不是'新技术更好'，" Maya 说。

"这个选择是'你的数据是什么形状，你会怎么访问它'，" Priya 确认道。"DynamoDB 对菜单来说是真的更好。对财务报表来说会是真的更糟。这两句话同时成立。"

Tom 把财务报表建在了 PostgreSQL 上。他写的第一条 GROUP BY 查询在80毫秒内返回。他一行扫描代码都不用写。

**何时使用哪种**

| 情况                                             | 选择                    |
|-------------------------------------------------------|-------------------------|
| 结构化数据、复杂查询、报表           | RDS（PostgreSQL、MySQL） |
| 灵活的数据形状、基于键的访问、超大规模 | DynamoDB                |
| 写入密集且关系复杂                | RDS                     |
| 读取密集且访问模式可预测           | DynamoDB                |
| 你需要连接和聚合                         | RDS                     |
| 你需要每秒数百万请求下的毫秒级延迟   | DynamoDB                |
| 跨多个实体的事务                 | RDS（通常）           |
| 无服务器 / 不可预测的流量峰值             | DynamoDB 按需      |
| 财务报表、临时分析                 | RDS 或数据仓库 |
| 事件溯源、变更捕获、实时处理  | DynamoDB + Streams      |

错误答案永远是"始终只用其中某一个"。Nimbus 最终两个都用了：RDS 用于订单历史和财务记录（结构化、关系型、需要报表），DynamoDB 用于菜单（灵活架构、高读取量、按餐厅 ID 访问）。

## 为合适的工作负载选合适的数据库

把时间快进六个月——DynamoDB 迁移早已尘埃落定——Nimbus 的看板上有了三个新项目。一个星期二的早晨，Maya 向团队逐一介绍。

"第一：一个推荐引擎。我们想根据顾客的历史，以及口味相似的人点过什么，向顾客展示他们可能会点的菜。第二：我们要让菜单数据支持更丰富的内容——完整的 JSON 菜单文档，每家餐厅结构不同，架构灵活。第三：我们马上要完成对 Barato 的收购，他们的数据团队为客户行为数据运行着一个 Cassandra 集群。他们想把它搬到 AWS 上，但不想重写他们的管道。"

三个项目。三种截然不同的数据需求。没有一个是显而易见适合 DynamoDB 的。

"这些都需要不同的数据库，" Priya 说。

"我们有 DynamoDB，" Leo 说。

"我们有选择正确工具的权利，" Priya 说。

**Amazon DocumentDB：当你的工作负载说 MongoDB 的语言**

第二个项目——具有灵活、按餐厅而异的架构的富 JSON 菜单文档——描述的就是一个文档数据库。Nimbus 已经在用 DynamoDB 的灵活架构存菜单了，但随着团队构建更复杂的菜单功能（嵌套修改选项、按时段定价、复杂的套餐结构），DynamoDB 的查询模型开始显露出极限。团队想要更丰富的文档查询：查找所有某个嵌套修改选项包含特定选项的菜单项，按 JSON 结构内部的任意字段过滤。

"这是文档数据库的模式，" Priya 说。"MongoDB。"

"我们可以在 EC2 上跑 MongoDB，" Leo 提议。

"或者我们可以用 DocumentDB，" Priya 说。

**Amazon DocumentDB** 是一个与 MongoDB 兼容的托管文档数据库。它以类 JSON 文档的形式存储数据，架构灵活——同一集合中的不同文档可以拥有不同的字段。DocumentDB 支持 MongoDB 的查询语言、API 和驱动程序。如果你的工作负载目前跑在 MongoDB 上，DocumentDB 说的是同一种语言。迁移路径是改一个连接字符串，而不是重写一个应用程序。

DocumentDB 是完全托管的：无需打补丁、自动备份、多 AZ 高可用、只读副本，以及随数据增长而自动扩容的存储。

"所以我们把菜单迁移到 DocumentDB，" Leo 说。"我们已经写好的 MongoDB 语法查询直接就能用？"

"做一点兼容性测试，是的，" Priya 确认道。"DocumentDB 支持 MongoDB 查询 API 的大部分。别假设完全覆盖，先查兼容性矩阵，但就文档查询和聚合而言，这很直接。"

DocumentDB 的考试信号很简单：**"MongoDB 兼容"**或**"文档存储"**。如果一个场景提到 MongoDB 或面向文档的数据，DocumentDB 就是 AWS 的托管答案。

**Amazon Neptune：当关系本身就是数据时**

推荐引擎是个更难的问题。

问题不是"这位顾客点过什么？"——那是一次简单的 DynamoDB 查找。问题是："哪些顾客与这位顾客的口味画像相似，而那些顾客喜欢过哪些这位顾客还没尝试过的菜？"

这是一个图问题。数据模型不是一张行的表，也不是一个文档集合。它是一张关系网络：顾客连接到菜品（点过、评分过、浏览过），菜品连接到餐厅和菜系类型，餐厅连接到街区和城市。推荐不在数据点里——它在数据点之间的路径里。

"我们需要一个图数据库，" Priya 说。

**Amazon Neptune** 是一个完全托管的图数据库。它支持两种图模型：**属性图**（用 Gremlin 遍历语言查询）和 **RDF**（用 SPARQL 查询）。你根据现有的图技术栈或团队偏好来选择；两者运行在同一套 Neptune 基础设施上。

图数据库是为这样的工作负载量身定做的：数据点之间的关系与数据本身同等重要——社交网络（谁和谁相连）、推荐引擎（相似的用户喜欢过什么）、欺诈检测（哪些交易在不同账户间共享可疑模式）、知识图谱（概念之间如何关联）。

对于 Nimbus 的推荐引擎：顾客和菜品成为 Neptune 中的节点。下单事件成为边。一次 Gremlin 遍历可以在单条查询里找出所有被订单历史相似的顾客评过高分的菜品，并按连接强度排序——既不需要关系数据库里那种复杂的 JOIN 链条，也不需要 DynamoDB 里那种多次往返的查询。

Neptune 的考试信号：**"社交网络"、"推荐引擎"、"知识图谱"、"欺诈检测"**或**"图遍历"**。如果一个场景描述的数据中，连接和数据本身同样重要，Neptune 就是答案。

**Amazon Keyspaces：没有运维负担的 Cassandra**

Barato 收购案把一个 Cassandra 集群带进了视野。Cassandra 是一个宽列 NoSQL 数据库——为极高的写入吞吐量和水平可扩展性而设计，常用于时间序列数据、用户活动日志和 IoT 遥测。Barato 的数据团队用它来跟踪客户行为：哪些商品被浏览了、哪些被加入了购物车、哪些被放弃了。

把 Cassandra 迁移到 AWS 有两个选项：在 EC2 上运行它（管理集群、升级、扩展的运维开销），或者使用托管选项。

"Amazon Keyspaces，" Priya 说。

**Amazon Keyspaces** 是一个无服务器的、与 Cassandra 兼容的托管数据库。它支持 Cassandra 查询语言（CQL）——也就是 Barato 的管道已经在用的那种查询语言。就像 DocumentDB 之于 MongoDB，Keyspaces 是那条托管路径：应用代码原样保留，把它指向一个 Keyspaces 端点而不是自管理的集群，让 AWS 来处理基础设施。

Keyspaces 随流量自动扩展，不需要容量规划，而且是无服务器的——你只为实际执行的读写付费。对于 Barato 的行为跟踪数据，这是正确的模型：流量极其多变（晚餐高峰对比凌晨3点）、宽列架构、高写入吞吐量。

考试信号：**"Cassandra 兼容"、"宽列"、"CQL"**或**"Cassandra 工作负载"**。

**选择正确的数据库：一张参考表**

到故事的这个节点，Nimbus 的数据库版图已经和第七章时完全不同了。每种工作负载对应的正确工具：

| 触发短语 | 数据库 |
|---|---|
| "MongoDB 兼容"或"文档存储" | DocumentDB |
| "图关系"、"社交网络"、"推荐引擎" | Neptune |
| "Cassandra 兼容"或"宽列" | Keyspaces |
| "任意规模的键值访问"、"个位数毫秒延迟" | DynamoDB |
| "关系型 + 无服务器"、"自动扩展的 SQL" | Aurora Serverless |
| "结构化数据、复杂查询、报表" | RDS（PostgreSQL、MySQL） |

"这张表还会继续变长吗？" Leo 看着清单问。

"会，" Maya 说。"因为不同的问题有不同的形状。用错形状，你付出的代价不是性能，就是开发者的时间，或者两者都有。"

"正确的问题不是'我们该用什么数据库'，" Priya 补充道。"而是'我们的数据是什么形状，我们会怎么访问它？'数据库是从答案里推出来的。"

这是她两年来关于数据库说过的最重要的一句话。

## 优势与局限性

**DynamoDB 为什么强大**：

- 任何规模下的个位数毫秒延迟
- 完全托管——无需打补丁、无需配置复制、没有维护窗口
- 自动多 AZ 复制（持久性内置）
- 按需扩展意味着零容量规划
- 与 Lambda、API Gateway、Streams 原生集成
- 时间点恢复（类似于 RDS 自动备份）
- DynamoDB Streams——把每一次变更捕获为事件（对实时处理很有用）

**DynamoDB 变得复杂的地方**：

- 访问模式设计没有商量余地——犯了错，纠正的代价很高
- 复杂查询需要二级索引（增加成本和复杂性）
- 扫描很昂贵——在生产环境中避免使用
- "项目大小限制"是400KB——大型项目需要不同的存储方案
- 如果你不理解读/写单位的成本，定价可能让你大吃一惊
- 热分区是无声的杀手——在限流开始之前没有任何报错

## 摘要

架构重设计花了两天时间和大量的白板空间。选择 NoSQL 数据库不仅仅是一个技术决策——它彻底改变了你思考数据的方式。但成果是一张可以增长到任意规模而不会变慢的菜单表。同样重要的是：团队搞清楚了 DynamoDB 的边界在哪里，以及当问题改变形状时该去找哪些专用数据库。

- DynamoDB 是 AWS 的托管 NoSQL 数据库服务。项目是灵活的文档——没有固定架构。每个项目都必须有一个**主键**：单独的分区键，或分区键 + 排序键。选择分区键时要追求均匀分布——热分区会导致限流。
- **按需**容量自动扩展；**预置**容量对可预测的流量更便宜。**最终一致**读取更便宜；**强一致**读取总是最新的，但在 GSI 上不可用。
- **DynamoDB Streams** 实时捕获项目级变更——用它们来驱动缓存失效、搜索索引更新和分析管道。
- DynamoDB 对报表、复杂连接和临时查询是错误的选择——这些用 RDS。
- **DocumentDB**（MongoDB 兼容）、**Neptune**（图数据库）和 **Keyspaces**（Cassandra 兼容）是 AWS 为不适合 DynamoDB 键值模型的工作负载提供的托管替代方案。

## 考试技巧

*SAA-C03 领域：设计高性能架构（领域3，任务3.3）*

- 掌握分区键规则：**高基数、均匀分布**。热分区是常见的考试陷阱。
- **按需 vs 预置**：不可预测的流量用按需；可预测的工作负载用预置（配合 Auto Scaling）。
- **DynamoDB Streams**：实时捕获项目级变更。常见考试场景："当记录变化时触发一个 Lambda 函数"。
- **Global Tables**：多区域、多活动（multi-active）复制，用于全球分布式应用程序和灾难恢复场景。在考试中，当工作负载需要在多个区域进行本地读写时，这是一个强烈信号。
- **DynamoDB TTL（Time to Live）**：在项目上设置一个过期时间戳属性，DynamoDB 会在到期后自动删除它们——**零成本**，不消耗任何写入容量。考试触发词："会话数据/临时项目必须在 N 小时后以最低成本自动删除" → TTL，绝不是定时 Lambda 扫描。过期的项目还可以流入 DynamoDB Streams 用于归档。
- **DAX（DynamoDB Accelerator）**：DynamoDB 的内存缓存层。把读取延迟从毫秒降到微秒。当 RDS 只读副本帮不上忙时（因为这是 DynamoDB 专用缓存），考试会用到它。
- **复合主键**：分区键 + 排序键允许在分区内进行灵活查询。示例：检索某客户两个日期之间的所有订单——`customerId` 是分区键，`orderDate` 是排序键。
- **GSI vs LSI**：GSI 可以在建表之后添加；LSI 不行。LSI 支持强一致读取；GSI 不支持。LSI 共享表的容量；GSI 有自己独立的容量。
- 了解何时不该用 DynamoDB：复杂连接、临时报表、多实体事务 → RDS 通常是答案。
- **专用数据库选择**——考试经常给出一个场景，问哪种数据库合适。把这个当作你的速查参考："MongoDB 兼容" → DocumentDB。"图/社交网络/推荐引擎/知识图谱" → Neptune。"Cassandra 兼容/宽列" → Keyspaces。"任意规模的键值/毫秒级延迟" → DynamoDB。"关系型/复杂查询/报表" → RDS 或 Aurora。

## 练习

**练习 1——回忆**

**练习 2——SAA-C03 场景题**

*场景*：一家全球游戏公司把玩家资料存储在 DynamoDB 中。每份资料包含用户名、等级、成就和物品栏等字段。有些玩家有10件物品；有些玩家有几百件——资料的形状各不相同，但每份都远低于 DynamoDB 400KB 的项目大小限制。公司需要在活跃游戏过程中对资料查找实现个位数毫秒的读取延迟。

哪种设计方案**最能**支持这个需求？

A) 使用 DynamoDB，以 `playerId` 为分区键，把整份资料存储为单个项目  
B) 迁移到在每个区域配有只读副本的 RDS Aurora  
C) 使用 DynamoDB，以 `level` 为分区键，把技能相近的玩家分组  
D) 在 RDS 前面使用 ElastiCache 以实现亚毫秒延迟

**提示 1**：访问模式是"按 ID 查找某个特定玩家"。哪个键让这变得高效？

**提示 2**：有一个选项会制造可怕的热分区。哪个属性的基数非常低？

**提示 3**：DynamoDB 原生就能提供个位数毫秒的延迟。

**答案**：A

**解析**：使用 `playerId` 作为分区键可以把数据均匀分布到各个分区，并支持按玩家 ID 即时查找——正是题目描述的访问模式。DynamoDB 灵活的文档模型无需架构变更就能处理大小不一的物品栏。

**为什么不是 B？** 带只读副本的 RDS Aurora 增加了复杂性，而且对这种游戏规模下基于键的资料查找来说，它仍然不是自然的首选。

**为什么不是 C？** 用 `level` 作为分区键会制造严重的热分区——大部分流量涌向等级1（新玩家）或满级（活跃老玩家），其他分区则闲置。

**为什么不是 D？** 题目描述的是 DynamoDB，不是 RDS。在 RDS 前面加 ElastiCache 引入了两个新服务，而 DynamoDB 单独就能解决问题。
