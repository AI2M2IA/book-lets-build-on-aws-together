# 第三十一章：云架构的建筑检查员

站起来。伸展一下。如果需要，可以真正地休息一下。

本章与之前的章节不同。我们花了 30 章积累了对特定服务和模式的知识。现在我们退后一步，看看整个画面。

*好的*云架构实际上是什么样子的？是否有一种系统的方式来评估你所构建的东西是否真正设计良好——而不仅仅是功能正常？

有的。AWS 称之为 Well-Architected Framework。

Nimbus 已经运行了两年。团队做出了数百个架构决策——有些是有意识的，有些是意外的，有些是在压力下做出的。系统在工作。但 Maya 有一个问题。

"我们的架构实际上*好*吗？"她问，"不只是能用。而是好。"

没有人立即回答。

"因为我一直在听说 Well-Architected Review，"她继续说，"AWS 向客户提供它。我们的一些投资者提到了它。我认为我们应该做一个。"

"那是什么？"Leo 问。

"用于评估云架构的 AWS 框架，"Priya 说，"六个支柱。每个的一组问题和最佳实践。你对照所有支柱评估你的架构并识别缺失的内容。"

"就像建筑检查，"Tom 说，"你知道建筑是能用的。检查告诉你它是否符合规范，以及在地震中什么可能会失败。"

**六个支柱**

AWS Well-Architected Framework 围绕六个支柱组织。每个支柱有一组设计原则、最佳实践和评估架构的问题。

**1. 运营卓越**

*关注点*：运行和监控系统以提供业务价值，并持续改进流程和程序。

关键领域：

- 你如何部署变更？（CI/CD、基础设施即代码、自动化部署）
- 你如何监控系统并知道什么时候出了问题？
- 你如何从失败中学习？（事后分析、操作手册、无责文化）
- 你如何大规模处理变更？

Nimbus 评估：

- 存在：带自动化部署的 CI/CD 流水线
- 存在：CloudWatch 警报和 GuardDuty
- 存在：季度混沌工程测试
- 警告：事后分析流程未正式化——事件被调查，但学习没有被系统地记录

**2. 安全**

*关注点*：通过风险评估和缓解策略保护信息、系统和资产。

关键领域：

- 谁可以访问什么，尽可能使用最小权限？
- 静态和传输中的数据如何加密？
- 如何检测和响应威胁？
- 是否有自动化安全控制？

Nimbus 评估：

- 存在：IAM 最小权限（在第 14 章清理之后）
- 存在：KMS 用于数据加密，Secrets Manager 用于凭证
- 存在：GuardDuty、WAF、Shield Standard
- 存在：带私有子网和安全组的 VPC
- 警告：EC2 实例上的安全补丁未完全自动化（Priya 几个月前指出了这一点，尚未解决）

**3. 可靠性**

*关注点*：确保系统正确一致地执行其预期功能，并能从失败中恢复。

关键领域：

- 系统如何处理组件级别的失败？
- 它如何从区域性失败中恢复？
- 需求如何管理？
- 系统如何针对失败进行测试？

Nimbus 评估：

- 存在：所有关键组件的 Multi-AZ
- 存在：带自动故障转移的 Aurora Serverless
- 存在：EC2 和 ECS 的 Auto Scaling
- 存在：混沌工程测试（季度）
- 警告：没有多区域部署（热备用尚未实现——计划下个季度）

**4. 性能效率**

*关注点*：高效使用 IT 和计算资源。

关键领域：

- 是否为工作负载使用了正确的实例类型和数据库类型？
- 扩展配置是否正确？
- 数据是否从最优位置传递给用户？

Nimbus 评估：

- 存在：CloudFront 用于全球内容传递
- 存在：ElastiCache 用于数据库读取加速
- 存在：Aurora 读副本
- 存在：Lambda 用于适当的工作负载
- 警告：自初始部署以来某些 EC2 实例从未进行过正确调整大小

**5. 成本优化**

*关注点*：避免不必要的成本。

关键领域：

- 资源是否适当调整了大小？
- 未使用的资源是否已退役？
- 是否使用了适当的定价模式？
- 是否检测了异常支出？

Nimbus 评估：

- 存在：已实施 Savings Plans（第 27 章）
- 存在：S3 生命周期策略（第 23 章）
- 存在：DynamoDB Auto Scaling
- 存在：带警报的 AWS Budgets
- 存在：季度成本审查

**6. 可持续性**

*关注点*：最大限度地减少运行云工作负载的环境影响。

关键领域：

- 利用率是否最大化（避免空闲资源）？
- 是否选择了节能的实例类型？
- 数据是否只在需要时存储？

Nimbus 评估：

- 存在：Lambda 和 Fargate 用于无服务器/容器化工作负载（比专用 EC2 资源效率更高）
- 存在：S3 生命周期策略（不再需要时删除数据）
- 警告：某些基于 Graviton 的实例尚未采用（AWS Graviton 更节能、更便宜）

**Well-Architected Review 流程**

评审不是你通过或失败的测试。它是一次关于你架构的结构化对话，由六个支柱的 60+ 个问题引导。

每个问题都识别出一个最佳实践。如果你的架构遵循了，那是一个优势。如果没有，那是一个"问题"——按风险级别（高、中、低）分类。

输出：一个按风险分类的架构改进建议优先列表。并非所有内容都需要立即修复。该框架帮助你理解每个差距的权衡，并决定首先解决什么。

AWS Well-Architected Tool（在 AWS 控制台中可用，免费）提供问题框架并生成带建议的报告。

对于 Nimbus，Maya 安排了一个半天研讨会。所有四名团队成员一起审查了每个支柱。到结束时，他们有一份 12 个"问题"的列表——三个高风险，五个中风险，四个低风险。

**高风险问题**：

1. 没有多区域灾难恢复计划（可靠性）
2. EC2 安全补丁未自动化（安全）
3. 没有正式的事件响应流程（运营卓越）

**中风险问题**：

5 个项目，包括：未采用 Graviton、某些 EC2 实例未正确调整大小、没有数据库故障转移的正式操作手册

**低风险问题**：

4 个项目，包括：CloudFront 缓存命中率可以通过调整 TTL 来提高，一些安全组规则比必要的更宽泛

**镜头：专业化评审**

核心 Well-Architected Framework 是技术无关的。AWS 还发布了**镜头**——针对特定用例或行业的框架扩展：

- **无服务器镜头**：针对以 Lambda 为主的架构的额外问题
- **SaaS 镜头**：用于多租户 SaaS 应用
- **机器学习镜头**：用于机器学习训练和推理工作负载
- **金融服务镜头**：金融科技的监管和合规问题
- **医疗保健镜头**：HIPAA 考虑

对于 Nimbus，SaaS 镜头是相关的。它添加了关于租户隔离、入驻自动化和每租户成本分配的问题——所有这些都是 Nimbus 正在积极开发的领域。

**设计良好与仅能正常工作的区别**

"我们的系统在工作，"Leo 在审查后说，"但我没有意识到我们有多少东西是'够好了'就继续了。"

"这很正常，"Priya 说，"在时间压力下构建意味着你做出务实的选择。Well-Architected 审查是重新审视这些选择的预定时间。"

"回头看，某些差距似乎是显而易见的，"他继续说，"安全补丁——我知道我们没有自动化它。我只是从未优先修复它。"

"因为'能用'和'架构良好'在日常感觉是一样的，"Maya 说，"区别只有在出问题时才会变得可见。"

这是高级工程师理解的最重要的事情之一：没有事故不意味着没有风险。这意味着风险尚未触发。

**基础设施即代码：运营卓越的推动者**

贯穿多个支柱的一个主题：**基础设施即代码（IaC）**。

如果你的基础设施是通过控制台手动配置的，那么：

- 在灾难恢复场景中重新创建它缓慢且容易出错
- 审计变更是不可能的（谁改了什么，什么时候改的？）
- 回滚坏的变更需要手动撤销
- 环境之间的一致性（开发/测试/生产）需要纪律

**AWS CloudFormation** 允许你在 YAML/JSON 模板中定义基础设施。**AWS CDK（Cloud Development Kit）** 允许你使用编程语言（Python、TypeScript、Java）定义基础设施。**Terraform** 是流行的第三方替代方案。

Nimbus 一直在使用 Terraform 逐渐迁移到 IaC。在 Well-Architected 审查时，他们大约 60% 的基础设施被定义为代码。审查建议达到 100%。

"为什么是剩余的 40%？"Leo 问。

"剩余的 40% 是我们关键基础设施所在的地方，"Priya 说，"如果我们无法从代码中重新创建它，我们就无法可靠地从区域性灾难中恢复。"

## 优势与局限

**Well-Architected Framework 的优势**：它给团队提供了讨论架构权衡的共同词汇——这种语言在人员变动和供应商对话中能够存活。进行 Well-Architected Review 迫使明确承认否则不可见的风险："是的，我们知道这里有单点故障；我们接受了这个权衡，因为消除它的成本超过了失败的预期成本。"这种有文档记录的、有意识的权衡是一次好评审的输出。

**它不能做什么**：框架是描述性的，而非规范性的。它描述了架构良好的系统的属性——它并不告诉你如何构建它们。在 Well-Architected Review 中勾选每一个框并不保证一个好的架构。一个系统可以高度可用、运营卓越、成本优化，但仍然解决了错误的问题。框架是一个镜头，而非蓝图。用它来提出正确的问题，而不是回答它们。

## 总结

- **AWS Well-Architected Framework** 有六个支柱：运营卓越、安全、可靠性、性能效率、成本优化和可持续性。
- 每个支柱通过结构化问题集评估的设计原则和最佳实践。
- **Well-Architected Tool**（AWS 控制台中免费）指导评审并生成报告。
- 输出是按风险分类的架构改进优先列表。
- **镜头**为特定领域（无服务器、SaaS、医疗保健、机器学习）专业化框架。
- **基础设施即代码**是跨支柱的推动者——由运营卓越、安全和可靠性支柱推荐。
- Well-Architected 审查不是通过/失败测试。它是一次结构化的改进对话。

## 考试技巧

*SAA-C03 领域：跨领域 — 所有领域*

- **了解所有六个支柱及其主要关注点**。考试将描述一个场景（例如，"团队希望确保他们的系统能够从 AZ 故障中恢复"），并要求你确定它属于哪个支柱（可靠性）。
- **支柱映射**：
  - "可靠地部署变更，从失败中学习，监控"→ 运营卓越
  - "IAM、加密、网络控制、威胁检测"→ 安全
  - "高可用性、故障转移、扩展、灾难恢复"→ 可靠性
  - "正确调整大小、CDN、正确的技术选择"→ 性能效率
  - "定价模式、未使用的资源、成本可见性"→ 成本优化
  - "能源效率、资源利用率、数据生命周期"→ 可持续性
- **基础设施即代码**：框架推荐用于可重复性、可审计性和恢复。CloudFormation、CDK 和 SAM 是 AWS 原生的 IaC 工具。
- **Well-Architected Tool**：指导评审过程的 AWS 控制台工具。免费使用。生成改进计划。
- **AWS Trusted Advisor**：类似于 Well-Architected 框架但是自动化的——扫描你的账户并提供跨成本、性能、安全和容错的建议。重叠是真实的：Trusted Advisor 自动化了框架手动评估的一些内容。

**练习 2 — 考试练习**

*场景*：一个工程团队正在准备 Well-Architected 审查。他们的应用程序在带 RDS Multi-AZ 的 EC2 上运行。最近，他们发现：

- 他们的部署过程有时会让 EC2 实例有不同的库版本（配置漂移）
- 当 RDS 故障转移被触发时，他们没有自动警报
- 他们的 IAM 用户都有 AdministratorAccess
- 他们 14 个月内没有测试过他们的备份恢复流程

将每个问题映射到最相关的 Well-Architected 支柱。

A) 配置漂移：运营卓越；没有 RDS 故障转移警报：可靠性；AdministratorAccess：安全；没有备份恢复测试：可靠性

B) 配置漂移：安全；没有 RDS 故障转移警报：性能效率；AdministratorAccess：运营卓越；没有备份恢复测试：成本优化

C) 配置漂移：可靠性；没有 RDS 故障转移警报：性能效率；AdministratorAccess：安全；没有备份恢复测试：运营卓越

D) 配置漂移：安全；没有 RDS 故障转移警报：可靠性；AdministratorAccess：成本优化；没有备份恢复测试：安全

**提示 1**："配置漂移"在部署过程中 → 哪个支柱涵盖部署实践？

**提示 2**："所有用户的 AdministratorAccess" → 哪个支柱涵盖访问控制？

**提示 3**："备份恢复未测试" → 哪个支柱涵盖测试你的恢复机制？

**答案**：A

**解释**：部署中的配置漂移（环境不一致）是运营卓越问题——它关乎可靠、一致的部署实践。RDS 故障转移无警报意味着你不知道 HA 机制何时被触发——可靠性问题（了解系统的健康状况）。所有用户的 AdministratorAccess 违反了最小权限——安全问题。未测试的备份恢复意味着你的可靠性机制（灾难恢复）未经验证。

**为什么不选 B？** B 将配置漂移错误地分配给安全（库版本不一致是部署操作问题，而非安全威胁）并将 AdministratorAccess 分配给运营卓越（访问控制是安全关注，而非运维流程）。

**为什么不选 C？** C 正确地将 AdministratorAccess 放在安全，但将配置漂移错误地分配给可靠性（部署一致性是运营卓越）并将未测试的备份恢复分配给运营卓越（恢复测试是可靠性问题——你在验证系统能否恢复，而非你的流程是否一致）。

**为什么不选 D？** D 将 AdministratorAccess 分配给成本优化（过于宽泛的权限与成本无关）并将未测试的备份恢复分配给安全（无法恢复备份是可靠性失败，而非安全漏洞）。

## 片尾彩蛋

Well-Architected 审查三周后，团队已经实施了三个高风险修复。

EC2 补丁现在通过 AWS Systems Manager Patch Manager 自动化。事件响应流程文档存在了（不完美，但已写出并共享）。多区域热备用计划已起草，定于下个季度实施。

Priya 审查了 Well-Architected Tool 报告。高风险数量：0。中风险：3。低风险：4。

"我们比以前更好，"她说。

"这算好吗？"Leo 问。

"这是进步，"她说，"Well-Architected 审查是不会结束的。你取得进步，然后六个月后再次审查。"

Maya 一直在想着什么。

"我们花了 31 章学习单个 AWS 服务，"她说，"现在我们开始着眼于整个系统。这就是架构师的思维方式。"

"我们思考架构已经有一段时间了，"Leo 说。

"我们一直在做架构决策，"Maya 说，"那是不同的。像架构师一样思考意味着你在做决定*之前*评估它们，而不是之后。"
