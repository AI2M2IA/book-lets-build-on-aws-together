# 第三十一章：云架构的建筑检查员

站起来。伸展一下。如果需要，就好好休息一会儿。

本章和之前的章节不同。我们花了 30 章积累关于具体服务和模式的知识。现在我们退后一步，看看整幅图景。

*好的*云架构究竟是什么样子？有没有一套系统化的方法，来评估你所构建的东西是真正设计精良——还是仅仅能用？

有。AWS 称之为 Well-Architected Framework（良好架构框架）。

**回顾：跟在数字后面的那个问题**

三个月的成本优化产出了一个让所有人都意外的数字：每年 $35,904 的节省，已识别并大部分落地。EC2 Savings Plans、S3 生命周期策略、存储清理、未使用的数据库副本、NAT Gateway 端点——每一项都是一次独立的发现、一次独立的修复。但在那个过程中的某个时刻，Maya 开始问一个不一样的问题。不是"浪费在哪里？"而是"它当初是怎么积累起来的？"这些成本问题是某种东西的症状。而 Well-Architected Framework 正是为那个"某种东西"命名的词汇。

Nimbus 已经运行了两年。团队做出过数百个架构决策——有些是有意识的，有些是出于偶然，有些是在压力之下做出的。系统是能用的。但 Maya 有一个问题。

"我们的架构真的*好*吗？"她问，"不只是能用。是好。"

没有人立刻回答。

"因为我一直在听人说起 Well-Architected Review，"她接着说，"AWS 向客户提供这项服务。我们的一些投资人提到过它。我觉得我们应该做一次。"

"那是什么？"Leo 问。

"AWS 用来评估云架构的框架，"Priya 说，"六个支柱。每个支柱配一组问题和最佳实践。你对照所有支柱评估你的架构，找出缺失的部分。"

"就像一次建筑检查，"Tom 说，"你知道这栋楼能用。检查告诉你它是否符合规范，以及在地震中什么可能会塌。"

**六大支柱**

AWS Well-Architected Framework 围绕六个支柱组织。每个支柱都有一组设计原则、最佳实践，以及评估你架构的问题。

**1. 卓越运营**

*关注点*：运行和监控系统以交付业务价值，并持续改进流程与规程。

关键领域：

- 你如何部署变更？（CI/CD、基础设施即代码、自动化部署）
- 你如何监控系统、如何知道出了问题？
- 你如何从故障中学习？（事后复盘、操作手册、无指责文化）
- 你如何大规模地处理变更？

Nimbus 评估：

- 已具备：带自动化部署的 CI/CD 流水线
- 已具备：CloudWatch 告警和 GuardDuty
- 已具备：季度混沌工程测试
- 警告：事后复盘流程尚未正式化——事件得到了调查，但经验教训没有被系统地记录下来

**2. 安全**

*关注点*：通过风险评估和缓解策略来保护信息、系统和资产。

关键领域：

- 谁能访问什么，是否尽可能采用了最小权限？
- 静态和传输中的数据如何加密？
- 你如何检测和响应威胁？
- 是否有自动化的安全控制？

Nimbus 评估：

- 已具备：采用最小权限的 IAM（在第 14 章清理之后）
- 已具备：用于数据加密的 KMS，用于凭证的 Secrets Manager
- 已具备：GuardDuty、WAF、Shield Standard
- 已具备：带私有子网和安全组的 VPC
- 警告：EC2 实例上的安全补丁尚未完全自动化（Priya 几个月前就指出了这一点，至今未解决）

"等等——但我们*为什么*会那样做？"当安全补丁的缺口被提出来时，Maya 问，"我们把部署自动化了。把备份自动化了。为什么偏偏把打补丁留成手动的？"

"因为打补丁感觉和部署代码不一样，"Priya 说，"我们担心打补丁会弄坏什么东西。所以我们保持手动以维持控制。"

"而正因为保持手动，我们让它变得不一致，"Maya 说，"那更糟。"

"是的，"Priya 说，"AWS Systems Manager Patch Manager 能解决这个问题。我们六个月前就该做了。"

**3. 可靠性**

*关注点*：确保系统正确、一致地执行其预期功能，并能从故障中恢复。

关键领域：

- 系统如何处理组件级别的故障？
- 它如何从区域级故障中恢复？
- 需求如何管理？
- 系统如何针对故障进行测试？

Nimbus 评估：

- 已具备：所有关键组件的 Multi-AZ
- 已具备：带自动故障转移的 Aurora Serverless
- 已具备：EC2 和 ECS 的 Auto Scaling
- 已具备：混沌工程测试（每季度）
- 警告：没有多区域部署（温备份尚未实现——计划在下个季度）

**4. 性能效率**

*关注点*：高效使用 IT 和计算资源。

关键领域：

- 是否为工作负载使用了正确的实例类型和数据库类型？
- 扩展配置是否正确？
- 数据是否从最优位置交付给用户？

Nimbus 评估：

- 已具备：用于全球内容分发的 CloudFront
- 已具备：用于数据库读取加速的 ElastiCache
- 已具备：Aurora 读副本
- 已具备：用于合适工作负载的 Lambda
- 警告：自首次部署以来，部分 EC2 实例从未调整过规格

**5. 成本优化**

*关注点*：避免不必要的成本。

关键领域：

- 资源规格是否合适？
- 未使用的资源是否已退役？
- 是否使用了合适的定价模型？
- 是否检测了支出异常？

Nimbus 评估：

- 已具备：实施了 Savings Plans（第 27 章）
- 已具备：S3 生命周期策略（第 23 章）
- 已具备：DynamoDB Auto Scaling
- 已具备：带告警的 AWS Budgets
- 已具备：季度成本审查

"这每个月到底要花多少钱——所有我们还没调整规格的东西？"Tom 问，"那些从来没被评估过的 EC2 实例。那些还停留在第一年配置规格上的实例。"

"我不知道，"Leo 说，"这正是问题所在。"

"那就是性能效率的缺口，"Priya 说，"我们优化了我们知道的东西。对于我们还没看过的东西，我们没有一个数字。"

**6. 可持续性**

*关注点*：最大限度减少运行云工作负载对环境的影响。

关键领域：

- 利用率是否最大化（避免空闲资源）？
- 是否选择了节能的实例类型？
- 数据是否只在需要时才存储？

Nimbus 评估：

- 已具备：用于无服务器/容器化工作负载的 Lambda 和 Fargate（资源效率优于专用 EC2）
- 已具备：S3 生命周期策略（不再需要时删除数据）
- 警告：部分基于 Graviton 的实例尚未采用（AWS Graviton 更节能、更便宜）

**Well-Architected Review 流程**

这场评审不是一场要么通过要么失败的考试。它是一次关于你架构的结构化对话，由六个支柱上的 60 多个问题引导。

每个问题都对应一项最佳实践。如果你的架构遵循了它，那是一个优势。如果没有，那就是一个"问题"——按风险级别（高、中、低）分类。

输出：一份按优先级排序的改进建议清单。并非所有东西都需要立刻修复。这个框架帮助你理解每个缺口的取舍，并决定先处理什么。

AWS 的 Well-Architected Tool（在 AWS 控制台中提供，免费）提供问题框架，并生成一份带建议的报告。

对于 Nimbus，Maya 安排了一场覆盖全部六个支柱的半天评审会议——并且决定不独自进行。这场会议本身，以及它产出的发现清单，正是本章接下来要讲的内容。

**镜头：让评审专业化**

核心的 Well-Architected Framework 是技术无关的。AWS 还发布了**镜头（Lenses）**——针对特定用例或行业的框架扩展：

- **Serverless 镜头**：针对以 Lambda 为主的架构的额外问题
- **SaaS 镜头**：针对多租户 SaaS 应用
- **机器学习镜头**：针对 ML 训练和推理工作负载
- **金融服务镜头**：针对金融科技的监管与合规问题
- **医疗健康镜头**：HIPAA 相关考量

你可能会想：在上线之前，你需要对照全部六个支柱跑完整的 Well-Architected 评审吗？不需要。价值在于问题，而不在于分数。如果你处于上线前阶段，挑出与你处境最相关的两个支柱——安全和可靠性几乎总是正确的起点——只把这些问题过一遍就好。一次真正做了的局部评审，比一次被推迟到架构"准备好"才做的完整评审更有价值。

对于 Nimbus，SaaS 镜头是相关的。它加入了关于租户隔离、入驻自动化和按租户成本分摊的问题——这些都是 Nimbus 正在积极开发的领域。

**Well-Architected 评审会议：Carlos 主持**

Maya 邀请了 Carlos——一位她在 AWS 社区活动上认识的资深架构师，专门为像他们这样的团队主持 Well-Architected 评审——来主持这场会议。他到场时，笔记本电脑上开着 Well-Architected Tool，手里只有一个记事本。没有议程。只有问题。

"我来问，你们如实回答，"他说，"如果实话是'我们不知道'，就这么说。那也是一个发现。"

他从卓越运营开始。

"你们针对最常见的五类事件有操作手册吗？"

Tom 看了看 Leo。Leo 看着天花板。

"我们有两类事件的操作手册，"Priya 说，"数据库连接数超限和 CloudFront 源站超时。另外三类——高峰期 EC2 实例故障、DynamoDB 限流和 Stripe webhook 失败——我们都是临时处理。"

Carlos 写下：*OPS-1：前五类事件的操作手册。现状：2/5。缺口：3。*

"上一次你们在演练中把现有的操作手册走一遍是什么时候？"

沉默。

"我们没演练过，"Priya 说，"我们是在事件发生后写的。我们从没测试过它们是否还准确。"

*OPS-2：操作手册验证。上次测试：从未。*

Carlos 继续。安全。

"现在谁拥有 root 账户的访问权限？"

"Root？"Leo 说，"就 Maya。我想 Tom 还有我们当初建账户时的 root 凭证——不过在第 14 章之后我们轮换过了。"他停顿了一下。"Tom，IAM 清理之后我们轮换 root 了吗？"

Tom 调出一条 1Password 记录。"我们改了密码并加了 MFA。但 root 凭证还在共享的 1Password 保险库里。三个人能访问那个保险库：我、Maya 和 Leo。"

"所以三个人拥有 root 访问权限，"Carlos 说，"AWS 的建议是，root 只应用于一份简短的、有记录的任务清单——大约十项账户级操作，全都很少见，而且大多数仅限紧急情况。完成这些操作后，root 会话就应该终止。root 访问有单独记录日志吗？"

"CloudTrail 会记录，"Priya 说。

"root 被使用时有告警吗？"

又一次停顿。

"没有，"Tom 说。

Carlos 写下：*SEC-1：root 账户访问控制。现状：3 名用户共享保险库，无使用告警。缺口：root 使用应触发即时 SNS 告警。目标：0 次非紧急 root 会话。*

"接下来：谁审查 IAM 权限的变更？对于新的 IAM 角色或策略扩张，有同行评审流程吗？"

"Priya 审查，"Leo 说，"她是事实上的安全审查人。"

"Priya 休假的时候怎么办？"

没人回答。

"那是一个流程缺口，"Carlos 不带评判地说，"不是 Priya 能力上的缺口——是流程设计上的缺口。一个依赖于某一个人是否在岗的安全审查，是你们安全态势中的单点故障。"

*SEC-2：IAM 审查流程。现状：单一审查人，无后备。缺口：指定一名后备审查人，并记录审查标准。*

Carlos 转向可靠性。

"你们在负载下测试过 Aurora Multi-AZ 故障转移吗？"

"我们在空闲时测过，"Tom 说，"我们在系统安静时运行了故障转移命令，确认副本在 45 秒内被提升。"

"当时的负载是多少？"

"大概是峰值的 5%。"

"在 80% 峰值负载下进行故障转移时，连接池会发生什么？"

Tom 想了想。"DNS 端点会更新。使用写入端点的应用在切换窗口期间会看到连接错误——通常是 20 到 45 秒。在 5% 负载下，我们有十个活跃连接。在峰值时，会有 300 个。前面有 RDS Proxy，由代理来处理重连。"

"RDS Proxy 在 Multi-AZ 故障转移期间真的会透明地重连吗？"

Tom 看向 Priya。"我相信会。但我没测试过。"

"那个答案和'会'不一样，"Carlos 说，"你们高可用设计中一个未经测试的假设，就是一个发现。"

*REL-1：负载下的 Aurora Multi-AZ 故障转移。已测试：仅空闲状态。缺口：在 70% 峰值负载下、有 RDS Proxy 的情况下测试。验证故障转移窗口期间的连接池行为。*

"你们想过吗，如果故障转移用了 90 秒而不是 45 秒会怎样？"Priya 问，她是冲着 Tom 而不是 Carlos 说的。她已经在做这件事了。

"90 秒的话，任何无法重试的请求都会出现应用超时，"Tom 说，"下单流程有重试逻辑。确认流程——就差一些。晚餐高峰期一次 90 秒的故障转移意味着一部分确认会失败，餐厅收不到订单，顾客拿到退款。"

"那就是爆炸半径，"Carlos 说，"很好。现在你知道你在防范什么，以及如何衡量它。这个测试应该同时验证故障转移时长和切换窗口期间的应用行为。"

他转到性能效率。

"你们在调整 EC2 实例的规格吗？"

"我们在成本审查时调整过规格，"Tom 说，"Savings Plans 承诺了当前的实例类型。"

"你们上一次看 Compute Optimizer 的建议是什么时候？"

Tom 把它调了出来。AWS Compute Optimizer 标记了三个实例可能配置过剩：两个 c6g.medium 后台处理器和一个 t3.medium VPN 服务器。VPN 服务器的建议是缩到 t3.small。处理器被以 82% 的置信度标记为"配置过剩"。

"我们设置好之后就没看过这个，"Tom 承认。

"Compute Optimizer 生成建议有多久了？"

Tom 查了查。"六周。"

Carlos 写下：*PERF-1：通过 Compute Optimizer 调整 EC2 规格。现状：建议已生成，未审查。缺口：每月审查 Compute Optimizer 的输出；经预发布验证后应用建议。*

"还有一个，"Carlos 说，"这个跨越所有支柱。"他在白板上写道：

*无事故不等于设计精良。*

他让这句话在那里停了一会儿。

"你们的系统运行了两年，没有发生过面向客户的重大故障，"他说，"这确实很好。但我希望你们注意到它告诉了你们什么——以及它没有告诉你们什么。"

"它告诉我们我们一直很走运？"Leo 试着说。

"它告诉你们，以你们今天拥有的架构，你们遇到过的故障模式都在你们的处理能力之内。它没有告诉你们这个架构是稳健的。一个还没出过故障的系统，并不能证明它有韧性。它证明的只是，它还没遇到那些会暴露其弱点的特定条件。"

"所以没出故障不代表没有脆弱性，"Maya 说。

"正确。Well-Architected 评审找的不是过去故障的证据。它找的是未来的暴露面。未经测试的故障转移。不存在的操作手册。权限过宽的 IAM 角色。这些都还没有引发过事故。它们全都可能引发。"

"这就是为什么补丁缺口很重要，"Priya 说，"我们还没有通过一台未打补丁的 EC2 实例被攻破过。这不代表我们不会。"

"正是如此，"Carlos 说，"没有受到伤害不是安全的证据。一个未处理的脆弱性的存在就是风险的证据——不管这个风险有没有真的发生。"

他给马克笔盖上盖子。

"这就是一个设计精良的系统和一个走运的系统之间的区别。"


**IAM 权限过宽的发现**

在安全支柱的评审中，Carlos 标记出了第二个需要深入查看的发现。

"你们处理订单通知的那个 Lambda 函数——它有哪些 IAM 权限？"

Leo 调出了执行角色。找到它花的时间比应有的多了三十秒——这个角色是在 Nimbus 早期创建的，名字起得很笼统。

"S3 完全访问权限，"他找到后说。

Carlos 等着。

"哪个存储桶？"他问。

"所有存储桶，"Leo 说。他读出策略，"`arn:aws:s3:::*`。我们给了它 S3 完全访问权限。"

"这个函数实际上拿 S3 干什么？"

"它从一个存储桶读取餐厅配置，"Leo 说，"`nimbus-restaurant-config` 存储桶。具体来说是 `restaurants/{restaurant_id}/config.json` 对象。它读取它们。仅此而已。"

"所以这个函数需要的是对 `arn:aws:s3:::nimbus-restaurant-config/restaurants/*/config.json` 的 `s3:GetObject`，"Carlos 说，"而它拥有的是对账户里每一个存储桶的 S3 完全权限。"

"包括，"Priya 说，"Aurora 快照存储桶。CloudTrail 日志存储桶。客户订单历史存储桶。"

"如果这个 Lambda 函数被攻破，"Carlos 说，"攻击者就拥有了对账户里每一个 S3 存储桶的完全访问权限。他们可以读取、写入或删除任何数据。"

"我当时已经部署了它——哦，"Leo 说。他正在读那条策略。"我两年前写的这个。我当时急着把通知系统弄起来。我给了它宽泛的权限，因为我还不确定它需要什么。然后我再也没回来收窄它。"

"那是生产系统中权限过宽最常见的来源，"Carlos 不带指责地说，"不是有意的疏忽——是时间压力下抄了一条近路，然后再也没有重新审视。"

Tom 已经在看全部 Lambda 执行角色的清单了。

"我们有多少个 Lambda 函数权限过宽？"Maya 问。

二十分钟审查后的答案：23 个 Lambda 函数里有 7 个的权限超出了其文档记录用途的需要。最令人担忧的：支付确认 Lambda 对所有表拥有 `dynamodb:*`。它只需要对 orders 表的 `dynamodb:GetItem` 和 `dynamodb:PutItem`。

"修完这七个要三个小时的工作，"Priya 估计道，"写出最小权限策略，挂上去，移除宽泛的那些。"

"这是目前为止风险最高的发现吗？"Maya 问 Carlos。

"和操作手册缺口并列，"他说，"IAM 问题是爆炸半径问题——如果这些函数中任何一个被攻破，攻击者的访问范围远比应有的大。操作手册问题是恢复时间问题——出了问题时，你是在临场发挥，而不是在遵循一套经过测试的流程。两者都是实打实的高风险。"

Maya 在跟踪文档里把它们俩都标记为 P1。

"那要是有人想入侵呢？"Priya 说，"我们一直在担心外部攻击者。但一个权限过宽的 Lambda 意味着一次内部故障——一次配置错误、一个依赖项漏洞、一次供应链攻击——都能有同样的爆炸半径。"

"纵深防御的前提是每一层都只有必需的最小访问权限，"Carlos 说，"当某一层拥有超出它所需的访问权限时，纵深防御就不再按设计运作了。你会得到一个被攻破的层，而它却握着另外三层的钥匙。"

Priya 把 IAM 权限过宽的发现标记为 P1，列在第一栏，截止日期定在一周后。


**给发现排序：P1、P2、P3**

会议结束时，团队在白板上有了 14 条发现。Carlos 请他们在离开前做分诊。

"这份清单上的每一条发现都需要一个优先级，"他说，"并非所有东西都同等重要。按以下标准排序：如果这件事失败，爆炸半径有多大？它失败的可能性有多高？修复它有多难？"

这 14 条发现：

1. 前五类事件中有 3 类没有操作手册（OPS）
2. 操作手册从未测试过（OPS）
3. 除操作手册之外没有正式的事件响应流程（OPS）
4. root 访问权限在共享保险库里，无使用告警（SEC）
5. IAM 审查流程没有后备审查人（SEC）
6. 7 个 Lambda 函数权限过宽（SEC）← Leo 的通知 Lambda

9. 多区域 DR 计划尚未实施（REL）

11. EC2 规格自上线以来未审查（PERF）
12. 未采用 Graviton 实例（SUST）
13. CloudFront 缓存 TTL 未调优（PERF）

"从明显的开始，"Carlos 说，"如果你们只有一周，会先修哪三个？"

Maya 立刻接话："root 访问告警。Lambda 权限过宽。安全补丁自动化。"

"为什么？"Carlos 问。

"因为这三个都是有清晰爆炸半径的安全缺口。其他的是可靠性和运营改进——重要，但我们一直带着它们生活，它们也没引发过事故。而这些安全缺口在我们没修复的每一天都在悄悄累积。"

Tom 温和地表示不同意。"Lambda 权限过宽是紧急的。但我会用 Aurora 故障转移测试换掉安全补丁。我们从来没确认过我们的 Multi-AZ 配置在负载下能否正确工作。如果它在某个周五晚餐高峰期失败，而我们又没有一份经过测试的操作手册，那我们就麻烦了。"

"两个都可以是 P1，"Priya 说，"我们有一周。五个工作日。Lambda 权限每个函数是两小时的修复。root 访问告警是三十分钟的 CloudWatch 事件规则。安全补丁自动化是两天的 Systems Manager 设置和测试。Aurora 故障转移测试是排在某个周二凌晨 2 点的半天工作。"

Carlos 点点头。"那才是正确的分诊方式。不只是'什么最重要'，而是'这一周我们实际能做什么，以及按什么顺序做？'"

最终的分诊：

**P1（本周）**：
- Lambda 执行角色最小权限修复（7 个函数）
- root 账户 CloudWatch 告警
- 负载下的 Aurora Multi-AZ 故障转移测试（安排在下周二凌晨 2 点）

**P2（本月）**：
- 通过 Systems Manager 实现安全补丁自动化
- 前三类事件缺失的操作手册
- 记录正式的事件响应流程
- 40% IaC 迁移——确定哪些资源，制定迁移计划

**P3（本季度）**：
- 操作手册验证演练
- 记录 IAM 审查流程的后备审查人
- 收紧过宽的安全组规则
- 通过 Compute Optimizer 审查 EC2 规格
- Graviton 采用计划
- CloudFront TTL 调优

"这就是十四条带负责人、截止日期和优先级的发现，"Maya 说，"我们对技术债从来没这么有条理过。"

"这正是评审的用处，"Carlos 说，"不是为了让你为这些缺口感到难堪。而是给你一套词汇和一份你真正能执行下去的清单。"


**设计精良与仅仅能用之间的区别**

"我们的系统能用，"评审之后 Leo 说，"但我没意识到我们有多少东西是做到'够好'就接着往前了。"

"我们想过吗，如果一直把这些缺口留着会怎样？"Priya 问，"补丁问题已经开了好几个月。事件响应流程根本不存在。这些不是小事——它们决定了一次周五晚上的故障是 20 分钟就能搞定，还是一场四小时的灾难。"

"这就是我们做评审的原因，"Maya 说。

"这很正常，"Priya 说，"在时间压力下构建意味着你会做出务实的选择。Well-Architected 评审就是重新审视这些选择的预定时间。"

"这些缺口里有些事后看起来显而易见，"她接着说，"安全补丁——我知道我们没有把它自动化。我只是从来没把修复它列为优先。"

"因为'它能用'和'它架构精良'在日常感觉上是一样的，"Maya 说，"区别只有在出问题时才会显现。"

这是资深工程师所理解的最重要的事情之一：没有事故不代表没有风险。它代表风险还没有被触发。

**基础设施即代码：卓越运营的使能器**

横跨多个支柱的一个主题：**基础设施即代码（IaC）**。

如果你的基础设施是通过控制台手动配置的，那么：

- 在 DR 场景中重建它既慢又容易出错
- 审计变更是不可能的（谁、在什么时候、改了什么？）
- 回滚一个糟糕的变更需要手动逆转
- 各环境（开发/预发布/生产）之间的一致性需要靠纪律来维持

**AWS CloudFormation** 让你用 YAML/JSON 模板定义基础设施。**AWS CDK（Cloud Development Kit）** 让你用编程语言（Python、TypeScript、Java）定义基础设施。**Terraform** 是一个流行的第三方替代方案。

Nimbus 一直在用 Terraform 逐步迁移到 IaC。到 Well-Architected 评审时，他们大约 60% 的基础设施已用代码定义。评审建议做到 100%。

"为什么剩下的 40%？"Leo 问。

"剩下的 40% 正是我们关键基础设施所在的地方，"Priya 说，"如果我们无法从代码重建它，我们就无法可靠地从区域级灾难中恢复。"

Leo 看着那份清单。"剩下的 40%——嗯。没事的，我们下个冲刺迁移它。"

Priya 的目光停留在屏幕上。"那是关键基础设施。多区域故障转移配置。IAM 角色层级。那些一旦我们必须在凌晨 3 点从头重建、就必须确信完全正确的东西。"

Leo 思考了片刻。

"……你说得对，"他平静地说，"我们已经有一些手动配置偏离了任何人写下来的东西。如果我们必须从头重建它，我们就是在猜。"

"这就是评审发现它的原因，"Maya 说，"不是为了归咎。是为了在它造成影响之前修好它。"

**深入 CloudFormation：AWS 原生的 IaC 工具**

虽然 Nimbus 采用了 Terraform，但 Well-Architected 评审还揭示出，团队从未完全理解 AWS CloudFormation——这个支撑着 CDK、SAM（无服务器应用模型）和 Service Catalog 等服务的 AWS 原生 IaC 服务。考试会专门考 CloudFormation，而且若干 AWS 服务都要求理解它。

Carlos 在会议早些时候指出的那个问题很具体：Leo 一直在手动点击控制台来创建环境。每次要花他 45 分钟，而预发布和生产之间的任何差异，在出问题之前都是不可见的。过去一年五次生产事故中有三次是由生产中某个与预发布不匹配的配置引起的——不同的安全组规则、不同的环境变量、不同的实例类型。

"控制台是一扇单向门，"Carlos 说，"你可以走进去改东西，但你没法轻易走出来、看清到底改了什么，或者重现昨天的状态。"

CloudFormation 就是那个问题的答案。它是这样工作的：

**模板（Template）**：一个声明你想要的 AWS 基础设施的 YAML 或 JSON 文件。不是如何创建它的指令——而是它应该长什么样的声明。"我想要一个带这些 CIDR 范围的 VPC、两个公有子网、两个私有子网、一个 Internet Gateway 和这些路由表。"CloudFormation 读取模板，自行算出如何让真实的基础设施与声明相符。

把模板想象成一份环境的食谱。食谱不变。从它创建出的每一个环境都是一模一样的。预发布和生产使用同一份模板，只是参数不同（不同的实例规格、不同的域名）。结构性的决策——存在哪些子网、哪些安全组、哪些 IAM 角色——是完全一致的。

**栈（Stack）**：模板已部署的实例。当 Leo 运行 `aws cloudformation deploy --template-file infrastructure.yaml` 时，CloudFormation 创建一个 Stack——模板所描述的实际 AWS 资源的一个具名集合。Stack 记得自己创建了哪些资源，并把它们作为一个整体来管理。更新模板并重新部署 Stack：CloudFormation 计算当前状态与新模板之间的差异，只应用所需的变更。删除 Stack：CloudFormation 会按正确的顺序拆除它创建的每一个资源，无需你去记住它们。

"所以 Stack 是部署，而不是模板？"Maya 问。

"模板是食谱。Stack 是做出来的那道菜。你想用同一份食谱做出同一道菜多少次都行。每次都一样。"

**变更集（Change Set）**：在对一个运行中的 Stack 应用更新之前，你可以创建一个变更集——一份 CloudFormation 将要做什么的预览。添加一个新资源？变更集会显示它。修改一个安全组？变更集会显示前后对比。替换一个 RDS 实例？变更集会在你确认之前把它标记为一次替换——这意味着停机。

"在应用之前看到差异，"Priya 说，"这正是 Leo 在控制台点东西时我们所缺少的。"

对 Nimbus 来说，规则变成了：对生产的所有基础设施变更都必须经过变更集审查。不允许直接在控制台编辑。变更集就是基础设施的同行评审流程。

**漂移检测（Drift Detection）**：随着时间推移，人们会在控制台里点东西。一次事件中临时加的一条安全组规则。一次部署中途改掉的一个环境变量。计划中的修复太慢、于是手动调大的一个实例类型。CloudFormation 把这称为**漂移**——当一个资源的实际状态不再与 Stack 模板所声称的它应有状态相符时。

CloudFormation 的漂移检测会扫描 Stack 的资源，并报告实际状态与模板定义状态之间的任何差异。当 Leo 第一次对现有的 Nimbus 栈运行漂移检测时，他发现了十一个发生漂移的资源。其中七个是安全组的修改。三个是 IAM 策略的变更。还有一个是一个 S3 存储桶，它的生命周期策略六个月前直接在控制台里被改过，从未反映到模板里。

"十一个真实基础设施与模板不一致的资源，"Priya 说，"十一处我们并不知道的、预发布与生产之间的潜在不一致。"

Leo 什么也没说。那些修改里有一些是他做的。

接下来的一周他都在把漂移的资源与模板对齐。其中三处手动变更是 bug——本就不该被应用的配置。其余的是合理的变更，只是从来没有被提交回模板。

**为什么它对 Well-Architected Framework 重要**：基础设施即代码处在卓越运营（可重复的部署、版本受控的基础设施、每次变更的可审计性）、可靠性（如果一个 Region 失效，你可以从模板而不是凭记忆重建环境）和安全（IAM 角色和安全组规则在代码中被审查，而不是事后在控制台里被发现）的交汇处。它不是锦上添花——它是这个框架始终如一推荐的基础实践之一。

> **考试技巧 — CloudFormation**
>
> *SAA-C03 领域：跨领域 — 卓越运营与可靠性*
>
> - **CloudFormation = AWS 上的声明式 IaC。** 你在模板中声明期望状态；CloudFormation 创建并管理资源。考试信号："可重复的部署"、"基础设施即代码"、"一致的环境"。
> - **模板** → **栈**：模板是声明；栈是已部署的资源。一个栈可以作为一个整体被创建、更新或删除。
> - **变更集**：在对运行中的栈应用更新之前预览将发生什么变化。"在应用之前看到差异。"考试信号："部署前审查基础设施变更"→ 变更集。
> - **漂移检测**：识别在 CloudFormation 之外被手动改动的资源。"有人在控制台点了什么"→ 漂移检测。
> - **DeletionPolicy 属性**：控制当资源所在的栈被删除时该资源会怎样。`Retain`——资源被保留（对于存有不想丢失数据的 S3 存储桶很有用）。`Delete`——资源被销毁（默认值）。`Snapshot`——对于 RDS 和其他一些服务，CloudFormation 在删除前会拍一个最终快照。考试信号："防止 RDS 数据库在栈被删除时被删除"→ `DeletionPolicy: Snapshot` 或 `DeletionPolicy: Retain`。
> - **CloudFormation StackSets**：通过一次操作把同一个栈部署到多个 AWS 账户和区域。考试信号："在一个组织内的所有账户中部署相同的基础设施"。

**变体：当框架把你引入歧途**

如果你在一次 Well-Architected 评审中勾选了每一个框，却没有在预发布环境中验证你的故障恢复，那么你的高可用架构会在第一次真正的事故中失败——因为韧性的文档不等于经过测试的韧性。框架问的是"你有 Multi-AZ 吗？"而不是"你确认过故障转移在你具体的配置下真的能正确工作吗？"

如果你把框架当成一份用来满足审计员的检查清单，而不是一个用来改进系统的思考工具，那么你产出的将是一份关于一个你并不完全理解的架构的准确文档。这些问题最有价值的时候，是它们揭示出你没料到会发现的缺口的时候。

## 优势与局限

**Well-Architected Framework 做得好的地方**：它给团队提供了一套讨论架构取舍的共同词汇——一种能在人员变动和供应商对话中存活下来的语言。进行一次 Well-Architected Review 会迫使你明确承认那些否则不可见的风险："是的，我们知道这里有一个单点故障；我们接受了这个取舍，因为消除它的成本超过了故障的预期成本。"这种有文档记录的、有意为之的取舍，正是一次好评审的产出。

**它做不到的事**：框架是描述性的，而非规定性的。它描述了架构精良的系统应有的属性——它并不告诉你如何构建它们。在一次 Well-Architected Review 中勾选每一个框，并不能保证一个好架构。一个系统可以高度可用、运营卓越、成本优化，却仍然解决了错误的问题。框架是一个镜头，而不是一张蓝图。用它来浮现出正确的问题，而不是用它来回答这些问题。

## 总结

Well-Architected 评审给他们留下了 14 个条目——三个需要立即关注，其余的需要一个计划。那些高风险的发现并不算意外；它们是团队早已知道、只是还没来得及处理的东西。评审给了他们一种结构化的方式来公开承认这些缺口、按风险排序、并承诺一个时间表。这种问责，比任何单条发现都更能成为价值所在。

- **AWS Well-Architected Framework** 有六个支柱：卓越运营、安全、可靠性、性能效率、成本优化和可持续性。
- 每个支柱都有通过结构化问题集来评估的设计原则和最佳实践。
- **Well-Architected Tool**（在 AWS 控制台中免费）引导评审并生成报告。
- 输出是一份按风险分类的、按优先级排序的架构改进清单。
- **基础设施即代码**是一个跨支柱的使能器——由卓越运营、安全和可靠性支柱共同推荐。

## 考试技巧

*SAA-C03 领域：跨领域 — 所有领域*

- **了解全部六个支柱及其主要关注点**。考试会描述一个场景（例如，"团队希望确保他们的系统能从 AZ 故障中恢复"），并问它属于哪个支柱（可靠性）。
- **支柱映射**：
  - "可靠地部署变更、从故障中学习、监控"→ 卓越运营
  - "IAM、加密、网络控制、威胁检测"→ 安全
  - "高可用、故障转移、扩展、DR"→ 可靠性
  - "调整规格、CDN、正确的技术选型"→ 性能效率
  - "定价模型、未使用的资源、成本可见性"→ 成本优化
  - "能源效率、资源利用率、数据生命周期"→ 可持续性
- **基础设施即代码**：框架推荐它以实现可重复性、可审计性和恢复能力。CloudFormation、CDK 和 SAM 是 AWS 原生的 IaC 工具。
- **Well-Architected Tool**：引导评审流程的 AWS 控制台工具。免费使用。生成改进计划。
- **AWS Trusted Advisor**：类似于 Well-Architected 框架，但是自动化的——扫描你的账户，并在成本、性能、安全和容错方面提供建议。这种重叠是真实存在的：Trusted Advisor 把框架手动评估的一部分内容自动化了。

**练习 2 — SAA-C03 场景题**

*场景*：一个工程团队正在准备一次 Well-Architected 评审。他们的应用运行在 EC2 上，配 RDS Multi-AZ。最近，他们发现：

- 他们的部署流程有时会让 EC2 实例带有不同的库版本（配置漂移）
- 当 RDS 故障转移被触发时，他们没有自动告警
- 他们的 IAM 用户全都拥有 AdministratorAccess
- 他们 14 个月没有测试过备份恢复流程

把每个问题映射到最相关的 Well-Architected 支柱。

A) 配置漂移：卓越运营；无 RDS 故障转移告警：可靠性；AdministratorAccess：安全；无备份恢复测试：可靠性

B) 配置漂移：安全；无 RDS 故障转移告警：性能效率；AdministratorAccess：卓越运营；无备份恢复测试：成本优化

C) 配置漂移：可靠性；无 RDS 故障转移告警：性能效率；AdministratorAccess：安全；无备份恢复测试：卓越运营

D) 配置漂移：安全；无 RDS 故障转移告警：可靠性；AdministratorAccess：成本优化；无备份恢复测试：安全

**提示 1**：部署流程中的"配置漂移"→ 哪个支柱涵盖部署实践？

**提示 2**：所有用户的"AdministratorAccess"→ 哪个支柱涵盖访问控制？

**提示 3**："备份恢复未测试"→ 哪个支柱涵盖测试你的恢复机制？

**答案**：A

**解释**：部署中的配置漂移（环境不一致）是卓越运营问题——它关乎可靠、一致的部署实践。RDS 故障转移无告警意味着你不知道 HA 机制何时被触发——这是可靠性问题（了解系统的健康状况）。所有用户的 AdministratorAccess 违反了最小权限——这是安全问题。未测试的备份恢复意味着你的可靠性机制（DR）未经验证。

**为什么不是 B？** B 把配置漂移错误地分给了安全（库版本不一致是部署运营问题，不是安全威胁），把 AdministratorAccess 分给了卓越运营（访问控制是安全关注，不是运维流程）。

**为什么不是 C？** C 正确地把 AdministratorAccess 放在了安全，但把配置漂移错误地分给了可靠性（部署一致性属于卓越运营），把未测试的备份恢复分给了卓越运营（恢复测试是可靠性问题——你验证的是系统能否恢复，而不是你的流程是否一致）。

**为什么不是 D？** D 把 AdministratorAccess 分给了成本优化（过宽的权限与成本毫无关系），把未测试的备份恢复分给了安全（无法恢复备份是可靠性失败，而不是安全漏洞）。
