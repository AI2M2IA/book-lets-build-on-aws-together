# 第10章：当数据库太慢时

页面加载指标显示在屏幕上。Leo 盯着它们已经二十分钟没有说话了。

每次页面加载发起四十七次 DynamoDB 请求。仅检索数据就需要一百八十八毫秒——浏览器还没有渲染一个像素。

他已经算过了。周五晚上一万个并发用户：每分钟四十七万次 DynamoDB 读取。成本是真实的。但延迟才是真正的问题。顾客打开 Nimbus 浏览页面，在任何内容显示之前就要等将近两百毫秒——而这还是在网络连接良好的情况下。

"数据库每次请求响应时间为四毫秒，" Leo 说。"实际上很快。DynamoDB 正在做它的工作。"

"那为什么页面很慢？" Maya 问。

"因为我们每次页面加载都调用了四十七次，" Priya 说。"问题不在于数据库。问题是我们和它交谈太多了。"

Tom 向前倾。他有了那种一个问题即将变成成本对话时的表情。"所以解决方案是少和它交谈？"

"少交谈。多记住。"

**餐厅类比**

想象一家餐厅的厨房。每次服务员需要知道今日特价，他们就走到后面，问厨师，再走回桌边。

如果你有两个服务员和三张桌子，这还可以。

现在想象两百个服务员和一千张桌子。每个人都为同一个问题走到后面。厨房成了瓶颈。厨师每小时要回答相同的问题四百次。

显而易见的解决方案：把特价写在餐厅前面的一块黑板上。每个服务员从黑板上读取。厨房得到了休息。黑板在特价改变时更新。

那块黑板就是缓存。

缓存是最近检索到的数据的快速本地存储。你不必反复从慢速来源获取相同的东西，而是获取一次，然后把它放在近处。

**为什么不直接用内存？**

"我们难道不能直接在应用程序的内存中存储菜单吗？" Leo 问。

这是个合理的问题。

你可以。对于单服务器应用程序，内存缓存可以正常工作。但 Nimbus 在负载均衡器后面、跨多个 EC2 实例运行。如果一个实例在其内存中缓存了菜单，其他实例没有那个数据。它们各自维护独立的缓存。当菜单更新时，你需要使所有缓存都失效。

这就是*缓存一致性问题*——让多个缓存保持一致。

ElastiCache 通过提供一个所有实例共享的*集中*缓存来解决这个问题。每台服务器都从同一个缓存读写，而不是各自有自己的内存。一次更新就传播到所有实例。

**认识 ElastiCache**

Amazon ElastiCache 是一种托管缓存服务。它运行流行的缓存引擎——Redis 和 Memcached——而不需要你管理服务器。

**Redis** 是两者中更强大的。它支持复杂的数据结构（字符串、列表、集合、哈希、有序集合）、持久性（数据在重启后存活）、复制和发布/订阅消息传递。Redis 能做的不仅仅是缓存——它可以作为轻量级数据存储。

**Memcached** 更简单。纯键值缓存，水平可扩展，无持久性。对于简单的使用场景更快，但功能更少。

对于 Nimbus：Redis。他们需要缓存菜单数据（结构化）、会话令牌（键值），之后他们还希望有用于"热门餐厅"排名的有序集合。

**缓存在实践中如何工作**

基本缓存模式称为**旁路缓存**（也称为懒加载）：

1. 应用程序需要数据
2. 首先检查缓存
3. 如果找到了（*缓存命中*）：立即返回数据
4. 如果没有找到（*缓存未命中*）：去数据库获取数据，将其存储在缓存中，然后返回

用伪代码：

```
menuData = cache.get("menu:restaurant-047")
if menuData is null:
    menuData = dynamodb.query(TableName="menu", KeyConditionExpression="restaurantId = '047'")
    cache.set("menu:restaurant-047", menuData, ttl=300)  # Cache for 5 minutes
return menuData
```

第一个请求总是会访问数据库。每个后续请求都会命中缓存。有了缓存，Nimbus 每次页面加载的四十七次 DynamoDB 读取变成了一两次缓存查找。快速、便宜、可扩展。

**TTL：你记住多长时间？**

每个缓存条目都有一个**生存时间（TTL）**：该条目过期后，下一个请求返回数据库获取新数据的持续时间。

这是缓存的核心张力：新鲜度与性能。

- **短 TTL（秒）**：非常新鲜的数据，但很多缓存未命中。缓存几乎没有帮助。
- **长 TTL（小时或天）**：非常快，但数据可能变得陈旧。顾客看到昨天的菜单。

对于菜单数据，五分钟是合理的。菜单不会每秒都变化。如果餐厅更新了他们的菜单，顾客可能在最多五分钟内看到旧版本——这是可以接受的。

对于会话令牌（这个用户是否已登录？），更短的 TTL 是有意义的，或者当会话改变时立即更新缓存。

对于财务数据（订单总额、支付记录），不要缓存它——或者如果你这样做，在写入时立即使其失效。

"计算机科学中只有两个难题，" Leo 引用道，带着练习已久的语气。"缓存失效和命名事物。"

"为什么缓存失效很难？" Maya 问。

"因为数据*实际上*是什么时候改变的？菜单是因为餐厅合作伙伴更新了它而改变的吗？还是因为 cron 任务运行了？还是因为管理员手动编辑了它？每个可以改变数据的地方都需要知道要告诉缓存。"

这就是为什么高级工程师以"写入路径是什么？"开始缓存对话，而不是"让我们添加 Redis"。

**缓存淘汰：当黑板写满时**

特价黑板的空间是有限的。当它写满时，你必须擦掉一些内容来腾出空间。

Redis（以及通常的缓存）有*淘汰策略*，决定当内存满时删除什么：

- **LRU（最近最少使用）**：删除最长时间没有被访问的项目。
- **LFU（最不频繁使用）**：删除访问最不频繁的项目。
- **allkeys-random**：随机淘汰。简单，不是最优的。
- **noeviction**：当内存满时返回错误（应用程序必须处理这种情况）。

对于大多数 Web 应用程序：LRU。最近没有查看的东西可能不太需要。

**ElastiCache for Redis：你获得的托管功能**

像 RDS 一样，ElastiCache 采用开源工具并处理运营工作：

- **自动备份**：按计划进行 Redis 快照
- **多 AZ 复制**：主节点 + 不同 AZ 中的只读副本
- **自动故障转移**：如果主 Redis 节点失败，副本会自动提升
- **集群模式**：跨多个节点的水平分片，用于非常大的缓存
- **加密**：传输加密和静态加密，用于合规性
- **VPC 集成**：缓存在你的私有网络中运行，不可公开访问

Tom 看了功能列表。"这要多少钱？"

"比我们要替换的 DynamoDB 读取要少，" Leo 说。"我算过了。"

Tom 的表情从怀疑转变为感兴趣。这是进步。

## 优势与局限性

**为什么缓存很强大**：

- 显著减少数据库负载（更少的查询，更低的成本）
- 缓存命中的亚毫秒响应时间
- 保护你的数据库免受流量峰值的影响
- Redis 支持比简单键值存储更丰富的数据结构

**缓存变得复杂的地方**：

- 缓存失效真的很难——陈旧数据会导致错误
- 增加了运营复杂性（另一个需要监控的服务，另一个故障点）
- 冷启动问题：当你全新部署时，缓存是空的——数据库承担全部负载
- 缓存雪崩：如果很多条目同时过期，所有请求同时访问数据库
- ElastiCache 节点不是免费的——即使空闲也要付费

**ElastiCache 与 DynamoDB DAX 的比较**：

如果你专门缓存 DynamoDB 数据，AWS 提供 **DAX（DynamoDB Accelerator）**——一个专为 DynamoDB 构建的内存缓存。DAX 对你的应用程序代码是透明的（相同的 API），将 DynamoDB 读取延迟降低到微秒，并自动处理缓存失效。

当你的瓶颈是 DynamoDB 读取时，使用 DAX。当你需要任何数据来源的通用缓存时，使用 ElastiCache。

## 摘要

- 缓存是最近检索数据的快速存储——你问一次，记住答案。
- ElastiCache 是 AWS 的托管缓存服务，支持 Redis 和 Memcached。
- **Redis** 更丰富（复杂数据结构、持久性、发布/订阅）。**Memcached** 更简单（纯键值、水平可扩展）。
- **旁路缓存模式**（懒加载）：先检查缓存，在未命中时回退到数据库。
- **TTL** 控制数据缓存的时长。短 TTL = 新鲜，未命中多。长 TTL = 快速，可能陈旧。
- 缓存失效很难。在添加缓存之前了解所有写入路径。
- ElastiCache 管理复制、故障转移、备份和加密——你专注于缓存设计。
- **DAX** 是 DynamoDB 专用缓存。ElastiCache 是通用缓存。

## 考试技巧

*SAA-C03 领域：设计高性能架构（领域3，任务3.3）*

- **考试中的 Redis vs Memcached**：Redis = 持久性、复制、复杂结构、发布/订阅。Memcached = 简单键值、纯水平扩展。当场景提到"不能丢失缓存数据"时，答案是 Redis（它持久化到磁盘）。
- **ElastiCache 使用信号**："数据库是瓶颈"、"读取密集型工作负载"、"减少延迟"、"会话存储"——都指向 ElastiCache。
- **DAX 信号**："减少 DynamoDB 读取延迟"或"DynamoDB 读取太慢"→ DAX，不是 ElastiCache。
- **会话管理**：ElastiCache Redis 是存储用户会话数据的标准答案。无状态应用程序 + Redis 会话存储 = 带一致会话的水平扩展。
- **写穿与旁路缓存**：旁路缓存（懒加载）是最常见的。写穿在每次写入时更新缓存——从不陈旧，但写入操作更多。考试可能区分它们。
- **缓存淘汰策略**：LRU（最近最少使用）是一般 Web 工作负载最常见的考试答案。

**练习 2——考试练习**

*场景*：一个视频流平台为数百万用户服务。可用电影的目录变化不频繁（每晚更新）。应用程序的数据库 CPU 使用率很高，因为每个用户请求都会查询目录。团队希望减少数据库负载，同时保持目录数据在更新后一小时内准确。

哪种解决方案*最能*满足这些需求？

A) 为 RDS 数据库添加只读副本以分配负载  
B) 将目录迁移到带按需容量的 DynamoDB  
C) 使用 ElastiCache for Redis，为目录数据设置1小时的 TTL  
D) 增加 RDS 实例大小以处理更多并发查询

**提示 1**：数据是读取密集型且变化不频繁。什么模式非常适合这种情况？

**提示 2**："在一小时内准确"直接转化为特定的缓存配置参数。

**提示 3**：目标是减少数据库负载，不仅仅是处理更多。

**答案**：C

**解析**：ElastiCache 带一小时 TTL 在第一次每个键的请求后缓存目录数据。后续请求从缓存返回，不访问数据库。当每晚更新运行时，条目在一小时内过期，下一次请求加载新数据。

**为什么不是 A？** 只读副本将读取流量分布到更多数据库节点，但不减少总查询数。它们对于扩展读取很有用，但不能减少频繁重复查询的数据库负载。

**为什么不是 B？** 迁移到 DynamoDB 不能解决根本问题——目录数据仍然会在每个用户请求时从数据库（DynamoDB）获取。

**为什么不是 D？** 扩大实例处理更多并发查询，但不减少查询数量。根本的低效率依然存在。
