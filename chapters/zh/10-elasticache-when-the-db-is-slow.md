# 第10章：当数据库太慢时

页面加载指标显示在屏幕上。Leo 盯着它们看了二十分钟，一句话都没说。

每次页面加载发起四十七次 DynamoDB 请求。光检索数据就要一百八十八毫秒——浏览器还没渲染哪怕一个像素。

他已经算过了。周五晚上一万个并发用户，每人大约每分钟加载一次浏览页：每分钟四十七万次 DynamoDB 读取。成本是实打实的。但延迟才是真正的问题。一个用户打开 Nimbus 的浏览页，要等差不多两百毫秒才能看到任何东西——而这还是在快速网络连接上。

---

*前一周，DynamoDB 的架构重设计奏效了。菜单表现在是灵活的——任何餐厅都可以添加任何修改选项、任何套餐结构、任何季节性变体。单次查找的性能非常出色。但出色的单次查找，乘以每页四十七次，加起来仍然是慢页面。DynamoDB 的问题解决了。一个新问题取代了它的位置。*

---

"数据库每次请求的响应时间是四毫秒，" Leo 说。"这其实很快。DynamoDB 在尽它的本分。"

"那为什么页面慢？" Maya 问。

"因为我们每次页面加载要调用它四十七次，" Priya 说。"问题不在数据库。问题是我们跟它说话说得太多了。"

Tom 向前倾了倾身子。他露出了那种"一个问题即将变成一场成本对话"的表情。"所以解决方案是少跟它说话？"

"少说话。多记住。"

**错误的第一次尝试**

Leo 的第一直觉是缓存按用户划分的数据。每个用户有一个会话，会话要加载他们的个人资料：保存的地址、支付方式、订单历史摘要。也许缓存这些能加快速度。

他实现了它。Redis 键格式：`user:{userId}:profile`。TTL：十分钟。

他跑了负载测试。页面加载快了六毫秒。

"不算多，" Tom 评论道。

"是不多，" Leo 说。

"为什么？"

Leo 盯着图表看了一会儿。"因为用户资料只是一次请求。每页还有四十六次 DynamoDB 调用。而那些是菜单调用——浏览页上每家餐厅一次。我缓存错了东西。"

这是缓存中的一个常见错误：优化了不是瓶颈的那个东西。用户资料的加载只要两毫秒。缓存一个那么快的东西几乎省不下什么。菜单数据——被获取四十七次、每次四毫秒——才是真正的问题。

"你需要按菜单缓存，而不是按用户缓存，" Priya 说。"047号餐厅的菜单对每个浏览它的用户来说都是一样的。那才是值得缓存的数据——它在成千上万次请求之间是完全相同的。"

当用户拥有昂贵的个性化状态时，按用户的缓存有价值。当同一份数据要服务成千上万的用户时，按实体的缓存（菜单、商品目录、配置）才有价值。先弄清你面对的是哪种问题，再动手写代码。

Leo 重新设计了缓存键：`menu:{restaurantId}`。每家餐厅一个缓存条目，由所有浏览这家餐厅的用户共享。

他又跑了一次负载测试。页面加载从188毫秒降到了12毫秒。这才是他们一直在找的那种改进。

**餐厅类比**

想象一家餐厅的厨房。每次服务员需要知道今日特餐，他们就走到后厨，问厨师，再走回餐桌。

如果你有两个服务员和三张桌子，这没问题。

现在想象两百个服务员和一千张桌子。每个人都为了同一个问题往后厨跑。厨房成了瓶颈。厨师每小时要回答同一个问题四百次。

显而易见的解决方案：把特餐写在餐厅前面的一块板子上。每个服务员都看板子。厨房得到了喘息。特餐变了，就更新板子。

那块板子就是缓存。

缓存是对最近检索过的数据的一份快速、就近的存储。与其反复从一个慢速来源获取同样的东西，不如取一次，放在手边。

还有一个工程师们觉得很好用的类比：图书馆的预留书架。当一本热门书被归还时，图书管理员知道它很快又会被借走，于是把它放在前台旁边的预留书架上，而不是放回书库。下一位读者不必走遍整座图书馆——在前台就能找到它。预留书架的空间是有限的。如果放满了，旧的书会被移回书库，给新书腾地方。缓存的工作方式完全相同：频繁访问的数据留在前面，不常访问的数据被淘汰出去腾出空间。

**为什么不直接用内存？**

"我们就不能直接把菜单存在应用程序的内存里吗？" Leo 问。

这是个合理的问题。

可以。对于单服务器应用程序，内存内缓存没问题。但 Nimbus 运行在负载均衡器之后、跨多个 EC2 实例。如果一个实例在自己的内存里缓存了菜单，其他实例就没有这份数据。它们各自维护独立的缓存。菜单更新时，你得让所有这些缓存都失效。

这就是*缓存一致性问题*——让多个缓存保持一致。

ElastiCache 通过提供一个所有实例共享的*集中式*缓存来解决这个问题。不是每台服务器各有各的内存，而是每台服务器都读写同一个缓存。一次更新，传播到所有实例。

**认识 ElastiCache**

"等等——可是*为什么*要那样做？" Maya 问。"为什么要一个全新的服务？为什么不直接增加数据库容量？"

好问题。答案是：增加数据库容量——更大的实例、更多的只读副本——并不能解决根本问题。每次页面加载的那四十七次请求，即使在更快的数据库上，依然要花时间和金钱。缓存不会让数据库变快；它意味着数据库被问到同一个问题的次数大大减少。对于反复被读取而又很少变化的数据——比如一家餐厅的菜单——有了缓存，数据库可能每五分钟才回答一次这个问题，而不是每次页面加载回答四十七次。

Amazon ElastiCache 是一种托管缓存服务。它运行流行的缓存引擎——Redis 和 Memcached——而你不需要管理服务器。

**Redis** 是两者中更强大的那个。它支持复杂的数据结构（字符串、列表、集合、哈希、有序集合）、持久化（数据在重启后仍然存在）、复制和发布/订阅消息。Redis 能做的不止缓存——它可以充当一个轻量级数据存储。

**Memcached** 更简单。纯键值缓存，可水平扩展，没有持久化。对简单用例更快，但功能更少。

对于 Nimbus：Redis。他们需要缓存菜单数据（结构化）、会话令牌（键值），而且之后他们还会需要有序集合来做"热门餐厅"排名。

**缓存在实践中如何工作**

基本的缓存模式叫做**旁路缓存**（cache-aside，也叫懒加载）：

1. 应用程序需要数据
2. 先检查缓存
3. 如果找到了（*缓存命中*）：立即返回数据
4. 如果没找到（*缓存未命中*）：去数据库取数据，把它存进缓存，再返回

用伪代码表示：

```
menuData = cache.get("menu:restaurant-047")
if menuData is null:
    menuData = dynamodb.query(TableName="menu", KeyConditionExpression="restaurantId = '047'")
    cache.set("menu:restaurant-047", menuData, ttl=300)  # Cache for 5 minutes
return menuData
```

第一个请求总是会打到数据库。之后的每个请求都命中缓存。有了缓存，Nimbus 每次页面加载的四十七次 DynamoDB 读取变成了一两次缓存查找。快、便宜、可扩展。

**TTL：你要记住多久？**

每个缓存条目都有一个**生存时间（TTL）**：超过这个时长后条目过期，下一个请求会回到数据库去取新鲜数据。

这是缓存的核心张力：新鲜度对性能。

- **短 TTL（秒级）**：数据非常新鲜，但缓存未命中很多。缓存几乎帮不上忙。
- **长 TTL（小时或天）**：非常快，但数据可能变陈旧。顾客看到的是昨天的菜单。

对于菜单数据，五分钟是合理的。菜单不会每秒都变。如果一家餐厅更新了菜单，顾客最多在五分钟内可能看到旧版本——可以接受。

对于会话令牌（这个用户登录了吗？），更短的 TTL 更合理，或者在会话变化时立即更新缓存。

对于财务数据（订单总额、支付记录），不要缓存——或者如果你缓存了，在写入时立即让它失效。

你可能想知道：为什么不直接增加数据库容量，而要引入一整层新的缓存？更多副本、更大的实例——为什么不那样？答案是：增加数据库容量放大的是你处理并发请求的能力，但它不会减少请求的数量。如果一万个用户每次页面加载各自触发四十七次读取，加一个第二只读副本只是意味着每个副本处理两万三千次请求而不是四万七千次——总工作量没有缩小。缓存则彻底消除了这些冗余工作：那一万个用户共享同一份缓存结果。

"计算机科学里只有两个难题，" Leo 引用道，带着说过很多遍的熟练腔调。"缓存失效，和给东西起名字。"

"为什么缓存失效很难？" Maya 问。

"因为数据*到底*是什么时候变的？菜单是因为餐厅合作伙伴更新了它而变的？还是因为某个 cron 任务跑了？还是因为某个管理员手动改了它？每一个能改动数据的地方，都得知道要去通知缓存。"

这就是为什么资深工程师开启一场缓存对话时，先问的是"写入路径有哪些？"，而不是"我们加个 Redis 吧"。

**缓存失效的故事**

第一次有餐厅合作伙伴投诉时，他们才发现缓存失效到底有多难。

112号餐厅——东区的一家哥伦比亚餐馆——在一个星期四的下午更新了价格。他们把 arepa（玉米饼）从 $8 涨到了 $9。二十分钟后他们打给了 Nimbus 的客服。

"我们的菜单还在显示旧价格，" 老板说。"顾客在按 $8 下单。我们现在不得不认这个价。"

Priya 追查 bug 的同时，Tom 在计算损失。那二十分钟里下的每一单都收的是 $8。餐厅想要的是 $9。差价得由 Nimbus 来承担。

五分钟的 TTL 早就应该过期了。已经过去二十分钟了。Priya 调出了代码。

缓存键是 `menu:restaurant-112`。它被设置了300秒的 TTL。她查了它最后一次被写入的时间。

"它是下午2:03被设置的，" 她说。"二十二分钟之前。"

"可 TTL 是五分钟，" Leo 说。

"TTL 是从它第一次被缓存起的五分钟。但每个命中缓存的请求都在刷新 TTL。这个缓存条目每隔几秒就被进来的请求碰一下，TTL 就被重置一次。"

"所以它永远不会过期。"

"在这个实现里不会。我们在每次缓存读取时都设置了 TTL。滑动窗口。只要有人在访问它，这个条目就一直活着。"

修复方案：使用只在写入时设置、从不在读取时延长的固定 TTL。条目在存储后恰好五分钟过期，不管它被读了多少次。餐厅更新菜单后，旧条目会在五分钟内过期，下一个请求就会取到新数据。

"那对于餐厅更新价格、我们需要立即生效的情况呢？" Tom 问。

"主动失效，" Priya 说。"当餐厅合作伙伴门户提交一次更新时，API 在返回之前调用 `cache.delete('menu:restaurant-112')`。下一个请求立即获取新数据。"

"但那要求门户知道缓存的存在。"

"每一条通往数据库的写入路径都需要知道缓存的存在。这就是 Leo 之前说的那句话。现在我们亲身经历了。"

"我已经部署上线了——哦。" Leo 在门户里实现了失效逻辑，却忘了管理员编辑界面。两周后，一名管理员通过内部仪表板更新了一份菜单，旧价格在缓存里又滞留了五分钟。同一起事故的缩小版。

他们添加了一个 DynamoDB Streams 处理程序——来自上一章——只要菜单项发生变化，无论是哪个系统触发的写入，它都会自动让缓存失效。一个处理程序，覆盖所有写入路径。

**缓存淘汰：当板子写满时**

特餐板的空间是有限的。写满了，你就得擦掉点什么来腾地方。

Redis（以及一般的缓存）有*淘汰策略*，决定内存满时删除什么：

- **LRU（最近最少使用）**：删除最长时间没有被访问的项目。
- **LFU（最不经常使用）**：删除访问频率最低的项目。
- **allkeys-random**：随机淘汰。简单，但不是最优。
- **noeviction**：内存满时返回错误（应用程序必须处理这种情况）。

对大多数 Web 应用程序来说：LRU。你最近没看过的东西，多半也不那么需要。

**缓存雪崩问题**

"我们想过整个缓存一下子全空了会发生什么吗？" Priya 问。

"什么时候会发生那种事？" Leo 说。

"部署一个新的 ElastiCache 集群的时候。一大批条目的 TTL 同时过期的时候。修完一个 bug 之后刷新缓存强制重载的时候。"

Leo 把这事想了一遍。"如果缓存是空的，每个请求都会打到数据库。同时打过去。在那几秒钟里，数据库要承担每一个并发用户的全部负载。"

"前面没有任何缓存挡着。"

"那会很疼。" Leo 看了看数据库的容量设置。"我们肯定会被限流。"

这叫做**缓存雪崩**（cache stampede，也叫惊群效应/thundering herd）。当许多缓存条目同时过期时就会发生——通常是因为它们在一次部署或冷启动期间被同时创建——突然涌起的缓存未命中浪潮会同时砸向数据库。

缓解策略：

**TTL 抖动（jitter）**：不要把每个菜单条目都精确设成300秒，而是加入随机变化：270到330秒。条目在略微不同的时间过期，把缓存未命中的浪潮摊开到一分钟里，而不是同时砸下来。

**概率性提前过期**：在条目过期之前，一小部分请求主动刷新它。这让条目在变陈旧之前就保持新鲜，使过期永远不会真正变成一次未命中。

**请求合并（互斥锁）**：发生缓存未命中时，先获取一把锁再访问数据库。对同一个键的其他并发请求等待第一个请求完成并重新填充缓存，然后从缓存读取。即使在高并发下，每次缓存未命中也只发出一次数据库请求。

对于 Nimbus，他们实现了 TTL 抖动。简单、有效、不增加任何额外复杂性。

```python
import random
TTL_BASE = 300
TTL_JITTER = 30
ttl = TTL_BASE + random.randint(-TTL_JITTER, TTL_JITTER)
cache.set(key, value, ttl=ttl)
```

"两行代码，" Leo 说。"就能防止部署期间一次潜在的数据库宕机。"

"大多数可靠性改进都是这样，" Priya 说。"实现起来便宜，等你发现自己需要它们时才知道有多贵。"

**Redis 数据结构：不止键值**

Nimbus 添加"热门餐厅"功能时，Leo 起初把排名存成了一个普通的 JSON 列表：`trending:global → ["NIMBUS-047", "NIMBUS-112", ...]`。

能用，但更新起来很别扭。要添加一家新餐厅或更新分数，他得读出整个列表，在应用代码里修改，再把整个东西写回去。在分析管道的并发写入之下，竞态条件导致分数被覆盖。

Priya 让他去看 Redis 的有序集合。

Redis 中的**有序集合（sorted set）**存储带有关联数值分数的成员。成员按分数自动排序。操作是原子的——并发更新不会产生竞态条件。

```
# Add/update a restaurant's score
ZADD trending:global 9420 "NIMBUS-047"
ZADD trending:global 8831 "NIMBUS-112"

# Get top 10 restaurants by score (highest first)
ZREVRANGE trending:global 0 9 WITHSCORES

# Increment a restaurant's score atomically
ZINCRBY trending:global 50 "NIMBUS-047"
```

分析 Lambda 在每次有人下单时调用 `ZINCRBY`，递增这家餐厅的分数。首页调用 `ZREVRANGE` 获取前十名。没有锁，没有竞态条件，没有"读-改-写"循环。

除了简单键值，Redis 还支持其他几种数据结构：

**列表（Lists）**：有序序列。可以从头部或尾部推入。用于队列、最近活动信息流、日志流。

**集合（Sets）**：无重复的无序集合。支持并集、交集、差集运算。用于"哪些用户看过这条通知？"或"哪些餐厅属于这个分类？"

**哈希（Hashes）**：一个键内的命名字段。用于结构化对象——你想更新单个字段而不重写整个对象的时候。

**HyperLogLog**：概率性基数估计。统计一个页面的独立访客数，而不存储每个访客的 ID。紧凑且快速。

**发布/订阅（Pub/Sub）**：向频道发布消息；订阅者实时收到。用于服务之间轻量级的实时通知。

"Redis 不只是一个缓存，" Leo 说。"它是一个数据结构服务器。"

"那是它的官方描述，" Priya 说。

"我还以为它只是一个高级点的字典。"

"它起初确实是。"

**写穿透：另一种缓存模式**

旁路缓存（懒加载）是最常见的模式。但还有第二种值得了解：**写穿透（write-through）**。

在写穿透缓存中，应用程序每次写入数据库时，也同时立即写入缓存。

```python
def update_menu(restaurant_id, menu_data):
    dynamodb.put_item(TableName="menu", Item=menu_data)
    cache.set(f"menu:{restaurant_id}", menu_data, ttl=300)
```

优点：缓存永远是最新的。在一次写入和 TTL 过期之间不存在陈旧数据。

缺点：每次写入要去两个地方。而且你填充进缓存的数据可能永远不会被读到。如果十家餐厅更新了菜单，但其中只有两家在接下来五分钟内有可观的流量，那你就为八个在过期前都不会被使用的缓存做了写穿透的无用功。

"等等——可是*为什么*要那样做？" Maya 问。"如果我们每次更新都要写缓存，那每次写入的工作量比以前还多。这怎么会更好？"

"它不总是更好，" Priya 说。"当你无法容忍写入之后存在任何陈旧数据窗口时，写穿透才有意义。旁路缓存接受最多一个 TTL 的陈旧期，换来的是不必在每次写入时做额外工作。"

对于 Nimbus：旁路缓存是正确的选择。菜单被读取的频率远高于被写入。五分钟的陈旧窗口可以接受。而对于一个每次价格更新都必须立即生效的金融交易系统，写穿透会更合适。

这个决策归结为两个问题：你的写读比是多少，以及你对写入之后的陈旧读取有多大容忍度？

**ElastiCache for Redis：托管为你做了什么**

和 RDS 一样，ElastiCache 把一个开源工具接过来，处理掉所有运营工作：

- **自动备份**：按计划做 Redis 快照
- **多 AZ 复制**：主节点 + 位于不同 AZ 的只读副本
- **自动故障转移**：如果 Redis 主节点失败，会自动提升一个副本
- **集群模式**：跨多个节点的水平分片，用于非常大的缓存
- **加密**：传输加密和静态加密，用于合规
- **VPC 集成**：缓存运行在你的私有网络中，不可公开访问

"这每个月要花多少钱？" Tom 问。

"比我们要替换掉的那些 DynamoDB 读取要少，" Leo 说。"大约每月省两百美元。"

Leo 调出了价格页面。他已经算过了，但他还是带着 Tom 过了一遍。

一个 `cache.t3.micro`——最小的节点——大约每月 $12。它有 0.5 GB 内存。对一个只有几百个缓存键的小应用来说足够了。

一个 `cache.r6g.large`——适合 Nimbus 流量的档位——有 13 GB 内存，大约每月 $140。作为对比，Nimbus 在引入缓存之前每月在 DynamoDB 读取上花费大约 $400。引入缓存后，那些读取下降了大约 89%。算下来，DynamoDB 读取大约每月省下 $356，减去 ElastiCache 上花的 $140——每月净省大约 $216。

Tom 的表情从怀疑变成了满意。"在扩大规模之前把数字好好算清楚，不过这账对得上。" 他记了下来。

"它会在私有子网里，" Leo 说。

**监控缓存**

"我们想过缓存工作不正常时会发生什么吗？" Redis 部署一周后，Priya 问。"不是说彻底挂掉——而是能用，但用得很差。未命中率高。淘汰率高。延迟在悄悄上升。"

"页面加载时间变长的时候我会注意到的，" Leo 说。

"到那个时候，数据库已经在苦苦支撑了，" 她说。

ElastiCache 通过 CloudWatch 暴露指标。最重要的几个：

**CacheHitRate**：返回了结果的缓存读取所占的百分比。对一个成熟的缓存来说，理想情况应高于 80%。命中率下降意味着你访问最频繁的数据不在缓存里——要么 TTL 太短，要么缓存太小，要么你的访问模式变了。

**CacheMisses**：缓存未命中的绝对计数。这里突然飙升意味着缓存没在起作用，数据库正在承担全部负载。

**Evictions**：为了给新条目腾地方而被淘汰的缓存项数量。高淘汰率意味着你的缓存对你的工作集来说太小了。你需要更多内存，或者更有选择性的缓存策略。

**CurrConnections**：当前到 Redis 的客户端连接数。连接太多会耗尽 Redis 的连接上限。应用程序应该使用连接池，避免每个请求都新开一个连接。

**ReplicationLag**：只读副本落后主节点的程度。如果它在增长，副本读取可能返回陈旧数据。

Leo 设置了两个 CloudWatch 警报。第一个：如果缓存命中率连续十五分钟低于 70% 就告警——那意味着一个值得在数据库感受到压力之前就去调查的问题。第二个：如果淘汰率超过每分钟100次就告警——那意味着缓存容量不足。

"两个警报，" Priya 一边检查配置一边说。"这是个好的开始。"

"我还加了一个仪表板，" Leo 说。"命中率、未命中率、淘汰数、延迟。全在一个地方可见。"

"这比等页面变慢要好。"

"好得多，" Leo 表示同意。

**ElastiCache 与 DAX：给 DynamoDB 用哪个缓存？**

"既然我们缓存的是 DynamoDB 的数据，" Maya 问，"为什么不用 DAX 而用 ElastiCache？我在文档里看到过它。"

好问题。

**DAX（DynamoDB Accelerator）**是一个专为 DynamoDB 构建的内存缓存。它在客户端层面拦截 DynamoDB 的 API 调用——你的应用代码用同一套 DynamoDB SDK 与 DAX 对话。缓存未命中会自动从 DynamoDB 获取。缓存命中以微秒级返回。数据变化时失效是自动处理的。

**ElastiCache** 是一个通用缓存。缓存键、TTL 逻辑、失效——全都由你来管理。更多控制权，更多责任。

各自的适用场景：

| 场景 | 推荐 |
|---|---|
| 你在缓存 DynamoDB 读取，并且希望零应用改动 | DAX |
| 你需要 DynamoDB 读取的微秒级延迟 | DAX |
| 你在缓存多个来源的数据（DynamoDB + RDS + 外部 API） | ElastiCache |
| 你需要 Redis 数据结构（有序集合、发布/订阅、HyperLogLog） | ElastiCache |
| 你需要细粒度的 TTL 控制和自定义失效逻辑 | ElastiCache |
| 你需要会话存储、限流或分布式锁 | ElastiCache |

对于 Nimbus：他们选择了 ElastiCache，因为他们要缓存多个来源的数据——DynamoDB 的菜单、RDS 的订单历史摘要、外部 API 的餐厅评分。DAX 只能配合 DynamoDB 使用。而且他们需要 Redis 有序集合来做热门排名。

"如果这纯粹是一个 DynamoDB 缓存问题，" Priya 说，"DAX 会是更简单的答案。一个服务、自动失效、同一套 API。但我们的数据来源不止一个。"

"所以只用 DynamoDB 的时候 DAX 更简单，" Maya 总结道。"需要完整工具箱的时候用 ElastiCache。"

"这就是取舍。"

### 当缓存数据不能丢失时：Amazon MemoryDB

"为什么会有人把 Redis 当主数据库用？" Maya 问。"它不是缓存吗？"

这正是该问的问题。

ElastiCache for Redis 是一个缓存——快速、内存内，并且从设计上就不是事实来源。如果一个 ElastiCache 节点失败，重启后缓存是空的。应用程序从数据库重新预热它。对缓存来说这没问题。

但有些用例把 Redis 当作的不是缓存，而是主数据存储——必须在重启后存活的会话状态、不容丢失的实时排行榜、必须挺过一次 AZ 故障的购物车。对这些用例来说，ElastiCache 的"最终持久性"是一种风险。

**Amazon MemoryDB for Redis** 是一个完全托管的、Redis 兼容的、持久的内存数据库。与 ElastiCache 不同，MemoryDB 使用一个跨多个 AZ 存储的分布式事务日志，让每一次写入在被确认之前就已经是持久的。数据能在节点故障中存活——不是因为它从一个更慢的数据库重放回来，而是因为它从来就不只存在于一个地方。

关键区别：

| | ElastiCache for Redis | MemoryDB for Redis |
|---|---|---|
| 角色 | 缓存层 | 主数据库 |
| 持久性 | 故障时不保证 | 多 AZ 事务日志 |
| 延迟 | 微秒级读写 | 微秒级读取，个位数毫秒级写入 |

两者支持同样的 Redis 命令和数据结构。API 是一样的。持久性保证则不一样。

对于 Nimbus：团队想把每家餐厅的实时订单计数存成一个 Redis 有序集合——而且它必须在一次 AZ 故障中存活，无需从数据库重新填充。这个需求——Redis 兼容*并且*持久——正是指向 MemoryDB 的确切信号。

"所以故障之后我们不用重新预热它？" Leo 问。

"这就是重点，" Priya 说。"如果节点挂了又恢复，数据还在。事务日志把它保住了。"

Leo 盯着价格页面看了一会儿。"它比 ElastiCache 贵。"

"值得信任的东西都贵，" Priya 说。

## 优势与局限性

**为什么缓存很强大**：

- 显著降低数据库负载（更少的查询，更低的成本）
- 缓存命中的亚毫秒级响应时间
- 保护你的数据库免受流量峰值冲击
- Redis 支持比简单键值存储更丰富的数据结构
- 缓存雪崩缓解措施（TTL 抖动、请求合并）能防御冷启动时的请求洪峰

**缓存变得复杂的地方**：

- 缓存失效真的很难——陈旧数据会引发 bug
- 增加运营复杂性（又一个要监控的服务，又一个故障点）
- 冷启动问题：全新部署时缓存是空的——数据库承担全部负载
- 缓存雪崩：如果许多条目同时过期，所有请求会同时打到数据库
- ElastiCache 节点不是免费的——即使空闲也要付费

**ElastiCache 与 DynamoDB DAX 的对比**：

如果你专门缓存 DynamoDB 的数据，AWS 提供 **DAX（DynamoDB Accelerator）**——一个专为 DynamoDB 构建的内存缓存。DAX 对你的应用代码是透明的（同一套 API），把 DynamoDB 读取延迟降到微秒级，并自动处理缓存失效。

当你的瓶颈是 DynamoDB 读取、并且想要零改动的缓存时，用 DAX。当你需要面向任意数据来源的通用缓存，或者需要 Redis 数据结构时，用 ElastiCache。

## 摘要

四十七次数据库调用变成了一次缓存查找。页面从188毫秒降到了12毫秒。添加缓存层是一个成长中的应用所能做出的杠杆效应最高的改动之一——但前提是缓存经过深思熟虑的设计，并对"这份数据什么时候会变？"这个问题有清晰的答案。

- 缓存是对最近检索数据的一份快速存储——问一次，记住答案。ElastiCache 是 AWS 的托管缓存服务，支持 **Redis**（持久化、复杂数据结构、发布/订阅）和 **Memcached**（纯键值、水平扩展）。
- **旁路缓存模式**（懒加载）：先查缓存，未命中时回退到数据库。**TTL** 控制数据缓存多久——短 TTL 意味着更新鲜的数据和更多未命中；长 TTL 意味着更快的响应和潜在的陈旧。
- 缓存对的东西：被许多用户共享的按实体数据，而不是每个会话独有的按用户数据。许多条目同时过期会引发缓存雪崩——用 TTL 抖动来缓解。
- 只涉及 DynamoDB 的缓存，**DAX** 是正确选择。多来源缓存和 Redis 数据结构，**ElastiCache** 更灵活。
- 缓存最难的部分是失效：知道数据何时变化，并在所有写入它的代码路径上更新缓存。缓存的可信度，取决于它的失效策略。

## 考试技巧

*SAA-C03 领域：设计高性能架构（领域3，任务3.3）*

- **考试中的 Redis vs Memcached**：Redis = 持久化、复制、复杂结构、发布/订阅。Memcached = 简单键值、纯水平扩展。当场景提到"不能丢失缓存数据"时，答案是 Redis（它会持久化到磁盘）。
- **ElastiCache 用例信号**："数据库是瓶颈"、"读取密集型工作负载"、"降低延迟"、"会话存储"——都指向 ElastiCache。
- **DAX 信号**："降低 DynamoDB 读取延迟"或"DynamoDB 读取太慢" → DAX，不是 ElastiCache。
- **会话管理**：ElastiCache Redis 是存储用户会话数据的标准答案。无状态应用 + Redis 会话存储 = 带一致会话的水平扩展。
- **写穿透 vs 旁路缓存**：旁路缓存（懒加载）最常见。写穿透在每次写入时更新缓存——永不陈旧，但写操作更多。考试可能区分它们。
- **缓存淘汰策略**：LRU（最近最少使用）是一般 Web 工作负载最常见的考试答案。
- **ElastiCache 与 MemoryDB 的对比：**ElastiCache = 缓存层，快速，故障时数据丢失可接受。MemoryDB = 持久的内存内主数据库，Redis 兼容，多 AZ 事务日志。考试触发词："Redis 兼容且持久"或"以 Redis 作为主数据存储" → MemoryDB，不是 ElastiCache。

**练习 2——SAA-C03 场景题**

*场景*：一个视频流媒体平台服务数百万用户。可观看电影的目录变化不频繁（每晚更新一次）。由于每个用户请求都查询目录，应用程序遇到了很高的数据库 CPU 使用率。团队希望在保持目录数据在更新后一小时内准确的前提下，降低数据库负载。

哪种方案**最能**满足这些需求？

A) 为 RDS 数据库添加只读副本以分散负载  
B) 把目录迁移到使用按需容量的 DynamoDB  
C) 使用 ElastiCache for Redis，为目录数据设置1小时的 TTL  
D) 增大 RDS 实例规格以处理更多并发查询

**提示 1**：数据是读取密集型且很少变化。什么模式最适合这种情况？

**提示 2**："在一小时内准确"直接对应一个特定的缓存配置参数。

**提示 3**：目标是减少数据库负载，而不只是承担更多负载。

**答案**：C

**解析**：带一小时 TTL 的 ElastiCache 在每个键的第一次请求之后缓存目录数据。后续请求从缓存返回，完全不触碰数据库。当每晚的更新运行后，条目会在一小时内过期，下一次请求加载新数据。

**为什么不是 A？** 只读副本把读取流量分散到更多数据库节点上，但不减少查询的总数。它们适合扩展读取，而不适合减少频繁重复查询带来的数据库负载。

**为什么不是 B？** 迁移到 DynamoDB 没有解决根本问题——目录数据仍然会在每个用户请求时从数据库（DynamoDB）获取。

**为什么不是 D？** 扩大实例能处理更多并发查询，但不减少查询数量。根本性的低效仍然存在。
