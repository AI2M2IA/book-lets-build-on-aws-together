# 附录 D：完整模拟考试（65 题）

这是一套完整的 SAA-C03 模拟考试：65 道题，按照真实考试的领域权重分布——设计安全架构（问题 1–20，约 30%）、设计弹性架构（问题 21–37，约 26%）、设计高性能架构（问题 38–53，约 24%）、设计成本优化架构（问题 54–65，约 20%）。

**如何使用：**

- 设置一个 **130 分钟**的计时器——这是真实考试的时长。练习节奏：平均每题两分钟。
- 有七道题标注了 **"（选择两项。）"**——它们有五个选项，恰好两个正确答案，和真实考试的多项响应题一样。两个都答对才能得分。
- 在做完全部 65 题之前不要看答案。真实考试中途没有任何反馈，训练你对不确定性的容忍度本身就是备考的一部分。
- 真实考试包含 15 道你无法识别的未评分实验题。这里的 65 题全部"计分"。一个通过基准：**答对 47 题或以上（约 72%）**意味着你处于 720/1000 标准化通过分数的区间内。低于 47 题，请在预约考试前，按照附录 B 中映射的章节复习你的薄弱领域。
- 对于每一道做错的题——以及每一道虽然做对但犹豫过的题——请阅读干扰项分析。考试考查的是貌似合理的选项之间的*差异*，学习的价值正在于此。

## 答案

### 第一部分 — 问题 1–20

**1. 答案：B** — SCP 永远不适用于组织的管理账户，因此其主体不受区域限制的影响。*为什么其他选项不对：* A——SCP 会通过嵌套 OU 继承；C——在成员账户中，IAM 的 Allow 无法覆盖 SCP 的 Deny；D——SCP 对附加点之下的所有当前和未来账户立即生效。

**2. 答案：C** — 通过角色创建操作上的条件强制执行的权限边界，可以限制开发人员创建的任何角色的最大权限，在保留自助服务的同时防止权限提升。*为什么其他选项不对：* A——人工审核增加运维开销并取消了自助服务；B——拒绝 iam:CreateRole 会阻断合法的工作流程；D——CloudTrail 告警是检测性的，不是预防性的。

**3. 答案：B** — 由客户定义并在信任策略条件中验证的 ExternalId 确保 SaaS 提供商只代表正确的客户代入角色，从而缓解混淆代理问题。*为什么其他选项不对：* A——MFA 对自动化的服务间角色代入不切实际，也无法解决代理混淆；C——加密一个本来就不是机密的 ARN 毫无意义；D——长期的 IAM 用户密钥比角色更不安全。

**4. 答案：B** — IAM Identity Center 与 Entra ID 只需联合一次，即可通过单一访问门户在所有组织账户中集中分配权限集。*为什么其他选项不对：* A——逐账户的 IAM 用户正是要避免的开销；C——Cognito 面向应用程序（客户）身份，而非员工对 AWS 账户的访问；D——手动逐账户配置 SAML 可行，但运维开销高得多。

**5. 答案：A** — User pool 处理身份验证（电子邮件/社交登录）；identity pool 将得到的令牌交换为受 IAM 角色限定范围的临时 AWS 凭证以访问 S3。*为什么其他选项不对：* B——颠倒了两项服务的用途；C——IAM Identity Center 面向员工用户，而非应用客户；D——user pool 令牌（JWT）本身不授予 AWS 服务访问权限。

**6. 答案：B** — 客户管理密钥可完全控制密钥策略、使用日志记录和禁用，并支持自动轮换（默认每年）。*为什么其他选项不对：* A——AWS 管理的密钥不允许编辑密钥策略或禁用密钥；C——AWS 拥有的密钥对客户完全不可见；D——导入（BYOK）密钥材料不支持自动轮换。

**7. 答案：B** — 信封加密：KMS 生成数据密钥；数据在本地用明文数据密钥加密，明文密钥随后被丢弃，而经 KMS 加密的数据密钥副本与密文一起存储。*为什么其他选项不对：* A 和 C——KMS 从不直接或以流式方式加密大型负载；D——硬编码密钥是反模式，也不是信封加密。

**8. 答案：C** — Secrets Manager 的交替用户策略维护两套凭证并轮流轮换，使用旧凭证的现有连接在轮换期间继续工作。*为什么其他选项不对：* A——Parameter Store 没有内置轮换；一切都要自己构建；B——单用户轮换会立即使旧密码失效，有连接失败的风险；D——KMS 轮换的是加密密钥材料，不是数据库密码。

**9. 答案：C** — SSE-C 允许客户在每次请求时提供加密密钥；AWS 仅在内存中将其用于该操作，从不存储。*为什么其他选项不对：* A——SSE-S3 密钥完全由 AWS 管理；B——SSE-KMS 密钥存储在 AWS KMS 中；D——aws/s3 是 AWS 管理的 KMS 密钥，根本不是客户端方案。

**10. 答案：B** — Object Lock 合规模式可防止任何用户（包括根用户）在保留期到期前删除或覆盖对象，且 Object Lock 要求启用版本控制。*为什么其他选项不对：* A——治理模式可以被拥有 s3:BypassGovernanceRetention 权限的用户绕过；C——桶策略可以被根用户修改或移除；D——生命周期过期并不能防止保留期内的删除。

**11. 答案：B** — NACL 是无状态的，因此返回客户端临时源端口的响应流量必须在出站方向明确允许。*为什么其他选项不对：* A——NACL 是无状态的，不是有状态的；C——安全组是有状态的，返回流量自动放行；D——0.0.0.0/0 在 NACL 规则中完全有效。

**12. 答案：A、B** — 安全组是有状态的（返回流量自动允许），NACL 按编号顺序处理规则并支持 Deny。*为什么其他选项不对：* C——安全组只支持 Allow 规则；D——NACL 附加到子网，而非 ENI（安全组才附加到 ENI）；E——安全组规则整体一起评估，没有顺序之分。

**13. 答案：B** — Shield Advanced 为 CloudFront 和 ALB 等受保护资源提供 Shield Response Team、DDoS 成本保护以及攻击可见性/诊断。*为什么其他选项不对：* A——Shield Standard 是自动的，但不包含 SRT 联系渠道和成本保护；C——WAF 针对第 7 层请求模式，无法满足全部要求；D——GuardDuty 是威胁检测，不是 DDoS 防护。

**14. 答案：B** — 在 ALB 上配置 AWS WAF，使用 SQLi 托管规则组加一条速率规则，无需修改任何应用代码即可阻止两种攻击模式。*为什么其他选项不对：* A——开发工作量大；C——Shield Standard 覆盖 L3/L4 洪泛，不防 SQL 注入；D——安全组无法检查请求内容。

**15. 答案：B** — GuardDuty = 基于日志和威胁情报的威胁检测；Macie = S3 中的敏感数据（PII）发现；Inspector = 对 EC2、ECR 镜像和 Lambda 的漏洞（CVE）扫描。*为什么其他选项不对：* A、C、D——每个都至少混淆了两项服务与用途的对应关系。

**16. 答案：B** — 网关终端节点恰好只为 S3 和 DynamoDB 而存在，将流量保留在 AWS 网络内，且没有按小时或按数据处理的费用。*为什么其他选项不对：* A——NAT gateway 经由公共 IP 空间路由且按小时/按 GB 收费；C——接口终端节点产生小时费和数据费，并非成本最低；D——internet gateway 将流量发送到公共互联网。

**17. 答案：A** — IMDSv2 要求通过 PUT 请求获取会话令牌，而典型的 SSRF 攻击向量无法执行 PUT；强制 HttpTokens=required 可阻止 IMDSv1 凭证窃取。*为什么其他选项不对：* B——许多代理和 SDK 合法地需要 IMDS；C——NACL 不影响实例与其自身元数据端点之间的链路本地流量；D——文件中的静态凭证远比角色凭证糟糕。

**18. 答案：C** — Parameter Store 标准参数免费，适合明文配置；Secrets Manager 仅为那 5 个密码提供内置轮换，使成本最小化。*为什么其他选项不对：* A——为 200 个普通配置值支付 Secrets Manager 的按机密计费是浪费；B——单靠 Parameter Store 没有针对密码的原生轮换；D——Parameter Store 没有内置自动轮换，该选项陈述了一个不存在的功能。

**19. 答案：B** — S3 Bucket Keys 让 S3 从 KMS 密钥生成一个有时效的桶级数据密钥，大幅减少按对象计的 KMS 请求（和成本），同时仍保持 SSE-KMS。*为什么其他选项不对：* A——SSE-S3 放弃了 KMS 要求；C——轮换频率不影响每次请求的 API 量；D——导入密钥材料不会改变请求计数。

**20. 答案：B、D** — 在策略评估中，明确 Deny 始终胜过任何 Allow；权限边界只限制（从不授予）权限。*为什么其他选项不对：* A——SCP 是限制可用权限的护栏，不授予任何权限；C——基于资源的策略可以独立地授予跨账户访问，这很常见；E——当没有任何策略允许某个操作时，IAM 默认隐式拒绝。

### 第二部分 — 问题 21–37

**21. 答案：C** — Multi-AZ 为 AZ 故障提供自动故障转移；读副本吸收报表读取流量——两个功能解决两个不同的问题。*为什么其他选项不对：* A——传统的 Multi-AZ 备用实例无法承担读取；B——副本提升是手动（或脚本化）的，仅有副本无法提供自动的 HA 故障转移；D——更大的单 AZ 实例在 AZ 弹性上同时不满足两个要求。

**22. 答案：B** — Multi-AZ DB 集群部署在三个 AZ 中运行一个写入实例和两个可读备用实例，并带有读取端点，使备用容量在承担读取的同时仍支持快速自动故障转移。*为什么其他选项不对：* A——实例部署中的单个备用实例不承担任何流量；C——读副本不提供托管的自动故障转移，RDS 数据库也不能通过 ALB 进行负载均衡；D——单 AZ 完全没有故障转移。

**23. 答案：B** — Aurora Global Database 的复制是存储层的异步复制，典型延迟低于一秒，因此跨区域 RPO 接近零，但永远无法保证恰好为 0。*为什么其他选项不对：* A——跨区域复制不是同步的；C——写转发将写入路由到主区域；它不改变复制语义；D——复制延迟通常低于一秒，不是 5 分钟的计划。

**24. 答案：B** — 恢复时间目标是可容忍的最长停机时间（4 小时）；恢复点目标是可容忍的最大数据丢失窗口（15 分钟）。*为什么其他选项不对：* A——颠倒了定义；C——MTBF/MTTR 是可靠性统计指标，不是 DR 目标；D——SLA 是合同承诺，不是数据丢失指标。

**25. 答案：B** — Pilot light 保持数据持续复制、核心资源已预置但处于关闭状态，以低成本实现数十分钟的 RTO——完全匹配。*为什么其他选项不对：* A——备份和恢复没有实时复制，RTO 长得多；C——warm standby 让整个技术栈持续运行，成本超出需求；D——主动/主动最昂贵，远超此要求。

**26. 答案：C、E** — Warm standby 是规模缩减但始终运行的完整副本；多站点主动/主动从多个区域提供服务，以最高的成本实现接近零的 RTO。*为什么其他选项不对：* A——备份和恢复的定义正是不预先运行资源；B——备份和恢复的 RTO 最高（最差）；D——pilot light 是预置但关闭的，不是承担流量的全容量副本。

**27. 答案：B** — 当 30 秒的可见性超时在处理中途失效时，消息会重新出现并被另一个消费者再次处理；应将可见性超时设置得超过最大处理时间（最佳实践如 6 倍）。*为什么其他选项不对：* A——FIFO 与标准队列的区别不是原因；C——长轮询影响空接收效率，与重复无关；D——保留期决定消息保存多久，与重复投递无关。

**28. 答案：A** — 带 maxReceiveCount 的重驱策略会将反复失败的（"毒丸"）消息移到死信队列以供离线分析，终止无限重试循环。*为什么其他选项不对：* B——更短的可见性超时只会让循环转得更快；C——FIFO 不会丢弃格式错误的消息；D——1 分钟的保留期也会使有效消息过期。

**29. 答案：B** — FIFO 队列在每个 MessageGroupId 内保证恰好一次处理和严格顺序；用账户 ID 作为组 ID 实现按账户排序和跨账户并行（高吞吐 FIFO 模式还能进一步扩展）。*为什么其他选项不对：* A——标准队列无法保证顺序或恰好一次；C——SNS 对这种模式不提供排序或恰好一次处理的保证；D——单一组 ID 会把所有处理串行化，摧毁吞吐量。

**30. 答案：B** — SNS 到 SQS 的扇出将每个事件传递到每个队列，每个消费者都获得持久缓冲和独立的处理节奏。*为什么其他选项不对：* A——一个队列上的三个消费者会分摊消息；每条消息只到达一个消费者；C——顺序调用不是带缓冲的独立并行处理；D——电子邮件订阅是发给人看的，不是持久的应用程序缓冲。

**31. 答案：B** — 预留并发为关键函数划出专用并发（给秒杀函数设置上限可限制其影响范围），防止单个函数耗尽共享的账户池。*为什么其他选项不对：* A——更长的超时会更久地占用并发槽位，使限流恶化；C——预置并发预热执行环境，但不会提高账户级并发配额；D——内存大小不影响并发限制。

**32. 答案：B** — Standard 工作流可运行长达一年，waitForTaskToken 回调模式使执行在零计算成本下暂停，直到 SendTaskSuccess/SendTaskFailure 返回令牌。*为什么其他选项不对：* A——Express 工作流最长 5 分钟；C——Lambda 最多运行 15 分钟，休眠还浪费钱；D——EventBridge 计划可以触发事件，但无法暂停并恢复工作流状态。

**33. 答案：A** — Express 工作流专为极高速率、短时长、至少一次的执行而构建且成本更低；Standard 工作流为对账作业提供恰好一次语义、最长一年的运行时间和完整的执行历史。*为什么其他选项不对：* B——Standard 无法经济地承受每秒 90,000 次启动；C——Express 最长 5 分钟且为至少一次，无法满足 12 小时恰好一次的作业；D——颠倒的分配两个工作负载都不满足。

**34. 答案：B** — 故障转移路由在主记录健康检查通过时将所有流量发送到主端点，当其失败时自动以次要记录应答。*为什么其他选项不对：* A——50/50 加权会始终将一半流量发送到被动副本；C——基于延迟的路由按性能分流，与主动/被动意图不符；D——地理位置路由按用户位置路由，与基于端点健康的故障转移无关。

**35. 答案：B** — 添加 ELB 健康检查类型后，ASG 会将 ALB 目标健康检查失败视为不健康，使应用崩溃的实例即使通过 EC2 状态检查也会被终止并替换。*为什么其他选项不对：* A——详细监控只改变指标粒度；C——宽限期会推迟健康评估，与需求相反；D——负载均衡器类型不是问题所在。

**36. 答案：B** — Network Load Balancer 工作在第 4 层（TCP/UDP），以超低延迟处理每秒数百万请求，并支持每个 AZ 一个静态（或弹性）IP。*为什么其他选项不对：* A——ALB 是第 7 层（HTTP/HTTPS），原生不提供静态 IP；C——Gateway Load Balancer 用于部署内联虚拟设备；D——Classic Load Balancer 已属遗留，两个要求都不满足。

**37. 答案：B、C** — CRR 要求源桶和目标桶都启用版本控制，而 EFS Standard 存储类是区域级（多 AZ）文件系统，可跨 AZ 并发挂载。*为什么其他选项不对：* A——CRR 只复制配置后的新对象，除非对已有对象运行 S3 Batch Replication；D——EFS 支持数千个并发 NFS 客户端，不同于单点附加的 EBS；E——版本控制是复制的前提条件，但其本身不复制任何内容。

### 第三部分 — 问题 38–53

**38. 答案：B** — io2 Block Express 提供高达 256,000 IOPS、亚毫秒级延迟和 99.999% 的持久性，满足全部三个要求。*为什么其他选项不对：* A——gp3 现在可以达到该 IOPS 数值（其上限在 2025 年末提升到了 80,000），但它不满足另外两个要求：持久性为 99.8–99.9%（题目要求 99.999%），延迟为个位数毫秒级，无法保证亚毫秒；B 是唯一同时满足三项要求的类型；C——st1 基于 HDD，不适合 IOPS 密集型数据库；D——gp2 最高 16,000 IOPS，且突发不是持续保证。

**39. 答案：C** — FSx for Lustre 专为 HPC 而生，具备亚毫秒级延迟、每秒数百 GB 的吞吐量和原生 S3 集成（延迟加载与导出）。*为什么其他选项不对：* A——EFS 无法匹配 Lustre 的 HPC 吞吐/延迟特性；B——FSx for Windows 面向 SMB/Windows 工作负载，不适合 Linux HPC；D——Mountpoint for S3 不提供共享的 POSIX 文件系统语义和所需的延迟。

**40. 答案：B** — FSx for Windows File Server 原生支持 SMB、Active Directory 集成和 NTFS ACL，Multi-AZ 模式覆盖了双 AZ 要求。*为什么其他选项不对：* A——EFS 是 NFS/POSIX，无法保留 NTFS 权限；C——S3 是对象存储，不是 SMB 文件共享；D——Lustre 是 Linux HPC 文件系统，不支持 SMB/AD。

**41. 答案：D、E** — Transfer Acceleration 将上传经由 AWS 边缘/骨干网络路由以加速长距离传输，分段上传使传输并行化并允许失败的分段单独重试，而无需重新上传整个 40 GB 文件。*为什么其他选项不对：* A——One Zone-IA 改变的是冗余性，不是上传性能；B——无法在 S3 前面放置 ALB 来处理上传；C——CRR 在上传后才复制，对摄取无济于事。

**42. 答案：B** — 实例存储 NVMe SSD 物理直连主机，为可重新生成的临时数据提供最低延迟。*为什么其他选项不对：* A 和 D——EBS 经过网络，增加延迟；C——EFS 是网络文件系统，延迟比两者都高。

**43. 答案：B** — 总体利用率低却在热分区上出现限流，是经典的低基数分区键问题；高基数键（如 game_id#player_id）能让流量均匀分布。*为什么其他选项不对：* A——容量模式的改变无法解决热分区；C——LSI 共享相同的分区键和相同的热分区；D——Streams 捕获变更，不会重新分布写入。

**44. 答案：B** — DAX 是与 DynamoDB API 兼容、对应用透明的内存缓存，以最少的代码更改提供微秒级读取。*为什么其他选项不对：* A——ElastiCache 需要重写应用程序来管理缓存；C——GSI 不缓存热点条目，也无法提供微秒级延迟；D——Global Tables 解决多区域访问问题，不是单条目读取延迟。

**45. 答案：B** — GSI 可以随时添加到现有表上，支持新的分区/排序键组合，并拥有与基表隔离的独立预置吞吐量。*为什么其他选项不对：* A——LSI 只能在创建表时创建，共享表的分区键和吞吐量；C——重建表既有破坏性又没必要；D——Streams 用于变更捕获，不是临时查询。

**46. 答案：B** — DynamoDB TTL 在后台自动删除过期条目，无额外成本。*为什么其他选项不对：* A——计划扫描会消耗读/写容量并产生费用；C——生命周期策略是 S3/EFS 的概念，不是 DynamoDB 的；D——Streams 在下游过滤事件，但不会从表中删除条目。

**47. 答案：B** — RDS Proxy 对连接进行池化和复用，让数千个 Lambda 调用共享一小批数据库连接，只需更改连接字符串。*为什么其他选项不对：* A——扩容成本高且只是推迟了上限；C——数据库迁移是重大的应用程序变更；D——将 Lambda 限制到 10 会扼杀吞吐量，而不是解决连接管理问题。

**48. 答案：A** — Aurora 副本（最多 15 个）位于读取端点之后并配合副本自动扩展，以最少的运维工作分担读取流量。*为什么其他选项不对：* B——Aurora 不使用被动备用模型；经典 RDS 意义上的备用实例不承担流量；C——分片对一个读取扩展问题来说运维开销过高；D——Backtrack 是将数据库回溯到过去的时间点，不承担读取。

**49. 答案：B** — Global Accelerator 提供两个静态 anycast IP，支持 UDP，可作为多个区域中 NLB 的前端，并通过 AWS 骨干网在数秒内完成故障转移。*为什么其他选项不对：* A——CloudFront 服务于 HTTP/HTTPS 内容，不支持任意 UDP，也没有面向客户端的静态 IP；C——Route 53 延迟路由的故障转移依赖 DNS TTL 且不提供静态 IP；D——ALB 是区域性的且仅支持 HTTP。

**50. 答案：B** — 地理位置路由根据用户所在国家应答 DNS 查询，确定性地强制执行德国→eu-central-1、法国→eu-west-3，满足授权合规。*为什么其他选项不对：* A——延迟路由选择最快的端点，可能违反授权规则；C——地理近邻偏置按距离调整边界，但不保证严格的国家映射；D——加权路由按权重随机分配，忽略位置。

**51. 答案：C** — 集群置放群组将实例紧密放置在一个 AZ 内，提供最低延迟和最高每秒数据包性能，是紧耦合 MPI 工作负载的理想选择。*为什么其他选项不对：* A——分散群组将实例分散到不同硬件上，增加延迟，且每个 AZ 上限 7 个；B——分区群组为分布式数据系统隔离故障域，不是为了低延迟 MPI；D——不同子网对实例的物理就近放置毫无帮助。

**52. 答案：B** — Amazon Data Firehose 完全托管，无需编写消费者或管理分片，自带记录缓冲，并能在投递到 S3 之前将 JSON 转换为 Parquet。*为什么其他选项不对：* A——Kinesis Data Streams 需要编写/管理消费者；C——SQS 加 EC2 轮询器是需要自建自运维的定制基础设施；D——MSK 需要管理 Kafka 集群和连接器。

**53. 答案：B** — Glue 爬虫将模式推断到 Data Catalog，Athena 直接对 S3 文件运行无服务器 SQL。*为什么其他选项不对：* A——Redshift 需要预置集群并加载数据；C——EMR 意味着管理一个长期运行的集群；D——RDS 需要把数据加载到数据库服务器中。

### 第四部分 — 问题 54–65

**54. 答案：C** — 带检查点、可重启的批量作业是理想的 Spot 工作负载，跨实例类型/AZ 多样化的 Spot Fleet 在最高约 90% 的节省下将中断影响降到最低。*为什么其他选项不对：* A——按需放弃了折扣却没有任何好处；B 和 D——承诺方案的折扣低于 Spot，并且为一个本就容许中断的作业锁定了支出。

**55. 答案：C** — Compute Savings Plans 自动适用于 EC2（任何系列/区域）、Fargate 和 Lambda，契合现代化路径。*为什么其他选项不对：* A——EC2 Instance Savings Plans 锁定在某个区域的实例系列，且不包含 Fargate/Lambda；B 和 D——预留实例只覆盖 EC2，不适用于 Fargate 或 Lambda。

**56. 答案：B** — 只有 EC2 Standard 预留实例可以在 Reserved Instance Marketplace 上挂牌出售；RDS（及其他服务）的 RI 无法转售。*为什么其他选项不对：* A 和 C——RDS RI 不符合 Marketplace 出售资格；D——EC2 Standard RI 事实上是可以在 Marketplace 上出售的。

**57. 答案：B** — AWS 在回收实例前两分钟发出 Spot 中断通知，留出排空和写检查点的时间。*为什么其他选项不对：* A——确实会提供警告；C 和 D——15 分钟和 24 小时都不是 Spot 中断窗口（再平衡建议可能更早到达，但不是有保证的固定窗口）。

**58. 答案：B** — Glacier Flexible Retrieval 提供低廉的归档存储成本，Expedited 检索可在 1–5 分钟内返回数据（约 $0.03/GB），满足 5 分钟的要求。*为什么其他选项不对：* A——Deep Archive 最快的检索约需 12 小时；C——Bulk 检索需要 5–12 小时；D——Standard-IA 可即时检索，但对于 7 年极少访问的存储成本高得多。

**59. 答案：B** — One Zone-IA 比 Standard-IA 便宜约 20%，对于可重新生成的缩略图，单 AZ 持久性的取舍是可以接受的。*为什么其他选项不对：* A——Standard-IA 为数据并不需要的冗余多花钱；C——Intelligent-Tiering 增加监控费用，且对已知不频繁访问的数据并非成本最低；D——Glacier Instant Retrieval 有 90 天最短期限，其检索成本结构也不适合这种模式。

**60. 答案：A、C** — Intelligent-Tiering 收取少量按对象计的监控/自动化费用，且小于 128 KB 的对象虽被存储但不被监控或分层（按 Frequent Access 费率计费）。*为什么其他选项不对：* B——Intelligent-Tiering 在其自动层之间没有检索费用；D——它从不进行跨区域复制；E——该存储类对每个对象没有 90 天最短期限。

**61. 答案：B** — 未完成的分段上传部分按存储计费但作为对象不可见；带 AbortIncompleteMultipartUpload 的生命周期规则会自动删除它们。*为什么其他选项不对：* A——版本控制会增加存储，而不是清理分段；C——更改存储类不会清除孤立的分段；D——Transfer Acceleration 加速传输，但无法清理已经被遗弃的上传。

**62. 答案：B** — gp3 将 IOPS/吞吐量与容量解耦，且每 GB 成本比 gp2 低约 20%，因此可以在保留所需 IOPS 的同时正确调整容量；迁移是一次在线的 ModifyVolume 操作。*为什么其他选项不对：* A——io2 更贵，不是更便宜；C——st1 无法提供所需的 IOPS；D——删除卷会摧毁线上数据。

**63. 答案：B** — 用于 S3 的网关 VPC 终端节点是免费的，并能消除同区域 S3 流量的 NAT gateway 数据处理费用。*为什么其他选项不对：* A——NAT 实例仍会产生 EC2 和运维成本；C——接口终端节点按小时和按 GB 计费，比免费的网关终端节点贵；D——公有子网增加公有 IPv4 费用并削弱安全性。

**64. 答案：B、E** — AWS 对每个使用中的公有 IPv4 地址收费，因此移除不需要的地址可削减成本，而 AWS Budgets 提供针对预测/实际支出的主动阈值警报。*为什么其他选项不对：* A——弹性 IP 即使在附加期间也按公有 IPv4 费用计费；C——Compute Optimizer 提供规格优化建议，但无法阻止或告警支出阈值；D——Shield Advanced 是 DDoS 服务，只会增加成本。

**65. 答案：A** — Aurora Serverless v2 支持缩放到 0 ACU（自动暂停，2024 年末起可用），并在有连接时自动恢复，在闲置期间消除计算成本且无需手动操作。值得了解的细节：自动暂停要求较新的引擎版本（Aurora PostgreSQL 13.15+/14.12+/15.7+/16.3+，Aurora MySQL 3.08+）；暂停后的首次连接需要约 15 秒恢复（暂停超过 24 小时则更长）；计算暂停期间存储仍持续计费；任何保持连接打开的东西——RDS Proxy、一个 keep-alive 健康检查——都会彻底阻止暂停。*为什么其他选项不对：* B——已停止的预置集群不会在开发人员连接时自动唤醒（且 7 天后会自动重启）；C——无头全球数据库次要集群解决的是 DR，不是闲置成本；D——缩减读取实例后写入实例仍在运行并计费。
