# 第5章：存在云端的文件柜

Leo 意识到 Nimbus 正在将上传的菜单照片直接存储在 EC2 实例上。顾客上传的每一张照片——酥脆的玉米饼、烤三文鱼拼盘、摆盘精美的沙拉碗——都放在单个虚拟机上。

如果那台机器被重启、调整大小或替换，会怎样？

消失不见了。

"顾客迄今为止上传了多少张照片？" Maya 问。

Leo 打开了控制台。"大约八百张。"

"如果我们重启服务器，那八百张照片会怎样？"

又是 Leo 那种意味深长的停顿。

这一章是关于文件在云端真正应该住在哪里的。

**把文件"存在服务器上"的问题**

当你将文件直接存储在 EC2 实例上——放在其文件系统内——你就把这些文件绑定到了那台特定机器的生命周期上。

这产生了几个问题：

**本质上是临时的。** EC2 实例可以被停止、终止、替换。它们的本地磁盘不是为永久使用而设计的。它只是临时的暂存空间。

**单点故障。** 如果实例失败，文件也随之消失。没有冗余。没有备份。一个倒霉的早上，八百张菜单照片就消失了。

**无法跨实例共享。** 当你添加第二台服务器时（第7章你会这样做），它看不到存储在第一台服务器磁盘上的文件。两台服务器是隔离的。上传照片的用户可能看得到；访问不同服务器的另一个用户可能看不到。

**没有扩展能力。** EC2 磁盘空间是有限的。如果你把它填满，你要么停止接受上传，要么在压力下紧急扩展存储。

有一个更好的模型。AWS 在 2006 年就建立了它，它至今仍是世界上使用最广泛的云服务之一。

**Amazon S3：存在线上的硬盘**

**Amazon S3**——简单存储服务——是 AWS 的对象存储服务。

把它想象成一个存在互联网上的硬盘。一个无限的硬盘。一个自动在至少三个可用区备份的硬盘，所以失去任何单一数据中心都不会丢失你的文件。

S3 中的关键概念是**对象**。

对象就是任何文件：照片、视频、PDF、CSV、备份、日志文件。S3 不关心类型或结构。它存储字节，当你需要时返回给你。

对象存放在**桶**里。桶就像一个顶级文件夹——S3 中一个存储你的对象的命名容器。每个桶都有一个全局唯一名称（所有 AWS 账户中没有两个桶可以共用一个名称），并存在于特定区域中。

**S3 的工作方式**

这个模型很简单，而这种简单性就是重点所在。

你**上传**一个对象到桶。S3 给它一个**键**——本质上是一个路径名，比如 `menus/restaurant-001/photo-arepa.jpg`。那个键在桶内唯一标识该对象。

你使用桶名和键**下载**（或检索）对象。

你也可以让对象公开访问——意味着任何有 URL 的人都可以下载它。这是大多数网站提供图片的方式：将图片存储在 S3 中，将其公开，将 URL 嵌入你的 HTML 中。

或者你保持对象私密——只有经过认证的请求才能访问。这是客户数据、备份和任何敏感内容的正确模型。

S3 不是文件系统。没有真正的文件夹。键名中的 `/` 只是一个惯例——S3 将整个键视为一个平面字符串。但它看起来像文件夹，大多数工具也将其呈现为文件夹，所以在实践中不用担心这个区别。

**S3 与普通硬盘的不同之处**

三件事让 S3 与 EC2 实例上的文件存储根本不同：

**持久性。** AWS 将 S3 设计为 99.999999999%（十一个九）的持久性。这意味着如果你存储了一千万个对象，你可能每一万年才会因硬件故障丢失一个对象。他们通过自动在至少三个可用区存储每个对象的多个副本来实现这一点。

**可用性。** S3 被设计为即使在单个组件失败时也可以访问。你不是在连接到一台服务器——你在连接到一个绕开故障路由的分布式系统。

**规模。** S3 可以存储无限量的数据。单个桶可以存储数万亿个对象。亚马逊自己使用 S3 以难以理解的规模存储数据。

**版本控制：撤销按钮**

这是 Maya 在探索 S3 控制台时发现的东西。

S3 支持**版本控制**。当你在桶上启用版本控制时，S3 保留每个对象的每个版本——包括先前版本和已删除的版本。

这是你文件的撤销按钮。

上传了一张新菜单照片意外覆盖了旧的？旧版本仍然在那里。错误地删除了文件？它可以恢复。被勒索软件攻击，所有文件都被覆盖成加密垃圾？有版本控制，你可以从攻击前恢复。

"保留所有这些版本要多少钱？" Tom 问。

你为每个版本的存储付费。如果你有很多大文件的多个版本，这会累积起来。AWS 有**生命周期策略**，可以在一定时间后自动删除旧版本——我们在第23章深入介绍成本优化时会介绍这些。

**访问控制：公开与私密**

默认情况下，S3 中的一切都是私密的。只有你的 AWS 账户可以访问它。

你可以将单个对象设为公开——这就是你向网站访客提供菜单图片的方式。或者你可以保持所有内容私密，并生成**预签名 URL**：有时效的链接，让某人可以下载特定对象而不需要 AWS 凭证。完美适合让顾客在24小时内下载他们的发票。

Priya 对此有非常强烈的意见。

"永远不要让一个桶完全公开，除非你有意识地决定让其中的每个对象对整个互联网开放，" 她说。"最常见的 S3 安全错误是意外暴露一个包含敏感数据的桶。"

AWS 现在有一个"阻止公开访问"设置，你可以在账户级别应用，强制所有桶保持私密，除非你为每个桶明确覆盖它。

启用它。始终如此。

**S3 存储类：并非所有数据都相等**

并非所有数据的访问频率都相同。

你最受欢迎的菜单照片每秒被获取数十次。你三年前的日志可能一年才被访问一次，如果有的话。S3 认识到这一点，并提供具有不同性能和成本权衡的不同**存储类**。

| 存储类 | 使用场景 | 检索时间 | 费用 |
|---|---|---|---|
| S3 标准 | 频繁访问的数据 | 即时 | 每 GB 较高 |
| S3 标准-IA | 不频繁访问，但仍需快速检索 | 即时 | 每 GB 较低，有检索费 |
| S3 Glacier 即时 | 偶尔访问的归档 | 即时 | 低得多 |
| S3 Glacier 灵活 | 很少访问的归档 | 分钟到小时 | 非常低 |
| S3 Glacier 深度归档 | 合规归档，几乎从不访问 | 最多12小时 | 最低 |

我们在第23章深入介绍这些。现在：概念是你可以根据对象的年龄和访问模式在存储类之间自动移动对象，在你很少触碰的数据上节省大量费用。

## 优势与局限性

**S3 出色的原因**：

- 十一个九的持久性。你的数据在 S3 中比几乎任何其他系统都更安全。
- 无限扩展。你从不需要配置存储——它只是增长。
- 对它提供的服务来说极其便宜（每 GB 每月不到一分钱）。
- 与几乎所有其他 AWS 服务原生集成。
- 支持静态网站托管——你可以直接从 S3 提供完整的静态网站，不需要服务器。

**S3 不是正确选择的场景**：

- S3 不是文件系统。如果你的应用程序需要挂载一个驱动器并像使用本地磁盘一样使用它（读取、写入、就地修改文件），S3 是错误的工具。使用 EFS（弹性文件系统，第6章）或 EBS 代替。
- S3 的延迟明显高于本地磁盘。对于需要快速、随机访问 I/O 的数据库或应用程序，块存储（EBS，第6章）是合适的。
- 大量数据传入 S3 是免费的。大量数据*传出*则要收费。这是一个常见的账单惊喜——我们在第30章解决这个问题。

## 摘要

- **Amazon S3** 是对象存储——一个将文件（称为对象）存储在命名容器（称为桶）中的地方。
- S3 通过自动将每个对象的副本存储在至少三个可用区，设计为十一个九的持久性。
- 存储在 EC2 实例上的文件与该实例的生命周期绑定。重要文件属于 S3，而不是服务器。
- **版本控制**保留对象的先前版本——你的撤销按钮。
- 默认情况下，S3 是私密的。在账户级别启用"阻止公开访问"。
- S3 有多个**存储类**，适用于不同的访问模式和成本。不频繁访问类别更便宜，但收取检索费。

## 考试技巧

*SAA-C03 领域3——任务3.1（高性能存储解决方案）*

- **S3 是对象存储，不是块存储。** 当考试场景需要一个多个服务器可以挂载的文件系统时，那是 EFS。当它需要单个 EC2 实例的磁盘时，那是 EBS。当它需要存储文件、备份、图片或通过 HTTP 访问的数据时——那是 S3。
- **十一个九的持久性**意味着 S3 自动在多个 AZ 复制数据。你不需要配置这个——这是默认的。
- **S3 是区域性的**，但可以全球访问。桶存在于特定区域，但你可以从任何地方访问它们。
- **预签名 URL** 允许对私有对象进行有时效的访问。常见模式：你的应用程序生成一个有效期15分钟的预签名 URL，将其给用户，用户直接从 S3 下载文件。
- **S3 标准-IA** 有最低存储时长收费（30天）。不要将其用于你会很快删除的数据。考试测试你是否知道存储类之间的权衡。
- **存储类决策树**：*频繁访问* → S3 标准；*不频繁访问但需要快速检索* → S3 标准-IA；*偶尔访问的归档* → S3 Glacier 即时检索；*很少访问的归档* → S3 Glacier 灵活检索；*合规归档，几乎不访问* → S3 Glacier 深度归档。当场景提到"成本优化"和"不频繁访问"时，标准-IA 几乎总是答案。当提到"合规"或"七年保留"时，想到 Glacier 深度归档。

## 练习

**练习 1——回忆**

用你自己的话：什么是 S3 对象？什么是 S3 桶？为什么将文件存储在 S3 中比存储在 EC2 实例的本地磁盘上更好？

*（提示：想想如果实例被终止，EC2 实例上的文件会怎样。S3 有什么不同的做法？）*

**练习 2——考试练习**

*场景*：一家媒体公司制作纪录片视频。他们需要存储原始 4K 素材（制作期间频繁访问）、编辑完成的最终剪辑（每月一次用于发行）和归档母版（无限期保存，但每年最多访问一次用于合规目的）。他们希望在满足每个层级访问要求的同时最小化存储成本。

哪种存储策略*最能*满足他们的需求？

A) 将所有内容存储在 S3 标准中，以获得一致的性能和简单性  
B) 将原始素材存储在 S3 标准中，最终剪辑存储在 S3 标准-IA 中，归档存储在 S3 Glacier 深度归档中  
C) 将所有内容存储在 EC2 实例存储中以获得最快访问速度  
D) 将所有内容存储在 S3 Glacier 深度归档中以最小化成本

**提示 1**：不同文件有不同的访问模式。S3 为不同的访问频率提供不同的存储类。哪个类与"频繁访问"匹配？

**提示 2**："每年最多一次"访问的归档不需要即时检索。哪个存储类是为最低成本的长期归档设计的？

**提示 3**：将每个层级的访问频率与适当的存储类匹配。频繁访问 = 标准。每月 = 标准-IA。每年一次 = Glacier 深度归档。

**答案**：B

**解析**：这个策略正确地将每个数据层级与适当的 S3 存储类匹配。频繁访问的原始素材留在标准中，以便立即访问，没有检索费。每月访问的最终剪辑转到标准-IA（较低的存储成本，可接受的检索费）。每年访问一次的归档转到 Glacier 深度归档，以获得最低可能的存储成本。

**为什么不是 A？** 将所有内容存储在标准中很简单但很昂贵。你为很少访问的归档内容付高额费用。

**为什么不是 C？** EC2 实例存储是临时的，不适合长期媒体存储。如果实例被终止，所有内容都会丢失。

**为什么不是 D？** Glacier 深度归档的检索时间最多需要12小时。将频繁访问的制作素材存储在那里会使制作工作无法进行。
