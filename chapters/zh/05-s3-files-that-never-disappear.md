# 第5章：存在云端的文件柜

早上九点，Leo 在清理 EC2 实例时发现了那个文件夹。

办公室很安静。Maya 还没到。咖啡还在煮。窗外，早班通勤的人流陆陆续续地走过。Leo 戴着耳机翻看目录，然后他停住了。

八百个文件。全是菜单照片。全都放在一台没有任何备份的机器上。

自从那次十二分钟的停机之后，运行 Nimbus 应用的 EC2 实例升级过一次，但照片存储从来没有挪过窝。每一份酥脆的玉米饼、每一盘烤三文鱼、每一碗摆盘精美的沙拉——都放在一台他们已经证明过会毫无预警宕机的单一虚拟机上。

而如果那台机器哪天被重启、调整规格或者替换掉呢？

消失不见。

"顾客迄今为止上传了多少张照片？" Maya 到了之后问。

Leo 转过身。"大约八百张。"

"如果我们重启服务器，那八百张照片会怎样？"

又是 Leo 那种意味深长的停顿。

这一章讲的是：在云端，文件究竟应该住在哪里。

**把文件"存在服务器上"的问题**

当你把文件直接存储在 EC2 实例上——放在它的文件系统里——你就把这些文件绑定到了那台特定机器的生命周期上。

这会造成几个问题：

**本质上是临时的。** EC2 实例可以被停止、终止、替换。它们的本地磁盘不是为永久保存而设计的。它只是临时的暂存空间。

**单点故障。** 如果实例发生故障，文件也随之消失。没有冗余。没有备份。一个倒霉的早晨，八百张菜单照片就没了。

**无法跨实例共享。** 当你添加第二台服务器时（你会的，在第7章），它看不到存储在第一台服务器磁盘上的文件。两台服务器是隔离的。上传照片的用户可能看得到照片；命中另一台服务器的另一个用户可能看不到。

**没有扩展能力。** EC2 磁盘空间是有限的。如果你把它填满，你要么停止接受上传，要么在压力下手忙脚乱地扩展存储。

Leo 之前没有考虑过多台服务器的情况会发生什么。他随口跟 Priya 提了一句。

"等等——如果有两台服务器，照片的问题会怎么样？" Priya 问。

"什么意思？"

"如果我们在负载均衡器后面有服务器 A 和服务器 B，" Priya 说，"一个顾客上传照片——请求落到了服务器 A，对吧？所以照片保存在服务器 A 的磁盘上。然后顾客的下一个请求落到了服务器 B。服务器 B 上没有那张照片。顾客会看到什么？"

Leo 张了张嘴。又闭上了。

"一张裂开的图片，" 他最后说。

"或者一个 404 错误，" Priya 说。"或者，如果应用程序尝试加载它然后崩溃了，就是一个错误页面。"

她在白板上画出了负载均衡器的方案——增加第二台服务器本来就在路线图上。一旦它落地，每一次照片上传都会变成抛硬币：上传到服务器 A，可能由服务器 B 提供，照片缺失，顾客一头雾水。

"我们大概要调试一个星期才能搞清楚问题出在哪，" Leo 说。

"我们想过开启 Auto Scaling、突然有了三四台服务器之后会发生什么吗？" Priya 问。"我们会一直在丢照片。"

这是一类不会在单元测试中现身的 bug。它只在生产环境中、在负载之下、当真实流量被分散到多台服务器时才会出现。修复方法是彻底停止把文件存储在服务器上。

有一个更好的模型。AWS 在 2006 年就构建了它，它至今仍是世界上使用最广泛的云服务之一。

**存在线上的硬盘**

想象一块住在互联网上的硬盘——它能扩展到容纳你需要的任何容量，并且只按你实际使用的部分收费。你从不需要预先配置它。你从不担心空间用完。今天放进去八百张照片，明年放进去八百万张，对你这一端来说，除了账单上的一行数字，什么都不会改变。

这就是 AWS 提供的东西。他们叫它 **Amazon S3**——Simple Storage Service（简单存储服务）。

S3 是 AWS 的对象存储服务。它不完全像文件系统，也不完全像数据库。它把文件——称为对象——存储在叫做桶的命名容器里。这个模型很简单，而这种简单正是重点所在。

S3 中的关键概念是**对象**。

对象就是任何文件：照片、视频、PDF、CSV、备份、日志文件。S3 不关心类型或结构。它存储字节，当你需要时返回给你。

对象存放在**桶**里。桶就像一个顶级文件夹——S3 中一个存放你的对象的命名容器。每个桶都有一个全局唯一的名称（所有 AWS 账户中不存在两个同名的桶），并存在于一个特定的区域中。

**S3 的工作方式**

你把一个对象**上传**到桶里。S3 给它一个**键**——本质上是一个路径名，比如 `menus/restaurant-001/photo-arepa.jpg`。那个键在桶内唯一标识该对象。

你使用桶名和键**下载**（或检索）对象。

你也可以让对象可以公开访问——意味着任何拥有 URL 的人都可以下载它。这是大多数网站提供图片的方式：把图片存储在 S3 中，将其公开，把 URL 嵌入你的 HTML。

或者你保持对象私密——只有经过身份验证的请求才能访问。这是客户数据、备份和任何敏感内容的正确模型。

S3 不是文件系统。没有真正的文件夹。键名中的 `/` 只是一个惯例——S3 把整个键当作一个扁平的字符串处理。但它看起来像文件夹，大多数工具也把它呈现为文件夹，所以在实践中不用纠结这个区别。

S3 有几个在实践中很重要、但从上面的描述里看不出来的运行特性：

**对象不可变性**：S3 对象不会被就地编辑。如果你更新一个文件，你是用相同的键上传该对象的一个新版本。S3 用新对象替换旧对象（或者在启用版本控制时，两者都保留）。不像数据库可以 `UPDATE` 一行记录，S3 对象是一次写入、多次读取。对于你经常编辑的文本文件和文档，这没问题——上传新版本就行。对于只想更新部分内容的超大文件，S3 的对象模型意味着每次都要重新上传整个文件。

**强读写一致性**：自 2020 年 12 月起，S3 为所有对象提供强一致性——新写入的内容对后续读取立即可见。在 2020 年之前，S3 对某些操作只有最终一致性，这在那些写入对象后立即尝试读取的应用程序中造成过隐蔽的 bug。一致性模型的改进消除了这一类 bug。

**对象 URL**：每个 S3 对象都有一个 URL。对于公开对象，它的形式是：`https://bucket-name.s3.region.amazonaws.com/key/path`。对于私有对象，你可以生成预签名 URL——其中包含身份验证信息，并在配置的时间之后过期。这两种 URL 格式就是应用程序和浏览器实际获取对象的方式——不涉及任何专有协议。

**没有目录可创建**：因为 S3 没有真正的文件夹，所以也不存在创建目录的操作。你只需上传一个键中包含路径前缀的对象。当存在带有该前缀的对象时，"文件夹"会自动出现在控制台中；当带有该前缀的对象全部被删除时，它也会自动消失。

**S3 与普通硬盘的不同之处**

有三件事让 S3 与 EC2 实例上的文件存储有着根本不同：

**持久性。** AWS 把 S3 设计为 99.999999999%（十一个九）的持久性。这意味着如果你存储一千万个对象，你大概每一万年才会因硬件故障丢失一个对象。他们通过自动在至少三个可用区存储每个对象的多个副本来实现这一点。

但持久性防的是硬件故障——防不了你不小心把东西删掉。那是版本控制的事。

**持久性**和**可用性**之间有一个重要区别。持久性关乎你的数据是否还存在。可用性关乎你此刻能否访问它。S3 标准提供 99.999999999% 的持久性和 99.99% 的可用性。持久性的数字高到几乎无法理解；99.99% 的可用性数字是一个*设计目标*——相当于每年大约 52 分钟的不可用时间。合同上的 *SLA* 其实更低（每月 99.9%），而未达到 SLA 换来的是服务积分，不是正常运行时间。在实践中，S3 的可用性比这两个数字都高得多——但值得理解的是：持久性和可用性是两个独立的保证，而设计目标和 SLA 是两个独立的承诺。

**可用性。** S3 被设计为即使单个组件发生故障也仍可访问。你连接的不是一台服务器——你连接的是一个会绕开故障进行路由的分布式系统。

**规模。** S3 能容纳本质上无限量的数据。单个桶可以容纳数万亿个对象。亚马逊自己就在用 S3 以一种难以想象的规模存储数据。世界上最大的 S3 桶存放着 EB 级的数据——数百万 TB。这种规模不需要你来管理；你只管上传对象，S3 处理底下的一切。

**成本。** 截至本书撰写时，S3 标准的价格约为每 GB 每月 0.023 美元。Nimbus 的八百张菜单照片，按平均每张 2MB 计算，是 1.6 GB 的存储——每月大约 0.04 美元。即使到了 80 万张照片，存储费也只是每月 37 美元左右。同样的存储放在 EBS 卷上大约要每月 128 美元，而且有一个固定的容量上限，加东西之前得先扩容。S3 自动增长、按比例收费。EBS 是固定大小、固定费用。

**版本控制：撤销按钮**

这是 Maya 在探索 S3 控制台时发现的东西。

S3 支持**版本控制**。当你在桶上启用版本控制时，S3 保留每个对象的每个版本——包括先前的版本和已删除的版本。

这是你文件的撤销按钮。

Priya 想先测试一下再信任它。她往桶里上传了一张菜单照片，然后用错误的文件上传了一个新版本——一张她花三十秒做出来的全黑图片。

她打开 S3 控制台，点击"显示版本"，两个版本都找到了：坏的版本（当前版本）和原始版本（先前版本）。她把先前版本复制回去作为新的当前版本，完成了恢复。

"管用，" 她说。

"保留所有这些版本要花多少钱？" Tom 问。

每个版本的存储你都要付费。如果你有很多大文件的多个版本，费用会累积起来。AWS 有**生命周期策略**，可以在一定时间后自动删除旧版本——我们在第23章深入讲成本优化时会介绍。

"那我们启用版本控制，但设置一条生命周期规则，三十天后删除旧版本，" Priya 说。"这样我们既有一个恢复窗口，又不用为永久保存每个版本付钱。"

Tom 把数字记了下来。保留三十天版本的存储费用是可以接受的。

**S3 事件通知：会做事的文件**

Leo 在从另一个角度看那些菜单照片。

"现在，" 他说，"餐厅上传照片时，我们存的是全分辨率的原图。有些是四千乘三千像素的。每次顾客在手机上加载菜单页面，我们都在传输一张四兆的图片。"

"这在带宽上要花多少钱？" Tom 问。

Leo 调出了账单上的数据传输数字。答案是"比应该花的多"。

S3 有一个功能叫**事件通知**（Event Notifications）。当一个对象被上传到桶里时，S3 可以自动触发另一个服务——比如 Lambda，我们在第20章介绍的无服务器计算服务。这个触发器可以在没有任何人工干预的情况下，对上传作出响应、运行代码。

Nimbus 的解决方案：每当一张照片上传到原始照片桶，S3 事件通知就触发一个 Lambda 函数。Lambda 函数读取原图，生成一张 400 像素宽的缩略图，并把它保存到已处理照片桶。面向顾客的应用提供缩略图而不是原图。

整个流水线：

1. 餐厅把 4MB 的原图上传到 `nimbus-photos-raw/restaurant-001/arepa.jpg`
2. S3 触发事件通知
3. Lambda 函数读取原图，生成 400x300 的缩略图
4. Lambda 把缩略图保存到 `nimbus-photos-processed/restaurant-001/arepa.jpg`
5. 顾客加载菜单，应用提供 40KB 的缩略图而不是 4MB 的原图

结果：图片带宽减少 99%。页面加载更快。账单上的数据传输那一行变小了。原图保留在原始桶里，所以如果 Nimbus 以后想生成更高分辨率的版本，源素材还在。

"这是自动运行的？" Maya 问。

"任何人每次上传照片都会运行，" Leo 说。"我们完全不用碰它。"

这种模式——由存储事件触发的事件驱动处理——是现代云架构中最常见、最强大的模式之一。我们会在第20章彻底重温它。

**跨区域复制：当一份副本不够时**

周末的时候，Priya 提出了一个合规问题。

"如果 Nimbus 扩展到为欧盟的餐厅提供服务，" 她说，"那些餐厅上传照片——这些照片是存在我们 `us-west-2` 的桶里吗？"

"是的，" Leo 说。

"那 GDPR 对这些数据存在哪里有没有什么说法？"

有。GDPR 的数据传输条款意味着，关于欧盟居民的个人数据可能需要存储在欧盟境内，或存储在数据保护水平充分的司法管辖区。

S3 对此的答案是**跨区域复制**（Cross-Region Replication，CRR）。当你在一个桶上启用 CRR 时，每个新上传的对象都会被自动复制到另一个区域的桶中。你需要配置源桶、目标桶，以及授予 S3 执行复制权限的 IAM 角色。

等欧盟扩张真正发生时，计划是这样的：欧盟餐厅上传的照片将进入一个 `eu-west-1` 的桶，CRR 会把它们复制到 `eu-central-1`（法兰克福）的一个备份桶用于灾难恢复。欧盟数据留在欧盟区域。

"那要花多少钱？" Tom 问。

需要支付跨区域数据传输费和存储费——大致是从源区域到目标区域的每 GB 传输费率，加上复制副本的存储费。Tom 按 Nimbus 预计的欧盟照片量算了一笔账，结论是可以接受。

"那如果有人想入侵复制管道呢？" Priya 问。"执行复制的那个 IAM 角色应该收得很紧——只允许 S3 复制操作，只针对那几个特定的桶。"

她把这条要求写进了扩张计划。

**分段上传与未完成上传的问题**

Tom 在 AWS 账单上发现了一个出乎意料的条目。

"我们在为 S3 的存储付费，" 他说，"但金额比我们照片数量应有的水平要高。"

Leo 去调查了。他在 S3 Storage Lens 报告里发现了一个类别：**未完成的分段上传**。

当 S3 上传超过一定大小的文件时，它使用**分段上传**（multipart upload）：文件被分成多个分段，每个分段单独上传，最后再把这些分段组装成最终对象。这让大文件上传更可靠——如果某个分段失败，只需要重试那个分段，而不是整个文件。

但如果一次分段上传开始之后被放弃了——用户关闭了浏览器、网络断了、应用程序崩溃了——那些不完整的分段会留在 S3 里，持续产生存储费用。它们不会以完成对象的形式出现，但作为存储在被计费。

"多少钱？" Tom 问。

"每月大约 12 美元，" Leo 说。"来自那些从未完成的不完整上传。"

修复方法：一条 S3 **生命周期规则**，在七天后自动删除未完成的分段上传。任何一周内没有完成的上传都视为已放弃，不完整的分段会被清理掉。

Tom 当天下午就加上了那条生命周期规则。每月 12 美元的费用几天之内就消失了。

"那是一年 144 美元，" Tom 看着自己的电子表格说。"白白扔掉。"

"我之前搭过一个用分段上传的负载测试，" Leo 说。"哦。" 停顿了一下。"那大概就是其中的大部分。测试做完之后我忘了清理。"

Tom 还是把它记了下来。

**访问控制：公开与私密**

默认情况下，S3 中的一切都是私密的。只有你的 AWS 账户可以访问它。

你可以把单个对象设为公开——这就是你向网站访客提供菜单图片的方式。或者你可以保持一切私密，并生成**预签名 URL**：有时效的链接，让某人无需 AWS 凭证就能下载特定对象。完美适合让顾客在24小时内下载他们的发票。

Priya 对此有非常强烈的看法。

"那如果有人想通过一个配置错误的桶入侵呢？" 她说。"永远不要把一个桶完全公开，除非你有意识地决定让其中的每一个对象都对整个互联网开放。最常见的 S3 安全错误，就是意外暴露了一个包含敏感数据的桶。"

AWS 现在有一个"阻止公开访问"（Block Public Access）设置，你可以在账户级别应用它，强制所有桶保持私密，除非你为某个桶显式覆盖。

启用它。永远启用。

这背后的历史是：在 AWS 加入账户级"阻止公开访问"之前，最常见的 S3 安全事件就是不小心把桶设成了公开。一个开发者建了个测试用的桶，为了图方便勾选了"公开"，往里加了一些文件——包括几个来自他没多想的其他文件夹的文件——然后就把它忘了。这个桶在那里公开可访问地躺了好几个月。在几起高调的事件中，那个"被遗忘的测试桶"里装着客户数据、内部文档或者凭证。

账户级"阻止公开访问"就是针对这种情况的保险措施。即使开发者不小心把某个桶配置成公开，账户级设置也会覆盖它。任何桶要变成公开之前，你必须先显式地关闭账户级设置——这制造了一个刻意的减速带，防止意外发生。

Nimbus 在账户级别启用了"阻止公开访问"。那么需要公开访问的菜单图片该怎么提供呢？标准模式——Nimbus 之后会在第13章采用——是在桶前面放一个 CDN，比如 CloudFront，配上一个源访问控制（Origin Access Control）策略：CDN 可以从私有的 S3 桶取对象，但没有人能直接访问那个桶。这种模式比公开桶更安全，而且 CDN 的缓存还能降低 S3 的请求费用。

"等等——可是*为什么*要这么做？" Maya 问。"图片反正是公开的，桶公不公开有什么关系？"

"因为公开的桶意味着任何人都可以枚举里面有什么，" Priya 说。"他们可以列出桶里的所有对象。有 CloudFront 在前面，他们只能看到我们在应用程序里暴露的那些 URL。桶本身保持私密。"

Maya 把"枚举"加进了她脑中关于攻击面的认知模型。

**S3 存储类：并非所有数据都生而平等**

并非所有数据的访问频率都相同。

你最受欢迎的菜单照片每秒被获取数十次。你三年前的日志可能一年才被访问一次，如果有人访问的话。S3 认识到这一点，并提供具有不同性能和成本权衡的多种**存储类**。

| 存储类 | 使用场景 | 检索时间 | 费用 |
|-------------------------|-----------------------------------------------|------------------|-----------------------------|
| S3 标准 | 频繁访问的数据 | 即时 | 每 GB 较高 |
| S3 标准-IA | 不频繁访问，但仍需快速检索 | 即时 | 每 GB 较低，有检索费 |
| S3 Glacier 即时检索 | 偶尔访问的归档 | 即时 | 低得多 |
| S3 Glacier 灵活检索 | 很少访问的归档 | 数分钟到数小时 | 非常低 |
| S3 Glacier 深度归档 | 合规归档，几乎从不访问 | 最多12小时 | 最低 |

我们在第23章深入介绍这些。现在只需理解这个概念：你可以根据对象的存在时间和访问模式，让它们在存储类之间自动迁移，在你很少触碰的数据上节省可观的费用。

还有 **S3 智能分层**（Intelligent-Tiering）——一种根据观察到的访问模式，自动在频繁访问层和不频繁访问层之间移动对象的存储类。你为每个对象每月支付一小笔监控费，S3 自动处理分层。当你不确定哪些对象会被频繁访问、哪些不会时，这很有用——服务会学习访问模式并相应地优化。

Tom 的做法更偏手动："我想知道每一块钱花在了哪里。"他选择了显式的生命周期规则而不是智能分层，因为显式规则可预测、可审计。在运营 Nimbus 的 S3 存储六个月之后，他对访问模式有了清晰的认识，于是设置了生命周期规则：对象在 30 天后迁移到标准-IA，在 180 天后迁移到 Glacier 灵活检索。

第一年里生命周期管理带来的存储费用总节省：约 340 美元。算不上改变人生，但是实打实的——而且在任何一个认真使用的 AWS 账户里，这种模式会在几十个桶上重复出现。

"差不多够一趟往返机票了，" Maya 说。

"这是良好的工程实践，" Tom 说。他把它记进了电子表格。

存储类的选择里有一个让许多团队中招的陷阱：**最短存储时长**。S3 标准-IA 有 30 天的最短存储时长——如果你把一个对象存入标准-IA 然后在第 15 天删除它，你仍然要支付 30 天的费用。Glacier 灵活检索的最短期限是 90 天。Glacier 深度归档是 180 天。

对于频繁被删除或生命周期很短的对象，这些最短期限会让 IA 和 Glacier 类别比标准更贵，而不是更便宜。在迁移到更便宜的存储类之前，先确认这些对象确实会在那里存活足够久，让节省的费用超过最短时长带来的罚金。

## 优势与局限性

**S3 出色的原因**：

- 十一个九的持久性。你的数据在 S3 中比在几乎任何其他系统上都更安全。
- 无限扩展。你从不需要预先配置存储——它自己增长。
- 相对于它所提供的能力来说极其便宜（每 GB 每月不到一美分）。
- 与几乎所有其他 AWS 服务原生集成。
- 支持静态网站托管——你可以直接从 S3 提供一个完整的静态网站，无需服务器。
- 事件驱动处理：当对象被创建或删除时，S3 事件通知会自动触发 Lambda、SQS 或 SNS，无需轮询或定时任务就能搭建强大的处理流水线。
- 跨区域复制可用于合规性数据驻留和灾难恢复。

**S3 不是正确选择的场景**：

- S3 不是文件系统。如果你的应用程序需要挂载一个驱动器并像本地磁盘一样使用它（读取、写入、就地修改文件），S3 是错误的工具。请改用 EFS（弹性文件系统，第6章）或 EBS。
- S3 的延迟明显高于本地磁盘。对于需要快速随机访问 I/O 的数据库或应用程序，块存储（EBS，第6章）才合适。
- 数据传*入* S3 不收带宽费——但并非完全免费：每次上传都是一个 PUT 请求，而 S3 按请求收费。上传数百万个小对象，请求费可能比存储费还高。数据传*出*则按 GB 收费。两者都是常见的账单惊喜——我们在第30章处理它们。
- S3 不是数据库。你可以按键存取对象，但不能按内容查询对象、做聚合运算或关系型操作。如果你需要查询所存数据的内容（而不仅仅是按名字取回它），你需要一个数据库，或者像 Athena（第26章）这样能用 SQL 查询 S3 对象的服务。
- 对象版本控制的存储费用会不断累积。每个版本控制对象的每一个先前版本都按存储计费。让旧版本过期的生命周期规则不是可选项——对任何启用了版本控制的桶来说，它们都是成本管理策略的一部分。

**S3 对象是如何加密的**

"那如果有人想入侵呢？" 照片上线那天，Priya 不出所料地问。"这些对象有静态加密吗？"

有——而这值得弄明白，因为 S3 加密是考试中考得最多的主题之一。每个上传到 S3 的对象默认都做了静态加密。问题在于*钥匙在谁手里*：

**SSE-S3（默认）**：S3 用它自己管理的密钥、采用 AES-256 加密每个对象。你什么都不用做、不用配置、不用付费。自 2023 年 1 月起，这在每个桶上都是自动的。对大多数数据来说，这就够了。

**SSE-KMS**：S3 用一把 KMS 密钥加密对象——可以是 AWS 托管的 `aws/s3` 密钥，也可以是你控制的客户托管密钥（第16章深入讲 KMS）。你得到的：CloudTrail 中每一次密钥使用的审计记录、通过密钥策略精确控制谁能解密的能力，以及通过禁用密钥来撤销访问的能力。你付出的：按请求计的 KMS API 费用。在高请求率下，启用 **S3 存储桶密钥**（Bucket Keys）——S3 从你的 KMS 密钥派生出一把短期的桶级密钥，最多可削减 99% 的 KMS API 调用（和费用）。

**SSE-C**：你*随每个请求*提供自己的加密密钥。AWS 只在内存中使用它，从不存储。适用于合规规则要求 AWS 绝不能持有密钥的组织。运营上要求很高——丢了密钥，就丢了数据。

考试套路："加密并需要密钥使用的审计记录"或"控制谁能解密" → SSE-KMS。"公司必须自行管理密钥且 AWS 绝不能存储它们" → SSE-C。"无管理开销的静态加密" → SSE-S3（已经开着了）。

**S3 对象锁定：一次写入，多次读取**

有些数据必须*不可能*被删除——不是靠策略保护，而是结构上就不可变。金融交易记录、审计日志、法律证据。**S3 对象锁定**（Object Lock）让对象在保留期内无法删除、无法修改，连管理员也不行。它要求启用版本控制，并提供两种考试最爱对比的模式：**治理模式**（governance mode，拥有特殊权限的用户仍可绕过锁定）和**合规模式**（compliance mode，在保留期到期之前，没有任何人能缩短保留期或删除对象——连 root 用户也不行）。诸如"WORM 存储"或"SEC Rule 17a-4"之类的监管措辞，是指向合规模式对象锁定的考试触发词。

**S3 传输加速：从远方快速上传**

当用户从地球另一端向一个桶上传大文件时，慢的部分是通往桶所在区域的那段漫长的公网路径。**S3 传输加速**（Transfer Acceleration）给桶提供一个特殊端点，把上传路由到最近的 AWS 边缘站点，然后通过 AWS 的私有骨干网把数据送到桶里。考试触发词："世界各地的用户向一个中心桶上传大文件；上传很慢" → 传输加速（通常与分段上传搭配）。注意方向：传输加速是把数据送*进* S3；CloudFront 是把数据送*出来*。

现在还值得知道一个存储类：**S3 单区-IA**（One Zone-IA）——类似标准-IA，但只存储在单个可用区，便宜约 20%，适用于那些万一该可用区丢失也可以重新生成的不频繁访问数据（缩略图、可再生成的报告）。它是考试里的标准干扰项；第23章会覆盖完整的存储类谱系。


## 摘要

八百张照片放在单个实例上，这就是问题。S3 解决了它——但 S3 不只是一个堆文件的地方。它是一个持久、可扩展、全球可访问的对象存储，拥有自己的访问模型、存储类、生命周期策略和事件系统。理解 S3 擅长什么、刻意不做什么，将塑造团队从此往后的每一个存储决策。

- **Amazon S3** 是对象存储——文件（对象）放在命名容器（桶）中。它把副本存储在至少三个可用区，实现十一个九的持久性。S3 不是文件系统：共享挂载用 EFS，单实例块存储用 EBS。
- 存储在 EC2 实例上的文件与该实例的生命周期绑定，当流量分散到多台服务器时会导致照片丢失的 bug。S3 独立于任何实例，从而解决了这个问题。
- **版本控制**保留对象的先前版本。**生命周期规则**自动完成存储类之间的转换，并清理那些否则会悄悄累积账单的未完成分段上传。
- 默认情况下，S3 是私密的。在账户级别启用"阻止公开访问"。通过带源访问控制的 CloudFront 提供公开对象，而不是把桶直接设为公开。
- S3 存储类让你把成本匹配到访问频率——但在把短命对象转入不频繁访问或 Glacier 层之前，注意最短存储时长费用。

## 考试技巧

*SAA-C03 领域3——任务3.1（高性能存储解决方案）*

- **S3 是对象存储，不是块存储。** 当考试场景需要一个多台服务器都能挂载的文件系统时，那是 EFS。当它需要单台 EC2 实例的磁盘时，那是 EBS。当它需要存储文件、备份、图片或通过 HTTP 访问的数据时——那是 S3。
- **十一个九的持久性**意味着 S3 自动跨多个可用区复制数据。你不需要配置——这是默认的。
- **S3 是区域性的**，但可以全球访问。桶存在于特定区域，但你可以从任何地方访问它们。
- **预签名 URL** 允许对私有对象进行有时效的访问。常见模式：你的应用程序生成一个有效期 15 分钟的预签名 URL，交给用户，用户直接从 S3 下载文件。
- **S3 标准-IA** 有最短存储时长费用（30天）。不要用于你会很快删除的数据。考试测试你是否了解各存储类之间的权衡。
- **存储类决策树**：*频繁访问* → S3 标准；*不频繁访问但需要快速检索* → S3 标准-IA；*偶尔访问的归档* → S3 Glacier 即时检索；*很少访问的归档* → S3 Glacier 灵活检索；*合规归档，几乎从不访问* → S3 Glacier 深度归档。
- **跨区域复制**要求源桶和目标桶都启用版本控制。关于灾难恢复或数据主权的考题经常涉及 CRR。

**练习 1——回忆**

用你自己的话：什么是 S3 对象？什么是 S3 桶？为什么把文件存储在 S3 中比存储在 EC2 实例的本地磁盘上更好？

*（提示：想想如果实例被终止，EC2 实例上的文件会怎样。S3 有什么不同的做法？）*

**练习 2——SAA-C03 场景题**

*场景*：一家媒体公司制作纪录片视频。他们需要存储原始 4K 素材（制作期间频繁访问）、编辑完成的最终剪辑（每月访问一次用于发行）和归档母版（无限期保存，但每年最多访问一次用于合规目的）。他们希望在满足每个层级访问要求的同时，最小化存储成本。

哪种存储策略**最能**满足他们的需求？

A) 将原始素材存储在 S3 标准中，最终剪辑存储在 S3 标准-IA 中，归档存储在 S3 Glacier 深度归档中  
B) 将所有内容存储在 S3 标准中，以获得一致的性能和简单性  
C) 将所有内容存储在 EC2 实例存储中以获得最快访问速度  
D) 将所有内容存储在 S3 Glacier 深度归档中以最小化成本

**提示 1**：不同文件有不同的访问模式。S3 为不同的访问频率提供不同的存储类。哪个类与"频繁访问"匹配？

**提示 2**："每年最多一次"访问的归档不需要即时检索。哪个存储类是为最低成本的长期归档设计的？

**提示 3**：将每个层级的访问频率与适当的存储类匹配。频繁访问 = 标准。每月一次 = 标准-IA。每年一次 = Glacier 深度归档。

**答案**：A

**解析**：这个策略正确地把每个数据层级与适当的 S3 存储类匹配。频繁访问的原始素材留在标准中，可以立即访问且没有检索费。每月访问一次的最终剪辑放入标准-IA（更低的存储成本，可接受的检索费）。每年访问一次的归档放入 Glacier 深度归档，以获得尽可能低的存储成本。

**为什么不是 B？** 把所有内容存在标准里很简单，但很昂贵。

**为什么不是 C？** EC2 实例存储是临时的，不适合长期的媒体存储。如果实例被终止，所有内容都会丢失。

**为什么不是 D？** Glacier 深度归档的检索时间最长可达12小时。把频繁访问的制作素材存在那里，会让制作工作无法进行。
