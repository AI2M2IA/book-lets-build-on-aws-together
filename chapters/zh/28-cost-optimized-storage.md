# 第二十八章：存储账单惊喜

Tom 已经为 EC2 提交了 Savings Plan。账单上的下一行是 S3：每月 $198（在第 23 章的生命周期策略变更后从 $847 降低）。

然后他看到了 EBS：每月 $440。

"这看起来很高，"他说。

Leo 调出了 EBS 卷列表。有 47 个 EBS 卷附加到实例上。然后还有另外 23 个卷没有附加到任何实例。

"这 23 个卷，"Tom 说，"它们是什么？"

Leo 查找了它们。它们都是分离状态的——没有实例在使用它们。大多数是出于调试目的从快照创建的。有些来自已终止但卷没有被删除的实例。

"我们为没有人在读取的存储支付每 GB 每月 $0.10，"Leo 说。

Tom 看了看总数：2.3TB 的未附加卷。

"每月两百三十美元，用于我们不使用的存储，"Tom 说，"这种情况持续了多久？"

Leo 查了创建日期。最旧的卷是 16 个月前的。

"三千六百八十美元，"Tom 静静地说，"我们花了三千六百美元在没有人访问的存储上。"

他删除了未附加的卷。随后的月份，EBS 账单降至 $210。

**存储成本审计**

Tom 的 EBS 发现是一个更广泛模式的症状：存储成本在无形中积累。与计算不同（当 47 台服务器在运行时你会注意到），存储悄悄累积。

想象一下存储单元租赁。为一个单元付费在信用卡账单上很明显。但如果你为一个项目租了第二个，然后为一些旧家具租了第三个，而你从不回去查看里面有什么——费用每月继续出现，悄悄地，早在你忘记你存储的是什么之后很久了。云存储的运作方式相同：字节就在那里，发票就来了，没有人质疑它，直到有人终于打开门，发现里面装满了没有人再需要的东西。

全面的存储成本审计包括：

**S3**：

- 所有桶都有生命周期策略吗？
- S3 中有没有旧的快照（RDS、EBS）？
- 对于访问模式不确定的桶，Intelligent-Tiering 合适吗？
- 是否有版本化对象创建从未访问过的多个副本？

**EBS**：

- 是否有未附加的卷（没有运行实例在使用它们）？
- gp3 卷是否配置正确？（默认 gp3 卷可能有不需要的过剩预置吞吐量/IOPS）
- 是否保留了超过必要时间的快照？

**RDS**：

- 自动备份保留期设置是否合适？（更长 = 更多存储成本）
- 旧实例的手动快照是否仍然存在？
- 数据库迁移后的读副本是否仍在运行？

**EFS**：

- EFS 卷是否在正确的存储类中？（Standard 对比 Infrequent Access）

**S3 版本控制：隐藏的成本**

在第 5 章中，我们提到 S3 版本控制保留对象的每个先前版本。这对安全性很好。如果你没有同时为版本设置生命周期规则，对成本来说就很糟糕。

当桶启用版本控制时，每次你覆盖一个对象，旧版本都会被保留。随着时间推移：

- 第 1 天：图片上传（v1）
- 第 30 天：图片更新（v1 现在是"非当前"版本，v2 是当前）
- 第 60 天：图片再次更新（v1 和 v2 是非当前的，v3 是当前的）
- 第 365 天：v1、v2... v12 都被存储。你在为图片的 12 个副本付费。

修复方法：对非当前版本的生命周期规则。

```
非当前版本在 30 天后过期
失败的分段上传在 7 天后删除
```

Tom 将这些规则应用到所有版本化桶。随后的月份，S3 存储减少了 18%。

**EBS：正确调整大小和 gp3 升级**

EBS 卷定价有两个组成部分：

1. 存储（每 GB 每月）
2. 预置 IOPS 和吞吐量（如果你用的是 io1/io2 或为 gp3 额外性能付费）

**gp3 机遇**：在第 6 章中，我们注意到 gp3 是当前默认设置，比 gp2 更便宜。如果 Nimbus 有在 gp3 可用（2020 年 12 月发布）之前创建的卷，那些可能仍然是 gp2。

Tom 发现了 12 个 gp2 卷，总计 1,200GB。迁移到 gp3 立即节省了这些卷 20% 的费用，没有任何性能下降。

**IOPS 和吞吐量**：gp3 卷默认提供 3,000 IOPS 和 125 MB/s 吞吐量，无需额外费用。如果你的工作负载需要，你可以预置更多。检查预置性能是否实际上在被使用。

Tom 发现两个 gp3 卷有 10,000 个预置 IOPS。他查了 CloudWatch 指标：实际平均 IOPS 为 1,200。他将预置 IOPS 减少到 4,000（实际峰值之上的安全余量）。

每月节省：$68。

**快照生命周期**：EBS 快照是增量的（每个快照只存储自上一个快照以来的变更），但它们会积累。Nimbus 早期的旧快照仍然存在。Tom 保留了 30 天的每日快照并删除了其余的。

**EFS：存储类**

Amazon EFS 有其自己的存储类：

- **EFS Standard**：用于频繁访问的文件。成本较高。
- **EFS Infrequent Access（IA）**：用于 30 天未访问的文件。比 Standard 便宜 92%。
- **EFS Archive**：用于 90 天未访问的文件。比 IA 更便宜。

**EFS Intelligent-Tiering**：根据访问模式自动在存储类之间移动文件。

Tom 在 EFS 卷上启用了 Intelligent-Tiering。六周后，68% 的文件已迁移到 Infrequent Access。每月 EFS 成本从 $89 降至 $31。

**S3 成本分配标签：找出谁在花什么**

随着 Nimbus 的增长，多个团队在 S3 中存储数据。分析团队有自己的桶。工程团队有他们的桶。餐厅数据团队有他们的桶。

账单只显示"S3：$198"。没有按团队的细分。

**成本分配标签**允许你用业务元数据（团队、项目、环境）标记 AWS 资源，然后在 AWS Cost Explorer 中查看按这些标签细分的成本。

Tom 为所有 S3 桶添加了标签：
```
Team: analytics
Environment: production
Project: nimbus-core
```

经过一个带标记的计费周期后，他可以看到："分析团队的数据湖每月 $74。工程备份每月 $43。餐厅数据每月 $81。"

现在他可以与每个团队进行预算对话，而不只是看一个汇总数字。

**AWS Cost Explorer 和 AWS Budgets**

**AWS Cost Explorer**：按服务、区域、标签和使用类型可视化历史和预测成本。了解金钱去向的必备工具。

**AWS Budgets**：当成本超过（或预测超过）阈值时设置警报。你可以按服务、区域、标签或账户制定预算。

Tom 设置了三个预算：

1. 月度总账单：在预算金额的 90% 时发出警报
2. EC2 按需：如果按需支出超过每月 $500 时发出警报（表示 Savings Plan 有缺口）
3. 数据传出：在每月 $200 时发出警报（数据传输成本可能意外急剧上升）

Budgets 向 Slack 频道发送警报。团队在接近限制时就能看到，而不是在月度发票上发现。

**忽视的代价**

Tom 制作了一个电子表格。他计算了 Nimbus 在以下方面的花费：

- 未附加 EBS 卷（16 个月）：$3,680
- 旧 S3 快照（发现并删除）：$890
- 不需要的预置 IOPS：$816
- gp2 到 gp3 迁移节省（如果更早进行，预计节省）：18 个月内 $2,160
- 积累的非当前 S3 版本：$1,340

识别的总浪费：18 个月约 $8,800。

"八千八百美元，"Maya 说。

"来自忽视，"Tom 说，"不是来自做出错误的架构决策。而是来自不清理。"

"系统性的修复是什么？"

"定期审计，"Priya 说，"每月 Cost Explorer 审查。AWS Trusted Advisor 自动标记未附加的卷和空闲资源。自动化清理已知的浪费模式：删除超过 N 天的快照，对未附加的 EBS 卷发出警报，过期旧的 S3 版本。"

"还有，"Tom 补充道，"将成本卫生作为部署过程的一部分。当工程师终止 EC2 实例时，除非他们明确选择退出，否则 EBS 卷会被自动删除。"

## 优势与局限

**成本优化纪律**：

- 定期审查在积累的浪费变得显著之前发现它
- 标记使问责制成为可能——团队看到自己的成本
- 自动警报防止计费意外
- 生命周期策略和正确调整大小通常是一次性设置后就可以忘记的节省

**复杂性所在**：

- 在拥有多个团队的大型账户中识别浪费需要集中工具
- 有些浪费是故意的（保留额外快照"以防万一"）——成本/风险权衡是一种判断
- gp3 迁移需要仔细验证（在某些边缘情况下 IOPS 和吞吐量默认值可能与 gp2 行为不同）
- 成本分配标签需要所有团队的纪律——不一致的标记使数据不完整

## 总结

- **存储成本在无形中积累**——定期审计是必不可少的。
- **未附加的 EBS 卷**是常见的浪费来源。删除它们（或在实例终止时自动删除）。
- **EBS 正确调整大小**：将 gp2 迁移到 gp3（通常节省 20%）。删除过剩的预置 IOPS。
- **S3 版本控制**：为非当前版本启用生命周期规则，避免为无限版本历史付费。
- **EFS Intelligent-Tiering**：根据访问频率自动将文件移动到更便宜的层。
- **成本分配标签**：用团队/项目/环境元数据标记资源，实现成本可见性和问责制。
- **AWS Budgets**：当成本接近阈值时主动发出警报。永远不要对月度账单感到意外。

## 考试技巧

*SAA-C03 领域：设计成本优化架构（领域 4，任务 4.1）*

- **成本分配标签**：在账单控制台中为成本分配启用用户定义标签；然后标记资源。Cost Explorer 按标签显示细分。考试场景："确定哪个部门产生了最多的 S3 成本"→ 成本分配标签。
- **AWS Trusted Advisor**：识别未充分利用的 EC2 实例、未附加的 EBS 卷、空闲负载均衡器和其他浪费。基本检查免费；完整检查需要 Business/Enterprise 支持。
- **EBS 成本组成部分**：存储（每 GB）、预置 IOPS（如果是 io1/io2 或额外 gp3）、吞吐量（如果是额外 gp3）。了解哪些组成部分可以正确调整大小。
- **S3 版本控制成本**：非当前版本的存储和计费与当前版本相同。过期非当前版本的生命周期规则对于版本化桶的成本控制至关重要。
- **AWS Compute Optimizer**：分析 EC2 利用率并推荐正确大小的实例类型。考试信号："通过选择正确的实例类型降低 EC2 成本"→ Compute Optimizer。
- **AWS Cost Anomaly Detection**：使用机器学习检测异常的消费模式。考试信号："自动检测意外的成本增加"→ Cost Anomaly Detection。

**练习 2 — 考试练习**

*场景*：一家公司的 AWS 账单在六个月内从 $5,000 增长到 $9,000/月，但他们没有添加新服务。工程团队怀疑存储成本是问题所在。哪种 AWS 工具组合最能识别和解释成本增长？

A) AWS CloudTrail 审查 API 调用并识别谁创建了新资源  
B) AWS Cost Explorer 进行服务级别成本细分，以及 AWS Trusted Advisor 检测空闲和未附加的资源  
C) Amazon CloudWatch 监控资源利用率并创建成本警报  
D) AWS Config 识别所有资源及其合规状态

**提示 1**："识别成本增长"→ 按服务可视化成本细分。

**提示 2**："空闲和未附加的资源"→ 特定工具主动识别这些。

**提示 3**：CloudTrail 记录 API 调用；Cost Explorer 显示成本趋势。哪个对成本分析更有用？

**答案**：B

**解释**：AWS Cost Explorer 按服务、区域和使用类型显示成本趋势——非常适合识别哪个服务驱动了增长。AWS Trusted Advisor 的成本优化检查识别未附加的 EBS 卷、空闲的 EC2 实例、未充分利用的负载均衡器和其他常见的浪费来源。

**为什么不选 A？** CloudTrail 记录谁创建了资源以及何时创建的，但不直接显示成本趋势或识别浪费。

**为什么不选 C？** CloudWatch 监控资源性能（CPU、内存）——对正确调整大小有用，但不用于识别积累的存储浪费。

**为什么不选 D？** AWS Config 追踪资源配置和合规性，但不是成本分析工具。
