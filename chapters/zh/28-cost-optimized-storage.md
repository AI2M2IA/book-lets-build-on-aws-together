# 第二十八章：存储账单惊喜

那份电子表格如今已经有十六个标签页了。Tom 把它开在第二个窗口里，就像有些人随手放着购物清单一样——一直可见，一直在累积。他为 EC2 加了一行（已完成，Savings Plan 已承诺），然后把光标移到下一行。

存储。

**回顾：EC2 搞定，还剩一项**

第二十七章的计算定价工作敲定了 EC2 策略：一份三年期、$0.45/小时的 Compute Savings Plan，外加用于夜间批处理的 Spot——整个期限内预计节省 $42,500。这项工作完成了，而且完成得很好。但那只是账单上的一行。从六个月的 Athena 成本分析中，Tom 学到了一件事：账单有很多行——而且每一行都值得同样的审视。下一个是 S3：每月 $198，在第二十三章的生命周期策略改动后已经从 $847 降下来了。不过，真正抓住他目光的数字在页面更靠下的位置。EBS：每月 $440。

"这看起来偏高，"他说。

Leo 调出了 EBS 卷列表。有 47 个 EBS 卷附加在实例上。然后还有另外 23 个卷没有附加到任何实例。

"这 23 个卷，"Tom 说，"它们是什么？"

**孤儿卷审计**

Leo 开始一个一个地排查。这不是一项快速的工作——这些卷的命名不统一，标签不一致，有些创建得太久远，已经没人记得当时的来龙去脉了。Tom 拉了把椅子过来旁观。

卷 ebs-021a4c。16 个月前创建。标签："debug-prod-db-snapshot-restore"。大小：200GB。最后一次附加：从未，或者附加历史已被清除。

"那个我记得，"Leo 说，"我们当时遇到一个数据库查询问题，我恢复了一个快照来核对数据。我查完了，问题不在那儿，然后忘了删这个卷。"

卷 ebs-07f38b。11 个月前创建。标签："load-test-temp"。大小：400GB。

Leo 沉默了一会儿。"我想那是我们在种子轮路演之前做的那次负载测试。我们临时开了额外的实例和额外的存储来模拟峰值负载，然后……我觉得我事后一个都没删。"

"我已经部署好了——哦，"他说，"负载测试是临时的。这些卷不是。"

卷 ebs-0ab12c 到 ebs-0ab134。连续八个卷，9 个月前创建。标签："k8s-experiment"。大小：每个 100GB，总共 800GB。

"那是 Kubernetes 评估，"Priya 从 Leo 肩膀上方看过来说，"我们花了三周评估是迁移到 ECS 还是 EKS。EKS 是落选方案。我们拆掉了实验集群，但显然把持久卷留下了。"

Tom 在另一个标签页里做着加法。一个卷一个卷地，数字累积起来：

- 调试恢复卷：4 个卷 × 200GB = 800GB
- 负载测试卷：六个卷，在 200 到 400GB 之间——总计约 1,200GB
- Kubernetes 实验卷：8 个卷 × 100GB = 800GB
- 其他未打标签的：5 个卷 × 各种大小 = 约 700GB

总计：23 个未附加的卷，约 3,500GB。

"这个每月要花多少钱？"Tom 问。答案：gp3 每 GB 每月 $0.08。3,500GB × $0.08 = 每月 $280。

他查了最早的创建日期。十六个月。他掏出了计算器。

"有些卷我们已经付了十六个月的钱，"他说，"有些九个月。所有这些平均下来大概十个月。"23 个卷，平均每个每月 $12，平均 10 个月。那大约是 $2,760。再加上那些更大的卷，算下来浪费总额大约是 $3,200。

"三千二百美元，"Tom 说，"花在没人使用的卷上。"

"而且没人注意到，因为这笔费用分散在几十个明细项里，"Leo 说，"它不是一笔 $3,200 的费用。它是 23 笔每月 $12、$50 或 $80 的费用，每一笔都小到不会触发任何警报。"

Tom 删除了全部 23 个未附加的卷。他和 Leo、Priya 逐一确认每个卷上都没有他们需要的数据——调试卷里是一个早已迁移的数据库的陈旧数据，负载测试数据已经无关紧要，Kubernetes 实验卷是空的。删除花了十五分钟。次月，EBS 账单从 $440 降到了 $160。

"等等——可是*为什么*要这么设计？"Tom 把这个发现讲给 Maya 听时，她问，"为什么终止实例时删除卷不是默认行为？"

"取决于是哪种卷，"Tom 说，"**根**卷默认确实会被删除——它的 `DeleteOnTermination` 是 true。但你附加的任何**额外**数据卷，默认是保留的。背后的假设是你可能还需要上面的数据。这 23 个孤儿全是数据卷——为了一次调试会话或一次负载测试附加上去，然后在实例终止时被遗忘。"

"所以这个默认行为是在保护你，避免数据卷上的数据被意外删除。"

"但你要是不留心，它就让你花钱。从现在起：任何额外的数据卷在实例终止时都要被显式删除——或者在附加时就设好 `DeleteOnTermination`——除非有人写下书面理由说明为什么需要保留。"

"我们有没有想过，要是有人忘了写那个理由会怎样？"Priya 问，"我们可能会删掉重要的东西。"

"这就是取舍，"Tom 说，"现在的取舍是反方向的——我们默认一切都该保留，并在它们其实不该保留时为之付钱。'保留这个卷'要写文档的纪律，比当前'悄悄保留一切'的默认行为风险更小。"

**存储成本审计**

Tom 的 EBS 发现是一个更大模式的症状：存储成本在无形中积累。与计算不同（47 台服务器在跑你是会注意到的），存储是悄无声息地累加的。

把它想成租迷你仓。租一个仓位，在信用卡账单上很显眼。但如果你为某个项目又租了第二个，再为一些旧家具租了第三个，而你从不回去看里面装了什么——费用就每个月继续出现，悄悄地，远在你已经忘了自己究竟存了什么之后。云存储的运作方式相同：字节躺在那里，发票照常到来，没有人质疑它，直到终于有人打开门，发现里面塞满了再也没人需要的东西。

一次彻底的存储成本审计要看：

**S3**：

- 所有桶都有生命周期策略吗？
- S3 中是否躺着旧快照（RDS、EBS）？
- 对于访问模式不确定的桶，Intelligent-Tiering 是否合适？
- 是否有版本化对象产生了从未被访问过的多份副本？
- 是否有未完成的分段上传在悄悄积累？

**EBS**：

- 是否有未附加的卷（没有任何运行中的实例在使用它们）？
- gp3 卷的配置是否合理？（默认 gp3 卷可能配有用不上的多余预置吞吐量/IOPS）
- 是否保留了超过必要时长的快照？

**RDS**：

- 自动备份保留期设置是否合适？（更长 = 更多存储成本）
- 旧实例的手动快照是否还躺在那里？
- 数据库迁移时建的只读副本是否还在运行？

**EFS**：

- EFS 卷是否处在正确的存储类中？（Standard 还是 Infrequent Access）

**S3 版本控制：隐藏的成本**

在第五章里，我们提到 S3 版本控制会保留对象的每一个历史版本。这对安全性极好。但如果你没有同时为这些版本设置生命周期规则，对成本来说就很糟糕。

当桶启用版本控制后，每次你覆盖一个对象，旧版本都会被保留。随着时间推移：

- 第 1 天：图片上传（v1）
- 第 30 天：图片更新（v1 现在是"非当前"版本，v2 是当前版本）
- 第 60 天：图片再次更新（v1 和 v2 是非当前版本，v3 是当前版本）
- 第 365 天：v1、v2……v12 全部都存着。你在为一张图片的 12 份副本付费。

你也许会想，为什么版本控制不自动清理旧版本。这个答案是有意为之——AWS 不希望自动删除你的数据。但后果就是：每个版本都会一直累积，直到你明确告诉 S3 该把它们保留多久。修复方法：针对非当前版本的生命周期规则。

```
Expire noncurrent versions after 30 days
Delete failed multipart uploads after 7 days
```

Tom 把这些规则应用到了所有启用版本控制的桶。次月，S3 存储减少了 18%。

**未完成的分段上传：看不见的积累**

还有一种更隐蔽的 S3 成本，大多数工程师完全没注意到：未完成的分段上传（incomplete multipart uploads）。

S3 上传大文件时，会把它切成多个分段分别上传。这就是分段上传机制——对几百兆以上的文件，它比单次大体积 PUT 更可靠。但如果上传开始之后中途失败——网络中断、客户端崩溃、应用 bug——已经上传的那些分段就留在了 S3 里。它们在你的桶里不会显示为对象。它们不出现在任何列表里。但它们被存储着，而且你按标准 S3 费率为它们付费。

Tom 是通过在 S3 控制台启用 S3 Storage Lens 仪表板、并按"未完成的分段上传"排序发现这一点的。Nimbus 有 340GB 的未完成分段上传数据，无声地躺在四个 AWS 账户的桶里，其中一部分已经超过一年。

"这个每月要花多少钱？"Tom 问。$0.023/GB/月 × 340GB = 每月 $7.82。单独看很小。但它已经累积了一年，没有任何人注意到。

修复方法：给每个桶加一条生命周期规则。

```
AbortIncompleteMultipartUpload:
  DaysAfterInitiation: 7
```

七天之后，任何未完成的分段上传都会被自动清理。这条规则会无限期生效，无需任何后续照看。

"如果这些东西已经在那儿躺了整整一年——算下来我们在失败的上传上花了 $94，"Leo 说。

"在失败的上传上，"Tom 确认道，"连成功的存储都算不上。这就是基础设施浪费的定义。"

**EBS：合理调整规格与 gp3 升级**

EBS 卷的定价有两个组成部分：

1. 存储（每 GB 每月）
2. 预置 IOPS 和吞吐量（如果你用的是 io1/io2，或为 gp3 的额外性能付费）

**gp3 机会**：在第六章里，我们提到 gp3 是当前的默认卷类型，比 gp2 更便宜。如果 Nimbus 有在 gp3 推出之前（它于 2020 年 12 月发布）创建的卷，那些卷可能仍然是 gp2。

迁移很简单：在 AWS 控制台或通过 CLI 把卷类型从 gp2 改成 gp3。不需要停机。转换期间卷始终可用。性能特征相同或更好——gp3 提供 3,000 IOPS 和 125 MB/s 的基准吞吐量，而 gp2 的突发模型对较小的卷可能表现不稳定。

"等等——可是*为什么*要这么设计？"Maya 问，"如果 gp3 更便宜而且至少和 gp2 一样好，AWS 为什么不直接自动把所有人都迁移过去？"

"因为 AWS 不会对客户基础设施做单方面的更改，"Tom 说，"哪怕是有益的更改。这种修改理论上对某些工作负载可能有副作用。必须由客户来发起。这也是为什么在 gp3 发布数年之后，仍有成千上万的团队还在付 gp2 的价格——只因为没人去查过。"

Tom 决定在一个周六早晨做 gp3 迁移——和他做 EC2 定价分析时一样的早晨纪律。安静的时间。没有站会。只有 AWS 控制台和一份计划。

他已经在生产环境里识别出 8 个仍是 gp2 的卷：四台 API 服务器的根卷、两个附加在后台处理器上的卷，以及两个在"新部署默认用 gp3"成为标准做法之前创建的遗留数据卷。加起来总共 960 GB。

迁移过程是对每个卷一次 API 调用：

```bash
aws ec2 modify-volume \
  --volume-id vol-0a1b2c3d4e5f67890 \
  --volume-type gp3 \
  --iops 3000 \
  --throughput 125
```

`--iops 3000` 和 `--throughput 125` 这两个参数与 gp3 的基准默认值一致。对于 gp2，Tom 先查了 CloudWatch 指标：每个卷的平均 IOPS 都在 200 到 800 之间。没有一个需要超过 gp3 免费提供的 3,000 IOPS 基准。吞吐量同样宽裕——远在 125 MB/s 的默认值之内。

"如果某个卷在切换之后需要更多 IOPS 怎么办？"Tom 讲解迁移计划时，Maya 问。

"我们随时可以提高 gp3 卷的预置 IOPS，"Tom 说，"迁移不会锁死任何东西。如果我们以 3,000 IOPS 切到 gp3 之后发现不够用，再次修改卷加上去就行。修改是在线进行的——不停机，不卸载。"

"那 gp2 不能原地修改吗？"

"gp2 可以原地修改成 gp3。你做不到的是从 gp3 退回 gp2——至少不容易，而且也没有理由这么做。"

实际的迁移，从第一条命令到全部 8 个卷完成，用了 73 分钟。AWS 在卷处于挂载和使用状态时完成了修改。整个过程中 API 服务器持续接收流量。CloudWatch 显示转换期间 I/O 延迟没有任何尖峰——对运行中的应用来说，这次切换完全透明。

"这才是'无需停机'真正的样子，"Leo 看着 Tom 记录下来的前后对比指标说，"我原以为'无需停机'指的是'短暂重启'。它的意思是：从应用的视角看，真的什么都没变。"

节省：gp2 是 $0.10/GB/月；gp3 是 $0.08/GB/月。960 GB 上：每月 $96 对比 $76.80。每月节省：$19.20。这个数字本身算不上脱胎换骨，但它代表的纪律才是。从那一刻起创建的任何新卷都默认使用 gp3。Tom 那个早晨写下的组织规则是：不许有 gp2 卷。任何工程师创建 EBS 卷都应使用 gp3，除非有具体的、写成文档的理由。

**IOPS 和吞吐量**：gp3 卷默认配备 3,000 IOPS 和 125 MB/s 吞吐量，不额外收费。如果工作负载需要，可以预置更多。要审查预置的性能是否真的被用上了。

在同一次审计中，Tom 发现两个卷配了 10,000 预置 IOPS——这是他入职之前留下的旧设置，是为一个早已迁移到 Aurora 的数据库配的规格。他查了 CloudWatch 指标：实际平均 IOPS 是 1,200。他把预置 IOPS 降到了 4,000（在实际峰值之上留出安全余量）。

每月节省：$68 的预置 IOPS 费用——这些钱一直在为无人使用的性能余量买单。

**快照生命周期**：EBS 快照是增量的（每个快照只存储自上一个快照以来的变更），但它们会积累。Nimbus 早期的旧快照仍然存在。Tom 保留了 30 天的每日快照，删除了其余的。

**EFS：存储类与 Intelligent-Tiering 的抉择**

Amazon EFS 有自己的一套存储类：

- **EFS Standard**：用于频繁访问的文件。成本较高。
- **EFS Infrequent Access（IA）**：用于 30 天未被访问的文件。比 Standard 便宜 92%。
- **EFS Archive**：用于 90 天未被访问的文件。比 IA 还便宜。

**EFS Intelligent-Tiering**：根据访问模式自动在存储类之间移动文件。

Tom 在 EFS 卷上启用了 Intelligent-Tiering。六周后，68% 的文件已经移到了 Infrequent Access。每月 EFS 成本从 $89 降到了 $31。

但在 Intelligent-Tiering 和手动生命周期规则之间做选择并非小事。Tom 仔细斟酌过。

"等等——可是*为什么*我们要用 Intelligent-Tiering，而不是直接设一条手动生命周期规则？"Maya 问，"如果我们知道超过 30 天的文件没人访问，为什么不直接设好规则一了百了？"

"Intelligent-Tiering 能处理那些会被重新访问的文件，"Tom 说，"如果我设一条 30 天后移到 IA 的生命周期规则，然后有人访问了一个已经在 IA 里待了六个月的文件，它还是留在 IA 里。而用 Intelligent-Tiering，一旦访问恢复，文件会自动移回 Standard。它是双向的。"

"那什么时候反而更应该用生命周期规则？"

"当你确定访问模式是单向的时候。归档日志——写入、变旧、为一次合规审计被访问一次，然后再也不会被碰。对这种模式，一条 90 天后移到 Archive 的生命周期规则比 Intelligent-Tiering 更便宜，因为你不用付监控开销。"

"还有监控费？"

"S3 Intelligent-Tiering 有，这也是为什么我们在 S3 生命周期那一章专门讲过小对象经济学。对 EFS，这个决策主要看访问模式：如果文件可能重新变热，Intelligent-Tiering 更稳妥。如果它们只朝一个方向老化，移到 Archive 的生命周期规则更便宜也更简单。"

**S3 成本分配标签：找出钱是谁花的**

随着 Nimbus 的增长，多个团队都在 S3 里存数据。分析团队有自己的桶。工程团队有他们的桶。餐厅数据团队有他们的桶。

而账单上只显示"S3：$198"。没有按团队的细分。

**成本分配标签（Cost allocation tags）**让你用业务元数据（团队、项目、环境）标记 AWS 资源，然后在 AWS Cost Explorer 中查看按这些标签细分的成本。

Tom 给所有 S3 桶加上了标签：
```
Team: analytics
Environment: production
Project: nimbus-core
```

带着标签跑完一个计费周期后，他可以看到："分析团队的数据湖每月 $74。工程备份每月 $43。餐厅数据每月 $81。"

现在他可以和每个团队进行预算对话，而不是只盯着一个汇总数字。

**AWS Cost Explorer 与 AWS Budgets**

**AWS Cost Explorer**：按服务、区域、标签和用量类型可视化历史和预测成本。理解钱花到哪里去的必备工具。

**AWS Budgets**：当成本超过（或预测将超过）阈值时发出警报。你可以按服务、区域、标签或账户设定预算。

Tom 设置了三个预算：

1. 月度总账单：在达到预算金额的 90% 时告警
2. EC2 按需：当 On-Demand 支出超过每月 $500 时告警（这是 Savings Plan 存在缺口的信号）
3. 数据传出：在每月 $200 时告警（数据传输成本可能意外飙升）

Budgets 把警报发到一个 Slack 频道。团队在接近上限时就能看到，而不是在月度发票上才发现。

**每一行都有收据：成本与用量报告**

Cost Explorer 回答了 Tom 的大多数问题。然后他撞上了一个它答不了的："上周二的费用尖峰究竟是哪些 S3 桶、逐小时地驱动的——又分别挂着哪些标签？"

对于这种取证级别的问题，AWS 提供 **Cost and Usage Report（CUR，成本与用量报告）**——现在通过 **Data Exports** 交付——这是 AWS 出产的最详细的账单数据：每一个明细项，**按资源、按小时**，带标签，交付到一个你自己拥有的 S3 桶。它不是仪表板；它是原始总账。标准用法是用 Athena 查询它（它以列式格式落地），或者喂给 QuickSight 做仪表板。

考试里的分工是：**Cost Explorer** = 控制台中的交互式可视化与预测。**Budgets** = 阈值告警。**CUR/Data Exports** = 粒度最细的数据，交付到 S3，供你自行分析。当题目说"用于自定义分析的资源级、按小时的成本数据"——那是 CUR，不是 Cost Explorer。

"我们有没有想过，要是从此再也不看这些会怎样？"Priya 问，"我们两天就找出了 $6,700。还有什么藏着没被发现？"

"定期审计，"她接着说，"每月做 Cost Explorer 审查。AWS Trusted Advisor 会自动标记未附加的卷和闲置资源。把已知浪费模式的清理自动化：删除超过 N 天的快照、对未附加的 EBS 卷告警、让旧的 S3 版本过期。"

**S3 Requester-Pays：转移传输成本**

在存储审计期间，Tom 发现了一个他没有预料到的情况。

Nimbus 的餐厅合作伙伴需要下载他们的菜单图片资源——即点餐平台向顾客展示的那些已处理、已缩放的图片。对一家更新菜单的餐厅来说，这意味着下载从 50 MB（小更新）到 800 MB（一次完整的季节性刷新）不等的图片文件。目前，每次下载的出站数据传输费都由 Nimbus 支付：从 S3 到合作伙伴所在地为 $0.09/GB。

按 287 家餐厅合作伙伴、平均每月一次菜单刷新、平均每次下载 200 MB 计算：287 × 0.2GB × $0.09 = 每月 $5.17。在当前规模下不算什么。

"到 2,000 家餐厅时会怎样？"Tom 问。

"同样的算法，"Maya 说，"大约每月 $36。"

"那到 10,000 家餐厅、合作伙伴开始下载大型季节性素材包——比如说节日菜单更新的 2 GB——呢？"

他算了一下。10,000 × 2GB × $0.09 = 每月 $1,800 的数据传输费，只是为了让合作伙伴下载他们需要的素材。

"这就是个真实的数字了，"Priya 说。

"我们有没有想过，要是这笔账单恰好出现在我们试图敲定 B 轮融资的那个月会怎样？"Priya 接着问。

"S3 Requester-Pays，"Tom 说。

S3 有一个叫 Requester-Pays（请求者付费）的功能：在桶上启用后，由发出请求的一方——而不是桶的所有者——支付数据传输和请求费用。桶所有者仍然支付存储费。但从这个桶发起的每一次下载，都计入请求者的 AWS 账户。

代价在于访问。Requester-Pays 要求请求者是拥有有效账户的 AWS 客户——对 Requester-Pays 桶的未认证或匿名访问会返回错误。对于 Nimbus 那些技术水平参差不齐的餐厅合作伙伴来说，要求他们为下载自己的菜单素材而开一个 AWS 账户，不是一个可行的模式。

"我们不能对合作伙伴的直接访问启用 Requester-Pays，"Maya 说，"我们的大多数合作伙伴不会为了下载几张照片去注册 AWS 账户。"

"正确，"Tom 说，"但我们可以把它用在 B2B 集成上——那些有技术团队和 AWS 账户的大型连锁。不是街角的小餐馆，而是那家有工程团队、直接对接我们 API 的 50 家门店的汉堡连锁。对那个客群，Requester-Pays 是说得通的。"

"那其他人呢？"

"我们给他们一个使用 S3 预签名 URL 的下载门户。传输仍然走 AWS，费用仍然由我们承担——但它本来也已经计入合作伙伴定价了。Requester-Pays 是我们会写进大客户合同谈判里的选项，不是今天就要部署的东西。"

Tom 把它加进了电子表格的"未来优化"一栏：为拥有 AWS 账户的企业级合作伙伴启用 S3 Requester-Pays。在 2,000 家餐厅、企业客户占 20%、每月下载 2 GB 的情形下：每月可能有 $72 转移给合作伙伴承担。在那个规模上不算大，但随着素材包变大，同样的模式会变得举足轻重。当合作伙伴数量超过 1,000，或者企业级合作伙伴开始拉取更大的季节性素材包时，重新评估。

"教训还是那个一贯的教训，"Tom 说，"在到达规模之前，先弄清楚成本在规模化之后会变成什么。今天的 $5 问题，就是三年后的 $1,800 问题。现在为它做设计，分文不花。"

**治理：自动删除还是只告警**

自动化的问题是引发最多分歧的那个。

"我们应该在 14 天后自动删除未附加的 EBS 卷吗？"Tom 问，"AWS Config 规则可以标记它们。Lambda 可以自动删除它们。"

"不行，"Priya 立刻说。

"为什么不行？"

"因为自动删除意味着我们终有一天会删掉某个有理由处于未附加状态的东西。也许有人为了把卷挪到另一台实例而把它分离了，而它已经躺了 12 天，正在等一个变更评审。第 14 天的自动删除会毁掉那份数据。"

"那就只告警？"Tom 说，"我们收到通知，但不自动删除。"

"先告警，"Priya 说，"强制让一个人来做决定。告警内容是：'此卷已处于未附加状态 14 天。如果你需要它，请打上 `keep: true` 标签，否则它将在下次评审中被标记为待删除。'人的决定就这样通过标签的有无被记录在案了。"

"那样更慢，"Leo 说。

"更慢，但更不容易毁掉数据，"Priya 说，"我们已经因为疏忽损失了 $3,200。我们还没有因为自动化损失过任何数据。我清楚我更愿意维持哪一种记录。"

Tom 最终采取了一个折中方案：第 7 天自动告警，需要 `keep: true` 标签才能压制后续告警，并每周生成一份所有"未打标签且未附加"的卷的报告供团队一起评审。不做自动删除。

**变奏：当清理的代价高过节省时**

如果你需要额外快照带来的安全感，留着它们——但每一个超过 90 天且无任何访问的快照都应该证明自己值得占着位置。这个取舍是不对称的：删掉一个你需要的快照，代价是一次事故；留着一个你不需要的快照，代价只是一笔小额月费。对于合规敏感的数据，保留旧快照的成本是真实的，但通常低于审计员索要时拿不出来的代价。对于 14 个月前一次测试留下的开发快照，这笔账就要反过来算了。

如果你为访问模式不确定的文件启用 EFS Intelligent-Tiering，自动分层既省钱又无需持续干预。如果文件可预测地朝归档访问的方向老化，直接的生命周期规则更简单。启用之前先测量。

SAA-C03 关联：考试会测试你能否在给定访问频率场景下在 S3 存储类（Standard、IA、Glacier）之间做出选择。这里适用同样的逻辑——正确的存储类取决于数据被访问的频率。

**忽视的代价**

Tom 做了一个电子表格。他计算了 Nimbus 在以下各项上花了多少钱：

- 未附加的 EBS 卷（16 个月）：$3,200
- 旧 S3 快照（已发现并删除）：$890
- 不需要的预置 IOPS：$816
- gp2 到 gp3 迁移的节省（如果更早进行，按预测）：18 个月 $346
- 不断积累的非当前 S3 版本：$1,340
- 未完成的分段上传：$94

识别出的浪费总额：18 个月约 $6,700。

"六千七百美元，"Maya 说。

"来自忽视，"Tom 说，"不是来自错误的架构决策。是来自不清理。"

"系统性的修复方案是什么？"

"还有，"Tom 补充道，"把成本卫生纳入部署流程。工程师终止 EC2 实例时，EBS 卷自动删除，除非他们明确选择保留。"

## 优势与局限

**成本优化纪律**：

- 定期审查能在累积的浪费变得显著之前发现它
- 打标签让问责成为可能——各团队看得到自己的成本
- 自动告警防止账单意外
- 生命周期策略和合理调整规格往往是一次设置、长期受益的节省

**复杂之处**：

- 在拥有众多团队的大型账户中识别浪费，需要集中化的工具
- 有些浪费是有意为之的（保留额外快照"以防万一"）——成本与风险的权衡是一种判断
- gp3 迁移需要仔细验证（在某些边缘情况下，IOPS 和吞吐量的默认值可能与 gp2 的行为不同）
- 成本分配标签要求所有团队都有纪律——不一致的标记会让数据不完整
- 对存储做自动删除的自动化是危险的——对卷和快照而言，告警加人工评审更安全

## 总结

存储审计用了两天。它揭出的浪费——18 个月里悄无声息积累出的 $6,700——与其说是决策的失败，不如说是注意力的失败。没有任何东西是故意配错的。那些快照、那些未附加的卷、那些不断累积的版本历史、那些未完成的分段上传：每一个在当时都有其道理，只是后来再也没人回头看过。这个教训无关具体的 AWS 服务。它关乎养成"去看一眼"的习惯。

- **存储成本在无形中积累**——定期审计必不可少。
- **未附加的 EBS 卷**是常见的浪费来源。删除它们（或在实例终止时自动删除）。
- **EBS 合理调整规格**：把 gp2 迁移到 gp3（通常节省 20%）。去掉多余的预置 IOPS。
- **S3 版本控制**：为非当前版本启用生命周期规则，避免为无限的版本历史付费。
- **未完成的分段上传**：给每个桶加上 `AbortIncompleteMultipartUpload` 生命周期规则。这一点常被忽视，且会悄悄积累。
- **EFS Intelligent-Tiering**：根据访问频率自动把文件移到更低成本的层级。对于可预测的访问模式，手动生命周期规则可能更便宜。
- **治理**：对未附加 7-14 天的卷告警；需要显式标签才能压制告警。避免对存储资源做自动删除。

## 考试技巧

*SAA-C03 领域：设计成本优化架构（领域 4，任务 4.1）*

- **成本分配标签**：在账单控制台中为成本分配启用用户定义标签；然后给资源打标签。Cost Explorer 按标签显示细分。考试场景："确定哪个部门产生了最多的 S3 成本" → 成本分配标签。
- **AWS Trusted Advisor**：识别利用率不足的 EC2 实例、未附加的 EBS 卷、闲置的负载均衡器和其他浪费。基本检查免费；完整检查需要 Business/Enterprise 支持计划。
- **EBS 成本组成**：存储（按 GB）、预置 IOPS（io1/io2 或 gp3 额外部分）、吞吐量（gp3 额外部分）。要知道哪些组成部分可以合理缩减。
- **S3 版本控制成本**：非当前版本按与当前版本相同的费率存储和计费。让非当前版本过期的生命周期规则，对版本化桶的成本控制至关重要。
- **AWS Compute Optimizer**：分析 EC2 利用率并推荐合适规格的实例类型。考试信号："通过选择正确的实例类型降低 EC2 成本" → Compute Optimizer。
- **AWS Cost Anomaly Detection**：用机器学习检测异常支出模式。考试信号："自动检测意外的成本增长" → Cost Anomaly Detection。
- **成本工具阵容**：交互式图表/预测 → Cost Explorer。阈值告警 → Budgets。"粒度最细的资源级/按小时账单数据，交付到 S3 供自定义分析（Athena/QuickSight）" → **Cost and Usage Report（Data Exports）**。
- **Requester Pays**："共享一个大型 S3 数据集；使用者自付下载费用" → S3 Requester Pays（所有者只继续付存储费；请求者必须用 AWS 账户进行认证）。

**练习 2 — SAA-C03 场景题**

*场景*：一家公司的 AWS 账单在六个月内从每月 $5,000 涨到了 $9,000，但他们没有新增任何服务。工程团队怀疑问题出在存储成本。哪种 AWS 工具组合最能识别并解释这次成本增长？

A) 用 AWS CloudTrail 审查 API 调用，找出是谁创建了新资源  
B) 用 AWS Cost Explorer 做服务级别的成本细分，并用 AWS Trusted Advisor 检测闲置和未附加的资源  
C) 用 Amazon CloudWatch 监控资源利用率并创建成本警报  
D) 用 AWS Config 识别所有资源及其合规状态

**提示 1**："识别成本增长" → 按服务可视化成本细分。

**提示 2**："闲置和未附加的资源" → 有一个特定工具会主动识别这些。

**提示 3**：CloudTrail 记录 API 调用；Cost Explorer 显示成本趋势。哪个对成本分析更有用？

**答案**：B

**解释**：AWS Cost Explorer 按服务、区域和用量类型显示成本趋势——非常适合找出是哪个服务驱动了增长。AWS Trusted Advisor 的成本优化检查能识别未附加的 EBS 卷、闲置的 EC2 实例、利用率不足的负载均衡器和其他常见的浪费来源。

**为什么不是 A？** CloudTrail 记录谁在何时创建了资源，但不直接显示成本趋势，也不识别浪费。

**为什么不是 C？** CloudWatch 监控资源性能（CPU、内存）——对调整规格有用，但不用于识别累积的存储浪费。

**为什么不是 D？** AWS Config 追踪资源配置和合规性，但它不是成本分析工具。
