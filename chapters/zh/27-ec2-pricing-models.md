# 第二十七章：为所需付费

Tom 在打开账单标签页之前先冲了一杯咖啡。他一向如此——有些报表，最好趁热看。他在窗边的椅子上坐下，杯子在手，周六的清晨外面还很安静。没有消息提示，没有站会。只有电子表格和数字。

他打开了那个标签页。

**回顾：从 Athena 的洞察到账单**

上一章的 Athena 分析做到了一件出乎意料的事：通过直接从 S3 查询成本与用量报告，Tom 终于不只是看到一个 AWS 账单总额，而是看到了过去六个月里每个服务每周实际花了多少钱的明细。浮现出的图景清晰得令人警觉。EC2 是单项最大的开支，而且模式一目了然——团队一直在为一家自己长期常住的酒店支付散客价。这个发现把 Tom 在一个周六的早晨送到了 EC2 定价页面前，端着一杯新冲的咖啡，下定决心要在下一张月度发票到来之前搞懂每一个选项。

自 Nimbus 成立以来，Tom 每个月都会审查 AWS 账单。第一年，他大概能看懂 60%。到现在，他几乎什么都懂了——除了为什么 EC2 那一栏总让他觉得他们付多了。EC2 部分是各种实例类型的"按需实例（On-Demand instances）"的混合，全部按小时计价，加起来每月 $2,340。

在给任何人打电话之前，他自己花了一个小时把实例清单过了一遍——不是为了下结论，而是为了形成可以验证的假设。

他看到四台标记为 "api-prod" 的 r6g.large 实例。他看到两台运行后台作业处理器的 c6g.medium 实例。他看到一台标着 "vpn-server" 的 t3.medium，从公司成立的第三个月起就一直在跑。他看到一对标记为 "analytics-batch" 的实例，每晚凌晨 3 点出现，早上 7 点之前消失。

他写下一列假设：

- API 服务器：可预测，一直在运行。
- 后台处理器：大概率可预测。
- VPN 服务器：一直在运行，从不变化。
- 批量分析：也许适合 Spot？

然后他在页边空白处写道：*在做任何决定之前逐一验证。*

这种纪律——把"我假设的"和"我知道的"分开——正是 Tom 的成本审查之所以有用的原因。他把其他人叫了过来。

"我们可以继续付散客价，"等大家上了线，Tom 说，"但我们不会。"

"散客价？"Leo 问。

"On-Demand 定价，"Tom 说，"就像在需要住的当天早上才去订酒店房间。最大的灵活性。最高的价格。"

"那替代方案是什么？"

**酒店类比**

Tom 想了一会儿。"你知道有些人是到店当天早上才订房的吧？我们现在就是那样。其实有更好的策略——提前六个月预订拿折扣、在最后一刻以大幅优惠拿下没卖出去的房间、或者如果你需要整层楼，就把整层楼租下来。同一家酒店，四种不同的价格。"

Leo 看着他。"那这些在 AWS 里分别对应什么？"

Tom 调出了 EC2 定价页面。"有四种定价模式。而我们只在用一种。"

EC2 定价与酒店订房策略的对应出奇地贴切：

**On-Demand（按需）**：不带预订直接走到前台。你付全额门市价，但想退房随时可以。完美适用于不可预测的住宿。

**Reserved Instances/Savings Plans（预留实例/Savings Plans）**：提前预订全年的房间。你获得可观的折扣——便宜 30-72%——以换取使用承诺。

**Spot Instances（竞价实例）**：以酒店大幅打折的现行价格拿下未售出的房间——不用讨价还价，酒店根据空置程度自己定价。最高可便宜 90%。但如果酒店需要把房间留给全价客人，他们可以提前两分钟通知请你离开。（多年前你确实需要为 Spot 容量*出价*；AWS 在 2017 年取消了竞价机制——你只需支付当前的 Spot 价格。）

**Dedicated Hosts（专用主机）**：把酒店的整层楼租下来独享。不与其他客人共享。明显贵得多。当软件许可或合规规则禁止共享物理主机时才需要。

每种模式都有其用例。Nimbus 犯的错误是：所有东西都用 On-Demand，包括那些全天候运行、完全可预测的工作负载。

**On-Demand 实例：最大灵活性，最高成本**

**何时使用**：

- 不可预测的工作负载（无法预测的流量峰值）
- 开发和测试（频繁启动和停止）
- 短期工作负载（运行一周的实验）
- 首次部署（在了解使用模式之前）

**何时不使用**：

- 你确定会运行超过一年的稳态生产工作负载
- 任何具有可预测基线负载的工作负载

**EC2 休眠：暂停而不丢失状态**

有一个未得到足够重视的成本优化技巧：**EC2 休眠（Hibernation）**。当你停止一台普通实例时，RAM 中的内容就没了——下一次启动是冷启动。操作系统引导、应用初始化、数据库连接重新建立。对大多数生产 Web 服务器来说，这没问题。对某些工作负载来说，这很昂贵。

当你休眠一台实例时，RAM 内容会在关机前保存到 EBS 根卷。下次启动时，实例从中断处原样恢复——进程在跑、连接已建立、应用状态完好——耗时只是冷启动的一小部分。这对那些你想在夜间暂停又不想丢状态的长时间分析作业特别有用，对那些启动和配置环境要花好几分钟的开发实例也是如此。

"我有一台数据科学实例，"Leo 看着打印纸说，"启动要九分钟。定制环境，十几个 Python 包，还预加载了一些模型权重。我每晚停掉，每天早上重启。"

"所以你每天花九分钟看着它开机，"Tom 说。

"是的。"

"那是每周 45 分钟的工程师时间，花在等一台 EC2 实例上。"

"是的。"

"让它休眠。"

启用休眠后，Leo 的实例在每天下班时暂停，把 RAM 保存到 EBS 根卷，第二天早上在 90 秒内恢复。分析会话从他离开的地方原样继续。

休眠的要求：休眠必须**在启动时启用**——你无法为一台已经在运行的实例打开它（Leo 不得不从 AMI 重新启动他的数据科学机器才能用上）。实例的 RAM 不得超过 150 GB（RAM 内容必须装得进 EBS 根卷），根卷必须大到能同时容纳操作系统和 RAM 转储，并且根卷必须加密（休眠会把内存中的敏感数据写到磁盘上）。裸金属实例以及 RAM 超过 150 GB 的实例不支持休眠。还有一条限制：一台实例最多只能保持休眠 **60 天**——超过之后必须被启动、停止或终止；它不能无限期地沉睡。

Tom 梳理了 Nimbus 的 On-Demand 实例：

- Web API 服务器：4 台 EC2 实例，全天候运行了 18 个月。*可预测的基线。*
- VPN 服务器：一直在运行。*可预测的基线。*
- 用于流量峰值的额外 API 服务器：不可预测。*这里用 On-Demand 是正确的。*

"等等——可是*为什么*峰值服务器要继续用 On-Demand？"Maya 问，"如果我们每个周五都有峰值，这难道不够可预测、不值得承诺吗？"

Tom 想了想。"基线是可预测的。峰值在时间上可预测，在幅度上不可预测。有些周五晚上比平时高 30%；有些高 150%。如果我为六台实例购买预留容量，而某次峰值只需要额外两台，我就承诺过头了。如果我只买两台，而峰值需要八台，我就不够用，超出部分反正还是跑 On-Demand。专门针对突发容量，On-Demand 或 Spot 才是正确的——流量开始攀升时，你没法实时买一个预留实例。"

"何时不使用"那份清单之所以重要是有原因的：如果同一批实例已经跑了六个月，而且你能预测它们会继续跑下去，那么在 On-Demand 上的每一个月，都是在为一间你长期占用的房间支付散客价。

**预留实例：为期一年的承诺**

**预留实例（Reserved Instances，RIs）**是一种计费承诺——你同意在特定区域使用特定实例类型 1 年或 3 年。作为交换，AWS 收取更低的小时费率。

**折扣档位**：

- 1 年，不预付：比 On-Demand 约低 30-40%
- 1 年，部分预付：约低 35-45%（现在付一部分，每小时少付一些）
- 1 年，全部预付：约低 40-50%（现在付清全年）
- 3 年，全部预付：约低 55-72%（最大折扣，最大承诺）

**Standard 与 Convertible RI**：

- **Standard（标准）**：锁定到确切的实例类型和区域。如果不再需要，可以在预留实例市场（Reserved Instance Marketplace）上出售。
- **Convertible（可转换）**：可以在承诺期内更改实例类型、操作系统和租赁模式。折扣低于 Standard（最高约 66%，对比 72%）。

Tom 为那 4 台 API 服务器（r6g.large，On-Demand 约 $0.101/小时）算了笔账：

- 年度 On-Demand 成本：$0.101 × 24 × 365 × 4 ≈ $3,540
- 1 年全部预付 RI（1 台实例）：约 $520 预付（≈ 41% 折扣）
- 4 台实例：约 $2,080 预付 = **第一年节省约 $1,460**

"仅仅靠做出承诺，我们第一年就能省下差不多一千五百美元，"Tom 说，"那这个每月到底要花多少——每台预留实例和我们现在付的相比？"

"它是前置投入，"Maya 说，"你要把全年的钱提前付掉。"

"等等——可是*为什么*实例类型还在演进的时候我们就要承诺 Standard RI？"Maya 问，"如果 r6g 明年就过时了怎么办？"

"如果我们觉得可能需要更换，就买 Convertible RI。折扣低一些——最高约 66% 而不是 72%——但换来的是承诺期内可以切换实例家族的灵活性。"

"那如果我们承诺之后，AWS 发布了更好的实例类型呢？"

"我们在 RI 到期时再评估。如果新类型更好，我们为下一个周期购买新 RI。当前的 RI 仍然以承诺价跑完它的周期。"

Tom 把盈亏平衡对比拉到了共享屏幕上，方便所有人跟上：

**三方对比：r6g.large，4 台实例，12 个月**

| 选项 | 年度成本 | 等效月度成本 | 灵活性 |
|---|---|---|---|
| On-Demand（$0.101/小时 × 4） | $3,540 | $295 | 完全 |
| Compute Savings Plan（1 年期约 34% 折扣，承诺 $0.27/小时） | $2,365 | $197 | 高 |
| Standard RI，1 年全部预付（4 × $520） | $2,080 | $173 | 低 |

"等等，"Leo 说，"RI 比 Savings Plan 还便宜？"

"同样的期限下，是的——这就是灵活性的价格，"Tom 说，"Compute Savings Plan 适用于*任何*实例类型、大小、区域，甚至 Fargate 和 Lambda，所以它的最大折扣更低——3 年期最高 66%。而 Standard RI 或 EC2 Instance Savings Plan 会把你锁定到一个实例家族，并用最高 72% 的折扣来回报这种锁定。你保留的自由越多，AWS 给的折扣就越少。"

"3 年期 RI 的盈亏平衡点在哪里？"

"3 年全部预付：每台实例约 $1,060，四台总共 $4,240——这买下的是 36 个月。等效月度成本：$118，对比 On-Demand 的 $295。预付款大约在第十四个月回本；之后将近两年都处在净节省区间。"

"那如果我们在第四个月决定需要换一个不同的实例家族，"Priya 说，"我们还在为原来的承诺付钱。"

"正确。Standard RI 可以在 RI 市场上出售，但不一定能卖到全价。Convertible RI 可以交换但不能出售。这就是为什么 Savings Plan 往往是更稳妥的选择——同样的原理，更少的锁定。"

**Savings Plans：灵活的承诺**

**Savings Plans** 是比预留实例更新、更灵活的替代方案。你承诺的不是某个特定的实例类型，而是一个特定的*每小时支出金额*（以美元计）。

**Compute Savings Plans**：适用于任何 EC2 实例，无论类型、大小、区域或操作系统。最灵活。最高 66% 折扣。

**EC2 Instance Savings Plans**：适用于某个区域中的特定实例家族（例如"us-west-2 中的 c6g 实例"）。比 Compute 限制更多，但最高 72% 折扣（与 RI 的最大折扣相同）。

**SageMaker Savings Plans**：专用于 SageMaker 机器学习训练和推理。

对于 Nimbus：API 服务器用 Compute Savings Plans。他们承诺了每小时 $0.45 的计算支出。任何实例类型、任何大小——而且这个承诺还覆盖 Fargate 和 Lambda，这对后面发生的事情很重要。当他们扩充机队或更换实例类型时，Savings Plan 仍然适用。

"这对我们来说比预留实例更好，"Leo 说，"我们还在试验实例类型。Compute Savings Plan 给了我们折扣，又不会把我们锁死在 r6g 上。"

"如果我们承诺了每小时 $0.45，而某些月份只用了 $0.36，会怎样？"Maya 问。

"无论如何你都付 $0.45，"Tom 说，"承诺是无条件的。Savings Plan 会套用到你不超过承诺额度的任何用量上。超出部分按 On-Demand 价格计费。这里的纪律在于：把承诺设在一个你有信心永远能达到的水平。"

"而且我们不该按平均值承诺——我们该按下限承诺，"Priya 说。

"完全正确。看过去六个月。找到用量最低的那一周。按那个数字的 90% 承诺。然后随着我们的增长按季度复核。"

"我们有没有想过承诺过头会怎样？"Priya 接着说，"我们买了一个 $2/小时的计划，结果下个季度我们做了优化，计算用量降到了 $1.50？"

"那 $0.50/小时的缺口就成了浪费，"Tom 说，"我们在为已经不存在的容量付钱。这就是承诺设得太高的风险。季度复核正是为了抓住这种情况——如果用量已经降到承诺之下，我们就知道下一次购买应该更小。有一个重要的细节：*Compute* Savings Plan 会跟着你去 Fargate 和 Lambda——把 EC2 工作负载迁移到容器并不会让它落空。真正会让承诺落空的，是计算用量切实减少，或者你持有的是针对某个你已经不再使用的实例家族的 *EC2 Instance* Savings Plan 或 RI。"

你也许会想：为什么不干脆按能负担的最大金额买 Savings Plans，让 AWS 自己去匹配？答案是：承诺是一个下限，不是上限。如果你承诺 $5/小时，但只用了 $3/小时，你照样付 $5/小时。每一美元与实际用量不匹配的承诺支出，都是浪费掉的一美元。季度复核不是可选项——它正是让 Savings Plan 保持为一项优化、而不是滑向过度承诺的关键。

**Spot 实例：90% 的折扣**

**Spot 实例**使用 AWS 的空闲 EC2 容量。当 AWS 有未使用的服务器时，你可以以低于 On-Demand 价格 60-90% 的价格租用它们。当 AWS 需要收回容量（给 On-Demand 或预留客户）时，他们会给你 2 分钟的警告，然后终止你的实例。

你也许会想：谁会围绕一种可能在两分钟通知后就消失的实例来设计系统？答案是：任何工作可以从头重启的人。批处理作业、分析、渲染流水线——这些都不要求开始干活的那台实例必须是干完活的那台。2 分钟的警告足够保存一个检查点、排空连接、干净地退出。

中断风险是其决定性特征。Spot 实例只适用于：

- **容错工作负载**：如果实例在任务中途终止，任务可以重启而不会损坏任何东西
- **无状态处理**：图片缩放、视频编码、批量分析、机器学习训练
- **短时批处理作业**：2 分钟的警告足以保存状态并写检查点
- **Auto Scaling 混合机队**：把 Spot 用于 ASG 的大部分，On-Demand 作为基线

对于 Nimbus：Spot 实例对每晚运行的批量分析作业（把当天的订单数据处理成汇总报告）很有意义。如果一台 Spot 实例在作业中途被终止，作业失败，但会在一台新实例上从头重启。S3 中的数据是安全的。

但在团队完全理解这个模式之前，Leo 是用惨痛的方式发现这一点的。

三个月前，他把夜间批处理作业迁到了 Spot，却没有内置检查点逻辑。第一晚，Spot 实例跑得很顺利。第二晚，它在凌晨 4:47 被中断——那时一个需要一小时二十分钟才能完成的作业才跑了四十七分钟。作业失败了。当餐厅合作伙伴那天早上登录时，前一天订单的最终报告不见了。

"我已经部署好了——哦，"Leo 当时看着作业失败通知说，"我以为不会有事。第一晚确实没事。"

"发生了什么？"Maya 当时问。

"Spot 中断。AWS 需要收回容量，给了我们两分钟，实例终止了。作业没有检查点。当一台新的 Spot 实例在凌晨 5 点启动重试时，它从零开始。早上 6:40 才跑完。报告晚了两个小时。"

修复很直接：每十五分钟把中间结果写到 S3。每个检查点都是一份完整的部分状态——足以让新实例读取最后一个检查点并从那里继续，而不是从头重来。

"夜间作业改用 Spot 后，成本从每晚 $12 降到了每晚 $2，"补丁上线后 Leo 汇报道，"就算把那一个糟糕的夜晚算进去，跑三个月的总成本也低于两周的 On-Demand 价格。"

"它不会有事的，"Leo 补充道，"就算它在运行中途被中断——对吧？"

"有了检查点机制，没事，"Tom 说，"没有的话，有事。对中断的容忍必须构建进作业里，而不是想当然。"

"那如果有人试图入侵呢？"Priya 问，"Spot 实例跑在共享硬件上。如果它被中断、一台新的启动了，实例之间会不会有数据泄露？"

"不会，"Tom 说，"AWS 在终止时会擦除实例存储。下一个拿到那块硬件的客户看到的是一块白板。但这是个好直觉——任何时候用共享容量，都值得去验证它的隔离模型。"

**Spot Fleet 多样化**

Leo 从那次被中断的批处理作业中还学到了一件事：当你只请求单一一种 Spot 实例类型时，你是在赌那个特定类型在那个可用区里的可用性。如果 us-west-2a 里 c5.2xlarge 的 Spot 容量耗尽，你的作业就只能等——或者失败。

**Spot Fleet** 解决了这个问题：它允许你在单个请求中指定多种实例类型和多个可用区。AWS 会从当时有可用容量、价格最低的任意组合中满足你的机队需求。

```
Spot Fleet request:
  Target capacity: 4 units
  Fleet diversification:
    - c5.2xlarge, us-west-2a
    - c5.2xlarge, us-west-2b
    - c5a.2xlarge, us-west-2a
    - m5.2xlarge, us-west-2a
    - c5d.2xlarge, us-west-2b
  Allocation strategy: diversified
```

使用多样化机队后，某一种实例类型或某一个可用区的中断只影响机队的一部分。其余部分继续运行。对于 Nimbus 的批处理作业，用四台实例的 Spot Fleet 取代单台大实例，意味着即便发生部分中断，作业也能跑完——慢一点，但不必完全重来。

"多样化机队往往还能拿到更好的价格，"Tom 说，"AWS 会在你机队里的所有类型中给你最低价。有些晚上你拿到的 c5a 比 c5 还便宜，只因为那边碰巧有容量。"

"和只用单一实例类型相比，这个每月要花多少钱？"Tom 自言自语地问——这个习惯如今已是完全的条件反射。他算了算。混合定价的 Spot Fleet 平均每晚 $1.80，对比单一类型请求的每晚 $2.00。绝对值上差别不大，但单是可靠性的提升就足以证明这次改动是值得的。

"那如果有人试图入侵 Spot Fleet 呢？"Priya 问。

"答案一如既往，"Tom 说，"每台实例都与其他实例隔离。Fleet 不会自动把它们放进一个共享的私有网段。你的安全组仍然分别作用于每一台实例。"

检查点让中断变得可控，而不是消失。作业仍然要从最后一个检查点重启，而且如果重启恰好撞上 Spot 价格飙升的时段，替换实例可能要 10 到 20 分钟才能就位。最后一个检查点已覆盖的工作在重启时被跳过；那之后的工作要重做。返工的总开销：很小，但真实存在。

Spot Fleet 干净利落地解决了可用性问题。通过在三个可用区里指定五种实例类型，Leo 把出现完全容量缺口的概率降到了接近零。AWS 的分配策略——diversified——把四台实例的机队分散到各个容量池，于是没有任何单一容量池的中断能让作业停摆。当一台实例被中断时，其余三台继续处理，而检查点意味着替换实例只需接手被中断的那台正处理到一半的工作。从头到尾，这个作业再也没有错过过早上 7 点的报告截止时间。

"多样化在复杂度上付出了什么代价？"Leo 把这些写成文档时，Maya 问。

"Spot Fleet 请求里多了三行，"Leo 说，"处理代码不知道、也不关心自己跑在哪种实例类型上。复杂度完全留在机队配置里，不在应用程序里。"

这就是从一开始就把应用设计成无状态的好处：伸缩和容错的决策成了基础设施层面的决策，而不是代码层面的决策。


**专用主机：合规选项**

某些软件许可（Oracle、某些配置下的 Windows Server）按物理插槽或核心计价。当你在共享主机（EC2 的默认模式）上运行这类软件时，你可能在为你并未使用的容量付许可费。

**专用主机（Dedicated Hosts）**让你独享一整台物理服务器。你可以带入现有的按插槽计价的许可证。没有任何其他 AWS 客户的实例运行在同一硬件上。

专用主机比标准 EC2 贵得多。它们是合规与许可的工具，不是成本优化的工具。

Nimbus 没有任何需要专用主机的许可要求。大多数云原生应用都不需要。

**变奏：当承诺适得其反时**

如果你的工作负载在 12 个月内可预测且稳定，预留实例能带来最大折扣——但如果你的实例类型需求可能在此期间发生重大变化，这种锁定让你失去的灵活性会比价差更值钱。Convertible RI 解决了其中一部分，但折扣打了折。Compute Savings Plans 解决了其中大部分，代价是最大折扣略低于 Standard RI。

如果你把 Spot 实例用于容错的批处理作业，可以实现 60-90% 的节省——但如果同样的实例在服务实时用户请求，一次请求中途的中断就意味着失败的交易和不开心的客户。工作负载对中断的容忍度才是决定性变量。

还有一种更隐蔽的错误选择：Savings Plan 承诺过头。如果你因为上个季度的计算用量平均为 $3.00/小时而购买了一个 $3.00/小时的 Compute Savings Plan，然后这个季度优化了服务（总用量降到 $1.80/小时），你照样要付承诺的 $3.00/小时。那 $1.20/小时的缺口就是浪费。（注意，把 EC2 工作负载迁移到 Fargate 或 Lambda *不会*让 Compute Savings Plan 落空——它三者都覆盖。让承诺落空的风险是用量的真实下降，或者 EC2 Instance Savings Plans 和 RI 的实例家族锁定。）这就是下限策略重要的原因：按你的最低值承诺，而不是平均值。并且按季度复核。

规则是：为你确定的部分做承诺。为你不确定的部分用 On-Demand。Spot 只用于能扛得住硬停机的工作。

**构建混合机队**

成熟的做法：把多种定价模式组合使用。

对于 Nimbus 的 API 机队：

- **基线负载（4 台实例，始终运行）**：由 Savings Plan 承诺覆盖
- **可预测的高峰（工作时间额外 2 台实例）**：如果承诺额度覆盖得到，由 Savings Plan 覆盖，否则用 On-Demand
- **流量峰值溢出**：Spot 实例（可以接受，因为 API 服务器是无状态的——实例终止时请求会重新分配）

结果是：一支在每一层都做了成本优化的机队——可预测部分用承诺定价，不可预测的增长用 On-Demand，突发容量用 Spot。

**监控 Savings Plan 利用率**

买下 Savings Plan 不是工作的结束。它是一项周期性义务的开始：搞清楚这份承诺有没有被兑现。

Tom 在每个季度的第一个周一设了日历提醒：Savings Plan 利用率复核。工具是 AWS Cost Explorer。具体来说，是"Reservations and Savings Plans"下的"Savings Plans"标签页，那里显示着他关心的三个数字：

- **利用率（Utilization rate）**：承诺支出中有多大比例被符合条件的实际用量匹配上了？低于 100% 意味着他在为没被用上的承诺付钱。
- **覆盖率（Coverage rate）**：符合条件的 EC2 用量中，有多大比例被 Savings Plan 覆盖，而不是在按 On-Demand 价格运行？低于 80% 意味着存在未被覆盖的用量，更大的承诺额度可以把它们收进来。
- **On-Demand 支出**：未被任何 Savings Plan 覆盖的那部分 EC2 支出。如果它在增长，要么是 Savings Plan 买小了，要么是有新工作负载加在了承诺范围之外。

第一次季度复核时，数字是这样的：

- 利用率：97%。承诺支出中有百分之三没被匹配上——在 $330/月的承诺里是每月 $9.90。这可以接受；它说明承诺设得略高于实际的用量下限，而这是有意为之。
- 覆盖率：84%。符合条件的 EC2 用量中有百分之十六在按 On-Demand 运行。那是突发容量——流量峰值期间启动、未被承诺覆盖的溢出实例。
- On-Demand EC2 支出：$147/月。其余大部分来自 Spot 实例（不在 Savings Plans 覆盖范围内，单独计价）。

"97% 的利用率是健康的，"Tom 说，"说明我们没有承诺过头。如果这个数是 80%，我就知道我们买多了。"

"那 84% 的覆盖率呢？"Maya 问。

"也没问题。那 16% 的 On-Demand 是突发容量——高峰时跑几个小时、而不是跑一整天的实例。要覆盖它们，我们得多买不少 Savings Plan 承诺，而它们可能不值得。"他算了算：那些未覆盖的 On-Demand 实例每月大概跑 40 个小时，每台 $0.101/小时。用 Savings Plan 覆盖它们，需要一份我们 90% 的时间都用不满的承诺。还是让它们留在 On-Demand 更好。

第二次季度复核，也就是六个月后，有一项指标变了：On-Demand EC2 支出涨到了每月 $290。Nimbus Instant 功能上线了，几台新的后台服务实例在 Tom 没注意的情况下加了进来。

"这三台实例，"Tom 指着 Cost Explorer 的明细说，"它们已经按 On-Demand 跑了三个月。如果它们会一直跑下去，我们应该把它们加进 Savings Plan 承诺。"

季度复核抓住了它。没有这次复核，那三台实例会无限期地继续按散客价跑下去。

"承诺怎么调整？"Priya 问。

"在现有计划之上再购买一份新的、追加的 Savings Plan，"Tom 说，"Savings Plans 可以叠加。我会为新的基线加一份 $0.10/小时的 Compute Savings Plan。现有的 $0.45/小时计划继续跑到它的三年期结束。新计划开始它自己的三年期。"

"所以我们会有两份相互重叠的 Savings Plans。"

"是的。它们各自独立地套用到任何符合条件的用量上。AWS 会按从最划算到最不划算的顺序进行匹配。"

"我们有没有想过，如果明年我们把其中一个后台服务卖掉会怎样？"Priya 问，"我们已经承诺了三年每小时 $0.55。"

"这就是三年期的风险，"Tom 说，"这也是为什么新承诺买得更小——我承诺的是新工作负载的下限，不是平均值。如果我们下线一个服务、用量下降，剩下的服务应该仍然能消化掉全部承诺额度。"

季度复核这套纪律并不光鲜。它是在 Cost Explorer 里的十五分钟，核对三个数字，做出或推迟一个决定。但放到三年的尺度上，这份纪律决定了一份 Savings Plan 究竟是保持 90% 以上的利用率——真金白银的节省——还是随着基础设施在它周围不断演化而逐渐滑向部分浪费。

## 优势与局限

**On-Demand**：无承诺。全价。用于不可预测或短期的工作负载。

**预留实例**：最高 72% 折扣。锁定到特定实例类型/区域/操作系统。未使用的容量可在 RI 市场出售。

**Savings Plans**：最高 66-72% 折扣。比 RI 更灵活（Compute Savings Plans 适用于任何实例类型）。自动套用到匹配的用量上。

**Spot 实例**：最高 90% 折扣。有 2 分钟中断的风险。只用于容错、无状态、可中断的工作负载。

**专用主机**：完整的物理服务器。最贵。某些许可或合规场景必需。

## 总结

Tom 用周六剩下的时间把 Nimbus 的每个工作负载映射到了最适合它的定价模式——基线对应 Savings Plans，夜间批处理作业对应 Spot，不可预测的溢出对应 On-Demand。这项练习把三个月的散客价支出变成了一项有意识的策略。数字一旦算出来，就很难再视而不见。

- EC2 定价有四种模式：**On-Demand**（全价，无承诺）、**预留实例/Savings Plans**（承诺支出换取可观折扣）、**Spot**（空闲容量，便宜 60-90%，可被中断）、**专用主机**（物理服务器独占）。
- 出于灵活性，**Savings Plans** 通常优于预留实例。
- **Spot 实例**要求容错、无状态的工作负载——只用于批处理作业、机器学习训练和可中断的处理。
- 基于 Spot 的批处理作业必须**向持久化存储（S3）写检查点**——被中断的作业应该从最后一个检查点恢复，而不是从零重启。
- 跨多种实例类型和可用区的 **Spot Fleet 多样化**能降低中断风险，而且往往能拿到更好的价格。
- 最优策略是**混合机队**：基线用 Savings Plans，不可预测的增长用 On-Demand，可中断的批处理工作用 Spot。
- 当工作负载已稳定运行 3 个月以上时，重新审视定价模式——从那时起，On-Demand 就开始变成浪费了。
- **按季度复核 Savings Plan 承诺**——按下限而非平均值做承诺，并随用量模式的变化进行调整。

## 考试技巧

*SAA-C03 领域：设计成本优化架构（领域 4，任务 4.2）*

- **Savings Plans 与预留实例**：Savings Plans 更灵活（Compute Savings Plans 适用于任何 EC2 实例）。预留实例锁定到特定实例类型。考试场景："需要在获得折扣的同时保持最大灵活性" → Savings Plans。"确定 3 年都会使用某个确切的实例类型" → Standard RI 以获得最大折扣。
- **Spot 信号**："对成本敏感"、"容错"、"批处理"、"可以承受中断"、"无状态工作负载"、"机器学习训练" → Spot。
- **Spot 中断处理**：Spot 实例在终止前会收到 2 分钟警告。你的应用必须优雅地处理它（保存状态、排空连接、干净退出）。
- **Web 服务器选 On-Demand 还是 Spot**：服务实时用户流量的 Web 服务器不应使用 Spot（中断会导致请求失败）。Web 层使用 On-Demand 或 Savings Plans。
- **EC2 Savings Plans 与 Compute Savings Plans**：EC2 Savings Plans 适用于特定实例家族和区域（折扣更高）。Compute Savings Plans 适用于任何 EC2 实例、Lambda 和 Fargate（最大折扣较低，更灵活）。
- **RI 市场**：未使用的 Standard 预留实例可以卖给其他 AWS 客户。Convertible RI 不能出售。
- **休眠（Hibernation）：**停止时把 RAM 内容保存到 EBS 根卷；启动时恢复。实例带着全部进程和状态恢复，比冷启动更快。当实例状态必须在会话之间保留时使用。要求：在启动时启用（不能为已有实例追加）、RAM ≤ 150 GB、EBS 根卷加密、不支持裸金属实例；最长休眠 60 天。考试信号："快速恢复实例并保留内存中的状态"或"开发实例初始化耗时过长" → 休眠。

**练习 2 — SAA-C03 场景题**

*场景*：一家媒体公司运行一条视频转码流水线，把上传的视频转换成多种格式。只要有视频上传，转码作业就持续运行（全天候运行，数量可变）。每个作业耗时 5-30 分钟。如果转码作业被中断，可以从头重启而不丢失数据。公司希望把成本降到最低。

哪种 EC2 定价模式最符合这些要求？

A) Auto Scaling Group 中的 On-Demand 实例  
B) 预留实例（1 年，全部预付）  
C) 使用 Spot Fleet 实现自动实例多样化的 Spot 实例  
D) 使用公司现有媒体软件许可证的专用主机

**提示 1**："可以从头重启而不丢失数据"——这是解锁某种特定定价模式的关键短语。

**提示 2**：对一个可中断的工作负载来说，"把成本降到最低"指向折扣最大的选项。

**提示 3**：Spot Fleet 从多种实例类型和多个可用区请求实例，降低中断的可能性。

**答案**：C

**解释**：转码作业是容错的——被中断后可以重启。这使它们成为 Spot 实例的理想用例，相比 On-Demand 可享 60-90% 的折扣。Spot Fleet 跨实例类型和可用区做多样化，降低大规模中断的可能性。

**为什么不是 A？** On-Demand 是成本最高的选项。对一个持续运行的容错工作负载来说，这是浪费。

**为什么不是 B？** 预留实例提供 50-72% 的折扣，但拿不到 Spot 为容错工作负载提供的、可能高达 90% 的折扣。此外，RI 面向可预测、稳态的工作负载——Spot 才是专为可中断批处理而生的。

**为什么不是 D？** 专用主机是为许可合规服务的，不是成本优化工具。它们是最贵的选项。
