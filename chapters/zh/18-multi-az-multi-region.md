# 第18章：当事情出错时

这一章是关于失败的——有计划地、有针对性地、并最终被接受为不可避免的失败。这可能是本书中最重要的章节。

Nimbus 运行良好。安全层已就位。监控已激活。流量在增长。

然后 Leo 在一个周四晚上11:23收到了一条 Slack 通知。

"us-east-1 可用区 us-east-1b——硬件故障——服务降级。"

他打开了 AWS 控制台。us-east-1b 中的 EC2 实例显示状态检查失败。他的自动扩展组检测到不健康的实例，正在启动替换——在 us-east-1b 中。

在那个正在失败的 AZ 中。

新实例也无法启动。它们在同一个硬件故障区域中。

"负载均衡器正在向两个 AZ 路由流量，" Leo 对自己说。"我们一半的流量正在去往无法工作的实例。"

在他注意到并手动将 ASG 切换到只使用 us-east-1a 之前，有二十二分钟的服务降级。

"这发生是因为一切都在一个 AZ 里，" Priya 第二天早上说。

"不，" Leo 说。"我在两个 AZ 都有实例。问题是替换实例在失败的 AZ 中生成。"

"数据库呢？"

Leo 停住了。

"RDS 实例是多 AZ 的，" 他说。"备用在 us-east-1b。这个正在失败。RDS 尝试故障转移到备用，而备用也失败了。"

二十二分钟的服务降级变成了三十八分钟。

**电网类比**

想想你家如何获得电力。电力不是来自单根线路连接到一台发电机。它来自电网——相互备份的发电机、变电站和输电线路网络。如果一个变电站着火，其他变电站绕过它重新路由电力。你不会注意到。灯继续亮着。

AWS 可用区的工作方式相同。不是让所有东西都依赖的一个巨大数据中心，AWS 将你的资源分布在多个物理上独立的设施中。如果一个设施停电或发生硬件故障，其他设施继续运行。流量自动重路由。你的应用程序保持运行——因为从来没有一根单独的线路可以切断。

多区域是下一个层次：想象在完全不同的城市有备用发电机。如果整个本地电网停止，远程城市接管。设置更复杂，但对灾难性故障更有弹性。

**失败的词汇表**

在为弹性设计之前，你需要描述你所设计对抗的东西的词汇。

**可用性**：系统运行的时间百分比。"四个九"（99.99%）意味着每年不到52分钟的停机时间。"五个九"（99.999%）意味着每年约5分钟。

**RTO（恢复时间目标）**：在成为业务问题之前，系统可以宕机多长时间？如果你的 RTO 是4小时，你有4小时来恢复服务，然后 SLA 被违反。

**RPO（恢复点目标）**：你能承受失去多少数据？如果你的 RPO 是1小时，你可以容忍在灾难性故障中丢失最多一小时的数据。在故障前最后一小时写入的所有内容都消失了。

**容错**：在组件失败时继续（在某种程度上）运行的能力。

**灾难恢复（DR）**：从灾难性故障中恢复的过程——数据中心火灾、区域范围的中断、意外的大规模删除。

这五个概念驱动本章中的每一个架构决定。

**多 AZ：在可用区故障中存活**

可用区（AZ）是区域内物理上独立的数据中心。AZ 被设计为独立的：独立的电源供应、独立的冷却、独立的网络基础设施。但它们足够近，使它们之间的网络延迟只有1-2毫秒。

**多 AZ 部署**将你的资源分布在一个区域内的两个或多个 AZ 中。如果一个 AZ 失败：

- 负载均衡器停止路由到失败 AZ 中的不健康实例
- 自动扩展组替换实例——但在*健康*的 AZ 中
- RDS 故障转移到健康 AZ 中的备用

Leo 的错误：他的自动扩展组没有配置为将替换实例限制到健康的 AZ。它被配置为维护 AZ 之间的平衡。当 us-east-1b 失败时，ASG 试图通过在 us-east-1b 中启动替换实例来平衡实例数量——那个失败的 AZ。

修复：配置 ASG 只启动到健康的 AZ，始终有最少两个 AZ 处于活跃状态。

更深层的教训：在生产中发生之前测试你的失败场景。

**模拟失败：混沌工程**

"我们怎么知道我们的多 AZ 设置实际上是否有效？" Maya 问。

"我们故意破坏一些东西，" Leo 说。

这听起来很鲁莽。实际上这是团队可以做的最负责任的事情。

**混沌工程**是有意向你的系统注入故障以验证其正确处理的实践。你故意终止一个 EC2 实例。你手动故障转移 RDS 实例。你阻止子网访问负载均衡器。

如果系统在你的 RTO 内自动恢复，你的设计是有效的。

如果没有，你在受控环境中学到了这一点——而不是在凌晨2点的生产事件中。

对于 Nimbus：Leo 编写了一个运行手册（记录的程序）来测试每个失败场景。每季度，他们会故意使一个组件失败，并测量恢复时间。如果恢复时间超过了 RTO，他们就修复设计。

**多区域：在区域性故障中存活**

大多数 AWS 故障影响的是可用区，而不是整个区域。区域性故障很罕见——但它们会发生。

对于区域性故障（或需要在全球各地有非常低延迟的全球应用程序），**多区域**是答案：在两个或多个 AWS 区域部署你的应用程序。

多区域引入了根本性的复杂性：

**数据复制**：你的数据库需要跨区域同步。在 us-east-1 写入的任何数据最终必须到达 eu-west-1。"最终"是问题所在——在时间延迟期间，区域对世界有略微不同的看法。

**主动-被动 vs 主动-主动**：

- **主动-被动**：一个区域提供所有流量。另一个是温备用。失败时，DNS 将流量切换到备用。更简单，但备用是空闲的，很贵。
- **主动-主动**：两个区域同时提供流量。构建起来更复杂（需要处理并发写入的冲突解决），但全球延迟更低，没有空闲资源。

**故障转移时间**：DNS 更改需要时间传播（取决于 TTL）。在传播窗口期间，一些用户仍然访问失败的区域。为非常低的 RTO 设计需要预先预热备用并提前最小化 TTL。

**灾难恢复策略：一个范围**

有四种常见的 DR 策略，从最便宜（恢复最慢）到最贵（恢复最快）：

**备份和恢复**（小时级 RPO/RTO）：

- 将所有内容备份到不同区域的 S3
- 灾难发生时：从头开始配置基础设施，从备份恢复
- 成本：非常低（你只为存储付费）
- 恢复时间：数小时

**导引灯**（分钟到1小时 RPO/RTO）：

- 在 DR 区域保持最小版本的应用程序运行（可以快速点亮的"导引灯"）
- 核心数据被复制（DR 区域中的 RDS 只读副本）
- 灾难发生时：在 DR 区域扩大规模，将只读副本提升为主，切换 DNS
- 成本：中等（你为小型运行的占用付费）
- 恢复时间：数十分钟

**温备用**（秒到分钟级 RPO/RTO）：

- 在 DR 区域运行完整应用程序的缩小版本
- 完全可运行，但容量减少
- 灾难发生时：扩大规模，切换 DNS
- 成本：较高（始终在缩小规模下运行完整栈）
- 恢复时间：分钟级

**主动-主动/多站点**（近零 RPO/RTO）：

- 在两个或多个区域以完整容量运行，同时提供流量
- 不需要恢复——如果一个区域失败，流量自动路由到另一个区域
- 成本：最高（两个完整规模的完整部署）
- 恢复时间：秒级（仅 DNS 传播）

对于现阶段的 Nimbus：温备用。他们负担不起主动-主动，但备份和恢复对他们的业务需求来说太慢了。

**Amazon RDS：多 AZ vs 只读副本 vs 多区域**

这三者是不同的，经常被混淆：

| 特性 | 多 AZ | 只读副本 | 多区域只读副本 |
|---|---|---|---|
| 目的 | 高可用性（故障转移） | 读取扩展 | 读取扩展 + DR |
| 数据同步 | 同步 | 异步 | 异步 |
| 故障转移 | 自动 | 手动提升 | 手动提升 |
| 可读？ | 否（备用是被动的） | 是 | 是 |
| 跨区域？ | 否（同一区域） | 是（可选） | 是 |
| 用于 | HA，RPO~0 | 读取负载 | 灾难恢复 |

关键洞察：多 AZ 备用是**同步的**——对主节点的每次写入在写入被确认之前都会在备用上确认。这意味着如果主节点失败，没有数据丢失。RPO = 0。

只读副本是**异步的**——有复制延迟。如果主节点失败，你提升了只读副本，你可能丢失几秒或几分钟的最近写入。RPO > 0。

## 优势与局限性

**多 AZ**：

- 生产工作负载必不可少——单 AZ 是单点故障
- AWS 服务（RDS、ElastiCache、EKS、ALB 都支持多 AZ）对此支持良好
- 与它提供的保护相比，相对较低的成本开销

**多区域**：

- 对于数据库来说正确实施很复杂
- 数据驻留/主权要求实际上可能需要它（欧盟用户数据必须留在欧盟）
- 全球用户的延迟优势来自路由，而非本身的多区域（对静态内容使用 CloudFront）
- 大多数组织不需要主动-主动；大多数对温备用投资不足

## 摘要

- **RTO**（恢复时间目标）：你可以宕机多长时间。**RPO**（恢复点目标）：你可以丢失多少数据。
- **多 AZ** 在区域内的可用区之间分布资源。保护免受 AZ 故障。
- **多区域** 在多个 AWS 区域部署。保护免受区域性故障，为全球用户提供更低的延迟。
- DR 策略（从最便宜到最贵）：备份和恢复 → 导引灯 → 温备用 → 主动-主动。
- RDS 多 AZ 备用：同步，自动故障转移，RPO = 0。只读副本：异步，手动提升，RPO > 0。
- 故意测试你的失败（混沌工程），在它们在生产中发生之前。

## 考试技巧

*SAA-C03 领域：设计弹性架构（领域2，任务2.2）*

- **RTO vs RPO**：期望考试给你需求（"组织最多可以忍受1小时的停机时间和没有数据丢失"），然后要求你选择正确的 DR 策略。映射：没有数据丢失 = 同步复制 = 多 AZ 或主动-主动。1小时停机时间 = 备份和恢复太慢；温备用可能有效。
- **多 AZ RDS vs 只读副本**：考试会询问 HA（多 AZ）vs 读取扩展（只读副本）。多 AZ 备用不可读。只读副本可以提升为主（手动）用于 DR。
- **导引灯 vs 温备用**：导引灯只有最少的基础设施运行（只有数据复制）。温备用有一个规模缩小但功能完整的应用程序运行。区别在于你可以多快扩大规模。
- **Aurora Global Database**：Aurora 特定的多区域主动-被动功能。主区域处理写入；次要区域用不到1秒的复制延迟处理读取。故障转移时，次要区域可以在1分钟内提升。考试信号："Aurora，多区域，RTO < 1分钟"。
- **AWS Backup**：EBS、RDS、DynamoDB、EFS、Storage Gateway 的集中备份服务。考试在备份和恢复场景中使用它。
- **Route 53 故障转移**：DR 的 DNS 层。主健康检查失败 → Route 53 路由到次要。传播时间意味着这不是即时的。

## 练习

**练习 1——回忆**

解释 RTO 和 RPO 之间的区别。为什么一个组织可能有低 RTO（不能长时间宕机）但高 RPO（可以容忍丢失最近的数据）？

*（提示：想想一个业务中，快速服务顾客比保存每笔交易更重要的场景。）*

**练习 2——考试练习**

*场景*：一家医疗公司在 `us-east-1` 的 RDS PostgreSQL 上运行患者记录系统。法规要求规定患者数据永远不能丢失（RPO = 0）。系统在灾难中最多可以忍受30分钟的停机时间（RTO = 30分钟）。成本是一个考虑因素。

哪种架构*最能*满足这些需求？

A) `us-east-1` 的 RDS 多 AZ，以及每日自动备份到 `us-west-2` 的 S3  
B) `us-east-1` 的 RDS 多 AZ，以及 `us-west-2` 中配置为手动提升的只读副本  
C) `us-east-1` 的 RDS 和 `us-west-2` 中带主动-主动复制的温备用  
D) 主在 `us-east-1`、次在 `us-west-2` 的 Aurora Global Database

**提示 1**：RPO = 0 意味着没有数据丢失，需要同步复制或近似同步。

**提示 2**：RTO = 30分钟意味着你有时间进行手动干预。你不需要完全自动的毫秒级故障转移。

**提示 3**：哪个选项提供多 AZ 保护（区域内 RPO = 0）加上跨区域 DR 能力？

**答案**：A

**解析**：`us-east-1` 中的 RDS 多 AZ 提供到同一区域备用的同步复制——AZ 故障的 RPO = 0。每日自动备份到 `us-west-2` 的 S3 提供跨区域 DR。在完整的区域性故障中，你从 `us-west-2` 的 S3 备份恢复——对于小型数据库在30分钟内。这具有成本效益，满足两个需求。

**为什么不是 B？** 只读副本是异步的——可能有复制延迟。如果主节点失败，自上次副本同步以来写入的数据会丢失。RPO > 0，违反了需求。

**为什么不是 C？** 跨区域的 PostgreSQL"主动-主动复制"实施起来很复杂，不是标准的 RDS 功能。这个选项技术上困难且昂贵。

**为什么不是 D？** Aurora Global Database 可以工作，但比 RDS 多 AZ 贵得多。场景说成本是一个考虑因素，而 Aurora 是高级定价。

## 彩蛋场景

Leo 构建了混沌工程运行手册。

每季度，在计划的维护窗口内，团队会：

1. 终止 us-east-1a 中的一个 EC2 实例，观察 ASG 是否正确替换它
2. 手动强制 RDS 多 AZ 故障转移，验证应用程序在60秒内重新连接
3. 通过调整 ASG 的可用区来模拟完整的 us-east-1b 故障
