# 第二十四章：随你成长的数据库

想象一座图书馆，最初只有两个书架和一位图书管理员。有那么一段时间，这就够了。管理员知道每样东西在哪里。读者的请求很快就能得到答复。后来图书馆扩大了：十个书架、二十个、四十个。还是同一位管理员、同一张服务台、同一个卡片目录。现在找任何东西都要排队等待。管理员并不慢——只是图书馆已经大到一个人无法再按原来的速度服务了。

解决办法不是找一位更快的管理员。而是换一种类型的图书馆。

**读副本：分发读流量**

大多数 Web 应用程序读取数据的频率远高于写入。一个浏览菜单的顾客会发出几十条 SELECT 查询。下一笔订单只会发出几条 INSERT/UPDATE 查询。比例通常是 10:1 甚至更高。

**读副本**是一个额外的 RDS 实例，它接收来自主库的所有写入的副本，并让这些写入可供 SELECT 查询使用。

工作原理：

1. 应用程序的写入（INSERT、UPDATE、DELETE）发送到主数据库
2. 主库将这些变更异步复制到读副本
3. 应用程序的读取（SELECT）分布到各个读副本
4. 读副本分担负载——每个处理总读流量的一部分

结果：主数据库只处理写入（以及可选的部分读取）。读副本处理读负载。对于 10:1 的读写比，添加一个读副本大致能把主库的总负载减半。

**重要限制**：复制是**异步的**。存在复制延迟——通常是毫秒级，但在负载下可能达到秒级。从副本读取可能会看到稍稍落后于主库的数据。对于大多数读取（浏览菜单、查看订单历史），这是可以接受的。对于"我的订单刚才成功了吗？"——从主库读取。

**读副本：细节**

- 每个主 RDS 实例最多可以有 15 个读副本（MySQL、PostgreSQL、MariaDB）
- 读副本可以在同一区域或不同区域（跨区域副本）
- 读副本本身也可以有读副本（链式）
- 读副本是独立的端点——你的应用程序必须把读取定向到副本端点
- 读副本可以提升为独立数据库（对灾难恢复很有用）

对于 Nimbus，Leo 添加了一个读副本。当 Priya 问他在切换流量之前是否测试过应用程序的读写路由逻辑时，他说："不会有问题的。"他并没有测试。接下来的四十分钟，他都在验证写入没有打到读副本端点。

**读后写一致性问题**

启用读副本三天后，来了一张支持工单。一家餐厅合作伙伴更新了菜单——下架了一个停售的菜品——然后打电话来确认它已被移除。客服坐席从 Nimbus 界面调出菜单。那个菜品还在。

二十秒后，它消失了。

异步复制延迟。写入（DELETE 菜单项）打到了主库。客服坐席的读取打到了副本，而副本还没收到这次变更。那一刻副本落后了 15 秒——不算反常，但看得见。

"那要是有人想利用最终一致性窗口来入侵呢？"Priya 问，"或者干脆——要是有顾客对一个刚被删除的菜品下了单怎么办？我们扣了顾客的钱，而餐厅根本没有这道菜。"

这是一个真实的一致性问题，而不只是用户体验上的小烦恼。

解决方案：识别哪些读取有一致性要求，并把它们路由到主库。

**可以走副本的读取**（最终一致性即可）：
- 顾客浏览餐厅菜单（陈旧 1-2 秒是无法察觉的）
- 订单历史查询（用户查看一分钟前的订单历史）
- 分析类读取（本周热门餐厅）

**必须走主库的读取**（要求读后写一致性）：
- 写入后立即进行的、应用程序需要确认写入成功的读取
- 下单后立即进行的订单状态读取
- 由餐厅管理界面触发的菜单读取（餐厅刚刚改过菜单）

应用程序在数据库连接层增加了一个路由提示：如果请求来自餐厅管理仪表板，路由到主库。如果来自顾客浏览，路由到副本。`X-Read-Consistency: strong` HTTP 头充当了这个信号。

"没那么难，"Leo 说，"你只需要知道哪些读取需要它。"

"还要写进文档，"Priya 说，"这样下一个添加新端点的人才知道该用哪个连接池。"

"如果主库挂了呢？"Maya 抢在 Tom 转向 Aurora 之前问道，"读副本会怎样？"

Leo 解释了副本提升。

**如果主 RDS 实例发生故障**，在 Multi-AZ 配置中，AWS 会自动故障转移到备用副本（这是另一种副本——同步备库，不是读副本）。Multi-AZ 备库成为新的主库。读副本继续提供读取服务，只是现在从新的主库复制。从应用程序的视角看，主库端点的 DNS 改为指向原来的备库，应用程序重新连接。

对 RDS PostgreSQL，故障转移通常需要 60-120 秒。在这个窗口期间，写入会失败。

**读副本提升**是一个独立的操作——也是一个独立的场景。如果你想把一个读副本变成一个独立的、可写的数据库（用于灾难恢复、迁移到新区域，或者主库已经没了、你需要提升而不是等待 Multi-AZ 故障转移），你可以把读副本提升为独立的主库。提升需要几分钟，之后该副本就不再从原主库复制——它成了自己的数据库。

"我们想过 us-west-2 的主库整个挂掉会怎样吗？"Priya 问，"不只是故障转移到 Multi-AZ 备库——而是整个区域。"

"如果区域故障，"Leo 说，"Multi-AZ 备库也在 us-west-2。两个一起挂。"

"所以对于真正的区域级灾难恢复场景，"Tom 说，"我们需要一个在 us-east-1 的、可以提升的读副本。"

"是的。一个跨区域读副本。我们还没有。"

"这每个月要花多少钱？"Tom 问。他已经知道答案会牵涉一个决策。

在 us-east-1 部署一个 db.r6g.large 的跨区域读副本：每月 $340（相同的实例成本）。加上用于复制的跨区域数据传输费：以 Nimbus 的写入量来说微不足道。总计：大约每月 $350，换一个灾难恢复副本。

**Amazon Aurora：重新思考数据库引擎**

Aurora 是 AWS 专有的关系数据库引擎，与 MySQL 和 PostgreSQL 兼容。它从零开始为云工作负载设计，重新构想了关系数据库存储层的工作方式。

在传统的 RDS 设置（MySQL、PostgreSQL）中，存储和计算紧密耦合。数据库引擎管理数据文件。复制把数据从主库拷贝到副本。副本必须重做每一个写操作。

这给复制速度设定了一个天花板：副本应用写入的速度，最快也只能和它处理复制日志的速度一样。在写入繁重的时期——批量导入、限时抢购、批量更新——副本可能会落后。复制延迟不是实现上的缺陷；它是这种架构的必然结果。

Leo 提出读副本时，Priya 立刻指出了这一点。"我们想过周五高峰期复制延迟飙到 30 秒会怎样吗？副本落后 30 秒。一位顾客下了单，厨房档期在主库里被预订了，但第二位查询副本的顾客看不到这个预订。两笔订单，一个档期。"

"那是一个库存一致性问题，"Leo 说。

"那恰恰就是一个库存一致性问题，"Priya 确认道，"这就是为什么库存读取——'这个菜品还有吗？'——必须走主库。"

Aurora 的架构直接解决了延迟问题。

Aurora 将存储与计算分离。它使用一个分布式、容错的存储层，自动把数据复制到三个可用区的六份副本中。计算层（数据库实例）坐落在这个存储层之上。

**这改变了什么**：

**读副本**：Aurora 副本不需要复制数据——它们本来就共享同一个存储层。这意味着：

- 最多 15 个共享存储卷的 Aurora 副本（普通 RDS 同样允许最多 15 个读副本，但每个都是一份完整的数据拷贝）
- 复制延迟通常低于 100 毫秒（而 RDS 在负载下可能是秒级）
- 副本可以在 30 秒内提升为主库（而不是几分钟）

**故障转移**：因为副本共享存储，故障转移快得多——提升不涉及数据传输，只是重定向写入。

**存储**：Aurora 以 10GB 为增量自动扩展存储，最高可达 128 TiB（较新的引擎版本为 256 TiB）。你永远不需要提前预配置存储。

**性能**：Aurora 宣称在同等实例类型下，吞吐量是标准 MySQL 的 5 倍、标准 PostgreSQL 的 3 倍。

你可能会想：如果所有副本共享同一份存储，这份存储不就成了单点故障吗？Aurora 的存储层会自动把数据复制成三个可用区中的六份副本。存储本身比任何单一的 RDS Multi-AZ 配置都更有韧性——它被设计成可以承受整个 AZ 的损失，零数据丢失，且无需故障转移。

第二个常见问题：既然 Aurora 兼容 MySQL/PostgreSQL，能不能在不改应用代码的情况下从 RDS PostgreSQL 迁移到 Aurora PostgreSQL？几乎可以。Aurora 的 PostgreSQL 兼容性意味着 Aurora 实现了 PostgreSQL 的有线协议，并支持绝大多数 PostgreSQL SQL 语法和特性。大多数应用程序零代码改动即可迁移。边缘情况是：少数 PostgreSQL 扩展在 Aurora 上不可用，一些系统目录查询会返回不同的值，某些管理操作也有差异。对于生产迁移，先用并行读流量测试，再切换写入。

对 Nimbus 来说，从 RDS PostgreSQL 迁移到 Aurora PostgreSQL 花了一个下午。应用程序指向了 Aurora 端点。那条菜单查询——在 Leo 添加了 Performance Insights 指出的、数据库负载头号消耗者所缺的索引之后——从 620ms 变成了 4ms。连接池不再触及 200 中的 198。P95 延迟降到了 28ms。

"这是一个不同的数据库引擎，"Leo 说，"而应用程序以为它还是原来那个数据库引擎。"

"那有意思的部分呢？"Maya 问。

"快速数据库克隆。"

**Aurora 定价：Tom 之问**

Aurora 的定价与 RDS 不同：

**实例定价**：按类型的实例定价与 RDS 类似。

**存储定价**：每 GB 每月 $0.10（按实际存储付费，自动扩展）。

**I/O 定价**：Aurora 按每个 I/O 请求（对存储的读/写）收费。对于写入密集型工作负载，这可能很可观。

"等等，"Tom 说，"我们要单独为 I/O 付费？"

"Aurora Serverless v2 和 Aurora I/O-Optimized 改变了这种定价模式，"Leo 说，"Aurora I/O-Optimized 不收 I/O 费，但存储和实例价格更高。对 I/O 密集型工作负载更划算。"

Tom 看了看这个权衡。对于读密集型的 Nimbus（大量菜单查询，很少写入），Aurora I/O-Optimized 可能反而更贵。标准 Aurora 定价可能更合适。

一个有用的经验法则：如果你的 I/O 费用超过 Aurora 总账单的约 25%，I/O-Optimized 很可能更便宜。对 Nimbus 的读密集型工作负载来说，I/O 费用很低——适用标准定价。对于像事件日志系统这样写入密集的工作负载，I/O-Optimized 可以显著降低成本。

这是高级工程师真实要做的成本决策：你必须了解工作负载的 I/O 模式才能做出正确选择。

如果你的工作负载小、稳定且可预测，RDS PostgreSQL 更简单，也明显更便宜——但如果你的流量不可预测、数据量增长超出你能提前预配置的范围，或者你需要 30 秒以内的自动故障转移，Aurora 的共享存储模型就配得上更高的基础成本。

**Aurora Serverless：不用考虑实例的扩展**

**Aurora Serverless v2** 是一种根据实际数据库负载自动扩展计算容量的配置。你不再选择固定的实例大小（db.r6g.large），而是以 Aurora 容量单位（ACU）设置最小和最大容量。

Aurora Serverless v2：

- 负载增加时在数秒内扩容
- 空闲期间缩容——而且从 2024 年底起，在没有连接时可以自动暂停一路降到 0 ACU（恢复约需 15 秒；自动暂停不适用于 RDS Proxy 或其他保持连接的代理）
- 成本：每 ACU-小时 $0.12（加上存储和 I/O）

对于流量起伏的工作负载——Nimbus 的周五高峰与周一早晨的安静——Serverless v2 在非高峰期降低成本，并在不预先配置的情况下应对高峰。

"所以在周五高峰，"Leo 说，"Aurora 自动扩容。周日早上我们几乎没有流量时，它缩回到最小值。"

"而我们只为正在使用的容量付费，"Tom 说。

"正确。"

在 Aurora Serverless v2 上跑了一个月后，Leo 调出了上一周的 ACU（Aurora 容量单位）曲线图。

图上呈现出两种截然不同的模式。工作日期间，数据库运行在 2-4 个 ACU——后台查询、ECS 健康检查、Glue ETL 作业和开发测试的低吟。周五晚上 18:00 到 22:00 之间，ACU 数攀升：

```
Friday 18:00  → 6 ACUs
Friday 19:00  → 14 ACUs
Friday 19:45  → 26 ACUs  (peak — pizza orders spike before NFL kickoff)
Friday 20:30  → 18 ACUs
Friday 21:00  → 12 ACUs
Friday 22:30  → 4 ACUs
Saturday 02:00 → 2 ACUs  (minimum)
```

扩展几乎是即时的——Aurora Serverless v2 以 0.5 ACU 为增量伸缩，它可以在数秒内增加容量，而预配置一个新的 RDS 实例需要数分钟。

"那个周五高峰花了多少钱？"Tom 问。

按每 ACU-小时 $0.12 计算：周五高峰是 4 个小时、平均 18 个 ACU → 高峰时段花费 $8.64。一周其余时间平均 3 个 ACU × 164 小时 × $0.12 = $59.04。整周总计：$67.68。

为应对周五高峰而预配置的同等实例（db.r6g.xlarge，4 个 vCPU，32 GB）将花费 $0.937/小时 × 168 小时 = **整周 $157.42**——无论周五的高峰是否真的出现。

"Serverless v2 一周 $67。按峰值预配置的实例一周 $157，"Tom 说，"降了 57%。"

"前提是这个数据库确实只在周五用 26 个 ACU 跑四个小时，一周其余时间只用 2 个 ACU，"Leo 说，"如果你的数据库整周都跑在持续的高负载上，预配置实例更便宜。节省来自波动性。"

Tom 缓缓点头。他正在把这条加进笔记里的一个规律：本季度每一个省钱故事都是同一个形状。你为用到的付费，而不是为可能需要的付费。S3 生命周期策略只为每个对象配得上的存储类付费。Lambda 只为调用时间付费。Fargate 只为任务的 CPU 和内存付费。Aurora Serverless v2 只为数据库实际消耗的 ACU 付费。

Tom 脸上是一副找到了自己一直在寻找的东西的表情。

**从一次糟糕的迁移中恢复：克隆、PITR 和后悔药**

迁移到 Aurora 两周后，Sam 在生产环境运行了一个数据库迁移脚本。这个脚本本应从 `menu_items` 表中删除 `legacy_menu_format` 列。他在运行时漏掉了自以为已经包含的 WHERE 子句。

结果不是删除一列。而是一条 DELETE 语句，从 `menu_items` 表中清掉了 40,000 行——大约 200 家餐厅的菜单数据，没了。

告警在 30 秒内触发。订单失败激增。菜单服务开始对 200 家餐厅返回空结果。

"它本来应该有一个 WHERE 子句的，"Sam 盯着控制台说。

传统的恢复路径：从最近的自动备份快照恢复。自动备份每 24 小时跑一次，完整的恢复加切换需要 20-40 分钟——在此期间*所有*餐厅都会熄火，而不只是受影响的那 200 家——而且备份之后下的每一笔订单都会丢失。

Leo 没有那么做。和标准 RDS 一样，Aurora 持续保留备份以支持**时间点恢复（PITR）**——你可以把集群恢复到备份保留窗口内的任意一秒，而不只是恢复到昨晚的快照。而且关键在于，恢复会创建一个*新的*集群；在你恢复期间，生产环境保持运行。

```bash
aws rds restore-db-cluster-to-point-in-time \
  --db-cluster-identifier nimbus-aurora-recovery \
  --source-db-cluster-identifier nimbus-aurora-cluster \
  --restore-to-time 2024-06-14T15:42:00Z
```

那个时间戳：15:42:00Z——Sam 运行迁移脚本的四分钟之前。恢复集群启动期间，生产环境的其余部分继续为未受影响的餐厅提供服务。一旦恢复集群可用，Leo 从恢复集群中导出了那 200 家受影响餐厅的 `menu_items` 行，并把它们插回生产环境。从告警到菜单完全恢复的总时间：不到 40 分钟——而且因为他是外科手术式地修复了这些行，而不是整库替换，15:42 之后下的订单一笔也没有丢。恢复集群事后被删除了；它已经完成了使命。

"我们损失了什么？"Maya 问。

有六笔在菜单短暂为空期间下的订单在结账时失败了——它们全都在 SQS 队列里，可以重放。没有任何客户数据被永久丢失。

"而这正是**快速数据库克隆**派上用场的地方，"Leo 在事后把团队召集起来说。Aurora 可以在几分钟内创建一个集群的**克隆**，与数据库大小无关，使用写时复制：克隆共享原集群的存储层，只有新增或更改的页面才占用额外空间。一份当前生产数据库的克隆既便宜、又快、还完全隔离——对克隆的写入永远不会触及生产环境。

"这意味着，"Priya 看着 Sam 说，"迁移脚本在跑生产之前，先在一份生产数据的克隆上测试。这是新规矩。"

Sam 点点头。他已经把它写在了一张便利贴上。

这幅图景里还有一件工具。Aurora MySQL——不是 Aurora PostgreSQL——有 **Aurora Backtrack**：一个能把集群*就地*回拨到特定时间点的功能，完全不需要恢复到新集群。如果 Nimbus 的集群是 Aurora MySQL，Leo 本可以在三分钟内把它回拨到 15:42——不过回拨整个集群也会一并回滚删除之后写入的那几笔合法订单，而外科手术式的 PITR 方案保住了它们。

"那要是有人想利用 Backtrack——或者时间点恢复——来入侵呢？"Priya 问，"攻击者能不能回拨审计日志或合规数据？"

Backtrack 需要 `rds:BacktrackDBCluster` API 权限，恢复操作则需要 `rds:RestoreDBClusterToPointInTime`——这些都是与普通数据库操作分开的 IAM 操作。标准的应用程序角色没有这些权限。只有拥有显式 IAM 策略授权的运维团队才能使用它们。她把这一条加进了 IAM 权限审查清单。

重要的注意事项：Aurora Backtrack 仅适用于 Aurora MySQL 兼容的集群，不适用于 PostgreSQL。Backtrack 窗口在集群创建时配置（1 小时到 72 小时，按回拨窗口的小时数收费）。而且 Backtrack 影响整个集群——你不能只 Backtrack 一张表或一组行。对于外科手术式的行级恢复——无论哪个引擎——Leo 用的"PITR 到临时集群"方案才是正确工具。

**Aurora Global Database：多区域读取**

**Aurora Global Database** 把 Aurora 扩展到多个 AWS 区域：

- **一个主区域**处理所有写入
- **最多五个次要区域**提供读取，复制延迟通常 <1 秒
- 次要区域可以在 1 分钟内提升为主区域（用于灾难恢复场景）

对于 Nimbus 的全球扩张，Aurora Global Database 将让伦敦的餐厅合作伙伴从欧盟读副本查询其本地菜单，而所有订单（写入）仍然通过美国的主库。

**RDS 与 Aurora：各自的选择时机**

| 因素 | RDS（PostgreSQL/MySQL） | Aurora |
|------|------------------------|--------|
| 成本 | 小型工作负载成本较低 | 基础成本较高，但扩展性更好 |
| 兼容性 | 完整 | 兼容 MySQL/PostgreSQL（有细微差异） |
| 最大副本数 | 15（每个都是完整数据拷贝） | 15（共享存储卷） |
| 副本延迟 | 可能达到秒级 | 通常 <100ms |
| 存储 | 固定预配置 | 自动扩展到 128 TiB（较新版本为 256 TiB） |
| 故障转移时间 | 60-120 秒 | <30 秒 |
| 无服务器选项 | 有限 | Aurora Serverless v2 |
| 最适合 | 稳定、可预测的工作负载 | 流量起伏、读取量大、需要快速故障转移 |

**超越关系型：专用数据库家族**

第 9 章介绍了 DocumentDB（兼容 MongoDB 的文档库）、Neptune（图关系）和 Keyspaces（兼容 Cassandra 的宽列库），第 10 章介绍了 MemoryDB（兼容 Redis 的持久化主数据库）。还有两个名字补全这个家族——你不需要深入了解它们，只需要能识别哪种数据形态指向哪个引擎，因为它们作为答案选项不断出现：

- **Amazon Timestream**：**时间序列**数据——传感器读数、指标、遥测。考试信号："随时间变化的 IoT 测量数据。"（在现实世界中，当前的产品是 Timestream for InfluxDB；最初的"LiveAnalytics"版本已于 2025 年停止接受新客户。）
- **Amazon QLDB**：你在较老的题目里可能仍会遇到它，作为"不可变的、可加密验证的账本"。AWS 已于 2025 年停售 QLDB（推荐改用 Aurora PostgreSQL）——把它当作过时的干扰项，而不是积木。

值得写在白板上的规则：**关系型行 → RDS/Aurora；大规模键值 → DynamoDB；文档 → DocumentDB；关系 → Neptune；时间 → Timestream；Cassandra → Keyspaces；持久化 Redis → MemoryDB。**对上了形态，题目就自己有了答案。

## 优势与局限

**Aurora 的优势**：

- 故障转移明显快于标准 RDS
- 最多 15 个延迟极小的读副本
- 自动扩展的存储
- 面向起伏工作负载的 Serverless v2
- 面向多区域部署的 Global Database

**Aurora 的局限**：

- 对小型、稳定的工作负载成本更高
- I/O 定价对写入密集型工作负载可能很可观（为此使用 I/O-Optimized）
- 细微的 MySQL/PostgreSQL 兼容性差异可能需要代码改动
- Serverless v2 从自动暂停中恢复（约 15 秒）以及快速扩容可能引发延迟尖峰

## 总结

第 23 章的 S3 生命周期工作通过把数据移到正确的存储层级降低了成本。Aurora 对计算做了等价的事：不再按峰值负载预配置并一直为它付费，而是让 Serverless v2 按需求伸缩。

- **读副本**从主库分流读流量。异步复制——轻微延迟对大多数读取是可接受的。把要求写一致性的读取（写入后立即的读取、管理界面的读取）路由到主库，而不是副本。
- **Aurora** 重新构想了存储层：分布式、跨副本共享、自动扩展。
- Aurora 提供：15 个读副本、<100ms 副本延迟、<30 秒故障转移、最高 128 TiB（较新版本为 256 TiB）的自动扩展存储。
- **Performance Insights**：在决定如何扩展之前，先识别造成数据库负载的具体 SQL 查询。一个缺失的索引可能让你根本不需要更大的实例。
- **CloudWatch 数据库指标**：DatabaseConnections（接近饱和意味着应用程序的连接池坏了）、CPUUtilization（持续高 CPU 意味着开销大的查询）、ReadLatency（随时间推移的退化往往是一张不断变大的表缺了索引）。
- **Aurora Serverless v2**：以 0.5 ACU 为增量自动伸缩计算容量。按 ACU-小时计费。对于峰谷差异大的工作负载，明显比预配置实例便宜。
- **时间点恢复（PITR）**：把 Aurora 集群恢复到备份保留窗口内的任意一秒——恢复到一个*新*集群，所以生产环境保持运行，你可以外科手术式地把丢失的行拷回去。
- **快速数据库克隆**：写时复制的集群克隆，几分钟内完成，与大小无关。便宜、隔离——用它在迁移脚本跑生产之前先在生产数据上测试。
- **Aurora Backtrack**（仅限 MySQL 兼容版——不支持 PostgreSQL）：把集群就地回拨到某个时间点，无需从备份恢复。窗口最长 72 小时。需要 `rds:BacktrackDBCluster` IAM 权限——限制给运维团队。
- **Aurora Global Database**：一个区域的主库，最多五个区域的读副本。
- **读副本提升**：跨区域读副本可以提升为独立主库，用于区域级灾难恢复。在灾难恢复收益与运行第二个完整实例的成本之间权衡。
- 较小、稳定、可预测的工作负载选择 RDS。需要规模、快速故障转移或应对起伏流量时选择 Aurora。

## 考试技巧

*SAA-C03 领域：设计高性能架构（领域 3，任务 3.3）*

- **Aurora 副本与 RDS 读副本**：Aurora 副本共享存储（接近零延迟，<30 秒故障转移）。RDS 读副本复制数据（可能有延迟，故障转移需要几分钟）。
- **Aurora Serverless v2**："自动扩展数据库容量"、"不可预测或突发的数据库流量"→ Aurora Serverless v2。注意：历史上只有 Serverless **v1** 能缩到零；v2 的最小值曾是 0.5 ACU，直到 2024 年底 v2 获得了自动暂停到 0 ACU 的能力。较老的考题可能仍然假设 v2 不能缩到零。
- **Aurora Global Database**："多区域数据库"、"在美国主库的情况下从欧盟低延迟读取"、"区域故障转移 RTO < 1 分钟"→ Aurora Global Database。
- **故障转移时间**：Aurora < 30 秒。RDS Multi-AZ 60-120 秒。两个都要记住。
- **按数据形态选专用数据库**："社交图谱 / 推荐 / 欺诈团伙"→ Neptune。"MongoDB"→ DocumentDB。"Cassandra"→ Keyspaces。"时间序列 / IoT 遥测"→ Timestream。"兼容 Redis 的*主*数据库（持久化）"→ MemoryDB（相对地 ElastiCache = 缓存）。"不可变加密账本"→ 老题目里是 QLDB（2025 年已停售）。
- **Aurora I/O-Optimized**：存储和实例成本更高，无按 I/O 计费。当 I/O 成本占大头时使用（写入密集型）。标准 Aurora：存储成本更低，按 I/O 付费。用于读密集型。
- **Aurora Backtrack**：把数据库就地回拨到特定时间点，无需从备份快照恢复。仅适用于 MySQL 兼容的 Aurora——对于 Aurora PostgreSQL，答案是时间点恢复（到新集群）或快速克隆。考试信号："意外删除数据，需要快速恢复而不必恢复完整备份"+ MySQL → Backtrack。
- **Aurora 快速数据库克隆**：写时复制克隆，几分钟内完成，与数据库大小无关。考试信号："快速、廉价地针对一份生产数据副本进行测试"→ 克隆，而不是快照恢复。

**练习 2 — SAA-C03 场景**

*场景*：一个社交媒体平台的 MySQL 数据库由于流量增长而出现高读取延迟。应用程序是读密集型的（95% 读，5% 写）。团队需要读取延迟保持一致，即使在流量高峰期间也是如此。他们需要停机时间最短的自动故障转移（目标 RTO < 30 秒）。数据量正在不可预测地增长。

哪种数据库方案最符合这些要求？

A) RDS MySQL Multi-AZ 配五个读副本  
B) Aurora MySQL 配 Aurora 副本和 Aurora Serverless v2  
C) RDS MySQL 换更大的实例类型（垂直扩展）  
D) DynamoDB 配 DynamoDB DAX 做读缓存

**提示 1**："RTO < 30 秒"——哪种服务能做到？检查每个选项的故障转移时间。

**提示 2**："高峰期间一致的读取延迟"——哪种服务的副本延迟接近零，而不是可能有秒级延迟？

**提示 3**："不可预测地增长的数据量"——哪种服务能自动扩展存储？

**答案**：B

**解释**：配 Aurora 副本的 Aurora MySQL 提供接近零的复制延迟（毫秒级，而非秒级），在负载下保持一致的读取性能。Aurora Serverless v2 在流量高峰期间自动扩展计算，无需过度预配置。Aurora 存储随数据增长自动扩展。Aurora 故障转移（提升一个副本）在 30 秒内完成——满足 RTO 要求。

**为什么不是 A？** RDS Multi-AZ 故障转移需要 60-120 秒——不满足 RTO < 30 秒。标准 RDS 读副本延迟在负载下可能达到秒级——"一致的"读取延迟更难保证。

**为什么不是 C？** 垂直扩展（更大的实例）增加了容量，但不分散读负载。数据库对读取来说仍然是单点故障。

**为什么不是 D？** DynamoDB 是 NoSQL——从 MySQL 迁移到 DynamoDB 需要重新设计数据模型和应用程序查询，这远超出了这次性能改进任务的范围。
