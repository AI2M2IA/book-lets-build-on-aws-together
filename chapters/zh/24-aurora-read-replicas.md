# 第二十四章：随你成长的数据库

Tom 的成本审查在数据库层发现了一些意外的东西。

Nimbus 正在运行 RDS PostgreSQL：Multi-AZ，db.r6g.large 实例。每月 $340。

"这看起来很高，"Tom 说，"但我不确定拿什么来比较。"

Leo 调出了性能指标。数据库 CPU 在周五晚餐高峰时峰值达到 85%。读查询正在排队。过去六个月中，P95 查询延迟翻了一番。

"数据库是瓶颈，"他说，"流量增加了。数据库没有随之扩展。"

"我们就不能把实例升级到更大的吗？"Maya 问。

"可以，"Leo 说，"这就是垂直扩展。我们从 r6g.large 升级到 r6g.xlarge。更多 CPU，更多内存。成本会更高，但能争取些时间。"

"但这并没有解决根本问题，"Priya 说，"最终我们会碰到最大的实例，需要不同的方法。"

"有两种方法，"Leo 说，"读副本，或者 Aurora。"

"有什么区别？"

这是个好问题。本章的其余部分就是答案。

想象一个繁忙的图书馆，有一位图书管理员负责归还书籍和回答读者问题。当图书馆变得热门时，就会排起长队。解决办法是：雇更多图书管理员——但只负责回答问题。归还书籍仍然通过原来的柜台。这就是读副本：处理读请求的额外容量，而所有写入仍然通过一个权威来源。Aurora 更进一步，重新设计了书架系统本身，使每个图书管理员共享同样的书架，始终看到同样的书，没有任何延迟。

**读副本：分发读流量**

大多数 Web 应用程序读取数据的频率远高于写入数据。浏览菜单的客户会发出数十条 SELECT 查询。下单会发出几条 INSERT/UPDATE 查询。比例通常是 10:1 或更高。

**读副本**是一个额外的 RDS 实例，它接收来自主库的所有写入的副本，并使这些写入可用于 SELECT 查询。

工作原理：

1. 应用程序写入（INSERT、UPDATE、DELETE）发送到主数据库
2. 主数据库将这些变更异步复制到读副本
3. 应用程序读取（SELECT）分布在读副本上
4. 读副本分担负载——每个处理总读流量的一小部分

结果：主数据库只处理写入（以及可选的一些读取）。读副本处理读负载。对于 10:1 的读写比，添加一个读副本大致将主库的总负载减半。

**重要限制**：复制是**异步的**。存在复制延迟——通常是毫秒级，但在负载下可能是秒级。从副本读取可能会看到稍微落后于主库的数据。对于大多数读取（浏览菜单、查看订单历史），这是可以接受的。对于"我的订单刚才成功了吗？"——从主库读取。

**读副本：详细信息**

- 每个主 RDS 实例最多可以有 5 个读副本
- 读副本可以在同一区域或不同区域（跨区域副本）
- 读副本本身也可以有读副本（链式）
- 读副本是独立的端点——你的应用程序必须将读取定向到副本端点
- 读副本可以提升为独立数据库（对灾难恢复很有用）

对于 Nimbus，Leo 添加了一个读副本。他更新了应用程序：

- 写操作 → 主库端点
- 菜单浏览、订单历史 → 副本端点

主库的 CPU 在高峰时从 85% 降至 41%。

Tom 看了看成本：相同实例类型的读副本与主库成本相同。从每月 $340 到 $680。

"我们花了双倍的成本大约将负载减半，"Tom 说。

"是的。但替代方案是升级到更大的实例类型，这样也会花更多钱，而且不会分发读负载。"

Tom 做了计算。他勉强地点点头。

"Aurora 是什么？"他问。

**Amazon Aurora：重新思考数据库引擎**

Aurora 是 AWS 专有的关系数据库引擎，与 MySQL 和 PostgreSQL 兼容。它从头开始为云工作负载设计，重新构想了关系数据库的存储层工作方式。

在传统的 RDS 设置（MySQL、PostgreSQL）中，存储和计算紧密耦合。数据库引擎管理数据文件。复制将数据从主库复制到副本。副本必须重做每一个写操作。

Aurora 将存储与计算分离。它使用一个分布式、容错的存储层，在三个可用区的六个副本中自动复制数据。计算层（数据库实例）位于此存储层之上。

**这改变了什么**：

**读副本**：Aurora 副本不需要复制数据——它们已经共享同一个存储层。这意味着：

- 最多 15 个读副本（普通 RDS 是 5 个）
- 复制延迟通常低于 100 毫秒（负载下 RDS 可能是秒级）
- 副本可以在 30 秒内提升为主库（RDS 需要几分钟）

**故障转移**：因为副本共享存储，故障转移更快——提升不涉及数据传输，只是重定向写入。

**存储**：Aurora 以 10GB 为单位自动扩展存储，最高可达 128TB。你不需要提前配置存储。

**性能**：Aurora 声称在同等实例类型下，吞吐量是标准 MySQL 的 5 倍，是标准 PostgreSQL 的 3 倍。

**Aurora 定价：Tom 的问题**

"成本是多少？"Tom 问。

Aurora 定价与 RDS 不同：

**实例定价**：按类型的实例定价与 RDS 类似。

**存储定价**：每 GB 每月 $0.10（你按存储的数量付费，自动扩展）。

**I/O 定价**：Aurora 按每个 I/O 请求（读/写到存储）收费。对于写入密集型工作负载，这可能很可观。

"等等，"Tom 说，"我们要单独为 I/O 付费？"

"Aurora Serverless v2 和 Aurora I/O-Optimized 改变了这种定价模式，"Leo 说，"Aurora I/O-Optimized 不收取 I/O 费，但存储和实例价格更高。对于 I/O 密集型工作负载更好。"

Tom 看了看权衡。对于 Nimbus 来说，它是读密集型的（大量菜单查询，很少写入），Aurora I/O-Optimized 可能会花费更多。标准 Aurora 定价可能更合适。

这是高级工程师做出的真实成本决策：你需要了解工作负载的 I/O 模式才能正确选择。

**Aurora Serverless：无需考虑实例即可扩展**

**Aurora Serverless v2** 是一种根据实际数据库负载自动扩展计算容量的配置。不是选择固定的实例大小（db.r6g.large），而是以 Aurora 容量单位（ACU）设置最小和最大容量。

Aurora Serverless v2：

- 负载增加时在秒内扩展
- 空闲期间缩减到接近零
- 成本：每 ACU-小时 $0.12（加上存储和 I/O）

对于流量可变的工作负载——Nimbus 的周五高峰与周一早晨的安静——Serverless v2 在非高峰期降低成本，并在不预先配置的情况下处理高峰。

"所以在周五高峰期，"Leo 说，"Aurora 自动扩展。周日早上当我们几乎没有流量时，它缩减到最小。"

"我们只为我们使用的容量付费，"Tom 说。

"正确。"

Tom 有一种找到了自己一直在寻找的东西的表情。

**Aurora Global Database：多区域读取**

**Aurora Global Database** 将 Aurora 扩展到多个 AWS 区域：

- **一个主区域**处理所有写入
- **最多五个次要区域**提供读取，通常有 <1 秒的复制延迟
- 次要区域可以在 1 分钟内提升为主库（用于灾难恢复场景）

对于 Nimbus 的全球扩张，Aurora Global Database 将允许伦敦的餐厅合作伙伴从欧盟读副本查询其本地菜单，而所有订单（写入）仍然通过美国主库。

**RDS 与 Aurora：何时选择各自**

| 因素 | RDS（PostgreSQL/MySQL） | Aurora |
|------|------------------------|--------|
| 成本 | 小型工作负载成本较低 | 基础成本较高，但扩展性更好 |
| 兼容性 | 完整兼容 | MySQL/PostgreSQL 兼容（有细微差异） |
| 最大副本数 | 5 | 15 |
| 副本延迟 | 可能是秒级 | 通常 <100ms |
| 存储 | 固定配置 | 自动扩展到 128TB |
| 故障转移时间 | 60-120 秒 | <30 秒 |
| 无服务器选项 | 有限 | Aurora Serverless v2 |
| 最适合 | 稳定、可预测的工作负载 | 可变流量、高读量、需要快速故障转移 |

## 优势与局限

**Aurora 优势**：

- 比标准 RDS 故障转移明显更快
- 最多 15 个延迟最小的读副本
- 存储自动扩展
- 可变工作负载的 Serverless v2
- 多区域部署的 Global Database

**Aurora 限制**：

- 小型、稳定工作负载的成本较高
- I/O 定价对于写入密集型工作负载可能很可观（为此使用 I/O-Optimized）
- 细微的 MySQL/PostgreSQL 兼容性差异可能需要代码更改
- Serverless v2 从接近零的冷启动可能导致延迟峰值

## 总结

- **读副本**从主库分发读流量。异步复制——对大多数读取来说轻微延迟是可以接受的。
- **Aurora** 重新设计了存储层：分布式，跨副本共享，自动扩展。
- Aurora 提供：15 个读副本，<100ms 副本延迟，<30 秒故障转移，最多 128TB 自动扩展存储。
- **Aurora Serverless v2**：根据负载自动扩展计算容量。适合可变流量。
- **Aurora Global Database**：一个区域的主库，最多五个区域的读副本。
- 对于较小、稳定、可预测的工作负载选择 RDS。当你需要规模、快速故障转移或处理可变流量时选择 Aurora。

## 考试技巧

*SAA-C03 领域：设计高性能架构（领域 3，任务 3.3）*

- **Aurora 副本与 RDS 读副本**：Aurora 副本共享存储（接近零延迟，<30 秒故障转移）。RDS 读副本复制数据（可能有延迟，故障转移需要几分钟）。
- **Aurora Serverless v2**："自动扩展数据库容量"、"不可预测或突发的数据库流量"、"扩展到零"→ Aurora Serverless v2。
- **Aurora Global Database**："多区域数据库"、"从美国主库以低延迟在欧盟读取"、"区域故障转移 RTO < 1 分钟"→ Aurora Global Database。
- **故障转移时间**：Aurora <30 秒。RDS Multi-AZ 60-120 秒。两个都要知道。
- **Aurora I/O-Optimized**：存储和实例成本更高，无每 I/O 费用。当 I/O 成本占主导地位时使用（写入密集型）。标准 Aurora：存储成本较低，按 I/O 付费。用于读取密集型。
- **Aurora Backtrack**：将数据库回滚到特定时间点，无需从备份快照恢复。仅适用于 MySQL 兼容的 Aurora。考试信号："意外删除数据，需要快速恢复而不需要恢复完整备份。"

**练习 2 — 考试练习**

*场景*：一个社交媒体平台的 MySQL 数据库由于流量增加而面临高读延迟。应用程序是读密集型的（95% 读，5% 写）。团队需要即使在流量峰值期间读延迟也保持一致。他们需要具有最短停机时间的自动故障转移（目标 RTO < 30 秒）。数据量正在不可预测地增长。

哪种数据库解决方案最符合这些要求？

A) RDS MySQL Multi-AZ 带五个读副本  
B) Aurora MySQL 带 Aurora 副本和 Aurora Serverless v2  
C) RDS MySQL 带更大的实例类型（垂直扩展）  
D) DynamoDB 带 DynamoDB DAX 进行读缓存

**提示 1**："RTO < 30 秒"——哪种服务能实现这一点？检查每个选项的故障转移时间。

**提示 2**："高峰期一致的读延迟"——哪种服务的副本延迟接近零，而不是可能有秒级延迟？

**提示 3**："数据量不可预测地增长"——哪种服务自动扩展存储？

**答案**：B

**解释**：带 Aurora 副本的 Aurora MySQL 提供接近零的复制延迟（毫秒，而非秒），在负载下提供一致的读性能。Aurora Serverless v2 在流量峰值期间自动扩展计算，无需过度配置。Aurora 存储随数据增长自动扩展。Aurora 故障转移（提升副本）在 30 秒内完成——满足 RTO 要求。

**为什么不选 A？** RDS Multi-AZ 故障转移需要 60-120 秒——不满足 RTO < 30 秒。标准 RDS 读副本延迟在负载下可能达到秒级——难以保证"一致"的读延迟。

**为什么不选 C？** 垂直扩展（更大的实例）增加了容量，但不分发读负载。数据库仍然是读取的单点故障。

**为什么不选 D？** DynamoDB 是 NoSQL——从 MySQL 迁移到 DynamoDB 需要重新设计数据模型和应用程序查询，这远超出这个性能改进任务的范围。
