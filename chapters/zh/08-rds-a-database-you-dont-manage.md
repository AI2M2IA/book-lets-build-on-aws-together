# 第8章：从不请病假的数据库管理员

凌晨3点，警报来了。

数据库服务器需要打安全补丁——那种需要重启的补丁。这个漏洞是真实的，补丁已准备好，而在不打扰客户的情况下应用它的窗口就是现在，就在半夜，当流量很低的时候。

Priya 是唯一醒着的人。她应用了补丁，重启了服务器，查看日志直到应用程序重新上线，然后在凌晨4点15分去睡觉。

早上她告诉了团队发生的事情。沉默了片刻。

"这会再发生，" Tom 说。

"每次有补丁都会发生，" Priya 说。"而且总是有补丁。必须有更好的方法来处理这个。"

有。只需要放弃他们需要自己管理数据库的想法。

**传统数据库问题**

当你在 EC2 实例上自己运行数据库时，你负责一切。

安装数据库软件。安全地配置它。当发现安全漏洞时给它打补丁。做备份。测试备份是否真的有效（大多数团队跳过这一步，直到为时已晚）。监控磁盘空间。为冗余设置复制。为主服务器宕机时配置故障转移。调整查询性能。在负载下管理连接。

这些都不是应用程序的功能。没有一个添加了功能。全都需要专业知识。

大多数开发团队不是数据库管理员。这造成了一个可预测的模式：数据库被安装、最低限度地配置，然后大多数时候被遗忘，直到出现灾难性的问题。

"我们是那样做的吗？" Maya 问。

Leo 的回答是沉默，这就等于是肯定。

**Amazon RDS：托管数据库**

**Amazon RDS**——关系数据库服务——处理运行关系数据库的运营负担，让你无需操心。

使用 RDS，AWS 管理：

- 安装和给数据库引擎打补丁
- 自动备份（存储在 S3，保留最多35天）
- 自动故障转移（当主数据库宕机时，备用数据库自动接管）
- 监控和指标
- 静态加密和传输加密
- 存储自动扩展（如果你启用它，磁盘在快满时自动增长）

你管理：

- 数据库架构（你表的结构）
- 你的查询和应用程序逻辑
- 谁可以访问数据库
- 哪种实例类型运行数据库
- 参数调优（尽管 RDS 提供合理的默认值）

类比：雇用一个从不请病假、从不犯配置错误、自动做每日备份、如果出了问题能自我修复的数据库管理员——但不写你的应用程序逻辑。

**支持的引擎**

RDS 支持几种流行的数据库引擎：

- **MySQL**——最广泛使用的开源关系数据库
- **PostgreSQL**——功能强大、可扩展，对复杂工作负载越来越受欢迎
- **MariaDB**——开源的 MySQL 分支，完全兼容
- **Oracle**——企业级，在有遗留要求的大型组织中使用
- **Microsoft SQL Server**——用于以 Windows 为主的环境
- **Amazon Aurora**——AWS 自己的 MySQL/PostgreSQL 兼容引擎，为云构建（我们在第24章深入介绍 Aurora）

对于 Nimbus，选择是 PostgreSQL。这是 Leo 所了解的，而且它很好地处理了关系数据。引擎选择对大多数应用程序来说没有你想象的那么重要——无论引擎如何，RDS 的运营优势都适用。

**多 AZ：接管的备用数据库**

这是完全改变可靠性计算的功能。

**多 AZ 部署**意味着 RDS 在与主数据库不同的可用区维护一个同步备用实例。提交到主数据库的每笔事务在确认之前都会同步复制到备用数据库。

当主数据库失败——硬件故障、AZ 中断、软件崩溃——RDS 自动故障转移到备用数据库。数据库端点的 DNS 记录会更新。你的应用程序重新连接到新的主数据库。

故障转移需要60-120秒。在这个窗口期间，你的应用程序会遇到连接错误。正确编写的应用程序应该能优雅地处理这个问题（带有退避的连接重试）。

备用数据库不是只读副本。它不提供读取流量。它的唯一目的就是准备好接管。

Tom："多 AZ 要多少钱？"

大约是单个实例成本的两倍——因为你实际上在运行两个数据库实例。备用数据库的成本与主数据库相同。

Tom："计划外的宕机要多少钱？"

他通过打开订单历史并估算他们周五高峰期每小时的收入来回答了自己的问题。

那天下午就启用了多 AZ。

**自动备份和时间点恢复**

RDS 每天自动备份。AWS 将这些备份存储在 S3 中（由 RDS 管理——你不会直接在 S3 控制台中看到它们）。你可以将数据库恢复到备份保留期内的任何时间点。

备份发生在可配置的**维护窗口**期间——一个低流量时段，通常在清晨。对于大多数引擎类型，备份不会造成停机时间。

**时间点恢复**是最有价值的功能之一：你可以恢复到保留期内的任何一秒钟。不只是每日快照——*任何一秒*。这是可能的，因为 RDS 除了每日备份之外还持续归档事务日志。

如果有人在下午2:37不小心运行了 `DELETE FROM orders WHERE 1=1`，你可以恢复到下午2:36。

Leo 在理解这个功能时明显松了口气。

"我们本来可以从我上个月删除的东西恢复吗？" 他问。

"在 RDS 之前？不行，" Priya 说。"在 RDS 之后？可以。"

**只读副本：扩展读取流量**

多 AZ 是关于可用性的。**只读副本**是关于性能的。

只读副本是你主数据库的异步副本，可以处理读取查询。对于大多数 RDS 引擎，你最多可以有五个只读副本（Aurora 更多）。

应用程序被修改为将读取查询发送到副本，将写入查询发送到主数据库。这分散了负载：主数据库处理写入和复杂事务；副本处理读取。

关键特征：

- 复制是**异步的**——主数据库和副本之间可能有小的延迟（滞后）。如果你写入一条记录并立即从副本读取，你可能还看不到它。
- 只读副本可以在同一区域或不同区域（跨区域副本增加延迟但支持地理分布）。
- 只读副本在灾难场景中可以提升为独立数据库。

对于 Nimbus：菜单查询是读取操作。订单历史是读取操作。绝大多数流量是读取流量。添加一个只读副本并将读取路由到它上面可以显著降低主数据库负载。

我们在第24章讨论 Aurora 时更深入地介绍只读副本。

**RDS 参数组和选项组**

考试中出现的两种配置机制：

**参数组**控制数据库引擎设置——如最大连接数、查询缓存大小、超时值。RDS 创建一个适合大多数情况的默认参数组。当你需要调整特定设置时，你创建自定义参数组。

**选项组**为某些引擎启用额外功能——如 Oracle 的本机网络加密或 SQL Server 的透明数据加密。大多数开源引擎部署不需要自定义选项组。

你不需要记住这些。只要知道它们存在用于自定义数据库引擎的行为。

## 优势与局限性

**为什么 RDS 很出色**：

- 消除了管理数据库软件的运营负担
- 自动备份和时间点恢复
- 用于自动故障转移的多 AZ，最小化 RTO
- 用于扩展读取流量的只读副本
- 内置的静态加密和传输加密
- 支持所有主要关系数据库引擎

**RDS 的局限性**：

- 你无法访问底层操作系统。你无法安装自定义操作系统级软件或更改操作系统设置。如果你的数据库有需要操作系统级访问的要求，你可能需要运行基于 EC2 的数据库。
- RDS 不是无服务器的（Aurora Serverless 是例外，在第24章介绍）。即使空闲也要为运行的实例付费。
- RDS 不是为水平分片数据库设计的。对于写入密集型关系工作负载的大规模扩展，你最终可能需要不同的架构。
- 对于非关系型（NoSQL）数据模式，DynamoDB（第9章）更合适。

## 摘要

- **Amazon RDS** 是托管的关系数据库服务。AWS 处理打补丁、备份、故障转移和存储管理。你处理架构、查询和应用程序逻辑。
- **多 AZ** 部署在不同 AZ 维护同步备用数据库。如果主数据库失败，在60-120秒内自动故障转移。
- 带有**时间点恢复**的**自动备份**让你可以恢复到保留期内的任何一秒。
- **只读副本**是服务读取流量的异步副本，减少主数据库的负载。复制滞后意味着它们可能稍微落后。
- 当你需要有托管运营的关系数据库时选择 RDS。当你需要更高性能或无服务器选项时使用 Aurora（第24章）。

## 考试技巧

*SAA-C03 领域3——任务3.3（数据库解决方案）*

- **多 AZ 用于高可用性，不是性能。** 备用数据库不提供读取流量。只读副本用于性能。这个区别经常被测试。
- **多 AZ 故障转移是自动的。** 你不需要配置发生的时间和方式。RDS 监控主数据库并自动触发故障转移。
- **复制滞后很重要。** 只读副本可能稍微落后于主数据库。如果你的应用程序需要读取它刚写入的数据，它必须从主数据库读取，而不是副本。这称为"读自己写一致性"。
- **自动备份保留0-35天。** 将保留期设为0会禁用自动备份。手动快照会永久保留，直到你删除它们。
- **RDS 存储自动扩展**防止磁盘满导致的中断。启用它。它只向上扩展，从不向下缩减。考试可能测试你是否知道这种不对称性。

**练习 2——考试练习**

*场景*：一家公司在 RDS 上运行生产 PostgreSQL 数据库。由于整天运行的报告查询，数据库的读取流量很高。团队也担心数据库可用性——他们在故障场景中不能承受超过几分钟的停机。他们希望最小化报告工作负载对主数据库的影响。

哪种 RDS 功能组合*最能*解决这两个问题？

A) 启用多 AZ，并针对备用实例运行所有查询  
B) 启用多 AZ 用于故障转移保护，并为报告查询创建只读副本  
C) 创建多个只读副本，并禁用多 AZ 以降低成本  
D) 更频繁地进行手动快照，如果主数据库失败则从快照恢复

**提示 1**：两个需求是：（1）故障期间的可用性，（2）卸载读取。哪些功能解决了哪个需求？

**提示 2**：多 AZ 提供自动故障转移。备用数据库不提供读取流量。所以单独的多 AZ 不能解决读取问题。

**提示 3**：只读副本提供读取流量。多 AZ 提供故障转移。你需要两者。

**答案**：B

**解析**：多 AZ 在不同 AZ 的备用数据库上提供自动故障转移——这解决了可用性需求。只读副本允许报告查询在不影响主数据库的情况下运行——这解决了性能需求。两种功能可以同时使用。

**为什么不是 A？** 多 AZ 备用数据库无法提供读取流量。它专门用于故障转移。尝试直接查询它不受支持。

**为什么不是 C？** 只读副本有助于读取性能，但不提供自动故障转移。如果主数据库失败，你需要手动提升只读副本——这需要时间，而且不是自动的。

**为什么不是 D？** 手动快照恢复数据库的完整副本——对于大型数据库来说是一个更长的过程（可能需要数小时）。这不满足"几分钟停机时间"的需求。
