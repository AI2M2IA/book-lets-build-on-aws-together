# 第0章：开始之前

Maya 站在家族餐厅的吧台后面，那是一个周五的晚上，一个念头突然击中了她。

餐厅已经开了四年。食物很好——人们驱车穿越整个城市只为吃上那份玉米饼。但每次有人打电话点餐，总是占线。每次有人开车过来取一份他们其实从未下成的订单，都是因为他们打过电话、最终放弃了。

订单在流失。钱还没进门就溜走了。

而最糟糕的是，没有人能指出某个明显的、戏剧性的失败点。

没有爆炸。没有崩溃。没有恶意破坏者，没有系统宕机的横幅，也没有明显损坏的屏幕。

这只是摩擦。细小的、悄无声息的、代价高昂的摩擦。

"我们每个周五都在丢订单，" Maya 对着空气说道。"不是因为食物不好。是因为没人能联系上我们。我们需要一个网站。"

她的表哥 Tom 从他正在手动更新的电子表格中抬起头。Tom——一位曾经的系统管理员，用服务器机房换来了家族生意——过去两年一直在管理餐厅的"系统"——这个说法其实过于好听，实际上不过是一个共享的 Google 表格和一块白板。

"网站，" 他重复道。"那网站究竟住在哪里？"

Maya 张了张嘴，又闭上了。

她完全不知道。

**一个听起来简单的问题**

网站住在哪里？

你可能从来没想过这个问题。大多数人都没有。你在浏览器里输入一个地址，页面就出现了，在这两件事之间的某个地方，魔法发生了。

直到有一天，你成了那个要为这份魔法付钱的人。

但这不是魔法。这是计算机。

在世界的某个角落，就在此刻，有一台物理计算机——一台服务器——正在存储着构成那个网站的文件。当你的浏览器请求那个页面时，你的请求穿越互联网，到达那台计算机，然后计算机把文件发回给你。

就是这样。这就是网站。

所以真正的问题是：*谁的*计算机？

这个问题把 Maya 引到了白板前。而白板引出了之后的一切。

**三个选项，一个问题**

回到餐厅，Maya 和 Tom 在白板上草拟了几个选项。

**选项一**：买一台计算机，把它安置在餐厅里，从这里运行网站。这叫做"本地部署"（on-premises）——你自己的建筑，你自己的机器。你会在整本书中看到这个术语。

Tom 在这个选项旁边写下了"电费"和"坏了怎么办"。然后他停顿了一下，开始在手机上认真查询价格。一台能承载一个中等规模 Web 应用的服务器，前期成本大约在八百到两千美元之间。再加上一台 UPS 不间断电源、一台可管理交换机和一台防火墙设备，在你为哪怕一个小时的运行付费之前，成本就已经接近四千美元了。然后是电费、散热需求，以及每三到五年就得更换硬件的事实。

"如果把所有因素都算进去，这每个月要花多少钱？" Tom 问，与其说是问 Maya，不如说是在问自己。

他算了一笔账。一台 2,000 美元的服务器按四年摊销：每月约 42 美元。每天 24 小时运行、功耗 300 到 500 瓦的电费：每月大约 25 到 40 美元。一条能承受真实流量的商用级互联网线路：每月 100 到 300 美元。此外，每过三到五年，这一切还得从头再来一遍。硬件不会永远好用。

"所以每月大约在 170 到 400 美元之间，" Tom 说，"这还不算请人来修的钱。而它一定会坏。"

"如果它在周五晚上 11 点坏了怎么办？" Maya 问。

Tom 知道怎么修服务器——在做系统管理员的前半生里，他干的就是这个。这正是问题所在。他清楚地知道成为唯一能修机器的人意味着什么：凌晨 2 点的电话、被故障硬盘吞掉的周末、因为电源烧坏而中途取消的假期。Maya 做不来这些，而 Tom 也不想成为"单点故障的单点故障"。餐厅的系统会陷入黑暗。订单会停止。而且没有任何冗余——一台机器，没有备份方案。

"那如果我们增长得很快呢？" Maya 补充道。"我们会按今天的业务量买服务器，可如果六个月后我们需要三倍的容量呢？我们就得再买硬件，等发货，再安装……"

Tom 在选项一下面加上了"无法扩展"、"更换成本"和"凌晨 2 点谁来修"。这一栏越来越长了。

**选项二**：付钱给一家托管公司，让他们运行一台小型服务器。便宜，简单。2008 年用来托管个人博客还行。对于一个不断成长的企业来说，可能不够灵活。

"如果我们突然同时收到一千个订单怎么办？" Maya 问道。

Tom 在选项二旁边加上了"无法扩展"。

他在调研时看过几个共享主机套餐。每月八美元，每月十二美元。但每个套餐都有硬性限制：磁盘空间、带宽、并发连接数。有一个很受欢迎的套餐在标题里吹嘘"无限带宽"，却把限速政策埋在服务条款的第四段里。一百个并发访客，服务就开始降级。两百个，网站直接宕掉。

"那不叫无限，" Tom 说。"那叫'在关键时刻之前都无限'。"

托管公司的独立服务器更有希望一些——每月 80 到 200 美元能买到点真东西——但团队仍然得自己配置和维护它。而且他们买到的仍然是一个固定的上限，没有任何随需求弹性伸缩的能力。

"每一天容量不够用，我们都在流失客户；每一天容量用不满，我们都在浪费钱，" Maya 说。"没有办法做到刚刚好。"

"除非这个上限能跟着我们移动，" Tom 说。

他本来没打算把这句话当作过渡，但它正好是。

**选项三**：别的什么。他们一直在听说的东西。一种叫做"云"的东西。

Tom 在白板上画了一朵云。一个真实的云朵形状，就像小孩画的那种。

"我其实不知道那是什么意思，" 他承认道。

"我也不知道，" Maya 说。

这就是一切的开始。

**"云"究竟是什么**

让我们立刻把这个说清楚，因为"云"这个词是技术领域里被滥用最多、解释最少的术语之一。

云不是一个让你的数据漂浮其中的神奇地方。

云是别人的计算机。

就是这样。当你把一张照片保存到 iCloud 或 Google Drive，你的照片被存储在苹果或谷歌拥有的某台物理计算机上，放在世界某处的一栋建筑里。当你使用 Netflix，你正在观看的视频正在从全球各地数据中心的物理服务器上发送过来。

"云"只是意味着：你通过互联网访问的计算机，你不必自己拥有或维护。

而亚马逊——没错，就是那家送快递的公司——建造了世界上最大的这类计算机集合之一。他们称之为亚马逊网络服务，或者 AWS。

**电网类比**

把它想象成电网。

一百年前，如果你想开一家工厂，你得自己建发电厂。你得雇工程师来运营它。你要为燃料、为维护、为让灯保持常亮的专业知识付钱。如果发电机坏了，你的工厂就停了。如果需求增长了，你就得建一台更大的发电机——一个昂贵而缓慢的过程，需要提前数年预测未来需求，并在你还不知道是否真的需要之前就投入资本。

然后电网出现了，游戏规则彻底改变。

你接入电网，只为你实际消耗的电付费。不需要发电厂。不需要维护团队。不需要燃料合同。需要的时候，容量就在那里。不需要的时候，你不为它付钱。你可以从一个小作坊起步，成长为一家大工厂，而无需为不确定的未来规模押上资本赌注。

云计算就是把同样的理念应用到计算上。AWS 建好了发电厂——实际上是分布在几十个国家的数千座发电厂，由一支支工程师团队运营，他们全部的职业使命就是让那些机器持续运转。企业接入进来，按使用量付费。基础设施是共享的、由专业人员维护的、随需可用的。你不再操心物理层，专注于你真正要构建的东西。

电网类比有一个值得指出的不同之处：电只有一种。而云计算有许多种类。存储、计算、数据库、网络、机器学习、安全——每一种资源都有自己的定价、自己的权衡和自己适用的场景。电网均匀地输送同一种东西，而 AWS 提供的是一个包含数百项服务的目录。这本书就是你浏览那份目录的指南，从最重要的服务开始。

**为什么是亚马逊？**

这是个合理的问题。亚马逊最初是一家书店。

事情是这样发展的：亚马逊增长得如此之快，以至于他们需要巨大的计算能力来运行自己的系统。他们建造了数据中心。他们雇用了工程师来管理这些中心。他们在大规模运行计算机方面变得非常、非常擅长。

然后亚马逊的某个人有了一个想法：如果我们把这些计算能力的访问权卖给其他人呢？

2006 年，亚马逊网络服务正式上线。如今，AWS 运行着互联网的相当大一部分。你用来订机票的网站、追踪你快递的应用程序、你昨晚看的流媒体服务——它们中至少有一部分很可能运行在 AWS 上。

这不是垄断。Google Cloud 和 Microsoft Azure 是真正的竞争者。但 AWS 是第一家，它规模庞大，而这本书就是讲 AWS 的。

**认识团队**

Maya 不是独自建造 Nimbus 的。

她首先打电话给 Tom——当然如此。Tom 有电子表格、供应商联系方式，以及真正执行一个想法所需要的那种固执。

Tom 是那种会认真读服务条款的人。不是因为他害怕，而是因为他相信：理解一件事的真实成本——金钱、风险、时间——是做出好决定的唯一途径。白板上那些越列越长的反对意见，不是悲观主义。那是 Tom 在做 Tom 一贯做的事：在做出任何承诺之前，先把现实世界的代价算清楚。当所有人还在为一个东西能做什么而兴奋时，他会问"这每个月要花多少钱？"。这经常为公司省下钱，偶尔还能在灾难被定性为灾难之前就把它扼杀掉。

Tom 认识一个开发者。Leo。二十四岁，自学成才，那种在你还没解释完问题之前就已经做好原型的人。他来参加第一次会议时带着一台笔记本电脑和一个做了一半的应用程序。

"我已经把它部署上去了——哦，" 他说，打开了屏幕。他脸上的表情清楚地表明他发现了某种意料之外的东西。"我想我把它部署到了某个地方。"

确实部署了。在一台他没完全搞明白的服务器上，在一个他没有刻意选择的区域里，运行着一定会在高负载下崩溃的代码。

他们立刻喜欢上了他。

Leo 动作很快。有时太快了。他拥有开发者的天赋——能造出可以运行的东西，也有开发者的盲点——那些*此刻*能运行、却在悄悄积累技术债的东西。他对待错误信息的方式，就像有些人对待警告标签——有参考价值，但不一定有约束力。面对潜在问题，他的默认回应是"没事的"，而他说对的次数足够多，以至于团队过了好一阵子才学会：当他用那种特有的、漫不经心的笃定语气说这句话时——那意味着他其实没去检查——就该警惕了。

Priya 是后来才加入的——由共同的朋友介绍。计算机科学学位，专注于安全，那种在周末晚上阅读著名技术故障事后分析报告的人。她在第一次会议上只提了一个问题。

"有人想过如果有人试图入侵会发生什么吗？"

沉默。

"欢迎加入团队，" Maya 说。

Priya 表达热情的方式是一份详细的威胁模型。她真心享受架构评审的过程。她是那个在没人要求的情况下就把 AWS 安全白皮书读完并标出相关章节的人。团队还会发现，对于那些他们尚未想到的事情，她的判断总是可靠地正确。她提问的方式，就像一位优秀的结构工程师检查承重墙——不是因为她预期它们会垮，而是因为想知道它们是否牢固，唯一的办法就是仔细察看并记录所发现的一切。

"我们有没有想过，如果……会发生什么"——Priya 的大多数发言都是这样开始的。随着时间推移，团队逐渐明白：正是这个问题，比任何其他问题都更有效地在灾难演变成事故之前阻止了它们。

四个人在一起，做出了一个能运转的东西。Maya 看见产品。Tom 盯住成本。Leo 把它造出来。Priya 守护它的安全。你正在读的这本书，就是他们所学到的一切的记录。

**这本书是什么**

这是 Nimbus 的故事。

Nimbus 从一个餐厅订单系统开始，变成了更大的东西。在它成长的过程中，它遇到了所有成长中的软件都会遇到的每一个问题：无法承受流量的系统、丢失的数据、在最糟糕的时刻宕机的服务器、比营收增长更快的成本。

每次他们遇到问题，他们都找到了一个专门为解决这类问题而设计的 AWS 服务。

这本书通过跟随这段旅程来教你 AWS。

你不仅会学到每个服务*是什么*，还会学到它*为什么*存在，*何时*使用它，以及——同样重要的——*何时不*使用它。每个工具都有权衡。每个决定都有成本。这就是高级工程师理解的、而初级工程师还在学习的东西。

当你读完这本书，你将准备好参加 AWS 解决方案架构师助理考试（SAA-C03）。不仅如此：你将准备好走进真正的技术对话，并站稳脚跟。

这是承诺。

下面是这一承诺在实践中的样子，逐部分展开。

**第 1–5 章：基础**。读到第 5 章结尾时，你将理解云计算究竟是什么、它为什么存在，如何控制谁能访问你的 AWS 账户、以及为什么 root 账户让安全工程师不寒而栗，你的服务器住在哪里、为什么地理位置很重要，EC2 实例是什么、如何为它们选型，以及如何在云中存储文件而不把它们绑死在某一台机器上。这些章节涵盖的是每个 AWS 架构师都习以为常的概念——但第一次接触时却没有人解释得足够清楚。

**第 6–10 章：数据与扩展**。这一部分讲的是应用增长之后会发生什么。你会看到 Nimbus 撞上扩展的天花板——一台服务器，太多用户，没有增长空间——然后看着他们用负载均衡器、自动扩展、托管数据库和缓存来解决它。读完这一部分，你将理解真实的生产系统如何应对波动的负载，以及为什么数据库几乎总是第一个瓶颈。

**第 11–17 章：网络与安全**。这里的概念在你需要它们之前都显得抽象。VPC、安全组、DNS、证书管理、密钥管理。读完这一部分，你将理解流量如何在云应用中穿行，以及如何阻止它流向不该去的地方。

**第 18–22 章：弹性与现代架构**。多区域设计、解耦系统、无服务器计算、容器。这些章节涵盖的是把生产系统与玩具项目区分开来的架构模式。读完这一部分，你将明白为什么经验丰富的架构师在思考功能之前先思考故障。

**第 23–26 章：性能与数据**。存储层级、生命周期策略、Aurora 与只读副本、网络性能，以及把原始数据变成答案的分析服务。读完这一部分，你将理解如何让一个系统更快——以及如何知道它究竟哪部分慢。

**第 27–30 章：成本优化**。AWS 定价很复杂，但它遵循原则。读完这一部分，你将理解如何读懂一份 AWS 账单，如何在确定架构之前预测成本，以及如何分辨哪些优化重要、哪些不重要。

**第 31–34 章：像架构师一样思考**。最后一部分从具体服务中退后一步，讨论推理过程本身。什么时候该增加复杂性？什么时候该保持简单？当存在多个合理的替代方案时，如何为一个决定辩护？这是最难、也最有价值的部分。


**开始之前的几件事**

**这本书假设你对云计算几乎一无所知。** 如果你听说过 AWS 但从未使用过，你来对地方了。如果你从未听说过 AWS，你也来对地方了。

**这本书不假设你是一名开发者。** Maya 不是。Tom 勉强算是。你不需要写代码来理解架构。你需要理解问题和解决方案。

**这本书有时会故意犯错。** 团队会犯错误。他们会选择错误的服务。他们会跳过一个将来会后悔的安全步骤。他们会过度配置，也会配置不足。这就是他们学习的方式，也是你学习的方式。

**考试技巧都是真实的。** SAA-C03 是一个真实的考试。每章末尾的情景题被设计得像真实的考试题一样。如果你能回答它们，你就在正确的轨道上。

还有一件事。

拿着铅笔读这本书，或者一个笔记应用，或者一份持续记录"我认为答案是……"的时刻的清单。

在团队做决定之前暂停一下。自己先做出判断。然后继续读，看看你是否会做出同样的权衡。

你也许会好奇：为什么要在一本 AWS 认证书里跟随一家餐饮初创公司的故事？答案是：当你已经亲身感受过问题，抽象概念才会真正记住。在你遇见每一个 AWS 服务之前，Nimbus 都会先需要它。

**如何阅读这本书**

每一章都遵循同样的结构。你会看到团队遇到一个问题——某个东西坏了、某个东西慢了、某个东西无法扩展。然后你会看着他们弄清楚究竟发生了什么。然后相关的 AWS 服务登场，被命名并被解释。然后是对技术细节的更深入探讨。然后是权衡、练习，以及一个为下一章做铺垫的场景。

每章末尾的练习分为三种类型。回忆练习检验你是否理解了刚刚读过的内容。SAA-C03 情景题在形式和感觉上都像真实的考题——猜答案之前先读提示，因为推理过程和答案同样重要。架构挑战没有唯一正确答案；它们的存在是为了让你练习思考，而不是背诵结果。

如果你读这本书主要是为了通过 SAA-C03，请密切关注"考试技巧"部分。它们标出了考试真正考查的内容，包括常见陷阱和考试使用的特定词汇。如果你读这本书是为了建立实践理解，那么架构挑战才是最深层学习发生的地方。

两件事同时成立：这既是一本备考书，也是一本实践指南。故事中出现的每一个概念，都同样出现在考试领域目标中。Nimbus 的旅程不是点缀。它就是课程本身。

最后关于角色再说一句。Maya 经常问"等等——可我们*为什么*要那样做？"。这是有意为之的。她是读者的化身。每次她这么问，都是因为一个真正的学习者也会问同样的问题。请仔细跟随她的提问——它们标记着推理最关键的时刻。

**关于主动阅读的一点实用建议。** 这不是一本可以被动阅读的书。章节之间层层递进——第 4 章做出的架构决策制造了第 7 章要解决的问题，第 7 章接受的权衡产生了第 27 章要化解的成本。如果你跳到自己感兴趣的服务，上下文就会缺失，推理也不会产生同样的效果。

读的时候带上可以写字的东西。当团队即将做出决定时，合上书一会儿，先做出你自己的判断。你会选哪个服务？你会接受哪种权衡？然后再往下读。把你的直觉与团队的决定相比较——并理解它们在哪里出现分歧——才是真正的学习发生的地方。

当你在章节末尾遇到情景题时，请在做出选择之后再读提示。提示是为纠正最常见的错误答案而设计的，这意味着只有当你已经选定了一个方向之后，它们才最有用。

如果你是作为 SAA-C03 备考的一部分来阅读这本书，请把节奏放慢到可以在章节之间反思。每天一到两章比周末突击马拉松更有效。这些概念会复利式叠加——考试考查的是跨服务的推理，而不只是单个服务的知识，而这种推理需要时间来固化。

如果有什么地方不清楚：团队会在你开口之前先提出那个问题。Maya 问"等等——可我们*为什么*要那样做？"正是为了这个。如果你对团队做出的某个决定感到困惑，等两段。Maya 很可能正要问同样的问题。

开始之前还有最后一件事。Tom 会在整本书中不断报价格，因为 Tom 对所有东西都报价格。那些数字——连同服务限制和功能细节——反映的是截至 2026 年年中的 AWS 文档。AWS 经常变动它们，而且价格几乎总是往下调。每个决策背后的推理会一直成立；具体的美元数和限制未必。当花的是你自己的钱时，请像 Tom 那样去查阅最新的 AWS 文档。

**还有一句诚实的提醒**：云并不总是正确答案。
对大多数初创公司和成长期公司来说，答案显然是云——Tom 在白板前算的那笔账就是证明——但确实存在一些真实的情形，从机密数据到大规模稳定的工作负载，自己拥有硬件才是赢家。团队会在下一章梳理这些例外情况——当 Tom 坚持要在拥抱云之前先听一听反对云的理由时。

**这种方法的优势**：通过连续叙事学习，让概念在获得名字之前就有了背景。当你读到 IAM 或 RDS 时，你已经感受过它们所解决的问题——因为 Nimbus 先感受过了。这使得记忆更深刻，权衡推理比死记硬背特性列表更自然。

**需要注意的局限性**：本书涵盖 AWS SAA-C03 解决方案架构师助理课程。这是相当大的范围，但并非每个 AWS 服务——而且生产架构总是涉及特定于你所在行业和规模的服务和约束。Nimbus 的故事是虚构的；真实的初创公司会以更凌乱的理由做出更凌乱的决定。用这本书来建立推理能力，而不是复制架构。

## 摘要

Nimbus 始于一个任何小企业都可能遇到的问题：客户联系不上他们，而没有人能指出某个明显的、戏剧性的失败点。这只是摩擦——细小、无声而昂贵。那次白板讨论没有产出一个解决方案。它产出了一个值得追问的问题：云究竟是什么？而这个答案最终比任何人预期的都更重要。

- **云**是通过互联网按需访问计算资源——别人的计算机，你无需自己拥有或维护。
- 三种托管选项：本地部署（你的硬件，你的成本，需要你自己的专业知识）、第三方小型服务器托管（有限，无法扩展）、云（按使用付费，随需求扩展）。
- 本地部署的成本是真实存在的，而且经常被低估：硬件折旧、电力、互联网线路和维护所需的专业知识，在你写下第一行应用代码之前就已显著累加。
- **AWS** 于 2006 年推出，当时亚马逊将其数据中心基础设施向外部客户开放。它仍然是最大的云提供商，其后是 Microsoft Azure 和 Google Cloud。
- 云并不总是正确答案——但对大多数需求不可预测、团队规模小的初创公司和成长期公司来说，答案显然是云。

## 考试技巧

*SAA-C03 考试领域：跨领域——云概念基础*

- **考试中的云**是指通过互联网按需、按使用付费的计算。这是一种交付模式，而非一种技术。
- **CapEx 与 OpEx**：本地基础设施是资本支出（CapEx——预先购买硬件）。云是运营支出（OpEx——按期使用费用）。考试场景中询问"消除前期成本"或"从 CapEx 转变为 OpEx"指向云的采用。
- **云的优势**：无前期硬件投入，弹性扩展，只为使用的部分付费，无需管理物理基础设施。"流量不可预测"或"小团队，没有硬件专业知识"的场景是云的有力信号。
- **本地部署（on-premises）**指在你自己的设施中运行你自己的硬件。考试经常将本地部署架构与云替代方案进行对比。
- **AWS 不是唯一的云**——Azure 和 GCP 是真正的竞争者——但 SAA-C03 考试是 AWS 专项的。你不会被要求比较不同的提供商。
- **规模经济**：AWS 能实现更低的单位成本，因为它聚合了成千上万客户的需求。这是 AWS 考试框架中云相对于本地部署的明确优势之一。当你在考试中看到"云的好处"时，规模经济永远是一个有效答案。
- **云计算的六大优势**（依据 AWS 文档）：以可变支出取代固定支出、受益于大规模的规模经济、停止猜测容量、提高速度和敏捷性、停止把钱花在运营数据中心上、数分钟内实现全球部署。这些表述会原封不动地出现在关于组织为何上云的考题中。
- **考试中的敏捷性（Agility）**指的是以较低的单次尝试成本快速试验和部署的能力——而不是单纯的速度。当场景提到缩短产品上市时间或支持快速迭代时，被考查的云优势就是敏捷性。

**练习 2——SAA-C03 情景题**

*场景*：一个小型初创公司正在推出一个外卖应用程序。他们预计初期流量较低，但如果产品成功，预计会快速增长。创始团队没有管理物理服务器的经验。他们希望最大限度地减少前期成本，避免维护硬件的运营负担。

以下哪种方案*最能*满足他们的需求？

A) 使用云提供商托管应用程序，只为使用的部分付费  
B) 购买一台专用服务器，在办公室托管应用程序  
C) 与托管数据中心（co-location）合作，自行上架服务器  
D) 将应用程序构建为完全离线运行，不需要互联网基础设施

**提示 1**：想想初创公司需要*避免*什么，就像他们需要*拥有*什么一样。

**提示 2**：场景明确提到"没有管理硬件的经验"和"最小化前期成本"。哪个选项消除了这些顾虑？

**提示 3**：我们在本章中将此选项描述为为"别人的计算机"付费。

**答案**：A

**解析**：AWS 等云提供商提供按使用付费的定价，无需前期硬件成本，并处理所有物理基础设施维护。这正是对流量不确定、没有硬件专业知识的初创公司有意义的模式——就像 Nimbus 一样。

**为什么不是 B？** 购买专用服务器需要前期资金、持续维护，且没有内置的随流量增长而扩展的能力。

**为什么不是 C？** 托管数据中心解决了空间问题，但初创公司仍然需要购买、维护和管理自己的服务器。

**为什么不是 D？** 外卖应用程序按定义需要互联网连接。

## 彩蛋场景

那天深夜，所有人都回家后，Maya 独自坐在餐厅里，打开了笔记本电脑。

她找到了 AWS 的网站。她点击浏览了几个页面。上面列出了数百个服务。数百个。

她往下滚动。又往下滚动。再往下滚动。

然后她关上了笔记本电脑。

"我们需要一个计划，" 她对着空荡荡的房间说。

Tom 把他早些时候查到的服务器价格发给了她。她又读了一遍那些数字：前期成本、折旧、电费、更换周期。然后她打开了 AWS 定价计算器。她输入了一台虚拟服务器——最小的那种，只是想看看。每月的数字比一间实体服务器机房的电费还要低。

她盯着那个数字看了好一会儿。

然后她给 Tom 发了条短信：*我们上云。*

他的回复不到一分钟就来了：*我知道。我也算过这笔账了。但我们要谨慎地做。*

她放下手机。窗外，餐厅一片安静。厨房一片漆黑。在厨房与云之间的某处，有一桩她即将建立的事业。
