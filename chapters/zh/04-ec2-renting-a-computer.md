# 第4章：别人大楼里的一台计算机

CPU 图表已经变成了背景音乐。

Tom 的笔记本电脑摊开在他桌子的一角，CloudWatch 每分钟刷新一次，利用率曲线以一种"有东西正在拼命工作"的斜率持续攀升。Maya 三天前就注意到了，但没有告诉任何人。她一直在盯着订单队列。

IAM 已经就位。凭证都井井有条。Priya 给所有东西都开了 MFA。团队第一次感觉到自己稍微有点负责任了。但"负责任"解决不了 Maya 正在盯着的问题：订单面板上的数字在攀升，而 CPU 曲线也跟着一起攀升。

Nimbus 应用程序运行在 Leo 当初没多想就启动的那个实例上——就是在任何人知道什么是区域之前，被他"部署在某个地方"的那一个。

用来给投资者展示演示，这没问题。但当 Maya 按下"发布"、第一周就涌入两百个注册——四十七家餐厅每天都在实际接单——这就不行了。Leo 即兴启动的实例现在处理着真实的订单、真实的菜单和真实的顾客——一台被意外选中、按默认值定规格、由一个边敲命令边学 AWS 的人配置的机器。

"我们需要一台服务器，" Maya 说。"真正的服务器。一台真正有人特意选出来的服务器。"

Tom 看了看 CPU 图表。那条线从房间另一头都看得见。

就是那时，他们开始研究租用一台计算机究竟意味着什么。

**没人解释的抽象层**

当人们说他们的应用程序"运行在云上"时，他们通常是说它在虚拟机上运行——一台不作为专用硬件实际存在，但在每个方面都表现得像真实硬件的计算机。

机制是这样的。

AWS 数据中心的一台物理服务器有很多资源：CPU 核心、内存、磁盘和网络带宽。AWS 使用一种叫做**虚拟机监控程序**（hypervisor）的软件来划分那台物理服务器——这种软件就像大楼的管理员，把物理服务器的资源分配给多个虚拟租户。虚拟机监控程序创建多个虚拟机，每个看起来都有自己的专用 CPU、内存和磁盘——但实际上共享底层物理硬件。

可以把它想象成在一栋大楼里租公寓，而不是买一套房子。

大楼的拥有者（AWS）维护物理结构——管道、电气、安保。你得到一个单元。你随意布置。你按月（或按小时）付费。当你需要更多空间时，你搬到更大的单元。当你搬出去时，你停止付费。

这些虚拟机租约中的每一个，就是 AWS 所说的 **EC2 实例**——Elastic Compute Cloud（弹性计算云）。

EC2 代表 Elastic Compute Cloud（弹性计算云）。"弹性"这部分很重要，我们稍后会讲到。现在只需知道：EC2 实例是你按小时租用的计算机。它有操作系统、网络连接和计算能力。它运行你的应用程序，就像物理服务器一样。

**选择你的实例：大小很重要**

并非所有 EC2 实例都相同。AWS 提供数百种实例类型，按照它们优化的用途组织成系列。

**通用型**（例如 `t3`、`m6i`）：平衡的 CPU 和内存。大多数 Web 应用程序的好默认选择。`t3` 系列是可突增的——它在低利用率期间积累 CPU 积分，在突增期间消耗这些积分。非常适合开发环境和 CPU 需求多变的工作负载。`m6i` 系列提供稳定、非突增式的性能——更适合有持续 CPU 需求的生产工作负载。

**计算优化型**（例如 `c7g`）：相对于内存有更多 CPU。适合视频编码、科学建模、批处理。`c7g` 中的"g"后缀表示该实例使用 AWS Graviton 处理器——AWS 自主设计的基于 ARM 的芯片，对许多工作负载而言，性价比优于同等的 x86 实例。

**内存优化型**（例如 `r7i`）：相对于 CPU 有更多内存。适合数据库、缓存、内存分析。如果你运行的数据库通过把更多数据放进 RAM 就能大幅提升性能，R 系列就是正确的起点。

**存储优化型**（例如 `i3`）：高速本地存储。适合需要非常快速磁盘 I/O 的数据密集型工作负载。这些实例上的本地 NVMe 存储比 EBS 快得多——但它也是临时性的。把它用于临时数据，不要存放任何丢不起的东西。

**加速计算型**（例如 `p4`）：附加 GPU。适合机器学习训练和图形渲染。这些实例很贵——一台 `p3.8xlarge` 每小时超过 12 美元——但对于受益于 GPU 并行计算的工作负载来说，没有替代品。

每个系列都有不同尺寸。`t3.micro` 有 2 个虚拟 CPU 和 1 GB 内存。`t3.xlarge` 有 4 个虚拟 CPU 和 16 GB。`t3.2xlarge` 再翻一倍。命名模式是一致的：后缀依次为 `nano`、`micro`、`small`、`medium`、`large`、`xlarge`、`2xlarge`、`4xlarge`、`8xlarge`，以此类推。

Leo 选择了 `t3.micro`。

"一个 `t3.micro` 能处理多少用户？" Tom 问。"更大一号的要贵多少？"

"取决于应用程序，" Leo 说。"但大概撑不住一百个并发用户同时进行图片上传和数据库查询。"

"那每个月要花多少钱？" Tom 一边看着实例类型对比页面一边问。

Leo 打开了 AWS 定价页面。t3.micro 每月大约 8 美元。t3.small 是 17 美元。t3.medium 是 33 美元。t3.large 大约 60 美元。越往上差距拉得越快——不是线性增长，而是每升一级大致翻倍。Tom 把数字记了下来，并注意到每升一级内存都翻倍——但奇怪的是，CPU 数量并没有增加。从 micro 到 large 的每一种 t3 都是同样的 2 个 vCPU；要到 xlarge 数量才开始增加。**CPU 积分基线**——实例可以持续使用这些 vCPU 而不耗尽突增积分的份额——也随之增长，但并非每一级都会增加。

Tom 在白板上写下"t3.micro"，旁边画了一个悲伤的表情。

**关于合理调整规格的对话**

t3.micro 撑了大约一个月，就被周五晚上的流量压垮了。Leo 匆忙升级——直接跳到了 t3.large，理由是"宁大勿小更安全"。换到 t3.large 两周后，Tom 提出了一个问题。

"CPU 在 9%，" 他说。"平均值。过去七天。"

Leo 看了看 CloudWatch 图表。平均 CPU 9%。周五晚餐时段的峰值大概 35%。其余时间：几乎纹丝不动。

"我们在运行一台每月 60 美元的服务器，" Tom 说，"只用了它 9% 的容量。"

"那周五的峰值怎么办？" Leo 说。"我们需要余量。"

"周五的峰值到 35%，" Tom 说。"t3.small 有同样的两个 vCPU——更小的是积分基线，大约 20% 的持续水平。我们平均才 9%。这意味着我们会全天候不停地攒 CPU 积分，只在周五晚上的几个小时花掉一部分。我核算过 `CPUCreditBalance` 的账——余额从来没有接近清零过。它每月 17 美元。我们有余量。"

Leo 看了看数字。又看了看图表。他体会到了一个工程师明知自己过度配置时的那种不自在。

"但万一来一波激增呢？" 他说。

"那指标会在出问题之前告诉我们，" Priya 说。"而且我们迟早会配置 Auto Scaling——它就是干这个的。一旦系统能自动增加实例，你就不需要手动为激增预留容量了。"

他们降级到了 t3.small。每月账单减少了 40 美元。一年下来就是 480 美元——不是小数目，对一家初创公司来说尤其如此。Tom 把它记进了自己的电子表格，带着一种等这个时刻等了两周的人才有的安静的满足感。

这个模式有个名字：**合理调整规格**（right-sizing）。它意味着让实例规格匹配实际工作负载，而不是想象中的最坏情况。AWS Compute Optimizer 和 CloudWatch 指标这样的 AWS 工具，能把合理调整规格变成一个由数据驱动的决策，而不是猜测。

**AMI：你的机器的初始状态**

在启动 EC2 实例之前，你要选择其操作系统和初始配置。在 AWS 中，这称为 **Amazon 机器映像**（AMI）。

AMI 是一个模板。它定义：

- 操作系统（Amazon Linux、Ubuntu、Windows Server 等）
- 预装软件
- 初始磁盘状态

当你从 AMI 启动实例时，AWS 为你创建该模板的全新副本。你也可以创建自己的 AMI——如果你把一台服务器配置得完全符合你的要求，你可以把那个状态"保存"为自定义 AMI，并用它快速启动完全相同的服务器。这就是大规模部署一致环境的方法。

把 AMI 想象成一个食谱。食谱描述了菜肴。每次你按照食谱做，你都会得到相同的菜肴。如果你想永久改变菜肴，你就更新食谱。

AWS 提供一个 AMI 市场——有些由 AWS 维护（Amazon Linux 2、Amazon Linux 2023），有些由主流 Linux 发行版维护（Ubuntu、Red Hat、SUSE），还有些来自第三方供应商（预配置的数据库服务器、安全设备、商业软件）。对大多数 Web 应用程序来说，AWS 维护的 Amazon Linux AMI 或 Ubuntu LTS AMI 是正确的起点。

对 Nimbus 而言，Leo 构建了一个自定义 AMI：从最新的 Amazon Linux 2023 基础镜像出发，加入了 Node.js 运行时、应用程序的系统依赖，以及一个预先创建好的应用进程服务文件。从这个 AMI 启动的新实例在 90 秒内就能开始处理流量——明显快于使用 UserData 脚本从零安装一切时四分钟的启动时间。

这里有一个权衡：自定义 AMI 需要维护。每次更新系统依赖或运行时版本，你都需要重新构建 AMI。任由 AMI 过时的团队，最终会发现自己运行着软件陈旧的实例——这是个安全风险。Priya 把"用最新软件包重建 AMI"加进了每月工程检查清单。

"存储 AMI 要花多少钱？" Tom 问。

AMI 以 EBS 快照的形式存储——你按 AMI 的大小支付 EBS 快照费率（大约每 GB 每月 0.05 美元）。一个带有 Nimbus 应用程序栈的典型 Amazon Linux AMI 大约 4 GB。按 $0.05/GB 计算：每个 AMI 每月 0.20 美元。为回滚目的保留五个历史 AMI：每月 1 美元。不算什么有意义的成本。

**UserData：引导脚本**

EC2 上还有一个配置选项，是 Leo 在试图避免每次应用代码变更都要构建新 AMI 时发现的。

当你启动 EC2 实例时，可以提供一个 **UserData 脚本**——一个在实例首次启动时自动运行的 Shell 脚本。它以 root 身份运行，在实例被视为"就绪"之前执行。

对 Nimbus 而言，UserData 脚本看起来大致是这样：

```bash
#!/bin/bash
yum update -y
yum install -y nodejs npm git
git clone https://github.com/nimbus-app/server.git /opt/nimbus
cd /opt/nimbus
npm install
systemctl enable nimbus
systemctl start nimbus
```

这个脚本安装 Node.js，拉取最新的应用代码，安装依赖，并启动应用服务。每一个从基础 AMI 启动的新实例都会运行这个脚本，启动完成时就已经自动装好了当前版本的应用程序。

这种方式意味着 AMI 保持简单（只是一个基础操作系统），而 UserData 负责应用程序的安装配置。代价是：UserData 脚本需要时间运行。一个实例可能需要三到五分钟才能启动并就绪。对于启动时间很重要的应用程序——比如 Auto Scaling 场景下需要新实例快速就绪——把应用程序预先"烘焙"进自定义 AMI 能显著缩短启动时间。

"没问题的，" 当 Priya 问起启动时间时，Leo 说。

"启动时间是多少？" 她问。

"四分钟。"

"在这四分钟里，实例在运行但不处理流量？"

"是的。"

"所以在突发流量激增期间，可能有四分钟新实例还帮不上忙？"

Leo 看了看自己的 UserData 脚本。他开始研究怎么构建自定义 AMI。

**密钥对：访问服务器的正确方式**

还记得上一章的"Admin123"灾难吗？

登录 EC2 实例的正确方式是使用**密钥对**。

密钥对是一个加密对：一个公钥（由 AWS 存储在服务器上）和一个私钥（你下载并保密的文件）。要登录，你使用 SSH——一个安全协议——配合你的私钥。没有密码。如果你丢失了私钥，你就失去了访问权限。SSH 没有"忘记密码"这回事。

这很重要，因为密钥对：

- 是你独有的
- 在密码学上不可能被猜出
- 不由 AWS 存储（私钥由你保管）
- 容易撤销（从服务器删除密钥，生成新的密钥对）

Priya 已经在 Nimbus 服务器上设置了基于密钥的访问。Admin123 那台服务器被停用了。没有人为此感到遗憾。

"那如果有人想入侵，在传输途中截获密钥对怎么办？" Priya 问。她其实早已想好了答案：私钥从不经过网络传输。你只下载一次。你把它保存在本地。它永远不离开你的机器。

**如果你弄丢了密钥对会怎样**

Leo 在第三周问了这个问题，带着那种还没弄丢密钥对、但已经开始担心的人特有的劲头。

"如果我把私钥文件弄丢了，会怎样？"

"你会失去对实例的 SSH 访问权限，" Priya 说。

"永久失去？"

"不一定。但恢复过程很难受。"

恢复过程是：停止实例，分离其根 EBS 卷，把它挂接到另一台你*确实*有访问权限的实例上，挂载该卷，在挂载卷上的 `authorized_keys` 文件中添加新公钥，分离后重新挂接回原实例，重启。

这是可行的。需要三十到六十分钟，而且要求小心执行。一步走错，事情可能更糟。

另一种办法——如果你的应用程序没有在根卷上存放任何关键数据（因为你一直遵循本书的建议，把数据存放在 S3 和 EBS 里）：终止该实例，从 AMI 启动一台全新的。顺便生成一个新的密钥对。

"把私钥存放在安全的地方，" Priya 说。"并且永远不要放在 EC2 实例上。"

Leo 看了看自己桌面上那个标着 `AWS_keys` 的文件夹。然后看了看 Priya。然后他把那个文件夹搬进了自己加密的密码管理器。

**安全组：你的实例的防火墙**

EC2 实例启动时需要一个**安全组**——一个虚拟防火墙，控制哪些网络流量可以到达它，以及它可以向外发送哪些流量。

安全组有两套规则：**入站**（进来的流量）和**出站**（出去的流量）。

默认情况下，新建的安全组阻止所有入站流量，允许所有出站流量。你通过添加入站规则，向特定来源开放特定端口。

对 Nimbus 的 Web 服务器，Priya 配置了：

- 允许 TCP 443 端口（HTTPS），来源为 `0.0.0.0/0`（整个互联网）
- 允许 TCP 80 端口（HTTP），来源为 `0.0.0.0/0`（在应用程序中重定向到 443）
- 允许 TCP 22 端口（SSH），仅限办公室 IP 地址——不对互联网开放

"等等——可是*为什么*要把 SSH 限制为只有办公室 IP？" Maya 问。

"因为如果 SSH 对整个互联网开放，" Priya 说，"自动化的机器人会一天二十四小时不停地撞 22 端口，尝试各种凭证组合。我们的日志会被失败的登录尝试填满。而且一旦 SSH 守护进程本身出现漏洞，全世界的攻击者都可以尝试利用它。"

"那如果 Leo 需要在家登录呢？"

"VPN，" Priya 说。

Leo 早就配好了 VPN。他脸上是那种以前被人问过这个问题的表情。

数据库还和应用程序住在同一台机器上——但 Priya 已经为它们分家的那一天准备好了一个单独的安全组：数据库端口只对来自 Web 服务器安全组的流量开放——不对互联网开放，不对 SSH 开放（即不允许直接访问数据库），不对任何其他来源开放。在那之前，她确保了这台共享实例的安全组完全不向互联网暴露数据库端口。数据库对一切都不可见，除了那个需要它的应用程序。

要直接触及数据库，攻击者必须先攻陷 Web 服务器。这是第一层防御。

"那第二层呢？" Tom 问。

"数据库的 IAM 身份验证。还有传输中加密。"

她把这两项都加进了配置检查清单。

**EC2 实例元数据与 IMDSv2**

EC2 安全还有一个在实践中很重要的部分，尽管入门内容很少讲到它。

当应用程序在 EC2 实例上运行时，它可以查询一个特殊的内部端点 `http://169.254.169.254/latest/meta-data/`，获取关于该实例的信息：实例 ID、区域、可用区，以及——至关重要的——与所挂接的 IAM Role 关联的临时 IAM 凭证。

这就是 EC2 实例上的应用程序在不硬编码凭证的情况下调用 AWS 服务的方式。它问元数据服务："我现在应该用什么凭证？"元数据服务返回会过期并自动轮换的临时凭证。

安全问题在于：这个元数据服务的旧版本（IMDSv1）会响应来自实例上任何进程的任何请求。如果应用程序存在服务器端请求伪造（SSRF）漏洞——一种攻击者能让服务器去获取攻击者指定的 URL 的缺陷——攻击者就可以利用该漏洞去获取 `http://169.254.169.254/latest/meta-data/iam/security-credentials/`，从而取得实例的 IAM 凭证。

这种攻击已经在真实的安全事件中被使用过。

**IMDSv2**（实例元数据服务第 2 版）修复了这个问题：元数据服务在响应之前要求一个会话令牌。令牌通过 PUT 请求获取。SSRF 攻击通常使用 GET 请求，无法完成 PUT 这一步——所以它们拿不到令牌，元数据也不会被返回。

"我们应该启用 IMDSv2 吗？" Leo 问。

"现在新实例默认就是它，" Priya 说。"但对已有的实例，你得手动开启。"

她当天下午就在所有现有的 Nimbus 实例上启用了它。

**实例生命周期：不是永久的**

这是许多初学者会忽略的东西。

EC2 实例默认不是永久的。当你停止一个实例时，计算资源被释放。当你再次启动它时，它可能运行在不同的物理硬件上。存储*在实例本身*（在其根卷上）的任何数据都能在停止/启动周期中存活——但公网 IP 地址会变化。

当你*终止*一个实例时，它就消失了。除非你有单独挂接的存储（我们在第6章介绍），否则实例上的任何数据都会消失。

EC2 实例可能处于的四种状态：

**Pending（待处理）**：实例正在启动。它已分配到硬件但尚未完成引导。

**Running（运行中）**：实例处于活动状态、可访问。你在为它付费。首次启动时，UserData 脚本也在此时运行。

**Stopping/Stopped（停止中/已停止）**：实例已关机。EBS 根卷被保留。你不再为计算付费，但仍要为所挂接的 EBS 存储付费。

**Shutting-down/Terminated（关闭中/已终止）**：实例正在被删除。除非你配置了 EBS 卷持久保留，否则其数据就没了。

这种"临时性"实际上是一个特性，而不是缺陷。它意味着你可以启动服务器、使用它们，然后扔掉它们。它支持水平扩展。但这也意味着你绝不应该把重要数据存储在 EC2 实例*本身*上。

那数据该住在哪里呢？

在单独的存储中。我们在接下来的两章中讲到这个。

你可能会想：如果实例每次重启都会拿到一个新 IP 地址，那应用程序怎么保持一个稳定的地址？AWS 有一个解决方案叫弹性 IP（Elastic IP）——一个归你所有的静态公网 IP，即使重启后也保持不变。关于费用的说明：自 2024 年 2 月起，AWS 对每一个公网 IPv4 地址按小时收取一笔小额费用——无论是弹性 IP（不管挂接与否）还是实例上自动分配的公网 IP 都一样。公网 IPv4 不再免费，这也是把实例放进负载均衡器之后的私有子网里的又一个理由。

对于负载均衡器之后的应用程序——这是任何生产环境 Web 应用程序的正确架构——你根本不需要弹性 IP。用户连接到负载均衡器稳定的 DNS 名称。负载均衡器通过 VPC 内的私有 IP 地址连接到各实例。实例可以来来去去、换新 IP、扩容缩容——负载均衡器透明地处理这一切。弹性 IP 用于特定场景：一台客户端直接通过 IP 连接的服务器、一台需要稳定地址的堡垒主机，或一个由于某种特定原因没有放在负载均衡器之后的应用程序。

Leo 起初计划给 Nimbus 的 Web 服务器使用弹性 IP。Priya 指出，有了负载均衡器，Web 服务器的 IP 地址对外部客户端来说就无关紧要了。负载均衡器拥有那个稳定的 DNS 名称。它身后的实例在设计上就是可丢弃的。

"所以弹性 IP 是为例外情况准备的，不是常规做法，" Leo 说。

"正确，" Priya 说。"而且如果你发现自己伸手要去拿一个弹性 IP，先问问这个架构是不是应该改用负载均衡器。"

**"弹性"意味着什么**

我们说过 EC2 代表 Elastic Compute Cloud（弹性计算云）。它的弹性体现在哪里？

两件事：

**垂直弹性**：你可以改变实例的大小。停止实例，将其从 `t3.micro` 改为 `t3.xlarge`，然后重启。更多 CPU 和内存，相同的应用程序，相同的设置。

**水平弹性**：你可以添加更多实例。不是一台大服务器，而是在负载均衡器后面运行十台中等服务器。当流量下降时，移除实例并停止为它们付费。

这两种方法都解决了"一台服务器，流量太大"的问题。它们各有不同的权衡，我们会在第7章给故事加上 Auto Scaling 时进行探讨。

关键洞察：使用 EC2，计算能力是你*调节*的东西，而不是*购买*的东西。需要更多？把旋钮调高。需要更少？调低。相应付费。

Maya 看着实例类型表格。"如果我们直接把服务器变大就行，何必费心搞十台中等的？"

"因为，" Leo 说，"一台大服务器仍然只是一台服务器。它一倒，全都倒。十台中等服务器意味着一台坏了，还有九台在运行。"

"而且，" Priya 补充道，"你没法在不重启的情况下把服务器变大。十台小的意味着你可以在不碰正在运行的那些的情况下增加更多。"

Tom 早已在他的笔记本上写下了"重启 = 停机"。

## 优势与局限性

**EC2 为什么强大**：

- 完全控制。你选择操作系统、软件、配置。这是你的计算机。
- 灵活的规格选择。数百种实例类型覆盖每个用例。
- 没有硬件需要管理。AWS 处理物理层。
- 对 Amazon Linux、Windows 和 Ubuntu 的 AMI 按秒计费，最低 60 秒起。（部分商业 Linux AMI，如 RHEL 和 SUSE，仍按小时计费——请查阅该 AMI 的计费条款。）你停止实例，你就停止付费。
- 与一切兼容。EC2 是大多数其他 AWS 服务构建于其上的基础。
- 多种定价模型（按需、预留、竞价型）使可预测或灵活的工作负载能够大幅优化成本——第27章详细介绍。

**事情变得复杂的地方**：

- 你负责给操作系统打补丁和更新。（共同责任模型——这是属于你的"云内部"那一部分。）
- 操作系统补丁不是可选项。未打补丁的 EC2 实例是云安全事件中最常见的攻击途径之一。AWS Systems Manager Patch Manager 可以把它自动化——但你必须配置并监控它。
- 规模化管理 EC2 意味着要管理实例状态、AMI、安全补丁，以及可能多达数千台机器的生命周期。这是运营开销。
- EC2 不是所有问题的正确答案。对于不频繁运行的事件驱动代码，Lambda（第20章）更便宜、更简单。对于容器化工作负载，ECS 和 EKS（第21章）提供更好的资源效率。
- 未使用的实例仍然要花钱。如果你停止一个实例，你停止为计算付费——但如果有存储挂接着，你仍然要为那份存储付费。

**关于"何时不该用 EC2"的判断**：EC2 给你最大的控制权——但控制权有运营成本。你运行的每一台 EC2 实例都是你必须打补丁、监控并最终更换的东西。对于不频繁运行的应用程序（Lambda 更便宜）、需要水平扩展到几十甚至几百台实例的应用程序（容器更高效），或数据库等托管型工作负载（RDS、ElastiCache），完全托管的服务以适度的费用溢价换来运营开销的大幅减少。当你确实需要 EC2 提供的控制权时再选择它——而不是默认就用它。

Priya 有个判断法则："如果一个能满足我们需求的托管服务可以让我们用得开心，就用托管服务。当托管选项不存在或不合适时，才用 EC2。"

Leo 起初对此有异议。"但 EC2 给我们更多选择。"

"选择就是开销，" Priya 说。"我们不需要每一个选项。我们需要的是正确的配置，并把它可靠地维护好。"

**EC2 置放群组：控制实例落在哪里**

EC2 让你控制实例*是什么*——它的规格、操作系统、配置。它也通过一个叫做**置放群组**（placement groups）的功能，让你对实例在物理上落在*哪里*拥有有限的控制权。

默认情况下，AWS 把实例分散到不同的物理硬件上，以最大化可用性。但对某些工作负载，你会想覆盖这个默认行为——要么让实例彼此更靠近，要么保证它们彼此远离。

三种置放群组类型：

**集群（Cluster）**：把实例紧密地放在单个可用区内，通常在同一物理机架或相邻硬件上。结果是群组内实例之间拥有最低的网络延迟和最高的网络吞吐量——实例之间的网络吞吐量可达 10 Gbps 或更高（不要把它和增强联网/ENA 混淆，后者是与置放群组无关的单实例联网特性）。这是 HPC（高性能计算）、大规模 ML 训练任务，以及实例间需要大量相互传输数据的紧耦合并行工作负载的选择。代价是可用性：如果底层硬件段发生故障，集群中的所有实例可能同时受到影响。

**分区（Partition）**：把实例划分到多个逻辑分区中，每个分区位于自己独立的一组硬件上——独立的机架、独立的电源、独立的网络交换机。同一分区内的实例彼此共享硬件，但分区之间从不共享硬件。这种设计限制了硬件故障的爆炸半径：一个机架宕机只影响一个分区，不影响其他分区。分区置放群组是为大型分布式和复制型工作负载——Apache Hadoop、Apache Cassandra、Apache Kafka——而构建的，在这些场景中你需要足够的故障隔离，使机架级故障不至于摧毁整个集群。

**分散（Spread）**：把每个实例放在完全独立的底层硬件上。实例之间最大程度的隔离。如果你有五台关键应用实例，绝不能共享同一物理主机（因为单次硬件故障绝不应同时摧毁多于一台），分散就是答案。限制：**每个置放群组在每个可用区最多 7 台实例**。分散是为少量不能容忍同机部署的关键实例设计的，不适合大型机群。

"所以集群是为了速度，分散是为了隔离，分区是为既需要一些聚集又需要一些隔离的分布式系统？" Maya 问。

"差不多，" Priya 说。"集群：实例之间低延迟，一个集中的大风险。分散：最大隔离，每个可用区硬上限 7 台。分区：为大型分布式系统提供结构化的隔离——你可以控制每台实例进哪个分区。"

对 Nimbus 当前的架构来说，这些暂时都用不上。但知道它们存在，就意味着知道什么时候该用它们——而更直接的好处是，知道一道关于"需要低节点间延迟的 HPC 工作负载"的考题究竟在问什么。

## 摘要

一台意外启动的实例永远成不了生产服务器。正确地理解 EC2 不只解决了容量问题——它还引入了一组会在后续几乎每一章里出现的概念。实例类型、AMI、密钥对、安全组和合理调整规格不是 EC2 的边角知识；它们是本书其余部分赖以构建的词汇表。在这里学会它们，后面的一切都会更说得通。

- **EC2 实例**是你在 AWS 中租用的虚拟机。实例类型按用例组织：通用型、计算优化型、内存优化型、存储优化型。选对系列，并依据实际工作负载指标合理调整规格——而不是依据想象中的最坏情况。
- **AMI**（Amazon 机器映像）是你实例的操作系统和初始配置的模板。自定义 AMI 支持一致的、可重复的部署。
- **密钥对**是安全访问 EC2 实例的方式。**安全组**是你实例的防火墙——把 SSH 限制在已知 IP，并把数据库端口只对应用程序的安全组开放。
- 所有实例都应启用 **IMDSv2**，以防范基于 SSRF 的、针对实例元数据服务的凭证窃取。
- EC2 实例默认不是永久的。被终止的实例会丢失本地数据——把重要数据存储在 S3 或 EBS 中，而不是实例磁盘上。

## 考试技巧

*SAA-C03 领域3——任务3.2（高性能计算解决方案）*

- **EC2 的共同责任**：你负责给操作系统打补丁。AWS 维护物理硬件和虚拟机监控程序。这是一个经常被测试的区分点。
- **实例系列对场景题很重要。** 如果场景提到高内存要求（内存缓存、SAP HANA），答案可能涉及内存优化实例。如果提到批处理或 HPC，则是计算优化型。
- **停止 ≠ 终止。** 停止实例会保留它（你可以重启）。终止会删除它。考试场景测试你是否知道这个区别。
- **重启后公网 IP 会变化。** 如果你的应用程序需要稳定的 IP 地址，使用**弹性 IP**——一个与你账户保持关联的静态公网 IP。自 2024 年 2 月起，AWS 对每一个公网 IPv4 地址按小时计费——弹性 IP（不管挂接与否）和自动分配的公网 IP 都一样。
- **按需、预留和竞价型**定价模型在领域4中被大量测试。我们在第27章中介绍它们。现在，知道按需意味着按秒付费、没有承诺即可。
- **安全组是有状态的。** 如果你允许某端口的入站流量，返回流量会自动被允许，无需显式的出站规则。NACL（第15章介绍）是无状态的——它们需要同时配置入站和出站规则。
- **置放群组：** 集群 = 实例间最低延迟（HPC、ML 训练——但对整个群组有单点故障风险）；分区 = 分布式系统（Hadoop、Kafka、Cassandra），按分区隔离故障；分散 = 实例间最大隔离，每个可用区最多 7 台。考题套路："紧耦合 HPC 工作负载需要节点之间最大网络吞吐量" → 集群置放群组。

**练习 2——SAA-C03 场景题**

*场景*：一家公司正在部署一个高流量的 Web 应用程序。该应用程序处理具有复杂过滤逻辑的产品目录搜索，这非常消耗 CPU。团队预计在促销活动期间会有明显的流量峰值。他们想确保选择正确的 EC2 实例类型，并为流量激增做好准备。

以下哪种组合**最能**满足他们的需求？

A) 内存优化实例，固定数量以确保一致的性能  
B) 计算优化实例，配合 Auto Scaling 来处理流量峰值  
C) 通用型实例，单个大型实例规格  
D) 存储优化实例，因为产品目录需要快速磁盘访问

**提示 1**：工作负载被描述为"CPU 密集型"。哪个实例系列针对 CPU 进行了优化？

**提示 2**：场景提到"促销活动期间的流量峰值"。固定数量的实例无法有效处理可变流量。哪个 AWS 功能可以处理这个问题？

**提示 3**：计算优化实例处理 CPU 密集型工作。Auto Scaling 根据需求添加和删除实例。它们一起回应了两个需求。

**答案**：B

**解析**：计算优化实例（如 `c` 系列）为 CPU 密集型工作负载提供更高的每美元 CPU 性能。Auto Scaling 根据负载自动调整实例数量——在促销活动期间添加实例，当流量恢复正常后移除它们。这种组合同时优化了性能和成本。

**为什么不是 A？** 内存优化实例是为需要大量 RAM 的工作负载设计的（数据库、内存缓存）。而这是一个 CPU 密集型工作负载。而且固定的实例数量要么意味着过度配置（浪费），要么意味着配置不足（失败）。

**为什么不是 C？** 通用型实例以牺牲一些 CPU 效率为代价换取均衡。对于已知的 CPU 密集型工作负载，计算优化型更合适。而且单个大型实例是一个单点故障。

**为什么不是 D？** 瓶颈是 CPU，不是磁盘 I/O。存储优化实例是为需要对本地存储有极高吞吐量的工作负载设计的。
