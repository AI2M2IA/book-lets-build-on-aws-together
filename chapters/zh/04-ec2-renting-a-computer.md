# 第4章：别人大楼里的一台计算机

Nimbus 的应用程序正在 Tom 的笔记本电脑上运行。

对于向投资者展示演示来说，这还可以。但当 Maya 按下"发布"后，第一周就有200家餐厅注册，这就不行了。Tom 的笔记本现在处理着真实的订单、真实的菜单和真实的顾客——放在 Tom 的桌子下面，靠着办公室的 Wi-Fi 运行，接在一个同时给空间加热器和咖啡机供电的插线板上。

"我们需要一台服务器，" Maya 说。"真正的服务器。放在不是你桌子底下的地方运行。"

Tom 看了看他的笔记本电脑。从房间另一头都能听到风扇的声音。

就是那时他们开始研究租用一台计算机究竟意味着什么。

**没人解释的抽象层**

当人们说他们的应用程序"运行在云上"时，他们通常是说它在虚拟机上运行——一台不作为专用硬件实际存在，但在每个方面都表现得像真实硬件的计算机。

这就是机制。

AWS 数据中心的一台物理服务器有很多资源：CPU 核心、内存、磁盘和网络带宽。AWS 使用称为**虚拟机监控程序**的软件来划分那台物理服务器。虚拟机监控程序创建多个虚拟机，每个看起来都有自己的专用 CPU、内存和磁盘——但实际上共享底层物理硬件。

这些虚拟机中的每一个就是 AWS 所说的 **EC2 实例**。

EC2 代表弹性计算云。"弹性"部分很重要，我们稍后会讲到。现在：EC2 实例是你按小时租用的计算机。它有操作系统、网络连接和计算能力。它运行你的应用程序，就像物理服务器一样。

类比：在一栋大楼里租公寓，而不是购买房子。

楼的拥有者（AWS）维护物理结构、管道、电气和安全。你得到一个单元。你随意布置。你按月（或按小时）付费。当你需要更多空间时，你搬到更大的单元。当你搬出去时，你停止付费。

**选择你的实例：大小很重要**

并非所有 EC2 实例都相同。AWS 提供数百种实例类型，按照它们优化的用途组织成系列。

**通用型**（例如 `t3`、`m6i`）：平衡的 CPU 和内存。大多数 Web 应用程序的好默认选择。

**计算优化型**（例如 `c7g`）：相对于内存有更多 CPU。适合视频编码、科学建模、批处理。

**内存优化型**（例如 `r7i`）：相对于 CPU 有更多内存。适合数据库、缓存、内存分析。

**存储优化型**（例如 `i3`）：高速本地存储。适合需要非常快速磁盘 I/O 的数据密集型工作负载。

**加速计算型**（例如 `p4`）：附加 GPU。适合机器学习训练和图形渲染。

每个系列都有不同尺寸。`t3.micro` 有 2 个虚拟 CPU 和 1 GB 内存。`t3.xlarge` 有 4 个虚拟 CPU 和 16 GB。你为工作负载选择合适的尺寸。

Leo 选择了 `t3.micro`。

"一个 `t3.micro` 能处理多少用户？" Tom 问。

"取决于应用程序，" Leo 说。"但可能不是一百个并发用户同时进行图片上传和数据库查询。"

Tom 在白板上写下"t3.micro"，旁边画了一个悲伤的表情。

**AMI：你的机器初始状态**

在启动 EC2 实例之前，你选择其操作系统和初始配置。在 AWS 中，这称为 **Amazon 机器映像**（AMI）。

AMI 是一个模板。它定义：

- 操作系统（Amazon Linux、Ubuntu、Windows Server 等）
- 预装软件
- 初始磁盘状态

当你从 AMI 启动实例时，AWS 为你创建该模板的全新副本。你也可以创建自己的 AMI——如果你按照自己的方式配置服务器，你可以将该状态"保存"为自定义 AMI，并用它快速启动相同的服务器。这就是你如何在规模上部署一致的环境。

把 AMI 想象成一个食谱。食谱描述了菜肴。每次你按照食谱做，你都会得到相同的菜肴。如果你想永久改变菜肴，你更新食谱。

**密钥对：访问服务器的正确方式**

还记得上一章的"Admin123"灾难吗？

登录 EC2 实例的正确方式是使用**密钥对**。

密钥对是一个加密对：一个公钥（由 AWS 存储在服务器上）和一个私钥（你下载并保密的文件）。要登录，你使用 SSH——一个安全协议——配合你的私钥。没有密码。如果你丢失了私钥，你就失去了访问权限。SSH 没有"忘记密码"。

这很重要，因为密钥对是：

- 你独有的
- 加密上不可能被猜到的
- AWS 不存储的（你保管私钥）
- 容易撤销的（从服务器删除密钥，生成新的密钥对）

Priya 已经在 Nimbus 服务器上设置了基于密钥的访问。Admin123 服务器被停用了。没有人为此感到遗憾。

**实例生命周期：不是永久的**

这是许多初学者会忽略的东西。

EC2 实例默认不是永久的。当你停止一个实例时，计算资源被释放。当你再次启动它时，它可能在不同的物理硬件上运行。存储*在实例本身*（在其根卷上）的任何数据都能在停止/启动周期中存活——但公网 IP 地址会变化。

当你*终止*一个实例时，它就消失了。除非你有单独的附加存储（我们在第6章介绍），否则实例上的任何数据都会消失。

这种"临时性"实际上是一个特性，而不是一个缺陷。这意味着你可以启动服务器、使用它们，然后扔掉它们。它支持水平扩展。但这也意味着你不应该在 EC2 实例*本身*上存储重要数据。

那数据住在哪里呢？

在单独的存储中。我们在接下来的两章中讲到这个。

**"弹性"意味着什么**

我们说 EC2 代表弹性计算云。它的弹性体现在哪里？

两件事：

**垂直弹性**：你可以改变实例的大小。停止实例，将其从 `t3.micro` 更改为 `t3.xlarge`，然后重启。更多 CPU 和内存，相同的应用程序，相同的设置。

**水平弹性**：你可以添加更多实例。不是一台大服务器，而是在负载均衡器后面运行十台中等服务器。当流量下降时，删除实例并停止为它们付费。

这两种方法都解决了"一台服务器，流量太大"的问题。它们有不同的权衡，我们在第7章给 Nimbus 添加自动扩展时会探讨这些权衡。

关键洞察：使用 EC2，计算能力是你*调节*的东西，而不是*购买*的东西。需要更多？调高。需要更少？调低。相应付费。

## 优势与局限性

**EC2 为什么强大**：

- 完全控制。你选择操作系统、软件、配置。这是你的计算机。
- 灵活的大小调整。数百种实例类型适用于每个用例。
- 没有硬件需要管理。AWS 处理物理层。
- 按秒计费（对于大多数实例类型）。你停止实例，你停止付费。
- 适用于所有情况。EC2 是大多数其他 AWS 服务构建的基础。

**事情变得复杂的地方**：

- 你负责给操作系统打补丁和更新。（共同责任模型——这是你的"云内部"部分。）
- 规模化管理 EC2 意味着管理实例状态、AMI、安全补丁，以及可能数千台机器的生命周期。这是运营开销。
- EC2 不是所有事情的正确答案。对于不频繁运行的事件驱动代码，Lambda（第20章）更便宜、更简单。对于容器化工作负载，ECS 和 EKS（第21章）提供更好的资源效率。
- 未使用的实例仍然要花钱。如果你停止一个实例，你停止为计算付费——但如果你附加了存储，你仍然要为那个存储付费。

## 摘要

- **EC2 实例**是你在 AWS 中租用的虚拟机。它有操作系统、网络访问和计算资源。
- 实例类型按用例组织：通用型、计算优化型、内存优化型、存储优化型、加速计算型。为你的工作负载选择合适的系列和大小。
- **AMI**（Amazon 机器映像）是你实例操作系统和初始配置的模板。自定义 AMI 支持一致的、可重复的部署。
- **密钥对**是安全访问 EC2 实例的方式。没有密码。
- EC2 实例默认不是永久的。终止的实例会丢失数据。将重要数据存储在单独的存储服务中。
- "弹性"意味着你可以垂直（更大的实例）和水平（更多实例）扩展计算。

## 考试技巧

*SAA-C03 领域3——任务3.2（高性能计算解决方案）*

- **EC2 的共同责任**：你负责给操作系统打补丁。AWS 维护物理硬件和虚拟机监控程序。这是一个经常被测试的区分点。
- **实例系列对场景题很重要。** 如果场景提到高内存要求（内存缓存、SAP HANA），答案可能涉及内存优化实例。如果提到批处理或 HPC，则是计算优化型。
- **停止 ≠ 终止。** 停止实例会保留它（你可以重启）。终止会删除它。考试场景测试你是否知道这个区别。
- **重启后公网 IP 会变化。** 如果你的应用程序需要稳定的 IP 地址，使用**弹性 IP**——一个与你账户关联的静态公网 IP。如果你分配了一个但不使用它，是要收费的。
- **按需、预留和竞价型**定价模型在领域4中被大量测试。我们在第27章中介绍它们。现在，知道按需意味着按秒付费，没有承诺。

**练习 2——考试练习**

*场景*：一家公司正在部署一个高流量的 Web 应用程序。该应用程序处理具有复杂过滤逻辑的产品目录搜索，这非常消耗 CPU。团队预计在促销活动期间会有明显的流量峰值。他们想确保选择正确的 EC2 实例类型，并为流量激增做好准备。

以下哪种组合*最能*满足他们的需求？

A) 内存优化实例，固定数量以确保一致的性能  
B) 计算优化实例，配合自动扩展来处理流量峰值  
C) 通用型实例，单个大型实例规格  
D) 存储优化实例，因为产品目录需要快速磁盘访问

**提示 1**：工作负载被描述为"CPU 密集型"。哪个实例系列针对 CPU 进行了优化？

**提示 2**：场景提到"促销活动期间的流量峰值"。固定数量的实例无法有效处理可变流量。哪个 AWS 功能可以处理这个问题？

**提示 3**：计算优化实例处理 CPU 密集型工作。自动扩展根据需求添加和删除实例。它们一起回答了两个需求。

**答案**：B

**解析**：计算优化实例（如 `c` 系列）为 CPU 密集型工作负载提供更多 CPU/美元。自动扩展根据负载自动调整实例数量——在促销活动期间添加实例，当流量恢复正常后删除它们。这种组合同时优化了性能和成本。

**为什么不是 A？** 内存优化实例为需要大量 RAM 的工作负载设计（数据库、内存缓存）。这是 CPU 密集型工作负载。固定实例数量要么意味着过度配置（浪费）要么配置不足（失败）。

**为什么不是 C？** 通用型实例以牺牲一些 CPU 效率为代价换取平衡。对于已知的 CPU 密集型工作负载，计算优化型更合适。单个大型实例是单点故障。

**为什么不是 D？** 瓶颈是 CPU，不是磁盘 I/O。存储优化实例为需要对本地存储有非常高吞吐量的工作负载设计。
