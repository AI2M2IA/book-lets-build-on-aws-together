# 第二十五章：私人高速公路

站起来一会儿。甩一甩手。

感受一下你的指尖与这个国家另一端某样东西之间的距离。想象发出一条消息，它必须穿越这段距离，在十几次运营商交接中找到出路，再返回来，你才能继续工作。再想象每秒做这件事数千次。

这就是数据传输的真实面貌——物理距离、物理基础设施、物理约束。

我们要谈谈数据移动。不是在 AWS 内部的服务之间，而是在现实世界与 AWS 之间——在你的办公室和你的云基础设施之间，在大陆与大陆之间。

---

数据库扩展完毕、存储成本降下来之后，Tom 把目光转向了网络账单。但 Leo 有一个更紧迫的问题——把 4 太字节的历史订单数据搬进 AWS，正在暴露他们当前连接的极限。

---

Nimbus 的基础设施团队（现在有四名工程师）在西雅图的一间共享办公室工作。他们需要访问自己管理的 AWS 基础设施。某些操作需要连接到 VPC 中的资源。

目前，他们在笔记本电脑上使用 VPN 访问公有子网中的堡垒机，再从那里 SSH 到各个资源。

这能用。就是慢。VPN 连接经由公共互联网路由：西雅图 → 多次运营商跳转 → us-west-2。往返时间不稳定——30 到 80 毫秒不等，取决于时段——而吞吐量受限于办公室的上行链路和公共路径。

"日常 SSH 用这个还能接受，"Leo 说，"但我们马上要开始迁移分析数据库了。4 太字节的历史订单数据。走这条连接，迁移要花好几周。"

"我们需要更好的连接，"Maya 说。

"一条私有连接，"Priya 补充道，"不走公共互联网。还有，要是数据传输期间有人想入侵呢？4TB 的订单历史走公共互联网——哪怕加了密——感觉就是个靶子。"

把它想象成通勤上班。Site-to-Site VPN 就像在公共道路上开车：你锁上车门（加密），但仍然和所有人共享车道，交通堵塞会让你不可预测地减速。Direct Connect 就像在高速公路上租一条专用的私人车道——没有共享车流，速度稳定，月租通行费更高。大多数日子，公共道路就够用了。当你要按紧张的时间表运送一卡车贵重货物时，你会为私人车道掏钱。

Snow Family 则是大多数人不会想到的选项：包租一架真正的货运航班。它不是随时可用。小批量货物不适合它。但对于满满一卡车的货物，它比开车更快到达，而且完全不依赖高速公路的路况。物理规律没有变——你搬的还是同样的比特——但机制从根本上不同。

**AWS Site-to-Site VPN：快速选项**

**AWS Site-to-Site VPN** 在你的本地网络和你的 VPC 之间创建一条加密隧道，穿越公共互联网。

设置步骤：

1. 创建一个虚拟私有网关（VGW）并附加到你的 VPC
2. 创建一个代表你本地路由器的客户网关
3. 在两者之间建立两条 VPN 隧道（用于冗余）

流量是加密的（AES-256）。它走公共互联网，这意味着延迟取决于互联网状况。AWS 自动提供两条隧道用于冗余——如果一条隧道出问题，流量切换到另一条。

**何时使用 Site-to-Site VPN**：

- 快速设置（几分钟到几小时）
- 成本经济（每条 VPN 连接 $0.05/小时）
- 带宽：每条隧道最高 1.25 Gbps
- 用例可以接受互联网级别的延迟

**Accelerated Site-to-Site VPN** 把 VPN 流量路由到 AWS 的全球网络上，而不是公共互联网——这与 Global Accelerator 提供的优化相同，只是应用到了 VPN 隧道上。延迟比标准 VPN 更低、更稳定。成本略高（要付 Global Accelerator 的数据传输费）。对于既想要 VPN 的快速设置和较低成本、又需要更好延迟的团队，Accelerated VPN 是介于标准 VPN 和 Direct Connect 之间的实用中间路线。

对于 Nimbus 的 4TB 迁移，走互联网的 VPN 在最高 1.25 Gbps 下需要：4TB / 1.25 Gbps ≈ 最少 7 小时，算上现实世界的开销接近 12-20 小时。可以接受，但公共互联网路径上的拥塞使它不可预测。

Leo 把账算得更仔细了，因为依他的经验，理论计算和实际传输时间从来没有对上过一次。

**理论值**：4 TB = 4,096 GB = 32,768 Gb。按 1 Gbps：32,768 秒 ≈ 9.1 小时。取整为 9 小时。

**实际值**：Leo 上周做过一次测试传输——从西雅图办公室向 S3 传了 50 GB。按他们实测的上行速度（875 Mbps）算的理论时间：457 秒。实际时间：724 秒。开销系数：1.58。

把它套到 875 Mbps 上行的 4TB 传输上：32,768 Gb / 0.875 Gbps × 1.58 开销 ≈ **59,200 秒 ≈ 16.4 小时**。

开销来自几个方面：建立连接时的 TCP 慢启动、需要重传的丢包（从西雅图到 us-west-2 的公共路径平均丢包率 0.2%——很小，但在数百万个数据包上会成倍放大）、每个分段上传分片的 HTTPS 握手开销，以及 S3 组装分段上传的处理时间。

"对一次性迁移来说，十六个小时没问题，"Leo 说，"真正的问题是传输在第 14 个小时被打断怎么办。"

S3 分段上传解决了中断问题：如果传输在第 14 小时失败，只需要重新上传当前的分片。之前的分片已经存在 S3 里，传输可以续传。但管理分段上传的开销让总传输时间增加了大约 3%。

最终的现实估算：**走 1 Gbps 互联网理论约 9 小时，实际约 17 小时**——考虑了他们办公室实测的 875 Mbps 上行速度、丢包开销，以及分段上传的处理时间。

Leo 思考了片刻。然后他打开了 Snow Family 的定价页面。

"另一个选项是什么？"Tom 问。

"等等——可是*为什么*我们需要 VPN 之外的任何东西？"Maya 问，"这 4TB 迁移就是一次性的事。"

"不是的，"Priya 说，"数据进了 AWS 之后，团队仍然需要每天访问它。而 VPN 的延迟会日积月累。"

**AWS Direct Connect：专用线路**

**AWS Direct Connect** 在你的所在地（或你的主机托管设施）和 AWS 之间建立一条专用的、私有的网络连接。流量永远不会触及公共互联网。

Direct Connect 是一条物理连接——一根从你的网络通向 AWS Direct Connect 站点的光纤线路。你与电信提供商合作建立物理电路。AWS 在他们那一侧提供端口。

**优势**：

- 一致、可预测的延迟（没有公共互联网的波动）
- 速度从 50 Mbps 到 100 Gbps（自 2024 年起，部分站点提供原生 400 Gbps 专用端口）
- 数据传输成本低于互联网（Direct Connect 的数据传输费率比标准的 AWS 数据传出费率便宜）
- 更安全（私有电路，而非公共互联网）

**权衡**：

- 设置需要数周到数月（物理基础设施开通）
- 成本明显高于 VPN
- 没有内置冗余（冗余电路要你自己建立）
- 对于地理上分散的办公室，没有多条电路就不适用

你可能会想：既然 Direct Connect 是一根物理光缆，万一有人不小心把它挖断了怎么办？这正是单条电路的单点故障问题——所以生产环境的 Direct Connect 部署会使用走地理上分离路径的冗余电路，或者保留一条 VPN 作为备份。光缆可以被挖断；业务照常运转。

"这每个月要花多少钱？"Tom 问。他已经查过了。"一个专用的 1Gbps 端口是 $216/月，"他说，"加上从我们办公室接出去的电路，电信公司报价 $800/月。"

"所以总共大约一千一个月。"

对 Nimbus 来说：以他们目前的规模，Direct Connect 是杀鸡用牛刀。但对于数据传输量巨大、或合规上要求私有网络连接的企业，Direct Connect 能收回成本。

**托管连接：中间地带**

不是每个组织都能为一条 100 Gbps 的专用光纤电路买单。**Direct Connect 托管连接（Hosted Connections）**允许 AWS Direct Connect 合作伙伴（获批的电信运营商）开通低于 1Gbps、由你与其他客户共享的连接。

设置更快（几天到几周，而不是几个月），成本也低于专用连接。代价是：共享容量意味着吞吐量不那么稳定。

对（不断成长的）Nimbus 来说：通过合作伙伴开通一条 500 Mbps 的托管连接，能以合理的价位提供私有连接。

考试时真正要紧的实际区别：托管连接的速度从 50 Mbps 到 10 Gbps（部分合作伙伴提供高达 25 Gbps），由 AWS 合作伙伴开通。专用连接直接对接 AWS，提供 1 Gbps、10 Gbps 和 100 Gbps（部分站点另有 400 Gbps）。对于低于 1 Gbps 的速度，托管连接是唯一的 Direct Connect 选项——专用连接最低从 1 Gbps 起。

**AWS Transit Gateway：VPC 的中心辐射式架构**

随着 Nimbus 的成长，他们会积累多个 VPC：生产 VPC、预发布 VPC、分析 VPC、安全工具 VPC。

如果不仔细规划，连接这些 VPC 需要一张完整的 VPC 对等连接网格。4 个 VPC：6 条对等连接。10 个 VPC：45 条对等连接。20 个 VPC：190 条连接。这没法扩展。

**AWS Transit Gateway** 是一个连接多个 VPC 和本地网络的网络枢纽。每个 VPC 不再织成对等连接的网格，而是各自连接到 Transit Gateway。Transit Gateway 在它们之间路由流量。

```
On-premises ──── Direct Connect ──┐
                                  │
Production VPC ───────────────── Transit Gateway
Staging VPC ──────────────────── Transit Gateway
Analytics VPC ────────────────── Transit Gateway
Security VPC ─────────────────── Transit Gateway
```

**传递路由**：如果 VPC A 和 VPC B 都连接到 Transit Gateway，它们就能通信——无需直接对等。路由由 Transit Gateway 处理。与 VPC 对等（不具有传递性）不同，Transit Gateway 支持中心辐射式拓扑。

**Transit Gateway 成本**：按附件（VPC 或 VPN/Direct Connect 连接）计费，外加每 GB 处理的数据费用。在规模化之后，这份简洁是值得的。

对 Nimbus 来说，引入 Transit Gateway 的触发事件是第四个 VPC 的加入。他们有了：生产、预发布、分析，以及现在的安全工具（一个用于漏洞扫描和 SOC2 合规监控的 VPC，它不应该和生产环境处在同一网段上）。

没有 Transit Gateway，连接四个 VPC 需要六条对等连接：
- 生产 ↔ 预发布
- 生产 ↔ 分析
- 生产 ↔ 安全
- 预发布 ↔ 分析
- 预发布 ↔ 安全
- 分析 ↔ 安全

六条对等连接、每个 VPC 六条路由表条目、六组要审查的安全组规则。而且 VPC 对等不具有传递性：如果生产与分析对等、分析与安全对等，生产也无法通过分析 VPC 到达安全 VPC。你需要显式地建立生产 ↔ 安全的对等连接。

有了 Transit Gateway：

```
Production VPC  ──┐
Staging VPC     ──┤──── Transit Gateway ────── On-premises (Direct Connect)
Analytics VPC   ──┤
Security VPC    ──┘
```

四个附件。一张要管理的路由表。传递路由：生产可以通过 Transit Gateway 到达安全 VPC，无需直接对等。

"那要是有人想通过 Transit Gateway 入侵呢？"Priya 问，"如果四个 VPC 共享一个 Transit Gateway，预发布 VPC 里一个被攻陷的资源就可能触及生产环境。"

Transit Gateway 支持**带隔离的路由表**：你可以定义哪些 VPC 允许通过 Transit Gateway 互相通信，哪些被隔离。安全工具 VPC 可以触达所有其他 VPC（它需要扫描它们）。预发布不能触达生产。生产不能直接触达分析（分析通过一个特定的只读端点查询数据）。

"一个 Transit Gateway，"Priya 说，"配上能够表达真实访问模型的路由策略。对比六条对等连接，却没有任何集中的方式来审计什么能到达什么。" 

**VPC 终端节点：对 AWS 服务的私有访问**

一个微妙的成本兼安全问题：当你的 EC2 实例（在私有子网中）调用 S3 API 时，流量会经由 NAT Gateway 路由（去往互联网，S3 的公共端点就在那里）。你要为 NAT Gateway 的处理付费。

**VPC 终端节点**允许你 VPC 中的资源私密地与 AWS 服务通信，不经过公共互联网——也不需要 NAT Gateway。

两种类型：

**网关终端节点**（免费）：用于 S3 和 DynamoDB。你在路由表中添加一条路由，把 S3 或 DynamoDB 流量定向到终端节点，而不是 NAT Gateway。创建免费；使用免费。

**接口终端节点**（收费）：用于其他 AWS 服务（SQS、SNS、Secrets Manager、SSM 等）。在你的子网中创建一个带私有 IP 的 ENI（弹性网络接口）。去往该服务的流量使用这个私有 IP。每个 AZ 每小时约 $0.01，外加数据处理费。

Leo 上周已经创建了网关终端节点，却没有更新路由表。"我已经部署了——哦，"他检查配置后说，"路由没更新。我来修。"

Tom 在得知 S3 和 DynamoDB 的网关终端节点是免费的之后，立即把它们创建了出来。NAT Gateway 的数据处理费降了 65%。

背后的算术是这样的：Nimbus 在私有子网中的 Lambda 函数和 ECS 任务在不停地向 S3（读取配置文件、写入日志导出）和 DynamoDB（读取餐厅数据、写入订单记录）发请求。每个请求都经由 NAT Gateway 路由，而它按每 GB 处理的数据收费 $0.045。

Nimbus 每月的 NAT Gateway 数据处理量：533 GB。费用：$24/月。添加 S3 和 DynamoDB 网关终端节点并更新路由表之后：S3 和 DynamoDB 流量完全绕开了 NAT Gateway。每月 NAT Gateway 处理量降到 187 GB——剩下的流量是对其他服务的 API 调用（Secrets Manager、SES、外部 webhook）。费用：$8.40/月。

节省：每月 $15.60，每年 $187，代价是两个免费的网关终端节点配置，花了 10 分钟设置。

"免费，"Tom 第三次说道。

"网关终端节点创建免费、使用免费，"Leo 确认道，"它们不只是安全上的改进——让 S3 和 DynamoDB 流量走私有终端节点而不是 NAT Gateway，等于把它从公共互联网上彻底移除了。"

"那要是有人想通过 NAT Gateway 的流量入侵呢？"Priya 问，"如果去 S3 的流量走 NAT，它就是从互联网上可寻址的。走网关终端节点，它就是私有的。"

这是网关终端节点的第二重好处，有时会被成本讨论盖过。经由 VPC 网关终端节点去往 S3 和 DynamoDB 的流量永远不会离开 AWS 网络，永远不会经过公共 IP 地址，并且受终端节点策略约束（一种基于资源的策略，可以限制该终端节点能访问哪些 S3 桶或 DynamoDB 表）。在一个存放客户数据的桶上加一个网关终端节点是额外的一层防护：即便桶策略配置错了，终端节点策略也可以把访问限制为来自特定 VPC 内部的流量。 

**AWS Global Accelerator：在边缘做路由**

Nimbus 从 us-west-2（俄勒冈）为东海岸用户提供服务时，延迟是 80ms。不是因为服务器远得离谱，而是因为波士顿和俄勒冈之间的公共互联网路由不够理想，在多个运营商网络之间来回弹跳。

**AWS Global Accelerator** 使用 AWS 的私有全球骨干网——一个由边缘站点组成的分布式网络，让流量经由 AWS 掌控的路径而非公共互联网的运营商跳转抵达你的应用。流量不走公共互联网路由，而是在最近的边缘站点进入 AWS 网络，沿着优化过的私有路径抵达你的应用。

对 Nimbus 来说，一位波士顿的用户会：

- **没有 Global Accelerator**：经由公共互联网运营商路由 → 约 80ms
- **有 Global Accelerator**：接入波士顿最近的 AWS 边缘 → 走 AWS 骨干网 → 抵达 us-west-2 → 约 60ms

Global Accelerator 不缓存内容（那是 CloudFront 的事）。它优化的是动态请求的网络路径。

在为 Nimbus API 启用 Global Accelerator 之后，Leo 对几个城市做了延迟对比：

| 城市 | 之前 | 之后 | 改善 |
|------|--------|-------|-------------|
| 西雅图（华盛顿州） | 12ms | 11ms | 8% |
| 洛杉矶（加利福尼亚州） | 28ms | 22ms | 21% |
| 芝加哥（伊利诺伊州） | 55ms | 40ms | 27% |
| 纽约（纽约州） | 82ms | 61ms | 26% |
| 伦敦（英国） | 145ms | 112ms | 23% |
| 东京（日本） | 180ms | 95ms | 47% |
| 悉尼（澳大利亚） | 210ms | 118ms | 44% |

改善对于地理上遥远的用户最为显著——东京从 180ms 降到 95ms，悉尼从 210ms 降到 118ms。对西雅图（紧邻俄勒冈的 us-west-2 数据中心）而言，改善较小——可供优化的公共互联网跳数本来就少。

"等等——可是*为什么*东京能改善 47%？"Maya 问，"如果数据中心还在 us-west-2，光速难道不才是真正的约束吗？"

"光速是下限，"Leo 说，"真正的约束是公共互联网路由。从东京到 us-west-2 的流量要穿越几十个自治系统——不同的运营商、不同的路由器、不同的对等协议。每一跳都增加延迟。Global Accelerator 让流量从东京的边缘站点经由 AWS 的私有光纤抵达 us-west-2，路径更短，路由调校得更好。"

从东京到 us-west-2 的理论最小值（基于光在光纤中的速度，往返约 15,500 公里）：约 77ms。有 Global Accelerator 的 95ms 已经在逼近这个理论最小值。没有它的 180ms 反映的是公共互联网路由的低效，而不是物理定律。

Global Accelerator 提供两个静态的 **anycast IP 地址**，路由到最近的边缘站点。与 CloudFront（使用会变化的动态 IP 地址）不同，这些 IP 是稳定的——对防火墙白名单以及需要固定 IP 供客户端连接的应用很有用。

**何时用 Global Accelerator，何时用 CloudFront**：

- CloudFront：静态和可缓存内容，CDN 用例
- Global Accelerator：动态内容、非 HTTP 协议（UDP、游戏、IoT），或者你需要一个静态 Anycast IP 地址时

## 搬运数据，而不只是流量：DataSync 与 Transfer Family

就在网络架构逐渐成形的同时，Maya 手上同时落下了三个新的连锁餐厅入驻项目。每一个都带有数据迁移需求——而且每个需求都不一样。

第一家连锁，Pacific Table，需要把 40 TB 的 NFS 文件共享搬到 S3。他们当前的文件存储在本地，分布在西雅图总部的四台文件服务器上。Leo 开始写迁移计划。

第二家连锁，Marisol Group，有一个会计团队，每天向一台本地 SFTP 服务器上传发票。这套 SFTP 工作流从 2015 年就在运行。会计人员只知道一件事：每天早上 9 点打开 SFTP 客户端，把发票丢进去，再关上。没人想改这个流程。"他们的会计用 WinSCP，"Maya 说，"这一点没得商量。"

"这是两种不同的工具，"Priya 说。

"是的，"Leo 说，"但这两种工具都存在。"

**AWS DataSync：打了激素的 rsync，外加一个 AWS 控制台**

对于 Pacific Table 的 40 TB 迁移，挑战不在带宽——西雅图办公室的上行连接很扎实。挑战在于编排：发现哪些文件存在、可靠地传输它们、校验校验和、安排传输时段以避免在工作时间挤爆办公室网络，以及在持续好几天的运行中监控进度。

**AWS DataSync** 是一个基于代理的数据迁移与复制服务。你在本地环境中安装一个轻量的 DataSync 代理——一台运行在 VMware 上或作为 EC2 实例的虚拟机。代理通过 NFS 或 SMB 连接到你的文件服务器，发现你的共享，并把它们同步到 AWS 中的目的地：一个 S3 桶、一个 EFS 文件系统或一个 FSx 文件系统。

把它想成打了激素的 rsync，外加一个 AWS 控制台。DataSync 负责处理：

- **发现**：代理自动清点你的源端共享
- **调度**：传输可以按既定计划运行（避开工作时间）或持续运行
- **校验**：DataSync 在两端计算校验和，并就任何不一致向你告警
- **监控**：传输进度、文件计数、错误报告和带宽利用率都能在控制台里看到
- **传输中加密**：所有数据在传输期间用 TLS 加密

对于 Pacific Table，Leo 在他们西雅图网络的一台虚拟机上装好了 DataSync 代理，把它指向那四个 NFS 共享，并配置了传输计划：工作日晚 8 点到早 6 点，周末持续运行。六天之后，全部 40 TB 落地 S3。他用 DataSync 内置的校验和报告验证了传输。零差异。

"那持续复制呢？"Maya 问，"迁移之后 Pacific Table 还会继续添加文件。"

"DataSync 支持增量传输，"Leo 说，"初次同步之后，它只拷贝变化的部分。我们可以把它当作复制作业每晚跑一次。"

**AWS Transfer Family：你的 SFTP 工作流，底层换成 S3**

Marisol Group 会计团队的需求则不同。没有人要离开 SFTP。会计们将继续用 WinSCP。问题在于：那些 SFTP 上传落到哪里？

目前，它们落在 Marisol 后台办公室的一台本地 Linux 服务器上。文件随后被手工搬进他们的会计系统。这台本地服务器需要维护、备份，还需要有人拥有 SSH 权限来管理它。

**AWS Transfer Family** 是一个全托管的 SFTP、FTPS 和 FTP 服务器——以 S3 或 EFS 作为存储目的地。你开通一个 Transfer Family 端点（它会得到一个主机名，以及可选的静态 IP 地址）。你的客户端用现有的 SFTP 软件连接它。他们上传文件时，文件直接落进一个 S3 桶。

会计团队什么也不用改。他们仍然每天早上 9 点打开 WinSCP。仍然用现有凭据连接一台 SFTP 服务器。仍然把发票丢进同一个文件夹。区别对他们是不可见的：在服务器侧，文件现在直接进了 S3，而不是落在一台本地 Linux 服务器上。

"而从 S3 出发，我们可以自动触发后续的整个工作流，"Priya 说，"一个 S3 事件触发一个 Lambda 函数，处理发票并写进会计系统。没有手工步骤。"

"所以会计们的工作流不变，"Maya 说，"但在我们这边，整件事自动化了。"

"是的。而且这台 SFTP 服务器本身是全托管的——不用打补丁，不用备份，没有要维护的服务器。"

Tom 已经查过定价了。Transfer Family 按端点可用的小时数加上每 GB 传输量收费。按 Marisol Group 的发票量，月成本远低于 $30。而它所取代的那台本地服务器的维护成本——硬件折旧、维护的工程时间、备份管理——要高得多。

> **考试技巧 — DataSync 与 Transfer Family**
>
> *SAA-C03 领域：设计高性能架构（领域 3，任务 3.1）*
>
> - **DataSync** = 把数据从本地批量搬进 AWS（NFS 或 SMB 文件共享 → S3、EFS 或 FSx）。考试信号："迁移文件共享"、"把 NFS 数据复制到 S3"、"本地到 AWS 的数据传输"、"文件数据的持续复制"。DataSync 使用安装在本地的代理；代理负责发现、调度和校验。
> - **Transfer Family** = 使用 SFTP、FTPS 或 FTP 协议的持续文件传输，无需更换客户端工具。考试信号："现有的 SFTP 工作流"、"合作伙伴通过 SFTP 上传文件"、"以 S3 为后端的 SFTP 服务器"、"SFTP 直接搬迁上云（lift-and-shift）"、"不能改变文件传输流程"。当需求是 SFTP 兼容性而非数据量时，Transfer Family 是答案。
> - **这个区别很重要**：DataSync 用于批量迁移和复制（基于代理、按计划驱动、网络优化）。Transfer Family 用于协议兼容的文件传输服务（基于端点、常驻在线、对客户端透明）。它们解决的是不同的问题。
> - DataSync 支持 S3、EFS 和 FSx 作为目的地。Transfer Family 支持 S3 和 EFS 作为存储后端。

**迁移服务器，而不只是文件：7 个 R 与 MGN**

Maya 手上的第三家连锁不只有文件——还有整台整台的服务器：一套运行在两台本地机器上的自研订座应用，没人想在搬迁之前重写它。迁移*应用程序*是一门独立的学问，AWS 描述了**七种迁移方式**（"7 个 R"），你大体上只需要能认出它们：

- **Rehost**（"直接搬迁"，lift and shift）：服务器原样搬走。最快，改动最少。
- **Replatform**（"边搬边修"，lift, tinker, and shift）：顺路做点小升级——比如把自管数据库搬到 RDS。
- **Repurchase**：抛弃旧系统，改买 SaaS。
- **Refactor**：按云原生重新设计。投入最大，回报也最大。
- **Retire**：原来根本没人在用。删掉它。
- **Retain**：暂时留在原地。
- **Relocate**：在虚拟化管理程序层面整体搬迁，什么都不改。

对于 rehost 的场景，工具是 **AWS Application Migration Service（MGN）**：代理把源服务器的磁盘逐块复制到 AWS 中的一个低成本暂存区；你随时可以启动测试副本；到切换的时候，MGN 把复制好的服务器转换成原生的 EC2 实例。搬迁、上线、收工——重构可以以后再做，按云上的节奏来。（它在组合规划上的两个伙伴，Application Discovery Service 和 Migration Hub，已于 2025 年底停止接受新客户——如果考试提到它们，把它们记成"资产清点发现"和"集中迁移跟踪"即可。）

**AWS Snow Family：物理选项**

还剩 4TB 历史数据集和那 17 小时的互联网估算没有着落。算完账之后，Leo 看了一眼 Snow Family 的定价页面，当场拍板。

对于几太字节以上、时间比简单性更重要的迁移，AWS 会把物理存储设备寄到你的所在地。你把数据装进去。再寄回去。AWS 把数据直接灌入 S3。

**Snowball Edge Storage Optimized**：80 TB 可用容量，加固外壳。2-5 个工作日送达你的所在地。你通过本地接口（NFS、S3 接口）装载数据。寄回。AWS 在收到后大约 1-3 个工作日内完成数据导入。

对于 Nimbus 的 4TB 迁移，流程如下：

1. **下单**：通过 AWS 控制台订购一台 Snowball Edge（用时 2 分钟，3 天发货）
2. **接入**：把设备接到西雅图办公室的网络；它会呈现为一个 NFS 挂载点
3. **拷贝**：用设备的 S3 兼容接口拷贝 4TB 历史订单数据：`aws s3 cp /data/orders s3://nimbus-data/ --endpoint-url http://192.168.1.100:8080 --profile snowballEdge`
4. **拷贝完成**：大约 2 小时（本地网络，不走互联网）
5. **寄回**：把设备寄回 AWS（含预付运费标签）
6. AWS 在收到后 72 小时内**导入**数据到 S3
7. **核验**——S3 提供一份作业完成报告，列出每个已传输的文件和校验和

总耗时：3 天送达 + 2 小时拷贝 + 1 天回程运输 + 2 天导入 = 大约 7 个日历日。对比连续约 17 个小时的传输——后者需要一条稳定、不中断的互联网连接，而且会在整夜以及大半个工作日里挤爆办公室的上行链路。

成本：Snowball Edge 设备租金 10 天 $300。运费（双程）：约 $80。S3 数据传入免费。迁移总成本：**$380**。

对比约 17 小时 875 Mbps 的持续互联网占用：VPN 隧道本身免费（$0.05/小时，但隧道本来就在跑）；S3 传入免费。这条"免费"的互联网路径有它的真实成本：工程时间（盯着一场 17 小时的传输）、风险（任何中断都需要重启）、机会成本（传输窗口期间他们的互联网连接被占满）。Leo 下了订单。后续如何，见本章的片尾彩蛋。

## 优势与局限

**Site-to-Site VPN**：

- 设置快，成本低
- 走公共互联网路径意味着延迟波动
- 带宽上限有限（每条隧道 1.25 Gbps）
- Accelerated VPN 选项以略高的成本改善延迟

**Direct Connect**：

- 一致、私有、高带宽
- 设置慢，持续性成本可观
- 物理电路是单点故障（增加冗余或保留 VPN 备份）
- 与传出流量节省的盈亏平衡点大约在每月 10-15 TB，取决于定价场景

**AWS Snow Family**：

- 对于 1-2 TB 以上的一次性迁移，往往比网络传输更快也更便宜
- 迁移期间不占用互联网带宽
- 设备租期 10 天；运费预付

**Transit Gateway**：

- 极大简化多 VPC 连接
- 传递路由（不同于 VPC 对等）
- 隔离路由表无需单独的对等连接即可实现分段
- 附件多了成本会累积

**VPC 终端节点**：

- S3/DynamoDB 的安全与成本双重收益（免费的网关终端节点）
- 消除了 AWS 服务流量的 NAT Gateway 成本
- 终端节点策略在 IAM 和桶策略之外增加一层访问控制
- 面向其他服务（Secrets Manager、SSM、SES）的接口终端节点能让流量保持私有，但每个 AZ 每小时约 $0.01

**Global Accelerator**：

- 改善全球用户的动态应用延迟：实践中遥远用户改善 33-47%
- 固定的 Anycast IP（不像 CloudFront 的动态 IP）——便于防火墙白名单
- 支持非 HTTP 协议（UDP、TCP）——CloudFront 仅支持 HTTP/HTTPS
- 额外成本（每个加速器 $0.025/小时 + 数据传输）

## 总结

第 24 章的 Aurora 工作优化了 Nimbus 向自己的应用提供数据的方式。本章关注的是数据如何在外部世界与 AWS 之间移动——以及如何让这种移动更可靠、更快、更省钱。

- **Site-to-Site VPN**：本地与 VPC 之间走公共互联网的加密隧道。设置快、成本较低、延迟有波动。两条隧道做冗余。每条隧道最高 1.25 Gbps。
- **Direct Connect**：通往 AWS 的私有专用光纤连接。延迟可预测、带宽更高、设置需数周、成本可观。按 Nimbus 的定价场景，与 VPN 在传出费用上的盈亏平衡点约为每月 13.5 TB。
- **AWS Snow Family**：用于批量数据迁移的物理存储设备。对多 TB 级迁移比互联网传输更快。Nimbus 的 4TB 迁移总共 $380，对比约 17 小时的网络饱和。
- **Transit Gateway**：VPC 与本地连接的枢纽。支持传递路由（不同于 VPC 对等）。支持隔离路由表，控制哪些 VPC 能触达哪些。可扩展到数百条连接。
- **VPC 终端节点**：无需 NAT Gateway 即可私密访问 AWS 服务。网关终端节点（S3、DynamoDB）免费——给每一个访问 S3 或 DynamoDB 的 VPC 都加上。为 Nimbus 每月省了 $15.60，并把 S3/DynamoDB 流量从 NAT Gateway 上撤了下来。
- **Global Accelerator**：把动态流量路由到 AWS 私有骨干网上，实现全球更低、更一致的延迟。静态 Anycast IP。遥远用户的延迟改善达 33-47%（东京：180ms → 95ms；悉尼：210ms → 118ms）。不是 CDN——不做缓存。
- **AWS DataSync**：基于代理的服务，把本地 NFS/SMB 文件数据迁移和复制到 S3、EFS 或 FSx。负责调度、校验和验证、监控。用于一次性迁移和文件共享的持续复制。
- **AWS Transfer Family**：以 S3 或 EFS 为后端的托管 SFTP、FTPS 和 FTP 服务器。让现有的 SFTP 客户端不改变工作流就能把文件上传到 S3。

## 考试技巧

*SAA-C03 领域：设计高性能架构（领域 3，任务 3.4）*

- **VPN 与 Direct Connect 的信号**：VPN ="加密通往 VPC 的流量"、"快速设置"、"对成本敏感"。Direct Connect ="一致的低延迟"、"大量数据传输"、"私有连接"、"合规要求私有网络"。
- **Transit Gateway 与 VPC 对等**：对等不具传递性（A→B→C 不意味着 A→C）。Transit Gateway 具有传递性。"许多 VPC 需要互相通信"→ Transit Gateway。
- **VPC 网关终端节点**：免费。仅限 S3 和 DynamoDB。改路由表。没有额外费用。考试场景："降低从私有子网访问 S3 的数据传输成本"→ 网关终端节点。
- **Global Accelerator 与 CloudFront**：Accelerator = 动态内容、非 HTTP、静态 IP、网络优化。CloudFront = 缓存、HTTP 内容、CDN。
- **Direct Connect + VPN**：你可以用 VPN 作为 Direct Connect 连接的备份。如果 Direct Connect 电路故障，流量切换到 VPN。比单独 VPN 贵，但比单独 Direct Connect 更可靠。
- **Direct Connect Gateway**：把一条 Direct Connect 电路连接到跨多个区域或账户的多个 VPC。没有它，一条 Direct Connect 电路只能连接到一个区域中的一个 VGW。
- **AWS Snow Family**："大规模数据迁移"、"传输速度太慢"、"PB 级迁移"→ Snow Family。Snowball Edge = 最高 80TB。先算传输账：如果走现有网络搬这些数据大概需要一周或更久，答案就是物理设备。*现实核查（2026）*：AWS 一直在让这个家族退役——Snowmobile 于 2024 年撤出，Snowcone 于 2024 年底停产，自 2025 年 11 月起 Snow 设备不再面向新客户提供（AWS 现在指向走高速链路的 DataSync 和 **Data Transfer Terminals**，即可自带硬盘前往的安全场所）。SAA-C03 题库早于这一切，所以在考试中，"数周的网络传输、带宽受限"仍然指向 Snowball。
- **Transit Gateway 路由表**：Transit Gateway 支持多张路由表用于网络分段。考试信号："隔离生产 VPC 与预发布"且通过 Transit Gateway 共享连接 → 独立的路由表。
- **Global Accelerator 固定 IP**：与 CloudFront 不同，Global Accelerator 提供两个静态 Anycast IP。考试信号："应用需要固定的 IP 地址供客户端加白名单"或"UDP 流量"→ Global Accelerator（CloudFront 仅支持 HTTP/HTTPS）。
- **AWS DataSync 信号**："把 NFS/SMB 文件共享迁移到 S3/EFS/FSx"、"本地文件数据的持续复制"、"基于代理的文件迁移"。DataSync 不是用来做协议兼容的 SFTP 传输的——它用于文件共享的批量迁移和复制。
- **AWS Transfer Family 信号**："现有的 SFTP 工作流"、"合作伙伴或客户通过 SFTP 上传文件"、"把 SFTP 服务器搬上云且不改客户端工具"、"以 S3 为后端的 SFTP/FTPS/FTP"。Transfer Family 不是数据迁移工具——它是一个托管的协议端点。区别在于：DataSync 按计划批量搬数据；Transfer Family 提供一个常驻在线的 SFTP/FTP 端点，用于持续的文件上传。
- **MGN（Application Migration Service）**："快速迁移数百台虚拟机，不改代码"、"rehost / 直接搬迁服务器到 EC2"→ MGN（块级复制、测试启动、切换为原生 EC2 实例）。DataSync 搬的是*文件*；DMS 搬的是*数据库*；MGN 搬的是*整台服务器*。

**练习 1 — 回顾**

解释 AWS Site-to-Site VPN 和 AWS Direct Connect 之间的区别。在什么场景下你会分别选择它们？

*（提示：考虑设置时间、成本、延迟一致性和带宽要求。）*

**练习 2 — SAA-C03 场景**

*场景*：一家金融服务公司需要从其本地数据中心到 AWS 的私有、加密、专用网络连接。他们每天传输 500GB 的敏感金融数据。连接必须具有一致、可预测的延迟，且不得经过公共互联网。他们还需要一条备份连接，以防主连接故障。

哪种架构最符合这些要求？

A) 使用 BGP 路由的 Site-to-Site VPN，外加第二条 VPN 做冗余  
B) 带 Direct Connect Gateway 的 Direct Connect 托管连接  
C) 通过不同互联网提供商的两条 Site-to-Site VPN 连接  
D) 一条 Direct Connect 连接，配 Site-to-Site VPN 作为备份

**提示 1**："不得经过公共互联网"——VPN 流量走公共互联网（加密）。只有 Direct Connect 是私有的。

**提示 2**："一致、可预测的延迟"——公共互联网上的 VPN 性能会波动。Direct Connect 是稳定的。

**提示 3**："备份连接"——当 Direct Connect 作为主连接时，推荐的方案是什么？

**答案**：D

**解释**：Direct Connect 提供一条不经过公共互联网的私有、专用连接——满足私密性和延迟要求。Site-to-Site VPN 作为备份提供冗余：如果 Direct Connect 电路故障，流量切换到加密的 VPN 上。这是 Direct Connect 的标准高可用模式。

**为什么不是 A？** Site-to-Site VPN 流量经过公共互联网，违反了"不得经过公共互联网"的要求。

**为什么不是 B？** 托管连接提供了一条 Direct Connect 连接，但选项 B 不包含备份。没有备份的单一 Direct Connect 是单点故障——物理光纤可能被挖断。

**为什么不是 C？** 通过不同 ISP 的两条 VPN 连接仍然走公共互联网，即使加了密也一样。不满足私有网络要求。

## 片尾彩蛋

数据迁移在 8 个日历日内完成——3 天等 Snowball Edge 送达，94 分钟拷贝数据，4 天等 AWS 收到设备并导入数据，最后再同步一次 Snowball 在途期间累积的增量。整件事的动手时间：不到四个小时。

最后那一步很关键。Snowball Edge 拷贝的是 4TB 数据集在某个时间点的快照。它在途期间，生产数据库一直在运行——新订单不断产生，新记录不断创建。通过 VPN 的增量同步是 12GB，18 分钟完成。

"大头是 Snowball 搬的，"Leo 说，"同步只是补上这 8 天里净增的数据。"

"我已经部署了——哦，"Leo 在 94 分钟后看着 Snowball Edge 上的拷贝完成时说，"我本该在本地拷贝上设置带宽限速，免得工作时间挤爆办公室网络。"

他没有设限速。办公室的互联网倒是没事——Snowball 是本地网络操作。但当拷贝逼近 9 Gbps 的本地吞吐量时，网络交换机短暂地成了瓶颈。

"重点在于，"他修好限速设置之后说，"超过某个数据量，实体邮寄就是比互联网快。"

"这要么是显而易见，要么是违反直觉，"Maya 说，"取决于你怎么想。"

"下次，"Leo 说，"我们应该搭一条 Direct Connect。"

Tom 没有去拿计算器——早在 Direct Connect 第一次被提起时，他就已经算过了：每月大约一千，端口加电路。

"以我们现在做的事情，大概不值得。但如果我们开始每月在办公室和 AWS 之间移动超过 10TB 的数据，Direct Connect 在数据传输上的节省就能抵消这笔成本。"

"所以我们监控数据传输量，"Priya 说，"等它越过阈值再重新评估。"

"这就是成本感知的架构，"Tom 说。

"这从来就是重点所在，"Maya 说。

Priya 从房间另一头看完了整场迁移。"下次我们再做这种事，"她说，"能不能在数据进入生产、业务依赖它之前做？迁移活动中的数据，永远比迁移静止的数据更危险。"

"业务在跑的时候，数据就从来没有静止过，"Leo 说。

"我知道，"她说，"这正是重点。在你需要迁移之前就规划好。而不是之后。"

Tom 已经算过在 us-east-1 维持一套随时能承接迁移的第二套基础设施要花多少钱。这个数字他暂时没有说出来。眼下还有更紧迫的章节要收尾。
