# 第二十五章：私人高速公路

站起来一会儿。甩一甩手。

我们要谈谈数据移动。不是在 AWS 内部的服务之间，而是在现实世界与 AWS 之间——在你的办公室和你的云基础设施之间，在大陆之间。

Nimbus 的基础设施团队（现在有四名工程师）在西雅图的一个共享办公室工作。他们需要访问他们管理的 AWS 基础设施。某些操作需要连接到 VPC 中的资源。

目前，他们在笔记本电脑上使用 VPN 访问公共子网中的堡垒机，然后从那里 SSH 到资源。

这能用。就是很慢。VPN 连接通过公共互联网路由：西雅图 → 跨国光纤 → 多个运营商跳转 → us-east-1。每次往返超过 80 毫秒。

"对于日常 SSH，这是可以接受的，"Leo 说，"但我们即将开始迁移我们的分析数据库。4 太字节的历史订单数据。通过这个连接，迁移将需要数周。"

"我们需要更好的连接，"Maya 说。

"私有连接，"Priya 补充道，"不通过公共互联网。"

把它想象成通勤上班。站点间 VPN 就像在公共道路上开车：你锁上车门（加密），但仍然与其他所有人共享车道，交通堵塞会让你无法预测地减速。Direct Connect 就像在高速公路上租用一条专用的私人车道——没有共享流量，速度一致，每月通行费更高。大多数时候公共道路没问题。当你在紧张的时间表内运输一卡车有价值的货物时，你会为私人车道付费。

**AWS Site-to-Site VPN：快速选项**

**AWS Site-to-Site VPN** 在你的本地网络和你的 VPC 之间创建一个加密隧道，通过公共互联网传输。

设置：

1. 创建附加到你的 VPC 的虚拟私有网关（VGW）
2. 创建代表你本地路由器的客户网关
3. 在它们之间建立两个 VPN 隧道（用于冗余）

流量是加密的（AES-256）。它通过公共互联网传输，这意味着延迟取决于互联网条件。AWS 自动提供两个隧道用于冗余——如果一个隧道有问题，流量切换到另一个。

**何时使用站点间 VPN**：

- 快速设置（几分钟到几小时）
- 成本效益高（每个 VPN 连接 $0.05/小时）
- 带宽：每个隧道最高 1.25 Gbps
- 用例可接受的互联网延迟

对于 Nimbus 的 4TB 迁移，基于互联网的 VPN 在最大 1.25 Gbps 时需要：4TB / 1.25 Gbps ≈ 最少 7 小时，实际开销接近 12-20 小时。可以接受，但公共互联网路径上的拥塞使其不可预测。

"另一个选项是什么？"Tom 问。

**AWS Direct Connect：专用线路**

**AWS Direct Connect** 在你的位置（或你的共同托管设施）和 AWS 之间建立一个专用、私有的网络连接。流量永远不会接触公共互联网。

Direct Connect 是一个物理连接——从你的网络到 AWS Direct Connect 位置的光纤线路。你与电信提供商合作建立物理电路。AWS 在他们那边提供端口。

**优势**：

- 一致、可预测的延迟（无公共互联网变化）
- 速度从 50 Mbps 到 100 Gbps
- 数据传输成本低于互联网（Direct Connect 数据传输率比标准 AWS 数据传出率便宜）
- 更安全（私有电路，非公共互联网）

**权衡**：

- 设置需要数周到数月（物理基础设施配置）
- 成本明显高于 VPN（每端口 $0.025-0.30/小时，加上电信电路成本——通常每月最少 $500-1000+）
- 没有内置冗余（你自己建立冗余电路）
- 没有多个电路的情况下不适合地理分布的办公室

对于 Nimbus：Direct Connect 对于他们目前的规模来说是过度设计。但对于具有大量数据传输量或需要私有网络连接合规要求的企业，Direct Connect 能够收回成本。

**托管连接：中间方案**

不是每个组织都能承担 100 Gbps 的专用光纤电路。**Direct Connect 托管连接**允许 AWS Direct Connect 合作伙伴（经批准的电信运营商）配置你与其他客户共享的低于 1Gbps 的连接。

设置更快（几天到几周，而不是几个月），成本低于专用连接。权衡是：共享容量意味着吞吐量不那么一致。

对于 Nimbus（随着他们的增长）：通过合作伙伴的 500 Mbps 托管连接将以合理的价格提供私有连接。

**AWS Transit Gateway：VPC 的中心辐射式结构**

随着 Nimbus 的增长，他们会积累多个 VPC：生产 VPC、测试 VPC、分析 VPC、安全工具 VPC。

没有仔细规划，连接这些 VPC 需要完整的 VPC 对等连接网格。4 个 VPC：6 个对等连接。10 个 VPC：45 个对等连接。20 个 VPC：190 个连接。这不可扩展。

**AWS Transit Gateway** 是一个连接多个 VPC 和本地网络的网络枢纽。不是对等连接的网格，每个 VPC 都连接到 Transit Gateway。Transit Gateway 在它们之间路由流量。

```
本地环境 ──── Direct Connect ──┐
                                  │
生产 VPC ───────────────── Transit Gateway
测试 VPC ──────────────────── Transit Gateway
分析 VPC ────────────────── Transit Gateway
安全 VPC ─────────────────── Transit Gateway
```

**传递路由**：如果 VPC A 和 VPC B 都连接到 Transit Gateway，它们可以通信——无需直接对等。Transit Gateway 处理路由。与 VPC 对等（不传递）不同，Transit Gateway 启用了中心辐射式拓扑。

**Transit Gateway 成本**：按附件（VPC 或 VPN/Direct Connect 连接）加上每 GB 处理数据收费。在规模上，这值得换来的简单性。

**VPC 终端节点：对 AWS 服务的私有访问**

一个微妙的成本和安全问题：当你的 EC2 实例（在私有子网中）调用 S3 API 时，流量通过 NAT Gateway 路由（到达互联网，S3 的公共端点就在那里）。你为 NAT Gateway 处理付费。

**VPC 终端节点**允许你的 VPC 中的资源私密地与 AWS 服务通信，无需通过公共互联网——也不需要 NAT Gateway。

两种类型：

**网关终端节点**（免费）：用于 S3 和 DynamoDB。你在路由表中添加一条路由，将 S3 或 DynamoDB 流量定向到终端节点，而不是 NAT Gateway。创建免费；使用免费。

**接口终端节点**（按价格收费）：用于其他 AWS 服务（SQS、SNS、Secrets Manager、SSM 等）。在你的子网中创建一个 ENI（弹性网络接口），带有私有 IP。到服务的流量使用此私有 IP。每个 AZ 每小时约 $0.01 加上数据处理费。

Tom 在了解到 S3 和 DynamoDB 的网关终端节点是免费的后，立即创建了这些终端节点。NAT Gateway 数据处理费降低了 30%。

**AWS Global Accelerator：在边缘路由**

当 Nimbus 从 us-east-1（弗吉尼亚）为西海岸用户提供服务时，延迟是 80 毫秒。不是因为服务器距离过远，而是因为西雅图和弗吉尼亚之间的公共互联网路由不理想，在多个运营商网络之间反复跳转。

**AWS Global Accelerator** 使用 AWS 的私有骨干网络（与 CloudFront 相同的基础设施）在用户和 AWS 应用程序之间路由流量。流量不是通过公共互联网路由，而是在最近的边缘位置进入 AWS 网络，并通过优化的私有路径到达你的应用程序。

对于 Nimbus，西雅图的用户：

- **没有 Global Accelerator**：通过公共互联网运营商路由 → 约 80ms
- **有 Global Accelerator**：访问西雅图最近的 AWS 边缘 → 通过 AWS 骨干传输 → 到达 us-east-1 → 约 45ms

Global Accelerator 不缓存内容（那是 CloudFront）。它优化动态请求的网络路径。

**何时使用 Global Accelerator 而非 CloudFront**：

- CloudFront：静态和可缓存内容，CDN 用例
- Global Accelerator：动态内容、非 HTTP 协议（UDP、游戏、IoT）或需要静态 Anycast IP 地址时

## 优势与局限

**站点间 VPN**：

- 快速设置，低成本
- 公共互联网路径意味着可变延迟
- 有限带宽上限

**Direct Connect**：

- 一致、私有、高带宽
- 设置慢，持续性高成本
- 物理电路是单点故障（添加冗余）

**Transit Gateway**：

- 大幅简化多 VPC 连接
- 传递路由（不像 VPC 对等）
- 对于多个附件成本累积

**VPC 终端节点**：

- S3/DynamoDB 的安全和成本优势（免费网关终端节点）
- 消除 AWS 服务流量的 NAT Gateway 成本

**Global Accelerator**：

- 提高全球用户的动态应用延迟
- 固定 Anycast IP（不像 CloudFront 的动态 IP）
- 额外成本（每个加速器 $0.025/小时 + 数据传输）

## 总结

- **站点间 VPN**：通过公共互联网在本地和 VPC 之间的加密隧道。快速设置，成本较低，可变延迟。
- **Direct Connect**：到 AWS 的私有、专用光纤连接。可预测延迟，更高带宽，设置需要数周，成本显著。
- **Transit Gateway**：VPC 和本地连接的枢纽。启用传递路由。可扩展到数百个连接。
- **VPC 终端节点**：无需 NAT Gateway 私密访问 AWS 服务。网关终端节点（S3、DynamoDB）免费。
- **Global Accelerator**：通过 AWS 骨干路由动态流量，实现全球更低、更一致的延迟。

## 考试技巧

*SAA-C03 领域：设计高性能架构（领域 3，任务 3.4）*

- **VPN 与 Direct Connect 信号**：VPN ="加密到 VPC 的流量"、"快速设置"、"对成本敏感"。Direct Connect ="一致的低延迟"、"大数据传输"、"私有连接"、"需要私有网络的合规"。
- **Transit Gateway 与 VPC 对等**：对等是不传递的（A→B→C 不允许 A→C）。Transit Gateway 是传递的。"需要通信的多个 VPC" → Transit Gateway。
- **VPC 网关终端节点**：免费。只有 S3 和 DynamoDB。路由表更改。没有额外费用。考试场景："从私有子网降低 S3 访问的数据传输成本"→ 网关终端节点。
- **Global Accelerator 与 CloudFront**：加速器 = 动态内容、非 HTTP、静态 IP、网络优化。CloudFront = 缓存、HTTP 内容、CDN。
- **Direct Connect + VPN**：你可以使用 VPN 作为 Direct Connect 连接的备份。如果 Direct Connect 电路失败，流量切换到 VPN。比单独 VPN 更昂贵，比单独 Direct Connect 更可靠。
- **Direct Connect Gateway**：将 Direct Connect 电路连接到跨多个区域或账户的多个 VPC。没有它，Direct Connect 电路只能连接到一个区域中的一个 VGW。

**练习 2 — 考试练习**

*场景*：一家金融服务公司需要从其本地数据中心到 AWS 的私有、加密、专用网络连接。他们每天传输 500GB 的敏感金融数据。连接必须具有一致、可预测的延迟，且不得经过公共互联网。他们还需要一个备份连接以防主连接失败。

哪种架构最符合这些要求？

A) 使用 BGP 路由的站点间 VPN 和第二个 VPN 用于冗余  
B) 以站点间 VPN 作为备份的 Direct Connect 连接  
C) 通过不同互联网提供商的两个站点间 VPN 连接  
D) 带 Direct Connect Gateway 的 Direct Connect 托管连接

**提示 1**："不得经过公共互联网"——VPN 流量经过公共互联网（加密）。只有 Direct Connect 是私有的。

**提示 2**："一致、可预测的延迟"——公共互联网 VPN 性能会变化。Direct Connect 是一致的。

**提示 3**："备份连接"——当 Direct Connect 是主连接时，推荐什么方法？

**答案**：B

**解释**：Direct Connect 提供一个不经过公共互联网的私有、专用连接——满足隐私和延迟要求。站点间 VPN 作为备份提供冗余：如果 Direct Connect 电路失败，流量切换到加密的 VPN。这是 Direct Connect 的标准高可用性模式。

**为什么不选 A？** 站点间 VPN 流量经过公共互联网，这违反了"不得经过公共互联网"的要求。

**为什么不选 C？** 通过不同 ISP 的两个 VPN 连接仍然经过公共互联网，即使加密了也不行。不满足私有网络要求。

**为什么不选 D？** 托管连接提供 Direct Connect 连接，但选项 D 不包括备份。没有备份的单一 Direct Connect 是单点故障——物理光纤可能被切断。
