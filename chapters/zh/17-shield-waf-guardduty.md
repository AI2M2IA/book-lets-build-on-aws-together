# 第17章：监视者们

罗马尼亚 IP 的事件已经被控制住了。秘密在 Secrets Manager 里。凭证已轮换。网络控制已收紧。

但 Priya 提出了那个为第16章收尾的问题："如果 CloudTrail 中出现了不寻常的东西，我们怎么会知道？"

诚实的答案是：他们多半不会知道。

---

*所有能锁的都锁上了。秘密在 Secrets Manager 里。加密密钥在 KMS 里。网络流量由安全组和 NACL 控制。边界防御很扎实。但边界防御假设你在攻击到来之前就知道攻击长什么样。Priya 问的是另一个问题：那些你看不见、不知道会来的攻击怎么办？*

---

CloudTrail 每天记录数千个事件。没有人能读完所有这些。Priya 每周手动检查，但这意味着某件事可能在周二发生，直到下周一才被注意到。

"我们需要一些东西来替我们监视日志，"她说。

Maya 抬起头。"自动地？"

"自动地。"

"那如果有人试图闯进来呢？"Priya 继续说。"不只是被盗的凭证——如果有人发起 DDoS 呢？如果他们开始探测我们的 API 端点寻找注入漏洞呢？如果他们已经在里面了而我们还不知道呢？"

"那是三个不同的问题，"Leo 说。

"是的，"Priya 说。"而 AWS 有三个不同的服务来应对它们。"

**三类威胁**

针对云应用程序的安全威胁通常分为三类：

**容量攻击（DDoS）**：攻击者发送如此多的流量，以至于你的应用程序无法响应合法用户。攻击可能是数百万个 HTTP 请求，或者一场旨在耗尽服务器连接表的 TCP SYN 包洪水。

**应用层攻击（漏洞利用）**：攻击者发送专门构造的请求，以利用应用程序中的弱点——SQL 注入、跨站脚本、使解析器崩溃的畸形输入。

**行为异常（侦察和入侵）**：不应该发生的 API 调用（有人在凌晨3点查询你的整个用户数据库）、不寻常的 IAM 活动（凭证从一个新的国家被使用），或者到意外目的地的网络流量。

AWS 为每一类都有一个专用服务：

- **AWS Shield**：DDoS 保护
- **AWS WAF**：应用层保护
- **Amazon GuardDuty**：行为威胁检测

**AWS Shield：DDoS 吸收器**

**AWS Shield 标准版**对所有 AWS 客户自动启用，不额外收费。它保护免受最常见的第3层（网络）和第4层（传输）DDoS 攻击——SYN 洪水、UDP 洪水、DNS 放大攻击。

CloudFront、Route 53 和 Elastic Load Balancing 坐落在 AWS 网络的边缘。当 DDoS 攻击针对你的应用程序时，它首先撞上这些托管服务。AWS 的网络基础设施在攻击到达你的 EC2 实例之前就把它吸收掉了。

**AWS Shield 高级版**是付费的高级层级（每个组织每月3,000美元，需要一年期承诺）。它是一个独立的订阅——它*不*包含在任何 AWS Support 计划中。它增加了：

- 对 EC2、ELB、CloudFront、Global Accelerator 和 Route 53 的保护
- 近实时的攻击通知
- 接入 AWS Shield 响应团队（SRT）——可以帮助你应对攻击的安全工程师（启用 SRT 还额外要求 Business 或 Enterprise Support 计划）
- 成本保护：如果攻击导致你的账单激增，AWS 会返还激增的费用
- 增强的第7层（应用层）DDoS 检测和缓解

"那每个月要花多少钱？"Tom 问。

"三千美元，"Priya 说。"每个组织。"

Tom 沉默了片刻。

"对于营收数百万的企业来说，一次让他们宕机两小时的 DDoS 的代价远超三千美元，"Priya 说。

Tom 默默地算了算。

"我们先用标准版，"他最终说。

**那次 DDoS 事件：Shield 实战是什么样子**

上线八个月后，Nimbus 遭遇了第一次真正的 DDoS 攻击。

它开始于一个星期二的上午11点43分。负载均衡器的 CloudWatch 仪表板显示，传入的连接请求在不到九十秒内从正常的每分钟3,000次飙升到每分钟180,000次。来源 IP 分布在四十个国家，入站流量峰值达到大约每秒五十吉比特。模式毫无悬念：一个僵尸网络在发动 SYN 洪水。

Leo 先看到了 CloudFront 的指标。"请求速率涨了六十倍。响应时间在飙升。"

Priya 把 CloudWatch 指标并排调了出来：边缘的连接尝试在垂直攀升，而实际到达源站的请求——一条平线。"Shield 标准版在硬吃这波攻击，"她说。没有告警，没有仪表板事件，没有通知。Shield 标准版默默工作：它始终开启、免费，并且**不提供任何攻击可见性**——没有事件控制台，没有通知，没有 DDoS 响应团队。（那种可见性——近实时的攻击仪表板和告警——正是 Shield *高级版*卖的东西。）Priya 能看到这次攻击的唯一途径，就是她自己的 CloudWatch 指标。

Shield 标准版在最初两分钟内自动检测到了 SYN 洪水并启动了缓解。攻击流量在 CloudFront 全球的边缘节点被吸收——为合法内容提供服务的那750多个接入点，同样吸收了攻击流量。

到上午11点52分——攻击开始九分钟后——Shield 的缓解措施已经把源站的请求速率拉回到正常水平。攻击在网络层面仍在继续，但缓解措施在处理它。整个过程中 Nimbus 的应用程序持续为用户提供服务。

"用户没察觉到？"Leo 看着错误率指标问。

"错误率上升了大约百分之二，持续了大约四分钟，"Priya 说。"一些用户的响应稍微慢了一点。没有宕机。应用程序一直在线。"

"因为 Shield 在边缘吸收了洪水。"

"在它到达我们的负载均衡器之前。那场五十吉比特的 SYN 洪水撞上的是 CloudFront。等到流量模式被识别并缓解时，我们的源站只见到了正常的请求量。"

攻击持续了四十七分钟。到中午12点30分，边缘指标回到了基线——这是 Shield 标准版给你的唯一"已解决"信号。

"而这还只是 Shield 标准版，"Tom 说。"免费版。"

"第3层和第4层的攻击。标准版自动防御这些。如果攻击更复杂——比如第7层的 HTTP 洪水，每个请求看起来都是合法的——标准版就不够了。那需要 Shield 高级版加上 WAF。"

Tom 在他的安全路线图上写下了"监控第7层 DDoS 模式"。

**AWS WAF：应用程序过滤器**

**AWS WAF（Web 应用程序防火墙）**在 HTTP 级别运作——它在 Web 请求到达你的应用程序之前检查请求的内容。

WAF 通过 **Web ACL（访问控制列表）**进行配置——定义允许、阻止或计数哪些请求的规则集。

WAF 可以附加到：

- CloudFront 分发（在边缘全球范围内检查请求）
- 应用负载均衡器（在区域级别检查请求）
- API Gateway
- AWS AppSync

**WAF 托管规则**：AWS 和第三方供应商发布预构建的规则集：

- **AWS 托管规则——核心规则集**：与配套规则组（SQL 数据库、已知恶意输入）一起，覆盖 OWASP 十大漏洞（SQL 注入、XSS、命令注入、路径遍历等）
- **AWS 托管规则——已知恶意输入**：阻止与已知攻击模式匹配的请求
- **AWS 托管规则——Amazon IP 信誉列表**：阻止已知与僵尸网络和扫描器相关的 IP
- **AWS 托管规则——机器人控制**：识别和管理机器人流量

你也可以创建自定义规则：

- "阻止任何 User-Agent 头包含'sqlmap'的请求"（一个常见的 SQL 注入扫描器）
- "速率限制：每个 IP 每5分钟最多允许1000个请求"
- "阻止任何参数值中包含 `<script>` 的请求"

对 Nimbus 而言，实际的设置是：在 CloudFront 分发上启用 WAF，并开启核心规则集。这样在请求到达 EC2 实例之前，就阻止了最常见的攻击模式。

你可能会想：如果 WAF 阻止的是已知攻击模式，那当出现一个 WAF 不认识的新攻击模式时会怎样？WAF 托管规则集会随着新威胁的出现由 AWS 和第三方供应商更新——你不必手动更新规则。但你说得对，WAF 本质上是针对已知模式的被动防御。全新的、新颖的攻击技术不会被一条尚不存在的规则阻止。这正是 GuardDuty 与 WAF 并存的原因：WAF 过滤前门，GuardDuty 监视屋子里的异常行为。一种新型攻击可能会穿过 WAF，但 GuardDuty 仍然可以标记它引发的异常活动——不寻常的 API 调用、意外的网络目的地、与基线不符的访问模式。

**我们有没有想过 WAF 产生误报会怎样？**Priya 问。"一个合法用户的请求被核心规则集挡掉了呢？"

"WAF 有一个'计数（Count）'模式，"Leo 说。"它不阻止，只是对匹配的请求计数。你先在计数模式下运行，审查它本来会阻止的内容，确认没有误报，然后再切换到阻止模式。"

"好，"Priya 说。"我们从计数模式开始。"

**创建一条 WAF 规则：速率限制的故事**

在以计数模式启用 WAF 两周后，Priya 审查了日志。核心规则集的发现很干净——合法流量没有误报，只有少数几次来自自动扫描器的 SQL 注入尝试被识别。

但她注意到一个核心规则集没有标记的模式：一个 IP 地址在五分钟内向 `/api/search` 发出了847个请求。每个请求在结构上都是有效的。但五分钟847次搜索，这不是人类。

"价格爬虫，"她说。"有人在自动查询我们的餐厅搜索，建一个竞品价格数据库。"

"我们在乎吗？"Leo 问。

"它消耗我们的计算资源，并且违反了我们的服务条款，"Tom 说。

"我们在乎，"Priya 确认道。

她创建了一条自定义的 WAF 基于速率的规则：

```
Rule name: RateLimitSearchAPI
Rule type: Rate-based rule
Rate limit: 100 requests per IP address
Evaluation window: 5 minutes (configurable: 1, 2, 5, or 10 minutes)
Scope-down statement: URI path starts with /api/search
Action: Block
```

scope-down 语句很重要——速率限制只适用于 `/api/search`。到其他端点的合法 API 流量不受影响。还要注意阻止机制的工作方式：没有固定的"惩罚"时长——WAF 持续地重新评估每个 IP 的请求速率，在速率高于限制时阻止它，一旦速率降回限制之下就（通常在几秒内）解除阻止。

她先把它设置为计数模式。运行了24小时。唯一触发规则的 IP 就是那个爬虫。没有任何合法用户在五分钟内向搜索端点发送过超过12个请求。

她切换到阻止模式。爬虫的下一个请求收到了403。它换了一个 IP。速率限制把那个也逮住了。

"他们最终会绕过去的，"Leo 说。"分散到更多 IP 上。"

"到那时他们就要用更多基础设施、付出更多成本、拿到更少数据，"Priya 说。"我们不需要完全阻止他们。我们需要让代价高到不值得。"

"那每个月要花多少钱？"Tom 问。

WAF 按 Web ACL 每月计费、按规则每月计费，再加上每百万请求的费用。对 Nimbus 的设置——CloudFront 上一个 Web ACL、五条规则——大约每月15美元加请求费用。

Tom 当场就批准了。

**Amazon GuardDuty：行为分析师**

"等等——但我们*为什么*要那样做？"Maya 问。"如果 WAF 在阻止攻击、Shield 在吸收洪水，为什么我们还需要第三个服务？GuardDuty 到底在监视什么？"

WAF 和 Shield 是过滤器——它们在恶意流量到达你的应用程序之前拦截它。GuardDuty 监视的是流量到达之后发生的事。它看的是你的基础设施在做什么：哪些 IAM 凭证正在被使用，你的实例在联系哪些域名，凌晨3点发生了哪些 API 调用。一个通过看似合法的请求穿过前门的攻击者不会被 WAF 拦下——但 GuardDuty 会注意到同一个凭证突然开始从罗马尼亚发起 API 调用。

GuardDuty 与 Shield 和 WAF 有着根本的不同。它不阻止攻击——它**检测异常行为**。

GuardDuty 持续分析几路活动流来检测威胁：**CloudTrail 管理事件和数据事件**（API 调用和操作）、**VPC 流日志**（网络流量模式）和 **DNS 查询日志**（域名查询）。这是 GuardDuty 一直依赖的三个基础数据源：

- **AWS CloudTrail 日志**：IAM 变更、API 调用、控制台登录
- **VPC 流日志**：你 VPC 内的网络流量模式
- **DNS 查询日志**：你的实例在解析什么（已知恶意软件通常会解析特定的 C2 域名）

但 GuardDuty 已经远远超出了这三项。AWS 把这些可选的附加功能称为**保护计划（protection plans）**——S3 Protection、EKS Protection、RDS Protection、Lambda Protection、Runtime Monitoring 和 Malware Protection——每项都单独启用。根据你启用了哪些，GuardDuty 还可以分析 **S3 数据事件**（对你的桶的异常访问模式）、**EKS 审计日志和运行时活动**（运行中容器内部的恶意行为）、**RDS 登录事件**（异常的数据库登录尝试）、**Lambda 网络流量**（函数调用意外的外部目的地）、**ECS/EC2 运行时行为**，以及**扫描 EBS 卷中的恶意软件**。对于考试，要熟记三个核心数据源；保护计划会出现在特定威胁检测场景中——"检测对 RDS 的异常登录尝试"或"识别运行中容器内的恶意行为"是提示你考虑 GuardDuty 可选保护计划的信号。

机器学习模型识别偏离你基线的模式。GuardDuty 在检测到异常时生成**发现结果（findings）**——分类的告警。

GuardDuty 能检测到的例子：

- IAM 用户从一个无法识别的 IP 地址登录（在他们从未使用过的国家）
- 从 Tor 出口节点发起的 API 调用
- 一个 EC2 实例与已知的加密货币挖矿池通信
- 异常高的 API 调用量（凭证滥用或扫描）
- 一个 S3 桶被一个已被标记为恶意活动的 IP 地址访问
- 到一个已知与恶意软件命令与控制相关的域名的出站流量

"这就是本可以抓住罗马尼亚 IP 的东西，"Leo 轻声说。

"如果我们当时启用了 GuardDuty，它会标记那个 EC2 实例在凌晨2点向一个无法识别的外部 IP 建立出站连接，"Priya 确认道。

**五种 GuardDuty 发现类型及应对方法**

Priya 为五种最常见的 GuardDuty 发现编写了一份运维手册。当一个发现触发时，团队能立即知道它意味着什么、该怎么做。

**1. UnauthorizedAccess:IAMUser/ConsoleLoginSuccess.B**

一个 IAM 用户从一个此账户以前从未见过的 IP 地址成功登录了 AWS 控制台，或者来自一个与之前登录不一致的地理位置。

应对：与该用户核实是否是他们本人发起的登录。如果不是——或者联系不上——立即：禁用该用户的访问密钥和控制台密码，撤销活跃会话，并开始对该用户过去24小时的所有操作进行 CloudTrail 审计。这个发现常常是凭证滥用的前兆。

**2. CryptoCurrency:EC2/BitcoinTool.B**

一个 EC2 实例正在查询与加密货币挖矿池相关的 IP 地址或域名。这几乎总是 EC2 实例被攻陷并被用作挖矿机器人的结果。

应对：立即隔离该实例——修改它的安全组，阻止除你的堡垒机之外的所有入站和出站流量。对 EBS 卷做一份取证快照。然后终止该实例，从干净的 AMI 启动替代实例。

**3. Recon:EC2/PortProbeUnprotectedPort**

一个 EC2 实例有一个对互联网开放的端口，正在被已知扫描器或 Tor 出口节点探测。GuardDuty 会标记那些在流日志中显示可从外部来源访问的端口。

应对：审查安全组规则。如果该端口是有意开放的，把这个发现标记为已解决并附上备注。如果不是有意的，立即关闭该端口。检查 CloudTrail，看是否有任何可能通过该端口发生的访问。

**4. Trojan:EC2/BlackholeTraffic**

一个 EC2 实例正试图与一个被识别为"黑洞"的 IP 地址通信——一个与恶意软件命令与控制基础设施相关的目的地。到这些 IP 的流量表明该实例已被感染，正试图回连母站。

应对：与 CryptoCurrency 发现相同——隔离、快照、替换。这个发现表明实例上有活跃的恶意软件。不要尝试就地清理实例；从干净的 AMI 重建一个新的。

**5. Policy:S3/BucketBlockPublicAccessDisabled**

有人禁用了某个 S3 桶上的"阻止公共访问"设置。这并不意味着桶变成了公开的——它意味着防止意外公开暴露的安全机制在该桶上被关闭了。这通常是意外操作，或是错误配置的部署的一部分。

应对：调查是谁做了这个更改（CloudTrail 里会有那次 API 调用）。重新启用"阻止公共访问"，除非有书面记录的理由说明它应该被禁用。考虑启用账户级别的"阻止公共访问"设置，以防止这个发现在未来再次出现。

"关于 GuardDuty 发现，最重要的一点，"Priya 说，"是它们不是告警——它们是假设。每个发现都在说'这个模式看起来异常'。你去验证、去调查、去响应。有些会是误报。大多数不会。"

"我们怎么排优先级？"Rafael 问。

"GuardDuty 会分配严重性级别：低、中、高。高严重性的发现需要当天响应。木马和凭证泄露类的发现永远是高级别。端口探测类的发现可能是中或低。从高级别开始，往下处理。"

"它要多少钱？"Tom 问。

GuardDuty 的定价基于分析的日志量——CloudTrail 事件、VPC 流数据、DNS 查询。对于中小型应用程序，通常每月50-150美元。即便在规模化时，它仍然只占基础设施成本的一小部分。

Tom 打开控制台启用了它。

"不会有事的，"Leo 说。"只是监控而已。又不会弄坏什么。"

"我已经部署了，"Leo 补充道——然后查看了 GuardDuty 仪表板。"哦。只有示例发现。真的要等一段时间。"

"GuardDuty 需要时间来建立'正常是什么样'的基线，"Priya 说。"给它几天。第一个真正的发现会来的——它们总会来。"

事实证明她说对了。但第一个发现的故事要留到本章结尾。

**把三个服务连起来**

Shield、WAF 和 GuardDuty 工作在不同的层面，相互补充：

| 服务 | 层 | 防护对象 | 操作 |
|------------|---------------------------|---------------------------------------------|------------------------------------|
| AWS Shield | 网络/传输（L3/L4） | DDoS 洪水 | 吸收/缓解攻击 |
| AWS WAF | 应用层（L7） | OWASP 十大、机器人、爬虫 | 允许、阻止或计数请求 |
| GuardDuty | 行为（所有日志） | 异常、被盗凭证、恶意软件 | 检测和告警 |

Shield 挡住洪水。WAF 过滤水流。GuardDuty 监视管道中的异常流动模式。Macie 审计储存在水库里的东西。Security Hub 是所有仪表板同时可见的控制室。

每个服务的失效模式解释了为什么你需要它们全部：

- 一场 50 Gbps 的 SYN 洪水不是 Web 请求。WAF 无法检查它。GuardDuty 也许会注意到相关的 CloudTrail 事件。Shield 把它拦住。
- 一个单独的 SQL 注入请求不是洪水。Shield 忽略它。GuardDuty 不知道 HTTP 请求的内容。WAF 抓住它。
- 一个合法的 AWS 用户用自己的凭证缓慢地外泄数据——没有 DDoS，没有注入，HTTP 都是有效的——Shield 和 WAF 看不到任何异常。GuardDuty 注意到这些凭证在凌晨3点从一个新的国家被使用。
- 一个不小心把客户数据上传到可公开访问的桶的开发者，完全不会产生任何异常行为。GuardDuty 没有东西可标记。Macie 扫描这个桶，发现里面的 PII。

每个服务都有盲区。它们的组合覆盖了这些盲区。

**CloudTrail：基础**

这三个服务都依赖日志。**AWS CloudTrail** 是捕获你 AWS 账户中每次 API 调用的日志服务——谁调用了什么、何时、从哪里、结果如何。

CloudTrail 在控制台中默认启用90天的历史。要长期保留日志：

1. 创建一个写入 S3 桶的跟踪（trail）
2. 可选地，发送到 CloudWatch Logs 以进行实时告警
3. 启用日志文件验证（用于检测日志是否被篡改）

GuardDuty、AWS Config、Security Hub 和 IAM Access Analyzer 都从 CloudTrail 读取数据。没有 CloudTrail 日志，这些服务就没有任何东西可分析。

"如果有人试图禁用 CloudTrail 呢？"Priya 问。"如果攻击者获得了管理员权限，他们的第一个动作可能就是禁用日志——掩盖踪迹。"

"那正是第14章的 SCP 所防止的，"Leo 说。"这个账户里没有人能禁用 CloudTrail，管理员也不行。"

"那如果他们不知怎么做到了呢？"

"Security Hub 会生成一个发现。CloudTrail 在配置变更时会向 SNS 发送通知。任何对 CloudTrail 的修改，我们都会在两分钟内收到告警。"

"而且 GuardDuty 会把那次 API 调用标记出来，"Rafael 补充说，"作为一次不寻常的 IAM 操作——禁用日志不是正常的运维活动。"

针对最关键的安全行为之一——篡改日志——有多层检测。这不是偶然的。Priya 是有意这样设计的。

"纵深防御同样适用于监控层，"她说。"不只是应用层。"

**Amazon Macie：S3 中的敏感数据**

"我们有没有想过，如果有人不小心把一个含有客户信用卡号的文件上传到 S3 会怎样？"Priya 问。"不是恶意的——只是一个开发者为了调试导出数据，结果传错了文件？"

"我们永远不会知道，"Leo 说。

"正是。除非我们有 Macie。"

**Amazon Macie** 是一个数据安全服务，使用机器学习自动发现并保护 S3 中的敏感数据。它持续扫描 S3 桶并识别：

- PII（个人身份信息）：姓名、电子邮件地址、电话号码、出生日期
- 金融数据：信用卡号、银行账号
- 凭证：嵌在文件中的密码、访问密钥、私钥
- 健康信息：患者记录、诊断

当 Macie 检测到敏感数据出现在不该出现的地方——或者 S3 桶的访问配置过于宽松时——它会生成发现结果。

"这和 GuardDuty 是一回事吗？"Maya 问。

"目的不同，"Priya 说。"GuardDuty 监视行为——正在发生哪些操作、这些操作是否异常。Macie 监视数据——存储了什么内容、这些内容是否敏感。GuardDuty 会标记一个发起异常 API 调用的 EC2 实例。Macie 会标记一个包含信用卡号的 S3 桶。"

"所以 GuardDuty 是行为分析师，"Leo 说，"而 Macie 是数据审计员。"

"正是。两者都需要。一个通过看似合法的 API 调用外泄数据的攻击者，可能会因为异常的 API 模式被 GuardDuty 标记。但如果一个员工把含有10,000条客户记录的文件上传到开发桶，就没有任何异常行为可检测——只是敏感数据放错了地方。Macie 能抓住这种情况。"

对 Nimbus 来说，Macie 最直接的价值体现在 `nimbus-debug-exports` 桶上——开发者用来转储调试数据的桶。Macie 在其中发现了三个文件，包含带有客户姓名和配送地址的订单历史。不是支付数据，但属于不应该出现在未加密开发桶里的个人数据。

文件被删除了。还增加了一条政策：调试桶只限合成测试数据。真实客户数据导出到生产环境之外的任何环境，都需要 Priya 的批准。

"那每个月要花多少钱？"Tom 问。

Macie 按每月评估的 S3 桶数量和扫描的数据量收费。对于桶数量适中的创业公司，大约每月10-50美元。前30天免费。

Tom 在午饭前就启用了它。

**AWS Security Hub：仪表板**

如果你在运行多个 AWS 账户，或者需要安全发现结果的整合视图，**AWS Security Hub** 可以把来自 GuardDuty、Inspector（漏洞评估）、Macie（数据隐私）、Config 和 Firewall Manager 的发现结果聚合到单个仪表板中。

它还会根据安全最佳实践（AWS 基础安全最佳实践标准）和 CIS AWS Foundations 基准检查你的配置。

Security Hub 回答的是这样一个问题："我怎样才能在一个地方看到所有安全发现，而不用在五个不同的控制台之间切换？"当 GuardDuty 生成一个发现时，它会出现在 GuardDuty 里，也出现在 Security Hub 里。当 Macie 在 S3 桶中发现敏感数据时，它会出现在 Macie 里，也出现在 Security Hub 里。当某条 Config 规则检测到错误配置时，它会出现在 Config 里，也出现在 Security Hub 里。

对单账户团队来说，Security Hub 增加的价值有限——它只是又一个要看的控制台。它的威力在规模化时显现：三个账户、十个账户、五十个账户。所有账户的所有发现聚合到管理账户的 Security Hub 中。一个团队监控一个仪表板。一套告警。不需要逐个账户查日志。

对 Nimbus 而言：现在还不需要 Security Hub。当他们扩展到三个账户（开发、预发布、生产）时，它将变得不可或缺。

"现在就设置好，"入职第三周的 Soo-Jin 说。"启用它要十五分钟。后悔没早点弄要三个月。"

他们启用了它。

**Amazon Inspector：漏洞评估**

启用 Macie 一周后，针对 Nimbus 生产集群上运行的 OpenSSL 版本发布了一个 CVE。Priya 一边喝咖啡一边读着安全公告。

"我们需要知道我们的哪些实例受影响，"她说。

"我可以跑一次手动扫描，"Leo 说。

"九个实例，当然可以。九十个呢？容器呢？"Priya 打开了 Inspector 控制台。"这就是 Inspector 的用武之地。"

**Amazon Inspector** 是一个自动化的漏洞评估服务。GuardDuty 监视的是行为——你的基础设施此刻正在做什么——而 Inspector 看的是环境里存在哪些可能被利用的东西。

- **EC2 实例：**Inspector 把操作系统和已安装的软件包与 NVD（国家漏洞数据库）——已知 CVE 的权威目录——进行比对扫描。如果你在运行 OpenSSL 1.1.1，而有一个 CVE 针对该版本，Inspector 就会标记它。
- **ECR 容器镜像：**Inspector 在 Elastic Container Registry 中的容器镜像被部署之前扫描它们。基础镜像里的脆弱软件包会在容器进入生产运行之前显示为一个发现。
- **Lambda 函数包：**Inspector 分析打包进你的 Lambda 函数的依赖项——Python 包、Node 模块、Java 依赖——查找已知漏洞。

与一次性扫描的关键区别在于：Inspector **持续**运行。它不是在你启用时检查一次实例然后宣布它们干净。当一个新的 CVE 发布时，Inspector 会自动用新漏洞重新评估你现有的资源。当一个 EC2 实例发生变化——安装了新软件包、更新了 AMI——Inspector 会重新扫描它。Priya 的 EC2 集群在启用 Inspector 后的几分钟内就被标记出了那个 OpenSSL CVE——不是因为她要求它扫描，而是因为这就是它的工作方式。

发现结果按严重性分级：严重、高、中、低、信息性。它们与 GuardDuty 和 Macie 的发现一起流向 Security Hub。一个仪表板。三个镜头全在。

"三个实例受影响，"Leo 读着 Inspector 的发现说。"另外六个用的是已修补的版本。"

"这周就给那三个打补丁，"Priya 说。

"容器镜像呢？"

Priya 看了 Inspector 的 ECR 发现。他们容器仓库里的两个基础镜像有已知漏洞——一些后来已修补的软件包的旧版本。她把它们标记为待重建。

"重要的是，"Priya 说，"我们在它被利用之前发现了它。而不是之后。"

**三镜头模型**

GuardDuty、Inspector 和 Macie 各自监视不同的东西：

- **GuardDuty** 是行为视角。它问的是：*此刻正在发生什么看起来不对劲的事？*来自意外位置的 API 调用、联系命令与控制服务器的 EC2 实例、在不寻常时间被使用的凭证。它捕捉活跃的威胁和异常。
- **Inspector** 是结构视角。它问的是：*我们的环境中存在什么可能被利用的东西？*未打补丁的软件包、有漏洞的依赖、过时的运行时。它捕捉让攻击成为可能的条件。
- **Macie** 关注数据。它问的是：*我们的 S3 桶里躺着什么本不该在那里的敏感信息？*PII、财务记录、遗留在文件里的凭证。它捕捉那些不产生任何异常行为的暴露——只是放错地方的数据。

一次涉及已知 CVE 的入侵可能在三者中都有体现：Inspector 会在攻击之前标记出漏洞。GuardDuty 会在攻击期间标记异常行为。Macie 会在外泄数据落入 S3 之后标记它。

三个不同的镜头，三条不同的时间线，谁也替代不了谁。

**AWS Network Firewall：流量检查员**

在工具箱合上之前，还有一位专家值得一提。安全组和 NACL（第15章）按 IP、端口和协议过滤流量——它们能决定*谁*可以和*什么*对话，但无法看进对话的内容。**AWS Network Firewall** 是一个托管的、有状态的防火墙，部署在 VPC 级别。它执行深度包检测：按域名过滤（只允许出站流量到 `*.eatnimbus.com` 和你的软件包仓库）、阻止匹配入侵特征的流量（IDS/IPS，兼容 Suricata 规则），以及检查那些安全组会因为端口号看起来没问题而直接放行的流量。

"所以它是一个长了脑子的安全组，"Leo 说。

"它是你会从防火墙厂商那里买的那种设备，"Priya 说，"只不过是托管的、自动扩展的，并且部署在它自己的子网里，让所有进出 VPC 的流量都经过它。"

考试信号："按域名或负载内容检查或过滤流量"、"VPC 的入侵检测/防御（IDS/IPS）"或"出站流量的集中式出口过滤" → Network Firewall。当问题是实例级和子网级按端口和 IP 的允许/拒绝时，答案是安全组和 NACL；当问题要求检查流量*内部*时，答案是 Network Firewall。而当问题问如何在许多账户之间一致地管理 WAF 规则、Shield 高级版、安全组*和* Network Firewall 策略时——那是 **AWS Firewall Manager**，位于其上的策略管理层。

## 优势与局限性

**AWS Shield**：

- 标准版：免费且自动——没有理由不用
- 高级版：对高知名度目标非常出色；对小团队来说昂贵
- 标准版自动吸收第3/4层攻击（SYN 洪水、UDP 洪水、DNS 放大）
- 高级版增加第7层保护、实时通知和 Shield 响应团队

**AWS WAF**：

- 托管规则组显著简化了设置——几次点击就能获得 OWASP 十大保护
- 自定义规则需要了解 HTTP 攻击模式
- 速率限制是一个常被忽视的强大功能——对爬虫和暴力破解都有效
- WAF 不能替代安全的应用程序代码——它是纵深防御中的一层
- 先从计数模式开始，验证后再切换到阻止模式

**GuardDuty**：

- 启用极其省力（几次点击，30天免费试用）
- 发现结果需要人工审查和响应——GuardDuty 负责检测，不负责修复
- 会出现误报——某些合法活动在 ML 模型看来很异常
- 严重性级别（低/中/高）帮助排定响应优先级
- 与 Security Hub、EventBridge 和 Lambda 集成，可构建自动化响应工作流

**Amazon Inspector**：

- 持续的、自动化的漏洞扫描——不是一次性检查
- 在新 CVE 发布或资源变化时自动重新扫描
- 覆盖 EC2 实例（操作系统和应用软件包）、ECR 容器镜像和 Lambda 函数包
- 发现结果流向 Security Hub；严重性评级帮助排定补丁优先级
- 不阻止攻击——它揭示的是让攻击成为可能的条件

**Amazon Macie**：

- 自动发现 S3 中的敏感数据（PII、凭证、金融数据）
- 捕捉没有任何异常行为模式的数据暴露——GuardDuty 会漏掉这种情况
- 30天免费试用；之后按桶按月付费
- 对拥有大量 S3 桶且敏感程度各异的团队最有价值

**AWS Security Hub**：

- 聚合来自 GuardDuty、Macie、Inspector、Config 和 Firewall Manager 的发现结果
- 根据安全基准（CIS、NIST、PCI-DSS）检查配置
- 在多账户规模下最有价值
- 趁早启用，即使你只有一个账户——发现历史是累积的

## 摘要

五个服务，五个层面。每一个应对一种不同的威胁——而且谁也替代不了谁。DDoS 攻击会绕过 WAF 和 GuardDuty。SQL 注入尝试会绕过 Shield。一个被盗的凭证如果用得缓慢而小心，可能完全绕过 Shield 和 WAF——但 GuardDuty 会看到异常。一个不小心把客户 PII 上传到调试 S3 桶的开发者会绕过这三者——但 Macie 能抓住它。

- **AWS Shield 标准版**：免费、自动的第3/4层 DDoS 保护。始终开启。在那场 50 Gbps 的 SYN 洪水到达 Nimbus 负载均衡器之前就把它吸收了。
- **AWS Shield 高级版**：带 SRT 接入和成本保护的高级 DDoS 保护。企业级使用场景。
- **AWS WAF**：应用层防火墙。检查并过滤 HTTP 请求。附加到 CloudFront、ALB 或 API Gateway。使用托管规则组获得 OWASP 十大保护。用基于速率的规则防御爬虫。
- **Amazon GuardDuty**：行为威胁检测。核心数据源：CloudTrail 事件、VPC 流日志和 DNS 日志。可选的扩展保护增加 S3 事件、EKS/ECS 运行时监控、RDS 登录事件和 Lambda 网络活动。为异常活动生成分类的发现结果。五种关键发现类型：UnauthorizedAccess（控制台登录）、CryptoCurrency（挖矿）、Recon（端口探测）、Trojan（C2 流量）、Policy（S3 错误配置）。
- **Amazon Inspector**：自动化漏洞评估。扫描 EC2 实例、ECR 容器镜像和 Lambda 函数包中的已知 CVE。持续运行，并在新漏洞发布时重新评估。发现结果流向 Security Hub。
- **Amazon Macie**：S3 中的敏感数据发现。检测 PII、凭证和金融数据。捕捉没有任何异常行为模式的暴露。
- **AWS Security Hub**：将所有安全服务的发现结果聚合到一个仪表板。实现跨多账户的集中监控。
- **CloudTrail**：所有 AWS 安全日志的基础。启用写入 S3 的跟踪以进行长期保留。每个安全服务都从它读取数据。

## 考试技巧

*SAA-C03 领域：设计安全架构（领域1，任务1.2）*

- **Shield 标准版 vs 高级版**：标准版免费且自动。高级版收费，增加 SRT、成本保护和更好的检测。高级版的考试信号："大规模 DDoS"、"攻击期间的 SLA 保证"、"针对 DDoS 相关成本激增的财务保护"。
- **WAF 使用场景信号**："阻止 SQL 注入"、"阻止跨站脚本"、"对 API 调用做速率限制"、"阻止特定 User-Agent"、"OWASP 十大保护" → WAF。
- **GuardDuty 信号**："检测异常 API 活动"、"识别被盗凭证"、"标记异常的 EC2 网络连接"、"威胁情报" → GuardDuty。
- **WAF 附加点**：可以附加到 CloudFront（全球）、ALB（区域）、API Gateway（区域）、AppSync。
- **GuardDuty 数据源**：三个核心来源——CloudTrail 事件、VPC 流日志、DNS 日志。扩展的可选来源包括 S3 数据事件、EKS 审计日志、RDS 登录事件、Lambda 网络活动和 ECS 运行时。考试可能会问哪个数据源与特定检测场景相关："异常的 RDS 登录" → GuardDuty RDS Protection；"容器运行时威胁" → GuardDuty EKS/ECS Runtime Monitoring。
- **Macie vs GuardDuty**：这是一个常见的考试干扰项。**Macie** 使用 ML 检测 S3 中的敏感数据（PII、凭证、金融数据）。**GuardDuty** 检测行为中的威胁和异常。Macie 关注内容。GuardDuty 关注行为。
- **Inspector vs GuardDuty vs Macie：**三个不同的镜头，谁也替代不了谁。**Inspector** = 漏洞扫描——EC2 实例、ECR 中的容器镜像和 Lambda 函数包上的 CVE。持续运行并在新 CVE 发布时重新扫描。**GuardDuty** = 行为威胁检测——此刻正在发生什么看起来异常的事。**Macie** = S3 中的敏感数据发现——不该在那里的 PII、凭证和金融数据。考试触发语："识别 EC2 上未打补丁的漏洞"或"扫描容器镜像中的 CVE" → Inspector。"检测不寻常的 API 调用或被盗凭证" → GuardDuty。"在 S3 中找到 PII 或敏感数据" → Macie。
- **Security Hub**：聚合来自多个服务和账户的安全发现结果。考试场景："公司有多个 AWS 账户，希望对所有安全发现有一个统一视图" → Security Hub。
- **WAF 中的基于速率的规则**：用于在一个时间窗口内限制每个 IP 的请求数。与核心规则集（匹配攻击模式）不同。考试用基于速率的规则来应对"防止暴力破解登录尝试"或"缓解爬取"。
- **CloudTrail + GuardDuty + Security Hub**：这三者共同构成 AWS 安全可观测性的核心。先启用 CloudTrail（GuardDuty 和 Security Hub 依赖它），再启用 GuardDuty，然后用 Security Hub 聚合发现结果。

## 练习

**练习 1——回忆**

解释 AWS WAF 和 Amazon GuardDuty 之间的区别。每个服务防护什么，各自在哪一层运作？

*（提示：把 WAF 想象成对传入请求的过滤器，把 GuardDuty 想象成监视你日志的行为分析师。）*

**练习 2——SAA-C03 场景题**

*场景*：一家零售公司的网站正在被一个僵尸网络攻击，该僵尸网络每小时向其产品搜索 API 发送数百万个请求。这些请求看起来合法（有效的 User-Agent 字符串、有效的会话 Cookie），但不会产生购买——它们在抓取产品价格。攻击导致合法客户遭遇响应缓慢。

哪种服务组合*最能*应对这种威胁？

A) 带速率限制规则的 AWS WAF 和 CloudFront  
B) AWS Shield 高级版和 CloudFront  
C) Amazon GuardDuty 和 AWS Shield 标准版  
D) 用网络 ACL 阻止僵尸网络的 IP 范围

**提示 1**：这些请求是 HTTP 级别的（应用层）。哪个服务在 HTTP 层运作？

**提示 2**：僵尸网络使用许多不同的 IP 地址——在 NACL 级别阻止特定 IP 范围对大型僵尸网络无效。

**提示 3**：按 IP 地址的速率限制可以减缓抓取，即使你无法完全阻止它。

**答案**：A

**解析**：AWS WAF 可以按 IP 地址限制请求速率，降低来自任何单一来源的高流量抓取的影响。CloudFront 把传入流量分散到 AWS 的边缘网络，吸收流量并保护源站。WAF 规则还可以匹配请求模式（对同一 API 端点的快速连续请求）来识别抓取行为。

**为什么不是 B？** Shield 高级版防护的是 DDoS 洪水（第3/4层）。该场景描述的是应用层抓取（第7层 HTTP 请求），Shield 不检查这些。

**为什么不是 C？** GuardDuty 检测的是你 AWS 账户行为中的异常——它不阻止传入的 HTTP 请求。Shield 标准版不处理应用层攻击。

**为什么不是 D？** 大型僵尸网络使用来自分布式来源的数千个 IP 地址。阻止特定范围是一种打地鼠式的做法，对付不了复杂的僵尸网络。

## 彩蛋场景

GuardDuty 启用了。

四十八小时后，它生成了第一个发现结果：*"EC2 实例 i-0abc123 正在与一个已知的 Tor 出口节点通信。"*

Leo 看了看实例 ID。

"那是内部监控实例，"他说。"我设置来跑网络诊断的那台。"

"它应该和 Tor 出口节点通信吗？"

"不应该。"他停顿了一下。"它为什么会？"

他调出了那个实例。有人在上面安装了一个工具——一个合法的开源网络扫描器，结果发现，它还会与 Tor 基础设施通信，用于匿名化数据收集。

"所以这个工具在偷偷回连，"Priya 说。

"在我不知情的情况下，"Leo 确认道。

"这是供应链风险。一个做着你未曾授权之事的依赖项。"

Leo 卸载了这个工具。他建立了一个流程：每个第三方工具在安装前都要经过审查。

"这就是我们现在的偏执程度吗？"Maya 问。

"是的，"Priya 说。

"这是我们本就应该一直保持的程度吗？"Maya 问。

"也是，"Priya 说。
