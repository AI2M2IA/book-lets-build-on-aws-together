# অধ্যায় ৮: ডেটাবেস অ্যাডমিনিস্ট্রেটর যিনি কখনো অসুস্থ হন না

রাত ৩টায় সতর্কতা আসল।

ডেটাবেস সার্ভারের একটি নিরাপত্তা প্যাচের প্রয়োজন ছিল — যে ধরনের restart প্রয়োজন। দুর্বলতা বাস্তব, প্যাচ উপলব্ধ, এবং গ্রাহকদের বাধা না দিয়ে এটি প্রয়োগ করার উইন্ডো ছিল এখনই, রাতের মাঝখানে, যখন ট্রাফিক কম।

Priya একমাত্র জেগে ছিল। সে প্যাচ প্রয়োগ করল, সার্ভার restart করল, অ্যাপ্লিকেশন ফিরে আসা পর্যন্ত logs দেখল এবং রাত ৪:১৫-এ ঘুমাতে গেল।

সকালে সে দলকে কী হয়েছিল বলল। একটি নীরবতা ছিল।

"এটা আবার হবে," Tom বলল।

"যতবার প্যাচ হবে ততবার হবে," Priya বলল। "এবং সবসময় প্যাচ থাকে। এটা আরো ভালো করার একটি উপায় থাকতে হবে।"

ছিল। এটার জন্য শুধু এই ধারণা ছাড়া দিতে হবে যে তাদের ডেটাবেস নিজেরা পরিচালনা করতে হবে।

**ঐতিহ্যবাহী ডেটাবেস সমস্যা**

আপনি যখন একটি EC2 instance-এ নিজে একটি ডেটাবেস চালান, আপনি সবকিছুর জন্য দায়বদ্ধ।

ডেটাবেস সফটওয়্যার ইনস্টল করা। নিরাপদে কনফিগার করা। নিরাপত্তার দুর্বলতা আবিষ্কার হলে প্যাচ করা। ব্যাকআপ নেওয়া। ব্যাকআপ আসলে কাজ করে কিনা পরীক্ষা করা (একটি পদক্ষেপ যা বেশিরভাগ দল skip করে যতক্ষণ না অনেক দেরি হয়ে যায়)। ডিস্ক স্পেস monitor করা। রিডান্ড্যান্সির জন্য replication সেটআপ করা। primary সার্ভার ডাউন হলে failover কনফিগার করা। Query পারফরম্যান্স tune করা। লোডের অধীনে connection পরিচালনা করা।

এর কোনোটিই অ্যাপ্লিকেশন নয়। কোনোটিই feature যোগ করে না। সবটির জন্য বিশেষজ্ঞতা প্রয়োজন।

বেশিরভাগ development দল database administrator নয়। এটি একটি পূর্বানুমানযোগ্য প্যাটার্ন তৈরি করে: ডেটাবেস install করা হয়, ন্যূনতমভাবে কনফিগার করা হয় এবং তারপর বেশিরভাগ ভুলে যাওয়া হয় যতক্ষণ না কিছু বিপর্যয়করভাবে ভুল হয়।

"এটাই কি আমরা করেছিলাম?" Maya জিজ্ঞেস করল।

Leo-র উত্তর ছিল নীরবতা, যা হ্যাঁ-র সমান।

**Amazon RDS: ম্যানেজড ডেটাবেস**

**Amazon RDS** — Relational Database Service — আপনাকে এটি করতে না হয় বলে একটি relational database চালানোর পরিচালনামূলক বোঝা পরিচালনা করে।

RDS-এর সাথে, AWS পরিচালনা করে:

- ডেটাবেস ইঞ্জিন ইনস্টল এবং প্যাচ করা
- স্বয়ংক্রিয় ব্যাকআপ (S3-এ সংরক্ষিত, ৩৫ দিন পর্যন্ত রাখা)
- স্বয়ংক্রিয় failover (primary ডাউন হলে, একটি standby স্বয়ংক্রিয়ভাবে নেয়)
- Monitoring এবং metrics
- বিশ্রামে এবং পরিবহনে এনক্রিপশন
- Storage auto-scaling (আপনি এটি সক্ষম করলে, disk পূর্ণ হলে বাড়ে)

আপনি পরিচালনা করেন:

- ডেটাবেস schema (আপনার টেবিলের কাঠামো)
- আপনার query এবং অ্যাপ্লিকেশন লজিক
- ডেটাবেসে কার অ্যাক্সেস আছে
- কোন instance type ডেটাবেস চালায়
- Parameter tuning (যদিও RDS সাধারণ ডিফল্ট প্রদান করে)

উপমাটি: একটি database administrator নিয়োগ করা যিনি কখনো অসুস্থ হন না, কখনো কনফিগারেশন ত্রুটি করেন না, স্বয়ংক্রিয়ভাবে দৈনিক ব্যাকআপ নেন এবং কিছু ভাঙলে নিজেকে ঠিক করেন — কিন্তু যিনি আপনার অ্যাপ্লিকেশন লজিক লেখেন না।

**সমর্থিত Engine**

RDS বেশ কয়েকটি জনপ্রিয় ডেটাবেস ইঞ্জিন সমর্থন করে:

- **MySQL** — সবচেয়ে বেশি ব্যবহৃত open-source relational ডেটাবেস
- **PostgreSQL** — শক্তিশালী, extensible, জটিল কাজের লোডের জন্য ক্রমবর্ধমান জনপ্রিয়
- **MariaDB** — open-source MySQL fork, সম্পূর্ণ compatible
- **Oracle** — enterprise-grade, legacy প্রয়োজনীয়তার সাথে বড় সংস্থায় ব্যবহৃত
- **Microsoft SQL Server** — Windows-heavy পরিবেশের জন্য
- **Amazon Aurora** — AWS-এর নিজস্ব MySQL/PostgreSQL-compatible ইঞ্জিন, ক্লাউডের জন্য নির্মিত (আমরা অধ্যায় ২৪-এ Aurora গভীরভাবে কভার করি)

Nimbus-এর জন্য, পছন্দ ছিল PostgreSQL। এটি Leo যা জানত, এবং এটি relational data ভালোভাবে সামলায়। ইঞ্জিনের পছন্দ বেশিরভাগ অ্যাপ্লিকেশনের জন্য আপনার ভাবার মতো ততটা গুরুত্বপূর্ণ নয় — RDS-এর পরিচালনামূলক সুবিধাগুলি নির্বিশেষে প্রযোজ্য।

**Multi-AZ: যে Standby নেয়**

এটিই সেই feature যা নির্ভরযোগ্যতার হিসাব সম্পূর্ণরূপে পরিবর্তন করে।

**Multi-AZ deployment** মানে RDS primary-এর থেকে ভিন্ন Availability Zone-এ একটি synchronous standby instance বজায় রাখে। primary-এ commit করা প্রতিটি transaction commit স্বীকার করার আগে synchronously standby-তে replicate করা হয়।

primary ব্যর্থ হলে — হার্ডওয়্যার ব্যর্থতা, AZ বিভ্রাট, সফটওয়্যার crash — RDS স্বয়ংক্রিয়ভাবে standby-এ failover করে। ডেটাবেস endpoint-এর DNS রেকর্ড আপডেট হয়। আপনার অ্যাপ্লিকেশন নতুন primary-এ পুনরায় সংযোগ করে।

Failover ৬০-১২০ সেকেন্ড নেয়। সেই উইন্ডোতে, আপনার অ্যাপ্লিকেশন connection error দেখবে। সঠিকভাবে লেখা অ্যাপ্লিকেশনগুলি এটি gracefully সামলাতে পারে (backoff সহ connection retry)।

Standby একটি read replica নয়। এটি read ট্রাফিক পরিবেশন করে না। এর একমাত্র উদ্দেশ্য হলো নেওয়ার জন্য প্রস্তুত থাকা।

Tom: "Multi-AZ-এর দাম কত?"

মোটামুটি একক instance-এর খরচের দ্বিগুণ — কারণ আপনি আক্ষরিক অর্থে দুটি ডেটাবেস instance চালাচ্ছেন। Standby-এর খরচ primary-এর মতোই।

Tom: "এবং primary মারা গেলে আমরা বিনামূল্যে যে failover পাব?"

সে নিজেই প্রশ্নের উত্তর দিল শুক্রবার পিকের সময় প্রতি ঘণ্টার আয় অনুমান করতে order history খুলে।

Multi-AZ সেই বিকেলেই সক্ষম হয়েছিল।

**স্বয়ংক্রিয় ব্যাকআপ এবং Point-in-Time Recovery**

RDS প্রতিদিন স্বয়ংক্রিয় ব্যাকআপ নেয়। AWS এই ব্যাকআপগুলি S3-এ সংরক্ষণ করে (RDS দ্বারা পরিচালিত — আপনি সেগুলি সরাসরি আপনার S3 কনসোলে দেখেন না)। আপনি আপনার ব্যাকআপ retention period-এর মধ্যে যেকোনো বিন্দুতে ডেটাবেস restore করতে পারেন।

ব্যাকআপগুলি একটি configurable **maintenance window**-এর সময় হয় — কম ট্রাফিকের একটি সময়কাল, সাধারণত ভোরবেলায়। বেশিরভাগ ইঞ্জিন type-এর জন্য, ব্যাকআপ downtime ঘটায় না।

**Point-in-time recovery** সবচেয়ে মূল্যবান feature গুলির একটি: আপনি আপনার retention period-এর মধ্যে যেকোনো *সেকেন্ডে* restore করতে পারেন। শুধু দৈনিক snapshot নয় — *যেকোনো সেকেন্ড*। এটি সম্ভব কারণ RDS দৈনিক ব্যাকআপের পাশাপাশি ক্রমাগত transaction log আর্কাইভ করে।

কেউ যদি দুপুর ২:৩৭-এ `DELETE FROM orders WHERE 1=1` চালায়, আপনি ২:৩৬-এ restore করতে পারেন।

এটি বুঝলে Leo দৃশ্যমানভাবে স্বস্তি পেল।

"গত মাসে আমি যা মুছেছিলাম তা থেকে আমরা কি পুনরুদ্ধার করতে পারতাম?" সে জিজ্ঞেস করল।

"RDS-এর আগে? না," Priya বলল। "RDS-এর পরে? হ্যাঁ।"

**Read Replicas: Read ট্রাফিক Scaling**

Multi-AZ availability সম্পর্কে। **Read replicas** পারফরম্যান্স সম্পর্কে।

একটি read replica হলো আপনার primary ডেটাবেসের একটি asynchronous copy যা read query পরিবেশন করতে পারে। বেশিরভাগ RDS ইঞ্জিনের জন্য আপনার পাঁচটি পর্যন্ত read replica থাকতে পারে (Aurora-র জন্য আরো)।

অ্যাপ্লিকেশন read query replica-তে এবং write query primary-তে পাঠাতে পরিবর্তিত হয়। এটি লোড বিতরণ করে: primary write এবং জটিল transaction সামলায়; replica গুলি read সামলায়।

মূল বৈশিষ্ট্য:

- Replication **asynchronous** — primary এবং replica-এর মধ্যে একটি ছোট বিলম্ব (lag) থাকতে পারে। আপনি একটি রেকর্ড write করলে এবং তাৎক্ষণিকভাবে replica থেকে read করলে, আপনি এটি দেখতে নাও পারেন।
- Read replica একই Region-এ বা ভিন্ন Region-এ (cross-Region replica লেটেন্সি যোগ করে কিন্তু ভৌগোলিক বিতরণ সক্ষম করে) থাকতে পারে।
- Read replica দুর্যোগ পরিস্থিতিতে standalone ডেটাবেসে promote করা যায়।

Nimbus-এর জন্য: মেনু lookup হলো read। অর্ডার ইতিহাস হলো read। ট্রাফিকের বিশাল সংখ্যাগরিষ্ঠতা হলো read ট্রাফিক। একটি read replica যোগ করা এবং read গুলি এতে route করা primary ডেটাবেস লোড উল্লেখযোগ্যভাবে কাটে।

আমরা অধ্যায় ২৪-এ Aurora নিয়ে আলোচনা করার সময় read replica আরো গভীরে কভার করি।

## শক্তি এবং সীমাবদ্ধতা

**RDS কেন চমৎকার**:

- ডেটাবেস সফটওয়্যার পরিচালনার পরিচালনামূলক বোঝা দূর করে
- স্বয়ংক্রিয় ব্যাকআপ এবং point-in-time recovery
- ন্যূনতম RTO সহ স্বয়ংক্রিয় failover-এর জন্য Multi-AZ
- Read ট্রাফিক scaling-এর জন্য Read replicas
- বিশ্রামে এবং পরিবহনে এনক্রিপশন অন্তর্নির্মিত
- সমস্ত প্রধান relational ডেটাবেস ইঞ্জিন সমর্থিত

**RDS-এর সীমা কোথায়**:

- আপনি অন্তর্নিহিত OS অ্যাক্সেস করতে পারবেন না। আপনি custom OS-স্তরের সফটওয়্যার install বা OS সেটিং পরিবর্তন করতে পারবেন না। আপনার ডেটাবেসের OS-স্তরের অ্যাক্সেস প্রয়োজনীয়তা থাকলে, আপনার EC2-ভিত্তিক ডেটাবেস চালানো প্রয়োজন হতে পারে।
- RDS serverless নয় (ব্যতিক্রম সহ — Aurora Serverless বিদ্যমান, অধ্যায় ২৪-এ কভার)। আপনি নিষ্ক্রিয় থাকলেও চলমান instance-এর জন্য পেমেন্ট করেন।
- RDS horizontally sharded ডেটাবেসের জন্য ডিজাইন করা নয়। write-heavy relational কাজের লোডের বিশাল scale-out-এর জন্য, আপনার শেষ পর্যন্ত একটি ভিন্ন আর্কিটেকচারের প্রয়োজন হতে পারে।
- Non-relational (NoSQL) ডেটা প্যাটার্নের জন্য, DynamoDB (অধ্যায় ৯) আরো উপযুক্ত।

## সারসংক্ষেপ

- **Amazon RDS** হলো একটি managed relational database service। AWS patching, backup, failover এবং storage পরিচালনা সামলায়। আপনি schema, query এবং অ্যাপ্লিকেশন লজিক সামলান।
- **Multi-AZ** deployment একটি ভিন্ন AZ-এ একটি synchronous standby বজায় রাখে। primary ব্যর্থ হলে স্বয়ংক্রিয় failover ৬০-১২০ সেকেন্ডে ঘটে।
- **স্বয়ংক্রিয় ব্যাকআপ** সহ **point-in-time recovery** আপনাকে retention period-এর মধ্যে যেকোনো সেকেন্ডে restore করতে দেয়।
- **Read replicas** হলো asynchronous copy যা read ট্রাফিক পরিবেশন করে, primary-এ লোড কমায়। Replication lag মানে সেগুলি কিছুটা পিছিয়ে থাকতে পারে।
- RDS বেছে নিন যখন managed operation সহ একটি relational ডেটাবেস প্রয়োজন। Aurora (অধ্যায় ২৪) বেছে নিন যখন উচ্চ পারফরম্যান্স বা serverless বিকল্প দরকার।

## পরীক্ষার টিপস

*SAA-C03 ডোমেন ৩ — টাস্ক ৩.৩ (ডেটাবেস সমাধান)*

- **Multi-AZ high availability-এর জন্য, পারফরম্যান্সের জন্য নয়।** Standby read ট্রাফিক পরিবেশন করে না। Read replica পারফরম্যান্সের জন্য। এই পার্থক্য ঘন ঘন পরীক্ষিত।
- **Multi-AZ failover স্বয়ংক্রিয়।** আপনি কখন বা কীভাবে হবে কনফিগার করেন না। RDS primary monitor করে এবং স্বয়ংক্রিয়ভাবে failover trigger করে।
- **Replication lag গুরুত্বপূর্ণ।** Read replica primary-এর থেকে কিছুটা পিছিয়ে থাকতে পারে। আপনার অ্যাপ্লিকেশন সদ্য লেখা ডেটা পড়ার প্রয়োজন হলে, এটি replica নয়, primary থেকে পড়তে হবে। এটিকে "read-your-writes consistency" বলা হয়।
- **স্বয়ংক্রিয় ব্যাকআপ ০-৩৫ দিন রাখা হয়।** Retention 0 সেট করলে স্বয়ংক্রিয় ব্যাকআপ অক্ষম হয়। Manual snapshot আপনি মুছে না দেওয়া পর্যন্ত অনির্দিষ্টকালের জন্য রাখা হয়।
- **RDS storage auto-scaling** disk-full outage প্রতিরোধ করে। এটি সক্ষম করুন। এটি শুধু scale up করে, কখনো ডাউন নয়। পরীক্ষা এই asymmetry আপনি জানেন কিনা পরীক্ষা করতে পারে।

## অনুশীলন

**অনুশীলন ১ — স্মরণ**

আপনার নিজের ভাষায়: RDS-এ Multi-AZ এবং read replica-র মধ্যে পার্থক্য কী? প্রতিটি কোন সমস্যা সমাধান করে?

*(ইঙ্গিত: একটি downtime-এর বিরুদ্ধে সুরক্ষা করে; অন্যটি read-heavy লোডের অধীনে পারফরম্যান্স উন্নত করে। তারা বিভিন্ন সমস্যা সমাধান করে এবং একসাথে ব্যবহার করা যায়।)*

**অনুশীলন ২ — পরীক্ষার অনুশীলন**

*দৃশ্যকল্প*: একটি কোম্পানি RDS-এ একটি production PostgreSQL ডেটাবেস চালায়। দিনের বেলা reporting query চলার কারণে ডেটাবেসে উচ্চ read ট্রাফিক অনুভব হয়। দল ডেটাবেসের availability নিয়েও উদ্বিগ্ন — তারা failure পরিস্থিতিতে মাত্র কয়েক মিনিটের বেশি downtime সামর্থ্য করতে পারে না। তারা reporting কাজের লোড থেকে primary ডেটাবেসের উপর প্রভাব কমাতে চায়।

কোন RDS feature-এর সংমিশ্রণ উভয় উদ্বেগ সর্বোত্তমভাবে সমাধান করে?

A) Multi-AZ সক্ষম করুন এবং standby instance-এর বিরুদ্ধে সমস্ত query চালান  
B) failover সুরক্ষার জন্য Multi-AZ সক্ষম করুন এবং reporting query-র জন্য একটি read replica তৈরি করুন  
C) খরচ কমাতে Multi-AZ অক্ষম রেখে একাধিক read replica তৈরি করুন  
D) primary ব্যর্থ হলে তাদের থেকে restore করতে আরো ঘন ঘন manual snapshot নিন

**ইঙ্গিত ১**: দুটি প্রয়োজনীয়তা হলো: (১) failure-এ availability, (২) read offloading। কোন feature কোন প্রয়োজনীয়তা সমাধান করে?

**ইঙ্গিত ২**: Multi-AZ স্বয়ংক্রিয় failover প্রদান করে। Standby read ট্রাফিক পরিবেশন করে না। তাই Multi-AZ একা read সমস্যা সমাধান করে না।

**ইঙ্গিত ৩**: Read replica read ট্রাফিক পরিবেশন করে। Multi-AZ failover প্রদান করে। আপনার উভয়ই প্রয়োজন।

**উত্তর**: B

**ব্যাখ্যা**: Multi-AZ একটি ভিন্ন AZ-এর standby-এ স্বয়ংক্রিয় failover প্রদান করে — এটি availability প্রয়োজনীয়তা সমাধান করে। একটি read replica reporting query-কে primary ডেটাবেসকে প্রভাবিত না করে চলতে দেয় — এটি পারফরম্যান্স প্রয়োজনীয়তা সমাধান করে। উভয় feature একসাথে ব্যবহার করা যায়।

**কেন A নয়?** Multi-AZ standby read ট্রাফিক পরিবেশন করতে পারে না। এটি একচেটিয়াভাবে failover-এর জন্য। সরাসরি query করার চেষ্টা সমর্থিত নয়।

**কেন C নয়?** Read replica read পারফরম্যান্সে সাহায্য করে কিন্তু স্বয়ংক্রিয় failover প্রদান করে না। primary ব্যর্থ হলে, আপনাকে ম্যানুয়ালি একটি read replica promote করতে হবে — যা সময় নেয় এবং স্বয়ংক্রিয় নয়।

**কেন D নয়?** Manual snapshot একটি ডেটাবেসের একটি সম্পূর্ণ কপি restore করে — বড় ডেটাবেসের জন্য সম্ভাব্য ঘণ্টার একটি অনেক দীর্ঘ প্রক্রিয়া। এটি "কয়েক মিনিট downtime" প্রয়োজনীয়তা পূরণ করে না।

*SAA-C03 ডোমেন ৩ — টাস্ক ৩.৩*

**অনুশীলন ৩ — আর্কিটেকচার চ্যালেঞ্জ** *(ঐচ্ছিক)*

Nimbus তাদের বিদ্যমান self-managed PostgreSQL ডেটাবেস (একটি EC2 instance-এ চলছে) RDS PostgreSQL-এ migrate করার কথা বিবেচনা করছে। Migration ন্যূনতম downtime-এর সাথে ঘটতে হবে — আদর্শভাবে ১৫ মিনিটের কম। ডেটাবেস ২০০ GB।

আপনি কোন পদ্ধতি সুপারিশ করবেন? কোন AWS পরিষেবাগুলি migration-এ সাহায্য করতে পারে? Production ট্রাফিক cutover করার আগে আপনি কোন ঝুঁকিগুলি পরীক্ষা করবেন?

*(একটি একক সঠিক উত্তর নেই। AWS Database Migration Service, logical replication এবং cutover-এর সময় ডেটা অসামঞ্জস্যের ঝুঁকি নিয়ে ভাবুন।)*

## পোস্ট-ক্রেডিটস দৃশ্য

দিনের শেষে, Nimbus Multi-AZ সক্ষম করে RDS PostgreSQL-এ migrate করেছিল। migration নিজে বেশিরভাগ বিকেল নিয়েছিল — Leo একটি ছোট maintenance window সহ একটি backup-and-restore পদ্ধতি ব্যবহার করেছিল।

Tom বিল সাবধানে দেখেছিল।

"RDS instance," সে বলল, "EC2 ডেটাবেসের দ্বিগুণ খরচ।"

"এবং স্বয়ংক্রিয় ব্যাকআপ?" Maya জিজ্ঞেস করল।

"কিছুটা বেশি।"

"এবং primary মারা গেলে আমরা বিনামূল্যে পাওয়া failover?"

Tom-এর কাছে এর কোনো মূল্য ছিল না। সে এটি একটি প্রশ্ন হিসেবে লিখে রাখল।

"সমস্যা," Priya বলল, "ডেটাবেস ইঞ্জিন নয়। এটি ডেটা মডেল।"
