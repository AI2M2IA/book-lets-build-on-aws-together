# অধ্যায় ৪: অন্য কারো ভবনে একটি কম্পিউটার

Nimbus অ্যাপটি Tom-এর ল্যাপটপে চলছিল।

বিনিয়োগকারীদের একটি ডেমো দেখানোর জন্য ঠিক ছিল। যখন Maya "লঞ্চ" চাপলেন এবং প্রথম সপ্তাহে ২০০টি রেস্তোরাঁ সাইন আপ করল তখন ঠিক ছিল না। Tom-এর ল্যাপটপ এখন বাস্তব অর্ডার, বাস্তব মেনু এবং বাস্তব গ্রাহকদের পরিচালনা করছিল — Tom-এর ডেস্কের নিচে বসে, অফিসের Wi-Fi-এ চলছে, একটি পাওয়ার স্ট্রিপে প্লাগ করা যা একটি স্পেস হিটার এবং একটি কফি মেকারও চালাচ্ছিল।

"আমাদের একটি সার্ভার দরকার," Maya বলল। "একটি বাস্তব। কোথাও চলছে যেটি আপনার ডেস্কের নিচে নয়।"

Tom তার ল্যাপটপের দিকে তাকাল। ফ্যানের আওয়াজ ঘরের ওপার থেকে শোনা যাচ্ছিল।

তখনই তারা একটি কম্পিউটার ভাড়া নেওয়ার আসলে কী মানে তা দেখতে শুরু করল।

**কেউ ব্যাখ্যা না করা অ্যাবস্ট্রাকশন**

যখন লোকেরা বলে তাদের অ্যাপ্লিকেশন "ক্লাউডে চলে," তারা সাধারণত বলতে চায় এটি একটি ভার্চুয়াল মেশিনে চলে — এমন একটি কম্পিউটার যা ডেডিকেটেড হার্ডওয়্যার হিসেবে ভৌতভাবে বিদ্যমান নয়, কিন্তু প্রতিটি উপায়ে যেন আছে এমনভাবে আচরণ করে।

এখানে প্রক্রিয়াটি।

AWS ডেটা সেন্টারে একটি ভৌত সার্ভারে অনেক রিসোর্স রয়েছে: CPU কোর, মেমরি, ডিস্ক এবং নেটওয়ার্ক ব্যান্ডউইথ। AWS সেই ভৌত সার্ভারটিকে **হাইপারভাইজার** নামক সফটওয়্যার ব্যবহার করে বিভক্ত করে। হাইপারভাইজার একাধিক ভার্চুয়াল মেশিন তৈরি করে, প্রতিটি তাদের নিজস্ব ডেডিকেটেড CPU, মেমরি এবং ডিস্ক রয়েছে বলে মনে হয় — কিন্তু আসলে অন্তর্নিহিত ভৌত হার্ডওয়্যার ভাগ করে নিচ্ছে।

সেই ভার্চুয়াল মেশিনগুলির প্রতিটিকে AWS একটি **EC2 instance** বলে।

EC2 মানে Elastic Compute Cloud। "ইলাস্টিক" অংশটি গুরুত্বপূর্ণ, এবং আমরা সেখানে পৌঁছাব। এখনের জন্য: একটি EC2 instance হলো একটি কম্পিউটার যা আপনি ঘণ্টা হিসেবে ভাড়া নেন। এটিতে একটি অপারেটিং সিস্টেম, একটি নেটওয়ার্ক সংযোগ এবং কম্পিউটিং শক্তি রয়েছে। এটি আপনার অ্যাপ্লিকেশন ঠিক একটি ভৌত সার্ভারের মতো চালায়।

উপমাটি: একটি বড় ভবনে একটি অ্যাপার্টমেন্ট ভাড়া নেওয়া বনাম একটি বাড়ি কেনা।

ভবনের মালিক (AWS) ভৌত কাঠামো, পাইপলাইন, বৈদ্যুতিক, নিরাপত্তা বজায় রাখে। আপনি একটি ইউনিট পান। আপনি এটি যেভাবে খুশি সাজান। আপনি মাসিক (বা ঘণ্টা হিসেবে) পেমেন্ট করেন। যখন আপনার আরো জায়গার প্রয়োজন হয়, আপনি একটি বড় ইউনিটে চলে যান। চলে যাওয়ার সময়, পেমেন্ট বন্ধ করুন।

**আপনার Instance বেছে নেওয়া: আকার গুরুত্বপূর্ণ**

সমস্ত EC2 instance একই নয়। AWS শত শত instance type অফার করে, তারা কীসের জন্য অপ্টিমাইজড তার উপর ভিত্তি করে পরিবারে সংগঠিত।

**General purpose** (যেমন `t3`, `m6i`): ভারসাম্যপূর্ণ CPU এবং মেমরি। বেশিরভাগ ওয়েব অ্যাপ্লিকেশনের জন্য ভালো ডিফল্ট পছন্দ।

**Compute optimized** (যেমন `c7g`): মেমরির তুলনায় বেশি CPU। ভিডিও এনকোডিং, বৈজ্ঞানিক মডেলিং, ব্যাচ প্রসেসিংয়ের জন্য ভালো।

**Memory optimized** (যেমন `r7i`): CPU-এর তুলনায় বেশি মেমরি। ডেটাবেস, ক্যাশিং, ইন-মেমরি অ্যানালিটিক্সের জন্য ভালো।

**Storage optimized** (যেমন `i3`): হাই-স্পিড লোকাল স্টোরেজ। খুব দ্রুত ডিস্ক I/O প্রয়োজন ডেটা-ইন্টেনসিভ কাজের লোডের জন্য ভালো।

**Accelerated computing** (যেমন `p4`): GPU সংযুক্ত। মেশিন লার্নিং ট্রেনিং এবং গ্রাফিক্স রেন্ডারিংয়ের জন্য ভালো।

প্রতিটি পরিবারে আকার রয়েছে। একটি `t3.micro`-তে ২টি ভার্চুয়াল CPU এবং ১ GB মেমরি আছে। একটি `t3.xlarge`-এ ৪টি ভার্চুয়াল CPU এবং ১৬ GB আছে। আপনি কাজের লোডের জন্য সঠিক আকার বেছে নিন।

Leo একটি `t3.micro` বেছেছিল।

"একটি `t3.micro` কতজন ব্যবহারকারী সামলাতে পারে?" Tom জিজ্ঞেস করল।

"অ্যাপ্লিকেশনের উপর নির্ভর করে," Leo বলল। "কিন্তু সম্ভবত ইমেজ আপলোড এবং ডেটাবেস কোয়েরি চালানো একশত সমসাময়িক ব্যবহারকারী নয়।"

Tom হোয়াইটবোর্ডে "t3.micro" লিখল এবং পাশে একটি দুঃখী মুখ আঁকল।

**AMI: আপনার মেশিনের প্রারম্ভিক অবস্থা**

EC2 instance চালু করার আগে, আপনি এর অপারেটিং সিস্টেম এবং প্রাথমিক কনফিগারেশন বেছে নেন। AWS-এ, এটিকে একটি **Amazon Machine Image (AMI)** বলা হয়।

একটি AMI একটি টেমপ্লেট। এটি সংজ্ঞায়িত করে:

- অপারেটিং সিস্টেম (Amazon Linux, Ubuntu, Windows Server, ইত্যাদি)
- প্রি-ইনস্টলড সফটওয়্যার
- প্রারম্ভিক ডিস্ক অবস্থা

যখন আপনি একটি AMI থেকে একটি instance চালু করেন, AWS আপনার জন্য সেই টেমপ্লেটের একটি তাজা কপি তৈরি করে। আপনি আপনার নিজস্ব AMI-ও তৈরি করতে পারেন — আপনি যদি একটি সার্ভার ঠিক যেভাবে চান সেভাবে কনফিগার করেন, আপনি সেই অবস্থা একটি কাস্টম AMI হিসেবে "সেভ" করতে পারেন এবং দ্রুত অভিন্ন সার্ভার চালু করতে ব্যবহার করতে পারেন। এভাবেই আপনি স্কেলে সামঞ্জস্যপূর্ণ পরিবেশ ডেপ্লয় করেন।

একটি AMI-কে একটি রেসিপি হিসেবে মনে করুন। রেসিপি খাবার বর্ণনা করে। প্রতিবার রেসিপি অনুসরণ করলে একই খাবার পাবেন। যদি আপনি স্থায়ীভাবে খাবার পরিবর্তন করতে চান, আপনি রেসিপি আপডেট করুন।

**Key Pairs: সার্ভার অ্যাক্সেস করার সঠিক উপায়**

গত অধ্যায় থেকে "Admin123" বিপর্যয় মনে আছে?

EC2 instance-এ লগ ইন করার সঠিক উপায় হলো একটি **key pair** দিয়ে।

একটি key pair হলো একটি ক্রিপ্টোগ্রাফিক জোড়া: একটি public key (সার্ভারে AWS দ্বারা সংরক্ষিত) এবং একটি private key (একটি ফাইল যা আপনি ডাউনলোড করেন এবং গোপন রাখেন)। লগ ইন করতে, আপনি আপনার private key দিয়ে SSH — একটি নিরাপদ প্রোটোকল — ব্যবহার করেন। কোনো পাসওয়ার্ড নেই। যদি আপনি private key হারান, আপনি অ্যাক্সেস হারান। SSH-এর জন্য কোনো "পাসওয়ার্ড ভুলে গেছি" নেই।

এটি গুরুত্বপূর্ণ কারণ key pair হলো:

- আপনার জন্য অনন্য
- ক্রিপ্টোগ্রাফিকভাবে অনুমান করা অসম্ভব
- AWS দ্বারা সংরক্ষিত নয় (আপনি private key রাখেন)
- প্রত্যাহার করা সহজ (সার্ভার থেকে key মুছুন, একটি নতুন জোড়া তৈরি করুন)

Priya ইতিমধ্যে Nimbus সার্ভারে key-ভিত্তিক অ্যাক্সেস সেটআপ করেছিল। Admin123 সার্ভার ডিকমিশন করা হয়েছিল। কেউ দুঃখী ছিল না।

**Instance Lifecycle: চিরকালের জন্য নয়**

এটি অনেক শিক্ষার্থী মিস করে।

EC2 instance ডিফল্টরূপে স্থায়ী নয়। যখন আপনি একটি instance বন্ধ করেন, কম্পিউট রিসোর্স মুক্ত হয়। যখন আপনি এটি আবার শুরু করেন, এটি ভিন্ন ভৌত হার্ডওয়্যারে চলতে পারে। *instance নিজেই* (এর root volume-এ) সংরক্ষিত যেকোনো ডেটা stop/start cycle-এ টিকে থাকে — কিন্তু public IP ঠিকানা পরিবর্তিত হয়।

যখন আপনি একটি instance *terminate* করেন, এটি চলে গেছে। আলাদা স্টোরেজ সংযুক্ত না থাকলে (যা আমরা অধ্যায় ৬-এ কভার করি), instance-এ যেকোনো ডেটা অদৃশ্য হয়ে যায়।

এই "অস্থায়িত্ব" আসলে একটি বৈশিষ্ট্য, বাগ নয়। এর মানে আপনি সার্ভার চালু করতে, ব্যবহার করতে এবং ফেলে দিতে পারেন। এটি হরিজোন্টাল স্কেলিং সক্ষম করে। কিন্তু এর মানে আপনার কখনো গুরুত্বপূর্ণ ডেটা EC2 instance *নিজেই* সংরক্ষণ করা উচিত নয়।

তাহলে ডেটা কোথায় থাকে?

আলাদা স্টোরেজে। আমরা পরবর্তী দুই অধ্যায়ে সেখানে পৌঁছাই।

**"Elastic" মানে কী**

আমরা বলেছিলাম EC2 মানে Elastic Compute Cloud। এটি সম্পর্কে কী ইলাস্টিক?

দুটি জিনিস:

**ভার্টিক্যাল ইলাস্টিসিটি**: আপনি একটি instance-এর আকার পরিবর্তন করতে পারেন। Instance বন্ধ করুন, `t3.micro` থেকে `t3.xlarge`-এ পরিবর্তন করুন, পুনরায় শুরু করুন। বেশি CPU এবং মেমরি, একই অ্যাপ্লিকেশন, একই সেটআপ।

**হরিজোন্টাল ইলাস্টিসিটি**: আপনি আরো instance যোগ করতে পারেন। একটি বড় সার্ভারের পরিবর্তে, একটি লোড ব্যালান্সারের পেছনে দশটি মাঝারি সার্ভার চালান। ট্রাফিক কমলে, instance সরিয়ে ফেলুন এবং পেমেন্ট করা বন্ধ করুন।

উভয় পদ্ধতি "একটি সার্ভার, অনেক বেশি ট্রাফিক" সমস্যা সমাধান করে। তাদের বিভিন্ন আপোস আছে, যা আমরা অধ্যায় ৭-এ Auto Scaling-এর গল্পে যোগ করার সময় অন্বেষণ করি।

মূল অন্তর্দৃষ্টি: EC2-এর সাথে, কম্পিউটিং শক্তি এমন কিছু যা আপনি *ডায়াল* করেন আপনি *কিনি* না। আরো দরকার? ডায়াল উপরে ঘুরান। কম দরকার? নিচে ঘুরান। সেই অনুযায়ী পেমেন্ট করুন।

## শক্তি এবং সীমাবদ্ধতা

**EC2 কেন শক্তিশালী**:

- সম্পূর্ণ নিয়ন্ত্রণ। আপনি OS, সফটওয়্যার, কনফিগারেশন বেছে নেন। এটি আপনার কম্পিউটার।
- নমনীয় আকার। প্রতিটি ব্যবহারের ক্ষেত্রে শত শত instance type।
- পরিচালনার জন্য কোনো হার্ডওয়্যার নেই। AWS ভৌত স্তর পরিচালনা করে।
- প্রতি-সেকেন্ড বিলিং (বেশিরভাগ instance type-এর জন্য)। আপনি instance বন্ধ করলে, পেমেন্ট বন্ধ হয়।
- সবকিছুর সাথে কাজ করে। EC2 হলো ভিত্তি যার উপর বেশিরভাগ অন্যান্য AWS পরিষেবা নির্মিত।

**যেখানে জটিল হয়**:

- আপনি অপারেটিং সিস্টেম প্যাচিং এবং আপডেট করার জন্য দায়বদ্ধ। (Shared Responsibility Model — এটি "ক্লাউডে" অংশ যেটি আপনার।)
- স্কেলে EC2 পরিচালনা মানে হাজার হাজার মেশিন জুড়ে instance অবস্থা, AMI, নিরাপত্তা প্যাচ এবং lifecycle পরিচালনা করা। এটি অপারেশনাল ওভারহেড।
- EC2 সবকিছুর সঠিক উত্তর নয়। ইভেন্ট-চালিত কোডের জন্য যা অনিয়মিত চলে, Lambda (অধ্যায় ২০) সস্তা এবং সহজ। কন্টেইনারাইজড কাজের লোডের জন্য, ECS এবং EKS (অধ্যায় ২১) আরো ভালো রিসোর্স দক্ষতা অফার করে।
- অব্যবহৃত instance এখনো অর্থ খরচ করে। যদি আপনি একটি instance বন্ধ করেন, আপনি compute-এর জন্য পেমেন্ট করা বন্ধ করেন — কিন্তু যদি স্টোরেজ সংযুক্ত থাকে, আপনি এখনো সেটির জন্য পেমেন্ট করেন।

## সারসংক্ষেপ

- একটি **EC2 instance** হলো AWS-এ আপনি ভাড়া নেওয়া একটি ভার্চুয়াল মেশিন। এটিতে একটি OS, নেটওয়ার্ক অ্যাক্সেস এবং কম্পিউট রিসোর্স রয়েছে।
- Instance type ব্যবহারের ক্ষেত্র অনুসারে সংগঠিত: general purpose, compute optimized, memory optimized, storage optimized, accelerated computing। আপনার কাজের লোডের জন্য সঠিক পরিবার এবং আকার বেছে নিন।
- একটি **AMI** (Amazon Machine Image) হলো আপনার instance-এর OS এবং প্রাথমিক কনফিগারেশনের টেমপ্লেট। কাস্টম AMI সামঞ্জস্যপূর্ণ, পুনরাবৃত্তিযোগ্য ডেপ্লয়মেন্ট সক্ষম করে।
- **Key pairs** EC2 instance অ্যাক্সেস করার নিরাপদ উপায়। পাসওয়ার্ড নেই।
- EC2 instance ডিফল্টরূপে স্থায়ী নয়। Terminated instance তাদের ডেটা হারায়। গুরুত্বপূর্ণ ডেটা আলাদা স্টোরেজ পরিষেবায় সংরক্ষণ করুন।
- "Elastic" মানে আপনি compute স্কেল আপ এবং ডাউন করতে পারেন — ভার্টিক্যালি (বড় instance) এবং হরিজোন্টালি (আরো instance)।

## পরীক্ষার টিপস

*SAA-C03 ডোমেন ৩ — টাস্ক ৩.২ (উচ্চ-পারফরমিং compute সমাধান)*

- **EC2-এর জন্য Shared Responsibility**: আপনি OS প্যাচ করার জন্য দায়বদ্ধ। AWS ভৌত হার্ডওয়্যার এবং হাইপারভাইজার বজায় রাখে। এটি একটি ঘন ঘন পরীক্ষিত পার্থক্য।
- **দৃশ্যকল্প প্রশ্নের জন্য Instance পরিবার গুরুত্বপূর্ণ।** যদি কোনো দৃশ্যকল্পে উচ্চ মেমরির প্রয়োজনীয়তা (ইন-মেমরি ক্যাশ, SAP HANA) উল্লেখ থাকে, উত্তরে সম্ভবত একটি memory-optimized instance জড়িত। যদি ব্যাচ প্রসেসিং বা HPC উল্লেখ থাকে, compute-optimized।
- **Stopping ≠ Terminating।** একটি instance বন্ধ করা এটি সংরক্ষণ করে (আপনি পুনরায় শুরু করতে পারেন)। Terminating মুছে দেয়। পরীক্ষার দৃশ্যকল্প পরীক্ষা করে আপনি এই পার্থক্য জানেন কিনা।
- **Restart-এ Public IP পরিবর্তিত হয়।** আপনার অ্যাপ্লিকেশনের যদি একটি স্থিতিশীল IP ঠিকানার প্রয়োজন হয়, একটি **Elastic IP** ব্যবহার করুন — একটি স্ট্যাটিক public IP যা আপনার অ্যাকাউন্টের সাথে যুক্ত থাকে। আপনি একটি বরাদ্দ করলে এবং ব্যবহার না করলে এটি অর্থ ব্যয় করে।
- **On-Demand, Reserved এবং Spot** মূল্য নির্ধারণ মডেল ডোমেন ৪-এ ভারীভাবে পরীক্ষিত। আমরা সেগুলি অধ্যায় ২৭-এ কভার করি। এখনের জন্য জানুন যে On-Demand মানে কোনো প্রতিশ্রুতি ছাড়া প্রতি সেকেন্ডে পেমেন্ট।

## অনুশীলন

**অনুশীলন ১ — স্মরণ**

আপনার নিজের ভাষায়: একটি EC2 instance কী? একটি AMI কী? তাদের মধ্যে সম্পর্ক কী?

*(ইঙ্গিত: রেসিপি উপমাটি নিয়ে ভাবুন — রেসিপি কোনটি, এবং খাবার কোনটি?)*

**অনুশীলন ২ — পরীক্ষার অনুশীলন**

*দৃশ্যকল্প*: একটি কোম্পানি একটি হাই-ট্রাফিক ওয়েব অ্যাপ্লিকেশন ডেপ্লয় করছে। অ্যাপ্লিকেশনটি জটিল ফিল্টারিং লজিক সহ পণ্য ক্যাটালগ সার্চ পরিচালনা করে যা CPU-ইন্টেনসিভ। দল সেল ইভেন্টের সময় উল্লেখযোগ্য ট্রাফিক স্পাইকের প্রত্যাশা করে। তারা নিশ্চিত করতে চায় তারা সঠিক EC2 instance type বেছে নিয়েছে এবং ট্রাফিক বৃদ্ধির জন্য প্রস্তুত।

কোন পছন্দের সমন্বয় তাদের প্রয়োজনীয়তা সর্বোত্তমভাবে পূরণ করে?

A) সামঞ্জস্যপূর্ণ পারফরম্যান্স নিশ্চিত করতে স্থির সংখ্যা সহ Memory-optimized instance  
B) ট্রাফিক স্পাইক সামলাতে Auto Scaling সহ Compute-optimized instance  
C) একটি একক বড় instance আকার সহ General-purpose instance  
D) পণ্য ক্যাটালগের দ্রুত ডিস্ক অ্যাক্সেস প্রয়োজন বলে Storage-optimized instance

**ইঙ্গিত ১**: কাজের লোড "CPU-ইন্টেনসিভ" হিসেবে বর্ণিত। কোন instance পরিবার CPU-এর জন্য অপ্টিমাইজড?

**ইঙ্গিত ২**: দৃশ্যকল্পে "সেল ইভেন্টের সময় ট্রাফিক স্পাইক" উল্লেখ আছে। instance-এর একটি স্থির সংখ্যা পরিবর্তনশীল ট্রাফিক দক্ষতার সাথে সামলাবে না। কোন AWS ফিচার এটি পরিচালনা করে?

**ইঙ্গিত ৩**: Compute-optimized instance CPU-ভারী কাজ সামলায়। Auto Scaling চাহিদার উপর ভিত্তি করে instance যোগ এবং সরায়। একসাথে তারা উভয় প্রয়োজনীয়তার উত্তর দেয়।

**উত্তর**: B

**ব্যাখ্যা**: Compute-optimized instance (যেমন `c` পরিবার) CPU-ইন্টেনসিভ কাজের লোডের জন্য প্রতি ডলারে বেশি CPU প্রদান করে। Auto Scaling লোডের উপর ভিত্তি করে স্বয়ংক্রিয়ভাবে instance-এর সংখ্যা সামঞ্জস্য করে — সেল ইভেন্টের সময় instance যোগ করে, ট্রাফিক স্বাভাবিক হলে সরিয়ে দেয়। এই সমন্বয় পারফরম্যান্স এবং খরচ উভয়ই অপ্টিমাইজ করে।

**কেন A নয়?** Memory-optimized instance বড় পরিমাণ RAM প্রয়োজন কাজের লোডের জন্য ডিজাইন করা (ডেটাবেস, ইন-মেমরি ক্যাশ)। এটি CPU-বাউন্ড কাজের লোড। এবং স্থির instance সংখ্যা মানে হয় অতিরিক্ত প্রভিশনিং (অপচয়) বা কম প্রভিশনিং (ব্যর্থতা)।

**কেন C নয়?** General-purpose instance কিছু CPU দক্ষতা ভারসাম্যের জন্য ট্রেড করে। একটি পরিচিত CPU-ইন্টেনসিভ কাজের লোডের জন্য, compute-optimized আরো উপযুক্ত। এবং একটি একক বড় instance একটি একক ব্যর্থতার বিন্দু।

**কেন D নয়?** বাধা হলো CPU, ডিস্ক I/O নয়। Storage-optimized instance লোকাল স্টোরেজে খুব উচ্চ থ্রুপুট প্রয়োজন কাজের লোডের জন্য ডিজাইন করা।

*SAA-C03 ডোমেন ৩ — টাস্ক ৩.২*

**অনুশীলন ৩ — আর্কিটেকচার চ্যালেঞ্জ** *(ঐচ্ছিক)*

Nimbus বর্তমানে সম্পূর্ণ অ্যাপ্লিকেশনের জন্য একটি একক `t3.micro` EC2 instance চালায়। দলটিকে সিদ্ধান্ত নিতে হবে: একটি বড় instance-এ আপগ্রেড করুন (`t3.2xlarge`) নাকি একটি লোড ব্যালান্সারের পেছনে আরো `t3.micro` instance যোগ করুন?

আপোসগুলি বিশ্লেষণ করুন। প্রতিটি পদ্ধতির সুবিধা কী? সিদ্ধান্ত নিতে আপনি কোন প্রশ্নগুলি করবেন? (ইঙ্গিত: একক ব্যর্থতার বিন্দু, খরচ, ডেপ্লয়মেন্ট জটিলতা এবং রক্ষণাবেক্ষণের সময় কী হয় তা নিয়ে ভাবুন।)

*(একটি একক সঠিক উত্তর নেই। এটি ভার্টিক্যাল বনাম হরিজোন্টাল স্কেলিং নিয়ে যুক্তি করার বিষয়ে।)*

"আমাদের আমাদের ইমেজের জন্য কিছু দরকার," সে বিষয় কিছুটা পরিবর্তন করে বলল। "এই মুহূর্তে, আপলোড করা মেনু ফটোগুলি সরাসরি সার্ভারে সেভ হয়। যদি আমরা instance রিসাইজ বা রিস্টার্ট করি, আমরা কি সেগুলি হারাব?"

Priya ইতিমধ্যে উত্তর জানত।

পরবর্তী অধ্যায়ে: ক্লাউডে ইঙ্গিত করার মতো কোনো হার্ড ড্রাইভ না থাকলে ফাইলগুলি কোথায় থাকে।
