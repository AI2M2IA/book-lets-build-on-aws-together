# অধ্যায় ৬: আপনার সাথে চলা ডিস্ক

Tom-এর একটি লাল কলম ছিল এবং একটি অভ্যাস যা Leo-কে নার্ভাস করত।

প্রতি শনিবার সকালে, Tom AWS কনসোল সারসংক্ষেপ প্রিন্ট করত — চলমান instance, storage volume, সংযুক্ত ডিস্ক — এবং প্রতিটি লাইন ধরে পড়ত। সে দুই সপ্তাহ থেকে এটি করে আসছিল। সে এটিকে "লেজার" বলত। Leo এটিকে বলত "সেই জিনিস যা Tom করে যা Leo-কে মনে করায় সে কিছু ভুল করেছে।"

সেই শনিবার, Tom কিছু একটা চিহ্নিত করে বিনা কথায় প্রিন্টআউটটি Maya-র ডেস্কে রেখে গেল।

সে সোমবার সকালে এটি পেল। একটি বৃত্ত। মার্জিনে একটি নোট, তিনটি শব্দ:

*সবকিছু। একটি মেশিন।*

ওয়েব সার্ভার। ডেটাবেস। সমস্ত গ্রাহক রেকর্ড। দুই মাসের অর্ডার ইতিহাস। সবকিছু একটি একক EC2 instance-এ চলছিল।

"Instance ক্র্যাশ হলে ডেটাবেসের কী হয়?" Maya জিজ্ঞেস করল, হাতে প্রিন্টআউট।

"এটাও ক্র্যাশ হয়," Leo বলল।

"এবং ডেটা?"

"ডেটাবেস কীভাবে এটি সংরক্ষণ করে তার উপর নির্ভর করে।"

সেই "নির্ভর করে" ছিল সমস্যা।

**EC2 Instance কীভাবে ডেটা সংরক্ষণ করে**

একটি EC2 instance চলার সময়, এর অপারেটিং সিস্টেম কোথাও একটি ডিস্কে থাকে। সেই ডিস্ককে **root volume** বলা হয়। ডিফল্টরূপে, এটি একটি **EBS volume** — এমনকি যখন আপনি এটি নিয়ে ভাবেন না তখনও।

কিন্তু আরো একটি বিষয় আছে: EC2 instance-এর **instance store** storage-ও আছে।

Instance store হলো অস্থায়ী storage যা আপনার ভার্চুয়াল মেশিন চালানো অন্তর্নিহিত হার্ডওয়্যারের সাথে ভৌতভাবে সংযুক্ত। এটি অত্যন্ত দ্রুত — AWS-এ প্রায় অন্য যেকোনো storage বিকল্পের চেয়ে দ্রুত। কিন্তু এটি একটি catch নিয়ে আসে।

Instance store **অস্থায়ী**।

Instance বন্ধ বা terminate করা হলে, instance store ডেটা চলে গেছে। স্থায়ীভাবে। পুনরুদ্ধারযোগ্য নয়। AWS এ বিষয়ে খুব জোরে সতর্ক করে না, যেটি কীভাবে দলগুলি এটি আবিষ্কার করে: ডেটা হারিয়ে।

Instance store ক্যাশ, অস্থায়ী প্রক্রিয়াকরণ ফাইল এবং স্ক্র্যাচ স্পেসের জন্য উপযুক্ত। আপনি যে ডেটার যত্ন নেন তার জন্য কখনো নয়।

**EBS: স্থায়ী ডিস্ক**

**Amazon EBS** — Elastic Block Store — হলো EC2 instance-এর জন্য persistent block storage।

Block storage মানে এটি একটি বাস্তব হার্ড ড্রাইভের মতো আচরণ করে: আপনার অপারেটিং সিস্টেম এতে filesystem তৈরি করতে পারে, যেকোনো অবস্থানে যেকোনো bytes পড়তে এবং লিখতে পারে, ডেটাবেস চালাতে পারে এবং এটিকে ঠিক একটি সংযুক্ত ডিস্কের মতো ব্যবহার করতে পারে।

মূল বৈশিষ্ট্য:

**Persistent।** Instance store-এর বিপরীতে, EBS volume instance stop, start এবং এমনকি instance termination-এও টিকে থাকে (কনফিগারেশনের উপর নির্ভর করে)। ডেটা volume-এ থাকে এমনকি কোনো instance এটি ব্যবহার না করলেও।

**সংযোগযোগ্য এবং বিচ্ছিন্নযোগ্য।** একটি EBS volume এক instance থেকে বিচ্ছিন্ন করে অন্যটিতে সংযুক্ত করা যায়। একটি ব্যর্থ instance থেকে ডেটা মাইগ্রেট বা পুনরুদ্ধার করার প্রয়োজন হলে, আপনি volume বিচ্ছিন্ন করে অন্য কোথাও পুনরায় সংযুক্ত করতে পারেন।

**একক সংযুক্তি (বেশিরভাগ ক্ষেত্রে)।** ডিফল্টরূপে, একটি EBS volume একসাথে ঠিক একটি EC2 instance-এ সংযুক্ত থাকে। একটি একক instance একাধিক EBS volume রাখতে পারে, কিন্তু একটি একক EBS volume একসাথে একাধিক instance দ্বারা মাউন্ট করা যায় না (একটি ব্যতিক্রম সহ: EBS Multi-Attach, যার সীমিত ব্যবহারের ক্ষেত্র এবং গুরুত্বপূর্ণ সীমাবদ্ধতা আছে)।

উপমা: EBS হলো একটি বাহ্যিক হার্ড ড্রাইভ যা আপনি একটি ল্যাপটপে প্লাগ করেন। ল্যাপটপ (EC2 instance) এটি পড়তে এবং লিখতে পারে। আপনি সম্পন্ন হলে, আপনি এটি আনপ্লাগ করতে এবং একটি ভিন্ন ল্যাপটপে প্লাগ করতে পারেন।

**EBS Volume Types**

সমস্ত EBS volume একই নয়। AWS বিভিন্ন পারফরম্যান্স এবং খরচ প্রোফাইল সহ বেশ কয়েকটি type অফার করে।

**gp3 (General Purpose SSD)**: বেশিরভাগ কাজের লোডের জন্য ডিফল্ট পছন্দ। পারফরম্যান্স এবং মূল্যের ভালো ভারসাম্য। boot volume, ছোট ডেটাবেস এবং development পরিবেশের জন্য উপযুক্ত।

**io2 (Provisioned IOPS SSD)**: I/O-ইন্টেনসিভ কাজের লোডের জন্য উচ্চ-পারফরম্যান্স বিকল্প। আপনি কতটি I/O অপারেশন প্রতি সেকেন্ড (IOPS) চান তা নির্দিষ্ট করুন, এবং AWS সেই পারফরম্যান্স গ্যারান্টি দেয়। বড় প্রোডাকশন ডেটাবেসের জন্য উপযুক্ত।

**st1 (Throughput Optimized HDD)**: বড় sequential reads এবং writes-এর জন্য অপ্টিমাইজড magnetic storage। SSD-এর চেয়ে কম খরচ, কিন্তু random I/O-এর জন্য ধীর। data warehousing এবং log processing-এর জন্য ভালো।

**sc1 (Cold HDD)**: সবচেয়ে সস্তা EBS বিকল্প। কম ঘন ঘন অ্যাক্সেস করা ডেটার জন্য। সময়-সংবেদনশীল যেকিছুর জন্য উপযুক্ত নয়।

পরীক্ষার জন্য সমস্ত type মুখস্থ করার প্রয়োজন নেই। এটি পরীক্ষা করে আপনি সঠিক type-এর সাথে প্রয়োজনীয়তা মেলাতে পারেন কিনা: IOPS প্রয়োজনীয়তা → io2। খরচ-সংবেদনশীল sequential কাজের লোড → st1। General web applications → gp3।

**EBS Snapshots: ব্যাকআপ**

এখানে এমন কিছু যা নিয়মিত কোম্পানিগুলিকে রক্ষা করে।

একটি **EBS snapshot** হলো একটি EBS volume-এর একটি পয়েন্ট-ইন-টাইম ব্যাকআপ, S3-এ সংরক্ষিত (যদিও আপনি এটি EBS ইন্টারফেসের মাধ্যমে অ্যাক্সেস করেন, সরাসরি S3-এর মাধ্যমে নয়)। Snapshot গুলি incremental: প্রথম snapshot সম্পূর্ণ volume ক্যাপচার করে; পরবর্তী snapshot গুলি শুধুমাত্র সেই শেষটির পর থেকে যা পরিবর্তিত হয়েছে তা সংরক্ষণ করে।

আপনি একটি snapshot থেকে একটি নতুন EBS volume তৈরি করতে পারেন — একটি ডেটাবেস দুর্নীতির আগে, একটি খারাপ ডেপ্লয়মেন্ট, বা একটি দুর্ঘটনামূলক মুছে ফেলার আগে একটি পয়েন্ট-ইন-টাইমে পুনরুদ্ধার করে।

আপনার snapshot স্বয়ংক্রিয় করা উচিত। AWS এই উদ্দেশ্যে **Amazon Data Lifecycle Manager** সরবরাহ করে: একটি নীতি সংজ্ঞায়িত করুন (প্রতি ৬ ঘণ্টায় একটি snapshot নিন, শেষ ৭ দিন রাখুন), এবং এটি স্বয়ংক্রিয়ভাবে চলে।

ডেটাবেস প্রোডাকশনে যাওয়ার আগেই Priya এটি সেটআপ করে রেখেছিল।

Leo এটি নিয়ে ভাবেনি।

**EFS: ভাগ করা ফাইলিং ক্যাবিনেট**

EBS হলো একটি instance-এ সংযুক্ত একটি ডিস্ক। যদি একাধিক instance-কে একসাথে একই ফাইলগুলিতে অ্যাক্সেস করতে হয়?

প্রবেশ করুন **Amazon EFS** — Elastic File System।

EFS হলো একটি managed network filesystem। একাধিক EC2 instance একই EFS filesystem মাউন্ট করতে পারে এবং একসাথে ভাগ করা ফাইলগুলিতে পড়তে/লিখতে পারে। এটাই মূল ক্ষমতা যা EBS প্রদান করে না।

এভাবে ভাবুন:

EBS হলো একটি বাহ্যিক হার্ড ড্রাইভ একটি ল্যাপটপে প্লাগ করা। শুধুমাত্র সেই ল্যাপটপ একবারে এটি ব্যবহার করতে পারে।

EFS হলো একটি অফিসের কেন্দ্রে একটি ফাইলিং ক্যাবিনেট। যেকোনো দলের সদস্য উঠে যেতে পারে, একটি ড্রয়ার খুলতে পারে, একটি ফাইল পড়তে পারে, কিছু ফিরিয়ে রাখতে পারে। একাধিক মানুষ, একসাথে, একই storage অ্যাক্সেস করছে।

**EFS কখন দরকার?**

- যখন একাধিক EC2 instance-কে ফাইল ভাগ করতে হবে — content management systems, ভাগ করা কনফিগারেশন ফাইল, ভাগ করা মিডিয়া লাইব্রেরি
- যখন আপনার একটি হরিজোন্টালি স্কেল করা অ্যাপ্লিকেশন থাকে যেখানে সমস্ত instance একই ডেটা অ্যাক্সেস করতে হবে
- যখন আপনার একটি persistent filesystem দরকার যা instance ব্যর্থতায় টিকে থাকে

**EFS বনাম S3:** EFS হলো একটি filesystem (ফোল্ডার, ফাইল, অনুমতি, লকিং)। S3 হলো object storage (upload, download, কোনো filesystem semantics নেই)। EFS S3-এর চেয়ে অনেক বেশি ব্যয়বহুল। সম্পূর্ণভাবে সংরক্ষিত এবং retrieved ফাইলের জন্য S3 ব্যবহার করুন। অ্যাপ্লিকেশন যে ফাইলগুলি standard filesystem অপারেশনের মাধ্যমে সক্রিয়ভাবে পড়ে এবং লেখে তার জন্য EFS ব্যবহার করুন।

**সঠিক Storage বেছে নেওয়া**

এখন আপনি AWS-এ তিন ধরনের storage দেখেছেন। সিদ্ধান্তটি স্পষ্ট করা যাক।

| প্রয়োজন                                      | Storage Type     |
|-----------------------------------------------|------------------|
| ডেটাবেসের persistent, দ্রুত ডিস্ক দরকার      | EBS (gp3 বা io2) |
| একাধিক সার্ভারের ভাগ করা ফাইল দরকার          | EFS              |
| ফাইল, ব্যাকআপ, ইমেজ, বড় object              | S3               |
| অস্থায়ী computation স্ক্র্যাচ স্পেস          | Instance Store   |
| ন্যূনতম খরচে দীর্ঘমেয়াদী আর্কাইভ            | S3 Glacier       |

এই সিদ্ধান্তটি সঠিক করা গুরুত্বপূর্ণ। যেখানে EFS দরকার সেখানে S3 ব্যবহার করলে পরিচালনামূলক জটিলতা যোগ হয়। যেখানে EFS দরকার সেখানে EBS ব্যবহার করলে স্কেলে ব্যর্থতা হয়। যেখানে persistence দরকার সেখানে instance store ব্যবহার করলে ডেটা হারায়।

Priya এই টেবিলটি প্রিন্ট করে দেয়ালে সাঁটিয়ে দিল।

"প্রতিবার আমরা একটি storage প্রয়োজনীয়তা যোগ করি," সে বলল, "আমরা এখান থেকে শুরু করি।"

- EC2-এর জন্য Persistent, দ্রুত block storage
- পয়েন্ট-ইন-টাইম ব্যাকআপ এবং পুনরুদ্ধারের জন্য snapshot
- বিভিন্ন কাজের লোডের জন্য একাধিক পারফরম্যান্স স্তর
- বিশ্রামে এনক্রিপশন নেটিভলি সমর্থিত

**EBS সীমাবদ্ধতা**:

- একবারে একটি instance-এ সংযুক্ত (সামান্য ব্যতিক্রম সহ)
- EC2 instance-এর মতো একই AZ-এ (অন্য AZ-এ কপি করতে snapshot প্রয়োজন)
- আপনি শুধু যা ব্যবহার করেন তার জন্য নয়, provisioned storage-এর জন্য পেমেন্ট করেন

**EFS শক্তি**:

- Multi-instance ভাগ করা filesystem — native NFS protocol
- স্বয়ংক্রিয়ভাবে স্কেল করে, আপনি ক্যাপাসিটি প্রভিশন করেন না
- একটি Region-এর মধ্যে AZ জুড়ে অ্যাক্সেসযোগ্য

**EFS সীমাবদ্ধতা**:

- প্রতি GB-এ S3-এর চেয়ে বেশি ব্যয়বহুল
- random I/O-এর জন্য EBS-এর চেয়ে বেশি লেটেন্সি
- সব Region-এ পাওয়া যায় না

## সারসংক্ষেপ

- **Instance store** হলো অস্থায়ী, দ্রুত storage ভৌতভাবে হোস্টের সাথে সংযুক্ত। Instance বন্ধ বা terminate হলে ডেটা হারায়। শুধুমাত্র স্ক্র্যাচ স্পেসের জন্য।
- **EBS** (Elastic Block Store) হলো একটি একক EC2 instance-এর জন্য persistent block storage। এটি instance stop-এ টিকে থাকে। ব্যাকআপের জন্য snapshot করা যায়। সঠিক volume type বেছে নিন (general use-এর জন্য gp3, high-IOPS প্রয়োজনীয়তার জন্য io2)।
- **EFS** (Elastic File System) হলো একটি ভাগ করা network filesystem যা একাধিক instance একসাথে মাউন্ট করতে পারে। যখন একাধিক সার্ভারের একই ফাইলে অ্যাক্সেস দরকার তখন ব্যবহার করুন।
- প্রয়োজনীয়তার সাথে storage type মেলান: database → EBS; ভাগ করা ফাইল → EFS; object/ব্যাকআপ → S3; আর্কাইভ → S3 Glacier।

## পরীক্ষার টিপস

*SAA-C03 ডোমেন ৩ — টাস্ক ৩.১ (storage সমাধান)*

- **EBS volume একটি AZ-এ থাকে।** এগুলি শুধুমাত্র একই AZ-এর instance-এ সংযুক্ত করা যায়। একটি ভিন্ন AZ-এ EBS volume ব্যবহার করতে, আপনি একটি snapshot তৈরি করে লক্ষ্য AZ-এ restore করুন।
- **EBS snapshot incremental এবং S3-এ সংরক্ষিত।** প্রথম snapshot সম্পূর্ণ; পরবর্তীগুলি শুধুমাত্র পরিবর্তন সংরক্ষণ করে। আপনি disaster recovery-এর জন্য অন্য Region-এ snapshot কপি করতে পারেন।
- **EFS cross-AZ।** একটি Region-এর মধ্যে বিভিন্ন AZ-এর একাধিক instance একই EFS filesystem মাউন্ট করতে পারে। এটি EBS থেকে একটি মূল পার্থক্যকারী।
- **যখন একটি পরীক্ষার দৃশ্যকল্পে "ভাগ করা কন্টেন্ট সহ ওয়েব অ্যাপ্লিকেশন" বা "একই ফাইল অ্যাক্সেস করা একাধিক instance" বলা হয়, EFS ভাবুন।** যখন "ডেটাবেস storage" বা "একটি সার্ভারের জন্য persistent disk" বলা হয়, EBS ভাবুন।
- **Instance store ডেটা একটি reboot-এ টিকে থাকে কিন্তু stop বা termination-এ নয়।** একটি প্রশ্ন "instance বন্ধ হওয়ার পরে ডেটা অদৃশ্য হয়" বর্ণনা করতে পারে — সেটি instance store কাজে আসছে।

## অনুশীলন

**অনুশীলন ১ — স্মরণ**

আপনার নিজের ভাষায়: EBS এবং EFS-এর মধ্যে পার্থক্য কী? আপনি কখন একটি অন্যটির উপর বেছে নেবেন?

*(ইঙ্গিত: একটি বা একাধিক instance একসাথে storage অ্যাক্সেস করতে হবে কিনা তা নিয়ে ভাবুন।)*

**অনুশীলন ২ — পরীক্ষার অনুশীলন**

*দৃশ্যকল্প*: একটি কোম্পানি একটি লোড ব্যালান্সারের পেছনে চারটি EC2 instance জুড়ে একটি ওয়েব অ্যাপ্লিকেশন চালায়। ব্যবহারকারীরা প্রোফাইল ফটো আপলোড করতে পারে। চারটি instance-কেই আপলোডের পরপরই যেকোনো ব্যবহারকারীর ফটো পরিবেশন করতে হবে, যে instance আপলোড পরিচালনা করেছিল তা নির্বিশেষে। দলটির persistent, ভাগ করা ফাইল storage দরকার।

কোন storage সমাধানটি তাদের প্রয়োজনীয়তা সর্বোত্তমভাবে পূরণ করে?

A) প্রতিটি EC2 instance-এ একটি EBS gp3 volume সংযুক্ত করুন এবং cron job ব্যবহার করে ফাইল sync করুন  
B) EC2 instance-এর instance store-এ সরাসরি ফটো সংরক্ষণ করুন  
C) সমস্ত চারটি EC2 instance-এ একসাথে মাউন্ট করা Amazon EFS ব্যবহার করুন  
D) S3-এ ফটো সংরক্ষণ করুন এবং সরাসরি অ্যাপ্লিকেশন কোড থেকে অ্যাক্সেস করুন

**ইঙ্গিত ১**: প্রয়োজনীয়তা হলো "সমস্ত চারটি instance যেকোনো ফটো পরিবেশন করতে পারবে।" কোন বিকল্পগুলি সমস্ত instance-এর কাছে একটি ফাইল তাৎক্ষণিকভাবে দৃশ্যমান করে?

**ইঙ্গিত ২**: Instance store অস্থায়ী। EBS একসাথে একাধিক instance-এ মাউন্ট করা যায় না। এটি সীমাবদ্ধ করে।

**ইঙ্গিত ৩**: C এবং D উভয়ই তাত্ত্বিকভাবে কাজ করতে পারে। ক্ষেত্রে যেখানে অ্যাপ্লিকেশনের filesystem অপারেশনের মাধ্যমে বনাম HTTP অনুরোধের মাধ্যমে ফটো অ্যাক্সেস করতে হয়, কোনটি আরো উপযুক্ত?

**উত্তর**: D

**ব্যাখ্যা**: S3-এ ফটো সংরক্ষণ করা এবং URL-এর মাধ্যমে পরিবেশন করা ওয়েব অ্যাপ্লিকেশনের জন্য আর্কিটেকচারালি সঠিক পছন্দ। আপলোড করা ফটোগুলি S3-এর URL-এর মাধ্যমে যেকোনো সার্ভার (এবং যেকোনো ব্রাউজার) থেকে তাৎক্ষণিকভাবে অ্যাক্সেসযোগ্য। S3 ঠিক এই ব্যবহারের ক্ষেত্রের জন্য ডিজাইন করা: উচ্চ availability এবং শূন্য ব্যবস্থাপনা ওভারহেড সহ স্কেলে user-আপলোড করা ফাইল সংরক্ষণ।

নোট: C (EFS) প্রযুক্তিগতভাবে কাজ করবে, কিন্তু S3 হলো ওয়েব অ্যাপ্লিকেশনে user-আপলোড করা বাইনারি ফাইলের জন্য পছন্দের প্যাটার্ন কারণ এটি সস্তা, আরো স্কেলযোগ্য এবং অ্যাপ্লিকেশনকে proxy হিসেবে কাজ না করে সরাসরি HTTP-এ ফাইল পরিবেশন করে।

**কেন A নয়?** cron job-এর মাধ্যমে ফাইল sync করলে race condition এবং consistency সমস্যা তৈরি হয়। আপলোড এবং পরবর্তী sync-এর মধ্যে, অন্য instance-এ ফাইল নিখোঁজ থাকবে।

**কেন B নয়?** Instance store ডেটা instance বন্ধ বা terminate হলে হারিয়ে যায়। ফটো অদৃশ্য হবে।

**কেন C নয়?** EFS সঠিক উত্তর যদি অ্যাপ্লিকেশনের filesystem semantics প্রয়োজন হয় (যেমন, জায়গায় ফাইল পরিবর্তন করা CMS)। ওয়েবে পরিবেশিত user-আপলোড করা ফটোর জন্য, S3 সহজ, সস্তা এবং আরো উপযুক্ত।

*SAA-C03 ডোমেন ৩ — টাস্ক ৩.১*

**অনুশীলন ৩ — আর্কিটেকচার চ্যালেঞ্জ** *(ঐচ্ছিক)*

Nimbus একটি নতুন ফিচার যোগ করছে: রেস্তোরাঁর মালিকরা PDF মেনু আপলোড করতে পারবেন যা তারপর parse করে Nimbus ডেটাবেস পূরণ করতে ব্যবহার করা হয়। PDF প্রক্রিয়াকরণ কাজটি EC2 instance-এর একটি fleet-এ চলে যাদের প্রয়োজন: (a) আপলোড করা PDF পড়তে, (b) অস্থায়ী প্রক্রিয়াকরণ ফাইল লিখতে, (c) parsed আউটপুট লিখতে।

এই তিনটি ধাপের প্রতিটির জন্য আপনি কোন storage পরিষেবাগুলি ব্যবহার করবেন, এবং কেন?

*(একটি একক সঠিক উত্তর নেই। প্রতিটি ধাপের বৈশিষ্ট্যে storage type মেলানোর উপর ফোকাস করুন।)*
