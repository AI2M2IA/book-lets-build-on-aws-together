# অধ্যায় ৫: ক্লাউডে থাকা ফাইলিং ক্যাবিনেট

Leo বুঝতে পারল যে Nimbus আপলোড করা মেনু ফটোগুলি সরাসরি EC2 instance-এ সংরক্ষণ করছে। গ্রাহকরা যা আপলোড করেন প্রতিটি ফটো — মচমচে arepa, গ্রিলড স্যামন প্লেট, নিখুঁতভাবে সাজানো সালাদ বাউল — একটি একক ভার্চুয়াল মেশিনে বসে ছিল।

এবং সেই মেশিনটি যদি কখনো রিস্টার্ট, রিসাইজ বা প্রতিস্থাপন করা হয়?

চলে যাবে।

"গ্রাহকরা এখন পর্যন্ত কতটি ফটো আপলোড করেছে?" Maya জিজ্ঞেস করল।

Leo কনসোল খুলল। "প্রায় আটশত।"

"এবং আমরা সার্ভার রিস্টার্ট করলে সেই আটশত ফটোর কী হবে?"

আরেকটি Leo-র অর্থবহ বিরতি।

এই অধ্যায়টি ক্লাউডে ফাইলগুলি আসলে কোথায় থাকে তা নিয়ে।

**"সার্ভারে" ফাইল সংরক্ষণের সমস্যা**

যখন আপনি সরাসরি একটি EC2 instance-এ ফাইল সংরক্ষণ করেন — এর ফাইলসিস্টেমে — আপনি সেই ফাইলগুলিকে সেই নির্দিষ্ট মেশিনের lifecycle-এর সাথে বেঁধে দিচ্ছেন।

এটি বেশ কয়েকটি সমস্যা তৈরি করে:

**স্বভাবতই অস্থায়ী।** EC2 instance বন্ধ, terminate, প্রতিস্থাপন করা যায়। তাদের লোকাল ডিস্ক স্থায়ী হওয়ার কথা নয়। এটি অস্থায়ী স্ক্র্যাচ স্পেস।

**ব্যর্থতার একক বিন্দু।** Instance ব্যর্থ হলে, ফাইলগুলি সাথে যায়। কোনো রিডান্ড্যান্সি নেই। কোনো ব্যাকআপ নেই। একটি খারাপ সকাল এবং আটশত মেনু ফটো অদৃশ্য হয়ে যায়।

**Instance জুড়ে ভাগ করতে পারে না।** যখন আপনি একটি দ্বিতীয় সার্ভার যোগ করেন (যা আপনি করবেন, অধ্যায় ৭-এ), এটি প্রথম সার্ভারের ডিস্কে সংরক্ষিত ফাইলগুলি দেখবে না। দুটি সার্ভার বিচ্ছিন্ন। একজন ব্যবহারকারী যে একটি ফটো আপলোড করেছে সে দেখতে পারে; একটি ভিন্ন সার্ভারে আঘাত করা অন্য ব্যবহারকারী দেখতে পারবে না।

**কোনো স্কেল নেই।** EC2 ডিস্ক স্পেস সীমিত। এটি পূরণ হলে, আপনি হয় আপলোড গ্রহণ করা বন্ধ করেন বা চাপের মধ্যে স্টোরেজ প্রসারিত করতে ছোটাছুটি করেন।

একটি ভালো মডেল আছে। AWS এটি ২০০৬ সালে তৈরি করেছিল, এবং এটি এখনো বিশ্বের সবচেয়ে বেশি ব্যবহৃত ক্লাউড পরিষেবাগুলির মধ্যে একটি।

**Amazon S3: অনলাইনে থাকা হার্ড ড্রাইভ**

**Amazon S3** — Simple Storage Service — হলো AWS-এর অবজেক্ট স্টোরেজ পরিষেবা।

এটিকে ইন্টারনেটে থাকা একটি হার্ড ড্রাইভ হিসেবে মনে করুন। একটি অসীম হার্ড ড্রাইভ। যেটি স্বয়ংক্রিয়ভাবে কমপক্ষে তিনটি Availability Zone জুড়ে একাধিক কপি ব্যাকআপ করা হয় যাতে কোনো একটি ডেটা সেন্টার হারানো আপনার ফাইল না হারায়।

S3-এর মূল কনসেপ্ট হলো **object**।

একটি object হলো যেকোনো ফাইল: একটি ফটো, একটি ভিডিও, একটি PDF, একটি CSV, একটি ব্যাকআপ, একটি লগ ফাইল। S3 ধরন বা কাঠামো নিয়ে চিন্তা করে না। এটি bytes সংরক্ষণ করে এবং আপনি জিজ্ঞেস করলে ফিরিয়ে দেয়।

Object গুলি **buckets**-এর মধ্যে থাকে। একটি bucket হলো একটি শীর্ষ-স্তরের ফোল্ডারের মতো — S3-এর মধ্যে একটি নামযুক্ত কন্টেইনার যা আপনার object ধারণ করে। প্রতিটি bucket-এর একটি বৈশ্বিকভাবে অনন্য নাম রয়েছে (সমস্ত AWS অ্যাকাউন্ট জুড়ে কোনো দুটি bucket একটি নাম ভাগ করতে পারে না) এবং একটি নির্দিষ্ট Region-এ বিদ্যমান।

**S3 কীভাবে কাজ করে**

মডেলটি সহজ, এবং সেই সরলতাই বিন্দু।

আপনি একটি bucket-এ একটি object **upload** করেন। S3 এটিকে একটি **key** দেয় — মূলত একটি পাথ নাম যেমন `menus/restaurant-001/photo-arepa.jpg`। সেই key bucket-এর মধ্যে object টি অনন্যভাবে চিহ্নিত করে।

আপনি bucket নাম এবং key ব্যবহার করে object টি **download** (বা retrieve) করেন।

আপনি object গুলি publicly accessible-ও করতে পারেন — মানে URL সহ যেকেউ সেগুলি ডাউনলোড করতে পারে। বেশিরভাগ ওয়েবসাইট ইমেজ পরিবেশনের এটাই উপায়: ইমেজ S3-এ সংরক্ষণ করুন, public করুন, আপনার HTML-এ URL embed করুন।

অথবা আপনি object গুলি private রাখুন — শুধুমাত্র authenticated অনুরোধের কাছে অ্যাক্সেসযোগ্য। এটি গ্রাহকের ডেটা, ব্যাকআপ এবং যেকোনো সংবেদনশীল বিষয়ের সঠিক মডেল।

S3 একটি ফাইলসিস্টেম নয়। কোনো বাস্তব ফোল্ডার নেই। একটি key নামে `/` শুধু একটি কনভেনশন — S3 পুরো key কে একটি ফ্ল্যাট স্ট্রিং হিসেবে ব্যবহার করে। কিন্তু এটি ফোল্ডারের মতো দেখায় এবং বেশিরভাগ সরঞ্জাম এটি ফোল্ডার হিসেবে উপস্থাপন করে, তাই ব্যবহারে এই পার্থক্য নিয়ে চিন্তা করবেন না।

**S3 কেন একটি নিয়মিত হার্ড ড্রাইভ থেকে আলাদা**

তিনটি জিনিস S3 কে একটি EC2 instance-এ ফাইল স্টোরেজ থেকে মৌলিকভাবে আলাদা করে:

**Durability।** AWS S3-কে ৯৯.৯৯৯৯৯৯৯৯৯% (এগারো নাইন) durability-র জন্য ডিজাইন করে। এর মানে যদি আপনি এক কোটি object সংরক্ষণ করেন, হার্ডওয়্যার ব্যর্থতার কারণে আপনি প্রতি দশ হাজার বছরে একটি object হারানোর আশা করতে পারেন। তারা এটি অর্জন করে স্বয়ংক্রিয়ভাবে কমপক্ষে তিনটি Availability Zone জুড়ে প্রতিটি object-এর একাধিক কপি সংরক্ষণ করে।

**Availability।** S3 পৃথক উপাদান ব্যর্থ হলেও অ্যাক্সেসযোগ্য থাকার জন্য ডিজাইন করা হয়েছে। আপনি একটি সার্ভারের সাথে সংযোগ করছেন না — আপনি একটি বিতরণ করা সিস্টেমের সাথে সংযোগ করছেন যা ব্যর্থতার চারপাশে রুট করে।

**Scale।** S3 মূলত অসীম পরিমাণ ডেটা ধারণ করে। একটি একক bucket ট্রিলিয়ন object ধারণ করতে পারে। Amazon নিজেই S3 ব্যবহার করে এমন স্কেলে ডেটা সংরক্ষণ করতে যা বোঝা কঠিন।

**Versioning: Undo বোতাম**

Maya যখন S3 কনসোল অন্বেষণ করছিল তখন সে এটি খুঁজে পেয়েছিল।

S3 **versioning** সমর্থন করে। যখন আপনি একটি bucket-এ versioning সক্ষম করেন, S3 প্রতিটি object-এর প্রতিটি ভার্সন রাখে — পূর্ববর্তী ভার্সন এবং মুছে ফেলা ভার্সন সহ।

এটি আপনার ফাইলের জন্য undo বোতাম।

একটি নতুন মেনু ফটো আপলোড করুন যা দুর্ঘটনাক্রমে পুরানোটি ওভাররাইট করে? পুরানো ভার্সন এখনো সেখানে আছে। ভুলবশত একটি ফাইল মুছুন? এটি পুনরুদ্ধারযোগ্য। র‌্যানসমওয়্যার দ্বারা আঘাত পান যা আপনার সমস্ত ফাইল এনক্রিপ্টেড আবর্জনা দিয়ে ওভাররাইট করে? Versioning-এর সাথে, আপনি আক্রমণের আগে থেকে পুনরুদ্ধার করুন।

"সমস্ত সেই ভার্সন রাখতে কত খরচ হয়?" Tom জিজ্ঞেস করল।

আপনি প্রতিটি ভার্সনের স্টোরেজের জন্য পেমেন্ট করেন। যদি আপনার বড় ফাইলের অনেক ভার্সন থাকে, এটি যোগ হয়। AWS-এর **lifecycle policies** আছে যা একটি নির্দিষ্ট সময়ের পরে স্বয়ংক্রিয়ভাবে পুরানো ভার্সন মুছে দেয় — আমরা অধ্যায় ২৩-এ খরচ অপ্টিমাইজেশনে গভীরে যাওয়ার সময় সেগুলি কভার করি।

**অ্যাক্সেস নিয়ন্ত্রণ: Public বনাম Private**

ডিফল্টরূপে, S3-তে সবকিছু private। শুধুমাত্র আপনার AWS অ্যাকাউন্ট এটি অ্যাক্সেস করতে পারে।

আপনি পৃথক object গুলি public করতে পারেন — যেটি আপনি ওয়েবসাইট দর্শকদের মেনু ইমেজ পরিবেশনের জন্য করবেন। অথবা আপনি সবকিছু private রাখতে পারেন এবং **pre-signed URLs** তৈরি করতে পারেন: সময়-সীমিত লিঙ্ক যা কাউকে AWS শংসাপত্র ছাড়াই একটি নির্দিষ্ট object ডাউনলোড করতে দেয়। ২৪ ঘণ্টার জন্য একজন গ্রাহককে তাদের ইনভয়েস ডাউনলোড করতে দেওয়ার জন্য নিখুঁত।

Priya এ বিষয়ে খুব দৃঢ় মতামত রাখতেন।

"একটি bucket কখনো সম্পূর্ণ public করবেন না যদি না আপনি সচেতনভাবে সিদ্ধান্ত নেন যে এতে থাকা প্রতিটি object পুরো ইন্টারনেটে অ্যাক্সেসযোগ্য হবে," তিনি বললেন। "সবচেয়ে সাধারণ S3 নিরাপত্তার ভুল হলো ঘটনাক্রমে এমন একটি bucket প্রকাশ করা যাতে সংবেদনশীল ডেটা রয়েছে।"

AWS-এ এখন একটি "Block Public Access" সেটিং আছে যা আপনি অ্যাকাউন্ট স্তরে প্রয়োগ করতে পারেন, সমস্ত bucket প্রতি-bucket-এ স্পষ্টভাবে ওভাররাইড না করলে private রাখতে বাধ্য করে।

সক্ষম করুন। সর্বদা।

**S3 Storage Classes: সমস্ত ডেটা সমান নয়**

সমস্ত ডেটা সমানভাবে অ্যাক্সেস করা হয় না।

আপনার সবচেয়ে জনপ্রিয় মেনু ফটোগুলি প্রতি সেকেন্ডে ডজন বার আনা হয়। তিন বছর আগের লগগুলি বছরে একবার, যদি সত্যিই, অ্যাক্সেস করা হয়। S3 এটি স্বীকার করে এবং বিভিন্ন পারফরম্যান্স এবং খরচ আপোস সহ বিভিন্ন **storage classes** অফার করে।

| Storage Class           | ব্যবহারের ক্ষেত্র                              | Retrieval        | খরচ                         |
|-------------------------|-----------------------------------------------|------------------|-----------------------------|
| S3 Standard             | ঘন ঘন অ্যাক্সেস করা ডেটা                     | তাৎক্ষণিক        | প্রতি GB বেশি               |
| S3 Standard-IA          | কম অ্যাক্সেস, তবুও দ্রুত retrieval প্রয়োজন  | তাৎক্ষণিক        | প্রতি GB কম, retrieval ফি   |
| S3 Glacier Instant      | মাঝে মাঝে অ্যাক্সেস করা আর্কাইভ              | তাৎক্ষণিক        | অনেক কম                     |
| S3 Glacier Flexible     | বিরল অ্যাক্সেস আর্কাইভ                        | মিনিট থেকে ঘণ্টা | খুব কম                      |
| S3 Glacier Deep Archive | সম্মতি আর্কাইভ, প্রায় কখনো অ্যাক্সেস হয় না | ১২ ঘণ্টা পর্যন্ত | সর্বনিম্ন                   |

আমরা অধ্যায় ২৩-এ এগুলির গভীরে যাই। এখনের জন্য: কনসেপ্টটি হলো আপনি তাদের বয়স এবং অ্যাক্সেস প্যাটার্নের উপর ভিত্তি করে স্বয়ংক্রিয়ভাবে storage class গুলির মধ্যে object স্থানান্তর করতে পারেন, যে ডেটা আপনি বিরল স্পর্শ করেন তাতে উল্লেখযোগ্য অর্থ সাশ্রয় করে।

## শক্তি এবং সীমাবদ্ধতা

**S3 কেন চমৎকার**:

- এগারো-নাইন durability। আপনার ডেটা S3-এ প্রায় যেকোনো অন্য সিস্টেমের চেয়ে নিরাপদ।
- অসীমিত স্কেল। আপনাকে কখনো স্টোরেজ প্রভিশন করতে হবে না — এটি শুধু বাড়তে থাকে।
- যা প্রদান করে তার জন্য অত্যন্ত সস্তা (প্রতি মাসে প্রতি GB-এর ভগ্নাংশ সেন্ট)।
- প্রায় প্রতিটি অন্যান্য AWS পরিষেবার সাথে নেটিভ ইন্টিগ্রেশন।
- স্ট্যাটিক ওয়েবসাইট হোস্টিং সমর্থন করে — আপনি S3 থেকে সরাসরি একটি সম্পূর্ণ স্ট্যাটিক ওয়েবসাইট পরিবেশন করতে পারেন, কোনো সার্ভার প্রয়োজন নেই।

**S3 সঠিক পছন্দ নয় যেখানে**:

- S3 একটি ফাইলসিস্টেম নয়। আপনার অ্যাপ্লিকেশনের যদি একটি ড্রাইভ মাউন্ট করার এবং একটি লোকাল ডিস্কের মতো ব্যবহার করার প্রয়োজন হয় (ফাইল পড়া, লেখা, জায়গায় পরিবর্তন করা), S3 ভুল হাতিয়ার। পরিবর্তে EFS (Elastic File System, অধ্যায় ৬) বা EBS ব্যবহার করুন।
- S3-এর লেটেন্সি একটি লোকাল ডিস্কের চেয়ে লক্ষণীয়ভাবে বেশি। ডেটাবেস বা অ্যাপ্লিকেশনের জন্য যার দ্রুত, র‌্যান্ডম-অ্যাক্সেস I/O প্রয়োজন, block storage (EBS, অধ্যায় ৬) উপযুক্ত।
- S3-তে বড় ডেটা ট্রান্সফার বিনামূল্যে। S3 *থেকে* বড় ডেটা ট্রান্সফার অর্থ ব্যয় করে। এটি একটি সাধারণ বিলিং বিস্ময় — আমরা অধ্যায় ৩০-এ এটি সমাধান করি।

## সারসংক্ষেপ

- **Amazon S3** হলো object storage — নামযুক্ত কন্টেইনারে (buckets বলা হয়) ফাইল (object বলা হয়) সংরক্ষণের একটি জায়গা।
- S3 স্বয়ংক্রিয়ভাবে কমপক্ষে তিনটি Availability Zone জুড়ে প্রতিটি object-এর কপি সংরক্ষণ করে এগারো-নাইন durability-র জন্য ডিজাইন করা।
- EC2 instance-এ সংরক্ষিত ফাইলগুলি সেই instance-এর lifecycle-এর সাথে বাঁধা। গুরুত্বপূর্ণ ফাইলগুলি S3-এ থাকে, সার্ভারে নয়।
- **Versioning** object-এর পূর্ববর্তী ভার্সন সংরক্ষণ করে — আপনার undo বোতাম।
- ডিফল্টরূপে, S3 private। অ্যাকাউন্ট স্তরে "Block Public Access" সক্ষম করুন।
- S3-এর বিভিন্ন অ্যাক্সেস প্যাটার্ন এবং খরচের জন্য একাধিক **storage classes** রয়েছে। Infrequent access class গুলি অনেক সস্তা কিন্তু retrieval ফি চার্জ করে।

## পরীক্ষার টিপস

*SAA-C03 ডোমেন ৩ — টাস্ক ৩.১ (উচ্চ-পারফরমিং storage সমাধান)*

- **S3 হলো object storage, block storage নয়।** যখন একটি পরীক্ষার দৃশ্যকল্পে একটি ফাইলসিস্টেম প্রয়োজন যা একাধিক সার্ভার মাউন্ট করতে পারে, সেটি EFS। যখন একটি EC2 instance-এর জন্য একটি ডিস্ক প্রয়োজন, সেটি EBS। যখন ফাইল, ব্যাকআপ, ইমেজ বা HTTP-এর মাধ্যমে অ্যাক্সেস করা ডেটা সংরক্ষণ করতে হয় — সেটি S3।
- **এগারো-নাইন durability** মানে S3 স্বয়ংক্রিয়ভাবে একাধিক AZ জুড়ে ডেটা রেপ্লিকেট করে। আপনাকে এটি কনফিগার করতে হবে না — এটি ডিফল্ট।
- **S3 Regional**, কিন্তু বৈশ্বিকভাবে অ্যাক্সেসযোগ্য। Bucket একটি নির্দিষ্ট Region-এ বিদ্যমান, কিন্তু আপনি সেগুলি যেকোনো জায়গা থেকে অ্যাক্সেস করতে পারেন।
- **Pre-signed URLs** private object-এ সময়-সীমিত অ্যাক্সেস অনুমতি দেয়। সাধারণ প্যাটার্ন: আপনার অ্যাপ্লিকেশন ১৫ মিনিটের জন্য বৈধ একটি pre-signed URL তৈরি করে, ব্যবহারকারীকে দেয়, ব্যবহারকারী সরাসরি S3 থেকে ফাইল ডাউনলোড করে।
- **S3 Standard-IA**-তে একটি ন্যূনতম storage সময়কাল চার্জ (৩০ দিন) আছে। এটি ডেটার জন্য ব্যবহার করবেন না যা আপনি দ্রুত মুছবেন। পরীক্ষা পরীক্ষা করে আপনি storage class-এর মধ্যে আপোস জানেন কিনা।
- **Storage class সিদ্ধান্ত গাছ**: *ঘন ঘন অ্যাক্সেস করা* → S3 Standard; *বিরল অ্যাক্সেস কিন্তু দ্রুত retrieval দরকার* → S3 Standard-IA; *মাঝে মাঝে অ্যাক্সেস করা আর্কাইভ* → S3 Glacier Instant Retrieval; *বিরল অ্যাক্সেস আর্কাইভ* → S3 Glacier Flexible Retrieval; *সম্মতি আর্কাইভ, প্রায় কখনো অ্যাক্সেস হয় না* → S3 Glacier Deep Archive।

## অনুশীলন

**অনুশীলন ১ — স্মরণ**

আপনার নিজের ভাষায়: একটি S3 object কী? একটি S3 bucket কী? EC2 instance-এর লোকাল ডিস্কে ফাইল সংরক্ষণ করার চেয়ে S3-এ সংরক্ষণ করা কেন ভালো?

*(ইঙ্গিত: EC2 instance terminate হলে ফাইলের কী হয় তা নিয়ে ভাবুন। S3 কী আলাদাভাবে করে?)*

**অনুশীলন ২ — পরীক্ষার অনুশীলন**

*দৃশ্যকল্প*: একটি মিডিয়া কোম্পানি ডকুমেন্টারি ভিডিও তৈরি করে। তাদের মূল 4K ফুটেজ (প্রযোজনার সময় ঘন ঘন অ্যাক্সেস করা), সম্পাদিত চূড়ান্ত কাট (বিতরণের জন্য মাসিক অ্যাক্সেস) এবং আর্কাইভ মাস্টার (অনির্দিষ্টকালের জন্য রাখা কিন্তু সম্মতির জন্য বছরে সর্বাধিক একবার অ্যাক্সেস) সংরক্ষণ করতে হবে। তারা প্রতিটি স্তরের অ্যাক্সেস প্রয়োজনীয়তা পূরণ করে storage খরচ কমাতে চায়।

কোন storage কৌশলটি তাদের প্রয়োজনীয়তা সর্বোত্তমভাবে পূরণ করে?

A) সামঞ্জস্যপূর্ণ পারফরম্যান্স এবং সরলতার জন্য S3 Standard-এ সমস্ত কন্টেন্ট সংরক্ষণ করুন  
B) S3 Standard-এ মূল ফুটেজ, S3 Standard-IA-তে চূড়ান্ত কাট এবং S3 Glacier Deep Archive-এ আর্কাইভ সংরক্ষণ করুন  
C) দ্রুততম অ্যাক্সেসের জন্য EC2 instance storage-এ সমস্ত কন্টেন্ট সংরক্ষণ করুন  
D) খরচ কমাতে S3 Glacier Deep Archive-এ সমস্ত কন্টেন্ট সংরক্ষণ করুন

**ইঙ্গিত ১**: বিভিন্ন ফাইলের বিভিন্ন অ্যাক্সেস প্যাটার্ন রয়েছে। S3 বিভিন্ন অ্যাক্সেস ফ্রিকোয়েন্সির জন্য বিভিন্ন storage class অফার করে। কোন class "ঘন ঘন অ্যাক্সেস করা" এর সাথে মেলে?

**ইঙ্গিত ২**: "বছরে সর্বাধিক একবার" অ্যাক্সেস করা আর্কাইভের তাৎক্ষণিক retrieval দরকার নেই। কোন storage class ন্যূনতম খরচে দীর্ঘমেয়াদী সংরক্ষণের জন্য ডিজাইন করা?

**ইঙ্গিত ৩**: প্রতিটি স্তরের অ্যাক্সেস ফ্রিকোয়েন্সি উপযুক্ত storage class-এর সাথে মেলান। ঘন ঘন অ্যাক্সেস = Standard। মাসিক = Standard-IA। বছরে একবার = Glacier Deep Archive।

**উত্তর**: B

**ব্যাখ্যা**: এই কৌশল প্রতিটি ডেটা স্তরকে উপযুক্ত S3 storage class-এর সাথে সঠিকভাবে মেলায়। ঘন ঘন অ্যাক্সেস করা মূল ফুটেজ কোনো retrieval ফি ছাড়াই তাৎক্ষণিক অ্যাক্সেসের জন্য Standard-এ থাকে। মাসিক-অ্যাক্সেস চূড়ান্ত কাট Standard-IA-তে যায় (কম storage খরচ, সাশ্রয়ী retrieval ফি)। বছরে একবার অ্যাক্সেস করা আর্কাইভ সর্বনিম্ন storage খরচের জন্য Glacier Deep Archive-এ যায়।

**কেন A নয়?** সবকিছু Standard-এ সংরক্ষণ করা সহজ কিন্তু ব্যয়বহুল। আপনি আর্কাইভ কন্টেন্টের জন্য প্রিমিয়াম মূল্য দিচ্ছেন যা আপনি বিরল অ্যাক্সেস করেন।

**কেন C নয়?** EC2 instance storage অস্থায়ী এবং দীর্ঘমেয়াদী মিডিয়া সংরক্ষণের জন্য উপযুক্ত নয়। Instance terminate হলে সমস্ত কন্টেন্ট হারিয়ে যাবে।

**কেন D নয়?** Glacier Deep Archive-এ ১২ ঘণ্টা পর্যন্ত retrieval সময় আছে। ঘন ঘন অ্যাক্সেস করা প্রোডাকশন ফুটেজ সেখানে সংরক্ষণ করলে প্রোডাকশন কাজ অসম্ভব হয়ে পড়বে।

*SAA-C03 ডোমেন ৩ — টাস্ক ৩.১ / ডোমেন ৪ — টাস্ক ৪.১*

**অনুশীলন ৩ — আর্কিটেকচার চ্যালেঞ্জ** *(ঐচ্ছিক)*

Nimbus S3-এ গ্রাহক-আপলোড করা অর্ডার ফটো সংরক্ষণ করে। একটি ডেটা সুরক্ষা নিয়ন্ত্রণ প্রয়োজন যে গ্রাহকের ফটোগুলি ৭ বছরের জন্য সংরক্ষিত হতে হবে কিন্তু তারপর মুছে ফেলা যাবে। দলটি আগের বছরের পুরানো ফটো সংরক্ষণের খরচও কমাতে চায়।

এই প্রয়োজনীয়তার জন্য একটি S3 storage কৌশল ডিজাইন করুন। আপনি কোন storage class ব্যবহার করবেন, এবং কখন তাদের মধ্যে রূপান্তরিত হবেন? মুছে ফেলার প্রয়োজনীয়তা সম্পর্কে আপনি কী করবেন?

*(ইঙ্গিত: lifecycle policies নিয়ে ভাবুন। একটি একক সঠিক উত্তর নেই — খরচ বনাম retrieval সময়ের আপোস নিয়ে যুক্তি করুন।)*

Leo সেই বিকেলে মেনু ফটোগুলি S3-এ মাইগ্রেট করল। আটশত object, তিনটি Availability Zone জুড়ে নিরাপদে সংরক্ষিত, versioning সক্ষম।

"তারা আসলে এখন আগের চেয়ে নিরাপদ," সে কিছুটা তৃপ্তি নিয়ে বলল।

"তারা সবসময় S3-এ নিরাপদ ছিল," Priya বলল। "আমরা শুধু সমস্যা তৈরি হওয়ার পরে এটি ঠিক করতে অপেক্ষা করলাম।"

Leo এটি গ্রহণ করল।

পরের সকালে, Tom একটি প্রিন্টআউট নিয়ে এলো। AWS বিল, লাল কলম দিয়ে টীকা করা।

"আমাদের একটি ডেটাবেস সমস্যা আছে," সে বলল। "আমরা ওয়েব সার্ভারের মতো একই EC2 instance-এ আমাদের অর্ডার ডেটাবেস চালাচ্ছি। এবং আমাদের মেনু ডেটাবেস। এবং আমাদের গ্রাহক রেকর্ড।"

সে থামল।

"সবকিছু একই মেশিনে। একটি মেশিন। আমাদের সমস্ত ডেটা।"

Maya প্রিন্টআউটটি দেখল। তারপর Tom-এর দিকে। তারপর সিলিংয়ের দিকে।

"এবং সেই মেশিন ভাঙলে?"

Tom লাল কলমের টীকার দিকে আঙুল তুলল।

পরবর্তী অধ্যায়ে: আপনি যে হার্ড ড্রাইভ ভাড়া নেন এবং পুরো অফিস যে ফাইলিং ক্যাবিনেট ভাগ করে তার মধ্যে পার্থক্য।
