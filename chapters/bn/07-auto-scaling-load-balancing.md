# অধ্যায় ৭: ব্যস্ত হলে বড় হওয়া রেস্তোরাঁ

শুক্রবার রাত ৭:৪৩-এ error rate ১২% অতিক্রম করল।

Tom প্রথমে লক্ষ্য করল কারণ Tom সবসময় প্রথমে লক্ষ্য করে। তার CloudWatch dashboard-এ একটি ট্যাব খোলা ছিল যা সে অন্যরা যেভাবে সোশ্যাল মিডিয়া চেক করে সেভাবে refresh করত — প্রতিফলিতভাবে, ক্রমাগত, ইচ্ছে না করেই।

"Leo," সে বলল।

Leo ইতিমধ্যে দেখছিল। Response time: বাড়ছে। অপেক্ষারত অনুরোধ: বাড়ছে। একক EC2 instance — এমনকি তারা গত মাসে আপগ্রেড করা বড়টিও — ৯৪% CPU-এ ছিল।

"আমরা গ্রাহক ফিরিয়ে দিচ্ছি," Tom বলল।

"আমরা তাদের ফিরিয়ে দিচ্ছি না," Leo বলল। "সার্ভার ফিরিয়ে দিচ্ছে।"

"এটা একই জিনিস।"

এটা ছিল। এবং প্রতি শুক্রবার তিন সপ্তাহ ধরে ঘটছিল। Nimbus storage সংকট থেকে বেঁচে গিয়েছিল — ডেটাবেসের নিজস্ব ডিস্ক ছিল, ফটোগুলি S3-এ ছিল — কিন্তু stable এবং scalable সম্পূর্ণ ভিন্ন সমস্যা। সিস্টেম কাজ করত। এটি শুধু বাড়ত না।

দলটির প্রয়োজন ছিল তাদের সিস্টেম স্বয়ংক্রিয়ভাবে পরিবর্তনশীল লোড সামলাক। খারাপ সময়ের জন্য যথেষ্ট সার্ভার কিনে শান্ত সময়ে অর্থ নষ্ট না করে। এবং ট্রাফিক স্পাইক হলে ম্যানুয়ালি তাড়াহুড়ো না করে।

এর জন্য একটি প্যাটার্ন আছে। AWS-এর দুটি পরিষেবা আছে যা এটি বাস্তবায়ন করে।

**কনসেপ্ট: Horizontal Scaling**

একটি সিস্টেমকে আরো লোড সামলাতে দুটি উপায় আছে।

**Vertical scaling** মানে একক সার্ভারটি বড় করা। আরো CPU। আরো RAM। আমরা অধ্যায় ৪-এ এটি করেছিলাম যখন `t3.micro` থেকে `t3.large`-এ আপগ্রেড করেছিলাম। এটি সাহায্য করে। কিন্তু এটির সীমা আছে: আপনি শুধু এতটাই বড় যেতে পারেন, instance resize করতে restart করতে হয়, এবং আপনার এখনো একটি single point of failure আছে।

**Horizontal scaling** মানে আরো সার্ভার যোগ করা। একটি বড় সার্ভারের পরিবর্তে, পাঁচটি মাঝারি সার্ভার চালান। ট্রাফিক কমলে, দুটি চালান। স্পাইক হলে, দশটি চালান।

Horizontal scaling-এর vertical-এর মতো না থাকা সুবিধা আছে:

- কোনো single point of failure নেই। একটি সার্ভার মারা গেলে, অন্যগুলি পরিবেশন চালিয়ে যায়।
- ক্যাপাসিটি যোগ করতে restart প্রয়োজন নেই।
- শুধুমাত্র যা ব্যবহার করছেন তার জন্য পে করুন — প্রয়োজনে সার্ভার যোগ করুন, না লাগলে সরান।
- Linear scaling: দ্বিগুণ সার্ভার, প্রায় দ্বিগুণ throughput।

ধরা: যদি আপনার একাধিক সার্ভার থাকে, ব্যবহারকারীরা কোনটিতে কথা বলবে তা কীভাবে জানবে?

**Application Load Balancer: এক দরজা, অনেক ঘর**

একটি **Application Load Balancer** (ALB) হলো আপনার অ্যাপ্লিকেশনের সামনের দরজা।

ব্যবহারকারীরা load balancer-এর সাথে সংযোগ করে। Load balancer আপনার EC2 instance-এর fleet জুড়ে আসা অনুরোধগুলি বিতরণ করে। প্রতিটি ব্যবহারকারী একটি ঠিকানা দেখে (load balancer-এর URL)। সেই ঠিকানার পেছনে, অনুরোধগুলি যতগুলি সার্ভার চলছে তাদের জুড়ে ছড়িয়ে পড়ে।

একটি বড় রেস্তোরাঁর মতো মনে করুন যার দরজায় হোস্ট স্ট্যান্ড আছে। ডাইনার আসে এবং হোস্ট তাদের একটি পাওয়া যাওয়া টেবিলে পরিচালিত করে। হোস্ট জানে কোন টেবিলগুলি ব্যস্ত এবং কোনগুলি খালি। ডাইনারদের কতটি টেবিল আছে তা জানার দরকার নেই — তারা শুধু ঢোকে এবং হোস্ট বিতরণ পরিচালনা করে।

একটি ALB ওয়েব অনুরোধের সাথে এটি করে। এটি প্রতিটি আসা HTTP অনুরোধ গ্রহণ করে এবং সিদ্ধান্ত নেয় কোন EC2 instance (**target** বলা হয়) এটি পরিচালনা করবে, যেমন কারণগুলির উপর ভিত্তি করে:

- Round-robin (প্রতিটি সার্ভার পর্যায়ক্রমে পায়)
- Least outstanding requests (সবচেয়ে কম in-flight অনুরোধ থাকা সার্ভার পরবর্তী অনুরোধ পায়)
- Health — শুধুমাত্র healthy target ট্রাফিক পায়

**Health checks** অপরিহার্য। ALB নিয়মিত প্রতিটি target-এ test অনুরোধ পাঠায়। যদি একটি target সঠিকভাবে সাড়া না দেয়, ALB এটিকে unhealthy চিহ্নিত করে এবং এতে ট্রাফিক পাঠানো বন্ধ করে। target পুনরুদ্ধার হলে, ট্রাফিক পুনরায় শুরু হয়।

এটি স্বয়ংক্রিয়। আপনি health check parameter কনফিগার করেন; ALB সেগুলি প্রয়োগ করে।

**Auto Scaling: আরো টেবিল খোলা রেস্তোরাঁ**

একটি ALB আপনার বিদ্যমান সার্ভার জুড়ে ট্রাফিক বিতরণ করে। কিন্তু আরো সার্ভার প্রয়োজন হলে এটি যোগ করে না।

**Auto Scaling** এটি করে।

একটি **Auto Scaling Group** (ASG) হলো এমন একটি কনফিগারেশন যা AWS-কে বলে:

- সবসময় সর্বনিম্ন কতটি instance চলবে
- অনুমোদিত সর্বাধিক instance সংখ্যা
- কখন scale out (instance যোগ) বা scale in (সরান) করার শর্তগুলি

স্কেলিং শর্তগুলিকে **policies** বলা হয়। সবচেয়ে সাধারণ type:

**Target tracking**: "গড় CPU utilization ৭০%-এ রাখুন।" গড় CPU ৭০% অতিক্রম করলে, AWS নতুন instance চালু করে। এটি কমলে, instance terminate হয়।

এটি স্বয়ংক্রিয়। কাউকে metrics দেখতে হয় না। কাউকে ম্যানুয়ালি সার্ভার চালু করতে হয় না। সিস্টেম রিয়েল টাইমে লোডে সাড়া দেয়।

Priya প্রথমবার একটি শুক্রবারের rush-এ এটি live দেখল। সার্ভারের সংখ্যা পনের মিনিটে ২ থেকে ৫-এ চলে গেল, তারপর rush-এর পরে ২-এ ফিরে এল।

"এটা," সে বলল, "সত্যিই চমৎকার।"

Tom পরিবর্তে cost graph দেখছিল। rush-এর সময় বিল বেড়েছিল এবং পরে কমেছিল। "আমরা শুধু যা ব্যবহার করেছি তার জন্য পেমেন্ট করেছি," সে বলল, সমানভাবে মুগ্ধ।

**ALB এবং ASG একসাথে কীভাবে কাজ করে**

দুটি পরিষেবা একসাথে ব্যবহারের জন্য ডিজাইন করা।

আপনি সামনে ALB রাখুন। ALB একটি **target group**-এর দিকে নির্দেশ করে — এমন instance-এর সংগ্রহ যা ট্রাফিক পাওয়া উচিত। Auto Scaling Group সেই instance গুলি পরিচালনা করে: scale out-এর সময় target group-এ যোগ করে, scale in-এর সময় সরায়।

প্রবাহ:

১. ট্রাফিক ALB-এ আসে
২. ALB healthy target-এ অনুরোধ বিতরণ করে
৩. সেই target-এ CPU/লোড বাড়ে
৪. ASG লোড বৃদ্ধি সনাক্ত করে, নতুন instance চালু করে
৫. নতুন instance health check পাস করে, ALB-এর সাথে নিবন্ধিত হয়
৬. ALB তাদের কাছে ট্রাফিক পাঠাতে শুরু করে
৭. লোড কমে, ASG অতিরিক্ত instance terminate করে
৮. ALB terminate করা instance-এ ট্রাফিক পাঠানো বন্ধ করে

এটি কোনো মানবিক হস্তক্ষেপ ছাড়াই ঘটে।

**Launch Templates: নতুন Instance-এর ব্লুপ্রিন্ট**

যখন ASG একটি নতুন instance চালু করে, এটি কী চালু করতে হবে তা জানতে হবে। এটি একটি **Launch Template**-এ সংজ্ঞায়িত করা হয় — একটি AMI, একটি instance type, প্রয়োগ করার security group এবং যেকোনো user data (startup script যা instance boot হলে চলে)।

একটি সাধারণ প্যাটার্ন: আপনি আপনার অ্যাপ্লিকেশন একটি custom AMI-তে নির্মাণ করেন (অধ্যায় ৪ দেখুন)। ASG-এর একটি নতুন instance দরকার হলে, এটি সেই AMI চালু করে। নতুন instance আপনার অ্যাপ্লিকেশন ইতিমধ্যে ইনস্টল নিয়ে boot করে। কোনো ম্যানুয়াল সেটআপ প্রয়োজন নেই।

আরো গতিশীল পরিবেশের জন্য, আপনি **user data scripts**-ও ব্যবহার করতে পারেন যা startup-এ আপনার কোডের সর্বশেষ সংস্করণ pull এবং install করে। এটি আরো নমনীয় কিন্তু boot করতে বেশি সময় নেয়।

সঠিক পছন্দ নির্ভর করে আপনার instance-গুলিকে boot করতে কতটা সময় লাগতে পারে এবং আপনার অ্যাপ্লিকেশন কত ঘন ঘন পরিবর্তিত হয়।

**Sticky Sessions: একটি সূক্ষ্ম সমস্যা**

এখানে এমন কিছু আছে যা অনেক দলকে হোঁচট খাওয়ায় যখন তারা প্রথম load balancing বাস্তবায়ন করে।

কিছু ওয়েব অ্যাপ্লিকেশন session data — login অবস্থা, shopping cart বিষয়বস্তু — সার্ভার নিজেই (মেমরিতে বা লোকাল ডিস্কে) সংরক্ষণ করে। একটি সার্ভারে এটি ঠিক আছে। একাধিক সার্ভারে, এটি ভাঙে।

একজন ব্যবহারকারী লগ ইন করে। অনুরোধটি Server A-তে যায়। Server A session সংরক্ষণ করে। পরবর্তী অনুরোধটি Server B-তে যায়। Server B-তে কোনো session নেই। ব্যবহারকারী logged out দেখায়।

এটি দুটি উপায়ে সমাধান করা যায়:

**Sticky sessions** (বা session affinity): ALB কনফিগার করুন যাতে একই ব্যবহারকারীর অনুরোধ সবসময় একই সার্ভারে যায়। এটি একটি short-term fix। এটি load balancing-কে ক্ষতিগ্রস্ত করে (কিছু সার্ভার বেশি "sticky" ব্যবহারকারী পায়) এবং instance terminate হলে সমস্যা তৈরি করে।

**Stateless application design**: session data বাইরে সংরক্ষণ করুন — একটি ডেটাবেস বা ElastiCache-এর মতো cache-এ (অধ্যায় ১০)। প্রতিটি সার্ভার বাইরের store থেকে যেকোনো ব্যবহারকারীর session পুনর্নির্মাণ করতে পারে। সার্ভারগুলি বিনিময়যোগ্য হয়। হরিজোন্টালি স্কেলযোগ্য অ্যাপ্লিকেশনের জন্য এটি সঠিক পদ্ধতি।

Priya এটিকে "multi-server যাওয়ার সময় আপনার সবচেয়ে গুরুত্বপূর্ণ আর্কিটেকচারাল সিদ্ধান্ত" বলেছিল। তিনি সঠিক। আমরা অধ্যায় ১০-এ এটি আবার সম্মুখীন হই।

**Load Balancer-এর প্রকার**

AWS তিন ধরনের load balancer অফার করে, প্রতিটি বিভিন্ন ট্রাফিকের জন্য উপযুক্ত:

**Application Load Balancer (ALB)**: HTTP এবং HTTPS ট্রাফিক। Layer 7 (HTTP বোঝে)। URL path (`/api` এক group-এ, `/static` অন্যটিতে), host header এবং query parameter-এর উপর ভিত্তি করে route করতে পারে। বেশিরভাগ ওয়েব অ্যাপ্লিকেশন এটি ব্যবহার করে।

**Network Load Balancer (NLB)**: TCP, UDP এবং TLS ট্রাফিক। Layer 4 (HTTP বোঝে না)। অত্যন্ত উচ্চ পারফরম্যান্স, প্রতি সেকেন্ডে কোটি অনুরোধ, অত্যন্ত কম লেটেন্সি। যখন raw গতি দরকার বা HTTP নিয়ে কাজ না করলে ব্যবহার করুন।

**Gateway Load Balancer (GWLB)**: তৃতীয় পক্ষের ভার্চুয়াল নেটওয়ার্ক appliance (firewall, intrusion detection) দিয়ে ট্রাফিক route করার জন্য। জুনিয়র স্তরে আপনার এটির খুব কমই প্রয়োজন হবে।

Nimbus (এবং বেশিরভাগ ওয়েব অ্যাপ্লিকেশন)-এর জন্য, ALB সঠিক পছন্দ।

## শক্তি এবং সীমাবদ্ধতা

**ALB + Auto Scaling কেন শক্তিশালী**:

- Zero-downtime scaling (বিদ্যমান সংযোগ ব্যাহত না করে instance যোগ/সরানো হয়)
- স্বয়ংক্রিয় failover (অস্বাস্থ্যকর instance স্বয়ংক্রিয়ভাবে ট্রাফিক থেকে সরানো হয়)
- খরচ দক্ষতা (শুধুমাত্র চলমান instance-এর জন্য পে করুন)
- কোনো single point of failure নেই — একাধিক AZ জুড়ে একাধিক instance

**যেখানে জটিল হয়**:

- Stateful অ্যাপ্লিকেশনের বিশেষ পরিচালনা প্রয়োজন (sticky session বা বাইরের state)
- Scale out সময় নেয় — ট্রাফিক তাৎক্ষণিকভাবে বাড়লে, নতুন instance প্রস্তুত হওয়ার আগে একটি lag থাকে। আপনি **scheduled scaling** (পরিচিত ইভেন্টের আগে pre-scale) বা বড় minimum instance count দিয়ে এটি প্রশমিত করতে পারেন
- আরো moving parts মানে monitor ও debug করার জন্য আরো
- কিছু অ্যাপ্লিকেশন সহজে হরিজোন্টালি scale করা যায় না (ডেটাবেস, নির্দিষ্ট legacy সিস্টেম)। Horizontal scaling stateless tier-এর জন্য সবচেয়ে ভালো কাজ করে।

## সারসংক্ষেপ

- **Horizontal scaling** (আরো সার্ভার যোগ করা) vertical scaling (একটি সার্ভার বড় করা)-এর চেয়ে পছন্দের কারণ এটি single point of failure দূর করে এবং elastic খরচ সক্ষম করে।
- একটি **Application Load Balancer (ALB)** একাধিক EC2 target জুড়ে আসা HTTP/HTTPS ট্রাফিক বিতরণ করে। এটি health check করে এবং শুধুমাত্র healthy instance-এ route করে।
- একটি **Auto Scaling Group (ASG)** সংজ্ঞায়িত scaling policy-এর উপর ভিত্তি করে স্বয়ংক্রিয়ভাবে EC2 instance-এর সংখ্যা সামঞ্জস্য করে (যেমন, target CPU utilization)।
- ALB এবং ASG একসাথে কাজ করে: ASG fleet পরিচালনা করে, ALB এটি জুড়ে ট্রাফিক বিতরণ করে।
- Stateful অ্যাপ্লিকেশনকে হয় sticky session (short-term fix) বা state externalize করতে হবে (সঠিক দীর্ঘমেয়াদী ডিজাইন)।
- HTTP ট্রাফিকের জন্য, ALB ব্যবহার করুন। Raw TCP/UDP পারফরম্যান্সের জন্য, NLB ব্যবহার করুন।

## পরীক্ষার টিপস

*SAA-C03 ডোমেন ২ — টাস্ক ২.১ (scalable architectures) / ডোমেন ৩ — টাস্ক ৩.২*

- **ASG health check EC2 বা ALB থেকে আসতে পারে।** EC2 health check শুধু instance চলছে কিনা সনাক্ত করে। ALB health check অ্যাপ্লিকেশন সঠিকভাবে সাড়া দিচ্ছে কিনা সনাক্ত করে। ALB health check আরো পুঙ্খানুপুঙ্খ এবং ওয়েব অ্যাপ্লিকেশনের জন্য পছন্দের।
- **Target tracking scaling হলো scaling policy-র সবচেয়ে সাধারণ পরীক্ষার উত্তর।** Simple scaling (alarm fire হলে N instance যোগ করুন) পুরানো এবং কম অভিযোজিত।
- **Scale-out দ্রুত; scale-in ধীর।** AWS ক্রমান্বয়ে scale-in-এর সময় instance terminate করে সক্রিয় সংযোগ ব্যাহত এড়াতে — একটি আচরণ ALB-এর **deregistration delay** সেটিং দ্বারা নিয়ন্ত্রিত।
- **Minimum instance count হলো আপনার সহনশীলতার মেঝে।** যদি আপনি minimum = 1 সেট করেন এবং সেই instance ব্যর্থ হয়, ASG সাড়া দেওয়ার আগে আপনার অ্যাপ্লিকেশন ডাউন। প্রকৃত সহনশীলতার জন্য minimum ≥ 2 এবং AZ জুড়ে ছড়িয়ে দিন।
- **ALB স্বয়ংক্রিয়ভাবে AZ জুড়ে ট্রাফিক বিতরণ করতে পারে।** Cross-zone load balancing সক্ষম থাকলে, প্রতিটি ALB node AZ নির্বিশেষে নিবন্ধিত সমস্ত target জুড়ে সমানভাবে অনুরোধ বিতরণ করে।

## অনুশীলন

**অনুশীলন ১ — স্মরণ**

আপনার নিজের ভাষায়: একটি Application Load Balancer এবং একটি Auto Scaling Group-এর মধ্যে পার্থক্য কী? প্রতিটি কোন সমস্যা সমাধান করে, এবং আপনি সাধারণত কেন একসাথে ব্যবহার করেন?

*(ইঙ্গিত: একটি ইতিমধ্যে বিদ্যমান ট্রাফিক বিতরণ করে; অন্যটি আপনার কতটুকু ক্যাপাসিটি আছে তা সামঞ্জস্য করে।)*

**অনুশীলন ২ — পরীক্ষার অনুশীলন**

*দৃশ্যকল্প*: একটি retail কোম্পানির e-commerce ওয়েবসাইটে অত্যন্ত পরিবর্তনশীল ট্রাফিক রয়েছে: সপ্তাহের দিনগুলিতে কম ট্রাফিক, সপ্তাহান্তে এবং flash sale ইভেন্টের সময় বিশাল স্পাইক। তারা চায় তাদের অ্যাপ্লিকেশন শান্ত সময়ে অব্যবহৃত ক্যাপাসিটি বজায় না রেখে পিক লোড সামলাক। অ্যাপ্লিকেশন বর্তমানে সার্ভার মেমরিতে session data সংরক্ষণ করে।

কোন আর্কিটেকচার পরিবর্তনটি তাদের scalability প্রয়োজনীয়তা সর্বোত্তমভাবে সমাধান করবে?

A) পিক ট্রাফিক সামলাতে পারে এমন একটি খুব বড় EC2 instance-এ আপগ্রেড করুন  
B) ElastiCache-এ session storage externalize করে একটি Auto Scaling Group সহ ALB-এর পেছনে একাধিক EC2 instance ডেপ্লয় করুন  
C) sticky session সক্ষম করে ALB-এর পেছনে একাধিক EC2 instance ডেপ্লয় করুন  
D) প্রতিটি প্রত্যাশিত ট্রাফিক স্পাইকের আগে ম্যানুয়ালি EC2 instance যোগ করুন এবং পরে terminate করুন

**ইঙ্গিত ১**: "অব্যবহৃত ক্যাপাসিটি বজায় না রেখে" মানে আপনার স্বয়ংক্রিয় scaling দরকার, কোনো স্থির বড় instance বা ম্যানুয়াল ব্যবস্থাপনা নয়।

**ইঙ্গিত ২**: সার্ভার মেমরিতে session storage multi-instance ডেপ্লয়মেন্টের জন্য একটি সমস্যা। কোন বিকল্পগুলি এটি সমাধান করে?

**ইঙ্গিত ৩**: বিকল্প C sticky session ব্যবহার করে — এটি একটি কাজ চালানো, fix নয়। কোন বিকল্পটি scaling এবং session storage উভয় সমস্যা সঠিকভাবে সমাধান করে?

**উত্তর**: B

**ব্যাখ্যা**: Auto Scaling Group সহ একটি ALB স্বয়ংক্রিয়, elastic scaling প্রদান করে — স্পাইকের সময় instance যোগ হয় এবং শান্ত সময়ে সরানো হয়। Session storage ElastiCache-এ (একটি বাইরের cache) সরিয়ে অ্যাপ্লিকেশনকে stateless করে: যেকোনো instance যেকোনো ব্যবহারকারীর অনুরোধ পরিচালনা করতে পারে, এবং ALB স্বাধীনভাবে ট্রাফিক বিতরণ করতে পারে। এটি আর্কিটেকচারালি সঠিক সমাধান।

**কেন A নয়?** একটি একক বড় instance, যতই বড় হোক, এখনো একটি single point of failure। এটি শান্ত সময়ে ক্যাপাসিটির বেশিরভাগ idle বসে থাকে অর্থও নষ্ট করে।

**কেন C নয়?** Sticky session একজন ব্যবহারকারীকে একই instance-এ route করে, যা session সমস্যাকে আংশিকভাবে হ্রাস করে কিন্তু load balancing-কে ক্ষতিগ্রস্ত করে। যদি সেই instance terminate হয় (scale-in বা ব্যর্থতার সময়), ব্যবহারকারী যাই হোক session হারায়।

**কেন D নয়?** ম্যানুয়াল scaling-এর জন্য কারো ট্রাফিক স্পাইক সঠিকভাবে পূর্বাভাস দিতে এবং অগ্রিম কাজ করতে হবে। এটি ধীর, ত্রুটিপ্রবণ এবং শ্রম-নিবিড়। Auto Scaling এটি স্বয়ংক্রিয়ভাবে পরিচালনা করে।

*SAA-C03 ডোমেন ২ — টাস্ক ২.১ / ডোমেন ৩ — টাস্ক ৩.২*

**অনুশীলন ৩ — আর্কিটেকচার চ্যালেঞ্জ** *(ঐচ্ছিক)*

Nimbus-এর একটি বড় প্রচার আসছে: আগামী শনিবার ৪ ঘণ্টার জন্য সমস্ত অর্ডারে ৫০% ছাড়। গত বছর, একটি অনুরূপ প্রচার স্বাভাবিক ট্রাফিকের ১০x কারণ হয়েছিল। দল আশা করছে স্পাইকটি হঠাৎ হবে এবং ঠিক ৪ ঘণ্টা স্থায়ী হবে।

Auto Scaling শেষ পর্যন্ত সাড়া দেবে, কিন্তু একটি lag আছে। আপনি এই পরিচিত স্পাইকের জন্য কীভাবে ডিজাইন করবেন? reactive এবং proactive scaling-এর মধ্যে পার্থক্য কী, এবং প্রতিটি কখন অর্থপূর্ণ?

*(একটি একক সঠিক উত্তর নেই। scheduled scaling action, pre-warming এবং প্রতিটির খরচের প্রভাব নিয়ে ভাবুন।)*
