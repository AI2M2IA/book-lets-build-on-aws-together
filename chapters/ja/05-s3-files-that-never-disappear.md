# 第5章：クラウドに住む収納キャビネット

レオは、メニュー写真が直接EC2インスタンスに保存されていることを悟った。
顧客がアップロードするすべての写真—カリカリのアルバのパン、グリルされたサーモン皿、完璧に盛り付けられたサラダボウル—が単一の仮想マシンに置かれていた。

そして、そのマシンが再起動されたり、サイズが変更されたり、置き換えられたりした場合はどうなる？

消えてしまうだろう。

「顧客がこれまでどれくらいの写真をアップロードしたか教えてください」マヤが尋ねた。

レオはコンソールを開いた。「約800個。」

「そして、サーバーを再起動した場合、その800個の写真はどうなる？」

レオの別の意味のある沈黙。

この章は、クラウドの中でファイルが実際にどこに属するかについて説明する。

**サーバーにファイルを保存することの問題点**

ファイルがEC2インスタンス—そのファイルシステム内—に直接保存されると、
その特定の機械のライフサイクルにファイルが関連付けられる。

これにより、いくつかの問題が発生する：

**本質的に一時的である。** EC2インスタンスは停止、終了、置き換えられる。
そのローカルディスクは、永続的なものではない。一時的なスクラッチスペースだ。

**単一障害点。** インスタンスが失敗した場合、ファイルも一緒に消えてしまう。
冗長性もバックアップもない。朝の悪夢が現実になったとき、800個のメニュー写真が消えてしまう。

**インスタンス間で共有できない。** 2番目のサーバー（第7章で導入する）を追加すると、
最初のサーバーのディスクに保存されたファイルは認識されない。2つのサーバーは
分離されている。写真のアップロードを行ったユーザーはそれを表示できるかもしれないが、別のサーバーでヒットしたユーザーは表示できないかもしれない。

**スケーラビリティがない。** EC2ディスクスペースは有限である。
満杯になると、アップロードを停止するか、プレッシャーの下でストレージを拡張するために
取り乱すことになる。

より良いモデルがある。AWSは2006年にそれを構築し、今でも世界で最も
広く使用されているクラウドサービスの一つだ。

**Amazon S3：オンラインで生きるハードドライブ**

**Amazon S3**—Simple Storage Service—はAWSのオブジェクトストレージサービスだ。

インターネットに存在するハードドライブを想像してください。無限のハードドライブ。
単一の可用性ゾーンに自動的にバックアップされるため、個々のデータセンターの
故障があなたのファイルを失わせないようにする。

S3の重要な概念は「オブジェクト」だ。

オブジェクトは、写真、ビデオ、PDF、CSV、バックアップ、ログファイルなど、
あらゆるファイルのことだ。S3はタイプや構造に関係なく、バイトを保存し、
必要に応じてそれを返す。

オブジェクトは「バケット」の中に存在する。バケットは、S3内の上位レベルの
フォルダ—名前が付けられたオブジェクトを保持する名前付きコンテナ—であり、
各バケットは一意の名前（すべてのAWSアカウントで共有されない）を持ち、
特定のリージョンに存在する。

**S3の仕組み**

モデルはシンプルで、そのシンプルさがポイントだ。

あなたはバケットにオブジェクトを「アップロード」する。S3はそれを一意の
名前—例えば、`menus/restaurant-001/photo-arepa.jpg`のようなパス名—を
付与する。その名前はバケット内のオブジェクトを一意に識別する。

あなたはバケット名とキーを使用してオブジェクトを「ダウンロード」（または取得）する。

あなたはオブジェクトを公開することもできる—つまり、URLを持つ誰でもダウンロードできるようにする。
これが、ほとんどのWebサイトが画像を提供する方法だ：S3に画像を保存し、URLを
埋め込み、HTMLにそれを組み込む。

または、オブジェクトをプライベートに保つ—認証されたリクエストのみにアクセス可能にする。
これは、顧客データ、バックアップ、および機密性の高いものに最適なモデルだ。

S3はファイルシステムではない。実際のフォルダは存在しない。キー名の`/`は単なる
慣習—S3はキー全体をフラットな文字列として扱う—だが、ほとんどのツールが
フォルダのように表示するため、この違いを心配する必要はない。

**S3が通常のハードドライブと異なる点**

3つの点がS3をEC2インスタンス上のファイルストレージと根本的に異なる点だ：

**耐久性。** AWSはS3の耐久性を99.999999999%（11ゼロ）に設計している。
つまり、100万個のオブジェクトを保存した場合、ハードウェアの故障により10,000年に
1回程度オブジェクトを失う可能性がある。これは、複数の可用性ゾーンにオブジェクトの
コピーを自動的に保存することで実現される。

**可用性。** S3は、個々のコンポーネントが失敗してもアクセス可能であるように設計されている。
単一のサーバーに接続するのではなく、分散システムに接続しており、障害を回避して
ルーティングしている。

**スケーラビリティ。** S3は、実質的に無限の量のデータを保持できる。
単一のバケットは、数兆ものオブジェクトを保持できる。Amazon自身がS3を使用して
理解しがたい規模でデータを保存している。

**バージョン管理：取り消しボタン**

マヤがS3コンソールを探索している間に発見したことの一つだ。

S3はバージョン管理をサポートする。バケットでバージョン管理を有効にすると、
すべてのオブジェクトのバージョン—以前のバージョンと削除されたバージョンを含む—が
保持される。

これは、ファイルの取り消しボタンだ。

メニュー写真が誤って古いバージョンを上書きした場合、古いバージョンはまだ存在する。
誤ってファイルを削除した場合、回復可能になる。ランサムウェアによってファイルが
すべてのエンコードされたゴミで上書きされた場合、バージョン管理を使用すると、
攻撃が発生する前の状態に復元できる。

「そのすべてのバージョンを維持するには、いくら費用がかかるのか？」トムが尋ねた。

あなたは、各バージョンのストレージ料金を支払います。大規模なファイルの多数のバージョンがある場合、費用がすぐに積み重なります。AWSには、特定の時間後に古いバージョンを自動的に削除する**ライフサイクルポリシー**があります—これは第23章で詳細に説明します（コスト最適化について）。

**アクセス制御：公開とプライベート**

デフォルトでは、S3内のすべてのものがプライベートです。あなたのAWSアカウントのみがアクセスできます。

個々のオブジェクトを公開することができます—これは、ウェブサイトの訪問者にメニュー画像を配信する方法です。あるいは、すべてをプライベートに保ち、**事前署名URL**を生成することもできます—これは、AWSの認証情報なしで特定のオブジェクトをダウンロードできる時間制限付きのリンクです。顧客が24時間、請求書をダウンロードできるようにするのに最適です。

プリヤは、この点について非常に強い意見を持っていました。

「公開バケットを完全に公開しない限り、そのバケット内のすべてのオブジェクトがインターネット全体にアクセスできるように明示的に決定していない限り」と彼女は言いました。「最も一般的なS3セキュリティの誤りは、機密データを含むバケットを誤って公開することです。」

AWSには、「公開アクセスをブロック」という設定があり、アカウントレベルで適用でき、明示的に上書きしない限り、すべてのバケットをプライベートに強制します。

有効にしてください。常に。

**S3ストレージクラス：すべてのデータは同じではありません**

すべてのデータが同じ頻度でアクセスされるわけではありません。

あなたの最も人気のあるメニュー写真が、毎秒数十回フェッチされます。3年前のログは、たぶん1年に1回、あるいは全くアクセスされません。S3はこれを認識し、異なる**ストレージクラス**を提供し、異なるパフォーマンスとコストのトレードオフがあります。

| ストレージクラス           | 用途                                      | 取得        | コスト                        |
|-------------------------|-----------------------------------------------|------------------|-----------------------------|
| S3 Standard             | 頻繁にアクセスされるデータ                      | 即時        | より高い1GBあたり               |
| S3 Standard-IA          | まれにアクセスされるが、高速な取得が必要な場合 | 即時        | より低い1GBあたり、取得料 |
| S3 Glacier Instant      | 稀にアクセスされるアーカイブ                   | 即時        | 非常に低い                  |
| S3 Glacier Flexible     | ほとんどアクセスされないアーカイブ              | 数分から数時間 | 非常に低い                    |
| S3 Glacier Deep Archive | ほとんどアクセスされないコンプライアンスアーカイブ | 最大12時間   | 最も低い                      |

これは第23章で詳しく説明します。現時点では：オブジェクトを年齢とアクセスパターンに基づいてストレージクラス間で自動的に移動できるという概念があり、ほとんど使用しないデータに対して大幅な節約につながります。

## 強みと限界

**S3が優れた理由**:

- 11ナインの耐久性。S3にデータを保存することは、ほとんどのシステムよりも安全です。
- 無限の拡張性。ストレージをプロビジョニングする必要はありません—それは単に成長します。
- 提供するもののために非常に安価（1GBあたり月あたり数セント）
- ほとんどすべてのAWSサービスとのネイティブ統合
- 静的ウェブサイトホスティングをサポート—S3で完全な静的ウェブサイトを直接配信でき、サーバーは必要ありません。

**S3が適切な選択肢ではない場所**:

- S3はファイルシステムではありません。アプリケーションがドライブをマウントし、ローカルディスクのように読み書きして変更する必要がある場合、S3は適切なツールではありません。EFS（第6章のElastic File System）またはEBSを使用してください。
- S3はローカルディスクよりもレイテンシが高くなります。データベースや、高速なランダムアクセスI/Oが必要なアプリケーションには、EBS（第6章のElastic Block Storage）に適しています。
- S3への大規模なデータ転送は無料です。S3からの大規模なデータ転送は費用がかかります。これは一般的な請求のサプライズ—これは第30章で対処します。

## 概要

- **Amazon S3**はオブジェクトストレージ—ファイル（オブジェクト）を名前付きコンテナ（バケット）に保存する場所です。
- S3は、少なくとも3つの可用性ゾーンにオブジェクトのコピーを保存することで、11ナインの耐久性を設計されています。
- EC2インスタンスに保存されたファイルは、そのインスタンスのライフサイクルに紐付けられています。重要なファイルはS3に保存し、サーバーに保存しないでください。
- **バージョン管理**は、オブジェクトの以前のバージョンを保存します—あなたの「アンドゥ」ボタンです。
- デフォルトでは、S3はプライベートです。アカウントレベルで「公開アクセスをブロック」を有効にします。
- S3には、異なるアクセスパターンとコストのための複数の**ストレージクラス**があります。まれなアクセスクラスは、より安価ですが、取得料が発生します。

## 試験のヒント

*SAA-C03 ドメイン3—タスク3.1（高性能ストレージソリューション）*

- **S3 はオブジェクトストレージであり、ブロックストレージではありません。** 複数のサーバーがマウントできるファイルシステムが必要なテストシナリオの場合、EFS が適しています。単一の EC2 インスタンスに必要なディスクの場合、EBS が適しています。ファイル、バックアップ、画像、HTTP を通じてアクセスされるデータなどを保存する必要がある場合、S3 が適しています。
- **11 段階の耐久性** は、S3 が複数の AZ にデータを自動的に複製することを意味します。これは設定する必要はありません。これはデフォルトです。
- **S3 はリージョナルですが、グローバルにアクセス可能です。** バケットは特定のリージョン内に存在しますが、どこからでもアクセスできます。
- **プレサインされた URL** は、プライベートオブジェクトへの時間限定アクセスを可能にします。一般的なパターンは、アプリケーションが 15 分有効なプレサインされた URL を生成し、それをユーザーに提供し、ユーザーが S3 から直接ファイルをダウンロードすることです。
- **S3 Standard-IA** は、最小ストレージ期間の課金 (30 日) を備えています。すぐに削除するデータには使用しないでください。試験では、ストレージクラス間のトレードオフを理解しているかどうかを確認します。
- **ストレージクラス決定木:** *頻繁にアクセスされる* → S3 Standard; *頻繁にはアクセスされないが高速な取得が必要な* → S3 Standard-IA; *時々アクセスされるアーカイブ* → S3 Glacier Instant Retrieval; *ほとんどアクセスされないアーカイブ* → S3 Glacier Flexible Retrieval; *コンプライアンスアーカイブ、ほとんどアクセスされない* → S3 Glacier Deep Archive。シナリオで「コスト最適化」と「不定期アクセス」という言葉が言及される場合、Standard-IA がほぼ常に答えとなります。コンプライアンスまたは「7 年の保持」という言葉が言及される場合は、Glacier Deep Archive を考えてください。

## 練習問題

**練習問題 1 — 回想**

ご自身の言葉で: S3 オブジェクトとは何ですか? S3 バケットとは何ですか? ファイルを S3 に保存することが、EC2 インスタンスのローカルディスクに保存するよりも良い理由は何ですか?

*(ヒント: EC2 インスタンスが終了すると、ファイルはどうなりますか? S3 はどのように異なりますか?)*

**練習問題 2 — 試験練習**

*シナリオ*: メディア会社はドキュメンタリービデオを制作しています。彼らはオリジナル 4K 映像 (生産中に頻繁にアクセスされる)、編集された最終カット (配布中に毎月アクセスされる)、およびコンプライアンス目的のために最大 1 年に一度アクセスされるアーカイブマスターを保存する必要があります。彼らはコストを最小限に抑えながら、各ティアのアクセス要件を満たすことを目指しています。

最もニーズに合ったストレージ戦略はどれですか?

A) 一貫性のあるパフォーマンスとシンプルさのために、すべてのコンテンツを S3 Standard に保存する
B) オリジナル映像を S3 Standard、最終カットを S3 Standard-IA、アーカイブを S3 Glacier Deep Archive に保存する
C) 最速のアクセスのために EC2 インスタンスストレージにすべてのコンテンツを保存する
D) コストを最小限に抑えるために、すべてのコンテンツを S3 Glacier Deep Archive に保存する

**ヒント 1:** 異なるファイルには異なるアクセスパターンがあります。S3 は、異なるアクセス頻度に対応するために、さまざまなストレージクラスを提供します。どのクラスが「頻繁にアクセスされる」に合致しますか?

**ヒント 2:** 1 年に一度「最大」アクセスされるアーカイブは、即時の取得を必要としません。最小コストで長期間のアーカイブを設計したストレージクラスは何ですか?

**ヒント 3:** 各ティアのアクセス頻度を適切なストレージクラスに一致させます。頻繁にアクセスされる = Standard。毎月 = Standard-IA。1 年に一度 = Glacier Deep Archive。

**答え:** B

**説明:** この戦略は、各データ層を適切な S3 ストレージクラスに正しく一致させています。頻繁にアクセスされるオリジナル映像は、即時のアクセスと取得料の発生なしで Standard に保持されます。毎月アクセスされる最終カットは、Standard-IA (より低いストレージコスト、手頃な取得料) に保持されます。1 年に一度アクセスされるアーカイブは、最低限のコストで Glacier Deep Archive に保持されます。

**A が正しくない理由:** すべてを Standard に保存することは簡単ですが、高価です。ほとんどアクセスされないアーカイブコンテンツに対してプレミアム価格を支払っています。

**C が正しくない理由:** EC2 インスタンスストレージは不揮発性であり、長期間のメディアストレージには適していません。インスタンスが終了すると、すべてのコンテンツが失われます。

**D が正しくない理由:** Glacier Deep Archive の取得時間は最大 12 時間です。頻繁にアクセスされる生産映像をそこに保持すると、生産作業は不可能になります。

*SAA-C03 ドメイン 3 - タスク 3.1 / ドメイン 4 - タスク 4.1*

**練習問題 3 — アーキテクチャチャレンジ** *(オプション)*

Nimbus は、顧客がアップロードした注文写真の写真を S3 に保存しています。データ保護規制により、顧客の写真は 7 年間保存する必要があり、その後削除できます。チームは、古い写真の保管コストを最小限に抑えることも望んでいます。

この要件を満たすための S3 ストレージ戦略を設計してください。どのストレージクラスを使用し、どのタイミングでクラス間で移行しますか? 削除要件をどのように処理しますか?

*(ヒント: ライフサイクルポリシーについて考えてください。正解の答えは 1 つではありません。コストと取得時間トレードオフについて考え抜いてください。)*

## クロスオーバーシーン

レオは午後にメニューの写真を S3 に移行しました。800 個のオブジェクトが、3 つの可用性ゾーンに安全に保存され、バージョン管理が有効になっていました。

「彼らは実際に以前よりも安全になった」と彼は満足そうに言いました。

「彼らは常に S3 で安全だった」とプリヤは言いました。「私たちは問題を構築した後で待つだけでした。」

レオはそれを認めました。

翌朝、トムがプリントアウトを持って到着しました。赤いペンで書き込まれたAWS請求書です。

「データベースの問題が発生しています」と彼は言いました。「注文データベース、メニューデータベース、顧客記録をすべて同じEC2インスタンスで実行しています。」

彼は一呼吸ついた。

「すべてが1台の機械の中にあります。1台の機械。すべてのデータです。」

マヤはプリントアウトを見つめました。そしてトムを見て、天井を見つめました。

「もしその機械が故障したら？」

トムは赤いペンで書き込まれた箇所を指さしました。

次の章では：レンタルするハードドライブと、オフィス全体で共有されている保管キャビネットの違いについて解説します。
