# 第7章：混雑すると伸びるレストラン

金曜日の夕方7時43分、エラー率が12%を超えました。

トムが最初に気づいたのは、トムがいつも最初に気づくからでした。彼はクラウドウォッチのダッシュボードを、他の人がソーシャルメディアをチェックするやり方と同じように、反射的に、絶えず、完全に意識せずにリフレッシュしていました。

「レオ」とトムは言いました。

レオはすでに見ていました。応答時間：増加中。キューに並んでいるリクエスト：増加中。単一のEC2インスタンス—つい先月より大きなものにアップグレードしたインスタンス—は94%のCPUを使用していました。

「顧客を退けさせています」とトムは言いました。

「顧客を退けさせていません」とレオは言いました。「サーバーがそうしています」

「それは同じことです」

そうでした。そして、それは3週間毎週起こっていました。ニームスはストレージ危機を乗り切りました—データベースは独自のディスクを持ち、写真はS3に住んでいました—しかし、安定性とスケーラビリティは全く異なる問題です。システムは機能していました。ただ、成長しませんでした。

チームは、システムが変動する負荷を自動的に処理できるようにする必要があります。最悪の場合に必要なサーバーを過剰に購入したり、静かな時間帯に無駄にしたりするのではなく、トラフィックが急増したときに手動で対応したりする必要はありません。

このためのパターンがあります。AWSには、この機能を実装する2つのサービスがあります。

**コンセプト：水平スケーリング**

システムがより多くの負荷を処理する方法は2つあります。

**垂直スケーリング**とは、単一のサーバーを大きくすることです。より多くのCPU。より多くのRAM。
当社は、第4章でt3.microからt3.largeにアップグレードした際にこれを行いました。これは役立ちます。
しかし、限界があります：サーバーは最大までしか大きくできません、インスタンスはサイズ変更のために再起動する必要があります、そして、単一障害点があります。

**水平スケーリング**とは、サーバーを増やすことです。1つの大きなサーバーの代わりに、5つの中くらいのサーバーを実行します。トラフィックが低下したら、2つ実行します。トラフィックが急増したら、10つ実行します。

水平スケーリングには、垂直スケーリングにはない利点があります。

- 単一障害点はありません。サーバーが死亡しても、他のサーバーが引き続きサービスを提供します。
- 容量を追加するために再起動は必要ありません。
- 使用しているものに対してのみ支払う—必要なときにサーバーを追加し、不要になったときに削除します。
- 線形スケーリング：サーバーの数を2倍にすると、おおよそトラフィックの処理能力も2倍になります。

ただし、複数のサーバーがある場合、ユーザーはどのサーバーに接続するかを知るにはどうすればよいでしょうか？

**アプリケーションロードバランサー：多くの部屋がある1つのドア**

**アプリケーションロードバランサー（ALB）**は、アプリケーションのフロントドアです。

ユーザーはロードバランサーに接続します。ロードバランサーは、EC2インスタンスのフリートに到着するリクエストを分散します。各ユーザーは1つのアドレス（ロードバランサーのURL）を見ます。そのアドレスの背後には、実行されているサーバーの数だけリクエストが分散されます。

それは、ホストスタンドがある大きなレストランを想像してください。顧客が到着し、ホストは利用可能なテーブルに顧客を案内します。ホストはどのテーブルが混雑しているか、どのテーブルが開いているかを知っています。顧客はテーブルの数を知る必要はありません—ただ入って、ホストが分散を処理します。

ALBは、Webリクエストに対してこれを行います。受信したすべてのHTTPリクエストを判断し、ラウンドロビン、最小の未処理リクエスト、健康状態に基づいて、どのEC2インスタンス（ターゲット）を処理するかを決定します。

**健康チェック**は不可欠です。ALBは定期的にターゲットにテストリクエストを送信します。ターゲットが正しく応答しない場合、ALBはターゲットを無効にし、トラフィックを送信しなくなります。ターゲットが回復すると、トラフィックが再開されます。

これは自動です。健康チェックのパラメータを設定するだけです。ALBはそれらを強制します。

**オートスケーリング：テーブルがより多く開くレストラン**

ALBはトラフィックを既存のサーバーに分散します。しかし、必要なときにサーバーを追加しません。

**オートスケーリング**はします。

**オートスケーリンググループ（ASG）**は、AWSに指示する構成です。

- 常に実行する必要がある最小インスタンス数
- 許可されている最大インスタンス数
- スケールアウト（インスタンスの追加）またはスケールイン（インスタンスの削除）を行う条件

これらの条件は**ポリシー**と呼ばれます。最も一般的なタイプは：

**ターゲットトラッキング**: 「平均CPU使用率を70%に保つ」です。平均CPUが70%を超えると、AWSは新しいインスタンスを起動します。CPUが低下すると、インスタンスが終了します。

これは自動です。誰かがメトリクスを監視する必要はありません。誰かが手動でサーバーを起動する必要はありません。システムはリアルタイムで負荷に反応します。

プリヤは、金曜日のピーク時にサーバー数が2から5に増加し、その後ピークが過ぎると2に戻るのを見ていました。

「それ」と彼女は言いました。「本当に印象的です」

トムはコストグラフを調べていました。ピーク時には請求額が増加し、その後減少しました。「必要なものだけを支払った」と彼は同じように感銘を受けて言いました。

**ALBとASGの連携**

2つのサービスは連携して使用するように設計されています。

AWSの初心者向け書籍のMarkdownを、自然で流暢な日本語に翻訳します。

- Markdown構文を保持します。見出しレベル、リスト、テーブル、リンク、インラインコード、 fenced code blocks、URL、およびAWSサービス名を維持します。
- 内容を省略、要約、創作、または追加しません。
- キャラクター名をソフィア、レオ、マヤ、トム、プリヤ、カルロスのように自然な形で翻訳します。NimbusはNimbusのままです。

ALBを最前線に配置します。ALBは、トラフィックを受け取るインスタンスのコレクションである**ターゲットグループ**に接続します。Auto Scaling Groupは、それらのインスタンスを管理します。スケールアウト時にインスタンスを追加し、スケールイン時に削除します。

流れ：

1.  ALBにトラフィックが到着します。
2.  ALBは、健全なターゲットにリクエストを分散します。
3.  それらのターゲットでCPU/負荷が上昇します。
4.  ASGは負荷の上昇を検出し、新しいインスタンスを起動します。
5.  新しいインスタンスは健康チェックをパスし、ALBに登録されます。
6.  ALBはそれらにトラフィックを送信し始めます。
7.  負荷が低下し、ASGは余分なインスタンスを停止します。
8.  ALBは停止したインスタンスにトラフィックを送信しなくなります。

これは人間の介入なしに自動的に発生します。

**Launch Templates: 新しいインスタンスの設計図**

ASGが新しいインスタンスを起動するとき、何を起動するかを知る必要があります。これは**Launch Template**で定義されます。これは、AMI、インスタンスタイプ、適用するセキュリティグループ、およびインスタンスの起動時に実行されるユーザーデータ（スクリプト）です。

一般的なパターン：アプリケーションをカスタムAMIに構築します（第4章を参照）。ASGが新しいインスタンスを必要とするとき、そのAMIを起動します。新しいインスタンスは、アプリケーションがすでにインストールされた状態で起動します。手動設定は必要ありません。

より動的な環境では、起動時に最新バージョンのコードをプルしてインストールする**ユーザーデータスクリプト**を使用することもできます。これはより柔軟ですが、起動に時間がかかります。

インスタンスが起動するために必要な時間とアプリケーションが変更される頻度によって、適切な選択肢が決まります。

**Sticky Sessions: わずかな問題**

ロードバランシングを初めて実装するチームにとって、多くの問題を引き起こすものがあります。

一部のWebアプリケーションは、サーバー自体（メモリまたはローカルディスク）でセッションデータを保存します。これは1つのサーバーでは問題ありません。複数のサーバーでは壊れます。

ユーザーがログインします。リクエストはサーバーAに送信されます。サーバーAはセッションを保存します。次のリクエストはサーバーBに送信されます。サーバーBにはセッションがありません。ユーザーはログアウトしたように見えます。

これは2つの方法で対処できます。

**Sticky sessions**（またはセッションアフィニティ）：ALBを同じユーザーに対して同じサーバーに常にリクエストを送信するように構成します。これは一時的な修正であり、ロードバランシングを損ない（一部のサーバーは他のサーバーよりも「Sticky」なユーザーをより多く受け取る）、インスタンスが停止された場合に問題が発生する可能性があります。

**Statelessアプリケーション設計**: セッションデータを外部に保存します。データベースまたはElastiCache（第10章）のようなキャッシュです。各サーバーは、外部ストアからユーザーのセッションを再構築できます。サーバーは互換性があります。これは、水平方向にスケーラブルなアプリケーションに適したアプローチです。

プリヤはこれを「マルチサーバーに移行するときにあなたが作成する最も重要なアーキテクチャ上の決定」と呼びました。彼女は正しいです。これは第10章で再び遭遇します。

**ロードバランサーのタイプ**

AWSは、さまざまなトラフィックに適した3種類のロードバランサーを提供します。

**Application Load Balancer (ALB)**: HTTPおよびHTTPSトラフィック。レイヤー7（HTTPを理解します）。URLパス（`/api`を1つのグループに、`/static`を別のグループに）、ホストヘッダー、クエリパラメータに基づいてルーティングできます。これは、ほとんどのWebアプリケーションで使用されます。

**Network Load Balancer (NLB)**: TCP、UDP、およびTLSトラフィック。レイヤー4（HTTPを理解しません）。数百万の要求/秒という極めて高いパフォーマンス、非常に低いレイテンシ。HTTPを扱わない場合、または生の速度が必要な場合に使用します。

**Gateway Load Balancer (GWLB)**: サードパーティの仮想ネットワークデバイス（ファイアウォール、侵入検知）へのトラフィックをルーティングします。ジュニアレベルではほとんど必要ありません。

Nimbus（およびほとんどのWebアプリケーション）には、ALBが適切な選択肢です。

## 強みと限界

**ALB + Auto Scalingの強力さ**

-   ゼロダウンタイムのスケール（既存の接続を中断することなくインスタンスを追加/削除）
-   自動フェールオーバー（不健全なインスタンスが自動的にトラフィックから削除されます）
-   コスト効率（実行中のインスタンスのみを支払う）
-   単一障害点がない—複数のインスタンスが複数のAZに分散されます

**複雑になる場所**

-   ステートフルアプリケーションには特別な処理が必要です（Sticky sessionsまたは外部状態）
-   スケールアウトには時間がかかります—トラフィックが瞬時に急増する場合、新しいインスタンスが準備完了するまでに遅延が発生します。スケジュールされたスケーリング（既知のイベントの前にスケーリング）またはより大きな最小インスタンス数を備えることで軽減できます。
-   より多くの移動部品があるため、監視とデバッグがより複雑になります。
-   データベースや、特定のレガシーシステムなど、水平方向に簡単にスケーリングできないアプリケーションもあります。水平スケーリングは、ステートレスの層に最適です。

## 概要

- **水平スケーリング**（より多くのサーバーの追加）は、
  **垂直スケーリング**（1つのサーバーを大きくすること）よりも好ましいです。
  これは単一障害点を取り除き、柔軟なコストを可能にします。
- **アプリケーションロードバランサー (ALB)** は、
  複数の EC2 ターゲットに HTTP/HTTPS トラフィックを分散します。
  ヘルスチェックを実行し、健全なインスタンスのみにルーティングします。
- **オートスケーリンググループ (ASG)** は、
  定義されたスケーリングポリシーに基づいて、EC2 インスタンスの数を自動的に調整します（例：ターゲット CPU 使用率）。
- ALB と ASG は連携して動作します：ASG はフリートを管理し、ALB はそれをトラフィックに分散します。
- ステートフルなアプリケーションは、
  スティッキーセッション（一時的な修正）を使用するか、
  状態を外部化（正しい長期設計）する必要があります。
- HTTP トラフィックの場合は、ALB を使用します。
  生の TCP/UDP パフォーマンスの場合は、NLB を使用します。

## 試験のヒント

*SAA-C03 ドメイン 2 - タスク 2.1 (スケーラブルなアーキテクチャ) / ドメイン 3 - タスク 3.2*

- **ASG のヘルスチェックは、EC2 または ALB から来る可能性があります。**
  EC2 ヘルスチェックは、インスタンスが実行されているかどうかのみを検出します。
  ALB ヘルスチェックは、アプリケーションが正しく応答しているかどうかを検出します。
  ALB ヘルスチェックはより詳細で、ウェブアプリケーションには好ましいです。
- **ターゲット追跡スケーリングは、最も一般的な試験の回答です。**
  単純なスケーリング（アラームが発火したら N 個のインスタンスを追加）は古いものであり、適応性が低いです。
- **スケーリングアウトは高速で、スケーリングインは遅いです。**
  AWS は、スケーリングイン中にインスタンスを段階的に終了して、アクティブな接続を中断しないようにします—これは ALB の **登録解除遅延** 設定によって制御されます。
- **最小インスタンス数は、あなたのレジリエンスの床です。**
  最小値を 1 に設定し、そのインスタンスが失敗した場合、ASG が反応する前にアプリケーションがダウンします。
  最小値を ≥ 2 に設定し、AZ に分散して、実際のレジリエンスを実現します。
- **ALB は、AZ 間でトラフィックを自動的に分散できます。**
  クロスゾーンロードバランシングを有効にすると、各 ALB ノードは登録されているすべてのターゲットにリクエストを均等に分散します。これは、AZ インスタンスの数が異なる場合に、バランスの取れた負荷を確保するのに役立ちます。

A) ピークトラフィックを処理できる、非常に大きな単一 EC2 インスタンスにアップグレードする
B) ALB とオートスケーリンググループの背後に複数の EC2 インスタンスを展開し、ElastiCache でセッションストレージを外部化する
C) ALB の背後に複数の EC2 インスタンスを展開し、スティッキーセッションを有効にする
D) 予想されるトラフィックの各スパイクの前に EC2 インスタンスを手動で追加し、スパイク後にそれらを終了する
D)

*(ヒント 1: “未使用の容量を維持しない” ということは、固定サイズの大きなインスタンスや手動管理ではなく、自動スケーリングが必要です。)*

*(ヒント 2: セッションストレージがサーバーメモリにあることは、マルチインスタンス展開における問題です。どのオプションがこの問題を解決しますか？)*

*(ヒント 3: オプション C はスティッキーセッションを使用しています—これは修正ではなく、単なる回避策です。どちらのオプションが、スケーリングとセッションストレージの問題を適切に解決しますか？)*

**回答**: B

**説明**: ALB とオートスケーリンググループは、自動、弾性スケーリングを提供します—インスタンスはスパイク中に追加され、平穏期間中に削除されます。セッションストレージを ElastiCache（外部キャッシュ）に移動することで、アプリケーションはステートレスになります：任意のインスタンスが任意のユーザーの要求を処理し、ALB はトラフィックを自由に分散できます。これは、アーキテクチャ的に正しいソリューションです。

**A なぜダメ？** 非常に大きな単一インスタンスは、どんなに大きくても単一障害点です。また、平穏期間中にほとんどの容量がアイドル状態になるため、お金を無駄にします。

**C なぜダメ？** スティッキーセッションはユーザーを同じインスタンスにルーティングしますが、部分的にセッションの問題を軽減するだけで、ロードバランシングを損ないます。そのインスタンスが終了（スケーリングインまたは障害中に）すると、ユーザーはセッションを失うため、セッションは再び失われます。

**D なぜダメ？** 手動スケーリングは、トラフィックスパイクを正しく予測し、事前に行動する必要があるため、遅く、エラーがかかり、労力もかかります。オートスケーリングはこれを自動的に処理します。
