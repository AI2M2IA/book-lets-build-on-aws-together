# 第10章：データベースが遅すぎるとき

画面にはページロードのメトリクスが開かれていました。レオは20分間、何も言わずにそれを見つめていました。

ページロードあたり47回のDynamoDBリクエスト。データを取得するだけで188ミリ秒、ブラウザが1ピクセルもレンダリングする前にです。

彼は計算していました。金曜の夕方に1万人の同時ユーザーがいて、それぞれが約1分に1回閲覧ページを読み込むと、1分あたり47万回のDynamoDB読み取りです。コストは現実でした。しかし、実際の問題はレイテンシでした。Nimbusの閲覧ページを開いたユーザーは、何かが表示されるまでにほぼ200ミリ秒待っていました。しかもそれは高速な接続でのことでした。

*前の週、DynamoDBのスキーマ再設計はうまくいっていました。メニューテーブルは今や柔軟でした。どのレストランも、どんなモディファイア、どんなコンボ構造、どんな季節限定バリエーションでも追加できました。個々のルックアップのパフォーマンスは優秀でした。しかし、優秀な個々のルックアップも、1ページあたり47倍されれば、それでも遅いページに積み上がりました。DynamoDBの問題は解決されました。新しい問題がその場所を占めていました。*

**間違った最初の試み**

レオの最初の本能は、ユーザーごとのデータをキャッシュすることでした。各ユーザーにはセッションがあり、セッションはプロファイル（保存された住所、支払い方法、注文履歴のサマリー）を読み込みました。たぶんそれをキャッシュすれば速くなるだろう、と。

彼はそれを実装しました。Redisのキー形式：`user:{userId}:profile`。TTL：10分。

彼は負荷テストを実行しました。ページロードは6ミリ秒下がりました。

「それは大したことないな」とトムは観察しました。

「ええ」とレオは言いました。

「なぜ？」

レオはしばらくグラフを見つめました。「ユーザープロファイルはたった1回のリクエストだからです。ページあたりまだ46回のDynamoDB呼び出しがあります。そしてそれらはメニューの呼び出しです。閲覧ページのレストランごとに1回。間違ったものをキャッシュしてしまいました。」

これはキャッシングでよくある間違いです。ボトルネックではないものを最適化することです。ユーザープロファイルは2ミリ秒で読み込まれました。それほど速いものをキャッシュしても、ほとんど何も節約できません。メニューデータ（47回取得され、それぞれ4ミリ秒かかる）が実際の問題でした。

「ユーザーごとではなく、メニューごとにキャッシュする必要があります」とプリヤは言いました。「レストラン047のメニューは、それを閲覧するすべてのユーザーにとって同じです。それがキャッシュする価値のあるデータです。何千ものリクエストにわたって同一なのです。」

ユーザーごとのキャッシュは、ユーザーが高価なパーソナライズされた状態を持つときに価値があります。エンティティごとのキャッシュ（メニュー、製品カタログ、設定）は、同じデータが何千ものユーザーに提供されるときに価値があります。コードを書く前に、自分がどちらの問題を抱えているかを知っておきましょう。

レオはキャッシュキーを再設計しました：`menu:{restaurantId}`。レストランごとに1つのキャッシュエントリで、そのレストランを閲覧するすべてのユーザーが共有します。

彼は再び負荷テストを実行しました。ページロードは188ミリ秒から12ミリ秒に下がりました。それが彼らが探していた改善でした。

**レストランのたとえ話**

レストランの厨房を想像してください。ウェイターが今日のスペシャルを知る必要があるたびに、彼らは奥に歩いていき、シェフに尋ね、テーブルに歩いて戻ります。

ウェイターが2人、テーブルが3つなら、それでうまくいきます。

では、ウェイターが200人、テーブルが1000個だと想像してください。全員が同じ質問のために奥に歩いていきます。厨房がボトルネックになります。シェフは1時間に400回も同じ質問に答えています。

明らかな解決策：スペシャルをレストランの前の掲示板に書きます。すべてのウェイターは掲示板から読みます。厨房は一息つけます。掲示板はスペシャルが変わったときに更新されます。

その掲示板がキャッシュです。

キャッシュは、最近取得したデータの高速でローカルなストアです。同じものを遅いソースから繰り返し取得する代わりに、一度取得して手元に置いておきます。

エンジニアが有用だと感じるもう1つのたとえ話があります。図書館の予約棚です。人気の本が返却されると、司書はすぐにまたリクエストされると分かっているので、書庫に戻す代わりに、受付近くの予約棚に置きます。次の利用者は図書館全体を歩く必要がありません。受付ですぐに見つかります。予約棚のスペースには限りがあります。いっぱいになると、古い本は新しい本のためにスペースを空けるべく書庫に戻されます。キャッシュも同じように機能します。頻繁にアクセスされるデータは前の方に残り、めったにアクセスされないデータは場所を空けるために退避されます。

**なぜメモリを使うだけではダメなのか？**

「メニューをアプリケーションのメモリに保存することはできないのか？」とレオは尋ねました。

もっともな質問です。

できます。単一サーバーのアプリケーションなら、インメモリキャッシュはうまくいきます。しかし、Nimbusはロードバランサーの背後で、複数のEC2インスタンスにまたがって動作しています。1つのインスタンスがメニューをそのメモリにキャッシュしても、他のインスタンスはそのデータを持っていません。それぞれが別々のキャッシュを維持します。メニューが更新されると、それらすべてを無効化しなければなりません。

これが*キャッシュコヒーレンス問題*です。複数のキャッシュの整合性を保つことです。

ElastiCacheは、すべてのインスタンスが共有する*集中型*キャッシュを提供することで、これを解決します。各サーバーが独自のメモリを持つのではなく、すべてのサーバーが同じキャッシュから読み取り、同じキャッシュに書き込みます。1つの更新がすべてに伝播します。

**ElastiCacheの登場**

「待って、でも*なぜ*そのようにするの？」とマヤは尋ねました。「なぜまったく新しいサービスを？データベースのキャパシティをもっと追加すればいいのでは？」

良い質問です。答えは、データベースのキャパシティを追加しても（より大きなインスタンス、より多くの読み取りレプリカ）、根本的な問題は解決しないということです。それら47回のページロードリクエストはそれぞれ、より速いデータベース上でも依然として時間とお金がかかります。キャッシュはデータベースを速くするのではありません。データベースが同じ質問をされる回数がはるかに少なくなるということです。繰り返し読み取られ、めったに変わらないデータ（レストランのメニューのような）の場合、キャッシュは、データベースがその質問にページロードあたり47回ではなく、5分に1回答えればよいということを意味します。

Amazon ElastiCacheはマネージドキャッシュサービスです。人気のキャッシュエンジン、RedisとMemcachedを、あなたがサーバーを管理する必要なしに実行します。

**Redis**は2つのうちより強力なものです。複雑なデータ構造（文字列、リスト、セット、ハッシュ、ソート済みセット）、永続化（データが再起動を生き延びる）、レプリケーション、パブリッシュ/サブスクライブメッセージングをサポートします。Redisはキャッシュ以上のことができます。軽量なデータストアとして機能できます。

**Memcached**はよりシンプルです。純粋なキーバリューキャッシュ、水平にスケーラブル、永続化なし。シンプルなユースケースには高速ですが、機能は少なくなります。

Nimbusの場合：Redisです。彼らはメニューデータ（構造化）、セッショントークン（キーバリュー）をキャッシュする必要があり、後には「トレンドレストラン」ランキングのためにソート済みセットが欲しくなりました。

**実際にキャッシングはどう機能するか**

基本的なキャッシングパターンは**キャッシュアサイド**（遅延読み込みとも呼ばれる）と呼ばれます。

1. アプリケーションがデータを必要とする
2. まずキャッシュを確認する
3. 見つかった場合（*キャッシュヒット*）：すぐにデータを返す
4. 見つからない場合（*キャッシュミス*）：データベースに行き、データを取得し、キャッシュに保存し、それを返す

疑似コードでは：

```
menuData = cache.get("menu:restaurant-047")
if menuData is null:
    menuData = dynamodb.query(TableName="menu", KeyConditionExpression="restaurantId = '047'")
    cache.set("menu:restaurant-047", menuData, ttl=300)  # Cache for 5 minutes
return menuData
```

最初のリクエストは常にデータベースにヒットします。それ以降のすべてのリクエストはキャッシュにヒットします。キャッシュがあれば、Nimbusのページロードあたり47回のDynamoDB読み取りは、1〜2回のキャッシュルックアップになります。速く、安く、スケーラブルです。

**TTL：どれくらい覚えておくか？**

すべてのキャッシュエントリには**有効期限（Time-To-Live、TTL）**があります。エントリが期限切れになり、次のリクエストが新鮮なデータのためにデータベースに戻るまでの期間です。

これがキャッシングの核心的な緊張です。鮮度対パフォーマンスです。

- **短いTTL（数秒）**：非常に新鮮なデータですが、多くのキャッシュミスが発生します。キャッシュはほとんど役立ちません。
- **長いTTL（数時間または数日）**：非常に高速ですが、データが古くなる可能性があります。顧客は昨日のメニューを見ます。

メニューデータの場合、5分は妥当です。メニューは毎秒変わるわけではありません。レストランがメニューを更新した場合、顧客は最大5分間、古いバージョンを見るかもしれません。許容範囲です。

セッショントークン（このユーザーはログインしているか？）の場合、より短いTTLが理にかなっています。あるいは、セッションが変わったらすぐにキャッシュを更新します。

財務データ（注文合計、支払い記録）の場合、キャッシュしないでください。あるいはキャッシュするなら、書き込み時にすぐに無効化してください。

こう思っているかもしれません。まったく新しいキャッシュレイヤーを導入する代わりに、データベースのキャパシティをもっと追加すればいいのでは？レプリカを増やす、より大きなインスタンス、なぜそれではダメなのか？答えは、追加のデータベースキャパシティは同時リクエストを処理する能力を倍増させますが、リクエストの数を減らさないということです。1万人のユーザーがそれぞれページロードあたり47回の読み取りをトリガーしている場合、2つ目の読み取りレプリカを追加しても、各レプリカが4万7000回ではなく2万3000回のリクエストを処理するというだけで、総作業量は縮みません。キャッシュは冗長な作業を完全に排除します。それら1万人のユーザーは同じキャッシュされた結果を共有します。

「コンピュータサイエンスには難しい問題が2つしかない」とレオは、以前に言ったことがある人の慣れた語り口で引用しました。「キャッシュの無効化と、命名だ。」

「なぜキャッシュの無効化は難しいの？」とマヤは尋ねました。

「データは*実際に*いつ変わるのか？メニューはレストランパートナーが更新したから変わったのか？それともcronジョブが実行されたから？それとも管理者が手動で編集したから？データを変更できるすべての場所が、キャッシュに伝えることを知っている必要がある。」

これが、シニアエンジニアがキャッシングの会話を「Redisを追加しよう」ではなく「書き込みパスは何か？」で始める理由です。

**キャッシュ無効化の物語**

彼らは、レストランパートナーが最初に苦情を言ったとき、キャッシュの無効化がどれほど難しいかを知りました。

レストラン112（イーストサイドのコロンビア料理店）は、木曜の午後に価格を更新していました。アレパを8ドルから9ドルに上げていました。彼らは20分後にNimbusサポートに電話しました。

「うちのメニューはまだ古い価格を表示している」とオーナーは言いました。「お客さんが8ドルで注文している。今その価格を守らなければならない。」

プリヤがバグをたどる間、トムは損失を計算しました。その20分間に出されたすべての注文が8ドルを課金していました。レストランは9ドルを望んでいました。Nimbusがその差額を負担することになります。

5分のTTLはとっくに期限切れになっているはずでした。20分が経過していました。プリヤはコードを引き出しました。

キャッシュキーは`menu:restaurant-112`でした。300秒のTTLで設定されていました。彼女は最後に書き込まれた時刻を確認しました。

「午後2時3分に設定されている」と彼女は言いました。「22分前。」

「でもTTLは5分だ」とレオは言いました。

「TTLは最初にキャッシュされてから5分です。でも、キャッシュにヒットしたすべてのリクエストがTTLを更新していました。キャッシュエントリは入ってくるリクエストによって数秒ごとに触れられていて、TTLがリセットされていました。」

「だから期限切れにならなかった。」

「この実装ではならなかった。私たちはキャッシュの読み取りごとにTTLを設定していました。スライディングウィンドウです。誰かがヒットし続けている限り、エントリは生き続けました。」

修正：書き込み時にのみ設定され、読み取りでは決して延長されない固定TTLを使うことです。エントリは、何回読み取られても、保存されてからきっかり5分後に期限切れになります。レストランがメニューを更新すると、古いエントリは5分以内に期限切れになり、次のリクエストが新鮮なデータを取得しました。

「レストランが価格を更新して、すぐに反映する必要がある場合は？」とトムは尋ねました。

「アクティブな無効化です」とプリヤは言いました。「レストランパートナーポータルが更新を送信したとき、APIは返す前に`cache.delete('menu:restaurant-112')`を呼び出します。次のリクエストはすぐに新鮮なデータを取得します。」

「でもそれは、ポータルがキャッシュについて知っている必要がある。」

「データベースへのすべての書き込みパスがキャッシュについて知る必要があります。それがレオがさっき言ったことです。今、私たちはそれを身をもって経験しました。」

「もうデプロイしたんだ—あ。」レオはポータルに無効化を実装していましたが、管理者編集インターフェースを忘れていました。2週間後、管理者が内部ダッシュボードを通じてメニューを更新し、古い価格が5分間キャッシュに残りました。同じ事件の小さい版です。

彼らはDynamoDB Streamsのハンドラー（前章のもの）を追加しました。これは、どのシステムが書き込みをトリガーしたかに関係なく、メニュー項目が変更されるたびに自動的にキャッシュを無効化しました。1つのハンドラーで、すべての書き込みパスがカバーされました。

**キャッシュの退避：掲示板がいっぱいになるとき**

スペシャル掲示板のスペースには限りがあります。いっぱいになると、場所を空けるために何かを消さなければなりません。

Redis（および一般的なキャッシュ）には、メモリがいっぱいになったときに何が削除されるかを決める*退避ポリシー*があります。

- **LRU（Least Recently Used、最も最近使われていないもの）**：最も長くアクセスされていない項目を削除します。
- **LFU（Least Frequently Used、最も使用頻度が低いもの）**：最もアクセス頻度の低い項目を削除します。
- **allkeys-random**：ランダムな退避。シンプルですが最適ではありません。
- **noeviction**：メモリがいっぱいになるとエラーを返します（アプリケーションがこれを処理する必要があります）。

ほとんどのWebアプリケーションでは：LRUです。最近見ていないものは、おそらくあまり必要とされていません。

**キャッシュスタンピード問題**

「キャッシュ全体が一度に空になったらどうなるか、考えたことはありますか？」とプリヤは尋ねました。

「それはいつ起きるんだ？」とレオは言いました。

「新しいElastiCacheクラスターをデプロイするとき。大量のエントリのTTLが同時に期限切れになるとき。バグ修正後に強制的にリフレッシュするためにキャッシュをフラッシュするとき。」

レオはそれを考え抜きました。「キャッシュが空なら、すべてのリクエストがデータベースに行く。一度に全部。数秒間、データベースがすべての同時ユーザーのフル負荷を処理する。」

「前にキャッシュがない状態で。」

「それは痛いな。」レオはデータベースのキャパシティ設定を見ました。「確実にスロットリングされる。」

これは**キャッシュスタンピード**（サンダリングハードとも呼ばれる）と呼ばれます。多くのキャッシュエントリが同時に期限切れになるときに起こります。多くの場合、それらがデプロイやコールドスタート時にすべて同時に作成されたためです。そして突然のキャッシュミスの波がすべて同時にデータベースにヒットします。

緩和策：

**TTLへのジッター**：すべてのメニューエントリをきっかり300秒に設定する代わりに、ランダムなばらつきを加えます：270秒から330秒。エントリはわずかに異なる時刻に期限切れになり、キャッシュミスの波が同時にヒットする代わりに1分間にわたって分散されます。

**確率的早期期限切れ**：エントリが期限切れになる前に、リクエストの小さな割合が積極的にそれをリフレッシュします。これにより、エントリが古くなる前に新鮮に保たれ、期限切れがミスになることを防ぎます。

**リクエストの合体（mutex/ロック）**：キャッシュミスが発生したとき、データベースにヒットする前にロックを取得します。同じキーに対する他の同時リクエストは、最初のリクエストが完了してキャッシュを再投入するのを待ち、それからキャッシュから読み取ります。高い同時実行性の下でも、キャッシュミスごとに1つのデータベースリクエストしか行われません。

Nimbusの場合、彼らはTTLジッターを実装しました。シンプルで、効果的で、追加の複雑さなしです。

```python
import random
TTL_BASE = 300
TTL_JITTER = 30
ttl = TTL_BASE + random.randint(-TTL_JITTER, TTL_JITTER)
cache.set(key, value, ttl=ttl)
```

「2行のコードだ」とレオは言いました。「デプロイ中の潜在的なデータベース障害を防ぐためにね。」

「ほとんどの信頼性の改善はそういうものです」とプリヤは言いました。「実装は安く、必要だったと知るのは高くつく。」

**Redisのデータ構造：キーバリュー以上のもの**

Nimbusが「トレンドレストラン」機能を追加したとき、レオは最初、ランキングをプレーンなJSONリストとして保存しました：`trending:global → ["NIMBUS-047", "NIMBUS-112", ...]`。

それは機能しましたが、更新が面倒でした。新しいレストランを追加したりスコアを更新したりするには、リスト全体を読み、アプリケーションコードでそれを変更し、全体を書き戻す必要がありました。分析パイプラインからの同時書き込みの下で、競合状態がスコアを上書きさせました。

プリヤは彼にRedisのソート済みセットを示しました。

Redisの**ソート済みセット**は、関連する数値スコアとともにメンバーを保存します。メンバーはスコアによって自動的にソートされます。操作はアトミックです。同時更新からの競合状態はありません。

```
# レストランのスコアを追加/更新
ZADD trending:global 9420 "NIMBUS-047"
ZADD trending:global 8831 "NIMBUS-112"

# スコア順の上位10レストランを取得（高い順）
ZREVRANGE trending:global 0 9 WITHSCORES

# レストランのスコアをアトミックにインクリメント
ZINCRBY trending:global 50 "NIMBUS-047"
```

分析Lambdaは注文が出されるたびに`ZINCRBY`を呼び出し、レストランのスコアをインクリメントしました。ホームページは`ZREVRANGE`を呼び出して上位10件を取得しました。ロックなし、競合状態なし、読み取り・変更・書き込みのサイクルなしです。

Redisは、単純なキーバリューを超えるいくつかの他のデータ構造もサポートしています。

**リスト**：順序付きのシーケンス。前または後ろにプッシュします。キュー、最近のアクティビティフィード、ログストリームに使います。

**セット**：重複のない順序なしのコレクション。和集合、積集合、差集合の操作。「どのユーザーがこの通知を見たか？」や「このカテゴリにはどのレストランがあるか？」に使います。

**ハッシュ**：キー内の名前付きフィールド。オブジェクト全体を書き直すことなく個々のフィールドを更新したい構造化オブジェクトに使います。

**HyperLogLog**：確率的なカーディナリティ推定。すべての訪問者IDを保存することなく、ページへのユニーク訪問者を数えます。コンパクトで高速です。

**パブリッシュ/サブスクライブ**：チャネルにメッセージを公開し、サブスクライバーがリアルタイムでそれらを受け取ります。サービス間の軽量なリアルタイム通知に使います。

**ライトスルー：もう1つのキャッシングパターン**

キャッシュアサイド（遅延読み込み）は最も一般的なパターンです。しかし、知っておく価値のある2つ目があります。**ライトスルー**です。

ライトスルーキャッシングでは、アプリケーションがデータベースに書き込むたびに、すぐにキャッシュにも書き込みます。

```python
def update_menu(restaurant_id, menu_data):
    dynamodb.put_item(TableName="menu", Item=menu_data)
    cache.set(f"menu:{restaurant_id}", menu_data, ttl=300)
```

利点：キャッシュは常に最新です。書き込みとTTLの期限切れの間に古いデータが存在しません。

欠点：すべての書き込みが2か所に行きます。そして、決して読まれないかもしれないデータでキャッシュを埋めます。10軒のレストランがメニューを更新しても、次の5分間にそのうち2軒だけが大きなトラフィックを得る場合、期限切れになる前に使われない8つのキャッシュのためにライトスルー作業をしたことになります。

「待って、でも*なぜ*そのようにするの？」とマヤは尋ねました。「更新のたびにキャッシュに書き込むなら、書き込みごとに以前よりも多くの作業をしている。どうしてそれが良いの？」

「常に良いわけではありません」とプリヤは言いました。「ライトスルーは、書き込み後に古いデータの窓を一切許容できない場合に理にかなっています。キャッシュアサイドは、書き込みごとに余分な作業をしない代わりに、最大1 TTL分の古さを受け入れます。」

Nimbusの場合：キャッシュアサイドが正しい選択でした。メニューは書き込まれるよりもはるかに頻繁に読まれました。5分の古さの窓は許容範囲でした。すべての価格更新がすぐに反映される必要のある金融取引システムなら、ライトスルーの方が適切でしょう。

決定は2つの問いに帰着します。書き込み対読み取りの比率はどうか、そして書き込み後の古い読み取りにどれだけ寛容か、です。

**ElastiCache for Redis：マネージドで得られるもの**

RDSと同様に、ElastiCacheはオープンソースのツールを取り、運用作業を処理します。

- **自動バックアップ**：スケジュールに沿ったRedisのスナップショット
- **マルチAZレプリケーション**：プライマリノード + 異なるAZの読み取りレプリカ
- **自動フェイルオーバー**：プライマリRedisノードが故障すると、レプリカが自動的に昇格される
- **クラスターモード**：非常に大きなキャッシュのための複数ノードにわたる水平シャーディング
- **暗号化**：コンプライアンスのための転送中および保管中の暗号化
- **VPC統合**：キャッシュはプライベートネットワークで実行され、パブリックにはアクセスできない

**キャッシュのモニタリング**

「キャッシュが正しく機能していないときに何が起きるか、考えたことはありますか？」とプリヤは、Redisのデプロイの1週間後に尋ねました。「完全に故障するだけでなく、機能はするけれど、うまくいかない。高いミス率。高い退避率。じわじわ上がるレイテンシ。」

「ページロード時間が増えたら気づくよ」とレオは言いました。

「その時点では、データベースはすでに苦しんでいます」と彼女は言いました。

ElastiCacheはCloudWatchを通じてメトリクスを公開します。最も重要なもの：

**CacheHitRate**：結果を返したキャッシュ読み取りの割合。成熟したキャッシュでは理想的には80%以上です。低下するヒット率は、最もアクセスされるデータがキャッシュにないことを示します。TTLが短すぎるか、キャッシュが小さすぎるか、アクセスパターンが変わったかのいずれかです。

**CacheMisses**：キャッシュミスの絶対数。ここでの突然のスパイクは、キャッシュが役立っておらず、データベースがフル負荷を受けていることを意味します。

**Evictions**：新しいもののために場所を空けるべく退避されたキャッシュ項目の数。高い退避率は、キャッシュがワーキングセットに対して小さすぎることを意味します。より多くのメモリか、より選択的なキャッシング戦略が必要です。

**CurrConnections**：Redisへの現在のクライアント接続。接続が多すぎると、Redisの接続制限を使い果たす可能性があります。アプリケーションは、リクエストごとに新しい接続を開かないように、接続プーリングを使うべきです。

**ReplicationLag**：読み取りレプリカがプライマリからどれだけ遅れているか。これが増えると、レプリカの読み取りが古いデータを返す可能性があります。

レオは2つのCloudWatchアラームを設定しました。1つ目：キャッシュヒット率が15分連続で70%を下回ったら警告。それはデータベースがそれを感じる前に調査する価値のある問題を示します。2つ目：退避率が1分あたり100退避を超えたら警告。それはキャッシュが小さすぎることを示します。

「2つのアラームね」とプリヤは設定を確認しながら言いました。「良いスタートです。」

「ダッシュボードも追加した」とレオは言いました。「ヒット率、ミス率、退避、レイテンシ。すべて1か所で見られる。」

「ページが遅くなるのを待つよりはいいわね。」

「かなりいいよ」とレオは同意しました。

**ElastiCache対DAX：DynamoDBにはどちらのキャッシュ？**

「DynamoDBのデータをキャッシュするなら」とマヤは尋ねました。「なぜElastiCacheの代わりにDAXを使わないの？ドキュメントで見たんだけど。」

良い質問です。

**DAX（DynamoDB Accelerator）**は、DynamoDB専用に作られたインメモリキャッシュです。DynamoDBのAPI呼び出しをクライアントレベルでインターセプトします。アプリケーションコードは、同じDynamoDB SDKを使ってDAXと話します。キャッシュミスは自動的にDynamoDBから取得されます。キャッシュヒットはマイクロ秒で返ります。無効化はデータが変わると自動的に処理されます。

**ElastiCache**は汎用キャッシュです。キャッシュキー、TTLのロジック、無効化、そのすべてを自分で管理します。より多くの制御、より多くの責任です。

それぞれをいつ使うか：

| シナリオ | 推奨 |
|---|---|
| DynamoDBの読み取りをキャッシュし、アプリケーションの変更をゼロにしたい | DAX |
| DynamoDBの読み取りにマイクロ秒のレイテンシが必要 | DAX |
| 複数のソース（DynamoDB + RDS + 外部API）からキャッシュしている | ElastiCache |
| Redisのデータ構造（ソート済みセット、パブリッシュ/サブスクライブ、HyperLogLog）が必要 | ElastiCache |
| きめ細かいTTL制御とカスタムの無効化ロジックが必要 | ElastiCache |
| セッションストレージ、レート制限、分散ロックが必要 | ElastiCache |

Nimbusの場合：彼らはElastiCacheを選びました。複数のソースからデータをキャッシュしていたからです。メニュー用のDynamoDB、注文履歴サマリー用のRDS、レストラン評価用の外部APIです。DAXはDynamoDBでしか機能しません。そして、トレンドランキングのためにRedisのソート済みセットが必要でした。

「純粋にDynamoDBのキャッシングの問題だったら」とプリヤは言いました。「DAXがよりシンプルな答えでしょう。1つのサービス、自動無効化、同じAPI。でも、私たちには複数のデータソースがあります。」

「つまり、DynamoDBだけのときはDAXがシンプルで」とマヤはまとめました。「フルツールボックスが必要なときはElastiCache。」

「それがトレードオフです。」

### キャッシュデータを失えないとき：Amazon MemoryDB

「なぜ誰かがRedisをプライマリデータベースとして使うの？」とマヤは尋ねました。「キャッシュじゃないの？」

それこそ正しい問いです。

ElastiCache for Redisはキャッシュです。高速で、インメモリで、設計上、信頼できる情報源（source of truth）ではありません。ElastiCacheのノードが故障すると、再起動時にキャッシュは空です。アプリケーションはデータベースからそれを再ウォームします。キャッシュにはそれで問題ありません。

しかし、いくつかのユースケースは、Redisをキャッシュとしてではなくプライマリデータストアとして扱います。再起動を生き延びなければならないセッション状態、失われてはならないリアルタイムのリーダーボード、AZ障害を越えて持続しなければならないショッピングカートなどです。これらのユースケースでは、ElastiCacheの結果的な耐久性はリスクです。

**Amazon MemoryDB for Redis**は、フルマネージドでRedis互換の、耐久性のあるインメモリデータベースです。ElastiCacheとは異なり、MemoryDBは複数のAZにわたって保存される分散トランザクションログを使用し、すべての書き込みが確認応答される前に耐久性を持つようにします。データはノード障害を生き延びます。より遅いデータベースから再生するからではなく、1か所だけにあったことが決してないからです。

主な違い：

| | ElastiCache for Redis | MemoryDB for Redis |
|---|---|---|
| 役割 | キャッシュレイヤー | プライマリデータベース |
| 耐久性 | 障害時に保証されない | マルチAZトランザクションログ |
| レイテンシ | マイクロ秒の読み取りと書き込み | マイクロ秒の読み取り、1桁ミリ秒の書き込み |

両方とも同じRedisのコマンドとデータ構造をサポートします。APIは同じです。耐久性の保証は違います。

Nimbusの場合：チームはレストランごとのリアルタイムの注文数をRedisのソート済みセットとして保存したいと考えており、それはデータベースから再シードすることなくAZ障害を生き延びなければなりません。その要件（Redis互換*かつ*耐久性）は、まさにMemoryDBのシグナルです。

「つまり、障害後に再ウォームする必要がないの？」とレオは尋ねました。

「それがポイントです」とプリヤは言いました。「ノードが故障して戻ってきても、データはそこにあります。トランザクションログがそれを保持していました。」

レオはしばらく料金ページを見つめました。「ElastiCacheより高いね。」

「信頼に値するものはすべてそうです」とプリヤは言いました。

## 強みと限界

**キャッシングが強力な理由**：

- データベースの負荷を劇的に削減する（クエリが減り、コストが下がる）
- キャッシュヒットにはサブミリ秒の応答時間
- データベースをトラフィックスパイクから保護する
- Redisは単純なキーバリューストアよりも豊富なデータ構造をサポートする
- キャッシュスタンピードの緩和（TTLジッター、合体）がコールドスタートの急増から保護する

**キャッシングが複雑になるところ**：

- キャッシュの無効化は本当に難しい—古いデータはバグを引き起こす
- 運用上の複雑さを追加する（監視すべき別のサービス、別の障害点）
- コールドスタート問題：新しくデプロイすると、キャッシュは空—データベースがフル負荷を受ける
- キャッシュスタンピード：多くのエントリが一度に期限切れになると、すべてのリクエストが同時にデータベースにヒットする
- ElastiCacheのノードは無料ではない—アイドル状態でも料金がかかる

**ElastiCache対DynamoDB DAX**：

DynamoDBのデータを特にキャッシュしている場合、AWSは**DAX（DynamoDB Accelerator）**を提供します。これはDynamoDB専用に作られたインメモリキャッシュです。DAXはアプリケーションコードに対して透過的で（同じAPI）、DynamoDBの読み取りレイテンシをマイクロ秒に削減し、キャッシュの無効化を自動的に処理します。

ボトルネックがDynamoDBの読み取りで、変更ゼロのキャッシングが欲しいときはDAXを使います。任意のデータソースの汎用キャッシュが必要なとき、またはRedisのデータ構造が必要なときはElastiCacheを使います。

## 概要

47回のデータベース呼び出しが1回のキャッシュルックアップになりました。ページは188ミリ秒から12ミリ秒になりました。キャッシングレイヤーを追加することは、成長中のアプリケーションができる最もレバレッジの高い変更の1つです。ただし、キャッシュが思慮深く設計され、「このデータはいつ変わるのか？」という問いに明確な答えがあるときに限ります。

- キャッシュは最近取得したデータの高速なストアです。一度尋ね、答えを覚えておきます。ElastiCacheはAWSのマネージドキャッシュサービスで、**Redis**（永続化、複雑なデータ構造、パブリッシュ/サブスクライブ）と**Memcached**（純粋なキーバリュー、水平スケーリング）をサポートします。
- **キャッシュアサイドパターン**（遅延読み込み）：まずキャッシュを確認し、ミス時にデータベースにフォールバックします。**TTL**はデータがどれだけ長くキャッシュされるかを制御します。短いTTLはより新鮮なデータとより多くのミスを意味します。長いTTLはより速い応答と潜在的な古さを意味します。
- 正しいものをキャッシュしましょう：各セッションに固有のユーザーごとのデータではなく、多くのユーザーで共有されるエンティティごとのデータです。キャッシュスタンピードは多くのエントリが同時に期限切れになるときに起こります。TTLジッターで緩和します。
- **DAX**はDynamoDB専用のキャッシングには正しい選択です。**ElastiCache**はマルチソースのキャッシングとRedisのデータ構造により柔軟です。
- キャッシングの最も難しい部分は無効化です。データがいつ変わるかを知り、それを書き込むすべてのコードパスにわたってキャッシュを更新することです。キャッシュは、その無効化戦略と同じだけしか信頼できません。

## 試験のヒント

*SAA-C03 ドメイン：高パフォーマンスアーキテクチャの設計（ドメイン3、タスク3.3）*

- **試験でのRedis対Memcached**：Redis = 永続化、レプリケーション、複雑な構造、パブリッシュ/サブスクライブ。Memcached = シンプルなキーバリュー、純粋な水平スケーリング。シナリオが「キャッシュされたデータを失えない」と述べているとき、答えはRedisです（ディスクに永続化されるため）。
- **ElastiCacheのユースケースシグナル**：「データベースがボトルネック」「読み取り中心のワークロード」「レイテンシを削減」「セッションストア」、すべてElastiCacheを指します。
- **DAXのシグナル**：「DynamoDBの読み取りレイテンシを削減」または「DynamoDBの読み取りが遅すぎる」→ElastiCacheではなくDAX。
- **セッション管理**：ElastiCache Redisは、ユーザーセッションデータを保存するための典型的な答えです。ステートレスなアプリケーション + Redisセッションストア = 一貫したセッションでの水平スケーリングです。
- **ライトスルー対キャッシュアサイド**：キャッシュアサイド（遅延読み込み）が最も一般的です。ライトスルーは書き込みごとにキャッシュを更新します。決して古くなりませんが、書き込み操作が増えます。試験でこれらを区別することがあります。
- **キャッシュ退避ポリシー**：LRU（最も最近使われていないもの）が、一般的なWebワークロードでの最も一般的な試験の答えです。
- **ElastiCache対MemoryDB**：ElastiCache = キャッシュレイヤー、高速、障害時のデータ損失は許容可能。MemoryDB = 耐久性のあるインメモリのプライマリデータベース、Redis互換、マルチAZトランザクションログ。試験のトリガー：「Redis互換かつ耐久性」または「Redisでのプライマリデータストア」→ElastiCacheではなくMemoryDB。

**演習2—SAA-C03シナリオ**

*シナリオ*：あるビデオストリーミングプラットフォームが数百万人のユーザーにサービスを提供しています。利用可能な映画のカタログはめったに変わりません（毎晩更新されます）。すべてのユーザーリクエストがカタログをクエリするため、アプリケーションはデータベースのCPU使用率が高くなっています。チームは、更新から1時間以内にカタログデータを正確に保ちながら、データベースの負荷を削減したいと考えています。

これらの要件を最もよく満たすソリューションはどれですか？

A) 負荷を分散するためにRDSデータベースに読み取りレプリカを追加する
B) カタログをオンデマンドキャパシティのDynamoDBに移行する
C) カタログデータに1時間のTTLでElastiCache for Redisを使う
D) より多くの同時クエリを処理するためにRDSインスタンスのサイズを大きくする

**ヒント1**：データは読み取り中心で、めったに変わりません。これに理想的なパターンは何ですか？

**ヒント2**：「1時間以内に正確」は、特定のキャッシュ構成パラメータに直接対応します。

**ヒント3**：目標はデータベースの負荷を削減することであり、より多くを処理することではありません。

**解答**: C

**説明**：1時間のTTLのElastiCacheは、キーごとに最初のリクエストの後にカタログデータをキャッシュします。それ以降のリクエストはデータベースに触れることなくキャッシュから返ります。毎晩の更新が実行されると、エントリは1時間以内に期限切れになり、次のリクエストで新鮮なデータが読み込まれます。

**なぜAではないのか？** 読み取りレプリカは読み取りトラフィックをより多くのデータベースノードに分散しますが、クエリの総数を減らしません。読み取りのスケーリングには有用ですが、頻繁に繰り返されるクエリからのデータベース負荷の削減には役立ちません。

**なぜBではないのか？** DynamoDBへの移行は根本的な問題を解決しません。カタログデータは、すべてのユーザーリクエストでデータベース（DynamoDB）から取得され続けるでしょう。

**なぜDではないのか？** インスタンスのスケールアップはより多くの同時クエリを処理しますが、クエリの数を減らしません。根本的な非効率は残ります。
