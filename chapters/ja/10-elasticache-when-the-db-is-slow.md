# 第10章: データベースが遅い場合

画面にはページロードのメトリクスが開かれていた。レオはそれを20分間見つめても何も言わずにいた。

ページロードごとにダイナモDBへのリクエストが47件。ブラウザが1ピクセルもレンダリングする前に、データ取得に188ミリ秒もかかる。

彼は計算した。金曜日の夜に1万人の同時ユーザー：ダイナモDBへの読み取りが1分あたり47万件。コストは現実だ。しかし、実際の問題はレイテンシだった。Nimbusのブラウズページを開いたユーザーは、高速な接続でもほぼ200ミリ秒待ってから何かが表示され、それが問題だった。

「データベースはリクエストごとに4ミリ秒で応答している」とレオは言った。「それは実際には速い。ダイナモDBは自分の仕事をこなしている。」

「では、なぜページが遅いのですか？」マヤが尋ねた。

「ページロードごとに47回呼び出しているからです」プリヤが言った。「問題はデータベースではない。問題は、それを何度も問い合わせていることだ。」

トムは前に体を乗り出した。問題がコストの話に発展しそうな時の彼独特の表情を浮かべていた。

「つまり、それに対して話す回数を減らすということですか？」

「話す回数を減らす。記憶する量を増やす。」

**レストランのたとえ話**

レストランの厨房を想像してみよう。ウェイターが今日のスペシャルを知るたびに、彼らは厨房に向かい、シェフに尋ね、戻ってテーブルに戻る。

2人のウェイターと3つのテーブルであれば問題ない。

しかし、200人のウェイターと1000個のテーブルであれば、それぞれのウェイターが厨房に向かうことになる。厨房がボトルネックになる。シェフは1時間あたり400回同じ質問に答えることになる。

明らかすぎる解決策：スペシャルをレストランの前方の掲示板に書く。すべてのウェイターは掲示板から読む。厨房が休憩できる。掲示板はスペシャルが変更されるときに更新される。

この掲示板がキャッシュだ。

キャッシュとは、最近取得したデータを保存する高速でローカルな場所のことだ。同じものを繰り返し遅いソースから取得する代わりに、一度取得して近くに保存する。

**メモリだけを使うことはできないのか？**

「メニューをアプリケーションのメモリに保存することはできないのか？」レオが尋ねた。

有効な質問だ。

できる。単一サーバーアプリケーションの場合、インメモリキャッシュはうまくいく。しかし、Nimbusはロードバランサーの背後に動作し、複数のEC2インスタンスにまたがっている。1つのインスタンスがメモリにメニューをキャッシュすると、他のインスタンスにはそのデータがない。それぞれのインスタンスは独自のキャッシュを維持し、メニューが更新されると、すべて無効にする必要がある。

これは*キャッシュの一貫性問題*だ。複数のキャッシュを一致させる必要がある。

ElastiCacheは、この問題を解決するために*集中型*キャッシュを提供します。各サーバーが独自のメモリを持つのではなく、すべてのサーバーが同じキャッシュから読み取りおよび書き込みます。1回の更新がすべてに伝播する。

**ElastiCacheに出会う**

Amazon ElastiCacheは、管理されたキャッシュサービスだ。RedisやMemcachedといった人気のあるキャッシュエンジンを実行し、サーバーの管理をあなたに任せる必要がない。

**Redis**は、より強力なものだ。文字列、リスト、セット、ハッシュ、ソートされたセットといった複雑なデータ構造をサポートし、永続性（再起動時にデータが生存する）、レプリケーション、パブリッシュ/サブスクライブメッセージングも提供する。Redisはキャッシュの機能だけではない。軽量なデータストアとしても機能する。

**Memcached**は、よりシンプルだ。純粋なキーバリューキャッシュで、水平方向にスケーラブルで、永続性がない。単純なユースケースではより高速だが、機能は少ない。

Nimbusの場合：Redisが必要だった。メニューデータ（構造化されたもの）、セッショントークン（キーバリュー）、そして後で「トレンドレストラン」ランキングのソートされたセットをキャッシュする必要がある。

**キャッシュが実際にどのように機能するか**

キャッシュパターンは**キャッシュサイド**（別名：ラジーローディング）と呼ばれている。

1. アプリケーションがデータを必要とする
2. まずキャッシュを確認する
3. 見つかった場合（*キャッシュヒット*）：すぐにデータを返す
4. 見つからなかった場合（*キャッシュミス*）：データベースにアクセスし、データを取得し、キャッシュに保存し、返す

疑似コードでは：

```
menuData = cache.get("menu:restaurant-047")
if menuData is null:
    menuData = dynamodb.query(TableName="menu", KeyConditionExpression="restaurantId = '047'")
    cache.set("menu:restaurant-047", menuData, ttl=300)  # Cache for 5 minutes
return menuData
```

最初のリクエストは常にデータベースにヒットします。その後のリクエストはキャッシュにヒットします。キャッシュがあれば、NimbusのページロードあたりのDynamoDB読み取り47件は1つか2つのキャッシュ検索に減少します。高速で、安価で、スケーラブルです。

**TTL: どれくらい記憶しているのか？**

すべてのキャッシュエントリには**生存時間 (TTL)** があります: エントリが期限切れになり、次のリクエストが新しいデータのためにデータベースに戻るまでの期間です。

これはキャッシュの核心的な緊張感：鮮度とパフォーマンスです。

- **短いTTL (秒)**: 非常に新鮮なデータですが、キャッシュミスが多くなります。キャッシュはほとんど役に立ちません。
- **長いTTL (時間または日数)**: 非常に高速ですが、データが古くなる可能性があります。顧客は昨日のメニューを見ます。

メニューデータの場合、5分は妥当です。メニューは毎秒変更されないためです。レストランがメニューを更新した場合、顧客は最大5分間古いバージョンを見ることがあります—許容範囲です。

セッショントークン（このユーザーはログインしているか？）の場合、短いTTLが適切であるか、セッションが変更されるとキャッシュをすぐに更新します。

金融データ（注文合計、支払い記録）の場合、キャッシュしないでください—または、キャッシュする場合は書き込み時にすぐに無効化してください。

「キャッシュ無効化が難しいのはなぜですか？」マヤは尋ねました。

「データが実際にどのように変更されるか？メニューはパートナーのレストランによって更新されたのか？それとも、cronジョブが実行されたのか？それとも、管理者が手動で編集したのか？データが変更される可能性のあるすべての場所は、キャッシュに伝える必要があります。」

これが、エンジニアが「キャッシュの書き込みパスは何ですか？」と尋ねる代わりに、「Redisを追加しましょう」と始める理由です。

**キャッシュエビクション: ボードがいっぱいになったとき**

スペシャルボードには限られたスペースがあります。満杯になると、何かを消去してスペースを作らなければなりません。

Redis（およびキャッシュ全体）には、メモリがいっぱいになった場合に削除されるものが決定する**エビクションポリシー**があります。

- **LRU (Least Recently Used)**: 最も最近アクセスされなかった項目を削除します。
- **LFU (Least Frequently Used)**: 最もアクセス頻度の低い項目を削除します。
- **allkeys-random**: ランダムエビクション。単純で、最適ではありません。
- **noeviction**: メモリがいっぱいになるとエラーを返す（アプリケーションはこれを処理する必要があります）。

ほとんどのWebアプリケーションでは、LRUを使用します。最近アクセスしなかったものは、おそらく必要ありません。

**ElastiCache for Redis: 管理されたものを手に入れる**

RDSと同様に、ElastiCacheはオープンソースツールを扱い、運用作業を処理します。

- **自動バックアップ**: Redisスナップショットをスケジュールで
- **マルチAZレプリケーション**: プライマリノード + 異なるAZの読み取りレプリカ
- **自動フェイルオーバー**: プライマリRedisノードが失敗した場合、レプリカが自動的にプロモーションされます
- **クラスタモード**: 非常に大きなキャッシュ用の複数のノードにわたる水平シャーディング
- **暗号化**: 準拠のために、送受信時と保管時の暗号化
- **VPC統合**: キャッシュがプライベートネットワークで実行され、公開アクセスされません

トムは機能リストを見ました。「コストはいくらですか？」

「DynamoDB読み取りを置き換えるよりも少ない」とレオは言いました。「私は数字を計算しました。」

トムの表情は懐疑的から興味へと変化しました。これは進歩です。

## 強みと限界

**なぜキャッシュは強力なのか**

- データベースの負荷を大幅に削減します（クエリが少なくなり、コストが低下します）
- キャッシュヒットに対するサブミリ秒の応答時間
- データベースをトラフィックスパイクから保護します
- Redisは、シンプルなキー値ストアよりも豊富なデータ構造をサポートします

**キャッシュが複雑になる場所**

- キャッシュ無効化は本物で難しい—古いデータはバグを引き起こします
- 運用複雑さを追加します（監視する必要がある別のサービス、別の障害点）
- 冷間起動問題: 新しいものをデプロイすると、キャッシュは空になります—データベースがフルロードします
- キャッシュスートーム: 多数のエントリが同時に期限切れになると、すべてのリクエストがデータベースに同時にヒットします
- ElastiCacheノードは無料ではありません—アイドル時でも支払う必要があります

**ElastiCache vs DynamoDB DAX**

DynamoDBのデータをキャッシュする特定のケースでは、AWSは**DAX (DynamoDB Accelerator)**という、DynamoDB専用のインメモリキャッシュを提供します。DAXは、アプリケーションコード（同じAPI）に透明であり、DynamoDBの読み取りレイテンシをマイクロ秒まで削減し、キャッシュ無効化を自動的に処理します。

DAXは、DynamoDBの読み取りがボトルネックになっている場合に使用します。ElastiCacheは、あらゆるデータソースの一般的な目的のキャッシュが必要な場合に使用します。

## 概要

- キャッシュとは、最近取得したデータを高速に保存する場所です。一度問い合わせれば、答えを記憶します。
- ElastiCache は AWS が提供するマネージド キャッシュ サービスで、Redis と Memcached をサポートしています。
- **Redis** はより複雑（複雑なデータ構造、永続化、パブリッシュ/サブスクライブ）です。**Memcached** はよりシンプル（純粋なキー値、水平方向にスケーラブル）です。
- **キャッシュサイドパターン**（ラジーロード）：最初にキャッシュを確認し、キャッシュミス時にデータベースにフォールバックします。
- **TTL** はデータがキャッシュされている期間を制御します。短い TTL = 新鮮、多くのキャッシュミス。長い TTL = 迅速ですが、潜在的に古い可能性があります。
- キャッシュ無効化は困難です。キャッシュに追加するすべての書き込みパスを知っておく必要があります。
- ElastiCache はレプリケーション、フェールオーバー、バックアップ、暗号化を管理し、あなたはキャッシュの設計に集中できます。
- **DAX** は DynamoDB に固有のキャッシュです。ElastiCache は汎用です。

## 試験のヒント

- **Redis と Memcached の試験における違い**: Redis = 永続化、レプリケーション、複雑な構造、パブリッシュ/サブスクライブ。Memcached = 単純なキー値、純粋な水平方向のスケーリング。キャッシュされたデータを失うことができないシナリオの場合、Redis（ディスクに永続化）が正解です。
- **ElastiCache のユースケースのシグナル**: 「データベースがボトルネックになっている」、「読み取り指向のワークロード」、「レイテンシを削減する」、「セッションストア」はすべて ElastiCache を示唆します。
- **DAX のシグナル**: 「DynamoDB の読み取りレイテンシを削減する」または「DynamoDB の読み取りが遅すぎる」→ DAX、ElastiCache ではありません。
- **セッション管理**: ユーザーセッションデータを保存するために ElastiCache Redis が標準的な回答です。ステートレス アプリケーション + Redis セッションストア = 一貫したセッションで水平方向にスケーリングします。
- **書き込みスルーとキャッシュサイドパターン**: キャッシュサイドパターン（ラジーロード）が最も一般的な回答です。書き込みスルーは、すべての書き込みに対してキャッシュを更新し、常に最新の状態を維持しますが、より多くの書き込み操作を行います。試験では、これらを区別することがあります。
- **キャッシュエビクションポリシー**: LRU（最頻使用された最近のデータ）が一般的なウェブワークロードの最も一般的な回答です。

**練習問題 2 — 試験練習**

*シナリオ*: 多数のユーザーを抱える動画ストリーミングプラットフォームがあります。利用可能な映画のカタログは夜に更新されます。アプリケーションは、カタログのデータがデータベースで毎回クエリされるため、CPU 使用率が高くなっています。チームは、カタログのデータを更新後 1 時間以内に正確に保ちながら、データベースの負荷を軽減したいと考えています。

これらの要件を満たす最良のソリューションはどれですか？

A) 負荷を分散するために、RDS データベースに読み取りレプリカを追加します。
B) DynamoDB にカタログを移行し、オンデマンド容量を使用します。
C) 1 時間の TTL を持つ ElastiCache Redis を使用してカタログデータをキャッシュします。
D) データベースの同時クエリを処理できるインスタンスサイズを増やします。

ヒント 1: データは読み取り指向で頻繁に更新されません。このシナリオに最適なパターンは何ですか？

ヒント 2: 「1 時間以内に正確である」はキャッシュ構成パラメータに直接翻訳されます。

ヒント 3: 負荷を増やすのではなく、根本的な非効率性を解決することを目指しています。

**答え**: C

**説明**: 1 時間の TTL を持つ ElastiCache でカタログデータを更新後 1 時間以内にキャッシュします。次のリクエストは、データベースにアクセスせずにキャッシュから返されます。夜間更新が実行されると、エントリが 1 時間以内に期限切れになり、新しいデータが次のリクエストでロードされます。

**A が正しくない理由**: 読み取りレプリカは読み取りトラフィックを複数のデータベースノードに分散しますが、総クエリ数を減らすことはありません。読み取りのスケールアップに役立ちますが、頻繁に繰り返されるクエリからのデータベース負荷を軽減するのには役立ちません。

**B が正しくない理由**: DynamoDB にカタログを移行すると、カタログデータは DynamoDB (DynamoDB) からのアクセスによって取得されます。ユーザーリクエストごとに。

**D が正しくない理由**: インスタンスサイズをスケールアップすると、同時クエリを処理できますが、クエリの数を減らすことはありません。根本的な非効率性は依然として存在します。
