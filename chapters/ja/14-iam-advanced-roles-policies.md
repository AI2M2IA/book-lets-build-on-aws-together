**IAMの再検討: 全体像**

第3章ではIAM（ユーザー、グループ、ロール、ポリシー）を紹介した。今度はもっと深く掘り下げてみよう。

IAMポリシーはJSONドキュメントであり、どのリソースに対してどのような操作が許可されるか、または拒否されるかを指定する。以下のような形式になっている：

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": [
        "s3:GetObject",
        "s3:PutObject"
      ],
      "Resource": "arn:aws:s3:::nimbus-assets/*"
    }
  ]
}
```

このポリシーは、`nimbus-assets` バケットへの読み書きを許可し、それ以外の操作は一切行いません。削除、バケットのリスト表示、その他の S3 操作、およびその他の AWS サービスは許可されません。

特定のアクション、特定のリソースに対する権限を付与することが正しい方法です。

**「管理者アクセス」の問題**

AWS マネージドポリシーのような `AdministratorAccess` は、迅速な開始を目的としています。これは、実際のチームメンバーが参加する本稼働環境を運用するために設計されていません。

`AdministratorAccess` は、すべてのリソースに対してすべての操作を許可します。このポリシーを持つチームメンバーが誤って S3 バケットを削除したり、間違った EC2 インスタンスを停止したり、セキュリティグループのルールを変更したりした場合、AWS はそれを阻止することができません。権限は付与されています。

チームメンバーの認証情報が侵害された場合（フィッシング攻撃、アクセスキーの漏洩、ラップトップの盗難）の場合、攻撃者はあなたの AWS アカウントのすべてのリソースに対する管理者アクセス権を取得します。

**IAM ロール：サービスのためのアイデンティティ**

第 3 章で紹介したように、ロールは EC2 インスタンスが認証情報を保存することなく AWS サービスにアクセスする方法です。具体的にしましょう。

Nimbus API を実行している EC2 インスタンスは、以下のタスクを実行する必要があります。

- DynamoDB から読み取り
- DynamoDB への書き込み
- S3 にオブジェクトを格納（レシート、アップロード）
- CloudWatch へのログ書き込み
- Secrets Manager から秘密を読み取り

アクセスキーを作成してインスタンスに保存するセキュリティの悪夢（アクセスキーは誰でも読み取れる可能性がある）の代わりに、EC2 インスタンスにこれらの権限を持つ **IAM ロール** を作成します。

EC2 インスタンスは自動的にロールをアサートします。インスタンスメタデータサービスを通じて一時的な認証情報を AWS が提供します。認証情報は自動的にローテーションされます。漏洩するアクセスキーはありません。

「もし誰かが EC2 インスタンスをハッキングした場合、どうなりますか？」レオは尋ねました。

「ロールが許可する範囲内でできるだけ行動できます。」プリヤは答えました。「つまり、メニューから読み取り、注文を書き込み、ログを送信することです。S3 バケットを削除したり、EC2 インスタンスを停止したり、IAM を変更したりすることはできません。」

「なぜなら、EC2 ロールにはそれらの権限が付与されていないからです。」

「まさにその通りです。」

**ロールアサート：サービスが他のサービスになる方法**

ロールは、以下のものによってアサートできます。

- AWS サービス（EC2、Lambda、ECS タスクなど）
- 自分のアカウント内の IAM ユーザー（ロール昇格 - より多くの権限を持つロールを一時的に付与すること）
- 別の AWS アカウント内の IAM ユーザー（クロスアカウントアクセス - あなたのアカウントにロールを付与できる別の組織のアカウント）
- 外部アイデンティティプロバイダー（Google、Active Directory、Okta - 人間のユーザーに対するフェデラティブアクセス）

この最後のパターン - **アイデンティティフェデレーション** - は、大規模な組織が従業員に AWS アクセスを付与する方法です。あなたの会社の Active Directory にあなたの認証情報が格納されます。AWS にログインすると、Active Directory に認証し、AWS はあなたにロールを付与します。

**権限境界：ロールが付与できる権限の最大値を制限する**

ここで問題が発生します。デフォルトでは、IAM はユーザーが現在持っている権限を超える権限を付与することを防ぎません。

ソフィアが `iam:CreatePolicy` と `iam:AttachUserPolicy` を持っている場合、彼女は S3 への書き込みアクセスを許可するポリシーを作成し、それを自分自身にアタッチすることができます - 既存のポリシーが S3 への読み取りアクセスのみを許可している場合でも。この脆弱性のクラスは「権限昇格」と呼ばれ、まさに権限境界が存在する理由です。

しかし、チームリーダーが IAM 権限の作成を委任しながら、あなたが意図した範囲を超える権限を付与しないようにするにはどうすればよいでしょうか？

**権限境界** は、アイデンティティが持つことができる権限の最大値を設定します。アイデンティティに付与されたポリシーがより広範であっても、その効果的な権限は権限境界によって制限されます。

たとえば、チームリーダーにロールを作成する権限を付与します。ただし、境界を設定して「このチームリーダーが作成したロールには S3 の削除アクセスが付与されない」ようにします。チームリーダーが S3 の完全アクセス権を持つロールを作成しても、境界は削除を効果的に防ぎます。

これは高度な概念ですが、試験で登場し、組織が IAM 管理を大規模で委任する方法を反映しています。

**IAM Analyzer：権限の監査**

プリヤはチームの IAM 設定を 2 日間レビューしました。彼女は以下のことを発見しました。

- レオの個人的なユーザーは管理者アクセス権を持っていました（発見されたとおり）
- 古い Lambda 関数はすべての S3 バケットを読み取る権限を持っていました（テストの残り）
- 存在しない DynamoDB テーブルへの書き込みアクセス権を持つサービスロール

**IAM Access Analyzer** は、S3 バケット、IAM ロール、KMS キー、Lambda 関数など、外部エンティティと共有されているリソース（S3 バケット、IAM ロール、KMS キー、Lambda 関数）を自動的に特定する AWS サービスです。また、過剰な権限を持つポリシーも特定します。

定期的な IAM 監査は、運用の一部として行うべきです。権限は増える一方であり、自然に減少することはありません。Access Analyzer は、見えないものを可視化するのに役立ちます。

**Service Control Policies: 組織レベルのガードレール**

AWS 環境が複数のアカウント（大規模チームにおける開発アカウント、ステージングアカウント、本番アカウントなど）に成長した場合、**AWS Organizations** を使用して、中央アカウントからそれらすべてを管理できます。

Organizations 内では、**Service Control Policies (SCPs)** がアカウント内のすべての IAM エンティティ（管理者を含む）にガードレールを適用します。

例：開発アカウントでは、誰でも eu-west-1 リージョンで EC2 インスタンスを作成できないようにします。

開発アカウントで誰かが管理者アクセス権を持っている場合でも、この SCP を違反することはできません。組織レベルで強制され、アカウントレベルよりも上位です。

SCPs は権限を付与するものではなく、制限します。アカウント内のすべての IAM エンティティが持つ可能性のある最大権限を定義します。

## 強みと限界

**IAM ロールと最小特権の重要性**:

- クレデンシャルが侵害された場合に、影響範囲を限定する
- 攻撃者がすぐにフルアクセスを得るのではなく、複数のシステムを介してエスカレーションする必要がある
- CloudTrail ログを使用して監査追跡が可能
- サービスに必要なアクセスについて意識的な意思決定を促す

**複雑になる点**:

- AWS のアクション/リソースモデルを理解する必要があるため、正確な IAM ポリシーを作成するのは難しい
- 過剰な制限されたポリシーはアプリケーションを壊す - 複数のサービスにわたる「アクセス拒否」エラーのデバッグは時間のかかる作業
- IAM は、通常数秒、場合によってはそれ以上遅延して変更をプロパゲートする - これにより、混乱を招くタイミングの問題が発生する
- クロスアカウントロールの信頼ポリシー設定には注意が必要

## 概要

- 開発環境では、**管理者アクセス** を使用しない - 設定には使用せず、運用には使用しない
- IAM ポリシーは **効果**、**アクション**、**リソース** を指定する必要がある - 全てにおいて具体的に記述する
- ポリシーをグループ（人間用）とロール（サービス用）にアタッチする
- EC2 インスタンス、Lambda 関数、その他の AWS サービスは、アクセスキーではなく **IAM ロール** を使用する
- **権限境界** は、アタッチされたポリシーに関係なく、任意のアイデンティティが持つ可能性のある最大権限を制限する
- **SCPs** (Service Control Policies) は、管理者であっても上書きできない組織全体に適用される制限
- **IAM Access Analyzer** は、過剰な権限を持つポリシーと、リソースへの外部アクセスを特定します。

## 試験のヒント

*SAA-C03 ドメイン: セキュアなアーキテクチャの設計 (ドメイン 1, タスク 1.1)*

- **EC2 用の IAM ロール**: EC2 が S3、DynamoDB、Secrets Manager、またはその他の AWS サービスにアクセスする必要がある場合に、標準的な回答
- **IAM ポリシー評価ロジック**: IAM は、明示的な許可/拒否の階層を使用してリクエストを評価します。明示的な **拒否** は、明示的な **許可** を常に上回り、デフォルトは **拒否** です。
- **権限境界**: IAM 管理を委任する場合に使用 - 開発者が Lambda 関数用のロールを作成できるようにし、それ以上の権限を付与しないようにするシナリオ
- **SCPs は権限を付与しない**: 制限するだけです。SCP が S3 を許可し、IAM ポリシーがそれを拒否する場合、S3 は拒否されます。SCP が S3 を拒否し、IAM ポリシーがそれを許可する場合、S3 は拒否されます。
- **リソースベースポリシー**: S3、SQS、Lambda などの一部の AWS サービスには、リソースベースポリシー（アイデンティティではなくリソースにアタッチされたポリシー）があります。これらのポリシーは、IAM ポリシーと並行して機能します。
- **クロスアカウントアクセス**: アカウント A の IAM ロールに、アカウント B がそれを継承できるようにする信頼ポリシー
- **IAM ユーザー vs フェデレーションアクセス**: 大規模な組織の場合、IAM Identity Center または直接フェデレーションを通じて、個別の IAM ユーザーよりもフェデレーションアクセス（IAM ユーザーまたは直接フェデレーションを通じて IDP との連携）が好ましい

**練習問題 2 - 試験練習**

*シナリオ*: Lambda 関数が S3 バケットから読み取り、DynamoDB テーブルに書き込みます。開発中に単純化するために、開発者が Lambda 関数に「AdministratorAccess」権限を持つロールを付与します。本番環境に移行する前に、セキュリティチームは最小特権を遵守したいと考えています。

次のうち、最適なアプローチはどれですか？

A) S3の読み取りとDynamoDBへの書き込みの権限を持つ新しいIAMユーザーを作成し、アクセスキーを生成します。アクセスキーをLambda環境変数に保存します。
B) Lambda関数の実行ロールに埋め込みポリシーをアタッチし、特定のバケットに対する`s3:GetObject`と特定のテーブルに対する`dynamodb:PutItem`を付与します。
C) `AdministratorAccess`を維持しつつ、S3とDynamoDB以外のすべての操作をブロックするSCPを追加します。
D) S3の読み取りとDynamoDBへの書き込みの権限を持つIAMグループを作成し、Lambda関数をそのグループに追加します。

**ヒント1**: Lambda関数は実行ロールを使用し、アクセスキーを使用しません。どのオプションがこれを尊重しますか？

**ヒント2**: 最少特権とは、特定のリソースに対する具体的なアクションであり、広範なポリシーではありません。

**ヒント3**: IAMグループはユーザーを含み、Lambda関数を含みません。

**解答**: B

**解説**: Lambdaの実行ロールには、関数が必要とする具体的な権限のみを付与する必要があります。特定の操作（`s3:GetObject`）と特定のリソース（バケットARN、DynamoDBテーブルARN）に対するスコープされた埋め込みポリシーが、最も少ない特権の実装です。

**Aがなぜ正しくないのか？** Lambda環境変数にアクセスキーを保存することは、セキュリティ上の悪癖です。キーは、Lambdaコンソールへのアクセスを持つ人、または実行コンテキストを通じて読み取られる可能性があります。Lambda関数は、IAMから一時的なクレデンシャルを提供する実行ロールを使用します。

**Cがなぜ正しくないのか？** SCPは組織/アカウントレベルで適用され、関数ごとの権限制御を機能させるものではありません。AdministratorAccessとSCPの組み合わせは、誤った階層です。

**Dがなぜ正しくないのか？** Lambda関数はIAMグループに追加できません。グループはIAMユーザーのみを対象としています。
