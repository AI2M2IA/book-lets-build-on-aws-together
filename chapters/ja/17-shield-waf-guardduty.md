**3つの脅威カテゴリ**

クラウドアプリケーションに対するセキュリティ脅威は、一般的に3つのカテゴリに分類されます。

**ボリューム攻撃（DDoS）**：攻撃者があまりに多くのトラフィックを送るので、あなたのアプリケーションが正当なユーザーに応答できなくなります。攻撃は数百万のHTTPリクエストかもしれませんし、サーバーの接続テーブルを使い果たすように設計されたTCP SYNパケットの洪水かもしれません。

**アプリケーション攻撃（エクスプロイト）**：攻撃者が、アプリケーションの弱点を悪用するように特別に細工されたリクエストを送ります。SQLインジェクション、クロスサイトスクリプティング、パーサーをクラッシュさせる不正な入力です。

**振る舞いの異常（偵察と侵害）**：起こるべきでないAPI呼び出し（午前3時に誰かがあなたのユーザーデータベース全体をクエリする）、異常なIAMアクティビティ（新しい国から使われる認証情報）、または予期しない宛先へのネットワークトラフィックです。

AWSには各々のための専用のサービスがあります。

- **AWS Shield**：DDoS保護
- **AWS WAF**：アプリケーション層の保護
- **Amazon GuardDuty**：振る舞いの脅威検知

**AWS Shield：DDoS吸収機**

**AWS Shield Standard**は、追加料金なしですべてのAWS顧客に対して自動的に有効化されます。最も一般的なレイヤー3（ネットワーク）とレイヤー4（トランスポート）のDDoS攻撃から保護します。SYNフラッド、UDPフラッド、DNS増幅攻撃です。

CloudFront、Route 53、Elastic Load BalancingはAWSのネットワークのエッジに位置します。DDoS攻撃があなたのアプリケーションを狙うと、まずこれらのマネージドサービスにヒットします。AWSのネットワークインフラが、EC2インスタンスに到達する前に攻撃を吸収します。

**AWS Shield Advanced**はプレミアムティアです（組織あたり月3,000ドル、1年のコミットメント付き）。別のサブスクリプションです。どのAWSサポートプランにも*含まれていません*。次を追加します。

- EC2、ELB、CloudFront、Global Accelerator、Route 53の保護
- ほぼリアルタイムの攻撃通知
- AWS Shield Response Team（SRT）へのアクセス—攻撃への対応を手伝えるセキュリティエンジニア（SRTの関与には、さらにBusinessまたはEnterpriseサポートプランが必要）
- コスト保護：攻撃があなたの請求を急増させた場合、AWSが急増コストをクレジットする
- レイヤー7（アプリケーション層）での強化されたDDoS検知と緩和

**DDoSインシデント：Shieldが実際に動くとどう見えるか**

立ち上げから8か月後、Nimbusは最初の本物のDDoS攻撃を受けました。

それはある火曜の午前11時43分に始まりました。ロードバランサーのCloudWatchダッシュボードは、入ってくる接続リクエストが、通常の毎分3,000から毎分180,000へ、90秒足らずで急上昇するのを示しました。送信元IPは40か国に分散していて、インバウンドのボリュームは毎秒約50ギガビットでピークに達しました。パターンは紛れもないものでした。SYNフラッドを仕掛けるボットネットです。

レオは最初にCloudFrontのメトリクスを見ました。「リクエスト率が60倍に上がっている。応答時間が急上昇している。」

プリヤはCloudWatchのメトリクスを並べて開きました。エッジでの接続の試みが垂直に上昇し、実際にオリジンに到達するリクエストは—平坦。「Shield Standardが食べている」と彼女は言いました。アラートも、ダッシュボードのイベントも、通知もありませんでした。Shield Standardは静かに機能します。常にオンで、無料で、**攻撃の可視性を一切与えません**。イベントコンソールも、通知も、DDoS対応チームもありません。（その可視性—ほぼリアルタイムの攻撃ダッシュボードとアラート—こそが、Shield *Advanced*が売るものです。）プリヤが攻撃を見られた唯一の方法は、彼女自身のCloudWatchメトリクスを通じてでした。

Shield StandardはSYNフラッドを自動的に検知し、最初の2分以内に緩和を開始していました。攻撃トラフィックは、CloudFrontのエッジノードでグローバルに吸収されていました。正当なコンテンツを提供したのと同じ750以上のポイントオブプレゼンスが、攻撃のボリュームも吸収しました。

午前11時52分までに—攻撃が始まってから9分後—Shieldの緩和は、オリジンでのリクエスト率を通常に戻していました。攻撃はまだネットワークレベルで実行中でしたが、緩和がそれを処理していました。Nimbusアプリケーションは、その間ずっとユーザーに提供し続けました。

「ユーザーは気づかなかった?」とレオは、エラー率のメトリクスを見ながら尋ねました。

「エラー率が約4分間、約2パーセント上がりました」とプリヤは言いました。「一部のユーザーがわずかに遅い応答を得ました。停止なし。アプリケーションは稼働し続けました。」

**AWS WAF：アプリケーションフィルター**

**AWS WAF（Web Application Firewall）**はHTTPレベルで動作します。Webリクエストの内容を、それがあなたのアプリケーションに到達する前に検査します。

WAFは**Web ACL（Access Control List）**で設定されます。何を許可、ブロック、またはカウントするかを定義するルールセットです。

WAFは次にアタッチできます。

- CloudFrontディストリビューション（エッジでリクエストを検査、グローバルに）
- Application Load Balancer（リージョナルレベルでリクエストを検査）
- API Gateway
- AWS AppSync

**WAFマネージドルール**：AWSとサードパーティのベンダーが事前構築されたルールセットを公開しています。

- **AWS Managed Rules - Core Rule Set**：コンパニオンのルールグループ（SQLデータベース、Known Bad Inputs）とともに、OWASP Top 10の脆弱性（SQLインジェクション、XSS、コマンドインジェクション、パストラバーサルなど）をカバーします
- **AWS Managed Rules - Known Bad Inputs**：既知の攻撃パターンに一致するリクエストをブロックします
- **AWS Managed Rules - Amazon IP Reputation List**：ボットネットやスキャナーに関連することで知られるIPをブロックします
- **AWS Managed Rules - Bot Control**：ボットトラフィックを特定・管理します

カスタムルールも作成できます。

- 「'sqlmap'（一般的なSQLインジェクションスキャナー）を含むUser-Agentヘッダーを持つ任意のリクエストをブロック」
- 「レート制限：IPあたり5分間に1000リクエストを超えて許可しない」
- 「任意のパラメータ値に`<script>`を含むリクエストをブロック」

Nimbusの場合、実用的なセットアップ：Core Rule Setを有効にしたCloudFrontディストリビューションのWAFです。これは、リクエストがEC2インスタンスに到達する前に、最も一般的な攻撃パターンをブロックします。

こう思っているかもしれません。WAFが既知の攻撃パターンをブロックするなら、WAFが知らない新しい攻撃パターンが現れたら何が起きるのか？WAFのマネージドルールセットは、新しい脅威が現れるとAWSとサードパーティのベンダーによって更新されます。ルールを手動で更新する必要はありません。しかし、WAFが根本的に既知のパターンに反応的であることは正しいです。新しく斬新な攻撃手法は、まだ存在しないルールではブロックされません。これが、GuardDutyがWAFと並んで存在する理由です。WAFは玄関をフィルターし、GuardDutyは家の中の異常な振る舞いを監視します。新しい攻撃タイプはWAFを通り抜けるかもしれませんが、GuardDutyはそれが引き起こす異常なアクティビティ—異常なAPI呼び出し、予期しないネットワーク宛先、ベースラインに一致しないアクセスパターン—に依然としてフラグを立てられます。

**WAFが誤検知を引き起こしたらどうなるか、考えたことはありますか?** とプリヤは尋ねました。「Core Rule Setにブロックされる正当なユーザーのリクエスト?」

「WAFには『Count』モードがあります」とレオは言いました。「ブロックする代わりに、一致するリクエストを数えるだけです。まずCountモードで実行し、何がブロックされていたかをレビューし、誤検知がないことを検証し、それからBlockに切り替えます。」

「いいわね」とプリヤは言いました。「Countモードから始めます。」

**WAFルールの作成：レート制限の物語**

CountモードでWAFを有効にして2週間後、プリヤはログをレビューしました。Core Rule Setの発見はきれいでした。正当なトラフィックに誤検知なし、自動スキャナーからのブロックされたSQLインジェクションの試みがいくつか。

しかし彼女は、Core Rule Setがフラグを立てていないパターンに気づきました。1つのIPアドレスが、5分間に`/api/search`に847リクエストをしていました。すべてのリクエストが構造的に有効でした。しかし5分間に847の検索は人間ではありませんでした。

「価格スクレイパー」と彼女は言いました。「誰かが、競合の価格データベースを構築するために、私たちのレストラン検索を自動的にクエリしています。」

「気にする?」とレオは尋ねました。

「私たちのコンピュートリソースを使っていて、利用規約に反している」とトムは言いました。

「気にします」とプリヤは確認しました。

彼女はカスタムのWAFレートベースルールを作成しました。

```
ルール名: RateLimitSearchAPI
ルールタイプ: レートベースルール
レート制限: IPアドレスあたり100リクエスト
評価ウィンドウ: 5分 (設定可能: 1, 2, 5, または10分)
スコープダウンステートメント: URIパスが/api/searchで始まる
アクション: ブロック
```

スコープダウンステートメントは重要です。レート制限は`/api/search`にだけ適用されます。他のエンドポイントへの正当なAPIトラフィックは影響を受けません。そしてブロックがどう機能するか注目してください。固定の「罰」期間はありません。WAFは各IPのリクエスト率を継続的に再評価し、率が制限を上回っている間それをブロックし、率が制限を下回ると（通常は数秒以内に）ブロックを解除します。

彼女はまずCountモードに設定しました。24時間実行しました。ルールに引っかかった唯一のIPはスクレイパーでした。正当なユーザーが、5分間に検索エンドポイントに12を超えるリクエストを送ったことは一度もありませんでした。

彼女はBlockモードに切り替えました。スクレイパーの次のリクエストは403を受け取りました。それは異なるIPに切り替えました。レート制限はそれも捕らえました。

「彼らはいずれ回避するでしょう」とレオは言いました。「より多くのIPに分散する。」

「その時点で、彼らはより多くのインフラを使い、より多く支払い、より少ないデータを得ています」とプリヤは言いました。「彼らを完全に止める必要はありません。それが割に合わないほど高価にする必要があります。」

「それは月にいくらかかる?」とトムは尋ねました。

WAFの料金は、Web ACLごと月ごと、ルールごと月ごと、そして100万リクエストごとです。Nimbusのセットアップ—1つのWeb ACL、CloudFront上の5つのルール—には、約月15ドルプラスリクエスト料金です。

トムはすぐにそれを承認しました。

**Amazon GuardDuty：振る舞いのアナリスト**

「待って、でも*なぜ*そのようにするの?」とマヤは尋ねました。「WAFが攻撃をブロックしていてShieldが洪水を吸収しているなら、なぜ3つ目のサービスが必要なの？GuardDutyは実際に何を監視しているの?」

WAFとShieldはフィルターです。悪いトラフィックがアプリケーションに到達する前にそれを傍受します。GuardDutyは、トラフィックが到着した後に何が起きるかを監視します。あなたのインフラが何をしているかを見ます。どのIAM認証情報が使われているか、あなたのインスタンスがどのドメインに接続しているか、午前3時にどんなAPI呼び出しが起きているか。正当に見えるリクエストを通じて玄関を通り抜けた攻撃者は、WAFに止められません。しかしGuardDutyは、同じ認証情報が突然ルーマニアからAPI呼び出しをしていることに気づきます。

GuardDutyはShieldやWAFと根本的に異なります。攻撃をブロックしません。**異常な振る舞いを検知します**。

GuardDutyは、脅威を検知するためにいくつかのアクティビティのストリームを継続的に分析します。**CloudTrailの管理イベントとデータイベント**（API呼び出しとアクション）、**VPCフローログ**（ネットワークトラフィックのパターン）、**DNSクエリログ**（ドメインのルックアップ）です。これらは、GuardDutyが常に依存してきた3つの基礎的なソースです。

- **AWS CloudTrailログ**：IAMの変更、API呼び出し、コンソールのログイン
- **VPCフローログ**：VPC内のネットワークトラフィックのパターン
- **DNSクエリログ**：あなたのインスタンスが何を解決しているか（既知のマルウェアはしばしば特定のC2ドメインを解決します）

しかしGuardDutyはこれら3つを大きく超えて拡張しました。AWSはオプションのアドオンを**保護プラン**と呼びます。S3 Protection、EKS Protection、RDS Protection、Lambda Protection、Runtime Monitoring、Malware Protectionで、それぞれ個別に有効化されます。どれを有効にするかによって、GuardDutyは、**S3データイベント**（バケットへの異常なアクセスパターン）、**EKS監査ログと実行時アクティビティ**（実行中のコンテナ内の悪意のある振る舞い）、**RDSログインイベント**（異常なデータベースログインの試み）、**Lambdaのネットワークトラフィック**（予期しない外部宛先を呼び出す関数）、**ECS/EC2の実行時の振る舞い**、そして**マルウェアをスキャンされたEBSボリューム**も分析できます。試験のために、3つのコアソースを暗記しましょう。保護プランは特定の脅威検知のコンテキストに関するシナリオに登場します。「RDSへの異常なログインの試みを検知する」または「実行中のコンテナ内の悪意のある振る舞いを特定する」は、GuardDutyのオプションの保護プランを考えるシグナルです。

機械学習モデルが、あなたのベースラインから逸脱するパターンを特定します。GuardDutyは異常を検知すると**findings（発見）**—分類されたアラート—を生成します。

GuardDutyが検知できるものの例：

- 認識されていないIPアドレス（これまで使ったことのない国）からログインするIAMユーザー
- Tor出口ノードから行われるAPI呼び出し
- 既知の暗号通貨マイニングプールと通信するEC2インスタンス
- 異常に高いAPI呼び出しのボリューム（認証情報の悪用またはスキャン）
- 悪意のあるアクティビティでフラグが立てられたIPアドレスによってアクセスされるS3バケット
- マルウェアのコマンド・アンド・コントロールに関連することで知られるドメインへのアウトバウンドトラフィック

「これがルーマニアIPを捕らえたものだ」とレオは静かに言いました。

「GuardDutyを有効にしていたら、午前2時に認識されていない外部IPへのアウトバウンド接続をしているEC2インスタンスにフラグを立てていたでしょう」とプリヤは確認しました。

**5つのGuardDuty findingタイプと何をすべきか**

プリヤは、最も一般的な5つのGuardDuty findingのためのランブックを作成しました。findingが発火すると、チームはそれが何を意味し、何をすべきかを即座に知ります。

**1. UnauthorizedAccess:IAMUser/ConsoleLoginSuccess.B**

IAMユーザーが、このアカウントでこれまで見られなかったIPアドレスから、または以前のログインと一貫しない地理的位置から、AWSコンソールに正常にログインしました。

対応：ユーザーにログインを開始したか確認します。していなければ—または連絡が取れなければ—即座に：ユーザーのアクセスキーとコンソールパスワードを無効化し、アクティブなセッションを取り消し、そのユーザーが過去24時間にしたすべてのことのCloudTrail監査を始めます。このfindingはしばしば認証情報の悪用に先行します。

**2. CryptoCurrency:EC2/BitcoinTool.B**

EC2インスタンスが、暗号通貨マイニングプールに関連するIPアドレスまたはドメイン名をクエリしています。これはほとんど常に、EC2インスタンスが侵害されてマイニングボットとして使われている結果です。

対応：インスタンスを即座に隔離します。セキュリティグループを変更して、踏み台ホストを除くすべてのインバウンドとアウトバウンドのトラフィックをブロックします。EBSボリュームのフォレンジックスナップショットを取ります。それからインスタンスを終了し、クリーンなAMIから代替を起動します。

**3. Recon:EC2/PortProbeUnprotectedPort**

EC2インスタンスが、既知のスキャナーまたはTor出口ノードによって探られているポートをインターネットに開いています。GuardDutyは、外部のソースからアクセス可能としてフローログに現れるポートにフラグを立てます。

対応：セキュリティグループのルールをレビューします。ポートが意図的に開いているなら、メモを付けてfindingを解決済みとマークします。意図的でないなら、ポートを即座に閉じます。そのポートを通じて発生したかもしれない任意のアクセスについてCloudTrailを確認します。

**4. Trojan:EC2/BlackholeTraffic**

EC2インスタンスが、「ブラックホール」として特定されたIPアドレス—マルウェアのコマンド・アンド・コントロールのインフラに関連する宛先—と通信しようとしています。これらのIPへのトラフィックは、インスタンスが感染して呼び出そうとしていることを示唆します。

対応：CryptoCurrencyのfindingと同じ—隔離、スナップショット、置き換え。このfindingはインスタンス上のアクティブなマルウェアを示します。インスタンスをその場でクリーンにしようとしないでください。クリーンなAMIから新しいものを構築します。

**5. Policy:S3/BucketBlockPublicAccessDisabled**

誰かがS3バケットのBlock Public Access設定を無効にしました。これはバケットがパブリックであることを意味しません。偶発的なパブリックな露出を防ぐ安全メカニズムが、そのバケットでオフにされたことを意味します。これはしばしば偶発的に、または誤って設定されたデプロイの一部として行われます。

対応：誰が変更したか調査します（CloudTrailにAPI呼び出しがあります）。無効にすべき文書化された理由がない限り、Block Public Accessを再び有効にします。このfindingが将来発生するのを防ぐために、アカウントレベルのBlock Public Access設定を有効にすることを検討します。

「GuardDutyのfindingについて最も重要なこと」とプリヤは言いました。「は、それらがアラートではないということです—仮説です。各findingは『このパターンは異常に見える』と言います。検証し、調査し、対応します。一部は誤検知でしょう。ほとんどはそうではありません。」

「どう優先順位をつける?」とラファエルは尋ねました。

「GuardDutyは深刻度レベルを割り当てます：低、中、高。高深刻度のfindingは当日の対応を要求します。Trojanと認証情報侵害のfindingは常に高です。ポート探りのfindingは中か低かもしれません。高から始めて、下に進みます。」

**3つのサービスを結びつける**

Shield、WAF、GuardDutyは異なるレイヤーで機能し、互いを補完します。

| サービス    | レイヤー                     | 何から保護するか                            | アクション                             |
|------------|---------------------------|---------------------------------------------|------------------------------------|
| AWS Shield | ネットワーク/トランスポート (L3/L4) | DDoS洪水                                 | 攻撃を吸収/緩和          |
| AWS WAF    | アプリケーション (L7)          | OWASP Top 10、ボット、スクレイパー                | リクエストを許可、ブロック、またはカウント |
| GuardDuty  | 振る舞い (すべてのログ)     | 異常、侵害された認証情報、マルウェア | 検知してアラート                 |

Shieldは洪水を止めます。WAFは水をフィルターします。GuardDutyは異常な流れのパターンを配管で監視します。Macieは貯水池に何が保管されているかを監査します。Security Hubは、すべてのダッシュボードが一度に見える管制室です。

それぞれの障害モードが、なぜそれらすべてが必要かを説明します。

- 50 GbpsのSYNフラッドはWebリクエストではありません。WAFはそれを検査できません。GuardDutyは関連するCloudTrailイベントに気づくかもしれません。Shieldがそれを止めます。
- 単一のSQLインジェクションのリクエストは洪水ではありません。Shieldはそれを無視します。GuardDutyはHTTPリクエストの内容を知りません。WAFがそれを捕らえます。
- 自分の認証情報を使ってゆっくりデータを流出させる正当なAWSユーザー—DDoSなし、インジェクションなし、有効なHTTP—ShieldとWAFは異常なものを何も見ません。GuardDutyは、認証情報が午前3時に新しい国から使われていることに気づきます。
- 顧客データを誤ってパブリックにアクセス可能なバケットにアップロードする開発者は、異常な振る舞いをまったく生み出しません。GuardDutyはフラグを立てるものがありません。MacieがバケットをスキャンしてPIIを見つけます。

各サービスには死角があります。組み合わせがそれらの死角をカバーします。

**CloudTrail：基盤**

3つすべてのサービスがログに依存します。**AWS CloudTrail**は、あなたのAWSアカウントのすべてのAPI呼び出しをキャプチャするロギングサービスです。誰が何を、いつ、どこから、どんな結果で呼び出したか。

CloudTrailはコンソールで90日の履歴のためにデフォルトで有効です。ログを長期保持するには：

1. S3バケットに書き込むトレイルを作成する
2. オプションで、リアルタイムのアラートのためにCloudWatch Logsに送る
3. ログファイル検証を有効にする（ログが改ざんされたか検知するため）

GuardDuty、AWS Config、Security Hub、IAM Access AnalyzerはすべてCloudTrailから読みます。CloudTrailのログなしでは、これらのサービスは分析するものが何もありません。

「誰かがCloudTrailを無効にしようとしたら?」とプリヤは尋ねました。「攻撃者が管理者アクセスを得たら、最初のアクションはロギングを無効にすること—痕跡を隠すこと—かもしれません。」

「それが第14章のSCPが防ぐものです」とレオは言いました。「このアカウントの誰も、管理者でさえCloudTrailを無効にできません。」

「そして、もし彼らが何とかしたら?」

「Security Hubがfindingを生成します。CloudTrailは設定変更でSNSに通知を送ります。CloudTrailの任意の変更から2分以内にアラートを得ます。」

「そしてGuardDutyがAPI呼び出しにフラグを立てます」とラファエルは付け加えました。「異常なIAMアクションとして—ロギングを無効にすることは通常の運用活動ではありません。」

最も重要なセキュリティアクションの1つ—ログの改ざん—のための複数のレイヤーの検知です。これは偶然ではありませんでした。プリヤはそれを意図的に設計していました。

「多層防御は監視のレイヤーにも適用されます」と彼女は言いました。「アプリケーションのレイヤーだけでなく。」

**Amazon Macie：S3の機密データ**

「誰かが顧客のクレジットカード番号を含むファイルを誤ってS3にアップロードしたら何が起きるか、考えたことはありますか?」とプリヤは尋ねました。「悪意なく—ただデバッグのためにデータをエクスポートする開発者が、間違ったファイルをアップロードする?」

「私たちは決して知らないでしょう」とレオは言いました。

「その通り。Macieがなければ。」

**Amazon Macie**は、機械学習を使ってS3の機密データを自動的に発見・保護するデータセキュリティサービスです。S3バケットを継続的にスキャンし、次を特定します。

- PII（個人を特定できる情報）：名前、メールアドレス、電話番号、生年月日
- 財務データ：クレジットカード番号、銀行口座番号
- 認証情報：ファイルに埋め込まれたパスワード、アクセスキー、秘密鍵
- 健康情報：患者記録、診断

Macieは、機密データがあるべきでない場所で検知されたとき—またはS3バケットが過度に寛容なアクセス設定を持っているとき—findingを生成します。

「これはGuardDutyと同じ?」とマヤは尋ねました。

「異なる目的です」とプリヤは言いました。「GuardDutyは振る舞いを監視します—どんなアクションが取られているか、それらのアクションが異常に見えるか。Macieはデータを監視します—どんな内容が保管されているか、その内容が機密か。GuardDutyは異常なAPI呼び出しをするEC2インスタンスにフラグを立てるでしょう。Macieはクレジットカード番号を含むS3バケットにフラグを立てるでしょう。」

「つまり、GuardDutyは振る舞いのアナリストで」とレオは言いました。「Macieはデータの監査人だ。」

「その通り。両方が必要です。正当に見えるAPI呼び出しを通じてデータを流出させる攻撃者は、異常なAPIパターンでGuardDutyにフラグを立てられるかもしれません。でも、従業員が1万件の顧客レコードを含むファイルを開発バケットにアップロードしたら、検知すべき異常な振る舞いはありません—間違った場所に機密データがあるだけです。Macieがそれを捕らえます。」

Nimbusの場合、Macieの最もすぐの価値は`nimbus-debug-exports`バケットにありました。開発者がデバッグのためにデータをダンプするのに使うバケットです。Macieは、顧客の名前と配達先住所を含む注文履歴を含む3つのファイルを見つけました。支払いデータではありませんが、暗号化されていない開発バケットにあるべきでない個人データでした。

ファイルは削除されました。ポリシーが追加されました。デバッグバケットは合成テストデータだけに制限されました。本物の顧客データは、本番以外の任意の環境にエクスポートするにはプリヤの承認を必要としました。

「それは月にいくらかかる?」とトムは尋ねました。

Macieは、月ごとに評価されるS3バケットの数とスキャンされるデータのボリュームに基づいて課金します。適度な数のバケットを持つスタートアップには、約月10〜50ドルです。最初の30日は無料です。

**AWS Security Hub：ダッシュボード**

複数のAWSアカウントを実行しているか、セキュリティのfindingの統合されたビューが必要なら、**AWS Security Hub**は、GuardDuty、Inspector（脆弱性評価）、Macie（データプライバシー）、Config、Firewall Managerからのfindingを単一のダッシュボードに集約します。

また、あなたの設定をセキュリティのベストプラクティス（AWS Foundational Security Best Practices標準）とCIS AWS Foundations Benchmarkに照らしてチェックします。

Security Hubは「5つの異なるコンソールを切り替えることなく、すべてのセキュリティのfindingを1か所で見るにはどうすればいいか？」への答えです。GuardDutyがfindingを生成すると、GuardDutyとSecurity Hubに現れます。MacieがS3バケットで機密データを見つけると、MacieとSecurity Hubに現れます。Configルールが設定ミスを検知すると、ConfigとSecurity Hubに現れます。

単一アカウントのチームには、Security Hubはわずかな価値を加えます—確認すべきもう1つのコンソールです。その力は大規模で現れます。3アカウント、10アカウント、50アカウント。すべてのアカウントからのすべてのfindingが、管理アカウントのSecurity Hubに集約されます。1つのチームが1つのダッシュボードを監視します。1組のアラート。アカウントごとのログ確認なし。

Nimbusの場合：Security Hubはまだ必要ありませんでした。3つのアカウント（開発、ステージング、本番）に成長したら、不可欠になります。

**Amazon Inspector：脆弱性評価**

Macieを有効にして1週間後、Nimbusの本番フリート全体で実行されているバージョンのOpenSSLにCVEが公開されました。プリヤはコーヒーを飲みながらアドバイザリを読みました。

「どのインスタンスが影響を受けるか知る必要がある」と彼女は言いました。

「手動スキャンを実行できます」とレオは言いました。

「9インスタンスなら、まあいい。90なら？コンテナなら？」プリヤはInspectorのコンソールを開きました。「これがInspectorの目的です。」

**Amazon Inspector**は、自動化された脆弱性評価サービスです。GuardDutyが振る舞いを監視する—あなたのインフラが今何をしているか—のに対し、Inspectorは、悪用されうる存在するものを見ます。

- **EC2インスタンス**：Inspectorは、オペレーティングシステムとインストールされたパッケージを、NVD（National Vulnerability Database）—既知のCVEの権威あるカタログ—に照らしてスキャンします。OpenSSL 1.1.1を実行していて、CVEがそのバージョンを狙うなら、Inspectorはそれにフラグを立てます。
- **ECRコンテナイメージ**：Inspectorは、Elastic Container Registryのコンテナイメージを、デプロイされる前にスキャンします。ベースイメージの脆弱なパッケージは、コンテナが本番で実行される前にfindingとして現れます。
- **Lambda関数パッケージ**：Inspectorは、Lambda関数にバンドルされた依存関係—Pythonパッケージ、Nodeモジュール、Java依存関係—を既知の脆弱性について分析します。

1回限りのスキャンとの決定的な違い：Inspectorは**継続的に**実行されます。有効にしたときに一度インスタンスを確認してクリーンと宣言するだけではありません。新しいCVEが公開されると、Inspectorは新しい脆弱性に照らして既存のリソースを自動的に再評価します。EC2インスタンスが変わると—新しいパッケージがインストールされる、AMIが更新される—Inspectorはそれを再スキャンします。プリヤのEC2フリートは、Inspectorを有効にしてから数分以内にOpenSSLのCVEでフラグを立てられました。彼女がスキャンするよう頼んだからではなく、それがInspectorがすることだからです。

findingは深刻度評価されます：Critical、High、Medium、Low、Informational。GuardDutyとMacieのfindingと並んでSecurity Hubに流れます。1つのダッシュボード。3つすべてのレンズ。

「3インスタンスが影響を受けている」とレオは、Inspectorのfindingを読みながら言いました。「他の6つはパッチ適用済みのバージョンだ。」

「その3つを今週パッチして」とプリヤは言いました。

「コンテナイメージは?」

プリヤはInspectorのECRのfindingを見ました。彼らのコンテナレジストリの2つのベースイメージに既知の脆弱性がありました。その後パッチされたパッケージの古いバージョンです。彼女はそれらを再構築のためにタグ付けしました。

「重要なこと」とプリヤは言いました。「は、悪用される前にこれを見つけたことです。後ではなく。」

**3つのレンズのモデル**

GuardDuty、Inspector、Macieはそれぞれ異なるものを監視します。

- **GuardDuty**は振る舞いです。問います：*今、間違って見える何が起きているか？* 予期しない場所からのAPI呼び出し、コマンド・アンド・コントロールのサーバーに接続するEC2インスタンス、異常な時間に使われる認証情報。アクティブな脅威と異常を捕らえます。
- **Inspector**は構造です。問います：*悪用されうる何が私たちの環境に存在するか？* パッチされていないパッケージ、脆弱な依存関係、古いランタイム。攻撃を可能にする条件を捕らえます。
- **Macie**はデータについてです。問います：*あるべきでないどんな機密情報がS3バケットにあるか？* PII、財務記録、ファイルに残された認証情報。異常な振る舞いを生み出さない露出—間違った場所にあるデータだけ—を捕らえます。

既知のCVEを伴う侵害は、3つすべてに現れるかもしれません。Inspectorは攻撃の前に脆弱性にフラグを立てていたでしょう。GuardDutyは攻撃中の異常な振る舞いにフラグを立てるでしょう。MacieはそれがS3に着地した後、流出したデータにフラグを立てるでしょう。

3つの異なるレンズ、3つの異なる時間軸、どれも互いの代替ではありません。

**AWS Network Firewall：トラフィック検査機**

ツールボックスが閉じる前に、もう1つの専門家が言及に値します。セキュリティグループとNACL（第15章）は、IP、ポート、プロトコルでトラフィックをフィルターします。*誰が*何と話せるかは言えますが、会話の中を見られません。**AWS Network Firewall**は、VPCレベルでデプロイするマネージドでステートフルなファイアウォールです。ディープパケットインスペクションを実行します。ドメイン名でフィルター（`*.eatnimbus.com`とあなたのパッケージリポジトリにだけアウトバウンドを許可）、侵入シグネチャに一致するトラフィックをブロック（IDS/IPS、Suricataのルールと互換）、そしてポート番号が問題なく見えたためセキュリティグループが単に通すフローを検査します。

「つまり、頭脳を持つセキュリティグループだ」とレオは言いました。

「ファイアウォールベンダーから買うアプライアンスです」とプリヤは言いました。「ただし、マネージドで、自動スケールし、独自のサブネットにデプロイされて、VPCの出入りのすべてのトラフィックがそれを通ってルーティングされます。」

試験のシグナル：「ドメイン名またはペイロードでトラフィックを検査またはフィルター」「VPCの侵入検知/防止（IDS/IPS）」または「アウトバウンドトラフィックの中央集権的なエグレスフィルタリング」→Network Firewall。セキュリティグループとNACLは、ポートとIPによるインスタンスレベルとサブネットレベルの許可/拒否の答えです。Network Firewallは、トラフィックの*中*の検査を質問が要求するときの答えです。そして質問が、WAFルール、Shield Advanced、セキュリティグループ、*そして*Network Firewallのポリシーを多数のアカウントにわたって一貫して管理する方法を尋ねるなら—それが**AWS Firewall Manager**、その上のポリシー管理レイヤーです。

## 強みと限界

**AWS Shield**：

- Standard：無料で自動—使わない理由がない
- Advanced：注目度の高いターゲットに優れている。小さなチームには高価
- Standardはレイヤー3/4の攻撃（SYNフラッド、UDPフラッド、DNS増幅）を自動的に吸収する
- Advancedはレイヤー7の保護、リアルタイムの通知、Shield Response Teamを追加する

**AWS WAF**：

- マネージドルールグループはセットアップを大幅に簡素化する—数クリックでOWASP Top 10の保護
- カスタムルールはHTTP攻撃パターンの理解を必要とする
- レート制限はしばしば見過ごされる強力な機能—スクレイパーとブルートフォースに効果的
- WAFは安全なアプリケーションコードの代替ではない—多層防御のレイヤー
- Countモードで始め、検証し、それからBlockに切り替える

**GuardDuty**：

- 有効にするのが極めて低労力（数クリック、30日の無料トライアル）
- findingは人間のレビューと対応を必要とする—GuardDutyは検知し、修正しない
- 誤検知は起こる—一部の正当なアクティビティがMLモデルには異常に見える
- 深刻度レベル（低/中/高）が対応の優先順位付けを助ける
- 自動対応のワークフローのためにSecurity Hub、EventBridge、Lambdaと統合する

**Amazon Inspector**：

- 継続的で自動化された脆弱性スキャン—1回限りの確認ではない
- 新しいCVEが公開されるか、リソースが変わると自動的に再スキャンする
- EC2インスタンス（OSとアプリケーションパッケージ）、ECRコンテナイメージ、Lambda関数パッケージをカバーする
- findingはSecurity Hubに流れる。深刻度評価がパッチ適用の優先順位付けを助ける
- 攻撃をブロックしない—攻撃を可能にする条件を表面化する

**Amazon Macie**：

- S3の機密データ（PII、認証情報、財務データ）を自動的に発見する
- 異常な振る舞いのパターンを持たないデータの露出を捕らえる—GuardDutyは見逃すだろう
- 30日の無料トライアル。その後はバケットごと月ごとに支払い
- 多くのS3バケットとさまざまな機密レベルを持つチームに最も価値がある

**AWS Security Hub**：

- GuardDuty、Macie、Inspector、Config、Firewall Managerからのfindingを集約する
- 設定をセキュリティベンチマーク（CIS、NIST、PCI-DSS）に照らしてチェックする
- マルチアカウント規模で最も価値がある
- 1つのアカウントしかなくても早く有効にする—findingの履歴は累積的

## 概要

5つのサービス、5つのレイヤー。それぞれが異なる種類の脅威に対処し、どれも他の代替ではありません。DDoS攻撃はWAFとGuardDutyをバイパスします。SQLインジェクションの試みはShieldをバイパスします。ゆっくり注意深く使われる侵害された認証情報は、ShieldとWAFを完全にバイパスするかもしれません—しかしGuardDutyは異常を見ます。デバッグ用のS3バケットに顧客のPIIを誤ってアップロードする開発者は、3つすべてをバイパスします—しかしMacieがそれを捕らえます。

- **AWS Shield Standard**：無料で自動的なレイヤー3/4のDDoS保護。常にオン。50 GbpsのSYNフラッドを、Nimbusのロードバランサーに到達する前に吸収しました。
- **AWS Shield Advanced**：SRTアクセスとコスト保護を持つプレミアムなDDoS保護。エンタープライズのユースケース。
- **AWS WAF**：アプリケーション層のファイアウォール。HTTPリクエストを検査・フィルターします。CloudFront、ALB、またはAPI Gatewayにアタッチします。OWASP Top 10の保護のためにマネージドルールグループを使います。スクレイパー防御のためにレートベースルールを使います。
- **Amazon GuardDuty**：振る舞いの脅威検知。コアデータソース：CloudTrailイベント、VPCフローログ、DNSログ。オプションの拡張保護がS3イベント、EKS/ECS実行時監視、RDSログインイベント、Lambdaネットワークアクティビティを追加します。異常なアクティビティのために分類されたfindingを生成します。5つの主要なfindingタイプ：UnauthorizedAccess（コンソールログイン）、CryptoCurrency（マイニング）、Recon（ポート探り）、Trojan（C2トラフィック）、Policy（S3の設定ミス）。
- **Amazon Inspector**：自動化された脆弱性評価。EC2インスタンス、ECRコンテナイメージ、Lambda関数パッケージを既知のCVEについてスキャンします。継続的に実行され、新しい脆弱性が公開されると再評価します。findingはSecurity Hubに流れます。
- **Amazon Macie**：S3の機密データの発見。PII、認証情報、財務データを検知します。異常な振る舞いのパターンを持たない露出を捕らえます。
- **AWS Security Hub**：すべてのセキュリティサービスからのfindingを1つのダッシュボードに集約します。複数のアカウントにわたる中央集権的な監視を可能にします。
- **CloudTrail**：すべてのAWSセキュリティロギングの基盤。長期保持のためにS3に書き込むトレイルを有効にします。すべてのセキュリティサービスがそれから読みます。

## 試験のヒント

*SAA-C03 ドメイン：セキュアなアーキテクチャの設計（ドメイン1、タスク1.2）*

- **Shield Standard対Advanced**：Standardは無料で自動。Advancedはお金がかかり、SRT、コスト保護、より良い検知を追加します。Advancedの試験のシグナル：「大規模DDoS」「攻撃中のSLA保証」「DDoS関連のコスト急増に対する金銭的保護」。
- **WAFのユースケースのシグナル**：「SQLインジェクションをブロック」「クロスサイトスクリプティングをブロック」「API呼び出しのレート制限」「特定のuser-agentをブロック」「OWASP Top 10の保護」→WAF。
- **GuardDutyのシグナル**：「異常なAPIアクティビティを検知」「侵害された認証情報を特定」「異常なEC2のネットワーク接続にフラグを立てる」「脅威インテリジェンス」→GuardDuty。
- **WAFのアタッチ**：CloudFront（グローバル）、ALB（リージョナル）、API Gateway（リージョナル）、AppSyncにアタッチできます。
- **GuardDutyのデータソース**：3つのコアソース—CloudTrailイベント、VPCフローログ、DNSログ。拡張オプションソースにはS3データイベント、EKS監査ログ、RDSログインイベント、Lambdaネットワークアクティビティ、ECS実行時が含まれます。試験は、特定の検知シナリオにどのデータソースが関連するか尋ねるかもしれません：「異常なRDSログイン」→GuardDuty RDS Protection。「コンテナ実行時の脅威」→GuardDuty EKS/ECS Runtime Monitoring。
- **Macie対GuardDuty**：これは一般的な試験のおとりです。**Macie**はMLを使ってS3の機密データ（PII、認証情報、財務データ）を検知します。**GuardDuty**は振る舞いの脅威と異常を検知します。Macieは内容についてです。GuardDutyは振る舞いについてです。
- **Inspector対GuardDuty対Macie**：3つの異なるレンズ、どれも互いの代替ではありません。**Inspector** = 脆弱性スキャン—EC2インスタンス、ECRのコンテナイメージ、Lambda関数パッケージのCVE。継続的に実行され、新しいCVEが公開されると再スキャンします。**GuardDuty** = 振る舞いの脅威検知—今、異常に見える何が起きているか。**Macie** = S3の機密データの発見—あるべきでないPII、認証情報、財務データ。試験のトリガー：「EC2のパッチされていない脆弱性を特定」または「コンテナイメージをCVEについてスキャン」→Inspector。「異常なAPI呼び出しまたは侵害された認証情報を検知」→GuardDuty。「S3のPIIまたは機密データを見つける」→Macie。
- **Security Hub**：複数のサービスとアカウントからのセキュリティのfindingを集約します。試験シナリオ：「会社が複数のAWSアカウントを持ち、すべてのセキュリティのfindingの単一のビューを望む」→Security Hub。
- **WAFのレートベースルール**：時間ウィンドウ内のIPごとのリクエストを制限するのに使われます。Core Rule Set（攻撃パターンに一致する）とは異なります。試験は「ブルートフォースのログイン試行を防ぐ」または「スクレイピングを緩和する」のためにレートベースルールを使います。
- **CloudTrail + GuardDuty + Security Hub**：これら3つで一緒にAWSのセキュリティ可観測性のコアを形成します。まずCloudTrailを有効にし（GuardDutyとSecurity Hubがそれに依存します）、それからGuardDuty、それからfindingを集約するためにSecurity Hubです。

## 演習

**演習1—想起**

AWS WAFとAmazon GuardDutyの違いを説明してください。各サービスは何から保護し、それぞれどのレイヤーで動作しますか？

*（ヒント：WAFを受信リクエストへのフィルターとして、GuardDutyをあなたのログを監視する振る舞いのアナリストとして考えてみてください。）*

**演習2—SAA-C03シナリオ**

*シナリオ*：ある小売会社のウェブサイトが、彼らの製品検索APIに毎時数百万のリクエストを送るボットネットに狙われています。リクエストは正当に見えます（有効なUser-Agent文字列、有効なセッションクッキー）が、購入につながりません—製品価格をスクレイピングしています。攻撃は正当な顧客に遅い応答時間を経験させています。

この脅威に最もよく対処するサービスの組み合わせはどれですか？

A) レート制限ルールを持つAWS WAFとCloudFront
B) AWS Shield AdvancedとCloudFront
C) Amazon GuardDutyとAWS Shield Standard
D) ボットネットのIP範囲をブロックするネットワークACL

**ヒント1**：リクエストはHTTPレベル（アプリケーション層）です。どのサービスがHTTP層で動作しますか？

**ヒント2**：ボットネットは多くの異なるIPアドレスを使います—NACLレベルで特定のIP範囲をブロックすることは、大きなボットネットに対して効果がありません。

**ヒント3**：IPアドレスごとのレート制限は、完全にブロックできなくてもスクレイピングを遅くできます。

**解答**: A

**説明**：AWS WAFはIPアドレスごとにリクエストをレート制限でき、任意の単一のソースからの大量のスクレイピングの影響を減らします。CloudFrontは入ってくるトラフィックをAWSのエッジネットワーク全体に分散し、ボリュームを吸収してオリジンを保護します。WAFのルールはまた、リクエストパターン（同じAPIエンドポイントへの急速な連続したリクエスト）に一致してスクレイピングの振る舞いを特定できます。

**なぜBではないのか？** Shield AdvancedはDDoS洪水（レイヤー3/4）から保護します。シナリオはアプリケーション層のスクレイピング（レイヤー7のHTTPリクエスト）を説明していて、Shieldはそれを検査しません。

**なぜCではないのか？** GuardDutyはあなたのAWSアカウントの振る舞いの異常を検知します—受信HTTPリクエストをブロックしません。Shield Standardはアプリケーション層の攻撃を扱いません。

**なぜDではないのか？** 大きなボットネットは、分散したソースから何千ものIPアドレスを使います。特定の範囲をブロックすることは、洗練されたボットネットに対して失敗するもぐら叩きのアプローチです。

*SAA-C03 ドメイン：セキュアなアーキテクチャの設計—タスク1.2*

**演習3—アーキテクチャチャレンジ** *(オプション)*

Nimbusは、クレジットカードデータを扱う準備をする中で、脅威モデルを検討しています。PCI-DSSのコンプライアンスレビューが次を要求します。

- ネットワーク層のDDoS攻撃に対する保護
- 既知のWebエクスプロイトに対するアプリケーション層のフィルタリング
- すべてのAPI呼び出しの、改ざんが検知できる長期ストアへのロギング
- 支払いサービスへの異常なアクセスパターンの検知

各要件を特定のAWSサービスまたは設定にマッピングしてください。Shield Standardで十分ですか、それともPCI-DSSのコンテキストがAdvancedを示唆しますか？WAFをどこにアタッチしますか？

## クレジット後のシーン

GuardDutyが有効になりました。

48時間後、それは最初のfindingを生成しました：*「EC2インスタンスi-0abc123が既知のTor出口ノードと通信しています。」*

レオはインスタンスIDを見ました。

「それは内部の監視インスタンスだ」と彼は言いました。「ネットワーク診断を実行するためにセットアップしたやつ。」

「それはTor出口ノードと通信するはずなの?」

「いや。」彼は一拍置きました。「なぜそうするんだ?」

彼はインスタンスを開きました。誰かがそれにツールをインストールしていました。正当なオープンソースのネットワークスキャナーで、判明したところ、匿名化されたデータ収集のためにTorのインフラとも通信していました。

「つまり、ツールが呼び出していた」とプリヤは言いました。

「私の知らないうちに」とレオは確認しました。

「それはサプライチェーンのリスクです。あなたが承認しなかったことをする依存関係。」

レオはツールをアンインストールしました。彼は、インストールの前にすべてのサードパーティツールをレビューするプロセスをセットアップしました。

「これが今、私たちがいる被害妄想のレベル?」とマヤは尋ねました。

「ええ」とプリヤは言いました。

「これが、私たちが常にいるべきだったレベル?」とマヤは尋ねました。

「それもええ」とプリヤは言いました。
