**AWS Step Functions: ワークフローのオーケストレーション**

**AWS Step Functions**は、アプリケーションのステップを視覚的なワークフローとして連携させるサーバーレスオーケストレーションサービスです。各ステップは、**ステートマシン**内の**ステート**です。

トップからボトムへと実行されるPythonスクリプトではなく、ワークフローをJSON/YAMLステートマシンとして定義します。

```json
{
  "StartAt": "ValidateLicense",
  "States": {
    "ValidateLicense": {
      "Type": "Task",
      "Resource": "arn:aws:lambda:us-east-1:123456789012:function:validate-license",
      "Next": "ImportMenu",
      "Catch": [{"ErrorEquals": ["*"], "Next": "OnboardingFailed"}]
    },
    "ImportMenu": {
      "Type": "Task",
      "Resource": "arn:aws:lambda:us-east-1:123456789012:function:import-menu",
      "Next": "SetupPayments",
      "Retry": [{"ErrorEquals": ["*"], "MaxAttempts": 3, "IntervalSeconds": 5}]
    },
    ...
  }
}
```

各ステートは以下のことができます：

- **Lambda関数の実行**（最も一般的なパターン）
- **ECSタスクの実行**（長時間実行のワークに対して）
- **特定の時間またはイベントの待機**（外部の何かが起こるまでワークフローを一時停止）
- **条件に基づいてパスの選択**（if/elseロジック）
- **並行ブランチの実行**を同時に
- **失敗時の再試行**（設定可能なバックオフ付き）
- **エラーのキャッチ**とエラー処理ステートへのルーティング

Step Functionsはステートの実行を永続的に管理します。ステップ3が失敗した場合、実行はステップ3で一時停止します。コンソールで失敗した実行を検査し、問題を修正し、ステップ3から再開できます—ステップ1と2を繰り返すことなく。

**ステートタイプ：構成要素**

**タスク**: アクションの実行—Lambda関数の呼び出し、ECSタスクの開始、APIの呼び出し。実際の作業が行われる場所です。

**選択**: 入力データに基づいて条件でブランチを選択します。コード内のif/elseに似ています。

**並行**: 複数のブランチを同時に実行し、すべてが完了するのを待ちます。

**マッピング**: リスト内の各アイテムに状態のセットを適用します。レストランメニューのアイテム50個を並行して処理します。

**待機**: 指定された時間またはタイムスタンプまで待機します。スケジュールされた遅延に役立ちます。

**通過**: ワークを処理することなく入力から出力を渡します。データ変換とテストに使用されます。

**成功/失敗**: 実行を終了するターミナル状態です。

レストランオンボーディングのために、レオはワークフローを設計しました：

1. ライセンスの検証 (タスク → Lambda)
2. メニューのインポート (タスク → Lambda、3回の再試行付き)
3. 並行ブランチ：
   a. 支払い設定 (タスク → Lambda)
   b. IAMロールの作成 (タスク → Lambda)
4. ウェルカムメールの送信 (タスク → Lambda、並行ブランチの完了を待機)
5. セールスチームへの通知 (タスク → Lambda)

ステップ3aと3bは並行して実行されます—互いに依存せず、同時に実行することで時間を節約します。

**標準ワークフローとエクスプレスワークフロー**

Step Functionsは2種類のワークフロータイプを提供します：

**標準ワークフロー**:

- 最大実行時間：1年
- 実行は永続的—状態は保持され、検査および監査可能
- 最低1回の実行（各タスクは少なくとも1回実行されます）
- ステート遷移ごとに課金
- 長時間、重要なワークフロー（注文処理、オンボーディング、支払いフロー）に最適です。

**エクスプレスワークフロー**:

- 最大実行時間：5分
- 高いスループット—1秒あたり最大10万
- 最低1回または最大1回（構成可能）
- 実行時間ごとに課金（Lambdaと同じ）
- 高いボリューム、短時間のワークフロー（リアルタイムイベント処理、IoTデータインジェスト）に最適です。

Nimbusのレストランオンボーディングのために：標準（重要であり、持続可能であり、手動手順が関与する場合に数時間かかる可能性があります）。

Nimbusのリアルタイム注文ステータス更新のために：エクスプレス（高いボリューム、短時間、それほど重要ではありません）。

**イベント駆動型アーキテクチャ：より大きな絵**

Step Functionsはより大きなパターンである**イベント駆動型アーキテクチャ**の一部です。サービスは直接呼び出しをすることなく互いにイベントを送信します（結合を減らす）。

本の中で見たように：

- 注文の作成 → SNSがイベントを公開 → SQSキューが消費者に配信
- S3ファイルがアップロードされる → Lambdaがトリガーされる
- DynamoDBレコードが変更される → DynamoDBストリーム → Lambdaがキャッシュを更新

**Amazon EventBridge**（以前はCloudWatch Events）は、このパターン向けの高度なイベントバスです。AWSサービスと独自のアプリケーションからイベントをターゲット（Lambda、SQS、Step Functionsなど）にルーティングします。ルールに基づいて。

EventBridgeは、注文サービスが`order.placed`イベントを公開しても、誰がリスンしているかを知らなくても、アーキテクチャレベルで結合を減らすことを可能にします。アナリティクスサービス、通知サービス、ロイヤリティポイントサービスはすべて独立してリスンします。新しいリスンを追加しても、注文サービスを変更する必要はありません。

**Step Functionsが適切なツールである場合**

Step Functionsは、次の場合に最適です：

**複数のステップのワークフロー**が、ステップ間で進行状況を追跡する必要がある場合

**人間によるループのプロセス**—Step Functionsは、人間の承認のような外部イベントの待機を無限に待機し、その後続行できる

**大規模なエラー処理**—多くのステップにわたる組み込みの再試行、キャッチ、およびフォールバックロジック

**監査可能なプロセス**—すべての実行がすべてのステート遷移を記録します。何が起こったかを正確に把握できます。

**複雑な並行または順次ロジック**—視覚的なワークフローは、同等のコードよりも推論を容易にします。

Step Functionsは、単純な2ステップのプロセスには過剰です。調整自体が価値がある場合に、および失敗シナリオが重要な場合にのみ使用してください。

## 強みと限界

**Step Functionsが強力な理由**:

- 実行履歴の視覚化—ワークフローが（または失敗した）どこにあるかを確認できます
- 組み込みの再試行とエラー処理—カスタム再試行コードは不要
- 持続的な状態—実行はサービス再起動と障害をサバイブします
- 200以上のAWSサービスとの直接統合（Lambdaのみではありません）
- 視覚的なワークフローは自己文書化されます

**それが複雑になる場所**:

- 標準ワークフローは状態遷移に基づいて価格設定されます。複雑なワークフローで多くの状態がある場合、規模が大きくなるとコストがかさむ可能性があります。
- ASL（Amazon States Language）JSON形式には学習曲線があります。
- 最大ペイロードサイズは256KBです。大きなデータはワークフローを介して直接ではなく、S3参照を通じて渡す必要があります。
- 多くの手動ステップを持つ長時間のワークフローには、慎重なタイムアウト設定が必要です。

## 概要

- **Step Functions** は、ステートマシンとしてマルチステップワークフローをオーケストレーションします。
- 各**ステート**は、Lambda関数を実行したり、ECSタスクを実行したり、待機したり、分岐したり、並行ステップを実行したりできます。
- 各ステートには**リトライとキャッチ**が組み込まれています。カスタムリトライコードは必要ありません。
- **標準ワークフロー**: 長時間の実行（最大1年）、耐久性、少なくとも一度。重要なビジネスプロセスに使用します。
- **Expressワークフロー**: 短い期間（最大5分）、高スループット。高ボリュームのイベント処理に使用します。
- **イベント駆動型アーキテクチャ**は、SNS、SQS、Lambda、EventBridgeなどのサービスを使用して、直接呼び出しではなくイベントに基づいてシステムを疎結合にします。
- Step Functionsを使用し、ステップのコーディネーション自体が複雑で、監査可能性が重要な場合にのみ使用します。

## 試験のヒント

*SAA-C03 ドメイン：回復力のあるアーキテクチャの設計 (ドメイン 2、タスク 2.1)*

- **Step Functions のユースケースシグナル**: 「複数の Lambda 関数をオーケストレーションする」、「リトライとエラー処理を含むワークフロー」、「自動ワークフローにおける人間の承認ステップ」、「各ワークフローステップの監査証跡」→ Step Functions。
- **標準 vs Express**: 長時間の実行、監査可能性、ビジネスクリティカルなワークフローには標準を使用します。高スループット、短期間のイベント処理にはExpressを使用します。
- **SQS vs Step Functions**: SQS は、プロデューサー/コンシューマーの単純なタスクキューに使用します。Step Functions は、複雑なロジック、リトライ、ステート追跡を備えたマルチステップワークフローに使用します。
- **EventBridge のシグナル**: 「AWS サービスからのイベントをターゲットにルーティングする」、「サービス間のイベント駆動型統合」、「Lambda 関数のスケジュール設定」→ EventBridge (以前は CloudWatch Events)。
- **コールバックパターン**: Step Functions は、実行を一時停止し、外部のコールバック（タスクトークン）を待機できます。ワーカーは完了したときにコールバックを呼び出します。Lambda の 15 分の制限を回避するために、長時間実行される ECS タスクに使用されます。
- **直接 SDK 統合**: Step Functions は、Lambda を介さずに、DynamoDB、S3、SQS などの AWS サービスを直接呼び出すことができます。これは、単純なサービス呼び出しのコストとレイテンシを削減します。

## 練習問題

**練習問題 1 — 回想**

Step Functions がマルチステップワークフローに役立つ理由を説明してください。単純な Lambda 関数が他の Lambda 関数を呼び出す場合に提供するものとは何ですか？

**練習問題 2 — 試験練習**

*シナリオ*: 金融サービス会社は、ローン申請の複数のステップを処理します。これには、信用調査、所得確認、ドキュメント検証、 underwriters のレビュー（手動）、意思決定通知が含まれます。各ステップは数秒（信用調査）から数日（underwriters のレビュー）までかかる可能性があります。会社は、コンプライアンスのために、各ステップの完全な監査証跡が必要です。自動化されたステップが失敗した場合、自動的にリトライする必要があります。手動ステップは一時停止し、人間の決定を待つ必要があります。

これらの要件を満たすサービスはどれですか？

A) SQS キューの間で各ステップをチェーンにした AWS Lambda 関数
B) Step Functions の標準ワークフローで、underwriters のレビューステップで「待機」コールバックパターンを使用
C) Step Functions の Express ワークフローで、自動化されたステップと FIFO SQS を使用
D) EventBridge でイベントルールを使用して、各ステップの Lambda 関数間でイベントをルーティング

**ヒント 1**: 「数日」の期間—どの Step Functions タイプがこれをサポートしますか？

**ヒント 2**: 「人間の決定を待つ」—このパターンは、Step Functions でどのような目的で使用されますか？

**ヒント 3**: 「完全な監査証跡のためのコンプライアンス」—どのサービスが実行ごとのステート履歴を提供しますか？

**答え**: B

**説明**: Step Functions の標準ワークフローは、1 年までの実行時間までサポートし、数日かかる underwriters のレビューステップをサポートします。「待機」コールバックパターンは、underwriters のステップでタスクトークンを使用して実行を一時停止します。underwriters が決定を下すと、トークンを使用してワークフローを続行します。標準ワークフローは、各ステート遷移を記録し、コンプライアンスのための完全な監査証跡を提供します。

**A を選択しない理由**: Lambda を SQS キューでチェーンにすると、組み込みのステート追跡や監査証跡は提供されません。失敗したステップにはカスタムリトライロジックが必要です。特定の失敗したステップから再開するには、カスタム実装が必要です。

**C を選択しない理由**: Express ワークフローは、5 分の最大実行時間しか持たず、数日かかるステップには互換性がありません。

**D を選択しない理由**: EventBridge はイベントをルーティングしますが、ワークフローの状態を維持したり、組み込みのリトライ/監査機能を提供したりしません。EventBridge のみを使用する場合、カスタムステート管理が必要です。
