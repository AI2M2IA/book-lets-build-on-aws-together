**AWS Step Functions: ワークフローのオーケストレーション**

**AWS Step Functions** は、アプリケーションのステップを視覚的なワークフローとして調整するサーバーレスのオーケストレーションサービスです。各ステップは **ステートマシン (state machine)** の中の **状態 (state)** です。

上から下に実行されてクラッシュする Python スクリプトの代わりに、ワークフローを JSON/YAML のステートマシンとして定義します:

```json
{
  "StartAt": "ValidateLicense",
  "States": {
    "ValidateLicense": {
      "Type": "Task",
      "Resource": "arn:aws:lambda:us-west-2:123456789012:function:validate-license",
      "Next": "ImportMenu",
      "Catch": [{"ErrorEquals": ["States.ALL"], "Next": "OnboardingFailed"}]
    },
    "ImportMenu": {
      "Type": "Task",
      "Resource": "arn:aws:lambda:us-west-2:123456789012:function:import-menu",
      "Next": "SetupPayments",
      "Retry": [{"ErrorEquals": ["States.ALL"], "MaxAttempts": 3, "IntervalSeconds": 5}]
    },
    ...
  }
}
```

各状態は次のことができます:

- **Lambda 関数を実行する** (最も一般的なパターン)
- **ECS タスクを実行する** (より長時間の作業のために)
- **特定の時間** または **イベント** を待つ (外部で何かが起こるまでワークフローを一時停止する)
- 条件に基づいて **パスを選ぶ** (if/else ロジック)
- **並列のブランチを同時に実行する**
- 設定可能なバックオフで **失敗時にリトライする**
- **エラーを捕捉して** エラー処理の状態にルーティングする

Step Functions は実行状態を耐久的に管理します。ステップ3が失敗すると、実行はステップ3で一時停止します。コンソールで失敗した実行を調べ、問題を修正し、ステップ3から再開できます — ステップ1と2を繰り返すことなく。

リトライロジックを Lambda 関数の中に書けばいいのでは、と疑問に思うかもしれません。はい — しかし、そうすると、失敗の追跡、状態の永続化、監査ロギングもコードで書くことになります。そして7つのうちステップ3が失敗したとき、どのレストランが処理されていたか、その前に何が起きたか、どこから再開すべきかを知る必要があります。Step Functions はそのすべてを行います。

**Nimbus の注文フロー: 注釈付きステートマシン**

これは、Nimbus が注文確認のために構築した実際の Step Functions ステートマシンの簡略版です — 各部分が何をするかが分かるように注釈を付けています:

```json
{
  "Comment": "Nimbus order confirmation workflow",
  "StartAt": "ChargeCard",
  "States": {
    "ChargeCard": {
      "Type": "Task",
      "Resource": "arn:aws:lambda:us-west-2:123456789012:function:charge-card",
      "Next": "SendConfirmationEmail",
      "Retry": [
        {
          "ErrorEquals": ["PaymentRetryableError"],
          "MaxAttempts": 2,
          "IntervalSeconds": 3,
          "BackoffRate": 2.0
        }
      ],
      "Catch": [
        {
          "ErrorEquals": ["PaymentDeclinedError"],
          "Next": "NotifyCustomerOfDecline"
        },
        {
          "ErrorEquals": ["States.ALL"],
          "Next": "ChargeCardFailed"
        }
      ]
    },
    "SendConfirmationEmail": {
      "Type": "Task",
      "Resource": "arn:aws:lambda:us-west-2:123456789012:function:send-confirmation-email",
      "Next": "NotifyRestaurant",
      "Retry": [
        {
          "ErrorEquals": ["States.ALL"],
          "MaxAttempts": 3,
          "IntervalSeconds": 5
        }
      ]
    },
    "NotifyRestaurant": {
      "Type": "Task",
      "Resource": "arn:aws:lambda:us-west-2:123456789012:function:notify-restaurant",
      "Next": "UpdateInventory",
      "Retry": [
        {
          "ErrorEquals": ["States.ALL"],
          "MaxAttempts": 3,
          "IntervalSeconds": 10,
          "BackoffRate": 2.0
        }
      ],
      "Catch": [
        {
          "ErrorEquals": ["States.ALL"],
          "Next": "RestaurantNotificationFailed"
        }
      ]
    },
    "UpdateInventory": {
      "Type": "Task",
      "Resource": "arn:aws:lambda:us-west-2:123456789012:function:update-inventory",
      "Next": "LogTransaction",
      "Retry": [{"ErrorEquals": ["States.ALL"], "MaxAttempts": 2}]
    },
    "LogTransaction": {
      "Type": "Task",
      "Resource": "arn:aws:lambda:us-west-2:123456789012:function:log-transaction",
      "End": true
    },
    "NotifyCustomerOfDecline": {
      "Type": "Task",
      "Resource": "arn:aws:lambda:us-west-2:123456789012:function:notify-decline",
      "End": true
    },
    "ChargeCardFailed": {
      "Type": "Fail",
      "Error": "ChargeCardFailed",
      "Cause": "Card charge failed after retries"
    },
    "RestaurantNotificationFailed": {
      "Type": "Task",
      "Resource": "arn:aws:lambda:us-west-2:123456789012:function:alert-support",
      "Comment": "Alert support team — order charged but restaurant not notified",
      "End": true
    }
  }
}
```

いくつか注目すべき点があります:

**`ChargeCard` には2つの Catch 句があります。** ひとつは `PaymentDeclinedError` (既知の、予期される失敗 — カードが拒否されたのであって、システムエラーではない) のため、もうひとつは `States.ALL` (それ以外のすべて — システム障害、タイムアウト、予期しない例外) のためです。それらは異なることを意味するので、異なる状態にルーティングされます。

**`NotifyRestaurant` には `RestaurantNotificationFailed` にルーティングする Catch があります。** これが11件のインシデントを引き起こしたバグです。古い Python スクリプトには同等のものがありませんでした — 通知が失敗すると、関数は静かにクラッシュするか、エラーをログに記録して続行しました。Step Functions は失敗のパスを明示的にします: それは特定のどこかに行き、そのどこかが、誰かが電話をかけなければならなくなる前にサポートチームに警告します。

**すべての Task に Retry があります。** メールサービスに一時的なタイムアウトがあれば、自動的に、3回、増加するバックオフでリトライします。顧客はこれを決して見ません。注文は失われません。

**フローはスクリプトではなくグラフです。** `NotifyRestaurant` が (リトライ後に) 永続的に失敗すると、実行は `UpdateInventory` に続きません。ワークフローは `RestaurantNotificationFailed` で停止します。注文を知らないレストランのために在庫が更新されることはありません。これが正しい動作です。

「待って — でも *なぜ* 決済拒否とシステムエラーで別々の失敗パスが必要なの?」とマヤが尋ねました。

「まったく異なる対応を必要とするからだ」とレオが言いました。「拒否されたカードは、顧客にメールしてもう一度試すよう頼むことを意味する。課金関数のシステムエラーは、なぜ Lambda 関数が失敗しているのかをエンジニアが調査する必要があることを意味する。観察可能な結果は同じ — 注文が通らなかった — が、対処はまったく異なる。」

**状態のタイプ: 構成要素**

**Task**: アクションを実行する — Lambda 関数を呼ぶ、ECS タスクを開始する、API を呼ぶ。ここで実際の作業が起こります。

**Choice**: 入力データの条件に基づいて分岐する。コードの if/else のようなもの。

**Parallel**: 複数のブランチを同時に実行し、すべてが完了するのを待つ。

**Map**: リストの各項目に一連の状態を適用する。50のレストランメニュー項目を並列で処理する。

Nimbus がレストランのメニューをインポートするとき、メニューには8から200の項目が含まれ得ました。各項目について、インポートプロセスは次のことをする必要がありました: フォーマットを検証する、アレルゲンデータをチェックする、写真をリサイズする、レコードを DynamoDB に書き込む。

Map 状態がなければ、これは項目を順次処理する単一の Lambda になります — 200項目 × 項目あたり200ミリ秒 = 40秒の処理時間。Map 状態を使うと、Step Functions は処理状態の並行実行を起動し — 設定された同時実行制限まで — それらすべてが完了するのを待ちます。同じ200項目が5秒未満で終わります。

**Wait**: 指定された時間、またはタイムスタンプまで一時停止する。スケジュールされた遅延に役立ちます。

**Pass**: 作業をせずに入力を出力に渡す。データ変換とテストに使われます。

**Succeed/Fail**: 実行を終了する終端状態。

レストランのオンボーディングのために、レオはワークフローを設計しました:

1. ValidateLicense (Task → Lambda)
2. ImportMenu (Task → Lambda、3回のリトライ付き)
3. 並列ブランチ:
   a. SetupPayments (Task → Lambda)
   b. CreateIAMRole (Task → Lambda)
4. SendWelcomeEmail (Task → Lambda、並列の完了を待つ)
5. NotifySalesTeam (Task → Lambda)

ステップ3a と3b は並列で動きます — それらは互いに依存せず、同時に実行することで時間を節約します。

最初のレストランのコホートがオンボーディングを完了したあと、コンプライアンス要件が生まれました: レストランパートナーが稼働する前に、Nimbus のアカウントマネージャーがライセンス文書を手動でレビューして承認しなければならない。これには1〜3営業日かかり得ました。

「それで、もし誰かがそのウィンドウの間に侵入しようとしたら?」とプリヤが尋ねました。「レストランが部分的に設定されていて — 決済アカウントは作成されたがまだ承認されていない — 誰かがその保留状態を発見したら、その半開きの設定を悪用しようとできる。」

より実際的には: 人間を待つために Step Functions のワークフローを3日間どうやって一時停止しますか?

答えは **タスクトークンを使ったコールバックパターン** です。

`ValidateLicense` が動くとき、自動的に完了する代わりに、3つのことをする Lambda を呼び出します:

1. レストランの文書とともにアカウントマネージャーにメールを送る
2. **タスクトークン** (Step Functions がこの特定の実行と状態のために生成する一意の識別子) を、その保留中のレビューに関連付けてデータベースに記録する
3. `.waitForTaskToken` で Step Functions に戻る — これは Step Functions に、この状態で実行を無期限に一時停止するよう伝える

Step Functions は実行を駐車させます。他に何もブロックされません — 待っているサーバーはありません。ステートマシンはただ待ち、コンピュートリソースを消費しません。

3日後、アカウントマネージャーは内部の管理ツールで「承認」をクリックします。管理ツールはデータベースからタスクトークンを調べ、呼び出します:

```python
stepfunctions.send_task_success(
    taskToken=token,
    output=json.dumps({"approved": True, "reviewedBy": "dana.cole@eatnimbus.com"})
)
```

Step Functions が再開します。実行はステップ2 (`ImportMenu`) から続き、レビュアーの情報がワークフローの状態で利用可能になります。

「実行は3日間一時停止された」とレオが言いました。「そして承認したときに起きた唯一のことは、1回の API 呼び出しだった。」

「それで、もしアカウントマネージャーが拒否したら?」とマヤが尋ねました。

「代わりに `send_task_failure` を呼ぶ。ステートマシンがそれを捕捉し、レストランパートナーにメールする `NotifyRejection` 状態にルーティングする。」

Step Functions はポーリングしません。リトライしません。タイムアウトしません (ハートビートタイムアウトを設定しない限り)。それは単にコールバックが到着するまで待ち、それから続けます。これはデータベースやキューをポーリングすることとは根本的に異なります — そしてこれが、Step Functions が自動と手動のステップを混在させるワークフローによく適している理由です。

**標準 vs Express ワークフロー**

Step Functions は2つのワークフロータイプを提供します:

**標準ワークフロー (Standard workflows)**:

- 最大時間: 1年
- 実行は耐久的 — 状態は永続化され、調査と監査ができる
- Exactly-once 実行 (Retry を設定しない限り、タスクが2回以上実行されることはない)
- 状態遷移ごとの課金
- 長時間実行の重要なワークフロー (注文処理、オンボーディング、決済フロー) に最適

**Express ワークフロー (Express workflows)**:

- 最大時間: 5分
- より高いスループット — 1秒あたり最大100,000
- At-least-once 実行 (非同期) または at-most-once (同期) — タスクは冪等になるよう設計する
- 時間ごとの課金 (Lambda のように)
- 大量、短時間のワークフロー (リアルタイムイベント処理、IoT データ取り込み) に最適

「それは月にいくらかかるんだ?」と、料金ページを呼び出しながらトムが尋ねました。「標準では状態遷移ごと — ステップがたくさんあると積み重なる。」

レオは計算を説明しました。レストランのオンボーディングワークフロー (実行ごとに6つの Task 状態、月におよそ12〜15の新規レストラン) では: 100未満の状態遷移 — 1セント未満で、月4,000遷移の無料枠の中に完全に収まるので、実質0ドル。フル Nimbus トラフィックでの注文確認ワークフローでは: より意味のある額ですが、それでも月11件の部分的成功を手動でデバッグするコストよりずっと低いものです。

「デバッグの時間が隠れたコストだ」とレオが言いました。

「それはいつも隠れたコストだ」とトムが言いました。

トムはより慎重に数字を出しました。トムはそういう男だったからです。

**Nimbus の注文確認フローの標準ワークフローのコスト**: ハッピーパスで注文あたり5つの状態、状態遷移あたり0.000025ドル。5つの状態遷移 × 0.000025ドル × 月15,000注文 = **月1.88ドル**。注文量が10倍で: 月約19ドル。1件の部分的成功インシデントのデバッグコスト (サポートエンジニアの24分) は、月の Step Functions の請求を何倍も超えました。

この比較は、誰かが高頻度のアナリティクスイベントに標準ワークフローを使うことを提案したときに重要になります。Nimbus が、すべての生のクリックストリームイベント — すべてのメニューページビュー、すべてのスクロール、すべての検索 — を処理するために Step Functions を使いたいとしましょう。それは現在の規模でおよそ1日80万イベントです。各イベントの5状態の標準ワークフロー: 800,000 × 5 × 0.000025ドル × 30日 = **月3,000ドル**。それはアナリティクスパイプラインにとって本物のお金です。

同じボリュームの Express ワークフロー: 状態遷移ごとではなく、リクエストごと + 時間ごとの課金。月2,400万の実行は、100万リクエストあたり1.00ドル = 24ドル。時間: 2,400万 × 500ミリ秒、64MB の課金最小値で ≈ 208 GB 時間 × 0.06ドル = 12.50ドル。合計 ≈ **月36.50ドル** — 標準の3,000ドルよりほぼ2桁安いものです。

「つまりワークフローのタイプは単にアーキテクチャ上の決定ではない」とトムが言いました。「コストの決定だ。同じ数の状態でも、どのワークフロータイプを使うかによって、ほぼ100倍もコストが違い得る。」

「そしてどちらが良いかは、ワークフローが何をするかに完全に依存する」とレオが言いました。「注文確認: 標準。それは重要で、意味のある失敗パスがあり、監査証跡が欲しい。アナリティクスイベント処理: Express。それは大量で、短時間で、すべてのページビューに90日の実行履歴は必要ない。」

プロセスが2つのステップで、監査証跡が必要ないなら、単純な Lambda 関数のほうが安く、JSON のステートマシン構文も不要です — しかし、どのステップも独立して失敗し得て、以前のステップを繰り返さずにリトライや再開が必要なら、Step Functions はデバッグと手動の対処の削減で元が取れます。

Nimbus のレストランオンボーディングには: 標準 (それは重要で、耐久的で、手動ステップが関わると数時間かかり得る)。

Nimbus のリアルタイム注文ステータス更新には: Express (大量、短時間、重要度が低い)。

**イベント駆動アーキテクチャ: より大きな絵**

Step Functions はより大きなパターンの一片です: **イベント駆動アーキテクチャ (event-driven architecture)**。サービスが互いを直接呼び出す (密結合) 代わりに、サービスはイベントを発行し、他のサービスがそれらのイベントに反応します。

私たちはこれを本書を通して見てきました:

- 注文が行われる → SNS がイベントを発行 → SQS キューがコンシューマーに配信
- S3 ファイルがアップロードされる → Lambda がトリガーされて処理
- DynamoDB のレコードが変更される → DynamoDB Streams → Lambda がキャッシュを更新

**Amazon EventBridge** (旧 CloudWatch Events) は、このパターンのための高度なイベントバスです。AWS サービスや自分のアプリケーションからのイベントを、ルールに基づいてターゲット (Lambda、SQS、Step Functions など) にルーティングします。

EventBridge はアーキテクチャレベルでの疎結合を可能にします: 注文サービスは、誰が聴いているかを知らずに `order.placed` イベントを発行します。アナリティクスサービス、通知サービス、ロイヤルティポイントサービスはすべて独立して聴きます。新しいリスナーを追加しても、注文サービスを変更する必要はありません。

EventBridge はまた、何十もの AWS サービスと **イベントソース** としてネイティブに統合します。CloudTrail の API 呼び出しがパターンに一致すると、EventBridge はルールを発火できます。EC2 インスタンスが状態を変えると、EventBridge は Lambda をトリガーできます。RDS インスタンスがフェイルオーバーすると、EventBridge はオンコールのエンジニアに警告できます。AWS のコントロールプレーン全体をイベントストリームとして扱えます。

Nimbus にとって、特に有用な EventBridge のルール: 新しいイメージが ECR にプッシュされるたびに Lambda をトリガーする。Lambda はイメージのスキャン結果をチェックし、HIGH または CRITICAL の CVE が見つかれば、誰かがイメージをデプロイする前にエンジニアリングの Slack チャンネルに投稿します。これは ECR のセキュリティスキャン (第21章から) を EventBridge のイベントルーティングと組み合わせて、自動化されたセキュリティゲートにします。

イベント駆動アーキテクチャの原則は、Step Functions のリトライロジックと同じです: 失敗を、静かに飲み込むのではなく、明示的でルーティングされたものにすること。イベントを通じて通信するサービスは優雅に失敗します — `OrderConfirmed` イベントが発火したときにロイヤルティポイントの Lambda がダウンしていれば、EventBridge は配信をリトライしたり、デッドレターキューに送ったりできます。注文確認そのものは影響を受けません。疎結合が回復力なのです。

**EventBridge: 副作用をメインフローから切り離す**

注文確認のステートマシンがきれいに動くようになったあと、マヤが次のアーキテクチャレビューで疑問を提起しました。

「注文が確認されたときにロイヤルティポイントを追加したいの。顧客は1ドル使うごとに1ポイントもらう。それはステートマシンのどこに入るの?」

レオの最初の本能: `LogTransaction` のあとに `GrantLoyaltyPoints` 状態を追加する。

プリヤの応答: 「それで、紹介ボーナスを追加するときは? 注文後のアンケートは? レストランの評価リクエストは? それぞれがクリティカルパスに状態を追加する。ロイヤルティポイントの Lambda が失敗すれば、注文確認全体が失敗する。」

「注文確認のフローは1つのことをすべき」と彼女は言いました。「注文を確認すること。それ以外のすべては副作用よ。」

これが、メインのワークフローから副作用を疎結合するメカニズムとしての **Amazon EventBridge** に対するアーキテクチャ上の論拠です。

改訂されたアプローチ: `LogTransaction` 状態が正常に完了すると、Lambda は EventBridge にイベントを発行します:

```json
{
  "source": "nimbus.orders",
  "detail-type": "OrderConfirmed",
  "detail": {
    "orderId": "ORD-8812",
    "customerId": "CUST-441",
    "restaurantId": "94",
    "total": 3200,
    "timestamp": "2024-03-15T14:23:43Z"
  }
}
```

それから EventBridge のルールが、そのイベントを独立したターゲットにルーティングします:

- **ルール1**: `OrderConfirmed` → ロイヤルティポイント Lambda (32ドルの注文に32ポイント付与)
- **ルール2**: `OrderConfirmed` → 注文後アンケート Lambda (配達の2時間後にアンケートをキューに入れる)
- **ルール3**: `OrderConfirmed` → アナリティクス Kinesis ストリーム (リアルタイムダッシュボードに供給)

各ルールは独立しています。ロイヤルティポイント Lambda は、アンケートキューに影響を与えずに失敗できます。アナリティクスパイプラインは、ロイヤルティシステムをブロックせずに遅れることができます。新しい副作用 (レストラン評価リクエスト、キャッシュバック通知) を追加するには、新しい EventBridge のルールを作成する必要があります — ステートマシンを変更するのではなく。

「それで、もし誰かが EventBridge のルールを通じて侵入しようとしたら?」とプリヤが尋ねました。「イベントが顧客の PII を含んでいたら、それを受け取るすべての Lambda がいまや PII のアクセスポイントになる。」

イベントは慎重に設計されていました: ID だけで、名前、住所、決済の詳細はありません。顧客データを必要とする Lambda は、顧客 ID を使ってデータベースから調べます — 自分自身の IAM 権限が、何にアクセスできるかを制御します。

「イベントはシグナルよ」とプリヤが言いました。「データのダンプではない。」

**Step Functions が正しいツールであるとき**

Step Functions が優れているのは、次がある場合です:

**ステップにまたがって進捗を追跡する必要のあるマルチステップワークフロー**

**人間が介在するプロセス** — Step Functions は外部イベント (人間が何かを承認するなど) を無期限に待ち、それから続けられます

**規模でのエラー処理** — 多くのステップにまたがる、組み込みのリトライ、キャッチ、フォールバックのロジック

**監査可能なプロセス** — すべての実行がすべての状態遷移を記録します。何がいつ起きたかを正確に見られます。

**複雑な並列または順次のロジック** — 視覚的なワークフローは、同等のコードより推論しやすくします

Step Functions は単純な2ステップのプロセスにはやり過ぎです。調整そのものが価値があり、失敗のシナリオが重要なときに使います。

**Step Functions が間違ったツールであるとき**

「待って — でも *なぜ* すべてに Step Functions を使わないの?」と、設計セッションの終わりにマヤが尋ねました。「レストランオンボーディングのワークフローを構築した。注文確認のフローもある。なぜすべてをステートマシンに変換しないの?」

正直な答え: Step Functions は、すべてのワークフローが正当化するわけではないオーバーヘッドを追加するからです。

**単純な2ステップのプロセス**: アップロードされたファイルを2つ目の Lambda を呼び出して処理する Lambda があるなら、ステートマシンの調整のオーバーヘッドは運用上の利益に見合いません。単一の関数内で順次呼び出される2つの Lambda のほうがシンプルで、テストしやすく、状態遷移ごとのコストもありません。

**超高頻度、サブ秒のワークフロー**: 標準ワークフローには、大量では積み重なる無視できない状態遷移ごとのコストがあります (上のアナリティクスの例が示したように)。Express ワークフローはコストの問題を解決しますが、耐久的な状態履歴を提供しません。非常に高頻度で非常に短時間なら、SQS + Lambda (第19章のパターン) のほうが、どちらの Step Functions タイプよりもシンプルで安価です。

**調整のない純粋なファンアウト**: 同じイベントを20のコンシューマーに送る必要があり、それぞれの結果を気にしないなら、SNS がツールです。Step Functions は、必要のない状態追跡を追加し、不必要に課金されます。

**リアルタイムの同期的なユーザーインタラクション**: Step Functions の実行は非同期です。ユーザーがチェックアウト画面で500ミリ秒未満の同期的な応答を待っているなら、Step Functions 標準ワークフローはこれのために設計されていません (Express ワークフローは同期的に呼び出せますが、レイテンシのオーバーヘッドは依然として直接の Lambda 呼び出しより高いです)。同期的なユーザー向けのフローには、よく設計されたエラー処理を備えた Lambda + API Gateway のほうがしばしば適切です。

原則: ステップの *調整* そのものが複雑なとき — ステップが独立して失敗し得るとき、以前のステップを繰り返さずに個々のステップをリトライする必要があるとき、実行履歴にコンプライアンスやデバッグの価値があるとき、またはワークフローが何日もかかり得る人間の承認ステップを含むとき — に Step Functions を使います。単一の関数としてうまく動く単純な順次ロジックにオーケストレーションのオーバーヘッドを追加するために使わないでください。

## 強みと限界

**なぜ Step Functions が強力なのか**:

- 視覚的な実行履歴 — ワークフローがどこにあるか (または失敗したか) を正確に見られる
- 組み込みのリトライとエラー処理 — カスタムのリトライコードなし
- 耐久的な状態 — 実行はサービスの再起動と障害を生き延びる
- 200以上の AWS サービスとの直接統合 (Lambda だけでなく)
- 視覚的なワークフローは自己文書化される
- コールバックパターンにより、コンピュートを消費せずに人間のアクションを無期限に待てる

**複雑になるところ**:

- 標準ワークフローは状態遷移ごとに課金される — 多くの状態を持つ複雑なワークフローは規模で高価になり得る
- ASL (Amazon States Language) の JSON フォーマットには学習曲線がある
- 最大ペイロードサイズは256KB — 大きなデータはワークフローを直接通すのではなく、S3 参照経由で渡さなければならない
- 多くの手動ステップを持つ長時間実行のワークフローには、慎重なタイムアウト設定が必要
- ASL のエラーのデバッグには実行を動かすことが必要。実サービスほど高機能なローカルエミュレーターはない
- ステートマシンが呼ぶ各リソースに IAM 権限を別々に付与しなければならない — 1つの権限を忘れると、実行時に紛らわしいエラーが起きる

## 概要

第21章のコンテナはデプロイを信頼できるものにしました。Step Functions はマルチステップのビジネスプロセスを信頼できるものにします — 「引き継ぎのリスクを排除する」という同じ原則をアプリケーションロジックに適用したものです。

- **Step Functions** はマルチステップのワークフローをステートマシンとしてオーケストレーションします。
- 各 **状態** は Lambda 関数を実行したり、ECS タスクを実行したり、待ったり、分岐したり、並列ステップを実行したりできます。
- **リトライとキャッチ** が各状態に組み込まれています — カスタムのリトライコードは不要です。
- **標準ワークフロー**: 長時間実行 (最大1年)、耐久的、exactly-once。重要なビジネスプロセスのために。
- **Express ワークフロー**: 短時間 (最大5分)、高スループット。大量のイベント処理のために。
- **タスクトークンを使ったコールバックパターン**: 外部イベントや人間のアクションを待ってワークフローを無期限に一時停止し、1回の API 呼び出しで再開する。
- **Map 状態**: 項目のリストを並行して処理する — 順次ループを並列のファンアウトで置き換える。
- **直接 SDK 統合**: Lambda のラッパーなしで、DynamoDB、S3、SQS、200以上の AWS サービスを状態から直接呼び出す。
- **EventBridge**: 副作用をメインのワークフローから切り離す — 単一のイベントを発行し、独立したルールに、コアのステートマシンを変更せずにそれをロイヤルティポイント、アナリティクス、アンケートのサービスにルーティングさせる。
- **標準 vs Express のコスト**: 状態遷移あたり0.000025ドルの標準は、低ボリュームの重要なワークフローにうまく機能します (Nimbus の注文確認で月1.88ドル)。リクエスト + 時間ごとの課金の Express は、標準なら何十倍もかかる高頻度イベント (Nimbus のクリックストリームの計算で約80倍) に適切です。
- **イベント駆動アーキテクチャ** は、SNS、SQS、Lambda、EventBridge のようなサービスを使って、直接呼び出しではなくイベントを中心にシステムを疎結合します。
- ステップの調整そのものが複雑なとき、そして監査可能性が重要なときに Step Functions を使います。単純な2ステップのシーケンス、超高頻度のワークフロー、純粋なファンアウト、同期的なユーザー向けのフローには使わないでください。

## 試験のヒント

*SAA-C03 ドメイン: 回復力のあるアーキテクチャの設計 (ドメイン2、タスク2.1)*

- **Step Functions のユースケースのシグナル**: 「複数の Lambda 関数をオーケストレーション」「リトライとエラー処理を伴うワークフロー」「自動化されたワークフローの中の人間の承認ステップ」「各ワークフローステップの監査証跡」 → Step Functions。
- **標準 vs Express**: 長時間実行の、監査可能な、ビジネスクリティカルなワークフローには標準。高スループット、短時間のイベント処理には Express。
- **SQS vs Step Functions**: 単純なタスクキュー (プロデューサー/コンシューマー) には SQS。複雑なロジック、リトライ、状態追跡を伴うマルチステップのワークフローには Step Functions。
- **EventBridge のシグナル**: 「AWS サービスからターゲットにイベントをルーティング」「サービス間のイベント駆動の統合」「Lambda 関数をスケジュール」 → EventBridge (旧 CloudWatch Events)。
- **コールバックパターン**: Step Functions は実行を一時停止し、外部のコールバック (タスクトークン) を待てます。ワーカーは完了したらコールバックします。Lambda の15分の制限を望まない長時間実行の ECS タスクに役立ちます。
- **直接 SDK 統合**: Step Functions は Lambda を経由せずに AWS サービス (DynamoDB、S3、SQS など) を直接呼び出せます。単純なサービス呼び出しのコストとレイテンシを削減します。たとえば、注文レコードを DynamoDB に書き込むことは、Lambda 関数なしでステートマシンからの直接 SDK 呼び出しにできます: `"Resource": "arn:aws:states:::dynamodb:putItem"`。これは Lambda のコールドスタート、Lambda の実行コスト、そして単に `dynamodb.put_item(...)` を呼んで返すだけのコードを排除します。

## 練習問題

**練習問題1 — 想起**

Step Functions がマルチステップのワークフローに有用な理由を説明してください。他の Lambda 関数を呼び出す単純な Lambda 関数が提供しないものを、それは何を提供しますか?

*(ヒント: 各アプローチで5つのうちステップ3が失敗したとき何が起こるかを考えてみてください。何が起きたかをどう知りますか? ステップ3だけをどうリトライしますか?)*

**練習問題2 — SAA-C03 シナリオ**

*シナリオ*: ある金融サービス会社が、ローン申請を複数のステップで処理します: 信用調査、収入確認、文書検証、引受人レビュー (手動)、決定通知。各ステップは数秒 (信用調査) から数日 (引受人レビュー) のどこかでかかり得ます。会社はコンプライアンスのためにすべてのステップの完全な監査証跡を必要とします。失敗した自動ステップは自動的にリトライしなければなりません。手動ステップは一時停止して人間の決定を待たなければなりません。

これらの要件を最も満たすサービスはどれですか?

A) 各ステップの間に SQS キューを挟んで連鎖させた AWS Lambda 関数  
B) 引受人レビューのステップに Wait for callback パターンを使った AWS Step Functions 標準ワークフロー  
C) 自動ステップに AWS Step Functions Express ワークフロー、手動ステップに SQS FIFO  
D) 各ステップの Lambda 関数間でルーティングするイベントルールを持つ Amazon EventBridge

**ヒント1**: 「最大数日」の時間 — どの Step Functions タイプがこれをサポートしますか?

**ヒント2**: 「人間の決定を待つ」 — どの Step Functions パターンがこれのために設計されていますか?

**ヒント3**: 「コンプライアンスのための完全な監査証跡」 — どのサービスが実行ごとの状態履歴を提供しますか?

**解答**: B

**説明**: Step Functions 標準ワークフローは最大1年実行でき、数日かかる引受人レビューのステップをサポートします。Wait for callback パターンは、タスクトークンで引受人のステップで実行を一時停止します。引受人が決定を下すと、トークンでコールバックしてワークフローを続けます。標準ワークフローはすべての状態遷移を記録します — コンプライアンスのための完全な監査証跡です。

**なぜ A ではないのか?** SQS 経由で連鎖した Lambda は、組み込みの状態追跡や監査証跡を提供しません。失敗したステップにはカスタムのリトライロジックが必要です。特定の失敗したステップからの再開にはカスタム実装が必要です。

**なぜ C ではないのか?** Express ワークフローは最大5分の時間です — 数日かかり得るステップとは互換性がありません。

**なぜ D ではないのか?** EventBridge はサービス間でイベントをルーティングしますが、ワークフローの状態を維持したり、組み込みのリトライ/監査を提供したりしません。これを EventBridge だけで構築するにはカスタムの状態管理が必要です。
