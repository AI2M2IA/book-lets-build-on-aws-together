**AWSがデータ転送にどう課金するか**

AWSのデータ転送の価格設定は非対称です。

**AWSへ（インバウンド）**：無料。好きなだけデータをアップロードできます。

**AWSからインターネットへ（アウトバウンド）**：課金される。最初の100GB/月は無料。その後：

- 最初の10TB/月は$0.09/GB（米国リージョン）
- 次の40TBは$0.085/GB
- より大きなボリュームではより低く

**同一アベイラビリティーゾーン内**：無料。同じAZで互いに話すEC2インスタンスは何も払いません。

**アベイラビリティーゾーン間（同一リージョン）**：各方向$0.01/GB。小さいが現実のコスト。

**リージョン間**：リージョンに応じて$0.02〜0.08/GB。クロスリージョンのトラフィックは大幅に高価です。

**NAT Gateway**：処理で$0.045/GB。プライベートEC2インスタンスがインターネットに到達するためにNAT Gateway経由で送るすべてのバイト——そして戻ってくるすべてのバイト——が課金されます。

**CloudFront**：直接のAWSからインターネットより低いデータ転送レート。最初の10TBは$0.085/GB（直接のデータ転送アウトよりわずかに少ない）。CloudFrontはしばしば合計の転送コストを減らします。エッジキャッシングにより、オリジンがデータを提供する頻度が減るからです。

**PrivateLinkの計算：それが意味を持つとき**

アーキテクチャが成長するにつれて出てくる、この会話のもっと複雑なバージョンがあります：他のAWS顧客がホストするサービス（あるいは他のVPCの自分自身のサービス）へのプライベートな接続を提供するためにAWS PrivateLinkを使うことです。

PrivateLink Interface Endpointは、AZあたり$0.01/時間プラス$0.01/GBかかります。エンドポイント経由で月1TBのトラフィックを生むサービスの場合：

- PrivateLinkのコスト：$0.01 × 2 AZ × 730時間 + $0.01 × 1,000GB = $14.60 + $10 = $24.60/月
- 代わりに同じトラフィックを既存のNAT Gateway経由でルーティングする：$0.045 × 1,000GB = 増分の処理料金で$45/月

比較は*増分*です。なぜなら、どちらにしてもNAT Gatewayは残るからです——それは依然として残りのインターネット向けトラフィックを処理するので、この1つのサービスがエンドポイントに移ってもその時間あたりのコスト（$0.045 × 2 × 730 = $65.70）は消えません。このトラフィックボリュームでは、PrivateLinkはおよそ月$20節約します。損益分岐点はおよそ420GB/月です——それを下回ると、NAT処理に対するGBあたりの節約より、エンドポイント自身の時間あたりのコストが上回ります。

「待って——でも*なぜ*VPNやピアリングではなくPrivateLinkを使うの？」とマヤが尋ねました。

「VPCピアリングはよりシンプルで、リージョン内転送は無料だ」とトムは言いました。「でもピアリングはVPC間に完全にルーティングされた接続を作る——VPC Aの何かが、VPC Bの何にでも潜在的に到達できる。PrivateLinkはより外科的だ。エンドポイントは、完全なネットワークルートではなく、特定のサービスを公開する。セキュリティを意識したアーキテクチャでは、その特定性が重要だ。」

「もし誰かがピアリングされたVPCに侵入しようとしたら？」とプリヤが尋ねました。「完全なピアリングは、1つのVPCの侵害されたインスタンスが、ピアリングされたVPCのすべてのインスタンスへのルートを持つことを意味する。」

「それが、サードパーティのサービスや別のチームが所有するサービスに接続するときの、ピアリングよりPrivateLinkを選ぶ論拠だ」とトムは言いました。「信頼された社内VPCにはピアリング。最小露出の接続が欲しいものにはPrivateLink。」

**クロスAZトラフィック：アーキテクチャの問い**

クロスAZデータ転送の$178/月は、もっと厄介でした。

その一部は避けられませんでした：ロードバランサーはトラフィックをAZ間に分散するので、一部のリクエストは1つのAZで発生し、ロードバランサーはそれを別のAZのインスタンスに転送します。

その一部は最適化可能でした：アプリケーションはRDSプライマリ（us-west-2a）に書き込み、リードレプリカ（us-west-2b）から読むよう構成されていました。すべての読み取りクエリがAZの境界を越えていました。

読み取りについて、1つの解決策：リクエストするインスタンスと同じAZのリードレプリカを優先するようアプリケーションを構成する。各AZが独自のリードレプリカを持つ。トラフィックはローカルに留まる。

**S3 Select：クエリでのデータ転送を減らす**

分析パイプラインをレビューしている間に、トムは、分析チームが大きなS3ファイルをどうクエリしているかに固有の、もう1つの最適化を見つけました。

パターン：毎朝、分析ジョブがS3から500MBのParquetファイルをダウンロードし、レストラン固有の注文データのためにメモリ内でフィルタしていました。ファイルのおよそ95%が、ダウンロード後に捨てられていました。

**S3 Select**は、ファイル全体をダウンロードしてアプリケーションでフィルタするのではなく、S3オブジェクト（CSV、JSON、Parquet）から必要な行と列だけを取得できるようにします。

> **重要な更新**：2024年半ば、AWSは新規顧客へのS3 Selectの提供をやめました——既存のユーザーは保持しますが、新しいアーキテクチャには行き止まりです。このセクションが教える原則（ストレージ層でフィルタし、ファイル全体を送らない）は普遍的です。そのための現代のツールは**Amazon Athena**です（S3に対して直接SQL、S3 Selectには決してなかった結合や集計を含む）。かつてもう1つの代替だった**S3 Object Lambda**は、S3 Selectに続いてレガシーの地位になりました：2025年11月7日時点で、それも新規顧客には閉ざされています（既存のワークロードは動き続けます）。現在の試験では、「S3上で所定の場所でデータをクエリする」はAthenaを指します。以下の話は、*推論*——まず測定し、フィルタをデータに移す——が教訓なので、保存されています。

S3 Selectなし：

**CloudFront：データ転送の割引**

ここに直感に反する事実があります：CloudFront経由でデータを提供することは、一般にEC2やS3から直接提供するより安いのです。

**EC2からインターネットへ直接**：$0.09/GB
**CloudFrontからインターネットへ**：$0.085/GB（わずかに安い）

しかし本当の節約はGBあたりのレートではありません——CloudFrontがエッジロケーションにデータをキャッシュすることです。1,000人のユーザーが同じメニュー写真をリクエストすると：

- **CloudFrontなし**：1,000のリクエストがS3から直接インターネットに出ていく × 写真サイズ × $0.09/GB
- **CloudFrontあり**：クライアントはエッジからCloudFrontのレート（$0.085/GB）で写真を得て、キャッシュフィル——1回のミスでCloudFrontがS3から取得すること——は**無料**（AWSはオリジンからCloudFrontへの転送を免除する。オリジンのGETリクエストだけ払う）

83%のキャッシュヒット率（第13章より）を持つニンバスでは、リクエストの83%がオリジンに一切触れませんでした——より少ないオリジンリクエスト、より少ないオリジン負荷、そしてすべてのバイトがS3のインターネットレートではなくエッジレートで課金されました。

「CloudFrontはパフォーマンスのためのCDNだけじゃない」とトムは言いました。「データ転送のコスト最適化でもある。」

「そのとおり。ユーザーがAWSからダウンロードしているなら、CloudFront経由にすべきだ。」

## 強みと限界

**NAT Gatewayのコスト**：

- NAT Gateway経由の大きなデータ量は素早く積み重なる
- VPCエンドポイントは一部のNATコストを完全に排除する
- プライベートインスタンスがどのサービスを呼び出すか、エンドポイントが利用可能かをレビューする

**コストのためのCloudFront**：

- キャッシュヒット率がコストの節約を直接決める
- 高いキャッシュヒット率 ＝ より少ないオリジンリクエストとより少ないオリジン負荷、加えてCloudFrontのより安いビューワー側のレートで課金されるより多くのバイト（AWSオリジンからCloudFrontへの転送は一切課金されない）
- すべての静的アセットの配信をCloudFront経由に移す

**クロスAZのトレードオフ**：

- クロスAZトラフィックをなくすには、たいてい節約より高くつくアーキテクチャの変更が必要
- 最適化する前に慎重に計算する

**S3 Select**（レガシー——2024年以来新規顧客には利用不可、代わりにAthenaを使う。S3 Object Lambdaも今やレガシー——2025年11月時点で新規顧客には閉ざされ、既存のワークロードは影響を受けない）：

- 原則は変わらない：大きなS3オブジェクトをダウンロードする代わりにストレージ層でフィルタする——節約はコンピュート時間、インスタンスサイズ、ジョブの長さに現れる（同一リージョンのS3転送はすでに無料）
- ファイル全体が必要なときは役立たない

## 概要

トムは、ホワイトボードの数字と、請求書の最後の未知数が実際に何だったかについてのより明確な理解とともに、ネットワーク分析を締めくくりました。ネットワークコストの$847/月は、無能のミステリーではありませんでした——それは、アベイラビリティーゾーンにまたがり、グローバルなユーザーに提供し、リージョンをまたいでデータをレプリケートする分散システムの、予想されるコストでした。そのほとんどは払う価値がありました。一部はそうではありませんでした。重要な前進は、どちらがどちらかを見分けられるようになったことでした。

- AWSは**アウトバウンドデータ**（インターネット：約$0.09/GB）、**クロスAZトラフィック**（各方向$0.01/GB）、**クロスリージョントラフィック**（$0.02〜0.08/GB）、**NAT Gateway処理**（$0.045/GB）に課金します。
- **インバウンドデータ**は無料です。**同一AZのトラフィック**は無料です。
- **VPC Flow Logs**は、VPC内のどの特定のトラフィックフローが各カテゴリのコストを生んでいるかを明らかにします——的を絞った最適化に不可欠です。VPCのネットワークインターフェイスを決して越えないフロー（CloudFrontがS3オリジンから取得するような）には、独自の計器が必要です：CloudFront標準ログまたはS3サーバーアクセスログ。
- **VPC Gateway Endpoint**（S3、DynamoDB）：無料。これらのサービスのNAT Gatewayコストを排除する。
- **VPC Interface Endpoint**：時間あたりプラスGBあたりで価格設定。高ボリュームのサービスではNAT Gatewayより安い。
- **CloudFront**は、直接のEC2からインターネットより低いレートでデータを提供し、キャッシングを通じてオリジンの転送量を劇的に減らします。
- 重要な問いは、ただの「いくら」ではなく「このコストは意図的か？」です。意図しないコスト——忘れられたテストパイプライン、NAT経由のデフォルトルーティング——こそが、本当の節約が隠れる場所です。

## 試験のヒント

*SAA-C03 ドメイン：コスト最適化されたアーキテクチャの設計（ドメイン4、タスク4.4）*

- **NAT Gateway 対 VPCエンドポイント**：試験のシナリオ：「プライベートサブネットのEC2が頻繁にS3/DynamoDBを呼び出す——NAT Gatewayコストをどう減らすか？」→ VPC Gateway Endpoint（S3とDynamoDBには無料）。
- **データ転送の価格ルール**：
  - AWSへ：無料
  - 同一AZ：無料
  - クロスAZ：課金される
  - クロスリージョン：課金される（より高いレート）
  - インターネット：課金される（相当なレート）
- **コスト最適化としてのCloudFront**：「グローバルなコンテンツ配信のデータ転送コストを減らす」→ CloudFront。キャッシュ層がオリジンリクエストを減らす。
- **S3 Transfer Acceleration**：CloudFrontのエッジロケーションを使ってS3*への*アップロードを高速化する。標準のS3より高コスト。地理的に遠い場所から大きなファイルをアップロードする顧客に使う。
- **クロスリージョンレプリケーションのコスト**：リージョンをまたいでデータをレプリケートするとデータ転送料金がかかる。S3 CRRでは、データ転送アウトのレートとS3リクエストのコストの両方を払う。
- **PrivateLink（VPC Interface Endpoint）**：AWSサービスと、他のAWS顧客がホストするサービスへのプライベートな接続を提供する。NAT経由より安全で、高ボリュームのサービスにはしばしば安い。NAT Gateway処理に対する損益分岐点はおよそ420GB/月（エンドポイント自身のAZあたりの時間あたりコストを数え、NAT Gatewayが他のトラフィックのために残ると仮定）。

## 演習

**演習1 — 記憶**

VPC Gateway EndpointとVPC Interface Endpointの違いを説明してください。それぞれどのAWSサービスで利用可能で、それぞれのコストは何ですか？

*（ヒント：Gateway Endpointは無料ですがS3とDynamoDBにだけです。Interface Endpointは時間あたりコストがかかりますが、他のほとんどのAWSサービスで動きます。）*

**演習2 — SAA-C03 シナリオ**

*シナリオ*：ある企業のアプリケーションが、プライベートサブネットのEC2インスタンスで動いています。インスタンスは、Amazon SQSとAmazon S3に頻繁にAPI呼び出しをします。現在、すべてのトラフィックはNAT Gateway経由で出ていきます。チームはNAT Gatewayのコストを減らしたいと考えています。データセキュリティは維持されなければなりません——どのトラフィックもパブリックインターネットを横切るべきではありません。

これらの要件を最小の継続コストで満たす、最良のアプローチはどれですか？

A) SQSのGateway EndpointとS3のGateway Endpointを作成する  
B) SQSとS3の両方にInterface Endpointを作成する  
C) SQSにInterface Endpointを、S3にGateway Endpointを作成する  
D) NAT Gatewayを削除し、API呼び出しに直接インターネットゲートウェイを使う

**ヒント1**：Gateway EndpointはS3とDynamoDBにしか使えません。

**ヒント2**：Interface EndpointはSQSや他の多くのサービスで利用可能です（ただしお金がかかる）。

**ヒント3**：プライベートサブネットのルートテーブルのインターネットゲートウェイは、それをパブリックサブネットにします——セキュリティ要件に違反します。

**解答**: C

**説明**：S3はGateway Endpoint（無料）を使います。SQSはInterface Endpoint（有料）が必要です。この組み合わせは、両方のサービスのNAT Gatewayのデータ処理コストを排除します。すべてのトラフィックはAWSのプライベートネットワーク内に留まります——パブリックインターネットの横断はありません。

**なぜAではないのか？** Gateway EndpointはSQSには利用できません。S3とDynamoDBだけがGateway Endpointを持ちます。

**なぜBではないのか？** これは機能しますが、S3に（無料のGateway Endpointの代わりに）Interface Endpointを使うのは不要な時間あたりの料金がかかります。S3とDynamoDBには常に無料のGateway Endpointを使ってください。

**なぜDではないのか？** プライベートサブネットからインターネットゲートウェイへのルートを追加すると、それはパブリックサブネットになります。プライベートサブネットのEC2インスタンスはたいていElastic IPを持たないので、追加の変更なしには実際にインターネットゲートウェイ経由でルーティングできません——そしてそうすることは、それらをインバウンドのインターネットトラフィックにさらすことになります。

*SAA-C03 ドメイン：コスト最適化されたアーキテクチャの設計 — タスク4.4*
