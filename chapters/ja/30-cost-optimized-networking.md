**CloudFront: データ転送割引**

一見すると矛盾する事実があります：CloudFront を通じてデータを配信することは、EC2 または S3 から直接配信するよりも一般的に安価です。

**EC2 からインターネットへの配信**: 0.09/GB
**CloudFront からインターネットへの配信**: 0.085/GB (わずかに安い)

しかし、実際の節約は 1 GB あたりのレートではありません。CloudFront がエッジロケーションでデータをキャッシュすることです。たとえば、1,000 人のユーザーが同じメニュー写真のリクエストを送信する場合：

- **CloudFront なし**: 1,000 件の要求が S3 のオリジンにヒット × 写真サイズ × 0.09/GB
- **CloudFront あり**: 1 件の要求が S3 にヒット (キャッシュミス) + 999 件の要求が CloudFront のエッジキャッシュから配信されるレートで

Nimbus のキャッシュヒット率が 83% (第 13 章を参照) であれば、83% のリクエストがエッジキャッシュから提供されました。彼らの「アウトバウンド」トラフィックの 17% が実際のオリジンデータ転送でした—エッジで 83% のトラフィックがキャッシュされました。

「CloudFront は単なるパフォーマンスのための CDN ではありません。また、データ転送のためのコスト最適化でもあります」とトムは言いました。

レオは考え込みました。「すべての静的コンテンツ配信を CloudFront を通じて行うべきです。レイテンシに敏感でないアセットでも」

「その通りです。ユーザーが AWS からダウンロードしている場合は、CloudFront を通して行うべきです」

## S3 Select を使って

S3 Select は、S3 バケット内のオブジェクトから、特定の条件に合致するデータのみを効率的に選択するための機能です。例えば、特定の期間のログデータや、特定の属性を持つアイテムのみを抽出することができます。これにより、S3 バケット内のデータ量を大幅に削減し、コストを抑えることができます。

S3 Select は、SQL ライクなクエリを使用して、S3 バケット内のデータを検索します。これにより、SQL の知識があれば、簡単に S3 Select を使用することができます。

### S3 Select の主な機能

*   **条件付きのデータ抽出:** 特定の条件に合致するデータのみを選択できます。
*   **コスト削減:** 不要なデータを抽出しないため、S3 バケット内のデータ量を削減し、コストを抑えることができます。
*   **SQL ライクなクエリ:** SQL の知識があれば、簡単に S3 Select を使用できます。
*   **AWS Lambda との連携:** S3 Select の結果を AWS Lambda 関数に送信し、さらに処理を行うことができます。

### S3 Select の使用例

例えば、S3 バケットに保存されているログデータから、特定の期間のアクセスログのみを抽出することができます。

SELECT * FROM logs WHERE timestamp BETWEEN '2023-10-26' AND '2023-10-27'

このクエリは、`logs` という名前のテーブルから、`timestamp` が '2023-10-26' から '2023-10-27' の範囲にある行のみを選択します。

```python
# Let S3 filter first, transfer only matching rows (~2MB instead of 500MB)
response = s3.select_object_content(
    Bucket='analytics',
    Key='orders-2024.csv',
    Expression="SELECT order_id, total FROM S3Object WHERE restaurant_id = '47'"
)

S3 Select は、S3 からアプリケーションへのデータ転送を削減します。大規模なファイルと選択的なクエリの場合、データボリューム—そしてそれによってコスト—を 10～100 倍削減できる可能性があります。

## 強みと限界

**NAT Gateway のコスト:**

- 大量のデータが NAT Gateway を通じて蓄積される
- VPC エンドポイントにより、一部の NAT コストが完全に排除される
- 貴社のプライベートインスタンスが呼び出すサービスと、エンドポイントが利用可能かどうかを確認する

**CloudFront によるコスト削減:**

- キャッシュヒット率が直接コスト削減に影響する
- 高いキャッシュヒット率 = オリジン転送の低下 + 全体的な転送コストの低下
- すべての静的アセットの配信を CloudFront を通じて行う

**帯域内トラフィックのトレードオフ:**

- 帯域内トラフィックを排除するには、通常、より多くのコストがかかるアーキテクチャ変更が必要
- 最適化する前に慎重に計算する

**S3 Select:**

- 大規模な S3 オブジェクトに対する選択的なクエリに対して、大幅な節約効果
- 完全にファイルが必要な場合は効果がありません

## 概要

- AWS は、**出口データ** (インターネット: 約 0.09/GB)、**帯域内トラフィック** (方向あたり 0.01/GB)、**帯域外トラフィック** (0.02～0.08/GB)、**NAT Gateway の処理** (0.045/GB) に対して料金を課します。
- **入出口データ** は無料です。**帯域内トラフィック** は無料です。
- **VPC Gateway エンドポイント** (S3、DynamoDB): 無料。NAT Gateway のコストを排除します。
- **VPC インターフェース エンドポイント**: 時間ごとの料金と 1 GB ごとの料金で価格設定されます。高体積サービスに対して NAT Gateway よりも安価です。
- **CloudFront** は、直接 EC2-インターネットよりも低いレートでデータを配信し、キャッシュを通じてオリジン転送量を大幅に削減します。
- **S3 Select** は、ソースでフィルタリングすることで、S3 からのデータ転送を削減します。
- ネットワークコストの中には、アーキテクチャ上のトレードオフがあるものがあります (帯域内トラフィックを HA にするために使用) — 理解し、常に排除する必要はありません。

## 練習問題

**練習問題 1 — 回想**

VPC Gateway エンドポイントと VPC インターフェース エンドポイントの違いを説明してください。各ものはどの AWS サービスで利用可能で、それぞれのコストはいくらですか?

*(ヒント: Gateway エンドポイントは無料ですが、S3 と DynamoDB のみです。インターフェース エンドポイントは時間ごとの料金ですが、ほとんどの他の AWS サービスで機能します。)*

**練習問題 2 — 試験練習**

*シナリオ*: 会社のアプリケーションがプライベートサブネット内の EC2 インスタンスで実行されています。インスタンスは頻繁に Amazon SQS と Amazon S3 への API 呼び出しをしています。現在、すべてのトラフィックは NAT Gateway を通じてエクスポートされています。チームは NAT Gateway のコストを削減したいと考えています。セキュリティは維持する必要があります—トラフィックは公共インターネットを通過してはなりません。

これらの要件を満たす最適なアプローチは、継続的なコストを最小限に抑えるにはどれですか?

A) SQS と Gateway Endpoint を作成し、S3 と Gateway Endpoint を作成します。
B) SQS と Gateway Endpoint を作成し、S3 と Gateway Endpoint を作成します。
C) SQS と S3 の両方に対して Interface Endpoint を作成します。
D) NAT Gateway を削除し、API 呼び出しに直接インターネット Gateway を使用します。

**ヒント 1**: Gateway Endpoint は S3 と DynamoDB のみで利用可能です。

**ヒント 2**: Interface Endpoint は SQS や他の多くのサービスで利用可能ですが、費用がかかります。

**ヒント 3**: プライベートサブネットのルートテーブルにインターネット Gateway を追加すると、サブネットがパブリックになり、セキュリティ要件に違反します。

**解答**: B

**解説**: S3 は Gateway Endpoint (無料) を使用します。SQS は Interface Endpoint (有料) を必要とします。この組み合わせにより、両方のサービスに対して NAT Gateway を使用したデータ処理の費用を削減できます。すべてのトラフィックは AWS のプライベートネットワーク内に留まり、パブリックインターネットを経由しません。

**A なぜダメなのか？**: Gateway Endpoint は SQS で利用できません。S3 と DynamoDB のみで Gateway Endpoint が利用可能です。

**C なぜダメなのか？**: これは機能しますが、S3 に Interface Endpoint (Gateway Endpoint ではなく) を使用すると、不要な時間単位の料金が発生します。S3 と DynamoDB のみで無料の Gateway Endpoint を使用してください。

**D なぜダメなのか？**: プライベートサブネットのルートテーブルにインターネット Gateway へのルートを追加すると、サブネットがパブリックになり、EC2 インスタンスが Elastic IP を持たないため、インターネット Gateway を使用してインターネットからの入ってくるトラフィックをルーティングすることはできません。そのため、追加の変更が必要になります—そして、それを行うとセキュリティ上のリスクが高まります。

- メニューの写真が S3 us-east-1 を通じて CloudFront エッジ (シアトル) からキャッシュされる (キャッシュ後に約 8ms)

チームは、西海岸ユーザーのために us-west-2 (オレゴン州) で 2 つ目のアプリケーションリージョンを追加することを検討しており、API 応答のレイテンシを削減します。
