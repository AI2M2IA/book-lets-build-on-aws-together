「火曜日の午前2時17分に」と彼女は言いました、「ロードバランサーからEC2インスタンスへのアウトバウンド接続がRomaniaのIPアドレスからありました。」

「それは私たちのインフラではありません」とレオは言いました。

「セキュリティグループがそれをブロックしました」とプリヤは言いました。「攻撃者は1つのEC2インスタンスにアクセスしました。ロードバランサーからのトラフィックのみを許可するセキュリティグループがあるため、他のインスタンスには到達できませんでした。」

レオは想像する必要はありませんでした。彼は元の設定でその構成を目撃していました。

**2層のネットワークセキュリティ**

VPCでは、ネットワークトラフィックを制御するための2つの異なるツールがあります：

**セキュリティグループ**: 個々のリソース（EC2インスタンス、RDSデータベース、ロードバランサー、VPC内のLambda関数）にアタッチされた仮想ファイアウォールです。それらはリソースレベルで動作します。

**ネットワークACL（NACL）**: サブネットにアタッチされたファイアウォールルールです。それらはサブネット境界で動作します—サブネットに到達する前にトラフィックを検査します。

両方を理解するには、1つの重要な違いを理解する必要があります：**ステートフル対ステートレス**。

**ステートフル：セキュリティグループ**

セキュリティグループは**ステートフル**です。

特定のポートへのインバウンドトラフィックを許可すると、応答トラフィックが自動的に許可されます—明示的なアウトバウンドルールがない場合でもです。

アウトバウンドトラフィックの宛先への許可は、応答トラフィックが自動的に許可されます。

オフィスビルのセキュリティガードを想像してください。あなたは入る際に身分証明書を見せます。あなたはその後出て行きます。ガードはあなたを再確認する必要はありません—システムはあなたが許可されていて、出て行くことができることを知っています。

**Nimbus API EC2インスタンスのセキュリティグループルール:**

- **インバウンド—TCP 8080—ロードバランサーSGから** → ALBからのAPIトラフィックを受け入れる
- **インバウンド—TCP 22—バッショングルームSGから** → バッショングルームからのSSHのみ
- **アウトバウンド—TCP 5432—RDS SGへの** → PostgreSQLへの接続
- **アウトバウンド—TCP 6379—ElastiCache SGへの** → Redisへの接続
- **アウトバウンド—TCP 443—0.0.0.0/0への** → 外部APIへのHTTPS

注意：ポート8080の明示的なアウトバウンドルールはありません。インバウンドルールはステートフルです—ロードバランサーからのAPIの応答トラフィックは自動的に許可されます。

また注意：セキュリティグループルールはIPアドレスではなく、*他のセキュリティグループ*を参照します。「ロードバランサーセキュリティグループからのインバウンドを許可する」とは、「このセキュリティグループがアタッチされたすべてのリソースからのトラフィックを許可する」という意味です。これはIPアドレスを追跡するよりも柔軟で保守しやすいです。

**デフォルト動作:**

- デフォルトでは、すべてのインバウンドトラフィックは拒否されます
- デフォルトでは、すべてのアウトバウンドトラフィックは許可されます
- すべてのルールが評価されます（セキュリティグループには順序付けられたルールはありません—すべての一致するルールが適用されます）
- セキュリティグループは*許可する*ことしかできません—明示的な拒否ルールを作成することはできません。

**ステートレス：ネットワークACL（NACL）**

NACLは**ステートレス**です。

ポート8080へのインバウンドトラフィックを許可すると、それはインバウンドトラフィックのみをカバーします。応答（エフェメラルポート上のアウトバウンドトラフィック）は、明示的にアウトバウンドルールで許可する必要があります。

金属探知機を想像してください。あなたは入る際に通過します。金属探知機はあなたがすでに通過したことを知りません—あなたは出るときにまた通過する必要があります。

NACLルールは番号付けされており、順序で評価されます。ルール100はルール200よりも先に評価されます。ルール100がトラフィックを拒否し、ルール200がそれを許可する場合、トラフィックは拒否されます。

NACLは*明示的に拒否する*ことができます—セキュリティグループとは異なり、NACLは許可するだけです。これにより、特定のIPアドレス範囲をブロックするための機能が提供されます。

**デフォルトNACL動作:**

- デフォルトNACL（VPCで作成）はすべてのインバウンドおよびアウトバウンドトラフィックを許可します
- カスタムNACLはデフォルトですべてのトラフィックを拒否します（許可したいものを明示的に許可する必要があります）。

**パブリックサブネットのNACL（簡略化）:**

*インバウンドルール（順序で評価—最初のマッチが勝つ）:*

- ルール100：TCP 443、0.0.0.0/0から → **許可** (HTTPS)
- ルール110：TCP 80、0.0.0.0/0から → **許可** (HTTP)
- ルール120：TCP 1024–65535、0.0.0.0/0から → **許可** (エフェメラル戻りポート)
- ルール\*: すべてのトラフィック → **拒否**

*アウトバウンドルール:*

- ルール100：TCP 443、0.0.0.0/0への → **許可** (HTTPS)
- ルール110：TCP 80、0.0.0.0/0への → **許可** (HTTP)
- ルール120：TCP 1024–65535、0.0.0.0/0への → **許可** (エフェメラル戻りポート)
- ルール\*: すべてのトラフィック → **拒否**

Rule 120 (ports 1024-65535) は、一時的な高番目のポートを使用してTCP応答トラフィックを行うエフェメラルポートを許可します。NACL はステートレスであるため、これらの出力トラフィックを明示的に許可する必要があります。そうしないと、サーバーの応答が通過しません。

**使用する際の判断基準**

**セキュリティグループ** を主なアクセス制御レイヤーとして使用します。管理が容易で、ステートフル（エフェメラルポートを忘れてしまうことによる誤ったブロックを防ぐ可能性が低い）、および他のセキュリティグループへの参照をサポートしています。

**NACL** は、特にサブネットレベルでの制御に使用します。

- **明示的な拒否ルール**: 既存のサブネットに到達する特定のIPアドレスまたは範囲をブロックします。
- **緊急ブロック**: IPアドレスが積極的にリソースに到達しようとしています。NACLで拒否ルールを追加して、サブネット全体をブロックします。

ソフィアは「セキュリティグループは微細な制御層であり、NACLは広範な制御層である」と述べていました。

「セキュリティグループは個々のリソースを保護し、NACLはサブネット全体を保護します。ネットワーク内の何らかのものを到達させないIPアドレスをブロックしたい場合はNACLを使用し、ロードバランサーがAPIサーバーに到達できるようにしたい場合はセキュリティグループを使用します。」

**インシデント：レイヤーが捉えたもの**

ルーマニアのIP攻撃に戻って：

**何が起こったか**: 攻撃者は、侵害されたデプロイキーを使用して、1つのEC2インスタンスにスキャンスクリプトをアップロードしました。スクリプトは他のサービスに接続を試みました。

**それを阻止したものは**:

- RDSセキュリティグループは、API EC2セキュリティグループからのポート5432へのインバウンドトラフィックのみを許可していました。スクリプトはスキャンツールからデータベースに到達できず、正しいセキュリティグループにアタッチしていませんでした。
- ElastiCacheセキュリティグループは、API EC2セキュリティグループからのポート6379へのインバウンドトラフィックのみを許可していました。
- その他のEC2インスタンスは、バッショントラップセキュリティグループからのSSH接続のみを許可していました。

**それを阻止しなかったものは**:

- EC2インスタンスの出力ルールは、パッケージのダウンロードに必要な0.0.0.0/0へのHTTPSトラフィックを許可していました。スクリプトはこのルールを使用して攻撃者のサーバーへの出力接続を作成しました。

インシデント後、プリヤは次を追加しました。

- ルーマニアのIPアドレス範囲をブロックするNACLルール
- EC2インスタンス（許可された特定の宛先のみを許可）でより制限された出力ルール

## 強みと限界

**セキュリティグループ**:

- ステートフル（エフェメラルポートのトラブルシューティングなし）
- 他のセキュリティグループへの参照が可能（IPアドレスよりも柔軟）
- 許可ルールのみ
- リソースレベルで動作 - 詳細

**NACL**:

- ステートレス（インバウンドおよびアウトバウンドの両方に対して、エフェメラルポートを含む明示的なルールが必要です）
- 明示的な拒否が可能 - 既知の悪意のあるIPアドレスをブロックするのに役立ちます
- サブネットレベルで動作 - 広範な制御
- 数の順にルールが評価される - 予測可能ですが、慎重な管理が必要です

## 概要

- **セキュリティグループ** は、個々のリソースのステートフル仮想ファイアウォールです。すべてのルールが評価されます。許可ルールのみが適用されます。
- **NACL** は、サブネット全体のステートレスファイアウォールです。許可および拒否ルールが適用されます。ルールは数値順に評価されます。
- **ステートフル** は、応答トラフィックが自動的に許可されることを意味します。**ステートレス** は、両方向のトラフィックを明示的に許可する必要があることを意味します。
- セキュリティグループは、主なアクセス制御レイヤーであり、NACLはサブネットレベルでの制御と明示的なブロックのための追加レイヤーです。
- NACLがインバウンドトラフィックを許可する場合、TCP応答が通過するために、出力エフェメラルポート（1024-65535）を許可する必要があります。
- セキュリティグループは他のセキュリティグループを参照できます—ロードバランサーセキュリティグループからのトラフィックを許可することは、IPアドレスを追跡するよりも保守が容易です。
- デフォルトNACLとカスタムNACL

## 試験のヒント

*SAA-C03 ドメイン：安全なアーキテクチャの設計 (ドメイン 1、タスク 1.2)*

- **ステートフルとステートレス**: この区別が最もテストされる概念です。セキュリティグループ = ステートフル = 応答が自動的に許可されます。NACL = ステートレス = 応答トラフィックを明示的に許可する必要があります。
- **セキュリティグループのルール**: 明示的な拒否はありません。複数のセキュリティグループがインスタンスにアタッチされている場合、すべてのルールが結合されます。すべての一致するルールが評価されます。
- **NACLのルール順序**: ルールは、数値が低い順に高い順に評価されます。ルール100はルール200の前にあります。最初のマッチが勝ります。`*`（アスタリスク）ルールは、最も下にあるため、デフォルトで拒否されます。
- **エフェメラルポート**: NACLでインバウンドHTTP（ポート80）を許可しているにもかかわらず、エフェメラルポート（1024-65535）を出力許可しない場合、ユーザーはリクエストを送信できますが、応答は受信できません。
- **セキュリティグループの参照**: セキュリティグループ（IPアドレスではなく）からトラフィックを許可できます。これは、VPC内のトラフィックの推奨されるパターンです。
- **デフォルトNACLとカスタムNACL**: デフォルトNACLはすべてのトラフィックを許可します。カスタムNACL（作成したNACL）は、すべてのトラフィックをデフォルトで拒否します。試験シナリオ：「新しいNACLを作成し、トラフィックがブロックされました」→ 許可ルールが欠落しているか確認します。

## 練習問題

**練習問題 1 - 記憶**

開発者がセキュリティグループにポート443へのインバウンドルールを追加しました。サーバーの応答を許可するために、彼女は出力ルールも追加する必要がありますか？なぜですか？

**演習 2 — 試験練習**

*シナリオ*: ウェブアプリケーションがパブリックサブネット内のEC2インスタンスで実行されている会社があります。そのアプリケーションはインターネットからHTTPSトラフィック（ポート443）を受け付けます。ユーザーはアプリケーションに接続できるものの、応答を受信できないと報告しています—リクエストがハングし、タイムアウトします。

EC2セキュリティグループには、ポート443のTCPトラフィックを0.0.0.0/0から許可するインバウンドルールがあります。サブネットのNACLには、ポート443のTCPトラフィックを0.0.0.0/0から許可するインバウンドルール（ルール100）と、ポート443のTCPトラフィックを0.0.0.0/0に送信するアウトバウンドルール（ルール100）があります。

最も可能性の高い原因は何ですか？

A) セキュリティグループにポート443のTCPアウトバウンドルールがありません。
B) NACLに、エフェメラルポート（1024-65535）を許可するアウトバウンドルールがありません。
C) セキュリティグループにエフェメラルポートのインバウンドルールがありません。
D) EC2インスタンスにElastic IPアドレスがありません。

**ヒント 1**: セキュリティグループはステートフルです—応答トラフィックは自動的に許可されます。NACLはステートレスです—許可されません。

**ヒント 2**: ブラウザがポート443でウェブサーバーに接続すると、サーバーの応答はランダムなエフェメラルポート（1024-65535）を介して戻ってきます—ポート443ではありません。

**ヒント 3**: NACLには443のアウトバウンドルールがありますが、応答は443のポートに送信されません。

**解答**: B

**解説**: NACLはステートレスです。ユーザーがポート443でサーバーに接続すると、サーバーのTCP応答はエフェメラルポート（1024-65535からランダムに選択）を介して戻ってきます。NACLのアウトバウンドルールはポート443のみを許可するため、応答はデフォルト拒否ルールによってブロックされます。エフェメラルポート（1024-65535）を許可するNACLのアウトバウンドルールを追加することで、これを修正できます。

**なぜAではないのですか？** セキュリティグループはステートフルです—応答トラフィックはアウトバウンドルールに関係なく自動的に許可されます。セキュリティグループのアウトバウンドルールは必要ありません。

**なぜCではないのですか？** エフェメラルポートはアウトバウンド応答トラフィック用であり、インバウンド用ではありません。ユーザーからのインバウンド接続はポート443を介して来ますが、これはすでに許可されています。

**なぜDではないのですか？** Elastic IPアドレスはインスタンスがパブリックIPを持っているかどうかを決定するのではなく、確立された接続が応答を受信できるかどうかを決定します。
