# 第19章：チケットマシン

チケットマシンは静かな革命でした。番号を取って、呼ばれるのを待ちます。列はキューになります。人々は座っていても構いません。サービスカウンターは独自のペースで動作します。誰もが誰かを邪魔しません。

Nimbusは、注文が人気になるまで、それが問題だとは感じられなかった問題がありました。

注文が1つでも置かれるたびに、APIサーバーは次のことを行いました。

1. 注文をデータベースに保存する
2. レストランのタブレットに通知を送信する
3. 顧客に確認メールを送信する
4. レストランの分析ダッシュボードを更新する
5. 課金を記録するためのイベントをログに記録する

これらのすべてが顧客への応答をAPIがトリガーする前に、同期的に発生する必要がありました。メールサービスが遅かった場合（時々そうでした）、顧客は待っていました。分析ダッシュボードがダウンしていた場合（時々そうでした）、注文は失敗しました。

「私たちは密接に結合されている」プリヤは言いました。「ダウンストリームのいずれかのステップが失敗すると、注文全体が失敗します。」

「もし注文を保存し、顧客にすぐに確認をすればどうだろうか」レオは言いました。「そして、残りの処理をバックグラウンドで処理すればどうだろうか？」

「それこそがキューです」プリヤは言いました。

**デリカウンターモデル**

活気のあるデリカウンターでは、レジの人が次の顧客を処理する前に、スライサーがスライスを完了するのを待つことはありません。注文を取り、キッチンに渡して、次の人にサービスを提供します。キッチンは注文を独自のペースで処理します。

顧客はより迅速なサービスを受けられます。キッチンは突然の急増に圧倒されることはありません。キッチンが遅い瞬間がある場合、注文はキューに溜まり、レジでエラーが発生する代わりに発生します。

これは**疎結合**です。ワークを取り扱うコンポーネントを処理するコンポーネントから分離することです。

ソフトウェアシステムでは、キューはメッセージブローカーであることがよくあります。これは、プロデューサーからメッセージを受け取り、消費者に配信するサービスです。

**Amazon SQS：キュー**

**Amazon SQS（Simple Queue Service）**は、AWSのマネージドメッセージキューサービスです。メッセージは消費者が処理するまで確実に保存されます。

基本的な流れ：

1. **プロデューサー**（APIサーバー）がキューにメッセージを置きます：`{ "orderId": "ORD-5532", "restaurantId": "47", "items": [...] }`
2. APIは顧客にすぐに確認応答を返します：「注文が確認されました！」
3. **消費者**（別々のワーカーサービス）がキューからメッセージを読み取り、それらを処理します：レストランへの通知の送信、確認メールの送信、分析の更新

顧客エクスペリエンス：即時の確認。ダウンストリームの処理：ワーカーのペースで非同期的に行われます。

**SQSのキーコンセプト**

**メッセージの可視性タイムアウト**: 顧客がSQSからメッセージを読み取ると、メッセージは他の消費者に対して30秒間（デフォルト）の間*不可視*になります。これにより、消費者がメッセージを処理するのに十分な時間を確保できます。消費者が正常に完了した場合、メッセージを削除します。消費者がクラッシュした場合、可視性タイムアウトが期限切れになり、メッセージが再び他の消費者に再試行のために可視化されます。

これにより、at-least-onceの配信が保証されます。メッセージは、消費者が失敗した場合でも、少なくとも1回処理されます。

**死葉キュー（DLQ）**: メッセージが構成可能な回数（たとえば、5回の再試行）の失敗で処理に失敗した場合、SQSはメッセージを死葉キューに移動します。DLQを検査して、メッセージが失敗する理由を理解し、損失を防ぎます。

**キュータイプ**:

**標準キュー**: 最大スループット（1秒あたりのメッセージ数に制限なし）。配信順序はベストエフォート（保証されません）。at-least-onceの配信（非常にまれに、メッセージが2回配信される可能性があります）。

**FIFOキュー**: 順序が厳密に先入れ先出し（FIFO）。正確な1回配信。バッチングで1秒あたり3,000件のメッセージ、バッチなしで300件のメッセージ。順序が重要な場合に使用します（金融取引、一貫した状態の変更）。

Nimbusの場合、ほとんどのキューは標準キューを使用しました。課金キューは、料金が順序で処理されるようにFIFOを使用しました。

**Amazon SNS：ブロードキャスター**

**Amazon SNS（Simple Notification Service）**は、パブリッシュ/サブスクライブ（pub/sub）メッセージサービスです。1つのプロデューサー、1つの消費者（キュー）ではなく、SNSは1つのメッセージを*複数の*サブスクライバーに同時に配信できます。

モデル：

1. **発行者**がSNS**トピック**にメッセージを送信します
2. すべての**サブスクライバー**がそのトピックのメッセージを同時に受信します（ファンアウト）

サブスクライバーは次のとおりです。

- SQSキュー（メッセージをキューにプッシュして非同期的に処理します）
- Lambda関数（関数を直接トリガーします）
- HTTP/HTTPSエンドポイント（Webhook配信）
- メールアドレス
- SMS（電話番号）

Nimbusの場合、注文が置かれたイベントは`order-events`という名前のSNSトピックに公開されます。

- レストラン通知サービスがサブスクライブ（そのキューに受信します）
- メールサービスがサブスクライブ（そのキューに受信します）
- 分析サービスがサブスクライブ（そのキューに受信します）
- 課金サービスがサブスクライブ（そのFIFOキューに受信します）

1つの注文イベント。4つのサブスクライバー。すべてが同時に通知されます。それぞれが独自のペースで処理します。

「SNSはアナウンスメントであり、SQSは各チームがそのアナウンスメントを独自のペースで処理するインボックスです」プリヤは言いました。

「まさにそうだ」レオは言った。「SNS/SQSのファンアウトは標準的なパターンだ。」

**SNS/SQS ファンアウトパターン**

SNSトピックが複数のSQSキューに供給されるこの組み合わせは、AWSにおける最も重要なアーキテクチャパターンの一つです。

```
API Server
    |
    | publishes to
    ↓
SNS Topic: "order-placed"
    |
    |—————————————————|—————————————————|
    ↓                 ↓                 ↓
SQS Queue         SQS Queue         SQS Queue
(notifications)  (email service)   (analytics)
    |                 |                 |
    ↓                 ↓                 ↓
Worker             Worker            Worker
Lambda/EC2        Lambda/EC2        Lambda/EC2
```

各キューは独立しています。分析サービスは遅くなることがあります—キューが埋まりますが、通知および電子メールサービスは影響を受けません。分析サービスがダウンすると、メッセージは復旧するまでキューに待ちます。何も失われません。

これが重要な特性です：**独立した障害**。ある消費者の問題は他の人に伝播しません。

**メッセージフィルタリング：すべてのメッセージをすべてのサブスクライバーに送信する必要はありません**

システムが成長するにつれて、すべてのサブスクライバーがすべてのメッセージを処理する必要はありません。分析サービスは、完了した注文に関する情報のみに関心がある場合、失敗した支払い処理に関するメッセージを受信する必要はありません。

**SNSメッセージフィルタリング**により、サブスクライバーはフィルタポリシーを指定できます—特定の属性に一致するメッセージのみを配信します。

レストラン通知サービスは次のフィルタでサブスクライブします：`status = "confirmed"` のメッセージのみを配信します。

エラーアラートサービスは次のフィルタでサブスクライブします：`status = "failed"` のメッセージのみを配信します。

各サブスクライバーは、必要なものだけを受け取ります。

**SQSとSNSを使用するタイミング**

**SQSのみ**: 1つのプロデューサー、1つの消費者（または同じキューの複数の競合消費者）。メッセージは一度だけ処理する必要があり、順序通り（FIFO）または順序なし（標準）。ワーカーキューパターン—1つのキュー、複数のワーカーがそれから消費します。

**SNSのみ**: 忘れ去られる通知を送信します。電子メール、SMS、HTTPエンドポイントにプッシュします。メッセージをキューに入れる必要はありません—通知するだけで済みます。

**SNS + SQS（ファンアウト）**: 1つのイベント、複数の独立した消費者。各消費者には独自のキューがあり、独立して処理し、独立して失敗できます。

## 強みと限界

**なぜSQSとSNSが強力なのか**:

- SQSは、メッセージを複数のAZに保存することで、耐久性があり、信頼性の高いメッセージ配信を提供します。
- デカップリングにより、プロデューサーおよび消費者サービス間の独立したスケーリングとデプロイが可能になります。
- デッドレターキューにより、障害が発生した場合にメッセージが黙って失われることはありません。
- SNSファンアウトパターンにより、プロデューサーを変更せずに新しい消費者を追加できます。

**複雑になる場所**:

- 最低1回配信により、消費者には冪等性が必要になります—同じメッセージを2回処理しても問題が発生しないようにします（重複した注文、重複した課金）。
- FIFOキューはより高価で、スループット制限があります。
- 複数のキューとサービスで失敗したメッセージのデバッグには、優れたログと可観測性が必要です。
- 複数のサービスで厳密な順序を保証することは限られています—順序が重要な場合、設計は複雑になります。

## 概要

- **デカップリング**は、ワークを生成するコンポーネントを、それを処理するコンポーネントから分離します。
- **SQS**は、管理されたキューです。プロデューサーはメッセージを送信し、消費者はそれらを読み取り、非同期的に処理します。
- **SQS標準**: 高スループット、ベストエフォートの順序、最少1回配信。
- **SQS FIFO**: 厳密な順序、正確な1回配信、低スループット。
- **SNS**は、パブリッシュ/サブスクライブサービスです。1つのメッセージ、複数のサブスクライバーが同時に受信します。
- **SNS + SQSファンアウト**: 1つのイベントが複数の独立した処理パイプラインをトリガーする標準パターン。
- **デッドレターキュー**: 多くの再試行後に処理に失敗した場合にメッセージをキャッチします。
- **冪等性**: 消費者が重複したメッセージを安全に処理できるように設計します。

## 試験のヒント

*SAA-C03 ドメイン：回復力のあるアーキテクチャの設計（タスク2.1、タスク2.1）*

- **SQS標準とFIFO**: 試験では順序と配信の保証が区別されます。“順序で処理する必要がある” → FIFO。“最大スループット” → 標準。
- **視認時間**: 最低1回配信のキーコンセプト。消費者が失敗した場合、タイムアウトよりも長い時間メッセージが再び表示されます。試験シナリオ：“メッセージが2回処理されている” → 視認時間が短すぎる（消費者がタイムアウトよりも長い時間メッセージを処理します）。
- **デッドレターキュー**: N回の再試行後に失敗した場合にメッセージが移動される場所。試験シナリオ：“処理が失敗してもメッセージが失われないようにする” → DLQ。
- **SNSファンアウト**: 1つのイベントが複数の消費者にトリガーする標準試験パターン。“注文が確定した通知が電子メール、SMS、および在庫更新を同時にトリガーする必要がある” → SNSトピックでSQSサブスクリプションを使用します。
- **SQS + Lambda**: LambdaはSQSキューをポーリングし、バッチメッセージごとにトリガーするように構成できます。試験では、大規模なイベント駆動型の処理に使用されます。
- **SQSロングポーリング**: 消費者が数秒ごとにポーリングするのではなく（短いポーリング、API呼び出しを浪費します）、最大20秒間メッセージの待ち時間がスケジュールされます。コストと誤った空の応答を削減します。
