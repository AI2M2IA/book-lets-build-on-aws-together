注文、実際のメニュー、実際の顧客を処理しています—トムの机の下で、オフィスWi-Fiで実行され、スペースヒーターとコーヒーメーカーを電力供給する電源タップに接続されています。

「サーバーが必要だ」とマヤは言いました。「本物のもの。あなたの机の下にある場所ではない場所で実行されるもの。」

それが、コンピュータをレンタルするという意味を理解し始めるきっかけになったのです。

**説明がほとんどない抽象化**

人々が「アプリケーションがクラウドで実行されている」と言う場合、それは通常、物理的なハードウェアに専属ではない仮想マシン—しかし、すべての点で同じように振る舞うコンピュータを指します。

仕組みは次のとおりです。

AWS データセンターにある物理サーバーには、CPU コア、メモリ、ディスク、
ネットワーク帯域幅など、多くのリソースがあります。AWSは、その物理サーバーをソフトウェアと呼ばれるものを使って分割します。このソフトウェアは、仮想マシンを作成し、それぞれが独自の専有CPU、メモリ、ディスクを持っているように見える—しかし、その下にある物理ハードウェアを共有しています。

それぞれの仮想マシンは、AWSが呼ぶ**EC2インスタンス**です。

EC2はElastic Compute Cloudの略です。「Elastic」という言葉は重要であり、後で説明します。現在：EC2インスタンスは、時間単位でレンタルできるコンピュータです。オペレーティングシステム、ネットワーク接続、コンピューティング能力を持っています。それは、物理サーバーと同じようにあなたのアプリケーションを実行します。

アナロジー：大きな建物でのアパートを借りるのとは、家を建てることのようです。

オーナー（AWS）は物理構造、配管、電気、セキュリティを維持します。あなたはユニットを受け取ります。あなたは自分の好きなように家具を飾り、毎月（または時間単位）支払います。より多くのスペースが必要な場合は、より大きなユニットに移動します。移動したら、支払いを停止します。

**インスタンスの選択：サイズが重要**

すべてのEC2インスタンスは同じではありません。AWSは、何に最適化されているかによって整理された、数百種類のインスタンスタイプを提供しています。

**汎用**（例：`t3`、`m6i`）：バランスの取れたCPUとメモリ。ほとんどのWebアプリケーションのデフォルトの選択肢です。

**計算最適化**（例：`c7g`）：メモリよりもCPUが多いため。ビデオエンコード、科学モデリング、バッチ処理に適しています。

**メモリ最適化**（例：`r7i`）：CPUよりもメモリが多い。データベース、キャッシュ、インメモリ分析に適しています。

**ストレージ最適化**（例：`i3`）：非常に高速なローカルストレージ。非常に高速なディスクI/Oが必要なデータ集約型ワークロードに適しています。

**加速コンピューティング**（例：`p4`）：GPUが接続されています。機械学習のトレーニングとグラフィックスレンダリングに適しています。

各ファミリーにはサイズがあります。`t3.micro`は2つの仮想CPUと1GBのメモリを持っています。`t3.xlarge`は4つの仮想CPUと16GBのメモリを持っています。ワークロードに適したサイズを選択します。

レオは`t3.micro`を選択していました。

「`t3.micro`は、何人のユーザーを処理できますか？」トムは尋ねました。

「アプリケーションによって異なります」とレオは言いました。「おそらく、画像アップロードとデータベースクエリを実行している100人程度の同時ユーザーを処理できるわけではありません。」

トムは「t3.micro」をホワイトボードに書き、それに横に悲しい顔の絵を描きました。

**AMI：機械の初期状態**

EC2インスタンスを起動する前に、オペレーティングシステムと初期構成を選択する必要があります。AWSでは、これは**Amazon Machine Image**（AMI）と呼ばれます。

AMIはテンプレートです。それは定義します。

- オペレーティングシステム（Amazon Linux、Ubuntu、Windows Serverなど）
- 事前インストールされたソフトウェア
- ディスクの状態

AMIからインスタンスを起動すると、AWSは単にこのテンプレートの新鮮なコピーを作成します。自分でAMIを作成することもできます—サーバーをあなたが望む方法で構成した場合、「その状態を保存」して、同じサーバーを迅速に起動するために使用できます。これにより、一貫した環境をスケーリングで展開できます。

AMIはレシピのようなものです。レシピは食事を説明します。レシピに従うと、同じ食事を得ます。食事を永久に変更したい場合は、レシピを更新します。

**キーペア：サーバーへのアクセス方法**

先ほどの「Admin123」の災難から。

EC2インスタンスにログインする方法は、**キーペア**を使用することです。

キーペアは、暗号化されたペアです—公開キー（サーバーにAWSによって保存）と、秘密キー（ダウンロードして秘密に保つファイル）です。ログインするには、SSH—安全なプロトコル—を使用して秘密キーを使用します。パスワードは使用しません。秘密キーを失うと、アクセス権を失います。「パスワードを忘れた」SSHはありません。

これは重要である理由は、キーペアが次のとおりだからです。

- あなたに固有です
- 推測することはできません
- AWSによって保存されていません（秘密キーを保持します）
- 取り消すことができます（サーバーからキーを削除し、新しいペアを生成します）

プリヤはすでにNimbusサーバーでキーベースのアクセスを設定していました。Admin123サーバーは廃止されました。誰もそれが悲しいとは思っていませんでした。

**インスタンスライフサイクル：永遠ではありません**

この章は多くの初心者にとって重要なポイントです。

EC2インスタンスはデフォルトでは永続的ではありません。インスタンスを停止すると、コンピューティングリソースが解放されます。それを再度起動すると、異なる物理ハードウェア上で実行される可能性があります。インスタンス自体（ルートボリューム上）に保存されたデータは、停止/再起動サイクルで生き残りますが、パブリックIPアドレスは変更されます。

インスタンスを*終了*すると、それは消滅します。ただし、別々のストレージが接続されている場合（第6章で説明します）を除き、インスタンス上のデータは失われます。

この「儚さ」は実際にはバグではなく、機能です。サーバーを起動して、使用して、捨てることができることを意味します。水平スケーリングを可能にします。しかし、同時に重要なデータをEC2インスタンス自体に保存すべきではないことを意味します。

では、どこにデータを保存しますか？

別々のストレージに保存します。次の2つの章でその詳細を説明します。

**「Elastic」の意味**

EC2は、Elastic Compute Cloudの略であると言いました。それは何が「Elastic」なのでしょうか？

2つのことです。

**垂直スケーラビリティ**: インスタンスのサイズを変更できます。インスタンスを停止し、`t3.micro`から`t3.xlarge`に変更し、再起動します。より多くのCPUとメモリ、同じアプリケーション、同じ設定です。

**水平スケーラビリティ**: 複数のインスタンスを追加できます。1つの大きなサーバーではなく、ロードバランサーの背後に10個の中規模サーバーを実行します。トラフィックが低下したら、インスタンスを削除して課金を停止します。

両方のアプローチは「1つのサーバー、トラフィックが多すぎる」という問題を解決します。異なるトレードオフがあり、第7章でAuto Scalingを追加する際に詳しく説明します。

重要な洞察：EC2では、コンピューティング能力は「ダイヤルする」ものであり、購入するものではありません。より多くのコンピューティング能力が必要な場合は、ダイヤルを上げてください。必要に応じて、ダイヤルを下げてください。それに応じて支払ってください。

## 強みと限界

**EC2の強み**:

- 完全な制御。OS、ソフトウェア、構成を選択できます。それはあなたのコンピューターです。
- 柔軟なサイズ調整。あらゆるユースケースで数百種類のインスタンスタイプがあります。
- ハードウェアを管理する必要はありません。AWSが物理レイヤーを管理します。
- ほとんどのインスタンスタイプでは、従量課金制（秒単位）の課金です。インスタンスを停止すると、課金が停止します。
- ほとんどすべてのものと動作します。EC2は、ほとんどのAWSサービスが構築されている基盤です。

**複雑になる場所**:

- OSのパッチとアップデートの管理を担当する必要があります。（共有責任モデル—クラウドの部分があなたのものである「クラウド」の部分）
- EC2を大規模で管理するには、インスタンスの状態、AMI、セキュリティパッチ、ライフサイクルを数千台の機械にわたって管理する必要があります。これは運用上のオーバーヘッドです。
- EC2はすべてに適しているわけではありません。頻繁に実行されないイベント駆動型のコードの場合、Lambda（第20章）はより安価で簡単です。コンテナ化されたワークロードの場合、ECSとEKS（第21章）はより効率的なリソースを提供します。
- 未使用インスタンスはまだお金がかかります。インスタンスを停止すると、コンピューティングの課金が停止しますが、ストレージが接続されている場合は、その課金も発生します。

## 概要

- **EC2インスタンス**は、AWSでレンタルする仮想マシンです。OS、ネットワークアクセス、コンピューティングリソースがあります。
- インスタンスタイプは、ユースケース別に整理されています：汎用、コンピューティング最適化、メモリ最適化、ストレージ最適化、加速コンピューティング。ワークロードに適したファミリーとサイズを選択してください。
- **AMI（Amazon Machine Image）**は、インスタンスのOSと初期構成のテンプレートです。カスタムAMIは、一貫性があり、再現可能なデプロイを可能にします。
- **キーペア**は、EC2インスタンスへのセキュアなアクセス方法です。パスワードは不要です。
- EC2インスタンスはデフォルトでは永続的ではありません。終了したインスタンスはデータの損失を伴います。重要なデータを別々のストレージサービスに保存してください。
- 「Elastic」とは、コンピューティング能力を上下に拡張できることを意味します（インスタンスのサイズを変更する—より大きなインスタンス）および（インスタンスの数を増やす—より多くのインスタンス）。

**演習 2 — 試験練習**

*シナリオ*: ある会社が、高トラフィックのウェブアプリケーションをデプロイしています。このアプリケーションは、複雑なフィルタリングロジックで CPU を集中的に使用する製品カタログの検索を処理します。チームは、セールイベント中に大幅なトラフィックスパイクを予想しており、適切な EC2 インスタンスタイプを選択し、トラフィックの急増に備えたいと考えています。

どの選択肢の組み合わせが、彼らの要件に最も合致しますか？

A) 一貫したパフォーマンスを確保するための固定数のメモリ最適化インスタンス
B) トラフィックスパイクを処理するための Auto Scaling と共に、コンピューティング最適化インスタンス
C) 単一の大規模インスタンスサイズを持つ汎用インスタンス
D) 製品カタログが高速なディスクアクセスを必要とするため、ストレージ最適化インスタンス

**ヒント 1**: ワークロードは「CPU 集約型」と記述されています。どのインスタンスファミリーが CPU に最適化されていますか？

**ヒント 2**: シナリオには「セールイベント中のトラフィックスパイク」が記載されています。固定数のインスタンスは、変動するトラフィックを効率的に処理できません。AWS でこの問題を処理する機能は何ですか？

**ヒント 3**: コンピューティング最適化インスタンスは、CPU 負荷の高い作業を処理します。Auto Scaling は、需要に応じてインスタンスを追加および削除します。これら 2 つを合わせて、両方の要件に対応します。

**答え**: B

**説明**: コンピューティング最適化インスタンス (例: `c` ファミリー) は、CPU 負荷の高いワークロードに対して、CPU ごとにコストを抑えたインスタンスを提供します。Auto Scaling は、負荷に基づいてインスタンス数を自動的に調整し、セールイベント中にインスタンスを追加し、トラフィックが正常な状態に戻るとインスタンスを削除します。この組み合わせは、パフォーマンスとコストの両方を最適化します。

**なぜ A が正しくないのか？** メモリ最適化インスタンスは、大量の RAM が必要なワークロード (データベース、インメモリキャッシュなど) に設計されています。これは CPU 負荷の高いワークロードです。また、固定インスタンス数は、オーバープロビジョニング (無駄) またはアンダープロビジョニング (失敗) を意味します。

**なぜ C が正しくないのか？** 汎用インスタンスは、バランスのために CPU 効率をある程度犠牲にします。既知の CPU 負荷の高いワークロードに対しては、コンピューティング最適化の方が適しています。また、単一の大規模インスタンスは、単一障害点です。

**なぜ D が正しくないのか？** ボトルネックは CPU であり、ディスク I/O ではありません。ストレージ最適化インスタンスは、ローカルストレージへの非常に高いスループットが必要なワークロードに設計されています。
