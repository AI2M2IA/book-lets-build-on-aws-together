**誰も説明しない抽象化**

人々がアプリケーションが「クラウドで動いている」と言うとき、彼らはたいてい、それが仮想マシンで動いていることを意味します——専用のハードウェアとして物理的には存在しないが、あらゆる点でそうであるかのように振る舞うコンピューターです。

その仕組みはこうです。

AWSのデータセンターの物理サーバーには、多くのリソースがあります。CPUコア、メモリ、ディスク、ネットワーク帯域幅。AWSはその物理サーバーを、**ハイパーバイザー**と呼ばれるソフトウェアを使って分割します——建物の管理人のように振る舞い、物理サーバーのリソースを複数の仮想テナントの間で分けるソフトウェアです。ハイパーバイザーは複数の仮想マシンを作り、それぞれが自分専用のCPU、メモリ、ディスクを持っているように見えます——しかし実際には、基盤となる物理ハードウェアを共有しています。

家を買うのではなく、大きな建物のアパートを借りるように考えてみてください。

建物のオーナー（AWS）は物理構造——配管、電気、セキュリティ——を保守します。あなたは1つの部屋を得ます。好きなように家具を置きます。毎月（あるいは毎時）払います。もっとスペースが必要になったら、より大きな部屋に移ります。引っ越したら、払うのをやめます。

それらの仮想マシンのレンタルのそれぞれが、AWSが**EC2インスタンス**——Elastic Compute Cloud——と呼ぶものです。

EC2はElastic Compute Cloudの略です。「Elastic（弾力的）」の部分が重要で、それは後で扱います。今のところは：EC2インスタンスは、時間単位で借りるコンピューターです。オペレーティングシステム、ネットワーク接続、コンピューティングパワーを持っています。物理サーバーがするのとちょうど同じように、あなたのアプリケーションを動かします。

**インスタンスを選ぶ：サイズが重要**

すべてのEC2インスタンスが同じではありません。AWSは数百のインスタンスタイプを提供しており、何のために最適化されているかに基づいてファミリーに整理されています。

**汎用**（例：`t3`、`m6i`）：バランスの取れたCPUとメモリ。ほとんどのウェブアプリケーションにとって良いデフォルトの選択。`t3`ファミリーはバースト可能です——低稼働期間中にCPUクレジットを蓄積し、バースト中にそれらを使います。開発環境と、変動するCPU需要を持つワークロードに最適。`m6i`ファミリーは一貫した、バーストしないパフォーマンスを提供します——持続的なCPUニーズを持つ本番ワークロードにより適しています。

**コンピュート最適化**（例：`c7g`）：メモリに対してより多くのCPU。動画エンコード、科学的モデリング、バッチ処理に最適。`c7g`の「g」のサフィックスは、インスタンスがAWS Gravitonプロセッサ——AWSが社内で設計したARMベースのチップで、多くのワークロードについて同等のx86インスタンスより優れた価格対性能を提供する——を使うことを意味します。

**メモリ最適化**（例：`r7i`）：CPUに対してより多くのメモリ。データベース、キャッシング、インメモリ分析に最適。より多くのデータをRAMに保つことでパフォーマンスが劇的に向上するデータベースを動かしているなら、Rファミリーが正しい出発点です。

**ストレージ最適化**（例：`i3`）：高速のローカルストレージ。非常に速いディスクI/Oを必要とするデータ集約的なワークロードに最適。これらのインスタンスのローカルNVMeストレージはEBSより大幅に速い——しかしそれは一時的でもあります。一時的なデータに使い、失っては困るものには使わないでください。

**高速コンピューティング**（例：`p4`）：GPUがアタッチされています。機械学習のトレーニングとグラフィックスのレンダリングに最適。これらのインスタンスは高価です——`p3.8xlarge`は1時間あたり12ドル超——しかしGPUの並列処理から恩恵を受けるワークロードには、代わりになるものがありません。

各ファミリーにはサイズがあります。`t3.micro`は2つの仮想CPUと1GBのメモリを持ちます。`t3.xlarge`は4つの仮想CPUと16GBを持ちます。`t3.2xlarge`はさらに倍になります。命名パターンは一貫しています。サフィックスは`nano`、`micro`、`small`、`medium`、`large`、`xlarge`、`2xlarge`、`4xlarge`、`8xlarge`、そしてその先へと進みます。

**AMI：マシンの開始状態**

EC2インスタンスを起動する前に、そのオペレーティングシステムと初期構成を選びます。AWSでは、これは**Amazon Machine Image**（AMI）と呼ばれます。

AMIはテンプレートです。それは以下を定義します：

- オペレーティングシステム（Amazon Linux、Ubuntu、Windows Serverなど）
- プリインストールされたソフトウェア
- 初期のディスク状態

AMIからインスタンスを起動すると、AWSはあなただけのためにそのテンプレートの新しいコピーを作ります。自分自身のAMIを作ることもできます——サーバーを思い通りに正確に構成したら、その状態をカスタムAMIとして「保存」し、同一のサーバーを素早く起動するのに使えます。これが、一貫した環境を規模を持ってデプロイする方法です。

AMIをレシピのように考えてください。レシピは料理を記述します。レシピに従うたびに、同じ料理が得られます。料理を永続的に変えたければ、レシピを更新します。

AWSはAMIのマーケットプレイスを提供しています——いくつかはAWSが保守し（Amazon Linux 2、Amazon Linux 2023）、いくつかは主要なLinuxディストリビューションが保守し（Ubuntu、Red Hat、SUSE）、いくつかはサードパーティのベンダーから来ます（あらかじめ構成されたデータベースサーバー、セキュリティアプライアンス、商用ソフトウェア）。ほとんどのウェブアプリケーションにとって、AWSが保守するAmazon LinuxのAMIまたはUbuntu LTSのAMIが正しい出発点です。

Nimbusのために、Leoは最新のAmazon Linux 2023のベースから始まり、Node.jsランタイム、アプリケーションのシステム依存関係、アプリケーションプロセスのためにあらかじめ作られたサービスファイルを追加したカスタムAMIを構築しました。このAMIから起動した新しいインスタンスは、90秒未満でトラフィックを処理し始めました——UserDataスクリプトを使ってすべてをゼロからインストールするときの4分のブート時間より大幅に速いものでした。

トレードオフがあります。カスタムAMIは保守される必要があります。システム依存関係やランタイムのバージョンを更新するたびに、AMIを再構築する必要があります。AMIを古くなるままにするチームは、時代遅れのソフトウェアでインスタンスを動かしていることに気づきます——セキュリティリスクです。Priyaは「最新のパッケージでAMIを再構築する」を月次のエンジニアリングのチェックリストに入れました。

「AMIを保存するのにいくらかかるんだ?」とTomは尋ねました。

AMIはEBSスナップショットとして保存されます——AMIのサイズについて、EBSスナップショットのレート（1GBあたり月およそ0.05ドル）を払います。Nimbusのアプリケーションスタックを持つ典型的なAmazon LinuxのAMIは約4GBでした。1GBあたり0.05ドルで：AMI 1つあたり月0.20ドル。ロールバックの目的で5つの歴史的なAMIを保持して：月1ドル。意味のあるコストではありません。

**UserData：ブートストラップスクリプト**

アプリケーションコードが変わるたびに新しいAMIを構築するのを避けようとしていたときにLeoが発見した、EC2のもう一つの構成オプションがあります。

EC2インスタンスを起動するとき、**UserDataスクリプト**——インスタンスが初めて起動するときに自動的に実行されるシェルスクリプト——を提供できます。それはインスタンスが「準備完了」とみなされる前に、rootとして実行されます。

Nimbusのために、UserDataスクリプトはこんな感じでした：

```bash
#!/bin/bash
yum update -y
yum install -y nodejs npm git
git clone https://github.com/nimbus-app/server.git /opt/nimbus
cd /opt/nimbus
npm install
systemctl enable nimbus
systemctl start nimbus
```

そのスクリプトはNode.jsをインストールし、最新のアプリケーションコードを取得し、依存関係をインストールし、アプリケーションサービスを開始します。ベースAMIから起動するすべての新しいインスタンスは、このスクリプトを実行し、現在のバージョンのアプリケーションがインストールされた状態で立ち上がります——自動的に。

このアプローチは、AMIをシンプルなまま（ただのベースOS）に保ち、UserDataがアプリケーションのセットアップを扱うことを意味します。トレードオフ：UserDataスクリプトは実行に時間がかかります。インスタンスはブートして準備完了になるのに3〜5分かかるかもしれません。起動時間が重要なアプリケーション——新しいインスタンスが素早く準備完了になる必要があるAuto Scalingのため——には、アプリケーションをカスタムAMIにあらかじめ焼き込むことでブート時間が大幅に短縮されます。

**キーペア：サーバーにアクセスする正しい方法**

前章の「Admin123」の大惨事を覚えていますか?

EC2インスタンスにログインする正しい方法は、**キーペア**を使うことです。

キーペアは暗号学的なペアです。公開鍵（AWSによってサーバーに保存される）と秘密鍵（あなたがダウンロードして秘密に保つファイル）。ログインするには、SSH——安全なプロトコル——をあなたの秘密鍵とともに使います。パスワードはありません。秘密鍵を失えば、アクセスを失います。SSHには「パスワードを忘れた」はありません。

これが重要なのは、キーペアが以下だからです：

- あなただけのもの
- 暗号学的に推測不可能
- AWSによって保存されない（あなたが秘密鍵を保持する）
- 取り消すのが簡単（サーバーから鍵を削除し、新しいペアを生成する）

PriyaはすでにNimbusのサーバーで鍵ベースのアクセスを設定していました。Admin123のサーバーは廃止されました。誰もそれを悲しみませんでした。

「で、もし誰かが侵入しようとして、転送中にキーペアを傍受したら?」とPriyaは尋ねました。彼女はすでに答えを出していました。秘密鍵はネットワークを通って移動することは決してありません。一度ダウンロードします。ローカルに保持します。それはあなたのマシンを決して離れません。

**キーペアを失ったら何が起きるか**

Leoは3週目にこの質問をしました。まだキーペアを失ってはいないが、それについて考えている人の特有のエネルギーで。

「秘密鍵ファイルを失ったら、何が起きるの?」

「インスタンスへのSSHアクセスを失うわ」とPriyaは言いました。

「永久に?」

「必ずしもそうじゃない。でも復旧のプロセスは不快よ。」

復旧のプロセス：インスタンスを停止し、そのルートEBSボリュームをデタッチし、アクセスを*持っている*別のインスタンスにアタッチし、ボリュームをマウントし、マウントしたボリュームの`authorized_keys`ファイルに新しい公開鍵を追加し、デタッチして元のインスタンスに再アタッチし、再起動する。

これは機能します。30〜60分かかり、慎重な実行を要します。1つ間違ったステップで、事態を悪化させることもあります。

代わりになるものは、アプリケーションがルートボリュームに重要なものを何も保存していないなら（あなたが本書のアドバイスに従い、データをS3とEBSに保存してきたから）：インスタンスを終了し、AMIから新しいものを起動する。その際に新しいキーペアを生成する。

「秘密鍵をどこか安全な場所に保存して」とPriyaは言いました。「そして決してEC2インスタンスには。」

Leoは`AWS_keys`とラベルの付いたデスクトップのフォルダを見ました。それからPriyaを。それからフォルダを暗号化されたパスワードマネージャーに移しました。

**セキュリティグループ：インスタンスのファイアウォール**

EC2インスタンスが起動するとき、それには**セキュリティグループ**——どのネットワークトラフィックがそれに到達でき、どのトラフィックを送り出せるかを制御する仮想ファイアウォール——が必要です。

セキュリティグループには2組のルールがあります。**インバウンド**（入ってくるトラフィック）と**アウトバウンド**（出て行くトラフィック）。

デフォルトでは、新しいセキュリティグループはすべてのインバウンドトラフィックをブロックし、すべてのアウトバウンドトラフィックを許可します。特定のソースに特定のポートを開けるために、インバウンドルールを追加します。

Nimbusのウェブサーバーのために、Priyaは以下を構成しました：

- `0.0.0.0/0`（インターネット全体）からのTCPポート443（HTTPS）を許可
- `0.0.0.0/0`（インターネット全体）からのTCPポート80（HTTP）を許可（アプリケーションで443にリダイレクト）
- オフィスのIPアドレスからのみのTCPポート22（SSH）を許可——インターネットからではなく

「待って——でも*なぜ*SSHをオフィスのIPだけに制限するの?」とMayaは尋ねました。

「なぜなら、SSHがインターネット全体に開いていると」とPriyaは言いました。「自動化されたボットが、認証情報の組み合わせを試して24時間ポート22を叩くからよ。私たちのログは失敗した試行で埋まる。そして、SSHデーモン自体にいつか脆弱性があれば、世界中のあらゆる攻撃者がそれを悪用しようとできる。」

「でも、もしLeoが家からログインする必要があったら?」

「VPN」とPriyaは言いました。

LeoはすでにVPNを設定していました。彼はこの質問を以前にもされたことのある人の表情をしていました。

データベースはまだアプリケーションと同じマシンに存在していました——しかしPriyaは、そうでなくなる日のために別のセキュリティグループを用意しました。データベースのポートはウェブサーバーのセキュリティグループからのトラフィックにのみ開かれ——インターネットからではなく、SSHから（直接のDBアクセスのため）でもなく、他のどこからでもなく。その間、彼女は共有インスタンスのセキュリティグループがデータベースのポートをインターネットにまったく露出しないことを確実にしました。データベースは、それを必要とするアプリケーション以外のすべてに対して見えないでしょう。

データベースに直接到達するには、攻撃者はまずウェブサーバーを侵害する必要があります。それが防御の最初の層でした。

「で、2つ目の層は?」とTomは尋ねました。

「データベースのためのIAM認証。そして転送中の暗号化。」

彼女は両方をセットアップのチェックリストに追加しました。

**EC2インスタンスメタデータとIMDSv2**

入門的なコンテンツではめったに説明されないとはいえ、実際に重要なEC2セキュリティのもう一つの部分があります。

アプリケーションがEC2インスタンスで動くとき、`http://169.254.169.254/latest/meta-data/`にある特別な内部エンドポイントに問い合わせて、インスタンスについての情報を取得できます。そのインスタンスID、そのリージョン、そのアベイラビリティーゾーン、そして——決定的に重要なことに——アタッチされたIAMロールに関連する一時的なIAM認証情報です。

これが、EC2インスタンス上のアプリケーションが、ハードコードされた認証情報なしにAWSサービスを呼び出す方法です。それはメタデータサービスに問います。「今、どの認証情報を使うべきか?」メタデータサービスは、期限切れになり自動的にローテーションする一時的な認証情報を返します。

セキュリティの問題：このメタデータサービスの古いバージョン（IMDSv1）は、インスタンス上のどんなプロセスからのどんなリクエストにも応答していました。アプリケーションにサーバーサイドリクエストフォージェリ（SSRF）の脆弱性——攻撃者がサーバーに攻撃者の選んだURLを取得させられるバグ——があれば、攻撃者はその脆弱性を使って`http://169.254.169.254/latest/meta-data/iam/security-credentials/`を取得し、インスタンスのIAM認証情報を取り出せました。

この攻撃は実際の侵害で使われてきました。

**IMDSv2**（Instance Metadata Service version 2）は、メタデータサービスが応答する前にセッショントークンを要求することでこれを修正します。トークンはPUTリクエストを通じて取得されます。SSRF攻撃は、たいていGETリクエストを使うので、PUTのステップを完了できません——だからトークンを得られず、メタデータは返されません。

「IMDSv2を有効にすべき?」とLeoは尋ねました。

「今は新しいインスタンスのデフォルトよ」とPriyaは言いました。「でも既存のインスタンスには、オプトインしなきゃいけない。」

彼女はその日の午後、すべての既存のNimbusインスタンスでそれを有効にしました。

**インスタンスのライフサイクル：永遠ではない**

これは多くの初心者が見落とすことです。

EC2インスタンスはデフォルトでは永続的ではありません。インスタンスを停止すると、コンピュートリソースは解放されます。再び起動すると、異なる物理ハードウェアで動くかもしれません。*インスタンス自体に*（そのルートボリュームに）保存されたデータは停止/開始のサイクルを生き延びます——しかしパブリックIPアドレスは変わります。

インスタンスを*終了*すると、それは消えます。別のストレージがアタッチされている（第6章で扱います）のでない限り、インスタンス上のデータは消えます。

EC2インスタンスがありうる4つの状態：

**Pending（保留中）**：インスタンスが起動中です。ハードウェアが割り当てられましたが、ブートを終えていません。

**Running（実行中）**：インスタンスがアクティブでアクセス可能です。あなたはそれに対して払っています。初回起動時、これはUserDataスクリプトが実行されるタイミングでもあります。

**Stopping/Stopped（停止中/停止済み）**：インスタンスがシャットダウンされています。ルートEBSボリュームは保持されます。コンピュートには払っていませんが、アタッチされたEBSストレージにはまだ払っています。

**Shutting-down/Terminated（シャットダウン中/終了済み）**：インスタンスが削除されています。EBSボリュームを永続化するよう構成していない限り、それらのデータは消えます。

この「一時性（エフェメラリティ）」は、実はバグではなく機能です。それは、サーバーを起動し、使い、捨てられることを意味します。それは水平スケーリングを可能にします。しかしそれはまた、重要なデータをEC2インスタンス*自体に*決して保存すべきでないことも意味します。

では、データはどこに存在するのでしょうか?

別のストレージに。それは次の2つの章で扱います。

こう思っているかもしれません。インスタンスが再起動するたびに新しいIPアドレスを得るなら、アプリケーションはどうやって安定したアドレスを保つのか? AWSにはElastic IP——あなたが所有し、再起動の後でも同じままの静的なパブリックIP——という解決策があります。コストについての注記：2024年2月以来、AWSはすべてのパブリックIPv4アドレスに対して小さな時間単位の料金を課しています——Elastic IP（アタッチされていてもいなくても）と、インスタンスの自動割り当てされたパブリックIPの両方に。パブリックIPv4はもう無料ではありません。これは、ロードバランサーの後ろのプライベートサブネットにインスタンスを保つもう一つの理由です。

ロードバランサーの後ろのアプリケーション——あらゆる本番ウェブアプリケーションにとって正しいアーキテクチャ——には、Elastic IPはまったく必要ありません。ユーザーはロードバランサーの安定したDNS名に接続します。ロードバランサーはVPC内のプライベートIPアドレスでインスタンスに接続します。インスタンスは出入りし、新しいIPを得て、スケールインやスケールアウトできます——ロードバランサーがそのすべてを透過的に扱います。Elastic IPは特定のユースケースのためのものです。クライアントがIPで直接接続するサーバー、安定したアドレスを持つ踏み台ホスト、何か特定の理由でロードバランサーの後ろにないアプリケーション。

Leoは当初、NimbusのウェブサーバーにElastic IPを使う計画を立てていました。Priyaは、ロードバランサーがあれば、ウェブサーバーのIPアドレスは外部のクライアントには無関係だと指摘しました。ロードバランサーが安定したDNS名を持っていました。その後ろのインスタンスは、設計上、使い捨てでした。

「じゃあElastic IPは、ルールじゃなくて例外のためのものなんだね」とLeoは言いました。

「正解」とPriyaは言いました。「そして、自分がそれに手を伸ばしているのに気づいたら、アーキテクチャに代わりにロードバランサーがあるべきじゃないかと問いなさい。」

**「Elastic」が意味するもの**

EC2はElastic Compute Cloudの略だと言いました。それの何が弾力的なのでしょうか?

2つのことです：

**垂直の弾力性**：インスタンスのサイズを変更できます。インスタンスを停止し、`t3.micro`から`t3.xlarge`に変え、再起動する。より多くのCPUとメモリ、同じアプリケーション、同じセットアップ。

**水平の弾力性**：より多くのインスタンスを追加できます。1台の大きなサーバーの代わりに、ロードバランサーの後ろで10台の中くらいのサーバーを動かす。トラフィックが下がったら、インスタンスを取り除き、それらに払うのをやめる。

両方のアプローチが「1台のサーバー、多すぎるトラフィック」の問題を解決します。それらには異なるトレードオフがあり、第7章でAuto Scalingを物語に加えるときにそれを探ります。

重要な洞察：EC2では、コンピューティングパワーは*買う*ものではなく、*ダイヤルで調整する*ものです。もっと必要? ダイヤルを上げる。少なくていい? 下げる。それに応じて払う。

Mayaはインスタンスタイプの表を見ました。「サーバーをただ大きくできるなら、なんで中くらいのを10台も使うの?」

「なぜなら」とLeoは言いました。「1台の大きなサーバーは、やっぱり1台のサーバーだ。ダウンしたら、全部ダウンする。中くらいのサーバー10台なら、1台が故障しても9台が動き続ける。」

「それに」とPriyaが付け加えました。「サーバーを再起動せずに大きくすることはできない。小さいのが10台なら、動いているものに触れずにもっと追加できる。」

Tomはすでにノートに「再起動 = ダウンタイム」と書いていました。

## 強みと限界

**EC2が強力な理由**：

- 完全な制御。OS、ソフトウェア、構成を選びます。それはあなたのコンピューターです。
- 柔軟なサイジング。あらゆるユースケースにまたがる数百のインスタンスタイプ。
- 管理するハードウェアなし。AWSが物理層を扱います。
- Amazon Linux、Windows、UbuntuのAMIには、60秒の最小で、秒単位の課金。（RHELやSUSEのような一部の商用LinuxのAMIは、まだ時間単位で課金します——AMIの課金条件を確認してください。）インスタンスを停止すれば、払うのをやめます。
- すべてと連携します。EC2は、他のほとんどのAWSサービスがその上に構築される基盤です。
- 複数の価格モデル（オンデマンド、リザーブド、スポット）が、予測可能または柔軟なワークロードに対して
  大幅なコスト最適化を可能にします——第27章で詳しく扱います。

**複雑になるところ**：

- オペレーティングシステムのパッチ適用と更新の責任はあなたにあります。（責任共有
  モデル——これがあなたのものである「クラウド内の」部分です。）
- OSのパッチ適用は任意ではありません。パッチが当たっていないEC2インスタンスは、クラウドの侵害で最も一般的な
  攻撃ベクトルの一つです。AWS Systems Manager Patch Managerがこれを自動化
  できます——しかし構成して監視しなければなりません。
- 規模でEC2を管理することは、潜在的に何千ものマシンにまたがって、インスタンスの状態、AMI、セキュリティパッチ、
  ライフサイクルを管理することを意味します。それは運用上のオーバーヘッドです。
- EC2はすべてに対する正しい答えではありません。頻繁には実行されない
  イベント駆動のコードには、Lambda（第20章）の方が安くシンプルです。コンテナ化された
  ワークロードには、ECSとEKS（第21章）の方が優れたリソース効率を提供します。
- 使われていないインスタンスもお金がかかります。インスタンスを停止すれば、コンピュートに払うのを
  やめます——しかしストレージがアタッチされていれば、それにはまだ払います。

**EC2をいつ使わないかの判断**：EC2は最大の制御を与えてくれます——しかし制御には運用上のコストがあります。動かすすべてのEC2インスタンスは、パッチを当て、監視し、最終的に交換しなければならないものです。頻繁には実行されないアプリケーション（Lambdaの方が安い）、数十または数百のインスタンスに水平にスケールする必要のあるアプリケーション（コンテナの方が効率的）、またはデータベースやその他のマネージドワークロード（RDS、ElastiCache）には、完全マネージド型のサービスがささやかなコストのプレミアムで大幅な運用上のオーバーヘッドを排除します。EC2は、それが提供する制御が必要なときの正しい選択です——デフォルトではありません。

Priyaにはヒューリスティックがありました。「必要なことをするマネージドサービスで満足できるなら、マネージドサービスを使う。マネージドの選択肢が存在しないか、合わないときにEC2を使う。」

Leoは当初これに反発しました。「でもEC2の方が選択肢が多い。」

「選択肢はオーバーヘッドよ」とPriyaは言いました。「すべての選択肢が必要なわけじゃない。必要なのは、正しい構成で、確実に保守されたもの。」

**EC2プレイスメントグループ：インスタンスがどこに着地するかを制御する**

EC2はインスタンスが何であるか——そのサイズ、そのOS、その構成——を制御させてくれます。それはまた、**プレイスメントグループ**という機能を通じて、インスタンスが物理的に*どこに*着地するかを限定的に制御させてくれます。

デフォルトでは、AWSは可用性を最大化するためにインスタンスを物理ハードウェアにまたがって分散させます。しかし特定のワークロードには、そのデフォルトを上書きしたくなります——インスタンスをより近づけるか、それらが遠く離れたままでいることを保証するために。

3つのプレイスメントグループのタイプ：

**クラスター**：単一のアベイラビリティーゾーン内で、たいてい同じ物理ラックか隣接するハードウェアで、インスタンスを近くにまとめます。結果は、グループ内のインスタンス間の最低のネットワークレイテンシと最高のネットワークスループットです——インスタンス間で10Gbps以上のネットワークスループットを伴って（これを拡張ネットワーキング/ENAと混同しないでください。それはプレイスメントグループとは独立したインスタンスごとのネットワーキング機能です）。これはHPC（ハイパフォーマンスコンピューティング）、大規模なMLトレーニングジョブ、そしてインスタンスが互いに多くのデータを送ることに多くの時間を費やす密結合の並列ワークロードのための選択です。トレードオフは可用性です。基盤となるハードウェアのセグメントが故障すれば、クラスター内のすべてのインスタンスが同時に影響を受けうります。

**パーティション**：インスタンスを論理的なパーティションにまたがって分けます。各パーティションは自身のハードウェアのセット——別々のラック、別々の電力、別々のネットワークスイッチ——に位置します。パーティション内のインスタンスは互いにハードウェアを共有しますが、パーティションは他のパーティションとハードウェアを決して共有しません。この設計はハードウェア障害の爆発半径を制限します。1つのラックがダウンしても、1つのパーティションに影響しますが、他には影響しません。パーティションプレイスメントグループは、大規模な分散・複製されたワークロード——Apache Hadoop、Apache Cassandra、Apache Kafka——のために作られています。ラックレベルの障害がクラスター全体をダウンさせないだけの十分な障害の隔離が欲しいところで。

**スプレッド**：各インスタンスを完全に別々の基盤ハードウェアに配置します。インスタンス間の最大の隔離です。物理ホストを決して共有してはならない5つの重要なアプリケーションインスタンスがある場合（単一のハードウェア障害が決して2つ以上をダウンさせるべきでないから）、スプレッドが答えです。限界：**アベイラビリティーゾーンごと、プレイスメントグループごとに7インスタンス**。スプレッドは、大きなフリートのためではなく、コロケーションに耐えられない少数の重要なインスタンスのために設計されています。

「じゃあクラスターは速度のため、スプレッドは隔離のため、そしてパーティションは、ある程度のクラスタリングとある程度の隔離の両方が必要な分散システムのためってこと?」とMayaは尋ねました。

「十分近いわ」とPriyaは言いました。「クラスター：インスタンス間の低レイテンシ、1つの大きなリスク。スプレッド：最大の隔離、AZごと7という厳しい制限。パーティション：大きな分散システムのための構造化された隔離——各インスタンスがどのパーティションに入るかを制御する。」

Nimbusの現在のアーキテクチャには、これらのどれもまだ当てはまりませんでした。しかし、それらが存在することを知っていることは、いつそれらに手を伸ばすかを知ることを意味しました——そしてより差し迫っては、「低いノード間レイテンシを必要とするHPCワークロード」についての試験問題が実際に何を尋ねているかを知ることを。

## まとめ

偶然に起動されたインスタンスは、決して本番サーバーになるはずがありませんでした。EC2を適切に理解することは、キャパシティの問題を解決しただけではありません——それは、ほぼ後続のすべての章で出てくる新しい一連の概念を導入しました。インスタンスタイプ、AMI、キーペア、セキュリティグループ、適正サイジングは、EC2の豆知識ではありません。それらは、本書の残りがその上に構築される語彙です。ここでそれらを学べば、他のすべてがより理にかなうようになります。

- **EC2インスタンス**はAWSで借りる仮想マシンです。インスタンスタイプはユースケースで整理されています。汎用、コンピュート最適化、メモリ最適化、ストレージ最適化。正しいファミリーを選び、想像上の最悪のケースではなく——実際のワークロードメトリクスに適正サイジングしましょう。
- **AMI**（Amazon Machine Image）は、インスタンスのOSと初期構成のテンプレートです。カスタムAMIは一貫した、再現可能なデプロイメントを可能にします。
- **キーペア**はEC2インスタンスにアクセスする安全な方法です。**セキュリティグループ**はインスタンスのファイアウォールです——SSHを既知のIPに制限し、データベースのポートをアプリケーションのセキュリティグループにのみロックしましょう。
- **IMDSv2**は、インスタンスメタデータサービスからのSSRFベースの認証情報の盗難から守るため、すべてのインスタンスで有効にされるべきです。
- EC2インスタンスはデフォルトでは永続的ではありません。終了したインスタンスはローカルデータを失います——重要なデータはインスタンスのディスクではなく、S3またはEBSに保存しましょう。

- **再起動でパブリックIPが変わります。** アプリケーションが安定したIPアドレスを必要とするなら、

  2024年2月以来、AWSはすべてのパブリックIPv4アドレスを時間単位で課金します——Elastic IP
  （アタッチされていてもいなくても）と自動割り当てされたパブリックIPの両方に。
- **オンデマンド、リザーブド、スポット**の価格モデルは、ドメイン4で重点的にテストされます。
  第27章でそれらを扱います。今のところは、オンデマンドはコミットメントなしで秒単位で
  払うことを意味すると知っておいてください。
- **セキュリティグループはステートフルです。** あるポートでインバウンドトラフィックを許可すると、
  戻りのトラフィックは明示的なアウトバウンドルールなしに自動的に許可されます。NACL
  （第15章で扱う）はステートレスです——インバウンドとアウトバウンドの両方のルールを要求します。
- **プレイスメントグループ：** クラスター = インスタンス間の最低のレイテンシ（HPC、MLトレーニング——しかしグループにとっての単一障害点のリスク）。パーティション = パーティションごとの障害の隔離を伴う分散システム（Hadoop、Kafka、Cassandra）。スプレッド = 最大のインスタンスの隔離、AZごと最大7。試験問題のパターン：「密結合のHPCワークロードがノード間で最大のネットワークスループットを必要とする」 → クラスタープレイスメントグループ。

C) 単一の大きなインスタンスサイズの汎用インスタンス  
D) 製品カタログが速いディスクアクセスを必要とするため、ストレージ最適化インスタンス

**ヒント1**：ワークロードは「CPU集約的」と表現されています。どのインスタンスファミリーが
CPUに最適化されていますか?

**ヒント2**：シナリオは「セールイベント中のトラフィックスパイク」に言及しています。固定数の
インスタンスは変動するトラフィックを効率的に処理しません。どのAWSの機能がこれを扱いますか?

**ヒント3**：コンピュート最適化インスタンスはCPU負荷の高い作業を処理します。Auto Scalingは
需要に基づいてインスタンスを追加・削除します。一緒に、それらは両方の要件に答えます。

**解答**: B

**解説**：コンピュート最適化インスタンス（`c`ファミリーのような）は、CPU集約的なワークロードに対して
1ドルあたりより多くのCPUを提供します。Auto Scalingは負荷に基づいてインスタンスの数を
自動的に調整します——セールイベント中にインスタンスを追加し、トラフィックが通常に戻ったら
それらを削除する。この組み合わせはパフォーマンスとコストの両方を最適化します。

**なぜAではないのか?** メモリ最適化インスタンスは、大量のRAMを必要とするワークロード
（データベース、インメモリキャッシュ）のために設計されています。これはCPUバウンドのワークロードです。そして固定の
インスタンス数は、過剰プロビジョニング（無駄）か過小プロビジョニング（障害）のどちらかを意味します。

**なぜCではないのか?** 汎用インスタンスはバランスのためにいくらかのCPU効率を引き換えにします。
既知のCPU集約的なワークロードには、コンピュート最適化の方が適切です。そして単一の
大きなインスタンスは単一障害点です。

**なぜDではないのか?** ボトルネックはディスクI/Oではなく、CPUです。ストレージ最適化インスタンス
は、ローカルストレージへの非常に高いスループットを必要とするワークロードのために設計されています。
