Nimbusの最初のレストランパートナーのキッチンは、午前10時でもにんにくと温かいパンの香りがしていました。マヤはデモのためにそこにいて、料理人がアプリをスワイプして代替メニューを記録するのを見ていました。エビが一時的に切れていたので、エビの代わりに魚です。スワイプが行われました。メニューが更新されました。街の別の場所にいる顧客は、数秒以内にその変更を見ました。

それは魔法のように感じられました。

オフィスに戻ると、その魔法は遅くなり始めていました。

メニューテーブルには5万件の商品がありました。

それは287軒のレストランにまたがるものでした。パートナー数は、ロードバランサーの時代の47軒から、1年足らずで300軒近くにまで爆発的に増えていました。それぞれに毎日のスペシャル、季節限定商品、地域限定バリエーションがありました。一部の商品にはモディファイア（サイズ、辛さレベル、タンパク質の選択）がありました。一部には他の商品を参照するコンボ取引がありました。一部は平日のみ、昼食時のみ、または特定の都市でのみメニューに表示されていました。

レストランのフルメニューを取得するSQLクエリは、かつては200ミリ秒で返ってきていました。

今は4秒かかっていました。

4秒は、誰かが注文を出すことと、誰かがアプリを閉じることとの差です。レオはクエリプランを実行しました。トムはインデックス構成を調べました。プリヤは読み取りレプリカの数を増やしました。しかし、どれも意味のある違いをもたらしませんでした。

**すべてをテーブルに収めることの問題**

リレーショナルデータベースの核心的な緊張はこうです。これらは*固定された*形状で*構造化された*データを保存するように設計されています。

もしすべてのメニュー項目が同じフィールド（名前、価格、説明、カテゴリ）を持っていれば、SQLは完璧でしょう。きれいな`menu_items`テーブル、各項目の行、そして意味の通るクエリを持てるでしょう。

しかし、実際のメニューはそのようには機能しません。

ある項目には「辛さレベル」のモディファイアがあるかもしれません。別の項目には「タンパク質の選択」があるかもしれません。3番目の項目にはネストされたコンボがあるかもしれません。「ファミリーミールを注文すると、メイン2つ、サイド2つ、ドリンクがつきます」のように。データの構造は*項目ごとに*異なります。

SQLでは、2つの選択肢があります。

**オプション1**：可能なすべてのモディファイアに対応する列を作成します。これにより、ほとんどの列がほとんどの場合空になる非常に幅広いテーブルが生まれます。

**オプション2**：別のモディファイアテーブルを作成し、メニュー項目テーブルに結合します。これは機能しますが、複雑なメニューには複数の結合が必要となり、高い読み取り量で5万件の項目を扱う場合、これらの結合は高価になります。

「3番目の選択肢があります」と、隅で静かにドキュメントを読んでいたプリヤが言いました。

彼女は新しいタブを開きました。「もしデータがテーブルに収まる必要がなかったとしたら？」

**データについて考える別の方法**

リレーショナルデータベースは、データをテーブル内の行として保存します。各行はテーブルのスキーマに準拠する必要があります。スキーマは事前に合意されます。

NoSQLデータベースは、データを異なる方法で保存します。一般的なアプローチの1つは*ドキュメントモデル*です。各レコードは自己完結型のドキュメント（通常はJSON）として保存され、同じコレクション内のドキュメントが同じフィールドを持つ必要はありません。

ドキュメントモデルでのメニュー項目は、次のようになるかもしれません。

```json
{
  "itemId": "ITEM-001",
  "restaurantId": "NIMBUS-047",
  "name": "Shrimp Arepa",
  "price": 3200,
  "modifiers": [
    { "name": "Spice Level", "options": ["mild", "medium", "hot"] },
    { "name": "Protein", "options": ["shrimp", "fish", "mixed"] }
  ],
  "available": true,
  "seasonalUntil": "2024-03-31"
}
```

別の項目は、まったく異なる外観になるかもしれません。

```json
{
  "itemId": "ITEM-002",
  "restaurantId": "NIMBUS-047",
  "name": "Family Feast",
  "price": 9800,
  "includes": ["ITEM-010", "ITEM-011", "ITEM-015", "ITEM-020"],
  "servings": 4,
  "available": true
}
```

異なる形状。同じコレクション。問題なし。

「つまり、データベースはテーブルというよりもファイリングシステムのようなものだ」とマヤは言いました。

「その通り」とプリヤは言いました。「どんなドキュメントもどんな引き出しに入れられる。ドキュメントを固定サイズに合わせて切る必要はない。」

**DynamoDBの登場**

Amazon DynamoDBは、AWSのマネージドNoSQLデータベースサービスです。データを（行ではなく）アイテムとして保存し、アイテムはテーブルにまとめられます（命名はSQLと似ていますが、動作は異なります）。

DynamoDBテーブル内の各アイテムには、それを一意に識別する**プライマリキー**が必要です。それ以外はすべて柔軟です。

プライマリキーは、次の2つの形式のいずれかになります。

**パーティションキーのみ**：すべてのアイテムにわたって一意でなければならない単一の属性。

**パーティションキー + ソートキー（複合プライマリキー）**：2つの属性が*合わせて*一意の組み合わせを形成します。これにより、同じパーティションキーを持つ複数のアイテムを、ソートキーで区別して持つことができます。

Nimbusのメニューの場合：

- パーティションキー：`restaurantId`
- ソートキー：`itemId`

これは、特定のレストランのすべての項目を効率的に取得できることを意味します。DynamoDBは、どのパーティションを調べればよいかを正確に把握しています。

「なぜパーティションキーと呼ばれるのですか？」とトムは尋ねました。

「もし誰かが侵入を試みたら？」とプリヤは尋ねました。「パーティションキーが推測可能だったら、誰かが1つのパーティションに書き込みでスパムを送って、意図的にホットスポット状態を引き起こせるのでは？」

「ええ」とレオは言いました。「それは実際、設計の悪いテーブルに対するサービス拒否（DoS）の手口です。それが、高カーディナリティのキーを選ぶもう1つの理由です。」

プリヤはそれを書き留めました。

**DynamoDBが内部でデータを保存する方法**

DynamoDBは、巨大なサイズまで水平にスケールするように構築されています。これは*パーティショニング*によって実現されます。データはパーティションキーに基づいて多数の物理マシンに分割されます。

アイテムを書き込むと、DynamoDBはパーティションキーの値をハッシュ化し、そのハッシュを使用して、どの物理パーティション（したがってどのサーバー）がアイテムを保存するかを決定します。アイテムを読み取るとき、DynamoDBは同じ計算を行って瞬時にそれを見つけます。

郵便システムのように考えてみてください。すべての封筒に郵便番号があれば、郵便サービスはどこに属するかを把握するためにすべての封筒を読む必要はありません。郵便番号で仕分けします。DynamoDBはパーティションキーのハッシュで仕分けします。

「待って、でも*なぜ*そのようにするのですか？」とマヤは尋ねました。「なぜパーティションキーの選択がそれほど重要なのですか？何でも選べばいいわけではないのですか？」

これは正しい問いです。パーティションキーは、DynamoDBスキーマにおける最も重要な設計上の決定です。理由はこうです。

低カーディナリティのパーティションキー（たとえば`available: true/false`や`category: "main/side/drink"`）を選ぶと、ほとんどのデータが同じ少数のパーティションに集中します。DynamoDBはこれを「ホットパーティション」と呼びます。1つのサーバーがトラフィックの大部分を処理します。そのサーバーが過負荷になります。DynamoDBはリクエストのスロットリングを開始します。ユーザーはエラーを見始めます。

- **良い**：高カーディナリティ、均等に分散された値（多くのレストランを持つ`restaurantId`）
- **悪い**：低カーディナリティ（`true/false`、`category`）—ほとんどのデータが少数のパーティションに集中し、「ホットスポット」を生み出す

「つまり、`available: true`をパーティションキーとして使ったら」とレオはゆっくりと言いました。「利用可能なすべての項目が同じパーティションに積み上がる。」

「そして、あなたのデータベースは夕食のラッシュで溶けてしまう」とプリヤは確認しました。

レオはゆっくりとラップトップを閉じました。

**スケールでの読み取りと書き込み**

DynamoDBは、毎秒数百万のリクエストを処理できます。しかし、どれだけのキャパシティをプロビジョニングすべきかを知る必要があります。

キャパシティモードは2つあります。

**プロビジョンドキャパシティ**：希望する読み取りユニットと書き込みユニットの数を指定します。DynamoDBはそのキャパシティを予約し、それを超えるトラフィックをスロットリングします。予測可能なコスト、リクエストあたりの低価格。

ユニットには正確な定義があり、試験ではそれらを知っていることが期待されます。1つの**読み取りキャパシティユニット（RCU）**は、最大4 KBのアイテムに対する毎秒1回の強い整合性読み取り、または同じサイズの2回の結果整合性読み取りです。1つの**書き込みキャパシティユニット（WCU）**は、最大1 KBのアイテムに対する毎秒1回の書き込みです。より大きなアイテムは比例してより多くを消費します。12 KBのアイテムを強い整合性で読み取ると3 RCUかかり、3 KBのアイテムを書き込むと3 WCUかかります。

**オンデマンドキャパシティ**：DynamoDBは実際のトラフィックに合わせて自動的にスケールします。日常的なキャパシティ計画は不要です。リクエストあたりのコストは高くなりますが、運用上はずっとシンプルです。ただし、テーブルの最近のトラフィックパターンをはるかに超える突然のスパイクが急速に増加すると、それでもスロットリングが発生する可能性があります。

Nimbusの場合、メニューは書き込まれるよりもはるかに頻繁に読み取られます。顧客がアプリを開いてメニューを閲覧する、それは多くの読み取りです。レストランパートナーが週に2回メニューを更新する、それはたまの書き込みです。

「今のところオンデマンドが理にかなっている」とトムは言いました。「私たちのトラフィックパターンはまだ分からない。プロビジョニング不足でスロットリングされるよりも、リクエストあたり多く払う方がいい。」

しぶしぶのインフラの知恵。トムからの。チームは正式に成長していました。

「それは月にいくらかかる？」とトムは尋ね、料金計算ツールを開きました。

「現在の読み取り量、1日約4万回の読み取りなら、オンデマンドは月に約12ドル」とレオは言いました。「プロビジョンドは、うまく調整すれば4ドルに近い。でも、キャパシティを手動で設定する必要があり、推測を間違えるとスロットリングのリスクがある。」

トムは両方の数字を書き留めました。彼はいつも数字を書き留めていました。

**整合性：データはどれくらい新鮮か？**

DynamoDBは、複数のアベイラビリティーゾーンにわたってデータを自動的にレプリケートします。それは耐久性には素晴らしいことですが、同時に、読み取り整合性について明確に考える必要があることを意味します。

DynamoDBから読み取るとき、選択肢があります。

**結果整合性読み取り**：これがデフォルトです。より安価で、結果が最近完了した書き込みよりも一時的に遅れている可能性があります。

**強い整合性読み取り**：テーブルまたはローカルセカンダリインデックスに対する読み取りでは、DynamoDBは成功した以前の書き込みからの最新のコミット済み値を返すことができます。これはより多くの読み取りキャパシティを消費し、グローバルセカンダリインデックスでは利用できません。

メニューデータの場合、結果整合性で問題ありません。1ミリ秒古いメニュー項目は問題になりません。

注文確認データ（「この注文は出されたか？」）については、強い整合性が欲しいでしょう。顧客は、注文がたった今保存されたのに「再試行してください」というメッセージを見るべきではありません。

「銀行残高をアプリで確認するのと、銀行に直接電話するのとの違いのようなものだ」とマヤは言いました。「アプリは30秒遅れているかもしれない。電話は常に最新だ。」

こう思っているかもしれません。DynamoDBが複数のAZにわたって自動的にレプリケートするなら、なぜ整合性モードが重要なのか？答えはこうです。レプリケーションには小さいながらもゼロではない時間（通常はミリ秒）がかかります。結果整合性読み取りは、まだ最新の書き込みを受け取っていないレプリカから提供されるかもしれません。強い整合性読み取りは、常にデータのプライマリコピーに接続します。ほとんどのユースケース（メニュー項目、製品カタログ、ユーザープロファイル）では、その遅れは知覚できません。読み取りの瞬間に正確性が重要なユースケース（支払い確認、在庫の利用可否）では、強い整合性が欲しいでしょう。

**セカンダリインデックス：プライマリキーを超えたクエリ**

プライマリキーが許可する以外の方法でデータにアクセスする必要がある場合はどうでしょうか？

DynamoDBは**セカンダリインデックス**をサポートしています。これは、同じデータを異なる属性を使ってクエリできるようにする代替キーです。

**ローカルセカンダリインデックス（LSI）**：テーブルと同じパーティションキーを使用しますが、異なるソートキーを使います。テーブル作成時に定義する必要があり、後から追加できません。テーブルのプロビジョンドキャパシティを共有します。LSIはパーティションを共有するため、強い整合性読み取りをサポートします。

**グローバルセカンダリインデックス（GSI）**：テーブルのプライマリキーとは異なる、独自のパーティションキーとソートキーを持つ完全に独立したインデックスです。テーブルの存在後に追加または削除でき、これが柔軟性を与えます。テーブルとは別の独自のプロビジョンドキャパシティ設定を持ちます。

Nimbusの場合：価格帯で項目をクエリする必要があれば、GSIがそれをサポートできます。ただし1つのルールを念頭に置く必要があります。パーティションキーは*等価*比較のみを受け付けるため、（範囲指定したい）`price`は**ソートキー**でなければならず、カテゴリや`cuisineType#region`のようなグループ化属性をGSIパーティションキーとします。これがまさに、以下のウォークスルーで構築されるインデックスです。

LSIを選べば、強い整合性と共有キャパシティが得られますが、テーブル作成時にその設計に固定されます。GSIを選べば、後から追加できる柔軟性と独立したスケーリングが得られますが、インデックスに対する強い整合性読み取りができなくなります。

**GSIクエリのウォークスルー**

プリヤは具体的な例をたどっていきました。Nimbusは「料理ジャンルで探す」機能をサポートしたいと考えていました。すべてのパートナーレストランにわたって、特定の料理ジャンルの利用可能なすべての料理を表示するのです。

メインテーブルは`restaurantId`をパーティションキー、`itemId`をソートキーとしています。「cuisineType = Colombianのすべての項目」を効率的にクエリすることはできません。それには、すべてのパーティションにわたるスキャンが必要になるでしょう。

彼らはGSIを作成しました。

- GSIパーティションキー：`cuisineType#region`（例：「Colombian#NYC」、「Mexican#Chicago」）
- GSIソートキー：`price`

GSIは、各項目の射影（閲覧ページに必要なフィールドだけ）をインデックスストレージに複製します。これで、`cuisineType#region = "Colombian#NYC"`でのGSIに対するクエリは、インデックスのそのパーティションに直接アクセスします。

「なぜ`cuisineType`だけを使わないのですか？」とレオは尋ねました。

「cuisineType単独では低カーディナリティだからです」とプリヤは言いました。「コロンビア、メキシコ、タイ、全部で20個の値。またホットパーティションです。リージョンを付加すると、Colombian#NYC、Colombian#Chicago、Colombian#LAになります。パーティションが増え、分散が良くなります。」

「ちょっと無理やりな感じがしますね。」

「これは標準的なDynamoDBのパターンです。パーティションキーシャーディングと呼ばれます。ときにはツールに合わせて作業する必要があります。」

コードでのGSIクエリは次のようになりました。

```python
response = dynamodb.query(
    TableName='menu',
    IndexName='cuisineType-price-index',
    KeyConditionExpression='#ct = :ct AND price BETWEEN :lo AND :hi',
    ExpressionAttributeNames={'#ct': 'cuisineType#region'},
    ExpressionAttributeValues={
        ':ct': {'S': 'Colombian#NYC'},
        ':lo': {'N': '1000'},
        ':hi': {'N': '2500'}
    }
)
```

これは、ニューヨーク市で10ドルから25ドルの間の価格のすべてのコロンビア料理を、価格順にソートして、約4ミリ秒で返しました。

「古いSQLクエリより1000倍速い」とレオは言いました。

「1つのインデックスの1つのパーティションにしか触れていないからです」とプリヤは確認しました。「結合されたテーブルのすべての行をスキャンしているのではありません。」

**DynamoDB Streams：変更に反応する**

「メニュー項目が更新されたときに何が起きるか、考えたことはありますか？」とプリヤはある朝尋ねました。「レストランパートナーが価格を変更する。検索インデックスを更新する必要がある。ElastiCacheのエントリを無効化する必要がある」—次章で出会うキャッシュサービスです—「そして、分析パイプラインのために変更をログに記録する必要がある。」

「それを全部APIハンドラーでやることもできる」とレオは言いました。「書き込みが起きたら、すべての下流の更新をトリガーする。」

「そして、そのうちの1つが失敗したら？」

「そのときは…リトライする。」

「書き込み後、下流の更新の前にEC2インスタンスがクラッシュしたら？データは保存されているのに、その変更を誰も知らない。」

レオはそれについて考えました。

「更新は保証される必要がある」と彼は言いました。「アプリケーションコードが途中で失敗したとしても。」

これが**DynamoDB Streams**が解決するものです。

DynamoDB Streamsは、DynamoDBテーブル内のすべてのアイテム変更を時系列順のログとしてキャプチャします。すべての挿入、更新、削除がイベントとしてストリームに書き込まれます。ストリームはイベントを24時間保持します。

ストリームにLambda関数をアタッチできます。アイテムが変更されるたびに、Lambda関数はアイテムの変更前と変更後の状態とともに呼び出されます。Lambdaは次のことができます。

- 検索インデックス（OpenSearch）を更新する
- ElastiCacheのキャッシュエントリを無効化する
- 別のシステムに通知を送る
- 分析パイプラインに供給する
- 変更を別のテーブルまたはデータベースに複製する

決定的な違い：Streamsは書き込みを下流の影響から分離します。DynamoDBの書き込みは、Lambdaが成功するかどうかとは独立して成功します。Lambdaが失敗すると、DynamoDBはそれをリトライします。書き込み後にアプリケーションがクラッシュしても、ストリームイベントはまだそこにあります。Lambdaは復旧したときにそれを処理します。

「つまり、DynamoDBに書き込むと」とレオはゆっくりと言いました。「DynamoDBは、私たちがクラッシュしても、下流の処理が最終的に行われることを保証する。」

「その通り」とプリヤは言いました。「すべての副作用が実行されることを願うのと、データベースがそれらを保証してくれるのとの違いです。」

Nimbusの場合、彼らはメニューテーブルのDynamoDB Streamsを、メニュー項目が変更されたときにElastiCacheのエントリを無効化するLambdaに接続しました。キャッシュは、無効化を管理するアプリケーションコードなしに、自動的にデータベースと整合性を保ちました。

「Streamsはいくらかかる？」とトムは尋ねました。

「ストリームからの読み取りに対して支払います。各Lambda呼び出しがそこから読み取ります。私たちの量なら、おそらく月に2〜3ドルです。」

トムはそれ以上の質問なしに承認しました。彼は、月2ドルがいつ価値があるかを学んでいました。

**トレードオフ：DynamoDBができないこと**

NoSQLはSQLよりも厳密に優れているわけではありません。異なる仕事のための異なるツールです。

DynamoDBが諦めるもの：

**柔軟なクエリ**：SQLでは、任意の列でフィルタリングおよびソートできます。DynamoDBでは、プライマリキーでのみ効率的にクエリできます。任意のフィールドでクエリするには、*スキャン*（テーブル内のすべてのアイテムを読み取ること）が必要であり、これは大規模では高価で遅くなります。

**結合**：DynamoDBは結合を行いません。2つのテーブルからデータが必要な場合、アプリケーションコードで2つの個別の読み取りを行います。

**トランザクション**：DynamoDBはトランザクションをサポートしていますが、多くのマルチエンティティのワークフロー、レポート中心のシステム、結合中心の設計では、リレーショナルデータベースの方が依然として自然な選択です。

**馴染み**：何十年にもわたるSQLのツール、スキル、思考モデルは、直接には引き継がれません。

DynamoDBが得意とするもの：

- キーバリューおよびドキュメントのアクセスパターン
- 大規模なスケール（どんなサイズでも1桁ミリ秒のレイテンシ）
- サーバーレス、インフラ管理不要
- 自動スケーリング、マルチAZレプリケーション、バックアップ
- データ量に関係なく予測可能なパフォーマンス

「つまりルールはこうだ」とマヤは言いました。「データにどうアクセスするかを*正確に*知っているときはDynamoDBを使う。まだ分からないときはSQLを使う。」

プリヤはうなずきました。「まずアクセスパターンを設計する。それからデータベースを選ぶ。」

これは、データベースの会話が生み出せる最もシニアなことの1つです。

**DynamoDBが間違った選択であるとき**

財務レポートモジュールを引き受けていたトムには質問がありました。

「財務レポートを構築している」と彼は言いました。「レストランごとの月次収益サマリー、税金計算、請求書履歴。それもDynamoDBに入れられる？」

チームは互いを見ました。

「待って、でも*なぜ*そのようにするの？」とマヤが、プリヤより先に尋ねました。

プリヤは微笑みました。マヤは習慣を身につけていました。

「クエリを教えてください」とプリヤはトムに言いました。

彼は仕様書を開きました。「必要なのは、週ごとにグループ化したレストランごとの総収益。すべてのレストランにわたる注文数による上位商品。料理ジャンル別に分解した収益。都市別の平均注文額。パートナーレポート用の前年同期比較。」

レオはリストを読みました。「どれもこれも集計だ。合計、グループ化、平均、比較。」

「DynamoDBには集計関数がありません」とプリヤは言いました。「GROUP BYなし。SUMなし。AVGなし。『今週のレストランごとの総収益』に答えるには、その週のすべての注文をスキャンし、すべてをアプリケーションメモリに引き込み、自分で計算する必要があるでしょう。」

「それは悪そうだ」とトムは言いました。

「私たちの規模では、それはレポートリクエストごとに数万のレコードをメモリに引き込むことになります。遅くて高価でしょう。そして新しいレポート要件を追加するたびに、新しいスキャン・計算コードを書くことになります。」

「では何を使う？」

「財務レポートには？RDSです。適切なインデックスを持つPostgreSQL。あなたが説明したクエリは、まさにSQLが設計された対象です。SQLなら10行でしょう。DynamoDBのスキャンコードなら200行でしょう。」

DynamoDBが間違っているのは次の場合です。

- アクセスパターンを事前に知らない（レポートは本質的に探索的）
- 大規模なデータセットにわたる集計（SUM、GROUP BY、COUNT）が必要
- データに複雑な関係があり、結合が必要
- アドホックなクエリの柔軟性が必要（まだ考えていない質問を投げかけるため）
- データが本質的にリレーショナルな構造を持ち、キーバリューに自然にマッピングされない

「つまり選択は『新しい技術の方が良い』ではない」とマヤは言いました。

「選択は『データの形は何で、どうアクセスするか』です」とプリヤは確認しました。「DynamoDBはメニューには本当に優れています。財務レポートには本当に劣るでしょう。両方の文が同時に真です。」

トムは財務レポートをPostgreSQL上に構築しました。彼が書いた最初のGROUP BYクエリは80ミリ秒で返ってきました。彼はスキャンコードを1行も書く必要がありませんでした。

**それぞれをいつ使うか**

| 状況                                                  | 選ぶべきもの            |
|-------------------------------------------------------|-------------------------|
| 構造化データ、複雑なクエリ、レポート                  | RDS（PostgreSQL、MySQL）|
| 柔軟なデータ形状、キーベースのアクセス、大規模スケール | DynamoDB                |
| 複雑な関係を伴う書き込み中心                          | RDS                     |
| 予測可能なアクセスパターンの読み取り中心             | DynamoDB                |
| 結合と集計が必要                                      | RDS                     |
| 毎秒数百万リクエストでのミリ秒レイテンシが必要        | DynamoDB                |
| 複数エンティティにわたるトランザクション             | RDS（通常）             |
| サーバーレス／予測不能なトラフィックスパイク         | DynamoDB オンデマンド   |
| 財務レポート、アドホック分析                          | RDSまたはデータウェアハウス |
| イベントソーシング、変更キャプチャ、リアルタイム処理 | DynamoDB + Streams      |

間違った答えは常に「常にどちらか一方を使う」です。Nimbusは結局両方を使いました。注文履歴と財務記録にはRDS（構造化され、リレーショナルで、レポートが必要）、メニューにはDynamoDB（柔軟なスキーマ、高い読み取り量、レストランIDによるアクセス）です。

## 適切なワークロードに適切なデータベースを

6か月先へ飛びましょう。DynamoDBへの移行が落ち着いてからずっと後、Nimbusのボードには3つの新しいプロジェクトがありました。ある火曜日の朝、マヤがチームにそれらを説明しました。

「1つ目：レコメンデーションエンジン。顧客の履歴と、似た嗜好を持つ人々が注文したものに基づいて、注文しそうな料理を顧客に表示したい。2つ目：メニューデータをよりリッチなコンテンツをサポートするように移行している。JSONでの完全なメニュードキュメント、レストランごとに異なる構造、柔軟なスキーマ。3つ目：まもなくBarato社の買収を完了する。彼らのデータチームは顧客行動データのためにCassandraクラスターを運用している。彼らはパイプラインを書き直さずにAWSに持ってきたい。」

3つのプロジェクト。3つの非常に異なるデータ要件。どれも明らかなDynamoDBの適合先ではありませんでした。

「これらはすべて異なるデータベースが必要だ」とプリヤは言いました。

「私たちにはDynamoDBがある」とレオは言いました。

「私たちには適切なツールを選ぶ権利がある」とプリヤは言いました。

**Amazon DocumentDB：ワークロードがMongoDBを話すとき**

2つ目のプロジェクト、柔軟なレストランごとのスキーマを持つリッチなJSONメニュードキュメントは、ドキュメントデータベースを説明していました。NimbusはすでにメニューにDynamoDBの柔軟なスキーマを使用していましたが、チームがより高度なメニュー機能（ネストされたモディファイア、時間ベースの価格設定、複雑なコンボ構造）を構築するにつれ、DynamoDBのクエリモデルはその限界を見せていました。チームはよりリッチなドキュメントクエリを望んでいました。ネストされたモディファイアが特定のオプションを含むすべてのメニュー項目を見つける、JSON構造内の任意のフィールドでフィルタリングする、といったものです。

「それはドキュメントデータベースのパターンです」とプリヤは言いました。「MongoDBです。」

「EC2でMongoDBを運用することもできる」とレオは提案しました。

「あるいはDocumentDBを使うこともできます」とプリヤは言いました。

**Amazon DocumentDB**は、MongoDB互換のマネージドドキュメントデータベースです。データを柔軟なスキーマを持つJSONのようなドキュメントとして保存します。同じコレクション内の異なるドキュメントが異なるフィールドを持てます。DocumentDBはMongoDBのクエリ言語、API、ドライバをサポートしています。ワークロードが現在MongoDBで動作しているなら、DocumentDBは同じ言語を話します。移行パスは、アプリケーションの書き直しではなく、接続文字列の移動です。

DocumentDBはフルマネージドです。パッチ適用なし、自動バックアップ、マルチAZ高可用性、読み取りレプリカ、そしてデータの増加に合わせて自動的に拡大するストレージです。

「つまり、メニューをDocumentDBに移行する」とレオは言いました。「そして、すでにMongoDB構文で持っているクエリはそのまま動く?」

「軽い互換性テストをすれば、はい」とプリヤは確認しました。「DocumentDBはMongoDBのクエリAPIのほとんどをサポートしています。完全なカバレッジを前提とする前に互換性マトリクスを確認してください。でも、ドキュメントクエリと集計については、簡単です。」

DocumentDBの試験シグナルはシンプルです。**「MongoDB互換」**または**「ドキュメントストア」**です。シナリオがMongoDBまたはドキュメント指向のデータに言及していれば、DocumentDBがマネージドなAWSの答えです。

**Amazon Neptune：関係こそがデータであるとき**

レコメンデーションエンジンはより難しい問題でした。

問いは「この顧客は何を注文したか？」ではありませんでした。それは単純なDynamoDBのルックアップです。問いは「どの顧客がこの顧客と似た嗜好プロファイルを持っていて、それらの顧客が好んだ料理のうち、この顧客がまだ試していないものは何か？」でした。

それはグラフの問題です。データモデルは行のテーブルでもドキュメントのコレクションでもありません。それは関係のネットワークです。顧客は料理に接続され（注文、評価、閲覧）、料理はレストランや料理ジャンルに接続され、レストランは地区や都市に接続されます。レコメンデーションはデータポイントの中にはなく、それらの間のパスの中にあります。

「グラフデータベースが必要です」とプリヤは言いました。

**Amazon Neptune**はフルマネージドのグラフデータベースです。2つのグラフモデルをサポートします。**プロパティグラフ**（Gremlinトラバーサル言語でクエリ）と**RDF**（SPARQLでクエリ）です。既存のグラフスタックやチームの好みに基づいて選択します。どちらも同じNeptuneインフラ上で動作します。

グラフデータベースは、データポイント間の関係がデータそのものと同じくらい重要なワークロードのために専用設計されています。ソーシャルネットワーク（誰が誰とつながっているか）、レコメンデーションエンジン（似たユーザーが何を好んだか）、不正検知（どの取引がアカウント間で疑わしいパターンを共有しているか）、ナレッジグラフ（概念がどう関連しているか）などです。

Nimbusのレコメンデーションエンジンの場合：顧客と料理がNeptune内のノードになりました。注文イベントがエッジになりました。Gremlinのトラバーサルは、単一のクエリで、似た注文履歴を持つ顧客が高く評価したすべての料理を、接続の強さでソートして見つけることができました。リレーショナルデータベースで必要となる複雑なJOINチェーンも、DynamoDBで必要となる複数の往復クエリもなしにです。

Neptuneの試験シグナル：**「ソーシャルネットワーク」「レコメンデーションエンジン」「ナレッジグラフ」「不正検知」**または**「グラフトラバーサル」**です。シナリオが、データそのものと同じくらいつながりが重要なデータを説明していれば、Neptuneが答えです。

**Amazon Keyspaces：運用なしのCassandra**

Barato社の買収は、Cassandraクラスターを構図に持ち込みました。CassandraはワイドカラムのNoSQLデータベースで、非常に高い書き込みスループットと水平スケーラビリティのために設計され、時系列データ、ユーザーアクティビティログ、IoTテレメトリによく使われます。Baratoのデータチームはそれを使って顧客の行動を追跡していました。どの商品が閲覧されたか、どれがカートに追加されたか、どれが放棄されたかです。

CassandraをAWSに移行するには2つの選択肢がありました。EC2で運用する（クラスター、アップグレード、スケーリングを管理する運用上のオーバーヘッド）か、マネージドオプションを使うかです。

「Amazon Keyspaces」とプリヤは言いました。

**Amazon Keyspaces**は、サーバーレスのCassandra互換マネージドデータベースです。Cassandra Query Language（CQL）をサポートしています。これはBaratoのパイプラインがすでに使っていたのと同じクエリ言語です。MongoDBに対するDocumentDBのように、Keyspacesはマネージドパスです。アプリケーションコードはそのままにして、自己管理クラスターの代わりにKeyspacesのエンドポイントに向け、インフラはAWSに任せます。

Keyspacesはトラフィックに合わせて自動的にスケールし、キャパシティ計画を必要とせず、サーバーレスです。実際に実行した読み取りと書き込みに対して支払います。Baratoの行動追跡データには、これが正しいモデルでした。極端に変動する量（夕食ラッシュ対午前3時）、ワイドカラムスキーマ、高い書き込みスループットです。

試験シグナル：**「Cassandra互換」「ワイドカラム」「CQL」**または**「Cassandraワークロード」**です。

**適切なデータベースの選択：リファレンステーブル**

物語のこの時点までに、Nimbusのデータベースの全体像は、第7章のときとはまったく異なるものになっていました。各ワークロードに適切なツールです。

| 「MongoDB互換」または「ドキュメントストア」 | DocumentDB |

## 強みと限界

**DynamoDBが強力な理由**：

- あらゆる規模で1桁ミリ秒のレイテンシ
- フルマネージド—パッチ適用なし、レプリケーション設定なし、メンテナンスウィンドウなし
- 自動マルチAZレプリケーション（耐久性が組み込まれている）
- オンデマンドスケーリングにより、キャパシティ計画はゼロ
- Lambda、API Gateway、Streamsとのネイティブ統合
- ポイントインタイムリカバリ（RDSの自動バックアップと同様）
- DynamoDB Streams—すべての変更をイベントとしてキャプチャ（リアルタイム処理に有用）

**DynamoDBが複雑になるところ**：

- アクセスパターン設計は譲れない—間違いは元に戻すのにコストがかかる
- 複雑なクエリにはセカンダリインデックスが必要（コストと複雑さを増す）
- スキャンは高価—本番環境では避ける
- 「アイテムサイズ制限」は400KB—大きなアイテムには異なるストレージが必要
- 読み取り／書き込みユニットのコストを理解していないと、料金が驚かせることがある
- ホットパーティションは静かなキラー—スロットリングが始まるまでエラーは出ない

## 概要

スキーマの再設計には2日間と、たくさんのホワイトボードのスペースがかかりました。NoSQLデータベースを選ぶことは、単なる技術的な決定ではありません。データについての考え方そのものを変えます。しかし結果は、どんなサイズに成長しても遅くならないメニューテーブルでした。同じくらい重要なこと：チームはDynamoDBの限界がどこにあるか、そして問題が形を変えたときにどの専門的なデータベースに手を伸ばすべきかを学びました。

- DynamoDBはAWSのマネージドNoSQLデータベースサービスです。アイテムは柔軟なドキュメントで、固定スキーマはありません。すべてのアイテムには**プライマリキー**が必要です。パーティションキー単独、またはパーティションキー + ソートキーです。均等な分散のためにパーティションキーを選びます。ホットパーティションはスロットリングを引き起こします。
- **オンデマンド**キャパシティは自動スケールします。**プロビジョンド**キャパシティは予測可能なトラフィックには安価です。**結果整合性**読み取りは安価です。**強い整合性**読み取りは常に最新ですが、GSIでは利用できません。
- **DynamoDB Streams**はアイテムレベルの変更をリアルタイムでキャプチャします。キャッシュの無効化、検索インデックスの更新、分析パイプラインの駆動に使います。
- DynamoDBは、レポート、複雑な結合、アドホッククエリには間違った選択です。それらにはRDSを使います。
- **DocumentDB**（MongoDB互換）、**Neptune**（グラフデータベース）、**Keyspaces**（Cassandra互換）は、DynamoDBのキーバリューモデルに適合しないワークロードのためのAWSマネージドの代替です。

## 試験のヒント

*SAA-C03 ドメイン：高パフォーマンスアーキテクチャの設計（ドメイン3、タスク3.3）*

- パーティションキーのルールを知っておきましょう：**高カーディナリティ、均等な分散**です。ホットパーティションは一般的な試験の罠です。
- **オンデマンド対プロビジョンド**：予測不能なトラフィックにはオンデマンド、予測可能なワークロードにはプロビジョンド（Auto Scaling付き）です。
- **DynamoDB Streams**：アイテムレベルの変更をリアルタイムでキャプチャします。一般的な試験シナリオ：「レコードが変更されたときにLambda関数をトリガーする」。
- **Global Tables**：グローバルに分散したアプリケーションや災害復旧シナリオのための、マルチリージョン、マルチアクティブのレプリケーションです。試験では、ワークロードが複数のリージョンでローカルな読み取りと書き込みを必要とするとき、これは強いシグナルです。
- **DynamoDB TTL（Time to Live）**：アイテムに有効期限のタイムスタンプ属性を設定すると、DynamoDBは有効期限後に自動的にそれらを削除します。**無料**で、書き込みキャパシティを消費しません。試験のトリガー：「セッションデータ／一時的なアイテムは、最低コストでN時間後に自動的に削除されなければならない」→TTL、スケジュールされたLambdaスキャンではありません。期限切れのアイテムは、アーカイブのためにDynamoDB Streamsに流すこともできます。
- **DAX（DynamoDB Accelerator）**：DynamoDB用のインメモリキャッシュレイヤーです。読み取りレイテンシをミリ秒からマイクロ秒に削減します。試験では、RDS読み取りレプリカが役立たないとき（DynamoDB固有のキャッシュであるため）に使われます。
- **複合プライマリキー**：パーティションキー + ソートキーにより、パーティション内での柔軟なクエリが可能になります。例：2つの日付の間の顧客のすべての注文を取得する—`customerId`がパーティションキー、`orderDate`がソートキーです。
- **GSI対LSI**：GSIはテーブル作成後に追加できます。LSIはできません。LSIは強い整合性読み取りをサポートします。GSIはしません。LSIはテーブルのキャパシティを共有します。GSIは独自のものを持ちます。
- DynamoDBを使わないタイミングを知っておきましょう：複雑な結合、アドホックなレポート、マルチエンティティのトランザクション→通常はRDSが答えです。
- **目的別データベースの選択**—試験は頻繁にシナリオを提示し、どのデータベースが適合するかを尋ねます。これをクイックリファレンスとして使いましょう：「MongoDB互換」→DocumentDB。「グラフ／ソーシャルネットワーク／レコメンデーションエンジン／ナレッジグラフ」→Neptune。「Cassandra互換／ワイドカラム」→Keyspaces。「あらゆる規模でのキーバリュー／ミリ秒のレイテンシ」→DynamoDB。「リレーショナル／複雑なクエリ／レポート」→RDSまたはAurora。

**演習2—SAA-C03シナリオ**

*シナリオ*：あるグローバルゲーム会社が、DynamoDBにプレイヤープロファイルを保存しています。各プロファイルには、ユーザー名、レベル、実績、インベントリなどのフィールドが含まれます。一部のプレイヤーは10個のインベントリアイテムを持ち、他のプレイヤーは数百個を持ちます。プロファイルは形状が異なりますが、それぞれがDynamoDBの400KBアイテムサイズ制限に余裕を持って収まっています。会社は、アクティブなゲームプレイ中のプロファイル検索に、1桁ミリ秒の読み取りレイテンシを必要としています。

この要件を最もよくサポートする設計アプローチはどれですか？

A) DynamoDBを使用し、`playerId`をパーティションキーとして、プロファイル全体を単一のアイテムとして保存する
B) 各リージョンに読み取りレプリカを持つRDS Auroraに移行する
C) DynamoDBを使用し、`level`をパーティションキーとして、似たスキルのプレイヤーをグループ化する
D) サブミリ秒のレイテンシを達成するために、RDSの前にElastiCacheを配置する

**ヒント1**：アクセスパターンは「IDで特定のプレイヤーを検索する」です。どのキーがそれを効率的にしますか？

**ヒント2**：あるオプションはひどいホットパーティションを作ります。どの属性が非常に低いカーディナリティを持っていますか？

**ヒント3**：DynamoDBはすでにネイティブで1桁ミリ秒のレイテンシを提供します。

**解答**: A

**説明**：`playerId`をパーティションキーとして使うと、データがパーティション全体に均等に分散され、プレイヤーIDによる瞬時の検索が可能になります。これはまさに説明されたアクセスパターンです。DynamoDBの柔軟なドキュメントモデルは、スキーマの変更なしに、さまざまなインベントリサイズを処理します。

**なぜBではないのか？** 読み取りレプリカを持つRDS Auroraは複雑さを加え、それでもゲーム規模でのこの種のキーベースのプロファイル検索にとって自然な第一選択ではありません。

**なぜCではないのか？** `level`をパーティションキーとして使うと、深刻なホットパーティションが生まれます。ほとんどのトラフィックがレベル1（新規プレイヤー）または最大レベル（アクティブなベテラン）に向かい、他のパーティションがアイドルのままになります。

**なぜDではないのか？** 質問はRDSではなくDynamoDBを説明しています。RDSの前にElastiCacheを追加することは、DynamoDB単独で問題を解決できるのに、2つの新しいサービスを導入します。
