**サーバーは常に答えではない**

EC2インスタンスは永久です。1つ開始し、停止するまで実行されます—24時間/7日、実際の使用状況に関係なく。ウェブサーバー（すべての時間帯でトラフィックを処理するもの）の場合、これは正しいです。メールサービス（メールのバーストを送信し、その後何時間もアイドル状態になるもの）の場合、これは無駄です。

Auto Scaling Groupは、オフピーク時間帯でメールサービスを1インスタンスにスケールダウンできます。しかし、1インスタンスは常に実行されます。

コードが仕事がある場合にのみ実行される場合、どうでしょうか？

それが**サーバーレスコンピューティング**の前提です。

**AWS Lambda: サーバーなしのコード**

**AWS Lambda**は、サーバーをプロビジョニングまたは管理することなく、イベントに応答してコードを実行できるようにします。関数をアップロードし、トリガーを定義し、Lambdaはトリガーが発火するとそれを実行します。

Lambda関数は：

- 持続的な状態を持っていません（各呼び出しは独立しています）
- 最大15分間実行されます（呼び出しごと）
- 0から数千の同時呼び出しの範囲で自動的にスケーリングされます
- 実行中の場合にのみ課金されます（割り当てられたメモリの1ミリ秒、上位に丸められたもの、GBあたり）

トリガーがない場合、Lambdaは費用をかけません。トリガーが発火すると、Lambdaは実行され、課金されます。10,000のトリガーが同時に発火すると、Lambdaは10,000の同時呼び出しを実行します。スケーリングは自動的でほぼ瞬時に行われます。

**イベントトリガー: Lambdaを起動するもの**

Lambda関数は自分自身で実行されません—イベントに応答します。一般的なトリガーには以下があります。

- **SQSキュー**: キューからのメッセージを処理します。Lambdaはキューをポーリングし、メッセージのバッチとともに関数を呼び出します。
- **API Gateway**: HTTPリクエストが到着します。API GatewayはLambdaをトリガーします。Lambdaは応答を生成します。
- **S3イベント**: ファイルがS3にアップロードされます。Lambdaはそれを処理します（画像をリサイズする、CSVを解析する、ドキュメントを検証する）。
- **SNS**: トピックにメッセージが公開されます。Lambdaは通知を受け取ります。
- **DynamoDB Streams**: DynamoDBのレコードが変更されます。Lambdaは変更を処理します。
- **CloudWatch Events (EventBridge)**: 定義された時間でスケジュールされたイベント（例：cronジョブ）が実行されます。
- **ALB**: ロードバランサーでHTTPリクエストが到着します。Lambdaは特定のルートを処理できます。

Nimbus（電子メールサービス）は、SQSキューをトリガーするLambda関数になりました。キューにメッセージが到着すると、Lambdaはメッセージの内容を使用して電子メールを送信し、SES（Simple Email Service）を使用して終了します。

サーバーなし。アイドル時間なし。アイドル時に費用がかからない。

**コールドスタートの問題**

Lambda関数は**実行環境**で実行されます—小さな、隔離されたコンテナです。関数が呼び出されると：

1. AWSは、利用可能な暖かい実行環境があるかどうかを確認します（最近の呼び出しを処理したもの）
2. もし暖かい場合：関数はすぐに実行されます
3. もし冷たい場合：AWSは新しい実行環境を初期化します—コードをダウンロードし、ランタイムを開始し、初期化コードを実行し、関数を実行します

**コールドスタート**は、ランタイム（Javaと.NETはPythonとNode.jsよりも長いコールドスタート時間）とコードパッケージのサイズによって、100msから数秒の遅延を追加します。

非同期処理（メール送信、画像リサイズ）の場合、コールドスタートはユーザーに不可視です。

同期API（ユーザーが応答を待っているHTTPリクエスト）の場合、コールドスタートはまれに遅い応答を引き起こす可能性があります。

**軽減策：**

- **プロビジョンドコンカーレンシー**: 必要な数の実行環境を事前に暖めます。それらは常に準備でき、使用されていない場合にのみ費用がかかります。
- **より小さいパッケージサイズ**: より小さいコードはより早く初期化されます。
- **ウォーミングアップ呼び出し**: 関数を暖めるためにスケジュールされたping（一般的なが不格好なアプローチ）。
- **適切なランタイムの選択**: PythonとNode.jsはJavaよりもコールドスタートが速いです。

**Lambdaの価格設定: トムが笑顔になった理由**

Lambdaの価格設定には、2つのコンポーネントがあります。

1. **リクエスト料金**: 1百万の呼び出しあたり0.20ドル
2. **時間料金**: 割り当てられたメモリ（秒あたりの実行時間）のGBあたり0.0000166667ドル

最初の1百万のリクエストは毎月無料です（常に、最初の1年間だけではありません）。

トムはメールサービスについて計算を行いました。

- 1,200件のメール/日 × 30日 = 月間36,000回の呼び出し
- 1回の呼び出しあたり約2秒で、256MBメモリを使用
- 期間: 36,000 × 2 × 0.25GB × $0.0000166667 = 1か月あたり$0.30
- リクエスト: 36,000 << 1,000,000 (無料枠) = 1か月あたり$0.00

メールサービスのEC2インスタンス: 月額$18

**Lambdaが優れていること（そして優れていないこと）**

Lambdaは以下の点で優れています：

- **イベント駆動型の処理**: ファイルアップロード、キューメッセージ、スケジュールされたタスクなどのイベントに応答する
- **短時間のタスク**: 15分以内に完了する処理
- **変動の激しいトラフィック**: Lambdaは0から数千に瞬時にスケール—事前プロビジョニングは不要
- **まれな操作**: 毎日の2時に実行されるレポート。毎週実行されるクリーンアップジョブ
- **Glueコード**: サービス間のデータ移動を行う小さな関数

Lambdaは以下の点で劣ります：

- **長時間実行のプロセス**: 15分の制限はハードな壁
- **ステートフルなアプリケーション**: Lambda関数はステートレスで設計されている—各呼び出しは独立している
- **高スループット、低レイテンシAPI**: コールドスタートによりレイテンシスパイクが発生する—プロビジョニングされた同時実行で緩和されるがコストが増加する
- **永続的な接続が必要なアプリケーション**: Lambdaは簡単に長期間のデータベース接続プールを維持できない（ただし、RDS Proxyのような接続プーリングツールが役立つ）
- **従来のWebサーバー**: 可能だが自然なフィットではない

「だからLambdaはEC2の代替ではない」とマヤは言いました。「異なるツールで異なる仕事をこなすのだ」

「NimbusのWeb APIはEC2またはECSに留まる」とレオが確認しました。「メールサービス、画像リサイザ、毎晩のレポート生成器、ログクリーン—それらはすべてLambdaに移動する」

**サーバーレスの哲学**

Lambdaはより広範な概念の一部である**サーバーレス**—サーバーを管理する必要がなく、コードのみを管理するアプリケーションを構築することです。

完全なサーバーレスのNimbusスタックは次のようになる可能性があります：

- API Gateway + Lambda (EC2とWebサーバーの代わりに)
- DynamoDB (RDS—サーバーレスも、サーバー管理は不要)
- S3 (静的アセット—本質的にサーバーレス)
- SNS + SQS (メッセージング—サーバーレス)
- Lambda (すべてのバックグラウンド処理)

その魅力：コードを書く—他のすべてはAWSが管理する。パッチの適用、スケーリング構成、キャパシティ計画の計画は不要

その現実：サーバーレスには独自の運用複雑さが存在する—分散されたLambda関数のデバッグ、コールドスタートの管理、同時実行制限の理解。より簡単ではなく、異なるだけです。

## 強みと限界

**Lambdaが強力な理由**

- 従量課金制—アイドル時にコストがかからない
- 設定なしで自動スケーリング
- パッチやメンテナンスする必要がないサーバー
- 寛大な無料枠（1か月あたり100万リクエスト、永久無料）
- AWSの他のすべてのサービスとの緊密な統合

**複雑になる場所**

- コールドスタートは現実であり、レイテンシに敏感なワークロードでは慎重に処理する必要がある
- 15分の実行制限は長時間のタスクには適用されない
- デバッグが難しい—SSHで接続できない永続サーバーがない
- ステートレス設計は外部化されたすべての状態（データベース、キャッシュ、S3）が必要
- 同時実行制限（デフォルト1,000同時呼び出し/アカウント）は、規模が大きくなるとスロットリングする
- VPC接続されたLambda関数には、追加のレイテンシとコールドスタートの問題がある

## 概要

- **AWS Lambda**は、サーバーを管理することなくイベントに応答してコードを実行します。
- **従量課金制**: 呼び出しごと、および1msの実行ごとに課金されます。アイドル時はコストがかかりません。
- 0から数千の同時呼び出しに自動的にスケールします。
- **コールドスタート**: 暖かい実行環境が存在しない場合に発生する初期化レイテンシ。プロビジョニングされた同時実行または軽量ランタイムで軽減されます。
- 最適な用途：イベント駆動型、短時間、変動の激しい、またはまれなワークロード
- 最適ではない用途：長時間実行のタスク、ステートフルなアプリケーション、プロビジョニングされた同時実行がない場合、高スループット、低レイテンシAPI

- **サーバーレス**は設計哲学—インフラストラクチャを管理するのではなく、コードを管理します。

## 試験のヒント

*SAA-C03 ドメイン：回復力のあるアーキテクチャの設計（タスク2.1）*

- **Lambda + S3**: クラシックなパターンです。S3にファイルがアップロードされると、Lambda関数がトリガーされ、処理（サムネイル生成、ウイルススキャン、データ変換）が行われます。サーバーは不要です。
- **Lambda + SQS**: LambdaはSQSをポーリングし、バッチを処理します。SQSはリトライ/DLQメカニズムを提供します。Lambdaは処理を提供します。
- **Lambda + API Gateway**: サーバーレスのHTTP APIです。API Gatewayはルーティング、認証、スロットリングを処理します。Lambdaはビジネスロジックを処理します。
- **Cold start シグナル**: 「最初のリクエスト時にレイテンシが発生する」「応答時間が一貫しない」→ Cold startです。解決策：プロビジョンドコンカーレンシー（費用がかかります）、より小さいパッケージ、軽量なランタイムです。
- **実行制限**: 最大15分。最大メモリ10GB。デフォルトでは512MB /tmp のエフェメラルストレージ（最大10GBまで構成可能）。これらの制限は、試験シナリオで現れます。
- **Lambda コンカーレンシー**: デフォルトは1,000回の同時実行実行（アカウントあたり）。**予約済みコンカーレンシー**: 関数が特定の数の実行を取得することを保証し、他の関数がそれらを消費することを防ぎます。**プロビジョンドコンカーレンシー**: 実行環境の sejumlah 個の事前ウォーミングを行います。
- **イベントソースマッピング**: Lambda機能をS3/DynamoDB Streams/Kinesisに接続します。Lambdaはソースをポーリングし、レコードをバッチ処理します。

**練習問題 2 — 試験練習**

*シナリオ*: 会社はサプライヤーからS3バケットに画像を受け取ります。各画像は、サムネイル、小、中、大の4つの標準サイズにリサイズされ、S3に返されます。その量は予測不可能で、何日かでは10枚、何日かでは10万枚です。処理は10分以内に完了する必要があります。コストを最小限に抑えなければなりません。

これらの要件を満たす最適なアーキテクチャはどれですか？

A) Auto Scaling GroupでS3バケットを監視し、長 pollingを行うEC2インスタンス
B) S3イベント通知がLambda関数をトリガーし、画像をリサイズして結果をS3に保存する
C) SQSキューをトリガーするECS Fargateタスク、S3イベントがキューに公開する
D) 1分ごとにS3をチェックする専用のEC2インスタンスとcronジョブ

**ヒント 1**: 不予測可能なボリュームは、ゼロコストスケールに有利です。それはどのオプションですか？

**ヒント 2**: 10分/画像はLambdaの15分制限内です。画像のリサイズ作業がLambdaの制約に適合するか確認してください。

**ヒント 3**: 24時間稼働する専用のEC2インスタンスは高価でスケーリングされません。

**答え**: B

**説明**: S3イベント通知が画像がアップロードされたときにLambdaをトリガーします。Lambdaは画像を4つの寸法にリサイズし、結果をS3に保存します。Lambdaは、予測不可能なボリュームを処理するために、0から数千の同時実行インスタンスに自動的にスケールします。画像が処理されていない場合にコストは発生しません。

**Aが最適ではない理由**: EC2をASGで実行すると、最小のインスタンスが常に実行されるため、ゼロスケールにはなりません。長 polling S3はネイティブ S3 イベントメカニズムではありません。スパイクのワークロードでは、長 polling S3よりもコストが高くなります。

**Cが最適ではない理由**: ECS Fargateは機能しますが、コンテナ管理、ECR、タスク定義など、より複雑であり、スパイクのワークロードではLambdaよりもコールドスタートの遅延がわずかに大きくなります。このユースケースでは、Lambdaがよりシンプルです。

**Dが最適ではない理由**: 24時間稼働する専用のEC2インスタンスは、単一障害点であり、スケーリングされません。また、60秒の検出遅延があるcronベースのアプローチです。
