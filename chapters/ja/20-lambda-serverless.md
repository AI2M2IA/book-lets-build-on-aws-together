ここには心に留めておく価値のある微妙な点があります。従来のモデルはこうです: 従業員を雇い、8時間分を支払い、可変の成果を得る。フリーランサーモデルはこうです: 電話が鳴ったときだけ支払い、要求されたものをちょうど得る。予測可能で一定の需要を持つ会社にとっては、従業員モデルのほうが効率的です — 電話が絶え間なく鳴ると分かっているので、時間給で支払うのは同等であり、契約と解約のオーバーヘッドもありません。可変で、急増する、あるいはまれな需要を持つ会社にとっては、フリーランサーモデルが劇的に安くなります。

AWS はそのモデルをコンピュートに提供しています — そしてそれが理にかなうかどうかは、あなたの需要パターンに依存します。最初の問いは決して「このモデルは良いか?」ではなく、「私のワークロードは実際にどう見えるか?」です。

スタートアップより大きいほとんどのワークロードにとっては: 混合です。あるものは絶えず実行されます (API サーバー、データベース)。あるものはトリガーされたときだけ実行されます (イベント処理、レポート生成、画像のリサイズ)。フリーランサーモデルは2番目のカテゴリのためのものです — そして Nimbus は、自社の請求のどれだけがそこに属するのかを発見しようとしていました。

**サーバーが常に答えとは限らない**

EC2 インスタンスは永続的です。1つを起動すると、停止するまで動き続けます — 実際の使用にかかわらず、1日24時間、週7日。Web サーバー (あらゆる時間にトラフィックを処理する) にとっては、それは正しいことです。メールサービス (メールをバーストで送り、それから何時間もアイドルになる) にとっては、無駄です。

Auto Scaling Group は、オフピーク時にメールサービスを1インスタンスまでスケールダウンできます。しかし、1インスタンスは依然として絶えず動いています。

これがトムが請求を見るたびに繰り返し戻ってきた問いでした: それら18時間の3% CPU の間、各サービスは実際に何をしていたのか? 厳密には、何もないわけではありません — インスタンスは待ち、イベントをチェックし、状態を維持していました。しかしビジネスの観点からは: 何もしていません。サービスは価値を届けていませんでした。課金されていました。

本当にほとんどの時間アイドルなワークロードにとって、常時稼働の EC2 インスタンスは、週末しか訪れないアパートの家賃を払っているようなものです。アパートはあなたのものですが、家賃は止まりません。

フリーランサーモデルはこれを完全に解決します。コードは存在します。実行する理由ができるまで、ただ実行されないだけです。アイドルコストなし。予約された容量なし。電話のそばで待つサーバーなし。

それが **サーバーレスコンピューティング (serverless computing)** の前提です。

**AWS Lambda: サーバーなしのコード**

**AWS Lambda** は、サーバーをプロビジョニングしたり管理したりすることなく、イベントに応答してコードを実行できるようにします。関数をアップロードし、何がそれをトリガーするかを指定すると、Lambda はトリガーが発火したときにそれを実行します。

Lambda 関数は:

- 永続的な状態を持ちません (各呼び出しは独立しています)
- 1回の呼び出しあたり最大15分実行されます
- 0 から数千の並行呼び出しまで自動的にスケールします
- 実行中のみ課金されます (実行1ミリ秒ごと、切り上げ、割り当てられたメモリの GB ごと)

トリガーがないとき、Lambda には何のコストもかかりません。トリガーが発火すると、Lambda は実行され課金されます。10,000のトリガーが同時に発火すると、Lambda は10,000の並行呼び出しを実行します。スケーリングは自動的で、ほぼ即時です。

**イベントトリガー: 何が Lambda を起こすか**

Lambda 関数は自分では実行されません — イベントに応答します。一般的なトリガーには次が含まれます:

- **SQS キュー**: キューからメッセージを処理します。Lambda はキューをポーリングし、メッセージのバッチで関数を呼び出します。
- **API Gateway**: HTTP リクエストが来ます。API Gateway が Lambda をトリガーします。Lambda が応答を生成します。
- **S3 イベント**: ファイルが S3 にアップロードされます。Lambda がそれを処理します (画像のリサイズ、CSV のパース、ドキュメントの検証)。
- **SNS**: メッセージがトピックに発行されます。Lambda が通知されます。
- **DynamoDB Streams**: DynamoDB のレコードが変更されます。Lambda が変更を処理します。
- **CloudWatch Events (EventBridge)**: スケジュールされたイベント (cron ジョブのような) が定義された時刻に実行されます。
- **ALB**: HTTP リクエストがロードバランサーに到着します。Lambda が特定のルートを処理できます。

Nimbus では、メールサービスがその SQS キューによってトリガーされる Lambda 関数になりました。メッセージがキューに到着すると、Lambda がメッセージの内容で呼び出され、SES (Simple Email Service) 経由でメールを送り、終了します。

サーバーゼロ。アイドル時間ゼロ。アイドル時のコストゼロ。

Lambda + SQS のパターンは身につける価値があります: SQS がキュー、耐久性、リトライロジック、DLQ を扱います。Lambda が処理を扱います。SQS の疎結合の利点を、Lambda のスケール・トゥ・ゼロの経済性とともに得られます。どちらのサービスも互いの仕事をしません。それらはきれいに組み合わさります。

「キューの中の不正な形式のメッセージはどうなるの?」とプリヤが尋ねました。「悪い入力が、アカウント内の他の関数に影響を与える形で Lambda をクラッシュさせることはある?」

Lambda の呼び出しは互いに分離されています。クラッシュする関数は他の関数に影響しません。不正な形式のメッセージで未処理の例外をスローする Lambda: メッセージはキューに戻り、設定された制限までリトライされ、それから DLQ に移動します。Lambda 自体は次のメッセージのために利用可能なままです。Lambda ハンドラ内の入力検証は依然として重要です — 処理を試みる前に不正な形式のデータを捕捉するために — しかし、1つの悪いメッセージが関数を停止させることはできません。

**コールドスタートの問題**

Lambda 関数は **実行環境 (execution environment)** で実行されます — 小さく分離されたコンテナです。関数が呼び出されると:

1. AWS はウォームな実行環境 (最近の呼び出しを処理したもの) が利用可能かどうかをチェックします
2. ウォームなら: 関数はただちに実行されます
3. コールドなら: AWS は新しい実行環境を初期化します — コードをダウンロードし、ランタイムを開始し、初期化コードを実行します — それから関数を実行します

**コールドスタート (cold start)** は、ランタイム (Java と .NET は Python と Node.js より長いコールドスタートを持ちます) とコードパッケージのサイズに応じて、100ミリ秒から数秒のレイテンシを追加します。

Lambda が毎回ゼロから始まるなら、すでに動いているサーバーより遅くなるのではないか、と疑問に思うかもしれません。はい — 時々は。それがコールドスタートの問題で、時間に敏感なユーザー向けの API にとっては重要です。ユーザーがすでに確認を受け取っているバックグラウンドジョブにとっては、まったく問題になりません。バックグラウンドで動くメールサービスの200ミリ秒のコールドスタートは、誰にも見えません。

非同期処理 (メール送信、画像リサイズ) では、コールドスタートはユーザーには見えません。

同期 API (ユーザーが応答を待っている HTTP リクエスト) では、コールドスタートはときどき遅い応答を引き起こすことがあります。

**緩和策**:

- **プロビジョンド同時実行 (Provisioned concurrency)**: 指定した数の実行環境を事前にウォームアップします。それらは常に準備ができています。リクエストを処理していないときでもこれに対して支払います。
- **より小さいパッケージサイズ**: より小さいコードはより速く初期化します。
- **ウォームアップ呼び出し**: 関数をウォームに保つためのスケジュールされた ping (一般的だが洗練されていないアプローチ)。
- **正しいランタイムを選ぶ**: Python と Node.js は Java より速くコールドスタートします。

**実際のコールドスタート調査**

Lambda への移行から2週間後、レオはレストランパートナーから Slack メッセージを受け取りました: 「注文確認が時々3秒かかります。たいていは速いです。何が起きているのですか?」

レオは Lambda 関数の CloudWatch メトリクスを呼び出しました。「Duration」グラフに、彼はパターンを見ることができました: 15〜20分を超える間隔のあとの最初の呼び出しは、2,800〜3,200ミリ秒にスパイクします。その後の呼び出しは: 180〜220ミリ秒。

典型的なコールドスタートです。

彼は3秒の呼び出しのひとつの X-Ray トレースを取り出しました。タイムラインはそれを明確に示していました:

- 初期化フェーズ: 2,640ミリ秒 (関数コードのダウンロード、Node.js ランタイムの開始、モジュールレベルの初期化コードの実行)
- ハンドラ関数の実行: 290ミリ秒

初期化フェーズが問題でした。彼は初期化コードを見ました。関数は、大きな SDK をインポートし、データベース接続を初期化し、AWS Secrets Manager から設定をロードしていました — すべて起動時に。

「この初期化の一部は、実行環境ごとに一度だけ起これば十分だ」とレオが言いました。「でも、すべてのコールドスタートで起きている。」

彼は Lambda コードを再構成して、データベース接続をハンドラ関数の外で初期化するようにし (ウォームな呼び出しをまたいで再利用されるように)、使われていない SDK モジュールを削除してパッケージサイズを縮小しました。彼はまた、AWS SDK 全体をバンドルする代わりに、必要な特定のサービスだけをインポートするように切り替えました。

最適化のあと:

- コールドスタートの時間: 1,100ミリ秒 (まだ存在するが、より軽度)
- ウォームな呼び出し: 165ミリ秒

1.1秒のコールドスタートは依然としてときどき起きました。メールサービス (非同期、ユーザー向けの遅延が見えない) にとっては、これは許容できました。レストラン通知の Lambda (顧客向け、タブレットから注文される) にとっては、プリヤがプロビジョンド同時実行を推しました: 常に準備された2つの事前ウォームアップ環境。

「それは月にいくらかかるんだ?」とトムが尋ねました。

256MB での2つのプロビジョンド同時実行環境: 月に約5.40ドル。レイテンシのスパイクは止まりました。

**Lambda の料金: なぜトムは微笑んだか**

Lambda の料金には2つの要素があります:

1. **リクエスト料金**: 100万回の呼び出しあたり0.20ドル
2. **時間料金**: GB 秒あたり0.0000166667ドル (割り当てられたメモリ × 実行秒数)

月の最初の100万リクエストは無料です (常に、最初の1年だけではありません)。

「それは月にいくらかかるんだ?」と、レオが計算機を開く前にトムが尋ねました。

トムはメールサービスの計算を自分でしました:

- 毎日が金曜日だと仮定する — 最悪のケース: 1日1,200通 × 30日 = 月36,000回の呼び出し
- 各呼び出しは256MB メモリで約2秒かかる
- 時間: 36,000 × 2 × 0.25GB × 0.0000166667ドル = 月0.30ドル
- リクエスト: 36,000 << 1,000,000 (無料枠) = 月0.00ドル

「それに、その18,000 GB 秒は、常に無料の400,000 GB 秒の時間の中に十分収まる」とトムが付け加えました。「だから実際の課金はゼロになる。でも、わざと無料枠を無視している — 本当の単価を知りたいんだ。」

メールサービスの EC2 インスタンス: 月18ドル。

「もうデプロイした — あ。」レオは自分を止めました。彼は DLQ の設定を終える前にメールサービスの Lambda を本番にプッシュしていました。「5分くれ。」

トムはしばらく黙っていました。それから: 「これをすべてに対してやるべきだ。」

**Lambda が得意なこと (そして得意でないこと)**

「待って — でも *なぜ* それなら、すべてに Lambda を使わないの?」とマヤが尋ねました。「もっと安くて自動的にスケールするなら、落とし穴は何?」

「15分の制限だ」とレオが言いました。「それに、ユーザー向けのあらゆるもののコールドスタート。それにステートレス性 — 呼び出しの間にメモリに何も保持できない。」

ワークロードが急増型で、イベント駆動で、15分未満で完了するなら、Lambda は常時稼働の EC2 インスタンスのほんの一部のコストになります — しかし、ワークロードが15分の制限に近づくか超える長時間実行のデータ処理ジョブなら、Lambda は間違ったツールであり、ECS、Batch、または EC2 ベースのアプローチが必要になります。

Lambda が優れているのは:

- **イベント駆動処理**: イベント (ファイルアップロード、キューメッセージ、スケジュールされたタスク) に応答する
- **短時間実行のタスク**: 15分内に余裕をもって完了する処理
- **急増する予測不能なトラフィック**: Lambda は 0 から数千まで即座にスケールします — 事前プロビジョニングなし
- **頻度の低い操作**: 毎日午前2時に動くレポート。毎週動くクリーンアップジョブ。
- **グルーコード**: サービス間でデータを移動する小さな関数

10,000のイベントの突然のバーストが同時に到着したとき、Lambda のスケーリングはどうなるのか、と疑問に思うかもしれません。Lambda のデフォルトの同時実行制限は、アカウントあたり1,000の並行実行です。10,000のイベントが一度に到着すると、最大1,000の呼び出しがただちに実行され、残りは (SQS 経由でトリガーされた場合) SQS キューで待ち、容量が空くにつれて処理されます。これはキューベースの処理では通常問題ありません。レイテンシに敏感なユースケースでは、Lambda のバースト制限 (新しい並行実行が追加される初期レート) が、突然のスパイク中に短時間のスロットリングを引き起こすことがあります — プロビジョンド同時実行は、容量を事前割り当てすることでこれを回避します。

Nimbus のメールサービスの現在の規模では、1,000の並行呼び出しは彼らが必要とするよりはるかに多いものでした。しかし、それは到達する前に知っておくべき正しい制約です。

Lambda が苦手なのは:

- **長時間実行のプロセス**: 15分の制限は固い壁です
- **ステートフルなアプリケーション**: Lambda 関数は設計上ステートレスです — 各呼び出しは独立しています
- **高スループット、低レイテンシの API**: コールドスタートがレイテンシのスパイクを引き起こすことがあります。プロビジョンド同時実行はこれを緩和しますがコストを追加します
- **永続的な接続を必要とするアプリケーション**: Lambda は長寿命のデータベース接続プールを簡単には維持できません (ただし RDS Proxy のような接続プーリングツールが助けになります)
- **従来の Web サーバー**: 可能ですが、自然な適合ではありません

**15分の壁: Lambda が間違ったツールであるとき**

移行から3週間後、レオはもう1つのワークロードを Lambda に移そうとしました: 夜間のアナリティクスレポートジェネレーターです。それはデータベースから注文データを引き出し、レストランのメタデータと結合し、統計を計算し、PDF を生成しました。

最初の夜、Lambda の呼び出しはタイムアウトエラーで失敗しました。

「レポート生成に17分かかった」と、翌朝レオが言いました。

「Lambda の最大は15分よ」とプリヤが言いました。

「ああ。今は分かっている。」

彼は平均処理時間 (8分) を確認し、Lambda で動くだろうと思い込んでいました。彼はテール — データ量が多くクエリが長くかかる夜 — を確認していませんでした。そうした夜には、15分では足りませんでした。

「それで、レポートは単に... 生成されないの?」とマヤが尋ねました。

「そのとおり。エラー通知なし。部分的なレポートなし。ただ沈黙。」

「もうデプロイした — あ」とレオが言いました。

これは Lambda が優雅でない形で失敗する具体的な方法のひとつでした: タイムアウトは出力を生み出さず、アプリケーション内のエラーメッセージも生み出さず、ただ CloudWatch のエラーログだけです。Lambda のタイムアウトエラーを特に監視していなければ、何日も気づかないかもしれません。

修正: レポートジェネレーターを ECS Fargate — サーバーを管理せずにコンテナを動かす。次の章 — に移します。それには時間制限がありません。Lambda は、ときどきでも15分を超える可能性のあるワークロードには間違ったツールでした。教訓は「Lambda は悪い」ではありませんでした。教訓は「Lambda は、その制約の中に収まるワークロードには正しいツールであり — そうでないときには驚くべき失敗の原因になる」でした。

**RDS Proxy: Lambda のための接続プーリング**

Lambda のステートレスな性質は、特定のデータベースの問題を生み出します。

EC2 インスタンスが RDS に接続するとき、それは永続的な接続プールを維持します。アプリケーションはプールから接続を再利用します。RDS は、たとえば200の同時接続を処理できます。

Lambda が500の同時呼び出しを処理するとき、各呼び出しは自分自身のデータベース接続を開こうとします。それは500の新しい接続です — 200をサポートするデータベースを圧倒します。

**Amazon RDS Proxy** は、Lambda 関数と RDS の間に位置し、永続的な接続プールを維持し、Lambda の短命な接続をそれを通じて多重化します。

次の代わりに: Lambda 呼び出し → 新しい RDS 接続 (500の並行呼び出しのそれぞれに対して)

RDS Proxy を使うと: Lambda 呼び出し → RDS Proxy → 20の永続的な RDS 接続のプール

「プロキシには RDS の認証情報が必要だ」とプリヤが言いました。「それはどこに置かれるの? プロキシがそれを保存するの?」

RDS Proxy は認証情報を Secrets Manager に保存し、自動的にローテーションします。Lambda 関数の IAM ロールは、(IAM 認証を使って) プロキシへのアクセスを与えるのであって、RDS の認証情報に直接アクセスを与えるのではありません。認証情報は Lambda コードに決して露出しません。

「つまり Lambda 関数は IAM 経由で認証する」とレオが確認しました。「そしてプロキシが実際のデータベース認証情報を扱う。」

Nimbus の注文処理 Lambda (注文検証のために RDS をクエリするもの) では、RDS Proxy が金曜のピークトラフィック中の接続プールの枯渇を解消しました。

**Lambda レイヤー: 共有された依存関係**

メールサービスの Lambda、通知の Lambda、レポートの Lambda はすべて、同じ内部ライブラリコードを共有していました: 通貨のフォーマット、入力のサニタイズ、標準フォーマットでのロギングのためのユーティリティ関数です。

Lambda レイヤーがなければ、その共有コードは各関数のデプロイパッケージにバンドルされなければなりませんでした。3つの関数、同じ2MB のライブラリの3つのコピー。ライブラリが更新されると、3つの関数すべてが新しいデプロイを必要としました。

**Lambda レイヤー (Lambda Layers)** は、Lambda 関数が実行時に参照できる別個のパッケージです。共有ライブラリはレイヤーに抽出されました。3つの関数はそのレイヤーを参照しました。共有ライブラリの更新は、3つの関数すべてを再デプロイするのではなく、レイヤーのバージョンを更新することを意味しました。

追加の利点: 個々の関数パッケージが小さくなることで、コールドスタートが速くなります。

「レイヤーが変えない1つのこと: 実行ロールよ」とプリヤが言いました。「Lambda が広すぎる権限を持っていたら、侵害された関数はアカウント内のすべてにアクセスできる。」

「EC2 ロールと同じ原則だ」とレオが言いました。「最小権限。各 Lambda は、実際に必要な権限だけを得る。」

「つまり Lambda は EC2 の置き換えではない」とマヤが言いました。「異なる仕事のための異なるツールね。」

「Nimbus の Web API は EC2 か ECS にとどまる」とレオが確認しました。「メールサービス、画像リサイザー、夜間レポートジェネレーター、ログクリーナー — それらは Lambda に移る。」

**サーバーレスの哲学**

Lambda はより広い概念の一部です: **サーバーレス (serverless)** — サーバーを一切管理せず、コードだけを管理するアプリケーションを構築すること。

完全にサーバーレスな Nimbus スタックは次のように見えるかもしれません:

- API Gateway + Lambda (Web サーバーを備えた EC2 の代わりに)
- DynamoDB (RDS の代わりに — これもサーバーレスで、サーバー管理なし)
- S3 (静的アセット — 本質的にサーバーレス)
- SNS + SQS (メッセージング — サーバーレス)
- Lambda (すべてのバックグラウンド処理)

魅力: あなたはコードを書き、AWS が他のすべてを管理します。パッチ適用なし、スケーリング設定なし、容量計画なし。

## Amazon API Gateway

Lambda のトリガーリストは API Gateway に簡単に言及しました: HTTP リクエストが来て、API Gateway が Lambda をトリガーする。それは正確ですが、API Gateway が実際に何であるかを過小評価しています。

「待って — でも *なぜ* Lambda の前に API Gateway を置くの?」とマヤが尋ねました。「Lambda は HTTP リクエストを直接受け取れないの?」

Lambda は関数 URL — シンプルで直接的な HTTPS エンドポイント — 経由で HTTP リクエストを受け取れます。しかし、それはルーティング、認可、スロットリング、キャッシュ、リクエスト変換を扱いません。本番の API にとって、それらの関心事は、バックエンドが Lambda か EC2 かにかかわらず存在します。

**Amazon API Gateway** は、あらゆる規模で API を作成、デプロイ、管理するためのフルマネージドサービスです。トラフィック管理、認可、スロットリング、キャッシュ、監視を扱うので、あなたの Lambda 関数 (または EC2、または任意の HTTP バックエンド) がそれらを自分で実装する必要がありません。

**3つの API タイプ:**

**REST API** は最も機能豊富な選択肢です。リクエストとレスポンスの変換、レスポンスのキャッシュ、API キーに紐づいた使用量プラン、すべての認可タイプをサポートします。API Gateway に言及するほとんどの SAA-C03 試験問題は REST API に関わります。

**HTTP API** はよりシンプルで安価です — REST API より約70%低いコストです。Lambda バックエンドと HTTP プロキシのために設計されています。OIDC と OAuth 2.0 の認可をサポートしますが、リクエスト変換やキャッシュはサポートしません。REST API の高度な機能が必要でなければ、HTTP API が正しい選択です。

**WebSocket API** は、永続的な双方向の接続を管理します。API Gateway が接続のライフサイクルを扱い、メッセージの内容に基づいてメッセージを Lambda にルーティングします。Lambda 関数はソケットの状態を管理する必要がありません — API Gateway がそれを行います。

**認可オプション** (試験がテストするもの):

**Cognito User Pool オーソライザー** は、Cognito User Pool からの JWT を検証します。Lambda は不要です。API Gateway がトークン自体をチェックします。有効なら、リクエストは通過します。

**Lambda オーソライザー** は、トークンを検証するために独自の Lambda 関数を実行します — カスタムの JWT、サードパーティの ID プロバイダーからの OAuth トークン、独自フォーマットの API キー。Lambda は IAM ポリシーを返します。ポリシーがアクションを許可すれば、リクエストは進みます。

**API キー** は、リクエストヘッダーで渡される単純なキーです。API キーは、認証のためではなく、クライアントごとのレート制限のためのものです。それらをセキュリティメカニズムとして使わないでください — それらはシークレットではなく、識別子です。

**スロットリングと使用量プラン:**

デフォルトでは、API Gateway はアカウントレベルで1秒あたり10,000リクエストを許可し (ソフトリミット)、バーストは5,000です。それを超えるとクライアントは `429 Too Many Requests` を受け取ります — バックエンドはそれを感じることすらありません。クライアントごとの制限が必要なときは、使用量プランを作成します: それを API キーに紐づけ、リクエストレートと日次または月次のクォータを設定します。1つのクライアントのバーストが、別のクライアントの割り当てを消費することはありません。

覚えておく価値のある2つの数字: 最大ペイロードは **10 MB**、デフォルトの統合タイムアウトは **29秒** です — バックエンドがそれより長くかかると、ゲートウェイは諦めます。(2024年以降、そのタイムアウトはクォータの引き上げにより、リージョナルおよびプライベートな REST API では29秒を超えて引き上げられます — しかし29秒のデフォルトが依然として試験が期待するものです。) API Gateway はリクエスト/レスポンスの API のためのもので、長時間実行のジョブのためのものではありません。そうしたジョブには、仕事を SQS または Step Functions に渡して、即座に応答します。

「これは月にいくらかかるんだ?」とトムが尋ねました。

REST API では: 100万 API 呼び出しあたり3.50ドル、加えてデータ転送の GB あたり0.09ドル。小〜中規模のトラフィックでは、本質的に無料です。大量の API では、HTTP API のより低い価格設定が意味を持ってきます。

レオは、彼が以前書いた Lambda のトリガーリストを指さしました。「つまり API Gateway は単に Lambda をトリガーする方法ではない。Lambda を本物の API のように感じさせるものだ。」

「Lambda 関数がビジネスロジックを扱う」とプリヤが言いました。「API Gateway がその前のすべてを扱う — ルーティング、認証、スロットリング、監視。それぞれが1つのことをする。」

「それで、もし誰かが API Gateway を迂回して Lambda を直接呼び出そうとしたら?」

「Lambda の実行ポリシーは、API Gateway からの呼び出しだけを許可する」とプリヤが言いました。「Lambda のリソースベースのポリシーが、それ以外のすべてを拒否する。」

現実: サーバーレスにはそれ自身の運用上の複雑さがあります — 分散した Lambda 関数のデバッグ、コールドスタートの管理、同時実行制限の理解。それはよりシンプルなのではなく、ただ違うのです。

「待って — でも *なぜ* サーバーレスは『よりシンプルではない』の?」とマヤが尋ねました。「売り文句のすべては、運用の負担を取り除くことなのに。」

「いくつかの運用の負担を取り除く」とレオが言いました。「インフラのプロビジョニング、パッチ適用、スケーリング設定 — それらはなくなる。残るのは違うものだ: コールドスタートの管理、SSH できない関数をまたいだ分散トレース、同時実行制限、関数のバージョンとエイリアスの管理、レイヤーの更新がどう伝播するかの理解、15分のタイムアウトを優雅に扱うこと。」

「つまり負担はシフトする」とプリヤが言いました。「インフラの運用から関数の運用へ。」

「そうだ。多くのワークロード — 特にイベント駆動の、小さい、急増するもの — にとっては、それはより良いトレードだ。エンジニアがやり取りしデバッグする必要のある長時間実行のアプリケーションサーバーにとっては、EC2 やコンテナがしばしば正しい選択のままだ。」

サーバーレスは未来であり、最終的にすべてが Lambda に移るべきか、と疑問に思うかもしれません。正直な答えは、ワークロードによる、です。サーバーレスはイベント駆動処理を支配してきました。(API Gateway + Lambda 経由で) HTTP API に大きく食い込んできました。それは常時稼働のアプリケーションサーバー、長時間実行のバッチ処理、ステートフルなサービスを置き換えてはいません — そしておそらく置き換えないでしょう。なぜなら、それらのユースケースは Lambda のモデルから恩恵を受けないからです。正しいツールの問いは決してなくなりません。それはただ、時とともに異なる選択肢に適用されるだけです。

## 強みと限界

**なぜ Lambda が強力なのか**:

- 真の従量課金 — アイドル時のコストはゼロ
- 設定なしの自動スケーリング
- パッチを当てたり維持したりするサーバーがない
- 寛大な無料枠 (月100万リクエスト、永久に無料)
- AWS の残りとの緊密な統合
- RDS Proxy と Lambda レイヤーは、最も一般的な Lambda の痛点 (接続プーリングとコード共有) のうち2つに、アーキテクチャの変更を要求せずに対処します

**複雑になるところ**:

- コールドスタートは現実のもので、レイテンシに敏感なワークロードには慎重な対処が必要です
- 15分の実行制限は長時間実行のタスクを除外します
- デバッグはより難しい — SSH できる永続的なサーバーがない
- ステートレスな設計は、すべての状態を外部化することを要求します (データベース、キャッシュ、S3)
- 同時実行制限 (デフォルトでアカウントあたり1,000の並行呼び出し) が規模でスロットリングすることがあります
- VPC 接続された Lambda 関数には追加のレイテンシとコールドスタートの問題があります

**SSH なしの Lambda 監視**

何かが Lambda 関数で壊れた最初のとき、レオの本能は SSH してプロセスを見ることでした。SSH できるプロセスはありません。Lambda の実行環境は一時的でアクセス不能です。

Lambda のデバッグには、異なるツールキットを学ぶことが必要です:

**CloudWatch Logs**: すべての Lambda 呼び出しは、その stdout/stderr を CloudWatch のロググループに書き込みます。構造化ロギング (JSON フォーマット) はこれらをフィルタ可能にします。最も有用なフィールド: 関数名、呼び出し ID、時間、エラータイプ、そしてあなたのカスタムの相関 ID。

**CloudWatch Metrics**: Lambda は Invocations、Duration、Errors、Throttles、ConcurrentExecutions のメトリクスを自動的に発行します。Errors と Throttles にアラームを設定することは、あらゆる Lambda デプロイの初日であるべきです。

**AWS X-Ray**: Lambda の分散トレース。小さなオーバーヘッド (呼び出しあたり2〜5ミリ秒) を追加しますが、関数内のどこで時間が費やされているかのフレームグラフを与えます。コールドスタート分析に不可欠です — X-Ray は初期化フェーズをハンドラフェーズと別に示します。

**Lambda Insights**: Lambda の拡張監視で、CloudWatch Lambda Insights 経由で利用できます。標準のメトリクスにメモリ使用量、CPU 時間、初期化時間を追加します。少し追加コストがかかりますが、本番関数には価値があります。

「それで、もし誰かが実行環境を通じて侵入しようとしたら?」とプリヤが尋ねました。「Lambda 関数は分離されたコンテナで動くけど、依存関係に脆弱性があれば、攻撃者は私たちの Lambda 内でコード実行を得られる?」

緩和策: 依存関係を最小限かつ最新に保つ (コールドスタート分析がすでにレオにパッケージサイズの縮小を促していました)、共有ライブラリをバージョン管理するために Lambda レイヤーを使う、そして Lambda 実行ロールに最小限の必要な権限を与える。関数が1つの特定の S3 バケットにのみ書き込め、1つの特定の DynamoDB テーブルにのみクエリできるなら、侵害された関数の爆発半径は、まさにそれだけに限定されます。

「Lambda 実行ロールの最小権限はオプションではない」とプリヤが言いました。「何かがうまくいかなくなったときに被害を限定するものよ。」

彼女は正しかったのです。そしてほとんどのセキュリティの助言と同じように、それは単に良いエンジニアリングでもありました。

## 概要

第19章の SQS/SNS アーキテクチャは、仕事を受け付けることと処理することの関心を分離しました。Lambda はそれをさらに進めます: 仕事を処理することと、それをするための容量に支払うことの関心を分離します。

- **AWS Lambda** は、サーバーを管理せずにイベントに応答してコードを実行します。
- **従量課金**: 呼び出しごと、実行1ミリ秒ごと (切り上げ) に課金されます。アイドル時のコストはゼロです。
- 0 から数千の並行呼び出しまで自動的にスケールします。
- **コールドスタート**: ウォームな実行環境が存在しないときの初期化レイテンシ。プロビジョンド同時実行や軽量なランタイムで緩和されます。
- **Lambda レイヤー**: 複数の関数が参照できる共有コードパッケージで、重複とパッケージサイズを削減します。
- **RDS Proxy**: Lambda と RDS の間に永続的なデータベース接続プールを維持することで、Lambda の接続枯渇の問題を解決します。
- **監視**: CloudWatch Logs、Metrics、X-Ray トレース、Lambda Insights を使います — SSH できるサーバーはありません。
- 最適なのは: イベント駆動、短時間実行、急増型、または頻度の低いワークロード。
- 理想的でないのは: 長時間実行のタスク (15分の固い制限)、ステートフルなアプリケーション、プロビジョンド同時実行なしの高スループット低レイテンシの API。
- **サーバーレス** は設計の哲学です — あなたはコードを管理し、インフラを管理しません。運用上の複雑さはシフトするのであって、消えるのではありません。

## 試験のヒント

*SAA-C03 ドメイン: 回復力のあるアーキテクチャの設計 (ドメイン2、タスク2.1)*

- **Lambda + S3**: 古典的なパターン — S3 にアップロードされたファイルが処理のために Lambda をトリガー (サムネイル生成、ウイルススキャン、データ変換)。サーバー不要。
- **Lambda + SQS**: Lambda が SQS をポーリングしバッチを処理。SQS がリトライ/DLQ メカニズムを提供。Lambda が処理を提供。
- **Lambda + API Gateway**: サーバーレス HTTP API。API Gateway がルーティング、認証、スロットリングを扱う。Lambda がビジネスロジックを扱う。
- **API Gateway のタイプ:** REST API = フル機能、リクエスト変換、キャッシュ、使用量プラン。HTTP API = よりシンプル、安価、OIDC/OAuth のみ。WebSocket API = 永続的な双方向接続。**認可:** Cognito オーソライザー = Cognito JWT をネイティブに検証。Lambda オーソライザー = カスタムのトークン検証ロジック。API キー = クライアントごとのレート制限 (認証ではない)。試験のトリガー: 「サーバーレス REST API」 → API Gateway + Lambda。
- **コールドスタートのシグナル**: 「最初のリクエストでレイテンシのスパイク」「一貫しない応答時間」 → コールドスタート。解決策: プロビジョンド同時実行 (お金がかかる)、より小さいパッケージ、より軽いランタイム。
- **実行制限**: 最大15分。最大10GB メモリ。デフォルトで512MB の /tmp 一時ストレージ (最大10GB まで設定可能)。これらの制限は試験のシナリオに現れます。
- **Lambda のタイムアウトエラーは静かである**: Lambda 関数がタイムアウトすると、CloudWatch のエラーを生み出しますが、アプリケーションレベルのエラー応答は生み出しません。CloudWatch の Lambda タイムアウトエラーを明示的に監視してください。これが、レオの17分のレポートジェネレーターが、アプリケーションレベルのアラームなしに最初の夜に失敗した方法です。
- **VPC Lambda のコールドスタート**: VPC 内の Lambda 関数には追加のコールドスタートレイテンシ (ENI のプロビジョニング) があります。AWS は Hyperplane ENI でこれを大幅に改善しましたが、VPC Lambda のコールドスタートは依然として非 VPC より遅いです。VPC リソースを必要としない (つまり、RDS、ElastiCache、または他の VPC 限定のリソースに接続しない) Lambda 関数では VPC を避けてください。
- **Lambda 同時実行**: デフォルトでアカウントあたり1,000の並行実行 (引き上げ可能)。**予約済み同時実行 (Reserved concurrency)**: 関数が特定の数の実行を得ることを保証し、他の関数がそれらを消費するのを防ぎます。**プロビジョンド同時実行 (Provisioned concurrency)**: いくつかの実行環境を事前ウォームアップします。
- **イベントソースマッピング**: SQS/DynamoDB Streams/Kinesis を Lambda に接続する Lambda の機能。Lambda がソースをポーリングしレコードをバッチ化します。
- **アカウント制限への到達**: 「アプリケーションがスケールするにつれてスロットリング / LimitExceeded される」 → **Service Quotas** で制限を確認し、そこで引き上げをリクエスト (Lambda 同時実行のような多くのクォータは調整可能。一部は固い制限)。
- **RDS Proxy**: 試験のシグナル: 「Lambda 関数がデータベース接続を多く作りすぎる」「Lambda での接続プール枯渇」。 → RDS Proxy が永続的な接続を維持し、Lambda の短命な接続を多重化。
- **Lambda レイヤー**: 試験のシグナル: 「複数の Lambda 関数でコードを共有」「デプロイパッケージサイズを削減」 → Lambda レイヤー。
- **Lambda + X-Ray**: Lambda の分散トレース。試験シナリオ: 「複数の Lambda 関数とサービスをまたいでリクエストをトレース」 → Lambda で X-Ray トレースを有効化。
- **Lambda Destinations:** 非同期の Lambda 呼び出しでは、成功と失敗の両方の結果に対して Destination を設定できます。成功した結果を SQS、SNS、EventBridge、または別の Lambda 関数に送ります。失敗をアラートのために SQS または SNS に送ります。これは非同期呼び出しにとって DLQ より好ましい代替策です。なぜなら、失敗だけでなく、成功と失敗の両方を捕捉するからです。試験のシグナル: 「成功した Lambda の結果を別のサービスにルーティング」または「非同期 Lambda から成功と失敗の両方の結果を捕捉」 → Lambda Destinations。「非同期呼び出しの失敗したメッセージだけを捕捉」 → DLQ も依然有効ですが、Destinations のほうがより完全な解決策です。

**演習2 — SAA-C03 シナリオ**

*シナリオ*: ある会社は、サプライヤーから S3 バケット経由で製品画像を受け取ります。各画像は4つの標準サイズ (サムネイル、小、中、大) にリサイズされ、S3 に戻して保存される必要があります。ボリュームは予測不能です — ある日は10枚、ある日は100,000枚。処理は画像あたり10分以内に完了しなければなりません。コストは最小化されなければなりません。

これらの要件を最も満たすアーキテクチャはどれですか?

A) ロングポーリングで S3 バケットを監視する Auto Scaling Group 内の EC2 インスタンス  
B) S3 を毎分新しい画像についてチェックする cron ジョブを持つ専用 EC2 インスタンス  
C) SQS キューによってトリガーされる ECS Fargate タスク、S3 イベントがキューに発行  
D) 画像をリサイズして結果を S3 に保存する Lambda 関数をトリガーする S3 イベント通知

**ヒント1**: 予測不能なボリュームはスケール・トゥ・ゼロを好みます。どの選択肢がそれを行いますか?

**ヒント2**: 画像あたり10分は Lambda の15分の制限内です。画像リサイズの作業が Lambda の制約に収まるかどうかを確認してください。

**ヒント3**: 24時間365日動く専用 EC2 インスタンスは高価で、スケールしません。

**解答**: D

**説明**: S3 イベント通知は、画像がアップロードされたときに Lambda をトリガーします。Lambda は画像を4つのサイズにリサイズし、結果を S3 に保存します。Lambda は 0 から数千の並行呼び出しまで自動的にスケールし、事前プロビジョニングなしで予測不能なボリュームを処理します。画像が処理されていないときのコストはゼロです。

**なぜ A ではないのか?** ASG 内の EC2 はゼロまでスケールしません — 最低1インスタンスが常に動いています。S3 のロングポーリングはネイティブな S3 イベントメカニズムではありません。急増型ワークロードでは Lambda より高コストです。

**なぜ B ではないのか?** 専用 EC2 インスタンスは単一障害点で、スケールせず、24時間365日動き、cron ベースのアプローチには最大60秒の検出遅延があります。

**なぜ C ではないのか?** ECS Fargate は機能しますが、より複雑で (コンテナ管理、ECR、タスク定義が必要)、Fargate タスクの起動には数十秒から数分かかり — Lambda のコールドスタートよりはるかに遅く — 急増型のイベント駆動の作業には適合が悪いです。Lambda はこのユースケースにはよりシンプルです。
