**3つの異なる問題**

Nimbus のデータの問題には3つの次元がありました:

**リアルタイムストリーミング**: 注文は今この瞬間に行われています。注文の速度のライブダッシュボード — 1分あたり何件、リージョンごと、レストランごと — を見たい。データは到着するにつれて処理される必要があります。

**データ変換**: データはさまざまなシステムから、異なるフォーマット (JSON、CSV、Parquet) で S3 にあります。それを分析できる前に、正規化する必要があります — 同じスキーマ、同じフォーマット、クリーンアップされ、参照データと結合されて。

**アドホック分析**: データが整理されたら、最初にデータベースにロードすることなく、それに対して SQL クエリを実行したい。「過去30日間で売上上位10位のレストランを教えて。」データをデータベースにロードすることなく。

これらのそれぞれが別個の問題です。AWS にはそれぞれに専用のサービスがあります。

**リアルタイムストリーム: データのためのティッカーテープ**

ティッカーテープマシン — 株価を連続した紙のロールに印刷したような種類 — を想像してください。価格は変化するにつれて印刷されました。現在の価格が欲しい誰もがテープを読めました。誰も他の誰かを待つ必要はありませんでした。テープは、何人が読んでいるかにかかわらず印刷を続けました。

それがリアルタイムデータストリーミングのモデルです。プロデューサーはデータを起こったときに送ります。複数のコンシューマーが同時にストリームを読めて、それぞれが自分のペースで、それぞれが全体像を得ます。

**Amazon Kinesis Data Streams** が、Nimbus のためのそのマシンです。注文が行われると、アプリケーションは Kinesis ストリームにイベントを発行します: `{ "orderId": "ORD-7741", "restaurantId": "47", "total": 3200, "timestamp": "...", "region": "us-west-2" }`。

このストリームのコンシューマー:

- リアルタイムダッシュボード (イベントを到着するにつれて読み、メトリクスを更新)
- 不正検出 Lambda (異常な注文パターンを探す)
- 永続的なストレージのための S3 へのストリーム

**Kinesis Data Streams の概念**:

- **シャード (Shard)**: 容量の基本単位。1つのシャードは1 MB/s の書き込み、2 MB/s の読み取りを処理します。
- **保持期間 (Retention period)**: データはストリームに24時間 (デフォルト) とどまり、Extended Data Retention で **365日** (1年) まで延長可能です。
- **シーケンス番号 (Sequence number)**: 各レコードにはシーケンス番号があります。コンシューマーはストリーム内の自分の位置を追跡します。

**Amazon Data Firehose** (旧 **Kinesis Data Firehose**): ストリーミングのプロデューサーと、S3、Redshift、OpenSearch のような宛先との間のマネージドな配信サービス。データを自動的にバッファ、圧縮、変換、配信します。

Nimbus にとって: Kinesis Data Streams → Amazon Data Firehose → S3 (Parquet フォーマット、圧縮、日付でパーティション分割)。

「もうデプロイした — あ。」レオは、最初に書き込みスループットを計算せずにシャード数を1に設定していました。Nimbus の注文量では、1つのシャードで問題ありませんでした。彼は誰かが推測したことに気づく前にこれを確認しました。

**翻訳者: 生データを理解する**

S3 のデータは生です。それを効率的に分析できる前に、そこに何があるかを発見し、それを一貫したフォーマットに変換し、異なるデータセットを一緒に結合し、不良レコードと欠損値を扱う必要があります。

それは専用の翻訳層の仕事です。

**AWS Glue** は、フルマネージドの ETL (Extract、Transform、Load) サービスです。2つの主要なコンポーネントがあります:

**Glue Data Catalog**: S3 のデータを記述するメタデータストア — どのテーブルが存在するか、どのカラムを持つか、データファイルがどこにあるか。それはあなたのデータレイクのためのカード目録のようなものです。

**Glue クローラー (Crawlers)**: S3 をスキャンし、スキーマを推論し、Data Catalog を populate する自動化されたエージェント。S3 バケットでクローラーを実行すると、10分後にはすべてのテーブルのカタログができています。

**Glue ジョブ (Jobs)**: 実際の変換を行うサーバーレスの Spark/Python ジョブ。変換ロジックを書く (または Glue のビジュアル ETL ツールを使う) と、Glue がそれをマネージドなインフラストラクチャで実行します。

Nimbus にとって:

1. Glue クローラーが S3 の注文データをスキャン → Glue Data Catalog にテーブル定義を作成
2. Glue ジョブが生の JSON 注文イベントをクリーンな、パーティション分割された Parquet フォーマットに変換
3. 変換されたデータが、クエリに最適化されたレイアウトで S3 に書き戻される

**ETL が壊れるとき: スキーマ進化の問題**

Glue のパイプラインは最初の3週間きれいに動きました。それから、レストランパートナー #412 が自分のメニューエクスポートに新しいフィールド `allergen_tags` を追加しました。そのフィールドは文字列の配列 — `["gluten", "dairy", "nuts"]` — で、レストランの夜間のデータエクスポートに現れました。

Glue ジョブのスキーマは厳格でした。注文 JSON に特定のフィールドを期待するように書かれていました。スキーマにないフィールド `allergen_tags` に遭遇したとき、Glue ジョブは失敗しました。

(パートナー #412 と同じメニューエクスポートフォーマットを使う) 47のレストランからの6時間分の注文データが、処理されずに S3 に蓄積されました。昨夜の注文を朝までにクエリ可能にするはずだった夜間の Glue 実行は、代わりに午前2時47分に停止し、CloudWatch に失敗レコードを書き込みました。

トムは、午前9時に Athena クエリを実行しようとして、過去12時間に `0 rows returned` を得たときにそれを見つけました。

「ソースデータが変わったから ETL が壊れたの?」と、レオが何が起きたかを説明したときマヤが尋ねました。

「ETL がスキーマ変更を扱う方法を知らなかったから ETL が壊れた」とレオが言いました。「私たちは、まさにこれらのフィールドを期待する厳格なジョブを書いた。新しいフィールドが現れたとき、それはパニックになった。」

「それで、もし誰かがスキーマ変更を通じて侵入しようとしたら?」とプリヤが尋ねました。「悪意あるレストランパートナーが、パイプラインをクラッシュさせるために意図的に予期しないフィールドを送る?」

その質問は考慮する価値がありました。予期しない入力でクラッシュする ETL パイプラインはサービス拒否のベクトルです: 異常なデータフォーマットを送り、パイプラインをクラッシュさせ、そのレストラン (とフォーマットを共有する他のすべて) が処理を停止します。

修正には2つの部分がありました:

**Glue スキーマ進化**: Glue の動的フレームはスキーマ進化をサポートします — 期待されるスキーマにないフィールドは、失敗を引き起こすのではなく通過させられます。ジョブスクリプトで DataFrames の代わりに DynamicFrames を使い、追加オプションで `mergeSchema` を設定することで有効にします。新しいフィールドは、次のクローラー実行で自動的にスキーマに追加されます。

```python
# 前 (厳格、新しいフィールドで壊れる)
datasource = glueContext.create_dynamic_frame.from_catalog(
    database="nimbus_db",
    table_name="orders"
)

# 後 (スキーマ進化が有効)
datasource = glueContext.create_dynamic_frame.from_catalog(
    database="nimbus_db",
    table_name="orders",
    additional_options={"mergeSchema": "true"}
)
```

**Glue ジョブのアラート**: パイプラインの失敗は、トムが気づくまで約6時間静かでした。Glue ジョブの実行状態 (`FAILED`) の CloudWatch アラームが、5分以内にオンコールのエンジニアに警告したでしょう。アラームのコスト: 月10セント — 実質的に無料です (メトリクス自体はコストがかからず、最初の10のアラームは無料枠に入ります)。

「6時間分のデータが S3 で処理されずに座っていた」と、追いつくために Glue ジョブを手動で再実行したあとレオが言いました。「何も失われなかった — でもアナリティクスがそれだけ遅れていた。アラームがあれば、遅延は30分だっただろう。」

より広い教訓: 外部データを処理する ETL パイプラインは、スキーマ変更を優雅に扱う必要があります。外部のパートナー — レストラン、決済プロバイダー、配達サービス — はデータフォーマットを変えます。パイプラインはそれらの変更に対して脆くてはなりません。

**クエリ層: S3 上で直接 SQL**

これでデータは S3 に、Parquet フォーマットで、日付でパーティション分割されていました。最後の一片: 最初にデータベースにロードすることなく、それに質問する方法。

**Amazon Athena** は、S3 のデータに対して直接 SQL クエリを実行する、サーバーレスでインタラクティブなクエリサービスです。プロビジョニングするデータベースなし、ロードするデータなし。テーブルを定義する (または Glue Data Catalog を使う) と、SQL を書き、Athena が S3 ファイルに対してクエリを実行します。

```sql
SELECT 
    restaurant_id,
    COUNT(*) as order_count,
    SUM(total) as revenue
FROM orders
WHERE year='2024' AND month='09'
GROUP BY restaurant_id
ORDER BY revenue DESC
LIMIT 10;
```

Athena の料金は、クエリがどれだけのデータをスキャンするかに基づきます。us-east-1、us-west-2、そしてほとんどの主要なリージョンでは、標準の SQL クエリはスキャンされたテラバイトあたり5ドルです。Parquet フォーマット (列指向) をパーティションプルーニング (`WHERE year='2024' AND month='09'`) とともに使うことは、Athena が必要なファイルだけをスキャンすることを意味し、それがコストを劇的に削減します。

「30日分のデータでこのクエリを実行できる」とレオが言いました。「そしてうまく保存すれば、驚くほど少ないコストかもしれない。」

「どうしてそんなに少ないコストになるの?」とマヤが尋ねました。「テラバイトのデータをスキャンするなら、どうしてそれが高くないの?」

レオは Parquet を説明しました。行ベースのフォーマット (JSON、CSV) では、20のうち2つのカラムを探すクエリは20すべてを読まなければなりません。Parquet のような列指向のフォーマットでは、必要な2つだけを読みます。50TB のデータセットでは、よく最適化されたクエリは200GB をスキャンするかもしれません。5ドル/TB で、それは1ドルです。

「それで、もし誰かが誤ってテーブル全体をクエリしたら?」とマヤが押しました。

「それが本当のコストリスクだ」とレオが言いました。

Athena がスキャンされたテラバイトあたりで課金するなら、1つの下手に書かれたクエリが大きな予期しない請求を生み出し得るのか、と疑問に思うかもしれません。はい — そしてこれは実際の本番環境で起こります。50TB の最適化されていないテーブルに対するクエリは、月の S3 の請求全体より高くつき得ます。これが、Parquet フォーマットとパーティション分割がオプションの最適化ではない理由です — それらはコストの制御です。Athena はまた、単一のクエリがスキャンを許可されるデータ量を制限するワークグループのクエリスキャン制限もサポートします。

「私たちが考えつくどんな任意の質問にも?」とトムが尋ねました。

「SQL で表現できるどんな質問にも、S3 に保存したどんなデータに対しても。」

トムはレオのノートパソコンに座り、最初のクエリを書きました:

```sql
SELECT
    r.restaurant_id,
    r.restaurant_name,
    AVG(EXTRACT(EPOCH FROM (o.confirmed_at - o.notification_sent_at)) / 60) 
        AS avg_confirmation_minutes,
    COUNT(DISTINCT c.customer_id) AS unique_customers,
    COUNT(DISTINCT CASE WHEN c.order_count > 1 THEN c.customer_id END) 
        AS returning_customers,
    ROUND(
        COUNT(DISTINCT CASE WHEN c.order_count > 1 THEN c.customer_id END) * 100.0 /
        NULLIF(COUNT(DISTINCT c.customer_id), 0),
        2
    ) AS reorder_rate_pct
FROM orders o
JOIN restaurants r ON r.restaurant_id = o.restaurant_id
JOIN (
    SELECT customer_id, restaurant_id, COUNT(*) AS order_count
    FROM orders
    WHERE year >= '2024'
    GROUP BY customer_id, restaurant_id
) c ON c.customer_id = o.customer_id AND c.restaurant_id = o.restaurant_id
WHERE o.year = '2024'
  AND o.status = 'delivered'
GROUP BY r.restaurant_id, r.restaurant_name
ORDER BY avg_confirmation_minutes ASC
LIMIT 20;
```

クエリは11秒間実行されました。結果: 20のレストラン、平均確認時間が速い順にソートされ、その再注文率が並んでいました。

トムは出力を見つめました。

最も速く確認するレストラン — 平均3〜4分以内に注文を認識し確認するもの — は、平均41% の再注文率を持っていました。最も遅く確認するレストラン (平均確認時間18〜22分) は、13% の再注文率を持っていました。

「素早く確認するレストランは、3倍のリピートビジネスを得る」とトムが言いました。

「それは大きな差ね」とマヤが言いました。「なぜ確認の速さが再注文率にそんなに影響するの?」

「顧客が注文をして、それから携帯電話を見ながらそこに座っていたからだ」とレオが言いました。「確認が3分で来れば、彼らは確信する。22分で来れば — あるいは決して来なければ — 彼らは不安になる。不安が製品の失敗なんだ。料理がちゃんと届いても。」

「これは製品の洞察ね」とマヤが言いました。「単なるアナリティクスの洞察じゃない。レストランに、カテゴリ平均と比較した確認時間のベンチマークを見せるべきよ。」

Athena クエリは1.2 GB のデータ (Parquet フォーマット、年と月でパーティション分割された2か月の注文) をスキャンしました。コスト: 0.006ドル。

半セント。Nimbus がレストランのオンボーディングをどう設計するか — どのレストランを成功コーチングのために優先するか、パートナー SLA の一部としてどんな確認時間の目標を設定するか — を変えたビジネスの洞察に対して。

トムは、捨ててきたすべてのデータの価値を再計算する人の表情をしていました。

「それで、もし誰かがクエリ層を通じて侵入しようとしたら?」とプリヤが尋ねました。「あるいは単に、生の注文データから誤って顧客の住所をエクスポートするアナリスト? 顧客の PII、注文履歴、財務記録 — どのテーブルが見えるかすら、誰が制御するの?」

彼女が質問を終える前に、レオも運用上の問題に気づいていました: 1つのチームが、単一のクエリで500ドルの Athena 請求を生み出す壊滅的なフルテーブルスキャンを実行するのを、どうやって止めますか?

**Athena ワークグループ (Workgroups)** が両方の問題を同時に解決します。

ワークグループは、Athena ユーザーをグループ化し、共有設定を適用する名前付きの設定です: クエリ結果の場所、暗号化、そして — 決定的に — クエリごとのデータスキャン制限。

```
ワークグループ: analytics-team
  クエリスキャン制限: クエリあたり10 GB
  制限超過時のアクション: クエリをキャンセル

ワークグループ: engineering-team
  クエリスキャン制限: クエリあたり100 GB
  制限超過時のアクション: 警告のみ

ワークグループ: finance-reports
  クエリスキャン制限: クエリあたり1 GB
  制限超過時のアクション: クエリをキャンセル
```

`analytics-team` ワークグループのアナリストは、誤って50TB のデータをスキャンして250ドルの Athena 料金を生み出すことはできません。クエリは10GB のスキャンを超えるとキャンセルされます。アナリストはエラーメッセージを見て、パーティションフィルターを追加する必要があることを知ります。

ワークグループはまた、チームごとに別個の結果の場所を強制します: エンジニアリングチームのクエリ結果は `s3://nimbus-query-results/engineering/` に行き、財務チームの結果は `s3://nimbus-query-results/finance/` に行きます。チーム間のクエリ結果へのアクセスはありません。

IAM が、どのユーザーがどのワークグループを使えるかを制御します。自動化されたレポートを実行する Lambda 関数は `finance-reports` ワークグループ (厳しく制限) を使います。本番の問題をデバッグするエンジニアは `engineering-team` ワークグループ (より広い制限、キャンセルではなく警告) を使います。生のイベントテーブル (顧客の PII を含む) へのアクセスは、Glue Data Catalog テーブルの IAM 条件を通じて `engineering-team` ワークグループに制限されます。

「それは単なるコスト制御じゃない」とプリヤが言いました。「アクセス制御よ。ワークグループが強制のポイントなの。」

それは彼女の質問に完全に答えました。アクセス制御を飛ばすすべてのデータパイプラインの議論は、最終的にコンプライアンスのインシデントになります — そしてここでは、アナリティクスチームは集約された注文テーブルだけを見て、顧客の PII を持つ生のイベントは明示的な IAM 認可の後ろにとどまりました。Glue Data Catalog は単なるスキーマのディレクトリではありませんでした。それはアクセス制御の境界でした。

「それは余分な仕事じゃない」とプリヤが言いました。「それが設計なの。」

**データレイクアーキテクチャ**

これら3つのサービスは、**データレイクアーキテクチャ (data lake architecture)** と呼ばれるもの — すべてのデータのための中央集権的な S3 リポジトリと、それを処理しクエリするツール — に組み合わさります:

```
アプリケーション (注文、メニュー、イベント)
    |
    | リアルタイムイベント
    ↓
Kinesis Data Streams ──→ Amazon Data Firehose ──→ S3 (生)
                                                   |
                                                   | Glue クローラーがスキーマを発見
                                                   ↓
                                              Glue Data Catalog
                                                   |
                                                   | Glue ジョブが変換
                                                   ↓
                                              S3 (クリーン、Parquet、パーティション分割)
                                                   |
                                                   | SQL クエリ
                                                   ↓
                                              Amazon Athena
                                                   |
                                                   ↓
                                          ビジネスインテリジェンスツール
                                       (QuickSight、Tableau など)
```

生のデータは常に保存されます (元の S3 バケットに)。変換されたデータは Athena 経由でクエリ可能です。新しい質問は、生のデータに対して新しい Glue ジョブを実行することで常に答えられます。

**Amazon Redshift: Athena では不十分なとき**

一部のユースケースでは、Athena は遅すぎるか高すぎます:

- 多くの結合を伴う非常に複雑なクエリ
- 同じクエリを1日に数千回実行するダッシュボード
- 構造化データに対する機械学習
- BI ツールのサブ秒の応答時間要件

**Amazon Redshift** は、フルマネージドのデータウェアハウスです: 大規模で繰り返される分析ワークロードのために設計された列指向の分析データベース。Athena が S3 でデータが存在する場所をクエリするのとは異なり、Redshift はデータを最適化されたウェアハウスストレージにロードし、クエリ最適化、ソート戦略、分散戦略を使って複雑な分析を加速します。

データ量が小さく、クエリが頻繁でない (週次や月次) なら、よく整理された S3 データを持つ Athena で十分で、ほぼ無料です — しかし、同じ分析ダッシュボードを1日に数百回実行するなら、Redshift の事前最適化された列指向ストレージのほうが速く、最終的により費用効率が高くなります。事前にデータをロードする必要があるにもかかわらず。

Redshift は、コスト (プロビジョニングされた容量) とクエリ前にデータをロードする要件を犠牲にして、複雑な分析クエリに大幅に速いです。

**Redshift Serverless** は容量計画の負担を取り除きます — クエリすると、Redshift がスケールします。コストは実際に使われたコンピュート容量に基づき、**RPU 時間** で測られ、秒ごとに課金されます (アクティベーションあたり60秒の最小値付き)。加えて GB 月あたりのマネージドストレージ — そしてウェアハウスがアイドルで座っている間のコンピュートには何もかかりません。(Athena はクエリごとに課金される唯一のもの: スキャンされた TB あたり5ドル。)

現在の規模の Nimbus にとって: Athena で十分です。5倍のデータ量で、BI ツールが同じダッシュボードを1日に数百回クエリするようになれば、Redshift が費用効率が高くなります。

**Athena が間違ったツールであるとき**

「それで落とし穴は何?」とマヤが尋ねました。「なぜすべてに Athena を使わないの? サーバーレスで、クエリごとの支払いで、インフラなし — 完璧に聞こえる。」

Athena が正しい答えでないケース:

**高頻度のダッシュボード**: 30秒ごとに更新され、1分あたり50のクエリを実行する顧客向けのアナリティクスダッシュボードは、良い Athena のユースケースではありません。スキャンされた TB あたり5ドルでは、それらのクエリはその頻度で費用効率が高くなるために極めてよく最適化される必要があります。サブ秒の応答時間要件を持つダッシュボードには、Redshift や事前集約されたデータベース (RDS でさえ) のほうが適切です。

**低レイテンシ要件のある運用クエリ**: カスタマーサービスのエージェントが特定の注文を500ミリ秒未満で調べる必要があれば、Athena はツールではありません — DynamoDB の検索や RDS のクエリです。Athena は運用のレイテンシではなく、分析のスループットに最適化されています。小さなデータセットに対するよく調整された Athena クエリでさえ、1〜3秒のコールドスタートのオーバーヘッドがあります。

**トランザクションシステム**: Athena は読み取り専用です。Athena でレコードを INSERT、UPDATE、DELETE することはできません (Lake Formation や Iceberg テーブルフォーマットのような特定の統合を除いて。それらには独自の複雑さがあります)。運用の書き込みワークロードには、トランザクションデータベースを使います。

**非常に小さい、頻繁に変わるデータセット**: データセットが毎分変わり、1GB しかないなら、それを RDS や DynamoDB にロードしてそこでクエリするほうが、古いかもしれない S3 ファイルに対して Athena クエリを実行するよりシンプルで速いです。Athena はクエリの時点での S3 ファイルをクエリします — ファイルが2分前に書き込まれたなら、それがあなたが得る鮮度です。

現れるパターン: Athena は、S3 データに対する大規模で、頻繁でない、アドホックな分析クエリに優れています。運用、トランザクション、またはサブ秒のレイテンシを必要とするあらゆるものには、適切な運用データベースを使います。

**Kinesis vs SQS: 混乱を解消する**

これはすべてのデータアーキテクチャの議論で出てくる質問です。Kinesis と SQS は両方ともメッセージを扱います。それぞれをいつ使いますか?

混乱は表面的な類似性から来ます: 両方ともプロデューサーからメッセージを受け付けます。両方ともそれらのメッセージをコンシューマーに配信します。両方ともマネージドな AWS サービスです。しかし、それらのデータモデルは根本的に異なります。

**SQS (Simple Queue Service)** はタスクキューです。メッセージを入れます。1つのコンシューマーがそれを取り出して処理します。処理が完了すると、メッセージは削除されます。10のコンシューマーがあれば、各メッセージはそのうちのちょうど1つに行きます。メッセージは消費後になくなります。

**Kinesis Data Streams** はログです。レコードを入れます。すべてのコンシューマーがすべてのレコードを読みます。コンシューマー A がそれらすべてを読みます。コンシューマー B もそれらすべてを、自分のペースで読みます。どちらのコンシューマーもレコードを削除しません — それは保持期間が切れるまでストリームにとどまります。いつでも3番目のコンシューマーを追加でき、それはストリームの最初から (保持ウィンドウ内で) 読めます。

「いつ実際に、すべてのコンシューマーがすべてのメッセージを見ることを望むの?」とマヤが尋ねました。

答えは、Kinesis が輝くユースケースです:

**リアルタイムダッシュボード + 不正検出 + S3 アーカイブ**: 3つすべてが同じ注文イベントストリームを同時に消費します。SQS を使ったら、3つの別個のキューに発行する必要があり — そして発行する者は3つすべてのコンシューマーについて知らなければなりません。Kinesis では、プロデューサーは一度発行し、任意の数のコンシューマーが独立して読めます。

**リプレイ**: コンシューマーが2時間失敗します (Lambda の同時実行制限に当たる、下流のサービスがダウン)。SQS では、それらのメッセージはすでに削除されていました (または定義された可視性タイムアウトがあります)。Kinesis では、コンシューマーは最後のチェックポイントから再開し、見逃した2時間分のレコードを処理します。データはストリームに保持されていました (Extended Data Retention で最大365日)。

**シャード内の順序**: 同じパーティションキーを持つレコードは常に同じシャードに行き、順序を保ちます。シンボル `AMZN` のすべての取引を順番に処理する必要のある株取引システムには、Kinesis がこれを保証します。SQS FIFO はグループごとの順序を提供しますが、より低いスループットで (標準モードでバッチングを伴うキューあたり最大1秒あたり3,000メッセージ — ハイスループットモードがこれを数万に上げる — に対して、Kinesis の1 MB/s またはシャードあたり1秒あたり1,000レコードに、必要なだけのシャードを掛けたもの)。

決定的な質問: **すべてのメッセージがちょうど1つのコンシューマーによって消費され、それから破棄される必要があるか?** → SQS。**各メッセージが複数のコンシューマーによって独立して見られる必要があるか、またはリプレイ機能が必要か?** → Kinesis。

Nimbus のリアルタイムダッシュボードには: Kinesis。複数のコンシューマー (ダッシュボード、不正検出、S3 アーカイブ) がすべて同じストリームを読みます。

Nimbus の注文処理キュー (注文が行われる → 1つの ECS タスクがそれを処理) には: SQS。1つのコンシューマー、リプレイ不要、ファンアウト不要。

## データの可視化: Amazon QuickSight

Athena がデータをクエリします。Glue がそれを準備します。しかし、ある時点で誰かがチャートを見る必要があります — そして、コンソールで SQL クエリを実行することによってではなく。

「本当にそのために別のサービスが必要なの?」とマヤが尋ねました。「Athena の結果をスプレッドシートにエクスポートするだけじゃだめ?」

「1つのクエリには、そうだ」とトムが言いました。彼はすでにこれを試した人の表情をしていました。「チーム全体と共有したいダッシュボードには、それは毎朝新しいスプレッドシートだ。」

**Amazon QuickSight** は、AWS のマネージドなビジネスインテリジェンス (BI) サービスです。Athena、S3、RDS、Redshift、その他のソースに直接接続し、別個の BI サーバーなしでダッシュボードと可視化を構築できます。

主要な機能:

- **SPICE** (Super-fast, Parallel, In-memory Calculation Engine): QuickSight はデータセットをそのインメモリエンジンにインポートして、ダッシュボードのロードごとに Athena を再クエリすることなく、規模でのサブ秒のクエリ性能を実現できます
- **ML Insights:** 異常検出と予測が組み込まれている — データサイエンス不要
- **埋め込みダッシュボード:** URL 経由で QuickSight ダッシュボードを自分の Web アプリケーションに埋め込めます

トムは QuickSight を Athena データソースに接続し、午後のうちに日次の注文、レストランごとの売上、コンバージョンファネルを示す動くダッシュボードを持っていました。

「それは月にいくらかかるんだ?」と彼は尋ね — それから誰かが答える前に自分の質問に答えました。「QuickSight はオーサー — ダッシュボードを構築する人々 — あたり月に約24ドル、リーダーあたり月に3ドルで動く。私たちにはそれを使う4人がいる。」

「だから月に約100ドルね」とマヤが言いました。

「そうでなければ別個のアナリティクスサーバーを動かすことを必要とする BI サービスに対して」とプリヤが言いました。「ええ。」

トムはダッシュボードを公開しました。翌朝、Athena クエリを実行する代わりに、チーム全体が URL を開きました。

> **試験のヒント — QuickSight**
>
> QuickSight は AWS のマネージドな BI と可視化のサービスです。Athena、S3、Redshift、RDS に接続します。SPICE は、繰り返されるダッシュボードクエリを加速するインメモリのクエリエンジンです。試験のトリガー: 「AWS でのビジネスインテリジェンスダッシュボード」または「Athena/Redshift からのデータを可視化」 → QuickSight。

## レイクの統治: AWS Lake Formation

Nimbus のデータレイクが成長するにつれて、データアクセスが統治の問題になりました。

「誰が生のトランザクションログをクエリできる?」と、次のアーキテクチャレビューでプリヤが尋ねました。「誰が顧客の PII を見られる? 誰が財務サマリーのテーブルにアクセスできる?」

「エンジニアリングはフルアクセスを持つ」とレオが言いました。「アナリティクスチームは集約されたテーブルへのアクセスを持つ。財務は売上テーブルへのアクセスを持つ。」

「どこで設定されているの?」

レオは間を置きました。「えーと... いくつかの異なる場所だ。S3 バケットポリシー、IAM ポリシー、Glue カタログの権限。」

「3つの別個のシステム、そのすべてが一貫していなければならない」とプリヤが言いました。「新しいアナリストを追加したとき何が起こるの? あるいは、特定のカラム — たとえば顧客の電話番号 — へのアクセスをアナリティクスチームから制限することにしたとき?」

その質問はギャップを露呈しました。S3 バケットポリシー、IAM、Glue Data Catalog をまたいできめ細かいデータアクセスを同時に管理することは脆いものでした。

**AWS Lake Formation** は、データレイクのアクセス制御を中央集権化するマネージドサービスです。バケットポリシー、IAM ポリシー、Glue カタログの権限を別々に管理する代わりに、Lake Formation はデータに対してカラムレベル、行レベル、テーブルレベルの権限を付与する単一の場所を提供します。

主要な機能:

- S3 と Glue Data Catalog の上に乗る — データ移行不要
- **きめ細かいアクセス制御:** 特定のユーザーやロールに、特定のテーブル、カラム、またはフィルタリングされた行へのアクセスを付与する — S3 データに対するデータベースレベルの権限に相当
- **データフィルタリング:** ユーザーが Athena 経由で Lake Formation が統治するテーブルをクエリすると、Lake Formation は彼らが見ることを許可されていないカラムや行を自動的にフィルタリングします

プリヤは、ラファエルがカラムレベルのルールを起草して、3つの権限の階層で Lake Formation をセットアップしました: エンジニアリングロールはすべてのテーブルとすべてのカラムを見ました。アナリティクスロールは集約された注文テーブルを見ましたが、顧客の PII カラムは見ませんでした。財務ロールは顧客の識別子がマスクされた売上テーブルを見ました。

「つまりアナリストは同じ Athena クエリを実行する」とレオが確認しました。「でも Lake Formation がそれを傍受して、彼らが見る権限のないカラムを取り除く?」

「そのとおり。フィルタリングは自動的だ。アナリストはそれが起きていることを知る必要はない — そして彼らは生の S3 ファイルを直接クエリすることでそれを回避できない。Lake Formation がカタログレベルでアクセスを制御するからだ。」

「それは余分な仕事じゃない」とプリヤが言いました。「それが設計なの。」

> **試験のヒント — Lake Formation**
>
> Lake Formation は、S3 と Glue Data Catalog の上に構築されたデータレイクのアクセス制御を中央集権化します。テーブル、カラム、行レベルできめ細かい権限をサポートします。試験のトリガー: 「S3 データレイクの特定のカラムへのアクセスを制限」または「データレイクの統治を中央集権化」 → Lake Formation。生の IAM との重要な区別: Lake Formation は、IAM ポリシー単独では表現できないカラムレベルと行レベルのフィルタリングを強制します。

## 強みと限界

**Kinesis Data Streams**: データが継続的に到着し、順序が重要なとき — クリックストリーム、金融取引、IoT テレメトリ — に Kinesis を使います。Kinesis はシャード内のレコードの順序を保ち、設定された保持ウィンドウ (デフォルト24時間、Extended Data Retention で最大365日) の間リプレイを可能にします。それが SQS と根本的に異なる点です。トレードオフは運用上の複雑さです: プロビジョンドモードでは、シャードの容量とコンシューマーの動作を管理します。順序が重要でなくリプレイが不要な単純なタスクキューには、SQS のほうがシンプルな選択です。

**AWS Glue**: Glue は従来の ETL クラスターのインフラストラクチャを排除します。変換ロジックを書く。AWS が Spark 環境を管理する。これは変換が複雑だったりデータ量が大きかったりするときに価値があります。限界はコストとコールドスタートです — Glue ジョブには数分の起動遅延があり、ほぼリアルタイムの変換には不向きです。単純なファイルフォーマット変換 (CSV から Parquet) には、Glue のオーバーヘッドは、Lambda 関数や軽量なスクリプトに比べて見合わないかもしれません。

**Amazon Athena**: Athena は、管理するインフラストラクチャなしで標準の SQL で S3 データをクエリできます。決定的な制約はコストです: Athena はスキャンされたデータのテラバイトあたりで課金します。全体をスキャンする10 TB のテーブルに対するクエリは、200 GB をスキャンする Parquet フォーマットでパーティション分割されたテーブルに対する同じクエリより大幅に高くつきます。本番で Athena を実行する前に、常に列指向のフォーマット (Parquet または ORC) を使い、データをパーティション分割してください。これらの最適化なしでは、Athena の請求があなたを驚かせ得ます。

## 概要

第25章のネットワークの作業は、Nimbus のデータパイプラインを可能にしました。この章は、そのパイプラインが何のためかです: Nimbus が生成してきたすべてのデータを実際に見えて行動可能なものにすること。

- **Amazon Kinesis**: リアルタイムデータストリーミング。プロデューサーがレコードを書く。コンシューマーが自分のペースで読む。Amazon Data Firehose はその後、より少ない運用作業でストリーミングデータを S3、Redshift、その他の宛先に配信できます。
- **AWS Glue**: ETL とデータカタログ化。クローラーがスキーマを発見する。ジョブがデータを変換する。Data Catalog がデータを Athena や他のツールから発見可能にする。
- **Amazon Athena**: S3 上のサーバーレス SQL。標準の SQL を使って S3 の任意のデータをクエリ。スキャンされた TB ごとに課金 — コストを最小化するために Parquet とパーティション分割を使う。
- **Amazon Redshift**: 高性能な分析のためのマネージドデータウェアハウス。データをロードし、繰り返される分析クエリのために最適化し、ウェアハウスの規模で速くクエリする。
- **データレイクパターン**: 生のデータを S3 へ → Glue がそれを変換 → Athena がそれをクエリ → BI ツールがそれを可視化。
- **Glue スキーマ進化**: 外部データを処理する ETL パイプラインは、スキーマ変更を優雅に扱わなければなりません。上流のデータが新しいフィールドを追加したときのパイプラインの失敗を避けるために、`mergeSchema: true` を持つ DynamicFrames を使います。
- **Athena ワークグループ**: チームごとのデータスキャン制限と結果の場所。1つの設定でのコスト制御とアクセス制御。マルチチームの Athena デプロイには必須。
- **Kinesis vs SQS**: 複数のコンシューマーへのファンアウトとリプレイ機能には Kinesis。単純なタスクキューには SQS Standard。順序付けされた、重複排除されたタスク処理には SQS FIFO。決定的な質問: すべてのコンシューマーがすべてのメッセージを見る必要があるか、それとも各メッセージが1つのコンシューマーに行くか?
- **Athena が間違っているとき**: 高頻度のダッシュボード (Redshift を使う)、運用クエリ (RDS や DynamoDB を使う)、非常に小さく頻繁に変わるデータセット (単にデータベースを使う)。
- **Amazon QuickSight**: AWS のマネージドな BI サービス。別個の BI サーバーを動かさずにダッシュボードを構築するために Athena、S3、Redshift、RDS に接続。SPICE は、繰り返されるダッシュボードクエリを加速するインメモリエンジン。
- **AWS Lake Formation**: S3 + Glue Data Catalog 上のデータレイクのための中央集権化されたアクセス制御。カラムレベル、行レベル、テーブルレベルの権限を可能にする — IAM 単独では表現できないきめ細かいデータ統治。

## 試験のヒント

*SAA-C03 ドメイン: 高性能なアーキテクチャの設計 (ドメイン3、タスク3.5)*

- **Kinesis vs SQS**: Kinesis = 順序付けされた、リアルタイムストリーミング、複数のコンシューマー、保持ウィンドウ内のリプレイ (デフォルト24時間、最大365日)。SQS = タスクキュー、各メッセージは一度処理される。「同じストリームを同時に読む複数のコンシューマー」 → Kinesis。「メッセージあたり1つのワーカー」 → SQS。
- **Athena の試験シグナル**: 「S3 上のサーバーレス SQL」「データベースにロードせずに S3 データを分析」「クエリごとの支払い」 → Athena。
- **Athena のコスト最適化**: 列指向フォーマット (Parquet または ORC) + パーティション分割が、スキャンされるデータとコストを劇的に削減します。試験は Athena のコストをどう削減するか尋ねることがあります。
- **Athena の料金**: スキャンされた TB あたり5ドル (us-east-1、us-west-2、そしてほとんどの主要なリージョン)。コストは返されたデータではなくスキャンされたデータで計算される — 本番のクエリを実行する前に常にストレージフォーマットを最適化する。
- **Glue クローラー**: 「S3 データのスキーマを自動的に発見」 → Glue クローラー。
- **Amazon Data Firehose**: 「コンシューマーを管理せずにストリーミングデータを S3/Redshift/OpenSearch に自動的にロード」 → Amazon Data Firehose。古い資料はまだそれを Kinesis Data Firehose と呼ぶかもしれません。
- **Redshift vs Athena**: 固定されたデータセットに対する高頻度で複雑なクエリ (BI ダッシュボード) には Redshift。頻繁に変わる S3 データに対するアドホッククエリには Athena。
- **EMR (Elastic MapReduce)**: AWS が管理する Hadoop/Spark クラスター。「既存の Hadoop/Spark ワークロード」または「カスタムのデータ処理フレームワーク」が言及されたとき、試験はこれを使います。Glue はほとんどのユースケースのためのマネージドな代替です。
- **QuickSight:** AWS のマネージドな BI と可視化。Athena、S3、Redshift、RDS に接続。SPICE = 速い繰り返しクエリのためのインメモリエンジン。試験のトリガー: 「AWS でのビジネスインテリジェンスダッシュボード」 → QuickSight。
- **Lake Formation:** データレイク (S3 + Glue Data Catalog) のための中央集権化されたアクセス制御。きめ細かい権限: テーブル、カラム、行レベル。試験のトリガー: 「S3 データレイクの特定のカラムへのアクセスを制限」または「データレイクの統治を中央集権化」 → Lake Formation。

## 練習問題

**練習問題1 — 想起**

Amazon Kinesis と Amazon SQS の違いを説明してください。それぞれをいつ使いますか?

*(ヒント: 何人のコンシューマーが同じデータを読めるか、メッセージが読み取り後に削除されるか、そして順序が重要かを考えてみてください。)*

**練習問題2 — SAA-C03 シナリオ**

*シナリオ*: あるライドシェア会社が旅程データを分析したいと考えています。毎日100万の旅程が完了します。旅程記録は S3 に JSON ファイル (それぞれ約2KB) として保存されます。アナリティクスチームは「先週の都市ごとの平均旅程時間」のようなアドホックな SQL クエリを実行したいと考えています。クエリは2分未満で完了すべきです。ストレージコストは最小化されるべきです。チームは週に20〜30のクエリを実行します。

これらの要件を最も満たすアーキテクチャはどれですか?

A) AWS Glue を使って JSON を日付と都市でパーティション分割された Parquet フォーマットに変換。Amazon Athena でクエリ  
B) 旅程データを毎日 RDS PostgreSQL にロード。標準の SQL でクエリ  
C) Amazon Data Firehose を使って旅程データを Amazon Redshift に配信。Redshift でクエリ  
D) 旅程データを DynamoDB にロードして SQL クエリに PartiQL を使う

**ヒント1**: 週に20〜30のクエリは低頻度です。時々のクエリに最も費用効率が高いサービスはどれですか?

**ヒント2**: Parquet フォーマット + パーティション分割が Athena によってスキャンされるデータ — したがってコスト — を劇的に削減します。

**ヒント3**: 100万の旅程 × 2KB = 1日あたり約2GB。1週間で約14GB。Athena の5ドル/TB で、最適化なしでも、これは手頃です。

**解答**: A

**説明**: Glue は JSON を Parquet (列指向フォーマットがスキャンされるデータを劇的に削減) に、日付と都市でパーティション分割して変換します (パーティションプルーニングは「先週」のクエリが7日分のパーティションだけをスキャンすることを意味します)。Athena は標準の SQL で S3 を直接クエリします。週に20〜30のクエリには、クエリごとの支払いの Athena が、常時動く Redshift に比べて極めて費用効率が高いです。

**なぜ B ではないのか?** 毎日2GB のデータを RDS にロードしてからクエリすることは、24時間365日動くデータベースインスタンスを必要とします。週に20〜30のクエリには、これは大幅に過剰設計で高価です。

**なぜ C ではないのか?** Redshift は高頻度のクエリ (同じデータセットに1日に数百回) には費用効率が高いです。週に20〜30のクエリには、常時オンの Redshift クラスターは Athena のクエリごとの料金よりはるかに高くつきます。

**なぜ D ではないのか?** DynamoDB は、キーベースのアクセスに最適化された key-value/ドキュメントストアで、アドホックな分析クエリのためではありません。DynamoDB の PartiQL は、記述されたような GROUP BY 集約をサポートしません。

*SAA-C03 ドメイン: 高性能なアーキテクチャの設計 — タスク3.5*

**練習問題3 — アーキテクチャチャレンジ** *(オプション)*

Nimbus は、注文のためのリアルタイム不正検出システムを構築したいと考えています。システムは次のことをすべきです:

- 同じアカウントによって60秒間に5回以上行われた注文を検出する
- 新しいアカウント (30日未満) からの500ドルを超える注文をフラグ付けする
- フラグ付けされた注文を人間のレビューキューに送る

アーキテクチャを設計してください。Kinesis は何を提供しますか? 不正のロジックはどこで動きますか? 「同じアカウント、60秒のウィンドウ」をどう相関付けますか? どのサービスがフラグ付けされた注文を受け取りますか?
