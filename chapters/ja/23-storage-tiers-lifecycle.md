**S3 ストレージクラス: 完全なスペクトラム**

第5章では、主要なストレージクラスとして S3 Standard を紹介しました。S3 には実際には8つのストレージクラスがあり、それぞれ異なるアクセスパターンのために設計されています (8番目の **S3 Express One Zone** は、レイテンシが重要なワークロードのための特殊な単一 AZ のクラスで、高性能シナリオの外ではめったに現れません):

**S3 Standard**: 頻繁にアクセスされるデータのために。低レイテンシ (ミリ秒)。最高コスト。最低保存期間なし。アクティブなデータに使います: 現在のメニュー写真、今日の注文、最近のログ。

**S3 Standard-Infrequent Access (S3 Standard-IA)**: 月に1回未満アクセスされるデータのために。Standard と同じミリ秒の取得ですが、より低いストレージコスト + GB あたりの取得料金。30日の最低保存期間。アクセスするときには即座に必要だが、めったにアクセスしないデータに使います: 古い注文レシート、6か月前のアナリティクスのエクスポート。

**S3 One Zone-Infrequent Access (S3 One Zone-IA)**: S3 Standard-IA と同じ (30日の最低保存期間を含む) ですが、(3つではなく) 1つの Availability Zone だけに保存されます。耐久性が低い (その AZ に災害があればデータが失われ得る) が、20%安いです。失われても再作成できるデータに使います: サムネイルキャッシュ、一時的な処理出力。

**S3 Glacier Instant Retrieval**: 時々必要なアーカイブされたデータ。ミリ秒の取得。非常に低いストレージコスト、より高い GB あたりの取得コスト。90日の最低保存期間。四半期に1回以下アクセスされるデータに使います: 四半期のコンプライアンスレポート、12か月前のバックアップスナップショット。

**S3 Glacier Flexible Retrieval**: ディープアーカイブ、数分から数時間で取得。Glacier Instant Retrieval より低コスト。緊急性の低いアーカイブデータに使います。

**S3 Glacier Deep Archive**: 最低コストの選択肢。12時間で取得。180日の最低保存期間。規制コンプライアンスのために保たれなければならないが、アクセスされることが決して予想されないデータに使います: 7年分の税務記録、10年分の監査ログ。

パターン: アクセス頻度が下がるにつれて、コストは下がるが取得時間は増えます (そして取得あたりのコストは増えます)。アクセスパターンに合うクラスを選びます。

**S3 ライフサイクルポリシー: 自動化されたファイリングシステム**

ファイルをストレージクラス間で手動で移動するのはエラーが起きやすく、時間がかかります。S3 の **ライフサイクルポリシー (lifecycle policies)** は、定義したルールに基づいてこれを自動化します。

ライフサイクルルールには2つの要素があります:

**フィルター**: ルールがどのオブジェクトに適用されるか (すべてのオブジェクト、特定のプレフィックスを持つオブジェクト、特定のタグを持つオブジェクト)。

**アクション**: 何を、何日後にするか。

Nimbus の注文レシートのためのライフサイクルポリシーの例:

```
90日後に S3 Standard-IA に移行
365日後に S3 Glacier Instant Retrieval に移行
540日後 (18か月) に S3 Glacier Flexible Retrieval に移行
2555日後 (7年) に S3 Glacier Deep Archive に移行
2920日後 (8年) に削除
```

この単一のポリシーが次を保証します:

- アクティブなレシート (90日未満): S3 Standard、高速アクセス
- 最近のレシート (90〜365日): Standard-IA、安いが即座に利用可能
- 古いレシート (1年〜18か月): Glacier Instant、非常に安く、必要なときはミリ秒
- 歴史的なレシート (18か月〜7年): Glacier Flexible、さらに安い — 取得には数時間かかり、ミリ秒ではない
- 期限切れのレシート (8年超): 自動的に削除

ひとつの落とし穴が計画をほとんど頓挫させかけました。2024年後半以降、ライフサイクルルールは **デフォルトで128 KB より小さいオブジェクトを移行しません** — そして Nimbus のレシートは平均で1つ18 KB でした。ポリシーが実際にそれらを移動するようにするために、レオはルールのデフォルトの最低オブジェクトサイズを上書きしなければなりませんでした (ライフサイクルフィルターは `ObjectSizeGreaterThan`/`ObjectSizeLessThan` でサイズでも選択できます)。デフォルトには良い理由があります: アーカイブクラスはオブジェクトあたり約40 KB のメタデータオーバーヘッドを課金し、すべての移行にはリクエスト料金がかかるので、何百万もの小さなオブジェクトでは、移行が節約する以上のコストになり得ます。レオはレシートの計算をしました — 7年保存では、それでも元が取れました。

トムは予測される節約をレビューしました: 月847ドルから約220ドルへ。

「そして S3 が自動的にそれを移動する」とレオが確認しました。「cron ジョブなし。手動の移行なし。忘れることなし。」

間違ったデータが Glacier に移されて、緊急に必要になったらどうなるのか、と疑問に思うかもしれません。取得料金を払って待つことになります — だからこそ、ライフサイクルルールを最初は小さな、重要でないバケットでテストし、本番データにロールアウトする前にアクセスログを検証すべきです。18か月分のバックアップでの取得ミスは、顧客向けのインシデントよりはるかに安く済みますが、それでも先にテストする価値があります。

データのアクセスパターンが予測可能 (ログは30日後には常にコールド) なら、明示的なライフサイクルルールを使います — それらは Intelligent-Tiering のオブジェクトごとの監視料金より費用効率が高いです。アクセスパターンが時とともに変わったり予測しにくかったりするなら、Intelligent-Tiering を使います — ただし、それは128 KB より小さいオブジェクトを単に無視することに注意してください: それらは監視されず、監視料金も課金されず、Frequent Access 層から決して出ません。

**S3 Intelligent-Tiering: 自己組織化するクラス**

データにどれだけ頻繁にアクセスするか分からない場合はどうでしょうか?

**S3 Intelligent-Tiering** は、各オブジェクトのアクセスパターンを監視し、アクセス層の間で自動的に移動します:

- **Frequent Access 層**: 最近アクセスされたオブジェクトのために
- **Infrequent Access 層**: 30日間アクセスされていないオブジェクト
- **Archive Instant Access 層**: 90日間アクセスされていないオブジェクト
- **Archive Access 層**: 90〜730日間アクセスされていないオブジェクト (オプション)
- **Deep Archive Access 層**: 180〜730日以上アクセスされていないオブジェクト (オプション)

S3 Intelligent-Tiering は、オブジェクトあたり月の小さな監視料金 (1,000オブジェクトあたり0.0025ドル) を課金しますが、Frequent と Infrequent の層には取得料金がありません。

Intelligent-Tiering を使うのは:

- アクセスパターンが予測不能、または時とともに変わる
- 簡単に分類できない、ホットとコールドのデータの混在がある
- 128KB より大きいオブジェクトがある (それより小さいオブジェクトは監視も自動階層化もまったくされません)

(ライフサイクルポリシーを伴う) 明示的なストレージクラスを使うのは:

- アクセスパターンが予測可能
- すべてのオブジェクト — 小さいものも含めて — を実際により安いクラスに移動したい
- オブジェクトが小さい (128KB 未満)

小さなファイルの注意点は強調に値します。Nimbus には S3 に230万の注文レシートオブジェクトがありました — それぞれが小さな JSON ファイルで、平均で約18KB でした。トムは当初、レシートのバケットに Intelligent-Tiering を検討していましたが、細かい注意書きを読むまでのことでした。

128KB より小さいオブジェクトは、Intelligent-Tiering では **監視されず、自動階層化されません**。それらは監視料金 (1,000オブジェクトあたり月0.0025ドル) を払いません — しかし、決して移動もしません: それらは Frequent Access 層に、Standard 相当の価格で、永遠に居座ります。

つまり18KB のレシートにとって、Intelligent-Tiering は Nimbus に追加で何のコストもかけなかったでしょう — ただ、何も *しなかった* でしょう。230万のコールドなレシートが、ホットストレージの価格 (GB あたり0.023ドル) を無期限に払い続け、一方でアーカイブ層 (GB あたり0.00099ドル) は手の届かないところにありました。

「つまり Intelligent-Tiering は大きなオブジェクトのために設計されているのね」とマヤが言いました。

「あるいは、本当にアクセスパターンが分からないワークロードのためだ」とトムが言いました。「レシートが90日間ホットで、その後コールドだと分かっている小さなファイルのバケットには、明示的なライフサイクルルール — 先ほどの小さなオブジェクトの上書きを伴う — が、実際にそれらを移動する唯一のものだ。」

Intelligent-Tiering は優れたサービスです。ただ、すべてのバケットに正しいツールではありません: 128KB の閾値より下では、それは無害だが無用であり、明示的なライフサイクルルール (サイズの上書きを伴う) だけが小さなオブジェクトを階層化します。

要求は正当なものでした。記録は S3 にあり、3つのストレージクラスにまたがっていました: 最新の90日は Standard-IA、その前の1年は Glacier Instant Retrieval、残りは Glacier Flexible Retrieval (ライフサイクルポリシーは18か月以上古いデータに Flexible を使っていました)。

Glacier Instant の記録は即座に利用可能でした。レオはレストラン ID でフィルタリングし、一致する注文記録を特定するために Athena クエリを実行し、それらを安全な S3 の場所にエクスポートしました。5分の作業です。

Glacier Flexible の記録には復元リクエストが必要でした:

```bash
aws s3api restore-object \
    --bucket nimbus-order-receipts \
    --key "2022/06/restaurant-47/" \
    --restore-request '{"Days":7,"GlacierJobParameters":{"Tier":"Standard"}}'
```

Glacier Flexible Retrieval の **Standard 層**: 3〜5時間。記録は7日間 S3 Standard の一時的なコピーとして利用可能になり、その後自動的に削除されます。元のアーカイブされたコピーは Glacier に残ります。

取得全体のコスト: Standard 層で取得した GB あたり0.01ドル、4.2 GB のアーカイブされた記録で。約4セント。(Expedited 層 — 1〜5分 — は GB あたり0.03ドルですが、その可用性は Standard のようには保証されません。)

「4セント」と、レオが報告したときマヤが言いました。「18か月分の記録に。」

「4.2GB を GB あたり月0.0036ドルで1年半保存した」とレオが言いました。「ストレージコストは合計で約27セントだった。取得コストは4セント。S3 Standard で18か月保っていたら1ドル74セントだったのと比べて。」

「そして重要だった唯一のことは」とプリヤが言いました。「それが Flexible Retrieval にあることを覚えていて、3〜5時間の待ちを計画していたことよ。弁護士がこれを30分で必要としていたら、問題になっていた。」

これが Glacier についての重要な運用上の教訓です: それは単にコストの決定ではなく、取得 SLA の決定です。データを Glacier Flexible や Deep Archive にアーカイブする前に、それを必要とするかもしれない誰かのために取得時間を文書化してください。「データが存在する」と「30分で取得できる」は、2つの異なる保証です。

**マルチパートアップロード: 大きなオブジェクトのために**

S3 には5GB の単一アップロード制限があります。より大きなオブジェクトには、**マルチパートアップロード (multipart upload)** を使わなければなりません: オブジェクトをパーツに分割し、それぞれを並列でアップロードすると、S3 がそれらを組み立てます。

利点:

- より速いアップロード (並列)
- 失敗したアップロードを再開できる (失敗したパーツだけを再アップロード)
- 5GB を超えるオブジェクトには必須

ライフサイクルルールのヒント: 不完全なマルチパートアップロードを7日後に削除するライフサイクルルールを設定します。アップロードが途中で失敗してクリーンアップされないと、それらの部分的なパーツが保存され、課金されます — それを示す組み立てられたオブジェクトもないままに。

トムはこのヒントを大いにありがたがりました。

彼はすべての Nimbus バケットにまたがる不完全なマルチパートアップロードをリストする AWS CLI コマンドを実行しました:

```bash
aws s3api list-multipart-uploads --bucket nimbus-restaurant-photos
```

**3つのセキュリティ層: 寄り道の前の簡単な復習**

「それで、もし誰かが侵入して監査ログを削除しようとしたら?」とプリヤが再び尋ねました — 今回は特定の脅威モデルの文脈で。「設定ミスのライフサイクルルールだけじゃない。悪意ある内部者。書き込みアクセスを持つ侵害された IAM キー。」

チームはすでに答えを持っていました — ただ、それをこのバケットに適用していなかっただけです。3つの層、それぞれが本書の前のほうで扱われ、それぞれが異なる脅威ベクトルに対処します:

**バージョニング** (第5章) は削除を取り消し可能にします — DELETE は削除マーカーになり、以前のバージョンは復元可能なまま残ります。注文レシートのような一度だけ書き込むデータでは、ストレージのオーバーヘッドは最小限です: オブジェクトあたり常に1つのバージョンしかありません。

**S3 Object Lock** (第5章) はオブジェクトを真に不変にします — 保存期間中は管理者のキーでさえ削除できない WORM ストレージ。レシートには、その7年の税務保存要件があるため、チームは Compliance モードを選びました: ライフサイクルの設定ミスも、IAM のミスも、侵害された認証情報も、監査人が尋ねる前にそれらを削除できません。そして Object Lock はライフサイクルの移行と共存します — レシートを Glacier Deep Archive に移動するルールは依然として機能します。データは安くなり、不変のまま保たれます。

**CloudTrail の S3 データイベント** (第16〜17章) は、データに何が起きたかを教えてくれます: すべての GET、PUT、DELETE、COPY が、誰が、どこから、いつ、とともにログに記録されます — GuardDuty (第17章) が異常を警告するために使う生の材料です。

「事故からの回復のためのバージョニング。コンプライアンスの不変性のための Object Lock。フォレンジックのための CloudTrail」とプリヤが要約しました。「それぞれを単独で扱った。今日の新しい決定は、このバケットに対して3つすべてを有効にすることよ。」

**クロスリージョンレプリケーション: ディザスタリカバリとしての注文記録**

Nimbus の注文レシートのバケットは us-west-2 にありました。それは意図的でした — us-west-2 はアプリケーションが動く場所です。しかし「アプリケーションが us-west-2 にある」と「すべての注文記録が us-west-2 にだけある」は、異なるリスクプロファイルです。

Nimbus が us-east-1 でディザスタリカバリサイトを起動する必要があれば、注文記録もそこにある必要があります。リージョン障害のさなかにそれらをコピーするのを待つのは、回復計画ではありません。

プリヤは注文レシートのバケットに **クロスリージョンレプリケーション (CRR)** を推奨しました。ルール:

```
ソース: nimbus-order-receipts (us-west-2)
宛先: nimbus-order-receipts-dr (us-east-1)
レプリケーション: すべてのオブジェクト
宛先のストレージクラス: S3 Standard-IA (より安い — これは DR コピーで、めったにアクセスされない)
```

仕組みは第5章でおなじみでした: 新しい書き込みの非同期レプリケーション (ほとんどのオブジェクトは15分以内。保証された SLA には **S3 Replication Time Control** に支払うことが必要)、両方のバケットでバージョニングが必要、ソース読み取り/宛先書き込みの権限を持つ IAM ロール。上記のルールで注目すべき詳細: 宛先がソースとは *異なるストレージクラス* を使います — めったに読まれない2つ目の Standard コピーに支払う代わりに、DR コピーには Standard-IA。そしてバージョニングの前提条件には追加コストがかかりませんでした — 彼らはすでに事故からの回復のためにバージョニングを有効にしていました。(CRR の兄弟である **同一リージョンレプリケーション (SRR)** は、*同じ* リージョンのバケット間でオブジェクトをコピーします — 別アカウントのコンプライアンスコピー、ログ集約、本番データから種を蒔いたテスト環境に役立ちます。)

誰かが当たる前にプリヤが指摘したひとつの落とし穴: レプリケーションは **遡及的ではありません**。ルールを有効にしたときにバケットにすでに存在するオブジェクトはレプリケートされません — 新しい書き込みだけです。チームは既存のすべてのデータが宛先に現れることを期待して CRR を有効にし、それから DR バケットがほぼ空であることを発見します。既存のオブジェクトには、**S3 Batch Replication** を実行します。それは、すでにそこにあったオブジェクトにレプリケーションルールを適用する別個の操作です。Nimbus は、既存の0.8 TB のレシートで DR バケットに種を蒔くために、それを一度実行しました。

「それで削除マーカーは?」とプリヤが尋ねました。「誰かが us-west-2 でレシートを削除したら、その削除は us-east-1 にレプリケートされるの?」

デフォルトでは、いいえ — 現在のレプリケーション設定 (コンソールが作成する V2 スキーマ) では、**削除マーカーはレプリケートされません**。誰かが us-west-2 でレシートを削除しても、us-east-1 のコピーは何も起きなかったかのようにそれを提供し続けます。DR バケットに削除をミラーリング *させたい* なら、ルールで削除マーカーレプリケーションを明示的に有効にします (タグフィルター付きのルールではサポートされません) — それはレガシーの V1 スキーマでのデフォルトで、古い資料がまだそれを記述しています。いずれにせよ、ライフサイクルの有効期限切れは、その削除マーカーをレプリケートしません。

ただし、レプリケーションは依然としてバックアップソリューションでは *ありません* — 逆の理由で: それは永続的なバージョンの削除や悪意ある上書きがミラーにレプリケートされるのを防がず、保存のセマンティクスもありません。真のバックアップには、バージョニングを Object Lock と組み合わせるか、AWS Backup を使います。

「それは月にいくらかかるんだ?」とトムが尋ねました。

us-east-1 の S3 Standard-IA での0.8 TB のストレージ: 月10.00ドル。加えてレプリケーションのデータ転送 (リージョン間で転送された GB ごとに課金): 現在の書き込み量では最小限。追加コストの合計: すべての注文記録の完全なクロスリージョンコピーに対して、おおよそ月10〜11ドル。

トムは文句を言わずにこれを書き留めました。

**S3 Storage Lens: 全体像を見る**

トムは監査を手動でしていました — AWS コンソールをバケットごとに開き、オブジェクトを数える AWS CLI コマンドを実行し、バケットごとのストレージコストについて課金エクスプローラーを確認していました。そのスプレッドシートを作るのに午後のほとんどがかかりました。

**S3 Storage Lens** は、その手動プロセスを置き換える AWS のツールです。すべてのバケット、すべてのアカウント、すべてのリージョンにまたがる S3 の使用状況とアクティビティへの組織全体の可視性を — 単一のダッシュボードで — 提供します。

コスト最適化に最も重要なメトリクス:

**非最新バージョンのバイト**: (バージョニングが有効なとき) 古いバージョンによって消費されるストレージはどれだけか。バージョニングは安全に不可欠ですが、ドキュメントが頻繁に更新されると、古いバージョンが積み重なります。非最新バージョンを30日後に期限切れにするライフサイクルルールが、バージョンの肥大化を防ぎます。

**不完全なマルチパートアップロードのバイト**: まさにレオがロードテストで引き起こした問題が、自動的に浮かび上がります。Storage Lens がなければ、トムは不完全なマルチパートアップロードを探すことを知っていなければなりませんでした。Storage Lens があれば、それらは項目としてダッシュボードに現れます。

**403 を返すリクエストの%**: 公開アクセス可能であるべきバケットでの403 (Forbidden) 応答のスパイクは、設定ミスのバケットポリシーを示すかもしれません。プライベートなバケットでのスパイクは、スキャンや探索の試みを示すかもしれません。いずれにせよ、調査する価値のあるシグナルです。

**平均オブジェクトサイズ**: 小さなオブジェクトのバケット (平均2KB) は、Intelligent-Tiering の経済性、リクエストコスト、Athena のクエリ性能の点で、大きなオブジェクトのバケット (平均50MB) とは異なる振る舞いをします。

S3 Storage Lens には、必須のメトリクスをカバーする無料枠があります。高度なメトリクス (リクエスト統計、フィルタリングのためのレンズグループ) には、月の100万オブジェクトあたりの追加コストがあります — それが可能にする節約に比べれば小さいものです。

「なぜ最初からこれを使わなかったの?」とマヤが尋ねました。

「最初は4.2テラバイトがなかった」とトムが言いました。「小規模では、スプレッドシートで機能する。この規模では、規模そのものがツールの論拠になる。」

これは Nimbus のアーキテクチャで繰り返されるテーマです: ある規模に正しいツールが、次の規模に常に正しいツールとは限らない。S3 Storage Lens は、S3 の使用が、午後に手動で監査できる以上に成長したらすぐに設定する価値があります — それはおおよそ、それが可能にする節約が、それが節約する時間を意味のある形で超え始める頃です。

## 強みと限界

**なぜ S3 ストレージ層が重要なのか**:

- 実際にアクセスされるものの耐久性や可用性を犠牲にせずに、大幅なコスト削減
- ライフサイクルポリシーがプロセス全体を自動化する — 運用上の負担なし
- S3 Intelligent-Tiering がアクセスパターンを予測する必要をなくす

**複雑になるところ**:

- Glacier クラスには最低保存期間の課金が適用される (Glacier Instant は90日、Deep Archive は180日) — 早く削除しても最低料金が発生する
- アーカイブされたデータに頻繁にアクセスすると、取得料金が驚かせることがある
- ライフサイクルの移行には時間がかかる — ルールがトリガーされた後、オブジェクトは即座に移動されない
- Intelligent-Tiering は128KB 未満のオブジェクトを無視する — 料金はないが、階層化もない。そしてライフサイクルルールは、最低オブジェクトサイズを上書きしない限り、デフォルトでそれらをスキップする

## 概要

第22章のワークフロー自動化は、Nimbus がリクエストを処理する方法を最適化しました。この章は、保ってはいるがアクセスしていないデータに対して Nimbus が支払うものを最適化します。原則は同じです: 間違った層に支払うのをやめること。

- S3 には8つのストレージクラスがあります: Standard、Standard-IA、Intelligent-Tiering、One Zone-IA、Glacier Instant Retrieval、Glacier Flexible Retrieval、Glacier Deep Archive — 加えて Express One Zone (特殊な低レイテンシ、単一 AZ)。
- **ライフサイクルポリシー** は、年齢に基づいてストレージクラス間の移行を自動化します — 一度定義すれば、S3 が永遠に扱います。
- **S3 Intelligent-Tiering** は、実際のアクセスパターンに基づいてオブジェクトを層の間で自動的に移動します — 128KB より大きいオブジェクトを持つ予測不能なワークロードに使います。それより小さいオブジェクトは監視も自動階層化もされず (監視料金も払わず) — Frequent Access 層にとどまります。
- **Glacier の取得** には、Flexible と Deep Archive の層では復元リクエストが必要です。取得に SLA のあるデータをアーカイブする前に、取得時間 (数分から12時間) を計画します。
- **不完全なマルチパートアップロード** は静かに積み重なり、ストレージ料金が発生します。すべてのバケットに、不完全なパーツを7日後に削除するライフサイクルルールを追加します。
- **3つのセキュリティ層**: バージョニング (取り消し可能な削除)、Object Lock (コンプライアンスのための不変性)、CloudTrail データイベント (フォレンジックと異常検出)。
- **クロスリージョンレプリケーション (CRR)**: 注文記録を DR リージョンに自動的にレプリケートします。両方のバケットでバージョニングが必要です。DR コピーがミラーかバックアップかに基づいて、削除マーカーがレプリケートされるかを設定します。
- **マルチパートアップロード** は5GB を超えるオブジェクトに必須で、100MB を超えるあらゆるものに推奨されます。
- **S3 Object Lock** はコンプライアンスシナリオのための WORM ストレージを提供します — Governance モードは管理者が上書きできます。Compliance モードは誰も上書きできません。

## 試験のヒント

*SAA-C03 ドメイン: コスト最適化アーキテクチャの設計 (ドメイン4、タスク4.1)*

- **ストレージクラス選択のシグナル**:
  - 「頻繁にアクセスされる」 → Standard
  - 「月に1回アクセス、即座の取得が必要」 → Standard-IA
  - 「数時間の取得時間を許容できる、めったにアクセスされない」 → Glacier Flexible Retrieval
  - 「規制コンプライアンス、7年以上の保存、決してアクセスされない」 → Glacier Deep Archive
  - 「不明、または変化するアクセスパターン」 → Intelligent-Tiering
- **ライフサイクルポリシーの試験パターン**: 「データの年齢とともにストレージコストを自動的に削減」「90日後にアーカイブに移行」 → ライフサイクルポリシー。
- **Intelligent-Tiering と小さなオブジェクト**: 128KB 未満のオブジェクトは監視されず、監視料金を払わず、決して自動階層化されません — Frequent Access にとどまります。ライフサイクルルールも、デフォルトでは128KB 未満のオブジェクトをスキップします (上書き可能)。試験はどちらの事実もテストし得ます。
- **CRR の要件**: ソースと宛先の両方のバケットでバージョニングが有効でなければなりません。ソースと宛先は異なるリージョンになければなりません。
- **S3 Object Lock**: 「WORM」「不変」「SEC 17a-4」「削除や変更ができない」 → Object Lock。Governance モード (管理者が上書きできる)。Compliance モード (root を含め誰も上書きできない)。
- **Glacier の復元**: Glacier のオブジェクトは即座に利用できません。アクセスするために、S3 Standard にコピーを「復元」しなければなりません。復元されたコピーは一時的です (期間を設定します)。元のものは Glacier に残ります。

## 練習問題

**練習問題1 — 想起**

S3 Standard-IA と S3 Glacier Instant Retrieval の違いを説明してください。どんなアクセスパターンがそれぞれを適切にしますか?

*(ヒント: どれだけ頻繁にデータにアクセスするか、そしてアクセスするときどれだけ速く必要かを考えてみてください。)*

**練習問題2 — SAA-C03 シナリオ**

*シナリオ*: ある会社は毎日500GB のアプリケーションログを生成します。ログは最初の7日間は (デバッグと監視のために) 頻繁にクエリされます。7日後、ログはめったにアクセスされませんが、必要なら30分以内に利用可能でなければなりません。1年後、ログはコンプライアンスのために保存されなければなりませんが、決してアクセスされません。会社はこれらの要件を満たしつつ、ストレージコストを最小化する必要があります。

これらの要件を最も満たす S3 ライフサイクルポリシーはどれですか?

A) 7日間 S3 Standard に保存。7日後に S3 Glacier Deep Archive に移行。365日後に期限切れ  
B) 7日間 S3 Standard に保存。7日後に S3 Standard-IA に移行。365日後に S3 Glacier Flexible Retrieval に移行  
C) すべてのログを1日目から S3 Intelligent-Tiering に保存  
D) 7日間 S3 Standard に保存。7日後に S3 Glacier Instant Retrieval に移行。365日後に S3 Glacier Deep Archive に移行

**ヒント1**: 「30分以内に利用可能」はどのストレージクラスを除外しますか?

**ヒント2**: Deep Archive は取得に12時間かかります — 7〜365日の30分要件を満たしません。

**ヒント3**: 365日後、取得時間は重要ではありません (決してアクセスされない) ので、最も安い選択肢が適用されます。

**解答**: D

**説明**: 7日間の S3 Standard が頻繁なアクセスを扱います。Glacier Instant Retrieval は7〜365日にミリ秒のアクセスを提供します — Standard-IA より大幅に低いコストで30分要件を満たします。365日後、Glacier Deep Archive が、決してアクセスされないデータに最も安い選択肢です。

**なぜ A ではないのか?** Glacier Deep Archive は取得に12時間かかります — 7〜365日の「30分の可用性」要件を満たしません。

**なぜ B ではないのか?** Standard-IA はここで最初の移行先にすらなれません: S3 は、ライフサイクルルールが Standard-IA や One Zone-IA に移行する前に、オブジェクトが Standard で30日経過することを要求します — だから「7日後に Standard-IA」は無効なルールです。(30日ルールは Glacier クラスには適用されません。だからこそ D が機能します。) そしてそれを脇に置いても、Glacier Instant Retrieval は7日目以降めったにアクセスされないデータに大幅に安いです。

**なぜ C ではないのか?** Intelligent-Tiering にはオブジェクトごとの監視料金があり、明示的なライフサイクルルールほど積極的にログをアーカイブ層に移動しないかもしれません。予測可能なアクセスパターンを持つ大量のログには、明示的なライフサイクルルールのほうが費用効率が高いです。

*SAA-C03 ドメイン: コスト最適化アーキテクチャの設計 — タスク4.1*

**練習問題3 — アーキテクチャチャレンジ** *(オプション)*

Nimbus には、異なる特性を持つ3種類の S3 データがあります:

- レストランの写真: 一度アップロードされ、顧客に何度もアクセスされ、決して削除されない
- 注文レシート: 最初の1か月は顧客にアクセスされ、税務目的で7年間保たれる
- アナリティクスのエクスポート: 毎日生成され、翌週に分析され、2年間保たれる

それぞれにライフサイクルポリシーを設計してください。レストランの写真に、Intelligent-Tiering は理にかないますか? 注文レシートでは、1か月から7年のウィンドウをどのストレージクラスがカバーしますか? アナリティクスのエクスポートでは、異なるプレフィックスに異なるポリシーを適用するためにバケットをどう構成しますか?

*(唯一の正解はありません。目標は、実世界のデータに対するストレージ層の選択を練習することです。)*
