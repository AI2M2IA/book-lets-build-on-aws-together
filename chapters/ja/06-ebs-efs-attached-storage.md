# 第6章：あなたについて回るディスク

Tomは赤ペンと、Leoを緊張させる習慣を持っていました。

毎週土曜の朝、彼はコーヒーを片手に座り、何かを印刷しました。メールではありません。レポートでもありません。彼はNimbusが動かしているものの一覧を印刷し、それを台帳のように、一行ずつ、ペンを手に読みました。彼は2週目からこれをしてきました。プリンターが温まる音が、週末の一部になっていました。

Leoはそれを「TomがやってLeoに何か悪いことをしたような気にさせるあれ」と呼びました。

その土曜日、Tomは何かに丸をつけ、一言もなくMayaのデスクに印刷物を置いていきました。

彼女は月曜の朝にそれを見つけました。1つの丸。余白に1つのメモ、3つの単語：

*すべて。1台のマシン。*

写真は今、安全にS3にありました——その問題は解決しました。しかしデータベースは依然としてウェブサーバーと同じEC2インスタンスにありました。注文履歴、顧客レコード、2カ月分の取引。アプリケーションとその下のすべてが、単一の仮想ディスクを共有していました。

「インスタンスがクラッシュしたら、データベースはどうなるの?」とMayaは、印刷物を手に尋ねました。

「それもクラッシュする」とLeoは言いました。

「で、データは?」

「データベースがどう保存しているかによる。」

その「による」が問題でした。

**EC2インスタンスがデータをどう保存するか**

EC2インスタンスが動くとき、そのオペレーティングシステムはディスクのどこかに存在します。そのディスクは**ルートボリューム**と呼ばれます。デフォルトでは、これは**EBSボリューム**です——あなたが意識していないときでも。

しかし別のものもあります。EC2インスタンスには**インスタンスストア**ストレージもあります。

インスタンスストアは、あなたの仮想マシンを動かす基盤ハードウェアに物理的にアタッチされた一時的なストレージです。それは極めて速い——AWSの他のほぼどのストレージオプションよりも速い。しかし落とし穴があります。

インスタンスストアは**一時的（エフェメラル）**です。

インスタンスが停止または終了すると、インスタンスストアのデータは消えます。永久に。回復不可能。AWSはこれについてあまり大きな声で警告しません。だからチームはそれを発見するのです。データを失うことで。

インスタンスストアは、キャッシュ、一時的な処理ファイル、スクラッチスペースに適しています。気にかけるデータには決して使いません。

**EBS：永続的なディスク**

EC2インスタンスに挿し込める外付けハードドライブ——抜いても消えず、必要なら別のマシンに移せるもの——を想像してください。AWSはこれを**EBS**：Elastic Block Storeと呼びます。

EBSはEC2インスタンスのための永続的なブロックストレージです。

ブロックストレージは、それが本物のハードドライブのように振る舞うことを意味します。あなたのオペレーティングシステムはその上にファイルシステムを作り、任意の位置で任意のバイトを読み書きし、その上でデータベースを動かし、それをアタッチされたディスクとまったく同じように扱えます。

重要な特性：

**永続的。** インスタンスストアとは違い、EBSボリュームはインスタンスの停止、開始、そしてインスタンスの終了さえ（構成による）生き延びます。インスタンスがそれを使っていないときでも、データはボリュームにとどまります。

ここに構成のニュアンスがあります。EC2インスタンスを作成するとき、ルートボリュームには「終了時に削除（Delete on Termination）」という設定があります。デフォルトでは、これはtrueに設定されています——インスタンスが終了されると、ルートボリュームは削除されます。アタッチする追加のデータボリュームには、デフォルトはfalseです——それらはインスタンスが終了された後も存続します。両方の設定を変更できます。ルートボリュームにインスタンスの終了を生き延びてほしいなら（フォレンジック分析やデータ復旧のため）、「終了時に削除」を無効にします。データボリュームを自動的に片付けてほしいなら、それを有効にします。

**アタッチ・デタッチ可能。** EBSボリュームは1つのインスタンスからデタッチして別のインスタンスにアタッチできます。データを移行したり、故障したインスタンスから復旧したりする必要があるなら、ボリュームをデタッチして別の場所に再アタッチできます。

デタッチ・再アタッチのワークフローは、スナップショットの復元より遅いですが、ボリュームの正確な状態——すべてのコミットされていない書き込み、すべてのキャッシュされたデータ、正確なファイルシステムの状態——を保ちます。これがそれを、フォレンジック分析（元のシステムをブートせずに分析用のインスタンスにボリュームをアタッチする）とデータ移行（スナップショットを取らずにデータベースのボリュームをより大きなインスタンスに移す）に役立つものにします。

**単一のアタッチメント（ほとんどの場合）。** デフォルトでは、EBSボリュームは一度に正確に1つのEC2インスタンスにアタッチされます。単一のインスタンスは複数のEBSボリュームを持てますが、単一のEBSボリュームは複数のインスタンスによって同時にマウントできません（1つの例外を除いて：EBS Multi-Attach。これは限定されたユースケースと重要な制限を持ちます）。

EBS Multi-Attachは、io1/io2（Provisioned IOPS）ボリュームを同じAZの複数のインスタンスに同時にアタッチすることを可能にします。これは「共有ストレージ」の問題を解決するように聞こえますが、深刻な制約を伴います。アタッチされたインスタンスのアプリケーションは、並行アクセスを調整できなければなりません——共有ファイルシステムのセマンティクス（ロック管理、書き込みの順序付け）はEBSによって提供されません。実際には、EBS Multi-Attachは、調整を自分自身で扱うクラスター化されたデータベースアプリケーションに使われます。一般的な共有ファイルアクセスには、EFSの方がシンプルで適切です。

EBSのアナロジー：1台のラップトップに挿された外付けハードドライブ。そのラップトップ（EC2インスタンス）はそれに読み書きできます。終わったら、それを抜いて別のラップトップに挿せます。

**EBSボリュームのタイプ**

すべてのEBSボリュームが同じではありません。AWSは、異なるパフォーマンスとコストのプロファイルを持ついくつかのタイプを提供しています。

**gp3（汎用SSD）**：ほとんどのワークロードのためのデフォルトの選択。パフォーマンスと価格の良いバランス。ブートボリューム、小さいデータベース、開発環境に適しています。

gp3がデフォルトになる前は、**gp2**がありました——そして実際の現場でまだそれに出会うでしょう。gp2ボリュームは、そのIOPSパフォーマンスをボリュームサイズに直接結びつけます。1ギガバイトあたり3 IOPS、最大1万6,000 IOPS（これは5,334GBのボリュームを要する）まで。スループットは250MB/sに制限されます。この結合は、gp2では、より多くのIOPSを得る唯一の方法がボリュームを大きくすることであることを意味します——余分なスペースが必要なくても。gp3はその依存関係を断ち切りました。それはサイズに関わらず3,000 IOPSと125MB/sから始まり、IOPSとスループットを独立して、より低いコストで構成させます。AWSは新しいボリュームにgp3を推奨しますが、多くの既存のワークロードがまだgp2で動いているので、両方を知る必要があります。

**io2（Provisioned IOPS SSD）**：I/O集約的なワークロードのための高性能なオプション。1秒あたり何回のI/O操作（IOPS）が必要かを指定し、AWSがそのパフォーマンスを保証します。大きな本番データベースに適しています。

**st1（スループット最適化HDD）**：大きな順次の読み書きに最適化された磁気ストレージ。SSDより低コストですが、ランダムI/Oには遅い。データウェアハウジングとログ処理に最適。

**sc1（コールドHDD）**：最も安いEBSオプション。低頻度でアクセスされるデータのため。時間に敏感なものには適していません。

「gp3と比べてio2はどれだけ高くつくんだ?」とTomは、ノートから顔を上げて尋ねました。

Leoは料金ページを開きました。io2はgp3よりGBあたりおよそ50〜60%高く、さらにプロビジョニングされたIOPSごとの別の料金がかかります——そして高パフォーマンスのボリュームでは、そのIOPSごとの料金が請求書を支配します。Tomはその差を記しました。「じゃあ、データベースが実際にパフォーマンスの保証を必要とするまでgp3を使う。」

試験はすべてのタイプの暗記を要求しません。それは、要件を正しいタイプに合わせる能力をテストします。IOPS要件 → io2。コストに敏感な順次ワークロード → st1。一般的なウェブアプリケーション → gp3。

**IOPS対スループット：なぜその区別が重要か**

Tomは翌火曜日、CloudWatchを確認した後、EBSボリュームの問題に戻ってきました。

「EBSのダッシュボードに2つのメトリクスが見える」と彼は言いました。「IOPSとスループット。それらは違うものか?」

そうです。

**IOPS**（Input/Output Operations Per Second）は、ディスクが1秒あたり何回の読み取りまたは書き込みの操作を処理できるかを測定します。各操作はたいてい小さい——4KBから256KB。高いIOPSは、多くの小さい、ランダムな読み書きをするデータベースにとって重要です。個々の行を取得する、レコードを更新する、並行クエリを処理する。

**スループット**（MB/sで測定）は、1秒あたりどれだけのデータが移動するかを測定します。高いスループットは、順次のワークロードにとって重要です。大きなログファイルを読む、ストリーミング分析、大きなデータセットの読み込み。

データベースはたいてい高いIOPSと低〜中程度のスループットを必要とします。大きなテーブルをスキャンするデータウェアハウスは高いスループットを必要とし、中程度のIOPSで生きられます。

TomはNimbusのデータベースのCloudWatchメトリクスを見ていました。IOPSはディナーラッシュ中にスパイクしていました——アプリケーションがメニューアイテムと注文データを取得するときの、短い、ランダムな読み取り。スループットは低かった。パターンは、より良いスループットではなく、より良いIOPSを必要とするデータベースのワークロードに合致しました。

「じゃあ、データベースが遅くなったら」とTomは言いました。「ボリュームをアップグレードする前に、それがIOPSバウンドかスループットバウンドかを確認する?」

「その通り」とPriyaは言いました。「gp3からio2へのアップグレードはコストをかけてIOPSを加える。問題がスループットなら、そのアップグレードは役立たない。まずメトリクスを確認して。」

これがまさに、間違った問題を解決する高価なストレージのアップグレードを避ける方法です。

**EBSスナップショット：バックアップ**

会社を定期的に救うものがあります。

**EBSスナップショット**は、EBSボリュームの特定時点のバックアップで、S3に保存されます（ただし、S3を通じて直接ではなく、EBSインターフェースを通じてアクセスします）。スナップショットは増分です。最初のスナップショットはフルのボリュームをキャプチャし、後続のスナップショットは前回から変わったものだけを保存します。

スナップショットから新しいEBSボリュームを作成できます——データベースの破損、不良なデプロイメント、誤った削除の前の時点に復元する。

スナップショットを自動化すべきです。AWSはこの目的のために**Amazon Data Lifecycle Manager**を提供しています。ポリシーを定義し（6時間ごとにスナップショットを取る、過去7日間を保持する）、それが自動的に実行されます。

Priyaはデータベースが本番に入る前からこれを設定していました。

Leoはそれを考えていませんでした。

「スナップショットのジョブが静かに失敗したら何が起きるか、考えたことある?」とPriyaは尋ねました。「ポリシーは実行されるけど、スナップショットが実際には有効じゃなかったら?」

彼らはその日の午後、復元のプロセスをテストしました。

Nimbusの本番データベースのためのPriyaの完全なスナップショットバックアップポリシー、彼女がそれを適切に文書化する時間ができたとき：

- **毎日のスナップショット**、7日間保持。これらは通常の復旧シナリオをカバーします。不良なデプロイメント、誤った削除、1週間以内に発見された破損のイベント。
- **毎週のスナップショット**（毎週日曜午前2時に取得）、30日間保持。これらは、問題が即座に検出されないシナリオをカバーします——数週間後にしか気づかれない微妙なデータ破損。
- `us-east-1`へのクロスリージョンのスナップショットコピー、週に1回、30日間保持。これらは、`us-west-2`リージョン全体が利用できず、Nimbusがどこか別の場所でデータベースを再構築する必要があるシナリオをカバーします。

「スナップショットが多すぎるように見える」とLeoは言いました。

「最初の後の各増分スナップショットは小さいの」とPriyaは言いました。「変わったものだけを保存している。総ストレージコストはささやかよ。」

Tomはすでに価格を調べていました。50GBのデータベースの毎日のスナップショットを7日間保持し、加えて30日間保持の毎週のスナップショット——月およそ3〜5ドル。それらを持たないコストは、データベースがいつか破損したら、計り知れないほど高いものでした。

「で、Fast Snapshot Restoreは?」とLeoは尋ねました。「設定を見ていたとき、あのオプションを見た。」

**Fast Snapshot Restore**（FSR）は、復元されたスナップショットを初めて使うときに通常起きるI/Oパフォーマンスのペナルティを排除するEBSの機能です。FSRなしでは、新しく復元されたEBSボリュームは、データがS3から遅延読み込みされる間、最初の数分または数時間、パフォーマンスが低い——読み取りが、まだボリュームに引き込まれていないデータをS3に当たります。特定のAZのスナップショットでFSRを有効にすると、復元されたボリュームは即座にフルパフォーマンスの準備ができています。

FSRは追加でコストがかかります——FSRが有効なスナップショットごと、AZごと、時間ごとに払います。Nimbusの災害復旧のスナップショットには、たまの使用が継続的なFSRのコストを正当化しませんでした。緊急時に数分以内に復元されて稼働可能になる必要のある本番データベースのスナップショットには、FSRは価値がありました。

「災害復旧のために実際に使う毎週のスナップショットでFSRを有効にして」とPriyaは言いました。「保持期間内のすべての毎日のスナップショットでそれを有効にしないで。」

Tomはコスト計算をスプレッドシートに追加しました。

**災害復旧のためのクロスリージョンスナップショットコピー**

EBSスナップショットは、それらが作成されたリージョンに存在します。`us-west-2`リージョン全体がダウンすれば、`us-west-2`のスナップショットはアクセス不可能です。

解決策：**クロスリージョンスナップショットコピー**。EBSスナップショットを別のリージョンにコピーでき、プライマリのリージョンが利用できなくても使えるバックアップを与えてくれます。

AWS Data Lifecycle Managerは、スナップショットポリシーの一部として自動化されたクロスリージョンコピーをサポートします。`us-west-2`で毎日のスナップショットを取り、週に1回それを自動的に`us-east-1`にコピーする。災害が起きたら、`us-east-1`で新しいEC2インスタンスを起動し、クロスリージョンのスナップショットから復元し、DNSエンドポイントを更新し、運用を続けます。

「これがデータベースのための私たちの災害復旧計画よ」とPriyaは、ポリシーの文書をチームに提示しながら言いました。「完全なマルチリージョンのアーキテクチャじゃない——それは今必要な以上の複雑さよ。でも`us-west-2`が完全にダウンしたら、2時間以内に`us-east-1`で復元できる。」

「2時間のダウンタイム」とTomは言いました。

「無限のダウンタイムと比べてね」とPriyaは言いました。

Tomはその区別を認めました。

**EBSの暗号化：その場で暗号化できない理由の物語**

Nimbusの本番データベースは6週間動いていたとき、Priyaがあることを指摘しました。

「EBSボリュームが暗号化されていない」と彼女は言いました。

「暗号化できる?」とLeoは尋ねました。

「ええ。でもその場ではできない。」

EBSの暗号化についてのことはこうです。既存の暗号化されていないEBSボリュームを直接暗号化することはできません。データはすでにプレーンテキストで書き込まれています。それを暗号化するには、以下をしなければなりません：

1. 暗号化されていないボリュームのスナップショットを作成する
2. スナップショットをコピーし、コピーで暗号化を有効にする
3. 暗号化されたスナップショットから新しい暗号化されたEBSボリュームを作成する
4. インスタンスを停止する
5. 古い暗号化されていないボリュームをデタッチする
6. 新しい暗号化されたボリュームをアタッチする
7. インスタンスを開始し、すべてが機能することを検証する

このプロセスにはダウンタイムの窓があります——停止、デタッチ、アタッチ、開始のシーケンス。Nimbusでは、小さいデータベースだったので、窓は約15分でした。数百GBの大きな本番データベースには、スナップショットとコピーのプロセスはより長くかかりえますが、実際のインスタンスのダウンタイムは依然として停止/開始のサイクルだけです。

「なぜスイッチを切り替えるだけじゃダメなの?」とLeoは尋ねました。

「ディスク上の既存のデータが暗号化されていないバイトだからよ」とPriyaは言いました。「AWSは、すべてのブロックを読んで書き直すことなくそれらを再暗号化できない——それがまさにスナップショットコピーのプロセスがすることよ。ソースのスナップショットからすべてのブロックを読み、それぞれを暗号化し、新しいスナップショットに書き込む。」

Leoはプロセスを順を追って進めました。新しい暗号化されたボリュームがアタッチされました。インスタンスはオンラインに戻りました。データベースは暗号化されたボリュームで動いていました。

「新しいEBSボリュームはデフォルトで暗号化されて作成できる」とPriyaは言いました。「アカウントレベルの設定がある。すべての新しいボリュームが自動的に暗号化される。初日にこれを有効にすべきだった。」

彼女はそれを有効にしました。その時点から、NimbusのAWSアカウントで作成されたすべてのEBSボリュームがデフォルトで暗号化されました——追加のステップは不要です。

**EFS：共有のファイリングキャビネット**

EBSは1つのインスタンスにアタッチされたディスクです。複数のインスタンスが同じファイルに同時にアクセスする必要があるなら?

必要なのは、オフィスの中央にあるファイリングキャビネットのようなものです——誰でも歩み寄り、ファイルを取り出し、戻し、次の人が即座に変更を見られる。複数の人が、同時に、同じストレージにアクセスする。

AWSはこれを**EFS**：Elastic File Systemと呼びます。

EFSはマネージドのネットワークファイルシステムです。複数のEC2インスタンスが同じEFSファイルシステムを同時にマウントし、共有ファイルに読み書きできます。これがEBSが提供しない重要な能力です。

はっきり言うと：

EBSは1台のラップトップに挿された外付けハードドライブです。一度にそのラップトップだけがそれを使えます。

EFSはオフィスの中央にあるファイリングキャビネットです。どのチームメンバーも歩み寄り、引き出しを開け、ファイルを読み、何かを戻せます。

**EFSはいつ必要か?**

- 複数のEC2インスタンスがファイルを共有する必要があるとき——コンテンツ管理システム、共有
  構成ファイル、共有メディアライブラリ
- すべてのインスタンスが同じデータにアクセスする必要のある水平にスケールされたアプリケーションが
  あるとき
- インスタンスの障害を生き延びる永続的なファイルシステムが必要なとき

EFSはNFSプロトコル（具体的にはNFSv4）を使ってネットワーク経由でアクセスされます。EFSマウントターゲットへのネットワーク接続を持つどのEC2インスタンスもそれをマウントできます——同じリージョン内の異なるAZのインスタンスを含めて。各AZにマウントターゲットを構成し、インスタンスは最適なパフォーマンスのために最も近いマウントターゲットに接続します。

実際的な含意：EFSは箱から出してすぐにAZをまたいで機能します。`us-west-2a`と`us-west-2b`にウェブサーバーがあり、両方が同じEFSファイルシステムをマウントしているなら、`2a`のサーバーによって書き込まれたファイルは`2b`のサーバーに即座に見えます。これがEBSが提供できない共有ファイルシステムの振る舞いです。

**EFSのパフォーマンスモード**

EFSにはサイジングにとって重要な2つのスループットモードがあります：

**Elastic Throughput**（ほとんどの新しいファイルシステムのデフォルト）：EFSは実際の使用に基づいてスループットを自動的にスケールアップ・ダウンします。スループットレベルをプロビジョニングしません。使った分だけ払います。これは、Nimbusのように——月曜の朝のトラフィックが金曜の夕方と違う——スループットのニーズが変動する変動するワークロードに正しいモードです。

**Provisioned Throughput**：保存されたデータに関わらず、スループットレベルを指定します。ワークロードが、Elasticモードで保存されたデータの量が提供するものを超える、一貫して高いスループットを必要とするときに役立ちます。どれだけ保存されているかに関わらず1分あたり数十ギガバイトを読むビルドシステムを動かしているなら、Provisioned Throughputが適切です。

3つ目のモード、**Bursting Throughput**もあります。これは元のEFSの振る舞いで、Elasticが利用可能になる前に作成されたファイルシステムには今もデフォルトです。Burstingモードでは、スループットはどれだけのデータを保存するかに応じてスケールします。1GBあたり50KB/sのベースラインに、ベースラインを下回るときに蓄積され、より高いスループットが必要なときに使えるバーストクレジット（小さいファイルシステムには最大100MB/s、より大きいものにはベースラインの倍数まで）を加えたものを得ます。それは、ファイルシステムが意味のあるバーストクレジットを稼ぐのに十分大きい、予測不可能またはスパイク状のアクセスパターンを持つワークロードに正しい選択です。ファイルシステムが小さくアクセスパターンがスパイク状なら、クレジットを素早く使い果たせます——どこにいるかを知るために`BurstCreditBalance`のCloudWatchメトリクスを見ましょう。

Tomの質問は即座でした。「Elasticの方が高い?」

「使用パターンによる」とLeoは言いました。「Elasticでは、実際に消費したスループットに払う。Provisionedでは、使っていなくても指定したスループットに払う。」

「じゃあ変動するワークロードには、たいていElasticの方が安い」とTomは言いました。

「たいていはね」とPriyaは言いました。「決める前に、CloudWatchで実際のスループットのパターンを確認して。」

EFSには2つのパフォーマンスモードもあります。**General Purpose**（低レイテンシ、ほとんどのワークロードに適している、デフォルト）と**Max I/O**（わずかに高いレイテンシを代償に、高度に並列化されたワークロードのためのより高いスループット）。General Purposeは大多数のユースケースを扱います。Max I/Oは、何千もの同時のファイルシステム操作をする必要のあるアプリケーションのために設計されました——大規模なメディア処理パイプライン、多くの並列リーダーを持つ科学計算のワークフロー。

**EFS対S3：** EFSはファイルシステム（フォルダ、ファイル、権限、ロック）です。S3はオブジェクトストレージ（アップロード、ダウンロード、ファイルシステムのセマンティクスなし）です。EFSはS3よりはるかに高価です——EFS Standardで1GBあたり月およそ0.30ドル対、S3 Standardで1GBあたり月0.023ドル。丸ごと保存・取得されるファイルにはS3を使います。アプリケーションが標準的なファイルシステムの操作を通じて積極的に読み書きするファイルにはEFSを使います。

**EBSなら1つのインスタンス、でもEFSなら多数**

EBS/EFSの決定は1つの質問に帰着します。いくつのインスタンスがこのストレージに同時にアクセスする必要があるか?

EBSで水平にスケールされたアプリケーションを構築するなら、各インスタンスは自分自身のディスクを持ちます——しかしユーザーがインスタンスAにファイルをアップロードすると、インスタンスBはそれを見られません。それはデータベースには問題ありません（各DBが自分自身のディスクを持つ）が、共有コンテンツには壊れています。共有アクセスが必要なら、EFSが答えです——しかしEFSはS3よりGBあたりコストがかかり、ランダムI/OについてEBSより高いレイテンシを持ちます。正しい選択は、アプリケーションがデータで何をするかに完全に依存します。

**正しいストレージを選ぶ**

これまでにAWSで3種類のストレージを見てきました。決定を明快にしましょう。

| ニーズ | ストレージタイプ |
|---------------------------------------|------------------|
| データベースが永続的で速いディスクを必要とする | EBS（gp3またはio2） |
| 複数のサーバーが共有ファイルを必要とする | EFS |
| ファイル、バックアップ、画像、大きなオブジェクト | S3 |
| 一時的な計算のスクラッチスペース | インスタンスストア |
| 最小のコストでの長期アーカイブ | S3 Glacier |

こう思っているかもしれません。EFSが複数のインスタンスにファイルを共有させるなら、なぜすべてにそれを使わないのか? なぜなら、EFSはS3よりGBあたり大幅にコストがかかり、ランダムI/OについてローカルなEBSより高いレイテンシを持つからです。それは共有ファイルシステムのアクセスのための正しいツールです——一般的なファイルストレージやデータベースストレージのためではありません。

この決定を正しく得ることは重要です。EFSが必要なところでS3を使うと、運用上の複雑さが加わります。EFSが必要なところでEBSを使うと、スケールするときに障害を引き起こします。永続性が必要なところでインスタンスストアを使うと、データを失います。

Priyaはこの表を印刷して壁に貼りました。

「ストレージの要件を追加するたびに」と彼女は言いました。「私たちはここから始める。」

決定を具体的にするために、いくつかの実際のシナリオを順を追って見てみましょう：

**シナリオA**：機械学習のトレーニングジョブがGPU EC2インスタンスで動き、200GBのデータセットを読む必要があります。ジョブは1日1回動き、2時間かかります。データセットは複数の研究チームによって共有されます。

決定：S3。データセットは大きく、ジョブごとに1回読まれ、共有されます。S3は安く、耐久性があり、どのEC2インスタンスやどのチームのアカウントからもアクセス可能です。GPUインスタンスはそれをS3 API経由で読みます。ここにファイルシステムは必要ありません。

**シナリオB**：WordPressサイトがロードバランサーの後ろの4つのEC2インスタンスで動いています。WordPressはプラグインファイル、テーマファイル、ユーザーのアップロードをサーバーのディレクトリに保存します。4つすべてのインスタンスが同じファイルを読み書きする必要があります。

決定：EFS。WordPressはファイルシステムのセマンティクスを使います——それはディレクトリを作り、ファイルを書き、パスでファイルを読みます。S3はWordPressプラグインのエコシステムを書き直すことを要求します。EFSは標準的なNFSファイルシステムとしてマウントされ、WordPressはそれとネイティブに連携します。

**シナリオC**：PostgreSQLデータベースがEC2インスタンスで動いています。クエリの実行とインデックスのルックアップのために速いランダムI/Oを必要とします。

決定：EBS（gp3またはio2）。データベースは、小さい、ランダムな読み書きのために低レイテンシのブロックストレージを必要とします。S3は遅すぎ、ファイルシステムのセマンティクスをサポートしません。EFSはランダムI/OについてEBSより高いレイテンシを持ちます。

パターン：ファイルのデフォルトはS3です。特定のインスタンスのためにブロックストレージが必要なときにEBSを加えます。複数のインスタンスがファイルシステムを共有する必要があるときにEFSを加えます。一時的なスクラッチスペースのためだけにインスタンスストアを。

## EFSで足りないとき：Amazon FSx

次のストレージの教訓は、障害やホワイトボードの議論として届きませんでした。それは販売契約として届きました——Mayaがポータルのローンチ以来追いかけてきた類いの、デモとフォローアップの電話に丸々四半期かかって成約する類いのもの。レストラン運営者向けのポータルがローンチしてから3カ月後、Nimbusは最初の複数拠点のクライアントと契約しました。Copper Kettle、中西部にまたがる十数の拠点を持つ家族経営のグループです。Mayaがその取引を進めました。Tomが財務モデルを構築しました。Leoはインクが乾く前から技術的な統合の計画を始めていました。

それから彼はCopper KettleのITチームからのインフラのメモを読みました。

「彼らのファイルサーバーはWindowsだ」と彼は言いました。「すべてがWindows。彼らのキッチン管理ソフトウェア、彼らのHRシステム、彼らのスケジューリングツール——すべてがWindowsファイルサーバーの共有ドライブに書き込む。SMBプロトコル。Active Directory認証。」

「彼らをEFSに持ち上げられる?」とMayaは尋ねました。

Leoは首を振りました。「EFSはNFSを使う。彼らのアプリケーションはSMBを話す。それらは異なるプロトコルだ。Copper KettleのソフトウェアはNFSが何か知らない。EFSマウントにそれを向けるだけ、ってわけにはいかない。」

「じゃあEFSは使えない。」

「これには無理だ。別のサービスがある。」

**FSx for Windows File Server：EFS、でもWindows向け**

**Amazon FSx for Windows File Server**は、完全マネージド型の、Windowsネイティブな共有ファイルシステムです。それはSMB（Server Message Block）プロトコル——Windowsサーバー、Windowsアプリケーション、オンプレミスのWindowsファイル共有が何十年も使ってきたのと同じプロトコル——をサポートします。それはActive Directoryと統合し、Windows ACL（ファイルレベルの権限）をサポートし、Windowsアプリケーションが実際に依存するWindows固有の機能をサポートします。

それをEFSのように、でもWindows向けに考えてください——あなたのActive Directory環境がすでに期待するすべてのWindows固有の機能とともに。Copper Kettleのキッチン管理ソフトウェアは、オンプレミスのファイルサーバーに接続していたのとまったく同じようにそれに接続するでしょう。アプリケーションは変わりません。プロトコルは変わりません。データはただ、シカゴのどこかの地下室のサーバーの代わりに、マネージドのAWSサービスに存在します。

Copper Kettleの移行のために：LeoはFSx for Windows File Serverのファイルシステムをプロビジョニングし、それをCopper KettleのActive Directory（AWS Managed Microsoft ADを通じてAWSに拡張）に接続し、既存のドライブレターをマッピングしました。キッチンソフトウェアは、期待したとおりの場所にファイル共有を見つけました。

「それは月いくらかかるんだ?」とTomは尋ねました。

Leoはすでに調べていました。FSx for WindowsはストレージのGBあたり月で価格付けされます——EFSより高価で、S3よりかなり高い、しかし十数の拠点にまたがってWindowsファイルサーバーを維持するよりはるかに安い。Tomは反対せずに数字を書き留めました。

**FSx for Lustre：MLジョブが数百のGPUに供給する必要があるとき**

その間、Leoは脇で推薦エンジンのプロトタイプを作り始めていました——過去の振る舞いと、似た顧客が注文したものに基づいて、顧客がどの料理を注文しそうかを予測する。トレーニングデータはまだ小さかったのですが、その実験は彼を、まじめなMLチームがどうやってモデルに供給するかの落とし穴へと送り込みました。実行のたびにS3から数百ギガバイトを読むトレーニングジョブです。

「ケーススタディで繰り返し出てくるパターンは」と彼は次のチームランチで報告しました。「I/Oでボトルネックになるトレーニングジョブだ。高価なGPUが40%の時間アイドルで座って、次のデータのバッチを待っている。」

これは共有ファイルストレージとは別の問題です。それはハイパフォーマンスコンピューティング（HPC）の問題です。すべてが同じデータセットから、非常に高いスループットで、同時にデータを読む必要のある数百の処理ユニットがあるとき。

**Amazon FSx for Lustre**は、Lustre並列ファイルシステムの完全マネージド型の実装です。Lustreはまさにこのシナリオのために特別に作られています——多くの同時のクライアントにまたがる、極めて高いスループットでの並列読み取り。それはS3とネイティブに統合します。FSx for LustreをS3バケットに向けると、それが自動的にそのデータをLustreファイルシステムを通じて利用可能にします。トレーニングジョブはローカルのマウントポイントから読み、FSxが舞台裏でS3からデータをストリーミングします。

MLトレーニングジョブが数百のGPUに同時にデータを供給する必要があるとき、FSx for Lustreがそのツールです。同じことが金融モデリング、ゲノミクスのワークロード、動画レンダリングにも当てはまります——ボトルネックがストレージ容量ではなく並列I/Oのスループットであるあらゆるワークロードに。

Leoがブックマークしたケーススタディは、その物語を2つの数字で語りました。トレーニングジョブをFSx for Lustreに移行した後、GPU稼働率は60%から94%に上がり、6時間かかっていたトレーニングの実行が3時間半で完了しました。Nimbusはその種の馬力を長い間必要としないでしょう——しかしLeoは、推薦エンジンが成長した日のためにそのパターンをしまっておきました。

**その他のFSxオプション**

AWSは**FSx for NetApp ONTAP**——すでにオンプレミスでNetAppストレージを動かしていて、マルチプロトコルアクセス（同じファイルシステムからのNFS、SMB、iSCSI）が欲しい企業のため——と**FSx for OpenZFS**——スナップショットやクローンのようなZFS固有の機能をファイルシステムレベルで必要とするワークロードのため——も提供しています。両方とも、特定の既存のインフラや要件を持つ組織のための専門的なツールです。

ほとんどのチームにとって、決定は4つのFSxのバリアントとEFSの間です。問題は常に同じです。ワークロードはどのプロトコルを話し、どんなパフォーマンス特性を必要とするか?

> **試験のヒント — Amazon FSx**
>
> *SAA-C03ドメイン：高性能なアーキテクチャの設計（ドメイン3、タスク3.1）*
>
> - **FSx for Windows = SMB + Active Directory + Windowsワークロード**。試験のシグナル：「Windowsファイルサーバー」「SMBプロトコル」「Active Directory統合」「Windowsアプリケーションのリフト&シフト」。それらのフレーズのいずれかを見たら、FSx for Windowsが答えです。
> - **FSx for Lustre = HPC + MLトレーニング + 並列I/O + S3統合**。試験のシグナル：「機械学習トレーニング」「ハイパフォーマンスコンピューティング」「HPC」「並列ファイルシステム」「I/O集約的なワークロード」「GPUクラスター」「ファイルシステムをS3と統合する」。それらのフレーズを見たら、FSx for Lustreが答えです。

> - クイックリファレンス：「SMBまたはWindowsファイルサーバー」 → FSx for Windows。「機械学習トレーニングまたはハイパフォーマンスコンピューティング」 → FSx for Lustre。「NetApp/マルチプロトコル」 → FSx for ONTAP。「ZFS」 → FSx for OpenZFS。

## クラウドへの架け橋：AWS Storage Gateway

Nimbusのこれまでで最大の見込み客——Meridian Kitchenという、3つの州にまたがる20の拠点を持つ地域チェーン——は、`aws s3 cp`では解決できない問題を伴ってやって来ました。

Meridianは、オンプレミスのファイルサーバーに存在する何年もの運用データを持っていました。レシピ、請求書、キッチンの動画映像、サプライヤーの契約。数ギガバイトではありません。テラバイトです。そしてこのデータを生成・消費するソフトウェア——彼らのキッチン管理システム、彼らの請求プラットフォーム、彼らのHRツール——そのすべてが、NFSまたはSMBを使ってローカルのファイル共有に書き込んでいました。それらのアプリケーションを書き直すのは現実的ではありませんでした。すべてのデータを一晩で移すのも現実的ではありませんでした。

「じゃあ、どうやって彼らのデータをAWSに入れ始めるの」とMayaは尋ねました。「彼らに1つのアプリケーションも変えるよう求めずに?」

「まさにこのためのサービスがあるわ」とPriyaは言いました。「彼らのデータセンターでVMとして動き、彼らの既存のソフトウェアには通常のファイルサーバーかストレージデバイスのように見え、舞台裏で静かにすべてをAWSに保存する。」

そのサービスが**AWS Storage Gateway**です。オンプレミスの環境をAWSのストレージに接続するハイブリッドストレージサービス。それは、あなたのアプリケーションがすでに理解しているプロトコルを使ってストレージを提示しつつ、実際にはデータをS3、S3 Glacier、またはEBSスナップショットとして永続化します。

3つのゲートウェイのタイプがあり、それぞれが異なるオンプレミスの問題を解決します。

**File Gateway**は、オンプレミスのアプリケーションにNFSまたはSMBインターフェースを提示します。ゲートウェイに書き込まれたファイルはS3のオブジェクトとして保存されます——しかしアプリケーションはそれを知りません。それはファイルシステムを見ます。頻繁にアクセスされるファイルは低レイテンシの読み取りのためにローカルにキャッシュされ、残りはS3に存在します。これがMeridianが必要としたものです。キッチン管理ソフトウェアはファイル共有のように見えるものに書き込み、データはNimbusがそれを分析し、バックアップし、検索できるS3に行き着きます。

「待って——でも*なぜ*そういうやり方でやるの?」とMayaは尋ねました。「なぜソフトウェアをS3に直接向けないの?」

なぜなら、NFSとSMBはS3ではないからです。キッチンソフトウェアはS3のAPIを話しません。それはファイルパスを開きます。それはディレクトリにバイトを書きます。File Gatewayは、アプリケーションが何かが変わったことを知ることなく、それをS3のオブジェクトの操作に翻訳します。

**Volume Gateway**は、オンプレミスのサーバーにiSCSIブロックストレージボリューム——物理的なハードドライブやSANデバイスが提示するのと同じインターフェース——を提示します。2つのモードがあります。*stored volumes*はプライマリのデータをオンプレミスに保持し、EBSスナップショットとしてS3に非同期のバックアップをします（クラウドバックアップも欲しいオンプレミスファーストのワークロードのため）。*cached volumes*はプライマリのデータをS3に保持し、頻繁にアクセスされるデータをオンプレミスにキャッシュします（S3をプライマリストレージとして扱う準備ができている組織のため）。

**Tape Gateway**は、Veeam、Veritas、NetBackupのようなバックアップソフトウェアに仮想テープライブラリ（VTL）を提示します。バックアップソフトウェアは物理的なテープカートリッジのように見えるものに書き込みます。それらの仮想テープはS3に保存され、S3 Glacierにアーカイブできます。バックアップソフトウェアは変わりません。物理的なテープロボットと棚はなくなります。

「MeridianのバックアップチームはVeeamを動かしている」とLeoは言いました。「彼らには実際の物理テープがある。オフサイトのストレージ、ローテーションのスケジュール、全部。」

「Tape Gatewayが物理テープを置き換えるわ」とPriyaは言いました。「同じVeeamの構成。同じバックアップジョブ。テープがラックの代わりにS3に存在するだけ。」

## 強みと限界

**EBSの強み**：

- EC2のための永続的で速いブロックストレージ
- 特定時点のバックアップと復旧のためのスナップショット
- 異なるワークロードのための複数のパフォーマンス階層
- 保存時の暗号化をネイティブにサポート——アカウントレベルの暗号化をデフォルトで有効にしましょう

**EBSの限界**：

- 一度に1つのインスタンスにアタッチされる（小さな例外を伴って）
- EC2インスタンスと同じAZにある（別のAZへのコピーはスナップショットを要する）
- 使った分だけでなく、プロビジョニングされたストレージに払う
- 既存の暗号化されていないボリュームを暗号化するには、メンテナンスの窓を伴うスナップショット-コピー-復元のサイクルを要する

**EFSの強み**：

- マルチインスタンスの共有ファイルシステム——ネイティブなNFSプロトコル
- 自動的にスケールし、容量をプロビジョニングしない
- リージョン内のAZをまたいでアクセス可能
- Elastic Throughputモードがワークロードに自動的に調整する

**EFSの限界**：

- GBあたりS3より高価
- ランダムI/OについてEBSより高いレイテンシ
- すべてのリージョンで利用できるわけではない

## データを一括で移す：DataSyncとSnowファミリー

Storage Gatewayはオンプレミスのアプリケーションをクラウドストレージに*継続的に接続*し続けます。しかし、他の2つの移行のシナリオが試験に絶えず現れます——そして最終的には実際のプロジェクトにも：

**AWS DataSync**は*オンラインの一括転送*のためのものです。オンプレミスのNFS/SMBファイルサーバー（または他のクラウド）とS3、EFS、FSxの間で大きなデータセットをネットワーク経由で移す——1回、またはスケジュールで。それは並列化、整合性の検証、再試行、帯域幅の調整を扱い、手作りのrsyncスタイルのスクリプトよりおよそ10倍速い。試験のトリガー：「オンプレミスのNFSサーバーからAmazon EFS/S3に何百万ものファイルを移行/転送する」 → DataSync。（それを*継続的なハイブリッドアクセス*のためのStorage Gatewayや、*データベース*を移行するDMSと混同しないでください。）

**AWS Snowファミリー**は、ネットワークがボトルネックであるときのためのものです。100 Mbpsの回線で100 TBを移すには3カ月以上かかります。トラックの方が速い。**Snowball Edge**はAWSがあなたに発送する頑丈なアプライアンスです——最大約80 TBをローカルに積み込み、送り返すと、AWSがそれをS3にインポートします。**Snowcone**はエッジロケーションのための小さな携帯版（約8〜14 TB）でした——2024年後半に廃止されましたが、古い試験問題にはまだ現れるかもしれません（第25章の現実チェックを参照）。試験の計算のトリガー：問題文がデータセットのサイズと細いまたは信頼できない回線を与え、最速の/最も実際的な移行を尋ねるとき、転送時間を計算してください——それが数週間または数カ月なら、答えはSnowファミリーです。

> **試験のヒント — AWS Backup**
>
> 本章をつなぎ合わせるもう一つのサービス：**AWS Backup**は、単一のバックアッププランでEBS、EFS、RDS、DynamoDB、FSx、Storage Gatewayにまたがってバックアップを一元化・自動化します——スケジュール、保持、リージョン間とアカウント間のコピー、そして不変性のためのBackup Vault Lock。試験のトリガー：「複数のAWSサービス/アカウントにまたがってバックアップを一元管理する」 → サービスごとのスクリプトではなく、AWS Backup。


## まとめ

Tomの赤ペンは本当の問題に丸をつけました。1台のマシンに多すぎる。ストレージをEC2インスタンスから移すことは、単に容量についてではありません——それは、各層が独立して管理され、スケールされ、保護されうるように関心事を分離することについてです。正しいストレージの選択は、4つの質問に依存します。何がストレージを必要とするか、いくつのものが一度にそれを必要とするか、それはどれくらい長く存在するか、そしてそれはどうアクセスされるか? それらの4つの質問が一貫して正しい答えに導きます。

- **EBS**（Elastic Block Store）は単一のEC2インスタンスのための永続的なブロックストレージです。インスタンスの停止を生き延び、バックアップのためにスナップショットを取れます。一般的なワークロードにはgp3を、高IOPS要件にはio2を使いましょう。インスタンスストアは一時的で速いですが、インスタンスが終了すると失われます。
- **EFS**（Elastic File System）は、複数のインスタンスが同時にマウントできる共有のネットワークファイルシステムです。EFSはリージョン内のAZにまたがります。EBSは単一のAZに制約されます。
- ストレージタイプを要件に合わせましょう。単一のEC2データベース → EBS。サーバー間の共有ファイル → EFS。オブジェクト、メディア、バックアップ → S3。アーカイブ → S3 Glacier。
- 既存のEBSボリュームの暗号化には：スナップショット → 暗号化されたコピー → 新しいボリューム → 交換、が必要です。新しいボリュームでこれを避けるため、アカウントレベルの暗号化をデフォルトで有効にしましょう。
- **EBSの「終了時に削除」**：ルートボリュームはインスタンスの終了時に削除されるのがデフォルト。データボリュームは存続するのがデフォルト。インスタンスのライフサイクルポリシーを設計するとき、両方の設定を見直しましょう。

## 試験のヒント

*SAA-C03ドメイン3——タスク3.1（ストレージソリューション）*

- **EBSボリュームは1つのAZに存在します。** それらは同じAZのインスタンスにのみ
  アタッチできます。別のAZでEBSボリュームを使うには、スナップショットを作成し、
  ターゲットのAZでそれを復元します。
- **EBSスナップショットは増分で、S3に保存されます。** 最初のスナップショットはフル。
  後続のものは変更だけを保存します。災害復旧のためにスナップショットを他のリージョンに
  コピーできます。
- **EFSはクロスAZです。** 同じリージョン内の異なるAZの複数のインスタンスが
  同じEFSファイルシステムをマウントできます。これがEBSとの重要な差別化要因です。
- **試験のシナリオが「共有コンテンツを持つウェブアプリケーション」または「同じファイルに
  アクセスする複数のインスタンス」と言うなら、EFSを考えてください。** 「データベースストレージ」
  または「1つのサーバーのための永続的なディスク」と言うなら、EBSを考えてください。
- **インスタンスストアのデータは再起動を生き延びますが、停止や終了は生き延びません。** 質問が
  「インスタンスが停止された後に消える」データを描写するかもしれません——それはインスタンス
  ストアが関わっています。
- **gp3対io2**：gp3は一般的な使用のためのデフォルト。io2は、保証された
  IOPS（大きなデータベース、ミッションクリティカルなシステム）を必要とするワークロードのため。「IOPS要件」
  または「一貫した低レイテンシのデータベースパフォーマンス」を描写する試験のシナリオは
  io2を指し示します。
- **gp2対gp3：** gp2のIOPSはサイズに結合（3 IOPS/GB、5,334GBで最大1万6,000 IOPS）。gp3のIOPSはサイズと独立（3,000のベース、2025年9月から最大8万まで構成可能——古い資料、おそらく試験の問題バンクも、まだ以前の1万6,000の上限を前提としている）。試験問題のパターン：ワークロードがストレージを増やさずにより多くのIOPSを必要とする——答えはgp2ではなくgp3またはio2。
- **EBSの保存時の暗号化**：既存の暗号化されていないボリュームをその場で
  暗号化することはできません——スナップショットを取り、暗号化してコピーし、復元しなければなりません。誤って暗号化されていないボリュームを作成するのを避けるため、アカウントレベルの暗号化のデフォルトを
  有効にしましょう。暗号化はKMSキーを使ったAES-256です。
- **Fast Snapshot Restore**は、新しく復元されたボリュームのパフォーマンスのペナルティを
  排除しますが、スナップショットごと、AZごとにお金がかかります。ボリュームを
  「即座にフルパフォーマンスで」復元することについての試験問題はFSRを指します。
- **EFSのパフォーマンスモード**：General Purpose（低レイテンシ、ほとんどのワークロードに適している）
  対Max I/O（高度に並列化されたワークロードのためのより高いスループット）。
- **EFSのスループットモード——3つのオプション：** Bursting（スループットがストレージサイズに応じてスケール、バーストクレジットを使う——スパイク状のワークロードに最適）、Elastic（自動スケール、従量課金——予測不可能なワークロードに最適）、Provisioned（ストレージに関わらず固定のスループット——一貫した高スループットのニーズに最適）。試験は、スループットをプロビジョニングするか、弾力的にスケールさせるか、バーストクレジットに頼るかをいつ知っているかをテストします。
- **クロスリージョンスナップショットコピー**：EBSスナップショットは災害復旧のために他のリージョンに
  コピーできます。コピーされたスナップショットは独立しており、復元中にデータ転送
  コストを加えません——コピーの操作自体の間だけです。
- **Storage Gatewayのタイプ：** File Gateway = NFS/SMB → S3（ファイルがオブジェクトになる）。Volume Gateway = iSCSIブロックストレージ → S3スナップショット（stored：プライマリはオンプレミス。cached：プライマリはS3）。Tape Gateway = VTL → S3/Glacier（物理テープを置き換える）。試験のトリガー：「オンプレミスのアプリがコードの変更なしにクラウドストレージを必要とする」 → Storage Gateway。「テープバックアップを置き換える」 → Tape Gateway。

## 演習

**演習1——想起**

自分の言葉で：EBSとEFSの違いは何ですか? どちらをいつ
選びますか?

*（ヒント：1つのインスタンスか複数のインスタンスが、ストレージに同時にアクセスする
必要があるかどうかを考えてみましょう。）*

**演習2——SAA-C03シナリオ**

*シナリオ*：ある会社が、ロードバランサーの後ろの4つのEC2インスタンスにまたがって
ウェブアプリケーションを動かしています。ユーザーはプロフィール写真をアップロードできます。どの写真も、どのインスタンスが
それを処理したかに関わらず、アップロード後すぐにユーザーが見られなければなりません。写真は
HTTP経由でブラウザに配信され、その場で変更されることは決してなく、チームは
最も運用上のオーバーヘッドが少ない、最もコスト効率の良い、スケーラブルな解決策を望んでいます。

どのストレージの解決策が彼らの要件を最もよく満たしますか?

A) 各EC2インスタンスにEBS gp3ボリュームをアタッチし、cronジョブを使って
   それらの間でファイルを同期する  
B) 写真をEC2インスタンスのインスタンスストアに直接保存する  
C) 4つすべてのEC2インスタンスに同時にマウントされたAmazon EFSを使う  
D) 写真をS3に保存し、アプリケーションコードから直接それらにアクセスする

**ヒント1**：要件は「4つすべてのインスタンスがどの写真も配信しなければならない」です。どの選択肢が
ファイルをすべてのインスタンスに即座に見えるようにしますか?

**ヒント2**：インスタンスストアは一時的です。EBSは複数のインスタンスに同時に
マウントできません。それで絞り込まれます。

**ヒント3**：CとDの両方が理論的には機能しうります。アプリケーションが
ファイルシステムの操作を通じて写真にアクセスする必要がある場合対HTTPリクエストの場合、
どちらがより適切でしょうか?

**解答**: D

**解説**：写真をS3に保存し、URL経由でそれらを配信することが、ウェブアプリケーションにとって
アーキテクチャ的に正しい選択です。アップロードされた写真は、S3のURLを通じて、
どのサーバーからも（そしてどのブラウザからも）即座にアクセス可能です。S3はまさにこの
ユースケースのために設計されています。ユーザーがアップロードしたファイルを、高い可用性とゼロの
管理オーバーヘッドで規模を持って保存する。

注：C（EFS）は技術的には機能するでしょうが、S3はウェブアプリケーションでユーザーがアップロードした
バイナリファイルのための好ましいパターンです。それはより安く、よりスケーラブルで、ファイルを
HTTP経由で直接配信し、アプリケーションがプロキシとして振る舞う必要がないからです。

**なぜAではないのか?** cronジョブを使ってファイルを同期することは、競合状態と整合性の
問題を生みます。アップロードと次の同期の間、ファイルは他のインスタンスで欠けるでしょう。

**なぜBではないのか?** インスタンスストアのデータは、インスタンスが停止または終了されると失われます。
写真は消えるでしょう。

**なぜCではないのか?** EFSは、質問がファイルシステムのセマンティクスを要求するときの正しい答えです
（たとえば、その場でファイルを変更するCMS）。ウェブ経由で配信されるユーザーがアップロードした
写真には、S3の方がシンプルで、安く、より適切です。

**試験キーワードの警告**：実際の試験では、問題文を文字通りに読んでください。それが
「共有**ファイル**ストレージ」「ファイルシステム」「NFS」または「POSIX」と言うなら、キーとなる答えは
**EFS**です——述べられた要件をアーキテクチャの好みで上書きしないでください。この
シナリオがS3にキーするのは、ファイルシステムではなく、HTTP経由のコスト効率の良いオブジェクトの配信を
求めているからです。
