**EC2インスタンスがデータを保存する方法**

EC2インスタンスが実行されると、そのオペレーティングシステムはディスク上にどこかに存在します。そのディスクは**ルートボリューム**と呼ばれます。デフォルトでは、これは**EBSボリューム**です—たとえ意識しなくても。

しかし、もう１つあります：EC2インスタンスには**インスタンスストア**ストレージも備わっています。

インスタンスストアは、仮想マシンを実行する基盤ハードウェアに物理的に接続された一時的なストレージです。それは非常に高速です—AWSの他のストレージオプションのほとんどよりも速いです。しかし、それにはキャッチがあります。

インスタンスストアは**儚い**です。

インスタンスが停止または終了すると、インスタンスストアのデータは消えます。永久に。回復できません。AWSはこれを非常に大きく警告しません—そのためチームは、データが失われることによってそれを発見します。

インスタンスストアは、キャッシュ、一時的な処理ファイル、スクラッチスペースに適しています。大切なデータには適していません。

**EBS：永続的なディスク**

**Amazon EBS**—Elastic Block Store—は、EC2インスタンス用の永続的なブロックストレージです。

ブロックストレージは、実際のハードドライブのように動作します。オペレーティングシステムは、それ上にファイルシステムを作成し、任意の位置の任意のバイトを読み書きし、データベースを実行し、アタッチされたディスクのように扱うことができます。

主な特性：

**永続性。**インスタンスストアとは異なり、EBSボリュームはインスタンスの停止、開始、さらにはインスタンスの終了（構成によっては）を生き残ります。インスタンスが使用されていない場合でも、ボリューム上のデータは残ります。

**アタッチ可能かつ取り外し可能。**EBSボリュームは１つのインスタンスから取り外して別のインスタンスにアタッチできます。データ移行や失敗したインスタンスからの復旧が必要な場合、ボリュームを取り外し、別の場所で再アタッチできます。

**１つのアタッチ（ほとんど）。**デフォルトでは、EBSボリュームは１つのEC2インスタンスにアタッチされます。１つのインスタンスには複数のEBSボリュームをアタッチできますが、１つのEBSボリュームは複数のインスタンスで同時にマウントすることはできません（１つの例外を除きます：EBSマルチアタッチ、これは限られたユースケースと重要な制限を備えています）。

アナロジー：EBSは、ラップトップに差し込むことができる外部ハードドライブです。ラップトップ（EC2インスタンス）は、それらを読み書きできます。作業が完了したら、取り外して別のラップトップに差し込むことができます。

**EBSボリュームタイプ**

EBSボリュームはすべて同じではありません。AWSは、異なるパフォーマンスとコストプロファイルを提供するいくつかのタイプを提供しています。

**gp3（汎用SSD）:** ほとんどのワークロードのデフォルトの選択肢です。パフォーマンスと価格のバランスが取れています。ブートボリューム、小型データベース、開発環境に適しています。

**io2（プロビジョンドIOPS SSD）:** I/O負荷の高いワークロード向けの高パフォーマンスオプションです。必要なI/O操作の秒数（IOPS）を指定し、AWSはパフォーマンスを保証します。大規模なプロ向けデータベースに適しています。

**st1（スループット最適化HDD）:** 大規模な順方向読み書きと書き込みに最適化された磁気ストレージです。SSDよりも低コストですが、ランダムI/Oには遅くなります。データウェアハウスやログ処理に適しています。

**sc1（コールドHDD）:** 最も安価なEBSオプションです。アクセス頻度が低いデータに使用されます。タイムセンシティブなものには適していません。

試験では、すべてのタイプを記憶する必要はありません。要件と適切なタイプを一致させる能力をテストします：IOPS要件→io2。コストに敏感な順方向ワークロード→st1。一般的なWebアプリケーション→gp3。

**EBSスナップショット：バックアップ**

会社が定期的に行うことの１つです。

**EBSスナップショット**は、EBSボリュームのポイントインタイムバックアップであり、S3に保存されます（EBSインターフェースを介してアクセスしますが、直接S3を介してアクセスしません）。スナップショットはインクリメンタルです：最初のスナップショットはボリューム全体をキャプチャし、その後のスナップショットは最後のものからの変更のみを保存します。

新しいEBSボリュームからスナップショットを作成できます—データベースの破損、悪いデプロイ、または誤って削除された時点からの復元。

スナップショットを自動化する必要があります。AWSは、これのために**Amazon Data Lifecycle Manager**を提供します：スナップショットを６時間ごとに取得し、最後の７日間を保持するポリシーを定義し、自動的に実行します。

プライヤは、データベースが本稼働する前にすでに設定していました。

レオはそれを思いつかなかった。

**EFS：共有ファイルキャビネット**

EBSは、1つのインスタンスに接続されたディスクです。複数のインスタンスが同時に同じファイルをアクセスする必要がある場合、どうすればいいでしょうか？

**Amazon EFS**—Elastic File Systemが登場します。

EFSは、管理されたネットワークファイルシステムです。複数のEC2インスタンスが同じEFSファイルシステムを同時にマウントして、共有ファイルに読み書きできます。これはEBSが提供できない重要な機能です。

次のように考えてみましょう：

EBSは、1台のラップトップに接続された外部ハードドライブです。そのラップトップのみがそれを使用できます。

EFSは、オフィスの中央にあるファイルキャビネットです。チームメンバーは誰でも引き出しを開いてファイルにアクセスしたり、何かを戻したりできます。複数の人が同時に同じストレージにアクセスします。

**EFSが必要なのはいつですか？**

* 複数のEC2インスタンスがファイルを共有する必要がある場合（コンテンツ管理システム、共有構成ファイル、共有メディアライブラリ）
* すべてのインスタンスが同じデータにアクセスする必要がある水平スケーリングされたアプリケーションの場合
* インスタンス障害に耐える永続ファイルシステムが必要な場合

**EFS vs. S3:** EFSはファイルシステム（フォルダ、ファイル、権限、ロック）です。S3はオブジェクトストレージ（アップロード、ダウンロード、ファイルシステムセマンティクスのないもの）です。EFSはS3よりもはるかに高価です。S3は、全体として保存および取得されるファイルに使用します。EFSは、アプリケーションが標準のファイルシステム操作を通じてアクティブに読み書きするファイルに使用します。

**適切なストレージの選択**

これまでに、AWSで3種類のストレージを見てきました。意思決定を明確にしましょう。

| 要件                                  | ストレージタイプ     |
|---------------------------------------|------------------|
| データベースの永続的で高速なディスクが必要 | EBS (gp3 または io2) |
| 複数のサーバーが共有ファイルが必要     | EFS              |
| ファイル、バックアップ、画像、大きなオブジェクト | S3               |
| 一時的な計算のスクラッチスペース       | インスタンスストア   |
| 最小限のコストで長期のアーカイブ       | S3 Glacier       |

この決定が正しくないと、S3でEFSが必要な場合に運用が複雑になります。EFSが必要な場合にEBSを使用すると、スケーリング時に障害が発生します。インスタンスストアで永続性を必要とする場合、データが失われます。

プライヤは、この表を印刷して壁に貼り付けました。

「ストレージの要件を追加するたびに、ここから始めます」と彼女は言いました。

## 強みと限界

**EBSの強み:**

* EC2向けの永続的で高速なブロックストレージ
* ポイント・イン・タイムのバックアップと復旧のためのスナップショット
* さまざまなワークロード向けの複数のパフォーマンス階層
* 組み込みでサポートされている暗号化

**EBSの限界:**

* 1つのインスタンスにのみ接続できる（軽微な例外あり）
* EC2インスタンスと同じAZにある
* 実際に使用した分だけではなく、プロビジョニングされたストレージを支払う

**EFSの強み:**

* 複数インスタンスの共有ファイルシステム—ネイティブNFSプロトコル
* 自動的にスケーリングされ、容量をプロビジョニングする必要はありません
* 同じ地域内の異なるAZにアクセス可能

**EFSの限界:**

* S3よりもGBあたりより高価
* 乱アクセスI/Oに対してEBSよりもレイテンシが高い
* すべてのリージョンで利用できない

## 概要

* **インスタンスストア**は、ホストに物理的に接続された一時的な高速ストレージです。インスタンスが停止または終了するとデータは失われます。スクラッチスペースのみに使用します。
* **EBS**（Elastic Block Store）は、1つのEC2インスタンス向けの永続ブロックストレージです。インスタンスが停止してもデータは保持されます。バックアップのためにスナップショットを作成できます。適切なボリュームタイプ（gp3は一般的な使用、io2は高IOPSの要件）を選択してください。
* **EFS**（Elastic File System）は、複数のインスタンスが同時にマウントできる共有ネットワークファイルシステムです。複数のサーバーが同じファイルを共有にアクセスする必要がある場合に使用します。

ストレージタイプを要件に一致させる：データベース→EBS；共有ファイル→EFS；オブジェクト/バックアップ→S3；アーカイブ→S3 Glacier。

## 試験のヒント

* SAA-C03 ドメイン3—タスク3.1（ストレージソリューション）

* **EBSボリュームは1つのAZに存在します。** 1つのAZにあるインスタンスにのみ接続できます。別のAZでEBSボリュームを使用するには、スナップショットを作成して復元する必要があります。
* **EBSスナップショットは増分でS3に保存されます。** 最初のスナップショットは完全です。その後のスナップショットは、変更のみを保存します。災害復旧のために他のリージョンにスナップショットをコピーできます。
* **EFSはクロスAZです。** 同じ地域内の異なるAZにある複数のインスタンスが同じEFSファイルシステムをマウントできます。これはEBSとは異なる重要な違いです。
* 試験のシナリオで「Webアプリケーションと共有コンテンツ」または「複数のインスタンスが同じファイルをアクセスする」という言葉が出てきた場合は、EFSを考えましょう。データベースストレージまたは1つのサーバー向けの永続ディスクが必要な場合は、EBSを考えましょう。
* インスタンスストアのデータは再起動時に失われることはありませんが、停止または終了すると失われます。質問が「インスタンスが停止するとデータが失われる」と記述されている場合、インスタンスストアが使用されます。

## 練習問題

**練習問題1—想起**

EBSとEFSの違いを、あなたの言葉で説明してください。どちらをいつ選択すればよいでしょうか？

*(ヒント：1つのインスタンスまたは複数のインスタンスが同時にストレージにアクセスする必要があるかどうかを考えてください。)*

**演習問題 2 — 試験練習**

*シナリオ*: 企業がロードバランダの後ろに4つのEC2インスタンスでWebアプリケーションを実行しています。ユーザーはプロフィール写真のアップロードできます。4つのインスタンスがすべて、アップロードされた直後にどのインスタンスが処理したかにかかわらず、すべてのユーザーの写真を提供できるようにする必要があります。チームは、永続的で共有されたファイルストレージを必要としています。

どのストレージソリューションが要件に最も適していますか？

A) 各EC2インスタンスにgp3ボリュームをアタッチし、cronジョブを使用してファイル間で同期する。
B) 写真をEC2インスタンスのインスタンスストアに直接保存する。
C) Amazon EFSをすべてのEC2インスタンスに同時にマウントする。
D) 写真をS3に保存し、アプリケーションコードから直接アクセスする。

**ヒント 1**: 要件は「すべての4つのインスタンスが写真を提供する必要がある」ことです。ファイルがすべてのインスタンスにすぐに表示されるオプションはどれですか？

**ヒント 2**: インスタンスストアは一時的なものです。EBSは複数のインスタンスに同時にマウントできません。これにより、選択肢が絞られます。

**ヒント 3**: CとDは理論的には機能する可能性があります。アプリケーションがファイルシステム操作とHTTPリクエストの両方で写真にアクセスする必要がある場合に、どちらがより適切ですか？

**答え**: D

**説明**: 写真をS3に保存し、URLで提供することが、Webアプリケーションにとってアーキテクチャ的に正しい選択です。アップロードされた写真は、S3のURLを通じて、どのサーバー（およびどのブラウザでも）からすぐにアクセスできます。S3は、このユースケースに設計されており、大規模なユーザーアップロードされたファイルを、高い可用性とゼロ管理オーバーヘッドで保存するために最適です。

注：C（EFS）は技術的には機能しますが、ユーザーアップロードされたバイナリファイルの場合、S3がより好ましいパターンです。なぜなら、S3はHTTPを介してファイルを直接提供し、アプリケーションがプロキシとして機能する必要がないため、より安価で、スケーラブルで、管理オーバーヘッドが少ないからです。

**なぜAではないのですか？** cronジョブを使用してファイル間で同期することは、競合条件と一貫性の問題を引き起こします。アップロードと次の同期の間、他のインスタンスでファイルが欠落します。

**なぜBではないのですか？** インスタンスストアのデータは、インスタンスが停止または終了すると失われます。写真が消えます。

**なぜCではないのですか？** EFSが適切な答えは、アプリケーションがファイルシステムの意味論（たとえば、CMSがファイルを変更する場所）を必要とする場合にのみです。Webで提供されるユーザーアップロードされた写真の場合、S3はよりシンプルで、安価で、より適切です。
