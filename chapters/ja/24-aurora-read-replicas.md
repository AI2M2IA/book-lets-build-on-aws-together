**読み取りレプリカ: 読み取りトラフィックを分散する**

ほとんどの Web アプリケーションは、データを書き込むよりはるかに頻繁に読み取ります。メニューを閲覧する顧客は何十もの SELECT クエリを行います。注文をするのはいくつかの INSERT/UPDATE クエリです。比率は通常10:1 以上です。

**読み取りレプリカ (read replica)** は、プライマリからすべての書き込みのコピーを受け取り、それらの書き込みを SELECT クエリに利用可能にする追加の RDS インスタンスです。

仕組み:

1. アプリケーションの書き込み (INSERT、UPDATE、DELETE) はプライマリデータベースに行く
2. プライマリはそれらの変更を読み取りレプリカに非同期にレプリケートする
3. アプリケーションの読み取り (SELECT) は読み取りレプリカに分散される
4. 読み取りレプリカが負荷を分担する — それぞれが総読み取りトラフィックの一部を処理する

結果: プライマリデータベースは書き込みのみ (とオプションでいくつかの読み取り) を処理します。読み取りレプリカが読み取り負荷を処理します。10:1 の読み取り/書き込み比率では、1つの読み取りレプリカを追加することで、プライマリの総負荷をおおよそ半分にします。

**重要な制限**: レプリケーションは **非同期** です。レプリケーションラグがあります — 通常ミリ秒ですが、負荷時には秒になり得ます。レプリカからの読み取りは、プライマリよりわずかに遅れたデータを見るかもしれません。ほとんどの読み取り (メニューの閲覧、注文履歴の表示) では、これは許容できます。「私の注文は通ったか?」には — プライマリから読みます。

**読み取りレプリカ: 詳細**

- プライマリの RDS インスタンスごとに最大15の読み取りレプリカを持てます (MySQL、PostgreSQL、MariaDB)
- 読み取りレプリカは同じリージョンにも別のリージョンにも置けます (クロスリージョンレプリカ)
- 読み取りレプリカ自身が読み取りレプリカを持てます (チェイニング)
- 読み取りレプリカは別個のエンドポイントです — アプリケーションは読み取りをレプリカのエンドポイントに向けなければなりません
- 読み取りレプリカはスタンドアロンのデータベースに昇格できます (DR に役立ちます)

Nimbus では、レオは1つの読み取りレプリカを追加しました。「大丈夫だ」と、トラフィックを切り替える前にアプリケーションの読み取り/書き込みルーティングロジックをテストしたかとプリヤが尋ねたとき、彼は言いました。彼はしていませんでした。彼は次の40分を、書き込みが読み取りレプリカのエンドポイントに行っていないことを検証するのに費やしました。

**Read-After-Write 一貫性の問題**

読み取りレプリカを有効にしてから3日後、サポートチケットが届きました。レストランパートナーが自分のメニューを更新し — 提供を終了した品目を削除し — それからそれが削除されたことを確認するために電話をかけました。カスタマーサービスのエージェントが Nimbus のインターフェースからメニューを呼び出しました。品目はまだそこにありました。

20秒後、それは消えました。

非同期レプリケーションラグです。書き込み (DELETE メニュー品目) はプライマリに行きました。カスタマーサービスのエージェントの読み取りはレプリカに行き、それはまだ変更を受け取っていませんでした。レプリカはその瞬間15秒遅れていました — 珍しくはないが、目に見えました。

「それで、もし誰かが結果整合性のウィンドウを通じて侵入しようとしたら?」とプリヤが尋ねました。「あるいは単に — ちょうど削除されたメニュー品目に対して注文が行われたら? 私たちは顧客に課金し、レストランはその品目を持っていない。」

これは単なる UX の煩わしさではなく、本物の一貫性の懸念でした。

解決策: どの読み取りに一貫性の要件があるかを特定し、それらをプライマリにルーティングすること。

**レプリカに行ける読み取り** (結果整合性で問題ない):
- レストランのメニューを閲覧する顧客 (1〜2秒古くても知覚できない)
- 注文履歴のクエリ (1分前からの注文履歴を見るユーザー)
- アナリティクス型の読み取り (今週の上位レストラン)

**プライマリに行かなければならない読み取り** (read-after-write 一貫性が必要):
- 書き込みの直後、アプリケーションが書き込みの成功を確認する必要があるとき
- 注文後の直後の注文ステータスの読み取り
- レストラン管理インターフェースによってトリガーされるメニューの読み取り (レストランがちょうどメニューを変更した)

アプリケーションはデータベース接続層にルーティングのヒントを追加しました: リクエストがレストラン管理ダッシュボードから来たなら、プライマリにルーティング。閲覧する顧客から来たなら、レプリカにルーティング。`X-Read-Consistency: strong` HTTP ヘッダーがそのシグナルとして機能しました。

**プライマリの RDS インスタンスが失敗すると**、AWS は Multi-AZ 設定のスタンバイレプリカに自動的にフェイルオーバーします (異なる種類のレプリカ — 同期スタンバイで、読み取りレプリカではありません)。Multi-AZ スタンバイが新しいプライマリになります。読み取りレプリカは読み取りの提供を続け、いまや新しいプライマリからレプリケートします。アプリケーションの視点からは、プライマリエンドポイントの DNS が以前のスタンバイを指すように変わり、アプリケーションは再接続します。

フェイルオーバーは RDS PostgreSQL では通常60〜120秒かかります。そのウィンドウの間、書き込みは失敗します。

**読み取りレプリカの昇格** は別個の操作です — そして別個のシナリオです。読み取りレプリカを取って、それを独立した、書き込み可能なデータベースにしたい (DR のため、新しいリージョンへの移行のため、またはプライマリがなくなって Multi-AZ フェイルオーバーを待つよりも昇格が必要なため) なら、読み取りレプリカをスタンドアロンのプライマリに昇格できます。昇格には数分かかり、その後レプリカは元のプライマリからレプリケートしなくなります — それ自身のデータベースです。

「us-west-2 のプライマリが完全にダウンしたらどうなるか考えた?」とプリヤが尋ねました。「Multi-AZ スタンバイへのフェイルオーバーだけじゃなく — リージョン全体。」

「リージョンが失敗したら」とレオが言いました。「Multi-AZ スタンバイも us-west-2 にある。両方が一緒に失敗する。」

「だから真のリージョン DR シナリオには」とトムが言いました。「昇格できる us-east-1 の読み取りレプリカが必要だ。」

「そうだ。クロスリージョンの読み取りレプリカ。まだ持っていない。」

「それは月にいくらかかるんだ?」とトムが尋ねました。彼はすでに答えが決定を含むことを知っていました。

us-east-1 の db.r6g.large のクロスリージョン読み取りレプリカ: 月340ドル (同じインスタンスコスト)。加えてレプリケーションのためのクロスリージョンデータ転送: Nimbus の書き込み量では最小限。合計: DR レプリカに対しておよそ月350ドル。

「それは年4,200ドルだ」とトムが言いました。「10年で5回未満しか AWS リージョンに起きていないシナリオに対して守るために。」

「それで、Nimbus がリージョンイベント中に24時間ダウンするコストは?」とプリヤが尋ねました。

**Amazon Aurora: データベースエンジンの再考**

Aurora は、MySQL と PostgreSQL と互換性のある AWS 独自のリレーショナルデータベースエンジンです。クラウドワークロードのためにゼロから設計され、リレーショナルデータベースのストレージ層がどう機能するかを再想像しました。

従来の RDS 構成 (MySQL、PostgreSQL) では、ストレージとコンピュートが密結合しています。データベースエンジンがデータファイルを管理します。レプリケーションがデータをプライマリからレプリカにコピーします。レプリカはすべての書き込み操作をやり直さなければなりません。

これはレプリケーション速度に天井を作ります: レプリカは、レプリケーションログを処理できる速さでしか書き込みを適用できません。書き込みが多い時期 — 一括インポート、フラッシュセール、バッチ更新 — には、レプリカが遅れることがあります。レプリケーションラグは実装の欠陥ではありません。アーキテクチャの帰結です。

レオが読み取りレプリカを提案したとき、プリヤはすぐにこれを指摘しました。「金曜のラッシュ中にレプリケーションラグが30秒にスパイクしたらどうなるか考えた? レプリカは30秒遅れる。顧客が注文をして、キッチンのスロットがプライマリで予約されるけど、レプリカをクエリする2人目の顧客はその予約を見ない。2つの注文、1つのスロット。」

「それは在庫の一貫性の問題だ」とレオが言いました。

「まさに在庫の一貫性の問題よ」とプリヤが確認しました。「だから在庫の読み取り — 『この品目はまだ利用可能か?』 — はプライマリに行かなければならない。」

Aurora のアーキテクチャはラグに直接対処します。

Aurora はストレージをコンピュートから分離します。3つの Availability Zone にまたがって6つのコピーでデータを自動的にレプリケートする、分散された、耐障害性のあるストレージ層を使います。コンピュート層 (データベースインスタンス) は、このストレージ層の上に乗ります。

**これが変えること**:

**読み取りレプリカ**: Aurora レプリカはデータをレプリケートする必要がありません — それらはすでに同じストレージ層を共有しています。これは次を意味します:

- ストレージボリュームを共有する最大15の Aurora レプリカ (通常の RDS も最大15の読み取りレプリカを許可しますが、それぞれが完全なデータコピーです)
- レプリケーションラグは通常100ミリ秒未満 (負荷時の RDS の秒に対して)
- レプリカは30秒未満でプライマリに昇格できる (数分に対して)

**フェイルオーバー**: レプリカがストレージを共有するため、フェイルオーバーははるかに速いです — 昇格はデータ転送を伴わず、書き込みをリダイレクトするだけです。

**ストレージ**: Aurora はストレージを10GB 単位で、最大128 TiB (最近のエンジンバージョンでは256 TiB) まで自動的にスケールします。事前にストレージをプロビジョニングすることは決してありません。

**性能**: Aurora は、同等のインスタンスタイプで標準 MySQL の5倍、標準 PostgreSQL の3倍のスループットを主張します。

すべてのレプリカが同じストレージを共有するなら、そのストレージが単一障害点にならないか、と疑問に思うかもしれません。Aurora のストレージ層は、3つの Availability Zone に6つのコピーでデータを自動的にレプリケートします。ストレージそのものは、どの単一の RDS Multi-AZ 構成よりも回復力があります — AZ 全体の喪失をデータ損失ゼロで、フェイルオーバー不要で生き延びるように設計されています。

2つ目のよくある質問: Aurora が MySQL/PostgreSQL 互換なら、アプリケーションコードを変更せずに RDS PostgreSQL から Aurora PostgreSQL に移行できるのか? ほとんど。Aurora PostgreSQL 互換性は、Aurora が PostgreSQL のワイヤープロトコルを実装し、PostgreSQL の SQL 構文と機能の大多数をサポートすることを意味します。ほとんどのアプリケーションはコード変更ゼロで移行します。エッジケース: 少数の PostgreSQL 拡張は Aurora で利用できず、一部のシステムカタログクエリは異なる値を返し、特定の管理操作は異なります。本番の移行では、書き込みを切り替える前に並列の読み取りトラフィックでテストします。

Nimbus では、RDS PostgreSQL から Aurora PostgreSQL への移行は午後1回かかりました。アプリケーションは Aurora エンドポイントを指しました。メニューのクエリは — レオが、Performance Insights がデータベース負荷の最大の消費者として指していたインデックスを追加したあと — 620ミリ秒ではなく4ミリ秒で実行されました。接続プールはもはや200のうち198に当たりませんでした。P95 のレイテンシは28ミリ秒に下がりました。

「これは違うデータベースエンジンだ」とレオが言いました。「でもアプリケーションは同じデータベースエンジンだと思っている。」

「それで面白い部分は?」とマヤが尋ねました。

「高速データベースクローニングだ。」

「メモした」と、部屋の向こうからサムが静かに言い、すでにタイプしていました。サムは、データベースの仕事の一部をレオから引き取るために数週間前にチームに加わったバックエンドエンジニアでした。誰も彼が何をしているか尋ねませんでした。

**Aurora の料金: トムの質問**

Aurora の料金は RDS とは異なります:

**インスタンスの料金**: タイプ別の RDS インスタンス料金と類似。

**ストレージの料金**: GB あたり月0.10ドル (保存されているものに対して支払い、自動的にスケール)。

**I/O の料金**: Aurora は I/O リクエスト (ストレージへの読み取り/書き込み) ごとに課金します。これは書き込みの多いワークロードでは significant になり得ます。

「待て」とトムが言いました。「I/O を別に支払うのか?」

「Aurora Serverless v2 と Aurora I/O-Optimized がこの料金モデルを変える」とレオが言いました。「Aurora I/O-Optimized は I/O 料金を課金しないが、より高いストレージとインスタンスの価格。I/O の多いワークロードに適している。」

トムはトレードオフを見ました。読み取りの多い (多くのメニュークエリ、少ない書き込み) Nimbus にとっては、Aurora I/O-Optimized はより高くつくかもしれません。標準の Aurora 料金が適切かもしれません。

有用な経験則: I/O 料金が Aurora の総請求のおよそ25% を超えるなら、I/O-Optimized のほうがおそらく安いです。Nimbus の読み取りの多いワークロードでは、I/O 料金は低い — 標準の料金が適用されます。イベントロギングシステムのような書き込みの多いワークロードには、I/O-Optimized がコストを大幅に削減できます。

これはシニアエンジニアがする本物のコストの決定です: 正しく選ぶには、ワークロードの I/O パターンを知る必要があります。

ワークロードが小さく、安定していて、予測可能なら、RDS PostgreSQL のほうがシンプルで意味のある形で安いです — しかし、トラフィックが予測不能なら、データ量が事前にプロビジョニングできる以上に成長しているなら、または30秒未満の自動フェイルオーバーが必要なら、Aurora の共有ストレージモデルがより高い基本コストを正当化します。

**Aurora Serverless: インスタンスを考えずにスケールする**

**Aurora Serverless v2** は、実際のデータベース負荷に基づいてコンピュート容量を自動的にスケールする設定です。固定のインスタンスサイズ (db.r6g.large) を選ぶ代わりに、Aurora Capacity Units (ACU) で最小と最大の容量を設定します。

Aurora Serverless v2:

- 負荷が増えると数秒でスケールアップする
- アイドル期間中にスケールダウンする — そして2024年後半以降、接続がないときは0 ACU まで自動一時停止できる (再開には約15秒。自動一時停止は RDS Proxy や他の接続を保持するプロキシでは機能しません)
- コスト: ACU 時間あたり0.12ドル (加えてストレージと I/O)

可変トラフィックのワークロード — Nimbus の金曜のスパイク対月曜朝の静けさ — には、Serverless v2 がオフピーク期間中のコストを削減し、事前プロビジョニングなしでピークを処理します。

「だから金曜のスパイク中に」とレオが言いました。「Aurora は自動的にスケールアップする。日曜の朝、ほとんどトラフィックがないときは、最小までスケールダウンする。」

「そして使っている容量に対してだけ支払う」とトムが言いました。

「そのとおり。」

Aurora Serverless v2 で1か月過ごしたあと、レオは前の週の ACU (Aurora Capacity Unit) グラフを呼び出しました。

グラフは2つの異なるパターンを示しました。週の間、データベースは2〜4 ACU で動いていました — バックグラウンドクエリ、ECS ヘルスチェック、Glue ETL ジョブ、開発テストの静かなざわめき。金曜の夕方18:00 から22:00 の間、ACU 数は登りました:

```
金曜 18:00  → 6 ACU
金曜 19:00  → 14 ACU
金曜 19:45  → 26 ACU  (ピーク — NFL のキックオフ前にピザの注文が急増)
金曜 20:30  → 18 ACU
金曜 21:00  → 12 ACU
金曜 22:30  → 4 ACU
土曜 02:00 → 2 ACU  (最小)
```

スケーリングはほぼ即時でした — Aurora Serverless v2 は0.5 ACU の単位でスケールし、新しい RDS インスタンスをプロビジョニングするのに必要な数分ではなく、数秒で容量を追加できます。

「あの金曜のピークはいくらかかったんだ?」とトムが尋ねました。

ACU 時間あたり0.12ドルで: 金曜のピークは平均18 ACU で4時間 → ピーク期間で8.64ドル。残りの週は平均3 ACU × 164時間 × 0.12ドル = 59.04ドル。週の合計: 67.68ドル。

金曜のピークを処理する同等のプロビジョニングされたインスタンス (db.r6g.xlarge、4 vCPU、32 GB) は、0.937ドル/時間 × 168時間 = **週で157.42ドル** — 金曜のピークが実現するかどうかにかかわらず。

「Serverless v2 は週67ドル。ピークに合わせたプロビジョニングされたインスタンスは157ドル」とトムが言いました。「57% の削減だ。」

「金曜に4時間正当に26 ACU を使い、週の残りは2 ACU を使うデータベースで」とレオが言いました。「データベースが週中ずっと一定の高負荷で動くなら、プロビジョニングされたインスタンスのほうが安い。節約は変動から来る。」

トムはゆっくりうなずきました。彼はメモのパターンにこれを追加していました: この四半期のすべての節約の話は同じ形をしていました。あなたは、必要かもしれないものではなく、使うものに対して支払う。S3 ライフサイクルポリシーは、各オブジェクトに値するストレージクラスにだけ支払いました。Lambda は呼び出し時間にだけ支払いました。Fargate はタスクの CPU とメモリにだけ支払いました。Aurora Serverless v2 は、データベースが実際に消費した ACU にだけ支払いました。

トムは、まさに探していたものを見つけた人の表情をしていました。

**悪い移行からの回復: クローン、PITR、そして元に戻すボタン**

Aurora に移ってから2週間後、サムは本番でデータベースの移行スクリプトを実行しました。スクリプトは `menu_items` テーブルから `legacy_menu_format` カラムを削除するはずでした。彼は、含めたと思っていた WHERE 句なしでそれを実行しました。

結果はカラムを削除することではありませんでした。それは `menu_items` テーブルから40,000行をクリアした DELETE 文でした — およそ200のレストラン分のメニューデータが、消えました。

アラートは30秒以内に発報しました。注文の失敗が急増しました。メニューサービスは200のレストランに対して空の結果を返し始めました。

「WHERE 句があるはずだった」と、コンソールを見つめながらサムが言いました。

従来の回復パス: 最新の自動バックアップスナップショットから復元する。自動バックアップは24時間ごとに1回実行され、完全な復元と入れ替えには20〜40分かかります — その間 *すべての* レストランが暗くなり、影響を受けた200だけではありません — そしてバックアップ以降に行われたすべての注文は失われます。

レオはそれをしませんでした。標準の RDS と同様に、Aurora は **ポイントインタイムリカバリ (PITR)** のために継続的なバックアップを保ちます — 最後の夜間スナップショットだけでなく、バックアップ保持ウィンドウ内の任意の秒にクラスターを復元できます。そして重要なことに、復元は *新しい* クラスターを作成します。回復している間、本番は稼働したままです。

```bash
aws rds restore-db-cluster-to-point-in-time \
  --db-cluster-identifier nimbus-aurora-recovery \
  --source-db-cluster-identifier nimbus-aurora-cluster \
  --restore-to-time 2024-06-14T15:42:00Z
```

タイムスタンプ: 15:42:00Z — サムが移行スクリプトを実行する4分前。回復クラスターが立ち上がる間、本番の残りは影響を受けていないレストランの提供を続けました。それが利用可能になると、レオは回復クラスターから影響を受けた200のレストランの `menu_items` 行をダンプし、それらを本番に挿入し直しました。アラートからメニューが完全に復元されるまでの合計時間: 40分弱 — そして彼はデータベース全体を入れ替える代わりに行を外科的に修復したので、15:42 以降に行われた注文は1つも失われませんでした。回復クラスターはその後削除されました。その目的を果たしたのです。

「何を失ったの?」とマヤが尋ねました。

短時間空だったメニューに対して行われた6つの注文がチェックアウトで失敗しました — そのすべてが SQS キューにあり、再生できました。永続的に失われた顧客データはありませんでした。

「そしてここで **高速データベースクローニング** が登場する」と、レオはあとでチームを集めながら言いました。Aurora は、コピーオンライトを使って、データベースのサイズにかかわらず数分でクラスターの **クローン** を作成できます: クローンは元のストレージ層を共有し、新しいまたは変更されたページだけが追加のスペースを消費します。現在の本番データベースのクローンは安く、速く、完全に分離されています — クローンへの書き込みが本番に触れることは決してありません。

「つまり」と、サムを見ながらプリヤが言いました。「移行スクリプトは、本番で実行される前に、本番データのクローンに対してテストされる。それが新しいルールよ。」

サムはうなずきました。彼はすでにそれを付箋に書いていました。

もう1つのツールがこの絵に属します。Aurora MySQL — Aurora PostgreSQL ではなく — には **Aurora Backtrack** があります: 新しいクラスターに復元することなく、クラスターを特定の時点に *その場で* 巻き戻す機能です。Nimbus のクラスターが Aurora MySQL だったら、レオは3分未満でそれを15:42 にバックトラックできたでしょう — もっとも、クラスター全体を巻き戻すと、削除後に書き込まれた一握りの正当な注文もロールバックされ、それは外科的な PITR アプローチが保存したものです。

「それで、もし誰かが Backtrack — またはポイントインタイム復元 — を使って侵入しようとしたら?」とプリヤが尋ねました。「攻撃者は監査ログやコンプライアンスデータを巻き戻せる?」

Backtrack には `rds:BacktrackDBCluster` API 権限が必要で、復元には `rds:RestoreDBClusterToPointInTime` が必要です — 通常のデータベース操作とは別個の IAM アクションです。標準のアプリケーションロールはこれらの権限を持ちません。明示的にそれらを許可する IAM ポリシーを持つ運用チームだけが、それらを使えました。彼女はこれを IAM 権限レビューのチェックリストに追加しました。

重要な注意点: Aurora Backtrack は Aurora MySQL 互換のクラスターでのみ利用可能で、PostgreSQL では利用できません。Backtrack のウィンドウはクラスター作成時に設定されます (1時間から72時間、バックトラックウィンドウの時間ごとに課金)。そして Backtrack はクラスター全体に影響します — 1つのテーブルや1組の行を Backtrack することはできません。外科的な行レベルの回復には — どちらのエンジンでも — レオが使った PITR から一時クラスターへのアプローチがツールです。

**Aurora Global Database: マルチリージョンの読み取り**

**Aurora Global Database** は Aurora を複数の AWS リージョンに拡張します:

- **1つのプライマリリージョン** がすべての書き込みを処理する
- **最大5つのセカンダリリージョン** が、通常1秒未満のレプリケーションラグで読み取りを提供する
- セカンダリリージョンは1分未満でプライマリに昇格できる (DR シナリオのために)

Nimbus のグローバル展開には、Aurora Global Database が、ロンドンのレストランパートナーに EU 読み取りレプリカから自分のローカルメニューをクエリさせ、一方ですべての注文 (書き込み) は依然として米国のプライマリを通るようにします。

**RDS vs Aurora: どちらを選ぶか**

| 要素              | RDS (PostgreSQL/MySQL)        | Aurora                                                     |
|-------------------|-------------------------------|------------------------------------------------------------|
| コスト            | 小さなワークロードには低い    | 基本は高いが、よりよくスケールする                         |
| 互換性            | 完全                          | MySQL/PostgreSQL 互換 (わずかな違いあり)                   |
| 最大レプリカ数    | 15 (それぞれ完全なデータコピー) | 15 (共有ストレージボリューム)                            |
| レプリカラグ      | 秒になり得る                  | 通常100ミリ秒未満                                          |
| ストレージ        | 固定プロビジョニング          | 128 TiB まで自動スケール (最近のバージョンでは256 TiB)     |
| フェイルオーバー時間 | 60〜120秒                  | 30秒未満                                                   |
| サーバーレスオプション | 限定的                     | Aurora Serverless v2                                       |
| 最適なのは        | 安定した、予測可能なワークロード | 可変トラフィック、高い読み取り量、高速フェイルオーバーの必要 |

**リレーショナルを超えて: 目的特化型ファミリー**

第9章では DocumentDB (MongoDB 互換のドキュメント)、Neptune (グラフの関係)、Keyspaces (Cassandra 互換のワイドカラム) を紹介し、第10章では MemoryDB (耐久的な Redis 互換のプライマリデータベース) を紹介しました。さらに2つの名前がファミリーを締めくくります — それらに深さは必要なく、どのデータの形がどのエンジンを指すかを認識できる能力だけでよいです。なぜなら、それらは答えの選択肢として絶えず現れるからです:

- **Amazon Timestream**: **時系列** データ — センサーの読み取り、メトリクス、テレメトリ。試験のシグナル: 「時間にわたる IoT 測定」。(実世界では、現在の提供は Timestream for InfluxDB です。元の「LiveAnalytics」フレーバーは2025年に新規顧客に閉じられました。)
- **Amazon QLDB**: 古い問題で「不変の、暗号的に検証可能な台帳」としてまだ出会うかもしれません。AWS は2025年に QLDB を廃止しました (代わりに Aurora PostgreSQL を推奨) — それを構成要素ではなく、レガシーのおとりとして扱ってください。

ホワイトボードに書く価値のあるルール: **リレーショナルの行 → RDS/Aurora。規模での key-value → DynamoDB。ドキュメント → DocumentDB。関係 → Neptune。時間 → Timestream。Cassandra → Keyspaces。耐久的な Redis → MemoryDB。** 形に合わせれば、問題は自ずと答えが出ます。

## 強みと限界

**Aurora の強み**:

- 標準の RDS より大幅に速いフェイルオーバー
- 最小限のラグで最大15の読み取りレプリカ
- 自動スケーリングするストレージ
- 可変ワークロードのための Serverless v2
- マルチリージョンデプロイのための Global Database

**Aurora の限界**:

- 小さく、安定したワークロードには高コスト
- I/O 料金が書き込みの多いワークロードでは significant になり得る (これには I/O-Optimized を使う)
- わずかな MySQL/PostgreSQL 互換性の違いがコード変更を必要とすることがある
- Serverless v2 の自動一時停止からの再開 (約15秒) と急速なスケールアップがレイテンシのスパイクを引き起こすことがある

## 概要

第23章の S3 ライフサイクルの作業は、データを正しいストレージ層に移すことでコストを削減しました。Aurora はコンピュートに対して同等のことをします: ピーク負荷のためにプロビジョニングしてそれを常に支払う代わりに、Serverless v2 は需要に合わせてスケールします。

- **読み取りレプリカ** は、プライマリから読み取りトラフィックを分散します。非同期レプリケーション — ほとんどの読み取りにはわずかなラグは許容できます。書き込み一貫性を必要とする読み取り (書き込み直後の読み取り、管理インターフェースの読み取り) は、レプリカではなくプライマリにルーティングします。
- **Aurora** はストレージ層を再想像します: 分散され、レプリカ間で共有され、自動スケーリングします。
- Aurora が提供するもの: 15の読み取りレプリカ、100ミリ秒未満のレプリカラグ、30秒未満のフェイルオーバー、128 TiB (最近のバージョンでは256 TiB) までの自動スケーリングストレージ。
- **Performance Insights**: どうスケールするかを決める前に、データベース負荷を引き起こしている特定の SQL クエリを特定します。欠けているインデックスが、より大きなインスタンスの必要をなくすことがあります。
- **CloudWatch のデータベースメトリクス**: DatabaseConnections (飽和に近いとアプリケーションの接続プーリングが壊れている)、CPUUtilization (持続的な高 CPU は高価なクエリを意味する)、ReadLatency (時間にわたる劣化は、しばしばインデックスの欠けた成長するテーブル)。
- **Aurora Serverless v2**: コンピュートを0.5 ACU の単位で自動スケールします。ACU 時間ごとに課金。ピークとオフピークの間の変動が大きいワークロードには、プロビジョニングされたインスタンスより大幅に安いです。
- **ポイントインタイムリカバリ (PITR)**: Aurora クラスターをバックアップ保持ウィンドウ内の任意の秒に — *新しい* クラスターに — 復元します。そのため、失われた行を外科的にコピーし直す間、本番は稼働したままです。
- **高速データベースクローニング**: サイズにかかわらず数分でのコピーオンライトのクラスターのクローン。安く、分離されている — 本番で実行される前に、本番データに対して移行をテストするために使います。
- **Aurora Backtrack** (MySQL 互換のみ — PostgreSQL ではない): バックアップから復元することなく、クラスターをその場で時点に巻き戻します。最大72時間のウィンドウで利用可能。`rds:BacktrackDBCluster` IAM 権限が必要 — 運用チームに制限します。
- **Aurora Global Database**: 1つのリージョンにプライマリ、最大5つのリージョンに読み取りレプリカ。
- **読み取りレプリカの昇格**: クロスリージョンの読み取りレプリカは、リージョン DR のためにスタンドアロンのプライマリに昇格できます。DR の利益を、2つ目の完全なインスタンスを動かすコストと天秤にかけます。
- 小さく、安定した、予測可能なワークロードには RDS を選びます。スケール、高速フェイルオーバー、または可変トラフィックの処理が必要なときは Aurora を選びます。

## 試験のヒント

*SAA-C03 ドメイン: 高性能なアーキテクチャの設計 (ドメイン3、タスク3.3)*

- **Aurora レプリカ vs RDS 読み取りレプリカ**: Aurora レプリカはストレージを共有 (ほぼゼロのラグ、30秒未満のフェイルオーバー)。RDS 読み取りレプリカはデータをレプリケート (ラグの可能性、フェイルオーバーに数分)。
- **Aurora Serverless v2**: 「データベース容量を自動スケール」「予測不能または急増するデータベーストラフィック」 → Aurora Serverless v2。注意: 歴史的に Serverless **v1** だけがゼロまでスケールしました。v2 の最小は2024年後半まで0.5 ACU でしたが、そのとき v2 が0 ACU への自動一時停止を得ました。古い試験問題はまだ v2 がゼロまでスケールできないと想定しているかもしれません。
- **Aurora Global Database**: 「マルチリージョンデータベース」「米国のプライマリから低レイテンシで EU から読み取り」「リージョンフェイルオーバーで RTO < 1分」 → Aurora Global Database。
- **フェイルオーバーのタイミング**: Aurora は30秒未満。RDS Multi-AZ は60〜120秒。両方を知っておく。
- **データの形による目的特化型データベース**: 「ソーシャルグラフ / レコメンデーション / 不正のリング」 → Neptune。「MongoDB」 → DocumentDB。「Cassandra」 → Keyspaces。「時系列 / IoT テレメトリ」 → Timestream。「Redis 互換の *プライマリ* データベース (耐久的)」 → MemoryDB (ElastiCache = キャッシュ に対して)。「不変の暗号的台帳」 → 古い問題では QLDB (2025年に廃止)。
- **Aurora I/O-Optimized**: より高いストレージとインスタンスのコスト、I/O ごとの課金なし。I/O コストが支配的なとき (書き込みの多い) に使う。標準 Aurora: より低いストレージコスト、I/O ごとに支払い。読み取りの多いものに使う。
- **Aurora Backtrack**: バックアップスナップショットから復元することなく、データベースをその場で特定の時点に巻き戻す。Aurora MySQL 互換のみで利用可能 — Aurora PostgreSQL には、答えはポイントインタイム復元 (新しいクラスターへ) または高速クローン。試験のシグナル: 「誤ってデータを削除、完全なバックアップを復元せずに素早く回復する必要」 + MySQL → Backtrack。
- **Aurora 高速データベースクローニング**: データベースサイズにかかわらず数分でのコピーオンライトのクローン。試験のシグナル: 「本番データのコピーに対して素早く安くテスト」 → クローン、スナップショット復元ではなく。

## 練習問題

**練習問題1 — 想起**

Aurora と標準の RDS 読み取りレプリカの違いを説明してください。なぜ Aurora のレプリケーションラグは通常より低いのですか?

*(ヒント: 重要な違いは共有ストレージ対データレプリケーションです。書き込みが到着したとき各レプリカが何をしなければならないかを考えてみてください。)*

**練習問題2 — SAA-C03 シナリオ**

*シナリオ*: あるソーシャルメディアプラットフォームの MySQL データベースが、増加するトラフィックのために高い読み取りレイテンシを経験しています。アプリケーションは読み取りが多いです (95% 読み取り、5% 書き込み)。チームは、トラフィックのスパイク中でも読み取りレイテンシが一貫していることを必要としています。最小限のダウンタイムでの自動フェイルオーバー (目標 RTO < 30秒) が必要です。データ量は予測不能に成長しています。

これらの要件を最も満たすデータベースソリューションはどれですか?

A) 5つの読み取りレプリカを持つ RDS MySQL Multi-AZ  
B) Aurora レプリカと Aurora Serverless v2 を持つ Aurora MySQL  
C) より大きなインスタンスタイプの RDS MySQL (垂直スケーリング)  
D) 読み取りキャッシュのための DynamoDB DAX を持つ DynamoDB

**ヒント1**: 「RTO < 30秒」 — どのサービスがこれを達成しますか? 各選択肢のフェイルオーバーのタイミングを確認してください。

**ヒント2**: 「スパイク中の一貫した読み取りレイテンシ」 — どのサービスのレプリカがほぼゼロのラグを持ち、どれが潜在的に秒のラグを持ちますか?

**ヒント3**: 「予測不能に成長するデータ量」 — どのサービスがストレージを自動スケールしますか?

**解答**: B

**説明**: Aurora レプリカを持つ Aurora MySQL は、負荷下での一貫した読み取り性能のために、ほぼゼロのレプリケーションラグ (秒ではなくミリ秒) を提供します。Aurora Serverless v2 は、過剰プロビジョニングなしでトラフィックのスパイク中にコンピュートを自動スケールします。Aurora のストレージはデータの成長とともに自動スケールします。Aurora のフェイルオーバー (レプリカの昇格) は30秒未満で完了します — RTO 要件を満たします。

**なぜ A ではないのか?** RDS Multi-AZ のフェイルオーバーは60〜120秒かかります — RTO < 30秒を満たしません。標準の RDS 読み取りレプリカのラグは負荷下で秒に達し得ます — 「一貫した」読み取りレイテンシを保証するのは難しいです。

**なぜ C ではないのか?** 垂直スケーリング (より大きなインスタンス) は容量を増やしますが、読み取り負荷を分散しません。データベースは読み取りの単一障害点のままです。

**なぜ D ではないのか?** DynamoDB は NoSQL です — MySQL から DynamoDB への移行はデータモデルとアプリケーションのクエリの再アーキテクチャを必要とし、それはこの性能改善タスクの範囲をはるかに超えます。

*SAA-C03 ドメイン: 高性能なアーキテクチャの設計 — タスク3.3*

**練習問題3 — アーキテクチャチャレンジ** *(オプション)*

Nimbus はグローバル展開を設計しています。東海岸、ドイツ、オーストラリアのレストランパートナーが、クロスリージョンのレイテンシなしに、自分の注文データを素早く見られるようにしたいと考えています。しかし、すべての書き込みは一貫性を維持するために単一の us-west-2 プライマリを通らなければなりません。

Aurora を使ってデータベースアーキテクチャを設計してください。Global Database をどう構成しますか — たとえば、us-east-1、eu-central-1、ap-southeast-2 のセカンダリクラスター? us-west-2 のプライマリがダウンしたらどうなりますか? 昇格のプロセスをどう扱いますか?

*(唯一の正解はありません。目標は、マルチリージョンのデータベース設計を練習することです。)*

## クレジット後シーン

レオは Serverless v2 を持つ Aurora に移行しました。

金曜のスパイクが来て、去りました。CPU は60% を超えませんでした。クエリのレイテンシは一貫したままでした。Aurora は負荷を処理するために自動的にスケールアップし、それからラッシュの後にスケールダウンしました。

「これは先週の金曜と比べていくらかかった?」と、月曜の朝トムが尋ねました。

レオは課金エクスプローラーを呼び出しました。「金曜は夕方のピークを通じて平均で約2.16ドル/時間。土曜の朝は0.24ドル/時間。」

トムは何も言いませんでした。

「古い構成は、負荷にかかわらず固定の0.47ドル/時間だった」とレオが付け加えました。

「つまり、スパイク中は以前より多く支払った」とトムが言いました。

「そうだ。でもオフピーク中は大幅に少ない。週全体の正味コストは低い。」

トムは計算しました。それからうなずきました。

「ここに教訓がある」と彼は言いました。「正しい問いは『これは安いか?』ではない。『これは私たちの実際の使用パターンにとって安いか?』だ。」

「それは」と、部屋の向こうからプリヤが言いました。「シニアエンジニアの本能よ。」

トムはそう描写されて少し驚いた様子でした。
