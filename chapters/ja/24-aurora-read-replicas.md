忙しい図書館を想像してみよう。1人の司書が本をチェックインし、パトロンからの質問に答える。図書館が人気になると、キューができる。解決策は、質問に答えるための司書を増員することだ。本のチェックインは元のデスクで行われる。これが読み取りレプリカだ：読み取りを処理する追加の容量を確保し、すべての書き込みは1つの権威的なソースを経由する。オーラは、すべての司書が同じ本を見、遅延なしでそれらを見るように、その棚システムの設計自体を再考する。

**読み取りレプリカ：読み取りトラフィックの分散**

ほとんどのWebアプリケーションでは、書き込みよりも読み取りのデータが圧倒的に多い。メニューを閲覧する顧客は、数十回のSELECTクエリを実行する。注文を出すには、いくつかのINSERT/UPDATEクエリを実行する。比率は通常10:1またはそれ以上だ。

**読み取りレプリカ**は、プライマリからのすべての書き込みのコピーを受信し、それらの書き込みをSELECTクエリ向けに利用できる追加のRDSインスタンスだ。

仕組みは以下の通り：

1. アプリケーションは書き込み（INSERT、UPDATE、DELETE）をプライマリデータベースに送信する
2. プライマリは、その変更を読み取りレプリカに非同期的に複製する
3. アプリケーションは読み取り（SELECT）を読み取りレプリカに分散する
4. 読み取りレプリカは負荷を共有する：各々は総読み取りトラフィックの割合を処理する

結果：プライマリデータベースは書き込み（オプションでいくつかの読み取りも）のみを処理する。読み取りレプリカは読み取りの負荷を処理する。読み取り/書き込み比率が10:1の場合、1つの読み取りレプリカを追加すると、プライマリの総負荷は約半分になる。

**重要な制限**: 複製は**非同期**だ。複製遅延がある：通常はミリ秒だが、負荷下では数秒になる可能性がある。レプリカからの読み取りは、プライマリよりもわずかに遅れたデータを見ることがある。メニューの閲覧、注文履歴の表示など、ほとんどの読み取り（読み取りレプリカ）には、これは許容範囲内だ。注文が本当に完了したのか？—プライマリから読み取る。

**読み取りレプリカ：詳細**

- プライマリRDSインスタンスあたり最大5つの読み取りレプリカを持つことができる
- 読み取りレプリカは同じ地域または異なる地域（クロスリージョンレプリカ）に配置できる
- 読み取りレプリカは自分自身で読み取りレプリカを持つことができる（チェーン化）
- 読み取りレプリカは別個のエンドポイントだ：アプリケーションは読み取りをレプリカエンドポイントに指示する必要がある
- 読み取りレプリカはスタンドアロンデータベースにプロモーションできる（DR用）

Nimbusの場合、レオは1つの読み取りレプリカを追加した。彼はアプリケーションを更新して：

- 書き込み操作 → プライマリエンドポイント
- メニューの閲覧、注文履歴 → レプリカエンドポイント

**Amazon Aurora: データベースエンジンの再考**

AuroraはAWSの独自の組み込み関係データベースエンジンで、MySQLおよびPostgreSQLと互換性がある。クラウドワークロードのために設計されており、リレーショナルデータベースのストレージ層の仕組みを再考している。

従来のRDS設定（MySQL、PostgreSQL）では、ストレージとコンピューティングが密接に結合されている。データベースエンジンがデータファイルを管理する。複製は、プライマリからレプリカへのデータをコピーする。レプリカは、すべての書き込み操作をプライマリから再実行する必要がある。

Auroraはストレージとコンピューティングを分離する。これは、3つの可用性ゾーンに6コピーで自動的にデータを複製する分散型、フォールトトレラントなストレージ層を使用する。データベースインスタンス（コンピューティング層）は、このストレージ層の上に配置される。

**これにより何が変わるか**:

**読み取りレプリカ**: オーラのレプリカはデータを複製する必要がない：すでに同じストレージ層を共有している。これにより、以下のことが可能になる：

- 通常のRDSの5個から最大15個の読み取りレプリカ
- 複製遅延は通常100ミリ秒（負荷下では秒）
- レプリカは30秒（通常のRDSの場合の数分）でプライマリにプロモーションできる

**フェイルオーバー**: レプリカがストレージを共有するため、フェイルオーバーは非常に高速です—プロモーションにはデータ転送は必要なく、書き込みの転送だけです。

**ストレージ**: Auroraは、ストレージを10GB単位で自動的にスケールし、最大128TBまでです。ストレージをあらかじめプロビジョニングする必要はありません。

**パフォーマンス**: Auroraは、標準のMySQLと標準のPostgreSQLに対して、同等のインスタンスタイプで5倍の処理スループット、3倍のパフォーマンスを主張しています。

**Auroraの価格：トムの質問**

「コストはいくらですか？」トムは尋ねました。

Auroraの価格はRDSとは異なります：

**インスタンス価格**: RDSインスタンスのタイプと同様の価格です。

**ストレージ価格**: 1か月あたりGBあたり0.10ドル（使用量に応じて自動的にスケールされ、使用量に応じて支払われます）。

**I/O価格**: Auroraは、ストレージへの読み書きリクエストごとに料金を請求します（読み書き）。書き込みが多いワークロードの場合、これは大幅に増加する可能性があります。

「待ってください」とトムは言いました。「I/Oの料金を個別に支払っているのですか？」

「Aurora Serverless v2とAurora I/O-Optimizedは、この価格モデルを変更します」とレオは言いました。「Aurora I/O-OptimizedはI/O料金は発生しませんが、インスタンスとストレージの価格は高くなります。I/O-ヘビーなワークロードに適しています。」

トムはトレードオフを検討しました。Nimbusは読み取りが多かった（メニュークエリが非常に多く、書き込みが少ない）ため、Aurora I/O-Optimizedの方が高くなる可能性があります。標準のAurora価格が適切かもしれません。

これは、シニアエンジニアが実際に検討するコストの決定です。ワークロードのI/Oパターンを知る必要があります。

**Aurora Serverless：インスタンスを気にせずにスケーリング**

**Aurora Serverless v2**は、データベースの負荷に応じてコンピューティング容量を自動的にスケーリングする構成です。db.r6g.largeのような固定インスタンスサイズを選択する代わりに、Aurora Capacity Units（ACU）で最小と最大容量を設定します。

Aurora Serverless v2：

- 負荷が増加すると数秒でスケールアップ
- 負荷が低下するとほぼゼロにスケールダウン
- コスト：1ACU時間あたり0.12ドル（ストレージとI/Oを含む）

可変のトラフィックを持つワークロード（Nimbusの金曜日のスパイクと月曜日の朝の静かな時間など）には、Serverless v2がオフピーク時にコストを削減し、事前プロビジョニングなしでピークを処理します。

「金曜日のスパイクの場合」とレオは言いました。「Auroraは自動的にスケールアップします。日曜日の朝にほとんど交通量がない場合、最小限の容量にスケールダウンします。」

「そして、使用している容量のみを支払うのです」とトムは言いました。

「その通りです」

トムは、まさに探していたものを発見した人の表情を浮かべていました。

**Aurora Global Database：マルチリージョン読み取り**

**Aurora Global Database**は、Auroraを複数のAWSリージョンに拡張します：

- **1つのプライマリリージョン**がすべての書き込みを処理
- **最大5つのセカンダリーリージョン**が通常1秒未満のレプリケーション遅延で読み取りを提供
- セカンダリーリージョンは、DRシナリオで<1分でプライマリリージョンにプロモーションされる
- 読み取りは、プライマリリージョンで処理され、セカンダリーリージョンで提供されます。

Nimbusのグローバル展開のため、Aurora Global Databaseは、ロンドンのレストランがEUリージョンの読み取りレプリカからローカルメニューをクエリし、すべての注文（書き込み）がUSプライマリリージョンで処理されるようにするのに役立ちます。

**RDS vs Aurora：どちらを選ぶべきか**

| 因子            | RDS (PostgreSQL/MySQL)        | Aurora                                                     |
|-------------------|-------------------------------|------------------------------------------------------------|
| コスト              | 小規模なワークロードの場合、低い | ベース価格は高いが、スケールが優れている                     |
| 互換性           | フル                          | MySQL/PostgreSQL互換（ただし、いくつかの違いがあります）       |
| 最大レプリカ      | 5                             | 15                                                         |
| レプリカ遅延       | 数秒                         | 通常<100ms                                             |
| ストレージ         | 固定プロビジョニング            | 128TBまで自動スケーリング                                   |
| フェイルオーバー時間 | 60-120秒                    | <30秒                                                |
| Serverlessオプション | 制限あり                       | Aurora Serverless v2                                       |
| 最適な用途        | 安定した予測可能なワークロード | 可変のトラフィック、高い読み取り量、高速なフェイルオーバーが必要 |

## 強みと限界

**Auroraの強み**:

- 標準のRDSよりも大幅に高速なフェイルオーバー
- 最小限の遅延で最大15の読み取りレプリカ
- 自動スケーリングストレージ
- 可変ワークロード向けのServerless v2
- マルチリージョン展開のためのGlobal Database

**Auroraの限界**:

- 小規模で安定したワークロードの場合、コストが高い
- I/O料金は、書き込みが多いワークロードの場合、大幅に増加する可能性がある（I/O-Optimizedを使用）
- MySQL/PostgreSQLとのわずかな互換性の違いにより、コードの変更が必要になる場合がある
- Serverless v2の冷機スタート（ほぼゼロから）により、レイテンシスパイクが発生する可能性がある

## 概要

- **Aurora レプリカ** は、プライマリからの読み取りトラフィックを分散します。 軽微な遅延が許容される非同期レプリケーションです。
- **Aurora** はストレージレイヤーを再構築します： 分散型、プライマリのレプリカ間で共有され、自動スケーリングされます。
- Aurora は以下の機能を提供します： 15 個の読み取りレプリカ、<100ms のレプリカ遅延、<30秒 のフェイルオーバー、最大 128TB の自動スケーリングストレージ。
- **Aurora Serverless v2**: 負荷に基づいてコンピューティング容量を自動的にスケーリングします。 変動するトラフィックに適しています。
- **Aurora グローバルデータベース**: 一つのリージョンにプライマリ、最大 5 つのリージョンに読み取りレプリカ。
- RDS を、より小さく、安定していて、予測可能なワークロードには選択してください。 スケーラビリティ、高速なフェイルオーバー、または変動するトラフィックの処理が必要な場合は、Aurora を選択してください。

## 試験のヒント

*SAA-C03 ドメイン： 高性能アーキテクチャの設計 (ドメイン 3、タスク 3.3)*

- **Aurora レプリカ vs RDS レプリカ**: Aurora レプリカはストレージを共有 (ほぼゼロの遅延、<30秒 のフェイルオーバー) し、RDS レプリカはデータを複製します (遅延が発生する可能性があり、フェイルオーバーには数分かかる)。
- **Aurora Serverless v2**: 「データベースのコンピューティング容量を自動的にスケーリングする」、「予測不可能またはスパイク型のデータベーストラフィック」、「ゼロにスケーリングする」→ Aurora Serverless v2。
- **Aurora グローバルデータベース**: 「マルチリージョンデータベース」、「EU から低レイテンシーで US プライマリから読み取る」、「RTO < 1 分鐘 の地域フェイルオーバー」→ Aurora グローバルデータベース。
- **フェイルオーバーのタイミング**: Aurora < 30 秒。 RDS Multi-AZ 60-120 秒。 両方を理解してください。
- **Aurora I/O-最適化**: より高いストレージとインスタンスコスト、I/O ごとの課金はありません。 I/O コストが支配的 (書き込みが多い) 場合に使用します。 標準 Aurora: より低いストレージコスト、I/O ごとの課金。 読み込みが多い場合に使用します。
- **Aurora Backtrack**: バックアップのスナップショットから復元せずにデータベースを特定の時点にリワインドします。 MySQL 互換の Aurora のみで利用可能です。 試験のヒント：「誤ってデータを削除し、フルバックアップからの復元なしで迅速に回復する必要がある」。

## 練習問題

**練習問題 1 — 回想**

Aurora と標準 RDS 読み取りレプリカの差は何ですか？ Aurora のレプリケーション遅延が通常、低いのはなぜですか？

*(ヒント： 重要な違いは共有ストレージとデータレプリケーションです。 各レプリカが書き込みが到着したときに何をするかを考えてください。)*

**練習問題 2 — 試験練習**

*シナリオ*: ソーシャルメディアプラットフォームの MySQL データベースが、増加するトラフィックにより読み取りレイテンシが経験しています。 アプリケーションは読み取りが中心 (読み取り 95%、書き込み 5%) です。 チームは、負荷下でも一貫した読み取りレイテンシを確保し、スパイク時の読み取りレイテンシを最小限に抑えることを目指しています (目標 RTO < 30 秒)。 データ量は予測不可能に増加しています。

これらの要件を満たすデータベースソリューションはどれですか？

A) RDS MySQL Multi-AZ と 5 個の読み取りレプリカ
B) Aurora MySQL と Aurora レプリカおよび Aurora Serverless v2
C) RDS MySQL とより大きなインスタンスタイプ (垂直スケーリング)
D) DynamoDB と DynamoDB DAX を使用した読み取りキャッシュ

**ヒント 1**: 「RTO < 30 秒」— どのサービスがこれを達成しますか？ オプションのフェイルオーバータイミングを確認してください。

**ヒント 2**: 「負荷下での一貫した読み取りレイテンシ」— どのサービスのレプリカがほぼゼロの遅延と、秒単位の遅延の可能性がありますか？

**ヒント 3**: 「予測不可能に増加するデータボリューム」— どのサービスがストレージを自動的にスケーリングしますか？

**答え**: B

**説明**: Aurora MySQL と Aurora レプリカは、ほぼゼロのレプリケーション遅延 (ミリ秒、秒ではない) で一貫した読み取りパフォーマンスを実現します。 Aurora Serverless v2 は、負荷に応じてコンピューティング容量を自動的にスケーリングします。 Aurora ストレージは、データが成長するにつれて自動的にスケーリングされます。 Aurora フェイルオーバー (レプリカのプロモーション) は、30 秒未満で完了し、RTO の要件を満たします。

**A が正しくない理由**: RDS Multi-AZ フェイルオーバーは 60-120 秒かかるため、RTO < 30 秒の要件を満たしません。 標準 RDS 読み取りレプリカの遅延は、負荷下で秒単位に達する可能性があります。 「一貫性のある」読み取りレイテンシを保証するのは難しいです。

**C が正しくない理由**: 垂直スケーリング (より大きなインスタンスタイプ) は容量を増やしますが、読み取り負荷を分散しません。 データベースは読み取りの単一障害点になります。

**D が正しくない理由**: DynamoDB は NoSQL です。 MySQL から DynamoDB にデータをモデル化し、アプリケーションクエリを再構築することは、このパフォーマンス改善タスクの範囲を超えています。
