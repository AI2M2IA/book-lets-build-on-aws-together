# Chapter 21: Shipping Containers for Code

1956年以前、貨物を船に積み込むことは、熟練を要する専門的な交渉でした。船ごとに船倉が異なっていました。港ごとにクレーンが異なっていました。運送業者ごとに、何がどこに行ったかを追跡するシステムが異なっていました。商品の木箱は、トラックから埠頭へ、船へ、埠頭へ、トラックへと、それぞれ異なる扱い方をする人々の連鎖を通って移動しました。貨物は失われました。貨物は損傷しました。同じ商品が二度出荷されると、両方とも扱い方が異なっていたために、異なる状態で到着しました。

ようやく誰かがそれを明確に問うたとき、答えはこうでした: コンテナを標準化せよ。あらゆる港で問題を解決しようとするな。一度、コンテナのレベルで解決せよ。中身だけでなく、箱ごと出荷せよ。

標準化された輸送コンテナは、単に出荷を速くしただけではありません。出荷を *予測可能* にしました。上海のコンテナの中身は、ロッテルダムに到着したときにまったく同じ状態でした — コンテナがあらゆる積み替え地点での変動からそれらを守ったからです。

それがまさにレオの抱えていたのと同じ問題でした。Nimbus の API は、あらゆる「港」で異なる形で「積み込まれて」いました: ステージングは本番とは異なる形でデプロイされ、インスタンス1はインスタンス3とは異なる形でデプロイされ、6週間の文書化されていない変更がフリートを予測不能にしていました。

コンテナはレオをより速い開発者にはしません。デプロイを予測可能にするのです。

コアの API はアイドルではありませんでした。それは Lambda には移れませんでした。しかし、別の問題を抱えていました: それを動かしている EC2 インスタンスが互いに分岐していたのです。

**コンテナとは何か**

「輸送コンテナのようなものと考えてくれ」とレオはマーカーを掴みながら言いました。「コンテナは、自分がどの船に乗っているかを気にしない。船は、コンテナの中に何があるかを気にしない。彼らは寸法とロック機構について合意した。それ以外のすべては箱の中だ。」

**コンテナ (container)** は、アプリケーションを、それが実行するために必要なすべてとともにパッケージ化する、軽量でポータブルなユニットです: ランタイム (Python 3.11、Node.js 20、Java 17)、ライブラリと依存関係、設定ファイル、そしてアプリケーションコードそのもの。

仮想マシン (オペレーティングシステムのカーネルを含む、コンピュータ全体をエミュレートする) とは異なり、コンテナは、他のすべてを分離したまま、ホスト OS のカーネルを共有します。これにより、コンテナは起動が速く (数秒、時にはミリ秒) 小さく (ギガバイトではなくメガバイト) なります。

最も人気のあるコンテナ技術は **Docker** です。Docker イメージは設計図 — アプリケーションとその環境のスナップショット — です。Docker コンテナは、そのイメージの実行中のインスタンスです。

重要な特性: **不変性 (immutability)**。今日ビルドされたイメージは、Docker をサポートする任意のホスト — ノートパソコン、EC2 インスタンス、別のデータセンターのサーバー — で同一に実行されます。環境は焼き込まれています。設定ドリフトは不可能です。

「つまり、EC2 インスタンスに何がインストールされているかを心配する代わりに」とレオが言いました。「すべてを持つイメージをビルドする。イメージはどこでも同じように動く。」

「それに、ローカルでテストする必要があれば、同じイメージを実行する」とプリヤが付け加えました。「もう『自分のマシンでは動く』はない。」

**Docker イメージのビルドと ECR へのプッシュ**

オーケストレーターがコンテナを管理できる前に、レオはそれをビルドし、ECS が取得できるどこかに保存しなければなりませんでした。

彼は Dockerfile を書きました:

```dockerfile
FROM python:3.11-slim

WORKDIR /app

COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

COPY . .

EXPOSE 8000
CMD ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8000"]
```

重要な行: `FROM python:3.11-slim`。Python 3.9 ではありません。3.10 でもありません。3.11 — チームが合意した特定のバージョンで、イメージに焼き込まれています。このイメージを実行するすべてのインスタンスは、まさに Python 3.11 を使います。decimal モジュールの丸めの動作は、どこでも同一になります。

彼はイメージをローカルでビルドしました: `docker build -t nimbus-api:1.0.0 .`

ビルドには4分かかりました。Docker はベースイメージを取得し、依存関係をインストールし、アプリケーションコードをコピーし、`nimbus-api:1.0.0` とタグ付けされたイメージを生成しました。

彼はそれをローカルで実行しました: `docker run -p 8000:8000 nimbus-api:1.0.0`

API が起動しました。本番サーバーと同じポート、同じ動作 — 環境が同一だったからです。

それから彼はそれを ECR にプッシュしました:

```bash
# Docker を ECR に認証する
aws ecr get-login-password --region us-west-2 |   docker login --username AWS --password-stdin   123456789012.dkr.ecr.us-west-2.amazonaws.com

# ECR 用にイメージをタグ付けする
docker tag nimbus-api:1.0.0   123456789012.dkr.ecr.us-west-2.amazonaws.com/nimbus-api:1.0.0

# プッシュ
docker push 123456789012.dkr.ecr.us-west-2.amazonaws.com/nimbus-api:1.0.0
```

プッシュには2分かかりました。ECR はイメージを保存し、ただちにイメージスキャンをトリガーし、5分以内に結果を報告しました。

**Amazon ECS: オーケストレーター**

1つのコンテナを実行するのは簡単です。複数のホストにまたがって何十ものコンテナを実行し、それらの間でトラフィックをルーティングし、失敗したコンテナを再起動し、ダウンタイムなしで新しいバージョンをデプロイすること — それには **オーケストレーター (orchestrator)** が必要です。

**Amazon ECS (Elastic Container Service)** は、AWS のマネージドコンテナオーケストレーションサービスです。次を定義します:

- **タスク定義 (Task definition)**: どのコンテナイメージを実行するか、どれだけの CPU とメモリを使うか、どの環境変数を使うか、どのポートを公開するか
- **サービス (Service)**: タスクのコピーをいくつ実行するか、障害とデプロイをどう扱うか
- **クラスター (Cluster)**: 基盤となるコンピュートインフラストラクチャ

ECS は残りを扱います: 利用可能な容量にタスクを配置し、失敗したタスクを再起動し、デプロイ中に接続をドレインし、健全なタスクをロードバランサーに登録します。

Nimbus では、API は手動で管理されるデプロイを持つ EC2 インスタンスから ECS に移りました。新しいデプロイのたびに、新しい Docker イメージが **Amazon ECR (Elastic Container Registry)** — AWS のマネージドコンテナレジストリ — にプッシュされ、ECS がそれをすべてのタスクにまたがってダウンタイムゼロでロールアウトしました。

**Fargate vs EC2 起動タイプ**

ECS はコンテナを2つのモードで実行できます:

**EC2 起動タイプ**: あなたが基盤となる EC2 インスタンスを管理します。インスタンスのパッチ適用、適切なサイジング、コンテナのための十分な容量の確保はあなたの責任です。より多くの制御、より多くの責任。

**Fargate (コンテナのためのサーバーレスコンピュート)**: AWS が基盤となるインフラストラクチャを完全に管理します。タスクごとの CPU とメモリを指定すると、Fargate が適切な容量を自動的にプロビジョニングします。管理する EC2 インスタンスはありません。vCPU 秒とメモリの GB 秒ごとに支払います。

Fargate は「サーバーレスコンテナ」モデルです — サーバーを管理せずに、コンテナの環境分離を得られます。トレードオフ: 基盤となるインスタンス設定に対する制御が少なく、単位あたりのコストがわずかに高いこと。

「それは月にいくらかかるんだ?」と、料金計算機を呼び出しながらトムが尋ねました。「Fargate 対 EC2 起動タイプ — 実際の数字が見たい。」

レオの直感的な見積もり — 誰もが持ち歩いているもの — は、Fargate のほうが高くつくだろう、というものでした。サーバーレスの利便性、プレミアム価格。彼は EC2 より20〜30%ほど高いかと推測しました。

「実際の数字を出せ」とトムが言いました。トムはそういう男だったからです。

Nimbus の API サービスは3つのタスクを実行し、それぞれが0.5 vCPU と1GB メモリを24時間365日必要としました:

**Fargate**: 0.04048ドル/vCPU 時間 × 0.5 × 3 × 720時間 = CPU で月43.72ドル。0.004445ドル/GB 時間 × 1 × 3 × 720 = メモリで月9.60ドル。合計: 月53.32ドル。

**EC2 起動タイプ** (3 × t3.medium、0.0416ドル/時間): 0.0416ドル × 3 × 720 = 月89.86ドル。

「待て」とトムが言いました。「Fargate のほうが安いのか?」

「このサイズでは、そうだ」とレオが言いました。「Fargate はあなたが割り当てたものちょうどに課金する。EC2 インスタンスにはオーバーヘッドがある — OS と ECS エージェントが、コンテナが起動する前にいくらかの CPU とメモリを消費する。t3.medium は2 vCPU と4GB を与えるが、コンテナあたり0.5 vCPU と1GB しか使っていない。残りは無駄だ。」

「でも EC2 起動タイプは、1つのインスタンスに複数のタスクを詰め込めるだろう。」

「そうだ。より大きな規模では、慎重なビンパッキングで、EC2 起動タイプのほうが安くなる。我々の規模 — 3つのタスク — では、Fargate が勝つ。」

トムはこれを書き留めました。

Nimbus の場合: API サービスには Fargate。彼らはコンテナのために EC2 インスタンスを管理したくありませんでした。

Fargate でコンテナ化すると、すべての EC2 管理オーバーヘッドを排除できます — しかし、インスタンスタイプをカスタマイズする能力を諦めることになり、それは GPU ワークロードや特殊なネットワーキングにとって重要です。AWS ネイティブなシンプルさのために ECS を選ぶと、緊密な IAM と ALB の統合を得られます — しかし、Kubernetes のエコシステムから締め出され、後でマルチクラウドの移植性が必要になった場合には再アーキテクチャが必要になります。

**Amazon EKS: Kubernetes が必要なとき**

**Kubernetes** はオープンソースのコンテナオーケストレーションシステムです — 本質的に、大規模なコンテナ管理の業界標準です。強力で、拡張可能で、複雑です。

**Amazon EKS (Elastic Kubernetes Service)** は、AWS のマネージド Kubernetes サービスです。Kubernetes のコントロールプレーン (管理層) をあなたのために実行し、あなたはワーカーノードを管理します (またはそれらにも Fargate を使います)。

Kubernetes が業界標準で、あらゆる求人にそれが言及されているなら、なぜそれを使わないのか、と疑問に思うかもしれません。なぜなら「業界標準」は、専任のプラットフォームチームを持つ大企業が使うものを表すからです。フードオーダーアプリを構築する6人のチームにとって、Kubernetes は、今のところ実際的な利益なしに運用上の複雑さを追加します。複雑さは現実のもので、利益はこの規模では理論上のものです。

Kubernetes は、ほとんどのチームが必要としないレベルの複雑さで価値を提供します: 内部プラットフォームを構築するためのカスタムリソース定義、高度なスケジューリング制約、きめ細かいデプロイ制御のためのポッド中断バジェット、数百のマイクロサービス間のトラフィック管理のためのサービスメッシュ統合。これらは本物の能力です。それらはまた、Nimbus の規模のスタートアップが決して行使しない能力でもあります。

ここでのエンジニアリングの原則は、ときに YAGNI と呼ばれます: You Aren't Gonna Need It (それは必要にならない)。ECS は Nimbus に、彼らが現在必要とするすべてを与えます。EKS は彼らに、必要とする以上のもの、加えて大きな学習曲線と運用上のオーバーヘッドを与えます。「あとで役に立つ」は、今複雑さを追加する良い理由ではありません。

EKS と ECS をいつ使うべきでしょうか?

**ECS を使う** のは:

- 主に AWS にいて、よりシンプルで AWS ネイティブな体験を望む場合
- チームに既存の Kubernetes の専門知識がない場合
- より少ない運用オーバーヘッドを望む場合

**EKS を使う** のは:

- Kubernetes 固有の機能 (カスタムリソース定義、Helm チャート、Kubernetes エコシステム) が必要な場合
- チームがすでに Kubernetes を知っている場合
- ハイブリッド環境 (一部オンプレミス、一部 AWS) を運用していて、一貫したオーケストレーション層を望む場合
- ワークロードに Kubernetes の拡張性に合致する要件がある場合

**コンテナのネットワーキング: 一時的な IP とサービスディスカバリ**

コンテナに移行するときにチームの不意を突くことのひとつ: コンテナの IP アドレスは、再起動するたびに変わります。

EC2 の世界では、インスタンスは比較的安定したプライベート IP を持っていました。設定ファイルにそれらをハードコードできました (すべきではありませんが)。サービスは互いを IP で知っていました。

コンテナの世界では、ECS の各タスクは起動時に VPC サブネットから IP を取得します。それが停止して新しいタスクが (デプロイや再起動の一部として) 起動すると、その新しいタスクは異なる IP を取得します。

「サービスが `10.0.1.45` を呼び出すようにハードコードされていて、そのコンテナが `10.0.1.82` に置き換えられたら何が起こるの?」とプリヤが尋ねました。「呼び出し側のサービスは、何もないところに当たり始める。」

これが、コンテナ環境でサービスディスカバリが重要な理由です。ECS + Application Load Balancer はこれを自動的に扱います: ALB の DNS 名は安定しています。ECS は健全なタスクをターゲットグループに登録します。ALB は現在健全な任意のタスクにルーティングします。呼び出し側のサービスは、個々のコンテナの IP ではなく、ALB の DNS 名と話します。

内部のサービス間通信 (ユーザー向けではない) には、**AWS Cloud Map** がサービスディスカバリを提供します: 各 ECS サービスは Cloud Map に登録し、安定した DNS 名を提供します。注文サービスは `http://notification.nimbus.local:8080` を呼び出し、Cloud Map がそれを通知サービスの現在健全な任意のタスクに解決します。

「つまりコンテナは、IP ではなく DNS 名を通じて互いと話す?」とレオが確認しました。

「そのとおり。IP は一時的だ。DNS 名が契約だ。」

**シークレットの注入: 環境変数にシークレットを置かない**

元の EC2 デプロイには、プリヤが何か月も指摘してきた問題がありました: シークレット (データベースパスワード、API キー、SES の認証情報) が、デプロイスクリプトで設定された EC2 インスタンス上の環境変数に保存されていたのです。

環境変数は、インスタンス上で動く任意のプロセスからアクセス可能です。それらはデバッグツール、一部のクラッシュレポート、プロセスリストに現れます。それらをログに記録すれば (一部の開発ツールはデフォルトでそうします) CloudWatch にも見えます。

コンテナはこれを自動的には解決しません — ECS のタスク定義で、依然としてシークレットを環境変数として渡せます。そして ECS のタスク定義は AWS コンソールに保存され、ECS アクセスを持つ誰にでも見えます。

正しいパターン: **AWS Secrets Manager + ECS タスク定義の統合**。

データベースパスワードをタスク定義に保存する代わりに:

```json
"secrets": [
  {
    "name": "DB_PASSWORD",
    "valueFrom": "arn:aws:secretsmanager:us-west-2:123456789012:secret:nimbus/prod/db-password"
  }
]
```

ECS はタスク起動時に Secrets Manager からシークレットを取得し、それを環境変数としてコンテナに注入します。シークレットの値はタスク定義に決して保存されません — Secrets Manager のシークレットの ARN だけです。コンテナは実行時に値を受け取ります。Secrets Manager は、タスク定義を変更せずに値をローテーションできます。

「それで、もし誰かがタスク定義を読んだら?」とプリヤが尋ねました。「Secrets Manager の ARN は見えるけど、値は見えない。」

「そして正しい IAM 権限がなければ」とレオが確認しました。「Secrets Manager から値を取得することもできない。」

「それが設計よ」とプリヤが言いました。「タスクの実行ロールは、その特定のシークレットを読む権限を持つ。それ以外は何も。タスク定義を侵害しても、得られるのは ARN であって、パスワードではない。」

「どっちを使うべき?」とマヤが尋ねました。「それに、なぜ Kubernetes じゃないの? あらゆる求人票にある。あらゆるカンファレンスのトークにも。」

「ECS だ」とプリヤがすぐに言いました。「私たちには Kubernetes の専門知識がない。ECS は私たちが必要とするすべてをこなす。今 Kubernetes を追加することは、実際的な利益なしに運用上の複雑さを追加することになる。」

前の会社で Kubernetes クラスターを運用していたスージンがうなずきました。「私はそのポケベルを背負っていた。必要になるまでは、それを持ちたくないわ。」

「ECS を使い切ったら、いつでも後で EKS に移行できる」とレオが付け加えました。

これは正しいシニアの答えです: 現在のニーズに合うよりシンプルなツールを選ぶこと。

**ECR: イメージのセキュリティ確保**

「それで、もし誰かが脆弱なベースイメージを通じて侵入しようとしたら?」とプリヤが尋ねました。「誰かが既知の CVE を持つ古いイメージを掴んで、それを使ってアプリケーションコンテナに足がかりを得る?」

それは、本番でコンテナをデプロイする前に問うべき正しい質問でした。

**Amazon ECR (Elastic Container Registry)** は、Docker イメージを保存し、デプロイ前にそれらを既知の脆弱性についてスキャンできます。ECR のイメージスキャンは、イメージを既知の CVE (Common Vulnerabilities and Exposures) のデータベースと照合し、問題を重大度ごとにフラグ付けします。

プリヤが書いたポリシー: CRITICAL 重大度の CVE を持つイメージは、本番にデプロイされない。CI/CD パイプラインは、ECS サービスを更新する前にスキャン結果をチェックします。重大な脆弱性が見つかれば、パイプラインは失敗し、チームに警告します。

「それはパラノイアではない」とプリヤが言いました。「デプロイする前にチェックを持っているだけよ。」

**コンテナがデプロイをどう変えるか**

コンテナの前は、Nimbus API の新しいバージョンをデプロイすることは、次を意味しました:

1. 各 EC2 インスタンスに SSH する
2. Git から最新のコードを取得する
3. 依存関係をインストール/更新する
4. アプリケーションプロセスを再起動する
5. ヘルスを検証する
6. 次のインスタンスに移る

これはエラーが起きやすく、遅いものでした。調整が必要でした。インスタンス4でステップ3が失敗すれば、一部のインスタンスが古いバージョンを動かし、一部が新しいバージョンの実行に失敗する、混在したデプロイになりました。

ECS とコンテナを使うと:

1. 新しい Docker イメージをビルドする (CI/CD パイプラインで自動化)
2. ECR にプッシュする
3. ECS サービスを新しいイメージのバージョンを使うように更新する

ECS はローリングデプロイを扱います: 新しいイメージで新しいタスクを起動し、それらが健全になるのを待ち、それから古いタスクを停止します。ダウンタイムゼロのデプロイ、自動化されています。

新しいバージョンがヘルスチェックに失敗すれば、ECS はデプロイを停止し、古いバージョンがトラフィックの処理を続けます。

**デプロイの最低限の設定: ヘルスチェック**

コンテナデプロイの安全性のすべては、ヘルスチェックが実際に機能することに依存します。

ECS は2種類のヘルスチェックを使います:

**コンテナレベルのヘルスチェック**: Dockerfile またはタスク定義で定義されます。コンテナ内で実行され、アプリケーションが応答していることを検証します。

```dockerfile
HEALTHCHECK --interval=30s --timeout=5s --retries=3   CMD curl -f http://localhost:8000/health || exit 1
```

**ALB ターゲットグループのヘルスチェック**: ロードバランサーが定期的にヘルスエンドポイントに HTTP リクエストを送ります。ヘルスチェックに失敗したタスクは、ターゲットグループから削除されます。

どちらのヘルスチェックも適切に設定されていなければ、ECS はすべてのタスクを健全とみなし — 停止せずに壊れたイメージをデプロイします。これは最も一般的なコンテナデプロイの間違いです。

「ヘルスチェックのエンドポイントが内部情報を漏らすことはある?」とプリヤが尋ねました。

`/health` のヘルスチェックエンドポイントは、`{"status": "ok"}` だけを返しました。バージョン番号なし、依存関係の状態なし、内部設定なし。ヘルス応答の中のあらゆる情報は、アプリケーションをマッピングする人に役立ち得ます。ヘルスエンドポイントは最小限に保ちます。

詳細な内部のヘルス状態 (データベース接続性、依存関係のチェック) には、別の認証された `/health/detail` エンドポイント — VPC 内からのみアクセス可能 — を使います。

**構造化ロギング: 実行中のコンテナへの唯一の窓**

EC2 では、何かがうまくいかなくなると SSH します。ログファイルを tail します。プロセステーブルを見ます。ディスク使用量を確認します。あちこち探ります。

コンテナには SSH がありません。コンテナは一時的です — それはクラスター内の任意のホストで動いている可能性があり、ヘルスチェックに失敗すれば ECS が警告なしに置き換えます。SSH しようと考える頃には、調べたかったコンテナはもはや存在しないかもしれません。

ログはコンテナ化された環境でのデバッグの便宜ではありません。それらは、何かが起きたことの唯一の証拠です。

「それで、もしコンテナが静かに失敗して、ログがなかったら?」と、コンテナのアーキテクチャレビュー中にプリヤが尋ねました。「タスクがコード1で終了して、終了する前にログが捕捉されていなければ、原因を決して知ることなく終わるかもしれない。」

これは仮定の話ではありません。それは最初のコンテナデプロイで、一貫して起こります。

正しいパターン: `awslogs` ログドライバーを使って、すべてのコンテナを構造化ログを **Amazon CloudWatch Logs** に送るように設定します。ECS が配送を自動的に扱います — インストールするログエージェントなし、必要なサイドカーコンテナなし。

タスク定義の中で:

```json
"logConfiguration": {
  "logDriver": "awslogs",
  "options": {
    "awslogs-group": "/ecs/nimbus-api",
    "awslogs-region": "us-west-2",
    "awslogs-stream-prefix": "ecs"
  }
}
```

コンテナ内で stdout または stderr に書き込まれたすべての行が捕捉され、タスク ID で整理されてロググループ `/ecs/nimbus-api` に送られます。ECS は各タスクに新しいログストリームを作成するので、失敗した特定のコンテナのログを — それが置き換えられた後でも — 見つけられます。

タスク実行ロールには、CloudWatch Logs に書き込む権限が必要です。それがなければ、ログドライバーは静かに失敗し、すべてのログ出力が失われます。

**構造化ログ vs プレーンテキスト**: プレーンテキストのログ (「Order 7741 placed」) には grep が必要です。構造化された JSON ログ (`{"event": "order_placed", "order_id": "7741", "restaurant_id": "47", "amount": 3200}`) は、SQL に似た構文を使って CloudWatch Logs Insights でクエリできます:

```
fields @timestamp, event, order_id, restaurant_id
| filter event = "order_placed"
| stats count(*) by restaurant_id
| sort count desc
| limit 10
```

そのクエリはロググループに対して直接実行されます。データベースなし。データパイプラインなし。ETL ジョブなし。答えは数秒でそこにあります。

これは第26章で構築するアナリティクスのデータレイクを置き換えるものではありません。それは運用上の問い — 「過去30分でレストラン47からの注文は何件?」 — に、Athena クエリを実行する時間がないインシデントのさなかに答えます。

**CloudWatch Container Insights**

**Container Insights** は、コンテナレベルのメトリクス — CPU、メモリ、ネットワーク I/O、ストレージ I/O — を ECS クラスター、サービス、タスクごとに収集し集約する CloudWatch の機能です。EC2 レベルのメトリクス (ホストの調子はどうか?) ではなく、タスクレベルのメトリクス (この特定の ECS サービスの調子はどうか?) を見られます。

ECS クラスターに1つの設定でそれを有効化します:

```bash
aws ecs update-cluster-settings \
  --cluster nimbus-production \
  --settings name=containerInsights,value=enabled
```

有効化後:

- サービスごとのダッシュボードが見えます: タスク数、CPU 使用率、メモリ使用率
- タスクレベルの CPU で (EC2 ホストの CPU ではなく、それはずっと粗いシグナルです) アラームを設定できます
- メモリのスパイクをログイベントと相関付けられます — タスクのメモリが14:22に95%まで上昇した。ログは、まさに14:21にレストラン47のメニューインポートからのインバウンドリクエストのスパイクを示している

「それは月にいくらかかるんだ?」とトムが尋ねました。

Container Insights は、それが生成するカスタムメトリクスとログストレージに課金します。Nimbus の規模 (3つのサービス、それぞれ3〜6タスク) では、これは約月12ドル — タスクレベルの運用上の可視性に対する妥当なトレードでした。

レオはその日のうちにそれを有効化しました。

タスクがヘルスチェックに失敗して ECS に置き換えられた最初のとき、Container Insights のダッシュボードがイベントを自動的に捕捉しました: タスク ID、開始時刻、失敗時刻、終了コード。そのタスクの CloudWatch ログストリームは、終了前の最後の40行の出力を保存していました — それは、新しいレストランパートナーからの不正な形式のメニュー JSON によってトリガーされた、捕捉されなかった例外を示していました。

Container Insights と構造化ロギングがなければ: エラー率の謎めいたスパイク、調査には失敗したタスクをもう動かしていないホストへの SSH が必要、45分の当て推量。

それらがあれば: CloudWatch ダッシュボードのログストリームへのリンク、正確な例外、レストラン ID、問題のフィールド — 5分未満で。

「SSH なし」と、事後分析をレビューしながらレオが言いました。「調査のためのダウンタイムなし。ログが仕事をした。」

「ログが仕事をするのは」とプリヤが言いました。「それらを捕捉するように設定した場合だけよ。」


**コンテナが間違った選択であるとき**

「待って — でも *なぜ* すべてをコンテナ化しないの?」とマヤが尋ねました。「コンテナがすべての設定ドリフトの問題を解決すると、今あなたが私を納得させたばかりよ。なぜ、すべてのサービスをコンテナとして動かさないの?」

それは、彼女が Lambda について尋ねたのと同じ質問でした。答えは似ていました。

コンテナは運用上の要件を追加します: コンテナレジストリ (ECR)、イメージをビルドしてプッシュする CI/CD パイプライン、オーケストレーター (ECS)、インスタンスレベルではなくタスクレベルの可視性のために設定された監視、そして Docker とイメージのバージョン管理を理解するチームが必要です。

すでに EC2 でうまく機能していて、安定していて、設定ドリフトに苦しんでいないサービスにとっては、それをコンテナ化するコストが利益を上回るかもしれません。

コンテナが間違った選択である具体的なケース:

**コンテナの移動性のために構築されていないステートフルなサービス**: コンテナ内のデータベースには、慎重な永続ボリュームの管理が必要です。コンテナでデータベースを動かすほとんどのチームは、この複雑さに遭遇したあと、最終的にそれらをマネージドサービス (RDS、ElastiCache) に戻します。

**特殊なハードウェア要件を持つサービス**: GPU ワークロード、特定のネットワークインターフェース設定、または FPGA ベースの処理には、特定のハードウェアを持つ EC2 インスタンスが必要です。コンテナはこれを変えません — 依然として EC2 起動タイプを使い、その上にコンテナを載せるだけで、コンテナの抽象化は利益なしに複雑さを追加します。

**非常に単純なスクリプトとジョブ**: 週に一度実行され、依存関係ドリフトの問題のない40行の Python スクリプト。これのために Docker、ECR、ECS タスク定義、CI/CD パイプラインを追加するのは不釣り合いです。Lambda のほうがシンプルです。単純な EC2 の cron ジョブのほうがさらにシンプルかもしれません。

「原則は」とレオが言いました。「いつもと同じだ: ツールを問題に合わせること。コンテナは設定ドリフトとデプロイの一貫性を解決する。その問題がなければ、コンテナは必要ない。」

## AWS Batch: 大規模ジョブのためのコンテナ

ECS と EKS は、長時間実行のサービス — 絶えず動き、リクエストを受け付け、トラフィックとともにスケールするアプリケーション — のために設計されています。しかし、一部のワークロードは異なります: それらは固定された時間だけ実行され、定義されたデータセットを処理し、それから停止します。数百のレストランの月末の請求書を生成する。機械学習のトレーニングジョブを実行する。夜間のアナリティクスのエクスポートを処理する。

これらのワークロードには、サービスは欲しくありません — ジョブが欲しいのです。

**AWS Batch** は、あらゆる規模でバッチコンピューティングジョブを実行するフルマネージドサービスです。ジョブを Docker コンテナ (ECS が使うのと同じコンテナフォーマット) として定義すると、Batch が残りを扱います: EC2 または Fargate のコンピュートをプロビジョニングし、ジョブをキューにスケジュールし、ジョブが到着すると容量をスケールアップし、終わるとゼロに戻します。

主要な概念:

- **ジョブ定義 (Job definition):** Docker コンテナ、リソース要件 (vCPU、メモリ)、実行するコマンド
- **ジョブキュー (Job queue):** 送信されたジョブが実行前に待つ場所。各キューは1つ以上のコンピュート環境に関連付けられます
- **コンピュート環境 (Compute environment):** 基盤となる EC2 または Fargate の容量。最大90%のコスト削減のためにスポットインスタンスを使えます — Batch が中断とリトライを自動的に扱います

「待って — でも *なぜ* 単に ECS タスクを実行する代わりに Batch を使うの?」とマヤが尋ねました。

「ECS サービスは常時オンだからだ」とレオが言いました。「それはリクエストを待つ。Batch ジョブは実行され、終了し、Batch がコンピュートをゼロに戻す。実行と実行の間は何も支払わない。」

トムが料金ページから顔を上げました。「それにスポットインスタンスは?」

「Batch はスポットで動ける。スポットインスタンスがジョブの途中で回収されても、Batch が自動的にリトライする。45分の請求ジョブにとっては、それで問題ない。」

**ECS/EKS との対比:** ECS/EKS はサービスを実行します — 常時オン、リクエスト駆動。Batch はジョブを実行します — 有限の時間、データ駆動、アイドル時にゼロまでスケール。

**Lambda との対比:** Lambda には15分のタイムアウトがあります。Batch ジョブは数時間または数日実行できます。

Nimbus のコンテキスト: 夜間の請求書生成ジョブは、数百のレストランパートナーに対して45分かかります。Lambda は15分でタイムアウトします。常時オンの ECS サービスは1日23時間お金を無駄にします。Batch はスポットインスタンスでジョブを実行し、38分で終え、1.20ドルかかり、シャットダウンします。

「古いスクリプトが終わるのを待っている間に買ったコーヒーより安い」とレオが言いました。

「それに管理する EC2 がない」とプリヤが付け加えました。「Batch がそれをプロビジョニングし、実行し、終了させる。」

## 強みと限界

**コンテナ**:

- 環境の不一致 (「自分のマシンでは動く」) を排除する
- 速く信頼性の高いデプロイを可能にする
- 不変 — 同じイメージがどこでも同一に動く
- 効率的 — VM より軽く、起動が速い

**ECS**:

- AWS 中心のワークロードには Kubernetes よりシンプル
- 緊密な AWS 統合 (IAM、ALB、CloudWatch、Secrets Manager)
- Fargate オプションが EC2 管理を完全に取り除く

**EKS**:

- 完全な Kubernetes 互換性 — エコシステム全体を使える
- ハイブリッド環境や Kubernetes の専門知識を持つチームに適している
- ECS よりセットアップと運用が複雑

**複雑になるところ**:

- コンテナイメージはビルドされバージョン管理されなければならない — CI/CD パイプラインが必要
- コンテナのデバッグには、従来のプロセスのデバッグとは異なるツールが必要
- ステートフルなコンテナ (コンテナ内のデータベース) には、慎重な永続ストレージの設定が必要
- コンテナ間のネットワーキング (サービス間通信) には、コンテナネットワーキングの概念の理解が必要

## 概要

Lambda はアイドルのコンピュートを無料にしました。コンテナはデプロイを決定論的にしました。両者は合わさって、成長するエンジニアリングチームにとって最も一般的な運用上の痛みの原因のうち2つを解決しました。

- **コンテナ** は、アプリケーションコード、ランタイム、依存関係を一緒にパッケージ化します — どこでも同一に動きます。
- **Docker** は標準的なコンテナ技術です。イメージは設計図、コンテナは実行中のインスタンスです。
- **ECR (Elastic Container Registry)** は AWS のマネージド Docker レジストリです — ここでイメージを保存、バージョン管理、スキャンします。デプロイ前に CVE を捕捉するためにイメージスキャンを有効化します。
- **ECS (Elastic Container Service)** はコンテナをオーケストレーションします。タスクとサービスを定義すると、ECS が配置とライフサイクルを管理します。
- **Fargate** はコンテナのためのサーバーレスコンピュートです — 管理する EC2 インスタンスがありません。EC2 オーバーヘッドの排除により、小規模では EC2 起動タイプよりしばしば安くなります。慎重なタスクのビンパッキングを伴う大規模では、EC2 起動タイプのほうがコスト効率が良くなることがあります。
- **EKS (Elastic Kubernetes Service)** はマネージド Kubernetes です — Kubernetes の機能や互換性が必要なチームのために。
- **Secrets Manager の統合**: タスク定義経由で起動時にシークレットをコンテナに注入します — 環境変数やタスク定義に直接シークレットの値を保存しないでください。
- **サービスディスカバリ**: コンテナの IP は一時的です。安定したサービスのアドレス指定には ALB の DNS 名や Cloud Map を使います。
- AWS でのシンプルさには ECS を選びます。Kubernetes エコシステムの互換性には EKS を選びます。

## 試験のヒント

*SAA-C03 ドメイン: 回復力のあるアーキテクチャの設計 (ドメイン2、タスク2.1)*

- **ECS vs EKS のシグナル**: 「Kubernetes」「Helm」「既存の Kubernetes の専門知識」「マルチクラウドのコンテナオーケストレーション」に言及する試験シナリオ → EKS。それ以外のすべて → ECS。
- **Fargate vs EC2 起動タイプ**: 「コンテナのために EC2 インスタンスを管理したくない」「サーバーレスコンテナ」「インフラ管理なし」 → Fargate。「特定のインスタンスタイプが必要」「GPU ワークロード」「きめ細かいインスタンス制御」 → EC2 起動タイプ。
- **タスクロール vs タスク実行ロール** — 実際の試験の識別ポイント。**タスク実行ロール (task execution role)** は、あなたのコードの前後で ECS の *エージェント* がタスクの代わりに使います: ECR からイメージを取得、Secrets Manager からシークレットを取得、CloudWatch にログを書き込む。**タスクロール (task role)** は、*コンテナ内のあなたのアプリケーションコード* が AWS サービスを呼び出すために使うものです: S3 から読み取り、DynamoDB に書き込む — EC2 インスタンスロールのようですが、タスクごとなので、各タスクが異なる権限を持てます。「コンテナが S3 から読み取る必要がある」 → **タスクロール** (タスク定義にアタッチ)。「タスクがイメージを取得できない / シークレットを取得できない」 → **実行ロール** に権限が不足。
- **Fargate Spot**: 障害耐性のあるコンテナを余剰容量で最大約70%オフで実行、2分間の中断警告付き — Fargate の EC2 スポット相当で、キャパシティプロバイダー経由で設定。試験のトリガー: 「インスタンスを管理せずに中断耐性のあるコンテナを最低コストで実行」 → Fargate Spot。
- **ECR イメージスキャン**: ECR はコンテナイメージを既知の脆弱性 (CVE) についてスキャンできます。試験のシグナル: 「コンテナをセキュリティ脆弱性についてスキャン」 → ECR イメージスキャン。
- **ブルー/グリーンデプロイ**: ECS は CodeDeploy 統合経由でブルー/グリーンデプロイをサポートします。自動ロールバック付きのダウンタイムゼロのデプロイ。試験パターン: 「自動ロールバック付きでダウンタイムなしにデプロイ」 → ECS + CodeDeploy ブルー/グリーン。
- **Secrets Manager の統合**: 試験のシグナル: 「タスク定義に値を保存せずにシークレットをコンテナに注入」 → Secrets Manager の ARN を参照するタスク定義の `secrets` フィールドを使います。タスク実行ロールには `secretsmanager:GetSecretValue` 権限が必要です。
- **ECS Service Auto Scaling**: CPU、メモリ、またはカスタムの CloudWatch メトリクスに基づいてタスクの数をスケールします。ALB と連携して、適切な数の実行中のタスクにトラフィックをルーティングします。
- **AWS Batch:** Docker コンテナのためのマネージドバッチコンピュート。ジョブキュー → コンピュート環境 (EC2 または Fargate、スポット対応)。使うとき: Lambda のタイムアウトが短すぎる、有限のジョブに ECS サービスは無駄。試験のトリガー: 「大規模なバッチ処理」または「数時間実行されるジョブ」 → AWS Batch。

## 練習問題

**練習問題1 — 想起**

Docker イメージと Docker コンテナの違いを説明してください。ECS と ECR の違いを説明してください。

*(ヒント: イメージとコンテナの関係は、レシピと調理された料理の関係のようなものです。ECR はイメージを保存し、ECS はそれらを実行します。)*

**練習問題2 — SAA-C03 シナリオ**

*シナリオ*: ある会社は、現在手動で管理されている EC2 インスタンス上で動くマイクロサービスアプリケーションを持っています。チームは一貫しないデプロイに苦しんでいます — 異なる EC2 インスタンスが異なるライブラリのバージョンを持ち、再現が難しいバグを引き起こしています。彼らは、基盤となるサーバーの管理の運用オーバーヘッドを最小限にしつつ、デプロイを標準化したいと考えています。チームには Kubernetes の経験がありません。

これらの要件を最も満たす解決策はどれですか?

A) アプリケーションを Docker でコンテナ化する。Fargate 起動タイプの Amazon ECS を使う  
B) インスタンスを一貫させるために AWS Systems Manager Patch Manager で EC2 にデプロイする  
C) アプリケーションを Docker でコンテナ化する。セルフマネージドのノードグループを持つ Amazon EKS を使う  
D) デプロイとインスタンス設定を自動的に管理するために AWS Elastic Beanstalk を使う

**ヒント1**: コンテナは「一貫しない環境」の問題を直接解決します。どの選択肢がコンテナを使いますか?

**ヒント2**: 「サーバー管理の運用オーバーヘッドを最小化」 → Fargate (EC2 管理なし) 対 セルフマネージドノード (依然として EC2 を管理)。

**ヒント3**: 「Kubernetes の経験がない」 → EKS は ECS より運用上の複雑さが大きい。

**解答**: A

**説明**: Docker でコンテナ化することで、すべてのデプロイが同じ依存関係を持つ同じイメージを使うことが保証され — 設定ドリフトを排除します。Fargate を使う ECS は、管理する EC2 インスタンスがないことを意味します。チームはサーバーのメンテナンスではなく、アプリケーションコードとコンテナ定義に集中します。(EKS ではなく) ECS は、Kubernetes の経験のないチームに適しています。

**なぜ B ではないのか?** Patch Manager は EC2 インスタンスを更新された状態に保ちますが、アプリケーション間のライブラリバージョンの不一致を解決しません。根本的な問題 (異なるインスタンス上の異なるコード環境) が残ります。

**なぜ C ではないのか?** セルフマネージドのノードグループを持つ EKS は、EC2 インスタンスの管理 *かつ* Kubernetes の学習を要求します。どちらも要件に合致しません。

**なぜ D ではないのか?** Elastic Beanstalk は EC2 上のアプリケーションデプロイを管理しますが、コンテナを使わない限り、根本的な環境の不一致を解決しません。Beanstalk はデフォルトでは Docker イメージを使いません (使うように設定はできますが)。

*SAA-C03 ドメイン: 回復力のあるアーキテクチャの設計 — タスク2.1*

**練習問題3 — アーキテクチャチャレンジ** *(オプション)*

Nimbus は、モノリシックな API を3つのマイクロサービスに分割しています: 注文サービス、メニューサービス、通知サービス。各サービスは異なるスケーリング要件を持ちます (注文サービスはトラフィックとともにスケールする。メニューサービスはほぼ読み取り専用で安定している。通知サービスは急増するバーストを持つ)。

これら3つのサービスのための ECS アーキテクチャを設計してください。サービス間通信をどう扱いますか? 1つの ECS クラスターを使いますか、それとも3つを? 各サービスに対して Auto Scaling をどう異なる形で設定しますか?

考えてみてください: メニューサービスは読み取りが多く、60秒間古いデータを提供できるかもしれません — その前にキャッシュを追加しますか? 通知サービスは金曜の夕方に激しくバーストスケールします — Fargate の最小容量を1、最大を20に設定しますか? スケールダウンのイベント中に進行中の通知はどうなりますか?

*(唯一の正解はありません。目標は、ECS でのマイクロサービスアーキテクチャを練習することです。)*

## クレジット後シーン

最初のコンテナデプロイは完璧でした。

API の新しいバージョン: ダウンタイムゼロ。ECS がそれをロールアウトし、ヘルスチェックが成功し、古いタスクがドレインされ、新しいタスクが引き継ぎました。レオは信じられないという気持ちに近いものを抱えて、コンソールでタスクのステータスを見守りました。

「ただ動いた」と彼は言いました。

「先週、あなたは手動の SSH デプロイについて同じことを言ったわ、インスタンス3で失敗する前にね」とプリヤが言いました。

「もうデプロイした — あ。」レオは止まりました。「イメージのバージョンをタグ付けせずにデプロイした。それを直させてくれ。」

「それが要点よ」とプリヤが言いました。「イメージのバージョン管理は、何が動いているかを追跡する方法なの。」

「今、本番にどのバージョンがあるか、どうやって分かるの?」とマヤが尋ねました。

レオは ECS コンソールを呼び出しました。実行中のタスクの下に、イメージが記載されていました: `123456789012.dkr.ecr.us-west-2.amazonaws.com/nimbus-api:1.0.3`。バージョン1.0.3。14:22 UTC にビルド。14:31 UTC にデプロイ。

「古い EC2 の構成では」とレオが言いました。「各依存関係のどのバージョンがインストールされているかを見るために、インスタンスに SSH して `pip show` を実行しなければならなかった。そしてそれは他のインスタンスでは違ったかもしれない。」

「それで今は?」

「イメージのタグが、何が動いているかを正確に教えてくれる。ECR のスキャン履歴が、それがスキャンされたかどうかを教えてくれる。ECS のデプロイ履歴が、それがいつデプロイされたか、前のバージョンが何だったかを教えてくれる。」

「SSH なし。ダウンタイムなし。『再起動を待て』なし。」

「イメージがデプロイの成果物だ」とプリヤが言いました。「環境は不変。デプロイのプロセスは宣言的。これがソフトウェアが出荷されるべきあり方よ。」

レオはもうしばらくコンソールを見つめました。

「僕は3年間 EC2 のデプロイを調整するのに費やした」と彼は言いました。「SSH スクリプトを調整して。デプロイのランブックを書いて。」

「あなたは問題を解決していたのよ」とプリヤが言いました。「コンテナが設計によって解決する問題をね。」

そのあと彼は何も言いませんでした。しかし翌朝、彼はコンテナのビルドプロセスについてのドキュメントを書き始めました。他の誰も、それを理解するのに3年を費やさなくて済むように。

インスタンス3のバグ、6週間の文書化されていないドリフト、そしてまだ捕まえていないそれに類する問題 — そのすべてが、単一の根本原因を持っていました。悪意ある行為者ではありません。ハードウェア障害ではありません。ただ、使い捨てのユニットではなく永続的な備品のように扱われてきたサーバーです。

コンテナはそれに対する答えでした。それが新しくて面白いからではありません。それが、その問いを問うことを不可能にしたからです。
