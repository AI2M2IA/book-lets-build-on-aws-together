**コンテナとは何か？**

**コンテナ**は、アプリケーションに必要なすべてをパッケージ化する軽量でポータブルなユニットです：実行時（Python 3.11、Node.js 20、Java 17）、ライブラリと依存関係、構成ファイル、アプリケーションコード自体です。

仮想マシン（オペレーティングシステムのカーネル全体をエミュレートする）とは異なり、コンテナはホストOSカーネルを共有しながら、それ以外のすべてを分離します。これにより、コンテナの起動が高速（数秒、場合によってはミリ秒）になり、サイズが小さく（メガバイトではなくギガバイト）、効率的になります。

最も一般的なコンテナ技術は **Docker** です。Docker イメージは、アプリケーションとその環境の設計図—スナップショットです。Docker コンテナは、そのイメージの実行インスタンスです。

重要な特性：**不変性**。今日作成されたイメージは、Docker をサポートするホスト上で同じように動作します—ラップトップ、EC2 インスタンス、別のデータセンターにあるサーバーなどです。環境が組み込まれています。構成ドリフトはありえません。

「EC2 インスタンスに何がインストールされているか心配する代わりに」とレオは言った、「すべてのものを備えたイメージを作成します。イメージは、どこでも同じように動作します。」

「そして、ローカルでテストする必要がある場合は、同じイメージを実行します」とプリヤは付け加えました。「『私のマシンで動く』という言葉をもう言う必要はありません。」

**Amazon ECS: オーケストレーター**

単一のコンテナを実行するのは簡単です。複数のホストにわたって複数のコンテナを実行し、トラフィックをルーティングし、失敗したコンテナを再起動し、ダウンタイムなしで新しいバージョンをデプロイする—そのためには、オーケストレーターが必要です。

**Amazon ECS (Elastic Container Service)** は、AWS の管理されたコンテナオーケストレーションサービスです。あなたは以下を定義します：

- **タスク定義**: 実行するコンテナイメージ、CPU とメモリの割り当て量、環境変数、公開するポート
- **サービス**: タスクのコピー数、障害とデプロイメントの処理方法
- **クラスタ**: 基になるコンピューティングインフラストラクチャ

ECS は残りのすべてを処理します：タスクを空いている容量に配置し、失敗したタスクを再起動し、ロードバランサーに健全なタスクを登録し、接続をデプロイ中にドレインします。

Nimbus の API は、手動で管理されたデプロイメントを持つ EC2 インスタンスから ECS に移行しました。新しいデプロイメントが新しい Docker イメージを **Amazon ECR (Elastic Container Registry)**—AWS の管理されたコンテナレジストリにプッシュし、ECS はゼロダウンタイムですべてのタスクにロールアウトしました。

**Fargate vs EC2 Launch Type**

ECS は、コンテナを 2 つのモードで実行できます：

**EC2 Launch Type**: 基になる EC2 インスタンスを管理します。インスタンスのパッチ適用、サイズ調整、コンテナに必要な容量の確保を担当します。より多くの制御、より多くの責任。

**Fargate (コンテナ用サーバーレスコンピューティング)**: 基になるインフラストラクチャを AWS が完全に管理します。タスクごとに CPU とメモリの割り当て量を指定します。Fargate は自動的に適切な容量をプロビジョニングします。EC2 インスタンスを管理する必要はありません。vCPU 秒あたりの支払いと、メモリの GB 秒あたりの支払いが発生します。

Fargate は「サーバーレスコンテナ」モデル—サーバーを管理することなく、コンテナの環境分離を取得します。トレードオフ：基になるインスタンス構成に対する制御の少なさ、およびわずかに高い単位あたりのコストです。

For Nimbus: Fargate を API サービスに使用します。EC2 インスタンスの管理を自分たちで行う必要はありませんでした。

**Amazon EKS: Kubernetes が必要な場合**

**Kubernetes** はオープンソースのコンテナオーケストレーションシステム—大規模なコンテナの管理における業界標準です。強力で拡張可能であり、複雑です。

**Amazon EKS (Elastic Kubernetes Service)** は、AWS のマネージド Kubernetes サービスです。Kubernetes コントロールプレーン (管理レイヤー) を AWS が実行し、あなたはワーカーノード (またはそれらにも Fargate を使用) を管理します。

EKS と ECS をどちらを使用すべきでしょうか？

**ECS を使用する場合:**

- 主に AWS 上にいて、よりシンプルで AWS ネイティブなエクスペリエンスを求める場合
- チームに Kubernetes の専門知識がない場合
- 運用負荷を軽減したい場合

**EKS を使用する場合:**

- Kubernetes 特有の機能 (カスタムリソース定義、Helm チャート、Kubernetes エコシステム) が必要な場合
- チームが Kubernetes の専門知識を持っている場合
- オンプレミス環境と AWS 環境を組み合わせて使用しており、一貫したオーケストレーション層が必要な場合
- ワークロードが Kubernetes の拡張性に合致する要件を持っている場合

「ECS だ」Priya はすぐに答えました。「私たちは Kubernetes の専門知識を持っていない。ECS が私たちが必要とするすべてを行う。今、Kubernetes を追加することは、実用的なメリットなしに運用複雑さを増すだけだ。」

**コンテナによるデプロイメントの変化**

コンテナが登場する以前、Nimbus API の新しいバージョンをデプロイするには、次のような手順が必要でした：

1. 各 EC2 インスタンスに SSH 接続
2. Git から最新のコードをプル
3. 依存関係をインストール/更新
4. アプリケーションプロセスを再起動
5. 健康状態を確認
6. 次のインスタンスに進む

これはエラーが発生しやすく、時間がかかりました。調整が必要でした。ステップ 3 がインスタンス 4 で失敗した場合、古いバージョンを実行しているインスタンスと、新しいバージョンを実行できないインスタンスが混在したデプロイメントになります。

ECS とコンテナを使用する場合：

1. 新しい Docker イメージをビルド (CI/CD パイプラインで自動化)
2. ECR にプッシュ
3. ECS サービスを新しいイメージバージョンを使用するように更新

ECS がロールイングデプロイメントを処理します：新しいイメージを使用してタスクを開始し、それらが正常に動作するのを待ち、古いタスクを停止します。ゼロダウンタイムデプロイメント、自動化されています。

新しいバージョンが健康チェックに失敗した場合、ECS はデプロイメントを停止し、古いバージョンがトラフィックを処理し続けます。

## 強みと限界

**コンテナ:**

- 環境の一貫性の問題 ("私のマシンで動作します") を解消
- 迅速で信頼性の高いデプロイメントを可能にする
- 不変性 - 同じイメージがどこでも同じように実行される
- 効率性 - VM よりも軽量で、起動が速い

**ECS:**

- Kubernetes よりも AWS 固有のワークロードに対してシンプル
- AWS との緊密な統合 (IAM、ALB、CloudWatch、Secrets Manager)
- Fargate オプションにより、EC2 管理を完全に排除

**EKS:**

- Kubernetes との完全な互換性 - 既存のエコシステムを使用
- Kubernetes の専門知識を持つチームや、ハイブリッド環境に適している
- ECS よりも設定と運用が複雑

**複雑になる場所:**

- コンテナイメージはビルドおよびバージョン管理する必要がある - CI/CD パイプラインが必要
- コンテナのデバッグには、従来のプロセスをデバッグするのに必要なツールとは異なるツールが必要
- ステートフルなコンテナ (コンテナ内のデータベース) を構成するには、注意深い永続ストレージ構成が必要
- コンテナ間のネットワーク (サービス間通信) を理解するには、コンテナネットワークの概念を理解する必要がある

## 概要

- **コンテナ** は、アプリケーションコード、ランタイム、依存関係を一緒にパッケージ化します - どこでも同じように実行されます。
- **Docker** は、標準的なコンテナ技術です。イメージは設計図であり、コンテナは実行インスタンスです。
- **ECR (Elastic Container Registry)** は、AWS のマネージド Docker レジストリ - イメージをここで保存およびバージョン管理します。
- **ECS (Elastic Container Service)** は、コンテナをオーケストレーションします。タスクとサービスを定義し、ECS が配置とライフサイクルを管理します。
- **Fargate** は、コンテナ用のサーバーレスコンピューティング - EC2 インスタンスを管理する必要はありません。
- **EKS (Elastic Kubernetes Service)** は、マネージド Kubernetes - Kubernetes の機能または互換性が必要なチームに使用します。
- 簡潔さを重視する場合は ECS を選択し、Kubernetes エコシステムとの互換性を重視する場合は EKS を選択してください。

## 試験のヒント

*SAA-C03 ドメイン: 堅牢なアーキテクチャの設計 (ドメイン 2、タスク 2.1)*

- **ECS と EKS のシグナル**: 「Kubernetes」、「Helm」、「既存の Kubernetes の専門知識」、または「マルチクラウドのコンテナオーケストレーション」というキーワードを含むシナリオ → EKS。すべての場合において ECS を使用。
- **Fargate と EC2 起動タイプ**: 「コンテナの管理に使用する EC2 インスタンスは不要」、「サーバーレスコンテナ」、「インフラストラクチャの管理は不要」→ Fargate。 「特定のインスタンスタイプが必要」、「GPU ワークロード」、「インスタンスの細かい制御が必要」→ EC2 起動タイプ。
- **ECS タスクの役割**: EC2 インスタンスの役割と同様に、ECS タスクにも IAM ロールがあります。 各タスクは異なる権限を持つことができます。 シナリオ例：「コンテナが S3 から読み取る必要がある」→ タスク定義に IAM ロールをアタッチします。
- **ECR イメージスキャン**: ECR は、コンテナイメージを既知の脆弱性 (CVE) についてスキャンできます。 シナリオ例：「コンテナのセキュリティ脆弱性をスキャンする」→ ECR イメージスキャン。
- **ブルー/グリーンデプロイメント**: ECS は CodeDeploy 統合を通じてブルー/グリーンデプロイメントをサポートします。 自動ロールバックによるゼロダウンタイムデプロイメント。 シナリオパターン：「ダウンタイムなしで自動ロールバックとともにデプロイする」→ ECS + CodeDeploy ブルー/グリーン。
- **ECS サービスオートスケーリング**: CPU、メモリ、または CloudWatch メトリックなどのカスタム値に基づいてタスクの数をスケーリングします。 ALB を使用して、実行中のタスクの数に応じてトラフィックをルーティングします。

## 練習問題

**練習問題 1 — 回想**

Docker イメージと Docker コンテナの違いを説明してください。 ECS と ECR の違いを説明してください。

*(ヒント: イメージは調理された料理のレシピであり、コンテナは料理そのものです。 ECR はイメージを保存し、ECS はそれを実行します。)*

**練習問題 2 — 試験練習**

*シナリオ*: マイクロサービスアプリケーションが現在 EC2 インスタンスで手動で管理されており、チームは不一致したデプロイメントに苦労しています。異なる EC2 インスタンスで異なるライブラリバージョンを使用しているため、再現困難なバグが発生します。 彼らはデプロイメントを標準化したいと考えていますが、その下層サーバーの管理オーバーヘッドを最小限に抑えたいと考えています。 彼らは Kubernetes の経験がありません。

これらの要件に最も適したソリューションはどれですか？

A) AWS Systems Manager Patch Manager を使用してインスタンスを一貫して維持し、EC2 でデプロイする。
B) アプリケーションを Docker でコンテナ化し、Amazon ECS と Fargate 起動タイプを使用する。
C) アプリケーションを Docker でコンテナ化し、Amazon EKS と自己管理されたノードグループを使用する。
D) AWS Elastic Beanstalk を使用してデプロイメントとインスタンス構成を自動的に管理する。

**ヒント 1**: コンテナは「不一致な環境」の問題を直接解決します。 どのオプションがコンテナを使用しますか？

**ヒント 2**: 「サーバーの管理オーバーヘッドを最小限に抑える」→ Fargate (EC2 インスタンスの管理なし) vs 自己管理されたノード (まだ EC2 インスタンスを管理します)。

**ヒント 3**: 「Kubernetes の経験がない」→ EKS は ECS よりも運用複雑さが高くなります。

**答え**: B

**説明**: Docker を使用してコンテナ化することで、同じイメージと依存関係を使用してすべてのデプロイメントが使用されるようにし、設定のずれを解消します。 Fargate と ECS を使用することで、EC2 インスタンスの管理が不要になります。 チームはアプリケーションコードとコンテナ定義に焦点を当て、サーバーのメンテナンスに焦点を当てません。 ECS (EKS ではない) は Kubernetes の経験がないチームに適しています。

**A が正しくない理由**: Patch Manager は EC2 インスタンスを更新しますが、アプリケーションの異なるライブラリバージョン間の設定のずれという根本的な問題を解決しません。

**C が正しくない理由**: EKS と自己管理されたノードグループを使用すると、EC2 インスタンスの管理 *と* Kubernetes の学習が必要です。 どちらも要件に合致しません。

**D が正しくない理由**: Elastic Beanstalk はアプリケーションのデプロイメントを EC2 で管理しますが、コンテナを使用しない限り、設定のずれという根本的な問題を解決しません。 Beanstalk はデフォルトでは Docker イメージを使用しません (構成で設定できます)。

*SAA-C03 ドメイン: 復元力のあるアーキテクチャの設計 — タスク 2.1*

**練習問題 3 — アーキテクチャチャレンジ** *(オプション)*

Nimbus は、API を注文サービス、メニューサービス、および通知サービスという 3 つのマイクロサービスに分割しています。 各サービスは異なるスケーリング要件を持ちます (注文サービスはトラフィックに応じてスケーリングされ、メニューサービスは主に読み取り専用で安定しており、通知サービスはスパイク状のバーストを持ちます)。

これらの 3 つのサービスに対して ECS アーキテクチャを設計してください。 サービス間の通信をどのように処理しますか？ 1 つの ECS クラスタを使用しますか、それとも 3 つのクラスタを使用しますか？ 各サービスに対してオートスケーリングをどのように構成しますか？

*(正解は 1 つではありません。 目的は ECS でマイクロサービスアーキテクチャを練習することです。)*
