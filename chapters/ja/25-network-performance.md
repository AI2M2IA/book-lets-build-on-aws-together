# Chapter 25: The Private Highway

少しの間、立ち上がってください。手を振りほどいてください。

あなたの指先と、国の反対側にある何かとの間の距離を感じてください。その距離を移動し、十数回のキャリアの引き継ぎを通り抜け、そしてあなたが作業を続けられる前に戻ってこなければならないメッセージを送ることを想像してください。今、それを1秒間に何千回もすることを想像してください。

それがデータ転送が実際に何であるかです — 物理的な距離、物理的なインフラストラクチャ、物理的な制約。

私たちはデータの移動について話します。AWS 内のサービス間ではなく、実世界と AWS の間 — あなたのオフィスとクラウドインフラストラクチャの間、大陸間 — の移動についてです。

---

データベースがスケールされ、ストレージコストが削減されたところで、トムはネットワーキングの請求に目を向けました。しかしレオには、より差し迫った問題がありました — 4テラバイトの過去の注文データを AWS に移すことが、彼らの現在の接続の限界を露呈していたのです。

---

Nimbus のインフラチーム (今は4人のエンジニア) は、シアトルの共有オフィスから働いていました。彼らは、自分たちが管理する AWS インフラストラクチャへのアクセスを必要としました。一部の操作には VPC のリソースへの接続が必要でした。

現在、彼らはノートパソコンの VPN を使ってパブリックサブネットの bastion ホストにアクセスし、そこからリソースに SSH していました。

それは機能しました。遅かったのです。VPN 接続はパブリックインターネット経由でルーティングされました: シアトル → 複数のキャリアホップ → us-west-2。往復は一貫していませんでした — 時間帯によって30〜80ミリ秒 — そしてスループットはオフィスのアップリンクとパブリックなパスによって制限されていました。

「日々の SSH には、それは許容できる」とレオが言いました。「でも、私たちはアナリティクスのデータベースを移し始めようとしている。4テラバイトの過去の注文データだ。この接続では、移行に何週間もかかる。」

「より良い接続が必要だ」とマヤが言いました。

「プライベートな接続」とプリヤが付け加えました。「パブリックインターネット経由ではなく。それに、もし誰かがデータ転送中に侵入しようとしたら? パブリックインターネット経由の4TB の注文履歴 — 暗号化されていても — 標的のように感じる。」

通勤のように考えてください。Site-to-Site VPN は公道を運転するようなものです: 車のドアをロック (暗号化) しますが、依然として他のみんなと車線を共有し、渋滞が予測不能に速度を落とします。Direct Connect は高速道路の専用のプライベートレーンを借りるようなものです — 共有トラフィックなし、一貫した速度、そしてより高い月の通行料。たいていの日は公道で問題ありません。タイトなスケジュールで貴重な貨物を満載したトラックを動かすときは、プライベートレーンに支払います。

Snow Family は、ほとんどの人が検討しない選択肢です: 実際の貨物便をチャーターすること。常に利用可能なわけではありません。小さな荷物には適切ではありません。しかし、満載のトラックには、運転するより速く到着し、高速道路の状況にまったく依存しません。物理は変わっていません — 依然として同じビットを動かしています — が、メカニズムは根本的に異なります。

**AWS Site-to-Site VPN: 手早い選択肢**

**AWS Site-to-Site VPN** は、あなたのオンプレミスネットワークと VPC の間に、パブリックインターネットを横断する暗号化されたトンネルを作成します。

セットアップ:

1. VPC にアタッチされた Virtual Private Gateway (VGW) を作成する
2. オンプレミスのルーターを表す Customer Gateway を作成する
3. それらの間に2つの VPN トンネルを (冗長性のために) 確立する

トラフィックは暗号化されます (AES-256)。それはパブリックインターネット経由で移動し、それはレイテンシがインターネットの状況に依存することを意味します。AWS は冗長性のために自動的に2つのトンネルを提供します — 1つのトンネルに問題があれば、トラフィックはもう一方にシフトします。

**Site-to-Site VPN を使うとき**:

- 手早いセットアップ (数分から数時間)
- 費用効率が高い (VPN 接続あたり0.05ドル/時間)
- 帯域幅: トンネルあたり最大1.25 Gbps
- ユースケースに許容できるインターネットレイテンシ

**Accelerated Site-to-Site VPN** は、VPN トラフィックをパブリックインターネットではなく AWS のグローバルネットワーク経由でルーティングします — Global Accelerator が提供するのと同じ最適化を VPN トンネルに適用したものです。レイテンシは標準の VPN より低く、より一貫しています。コストはわずかに高いです (Global Accelerator のデータ転送料金が適用されます)。VPN の手早いセットアップと低いコストを望むが、より良いレイテンシが必要なチームには、Accelerated VPN が標準の VPN と Direct Connect の間の実用的な中間の道です。

Nimbus の4TB の移行では、最大1.25 Gbps のインターネットベースの VPN は次の時間がかかります: 4TB / 1.25 Gbps ≈ 最低7時間、実世界のオーバーヘッドで12〜20時間に近づきます。許容できますが、パブリックインターネットのパスの混雑がそれを予測不能にします。

レオはより慎重に計算しました。なぜなら、理論的な計算と実際の転送時間が、彼の経験で一度も一致したことがなかったからです。

**理論値**: 4 TB = 4,096 GB = 32,768 Gb。1 Gbps で: 32,768秒 ≈ 9.1時間。9時間に丸めます。

**実際**: レオは前の週にテスト転送を実行していました — シアトルのオフィスから S3 へ50 GB。測定されたアップストリーム速度 (875 Mbps) での理論時間: 457秒。実際の時間: 724秒。オーバーヘッド係数: 1.58。

875 Mbps アップストリームでの4TB 転送に適用すると: 32,768 Gb / 0.875 Gbps × 1.58 オーバーヘッド ≈ **59,200秒 ≈ 16.4時間**。

オーバーヘッドはいくつかの源から来ました: 接続確立時の TCP スロースタート、再送を必要とするパケット損失 (シアトルから us-west-2 へのパブリックなパスは平均0.2% のパケット損失 — 小さいが、何百万ものパケットにわたって乗算的)、各マルチパートアップロードセグメントの HTTPS ハンドシェイクのオーバーヘッド、そしてマルチパートアップロードを組み立てる S3 の処理時間。

「16時間は一度きりの移行には問題ない」とレオが言いました。「本当の問題は、転送が14時間目に中断されたら、だ。」

S3 マルチパートアップロードは中断の問題を解決します: 転送が14時間目に失敗しても、現在のパートだけを再アップロードすればよいのです。以前のパーツは S3 に保存され、転送を再開できます。しかし、マルチパートアップロードの管理のオーバーヘッドが総転送時間におよそ3% を追加しました。

最終的な実世界の見積もり: **1 Gbps インターネットで理論値約9時間、実際は約17時間** — オフィスの875 Mbps の測定されたアップストリーム速度、パケット損失のオーバーヘッド、マルチパートアップロードの処理を考慮して。

レオはこれをしばらく考えました。それから彼は Snow Family の料金ページを見ました。

「他の選択肢は何だ?」とトムが尋ねました。

「待って — でも *なぜ* VPN より多くのものが必要なの?」とマヤが尋ねました。「4TB の移行は一度きりのイベントよ。」

「そうではない」とプリヤが言いました。「データが AWS に入ったら、チームは依然として毎日それにアクセスする必要がある。そして VPN のレイテンシは積み重なる。」

**AWS Direct Connect: 専用線**

**AWS Direct Connect** は、あなたの場所 (またはコロケーション施設) と AWS の間に、専用のプライベートなネットワーク接続を確立します。トラフィックがパブリックインターネットに触れることは決してありません。

Direct Connect は物理的な接続です — あなたのネットワークから AWS Direct Connect のロケーションへの光ファイバー線です。物理回線を確立するために通信プロバイダーと協力します。AWS は自分の側のポートを提供します。

**利点**:

- 一貫した、予測可能なレイテンシ (パブリックインターネットの変動なし)
- 50 Mbps から100 Gbps の速度 (2024年以降、特定のロケーションでネイティブの400 Gbps 専用ポート)
- インターネットより低いデータ転送コスト (Direct Connect のデータ転送料金は標準の AWS データ転送料金より安い)
- より安全 (プライベート回線、パブリックインターネットではない)

**トレードオフ**:

- セットアップに数週間から数か月かかる (物理インフラのプロビジョニング)
- VPN より大幅に高いコスト
- 組み込みの冗長性なし (冗長な回線は自分で確立する)
- 複数の回線なしでは地理的に分散したオフィスに適していない

Direct Connect が物理的な光ファイバーケーブルなら、誰かが誤ってそれを切断したらどうなるのか、と疑問に思うかもしれません。それが単一回線での単一障害点の問題です — だからこそ、本番の Direct Connect 構成は、地理的に分離されたパスの冗長な回線を使うか、バックアップとして VPN を維持します。ケーブルは切断され得ます。ビジネスは続きます。

「それは月にいくらかかるんだ?」とトムが尋ねました。彼はすでに調べていました。「専用の1Gbps ポートは月216ドルだ」と彼は言いました。「加えて私たちのオフィスからの回線で、通信業者が月800ドルと見積もった。」

「だから合計で月に約1,000ドル。」

Nimbus にとって: Direct Connect は現在の規模には過剰でした。しかし、significant なデータ転送量やプライベートなネットワーク接続のコンプライアンス要件を持つ企業にとっては、Direct Connect は元が取れます。

**ホスト接続: 中間の選択**

すべての組織が100 Gbps の専用光ファイバー回線にコミットできるわけではありません。**Direct Connect ホスト接続 (Hosted Connections)** は、AWS Direct Connect パートナー (承認された通信業者) が、他の顧客と共有する1Gbps 未満の接続をプロビジョニングできるようにします。

セットアップはより速く (数か月ではなく数日から数週間)、専用接続よりコストが低いです。トレードオフ: 共有容量は、より一貫しないスループットを意味します。

Nimbus にとって (成長するにつれて): パートナー経由のホスト型500 Mbps 接続は、妥当な価格でプライベートな接続性を提供します。

試験時に重要な実際的な違い: ホスト接続は、AWS パートナーによってプロビジョニングされ、50 Mbps から10 Gbps の速度で利用可能です (一部のパートナーは最大25 Gbps を提供)。専用接続は AWS に直接行き、1 Gbps、10 Gbps、100 Gbps で利用可能です (加えて特定のロケーションで400 Gbps)。1 Gbps 未満の速度には、ホスト接続が唯一の Direct Connect の選択肢です — 専用接続は最低1 Gbps から始まります。

**AWS Transit Gateway: VPC のためのハブアンドスポーク**

Nimbus が成長するにつれて、彼らは複数の VPC を蓄積するでしょう: 本番 VPC、ステージング VPC、アナリティクス VPC、セキュリティツーリング VPC。

慎重な計画なしには、これらの VPC を接続するには VPC ピアリング接続の完全なメッシュが必要です。4つの VPC には: 6つのピアリング接続。10の VPC には: 45のピアリング接続。20の VPC には: 190の接続。これはスケールしません。

**AWS Transit Gateway** は、複数の VPC とオンプレミスネットワークを接続するネットワークハブです。ピアリング接続のメッシュの代わりに、各 VPC が Transit Gateway に接続します。Transit Gateway がそれらの間でトラフィックをルーティングします。

```
オンプレミス ──── Direct Connect ──┐
                                  │
本番 VPC ──────────────────────── Transit Gateway
ステージング VPC ───────────────── Transit Gateway
アナリティクス VPC ─────────────── Transit Gateway
セキュリティ VPC ───────────────── Transit Gateway
```

**推移的ルーティング**: VPC A と VPC B が両方とも Transit Gateway に接続していれば、直接のピアなしで通信できます。Transit Gateway がルーティングを扱います。VPC ピアリング (推移的でない) とは異なり、Transit Gateway はハブアンドスポークのトポロジーを可能にします。

**Transit Gateway のコスト**: アタッチメント (VPC または VPN/Direct Connect 接続) ごと、加えて処理されたデータの GB ごとに課金されます。規模では、これはシンプルさに見合います。

Nimbus にとって、Transit Gateway のきっかけとなったイベントは4つ目の VPC の追加でした。彼らには: 本番、ステージング、アナリティクス、そして今やセキュリティツーリング (脆弱性スキャンと SOC2 コンプライアンス監視のための VPC で、本番と同じネットワークセグメント上にあるべきでない) がありました。

Transit Gateway なしでは、4つの VPC を接続するには6つのピアリング接続が必要です:
- 本番 ↔ ステージング
- 本番 ↔ アナリティクス
- 本番 ↔ セキュリティ
- ステージング ↔ アナリティクス
- ステージング ↔ セキュリティ
- アナリティクス ↔ セキュリティ

6つのピアリング接続、VPC ごとに6つのルートテーブルエントリ、レビューする6つのセキュリティグループルール。そして VPC ピアリングは非推移的です: 本番とアナリティクスがピアされ、アナリティクスとセキュリティがピアされていても、本番はアナリティクス VPC を通じてセキュリティに到達できません。本番 ↔ セキュリティのピアリングを明示的に必要とします。

Transit Gateway を使うと:

```
本番 VPC          ──┐
ステージング VPC   ──┤──── Transit Gateway ────── オンプレミス (Direct Connect)
アナリティクス VPC ──┤
セキュリティ VPC   ──┘
```

4つのアタッチメント。管理する1つのルートテーブル。推移的ルーティング: 本番は直接のピアなしで Transit Gateway を通じてセキュリティに到達できます。

「それで、もし誰かが Transit Gateway を通じて侵入しようとしたら?」とプリヤが尋ねました。「4つすべての VPC が Transit Gateway を共有していたら、ステージング VPC の侵害されたリソースが本番に到達できる。」

Transit Gateway は **分離のあるルートテーブル** をサポートします: Transit Gateway を通じてどの VPC が通信を許可され、どれが分離されるかを定義できます。セキュリティツーリング VPC は他のすべてに到達できます (それらをスキャンする必要があるため)。ステージングは本番に到達できません。本番はアナリティクスに直接到達できません (アナリティクスは特定の読み取り専用のエンドポイント経由でデータをクエリします)。

「1つの Transit Gateway」とプリヤが言いました。「実際のアクセスモデルを表現するルーティングポリシーを伴って。何が何に到達するかを監査する中央集権的な方法のない6つのピアリング接続に対して。」

**VPC エンドポイント: AWS サービスへのプライベートアクセス**

微妙なコストとセキュリティの問題: (プライベートサブネットの) EC2 インスタンスが S3 API を呼ぶとき、そのトラフィックは NAT Gateway 経由でルーティングされます (インターネットに到達するため。そこに S3 のパブリックエンドポイントがあります)。NAT Gateway の処理に支払います。

**VPC エンドポイント (VPC Endpoints)** は、VPC のリソースが AWS サービスとプライベートに — パブリックインターネット経由でなく、そして NAT Gateway なしで — 通信できるようにします。

2つのタイプ:

**ゲートウェイエンドポイント (Gateway endpoints)** (無料): S3 と DynamoDB のため。NAT Gateway の代わりに S3 や DynamoDB のトラフィックをエンドポイントに向けるルートをルートテーブルに追加します。作成無料。使用無料。

**インターフェースエンドポイント (Interface endpoints)** (有料): 他の AWS サービス (SQS、SNS、Secrets Manager、SSM など) のため。プライベート IP を持つ ENI (Elastic Network Interface) をサブネットに作成します。サービスへのトラフィックはこのプライベート IP を使います。AZ あたり約0.01ドル/時間 + データ処理がかかります。

レオは前の週にすでにゲートウェイエンドポイントを作成していましたが、ルートテーブルを更新していませんでした。「もうデプロイした — あ」と、設定を確認しながら彼は言いました。「ルートが更新されていなかった。それを直させてくれ。」

トムは、それらが無料だと知ってすぐに S3 と DynamoDB のゲートウェイエンドポイントを作成しました。NAT Gateway のデータ処理料金は65% 下がりました。

なぜかの計算: プライベートサブネットの Nimbus の Lambda 関数と ECS タスクは、S3 (設定ファイルの読み取り、ログエクスポートの書き込み) と DynamoDB (レストランデータの読み取り、注文記録の書き込み) に絶えずリクエストをしていました。各リクエストは NAT Gateway 経由でルーティングされ、それは処理されたデータの GB あたり0.045ドルを課金しました。

Nimbus の月の NAT Gateway データ処理: 533 GB。コスト: 月24ドル。S3 と DynamoDB のゲートウェイエンドポイントを追加してルートテーブルを更新したあと: S3 と DynamoDB のトラフィックは NAT Gateway を完全にバイパスしました。月の NAT Gateway 処理は187 GB に下がりました — 残りのトラフィックは他のサービス (Secrets Manager、SES、外部の Webhook) への API 呼び出しでした。コスト: 月8.40ドル。

節約: 月15.60ドル、年187ドル、セットアップに10分かかった2つの無料のゲートウェイエンドポイント設定に対して。

「無料」とトムが、3回目に言いました。

「ゲートウェイエンドポイントは作成も使用も無料だ」とレオが確認しました。「それらは単なるセキュリティの改善ではない — S3 と DynamoDB のトラフィックを NAT Gateway ではなくプライベートエンドポイント経由でルーティングすることが、それをパブリックインターネットから完全に取り除く。」

「それで、もし誰かが NAT Gateway のトラフィックを通じて侵入しようとしたら?」とプリヤが尋ねました。「S3 へのトラフィックが NAT を通るなら、それはインターネットからアドレス指定可能だ。ゲートウェイエンドポイント経由なら、それはプライベートだ。」

これは、コストの議論が時に覆い隠してしまうゲートウェイエンドポイントの二次的な利点です。VPC ゲートウェイエンドポイント経由の S3 と DynamoDB へのトラフィックは、AWS ネットワークを決して離れず、パブリック IP アドレスを決して横断せず、エンドポイントポリシー (エンドポイントがアクセスできる S3 バケットや DynamoDB テーブルを制限できるリソースベースのポリシー) によって統治されます。顧客データを保存するバケットのゲートウェイエンドポイントは、追加の層を加えます: バケットポリシーが設定ミスされていても、エンドポイントポリシーが特定の VPC 内から発信されたトラフィックにアクセスを制限できます。

**AWS Global Accelerator: エッジでのルーティング**

Nimbus が us-west-2 (オレゴン) から東海岸のユーザーにサービスを提供したとき、レイテンシは80ミリ秒でした。サーバーが法外に遠かったからではなく、ボストンとオレゴンの間のパブリックインターネットのルーティングが最適でなく、複数のキャリアネットワークを跳ね回っていたからです。

**AWS Global Accelerator** は、AWS のプライベートなグローバルバックボーン — パブリックインターネットのキャリアホップではなく AWS が制御するパスを通じてアプリケーションにトラフィックをルーティングするエッジロケーションの分散ネットワーク — を使います。パブリックインターネットのルーティングの代わりに、トラフィックは最も近いエッジロケーションで AWS のネットワークに入り、最適化されたプライベートなパスをアプリケーションまで移動します。

Nimbus にとって、ボストンのユーザーは:

- **Global Accelerator なし**: パブリックインターネットのキャリア経由でルーティング → 約80ミリ秒
- **Global Accelerator あり**: ボストンの最も近い AWS エッジに当たる → AWS バックボーンを移動 → us-west-2 に到達 → 約60ミリ秒

Global Accelerator はコンテンツをキャッシュしません (それは CloudFront です)。動的なリクエストのためのネットワークパスを最適化します。

レオは、Nimbus API に Global Accelerator を有効にしたあと、いくつかの都市にまたがってレイテンシの比較を実行しました:

| 都市 | 前 | 後 | 改善 |
|------|--------|-------|-------------|
| シアトル, WA | 12ms | 11ms | 8% |
| ロサンゼルス, CA | 28ms | 22ms | 21% |
| シカゴ, IL | 55ms | 40ms | 27% |
| ニューヨーク, NY | 82ms | 61ms | 26% |
| ロンドン, UK | 145ms | 112ms | 23% |
| 東京, 日本 | 180ms | 95ms | 47% |
| シドニー, オーストラリア | 210ms | 118ms | 44% |

改善は地理的に遠いユーザーで最も劇的でした — 東京は180ミリ秒から95ミリ秒、シドニーは210ミリ秒から118ミリ秒。シアトル (オレゴンの us-west-2 データセンターに近い) では、改善はより小さいものでした — 最適化するパブリックインターネットのホップが少なかったのです。

「待って — でも *なぜ* 東京は47% の改善を得ているの?」とマヤが尋ねました。「データセンターが依然として us-west-2 にあるなら、光の速度が実際の制約じゃないの?」

「光の速度は下限だ」とレオが言いました。「実際の制約はパブリックインターネットのルーティングだ。東京から us-west-2 へのトラフィックは何十もの自律システムを横断する — 異なるキャリア、異なるルーター、異なるピアリング協定。各ホップがレイテンシを追加する。Global Accelerator は、東京のエッジロケーションから us-west-2 へのトラフィックを AWS のプライベートな光ファイバー経由でルーティングする。それはより短いパスとよりよく調整されたルーティングを持つ。」

東京から us-west-2 への理論的最小値 (光ファイバー上の光の速度、往復およそ15,500 km に基づく): 約77ミリ秒。Global Accelerator での95ミリ秒は、その理論的最小値に近づいています。それなしの180ミリ秒は、物理法則ではなく、パブリックインターネットのルーティングの非効率を反映しています。

Global Accelerator は、最も近いエッジロケーションにルーティングする2つの静的な **エニーキャスト IP アドレス (anycast IP addresses)** を提供します。CloudFront (変化する動的な IP アドレスを使う) とは異なり、これらの IP は安定しています — ファイアウォールの許可リストや、クライアントが接続するために固定 IP を必要とするアプリケーションに役立ちます。

**Global Accelerator と CloudFront をいつ使うか**:

- CloudFront: 静的でキャッシュ可能なコンテンツ、CDN のユースケース
- Global Accelerator: 動的なコンテンツ、非 HTTP プロトコル (UDP、ゲーム、IoT)、または静的なエニーキャスト IP アドレスが必要なとき

## トラフィックだけでなくデータの移動: DataSync と Transfer Family

ネットワーキングのアーキテクチャが形を取りつつある間、マヤには3つの新しいレストランチェーンのオンボーディングプロジェクトが同時に降ってきました。それぞれにデータ移行の要件があり — そして各要件は異なっていました。

最初のチェーン、Pacific Table は、40 TB の NFS ファイル共有を S3 に移す必要がありました。彼らの現在のファイルストレージはオンプレミスで、シアトル本社の4つのファイルサーバーに分散していました。レオは移行計画を書き始めました。

2番目のチェーン、Marisol Group には、毎日請求書をローカルの SFTP サーバーにアップロードする経理チームがありました。その SFTP のワークフローは2015年から動いていました。経理スタッフは1つのことを知っていました: 毎朝9時に SFTP クライアントを開き、請求書をドロップし、それを閉じる。誰もこれを変えたくありませんでした。「彼らの経理担当者は WinSCP を使う」とマヤが言いました。「それは交渉の余地がない。」

「それは2つの異なるツールだ」とプリヤが言いました。

「そうだ」とレオが言いました。「でも両方とも存在する。」

**AWS DataSync: AWS コンソール付きのステロイドを打った rsync**

Pacific Table の40 TB の移行では、課題は帯域幅ではありませんでした — シアトルのオフィスには堅固なアップストリーム接続がありました。課題はオーケストレーションでした: どのファイルが存在するかを発見し、それらを信頼性高く転送し、チェックサムを検証し、営業時間中にオフィスのネットワークを飽和させないように転送をスケジュールし、数日間の継続的な操作にわたって進捗を監視すること。

**AWS DataSync** は、エージェントベースのデータ移行とレプリケーションのサービスです。オンプレミス環境に軽量な DataSync エージェント — VMware で動く、または EC2 インスタンスとして動く仮想マシン — をインストールします。エージェントは NFS または SMB 経由でファイルサーバーに接続し、共有を発見し、それらを AWS の宛先 — S3 バケット、EFS ファイルシステム、または FSx ファイルシステム — に同期します。

AWS コンソール付きのステロイドを打った rsync のように考えてください。DataSync は次を扱います:

- **発見**: エージェントがソースの共有を自動的にインベントリ化する
- **スケジューリング**: 転送は定義されたスケジュール (営業時間外) または継続的に実行できる
- **検証**: DataSync は両端でチェックサムを計算し、不整合を警告する
- **監視**: 転送の進捗、ファイル数、エラーレポート、帯域幅使用率がすべてコンソールで見える
- **転送中の暗号化**: すべてのデータは転送中に TLS を使って暗号化される

Pacific Table では、レオは彼らのシアトルのネットワークの VM に DataSync エージェントをインストールし、それを4つの NFS 共有に向け、転送スケジュールを設定しました: 平日は午後8時から午前6時、週末は継続的。6日後、すべての40 TB が S3 に着地しました。彼は DataSync の組み込みのチェックサムレポートで転送を検証しました。不一致ゼロ。

「それで継続的なレプリケーションは?」とマヤが尋ねました。「Pacific Table は移行後もまだファイルを追加する。」

「DataSync は増分転送をサポートする」とレオが言いました。「最初の同期のあと、変更されたものだけをコピーする。夜間のレプリケーションジョブとして実行できる。」

**AWS Transfer Family: S3 に支えられたあなたの SFTP ワークフロー**

Marisol Group の経理チームには、要件が異なりました。誰も SFTP から離れようとしていませんでした。経理担当者は WinSCP を使い続けるつもりでした。問いはこうでした: それらの SFTP アップロードはどこに着地するか?

現在、それらは Marisol のバックオフィスのローカルな Linux サーバーに着地していました。ファイルはその後、手動で彼らの経理システムに移されていました。ローカルサーバーは、メンテナンス、バックアップ、そしてそれを管理する SSH アクセスを持つ誰かを必要としました。

**AWS Transfer Family** は、S3 または EFS をストレージの宛先として支えられた、フルマネージドの SFTP、FTPS、FTP サーバーです。Transfer Family のエンドポイントをプロビジョニングします (それはホスト名と、オプションで静的 IP アドレスを得ます)。クライアントは既存の SFTP ソフトウェアを使ってそれに接続します。彼らがファイルをアップロードすると、それらのファイルは直接 S3 バケットに着地します。

経理チームは何も変えません。彼らは依然として毎朝9時に WinSCP を開きます。彼らは依然として既存の認証情報で SFTP サーバーに接続します。彼らは依然として同じフォルダに請求書をドロップします。違いは彼らには見えません: サーバー側では、ファイルはいまやローカルな Linux サーバーではなく直接 S3 に行きます。

「そして S3 から、私たちは残りのワークフローを自動的にトリガーできる」とプリヤが言いました。「S3 イベントが、請求書を処理して経理システムに挿入する Lambda 関数をトリガーする。手動のステップなし。」

「つまり経理担当者のワークフローは変わらない」とマヤが言いました。「でも私たちの側では、全体が自動化される。」

「そうだ。そして SFTP サーバー自体がフルマネージド — パッチ適用なし、バックアップなし、維持するサーバーなし。」

トムはすでに料金を調べていました。Transfer Family は、エンドポイントの可用性の時間ごと、加えて転送された GB ごとに課金します。Marisol Group の請求書量では、月のコストは30ドルを十分に下回りました。それが置き換えるローカルサーバーを維持するコスト — ハードウェアの減価償却、メンテナンスのためのエンジニアリング時間、バックアップ管理 — はかなり多いものでした。

---

> **試験のヒント — DataSync と Transfer Family**
>
> *SAA-C03 ドメイン: 高性能なアーキテクチャの設計 (ドメイン3、タスク3.1)*
>
> - **DataSync** = オンプレミスから AWS へのデータの一括移動 (NFS または SMB のファイル共有 → S3、EFS、または FSx)。試験のシグナル: 「ファイル共有を移行」「NFS データを S3 にレプリケート」「オンプレミスから AWS へのデータ転送」「ファイルデータの継続的なレプリケーション」。DataSync はオンプレミスにインストールされたエージェントを使います。エージェントが発見、スケジューリング、検証を扱います。
> - **Transfer Family** = クライアントツールを変えずに SFTP、FTPS、FTP プロトコルを使った継続的なファイル転送。試験のシグナル: 「既存の SFTP ワークフロー」「パートナーが SFTP 経由でファイルをアップロード」「S3 に支えられた SFTP サーバー」「SFTP のリフト・アンド・シフト」「ファイル転送プロセスを変更できない」。Transfer Family は、要件がデータ量ではなく SFTP 互換性のときの答えです。
> - **区別が重要**: DataSync は一括移行とレプリケーションのため (エージェントベース、スケジュール駆動、ネットワーク最適化)。Transfer Family はプロトコル互換のファイル転送サービスのため (エンドポイントベース、常時オン、クライアントに透過的)。それらは異なる問題を解決します。
> - DataSync は S3、EFS、FSx を宛先としてサポートします。Transfer Family は S3 と EFS をストレージのバックエンドとしてサポートします。

**ファイルだけでなくサーバーの移行: 7つの R と MGN**

マヤのパイプラインの3番目のチェーンには、ファイルだけでなく — 丸ごとのサーバーがありました: 移行前に誰も書き直したくなかった、2つのオンプレミスマシンで動くカスタムの予約アプリケーションです。*アプリケーション* を移動することはそれ自体の規律で、AWS は **7つの移行方法** (「7つの R」) を記述しています。それらはほとんど認識できればよいものです:

- **Rehost** (「リフト・アンド・シフト」): サーバーをそのまま移動する。最速、最小の変更。
- **Replatform** (「リフト、いじる、シフト」): 途中での小さなアップグレード — 自己管理のデータベースを RDS に移すような。
- **Repurchase**: 古いシステムを捨て、代わりに SaaS を買う。
- **Refactor**: クラウドネイティブに再設計する。最大の労力、最大の見返り。
- **Retire**: 結局誰も使っていなかった。削除する。
- **Retain**: 今のところ、あるところに残す。
- **Relocate**: 何も変えずにハイパーバイザーレベルで移動する。

リホストのケースでは、ツールは **AWS Application Migration Service (MGN)** です: エージェントがソースサーバーのディスクをブロック単位で、AWS の低コストのステージングエリアにレプリケートします。好きなときにテストコピーを起動します。カットオーバー時に、MGN はレプリケートされたサーバーをネイティブの EC2 インスタンスに変換します。リフト、シフト、完了 — リファクタリングは後で、クラウドの時間で行えます。(ポートフォリオ計画のための仲間である Application Discovery Service と Migration Hub は、2025年後半に新規顧客に閉じられました — 試験が言及したら、それらの名前を「インベントリ発見」と「中央集権的な移行追跡」として知っておいてください。)

**AWS Snow Family: 物理的な選択肢**

まだ4TB の過去のデータセットと17時間のインターネットの見積もりの問題がありました。それを計算したあと、レオは Snow Family の料金ページを見て、すぐに決断しました。

時間がシンプルさより重要な数テラバイトを超える移行には、AWS が物理的なストレージアプライアンスをあなたの場所に送ります。あなたはそれらをデータで満たします。あなたはそれらを送り返します。AWS はデータを直接 S3 に取り込みます。

**Snowball Edge Storage Optimized**: 80 TB の使用可能容量、堅牢な筐体。あなたの場所に2〜5営業日で出荷されます。ローカルインターフェース (NFS、S3 インターフェース) を使ってデータをロードします。あなたはそれを送り返します。AWS は受領後およそ1〜3営業日でデータを取り込みます。

Nimbus の4TB の移行のプロセス:

1. AWS コンソールを通じて Snowball Edge を **注文** する (2分かかり、3日で出荷)
2. アプライアンスをシアトルのオフィスネットワークに **接続** する。それは NFS マウントポイントとして現れる
3. デバイスの S3 互換インターフェースを使って4TB の過去の注文データを **コピー** する: `aws s3 cp /data/orders s3://nimbus-data/ --endpoint-url http://192.168.1.100:8080 --profile snowballEdge`
4. **コピーが完了** する。約2時間 (ローカルネットワーク、インターネットなし)
5. アプライアンスを AWS に **送り返す** (前払いのラベルが同梱)
6. AWS が受領後72時間以内にデータを S3 に **取り込む**
7. **検証** — S3 が、転送されたすべてのファイルとチェックサムを示すジョブ完了レポートを提供する

総経過時間: 配達に3日 + コピーに2時間 + 配送に1日 + 取り込みに2日 = およそ7暦日。継続的に約17時間に対して — それは安定した、中断のないインターネット接続を必要とし、一晩と営業日のほとんどを通じてオフィスのアップリンクを飽和させたでしょう。

コスト: Snowball Edge デバイスのレンタルは10日で300ドル。配送 (往復): 約80ドル。S3 へのデータ転送は無料。総移行コスト: **380ドル**。

約17時間の875 Mbps の持続的なインターネット使用と比較して: VPN トンネルは無料 (0.05ドル/時間だがトンネルはすでに動いていた)。S3 への転送は無料。「無料の」インターネットパスには、エンジニアリング時間 (17時間の転送の監視)、リスク (再起動を必要とするあらゆる中断)、機会費用 (転送ウィンドウ中にインターネット接続が飽和) における本物のコストがありました。レオは注文を出しました。それがどう展開したかは、この章のクレジット後シーンにあります。

## 強みと限界

**Site-to-Site VPN**:

- 手早いセットアップ、低コスト
- パブリックインターネットのパスは可変のレイテンシを意味する
- 限られた帯域幅の天井 (トンネルあたり1.25 Gbps)
- Accelerated VPN オプションがわずかに高いコストでレイテンシを改善する

**Direct Connect**:

- 一貫した、プライベートな、高帯域幅
- セットアップが遅い、significant な継続コスト
- 物理回線は単一障害点 (冗長性を追加するか VPN バックアップを維持する)
- 料金シナリオに応じて、おおよそ月10〜15 TB で egress コストの節約と損益分岐

**AWS Snow Family**:

- 1〜2 TB を超える一度きりの移行には、しばしばネットワーク転送より速く安い
- 移行中のインターネット帯域幅の消費なし
- 10日間のデバイスレンタルウィンドウ。前払いの配送

**Transit Gateway**:

- マルチ VPC の接続性を劇的に簡素化する
- 推移的ルーティング (VPC ピアリングとは異なり)
- 分離ルートテーブルが別個のピアリング接続なしにセグメンテーションを可能にする
- 多くのアタッチメントではコストが積み重なる

**VPC エンドポイント**:

- S3/DynamoDB のセキュリティとコストの利点 (無料のゲートウェイエンドポイント)
- AWS サービスのトラフィックの NAT Gateway コストを排除する
- エンドポイントポリシーが IAM とバケットポリシーを超えた追加のアクセス制御層を加える
- 他のサービス (Secrets Manager、SSM、SES) のインターフェースエンドポイントはトラフィックをプライベートに保つが AZ あたり約0.01ドル/時間かかる

**Global Accelerator**:

- グローバルユーザーの動的なアプリケーションのレイテンシを改善する: 遠いユーザーには実際に33〜47% の改善
- 固定のエニーキャスト IP (CloudFront の動的な IP とは異なり) — ファイアウォールの許可リストに役立つ
- 非 HTTP プロトコル (UDP、TCP) — CloudFront は HTTP/HTTPS のみ
- 追加コスト (アクセラレーターあたり0.025ドル/時間 + データ転送)

## 概要

第24章の Aurora の作業は、Nimbus が自分のアプリケーションにデータを提供する方法を最適化しました。この章は、データが外の世界と AWS の間でどう移動するか — そしてその移動をより信頼性高く、速く、安くする方法 — についてです。

- **Site-to-Site VPN**: オンプレミスと VPC の間のパブリックインターネット経由の暗号化されたトンネル。手早いセットアップ、低コスト、可変のレイテンシ。冗長性のための2つのトンネル。トンネルあたり最大1.25 Gbps。
- **Direct Connect**: AWS へのプライベートで専用の光ファイバー接続。予測可能なレイテンシ、より高い帯域幅、セットアップに数週間、significant なコスト。Nimbus の料金シナリオでは、VPN の egress 節約とおよそ月13.5 TB で損益分岐。
- **AWS Snow Family**: 一括データ移行のための物理ストレージアプライアンス。マルチ TB の移行ではインターネット転送より速い。Nimbus の4TB の移行に合計380ドル対 約17時間のネットワーク飽和。
- **Transit Gateway**: VPC とオンプレミスの接続性のためのハブ。推移的ルーティングを可能にする (VPC ピアリングとは異なり)。どの VPC がどれに到達できるかを制御する分離ルートテーブルをサポート。数百の接続にスケール。
- **VPC エンドポイント**: NAT Gateway なしの AWS サービスへのプライベートアクセス。ゲートウェイエンドポイント (S3、DynamoDB) は無料 — S3 や DynamoDB にアクセスするすべての VPC に追加します。Nimbus に月15.60ドルを節約し、S3/DynamoDB のトラフィックを NAT Gateway から取り除いた。
- **Global Accelerator**: 動的なトラフィックを AWS のプライベートバックボーン経由でルーティングし、グローバルにより低く、より一貫したレイテンシ。静的なエニーキャスト IP。遠いユーザーには33〜47% のレイテンシ改善 (東京: 180ms → 95ms、シドニー: 210ms → 118ms)。CDN ではない — キャッシュしない。
- **AWS DataSync**: オンプレミスの NFS/SMB のファイルデータを S3、EFS、FSx に移行しレプリケートするエージェントベースのサービス。スケジューリング、チェックサム検証、監視を扱う。一度きりの移行とファイル共有の継続的なレプリケーションに使われる。
- **AWS Transfer Family**: S3 または EFS に支えられたマネージドの SFTP、FTPS、FTP サーバー。既存の SFTP クライアントが、ワークフローを変えずにファイルを S3 にアップロードできるようにする。

## 試験のヒント

*SAA-C03 ドメイン: 高性能なアーキテクチャの設計 (ドメイン3、タスク3.4)*

- **VPN vs Direct Connect のシグナル**: VPN = 「VPC へのトラフィックを暗号化」「手早いセットアップ」「コストに敏感」。Direct Connect = 「一貫した低レイテンシ」「大きなデータ転送」「プライベートな接続」「プライベートネットワークを要求するコンプライアンス」。
- **Transit Gateway vs VPC ピアリング**: ピアリングは非推移的 (A→B→C は A→C を許可しない)。Transit Gateway は推移的。「通信する必要のある多くの VPC」 → Transit Gateway。
- **VPC ゲートウェイエンドポイント**: 無料。S3 と DynamoDB のみ。ルートテーブルの変更。追加コストなし。試験シナリオ: 「プライベートサブネットからの S3 アクセスのデータ転送コストを削減」 → ゲートウェイエンドポイント。
- **Global Accelerator vs CloudFront**: Accelerator = 動的なコンテンツ、非 HTTP、静的 IP、ネットワーク最適化。CloudFront = キャッシュ、HTTP コンテンツ、CDN。
- **Direct Connect + VPN**: VPN を Direct Connect 接続のバックアップとして使えます。Direct Connect 回線が失敗すると、トラフィックは VPN にフェイルオーバーします。VPN 単独より高価で、Direct Connect 単独より信頼性が高い。
- **Direct Connect Gateway**: Direct Connect 回線を、複数のリージョンやアカウントにまたがる複数の VPC に接続します。それなしでは、Direct Connect 回線は1つのリージョンの1つの VGW に接続します。
- **AWS Snow Family**: 「大きなデータ移行」「転送速度が遅すぎる」「ペタバイト規模の移行」 → Snow Family。Snowball Edge = 最大80TB。まず転送の計算をします: 利用可能なネットワーク経由でデータを移動するのにおおよそ1週間以上かかるなら、答えは物理デバイスです。*現実チェック (2026)*: AWS はファミリーを引退させてきました — Snowmobile は2024年に撤回され、Snowcone は2024年後半に廃止され、2025年11月時点で Snow デバイスは新規顧客に提供されなくなりました (AWS は今や高速リンク経由の DataSync と、自分のドライブを持ち込む安全な場所である **Data Transfer Terminals** を指しています)。SAA-C03 の問題バンクはこのすべてに先行するので、試験では「数週間のネットワーク転送、限られた帯域幅」は依然として Snowball を指します。
- **Transit Gateway のルートテーブル**: Transit Gateway はネットワークセグメンテーションのために複数のルートテーブルをサポートします。試験のシグナル: Transit Gateway 経由の共有接続性で「本番 VPC をステージングから分離」 → 別個のルートテーブル。
- **Global Accelerator の固定 IP**: CloudFront とは異なり、Global Accelerator は2つの静的なエニーキャスト IP を提供します。試験のシグナル: 「アプリケーションがクライアントが許可リストに入れる固定 IP アドレスを必要とする」または「UDP トラフィック」 → Global Accelerator (CloudFront は HTTP/HTTPS のみ)。
- **AWS DataSync のシグナル**: 「NFS/SMB のファイル共有を S3/EFS/FSx に移行」「オンプレミスのファイルデータの継続的なレプリケーション」「エージェントベースのファイル移行」。DataSync はプロトコル互換の SFTP 転送のためではありません — 一括ファイル共有の移行とレプリケーションのためです。
- **AWS Transfer Family のシグナル**: 「既存の SFTP ワークフロー」「パートナーや顧客が SFTP 経由でファイルをアップロード」「クライアントツールを変えずに SFTP サーバーをクラウドにリフト」「S3 に支えられた SFTP/FTPS/FTP」。Transfer Family はデータ移行ツールではありません — マネージドなプロトコルエンドポイントです。区別: DataSync はスケジュールでデータを一括移動します。Transfer Family は継続的なファイルアップロードのための常時オンの SFTP/FTP エンドポイントを提供します。
- **MGN (Application Migration Service)**: 「コード変更なしで何百もの VM を素早く移行」「サーバーを EC2 にリホスト / リフト・アンド・シフト」 → MGN (ブロックレベルのレプリケーション、テスト起動、ネイティブの EC2 インスタンスへのカットオーバー)。DataSync は *ファイル* を移動します。DMS は *データベース* を移動します。MGN は *丸ごとのサーバー* を移動します。

## 練習問題

**練習問題1 — 想起**

AWS Site-to-Site VPN と AWS Direct Connect の違いを説明してください。どんなシナリオでそれぞれを選びますか?

*(ヒント: セットアップ時間、コスト、レイテンシの一貫性、帯域幅の要件を考えてみてください。)*

**練習問題2 — SAA-C03 シナリオ**

*シナリオ*: ある金融サービス会社は、オンプレミスのデータセンターから AWS へのプライベートで暗号化された専用のネットワーク接続を必要としています。彼らは毎日500GB の機密の金融データを転送します。接続は一貫した、予測可能なレイテンシを持たなければならず、パブリックインターネットを横断してはなりません。彼らはまた、プライマリが失敗した場合のバックアップ接続も必要としています。

これらの要件を最も満たすアーキテクチャはどれですか?

A) BGP ルーティングを持つ Site-to-Site VPN と、冗長性のための2つ目の VPN  
B) Direct Connect Gateway を持つ Direct Connect ホスト接続  
C) 異なるインターネットプロバイダー経由の2つの Site-to-Site VPN 接続  
D) バックアップとして Site-to-Site VPN を持つ Direct Connect 接続

**ヒント1**: 「パブリックインターネットを横断してはならない」 — VPN トラフィックはパブリックインターネット経由で行きます (暗号化されて)。Direct Connect だけがプライベートです。

**ヒント2**: 「一貫した、予測可能なレイテンシ」 — パブリックインターネットの VPN 性能は変動します。Direct Connect は一貫しています。

**ヒント3**: 「バックアップ接続」 — Direct Connect がプライマリのとき推奨されるアプローチは何ですか?

**解答**: D

**説明**: Direct Connect は、パブリックインターネットを横断しないプライベートで専用の接続を提供します — プライバシーとレイテンシの要件を満たします。バックアップとしての Site-to-Site VPN が冗長性を提供します: Direct Connect 回線が失敗すると、トラフィックは暗号化された VPN にフェイルオーバーします。これが Direct Connect の標準的な HA パターンです。

**なぜ A ではないのか?** Site-to-Site VPN のトラフィックはパブリックインターネットを横断し、「パブリックインターネットを横断してはならない」要件に違反します。

**なぜ B ではないのか?** ホスト接続は Direct Connect 接続を提供しますが、選択肢 B はバックアップを含みません。バックアップなしの単一の Direct Connect は単一障害点です — 物理的な光ファイバーは切断され得ます。

**なぜ C ではないのか?** 異なる ISP 経由の2つの VPN 接続は、暗号化されていても、依然としてパブリックインターネットを横断します。プライベートネットワークの要件を満たしません。

*SAA-C03 ドメイン: 高性能なアーキテクチャの設計 — タスク3.4*

**練習問題3 — アーキテクチャチャレンジ** *(オプション)*

Nimbus は、シアトル、ベルリン、シンガポールに地域のエンジニアリングチームを持つように拡大しています。各地域のチームは次へのアクセスを必要とします:

- 本番 VPC (デバッグのための読み取り専用)
- ステージング VPC (テストのためのフルアクセス)
- アナリティクス VPC (レポートのための読み取り専用)

ネットワークの接続性を設計してください。Transit Gateway を使いますか? 各地域で Direct Connect、それとも Site-to-Site VPN? 本番の読み取り専用アクセスをどう強制しますか? (ヒント: これはネットワークと IAM の両方の問題です。)

*(唯一の正解はありません。目標は、マルチリージョン、マルチチームのネットワーク設計を練習することです。)*

**拡張**: ベルリンチームは、本番 VPC (us-west-2) への VPN レイテンシが平均160ミリ秒だと報告しています。どのデータ量で、Accelerated Site-to-Site VPN または Direct Connect ホスト接続がより良い選択肢になりますか? ヨーロッパの AWS パートナーからの現在の Direct Connect ホスト接続の料金を調べてください。あなたの見積もったデータ量で、レイテンシの改善だけがコストを正当化しますか?

## クレジット後シーン

データ移行は8暦日で完了しました — Snowball Edge の到着に3日、データのコピーに94分、AWS がデバイスを受け取りデータを取り込むのに4日、それから Snowball が輸送中に蓄積したデルタの最終同期。全体のハンズオン時間: 4時間未満。

その最後のステップが重要でした。Snowball Edge は4TB のデータセットのある時点のスナップショットをコピーしました。それが輸送中の間、本番データベースは動き続けていました — 新しい注文が行われ、新しいレコードが作成されていました。VPN 経由のデルタ同期は12GB で、18分で完了しました。

「一括転送が Snowball だった」とレオが言いました。「同期は、それがかかった8日間の純粋に新しいデータだけだった。」

「もうデプロイした — あ」と、94分後に Snowball Edge でコピーが完了するのを見ながらレオが言いました。「営業時間中にオフィスネットワークを飽和させないように、ローカルコピーに帯域幅スロットルを設定すべきだった。」

彼はスロットルを設定していませんでした。オフィスのインターネットは問題ありませんでした — Snowball はローカルネットワークの操作でした。しかし、コピーがローカルスループットで9 Gbps に近づくにつれて、ネットワークスイッチが一時的にボトルネックになりました。

「要点は」と、スロットルの設定を直したあと彼は言いました。「ある一定のデータ量を超えると、物理的な郵便がインターネットより速いということだ。」

「それは明白か、直感に反するかのどちらかね」とマヤが言いました。「どう考えるかによるけど。」

「次回は」とレオが言いました。「Direct Connect をセットアップすべきだ。」

トムは計算機に手を伸ばしませんでした — Direct Connect が最初に出てきたとき、彼はすでに計算を実行していました: 月に約1,000ドル、ポート + 回線。

「私たちが今やっていることには、たぶん見合わない。でも、オフィスと AWS の間で月10TB 以上を動かし始めたら、Direct Connect のデータ転送の節約がコストを相殺するだろう。」

「だからデータ転送量を監視して」とプリヤが言いました。「閾値を越えたら再検討する。」

「それがコスト意識のあるアーキテクチャだ」とトムが言いました。

「それがずっと要点だった」とマヤが言いました。

プリヤは部屋の向こうから移行を見守っていました。「次にこういうことをするとき」と彼女は言いました。「データが本番に入ってビジネスがそれに依存する前にできる? ライブデータを移行するのは、静止しているデータを移行するより常にリスクが高い。」
