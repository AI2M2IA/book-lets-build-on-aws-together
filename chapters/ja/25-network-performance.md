# 第25章：プライベート高速道路

立ち上がって、少し体を揺らしてください。手を伸ばして広げてください。

データ移動について話します。AWSのサービス間ではなく、AWSと現実世界の間、または大陸間での移動です。

Nimbusのインフラストラクチャチーム（現在は4名のエンジニア）は、シアトルにある共有オフィスで作業していました。彼らは管理していたAWSインフラストラクチャにアクセスする必要がありました。一部の運用では、VPC内のリソースへの接続が必要です。

現在、彼らはラップトップにVPNを接続して、パブリックサブネットのバッショングループにアクセスし、そこからSSHでリソースに接続していました。

うまくいきました。遅かったのですが、VPN接続はパブリックインターネットを介してルーティングされました：シアトル → 大陸横断ファイバー → 複数のキャリアホップ → us-east-1。片道は80ミリ秒以上でした。

「日常的なSSHには許容範囲です」とレオは言いました。「今、分析データベースの移行を開始します。4テラバイトの履歴データ注文。この接続では、移行には数週間かかるでしょう。」

「より良い接続が必要です」とマヤは言いました。

「パブリックインターネットを経由しないプライベート接続」とプリヤが付け加えました。

これは通勤に例えることができます。サイト・ツー・サイトVPNは、公共道路を運転するのと同じです：車（暗号化）のドアをロックしますが、他のすべての車両と車線（帯域幅）を共有し、交通渋滞が予測不能な速度で遅延を引き起こします。ダイレクトコネクトは、高速道路で専用のプライベートレーンをレンタルするのと同じです。通常、公共道は問題ありません。貴重な貨物をスケジュール通りに輸送する必要がある場合は、プライベートレーンを支払います。

**AWSサイト・ツー・サイトVPN：クイックなオプション**

**AWSサイト・ツー・サイトVPN**は、暗号化されたトンネルをオンプレミスネットワークとVPCの間に作成し、パブリックインターネットを介してルーティングします。

設定：

1. VPCにアタッチされたVGW（仮想プライベートゲートウェイ）を作成します。
2. オンプレミスルーターを表す顧客ゲートウェイを作成します。
3. 2つのVPNトンネル（冗長性のために）を確立します。

トラフィックは暗号化（AES-256）されます。パブリックインターネットを介して移動するため、レイテンシはインターネット条件に依存します。AWSは、問題が発生した場合に備えて、2つのトンネルを自動的に提供します。

**サイト・ツー・サイトVPNを使用するタイミング：**

- 設定が迅速（数時間）
- コスト効率が高い（VPN接続あたり0.05ドル/時間）
- 帯域幅：トンネルあたり最大1.25 Gbps
- 用途に適したインターネットレイテンシ

Nimbusの4TB移行の場合、最大1.25 GbpsのインターネットベースのVPNでは、実際のオーバーヘッドを考慮すると、最小7時間、現実的には12〜20時間かかる可能性があります。許容範囲ですが、パブリックインターネットパスの混雑により、予測不能になります。

「別のオプションは何ですか？」トムが尋ねました。

**AWSダイレクトコネクト：専用ライン**

**AWSダイレクトコネクト**は、あなたの場所（またはコローケーション施設）とAWS間の専用、プライベートネットワーク接続を確立します。トラフィックはパブリックインターネットを介して移動しません。

ダイレクトコネクトは物理接続です。ネットワークからAWSダイレクトコネクトの場所までの一本のファイバーラインです。あなたは、物理回路を確立するために、通信事業者と協力します。AWSが彼らの側でポートを提供します。

**利点：**

- 一貫性があり予測可能なレイテンシ（パブリックインターネットの変動なし）
- 50 Mbpsから100 Gbpsまでの速度
- インターネットよりもデータ転送コストが低い（ダイレクトコネクトデータ転送レートは、標準AWSデータ転送アウトレートよりも安価）
- より安全（パブリックインターネットではなく、プライベート回路）

**トレードオフ：**

- 設定には数週間から数か月かかる（物理インフラストラクチャのプロビジョニング）
- VPNよりも大幅にコストが高い（ポートあたり0.025〜0.30ドル/時間、および通信事業者回路コスト—通常は500〜1000ドル/月以上）
- 組み込みの冗長性がない（自分で冗長回路を確立する必要があります）
- 地理的に分散されたオフィスには適さない（複数の回路がない場合）

Nimbusの場合：彼らの現在のサイズでは、ダイレクトコネクトは過剰でした。しかし、大規模なデータ転送量や、プライベートネットワーク接続に関するコンプライアンス要件を持つエンタープライズでは、ダイレクトコネクトは費用対効果が高くなります。

**ホスト接続：中間地点**

すべての組織が100Gbpsの専用ファイバー回路をコミットできるわけではありません。**ダイレクトコネクトホスト接続**は、承認された通信事業者が提供する、1Gbps未満の接続を許可し、他の顧客と共有できます。

設定は迅速（数日〜数週間、数か月ではない）で、専用接続よりも安価です。トレードオフは、共有容量により、一貫したスループットが低下することです。

Nimbus（成長するにつれて）：パートナーを通じて500 Mbpsのホスト接続を使用すると、適切な価格でプライベート接続を提供します。

**AWSトランジットゲートウェイ：VPCのハブ・アンド・スポーク**

Nimbusが成長するにつれて、彼らは複数のVPCを収集することになります：生産VPC、ステージングVPC、分析VPC、セキュリティツールVPC。

注意深く計画しない場合、これらのVPCを接続するには、VPCピア接続のメッシュ全体を作成する必要があります。4つのVPCの場合：6つのピア接続。10つのVPCの場合：45つのピア接続。20つのVPCの場合：190つの接続。これはスケーラブルではありません。

**AWS Transit Gateway** は、複数の VPC とオンプレミスネットワークを接続するネットワークハブです。ペアリング接続のメッシュではなく、各 VPC は Transit Gateway に接続され、Transit Gateway がそれらの間のトラフィックをルーティングします。

```
On-premises ──── Direct Connect ──┐
                                  │
Production VPC ───────────────── Transit Gateway
Staging VPC ──────────────────── Transit Gateway
Analytics VPC ────────────────── Transit Gateway
Security VPC ─────────────────── Transit Gateway
```

**トランジティブルーティング**: VPC A と VPC B が Transit Gateway に接続している場合、両者は直接ピア接続なしで通信できます。Transit Gateway がルーティングを処理します。VPC ピアリング（トランジティブではないため）とは異なり、Transit Gateway はハブアンドスホークのトポロジーを可能にします。

**Transit Gateway の費用**: アタッチメント（VPC または VPN/Direct Connect 接続）ごとに課金され、処理されるデータ量（GB）ごとに課金されます。大規模になると、そのシンプルさのために費用は正当化されます。

**VPC エンドポイント：AWS サービスへのプライベートアクセス**

微妙な費用とセキュリティの問題：プライベートサブネットにある EC2 インスタンスが S3 API を呼び出す場合、そのトラフィックは NAT Gateway を通じてルーティングされ（インターネットに到達し、S3 のパブリックエンドポイントが存在する）、NAT Gateway の処理に対して費用が発生します。

**VPC エンドポイント** は、パブリックインターネットを経由せずに、VPC 内のリソースが AWS サービスとプライベートに通信できるようにし、NAT Gateway を必要としません。

2 種類があります。

**ゲートウェイエンドポイント**（無料）：S3 と DynamoDB 用。ルートテーブルに S3 または DynamoDB のトラフィックをエンドポイントにルーティングするルートを追加します。作成と使用の両方が無料です。

**インターフェースエンドポイント**（有料）：SQS、SNS、Secrets Manager、SSM などの他の AWS サービス用。サブネットに ENI（Elastic Network Interface）を作成し、その ENI にプライベート IP アドレスを割り当てます。サービスへのトラフィックはこのプライベート IP アドレスを使用します。1 時間あたり約 0.01 ドル、データ処理のコストがかかります。

トムは、それらが無料であるということを学んだ後、すぐに S3 と DynamoDB 用のゲートウェイエンドポイントを作成しました。NAT Gateway のデータ処理費用が 30% 削減されました。

**AWS グローバルアクセラレーター：エッジでのルーティング**

Nimbus が us-east-1（バージニア州）から西海岸ユーザーにサービスを提供していた場合、レイテンシは 80ms でした。サーバーが明らかに遠いからではなく、シアトルとバージニア州間のパブリックインターネットルーティングが最適ではなく、複数のキャリアネットワークを経由していたためです。

**AWS グローバルアクセラレーター** は、CloudFront と同じインフラストラクチャである AWS のプライベートバックボーンネットワークを使用して、ユーザーと AWS アプリケーション間のトラフィックをルーティングします。トラフィックは、最も近いエッジロケーションで AWS ネットワークに入り、最適化されたプライベートパスでアプリケーションに到達します。

Nimbus の場合、シアトルにいるユーザーは：

- **グローバルアクセラレーターなしの場合**: パブリックインターネットキャリアを経由 → ~80ms
- **グローバルアクセラレーターありの場合**: 最も近い AWS エッジ（シアトル）にヒット → AWS バックボーンを経由 → us-east-1 に到達 → ~45ms

グローバルアクセラレーターはコンテンツをキャッシュしません（CloudFront がその役割を担います）。これは、動的リクエストのネットワークパスを最適化することです。

**グローバルアクセラレーターと CloudFront の使い分け**:

- CloudFront: 静的でキャッシュ可能なコンテンツ、CDN 用のユースケース
- グローバルアクセラレーター: 非 HTTP プロトコル（UDP、ゲーム、IoT）、または静的な Anycast IP アドレスが必要な場合

## 強みと限界

**サイトツーサイト VPN**:

- 迅速な設定、低コスト
- パブリックインターネットパスにより、変動するレイテンシ
- 制限された帯域幅上限

**Direct Connect**:

- 一貫性があり、プライベートで、高帯域幅
- 設定が遅く、継続的なコストが高い
- 物理回路は単一障害点となりうる（冗長性を追加）

**Transit Gateway**:

- マルチ VPC 接続の簡素化
- トランジティブルーティング（VPC ピアリングとは異なり）
- 多数のアタッチメントにより費用が増加する可能性がある

**VPC エンドポイント**:

- S3/DynamoDB のセキュリティとコストメリット（無料のゲートウェイエンドポイント）
- NAT Gateway のコストを AWS サービスへのトラフィックに対して排除

**Global Accelerator**:

- グローバルユーザー向けの動的アプリケーションレイテンシを改善
- CloudFront の動的な IP アドレスとは異なり、固定の Anycast IP アドレス
- アクセラレーターあたり 0.025/時間 + データ転送のコスト

## 概要

- **サイトツーサイト VPN**: オンプレミス環境と VPC の間の暗号化されたトンネル。迅速な設定、低コスト、変動するレイテンシ。
- **Direct Connect**: AWS へのプライベート、専用のファイバー接続。予測可能なレイテンシ、高帯域幅、設定に数週間、継続的なコストが高い。
- **Transit Gateway**: VPC とオンプレミス接続のハブ。トランジティブルーティングを可能にします。数百もの接続をスケーリングできます。
- **VPC エンドポイント**: NAT Gateway を必要とせずに、AWS サービスへのプライベートアクセス。ゲートウェイエンドポイント（S3、DynamoDB）は無料です。
- **Global Accelerator**: グローバルでより低く、より一貫したレイテンシのために、AWS バックボーンを介して動的トラフィックをルーティングします。

## 試験のヒント

*SAA-C03 ドメイン：高パフォーマンスなアーキテクチャの設計（ドメイン 3、タスク 3.4）*

- **VPN と Direct Connect のシグナル**: VPN = 「トラフィックを VPC に暗号化する」、「クイックなセットアップ」、「コストに敏感」。Direct Connect = 「一貫した低レイテンシ」、「大規模なデータ転送」、「プライベート接続」、「コンプライアンス要件を満たすプライベートネットワーク」。
- **Transit Gateway と VPC Peering**: Peering は非トランジティブ (A→B→C が A→C を許可しない) です。Transit Gateway はトランジティブです。「多くの VPC が通信する必要がある」→ Transit Gateway。
- **VPC Gateway エンドポイント**: 無料。S3 と DynamoDB のみ。ルーティングテーブルの変更。追加費用はかかりません。シナリオ例: 「S3 へのアクセスにおけるデータ転送コストを削減するプライベートサブネット」→ Gateway エンドポイント。
- **Global Accelerator と CloudFront**: Accelerator = 動的コンテンツ、非 HTTP、静的 IP、ネットワーク最適化。CloudFront = キャッシュ、HTTP コンテンツ、CDN。
- **Direct Connect + VPN**: Direct Connect 接続のバックアップとして VPN を使用できます。Direct Connect 回線が失敗した場合、トラフィックが VPN にフェイルオーバーします。Direct Connect 単独よりもコストが高く、Direct Connect 単独よりも信頼性が高くなります。
- **Direct Connect Gateway**: Direct Connect 回線を複数のリージョンまたはアカウントにわたる複数の VPC に接続します。そうしないと、Direct Connect 回線は 1 つの VGW に 1 つのリージョンに接続されます。

## 練習問題

**練習問題 1 — 回想**

AWS Site-to-Site VPN と AWS Direct Connect の違いを説明してください。それぞれのシナリオでどちらを選択しますか？

*(ヒント: セットアップ時間、コスト、レイテンシの一貫性、帯域幅要件について考えてみてください。)*

**練習問題 2 — 試験練習**

*シナリオ*: 金融サービス会社が、オンプレミスのデータセンターから AWS へのプライベート、暗号化された、専用のネットワーク接続を必要としています。彼らは 1 日あたり 500GB の機密財務データを転送します。接続は一貫性があり予測可能なレイテンシを持ち、パブリックインターネットを通過してはなりません。また、プライマリが失敗した場合のバックアップ接続も必要です。

これらの要件を満たす最適なアーキテクチャはどれですか？

A) BGP ルーティングと冗長化のための 2 つ目の VPN を備えた Site-to-Site VPN
B) Direct Connect と、バックアップとして Site-to-Site VPN
C) 異なるインターネットプロバイダーから 2 つの Site-to-Site VPN 接続
D) Direct Connect Hosted Connection と Direct Connect Gateway

**ヒント 1**: 「パブリックインターネットを通過してはならない」→ VPN トラフィックはパブリックインターネットを通過します (暗号化されます)。Direct Connect のみですべてがプライベートです。

**ヒント 2**: 「一貫性があり予測可能なレイテンシ」→ パブリックインターネット VPN のパフォーマンスは変動します。Direct Connect は一貫性があります。

**ヒント 3**: 「バックアップ接続」→ Direct Connect がプライマリの場合、どのようなアプローチが推奨されますか？

**答え**: B

**説明**: Direct Connect は、パブリックインターネットを通過しないプライベート専用接続を提供し、プライバシーとレイテンシの要件を満たします。Site-to-Site VPN は、Direct Connect 回線が失敗した場合のバックアップとして、フェイルオーバーを提供します。これは Direct Connect の標準的な HA パターンです。

**A が正しくない理由**: Site-to-Site VPN トラフィックはパブリックインターネットを通過し、プライバシー要件を満たしません。

**C が正しくない理由**: 異なる ISP を通る 2 つの VPN 接続は、暗号化されてもパブリックインターネットを通過します。プライベートネットワークの要件を満たしません。

**D が正しくない理由**: Hosted Connection は Direct Connect 接続を提供しますが、オプション D にバックアップは含まれていません。単独の Direct Connect がない場合、ファイバーが切断されるため、単一障害点となります。
