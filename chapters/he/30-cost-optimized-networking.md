# פרק 30: העלות הנסתרת

ל-Tom היה לוח מחיק בחדר הישיבות עם שלוש עמודות: חישוב, אחסון, רשת. שתי הראשונות היו מלאות — מספרים, תאריכים, שמות של אופטימיזציות שהושלמו. הוא עמד מול הלוח רגע ארוך לפני שכתב משהו בעמודה השלישית. שורות הרשת בחשבון הענן התפזרו על פני הדף בצורה שהאחרות לא. לכל אחת היה שם שונה, יחידה שונה, הצדקה שונה לכך שכסף יוצא.

הוא הסיר את המכסה מהטוש.

ביקורת מסד הנתונים סגרה את פריט השורה הגדול האחרון ש-Tom עבד עליו באופן פעיל — $491/חודש שהוחזרו, $5,892 לשנה. הוסיפו את ה-EC2 Savings Plans, את מדיניות מחזור החיים של S3 ואת ניקוי האחסון, והסכום המצטבר עמד על $34,092 בחיסכון שנתי על פני שלושה חודשי עבודה. אבל Tom שם לב, במהלך הצלילה העמוקה למסדי הנתונים, שקטגוריה אחת בקושי נבדקה. עלויות אחסון הופיעו כשורה אחת: "S3: $198." עלויות חישוב הופיעו כשורה אחת: "EC2: $2,340" — לפני שהנחות ה-Savings Plan מפרק 27 נכנסו לתוקף. עלויות רשת התפזרו על פני תריסר פריטי שורה עם שמות כמו "Data Transfer Out," "NAT Gateway Processing," "VPC Peering Data Transfer," ו-"CloudFront Data Transfer." הוא מעולם לא חיבר אותם והסתכל על הסכום. זו הייתה העבודה של היום.

Tom פתח את החשבון. מצא את חלק העברת הנתונים. חיבר את כל פריטי השורה.

עלויות רשת ב-AWS הן כמו מערכת גביית אגרת הדרך של עיר: נסיעה לתוך העיר חינם, אבל כל מנהרה שאתה לוקח החוצה עולה כסף, ונסיעה בין שכונות עולה גם היא קצת. רוב האנשים לא חושבים על האגרות עד שהם מקבלים חשבון בסוף החודש ומבינים שהיו נוסעים במנהרה כל יום כשהיה כביש עילי חינמי לאורך כל הדרך. מטרת הפרק הזה היא להבין כל תא-גבייה — ולהחליט אילו מהם שווה לשלם.

$847/חודש.

"אנחנו מוציאים $847 לחודש על העברת נתונים," הוא אמר.

"זה הרבה?" שאל Leo.

"זה בדיוק כמו שהיה חשבון ה-S3 שלנו לפני שמיטבנו אותו. ואפילו לא ידעתי שיש לנו חשבון העברת נתונים בגודל כזה."

Maya הביטה לעברו. "מה זו בדיוק העברת נתונים?"

"זה מה ש-AWS גובה על הזזת בייטים. בייטים לתוך AWS: בדרך כלל חינם. בייטים שיוצאים מ-AWS לאינטרנט: בתשלום. בייטים בין שירותים באזורים שונים: בתשלום. בייטים שעוברים דרך NAT Gateway: בתשלום."

"אתה יכול לפרק את זה?"

Tom יכול היה. אבל הפעם הוא לא עצר בקונסולת החיוב. הוא הפעיל VPC Flow Logs בכל ה-VPCs שלהם והזין אותם ל-CloudWatch Logs Insights. זה אפשר לו לתשאל זרימות תעבורה בפועל — לא רק סכומי דולרים, אלא אילו מקורות שולחים נתונים לאן, וכמה.

השאילתה רצה שתי דקות. בשילוב עם מקור לוגים נוסף אחד שהוא ימשוך בקרוב, הפלט היה ספציפי מספיק כדי לפעול לפיו.

**ניתוח תעבורה: מה באמת מייצר את החשבון**

חמש זרימות התעבורה המובילות לפי נפח, לפי הסדר:

1. שרתי אפליקציה EC2 ← NAT Gateway ← שירותי AWS (SSM, Secrets Manager, CloudWatch, SQS): 3.9TB/חודש
2. שרתי אפליקציה EC2 ← NAT Gateway ← APIs חיצוניים: 1.3TB/חודש
3. נקודת הקצה של ה-reader של Aurora ← שרתי אפליקציה EC2 (בין-AZ): 0.4TB/חודש
4. צינור האנליטיקה ← bucket S3 ב-us-east-1 (בין-אזורי): 0.3TB/חודש
5. CloudFront ← מקור S3 (החטאות מטמון): 0.2TB/חודש

ארבע הזרימות הראשונות הגיעו ישירות מה-Flow Logs. החמישית לא יכלה להגיע משם: VPC Flow Logs רואים רק תעבורה שחוצה ממשקי רשת בתוך ה-VPCs שלך, והחטאת מטמון של CloudFront שמושכת מ-S3 לעולם לא נוגעת ב-VPC בכלל — זה CloudFront שמדבר ישירות עם S3. בשביל הזרימה הזו, Tom משך את לוגי הגישה הסטנדרטיים של CloudFront וסינן לפי השדה `x-edge-result-type`: כל רשומה שמסומנת `Miss` היא בקשה ש-CloudFront נאלץ למשוך מהמקור, וסכימת הבייטים נתנה לו את ה-0.2TB. חשבון אחד, שני מכשירי מדידה — כל אחד עיוור למה שהשני רואה.

"זרימה מספר ארבע," אמרה Priya. "למה צינור האנליטיקה שלנו מדבר עם bucket ב-us-east-1?"

ל-Leo הייתה הבעת פנים ש-Tom זיהה.

"כבר פרסתי את זה — אה," אמר Leo. "לפני שישה חודשים בדקתי אם צינור האנליטיקה שלנו יכול להתפצל לכמה אזורים במקביל. הקמתי bucket לבדיקה ב-us-east-1, כיוונתי אליו את הצינור, והרצתי אותו שבוע. הבדיקה הסתיימה אבל שכחתי להסיר את יעד ה-us-east-1 מתצורת הצינור."

"אז במשך חמישה חודשים," אמר Tom, "כתבנו עותק של כל תוצאת אנליטיקה ל-bucket בווירג'יניה."

"כמה זה עולה לחודש?" שאל Tom.

העברה בין-אזורית מ-us-west-2 ל-us-east-1: $0.02/GB. ‏300GB/חודש = $6/חודש על ההעברה. בנוסף, אחסון S3 לנתונים הכפולים ב-us-east-1: ‏300GB × ‏5 חודשים × $0.023/GB = $34.50 בנתונים מאוחסנים.

"לא ענק," אמר Leo.

"לא ענק לחודש," אמר Tom. "אבל זה רץ חמישה חודשים ואף אחד לא ידע. זו עלות לא מכוונת. השאלה היא לא אם $6 משנים — אלא אם אנחנו יודעים למה כל דולר מוצא."

Leo מחק את ה-bucket לבדיקה ב-us-east-1 והסיר את היעד מתצורת הצינור.

הממצא הניתן ביותר לפעולה בפלט ה-flow logs היה זרימה מספר אחת: שרתי אפליקציה EC2 שקוראים לשירותי AWS דרך ה-NAT Gateway.

Tom משך את רשומות הלוג הספציפיות לשאילתת ה-CloudWatch Logs Insights, מסוננות להציג רק תעבורה שמיועדת לטווחי ה-IP של שירותי AWS:

```
fields @timestamp, srcAddr, dstAddr, bytes, protocol
| filter dstAddr like "52.94." or dstAddr like "54.239." or dstAddr like "52.46."
| stats sum(bytes) as totalBytes by srcAddr, dstAddr
| sort totalBytes desc
| limit 20
```

הפלט הראה משהו שהוא לא ציפה לו: בערך 300 GB לחודש של תעבורת S3 באותו אזור — נפרדת מהזרימה הבין-אזורית ל-bucket של Leo ב-us-east-1 — עברה דרך ה-NAT Gateway. אבל Tom כבר הגדיר S3 Gateway Endpoints לפני חודשים.

"יש לנו S3 Gateway Endpoint," אמר Leo. "למה תעבורת S3 עדיין עוברת דרך NAT?"

Tom הסתכל על טבלת הניתוב. ה-Gateway Endpoint היה מוגדר — אבל רק ל-VPC של האפליקציה. צינור האנליטיקה רץ ב-VPC נפרד שנוצר לפני תשעה חודשים לצורך בידוד נתונים. ל-VPC הזה לא היה S3 Gateway Endpoint. כל קריאת S3 ממכונות ה-EC2 של צינור האנליטיקה נותבה דרך ה-NAT Gateway של אותו VPC.

"0.3TB של תעבורת צינור אנליטיקה × $0.045/GB = $13.50/חודש," אמר Tom. "רק מה-endpoint החסר ב-VPC השני."

"כמה יעלה להוסיף את ה-endpoint?" שאל Leo.

"אפס," אמר Tom. "S3 Gateway Endpoints הם חינמיים. זו רשומה בטבלת ניתוב."

הוספת ה-Gateway Endpoint ל-VPC של האנליטיקה תיקח ארבע דקות ותקצץ $13.50 מהחיוב החודשי של ה-NAT Gateway — מספר מוחלט קטן, אבל הממצא היה העיקרון. הם הוסיפו בקרת עלות ב-VPC אחד ושכחו לשכפל אותה כשיצרו את השני. עקביות דורשת תהליך, לא רק ידע.

Tom הוסיף לרשימת הבדיקה של הפריסות: כשיוצרים VPC חדש, יש להוסיף Gateway Endpoints ל-S3 ול-DynamoDB לפני חיבור עומסי עבודה כלשהם.

הממצא הספציפי השני מה-flow logs היה יקר יותר. תעבורה מפונקציות ה-Lambda שהריצו את מערכת התראות ההזמנות — גישת S3 לקריאת קובצי תצורה של מסעדות — עברה דרך NAT Gateway במקום דרך ה-endpoint של S3. פונקציות ה-Lambda רצו בתוך ה-VPC (לצורך גישה ל-RDS), וה-endpoint של S3 ב-VPC היה מוגדר רק למכונות EC2 בתת-הרשת של האפליקציה. פונקציות Lambda בתת-הרשת של Lambda נותבו דרך NAT.

"רגע — אבל *למה* שנעשה את זה ככה?" שאלה Maya. "יש לנו את ה-endpoint. למה Lambda לא משתמשת בו?"

"VPC Gateway Endpoints חלים לפי תת-רשת על בסיס טבלאות ניתוב," אמר Tom. "פונקציות ה-Lambda נמצאות בתת-רשת משלהן עם טבלת ניתוב משלהן. בטבלת הניתוב הזו לא היה מסלול ה-endpoint. הוספתי אותו לתת-הרשת של האפליקציה. פספסתי את תת-הרשת של Lambda."

הוספת מסלול ה-endpoint של S3 לטבלת הניתוב של תת-הרשת של Lambda תחסוך עוד $41/חודש בדמי עיבוד NAT Gateway שנגבו על קריאות S3 שהיו אמורות להיות חינמיות.

ניתוח ה-flow logs שילם את עצמו. שלוש שעות של שאילתות, שלושה ממצאים קונקרטיים: ה-endpoint הנשכח ב-VPC של האנליטיקה ($13.50/חודש), פער הניתוב בתת-הרשת של Lambda ($41/חודש), והממצא הגדול המקורי שהפך לבסיס להחלטות ה-Interface Endpoints. סך החיסכון החודשי הנוסף שזוהה בניתוח ה-flow logs: ‏$54.50, מעבר ל-$78 מ-Interface Endpoints שהניתוח כבר חשף. שני התיקונים הקטנים האלה נכנסו ל-backlog לספרינט הבא; טבלת החיסכון בסוף הפרק סופרת רק את מה שיושם בפועל.

"הלקח הוא ש-VPC endpoints אינם תצורה חד-פעמית," אמר Tom. "כל VPC חדש, כל תת-רשת חדשה, כל סוג חדש של עומס עבודה דורשים את אותה בדיקה. ברירת המחדל לכל דבר בתת-רשת פרטית היא לנתב דרך NAT. הבדיקה היא: האם עומס העבודה הזה קורא ל-S3, ל-DynamoDB או לאחד משירותי AWS עתירי התעבורה? אם כן, האם יש לו מסלול endpoint?"

"חשבנו על אוטומציה של הבדיקה הזו?" שאלה Priya. "כלל AWS Config שמתריע כשתת-רשת פרטית נוצרת בלי מסלול endpoint ל-S3?"

"זה ברשימה," אמר Tom. "מיד אחרי ההתראה על כרכים יתומים."

ועם זה, ל-Tom הייתה התשובה לשאלה שהתחילה את הניתוח. עלויות רשת לא היו בעיה אחת. הן היו חמש בעיות שונות, לכל אחת פתרון משלה.

**כיצד AWS גובה עבור העברת נתונים**

תמחור העברת הנתונים של AWS הוא אסימטרי:

**לתוך AWS (כניסה)**: חינם. אתה יכול להעלות כמה נתונים שתרצה.

**מחוץ ל-AWS לאינטרנט (יציאה)**: בתשלום. ‏100GB/חודש הראשונים חינם. לאחר מכן:

- $0.09/GB ל-10TB/חודש הראשונים (אזורי ארה"ב)
- $0.085/GB ל-40TB הבאים
- נמוך יותר בנפחים גבוהים יותר

**בתוך אותה Availability Zone**: חינם. מכונות EC2 שמדברות זו עם זו באותה AZ לא משלמות כלום.

**בין Availability Zones (אותו אזור)**: $0.01/GB בכל כיוון. עלות קטנה אבל אמיתית.

**בין אזורים**: $0.02-0.08/GB בהתאם לאזורים. תעבורה בין-אזורית יקרה משמעותית יותר.

**NAT Gateway**: $0.045/GB מעובד. כל בייט שמכונת ה-EC2 הפרטית שלך שולחת דרך ה-NAT Gateway כדי להגיע לאינטרנט — וכל בייט שחוזר — מחויב.

**CloudFront**: תעריפי העברת נתונים נמוכים יותר מ-AWS-ישירות-לאינטרנט. $0.085/GB ל-10TB הראשונים (קצת פחות מהעברת נתונים ישירה החוצה). CloudFront לרוב מפחית עלויות העברה כוללות מכיוון שמטמון הקצה שלו אומר שהמקור מגיש נתונים לעיתים רחוקות יותר.

**הפירוט של Tom**

"כמה זה עולה לחודש?" שאל Tom, על כל פריט שורה בתורו. הוא הוסיף אותם ללשונית נפרדת בגיליון — לא הסכום החודשי, אלא כל קטגוריה בנפרד. הסכום הכולל היה שימושי פחות מההבנה איזה חלק מהחשבון הוא איזה סוג של עלות.

לאחר סיווג כל פריט שורה:

**נתונים יוצאים לאינטרנט**: $214/חודש

- תגובות API ללקוחות ברחבי העולם
- נכסים שעדיין מוגשים ישירות מ-S3 ומה-ALB ללקוחות, תוך עקיפת CloudFront (מילויי המטמון עצמם — CloudFront שמושך ממקור AWS — חינמיים: AWS מוותרת על חיוב ההעברה ממקור ל-CloudFront)

**עיבוד NAT Gateway**: $289/חודש

- שרתי אפליקציה שקוראים ל-APIs חיצוניים (מעבד תשלומים, שירות אימייל, נתוני מפות)
- קריאות DynamoDB שעוברות דרך NAT Gateway (לפני שהוגדרו VPC endpoints לחלק מהטבלאות)

**העברת נתונים בין-AZ**: $178/חודש

- load balancer למכונות EC2 (ה-load balancer נמצא ב-AZ אחת, חלק מהמכונות ב-AZ אחרת)
- שרת אפליקציה ל-RDS read replica (ב-AZ שונה)

**העברת נתונים בין-אזורית**: $166/חודש

- שכפול Aurora Global Database (ראשי ב-us-west-2, reader ב-us-east-1)
- S3 Cross-Region Replication לגיבויים
- צינור הבדיקה הנשכח של Leo ‏($6/חודש מתוך הסכום הזה)

**NAT Gateway: ההפתעה הגדולה ביותר**

$289/חודש בדמי עיבוד NAT Gateway היו הפריט הגדול ביותר. כש-Tom הסתכל לאחרונה על השורה הזו — אז, כשהגדיר את ה-Gateway Endpoints — עיבוד ה-NAT עמד על $8.40 לחודש. מאז, נפח ההזמנות הוכפל פי כמה וצי של שירותי רקע חדשים עלה לאוויר, וכל אחד מהם שולח לוגים, מתשאל תורים ומושך אישורי גישה דרך אותו NAT Gateway. וניתוח ה-VPC Flow Logs הפך את זה לספציפי: הצרכן המוביל היה שרתי אפליקציה שקוראים ל-APIs של שירותי AWS ‏(SSM, Secrets Manager, CloudWatch Logs) דרך NAT Gateway.

בפרק 25, Tom הגדיר VPC Gateway Endpoints ל-S3 ול-DynamoDB. אלה היו חינמיים. אבל הוא פספס הגדרת Interface Endpoints לכמה שירותים אחרים:

- Systems Manager ‏(SSM) לניהול עדכונים
- Secrets Manager לשליפת אישורי גישה
- CloudWatch לשליחת מדדים ולוגים
- SQS לתשאול הודעות

כל קריאה לשירותים האלה ממכונות EC2 פרטיות עברה דרך ה-NAT Gateway. כל קריאה חויבה $0.045/GB.

אולי אתה תוהה למה AWS גובה על תעבורה שעוברת דרך ה-NAT Gateway כשאתה כבר בתוך הרשת של AWS. התשובה היא שה-NAT Gateway עצמו הוא שירות מנוהל — עולה כסף להריץ אותו, ו-AWS מגלגלת את העלות הזו לפי גיגה-בייט. VPC Endpoints מבטלים את המתווך, ולכן הם מקטינים את החשבון.

**חישוב ה-PrivateLink: מתי זה משתלם**

יש גרסה מורכבת יותר של השיחה הזו שעולה ככל שארכיטקטורות גדלות: שימוש ב-AWS PrivateLink כדי לספק קישוריות פרטית לשירותים שמתארחים אצל לקוחות AWS אחרים (או לשירותים שלך ב-VPCs אחרים).

Interface Endpoints של PrivateLink עולים $0.01/שעה לכל AZ בתוספת $0.01/GB. לשירות שמייצר 1TB/חודש של תעבורה דרך ה-endpoint:

- עלות PrivateLink: ‏$0.01 × ‏2 AZs × ‏730 שעות + ‏$0.01 × ‏1,000GB = ‏$14.60 + ‏$10 = ‏$24.60/חודש
- ניתוב אותה תעבורה דרך ה-NAT Gateway הקיים במקום זאת: ‏$0.045 × ‏1,000GB = ‏$45/חודש בחיובי עיבוד תוספתיים

ההשוואה היא *תוספתית*, כי ה-NAT Gateway נשאר בכל מקרה — הוא עדיין משרת את שאר התעבורה שיוצאת לאינטרנט, כך שהעלות השעתית שלו ($0.045 × ‏2 × ‏730 = ‏$65.70) לא נעלמת כשהשירות האחד הזה עובר ל-endpoint. בנפח התעבורה הזה, PrivateLink חוסך בערך $20/חודש. נקודת האיזון היא בערך 420GB/חודש — מתחת לזה, העלות השעתית של ה-endpoint עצמו עולה על החיסכון לפי GB יחסית לעיבוד NAT.

"רגע — אבל *למה* שנשתמש ב-PrivateLink במקום פשוט VPN או peering?" שאלה Maya.

"ומה אם מישהו ינסה לפרוץ ל-VPC עם peering?" שאלה Priya. "peering מלא אומר שלמכונה שנפרצה ב-VPC אחד יש מסלול לכל מכונה ב-VPC המחובר."

**תעבורה בין-AZ: שאלה ארכיטקטונית**

$178/חודש בהעברת נתונים בין-AZ היו עניין מסובך יותר.

חלק מזה היה בלתי נמנע: ה-load balancer מפזר תעבורה בין AZs, כך שחלק מהבקשות מתחילות ב-AZ אחת וה-load balancer מעביר אותן למכונה ב-AZ אחרת.

חלק מזה היה ניתן לאופטימיזציה: האפליקציה הייתה מוגדרת לכתוב ל-RDS primary ‏(ב-us-west-2a) ולקרוא מה-read replica ‏(ב-us-west-2b). כל שאילתת קריאה חצתה גבולות AZ.

לקריאות, פתרון אחד: להגדיר את האפליקציה להעדיף read replica באותה AZ של המכונה המבקשת. כל AZ מקבלת read replica משלה. התעבורה נשארת מקומית.

הפשרה: יותר read replicas = יותר עלות. אם עלות התעבורה הבין-AZ היא $50/חודש ו-read replica נוסף עולה $190/חודש, האופטימיזציה המקומית-ל-AZ לא משתלמת.

שאר העלויות הבין-AZ היו ניתוב load balancer ותקשורת שירות-לשירות — בלתי נמנעות במידה רבה ברמת הארכיטקטורה הנוכחית.

**S3 Select: הפחתת העברת נתונים בשאילתות**

הדפוס: כל בוקר, משימת אנליטיקה הורידה קובץ Parquet של 500MB מ-S3 כדי לסנן אותו בזיכרון לנתוני הזמנות ספציפיים-למסעדה. בערך 95% מהקובץ נזרק אחרי ההורדה.

**S3 Select** מאפשר לך לשלוף רק את השורות והעמודות שאתה צריך מאובייקט S3 ‏(CSV, JSON, Parquet), במקום להוריד את כל הקובץ כדי לסנן אותו באפליקציה שלך.

> **עדכון חשוב**: באמצע 2024, AWS הפסיקה להציע את S3 Select ללקוחות חדשים — משתמשים קיימים שומרים עליו, אבל זה מבוי סתום לארכיטקטורות חדשות. העיקרון שהסעיף הזה מלמד (סנן בשכבת האחסון, אל תשלח את כל הקובץ) הוא נצחי; הכלי המודרני לכך הוא **Amazon Athena** ‏(SQL ישירות מעל S3, כולל joins וצבירות ש-S3 Select מעולם לא היו לו). **S3 Object Lambda**, שהיה פעם החלופה האחרת, הלך בעקבות S3 Select למעמד legacy: נכון ל-7 בנובמבר 2025 הוא סגור גם הוא ללקוחות חדשים (עומסי עבודה קיימים ממשיכים לרוץ). בבחינה עדכנית, "תשאול נתונים במקום על S3" מצביע על Athena. הסיפור שלמטה נשמר כי *ההיגיון* — מדוד קודם, הזז את המסנן אל הנתונים — הוא הלקח.

ללא S3 Select:
```python
# הורד קובץ של 500MB, עבד בזיכרון
data = s3.get_object(Bucket='analytics', Key='orders-2024.csv')
df = pd.read_csv(data['Body'])
result = df[df['restaurant_id'] == '47'][['order_id', 'total']]
```

עם S3 Select:
```python
# תן ל-S3 לסנן קודם, העבר רק שורות תואמות (~2MB במקום 500MB)
response = s3.select_object_content(
    Bucket='analytics',
    Key='orders-2024.csv',
    Expression="SELECT order_id, total FROM S3Object WHERE restaurant_id = '47'"
)
```

S3 Select מפחית את כמות הנתונים שעוברת מ-S3 לאפליקציה שלך. לקבצים גדולים עם שאילתות סלקטיביות, זו יכולה להיות הפחתה של פי 10-100 בנפח הנתונים — ומכיוון שמכונת האנליטיקה רצה באותו אזור כמו ה-bucket, הרווח אינו חשבון העברה (העברת S3-ל-EC2 באותו אזור חינמית): הרווח הוא החישוב, הזיכרון והזמן שמושקעים בהורדה ובסינון של נתונים שאתה זורק מיד.

**CloudFront: הנחת העברת הנתונים**

הנה עובדה לא אינטואיטיבית: הגשת נתונים דרך CloudFront בדרך כלל זולה יותר מהגשה ישירה מ-EC2 או מ-S3.

**EC2 ישירות לאינטרנט**: $0.09/GB
**CloudFront לאינטרנט**: $0.085/GB (קצת יותר זול)

אבל החיסכון האמיתי אינו בתעריף ל-GB — אלא בכך ש-CloudFront שומר נתונים במטמון במיקומי הקצה. אם 1,000 משתמשים מבקשים את אותה תמונת תפריט:

- **ללא CloudFront**: ‏1,000 בקשות יוצאות מ-S3 ישירות לאינטרנט × גודל התמונה × $0.09/GB
- **עם CloudFront**: הלקוחות מקבלים את התמונה מהקצה בתעריף של CloudFront ‏($0.085/GB), ומילוי המטמון — CloudFront שמושך מ-S3 בהחטאה האחת — הוא **חינמי** ‏(AWS מוותרת על חיוב ההעברה ממקור ל-CloudFront; אתה משלם רק על בקשות ה-GET למקור)

עבור Nimbus, עם שיעור פגיעת מטמון של 83% (מפרק 13), ‏83% מהבקשות מעולם לא נגעו במקור בכלל — פחות בקשות למקור, פחות עומס על המקור, וכל בייט מחויב בתעריף הקצה במקום בתעריף האינטרנט של S3.

"CloudFront אינו רק CDN לביצועים," אמר Tom. "הוא גם אופטימיזציית עלות להעברת נתונים."

"נכון. אם משתמשים מורידים את זה מ-AWS, זה צריך לעבור דרך CloudFront."

## חוזקות ומגבלות

**עלויות NAT Gateway**:

- נפחי נתונים גדולים דרך NAT Gateway מצטברים במהירות
- VPC Endpoints מבטלים חלק מעלויות NAT לחלוטין
- בדוק אילו שירותים הקורא למכונות הפרטיות שלך ואם endpoints זמינים

**CloudFront לעלות**:

- שיעור פגיעת מטמון קובע ישירות חיסכוני עלות
- שיעור פגיעה גבוה = העברה נמוכה יותר מהמקור + עלות העברה כוללת נמוכה יותר
- העבר את כל הגשת נכסים סטטיים דרך CloudFront

**פשרות בין-AZ**:

- ביטול תעבורת בין-AZ לרוב דורש שינויים ארכיטקטוניים שעולים יותר מהחיסכון
- חשב בקפידה לפני אופטימיזציה

**S3 Select**:

- חיסכון משמעותי לשאילתות סלקטיביות על עצמי S3 גדולים
- לא עוזר כשאתה צריך את הקובץ כולו

בפרק הבא: המסגרת בעלת ששת העמודים ששואלת את השאלות שכל סקירת ארכיטקטורה צריכה להתחיל בהן.

## סיכום

- AWS גובה עבור **נתונים יוצאים** (אינטרנט: ~$0.09/GB), **תעבורת בין-AZ** ($0.01/GB בכל כיוון), **תעבורת בין-אזורים** ($0.02-0.08/GB), ועיבוד **NAT Gateway** ($0.045/GB).
- **נתונים נכנסים** חינמיים. **תעבורת אותה AZ** חינמית.
- **VPC Gateway Endpoints** (S3, DynamoDB): חינמיים. מבטלים עלויות NAT Gateway לשירותים אלה.
- **VPC Interface Endpoints**: מתומחרים לפי שעה בנוסף ל-GB. זולים יותר מ-NAT Gateway לשירותים בנפח גבוה.
- **CloudFront** מגיש נתונים בשיעורים נמוכים יותר מ-EC2-ישיר-לאינטרנט ומפחית בצורה דרמטית נפח העברה מהמקור דרך שמירה במטמון.
- **S3 Select** מפחית העברת נתונים מ-S3 על ידי סינון במקור.
- חלק מעלויות הרשת הן פשרות ארכיטקטוניות (בין-AZ לזמינות גבוהה) — הבן אותן, אל תמחוק אותן תמיד.

## טיפים למבחן

*תחום SAA-C03: עיצוב ארכיטקטורות מותאמות עלות (תחום 4, משימה 4.4)*

- **NAT Gateway לעומת VPC Endpoints**: תרחיש בחינה: "EC2 בתת-רשת פרטית קורא ל-S3/DynamoDB לעתים קרובות — כיצד להפחית עלויות NAT Gateway?" ← VPC Gateway Endpoints (חינמיים ל-S3 וגם ל-DynamoDB).
- **כללי תמחור העברת נתונים**:
  - לתוך AWS: חינם
  - אותה AZ: חינם
  - בין AZ: מחויב
  - בין אזורים: מחויב (שיעור גבוה יותר)
  - אינטרנט: מחויב (שיעור משמעותי)
- **CloudFront כאופטימיזציית עלות**: "הפחתת עלויות העברת נתונים להגשת תוכן גלובלי" ← CloudFront. שכבת המטמון מפחיתה בקשות למקור.
- **S3 Transfer Acceleration**: מאיץ העלאות *לתוך* S3 באמצעות מיקומי קצה CloudFront. עלות גבוהה יותר מ-S3 סטנדרטי. השתמש ללקוחות שמעלים קבצים גדולים ממיקומים גיאוגרפיים מרוחקים.
- **עלויות שכפול בין-אזורים**: שכפול נתונים בין אזורים גורר חיובי העברת נתונים. עבור S3 CRR, אתה משלם גם על שיעור ההעברה החוצה וגם על עלות הבקשה של S3.
- **PrivateLink (VPC Interface Endpoints)**: מספק קישוריות פרטית לשירותי AWS ולשירותים שמתארחים על ידי לקוחות AWS אחרים. בטוח יותר מעבור דרך NAT, לרוב זול יותר לשירותים בנפח גבוה.

## תרגילים

**תרגיל 1 — זכירה**

הסבר את ההבדל בין VPC Gateway Endpoint לבין VPC Interface Endpoint. לאילו שירותי AWS כל אחד זמין, ומה עלות כל אחד?

*(רמז: Gateway Endpoints חינמיים אבל רק ל-S3 ו-DynamoDB. Interface Endpoints עולים לפי שעה אבל עובדים לרוב שירותי AWS האחרים.)*

**תרגיל 2 — תרגול בחינה**

*תרחיש*: האפליקציה של חברה פועלת על מכונות EC2 בתת-רשתות פרטיות. המכונות מבצעות קריאות API תכופות ל-Amazon SQS ול-Amazon S3. כרגע, כל התעבורה יוצאת דרך NAT Gateway. הצוות רוצה להפחית עלויות NAT Gateway. אבטחת נתונים חייבת להישמר — אף תעבורה לא תחצה את האינטרנט הציבורי.

איזו גישה עונה **הכי טוב** על הדרישות הללו בעלות שוטפת מינימלית?

A) יצירת Gateway Endpoint ל-SQS וגם ל-S3  
B) יצירת Interface Endpoints לשניהם, SQS ו-S3  
C) יצירת Interface Endpoint ל-SQS ו-Gateway Endpoint ל-S3  
D) הסרת NAT Gateway ושימוש ב-Internet Gateway ישירות לקריאות API

**רמז 1**: Gateway Endpoints זמינים רק ל-S3 ו-DynamoDB.

**רמז 2**: Interface Endpoints זמינים ל-SQS ולשירותים רבים אחרים (אבל עולים כסף).

**רמז 3**: Internet Gateway בתת-רשת הפרטית יהפוך אותה לתת-רשת ציבורית — מפר את דרישות האבטחה.

**תשובה**: C

**הסבר**: S3 משתמש ב-Gateway Endpoint (חינם). SQS דורש Interface Endpoint (בתשלום). שילוב זה מבטל עלויות עיבוד NAT Gateway לשני השירותים. כל התעבורה נשארת בתוך הרשת הפרטית של AWS — ללא מעבר דרך האינטרנט הציבורי.

**למה לא A?** Gateway Endpoints אינם זמינים ל-SQS. רק S3 ו-DynamoDB יש להם Gateway Endpoints.

**למה לא B?** אמנם זה עובד, אבל שימוש ב-Interface Endpoint ל-S3 (במקום ה-Gateway Endpoint החינמי) גורם בחיובים שעתיים מיותרים. השתמש תמיד ב-Gateway Endpoint החינמי ל-S3 ול-DynamoDB.

**למה לא D?** הוספת מסלול ל-Internet Gateway מהתת-רשת הפרטית הופכת אותה לתת-רשת ציבורית. למכונות EC2 בתת-רשתות פרטיות בדרך כלל אין Elastic IPs, כך שלא יכלו לנתב דרך Internet Gateway ללא שינויים נוספים — ועשיית זאת הייתה חושפת אותן לתעבורת אינטרנט נכנסת.

*תחום SAA-C03: עיצוב ארכיטקטורות מותאמות עלות — משימה 4.4*

**תרגיל 3 — אתגר ארכיטקטורה** *(אופציונלי)*
