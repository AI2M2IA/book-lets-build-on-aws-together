# פרק 14: מי רשאי לעשות מה

ל-Tom היו מפתחות גישה פתוחים בקובץ טקסט, מוכן להעתיק.

"מה אתה עושה?" שאלה Priya.

"מכונת EC2 צריכה לקרוא קבצי תצורה מ-S3. אני מכניס את האישורים בתצורת השרת."

היא הסתכלה על המסך לרגע. "סגור את הקובץ הזה."

"אם מישהו נכנס לשרת הזה," אמרה, "הם מקבלים את המפתחות האלה. ואותם מפתחות נוגעים בכל מה שמשתמש IAM מורשה לגעת בו."

Tom סגר את הקובץ.

"יש דרך טובה יותר," היא אמרה. "לשרת עצמו יכול להיות תפקיד. תחשוב על זה כמו תואר תפקיד — למכונה אין צורך באישורים כי המערכת כבר יודעת מה היא ומה מותר לה לעשות."

**חזרה ל-IAM: התמונה המלאה**

מדיניות IAM הן מסמכי JSON המציינים אילו פעולות מותרות או נדחות על אילו משאבים:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": [
        "s3:GetObject",
        "s3:PutObject"
      ],
      "Resource": "arn:aws:s3:::nimbus-assets/*"
    }
  ]
}
```

**הבעיה עם "AdministratorAccess"**

`AdministratorAccess` מעניקה כל פעולה על כל משאב. אם חבר צוות עם מדיניות זו עושה טעות — מוחק סל S3 בטעות, מסיים את מכונת EC2 הלא נכונה — אין שום דבר ש-AWS יכולה לעשות כדי לעצור אותם.

**תפקידי IAM: זהויות לשירותים**

מכונות EC2 הפועלות של Nimbus API צריכות:

- לקרוא מ-DynamoDB (התפריט)
- לכתוב ל-DynamoDB (הזמנות)
- לשים אובייקטים ב-S3 (קבלות, העלאות)
- לכתוב יומנים ל-CloudWatch
- לקרוא סודות מ-Secrets Manager

במקום ליצור משתמש עם מפתח גישה ולאחסן אותו על המכונה — סיוט אבטחה — אתם יוצרים **תפקיד IAM** למכונת EC2 עם בדיוק ההרשאות האלה.

**תחומי הרשאות: הגבלת מה שתפקידים יכולים להעניק**

**Permission boundaries** קובעות את ההרשאות המקסימליות שניתן להעניק אי פעם לזהות. גם אם המדיניות המצורפת לזהות רחבה יותר, ההרשאות האפקטיביות מוגבלות על ידי תחום ההרשאות.

**SCPs: גבולות ברמת ארגון**

**Service Control Policies (SCPs)** מחילים גבולות ארגוניים המשפיעים על *כל* ישות IAM בחשבון, כולל מנהלים.

## סיכום

- הימנעו מ**AdministratorAccess** בייצור.
- מדיניות IAM מציינות **Effect**, **Action** ו-**Resource** — היו ספציפיים בכולם.
- מכונות EC2, פונקציות Lambda ושירותי AWS אחרים צריכים להשתמש ב**תפקידי IAM**, לא מפתחות גישה.
- **Permission boundaries** מגבלות את ההרשאות המקסימליות שלזהות יכולה להיות.
- **SCPs** מחילות הגבלות כלל-ארגוניות שאפילו מנהלים לא יכולים לעקוף.

## עצות לבחינה

- **תפקידי IAM ל-EC2**: התשובה הקנונית כשEC2 צריכה לגשת ל-S3, DynamoDB, Secrets Manager.
- **לוגיקת הערכת מדיניות**: Deny מפורש תמיד מנצח, גם על Allow מפורש.
- **Permission boundaries**: משמשות בהאצלת ניהול IAM.
- **SCPs לא מעניקות הרשאות**: הן רק מגבילות.
