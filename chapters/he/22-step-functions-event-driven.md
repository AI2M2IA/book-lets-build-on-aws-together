**AWS Step Functions: תזמור Workflows**

**AWS Step Functions** הוא שירות תזמור serverless שמתאם שלבים של יישום כ-workflow ויזואלי. כל שלב הוא **מצב** ב**state machine**.

במקום סקריפט Python שרץ מלמעלה למטה וקורס, אתם מגדירים את ה-workflow כ-state machine ב-JSON/YAML:

```json
{
  "StartAt": "ValidateLicense",
  "States": {
    "ValidateLicense": {
      "Type": "Task",
      "Resource": "arn:aws:lambda:us-west-2:123456789012:function:validate-license",
      "Next": "ImportMenu",
      "Catch": [{"ErrorEquals": ["States.ALL"], "Next": "OnboardingFailed"}]
    },
    "ImportMenu": {
      "Type": "Task",
      "Resource": "arn:aws:lambda:us-west-2:123456789012:function:import-menu",
      "Next": "SetupPayments",
      "Retry": [{"ErrorEquals": ["States.ALL"], "MaxAttempts": 3, "IntervalSeconds": 5}]
    },
    ...
  }
}
```

כל מצב יכול:

- **לבצע פונקציית Lambda** (הדפוס הנפוץ ביותר)
- **לבצע ECS task** (לעבודה ארוכת-טווח)
- **לחכות לזמן ספציפי** או **לאירוע** (השהיית ה-workflow עד שמשהו חיצוני קורה)
- **לבחור מסלול** בהתבסס על תנאים (לוגיקת if/else)
- **להריץ ענפים מקבילים** בו-זמנית
- **לנסות שוב על כשל** עם backoff ניתן לתצורה
- **לתפוס שגיאות** ולנתב למצבי טיפול בשגיאות

Step Functions מנהלת את מצב הביצוע בצורה עמידה. אם שלב 3 נכשל, הביצוע מושהה בשלב 3. ניתן לבחון את הביצוע הכושל במסוף, לתקן את הבעיה, ולהפעיל שוב משלב 3 — מבלי לחזור על שלבים 1 ו-2.

אולי תהיתם: האם לא ניתן פשוט לכתוב לוגיקת retry בפונקציית Lambda? כן — אבל אז אתם גם כותבים מעקב כשלים, שמירת מצב, ורישום audit בקוד. וכשהשלב 3 מ-7 נכשל, אתם צריכים לדעת איזו מסעדה עובדת, מה קרה לפני, והיכן להמשיך. Step Functions עושה את כל זה.

**תהליך ההזמנה של Nimbus: State Machine עם הערות**

הנה גרסה מפושטת של state machine של Step Functions בפועל שבנתה Nimbus לאישור הזמנות — עם הערות כדי שתוכלו לראות מה כל חלק עושה:

```json
{
  "Comment": "Nimbus order confirmation workflow",
  "StartAt": "ChargeCard",
  "States": {
    "ChargeCard": {
      "Type": "Task",
      "Resource": "arn:aws:lambda:us-west-2:123456789012:function:charge-card",
      "Next": "SendConfirmationEmail",
      "Retry": [
        {
          "ErrorEquals": ["PaymentRetryableError"],
          "MaxAttempts": 2,
          "IntervalSeconds": 3,
          "BackoffRate": 2.0
        }
      ],
      "Catch": [
        {
          "ErrorEquals": ["PaymentDeclinedError"],
          "Next": "NotifyCustomerOfDecline"
        },
        {
          "ErrorEquals": ["States.ALL"],
          "Next": "ChargeCardFailed"
        }
      ]
    },
    "SendConfirmationEmail": {
      "Type": "Task",
      "Resource": "arn:aws:lambda:us-west-2:123456789012:function:send-confirmation-email",
      "Next": "NotifyRestaurant",
      "Retry": [
        {
          "ErrorEquals": ["States.ALL"],
          "MaxAttempts": 3,
          "IntervalSeconds": 5
        }
      ]
    },
    "NotifyRestaurant": {
      "Type": "Task",
      "Resource": "arn:aws:lambda:us-west-2:123456789012:function:notify-restaurant",
      "Next": "UpdateInventory",
      "Retry": [
        {
          "ErrorEquals": ["States.ALL"],
          "MaxAttempts": 3,
          "IntervalSeconds": 10,
          "BackoffRate": 2.0
        }
      ],
      "Catch": [
        {
          "ErrorEquals": ["States.ALL"],
          "Next": "RestaurantNotificationFailed"
        }
      ]
    },
    "UpdateInventory": {
      "Type": "Task",
      "Resource": "arn:aws:lambda:us-west-2:123456789012:function:update-inventory",
      "Next": "LogTransaction",
      "Retry": [{"ErrorEquals": ["States.ALL"], "MaxAttempts": 2}]
    },
    "LogTransaction": {
      "Type": "Task",
      "Resource": "arn:aws:lambda:us-west-2:123456789012:function:log-transaction",
      "End": true
    },
    "NotifyCustomerOfDecline": {
      "Type": "Task",
      "Resource": "arn:aws:lambda:us-west-2:123456789012:function:notify-decline",
      "End": true
    },
    "ChargeCardFailed": {
      "Type": "Fail",
      "Error": "ChargeCardFailed",
      "Cause": "Card charge failed after retries"
    },
    "RestaurantNotificationFailed": {
      "Type": "Task",
      "Resource": "arn:aws:lambda:us-west-2:123456789012:function:alert-support",
      "Comment": "התרע לצוות התמיכה — הזמנה חויבה אבל המסעדה לא הוזנה",
      "End": true
    }
  }
}
```

כמה דברים לשים לב אליהם:

**ל-`ChargeCard` יש שני סעיפי Catch.** אחד ל-`PaymentDeclinedError` (כשל ידוע ומצופה — הכרטיס סורב, לא שגיאת מערכת) ואחד ל-`States.ALL` (כל שאר — הפסקת שירות, timeout, חריגה בלתי צפויה). הם מנתבים למצבים שונים כי הם מתכוונים לדברים שונים.

**ל-`NotifyRestaurant` יש Catch שמנתב ל-`RestaurantNotificationFailed`.** זה הבאג שגרם לאחד עשר התקריות. בסקריפט ה-Python הישן, לא היה שווה-ערך — אם ההודעה נכשלה, הפונקציה או קרסה בשקט או רשמה שגיאה והמשיכה. Step Functions הופכת את מסלול הכישלון לברור: הוא הולך למקום ספציפי, ואותו מקום מתריע לצוות התמיכה לפני שאף אחד צריך לטלפן.

**לכל Task יש Retry.** אם לשירות האימייל יש timeout חולף, הוא מנסה שוב אוטומטית, שלוש פעמים, עם backoff הולך וגדל. הלקוח לעולם לא רואה זאת. ההזמנה אינה אבודה.

**התהליך הוא גרף, לא סקריפט.** אם `NotifyRestaurant` נכשל לצמיתות (לאחר ניסיונות חוזרים), הביצוע לא ממשיך ל-`UpdateInventory`. ה-workflow עוצר ב-`RestaurantNotificationFailed`. המלאי אינו מתעדכן למסעדה שלא יודעת על ההזמנה. זו התנהגות נכונה.

"רגע — אבל *למה* אנחנו צריכים מסלולי כישלון נפרדים לכרטיס שנדחה לעומת שגיאת מערכת?" שאלה Maya.

"כי הם דורשים תגובות שונות לחלוטין," אמר Leo. "כרטיס שנדחה פירושו שאנחנו שולחים אימייל ללקוח ומבקשים ממנו לנסות שוב. שגיאת מערכת בפונקציית החיוב פירושה שאנחנו צריכים מהנדס שיחקור מדוע פונקציית ה-Lambda נכשלת. אותה תוצאה הנצפית — ההזמנה לא עברה — אבל תיקון שונה לחלוטין."

**סוגי מצב: אבני הבניין**

**Task**: ביצוע פעולה — קריאה לפונקציית Lambda, הפעלת ECS task, קריאה ל-API. כאן מתרחשת העבודה האמיתית.

**Choice**: סתעפות בהתבסס על תנאים בנתוני הקלט. כמו if/else בקוד.

**Parallel**: הרצת ענפים מרובים בו-זמנית והמתנה לסיום כולם.

**Map**: החלת קבוצת מצבים על כל פריט ברשימה. עיבוד 50 פריטי תפריט מסעדה במקביל.

כשNimbus ייבאה תפריט מסעדה, התפריט יכול היה להכיל בין 8 ל-200 פריטים. עבור כל פריט, תהליך הייבוא היה צריך: לאמת את הפורמט, לבדוק נתוני אלרגנים, לשנות גודל התמונה, ולכתוב את הרשומה ל-DynamoDB.

ללא מצב ה-Map, זה היה Lambda יחיד המעבד פריטים סדרתית — 200 פריטים × 200ms לפריט = 40 שניות של זמן עיבוד. עם מצב ה-Map, Step Functions מפעיל ביצועים מקביליים של מצבי העיבוד — עד למגבלת ה-concurrency המוגדרת — וממתין שכולם יסתיימו. אותם 200 פריטים יכולים להסתיים בפחות מ-5 שניות.

**Wait**: השהייה לזמן מוגדר או עד timestamp. שימושי לעיכובים מתוזמנים.

**Pass**: העברת קלט לפלט ללא ביצוע עבודה. משמש להמרת נתונים ובדיקה.

**Succeed/Fail**: מצבים סופניים המסיימים את הביצוע.

לקבלת המסעדה, Leo תכנן workflow:

1. ValidateLicense (Task ← Lambda)
2. ImportMenu (Task ← Lambda, עם 3 ניסיונות חוזרים)
3. ענף Parallel:
   א. SetupPayments (Task ← Lambda)
   ב. CreateIAMRole (Task ← Lambda)
4. SendWelcomeEmail (Task ← Lambda, ממתין לסיום ה-Parallel)
5. NotifySalesTeam (Task ← Lambda)

שלבים 3א ו-3ב פועלים במקביל — הם אינם תלויים זה בזה, והפעלתם בו-זמנית חוסכת זמן.

לאחר סיום קבלת קבוצת המסעדות הראשונה, עלתה דרישת ציות: לפני שמסעדה שותפה יכולה לצאת לאוויר, מנהל חשבון של Nimbus היה צריך לסקור ידנית ולאשר את תיעוד הרישיון. זה יכול לקחת יום עד שלושה ימי עסקים.

"ומה אם מישהו מנסה לפרוץ בחלון זה?" שאלה Priya. "אם המסעדה מוגדרת חלקית — חשבון תשלומים נוצר אבל טרם אושר — ומישהו מגלה את המצב הממתין, הוא יכול לנסות לנצל את ההגדרה החצי-פתוחה."

יותר מעשית: כיצד משהים workflow של Step Functions שלושה ימים בהמתנה לאנושי?

התשובה היא **דפוס ה-callback עם task token**.

כש-`ValidateLicense` פועל, במקום להסתיים אוטומטית, הוא קורא ל-Lambda שעושה שלושה דברים:

1. שולחת אימייל למנהל החשבון עם מסמכי המסעדה
2. מקליטה **task token** (מזהה ייחודי שStep Functions מייצרת לביצוע ולמצב הספציפי) במסד נתונים, מקושר לאותה ביקורת ממתינה
3. מחזירה ל-Step Functions עם `.waitForTaskToken` — שאומר לStep Functions להשהות ביצוע במצב זה ללא הגבלת זמן

Step Functions מחנה את הביצוע. כלום אחר אינו חסום — אין שרת שיושב ומחכה. ה-state machine פשוט ממתין, צורכת אפס משאבי מחשוב.

שלושה ימים לאחר מכן, מנהל החשבון לוחץ "אשר" בכלי ה-admin הפנימי. כלי ה-admin מחפש את ה-task token ממסד הנתונים וקורא:

```python
stepfunctions.send_task_success(
    taskToken=token,
    output=json.dumps({"approved": True, "reviewedBy": "dana.cole@eatnimbus.com"})
)
```

Step Functions ממשיכה. הביצוע ממשיך משלב 2 (`ImportMenu`), עם מידע הסוקר זמין במצב ה-workflow.

"הביצוע הושהה שלושה ימים," אמר Leo, "ודבר היחיד שקרה כשאישרתי היה קריאת API אחת."

"ואם מנהל החשבון דוחה?" שאלה Maya.

"אנחנו קוראים ל-`send_task_failure` במקום. ה-state machine תופסת זאת ומנתבת למצב `NotifyRejection` ששולח אימייל לשותפת המסעדה."

Step Functions לא מבצעת polling. לא מנסה שוב. לא פוגת זמן (אלא אם כן מגדירים heartbeat timeout). היא פשוט ממתינה עד שה-callback מגיע, ואז ממשיכה. זה שונה מהותית מבדיקת מסד נתונים או תור — ולכן Step Functions מתאימה היטב ל-workflows שמערבים שלבים אוטומטיים וידניים.

ב-42 שניות, Step Functions חייבה את הכרטיס, שלחה את האימייל, ניסתה את הודעת המסעדה שלוש פעמים, תפסה את הכשל, התריעה לצוות התמיכה, ורשמה את ההיסטוריה המלאה. לפני Step Functions, הכשל הזה היה בלתי נראה — פונקציית ה-Python הייתה רושמת "ההודעה נכשלה" ומחזירה 200 לקורא כאילו שום דבר לא השתבש.

"ציר הזמן מראה בדיוק היכן הדברים השתבשו ומתי," אמר Leo. "וכל ניסיון חוזר עם חותמת זמן. ניתן לראות מרווחי ה-backoff."

Priya הסתכלה על המסוף. "וההיסטוריה הזו מאוחסנת כמה זמן?"

היסטוריית ביצוע workflow סטנדרטי מאוחסנת 90 יום. לציות או ביקורת ארוכת-טווח, ניתן לייצא גם אירועי ביצוע ל-CloudWatch Logs ולשמור אותם ללא הגבלת זמן.

**Workflows Standard לעומת Express**

Step Functions מציעה שני סוגי workflow:

**Workflows Standard**:

- משך מרבי: שנה אחת
- ביצועים עמידים — מצב מתמיד, ניתן לבדיקה ולביקורת
- ביצוע לפחות-פעם-אחת (task לא פועל יותר מפעם אחת אלא אם כן מגדירים Retry)
- מחיר לפי מעבר מצב
- מיטבי ל-workflows ארוכי-טווח וחשובים (עיבוד הזמנות, קבלה, תהליכי תשלום)

**Express Workflows**:

- משך מרבי: 5 דקות
- תפוקה גבוהה יותר — עד 100,000 לשנייה
- ביצוע לפחות-פעם-אחת (אסינכרוני) או לכל-היותר-פעם-אחת (סינכרוני) — תכננו tasks להיות אידמפוטנטיים
- מחיר לפי משך (כמו Lambda)
- מיטבי ל-workflows בנפח גבוה ומשך קצר (עיבוד אירועים בזמן אמיתי, קליטת נתוני IoT)

"כמה זה עולה בחודש?" שאל Tom, פותח את דף התמחור. "לפי מעבר מצב ב-Standard — זה מסתכם אם יש הרבה שלבים."

Leo עבר על החשבון. לworkflow קבלת המסעדה (שישה מצבי task לביצוע, בערך 12-15 מסעדות חדשות בחודש): פחות ממאה מעברי מצב — פחות מסנט, ובתוך שכבת ה-4,000-מעבר החינמית החודשית, כלומר ביעילות $0. לworkflow אישור ההזמנות בתנועה מלאה של Nimbus: יותר משמעותי, אבל עדיין הרבה מתחת לעלות ניפוי הבאגים של אחד עשר מקרי הצלחה-חלקית בחודש ידנית.

"עלות ניפוי הבאגים היא העלות הנסתרת," אמר Leo.

"זו תמיד העלות הנסתרת," אמר Tom.

Tom חישב את המספרים ביתר קפידה, כי זה היה Tom.

**עלות workflow Standard לתהליך אישור ההזמנות של Nimbus**: חמישה מצבים לכל הזמנה במסלול המאושר, לפי $0.000025 למעבר מצב. חמישה מעברי מצב × $0.000025 × 15,000 הזמנות לחודש = **$1.88/חודש**. בפי עשרה מנפח ההזמנות: כ-$19/חודש. עלות ניפוי הבאגים למקרה הצלחה-חלקית אחד (24 דקות של זמן מהנדס תמיכה) עלתה על חשבון Step Functions החודשי כמה פעמים.

ההשוואה הופכת חשובה אם מישהו מציע להשתמש ב-Standard workflows לאירועי ניתוח בתדירות גבוהה. נניח שNimbus רצתה להשתמש ב-Step Functions לעיבוד כל אירוע clickstream גולמי — כל תצוגת דף תפריט, כל גלילה, כל חיפוש. זה בערך 800,000 אירועים ביום בהיקף הנוכחי שלהם. workflow Standard בן חמישה מצבים לכל אירוע: 800,000 × 5 × $0.000025 × 30 יום = **$3,000/חודש**. זה כסף אמיתי לצינור ניתוח.

Express workflows לאותו נפח: מחיר לפי בקשה בתוספת משך, לא לפי מעבר מצב. 24 מיליון ביצועים חודשיים עולים $1.00 למיליון בקשות = $24. משך: 24M × 500ms במינימום החיוב של 64MB ≈ 208 GB-שעות × $0.06 = $12.50. סה"כ ≈ **$36.50/חודש** — זול בכמעט שני סדרי גודל מ-$3,000 של Standard.

"אז סוג ה-workflow אינו רק החלטה ארכיטקטונית," אמר Tom. "זו החלטת עלויות. אותו מספר מצבים יכול לעלות כמעט מאה פעמים יותר בהתאם לסוג ה-workflow שבו משתמשים."

"ואיזה עדיף תלוי לחלוטין במה ה-workflow עושה," אמר Leo. "אישור הזמנות: Standard. זה חשוב, יש לו מסלולי כשל משמעותיים, אנחנו רוצים את ה-audit trail. עיבוד אירועי ניתוח: Express. זה נפח גבוה, משך קצר, ואנחנו לא צריכים 90 יום היסטוריית ביצוע לכל תצוגת דף."

אם לתהליך שלכם יש שני שלבים ואין לו צורך ב-audit trail, פונקציית Lambda פשוטה זולה יותר ואינה מצריכה syntax של JSON state machine — אבל אם כל שלב יכול להיכשל באופן עצמאי וצריך לנסות שוב או להתחיל מחדש מבלי לחזור על שלבים קודמים, Step Functions משתלמת בחיסכון בניפוי באגים ותיקון ידני.

לקבלת המסעדה של Nimbus: Standard (זה חשוב, עמיד, ועשוי לקחת שעות אם מעורבים שלבים ידניים).

לעדכוני מצב הזמנות בזמן אמיתי של Nimbus: Express (נפח גבוה, משך קצר, פחות קריטי).

**ארכיטקטורה מונעת-אירועים: התמונה הגדולה**

Step Functions הוא חלק אחד מדפוס גדול יותר: **ארכיטקטורה מונעת-אירועים**. במקום שירותים שקוראים זה לזה ישירות (צימוד הדוק), שירותים פולטים אירועים, ושירותים אחרים מגיבים לאירועים אלה.

ראינו זאת לאורך כל הספר:

- הזמנות שהוזמנו ← SNS פורס אירוע ← SQS מתורים מספקים לצרכנים
- קובץ שהועלה ל-S3 ← Lambda מופעלת לעיבוד
- רשומה ב-DynamoDB שהשתנתה ← DynamoDB Streams ← Lambda מעדכנת cache

**Amazon EventBridge** (לשעבר CloudWatch Events) הוא אוטובוס האירועים המתקדם לדפוס זה. הוא מנתב אירועים משירותי AWS ומהיישומים שלכם ליעדים (Lambda, SQS, Step Functions וכדומה) בהתבסס על כללים.

EventBridge מאפשר צימוד רופף ברמה ארכיטקטונית: שירות ההזמנות פורס אירועי `order.placed` מבלי לדעת מי מקשיב. שירות הניתוח, שירות ההתראות, ושירות נקודות הנאמנות כולם מקשיבים באופן עצמאי. הוספת מאזין חדש אינה מצריכה שינוי בשירות ההזמנות.

EventBridge גם מתאים באופן טבעי עם עשרות שירותי AWS כ**מקורות אירועים**. כשקריאת API של CloudTrail תואמת דפוס, EventBridge יכול להפעיל כלל. כשמכונת EC2 משנה מצב, EventBridge יכול להפעיל Lambda. כשמכונת RDS מבצעת failover, EventBridge יכול להתריע למהנדס התורן. ניתן לטפל בכל מישור הבקרה של AWS כזרם אירועים.

עבור Nimbus, כלל EventBridge שימושי במיוחד: הפעלת Lambda בכל פעם שתמונה חדשה נדחפת ל-ECR. ה-Lambda בודקת את תוצאת סריקת התמונה ומפרסמת בערוץ Slack של ההנדסה אם נמצאים CVEs ברמת HIGH או CRITICAL — לפני שמישהו פורס את התמונה. זה משלב את סריקת האבטחה של ECR (מהפרק 21) עם ניתוב האירועים של EventBridge לשער אבטחה אוטומטי.

עיקרון הארכיטקטורה מונעת-אירועים זהה ללוגיקת ה-retry של Step Functions: הפכו כשל לברור ומנותב, לא שקט ובלוע. שירותים שמתקשרים דרך אירועים נכשלים בחן — אם Lambda נקודות הנאמנות מקועה כשאירוע `OrderConfirmed` נשלח, EventBridge יכול לנסות שוב את המסירה או לשלוח לתור מכתב-מת. אישור ההזמנה עצמו אינו מושפע. הניתוק הוא החוסן.

**EventBridge: ניתוק תוצאות-לוואי מהתהליך הראשי**

לאחר שstate machine אישור ההזמנות פעלה בצורה נקייה, Maya העלתה שאלה בסקירת הארכיטקטורה הבאה.

"אנחנו רוצים להעניק נקודות נאמנות כשהזמנה מאושרת. הלקוח מקבל נקודה אחת לכל דולר שהוצא. היכן זה הולך ב-state machine?"

אינסטינקט ראשון של Leo: הוספת מצב `GrantLoyaltyPoints` לאחר `LogTransaction`.

תגובת Priya: "ואחר כך כשנוסיף בונוסי הפניה? וסקרים לאחר הזמנה? ובקשות דירוג מסעדות? כל אחד מוסיף מצב למסלול הקריטי. אם Lambda נקודות הנאמנות נכשלת, כל אישור ההזמנה נכשל."

"תהליך אישור ההזמנות צריך לעשות דבר אחד," אמרה. "לאשר את ההזמנה. כל השאר הוא תוצאת-לוואי."

זו הטיעון הארכיטקטוני לטובת **Amazon EventBridge** כמנגנון לניתוק תוצאות-לוואי מה-workflow הראשי.

הגישה המתוקנת: כש-`LogTransaction` מסתיים בהצלחה, ה-Lambda מפרסמת אירוע ל-EventBridge:

```json
{
  "source": "nimbus.orders",
  "detail-type": "OrderConfirmed",
  "detail": {
    "orderId": "ORD-8812",
    "customerId": "CUST-441",
    "restaurantId": "94",
    "total": 3200,
    "timestamp": "2024-03-15T14:23:43Z"
  }
}
```

ואז כללי EventBridge מנתבים את האירוע ליעדים עצמאיים:

- **כלל 1**: `OrderConfirmed` ← Lambda נקודות נאמנות (מעניקה 32 נקודות להזמנה של $32)
- **כלל 2**: `OrderConfirmed` ← Lambda סקר לאחר הזמנה (מוסיפה לתור סקר לשעתיים לאחר המסירה)
- **כלל 3**: `OrderConfirmed` ← Kinesis Stream ניתוח (מזין את ה-dashboard בזמן אמיתי)

כל כלל עצמאי. Lambda נקודות הנאמנות יכולה להיכשל מבלי להשפיע על תור הסקר. צינור הניתוח יכול להיפגר מבלי לחסום את מערכת הנאמנות. הוספת תוצאת-לוואי חדשה (בקשת דירוג מסעדה, הודעת cashback) מצריכה יצירת כלל EventBridge חדש — לא שינוי ב-state machine.

"ומה אם מישהו מנסה לפרוץ דרך כלל EventBridge?" שאלה Priya. "אם האירוע מכיל PII של לקוח, כל Lambda שמקבלת אותו היא כעת נקודת גישה ל-PII."

האירוע תוכנן בקפידה: רק המזהים, לא השמות, הכתובות, או פרטי התשלום. כל Lambda הזקוקה לנתוני לקוח תחפש אותם ממסד הנתונים באמצעות מזהה הלקוח — עם הרשאות IAM משלה השולטות במה שהיא יכולה לגשת.

"האירוע הוא אות," אמרה Priya. "לא שחרור נתונים."

**מתי Step Functions הוא הכלי הנכון**

Step Functions מצטיין כש:

**workflows רב-שלביים** שצריכים לעקוב אחרי התקדמות על פני שלבים

**תהליכים עם אנושי-בתהליך** — Step Functions יכולה לחכות ללא הגבלת זמן לאירוע חיצוני (כמו אנושי שמאשר משהו) ואחר כך להמשיך

**טיפול שגיאות בהיקף** — לוגיקת retry, catch וfallback מובנית על פני שלבים רבים

**תהליכים הניתנים לביקורת** — כל ביצוע מקליט כל מעבר מצב. ניתן לראות בדיוק מה קרה ומתי.

**לוגיקה מקבילה או סדרתית מורכבת** — ה-workflow הויזואלי מקל על הנמקה לעומת קוד שווה-ערך

Step Functions מוגזם לתהליכים פשוטים דו-שלביים. השתמשו בו כשהתיאום עצמו בעל ערך ותרחישי הכשל חשובים.

**מתי Step Functions הוא הכלי הלא נכון**

"רגע — אבל *למה* לא נשתמש ב-Step Functions לכל דבר?" שאלה Maya בסוף ישיבת התכנון. "בנינו את workflow קבלת המסעדה. יש לנו את תהליך אישור ההזמנות. למה לא להמיר הכל ל-state machines?"

התשובה הכנה: כי Step Functions מוסיפה תקורה שלא כל workflow מצדיק.

**תהליכים פשוטים דו-שלביים**: אם יש לכם Lambda שמעבדת קובץ שהועלה על ידי קריאה ל-Lambda שניה, תקורת התיאום של state machine אינה שווה את היתרון התפעולי. שתי Lambdas שנקראות סדרתית בתוך פונקציה אחת פשוטות יותר, קלות יותר לבדיקה, ואין להן עלות מעבר-מצב.

**workflows בתדירות-גבוהה-מאוד ותת-שנייתית**: ל-Standard workflows יש עלות מעבר-מצב לא-מבוטלת שמצטברת בנפח גבוה (כפי שדוגמת הניתוח לעיל הראתה). Express workflows פותרים את בעיית העלות אבל אינם מספקים היסטוריית מצב עמידה. בתדירות גבוהה מאוד עם משך קצר מאוד, SQS בתוספת Lambda (הדפוס מהפרק 19) פשוט וזול יותר משני סוגי Step Functions.

**fan-out טהור ללא תיאום**: אם אתם צריכים לשלוח את אותו אירוע לעשרים צרכנים ואינכם אכפתיים מתוצאת כל אחד, SNS הוא הכלי. Step Functions מוסיפה מעקב מצב שאינכם צריכים ותשלמו עליו שלא לצורך.

**אינטראקציות משתמש סינכרוניות בזמן אמיתי**: ביצועי Step Functions הם אסינכרוניים. אם משתמש ממתין במסך checkout לתגובה סינכרונית בפחות מ-500ms, workflow Standard של Step Functions אינו מתוכנן לזה (Express workflows ניתנים להפעלה סינכרונית, אבל תקורת ה-latency עדיין גבוהה יותר מקריאת Lambda ישירה). לתהליכים סינכרוניים פונים-למשתמש, Lambda + API Gateway עם טיפול שגיאות מעוצב היטב לעיתים קרובות מתאימים יותר.

העיקרון: השתמשו ב-Step Functions כש*התיאום* של שלבים בעצמו מורכב — כשהשלבים יכולים להיכשל באופן עצמאי, כשאתם צריכים לנסות שוב שלבים בודדים מבלי לחזור על קודמים, כשלהיסטוריית הביצוע יש ערך ציות או איתור באגים, או כשה-workflow כולל שלבי אישור אנושי שעשויים לקחת ימים. אל תשתמשו בו להוספת תקורת תזמור ללוגיקה סדרתית פשוטה שעובדת בסדר כפונקציה אחת.

## חוזקות ומגבלות

**מדוע Step Functions חזקה**:

- היסטוריית ביצוע ויזואלית — ראו בדיוק היכן workflow נמצא (או נכשל)
- retry וטיפול שגיאות מובנים — ללא קוד retry מותאם
- מצב עמיד — ביצועים שורדים הפעלות מחדש של שירותים ו-outages
- אינטגרציות ישירות עם 200+ שירותי AWS (לא רק Lambda)
- ה-workflow הויזואלי הוא מתועד-עצמי
- דפוס ה-callback מאפשר המתנה ללא הגבלת זמן לפעולות אנושיות מבלי לצרוך מחשוב

**איפה זה מסתבך**:

- Standard workflows מחויבים לפי מעבר מצב — workflows מורכבים עם מצבים רבים עשויים להיות יקרים בהיקף גדול
- פורמט JSON של ASL (Amazon States Language) דורש עקומת למידה
- גודל payload מרבי הוא 256KB — נתונים גדולים חייבים להועבר דרך הפניות S3, לא ישירות דרך ה-workflow
- workflows ארוכים עם שלבים ידניים רבים דורשים הגדרת timeout זהירה
- ניפוי באגים של שגיאות ASL דורש הרצת ביצועים; אין אמולטור מקומי עוצמתי כמו השירות האמיתי
- הרשאות IAM חייבות להינתן בנפרד לכל משאב שה-state machine קורא — שכחת הרשאה אחת גורמת לשגיאה מבלבלת בזמן ריצה

## סיכום

המיכלים בפרק 21 הפכו פריסות לאמינות. Step Functions הופך תהליכים עסקיים רב-שלביים לאמינים — אותו עיקרון של "חיסול סיכון ההעברה" מיושם ללוגיקת יישום.

- **Step Functions** מתזמרת workflows רב-שלביים כ-state machines.
- כל **מצב** יכול להריץ פונקציית Lambda, לבצע ECS task, לחכות, להסתעף, או להריץ שלבים מקבילים.
- **Retry ו-catch** מובנים בכל מצב — ללא קוד retry מותאם נדרש.
- **Standard workflows**: ארוכי טווח (עד שנה), עמידים, לפחות-פעם-אחת. לתהליכים עסקיים קריטיים.
- **Express workflows**: קצרי-טווח (עד 5 דקות), תפוקה גבוהה. לעיבוד אירועים בנפח גבוה.
- **דפוס Callback עם task token**: השהיית workflow ללא הגבלת זמן בהמתנה לאירוע חיצוני או פעולה אנושית; חידוש עם קריאת API אחת.
- **מצב Map**: עיבוד רשימת פריטים בצורה מקבילה — החלפת לולאות סדרתיות ב-fan-out מקביל.
- **אינטגרציות SDK ישירות**: קריאה ל-DynamoDB, S3, SQS, ו-200+ שירותי AWS ישירות ממצב, ללא עטיפת Lambda.
- **EventBridge**: ניתוק תוצאות-לוואי מה-workflow הראשי — פרסום אירוע אחד, תן לכללים עצמאיים לנתב אותו לנקודות נאמנות, ניתוח, ושירותי סקר מבלי לשנות את ה-state machine המרכזי.
- **עלות Standard לעומת Express**: Standard לפי $0.000025 למעבר מצב מתאים היטב ל-workflows קריטיים בנפח נמוך (אישור הזמנות ב-$1.88/חודש לNimbus). Express לפי מחיר בקשה-בתוספת-משך מתאים לאירועים בתדירות גבוהה שבהם Standard יעלה פי עשרות (~80x בחשבון ה-clickstream של Nimbus).
- **ארכיטקטורה מונעת-אירועים** משתמשת בשירותים כמו SNS, SQS, Lambda, ו-EventBridge לניתוק מערכות סביב אירועים במקום קריאות ישירות.
- השתמשו ב-Step Functions כשהתיאום של שלבים מורכב בעצמו וכשיכולת הביקורת חשובה. אל תשתמשו בו לרצפים דו-שלביים פשוטים, workflows בתדירות-גבוהה-מאוד, fan-out טהור, או תהליכים סינכרוניים פונים-למשתמש.

## טיפים למבחן

*SAA-C03 תחום: עיצוב ארכיטקטורות עמידות (תחום 2, משימה 2.1)*

- **אותות מקרה שימוש Step Functions**: "תזמור פונקציות Lambda מרובות," "workflow עם retries וטיפול שגיאות," "שלב אישור אנושי ב-workflow אוטומטי," "audit trail של כל שלב workflow" ← Step Functions.
- **Standard לעומת Express**: Standard לworkflows ארוכים, ניתנים לביקורת, קריטיים עסקית. Express לעיבוד אירועים בתפוקה גבוהה ומשך קצר.
- **SQS לעומת Step Functions**: SQS לתורי משימות פשוטים (יצרן/צרכן). Step Functions לworkflows רב-שלביים עם לוגיקה מורכבת, retries, ומעקב מצב.
- **אותות EventBridge**: "ניתוב אירועים משירותי AWS ליעדים," "אינטגרציה מונעת-אירועים בין שירותים," "תזמון פונקציית Lambda" ← EventBridge (לשעבר CloudWatch Events).
- **דפוס Callback**: Step Functions יכולה להשהות ביצוע ולחכות ל-callback חיצוני (task token). העובד מחזיר כשנגמר. שימושי ל-ECS tasks ארוכים שבהם אינכם רוצים מגבלת 15 הדקות של Lambda.
- **אינטגרציות SDK ישירות**: Step Functions יכולה לקרוא לשירותי AWS ישירות (DynamoDB, S3, SQS וכדומה) ללא מעבר דרך Lambda. מפחיתה עלות ו-latency לקריאות שירות פשוטות. לדוגמה, כתיבת רשומת הזמנה ל-DynamoDB יכולה להיות קריאת SDK ישירה מה-state machine ללא פונקציית Lambda: `"Resource": "arn:aws:states:::dynamodb:putItem"`. זה מחסל את ה-cold start של Lambda, עלות ביצוע Lambda, והקוד שפשוט קורא ל-`dynamodb.put_item(...)` ומחזיר.

## תרגילים

**תרגיל 1 — שחזור**

הסבירו מדוע Step Functions שימושית ל-workflows רב-שלביים. מה היא מספקת שפונקציית Lambda פשוטה הקוראת לפונקציות Lambda אחרות אינה מספקת?

*(רמז: חשבו על מה שקורה כשהשלב 3 מ-5 נכשל בכל גישה. כיצד יודעים מה קרה? כיצד מנסים שוב רק שלב 3?)*

**תרגיל 2 — תרחיש SAA-C03**

*תרחיש*: חברת שירותים פיננסיים מעבדת בקשות הלוואה במספר שלבים: בדיקת אשראי, אימות הכנסה, אימות מסמכים, ביקורת חותם (ידנית), והודעת החלטה. כל שלב יכול לקחת בין שניות (בדיקת אשראי) לימים (ביקורת חותם). החברה צריכה audit trail מלא של כל שלב לציות. שלבים אוטומטיים שנכשלים חייבים לנסות שוב אוטומטית; שלבים ידניים חייבים להשהות ולחכות להחלטה אנושית.

איזה שירות **מתאים ביותר** לדרישות אלה?

A) פונקציות AWS Lambda מקושרות זו לזו עם תורי SQS בין כל שלב  
B) AWS Step Functions Standard workflows עם דפוס Wait for callback לשלב ביקורת החותם  
C) AWS Step Functions Express workflows לשלבים האוטומטיים ו-SQS FIFO לשלב הידני  
D) Amazon EventBridge עם כללי אירוע המנתבים בין פונקציות Lambda לכל שלב

**רמז 1**: "עד ימים" משך — איזה סוג Step Functions תומך בזה?

**רמז 2**: "המתנה להחלטה אנושית" — איזה דפוס Step Functions מיועד לזה?

**רמז 3**: "Audit trail מלא לציות" — איזה שירות מספק היסטוריית מצב לכל ביצוע?

**תשובה**: B

**הסבר**: Standard workflows של Step Functions יכולים לפעול עד שנה אחת, התומכים בשלב ביקורת החותם ארוך הימים. דפוס Wait for callback משהה ביצוע בשלב החותם עם task token; כשהחותם מקבל החלטה, הוא מחזיר עם ה-token להמשך ה-workflow. Standard workflows מקליטים כל מעבר מצב — audit trail מלא לציות.

**למה לא A?** Lambda מקושרת דרך SQS לא מספקת מעקב מצב מובנה או audit trail. שלבים כושלים דורשים לוגיקת retry מותאמת. הפעלה מחדש משלב כושל ספציפי דורשת יישום מותאם.

**למה לא C?** ל-Express workflows יש משך מרבי של 5 דקות — בלתי-תואם עם שלב שיכול לקחת ימים.

**למה לא D?** EventBridge מנתב אירועים בין שירותים אבל אינו שומר מצב workflow ואינו מספק retry/audit מובנה. בניית זה על EventBridge בלבד דורשת ניהול מצב מותאם.

## סצנה לאחר הקרדיטים

ה-workflow של קבלת המסעדה היה חי.

בחודש הבא, 12 שותפי מסעדות חדשים עברו קבלה. לשניים היו כשלים במהלך שלב עיבוד התשלום (שלב 3). בשני המקרים, Step Functions לכד את השגיאה המדויקת, שמר את מצב הביצוע, ושלח התראה לצוות Nimbus.

Leo תיקן את הסיבה השורשית (מפתח API שגוי להגדרה לספק התשלומים) ואחר כך הפעיל שוב את שני הביצועים משלב 3. הביצועים הסתיימו ב-23 שניות כל אחד, ממשיכים בדיוק מהמקום שנכשלו.

שום מסעדה לא הייתה צריכה לייבוא מחדש. שום תפקידי IAM לא נוצרו פעמיים. שום אימיילי ברוכים הבאים כפולים לא נשלחו.

"לפני Step Functions," אמר Leo ל-Maya, "זה היה דורש ממישהו לעקוב ידנית אחר מה שנעשה ומה שלא נעשה לכל מסעדה, ולהפעיל ידנית את השלבים החסרים."

"ועכשיו?"

"עכשיו אני לוחץ retry במסוף. המערכת יודעת מה נעשה."

Maya חשבה על כך.

"זה לא רק שיפור טכני," אמרה. "זה ההבדל בין תהליך שמתרחב לכזה שאינו."

בפרק הבא: מה לעשות עם נתונים שאינכם ניגשים אליהם עכשיו, אבל בהחלט רוצים לשמור לנצח.
