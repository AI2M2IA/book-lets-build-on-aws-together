# פרק 9: כשהטבלה גדלה

לטבלת התפריט היו 50,000 פריטים.

זה היה על פני 287 מסעדות, כל אחת עם מיוחדים יומיים, פריטים עונתיים ווריאציות אזוריות. לחלק מהפריטים היו מאפיינים — גודל, רמת חריפות, בחירת חלבון. לחלק היו עסקות קומבו שהתייחסו לפריטים אחרים.

שאילתת SQL שאחזרה את התפריט המלא של מסעדה נהגה לחזור ב-200 אלפיות שנייה.

עכשיו לקחה ארבע שניות.

ארבע שניות הן ההבדל בין מישהו שמבצע הזמנה למישהו שסוגר את האפליקציה.

**הבעיה עם התאמת הכל לטבלה**

הנה המתח המרכזי של מסדי נתונים רלציוניים: הם מתוכננים לאחסן נתונים *מובנים* בצורות *קבועות*.

אם לכל פריט תפריט היו אותם שדות — שם, מחיר, תיאור, קטגוריה — SQL היה מושלם. היה לכם טבלת `menu_items` נקייה, שורות לכל פריט, ושאילתות הגיוניות.

אבל תפריטים אמיתיים לא עובדים כך.

**אופן שונה לחשוב על נתונים**

מסדי נתונים NoSQL מאחסנים נתונים אחרת. גישה נפוצה אחת היא *מודל המסמך*: כל רשומה מאוחסנת כמסמך עצמאי (בדרך כלל JSON), ומסמכים באותו אוסף לא חייבים לכלול אותם שדות.

פריט תפריט במודל מסמך עשוי להיראות כך:

```json
{
  "itemId": "ITEM-001",
  "restaurantId": "NIMBUS-047",
  "name": "Shrimp Arepa",
  "price": 3200,
  "modifiers": [
    { "name": "Spice Level", "options": ["mild", "medium", "hot"] },
    { "name": "Protein", "options": ["shrimp", "fish", "mixed"] }
  ],
  "available": true,
  "seasonalUntil": "2024-03-31"
}
```

פריט אחר עשוי להיראות שונה לחלוטין. צורות שונות. אותו אוסף. אין בעיה.

**פגשו את DynamoDB**

Amazon DynamoDB הוא שירות מסד הנתונים NoSQL המנוהל של AWS. הוא מאחסן נתונים כפריטים (לא שורות), ופריטים נאספים לטבלאות.

לכל פריט בטבלת DynamoDB חייב להיות **מפתח ראשי**, שמזהה אותו ייחודית. כל השאר גמיש.

המפתח הראשי יכול להיות אחד משני הצורות:

**מפתח חלוקה בלבד**: תכונה בודדת שחייבת להיות ייחודית בין כל הפריטים.

**מפתח חלוקה + מפתח מיון (מפתח ראשי מרוכב)**: שתי תכונות שיחד יוצרות שילוב ייחודי.

עבור תפריט Nimbus:

- מפתח חלוקה: `restaurantId`
- מפתח מיון: `itemId`

זה אומר שניתן לאחזר ביעילות את כל הפריטים של מסעדה ספציפית — DynamoDB יודע בדיוק באיזה חלוקה לחפש.

**כיצד DynamoDB מאחסן נתונים פנימית**

DynamoDB בנוי לסקאלינג אופקי לגדלים עצומים. הוא משיג זאת באמצעות *חלוקה* — נתונים מתפצלים על פני מכונות פיזיות רבות בהתבסס על מפתח החלוקה.

כשאתם כותבים פריט, DynamoDB מחשב hash את ערך מפתח החלוקה ומשתמש ב-hash הזה כדי לקבוע איזה חלוקה פיזית מאחסנת את הפריט. כשאתם קוראים פריט, DynamoDB עושה את אותה חישוב כדי למצוא אותו באופן מיידי.

**בחירת מפתח חלוקה טוב**:

- **טוב**: קרדינליות גבוהה, ערכים מופצים בצורה שווה (`restaurantId` עם מסעדות רבות)
- **רע**: קרדינליות נמוכה (`true/false`, `category`) — רוב הנתונים נחתים על מספר חלוקות, יוצרים "נקודות חמות"

נקודה חמה אומרת שחלוקה אחת מקבלת את רוב התנועה. חלוקה זו הופכת לצוואר בקבוק.

**מצבי קיבולת**

DynamoDB יכול לטפל במיליוני בקשות לשנייה. אבל הוא צריך לדעת כמה קיבולת להקצות.

יש שני מצבי קיבולת:

**קיבולת מופרשת**: אתם מציינים כמה יחידות קריאה וכתיבה אתם רוצים. DynamoDB שומר קיבולת זו עבורכם.

**קיבולת לפי דרישה**: DynamoDB מתרחב אוטומטית עם התנועה בפועל.

**עקביות: עד כמה טרי הנתונים שלכם?**

כשאתם קוראים מ-DynamoDB, יש לכם בחירה:

**קריאה עקבית בסופו של דבר**: ברירת מחדל. זולה יותר, והתוצאה עשויה לפגר מעט אחרי כתיבה שהושלמה לאחרונה.

**קריאה עקבית מאוד**: DynamoDB יכול להחזיר את הערך הסופי שהתחייב. עולה יותר קיבולת קריאה.

עבור נתוני תפריט, עקביות בסופו של דבר בסדר. פריט תפריט שהוא אלפית שנייה מיושן לא חשוב.

## סיכום

- DynamoDB הוא שירות מסד נתונים NoSQL המנוהל של AWS.
- פריטים מאוחסנים כמסמכים גמישים — אין צורך בסכמה קבועה.
- לכל פריט חייב להיות **מפתח ראשי**: מפתח חלוקה לבדו, או מפתח חלוקה + מפתח מיון.
- מפתח החלוקה קובע איזה חלוקה פיזית מאחסנת את הפריט.
- **לפי דרישה** מתרחב אוטומטית; **מופרש** זול יותר אם התנועה שלכם ניתנת לחיזוי.
- קריאות **עקביות בסופו של דבר** זולות ומהירות יותר. קריאות **עקביות מאוד** תמיד עדכניות.

## עצות לבחינה

*SAA-C03 דומיין: עיצוב ארכיטקטורות ביצועיות גבוהות (דומיין 3, משימה 3.3)*

- דעו את חוקי מפתח החלוקה: **קרדינליות גבוהה, הפצה שווה**. חלוקות חמות הן מלכוד בחינה נפוץ.
- **On-demand לעומת provisioned**: לפי דרישה לתנועה בלתי צפויה; provisioned (עם Auto Scaling) לעומסי עבודה ניתנים לחיזוי.
- **DynamoDB Streams**: לוכד שינויים ברמת פריט בזמן אמת. תרחיש בחינה נפוץ: "הפעל פונקציית Lambda כשרשומה משתנה."
- **Global Tables**: שכפול רב-אזורי, רב-פעיל ליישומים מבוזרים גלובלית.
- **DAX (DynamoDB Accelerator)**: שכבת מטמון בזיכרון עבור DynamoDB. מפחית זמן תגובה קריאה ממילישניות למיקרושניות.
