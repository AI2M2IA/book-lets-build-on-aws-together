# פרק 21: מכולות משלוח לקוד

לפני 1956, טעינת מטען לאוניה הייתה משא ומתן מיומן ומתמחה. לכל אוניה היו תאי מטען שונים. לכל נמל היו עגורנים שונים. לכל מוביל היו מערכות שונות למעקב אחרי מה ולאן. ארגז סחורה עבר ממשאית לרציף לאוניה לרציף למשאית דרך שרשרת אנשים שכולם טיפלו בו בצורה שונה. מטען אבד. מטען ניזוק. אותן סחורות, שנשלחו פעמיים, הגיעו במצב שונה כי הטיפול היה שונה בשני הפעמים.

התשובה, כשמישהו לבסוף שאל אותה בבירור, הייתה: תקנו את המכולה. אל תפתרו את הבעיה בכל נמל. פתרו אותה פעם אחת, ברמת המכולה. שלחו את הקופסה, לא רק את תכולתה.

מכולת המשלוח התקנית לא רק הפכה את המשלוח למהיר יותר. היא הפכה אותו *לצפוי*. תכולת מכולה בשנגחאי הייתה באותו מצב כשהגיעה לרוטרדם — כי המכולה הגנה עליה מפני שונות בכל נקודת העברה.

זו הייתה בדיוק אותה הבעיה של Leo. ה-API של Nimbus "נטען" בצורה שונה בכל "נמל": staging נפרס בצורה שונה מ-production, instance אחד נפרס בצורה שונה מ-instance שלוש, ושישה שבועות של שינויים לא מתועדים הפכו את הצי לבלתי צפוי.

המכולה לא הייתה הופכת את Leo למפתח מהיר יותר. היא הייתה הופכת את הפריסות לצפויות.

---

הגירת ה-Lambda הפחיתה את חשבון ה-EC2 לשירותים קטנים יותר. אבל ה-API המרכזי היה שונה — הוא פעל ברציפות, נשא את כל תנועת ההזמנות, וצבר היסטוריית הגדרות במשך שמונה חודשים. Lambda פתרה סרק. מיכלים יפתרו חוסר עקביות.

ה-API המרכזי לא היה סרק; לא יכול היה לעבור ל-Lambda. אבל הייתה לו בעיה אחרת: מכונות ה-EC2 שהריצו אותו סטו זו מזו.

---

Leo למד שלא לאמור "זה עובד על המחשב שלי" בקול. זה לא היה הגנה — זה היה אבחון. והאבחון הפעם היה מכונת EC2 ייצור מספר שלוש, שקיבלה עדכון ספרייה שישה שבועות קודם שאף אחד לא תיעד, שלשתי המכונות האחרות לא קיבלו, ושגרמה כעת לבאג שקיים רק שם, באותו instance, בלתי נראה בכל מקום אחר.

הוא בילה שלוש שעות בלילה הקודם עוקב אחריו.

"בכל פעם שאנחנו פורסים," אמר למחרת בבוקר, "אנחנו מתאמים על פני instances מרובים. גרסה חדשה, תלויות שונות. עובד ב-staging, נשבר ב-production כי הסביבות סטו."

"כי מישהו עדכן חבילה ב-instance שלוש מבלי לעדכן את האחרים," אמרה Priya. לא ברשעות.

"הייתי צריך גרסה ספציפית של—"

"אני יודעת," אמרה. "ועכשיו ל-instance שלוש יש היסטוריה שונה מ-instance אחת ושתיים. זה קריסת תצורה. שקטה עד שהיא לא."

"מה הפתרון בפועל?" שאלה Maya.

"הפסיקו להתייחס לשרתים כדברים קבועים שמגדירים," אמרה Priya. "התחילו להתייחס אליהם כיחידות מתכלות שמחליפים."

**מה הוא Container?**

"חשבו על זה כמו מכולת משלוח," אמר Leo, תופס טוש. "המכולה לא אכפת לה על איזו אוניה היא נמצאת. לאוניה לא אכפת מה בתוך המכולה. הם הסכימו על המידות ומנגנון הנעילה. כל השאר בתוך הקופסה."

**container** הוא יחידה קלה וניידת שאורזת את היישום שלכם יחד עם כל מה שהוא צריך להריץ: ה-runtime (Python 3.11, Node.js 20, Java 17), הספריות והתלויות, קבצי התצורה, וקוד היישום עצמו.

בשונה ממכונה וירטואלית (שמדמה מחשב שלם, כולל גרעין מערכת ההפעלה), container חולק את גרעין ה-OS של המארח תוך שמירת כל שאר מבודד. זה הופך containers למהירים להפעלה (שניות, לפעמים אלפיות שנייה) וקטנים (מגה-בייטים, לא גיגה-בייטים).

טכנולוגיית ה-container הפופולרית ביותר היא **Docker**. Docker image היא התבנית — snapshot של היישום וסביבתו. Docker container הוא instance פועל של אותה תמונה.

המאפיין המרכזי: **אי-שינוי**. תמונה שנבנתה היום תפעל זהה על כל מארח התומך ב-Docker — מחשב נייד, מכונת EC2, שרת במרכז נתונים אחר. הסביבה אפויה פנימה. קריסת תצורה בלתי אפשרית.

"אז במקום לדאוג מה מותקן על מכונת ה-EC2," אמר Leo, "אנחנו בונים תמונה שיש לה הכל. התמונה פועלת באותה צורה בכל מקום."

"ואם אתם צריכים לבדוק אותה מקומית, אתם מריצים את אותה תמונה," הוסיפה Priya. "לא עוד 'זה עובד על המחשב שלי.'"

**בניית Docker Image ודחיפה ל-ECR**

לפני שאיזה orchestrator יכול לנהל את ה-container, Leo היה צריך לבנות אותו ולאחסן אותו במקום שבו ECS יכול למשוך ממנו.

הוא כתב את ה-Dockerfile:

```dockerfile
FROM python:3.11-slim

WORKDIR /app

COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

COPY . .

EXPOSE 8000
CMD ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8000"]
```

השורה המרכזית: `FROM python:3.11-slim`. לא Python 3.9. לא Python 3.10. 3.11 — הגרסה הספציפית שעליה הסכים הצוות, אפויה לתוך התמונה. כל instance שמריץ תמונה זו ישתמש בדיוק ב-Python 3.11. התנהגות עיגול מודול ה-decimal תהיה זהה בכל מקום.

הוא בנה את התמונה מקומית: `docker build -t nimbus-api:1.0.0 .`

הבנייה לקחה 4 דקות. Docker משך את תמונת הבסיס, התקין תלויות, העתיק את קוד היישום, ויצר תמונה עם תג `nimbus-api:1.0.0`.

הוא הריץ אותה מקומית: `docker run -p 8000:8000 nimbus-api:1.0.0`

ה-API התחיל. אותו פורט, אותה התנהגות כמו שרת ה-production — כי הסביבה הייתה זהה.

אחר כך הוא דחף אותה ל-ECR:

```bash
# אימות Docker ל-ECR
aws ecr get-login-password --region us-west-2 |   docker login --username AWS --password-stdin   123456789012.dkr.ecr.us-west-2.amazonaws.com

# תיוג התמונה עבור ECR
docker tag nimbus-api:1.0.0   123456789012.dkr.ecr.us-west-2.amazonaws.com/nimbus-api:1.0.0

# דחיפה
docker push 123456789012.dkr.ecr.us-west-2.amazonaws.com/nimbus-api:1.0.0
```

הדחיפה לקחה 2 דקות. ECR אחסן את התמונה, הפעיל מיד סריקת תמונה, ודיווח תוצאות תוך 5 דקות.

**Amazon ECS: ה-Orchestrator**

הפעלת container אחד פשוטה. הפעלת עשרות containers על פני מארחים מרובים, ניתוב תנועה ביניהם, הפעלה מחדש של containers שנכשלו, פריסת גרסאות חדשות ללא השבתה — זה דורש **orchestrator**.

**Amazon ECS (Elastic Container Service)** הוא שירות תזמור containers מנוהל של AWS. אתם מגדירים:

- **Task definition**: איזה container image להריץ, כמה CPU וזיכרון, אילו משתני סביבה, אילו פורטים לחשוף
- **Service**: כמה עותקים של ה-task להריץ, כיצד לטפל בכשלים ופריסות
- **Cluster**: תשתית המחשוב הבסיסית

ECS מטפל בשאר: מיקום tasks על קיבולת זמינה, הפעלה מחדש של tasks שנכשלו, ניקוז חיבורים במהלך פריסות, רישום tasks בריאים ל-load balancer.

עבור Nimbus, ה-API עבר ממכונות EC2 עם פריסות מנוהלות ידנית ל-ECS. כל פריסה חדשה דחפה Docker image חדש ל-**Amazon ECR (Elastic Container Registry)** — registry container מנוהל של AWS — ו-ECS גילגל אותה על כל ה-tasks ללא השבתה.

**Fargate לעומת EC2 Launch Type**

ECS יכול להריץ containers בשני מצבים:

**EC2 launch type**: אתם מנהלים את מכונות ה-EC2 הבסיסיות. אתם אחראים לטלוא את המכונות, לקבוע את גדלן הנכון, ולוודא שיש מספיק קיבולת לcontainers שלכם. שליטה רבה יותר, אחריות רבה יותר.

**Fargate (serverless compute למיכלים)**: AWS מנהל את התשתית הבסיסית לחלוטין. אתם מציינים CPU וזיכרון לכל task; Fargate מספק את הקיבולת הנכונה אוטומטית. אין מכונות EC2 לנהל. אתם משלמים לפי vCPU-שנייה ו-GB-שנייה של זיכרון.

Fargate הוא מודל "containers serverless" — אתם מקבלים את בידוד הסביבה של containers מבלי לנהל שרתים. הפשרה: פחות שליטה על הגדרת instance הבסיסית ועלות מעט גבוהה יותר ליחידה.

"כמה זה עולה בחודש?" שאל Tom, פותח את מחשבון התמחור. "Fargate לעומת EC2 launch type — אני רוצה לראות את המספרים בפועל."

האמדן של Leo — הזה שכולם נושאים בראש — היה שFargate יעלה יותר. נוחות serverless, מחיר פרמיום. הוא ניחש אולי עשרים או שלושים אחוז מעל EC2.

"הריצו את המספרים בפועל," אמר Tom, כי זה היה Tom.

שירות ה-API של Nimbus הריץ 3 tasks, כל אחד זקוק ל-0.5 vCPU וזיכרון של 1GB, 24/7:

**Fargate**: $0.04048/vCPU-שעה × 0.5 × 3 × 720 שעות = $43.72/חודש עבור CPU. $0.004445/GB-שעה × 1 × 3 × 720 = $9.60/חודש עבור זיכרון. סה"כ: $53.32/חודש.

**EC2 launch type** (3 × t3.medium ב-$0.0416/שעה): $0.0416 × 3 × 720 = $89.86/חודש.

"רגע," אמר Tom. "Fargate זולה יותר?"

"בגודל הזה, כן," אמר Leo. "Fargate מחייב בדיוק על מה שאתם מקצים. למכונות EC2 יש תקורה — ה-OS וסוכן ה-ECS צורכים קצת CPU וזיכרון לפני שה-containers שלכם אפילו מתחילים. t3.medium נותנת 2 vCPU ו-4GB, אבל אתם משתמשים ב-0.5 vCPU ו-1GB לכל container. השאר מתבזבז."

"אבל EC2 launch type מאפשר לכם לארוז tasks מרובים על instance אחד."

"כן. בהיקפים גדולים יותר, עם bin-packing זהיר, EC2 launch type הופך לזול יותר. בהיקף שלנו — שלושה tasks — Fargate מנצח."

Tom כתב זאת.

עבור Nimbus: Fargate לשירות ה-API. הם לא רצו לנהל מכונות EC2 עבור containers.

אם אתם מתמכלים עם Fargate, אתם מחסלים את כל תקורת ניהול ה-EC2 — אבל אתם ויתרתם על היכולת להתאים סוגי instances, שחשובה לעומסי GPU או רשת מתמחים. אם אתם בוחרים ECS לפשטות AWS-נייטיב, אתם מקבלים אינטגרציה הדוקה של IAM ו-ALB — אבל אתם נעולים מחוץ לאקוסיסטם Kubernetes, שדורש ארכיטקטורה מחדש אם תצטרכו ניידות מרובת-ענן מאוחר יותר.

**Amazon EKS: כשאתם צריכים Kubernetes**

**Kubernetes** הוא מערכת תזמור containers קוד-פתוח — בעיקרה תקן התעשייה לניהול containers בקנה מידה. עוצמתית, ניתנת להרחבה, ומורכבת.

**Amazon EKS (Elastic Kubernetes Service)** הוא שירות Kubernetes המנוהל של AWS. הוא מריץ את Kubernetes control plane (שכבת הניהול) עבורכם, בזמן שאתם מנהלים את worker nodes (או משתמשים ב-Fargate גם לאלה).

אולי תהיתם: אם Kubernetes הוא תקן התעשייה וכל מודעת עבודה מזכירה אותו, מדוע שלא פשוט נשתמש בו? כי "תקן תעשייה" מתאר מה שחברות גדולות עם צוותי פלטפורמה ייעודיים משתמשות. לצוות של שישה אנשים שבונה אפליקציית הזמנת אוכל, Kubernetes מוסיף מורכבות תפעולית ללא תועלת מעשית כרגע. המורכבות אמיתית; התועלת תיאורטית בהיקף זה.

Kubernetes מספק ערך ברמת מורכבות שרוב הצוותים אינם צריכים: הגדרות משאב מותאמות לבניית פלטפורמות פנימיות, אילוצי תזמון מתקדמים, pod disruption budgets לשליטה עדינה בפריסה, ואינטגרציה של service mesh לניהול תנועה בין מאות microservices. אלה יכולות אמיתיות. הן גם יכולות שסטארט-אפ בגודל Nimbus לעולם לא ינצל.

עיקרון הנדסי הנקרא לפעמים YAGNI: You Aren't Gonna Need It. ECS נותנת ל-Nimbus כל מה שהיא צריכה כרגע. EKS נותנת לה יותר ממה שהיא צריכה, בתוספת עקומת למידה משמעותית ותקורה תפעולית. "זה יהיה שימושי מאוחר יותר" אינה סיבה טובה להוסיף מורכבות עכשיו.

מתי להשתמש ב-EKS לעומת ECS?

**השתמשו ב-ECS** אם:

- אתם בעיקר ב-AWS ורוצים חוויה פשוטה יותר, יותר AWS-נייטיב
- לצוות שלכם אין מומחיות Kubernetes קיימת
- אתם רוצים תקורה תפעולית פחותה

**השתמשו ב-EKS** אם:

- אתם צריכים תכונות ספציפיות ל-Kubernetes (Custom Resource Definitions, charts של Helm, אקוסיסטם Kubernetes)
- הצוות שלכם כבר מכיר Kubernetes
- אתם מריצים סביבה היברידית (חלק on-premises, חלק ב-AWS) ורוצים שכבת תזמור עקבית
- לעומס העבודה שלכם יש דרישות התואמות את הרחבת Kubernetes

**רשת Containers: IPs חולפים וגילוי שירותים**

דבר אחד שתופס צוותים לא מוכנים כשעוברים למיכלים: כתובת ה-IP של container משתנה בכל פעם שהוא מופעל מחדש.

בעולם EC2, ל-instances היו IPs פרטיים יחסית יציבים. יכולתם (אם כי לא הייתם צריכים) לכתוב אותם בקוד בקבצי תצורה. שירותים הכירו זה את זה לפי IP.

בעולם ה-containers, כל task ב-ECS מקבל IP מ-subnet ה-VPC כשהוא מתחיל. כשהוא נעצר וtask חדש מתחיל (כחלק מפריסה או הפעלה מחדש), אותו task חדש מקבל IP שונה.

"מה קורה כששירות מוגדר בקוד ל-`10.0.1.45` ו-container זה מוחלף ב-`10.0.1.82`?" שאלה Priya. "השירות הקורא מתחיל לפגוע בחלל."

לכן גילוי שירותים חשוב בסביבות containers. ECS + Application Load Balancer מטפל בזאת אוטומטית: שם ה-DNS של ALB יציב; ECS רושם tasks בריאים לקבוצת ה-target; ה-ALB מנתב לאיזה tasks שפועלים כרגע באופן בריא. השירות הקורא מדבר לשם ה-DNS של ALB, לא ל-IPs בודדים של containers.

לתקשורת שירות-לשירות פנימית (לא פונה למשתמש), **AWS Cloud Map** מספק גילוי שירותים: כל שירות ECS רושם עצמו ב-Cloud Map, שמספק שם DNS יציב. שירות ההזמנות קורא `http://notification.nimbus.local:8080`, ו-Cloud Map פותר זאת לאיזה tasks בשירות ההתראות פועלים כרגע באופן בריא.

"אז containers מדברים זה לזה דרך שמות DNS, לא IPs?" אישר Leo.

"נכון. ה-IP חולף. שם ה-DNS הוא החוזה."

**הזרקת סודות: אין סודות במשתני סביבה**

לפריסת ה-EC2 המקורית הייתה בעיה ש-Priya סימנה במשך חודשים: סודות (סיסמת מסד נתונים, מפתחות API, אישורי SES) אוחסנו במשתני סביבה על מכונת ה-EC2, שנקבעו דרך סקריפט פריסה.

משתני סביבה נגישים לכל תהליך שפועל על ה-instance. הם מופיעים בכלי איתור באגים, בחלק מדוחות קריסה, וברשימות תהליכים. הם גם גלויים ב-CloudWatch אם מתעדים אותם (מה שחלק מכלי הפיתוח עושים כברירת מחדל).

מיכלים לא פותרים זאת אוטומטית — עדיין ניתן להעביר סודות כמשתני סביבה בהגדרת task של ECS. והגדרות task של ECS מאוחסנות ב-AWS console, גלויות לכל מי שיש לו גישה ל-ECS.

הדפוס הנכון: **אינטגרציה של AWS Secrets Manager + הגדרת task של ECS**.

במקום לאחסן את סיסמת מסד הנתונים בהגדרת task:

```json
"secrets": [
  {
    "name": "DB_PASSWORD",
    "valueFrom": "arn:aws:secretsmanager:us-west-2:123456789012:secret:nimbus/prod/db-password"
  }
]
```

ECS מאחזר את הסוד מ-Secrets Manager בעת הפעלת task ומזריק אותו לתוך ה-container כמשתנה סביבה. ערך הסוד אינו אי פעם מאוחסן בהגדרת task — רק ה-ARN של סוד Secrets Manager. ה-container מקבל את הערך בזמן ריצה. Secrets Manager יכול לסובב את הערך מבלי לשנות את הגדרת task.

"ואם מישהו קורא את הגדרת task?" שאלה Priya. "הם יראו את ARN של Secrets Manager, אבל לא את הערך."

"ובלי הרשאות IAM הנכונות," אישר Leo, "הם לא יכולים לאחזר את הערך מ-Secrets Manager גם."

"זה העיצוב," אמרה Priya. "לתפקיד הביצוע של ה-task יש הרשאה לקרוא את הסוד הספציפי הזה. כלום אחר. פריצה להגדרת task נותנת לך ARN, לא סיסמה."

"באיזה מהם עלינו להשתמש?" שאלה Maya. "ולמה לא Kubernetes? זה בכל מודעת עבודה. בכל הרצאת כנס."

"ECS," אמרה Priya מיד. "אין לנו מומחיות Kubernetes. ECS עושה כל מה שאנחנו צריכים. הוספת Kubernetes כרגע תוסיף מורכבות תפעולית ללא תועלת מעשית."

Soo-Jin, שהריצה clusters של Kubernetes בחברתה הקודמת, הנהנה. "נשאתי את ה-pager הזה. לא תרצו אותו עד שתצטרכו אותו."

"תמיד אפשר לעבור ל-EKS מאוחר יותר אם נגדל מ-ECS," הוסיף Leo.

זו תשובת בכיר נכונה: בחרו את הכלי הפשוט יותר שמתאים לצרכים הנוכחיים שלכם.

**ECR: אבטחת התמונות שלכם**

"ומה אם מישהו מנסה לפרוץ דרך תמונת בסיס פגיעה?" שאלה Priya. "מישהו תופס תמונה ישנה עם CVE ידוע ומשתמש בה כדי לקבל אחיזה בcontainer של היישום?"

זו השאלה הנכונה לשאול לפני פריסת כל container ב-production.

**Amazon ECR (Elastic Container Registry)** מאחסן את Docker images שלכם ויכול לסרוק אותם לפגיעויות ידועות לפני פריסה. סריקת תמונות ECR בודקת את התמונה מול מסד נתונים של CVEs (Common Vulnerabilities and Exposures) ידועים ומסמנת בעיות לפי חומרה.

המדיניות ש-Priya כתבה: אף תמונה עם CVE של חומרה CRITICAL לא תיפרס ל-production. צינור ה-CI/CD יבדוק את תוצאות הסריקה לפני עדכון שירות ECS. אם נמצאה פגיעות קריטית, הצינור ייכשל ויתריע לצוות.

"זה לא פרנויה," אמרה Priya. "זה פשוט בדיקה לפני שפורסים."

**כיצד Containers משנים פריסות**

לפני containers, פריסת גרסה חדשה של ה-API של Nimbus פירושה:

1. התחברות ב-SSH לכל מכונת EC2
2. משיכת הקוד האחרון מ-Git
3. התקנה/עדכון של תלויות
4. הפעלה מחדש של תהליך היישום
5. אימות בריאות
6. מעבר למכונה הבאה

זה היה מועד לשגיאות ואיטי. נדרש תיאום. אם שלב 3 נכשל ב-instance 4, הייתה לכם פריסה מעורבת עם instances מסוימים שמריצים גרסה ישנה וחלק שנכשלים בהפעלת הגרסה החדשה.

עם ECS ומיכלים:

1. בניית Docker image חדש (אוטומטי בצינור CI/CD)
2. דחיפה ל-ECR
3. עדכון שירות ECS לשימוש בגרסת התמונה החדשה

ECS מטפל בפריסה המתגלגלת: מתחיל tasks חדשים עם התמונה החדשה, ממתין שיהיו בריאים, ואז עוצר tasks ישנים. פריסה ללא-השבתה, אוטומטית.

אם הגרסה החדשה נכשלת בבדיקות בריאות, ECS עוצר את הפריסה והגרסה הישנה ממשיכה לשרת תנועה.

**הגדרת הפריסה המינימלית: בדיקות בריאות**

כל הבטיחות של פריסות container תלויה בבדיקות בריאות שעובדות בפועל.

ECS משתמש בשני סוגי בדיקות בריאות:

**בדיקת בריאות ברמת container**: מוגדרת ב-Dockerfile או הגדרת task. פועלת בתוך ה-container לאימות שהיישום מגיב.

```dockerfile
HEALTHCHECK --interval=30s --timeout=5s --retries=3   CMD curl -f http://localhost:8000/health || exit 1
```

**בדיקת בריאות של קבוצת target של ALB**: ה-load balancer שולח מדי פעם בקשות HTTP לנקודת קצה בריאות. Tasks שנכשלים בבדיקת הבריאות מוסרים מקבוצת ה-target.

אם אף בדיקת בריאות אינה מוגדרת כראוי, ECS מחשיב כל task בריא — ויפרוס תמונה שבורה מבלי לעצור. זהו שגיאת הפריסה הנפוצה ביותר של containers.

"האם נקודת קצה בדיקת הבריאות יכולה לדלוף מידע פנימי?" שאלה Priya.

נקודת קצה הבריאות ב-`/health` החזירה רק: `{"status": "ok"}`. ללא מספרי גרסה, ללא מצבי תלויות, ללא הגדרה פנימית. כל מידע בתגובת הבריאות יכול להיות שימושי למישהו שממפה את היישום. שמרו על נקודות קצה בריאות מינימליות.

לסטטוס בריאות פנימי מפורט (קישוריות מסד נתונים, בדיקות תלויות), השתמשו בנקודת קצה `/health/detail` מאומתת נפרדת — נגישה רק מבתוך ה-VPC.

**רישום מובנה: החלון היחיד לתוך Container פועל**

ב-EC2, משהו משתבש ואתם מתחברים ב-SSH. אתם עוקבים אחרי קובץ הלוג. מסתכלים על טבלת התהליכים. בודקים שימוש בדיסק. מסתובבים.

ב-container, אין SSH. ה-container חולף — הוא עשוי לפעול על כל מארח באשכול, ו-ECS יחליף אותו ללא התראה אם הוא נכשל בבדיקות בריאות. עד שאתם חושבים על התחברות ב-SSH, ה-container שרציתם לבחון אולי כבר לא קיים.

לוגים אינם נוחות איתור באגים בסביבות מתמכלות. הם הראיה היחידה שמשהו קרה.

"ומה אם container נכשל בשקט ואין לנו לוגים?" שאלה Priya בסקירת ארכיטקטורת המיכלים. "task יכול לצאת עם קוד 1 ולעולם לא נדע את הסיבה אם הלוגים לא נלכדו לפני שהוא סיים."

זה לא היפותטי. זה קורה בפריסות containers ראשונות, בעקביות.

הדפוס הנכון: הגדירו כל container לשלוח לוגים מובנים ל-**Amazon CloudWatch Logs** באמצעות מנהל הלוג `awslogs`. ECS מטפל בשינוע אוטומטית — אין סוכן לוג להתקין, אין צורך ב-container מלווה.

בהגדרת task:

```json
"logConfiguration": {
  "logDriver": "awslogs",
  "options": {
    "awslogs-group": "/ecs/nimbus-api",
    "awslogs-region": "us-west-2",
    "awslogs-stream-prefix": "ecs"
  }
}
```

כל שורה שנכתבת ל-stdout או stderr בתוך ה-container נלכדת ונשלחת לקבוצת לוג `/ecs/nimbus-api`, מאורגנת לפי מזהה task. ECS יוצר stream לוג חדש לכל task, כך שתוכלו למצוא את הלוגים ל-container הספציפי שנכשל — גם לאחר שהוחלף.

לתפקיד הביצוע של task נדרשת הרשאה לכתוב ל-CloudWatch Logs. ללא זה, מנהל הלוג נכשל בשקט וכל פלט הלוג אובד.

**לוגים מובנים לעומת טקסט רגיל**: לוגים בטקסט רגיל ("הזמנה 7741 הוזמנה") דורשים grep. לוגי JSON מובנים (`{"event": "order_placed", "order_id": "7741", "restaurant_id": "47", "amount": 3200}`) ניתנים לשאילתה עם CloudWatch Logs Insights באמצעות syntax הדומה ל-SQL:

```
fields @timestamp, event, order_id, restaurant_id
| filter event = "order_placed"
| stats count(*) by restaurant_id
| sort count desc
| limit 10
```

שאילתה זו פועלת ישירות על קבוצת הלוג. ללא מסד נתונים. ללא pipeline נתונים. ללא ETL. התשובה שם בשניות.

זה לא מחליף את data lake הניתוח שנבנה בפרק 26. זה עונה על שאלות תפעוליות — "כמה הזמנות ממסעדה 47 בשלושים הדקות האחרונות?" — באמצע תקרית, כשאין זמן להריץ שאילתת Athena.

**CloudWatch Container Insights**

**Container Insights** הוא תכונת CloudWatch שאוספת ומצברת מדדים ברמת container — CPU, זיכרון, קלט/פלט רשת, קלט/פלט אחסון — לפי cluster ECS, שירות ו-task. במקום מדדים ברמת EC2 (כיצד המארח מתנהג?), אתם רואים מדדים ברמת task (כיצד שירות ECS ספציפי זה מתנהג?).

הפעילו אותו עם הגדרה אחת על cluster ה-ECS:

```bash
aws ecs update-cluster-settings \
  --cluster nimbus-production \
  --settings name=containerInsights,value=enabled
```

לאחר ההפעלה:

- אתם רואים dashboard לכל שירות: ספירת tasks, ניצול CPU, ניצול זיכרון
- אתם יכולים להתריע על CPU ברמת task (במקום CPU של מארח EC2, שהוא אות מאוד כהה)
- אתם יכולים לקשר קפיצות זיכרון לאירועי לוג — זיכרון ה-task עלה ל-95% ב-14:22; הלוגים מראים קפיצה בבקשות נכנסות מייבוא תפריט של מסעדה 47 בדיוק ב-14:21

"כמה זה עולה בחודש?" שאל Tom.

Container Insights מחייב עבור המדדים המותאמים ואחסון הלוג שהוא מייצר. בהיקף של Nimbus (שלושה שירותים, 3-6 tasks כל אחד), זה היה כ-$12/חודש — פשרה סבירה לנראות תפעולית ברמת task.

Leo הפעיל אותו תוך יום.

בפעם הראשונה שtask נכשל בבדיקת בריאות והוחלף על ידי ECS, ה-dashboard של Container Insights לכד את האירוע אוטומטית: מזהה task, זמן התחלה, זמן כשל, קוד יציאה. stream הלוג של CloudWatch לאותו task שמר את 40 השורות האחרונות של פלט לפני הסיום — שהראה חריגה ללא טיפול שהופעלה על ידי JSON תפריט פגום ממסעדה שותפה חדשה.

ללא Container Insights ורישום מובנה: קפיצה מסתורית בשיעורי שגיאה, חקירה שדרשה התחברות SSH למארח שכבר אינו מריץ את ה-task הכושל, 45 דקות של ניחושים.

עם הם: קישור ל-stream לוג ב-dashboard של CloudWatch, החריגה המדויקת, מזהה המסעדה, השדה הפוגע — בפחות מחמש דקות.

"ללא SSH," אמר Leo, בוחן את הpost-mortem. "ללא השבתה לחקירה. הלוגים עשו את העבודה."

"הלוגים עושים את העבודה," אמרה Priya, "רק אם הגדרתם אותם להיות מלכודים."


**מתי Containers הם הבחירה הלא נכונה**

"רגע — אבל *למה* שלא נמכל הכל?" שאלה Maya. "בדיוק שכנעתם אותי שmיכלים פותרים את כל בעיות קריסת התצורה. למה שלא נריץ כל שירות כ-container?"

זו הייתה אותה שאלה שהיא שאלה על Lambda. התשובה הייתה דומה.

מיכלים מוסיפים דרישות תפעוליות: אתם צריכים registry מיכלים (ECR), צינור CI/CD שבונה ודוחף תמונות, orchestrator (ECS), ניטור מוגדר לנראות ברמת task במקום ברמת instance, וצוות שמבין Docker וניהול גרסאות תמונות.

עבור שירות שכבר עובד טוב על EC2, יציב, ואינו סובל מקריסת תצורה, עלות המיכול שלו עשויה לעלות על התועלת.

מקרים ספציפיים שבהם containers הם הבחירה הלא נכונה:

**שירותים עם מצב שאינם בנויים לניידות containers**: מסדי נתונים ב-containers דורשים ניהול אחסון עמיד זהיר. רוב הצוותים שמריצים מסדי נתונים ב-containers מחזירים אותם בסופו של דבר לשירותים מנוהלים (RDS, ElastiCache) לאחר פגישה עם המורכבות הזו.

**שירותים עם דרישות חומרה מתמחות**: עומסי GPU, הגדרות ממשק רשת ספציפיות, או עיבוד מבוסס FPGA דורשים מכונות EC2 עם חומרה ספציפית. מיכלים לא משנים זאת — עדיין תשתמשו ב-EC2 launch type, רק עם containers על גביו, והפשטת ה-container מוסיפה מורכבות ללא תועלת.

**סקריפטים ועבודות פשוטות מאוד**: סקריפט Python בן 40 שורות שפועל פעם בשבוע ואין לו בעיות קריסת תלויות. הוספת Docker, ECR, הגדרות ECS task, וצינור CI/CD לזה אינה מידתית. Lambda פשוטה יותר. עבודת cron פשוטה על EC2 עשויה להיות פשוטה עוד יותר.

"העיקרון," אמר Leo, "זהה תמיד: התאימו את הכלי לבעיה. מיכלים פותרים קריסת תצורה ועקביות פריסה. אם אין לכם את הבעיה הזו, אינכם צריכים מיכלים."

## AWS Batch: מיכלים לעבודות בקנה מידה גדול

ECS ו-EKS מתוכננים לשירותים ארוכי טווח — יישומים שפועלים ברציפות, מקבלים בקשות, ומתרחבים עם תנועה. אבל חלק מעומסי העבודה שונים: הם פועלים למשך זמן קבוע, מעבדים מערך נתונים מוגדר, ואחר כך עוצרים. יצירת חשבוניות סוף-חודש עבור מאות מסעדות. הרצת עבודת אימון למידת מכונה. עיבוד ייצוא ניתוח לילי.

עבור עומסי עבודה אלה, אינכם רוצים שירות — אתם רוצים עבודה.

**AWS Batch** הוא שירות מנוהל במלואו שמריץ עבודות מחשוב אצוות בכל היקף. אתם מגדירים את העבודה שלכם כ-Docker container (אותו פורמט container ש-ECS משתמש), ו-Batch מטפל בשאר: אספקת מחשוב EC2 או Fargate, תזמון עבודות לתורים, קנה מידה של קיבולת למעלה כשעבודות מגיעות ובחזרה לאפס כשהן מסתיימות.

מושגי מפתח:

- **הגדרת עבודה:** ה-Docker container, דרישות משאב (vCPU, זיכרון), והפקודה להרצה
- **תור עבודות:** מקום שבו עבודות שהוגשו ממתינות לפני הרצה; כל תור מקושר לסביבת מחשוב אחת או יותר
- **סביבת מחשוב:** קיבולת EC2 או Fargate הבסיסית. יכולה להשתמש ב-Spot Instances לחיסכון של עד 90% — Batch מטפל בהפרעות וניסיונות חוזרים אוטומטית

"רגע — אבל *למה* שנשתמש ב-Batch במקום פשוט להריץ ECS task?" שאלה Maya.

"כי שירות ECS תמיד דולק," אמר Leo. "הוא ממתין לבקשות. עבודת Batch רצה, מסתיימת, ו-Batch מוריד את המחשוב בחזרה לאפס. לא משלמים כלום בין הרצות."

Tom הרים עיניים מדף התמחור. "ו-Spot Instances?"

"Batch יכול לפעול על Spot. אם Spot Instance מיוחל באמצע עבודה, Batch מנסה שוב אוטומטית. לעבודת חשבוניות של 45 דקות, זה בסדר."

**לעומת ECS/EKS:** ECS/EKS מריצים שירותים — תמיד דולקים, מונעי-בקשה. Batch מריץ עבודות — משך קבוע, מונע-נתונים, קנה מידה לאפס בסרק.

**לעומת Lambda:** ל-Lambda יש timeout של 15 דקות. עבודות Batch יכולות לפעול שעות או ימים.

הקשר Nimbus: עבודת יצירת החשבוניות הלילית לוקחת 45 דקות עבור מאות שותפי מסעדות. Lambda מסתיים ב-15 דקות. שירות ECS תמיד-דולק מבזבז כסף 23 שעות ביום. Batch מריץ את העבודה על Spot Instances, מסיים ב-38 דקות, עולה $1.20, ומכבה.

"זה זול יותר מהקפה שקניתי בזמן שחיכיתי לסקריפט הישן לסיים," אמר Leo.

"ואין EC2 לנהל," הוסיפה Priya. "Batch מספק אותה, מריץ, מסיים."

## חוזקות ומגבלות

**מיכלים**:

- מחסלים אי-עקביות סביבה ("עובד על המחשב שלי")
- מאפשרים פריסות מהירות ואמינות
- בלתי-משתנים — אותה תמונה פועלת זהה בכל מקום
- יעילים — קלים יותר מ-VMs, אתחול מהיר יותר

**ECS**:

- פשוט יותר מ-Kubernetes לעומסי עבודה AWS-מרכזיים
- אינטגרציה הדוקה של AWS (IAM, ALB, CloudWatch, Secrets Manager)
- אפשרות Fargate מסירה ניהול EC2 לחלוטין

**EKS**:

- תאימות מלאה ל-Kubernetes — שימוש באקוסיסטם המלא
- טוב יותר לסביבות היברידיות או צוותים עם מומחיות Kubernetes
- מורכב יותר לבנייה ותפעול מ-ECS

**איפה זה מסתבך**:

- תמונות container חייבות להיבנות ולהיות עם גרסאות — דורש צינור CI/CD
- ניפוי באגים של containers דורש כלים שונים מניפוי באגים של תהליכים מסורתיים
- containers עם מצב (מסדי נתונים ב-containers) דורשים הגדרת אחסון עמיד זהיר
- רשת בין containers (תקשורת שירות-לשירות) דורשת הבנת מושגי רשת containers

## סיכום

Lambda הפכה את המחשוב הסרק לחינמי. Containers הפכו את הפריסה לדטרמיניסטית. יחד, הם פתרו שניים מהגורמים הנפוצים ביותר לכאב תפעולי עבור צוותי הנדסה גדלים.

- **מיכלים** אורזים קוד יישום, runtime ותלויות יחד — פועלים זהה בכל מקום.
- **Docker** היא טכנולוגיית container סטנדרטית. תמונות הן תבניות; containers הם instances פועלים.
- **ECR (Elastic Container Registry)** הוא registry Docker מנוהל של AWS — אחסנו, נהלו גרסאות, וסרקו תמונות כאן. הפעילו סריקת תמונות לתפיסת CVEs לפני פריסה.
- **ECS (Elastic Container Service)** מתזמר containers. אתם מגדירים tasks ושירותים; ECS מנהל מיקום ומחזור חיים.
- **Fargate** הוא מחשוב serverless למיכלים — אין מכונות EC2 לנהל. לעיתים קרובות זולה יותר מ-EC2 launch type בהיקפים קטנים בשל חיסול תקורת EC2. בהיקפים גדולים עם bin-packing זהיר של tasks, EC2 launch type יכול להיות חסכוני יותר.
- **EKS (Elastic Kubernetes Service)** הוא Kubernetes מנוהל — לצוותים שצריכים תכונות Kubernetes או תאימות.
- **אינטגרציה של Secrets Manager**: הזרקת סודות למיכלים בזמן הפעלה דרך הגדרת task — אל תאחסנו ערכי סודות במשתני סביבה או הגדרות task ישירות.
- **גילוי שירותים**: IPs של containers הם חולפים. השתמשו בשמות DNS של ALB או Cloud Map לכתובת שירות יציבה.
- בחרו ECS לפשטות ב-AWS; בחרו EKS לתאימות אקוסיסטם Kubernetes.

## טיפים למבחן

*SAA-C03 תחום: עיצוב ארכיטקטורות עמידות (תחום 2, משימה 2.1)*

- **אותות ECS לעומת EKS**: תרחישי מבחן שמזכירים "Kubernetes," "Helm," "מומחיות Kubernetes קיימת," או "תזמור containers מרובת-ענן" ← EKS. כל שאר ← ECS.
- **Fargate לעומת EC2 launch type**: "לא רוצה לנהל מכונות EC2 למיכלים," "containers serverless," "אין ניהול תשתית" ← Fargate. "צריך סוגי instances ספציפיים," "עומסי GPU," "שליטה עדינה ב-instance" ← EC2 launch type.
- **תפקיד task לעומת תפקיד ביצוע task** — מבחין מבחן אמיתי. **תפקיד ביצוע task** משמש את *סוכן ECS* מטעם ה-task, לפני ובסביבות הקוד שלכם: משיכת התמונה מ-ECR, שליפת סודות מ-Secrets Manager, כתיבת לוגים ל-CloudWatch. **תפקיד task** הוא מה ש*קוד היישום שלכם בתוך ה-container* משתמש כדי לקרוא לשירותי AWS: קריאה מ-S3, כתיבה ל-DynamoDB — כמו תפקידי instance EC2, אבל לפי task, כך שכל task יכול לקבל הרשאות שונות. "Container צריך לקרוא מ-S3" ← **תפקיד task** (מצורף בהגדרת task). "Task נכשל למשוך תמונה / לא יכול לשלוף סוד" ← **תפקיד ביצוע** חסר הרשאות.
- **Fargate Spot**: הרצת containers עמידים לשיבושים על קיבולת פנויה בעד ~70% הנחה, עם אזהרת הפרעה של שתי דקות — שוות ערך ל-EC2 Spot של Fargate, מוגדר דרך capacity providers. אות מבחן: "הרצת containers עמידים לשיבושים בעלות הנמוכה ביותר ללא ניהול instances" ← Fargate Spot.
- **סריקת תמונות ECR**: ECR יכול לסרוק תמונות container לפגיעויות ידועות (CVEs). אות מבחן: "סריקת containers לפגיעויות אבטחה" ← סריקת תמונות ECR.
- **פריסות Blue/Green**: ECS תומך בפריסות blue/green דרך אינטגרציה עם CodeDeploy. פריסה ללא-השבתה עם rollback אוטומטי. דפוס מבחן: "פריסה ללא השבתה עם rollback אוטומטי" ← ECS + CodeDeploy blue/green.
- **אינטגרציה של Secrets Manager**: אות מבחן: "הזרקת סודות למיכלים מבלי לאחסן ערכים בהגדרות task" ← השתמשו בשדה `secrets` בהגדרת task המפנה ל-ARN של Secrets Manager. לתפקיד ביצוע task נדרשת הרשאת `secretsmanager:GetSecretValue`.
- **ECS Service Auto Scaling**: קנה מידה של מספר tasks בהתבסס על CPU, זיכרון, או מדדי CloudWatch מותאמים. עובד עם ALB לניתוב תנועה למספר הנכון של tasks פועלים.
- **AWS Batch:** מחשוב אצוות מנוהל למיכלי Docker. תור עבודות ← סביבת מחשוב (EC2 או Fargate, תומכת ב-Spot). השתמשו כש: timeout Lambda קצר מדי, שירות ECS בזבזני לעבודות בעלות משך מוגדר. אות מבחן: "עיבוד אצוות בקנה מידה גדול" או "עבודה שפועלת שעות" ← AWS Batch.

## תרגילים

**תרגיל 1 — שחזור**

הסבירו את ההבדל בין Docker image ל-Docker container. הסבירו את ההבדל בין ECS ל-ECR.

*(רמז: image ל-container כמו מתכון לתבשיל מוכן. ECR מאחסן תמונות; ECS מריץ אותן.)*

**תרגיל 2 — תרחיש SAA-C03**

*תרחיש*: לחברה יש יישום microservices שפועל כרגע על מכונות EC2 המנוהלות ידנית. הצוות מתקשה עם פריסות לא עקביות — למכונות EC2 שונות יש גרסאות ספריות שונות, הגורמות לבאגים קשים לשחזור. הם רוצים לסטנדרטיז פריסות תוך מזעור תקורה תפעולית לניהול השרתים הבסיסיים. לצוות אין ניסיון Kubernetes.

איזו פתרון **מתאים ביותר** לדרישות אלה?

A) מיכול היישום עם Docker; שימוש ב-Amazon ECS עם Fargate launch type  
B) פריסה על EC2 עם AWS Systems Manager Patch Manager לשמירת עקביות instances  
C) מיכול היישום עם Docker; שימוש ב-Amazon EKS עם self-managed node groups  
D) שימוש ב-AWS Elastic Beanstalk לניהול פריסות ותצורת instances אוטומטית

**רמז 1**: מיכלים פותרים את בעיית "סביבה לא עקבית" ישירות. אילו אפשרויות משתמשות במיכלים?

**רמז 2**: "מזעור תקורה תפעולית לניהול שרתים" ← Fargate (ללא ניהול EC2) לעומת self-managed nodes (עדיין מנהלים EC2).

**רמז 3**: "ללא ניסיון Kubernetes" ← EKS מורכב תפעולית יותר מ-ECS.

**תשובה**: A

**הסבר**: מיכול עם Docker מבטיח שכל פריסה משתמשת באותה תמונה עם אותן תלויות — מחסל קריסת תצורה. ECS עם Fargate פירושו אין מכונות EC2 לנהל. הצוות מתמקד בקוד יישום והגדרות container, לא בתחזוקת שרתים. ECS (לא EKS) מתאים לצוותים ללא ניסיון Kubernetes.

**למה לא B?** Patch Manager שומר מכונות EC2 מעודכנות אבל אינו פותר אי-עקביות גרסת ספריות בין יישומים. הבעיה הבסיסית (סביבות קוד שונות על instances שונים) נשארת.

**למה לא C?** EKS עם self-managed node groups דורש ניהול מכונות EC2 *וגם* למידת Kubernetes. אף אחד מהם לא מתיישב עם הדרישות.

**למה לא D?** Elastic Beanstalk מנהל פריסת יישום על EC2 אבל לא פותר את אי-עקביות הסביבה הבסיסית אלא אם משתמשים במיכלים. Beanstalk לא משתמש ב-Docker images כברירת מחדל (אם כי ניתן להגדיר כך).

*SAA-C03 תחום: עיצוב ארכיטקטורות עמידות — משימה 2.1*

**תרגיל 3 — אתגר ארכיטקטוני** *(אופציונלי)*

Nimbus מפצלת את ה-API המונוליטי לשלושה microservices: שירות הזמנות, שירות תפריטים, ושירות התראות. לכל שירות דרישות קנה מידה שונות (שירות ההזמנות מתרחב עם תנועה; שירות התפריטים בעיקר קריאה-בלבד ויציב; שירות ההתראות מגיע לשיאים קוצניים).

תכננו את ארכיטקטורת ECS לשלושת השירותים האלה. כיצד תטפלו בתקשורת שירות-לשירות? האם תשתמשו ב-cluster ECS אחד או שלושה? כיצד תגדירו Auto Scaling בצורה שונה לכל שירות?

שקלו: שירות התפריטים כבד-קריאה ויכול לשרת נתונים לא עדכניים למשך 60 שניות — האם תוסיפו caching לפניו? שירות ההתראות מגיע לשיאים גדולים בערבי שישי — האם תגדירו Fargate Min capacity ל-1 ו-Max ל-20? מה קורה להתראות בטיסה במהלך אירוע scale-down?

*(אין תשובה נכונה יחידה. המטרה היא לתרגל ארכיטקטורת microservices על ECS.)*

## סצנה לאחר הקרדיטים

פריסת ה-container הראשונה הייתה ללא דופי.

גרסה חדשה של ה-API: אפס השבתה. ECS גילגל אותה, בדיקות בריאות עברו, tasks ישנים התנקזו, tasks חדשים השתלטו. Leo צפה בסטטוס ה-task במסוף עם משהו שהתקרב לחוסר אמונה.

"זה פשוט עבד," אמר.

"שבוע שעבר אמרת את אותו הדבר על פריסת ה-SSH הידנית לפני שנכשלה ב-instance שלוש," אמרה Priya.

"כבר פרסתי את זה — אוי." Leo עצר. "פרסתי ללא תיוג גרסת התמונה. תנו לי לתקן זאת."

"זו הנקודה," אמרה Priya. "ניהול גרסאות תמונה הוא האופן שבו אתם עוקבים אחר מה שפועל."

"כיצד אתם יודעים איזו גרסה פועלת ב-production עכשיו?" שאלה Maya.

Leo פתח את מסוף ECS. תחת ה-task הפועל, התמונה הופיעה: `123456789012.dkr.ecr.us-west-2.amazonaws.com/nimbus-api:1.0.3`. גרסה 1.0.3. נבנתה ב-14:22 UTC. נפרסה ב-14:31 UTC.

"בהגדרת EC2 הישנה," אמר Leo, "הייתי צריך להתחבר ב-SSH ל-instance ולהריץ `pip show` כדי לראות איזו גרסה של כל תלות מותקנת. והיא עשויה הייתה להיות שונה על instances אחרים."

"ועכשיו?"

"התג על התמונה אומר לי בדיוק מה פועל. היסטוריית סריקת ECR אומרת לי אם היא נסרקה. היסטוריית פריסת ECS אומרת לי מתי היא נפרסה ומה הייתה הגרסה הקודמת."

"ללא SSH. ללא השבתה. ללא 'חכה שהוא יופעל מחדש.'"

"התמונה היא artifact הפריסה," אמרה Priya. "הסביבה בלתי-ניתנת לשינוי. תהליך הפריסה דקלרטיבי. כך תוכנה צריכה להישלח."

Leo בהה במסוף עוד רגע.

"בזבזתי שלוש שנים בתיאום פריסות EC2," אמר. "תיאום סקריפטי SSH. כתיבת runbooks פריסה."

"היית פותר בעיה," אמרה Priya, "שמיכלים פותרים בעיצוב."

הוא לא אמר דבר לאחר מכן. אבל למחרת בבוקר, הוא התחיל לכתוב תיעוד על תהליך בניית ה-container, כדי שאף אחד אחר לא יצטרך לבלות שלוש שנים כדי להבין זאת.

הבאג של instance-שלוש, שישה שבועות של קריסה לא מתועדת, והבעיות כמותו שעדיין לא תפסו — כולם היו עם סיבה שורשית אחת. לא שחקן זדוני. לא כשל חומרה. רק שרת שהתייחסו אליו כקבע במקום כיחידה מתכלה.

המכולה הייתה התשובה לכך. לא כי היא חדשה ומעניינת. כי היא הפכה את השאלה לבלתי אפשרית לשאול.

בפרק הבא: תרשים הזרימה שמריץ את עצמו — וזוכר היכן עצר.
