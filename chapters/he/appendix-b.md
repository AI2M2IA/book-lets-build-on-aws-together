## תחום 1: עיצוב ארכיטקטורות מאובטחות (30%)

**משימה 1.1 — עיצוב גישה מאובטחת למשאבי AWS**

מושגי ליבה: IAM users, groups, roles, policies. עקרון הרשאה מינימלית. גישה בין-חשבונית. Service roles. SCP (Service Control Policies) ב-AWS Organizations.

דפוסי בחינה מרכזיים:

- "EC2 צריך לגשת ל-S3 ללא אישורים קשיחים" → IAM role עם מדיניות S3 מחוברת ל-EC2 instance profile
- "חשבונות שונים צריכים לשתף משאבים" → IAM role עם cross-account trust policy
- "מנע כל משתמשי IAM ב-OU מגישה לשירות" → SCP ב-AWS Organizations

---

**משימה 1.2 — עיצוב עומסי עבודה ואפליקציות מאובטחים**

מושגי ליבה: עיצוב VPC, קבוצות אבטחה לעומת NACLs, בידוד רשת, הגנת DDoS, WAF, GuardDuty.

דפוסי בחינה מרכזיים:

- "חסום IP ספציפי מתת-הרשת" → כלל deny ב-NACL
- "אפשר HTTP פנימה, אפשר אוטומטית HTTP חזרה" → קבוצת אבטחה (stateful)
- "הגן על אפליקציית web מ-SQL injection" → WAF עם כלל SQL injection
- "זהה אישורי IAM שנפגעו" → GuardDuty

---

**משימה 1.3 — קביעת בקרות אבטחת נתונים מתאימות**

מושגי ליבה: הצפנה בשאר ובמעבר, KMS, Secrets Manager, Parameter Store, הצפנת S3.

דפוסי בחינה מרכזיים:

- "סובב אישורי מסד נתונים אוטומטית" → Secrets Manager עם אינטגרציית RDS
- "שלוט מי יכול להשתמש במפתחות הצפנה על פני חשבונות" → מדיניות KMS key
- "אחסן ערכי תצורה שאינם רגישים" → SSM Parameter Store (לא Secrets Manager)
- "הצפן עצמי S3 עם מפתחות מנוהלי חברה" → SSE-KMS עם CMK

---

## תחום 2: עיצוב ארכיטקטורות עמידות (26%)

**משימה 2.1 — עיצוב ארכיטקטורות ניתנות להגדלה ומנותקות**

מושגי ליבה: Auto Scaling, load balancers, ניתוק SQS/SNS, Lambda event triggers, ECS/EKS, Step Functions.

דפוסי בחינה מרכזיים:

- "נתק עיבוד הזמנות מעדכון מלאי" → תור SQS בין שירותים
- "הודע לשירותים מרובים כשהזמנה חדשה מונחת" → SNS topic עם מנויי SQS (fan-out)
- "עבד העלאות S3 אוטומטית" → S3 event notification → Lambda
- "הרץ תהליך עבודה רב-שלבי עם לוגיקת ניסיון חוזר" → Step Functions

---

**משימה 2.2 — עיצוב ארכיטקטורות זמינות גבוהה ו/או סובלנות לתקלות**

מושגי ליבה: Multi-AZ, Multi-Region, Route 53 failover, RDS read replicas, Aurora Global Database, backup ו-restore.

דפוסי בחינה מרכזיים:

- "כשל-אוטומטי אם RDS ראשי נכשל" → RDS Multi-AZ (לא Read Replica)
- "הגש קריאות גלובלית עם זמן השהיה נמוך" → Aurora Global Database
- "נתב תעבורה לאזור משני אם ראשי לא זמין" → Route 53 עם Failover routing + health checks
- "RTO של דקה, RPO של 0" → פריסת Multi-AZ (לא Multi-Region)
- "RTO של 15 דקות, בין-אזורים" → אסטרטגיית Pilot Light

---

## תחום 3: עיצוב ארכיטקטורות בביצועים גבוהים (24%)

**משימה 3.1 — קביעת פתרונות אחסון בביצועים גבוהים ו/או ניתנים להגדלה**

דפוסי בחינה מרכזיים:

- "מערכת קבצים משותפת נגישה ממכונות EC2 מרובות" → EFS (לא EBS; EBS מחובר למכונה אחת)
- "IOPS גבוה לעומס עבודה מסד נתונים" → io2 EBS
- "הפחת עלות לקבצים שלא ניגשו אליהם 90 יום" → מדיניות מחזור חיים S3 → Glacier
- "העלה קבצים גדולים ממיקומים מרוחקים מהר יותר" → S3 Transfer Acceleration

---

**משימה 3.2 — קביעת פתרונות חישוב בביצועים גבוהים ו/או ניתנים להגדלה**

דפוסי בחינה מרכזיים:

- "עומס עבודה אימון ML, מזעור עלות, ניתן להפרעה" → Spot Instances
- "תגובת Lambda עקבית מתחת ל-100ms" → Provisioned concurrency (מבטל cold start)
- "microservice ב-container, ללא ניהול תשתית" → ECS Fargate

---

**משימה 3.3 — קביעת פתרונות מסד נתונים בביצועים גבוהים**

דפוסי בחינה מרכזיים:

- "קריאות במיקרושניות למאגר סשנים" → ElastiCache Redis או DAX (אם backend DynamoDB)
- "גישת key-value בתפוקה גבוהה עם סכמה גמישה" → DynamoDB
- "joins מורכבים ועסקאות ACID" → Aurora או RDS
- "אנליטיקה על פטה-בייט של נתונים מובנים" → Redshift

---

**משימה 3.4 — קביעת ארכיטקטורות רשת בביצועים גבוהים ו/או ניתנות להגדלה**

דפוסי בחינה מרכזיים:

- "הפחת זמן השהיה למשתמשים גלובליים שניגשים לתגובות API דינמיות" → Global Accelerator (לא CloudFront)
- "הפחת זמן השהיה לנכסים סטטיים גלובלית" → CloudFront
- "קישוריות פרטית עקבית ל-AWS מ-on-premises" → Direct Connect
- "העלאה מהירה מלקוחות ברחבי העולם לדלי S3 שלך" → S3 Transfer Acceleration

---

**משימה 3.5 — קביעת פתרונות קליטה וטרנספורמציה נתונים בביצועים גבוהים**

דפוסי בחינה מרכזיים:

- "עיבד נתוני click-stream בזמן אמיתי" → Kinesis Data Streams + Lambda או KDA
- "ספק נתוני זרימה ל-S3 לניתוח מאוחר" → Kinesis Firehose
- "טרנספורם וקטלג נתונים ממקורות מרובים" → AWS Glue
- "שאל נתונים היסטוריים המאוחסנים ב-S3 עם SQL" → Athena

## תחום 4: עיצוב ארכיטקטורות מותאמות עלות (20%)

**משימה 4.1 — עיצוב פתרונות אחסון מותאמות עלות**

דפוסי בחינה מרכזיים:

- "זהה איזה צוות מייצר הכי הרבה עלויות S3" → תגיות הקצאת עלות + Cost Explorer
- "הפחת עלויות לעצמים הנגישים לעתים רחוקות אוטומטית" → S3 Intelligent-Tiering
- "התראה כשעלויות חודשיות עולות על $10,000" → AWS Budgets

---

**משימה 4.2 — עיצוב פתרונות חישוב מותאמות עלות**

דפוסי בחינה מרכזיים:

- "הפחת עלות לעומסי עבודה ייצור יציבים" → Savings Plans (גמיש יותר) או Reserved Instances
- "מזעור עלות לעבודות אצווה הניתנות להפרעה" → Spot Instances
- "עיבוד event-driven עם עלות אפסית ללא פעילות" → Lambda

---

**משימה 4.3 — עיצוב פתרונות מסד נתונים מותאמות עלות**

דפוסי בחינה מרכזיים:

- "תנועת DynamoDB בלתי צפויה" → מצב קיבולת on-demand
- "תנועת DynamoDB עקבית עם שיאים ידועים" → Provisioned + Auto Scaling
- "הפחת עלויות RDS לעומס עבודה יציב" → Reserved Instances (1 או 3 שנים)

---

**משימה 4.4 — עיצוב ארכיטקטורות רשת מותאמות עלות**

דפוסי בחינה מרכזיים:

- "EC2 בתת-רשת פרטית קורא ל-S3 — בטל עלויות NAT Gateway" → S3 Gateway Endpoint (חינם)
- "EC2 בתת-רשת פרטית קורא ל-SQS — הפחת עלויות NAT Gateway" → SQS Interface Endpoint
- "הפחת עלויות העברת נתונים להגשת תוכן גלובלי" → CloudFront (מטמון מפחית בקשות למקור)

## צ'קליסט לפני הבחינה

לפני ישיבה ב-SAA-C03:

**אזורים בעלי משקל גבוה (הנוטים ביותר להופיע)**

- [ ] הגיון הערכת מדיניות IAM (deny מפורש → allow מפורש → deny משתמע)
- [ ] רכיבי VPC: תת-רשתות, טבלאות מסלול, IGW, NAT Gateway, קבוצות אבטחה, NACLs
- [ ] מחלקות אחסון S3 ומתי להשתמש בכל אחת
- [ ] RDS Multi-AZ לעומת Read Replica (כשל-אוטומטי לעומת הגדלת קריאות)
- [ ] SQS לעומת SNS לעומת EventBridge (pull לעומת push לעומת ניתוב אירועים)
- [ ] מודלי תמחור EC2: Spot לסובל תקלות, Savings Plans לעומסי עבודה מחויבים
- [ ] Lambda triggers ובו-זמניות
- [ ] DynamoDB לעומת Aurora לעומת Redshift (דפוס גישה קובע בחירה)
- [ ] CloudFront: CDN לסטטי, Global Accelerator לדינמי

**מלכודות נפוצות**

- [ ] EBS מחובר למכונה אחת; EFS הוא משותף
- [ ] RDS Read Replicas הם להגדלת קריאות, לא לכשל-אוטומטי (זה Multi-AZ)
- [ ] NACLs הם stateless (דורשים כללי כניסה ויציאה)
- [ ] Gateway Endpoints הם חינמיים ורק ל-S3 ו-DynamoDB
- [ ] Kinesis שומר ו-replay; SQS מוחק בעת צריכה
- [ ] "ניתוק" לא תמיד אומר SQS — SNS fan-out ו-EventBridge הם גם דפוסי ניתוק
- [ ] Shield Standard הוא חינמי ואוטומטי; Advanced הוא מנוי בתשלום

**מבנה הבחינה**

- 65 שאלות, 130 דקות (2 שעות ו-10 דקות)
- בחירה מרובה (נכון אחד) ותגובה מרובה (בחר N נכונים)
- ציון עובר: 720 מתוך 1000
- שאלות לא מנוקדות מוטמעות; לא ניתן לזהות אילו הן
- ניהול זמן: ~2 דקות לשאלה; סמן קשות וחזור
