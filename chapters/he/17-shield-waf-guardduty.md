**שלוש קטגוריות איום**

איומי אבטחה נגד יישום ענן בדרך כלל נופלים לשלוש קטגוריות:

**התקפות נפח (DDoS)**: תוקף שולח כל כך הרבה תעבורה שהיישום שלכם לא יכול להגיב למשתמשים לגיטימיים. ההתקפה עשויה להיות מיליוני בקשות HTTP, או הצפה של חבילות TCP SYN המתוכננות למצות את טבלת החיבורים של השרת שלכם.

**התקפות יישום (Exploits)**: תוקף שולח בקשות מעוצבות ספציפית המתוכננות לנצל חולשות ביישום שלכם — ‏SQL injection, ‏cross-site scripting, קלט פגום שמרסק parser.

**חריגות התנהגותיות (סיור ופריצה)**: קריאות API שלא צריכות לקרות (מישהו שואל את כל מסד נתוני המשתמשים שלכם ב-3 לפנות בוקר), פעילות IAM חריגה (אישורים בשימוש ממדינה חדשה), או תעבורת רשת ליעדים בלתי-צפויים.

ל-AWS יש שירות ייעודי לכל אחד:

- **AWS Shield**: הגנת DDoS
- **AWS WAF**: הגנה ברמת היישום
- **Amazon GuardDuty**: זיהוי איומים התנהגותי

**AWS Shield: סופג ה-DDoS**

**AWS Shield Standard** מופעל אוטומטית עבור כל לקוחות AWS ללא חיוב נוסף. הוא מגן מפני התקפות ה-DDoS הנפוצות ביותר בשכבה 3 (רשת) ושכבה 4 (תעבורה) — ‏SYN floods, ‏UDP floods, התקפות הגברת DNS.

‏CloudFront, ‏Route 53, ו-Elastic Load Balancing יושבים בקצה רשת AWS. כשהתקפת DDoS מכוונת ליישום שלכם, היא פוגעת בשירותים מנוהלים אלה תחילה. תשתית הרשת של AWS סופגת את ההתקפה לפני שהיא מגיעה למכונות ה-EC2 שלכם.

**AWS Shield Advanced** היא השכבה הפרמיום ($3,000/חודש לארגון, עם התחייבות של שנה). זהו מנוי נפרד — הוא *אינו* כלול בשום תוכנית AWS Support. הוא מוסיף:

- הגנה ל-EC2, ‏ELB, ‏CloudFront, ‏Global Accelerator, ו-Route 53
- הודעות התקפה כמעט-בזמן-אמת
- גישה ל-AWS Shield Response Team (SRT) — מהנדסי אבטחה שיכולים לעזור לכם להגיב להתקפות (הפעלת ה-SRT דורשת בנוסף תוכנית Business או Enterprise Support)
- הגנת עלות: אם התקפה גורמת לחשבון שלכם לזנק, ‏AWS מזכה את עלויות העלייה
- זיהוי והפחתת DDoS משופרים בשכבה 7 (שכבת היישום)

**AWS WAF: מסנן היישום**

**AWS WAF (Web Application Firewall)** פועל ברמת ה-HTTP — הוא בוחן את תוכן בקשות האינטרנט לפני שהן מגיעות ליישום שלכם.

‏WAF מוגדר עם **Web ACLs (Access Control Lists)** — מערכי כללים שמגדירים מה לאפשר, לחסום, או לספור.

ניתן לצרף WAF ל:

- ‏CloudFront distributions (בחינת בקשות ב-edge, גלובלית)
- ‏Application Load Balancers (בחינת בקשות ברמה האזורית)
- API Gateway
- AWS AppSync

**WAF Managed Rules**: ‏AWS וספקי צד-שלישי מפרסמים מערכי כללים בנויים-מראש:

- **AWS Managed Rules - Core Rule Set**: יחד עם קבוצות כללים נלוות (SQL database, Known Bad Inputs), מכסה את 10 הפגיעויות המובילות של OWASP (SQL injection, ‏XSS, ‏command injection, ‏path traversal, וכו')
- **AWS Managed Rules - Known Bad Inputs**: חוסם בקשות התואמות דפוסי התקפה ידועים
- **AWS Managed Rules - Amazon IP Reputation List**: חוסם IPs ידועים כמשויכים ל-botnets וסורקים
- **AWS Managed Rules - Bot Control**: מזהה ומנהל תעבורת bot

אתם יכולים גם ליצור כללים מותאמים:

- "חסום כל בקשה עם כותרת User-Agent המכילה 'sqlmap'" (סורק SQL injection נפוץ)
- "‏rate limit: אפשר לא יותר מ-1000 בקשות לכל IP ב-5 דקות"
- "חסום בקשות שמכילות `<script>` בכל ערך פרמטר"

עבור Nimbus, ההגדרה המעשית: ‏WAF על ה-CloudFront distribution עם ה-Core Rule Set מופעל. זה חוסם את דפוסי ההתקפה הנפוצים ביותר לפני שבקשות מגיעות אי פעם למכונות ה-EC2.

אולי אתם תוהים: אם WAF חוסם דפוסי התקפה ידועים, מה קורה כשמופיע דפוס התקפה חדש ש-WAF לא מכיר? מערכי הכללים המנוהלים של WAF מתעדכנים על ידי AWS וספקי צד-שלישי ככל שאיומים חדשים מופיעים — אתם לא צריכים לעדכן כללים ידנית. אבל אתם צודקים ש-WAF בעצם תגובתי לדפוסים ידועים. טכניקות התקפה חדשות, חדשניות לא ייחסמו על ידי כלל שעדיין לא קיים. זו הסיבה ש-GuardDuty קיים לצד WAF: ‏WAF מסנן את הדלת הקדמית, ‏GuardDuty צופה בהתנהגות חריגה בתוך הבית. סוג התקפה חדש עשוי לעבור את WAF, אבל GuardDuty עדיין יכול לסמן את הפעילות החריגה שהוא גורם — קריאות API חריגות, יעדי רשת בלתי-צפויים, דפוסי גישה שלא תואמים את קו הבסיס.

**חשבנו על מה שקורה אם WAF גורם ל-false positives?** שאלה Priya. "בקשה של משתמש לגיטימי שנחסמת על ידי ה-Core Rule Set?"

"ל-WAF יש מצב 'Count'," אמר Leo. "במקום לחסום, הוא פשוט סופר בקשות תואמות. אתם מריצים אותו במצב Count תחילה, סוקרים מה הוא היה חוסם, מאמתים שאין false positives, ואז עוברים ל-Block."

"טוב," אמרה Priya. "אנחנו מתחילים במצב Count."

**יצירת כלל WAF: סיפור ה-Rate Limit**

שבועיים לאחר הפעלת WAF במצב Count, ‏Priya סקרה את היומנים. ממצאי ה-Core Rule Set היו נקיים — אין false positives על תעבורה לגיטימית, קומץ ניסיונות SQL injection חסומים מסורקים אוטומטיים.

אבל היא שמה לב לדפוס שה-Core Rule Set לא סימן: כתובת IP אחת ביצעה 847 בקשות ל-`/api/search` בחמש דקות. כל בקשה הייתה תקפה מבנית. אבל 847 חיפושים בחמש דקות לא היו אדם.

"‏price scraper," אמרה. "מישהו שואל אוטומטית את חיפוש המסעדות שלנו כדי לבנות מסד נתוני מחירים תחרותי."

"אכפת לנו?" שאל Leo.

"זה משתמש במשאבי המחשוב שלנו וזה נגד תנאי השירות שלנו," אמר Tom.

"אכפת לנו," אישרה Priya.

היא יצרה כלל מבוסס-קצב מותאם של WAF:

```
Rule name: RateLimitSearchAPI
Rule type: Rate-based rule
Rate limit: 100 requests per IP address
Evaluation window: 5 minutes (configurable: 1, 2, 5, or 10 minutes)
Scope-down statement: URI path starts with /api/search
Action: Block
```

הצהרת ה-scope-down חשובה — ה-rate limit חל רק על `/api/search`. תעבורת API לגיטימית לנקודות קצה אחרות אינה מושפעת. ושימו לב איך החסימה עובדת: אין תקופת "ענישה" קבועה — ‏WAF מעריך מחדש את שיעור הבקשות של כל IP ברציפות, חוסם אותו כל עוד השיעור נשאר מעל הגבול, ומבטל את החסימה (בדרך כלל תוך שניות) ברגע שהשיעור יורד חזרה מתחת.

היא הגדירה אותו למצב Count תחילה. הריצה אותו 24 שעות. ה-IP היחיד שהפעיל את הכלל היה ה-scraper. אף משתמש לגיטימי מעולם לא שלח יותר מ-12 בקשות לנקודת קצה החיפוש בחמש דקות.

היא עברה למצב Block. הבקשה הבאה של ה-scraper קיבלה 403. הוא עבר ל-IP שונה. ה-rate limit תפס גם אותו.

"הם יעקפו את זה בסופו של דבר," אמר Leo. "יפזרו על פני יותר IPs."

"שבנקודה זו הם משתמשים ביותר תשתית, משלמים יותר, ומקבלים פחות נתונים," אמרה Priya. "אנחנו לא צריכים לעצור אותם לחלוטין. אנחנו צריכים להפוך את זה ליקר מספיק כדי שלא יהיה שווה את זה."

"כמה זה עולה לחודש?" שאל Tom.

תמחור WAF הוא לכל Web ACL לחודש, לכל כלל לחודש, ולכל מיליון בקשות. עבור הגדרת Nimbus — ‏Web ACL אחד, חמישה כללים על CloudFront — בערך $15 לחודש בתוספת חיובי בקשות.

‏Tom אישר את זה מיד.

**Amazon GuardDuty: האנליסט ההתנהגותי**

"רגע — אבל *למה* היינו עושים את זה כך?" שאלה Maya. "אם WAF חוסם התקפות ו-Shield סופג הצפות, למה אנחנו צריכים שירות שלישי? למה GuardDuty באמת צופה?"

‏WAF ו-Shield הם מסננים — הם מיירטים תעבורה רעה לפני שהיא מגיעה ליישום שלכם. ‏GuardDuty צופה במה שקורה אחרי שתעבורה מגיעה. הוא מסתכל במה שהתשתית שלכם עושה: אילו אישורי IAM בשימוש, אילו דומיינים המכונות שלכם יוצרות קשר איתם, אילו קריאות API קורות ב-3 לפנות בוקר. תוקף שעובר את הדלת הקדמית דרך בקשה שנראית לגיטימית לא ייעצר על ידי WAF — אבל GuardDuty ישים לב שאותו אישור פתאום מבצע קריאות API מרומניה.

‏GuardDuty שונה ביסודו מ-Shield ו-WAF. הוא לא חוסם התקפות — הוא **מזהה התנהגות חריגה**.

‏GuardDuty מנתח ברציפות מספר זרמים של פעילות כדי לזהות איומים: **CloudTrail management ו-data events** (קריאות ופעולות API), ‏**VPC Flow Logs** (דפוסי תעבורת רשת), ו-**DNS query logs** (חיפושי דומיין). אלה שלושת המקורות היסודיים ש-GuardDuty תמיד הסתמך עליהם:

- **AWS CloudTrail logs**: שינויי IAM, קריאות API, התחברויות לקונסולה
- **VPC Flow Logs**: דפוסי תעבורת רשת בתוך ה-VPC שלכם
- **DNS query logs**: מה המכונות שלכם פותרות (תוכנה זדונית ידועה לעיתים קרובות פותרת דומייני C2 ספציפיים)

אבל GuardDuty התרחב משמעותית מעבר לשלושה אלה. ‏AWS קוראת לתוספות האופציונליות **protection plans** — ‏S3 Protection, ‏EKS Protection, ‏RDS Protection, ‏Lambda Protection, ‏Runtime Monitoring, ו-Malware Protection — כל אחת מופעלת בנפרד. בהתאם למה שאתם מפעילים, ‏GuardDuty יכול גם לנתח **S3 data events** (דפוסי גישה חריגים לדליים שלכם), ‏**EKS audit logs ופעילות runtime** (התנהגות זדונית בתוך מכולות רצות), ‏**RDS login events** (ניסיונות התחברות חריגים למסד נתונים), ‏**Lambda network traffic** (פונקציות שקוראות ליעדים חיצוניים בלתי-צפויים), ‏**התנהגות runtime של ECS/EC2**, ו-**נפחי EBS שנסרקים לתוכנה זדונית**. למבחן, דעו את שלושת המקורות הליבתיים בעל-פה; ה-protection plans מופיעים בתרחישים על הקשרי זיהוי איום ספציפיים — "זהה ניסיונות התחברות חריגים ל-RDS" או "זהה התנהגות זדונית בתוך מכולה רצה" הם אותות לחשוב על ה-protection plans האופציונליים של GuardDuty.

מודלי למידת מכונה מזהים דפוסים שסוטים מקו הבסיס שלכם. ‏GuardDuty מייצר **findings** — התראות מסווגות — כשהוא מזהה חריגות.

דוגמאות למה ש-GuardDuty יכול לזהות:

- משתמש IAM שמתחבר מכתובת IP לא-מזוהה (במדינה שמעולם לא השתמשו בה)
- קריאות API שמבוצעות מ-Tor exit node
- מכונת EC2 שמתקשרת עם מאגר כריית מטבעות קריפטוגרפיים ידוע
- נפח קריאות API חריג גבוה (ניצול אישורים או סריקה)
- דלי S3 שניגשים אליו מכתובת IP שסומנה כפעילות זדונית
- תעבורה יוצאת לדומיין ידוע כמשויך לפיקוד-ובקרה של תוכנה זדונית

"זה מה שהיה תופס את ה-IP הרומני," אמר Leo בשקט.

"אם היה לנו GuardDuty מופעל, הוא היה מסמן את מכונת ה-EC2 שמבצעת חיבורים יוצאים ל-IP חיצוני לא-מזוהה ב-2 לפנות בוקר," אישרה Priya.

**חמישה סוגי findings של GuardDuty ומה לעשות**

‏Priya יצרה runbook לחמשת ה-findings הנפוצים ביותר של GuardDuty. כש-finding מופעל, הצוות יודע מיד מה זה אומר ומה לעשות.

**1. UnauthorizedAccess:IAMUser/ConsoleLoginSuccess.B**

משתמש IAM התחבר בהצלחה לקונסולת AWS מכתובת IP שלא נראתה עבור חשבון זה קודם, או ממיקום גאוגרפי שאינו עקבי עם התחברויות קודמות.

תגובה: ודאו עם המשתמש שהוא יזם את ההתחברות. אם לא — או אם אי אפשר להשיגו — מיד: נטרלו את מפתח הגישה וסיסמת הקונסולה של המשתמש, בטלו סשנים פעילים, והתחילו ביקורת CloudTrail של כל מה שאותו משתמש עשה ב-24 השעות האחרונות. ‏finding זה לעיתים קרובות מקדים ניצול אישורים.

**2. CryptoCurrency:EC2/BitcoinTool.B**

מכונת EC2 שואלת כתובות IP או שמות דומיין המשויכים למאגרי כריית מטבעות קריפטוגרפיים. זה כמעט תמיד תוצאה של מכונת EC2 שנפרצה ומשמשת כ-bot כרייה.

תגובה: בודדו את המכונה מיד — שנו את ה-security group שלה כדי לחסום את כל התעבורה הנכנסת והיוצאת מלבד ה-bastion host שלכם. קחו snapshot פורנזי של נפח ה-EBS. אחר כך סיימו את המכונה והפעילו תחליף מ-AMI נקי.

**3. Recon:EC2/PortProbeUnprotectedPort**

למכונת EC2 יש פורט פתוח לאינטרנט שנבדק על ידי סורקים ידועים או מ-Tor exit node. ‏GuardDuty מסמן פורטים שמופיעים ב-flow logs כנגישים ממקורות חיצוניים.

תגובה: סקרו את כללי ה-security group. אם הפורט פתוח בכוונה, סמנו את ה-finding כנפתר עם הערה. אם זה לא מכוון, סגרו את הפורט מיד. בדקו את CloudTrail לכל גישה שאולי התרחשה דרך אותו פורט.

**4. Trojan:EC2/BlackholeTraffic**

מכונת EC2 מנסה לתקשר עם כתובת IP שזוהתה כ"black hole" — יעד המשויך לתשתית פיקוד-ובקרה של תוכנה זדונית. תעבורה ל-IPs אלה מרמזת שהמכונה הודבקה ומנסה להתקשר הביתה.

תגובה: זהה ל-findings של CryptoCurrency — בודדו, ‏snapshot, החליפו. ‏finding זה מצביע על תוכנה זדונית פעילה על המכונה. אל תנסו לנקות את המכונה במקום; בנו חדשה מ-AMI נקי.

**5. Policy:S3/BucketBlockPublicAccessDisabled**

מישהו ניטרל את הגדרת Block Public Access על דלי S3. זה לא אומר שהדלי ציבורי — זה אומר שמנגנון הבטיחות שמונע חשיפה ציבורית מקרית כובה עבור אותו דלי. זה לעיתים קרובות נעשה בטעות או כחלק מפריסה שגויה.

תגובה: חקרו מי ביצע את השינוי (CloudTrail יחזיק את קריאת ה-API). הפעילו מחדש את Block Public Access אלא אם יש סיבה מתועדת שהוא צריך להיות מנוטרל. שקלו להפעיל את הגדרת Block Public Access ברמת החשבון כדי למנוע מ-finding זה להתרחש בעתיד.

"הדבר החשוב ביותר לגבי findings של GuardDuty," אמרה Priya, "הוא שהם אינם התראות — הם השערות. כל finding אומר 'הדפוס הזה נראה חריג'. אתם מאמתים, חוקרים, מגיבים. חלקם יהיו false positives. רובם לא."

"איך אנחנו מתעדפים?" שאל Rafael.

"‏GuardDuty מקצה רמות חומרה: ‏Low, ‏Medium, ‏High. ‏findings בחומרה גבוהה דורשים תגובה באותו יום. ‏findings של Trojan ופריצת אישורים תמיד High. ‏findings של בדיקת פורט עשויים להיות Medium או Low. התחילו ב-High, רדו למטה."

**חיבור שלושת השירותים**

‏Shield, ‏WAF, ו-GuardDuty עובדים בשכבות שונות ומשלימים זה את זה:

| שירות | שכבה | מגן מפני | פעולה |
|------------|---------------------------|---------------------------------------------|------------------------------------|
| AWS Shield | רשת/תעבורה (L3/L4) | הצפות DDoS | סופג/מפחית התקפות |
| AWS WAF | יישום (L7) | OWASP Top 10, bots, scrapers | מאפשר, חוסם, או סופר בקשות |
| GuardDuty | התנהגותי (כל היומנים) | חריגות, אישורים פרוצים, תוכנה זדונית | מזהה ומתריע |

‏Shield עוצר את ההצפה. ‏WAF מסנן את המים. ‏GuardDuty צופה באינסטלציה לדפוסי זרימה חריגים. ‏Macie מבקר את מה שמאוחסן במאגרים. ‏Security Hub הוא חדר הבקרה שבו כל לוחות המחוונים נראים בבת אחת.

מצב הכשל של כל אחד מסביר למה אתם צריכים את כולם:

- ‏SYN flood של 50 Gbps אינו בקשת אינטרנט. ‏WAF אינו יכול לבחון אותה. ‏GuardDuty עשוי לשים לב לאירועי ה-CloudTrail הקשורים. ‏Shield עוצר אותה.
- בקשת SQL injection בודדת אינה הצפה. ‏Shield מתעלם ממנה. ‏GuardDuty אינו יודע את תוכן בקשות ה-HTTP. ‏WAF תופס אותה.
- משתמש AWS לגיטימי שמשתמש באישורים שלו כדי להוציא נתונים לאט — אין DDoS, אין injection, ‏HTTP תקף — ‏Shield ו-WAF לא רואים דבר חריג. ‏GuardDuty שם לב שהאישורים בשימוש ממדינה חדשה ב-3 לפנות בוקר.
- מפתח שמעלה בטעות נתוני לקוח לדלי נגיש-לציבור אינו מייצר התנהגות חריגה כלל. ל-GuardDuty אין מה לסמן. ‏Macie סורק את הדלי ומוצא את ה-PII.

לכל שירות יש נקודה עיוורת. השילוב מכסה את הנקודות העיוורות האלה.

**CloudTrail: הבסיס**

כל שלושת השירותים מסתמכים על יומנים. ‏**AWS CloudTrail** הוא שירות הרישום שלוכד כל קריאת API בחשבון ה-AWS שלכם — מי קרא למה, מתי, מאיפה, עם איזו תוצאה.

‏CloudTrail מופעל כברירת מחדל להיסטוריה של 90 יום בקונסולה. כדי לשמור יומנים לטווח ארוך:

1. צרו trail שכותב לדלי S3
2. אופציונלית, שלחו ל-CloudWatch Logs להתראה בזמן אמת
3. הפעילו log file validation (כדי לזהות אם יומנים נחבלו)

‏GuardDuty, ‏AWS Config, ‏Security Hub, ו-IAM Access Analyzer כולם קוראים מ-CloudTrail. ללא יומני CloudTrail, לשירותים האלה אין מה לנתח.

"מה אם מישהו מנסה לנטרל את CloudTrail?" שאלה Priya. "אם תוקף משיג גישת מנהל, הפעולה הראשונה שלו עשויה להיות לנטרל רישום — לכסות את עקבותיו."

"זה מה שה-SCP מפרק 14 מונע," אמר Leo. "אף אחד בחשבון הזה לא יכול לנטרל את CloudTrail, אפילו מנהלים."

"ואם איכשהו עשו?"

"‏Security Hub היה מייצר finding. ‏CloudTrail שולח הודעה ל-SNS על שינויי תצורה. אנחנו מקבלים התראה תוך שתי דקות מכל שינוי CloudTrail."

"ו-GuardDuty היה מסמן את קריאת ה-API," הוסיף Rafael, "כפעולת IAM חריגה — ניטרול רישום אינו פעילות תפעולית נורמלית."

"הגנה לעומק חלה גם על שכבת הניטור," אמרה. "לא רק שכבת היישום."

**Amazon Macie: נתונים רגישים ב-S3**

"חשבנו על מה שקורה אם מישהו מעלה בטעות קובץ עם מספרי כרטיסי אשראי של לקוחות ל-S3?" שאלה Priya. "לא בזדון — סתם מפתח שמייצא נתונים לניפוי באגים ומעלה את הקובץ הלא-נכון?"

"לעולם לא היינו יודעים," אמר Leo.

"בדיוק. אלא אם יש לנו Macie."

**Amazon Macie** הוא שירות אבטחת נתונים שמשתמש בלמידת מכונה כדי לגלות ולהגן אוטומטית על נתונים רגישים ב-S3. הוא סורק ברציפות דליי S3 ומזהה:

- ‏PII (מידע אישי מזהה): שמות, כתובות דוא"ל, מספרי טלפון, תאריכי לידה
- נתונים פיננסיים: מספרי כרטיסי אשראי, מספרי חשבון בנק
- אישורים: סיסמאות, מפתחות גישה, מפתחות פרטיים מוטמעים בקבצים
- מידע בריאותי: רשומות מטופלים, אבחנות

‏Macie מייצר findings כשהוא מזהה נתונים רגישים במקומות שהם לא צריכים להיות — או כשלדליי S3 יש תצורות גישה מתירניות מדי.

"מטרה שונה," אמרה Priya. "‏GuardDuty צופה בהתנהגות — אילו פעולות מבוצעות, האם הפעולות האלה נראות חריגות. ‏Macie צופה בנתונים — איזה תוכן מאוחסן, האם התוכן הזה רגיש. ‏GuardDuty היה מסמן מכונת EC2 שמבצעת קריאות API חריגות. ‏Macie היה מסמן דלי S3 המכיל מספרי כרטיסי אשראי."

"אז GuardDuty הוא האנליסט ההתנהגותי," אמר Leo, "ו-Macie הוא מבקר הנתונים."

"בדיוק. אתם צריכים את שניהם. תוקף שמוציא נתונים דרך קריאת API שנראית לגיטימית עשוי להיות מסומן על ידי GuardDuty בגלל דפוס ה-API החריג. אבל אם עובד מעלה קובץ עם 10,000 רשומות לקוח לדלי פיתוח, אין התנהגות חריגה לזהות — סתם נתונים רגישים במקום הלא-נכון. ‏Macie תופס את זה."

עבור Nimbus, הערך המיידי ביותר של Macie היה על דלי `nimbus-debug-exports` — דלי שמפתחים השתמשו בו כדי לזרוק נתונים לניפוי באגים. ‏Macie מצא שלושה קבצים המכילים היסטוריות הזמנות עם שמות לקוחות וכתובות משלוח. לא נתוני תשלום, אבל נתונים אישיים שלא היו צריכים להיות בדלי פיתוח לא-מוצפן.

הקבצים הוסרו. נוספה מדיניות: דלי הניפוי הוגבל לנתוני בדיקה סינתטיים בלבד. נתוני לקוח אמיתיים דרשו את אישורה של Priya לייצוא לכל סביבה מחוץ לייצור.

"כמה זה עולה לחודש?" שאל Tom.

**AWS Security Hub: לוח המחוונים**

אם אתם מריצים מספר חשבונות AWS או צריכים תצוגה מאוחדת של ממצאי אבטחה, ‏**AWS Security Hub** מצבר findings מ-GuardDuty, ‏Inspector (הערכת פגיעות), ‏Macie (פרטיות נתונים), ‏Config, ו-Firewall Manager ללוח מחוונים יחיד.

הוא גם בודק את התצורה שלכם מול שיטות עבודה מומלצות של אבטחה (תקן AWS Foundational Security Best Practices) וה-CIS AWS Foundations Benchmark.

‏Security Hub הוא התשובה ל"איך אני רואה את כל ממצאי האבטחה שלי במקום אחד מבלי לעבור בין חמש קונסולות שונות?" כש-GuardDuty מייצר finding, הוא מופיע ב-GuardDuty וב-Security Hub. כש-Macie מוצא נתונים רגישים בדלי S3, הוא מופיע ב-Macie וב-Security Hub. כשכלל Config מזהה תצורה שגויה, הוא מופיע ב-Config וב-Security Hub.

לצוות עם חשבון יחיד, ‏Security Hub מוסיף ערך שולי — זו עוד קונסולה לבדוק. הכוח שלו מתגלה בקנה מידה: שלושה חשבונות, עשרה חשבונות, חמישים חשבונות. כל ה-findings מכל החשבונות מצטברים ל-Security Hub של חשבון ניהול. צוות אחד מנטר לוח מחוונים אחד. מערך התראות אחד. אין בדיקת יומנים חשבון-אחר-חשבון.

עבור Nimbus: ‏Security Hub לא היה נחוץ עדיין. כשהם יגדלו לשלושה חשבונות (dev, staging, production), הוא יהפוך לחיוני.

"הגדירו אותו עכשיו," אמרה Soo-Jin, בשבוע השלישי שלה. "לוקח חמש-עשרה דקות להפעיל. לוקח שלושה חודשים לאחל שעשיתם את זה מוקדם יותר."

הם הפעילו אותו.

**Amazon Inspector: הערכת פגיעות**

שבוע לאחר הפעלת Macie, ‏CVE פורסם עבור הגרסה של OpenSSL שרצה על פני צי הייצור של Nimbus. ‏Priya קראה את ההתראה מעל קפה.

"אנחנו צריכים לדעת אילו מהמכונות שלנו מושפעות," אמרה.

"אני יכול להריץ סריקה ידנית," אמר Leo.

"לתשע מכונות, בטח. לתשעים? למכולות?" ‏Priya פתחה את קונסולת ה-Inspector. "לשם כך Inspector קיים."

**Amazon Inspector** הוא שירות הערכת פגיעות אוטומטי. היכן ש-GuardDuty צופה בהתנהגות — מה התשתית שלכם עושה ממש עכשיו — ‏Inspector מסתכל במה שנמצא שיכול להיות מנוצל.

- **מכונות EC2:** ‏Inspector סורק את מערכת ההפעלה והחבילות המותקנות מול ה-NVD (National Vulnerability Database) — הקטלוג הסמכותי של CVEs ידועים. אם אתם מריצים OpenSSL 1.1.1 ו-CVE מכוון לאותה גרסה, ‏Inspector מסמן אותו.
- **תמונות מכולה ב-ECR:** ‏Inspector סורק תמונות מכולה ב-Elastic Container Registry לפני שהן נפרסות. חבילה פגיעה בתמונת בסיס מופיעה כ-finding לפני שהמכולה אי פעם רצה בייצור.
- **חבילות פונקציות Lambda:** ‏Inspector מנתח את התלויות הארוזות בפונקציות ה-Lambda שלכם — חבילות Python, מודולי Node, תלויות Java — לפגיעויות ידועות.

ההבדל הקריטי מסריקה חד-פעמית: ‏Inspector רץ **ברציפות**. הוא לא רק בודק את המכונות שלכם פעם אחת כשאתם מפעילים אותו ומכריז עליהן כנקיות. כש-CVE חדש מפורסם, ‏Inspector מעריך מחדש אוטומטית את המשאבים הקיימים שלכם מול הפגיעות החדשה. כשמכונת EC2 משתנה — חבילה חדשה מותקנת, ‏AMI מעודכן — ‏Inspector סורק אותה מחדש. צי ה-EC2 של Priya סומן עבור ה-CVE של OpenSSL תוך דקות מהפעלת Inspector, לא כי היא ביקשה ממנו לסרוק, אלא כי זה מה שהוא עושה.

‏findings מדורגים-חומרה: ‏Critical, ‏High, ‏Medium, ‏Low, ‏Informational. הם זורמים ל-Security Hub לצד findings של GuardDuty ו-Macie. לוח מחוונים אחד. כל שלוש העדשות.

"שלוש מכונות מושפעות," אמר Leo, קורא את ממצאי ה-Inspector. "השש האחרות בגרסה מתוקנת."

"תקנו את השלוש האלה השבוע," אמרה Priya.

"מה לגבי תמונות המכולה?"

‏Priya הסתכלה בממצאי ה-Inspector של ECR. שתי תמונות בסיס במאגר המכולות שלהם היו בעלות פגיעויות ידועות — גרסאות ישנות של חבילות שמאז תוקנו. היא תייגה אותן לבנייה מחדש.

"הדבר החשוב," אמרה Priya, "הוא שמצאנו את זה לפני שזה נוצל. לא אחרי."

**מודל שלוש-העדשות**

‏GuardDuty, ‏Inspector, ו-Macie כל אחד צופה בדבר שונה:

- **GuardDuty** הוא התנהגותי. הוא שואל: *מה קורה ממש עכשיו שנראה שגוי?* קריאות API ממיקומים בלתי-צפויים, מכונות EC2 שיוצרות קשר עם שרתי פיקוד-ובקרה, אישורים בשימוש בשעות חריגות. הוא תופס איומים פעילים וחריגות.
- **Inspector** הוא מבני. הוא שואל: *מה נמצא בסביבה שלנו שיכול להיות מנוצל?* חבילות לא-מתוקנות, תלויות פגיעות, runtimes מיושנים. הוא תופס את התנאים שמאפשרים התקפות.
- **Macie** עוסק בנתונים. הוא שואל: *איזה מידע רגיש יושב בדליי ה-S3 שלנו שלא צריך להיות שם?* ‏PII, רשומות פיננסיות, אישורים שהושארו בקבצים. הוא תופס חשיפה שאינה מייצרת התנהגות חריגה — סתם נתונים במקום הלא-נכון.

פריצה הכוללת CVE ידוע עשויה להופיע בכל שלושתם: ‏Inspector היה מסמן את הפגיעות לפני ההתקפה. ‏GuardDuty היה מסמן את ההתנהגות החריגה במהלך ההתקפה. ‏Macie היה מסמן את הנתונים שהוצאו לאחר שנחתו ב-S3.

שלוש עדשות שונות, שלושה אופקי זמן שונים, אף אחת מהן אינה תחליף לאחרות.

**AWS Network Firewall: בוחן התעבורה**

עוד מומחה אחד ראוי לאזכור לפני שתיבת הכלים נסגרת. ‏security groups ו-NACLs (פרק 15) מסננים תעבורה לפי IP, פורט, ופרוטוקול — הם יכולים לומר *מי* יכול לדבר עם *מה*, אבל הם לא יכולים להסתכל בתוך השיחה. ‏**AWS Network Firewall** הוא firewall מנוהל, ‏stateful שאתם פורסים ברמת ה-VPC. הוא מבצע deep packet inspection: סינון לפי שם דומיין (אפשר יוצא רק ל-`*.eatnimbus.com` ולמאגרי החבילות שלכם), חסימת תעבורה שתואמת חתימות חדירה (IDS/IPS, תואם לכללי Suricata), ובחינת זרימות ש-security groups היו פשוט מעבירים כי מספר הפורט נראה בסדר.

"אז זה security group עם מוח," אמר Leo.

"זה המכשיר שהייתם קונים מספק firewall," אמרה Priya, "רק מנוהל, מתרחב-אוטומטית, ופרוס ברשת המשנה שלו כך שכל התעבורה פנימה והחוצה מה-VPC מנותבת דרכו."

אותות מבחן: "בחן או סנן תעבורה לפי שם דומיין או מטען," "זיהוי/מניעת חדירה (IDS/IPS) ל-VPC," או "סינון egress מרכזי לתעבורה יוצאת" → Network Firewall. ‏security groups ו-NACLs הם התשובה ל-allow/deny ברמת מכונה ורמת רשת משנה לפי פורט ו-IP; ‏Network Firewall הוא התשובה כשהשאלה דורשת בחינה *בתוך* התעבורה. וכשהשאלה שואלת איך לנהל כללי WAF, ‏Shield Advanced, ‏security groups, *ו-*מדיניויות Network Firewall באופן עקבי על פני חשבונות רבים — זה **AWS Firewall Manager**, שכבת ניהול המדיניות שמעל.

## חוזקות ומגבלות

**AWS Shield**:

- ‏Standard: חינמי ואוטומטי — אין סיבה לא להשתמש בו
- ‏Advanced: מצוין למטרות בעלות פרופיל גבוה; יקר לצוותים קטנים
- ‏Standard סופג התקפות שכבה 3/4 (SYN floods, ‏UDP floods, הגברת DNS) אוטומטית
- ‏Advanced מוסיף הגנת שכבה 7, הודעות בזמן אמת, ואת Shield Response Team

**AWS WAF**:

- קבוצות כללים מנוהלות מפשטות את ההגדרה משמעותית — הגנת OWASP Top 10 בכמה לחיצות
- כללים מותאמים דורשים הבנת דפוסי התקפת HTTP
- ‏rate limiting הוא תכונה חזקה שלעיתים קרובות מתעלמים ממנה — אפקטיבית מול scrapers ו-brute force
- ‏WAF אינו תחליף לקוד יישום מאובטח — הוא שכבת הגנה-לעומק
- התחילו במצב Count, אמתו, ואז עברו ל-Block

**GuardDuty**:

- מאמץ נמוך במיוחד להפעלה (כמה לחיצות, ניסיון חינם של 30 יום)
- ‏findings דורשים סקירה ותגובה אנושית — ‏GuardDuty מזהה, הוא לא מתקן
- ‏false positives קורים — חלק מהפעילות הלגיטימית נראה חריג למודלי ML
- רמות חומרה (Low/Medium/High) עוזרות לתעדף תגובה
- משתלב עם Security Hub, ‏EventBridge, ו-Lambda לזרימות תגובה אוטומטיות

**Amazon Inspector**:

- סריקת פגיעות אוטומטית, רציפה — לא בדיקה חד-פעמית
- סורק מחדש אוטומטית כש-CVEs חדשים מפורסמים או כשמשאבים משתנים
- מכסה מכונות EC2 (חבילות OS ויישום), תמונות מכולה ב-ECR, וחבילות פונקציות Lambda
- ‏findings זורמים ל-Security Hub; דירוגי חומרה עוזרים לתעדף תיקון
- אינו חוסם התקפות — הוא מציף את התנאים שמאפשרים התקפות

**Amazon Macie**:

- מגלה אוטומטית נתונים רגישים (PII, אישורים, נתונים פיננסיים) ב-S3
- תופס חשיפת נתונים שאין לה דפוס התנהגות חריג — ‏GuardDuty היה מפספס אותה
- ניסיון חינם של 30 יום; תשלום לכל דלי לחודש לאחר מכן
- בעל הערך הרב ביותר לצוותים עם דליי S3 רבים ורמות רגישות משתנות

**AWS Security Hub**:

- מצבר findings מ-GuardDuty, ‏Macie, ‏Inspector, ‏Config, ו-Firewall Manager
- בודק תצורה מול benchmarks של אבטחה (CIS, ‏NIST, ‏PCI-DSS)
- בעל הערך הרב ביותר בקנה מידה רב-חשבונות
- הפעילו מוקדם, אפילו אם יש לכם רק חשבון אחד — היסטוריית ה-findings מצטברת

## סיכום

חמישה שירותים, חמש שכבות. כל אחד מטפל בסוג שונה של איום — ואף אחד מהם אינו מחליף את האחרים. התקפת DDoS עוקפת את WAF ו-GuardDuty. ניסיון SQL injection עוקף את Shield. אישור פרוץ בשימוש לאט ובזהירות עשוי לעקוף את Shield ו-WAF לחלוטין — אבל GuardDuty יראה את החריגה. מפתח שמעלה בטעות PII של לקוחות לדלי S3 לניפוי באגים עוקף את שלושתם — אבל Macie תופס את זה.

- **AWS Shield Standard**: הגנת DDoS חינמית, אוטומטית בשכבה 3/4. תמיד פעיל. ספג את ה-SYN flood של 50 Gbps לפני שהגיע ל-load balancer של Nimbus.
- **AWS Shield Advanced**: הגנת DDoS פרמיום עם גישת SRT והגנת עלות. מקרה שימוש ארגוני.
- **AWS WAF**: ‏firewall ברמת היישום. בחנו וסננו בקשות HTTP. צרפו ל-CloudFront, ‏ALB, או API Gateway. השתמשו ב-Managed Rule Groups להגנת OWASP Top 10. כללים מבוססי-קצב להגנה מ-scrapers.
- **Amazon GuardDuty**: זיהוי איומים התנהגותי. מקורות נתונים ליבתיים: אירועי CloudTrail, ‏VPC Flow Logs, ו-DNS logs. הגנות מורחבות אופציונליות מוסיפות S3 events, ‏EKS/ECS runtime monitoring, ‏RDS login events, ופעילות רשת של Lambda. מייצר findings מסווגים לפעילות חריגה. חמישה סוגי findings מרכזיים: ‏UnauthorizedAccess (התחברות לקונסולה), ‏CryptoCurrency (כרייה), ‏Recon (בדיקת פורט), ‏Trojan (תעבורת C2), ‏Policy (תצורת S3 שגויה).
- **Amazon Inspector**: הערכת פגיעות אוטומטית. סורק מכונות EC2, תמונות מכולה ב-ECR, וחבילות פונקציות Lambda ל-CVEs ידועים. רץ ברציפות ומעריך מחדש כשפגיעויות חדשות מפורסמות. ‏findings זורמים ל-Security Hub.
- **Amazon Macie**: גילוי נתונים רגישים ב-S3. מזהה PII, אישורים, ונתונים פיננסיים. תופס חשיפה שאין לה דפוס התנהגות חריג.
- **AWS Security Hub**: מצבר findings מכל שירותי האבטחה ללוח מחוונים אחד. מאפשר ניטור מרכזי על פני מספר חשבונות.
- **CloudTrail**: הבסיס של כל רישום האבטחה של AWS. הפעילו trail שכותב ל-S3 לשמירה ארוכת-טווח. כל שירות אבטחה קורא ממנו.

## טיפים למבחן

*תחום SAA-C03: תכנון ארכיטקטורות מאובטחות (תחום 1, משימה 1.2)*

- **Shield Standard מול Advanced**: ‏Standard חינמי ואוטומטי. ‏Advanced עולה כסף ומוסיף את ה-SRT, הגנת עלות, וזיהוי טוב יותר. אותות מבחן ל-Advanced: "‏DDoS בקנה מידה גדול," "ערובת SLA במהלך התקפות," "הגנה פיננסית מפני זינוקי עלות הקשורים ל-DDoS."
- **אותות מקרה שימוש של WAF**: "חסום SQL injection," "חסום cross-site scripting," "‏rate limit קריאות API," "חסום user-agents ספציפיים," "הגנת OWASP Top 10" → WAF.
- **אותות GuardDuty**: "זהה פעילות API חריגה," "זהה אישורים פרוצים," "סמן חיבורי רשת EC2 חריגים," "מודיעין איומים" → GuardDuty.
- **צירוף WAF**: ניתן לצרף ל-CloudFront (גלובלי), ‏ALB (אזורי), ‏API Gateway (אזורי), ‏AppSync.
- **מקורות נתונים של GuardDuty**: שלושה מקורות ליבתיים — אירועי CloudTrail, ‏VPC Flow Logs, ‏DNS logs. מקורות אופציונליים מורחבים כוללים S3 data events, ‏EKS audit logs, ‏RDS login events, פעילות רשת של Lambda, ו-ECS runtime. המבחן עשוי לשאול איזה מקור נתונים רלוונטי לתרחיש זיהוי ספציפי: "התחברויות RDS חריגות" → GuardDuty RDS Protection; "איומי runtime של מכולה" → GuardDuty EKS/ECS Runtime Monitoring.
- **Macie מול GuardDuty**: זהו מסיח מבחן נפוץ. ‏**Macie** משתמש ב-ML כדי לזהות נתונים רגישים ב-S3 (PII, אישורים, נתונים פיננסיים). ‏**GuardDuty** מזהה איומים וחריגות בהתנהגות. ‏Macie עוסק בתוכן. ‏GuardDuty עוסק בהתנהגות.
- **Inspector מול GuardDuty מול Macie:** שלוש עדשות שונות, אף אחת לא מחליפה את האחרות. ‏**Inspector** = סריקת פגיעות — ‏CVEs על מכונות EC2, תמונות מכולה ב-ECR, וחבילות פונקציות Lambda. רץ ברציפות וסורק מחדש כש-CVEs חדשים מפורסמים. ‏**GuardDuty** = זיהוי איומים התנהגותי — מה קורה ממש עכשיו שנראה חריג. ‏**Macie** = גילוי נתונים רגישים ב-S3 — ‏PII, אישורים, ונתונים פיננסיים שלא צריכים להיות שם. טריגר מבחן: "זהה פגיעויות לא-מתוקנות על EC2" או "סרוק תמונות מכולה ל-CVEs" → Inspector. "זהה קריאות API חריגות או אישורים פרוצים" → GuardDuty. "מצא PII או נתונים רגישים ב-S3" → Macie.
- **Security Hub**: מצבר ממצאי אבטחה ממספר שירותים וחשבונות. תרחיש מבחן: "לחברה יש מספר חשבונות AWS והיא רוצה תצוגה יחידה של כל ממצאי האבטחה" → Security Hub.
- **כללים מבוססי-קצב ב-WAF**: בשימוש להגבלת בקשות לכל IP בחלון זמן. שונה מה-Core Rule Set (שתואם דפוסי התקפה). המבחן משתמש בכללים מבוססי-קצב עבור "מנע ניסיונות התחברות brute force" או "הפחת scraping."
- **CloudTrail + GuardDuty + Security Hub**: שלושת אלה יחד מהווים את הליבה של נצפות האבטחה של AWS. הפעילו CloudTrail תחילה (GuardDuty ו-Security Hub תלויים בו), אז GuardDuty, אז Security Hub כדי לצבר findings.

B) AWS Shield Advanced ו-CloudFront  
C) Amazon GuardDuty ו-AWS Shield Standard  
D) Network ACLs שחוסמים את טווחי ה-IP של ה-botnet

**רמז 1**: הבקשות הן ברמת ה-HTTP (שכבת היישום). איזה שירות פועל בשכבת ה-HTTP?

**רמז 2**: ‏botnets משתמשים בכתובות IP רבות ושונות — חסימת טווחי IP ספציפיים ברמת ה-NACL אינה אפקטיבית מול botnets גדולים.

**רמז 3**: ‏rate limiting לפי כתובת IP יכול להאט את ה-scraping אפילו אם אתם לא יכולים לחסום אותו לחלוטין.

**תשובה**: A

**הסבר**: ‏AWS WAF יכול להגביל קצב בקשות לכל כתובת IP, ומפחית את ההשפעה של scraping בנפח גבוה מכל מקור יחיד. ‏CloudFront מפזר את התעבורה הנכנסת על פני רשת ה-edge של AWS, סופג את הנפח ומגן על ה-origin. כללי WAF יכולים גם להתאים על דפוסי בקשה (בקשות רצופות מהירות לאותה נקודת קצה של API) כדי לזהות התנהגות scraping.

**מדוע לא B?** ‏Shield Advanced מגן מפני הצפות DDoS (שכבה 3/4). התרחיש מתאר scraping ברמת היישום (בקשות HTTP של שכבה 7), ש-Shield אינו בוחן.

**מדוע לא C?** ‏GuardDuty מזהה חריגות בהתנהגות חשבון ה-AWS שלכם — הוא אינו חוסם בקשות HTTP נכנסות. ‏Shield Standard אינו מטפל בהתקפות ברמת היישום.

**מדוע לא D?** ‏botnets גדולים משתמשים באלפי כתובות IP ממקורות מבוזרים. חסימת טווחים ספציפיים היא גישת whack-a-mole שנכשלת מול botnets מתוחכמים.

*תחום SAA-C03: תכנון ארכיטקטורות מאובטחות — משימה 1.2*

**תרגיל 3 — אתגר ארכיטקטורה** *(אופציונלי)*

‏Nimbus שוקלת את מודל האיומים שלה כשהיא מתכוננת לטפל בנתוני כרטיסי אשראי. סקירת ציות PCI-DSS דורשת:

- הגנה מפני התקפות DDoS ברמת הרשת
- סינון ברמת היישום לניצולי אינטרנט ידועים
- רישום של כל קריאות ה-API למאגר ארוך-טווח, עמיד-חבלה
- זיהוי דפוסי גישה חריגים לשירות התשלומים

מפו כל דרישה לשירות AWS ספציפי או תצורה. האם Shield Standard מספיק, או שהקשר ה-PCI-DSS מציע Advanced? היכן הייתם מצרפים WAF?

‏GuardDuty הופעל.

ארבעים ושמונה שעות לאחר מכן, הוא ייצר את ה-finding הראשון שלו: *"מכונת EC2 ‏i-0abc123 מתקשרת עם Tor exit node ידוע."*

‏Leo הסתכל במזהה המכונה.

"זו מכונת הניטור הפנימית," אמר. "זו שהגדרתי כדי להריץ אבחון רשת."

"האם היא אמורה לתקשר עם Tor exit nodes?"

"לא." הוא עצר. "למה שהיא תעשה?"

הוא פתח את המכונה. מישהו התקין עליה כלי — סורק רשת קוד-פתוח לגיטימי שהתברר שגם תקשר עם תשתית Tor לאיסוף נתונים אנונימי.

"אז הכלי התקשר הביתה," אמרה Priya.

"ללא ידיעתי," אישר Leo.

‏Leo הסיר את הכלי. הוא הגדיר תהליך לסקור כל כלי צד-שלישי לפני התקנה.

"זו רמת הפרנויה שאנחנו בה עכשיו?" שאלה Maya.

"כן," אמרה Priya.

"זו הרמה שתמיד היינו צריכים להיות בה?" שאלה Maya.
