# บทที่ 9: เมื่อตารางโตขึ้น

ตารางเมนูมี 50,000 รายการ

นั่นคือผ่าน 287 ร้านอาหาร แต่ละร้านมีพิเศษประจำวัน รายการตามฤดูกาล และรูปแบบตามภูมิภาค รายการบางอย่างมีตัวปรับ — ขนาด ระดับเผ็ด ตัวเลือกโปรตีน

SQL query ที่ดึงเมนูทั้งหมดของร้านอาหารเคยส่งคืนใน 200 มิลลิวินาที

ตอนนี้ใช้เวลาสี่วินาที

สี่วินาทีคือความแตกต่างระหว่างคนที่สั่งอาหารกับคนที่ปิดแอป

**ปัญหากับการยัดทุกอย่างลงในตาราง**

นี่คือความตึงเครียดหลักของฐานข้อมูล relational: ถูกออกแบบมาเพื่อเก็บข้อมูล *ที่มีโครงสร้าง* ในรูปแบบ *ตายตัว*

ถ้าทุกรายการเมนูมีฟิลด์เดียวกัน SQL จะสมบูรณ์แบบ แต่เมนูจริงไม่ได้ทำงานแบบนั้น

**วิธีคิดที่แตกต่างเกี่ยวกับข้อมูล**

ฐานข้อมูล NoSQL เก็บข้อมูลต่างกัน วิธีการทั่วไปหนึ่งคือ *โมเดลเอกสาร*: แต่ละบันทึกถูกเก็บเป็นเอกสารที่เป็นตัวเอง (โดยปกติเป็น JSON) และเอกสารในคอลเลกชันเดียวกันไม่จำเป็นต้องมีฟิลด์เดียวกัน

รายการเมนูในโมเดลเอกสารอาจมีลักษณะดังนี้:

```json
{
  "itemId": "ITEM-001",
  "restaurantId": "NIMBUS-047",
  "name": "Shrimp Arepa",
  "price": 3200,
  "modifiers": [
    { "name": "Spice Level", "options": ["mild", "medium", "hot"] },
    { "name": "Protein", "options": ["shrimp", "fish", "mixed"] }
  ],
  "available": true,
  "seasonalUntil": "2024-03-31"
}
```

รายการอื่นอาจมีลักษณะแตกต่างกันโดยสิ้นเชิง รูปทรงต่างกัน คอลเลกชันเดียวกัน ไม่มีปัญหา

**พบกับ DynamoDB**

Amazon DynamoDB คือ managed NoSQL database service ของ AWS มันเก็บข้อมูลเป็น items (ไม่ใช่ rows) และ items ถูกรวบรวมเป็น tables

ทุก item ใน DynamoDB table ต้องมี **primary key** ที่ระบุมันได้อย่างไม่ซ้ำกัน ทุกอย่างอื่นยืดหยุ่น

Primary key สามารถเป็นหนึ่งในสองรูปแบบ:

**เฉพาะ partition key**: attribute เดียวที่ต้องไม่ซ้ำกันใน items ทั้งหมด

**Partition key + sort key (composite primary key)**: สอง attributes ที่ *ร่วมกัน* สร้างชุดค่าผสมที่ไม่ซ้ำกัน

สำหรับเมนูของ Nimbus:

- Partition key: `restaurantId`
- Sort key: `itemId`

ซึ่งหมายความว่าคุณสามารถดึง items ทั้งหมดสำหรับร้านอาหารเฉพาะได้อย่างมีประสิทธิภาพ

**การเลือก partition key ที่ดี**:

- **ดี**: Cardinality สูง กระจายอย่างสม่ำเสมอ (`restaurantId` กับร้านอาหารจำนวนมาก)
- **แย่**: Cardinality ต่ำ (`true/false`, `category`) — ข้อมูลส่วนใหญ่ตกอยู่ที่ partition ไม่กี่อัน สร้าง "hot spots"

**โหมดความจุ**

**Provisioned capacity**: คุณระบุจำนวน read และ write units ที่ต้องการ

**On-demand capacity**: DynamoDB ขยายขนาดโดยอัตโนมัติตาม traffic จริง

**ความสม่ำเสมอ**

**Eventually consistent read**: ค่าเริ่มต้น ถูกกว่า และผลลัพธ์อาจล้าหลังการเขียนที่เสร็จสมบูรณ์ล่าสุดเล็กน้อย

**Strongly consistent read**: DynamoDB สามารถส่งคืนค่า committed ล่าสุด ใช้ read capacity มากกว่า

## สรุป

- DynamoDB คือ managed NoSQL database service ของ AWS
- Items ถูกเก็บเป็นเอกสารที่ยืดหยุ่น — ไม่จำเป็นต้องมี schema ตายตัว
- ทุก item ต้องมี **primary key**: partition key เพียงอย่างเดียว หรือ partition key + sort key
- **On-demand** ขยายขนาดโดยอัตโนมัติ **Provisioned** ถูกกว่าถ้า traffic ของคุณคาดเดาได้
- Reads แบบ **Eventually consistent** ถูกกว่าและเร็วกว่า Reads แบบ **Strongly consistent** ทันสมัยเสมอ

## เคล็ดลับการสอบ

*SAA-C03 Domain: ออกแบบสถาปัตยกรรมที่มีประสิทธิภาพสูง (Domain 3, Task 3.3)*

- รู้กฎ partition key: **cardinality สูง กระจายอย่างสม่ำเสมอ** Hot partitions เป็นกับดักการสอบที่พบบ่อย
- **DynamoDB Streams**: บันทึกการเปลี่ยนแปลงระดับ item แบบ real-time สถานการณ์การสอบทั่วไป: "เรียก Lambda function เมื่อ record เปลี่ยนแปลง"
- **DAX (DynamoDB Accelerator)**: in-memory caching layer สำหรับ DynamoDB
