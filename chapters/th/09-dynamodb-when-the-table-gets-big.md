**ปัญหากับการยัดทุกอย่างลงในตาราง**

นี่คือความตึงเครียดหลักของฐานข้อมูล relational: ถูกออกแบบมาเพื่อเก็บข้อมูล *ที่มีโครงสร้าง* ในรูปแบบ *ตายตัว*

ถ้าทุกรายการเมนูมีฟิลด์เดียวกัน — ชื่อ ราคา คำอธิบาย หมวดหมู่ — SQL จะสมบูรณ์แบบ คุณจะมีตาราง `menu_items` ที่สะอาด แถวสำหรับแต่ละรายการ และ queries ที่สมเหตุสมผล

แต่เมนูจริงไม่ได้ทำงานแบบนั้น

รายการหนึ่งอาจมีตัวปรับ "ระดับเผ็ด" อีกรายการอาจมี "ตัวเลือกโปรตีน" รายการที่สามอาจมีคอมโบซ้อนกัน — "สั่งชุดครอบครัวแล้วได้จานหลักสองจาน เครื่องเคียงสองอย่าง และเครื่องดื่มหนึ่งแก้ว" โครงสร้างของข้อมูลแตกต่าง *ในแต่ละรายการ*

ใน SQL คุณมีสองทางเลือก:

**ทางเลือกที่ 1**: สร้างคอลัมน์สำหรับตัวปรับทุกแบบที่เป็นไปได้ สิ่งนี้สร้างตารางที่กว้างมากซึ่งคอลัมน์ส่วนใหญ่ว่างเปล่าตลอดเวลา

**ทางเลือกที่ 2**: สร้างตาราง modifiers แยกต่างหากแล้ว join เข้ากับตาราง menu items วิธีนี้ใช้ได้ แต่เมนูที่ซับซ้อนต้องใช้หลาย join และที่ห้าหมื่นรายการกับปริมาณการอ่านสูง join เหล่านั้นกลายเป็นค่าใช้จ่ายสูง

"มีทางเลือกที่สาม" Priya พูด เธอนั่งอ่านเอกสารเงียบ ๆ อยู่ที่มุมห้อง

เธอเปิดแท็บใหม่ "ถ้าข้อมูลไม่ต้องยัดลงในตารางล่ะ?"

**วิธีคิดที่แตกต่างเกี่ยวกับข้อมูล**

ฐานข้อมูล relational เก็บข้อมูลเป็นแถวในตาราง แต่ละแถวต้องเป็นไปตาม schema ของตาราง schema ถูกตกลงไว้ล่วงหน้า

ฐานข้อมูล NoSQL เก็บข้อมูลต่างกัน วิธีการทั่วไปหนึ่งคือ *โมเดลเอกสาร*: แต่ละบันทึกถูกเก็บเป็นเอกสารที่เป็นตัวเอง (โดยปกติเป็น JSON) และเอกสารในคอลเลกชันเดียวกันไม่จำเป็นต้องมีฟิลด์เดียวกัน

รายการเมนูในโมเดลเอกสารอาจมีลักษณะดังนี้:

```json
{
  "itemId": "ITEM-001",
  "restaurantId": "NIMBUS-047",
  "name": "Shrimp Arepa",
  "price": 3200,
  "modifiers": [
    { "name": "Spice Level", "options": ["mild", "medium", "hot"] },
    { "name": "Protein", "options": ["shrimp", "fish", "mixed"] }
  ],
  "available": true,
  "seasonalUntil": "2024-03-31"
}
```

รายการอื่นอาจมีลักษณะแตกต่างกันโดยสิ้นเชิง:

```json
{
  "itemId": "ITEM-002",
  "restaurantId": "NIMBUS-047",
  "name": "Family Feast",
  "price": 9800,
  "includes": ["ITEM-010", "ITEM-011", "ITEM-015", "ITEM-020"],
  "servings": 4,
  "available": true
}
```

รูปทรงต่างกัน คอลเลกชันเดียวกัน ไม่มีปัญหา

"ดังนั้นฐานข้อมูลเป็นเหมือนระบบจัดแฟ้มมากกว่าตาราง" Maya พูด

"ใช่เลย" Priya พูด "คุณใส่เอกสารใดก็ได้ในลิ้นชักใดก็ได้ คุณไม่ต้องตัดเอกสารให้พอดีกับขนาดที่ตายตัว"

**พบกับ DynamoDB**

Amazon DynamoDB คือ managed NoSQL database service ของ AWS มันเก็บข้อมูลเป็น items (ไม่ใช่ rows) และ items ถูกรวบรวมเป็น tables (การตั้งชื่อคล้ายกับ SQL แต่พฤติกรรมต่างกัน)

ทุก item ใน DynamoDB table ต้องมี **primary key** ที่ระบุมันได้อย่างไม่ซ้ำกัน ทุกอย่างอื่นยืดหยุ่น

Primary key สามารถเป็นหนึ่งในสองรูปแบบ:

**เฉพาะ partition key**: attribute เดียวที่ต้องไม่ซ้ำกันใน items ทั้งหมด

**Partition key + sort key (composite primary key)**: สอง attributes ที่ *ร่วมกัน* สร้างชุดค่าผสมที่ไม่ซ้ำกัน สิ่งนี้ทำให้คุณมีหลาย items ที่มี partition key เดียวกันได้ โดยแยกแยะด้วย sort key ของมัน

สำหรับเมนูของ Nimbus:

- Partition key: `restaurantId`
- Sort key: `itemId`

ซึ่งหมายความว่าคุณสามารถดึง items ทั้งหมดสำหรับร้านอาหารเฉพาะได้อย่างมีประสิทธิภาพ — DynamoDB รู้แน่ชัดว่าต้องมองที่ partition ไหน

"ทำไมถึงเรียกว่า partition key?" Tom ถาม

"แล้วถ้ามีคนพยายามบุกรุกล่ะ?" Priya ถาม "ถ้า partition key เดาได้ จะมีคนสแปม partition เดียวด้วยการเขียนและทำให้เกิดสภาวะ hot-spot โดยตั้งใจได้ไหม?"

"ได้" Leo พูด "นั่นคือ vector ของ denial-of-service สำหรับตารางที่ออกแบบไม่ดีจริง ๆ ซึ่งเป็นเหตุผลอีกข้อหนึ่งที่ต้องเลือก key ที่มี cardinality สูง"

Priya จดมันลงไป

**DynamoDB เก็บข้อมูลภายในอย่างไร**

DynamoDB ถูกสร้างมาเพื่อ scale แนวนอนไปยังขนาดมหึมา มันทำได้ผ่าน *partitioning* — ข้อมูลถูกแยกข้ามเครื่องจริงจำนวนมากตาม partition key

เมื่อคุณเขียน item DynamoDB จะ hash ค่า partition key และใช้ hash นั้นเพื่อกำหนดว่า partition จริง (และดังนั้นเซิร์ฟเวอร์ใด) ที่เก็บ item เมื่อคุณอ่าน item DynamoDB ทำการคำนวณเดียวกันเพื่อหามันได้ทันที

คิดเหมือนระบบไปรษณีย์ ถ้าทุกซองมีรหัสไปรษณีย์ บริการไปรษณีย์ไม่อ่านทุกซองเพื่อหาว่ามันควรไปที่ไหน — มันคัดแยกตามรหัสไปรษณีย์ DynamoDB คัดแยกตาม hash ของ partition key

"เดี๋ยว — แต่ *ทำไม* เราถึงทำแบบนั้น?" Maya ถาม "ทำไมการเลือก partition key ถึงสำคัญมากนัก? เราเลือกอะไรก็ได้ไม่ได้หรือ?"

นี่คือคำถามที่ถูกต้อง partition key คือการตัดสินใจออกแบบที่สำคัญที่สุดเพียงข้อเดียวใน DynamoDB schema นี่คือเหตุผล:

ถ้าคุณเลือก partition key ที่มี cardinality ต่ำ — เช่น `available: true/false` หรือ `category: "main/side/drink"` — ข้อมูลส่วนใหญ่ของคุณตกอยู่บน partition ไม่กี่อันเดียวกัน DynamoDB เรียกสิ่งนี้ว่า "hot partition" เซิร์ฟเวอร์เดียวจัดการ traffic ส่วนใหญ่ มันโหลดเกิน DynamoDB เริ่ม throttle คำขอ ผู้ใช้เริ่มเห็น error

- **ดี**: Cardinality สูง ค่ากระจายอย่างสม่ำเสมอ (`restaurantId` กับร้านอาหารจำนวนมาก)
- **แย่**: Cardinality ต่ำ (`true/false`, `category`) — ข้อมูลส่วนใหญ่ตกอยู่ที่ partition ไม่กี่อัน สร้าง "hot spots"

"ดังนั้นถ้าผมใช้ `available: true` เป็น partition key" Leo พูดช้า ๆ "รายการที่มีให้ทั้งหมดจะกองอยู่บน partition เดียวกัน"

"และฐานข้อมูลของคุณจะละลายตอนช่วงมื้อเย็นเร่งด่วน" Priya ยืนยัน

Leo ปิดแล็ปท็อปช้า ๆ

**เหตุการณ์ Hot Partition**

พวกเขาไม่ต้องจินตนาการมัน หลายเดือนต่อมา — ในช่วงเดือนที่สองบน DynamoDB ก่อนที่พวกเขาจะซึมซับกฎจริง ๆ — พวกเขาจะได้เรียนรู้มันอย่างยากลำบาก

ทีมเปิดตัวฟีเจอร์ใหม่: badge "Featured Items" พาร์ทเนอร์ร้านอาหารสามารถมาร์กรายการได้สูงสุดห้ารายการว่าเป็น featured ฟีเจอร์นี้เก็บ attribute `featured: true` บนแต่ละรายการ

Leo คิดว่ามันจะมีประโยชน์ที่จะ query รายการ featured ทั้งหมดข้ามทุกร้านอาหาร — สำหรับ widget "trending items" บนหน้าแรก เขาสร้าง secondary index เพื่อรองรับ query นี้ index ใช้ `featured` เป็น partition key

"มันจะไม่เป็นไร" เขาพูด "จะมีรายการ featured ได้กี่รายการกัน?"

ประมาณหนึ่งพันสองร้อยรายการ กระจายข้ามสองร้อยสี่สิบร้านอาหาร

**การอ่านและเขียนในระดับใหญ่**

DynamoDB จัดการคำขอได้หลายล้านต่อวินาที แต่มันต้องรู้ว่าจะ provision capacity เท่าไร

มีโหมดความจุสองแบบ:

**Provisioned capacity**: คุณระบุจำนวน read และ write units ที่ต้องการ DynamoDB สำรองความจุนั้นไว้ให้คุณและ throttle traffic ที่เกิน ราคาคาดเดาได้ ราคาต่อคำขอต่ำกว่า

units มีนิยามที่แม่นยำ และข้อสอบคาดหวังให้คุณรู้: หนึ่ง **Read Capacity Unit (RCU)** คือหนึ่ง strongly consistent read ต่อวินาทีของ item ขนาดไม่เกิน 4 KB — หรือสอง eventually consistent reads ของขนาดเดียวกัน หนึ่ง **Write Capacity Unit (WCU)** คือหนึ่ง write ต่อวินาทีของ item ขนาดไม่เกิน 1 KB items ที่ใหญ่กว่ากินมากขึ้นตามสัดส่วน: การอ่าน item ขนาด 12 KB แบบ strongly consistent กิน 3 RCUs การเขียน item ขนาด 3 KB กิน 3 WCUs

**On-demand capacity**: DynamoDB ขยายขนาดโดยอัตโนมัติตาม traffic จริงของคุณ ไม่ต้องวางแผน capacity เป็นประจำ ราคาต่อคำขอสูงกว่า และง่ายกว่ามากในการดำเนินงาน แม้ว่าการพุ่งขึ้นกะทันหันเกินรูปแบบ traffic ล่าสุดของตารางไปไกลก็ยังทำให้เกิด throttling ได้ถ้ามันไต่ขึ้นเร็วเกินไป

สำหรับ Nimbus เมนูถูกอ่านบ่อยกว่าถูกเขียนมาก ลูกค้าเปิดแอป เรียกดูเมนู — นั่นคือการอ่านจำนวนมาก พาร์ทเนอร์ร้านอาหารอัปเดตเมนูสัปดาห์ละสองครั้ง — นั่นคือการเขียนเป็นครั้งคราว

"On-demand สมเหตุสมผลสำหรับตอนนี้" Tom พูด "เรายังไม่รู้รูปแบบ traffic ของเรา จ่ายต่อคำขอแพงกว่าดีกว่า under-provision แล้วโดน throttle"

**ความสม่ำเสมอ: ข้อมูลของคุณสดแค่ไหน?**

DynamoDB ทำซ้ำข้อมูลข้ามหลาย Availability Zone โดยอัตโนมัติ นั่นดีเยี่ยมสำหรับความทนทาน แต่มันก็หมายความว่าคุณต้องคิดให้ชัดเจนเรื่อง read consistency

เมื่อคุณอ่านจาก DynamoDB คุณมีทางเลือก:

**Eventually consistent read**: นี่คือค่าเริ่มต้น มันถูกกว่า และผลลัพธ์อาจล้าหลังการเขียนที่เพิ่งเสร็จสมบูรณ์เล็กน้อย

**Strongly consistent read**: สำหรับการอ่านกับตารางหรือ local secondary index DynamoDB สามารถส่งคืนค่า committed ล่าสุดจากการเขียนก่อนหน้าที่สำเร็จ สิ่งนี้กิน read capacity มากกว่าและไม่มีให้สำหรับ global secondary indexes

สำหรับข้อมูลเมนู eventual consistency ก็โอเค รายการเมนูที่ล้าหลังหนึ่งมิลลิวินาทีไม่สำคัญ

สำหรับข้อมูลยืนยันออเดอร์ — "ออเดอร์นี้ถูกสั่งแล้วหรือยัง?" — คุณจะต้องการ strong consistency ลูกค้าไม่ควรเห็นข้อความ "ลองใหม่" ในขณะที่ออเดอร์ของพวกเขาเพิ่งถูกบันทึก

"มันเหมือนความแตกต่างระหว่างการเช็คยอดเงินในธนาคารบนแอปกับการโทรหาธนาคารโดยตรง" Maya พูด "แอปอาจช้ากว่าสามสิบวินาที การโทรเป็นปัจจุบันเสมอ"

คุณอาจสงสัย: ถ้า DynamoDB ทำซ้ำข้ามหลาย AZ โดยอัตโนมัติ ทำไม consistency mode ถึงสำคัญเลย? นี่คือคำตอบ: การทำซ้ำใช้เวลาเล็กน้อยแต่ไม่ใช่ศูนย์ — โดยปกติเป็นมิลลิวินาที eventually consistent read อาจถูกเสิร์ฟจาก replica ที่ยังไม่ได้รับการเขียนล่าสุด strongly consistent read ติดต่อ copy หลักของข้อมูลเสมอ สำหรับ use case ส่วนใหญ่ (รายการเมนู แคตตาล็อกสินค้า โปรไฟล์ผู้ใช้) ความล่าช้าแทบสังเกตไม่เห็น สำหรับ use case ที่ความถูกต้องสำคัญในขณะที่อ่าน (การยืนยันการชำระเงิน ความพร้อมของสินค้าคงคลัง) คุณต้องการ strong consistency

**Secondary Indexes: Query นอกเหนือจาก Primary Key**

จะเป็นยังไงถ้าคุณต้องเข้าถึงข้อมูลในแบบที่ต่างจากที่ primary key อนุญาต?

DynamoDB รองรับ **secondary indexes** — key ทางเลือกที่ทำให้คุณ query ข้อมูลเดียวกันโดยใช้ attribute ต่างกัน

**Local Secondary Index (LSI)**: ใช้ partition key เดียวกับตาราง แต่ sort key ต่างกัน ต้องกำหนดในตอนสร้างตารางและเพิ่มภายหลังไม่ได้ ใช้ provisioned capacity ของตารางร่วมกัน เพราะ LSI ใช้ partition ร่วมกัน มันรองรับ strongly consistent reads

**Global Secondary Index (GSI)**: index ที่แยกออกมาโดยสิ้นเชิงด้วย partition key และ sort key ของตัวเอง — ต่างจาก primary key ของตาราง สามารถเพิ่มหรือลบได้หลังจากตารางมีอยู่แล้ว ซึ่งให้ความยืดหยุ่นแก่คุณ มีการตั้งค่า provisioned capacity ของตัวเอง แยกจากตาราง

สำหรับ Nimbus: ถ้าพวกเขาต้องการ query รายการตามช่วงราคา GSI สามารถรองรับสิ่งนั้นได้ — แต่มีกฎหนึ่งข้อที่ต้องจำ: partition key รับเฉพาะการเปรียบเทียบ *เท่ากัน* ดังนั้น `price` (ซึ่งคุณต้องการ range ผ่าน) ต้องเป็น **sort key** โดยมี attribute สำหรับจัดกลุ่มเช่น category หรือ `cuisineType#region` เป็น GSI partition key นั่นคือ index ที่สร้างในตัวอย่างเดินผ่านด้านล่างพอดี

ถ้าคุณเลือก LSI คุณจะได้ strong consistency และ capacity ที่ใช้ร่วมกัน แต่คุณถูกล็อกไว้กับการออกแบบนั้นตอนสร้างตาราง; ถ้าคุณเลือก GSI คุณจะได้ความยืดหยุ่นในการเพิ่มมันภายหลังและการ scale อิสระ แต่คุณเสียความสามารถในการทำ strongly consistent reads กับ index

**ตัวอย่างเดินผ่าน GSI Query**

Priya เดินผ่านตัวอย่างที่เป็นรูปธรรม Nimbus อยากรองรับฟีเจอร์ "เรียกดูตามประเภทอาหาร": แสดงอาหารที่มีให้ทั้งหมดของประเภทอาหารหนึ่ง ๆ ข้ามทุกร้านอาหารพาร์ทเนอร์

ตารางหลักมี `restaurantId` เป็น partition key และ `itemId` เป็น sort key คุณ query "ทุกรายการที่มี cuisineType = Colombian" อย่างมีประสิทธิภาพไม่ได้ — นั่นต้องการ scan ข้ามทุก partition

พวกเขาสร้าง GSI:

- GSI partition key: `cuisineType#region` (เช่น "Colombian#NYC", "Mexican#Chicago")
- GSI sort key: `price`

GSI ทำซ้ำ projection ของแต่ละ item — เฉพาะฟิลด์ที่ต้องการสำหรับหน้าเรียกดู — ลงในที่เก็บ index ตอนนี้ query กับ GSI ด้วย `cuisineType#region = "Colombian#NYC"` ไปยัง partition นั้นของ index โดยตรง

"ทำไมไม่ใช้ `cuisineType` อย่างเดียว?" Leo ถาม

"เพราะ cuisineType อย่างเดียวมี cardinality ต่ำ" Priya พูด "Colombian, Mexican, Thai — ยี่สิบค่ารวม Hot partition อีกแล้ว การเพิ่ม region ให้เรา Colombian#NYC, Colombian#Chicago, Colombian#LA partition มากขึ้น กระจายดีขึ้น"

"มันรู้สึกเหมือนแฮกนิดหน่อย"

"มันคือ pattern มาตรฐานของ DynamoDB เรียกว่า partition key sharding บางครั้งคุณต้องทำงานกับเครื่องมือ"

GSI query ในโค้ดมีลักษณะดังนี้:

```python
response = dynamodb.query(
    TableName='menu',
    IndexName='cuisineType-price-index',
    KeyConditionExpression='#ct = :ct AND price BETWEEN :lo AND :hi',
    ExpressionAttributeNames={'#ct': 'cuisineType#region'},
    ExpressionAttributeValues={
        ':ct': {'S': 'Colombian#NYC'},
        ':lo': {'N': '1000'},
        ':hi': {'N': '2500'}
    }
)
```

นั่นส่งคืนอาหาร Colombian ทั้งหมดใน New York City ราคาระหว่าง $10 และ $25 เรียงตามราคา ในเวลาประมาณ 4 มิลลิวินาที

"นั่นเร็วกว่า SQL query เก่าด้วยปัจจัยหนึ่งพัน" Leo พูด

"เพราะมันสัมผัสแค่ partition เดียวของ index เดียว" Priya ยืนยัน "ไม่ใช่ scan ทุกแถวในตารางที่ join แล้ว"

**DynamoDB Streams: ตอบสนองต่อการเปลี่ยนแปลง**

"เราคิดเรื่องว่าจะเกิดอะไรขึ้นเมื่อรายการเมนูถูกอัปเดตหรือยัง?" Priya ถามเช้าวันหนึ่ง "พาร์ทเนอร์ร้านอาหารเปลี่ยนราคา เราต้องอัปเดต search index เราต้อง invalidate รายการ ElastiCache" — บริการ caching ที่เราจะพบในบทถัดไป — "และเราต้อง log การเปลี่ยนแปลงสำหรับ analytics pipeline ของเรา"

"เราทำทั้งหมดนั้นใน API handler ได้" Leo พูด "เมื่อการเขียนเกิดขึ้น ทริกเกอร์การอัปเดต downstream ทั้งหมด"

"แล้วถ้าอันใดอันหนึ่งล้มเหลวล่ะ?"

"ก็... เรา retry"

"ถ้า EC2 instance crash หลังการเขียนแต่ก่อนการอัปเดต downstream ล่ะ? ข้อมูลถูกบันทึก แต่ไม่มีอะไรรู้เรื่องการเปลี่ยนแปลง"

Leo คิดเกี่ยวกับมัน

"เราต้องการให้การอัปเดตถูกรับประกัน" เขาพูด "แม้แอปพลิเคชันโค้ดของเราล้มเหลวกลางทาง"

นี่คือสิ่งที่ **DynamoDB Streams** แก้ไข

DynamoDB Streams จับ log ที่เรียงตามเวลาของทุกการแก้ไข item ใน DynamoDB table ทุกการ insert, update และ delete ถูกเขียนลง stream เป็น event stream เก็บ event ไว้ 24 ชั่วโมง

คุณสามารถแนบ Lambda function เข้ากับ stream ทุกครั้งที่ item เปลี่ยน Lambda function ถูกเรียกพร้อมสถานะก่อนและหลังของ item จากนั้น Lambda สามารถ:

- อัปเดต search index (OpenSearch)
- Invalidate รายการ cache ใน ElastiCache
- ส่งการแจ้งเตือนไปยังระบบอื่น
- ป้อน analytics pipeline
- ทำซ้ำการเปลี่ยนแปลงไปยังตารางหรือฐานข้อมูลอื่น

ความแตกต่างสำคัญ: Streams แยกการเขียนออกจากผลกระทบ downstream การเขียน DynamoDB สำเร็จโดยอิสระจากว่า Lambda จะสำเร็จหรือไม่ ถ้า Lambda ล้มเหลว DynamoDB retry มัน ถ้าแอปพลิเคชัน crash หลังการเขียน stream event ยังอยู่ที่นั่น — Lambda จะประมวลผลมันเมื่อสิ่งต่าง ๆ ฟื้นตัว

"ดังนั้นเราเขียนลง DynamoDB" Leo พูดช้า ๆ "และ DynamoDB รับประกันว่าการประมวลผล downstream เกิดขึ้นในที่สุด แม้เรา crash"

"ใช่เลย" Priya พูด "มันคือความแตกต่างระหว่างการหวังว่า side effect ทั้งหมดของคุณจะรัน กับการมีฐานข้อมูลรับประกันพวกมัน"

สำหรับ Nimbus พวกเขาต่อ DynamoDB Streams บนตารางเมนูเข้ากับ Lambda ที่ invalidate รายการ ElastiCache เมื่อรายการเมนูเปลี่ยน cache อยู่ในสภาพสม่ำเสมอกับฐานข้อมูล โดยอัตโนมัติ โดยไม่มีแอปพลิเคชันโค้ดใดจัดการการ invalidation

**การแลกเปลี่ยน: สิ่งที่ DynamoDB ทำไม่ได้**

NoSQL ไม่ได้ดีกว่า SQL อย่างเด็ดขาด มันคือเครื่องมือที่ต่างกันสำหรับงานที่ต่างกัน

สิ่งที่ DynamoDB ยอมเสียไป:

**Query ที่ยืดหยุ่น**: ใน SQL คุณ filter และ sort ตามคอลัมน์ใดก็ได้ ใน DynamoDB คุณ query ได้อย่างมีประสิทธิภาพเฉพาะตาม primary key การ query ตามฟิลด์ใด ๆ ต้องการ *scan* (อ่านทุก item ในตาราง) ซึ่งแพงและช้าในระดับใหญ่

**Joins**: DynamoDB ไม่ทำ joins ถ้าคุณต้องการข้อมูลจากสองตาราง คุณทำการอ่านสองครั้งแยกกันในแอปพลิเคชันโค้ดของคุณ

**Transactions**: DynamoDB รองรับ transactions แต่ฐานข้อมูล relational ยังเหมาะกว่าโดยธรรมชาติสำหรับ multi-entity workflows หลายอย่าง ระบบที่เน้นรายงาน และการออกแบบที่เน้น join

**ความคุ้นเคย**: เครื่องมือ ทักษะ และโมเดลความคิดของ SQL หลายทศวรรษไม่ได้โอนย้ายโดยตรง

สิ่งที่ DynamoDB ทำได้ดีเยี่ยม:

- access pattern แบบ key-value และ document
- ขนาดมหึมา (latency มิลลิวินาทีหลักเดียวที่ขนาดใด ๆ)
- Serverless ไม่ต้องจัดการโครงสร้างพื้นฐาน
- การ scale อัตโนมัติ, multi-AZ replication, backups
- ประสิทธิภาพที่คาดเดาได้ไม่ว่าปริมาณข้อมูลจะเท่าไร

"ดังนั้นกฎคือ" Maya พูด "ใช้ DynamoDB เมื่อคุณรู้ *แน่ชัด* ว่าคุณจะเข้าถึงข้อมูลอย่างไร ใช้ SQL เมื่อคุณยังไม่รู้"

**Amazon DocumentDB: เมื่อ Workload ของคุณพูดภาษา MongoDB**

โปรเจกต์ที่สอง — เอกสารเมนู JSON ที่สมบูรณ์พร้อม schema ที่ยืดหยุ่นในแต่ละร้าน — อธิบายฐานข้อมูลแบบเอกสาร Nimbus ใช้ schema ยืดหยุ่นของ DynamoDB สำหรับเมนูอยู่แล้ว แต่เมื่อทีมสร้างฟีเจอร์เมนูที่ซับซ้อนขึ้น (ตัวปรับซ้อนกัน การตั้งราคาตามเวลา โครงสร้างคอมโบที่ซับซ้อน) โมเดล query ของ DynamoDB เริ่มแสดงขีดจำกัด ทีมต้องการ document query ที่สมบูรณ์ขึ้น: หารายการเมนูทั้งหมดที่ตัวปรับซ้อนกันมีตัวเลือกเฉพาะ filter ตามฟิลด์ใด ๆ ภายในโครงสร้าง JSON

"นั่นคือ pattern ของฐานข้อมูลเอกสาร" Priya พูด "MongoDB"

"เรารัน MongoDB บน EC2 ได้" Leo เสนอ

"หรือเราใช้ DocumentDB ได้" Priya พูด

**Amazon DocumentDB** คือ managed document database ที่เข้ากันได้กับ MongoDB มันเก็บข้อมูลเป็นเอกสารแบบ JSON ที่มี schema ยืดหยุ่น — เอกสารต่างกันในคอลเลกชันเดียวกันมีฟิลด์ต่างกันได้ DocumentDB รองรับภาษา query, API และ driver ของ MongoDB ถ้า workload ของคุณรันบน MongoDB อยู่แล้ว DocumentDB พูดภาษาเดียวกัน เส้นทางการย้ายคือการย้าย connection string ไม่ใช่การเขียนแอปพลิเคชันใหม่

DocumentDB เป็น managed เต็มรูปแบบ: ไม่ต้อง patch, automated backups, Multi-AZ high availability, read replicas และที่เก็บที่ขยายขึ้นโดยอัตโนมัติเมื่อข้อมูลของคุณโต

"ดังนั้นเราย้ายเมนูไป DocumentDB" Leo พูด "และ query ที่เรามีอยู่แล้วในรูปแบบ MongoDB ก็ใช้งานได้เลย?"

"ด้วยการทดสอบความเข้ากันได้เล็กน้อย ใช่" Priya ยืนยัน "DocumentDB รองรับ query API ส่วนใหญ่ของ MongoDB ตรวจสอบ compatibility matrix ก่อนสมมติว่าครอบคลุมทั้งหมด แต่สำหรับ document query และ aggregations มันตรงไปตรงมา"

สัญญาณในข้อสอบสำหรับ DocumentDB ง่าย: **"MongoDB-compatible"** หรือ **"document store"** ถ้าสถานการณ์กล่าวถึง MongoDB หรือข้อมูลแบบเอกสาร DocumentDB คือคำตอบ AWS แบบ managed

**Amazon Neptune: เมื่อความสัมพันธ์คือข้อมูล**

recommendation engine เป็นปัญหาที่ยากกว่า

คำถามไม่ใช่ "ลูกค้าคนนี้สั่งอะไร?" — นั่นคือ DynamoDB lookup ง่าย ๆ คำถามคือ: "ลูกค้าคนไหนมีโปรไฟล์รสนิยมคล้ายกับลูกค้าคนนี้ และอาหารอะไรที่ลูกค้าเหล่านั้นชอบที่ลูกค้าคนนี้ยังไม่เคยลอง?"

นั่นคือปัญหา graph โมเดลข้อมูลไม่ใช่ตารางของแถวหรือคอลเลกชันของเอกสาร มันคือเครือข่ายของความสัมพันธ์: ลูกค้าเชื่อมต่อกับอาหาร (สั่ง ให้คะแนน ดู) อาหารเชื่อมต่อกับร้านอาหารและประเภทอาหาร ร้านอาหารเชื่อมต่อกับย่านและเมือง คำแนะนำไม่ได้อยู่ในจุดข้อมูล — มันอยู่ในเส้นทางระหว่างพวกมัน

"เราต้องการฐานข้อมูล graph" Priya พูด

**Amazon Neptune** คือ managed graph database เต็มรูปแบบ มันรองรับโมเดล graph สองแบบ: **property graph** (query ด้วยภาษา traversal ชื่อ Gremlin) และ **RDF** (query ด้วย SPARQL) คุณเลือกตาม graph stack ที่มีอยู่หรือความชอบของทีม ทั้งสองรันบนโครงสร้างพื้นฐาน Neptune เดียวกัน

ฐานข้อมูล graph ถูกสร้างมาเฉพาะสำหรับ workload ที่ความสัมพันธ์ระหว่างจุดข้อมูลสำคัญพอ ๆ กับตัวข้อมูลเอง: social network (ใครเชื่อมกับใคร), recommendation engine (ผู้ใช้ที่คล้ายกันชอบอะไร), fraud detection (transaction ไหนแชร์ pattern ที่น่าสงสัยข้ามบัญชี) และ knowledge graph (แนวคิดเกี่ยวข้องกันอย่างไร)

สำหรับ recommendation engine ของ Nimbus: ลูกค้าและอาหารกลายเป็น node ใน Neptune event การสั่งกลายเป็น edge Gremlin traversal สามารถหาอาหารทั้งหมดที่ลูกค้าที่มีประวัติการสั่งคล้ายกันให้คะแนนสูง ในหนึ่ง query เรียงตามความแข็งแกร่งของการเชื่อมต่อ — โดยไม่ต้องมีลูกโซ่ JOIN ที่ซับซ้อนที่จำเป็นในฐานข้อมูล relational หรือหลาย query ไป-กลับที่จำเป็นใน DynamoDB

สัญญาณในข้อสอบสำหรับ Neptune: **"social network," "recommendation engine," "knowledge graph," "fraud detection,"** หรือ **"graph traversal"** ถ้าสถานการณ์อธิบายข้อมูลที่การเชื่อมต่อสำคัญพอ ๆ กับตัวข้อมูลเอง Neptune คือคำตอบ

**Amazon Keyspaces: Cassandra โดยไม่ต้องดำเนินงาน**

การซื้อกิจการ Barato นำ Cassandra cluster เข้ามาในภาพ Cassandra คือฐานข้อมูล NoSQL แบบ wide-column — ออกแบบมาสำหรับ write throughput ที่สูงมากและ scalability แนวนอน ใช้กันทั่วไปสำหรับข้อมูล time-series, user activity log และ IoT telemetry ทีมข้อมูลของ Barato ใช้มันติดตามพฤติกรรมลูกค้า: รายการไหนถูกดู รายการไหนถูกเพิ่มลงตะกร้า รายการไหนถูกละทิ้ง

## จุดแข็งและข้อจำกัด

**ทำไม DynamoDB ถึงทรงพลัง**:

- latency มิลลิวินาทีหลักเดียวที่ขนาดใด ๆ
- Managed เต็มรูปแบบ — ไม่ต้อง patch ไม่ต้องตั้งค่า replication ไม่มี maintenance window
- multi-AZ replication อัตโนมัติ (ความทนทานในตัว)
- การ scale แบบ on-demand หมายถึงไม่ต้องวางแผน capacity เลย
- การ integrate กับ Lambda, API Gateway, Streams ในตัว
- Point-in-time recovery (คล้าย automated backups ของ RDS)
- DynamoDB Streams — จับทุกการเปลี่ยนแปลงเป็น event (มีประโยชน์สำหรับการประมวลผล real-time)

**ที่ที่ DynamoDB ซับซ้อน**:

- การออกแบบ access pattern เป็นสิ่งที่ต่อรองไม่ได้ — ความผิดพลาดมีค่าใช้จ่ายสูงที่จะแก้ย้อน
- query ซับซ้อนต้องการ secondary index (เพิ่มค่าใช้จ่ายและความซับซ้อน)
- Scan แพง — หลีกเลี่ยงใน production
- "ขีดจำกัดขนาด item" คือ 400KB — item ใหญ่ต้องการที่เก็บแบบอื่น
- ราคาอาจทำให้คุณประหลาดใจถ้าคุณไม่เข้าใจค่า read/write unit
- Hot partition คือนักฆ่าเงียบ — ไม่มี error จนกว่า throttling จะเริ่ม

## สรุป

การออกแบบ schema ใหม่ใช้เวลาสองวันและพื้นที่ไวท์บอร์ดมากมาย การเลือกฐานข้อมูล NoSQL ไม่ใช่แค่การตัดสินใจทางเทคนิค — มันเปลี่ยนวิธีที่คุณคิดเกี่ยวกับข้อมูลทั้งหมด แต่ผลลัพธ์คือตารางเมนูที่สามารถโตได้ถึงขนาดใด ๆ โดยไม่ช้าลง สำคัญพอ ๆ กัน: ทีมเรียนรู้ว่าขอบของ DynamoDB อยู่ที่ไหน และฐานข้อมูลเฉพาะทางใดที่ควรหยิบมาใช้เมื่อปัญหาเปลี่ยนรูปทรง

- DynamoDB คือ managed NoSQL database service ของ AWS Items เป็นเอกสารที่ยืดหยุ่น — ไม่มี schema ตายตัว ทุก item ต้องมี **primary key**: partition key อย่างเดียว หรือ partition key + sort key เลือก partition key เพื่อการกระจายอย่างสม่ำเสมอ — hot partition ทำให้เกิด throttling
- ความจุ **On-demand** scale อัตโนมัติ; ความจุ **provisioned** ถูกกว่าสำหรับ traffic ที่คาดเดาได้ Reads แบบ **Eventually consistent** ถูกกว่า; Reads แบบ **strongly consistent** ทันสมัยเสมอแต่ไม่มีให้บน GSI
- **DynamoDB Streams** จับการเปลี่ยนแปลงระดับ item แบบ real-time — ใช้พวกมันขับเคลื่อนการ invalidate cache การอัปเดต search index และ analytics pipeline
- DynamoDB เป็นทางเลือกที่ผิดสำหรับการรายงาน join ที่ซับซ้อน และ query แบบ ad-hoc — ใช้ RDS สำหรับสิ่งเหล่านั้น
- **DocumentDB** (เข้ากันได้กับ MongoDB), **Neptune** (graph database) และ **Keyspaces** (เข้ากันได้กับ Cassandra) คือทางเลือก managed ของ AWS สำหรับ workload ที่ไม่เข้ากับโมเดล key-value ของ DynamoDB

## เคล็ดลับการสอบ

*SAA-C03 Domain: ออกแบบสถาปัตยกรรมที่มีประสิทธิภาพสูง (Domain 3, Task 3.3)*

- รู้กฎ partition key: **cardinality สูง กระจายอย่างสม่ำเสมอ** Hot partitions เป็นกับดักการสอบที่พบบ่อย
- **On-demand vs provisioned**: on-demand สำหรับ traffic ที่คาดเดาไม่ได้; provisioned (พร้อม Auto Scaling) สำหรับ workload ที่คาดเดาได้
- **DynamoDB Streams**: จับการเปลี่ยนแปลงระดับ item แบบ real-time สถานการณ์การสอบทั่วไป: "เรียก Lambda function เมื่อ record เปลี่ยนแปลง"
- **Global Tables**: replication แบบ multi-Region, multi-active สำหรับแอปพลิเคชันที่กระจายทั่วโลกและสถานการณ์ disaster recovery ในข้อสอบ นี่คือสัญญาณที่ชัดเจนเมื่อ workload ต้องการการอ่านและเขียน local ในมากกว่าหนึ่ง Region
- **DynamoDB TTL (Time to Live)**: ตั้ง attribute เวลาหมดอายุบน items แล้ว DynamoDB ลบมันโดยอัตโนมัติหลังหมดอายุ — **โดยไม่มีค่าใช้จ่าย** ไม่กิน write capacity ทริกเกอร์ในข้อสอบ: "ข้อมูล session/item ชั่วคราวต้องถูกลบโดยอัตโนมัติหลัง N ชั่วโมงด้วยต้นทุนต่ำที่สุด" → TTL ไม่ใช่ scheduled Lambda scan items ที่หมดอายุยังไหลไปยัง DynamoDB Streams เพื่อ archival ได้
- **DAX (DynamoDB Accelerator)**: in-memory caching layer สำหรับ DynamoDB ลด read latency จากมิลลิวินาทีเป็นไมโครวินาที ข้อสอบใช้สิ่งนี้เมื่อ RDS read replica ไม่ช่วย (เพราะมันคือ cache เฉพาะของ DynamoDB)
- **Composite primary key**: partition key + sort key อนุญาตให้ query ยืดหยุ่นภายใน partition ตัวอย่าง: ดึงทุกออเดอร์ของลูกค้าระหว่างสองวันที่ — `customerId` คือ partition key, `orderDate` คือ sort key
- **GSI vs LSI**: GSI เพิ่มได้หลังสร้างตาราง; LSI เพิ่มไม่ได้ LSI รองรับ strongly consistent reads; GSI ไม่รองรับ LSI ใช้ capacity ของตารางร่วมกัน; GSI มีของตัวเอง
- รู้ว่าเมื่อไร**ไม่ควร**ใช้ DynamoDB: join ซับซ้อน รายงาน ad-hoc transaction หลาย entity → RDS มักเป็นคำตอบ
- **การเลือกฐานข้อมูลแบบ purpose-built** — ข้อสอบมักนำเสนอสถานการณ์และถามว่าฐานข้อมูลใดเหมาะ ใช้สิ่งนี้เป็นข้อมูลอ้างอิงด่วน: "MongoDB-compatible" → DocumentDB "Graph/social network/recommendation engine/knowledge graph" → Neptune "Cassandra-compatible/wide-column" → Keyspaces "Key-value at any scale/millisecond latency" → DynamoDB "Relational/complex queries/reporting" → RDS หรือ Aurora

*สถานการณ์*: บริษัทเกมระดับโลกเก็บโปรไฟล์ผู้เล่นใน DynamoDB แต่ละโปรไฟล์มีฟิลด์เช่น username, level, achievements และ inventory ผู้เล่นบางคนมี 10 รายการ inventory; คนอื่นมีไม่กี่ร้อย — โปรไฟล์รูปทรงต่างกันแต่แต่ละอันอยู่ต่ำกว่าขีดจำกัดขนาด item 400KB ของ DynamoDB อย่างสบาย บริษัทต้องการ read latency มิลลิวินาทีหลักเดียวสำหรับการ lookup โปรไฟล์ระหว่างการเล่นเกม

แนวทางการออกแบบใดรองรับความต้องการนี้ได้ดีที่สุด?

A) ใช้ DynamoDB โดยมี `playerId` เป็น partition key และเก็บโปรไฟล์ทั้งหมดเป็น item เดียว  
B) ย้ายไป RDS Aurora พร้อม read replica ในแต่ละ region  
C) ใช้ DynamoDB โดยมี `level` เป็น partition key เพื่อจัดกลุ่มผู้เล่นที่มีทักษะคล้ายกัน  
D) ใช้ ElastiCache ด้านหน้า RDS เพื่อให้ได้ latency ต่ำกว่ามิลลิวินาที

**คำใบ้ 1**: access pattern คือ "lookup ผู้เล่นเฉพาะตาม ID" key ใดทำให้สิ่งนั้นมีประสิทธิภาพ?

**คำใบ้ 2**: ทางเลือกหนึ่งสร้าง hot partition ที่แย่มาก attribute ใดมี cardinality ต่ำมาก?

**คำใบ้ 3**: DynamoDB ส่งมอบ latency มิลลิวินาทีหลักเดียวโดยกำเนิดอยู่แล้ว

**คำตอบ**: A

**คำอธิบาย**: การใช้ `playerId` เป็น partition key กระจายข้อมูลอย่างสม่ำเสมอข้าม partition และเปิดให้ lookup ตาม player ID ได้ทันที — ตรงกับ access pattern ที่อธิบายพอดี โมเดลเอกสารที่ยืดหยุ่นของ DynamoDB จัดการขนาด inventory ที่แตกต่างกันได้โดยไม่ต้องเปลี่ยน schema

**ทำไมไม่ใช่ B?** RDS Aurora พร้อม read replica เพิ่มความซับซ้อนและยังไม่ใช่ตัวเลือกแรกโดยธรรมชาติสำหรับการ lookup โปรไฟล์ตาม key แบบนี้ในระดับเกม

**ทำไมไม่ใช่ C?** การใช้ `level` เป็น partition key สร้าง hot partition รุนแรง — traffic ส่วนใหญ่ไปที่ level 1 (ผู้เล่นใหม่) หรือ level สูงสุด (ทหารผ่านศึกที่ active) ทิ้ง partition อื่นว่างเปล่า

**ทำไมไม่ใช่ D?** คำถามอธิบาย DynamoDB ไม่ใช่ RDS การเพิ่ม ElastiCache ด้านหน้า RDS แนะนำสองบริการใหม่ในขณะที่ DynamoDB อย่างเดียวแก้ปัญหาได้
