# บทที่ 33: มันขึ้นอยู่กับ

หายใจลึกๆ ครั้งสุดท้ายก่อนบทนี้

คุณมาถึงท้ายสุดของหนังสือแล้ว นี่คือทั้งบทสรุปและการเริ่มต้น — บทสุดท้าย และวันแรกที่คุณจะตัดสินใจสถาปัตยกรรมด้วยตัวเอง

บทนี้มีงานเดียว: ซื่อสัตย์กับคุณเกี่ยวกับสิ่งที่ไม่มีใครบอกคุณอย่างชัดเจนพอ

**คำถาม**

ท้ายสุดของการสนทนาสถาปัตยกรรมแทบทุกครั้ง มีคนมักถามว่า: "คำตอบที่ถูกต้องคืออะไร?"

และคำตอบที่มีประโยชน์ น่าหงุดหงิด ซื่อสัตย์ และเข้าใจผิดมากที่สุดในวิศวกรรมซอฟต์แวร์ทั้งหมดคือ:

**มันขึ้นอยู่กับ**

ไม่ใช่เพราะคำถามตอบไม่ได้ ไม่ใช่เพราะผู้เชี่ยวชาญกำลังหลบเลี่ยง แต่เพราะคำตอบที่ถูกต้องขึ้นอยู่กับ context ที่ไม่ได้อยู่ในคำถามจริงๆ เชิงโครงสร้าง

บทนี้เกี่ยวกับการเรียนรู้ที่จะพูด "มันขึ้นอยู่กับ" อย่างถูกต้อง — ซึ่งหมายความว่าสามารถ complete ประโยคได้

ลองนึกถึงแพทย์ที่ถูกถามว่า "การผ่าตัดเป็นการรักษาที่ถูกต้องไหม?" แพทย์ที่ไม่ดีพูดว่าใช่หรือไม่ใช่โดยไม่ตรวจผู้ป่วย แพทย์ที่ดีพูดว่า "มันขึ้นอยู่กับ — การวินิจฉัย อายุผู้ป่วย โรคอื่นๆ ของพวกเขา และสิ่งที่เกิดขึ้นถ้าเราต้องรอ" คำตอบไม่ใช่การหลบเลี่ยง มันคือความแม่นยำ "มันขึ้นอยู่กับ" ตามด้วยประโยคที่ complete คือสิ่งที่มีประโยชน์ที่สุดที่แพทย์ — หรือสถาปนิก — สามารถพูดได้

**จุดสิ้นสุดของ Nimbus**

สองปีหลังจากการเริ่มต้น Maya ยืนอยู่ในห้องประชุมในซีแอตเทิล นำเสนอต่อนักลงทุน venture capital

Nimbus เติบโตขึ้น: พาร์ทเนอร์ร้านอาหาร 947 แห่ง คำสั่งซื้อต่อวัน 18,000 รายการ GMV รายเดือน $2.1 ล้าน สามเมืองที่ live อีกสองเมืองกำลังเปิดตัว ทีมวิศวกร 14 คนใน 2 time zones

นักลงทุนมีคำถาม หนึ่งในนั้น — technical partner ของกองทุน — เอนตัวไปข้างหน้า

"คุณใช้ฐานข้อมูลอะไร?" เขาถาม

Maya ไม่ลังเล

"สำหรับคำสั่งซื้อและข้อมูลลูกค้า: Aurora PostgreSQL สำหรับ catalog เมนู: DynamoDB สำหรับการจัดการ session และ caching: ElastiCache Redis สำหรับ analytics: Athena บน S3 Parquet files พร้อม Redshift สำหรับ dashboard queries ที่มีความถี่สูง"

เขาพยักหน้า "ทำไม Aurora สำหรับคำสั่งซื้อไม่ใช่ DynamoDB?"

"เพราะคำสั่งซื้อมีโครงสร้าง relational ที่ซับซ้อน — มันอ้างอิงรายการเมนู บัญชีลูกค้า ที่อยู่ร้านอาหาร วิธีการชำระเงิน เราต้องการ transactional consistency ข้าม entities หลายอัน relational database คือเครื่องมือที่ถูกต้องสำหรับนั้น จุดแข็งของ DynamoDB คือการเข้าถึงแบบ key-value throughput สูงพร้อม schema ที่ยืดหยุ่น ซึ่งเป็น access pattern ของ menu catalog อย่างแน่ชัด"

เขาเขียนบางอย่างลงไป "เรื่อง scaling ล่ะ? คุณบอกว่าคำสั่งซื้อต่อวัน 18,000 รายการ นั่นคือเฉลี่ยประมาณ 12 ต่อนาที คุณออกแบบสำหรับ peak อย่างไร?"

"Friday dinner rush คือประมาณ 25x ค่าเฉลี่ย เราขยาย horizontally ด้วย ECS และ Aurora Serverless v2 ซึ่งรองรับ burst โดยอัตโนมัติ CloudFront รองรับโหลด static content API เป็น stateless ดังนั้น horizontal scaling สะอาด"

"และถ้า Aurora Serverless v2 ไม่สามารถขยายเร็วพอ?"

"เรามีผลลัพธ์การ load test เวลา scale-to สำหรับ Aurora Serverless v2 น้อยกว่า 10 วินาที การเพิ่ม spike วันศุกร์เฉลี่ยของเราใช้เวลา 8 นาทีจาก baseline เราสบายใจกับ headroom"

Technical partner มองนักลงทุนที่เหลือ "เธอรู้จักระบบของตัวเอง"

**สี่คำถามที่อยู่ใต้ "มันขึ้นอยู่กับ"**

ทุก architecture trade-off ลดลงเหลือสี่คำถามพื้นฐาน ไม่ใช่ทุกคำถามมีความสำคัญเท่ากันสำหรับทุกการตัดสินใจ แต่สี่คำถามอยู่ในเกมเสมอ:

**1. Access pattern คืออะไร?**

ข้อมูลถูกเขียนและอ่านอย่างไร? ที่ความถี่อะไร? โดยผู้ใช้พร้อมกันกี่คน? ในลำดับอะไร? โดย keys อะไร?

คำถามนี้กำหนดการเลือกเทคโนโลยีในระดับพื้นฐานที่สุด DynamoDB vs Aurora vs Redshift vs Athena — คำตอบที่ถูกต้องขึ้นอยู่กับ access pattern เกือบทั้งหมด

**2. Scale คืออะไร?**

ไม่ใช่แค่ตอนนี้ — ใน 12 เดือน ใน 5 ปี Scale เปลี่ยนคำตอบที่ถูกต้อง สิ่งที่ทำงานที่ 100 requests ต่อวันพังที่ 100 ล้าน สิ่งที่ overkill ที่ 10 ผู้ใช้จำเป็นที่ 10,000

และ scale ไม่ใช่แค่ traffic มันคือขนาดทีม (สถาปัตยกรรมต้องบำรุงรักษาได้โดยทีมที่คุณมี) มันคือปริมาณข้อมูล มันคือการเข้าถึงทางภูมิศาสตร์

**3. ผลลัพธ์ของความล้มเหลวคืออะไร?**

ถ้าสิ่งนี้พัง จะเกิดอะไรขึ้น? ผู้ใช้เห็นหน้าที่ช้าไหม? คำสั่งซื้อล้มเหลวไหม? เงินเคลื่อนไหวผิดพลาดไหม? Medical record ของใครบางคนไม่สามารถเข้าถึงได้ไหม?

ผลลัพธ์กำหนดว่าคุณลงทุนเท่าไหร่ใน reliability หน้าเมนูที่ช้าสมเหตุสมผลกับ eventual consistency การชำระเงินที่ล้มเหลวสมเหตุสมผลกับ synchronous writes และการยืนยันอย่างชัดเจน

**4. Cost constraint คืออะไร?**

ไม่ใช่แค่เงิน — แต่ยังรวมถึง operational complexity (ซึ่งเป็นรูปแบบต้นทุนในตัวเอง) โซลูชันที่ต้องการบริการเพิ่มเติมสามอันอาจ technically ดีกว่าโซลูชันที่เรียบง่ายกว่าแต่แพงเกินไปที่จะดูแลด้วยทีมสี่คน

**"มันขึ้นอยู่กับ": วิธี Complete ประโยค**

วิธีที่ถูกต้องในการพูด "มันขึ้นอยู่กับ" คือ complete มันทันที:

*"เราควรใช้ DynamoDB หรือ Aurora?"*

"มันขึ้นอยู่กับ access pattern ถ้าคุณต้องการ key-based lookups throughput สูงพร้อม schema ยืดหยุ่น DynamoDB ถ้าคุณต้องการ transactional consistency ข้าม entities ที่เกี่ยวข้องกันพร้อม complex queries Aurora"

*"เราควรใช้ Lambda หรือ EC2?"*

"มันขึ้นอยู่กับ workload characteristics Lambda สำหรับ event-driven, short-duration, workloads ที่ผันผวนที่ zero idle cost มีความสำคัญ EC2 หรือ ECS สำหรับ processes ที่ persistent, stateful หรือ long-running ที่ predictable performance สำคัญกว่า idle cost"

*"เราควรใช้ Multi-AZ หรือ Multi-Region?"*

"มันขึ้นอยู่กับ RTO/RPO requirements และ threat model ของคุณ Multi-AZ ป้องกัน AZ failures (failure mode ที่พบบ่อยที่สุดของ AWS) และให้ RPO ประมาณ 0 และ RTO ประมาณ 60 วินาทีสำหรับ RDS Multi-Region ป้องกัน regional failures (หายาก) และให้บริการผู้ใช้ที่กระจายทั่วโลกพร้อม latency ต่ำกว่า ถ้าคุณต้องการ failover น้อยกว่าหนึ่งนาทีจากภัยพิบัติ regional, Multi-Region ถ้า AZ resilience เพียงพอ Multi-AZ ง่ายกว่าและถูกกว่ามาก"

"มันขึ้นอยู่กับ" ไม่ใช่จุดสิ้นสุดของคำตอบ มันคือจุดเริ่มต้นของคำตอบจริง

**Patterns ที่ไม่เปลี่ยนแปลง**

ขณะที่การเลือกเทคโนโลยีเฉพาะพัฒนา — บริการใหม่เปิดตัว ราคาเปลี่ยน ทางเลือกที่ดีกว่าปรากฏขึ้น — patterns พื้นฐานบางอย่างยังคงเสถียรมาหลายทศวรรษ:

**Separation of concerns**: Components ที่ทำสิ่งต่างกันควรเป็นอิสระ การเปลี่ยนแปลงในอันหนึ่งไม่ควรต้องการการเปลี่ยนแปลงในอีกอัน นี่คือสาเหตุที่คุณ decouple ด้วย SQS ไม่ใช่การเรียกโดยตรง ทำไมคุณใช้ S3 สำหรับ objects ไม่ใช่ databases ทำไม web tier และ database tier แยกกัน

**Defense in depth**: ไม่มี security control ตัวเดียวที่เพียงพอ คุณมี IAM, security groups, NACLs, WAF, GuardDuty, Secrets Manager, KMS ถ้า layer หนึ่งล้มเหลว layer ถัดไปจะจับ

**จ่ายสำหรับสิ่งที่คุณใช้ เมื่อคุณใช้**: หลักการเศรษฐกิจพื้นฐานของ cloud Lambda ขยายเป็นศูนย์ Spot instances ใช้ spare capacity S3 lifecycle policies ย้ายข้อมูลเย็นไปยัง storage ที่ถูกกว่า DynamoDB on-demand คิดค่าต่อ request Patterns ต่างกัน หลักการเดียวกัน

**Optimize สำหรับความล้มเหลวที่น่าจะเป็นที่สุด**: Multi-AZ ก่อน (AZ failures เกิดขึ้น) Cross-region DR ที่สอง (regional failures หายากกว่า) ความซ้ำซ้อน within-AZ (instances หลายตัว) ก่อน cross-region complexity สร้างสำหรับความล้มเหลวที่สมจริง ไม่ใช่ที่หายนะแต่ไม่น่าจะ

**วัดก่อน optimize**: แนวทางของ Tom — ดึง CloudWatch metrics เข้าใจรูปแบบจริง จากนั้นตัดสินใจ — มีค่ามากกว่าการ optimize ก่อนกำหนดตาม assumptions

**สิ่งที่หนังสือเล่มนี้สอนไม่ได้**

มาพูดตรงๆ เกี่ยวกับขีดจำกัด

หนังสือเล่มนี้สอนคุณ:

- สิ่งที่บริการ AWS หลักแต่ละอันทำ
- การเปรียบเทียบที่ทำให้พวกมันเข้าใจง่าย
- การแลกเปลี่ยนระหว่างทางเลือก
- ความรู้สอบที่คุณต้องการสำหรับ SAA-C03
- Framework สำหรับคิดเกี่ยวกับการตัดสินใจสถาปัตยกรรม

หนังสือเล่มนี้ไม่สามารถสอนคุณ:

- **Production instinct**: ความรู้สึกในลำไส้ที่พูดว่า "สิ่งนี้จะแปลกภายใต้โหลด" ก่อนที่คุณจะเห็นมันเกิดขึ้น นี่มาจากการดำเนินงานระบบจริง
- **Technical judgment ภายใต้แรงกดดัน**: การตัดสินใจว่าจะทำอะไรตอนตี 3 เมื่อระบบล่มและคุณมีข้อมูลไม่ครบ นี่มาจากเหตุการณ์ต่างๆ
- **Stakeholder intuition**: การรู้ว่าเมื่อไหร่ควร pushback กับ business requirement เพราะ technical cost สูงเกินไป นี่มาจากประสบการณ์กับทั้งฝั่ง technical และ business
- **คำถามที่ถูกต้องสำหรับ context เฉพาะ**: Carlos สามารถถามคำถามที่ถูกต้องเพราะเขาเห็นปัญหาที่คล้ายกันหลายสิบครั้ง ความรู้นี้ได้มา ไม่ใช่อ่านได้

คุณยังไม่เสร็จสิ้นการเรียนรู้ คุณเพิ่งเริ่มต้น

**การสอบไม่ใช่จุดหมาย**

คุณหยิบหนังสือเล่มนี้เพื่อเตรียมตัวสำหรับ AWS Solutions Architect Associate exam นั่นถูกต้อง การรับรอง SAA-C03 มีจริง มีคุณค่า และจะเปิดประตู

แต่การสอบทดสอบความรู้และ pattern recognition มันไม่ทดสอบการตัดสิน มันไม่ทดสอบประสบการณ์การดำเนินงาน มันไม่ทดสอบว่าคุณทำอะไรเมื่อสถาปัตยกรรมที่คุณสร้างหยุดทำงานตอน 11 โมงคืนวันศุกร์

การรับรองคือ credential เริ่มต้น เมื่อคุณผ่านสอบ คุณจะรู้ว่าบริการ AWS ทำงานอย่างไรและรวมกันอย่างไร คุณจะมี framework สำหรับคิดเกี่ยวกับสถาปัตยกรรม คุณยังไม่ได้ทำมัน

ขั้นตอนถัดไปหลังสอบ: สร้างบางอย่างจริงๆ Deploy มัน ดำเนินงานมัน ดูมันล้มเหลว แก้ไขมัน หมดเงินในบริการหนึ่งและย้ายต้นทุนไปที่อื่น ถูก page กลางดึกและตัดสินใจด้วยข้อมูลไม่เพียงพอ

นั่นคือวิธีที่ความรู้ในหนังสือเล่มนี้กลายเป็นการตัดสิน

## สรุป

- **"มันขึ้นอยู่กับ" คือจุดเริ่มต้นของคำตอบ** ไม่ใช่จุดสิ้นสุด Complete ประโยคด้วยเงื่อนไขที่มันขึ้นอยู่กับเสมอ
- สี่คำถามที่อยู่ใต้ทุก architecture trade-off: access pattern, scale, ผลลัพธ์ของความล้มเหลว, cost constraint
- Patterns ที่ยั่งยืน: separation of concerns, defense in depth, จ่ายสำหรับสิ่งที่คุณใช้, optimize สำหรับความล้มเหลวที่น่าจะเป็น, วัดก่อน optimize
- **Cloud ขยายการตัดสินใจ** — ทั้งที่ดีและไม่ดี การตัดสินใจที่ไม่ดี on-premises มีค่าใช้จ่ายหนึ่งสัปดาห์ การตัดสินใจที่ไม่ดีใน cloud สะสมรายเดือน ในระดับขนาดใหญ่
- การรับรอง SAA-C03 ทดสอบความรู้และ pattern recognition ประสบการณ์ production เปลี่ยนความรู้นั้นเป็นการตัดสิน

## เคล็ดลับสอบ

*SAA-C03 Domain: Cross-domain — all domains*

บทนี้ปิดเนื้อหาสอบของหนังสือเล่มนี้ ก่อนที่คุณจะนั่งสอบ:

**ทบทวนบริการที่คุณไม่มั่นใจที่สุด**:

- สำหรับคนส่วนใหญ่: Kinesis vs SQS (ความแตกต่างระหว่าง stream กับ queue)
- VPC networking (route tables, subnets, NAT Gateway, Internet Gateway)
- IAM policy evaluation logic (explicit deny > explicit allow > implicit deny)
- การเลือก storage class (รู้ S3 storage classes ทั้งหกและ trade-offs)
- RDS vs Aurora vs DynamoDB สำหรับกรณีการใช้งานเฉพาะ

**รู้โครงสร้างสถานการณ์ทั่วไปของสอบ**:

SAA-C03 นำเสนอ business requirement ("บริษัทต้องการ availability 99.99%") และขอให้คุณระบุสถาปัตยกรรมที่ตรงตามมัน อ่าน requirement เสมอ ระบุ constraint สำคัญ และตัดตัวเลือกที่ไม่ตรงตามมัน

**ฝึกระบุ distractor**:

คำตอบผิดทุกอันในสอบผิดด้วยเหตุผลเฉพาะ การเรียนรู้ที่จะระบุว่าทำไมแต่ละคำตอบผิดมีคุณค่ามากกว่าการท่องจำคำตอบที่ถูกต้อง

**สอบให้รางวัล pattern recognition**:

- "Decouple" → SQS/SNS
- "Serverless" → Lambda, DynamoDB, Aurora Serverless
- "Global low latency" → CloudFront, Global Accelerator, Global DynamoDB, Aurora Global
- "Compliance/auditing" → CloudTrail, Config, Security Hub, Macie
- "Cost optimization" → Spot Instances, Savings Plans, lifecycle policies, right-sizing

**คุณพร้อมแล้ว** ไม่ใช่เพราะหนังสือเล่มนี้ครอบคลุมทุกอย่าง — ไม่มีสิ่งใดทำได้ แต่เพราะคุณเข้าใจหลักการดีพอที่จะใช้เหตุผลหาคำตอบแม้เมื่อคุณไม่ได้รู้จักสถานการณ์นั้นทันที
