# บทที่ 33: มันขึ้นอยู่กับ

หายใจลึกๆ ครั้งสุดท้ายก่อนบทนี้

เคอร์เซอร์กะพริบอยู่บนสไลด์ว่างของ Maya หัวข้อ: "Architecture at Nimbus" เธอลบมันและพิมพ์: "The Question" จากนั้นเธอมองห้องและตระหนักว่าเธอไม่ต้องการสไลด์เลย

**ย้อนความ: จากการตรวจสอบสู่การนำเสนอ**

การตรวจสอบสถาปัตยกรรมกับ Carlos — หกเดือนและการเปิดตัวร้านอาหารหลายร้อยแห่งผ่านไปแล้วตอนนี้ — ทิ้งทีมไว้กับ ADRs หนึ่งกองและวิธีคิดที่สะอาดขึ้นเกี่ยวกับการตัดสินใจก่อนที่จะส่งมอบ Maya กำลังเตรียมตัวสำหรับการนำเสนอนักลงทุนเมื่อเธอตระหนักว่าทุกอย่างที่ Carlos ถาม — และทุกอย่างที่เธอตอบอย่างมั่นใจ — ลดลงเหลือตรรกะพื้นฐานเดียวกัน นักลงทุนจะถามว่าทำไม เธอเรียนรู้ ตลอดสองปีของการสร้าง Nimbus ว่าคำตอบไม่เคยเป็นชื่อบริการ คำตอบเสมอคือชุดเงื่อนไขที่ทำให้บริการหนึ่งถูกต้องและอีกอันผิด เธอกำลังจะเดินเข้าไปในห้องของคนที่จะขอให้เธอปกป้องทุกตัวเลือกสถาปัตยกรรม เธอพร้อมแล้ว

**คำถาม**

ท้ายสุดของการสนทนาสถาปัตยกรรมแทบทุกครั้ง มีคนมักถามว่า: "คำตอบที่ถูกต้องคืออะไร?"

และคำตอบที่มีประโยชน์ น่าหงุดหงิด ซื่อสัตย์ และเข้าใจผิดมากที่สุดในวิศวกรรมซอฟต์แวร์ทั้งหมดคือ:

**มันขึ้นอยู่กับ**

ไม่ใช่เพราะคำถามตอบไม่ได้ ไม่ใช่เพราะผู้เชี่ยวชาญกำลังหลบเลี่ยง แต่เพราะคำตอบที่ถูกต้องขึ้นอยู่กับ context ที่ไม่ได้อยู่ในคำถามจริงๆ เชิงโครงสร้าง

บทนี้เกี่ยวกับการเรียนรู้ที่จะพูด "มันขึ้นอยู่กับ" อย่างถูกต้อง — ซึ่งหมายความว่าสามารถ complete ประโยคได้

ลองนึกถึงแพทย์ที่ถูกถามว่า "การผ่าตัดเป็นการรักษาที่ถูกต้องไหม?" แพทย์ที่ไม่ดีพูดว่าใช่หรือไม่ใช่โดยไม่ตรวจผู้ป่วย แพทย์ที่ดีพูดว่า "มันขึ้นอยู่กับ — การวินิจฉัย อายุผู้ป่วย โรคอื่นๆ ของพวกเขา และสิ่งที่เกิดขึ้นถ้าเราต้องรอ" คำตอบไม่ใช่การหลบเลี่ยง มันคือความแม่นยำ "มันขึ้นอยู่กับ" ตามด้วยประโยคที่ complete คือสิ่งที่มีประโยชน์ที่สุดที่แพทย์ — หรือสถาปนิก — สามารถพูดได้

**จุดสิ้นสุดของ Nimbus**

สองปีครึ่งหลังจากการเริ่มต้น Maya ยืนอยู่ในห้องประชุมในซีแอตเทิล นำเสนอต่อนักลงทุน venture capital

Nimbus เติบโตขึ้น: พาร์ทเนอร์ร้านอาหาร 947 แห่ง คำสั่งซื้อต่อวัน 18,000 รายการ GMV รายเดือน $18 ล้าน สามเมืองที่ live อีกสองเมืองกำลังเปิดตัว ทีมวิศวกร 14 คนใน 2 time zones

นักลงทุนมีคำถาม หนึ่งในนั้น — technical partner ของกองทุน — เอนตัวไปข้างหน้า

"คุณใช้ฐานข้อมูลอะไร?" เขาถาม

Maya ไม่ลังเล

"สำหรับคำสั่งซื้อและข้อมูลลูกค้า: Aurora PostgreSQL สำหรับ catalog เมนู: DynamoDB สำหรับการจัดการ session และ caching: ElastiCache Redis สำหรับ analytics: Athena บน S3 Parquet files พร้อม Redshift สำหรับ dashboard queries ที่มีความถี่สูง"

เขาพยักหน้า "ทำไม Aurora สำหรับคำสั่งซื้อไม่ใช่ DynamoDB?"

"เพราะคำสั่งซื้อมีโครงสร้าง relational ที่ซับซ้อน — มันอ้างอิงรายการเมนู บัญชีลูกค้า ที่อยู่ร้านอาหาร วิธีการชำระเงิน เราต้องการ transactional consistency ข้าม entities หลายอัน relational database คือเครื่องมือที่ถูกต้องสำหรับนั้น จุดแข็งของ DynamoDB คือการเข้าถึงแบบ key-value throughput สูงพร้อม schema ที่ยืดหยุ่น ซึ่งเป็น access pattern ของ menu catalog อย่างแน่ชัด"

เขาเขียนบางอย่างลงไป "เรื่อง scaling ล่ะ? คุณบอกว่าคำสั่งซื้อต่อวัน 18,000 รายการ นั่นคือเฉลี่ยประมาณ 12 ต่อนาที คุณออกแบบสำหรับ peak อย่างไร?"

"Friday dinner rush คือประมาณ 25x ค่าเฉลี่ย เราขยาย horizontally ด้วย ECS และ Aurora Serverless v2 ซึ่งรองรับ burst โดยอัตโนมัติ CloudFront รองรับโหลด static content API เป็น stateless ดังนั้น horizontal scaling สะอาด"

"และถ้า Aurora Serverless v2 ไม่สามารถขยายเร็วพอ?"

"เรามีผลลัพธ์การ load test เวลา scale-to สำหรับ Aurora Serverless v2 น้อยกว่า 10 วินาที การเพิ่ม spike วันศุกร์เฉลี่ยของเราใช้เวลา 8 นาทีจาก baseline เราสบายใจกับ headroom"

Technical partner มองนักลงทุนที่เหลือ "เธอรู้จักระบบของตัวเอง"

เขามีคำถามเพิ่ม

"คุณจัดการความปลอดภัยของการ deploy อย่างไร? ที่ 947 ร้านอาหาร การ deploy ที่ไม่ดีหมายความว่า 947 ร้านอาหารรับคำสั่งซื้อไม่ได้"

Maya เคยถูกถามเรื่องนี้มาแล้ว ภายในทีม "Feature flags สำหรับการเปลี่ยนพฤติกรรมทั้งหมด เรา deploy โค้ดต่อเนื่อง แต่พฤติกรรมใหม่ถูก gate หลัง flags ที่เราเปิดทีละน้อย การ deploy ที่เปลี่ยน order confirmation flow ถูก rollout ไปยัง 1% ของร้านอาหารเป็นเวลา 24 ชั่วโมง จากนั้น 10% จากนั้น 50% จากนั้น 100% — พร้อม automated rollback ถ้า error rates เกิน threshold ที่ stage ใดก็ตาม"

"การ rollout เต็มรูปแบบใช้เวลานานแค่ไหน?"

"สามวันสำหรับการเปลี่ยนแปลงที่เสี่ยงสูง หนึ่งวันสำหรับเสี่ยงต่ำ Emergency rollbacks เสร็จในน้อยกว่าสี่นาที"

"p99 Stripe latency ของคุณคือเท่าไหร่?"

Tom ตอบก่อนที่ Maya จะตอบได้ "214 มิลลิวินาที"

"นั่นสูง" นักลงทุนพูด

"SLA ของเราต่อร้านอาหารคือ การสั่งคำสั่งซื้อไปจนถึงการยืนยันในน้อยกว่า 5 วินาที" Tom พูด "214ms สำหรับ Stripe call คือ 4.3% ของ budget นั้น เวลาที่เหลือคือ Aurora write, SQS message delivery, restaurant tablet push notification เรามี headroom"

"จะเป็นอย่างไรถ้า Stripe มีเหตุการณ์?"

"เราใช้ asynchronous payment capture ของ Stripe คำสั่งซื้อถูกยอมรับและร้านอาหารถูกแจ้งทันที Payment capture เกิดขึ้นแบบ asynchronous ถ้า Stripe ช้า คำสั่งซื้อยังผ่าน — capture retry ถ้า Stripe ล่มสมบูรณ์ เราคิว capture attempt ด้วย exponential backoff และแจ้ง on-call ของเรา เราไม่เคยกักคำสั่งซื้อไว้สำหรับ Stripe ใน 14 เดือน"

นักลงทุนเขียนบางอย่าง "คุณมี single points of failure ใดไหม?"

Priya ตอบ "Aurora ใน region เดียวคือ single-region dependency เรามี Multi-AZ สำหรับความล้มเหลวระดับ AZ และ Aurora Global Database reader ที่กำลังทำงานอยู่แล้วใน us-east-1 ความล้มเหลว regional เต็มรูปแบบจะหมายถึงการ failover ไปยัง reader นั้น — และ automated regional failover รอบมันคือสิ่งที่เรากำลังสร้างในไตรมาสนี้ จนกว่าจะถึงตอนนั้น ใช่ — ความล้มเหลว regional ของ us-west-2 จะทำให้ Nimbus ล่ม"

"ทำไมคุณยังไม่สร้าง multi-region failover?"

"เพราะจนกระทั่งหกเดือนก่อน ต้นทุนวิศวกรรมในการสร้างมันอย่างถูกต้องเกินความเสี่ยงทางธุรกิจของ outage" Priya พูด "เราไม่เคยมีความล้มเหลว regional ของ AWS ที่นานกว่า 30 นาทีใน operating region ของเรา ที่ 287 ร้านอาหาร — ประมาณ 4,200 คำสั่งซื้อต่อวันที่มูลค่าคำสั่งซื้อเฉลี่ย $34 — outage regional 2 ชั่วโมงมีค่าใช้จ่ายเราประมาณ $12,000 ใน GMV ต้นทุนวิศวกรรมของ warm standby ที่ implement อย่างถูกต้องคือเวลาวิศวกรอาวุโส 3 เดือน ที่รายได้ปัจจุบันของเรา คณิตศาสตร์เอนไปทางการเลื่อนออกไป"

"และตอนนี้?"

"ที่ 947 ร้านอาหารและ 18,000 คำสั่งซื้อต่อวัน outage 2 ชั่วโมงเดียวกันมีค่าใช้จ่ายราว $51,000 ใน GMV และสร้างความเสียหายด้านชื่อเสียงที่มีนัยสำคัญกับพาร์ทเนอร์ร้านอาหารที่พึ่งพาเราสำหรับบริการอาหารเย็นของพวกเขา คณิตศาสตร์เปลี่ยนแล้ว โปรเจกต์ failover เริ่มใน sprint หน้า"

นักลงทุนมองนักลงทุนคนอื่นในห้อง "เธอรู้จัก risk profile ของเธอด้วย"


**สี่คำถามที่อยู่ใต้ "มันขึ้นอยู่กับ"**

เธอถามคำถามเหล่านี้แต่ละเวอร์ชันมาสองปีโดยไม่รู้ว่าเธอกำลังถามคำถามเดียวกันในสี่แบบที่ต่างกัน Session นักลงทุนทำให้มันชัดเจน ทุกตัวเลือกที่เธออธิบายอย่างมั่นใจกลับมาที่สี่แกนเดียวกัน

**1. Access pattern คืออะไร?**

ข้อมูลถูกเขียนและอ่านอย่างไร? ที่ความถี่อะไร? โดยผู้ใช้พร้อมกันกี่คน? ในลำดับอะไร? โดย keys อะไร?

คำถามนี้กำหนดการเลือกเทคโนโลยีในระดับพื้นฐานที่สุด DynamoDB vs Aurora vs Redshift vs Athena — คำตอบที่ถูกต้องขึ้นอยู่กับ access pattern เกือบทั้งหมด

**2. Scale คืออะไร?**

ไม่ใช่แค่ตอนนี้ — ใน 12 เดือน ใน 5 ปี Scale เปลี่ยนคำตอบที่ถูกต้อง สิ่งที่ทำงานที่ 100 requests ต่อวันพังที่ 100 ล้าน สิ่งที่ overkill ที่ 10 ผู้ใช้จำเป็นที่ 10,000

และ scale ไม่ใช่แค่ traffic มันคือขนาดทีม (สถาปัตยกรรมต้องบำรุงรักษาได้โดยทีมที่คุณมี) มันคือปริมาณข้อมูล มันคือการเข้าถึงทางภูมิศาสตร์

**3. ผลลัพธ์ของความล้มเหลวคืออะไร?**

ถ้าสิ่งนี้พัง จะเกิดอะไรขึ้น? ผู้ใช้เห็นหน้าที่ช้าไหม? คำสั่งซื้อล้มเหลวไหม? เงินเคลื่อนไหวผิดพลาดไหม? Medical record ของใครบางคนไม่สามารถเข้าถึงได้ไหม?

ผลลัพธ์กำหนดว่าคุณลงทุนเท่าไหร่ใน reliability หน้าเมนูที่ช้าสมเหตุสมผลกับ eventual consistency การชำระเงินที่ล้มเหลวสมเหตุสมผลกับ synchronous writes และการยืนยันอย่างชัดเจน

**4. Cost constraint คืออะไร?**

ไม่ใช่แค่เงิน — แต่ยังรวมถึง operational complexity (ซึ่งเป็นรูปแบบต้นทุนในตัวเอง) โซลูชันที่ต้องการบริการเพิ่มเติมสามอันอาจ technically ดีกว่าโซลูชันที่เรียบง่ายกว่าแต่แพงเกินไปที่จะดูแลด้วยทีมสี่คน

"เดี๋ยว — แต่ *ทำไม* access pattern ถึงสำคัญมากนัก?" Maya ถาม สองปีก่อน เมื่อ Tom เสนอแยก menu catalog ออกจาก orders database เป็นครั้งแรก "เราแค่ optimize ทีหลังไม่ได้เหรอ?"

คำถามนั้น กลายเป็นว่า เป็นจุดเริ่มต้นของคำตอบ คุณไม่สามารถ optimize relational schema สำหรับ key-value access patterns โดยไม่สร้างมันใหม่ Access pattern ต้องรู้ตอนออกแบบ ไม่ใช่ retrofit ทุกการตัดสินใจสถาปัตยกรรมที่เธอทำตั้งแต่นั้นเริ่มด้วยคำถามเดียวกัน

คุณอาจสงสัยว่า: ถ้า "มันขึ้นอยู่กับ" เป็นคำตอบที่ถูกต้องเสมอ คุณจะตัดสินใจได้อย่างไร? คำตอบคือการ complete ประโยคบังคับให้คุณตั้งชื่อเงื่อนไข และเมื่อคุณตั้งชื่อพวกมันแล้ว คุณรู้ว่าคุณต้องการข้อมูลอะไร "มันขึ้นอยู่กับ access pattern" กลายเป็น "ไปหาว่า access pattern จริงๆ คืออะไร" สี่คำถามไม่ใช่วิธีหลีกเลี่ยงการตัดสินใจ — มันคือวิธีทำการตัดสินใจด้วยข้อมูลที่ถูกต้อง

**"มันขึ้นอยู่กับ": วิธี Complete ประโยค**

วิธีที่ถูกต้องในการพูด "มันขึ้นอยู่กับ" คือ complete มันทันที:

*"เราควรใช้ DynamoDB หรือ Aurora?"*

"มันขึ้นอยู่กับ access pattern ถ้าคุณต้องการ key-based lookups throughput สูงพร้อม schema ยืดหยุ่น DynamoDB ถ้าคุณต้องการ transactional consistency ข้าม entities ที่เกี่ยวข้องกันพร้อม complex queries Aurora"

*"เราควรใช้ Lambda หรือ EC2?"*

"มันขึ้นอยู่กับ workload characteristics Lambda สำหรับ event-driven, short-duration, workloads ที่ผันผวนที่ zero idle cost มีความสำคัญ EC2 หรือ ECS สำหรับ processes ที่ persistent, stateful หรือ long-running ที่ predictable performance สำคัญกว่า idle cost"

*"เราควรใช้ Multi-AZ หรือ Multi-Region?"*

"มันขึ้นอยู่กับ RTO/RPO requirements และ threat model ของคุณ Multi-AZ ป้องกัน AZ failures (failure mode ที่พบบ่อยที่สุดของ AWS) และให้ RPO ประมาณ 0 และ RTO ประมาณ 60 วินาทีสำหรับ RDS Multi-Region ป้องกัน regional failures (หายาก) และให้บริการผู้ใช้ที่กระจายทั่วโลก ถ้าคุณต้องการ failover น้อยกว่าหนึ่งนาทีจากภัยพิบัติ regional, Multi-Region ถ้า AZ resilience เพียงพอ Multi-AZ ง่ายกว่าและถูกกว่ามาก"

**ความผันแปร: เมื่อ "มันขึ้นอยู่กับ" ทำให้คุณมีปัญหา**

ถ้า access pattern เอนไปทาง key-value lookups และคุณเลือก DynamoDB คุณจะทำได้ดีกว่า Aurora ที่ scale — แต่ถ้าคุณเพิ่มฟีเจอร์ที่ต้องการ JOIN queries ข้ามสาม entities คุณสร้างพื้นฐานที่ผิดและจะต้องย้ายภายใต้แรงกดดัน คำตอบ "มันขึ้นอยู่กับ" ดีเท่ากับความเข้าใจของคุณเกี่ยวกับเงื่อนไขที่คุณกำลังขึ้นอยู่กับ

ถ้าคุณ optimize สำหรับ scale ปัจจุบันและ access pattern ปัจจุบัน คุณจะตัดสินใจถูกต้องสำหรับวันนี้ — แต่ถ้า traffic เติบโต 50x ในหนึ่งปีโดยที่สถาปัตยกรรมของคุณไม่ปรับตัว การตัดสินใจที่ถูกต้องสำหรับวันแรกกลายเป็น bottleneck สำหรับวันที่ 365 สี่คำถามต้องถามไม่ใช่แค่ตอนออกแบบแต่กลับมาพิจารณาเมื่อระบบเติบโต

**Patterns ที่ไม่เปลี่ยนแปลง**

ขณะที่การเลือกเทคโนโลยีเฉพาะพัฒนา — บริการใหม่เปิดตัว ราคาเปลี่ยน ทางเลือกที่ดีกว่าปรากฏขึ้น — patterns พื้นฐานบางอย่างยังคงเสถียรมาหลายทศวรรษ:

**Separation of concerns**: Components ที่ทำสิ่งต่างกันควรเป็นอิสระ การเปลี่ยนแปลงในอันหนึ่งไม่ควรต้องการการเปลี่ยนแปลงในอีกอัน นี่คือสาเหตุที่คุณ decouple ด้วย SQS ไม่ใช่การเรียกโดยตรง ทำไมคุณใช้ S3 สำหรับ objects ไม่ใช่ databases ทำไม web tier และ database tier แยกกัน

**Defense in depth**: ไม่มี security control ตัวเดียวที่เพียงพอ คุณมี IAM, security groups, NACLs, WAF, GuardDuty, Secrets Manager, KMS ถ้า layer หนึ่งล้มเหลว layer ถัดไปจะจับ

**จ่ายสำหรับสิ่งที่คุณใช้ เมื่อคุณใช้**: หลักการเศรษฐกิจพื้นฐานของ cloud Lambda ขยายเป็นศูนย์ Spot instances ใช้ spare capacity S3 lifecycle policies ย้ายข้อมูลเย็นไปยัง storage ที่ถูกกว่า DynamoDB on-demand คิดค่าต่อ request Tom ถาม "มันมีค่าใช้จ่ายต่อเดือนเท่าไหร่?" หนึ่งหมื่นครั้งตลอดสองปี คำถามนั้น — ถามอย่างสม่ำเสมอ ตอบอย่างเข้มงวด — กลายเป็นการประหยัดเกือบ $36,000 ต่อปี Patterns ต่างกัน หลักการเดียวกัน

**Optimize สำหรับความล้มเหลวที่น่าจะเป็นที่สุด**: Multi-AZ ก่อน (AZ failures เกิดขึ้น) Cross-region DR ที่สอง (regional failures หายากกว่า) ความซ้ำซ้อน within-AZ (instances หลายตัว) ก่อน cross-region complexity สร้างสำหรับความล้มเหลวที่สมจริง ไม่ใช่ที่หายนะแต่ไม่น่าจะ

**วัดก่อน optimize**: แนวทางของ Tom — ดึง CloudWatch metrics เข้าใจรูปแบบจริง จากนั้นตัดสินใจ — มีค่ามากกว่าการ optimize ก่อนกำหนดตาม assumptions สัญชาตญาณของ Leo เกี่ยวกับ nightly batch jobs — "มันจะโอเค" — คือสิ่งสำคัญที่สุดที่จะฝึกตัวเองให้เลิก มันมักจะโอเค จนกว่าครั้งเดียวที่มันไม่โอเค และคุณไม่ได้วัดอะไร


**ต้นทุนที่ทบของ defaults ที่ผิด**

Tom มีอีก pattern หนึ่งที่จะเพิ่มในรายการ อันที่เขาระบุได้หลังจากสามเดือนของ cost review เท่านั้น: ต้นทุนของการไม่เปลี่ยน default

บริการ AWS ถูกออกแบบให้ปลอดภัยและใช้งานได้ทันทีออกจากกล่อง Defaults ไม่ได้ถูกออกแบบให้ optimal สำหรับทุก workload gp2 เป็น EBS volume type เริ่มต้นจนกว่า gp3 จะเปิดตัวในเดือนธันวาคม 2020 หลังจากนั้น gp3 กลายเป็นค่าเริ่มต้นสำหรับ volumes ใหม่ — แต่ gp2 volumes ที่มีอยู่ไม่เคยถูกแปลง เพราะ AWS ไม่แก้ไขทรัพยากรลูกค้าที่มีอยู่โดยไม่มีการกระทำที่ชัดเจน

ผลด้านต้นทุน: ทุกทีมที่สร้าง EBS volumes ก่อน gp3 และไม่เคยรัน migration audit จ่ายมากขึ้น 25% ต่อ GB เป็นเวลาหลายปี ไม่ใช่เพราะพวกเขาตัดสินใจผิด แต่เพราะพวกเขาไม่ได้ตัดสินใจ Default คงอยู่ และต้นทุนทบขึ้นเงียบๆ

นี่คือสาเหตุที่คำถาม "เดี๋ยว แต่ทำไมเราถึงทำแบบนั้น?" กลายเป็นสิ่งที่มีค่าที่สุดที่ทีมถาม มันไม่ใช่เสมอเกี่ยวกับการท้าทายการตัดสินใจที่ทำ บางครั้งมันเกี่ยวกับการตั้งคำถามต่อ non-decision: default ที่ถูกยอมรับโดยไม่มีการตรวจสอบ

Pattern ทั่วไป: กลับมาพิจารณา defaults เมื่อ AWS เปิดตัวตัวเลือกใหม่ gp2 ไป gp3 On-Demand DynamoDB ไป provisioned พร้อม Auto Scaling เมื่อ traffic เสถียร Standard S3 ไป Intelligent-Tiering เมื่อ access patterns ไม่แน่นอน การกลับมาพิจารณาไม่ต้องแพง — บ่ายวันหนึ่งของการวิเคราะห์ต่อหมวดหมู่ รายไตรมาส แต่มันข้ามไม่ได้ Defaults ทบขึ้น

**เหตุการณ์ analytics pipeline**

แปดเดือนก่อนหน้า analytics pipeline ถูก couple กับ main order processing service Order events ถูกเขียนไปยัง SQS queue เดียวกันที่ analytics pipeline consume การ coupling ดูสมเหตุสมผล: analytics ต้องการ order data, order processing สร้าง order data

ในเย็นวันพุธ บั๊กใน analytics aggregation Lambda ทำให้มันหยุด consume จาก queue ความลึกของ queue เติบโต เพราะ order processing service แชร์ SQS queue เดียวกันสำหรับ confirmation messages ของมัน ทั้ง analytics pipeline และ order confirmation path กำลัง backing up พร้อมกัน พาร์ทเนอร์ร้านอาหารเริ่มเห็นความล่าช้าในการยืนยัน SQS queue กำลังเข้าใกล้ message retention limit

"ผม deploy การแก้ไขแล้ว" Leo พูด ตอน 5 ทุ่มคืนนั้น — แล้วก็หยุด การแก้บั๊ก analytics จะต้องการการ redeploy Lambda ที่จะเคลียร์ queue แต่เขาไม่ได้ตรวจสอบว่า order confirmation messages ใน queue ยังอยู่ใน visibility timeout หรือไม่ ถ้า timeout หมดอายุ Lambda จะ reprocess พวกมัน และพาร์ทเนอร์ร้านอาหารจะได้รับ order confirmations ซ้ำ

เหตุการณ์ใช้เวลาสามชั่วโมงและต้องการ rollbacks สองครั้ง

บทเรียนสถาปัตยกรรมเรียบง่าย: analytics และ operational processing ไม่ควรแชร์ queue เดียวกัน พวกมันมี performance characteristics ที่ต่างกัน failure modes ที่ต่างกัน และผลลัพธ์ที่ต่างกันเมื่อพวกมันล้มเหลว การ couple พวกมันหมายความว่าความล้มเหลวใน path ที่มีลำดับความสำคัญต่ำกว่าสามารถทำให้ path ที่มีลำดับความสำคัญสูงกว่าเสื่อม

หลังจากเหตุการณ์ Nimbus แยก pipelines อย่างสมบูรณ์ Order events ไปยัง operational queue เฉพาะ EventBridge rule แยกต่างหากทำซ้ำ events ไปยัง analytics-only queue สอง pipelines ไม่มี infrastructure ที่แชร์ยกเว้น event source ครั้งถัดไปที่ analytics Lambda มีบั๊ก — และมันมี สองเดือนต่อมา — มันล้มเหลวเงียบๆ analytics queue backed up รายงานเช้าสาย และ order confirmation path ไม่ได้รับผลกระทบเลย

"Separation of concerns" Priya พูด หลังจากบั๊ก analytics Lambda ครั้งที่สอง "หลักการเดียวกันที่ระดับ infrastructure เหมือนที่ระดับโค้ด สองสิ่งที่ล้มเหลวต่างกันไม่ควรแชร์ failure domain เดียวกัน"

**Premature abstraction**

สามเดือนก่อน Series A Leo เสนอสร้าง generic restaurant configuration service Nimbus มี configuration เฉพาะร้านอาหารสามประเภทในเวลานั้น: menu settings, delivery zone parameters และ notification preferences Generic configuration service, Leo โต้แย้ง จะให้พวกเขาเพิ่ม configuration types ใหม่โดยไม่ต้องสร้าง storage และ retrieval logic ใหม่แต่ละครั้ง

ทีมสร้างมัน สองสัปดาห์เพื่อออกแบบ data model หนึ่งสัปดาห์เพื่อ implement service อีกหนึ่งสัปดาห์เพื่อย้าย configuration types ที่มีอยู่สามอันเข้ามา รวมสี่สัปดาห์

เมื่อพวกเขาสร้าง generic configuration service เสร็จ พวกเขามี... configuration types สามอัน อันเดียวกันสามอันที่พวกเขาเคยมี Generic service ไม่ได้เพิ่มความสามารถใหม่; มันแค่ทำให้ความสามารถที่มีอยู่เข้าใจยากขึ้น Key-value schema ที่ทำให้ service "generic" ก็ทำให้เป็นไปไม่ได้ที่จะเพิ่ม validation หรือ type constraints โดยไม่สร้าง schema registry ทับมัน

การประชุมนักลงทุนไปได้ดี ไม่ใช่เพราะ Maya ท่องจำโครงสร้างราคาของทุกบริการ แต่เพราะเธอสามารถตอบ *ทำไม* สำหรับทุกตัวเลือกที่ Nimbus ทำ คำตอบ "มันขึ้นอยู่กับ" ที่เธอให้นั้นแม่นยำ มีเงื่อนไข และตั้งอยู่บนสี่คำถามเดียวกันที่เธอถามมา ในรูปแบบต่างๆ เป็นเวลาสองปี

- **Cloud ขยายการตัดสินใจ** — ทั้งที่ดีและไม่ดี การตัดสินใจที่ไม่ดี on-premises มีค่าใช้จ่ายหนึ่งสัปดาห์ การตัดสินใจที่ไม่ดีใน cloud สะสมรายเดือน ในระดับขนาดใหญ่
- การรับรอง SAA-C03 ทดสอบความรู้และ pattern recognition ประสบการณ์ production เปลี่ยนความรู้นั้นเป็นการตัดสิน

## เคล็ดลับการสอบ

*SAA-C03 Domain: Cross-domain — all domains*

บทนี้ปิดเนื้อหาสอบของหนังสือเล่มนี้ ก่อนที่คุณจะนั่งสอบ:

**ทบทวนบริการที่คุณไม่มั่นใจที่สุด**:

- สำหรับคนส่วนใหญ่: Kinesis vs SQS (ความแตกต่างระหว่าง stream กับ queue)
- VPC networking (route tables, subnets, NAT Gateway, Internet Gateway)
- IAM policy evaluation logic (explicit deny > explicit allow > implicit deny)
- การเลือก storage class (รู้ S3 storage classes ทั้งแปดและ trade-offs)
- RDS vs Aurora vs DynamoDB สำหรับกรณีการใช้งานเฉพาะ

**รู้โครงสร้างสถานการณ์ทั่วไปของสอบ**:

SAA-C03 นำเสนอ business requirement ("บริษัทต้องการ availability 99.99%") และขอให้คุณระบุสถาปัตยกรรมที่ตรงตามมัน อ่าน requirement เสมอ ระบุ constraint สำคัญ และตัดตัวเลือกที่ไม่ตรงตามมัน

**ฝึกระบุ distractor**:

คำตอบผิดทุกอันในสอบผิดด้วยเหตุผลเฉพาะ การเรียนรู้ที่จะระบุว่า *ทำไม* แต่ละคำตอบผิดมีคุณค่ามากกว่าการท่องจำคำตอบที่ถูกต้อง

**สอบให้รางวัล pattern recognition**:

- "Decouple" → SQS/SNS
- "Serverless" → Lambda, DynamoDB, Aurora Serverless
- "Global low latency" → CloudFront, Global Accelerator, Global DynamoDB, Aurora Global
- "Compliance/auditing" → CloudTrail, Config, Security Hub, Macie
- "Cost optimization" → Spot Instances, Savings Plans, lifecycle policies, right-sizing

**คุณพร้อมแล้ว** ไม่ใช่เพราะหนังสือเล่มนี้ครอบคลุมทุกอย่าง — ไม่มีสิ่งใดทำได้ แต่เพราะคุณเข้าใจหลักการดีพอที่จะใช้เหตุผลหาคำตอบแม้เมื่อคุณไม่ได้รู้จักสถานการณ์นั้นทันที
