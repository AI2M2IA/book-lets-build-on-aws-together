# บทที่ 10: เมื่อฐานข้อมูลช้าเกินไป

ตัวชี้วัดเวลาโหลดหน้าเพจเปิดอยู่บนหน้าจอ Leo จ้องมองมันยี่สิบนาทีโดยไม่พูดอะไร

คำขอ DynamoDB สี่สิบเจ็ดรายการต่อการโหลดหน้าเพจ หนึ่งร้อยแปดสิบแปดมิลลิวินาทีแค่เพื่อดึงข้อมูล — ก่อนที่เบราว์เซอร์จะ render แม้แต่ pixel เดียว

เขาคำนวณแล้ว ผู้ใช้พร้อมกันหนึ่งหมื่นคนในเย็นวันศุกร์ แต่ละคนโหลดหน้าเรียกดูประมาณนาทีละครั้ง: สี่แสนเจ็ดหมื่นการอ่าน DynamoDB ต่อนาที ค่าใช้จ่ายเป็นจริง แต่ latency คือปัญหาที่แท้จริง ผู้ใช้ที่เปิดหน้าเรียกดูของ Nimbus รอเกือบสองร้อยมิลลิวินาทีก่อนที่อะไรจะปรากฏ — และนั่นบนการเชื่อมต่อที่เร็ว

*สัปดาห์ก่อน การออกแบบ DynamoDB schema ใหม่ใช้งานได้ ตารางเมนูยืดหยุ่นแล้ว — ร้านอาหารใดก็เพิ่มตัวปรับใด ๆ โครงสร้างคอมโบใด ๆ รูปแบบตามฤดูกาลใด ๆ ได้ ประสิทธิภาพในการ lookup แต่ละครั้งยอดเยี่ยม แต่การ lookup แต่ละครั้งที่ยอดเยี่ยม คูณด้วยสี่สิบเจ็ดต่อหน้า ก็ยังรวมกันเป็นหน้าที่ช้า ปัญหา DynamoDB ถูกแก้แล้ว ปัญหาใหม่เข้ามาแทนที่*

**ความพยายามครั้งแรกที่ผิด**

สัญชาตญาณแรกของ Leo คือ cache ข้อมูลแบบรายผู้ใช้ ผู้ใช้แต่ละคนมี session และ session โหลดโปรไฟล์ของพวกเขา: ที่อยู่ที่บันทึก วิธีการชำระเงิน สรุปประวัติออเดอร์ บางที cache สิ่งนั้นอาจเร่งความเร็วได้

เขาทำมัน รูปแบบ Redis key: `user:{userId}:profile` TTL: สิบนาที

เขารัน load test การโหลดหน้าเพจลดลงหกมิลลิวินาที

"นั่นไม่มากนัก" Tom สังเกต

"ใช่" Leo พูด

"ทำไมล่ะ?"

Leo จ้องมองกราฟชั่วครู่ "เพราะโปรไฟล์ผู้ใช้เป็นแค่คำขอเดียว ยังมีการเรียก DynamoDB สี่สิบหกครั้งต่อหน้า และพวกนั้นคือการเรียกเมนู — หนึ่งต่อร้านอาหารบนหน้าเรียกดู ผม cache ผิดสิ่ง"

นี่คือความผิดพลาดที่พบบ่อยในการ caching: การ optimize สิ่งที่ไม่ใช่ bottleneck โปรไฟล์ผู้ใช้โหลดในสองมิลลิวินาที การ cache สิ่งที่เร็วขนาดนั้นแทบไม่ช่วยอะไร ข้อมูลเมนู — ดึงสี่สิบเจ็ดครั้ง ใช้เวลาสี่มิลลิวินาทีต่อครั้ง — คือปัญหาที่แท้จริง

"คุณต้อง cache แบบรายเมนู ไม่ใช่รายผู้ใช้" Priya พูด "เมนูของ Restaurant 047 เหมือนกันสำหรับผู้ใช้ทุกคนที่เรียกดู นั่นคือข้อมูลที่คุ้มค่าจะ cache — มันเหมือนกันข้ามคำขอนับพัน"

cache แบบรายผู้ใช้มีค่าเมื่อผู้ใช้มี state ส่วนตัวที่มีราคาแพง cache แบบราย entity (เมนู แคตตาล็อกสินค้า config) มีค่าเมื่อข้อมูลเดียวกันถูกเสิร์ฟให้ผู้ใช้นับพัน รู้ว่าคุณมีปัญหาแบบไหนก่อนที่คุณจะเขียนโค้ด

Leo ออกแบบ cache key ใหม่: `menu:{restaurantId}` หนึ่ง cache entry ต่อร้านอาหาร ใช้ร่วมกันโดยผู้ใช้ทุกคนที่เรียกดูร้านนั้น

เขารัน load test อีกครั้ง การโหลดหน้าเพจลดจาก 188 มิลลิวินาทีเป็น 12 มิลลิวินาที นั่นคือการปรับปรุงที่พวกเขาตามหา

**การเปรียบเปรยกับร้านอาหาร**

ลองนึกภาพครัวของร้านอาหาร ทุกครั้งที่พนักงานเสิร์ฟต้องการรู้เมนูพิเศษวันนี้ พวกเขาเดินไปด้านหลัง ถามพ่อครัว แล้วเดินกลับมาที่โต๊ะ

นั่นใช้ได้ดีถ้าคุณมีพนักงานเสิร์ฟสองคนและโต๊ะสามโต๊ะ

ตอนนี้ลองนึกภาพพนักงานเสิร์ฟสองร้อยคนและโต๊ะหนึ่งพันโต๊ะ ทุกคนเดินไปด้านหลังถามคำถามเดียวกัน ครัวกลายเป็น bottleneck พ่อครัวตอบคำถามเดิมสี่ร้อยครั้งต่อชั่วโมง

วิธีแก้ที่ชัดเจน: เขียนเมนูพิเศษบนกระดานที่ด้านหน้าของร้านอาหาร พนักงานเสิร์ฟทุกคนอ่านจากกระดาน ครัวได้พัก กระดานถูกอัปเดตเมื่อเมนูพิเศษเปลี่ยน

กระดานนั้นคือ cache

cache คือที่เก็บข้อมูลที่ดึงมาล่าสุดที่เร็วและอยู่ใกล้ แทนที่จะดึงสิ่งเดิมจากแหล่งที่ช้าซ้ำ ๆ คุณดึงครั้งเดียวและเก็บมันไว้ใกล้ ๆ

มีการเปรียบเปรยอีกอันที่วิศวกรเห็นว่ามีประโยชน์: ชั้นหนังสือสำรองของห้องสมุด เมื่อหนังสือยอดนิยมถูกคืน บรรณารักษ์รู้ว่ามันจะถูกขอใหม่เร็ว ๆ นี้ จึงวางมันบนชั้นสำรองใกล้โต๊ะหน้าแทนที่จะเก็บลงชั้นในกอง ผู้ใช้คนถัดไปไม่ต้องเดินทั่วห้องสมุด — พวกเขาเจอมันตรงโต๊ะเลย ชั้นสำรองมีพื้นที่จำกัด ถ้ามันเต็ม หนังสือเก่ากว่าถูกย้ายกลับไปกองเพื่อทำที่ว่างให้เล่มใหม่ cache ทำงานเหมือนกันเป๊ะ: ข้อมูลที่เข้าถึงบ่อยอยู่ใกล้หน้า ข้อมูลที่เข้าถึงไม่บ่อยถูก evict เพื่อทำที่ว่าง

**ทำไมไม่ใช้แค่หน่วยความจำ?**

"เราเก็บเมนูในหน่วยความจำของแอปพลิเคชันไม่ได้หรือ?" Leo ถาม

คำถามที่สมเหตุสมผล

ได้ สำหรับแอปพลิเคชันเซิร์ฟเวอร์เดียว in-memory caching ใช้ได้ดี แต่ Nimbus รันอยู่หลัง load balancer ข้ามหลาย EC2 instance ถ้า instance หนึ่ง cache เมนูในหน่วยความจำของมัน instance อื่นไม่มีข้อมูลนั้น แต่ละตัวรักษา cache แยกกัน เมื่อเมนูอัปเดต คุณต้อง invalidate ทั้งหมด

นี่คือ *cache coherence problem* — การรักษาหลาย cache ให้สม่ำเสมอ

ElastiCache แก้สิ่งนี้โดยให้ cache แบบ *รวมศูนย์* ที่ทุก instance ของคุณใช้ร่วมกัน แทนที่แต่ละเซิร์ฟเวอร์จะมีหน่วยความจำของตัวเอง ทุกเซิร์ฟเวอร์อ่านจากและเขียนไปยัง cache เดียวกัน การอัปเดตหนึ่งครั้งกระจายไปยังทั้งหมด

**พบกับ ElastiCache**

"เดี๋ยว — แต่ *ทำไม* เราถึงทำแบบนั้น?" Maya ถาม "ทำไมต้องบริการใหม่ทั้งบริการ? ทำไมไม่แค่เพิ่ม database capacity?"

คำถามที่ดี คำตอบคือการเพิ่ม database capacity — instance ที่ใหญ่ขึ้น read replica มากขึ้น — ไม่ได้แก้ปัญหาพื้นฐาน แต่ละคำขอจากสี่สิบเจ็ดคำขอต่อการโหลดหน้ายังเสียเวลาและเงิน แม้บนฐานข้อมูลที่เร็วกว่า cache ไม่ได้ทำให้ฐานข้อมูลเร็วขึ้น; มันหมายความว่าฐานข้อมูลถูกถามคำถามเดียวกันน้อยลงมาก สำหรับข้อมูลที่ถูกอ่านซ้ำและเปลี่ยนไม่บ่อย — เช่นเมนูของร้านอาหาร — cache หมายความว่าฐานข้อมูลอาจตอบคำถามนั้นครั้งเดียวทุกห้านาที แทนที่จะสี่สิบเจ็ดครั้งต่อการโหลดหน้า

Amazon ElastiCache คือ managed caching service มันรัน caching engine ยอดนิยม — Redis และ Memcached — โดยที่คุณไม่ต้องจัดการเซิร์ฟเวอร์

**Redis** ทรงพลังกว่าในสอง มันรองรับโครงสร้างข้อมูลที่ซับซ้อน (strings, lists, sets, hashes, sorted sets), persistence (ข้อมูลอยู่รอดผ่านการรีสตาร์ท), replication และ pub/sub messaging Redis ทำได้มากกว่า caching — มันทำหน้าที่เป็นที่เก็บข้อมูลแบบเบาได้

**Memcached** เรียบง่ายกว่า key-value caching ล้วน ขยายในแนวนอน ไม่มี persistence เร็วกว่าสำหรับ use case ง่าย ๆ แต่มีฟีเจอร์น้อยกว่า

สำหรับ Nimbus: Redis พวกเขาต้องการ cache ข้อมูลเมนู (มีโครงสร้าง), session tokens (key-value) และต่อมาจะต้องการ sorted set สำหรับการจัดอันดับ "ร้านอาหารยอดนิยม"

**วิธีที่ Caching ทำงานในทางปฏิบัติ**

รูปแบบ caching พื้นฐานเรียกว่า **cache-aside** (หรือเรียก lazy loading):

1. แอปพลิเคชันต้องการข้อมูล
2. ตรวจสอบ cache ก่อน
3. ถ้าพบ (*cache hit*): ส่งคืนข้อมูลทันที
4. ถ้าไม่พบ (*cache miss*): ไปที่ฐานข้อมูล ดึงข้อมูล เก็บใน cache ส่งคืน

ใน pseudocode:

```
menuData = cache.get("menu:restaurant-047")
if menuData is null:
    menuData = dynamodb.query(TableName="menu", KeyConditionExpression="restaurantId = '047'")
    cache.set("menu:restaurant-047", menuData, ttl=300)  # Cache for 5 minutes
return menuData
```

คำขอแรกชนฐานข้อมูลเสมอ ทุกคำขอถัดไปชน cache ด้วย cache การอ่าน DynamoDB สี่สิบเจ็ดครั้งต่อการโหลดหน้าของ Nimbus กลายเป็นการ lookup cache หนึ่งหรือสองครั้ง เร็ว ถูก และขยายได้

**TTL: คุณจำได้นานแค่ไหน?**

ทุก cache entry มี **Time-To-Live (TTL)**: ระยะเวลาที่ entry จะหมดอายุและคำขอถัดไปกลับไปที่ฐานข้อมูลเพื่อข้อมูลใหม่

นี่คือความตึงเครียดหลักของ caching: ความสดใหม่ vs ประสิทธิภาพ

- **TTL สั้น (วินาที)**: ข้อมูลสดมาก แต่ cache miss เยอะ cache แทบไม่ช่วย
- **TTL ยาว (ชั่วโมงหรือวัน)**: เร็วมาก แต่ข้อมูลอาจเก่า ลูกค้าเห็นเมนูเมื่อวาน

สำหรับข้อมูลเมนู ห้านาทีสมเหตุสมผล เมนูไม่ได้เปลี่ยนทุกวินาที ถ้าร้านอาหารอัปเดตเมนู ลูกค้าอาจเห็นเวอร์ชันเก่านานสูงสุดห้านาที — ยอมรับได้

สำหรับ session token (ผู้ใช้คนนี้ล็อกอินอยู่ไหม?) TTL สั้นกว่าสมเหตุสมผล หรือคุณอัปเดต cache ทันทีเมื่อ session เปลี่ยน

สำหรับข้อมูลทางการเงิน (ยอดออเดอร์ บันทึกการชำระเงิน) อย่า cache มัน — หรือถ้าทำ ให้ invalidate ทันทีตอนเขียน

คุณอาจสงสัย: ทำไมไม่แค่เพิ่ม database capacity แทนการแนะนำ caching layer ทั้งชั้น? replica มากขึ้น instance ใหญ่ขึ้น — ทำไมไม่ทำแบบนั้น? คำตอบคือ database capacity ที่เพิ่มขึ้นคูณความสามารถของคุณในการจัดการคำขอพร้อมกัน แต่มันไม่ได้ลดจำนวนคำขอ ถ้าผู้ใช้หนึ่งหมื่นคนแต่ละคนทริกเกอร์การอ่านสี่สิบเจ็ดครั้งต่อการโหลดหน้า การเพิ่ม read replica ตัวที่สองแค่หมายความว่าแต่ละ replica จัดการสองหมื่นสามพันคำขอแทนสี่หมื่นเจ็ดพัน — งานรวมไม่ได้หดลง cache กำจัดงานที่ซ้ำซ้อนทั้งหมด: ผู้ใช้หนึ่งหมื่นคนนั้นใช้ผลลัพธ์ที่ cache ไว้เดียวกันร่วมกัน

"มีปัญหายากแค่สองอย่างในวิทยาการคอมพิวเตอร์" Leo อ้างคำพูด ด้วยการพูดที่ฝึกมาแล้วของคนที่เคยพูดมาก่อน "cache invalidation และการตั้งชื่อสิ่งต่าง ๆ"

"ทำไม cache invalidation ถึงยาก?" Maya ถาม

"เพราะข้อมูล *เปลี่ยนจริง ๆ* เมื่อไร? เมนูเปลี่ยนเพราะพาร์ทเนอร์ร้านอาหารอัปเดตหรือ? หรือเพราะ cron job รัน? หรือเพราะ admin แก้ด้วยมือ? ทุกที่ที่เปลี่ยนข้อมูลได้ต้องรู้ว่าต้องบอก cache"

นี่คือเหตุผลที่วิศวกร senior เริ่มการสนทนาเรื่อง caching ด้วย "write path มีอะไรบ้าง?" แทน "มาเพิ่ม Redis กัน"

**Cache Eviction: เมื่อกระดานเต็ม**

กระดานเมนูพิเศษมีพื้นที่จำกัด เมื่อมันเต็ม คุณต้องลบบางอย่างเพื่อทำที่ว่าง

Redis (และ cache โดยทั่วไป) มี *eviction policy* ที่กำหนดว่าอะไรถูกลบเมื่อหน่วยความจำเต็ม:

- **LRU (Least Recently Used)**: ลบ item ที่ไม่ถูกเข้าถึงมานานที่สุด
- **LFU (Least Frequently Used)**: ลบ item ที่ถูกเข้าถึงน้อยที่สุด
- **allkeys-random**: eviction แบบสุ่ม ง่าย ไม่เหมาะที่สุด
- **noeviction**: ส่งคืน error เมื่อหน่วยความจำเต็ม (แอปพลิเคชันต้องจัดการสิ่งนี้)

สำหรับเว็บแอปพลิเคชันส่วนใหญ่: LRU สิ่งที่คุณไม่ได้ดูเร็ว ๆ นี้น่าจะถูกต้องการน้อยกว่า

**ปัญหา Cache Stampede**

"เราคิดเรื่องว่าจะเกิดอะไรขึ้นถ้า cache ทั้งหมดว่างเปล่าพร้อมกันหรือยัง?" Priya ถาม

"เมื่อไรที่จะเกิดขึ้น?" Leo พูด

"เมื่อคุณ deploy ElastiCache cluster ใหม่ เมื่อ TTL ของ entry จำนวนมากหมดอายุพร้อมกัน เมื่อคุณ flush cache เพื่อบังคับรีเฟรชหลังแก้บั๊ก"

Leo คิดทบทวน "ถ้า cache ว่าง ทุกคำขอไปที่ฐานข้อมูล พร้อมกันทั้งหมด เป็นเวลาไม่กี่วินาที ฐานข้อมูลจัดการโหลดเต็มของผู้ใช้พร้อมกันทุกคน"

"โดยไม่มี cache อยู่ด้านหน้า"

"นั่นจะเจ็บ" Leo มองที่การตั้งค่า database capacity "เราโดน throttle แน่นอน"

นี่เรียกว่า **cache stampede** (หรือเรียก thundering herd) มันเกิดขึ้นเมื่อ cache entry จำนวนมากหมดอายุพร้อมกัน — มักเพราะพวกมันถูกสร้างพร้อมกันระหว่าง deploy หรือ cold start — และคลื่นของ cache miss กะทันหันทั้งหมดชนฐานข้อมูลพร้อมกัน

กลยุทธ์การบรรเทา:

**Jitter บน TTL**: แทนที่จะตั้งทุก entry เมนูเป็น 300 วินาทีเป๊ะ เพิ่มความผันแปรแบบสุ่ม: 270 ถึง 330 วินาที entry หมดอายุในเวลาที่ต่างกันเล็กน้อย กระจายคลื่น cache miss ออกไปในหนึ่งนาทีแทนที่จะชนพร้อมกัน

**Probabilistic early expiration**: ก่อน entry หมดอายุ คำขอเปอร์เซ็นต์เล็กน้อยรีเฟรชมันเชิงรุก สิ่งนี้ทำให้ entry สดก่อนที่มันจะเก่า ป้องกันไม่ให้การหมดอายุกลายเป็น miss

**Request coalescing (mutex/lock)**: เมื่อเกิด cache miss ให้ acquire lock ก่อนชนฐานข้อมูล คำขอพร้อมกันอื่นสำหรับ key เดียวกันรอให้คำขอแรกเสร็จและเติม cache แล้วอ่านจาก cache มีคำขอฐานข้อมูลแค่หนึ่งครั้งต่อ cache miss แม้ภายใต้ concurrency สูง

สำหรับ Nimbus พวกเขาทำ TTL jitter ง่าย มีประสิทธิภาพ ไม่เพิ่มความซับซ้อน

```python
import random
TTL_BASE = 300
TTL_JITTER = 30
ttl = TTL_BASE + random.randint(-TTL_JITTER, TTL_JITTER)
cache.set(key, value, ttl=ttl)
```

"สองบรรทัดของโค้ด" Leo พูด "เพื่อป้องกัน database outage ที่อาจเกิดขึ้นระหว่าง deploy"

"การปรับปรุงความน่าเชื่อถือส่วนใหญ่เป็นแบบนั้น" Priya พูด "ถูกที่จะทำ แพงที่จะเรียนรู้ว่าคุณต้องการมัน"

**โครงสร้างข้อมูล Redis: มากกว่า Key-Value**

เมื่อ Nimbus เพิ่มฟีเจอร์ "ร้านอาหารยอดนิยม" Leo เก็บการจัดอันดับเป็น JSON list ธรรมดาในตอนแรก: `trending:global → ["NIMBUS-047", "NIMBUS-112", ...]`

มันใช้ได้ แต่การอัปเดตมันงุ่มง่าม เพื่อเพิ่มร้านอาหารใหม่หรืออัปเดตคะแนน เขาต้องอ่านลิสต์ทั้งหมด แก้มันในแอปพลิเคชันโค้ด และเขียนทั้งหมดกลับ ภายใต้การเขียนพร้อมกันจาก analytics pipeline race condition ทำให้คะแนนถูกเขียนทับ

Priya ชี้เขาไปที่ Redis sorted set

**sorted set** ใน Redis เก็บสมาชิกพร้อมคะแนนตัวเลขที่เกี่ยวข้อง สมาชิกถูกเรียงตามคะแนนโดยอัตโนมัติ การดำเนินการเป็น atomic — ไม่มี race condition จากการอัปเดตพร้อมกัน

```
# Add/update a restaurant's score
ZADD trending:global 9420 "NIMBUS-047"
ZADD trending:global 8831 "NIMBUS-112"

# Get top 10 restaurants by score (highest first)
ZREVRANGE trending:global 0 9 WITHSCORES

# Increment a restaurant's score atomically
ZINCRBY trending:global 50 "NIMBUS-047"
```

analytics Lambda เรียก `ZINCRBY` ทุกครั้งที่มีออเดอร์ เพิ่มคะแนนของร้านอาหาร หน้าแรกเรียก `ZREVRANGE` เพื่อเอาสิบอันดับแรก ไม่มี lock ไม่มี race condition ไม่มี read-modify-write cycle

Redis รองรับโครงสร้างข้อมูลอื่น ๆ อีกหลายอย่างนอกเหนือจาก key-value ง่าย ๆ:

**Lists**: ลำดับที่เรียงกัน Push ไปด้านหน้าหรือด้านหลัง ใช้สำหรับ queue, ฟีดกิจกรรมล่าสุด, log stream

**Sets**: คอลเลกชันที่ไม่เรียงโดยไม่มีค่าซ้ำ การดำเนินการ union, intersection, difference ใช้สำหรับ "ผู้ใช้คนไหนเห็นการแจ้งเตือนนี้?" หรือ "ร้านอาหารไหนอยู่ในหมวดนี้?"

**Hashes**: ฟิลด์ที่มีชื่อภายใน key ใช้สำหรับ object ที่มีโครงสร้างซึ่งคุณอยากอัปเดตฟิลด์แต่ละอันโดยไม่เขียน object ทั้งหมดใหม่

**HyperLogLog**: การประมาณ cardinality เชิงความน่าจะเป็น นับผู้เยี่ยมชมหน้าที่ไม่ซ้ำกันโดยไม่เก็บ ID ผู้เยี่ยมชมทุกคน กระชับและเร็ว

**Pub/Sub**: เผยแพร่ข้อความไปยัง channel; subscriber รับมันแบบ real time ใช้สำหรับการแจ้งเตือน real-time แบบเบาระหว่างบริการ

"Redis ไม่ใช่แค่ cache" Leo พูด "มันคือ data structure server"

"นั่นคือคำอธิบายอย่างเป็นทางการของมัน" Priya พูด

"ผมคิดว่ามันเป็นแค่ dictionary หรู ๆ"

"มันเริ่มต้นแบบนั้น"

**Write-Through: รูปแบบ Caching อีกแบบ**

cache-aside (lazy loading) คือรูปแบบที่พบบ่อยที่สุด แต่มีอีกแบบที่ควรรู้: **write-through**

ใน write-through caching ทุกครั้งที่แอปพลิเคชันของคุณเขียนไปยังฐานข้อมูล มันก็เขียนไปยัง cache ทันทีด้วย

```python
def update_menu(restaurant_id, menu_data):
    dynamodb.put_item(TableName="menu", Item=menu_data)
    cache.set(f"menu:{restaurant_id}", menu_data, ttl=300)
```

ข้อดี: cache ทันสมัยเสมอ ไม่มีข้อมูลเก่าระหว่างการเขียนกับการหมดอายุ TTL

ข้อเสีย: ทุกการเขียนไปสองที่ และคุณเติม cache ด้วยข้อมูลที่อาจไม่เคยถูกอ่าน ถ้าสิบร้านอาหารอัปเดตเมนู แต่มีแค่สองร้านที่ได้ traffic มากในห้านาทีถัดไป คุณทำงาน write-through ให้ cache แปดอันที่จะไม่ถูกใช้ก่อนหมดอายุ

"เดี๋ยว — แต่ *ทำไม* เราถึงทำแบบนั้น?" Maya ถาม "ถ้าเราเขียนไปยัง cache ในทุกการอัปเดต เราทำงานต่อการเขียนมากกว่าเดิม นั่นดีกว่ายังไง?"

"มันไม่ได้ดีกว่าเสมอไป" Priya พูด "write-through สมเหตุสมผลเมื่อคุณทนช่วงข้อมูลเก่าหลังการเขียนไม่ได้เลย cache-aside ยอมรับข้อมูลเก่าสูงสุดหนึ่ง TTL แลกกับการไม่ทำงานพิเศษในทุกการเขียน"

สำหรับ Nimbus: cache-aside คือทางเลือกที่ถูกต้อง เมนูถูกอ่านบ่อยกว่าถูกเขียนมาก ช่วงเก่าห้านาทียอมรับได้ สำหรับระบบ trading ทางการเงินที่ทุกการอัปเดตราคาต้องสะท้อนทันที write-through จะเหมาะกว่า

การตัดสินใจมาลงที่สองคำถาม: อัตราการเขียนต่อการอ่านของคุณเป็นเท่าไร และคุณทนการอ่านที่เก่าหลังการเขียนได้แค่ไหน

**ElastiCache for Redis: สิ่งที่คุณได้แบบ Managed**

เหมือน RDS ElastiCache เอาเครื่องมือ open-source มาจัดการงานด้านการดำเนินงาน:

- **Automated backups**: snapshot ของ Redis ตามตารางเวลา
- **Multi-AZ replication**: primary node + read replica ในคนละ AZ
- **Automatic failover**: ถ้า primary Redis node ล้มเหลว replica ถูก promote โดยอัตโนมัติ
- **Cluster mode**: horizontal sharding ข้ามหลาย node สำหรับ cache ขนาดใหญ่มาก
- **Encryption**: การเข้ารหัสระหว่างส่งและขณะพักเพื่อ compliance
- **VPC integration**: cache รันในเครือข่ายส่วนตัวของคุณ ไม่เข้าถึงได้แบบสาธารณะ

**CacheHitRate**: เปอร์เซ็นต์ของการอ่าน cache ที่ส่งคืนผลลัพธ์ ในอุดมคติเหนือ 80% สำหรับ cache ที่โตแล้ว hit rate ที่ลดลงเป็นสัญญาณว่าข้อมูลที่เข้าถึงมากที่สุดของคุณไม่อยู่ใน cache — ไม่ TTL สั้นเกินไป cache เล็กเกินไป หรือ access pattern ของคุณเปลี่ยนไป

**CacheMisses**: จำนวน cache miss สัมบูรณ์ การพุ่งขึ้นกะทันหันที่นี่หมายความว่า cache ไม่ช่วยและฐานข้อมูลกำลังรับโหลดเต็ม

**Evictions**: จำนวน cache item ที่ถูก evict เพื่อทำที่ว่างให้อันใหม่ eviction rate สูงหมายความว่า cache ของคุณเล็กเกินไปสำหรับ working set คุณต้องการหน่วยความจำมากขึ้นหรือกลยุทธ์ caching ที่เลือกมากขึ้น

**CurrConnections**: การเชื่อมต่อ client ปัจจุบันไปยัง Redis การเชื่อมต่อมากเกินไปทำให้ขีดจำกัดการเชื่อมต่อของ Redis หมด แอปพลิเคชันควรใช้ connection pooling เพื่อหลีกเลี่ยงการเปิดการเชื่อมต่อใหม่ในทุกคำขอ

**ReplicationLag**: read replica ตามหลัง primary แค่ไหน ถ้านี่โตขึ้น การอ่าน replica อาจส่งคืนข้อมูลเก่า

**ElastiCache vs DAX: Cache แบบไหนสำหรับ DynamoDB?**

"ถ้าเรากำลัง cache ข้อมูล DynamoDB" Maya ถาม "ทำไมไม่ใช้ DAX แทน ElastiCache? ฉันเห็นมันในเอกสาร"

คำถามที่ดี

**DAX (DynamoDB Accelerator)** คือ in-memory cache ที่สร้างมาเฉพาะสำหรับ DynamoDB มันดักการเรียก DynamoDB API ที่ระดับ client — แอปพลิเคชันโค้ดของคุณคุยกับ DAX โดยใช้ DynamoDB SDK เดียวกัน cache miss ถูกดึงจาก DynamoDB โดยอัตโนมัติ cache hit ส่งคืนในไมโครวินาที การ invalidation ถูกจัดการโดยอัตโนมัติเมื่อข้อมูลเปลี่ยน

**ElastiCache** คือ cache อเนกประสงค์ คุณจัดการ cache key, ตรรกะ TTL, การ invalidation — ทั้งหมด ควบคุมได้มากขึ้น รับผิดชอบมากขึ้น

เมื่อไรใช้แต่ละอย่าง:

| สถานการณ์ | คำแนะนำ |
|---|---|
| คุณกำลัง cache การอ่าน DynamoDB และต้องการการเปลี่ยนแปลงแอปพลิเคชันเป็นศูนย์ | DAX |
| คุณต้องการ latency ไมโครวินาทีในการอ่าน DynamoDB | DAX |
| คุณกำลัง cache จากหลายแหล่ง (DynamoDB + RDS + external API) | ElastiCache |
| คุณต้องการโครงสร้างข้อมูล Redis (sorted set, pub/sub, HyperLogLog) | ElastiCache |
| คุณต้องการการควบคุม TTL ละเอียดและตรรกะ invalidation แบบกำหนดเอง | ElastiCache |
| คุณต้องการ session storage, rate limiting หรือ distributed lock | ElastiCache |

สำหรับ Nimbus: พวกเขาเลือก ElastiCache เพราะกำลัง cache ข้อมูลจากหลายแหล่ง — DynamoDB สำหรับเมนู, RDS สำหรับสรุปประวัติออเดอร์, external API สำหรับเรตติ้งร้านอาหาร DAX ใช้ได้กับ DynamoDB เท่านั้น และพวกเขาต้องการ Redis sorted set สำหรับการจัดอันดับยอดนิยม

"ถ้าเป็นปัญหา caching DynamoDB ล้วน ๆ" Priya พูด "DAX จะเป็นคำตอบที่ง่ายกว่า บริการเดียว invalidation อัตโนมัติ API เดียวกัน แต่เรามีแหล่งข้อมูลมากกว่าหนึ่งแหล่ง"

"ดังนั้น DAX ง่ายกว่าเมื่อคุณใช้ DynamoDB อย่างเดียว" Maya สรุป "ElastiCache เมื่อคุณต้องการกล่องเครื่องมือเต็ม"

"นั่นคือการแลกเปลี่ยน"

### เมื่อข้อมูล Cache ห้ามสูญหาย: Amazon MemoryDB

"ทำไมใครจะใช้ Redis เป็นฐานข้อมูลหลัก?" Maya ถาม "มันไม่ใช่ cache หรือ?"

นั่นคือคำถามที่ถูกต้องเป๊ะ

ElastiCache for Redis คือ cache — เร็ว in-memory และโดยการออกแบบ ไม่ใช่แหล่งความจริง ถ้า ElastiCache node ล้มเหลว cache ว่างตอนรีสตาร์ท แอปพลิเคชันอุ่นมันใหม่จากฐานข้อมูล นั่นโอเคสำหรับ cache

แต่บาง use case ใช้ Redis ไม่ใช่เป็น cache แต่เป็นที่เก็บข้อมูลหลัก — session state ที่ต้องอยู่รอดผ่านการรีสตาร์ท leaderboard แบบ real-time ที่ห้ามสูญหาย ตะกร้าสินค้าที่ต้องคงอยู่ผ่าน AZ failure สำหรับ use case เหล่านี้ ความทนทานแบบ eventual ของ ElastiCache คือความเสี่ยง

**Amazon MemoryDB for Redis** คือ durable in-memory database ที่ managed เต็มรูปแบบและเข้ากันได้กับ Redis ต่างจาก ElastiCache MemoryDB ใช้ distributed transaction log ที่เก็บข้ามหลาย AZ ซึ่งทำให้ทุกการเขียน durable ก่อนที่จะถูก acknowledge ข้อมูลอยู่รอดผ่าน node failure — ไม่ใช่เพราะมันเล่นซ้ำจากฐานข้อมูลที่ช้ากว่า แต่เพราะมันไม่เคยอยู่ที่เดียว

ความแตกต่างสำคัญ:

| | ElastiCache for Redis | MemoryDB for Redis |
|---|---|---|
| บทบาท | Cache layer | Primary database |
| ความทนทาน | ไม่รับประกันตอนล้มเหลว | Multi-AZ transaction log |
| Latency | อ่านและเขียนไมโครวินาที | อ่านไมโครวินาที เขียนมิลลิวินาทีหลักเดียว |

ทั้งสองรองรับคำสั่งและโครงสร้างข้อมูล Redis เดียวกัน API เหมือนกัน การรับประกันความทนทานไม่เหมือนกัน

สำหรับ Nimbus: ทีมอยากเก็บจำนวนออเดอร์รายร้านอาหารแบบ real-time เป็น Redis sorted set — และมันต้องอยู่รอดผ่าน AZ failure โดยไม่ต้อง reseed จากฐานข้อมูล ความต้องการนั้น — เข้ากันได้กับ Redis *และ* durable — คือสัญญาณเป๊ะสำหรับ MemoryDB

"ดังนั้นเราไม่ต้องอุ่นมันใหม่หลัง failure?" Leo ถาม

"นั่นคือประเด็น" Priya พูด "ถ้า node ล้มเหลวและกลับมา ข้อมูลอยู่ที่นั่น transaction log เก็บมันไว้"

Leo จ้องมองหน้าราคาชั่วครู่ "มันแพงกว่า ElastiCache"

"ทุกอย่างที่คุ้มค่าให้ไว้ใจเป็นแบบนั้น" Priya พูด

## จุดแข็งและข้อจำกัด

**ทำไม caching ถึงทรงพลัง**:

- ลดโหลดฐานข้อมูลอย่างมาก (query น้อยลง ต้นทุนต่ำลง)
- เวลาตอบสนองต่ำกว่ามิลลิวินาทีสำหรับ cache hit
- ปกป้องฐานข้อมูลของคุณจากการพุ่งของ traffic
- Redis รองรับโครงสร้างข้อมูลที่สมบูรณ์กว่า key-value store ง่าย ๆ
- การบรรเทา cache stampede (TTL jitter, coalescing) ปกป้องจากการพุ่งตอน cold-start

**ที่ที่ caching ซับซ้อน**:

- cache invalidation ยากจริง ๆ — ข้อมูลเก่าทำให้เกิดบั๊ก
- เพิ่มความซับซ้อนด้านการดำเนินงาน (อีกบริการที่ต้องตรวจสอบ อีกจุดที่ล้มเหลวได้)
- ปัญหา cold start: เมื่อคุณ deploy ใหม่ cache ว่าง — ฐานข้อมูลรับโหลดเต็ม
- cache stampede: ถ้า entry จำนวนมากหมดอายุพร้อมกัน ทุกคำขอชนฐานข้อมูลพร้อมกัน
- ElastiCache node ไม่ฟรี — คุณจ่ายแม้ตอนว่าง

**ElastiCache vs DynamoDB DAX**:

ถ้าคุณ cache ข้อมูล DynamoDB โดยเฉพาะ AWS เสนอ **DAX (DynamoDB Accelerator)** — in-memory cache ที่สร้างมาเฉพาะสำหรับ DynamoDB DAX โปร่งใสต่อแอปพลิเคชันโค้ดของคุณ (API เดียวกัน) ลด DynamoDB read latency เป็นไมโครวินาที และจัดการ cache invalidation โดยอัตโนมัติ

ใช้ DAX เมื่อ bottleneck ของคุณคือการอ่าน DynamoDB และคุณต้องการ caching แบบไม่ต้องเปลี่ยนโค้ด ใช้ ElastiCache เมื่อคุณต้องการ cache อเนกประสงค์สำหรับแหล่งข้อมูลใด ๆ หรือเมื่อคุณต้องการโครงสร้างข้อมูล Redis

## สรุป

การเรียกฐานข้อมูลสี่สิบเจ็ดครั้งกลายเป็นการ lookup cache หนึ่งครั้ง หน้าเพจไปจาก 188 มิลลิวินาทีเป็น 12 การเพิ่ม caching layer คือหนึ่งในการเปลี่ยนแปลงที่ให้ leverage สูงที่สุดที่แอปพลิเคชันที่กำลังเติบโตทำได้ — แต่เฉพาะเมื่อ cache ถูกออกแบบอย่างรอบคอบ ด้วยคำตอบที่ชัดเจนต่อคำถาม "ข้อมูลนี้เปลี่ยนเมื่อไร?"

- cache คือที่เก็บข้อมูลที่ดึงมาล่าสุดที่เร็ว — คุณถามครั้งเดียว จำคำตอบ ElastiCache คือ managed caching service ของ AWS รองรับ **Redis** (persistence, โครงสร้างข้อมูลซับซ้อน, pub/sub) และ **Memcached** (key-value ล้วน, horizontal scaling)
- **cache-aside pattern** (lazy loading): ตรวจ cache ก่อน ถอยกลับไปฐานข้อมูลตอน miss **TTL** ควบคุมว่าข้อมูลอยู่ใน cache นานแค่ไหน — TTL สั้นหมายถึงข้อมูลสดกว่าและ miss มากกว่า; TTL ยาวหมายถึงตอบสนองเร็วกว่าและอาจเก่า
- cache สิ่งที่ถูกต้อง: ข้อมูลราย entity ที่ใช้ร่วมกันข้ามผู้ใช้จำนวนมาก ไม่ใช่ข้อมูลรายผู้ใช้ที่เฉพาะแต่ละ session cache stampede เกิดขึ้นเมื่อ entry จำนวนมากหมดอายุพร้อมกัน — บรรเทาด้วย TTL jitter
- **DAX** คือทางเลือกที่ถูกต้องสำหรับ caching DynamoDB อย่างเดียว **ElastiCache** ยืดหยุ่นกว่าสำหรับ caching หลายแหล่งและโครงสร้างข้อมูล Redis
- ส่วนที่ยากที่สุดของ caching คือ invalidation: การรู้ว่าข้อมูลเปลี่ยนเมื่อไรและอัปเดต cache ข้ามทุก code path ที่เขียนมัน cache น่าเชื่อถือได้แค่เท่ากับกลยุทธ์ invalidation ของมัน

## เคล็ดลับการสอบ

*SAA-C03 Domain: ออกแบบสถาปัตยกรรมที่มีประสิทธิภาพสูง (Domain 3, Task 3.3)*

- **Redis vs Memcached ในการสอบ**: Redis = persistence, replication, โครงสร้างซับซ้อน, pub/sub Memcached = key-value ง่าย, horizontal scaling ล้วน เมื่อสถานการณ์กล่าวถึง "คุณห้ามสูญเสียข้อมูลที่ cache ไว้" คำตอบคือ Redis (มัน persist ลงดิสก์)
- **สัญญาณ use case ของ ElastiCache**: "ฐานข้อมูลเป็น bottleneck," "งานที่อ่านหนัก," "ลด latency," "session store" — ทั้งหมดชี้ไปที่ ElastiCache
- **สัญญาณ DAX**: "ลด DynamoDB read latency" หรือ "การอ่าน DynamoDB ช้าเกินไป" → DAX ไม่ใช่ ElastiCache
- **การจัดการ session**: ElastiCache Redis คือคำตอบมาตรฐานสำหรับการเก็บข้อมูล session ผู้ใช้ แอปพลิเคชันแบบ stateless + Redis session store = horizontal scaling พร้อม session ที่สม่ำเสมอ
- **Write-through vs cache-aside**: Cache-aside (lazy loading) พบบ่อยที่สุด Write-through อัปเดต cache ในทุกการเขียน — ไม่เคยเก่า แต่มีการดำเนินการเขียนมากกว่า ข้อสอบอาจแยกแยะพวกมัน
- **eviction policy ของ cache**: LRU (least recently used) คือคำตอบในการสอบที่พบบ่อยที่สุดสำหรับ web workload ทั่วไป
- **ElastiCache vs. MemoryDB:** ElastiCache = cache layer, เร็ว, ข้อมูลสูญหายตอนล้มเหลวยอมรับได้ MemoryDB = durable in-memory primary database, เข้ากันได้กับ Redis, multi-AZ transaction log ทริกเกอร์ในข้อสอบ: "เข้ากันได้กับ Redis และ durable" หรือ "ที่เก็บข้อมูลหลักใน Redis" → MemoryDB ไม่ใช่ ElastiCache

**คำใบ้ 3**: เป้าหมายคือลดโหลดฐานข้อมูล ไม่ใช่แค่จัดการมันให้มากขึ้น

**คำตอบ**: C

**คำอธิบาย**: ElastiCache ด้วย TTL หนึ่งชั่วโมง cache ข้อมูลแคตตาล็อกหลังคำขอแรกต่อ key คำขอถัดไปส่งคืนจาก cache โดยไม่แตะฐานข้อมูล เมื่อการอัปเดตทุกคืนรัน entry หมดอายุภายในหนึ่งชั่วโมงและข้อมูลใหม่ถูกโหลดในคำขอถัดไป

**ทำไมไม่ใช่ A?** read replica กระจาย read traffic ข้าม node ฐานข้อมูลมากขึ้นแต่ไม่ลดจำนวน query ทั้งหมด มีประโยชน์สำหรับการ scale การอ่าน ไม่ใช่การลดโหลดฐานข้อมูลจาก query ที่ทำซ้ำบ่อย

**ทำไมไม่ใช่ B?** การย้ายไป DynamoDB ไม่แก้ปัญหาที่อยู่เบื้องล่าง — ข้อมูลแคตตาล็อกยังถูกดึงจากฐานข้อมูล (DynamoDB) ในทุกคำขอผู้ใช้

**ทำไมไม่ใช่ D?** การ scale up instance จัดการ query พร้อมกันมากขึ้นแต่ไม่ลดจำนวน query ความไม่มีประสิทธิภาพพื้นฐานยังคงอยู่
