# บทที่ 4: คอมพิวเตอร์ในอาคารของคนอื่น

แอป Nimbus กำลังรันบนแล็ปท็อปของ Tom

ไม่เป็นไรสำหรับการสาธิตต่อนักลงทุน แต่ไม่โอเคเมื่อ Maya กดปุ่ม "เปิดตัว" และร้านอาหาร 200 แห่งสมัครในสัปดาห์แรก แล็ปท็อปของ Tom ตอนนี้กำลังจัดการออร์เดอร์จริง เมนูจริง และลูกค้าจริง — นั่งอยู่ใต้โต๊ะของ Tom ทำงานผ่าน Wi-Fi ของสำนักงาน เสียบกับปลั๊กไฟที่ยังจ่ายไฟให้เครื่องทำความร้อนและเครื่องชงกาแฟด้วย

"เราต้องการเซิร์ฟเวอร์" Maya พูด "เซิร์ฟเวอร์จริง ทำงานอยู่ที่ไหนสักแห่งที่ไม่ใช่ใต้โต๊ะของคุณ"

Tom มองแล็ปท็อป เสียงพัดลมได้ยินจากทั่วห้อง

นั่นคือเมื่อพวกเขาเริ่มดูว่าการเช่าคอมพิวเตอร์หมายความว่าอะไรจริงๆ

**การนามธรรมที่ไม่มีใครอธิบาย**

เมื่อคนพูดว่าแอปพลิเคชันของพวกเขา "รันบนคลาวด์" พวกเขามักหมายความว่ามันรันบนเครื่องเสมือน — คอมพิวเตอร์ที่ไม่มีตัวตนทางกายภาพเป็นฮาร์ดแวร์เฉพาะ แต่ทำงานในทุกๆ ทางเหมือนว่ามันมี

นี่คือกลไก

เซิร์ฟเวอร์ทางกายภาพในศูนย์ข้อมูลของ AWS มีทรัพยากรมากมาย: คอร์ CPU หน่วยความจำ ดิสก์ และแบนด์วิดธ์เครือข่าย AWS นำเซิร์ฟเวอร์ทางกายภาพนั้นและแบ่งมันโดยใช้ซอฟต์แวร์ที่เรียกว่า **hypervisor** Hypervisor สร้างเครื่องเสมือนหลายเครื่อง แต่ละเครื่องดูเหมือนมี CPU หน่วยความจำและดิสก์ของตัวเอง — แต่จริงๆ แล้วแชร์ฮาร์ดแวร์ทางกายภาพพื้นฐาน

เครื่องเสมือนแต่ละเครื่องนั้นคือสิ่งที่ AWS เรียกว่า **EC2 instance**

EC2 ย่อมาจาก Elastic Compute Cloud ส่วน "elastic" มีความสำคัญ และเราจะมาถึงมัน สำหรับตอนนี้: EC2 instance คือคอมพิวเตอร์ที่คุณเช่าตามชั่วโมง มันมีระบบปฏิบัติการ การเชื่อมต่อเครือข่าย และพลังการประมวลผล มันรันแอปพลิเคชันของคุณเหมือนที่เซิร์ฟเวอร์ทางกายภาพจะทำ

การเปรียบเปรย: การเช่าอพาร์ตเมนต์ในอาคารใหญ่เทียบกับการซื้อบ้าน

เจ้าของอาคาร (AWS) ดูแลโครงสร้างทางกายภาพ ระบบประปา ไฟฟ้า ความปลอดภัย คุณได้รับหน่วย คุณตกแต่งมันตามต้องการ คุณจ่ายรายเดือน (หรือรายชั่วโมง) เมื่อต้องการพื้นที่มากขึ้น คุณย้ายไปยังหน่วยที่ใหญ่กว่า เมื่อคุณย้ายออก คุณหยุดจ่าย

**การเลือก Instance ของคุณ: ขนาดสำคัญ**

EC2 instance ทั้งหมดไม่เหมือนกัน AWS เสนอ instance ประเภทหลายร้อยแบบ จัดระเบียบเป็นตระกูลตามสิ่งที่ถูกปรับให้เหมาะสม

**ทั่วไป** (เช่น `t3`, `m6i`): CPU และหน่วยความจำสมดุล ตัวเลือกเริ่มต้นที่ดีสำหรับ web application ส่วนใหญ่

**ประมวลผลปรับปรุง** (เช่น `c7g`): CPU มากกว่าหน่วยความจำ เหมาะสำหรับการเข้ารหัสวิดีโอ การสร้างแบบจำลองทางวิทยาศาสตร์ การประมวลผลแบบ batch

**หน่วยความจำปรับปรุง** (เช่น `r7i`): หน่วยความจำมากกว่า CPU เหมาะสำหรับฐานข้อมูล การ caching การวิเคราะห์ในหน่วยความจำ

**พื้นที่เก็บข้อมูลปรับปรุง** (เช่น `i3`): พื้นที่เก็บข้อมูลในเครื่องความเร็วสูง เหมาะสำหรับงานที่ต้องการ disk I/O เร็วมาก

**การประมวลผลเร่งความเร็ว** (เช่น `p4`): มี GPU เหมาะสำหรับการฝึก machine learning และการเรนเดอร์กราฟิก

แต่ละตระกูลมีขนาด `t3.micro` มี 2 CPU เสมือนและหน่วยความจำ 1 GB `t3.xlarge` มี 4 CPU เสมือนและ 16 GB คุณเลือกขนาดที่เหมาะสมสำหรับงาน

Leo เลือก `t3.micro`

"หนึ่ง `t3.micro` รองรับผู้ใช้ได้กี่คน?" Tom ถาม

"ขึ้นอยู่กับแอปพลิเคชัน" Leo พูด "แต่อาจไม่ใช่ผู้ใช้พร้อมกัน 100 คนที่กำลังอัพโหลดรูปภาพและ query ฐานข้อมูล"

Tom เขียน "t3.micro" บนไวท์บอร์ดและวาดหน้าเศร้าข้างๆ

**AMI: สถานะเริ่มต้นของเครื่องของคุณ**

ก่อนที่คุณจะเปิดใช้งาน EC2 instance คุณจะเลือกระบบปฏิบัติการและการกำหนดค่าเริ่มต้น ใน AWS สิ่งนี้เรียกว่า **Amazon Machine Image** (AMI)

AMI คือเทมเพลต มันกำหนด:

- ระบบปฏิบัติการ (Amazon Linux, Ubuntu, Windows Server ฯลฯ)
- ซอฟต์แวร์ที่ติดตั้งไว้ล่วงหน้า
- สถานะดิสก์เริ่มต้น

เมื่อคุณเปิดใช้ instance จาก AMI AWS จะสร้างสำเนาใหม่ของเทมเพลตนั้นสำหรับคุณ คุณยังสามารถสร้าง AMI ของคุณเองได้ — ถ้าคุณกำหนดค่าเซิร์ฟเวอร์ตรงตามที่ต้องการ คุณสามารถ "บันทึก" สถานะนั้นเป็น AMI ที่กำหนดเองและใช้มันเพื่อเปิดใช้เซิร์ฟเวอร์ที่เหมือนกันอย่างรวดเร็ว

ลองนึกถึง AMI เหมือนสูตรอาหาร สูตรอาหารอธิบายอาหาร ทุกครั้งที่คุณทำตามสูตร คุณจะได้อาหารเดิม ถ้าคุณต้องการเปลี่ยนอาหารอย่างถาวร คุณอัพเดตสูตร

**คู่คีย์: วิธีที่ถูกต้องในการเข้าถึงเซิร์ฟเวอร์**

จำหายนะ "Admin123" จากบทที่แล้วได้ไหม?

วิธีที่ถูกต้องในการเข้าสู่ระบบ EC2 instance คือด้วย **คู่คีย์**

คู่คีย์คือคู่การเข้ารหัส: คีย์สาธารณะ (เก็บโดย AWS บนเซิร์ฟเวอร์) และคีย์ส่วนตัว (ไฟล์ที่คุณดาวน์โหลดและเก็บเป็นความลับ) ในการเข้าสู่ระบบ คุณใช้ SSH — โปรโตคอลที่ปลอดภัย — กับคีย์ส่วนตัวของคุณ ไม่มีรหัสผ่าน ถ้าคุณทำคีย์ส่วนตัวหาย คุณก็เสียสิทธิ์เข้าถึง ไม่มี "ลืมรหัสผ่าน" สำหรับ SSH

สิ่งนี้สำคัญเพราะคู่คีย์คือ:

- เฉพาะตัวสำหรับคุณ
- เป็นไปไม่ได้ที่จะเดาทางการเข้ารหัส
- ไม่เก็บโดย AWS (คุณเก็บคีย์ส่วนตัว)
- ง่ายต่อการเพิกถอน (ลบคีย์ออกจากเซิร์ฟเวอร์ สร้างคู่ใหม่)

Priya ตั้งค่าการเข้าถึงแบบใช้คีย์บนเซิร์ฟเวอร์ Nimbus แล้ว เซิร์ฟเวอร์ Admin123 ถูกปลดระวาง ไม่มีใครเสียใจ

**วงจรชีวิต Instance: ไม่ตลอดกาล**

นี่คือสิ่งที่ผู้เริ่มต้นหลายคนพลาด

EC2 instances ไม่ถาวรโดยค่าเริ่มต้น เมื่อคุณหยุด instance ทรัพยากรการประมวลผลจะถูกปล่อย เมื่อคุณเริ่มใหม่ มันอาจทำงานบนฮาร์ดแวร์ทางกายภาพที่แตกต่างกัน ข้อมูลใดๆ ที่จัดเก็บ *บน instance เอง* (บน root volume) จะรอดผ่านวงจรหยุด/เริ่ม — แต่ IP ที่อยู่สาธารณะจะเปลี่ยน

เมื่อคุณ *ยุติ* instance มันหายไป เว้นแต่คุณจะมีพื้นที่เก็บข้อมูลแยกต่างหากแนบไว้ (ที่เราจะครอบคลุมในบทที่ 6) ข้อมูลใดๆ บน instance จะหายไป

"ความไม่ถาวร" นี้เป็นจริงๆ แล้วเป็นคุณสมบัติ ไม่ใช่ข้อบกพร่อง มันหมายความว่าคุณสามารถเปิดใช้เซิร์ฟเวอร์ ใช้มัน และทิ้งมันได้ มันเปิดใช้งานการปรับขนาดแนวนอน แต่มันยังหมายความว่าคุณไม่ควรเก็บข้อมูลสำคัญ *บน* EC2 instance เอง

ข้อมูลอยู่ที่ไหนถ้าอย่างนั้น?

ในพื้นที่เก็บข้อมูลแยกต่างหาก เราจะมาถึงนั้นในสองบทถัดไป

**"Elastic" หมายความว่าอะไร**

เราบอกว่า EC2 ย่อมาจาก Elastic Compute Cloud อะไรที่ยืดหยุ่น?

สองสิ่ง:

**ความยืดหยุ่นแนวตั้ง**: คุณสามารถเปลี่ยนขนาดของ instance ได้ หยุด instance เปลี่ยนจาก `t3.micro` เป็น `t3.xlarge` เริ่มใหม่ CPU และหน่วยความจำมากขึ้น แอปพลิเคชันเดิม การตั้งค่าเดิม

**ความยืดหยุ่นแนวนอน**: คุณสามารถเพิ่ม instance มากขึ้นได้ แทนที่จะเป็นเซิร์ฟเวอร์ใหญ่หนึ่งเครื่อง ให้รันเซิร์ฟเวอร์ขนาดกลางสิบเครื่องหลัง load balancer เมื่อ traffic ลดลง ให้ลบ instances และหยุดจ่าย

ทั้งสองวิธีแก้ปัญหา "เซิร์ฟเวอร์หนึ่งเครื่อง ปริมาณ traffic มากเกินไป" มีการแลกเปลี่ยนที่แตกต่างกัน ซึ่งเราจะสำรวจในบทที่ 7 เมื่อเราเพิ่ม Auto Scaling ในเรื่อง

ข้อมูลเชิงลึกสำคัญ: ด้วย EC2 พลังการประมวลผลเป็นสิ่งที่คุณ *ปรับ* ไม่ใช่สิ่งที่คุณ *ซื้อ* ต้องการมากขึ้น? หมุนปุ่ม ต้องการน้อยลง? ลดลง จ่ายตามนั้น

## จุดแข็งและข้อจำกัด

**ทำไม EC2 จึงมีประสิทธิภาพ**:

- ควบคุมได้อย่างสมบูรณ์ คุณเลือก OS ซอฟต์แวร์ การกำหนดค่า มันคือคอมพิวเตอร์ของคุณ
- ขนาดยืดหยุ่น Instance ประเภทหลายร้อยแบบสำหรับทุกกรณีการใช้งาน
- ไม่มีฮาร์ดแวร์ที่ต้องจัดการ AWS จัดการชั้นกายภาพ
- การเรียกเก็บเงินต่อวินาที (สำหรับ instance ประเภทส่วนใหญ่) คุณหยุด instance คุณหยุดจ่าย
- ใช้ร่วมกับทุกอย่าง EC2 เป็นพื้นฐานที่ AWS services ส่วนใหญ่สร้างขึ้น

**ที่ซึ่งมันซับซ้อนขึ้น**:

- คุณรับผิดชอบในการ patch และอัปเดตระบบปฏิบัติการ
- การจัดการ EC2 ในระดับขนาดหมายถึงการจัดการสถานะ instance, AMIs, แพทช์ความปลอดภัย
- EC2 ไม่ใช่คำตอบที่ถูกต้องสำหรับทุกอย่าง
- Instances ที่ไม่ได้ใช้ยังเสียค่าใช้จ่าย

## สรุป

- **EC2 instance** คือเครื่องเสมือนที่คุณเช่าใน AWS มีระบบปฏิบัติการ การเข้าถึงเครือข่าย และทรัพยากรการประมวลผล
- ประเภท instance จัดระเบียบตามกรณีการใช้งาน: ทั่วไป ประมวลผลปรับปรุง หน่วยความจำปรับปรุง พื้นที่เก็บข้อมูลปรับปรุง การประมวลผลเร่งความเร็ว
- **AMI** (Amazon Machine Image) คือเทมเพลตสำหรับ OS และการกำหนดค่าเริ่มต้น AMI ที่กำหนดเองช่วยให้ deploy ได้อย่างสม่ำเสมอและทำซ้ำได้
- **คู่คีย์** คือวิธีที่ปลอดภัยในการเข้าถึง EC2 instances ไม่มีรหัสผ่าน
- EC2 instances ไม่ถาวรโดยค่าเริ่มต้น Instances ที่ยุติจะเสียข้อมูล
- "Elastic" หมายความว่าคุณสามารถปรับขนาดการประมวลผลขึ้นและลง — ทั้งแนวตั้ง (instance ใหญ่กว่า) และแนวนอน (instance มากขึ้น)

*SAA-C03 Domain 3 — Task 3.2 (โซลูชันการประมวลผลที่มีประสิทธิภาพสูง)*

- **ความรับผิดชอบร่วมกันสำหรับ EC2**: คุณรับผิดชอบในการ patch OS AWS ดูแลฮาร์ดแวร์ทางกายภาพและ hypervisor
- **ตระกูล instance สำคัญสำหรับคำถามสถานการณ์** ถ้าสถานการณ์กล่าวถึงข้อกำหนดหน่วยความจำสูง คำตอบน่าจะเกี่ยวข้องกับ instance ที่ปรับแต่งหน่วยความจำ

ก) Instances ที่ปรับแต่งหน่วยความจำพร้อมจำนวนคงที่  
ข) Instances ที่ปรับแต่งการประมวลผลพร้อม Auto Scaling เพื่อจัดการ traffic spikes  
ค) Instances ทั่วไปพร้อม instance size ขนาดใหญ่เดียว  
ง) Instances ที่ปรับแต่งพื้นที่เก็บข้อมูลเพราะแคตตาล็อกสินค้าต้องการการเข้าถึงดิสก์ที่รวดเร็ว

**คำอธิบาย**: Instances ที่ปรับแต่งการประมวลผล (เช่นตระกูล `c`) ให้ CPU มากขึ้นต่อดอลลาร์สำหรับงานที่ใช้ CPU เข้มข้น Auto Scaling ปรับจำนวน instances โดยอัตโนมัติตามโหลด — เพิ่ม instances ในช่วงงานขาย ลบออกเมื่อ traffic กลับสู่ปกติ
