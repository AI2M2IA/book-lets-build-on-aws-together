นั่นคือตอนที่พวกเขาเริ่มดูว่าการเช่าคอมพิวเตอร์หมายความว่าอย่างไรจริง ๆ

**การนามธรรมที่ไม่มีใครอธิบาย**

เมื่อคนพูดว่าแอปพลิเคชันของพวกเขา "รันบนคลาวด์" พวกเขามักหมายความว่ามันรันบนเครื่องเสมือน — คอมพิวเตอร์ที่ไม่มีตัวตนทางกายภาพเป็นฮาร์ดแวร์เฉพาะ แต่ทำงานในทุก ๆ ทางเหมือนกับว่ามันมี

นี่คือกลไก

เซิร์ฟเวอร์ทางกายภาพในศูนย์ข้อมูลของ AWS มีทรัพยากรมากมาย: คอร์ CPU หน่วยความจำ ดิสก์ และแบนด์วิดท์เครือข่าย AWS นำเซิร์ฟเวอร์ทางกายภาพนั้นมาแบ่งด้วยซอฟต์แวร์ที่เรียกว่า **hypervisor** — ซอฟต์แวร์ที่ทำหน้าที่เหมือนผู้ดูแลอาคาร แบ่งทรัพยากรของเซิร์ฟเวอร์ทางกายภาพให้ผู้เช่าเสมือนหลายราย hypervisor สร้างเครื่องเสมือนหลายเครื่อง แต่ละเครื่องดูเหมือนมี CPU หน่วยความจำ และดิสก์ของตัวเอง — แต่จริง ๆ แล้วแชร์ฮาร์ดแวร์ทางกายภาพที่อยู่เบื้องล่าง

ลองคิดว่ามันเหมือนการเช่าอพาร์ตเมนต์ในอาคารใหญ่ แทนที่จะซื้อบ้าน

เจ้าของอาคาร (AWS) ดูแลโครงสร้างทางกายภาพ — ระบบประปา ระบบไฟฟ้า ความปลอดภัย คุณได้ยูนิตหนึ่ง คุณตกแต่งมันตามที่ต้องการ คุณจ่ายรายเดือน (หรือรายชั่วโมง) เมื่อต้องการพื้นที่มากขึ้น คุณย้ายไปยังยูนิตที่ใหญ่กว่า เมื่อคุณย้ายออก คุณหยุดจ่าย

เครื่องเสมือนแต่ละเครื่องที่เช่ามานั้นคือสิ่งที่ AWS เรียกว่า **EC2 instance** — Elastic Compute Cloud

EC2 ย่อมาจาก Elastic Compute Cloud ส่วน "elastic" สำคัญ และเราจะมาถึงมัน สำหรับตอนนี้: EC2 instance คือคอมพิวเตอร์ที่คุณเช่าเป็นรายชั่วโมง มันมีระบบปฏิบัติการ การเชื่อมต่อเครือข่าย และพลังการประมวลผล มันรันแอปพลิเคชันของคุณเหมือนที่เซิร์ฟเวอร์ทางกายภาพจะทำ

**การเลือก Instance ของคุณ: ขนาดสำคัญ**

EC2 instance ไม่เหมือนกันทั้งหมด AWS เสนอ instance หลายร้อยประเภท จัดระเบียบเป็นตระกูลตามสิ่งที่พวกมันถูกปรับให้เหมาะสม

**General purpose (ทั่วไป)** (เช่น `t3`, `m6i`): CPU และหน่วยความจำสมดุล ตัวเลือกเริ่มต้นที่ดีสำหรับเว็บแอปพลิเคชันส่วนใหญ่ ตระกูล `t3` เป็นแบบ burstable — มันสะสมเครดิต CPU ในช่วงที่ใช้งานต่ำและใช้พวกมันในช่วงพีค เยี่ยมสำหรับสภาพแวดล้อม development และเวิร์กโหลดที่มีความต้องการ CPU ผันแปร ตระกูล `m6i` ให้ประสิทธิภาพที่สม่ำเสมอ ไม่ burstable — ดีกว่าสำหรับเวิร์กโหลด production ที่มีความต้องการ CPU ต่อเนื่อง

**Compute optimized (ปรับเพื่อการประมวลผล)** (เช่น `c7g`): CPU มากกว่าเมื่อเทียบกับหน่วยความจำ ดีสำหรับการเข้ารหัสวิดีโอ การสร้างแบบจำลองทางวิทยาศาสตร์ การประมวลผลแบบ batch คำต่อท้าย "g" ใน `c7g` หมายถึง instance ใช้โปรเซสเซอร์ AWS Graviton — ชิปที่ใช้สถาปัตยกรรม ARM ที่ AWS ออกแบบเอง ให้อัตราส่วนราคาต่อประสิทธิภาพที่ดีกว่าสำหรับเวิร์กโหลดจำนวนมากเมื่อเทียบกับ instance x86 ที่เทียบเท่า

**Memory optimized (ปรับเพื่อหน่วยความจำ)** (เช่น `r7i`): หน่วยความจำมากกว่าเมื่อเทียบกับ CPU ดีสำหรับฐานข้อมูล การแคช การวิเคราะห์ในหน่วยความจำ ถ้าคุณรันฐานข้อมูลที่ประสิทธิภาพดีขึ้นอย่างมากด้วยการเก็บข้อมูลไว้ใน RAM มากขึ้น ตระกูล R คือจุดเริ่มต้นที่ถูกต้อง

**Storage optimized (ปรับเพื่อพื้นที่จัดเก็บ)** (เช่น `i3`): พื้นที่จัดเก็บในเครื่องความเร็วสูง ดีสำหรับเวิร์กโหลดที่ใช้ข้อมูลหนักที่ต้องการ disk I/O ที่เร็วมาก พื้นที่จัดเก็บ NVMe ในเครื่องบน instance เหล่านี้เร็วกว่า EBS อย่างมีนัยสำคัญ — แต่มันก็เป็นแบบชั่วคราว ใช้มันสำหรับข้อมูลชั่วคราว ไม่ใช่สำหรับอะไรก็ตามที่คุณยอมเสียไม่ได้

**Accelerated computing (การประมวลผลแบบเร่ง)** (เช่น `p4`): มี GPU แนบมาด้วย ดีสำหรับการฝึก machine learning และการเรนเดอร์กราฟิก instance เหล่านี้แพง — `p3.8xlarge` มีราคาเกิน $12 ต่อชั่วโมง — แต่สำหรับเวิร์กโหลดที่ได้ประโยชน์จากความขนานของ GPU ไม่มีอะไรทดแทนได้

แต่ละตระกูลมีขนาดต่าง ๆ `t3.micro` มี 2 virtual CPU และหน่วยความจำ 1 GB `t3.xlarge` มี 4 virtual CPU และ 16 GB `t3.2xlarge` เพิ่มเป็นสองเท่าอีกครั้ง รูปแบบการตั้งชื่อสอดคล้องกัน: คำต่อท้ายไล่จาก `nano`, `micro`, `small`, `medium`, `large`, `xlarge`, `2xlarge`, `4xlarge`, `8xlarge` และต่อไป

รูปแบบนี้มีชื่อ: **การกำหนดขนาดให้เหมาะสม (right-sizing)** มันหมายถึงการจับคู่ขนาด instance กับเวิร์กโหลดจริง ไม่ใช่กรณีเลวร้ายที่สุดที่จินตนาการขึ้น เครื่องมือ AWS เช่น AWS Compute Optimizer และเมตริก CloudWatch ทำให้การกำหนดขนาดให้เหมาะสมเป็นการตัดสินใจที่ขับเคลื่อนด้วยข้อมูลแทนที่จะเป็นการเดา

**AMI: สถานะเริ่มต้นของเครื่องคุณ**

ก่อนที่คุณจะเปิด EC2 instance คุณเลือกระบบปฏิบัติการและการกำหนดค่าเริ่มต้นของมัน ใน AWS สิ่งนี้เรียกว่า **Amazon Machine Image** (AMI)

AMI คือเทมเพลต มันกำหนด:

- ระบบปฏิบัติการ (Amazon Linux, Ubuntu, Windows Server ฯลฯ)
- ซอฟต์แวร์ที่ติดตั้งไว้ล่วงหน้า
- สถานะเริ่มต้นของดิสก์

เมื่อคุณเปิด instance จาก AMI AWS จะสร้างสำเนาใหม่ของเทมเพลตนั้นให้คุณโดยเฉพาะ คุณยังสามารถสร้าง AMI ของตัวเองได้ — ถ้าคุณกำหนดค่าเซิร์ฟเวอร์ในแบบที่คุณต้องการพอดี คุณสามารถ "บันทึก" สถานะนั้นเป็น AMI ที่กำหนดเองและใช้มันเพื่อเปิดเซิร์ฟเวอร์ที่เหมือนกันได้อย่างรวดเร็ว นี่คือวิธีที่คุณ deploy สภาพแวดล้อมที่สอดคล้องกันในระดับขนาดใหญ่

ลองคิดว่า AMI เป็นสูตรอาหาร สูตรอธิบายอาหารจานนั้น ทุกครั้งที่คุณทำตามสูตร คุณก็ได้อาหารจานเดียวกัน ถ้าคุณต้องการเปลี่ยนอาหารอย่างถาวร คุณก็อัปเดตสูตร

AWS มีตลาดของ AMI — บางอันได้รับการดูแลโดย AWS (Amazon Linux 2, Amazon Linux 2023) บางอันได้รับการดูแลโดยดิสทริบิวชัน Linux รายใหญ่ (Ubuntu, Red Hat, SUSE) และบางอันมาจากผู้ขายบุคคลที่สาม (เซิร์ฟเวอร์ฐานข้อมูลที่กำหนดค่าไว้ล่วงหน้า อุปกรณ์ความปลอดภัย ซอฟต์แวร์เชิงพาณิชย์) สำหรับเว็บแอปพลิเคชันส่วนใหญ่ AMI ของ Amazon Linux ที่ AWS ดูแลหรือ AMI ของ Ubuntu LTS คือจุดเริ่มต้นที่ถูกต้อง

สำหรับ Nimbus Leo สร้าง AMI ที่กำหนดเองซึ่งเริ่มจากฐาน Amazon Linux 2023 ล่าสุดและเพิ่ม Node.js runtime ระบบ dependency ของแอปพลิเคชัน และไฟล์ service ที่สร้างไว้ล่วงหน้าสำหรับกระบวนการแอปพลิเคชัน instance ใหม่ที่เปิดจาก AMI นี้เริ่มให้บริการทราฟฟิกในเวลาต่ำกว่า 90 วินาที — เร็วกว่าเวลาบูตสี่นาทีอย่างมีนัยสำคัญเมื่อใช้สคริปต์ UserData ในการติดตั้งทุกอย่างใหม่ตั้งแต่ต้น

มีข้อแลกเปลี่ยน: AMI ที่กำหนดเองต้องได้รับการดูแลรักษา ทุกครั้งที่คุณอัปเดต system dependency หรือเวอร์ชัน runtime คุณต้องสร้าง AMI ใหม่ ทีมที่ปล่อยให้ AMI ของตัวเองเก่าจะพบว่าตัวเองรัน instance ที่มีซอฟต์แวร์ล้าสมัย — ความเสี่ยงด้านความปลอดภัย Priya ใส่ "สร้าง AMI ใหม่ด้วยแพ็กเกจล่าสุด" ลงในรายการตรวจสอบทางวิศวกรรมรายเดือน

"การจัดเก็บ AMI มีต้นทุนเท่าไหร่?" Tom ถาม

AMI ถูกจัดเก็บเป็น EBS snapshot — คุณจ่ายอัตรา EBS snapshot (ประมาณ $0.05 ต่อ GB ต่อเดือน) สำหรับขนาดของ AMI AMI ของ Amazon Linux ทั่วไปพร้อม stack แอปพลิเคชัน Nimbus มีขนาดราว ๆ 4 GB ที่ $0.05/GB: $0.20 ต่อเดือนต่อ AMI การเก็บ AMI ในอดีตห้าตัวไว้เพื่อจุดประสงค์การ rollback: $1/เดือน ไม่ใช่ต้นทุนที่มีนัยสำคัญ

**UserData: สคริปต์ Bootstrap**

มีอีกหนึ่งตัวเลือกการกำหนดค่าบน EC2 ที่ Leo ค้นพบเมื่อเขาพยายามหลีกเลี่ยงการสร้าง AMI ใหม่ทุกครั้งที่โค้ดแอปพลิเคชันเปลี่ยน

เมื่อคุณเปิด EC2 instance คุณสามารถให้ **สคริปต์ UserData** — สคริปต์ shell ที่รันโดยอัตโนมัติเมื่อ instance เริ่มต้นเป็นครั้งแรก มันรันในฐานะ root ก่อนที่ instance จะถือว่า "พร้อม"

สำหรับ Nimbus สคริปต์ UserData มีหน้าตาประมาณนี้:

```bash
#!/bin/bash
yum update -y
yum install -y nodejs npm git
git clone https://github.com/nimbus-app/server.git /opt/nimbus
cd /opt/nimbus
npm install
systemctl enable nimbus
systemctl start nimbus
```

สคริปต์นั้นติดตั้ง Node.js ดึงโค้ดแอปพลิเคชันล่าสุด ติดตั้ง dependency และเริ่ม service แอปพลิเคชัน ทุก instance ใหม่ที่เปิดจาก AMI ฐานจะรันสคริปต์นี้และขึ้นมาพร้อมเวอร์ชันปัจจุบันของแอปพลิเคชันที่ติดตั้งไว้ — โดยอัตโนมัติ

แนวทางนี้หมายความว่า AMI ยังคงเรียบง่าย (แค่ OS ฐาน) และ UserData จัดการการตั้งค่าแอปพลิเคชัน ข้อแลกเปลี่ยน: สคริปต์ UserData ใช้เวลารัน instance อาจใช้เวลาสามถึงห้านาทีในการบูตและพร้อม สำหรับแอปพลิเคชันที่เวลาเริ่มต้นสำคัญ — สำหรับ Auto Scaling ที่คุณต้องการให้ instance ใหม่พร้อมอย่างรวดเร็ว — การอบแอปพลิเคชันไว้ล่วงหน้าใน AMI ที่กำหนดเองลดเวลาบูตได้อย่างมีนัยสำคัญ

"เดี๋ยวก็ไม่เป็นไรหรอก" Leo พูด เมื่อ Priya ถามเกี่ยวกับเวลาบูต

"เวลาบูตเท่าไหร่?" เธอถาม

"สี่นาที"

"และระหว่างสี่นาทีนั้น instance รันอยู่แต่ไม่ให้บริการทราฟฟิก?"

"ใช่"

"ดังนั้นในระหว่างการพุ่งขึ้นของทราฟฟิกอย่างกะทันหัน เราอาจมีสี่นาทีที่ instance ใหม่ยังไม่ได้ช่วยอะไร?"

Leo มองสคริปต์ UserData ของเขา เขาเริ่มดูวิธีสร้าง AMI ที่กำหนดเอง

**Key Pairs: วิธีเข้าถึงเซิร์ฟเวอร์ที่ถูกต้อง**

จำหายนะ "Admin123" จากบทที่แล้วได้ไหม?

วิธีที่ถูกต้องในการล็อกอินเข้า EC2 instance คือด้วย **key pair**

key pair คือคู่การเข้ารหัส: public key (เก็บโดย AWS บนเซิร์ฟเวอร์) และ private key (ไฟล์ที่คุณดาวน์โหลดและเก็บเป็นความลับ) ในการล็อกอิน คุณใช้ SSH — โปรโตคอลที่ปลอดภัย — ด้วย private key ของคุณ ไม่มีรหัสผ่าน ถ้าคุณทำ private key หาย คุณก็เสียการเข้าถึง ไม่มี "ลืมรหัสผ่าน" สำหรับ SSH

สิ่งนี้สำคัญเพราะ key pair นั้น:

- ไม่ซ้ำกับใคร เป็นของคุณ
- เป็นไปไม่ได้ที่จะเดาทางการเข้ารหัส
- ไม่ถูกเก็บโดย AWS (คุณเก็บ private key)
- เพิกถอนได้ง่าย (ลบ key ออกจากเซิร์ฟเวอร์ สร้างคู่ใหม่)

Priya ตั้งค่าการเข้าถึงแบบ key-based บนเซิร์ฟเวอร์ Nimbus ไว้แล้ว เซิร์ฟเวอร์ Admin123 ถูกปลดระวาง ไม่มีใครเศร้ากับมัน

"แล้วถ้ามีคนพยายามบุกรุกและดักจับ key pair ระหว่างทางล่ะ?" Priya ถาม เธอคิดคำตอบไว้แล้ว: private key ไม่เคยเดินทางผ่านเครือข่าย คุณดาวน์โหลดมันครั้งเดียว คุณเก็บมันไว้ในเครื่อง มันไม่เคยออกจากเครื่องของคุณ

**เกิดอะไรขึ้นถ้าคุณทำ Key Pair หาย**

Leo ถามคำถามนี้ในสัปดาห์ที่สาม ด้วยพลังเฉพาะตัวของคนที่ยังไม่ได้ทำ key pair หายแต่กำลังคิดถึงมัน

"ถ้าผมทำไฟล์ private key หาย จะเกิดอะไรขึ้น?"

"คุณเสียการเข้าถึง SSH ไปยัง instance" Priya พูด

"ถาวรเลยเหรอ?"

"ไม่จำเป็น แต่กระบวนการกู้คืนไม่น่าพอใจ"

กระบวนการกู้คืน: หยุด instance ถอด root EBS volume ของมัน แนบมันกับ instance อื่นที่คุณ *มี* สิทธิ์เข้าถึง mount volume เพิ่ม public key ใหม่ลงในไฟล์ `authorized_keys` บน volume ที่ mount อยู่ ถอดและแนบมันกลับเข้ากับ instance เดิม แล้วรีสตาร์ท

มันใช้ได้ มันใช้เวลาสามสิบถึงหกสิบนาทีและต้องการการดำเนินการอย่างระมัดระวัง ผิดขั้นเดียวคุณก็ทำให้สิ่งต่าง ๆ แย่ลงได้

ทางเลือกอื่น ถ้าแอปพลิเคชันของคุณไม่เก็บอะไรสำคัญไว้บน root volume (เพราะคุณทำตามคำแนะนำในหนังสือเล่มนี้และเก็บข้อมูลใน S3 และ EBS): ยุติ instance และเปิดตัวใหม่จาก AMI สร้าง key pair ใหม่เมื่อคุณทำ

"เก็บ private key ไว้ที่ไหนสักแห่งที่ปลอดภัย" Priya พูด "และไม่เคยบน EC2 instance"

Leo มองโฟลเดอร์เดสก์ท็อปของเขาที่ติดป้ายว่า `AWS_keys` จากนั้นมอง Priya จากนั้นเขาย้ายโฟลเดอร์ไปยังตัวจัดการรหัสผ่านที่เข้ารหัสของเขา

**Security Groups: ไฟร์วอลล์ของ Instance ของคุณ**

เมื่อ EC2 instance เปิดขึ้น มันต้องการ **security group** — ไฟร์วอลล์เสมือนที่ควบคุมว่าทราฟฟิกเครือข่ายใดเข้าถึงมันได้และทราฟฟิกใดที่มันส่งออกได้

security group มีกฎสองชุด: **inbound** (ทราฟฟิกที่เข้ามา) และ **outbound** (ทราฟฟิกที่ออกไป)

โดยค่าเริ่มต้น security group ใหม่บล็อกทราฟฟิก inbound ทั้งหมดและอนุญาตทราฟฟิก outbound ทั้งหมด คุณเพิ่มกฎ inbound เพื่อเปิด port เฉพาะให้กับแหล่งเฉพาะ

สำหรับเว็บเซิร์ฟเวอร์ Nimbus Priya กำหนดค่า:

- อนุญาต TCP port 443 (HTTPS) จาก `0.0.0.0/0` (อินเทอร์เน็ตทั้งหมด)
- อนุญาต TCP port 80 (HTTP) จาก `0.0.0.0/0` (เปลี่ยนเส้นทางไป 443 ในแอปพลิเคชัน)
- อนุญาต TCP port 22 (SSH) จากที่อยู่ IP ของสำนักงานเท่านั้น — ไม่ใช่จากอินเทอร์เน็ต

"เดี๋ยวนะ — แต่ *ทำไม* เราถึงจะจำกัด SSH ไว้แค่ IP ของสำนักงาน?" Maya ถาม

"เพราะถ้า SSH เปิดให้อินเทอร์เน็ตทั้งหมด" Priya พูด "บอตอัตโนมัติจะถล่ม port 22 พยายามผสมข้อมูลประจำตัวยี่สิบสี่ชั่วโมงต่อวัน บันทึกของเราจะเต็มไปด้วยความพยายามที่ล้มเหลว และถ้ามีช่องโหว่ใน SSH daemon เอง ผู้โจมตีทุกคนในโลกก็พยายามใช้ประโยชน์จากมันได้"

"แต่ถ้า Leo ต้องการล็อกอินจากบ้านล่ะ?"

"VPN" Priya พูด

Leo ตั้งค่า VPN ไว้แล้ว เขามีสีหน้าของคนที่เคยถูกถามคำถามนี้มาก่อน

ฐานข้อมูลยังอยู่บนเครื่องเดียวกับแอปพลิเคชัน — แต่ Priya เตรียม security group แยกต่างหากไว้สำหรับวันที่มันจะไม่อยู่: port ฐานข้อมูลเปิดเฉพาะทราฟฟิกจาก security group ของเว็บเซิร์ฟเวอร์ — ไม่ใช่จากอินเทอร์เน็ต ไม่ใช่จาก SSH (สำหรับการเข้าถึง DB โดยตรง) ไม่ใช่จากที่อื่นใด ในระหว่างนั้น เธอทำให้แน่ใจว่า security group ของ instance ที่แชร์กันไม่เปิด port ฐานข้อมูลให้อินเทอร์เน็ตเลย ฐานข้อมูลจะมองไม่เห็นสำหรับทุกอย่างยกเว้นแอปพลิเคชันที่ต้องการมัน

ในการเข้าถึงฐานข้อมูลโดยตรง ผู้โจมตีต้องบุกรุกเว็บเซิร์ฟเวอร์ก่อน นั่นคือชั้นป้องกันชั้นแรก

"การยืนยันตัวตนแบบ IAM สำหรับฐานข้อมูล และการเข้ารหัสระหว่างการส่ง"

เธอเพิ่มทั้งสองอย่างลงในรายการตรวจสอบการตั้งค่า

**EC2 Instance Metadata และ IMDSv2**

มีอีกหนึ่งส่วนของความปลอดภัย EC2 ที่สำคัญในทางปฏิบัติ แม้ว่ามันจะแทบไม่เคยถูกอธิบายในเนื้อหาเบื้องต้น

เมื่อแอปพลิเคชันรันบน EC2 instance มันสามารถสืบค้น endpoint ภายในพิเศษที่ `http://169.254.169.254/latest/meta-data/` เพื่อดึงข้อมูลเกี่ยวกับ instance: instance ID ของมัน Region ของมัน availability zone ของมัน และ — ที่สำคัญ — ข้อมูลประจำตัว IAM ชั่วคราวที่เชื่อมโยงกับ IAM Role ที่แนบอยู่

นี่คือวิธีที่แอปพลิเคชันบน EC2 instance เรียก AWS service โดยไม่มีข้อมูลประจำตัวที่ฮาร์ดโค้ดไว้ มันถามบริการ metadata: "ฉันควรใช้ข้อมูลประจำตัวอะไรในตอนนี้?" บริการ metadata ส่งคืนข้อมูลประจำตัวชั่วคราวที่หมดอายุและหมุนเวียนโดยอัตโนมัติ

ปัญหาด้านความปลอดภัย: บริการ metadata เวอร์ชันเก่า (IMDSv1) จะตอบสนองต่อคำขอใด ๆ จากกระบวนการใด ๆ บน instance ถ้าแอปพลิเคชันมีช่องโหว่ server-side request forgery (SSRF) — บั๊กที่ผู้โจมตีทำให้เซิร์ฟเวอร์ดึง URL ที่ผู้โจมตีเลือกได้ — ผู้โจมตีก็ใช้ช่องโหว่นั้นในการดึง `http://169.254.169.254/latest/meta-data/iam/security-credentials/` และดึงข้อมูลประจำตัว IAM ของ instance ได้

การโจมตีนี้ถูกใช้ในการละเมิดจริง

**IMDSv2** (Instance Metadata Service version 2) แก้ปัญหานี้โดยกำหนดให้มี session token ก่อนที่บริการ metadata จะตอบสนอง token ได้มาผ่านคำขอ PUT การโจมตี SSRF ซึ่งโดยทั่วไปใช้คำขอ GET ทำขั้นตอน PUT ให้สมบูรณ์ไม่ได้ — ดังนั้นพวกมันจึงได้ token ไม่ได้ และ metadata ก็ไม่ถูกส่งคืน

**วงจรชีวิตของ Instance: ไม่ใช่ตลอดไป**

นี่คือสิ่งที่ผู้เริ่มต้นหลายคนพลาด

EC2 instance ไม่ถาวรโดยค่าเริ่มต้น เมื่อคุณหยุด instance ทรัพยากรคอมพิวต์จะถูกปล่อย เมื่อคุณเริ่มมันอีกครั้ง มันอาจรันบนฮาร์ดแวร์ทางกายภาพคนละตัว ข้อมูลใด ๆ ที่เก็บไว้ *บนตัว instance เอง* (บน root volume ของมัน) รอดผ่านวงจร stop/start — แต่ที่อยู่ IP สาธารณะเปลี่ยน

เมื่อคุณ *ยุติ (terminate)* instance มันก็หายไป เว้นแต่คุณจะมีพื้นที่จัดเก็บแยกต่างหากที่แนบอยู่ (ซึ่งเราครอบคลุมในบทที่ 6) ข้อมูลใด ๆ บน instance ก็หายไป

สี่สถานะที่ EC2 instance อยู่ได้:

**Pending**: instance กำลังเริ่มต้น มันได้รับการจัดสรรฮาร์ดแวร์แล้วแต่ยังบูตไม่เสร็จ

**Running**: instance ทำงานและเข้าถึงได้ คุณกำลังจ่ายเงินสำหรับมัน ในการบูตครั้งแรก นี่คือเวลาที่สคริปต์ UserData รันด้วย

**Stopping/Stopped**: instance ถูกปิด root volume EBS ถูกเก็บรักษาไว้ คุณไม่ได้จ่ายค่าคอมพิวต์ แต่คุณยังจ่ายค่าพื้นที่จัดเก็บ EBS ที่แนบอยู่

**Shutting-down/Terminated**: instance กำลังถูกลบ เว้นแต่คุณจะกำหนดค่า volume EBS ให้คงอยู่ ข้อมูลของพวกมันก็หายไป

"ความชั่วคราว" นี้จริง ๆ แล้วเป็นคุณสมบัติ ไม่ใช่ข้อบกพร่อง มันหมายความว่าคุณเปิดเซิร์ฟเวอร์ ใช้มัน และทิ้งมันได้ มันเปิดให้มีการขยายแบบแนวนอน แต่มันก็หมายความว่าคุณไม่ควรเก็บข้อมูลสำคัญ *บน* ตัว EC2 instance เอง

แล้วข้อมูลอยู่ที่ไหน?

ในพื้นที่จัดเก็บแยกต่างหาก เราจะมาถึงเรื่องนั้นในสองบทถัดไป

คุณอาจสงสัย: ถ้า instance ได้ที่อยู่ IP ใหม่ทุกครั้งที่รีสตาร์ท แอปพลิเคชันของคุณจะรักษาที่อยู่ที่เสถียรได้อย่างไร? AWS มีทางออกเรียกว่า Elastic IP — IP สาธารณะแบบสแตติกที่คุณเป็นเจ้าของและที่อยู่เดิมแม้หลังการรีสตาร์ท หมายเหตุเรื่องต้นทุน: ตั้งแต่กุมภาพันธ์ 2024 AWS เรียกเก็บค่าธรรมเนียมรายชั่วโมงเล็กน้อยสำหรับทุกที่อยู่ IPv4 สาธารณะ — Elastic IP (แนบอยู่หรือไม่) และ IP สาธารณะที่กำหนดอัตโนมัติบน instance เหมือนกัน IPv4 สาธารณะไม่ฟรีอีกต่อไป ซึ่งเป็นอีกเหตุผลหนึ่งที่ควรเก็บ instance ไว้ใน subnet ส่วนตัวหลัง load balancer

สำหรับแอปพลิเคชันที่อยู่หลัง load balancer — ซึ่งเป็นสถาปัตยกรรมที่ถูกต้องสำหรับเว็บแอปพลิเคชัน production ใด ๆ — คุณไม่ต้องการ Elastic IP เลย ผู้ใช้เชื่อมต่อกับชื่อ DNS ที่เสถียรของ load balancer load balancer เชื่อมต่อกับ instance ด้วยที่อยู่ IP ส่วนตัวของพวกมันภายใน VPC instance มาและไป ได้ IP ใหม่ ขยายเข้าและออก — load balancer จัดการมันทั้งหมดอย่างโปร่งใส Elastic IP มีไว้สำหรับกรณีการใช้งานเฉพาะ: เซิร์ฟเวอร์ที่ไคลเอนต์เชื่อมต่อโดยตรงด้วย IP, bastion host ที่มีที่อยู่เสถียร, แอปพลิเคชันที่ไม่ได้อยู่หลัง load balancer ด้วยเหตุผลเฉพาะบางอย่าง

**"Elastic" หมายความว่าอะไร**

เราบอกว่า EC2 ย่อมาจาก Elastic Compute Cloud อะไรที่ elastic เกี่ยวกับมัน?

สองสิ่ง:

**ความยืดหยุ่นแนวตั้ง (Vertical elasticity)**: คุณเปลี่ยนขนาดของ instance ได้ หยุด instance เปลี่ยนมันจาก `t3.micro` เป็น `t3.xlarge` รีสตาร์ทมัน CPU และหน่วยความจำมากขึ้น แอปพลิเคชันเดียวกัน การตั้งค่าเดียวกัน

**ความยืดหยุ่นแนวนอน (Horizontal elasticity)**: คุณเพิ่ม instance ได้มากขึ้น แทนที่จะเป็นเซิร์ฟเวอร์ใหญ่หนึ่งเครื่อง รันเซิร์ฟเวอร์กลางสิบเครื่องหลัง load balancer เมื่อทราฟฟิกลดลง ลบ instance และหยุดจ่ายเงินสำหรับพวกมัน

## จุดแข็งและข้อจำกัด

**ทำไม EC2 จึงทรงพลัง**:

- การควบคุมเต็มรูปแบบ คุณเลือก OS ซอฟต์แวร์ การกำหนดค่า มันคือคอมพิวเตอร์ของคุณ
- การกำหนดขนาดที่ยืดหยุ่น instance หลายร้อยประเภทครอบคลุมทุกกรณีการใช้งาน
- ไม่มีฮาร์ดแวร์ให้จัดการ AWS จัดการชั้นกายภาพ
- การเรียกเก็บเงินรายวินาที โดยมีขั้นต่ำ 60 วินาที สำหรับ AMI ของ Amazon Linux, Windows และ Ubuntu (AMI ของ Linux เชิงพาณิชย์บางอัน เช่น RHEL และ SUSE ยังเรียกเก็บรายชั่วโมง — ตรวจสอบเงื่อนไขการเรียกเก็บเงินของ AMI) คุณหยุด instance คุณหยุดจ่าย
- ทำงานกับทุกอย่าง EC2 เป็นรากฐานที่ AWS service อื่น ๆ ส่วนใหญ่สร้างขึ้นบนมัน
- โมเดลการกำหนดราคาหลายแบบ (On-Demand, Reserved, Spot) ช่วยให้เพิ่มประสิทธิภาพต้นทุน
  ได้อย่างมากสำหรับเวิร์กโหลดที่คาดเดาได้หรือยืดหยุ่น — ครอบคลุมรายละเอียดในบทที่ 27

**ที่ซึ่งมันเริ่มซับซ้อน**:

- คุณรับผิดชอบในการ patch และอัปเดตระบบปฏิบัติการ (โมเดลความรับผิดชอบร่วมกัน —
  นี่คือส่วน "ในคลาวด์" ที่เป็นของคุณ)
- การ patch OS ไม่ใช่ทางเลือก EC2 instance ที่ไม่ได้ patch เป็นหนึ่งในช่องทาง
  การโจมตีที่พบบ่อยที่สุดในการละเมิดคลาวด์ AWS Systems Manager Patch Manager
  ทำให้สิ่งนี้เป็นอัตโนมัติได้ — แต่คุณต้องกำหนดค่ามันและมอนิเตอร์มัน
- การจัดการ EC2 ในระดับขนาดใหญ่หมายถึงการจัดการสถานะ instance, AMI, security patch
  และวงจรชีวิตข้ามเครื่องที่อาจมีหลายพันเครื่อง นั่นคือภาระในการดำเนินงาน
- EC2 ไม่ใช่คำตอบที่ถูกต้องสำหรับทุกอย่าง สำหรับโค้ดที่ขับเคลื่อนด้วยเหตุการณ์ที่รัน
  ไม่บ่อย Lambda (บทที่ 20) ถูกกว่าและง่ายกว่า สำหรับเวิร์กโหลดแบบคอนเทนเนอร์
  ECS และ EKS (บทที่ 21) ให้ประสิทธิภาพทรัพยากรที่ดีกว่า
- instance ที่ไม่ได้ใช้ก็ยังมีต้นทุน ถ้าคุณหยุด instance คุณหยุดจ่ายค่าคอมพิวต์ —
  แต่ถ้าคุณมีพื้นที่จัดเก็บแนบอยู่ คุณก็ยังจ่ายค่ามัน

**การตัดสินใจว่าเมื่อไหร่ไม่ควรใช้ EC2**: EC2 ให้การควบคุมสูงสุด — แต่การควบคุมมีต้นทุนในการดำเนินงาน ทุก EC2 instance ที่คุณรันเป็นสิ่งที่คุณต้อง patch มอนิเตอร์ และในที่สุดต้องเปลี่ยน สำหรับแอปพลิเคชันที่รันไม่บ่อย (Lambda ถูกกว่า) สำหรับแอปพลิเคชันที่ต้องขยายแนวนอนไปหลายสิบหรือหลายร้อย instance (คอนเทนเนอร์มีประสิทธิภาพกว่า) หรือสำหรับฐานข้อมูลและเวิร์กโหลดที่มีการจัดการอื่น ๆ (RDS, ElastiCache) บริการที่มีการจัดการเต็มรูปแบบขจัดภาระในการดำเนินงานที่มีนัยสำคัญด้วยส่วนเพิ่มของต้นทุนที่พอประมาณ EC2 เป็นทางเลือกที่ถูกต้องเมื่อคุณต้องการการควบคุมที่มันให้ — ไม่ใช่โดยปริยาย

Priya มีหลักการง่าย ๆ: "ถ้าเราจะพอใจกับบริการที่มีการจัดการที่ทำสิ่งที่เราต้องการ ใช้บริการที่มีการจัดการ ใช้ EC2 เมื่อตัวเลือกที่มีการจัดการไม่มีหรือไม่เหมาะ"

ตอนแรก Leo คัดค้านเรื่องนี้ "แต่ EC2 ให้ตัวเลือกเรามากกว่า"

"ตัวเลือกคือภาระ" Priya พูด "เราไม่ต้องการทุกตัวเลือก เราต้องการการกำหนดค่าที่ถูกต้อง บำรุงรักษาอย่างน่าเชื่อถือ"

**EC2 Placement Groups: การควบคุมว่า Instance ไปอยู่ที่ไหน**

EC2 ให้คุณควบคุมว่า instance ของคุณคืออะไร — ขนาดของมัน OS ของมัน การกำหนดค่าของมัน มันยังให้การควบคุมแบบจำกัดว่า *ที่ไหน* ที่มันไปอยู่ทางกายภาพ ผ่านฟีเจอร์ที่เรียกว่า **placement groups**

โดยค่าเริ่มต้น AWS กระจาย instance ข้ามฮาร์ดแวร์ทางกายภาพเพื่อให้ความพร้อมใช้งานสูงสุด แต่สำหรับเวิร์กโหลดบางอย่าง คุณต้องการลบล้างค่าเริ่มต้นนั้น — ไม่ว่าจะเพื่อให้ instance อยู่ใกล้กันมากขึ้น หรือเพื่อรับประกันว่าพวกมันอยู่ห่างกัน

placement group สามประเภท:

**Cluster**: บรรจุ instance ไว้ใกล้กันภายใน Availability Zone เดียว โดยทั่วไปบนแร็คทางกายภาพเดียวกันหรือฮาร์ดแวร์ที่อยู่ติดกัน ผลลัพธ์คือความหน่วงเครือข่ายต่ำที่สุดและทรูพุตเครือข่ายสูงที่สุดระหว่าง instance ในกลุ่ม — ด้วยทรูพุตเครือข่าย 10 Gbps หรือสูงกว่าระหว่าง instance (อย่าสับสนกับ Enhanced Networking/ENA ซึ่งเป็นฟีเจอร์เครือข่ายต่อ instance ที่เป็นอิสระจาก placement group) นี่คือทางเลือกสำหรับ HPC (high-performance computing), งานฝึก ML ขนาดใหญ่ และเวิร์กโหลดแบบขนานที่จับคู่กันแน่นซึ่ง instance ใช้เวลามากในการส่งข้อมูลให้กัน ข้อแลกเปลี่ยนคือความพร้อมใช้งาน: ถ้าส่วนของฮาร์ดแวร์ที่อยู่เบื้องล่างล้มเหลว instance ทั้งหมดในคลัสเตอร์อาจได้รับผลกระทบพร้อมกัน

**Partition**: แบ่ง instance ข้ามพาร์ติชันเชิงตรรกะ ที่แต่ละพาร์ติชันอยู่บนชุดฮาร์ดแวร์ของตัวเอง — แร็คแยก พลังงานแยก สวิตช์เครือข่ายแยก instance ภายในพาร์ติชันแชร์ฮาร์ดแวร์กัน แต่พาร์ติชันไม่เคยแชร์ฮาร์ดแวร์กับพาร์ติชันอื่น การออกแบบนี้จำกัดรัศมีความเสียหายของความล้มเหลวของฮาร์ดแวร์: แร็คที่ล่มส่งผลต่อพาร์ติชันหนึ่งแต่ไม่ใช่อันอื่น partition placement group ถูกสร้างขึ้นสำหรับเวิร์กโหลดแบบกระจายและจำลองขนาดใหญ่ — Apache Hadoop, Apache Cassandra, Apache Kafka — ที่คุณต้องการการแยกความล้มเหลวให้เพียงพอที่ความล้มเหลวระดับแร็คจะไม่ทำให้ทั้งคลัสเตอร์ของคุณล่ม

**Spread**: วางแต่ละ instance บนฮาร์ดแวร์ที่อยู่เบื้องล่างที่แยกกันโดยสิ้นเชิง การแยกสูงสุดระหว่าง instance ถ้าคุณมี instance แอปพลิเคชันสำคัญห้าตัวที่ต้องไม่แชร์โฮสต์ทางกายภาพเดียวกัน (เพราะความล้มเหลวของฮาร์ดแวร์ครั้งเดียวไม่ควรทำให้มากกว่าหนึ่งตัวล่ม) Spread คือคำตอบ ขีดจำกัด: **7 instance ต่อ Availability Zone ต่อ placement group** Spread ออกแบบมาสำหรับ instance สำคัญจำนวนน้อยที่ทนการอยู่ร่วมกันไม่ได้ ไม่ใช่สำหรับฟลีตขนาดใหญ่

"ดังนั้น Cluster มีไว้สำหรับความเร็ว Spread มีไว้สำหรับการแยก และ Partition มีไว้สำหรับระบบกระจายที่ต้องการทั้งการรวมกลุ่มบ้างและการแยกบ้าง?" Maya ถาม

"ใกล้เคียงพอ" Priya พูด "Cluster: ความหน่วงต่ำระหว่าง instance ความเสี่ยงใหญ่อันเดียว Spread: การแยกสูงสุด ขีดจำกัดตายตัวเจ็ดตัวต่อ AZ Partition: การแยกแบบมีโครงสร้างสำหรับระบบกระจายขนาดใหญ่ — คุณควบคุมว่าแต่ละ instance ไปอยู่ในพาร์ติชันไหน"

สำหรับสถาปัตยกรรมปัจจุบันของ Nimbus ยังไม่มีอันไหนที่ใช้ได้ แต่การรู้ว่าพวกมันมีอยู่หมายถึงการรู้ว่าเมื่อไหร่ควรเอื้อมไปหยิบพวกมัน — และที่เฉพาะหน้ากว่านั้น การรู้ว่าคำถามสอบเกี่ยวกับ "เวิร์กโหลด HPC ที่ต้องการความหน่วงระหว่างโหนดต่ำ" จริง ๆ แล้วกำลังถามถึงอะไร

## สรุป

instance ที่เปิดขึ้นโดยบังเอิญไม่มีทางจะเป็นเซิร์ฟเวอร์ production การเข้าใจ EC2 อย่างถูกต้องไม่ได้แค่แก้ปัญหากำลังการผลิต — มันแนะนำชุดแนวคิดใหม่ที่จะปรากฏในเกือบทุกบทถัดไป ประเภท instance, AMI, key pair, security group และการกำหนดขนาดให้เหมาะสมไม่ใช่เกร็ดความรู้ EC2 พวกมันคือคำศัพท์ที่หนังสือส่วนที่เหลือถูกสร้างขึ้น เรียนรู้พวกมันที่นี่แล้วทุกอย่างอื่นก็จะเข้าใจง่ายขึ้น

- **EC2 instance** คือเครื่องเสมือนที่คุณเช่าใน AWS ประเภท instance จัดระเบียบตามกรณีการใช้งาน: general purpose, compute optimized, memory optimized, storage optimized เลือกตระกูลที่ถูกต้องและกำหนดขนาดให้เหมาะกับเมตริกเวิร์กโหลดจริง — ไม่ใช่กรณีเลวร้ายที่สุดที่จินตนาการขึ้น
- **AMI** (Amazon Machine Image) คือเทมเพลตสำหรับ OS และการกำหนดค่าเริ่มต้นของ instance ของคุณ AMI ที่กำหนดเองเปิดให้มีการ deploy ที่สอดคล้องและทำซ้ำได้
- **Key pair** คือวิธีที่ปลอดภัยในการเข้าถึง EC2 instance **Security group** คือไฟร์วอลล์ของ instance ของคุณ — จำกัด SSH ไว้ที่ IP ที่รู้จักและล็อก port ฐานข้อมูลไว้ที่ security group ของแอปพลิเคชันเท่านั้น
- **IMDSv2** ควรเปิดใช้งานบนทุก instance เพื่อป้องกันการขโมยข้อมูลประจำตัวจากบริการ metadata ของ instance ที่อาศัย SSRF
- EC2 instance ไม่ถาวรโดยค่าเริ่มต้น instance ที่ถูกยุติจะเสียข้อมูลในเครื่อง — เก็บข้อมูลสำคัญใน S3 หรือ EBS ไม่ใช่บนดิสก์ของ instance

## เคล็ดลับการสอบ

*SAA-C03 Domain 3 — Task 3.2 (โซลูชันคอมพิวต์ประสิทธิภาพสูง)*

- **ความรับผิดชอบร่วมกันสำหรับ EC2**: คุณรับผิดชอบในการ patch OS
  AWS ดูแลฮาร์ดแวร์ทางกายภาพและ hypervisor นี่คือความแตกต่างที่ถูกทดสอบบ่อย
- **ตระกูล instance สำคัญสำหรับคำถามสถานการณ์** ถ้าสถานการณ์กล่าวถึงความต้องการ
  หน่วยความจำสูง (แคชในหน่วยความจำ, SAP HANA) คำตอบน่าจะเกี่ยวข้องกับ
  instance ที่ปรับเพื่อหน่วยความจำ ถ้ามันกล่าวถึงการประมวลผลแบบ batch หรือ HPC ก็ปรับเพื่อการประมวลผล
- **Stopping ≠ Terminating** การหยุด instance รักษามันไว้ (คุณรีสตาร์ทได้)
  การยุติลบมัน สถานการณ์การสอบทดสอบว่าคุณรู้ความแตกต่างนี้หรือไม่
- **IP สาธารณะเปลี่ยนเมื่อรีสตาร์ท** ถ้าแอปพลิเคชันของคุณต้องการที่อยู่ IP ที่เสถียร
  ใช้ **Elastic IP** — IP สาธารณะแบบสแตติกที่ยังเชื่อมโยงกับบัญชีของคุณ
  ตั้งแต่กุมภาพันธ์ 2024 AWS เรียกเก็บค่าทุกที่อยู่ IPv4 สาธารณะรายชั่วโมง — Elastic IP
  (แนบอยู่หรือไม่) และ IP สาธารณะที่กำหนดอัตโนมัติเหมือนกัน
- โมเดลการกำหนดราคา **On-Demand, Reserved และ Spot** ถูกทดสอบหนักใน Domain 4
  เราครอบคลุมพวกมันในบทที่ 27 สำหรับตอนนี้ รู้ว่า On-Demand หมายถึงการจ่ายรายวินาที
  โดยไม่มีข้อผูกมัด
- **Security group เป็น stateful** ถ้าคุณอนุญาตทราฟฟิก inbound บน port หนึ่ง
  ทราฟฟิกที่ส่งกลับจะถูกอนุญาตโดยอัตโนมัติโดยไม่ต้องมีกฎ outbound ที่ชัดเจน NACL
  (ครอบคลุมในบทที่ 15) เป็น stateless — พวกมันต้องการทั้งกฎ inbound และ outbound
- **Placement Groups:** Cluster = ความหน่วงต่ำที่สุดระหว่าง instance (HPC, การฝึก ML — แต่มีความเสี่ยงจุดล้มเหลวเดียวสำหรับกลุ่ม) Partition = ระบบกระจาย (Hadoop, Kafka, Cassandra) พร้อมการแยกความล้มเหลวต่อพาร์ติชัน Spread = การแยก instance สูงสุด สูงสุด 7 ตัวต่อ AZ รูปแบบคำถามสอบ: "เวิร์กโหลด HPC ที่จับคู่กันแน่นต้องการทรูพุตเครือข่ายสูงสุดระหว่างโหนด" → Cluster placement group

## แบบฝึกหัด

**แบบฝึกหัด 1 — การจำ**

ด้วยคำพูดของคุณเอง: EC2 instance คืออะไร? AMI คืออะไร? ความสัมพันธ์ระหว่างพวกมันคืออะไร?

**แบบฝึกหัด 2 — สถานการณ์ SAA-C03**

*สถานการณ์*: บริษัทกำลัง deploy เว็บแอปพลิเคชันที่มีทราฟฟิกสูง แอปพลิเคชันจัดการการค้นหาแคตตาล็อกสินค้าด้วยตรรกะการกรองที่ซับซ้อนซึ่งใช้ CPU หนัก ทีมคาดว่าจะมีการพุ่งขึ้นของทราฟฟิกอย่างมากในช่วงงานลดราคา พวกเขาต้องการให้แน่ใจว่าเลือกประเภท EC2 instance ที่ถูกต้องและพร้อมรับมือกับคลื่นทราฟฟิก

ชุดของทางเลือกใดตอบสนองความต้องการของพวกเขาได้ดีที่สุด?

A) instance ที่ปรับเพื่อหน่วยความจำในจำนวนคงที่เพื่อให้ประสิทธิภาพสม่ำเสมอ  
B) instance ที่ปรับเพื่อการประมวลผลพร้อม Auto Scaling เพื่อรับมือกับการพุ่งขึ้นของทราฟฟิก  
C) instance ทั่วไปด้วยขนาด instance ใหญ่เพียงตัวเดียว  
D) instance ที่ปรับเพื่อพื้นที่จัดเก็บเพราะแคตตาล็อกสินค้าต้องการการเข้าถึงดิสก์ที่เร็ว

**คำใบ้ 1**: เวิร์กโหลดถูกอธิบายว่า "ใช้ CPU หนัก" ตระกูล instance ใดที่ปรับเพื่อ CPU?

**คำใบ้ 2**: สถานการณ์กล่าวถึง "การพุ่งขึ้นของทราฟฟิกในช่วงงานลดราคา" จำนวน instance คงที่จะรับมือกับทราฟฟิกผันแปรได้ไม่อย่างมีประสิทธิภาพ ฟีเจอร์ AWS ใดจัดการสิ่งนี้?

**คำใบ้ 3**: instance ที่ปรับเพื่อการประมวลผลจัดการงานที่ใช้ CPU หนัก Auto Scaling เพิ่มและลบ instance ตามความต้องการ ทั้งสองอย่างรวมกันตอบทั้งสองข้อกำหนด

**คำตอบ**: B

**คำอธิบาย**: instance ที่ปรับเพื่อการประมวลผล (เช่นตระกูล `c`) ให้ CPU ต่อดอลลาร์มากกว่าสำหรับเวิร์กโหลดที่ใช้ CPU หนัก Auto Scaling ปรับจำนวน instance ตามโหลดโดยอัตโนมัติ — เพิ่ม instance ในช่วงงานลดราคา ลบมันเมื่อทราฟฟิกกลับสู่ปกติ ชุดนี้เพิ่มประสิทธิภาพทั้งประสิทธิภาพและต้นทุน

**ทำไมไม่ใช่ A?** instance ที่ปรับเพื่อหน่วยความจำออกแบบสำหรับเวิร์กโหลดที่ต้องการ RAM จำนวนมาก (ฐานข้อมูล แคชในหน่วยความจำ) นี่คือเวิร์กโหลดที่ผูกกับ CPU และจำนวน instance คงที่หมายถึงการจัดสรรเกิน (สิ้นเปลือง) หรือการจัดสรรน้อยเกินไป (ล้มเหลว)

**ทำไมไม่ใช่ C?** instance ทั่วไปแลกประสิทธิภาพ CPU บางส่วนเพื่อความสมดุล สำหรับเวิร์กโหลดที่รู้ว่าใช้ CPU หนัก instance ที่ปรับเพื่อการประมวลผลเหมาะสมกว่า และ instance ใหญ่ตัวเดียวคือจุดล้มเหลวเดียว

**ทำไมไม่ใช่ D?** คอขวดคือ CPU ไม่ใช่ disk I/O instance ที่ปรับเพื่อพื้นที่จัดเก็บออกแบบสำหรับเวิร์กโหลดที่ต้องการทรูพุตสูงมากไปยังพื้นที่จัดเก็บในเครื่อง
