**คำถาม**

สถาปนิกคืออะไร?

ไม่ใช่ตำแหน่ง ไม่ใช่ org chart ไม่ใช่ประสบการณ์หลายปีที่ระบุไว้ใน job description สิ่งจริงๆ

ในสิบสี่เดือนนับตั้งแต่รอบการระดมทุน ทั้งสี่คนกลายเป็นผู้รับผิดชอบอย่างเป็นทางการหรือไม่เป็นทางการสำหรับการตัดสินใจสถาปัตยกรรมที่ Nimbus Maya เป็น CTO อย่างเป็นทางการ Tom เป็น Head of Infrastructure Priya ดูแลทีม platform Leo เป็น Principal Engineer ซึ่งหมายความว่าเขาถูกปรึกษาในทุกเรื่องและไม่ได้เป็นเจ้าของสิ่งเฉพาะใด ซึ่งเขาพบว่าทั้งเป็นอิสระและบางครั้งทำให้หงุดหงิด

ไม่มีใครคาดว่าจะมาถึงที่นี่ Maya เป็น developer Tom เป็น systems administrator ที่คิดว่าจะอยู่ต่อไป Priya มีปริญญาโทด้านวิทยาการคอมพิวเตอร์และใช้เวลาสองปีเขียน mobile apps Leo ออกจากโปรแกรมคณิตศาสตร์และสอนตัวเองเขียนโค้ด

ไม่มีสิ่งใดนั้นเป็น job description สำหรับ "สถาปนิก"

"นี่คือสิ่งที่ผมคิดว่ามันคือ" Priya พูด "สถาปนิกคือคนที่ยอมรับว่าตนเองรับผิดชอบต่อผลลัพธ์ของการตัดสินใจของพวกเขา ไม่ใช่แค่การตัดสินใจเอง"

"พูดเพิ่มเติม" Leo พูด

"เมื่อคุณอยู่ต้นๆ ของอาชีพ คุณตัดสินใจและก้าวไปข้างหน้า คุณ implement มันหรือไม่ก็ได้ มีคนอื่น review มัน อนุมัติมัน deploy มัน ผลลัพธ์ของการผิดพลาดคือมีคนข้างบนจับข้อผิดพลาด"

"และต่อมา?"

"ต่อมา ไม่มีใครอยู่ข้างบน การตัดสินใจถูกส่ง ผลลัพธ์คือ production"

Tom พยักหน้าช้าๆ "นั่นคือเมื่อคุณเริ่มคิดต่างออกไป ไม่ใช่เพราะคุณรู้มากกว่า แม้ว่าคุณจะรู้ แต่เพราะ blast radius ของการผิดพลาดเปลี่ยนไป"

**การก้าวหน้าจาก Junior สู่สถาปนิก: การก้าวหน้าจริง**

การก้าวหน้าจาก junior engineer สู่สถาปนิกไม่ใช่เส้นตรงของความรู้ที่สะสม มันคือชุดการเปลี่ยนแปลงในวิธีที่คุณเข้าใจงานของคุณ

*Junior engineers* ถามว่า: ผมจะทำให้สิ่งนี้ทำงานได้อย่างไร? คำถามหลักของพวกเขาคือ implementation ตาม requirement ทำให้ระบบทำงานได้อย่างไร? นี่คือทักษะสำคัญแรก ทุกอย่างพักอยู่บนมัน

*Mid-level engineers* ถามว่า: ผมจะทำให้สิ่งนี้ทำงานได้อย่างถูกต้องอย่างไร? คำถามขยายครอบคลุมความถูกต้อง ไม่ใช่แค่ "มันรันได้" แต่ "มันจัดการกับ edge cases, error conditions, unexpected inputs ได้ไหม" พวกเขาเริ่มคิดเรื่อง testing พวกเขาเริ่มคิดเรื่อง maintenance

*Senior engineers* ถามว่า: ผมจะทำให้สิ่งนี้ทำงานได้อย่างถูกต้อง *และ* ยั่งยืนอย่างไร? time horizon ขยาย พวกเขาคิดเรื่องวิศวกรที่จะอ่านโค้ดนี้ในหนึ่งปี พวกเขาคิดเรื่องระบบที่จะรองรับโหลดสิบเท่าปัจจุบัน พวกเขาคิดเรื่องสิ่งที่เกิดขึ้นเมื่อ dependency เปลี่ยน

*Staff และ principal engineers* ถามว่า: ทำไมเราถึงสร้างสิ่งนี้เลย? พวกเขาถอยออกจาก implementation และตั้งคำถามกับ premise นี่คือปัญหาที่ถูกต้องที่จะแก้ไหม? ถึงเวลาที่ถูกต้องที่จะแก้ไหม? มีแนวทางที่เรียบง่ายกว่าที่ยอมแลก sophistication เพื่อ survivability ไหม?

*สถาปนิก* ถามว่า: อะไรที่แตกก่อน เราจะรู้ได้อย่างไร และใครจะทำอะไรตอนตี 3 เมื่อมันทำ?

"คำถามตี 3" Leo พูด "Carlos ใช้อันนั้น"

"เพราะมันเป็นความจริง" Priya พูด "นั่นคือการทดสอบ คุณสามารถเขียน runbook ได้ไหม? คุณเข้าใจ failure modes ดีพอที่จะเขียนขั้นตอนสำหรับคนที่ง่วงครึ่งหลับและอยู่ภายใต้แรงกดดันไหม?"

**สิ่งที่ไม่เปลี่ยนแปลง**

มีสิ่งที่สถาปนิกรู้ที่ junior engineers ไม่รู้ พฤติกรรมเฉพาะของบริการ ลักษณะความล้มเหลวในระดับขนาดใหญ่ พลวัตองค์กรในการอนุมัติการตัดสินใจ ประวัติการตัดสินใจที่ทำในบริบทที่คล้ายกันซึ่งไม่ได้ผล

แต่ความรู้ไม่ใช่สิ่งสำคัญ

สิ่งสำคัญคือชุดคำถามเริ่มต้น model ความคิดที่เปิดใช้งานเมื่อมีคนอธิบายปัญหา

Junior engineers ได้ยินปัญหาและคิดเรื่องโซลูชัน สถาปนิกได้ยินปัญหาและคิดเรื่อง constraints, failure modes และช่องว่างระหว่างสิ่งที่ธุรกิจบอกว่าต้องการกับสิ่งที่มันต้องการจริงๆ

ไม่ใช่เพราะพวกเขาเย็นชากว่า

แต่เพราะพวกเขากำลังพยายามปกป้องคนที่จะต้องอยู่กับผลลัพธ์

"มันไม่ใช่ว่าเราเรียนรู้มากกว่า" Tom พูด "เราถามคำถามต่างกันก่อน"

Maya นิ่งสักพัก เธอพูดว่า: "เมื่อผมคุยกับวิศวกรใหม่คนนั้น ผมตระหนักว่าสิ่งที่ผมพยายามจะพูดจริงๆ คือ เขาถามวิธีเป็นสถาปนิก และผมต้องการพูดว่า: เริ่มด้วยการสังเกตว่าอะไรพัง ไม่ใช่แค่เมื่อบางอย่างพังแล้ว แต่ก่อนหน้า ระหว่างการออกแบบ ระหว่างการ review ถาม: อะไรที่แตกก่อน เราจะรู้ได้อย่างไร ใครที่เราโทร?"

"นั่นไม่ใช่ตำแหน่ง" Leo พูด "นั่นคือนิสัย"

"ใช่"

**Ownership**

อีกสิ่งหนึ่ง ทุกคนเห็นด้วย คือ ownership

ไม่ใช่ ownership ในแง่กฎหมาย Ownership ในแง่จิตวิทยา: ความรู้สึกที่ว่าถ้าระบบนี้เสื่อมลง คุณจะเป็นคนที่ใส่ใจมากที่สุด

ต้นๆ ของอาชีพ นี่ไม่ใช่ท่าทีที่คาดหวัง คุณรับผิดชอบต่อ tickets, PRs, stories ที่ถูก assign ระบบเป็นของคนอื่น

ต่อมา ขอบเขตละลาย ระบบเป็นของคุณ ไม่ใช่ของคุณคนเดียว — แชร์ เสมอแชร์ — แต่เป็นของคุณในแง่ที่คุณรู้สึกถึงความล้มเหลวของมันเป็นการส่วนตัว เหตุการณ์ production ตี 2 ไม่ใช่การขัดจังหวะชีวิต มันเป็นส่วนหนึ่งของงาน

"นั่นคือการเปลี่ยนแปลงที่ผมไม่สามารถสอนใครได้" Tom พูด "คุณต้องรู้สึก outages สักไม่กี่ครั้ง คุณต้องเป็นคนที่ไม่จับ failure mode ก่อนที่มันจะถึง production นั่นคือเมื่อคำถามเปลี่ยน"

"บางคนไม่เกิดการเปลี่ยนแปลงนั้น" Priya พูด "วิศวกรที่ดี วิศวกรที่ยอดเยี่ยม พวกเขาทำงานที่ยอดเยี่ยมภายใน scope ที่กำหนดและระมัดระวังและน่าเชื่อถือภายในนั้น พวกเขาไม่รู้สึก ownership นั่นไม่ใช่ความล้มเหลวทางศีลธรรม มันแค่เป็นความสัมพันธ์ที่ต่างออกไปกับงาน"

"และสถาปนิกต้องรู้สึกมัน" Maya พูด

"สถาปนิกรู้สึกมันโดย default" Priya พูด "แม้เมื่อพวกเขาหยุดพัก โดยเฉพาะตอนนั้น"

**Technical Breadth vs. Depth**

มีคำถามที่ถูกถามในทุก architecture interview: คุณเป็น generalist หรือ specialist?

คำตอบที่ซื่อสัตย์คือ: อย่างเดียวไม่เพียงพอ

สถาปนิกต้องการ depth เพียงพอที่จะรู้ว่าตนเองไม่รู้อะไร — เพื่อรู้จักเมื่อปัญหาอยู่ที่ขอบความรู้ของพวกเขา เมื่อควรนำคนที่มีความเชี่ยวชาญเฉพาะมากกว่าเข้ามา คุณไม่รู้ว่าเมื่อไหร่ควรโทรหาผู้เชี่ยวชาญฐานข้อมูลถ้าคุณไม่เข้าใจฐานข้อมูลดีพอที่จะรู้ว่าคุณขาดอะไร

และสถาปนิกต้องการ breadth เพียงพอที่จะเชื่อมสิ่งต่างๆ ระบบที่พวกเขาออกแบบครอบคลุมโดเมน: storage และ compute และ network และ security และ observability และต้นทุน การตัดสินใจในพื้นที่หนึ่งมีผลลัพธ์ในอีกพื้นที่ คุณไม่สามารถ optimize networking costs โดยไม่เข้าใจพฤติกรรมแอปพลิเคชัน คุณไม่สามารถออกแบบ data model โดยไม่เข้าใจ access patterns คุณไม่สามารถเลือก deployment model โดยไม่เข้าใจ failure modes

"มันไม่ใช่ depth หรือ breadth" Leo พูด "มันคือ depth ในบางสิ่งและ awareness ของทุกอย่าง"

"T-shaped" Priya พูด

"ผมเคยเกลียด metaphor นั้นเสมอ" เขาพูด "แต่ใช่"

**Trade-off Reasoning**

สิ่งที่สถาปนิกพูดบ่อยที่สุดคือ: มันขึ้นอยู่กับ

ความผิดพลาดคือพูดมันโดยไม่จบประโยค

*มันขึ้นอยู่กับ access pattern* มันขึ้นอยู่กับ scale มันขึ้นอยู่กับผลลัพธ์ของความล้มเหลว มันขึ้นอยู่กับ operational capacity ของทีม มันขึ้นอยู่กับ cost constraint มันขึ้นอยู่กับว่าคุณคาดหวังว่าระบบจะอยู่ในรูปแบบปัจจุบันนานแค่ไหน

การจบประโยคคืองาน การจบทุกประโยคเปิดเผยมิติของปัญหาที่มองไม่เห็นมาก่อน ทุกมิติที่ทำให้มองเห็นได้คือการตัดสินใจที่สามารถทำได้อย่างตั้งใจแทนที่จะเป็นโดยบังเอิญ

Priya เขียนรายการไว้สักพักก่อน รายการการตัดสินใจที่ Nimbus ทำโดยบังเอิญ ไม่ใช่อย่างอาฆาตมาดร้าย ไม่ใช่อย่างประมาท แต่โดยไม่เข้าใจอย่างครบถ้วนว่าการตัดสินใจกำลังถูกทำ เธอตรวจสอบมันบางครั้ง มันเป็นเอกสารที่มีประโยชน์

"การตัดสินใจสถาปัตยกรรมที่ดีที่สุดที่ผมเคยเห็น" เธอพูด "คือการที่มีคนพูดว่า: นี่คือตัวเลือกสี่อัน นี่คือ trade-offs นี่คือสิ่งที่ผมแนะนำ นี่คือสิ่งที่จะทำให้ผมเปลี่ยนคำแนะนำ"

"ADR" Leo พูด

"ADR" เธอเห็นด้วย "หรือแค่ประโยคใน Slack message รูปแบบไม่สำคัญ การใช้เหตุผลสำคัญ"

"เพราะการใช้เหตุผลอยู่รอดแม้เมื่อการตัดสินใจถูกกลับมาพิจารณา" Tom พูด

"เพราะการใช้เหตุผลคือความรู้" Maya พูด "การตัดสินใจแค่เป็นผลลัพธ์"

**ความอาวุโสไม่ใช่อะไร**

มันไม่ใช่ tenure คุณสามารถทำงานที่ไหนบางแห่งได้สิบปีและไม่พัฒนา architectural judgment คุณสามารถอยู่มาสามปีและคิดเหมือนสถาปนิก เวลาสัมพันธ์กันเพียงเล็กน้อยกับสิ่งสำคัญ

มันไม่ใช่การรู้ทุกอย่าง มีบริการใน AWS catalog ที่ไม่มีใครในพวกเขาเคยใช้ offerings เฉพาะสำหรับอุตสาหกรรมเฉพาะ features ที่ประกาศและยังไม่ต้องการ นั่นไม่เป็นไร catalog กว้างมาก งานไม่ใช่ความรู้แบบสารานุกรม มันคือการใช้เหตุผลอย่างมีหลักการจากสิ่งที่คุณรู้

มันไม่ใช่การไม่มีข้อสงสัย สถาปนิกสงสัยอยู่ตลอดเวลา พวกเขาถือการตัดสินใจของพวกเขาได้เบากว่า junior engineers เพราะพวกเขาเห็นการตัดสินใจที่ดีล้มเหลวในสถานการณ์ที่ไม่คาดคิดมากพอที่จะรู้ว่าความมั่นใจเป็นเรื่องตามสถานการณ์ "ผมมั่นใจในสิ่งนี้ตาม constraints ปัจจุบัน" คือท่าทีที่ถูกต้อง ไม่ใช่ "ผมถูก"

มันไม่ใช่ความไม่สามารถผิดพลาดได้ Carlos บอกพวกเขา ในการตรวจสอบสถาปัตยกรรมแรกนั้น เกี่ยวกับระบบที่เขาออกแบบที่ล้มเหลวอย่างหายนะเพราะเขาวิเคราะห์ failure mode ผิด เขาอธิบายมันอย่างตรงไปตรงมา ไม่มีการป้องกันตัว "ผมพลาด" เขาพูด "เราเรียนรู้จากมัน ระบบถัดไปไม่มี failure mode นั้น"

"นั่นทำให้เขาน่าเชื่อถือ" Maya พูด เมื่อเธอเล่าเรื่องให้วิศวกรใหม่ฟัง "ไม่ใช่ว่าเขาไม่เคยผิดพลาด แต่เขาผิดพลาด เข้าใจว่าทำไม และนำมันไปข้างหน้า"

**การเปลี่ยนผ่านสู่ Senior**

สำหรับใครก็ตามที่อ่านสิ่งนี้ที่ยังเป็น junior หรือ mid-level ที่อยู่บนเส้นทางสู่การคิดแบบนี้:

การเปลี่ยนผ่านไม่ใช่การทดสอบที่คุณผ่าน มันคือท่าทีที่คุณยอมรับ ค่อยๆ แล้วไม่ยอมแพ้

เริ่มถามคำถามเรื่องความล้มเหลว ในทุกการออกแบบ ในทุกการ review สำหรับทุกระบบที่คุณสัมผัส: *อะไรที่แตกก่อน?* ไม่ใช่สมมุติฐาน — ตามผ่านมัน load balancer ได้รับ request application server ประมวลผลมัน ฐานข้อมูลรับ query อะไรที่แตกก่อนภายใต้โหลด? อะไรที่แตกก่อนถ้า dependency ช้า? อะไรที่แตกก่อนที่ traffic 10x ปัจจุบัน?

เริ่ม own สิ่งต่างๆ หลังจาก delivery เมื่อคุณ deploy บางอย่าง อย่า hand off มันและก้าวไปข้างหน้า ดูมันหนึ่งสัปดาห์ ดู metrics ดู error logs ดูต้นทุน ถาม: ระบบนี้ทำงานในแบบที่ผมคาดหวังไหม? ถ้าไม่ทำไม?

เริ่มทำ trade-offs อย่างชัดเจน เมื่อคุณเลือกแนวทาง ระบุว่าทำไมคุณถึงปฏิเสธทางเลือก เขียนมัน แม้แต่สั้นๆ "ผมเลือก X แทน Y เพราะ Z" การระบุนั้นคือจุดเริ่มต้นของการใช้เหตุผลเชิงสถาปัตยกรรม

เริ่มมอง post-mortems เป็นการศึกษา ไม่ใช่การดำเนินคดี ทุกเหตุการณ์คือ case study อ่านอันที่สาธารณะ — AWS, Cloudflare, Stripe, GitHub ทั้งหมดเผยแพร่พวกมัน อ่านอันภายใน ถาม: failure mode คืออะไร? สมมุติฐานใดที่กลับมาผิด? ผมจะทำอะไรต่างออกไป?

การก้าวหน้าจาก junior สู่สถาปนิกไม่ได้เกี่ยวกับสิ่งที่คุณรู้เป็นหลัก มันเกี่ยวกับสิ่งที่คุณสังเกต

## สิ่งที่เปลี่ยนแปลงเมื่อคุณเติบโต

**จาก implementation สู่ consequence** Junior engineers ถาม "มันทำงานได้ไหม?" Senior engineers ถาม "มันยังทำงานได้ไหม?" สถาปนิกถาม "จะเกิดอะไรขึ้นเมื่อมันหยุดทำงาน?"

**จาก features สู่ systems** Junior engineers เพิ่ม features สถาปนิกคิดเรื่องระบบจะกลายเป็นอะไรเมื่อ features สิบอันถูกเพิ่มเข้าไป รูปร่างของการตัดสินใจในอนาคตมองเห็นได้แล้วในการตัดสินใจปัจจุบัน

**จาก correctness สู่ trade-offs** มักมี implementation "ถูกต้องที่สุด" ของ feature แทบไม่มี architecture "ถูกต้องที่สุด" มี trade-offs และสถาปนิกที่ดีทำมันอย่างชัดเจนและตั้งใจแทนที่จะเป็นโดยบังเอิญ

**จาก confidence สู่ calibration** Junior engineers มักเป็นทั้ง underconfident (ไม่แน่ใจในการตัดสินใจที่ถูกต้อง) หรือ overconfident (ไม่รู้ว่าตนเองไม่รู้อะไร) สถาปนิกที่มีประสบการณ์มี calibration: พวกเขารู้ขอบเขตและขีดจำกัดของความรู้ และถือข้อสรุปในระดับความแน่ใจที่เหมาะสม

**จาก knowledge สู่ judgment** Judgment คือการรู้ว่า DynamoDB ใช้ partition keys Knowledge คือการรู้ว่า access pattern ของกรณีการใช้งานเฉพาะนี้จะทำให้เกิด hot partitions และผลกระทบทางธุรกิจของ failure mode นั้นในระดับ scale ที่คาดการณ์หมายความว่าคุณควรพิจารณาการออกแบบใหม่ตอนนี้
