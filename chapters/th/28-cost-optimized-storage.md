# บทที่ 28: ความประหลาดใจในบิล Storage

Tom ส่ง Savings Plan สำหรับ EC2 แล้ว บรรทัดถัดไปในบิลคือ S3: $198/เดือน (ลดจาก $847 หลังจากการเปลี่ยน lifecycle policy ในบทที่ 23)

จากนั้นเขาดู EBS: $440/เดือน

"ดูเหมือนสูงมาก" เขาพูด

Leo ดึงรายการ EBS volume ขึ้นมา มี EBS volumes 47 อันที่แนบกับ instances และมีอีก 23 อันที่ไม่ได้แนบกับ instance ใดเลย

"23 volumes เหล่านี้" Tom พูด "คืออะไร?"

Leo ตรวจสอบดู พวกมันทั้งหมด detached — ไม่มี instance ใดที่ใช้งานอยู่ที่ใช้มันในขณะนี้ ส่วนใหญ่ถูกสร้างจาก snapshots เพื่อวัตถุประสงค์ในการ debug บางอันมาจาก instances ที่ถูกยุติแล้วแต่ volumes ไม่ได้ถูกลบ

"เราจ่าย $0.10 ต่อ GB ต่อเดือนสำหรับ storage ที่ไม่มีใครอ่าน" Leo พูด

Tom ดูรวม: 2.3 TB ของ volumes ที่ไม่ได้แนบ

"สองร้อยสามสิบดอลลาร์ต่อเดือนสำหรับ storage ที่เราไม่ได้ใช้" Tom พูด "นานแค่ไหนแล้วที่เป็นแบบนี้?"

Leo ตรวจสอบวันที่สร้าง volume ที่เก่าที่สุดมาจาก 16 เดือนที่แล้ว

"สามพันหกร้อยแปดสิบดอลลาร์" Tom พูดเบาๆ "เราใช้เงินสามพันหกร้อยดอลลาร์กับ storage ที่ไม่มีใครเข้าถึง"

เขาลบ volumes ที่ไม่ได้แนบทิ้ง เดือนถัดมา EBS bill ลดลงเหลือ $210

**การตรวจสอบต้นทุน Storage**

การค้นพบ EBS ของ Tom เป็นอาการของรูปแบบที่กว้างกว่า: ค่า storage สะสมอย่างมองไม่เห็น ต่างจาก compute (คุณสังเกตเมื่อเซิร์ฟเวอร์ 47 ตัวกำลังทำงาน) storage เพิ่มขึ้นเงียบๆ

ลองนึกภาพการเช่าห้องเก็บของ การเช่าห้องหนึ่งห้องเห็นได้ชัดในใบแจ้งหนี้บัตรเครดิต แต่ถ้าคุณเช่าห้องที่สองสำหรับโปรเจกต์ จากนั้นห้องที่สามสำหรับเฟอร์นิเจอร์เก่า และคุณไม่เคยกลับไปตรวจสอบว่ามีอะไรข้างใน ค่าใช้จ่ายก็ยังคงปรากฏในทุกเดือนอย่างเงียบๆ นานหลังจากที่คุณลืมไปแล้วว่าคุณกำลังจัดเก็บอะไรไว้ Cloud storage ทำงานในลักษณะเดียวกัน: bytes อยู่นั่น ใบแจ้งหนี้มาถึง และไม่มีใครตั้งคำถามจนกว่าจะมีคนเปิดประตูและพบว่ามันเต็มไปด้วยสิ่งที่ไม่มีใครต้องการอีกต่อไป

การตรวจสอบต้นทุน storage อย่างละเอียดดูที่:

**S3**:

- มี lifecycle policies สำหรับ buckets ทุกอันไหม?
- มี snapshots เก่า (RDS, EBS) อยู่ใน S3 ไหม?
- Intelligent-Tiering เหมาะสมสำหรับ buckets ที่มีรูปแบบการเข้าถึงที่ไม่แน่นอนไหม?
- มี versioned objects ที่สร้างสำเนาหลายชุดที่ไม่มีใครเข้าถึงไหม?

**EBS**:

- มี volumes ที่ไม่ได้แนบ (ไม่มี instance ที่กำลังทำงานที่ใช้งาน) ไหม?
- gp3 volumes ได้รับการกำหนดค่าอย่างถูกต้องไหม? (gp3 volumes ค่าเริ่มต้นอาจมี throughput/IOPS ที่จัดสรรเกินความจำเป็น)
- มี snapshots ที่เก่าเกินความจำเป็นถูกเก็บไว้ไหม?

**RDS**:

- ระยะเวลา retention ของ automated backup ตั้งค่าไว้เหมาะสมไหม? (ยาวขึ้น = ค่า storage มากขึ้น)
- มี manual snapshots จาก instances เก่าที่ยังอยู่รอบๆ ไหม?
- มี read replicas จาก database migrations ที่ยังคงทำงานอยู่ไหม?

**EFS**:

- EFS volume อยู่ใน storage class ที่ถูกต้องไหม? (Standard vs Infrequent Access)

**S3 Versioning: ต้นทุนที่ซ่อนอยู่**

ในบทที่ 5 เราพูดถึงว่า S3 versioning เก็บทุก version ก่อนหน้าของ object ไว้ ดีเยี่ยมสำหรับความปลอดภัย แต่แย่มากสำหรับต้นทุนถ้าคุณไม่มี lifecycle rules สำหรับ versions ด้วย

เมื่อเปิด versioning บน bucket ทุกครั้งที่คุณเขียนทับ object version เก่าจะถูกเก็บไว้ เมื่อเวลาผ่านไป:

- วันที่ 1: รูปภาพถูก upload (v1)
- วันที่ 30: รูปภาพถูกอัปเดต (v1 กลายเป็น "noncurrent" version, v2 คือปัจจุบัน)
- วันที่ 60: รูปภาพถูกอัปเดตอีกครั้ง (v1 และ v2 เป็น noncurrent, v3 คือปัจจุบัน)
- วันที่ 365: v1, v2... v12 ทั้งหมดถูกเก็บ คุณจ่ายสำหรับ 12 สำเนาของรูปภาพ

การแก้ไข: lifecycle rules สำหรับ noncurrent versions

```
Expire noncurrent versions after 30 days
Delete failed multipart uploads after 7 days
```

Tom ใช้ rules เหล่านี้กับ versioned buckets ทั้งหมด เดือนถัดมา S3 storage ลดลง 18%

**EBS: Right-Sizing และการอัปเกรด gp3**

EBS volume pricing มีสองส่วนประกอบ:

1. Storage (ต่อ GB ต่อเดือน)
2. Provisioned IOPS และ throughput (ถ้าคุณใช้ io1/io2 หรือจ่ายสำหรับประสิทธิภาพ gp3 เพิ่มเติม)

**โอกาสของ gp3**: ในบทที่ 6 เราระบุว่า gp3 เป็นค่าเริ่มต้นปัจจุบันและถูกกว่า gp2 ถ้า Nimbus มี volumes ที่สร้างก่อนที่ gp3 จะพร้อมใช้งาน (เปิดตัวในเดือนธันวาคม 2020) volumes เหล่านั้นอาจยังเป็น gp2

Tom พบ gp2 volumes 12 อันรวม 1,200 GB การย้ายไป gp3 ประหยัดได้ทันที 20% บน volumes เหล่านั้น โดยไม่มีประสิทธิภาพที่ลดลง

**IOPS และ throughput**: gp3 volumes มี IOPS 3,000 และ throughput 125 MB/s ตามค่าเริ่มต้น โดยไม่มีค่าใช้จ่ายเพิ่ม คุณสามารถจัดสรรมากขึ้นถ้า workload ต้องการ ตรวจสอบว่า provisioned performance กำลังถูกใช้งานจริงหรือไม่

Tom พบ gp3 volumes สองอันที่มี 10,000 provisioned IOPS เขาตรวจสอบ CloudWatch metrics: IOPS เฉลี่ยจริงคือ 1,200 เขาลด provisioned IOPS เหลือ 4,000 (safety margin เหนือ peak จริง)

ประหยัดต่อเดือน: $68

**Snapshot lifecycle**: EBS snapshots เป็นแบบ incremental (แต่ละ snapshot จัดเก็บเฉพาะการเปลี่ยนแปลงตั้งแต่ snapshot ก่อนหน้า) แต่สะสมกันขึ้น Snapshots เก่าจากยุคแรกของ Nimbus ยังมีอยู่ Tom เก็บ daily snapshots 30 วันและลบส่วนที่เหลือ

**EFS: Storage Classes**

Amazon EFS มี storage classes ของตัวเอง:

- **EFS Standard**: สำหรับไฟล์ที่เข้าถึงบ่อย ราคาสูงกว่า
- **EFS Infrequent Access (IA)**: สำหรับไฟล์ที่ไม่ได้เข้าถึงนาน 30 วัน ถูกกว่า Standard 92%
- **EFS Archive**: สำหรับไฟล์ที่ไม่ได้เข้าถึงนาน 90 วัน ถูกกว่า IA อีก

**EFS Intelligent-Tiering**: ย้ายไฟล์ระหว่าง storage classes โดยอัตโนมัติตามรูปแบบการเข้าถึง

Tom เปิด Intelligent-Tiering บน EFS volume หกสัปดาห์ต่อมา 68% ของไฟล์ย้ายไปยัง Infrequent Access ค่า EFS รายเดือนลดจาก $89 เหลือ $31

**S3 Cost Allocation Tags: ค้นหาว่าใครใช้จ่ายอะไร**

เมื่อ Nimbus เติบโตขึ้น หลายทีมกำลังจัดเก็บข้อมูลใน S3 ทีม analytics มี buckets ของตัวเอง ทีมวิศวกรรมมี buckets ของตัวเอง ทีมข้อมูลร้านอาหารมี buckets ของตัวเอง

บิลแสดงแค่ "S3: $198" ไม่มีการแยกตามทีม

**Cost allocation tags** ช่วยให้คุณ tag AWS resources ด้วย business metadata (ทีม โปรเจกต์ สภาพแวดล้อม) จากนั้นดูต้นทุนแยกตาม tags เหล่านั้นใน AWS Cost Explorer

Tom เพิ่ม tags ให้ S3 buckets ทั้งหมด:
```
Team: analytics
Environment: production
Project: nimbus-core
```

หลังจาก billing cycle พร้อม tagging เขาสามารถเห็น: "data lake ของทีม analytics คือ $74/เดือน Engineering backups คือ $43/เดือน ข้อมูลร้านอาหารคือ $81/เดือน"

ตอนนี้เขาสามารถมีการสนทนาเกี่ยวกับงบประมาณกับแต่ละทีมแทนที่จะดูแค่ตัวเลขรวม

**AWS Cost Explorer และ AWS Budgets**

**AWS Cost Explorer**: แสดงภาพต้นทุนในอดีตและที่คาดการณ์แยกตาม service, region, tag และประเภทการใช้งาน จำเป็นสำหรับการเข้าใจว่าเงินไปไหน

**AWS Budgets**: ตั้งการแจ้งเตือนเมื่อต้นทุนเกิน (หรือคาดว่าจะเกิน) เกณฑ์ที่กำหนด คุณสามารถตั้งงบประมาณตาม service, region, tag หรือ account

Tom ตั้ง budgets สามอัน:

1. บิลรายเดือนรวม: แจ้งเตือนที่ 90% ของจำนวนที่งบประมาณไว้
2. EC2 On-Demand: แจ้งเตือนถ้า On-Demand spend เกิน $500/เดือน (สัญญาณว่ามีช่องว่าง Savings Plan)
3. Data transfer out: แจ้งเตือนที่ $200/เดือน (ค่า data transfer สามารถพุ่งสูงได้โดยไม่คาดคิด)

Budgets ส่งการแจ้งเตือนไปยัง Slack channel ทีมเห็นเมื่อพวกเขากำลังเข้าใกล้ขีดจำกัด แทนที่จะค้นพบในใบแจ้งหนี้รายเดือน

**ต้นทุนของการละเลย**

Tom สร้าง spreadsheet เขาคำนวณว่า Nimbus ใช้จ่ายไปเท่าไหร่กับ:

- EBS volumes ที่ไม่ได้แนบ (16 เดือน): $3,680
- S3 snapshots เก่า (ค้นพบและลบ): $890
- Provisioned IOPS ที่ไม่จำเป็น: $816
- การประหยัดจากการย้าย gp2 ไป gp3 (ที่คาดการณ์ ถ้าทำเร็วกว่านี้): $2,160 ตลอด 18 เดือน
- Noncurrent S3 versions ที่สะสม: $1,340

รวมการสูญเสียที่ระบุ: ประมาณ $8,800 ตลอด 18 เดือน

## จุดแข็งและข้อจำกัด

**วินัยการ optimize ต้นทุน**:

- การตรวจสอบสม่ำเสมอจับการสูญเสียที่สะสมก่อนที่จะมีนัยสำคัญ
- Tagging ทำให้มีความรับผิดชอบ — ทีมเห็นต้นทุนของตัวเอง
- การแจ้งเตือนอัตโนมัติป้องกันการประหลาดใจในการเรียกเก็บเงิน
- Lifecycle policies และ right-sizing มักเป็นการประหยัดที่ตั้งค่าครั้งเดียวและลืมได้

**จุดที่ซับซ้อน**:

- การระบุการสูญเสียในบัญชีขนาดใหญ่ที่มีหลายทีมต้องการเครื่องมือส่วนกลาง
- การสูญเสียบางอย่างเป็นเรื่องที่ตั้งใจ (เก็บ snapshots เพิ่มเติม "เผื่อไว้") การแลกเปลี่ยนระหว่างต้นทุน/ความเสี่ยงเป็นการตัดสินใจตามดุลพินิจ
- การย้าย gp3 ต้องการการ validate อย่างระมัดระวัง (ค่าเริ่มต้น IOPS และ throughput อาจต่างจากพฤติกรรม gp2 ในบางกรณี edge)
- Cost allocation tags ต้องการวินัยในทุกทีม การ tag ที่ไม่สอดคล้องกันทำให้ข้อมูลไม่สมบูรณ์

## สรุป

- **ค่า storage สะสมอย่างมองไม่เห็น** — การตรวจสอบสม่ำเสมอมีความจำเป็น
- **EBS volumes ที่ไม่ได้แนบ** เป็นแหล่งการสูญเสียที่พบบ่อย ลบทิ้ง (หรือทำการลบอัตโนมัติเมื่อ instances ยุติ)
- **EBS right-sizing**: ย้าย gp2 ไป gp3 (โดยทั่วไปประหยัด 20%) ลบ provisioned IOPS ส่วนเกิน
- **S3 versioning**: เปิด lifecycle rules สำหรับ noncurrent versions เพื่อหลีกเลี่ยงการจ่ายสำหรับ version history ที่ไม่จำกัด
- **EFS Intelligent-Tiering**: ย้ายไฟล์ไปยัง tiers ที่ถูกกว่าโดยอัตโนมัติตามความถี่การเข้าถึง
- **Cost allocation tags**: Tag ทรัพยากรด้วย team/project/environment metadata เพื่อการมองเห็นต้นทุนและความรับผิดชอบ
- **AWS Budgets**: การแจ้งเตือนเชิงรุกเมื่อต้นทุนเข้าใกล้เกณฑ์ ไม่มีวันประหลาดใจกับบิลรายเดือน

## เคล็ดลับสอบ

*SAA-C03 Domain: Design Cost-Optimized Architectures (Domain 4, Task 4.1)*

- **Cost allocation tags**: เปิด User-Defined Tags สำหรับการจัดสรรต้นทุนใน billing console จากนั้น tag ทรัพยากร Cost Explorer แสดงการแยกตาม tag สถานการณ์สอบ: "ระบุว่าแผนกใดสร้างค่า S3 มากที่สุด" → cost allocation tags
- **AWS Trusted Advisor**: ระบุ EC2 instances ที่ใช้น้อย EBS volumes ที่ไม่ได้แนบ load balancers ที่ไม่ได้ใช้งาน และการสูญเสียอื่นๆ การตรวจสอบพื้นฐานฟรี การตรวจสอบเต็มรูปแบบต้องใช้ Business/Enterprise Support
- **ส่วนประกอบต้นทุน EBS**: Storage (ต่อ GB), provisioned IOPS (ถ้า io1/io2 หรือ gp3 เพิ่มเติม), throughput (ถ้า gp3 เพิ่มเติม) รู้ว่าส่วนประกอบใดที่สามารถ right-size ได้
- **ค่า S3 versioning**: Noncurrent versions ถูกเก็บและคิดค่าบริการในอัตราเดียวกับ current versions Lifecycle rules ที่หมดอายุ noncurrent versions มีความสำคัญอย่างยิ่งสำหรับการควบคุมต้นทุนใน versioned buckets
- **AWS Compute Optimizer**: วิเคราะห์การใช้งาน EC2 และแนะนำ instance types ที่ right-sized สัญญาณสอบ: "ลดต้นทุน EC2 โดยเลือก instance type ที่ถูกต้อง" → Compute Optimizer
- **AWS Cost Anomaly Detection**: ใช้ ML เพื่อตรวจจับรูปแบบการใช้จ่ายที่ผิดปกติ สัญญาณสอบ: "ตรวจจับการเพิ่มขึ้นของต้นทุนที่ไม่คาดคิดโดยอัตโนมัติ" → Cost Anomaly Detection

## แบบฝึกหัด

**แบบฝึกหัดที่ 1 — จำและเล่า**

อธิบายว่าทำไม EBS volumes ที่ไม่ได้แนบจึงสร้างต้นทุนแม้ว่าจะไม่มี EC2 instance ใดใช้งานอยู่ วิศวกรควรทำตามขั้นตอนอะไรเมื่อยุติ EC2 instance เพื่อหลีกเลี่ยงการสูญเสียนี้?

*(คำใบ้: EBS volumes จัดเก็บข้อมูลบน physical disk และ disk นั้นมีค่าใช้จ่ายโดยไม่คำนึงว่ากำลังถูกอ่านหรือไม่)*

**แบบฝึกหัดที่ 2 — ฝึกสอบ**

*สถานการณ์*: บิล AWS ของบริษัทเพิ่มขึ้นจาก $5,000 เป็น $9,000/เดือนในหกเดือน แต่พวกเขาไม่ได้เพิ่มบริการใหม่ ทีมวิศวกรรมสงสัยว่าค่า storage เป็นปัญหา เครื่องมือ AWS ชุดใดที่จะระบุและอธิบายการเพิ่มขึ้นของต้นทุนได้ดีที่สุด?

A) AWS CloudTrail เพื่อตรวจสอบ API calls และระบุว่าใครสร้างทรัพยากรใหม่  
B) AWS Cost Explorer สำหรับการแยกต้นทุนระดับ service และ AWS Trusted Advisor สำหรับการตรวจจับทรัพยากรที่ไม่ได้ใช้งานและไม่ได้แนบ  
C) Amazon CloudWatch สำหรับการตรวจสอบการใช้งานทรัพยากรและสร้าง cost alarms  
D) AWS Config สำหรับการระบุทรัพยากรทั้งหมดและสถานะการปฏิบัติตาม

**คำใบ้ที่ 1**: "ระบุการเพิ่มขึ้นของต้นทุน" → แสดงภาพการแยกต้นทุนตาม service

**คำใบ้ที่ 2**: "ทรัพยากรที่ไม่ได้ใช้งานและไม่ได้แนบ" → เครื่องมือเฉพาะระบุสิ่งเหล่านี้เชิงรุก

**คำใบ้ที่ 3**: CloudTrail บันทึก API calls; Cost Explorer แสดง cost trends อันไหนมีประโยชน์มากกว่าสำหรับการวิเคราะห์ต้นทุน?

**คำตอบ**: B

**คำอธิบาย**: AWS Cost Explorer แสดง cost trends แยกตาม service, region และประเภทการใช้งาน เหมาะสำหรับการระบุว่า service ใดขับเคลื่อนการเพิ่มขึ้น การตรวจสอบ cost optimization ของ AWS Trusted Advisor ระบุ EBS volumes ที่ไม่ได้แนบ EC2 instances ที่ไม่ได้ใช้งาน load balancers ที่ไม่ได้ใช้งาน และแหล่งการสูญเสียทั่วไปอื่นๆ

**ทำไมไม่ใช่ A?** CloudTrail บันทึกว่าใครสร้างทรัพยากรและเมื่อไหร่ แต่ไม่แสดง cost trends หรือระบุการสูญเสียโดยตรง

**ทำไมไม่ใช่ C?** CloudWatch ตรวจสอบประสิทธิภาพทรัพยากร (CPU, memory) มีประโยชน์สำหรับ right-sizing แต่ไม่ใช่สำหรับการระบุการสูญเสีย storage ที่สะสม

**ทำไมไม่ใช่ D?** AWS Config ติดตามการกำหนดค่าทรัพยากรและการปฏิบัติตาม แต่ไม่ใช่เครื่องมือวิเคราะห์ต้นทุน

**แบบฝึกหัดที่ 3 — ความท้าทายด้านสถาปัตยกรรม** *(ไม่บังคับ)*

บิล S3 ของ Nimbus แสดง $340/เดือนสำหรับ bucket ที่มีป้ายกำกับ "backups" bucket มี versioning เปิดใช้งานและมี:

- Daily database snapshots (7 วันก็พอสำหรับ policy ของพวกเขา)
- Weekly full backups (เก็บไว้ 3 เดือน)
- Quarterly archives (เก็บไว้ 7 ปีสำหรับการปฏิบัติตามด้านภาษี)

ออกแบบ lifecycle policy สำหรับ bucket นี้ที่ลดต้นทุนให้น้อยที่สุดในขณะที่ตรงตามข้อกำหนด retention เหล่านี้ ข้อมูลแต่ละประเภทควรใช้ storage class ใด? คุณจะจัดการ versioning อย่างไรเพื่อป้องกันไม่ให้ versions เก่าสะสม?

*(ไม่มีคำตอบที่ถูกต้องเพียงคำตอบเดียว เป้าหมายคือการฝึกออกแบบ lifecycle policy)*
