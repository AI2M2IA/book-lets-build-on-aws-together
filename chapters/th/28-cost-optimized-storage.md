**การตรวจสอบต้นทุน Storage**

การค้นพบ EBS ของ Tom เป็นอาการของรูปแบบที่กว้างกว่า: ค่า storage สะสมอย่างมองไม่เห็น ต่างจาก compute (คุณสังเกตเมื่อเซิร์ฟเวอร์ 47 ตัวกำลังทำงาน) storage เพิ่มขึ้นเงียบๆ

ลองนึกภาพการเช่าห้องเก็บของ การเช่าห้องหนึ่งห้องเห็นได้ชัดในใบแจ้งหนี้บัตรเครดิต แต่ถ้าคุณเช่าห้องที่สองสำหรับโปรเจกต์ จากนั้นห้องที่สามสำหรับเฟอร์นิเจอร์เก่า และคุณไม่เคยกลับไปตรวจสอบว่ามีอะไรข้างใน ค่าใช้จ่ายก็ยังคงปรากฏในทุกเดือนอย่างเงียบๆ นานหลังจากที่คุณลืมไปแล้วว่าคุณกำลังจัดเก็บอะไรไว้ Cloud storage ทำงานในลักษณะเดียวกัน: bytes อยู่นั่น ใบแจ้งหนี้มาถึง และไม่มีใครตั้งคำถามจนกว่าจะมีคนเปิดประตูและพบว่ามันเต็มไปด้วยสิ่งที่ไม่มีใครต้องการอีกต่อไป

การตรวจสอบต้นทุน storage อย่างละเอียดดูที่:

**S3**:

- มี lifecycle policies สำหรับ buckets ทุกอันไหม?
- มี snapshots เก่า (RDS, EBS) อยู่ใน S3 ไหม?
- Intelligent-Tiering เหมาะสมสำหรับ buckets ที่มีรูปแบบการเข้าถึงที่ไม่แน่นอนไหม?
- มี versioned objects ที่สร้างสำเนาหลายชุดที่ไม่มีใครเข้าถึงไหม?
- มี incomplete multipart uploads ที่สะสมอย่างเงียบๆ ไหม?

**EBS**:

- มี volumes ที่ไม่ได้แนบ (ไม่มี instance ที่กำลังทำงานที่ใช้งาน) ไหม?
- gp3 volumes ได้รับการกำหนดค่าอย่างถูกต้องไหม? (gp3 volumes ค่าเริ่มต้นอาจมี throughput/IOPS ที่จัดสรรเกินความจำเป็น)
- มี snapshots ที่เก่าเกินความจำเป็นถูกเก็บไว้ไหม?

**RDS**:

- ระยะเวลา retention ของ automated backup ตั้งค่าไว้เหมาะสมไหม? (ยาวขึ้น = ค่า storage มากขึ้น)
- มี manual snapshots จาก instances เก่าที่ยังอยู่รอบๆ ไหม?
- มี read replicas จาก database migrations ที่ยังคงทำงานอยู่ไหม?

**EFS**:

- EFS volume อยู่ใน storage class ที่ถูกต้องไหม? (Standard vs Infrequent Access)

**S3 Versioning: ต้นทุนที่ซ่อนอยู่**

ในบทที่ 5 เราพูดถึงว่า S3 versioning เก็บทุก version ก่อนหน้าของ object ไว้ ดีเยี่ยมสำหรับความปลอดภัย แต่แย่มากสำหรับต้นทุนถ้าคุณไม่มี lifecycle rules สำหรับ versions ด้วย

เมื่อเปิด versioning บน bucket ทุกครั้งที่คุณเขียนทับ object version เก่าจะถูกเก็บไว้ เมื่อเวลาผ่านไป:

- วันที่ 1: รูปภาพถูก upload (v1)
- วันที่ 30: รูปภาพถูกอัปเดต (v1 กลายเป็น "noncurrent" version, v2 คือปัจจุบัน)
- วันที่ 60: รูปภาพถูกอัปเดตอีกครั้ง (v1 และ v2 เป็น noncurrent, v3 คือปัจจุบัน)
- วันที่ 365: v1, v2... v12 ทั้งหมดถูกเก็บ คุณจ่ายสำหรับ 12 สำเนาของรูปภาพ

คุณอาจสงสัยว่าทำไม versioning ไม่ล้าง versions เก่าโดยอัตโนมัติ คำตอบคือเป็นความตั้งใจ — AWS ไม่ต้องการลบข้อมูลของคุณโดยอัตโนมัติ แต่ผลที่ตามมาคือทุก version สะสมจนกว่าคุณจะบอก S3 อย่างชัดเจนว่าจะเก็บไว้นานแค่ไหน การแก้ไข: lifecycle rules สำหรับ noncurrent versions

```
Expire noncurrent versions after 30 days
Delete failed multipart uploads after 7 days
```

Tom ใช้ rules เหล่านี้กับ versioned buckets ทั้งหมด เดือนถัดมา S3 storage ลดลง 18%

**Incomplete Multipart Uploads: การสะสมที่มองไม่เห็น**

มีต้นทุน S3 ที่ละเอียดอ่อนกว่าที่วิศวกรส่วนใหญ่มองข้ามไปโดยสิ้นเชิง: incomplete multipart uploads

เมื่อ S3 upload ไฟล์ขนาดใหญ่ มันแบ่งเป็นส่วนๆ และ upload แต่ละส่วนแยกกัน นี่คือกลไก multipart upload — น่าเชื่อถือกว่า single large PUT สำหรับไฟล์ที่เกินกว่าสองสามร้อยเมกะไบต์ แต่ถ้า upload เริ่มแล้วล้มเหลวกลางคัน — การขัดข้องของเครือข่าย client crash บั๊กแอปพลิเคชัน — ส่วนที่ upload ไปแล้วยังคงอยู่ใน S3 พวกมันไม่ปรากฏเป็น objects ใน bucket ของคุณ ไม่ปรากฏในรายการใดๆ แต่พวกมันถูกจัดเก็บ และคุณถูกเรียกเก็บสำหรับพวกมันที่อัตรา S3 มาตรฐาน

Tom พบสิ่งนี้โดยการเปิด S3 Storage Lens dashboard ใน S3 console และเรียงตาม "incomplete multipart uploads" Nimbus มีข้อมูล incomplete multipart upload 340GB นั่งอยู่เงียบๆ ใน buckets ทั่วสี่ AWS accounts บางอันเก่ากว่าหนึ่งปี

"มันมีค่าใช้จ่ายต่อเดือนเท่าไหร่?" Tom ถาม $0.023/GB/เดือน × 340GB = $7.82/เดือน เล็กรายตัว แต่มันสะสมมาหนึ่งปีโดยไม่มีใครสังเกต

การแก้ไข: เพิ่ม lifecycle rule ให้ทุก bucket

```
AbortIncompleteMultipartUpload:
  DaysAfterInitiation: 7
```

หลังจากเจ็ดวัน incomplete multipart upload ใดๆ จะถูกล้างอัตโนมัติ สิ่งนี้รันอย่างไม่มีกำหนดโดยไม่ต้องดูแลต่อเนื่อง

"ถ้าทั้งหมดนั้นนั่งอยู่ที่นั่นเต็มหนึ่งปี — ก็ราว $94 ที่เราใช้ไปกับ failed uploads" Leo พูด

"กับ failed uploads" Tom ยืนยัน "ไม่ใช่แม้แต่กับ storage ที่สำเร็จ นี่คือคำนิยามของการสูญเปล่า infrastructure"

**EBS: Right-Sizing และการอัปเกรด gp3**

EBS volume pricing มีสองส่วนประกอบ:

1. Storage (ต่อ GB ต่อเดือน)
2. Provisioned IOPS และ throughput (ถ้าคุณใช้ io1/io2 หรือจ่ายสำหรับประสิทธิภาพ gp3 เพิ่มเติม)

**โอกาสของ gp3**: ในบทที่ 6 เราระบุว่า gp3 เป็นค่าเริ่มต้นปัจจุบันและถูกกว่า gp2 ถ้า Nimbus มี volumes ที่สร้างก่อนที่ gp3 จะพร้อมใช้งาน (เปิดตัวในเดือนธันวาคม 2020) volumes เหล่านั้นอาจยังเป็น gp2

การย้ายตรงไปตรงมา: แก้ไข volume type จาก gp2 เป็น gp3 ใน AWS console หรือผ่าน CLI ไม่ต้องมี downtime Volume ยังคงพร้อมใช้งานระหว่างการแปลง คุณลักษณะด้านประสิทธิภาพเท่ากันหรือดีกว่า — gp3 ให้ 3,000 IOPS และ baseline throughput 125 MB/s เทียบกับ burstable model ของ gp2 ที่อาจไม่สม่ำเสมอสำหรับ volumes ขนาดเล็ก

"เดี๋ยว — แต่ *ทำไม* เราถึงทำแบบนั้น?" Maya ถาม "ถ้า gp3 ถูกกว่าและอย่างน้อยดีเท่า gp2 ทำไม AWS ไม่ย้ายทุกคนโดยอัตโนมัติ?"

"เพราะ AWS ไม่ทำการเปลี่ยนแปลงฝ่ายเดียวต่อ infrastructure ของลูกค้า" Tom พูด "แม้แต่การเปลี่ยนแปลงที่เป็นประโยชน์ การแก้ไขในทางทฤษฎีอาจมีผลข้างเคียงสำหรับบาง workload ลูกค้าต้องเป็นผู้ริเริ่ม ซึ่งเป็นเหตุผลที่ทีมนับพันยังจ่ายราคา gp2 หลายปีหลังจาก gp3 เปิดตัว เพียงเพราะไม่มีใครไปมองหา"

Tom ตัดสินใจทำการย้าย gp3 ในเช้าวันเสาร์ — วินัยยามเช้าแบบเดียวกับที่เขาใช้กับการวิเคราะห์ EC2 pricing เวลาเงียบสงบ ไม่มี standup มีแค่ AWS console กับแผน

เขาระบุ 8 volumes ทั่ว production environment ที่ยังเป็น gp2: root volumes ของ API server สี่ตัว สอง volumes ที่แนบกับ background processors และสอง legacy data volumes ที่ถูกสร้างก่อนที่การย้าย gp3 จะกลายเป็นแนวปฏิบัติมาตรฐานสำหรับ deployments ใหม่ รวมกันได้ 960 GB

กระบวนการย้ายคือ API call เดียวต่อ volume:

```bash
aws ec2 modify-volume \
  --volume-id vol-0a1b2c3d4e5f67890 \
  --volume-type gp3 \
  --iops 3000 \
  --throughput 125
```

พารามิเตอร์ `--iops 3000` และ `--throughput 125` ตรงกับค่าเริ่มต้น baseline ของ gp3 สำหรับ gp2 Tom ตรวจสอบ CloudWatch metrics ก่อน: IOPS เฉลี่ยบนแต่ละ volume อยู่ระหว่าง 200 ถึง 800 ไม่มีอันไหนต้องการมากกว่า baseline 3,000 IOPS ที่ gp3 ให้ฟรี Throughput ก็สบายๆ เช่นกัน — อยู่ในค่าเริ่มต้น 125 MB/s อย่างมาก

"จะเป็นอย่างไรถ้า volume ต้องการ IOPS มากขึ้นหลังจากเราสลับ?" Maya ถามเมื่อ Tom อธิบายแผนการย้าย

"เราสามารถเพิ่ม provisioned IOPS บน gp3 volume ได้ตลอดเวลา" Tom พูด "การย้ายไม่ล็อคอะไรไว้ ถ้าเราไป gp3 ที่ 3,000 IOPS และพบว่ามันไม่เพียงพอ เราแก้ไข volume อีกครั้งเพื่อเพิ่ม การแก้ไขเป็นแบบ live — ไม่มี downtime ไม่มีการ unmount"

"และ gp2 แก้ไขแบบ in place ไม่ได้เหรอ?"

"gp2 สามารถแก้ไขเป็น gp3 แบบ in place ได้ สิ่งที่คุณทำไม่ได้คือการกลับจาก gp3 ไป gp2 — อย่างน้อยก็ไม่ง่าย และไม่มีเหตุผลที่จะทำ"

การย้ายจริงใช้เวลา 73 นาทีตั้งแต่คำสั่งแรกจนเสร็จทั้ง 8 volumes AWS แก้ไขแต่ละ volume ขณะที่มันถูก mount และใช้งานอยู่ API servers ยังรับ traffic ตลอด CloudWatch ไม่แสดง spikes ใน I/O latency ระหว่างการแปลง — การเปลี่ยนผ่านโปร่งใสโดยสมบูรณ์ต่อแอปพลิเคชันที่กำลังทำงาน

"นั่นคือสิ่งที่ 'ไม่ต้องมี downtime' หน้าตาจริงๆ" Leo พูด มองที่ metrics ก่อน-หลังที่ Tom เก็บไว้ "ผมสมมติว่า 'ไม่มี downtime' หมายถึง 'รีสตาร์ทสั้นๆ' มันหมายถึงไม่มีอะไรเปลี่ยนแปลงเลยตามมุมมองของแอปพลิเคชัน"

การประหยัด: gp2 คือ $0.10/GB/เดือน; gp3 คือ $0.08/GB/เดือน บน 960 GB: $96/เดือน vs $76.80/เดือน ประหยัดต่อเดือน: $19.20 ไม่ใช่การเปลี่ยนแปลงครั้งใหญ่ในตัวเอง แต่วินัยที่มันแสดงนั้นใช่ Volume ใหม่ใดๆ ที่สร้างจากจุดนั้นเป็นต้นไปใช้ gp3 โดยค่าเริ่มต้น กฎองค์กรที่ Tom เขียนในเช้านั้น: ไม่มี gp2 volumes วิศวกรใดๆ ที่สร้าง EBS volume ควรใช้ gp3 เว้นแต่มีเหตุผลเฉพาะที่มีเอกสารเป็นอย่างอื่น

**IOPS และ throughput**: gp3 volumes มี IOPS 3,000 และ throughput 125 MB/s ตามค่าเริ่มต้น โดยไม่มีค่าใช้จ่ายเพิ่ม คุณสามารถจัดสรรมากขึ้นถ้า workload ต้องการ ตรวจสอบว่า provisioned performance กำลังถูกใช้งานจริงหรือไม่

ในการตรวจสอบเดียวกัน Tom พบสอง volumes ที่มี 10,000 provisioned IOPS — การตั้งค่าเก่าจากก่อนที่เขาจะเข้ามา ปรับขนาดสำหรับ database ที่ย้ายไป Aurora แล้ว เขาตรวจสอบ CloudWatch metrics: IOPS เฉลี่ยจริงคือ 1,200 เขาลด provisioned IOPS เหลือ 4,000 (safety margin เหนือ peak จริง)

ประหยัดต่อเดือน: $68 ในค่า provisioned IOPS ที่จ่ายไปกับ performance headroom ที่ไม่มีใครใช้

**Snapshot lifecycle**: EBS snapshots เป็นแบบ incremental (แต่ละ snapshot จัดเก็บเฉพาะการเปลี่ยนแปลงตั้งแต่ snapshot ก่อนหน้า) แต่สะสมกันขึ้น Snapshots เก่าจากยุคแรกของ Nimbus ยังมีอยู่ Tom เก็บ daily snapshots 30 วันและลบส่วนที่เหลือ

**EFS: Storage Classes และการตัดสินใจ Intelligent-Tiering**

Amazon EFS มี storage classes ของตัวเอง:

- **EFS Standard**: สำหรับไฟล์ที่เข้าถึงบ่อย ราคาสูงกว่า
- **EFS Infrequent Access (IA)**: สำหรับไฟล์ที่ไม่ได้เข้าถึงนาน 30 วัน ถูกกว่า Standard 92%
- **EFS Archive**: สำหรับไฟล์ที่ไม่ได้เข้าถึงนาน 90 วัน ถูกกว่า IA อีก

**EFS Intelligent-Tiering**: ย้ายไฟล์ระหว่าง storage classes โดยอัตโนมัติตามรูปแบบการเข้าถึง

Tom เปิด Intelligent-Tiering บน EFS volume หกสัปดาห์ต่อมา 68% ของไฟล์ย้ายไปยัง Infrequent Access ค่า EFS รายเดือนลดจาก $89 เหลือ $31

แต่ตัวเลือกระหว่าง Intelligent-Tiering กับ manual lifecycle rule ไม่ใช่เรื่องเล็กน้อย Tom ได้พิจารณามัน

"เดี๋ยว — แต่ *ทำไม* เราถึงทำ Intelligent-Tiering เทียบกับการตั้ง manual lifecycle rule?" Maya ถาม "ถ้าเรารู้ว่าไฟล์ที่เก่ากว่า 30 วันไม่ถูกเข้าถึง ทำไมไม่ตั้ง rule แล้วจบ?"

"Intelligent-Tiering จัดการไฟล์ที่กลับมา" Tom พูด "ถ้าผมตั้ง lifecycle rule ให้ย้ายไฟล์ไป IA หลัง 30 วัน แล้วมีคนเข้าถึงไฟล์ที่อยู่ใน IA มาหกเดือน มันยังอยู่ใน IA ด้วย Intelligent-Tiering ถ้าการเข้าถึงกลับมา ไฟล์ย้ายกลับไป Standard โดยอัตโนมัติ มันเป็นแบบสองทิศทาง"

"แล้วเมื่อไหร่คุณจะชอบ lifecycle rule มากกว่า?"

"เมื่อคุณแน่ใจว่ารูปแบบการเข้าถึงเป็นทิศทางเดียว Archive logs — พวกมันถูกเขียน เก่าลง ถูกเข้าถึงครั้งหนึ่งสำหรับ compliance audit แล้วไม่อีกเลย สำหรับรูปแบบนั้น lifecycle rule ที่ย้ายไป Archive หลัง 90 วันถูกกว่า Intelligent-Tiering เพราะคุณไม่จ่าย monitoring overhead"

"มี monitoring fee เหรอ?"

"สำหรับ S3 Intelligent-Tiering มี ซึ่งเป็นเหตุผลที่เราครอบคลุม small-object economics ในบท S3 lifecycle สำหรับ EFS การตัดสินใจส่วนใหญ่เกี่ยวกับรูปแบบการเข้าถึง: ถ้าไฟล์อาจกลับมา hot อีก Intelligent-Tiering ปลอดภัยกว่า ถ้าพวกมันเก่าลงในทิศทางเดียวเท่านั้น lifecycle rule ไป Archive ถูกกว่าและง่ายกว่า"

**S3 Cost Allocation Tags: ค้นหาว่าใครใช้จ่ายอะไร**

เมื่อ Nimbus เติบโตขึ้น หลายทีมกำลังจัดเก็บข้อมูลใน S3 ทีม analytics มี buckets ของตัวเอง ทีมวิศวกรรมมี buckets ของตัวเอง ทีมข้อมูลร้านอาหารมี buckets ของตัวเอง

บิลแสดงแค่ "S3: $198" ไม่มีการแยกตามทีม

**Cost allocation tags** ช่วยให้คุณ tag AWS resources ด้วย business metadata (ทีม โปรเจกต์ สภาพแวดล้อม) จากนั้นดูต้นทุนแยกตาม tags เหล่านั้นใน AWS Cost Explorer

Tom เพิ่ม tags ให้ S3 buckets ทั้งหมด:
```
Team: analytics
Environment: production
Project: nimbus-core
```

หลังจาก billing cycle พร้อม tagging เขาสามารถเห็น: "data lake ของทีม analytics คือ $74/เดือน Engineering backups คือ $43/เดือน ข้อมูลร้านอาหารคือ $81/เดือน"

ตอนนี้เขาสามารถมีการสนทนาเกี่ยวกับงบประมาณกับแต่ละทีมแทนที่จะดูแค่ตัวเลขรวม

**AWS Cost Explorer และ AWS Budgets**

**AWS Cost Explorer**: แสดงภาพต้นทุนในอดีตและที่คาดการณ์แยกตาม service, region, tag และประเภทการใช้งาน จำเป็นสำหรับการเข้าใจว่าเงินไปไหน

**AWS Budgets**: ตั้งการแจ้งเตือนเมื่อต้นทุนเกิน (หรือคาดว่าจะเกิน) เกณฑ์ที่กำหนด คุณสามารถตั้งงบประมาณตาม service, region, tag หรือ account

Tom ตั้ง budgets สามอัน:

1. บิลรายเดือนรวม: แจ้งเตือนที่ 90% ของจำนวนที่งบประมาณไว้
2. EC2 On-Demand: แจ้งเตือนถ้า On-Demand spend เกิน $500/เดือน (สัญญาณว่ามีช่องว่าง Savings Plan)
3. Data transfer out: แจ้งเตือนที่ $200/เดือน (ค่า data transfer สามารถพุ่งสูงได้โดยไม่คาดคิด)

Budgets ส่งการแจ้งเตือนไปยัง Slack channel ทีมเห็นเมื่อพวกเขากำลังเข้าใกล้ขีดจำกัด แทนที่จะค้นพบในใบแจ้งหนี้รายเดือน

**ใบเสร็จที่มีทุกบรรทัด: Cost and Usage Reports**

Cost Explorer ตอบคำถามส่วนใหญ่ของ Tom จากนั้นเขาเจอคำถามหนึ่งที่มันตอบไม่ได้: "S3 buckets ใดกันแน่ ชั่วโมงต่อชั่วโมง ที่ขับเคลื่อน spike เมื่อวันอังคารที่แล้ว — และภายใต้ tags ใด?"

สำหรับคำถามระดับ forensic AWS ให้ **Cost and Usage Report (CUR)** — ตอนนี้ส่งผ่าน **Data Exports** — ข้อมูลการเรียกเก็บเงินที่ละเอียดที่สุดที่ AWS ผลิต: ทุกรายการ **ต่อทรัพยากร ต่อชั่วโมง** พร้อม tags ส่งไปยัง S3 bucket ที่คุณเป็นเจ้าของ มันไม่ใช่ dashboard; มันคือ raw ledger รูปแบบมาตรฐานคือคิวรีมันด้วย Athena (มันลงในรูปแบบ columnar) หรือป้อนให้ QuickSight สำหรับ dashboards

การแบ่งงานในข้อสอบ: **Cost Explorer** = การแสดงภาพแบบโต้ตอบและการคาดการณ์ใน console **Budgets** = การแจ้งเตือนบนเกณฑ์ **CUR/Data Exports** = ข้อมูลที่ละเอียดที่สุด ส่งไปยัง S3 สำหรับการวิเคราะห์ของคุณเอง เมื่อคำถามบอกว่า "ข้อมูลต้นทุนระดับทรัพยากร รายชั่วโมง สำหรับการวิเคราะห์แบบกำหนดเอง" — นั่นคือ CUR ไม่ใช่ Cost Explorer

"เราคิดถึงสิ่งที่จะเกิดขึ้นถ้าเราไม่เคยดูสิ่งนี้เลยไหม?" Priya ถาม "เราพบ $6,700 ในสองวัน อะไรยังซ่อนอยู่อีก?"

"การตรวจสอบสม่ำเสมอ" เธอพูดต่อ "การตรวจสอบ Cost Explorer รายเดือน AWS Trusted Advisor flags volumes ที่ไม่ได้แนบและทรัพยากรที่ไม่ได้ใช้โดยอัตโนมัติ ทำให้การทำความสะอาดรูปแบบการสูญเสียที่รู้จักเป็นอัตโนมัติ: ลบ snapshots ที่เก่ากว่า N วัน แจ้งเตือนบน EBS volumes ที่ไม่ได้แนบ หมดอายุ S3 versions เก่า"

**S3 Requester-Pays: การโยกย้ายต้นทุน Transfer**

ระหว่างการตรวจสอบ storage Tom พบสถานการณ์ที่เขาไม่ได้คาดการณ์

พาร์ทเนอร์ร้านอาหารของ Nimbus ต้องการดาวน์โหลด menu photo assets ของพวกเขา — รูปภาพที่ประมวลผลและปรับขนาดแล้วที่แพลตฟอร์มสั่งอาหารให้บริการแก่ลูกค้า สำหรับร้านอาหารที่อัปเดตเมนู นี่หมายถึงการดาวน์โหลดไฟล์รูปภาพที่ใดก็ได้ตั้งแต่ 50 MB (อัปเดตเล็ก) ถึง 800 MB (รีเฟรชตามฤดูกาลเต็มรูปแบบ) ปัจจุบัน Nimbus จ่ายค่า outbound data transfer ในทุกการดาวน์โหลด: $0.09/GB จาก S3 ไปยังตำแหน่งของพาร์ทเนอร์

ที่ 287 พาร์ทเนอร์ร้านอาหาร ด้วยค่าเฉลี่ยหนึ่งครั้งรีเฟรชเมนูต่อเดือนและการดาวน์โหลดเฉลี่ย 200 MB คณิตศาสตร์คือ: 287 × 0.2GB × $0.09 = $5.17/เดือน ไม่มีนัยสำคัญที่ scale ปัจจุบัน

เขารันมัน 10,000 × 2GB × $0.09 = $1,800/เดือน ใน data transfer แค่สำหรับพาร์ทเนอร์ที่ดาวน์โหลด assets ที่พวกเขาต้องการ

## จุดแข็งและข้อจำกัด

**วินัยการ optimize ต้นทุน**:

- การตรวจสอบสม่ำเสมอจับการสูญเสียที่สะสมก่อนที่จะมีนัยสำคัญ
- Tagging ทำให้มีความรับผิดชอบ — ทีมเห็นต้นทุนของตัวเอง
- การแจ้งเตือนอัตโนมัติป้องกันการประหลาดใจในการเรียกเก็บเงิน
- Lifecycle policies และ right-sizing มักเป็นการประหยัดที่ตั้งค่าครั้งเดียวและลืมได้

**จุดที่ซับซ้อน**:

- การระบุการสูญเสียในบัญชีขนาดใหญ่ที่มีหลายทีมต้องการเครื่องมือส่วนกลาง
- การสูญเสียบางอย่างเป็นเรื่องที่ตั้งใจ (เก็บ snapshots เพิ่มเติม "เผื่อไว้") การแลกเปลี่ยนระหว่างต้นทุน/ความเสี่ยงเป็นการตัดสินใจตามดุลพินิจ
- การย้าย gp3 ต้องการการ validate อย่างระมัดระวัง (ค่าเริ่มต้น IOPS และ throughput อาจต่างจากพฤติกรรม gp2 ในบางกรณี edge)
- Cost allocation tags ต้องการวินัยในทุกทีม การ tag ที่ไม่สอดคล้องกันทำให้ข้อมูลไม่สมบูรณ์
- Auto-deletion automation อันตรายสำหรับ storage — alert-and-review ปลอดภัยกว่าสำหรับ volumes และ snapshots

## สรุป

การตรวจสอบ storage ใช้เวลาสองวัน การสูญเสียที่มันเปิดเผย — $6,700 ตลอด 18 เดือนของการสะสมที่มองไม่เห็น — ไม่ใช่ความล้มเหลวของการตัดสินใจมากนัก แต่เป็นความล้มเหลวของความใส่ใจ ไม่มีอะไรถูกกำหนดค่าผิดโดยตั้งใจ Snapshots, volumes ที่ไม่ได้แนบ, version history ที่สะสม, incomplete multipart uploads: แต่ละอันสมเหตุสมผลในตอนนั้นและเพียงแต่ไม่เคยถูกกลับไปดูอีก บทเรียนไม่ใช่เกี่ยวกับ AWS services เฉพาะ มันคือเรื่องการสร้างนิสัยของการมองหา

- **ค่า storage สะสมอย่างมองไม่เห็น** — การตรวจสอบสม่ำเสมอมีความจำเป็น
- **EBS volumes ที่ไม่ได้แนบ** เป็นแหล่งการสูญเสียที่พบบ่อย ลบทิ้ง (หรือทำการลบอัตโนมัติเมื่อ instances ยุติ)
- **EBS right-sizing**: ย้าย gp2 ไป gp3 (โดยทั่วไปประหยัด 20%) ลบ provisioned IOPS ส่วนเกิน
- **S3 versioning**: เปิด lifecycle rules สำหรับ noncurrent versions เพื่อหลีกเลี่ยงการจ่ายสำหรับ version history ที่ไม่จำกัด
- **Incomplete multipart uploads**: เพิ่ม lifecycle rule `AbortIncompleteMultipartUpload` ให้ทุก bucket สิ่งนี้มักถูกมองข้ามและสะสมอย่างเงียบๆ
- **EFS Intelligent-Tiering**: ย้ายไฟล์ไปยัง tiers ที่ถูกกว่าโดยอัตโนมัติตามความถี่การเข้าถึง สำหรับรูปแบบการเข้าถึงที่คาดเดาได้ manual lifecycle rules อาจถูกกว่า
- **ธรรมาภิบาล**: แจ้งเตือนบน volumes ที่ไม่ได้แนบหลัง 7-14 วัน; ต้องการการ tag อย่างชัดเจนเพื่อระงับ หลีกเลี่ยง auto-deletion สำหรับ storage resources

## เคล็ดลับการสอบ

*SAA-C03 Domain: Design Cost-Optimized Architectures (Domain 4, Task 4.1)*

- **Cost allocation tags**: เปิด User-Defined Tags สำหรับการจัดสรรต้นทุนใน billing console จากนั้น tag ทรัพยากร Cost Explorer แสดงการแยกตาม tag สถานการณ์สอบ: "ระบุว่าแผนกใดสร้างค่า S3 มากที่สุด" → cost allocation tags
- **AWS Trusted Advisor**: ระบุ EC2 instances ที่ใช้น้อย EBS volumes ที่ไม่ได้แนบ load balancers ที่ไม่ได้ใช้งาน และการสูญเสียอื่นๆ การตรวจสอบพื้นฐานฟรี การตรวจสอบเต็มรูปแบบต้องใช้ Business/Enterprise Support
- **ส่วนประกอบต้นทุน EBS**: Storage (ต่อ GB), provisioned IOPS (ถ้า io1/io2 หรือ gp3 เพิ่มเติม), throughput (ถ้า gp3 เพิ่มเติม) รู้ว่าส่วนประกอบใดที่สามารถ right-size ได้
- **ค่า S3 versioning**: Noncurrent versions ถูกเก็บและคิดค่าบริการในอัตราเดียวกับ current versions Lifecycle rules ที่หมดอายุ noncurrent versions มีความสำคัญอย่างยิ่งสำหรับการควบคุมต้นทุนใน versioned buckets
- **AWS Compute Optimizer**: วิเคราะห์การใช้งาน EC2 และแนะนำ instance types ที่ right-sized สัญญาณสอบ: "ลดต้นทุน EC2 โดยเลือก instance type ที่ถูกต้อง" → Compute Optimizer
- **AWS Cost Anomaly Detection**: ใช้ ML เพื่อตรวจจับรูปแบบการใช้จ่ายที่ผิดปกติ สัญญาณสอบ: "ตรวจจับการเพิ่มขึ้นของต้นทุนที่ไม่คาดคิดโดยอัตโนมัติ" → Cost Anomaly Detection
- **กลุ่มเครื่องมือต้นทุน**: charts/forecasts แบบโต้ตอบ → Cost Explorer การแจ้งเตือนตามเกณฑ์ → Budgets "ข้อมูลการเรียกเก็บเงินที่ละเอียดที่สุด ระดับทรัพยากร/รายชั่วโมง ส่งไปยัง S3 สำหรับการวิเคราะห์แบบกำหนดเอง (Athena/QuickSight)" → **Cost and Usage Report (Data Exports)**
- **Requester Pays**: "แชร์ S3 dataset ขนาดใหญ่; ผู้บริโภคจ่ายค่าดาวน์โหลดของตัวเอง" → S3 Requester Pays (เจ้าของยังจ่าย storage เท่านั้น; ผู้ขอต้อง authenticate ด้วย AWS account)

**คำใบ้ที่ 2**: "ทรัพยากรที่ไม่ได้ใช้งานและไม่ได้แนบ" → เครื่องมือเฉพาะระบุสิ่งเหล่านี้เชิงรุก

**คำใบ้ที่ 3**: CloudTrail บันทึก API calls; Cost Explorer แสดง cost trends อันไหนมีประโยชน์มากกว่าสำหรับการวิเคราะห์ต้นทุน?

**คำตอบ**: B

**คำอธิบาย**: AWS Cost Explorer แสดง cost trends แยกตาม service, region และประเภทการใช้งาน เหมาะสำหรับการระบุว่า service ใดขับเคลื่อนการเพิ่มขึ้น การตรวจสอบ cost optimization ของ AWS Trusted Advisor ระบุ EBS volumes ที่ไม่ได้แนบ EC2 instances ที่ไม่ได้ใช้งาน load balancers ที่ไม่ได้ใช้งาน และแหล่งการสูญเสียทั่วไปอื่นๆ

**ทำไมไม่ใช่ A?** CloudTrail บันทึกว่าใครสร้างทรัพยากรและเมื่อไหร่ แต่ไม่แสดง cost trends หรือระบุการสูญเสียโดยตรง

**ทำไมไม่ใช่ C?** CloudWatch ตรวจสอบประสิทธิภาพทรัพยากร (CPU, memory) มีประโยชน์สำหรับ right-sizing แต่ไม่ใช่สำหรับการระบุการสูญเสีย storage ที่สะสม

**ทำไมไม่ใช่ D?** AWS Config ติดตามการกำหนดค่าทรัพยากรและการปฏิบัติตาม แต่ไม่ใช่เครื่องมือวิเคราะห์ต้นทุน
