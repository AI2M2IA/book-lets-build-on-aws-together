**"คลาวด์" คืออะไรกันแน่**

มาทำให้ชัดเจนทันที เพราะคำว่า "คลาวด์" เป็นหนึ่งในคำที่ถูกใช้มากเกินไปและอธิบายน้อยเกินไปในวงการเทคโนโลยี

คลาวด์ไม่ใช่สถานที่วิเศษที่ข้อมูลของคุณลอยอยู่

คลาวด์คือคอมพิวเตอร์ของคนอื่น

แค่นั้นเอง เมื่อคุณบันทึกรูปภาพไปยัง iCloud หรือ Google Drive รูปภาพของคุณถูกเก็บไว้บนคอมพิวเตอร์จริงที่เป็นของ Apple หรือ Google ซึ่งตั้งอยู่ในอาคารแห่งใดแห่งหนึ่ง เมื่อคุณใช้ Netflix วิดีโอที่คุณกำลังดูถูกส่งมาจากเซิร์ฟเวอร์จริงในศูนย์ข้อมูลทั่วโลก

"คลาวด์" เพียงหมายความว่า: คอมพิวเตอร์ที่คุณเข้าถึงผ่านอินเทอร์เน็ต ที่คุณไม่ต้องเป็นเจ้าของหรือดูแลรักษาด้วยตัวเอง

และ Amazon — ใช่ บริษัทที่ส่งพัสดุ — ได้สร้างหนึ่งในคอลเลกชั่นคอมพิวเตอร์ที่ใหญ่ที่สุดในโลก พวกเขาเรียกมันว่า Amazon Web Services หรือ AWS

**ทำไมต้อง Amazon?**

เป็นคำถามที่สมเหตุสมผล Amazon เริ่มต้นเป็นร้านขายหนังสือ

นี่คือสิ่งที่เกิดขึ้น: Amazon เติบโตเร็วมากจนต้องการพลังการประมวลผลจำนวนมหาศาลในการรันระบบของตัวเอง พวกเขาสร้างศูนย์ข้อมูล จ้างวิศวกรมาดูแล และกลายเป็นผู้เชี่ยวชาญด้านการรันคอมพิวเตอร์ในระดับขนาดใหญ่มาก

แล้วมีคนที่ Amazon คิดขึ้นมา: ถ้าเราขายสิทธิ์การเข้าถึงพลังการประมวลผลทั้งหมดนี้ให้กับคนอื่นล่ะ?

ในปี 2549 Amazon Web Services เปิดตัว วันนี้ AWS รันส่วนสำคัญของอินเทอร์เน็ต เว็บไซต์ที่คุณใช้จองตั๋วเครื่องบิน แอปที่ติดตามการจัดส่งของคุณ บริการสตรีมมิ่งที่คุณดูเมื่อคืน — มีโอกาสดีที่อย่างน้อยบางส่วนรันบน AWS

นี่ไม่ใช่การผูกขาด Google Cloud และ Microsoft Azure เป็นคู่แข่งที่จริงจัง แต่ AWS เป็นคนแรก มีขนาดใหญ่ และนี่คือสิ่งที่หนังสือเล่มนี้พูดถึง

Nimbus เริ่มต้นเป็นระบบสั่งอาหารของร้านอาหารและกลายเป็นอะไรที่ใหญ่กว่านั้นมาก เมื่อมันเติบโตขึ้น ก็พบกับปัญหาทุกอย่างที่ซอฟต์แวร์ที่กำลังเติบโตพบ: ระบบที่ไม่สามารถรับมือกับปริมาณการใช้งานได้ ข้อมูลที่สูญหาย เซิร์ฟเวอร์ที่หยุดทำงานในเวลาที่เลวร้ายที่สุด ต้นทุนที่เพิ่มขึ้นเร็วกว่ารายได้

และทุกครั้งที่พวกเขาพบปัญหา พวกเขาก็พบ AWS service ที่ออกแบบมาเพื่อแก้ปัญหาประเภทนั้นพอดี

หนังสือเล่มนี้สอน AWS ของคุณโดยการติดตามการเดินทางนั้น

คุณจะได้เรียนรู้ไม่ใช่แค่ *ว่า* แต่ละ service ทำอะไร แต่ *ทำไม* มันถึงมีอยู่ *เมื่อไหร่* ที่จะใช้มัน และ — สำคัญพอๆ กัน — *เมื่อไหร่ที่ไม่ควรใช้มัน* ทุกเครื่องมือมีการแลกเปลี่ยน ทุกการตัดสินใจมีต้นทุน นั่นคือสิ่งที่วิศวกรอาวุโสเข้าใจซึ่งวิศวกรระดับจูเนียร์ยังคงเรียนรู้อยู่

เมื่อคุณอ่านหนังสือเล่มนี้จบ คุณจะพร้อมสอบ AWS Solutions Architect Associate (SAA-C03) มากกว่านั้น: คุณจะพร้อมเดินเข้าสู่การสนทนาทางเทคนิคจริงๆ และยืนหยัดได้

**หนังสือเล่มนี้ไม่สมมติว่าคุณเป็นนักพัฒนา** Maya ไม่ใช่ Tom แทบจะไม่ใช่ คุณไม่จำเป็นต้องเขียน code เพื่อทำความเข้าใจสถาปัตยกรรม คุณต้องเข้าใจปัญหาและวิธีแก้ปัญหา

**หนังสือเล่มนี้บางครั้งจะผิดโดยตั้งใจ** ทีมจะทำผิดพลาด พวกเขาจะเลือก service ที่ผิด พวกเขาจะข้ามขั้นตอนความปลอดภัยที่จะเสียใจในภายหลัง พวกเขาจะจัดสรรเกินและน้อยเกินไป นั่นคือวิธีที่พวกเขาจะเรียนรู้ และนั่นคือวิธีที่คุณจะเรียนรู้ด้วย

**เคล็ดลับการสอบเป็นของจริง** SAA-C03 เป็นการสอบจริง คำถามสถานการณ์ท้ายแต่ละบทออกแบบมาให้รู้สึกเหมือนการสอบจริง ถ้าคุณตอบได้ คุณอยู่ในเส้นทางที่ถูกต้อง

และอีกหนึ่งสิ่ง

อ่านหนังสือเล่มนี้พร้อมดินสอ หรือแอปจดบันทึก หรือรายการที่กำลังทำงานของช่วงเวลา "ฉันคิดว่าคำตอบคือ..."

หยุดก่อนที่ทีมจะตัดสินใจบางอย่าง ทำการตัดสินใจด้วยตัวเอง แล้วอ่านต่อไปเพื่อดูว่าคุณจะทำการแลกเปลี่ยนแบบเดียวกันหรือไม่

## สรุป

- **คลาวด์** คือการเข้าถึงทรัพยากรการประมวลผลตามต้องการผ่านอินเทอร์เน็ต — คอมพิวเตอร์ของคนอื่นที่คุณไม่ต้องเป็นเจ้าของหรือดูแลรักษา
- สามตัวเลือกการโฮสต์: on-premises (ฮาร์ดแวร์ของคุณ ต้นทุนของคุณ), shared hosting (จำกัด ไม่สามารถขยายได้), คลาวด์ (จ่ายตามการใช้งาน ขยายตามความต้องการ)
- **AWS** เปิดตัวในปี 2549 เมื่อ Amazon เปิดโครงสร้างพื้นฐานศูนย์ข้อมูลให้กับลูกค้าภายนอก ยังคงเป็นผู้ให้บริการคลาวด์ที่ใหญ่ที่สุด รองลงมาคือ Microsoft Azure และ Google Cloud
- Nimbus — เรื่องราวที่หนังสือเล่มนี้ติดตาม — เริ่มต้นเป็นระบบสั่งอาหารของร้านอาหารและเติบโตเป็นสถาปัตยกรรมคลาวด์ระดับการผลิต
- หนังสือเล่มนี้สอนไม่ใช่แค่ *ว่า* แต่ละ AWS service ทำอะไร แต่ *ทำไม* มันมีอยู่ *เมื่อไหร่* ที่จะใช้มัน และ *เมื่อไหร่ที่ไม่ควร*

## เคล็ดลับการสอบ

*SAA-C03 Domain: ข้ามโดเมน — พื้นฐานแนวคิดคลาวด์*

- **คลาวด์ในการสอบ** หมายถึงการประมวลผลตามต้องการ จ่ายตามการใช้งานผ่านอินเทอร์เน็ต มันเป็นรูปแบบการส่งมอบ ไม่ใช่เทคโนโลยี
- **CapEx กับ OpEx**: โครงสร้างพื้นฐาน on-premises เป็นรายจ่ายฝ่ายทุน (CapEx — ซื้อฮาร์ดแวร์ล่วงหน้า) คลาวด์เป็นรายจ่ายในการดำเนินงาน (OpEx — ค่าใช้จ่ายใช้งานที่เกิดซ้ำ) สถานการณ์การสอบที่ถามเกี่ยวกับ "การขจัดต้นทุนล่วงหน้า" หรือ "การเปลี่ยนจาก CapEx เป็น OpEx" ชี้ไปที่การนำคลาวด์มาใช้
- **ประโยชน์ของคลาวด์**: ไม่มีฮาร์ดแวร์ล่วงหน้า การปรับขนาดอย่างยืดหยุ่น จ่ายเฉพาะสิ่งที่คุณใช้ ไม่มีการจัดการโครงสร้างพื้นฐานทางกายภาพ สถานการณ์ที่มี "ปริมาณการใช้งานที่คาดเดาไม่ได้" หรือ "ทีมเล็ก ไม่มีความเชี่ยวชาญฮาร์ดแวร์" เป็นสัญญาณที่ชัดเจนสำหรับคลาวด์
- **AWS ไม่ใช่คลาวด์เดียว** — Azure และ GCP เป็นคู่แข่งที่จริงจัง — แต่การสอบ SAA-C03 เฉพาะสำหรับ AWS คุณจะไม่ถูกถามให้เปรียบเทียบผู้ให้บริการ

## จุดแข็งและข้อจำกัด

**จุดแข็งของแนวทางนี้**: การเรียนรู้ผ่านการเล่าเรื่องต่อเนื่องให้บริบทแนวคิดก่อนที่จะได้ชื่อ เมื่อถึงตอนที่คุณถึง IAM หรือ RDS คุณก็รู้สึกถึงปัญหาที่พวกมันแก้ไขแล้ว — เพราะ Nimbus รู้สึกมันก่อน สิ่งนี้ทำให้การจดจำสูงขึ้นและการให้เหตุผลการแลกเปลี่ยนเป็นธรรมชาติมากกว่าการท่องจำรายการคุณสมบัติ

**ข้อจำกัดที่ควรทราบ**: หนังสือเล่มนี้ครอบคลุมหลักสูตร AWS SAA-C03 Solutions Architect Associate นั่นเป็นขอบเขตที่สำคัญ แต่ไม่ใช่ทุก AWS service — และสถาปัตยกรรมการผลิตมักเกี่ยวข้องกับ service และข้อจำกัดเฉพาะสำหรับอุตสาหกรรมและขนาดของคุณ เรื่องราว Nimbus เป็นเรื่องสมมติ สตาร์ทอัปจริงตัดสินใจอย่างยุ่งเหยิงกว่าเพราะเหตุผลที่ยุ่งเหยิงกว่า ใช้หนังสือเล่มนี้เพื่อสร้างการใช้เหตุผล ไม่ใช่เพื่อคัดลอกสถาปัตยกรรม

## แบบฝึกหัด

**แบบฝึกหัด 1 — การจำ**

ด้วยคำพูดของคุณเอง: "คลาวด์" คืออะไร และทำไมธุรกิจขนาดเล็กถึงจะเลือกมันแทนที่จะซื้อเซิร์ฟเวอร์ของตัวเอง?

*(คำใบ้: คิดเกี่ยวกับสิ่งที่ Maya และ Tom เขียนข้างตัวเลือก 1 บนไวท์บอร์ด)*

**แบบฝึกหัด 2 — การฝึกสอบ**

*สถานการณ์*: สตาร์ทอัปขนาดเล็กกำลังเปิดตัวแอปพลิเคชันสั่งอาหาร พวกเขาคาดหวังปริมาณการใช้งานต่ำในตอนแรก แต่คาดการณ์การเติบโตอย่างรวดเร็วหากผลิตภัณฑ์ประสบความสำเร็จ ทีมผู้ก่อตั้งไม่มีประสบการณ์ในการจัดการเซิร์ฟเวอร์จริง พวกเขาต้องการลดต้นทุนล่วงหน้าและหลีกเลี่ยงภาระในการดูแลรักษาฮาร์ดแวร์

แนวทางใดต่อไปนี้ตอบสนองความต้องการของพวกเขาได้ดีที่สุด?

ก) ซื้อเซิร์ฟเวอร์เฉพาะและโฮสต์แอปพลิเคชันในสำนักงานของพวกเขา  
ข) ใช้ผู้ให้บริการคลาวด์โฮสต์แอปพลิเคชันและจ่ายเฉพาะสิ่งที่ใช้  
ค) ร่วมมือกับศูนย์ข้อมูล co-location เพื่อติดตั้งเซิร์ฟเวอร์ของตัวเอง  
ง) สร้างแอปพลิเคชันให้ทำงานแบบออฟไลน์อย่างสมบูรณ์โดยไม่มีโครงสร้างพื้นฐานอินเทอร์เน็ต

**คำใบ้ 1**: คิดเกี่ยวกับสิ่งที่สตาร์ทอัปต้องการ *หลีกเลี่ยง* มากพอๆ กับสิ่งที่ต้องการมี

**คำใบ้ 2**: สถานการณ์ระบุ "ไม่มีประสบการณ์ในการจัดการฮาร์ดแวร์" และ "ลดต้นทุนล่วงหน้า" ตัวเลือกใดขจัดข้อกังวลเหล่านั้น?

**คำใบ้ 3**: เราอธิบายตัวเลือกนี้ในบทนี้ว่าการจ่ายเงินสำหรับ "คอมพิวเตอร์ของคนอื่น"

**คำตอบ**: ข

**คำอธิบาย**: ผู้ให้บริการคลาวด์เช่น AWS เสนอการกำหนดราคาแบบจ่ายตามการใช้งานโดยไม่มีต้นทุนฮาร์ดแวร์ล่วงหน้า และพวกเขาจัดการการบำรุงรักษาโครงสร้างพื้นฐานทางกายภาพทั้งหมด นี่คือโมเดลที่เหมาะสมสำหรับสตาร์ทอัปที่มีปริมาณการใช้งานไม่แน่นอนและไม่มีความเชี่ยวชาญด้านฮาร์ดแวร์ — เช่นเดียวกับ Nimbus

**ทำไมไม่ใช่ ก?** การซื้อเซิร์ฟเวอร์เฉพาะต้องใช้เงินทุนล่วงหน้า การบำรุงรักษาอย่างต่อเนื่อง และไม่มีความสามารถในการขยายขนาดในตัวเมื่อปริมาณการใช้งานเพิ่มขึ้น

**ทำไมไม่ใช่ ค?** Co-location แก้ปัญหาพื้นที่แต่สตาร์ทอัปยังต้องซื้อ บำรุงรักษา และจัดการเซิร์ฟเวอร์ของตัวเอง

**ทำไมไม่ใช่ ง?** แอปพลิเคชันสั่งอาหารต้องการการเชื่อมต่ออินเทอร์เน็ตตามนิยาม

*SAA-C03 Domain: ข้ามโดเมน — พื้นฐานแนวคิดคลาวด์*

**แบบฝึกหัด 3 — ความท้าทายด้านสถาปัตยกรรม** *(ตัวเลือก)*

Maya ต้องการโน้มน้าวลุงของเธอ (ที่เป็นเจ้าของร้านอาหาร) ให้อนุญาตให้เธอสร้างระบบสั่งอาหารบนคลาวด์ เขาสงสัย: "ทำไมเราต้องจ่ายให้ Amazon ทุกเดือนในเมื่อเราแค่ซื้อคอมพิวเตอร์ครั้งเดียวก็ได้?"
