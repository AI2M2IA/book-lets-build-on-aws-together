# บทที่ 1: ทำไมต้องเช่าเมื่อคุณเป็นเจ้าของได้?

Tom นั่งอยู่กับคำถามนั้นตั้งแต่คืนก่อน เขาเขียนมันลงในสมุด แล้วก็ขีดทิ้ง แล้วก็เขียนใหม่

เมื่อ Leo และ Priya มาถึงในเช้าวันรุ่งขึ้น — กาแฟในมือ ถกเถียงเรื่องอะไรบางอย่างที่ไม่เกี่ยวข้อง — Tom ยืนอยู่ที่ไวท์บอร์ดแล้ว ตัวเลือกที่สามยังอยู่ที่นั่น ยังไม่ได้แตะ รูปร่างเมฆที่วาดโดยคนที่ยอมรับว่าไม่รู้ว่ามันหมายความว่าอะไร

"ผมต้องการให้ใครสักคนอธิบายบางอย่างให้ผมฟัง" Tom พูดโดยไม่หันกลับมา "ถ้าเราเช่าคอมพิวเตอร์จาก Amazon แทนที่จะซื้อของเราเอง — ทำไมถึงจะ *ถูกกว่า*?"

ห้องเงียบ มันเป็นคำถามประเภทที่ฟังดูเรียบง่ายแต่ไม่ใช่

"เพราะ" Leo เริ่มต้น

"ไม่" Tom พูด "ผมอยากเข้าใจมัน ไม่ใช่แค่ได้ยินคำตอบ ทำไมการเช่าถึงถูกกว่าการเป็นเจ้าของ?"

**ปัญหาที่ชัดเจนของการเป็นเจ้าของเซิร์ฟเวอร์**

ลองนึกภาพว่าคุณตัดสินใจเปิดร้านอาหาร ไม่ใช่แบบ Nimbus — ร้านอาหารทั่วไป

ก่อนที่ลูกค้าคนแรกจะเดินเข้ามา คุณต้องมีโต๊ะ เก้าอี้ ครัว เตา จาน พนักงาน คุณต้องมีทุกอย่างนี้ตั้งแต่วันแรก แม้ว่าสัปดาห์แรกจะช้า แม้ว่าคุณจะใช้เวลาสามเดือนกับลูกค้าหกคนต่อวันก่อนที่ข่าวจะแพร่กระจาย

เซิร์ฟเวอร์ทางกายภาพก็ทำงานเหมือนกัน

ถ้า Nimbus ซื้อเซิร์ฟเวอร์ของตัวเอง พวกเขาต้องซื้อสำหรับยอดสูงสุดที่พวกเขาคาดว่าจะเกิดขึ้น คืนวันศุกร์ที่วุ่นวายที่สุดที่พวกเขาจินตนาการได้ ช่วงเวลา viral ที่บล็อกเกอร์อาหารเขียนเกี่ยวกับ arepa และหมื่นคนพยายามสั่งในคราวเดียว

แต่ส่วนใหญ่แล้วมันไม่ได้วุ่นวายขนาดนั้น ส่วนใหญ่แล้วเซิร์ฟเวอร์พวกนั้นก็แค่นั่งอยู่นั่น ใช้ไฟฟ้า ทำแทบไม่มีอะไร

"เราจะต้องจ่ายสำหรับกำลังการผลิตที่เราไม่ได้ใช้" Maya พูด

"นั่นแหละ" Tom พูด ซึ่งทำให้ทุกคนประหลาดใจเพราะเขาเป็นคนถามคำถาม

**โมเดลการเช่า**

นี่คือสิ่งที่ทำให้การประมวลผลแบบคลาวด์แตกต่าง

เมื่อคุณใช้ AWS คุณไม่ได้ซื้อเซิร์ฟเวอร์ คุณเช่าพลังการประมวลผลและคุณจ่ายเฉพาะสิ่งที่คุณใช้ มันใกล้เคียงกับการเช่าสถานที่มากกว่าการเป็นเจ้าของอาคารร้านอาหาร

ลองคิดแบบนี้

ถ้าคุณต้องการจัดงานปาร์ตี้วันเกิดสำหรับห้าสิบคน คุณสามารถซื้อบ้านที่ใหญ่พอสำหรับห้าสิบคนพร้อมโต๊ะและเก้าอี้ของพวกเขา หรือคุณสามารถเช่าสถานที่สี่ชั่วโมงในวันเสาร์ จ่ายเฉพาะพื้นที่และเวลาที่คุณต้องการ และคืนกุญแจเมื่อปาร์ตี้เสร็จ

สถานที่ยังอยู่ที่นั่นเมื่อคุณต้องการ มันพร้อมใช้งานอีกครั้งเมื่อมีอะไรอื่นเกิดขึ้น คุณไม่ต้องจ้างผู้จัดการอาคาร คุณไม่ได้จ่ายภาษีทรัพย์สินสำหรับมันตลอดทั้งปี

นั่นคือโมเดลคลาวด์ AWS มี "สถานที่" คุณมาเมื่อคุณต้องการ

**แต่รอก่อน — ยังมีอีก**

"โอเค" Leo พูด "แต่ถ้าสถานที่ของผมถูกไฟไหม้ล่ะ?"

สัญชาตญาณดี มืดหน่อย แต่ดี

หนึ่งในสมมติฐานที่ไม่พูดถึงเมื่อคุณเป็นเจ้าของเซิร์ฟเวอร์ของตัวเองคือ *คุณ* รับผิดชอบในการรักษาให้มันทำงาน ถ้าเซิร์ฟเวอร์ในสำนักงานของคุณถูกนักศึกษาฝึกงานที่งุ่มง่ามล้มลง เว็บไซต์ของคุณก็ล่ม ถ้าอาคารสูญเสียไฟฟ้า เว็บไซต์ของคุณก็ล่ม ถ้าฮาร์ดดิสก์เสีย — และฮาร์ดดิสก์มักเสียในที่สุด — เว็บไซต์ของคุณก็ล่ม

AWS ดำเนินงานศูนย์ข้อมูล สิ่งอำนวยความสะดวกขนาดใหญ่ที่จัดการอย่างมืออาชีพพร้อมพลังงานสำรอง การเชื่อมต่อเครือข่ายซ้ำซ้อน ความปลอดภัยทางกายภาพ และทีมวิศวกรที่งานเดียวของพวกเขาคือรักษาให้เครื่องจักรเหล่านั้นทำงาน

คุณไม่ได้แค่เช่าพลังการประมวลผล คุณเช่าความน่าเชื่อถือ

"มันราคาเท่าไหร่?" Tom ถาม

เราจะพูดถึงเรื่องนั้น อีกหลายบทจากนี้ เมื่อดวงตาของ Tom จะไม่เหม่อลอย

**สามสิ่งที่คลาวด์ทำแตกต่าง**

มาทำให้เป็นรูปธรรม นี่คือความแตกต่างหลักสามประการระหว่างการรันเซิร์ฟเวอร์ของตัวเองกับการใช้ผู้ให้บริการคลาวด์

**1. คุณจ่ายสำหรับสิ่งที่คุณใช้**

ไม่มีเซิร์ฟเวอร์ที่นั่งว่าง ไม่มีการซื้อล่วงหน้า ถ้า Nimbus ไม่ได้รับออร์เดอร์ในเช้าวันจันทร์ พวกเขาจ่ายแทบไม่มีอะไร ถ้าพวกเขาล้นมือในคืนปีใหม่ AWS มีกำลังการผลิตพร้อมอัตโนมัติ

**2. คนอื่นจัดการฮาร์ดแวร์**

AWS ดูแลเครื่องจักรทางกายภาพ สายเคเบิลเครือข่าย แหล่งจ่ายไฟ ระบบระบายความร้อน Nimbus ไม่ต้องจ้างใครทำสิ่งนี้ พวกเขามุ่งเน้นที่แอปพลิเคชันของตนเอง ไม่ใช่โครงสร้างพื้นฐานข้างใต้

**3. คุณสามารถขยายขึ้น — และลง — ได้ทันที**

นี่คือสิ่งที่ต้องใช้เวลาหน่อยในการชื่นชมอย่างเต็มที่ ด้วยเซิร์ฟเวอร์ทางกายภาพ การขยายขึ้นหมายถึงการสั่งฮาร์ดแวร์ใหม่ รอสัปดาห์เพื่อจัดส่ง ตั้งค่า ด้วย AWS การขยายขึ้นหมายถึงการกดปุ่ม (หรือให้ระบบทำโดยอัตโนมัติ) และเมื่อคุณไม่ต้องการกำลังการผลิตเพิ่มเติมอีกต่อไป คุณก็ลดขนาดลง คุณหยุดจ่าย

Priya เงียบในระหว่างคำอธิบายนี้ เธอมีคำถาม

"แล้วเรื่องความปลอดภัยล่ะ? ใครรับผิดชอบในการรักษาความปลอดภัยข้อมูล?"

และนั่นคือที่ที่มันน่าสนใจ

**โมเดลความรับผิดชอบร่วมกัน**

นี่เป็นหนึ่งในแนวคิดที่สำคัญที่สุดใน AWS ทั้งหมด มันเรียบง่ายเมื่อคุณเข้าใจ แต่มันทำให้คนสะดุดมาก — รวมถึงในการสอบ

AWS และคุณแบ่งปันความรับผิดชอบด้านความปลอดภัย แต่แต่ละฝ่ายรับผิดชอบสิ่งที่แตกต่างกัน

**AWS รับผิดชอบความปลอดภัย *ของ* คลาวด์**

ศูนย์ข้อมูลทางกายภาพ ฮาร์ดแวร์ โครงสร้างพื้นฐานเครือข่าย Hypervisor ที่รันเครื่องเสมือน ถ้ามีคนบุกรุกศูนย์ข้อมูลของ AWS นั่นเป็นปัญหาของ Amazon

**คุณรับผิดชอบความปลอดภัย *ใน* คลาวด์**

ข้อมูลของคุณ แอปพลิเคชันของคุณ บัญชีผู้ใช้ของคุณและใครสามารถเข้าถึงอะไรได้ การตั้งค่าที่คุณเลือก ถ้าใครขโมยรหัสผ่านของคุณและเข้าสู่ระบบบัญชี AWS ของคุณ นั่นเป็นปัญหาของคุณ

Priya พยักหน้าช้าๆ "พวกเขาปกป้องตัวอาคาร เราปกป้องสิ่งที่อยู่ข้างใน"

"นั่นแหละ" Maya พูด

"แล้วถ้า Leo เปิด port ที่ไม่ควร..."

"ยังเป็นปัญหาของเรา" Maya ยืนยัน มองไปที่ Leo

Leo กำลังพิมพ์อะไรบางอย่างบนแล็ปท็อปและแสร้งทำเป็นว่าไม่ได้ยิน

## จุดแข็งและข้อจำกัด

ไม่มีเครื่องมือใดที่สมบูรณ์แบบ มาพูดถึงทั้งสองด้านอย่างตรงไปตรงมา

**ทำไมคลาวด์จึงดีเยี่ยม**:

- ไม่มีต้นทุนฮาร์ดแวร์ล่วงหน้า
- จ่ายเฉพาะสิ่งที่คุณใช้
- ขยายขนาดได้ทันทีในทั้งสองทิศทาง
- ความน่าเชื่อถือและความปลอดภัยทางกายภาพระดับมืออาชีพ
- เข้าถึงบริการที่จัดการหลายร้อยรายการ (ฐานข้อมูล คิว machine learning และอื่นๆ)
  โดยไม่ต้องสร้างหรือดูแลรักษาด้วยตัวเอง

**ที่ซึ่งมันซับซ้อนขึ้น**:

- ค่าใช้จ่ายอาจคาดเดาไม่ได้ถ้าคุณไม่ใส่ใจ (ฝันร้ายในอนาคตของ Tom)
- คุณพึ่งพาบุคคลที่สามสำหรับโครงสร้างพื้นฐาน — ถ้า AWS มีการหยุดทำงานใน
  region ของคุณ บริการของคุณก็ได้รับผลกระทบเช่นกัน
- มีเส้นการเรียนรู้ AWS มีบริการหลายร้อยรายการ การรู้ว่าควรใช้อะไร
  ต้องการประสบการณ์หรือหนังสือเช่นนี้
- ข้อมูลที่ออกจากคลาวด์อาจมีราคาแพง การย้ายข้อมูลจำนวนมากออกจาก AWS
  เสียค่าใช้จ่าย (เราจะพูดถึงเรื่องนี้อีกครั้งในบทที่ 30)

"เราแลกเปลี่ยนการควบคุมเพื่อความสะดวก" Tom พูด

"และแลกเปลี่ยนต้นทุนล่วงหน้าเพื่อต้นทุนต่อเนื่อง" Maya เพิ่มเติม

"และแลกเปลี่ยนปัญหาของคนอื่นเป็นปัญหาของตัวเองในด้านความปลอดภัย" Priya พูด

"แต่เราก็แลกเปลี่ยนเซิร์ฟเวอร์ที่เสียของ Leo เป็นเซิร์ฟเวอร์ที่ไม่เสียมากของ Amazon" Leo พูด ซึ่งดูเหมือนว่าเขาฟังอยู่ตลอดเวลา

เขาไม่ได้ผิดเสียทีเดียว

## สรุป

- คลาวด์คือพลังการประมวลผลที่คุณเช่าแทนที่จะเป็นเจ้าของ
- AWS คือผู้ให้บริการคลาวด์ที่ใหญ่ที่สุดในโลก
- ประโยชน์หลักคือการปรับขนาดแบบจ่ายตามการใช้งาน: คุณจ่ายเฉพาะสิ่งที่คุณใช้ และคุณ
  สามารถขยายขนาดขึ้นหรือลงตามต้องการ
- AWS จัดการโครงสร้างพื้นฐานทางกายภาพ คุณจัดการแอปพลิเคชัน ข้อมูล
  และการตั้งค่าของคุณ การแบ่งนี้เรียกว่า **โมเดลความรับผิดชอบร่วมกัน**
- คลาวด์ไม่ได้ถูกกว่าหรือง่ายกว่าเสมอ — แต่มันขจัดอุปสรรคในการเริ่มต้น
  และทำให้การปรับขนาดเป็นไปได้ในแบบที่เซิร์ฟเวอร์ทางกายภาพไม่สามารถทำได้

## เคล็ดลับการสอบ

*SAA-C03 Domain: ข้ามโดเมน — พื้นฐานแนวคิดคลาวด์*

- **โมเดลความรับผิดชอบร่วมกัน** ปรากฏในการสอบอย่างสม่ำเสมอ จำว่า: AWS
  รับผิดชอบความปลอดภัย *ของ* คลาวด์ (ฮาร์ดแวร์ ศูนย์ข้อมูล เครือข่ายทั่วโลก)
  คุณรับผิดชอบความปลอดภัย *ใน* คลาวด์ (ข้อมูล ตัวตน การกำหนดค่าแอปพลิเคชัน)
- **ความแตกต่างที่สำคัญ**: การแบ่งเปลี่ยนแปลงตามประเภทบริการ สำหรับ EC2
  (เครื่องเสมือนที่คุณควบคุม) *คุณ* patch ระบบปฏิบัติการ สำหรับ RDS (a
  ฐานข้อมูลที่จัดการ) AWS patch engine ฐานข้อมูล ยิ่งบริการ "จัดการ" มากเท่าไหร่
  ยิ่งมีความรับผิดชอบย้ายไปยัง AWS มากขึ้น สถานการณ์การสอบจะอธิบายเหตุการณ์
  และถามว่าใครรับผิดชอบ — ถามเสมอว่า "บริการนี้ได้รับการจัดการมากแค่ไหน?"
- คำถามเกี่ยวกับ *ประโยชน์* ของคลาวด์มักทดสอบ CapEx กับ OpEx ฮาร์ดแวร์ on-premises
  เป็นรายจ่ายฝ่ายทุน (CapEx — ซื้อครั้งเดียว คิดค่าเสื่อมราคาเมื่อเวลาผ่านไป) คลาวด์เป็น
  รายจ่ายในการดำเนินงาน (OpEx — จ่ายรายเดือน) AWS เปลี่ยนต้นทุนจาก CapEx เป็น OpEx
- "ความยืดหยุ่น" — ความสามารถในการขยายขึ้น *และลง* โดยอัตโนมัติ — เป็นประโยชน์คลาวด์หลัก
  คุณอาจเห็นมันจับคู่กับ "ความสามารถในการขยาย" ในการสอบ ความยืดหยุ่นหมายถึง
  การปรับขนาดอัตโนมัติที่ขับเคลื่อนโดยความต้องการในทั้งสองทิศทาง ความสามารถในการขยายหมายถึงระบบ
  *สามารถ* เติบโตได้ แต่ไม่จำเป็นต้องหดตัวโดยอัตโนมัติ

## แบบฝึกหัด

**แบบฝึกหัด 1 — การจำ**

ด้วยคำพูดของคุณเอง: อธิบายโมเดลความรับผิดชอบร่วมกัน ใครรับผิดชอบอะไร
และทำไมความแตกต่างนั้นจึงสำคัญ?

*(คำใบ้: คิดถึงการเปรียบเทียบของ Priya — ใครปกป้องอาคาร และใครปกป้องสิ่งที่อยู่ข้างใน)*

**แบบฝึกหัด 2 — การฝึกสอบ**

*สถานการณ์*: บริษัทกำลังย้ายแอปพลิเคชันเว็บจากศูนย์ข้อมูล on-premises
ไปยัง AWS ทีมความปลอดภัยกังวลเกี่ยวกับการรักษาการปฏิบัติตามนโยบายการปกป้องข้อมูล วิศวกรใหม่ถาม: "ตอนนี้เราอยู่บน AWS Amazon จัดการ
ความต้องการด้านความปลอดภัยทั้งหมดของเราหรือเปล่า?"

ข้อใดต่อไปนี้ BEST อธิบายวิธีการแบ่งความรับผิดชอบด้านความปลอดภัย?

ก) AWS รับผิดชอบอย่างสมบูรณ์ต่อความปลอดภัยทั้งหมดเมื่อแอปพลิเคชันถูกโฮสต์ในคลาวด์  
ข) ลูกค้ารับผิดชอบอย่างสมบูรณ์ต่อความปลอดภัยทั้งหมด รวมถึงความปลอดภัยศูนย์ข้อมูลทางกายภาพ  
ค) AWS จัดการความปลอดภัยของโครงสร้างพื้นฐานพื้นฐาน ลูกค้าจัดการความปลอดภัยของข้อมูล แอปพลิเคชัน และการตั้งค่าของตน  
ง) ความรับผิดชอบด้านความปลอดภัยถูกเจรจาต่อรองตามบัญชีและขึ้นอยู่กับระดับบริการของลูกค้า

**คำใบ้ 1**: คิดเกี่ยวกับสิ่งที่ AWS ควบคุมทางกายภาพเทียบกับสิ่งที่คุณควบคุม

**คำใบ้ 2**: AWS เป็นเจ้าของศูนย์ข้อมูล คุณเลือกสิ่งที่จะนำใส่และวิธีกำหนดค่าแอปพลิเคชันของคุณ

**คำใบ้ 3**: เราแนะนำชื่อเฉพาะสำหรับการแบ่งความรับผิดชอบนี้ในบทนี้

**คำตอบ**: ค

**คำอธิบาย**: โมเดลความรับผิดชอบร่วมกันของ AWS แบ่งความปลอดภัยออกเป็นสองโดเมน
AWS รักษาความปลอดภัยโครงสร้างพื้นฐานทางกายภาพ — ศูนย์ข้อมูล ฮาร์ดแวร์ และเครือข่าย
ลูกค้ารักษาความปลอดภัยทุกอย่างที่พวกเขา deploy ขึ้นไป: ข้อมูล การควบคุมการเข้าถึง การกำหนดค่าแอปพลิเคชัน และการตั้งค่าเครือข่ายของพวกเขา

**ทำไมไม่ใช่ ก?** AWS ไม่เคยรับผิดชอบอย่างสมบูรณ์ต่อความปลอดภัยแอปพลิเคชันลูกค้า
ทันทีที่คุณกำหนดค่าบางอย่าง การกำหนดค่านั้นเป็นของคุณเพื่อจัดการ

**ทำไมไม่ใช่ ข?** ลูกค้าไม่รับผิดชอบต่อความปลอดภัยศูนย์ข้อมูลทางกายภาพ —
นั่นคือหนึ่งในข้อได้เปรียบของการใช้ AWS พอดี

**ทำไมไม่ใช่ ง?** โมเดลความรับผิดชอบร่วมกันเป็นกรอบที่แน่นอน ไม่ใช่การจัดการที่เจรจาต่อรอง

*SAA-C03 Domain: ข้ามโดเมน — แนวคิดคลาวด์ / ความรับผิดชอบร่วมกัน*

**แบบฝึกหัด 3 — ความท้าทายด้านสถาปัตยกรรม** *(ตัวเลือก)*

เพื่อนกำลังเปิดตัวแอปใหม่และขอความคิดเห็นของคุณ พวกเขากำลังตัดสินใจระหว่าง
การซื้อเซิร์ฟเวอร์ทางกายภาพสองเครื่อง (หนึ่งสำหรับแอป หนึ่งสำหรับฐานข้อมูล) หรือใช้ผู้ให้บริการคลาวด์ ปริมาณการใช้งานที่คาดการณ์ของพวกเขาคือ 10-100 ผู้ใช้ต่อวัน แต่พวกเขามีงานเปิดตัว
ในสามเดือนที่อาจนำมาซึ่ง 10,000 ผู้ใช้ในวันเดียว

พิจารณาการแลกเปลี่ยน คุณจะแนะนำตัวเลือกใด และเหตุผลหลักคืออะไร? คุณจะสละอะไรกับตัวเลือกของคุณ?
