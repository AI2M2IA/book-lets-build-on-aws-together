**แนวคิด: การจัดการข้อมูลประจำตัวและการเข้าถึง**

ทางเลือกอื่นคือระบบที่คุณไม่ได้ให้คีย์เดียวกันแก่ทุกคน คุณให้แต่ละคน — และแต่ละบริการ — มีสิทธิ์เข้าถึงที่พวกเขาต้องการอย่างแม่นยำ ไม่มากกว่า ไม่น้อยกว่า

ใน AWS ระบบนี้เรียกว่า **IAM**: การจัดการข้อมูลประจำตัวและการเข้าถึง

คิดว่า IAM เหมือนระบบบัตรกุญแจในอาคารสำนักงานขนาดใหญ่

อาคารมีหลายสิบชั้น ห้องเซิร์ฟเวอร์อยู่ชั้น 12 สำนักงานการเงินอยู่ชั้น 8 ห้องชุด CEO อยู่ชั้น 20 พนักงานทุกคนมีบัตรกุญแจ แต่แต่ละบัตรเปิดได้เฉพาะประตูที่พนักงานคนนั้นต้องเปิดสำหรับงานของตน นักฝึกงานไม่สามารถรูดเข้าห้องเซิร์ฟเวอร์ได้ นักบัญชีไม่สามารถเข้าชั้นผู้บริหารหลังเวลาทำการ

IAM ทำงานในแบบเดียวกัน คุณกำหนดว่าใครมีตัวตน (ข้อมูลประจำตัว) สิ่งที่พวกเขาได้รับอนุญาตให้ทำ (สิทธิ์) และใช้สิทธิ์เหล่านั้นผ่าน policies

**องค์ประกอบพื้นฐานของ IAM**

IAM มีสี่แนวคิดหลัก สิ่งเหล่านี้สร้างขึ้นต่อกัน

**Users** คือข้อมูลประจำตัวส่วนบุคคล Maya มี IAM user Tom มี IAM user แต่ละ user มีข้อมูลประจำตัวของตัวเอง — และควรมีเฉพาะสิทธิ์ที่พวกเขาต้องการโดยเฉพาะ

**Groups** คือกลุ่มของ users แทนที่จะตั้งค่าสิทธิ์สำหรับ Maya, Tom, Priya และ Leo แยกกัน คุณสร้างกลุ่ม "Developers" ที่มีสิทธิ์นักพัฒนาและเพิ่มพวกเขาเข้าไป เมื่อคนที่ห้าเข้าร่วม คุณเพิ่มพวกเขาในกลุ่มและพวกเขาสืบทอดสิทธิ์ที่ถูกต้องทันที

**Roles** คือข้อมูลประจำตัวชั่วคราวที่สามารถ *รับช่วง* โดยบางสิ่ง — คน บริการ หรือบัญชี AWS อื่น เราจะเจาะลึกใน roles ในบทที่ 14 สำหรับตอนนี้: ถ้า User เป็นพนักงานถาวร Role คือบัตรผ่านสำหรับผู้เยี่ยมชม มันให้สิทธิ์เข้าถึงเฉพาะเจาะจงสำหรับเวลาหรือวัตถุประสงค์เฉพาะ

**Policies** คือกฎสิทธิ์จริงๆ Policy คือเอกสาร (เขียนใน JSON ภายใน แต่ไม่จำเป็นต้องจำรูปแบบ) ที่ระบุว่า: "ผู้ถือ policy นี้ได้รับอนุญาตให้ดำเนินการ X บนทรัพยากร Y" หรือ "ถูกปฏิเสธการดำเนินการ Z"

โมเดลการประเมิน IAM คือ: โดยค่าเริ่มต้นทุกอย่างถูกปฏิเสธ ต้องให้สิทธิ์อย่างชัดเจน ถ้า policy ไม่ระบุว่าคุณสามารถทำอะไรได้ คุณก็ทำไม่ได้

**เกิดอะไรขึ้นเมื่อคุณทำสิ่งนี้ผิด**

สามสถานการณ์ เรียงตามความรุนแรงที่เพิ่มขึ้น:

**สถานการณ์ 1**: พนักงานที่มีสิทธิ์ admin ลาออก ไม่มีใครปิดใช้งานบัญชีของพวกเขา สามเดือนต่อมา พวกเขายังมีสิทธิ์เข้าถึง สิ่งนี้เกิดขึ้นตลอดเวลา IAM แก้ปัญหาได้: คุณปิดใช้งาน user ทันที ทุกที่

**สถานการณ์ 2**: แล็ปท็อปของนักพัฒนาถูกบุกรุก ผู้โจมตีพบข้อมูลประจำตัว AWS ที่จัดเก็บไว้ในไฟล์ config พร้อมสิทธิ์ admin เต็มรูปแบบ เนื่องจากข้อมูลประจำตัวมีสิทธิ์เข้าถึงกว้าง ผู้โจมตีสามารถทำอะไรก็ได้ ด้วยหลักการสิทธิ์ขั้นต่ำ: ข้อมูลประจำตัวทำงานได้เฉพาะสำหรับขอบเขตจำกัดของพวกมัน รัศมีความเสียหายถูกควบคุม

**สถานการณ์ 3**: แอปพลิเคชันที่เขียนไม่ดีเปิดเผยข้อมูลประจำตัว AWS ในบันทึกของมัน ถ้าข้อมูลประจำตัยเหล่านั้นมีสิทธิ์เข้าถึงกว้าง คุณมีการละเมิดที่เป็นหายนะ ถ้ามีสิทธิ์เข้าถึงแคบ — เฉพาะ S3 bucket ที่แอปพลิเคชันต้องการ — การเปิดเผยถูกจำกัดและควบคุม

รูปแบบ: การเข้าถึงควรถูกจำกัดให้น้อยที่สุด เสมอ ไม่ใช่เพราะคุณไม่ไว้ใจคนของคุณ แต่เพราะคุณไม่สามารถควบคุมสิ่งที่เกิดขึ้นกับข้อมูลประจำตัวที่ถูกบุกรุก

**การยืนยันตัวตนแบบหลายปัจจัย: การล็อคที่สอง**

อีกแนวคิดหนึ่งก่อนที่เราจะปิดบท

แม้จะมีหลักการสิทธิ์ขั้นต่ำ ข้อมูลประจำตัวก็ยังถูกขโมยได้ รหัสผ่านสามารถถูกเดา ถูก phish หรือรั่วไหลได้ IAM แก้ปัญหานี้ด้วย **การยืนยันตัวตนแบบหลายปัจจัย (MFA)**

MFA ต้องการสิ่งที่คุณ *รู้* (รหัสผ่าน) บวกกับสิ่งที่คุณ *มี* (โทรศัพท์ กุญแจฮาร์ดแวร์) แม้ผู้โจมตีขโมยรหัสผ่านของคุณ พวกเขาก็ไม่สามารถเข้าสู่ระบบได้หากไม่มีโทรศัพท์ของคุณด้วย

ควรเปิดใช้งาน MFA สำหรับ IAM user ทุกคน มันเป็นสิ่งที่ไม่สามารถต่อรองได้สำหรับบัญชี root

## จุดแข็งและข้อจำกัด

**IAM เป็นเครื่องมือที่เหมาะสำหรับ**: การควบคุมว่าใครและอะไรสามารถเข้าถึงทรัพยากร AWS ทุกอย่างได้; การนำหลักการสิทธิ์ขั้นต่ำมาใช้กับ users, services และขอบเขตข้ามบัญชี; การสร้างเส้นทางการตรวจสอบของทุกการเรียก API ผ่านการรวม CloudTrail; การขจัดความจำเป็นในการแชร์ข้อมูลประจำตัวที่มีอายุยาวนานระหว่างระบบ

**ที่ซึ่ง IAM ยากขึ้น**: policies IAM สามารถเติบโตเป็นหลายร้อย statements ข้าม roles หลายสิบอัน และการ debug ข้อผิดพลาด "Access Denied" ต้องการการทำความเข้าใจว่า policy ใดเป็น policy ที่มีผล — งานที่ยากกว่าที่ฟังดู สิ่งที่ผิดพลาดใน IAM มากที่สุดไม่ใช่การเข้าถึงน้อยเกินไป — มันเป็นมากเกินไป

## สรุป

- **IAM** (การจัดการข้อมูลประจำตัวและการเข้าถึง) คือวิธีที่คุณควบคุมว่าใครสามารถทำอะไรใน AWS
- องค์ประกอบพื้นฐานหลักคือ: **Users** (บุคคล), **Groups** (กลุ่มของ users), **Roles** (ข้อมูลประจำตัวชั่วคราว) และ **Policies** (กฎสิทธิ์)
- โดยค่าเริ่มต้น ทุกอย่างใน AWS ถูก **ปฏิเสธ** ต้องให้สิทธิ์อย่างชัดเจน
- **หลักการสิทธิ์ขั้นต่ำ** หมายถึงการให้แต่ละข้อมูลประจำตัวมีเฉพาะสิทธิ์เข้าถึงที่ต้องการ ไม่มากกว่านั้น
- **บัญชี root** สามารถทำอะไรก็ได้ รวมถึงสิ่งที่เป็นหายนะ ล็อคมันไว้ด้วย MFA และใช้งานน้อยที่สุด
- เปิดใช้งาน **MFA** สำหรับทุก IAM user ไม่สามารถต่อรองได้

## เคล็ดลับการสอบ

*SAA-C03 Domain 1 — Task 1.1 (การเข้าถึงทรัพยากร AWS อย่างปลอดภัย)*

- **ทุกอย่างถูกปฏิเสธโดยค่าเริ่มต้น** ต้องการ "Allow" อย่างชัดเจน ถ้า policy ไม่กล่าวถึงการกระทำ การกระทำนั้นถูกปฏิเสธ
- **Explicit Deny ชนะเสมอ** ถ้า policy ใดๆ ในห่วงโซ่ปฏิเสธการกระทำ การปฏิเสธนั้นไม่สามารถถูกแทนที่ด้วย Allow ที่อื่นใดในห่วงโซ่
- **บัญชี root ≠ admin IAM** บัญชี root เป็นข้อมูลประจำตัวแยกต่างหากจาก IAM คุณไม่สามารถลบบัญชี root ได้ คุณ *สามารถ* (และควร) จำกัดเมื่อไหร่ที่ใช้
- **IAM เป็น global** ไม่ใช่ Regional IAM users, groups, roles และ policies มีอยู่ทั่วทั้งบัญชี AWS ไม่ใช่ต่อ Region
- **Roles เป็นวิธีที่ต้องการในการให้สิทธิ์เข้าถึง AWS services** ถ้า EC2 instance ต้องการเข้าถึง S3 คุณแนบ IAM Role เข้ากับ instance — คุณไม่เก็บข้อมูลประจำตัวบนเครื่อง

**แบบฝึกหัด 2 — การฝึกสอบ**

*สถานการณ์*: บริษัทรัน web application บน EC2 instances ที่ต้องอ่านไฟล์จาก S3 bucket นักพัฒนาระดับจูเนียร์เสนอให้เก็บ AWS access keys ไว้ในโค้ดแอปพลิเคชันบน EC2 instances โดยตรง ทีมความปลอดภัยคัดค้าน

วิธีแก้ปัญหาใดที่ปลอดภัยที่สุดและเหมาะสมในการดำเนินงานมากที่สุด?

ก) เก็บ access keys ในตัวแปรสภาพแวดล้อมบน EC2 instance แทนที่จะเป็น code  
ข) สร้าง IAM user เฉพาะที่มีสิทธิ์อ่าน S3 และแชร์ข้อมูลประจำตัวกับทีมพัฒนา  
ค) แนบ IAM Role ที่มีสิทธิ์อ่าน S3 ที่เหมาะสมเข้ากับ EC2 instances โดยตรง  
ง) ใช้ข้อมูลประจำตัวบัญชี root เพื่อให้แอปพลิเคชันเข้าถึงทรัพยากร AWS ทั้งหมดได้อย่างสมบูรณ์

**คำตอบ**: ค

**คำอธิบาย**: การแนบ IAM Role เข้ากับ EC2 instance คือรูปแบบที่ถูกต้อง Instance จะได้รับข้อมูลประจำตัวชั่วคราวที่หมุนเวียนโดยอัตโนมัติผ่านบริการ metadata EC2 ไม่มีข้อมูลประจำตัวที่มีอายุยาวนานที่จะรั่วไหล หมุนเวียน หรือ commit โดยไม่ตั้งใจไปยัง repository
