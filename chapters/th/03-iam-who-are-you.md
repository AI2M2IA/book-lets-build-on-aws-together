วิกฤตสิงคโปร์ผ่านพ้นไปแล้ว region ถูกแก้แล้ว เซิร์ฟเวอร์รันอยู่ใน us-west-2 และทีมก็รู้สึกว่ามีความสามารถอยู่ครู่หนึ่ง ความรู้สึกนั้นกินเวลาประมาณสี่สิบแปดชั่วโมงก่อนที่ปัญหาใหม่จะโผล่ขึ้นมา: Leo deploy ไป production ไม่ได้ ไม่มีใครตั้งค่าสิทธิ์ของเขา ไม่มีใครตั้งค่าสิทธิ์ของใครเลย บัญชี AWS เปิดโล่งที่ระดับ root และล็อกตายที่อื่นทุกที่ และไม่มีใครสังเกตเพราะไม่มีใครเคยลอง

นั่นคือปัญหา

**ปัญหากับรหัสผ่าน**

รหัสผ่านเป็นโมเดลที่ไม่ดีสำหรับระบบคอมพิวเตอร์

ไม่ใช่เพราะมันอ่อนแอเสมอ แต่เพราะมันเป็นแบบไบนารี: คุณมีรหัสผ่านหรือไม่มี ถ้าคุณมี คุณทำอะไรก็ได้ที่บัญชีได้รับอนุญาตให้ทำ

นั่นโอเคสำหรับผู้ใช้คนเดียวบนแล็ปท็อปส่วนตัว แต่มันเป็นหายนะสำหรับโครงสร้างพื้นฐานคลาวด์ของบริษัท

ลองพิจารณาสิ่งที่ Nimbus ต้องจัดการ: เว็บเซิร์ฟเวอร์ ฐานข้อมูล การจัดเก็บไฟล์ เครือข่าย การแจ้งเตือนการเรียกเก็บเงิน บัญชีผู้ใช้ ถ้าทุกอย่างได้รับการปกป้องด้วยรหัสผ่านเดียว — หรือแม้แต่ชุดข้อมูลประจำตัวเดียว — ใครก็ตามที่ได้รหัสผ่านนั้นก็ได้ทุกอย่าง

และ "ทุกอย่าง" บน AWS หมายถึงความสามารถในการลบฐานข้อมูล เปิดเซิร์ฟเวอร์ที่สร้างบิล $50,000 ดูดทุกบันทึกลูกค้าออกไป ทำลายข้อมูลสำรอง

มีปัญหาอีกอย่างหนึ่งนอกเหนือจากธรรมชาติแบบไบนารีของรหัสผ่าน: รหัสผ่านเป็นแบบสแตติก พวกมันไม่หมดอายุโดยอัตโนมัติ พวกมันมักถูกใช้ซ้ำข้ามบริการ พวกมันถูกจดลงไป พวกมันถูกเก็บไว้ในสเปรดชีตที่ติดป้ายว่า "รหัสผ่าน ห้ามแชร์" พวกมันถูกแชร์อยู่ดี เพราะความสะดวกชนะความปลอดภัยเมื่อกลไกความปลอดภัยคือความเสียดทาน

ปัญหา "ข้อมูลประจำตัวที่แชร์กัน" ไม่ใช่ข้อบกพร่องด้านนิสัย มันเป็นปัญหาเชิงระบบ เมื่อวิธีเดียวที่จะให้คนเข้าถึงระบบชั่วคราวคือการให้รหัสผ่านถาวรแก่พวกเขา คนก็จะแชร์รหัสผ่าน ทางออกคือการสร้างระบบที่การเข้าถึงชั่วคราวและจำกัดขอบเขตเป็นค่าเริ่มต้น — ไม่ใช่ทางเลี่ยงที่ต้องใช้ความพยายามแบบวีรบุรุษ

นั่นคือสิ่งที่ IAM ทำ ไม่ใช่แค่ "รหัสผ่านที่ดีกว่า" แต่เป็นโมเดลที่แตกต่างโดยพื้นฐานที่การเข้าถึงถูกกำหนดโดยตัวตนและ policy แทนที่จะเป็นโดยใครรู้สตริงของอักขระ

Priya ไม่ได้อธิบายสิ่งนี้ในแง่ที่สงบและเป็นนามธรรม เธออธิบายมันเป็นเรื่องราว

**การละเมิดที่ทำให้เสีย $80,000 ในสี่ชั่วโมง**

นักพัฒนาคนหนึ่งที่สตาร์ทอัปดันสคริปต์ deploy ของ GitHub Actions ไปยัง repository สาธารณะของพวกเขา สคริปต์มีข้อมูลประจำตัว AWS ที่ฮาร์ดโค้ดไว้เป็นตัวแปรสภาพแวดล้อม — ความผิดพลาดที่พบบ่อยพอจะมีหมวดหมู่ของตัวเองในรายงานการชันสูตรความปลอดภัยคลาวด์ ข้อมูลประจำตัวมีสิทธิ์เข้าถึงระดับ admin เต็มรูปแบบของบัญชี AWS ของบริษัท เพราะมีคนกำหนดค่ามันแบบนั้นไว้เมื่อหกเดือนก่อนเพื่อหลีกเลี่ยงการยุ่งกับ policy ของ IAM

ข้อมูลประจำตัวอยู่ในไฟล์ประมาณหกนาทีก่อนที่สแกนเนอร์อัตโนมัติ — ที่รันโดยผู้โจมตี ไม่ใช่นักวิจัยความปลอดภัย — จะพบมัน

สแกนเนอร์จัดทำดัชนีข้อมูลประจำตัว ประเมินสิทธิ์ของบัญชี และเริ่มเปิด GPU instance ในหลาย region GPU instance แพง พวกมันยังมีประโยชน์สำหรับการขุด cryptocurrency ภายในชั่วโมงแรก instance `p3.8xlarge` สี่สิบเจ็ดตัวกำลังรันอยู่ทั่ว `us-east-1`, `eu-west-1` และ `ap-southeast-1`

`p3.8xlarge` มีราคาประมาณ $12 ต่อชั่วโมง สี่สิบเจ็ดตัวมีราคา $564 ต่อชั่วโมง

เมื่อถึงเวลาที่การแจ้งเตือนการเรียกเก็บเงินของสตาร์ทอัปทำงาน — ตั้งค่าไว้ที่ $1,000 ต่อวัน ซึ่งไม่มีใครคิดจะปรับให้เข้มขึ้น — เวลาก็ผ่านไปสี่ชั่วโมง บิลกำลังเข้าใกล้ $2,200 และกำลังไต่ขึ้น

เมื่อถึงเวลาที่มีคนเข้าใจว่าเกิดอะไรขึ้นและเพิกถอนข้อมูลประจำตัว บิลก็ถึง $3,400 สำหรับไม่กี่ชั่วโมงนั้น แต่ต้นทุนที่แท้จริงมาทีหลัง: การตรวจสอบเผยให้เห็นว่าผู้โจมตีขุดมาหลายสัปดาห์แล้ว อย่างเงียบ ๆ ในตอนกลางคืน โดยใช้ชุดข้อมูลประจำตัวที่รั่วไหลชุดที่สองซึ่งไม่มีใครสังเกต ความเสียหายรวมเมื่อถึงเวลาที่การตรวจสอบเสร็จสมบูรณ์: มากกว่า $80,000

**แนวคิด: การจัดการตัวตนและการเข้าถึง**

ทางเลือกอื่นคือระบบที่คุณไม่ได้ให้กุญแจดอกเดียวกันแก่ทุกคน

ลองนึกภาพอาคารสำนักงานที่ทุกชั้นมีพื้นที่ต่างกัน และพนักงานทุกคนมีบัตรกุญแจที่เปิดได้เฉพาะประตูที่พวกเขาต้องการสำหรับงานของตน บัตรกุญแจของนักศึกษาฝึกงานใช้ได้กับชั้นสาม บัตรกุญแจของนักบัญชีเปิดสำนักงานการเงินได้แต่ไม่ใช่ห้องเซิร์ฟเวอร์ ไม่มีใครเดินผ่านประตูที่ตัวเองไม่มีเหตุผลจะเดินผ่าน

นั่นคือโมเดลที่ AWS ใช้

AWS เรียกระบบนี้ว่า **IAM**: Identity and Access Management (การจัดการตัวตนและการเข้าถึง)

IAM คือระบบบัตรกุญแจสำหรับทั้งบัญชีคลาวด์ของคุณ คุณกำหนดว่าใครมีตัวตน (ตัวตน) สิ่งที่พวกเขาได้รับอนุญาตให้ทำ (สิทธิ์) และใช้สิทธิ์เหล่านั้นผ่าน policy อาคารมีหลายสิบชั้น IAM ทำให้แน่ใจว่าแต่ละคนเข้าถึงได้เฉพาะชั้นที่ตัวเองต้องการ

การเปรียบเทียบกับบัตรกุญแจขยายต่อไปได้อีก ในอาคารที่บริหารดี คุณรู้ได้ทุกขณะว่าใครมีสิทธิ์เข้าถึงอะไร คุณพิมพ์รายงานได้: นี่คือสิทธิ์เข้าถึงของบัตรกุญแจทุกใบ นี่คือคนที่อยู่ในห้องเซิร์ฟเวอร์ในช่วง 30 วันที่ผ่านมา นี่คือบัตรที่ไม่ได้ใช้ใน 90 วัน (ตัวบ่งชี้ที่เป็นไปได้ของบัตรของพนักงานที่ถูกเลิกจ้างซึ่งไม่ได้ถูกปิดใช้งาน)

IAM ให้ทัศนวิสัยแบบเดียวกัน ทุกการกระทำที่ทำผ่าน IAM — ทุกการเรียก API ทุกการล็อกอินคอนโซล ทุกการให้สิทธิ์ — ถูกบันทึกใน **AWS CloudTrail** ถ้าคุณต้องการรู้ว่าใครลบฐานข้อมูลตอนตีสองของวันอังคาร CloudTrail มีคำตอบ ถ้าคุณต้องการแสดงให้ผู้ตรวจสอบเห็นว่ามีเฉพาะผู้ใช้ที่ได้รับอนุญาตเท่านั้นที่เข้าถึงระบบ production ได้ CloudTrail ให้หลักฐาน

AWS CloudTrail เก็บประวัติเหตุการณ์การจัดการ 90 วันโดยอัตโนมัติ อ่านได้จากคอนโซล แต่ 90 วันมักจะไม่ค่อยพอเมื่อทีมความปลอดภัยของคุณต้องการตรวจสอบบางอย่างจากไตรมาสที่แล้ว สำหรับการบันทึกแบบถาวรระยะยาว — และสำหรับการแจ้งเตือน — คุณต้องสร้าง **Trail** ซึ่งเขียนเหตุการณ์ทั้งหมดไปยัง S3 bucket และสามารถสตรีมไปยัง CloudWatch Logs Trail ไม่ใช่อัตโนมัติ มันเป็นสิ่งที่คุณกำหนดค่าครั้งเดียวแล้วลืมมันไป จนกว่าคุณจะต้องการมัน

การรวมกันของการควบคุมการเข้าถึงของ IAM กับการบันทึกการตรวจสอบของ CloudTrail คือสิ่งที่ทำให้องค์กรขนาดใหญ่รันบัญชี AWS ในระดับขนาดใหญ่ได้อย่างมั่นใจ: การเข้าถึงถูกกำหนดและบังคับใช้โดย IAM ทุกการใช้สิทธิ์เข้าถึงนั้นถูกบันทึกโดย CloudTrail

**การเปรียบเทียบกับโรงพยาบาล**

นี่คือวิธีคิดที่สอง — วิธีที่ทำให้ลำดับชั้นการเข้าถึงเข้าใจง่ายขึ้น

ลองนึกภาพโรงพยาบาล ไม่ใช่แค่ตัวอาคาร แต่เป็นโครงสร้างองค์กรที่สมบูรณ์ของคน บทบาท และข้อมูล

**พนักงานต้อนรับ** เห็นตารางนัดหมายผู้ป่วยและข้อมูลประกันได้ พวกเขาเช็คอินและเช็คเอาต์ผู้ป่วยได้ พวกเขาเข้าถึงเวชระเบียนไม่ได้ แก้ไขใบสั่งยาไม่ได้ ดูประวัติการผ่าตัดไม่ได้

**พยาบาล** เข้าถึงเวชระเบียนสำหรับผู้ป่วยในหอผู้ป่วยของตนได้ พวกเขาให้ยาตามคำสั่งแพทย์ได้ พวกเขาสั่งยาเองไม่ได้ พวกเขาอนุมัติการผ่าตัดไม่ได้

**แพทย์** ดูและแก้ไขเวชระเบียน เขียนใบสั่งยา และสั่งตรวจได้ พวกเขาเข้าถึงระบบเงินเดือนไม่ได้ พวกเขาแก้ไขใบสั่งยาของแพทย์คนอื่นไม่ได้โดยไม่มีการ override เฉพาะ

**ศัลยแพทย์** เข้าถึงระบบห้องผ่าตัดได้ พวกเขามีสิทธิ์เฉพาะสำหรับบันทึกการผ่าตัดที่แพทย์ส่วนใหญ่ไม่ต้องการ

**พนักงานทำความสะอาด** เข้าถึงแผนผังพื้นและตารางห้องได้ พวกเขาเข้าถึงข้อมูลผู้ป่วยใด ๆ ไม่ได้

แต่ละคนในโรงพยาบาลมีสิทธิ์เข้าถึงที่ตัวเองต้องการสำหรับงานของตน — และเท่านั้น พนักงานต้อนรับไม่มีสิทธิ์เข้าถึงการผ่าตัด พนักงานทำความสะอาดไม่เห็นเวชระเบียน และที่สำคัญ: ถ้าบัตรกุญแจของพนักงานทำความสะอาดถูกขโมย ผู้โจมตีก็ได้ตารางทำความสะอาด พวกเขาไม่ได้เวชระเบียน รัศมีความเสียหายของการละเมิดถูกจำกัดอยู่ที่สิ่งที่บัตรกุญแจนั้นเข้าถึงได้

นี่คือวิธีที่ IAM ทำงาน แต่ละตัวตน — ผู้ใช้แต่ละคน แต่ละบริการ แต่ละกระบวนการอัตโนมัติ — ได้สิทธิ์ที่ตัวเองต้องการพอดี ไม่มากกว่านั้น

**องค์ประกอบพื้นฐานของ IAM**

IAM มีสี่แนวคิดหลัก พวกมันต่อยอดกัน

**Users** คือตัวตนส่วนบุคคล Maya มี IAM user Tom มี IAM user แต่ละ user มีข้อมูลประจำตัวของตัวเอง — และควรมีเฉพาะสิทธิ์ที่พวกเขาต้องการโดยเฉพาะ

IAM user มีข้อมูลประจำตัวสองประเภท: **รหัสผ่าน** สำหรับการเข้าถึงคอนโซล (ล็อกอินเข้าเว็บอินเทอร์เฟซของ AWS) และ **access key** (key ID และ secret key) สำหรับการเข้าถึงแบบโปรแกรมผ่าน CLI หรือ SDK คุณไม่จำเป็นต้องมีทั้งสองอย่างเสมอ นักพัฒนาที่ใช้เฉพาะ CLI ไม่ต้องการรหัสผ่านคอนโซล ผู้ใช้ที่ไม่ใช่สายเทคนิคที่ต้องการเฉพาะคอนโซลไม่ต้องการ access key ให้เฉพาะสิ่งที่จำเป็น

**Groups** คือกลุ่มของ user แทนที่จะตั้งค่าสิทธิ์สำหรับ Maya, Tom, Priya และ Leo แยกกัน คุณสร้างกลุ่ม "Developers" ที่มีสิทธิ์นักพัฒนาและเพิ่มพวกเขาเข้าไป เมื่อคนที่ห้าเข้าร่วม คุณเพิ่มพวกเขาในกลุ่มและพวกเขาก็สืบทอดสิทธิ์ที่ถูกต้องทันที

ประโยชน์เชิงปฏิบัติของกลุ่มคือความง่ายในการบำรุงรักษา ถ้ากลุ่ม "Developers" ต้องการสิทธิ์ใหม่ — สมมติว่าการเข้าถึง S3 bucket ใหม่ — คุณเพิ่มมันลงในกลุ่มครั้งเดียวและนักพัฒนาทุกคนก็มีมันทันที หากไม่มีกลุ่ม คุณจะต้องอัปเดต user แต่ละคนทีละคน ซึ่งสร้างโอกาสให้เกิดความไม่สอดคล้องและพลาดบางคน

**Roles** คือตัวตนชั่วคราวที่บางสิ่งสามารถ *รับเอา* ได้ — คน บริการ หรือบัญชี AWS อื่น เราจะเจาะลึก role ในบทที่ 14 ตอนนี้: ถ้า User เป็นพนักงานถาวร Role คือบัตรผ่านสำหรับผู้เยี่ยมชม มันให้สิทธิ์เข้าถึงเฉพาะสำหรับเวลาหรือวัตถุประสงค์เฉพาะ

การใช้ Role ที่สำคัญที่สุดสำหรับบทนี้: IAM Role สำหรับ EC2 instance เมื่อคุณแนบ Role เข้ากับ EC2 instance แอปพลิเคชันที่รันบน instance นั้นสามารถเรียก AWS API โดยใช้สิทธิ์ของ Role — โดยไม่มีข้อมูลประจำตัวแบบสแตติกเก็บไว้ที่ใดเลย ข้อมูลประจำตัวเป็นแบบชั่วคราว หมุนเวียนโดยอัตโนมัติโดย AWS และจำกัดอยู่ที่ policy ของ Role สิ่งนี้ขจัดปัญหา "ข้อมูลประจำตัวในไฟล์ config" ออกไปอย่างสิ้นเชิง

**Policies** คือกฎสิทธิ์จริง ๆ Policy คือเอกสาร (เขียนใน JSON ภายใน แต่คุณไม่จำเป็นต้องจำรูปแบบ) ที่ระบุว่า: "ผู้ถือ policy นี้ได้รับอนุญาตให้ดำเนินการ X บนทรัพยากร Y" หรือ "ถูกปฏิเสธการดำเนินการ Z"

AWS มี **managed policy** หลายร้อยรายการ — policy ที่เขียนไว้ล่วงหน้าสำหรับกรณีการใช้งานทั่วไป `AmazonS3ReadOnlyAccess` ให้สิทธิ์อ่านไปยัง S3 bucket ทั้งหมด `AmazonEC2FullAccess` ให้การควบคุม EC2 เต็มรูปแบบ สำหรับการใช้งานใน production คุณมักต้องการ **customer-managed policy** — policy ที่คุณเขียนเอง จำกัดขอบเขตอย่างแม่นยำให้ตรงกับทรัพยากรและการกระทำที่แอปพลิเคชันของคุณต้องการจริง

โมเดลการประเมิน IAM คือ: โดยค่าเริ่มต้น ทุกอย่างถูกปฏิเสธ ต้องให้สิทธิ์อย่างชัดเจน ถ้า policy ไม่ระบุว่าคุณทำอะไรได้ คุณก็ทำไม่ได้

**หลักการสิทธิ์ขั้นต่ำ**

ให้คนและระบบมีเฉพาะสิทธิ์เข้าถึงที่พวกเขาต้องการเพื่อทำงานของตน ไม่มากกว่านั้น

Priya เรียกสิ่งนี้ว่า "หลักการสิทธิ์ขั้นต่ำ (principle of least privilege)" มันฟังดูชัดเจน ในทางปฏิบัติ ทีมส่วนใหญ่ละเมิดมันอยู่ตลอดเวลา — ไม่ใช่ด้วยเจตนาร้าย แต่ด้วยความสะดวก

"เราจะให้สิทธิ์ admin แก่ Leo เพื่อให้เขา deploy ได้เร็วขึ้นได้ไหม?"

ไม่

"เราจะใช้บัญชี root สำหรับทุกอย่างได้ไหม?"

ไม่ได้เด็ดขาด

บัญชี root คือกุญแจหลักสู่บัญชี AWS ทั้งหมดของคุณ มันทำอะไรก็ได้ รวมถึงปิดบัญชีเอง คุณควรสร้างมันครั้งเดียว ตั้งค่าการยืนยันตัวตนแบบหลายปัจจัย แล้วไม่ใช้มันอีกสำหรับงานประจำวัน

มีงานเพียงไม่กี่อย่างเท่านั้นที่ต้องการบัญชี root: การเปลี่ยนที่อยู่อีเมลของบัญชี การดูข้อมูลการเรียกเก็บเงินที่ไม่ได้มอบหมายไว้เป็นอย่างอื่น การปิดบัญชี และการดำเนินการด้านการจัดการอีกไม่กี่อย่างที่ AWS จำกัดไว้สำหรับ root โดยชัดเจน สำหรับทุกอย่างอื่น — การสร้างผู้ใช้ การ deploy โครงสร้างพื้นฐาน การเข้าถึงฐานข้อมูล — คุณใช้ IAM user และ role บัญชี root มีไว้สำหรับผู้จัดการอาคาร ทุกคนอื่นมีบัตรกุญแจที่เหมาะสม

Priya สร้าง IAM user แยกต่างหากสำหรับทุกคนในบ่ายวันนั้น เธอให้สิทธิ์ Leo ในการ deploy ไปยังสภาพแวดล้อม development ไม่ใช่ production ไม่ใช่การเรียกเก็บเงิน ไม่ใช่เครือข่าย แค่การ deploy

"รู้สึกจำกัดจัง" Leo พูด

"นั่นแหละที่บอกว่ามันถูกต้อง" Priya ตอบ

เส้นแบ่งระหว่าง development กับ production เป็นเส้นสิทธิ์ขั้นต่ำเส้นแรกและสำคัญที่สุดที่ Priya ขีดไว้ นักพัฒนาต้องเคลื่อนที่เร็วใน development: สร้างทรัพยากร ทดสอบการกำหนดค่า ทำผิดพลาด แต่ production ต่างออกไป การเปลี่ยนแปลง production ต้องตั้งใจ ตรวจทาน และดำเนินการผ่านกระบวนการที่ควบคุมได้ การให้นักพัฒนาเข้าถึง production โดยตรงคือการให้พวกเขามีความสามารถในการทำผิดพลาดใน production ด้วยความเร็วของ development

เมื่อเวลาผ่านไป Priya สร้างระบบที่การเข้าถึง production ถูกให้ชั่วคราวผ่านกระบวนการรับ role: นักพัฒนาที่ต้องการเปลี่ยนแปลง production จะร้องขอการเข้าถึง ได้มันเป็นเวลา 4 ชั่วโมง ทำการเปลี่ยนแปลง และการเข้าถึงก็หมดอายุโดยอัตโนมัติ ช่วงเวลานั้นถูกบันทึกใน CloudTrail การเข้าถึงใช้ไม่ได้หลังจากมันหมดอายุ Production ถูกปกป้องไม่ใช่ด้วยการปฏิเสธการเข้าถึงถาวร แต่ด้วยการทำให้การเข้าถึงมีกรอบเวลาและตรวจสอบได้

คุณอาจสงสัย: ถ้าทุกอย่างถูกปฏิเสธโดยค่าเริ่มต้น ทำไมบัญชี root ถึงมีสิทธิ์เข้าถึงเต็มรูปแบบ? บัญชี root พิเศษ — มันข้าม IAM ทั้งหมด นั่นคือเหตุผลที่คุณล็อกมันเก็บไว้พอดี ทุกการกระทำอื่นใน AWS ผ่านห่วงโซ่การประเมินของ IAM ที่การไม่มี Allow ก็เหมือนกับ Deny

**รัศมีความเสียหาย: ทำไมสิทธิ์ขั้นต่ำจึงช่วยบริษัทไว้**

มีแนวคิดหนึ่งที่วิศวกรความปลอดภัยใช้คิดเกี่ยวกับการบุกรุกข้อมูลประจำตัว: **รัศมีความเสียหาย (blast radius)**

รัศมีความเสียหายคือความเสียหายสูงสุดที่ผู้โจมตีทำได้ถ้าพวกเขาได้ข้อมูลประจำตัวหนึ่ง ๆ มา

ผู้โจมตีที่มีข้อมูลประจำตัว root ของบัญชี AWS มีรัศมีความเสียหายไม่จำกัด พวกเขาลบทรัพยากรทุกอย่างได้ ดูดข้อมูลทุกไบต์ออกไปได้ เปิด GPU instance ในทุก Region และปิดบัญชีได้ ข้อมูลประจำตัวตัวมันเองไม่มีขีดจำกัด

ผู้โจมตีที่มีข้อมูลประจำตัว IAM ของ Leo — จำกัดอยู่ที่การ deploy ไปยังสภาพแวดล้อม development และอ่านจาก S3 bucket หนึ่ง — มีรัศมีความเสียหายเล็กจิ๋ว พวกเขา deploy ไป dev ได้ พวกเขาอ่านบางไฟล์ได้ พวกเขาแตะ production ไม่ได้ พวกเขาเข้าถึงฐานข้อมูลไม่ได้ พวกเขาเห็นการเรียกเก็บเงินไม่ได้ พวกเขาเปิด GPU instance ไม่ได้

เรื่องราวการละเมิดจากก่อนหน้านี้มีรัศมีความเสียหายขนาดใหญ่เพราะข้อมูลประจำตัวของนักพัฒนาเป็นแบบ admin ถ้าข้อมูลประจำตัวเดียวกันนั้นถูกจำกัดให้ตรงกับงานจริงของพวกเขา — การ deploy ไปยังสภาพแวดล้อมหนึ่งโดยเฉพาะ — ความเสียหายก็จะเล็กกว่ามาก การโจมตีอาจยังเกิดขึ้นได้ แต่ผลลัพธ์ก็จะต่างออกไป

นี่คือเหตุผลที่สิทธิ์ขั้นต่ำไม่ใช่แค่นโยบาย มันคือสถาปัตยกรรม ทุกสิทธิ์ที่คุณไม่ให้คือรัศมีความเสียหายที่คุณไม่มี

**เกิดอะไรขึ้นเมื่อคุณทำสิ่งนี้ผิด**

สามสถานการณ์ เรียงตามความรุนแรงที่เพิ่มขึ้น:

**สถานการณ์ที่ 1**: พนักงานที่มีสิทธิ์ admin ลาออกจากบริษัท ไม่มีใครปิดใช้งานบัญชีของพวกเขา สามเดือนต่อมา พวกเขายังมีสิทธิ์เข้าถึง สิ่งนี้เกิดขึ้นตลอดเวลา IAM แก้มันได้: คุณปิดใช้งาน user ทันที ทุกที่

นี่คือโหมดความล้มเหลวของ IAM ที่พบบ่อยที่สุด และมันป้องกันได้ทั้งหมด องค์กรส่วนใหญ่มีกระบวนการสำหรับการเพิกถอนการเข้าถึงทางกายภาพ (คืนบัตร คืนแล็ปท็อป) แต่มองข้าม IAM รายการตรวจสอบการออกจากงานที่รวม "ปิดใช้งาน IAM user" และ "ลบออกจากทุก IAM group" ไม่ใช่ความท้าทายทางวิศวกรรมที่ซับซ้อน — มันเป็นวินัยในกระบวนการ ทีมที่ทำมันอย่างสม่ำเสมอคือทีมที่ไม่เคยต้องรู้ว่าเกิดอะไรขึ้นเมื่ออดีตพนักงานยังเข้าถึงฐานข้อมูล production ได้

**สถานการณ์ที่ 2**: แล็ปท็อปของนักพัฒนาถูกบุกรุก ผู้โจมตีพบข้อมูลประจำตัว AWS ที่เก็บไว้ในไฟล์ config พร้อมสิทธิ์ admin เต็มรูปแบบ เพราะข้อมูลประจำตัวมีสิทธิ์เข้าถึงกว้าง ผู้โจมตีทำอะไรก็ได้: ขุด cryptocurrency ขโมยข้อมูล ลบข้อมูลสำรอง ด้วยสิทธิ์ขั้นต่ำ: ข้อมูลประจำตัวทำงานได้เฉพาะสำหรับขอบเขตจำกัดของมัน รัศมีความเสียหายถูกควบคุม

รูปแบบข้อมูลประจำตัวในไฟล์ config พบบ่อยกว่าที่ควรจะเป็น นักพัฒนามักเก็บข้อมูลประจำตัว AWS ใน `~/.aws/credentials` สำหรับการพัฒนาในเครื่อง — ซึ่งโอเค ปัญหาคือเมื่อข้อมูลประจำตัวเหล่านั้นมีสิทธิ์เข้าถึงระดับ production แทนที่จะถูกจำกัดอยู่ที่สภาพแวดล้อม sandbox ข้อมูลประจำตัวสำหรับการพัฒนาควรถูกจำกัดอยู่ที่สภาพแวดล้อม development การเข้าถึง production ควรต้องมีขั้นตอนที่ชัดเจนในการรับ ไม่ใช่อยู่บนทุกแล็ปท็อปตลอดเวลา

**สถานการณ์ที่ 3**: แอปพลิเคชันที่เขียนไม่ดีเปิดเผยข้อมูลประจำตัว AWS ในบันทึกของมันโดยไม่ตั้งใจ ถ้าข้อมูลประจำตัวเหล่านั้นมีสิทธิ์เข้าถึงกว้าง คุณมีการละเมิดที่เป็นหายนะ ถ้าพวกมันมีสิทธิ์เข้าถึงแคบ — เฉพาะ S3 bucket ที่แอปพลิเคชันต้องการ — การเปิดเผยถูกจำกัดและควบคุม

สถานการณ์ข้อมูลประจำตัวแอปพลิเคชันในบันทึกนั้นแยบยล มันมักเกิดขึ้นเมื่อโค้ดดีบักบันทึกบริบทคำขอเต็มรูปแบบ — รวมถึง authorization header — หรือเมื่อตัวจัดการข้อผิดพลาดทำให้ตัวแปรสภาพแวดล้อมทั้งหมด (รวมถึง `AWS_ACCESS_KEY_ID`) เป็นอนุกรมลงในไฟล์บันทึก การป้องกันในที่นี้คือ IAM Role สำหรับ EC2 ซึ่งขจัดข้อมูลประจำตัวแบบสแตติกออกจากสภาพแวดล้อมแอปพลิเคชันอย่างสิ้นเชิง ถ้าไม่มีข้อมูลประจำตัวแบบสแตติก พวกมันก็ปรากฏในบันทึกไม่ได้

รูปแบบ: การเข้าถึงควรถูกจำกัดให้น้อยที่สุด เสมอ ไม่ใช่เพราะคุณไม่ไว้ใจคนของคุณ แต่เพราะคุณควบคุมสิ่งที่เกิดขึ้นกับข้อมูลประจำตัวที่ถูกบุกรุกไม่ได้

**ถ้าการเข้าถึงกว้าง ก็ได้ความสะดวกแต่ก็เสี่ยงเปิดเผย**

มีสิ่งล่อใจเสมอที่จะให้ทีมเข้าถึงกว้างกว่าที่พวกเขาต้องการ — มันทำให้การ deploy เร็วขึ้น ลดความเสียดทาน หลีกเลี่ยงช่วงเวลา "Access Denied" ที่ขัดจังหวะการทำงาน ถ้าคุณให้ทุกคนเข้าถึงระดับ admin การ deploy ก็ราบรื่นและไม่มีใครถูกบล็อก — แต่เมื่อข้อมูลประจำตัวรั่ว (และมันรั่วจริง) ผู้โจมตีก็สืบทอดสิทธิ์ admin เต็มรูปแบบ แล็ปท็อปที่ถูกบุกรุกเครื่องเดียวกลายเป็นการละเมิดบัญชีทั้งหมด เขียนสิทธิ์ขั้นต่ำก่อน ขยายเฉพาะเมื่อบางอย่างล้มเหลว กฎนั้นช่วยบริษัทไว้

**การยืนยันตัวตนแบบหลายปัจจัย: การล็อกที่สอง**

แม้จะมีสิทธิ์ขั้นต่ำ ข้อมูลประจำตัวก็ยังถูกขโมยได้ รหัสผ่านถูกเดา ถูก phish หรือรั่วได้ IAM จัดการเรื่องนี้ด้วย **การยืนยันตัวตนแบบหลายปัจจัย (Multi-Factor Authentication, MFA)**

MFA ต้องการสิ่งที่คุณ *รู้* (รหัสผ่าน) บวกกับสิ่งที่คุณ *มี* (โทรศัพท์ กุญแจฮาร์ดแวร์) แม้ผู้โจมตีขโมยรหัสผ่านของคุณ พวกเขาก็ล็อกอินไม่ได้หากไม่มีโทรศัพท์ของคุณด้วย

ควรเปิดใช้งาน MFA สำหรับ IAM user ทุกคน มันต่อรองไม่ได้สำหรับบัญชี root

## จุดแข็งและข้อจำกัด

**IAM เป็นเครื่องมือที่เหมาะสำหรับ**:

- การควบคุมว่าใครและอะไรเข้าถึงทรัพยากร AWS ทุกอย่างได้
- การนำสิทธิ์ขั้นต่ำมาใช้ข้าม user, service และขอบเขตข้ามบัญชี
- การขจัดความจำเป็นในการแชร์ข้อมูลประจำตัวที่มีอายุยาวระหว่างระบบ
- ทุกการกระทำของ IAM ถูกบันทึกโดยอัตโนมัติ ให้เส้นทางการตรวจสอบว่าใครทำอะไรเมื่อไหร่ (ครอบคลุมในบทที่ 14)
- การเข้าถึงข้ามบัญชี: IAM Role ในบัญชี A สามารถถูกรับเอาโดย principal ในบัญชี B อนุญาตให้แชร์ทรัพยากรระหว่างบัญชี AWS ได้แบบควบคุมโดยไม่ต้องแชร์ข้อมูลประจำตัว

**ที่ซึ่ง IAM เริ่มยาก**: policy IAM สามารถเติบโตเป็น statement หลายร้อยรายการข้าม role หลายสิบอัน และการดีบักข้อผิดพลาด "Access Denied" ต้องอาศัยการเข้าใจว่า policy ใดในนั้นเป็นอันที่มีผล — งานที่ยากกว่าที่ฟังดู ความผิดพลาด IAM ที่พบบ่อยที่สุดไม่ใช่การเข้าถึงน้อยเกินไป — มันคือมากเกินไป policy ที่ให้สิทธิ์เกินที่สร้างขึ้นเพื่อ "ให้มันทำงานได้ก่อน" กลายเป็นภาระด้านความปลอดภัยที่ย้อนกลับได้ยากในภายหลัง เขียนสิทธิ์ขั้นต่ำก่อน ขยายเฉพาะเมื่อบางอย่างล้มเหลว

มีความท้าทายเชิงปฏิบัติกับ IAM ในระดับขนาดใหญ่: **policy sprawl (การกระจัดกระจายของ policy)** องค์กรที่รัน AWS มาหลายปีมักมี policy ที่กำหนดเองหลายสิบหรือหลายร้อยรายการ หลายอันทับซ้อนกัน บางอันไม่เคยถูกใช้ และบางอันขัดแย้งกันในแบบที่ไม่มีใครสังเกตเพราะความขัดแย้งสำคัญเฉพาะกับกรณีขอบ AWS มี **IAM Access Analyzer** (ที่เราแนะนำในบทนี้) และเครื่องมือ **IAM policy simulation** เพื่อช่วยตรวจสอบและจัดระเบียบ policy แต่กลยุทธ์ที่มีประสิทธิภาพที่สุดคือการสร้าง policy ที่สะอาดตั้งแต่ต้นและตรวจสอบเป็นประจำ — แทนที่จะปล่อยให้ policy สะสมแล้วพยายามแกะมันออกในภายหลัง

Priya ตั้งค่าการตรวจทาน IAM รายไตรมาส: รายการ role และ policy ทั้งหมด ตรวจสอบว่าอันไหนถูกใช้งานจริงผ่านบันทึก CloudTrail ทำเครื่องหมายข้อมูลประจำตัวที่ไม่ได้ใช้หรือ policy ที่กว้างเกินไปเพื่อลบหรือจำกัด การตรวจทานใช้เวลาสองชั่วโมงต่อไตรมาสและพบปัญหา policy สามอย่างในปีแรก

"มันไม่ใช่งานที่น่าตื่นเต้น" เธอพูด "แต่การตรวจทานการเข้าถึงคือวิธีที่คุณพบสิ่งที่จะกลายเป็นหายนะถ้ามีคนอื่นสังเกตเห็นมันก่อน"

## สรุป

รหัสผ่าน Admin123 เป็นอาการ โรคคือ Nimbus ไม่มีกลยุทธ์การควบคุมการเข้าถึงเลย — ข้อมูลประจำตัว root ที่แชร์กัน ไม่มี role ไม่มี policy ไม่มีเส้นทางการตรวจสอบ IAM ไม่ได้แค่แก้อาการ มันบังคับให้ทีมตอบคำถามที่พวกเขาหลีกเลี่ยงมา: ใครกันแน่ที่ได้รับอนุญาตให้ทำอะไร? คำตอบของคำถามนั้นคือรากฐานของทุกสถาปัตยกรรม AWS ที่ปลอดภัย

- **IAM** (Identity and Access Management) คือวิธีที่คุณควบคุมว่าใครทำอะไรได้ใน AWS องค์ประกอบพื้นฐานหลักคือ: **Users**, **Groups**, **Roles** และ **Policies**
- โดยค่าเริ่มต้น ทุกอย่างใน AWS ถูก **ปฏิเสธ** ต้องให้สิทธิ์อย่างชัดเจน
- **หลักการสิทธิ์ขั้นต่ำ** หมายถึงการให้แต่ละตัวตนมีเฉพาะสิทธิ์เข้าถึงที่ต้องการ — ลด **รัศมีความเสียหาย** หากข้อมูลประจำตัวถูกบุกรุก
- **บัญชี root** ทำอะไรก็ได้ รวมถึงสิ่งที่เป็นหายนะ ล็อกมันไว้หลัง MFA และใช้มันให้น้อยที่สุด
- เปิดใช้งาน **MFA** สำหรับทุก IAM user ต่อรองไม่ได้ — ทั้งในการสอบและใน production

## เคล็ดลับการสอบ

*SAA-C03 Domain 1 — Task 1.1 (การเข้าถึงทรัพยากร AWS อย่างปลอดภัย)*

- **ทุกอย่างถูกปฏิเสธโดยค่าเริ่มต้น** ต้องมี "Allow" อย่างชัดเจน ถ้า policy ไม่กล่าวถึง
  การกระทำ การกระทำนั้นถูกปฏิเสธ
- **Explicit Deny ชนะเสมอ** ถ้า policy ใด ๆ ในห่วงโซ่ปฏิเสธการกระทำ การปฏิเสธนั้น
  ไม่สามารถถูกแทนที่ด้วย Allow ที่อื่นใดในห่วงโซ่ สิ่งนี้ทำให้ผู้เข้าสอบหลายคนพลาด
- **บัญชี root ≠ admin IAM** บัญชี root เป็นข้อมูลประจำตัวแยกต่างหากจาก IAM
  คุณลบบัญชี root ไม่ได้ คุณ *สามารถ* (และควร) จำกัดเมื่อไหร่ที่ใช้มัน
- **IAM เป็น global** ไม่ใช่ Regional IAM user, group, role และ policy มีอยู่
  ทั่วทั้งบัญชี AWS ไม่ใช่ต่อ Region
- **Role เป็นวิธีที่ต้องการในการให้สิทธิ์เข้าถึง AWS service** ถ้า EC2 instance
  ต้องการเข้าถึง S3 คุณแนบ IAM Role เข้ากับ instance — คุณไม่เก็บข้อมูลประจำตัว
  บนเครื่อง รูปแบบนี้ปรากฏในการสอบอยู่ตลอด
- **IAM Access Analyzer** สร้างผลการตรวจพบเมื่อทรัพยากรเข้าถึงได้จากนอกบัญชีหรือจากนอกองค์กร เมื่อสถานการณ์การสอบกล่าวถึงการตรวจจับการเข้าถึงภายนอกที่ไม่ตั้งใจไปยัง S3 หรือ KMS คำตอบคือ Access Analyzer
- **MFA สำหรับบัญชี root เป็นข้อบังคับ** ไม่ใช่ทางเลือก ในบริบทของแนวทางปฏิบัติที่ดีที่สุดด้านความปลอดภัยของ AWS คำถามสอบเกี่ยวกับการรักษาความปลอดภัยบัญชี root มักรวม MFA เป็นส่วนหนึ่งของคำตอบที่ถูกต้อง
- **Permission boundaries** เป็นฟีเจอร์ IAM ขั้นสูง (ครอบคลุมในบทที่ 14) ที่จำกัดสิทธิ์สูงสุดที่ IAM user หรือ role มีได้ แม้ว่า policy ของพวกเขาจะให้มากกว่า คำถามสอบเกี่ยวกับ "การป้องกันการยกระดับสิทธิ์" หรือ "การตั้งเพดานสิทธิ์สูงสุด" ชี้ไปที่ permission boundaries
- **Service Control Policies (SCPs)** เป็น policy ระดับองค์กรที่จำกัดสิ่งที่ทำได้ในบัญชีสมาชิกของ AWS Organization พวกมันทำงานเหนือระดับ IAM — แม้แต่ผู้ดูแลบัญชีก็เกินขีดจำกัดที่ SCP ตั้งไว้ไม่ได้ เมื่อสถานการณ์การสอบเกี่ยวข้องกับการกำกับดูแลความปลอดภัยแบบหลายบัญชี ให้คิดถึง SCP
- **CloudTrail** บันทึกการเรียก API ของ IAM ทั้งหมด เมื่อสถานการณ์การสอบถามว่า "คุณจะตรวจสอบว่าผู้ใช้คนใดเปลี่ยน policy ของ IAM อย่างไร" คำตอบคือ CloudTrail ทุกการกระทำของ IAM — การสร้างผู้ใช้ การแก้ไข policy การรับ role — ถูกบันทึก ประวัติเหตุการณ์ 90 วันเป็นอัตโนมัติและฟรี สำหรับการเก็บรักษาระยะยาวและการแจ้งเตือน คุณต้องสร้าง Trail ที่ส่งบันทึกไปยัง S3 bucket

## แบบฝึกหัด

**แบบฝึกหัด 1 — การจำ**

ด้วยคำพูดของคุณเอง: ความแตกต่างระหว่าง IAM User, Group และ Role คืออะไร? คุณจะใช้แต่ละอันเมื่อไหร่?

*(คำใบ้: คิดถึงการเปรียบเทียบกับอาคารบัตรกุญแจ — อันไหนเป็นบัตรถาวร อันไหนเป็นการจัดกลุ่มแผนก และอันไหนเป็นบัตรผู้เยี่ยมชม?)*

**แบบฝึกหัด 2 — สถานการณ์ SAA-C03**

*สถานการณ์*: บริษัทรันเว็บแอปพลิเคชันบน EC2 instance ที่ต้องอ่านไฟล์จาก S3 bucket นักพัฒนาระดับจูเนียร์เสนอให้เก็บ AWS access key ไว้ในโค้ดแอปพลิเคชันบน EC2 instance โดยตรง ทีมความปลอดภัยคัดค้าน

วิธีแก้ปัญหาใดที่ปลอดภัยที่สุดและเหมาะสมในการดำเนินงานมากที่สุด?

A) เก็บ access key ในตัวแปรสภาพแวดล้อมบน EC2 instance แทนที่จะเป็นในโค้ด  
B) สร้าง IAM user เฉพาะที่มีสิทธิ์อ่าน S3 และแชร์ข้อมูลประจำตัวกับทีมพัฒนา  
C) แนบ IAM Role ที่มีสิทธิ์อ่าน S3 ที่เหมาะสมเข้ากับ EC2 instance โดยตรง  
D) ใช้ข้อมูลประจำตัวบัญชี root เพื่อให้แอปพลิเคชันเข้าถึงทรัพยากร AWS ทั้งหมดได้อย่างสมบูรณ์

**คำใบ้ 1**: ปัญหาของการเก็บข้อมูลประจำตัวที่ใดก็ตามบน instance คือข้อมูลประจำตัวรั่วได้ มีวิธีให้ EC2 instance เข้าถึงได้โดยไม่ต้องใช้ข้อมูลประจำตัวเลยไหม?

**คำใบ้ 2**: AWS มีกลไกที่บริการสามารถได้รับสิทธิ์โดยไม่ต้องมีข้อมูลประจำตัวแบบสแตติก กลไกนั้นเรียกว่าอะไร?

**คำใบ้ 3**: IAM Role สามารถแนบเข้ากับ EC2 instance ได้ เมื่อแนบแล้ว instance จะได้รับข้อมูลประจำตัวชั่วคราวที่หมุนเวียนโดย AWS โดยอัตโนมัติ ไม่ต้องมีข้อมูลประจำตัวแบบสแตติก

**คำตอบ**: C

**คำอธิบาย**: การแนบ IAM Role เข้ากับ EC2 instance คือรูปแบบที่ถูกต้อง instance จะได้รับข้อมูลประจำตัวชั่วคราวที่หมุนเวียนโดยอัตโนมัติผ่านบริการ metadata ของ EC2 ไม่มีข้อมูลประจำตัวที่มีอายุยาวที่จะรั่วไหล หมุนเวียน หรือ commit โดยไม่ตั้งใจไปยัง repository

**ทำไมไม่ใช่ A?** ตัวแปรสภาพแวดล้อมบน EC2 instance ก็ยังรั่วได้ — ผ่านบันทึกแอปพลิเคชัน endpoint การดีบัก หรือถ้า instance ถูกบุกรุก ข้อมูลประจำตัวแบบสแตติกคือปัญหา ไม่ใช่ตำแหน่งของมัน

**ทำไมไม่ใช่ B?** การสร้าง IAM user ที่แชร์กันและแจกจ่ายข้อมูลประจำตัวให้ทีมละเมิดสิทธิ์ขั้นต่ำและทำให้การหมุนเวียนข้อมูลประจำตัวเป็นฝันร้าย ถ้าคนหนึ่งลาออก คุณก็เพิกถอนเฉพาะการเข้าถึงของพวกเขาได้ยากโดยไม่เปลี่ยนข้อมูลประจำตัวที่แชร์กัน

**ทำไมไม่ใช่ D?** การใช้ข้อมูลประจำตัวบัญชี root สำหรับแอปพลิเคชันใด ๆ เป็นการละเมิดความปลอดภัยร้ายแรง บัญชี root มีสิทธิ์เข้าถึงไม่จำกัดและข้อมูลประจำตัวของมันไม่ควรออกจากการควบคุมของเจ้าของบัญชี

Nimbus กำลังรับนักพัฒนาใหม่สามคนในเดือนหน้า แต่ละคนจะต้องการระดับการเข้าถึงที่ต่างกัน: คนหนึ่งทำงานที่ชั้นฐานข้อมูล คนหนึ่งที่เซิร์ฟเวอร์แอปพลิเคชัน คนหนึ่งที่ไฟล์สแตติกฝั่ง front-end ยังมี CI/CD pipeline ที่ต้อง deploy โค้ด
