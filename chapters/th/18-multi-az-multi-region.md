**การเปรียบเปรยกับกริดไฟฟ้า**

ลองนึกถึงวิธีที่บ้านของคุณได้รับไฟฟ้า ไฟฟ้าไม่ได้มาจากสายไฟเส้นเดียวจากเครื่องกำเนิดไฟเดียว มันมาจาก grid — เครือข่ายเครื่องกำเนิดไฟ สถานีย่อย และสายส่งที่สำรองซึ่งกันและกัน

Availability Zones ของ AWS ทำงานในแบบเดียวกัน

**คำศัพท์เกี่ยวกับความล้มเหลว**

**Availability**: เปอร์เซ็นต์ของเวลาที่ระบบทำงาน "สี่เก้า" (99.99%) หมายถึงน้อยกว่า 52 นาทีหยุดทำงานต่อปี

**RTO (Recovery Time Objective)**: ระบบจะหยุดทำงานได้นานแค่ไหน?

**RPO (Recovery Point Objective)**: คุณสามารถสูญเสียข้อมูลได้แค่ไหน?

**การ deploy แบบ Multi-AZ**

การ deploy แบบ Multi-AZ กระจาย resources ของคุณข้ามสอง AZs หรือมากกว่าภายใน Region ถ้า AZ หนึ่งล้มเหลว load balancer หยุด routing ไปยัง instances ที่ไม่แข็งแรงใน AZ ที่ล้มเหลว Auto Scaling Group แทนที่ instances — แต่ใน AZ ที่ *แข็งแรง* RDS failover ไปยัง standby ใน AZ ที่แข็งแรง

**กลยุทธ์ Disaster Recovery: สเปกตรัม**

**Backup and Restore** (ชั่วโมง RPO/RTO):

- สำรองทุกอย่างไปยัง S3 ใน Region อื่น
- ค่าใช้จ่าย: ต่ำมาก

**Pilot Light** (นาทีถึง 1 ชั่วโมง RPO/RTO):

- เก็บเวอร์ชันขั้นต่ำของแอปพลิเคชันทำงานใน DR region

**Warm Standby** (วินาทีถึงนาที RPO/RTO):

- รันเวอร์ชันย่อของแอปพลิเคชันเต็มรูปแบบใน DR region

**Active-Active / Multi-Site** (RPO/RTO ใกล้ศูนย์):

- กำลังการผลิตเต็มรูปแบบในสองหรือมาก Regions ให้บริการ traffic พร้อมกัน

## สรุป

- **RTO**: ระบบจะหยุดทำงานได้นานแค่ไหน **RPO**: สูญเสียข้อมูลได้แค่ไหน
- **Multi-AZ** กระจาย resources ข้าม Availability Zones ภายใน Region ป้องกันความล้มเหลวของ AZ
- **Multi-Region** deploy ใน AWS Regions หลายอัน ป้องกันความล้มเหลวของ Region
- กลยุทธ์ DR (ถูกที่สุดถึงแพงที่สุด): Backup & Restore → Pilot Light → Warm Standby → Active-Active
- RDS Multi-AZ standby: synchronous, automatic failover, RPO = 0 Read replicas: asynchronous, manual promotion, RPO > 0
