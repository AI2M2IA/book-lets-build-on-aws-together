**การเปรียบเปรยกับคลังสินค้าที่เตรียมไว้ล่วงหน้า**

ลองนึกภาพ Amazon ผู้ค้าปลีก ไม่ใช่บริษัทคลาวด์ พวกเขามีคลังสินค้าขนาดใหญ่ในที่เดียวที่มีทุกผลิตภัณฑ์ ถ้าพวกเขาส่งทุกออเดอร์จากคลังเดียวนั้น ลูกค้าในเมืองที่ห่างไกลจะรอเป็นวัน ๆ

แทนที่ Amazon มีศูนย์ปฏิบัติงานใกล้ศูนย์กลางประชากรหลัก เมื่อผลิตภัณฑ์เป็นที่นิยม พวกเขาเตรียมสต็อกคลังท้องถิ่นเหล่านั้นล่วงหน้า เมื่อลูกค้าในซีแอตเทิลสั่งหนังสือ มันถูกส่งจากศูนย์ปฏิบัติงานท้องถิ่น — ไม่ใช่จากอีกฟากของประเทศ

นี่คือ **Content Delivery Network (CDN)**: เครือข่ายของเซิร์ฟเวอร์ที่กระจายทางภูมิศาสตร์ที่ cache สำเนาของเนื้อหาของคุณไว้ใกล้ผู้ใช้

เมื่อผู้ใช้ในบอสตันขอหน้าแรกของคุณ CDN ให้บริการมันจากเซิร์ฟเวอร์ในบอสตัน ไม่ใช่ออริกอน คำขอไม่เคยข้ามประเทศ

**พบกับ CloudFront**

Amazon CloudFront คือ CDN ของ AWS มันทำงานผ่านเครือข่ายทั่วโลกของ **edge location** — เซิร์ฟเวอร์ caching ที่วางอยู่ในเมืองต่าง ๆ ทั่วโลก ในขณะที่เขียนนี้ มี point of presence มากกว่า 750 อันใน 100+ เมือง

เมื่อคุณกำหนดค่า CloudFront คุณระบุ **origin**: แหล่งของเนื้อหาจริงของคุณ origin ของคุณอาจเป็น:

- S3 bucket (ไฟล์ static: รูป CSS JavaScript PDF)
- Application Load Balancer (เนื้อหา dynamic จากแอปพลิเคชันของคุณ)
- EC2 instance
- HTTP server ที่ไหนก็ได้บนอินเทอร์เน็ต

CloudFront นั่งอยู่หน้า origin ของคุณ คำขอเข้ามาที่ edge location ที่ใกล้ที่สุด ถ้า edge มีเนื้อหา cache ไว้ มันส่งคืนทันที ถ้าไม่ (*cache miss*) มันดึงจาก origin ของคุณ cache มัน และส่งคืน

**Caching ของ CloudFront ทำงานอย่างไร**

คำขอแรกสำหรับเนื้อหาชิ้นใด ๆ เป็น cache miss เสมอ — มันไปยัง origin ทุกคำขอถัดไปชน cache ที่ edge location

สำหรับ Nimbus รูปเมนูเป็นตัวเลือก CloudFront ที่สมบูรณ์แบบ รูปร้านอาหารเปลี่ยนไม่บ่อย (อาจตอนร้านอาหารอัปเดตโปรไฟล์) ด้วย CloudFront:

1. ผู้ใช้ในบอสตันขอ `images.eatnimbus.com/restaurant-047/photo.jpg`
2. CloudFront ตรวจ edge location ในบอสตัน — ยังไม่ได้ cache (cache miss)
3. CloudFront ดึงจาก S3 ใน us-west-2 (~80ms)
4. CloudFront เก็บรูปใน edge location ของบอสตัน
5. ผู้ใช้ถัดไปในบอสตันขอรูปเดียวกัน
6. CloudFront ให้บริการจาก edge cache ท้องถิ่น (~5ms)

โทษ 80ms เท่าเดิมสำหรับคำขอแรก แต่คำขอที่หนึ่งพันจากเมืองเดียวกันคือ 5 มิลลิวินาที

**Cache-Control header** และ **การตั้งค่า TTL** ใน CloudFront กำหนดว่าเนื้อหาอยู่ใน cache ที่ edge นานแค่ไหน ไฟล์รูป cache ได้เป็นชั่วโมงหรือวัน หน้า HTML (ซึ่งเปลี่ยนบ่อยกว่า) อาจ cache ได้เป็นนาทีหรือวินาที

คุณอาจสงสัย: ทำไมไม่ host แอปพลิเคชันทั้งหมดในหลาย region แทนการใช้ CDN? ถ้าข้อมูลอยู่ในออริกอน ทำไมไม่ใส่สำเนาเต็มในนิวยอร์ก โตเกียว และเซาเปาโล? คุณทำได้ แต่นั่นหมายถึงการทำให้หลายฐานข้อมูลซิงค์กัน การจัดการ deploy ข้าม region พร้อมกัน การจัดการสถานการณ์ split-brain ที่ region ไม่เห็นด้วยกัน CDN เป็นคำตอบที่ง่ายกว่ามากสำหรับเนื้อหา static และกึ่ง static: หนึ่ง origin หลายสำเนาที่ cache ที่ edge คุณเพิ่มความซับซ้อนหลาย region เฉพาะเมื่อคุณต้องการ compute หรือการดำเนินการฐานข้อมูลใกล้ผู้ใช้จริง ๆ — สำหรับเนื้อหาส่วนใหญ่ edge caching ก็พอ

"เดี๋ยว — แต่ *ทำไม* เราถึงทำแบบนั้น?" Maya ถาม "ทำไมวาง cache ที่ edge แทนการแค่เพิ่ม ElastiCache cluster ที่ใหญ่ขึ้นในออริกอน?"

**เนื้อหา Dynamic: CloudFront สำหรับมากกว่า Caching**

"แต่ API response ของเราล่ะ?" Leo ถาม "พวกนั้นเป็น dynamic — มันเปลี่ยนต่อผู้ใช้ ต่อคำขอ คุณ cache หน้าประวัติออเดอร์ไม่ได้"

จริง แต่ CloudFront ยังช่วยกับเนื้อหา dynamic

แม้เมื่อเนื้อหา cache ไม่ได้ CloudFront ส่งคำขอจาก edge location ไปยัง origin ผ่าน private backbone network ของ AWS — ไฟเบอร์ความเร็วสูงที่เชื่อมโครงสร้างพื้นฐาน AWS ทั่วโลก สิ่งนี้เร็วและน่าเชื่อถือกว่าการ route ผ่านอินเทอร์เน็ตสาธารณะ ที่ traffic เด้งผ่านหลายผู้ให้บริการ

ผลลัพธ์: คำขอ dynamic ยังเร็วกว่า 20-40% ผ่าน CloudFront เทียบกับไปยัง origin โดยตรงผ่านอินเทอร์เน็ตสาธารณะ ไม่ใช่เพราะ caching แต่เพราะเส้นทางเครือข่าย

"นั่นไม่สมเหตุสมผล" Maya พูด "ถ้า API response ยังต้องเดินทางจากออริกอนไป edge แล้วไปบอสตัน มันเร็วกว่าการไปตรงจากออริกอนไปบอสตันยังไง?"

"สองเหตุผล" Priya พูด "หนึ่ง private backbone ของ AWS เร็วและน่าเชื่อถือกว่าอินเทอร์เน็ตสาธารณะ traffic อินเทอร์เน็ตสาธารณะ route ผ่านหลายผู้ให้บริการ แต่ละรายเพิ่ม latency และความผันแปรของตัวเอง backbone เป็นไฟเบอร์ตรง latency ต่ำ สอง SSL termination เกิดที่ edge ผู้ใช้สร้างการเชื่อมต่อ TLS ไปยัง CloudFront edge location ที่ใกล้ที่สุด — handshake เร็ว แล้ว CloudFront เก็บการเชื่อมต่อแบบถาวรที่สร้างไว้ล่วงหน้าไปยัง origin สองการเชื่อมต่อระยะใกล้แทนหนึ่งการเชื่อมต่อระยะไกล"

"ดังนั้นแม้สำหรับเนื้อหาที่ไม่ได้ cache CloudFront ก็ตัดเวลาออกจาก connection overhead" Leo พูด

"โดยปกติสิบถึงสี่สิบเปอร์เซ็นต์ ไม่น่าตื่นเต้นเท่า caching แต่เป็นจริง"

นอกจากนี้ CloudFront ให้:

**SSL/TLS termination**: CloudFront จัดการ HTTPS ที่ edge การเชื่อมต่อระหว่างผู้ใช้และ CloudFront ถูกเข้ารหัส CloudFront เชื่อมต่อกับ origin ของคุณผ่าน HTTP ภายในได้ (ลดโหลด origin) หรือ HTTPS (สำหรับการเข้ารหัสปลายทางถึงปลายทาง)

**DDoS protection**: CloudFront รวมเข้ากับ AWS Shield Standard traffic ที่กระจายข้ามหลายร้อย edge location หมายความว่าการโจมตีถูกดูดซับที่ edge แทนที่จะกระแทก origin ของคุณ

**Geo-restriction**: บล็อกการเข้าถึงจากประเทศเฉพาะ ถ้า Nimbus ได้รับอนุญาตให้ดำเนินการในตลาดบางแห่งเท่านั้น CloudFront บังคับสิ่งนั้นที่ edge ได้โดยคำขอไม่เคยถึงเซิร์ฟเวอร์ของคุณ

**แล้วถ้ามีคนพยายามบุกรุกผ่าน CDN ล่ะ?** Priya ถาม "Cache poisoning — ถ้ามีคนสามารถ inject เนื้อหาที่ไม่ดีเข้า edge cache ล่ะ?"

"CloudFront มีการควบคุม cache key" Leo พูด "คุณกำหนดว่า attribute ใดกำหนดว่าสองคำขอได้ cached response เดียวกันหรือไม่ Header query string cookie ผู้โจมตี inject cached response ที่ต่างออกไปไม่ได้โดยไม่ตรงกับ cache key เป๊ะ"

"และ Origin Access Control หมายความว่า S3 bucket จะไม่ให้บริการอะไรที่ไม่ได้มาผ่าน CloudFront" Priya พูด "attack surface เดียวแทนสอง"

**CloudFront Behaviors: กฎ Caching แบบละเอียด**

CloudFront distribution มีหลาย **behavior** ได้ — กฎการ routing ตามรูปแบบ URL

สำหรับ Nimbus:

- `/images/*` → Cache ที่ edge เป็นเวลา 7 วัน (รูปไม่เปลี่ยนบ่อย)
- `/static/*` → Cache ที่ edge เป็นเวลา 30 วัน (CSS และ JavaScript ที่มีชื่อไฟล์เป็นเวอร์ชัน)
- `/api/*` → ไม่ cache; ส่งต่อไปยัง load balancer โดยตรง
- `/*` → Cache เป็นเวลา 5 นาที (หน้า HTML)

สิ่งนี้ทำให้ CloudFront ฉลาด: cache อย่างหนักสิ่งที่เสถียร ส่งผ่านสิ่งที่เป็น dynamic

behavior ถูกจับคู่จากเฉพาะที่สุดไปยังเฉพาะน้อยที่สุด `/images/hero.jpg` ตรงกับ `/images/*` ก่อนที่มันจะตรงกับ `/*` catch-all `/*` ที่ด้านล่างเป็นค่าเริ่มต้น — มันใช้กับอะไรก็ตามที่ไม่ตรงกับรูปแบบที่เฉพาะกว่า

"ถ้าเราต้องการ caching ต่างกันสำหรับผู้ใช้ที่ตรวจสอบสิทธิ์ vs ไม่ตรวจสอบสิทธิ์ล่ะ?" Priya ถาม "URL เดียวกันอาจส่งคืนเนื้อหาต่างกันขึ้นกับว่าผู้ใช้ล็อกอินหรือไม่"

"แล้วคุณรวม session cookie ใน cache key" Leo พูด "แต่นั่นหมายความว่าผู้ใช้ที่ล็อกอินทุกคนได้ cache entry ของตัวเอง hit rate ของคุณพังสำหรับเนื้อหาที่ตรวจสอบสิทธิ์"

"ซึ่งเป็นเหตุผลที่คุณแยกเนื้อหาที่ตรวจสอบสิทธิ์ออกจากเนื้อหาสาธารณะที่ระดับ URL" Priya พูด "อะไรที่ต้องการการตรวจสอบสิทธิ์ไปที่ `/app/*` และไม่ถูก cache เนื้อหาสาธารณะไปที่ `/browse/*` และถูก cache อย่างหนัก ขอบเขตชัดเจนเดียว"

บทเรียน: CloudFront ทำงานดีที่สุดเมื่อโครงสร้าง URL ของคุณสะท้อนเจตนา caching URL ที่ชี้ไปยังข้อมูล static สาธารณะเต็มที่ควรดูต่างจาก URL ที่ส่งคืนข้อมูลส่วนตัว dynamic ถ้าพวกมันดูเหมือนกันต่อ CloudFront ไม่ cache พังก็เนื้อหาผิดถูกส่ง

**Origin Access Control: รักษาความปลอดภัย S3 ด้วย CloudFront**

ถ้า S3 bucket ของคุณมีเนื้อหาส่วนตัวที่ควรให้บริการผ่าน CloudFront เท่านั้น (ไม่ใช่โดยตรง) คุณใช้ **Origin Access Control (OAC)** เพื่อให้แน่ใจว่า S3 ปฏิเสธคำขอที่ไม่ได้มาจาก CloudFront

ด้วยวิธีนี้:

- `d1234abcd.cloudfront.net/image.jpg` → ให้บริการ (CloudFront มีสิทธิ์)
- `nimbus-assets.s3.amazonaws.com/image.jpg` → ถูกบล็อก (การเข้าถึง S3 โดยตรงถูกปฏิเสธ)

เนื้อหาของคุณเข้าถึงได้เฉพาะผ่าน distribution ของคุณ พร้อมกฎ cache และการตั้งค่าความปลอดภัยของคุณที่ใช้

**Multiple Origins: ALB และ S3 ด้วยกัน**

"เรามีรูปบน S3 และ API บน load balancer" Maya พูด "เราต้องการ CloudFront distribution สองอันไหม?"

"ไม่" Leo พูด "หนึ่ง distribution หลาย origin"

CloudFront distribution เดียว route รูปแบบ URL ที่ต่างกันไปยัง origin ที่ต่างกันได้ นี่คือรูปแบบ multi-origin:

```
eatnimbus.com/*         → Origin: ALB in us-west-2 (dynamic content)
eatnimbus.com/images/*  → Origin: S3 bucket (static images)
eatnimbus.com/static/*  → Origin: S3 bucket (CSS, JS, fonts)
```

CloudFront ประเมิน behavior ตามลำดับความเฉพาะ คำขอไปยัง `/images/hero.jpg` ตรงกับ behavior `/images/*` และไปยัง S3 คำขอไปยัง `/api/orders` ตรงกับ catch-all `/*` และไปยัง ALB

ประโยชน์: หนึ่ง domain หนึ่ง SSL certificate หนึ่ง CloudFront distribution หลาย backend ผู้ใช้เห็น domain ที่เป็นหนึ่งเดียว การ routing มองไม่เห็นสำหรับพวกเขา

รายละเอียดด้านการดำเนินงานหนึ่งที่ก็เป็นข้อเท็จจริงในข้อสอบที่รับประกัน: SSL certificate นั้นมาจาก AWS Certificate Manager (ACM) และ **certificate ที่ CloudFront ใช้ต้องถูกขอหรือ import ใน `us-east-1`** — ไม่ว่า origin ของคุณอยู่ที่ไหน CloudFront เป็นบริการ global ที่ control plane อยู่ใน us-east-1; certificate ที่อยู่ใน us-west-2 จะไม่ปรากฏใน dropdown ของ distribution (สำหรับบริการระดับ region อย่าง ALB certificate อยู่ใน region ของ ALB เอง)

"และ ALB ไม่หันหน้าสู่สาธารณะใช่ไหม?" Priya ถาม

"เฉพาะ CloudFront คุยกับ ALB" Leo พูด "เราจำกัด security group ของ ALB ไปยัง managed prefix list ของ CloudFront การเชื่อมต่อโดยตรงไปยัง ALB จากอินเทอร์เน็ตถูกบล็อก"

"ดังนั้นวิธีเดียวที่จะเข้าถึงแอปพลิเคชันคือผ่าน CloudFront"

"ซึ่งหมายความว่ากฎ WAF, SSL termination และ DDoS protection ใช้กับ traffic ทั้งหมดก่อนถึงเรา"

**CloudFront Functions vs Lambda@Edge**

"เราคิดเรื่องว่าเราจะทำอะไรถ้าต้อง rewrite URL ที่ edge หรือยัง?" Priya ถาม "หรือเพิ่ม security header ในทุก response?"

"เราทำสิ่งนั้นในแอปพลิเคชันไม่ได้หรือ?" Leo ถาม

"เราทำได้ แต่ถ้ามันเกิดที่ edge — ก่อน CloudFront ให้บริการจาก cache — เราประหยัด round trip ไปยัง origin"

CloudFront รองรับสองกลไกสำหรับการรันโค้ดที่ edge:

**CloudFront Functions** คือ JavaScript function เบาที่รันที่ทุก edge location พวกมันทำงานในเวลาต่ำกว่ามิลลิวินาที จัดการคำขอหลายล้านต่อวินาที และออกแบบมาสำหรับการแปลงง่าย ๆ: URL rewrite การจัดการ header การ normalize query string redirect ง่าย ๆ พวกมันรันบน viewer request และ viewer response ได้ (ก่อนและหลัง cache จากมุมมองของผู้ใช้) พวกมันทำ network call ไม่ได้ ต้นทุน: $0.10 ต่อการเรียกหนึ่งล้านครั้ง

**Lambda@Edge** รัน Lambda function จริงที่ CloudFront regional edge location (ไม่ใช่ทุก pop แต่หลายสิบอันหลักทั่วโลก) Lambda@Edge ทำ network call เข้าถึงฐานข้อมูล สร้าง dynamic response ทำตรรกะการตรวจสอบสิทธิ์ที่ซับซ้อนได้ มันรันบน viewer request, origin request, origin response และ viewer response — ให้คุณสี่จุดแทรกแซงในวงจรชีวิตคำขอ ต้นทุน: สูงกว่า CloudFront Functions คิดต่อคำขอและระยะเวลา

โมเดลความคิด:

| กรณีใช้งาน | เครื่องมือ |
|---|---|
| Rewrite `/old-path` เป็น `/new-path` | CloudFront Functions |
| เพิ่ม `Strict-Transport-Security` header | CloudFront Functions |
| Normalize query string ก่อน cache lookup | CloudFront Functions |
| A/B test: กำหนด test cookie บน viewer request | CloudFront Functions |
| A/B test: route ผู้ใช้ 10% ไปยัง origin ที่ต่างกัน | Lambda@Edge (origin request — CloudFront Functions เปลี่ยน origin ไม่ได้) |
| ตรวจสอบสิทธิ์ JWT token (ต้องการ crypto library) | Lambda@Edge |
| ดึงเนื้อหาส่วนตัวจากฐานข้อมูลที่ edge | Lambda@Edge |
| สร้าง image thumbnail ตามคำขอที่ edge | Lambda@Edge |

สำหรับ Nimbus: พวกเขาใช้ CloudFront Function เพื่อเพิ่ม security header ในทุก response — `Strict-Transport-Security`, `X-Content-Type-Options`, `X-Frame-Options` JavaScript สองโหลบรรทัด การทำงานต่ำกว่ามิลลิวินาที ไม่ต้อง roundtrip ไป origin

"มันจะใช้เวลานานกว่าในการอธิบาย header ให้วิศวกรจูเนียร์" Leo พูด "เทียบกับการเขียน function"

**Price Classes: เลือกว่า Edge Location ไหน**

"เราคิดเรื่องว่านี่มีต้นทุนเท่าไรในระดับใหญ่หรือยัง?" Tom ถาม เลื่อนดูหน้าราคา CloudFront

"ราคาเท่าไรต่อเดือน?" จริง ๆ เป็นสองคำถามที่นี่ อันแรก: CloudFront คิดราคาเท่าไร? อันที่สอง: คุณต้องการทุก edge location ในโลกไหม?

ราคาการถ่ายโอนข้อมูล CloudFront ผันแปรตาม region traffic ที่ให้บริการจาก edge location ในอเมริกาเหนือและยุโรปถูกที่สุด traffic จากอเมริกาใต้ เอเชียแปซิฟิก ออสเตรเลีย และอินเดียแพงกว่า — เพราะโครงสร้างพื้นฐานมีต้นทุนสูงกว่าที่นั่น

AWS ให้คุณเลือก **price class** สำหรับ distribution ของคุณ:

- **Price Class All**: ใช้ทุก edge location ทั่วโลก ประสิทธิภาพดีที่สุดทุกที่ ต้นทุนการถ่ายโอนข้อมูลสูงสุดสำหรับ region นอกอเมริกาเหนือและยุโรป
- **Price Class 200**: ใช้ edge location ส่วนใหญ่ (อเมริกาเหนือ ยุโรป เอเชีย ตะวันออกกลาง แอฟริกา) ไม่รวมตำแหน่งอเมริกาใต้ที่แพงที่สุดและ Oceania บางแห่ง
- **Price Class 100**: ใช้เฉพาะ edge location อเมริกาเหนือและยุโรป ถูกที่สุด ผู้ใช้ในเซาเปาโล โตเกียว และซิดนีย์ยังได้รับบริการ — แต่จาก edge อเมริกาเหนือหรือยุโรป ไม่ใช่อันที่ใกล้ที่สุด

"ดังนั้นถ้าเราเลือก Price Class 100" Tom พูด "ผู้ใช้ในเซาเปาโลได้รับบริการจาก... ไมแอมี? นิวยอร์ก?"

"ที่ไหนก็ตามที่ edge ที่รวมอยู่ใกล้ที่สุด อาจ 50 มิลลิวินาทีแทน 230 มิลลิวินาทีตรงไปออริกอน" Priya พูด "ยังเป็นการปรับปรุงที่มีความหมาย ไม่ดีเท่า Price Class All"

"แล้วความแตกต่างของต้นทุนล่ะ?"

"การถ่ายโอนข้อมูลออกจากอเมริกาใต้ประมาณสองเท่าของต้นทุนอเมริกาเหนือ สำหรับสตาร์ทอัปที่ยังสร้าง traffic Price Class 200 เป็นการประนีประนอมที่สมเหตุสมผล — คุณได้เอเชียและยุโรปด้วยต้นทุนต่ำกว่า Price Class All และผู้ใช้ส่วนใหญ่ของคุณครอบคลุม"

"เริ่มด้วย 200" Tom พูด "เมื่อเรามีข้อมูล traffic จริงจากแต่ละ region เราจะตัดสินว่า All คุ้มค่าไหม"

**การออกแบบ Cache Key**

"เราคิดเรื่องว่าจะเกิดอะไรขึ้นเมื่อผู้ใช้สองคนที่ต่างกันขอ URL เดียวกันแต่ได้เนื้อหาต่างกันหรือยัง?" Priya ถาม

Leo คิดเกี่ยวกับมัน "หน้าที่ส่วนตัว"

"หรือหน้าที่เฉพาะภาษา หรือเวอร์ชัน mobile vs desktop หรือหน้าที่ผันแปรตาม cookie"

โดยค่าเริ่มต้น CloudFront ใช้เฉพาะ URL path เป็น cache key สองคำขอไปยัง `/browse` ได้ cached response เดียวกัน ไม่ว่าความชอบภาษา ประเภทอุปกรณ์ หรือ session cookie ของผู้ใช้

ถ้าแอปพลิเคชันของคุณให้บริการเนื้อหาที่ต่างกันตาม query string, header หรือ cookie — และคุณอยากให้ CloudFront cache รูปแบบเหล่านั้นแยกกัน — คุณต้องรวม attribute เหล่านั้นใน **cache key**

สำหรับ Nimbus:

- `/browse?city=miami` ควร cache แยกจาก `/browse?city=boston` — รายการร้านอาหารต่างกัน รวม query string ใน cache key
- ผู้ใช้ mobile อาจได้ layout ต่างกัน รวมประเภทอุปกรณ์ที่ normalize (มาจาก header `User-Agent`) ใน cache key
- header `Accept-Language` กำหนดว่าหน้า render ในภาษาใด รวมมันใน cache key

ระวังด้วย ทุก cache key attribute ที่คุณเพิ่มสร้างรูปแบบ cache มากขึ้น ถ้าคุณรวม string `User-Agent` ทั้งหมด (ซึ่งผันแปรตามเวอร์ชันเบราว์เซอร์ เวอร์ชัน OS และระดับ patch) คุณทำลาย caching โดยพฤตินัย — ผู้ใช้ทุกคนมี User-Agent ที่ต่างกันเล็กน้อย ดังนั้นทุกคำขอเป็น cache miss

วินัย: normalize ก่อน cache ลด "iPhone 15 Pro Safari 17.4.1" เป็น "mobile" ลดภาษาที่ยอมรับทั้งหมดเป็นสองหรือสามภาษาที่คุณรองรับจริง รวมเฉพาะสิ่งที่เปลี่ยน response จริง ๆ

"ยิ่ง cache key ของคุณเฉพาะ" Leo พูด "hit rate ของคุณยิ่งแย่"

"และยิ่งทั่วไป" Priya พูด "ยิ่งมีโอกาสที่คุณให้บริการเนื้อหาผิดแก่ผู้ใช้ผิด"

"ดังนั้นการออกแบบ cache key เป็นการแลกเปลี่ยนเดียวกับทุกอย่างอื่นใน caching"

"ใช่" Priya พูด "มันเป็นการแลกเปลี่ยนเดียวกันเสมอ"

## เมื่อ CloudFront ไม่ใช่คำตอบ: Global Accelerator

แอป mobile ของ Nimbus มีฟีเจอร์ที่ Tom เฝ้าดูเงียบ ๆ มาสองเดือน: สถานะออเดอร์แบบ real-time เมื่อลูกค้าสั่งอาหาร แอปเชื่อมต่ออยู่ผ่าน WebSocket และหน้าจอจัดการออเดอร์ของครัวอัปเดตแบบ real time ไม่มีปุ่มรีเฟรช ไม่มี polling การเชื่อมต่อแบบสดที่ push อัปเดตทันทีที่ครัวมาร์กรายการว่าพร้อม

"นี่ใช้ WebSocket" Tom พูด มองที่ตัวชี้วัด latency ในเช้าวันหนึ่ง "จากผู้ใช้ในเซาเปาโล การสร้างการเชื่อมต่อใช้เวลา 340 มิลลิวินาที มีอะไรผิด"

"CloudFront ไม่ cache การเชื่อมต่อ WebSocket" Leo พูด "มัน proxy พวกมัน — ส่งผ่านไปยัง origin ไม่มีประโยชน์ caching"

"ถูก แล้วทำไมมันยังช้า?"

"เพราะ WebSocket ยังเดินทางจากเซาเปาโลไปเซิร์ฟเวอร์ของเราในออริกอนผ่านอินเทอร์เน็ตสาธารณะ" Leo พูด "CloudFront ช่วย เพราะมันทำ TLS handshake ที่ edge แล้วใช้ backbone ของ AWS ไปยัง origin แต่สำหรับการเชื่อมต่อ WebSocket แบบถาวร นั่นยังเป็นการเชื่อมต่อระยะไกล"

"มีบริการสำหรับปัญหานี้เป๊ะ" Priya พูด

**AWS Global Accelerator** ไม่ใช่ CDN มันไม่ cache อะไร มันไม่ให้บริการเนื้อหาจาก edge location สิ่งที่มันทำคือให้ static Anycast IP address สองอันที่ประกาศทั่วโลกจากทุก AWS edge location พร้อมกัน — แล้ว route traffic ของผู้ใช้ของคุณผ่าน private backbone ของ AWS แทนอินเทอร์เน็ตสาธารณะ

เมื่อลูกค้าในเซาเปาโลเปิดแอป Nimbus อุปกรณ์ของพวกเขาเชื่อมต่อกับ AWS edge location ที่ใกล้ที่สุด (ซึ่งอาจอยู่ในเซาเปาโลเอง) จาก edge location นั้น traffic เดินทางไปเซิร์ฟเวอร์ของ Nimbus ในออริกอนผ่านเครือข่ายไฟเบอร์ส่วนตัว ที่ตรวจสอบ ที่ optimize ของ AWS — ไม่ใช่ผ่านอินเทอร์เน็ตสาธารณะที่ packet เด้งผ่านผู้ให้บริการและ routing hop ที่คาดเดาไม่ได้

อินเทอร์เน็ตสาธารณะไม่ได้ออกแบบมาสำหรับ latency มันออกแบบมาสำหรับ resilience — packet ใช้เส้นทางที่มีให้อันใดก็ได้ backbone ของ AWS ออกแบบต่างกัน: มันตรง congestion ต่ำ และอยู่ภายใต้การควบคุมด้านการดำเนินงานของ AWS

Tom benchmark ความแตกต่าง

| เส้นทาง | Latency (เซาเปาโลไปออริกอน) |
|---|---|
| อินเทอร์เน็ตสาธารณะ | 340ms |
| ผ่าน Global Accelerator | 180ms |

ลด 47% ไม่ใช่จาก caching — จากเส้นทางเครือข่ายที่ดีกว่า

"แล้วทำไมเราไม่ใช้ CloudFront สำหรับทุกอย่าง?" Maya ถาม "CloudFront route ผ่าน backbone ของ AWS สำหรับเนื้อหา dynamic อยู่แล้ว"

"CloudFront เป็น HTTP และ HTTPS เท่านั้น" Priya พูด "WebSocket ทำงานกับ CloudFront แต่ผ่าน HTTP upgrade เท่านั้น และโปรโตคอลบางอย่างของเรา — ข้อมูลเซ็นเซอร์ IoT เป็นต้น — เป็น TCP หรือ UDP ล้วน CloudFront ไม่จัดการพวกนั้น Global Accelerator ไม่สนใจโปรโตคอล TCP, UDP, WebSocket อะไรก็ตาม มันย้าย packet ไม่ใช่คำขอ HTTP"

มีความแตกต่างอีกอันที่ Priya บันทึกในเอกสารความปลอดภัยของเธอ

"Global Accelerator ให้ static Anycast IP สองอัน" เธอพูด "IP เหล่านั้นไม่เคยเปลี่ยน นั่นหมายความว่าเราเพิ่มมันใน security policy เพิ่มมันใน partner whitelist เพิ่มมันใน firewall rule ได้ IP address ของ CloudFront เปลี่ยนตามเวลา — พวกมันถูกจัดการโดย AWS และไม่ตายตัว"

"แล้ว failover ล่ะ?" Leo ถาม

"ทันที" Priya พูด "ถ้าแอปพลิเคชัน us-west-2 ของเรามีปัญหา Global Accelerator เปลี่ยน traffic ไปยัง backup ใน us-east-1 ในเวลาต่ำกว่า 30 วินาทีได้ — โดยไม่เปลี่ยน IP address ที่ผู้ใช้เชื่อมต่ออยู่ DNS failover ผ่าน Route 53 ใช้เวลา 60-300 วินาทีขึ้นกับ TTL Global Accelerator เร็วกว่า"

**CloudFront vs. Global Accelerator — โมเดลความคิด:**

CloudFront ปรับปรุงการส่งมอบด้วยการ caching มันสร้างมาสำหรับ HTTP/HTTPS และประโยชน์ใหญ่ที่สุดเมื่อเนื้อหา cache ได้ใกล้ผู้ใช้ — ไฟล์ static รูป JavaScript เมื่อเนื้อหา cache ไม่ได้ CloudFront ยังช่วยผ่าน backbone routing แต่การปรับปรุงเล็กกว่า

Global Accelerator ปรับปรุงการส่งมอบด้วยการ routing มันไม่ย้ายเนื้อหา มันไม่ cache อะไร ประโยชน์ใช้กับทุก packet — cache หรือไม่ HTTP หรือไม่ static หรือ dynamic static IP สองอันทำงานทั่วโลก failover เกือบทันที กรณีใช้งานที่ CloudFront ไม่เพียงพอ — WebSocket แบบ real-time โปรโตคอลแบบ UDP traffic ที่ไม่ใช่ HTTP แอปพลิเคชันระดับโลกที่ต้องการ fixed IP — คือที่ที่ Global Accelerator เป็นเครื่องมือที่ถูกต้อง

Tom อัปเดตแอป mobile ของ Nimbus ให้เชื่อมต่อกับ Global Accelerator endpoint สำหรับฟีเจอร์สถานะออเดอร์แบบ real-time การสร้างการเชื่อมต่อ WebSocket ในเซาเปาโลลดจาก 340ms เป็น 180ms การอัปเดตของครัวยังรู้สึกทันที — เพราะตอนนี้ สำหรับผู้ใช้นอกอเมริกาเหนือ มันทันทีจริง ๆ

## จุดแข็งและข้อจำกัด

**ทำไม CloudFront ถึงทรงพลัง**:

- point of presence มากกว่า 750 อันใน 100+ เมือง — ผู้ใช้ส่วนใหญ่ได้เนื้อหาจากที่ห่าง <20ms
- เนื้อหา static ให้บริการในมิลลิวินาทีหลักเดียวหลัง cache แรก
- ลดโหลด origin อย่างมาก (traffic ซ้ำไม่เคยชนเซิร์ฟเวอร์ของคุณ)
- รวมเข้ากับ AWS Shield, WAF และ Certificate Manager
- ไม่ต้องวางแผน capacity — CloudFront scale อัตโนมัติ
- multi-origin distribution route path ต่างกันไปยัง backend ต่างกันจาก domain เดียว
- CloudFront Functions จัดการตรรกะ edge เบาที่ latency ต่ำกว่ามิลลิวินาที

**ที่ที่มันซับซ้อน**:

- เนื้อหาที่ cache ไว้อาจเก่า — การ invalidate cache เสียเงิน ($0.005 ต่อ path หลัง 1,000 path ฟรีแรกของแต่ละเดือน) ใช้ชื่อไฟล์ที่เป็นเวอร์ชันแทน
- Cache-Control header ต้องตั้งถูกต้องที่ origin — ความผิดพลาดทำให้เนื้อหาเก่า
- เนื้อหา dynamic ได้ประโยชน์จากการ optimize routing แต่ไม่จาก caching
- การดีบักพฤติกรรม cache (อะไร cache ที่ไหน นานแค่ไหน) ต้องเข้าใจหลายชั้น: origin header, การตั้งค่า CloudFront TTL, กฎ behavior
- การถ่ายโอนข้อมูลออกผ่าน CloudFront เสียเงิน แม้น้อยกว่าการถ่ายโอนข้อมูลมาตรฐาน
- การออกแบบ cache key ต้องการการคิดอย่างระมัดระวัง — เฉพาะเกินไปทำลาย caching ทั่วไปเกินไปให้บริการเนื้อหาผิด

## สรุป

CloudFront ไม่ได้เปลี่ยนฟิสิกส์ แสงยังเดินทางที่ความเร็วเดิม แต่มันเปลี่ยนว่าคำตอบอยู่ที่ไหน — และสำหรับผู้ใช้ส่วนใหญ่ คำตอบตอนนี้ห่างไม่กี่มิลลิวินาทีแทนที่จะไม่กี่ร้อย Cache hit rate หลังการ deploy: 83% นั่นหมายความว่า 830,000 จากทุกหนึ่งล้านคำขอไม่เคยถึงเซิร์ฟเวอร์ origin เลย ผู้ใช้ในเซาเปาโลไปจาก 290 มิลลิวินาทีเป็น 35 มิลลิวินาที ผู้ใช้ในโตเกียวจาก 260 เป็น 28

- **CDN** cache สำเนาของเนื้อหาของคุณที่ edge location ใกล้ผู้ใช้ — ลด latency และโหลด origin
- **CloudFront** คือ CDN ของ AWS มี point of presence 750+ อันทั่วโลก
- Cache miss ดึงจาก **origin** (S3, ALB, EC2) Cache hit ให้บริการจาก edge — มิลลิวินาที ไม่ใช่หลายร้อยมิลลิวินาที
- **Behaviors** ให้คุณตั้งกฎ caching ต่างกันสำหรับรูปแบบ URL ต่างกัน distribution เดียวให้บริการ `/images/*` จาก S3 และ `/*` จาก ALB ได้
- เนื้อหา dynamic ไม่ถูก cache แต่ CloudFront ยังปรับปรุงประสิทธิภาพผ่าน private backbone network ของ AWS
- **หลีกเลี่ยงเนื้อหาเก่า** โดยใช้ชื่อไฟล์ที่เป็นเวอร์ชัน (เช่น `hero-v2.jpg`) แทน invalidation — ถูกกว่าและน่าเชื่อถือกว่า
- **CloudFront Functions** จัดการตรรกะ edge เบา (การจัดการ header, URL rewrite) ที่ความเร็วต่ำกว่ามิลลิวินาที **Lambda@Edge** จัดการการประมวลผลที่หนักกว่าที่ต้องการ network call
- **Price classes** ให้คุณควบคุมว่า edge location ใดให้บริการ traffic ของคุณ — และดังนั้นต้นทุนการถ่ายโอนข้อมูลของคุณ
- **การออกแบบ cache key** กำหนดว่า attribute คำขอใดสร้างรูปแบบ cache แยกกัน key ที่เฉพาะกว่า = hit rate ต่ำกว่า เฉพาะน้อยกว่า = เสี่ยงให้บริการเนื้อหาผิด

## เคล็ดลับการสอบ

*SAA-C03 Domain: ออกแบบสถาปัตยกรรมที่มีประสิทธิภาพสูง (Domain 3, Task 3.4)*

- **CloudFront + S3**: รูปแบบข้อสอบคลาสสิกสำหรับการให้บริการเว็บไซต์ static ทั่วโลก S3 bucket เป็น origin, CloudFront เป็น CDN, Origin Access Control เพื่อป้องกันการเข้าถึง S3 โดยตรง
- **Edge locations vs Regions vs AZs**: Edge location มีจำนวนมากกว่าและมีอยู่เพื่อวัตถุประสงค์ caching/CDN เท่านั้น พวกมันไม่เหมือน AZ (ซึ่งรัน compute ของคุณ)
- **Cache invalidation**: สร้าง invalidation `/images/*` เพื่อบังคับ CloudFront ดึงเนื้อหาใหม่ เสียเงิน — ข้อสอบอาจถามทางเลือกที่คุ้มค่า: URL ที่เป็นเวอร์ชัน (`image-v2.jpg` แทน `image.jpg`) ซึ่งข้าม cache ตามธรรมชาติ
- **TTL control**: `Cache-Control: max-age=3600` ที่ origin ตั้ง cache TTL 1 ชั่วโมง CloudFront เคารพ header เหล่านี้ Minimum TTL, maximum TTL และ default TTL ตั้งใน distribution behavior ได้ด้วย
- **CloudFront Functions vs Lambda@Edge**: CloudFront Functions รันที่ edge สำหรับการจัดการ request/response เบา (ต่ำกว่ามิลลิวินาที) Lambda@Edge รันโค้ด Lambda ของคุณที่ regional edge location สำหรับการประมวลผลที่หนักกว่า ข้อสอบแยกแยะพวกมันด้วยความซับซ้อนของกรณีใช้งาน CloudFront Functions ทำ network call ไม่ได้; Lambda@Edge ทำได้
- **Signed URLs และ Signed Cookies**: ควบคุมว่าใครเข้าถึงเนื้อหาผ่าน CloudFront ได้ Signed URL ให้การเข้าถึงไฟล์เฉพาะ; signed cookie ให้การเข้าถึงหลายไฟล์ ข้อสอบใช้สิ่งเหล่านี้สำหรับ "เนื้อหาสมาชิกแบบจ่ายเงิน"
- **Price Class**: ข้อสอบอาจถามว่าจะเลือก price class ใดสำหรับผู้ชมระดับโลก vs ผู้ชมอเมริกาเหนือ/ยุโรป Price Class All = ประสิทธิภาพดีที่สุด ต้นทุนสูงสุด Price Class 100 = อเมริกาเหนือและยุโรปเท่านั้น ต้นทุนต่ำสุด
- **Cache key**: cache key เริ่มต้นคือ URL การเพิ่ม query string, header หรือ cookie ใน cache key สร้างรูปแบบ cache แยกกัน — แต่เพิ่มอัตรา cache miss ข้อสอบอาจนำเสนอสถานการณ์ที่เนื้อหาผันแปรตาม query parameter และถามว่าจะกำหนดค่า caching อย่างไร
- **Origin failover**: CloudFront รองรับ origin group ที่มี primary และ secondary origin ถ้า primary origin ส่งคืน error 5xx CloudFront retry กับ secondary โดยอัตโนมัติ ต่างจาก Route 53 failover — นี่อยู่ภายใน CloudFront distribution เดียว
- **Multi-origin behaviors**: distribution เดียว route `/images/*` ไปยัง S3 และ `/*` ไปยัง ALB ได้ ข้อสอบอาจนำเสนอนี่เป็น "วิธีให้บริการเนื้อหา static และ dynamic จาก domain เดียวโดยไม่ต้องมีสอง distribution"
- **CloudFront vs. Global Accelerator:** CloudFront = HTTP/HTTPS CDN, cache เนื้อหาที่ edge location, ลดโหลด origin, ดีที่สุดสำหรับเนื้อหา static และ cache ได้ Global Accelerator = โปรโตคอล TCP/UDP ใด ๆ, ไม่ cache อะไร, route traffic ผ่าน private backbone ของ AWS, ให้ static Anycast IP 2 อัน, รองรับ regional failover เกือบทันที ทริกเกอร์ในข้อสอบ: "ปรับปรุง latency สำหรับ traffic ที่ไม่ใช่ HTTP" หรือ "static IP สำหรับแอปพลิเคชันระดับโลก" หรือ "ประสิทธิภาพ WebSocket สำหรับผู้ใช้ทั่วโลก" หรือ "regional failover ที่เร็วกว่า DNS" → Global Accelerator "ให้บริการไฟล์ static ทั่วโลกด้วย latency ต่ำ" → CloudFront

## แบบฝึกหัด

**แบบฝึกหัด 1 — ทบทวน**

อธิบายความแตกต่างระหว่าง CloudFront cache hit กับ cache miss เกิดอะไรขึ้นในแต่ละกรณี?

*(คำใบ้: คิดถึงว่าเนื้อหามาจากที่ไหน และเวลาตอบสนองต่างกันอย่างไรระหว่างสองกรณี)*

**แบบฝึกหัด 2 — สถานการณ์ SAA-C03**

*สถานการณ์*: บริษัทซอฟต์แวร์แจกจ่ายไฟล์ installer ขนาดใหญ่ (~2GB แต่ละไฟล์) จาก S3 bucket ไปยังลูกค้าทั่วโลก ความเร็วดาวน์โหลดช้าสำหรับลูกค้าในเอเชีย ทีมอยากปรับปรุงประสิทธิภาพโดยไม่ทำซ้ำ S3 bucket ไปหลาย region พวกเขายังต้องมั่นใจว่าเฉพาะลูกค้าที่จ่ายเงินเท่านั้นที่ดาวน์โหลด installer ได้

วิธีแก้ใดตอบความต้องการเหล่านี้ได้ดีที่สุด?

A) เปิด S3 Transfer Acceleration บน bucket และสร้าง pre-signed URL สำหรับลูกค้าที่จ่ายเงิน  
B) ใช้ CloudFront โดยมี S3 bucket เป็น origin เปิด Origin Access Control และใช้ CloudFront Signed URL สำหรับลูกค้าที่จ่ายเงิน  
C) สร้าง S3 bucket ในแต่ละ AWS region และใช้ Route 53 geolocation routing เพื่อนำทางลูกค้าไปยัง bucket ที่ใกล้ที่สุด  
D) ใช้ Application Load Balancer ในแต่ละ region พร้อม EC2 instance ที่ให้บริการไฟล์ installer

**คำใบ้ 1**: ความต้องการคือปรับปรุงประสิทธิภาพทั่วโลก *โดยไม่* ทำซ้ำ bucket ตัวเลือกใดไม่ต้องการหลาย bucket?

**คำใบ้ 2**: บริการใดควบคุมว่าใครเข้าถึงเนื้อหาที่ให้บริการผ่าน CloudFront ได้โดยเฉพาะ?

**คำใบ้ 3**: S3 Transfer Acceleration optimize สำหรับการอัปโหลดระยะไกล *ไปยัง* S3 สำหรับการส่งมอบเนื้อหา *จาก* S3 ไปยังผู้ใช้ปลายทางทั่วโลก CloudFront คือเครื่องมือที่ถูกต้อง

**คำตอบ**: B

**คำอธิบาย**: CloudFront cache ไฟล์ installer ที่ edge location ทั่วโลกหลังการดาวน์โหลดครั้งแรก การดาวน์โหลดถัดไปจาก region เดียวกันมาจาก edge — เร็วกว่าการข้ามแปซิฟิกจาก S3 ใน us-west-2 มาก Origin Access Control รับประกันว่า S3 bucket เข้าถึงได้เฉพาะผ่าน CloudFront Signed URL จำกัดการเข้าถึงเฉพาะลูกค้าที่จ่ายเงิน

**ทำไมไม่ใช่ A?** S3 Transfer Acceleration optimize สำหรับการอัปโหลดระยะไกล *เข้า* S3 — ไม่ใช่สำหรับการแจกจ่ายเนื้อหา *จาก* S3 ไปยังผู้ชมระดับโลก สำหรับนั้น CloudFront คือเครื่องมือที่ถูกต้อง pre-signed URL ควบคุมการเข้าถึงแต่ไม่ปรับปรุงประสิทธิภาพทั่วโลก

**ทำไมไม่ใช่ C?** การสร้าง S3 bucket ต่อ region ใช้ได้สำหรับประสิทธิภาพ แต่มันขัดกับความต้องการที่จะหลีกเลี่ยงการทำซ้ำ มันยังต้องการกลยุทธ์การซิงค์ข้อมูลข้าม bucket

**ทำไมไม่ใช่ D?** EC2 instance หลัง load balancer ในแต่ละ region แพงกว่า CloudFront อย่างมีนัยสำคัญและต้องการการจัดการเซิร์ฟเวอร์ในหลาย region
