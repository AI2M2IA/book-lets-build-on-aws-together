# บทที่ 2: เซิร์ฟเวอร์ของคุณอยู่ที่ไหนในโลก?

ลุกขึ้น เดินไปที่หน้าต่างถ้ามีหน้าต่างอยู่ใกล้ๆ

มองออกไปข้างนอก สิ่งที่คุณเห็น — อาคาร ต้นไม้ ลานจอดรถ สวนหลังบ้านของใครสักคน — ไม่มีสิ่งใดเป็นที่อยู่ของข้อมูลของคุณ ข้อมูลของคุณอยู่ที่อื่นโดยสิ้นเชิง อาจเป็นที่ที่คุณไม่เคยไป

นั่นไม่ใช่ปัญหา แต่การเข้าใจว่า *ที่ไหน* ทำให้สิ่งต่างๆ ที่น่าแปลกใจมากมายมีความหมาย

บทที่แล้ว Leo สร้างบัญชี AWS เมื่อ 4 ทุ่มและเปิดเซิร์ฟเวอร์ที่ไหนสักที่ "ที่ไหนสักที่" เป็นคำสำคัญ — เขาไม่แน่ใจว่าเขาเลือกส่วนใดของโลก เพราะเขาไม่ได้เลือกโดยตั้งใจ

เช้าวันถัดไป Maya สังเกตว่าเซิร์ฟเวอร์อยู่ที่สิงคโปร์

"ทำไมถึงเป็นสิงคโปร์?" เธอถาม

"มันเป็นค่าเริ่มต้น" Leo บอก

Tom เงยหน้าจากกาแฟ "ราคาเท่าไหร่ที่จะรันเซิร์ฟเวอร์ในสิงคโปร์เมื่อลูกค้าทั้งหมดของเราอยู่ที่ฝั่งตะวันตก?"

Leo ไม่มีคำตอบ

Priya มีคำตอบอยู่แล้ว: "มันช้ากว่าด้วย ทุกคำขอต้องเดินทางครึ่งโลก"

บทนี้เกี่ยวกับการแก้ไขการตัดสินใจนั้น — และการเข้าใจว่าทำไมมันถึงสำคัญ

**ปัญหากับ "ที่ไหนสักที่"**

เมื่อคุณใช้ AWS คุณไม่ได้ใช้ศูนย์ข้อมูลเดียว คุณกำลังใช้เครือข่ายทั่วโลกของพวกเขา AWS มีโครงสร้างพื้นฐานในหลายสิบประเทศ

นั่นเป็นคุณสมบัติ ไม่ใช่แค่ข้อเท็จจริง แต่หมายความว่าคุณต้องเลือก: *ที่ไหน* ที่คุณต้องการให้โครงสร้างพื้นฐานของคุณทำงาน?

การเลือกสำคัญด้วยสามเหตุผล:

**ประสิทธิภาพ** ยิ่งเซิร์ฟเวอร์ของคุณใกล้กับผู้ใช้มากเท่าไหร่ การตอบสนองก็เร็วขึ้นเท่านั้น ฟิสิกส์ไม่สามารถต่อรองได้ ข้อมูลเดินทางด้วยความเร็วประมาณสองในสามของความเร็วแสงผ่านสายไฟเบอร์ออปติก คำขอจากซีแอตเทิลไปสิงคโปร์ใช้เวลาประมาณ 300 มิลลิวินาทีแค่ในการเดินทาง — ก่อนที่แอปพลิเคชันของคุณจะทำอะไรเลย

**การปฏิบัติตาม** บางอุตสาหกรรมมีกฎหมายเกี่ยวกับที่ที่ข้อมูลสามารถเก็บได้ ข้อมูลสุขภาพของสหรัฐฯ อาจต้องอยู่ในประเทศ ข้อมูลทางการเงินอาจต้องอยู่ในภูมิภาคเฉพาะ การเลือก Region ที่ผิดอาจสร้างปัญหาทางกฎหมาย

**ความยืดหยุ่นต่อภัยพิบัติ** ถ้าสถานที่หนึ่งไฟดับ แผ่นดินไหว หรือเครือข่ายล้มเหลว คุณต้องการให้ระบบของคุณรอดชีวิต การกระจายโครงสร้างพื้นฐานในหลายสถานที่คือวิธีที่คุณป้องกันภัยพิบัติในท้องถิ่น

**AWS จัดระเบียบโครงสร้างพื้นฐานอย่างไร**

AWS แบ่งโครงสร้างพื้นฐานทั่วโลกออกเป็นสามแนวคิดที่ซ้อนกัน คิดว่าพวกมันเหมือนตุ๊กตาแม่ลูกดกรัสเซีย จากใหญ่ที่สุดไปเล็กที่สุด

**Regions → Availability Zones → Edge Locations**

มาเปิดแต่ละอันกัน

**Regions: กล่องใหญ่**

**Region** คือพื้นที่ทางภูมิศาสตร์ที่ AWS มีคลัสเตอร์ศูนย์ข้อมูล แต่ละ Region ตั้งชื่อตามตำแหน่ง: `us-west-2` คือรัฐออริกอน `us-east-1` คือเวอร์จิเนียเหนือ `eu-west-1` คือไอร์แลนด์ `ap-southeast-1` คือสิงคโปร์ — ที่ที่เซิร์ฟเวอร์ของ Leo ซ่อนอยู่

มีมากกว่า 30 Region ทั่วโลก และ AWS เพิ่มอยู่เสมอ

แต่ละ Region เป็นอิสระอย่างสมบูรณ์ ข้อมูลใน `us-west-2` อยู่ใน `us-west-2` เว้นแต่คุณจะย้ายมันอย่างชัดเจน สิ่งนี้สำคัญมากสำหรับการปฏิบัติตามและความยืดหยุ่น — การหยุดทำงานครั้งใหญ่ใน Region หนึ่งไม่ส่งผลต่อ Region อื่นๆ โดยอัตโนมัติ

"เราควรเลือก `us-west-2` สำหรับ Nimbus ไหม?" Tom ถาม

ใช่ สำหรับธุรกิจในสหรัฐฯ ที่มุ่งเป้าลูกค้าฝั่งตะวันตก ใช่ ความหน่วงต่ำลงและผู้ใช้ของคุณจะได้รับการตอบสนองที่เร็วขึ้น

"แพงกว่าสิงคโปร์เท่าไหร่?" Tom เพิ่มเติม

ราคาแตกต่างกันตาม Region — โดยปกติไม่กี่เปอร์เซ็นต์ ประโยชน์ด้านประสิทธิภาพและการปฏิบัติตามของ Region ที่ถูกต้องคุ้มค่ากับความแตกต่างของราคาเล็กน้อย

**Availability Zones: ความซ้ำซ้อนที่แท้จริง**

นี่คือที่ที่น่าสนใจ

แต่ละ Region ไม่ใช่ศูนย์ข้อมูลเดียว มันเป็นคลัสเตอร์ของศูนย์ข้อมูลแยกทางกายภาพหลายแห่งที่เรียกว่า **Availability Zones** (หรือ AZs)

ออริกอน (`us-west-2`) มีสี่ Availability Zone: `us-west-2a`, `us-west-2b`, `us-west-2c`, `us-west-2d` เหล่านี้เป็นอาคารจริง แยกออกจากกันในระยะที่มีความหมาย — ห่างพอที่ไฟไหม้ น้ำท่วม หรือไฟดับในหนึ่งจะไม่ส่งผลต่ออีกอัน แต่ใกล้พอที่เครือข่ายระหว่างพวกมันจะเร็วมาก (ความหน่วงหลักมิลลิวินาทีเดียว)

นี่คือสถาปัตยกรรมที่ทำให้ AWS น่าเชื่อถือในระดับที่ศูนย์ข้อมูลเดียวไม่สามารถทำได้

Priya โน้มตัวไปข้างหน้า "ถ้าเราเรียกใช้แอปพลิเคชันของเราบน Availability Zone สองอันและอันหนึ่งล้มเหลว—"

"อันอื่นยังทำงานต่อไป" Maya สรุป

"นั่นแหละ"

Leo ที่นั่งฟังเงียบๆ: "ผม deploy ทุกอย่างไว้ใน AZ เดียว"

"ใช่" Priya พูด "เราสังเกตแล้ว"

แนวคิดของการกระจายแอปพลิเคชันของคุณข้าม AZs หลายอัน — เรียกว่า **การ deploy แบบ Multi-AZ** — เป็นหนึ่งในรูปแบบความยืดหยุ่นที่สำคัญที่สุดใน AWS เราจะเจาะลึกในบทที่ 18

**Edge Locations: ความเร็ว ทุกที่**

AZs แก้ปัญหาความยืดหยุ่น แต่ไม่แก้ปัญหาของการให้บริการเนื้อหาอย่างรวดเร็วแก่ผู้ใช้ในเมืองที่อยู่ห่างไกลจาก Region หลักของคุณ

เข้ามา **Edge Locations**

Edge Location เป็นจุดโครงสร้างพื้นฐานขนาดเล็กน้ำหนักเบาที่กระจายอยู่ในกว่า 400 เมืองทั่วโลก พวกมันไม่ใช่ศูนย์ข้อมูลเต็มรูปแบบ — พวกมันไม่สามารถรันแอปพลิเคชันของคุณได้ สิ่งที่พวกมัน *สามารถ* ทำได้คือแคชเนื้อหาใกล้กับผู้ใช้ของคุณ

ลองนึกภาพรูปเมนูที่จัดเก็บบนเซิร์ฟเวอร์ในเวอร์จิเนีย ทุกครั้งที่มีคนในโตเกียวต้องการดูมัน คำขอต้องข้ามมหาสมุทรแปซิฟิกและกลับมา ด้วย Edge Location AWS สามารถจัดเก็บสำเนาของไฟล์นั้นในโตเกียวและให้บริการมันในเครื่อง — มิลลิวินาทีแทนที่จะเป็นร้อยมิลลิวินาที

นี่คือกระดูกสันหลังของ CloudFront เครือข่ายการส่งเนื้อหาของ AWS เราจะขุดลึกใน CloudFront ในบทที่ 13

**การเลือก Region: รายการตรวจสอบของวิศวกรอาวุโส**

เมื่อ Nimbus ขยายไปให้บริการผู้ใช้ในเม็กซิโกและโคลอมเบีย (ซึ่งเกิดขึ้นในบทที่ 12) การตัดสินใจ Region ไม่ได้เป็นเรื่องสุ่ม นี่คือวิธีคิด:

**1. ผู้ใช้ของคุณอยู่ที่ไหน?**

เริ่มจากนี้ เลือก Region ที่ใกล้กับผู้ใช้ส่วนใหญ่ของคุณมากที่สุด ความหน่วงคือผลกระทบที่ตรงและวัดได้มากที่สุดของการเลือก Region

**2. มีข้อกำหนดการปฏิบัติตามหรือไม่?**

งานในด้านการดูแลสุขภาพ การเงิน และรัฐบาลมักมีกฎระเบียบที่เข้มงวดเกี่ยวกับที่อยู่ของข้อมูล รู้สภาพแวดล้อมด้านกฎหมายของคุณก่อนเลือก

**3. คุณต้องการ service อะไรบ้าง?**

ไม่ใช่ทุก AWS service จะมีในทุก Region บริการใหม่เปิดตัวใน `us-east-1` ก่อน ถ้าคุณต้องการ service เฉพาะ ตรวจสอบว่า Region เป้าหมายของคุณรองรับหรือไม่

**4. ราคาเป็นอย่างไร?**

Region มีราคาแตกต่างกัน `us-east-1` (เวอร์จิเนียเหนือ) มีแนวโน้มที่จะถูกที่สุดเนื่องจากขนาดและอายุ อเมริกาใต้แพงกว่าเล็กน้อย ตรวจสอบหน้าราคาของ AWS ก่อนตัดสินใจ

**5. คุณต้องการ Multi-Region หรือไม่?**

สำหรับแอปพลิเคชันส่วนใหญ่ AZs หลายอันใน Region เดียวเป็นความยืดหยุ่นที่เพียงพอ สำหรับแอปพลิเคชันที่สำคัญที่แม้แต่การหยุดทำงานของ Region ก็ไม่ยอมรับได้ คุณออกแบบสำหรับ Multi-Region — แต่นั่นเป็นความมุ่งมั่นทางสถาปัตยกรรมที่สำคัญ อย่าทำแบบนั้นโดยการคาดเดา

**ข้อจำกัดที่ไม่มีใครพูดถึง**

Regions มีประสิทธิภาพ แต่สร้างความตึงเครียดสำคัญหนึ่งอย่าง

การรันใน Regions หลายอันยากจริงๆ

การสำเนาข้อมูลระหว่าง Region มีความหน่วง การรักษา Region สองอันให้ซิงโครไนซ์ — เพื่อให้ธุรกรรมใน Region A สามารถมองเห็นได้ทันทีใน Region B — เป็นหนึ่งในปัญหาที่ยากที่สุดในระบบกระจาย AWS มีเครื่องมือสำหรับมัน แต่มีค่าใช้จ่ายและเพิ่มความซับซ้อนในการดำเนินงาน

แอปพลิเคชันส่วนใหญ่ควรเริ่มด้วย Region เดียว AZs หลายอัน และขยายไปยัง Multi-Region เมื่อมีข้อกำหนดที่ชัดเจนเท่านั้น

Tom พยักหน้า "เราจึงไม่ทำ Multi-Region เพียงเพราะเราทำได้"

"ไม่ จนกว่าเราจะต้องการ" Maya พูด "และเราจะรู้เมื่อเราต้องการ"

"เราจะรู้ได้อย่างไร?" Leo ถาม

"เมื่อเอกสารสถาปัตยกรรมของคุณมีข้อกำหนดที่บอกว่า 'ต้องรอดชีวิตจากการหยุดทำงานของ Region'" Priya พูด "จนกว่านั้น: Multi-AZ"

## จุดแข็งและข้อจำกัด

**ใช้การออกแบบ Multi-Region และ Multi-AZ เมื่อ**: แอปพลิเคชันของคุณมีผู้ใช้ในหลายภูมิศาสตร์และความหน่วงสำคัญ; SLA ของคุณต้องการความพร้อมใช้งาน 99.99% หรือสูงกว่า; ข้อกำหนดด้านกฎระเบียบบังคับให้ข้อมูลอยู่ใน region เฉพาะ; คุณต้องการการกู้คืนจากภัยพิบัติด้วย RTO ภายในหนึ่งชั่วโมง

**การแลกเปลี่ยนเป็นเรื่องจริง**: การสำเนาข้อมูลข้าม region เพิ่มต้นทุน — การถ่ายโอนข้อมูลข้าม region เป็นหนึ่งในรายการที่ถูกประเมินต่ำที่สุดในบิล AWS มันยังเพิ่มความซับซ้อนในการดำเนินงานด้วย

## สรุป

- AWS จัดระเบียบโครงสร้างพื้นฐานทั่วโลกเป็น **Regions**, **Availability Zones** และ **Edge Locations**
- **Region** คือคลัสเตอร์ศูนย์ข้อมูลทางภูมิศาสตร์ แต่ละ Region แยกออกจากกัน — ข้อมูลอยู่ใน Region เว้นแต่คุณจะย้ายมันอย่างชัดเจน
- **Availability Zones** คือศูนย์ข้อมูลที่แยกทางกายภาพภายใน Region เชื่อมต่อด้วยเครือข่ายความหน่วงต่ำ
- **Edge Locations** แคชเนื้อหาใกล้กับผู้ใช้ทั่วโลก พวกมันขับเคลื่อน CloudFront
- เลือก Region ของคุณตามตำแหน่งผู้ใช้ ข้อกำหนดการปฏิบัติตาม ความพร้อมใช้งานของ service และราคา — ตามลำดับนั้น
- Multi-AZ คือเส้นฐานความยืดหยุ่นมาตรฐาน Multi-Region สำหรับงานที่สำคัญพร้อมข้อกำหนดเฉพาะที่บันทึกไว้ — ไม่ใช่จุดเริ่มต้นเริ่มต้น

- **Region แยกออกจากกันโดยค่าเริ่มต้น** ข้อมูลไม่สำเนาระหว่าง Region เว้นแต่คุณจะกำหนดค่า สิ่งนี้สำคัญสำหรับสถานการณ์อธิปไตยข้อมูลและการปฏิบัติตาม
- **AZ คือหน่วยความยืดหยุ่นสำหรับคำถามส่วนใหญ่** เมื่อการสอบถามถึงวิธีรอดชีวิตจากความล้มเหลวของศูนย์ข้อมูล คำตอบเกี่ยวข้องกับ AZs หลายอันใน Region เดียว
- **Multi-Region สำหรับความยืดหยุ่นต่อการหยุดทำงานของ Region** ถ้าสถานการณ์บอกว่า "ต้องยังคงทำงานแม้ AWS Region ทั้งหมดล้มเหลว" คำตอบเกี่ยวข้องกับสถาปัตยกรรม Multi-Region
- **Edge Location ≠ AZs** Edge Location แคชเนื้อหา — ไม่สามารถรันเซิร์ฟเวอร์แอปพลิเคชันของคุณได้

## แบบฝึกหัด

**แบบฝึกหัด 1 — การจำ**

ด้วยคำพูดของคุณเอง: ความแตกต่างระหว่าง Region และ Availability Zone คืออะไร? ทำไมความแตกต่างนั้นจึงสำคัญเมื่อออกแบบแอปพลิเคชันเว็บที่มีความยืดหยุ่น?

**แบบฝึกหัด 2 — การฝึกสอบ**

*สถานการณ์*: บริษัทดูแลสุขภาพในสหรัฐฯ ต้องจัดเก็บข้อมูลผู้ป่วยทั้งหมดใน AWS Region เดียวเพื่อปฏิบัติตามนโยบายที่อยู่ข้อมูลภายใน พวกเขากำลังออกแบบแอปพลิเคชันคลาวด์ใหม่บนชายฝั่งตะวันตกและต้องการเพิ่มความยืดหยุ่นสูงสุดโดยไม่ย้ายข้อมูลไปยัง Region อื่น

การกำหนดค่าใด BEST ตอบสนองความต้องการของพวกเขา?

ก) Deploy ใน `us-east-1` และใช้ CloudFront Edge Locations ในรัฐออริกอนเพื่อให้บริการเนื้อหาได้เร็วขึ้น  
ข) Deploy ใน `us-west-2` (ออริกอน) ข้าม Availability Zones หลายอัน  
ค) Deploy ในหลาย Region รวมถึง `us-west-2` และ `us-east-1` พร้อมการสำเนาข้อมูลข้าม Region  
ง) Deploy ใน `us-west-2` ใน Availability Zone เดียวเพื่อลดต้นทุน

**คำตอบ**: ข

**คำอธิบาย**: `us-west-2` เก็บข้อมูลทั้งหมดใน Region เดียว ตอบสนองข้อกำหนดนโยบาย การ deploy ข้าม AZs หลายอันใน Region นั้นป้องกันความล้มเหลวของศูนย์ข้อมูลโดยไม่ย้ายข้อมูลไปยัง Region อื่น
