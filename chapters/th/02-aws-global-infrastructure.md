# บทที่ 2: เซิร์ฟเวอร์ของคุณอยู่ที่ไหนในโลก?

ลุกขึ้น เดินไปที่หน้าต่างถ้ามีหน้าต่างอยู่ใกล้ ๆ

มองออกไปข้างนอก สิ่งที่คุณเห็น — อาคาร ต้นไม้ ลานจอดรถ สวนหลังบ้านของใครสักคน — ไม่มีสิ่งใดเป็นที่อยู่ของข้อมูลของคุณ ข้อมูลของคุณอยู่ที่อื่นโดยสิ้นเชิง อาจเป็นที่ที่คุณไม่เคยไป

นั่นไม่ใช่ปัญหา แต่การเข้าใจว่า *ที่ไหน* ทำให้สิ่งต่าง ๆ จำนวนมากอย่างน่าแปลกใจเข้าที่เข้าทาง

หลังจากการประชุมที่ไวท์บอร์ด การตัดสินใจก็เกิดขึ้น: Nimbus จะใช้ AWS คลาวด์คือคำตอบ แต่ "คลาวด์" กลับกลายเป็นสิ่งเฉพาะเจาะจงในตำแหน่งเฉพาะเจาะจง — และ Leo ได้เลือกตำแหน่งนั้นโดยไม่ได้ตั้งใจ

เช้าวันถัดมา Maya สังเกตเห็นว่าเซิร์ฟเวอร์อยู่ที่สิงคโปร์

"ทำไมถึงเป็นสิงคโปร์?" เธอถาม

"มันเป็นค่าเริ่มต้น" Leo บอก

Tom เงยหน้าขึ้นจากกาแฟ "มันมีต้นทุนเท่าไหร่ในการรันเซิร์ฟเวอร์ในสิงคโปร์ในเมื่อลูกค้าทั้งหมดของเราอยู่ที่ชายฝั่งตะวันตก?"

Leo ไม่มีคำตอบ

Priya มีข้อกังวลที่ต่างออกไปอยู่แล้ว "และใครจะรู้ว่าข้อมูลนั้นกำลังผ่านเขตอำนาจศาลไหนบ้าง?"

บทนี้เกี่ยวกับการแก้ไขการตัดสินใจนั้น — และการเข้าใจว่าทำไมมันถึงสำคัญ

**ปัญหากับคำว่า "ที่ไหนสักที่"**

เมื่อคุณใช้ AWS คุณไม่ได้ใช้ศูนย์ข้อมูลเดียว คุณกำลังใช้เครือข่ายทั่วโลกของพวกมัน AWS มีโครงสร้างพื้นฐานในหลายสิบประเทศ

นั่นเป็นคุณสมบัติ ไม่ใช่แค่ข้อเท็จจริง แต่มันหมายความว่าคุณต้องเลือก: *ที่ไหน* ที่คุณต้องการให้โครงสร้างพื้นฐานของคุณทำงาน?

การเลือกสำคัญด้วยสามเหตุผล:

**ประสิทธิภาพ** ยิ่งเซิร์ฟเวอร์ของคุณใกล้กับผู้ใช้มากเท่าไหร่ การตอบสนองก็ยิ่งเร็วขึ้น ฟิสิกส์ต่อรองไม่ได้ ข้อมูลเดินทางด้วยความเร็วประมาณสองในสามของความเร็วแสงผ่านสายไฟเบอร์ออปติก การเดินทางไป-กลับจากซีแอตเทิลไปสิงคโปร์ใช้เวลาราว ๆ 170 มิลลิวินาทีแค่ในการเดินทาง — ก่อนที่แอปพลิเคชันของคุณจะทำอะไรเลย คำขอเดียวกันนั้นจากซีแอตเทิลไปออริกอน (`us-west-2`) ใช้เวลาราว ๆ 20 มิลลิวินาที ความแตกต่างนี้ไม่ใช่ความคลาดเคลื่อนจากการปัดเศษ สำหรับแอปสั่งอาหารร้านอาหารที่ลูกค้าคาดหวังว่าหน้าเพจจะรู้สึกทันใจ — และที่หน้าเพจเดียวกระตุ้นการเดินทางไป-กลับหลายครั้ง — ความหน่วงพื้นฐาน 170ms ต่อการเดินทางไป-กลับคือความแตกต่างระหว่างผลิตภัณฑ์ที่เร็วกับผลิตภัณฑ์ที่อืดอาด

Tom หยิบโทรศัพท์ขึ้นมา เปิดแอป Nimbus และโหลดหน้าร้านอาหาร เขาจับเวลาด้วยแอปนาฬิกาจับเวลา

"เกือบสามวินาที" เขาพูด

Leo ตรวจสอบรายละเอียดความหน่วงในบันทึกเซิร์ฟเวอร์ แค่การเดินทางไป-กลับสิงคโปร์ — ไม่เกี่ยวกับการสืบค้นฐานข้อมูล — กำลังเพิ่มราว ๆ 170 มิลลิวินาทีต่อคำขอ และแอปทำการเดินทางไป-กลับหลายครั้งต่อหน้าเพจ

"แล้วถ้าเราย้ายเซิร์ฟเวอร์ไปออริกอนล่ะ?" Tom ถาม

"ยี่สิบมิลลิวินาที" Leo พูด "อาจน้อยกว่านั้น"

"มันมีต้นทุนต่อเดือนเท่าไหร่?"

ความแตกต่างของราคาอยู่ที่ไม่กี่เปอร์เซ็นต์ ไม่ใช่ศูนย์ แต่ก็ไม่ใช่ตัวแปรหลัก พวกเขาย้ายเซิร์ฟเวอร์ไป `us-west-2` ในบ่ายวันนั้น

"ผม deploy เอเจนต์มอนิเตอร์ไปที่ instance สิงคโปร์แล้วน่ะ" Leo พูดกับตัวเองครึ่งหนึ่ง "อ้าว" เขาหยุด "ผมจะตั้งค่ามันในออริกอนแทน"

**การปฏิบัติตามข้อกำหนด** บางอุตสาหกรรมมีกฎหมายเกี่ยวกับว่าข้อมูลสามารถเก็บได้ที่ไหน ข้อมูลสุขภาพของสหรัฐฯ อาจต้องอยู่ภายในประเทศ ข้อมูลทางการเงินอาจต้องอยู่ในภูมิภาคเฉพาะ การเลือก Region ที่ผิดอาจสร้างปัญหาทางกฎหมาย

Priya ค้นคว้าเรื่องนี้มาก่อนที่ใครจะขอให้เธอทำ

"GDPR" เธอพูด พลางเงยหน้าขึ้นจากบันทึกของเธอในการประชุม standup เช้าวันถัดไป "ถ้า Nimbus ให้บริการลูกค้าในสหภาพยุโรปเมื่อไหร่ — แม้แต่ลูกค้ารายเดียว — ข้อมูลส่วนบุคคลเกี่ยวกับพวกเขาอาจต้องอยู่ภายในสหภาพยุโรปหรือในประเทศที่มีการคุ้มครองที่เทียบเท่า นั่นไม่ใช่ทางเลือก นั่นคือกฎหมาย"

"เราเป็นแอปสั่งอาหารร้านอาหารนะ" Leo พูด "ในแคลิฟอร์เนีย"

"ตอนนี้" Priya พูด "เราคิดถึงเรื่องที่จะเกิดขึ้นถ้าเราขยายไปยุโรปในอีกสิบแปดเดือนแล้วพบว่าเราเก็บข้อมูลลูกค้ายุโรปไว้ในออริกอนมาปีครึ่งหรือยัง?"

หยุดชั่วครู่

"เราก็จะแก้มันตอนนั้น" Leo พูด

"คุณแก้การละเมิดเรื่องถิ่นที่อยู่ของข้อมูลย้อนหลังไม่ได้" Priya พูด "การละเมิดเกิดขึ้นไปแล้ว"

เธอไม่ได้พูดเกินจริง ค่าปรับ GDPR สูงถึง 4% ของรายได้ทั่วโลกต่อปี การละเมิด HIPAA ในด้านสุขภาพของสหรัฐฯ อาจสูงเกิน $2 ล้านต่อหมวดการละเมิดต่อปี สิ่งเหล่านี้ไม่ใช่เรื่องสมมติ — มันเป็นเหตุผลที่การตัดสินใจเรื่องคลาวด์ขององค์กรขนาดใหญ่เริ่มต้นด้วยการทำแผนที่การปฏิบัติตามข้อกำหนด ไม่ใช่การกำหนดค่าโครงสร้างพื้นฐาน

สำหรับ Nimbus ความเสี่ยงด้านกฎระเบียบเฉพาะหน้านั้นต่ำ: ลูกค้าสหรัฐฯ ไม่มีข้อมูลสุขภาพ ไม่มีบริการทางการเงิน แต่การเลือก Region สำหรับธุรกิจที่ตั้งใจจะเติบโตหมายถึงการเลือกโดยคำนึงถึงการเติบโต

**ความยืดหยุ่นต่อภัยพิบัติ** ถ้าสถานที่หนึ่งไฟดับ แผ่นดินไหว หรือเครือข่ายล้มเหลว คุณต้องการให้ระบบของคุณรอด การกระจายโครงสร้างพื้นฐานในหลายสถานที่คือวิธีที่คุณป้องกันภัยพิบัติในท้องถิ่น

**AWS จัดระเบียบโครงสร้างพื้นฐานอย่างไร**

AWS แบ่งโครงสร้างพื้นฐานทั่วโลกออกเป็นสามแนวคิดที่ซ้อนกัน คิดว่าพวกมันเหมือนตุ๊กตาแม่ลูกดกรัสเซีย จากใหญ่ที่สุดไปเล็กที่สุด: ตุ๊กตาใหญ่ที่เปิดออกเผยให้เห็นตุ๊กตากลาง ซึ่งเปิดออกเผยให้เห็นตุ๊กตาเล็ก แต่ละชั้นซ้อนอยู่ในชั้นถัดไป

ตุ๊กตาชั้นนอกสุดคือสิ่งที่ AWS เรียกว่า **Region** ภายใน Region มีคลัสเตอร์ของ **Availability Zone** อยู่ และกระจายอยู่ทั่วทุกที่ทั่วโลก เป็นอิสระจากทั้งสองอย่าง คือ **Edge Location**

มาเปิดแต่ละอันกัน

**Regions: กล่องใหญ่**

**Region** คือพื้นที่ทางภูมิศาสตร์ที่ AWS มีคลัสเตอร์ของศูนย์ข้อมูล แต่ละ Region ตั้งชื่อตามตำแหน่ง: `us-west-2` คือออริกอน `us-east-1` คือเวอร์จิเนียเหนือ `eu-west-1` คือไอร์แลนด์ `ap-southeast-1` คือสิงคโปร์ — ที่ที่เซิร์ฟเวอร์ของ Leo ซ่อนอยู่

มีเกือบ 40 Region ทั่วโลก และ AWS เพิ่มขึ้นอยู่เสมอ รายการยังเติบโตต่อเนื่องเมื่อ AWS ขยายตัว: มี Region ในอเมริกาเหนือ อเมริกาใต้ ยุโรป ตะวันออกกลาง เอเชียแปซิฟิก และแอฟริกา โดยทั่วไปแต่ละ Region ใหม่จะประกาศล่วงหน้าหลายเดือนก่อนเปิด มี Availability Zone อย่างน้อยสามแห่งตั้งแต่เปิดตัว และใช้เวลาหลายปีก่อนที่ทุก AWS service จะพร้อมใช้งานในนั้น

แต่ละ Region เป็นอิสระอย่างสมบูรณ์ ข้อมูลใน `us-west-2` อยู่ใน `us-west-2` เว้นแต่คุณจะย้ายมันอย่างชัดเจน สิ่งนี้สำคัญยิ่งสำหรับการปฏิบัติตามข้อกำหนดและความยืดหยุ่น — การหยุดทำงานครั้งใหญ่ใน Region หนึ่งไม่ส่งผลต่อ Region อื่นโดยอัตโนมัติ เหตุการณ์ที่ขัดขวางโครงข่ายไฟฟ้าในเวอร์จิเนียเหนือไม่ส่งผลต่อออริกอน ภัยธรรมชาติในไอร์แลนด์ไม่ส่งผลต่อสิงคโปร์ Region แยกออกจากกันอย่างแท้จริงที่ระดับโครงสร้างพื้นฐานทางกายภาพ

ความเป็นอิสระนั้นสมบูรณ์มากจนถ้า Region หนึ่งกำลังประสบการหยุดทำงานครั้งใหญ่ แม้แต่คอนโซลการจัดการ AWS ก็อาจโหลดช้า — เพราะคอนโซลเองรันอยู่ในโครงสร้างพื้นฐานของ AWS สิ่งนี้ควรค่าแก่การรู้: ในระหว่างเหตุการณ์ AWS จริง คุณอาจพบว่าเข้าถึงเครื่องมือมอนิเตอร์ที่คุณต้องการได้ยากในเวลาที่คุณต้องการมันมากที่สุดพอดี นี่เป็นส่วนหนึ่งของเหตุผลที่ทีมที่มีประสบการณ์มอนิเตอร์บริการของตัวเองโดยอิสระจากคอนโซลของ AWS

"ดังนั้นเราควรเลือก `us-west-2` สำหรับ Nimbus ใช่ไหม?" Tom ถาม

ใช่ สำหรับธุรกิจในสหรัฐฯ ที่มุ่งเป้าลูกค้าชายฝั่งตะวันตก ใช่ ความหน่วงต่ำลงและผู้ใช้ของคุณได้รับการตอบสนองที่เร็วขึ้น

"มันแพงกว่าสิงคโปร์เท่าไหร่?" Tom เสริม

ราคาแตกต่างกันตาม Region — โดยปกติไม่กี่เปอร์เซ็นต์ ประโยชน์ด้านประสิทธิภาพและการปฏิบัติตามข้อกำหนดของ Region ที่ถูกต้องคุ้มค่ากับความแตกต่างของราคาเล็กน้อย

**การถกเถียงเรื่องการเลือก Region ที่ Nimbus เกือบทำผิด**

ก่อนที่ทีมจะลงตัวกับ `us-west-2` มีการถกเถียงสั้น ๆ ว่า `us-east-1` (เวอร์จิเนียเหนือ) สมเหตุสมผลกว่าหรือไม่ มันเป็น Region ที่เก่าแก่ที่สุด ใหญ่ที่สุด เป็น Region ที่ AWS ปล่อยบริการใหม่ก่อน มันยังเป็น Region ที่ถูกที่สุดในหน้าราคาส่วนใหญ่ Tom ชอบสิ่งนี้

"แต่ผู้ใช้ของเราอยู่ในแคลิฟอร์เนีย ออริกอน และวอชิงตัน" Maya พูด "ทำไมเราถึงจะรันเซิร์ฟเวอร์ของเราที่อีกฟากของประเทศ?"

"ถูกกว่า" Tom พูด "และมีบริการให้ใช้มากกว่า"

"เดี๋ยวนะ — แต่ *ทำไม* เราถึงจะทำแบบนั้น?" Maya พูด "ผู้ใช้ของเราอยู่ที่ชายฝั่งตะวันตก เซิร์ฟเวอร์ของเราควรอยู่ที่ชายฝั่งตะวันตก ความแตกต่างของราคาคือเท่าไหร่ หกเปอร์เซ็นต์? เจ็ด? เราจะเสียมากกว่าจากความหน่วงพิเศษในรูปของลูกค้าที่หายไป มากกว่าที่เราจะประหยัดได้จากบิลคอมพิวต์"

เธอพูดถูก Region ที่ถูกต้องสำหรับเวิร์กโหลดคือ Region ที่ใกล้กับผู้ใช้ที่สำคัญที่สุดมากที่สุด — เว้นแต่การปฏิบัติตามข้อกำหนด ความพร้อมใช้งานของบริการ หรือส่วนต่างของต้นทุนจะคุ้มค่ากับการแลก สำหรับ Nimbus ไม่มีปัจจัยใดเลยที่คุ้ม

นี่เป็นการตัดสินใจที่รู้สึกเล็กแต่ไม่เล็ก ทีมที่เลือก `us-east-1` เพราะ "มันเป็นค่าเริ่มต้น" แล้วให้บริการผู้ใช้ชายฝั่งตะวันตกจากชายฝั่งตะวันออกกำลังทิ้งประสิทธิภาพที่เป็นจริงไป คอนโซล AWS ตั้งค่าเริ่มต้นเป็น `us-east-1` ด้วยเหตุผลทางประวัติศาสตร์ มันไม่ใช่คำแนะนำ

**Availability Zones: ความซ้ำซ้อนที่แท้จริง**

นี่คือที่ที่มันเริ่มน่าสนใจ

แต่ละ Region ไม่ใช่ศูนย์ข้อมูลเดียว มันเป็นคลัสเตอร์ของศูนย์ข้อมูลที่แยกกันทางกายภาพหลายแห่งที่เรียกว่า **Availability Zone** (หรือ AZ)

ออริกอน (`us-west-2`) มี Availability Zone สี่แห่ง: `us-west-2a`, `us-west-2b`, `us-west-2c`, `us-west-2d` เหล่านี้เป็นอาคารจริง แยกออกจากกันด้วยระยะทางที่มีความหมาย — ห่างกันพอที่ไฟไหม้ น้ำท่วม หรือไฟดับในแห่งหนึ่งจะไม่ส่งผลต่ออีกแห่ง แต่ใกล้พอที่เครือข่ายระหว่างพวกมันเร็วมาก (ความหน่วงระดับมิลลิวินาทีหลักเดียว)

"ระยะทางที่มีความหมาย" ห่างกันแค่ไหน? AWS ไม่ได้เผยแพร่พิกัดที่แน่นอน แต่นักวิจัยอิสระประมาณว่า AZ ภายใน Region มักแยกกันด้วยระยะหลายสิบไมล์ — ห่างพอที่จะอยู่บนโครงข่ายไฟฟ้าและเส้นทางไฟเบอร์ที่ต่างกัน ไม่ห่างมากจนความเร็วแสงกลายเป็นปัจจัยจำกัดสำหรับการจำลองข้อมูลแบบซิงโครนัส

การแยกนี้เป็นไปอย่างตั้งใจและสำคัญ ถ้า AZ สองแห่งใช้สถานีไฟฟ้าย่อยเดียวกัน ความล้มเหลวของสถานีย่อยก็จะทำให้ AZ ทั้งสองล่มพร้อมกัน — ขจัดความซ้ำซ้อน การแยกทางกายภาพช่วยให้แน่ใจว่าความล้มเหลวแบบโหมดร่วม (ประเภทที่ส่งผลต่อพื้นที่ทางภูมิศาสตร์ทั้งหมด) เป็นเหตุการณ์ที่หายากอย่างแท้จริง ไม่ใช่ความเสี่ยงที่คาดการณ์ได้

นี่คือสถาปัตยกรรมที่ทำให้ AWS น่าเชื่อถือในระดับที่ศูนย์ข้อมูลเดียวเทียบไม่ได้

Priya โน้มตัวไปข้างหน้า "ดังนั้นถ้าเรารันแอปพลิเคชันของเราข้าม Availability Zone สองแห่งและแห่งหนึ่งล่ม—"

"อีกแห่งก็ทำงานต่อไป" Maya พูดต่อ

"นั่นแหละ"

Leo ที่นั่งฟังเงียบ ๆ: "ผม deploy ทุกอย่างไว้ใน AZ เดียว"

"ใช่" Priya พูด "เราสังเกตเห็นแล้ว"

แนวคิดของการกระจายแอปพลิเคชันของคุณข้าม AZ หลายแห่ง — เรียกว่า **การ deploy แบบ Multi-AZ** — เป็นหนึ่งในรูปแบบความยืดหยุ่นที่สำคัญที่สุดใน AWS เราจะเจาะลึกมันในบทที่ 18 ตอนนี้ ให้เข้าใจว่า AZ มีอยู่เพื่อทำให้สิ่งนี้เป็นไปได้โดยเฉพาะ

มีรายละเอียดหนึ่งที่ควรรู้: ชื่อ AZ (`us-west-2a`, `us-west-2b` ฯลฯ) ไม่สอดคล้องกันข้ามบัญชี AWS สิ่งที่ปรากฏเป็น `us-west-2a` ในบัญชีของคุณอาจเป็นศูนย์ข้อมูลทางกายภาพคนละแห่งกับสิ่งที่ปรากฏเป็น `us-west-2a` ในบัญชีของเพื่อนร่วมงาน AWS สุ่มการแมปเพื่อป้องกันไม่ให้ลูกค้าทั้งหมด deploy ไปยัง AZ ทางกายภาพเดียวกันเมื่อพวกเขาใช้ค่าเริ่มต้น "a" ถ้าคุณต้องการประสานงานว่าคุณอยู่ใน AZ ทางกายภาพใดกับอีกบัญชีหนึ่ง (เช่นสำหรับการสื่อสารระหว่างบัญชีที่ความหน่วงต่ำ) AWS มี AZ ID — ตัวระบุที่เสถียรซึ่งแมปกับตำแหน่งทางกายภาพเดียวกันข้ามบัญชี ชื่อ AZ (`2a`, `2b`) เป็นแบบสัมพัทธ์กับบัญชี AZ ID (`usw2-az1`, `usw2-az2`) เป็นแบบกายภาพ การสอบทดสอบความแตกต่างนี้เป็นบางครั้ง

**ความล้มเหลวของ AZ มีหน้าตาเป็นอย่างไรจริง ๆ**

นี่ไม่ใช่เรื่องนามธรรม ขอเดินผ่านไทม์ไลน์จริง

ตอนนี้เป็นเวลา 14:47 น. ของวันอังคาร ความผิดปกติทางไฟฟ้าในหม้อแปลงตัวหนึ่งที่จ่ายไฟให้ `us-west-2b` ทำให้เกิดการหยุดทำงานในศูนย์ข้อมูลนั้น เหตุการณ์นี้ไม่ได้ถูกคาดการณ์

นี่คือความแตกต่างระหว่าง Multi-AZ กับ single-AZ ขอบเขตของ AZ คือที่ที่การออกแบบความซ้ำซ้อนของ AWS กลายเป็นความยืดหยุ่นของแอปพลิเคชันของคุณ

**คณิตศาสตร์ความน่าเชื่อถือของ Multi-AZ**

AWS ออกแบบให้แต่ละ AZ เป็นอิสระ — ไม่ใช่แค่ทางกายภาพ แต่ด้วยพลังงาน การระบายความร้อน และเครือข่ายที่แยกกัน ความน่าจะเป็นที่ AZ สองแห่งใน Region เดียวกันจะล้มเหลวพร้อมกันถูกออกแบบให้ต่ำมาก

ถ้า AZ เดียวมีความพร้อมใช้งาน 99.9% (ประมาณ 8.7 ชั่วโมงของการหยุดทำงานต่อปี) สถาปัตยกรรมสอง AZ ที่ถือว่าความล้มเหลวเป็นเหตุการณ์อิสระก็จะมีความพร้อมใช้งานราว ๆ 99.9999% สำหรับโหมดความล้มเหลวเดียวกัน — ประมาณ 31 วินาทีของการหยุดทำงานต่อปีจากความล้มเหลวของ AZ

ในทางปฏิบัติ ปัจจัยจำกัดสำหรับแอปพลิเคชันส่วนใหญ่ไม่ใช่ความพร้อมใช้งานของ AZ มันคือโค้ดแอปพลิเคชัน กระบวนการ deploy และฐานข้อมูล แต่คณิตศาสตร์นี้แสดงให้เห็นว่าทำไม Multi-AZ จึงเป็นเส้นฐานมาตรฐาน: ต้นทุนของการรันข้ามสอง AZ นั้นพอประมาณ การปรับปรุงความพร้อมใช้งานนั้นมาก

**Edge Locations: ความเร็ว ทุกที่**

AZ แก้ปัญหาความยืดหยุ่น พวกมันไม่แก้ปัญหาของการให้บริการเนื้อหาอย่างรวดเร็วแก่ผู้ใช้ในเมืองที่อยู่ไกลจาก Region หลักของคุณ

เข้ามา **Edge Location**

Edge Location เป็นจุดโครงสร้างพื้นฐานขนาดเล็กน้ำหนักเบา — มากกว่า 750 จุดที่ตั้งกระจายอยู่ใน 100+ เมืองทั่วโลก พวกมันไม่ใช่ศูนย์ข้อมูลเต็มรูปแบบ — พวกมันรันแอปพลิเคชันของคุณไม่ได้ สิ่งที่พวกมัน *ทำได้* คือแคชเนื้อหาให้ใกล้กับผู้ใช้ของคุณ

ลองนึกภาพรูปเมนูที่จัดเก็บบนเซิร์ฟเวอร์ในเวอร์จิเนีย ทุกครั้งที่คนในโตเกียวต้องการดูมัน คำขอเดินทางข้ามมหาสมุทรแปซิฟิกและกลับมา ด้วย Edge Location AWS สามารถจัดเก็บสำเนาของไฟล์นั้นในโตเกียวและให้บริการมันในเครื่อง — มิลลิวินาทีแทนที่จะเป็นหลายร้อยมิลลิวินาที

นี่คือกระดูกสันหลังของ CloudFront เครือข่ายการส่งมอบเนื้อหาของ AWS เราจะเจาะลึก CloudFront ในบทที่ 13 ตอนนี้: Edge Location เกี่ยวกับความเร็วสำหรับเนื้อหาแบบสแตติก

คุณอาจสงสัย: ถ้า Edge Location แคชเนื้อหา พวกมันก็เก็บข้อมูลของคุณถาวรด้วยหรือไม่? ไม่ Edge Location เก็บสำเนาเนื้อหาชั่วคราวเพื่อให้บริการได้เร็วขึ้น — ต้นฉบับอยู่ใน Region ของคุณเสมอ ถ้าแคชหมดอายุหรือเนื้อหาเปลี่ยน Edge Location จะดึงสำเนาใหม่จากแหล่งที่มา

เครือข่าย Edge Location แยกจากโครงสร้าง Region และ AZ เมื่อคุณคิดเกี่ยวกับว่าแอปพลิเคชันของคุณ *รัน* ที่ไหน คุณคิดถึง Region และ AZ เมื่อคุณคิดเกี่ยวกับว่าเนื้อหาไปถึงผู้ใช้ของคุณ *อย่างรวดเร็ว* ได้อย่างไร คุณคิดถึง Edge Location และ CloudFront พวกมันแก้ปัญหาที่ต่างกันและทำงานที่ชั้นที่ต่างกัน

AWS ยังมีแนวคิดที่เกี่ยวข้องเรียกว่า **Regional Edge Cache** — โหนดแคชที่ใหญ่กว่าซึ่งอยู่ระหว่าง Region ของคุณกับ Edge Location ถ้า Edge Location ในเมืองหนึ่งไม่มีสำเนาแคชของไฟล์ มันจะดึงจาก Regional Edge Cache แทนที่จะกลับไปจนถึง Region ของคุณ สิ่งนี้ลดโหลดบน origin ของคุณและปรับปรุงอัตราการเจอแคชสำหรับเนื้อหาที่ได้รับความนิยมน้อยกว่า คุณไม่ได้กำหนดค่า Regional Edge Cache โดยตรง — พวกมันเป็นส่วนหนึ่งของโครงสร้างพื้นฐาน CloudFront ที่ทำงานโดยอัตโนมัติ

ผลลัพธ์เชิงปฏิบัติสำหรับ Nimbus: เมื่อทีมเพิ่ม CloudFront ในบทที่ 13 รูปเมนูที่เคยเดินทางจากออริกอนไปยังเบราว์เซอร์ของลูกค้าในทุกคำขอจะถูกให้บริการจาก Edge Location ที่ใกล้ที่สุดแทน — ดัลลาสสำหรับลูกค้าเท็กซัส แอตแลนตาสำหรับลูกค้าจอร์เจีย ชิคาโกสำหรับลูกค้าอิลลินอยส์ ผู้ใช้ในชิคาโกได้รูปเมนูจากเซิร์ฟเวอร์ที่ห่าง 300 ไมล์แทนที่จะ 2,000 ไมล์ ความแตกต่างนั้นวัดได้และมีความหมาย

**ข้อควรระวังเกี่ยวกับสำเนาที่แคช**

มีรายละเอียดหนึ่งเกี่ยวกับ Edge Location ที่ควรชี้ให้เห็นตอนนี้ แม้ว่าเรื่องราวฉบับเต็มจะเป็นของบทที่ 13: สำเนาที่แคชคือ *สำเนา* และสำเนาก็เก่าได้ ถ้าต้นฉบับเปลี่ยนใน Region ของคุณ Edge Location อาจให้บริการเวอร์ชันเก่าต่อไปสักพัก นานแค่ไหน และคุณทำอะไรเกี่ยวกับมันได้บ้าง คือการควบคุมแบบที่ CDN ให้คุณพอดี — และเป็นสิ่งที่ทีมจะต้องต่อสู้ด้วยเมื่อ Nimbus deploy CloudFront จริง ตอนนี้ ให้นำเพียงสิ่งนี้ติดตัวไป: เนื้อหาสามารถอยู่ใกล้ผู้ใช้ได้ และ "ใกล้" บางครั้งหมายถึง "ล้าสมัยไปนิดหน่อย"

**การเลือก Region: รายการตรวจสอบของวิศวกรอาวุโส**

ถ้าวันหนึ่ง Nimbus ขยายไปให้บริการผู้ใช้ในเม็กซิโกและโคลอมเบีย — สถานการณ์ที่เราจะฝึกในแบบฝึกหัดของบทนี้ — การตัดสินใจ Region ไม่ได้เป็นเรื่องสุ่ม นี่คือวิธีคิด:

**1. ผู้ใช้ของคุณอยู่ที่ไหน?**

เริ่มจากที่นี่ เลือก Region ที่ใกล้กับผู้ใช้ส่วนใหญ่ของคุณมากที่สุด ความหน่วงคือผลกระทบที่ตรงและวัดได้มากที่สุดของการเลือก Region

ระยะทางทางกายภาพระหว่างผู้ใช้กับเซิร์ฟเวอร์สำคัญในแบบที่ประเมินค่าต่ำได้ง่าย การเดินทางไป-กลับ 170ms ไปสิงคโปร์เทียบกับการเดินทางไป-กลับ 20ms ไปออริกอนไม่ใช่ตัวชี้วัดประสิทธิภาพนามธรรม — มันคือความแตกต่างระหว่างหน้าเพจที่รู้สึกทันใจกับหน้าเพจที่รู้สึกอืดอาด บนอุปกรณ์มือถือที่มีความหน่วงจากคลื่นวิทยุเพิ่มเติม โทษของสิงคโปร์ยิ่งทบทวีคูณ สำหรับผู้ใช้ในซานโฮเซ `us-west-2` (ออริกอน) คือ Region ที่ถูกต้องก่อนที่คุณจะพิจารณาปัจจัยอื่นใดด้วยซ้ำ

**2. มีข้อกำหนดด้านการปฏิบัติตามหรือไม่?**

เวิร์กโหลดด้านสุขภาพ การเงิน และรัฐบาลมักมีกฎเรื่องถิ่นที่อยู่ของข้อมูลที่เข้มงวด จงรู้สภาพแวดล้อมด้านกฎระเบียบของคุณก่อนเลือก GDPR กำหนดว่าข้อมูลส่วนบุคคลจากผู้อยู่อาศัยในสหภาพยุโรปต้องเก็บในเขตอำนาจศาลที่มีการคุ้มครองข้อมูลที่เพียงพอ — ไม่ว่าจะเป็นสหภาพยุโรปเองหรือประเทศที่มีคำตัดสินว่าเพียงพอ HIPAA กำหนดให้มีการป้องกันที่มีเอกสารสำหรับข้อมูลสุขภาพของสหรัฐฯ สิ่งเหล่านี้ไม่ใช่ข้อพิจารณาที่เป็นทางเลือกให้กลับมาทบทวนในภายหลัง

ในทางปฏิบัติ: พูดคุยกับทีมกฎหมายของคุณก่อนเลือก Region สำหรับเวิร์กโหลดที่มีกฎระเบียบใด ๆ AWS รักษาเอกสารการปฏิบัติตามข้อกำหนดที่ครอบคลุมสำหรับแต่ละ Region รวมถึงใบรับรองเช่น SOC 2, ISO 27001, PCI DSS และความเหมาะสมกับ HIPAA แต่ใบรับรองบอกคุณว่า AWS ได้ทำอะไร ทีมกฎหมายของคุณบอกคุณว่านั่นเพียงพอสำหรับบริบทกฎระเบียบเฉพาะของคุณหรือไม่

**3. คุณต้องการบริการอะไรบ้าง?**

ไม่ใช่ทุก AWS service จะมีในทุก Region บริการใหม่เปิดตัวใน `us-east-1` ก่อน ถ้าคุณต้องการบริการเฉพาะ ให้ตรวจสอบว่า Region เป้าหมายของคุณรองรับมันหรือไม่

นี่เป็นข้อกังวลที่น้อยกว่าสำหรับบริการในหนังสือเล่มนี้ — บริการหลักทั้งหมดมีให้ใช้อย่างกว้างขวาง — แต่สำคัญสำหรับบริการที่ใหม่กว่า ฮาร์ดแวร์เฉพาะทาง (instance ประเภท GPU บางอย่างมีอยู่เฉพาะใน Region บางแห่ง) และ AWS GovCloud (Region แยกต่างหากที่ออกแบบสำหรับเวิร์กโหลดรัฐบาลสหรัฐฯ ที่มีข้อกำหนดด้านกฎระเบียบเฉพาะ)

**4. ราคาเป็นอย่างไร?**

Region มีราคาต่างกัน `us-east-1` (เวอร์จิเนียเหนือ) มีแนวโน้มถูกที่สุดเพราะขนาดและอายุของมัน อเมริกาใต้แพงกว่าเล็กน้อย ตรวจสอบหน้าราคาของ AWS ก่อนตัดสินใจขั้นสุดท้าย

ส่วนต่างของราคามักเล็ก — ไม่กี่ถึงสิบเปอร์เซ็นต์ระหว่าง Region ยอดนิยม มันแทบไม่เคยเป็นปัจจัยตัดสิน แต่สำหรับเวิร์กโหลดที่ไวต่อต้นทุนซึ่งรัน instance หลายพันตัว แม้แต่ความแตกต่างของราคา 5% ก็ทบต้นกันเมื่อเวลาผ่านไป Tom จะตรวจสอบตัวเลขและนำมาคำนวณ เช่นเดียวกับที่ Tom ตรวจสอบตัวเลขทั้งหมดและนำมาคำนวณ

**5. คุณต้องการ multi-Region หรือไม่?**

สำหรับแอปพลิเคชันส่วนใหญ่ AZ หลายแห่งภายใน Region เดียวเป็นความยืดหยุ่นที่เพียงพอ สำหรับแอปพลิเคชันสำคัญที่แม้แต่การหยุดทำงานระดับภูมิภาคก็ยอมรับไม่ได้ คุณออกแบบสำหรับ multi-Region — แต่นั่นเป็นความมุ่งมั่นทางสถาปัตยกรรมที่สำคัญ อย่าทำมันโดยการเก็งกำไร

"กฎสำหรับเมื่อเราเพิ่ม Region ที่สองคืออะไร?" Leo ถาม

"เมื่อเรามีข้อกำหนดที่มีเอกสารซึ่งบอกว่า 'ต้องยังคงทำงานได้ถ้า AWS Region ทั้งหมดไม่พร้อมใช้งาน'" Priya พูด "ไม่ใช่ 'มันคงจะดี' ข้อกำหนดเฉพาะ พร้อมเหตุผลทางธุรกิจเฉพาะ ที่เราได้ชั่งน้ำหนักกับความซับซ้อนและต้นทุนแล้ว"

"นั่นมีหน้าตาเป็นอย่างไรในทางปฏิบัติ?"

"สัญญาลูกค้าพร้อม SLA ที่กำหนด uptime 99.99% ข้อบังคับด้านกฎระเบียบสำหรับความซ้ำซ้อนทางภูมิศาสตร์ สถานการณ์การสูญเสีย Region ที่เราสามารถวัดเป็นรายได้ได้จริง ไม่ใช่แค่ 'จะเกิดอะไรขึ้นถ้า us-west-2 ล่ม'"

Leo มองสถาปัตยกรรม Nimbus ปัจจุบัน พวกเขายังอยู่บน AZ เดียว

**ข้อจำกัดที่ไม่มีใครพูดถึง**

Region ทรงพลัง แต่พวกมันสร้างความตึงเครียดสำคัญหนึ่งอย่าง

การรันในหลาย Region ยากจริง ๆ

การจำลองข้อมูลระหว่าง Region มีความหน่วง การรักษา Region สองแห่งให้ซิงค์กัน — เพื่อให้ธุรกรรมใน Region A มองเห็นได้ทันทีใน Region B — เป็นหนึ่งในปัญหาที่ยากที่สุดในระบบกระจาย AWS มีเครื่องมือสำหรับมัน แต่มันมีต้นทุนและเพิ่มความซับซ้อนในการดำเนินงาน

แอปพลิเคชันส่วนใหญ่ควรเริ่มด้วย Region เดียว AZ หลายแห่ง และขยายไปยัง multi-Region เมื่อมีข้อกำหนดที่ชัดเจนเท่านั้น: ข้อบังคับด้านกฎระเบียบ SLA ตามสัญญาที่ต้องการการหยุดทำงานระดับภูมิภาคใกล้ศูนย์ หรือฐานผู้ใช้ที่กระจายอยู่ทั่วทวีปอย่างแท้จริง

การจำลองข้อมูลข้าม region เพิ่มต้นทุน — การถ่ายโอนข้อมูลข้าม region เป็นหนึ่งในรายการในบิลที่ถูกประเมินค่าต่ำที่สุดในบิล AWS มันยังเพิ่มความซับซ้อนในการดำเนินงาน: ทุกการเขียนที่ต้องสอดคล้องกันข้าม region จะเพิ่มความหน่วง

ความล้มเหลวส่วนใหญ่ที่ส่งผลต่อแอปพลิเคชันจริงไม่ใช่หายนะข้าม region พวกมันเป็นปัญหาภายใน region เช่น security group ที่กำหนดค่าผิดหรือการ deploy ที่ผิดพลาด สถานการณ์ดราม่า "Region ทั้งหมดล่ม" ขึ้นพาดหัวข่าวเพราะมันหายากพอดี ลงทุนใน multi-AZ ก่อน multi-region เพิ่ม multi-region เมื่อกรณีทางธุรกิจชัดเจน

ใส่ตัวเลขเฉพาะเข้าไป: AWS มีเหตุการณ์ single-region ที่สำคัญจำนวนน้อยในประวัติศาสตร์ของมัน การหยุดทำงานระดับภูมิภาคเต็มรูปแบบนั้นไม่ค่อยเกิดขึ้นจริง เหตุการณ์ระดับ AZ — การหยุดทำงานช่วงสั้นที่ส่งผลต่อศูนย์ข้อมูลแห่งหนึ่งภายใน region — หายากน้อยกว่าและเป็นสิ่งที่การ deploy แบบ Multi-AZ ออกแบบมาเพื่อรองรับพอดี ความถี่ของเหตุการณ์ AZ เมื่อเทียบกับเหตุการณ์ระดับภูมิภาคนั้นสูงกว่าราว ๆ หนึ่งลำดับขนาด การทุ่มความพยายามทางสถาปัตยกรรมไปที่โหมดความล้มเหลวที่พบบ่อยกว่าก่อนเป็นทางเลือกที่มีเหตุผล

สถาปัตยกรรม multi-Region ก่อนเวลาอันควรเป็นหนึ่งในข้อผิดพลาดที่พบบ่อยและแพงที่สุดที่วิศวกรระดับจูเนียร์ทำเมื่อพวกเขาเริ่มรู้สึกมั่นใจ

Tom พยักหน้า "ดังนั้นเราจึงไม่ทำ multi-Region เพียงเพราะเราทำได้"

"ไม่ จนกว่าเราจะต้องการ" Maya พูด "และเราจะรู้เมื่อเราต้องการ"

"เมื่อเอกสารตรวจทานสถาปัตยกรรมของคุณมีข้อกำหนดที่บอกว่า 'ต้องรอดจากการหยุดทำงานระดับภูมิภาค'" Priya พูด "เราคิดถึงเรื่องที่จะเกิดขึ้นถ้า AZ ทั้งหมดล่มก่อนที่เราจะตั้งค่า Multi-AZ ด้วยซ้ำหรือยัง? เราควรแก้ตรงนั้นก่อน จนกว่านั้น: multi-AZ"

## เมื่อ AWS มาหาคุณ: Outposts และ Wavelength

Region และ Availability Zone ครอบคลุมทั่วโลก — แต่ไม่ใช่ทุกปัญหาที่แก้ได้ด้วยการย้ายข้อมูลไป AWS เวิร์กโหลดบางอย่างต้องอยู่ on-premises: ระบบในโรงงานการผลิตที่ต้องการความหน่วงต่ำกว่ามิลลิวินาที แอปพลิเคชันด้านสุขภาพที่มีข้อกำหนดเรื่องถิ่นที่อยู่ของข้อมูล ระบบ point-of-sale ในร้านค้าปลีกที่ไม่มีอินเทอร์เน็ตที่น่าเชื่อถือ สำหรับสิ่งเหล่านี้ AWS ขยายโครงสร้างพื้นฐานของมันไปยังตำแหน่งของลูกค้า

"เดี๋ยวนะ — แล้วถ้าในที่สุดเราทำงานกับระบบโรงพยาบาลล่ะ?" Priya ถาม "ซอฟต์แวร์มอนิเตอร์ผู้ป่วยของพวกเขาทนการเดินทางไป-กลับคลาวด์ไม่ได้จริง ๆ และมันอาจไม่ได้รับอนุญาตทางกฎหมายให้ออกจากอาคาร"

Maya เปิดเอกสาร AWS ขึ้นมา มีสองบริการที่ปรากฏขึ้นเรื่อย ๆ

**AWS Outposts**

แร็คฮาร์ดแวร์ AWS ที่มีการจัดการเต็มรูปแบบซึ่งติดตั้งในศูนย์ข้อมูลของคุณเองหรือสิ่งอำนวยความสะดวก co-location Outposts รันโครงสร้างพื้นฐาน บริการ API และเครื่องมือ AWS เดียวกันกับคลาวด์ AWS — EC2, EBS, RDS, EKS, S3 บน Outposts — แต่อยู่ในอาคารของคุณทางกายภาพ

กรณีการใช้งาน: เวิร์กโหลดการผลิตที่ไวต่อความหน่วง ข้อกำหนดเรื่องถิ่นที่อยู่ของข้อมูลที่ข้อมูลต้องอยู่ในตำแหน่งเฉพาะทางกายภาพ แอปพลิเคชันที่ต้องการ AWS API แต่ทนช่วงที่ขาดการเชื่อมต่อกับคลาวด์สาธารณะไม่ได้

ประเด็นสำคัญ: Outposts ยังคงได้รับการจัดการโดย AWS AWS ติดตั้งมัน patch มัน และมอนิเตอร์มัน คุณเป็นเจ้าของพื้นที่แร็คและพลังงาน API และเครื่องมือเหมือนกับคลาวด์สาธารณะทุกประการ — เทมเพลต CloudFormation เดียวกัน นโยบาย IAM เดียวกัน คำสั่ง CLI เดียวกัน ความแตกต่างในการสอบคือตำแหน่งทางกายภาพ ไม่ใช่โมเดลการดำเนินงาน

**AWS Wavelength**

โครงสร้างพื้นฐาน AWS ที่ deploy อยู่ภายในเครือข่าย 5G ของผู้ให้บริการโทรคมนาคม Wavelength Zone อยู่ที่ขอบของเครือข่าย 5G ใกล้กับผู้ใช้มือถือทางกายภาพ ทำให้ความหน่วงระดับมิลลิวินาทีหลักเดียวเป็นไปได้สำหรับแอปพลิเคชันมือถือ

กรณีการใช้งาน: เกมแบบเรียลไทม์ AR/VR เทเลเมตรีของยานยนต์ไร้คนขับ การประมวลผลวิดีโอสดที่ขอบ 5G

"อันนั้นไม่ใช่สำหรับโรงพยาบาล" Tom พูด "นั่นสำหรับคนที่กำลังสร้างเกมมือถือผู้เล่นหลายคนรุ่นต่อไป"

"หรือเทเลเมตรีของรถยนต์ขับเคลื่อนอัตโนมัติ" Priya พูด "อะไรก็ตามที่อุปกรณ์มือถือต้องคุยกับเซิร์ฟเวอร์และ 50 มิลลิวินาทีนั้นช้าเกินไป"

**ความแตกต่าง:** Outposts นำ AWS มายังศูนย์ข้อมูลของคุณ — อาคารของคุณ แร็คของคุณ พลังงานของคุณ Wavelength นำ AWS มายังขอบเครือข่ายโทรคมนาคม — ตั้งอยู่ร่วมกันทางกายภาพกับโครงสร้างพื้นฐานวิทยุ 5G ใกล้กับผู้ใช้มือถือที่ไม่เคยแตะเครือข่ายส่วนตัวของคุณเลย

**AWS Local Zones**

มีพี่น้องคนที่สามในครอบครัวนี้ — และในการสอบ มันเป็นอันที่ถูกทดสอบบ่อยที่สุดในสามอัน **Local Zone** คือโครงสร้างพื้นฐาน AWS ที่ deploy ในเขตมหานครขนาดใหญ่ที่ไม่มี Region เต็มรูปแบบ — ลอสแอนเจลิส ฮูสตัน ไมอามี ลากอส และอีกหลายสิบแห่ง Local Zone เป็นส่วนขยายของ Region แม่: คุณรัน EC2, EBS และบริการอื่น ๆ ชุดย่อย *ในตัวเขตมหานครเอง* ได้ความหน่วงระดับมิลลิวินาทีหลักเดียวกับผู้ใช้ในเมืองนั้น ในขณะที่ทุกอย่างอื่น (และการจัดการทั้งหมด) อยู่ใน Region แม่

รูปแบบที่ต้องจำ — พี่น้อง "edge compute" สามอัน สามตัวกระตุ้น:

- "ความหน่วงระดับมิลลิวินาทีหลักเดียวกับผู้ใช้ปลายทาง **ในเมือง/เขตมหานครเฉพาะ**" → **Local Zones**
- "ความหน่วงต่ำมากสำหรับ **อุปกรณ์มือถือ 5G**" → **Wavelength**
- "AWS service ที่รัน **ในศูนย์ข้อมูลของเราเอง** / ข้อมูลต้องอยู่ on-premises" → **Outposts**

ไม่มีในสามอันที่เป็นคำตอบสำหรับเว็บแอปพลิเคชันทั่วไป ทั้งหมดปรากฏในการสอบ SAA-C03 เป็นกับดักการจับคู่รูปแบบ: วลีที่กระตุ้นนั้นสำคัญ

## จุดแข็งและข้อจำกัด

**ใช้การออกแบบ multi-region และ multi-AZ เมื่อ**: แอปพลิเคชันของคุณมีผู้ใช้ในหลายภูมิศาสตร์และความหน่วงสำคัญ; SLA ของคุณต้องการความพร้อมใช้งาน 99.99% หรือสูงกว่า; ข้อกำหนดด้านกฎระเบียบบังคับให้ข้อมูลอยู่ใน region เฉพาะ; คุณต้องการการกู้คืนจากภัยพิบัติด้วย RTO ภายในหนึ่งชั่วโมง

**ข้อแลกเปลี่ยนเป็นเรื่องจริง**: การรันในหลาย Region ให้ความซ้ำซ้อนต่อการหยุดทำงานระดับภูมิภาค — แต่ด้วยต้นทุนและความซับซ้อนที่มีนัยสำคัญ

จำคำเตือนเรื่องต้นทุนจากก่อนหน้านี้ในบทนี้: ทุกไบต์ที่เคลื่อนที่ระหว่าง region มีต้นทุน ในการตั้งค่า multi-region แบบ active-active ที่การเขียนต้องสอดคล้องกัน คุณกำลังจ่ายต้นทุนนั้นอยู่ตลอดเวลา

ความซับซ้อนในการดำเนินงานก็ขยายตัวด้วย การดีบักเหตุการณ์ใน region เดียวนั้นยาก การดีบักเหตุการณ์แบบกระจายข้าม region — ที่คำขอเดียวกันแตะโครงสร้างพื้นฐานในสองทวีป — เป็นความยากคนละประเภทโดยสิ้นเชิง

**ความก้าวหน้าที่ถูกต้องสำหรับแอปพลิเคชันส่วนใหญ่**: เริ่มด้วย Region เดียวและ AZ หลายแห่ง นั่นให้ความยืดหยุ่นต่อความล้มเหลวที่เกิดขึ้นจริง — การหยุดทำงานระดับ AZ ความล้มเหลวของฮาร์ดแวร์ เหตุการณ์ไฟฟ้า — ด้วยเศษเสี้ยวของความซับซ้อนของสถาปัตยกรรม multi-region เพิ่ม multi-region เมื่อข้อกำหนดที่เฉพาะเจาะจงและมีเอกสารทำให้มันจำเป็น ไม่ใช่ก่อนหน้านั้น

รูปแบบที่พบบ่อยสำหรับทีมที่กระโดดไป multi-region เร็วเกินไป: ความซับซ้อนของการจัดการสอง region แนะนำโหมดความล้มเหลวของมันเอง — บั๊กการซิงค์ข้อมูล สถานการณ์ split-brain การ deploy ที่ไม่สอดคล้องกัน สถาปัตยกรรมความยืดหยุ่นที่ออกแบบมาเพื่อป้องกันความล้มเหลวบางครั้งแนะนำหมวดหมู่ความล้มเหลวใหม่ที่ไม่น่าจะมีอยู่ในการออกแบบที่เรียบง่ายกว่า

Priya มีเอกสารที่เธอเรียกว่า "งบประมาณความซับซ้อน" แนวคิด: ทุกการตัดสินใจทางสถาปัตยกรรมที่เพิ่มความซับซ้อนในการดำเนินงานมีต้นทุน และองค์กรมีความสามารถจำกัดในการจัดการความซับซ้อนนั้น การใช้งบประมาณความซับซ้อนไปกับสถาปัตยกรรม multi-region ก่อนที่คุณจะเชี่ยวชาญความน่าเชื่อถือของ single-region เป็นการลงทุนที่ไม่ดี ความซับซ้อนควรไปที่โหมดความล้มเหลวที่คุณเผชิญจริง ไม่ใช่อันที่สร้างเรื่องราวการกู้คืนจากภัยพิบัติที่ดี

## สรุป

อุบัติเหตุสิงคโปร์ของ Leo กลายเป็นบทเรียนที่มีประโยชน์ — ไม่ใช่เพราะมันสร้างความเสียหายถาวร แต่เพราะมันบังคับให้ทีมเข้าใจบางสิ่งที่มักถูกข้าม: ที่ที่โครงสร้างพื้นฐานของคุณรันไม่ใช่การตัดสินใจเรื่องผิวเผิน ฟิสิกส์ต่อรองไม่ได้ ความหน่วงพื้นฐานหนึ่งร้อยเจ็ดสิบมิลลิวินาทีต่อการเดินทางไป-กลับคือความแตกต่างระหว่างผลิตภัณฑ์ที่เร็วกับผลิตภัณฑ์ที่อืดอาด และกฎการปฏิบัติตามเกี่ยวกับว่าข้อมูลอยู่ที่ไหนไม่สนใจว่าคุณย้ายได้เร็วแค่ไหน

- AWS จัดระเบียบโครงสร้างพื้นฐานทั่วโลกเป็น **Regions**, **Availability Zones** และ **Edge Locations**
- **Region** คือคลัสเตอร์ศูนย์ข้อมูลทางภูมิศาสตร์ แต่ละ Region แยกออกจากกัน — ข้อมูลอยู่ใน Region เว้นแต่คุณจะย้ายมันอย่างชัดเจน
- **Availability Zone** คือศูนย์ข้อมูลที่แยกกันทางกายภาพภายใน Region เชื่อมต่อด้วยเครือข่ายความหน่วงต่ำ การ deploy ข้าม AZ หลายแห่งเป็นวิธีมาตรฐานในการรอดจากความล้มเหลวในท้องถิ่น
- เลือก Region ของคุณตามตำแหน่งผู้ใช้ ข้อกำหนดด้านการปฏิบัติตาม ความพร้อมใช้งานของบริการ และราคา — ตามลำดับนั้น
- Multi-AZ คือเส้นฐานความยืดหยุ่นมาตรฐาน Multi-Region สำหรับเวิร์กโหลดสำคัญที่มีข้อกำหนดเฉพาะและมีเอกสาร — ไม่ใช่จุดเริ่มต้นโดยปริยาย

## เคล็ดลับการสอบ

*SAA-C03 Domain 1 — Task 1.1 / Domain 2 — Task 2.2*

- **Region แยกออกจากกันโดยค่าเริ่มต้น** ข้อมูลไม่จำลองระหว่าง Region เว้นแต่คุณจะกำหนดค่ามัน
  สิ่งนี้สำคัญสำหรับสถานการณ์อธิปไตยข้อมูลและการปฏิบัติตามข้อกำหนด
- **AZ คือหน่วยความยืดหยุ่นสำหรับคำถามส่วนใหญ่** เมื่อการสอบถามถึงวิธีรอดจาก
  ความล้มเหลวของศูนย์ข้อมูล คำตอบเกี่ยวข้องกับ AZ หลายแห่งภายใน Region เดียว
- **Multi-Region สำหรับความยืดหยุ่นต่อการหยุดทำงานระดับภูมิภาค** ถ้าสถานการณ์บอกว่า "ต้องยังคง
  ทำงานได้แม้ AWS Region ทั้งหมดล้มเหลว" คำตอบเกี่ยวข้องกับสถาปัตยกรรม multi-Region
- **Edge Location ≠ AZ** Edge Location แคชเนื้อหา — พวกมันรันเซิร์ฟเวอร์แอปพลิเคชัน
  ของคุณไม่ได้ อย่าสับสนพวกมันกับศูนย์ข้อมูล
- การสอบทดสอบความสัมพันธ์ระหว่างการปฏิบัติตามข้อกำหนดและการเลือก Region อยู่บ่อยครั้ง
  ถ้าสถานการณ์กล่าวถึงข้อกำหนดเรื่องถิ่นที่อยู่ของข้อมูล การเลือก Region เป็นส่วนหนึ่งของคำตอบ
- สถานการณ์ **GDPR และถิ่นที่อยู่ของข้อมูล** ในการสอบมักชี้ไปที่การเก็บข้อมูลไว้ภายใน Region เฉพาะและการทำให้แน่ใจว่าการจำลองข้าม region ถูกปิดใช้งานหรือควบคุม
- **Outposts กับ Wavelength กับ Local Zones:** Outposts = แร็ค AWS ในศูนย์ข้อมูลของคุณ (on-premises, ถิ่นที่อยู่ของข้อมูล, ความหน่วงในเครื่อง) Wavelength = AWS ในขอบเครือข่าย 5G (ผู้ใช้มือถือ, ความหน่วงต่ำมาก) Local Zones = คอมพิวต์ AWS ในเขตมหานครที่ไม่มี Region เต็มรูปแบบ ตัวกระตุ้นการสอบ: "รัน AWS ในสิ่งอำนวยความสะดวกของคุณเอง" → Outposts "ความหน่วงต่ำมากสำหรับผู้ใช้มือถือ 5G" → Wavelength "ความหน่วงระดับมิลลิวินาทีหลักเดียวกับผู้ใช้ในเมืองเฉพาะ" → Local Zones

   ข้าม Region  
D) Deploy ใน `us-west-2` (ออริกอน) ข้าม Availability Zone หลายแห่ง

**คำใบ้ 1**: นโยบายหมายความว่าข้อมูลต้องอยู่ใน Region เดียว ตัวเลือกใดย้ายข้อมูลไปยัง Region อื่น?

**คำใบ้ 2**: ในบรรดาตัวเลือกที่เก็บข้อมูลใน `us-west-2` อันใดให้ความยืดหยุ่นมากที่สุด?

**คำใบ้ 3**: AZ หลายแห่งภายใน Region เดียวให้ความยืดหยุ่นโดยไม่ข้ามขอบเขต Region

**คำตอบ**: D

**คำอธิบาย**: `us-west-2` เก็บข้อมูลทั้งหมดไว้ใน Region เดียว ตอบสนองข้อกำหนดของนโยบาย การ deploy ข้าม AZ หลายแห่งภายใน Region นั้นป้องกันความล้มเหลวของศูนย์ข้อมูลโดยไม่ย้ายข้อมูลไปยัง Region อื่น นี่คือความสมดุลที่ถูกต้องของการปฏิบัติตามข้อกำหนดและความยืดหยุ่น

**ทำไมไม่ใช่ A?** ตัวเลือก A deploy ใน `us-east-1` ห่างจากผู้ใช้ชายฝั่งตะวันตก — และ CloudFront จะแคชเนื้อหาที่อยู่ติดกับข้อมูลผู้ป่วยที่ Edge Location นอก Region ที่เลือก ละเมิดนโยบายถิ่นที่อยู่

**ทำไมไม่ใช่ B?** AZ เดียวไม่มีความยืดหยุ่น ถ้า AZ นั้นประสบการหยุดทำงาน แอปพลิเคชันก็ล้มเหลวอย่างสมบูรณ์

**ทำไมไม่ใช่ C?** การจำลองไปยัง `us-east-1` ย้ายข้อมูลผู้ป่วยไปยังชายฝั่งตะวันออก ละเมิดข้อกำหนด Region เดียวโดยตรง
