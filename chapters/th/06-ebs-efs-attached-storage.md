**EC2 Instance เก็บข้อมูลอย่างไร**

เมื่อ EC2 instance รัน ระบบปฏิบัติการของมันอยู่ที่ไหนสักแห่งบนดิสก์ ดิสก์นั้นเรียกว่า **root volume** โดยค่าเริ่มต้น นี่คือ **EBS volume** — แม้เมื่อคุณไม่ได้คิดถึงมัน

แต่ยังมีอย่างอื่น: EC2 instance ยังมีพื้นที่จัดเก็บ **instance store** ด้วย

instance store คือพื้นที่จัดเก็บชั่วคราวที่แนบทางกายภาพกับฮาร์ดแวร์ที่อยู่เบื้องล่างซึ่งรันเครื่องเสมือนของคุณ มันเร็วอย่างยิ่ง — เร็วกว่าตัวเลือกพื้นที่จัดเก็บเกือบทุกตัวใน AWS แต่มันมาพร้อมเงื่อนไข

instance store เป็น **แบบชั่วคราว (ephemeral)**

เมื่อ instance หยุดหรือถูกยุติ ข้อมูล instance store ก็หายไป ถาวร กู้คืนไม่ได้ AWS ไม่ได้เตือนคุณเสียงดังนักเกี่ยวกับเรื่องนี้ ซึ่งเป็นวิธีที่ทีมค้นพบมัน: โดยการเสียข้อมูล

instance store เหมาะสำหรับแคช ไฟล์ประมวลผลชั่วคราว และพื้นที่ทำงานชั่วคราว ไม่เคยสำหรับข้อมูลที่คุณใส่ใจ

**EBS: ดิสก์ถาวร**

ลองนึกภาพฮาร์ดไดรฟ์ภายนอกที่คุณเสียบเข้า EC2 instance ของคุณได้ — ตัวที่ไม่หายไปเมื่อคุณถอดมันออก และที่คุณย้ายไปยังเครื่องอื่นได้ถ้าต้องการ AWS เรียกมันว่า **EBS**: Elastic Block Store

EBS คือ block storage แบบถาวรสำหรับ EC2 instance

block storage หมายความว่ามันทำงานเหมือนฮาร์ดไดรฟ์จริง: ระบบปฏิบัติการของคุณสร้างระบบไฟล์บนมันได้ อ่านและเขียนไบต์ตามอำเภอใจที่ตำแหน่งตามอำเภอใจ รันฐานข้อมูลบนมัน และปฏิบัติต่อมันเหมือนดิสก์ที่แนบอยู่ทุกประการ

คุณสมบัติหลัก:

**ถาวร** ไม่เหมือน instance store EBS volume รอดผ่านการหยุด เริ่ม และแม้แต่การยุติ instance (ขึ้นอยู่กับการกำหนดค่า) ข้อมูลอยู่บน volume แม้เมื่อไม่มี instance ใช้มัน

มีรายละเอียดการกำหนดค่าตรงนี้: เมื่อคุณสร้าง EC2 instance root volume มีการตั้งค่าที่เรียกว่า "Delete on Termination" โดยค่าเริ่มต้น มันถูกตั้งเป็น true — root volume ถูกลบเมื่อ instance ถูกยุติ สำหรับ volume ข้อมูลเพิ่มเติมที่คุณแนบ ค่าเริ่มต้นคือ false — พวกมันคงอยู่หลังจาก instance ถูกยุติ คุณเปลี่ยนทั้งสองการตั้งค่าได้ ถ้าคุณต้องการให้ root volume รอดจากการยุติ instance (สำหรับการวิเคราะห์ทางนิติเวชหรือการกู้คืนข้อมูล) ให้ปิดใช้งาน "Delete on Termination" ถ้าคุณต้องการให้ volume ข้อมูลถูกทำความสะอาดโดยอัตโนมัติ ให้เปิดใช้งานมัน

**แนบและถอดได้** EBS volume สามารถถอดจาก instance หนึ่งและแนบกับอีกตัวได้ ถ้าคุณต้องการย้ายข้อมูลหรือกู้คืนจาก instance ที่ล้มเหลว คุณถอด volume และแนบมันใหม่ที่อื่นได้

เวิร์กโฟลว์ถอด-แล้ว-แนบใหม่ช้ากว่าการกู้คืน snapshot แต่รักษาสถานะที่แน่นอนของ volume — การเขียนที่ยังไม่ได้ commit ทั้งหมด ข้อมูลที่แคชทั้งหมด สถานะระบบไฟล์ที่แน่นอน สิ่งนี้ทำให้มันมีประโยชน์สำหรับการวิเคราะห์ทางนิติเวช (แนบ volume กับ instance วิเคราะห์โดยไม่บูตระบบเดิม) และสำหรับการย้ายข้อมูล (ย้าย volume ฐานข้อมูลไปยัง instance ที่ใหญ่กว่าโดยไม่ต้องทำ snapshot)

**การแนบเดี่ยว (ส่วนใหญ่)** โดยค่าเริ่มต้น EBS volume แนบกับ EC2 instance หนึ่งตัวในแต่ละครั้งเท่านั้น instance เดียวมี EBS volume หลายอันได้ แต่ EBS volume เดียว mount โดย instance หลายตัวพร้อมกันไม่ได้ (ยกเว้นหนึ่งอย่าง: EBS Multi-Attach ซึ่งมีกรณีการใช้งานจำกัดและข้อจำกัดสำคัญ)

EBS Multi-Attach อนุญาตให้ volume io1/io2 (Provisioned IOPS) แนบกับ instance หลายตัวพร้อมกันใน AZ เดียวกัน สิ่งนี้ฟังดูเหมือนแก้ปัญหา "พื้นที่จัดเก็บที่แชร์" แต่มันมาพร้อมข้อจำกัดร้ายแรง: แอปพลิเคชันบน instance ที่แนบต้องประสานการเข้าถึงพร้อมกันได้ — semantics ระบบไฟล์ที่แชร์ (การจัดการล็อก การเรียงลำดับการเขียน) ไม่ได้จัดให้โดย EBS ในทางปฏิบัติ EBS Multi-Attach ใช้สำหรับแอปพลิเคชันฐานข้อมูลแบบคลัสเตอร์ที่จัดการการประสานเอง สำหรับการเข้าถึงไฟล์ที่แชร์ทั่วไป EFS เรียบง่ายกว่าและเหมาะสมกว่า

การเปรียบเทียบ EBS: ฮาร์ดไดรฟ์ภายนอกที่เสียบเข้าแล็ปท็อปเครื่องเดียว แล็ปท็อป (EC2 instance) อ่านและเขียนลงมันได้ เมื่อคุณเสร็จ คุณถอดมันออกและเสียบเข้าแล็ปท็อปเครื่องอื่นได้

**ประเภท EBS Volume**

EBS volume ไม่เหมือนกันทั้งหมด AWS เสนอหลายประเภทด้วยโปรไฟล์ประสิทธิภาพและต้นทุนที่ต่างกัน

**gp3 (General Purpose SSD)**: ตัวเลือกเริ่มต้นสำหรับเวิร์กโหลดส่วนใหญ่ ความสมดุลที่ดีของประสิทธิภาพและราคา เหมาะสำหรับ boot volume ฐานข้อมูลขนาดเล็ก และสภาพแวดล้อม development

ก่อนที่ gp3 จะกลายเป็นค่าเริ่มต้น มี **gp2** — และคุณยังเจอมันในของจริง gp2 volume ผูกประสิทธิภาพ IOPS ไว้กับขนาด volume โดยตรง: คุณได้ 3 IOPS ต่อกิกะไบต์ สูงสุด 16,000 IOPS (ซึ่งต้องการ volume ขนาด 5,334 GB) ทรูพุตถูกจำกัดที่ 250 MB/s การผูกนี้หมายความว่าบน gp2 วิธีเดียวที่จะได้ IOPS มากขึ้นคือทำให้ volume ใหญ่ขึ้น — แม้คุณไม่ต้องการพื้นที่พิเศษ gp3 ทำลายการพึ่งพานั้น: มันเริ่มที่ 3,000 IOPS และ 125 MB/s ไม่ว่าขนาดเท่าไหร่ และให้คุณกำหนดค่า IOPS และทรูพุตอย่างอิสระ ด้วยต้นทุนที่ต่ำกว่า AWS แนะนำ gp3 สำหรับ volume ใหม่ แต่เนื่องจากเวิร์กโหลดที่มีอยู่หลายอันยังรันบน gp2 คุณต้องรู้ทั้งสองอย่าง

**io2 (Provisioned IOPS SSD)**: ตัวเลือกประสิทธิภาพสูงสำหรับเวิร์กโหลดที่ใช้ I/O หนัก คุณระบุว่าต้องการการดำเนินการ I/O ต่อวินาที (IOPS) กี่ครั้ง และ AWS รับประกันประสิทธิภาพนั้น เหมาะสำหรับฐานข้อมูล production ขนาดใหญ่

**st1 (Throughput Optimized HDD)**: พื้นที่จัดเก็บแม่เหล็กที่ปรับเพื่อการอ่านและเขียนแบบลำดับขนาดใหญ่ ต้นทุนต่ำกว่า SSD แต่ช้ากว่าสำหรับ I/O แบบสุ่ม ดีสำหรับ data warehousing และการประมวลผลบันทึก

**sc1 (Cold HDD)**: ตัวเลือก EBS ที่ถูกที่สุด สำหรับข้อมูลที่เข้าถึงไม่บ่อย ไม่เหมาะสำหรับอะไรที่ไวต่อเวลา

"io2 แพงกว่า gp3 แค่ไหน?" Tom ถาม พลางเงยหน้าขึ้นจากสมุดบันทึกของเขา

Leo เปิดหน้าราคา io2 แพงกว่า gp3 ราว 50–60% ต่อ GB บวกค่าใช้จ่ายแยกต่างหากต่อ IOPS ที่จัดสรร — และสำหรับ volume ประสิทธิภาพสูง ค่าใช้จ่ายต่อ IOPS เหล่านั้นคือสิ่งที่ครอบงำบิล Tom สังเกตช่องว่าง "ดังนั้นเราใช้ gp3 จนกว่าฐานข้อมูลจะต้องการการรับประกันประสิทธิภาพจริง ๆ"

การสอบไม่ต้องการให้คุณท่องจำทุกประเภท แต่มันทดสอบความสามารถของคุณในการจับคู่ข้อกำหนดกับประเภทที่ถูกต้อง: ข้อกำหนด IOPS → io2 เวิร์กโหลดแบบลำดับที่ไวต่อต้นทุน → st1 เว็บแอปพลิเคชันทั่วไป → gp3

**IOPS กับ Throughput: ทำไมความแตกต่างจึงสำคัญ**

Tom กลับมาที่คำถามเรื่อง EBS volume ในวันอังคารถัดไป หลังจากตรวจสอบ CloudWatch

"ผมเห็นสองเมตริกบนแดชบอร์ด EBS" เขาพูด "IOPS และ throughput พวกมันเป็นคนละเรื่องกันเหรอ?"

ใช่

**IOPS** (Input/Output Operations Per Second) วัดว่าดิสก์จัดการการอ่านหรือเขียนได้กี่ครั้งต่อวินาที แต่ละการดำเนินการโดยทั่วไปเล็ก — 4KB ถึง 256KB IOPS สูงสำคัญสำหรับฐานข้อมูลที่ทำการอ่านและเขียนแบบสุ่มเล็ก ๆ หลายครั้ง: การดึงแถวแต่ละแถว การอัปเดตบันทึก การจัดการคำสืบค้นพร้อมกัน

**Throughput** (วัดเป็น MB/s) วัดว่าข้อมูลเคลื่อนที่เท่าไหร่ต่อวินาที throughput สูงสำคัญสำหรับเวิร์กโหลดแบบลำดับ: การอ่านไฟล์บันทึกขนาดใหญ่ การวิเคราะห์แบบสตรีม การโหลดชุดข้อมูลขนาดใหญ่

ฐานข้อมูลโดยทั่วไปต้องการ IOPS สูงและ throughput ต่ำถึงปานกลาง data warehouse ที่สแกนตารางขนาดใหญ่ต้องการ throughput สูงและอยู่กับ IOPS ปานกลางได้

Tom เฝ้าดูเมตริก CloudWatch ของฐานข้อมูล Nimbus IOPS พุ่งขึ้นในช่วงเร่งด่วนมื้อค่ำ — การอ่านแบบสุ่มสั้น ๆ ขณะที่แอปพลิเคชันดึงรายการเมนูและข้อมูลออร์เดอร์ throughput ต่ำ รูปแบบตรงกับเวิร์กโหลดฐานข้อมูลที่ต้องการ IOPS ที่ดีกว่า ไม่ใช่ throughput ที่ดีกว่า

"ดังนั้นถ้าฐานข้อมูลช้า" Tom พูด "เราตรวจสอบว่ามันผูกกับ IOPS หรือ throughput ก่อนที่เราจะอัปเกรด volume?"

"ถูกต้อง" Priya พูด "การอัปเกรดจาก gp3 ไป io2 เพิ่ม IOPS โดยมีค่าใช้จ่าย ถ้าปัญหาคือ throughput การอัปเกรดนั้นจะไม่ช่วย ตรวจสอบเมตริกก่อน"

นี่คือวิธีที่คุณหลีกเลี่ยงการอัปเกรดพื้นที่จัดเก็บที่แพงซึ่งแก้ปัญหาที่ผิดพอดี

**EBS Snapshots: ข้อมูลสำรอง**

นี่คือสิ่งที่ช่วยบริษัทไว้เป็นประจำ

**EBS snapshot** คือข้อมูลสำรอง ณ จุดเวลาหนึ่งของ EBS volume เก็บใน S3 (แม้ว่าคุณเข้าถึงมันผ่านอินเทอร์เฟซ EBS ไม่ใช่ผ่าน S3 โดยตรง) snapshot เป็นแบบเพิ่มทีละส่วน: snapshot แรกจับ volume ทั้งหมด snapshot ที่ตามมาเก็บเฉพาะสิ่งที่เปลี่ยนไปตั้งแต่ครั้งก่อน

คุณสร้าง EBS volume ใหม่จาก snapshot ได้ — กู้คืนไปยังจุดเวลาก่อนการเสียหายของฐานข้อมูล การ deploy ที่แย่ หรือการลบโดยไม่ตั้งใจ

คุณควรทำ snapshot ให้เป็นอัตโนมัติ AWS มี **Amazon Data Lifecycle Manager** เพื่อจุดประสงค์นี้: กำหนด policy (ทำ snapshot ทุก 6 ชั่วโมง เก็บ 7 วันล่าสุด) และมันรันโดยอัตโนมัติ

**EFS: ตู้เอกสารที่แชร์กัน**

EBS คือดิสก์ที่แนบกับ instance หนึ่งตัว แล้วถ้า instance หลายตัวต้องเข้าถึงไฟล์เดียวกันพร้อมกันล่ะ?

สิ่งที่คุณต้องการคืออะไรบางอย่างเหมือนตู้เอกสารที่อยู่ตรงกลางออฟฟิศ — ใครก็เดินมาได้ ดึงไฟล์ออก ใส่กลับ และคนถัดไปเห็นการเปลี่ยนแปลงทันที หลายคน พร้อมกัน เข้าถึงพื้นที่จัดเก็บเดียวกัน

AWS เรียกมันว่า **EFS**: Elastic File System

EFS คือระบบไฟล์เครือข่ายที่มีการจัดการ EC2 instance หลายตัว mount ระบบไฟล์ EFS เดียวกันในเวลาเดียวกันและอ่าน/เขียนไปยังไฟล์ที่แชร์ได้ นี่คือความสามารถหลักที่ EBS ไม่ให้

พูดง่าย ๆ:

EBS คือฮาร์ดไดรฟ์ภายนอกที่เสียบเข้าแล็ปท็อปเครื่องเดียว มีเพียงแล็ปท็อปนั้นที่ใช้มันได้ในแต่ละครั้ง

EFS คือตู้เอกสารที่อยู่ตรงกลางออฟฟิศ สมาชิกทีมคนใดก็เดินมาได้ เปิดลิ้นชัก อ่านไฟล์ ใส่บางอย่างกลับ

**คุณต้องการ EFS เมื่อไหร่?**

- เมื่อ EC2 instance หลายตัวต้องแชร์ไฟล์ — ระบบจัดการเนื้อหา ไฟล์การกำหนดค่าที่แชร์
  ไลบรารีสื่อที่แชร์
- เมื่อคุณมีแอปพลิเคชันที่ขยายแนวนอนซึ่งทุก instance ต้องเข้าถึง
  ข้อมูลเดียวกัน
- เมื่อคุณต้องการระบบไฟล์ถาวรที่รอดจากความล้มเหลวของ instance

EFS ถูกเข้าถึงผ่านเครือข่ายโดยใช้โปรโตคอล NFS (โดยเฉพาะ NFSv4) EC2 instance ใด ๆ ที่มีการเชื่อมต่อเครือข่ายไปยัง EFS mount target สามารถ mount มันได้ — รวมถึง instance ใน AZ ต่างกันภายใน Region เดียวกัน คุณกำหนดค่า mount target ในแต่ละ AZ และ instance เชื่อมต่อกับ mount target ที่ใกล้ที่สุดเพื่อประสิทธิภาพที่ดีที่สุด

ผลในทางปฏิบัติ: EFS ทำงานข้าม AZ ได้ทันที ถ้าคุณมีเว็บเซิร์ฟเวอร์ใน `us-west-2a` และ `us-west-2b` ที่ทั้งคู่ mount ระบบไฟล์ EFS เดียวกัน ไฟล์ที่เขียนโดยเซิร์ฟเวอร์ใน `2a` มองเห็นได้ทันทีสำหรับเซิร์ฟเวอร์ใน `2b` นี่คือพฤติกรรมระบบไฟล์ที่แชร์ที่ EBS ให้ไม่ได้

**EFS Performance Modes**

EFS มีโหมด throughput สองโหมดที่สำคัญสำหรับการกำหนดขนาด:

**Elastic Throughput** (ค่าเริ่มต้นสำหรับระบบไฟล์ใหม่ส่วนใหญ่): EFS ปรับขนาด throughput ขึ้นและลงโดยอัตโนมัติตามการใช้งานจริง คุณไม่ได้จัดสรรระดับ throughput คุณจ่ายตามที่คุณใช้ นี่คือโหมดที่ถูกต้องสำหรับเวิร์กโหลดผันแปรที่ความต้องการ throughput ผันผวน — เช่น Nimbus ที่ทราฟฟิกเช้าวันจันทร์ต่างจากเย็นวันศุกร์

**Provisioned Throughput**: คุณระบุระดับ throughput ไม่ว่าข้อมูลที่เก็บจะเป็นเท่าไหร่ มีประโยชน์เมื่อเวิร์กโหลดของคุณต้องการ throughput สูงอย่างสม่ำเสมอที่เกินกว่าที่ปริมาณข้อมูลที่เก็บจะให้ในโหมด Elastic ถ้าคุณรันระบบ build ที่อ่านหลายสิบกิกะไบต์ต่อนาทีไม่ว่าจะเก็บไว้เท่าไหร่ Provisioned Throughput เหมาะสม

ยังมีโหมดที่สาม **Bursting Throughput** ซึ่งเป็นพฤติกรรม EFS ดั้งเดิมและยังเป็นค่าเริ่มต้นสำหรับระบบไฟล์ที่สร้างก่อน Elastic จะพร้อมใช้งาน ในโหมด Bursting throughput ปรับขนาดตามจำนวนข้อมูลที่คุณเก็บ: คุณได้เส้นฐาน 50 KB/s ต่อ GB บวกเครดิต burst ที่สะสมเมื่อคุณอยู่ใต้เส้นฐานและใช้ได้เมื่อคุณต้องการ throughput ที่สูงกว่า (สูงสุด 100 MB/s สำหรับระบบไฟล์ที่เล็กกว่า หรือสูงสุดเป็นทวีคูณของเส้นฐานสำหรับอันที่ใหญ่กว่า) มันเป็นทางเลือกที่ถูกต้องสำหรับเวิร์กโหลดที่มีรูปแบบการเข้าถึงที่คาดเดาไม่ได้หรือพุ่งกระชากซึ่งระบบไฟล์ใหญ่พอที่จะได้เครดิต burst ที่มีความหมาย ถ้าระบบไฟล์ของคุณเล็กและรูปแบบการเข้าถึงของคุณพุ่งกระชาก คุณก็เผาผลาญเครดิตได้เร็ว — เฝ้าดูเมตริก `BurstCreditBalance` ของ CloudWatch เพื่อรู้ว่าคุณอยู่ตรงไหน

"ขึ้นอยู่กับรูปแบบการใช้งาน" Leo พูด "ด้วย Elastic คุณจ่ายค่า throughput ที่คุณใช้จริง ด้วย Provisioned คุณจ่ายค่า throughput ที่คุณระบุแม้ว่าคุณจะไม่ได้ใช้มัน"

"มักจะ" Priya พูด "ตรวจสอบรูปแบบ throughput จริงของคุณใน CloudWatch ก่อนตัดสินใจ"

EFS ยังมี performance mode สองโหมด: **General Purpose** (ความหน่วงต่ำ เหมาะสำหรับเวิร์กโหลดส่วนใหญ่ ค่าเริ่มต้น) และ **Max I/O** (throughput สูงกว่าสำหรับเวิร์กโหลดที่ขนานสูง โดยแลกกับความหน่วงที่สูงขึ้นเล็กน้อย) General Purpose จัดการกรณีการใช้งานส่วนใหญ่ Max I/O ออกแบบสำหรับแอปพลิเคชันที่ต้องทำการดำเนินการระบบไฟล์พร้อมกันหลายพันครั้ง — ไปป์ไลน์การประมวลผลสื่อขนาดใหญ่ เวิร์กโฟลว์คอมพิวเตอร์ทางวิทยาศาสตร์ที่มีตัวอ่านขนานหลายตัว

**EFS กับ S3:** EFS คือระบบไฟล์ (โฟลเดอร์ ไฟล์ สิทธิ์ การล็อก) S3 คือ object storage (อัปโหลด ดาวน์โหลด ไม่มี semantics ระบบไฟล์) EFS แพงกว่า S3 มาก — ราว ๆ $0.30 ต่อ GB ต่อเดือนสำหรับ EFS Standard เทียบกับ $0.023 ต่อ GB ต่อเดือนสำหรับ S3 Standard ใช้ S3 สำหรับไฟล์ที่ถูกเก็บและดึงทั้งก้อน ใช้ EFS สำหรับไฟล์ที่แอปพลิเคชันอ่านและเขียนอย่างแข็งขันผ่านการดำเนินการระบบไฟล์มาตรฐาน

**ถ้า EBS ก็ Instance เดียว แต่ถ้า EFS ก็ได้หลายตัว**

การตัดสินใจ EBS/EFS ลงมาที่คำถามเดียว: instance กี่ตัวต้องเข้าถึงพื้นที่จัดเก็บนี้ในเวลาเดียวกัน?

ถ้าคุณสร้างแอปพลิเคชันที่ขยายแนวนอนบน EBS แต่ละ instance มีดิสก์ของตัวเอง — แต่เมื่อผู้ใช้อัปโหลดไฟล์ไปยัง instance A instance B มองไม่เห็นมัน นั่นโอเคสำหรับฐานข้อมูล (แต่ละ DB มีดิสก์ของตัวเอง) แต่พังสำหรับเนื้อหาที่แชร์ ถ้าคุณต้องการการเข้าถึงที่แชร์ EFS คือคำตอบ — แต่ EFS มีต้นทุนต่อ GB มากกว่า S3 และมีความหน่วงสูงกว่า EBS สำหรับ I/O แบบสุ่ม ทางเลือกที่ถูกต้องขึ้นอยู่กับว่าแอปพลิเคชันของคุณทำอะไรกับข้อมูลทั้งหมด

**การเลือกพื้นที่จัดเก็บที่ถูกต้อง**

ถึงตอนนี้คุณได้เห็นพื้นที่จัดเก็บสามประเภทใน AWS มาทำให้การตัดสินใจชัดเจน

| ความต้องการ                                | ประเภทพื้นที่จัดเก็บ |
|--------------------------------------------|---------------------|
| ฐานข้อมูลต้องการดิสก์ถาวร เร็ว              | EBS (gp3 หรือ io2)  |
| เซิร์ฟเวอร์หลายตัวต้องการไฟล์ที่แชร์         | EFS                 |
| ไฟล์ ข้อมูลสำรอง รูปภาพ object ขนาดใหญ่      | S3                  |
| พื้นที่ทำงานชั่วคราวสำหรับการคำนวณ          | Instance Store      |
| คลังระยะยาวด้วยต้นทุนต่ำสุด                  | S3 Glacier          |

คุณอาจสงสัย: ถ้า EFS ให้ instance หลายตัวแชร์ไฟล์ ทำไมไม่ใช้มันสำหรับทุกอย่าง? เพราะ EFS มีต้นทุนต่อ GB มากกว่า S3 อย่างมีนัยสำคัญ และมีความหน่วงสูงกว่า EBS ในเครื่องสำหรับ I/O แบบสุ่ม มันเป็นเครื่องมือที่ถูกต้องสำหรับการเข้าถึงระบบไฟล์ที่แชร์ — ไม่ใช่สำหรับการจัดเก็บไฟล์ทั่วไปหรือการจัดเก็บฐานข้อมูล

การได้การตัดสินใจนี้ถูกต้องสำคัญ การใช้ S3 ที่ที่คุณต้องการ EFS เพิ่มความซับซ้อนในการดำเนินงาน การใช้ EBS ที่ที่คุณต้องการ EFS ทำให้เกิดความล้มเหลวเมื่อคุณขยาย การใช้ instance store ที่ที่คุณต้องการความถาวรทำให้ข้อมูลสูญหาย

Priya พิมพ์ตารางนี้และติดมันไว้บนผนัง

"ทุกครั้งที่เราเพิ่มข้อกำหนดพื้นที่จัดเก็บ" เธอพูด "เราเริ่มที่นี่"

มาเดินผ่านสถานการณ์จริงไม่กี่อย่างเพื่อทำให้การตัดสินใจเป็นรูปธรรม:

**สถานการณ์ A**: งานฝึก machine learning รันบน GPU EC2 instance และต้องอ่านชุดข้อมูล 200GB งานรันวันละครั้งและใช้เวลาสองชั่วโมง ชุดข้อมูลถูกแชร์โดยทีมวิจัยหลายทีม

การตัดสินใจ: S3 ชุดข้อมูลใหญ่ อ่านครั้งเดียวต่องาน และแชร์ S3 ถูก ทนทาน และเข้าถึงได้จาก EC2 instance ใด ๆ หรือบัญชีของทีมใด ๆ GPU instance อ่านมันผ่าน S3 API ไม่จำเป็นต้องมีระบบไฟล์ที่นี่

**สถานการณ์ B**: เว็บไซต์ WordPress รันบน EC2 instance สี่ตัวหลัง load balancer WordPress เก็บไฟล์ปลั๊กอิน ไฟล์ธีม และการอัปโหลดของผู้ใช้ในไดเรกทอรีบนเซิร์ฟเวอร์ ทั้งสี่ instance ต้องอ่านและเขียนไฟล์เดียวกัน

การตัดสินใจ: EFS WordPress ใช้ semantics ระบบไฟล์ — มันสร้างไดเรกทอรี เขียนไฟล์ อ่านไฟล์ตามพาธ S3 จะต้องเขียนระบบนิเวศปลั๊กอิน WordPress ใหม่ EFS mount เป็นระบบไฟล์ NFS มาตรฐาน ซึ่ง WordPress ทำงานด้วยโดยกำเนิด

**สถานการณ์ C**: ฐานข้อมูล PostgreSQL รันบน EC2 instance มันต้องการ I/O แบบสุ่มที่เร็วสำหรับการรันคำสืบค้นและการค้นหา index

การตัดสินใจ: EBS (gp3 หรือ io2) ฐานข้อมูลต้องการ block storage ที่มีความหน่วงต่ำสำหรับการอ่านและเขียนแบบสุ่มเล็ก ๆ S3 ช้าเกินไปและไม่รองรับ semantics ระบบไฟล์ EFS มีความหน่วงสูงกว่า EBS สำหรับ I/O แบบสุ่ม

รูปแบบ: ค่าเริ่มต้นสำหรับไฟล์คือ S3 เพิ่ม EBS เมื่อคุณต้องการ block storage สำหรับ instance เฉพาะ เพิ่ม EFS เมื่อ instance หลายตัวต้องแชร์ระบบไฟล์ instance store สำหรับพื้นที่ทำงานชั่วคราวเท่านั้น

## เมื่อ EFS ไม่เพียงพอ: Amazon FSx

บทเรียนพื้นที่จัดเก็บถัดไปไม่ได้มาในรูปของการหยุดทำงานหรือการถกเถียงที่ไวท์บอร์ด มันมาในรูปของสัญญาการขาย — แบบที่ Maya ไล่ตามตั้งแต่พอร์ทัลเปิดตัว แบบที่ใช้เวลาทั้งไตรมาสของการเดโมและสายติดตามผลจึงปิดได้ สามเดือนหลังจากพอร์ทัลผู้ดำเนินการร้านอาหารเปิดตัว Nimbus เซ็นลูกค้าหลายสาขารายแรก: Copper Kettle กลุ่มร้านอาหารที่เป็นกิจการครอบครัวสิบสองสาขาทั่วมิดเวสต์ Maya ดำเนินการดีลนี้ Tom สร้างแบบจำลองทางการเงิน Leo เริ่มวางแผนการผสานรวมทางเทคนิคก่อนหมึกจะแห้ง

จากนั้นเขาอ่านบันทึกโครงสร้างพื้นฐานจากทีม IT ของ Copper Kettle

"ไฟล์เซิร์ฟเวอร์ของพวกเขาเป็น Windows" เขาพูด "ทุกอย่างเป็น Windows ซอฟต์แวร์จัดการครัวของพวกเขา ระบบ HR ของพวกเขา เครื่องมือจัดตารางของพวกเขา — ทั้งหมดเขียนไปยังไดรฟ์ที่แชร์บนไฟล์เซิร์ฟเวอร์ Windows โปรโตคอล SMB การยืนยันตัวตน Active Directory"

"เรายก them ขึ้น EFS ได้ไหม?" Maya ถาม

Leo ส่ายหัว "EFS ใช้ NFS แอปพลิเคชันของพวกเขาพูด SMB นั่นเป็นโปรโตคอลคนละตัว ซอฟต์แวร์ Copper Kettle ไม่รู้ว่า NFS คืออะไร คุณชี้มันไปที่ EFS mount เฉย ๆ ไม่ได้"

"ดังนั้นเราใช้ EFS ไม่ได้"

"ไม่ใช่สำหรับอันนี้ มีบริการอื่น"

**FSx for Windows File Server: EFS แต่สำหรับ Windows**

**Amazon FSx for Windows File Server** คือระบบไฟล์ที่แชร์แบบ Windows-native ที่มีการจัดการเต็มรูปแบบ มันรองรับโปรโตคอล SMB (Server Message Block) — โปรโตคอลเดียวกับที่เซิร์ฟเวอร์ Windows แอปพลิเคชัน Windows และไฟล์แชร์ Windows on-premises ใช้มาหลายทศวรรษ มันผสานรวมกับ Active Directory รองรับ Windows ACL (สิทธิ์ระดับไฟล์) และรองรับฟีเจอร์เฉพาะ Windows ที่แอปพลิเคชัน Windows พึ่งพาจริง

ลองคิดว่ามันเป็น EFS แต่สำหรับ Windows — พร้อมฟีเจอร์เฉพาะ Windows ทั้งหมดที่สภาพแวดล้อม Active Directory ของคุณคาดหวังอยู่แล้ว ซอฟต์แวร์จัดการครัว Copper Kettle จะเชื่อมต่อกับมันเหมือนที่มันเชื่อมต่อกับไฟล์เซิร์ฟเวอร์ on-premises พอดี แอปพลิเคชันไม่เปลี่ยน โปรโตคอลไม่เปลี่ยน ข้อมูลแค่อยู่บนบริการ AWS ที่มีการจัดการแทนเซิร์ฟเวอร์ในห้องใต้ดินที่ไหนสักแห่งในชิคาโก

สำหรับการย้าย Copper Kettle: Leo จัดสรรระบบไฟล์ FSx for Windows File Server เชื่อมต่อมันกับ Active Directory ของ Copper Kettle (ขยายไปยัง AWS ผ่าน AWS Managed Microsoft AD) และแมปตัวอักษรไดรฟ์ที่มีอยู่ ซอฟต์แวร์ครัวพบไฟล์แชร์ของมันตรงที่มันคาดหวังพอดี

"นั่นมีต้นทุนต่อเดือนเท่าไหร่?" Tom ถาม

Leo ดูไว้แล้ว FSx for Windows มีราคาต่อ GB ของพื้นที่จัดเก็บต่อเดือน — แพงกว่า EFS แพงกว่า S3 อย่างมาก แต่ถูกกว่าการดูแลไฟล์เซิร์ฟเวอร์ Windows ทั่วสิบสองสาขามาก Tom เขียนตัวเลขลงไปโดยไม่คัดค้าน

**FSx for Lustre: เมื่องาน ML ของคุณต้องป้อนข้อมูลให้ GPU หลายร้อยตัว**

ในขณะเดียวกัน Leo เริ่มทำต้นแบบเอนจินแนะนำควบคู่ไปด้วย — ทำนายว่าลูกค้าน่าจะสั่งจานไหนตามพฤติกรรมในอดีตและสิ่งที่ลูกค้าที่คล้ายกันสั่ง ข้อมูลการฝึกยังเล็ก แต่การทดลองพาเขาลงไปในรูกระต่ายของวิธีที่ทีม ML จริงจังป้อนข้อมูลให้โมเดล: งานฝึกที่อ่านหลายร้อยกิกะไบต์จาก S3 ในทุกรอบ

"รูปแบบที่ปรากฏขึ้นเรื่อย ๆ ในกรณีศึกษา" เขารายงานที่มื้อกลางวันทีมครั้งถัดไป "คืองานฝึกที่คอขวดอยู่ที่ I/O GPU ราคาแพงนั่งว่าง 40% ของเวลา รอ batch ข้อมูลถัดไป"

นี่คือปัญหาที่ต่างจากการจัดเก็บไฟล์ที่แชร์ มันเป็นปัญหา high-performance computing (HPC): เมื่อคุณมีหน่วยประมวลผลหลายร้อยตัวที่ทั้งหมดต้องอ่านข้อมูลพร้อมกัน ที่ throughput สูงมาก จากชุดข้อมูลเดียวกัน

**Amazon FSx for Lustre** คือการนำระบบไฟล์ขนาน Lustre มาใช้แบบที่มีการจัดการเต็มรูปแบบ Lustre ถูกสร้างขึ้นโดยเฉพาะสำหรับสถานการณ์นี้พอดี — การอ่านขนานที่ throughput สูงมาก ข้ามไคลเอนต์พร้อมกันหลายตัว มันผสานรวมกับ S3 โดยกำเนิด: คุณชี้ FSx for Lustre ไปที่ S3 bucket และมันทำให้ข้อมูลนั้นพร้อมใช้งานผ่านระบบไฟล์ Lustre โดยอัตโนมัติ งานฝึกอ่านจากจุด mount ในเครื่อง FSx สตรีมข้อมูลจาก S3 เบื้องหลัง

เมื่องานฝึก ML ของคุณต้องป้อนข้อมูลให้ GPU หลายร้อยตัวพร้อมกัน FSx for Lustre คือเครื่องมือ เช่นเดียวกันกับการสร้างแบบจำลองทางการเงิน เวิร์กโหลดจีโนมิกส์ และการเรนเดอร์วิดีโอ — เวิร์กโหลดใด ๆ ที่คอขวดคือ throughput ของ I/O ขนานมากกว่าความจุพื้นที่จัดเก็บ

กรณีศึกษาที่ Leo บุ๊กมาร์กไว้เล่าเรื่องในสองตัวเลข: หลังจากย้ายงานฝึกไปยัง FSx for Lustre การใช้งาน GPU ไต่จาก 60% เป็น 94% และการรันฝึกที่เคยใช้เวลาหกชั่วโมงเสร็จในสามชั่วโมงครึ่ง Nimbus จะไม่ต้องการแรงม้าแบบนั้นไปอีกนาน — แต่ Leo เก็บรูปแบบนี้ไว้สำหรับวันที่เอนจินแนะนำเติบโตขึ้น

**ตัวเลือก FSx อื่น ๆ**

AWS ยังเสนอ **FSx for NetApp ONTAP** — สำหรับองค์กรที่รันพื้นที่จัดเก็บ NetApp on-premises อยู่แล้วและต้องการการเข้าถึงหลายโปรโตคอล (NFS, SMB และ iSCSI จากระบบไฟล์เดียวกัน) — และ **FSx for OpenZFS** สำหรับเวิร์กโหลดที่ต้องการฟีเจอร์เฉพาะ ZFS เช่น snapshot และ clone ที่ระดับระบบไฟล์ ทั้งสองเป็นเครื่องมือเฉพาะทางสำหรับองค์กรที่มีโครงสร้างพื้นฐานหรือข้อกำหนดเฉพาะที่มีอยู่

สำหรับทีมส่วนใหญ่ การตัดสินใจอยู่ระหว่างสี่รูปแบบ FSx กับ EFS คำถามเหมือนเดิมเสมอ: เวิร์กโหลดพูดโปรโตคอลอะไร และมันต้องการคุณลักษณะประสิทธิภาพอะไร?

> - **FSx for Windows = SMB + Active Directory + เวิร์กโหลด Windows** สัญญาณการสอบ: "Windows file server" "โปรโตคอล SMB" "การผสานรวม Active Directory" "lift-and-shift แอปพลิเคชัน Windows" เมื่อคุณเห็นวลีใด ๆ เหล่านั้น FSx for Windows คือคำตอบ
> - **FSx for Lustre = HPC + การฝึก ML + I/O ขนาน + การผสานรวม S3** สัญญาณการสอบ: "การฝึก machine learning" "high-performance computing" "HPC" "ระบบไฟล์ขนาน" "เวิร์กโหลดที่ใช้ I/O หนัก" "GPU cluster" "ผสานรวมระบบไฟล์กับ S3" เมื่อคุณเห็นวลีเหล่านั้น FSx for Lustre คือคำตอบ
> - **EFS ไม่ใช่สิ่งทดแทนสำหรับอันใดอันหนึ่ง** EFS คือ NFS สำหรับเวิร์กโหลด Linux มันไม่พูด SMB มันไม่ใช่ระบบไฟล์ประสิทธิภาพสูงแบบขนาน การใช้ EFS ที่ที่ต้องการ FSx หมายความว่าแอปพลิเคชันไม่ทำงาน (Windows) หรือคอขวดที่ I/O (HPC)
> - **FSx for NetApp ONTAP และ FSx for OpenZFS** ปรากฏไม่บ่อยนัก แต่สัญญาณชัดเจน "ย้ายพื้นที่จัดเก็บ NetApp/ONTAP ที่มีอยู่" "การเข้าถึงหลายโปรโตคอล (NFS + SMB + iSCSI)" หรือ "SnapMirror" → FSx for NetApp ONTAP "ZFS" "NFS พร้อม snapshot/clone ทันที" หรือ "ย้ายไฟล์เซิร์ฟเวอร์ ZFS on-premises" → FSx for OpenZFS
> - อ้างอิงด่วน: "SMB หรือ Windows file server" → FSx for Windows "การฝึก machine learning หรือ high-performance computing" → FSx for Lustre "NetApp/หลายโปรโตคอล" → FSx for ONTAP "ZFS" → FSx for OpenZFS

## สะพานสู่คลาวด์: AWS Storage Gateway

ลูกค้ารายใหญ่ที่สุดของ Nimbus จนถึงตอนนี้ — เครือร้านระดับภูมิภาคชื่อ Meridian Kitchen ยี่สิบสาขาทั่วสามรัฐ — มาพร้อมปัญหาที่แก้ด้วย `aws s3 cp` ไม่ได้

Meridian มีข้อมูลการดำเนินงานหลายปีอยู่บนไฟล์เซิร์ฟเวอร์ on-premises สูตรอาหาร ใบแจ้งหนี้ วิดีโอครัว สัญญาซัพพลายเออร์ ไม่ใช่ไม่กี่กิกะไบต์ แต่เป็น terabyte และซอฟต์แวร์ที่สร้างและใช้ข้อมูลนี้ — ระบบจัดการครัวของพวกเขา แพลตฟอร์มออกใบแจ้งหนี้ของพวกเขา เครื่องมือ HR ของพวกเขา — ทั้งหมดเขียนไปยังไฟล์แชร์ในเครื่องโดยใช้ NFS หรือ SMB การเขียนแอปพลิเคชันเหล่านั้นใหม่ไม่เป็นไปได้ การย้ายข้อมูลทั้งหมดในชั่วข้ามคืนก็ไม่เป็นไปได้เช่นกัน

"แล้วเราจะเริ่มนำข้อมูลของพวกเขาเข้า AWS ได้อย่างไร" Maya ถาม "โดยไม่ขอให้พวกเขาเปลี่ยนแอปพลิเคชันแม้แต่ตัวเดียว?"

"มีบริการสำหรับเรื่องนี้พอดี" Priya พูด "มันรันในศูนย์ข้อมูลของพวกเขาเป็น VM ดูเหมือนไฟล์เซิร์ฟเวอร์หรืออุปกรณ์จัดเก็บปกติสำหรับซอฟต์แวร์ที่มีอยู่ของพวกเขา และเก็บทุกอย่างใน AWS อย่างเงียบ ๆ เบื้องหลัง"

บริการนั้นคือ **AWS Storage Gateway**: บริการจัดเก็บแบบไฮบริดที่เชื่อมต่อสภาพแวดล้อม on-premises กับพื้นที่จัดเก็บ AWS มันนำเสนอพื้นที่จัดเก็บให้แอปพลิเคชันของคุณโดยใช้โปรโตคอลที่พวกมันเข้าใจอยู่แล้ว ในขณะที่จริง ๆ แล้วเก็บข้อมูลใน S3, S3 Glacier หรือเป็น EBS snapshot

มี gateway สามประเภท แต่ละอันแก้ปัญหา on-premises ที่ต่างกัน

**File Gateway** นำเสนออินเทอร์เฟซ NFS หรือ SMB ให้แอปพลิเคชัน on-premises ไฟล์ที่เขียนไปยัง gateway ถูกเก็บเป็น object ใน S3 — แต่แอปพลิเคชันไม่รู้สิ่งนั้น มันเห็นระบบไฟล์ ไฟล์ที่เข้าถึงบ่อยถูกแคชในเครื่องเพื่อการอ่านที่ความหน่วงต่ำ ส่วนที่เหลืออยู่ใน S3 นี่คือสิ่งที่ Meridian ต้องการ: ซอฟต์แวร์จัดการครัวเขียนไปยังสิ่งที่ดูเหมือนไฟล์แชร์ และข้อมูลลงเอยใน S3 ที่ Nimbus วิเคราะห์ สำรอง และค้นหามันได้

"เดี๋ยวนะ — แต่ *ทำไม* เราถึงจะทำแบบนั้น?" Maya ถาม "ทำไมไม่ชี้ซอฟต์แวร์ไปที่ S3 โดยตรง?"

เพราะ NFS และ SMB ไม่ใช่ S3 ซอฟต์แวร์ครัวไม่พูด API ของ S3 มันเปิดพาธไฟล์ มันเขียนไบต์ไปยังไดเรกทอรี File Gateway แปลสิ่งนั้นเป็นการดำเนินการ object ของ S3 โดยที่แอปพลิเคชันไม่รู้ว่าอะไรเปลี่ยน

**Volume Gateway** นำเสนอ volume block storage แบบ iSCSI ให้เซิร์ฟเวอร์ on-premises — อินเทอร์เฟซเดียวกับที่ฮาร์ดไดรฟ์จริงหรืออุปกรณ์ SAN จะนำเสนอ มันมีสองโหมด: *stored volume* เก็บข้อมูลหลักไว้ on-premises พร้อมการสำรองแบบอะซิงโครนัสไปยัง S3 เป็น EBS snapshot (สำหรับเวิร์กโหลดที่ on-premises มาก่อนซึ่งต้องการการสำรองบนคลาวด์ด้วย) และ *cached volume* เก็บข้อมูลหลักใน S3 พร้อมข้อมูลที่เข้าถึงบ่อยถูกแคช on-premises (สำหรับองค์กรที่พร้อมปฏิบัติต่อ S3 เป็นพื้นที่จัดเก็บหลัก)

**Tape Gateway** นำเสนอ virtual tape library (VTL) ให้ซอฟต์แวร์สำรองข้อมูลเช่น Veeam, Veritas หรือ NetBackup ซอฟต์แวร์สำรองเขียนไปยังสิ่งที่ดูเหมือนตลับเทปจริง เทปเสมือนเหล่านั้นถูกเก็บใน S3 และเก็บถาวรไปยัง S3 Glacier ได้ ซอฟต์แวร์สำรองไม่เปลี่ยน หุ่นยนต์เทปจริงและชั้นวางก็หายไป

"ทีมสำรองของ Meridian รัน Veeam" Leo พูด "พวกเขามีเทปจริง การจัดเก็บนอกสถานที่ ตารางหมุนเวียน ทุกอย่างเลย"

"Tape Gateway แทนที่เทปจริง" Priya พูด "การกำหนดค่า Veeam เดิม งานสำรองเดิม เทปแค่อยู่ใน S3 แทนแร็ค"

Tom ค้นต้นทุนการจัดเก็บเทปนอกสถานที่ เขาปิดแท็บนั้นโดยไม่แสดงความเห็นและอนุมัติแผนการย้าย

> **เคล็ดลับการสอบ — AWS Storage Gateway**
>
> *SAA-C03 Domain: การออกแบบสถาปัตยกรรมประสิทธิภาพสูง (Domain 3)*
>
> - **File Gateway = NFS/SMB → S3** ไฟล์ที่เขียนโดยแอปพลิเคชัน on-premises กลายเป็น object ของ S3 ไฟล์ที่เข้าถึงบ่อยถูกแคชในเครื่อง ตัวกระตุ้นการสอบ: "แอปพลิเคชัน on-premises ต้องเก็บไฟล์ใน S3 โดยไม่ต้องเปลี่ยนโค้ด"
> - **Volume Gateway = iSCSI block storage → S3 snapshot** โหมด stored: ข้อมูลหลัก on-premises สำรองไปยัง S3 เป็น EBS snapshot โหมด cached: ข้อมูลหลักใน S3 บล็อกที่เข้าถึงบ่อยถูกแคชในเครื่อง ตัวกระตุ้นการสอบ: "เซิร์ฟเวอร์ on-premises ต้องการ block storage ที่สำรองบนคลาวด์"
> - **Tape Gateway = VTL → S3/Glacier** ซอฟต์แวร์สำรองเขียนไปยังเทปเสมือน เทปเก็บใน S3 หรือเก็บถาวรไปยัง Glacier ตัวกระตุ้นการสอบ: "แทนที่โครงสร้างพื้นฐานสำรองเทปจริงโดยไม่เปลี่ยนซอฟต์แวร์สำรอง"
> - **รูปแบบการสอบสำคัญ:** "แอปพลิเคชัน on-premises ต้องการพื้นที่จัดเก็บคลาวด์โดยไม่ต้องเปลี่ยนโค้ด" → Storage Gateway "แทนที่การสำรองเทป" → Tape Gateway โดยเฉพาะ

## จุดแข็งและข้อจำกัด

**จุดแข็งของ EBS**:

- block storage ที่ถาวร เร็ว สำหรับ EC2
- snapshot สำหรับการสำรองและกู้คืน ณ จุดเวลา
- ระดับประสิทธิภาพหลายระดับสำหรับเวิร์กโหลดต่างกัน
- รองรับการเข้ารหัสตอนพักโดยกำเนิด — เปิดใช้งานการเข้ารหัสระดับบัญชีโดยค่าเริ่มต้น

**ข้อจำกัดของ EBS**:

- แนบกับ instance เดียวในแต่ละครั้ง (โดยมีข้อยกเว้นเล็กน้อย)
- อยู่ใน AZ เดียวกับ EC2 instance (การคัดลอกไปยัง AZ อื่นต้องใช้ snapshot)
- คุณจ่ายค่าพื้นที่จัดเก็บที่จัดสรร ไม่ใช่แค่สิ่งที่คุณใช้
- การเข้ารหัส volume ที่มีอยู่และไม่ได้เข้ารหัสต้องการวงจร snapshot-copy-restore พร้อมหน้าต่างการบำรุงรักษา

**จุดแข็งของ EFS**:

- ระบบไฟล์ที่แชร์หลาย instance — โปรโตคอล NFS โดยกำเนิด
- ปรับขนาดอัตโนมัติ คุณไม่ได้จัดสรรความจุ
- เข้าถึงได้ข้าม AZ ภายใน Region
- โหมด Elastic Throughput ปรับโดยอัตโนมัติตามเวิร์กโหลด

**ข้อจำกัดของ EFS**:

- แพงกว่า S3 ต่อ GB
- ความหน่วงสูงกว่า EBS สำหรับ I/O แบบสุ่ม
- ไม่มีให้ใช้ในทุก Region

## การย้ายข้อมูลจำนวนมาก: DataSync และ Snow Family

Storage Gateway รักษาให้แอปพลิเคชัน on-premises *เชื่อมต่ออย่างต่อเนื่อง* กับพื้นที่จัดเก็บคลาวด์ แต่มีสถานการณ์การย้ายอีกสองอย่างที่ปรากฏในการสอบอยู่ตลอด — และในที่สุดในโปรเจกต์จริง:

**AWS DataSync** มีไว้สำหรับ *การถ่ายโอนจำนวนมากแบบออนไลน์*: การย้ายชุดข้อมูลขนาดใหญ่ผ่านเครือข่ายระหว่างไฟล์เซิร์ฟเวอร์ NFS/SMB on-premises (หรือคลาวด์อื่น) กับ S3, EFS หรือ FSx — ครั้งเดียว หรือตามกำหนดเวลา มันจัดการการขนาน การตรวจสอบความสมบูรณ์ การลองใหม่ และการจำกัดแบนด์วิดท์ และมันเร็วกว่าสคริปต์แบบ rsync ที่เขียนเองราว ๆ 10 เท่า ตัวกระตุ้นการสอบ: "ย้าย/ถ่ายโอนไฟล์หลายล้านไฟล์จากเซิร์ฟเวอร์ NFS on-premises ไปยัง Amazon EFS/S3" → DataSync (อย่าสับสนกับ Storage Gateway ซึ่งมีไว้สำหรับ *การเข้าถึงไฮบริดต่อเนื่อง* หรือ DMS ซึ่งย้าย *ฐานข้อมูล*)

**AWS Snow Family** มีไว้สำหรับเมื่อเครือข่ายคือคอขวด การย้าย 100 TB ผ่านสาย 100 Mbps ใช้เวลามากกว่าสามเดือน รถบรรทุกเร็วกว่า **Snowball Edge** คืออุปกรณ์ทนทานที่ AWS ส่งให้คุณ — โหลดได้สูงสุด ~80 TB ในเครื่อง ส่งกลับ AWS นำเข้ามันใน S3 **Snowcone** เป็นเวอร์ชันพกพาขนาดเล็ก (~8–14 TB) สำหรับตำแหน่ง edge — เลิกผลิตในปลายปี 2024 แม้ว่ามันอาจยังปรากฏในคำถามสอบเก่า (ดูการตรวจสอบความจริงในบทที่ 25) ตัวกระตุ้นคณิตศาสตร์ในการสอบ: เมื่อโจทย์ให้ขนาดชุดข้อมูลและสายที่บางหรือไม่น่าเชื่อถือและถามถึงการย้ายที่เร็วที่สุด/ปฏิบัติได้มากที่สุด ให้คำนวณเวลาถ่ายโอน — ถ้าเป็นสัปดาห์หรือเดือน คำตอบคือ Snow Family

> **เคล็ดลับการสอบ — AWS Backup**
>
> มีอีกหนึ่งบริการที่เย็บบทนี้เข้าด้วยกัน: **AWS Backup** รวมศูนย์และทำให้การสำรองข้อมูลเป็นอัตโนมัติข้าม EBS, EFS, RDS, DynamoDB, FSx และ Storage Gateway ด้วยแผนสำรองเดียว — กำหนดการ การเก็บรักษา การคัดลอกข้าม region และข้ามบัญชี และ Backup Vault Lock สำหรับความไม่เปลี่ยนแปลง ตัวกระตุ้นการสอบ: "จัดการการสำรองข้อมูลข้าม AWS service/บัญชีหลายอันแบบรวมศูนย์" → AWS Backup ไม่ใช่สคริปต์ต่อบริการ


## สรุป

ปากกาแดงของ Tom วงกลมปัญหาที่แท้จริง: มากเกินไปบนเครื่องเดียว การย้ายพื้นที่จัดเก็บออกจาก EC2 instance ไม่ใช่แค่เรื่องความจุ — มันเกี่ยวกับการแยกความรับผิดชอบเพื่อให้แต่ละชั้นถูกจัดการ ขยาย และรักษาความปลอดภัยได้อย่างอิสระ ทางเลือกพื้นที่จัดเก็บที่ถูกต้องขึ้นอยู่กับสี่คำถาม: อะไรต้องการพื้นที่จัดเก็บ มีกี่อย่างต้องการมันในเวลาเดียวกัน มันอยู่นานแค่ไหน และมันถูกเข้าถึงอย่างไร? สี่คำถามนั้นนำไปสู่คำตอบที่ถูกต้องอย่างสม่ำเสมอ

- **EBS** (Elastic Block Store) คือ block storage ถาวรสำหรับ EC2 instance เดียว มันรอดจากการหยุด instance และทำ snapshot เพื่อสำรองได้ ใช้ gp3 สำหรับเวิร์กโหลดทั่วไป io2 สำหรับข้อกำหนด IOPS สูง instance store เป็นแบบชั่วคราวและเร็วแต่หายไปเมื่อ instance ถูกยุติ
- **EFS** (Elastic File System) คือระบบไฟล์เครือข่ายที่แชร์ซึ่ง instance หลายตัว mount พร้อมกันได้ EFS ครอบคลุม AZ ภายใน Region EBS ถูกจำกัดอยู่ที่ AZ เดียว
- จับคู่ประเภทพื้นที่จัดเก็บกับข้อกำหนด: ฐานข้อมูล EC2 เดียว → EBS; ไฟล์ที่แชร์ข้ามเซิร์ฟเวอร์ → EFS; object สื่อ ข้อมูลสำรอง → S3; คลัง → S3 Glacier
- การเข้ารหัส EBS volume ที่มีอยู่ต้องการ: snapshot → คัดลอกที่เข้ารหัส → volume ใหม่ → สลับ เปิดใช้งานการเข้ารหัสระดับบัญชีโดยค่าเริ่มต้นเพื่อหลีกเลี่ยงสิ่งนี้สำหรับ volume ใหม่
- **EBS "Delete on Termination"**: root volume ค่าเริ่มต้นลบเมื่อ instance ถูกยุติ; volume ข้อมูลค่าเริ่มต้นคงอยู่ ตรวจสอบทั้งสองการตั้งค่าเมื่อออกแบบ policy วงจรชีวิต instance

## เคล็ดลับการสอบ

*SAA-C03 Domain 3 — Task 3.1 (โซลูชันพื้นที่จัดเก็บ)*

- **EBS volume อยู่ใน AZ เดียว** พวกมันแนบได้เฉพาะกับ instance ใน AZ เดียวกัน
  ในการใช้ EBS volume ใน AZ อื่น คุณสร้าง snapshot และกู้คืนมันใน AZ เป้าหมาย
- **EBS snapshot เป็นแบบเพิ่มทีละส่วนและเก็บใน S3** snapshot แรกเต็ม
  อันที่ตามมาเก็บเฉพาะการเปลี่ยนแปลง คุณคัดลอก snapshot ไปยัง Region อื่นสำหรับ
  การกู้คืนจากภัยพิบัติได้
- **EFS ข้าม AZ** instance หลายตัวใน AZ ต่างกันภายใน Region เดียวกัน
  mount ระบบไฟล์ EFS เดียวกันได้ นี่คือตัวแยกความแตกต่างสำคัญจาก EBS
- **เมื่อสถานการณ์การสอบบอกว่า "เว็บแอปพลิเคชันที่มีเนื้อหาที่แชร์" หรือ "instance
  หลายตัวเข้าถึงไฟล์เดียวกัน" ให้คิดถึง EFS** เมื่อมันบอกว่า "การจัดเก็บฐานข้อมูล"
  หรือ "ดิสก์ถาวรสำหรับเซิร์ฟเวอร์เดียว" ให้คิดถึง EBS
- **ข้อมูล instance store รอดจากการรีบูตแต่ไม่ใช่การหยุดหรือยุติ** คำถาม
  อาจอธิบายข้อมูลที่ "หายไปหลังจาก instance ถูกหยุด" — นั่นคือ instance
  store เข้ามาเกี่ยวข้อง
- **gp3 กับ io2**: gp3 เป็นค่าเริ่มต้นสำหรับการใช้งานทั่วไป io2 สำหรับเวิร์กโหลดที่
  ต้องการ IOPS ที่รับประกัน (ฐานข้อมูลขนาดใหญ่ ระบบสำคัญยิ่ง) สถานการณ์การสอบที่
  อธิบาย "ข้อกำหนด IOPS" หรือ "ประสิทธิภาพฐานข้อมูลความหน่วงต่ำที่สม่ำเสมอ"
  ชี้ไปที่ io2
- **gp2 กับ gp3:** IOPS ของ gp2 ผูกกับขนาด (3 IOPS/GB สูงสุด 16,000 IOPS ที่ 5,334 GB); IOPS ของ gp3 เป็นอิสระจากขนาด (เส้นฐาน 3,000 กำหนดค่าได้สูงสุด 80,000 ตั้งแต่กันยายน 2025 — เนื้อหาเก่า และอาจรวมถึงคลังคำถามสอบ ยังสันนิษฐานเพดาน 16,000 เดิม) รูปแบบคำถามสอบ: เวิร์กโหลดต้องการ IOPS มากขึ้นโดยไม่เพิ่มพื้นที่จัดเก็บ — คำตอบคือ gp3 หรือ io2 ไม่ใช่ gp2
- **การเข้ารหัสตอนพักสำหรับ EBS**: คุณเข้ารหัส volume ที่มีอยู่และไม่ได้เข้ารหัส
  ในที่ไม่ได้ — คุณต้อง snapshot คัดลอกที่เข้ารหัส กู้คืน เปิดใช้งานค่าเริ่มต้นการเข้ารหัส
  ระดับบัญชีเพื่อหลีกเลี่ยงการสร้าง volume ที่ไม่เข้ารหัสโดยไม่ตั้งใจ การเข้ารหัสเป็น AES-256
  โดยใช้คีย์ KMS
- **Fast Snapshot Restore** ขจัดบทลงโทษด้านประสิทธิภาพบน volume ที่เพิ่งกู้คืน
  แต่มีค่าใช้จ่ายต่อ snapshot ต่อ AZ คำถามสอบเกี่ยวกับการกู้คืน volume
  "ทันทีที่ประสิทธิภาพเต็มรูปแบบ" ชี้ไปที่ FSR
- **EFS performance mode**: General Purpose (ความหน่วงต่ำ เหมาะสำหรับเวิร์กโหลดส่วนใหญ่)
  กับ Max I/O (throughput สูงกว่าสำหรับเวิร์กโหลดที่ขนานสูง)
- **EFS throughput mode — สามตัวเลือก:** Bursting (throughput ปรับขนาดตามขนาดพื้นที่จัดเก็บ ใช้เครดิต burst — ดีสำหรับเวิร์กโหลดพุ่งกระชาก) Elastic (ปรับขนาดอัตโนมัติ จ่ายตามการใช้ — ดีสำหรับเวิร์กโหลดที่คาดเดาไม่ได้) Provisioned (throughput คงที่ไม่ว่าพื้นที่จัดเก็บเท่าไหร่ — ดีสำหรับความต้องการ throughput สูงที่สม่ำเสมอ) การสอบทดสอบว่าคุณรู้เมื่อไหร่ควรจัดสรร throughput เทียบกับให้มันปรับขนาดแบบ elastic หรือพึ่งเครดิต burst หรือไม่
- **Cross-region snapshot copy**: EBS snapshot คัดลอกไปยัง Region อื่นสำหรับ
  การกู้คืนจากภัยพิบัติได้ snapshot ที่คัดลอกเป็นอิสระและไม่เพิ่มต้นทุนการถ่ายโอนข้อมูล
  ในระหว่างการกู้คืน — เฉพาะในระหว่างการดำเนินการคัดลอกเอง
- **ประเภท Storage Gateway:** File Gateway = NFS/SMB → S3 (ไฟล์กลายเป็น object) Volume Gateway = iSCSI block storage → S3 snapshot (stored: หลัก on-prem; cached: หลักใน S3) Tape Gateway = VTL → S3/Glacier (แทนที่เทปจริง) ตัวกระตุ้นการสอบ: "แอป on-premises ต้องการพื้นที่จัดเก็บคลาวด์โดยไม่ต้องเปลี่ยนโค้ด" → Storage Gateway "แทนที่การสำรองเทป" → Tape Gateway

## แบบฝึกหัด

**แบบฝึกหัด 1 — การจำ**

ด้วยคำพูดของคุณเอง: ความแตกต่างระหว่าง EBS กับ EFS คืออะไร? คุณจะเลือกอันหนึ่งเหนืออีกอันเมื่อไหร่?

*(คำใบ้: คิดถึงว่า instance เดียวหรือ instance หลายตัวต้องเข้าถึงพื้นที่จัดเก็บในเวลาเดียวกัน)*

**แบบฝึกหัด 2 — สถานการณ์ SAA-C03**

*สถานการณ์*: บริษัทรันเว็บแอปพลิเคชันบน EC2 instance สี่ตัวหลัง load balancer ผู้ใช้อัปโหลดรูปโปรไฟล์ได้ รูปใด ๆ ต้องดูได้โดยผู้ใช้ทันทีหลังการอัปโหลด ไม่ว่า instance ใดจะจัดการมัน รูปถูกให้บริการแก่เบราว์เซอร์ผ่าน HTTP ไม่เคยถูกแก้ไขในที่ และทีมต้องการโซลูชันที่คุ้มค่าที่สุด ขยายได้ พร้อมภาระในการดำเนินงานน้อยที่สุด

โซลูชันพื้นที่จัดเก็บใดตอบสนองความต้องการของพวกเขาได้ดีที่สุด?

A) แนบ EBS gp3 volume กับ EC2 instance แต่ละตัวและซิงค์ไฟล์ระหว่างกันโดยใช้
   cron job  
B) เก็บรูปบน instance store ของ EC2 instance โดยตรง  
C) ใช้ Amazon EFS mount บน EC2 instance ทั้งสี่ตัวพร้อมกัน  
D) เก็บรูปใน S3 และเข้าถึงพวกมันโดยตรงจากโค้ดแอปพลิเคชัน

**คำใบ้ 1**: ข้อกำหนดคือ "ทั้งสี่ instance ต้องให้บริการรูปใด ๆ ได้" ตัวเลือกใดทำให้ไฟล์มองเห็นได้ทันทีสำหรับทุก instance?

**คำใบ้ 2**: instance store เป็นแบบชั่วคราว EBS mount บน instance หลายตัวพร้อมกันไม่ได้ นั่นทำให้แคบลง

**คำใบ้ 3**: ทั้ง C และ D ในทางทฤษฎีอาจทำงานได้ อันไหนเหมาะสมกว่าสำหรับกรณีที่แอปพลิเคชันต้องเข้าถึงรูปผ่านการดำเนินการระบบไฟล์เทียบกับคำขอ HTTP?

**คำตอบ**: D

**คำอธิบาย**: การเก็บรูปใน S3 และให้บริการพวกมันผ่าน URL เป็นทางเลือกที่ถูกต้องทางสถาปัตยกรรมสำหรับเว็บแอปพลิเคชัน รูปที่อัปโหลดเข้าถึงได้ทันทีจากเซิร์ฟเวอร์ใด ๆ (และจากเบราว์เซอร์ใด ๆ) ผ่าน URL ของ S3 S3 ออกแบบมาสำหรับกรณีการใช้งานนี้พอดี: การเก็บไฟล์ที่ผู้ใช้อัปโหลดในระดับขนาดใหญ่ด้วยความพร้อมใช้งานสูงและภาระการจัดการเป็นศูนย์

หมายเหตุ: C (EFS) ในทางเทคนิคจะทำงานได้ แต่ S3 เป็นรูปแบบที่นิยมสำหรับไฟล์ไบนารีที่ผู้ใช้อัปโหลดในเว็บแอปพลิเคชันเพราะมันถูกกว่า ขยายได้มากกว่า และให้บริการไฟล์ผ่าน HTTP โดยตรงโดยไม่ต้องให้แอปพลิเคชันทำหน้าที่เป็น proxy

**ทำไมไม่ใช่ A?** การซิงค์ไฟล์ผ่าน cron job สร้าง race condition และปัญหาความสอดคล้อง ระหว่างการอัปโหลดและการซิงค์ครั้งถัดไป ไฟล์จะหายไปบน instance อื่น

**ทำไมไม่ใช่ B?** ข้อมูล instance store หายไปเมื่อ instance ถูกหยุดหรือยุติ รูปจะหายไป

**ทำไมไม่ใช่ C?** EFS เป็นคำตอบที่ถูกต้องเมื่อคำถามเรียกร้อง semantics ระบบไฟล์ (เช่น CMS ที่แก้ไขไฟล์ในที่) สำหรับรูปที่ผู้ใช้อัปโหลดที่ให้บริการผ่านเว็บ S3 เรียบง่ายกว่า ถูกกว่า และเหมาะสมกว่า

**คำเตือนคำสำคัญในการสอบ**: ในการสอบจริง อ่านโจทย์ตามตัวอักษร ถ้ามันบอกว่า "การจัดเก็บ **ไฟล์** ที่แชร์" "ระบบไฟล์" "NFS" หรือ "POSIX" คำตอบที่กำหนดไว้คือ **EFS** — อย่าลบล้างข้อกำหนดที่ระบุด้วยรสนิยมทางสถาปัตยกรรม สถานการณ์นี้กำหนดไว้ที่ S3 เพราะมันขอการส่งมอบ object ที่คุ้มค่าผ่าน HTTP ไม่ใช่ระบบไฟล์
