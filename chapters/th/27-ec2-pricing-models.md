Leo มองเขา "แล้วเวอร์ชัน AWS ของสิ่งเหล่านั้นคืออะไร?"

Tom ดึงหน้า EC2 pricing ขึ้นมา "มีสี่ pricing models และเราใช้แค่หนึ่งอัน"

EC2 pricing ใช้กับกลยุทธ์การจองห้องโรงแรมได้อย่างน่าแปลกใจ:

**On-Demand**: เดินไปที่ front desk โดยไม่มีการจอง คุณจ่ายราคาเต็ม rack rate แต่คุณสามารถ check out เมื่อใดก็ได้ เหมาะสำหรับการพักที่ไม่แน่นอน

**Reserved Instances/Savings Plans**: จองห้องล่วงหน้าทั้งปี คุณได้ส่วนลดมาก — 30-72% ลด — เพื่อแลกกับการให้สัญญาว่าจะใช้

**Spot Instances**: เอาห้องที่ขายไม่ออกของโรงแรมในราคาที่ลดอย่างหนักที่โรงแรมกำหนด — ไม่ต้องต่อรอง โรงแรมตั้งราคาตามว่าห้องว่างมากแค่ไหน ลดได้ถึง 90% แต่โรงแรมสามารถขอให้คุณออกได้โดยแจ้งล่วงหน้า 2 นาทีหากต้องการห้องสำหรับลูกค้าที่จ่ายเต็มราคา (หลายปีก่อนคุณต้อง *ประมูล* Spot capacity; AWS ยกเลิกการประมูลในปี 2017 — คุณเพียงแค่จ่ายราคา Spot ปัจจุบัน)

**Dedicated Hosts**: เช่าทั้งชั้นของโรงแรมเพื่อตัวเองเท่านั้น ไม่มีการแชร์กับแขกอื่น แพงกว่าอย่างมีนัยสำคัญ จำเป็นเมื่อ software licensing หรือกฎระเบียบด้านการปฏิบัติตามห้ามแชร์ physical host

แต่ละ model มีกรณีการใช้งาน ความผิดพลาดที่ Nimbus กำลังทำ: ใช้ On-Demand สำหรับทุกอย่าง รวมถึง workload ที่ทำงาน 24/7 และคาดเดาได้อย่างสมบูรณ์

**On-Demand Instances: ความยืดหยุ่นสูงสุด ต้นทุนสูงสุด**

**เมื่อควรใช้**:

- Workload ที่คาดเดาไม่ได้ (traffic spikes ที่คาดการณ์ไม่ได้)
- Development และ testing (เริ่มและหยุดบ่อย)
- Workload ระยะสั้น (รัน experiment หนึ่งสัปดาห์)
- การ deploy แรก (ก่อนที่คุณเข้าใจรูปแบบการใช้งาน)

**เมื่อไม่ควรใช้**:

- Production workload ที่คงที่ที่คุณรู้ว่าจะทำงานมากกว่าหนึ่งปี
- อะไรก็ตามที่มี baseline load ที่คาดเดาได้

**EC2 Hibernation: การหยุดชั่วคราวโดยไม่สูญเสียสถานะ**

เทคนิคการ optimize ต้นทุนอย่างหนึ่งที่ไม่ค่อยได้รับความสนใจคือ **EC2 Hibernation** เมื่อคุณหยุด instance ปกติ เนื้อหาใน RAM จะหายไป — การเริ่มต้นครั้งต่อไปคือ cold start ระบบปฏิบัติการบูต แอปพลิเคชันเริ่มต้น database connections ถูกสร้างขึ้นใหม่ สำหรับ production web servers ส่วนใหญ่ นี่ไม่เป็นไร สำหรับ workload บางอย่าง มันแพง

เมื่อคุณ hibernate instance เนื้อหาใน RAM จะถูกบันทึกไปยัง EBS root volume ก่อน shutdown ในการเริ่มต้นครั้งต่อไป instance จะกลับมาทำงานต่อในจุดที่ค้างไว้พอดี — processes ทำงาน connections ถูกสร้าง สถานะแอปพลิเคชันยังคงอยู่ — ในเวลาเพียงเศษเสี้ยวของเวลาที่ cold start จะใช้ มันมีประโยชน์เป็นพิเศษสำหรับงานวิเคราะห์ที่ทำงานนานๆ ที่คุณต้องการหยุดชั่วคราวข้ามคืนโดยไม่สูญเสียสถานะ หรือสำหรับ development instances ที่ใช้เวลาหลายนาทีในการบูตและกำหนดค่า environment

"Hibernate มันสิ"

ด้วย hibernation instance ของ Leo หยุดชั่วคราวเมื่อสิ้นวัน บันทึก RAM ไปยัง EBS root volume และกลับมาทำงานต่อในไม่ถึง 90 วินาทีในเช้าวันถัดไป Session การวิเคราะห์ดำเนินต่อไปในจุดที่เขาค้างไว้พอดี

ข้อกำหนดของ hibernation: hibernation ต้อง **เปิดใช้งานตอน launch** — คุณไม่สามารถเปิดมันสำหรับ instance ที่กำลังทำงานอยู่แล้วได้ (Leo ต้อง relaunch กล่อง data science ของเขาจาก AMI เพื่อให้ได้มันมา) Instances ต้องมี RAM ไม่เกิน 150 GB (เนื้อหาใน RAM ต้องพอดีกับ EBS root volume) root volume ต้องใหญ่พอที่จะเก็บทั้ง OS และ RAM dump และ root volume ต้องเข้ารหัส (hibernation บันทึกข้อมูล in-memory ที่ละเอียดอ่อนลงดิสก์) Bare-metal instances และ instances ที่มี RAM มากกว่า 150 GB ไม่รองรับ hibernation ข้อจำกัดอีกหนึ่งอย่าง: instance สามารถ hibernate ได้นานสุด **60 วัน** — หลังจากนั้นต้องเริ่ม หยุด หรือ terminate; มันนอนหลับตลอดไปไม่ได้

มีเหตุผลที่รายการ "เมื่อไม่ควรใช้" สำคัญ: ถ้าคุณรัน instances เดียวกันมาหกเดือนและคุณคาดเดาได้ว่ามันจะรันต่อไป ทุกเดือนบน On-Demand คือเดือนที่คุณจ่ายราคาแบบ walk-in สำหรับห้องที่คุณครอบครองถาวร

**Reserved Instances: การให้สัญญาหนึ่งปี**

**Reserved Instances (RIs)** คือข้อผูกมัดด้านการเรียกเก็บเงิน — คุณตกลงที่จะใช้ instance type เฉพาะใน region เฉพาะเป็นเวลา 1 หรือ 3 ปี เพื่อแลกกับ AWS คิดอัตรารายชั่วโมงที่ต่ำกว่า

**ระดับส่วนลด**:

- 1 ปี, No Upfront: ส่วนลดประมาณ 30-40% เทียบกับ On-Demand
- 1 ปี, Partial Upfront: ส่วนลดประมาณ 35-45% (จ่ายบางส่วนตอนนี้ น้อยลงต่อชั่วโมง)
- 1 ปี, All Upfront: ส่วนลดประมาณ 40-50% (จ่ายทั้งปีตอนนี้)
- 3 ปี, All Upfront: ส่วนลดประมาณ 55-72% (ส่วนลดสูงสุด ข้อผูกมัดสูงสุด)

**Standard vs Convertible RIs**:

- **Standard**: ล็อคกับ instance type และ region ที่แน่นอน สามารถขายบน Reserved Instance Marketplace ได้หากไม่ต้องการอีก
- **Convertible**: สามารถเปลี่ยน instance type, OS และ tenancy ได้ในช่วงระยะเวลาที่กำหนด ส่วนลดน้อยกว่า Standard (สูงสุด ~66% เทียบกับ 72%)

**Spot Instances: ส่วนลด 90%**

**Spot Instances** ใช้ EC2 capacity สำรองของ AWS เมื่อ AWS มีเซิร์ฟเวอร์ที่ไม่ได้ใช้งาน คุณสามารถเช่าได้ในราคา 60-90% ต่ำกว่า On-Demand เมื่อ AWS ต้องการ capacity กลับ (สำหรับลูกค้า On-Demand หรือ Reserved) พวกเขาให้การแจ้งเตือน 2 นาทีและยุติ instance ของคุณ

คุณอาจสงสัยว่า: ใครจะออกแบบระบบรอบ instances ที่สามารถหายไปพร้อมการแจ้งเตือนสองนาที? คำตอบคือ: ใครก็ตามที่งานสามารถเริ่มใหม่ตั้งแต่ต้นได้ Batch jobs, analytics, rendering pipelines — ไม่มีอันไหนต้องการให้ instance เฉพาะที่เริ่มงานเป็นตัวที่ทำงานเสร็จ การแจ้งเตือน 2 นาทีเพียงพอที่จะบันทึก checkpoint, drain connections และออกอย่างสะอาด

ความเสี่ยงจากการหยุดชะงักคือลักษณะที่กำหนด Spot Instances เหมาะสำหรับ:

- **Fault-tolerant workloads**: ถ้า instance ถูกยุติระหว่าง task งานสามารถเริ่มต้นใหม่โดยไม่ทำอะไรเสียหาย
- **Stateless processing**: การปรับขนาดรูปภาพ การเข้ารหัสวิดีโอ batch analytics, ML training
- **Batch jobs ระยะสั้น**: การแจ้งเตือน 2 นาทีเพียงพอที่จะบันทึกสถานะและ checkpoint
- **Auto Scaling mixed fleets**: ใช้ Spot สำหรับส่วนใหญ่ของ ASG พร้อม On-Demand เป็น baseline

สำหรับ Nimbus: Spot Instances สมเหตุสมผลสำหรับ batch analytics jobs ที่รันทุกคืน (ประมวลผลข้อมูลคำสั่งซื้อของวันเป็นรายงาน aggregated) ถ้า Spot Instance ถูกยุติระหว่าง job งานล้มเหลวแต่เริ่มต้นใหม่ตั้งแต่ต้นบน instance ใหม่ ข้อมูลใน S3 ปลอดภัย

**Spot Fleet Diversification**

Leo ได้เรียนรู้อีกหนึ่งอย่างจาก batch job ที่ถูกขัดจังหวะ: เมื่อคุณร้องขอ Spot Instance type เดียว คุณกำลังเดิมพันกับความพร้อมใช้งานของ type เฉพาะนั้นใน AZ นั้น ถ้า Spot capacity สำหรับ c5.2xlarge ใน us-west-2a หมด งานของคุณรอ — หรือล้มเหลว

**Spot Fleet** แก้ปัญหานี้โดยให้คุณระบุ instance types และ AZs หลายอันในคำขอเดียว AWS เติมเต็ม fleet จากการผสมผสานใดก็ตามที่มี capacity พร้อมใช้งานในราคาต่ำที่สุด

```
Spot Fleet request:
  Target capacity: 4 units
  Fleet diversification:
    - c5.2xlarge, us-west-2a
    - c5.2xlarge, us-west-2b
    - c5a.2xlarge, us-west-2a
    - m5.2xlarge, us-west-2a
    - c5d.2xlarge, us-west-2b
  Allocation strategy: diversified
```

ด้วย diversified fleet การขัดจังหวะใน instance type หรือ AZ หนึ่งกระทบเพียงส่วนหนึ่งของ fleet ส่วนที่เหลือยังคงทำงานต่อ สำหรับ Nimbus batch job การรัน Spot Fleet สี่ instance แทนที่จะเป็น instance ใหญ่เดียวหมายความว่าแม้การขัดจังหวะบางส่วนก็ยังให้งานเสร็จได้ — ช้ากว่า แต่ไม่ต้องเริ่มใหม่ทั้งหมด

Checkpointing ทำให้การขัดจังหวะจัดการได้ ไม่ใช่กำจัดมัน งานยังเริ่มต้นใหม่จาก checkpoint ล่าสุด และถ้าการเริ่มใหม่ตรงกับช่วงที่ราคา Spot พุ่ง instance ทดแทนอาจใช้เวลา 10 ถึง 20 นาทีในการพร้อมใช้งาน งานที่ครอบคลุมโดย checkpoint ล่าสุดแล้วจะถูกข้ามตอนเริ่มใหม่; งานตั้งแต่นั้นจะถูกทำซ้ำ overhead ของการทำซ้ำทั้งหมด: เล็ก แต่มีจริง

Spot Fleet แก้ปัญหาความพร้อมใช้งานได้อย่างหมดจด ด้วยการระบุ instance types ห้าอันใน AZs สามอัน Leo ลดความน่าจะเป็นของ capacity gap ที่สมบูรณ์ให้ใกล้ศูนย์ Allocation strategy ของ AWS — diversified — กระจาย four-instance fleet ทั่ว pools ดังนั้นการขัดจังหวะของ pool เดียวไม่สามารถหยุดงานได้ เมื่อ instance หนึ่งถูกขัดจังหวะ อีกสามตัวที่เหลือทำงานต่อ และ checkpoint หมายความว่า instance ทดแทนรับเฉพาะงานที่ instance ที่ถูกขัดจังหวะกำลังประมวลผลอยู่ระหว่างกลาง ตั้งแต่ต้นจนจบ งานไม่เคยพลาดกำหนดส่งรายงาน 7 โมงเช้าอีกเลย

"Diversification มีค่าใช้จ่ายในแง่ความซับซ้อนเท่าไหร่?" Maya ถามเมื่อ Leo บันทึกสิ่งนี้

"สามบรรทัดเพิ่มเติมในคำขอ Spot Fleet" Leo พูด "Processing code ไม่รู้หรือสนใจว่ามันรันบน instance type ไหน ความซับซ้อนอยู่ทั้งหมดใน fleet configuration ไม่ใช่ในแอปพลิเคชัน"

นั่นคือข้อได้เปรียบของการออกแบบแอปพลิเคชันให้เป็น stateless ตั้งแต่เริ่มต้น: การตัดสินใจเรื่อง scaling และ fault-tolerance กลายเป็นการตัดสินใจด้าน infrastructure ไม่ใช่การตัดสินใจด้านโค้ด


**Dedicated Hosts: ตัวเลือกด้านการปฏิบัติตามกฎระเบียบ**

Software licenses บางตัว (Oracle, Windows Server ในบางการกำหนดค่า) มีราคาต่อ physical socket หรือ core เมื่อคุณรัน software นี้บน shared host (ค่าเริ่มต้นสำหรับ EC2) คุณอาจจ่ายสำหรับ capacity ที่คุณไม่ได้ใช้

**Dedicated Hosts** ให้คุณเข้าถึง physical server ทั้งหมดสำหรับใช้งานของคุณ คุณสามารถนำ per-socket licenses ที่มีอยู่มาใช้ ไม่มี instances ของลูกค้า AWS รายอื่นทำงานบน hardware เดียวกัน

Dedicated Hosts แพงกว่า EC2 มาตรฐานอย่างมีนัยสำคัญ พวกมันคือเครื่องมือด้านการปฏิบัติตามกฎระเบียบและ licensing ไม่ใช่เครื่องมือ optimize ต้นทุน

Nimbus ไม่มีข้อกำหนด licensing ที่ต้องการ Dedicated Hosts แอปพลิเคชัน cloud-native ส่วนใหญ่ไม่มี

**ความผันแปร: เมื่อข้อผูกมัดย้อนกลับมาทำร้าย**

ถ้า workload ของคุณคาดเดาได้และคงที่เป็นเวลา 12 เดือน Reserved Instances ให้ส่วนลดสูงสุด — แต่ถ้าความต้องการ instance type ของคุณอาจเปลี่ยนแปลงอย่างมีนัยสำคัญในช่วงเวลานั้น การล็อคนั้นจะทำให้คุณเสียความยืดหยุ่นที่มีค่ามากกว่าผลต่างของราคา Convertible RIs แก้ปัญหานั้นได้บางส่วน แต่ในส่วนลดที่ลดลง Compute Savings Plans แก้ปัญหาส่วนใหญ่ ที่ส่วนลดสูงสุดต่ำกว่า Standard RIs เล็กน้อย

ถ้าคุณใช้ Spot Instances สำหรับ fault-tolerant batch jobs คุณสามารถประหยัด 60-90% — แต่ถ้า instances เดียวกันให้บริการ live user requests การขัดจังหวะกลาง request หมายถึง transactions ที่ล้มเหลวและลูกค้าที่ไม่พอใจ การทนต่อการขัดจังหวะของ workload คือตัวแปรที่ตัดสิน

มีกรณีตัวเลือกผิดที่ละเอียดอ่อนกว่า: การ over-commit Savings Plan ถ้าคุณซื้อ Compute Savings Plan $3.00/ชั่วโมงเพราะการใช้ compute ของคุณเฉลี่ย $3.00/ชั่วโมงในไตรมาสที่แล้ว แล้ว optimize บริการของคุณในไตรมาสนี้ (ลดการใช้รวมเหลือ $1.80/ชั่วโมง) คุณจ่าย $3.00/ชั่วโมงที่ให้สัญญาไว้ไม่ว่าอย่างไร ช่องว่าง $1.20/ชั่วโมงคือการสูญเปล่า (สังเกตว่าการย้าย EC2 workloads ไปยัง Fargate หรือ Lambda จะ *ไม่* ทำให้ Compute Savings Plan เคว้ง — มันครอบคลุมทั้งสาม ความเสี่ยงในการเคว้งคือการลดการใช้งานจริง หรือการล็อค family ด้วย EC2 Instance Savings Plans และ RIs) นี่คือเหตุผลที่กลยุทธ์พื้นสำคัญ: ให้สัญญากับขั้นต่ำของคุณ ไม่ใช่ค่าเฉลี่ย และทบทวนทุกไตรมาส

กฎคือ: ให้สัญญากับสิ่งที่คุณแน่ใจ ใช้ On-Demand สำหรับสิ่งที่คุณไม่แน่ใจ ใช้ Spot เฉพาะสำหรับสิ่งที่รอดจากการหยุดกะทันหันได้

**การสร้าง Mixed Fleet**

แนวทางที่มีวุฒิภาวะ: ใช้ pricing models หลายอันร่วมกัน

สำหรับ API fleet ของ Nimbus:

- **Baseline load (4 instances ที่ทำงานตลอดเวลา)**: ครอบคลุมด้วยข้อผูกมัด Savings Plan
- **Peak ที่คาดเดาได้ (2 instances เพิ่มเติมในช่วงเวลาทำการ)**: ครอบคลุมด้วย Savings Plan ถ้าข้อผูกมัดครอบคลุม มิฉะนั้น On-Demand
- **Traffic spike overflow**: Spot Instances (ยอมรับได้เพราะ API servers เป็น stateless — requests กระจายไปหาก instance ถูกยุติ)

ผลลัพธ์: fleet ที่ optimize ต้นทุนในทุกชั้น — committed pricing สำหรับส่วนที่คาดเดาได้ On-Demand สำหรับการเติบโตที่คาดเดาไม่ได้ Spot สำหรับ burst capacity

**การติดตามการใช้ประโยชน์ Savings Plan**

การซื้อ Savings Plan ไม่ใช่จุดสิ้นสุดของงาน มันคือจุดเริ่มต้นของพันธะที่เกิดซ้ำ: การรู้ว่าข้อผูกมัดกำลังถูกใช้คุ้มค่าหรือไม่

Tom ตั้งการเตือนในปฏิทินสำหรับวันจันทร์แรกของทุกไตรมาส: การทบทวนการใช้ประโยชน์ Savings Plan เครื่องมือคือ AWS Cost Explorer โดยเฉพาะแท็บ "Savings Plans" ภายใต้ "Reservations and Savings Plans" ซึ่งแสดงสามตัวเลขที่เขาสนใจ:

- **อัตราการใช้ประโยชน์ (Utilization rate)**: committed spend กี่เปอร์เซ็นต์ที่ถูกจับคู่จริงโดยการใช้งานที่เข้าเกณฑ์? ตัวเลขต่ำกว่า 100% หมายความว่าเขากำลังจ่ายสำหรับข้อผูกมัดที่ไม่ได้ถูกใช้
- **อัตราการครอบคลุม (Coverage rate)**: การใช้ EC2 ที่เข้าเกณฑ์กี่เปอร์เซ็นต์ที่ถูกครอบคลุมโดย Savings Plan เทียบกับการรันที่อัตรา On-Demand? ตัวเลขต่ำกว่า 80% หมายความว่ามีการใช้งานที่ไม่ได้ครอบคลุมที่ข้อผูกมัดที่ใหญ่กว่าจะจับได้
- **On-Demand spend**: ส่วนของ EC2 spend ที่ไม่ได้ครอบคลุมโดย Savings Plan ใดๆ ถ้าสิ่งนี้กำลังเติบโต ก็แสดงว่า Savings Plan มีขนาดเล็กเกินไป หรือมี workloads ใหม่ที่ถูกเพิ่มนอกขอบเขตของข้อผูกมัด

ที่การทบทวนรายไตรมาสครั้งแรก ตัวเลขเป็นแบบนี้:

- Utilization: 97% สามเปอร์เซ็นต์ของ committed spend ไม่ได้ถูกจับคู่ — $9.90 ต่อเดือนบนข้อผูกมัด $330/เดือน นั่นยอมรับได้; มันหมายความว่าข้อผูกมัดถูกตั้งสูงกว่าการใช้งานพื้นจริงเล็กน้อย ซึ่งเป็นความตั้งใจ
- Coverage: 84% สิบหกเปอร์เซ็นต์ของการใช้ EC2 ที่เข้าเกณฑ์รันบน On-Demand นั่นคือ burst capacity — instances ส่วนเกินที่สปินขึ้นในช่วง traffic spikes และไม่ได้ครอบคลุมโดยข้อผูกมัด
- On-Demand EC2 spend: $147/เดือน Spot Instances (ไม่ครอบคลุมโดย Savings Plans คิดราคาแยก) คิดเป็นส่วนใหญ่ของที่เหลือ

"Utilization 97% ดีต่อสุขภาพ" Tom พูด "มันหมายความว่าเราไม่ over-commit ถ้านี่คือ 80% ผมจะรู้ว่าเราซื้อมากเกินไป"

"แล้ว coverage 84% ล่ะ?" Maya ถาม

"นั่นก็โอเคเช่นกัน 16% ที่เป็น On-Demand คือ burst capacity — instances ที่รันเป็นชั่วโมงในช่วง peak ไม่ใช่ทั้งวัน เราจะต้องซื้อข้อผูกมัด Savings Plan เพิ่มอย่างมีนัยสำคัญเพื่อครอบคลุมพวกมัน และมันอาจไม่คุ้ม" เขารันตัวเลข: On-Demand instances ที่ไม่ครอบคลุมรันราว 40 ชั่วโมงต่อเดือนที่ $0.101/ชั่วโมงต่อ instance การครอบคลุมพวกมันด้วย Savings Plan จะต้องใช้ข้อผูกมัดที่เราจะใช้ประโยชน์ไม่เต็ม 90% ของเวลา ปล่อยให้พวกมันเป็น On-Demand ดีกว่า

ที่การทบทวนรายไตรมาสครั้งที่สอง ผ่านไปหกเดือน มีหนึ่งเมตริกเปลี่ยน: On-Demand EC2 spend เติบโตเป็น $290/เดือน ฟีเจอร์ Nimbus Instant ได้เปิดตัว และมี background service instances ใหม่หลายตัวถูกเพิ่มโดยที่ Tom ไม่ทันสังเกต

"สาม instances นี้" Tom พูด ชี้ไปที่ Cost Explorer breakdown "พวกมันรันบน On-Demand มาสามเดือน ถ้าพวกมันจะรันต่อ เราควรเพิ่มพวกมันเข้าในข้อผูกมัด Savings Plan"

การทบทวนรายไตรมาสจับมันได้ ถ้าไม่มีการทบทวน สาม instances นั้นจะรันที่ราคา walk-in ต่อไปอย่างไม่มีกำหนด

"คุณปรับข้อผูกมัดอย่างไร?" Priya ถาม

"คุณซื้อ Savings Plan ใหม่เพิ่มเติมบนตัวที่มีอยู่" Tom พูด "Savings Plans ซ้อนกันได้ ผมจะเพิ่ม Compute Savings Plan $0.10/ชั่วโมงสำหรับ baseline ใหม่ แผน $0.45/ชั่วโมงที่มีอยู่ดำเนินต่อจนกว่าเทอมสามปีของมันจะสิ้นสุด แผนใหม่เริ่มเทอมสามปีของตัวเอง"

"ดังนั้นเราจะมี Savings Plans สองอันที่ทับซ้อนกัน"

"ใช่ พวกมันใช้แยกกันกับการใช้งานที่เข้าเกณฑ์ใดก็ตามที่มี AWS จับคู่พวกมันตามลำดับจากที่เป็นประโยชน์มากที่สุดไปน้อยที่สุด"

"เราคิดถึงสิ่งที่จะเกิดขึ้นถ้าเราขาย background services ตัวหนึ่งในปีหน้าไหม?" Priya ถาม "เราให้สัญญา $0.55/ชั่วโมงเป็นเวลาสามปี"

"นั่นคือความเสี่ยงของเทอมสามปี" Tom พูด "ซึ่งเป็นเหตุผลที่ข้อผูกมัดใหม่เล็กลง — ผมกำลังให้สัญญากับพื้นของ workloads ใหม่ ไม่ใช่ค่าเฉลี่ย ถ้าเราปลด service หนึ่งและการใช้งานลดลง services ที่เหลือก็ยังควรใช้จำนวนที่ให้สัญญาเต็ม"

วินัยของการทบทวนรายไตรมาสไม่หรูหรา มันคือสิบห้านาทีใน Cost Explorer สามตัวเลขที่ตรวจสอบ การตัดสินใจที่ทำหรือเลื่อนออกไป แต่ตลอดสามปี วินัยนั้นคือความแตกต่างระหว่าง Savings Plan ที่ให้การใช้ประโยชน์ 90%+ — การประหยัดที่แท้จริง — กับตัวที่เคลื่อนเข้าสู่การสูญเปล่าบางส่วนขณะที่ infrastructure วิวัฒน์ไปรอบๆ มัน

## จุดแข็งและข้อจำกัด

**On-Demand**: ไม่มีข้อผูกมัด ราคาเต็ม ใช้สำหรับ workload ที่คาดเดาไม่ได้หรือระยะสั้น

**Reserved Instances**: ส่วนลดสูงสุด 72% ล็อคกับ instance type/region/OS เฉพาะ ขาย capacity ที่ไม่ได้ใช้บน RI Marketplace

**Savings Plans**: ส่วนลดสูงสุด 66-72% ยืดหยุ่นกว่า RIs (Compute Savings Plans ใช้กับ instance type ใดก็ได้) ใช้โดยอัตโนมัติกับการใช้งานที่ตรงกัน

**Spot Instances**: ส่วนลดสูงสุด 90% ความเสี่ยงจากการหยุดชะงัก 2 นาที เหมาะสำหรับ fault-tolerant, stateless, workload ที่หยุดชะงักได้เท่านั้น

**Dedicated Hosts**: Physical server เต็มรูปแบบ แพงที่สุด จำเป็นสำหรับ licensing หรือสถานการณ์ด้านการปฏิบัติตามกฎระเบียบบางอย่าง

## สรุป

Tom ใช้เวลาที่เหลือของวันเสาร์ในการแมป Nimbus workload ทุกตัวเข้ากับ pricing model ที่เหมาะสมที่สุด — baseline ไปยัง Savings Plans, nightly batch jobs ไปยัง Spot, overflow ที่คาดเดาไม่ได้ไปยัง On-Demand แบบฝึกหัดนี้เปลี่ยนสามเดือนของการจ่ายราคาแบบ walk-in เป็นกลยุทธ์ที่จงใจ ตัวเลข เมื่อคำนวณแล้ว ยากที่จะเพิกเฉย

- EC2 pricing มีสี่ models: **On-Demand** (ราคาเต็ม ไม่มีข้อผูกมัด), **Reserved Instances/Savings Plans** (committed spend เพื่อส่วนลดมาก), **Spot** (spare capacity ที่ 60-90% ลด หยุดชะงักได้), **Dedicated Hosts** (ความเป็นส่วนตัวของ physical server)
- **Savings Plans** โดยทั่วไปดีกว่า Reserved Instances เพื่อความยืดหยุ่น
- **Spot Instances** ต้องการ fault-tolerant, stateless workloads — เฉพาะสำหรับ batch jobs, ML training และการประมวลผลที่หยุดชะงักได้
- **Checkpointing ไปยัง durable storage** (S3) จำเป็นสำหรับ Spot-based batch jobs — งานที่ถูกขัดจังหวะควรทำงานต่อจาก checkpoint ล่าสุด ไม่ใช่เริ่มใหม่จากศูนย์
- **Spot Fleet diversification** ทั่ว instance types และ AZs หลายอันลดความเสี่ยงการขัดจังหวะและมักให้ราคาที่ดีกว่า
- กลยุทธ์ optimal คือ **mixed fleet**: Savings Plans สำหรับ baseline, On-Demand สำหรับการเติบโตที่คาดเดาไม่ได้, Spot สำหรับ interruptible batch work
- ทบทวน pricing models เมื่อ workload ทำงานอย่างต่อเนื่องมากกว่า 3 เดือน นั่นคือเมื่อ On-Demand เริ่มเป็นการสูญเสีย
- **ทบทวนข้อผูกมัด Savings Plan ทุกไตรมาส** — ให้สัญญากับพื้นของคุณ ไม่ใช่ค่าเฉลี่ย และปรับเมื่อรูปแบบการใช้งานเปลี่ยน

- **Savings Plans vs Reserved Instances**: Savings Plans ยืดหยุ่นกว่า (ใช้กับ EC2 instance ใดก็ได้สำหรับ Compute Savings Plans) Reserved Instances ล็อคกับ instance type เฉพาะ สถานการณ์สอบ: "ต้องการความยืดหยุ่นสูงสุดในขณะที่ยังได้ส่วนลด" → Savings Plans "รู้ instance type ที่แน่นอนเป็นเวลา 3 ปี" → Standard RI เพื่อส่วนลดสูงสุด
- **สัญญาณ Spot**: "คำนึงถึงต้นทุน", "fault-tolerant", "batch processing", "รับการหยุดชะงักได้", "stateless workloads", "ML training" → Spot
- **การจัดการการหยุดชะงักของ Spot**: Spot instances ได้รับการแจ้งเตือน 2 นาทีก่อนยุติ แอปพลิเคชันของคุณต้องจัดการเรื่องนี้อย่างสง่างาม (บันทึกสถานะ drain connections ออกอย่างสะอาด)
- **On-Demand vs Spot สำหรับ web servers**: Web servers ที่ให้บริการ live user traffic ไม่ควรใช้ Spot (การหยุดชะงักทำให้ requests ล้มเหลว) ใช้ On-Demand หรือ Savings Plans สำหรับ web tier
- **EC2 Savings Plans vs Compute Savings Plans**: EC2 Savings Plans ใช้กับ instance family และ region เฉพาะ (ส่วนลดสูงกว่า) Compute Savings Plans ใช้กับ EC2 instance ใดก็ได้, Lambda และ Fargate (ส่วนลดสูงสุดน้อยกว่า ยืดหยุ่นกว่า)
- **RI Marketplace**: Standard Reserved Instances ที่ไม่ได้ใช้สามารถขายให้ลูกค้า AWS รายอื่นได้ Convertible RIs ขายไม่ได้
- **Hibernation:** บันทึกเนื้อหา RAM ไปยัง EBS root volume เมื่อหยุด; กู้คืนเมื่อเริ่ม Instance กลับมาทำงานต่อเร็วกว่า cold start โดยมี processes และสถานะครบถ้วน ใช้เมื่อต้องรักษาสถานะ instance ระหว่าง sessions ต้องการ: เปิดใช้งานตอน launch (เพิ่มใน instance ที่มีอยู่ไม่ได้), RAM ≤ 150 GB, encrypted EBS root volume, ไม่มีให้สำหรับ bare-metal instances; hibernate ได้สูงสุด 60 วัน สัญญาณสอบ: "กลับมาทำงาน instance อย่างรวดเร็วโดยรักษาสถานะ in-memory" หรือ "development instance ใช้เวลาเริ่มต้นนานเกินไป" → Hibernation

**แบบฝึกหัดที่ 2 — สถานการณ์ SAA-C03**

*สถานการณ์*: บริษัทสื่อรัน pipeline การ transcode วิดีโอที่แปลงวิดีโอที่ upload มาเป็นหลายรูปแบบ Transcoding jobs ทำงานต่อเนื่องทุกครั้งที่มีวิดีโอ upload มา (ทำงาน 24/7, ปริมาณผันผวน) แต่ละ job ใช้เวลา 5-30 นาที ถ้า transcoding job ถูกขัดจังหวะ job สามารถเริ่มต้นใหม่ตั้งแต่ต้นโดยไม่เสียข้อมูล บริษัทต้องการลดต้นทุน

EC2 pricing model ใดที่ตอบสนองความต้องการเหล่านี้ได้ดีที่สุด?

A) On-Demand instances ใน Auto Scaling Group  
B) Reserved Instances (1-year, All Upfront)  
C) Spot Instances พร้อม Spot Fleet สำหรับ instance diversification อัตโนมัติ  
D) Dedicated Hosts พร้อม media software licenses ที่มีอยู่ของบริษัท

**คำใบ้ที่ 1**: "สามารถเริ่มต้นใหม่ตั้งแต่ต้นโดยไม่เสียข้อมูล" — นี่คือวลีสำคัญที่เปิดใช้ pricing model เฉพาะ

**คำใบ้ที่ 2**: "ลดต้นทุน" พร้อม workload ที่หยุดชะงักได้ชี้ไปยังตัวเลือกที่มีส่วนลดสูงสุด

**คำใบ้ที่ 3**: Spot Fleet ร้องขอ instances จาก instance types และ AZs หลายอัน ลดโอกาสการหยุดชะงัก

**คำตอบ**: C

**คำอธิบาย**: Transcoding jobs เป็น fault-tolerant — สามารถเริ่มต้นใหม่ได้ถ้าถูกขัดจังหวะ ทำให้เหมาะสำหรับ Spot Instances ซึ่งมีส่วนลด 60-90% เหนือ On-Demand Spot Fleet กระจายไปยัง instance types และ Availability Zones ลดความน่าจะเป็นของการหยุดชะงักจำนวนมาก

**ทำไมไม่ใช่ A?** On-Demand คือตัวเลือกที่มีต้นทุนสูงที่สุด สำหรับ workload ที่ทำงานต่อเนื่องและ fault-tolerant นี้เป็นการสูญเสีย

**ทำไมไม่ใช่ B?** Reserved Instances ให้ส่วนลด 50-72% แต่ไม่ให้ส่วนลดที่อาจได้ถึง 90% ของ Spot สำหรับ fault-tolerant workloads นอกจากนี้ RIs ใช้สำหรับ workload ที่คงที่และคาดเดาได้ Spot ใช้สำหรับ interruptible batch processing โดยเฉพาะ

**ทำไมไม่ใช่ D?** Dedicated Hosts ใช้สำหรับการปฏิบัติตาม licensing ไม่ใช่การ optimize ต้นทุน พวกมันคือตัวเลือกที่แพงที่สุด

**แบบฝึกหัดที่ 3 — ความท้าทายด้านสถาปัตยกรรม** *(ไม่บังคับ)*

Infrastructure ของ Nimbus มี workloads เหล่านี้:

1. API servers: 6 instances ทำงาน 24/7 คงที่มา 2 ปีแล้ว ใช้ r6g.large
2. Nightly analytics batch jobs: 4 instances ทำงาน 3AM-6AM ทุกคืน ใช้ instance type เดิมเสมอ
3. Testing environment: 2 instances ใช้โดยวิศวกร 9 AM-6 PM ในวันทำการ
4. Traffic spike overflow: 0-8 instances spin up ในช่วง peak hours คาดเดาไม่ได้อย่างสมบูรณ์

ออกแบบกลยุทธ์ pricing ที่ optimal สำหรับ workload แต่ละประเภท จำนวน Savings Plan commitment ที่ครอบคลุม workloads 1 และ 2 จะเป็นเท่าไหร่? สำหรับ workload ที่ 3 มีกลยุทธ์ที่ฉลาดกว่า On-Demand ไหม?
