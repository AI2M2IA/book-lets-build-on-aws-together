# บทที่ 5: ตู้เก็บเอกสารที่อยู่ในคลาวด์

Leo กำลังทำความสะอาด EC2 instance ตอนเก้าโมงเช้าเมื่อเขาพบโฟลเดอร์นั้น

ออฟฟิศเงียบ Maya ยังไม่มา กาแฟยังกำลังชง นอกหน้าต่าง คนเดินทางช่วงเช้ากำลังทยอยผ่านไป Leo ใส่หูฟังและกำลังเลื่อนดูไดเรกทอรีต่าง ๆ เมื่อเขาหยุด

แปดร้อยไฟล์ ทั้งหมดเป็นรูปเมนู ทั้งหมดอยู่บนเครื่องเดียวโดยไม่มีข้อมูลสำรอง

EC2 instance ที่แอป Nimbus รันอยู่ถูกอัปเกรดไปครั้งหนึ่งตั้งแต่การหยุดทำงานสิบสองนาที แต่พื้นที่จัดเก็บรูปไม่เคยถูกย้าย arepa กรอบ ๆ ทุกชิ้น จานแซลมอนย่างทุกจาน ชามสลัดที่จัดอย่างสมบูรณ์แบบทุกชาม — นั่งอยู่บนเครื่องเสมือนเครื่องเดียวที่พวกเขาพิสูจน์แล้วว่าล่มได้โดยไม่มีการเตือน

และถ้าเครื่องนั้นถูกรีสตาร์ท ปรับขนาด หรือเปลี่ยนทดแทนเมื่อไหร่?

หายไป

"จนถึงตอนนี้ลูกค้าอัปโหลดรูปไปกี่รูปแล้ว?" Maya ถาม เมื่อเธอมาถึง

Leo หันกลับมา "ประมาณแปดร้อย"

"แล้วจะเกิดอะไรขึ้นกับรูปแปดร้อยรูปนั้นถ้าเรารีสตาร์ทเซิร์ฟเวอร์?"

อีกหนึ่งช่วงหยุดที่มีความหมายของ Leo

บทนี้เกี่ยวกับว่าไฟล์อยู่ที่ไหนกันแน่ในคลาวด์

**ปัญหากับการเก็บไฟล์ "ไว้บนเซิร์ฟเวอร์"**

เมื่อคุณเก็บไฟล์ไว้บน EC2 instance โดยตรง — ภายในระบบไฟล์ของมัน — คุณกำลังผูกไฟล์เหล่านั้นไว้กับวงจรชีวิตของเครื่องเฉพาะนั้น

สิ่งนี้สร้างปัญหาหลายอย่าง:

**ชั่วคราวโดยธรรมชาติ** EC2 instance ถูกหยุด ยุติ เปลี่ยนทดแทนได้ ดิสก์ในเครื่องของมันไม่ได้มีไว้ให้ถาวร มันคือพื้นที่ทำงานชั่วคราว

**จุดล้มเหลวเดียว** ถ้า instance ล้มเหลว ไฟล์ก็ไปกับมัน ไม่มีความซ้ำซ้อน ไม่มีข้อมูลสำรอง เช้าวันร้ายเช้าเดียวและรูปเมนูแปดร้อยรูปก็หายไป

**แชร์ข้าม instance ไม่ได้** เมื่อคุณเพิ่มเซิร์ฟเวอร์ตัวที่สอง (ซึ่งคุณจะทำในบทที่ 7) มันจะมองไม่เห็นไฟล์ที่เก็บไว้บนดิสก์ของเซิร์ฟเวอร์ตัวแรก เซิร์ฟเวอร์สองตัวแยกจากกัน ผู้ใช้ที่อัปโหลดรูปอาจเห็นมัน ผู้ใช้อีกคนที่ไปเจอเซิร์ฟเวอร์อีกตัวอาจไม่เห็น

**ไม่มีการขยาย** พื้นที่ดิสก์ EC2 มีจำกัด ถ้าคุณเติมมันเต็ม คุณก็ต้องหยุดรับการอัปโหลดหรือดิ้นรนขยายพื้นที่จัดเก็บภายใต้ความกดดัน

Leo ไม่ได้พิจารณาว่าเกิดอะไรขึ้นเมื่อมีเซิร์ฟเวอร์หลายตัว เขาพูดถึงมันแบบไม่ตั้งใจกับ Priya

"เดี๋ยวนะ — ปัญหารูปจะทำงานยังไงกับเซิร์ฟเวอร์สองตัว?" Priya ถาม

"หมายความว่ายังไง?"

"ถ้าเรามีเซิร์ฟเวอร์ A และเซิร์ฟเวอร์ B หลัง load balancer" Priya พูด "และลูกค้าอัปโหลดรูป — คำขอของพวกเขาไปที่เซิร์ฟเวอร์ A ใช่ไหม? ดังนั้นรูปถูกบันทึกไว้บนดิสก์ของเซิร์ฟเวอร์ A ตอนนี้คำขอถัดไปของพวกเขาไปที่เซิร์ฟเวอร์ B เซิร์ฟเวอร์ B ไม่มีรูปนั้น ลูกค้าเห็นอะไร?"

Leo อ้าปาก จากนั้นก็ปิดมัน

"รูปที่แตก" เขาพูดในที่สุด

"หรือ error 404" Priya พูด "หรือถ้าแอปพยายามโหลดมันแล้วล่ม ก็หน้าแสดงข้อผิดพลาด"

เธอร่างแผน load-balancer บนไวท์บอร์ด — การเพิ่มเซิร์ฟเวอร์ตัวที่สองอยู่ในแผนงานอยู่แล้ว เมื่อมันเกิดขึ้น การอัปโหลดรูปทุกครั้งจะกลายเป็นการโยนเหรียญ: อัปโหลดไปเซิร์ฟเวอร์ A อาจถูกให้บริการจากเซิร์ฟเวอร์ B รูปหายไป ลูกค้าสับสน

"เราคงดีบักมันอยู่เป็นสัปดาห์ก่อนจะรู้ว่าอะไรผิด" Leo พูด

"เราคิดถึงเรื่องที่จะเกิดขึ้นเมื่อเราเปิด Auto Scaling แล้วจู่ ๆ มีเซิร์ฟเวอร์สามหรือสี่ตัวหรือยัง?" Priya ถาม "เราจะรูปหายตลอดเวลา"

นี่คือคลาสของบั๊กที่ไม่ปรากฏใน unit test มันปรากฏเฉพาะใน production ภายใต้โหลด เมื่อทราฟฟิกจริงกระจายข้ามเซิร์ฟเวอร์หลายตัว การแก้คือหยุดเก็บไฟล์ไว้บนเซิร์ฟเวอร์โดยสิ้นเชิง

มีโมเดลที่ดีกว่า AWS สร้างมันในปี 2006 และมันยังเป็นหนึ่งในบริการคลาวด์ที่ถูกใช้กว้างขวางที่สุดในโลก

**ฮาร์ดไดรฟ์ที่อยู่ออนไลน์**

ลองนึกภาพฮาร์ดไดรฟ์ที่อยู่บนอินเทอร์เน็ต — ตัวที่ขยายเพื่อเก็บได้มากเท่าที่คุณเคยต้องการ และเรียกเก็บเงินจากคุณเฉพาะสิ่งที่คุณใช้จริง คุณไม่เคยจัดสรรมัน คุณไม่เคยกังวลเรื่องพื้นที่หมด ถ้าคุณใส่รูปแปดร้อยรูปวันนี้และแปดล้านรูปในปีหน้า ไม่มีอะไรเปลี่ยนในฝั่งของคุณยกเว้นรายการในบิล

นั่นคือสิ่งที่ AWS เสนอ พวกเขาเรียกมันว่า **Amazon S3** — Simple Storage Service

S3 คือบริการ object storage ของ AWS มันไม่เหมือนระบบไฟล์เสียทีเดียว และไม่เหมือนฐานข้อมูลเสียทีเดียว มันเก็บไฟล์ — เรียกว่า object — ในคอนเทนเนอร์ที่ตั้งชื่อเรียกว่า bucket โมเดลนี้เรียบง่าย และความเรียบง่ายนั้นคือประเด็น

แนวคิดหลักใน S3 คือ **object**

object คือไฟล์ใด ๆ: รูปภาพ วิดีโอ PDF CSV ข้อมูลสำรอง ไฟล์บันทึก S3 ไม่สนใจประเภทหรือโครงสร้าง มันเก็บไบต์และคืนพวกมันเมื่อคุณขอ

object อยู่ภายใน **bucket** bucket เหมือนโฟลเดอร์ระดับบนสุด — คอนเทนเนอร์ที่ตั้งชื่อภายใน S3 ที่เก็บ object ของคุณ แต่ละ bucket มีชื่อที่ไม่ซ้ำกันทั่วโลก (ไม่มี bucket สองอันข้ามทุกบัญชี AWS ที่ใช้ชื่อเดียวกันได้) และมีอยู่ใน Region เฉพาะ

**S3 ทำงานอย่างไร**

คุณ **อัปโหลด** object ไปยัง bucket S3 ให้ **key** กับมัน — โดยพื้นฐานคือชื่อพาธเช่น `menus/restaurant-001/photo-arepa.jpg` key นั้นระบุ object ภายใน bucket อย่างไม่ซ้ำกัน

คุณ **ดาวน์โหลด** (หรือดึง) object โดยใช้ชื่อ bucket และ key

คุณยังสามารถทำให้ object เข้าถึงได้แบบสาธารณะ — หมายความว่าใครก็ตามที่มี URL สามารถดาวน์โหลดได้ นี่คือวิธีที่เว็บไซต์ส่วนใหญ่ให้บริการรูปภาพ: เก็บรูปใน S3 ทำให้มันสาธารณะ ฝัง URL ใน HTML ของคุณ

หรือคุณเก็บ object ไว้เป็นส่วนตัว — เข้าถึงได้เฉพาะคำขอที่ยืนยันตัวตนแล้ว นี่คือโมเดลที่ถูกต้องสำหรับข้อมูลลูกค้า ข้อมูลสำรอง และอะไรก็ตามที่อ่อนไหว

S3 ไม่ใช่ระบบไฟล์ ไม่มีโฟลเดอร์จริง `/` ในชื่อ key เป็นเพียงข้อตกลง — S3 ปฏิบัติต่อ key ทั้งหมดเป็นสตริงแบน ๆ แต่มันดูเหมือนโฟลเดอร์และเครื่องมือส่วนใหญ่นำเสนอมันเป็นโฟลเดอร์ ดังนั้นอย่ากังวลกับความแตกต่างนี้ในทางปฏิบัติ

มีคุณลักษณะการดำเนินงานไม่กี่อย่างของ S3 ที่สำคัญในทางปฏิบัติแต่ไม่ชัดเจนจากคำอธิบาย:

**ความไม่เปลี่ยนแปลงของ object (Object immutability)**: object ของ S3 ไม่ได้ถูกแก้ไขในที่ ถ้าคุณอัปเดตไฟล์ คุณอัปโหลดเวอร์ชันใหม่ของ object ด้วย key เดียวกัน S3 แทนที่ object เก่าด้วยอันใหม่ (หรือเมื่อเปิดใช้งาน versioning ก็เก็บทั้งคู่) ไม่เหมือนฐานข้อมูลที่คุณ `UPDATE` แถว object ของ S3 เป็นแบบเขียนครั้งเดียว อ่านได้หลายครั้ง สำหรับไฟล์ข้อความและเอกสารที่คุณแก้ไขบ่อย นี่โอเค — แค่อัปโหลดเวอร์ชันใหม่ สำหรับไฟล์ที่ใหญ่มากที่คุณต้องการอัปเดตเพียงบางส่วนของเนื้อหา โมเดล object ของ S3 หมายความว่าคุณอัปโหลดทั้งไฟล์ใหม่ทุกครั้ง

**ความสอดคล้องแบบ strong read-after-write**: ตั้งแต่ธันวาคม 2020 S3 ให้ความสอดคล้องแบบ strong สำหรับทุก object — การเขียนใหม่มองเห็นได้ทันทีสำหรับการอ่านที่ตามมา ก่อนปี 2020 S3 มีความสอดคล้องแบบ eventual สำหรับบางการดำเนินการ ซึ่งทำให้เกิดบั๊กแยบยลในแอปพลิเคชันที่เขียน object แล้วพยายามอ่านมันทันที การปรับปรุงโมเดลความสอดคล้องขจัดคลาสของบั๊กนี้ออกไป

**URL ของ object**: ทุก object ของ S3 มี URL สำหรับ object สาธารณะ มันมีหน้าตาเป็น: `https://bucket-name.s3.region.amazonaws.com/key/path` สำหรับ object ส่วนตัว คุณสร้าง pre-signed URL ที่มีข้อมูลการยืนยันตัวตนและหมดอายุหลังจากเวลาที่กำหนดได้ ทั้งสองรูปแบบ URL เป็นวิธีที่แอปพลิเคชันและเบราว์เซอร์ดึง object จริง ๆ — ไม่มีโปรโตคอลกรรมสิทธิ์เข้ามาเกี่ยวข้อง

**ไม่มีไดเรกทอรีให้สร้าง**: เพราะ S3 ไม่มีโฟลเดอร์จริง จึงไม่มีการดำเนินการสร้างไดเรกทอรี คุณแค่อัปโหลด object ด้วย key ที่มีคำนำหน้าพาธ "โฟลเดอร์" ปรากฏโดยอัตโนมัติในคอนโซลเมื่อ object ที่มีคำนำหน้านั้นมีอยู่ และหายไปโดยอัตโนมัติเมื่อ object ทั้งหมดที่มีคำนำหน้านั้นถูกลบ

**ทำไม S3 ถึงต่างจากฮาร์ดไดรฟ์ธรรมดา**

สามสิ่งที่ทำให้ S3 ต่างจากการจัดเก็บไฟล์บน EC2 instance โดยพื้นฐาน:

**ความทนทาน (Durability)** AWS ออกแบบ S3 สำหรับความทนทาน 99.999999999% (สิบเอ็ดเก้า) นั่นหมายความว่าถ้าคุณเก็บ object สิบล้านชิ้น คุณอาจคาดว่าจะเสีย object หนึ่งชิ้นทุกหมื่นปีเนื่องจากความล้มเหลวของฮาร์ดแวร์ พวกเขาบรรลุสิ่งนี้ด้วยการเก็บสำเนาของทุก object หลายชุดข้าม Availability Zone อย่างน้อยสามแห่งโดยอัตโนมัติ

แต่ความทนทานป้องกันความล้มเหลวของฮาร์ดแวร์ — ไม่ใช่การที่คุณลบบางอย่างโดยไม่ตั้งใจ นั่นคือสิ่งที่ versioning มีไว้

มีความแตกต่างที่สำคัญระหว่าง **ความทนทาน** กับ **ความพร้อมใช้งาน** ความทนทานเกี่ยวกับว่าข้อมูลของคุณยังมีอยู่หรือไม่ ความพร้อมใช้งานเกี่ยวกับว่าคุณเข้าถึงมันได้ตอนนี้หรือไม่ S3 Standard ให้ความทนทาน 99.999999999% และความพร้อมใช้งาน 99.99% ตัวเลขความทนทานสูงแบบเข้าใจยากเกือบ ตัวเลขความพร้อมใช้งาน 99.99% เป็น *เป้าหมายการออกแบบ* — ประมาณ 52 นาทีของการไม่พร้อมใช้งานต่อปี *SLA* ตามสัญญาจริง ๆ ต่ำกว่านั้น (99.9% ต่อเดือน) และการพลาดมันได้เครดิตบริการ ไม่ใช่ uptime ในทางปฏิบัติ ความพร้อมใช้งานของ S3 สูงกว่าทั้งสองตัวเลขมาก — แต่ควรเข้าใจว่าความทนทานและความพร้อมใช้งานเป็นการรับประกันที่แยกกัน และเป้าหมายการออกแบบกับ SLA เป็นคำสัญญาที่แยกกัน

**ความพร้อมใช้งาน (Availability)** S3 ถูกออกแบบให้เข้าถึงได้แม้เมื่อส่วนประกอบแต่ละชิ้นล้มเหลว คุณไม่ได้เชื่อมต่อกับเซิร์ฟเวอร์ตัวเดียว — คุณเชื่อมต่อกับระบบกระจายที่หลีกเลี่ยงความล้มเหลว

**การขยาย (Scale)** S3 เก็บข้อมูลปริมาณที่ไม่จำกัดโดยพื้นฐาน bucket เดียวเก็บ object ได้หลายล้านล้านชิ้น Amazon เองใช้ S3 เพื่อเก็บข้อมูลในระดับที่เข้าใจได้ยาก bucket S3 ที่ใหญ่ที่สุดในโลกเก็บข้อมูลระดับ exabyte — หลายล้าน terabyte คุณไม่ได้จัดการขนาดนี้ คุณแค่อัปโหลด object และ S3 จัดการทุกอย่างข้างใต้

**ต้นทุน (Cost)** S3 Standard มีราคาประมาณ $0.023 ต่อ GB ต่อเดือน ณ ตอนเขียนนี้ สำหรับรูปเมนูแปดร้อยรูปของ Nimbus ที่เฉลี่ย 2MB ต่อรูป นั่นคือพื้นที่จัดเก็บ 1.6 GB — ประมาณ $0.04 ต่อเดือน แม้ที่รูป 800,000 รูป คุณก็มองที่ $37 ต่อเดือนสำหรับพื้นที่จัดเก็บ ต้นทุนของพื้นที่จัดเก็บเดียวกันบน volume EBS จะอยู่ที่ประมาณ $128 ต่อเดือน โดยมีเพดานตายตัวที่ต้องการการขยายก่อนที่คุณจะเพิ่มได้มากขึ้น S3 เติบโตโดยอัตโนมัติและเรียกเก็บเงินตามสัดส่วน EBS มีขนาดตายตัวและต้นทุนตายตัว

ไปป์ไลน์:

1. ร้านอาหารอัปโหลดรูปต้นฉบับ 4MB ไปยัง `nimbus-photos-raw/restaurant-001/arepa.jpg`
2. S3 ยิง Event Notification
3. ฟังก์ชัน Lambda อ่านต้นฉบับ สร้างภาพย่อ 400x300
4. Lambda บันทึกภาพย่อไปยัง `nimbus-photos-processed/restaurant-001/arepa.jpg`
5. ลูกค้าโหลดเมนู แอปให้บริการภาพย่อ 40KB แทนต้นฉบับ 4MB

**Cross-Region Replication: เมื่อสำเนาเดียวไม่พอ**

มี บทบัญญัติการถ่ายโอนข้อมูลของ GDPR หมายความว่าข้อมูลส่วนบุคคลเกี่ยวกับผู้อยู่อาศัยในสหภาพยุโรปอาจต้องเก็บภายในสหภาพยุโรปหรือในเขตอำนาจศาลที่มีการคุ้มครองข้อมูลที่เพียงพอ

คำตอบของ S3 ต่อเรื่องนี้คือ **Cross-Region Replication** (CRR) เมื่อคุณเปิดใช้งาน CRR บน bucket ทุก object ใหม่ที่อัปโหลดจะถูกจำลองไปยัง bucket ใน Region อื่นโดยอัตโนมัติ คุณกำหนดค่า bucket ต้นทาง bucket ปลายทาง และ IAM role ที่ให้ S3 มีสิทธิ์ดำเนินการจำลอง

เมื่อการขยายไปยังสหภาพยุโรปเกิดขึ้น แผนคือ: รูปที่อัปโหลดโดยร้านอาหารในสหภาพยุโรปจะเข้า bucket `eu-west-1` และ CRR จะจำลองพวกมันไปยัง bucket สำรองใน `eu-central-1` (แฟรงก์เฟิร์ต) สำหรับการกู้คืนจากภัยพิบัติ ข้อมูลสหภาพยุโรปอยู่ใน Region ของสหภาพยุโรป

เมื่อ S3 อัปโหลดไฟล์ที่ใหญ่กว่าขนาดที่กำหนด มันใช้ **multipart upload**: ไฟล์ถูกแบ่งเป็นส่วน ๆ แต่ละส่วนถูกอัปโหลดแยกกัน จากนั้นส่วนต่าง ๆ ถูกประกอบเข้าเป็น object สุดท้าย สิ่งนี้ทำให้การอัปโหลดขนาดใหญ่น่าเชื่อถือกว่า — ถ้าส่วนหนึ่งล้มเหลว เฉพาะส่วนนั้นต้องลองใหม่ ไม่ใช่ทั้งไฟล์

แต่ถ้า multipart upload เริ่มแล้วถูกทิ้ง — ผู้ใช้ปิดเบราว์เซอร์ เครือข่ายหลุด แอปพลิเคชันล่ม — ส่วนบางส่วนยังอยู่ใน S3 สะสมค่าพื้นที่จัดเก็บ พวกมันมองไม่เห็นเป็น object ที่สมบูรณ์ แต่พวกมันถูกเรียกเก็บเงินเป็นพื้นที่จัดเก็บ

Block Public Access ระดับบัญชีเป็นการป้องกันสิ่งนี้ แม้ว่านักพัฒนาจะกำหนดค่า bucket ให้เป็นสาธารณะโดยไม่ตั้งใจ การตั้งค่าระดับบัญชีก็ลบล้างมัน คุณต้องปิดใช้งานการตั้งค่าระดับบัญชีอย่างชัดเจนก่อนที่ bucket ใด ๆ จะกลายเป็นสาธารณะได้ — ซึ่งสร้างเนินชะลอความเร็วที่ตั้งใจซึ่งป้องกันอุบัติเหตุ

**S3 Storage Classes: ไม่ใช่ข้อมูลทุกอย่างที่เท่ากัน**

ไม่ใช่ข้อมูลทุกอย่างที่ถูกเข้าถึงเท่ากัน

รูปเมนูที่ได้รับความนิยมที่สุดของคุณถูกดึงหลายสิบครั้งต่อวินาที บันทึกของคุณจากสามปีก่อนถูกเข้าถึงอาจปีละครั้ง ถ้ามีเลย S3 ตระหนักถึงสิ่งนี้และเสนอ **storage class** ที่ต่างกันด้วยข้อแลกเปลี่ยนด้านประสิทธิภาพและต้นทุนที่ต่างกัน

| Storage Class           | กรณีการใช้งาน                                  | การดึงข้อมูล      | ต้นทุน                       |
|-------------------------|-----------------------------------------------|------------------|-----------------------------|
| S3 Standard             | ข้อมูลที่เข้าถึงบ่อย                           | ทันที            | สูงกว่าต่อ GB                |
| S3 Standard-IA          | เข้าถึงไม่บ่อย แต่ยังต้องการการดึงที่เร็ว       | ทันที            | ต่ำกว่าต่อ GB มีค่าดึงข้อมูล |
| S3 Glacier Instant      | คลังที่เข้าถึงเป็นครั้งคราว                     | ทันที            | ต่ำกว่ามาก                   |
| S3 Glacier Flexible     | คลังที่เข้าถึงน้อยมาก                          | นาทีถึงชั่วโมง   | ต่ำมาก                       |
| S3 Glacier Deep Archive | คลังการปฏิบัติตามข้อกำหนด เข้าถึงแทบไม่เคย     | สูงสุด 12 ชั่วโมง | ต่ำที่สุด                    |

เราเจาะลึกพวกมันในบทที่ 23 สำหรับตอนนี้: แนวคิดคือคุณสามารถย้าย object ระหว่าง storage class โดยอัตโนมัติตามอายุและรูปแบบการเข้าถึงของพวกมัน ประหยัดเงินอย่างมากกับข้อมูลที่คุณแทบไม่แตะ

ยังมี **S3 Intelligent-Tiering** — storage class ที่ย้าย object ระหว่างระดับการเข้าถึงบ่อยและการเข้าถึงไม่บ่อยโดยอัตโนมัติตามรูปแบบการเข้าถึงที่สังเกตได้ คุณจ่ายค่ามอนิเตอร์เล็กน้อยต่อ object ต่อเดือน และ S3 จัดการการแบ่งระดับโดยอัตโนมัติ สิ่งนี้มีประโยชน์เมื่อคุณไม่แน่ใจว่า object ใดจะถูกเข้าถึงบ่อยและอันไหนจะไม่ — บริการเรียนรู้รูปแบบและเพิ่มประสิทธิภาพตามนั้น

แนวทางของ Tom เป็นแบบใช้มือมากกว่า: "ผมอยากรู้ว่าทุกดอลลาร์ไปที่ไหน" เขาเลือกกฎ lifecycle ที่ชัดเจนแทน Intelligent-Tiering เพราะกฎที่ชัดเจนคาดเดาได้และตรวจสอบได้ หลังจากดำเนินงานพื้นที่จัดเก็บ S3 ของ Nimbus หกเดือน เขามีภาพที่ชัดเจนของรูปแบบการเข้าถึงและตั้งกฎ lifecycle ที่ย้าย object ไปยัง Standard-IA หลังจาก 30 วันและไปยัง Glacier Flexible Retrieval หลังจาก 180 วันได้

การประหยัดพื้นที่จัดเก็บรวมจากการจัดการ lifecycle ในปีแรก: ประมาณ $340 ไม่ได้เปลี่ยนชีวิต แต่เป็นจริง — และรูปแบบนี้เกิดซ้ำข้าม bucket หลายสิบอันในบัญชี AWS ที่จริงจังใด ๆ

"นั่นเกือบจะเที่ยวบินไป-กลับ" Maya พูด

"มันเป็นแนวปฏิบัติทางวิศวกรรมที่ดี" Tom พูด เขาใส่มันลงในสเปรดชีต

มีกับดักหนึ่งในการเลือก storage class ที่ทำให้หลายทีมพลาด: **ระยะเวลาจัดเก็บขั้นต่ำ (minimum storage duration)** S3 Standard-IA มีระยะเวลาจัดเก็บขั้นต่ำ 30 วัน — ถ้าคุณเก็บ object ใน Standard-IA และลบมันหลังจาก 15 วัน คุณก็ยังจ่ายค่า 30 วัน Glacier Flexible Retrieval มีขั้นต่ำ 90 วัน Glacier Deep Archive มีขั้นต่ำ 180 วัน

สำหรับ object ที่ถูกลบบ่อยหรือมีอายุสั้น ขั้นต่ำเหล่านี้ทำให้คลาส IA และ Glacier แพงกว่า Standard ไม่ใช่ถูกกว่า ก่อนย้ายไปยัง storage class ที่ถูกกว่า ให้ตรวจสอบว่า object จะอยู่ที่นั่นนานพอจริง ๆ ให้การประหยัดเกินบทลงโทษระยะเวลาขั้นต่ำ

## จุดแข็งและข้อจำกัด

**ทำไม S3 จึงยอดเยี่ยม**:

- ความทนทานสิบเอ็ดเก้า ข้อมูลของคุณปลอดภัยใน S3 มากกว่าเกือบทุกระบบอื่น
- การขยายไม่จำกัด คุณไม่เคยต้องจัดสรรพื้นที่จัดเก็บ — มันแค่เติบโต
- ถูกอย่างยิ่งสำหรับสิ่งที่มันให้ (เศษเสี้ยวของเซ็นต์ต่อ GB ต่อเดือน)
- การผสานรวมในตัวกับเกือบทุก AWS service อื่น
- รองรับการโฮสต์เว็บไซต์แบบสแตติก — คุณให้บริการเว็บไซต์สแตติกที่สมบูรณ์
  จาก S3 โดยตรงได้ ไม่ต้องมีเซิร์ฟเวอร์
- การประมวลผลที่ขับเคลื่อนด้วยเหตุการณ์: S3 Event Notifications กระตุ้น Lambda, SQS หรือ SNS
  โดยอัตโนมัติเมื่อ object ถูกสร้างหรือลบ เปิดให้มีไปป์ไลน์การประมวลผลที่ทรงพลัง
  โดยไม่ต้อง polling หรืองานตามกำหนดเวลา
- Cross-Region Replication สำหรับถิ่นที่อยู่ข้อมูลตามการปฏิบัติตามข้อกำหนดและการกู้คืนจากภัยพิบัติ

**ที่ซึ่ง S3 ไม่ใช่ทางเลือกที่ถูกต้อง**:

- S3 ไม่ใช่ระบบไฟล์ ถ้าแอปพลิเคชันของคุณต้อง mount ไดรฟ์และใช้มันเหมือนดิสก์ในเครื่อง
  (อ่าน เขียน แก้ไขไฟล์ในที่) S3 เป็นเครื่องมือที่ผิด
  ใช้ EFS (Elastic File System บทที่ 6) หรือ EBS แทน
- S3 มีความหน่วงที่สูงกว่าดิสก์ในเครื่องอย่างเห็นได้ชัด สำหรับฐานข้อมูลหรือ
  แอปพลิเคชันที่ต้องการ I/O แบบสุ่มเข้าถึงที่เร็ว block storage (EBS บทที่ 6)
  เหมาะสม
- การถ่ายโอนข้อมูล *เข้า* S3 ฟรีจากค่าแบนด์วิดท์ — แต่ไม่ฟรีทั้งหมด:
  ทุกการอัปโหลดเป็นคำขอ PUT และ S3 เรียกเก็บเงินต่อคำขอ การอัปโหลด object เล็ก
  หลายล้านชิ้นอาจมีต้นทุนในค่าคำขอมากกว่าในพื้นที่จัดเก็บ การถ่ายโอนข้อมูล *ออก*
  มีต้นทุนต่อ GB ทั้งสองอย่างเป็นเซอร์ไพรส์ในบิลที่พบบ่อย — เราจัดการพวกมันในบทที่ 30
- S3 ไม่ใช่ฐานข้อมูล คุณเก็บและดึง object ตาม key ได้ แต่คุณสืบค้น object
  ตามเนื้อหาของพวกมัน รัน aggregation หรือทำการดำเนินการเชิงสัมพันธ์ไม่ได้
  ถ้าคุณต้องการสืบค้นเนื้อหาของข้อมูลที่จัดเก็บ (ไม่ใช่แค่ดึงตามชื่อ)
  คุณต้องการฐานข้อมูลหรือบริการเช่น Athena (บทที่ 26) ที่สืบค้น object ของ S3
  ด้วย SQL ได้
- การทำ versioning ของ object เก็บต้นทุนที่ทบต้น ทุกเวอร์ชันก่อนหน้าของทุก object
  ที่ทำ versioning ถูกเรียกเก็บเป็นพื้นที่จัดเก็บ กฎ lifecycle ที่หมดอายุเวอร์ชันเก่า
  ไม่ใช่ทางเลือก — พวกมันเป็นส่วนหนึ่งของกลยุทธ์การจัดการต้นทุนสำหรับ bucket ใด ๆ
  ที่เปิดใช้งาน versioning

**Object ของ S3 ถูกเข้ารหัสอย่างไร**

"แล้วถ้ามีคนพยายามบุกรุกล่ะ?" Priya ถามอย่างที่คาดได้ ในวันที่รูปขึ้นใช้งานจริง "object เหล่านี้เข้ารหัสตอนพักหรือเปล่า?"

มัน — และนั่นควรค่าแก่การเข้าใจ เพราะการเข้ารหัส S3 เป็นหนึ่งในหัวข้อที่ถูกทดสอบมากที่สุดในการสอบ ทุก object ที่อัปโหลดไปยัง S3 ถูกเข้ารหัสตอนพักโดยค่าเริ่มต้น คำถามคือ *ใครถือคีย์*:

**SSE-S3 (ค่าเริ่มต้น)**: S3 เข้ารหัสทุก object ด้วยคีย์ที่ S3 เองจัดการ โดยใช้ AES-256 คุณไม่ต้องทำอะไร ไม่กำหนดค่าอะไร ไม่จ่ายอะไร ตั้งแต่มกราคม 2023 นี่เป็นอัตโนมัติบนทุก bucket สำหรับข้อมูลส่วนใหญ่ มันเพียงพอ

**SSE-KMS**: S3 เข้ารหัส object ด้วยคีย์ KMS — ไม่ว่าจะเป็นคีย์ `aws/s3` ที่ AWS จัดการหรือคีย์ที่ลูกค้าจัดการซึ่งคุณควบคุม (บทที่ 16 ครอบคลุม KMS อย่างละเอียด) สิ่งที่คุณได้: เส้นทางการตรวจสอบใน CloudTrail ของทุกการใช้คีย์ ความสามารถในการควบคุมอย่างแม่นยำว่าใครถอดรหัสได้ผ่าน policy ของคีย์ และความสามารถในการเพิกถอนการเข้าถึงด้วยการปิดใช้งานคีย์ สิ่งที่คุณจ่าย: ค่า KMS API ต่อคำขอ ที่อัตราคำขอสูง เปิดใช้งาน **S3 Bucket Keys** — S3 สร้างคีย์ระดับ bucket อายุสั้นจากคีย์ KMS ของคุณ ลดการเรียก KMS API (และต้นทุน) ได้ถึง 99%

**SSE-C**: คุณให้คีย์เข้ารหัสของคุณเอง *กับทุกคำขอ* AWS ใช้มันในหน่วยความจำและไม่เคยเก็บมัน สำหรับองค์กรที่กฎการปฏิบัติตามบอกว่า AWS ต้องไม่เคยถือคีย์ ต้องการความใส่ใจในการดำเนินงานสูง — ทำคีย์หาย เสียข้อมูล

รูปแบบการสอบ: "การเข้ารหัสพร้อมเส้นทางการตรวจสอบการใช้คีย์" หรือ "ควบคุมว่าใครถอดรหัสได้" → SSE-KMS "บริษัทต้องจัดการคีย์ของตัวเองและ AWS ต้องไม่เก็บมัน" → SSE-C "การเข้ารหัสตอนพักโดยไม่มีภาระการจัดการ" → SSE-S3 (เปิดอยู่แล้ว)

**S3 Object Lock: เขียนครั้งเดียว อ่านได้หลายครั้ง**

ข้อมูลบางอย่างต้อง *เป็นไปไม่ได้* ที่จะลบ — ไม่ใช่ป้องกันด้วยนโยบาย แต่ไม่เปลี่ยนแปลงโดยโครงสร้าง บันทึกการซื้อขายทางการเงิน บันทึกการตรวจสอบ หลักฐานทางกฎหมาย **S3 Object Lock** ทำให้ object ลบและแก้ไขไม่ได้เป็นระยะเวลาเก็บรักษา แม้แต่โดยผู้ดูแลระบบ มันต้องการ versioning และมาในสองโหมดที่การสอบชอบเปรียบเทียบ: **governance mode** (ผู้ใช้ที่มีสิทธิ์พิเศษยังข้ามการล็อกได้) และ **compliance mode** (ไม่มีใครย่นระยะเวลาเก็บรักษาหรือลบ object ได้ — แม้แต่ root user — จนกว่าระยะเวลาจะหมด) วลีด้านกฎระเบียบเช่น "WORM storage" หรือ "SEC Rule 17a-4" เป็นตัวกระตุ้นการสอบสำหรับ Object Lock ใน compliance mode

**S3 Transfer Acceleration: การอัปโหลดที่เร็วจากระยะไกล**

เมื่อผู้ใช้อัปโหลดไฟล์ขนาดใหญ่ไปยัง bucket จากอีกฟากของโลก ส่วนที่ช้าคือเส้นทางอินเทอร์เน็ตสาธารณะที่ยาวไปยัง region ของ bucket **S3 Transfer Acceleration** ให้ bucket มี endpoint พิเศษที่กำหนดเส้นทางการอัปโหลดเข้าสู่ edge location ของ AWS ที่ใกล้ที่สุด จากนั้นนำพวกมันผ่าน backbone ส่วนตัวของ AWS ไปยัง bucket ตัวกระตุ้นการสอบ: "ผู้ใช้ทั่วโลกอัปโหลดไฟล์ขนาดใหญ่ไปยัง bucket ส่วนกลาง การอัปโหลดช้า" → Transfer Acceleration (มักจับคู่กับ multipart upload) สังเกตทิศทาง: Transfer Acceleration เกี่ยวกับการนำข้อมูล *เข้า* S3 CloudFront เกี่ยวกับการให้บริการข้อมูล *ออก*

อีกหนึ่ง storage class ที่ควรรู้ตอนนี้: **S3 One Zone-IA** — เหมือน Standard-IA แต่เก็บใน Availability Zone เดียว ถูกกว่าราว ๆ 20% สำหรับข้อมูลที่เข้าถึงไม่บ่อยซึ่งคุณสร้างใหม่ได้ถ้า AZ นั้นสูญหาย (ภาพย่อ รายงานที่สร้างใหม่ได้) มันเป็นตัวลวงในการสอบมาตรฐาน บทที่ 23 ครอบคลุมสเปกตรัม storage class เต็มรูปแบบ


## สรุป

รูปแปดร้อยรูปบน instance เดียวคือปัญหา S3 แก้มันได้ — แต่ S3 เป็นมากกว่าที่เก็บไฟล์ มันคือที่เก็บ object ที่ทนทาน ขยายได้ เข้าถึงได้ทั่วโลก พร้อมโมเดลการเข้าถึงของตัวเอง storage class นโยบาย lifecycle และระบบเหตุการณ์ การเข้าใจว่า S3 เก่งเรื่องอะไร และอะไรที่มันตั้งใจไม่เป็น กำหนดทุกการตัดสินใจด้านพื้นที่จัดเก็บที่ทีมจะทำต่อจากนี้ไป

- **Amazon S3** คือ object storage — ไฟล์ (object) ในคอนเทนเนอร์ที่ตั้งชื่อ (bucket) มันเก็บสำเนาข้าม Availability Zone อย่างน้อยสามแห่งเพื่อความทนทานสิบเอ็ดเก้า S3 ไม่ใช่ระบบไฟล์: ใช้ EFS สำหรับ mount ที่แชร์ EBS สำหรับ block storage ของ instance เดียว
- ไฟล์ที่เก็บบน EC2 instance ผูกกับวงจรชีวิตของ instance นั้น ทำให้เกิดบั๊กรูปหายเมื่อทราฟฟิกกระจายข้ามเซิร์ฟเวอร์หลายตัว S3 แก้สิ่งนี้ด้วยการเป็นอิสระจาก instance ใด ๆ
- **Versioning** เก็บเวอร์ชัน object ก่อนหน้า **กฎ lifecycle** ทำให้การเปลี่ยนผ่านระหว่าง storage class เป็นอัตโนมัติและทำความสะอาด multipart upload ที่ไม่สมบูรณ์ซึ่งมิฉะนั้นจะสะสมค่าใช้จ่ายในบิลแบบเงียบ ๆ
- โดยค่าเริ่มต้น S3 เป็นส่วนตัว เปิดใช้งาน "Block Public Access" ในระดับบัญชี ให้บริการ object สาธารณะผ่าน CloudFront ด้วย Origin Access Control แทนที่จะทำให้ bucket เป็นสาธารณะโดยตรง
- storage class ของ S3 ให้คุณจับคู่ต้นทุนกับความถี่ในการเข้าถึง — แต่ระวังค่าระยะเวลาจัดเก็บขั้นต่ำก่อนเปลี่ยนผ่าน object ที่มีอายุสั้นไปยังระดับ Infrequent Access หรือ Glacier

## เคล็ดลับการสอบ

*SAA-C03 Domain 3 — Task 3.1 (โซลูชันพื้นที่จัดเก็บประสิทธิภาพสูง)*

- **S3 คือ object storage ไม่ใช่ block storage** เมื่อสถานการณ์การสอบต้องการ
  ระบบไฟล์ที่เซิร์ฟเวอร์หลายตัว mount ได้ นั่นคือ EFS เมื่อมันต้องการดิสก์
  สำหรับ EC2 instance เดียว นั่นคือ EBS เมื่อมันต้องการเก็บไฟล์ ข้อมูลสำรอง
  รูปภาพ หรือข้อมูลที่เข้าถึงผ่าน HTTP — นั่นคือ S3
- **ความทนทานสิบเอ็ดเก้า** หมายความว่า S3 จำลองข้อมูลข้าม AZ หลายแห่ง
  โดยอัตโนมัติ คุณไม่ได้กำหนดค่านี้ — มันเป็นค่าเริ่มต้น
- **S3 เป็น Regional** แต่เข้าถึงได้ทั่วโลก bucket มีอยู่ใน Region เฉพาะ
  แต่คุณเข้าถึงพวกมันได้จากทุกที่
- **Pre-signed URL** ให้การเข้าถึงที่จำกัดเวลาไปยัง object ส่วนตัว รูปแบบที่พบบ่อย:
  แอปพลิเคชันของคุณสร้าง pre-signed URL ที่ใช้ได้ 15 นาที ให้กับผู้ใช้
  ผู้ใช้ดาวน์โหลดไฟล์โดยตรงจาก S3
- **S3 Standard-IA** มีค่าระยะเวลาจัดเก็บขั้นต่ำ (30 วัน) อย่าใช้มัน
  สำหรับข้อมูลที่คุณจะลบเร็ว การสอบทดสอบว่าคุณรู้ข้อแลกเปลี่ยน
  ระหว่าง storage class หรือไม่
- **ต้นไม้การตัดสินใจ storage class**: *เข้าถึงบ่อย* → S3 Standard; *เข้าถึงไม่บ่อยแต่ต้องการการดึงที่เร็ว* → S3 Standard-IA; *คลังที่เข้าถึงเป็นครั้งคราว* → S3 Glacier Instant Retrieval; *คลังที่เข้าถึงน้อยมาก* → S3 Glacier Flexible Retrieval; *คลังการปฏิบัติตามข้อกำหนด เข้าถึงแทบไม่เคย* → S3 Glacier Deep Archive
- **Cross-Region Replication** ต้องเปิดใช้งาน versioning บนทั้ง bucket ต้นทางและปลายทาง คำถามสอบเกี่ยวกับการกู้คืนจากภัยพิบัติหรืออธิปไตยข้อมูลมักเกี่ยวข้องกับ CRR

## แบบฝึกหัด

**แบบฝึกหัด 1 — การจำ**

ด้วยคำพูดของคุณเอง: object ของ S3 คืออะไร? bucket ของ S3 คืออะไร? ทำไมการเก็บไฟล์ใน S3 ถึงดีกว่าการเก็บพวกมันบนดิสก์ในเครื่องของ EC2 instance?

*(คำใบ้: คิดถึงสิ่งที่เกิดขึ้นกับไฟล์บน EC2 instance ถ้า instance ถูกยุติ S3 ทำอะไรต่างออกไป?)*

**แบบฝึกหัด 2 — สถานการณ์ SAA-C03**

*สถานการณ์*: บริษัทสื่อผลิตวิดีโอสารคดี พวกเขาต้องเก็บฟุตเทจต้นฉบับ 4K (เข้าถึงบ่อยในระหว่างการผลิต) ฉบับตัดต่อสุดท้าย (เข้าถึงรายเดือนสำหรับการเผยแพร่) และมาสเตอร์คลัง (เก็บไว้อย่างไม่มีกำหนดแต่เข้าถึงอย่างมากปีละครั้งเพื่อจุดประสงค์การปฏิบัติตามข้อกำหนด) พวกเขาต้องการลดต้นทุนพื้นที่จัดเก็บให้น้อยที่สุดในขณะที่ตอบสนองข้อกำหนดการเข้าถึงของแต่ละระดับ

กลยุทธ์พื้นที่จัดเก็บใดตอบสนองความต้องการของพวกเขาได้ดีที่สุด?

A) เก็บฟุตเทจต้นฉบับใน S3 Standard ฉบับตัดต่อสุดท้ายใน S3 Standard-IA และคลัง
   ใน S3 Glacier Deep Archive  
B) เก็บเนื้อหาทั้งหมดใน S3 Standard เพื่อประสิทธิภาพที่สม่ำเสมอและความเรียบง่าย  
C) เก็บเนื้อหาทั้งหมดบนพื้นที่จัดเก็บ EC2 instance เพื่อการเข้าถึงที่เร็วที่สุด  
D) เก็บเนื้อหาทั้งหมดใน S3 Glacier Deep Archive เพื่อลดต้นทุนให้น้อยที่สุด

**คำใบ้ 1**: ไฟล์ต่างกันมีรูปแบบการเข้าถึงต่างกัน S3 เสนอ storage class ต่างกันสำหรับความถี่การเข้าถึงต่างกัน คลาสใดตรงกับ "เข้าถึงบ่อย"?

**คำใบ้ 2**: คลังที่เข้าถึง "อย่างมากปีละครั้ง" ไม่ต้องการการดึงทันที storage class ใดออกแบบมาสำหรับการเก็บคลังระยะยาวด้วยต้นทุนต่ำสุด?

**คำใบ้ 3**: จับคู่ความถี่การเข้าถึงของแต่ละระดับกับ storage class ที่เหมาะสม เข้าถึงบ่อย = Standard รายเดือน = Standard-IA ปีละครั้ง = Glacier Deep Archive

**คำตอบ**: A

**คำอธิบาย**: กลยุทธ์นี้จับคู่แต่ละระดับข้อมูลกับ storage class ของ S3 ที่เหมาะสมอย่างถูกต้อง ฟุตเทจต้นฉบับที่เข้าถึงบ่อยอยู่ใน Standard เพื่อการเข้าถึงทันทีโดยไม่มีค่าดึงข้อมูล ฉบับตัดต่อสุดท้ายที่เข้าถึงรายเดือนไปยัง Standard-IA (ต้นทุนพื้นที่จัดเก็บต่ำกว่า ค่าดึงข้อมูลที่จ่ายได้) คลังที่เข้าถึงปีละครั้งไปยัง Glacier Deep Archive เพื่อต้นทุนพื้นที่จัดเก็บที่ต่ำที่สุดเท่าที่จะเป็นไปได้

**ทำไมไม่ใช่ B?** การเก็บทุกอย่างใน Standard เรียบง่ายแต่แพง

**ทำไมไม่ใช่ C?** พื้นที่จัดเก็บ EC2 instance เป็นแบบชั่วคราวและไม่เหมาะสำหรับการเก็บสื่อระยะยาว ถ้า instance ถูกยุติ เนื้อหาทั้งหมดก็สูญหาย

**ทำไมไม่ใช่ D?** Glacier Deep Archive มีเวลาดึงข้อมูลสูงถึง 12 ชั่วโมง การเก็บฟุตเทจการผลิตที่เข้าถึงบ่อยไว้ที่นั่นจะทำให้งานการผลิตเป็นไปไม่ได้

**แบบฝึกหัด 3 — ความท้าทายด้านสถาปัตยกรรม** *(ตัวเลือกเสริม)*
