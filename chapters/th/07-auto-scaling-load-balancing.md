**แนวคิด: การขยายขนาดในแนวนอน**

มีสองวิธีในการทำให้ระบบจัดการโหลดได้มากขึ้น

**การขยายในแนวตั้ง** หมายถึงการทำให้เซิร์ฟเวอร์เดียวใหญ่ขึ้น CPU มากขึ้น RAM มากขึ้น เราทำสิ่งนี้ในบทที่ 4 เมื่ออัพเกรดจาก `t3.micro` เป็น `t3.large` มันช่วย แต่มีขีดจำกัด: ขยายได้แค่ไหน instance ต้องรีสตาร์ทเพื่อปรับขนาด และยังมีจุดล้มเหลวเดียว

**การขยายในแนวนอน** หมายถึงการเพิ่มเซิร์ฟเวอร์มากขึ้น แทนที่จะเป็นเซิร์ฟเวอร์ใหญ่หนึ่งเครื่อง รันเซิร์ฟเวอร์ขนาดกลางห้าเครื่อง เมื่อ traffic ลดลง รันสอง เมื่อพุ่งสูง รันสิบ

การขยายในแนวนอนมีข้อดีที่การขยายในแนวตั้งไม่มี:

- ไม่มีจุดล้มเหลวเดียว ถ้าเซิร์ฟเวอร์หนึ่งตาย อื่นๆ ยังให้บริการต่อ
- ไม่จำเป็นต้องรีสตาร์ทเพื่อเพิ่มกำลังการผลิต
- จ่ายเฉพาะสิ่งที่คุณใช้ — เพิ่มเซิร์ฟเวอร์เมื่อต้องการ ลบออกเมื่อไม่ต้อง
- การขยายแบบเชิงเส้น: สองเท่าของเซิร์ฟเวอร์ ประมาณสองเท่าของ throughput

ข้อเสีย: ถ้าคุณมีเซิร์ฟเวอร์หลายเครื่อง ผู้ใช้รู้ได้อย่างไรว่าจะคุยกับเครื่องไหน?

**Application Load Balancer: ประตูหนึ่ง ห้องหลาย**

**Application Load Balancer** (ALB) คือประตูหน้าของแอปพลิเคชันคุณ

ผู้ใช้เชื่อมต่อกับ load balancer load balancer กระจายคำขอที่เข้ามาตลอด EC2 instances ของคุณ ผู้ใช้แต่ละคนเห็นที่อยู่หนึ่ง (URL ของ load balancer) เบื้องหลังที่อยู่นั้น คำขอกระจายไปตลอดเซิร์ฟเวอร์ที่กำลังทำงาน

คิดว่ามันเหมือนร้านอาหารขนาดใหญ่ที่มีโต๊ะรับรองที่ประตู ลูกค้ามาถึงและโฮสต์ชี้นำพวกเขาไปยังโต๊ะที่ว่าง โฮสต์รู้ว่าโต๊ะไหนยุ่งและไหนว่าง ลูกค้าไม่จำเป็นต้องรู้ว่ามีโต๊ะกี่โต๊ะ — พวกเขาแค่เดินเข้ามาและโฮสต์จัดการการกระจาย

ALB ทำสิ่งนี้กับคำขอเว็บ มันรับคำขอ HTTP ที่เข้ามาแต่ละอันและตัดสินใจว่า EC2 instance ใด (เรียกว่า **target**) ควรจัดการมัน ขึ้นอยู่กับปัจจัยเช่น:

- Round-robin (แต่ละเซิร์ฟเวอร์หมุนเวียน)
- คำขอที่รอน้อยที่สุด
- สุขภาพ — มีเฉพาะ targets ที่แข็งแรงเท่านั้นที่ได้รับ traffic

**การตรวจสุขภาพ** จำเป็น ALB ส่งคำขอทดสอบไปยังแต่ละ target เป็นประจำ ถ้า target ไม่ตอบสนองอย่างถูกต้อง ALB ทำเครื่องหมายว่าไม่แข็งแรงและหยุดส่ง traffic ไปยังมัน เมื่อ target ฟื้นตัว traffic ก็กลับมา

สิ่งนี้เป็นอัตโนมัติ คุณกำหนดค่าพารามิเตอร์การตรวจสุขภาพ ALB บังคับใช้พวกมัน

**Auto Scaling: ร้านอาหารที่เปิดโต๊ะเพิ่ม**

ALB กระจาย traffic ตลอดเซิร์ฟเวอร์ที่มีอยู่ของคุณ แต่มันไม่เพิ่มเซิร์ฟเวอร์เมื่อคุณต้องการมากขึ้น

**Auto Scaling** ทำสิ่งนั้น

**Auto Scaling Group** (ASG) คือการกำหนดค่าที่บอก AWS:

- จำนวน instances ขั้นต่ำที่จะรันเสมอ
- จำนวน instances สูงสุดที่อนุญาต
- เงื่อนไขสำหรับ scale out (เพิ่ม instances) หรือ scale in (ลบพวกมัน)

เงื่อนไขการขยายขนาดเรียกว่า **policies** ประเภทที่พบบ่อยที่สุด:

**Target tracking**: "รักษาการใช้งาน CPU เฉลี่ยที่ 70%" เมื่อ CPU เฉลี่ยเกิน 70% AWS เปิดตัว instances ใหม่ เมื่อมันลดลง instances ถูกยุติ

สิ่งนี้เป็นอัตโนมัติ ไม่มีใครต้องดูตัวชี้วัด ไม่มีใครต้องเปิดตัวเซิร์ฟเวอร์ด้วยตนเอง

**วิธีที่ ALB และ ASG ทำงานร่วมกัน**

Services ทั้งสองออกแบบมาให้ใช้ร่วมกัน

คุณวาง ALB ไว้ข้างหน้า ALB ชี้ไปยัง **target group** — กลุ่มของ instances ที่ควรได้รับ traffic Auto Scaling Group จัดการ instances เหล่านั้น: เพิ่มพวกมันไปยัง target group เมื่อ scale out ลบออกเมื่อ scale in

กระบวนการ:

1. Traffic มาถึง ALB
2. ALB กระจายคำขอไปยัง targets ที่แข็งแรง
3. CPU/โหลดเพิ่มขึ้นบน targets เหล่านั้น
4. ASG ตรวจพบการเพิ่มขึ้นของโหลด เปิดตัว instances ใหม่
5. Instances ใหม่ผ่านการตรวจสุขภาพ ลงทะเบียนกับ ALB
6. ALB เริ่มส่ง traffic ไปยังพวกมัน
7. โหลดลดลง ASG ยุติ instances เพิ่มเติม
8. ALB หยุดส่ง traffic ไปยัง instances ที่ถูกยุติ

สิ่งนี้เกิดขึ้นโดยไม่มีการแทรกแซงของมนุษย์

**Sticky Sessions: ปัญหาเบื้องหลัง**

นี่คือสิ่งที่ทำให้หลายทีมสะดุดเมื่อใช้งาน load balancing ครั้งแรก

แอปพลิเคชันเว็บบางตัวเก็บข้อมูล session — สถานะการเข้าสู่ระบบ เนื้อหาตะกร้าสินค้า — บนเซิร์ฟเวอร์เอง (ในหน่วยความจำหรือดิสก์ในเครื่อง) สิ่งนี้ทำงานได้ดีกับเซิร์ฟเวอร์หนึ่งเครื่อง แต่พังกับหลายเซิร์ฟเวอร์

ผู้ใช้ล็อกอิน คำขอไปที่เซิร์ฟเวอร์ A เซิร์ฟเวอร์ A เก็บ session คำขอต่อไปไปที่เซิร์ฟเวอร์ B เซิร์ฟเวอร์ B ไม่มี session ผู้ใช้ดูเหมือนออกจากระบบ

สามารถแก้ไขได้สองวิธี:

**Sticky sessions** (หรือ session affinity): กำหนดค่า ALB ให้ส่งคำขอจากผู้ใช้เดิมไปยังเซิร์ฟเวอร์เดิมเสมอ นี่เป็นการแก้ไขระยะสั้น

**การออกแบบแอปพลิเคชันแบบ stateless**: เก็บข้อมูล session ภายนอก — ในฐานข้อมูลหรือ cache เช่น ElastiCache (บทที่ 10) นี่คือแนวทางที่ถูกต้องสำหรับแอปพลิเคชันที่ขยายในแนวนอน

## สรุป

- **การขยายในแนวนอน** (เพิ่มเซิร์ฟเวอร์) เป็นที่นิยมกว่าการขยายในแนวตั้ง
- **Application Load Balancer (ALB)** กระจาย HTTP/HTTPS traffic ที่เข้ามาตลอด EC2 targets หลายอัน ทำการตรวจสุขภาพและกำหนดเส้นทางเฉพาะ instances ที่แข็งแรง
- **Auto Scaling Group (ASG)** ปรับจำนวน EC2 instances โดยอัตโนมัติตาม scaling policies ที่กำหนด
- ALB และ ASG ทำงานร่วมกัน: ASG จัดการ fleet, ALB กระจาย traffic ตลอด
- แอปพลิเคชันที่มีสถานะต้องใช้ sticky sessions (การแก้ระยะสั้น) หรือ externalize state (การออกแบบระยะยาวที่ถูกต้อง)

## เคล็ดลับการสอบ

*SAA-C03 Domain 2 — Task 2.1 / Domain 3 — Task 3.2*

- **การตรวจสุขภาพ ASG สามารถมาจาก EC2 หรือ ALB** การตรวจสุขภาพ EC2 ตรวจสอบแค่ว่า instance กำลังทำงาน การตรวจสุขภาพ ALB ตรวจสอบว่าแอปพลิเคชันตอบสนองถูกต้อง
- **Target tracking scaling เป็นคำตอบการสอบที่พบบ่อยที่สุด** สำหรับ scaling policies
- **Scale-out เร็ว; scale-in ช้า** AWS ยุติ instances อย่างค่อยเป็นค่อยไประหว่าง scale-in
- **จำนวน instances ขั้นต่ำคือพื้นความยืดหยุ่นของคุณ** ถ้าคุณตั้ง minimum = 1 และ instance นั้นล้มเหลว แอปพลิเคชันของคุณล่มก่อนที่ ASG จะตอบสนองได้
