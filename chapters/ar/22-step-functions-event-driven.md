**AWS Step Functions: تنسيق سير العمل**

**AWS Step Functions** خدمة تنسيق serverless تُنسّق خطوات تطبيق كسير عمل مرئي. كل خطوة **حالة** في **آلة حالة**.

بدلاً من نص Python يعمل من الأعلى للأسفل ويتعطّل، تُعرّف سير العمل كآلة حالة JSON/YAML:

```json
{
  "StartAt": "ValidateLicense",
  "States": {
    "ValidateLicense": {
      "Type": "Task",
      "Resource": "arn:aws:lambda:us-west-2:123456789012:function:validate-license",
      "Next": "ImportMenu",
      "Catch": [{"ErrorEquals": ["States.ALL"], "Next": "OnboardingFailed"}]
    },
    "ImportMenu": {
      "Type": "Task",
      "Resource": "arn:aws:lambda:us-west-2:123456789012:function:import-menu",
      "Next": "SetupPayments",
      "Retry": [{"ErrorEquals": ["States.ALL"], "MaxAttempts": 3, "IntervalSeconds": 5}]
    },
    ...
  }
}
```

كل حالة يمكنها:

- **تنفيذ دالة Lambda** (النمط الأكثر شيوعاً)
- **تنفيذ مهمة ECS** (للعمل الأطول تشغيلاً)
- **الانتظار لوقت محدد** أو **حدث** (إيقاف سير العمل مؤقتاً حتى يحدث شيء خارجي)
- **اختيار مسار** بناءً على شروط (منطق if/else)
- **تشغيل فروع متوازية** في آن واحد
- **إعادة المحاولة عند الفشل** بتراجع قابل للتكوين
- **التقاط الأخطاء** والتوجيه إلى حالات معالجة الأخطاء

تدير Step Functions حالة التنفيذ بشكل متين. إذا فشلت الخطوة 3، يتوقّف التنفيذ مؤقتاً عند الخطوة 3. يمكنك فحص التنفيذ الفاشل في وحدة التحكم، إصلاح المشكلة، وإعادة البدء من الخطوة 3 — دون تكرار الخطوتين 1 و2.

ربما تتساءل: ألا يمكنك كتابة منطق إعادة المحاولة في دالة Lambda الخاصة بك؟ نعم — لكنك حينها تكتب أيضاً تتبّع الإخفاق، وإدامة الحالة، وتسجيل التدقيق في الكود. وحين تفشل الخطوة 3 من 7، تحتاج معرفة أي مطعم كان يُعالَج، وما حدث قبل ذلك، وأين تستأنف. Step Functions تفعل كل ذلك.

**تدفق طلب Nimbus: آلة حالة مُعلَّقة**

إليك نسخة مبسّطة من آلة حالة Step Functions الفعلية التي بنتها Nimbus لتأكيد الطلب — مُعلَّقة لترى ما يفعله كل جزء:

```json
{
  "Comment": "Nimbus order confirmation workflow",
  "StartAt": "ChargeCard",
  "States": {
    "ChargeCard": {
      "Type": "Task",
      "Resource": "arn:aws:lambda:us-west-2:123456789012:function:charge-card",
      "Next": "SendConfirmationEmail",
      "Retry": [
        {
          "ErrorEquals": ["PaymentRetryableError"],
          "MaxAttempts": 2,
          "IntervalSeconds": 3,
          "BackoffRate": 2.0
        }
      ],
      "Catch": [
        {
          "ErrorEquals": ["PaymentDeclinedError"],
          "Next": "NotifyCustomerOfDecline"
        },
        {
          "ErrorEquals": ["States.ALL"],
          "Next": "ChargeCardFailed"
        }
      ]
    },
    "SendConfirmationEmail": {
      "Type": "Task",
      "Resource": "arn:aws:lambda:us-west-2:123456789012:function:send-confirmation-email",
      "Next": "NotifyRestaurant",
      "Retry": [
        {
          "ErrorEquals": ["States.ALL"],
          "MaxAttempts": 3,
          "IntervalSeconds": 5
        }
      ]
    },
    "NotifyRestaurant": {
      "Type": "Task",
      "Resource": "arn:aws:lambda:us-west-2:123456789012:function:notify-restaurant",
      "Next": "UpdateInventory",
      "Retry": [
        {
          "ErrorEquals": ["States.ALL"],
          "MaxAttempts": 3,
          "IntervalSeconds": 10,
          "BackoffRate": 2.0
        }
      ],
      "Catch": [
        {
          "ErrorEquals": ["States.ALL"],
          "Next": "RestaurantNotificationFailed"
        }
      ]
    },
    "UpdateInventory": {
      "Type": "Task",
      "Resource": "arn:aws:lambda:us-west-2:123456789012:function:update-inventory",
      "Next": "LogTransaction",
      "Retry": [{"ErrorEquals": ["States.ALL"], "MaxAttempts": 2}]
    },
    "LogTransaction": {
      "Type": "Task",
      "Resource": "arn:aws:lambda:us-west-2:123456789012:function:log-transaction",
      "End": true
    },
    "NotifyCustomerOfDecline": {
      "Type": "Task",
      "Resource": "arn:aws:lambda:us-west-2:123456789012:function:notify-decline",
      "End": true
    },
    "ChargeCardFailed": {
      "Type": "Fail",
      "Error": "ChargeCardFailed",
      "Cause": "Card charge failed after retries"
    },
    "RestaurantNotificationFailed": {
      "Type": "Task",
      "Resource": "arn:aws:lambda:us-west-2:123456789012:function:alert-support",
      "Comment": "Alert support team — order charged but restaurant not notified",
      "End": true
    }
  }
}
```

بضعة أشياء يجدر ملاحظتها:

**`ChargeCard` لديها كتلتا Catch.** واحدة لـ `PaymentDeclinedError` (إخفاق معروف ومتوقّع — رُفضت البطاقة، لا خطأ نظام) وواحدة لـ `States.ALL` (أي شيء آخر — انقطاع نظام، مهلة، استثناء غير متوقّع). تُوجّهان إلى حالات مختلفة لأنهما تعنيان أشياء مختلفة.

**`NotifyRestaurant` لديها Catch تُوجّه إلى `RestaurantNotificationFailed`.** هذا هو الخطأ الذي تسبّب في الحوادث الإحدى عشرة. في نص Python القديم، لم يكن هناك مكافئ — إذا فشل الإشعار، إما أن الدالة تتعطّل بصمت أو تسجّل خطأً وتواصل. Step Functions تجعل مسار الإخفاق صريحاً: يذهب إلى مكان محدد، وذلك المكان ينبّه فريق الدعم قبل أن يضطر أحد إلى الاتصال.

**كل Task لديها Retry.** إذا كان لخدمة البريد الإلكتروني مهلة عابرة، تُعيد المحاولة تلقائياً، ثلاث مرات، بتراجع متزايد. العميل لا يرى هذا أبداً. الطلب لا يُفقد.

**التدفق رسم بياني، لا نص.** إذا فشلت `NotifyRestaurant` نهائياً (بعد إعادات المحاولة)، لا يستمر التنفيذ إلى `UpdateInventory`. يتوقّف سير العمل عند `RestaurantNotificationFailed`. المخزون لا يُحدَّث لمطعم لا يعلم بالطلب. هذا سلوك صحيح.

سألت Maya: "لحظة — لكن *لماذا* نحتاج مسارات إخفاق منفصلة لبطاقة مرفوضة مقابل خطأ نظام؟"

قال Leo: "لأنهما يتطلبان استجابات مختلفة تماماً. بطاقة مرفوضة تعني أننا نراسل العميل ونطلب منه المحاولة مجدداً. خطأ نظام في دالة الخصم يعني أننا نحتاج مهندساً للتحقيق في سبب فشل دالة Lambda. النتيجة المُلاحَظة ذاتها — الطلب لم يمر — لكن معالجة مختلفة تماماً."

**أنواع الحالات: اللبنات الأساسية**

**Task**: تنفيذ إجراء — استدعاء دالة Lambda، بدء مهمة ECS، استدعاء API. هذا حيث يحدث العمل الحقيقي.

**Choice**: التفرّع بناءً على شروط في بيانات المدخل. مثل if/else في الكود.

**Parallel**: تشغيل فروع متعددة في آن واحد والانتظار حتى تكتمل جميعها.

**Map**: تطبيق مجموعة من الحالات على كل عنصر في قائمة. معالجة 50 صنف قائمة مطعم بالتوازي.

حين استوردت Nimbus قائمة مطعم، كان يمكن للقائمة أن تحتوي ما بين 8 و200 صنف. لكل صنف، احتاجت عملية الاستيراد إلى: التحقق من التنسيق، فحص بيانات مسبّبات الحساسية، تغيير حجم الصورة، وكتابة السجل إلى DynamoDB.

بدون حالة Map، سيكون هذا Lambda واحدة تُعالج الأصناف بالتسلسل — 200 صنف × 200 مللي ثانية لكل صنف = 40 ثانية من وقت المعالجة. مع حالة Map، تُطلق Step Functions تنفيذات متزامنة لحالات المعالجة — حتى حد التزامن المُكوَّن — وتنتظر اكتمالها جميعاً. الـ 200 صنف ذاتها يمكن أن تنتهي في أقل من 5 ثوانٍ.

**Wait**: التوقّف لوقت محدد أو حتى طابع زمني. مفيد للتأخيرات المجدوَلة.

**Pass**: تمرير المدخل إلى المخرج دون أداء عمل. يُستخدم لتحويل البيانات والاختبار.

**Succeed/Fail**: حالات نهائية تُنهي التنفيذ.

سألت Priya: "وماذا لو حاول أحدهم الاختراق أثناء تلك النافذة؟ إذا كان المطعم مُكوّناً جزئياً — حساب الدفع مُنشأ لكن لم يُوافَق عليه بعد — واكتشف أحدهم الحالة المعلّقة، يمكنهم محاولة استغلال التكوين نصف المفتوح."

وبشكل أكثر عملية: كيف توقف سير عمل Step Functions مؤقتاً لثلاثة أيام انتظاراً لإنسان؟

الجواب هو **نمط الاسترجاع (callback) مع رمز مهمة**.

حين تعمل `ValidateLicense`، بدلاً من الاكتمال تلقائياً، تستدعي Lambda تفعل ثلاثة أشياء:

1. ترسل بريداً إلكترونياً إلى مدير الحساب بوثائق المطعم
2. تسجّل **رمز مهمة** (مُعرّف فريد تُولّده Step Functions لهذا التنفيذ والحالة المحددين) في قاعدة بيانات، مرتبطاً بتلك المراجعة المعلّقة
3. تعود إلى Step Functions بـ `.waitForTaskToken` — الذي يخبر Step Functions بإيقاف التنفيذ مؤقتاً عند هذه الحالة إلى أجل غير مسمى

توقف Step Functions التنفيذ. لا شيء آخر مُعطَّل — لا خادم يجلس منتظراً. آلة الحالة تنتظر فحسب، دون استهلاك أي موارد حوسبة.

بعد ثلاثة أيام، ينقر مدير الحساب "موافقة" في أداة الإدارة الداخلية. تبحث أداة الإدارة عن رمز المهمة من قاعدة البيانات وتستدعي:

```python
stepfunctions.send_task_success(
    taskToken=token,
    output=json.dumps({"approved": True, "reviewedBy": "dana.cole@eatnimbus.com"})
)
```

تستأنف Step Functions. يستمر التنفيذ من الخطوة 2 (`ImportMenu`)، مع توفّر معلومات المُراجِع في حالة سير العمل.

قال Leo: "أُوقف التنفيذ لثلاثة أيام، والشيء الوحيد الذي حدث حين وافقت كان استدعاء API واحداً."

سألت Maya: "وإذا رفض مدير الحساب؟"

"نستدعي `send_task_failure` بدلاً من ذلك. آلة الحالة تلتقط ذلك وتُوجّه إلى حالة `NotifyRejection` تراسل شريك المطعم بالبريد الإلكتروني."

Step Functions لا تستقرئ. لا تُعيد المحاولة. لا تنتهي مهلتها (إلا إذا ضبطت مهلة نبضة قلب). تنتظر ببساطة حتى يصل الاسترجاع، ثم تواصل. هذا مختلف جوهرياً عن استقراء قاعدة بيانات أو قائمة انتظار — ولهذا تكون Step Functions مناسبة جداً لسير العمل الذي يمزج خطوات مؤتمتة ويدوية.

**سير العمل القياسي مقابل السريع**

تقدّم Step Functions نوعين من سير العمل:

**سير العمل القياسي (Standard)**:

- أقصى مدة: سنة واحدة
- التنفيذات متينة — الحالة مُدامة، يمكن فحصها وتدقيقها
- تنفيذ مرة واحدة بالضبط (المهمة لا تُشغَّل أبداً أكثر من مرة إلا إذا كوّنت Retry)
- مُسعّر لكل انتقال حالة
- الأنسب لسير العمل المهم طويل التشغيل (معالجة الطلبات، الانضمام، تدفقات الدفع)

**سير العمل السريع (Express)**:

- أقصى مدة: 5 دقائق
- إنتاجية أعلى — حتى 100,000 في الثانية
- تنفيذ مرة على الأقل (غير متزامن) أو على الأكثر مرة (متزامن) — صمّم المهام لتكون خاملة التكرار
- مُسعّر لكل مدة (مثل Lambda)
- الأنسب لسير العمل عالي الحجم قصير المدة (معالجة الأحداث في الوقت الفعلي، استيعاب بيانات إنترنت الأشياء)

سأل Tom وهو يستدعي صفحة التسعير: "كم يكلّف ذلك شهرياً؟ لكل انتقال حالة للقياسي — ذلك يتراكم إذا كان لديك خطوات كثيرة."

شرح Leo الحساب. لسير عمل انضمام المطاعم (ست حالات مهمة لكل تنفيذ، نحو 12-15 مطعماً جديداً شهرياً): أقل من مئة انتقال حالة — أقل من سنت، وداخل الفئة المجانية البالغة 4,000 انتقال شهرياً بالكامل، فعملياً 0 دولار. لسير عمل تأكيد الطلب عند زيارات Nimbus الكاملة: أكثر دلالة، لكن لا يزال أقل بكثير من تكلفة تصحيح إحدى عشرة حالة نجاح جزئي شهرياً يدوياً.

قال Leo: "وقت التصحيح هو التكلفة الخفية."

قال Tom: "تلك دائماً التكلفة الخفية."

حسب Tom الأرقام بعناية أكثر، لأن ذلك كان طبع Tom.

**تكلفة سير العمل القياسي لتدفق تأكيد طلب Nimbus**: خمس حالات لكل طلب على المسار السعيد، بـ 0.000025 دولار لكل انتقال حالة. خمسة انتقالات حالة × 0.000025 دولار × 15,000 طلب شهرياً = **1.88 دولار/شهر**. عند عشرة أضعاف حجم الطلبات: نحو 19 دولاراً/شهر. تكلفة تصحيح حادثة نجاح جزئي واحدة (24 دقيقة من وقت مهندس الدعم) تجاوزت فاتورة Step Functions الشهرية أضعافاً مضاعفة.

تصبح المقارنة مهمة إذا اقترح أحدهم استخدام سير العمل القياسي لأحداث تحليلات عالية التردد. افترض أن Nimbus أرادت استخدام Step Functions لمعالجة كل حدث تدفق نقر خام — كل مشاهدة صفحة قائمة، كل تمرير، كل بحث. ذلك نحو 800,000 حدث يومياً بحجمها الحالي. سير عمل قياسي بخمس حالات لكل حدث: 800,000 × 5 × 0.000025 دولار × 30 يوماً = **3,000 دولار/شهر**. ذلك مال حقيقي لخط أنابيب تحليلات.

سير العمل السريع لذلك الحجم ذاته: مُسعّر لكل طلب إضافة إلى المدة، لا لكل انتقال حالة. الـ 24 مليون تنفيذ شهري تكلّف 1.00 دولار لكل مليون طلب = 24 دولاراً. المدة: 24 مليون × 500 مللي ثانية عند الحد الأدنى للفوترة البالغ 64MB ≈ 208 GB-ساعة × 0.06 دولار = 12.50 دولار. الإجمالي ≈ **36.50 دولار/شهر** — أرخص بنحو مرتبتين من الـ 3,000 دولار للقياسي.

قال Tom: "إذن نوع سير العمل ليس مجرد قرار معماري. إنه قرار تكلفة. العدد ذاته من الحالات يمكن أن يكلّف نحو مئة مرة أكثر تبعاً لأي نوع سير عمل تستخدم."

قال Leo: "وأيهما أفضل يعتمد كلياً على ما يفعله سير العمل. تأكيد الطلب: قياسي. مهم، لديه مسارات إخفاق ذات معنى، نريد أثر التدقيق. معالجة أحداث التحليلات: سريع. عالي الحجم، قصير المدة، ولا نحتاج تاريخ تنفيذ 90 يوماً لكل مشاهدة صفحة."

إذا كان لعمليتك خطوتان ولا تحتاج أثر تدقيق، فدالة Lambda بسيطة أرخص ولا تتطلب صياغة آلة حالة JSON — لكن إذا كانت أي خطوة يمكن أن تفشل بشكل مستقل وتحتاج إعادة محاولة أو إعادة بدء دون تكرار الخطوات الأسبق، فإن Step Functions تدفع ثمن نفسها في تقليل التصحيح والمعالجة اليدوية.

لانضمام مطاعم Nimbus: قياسي (مهم، متين، قد يستغرق ساعات إذا انطوى على خطوات يدوية).

لتحديثات حالة طلبات Nimbus في الوقت الفعلي: سريع (عالي الحجم، قصير المدة، أقل حرجاً).

**المعمارية المدفوعة بالأحداث: الصورة الأكبر**

Step Functions جزء واحد من نمط أكبر: **المعمارية المدفوعة بالأحداث**. بدلاً من استدعاء الخدمات بعضها بعضاً مباشرةً (اقتران محكم)، تبثّ الخدمات أحداثاً، وتتفاعل خدمات أخرى مع تلك الأحداث.

رأينا هذا عبر الكتاب:

- طلبات موضوعة ← SNS ينشر حدثاً ← قوائم انتظار SQS تُقدّم للمستهلكين
- ملف S3 مرفوع ← Lambda مُحفّزة لمعالجته
- سجل DynamoDB تغيّر ← DynamoDB Streams ← Lambda تُحدّث ذاكرة تخزين مؤقت

**Amazon EventBridge** (المعروف سابقاً بـ CloudWatch Events) هو ناقل الأحداث المتقدم لهذا النمط. يُوجّه الأحداث من خدمات AWS وتطبيقاتك الخاصة إلى أهداف (Lambda، SQS، Step Functions، إلخ) بناءً على قواعد.

يتيح EventBridge اقتراناً مرناً على مستوى معماري: خدمة الطلبات تنشر أحداث `order.placed` دون معرفة من يستمع. خدمة التحليلات، وخدمة الإشعارات، وخدمة نقاط الولاء كلها تستمع بشكل مستقل. إضافة مستمع جديد لا تتطلب تغيير خدمة الطلبات.

يتكامل EventBridge أيضاً أصلياً مع عشرات خدمات AWS كـ **مصادر أحداث**. حين يطابق استدعاء API لـ CloudTrail نمطاً، يمكن لـ EventBridge إطلاق قاعدة. حين تغيّر نسخة EC2 حالتها، يمكن لـ EventBridge تحفيز Lambda. حين تتحوّل نسخة RDS، يمكن لـ EventBridge تنبيه المهندس المناوب. يمكنك معاملة مستوى تحكم AWS بأكمله كتدفق أحداث.

بالنسبة لـ Nimbus، قاعدة EventBridge مفيدة بشكل خاص: تحفيز Lambda كلما دُفعت صورة جديدة إلى ECR. تتحقق Lambda من نتيجة فحص الصورة وتنشر إلى قناة Slack الهندسية إذا عُثر على أي CVEs بخطورة HIGH أو CRITICAL — قبل أن ينشر أحد الصورة. هذا يجمع فحص ECR الأمني (من الفصل الحادي والعشرين) مع توجيه أحداث EventBridge في بوابة أمان مؤتمتة.

مبدأ المعمارية المدفوعة بالأحداث هو ذاته كمنطق إعادة محاولة Step Functions: اجعل الإخفاق صريحاً ومُوجَّهاً، لا صامتاً ومُبتلَعاً. الخدمات التي تتواصل عبر الأحداث تفشل برشاقة — إذا كانت Lambda نقاط الولاء معطّلة حين يُطلَق حدث `OrderConfirmed`، يمكن لـ EventBridge إعادة محاولة التقديم أو الإرسال إلى قائمة رسائل ميتة. تأكيد الطلب نفسه لا يتأثر. الفصل هو المرونة.

**EventBridge: فصل الآثار الجانبية عن التدفق الرئيسي**

بعد أن أصبحت آلة حالة تأكيد الطلب تعمل بنظافة، طرحت Maya سؤالاً في مراجعة المعمارية التالية.

"نريد إضافة نقاط ولاء حين يُؤكَّد طلب. يحصل العميل على نقطة واحدة لكل دولار يُنفَق. أين يذهب ذلك في آلة الحالة؟"

غريزة Leo الأولى: إضافة حالة `GrantLoyaltyPoints` بعد `LogTransaction`.

رد Priya: "وحين نُضيف مكافآت الإحالة؟ واستطلاعات ما بعد الطلب؟ وطلبات تقييم المطعم؟ كل واحدة تُضيف حالة إلى المسار الحرج. إذا فشلت Lambda نقاط الولاء، يفشل تأكيد الطلب بأكمله."

قالت: "تدفق تأكيد الطلب ينبغي أن يفعل شيئاً واحداً. يؤكّد الطلب. كل شيء آخر أثر جانبي."

هذه هي الحجة المعمارية لـ **Amazon EventBridge** كآلية لفصل الآثار الجانبية مرنياً عن سير العمل الرئيسي.

النهج المُنقَّح: حين تكتمل حالة `LogTransaction` بنجاح، تنشر Lambda حدثاً إلى EventBridge:

```json
{
  "source": "nimbus.orders",
  "detail-type": "OrderConfirmed",
  "detail": {
    "orderId": "ORD-8812",
    "customerId": "CUST-441",
    "restaurantId": "94",
    "total": 3200,
    "timestamp": "2024-03-15T14:23:43Z"
  }
}
```

ثم تُوجّه قواعد EventBridge ذلك الحدث إلى أهداف مستقلة:

- **القاعدة 1**: `OrderConfirmed` ← Lambda نقاط الولاء (تمنح 32 نقطة لطلب بقيمة 32 دولاراً)
- **القاعدة 2**: `OrderConfirmed` ← Lambda استطلاع ما بعد الطلب (تُدرج استطلاعاً بعد ساعتين من التوصيل)
- **القاعدة 3**: `OrderConfirmed` ← Kinesis Stream للتحليلات (تُغذّي لوحة الوقت الفعلي)

كل قاعدة مستقلة. يمكن أن تفشل Lambda نقاط الولاء دون التأثير على قائمة انتظار الاستطلاع. يمكن لخط أنابيب التحليلات التأخّر دون إعاقة نظام الولاء. إضافة أثر جانبي جديد (طلب تقييم مطعم، إشعار استرداد نقدي) يتطلب إنشاء قاعدة EventBridge جديدة — لا تعديل آلة الحالة.

سألت Priya: "وماذا لو حاول أحدهم الاختراق عبر قاعدة EventBridge؟ إذا احتوى الحدث على بيانات شخصية للعميل، فإن كل Lambda تستقبله أصبحت الآن نقطة وصول لبيانات شخصية."

صُمّم الحدث بعناية: فقط المُعرّفات، لا الأسماء، العناوين، أو تفاصيل الدفع. أي Lambda تحتاج بيانات العميل ستبحث عنها من قاعدة البيانات باستخدام معرّف العميل — مع أذونات IAM الخاصة بها تتحكم بما يمكنها الوصول إليه.

قالت Priya: "الحدث إشارة. لا تفريغ بيانات."

**حين تكون Step Functions الأداة الصحيحة**

تتفوّق Step Functions حين يكون لديك:

**سير عمل متعدد الخطوات** يحتاج تتبّع التقدّم عبر الخطوات

**عمليات بمشاركة بشرية** — يمكن لـ Step Functions الانتظار إلى أجل غير مسمى لحدث خارجي (مثل موافقة إنسان على شيء) ثم المواصلة

**معالجة أخطاء على نطاق** — منطق إعادة المحاولة والالتقاط والاحتياط المدمج عبر خطوات كثيرة

**عمليات قابلة للتدقيق** — كل تنفيذ يسجّل كل انتقال حالة. يمكنك رؤية ما حدث بالضبط ومتى.

**منطق متوازٍ أو تسلسلي معقّد** — سير العمل المرئي يجعل التفكير فيه أسهل من الكود المكافئ

Step Functions مبالغة لعمليات بسيطة من خطوتين. استخدمها حين يكون التنسيق نفسه ذا قيمة وسيناريوهات الإخفاق مهمة.

**حين تكون Step Functions الأداة الخطأ**

سألت Maya في نهاية جلسة التصميم: "لحظة — لكن *لماذا* لا نستخدم Step Functions لكل شيء؟ بنينا سير عمل انضمام المطاعم. لدينا تدفق تأكيد الطلب. لماذا لا نحوّل كل شيء إلى آلات حالة؟"

الجواب الصادق: لأن Step Functions تُضيف عبئاً لا يبرّره كل سير عمل.

**العمليات البسيطة من خطوتين**: إذا كانت لديك Lambda تُعالج ملفاً مرفوعاً باستدعاء Lambda ثانية، فإن عبء التنسيق لآلة حالة لا يستحق الفائدة التشغيلية. Lambda اثنتان تُستدعيان بالتسلسل ضمن دالة واحدة أبسط، أسهل اختباراً، وبلا تكلفة لكل انتقال حالة.

**سير عمل فائق التردد دون الثانية**: سير العمل القياسي له تكلفة غير تافهة لكل انتقال حالة تتراكم عند حجم عالٍ (كما أظهر مثال التحليلات أعلاه). سير العمل السريع يحلّ مشكلة التكلفة لكنه لا يوفّر تاريخ حالة متيناً. عند تردد عالٍ جداً بمدة قصيرة جداً، يكون SQS مع Lambda (النمط من الفصل التاسع عشر) أبسط وأرخص من أي نوع Step Functions.

**التوزيع الصرف بلا تنسيق**: إذا كنت تحتاج إرسال الحدث ذاته إلى عشرين مستهلكاً ولا تهتم بنتيجة كل واحد، فإن SNS هو الأداة. Step Functions تُضيف تتبّع حالة لا تحتاجه وستدفع مقابله دون داعٍ.

**التفاعلات المتزامنة مع المستخدم في الوقت الفعلي**: تنفيذات Step Functions غير متزامنة. إذا كان مستخدم ينتظر عند شاشة دفع لاستجابة متزامنة في أقل من 500 مللي ثانية، فإن سير عمل Step Functions القياسي ليس مُصمَّماً لهذا (يمكن استدعاء سير العمل السريع بشكل متزامن، لكن عبء زمن الاستجابة لا يزال أعلى من استدعاء Lambda مباشر). للتدفقات المتزامنة التي تواجه المستخدم، يكون Lambda + API Gateway مع معالجة أخطاء جيدة التصميم غالباً أكثر ملاءمة.

المبدأ: استخدم Step Functions حين يكون *تنسيق* الخطوات نفسه معقّداً — حين يمكن أن تفشل الخطوات بشكل مستقل، حين تحتاج إعادة محاولة خطوات فردية دون تكرار الأسبق، حين يكون لتاريخ التنفيذ قيمة امتثال أو تصحيح، أو حين ينطوي سير العمل على خطوات موافقة بشرية قد تستغرق أياماً. لا تستخدمها لإضافة عبء تنسيق إلى منطق تسلسلي بسيط يعمل جيداً كدالة واحدة.

## نقاط القوة والقيود

**لماذا Step Functions قوية**:

- تاريخ تنفيذ مرئي — ترى بالضبط أين سير العمل (أو أين فشل)
- إعادة محاولة ومعالجة أخطاء مدمجة — لا كود إعادة محاولة مخصص
- حالة متينة — التنفيذات تنجو من إعادات تشغيل الخدمات والانقطاعات
- تكاملات مباشرة مع أكثر من 200 خدمة AWS (لا Lambda فقط)
- سير العمل المرئي مُوثِّق لذاته
- نمط الاسترجاع يُتيح انتظاراً غير محدود لإجراءات بشرية دون استهلاك حوسبة

**أين يصبح الأمر معقداً**:

- سير العمل القياسي مُسعّر لكل انتقال حالة — سير العمل المعقّد بحالات كثيرة يمكن أن يصبح مكلفاً على نطاق
- تنسيق JSON الخاص بـ ASL (Amazon States Language) له منحنى تعلّم
- أقصى حجم حمولة 256KB — البيانات الكبيرة يجب تمريرها عبر مراجع S3، لا مباشرةً عبر سير العمل
- سير العمل طويل التشغيل بخطوات يدوية كثيرة يتطلب تكوين مهلة دقيقاً
- تصحيح أخطاء ASL يتطلب تشغيل تنفيذات؛ لا يوجد مُحاكي محلي بقدرة الخدمة الحقيقية
- يجب منح أذونات IAM بشكل منفصل لكل مورد تستدعيه آلة الحالة — نسيان إذن واحد يُسبّب خطأً مُربكاً وقت التشغيل

## الملخص

جعلت الحاويات في الفصل الحادي والعشرين عمليات النشر موثوقة. تجعل Step Functions العمليات التجارية متعددة الخطوات موثوقة — المبدأ ذاته "ألغِ مخاطرة التسليم" مُطبَّقاً على منطق التطبيق.

- **Step Functions** تُنسّق سير العمل متعدد الخطوات كآلات حالة.
- كل **حالة** يمكنها تشغيل دالة Lambda، تنفيذ مهمة ECS، الانتظار، التفرّع، أو تشغيل خطوات متوازية.
- **إعادة المحاولة والالتقاط** مدمجان في كل حالة — لا حاجة لكود إعادة محاولة مخصص.
- **سير العمل القياسي**: طويل التشغيل (حتى سنة واحدة)، متين، مرة واحدة بالضبط. للعمليات التجارية الحرجة.
- **سير العمل السريع**: قصير المدة (حتى 5 دقائق)، إنتاجية عالية. لمعالجة الأحداث عالية الحجم.
- **نمط الاسترجاع مع رمز المهمة**: أوقف سير عمل مؤقتاً إلى أجل غير مسمى انتظاراً لحدث خارجي أو إجراء بشري؛ استأنف باستدعاء API واحد.
- **حالة Map**: عالج قائمة عناصر بشكل متزامن — استبدل الحلقات التسلسلية بتوزيع مروحة متوازٍ.
- **تكاملات SDK المباشرة**: استدعِ DynamoDB وS3 وSQS وأكثر من 200 خدمة AWS مباشرةً من حالة، دون غلاف Lambda.
- **EventBridge**: افصل الآثار الجانبية عن سير العمل الرئيسي — انشر حدثاً واحداً، دع قواعد مستقلة تُوجّهه إلى خدمات نقاط الولاء والتحليلات والاستطلاع دون تعديل آلة الحالة الأساسية.
- **تكلفة القياسي مقابل السريع**: القياسي بـ 0.000025 دولار لكل انتقال حالة يعمل جيداً لسير العمل الحرج منخفض الحجم (تأكيد الطلب بـ 1.88 دولار/شهر لـ Nimbus). السريع بتسعير لكل-طلب-إضافة-إلى-المدة مناسب للأحداث عالية التردد حيث سيكلّف القياسي عشرات المرات أكثر (نحو 80 ضعفاً في حساب تدفق نقر Nimbus).
- **المعمارية المدفوعة بالأحداث** تستخدم خدمات مثل SNS وSQS وLambda وEventBridge لفصل الأنظمة حول الأحداث بدلاً من الاستدعاءات المباشرة.
- استخدم Step Functions حين يكون تنسيق الخطوات نفسه معقّداً وحين تهم القابلية للتدقيق. لا تستخدمها لتسلسلات بسيطة من خطوتين، أو سير عمل فائق التردد، أو توزيع صرف، أو تدفقات متزامنة تواجه المستخدم.

## نصائح الامتحان

*SAA-C03 المجال: تصميم معماريات مرنة (المجال الثاني، المهمة 2.1)*

- **إشارات حالة استخدام Step Functions**: "تنسيق دوال Lambda متعددة"، "سير عمل بإعادات محاولة ومعالجة أخطاء"، "خطوة موافقة بشرية في سير عمل مؤتمت"، "أثر تدقيق لكل خطوة سير عمل" ← Step Functions.
- **القياسي مقابل السريع**: القياسي لسير العمل طويل التشغيل القابل للتدقيق الحرج للأعمال. السريع لمعالجة أحداث عالية الإنتاجية قصيرة المدة.
- **SQS مقابل Step Functions**: SQS لقوائم مهام بسيطة (منتج/مستهلك). Step Functions لسير عمل متعدد الخطوات بمنطق معقّد وإعادات محاولة وتتبّع حالة.
- **إشارات EventBridge**: "توجيه أحداث من خدمات AWS إلى أهداف"، "تكامل مدفوع بالأحداث بين الخدمات"، "جدولة دالة Lambda" ← EventBridge (المعروف سابقاً بـ CloudWatch Events).
- **نمط الاسترجاع**: يمكن لـ Step Functions إيقاف التنفيذ مؤقتاً وانتظار استرجاع خارجي (رمز مهمة). يعود العامل بالاتصال حين ينتهي. مفيد لمهام ECS طويلة التشغيل حيث لا تريد حد Lambda البالغ 15 دقيقة.
- **تكاملات SDK المباشرة**: يمكن لـ Step Functions استدعاء خدمات AWS مباشرةً (DynamoDB، S3، SQS، إلخ) دون المرور عبر Lambda. يُقلّل التكلفة وزمن الاستجابة لاستدعاءات الخدمة البسيطة. مثلاً، كتابة سجل طلب إلى DynamoDB يمكن أن تكون استدعاء SDK مباشراً من آلة الحالة دون دالة Lambda: `"Resource": "arn:aws:states:::dynamodb:putItem"`. هذا يُلغي إقلاع Lambda البارد، وتكلفة تنفيذ Lambda، والكود الذي يستدعي فقط `dynamodb.put_item(...)` ويعود.

## التمارين

**تمرين 2 — سيناريو SAA-C03**

*سيناريو*: شركة خدمات مالية تُعالج طلبات القروض في خطوات متعددة: فحص ائتماني، التحقق من الدخل، التحقق من الوثائق، مراجعة المُكتتب (يدوية)، وإشعار القرار. كل خطوة يمكن أن تستغرق ما بين ثوانٍ (الفحص الائتماني) إلى أيام (مراجعة المُكتتب). تحتاج الشركة أثر تدقيق كاملاً لكل خطوة للامتثال. الخطوات المؤتمتة الفاشلة يجب أن تُعيد المحاولة تلقائياً؛ الخطوات اليدوية يجب أن تتوقف مؤقتاً وتنتظر قراراً بشرياً.

أي خدمة تلبّي هذه المتطلبات على أفضل وجه؟

A) دوال AWS Lambda مُسلسَلة معاً مع قوائم انتظار SQS بين كل خطوة  
B) سير عمل AWS Step Functions القياسي مع نمط Wait للاسترجاع لخطوة مراجعة المُكتتب  
C) سير عمل AWS Step Functions السريع للخطوات المؤتمتة وSQS FIFO للخطوة اليدوية  
D) Amazon EventBridge مع قواعد أحداث تُوجّه بين دوال Lambda لكل خطوة

**تلميح 1**: مدة "حتى أيام" — أي نوع Step Functions يدعم هذا؟

**تلميح 2**: "انتظار قرار بشري" — أي نمط Step Functions مُصمَّم لهذا؟

**تلميح 3**: "أثر تدقيق كامل للامتثال" — أي خدمة توفّر تاريخ حالة لكل تنفيذ؟

**الإجابة**: B

**الشرح**: سير عمل Step Functions القياسي يمكن أن يعمل حتى سنة واحدة، داعماً خطوة مراجعة المُكتتب التي تستغرق أياماً. نمط Wait للاسترجاع يوقف التنفيذ مؤقتاً عند خطوة المُكتتب برمز مهمة؛ حين يتخذ المُكتتب قراراً، يعود بالاتصال بالرمز لمواصلة سير العمل. سير العمل القياسي يسجّل كل انتقال حالة — أثر تدقيق كامل للامتثال.

**لماذا ليس A؟** Lambda مُسلسَلة عبر SQS لا توفّر تتبّع حالة أو أثر تدقيق مدمجاً. الخطوات الفاشلة تتطلب منطق إعادة محاولة مخصصاً. إعادة البدء من خطوة فاشلة محددة تتطلب تنفيذاً مخصصاً.

**لماذا ليس C؟** سير العمل السريع له أقصى مدة 5 دقائق — غير متوافق مع خطوة يمكن أن تستغرق أياماً.

**لماذا ليس D؟** EventBridge يُوجّه الأحداث بين الخدمات لكنه لا يحافظ على حالة سير العمل أو يوفّر إعادة محاولة/تدقيق مدمجاً. بناء هذا على EventBridge وحده يتطلب إدارة حالة مخصصة.

*SAA-C03 المجال: تصميم معماريات مرنة — المهمة 2.1*

**تمرين 3 — تحدي المعمارية** *(اختياري)*

تبني Nimbus عملية حلّ نزاعات جودة الطعام. حين يُبلّغ عميل عن تجربة سيئة:

1. يُتحقَّق من البلاغ تلقائياً (يفحص ما إذا كان الطلب موجوداً، وما إذا كان حديثاً بما يكفي)
2. يُخطَر المطعم تلقائياً
3. يراجع وكيل دعم Nimbus الشكوى (خطوة يدوية — يمكن أن تستغرق 1-3 أيام عمل)
4. بناءً على قرار الوكيل: إصدار استرداد (Lambda ← معالج الدفع) أو إرسال قسيمة اعتذار (Lambda ← خدمة القسائم) أو التصعيد للإدارة (سير عمل فرعي لـ Step Functions)
5. يُخطَر العميل بالنتيجة
