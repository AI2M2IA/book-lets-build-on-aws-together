**ثلاث فئات من التهديدات**

تقع التهديدات الأمنية ضد التطبيقات السحابية عموماً في ثلاث فئات:

**هجمات الحجم (DDoS)**: يُرسل مهاجم حركة مرور هائلة حتى لا يتمكن تطبيقك من الاستجابة للمستخدمين الشرعيين. قد يكون الهجوم ملايين طلبات HTTP، أو فيضاناً من حزم SYN مصمَّماً لاستنفاد جدول اتصالات خادمك.

**هجمات التطبيق (الاستغلال)**: يُرسل مهاجم طلبات مُعدَّة خصيصاً لاستغلال نقاط ضعف في تطبيقك — حقن SQL، سكريبت عبر المواقع، إدخال مشوَّه يُعطّل محلّلاً.

**الشذوذات السلوكية (الاستكشاف والاختراق)**: استدعاءات API لا ينبغي أن تحدث (شخص يستعلم قاعدة مستخدميك كاملة الساعة 3 صباحاً)، نشاط IAM غير عادي (بيانات اعتماد تُستخدم من دولة جديدة)، أو حركة شبكة لوجهات غير متوقعة.

لدى AWS خدمة مخصصة لكل منها:

- **AWS Shield**: حماية من DDoS
- **AWS WAF**: حماية طبقة التطبيق
- **Amazon GuardDuty**: كشف التهديدات السلوكية

**AWS Shield: ماصّ DDoS**

**AWS Shield Standard** مُفعَّل تلقائياً لجميع عملاء AWS بدون رسوم إضافية. يحمي من هجمات DDoS الطبقة 3 (الشبكة) والطبقة 4 (النقل) الأكثر شيوعاً — فيضانات SYN، فيضانات UDP، هجمات تضخيم DNS.

CloudFront وRoute 53 وElastic Load Balancing تقع على حافة شبكة AWS. حين يستهدف هجوم DDoS تطبيقك، يضرب هذه الخدمات المُدارة أولاً. البنية التحتية لشبكة AWS تمتصّ الهجوم قبل وصوله إلى نسخ EC2 الخاصة بك.

**AWS Shield Advanced** هو الطبقة المميزة (3,000 دولار/شهر لكل منظمة، بالتزام لسنة واحدة). إنه اشتراك منفصل — *ليس* مُضمَّناً في أي خطة دعم AWS. يضيف:

- حماية لـ EC2 وELB وCloudFront وGlobal Accelerator وRoute 53
- إشعارات هجمات شبه آنية
- وصول إلى فريق AWS Shield Response (SRT) — مهندسو أمن يمكنهم مساعدتك في الاستجابة للهجمات (الاستعانة بـ SRT تتطلب إضافةً خطة دعم Business أو Enterprise)
- حماية التكلفة: إذا تسبّب هجوم في ارتفاع فاتورتك، تُضيف AWS رصيداً لتكاليف الارتفاع
- كشف وتخفيف DDoS محسّن على الطبقة 7 (طبقة التطبيق)

**AWS WAF: مرشّح التطبيق**

يعمل **AWS WAF (جدار حماية تطبيقات الويب)** على مستوى HTTP — يفحص محتوى طلبات الويب قبل وصولها إلى تطبيقك.

يُضبط WAF بـ **قوائم تحكم الويب في الوصول (Web ACLs)** — مجموعات قواعد تُحدد ما يُسمح به أو يُحجب أو يُعدّ.

يمكن إرفاق WAF بـ:

- توزيعات CloudFront (فحص الطلبات في الحافة، عالمياً)
- Application Load Balancers (فحص الطلبات على المستوى الإقليمي)
- API Gateway
- AWS AppSync

**قواعد WAF المُدارة**: تنشر AWS وبائعون خارجيون مجموعات قواعد جاهزة:

- **قواعد AWS المُدارة - مجموعة القواعد الأساسية**: مع مجموعات قواعد مرافقة (قاعدة بيانات SQL، المدخلات السيئة المعروفة)، تغطّي ثغرات OWASP Top 10 (حقن SQL، XSS، حقن الأوامر، اجتياز المسار، إلخ)
- **قواعد AWS المُدارة - المدخلات السيئة المعروفة**: تحجب الطلبات المطابقة لأنماط هجوم معروفة
- **قواعد AWS المُدارة - قائمة سمعة IP الخاصة بـ Amazon**: تحجب IPs المعروفة بارتباطها بشبكات روبوتات ومحركات فحص
- **قواعد AWS المُدارة - التحكم في الروبوتات**: تُحدد حركة الروبوتات وتُديرها

يمكنك أيضاً إنشاء قواعد مخصصة:

- "احجب أي طلب يحتوي ترويسة User-Agent على 'sqlmap'" (ماسح حقن SQL شائع)
- "تحديد المعدل: لا تسمح بأكثر من 1000 طلب لكل IP كل 5 دقائق"
- "احجب الطلبات التي تحتوي `<script>` في أي قيمة معامل"

بالنسبة لـ Nimbus، الإعداد العملي: WAF على توزيع CloudFront مع تفعيل مجموعة القواعد الأساسية. هذا يحجب أكثر أنماط الهجوم شيوعاً قبل وصول الطلبات إلى نسخ EC2.

قد تتساءل: إذا كان WAF يحجب أنماط الهجوم المعروفة، فماذا يحدث حين يظهر نمط هجوم جديد لا يعرفه WAF؟ تُحدَّث مجموعات قواعد WAF المُدارة من قِبَل AWS وبائعين خارجيين كلما ظهرت تهديدات جديدة — لا تضطر إلى تحديث القواعد يدوياً. لكنك محقّ أن WAF تفاعلي جوهرياً مع الأنماط المعروفة. تقنيات الهجوم الجديدة والمبتكرة لن تُحجب بقاعدة لا توجد بعد. لهذا توجد GuardDuty بجانب WAF: WAF يُرشّح الباب الأمامي، GuardDuty يراقب السلوك غير العادي داخل المنزل. قد يمر نوع هجوم جديد عبر WAF، لكن GuardDuty لا تزال تستطيع الإبلاغ عن النشاط الشاذ الذي يُسبّبه — استدعاءات API غير عادية، وجهات شبكة غير متوقعة، أنماط وصول لا تطابق الأساس.

أنشأت قاعدة WAF مخصصة قائمة على المعدل:


**Amazon GuardDuty: المحلل السلوكي**

سألت Maya: "مهلاً — لكن *لماذا* نفعل ذلك بهذه الطريقة؟ إذا كان WAF يحجب الهجمات وShield يمتصّ الفيضانات، فلماذا نحتاج خدمة ثالثة؟ ما الذي تراقبه GuardDuty فعلاً؟"

WAF وShield مرشّحان — يعترضان الزيارات السيئة قبل وصولها إلى تطبيقك. GuardDuty تراقب ما يحدث بعد وصول الزيارات. تنظر إلى ما تفعله بنيتك التحتية: أي بيانات اعتماد IAM تُستخدم، أي نطاقات تتصل بها نسخك، أي استدعاءات API تحدث الساعة 3 صباحاً. مهاجم يمر عبر الباب الأمامي بطلب يبدو مشروعاً لن يوقفه WAF — لكن GuardDuty ستلاحظ أن نفس بيانات الاعتماد تُجري فجأةً استدعاءات API من رومانيا.

GuardDuty مختلفة جوهرياً عن Shield وWAF. لا تحجب الهجمات — تـ**كشف السلوك غير العادي**.

تُحلّل GuardDuty باستمرار عدة تدفقات نشاط لكشف التهديدات: **أحداث إدارة وبيانات CloudTrail** (استدعاءات API والإجراءات)، **سجلات تدفق VPC** (أنماط حركة الشبكة)، و**سجلات استعلامات DNS** (عمليات البحث عن النطاقات). هذه المصادر الثلاثة الأساسية التي اعتمدت عليها GuardDuty دائماً:

- **سجلات AWS CloudTrail**: تغييرات IAM، استدعاءات API، تسجيلات الدخول للوحة التحكم
- **سجلات تدفق VPC**: أنماط حركة الشبكة داخل VPC
- **سجلات استعلامات DNS**: ما الذي تحلّه نسخك (البرمجيات الخبيثة المعروفة تحلّ كثيراً نطاقات C2 محددة)

لكن GuardDuty توسّعت بشكل كبير بما يتجاوز هذه الثلاثة. تُسمّي AWS الإضافات الاختيارية **خطط الحماية** — حماية S3، حماية EKS، حماية RDS، حماية Lambda، مراقبة وقت التشغيل، وحماية البرمجيات الخبيثة — كلٌّ مُفعَّل بشكل فردي. بحسب ما تُفعّله، يمكن لـ GuardDuty أيضاً تحليل **أحداث بيانات S3** (أنماط وصول غير عادية لدلواتك)، **سجلات تدقيق EKS ونشاط وقت التشغيل** (سلوك خبيث داخل حاويات عاملة)، **أحداث تسجيل دخول RDS** (محاولات تسجيل دخول شاذة لقاعدة البيانات)، **حركة شبكة Lambda** (دوال تتصل بوجهات خارجية غير متوقعة)، **سلوك وقت تشغيل ECS/EC2**، و**أقراص EBS مفحوصة بحثاً عن برمجيات خبيثة**. للاختبار، اعرف المصادر الأساسية الثلاثة عن ظهر قلب؛ خطط الحماية تظهر في سيناريوهات عن سياقات كشف تهديدات محددة — "كشف محاولات تسجيل دخول شاذة لـ RDS" أو "تحديد سلوك خبيث داخل حاوية عاملة" إشارات للتفكير في خطط حماية GuardDuty الاختيارية.

نماذج تعلم الآلة تُحدد الأنماط التي تنحرف عن خطّك الأساسي. تُنشئ GuardDuty **نتائج** — تنبيهات مُصنَّفة — عند اكتشاف شذوذات.

أمثلة على ما يمكن لـ GuardDuty كشفه:

- مستخدم IAM يسجّل دخولاً من عنوان IP غير معروف (في بلد لم يستخدمه من قبل)
- استدعاءات API تُجرى من عقدة خروج Tor

- حجم استدعاء API مرتفع بشكل غير عادي (إساءة استخدام بيانات اعتماد أو فحص)
- وصول إلى دلو S3 من عنوان IP مُبلَّغ عنه لنشاط خبيث

**خمسة أنواع نتائج GuardDuty وماذا تفعل**

أنشأت Priya دليل تشغيل لأكثر خمس نتائج GuardDuty شيوعاً. حين تُطلَق نتيجة، يعرف الفريق فوراً ما تعنيه وما يفعل.

**1. UnauthorizedAccess:IAMUser/ConsoleLoginSuccess.B**

مستخدم IAM سجّل دخولاً بنجاح إلى وحدة تحكم AWS من عنوان IP لم يُشاهَد لهذا الحساب من قبل، أو من موقع جغرافي غير متسق مع تسجيلات الدخول السابقة.

الاستجابة: تحقّق مع المستخدم أنه بدأ تسجيل الدخول. إن لم يفعل — أو تعذّر الوصول إليه — فوراً: عطّل مفتاح وصول المستخدم وكلمة مرور وحدة التحكم، ألغِ الجلسات النشطة، وابدأ تدقيق CloudTrail لكل ما فعله ذلك المستخدم في آخر 24 ساعة. هذه النتيجة كثيراً ما تسبق إساءة استخدام بيانات الاعتماد.

**2. CryptoCurrency:EC2/BitcoinTool.B**

نسخة EC2 تستعلم عناوين IP أو أسماء نطاقات مرتبطة بتجمّعات تعدين العملات المشفّرة. هذا دائماً تقريباً نتيجة اختراق نسخة EC2 واستخدامها كروبوت تعدين.

الاستجابة: اعزل النسخة فوراً — عدّل مجموعة أمانها لحجب كل الزيارات الواردة والصادرة عدا مضيف البروز. خذ لقطة جنائية لقرص EBS. ثم أوقف النسخة وأطلق بديلاً من AMI نظيف.

**3. Recon:EC2/PortProbeUnprotectedPort**

نسخة EC2 لها منفذ مفتوح للإنترنت يُتحسّس من ماسحات معروفة أو من عقدة خروج Tor. تُعلّم GuardDuty المنافذ التي تظهر في سجلات التدفق كقابلة للوصول من مصادر خارجية.

الاستجابة: راجع قواعد مجموعة الأمان. إذا كان المنفذ مفتوحاً عمداً، علّم النتيجة كمُحلّة مع ملاحظة. إن لم يكن عمدياً، أغلق المنفذ فوراً. تحقّق من CloudTrail لأي وصول قد يكون حدث عبر ذلك المنفذ.

**4. Trojan:EC2/BlackholeTraffic**

نسخة EC2 تحاول التواصل مع عنوان IP حُدّد كـ "ثقب أسود" — وجهة مرتبطة ببنية تحتية لأوامر والتحكم في البرمجيات الخبيثة. الزيارات لهذه IPs تشير إلى أن النسخة أُصيبت وتحاول الاتصال بالمنزل.

الاستجابة: نفس نتائج CryptoCurrency — اعزل، خذ لقطة، استبدل. تشير هذه النتيجة إلى برمجيات خبيثة نشطة على النسخة. لا تحاول تنظيف النسخة في مكانها؛ ابنِ واحدة جديدة من AMI نظيف.

**5. Policy:S3/BucketBlockPublicAccessDisabled**

عطّل أحدهم إعداد Block Public Access على دلو S3. هذا لا يعني أن الدلو عام — يعني أن آلية الأمان التي تمنع التعرّض العام العرضي قد أُوقفت لذلك الدلو. كثيراً ما يُفعَل هذا عرضياً أو كجزء من نشر مضبوط خطأً.

الاستجابة: حقّق فيمن أجرى التغيير (CloudTrail سيحتوي استدعاء API). أعِد تفعيل Block Public Access ما لم يكن هناك سبب موثّق لتعطيله. فكّر في تفعيل إعداد Block Public Access على مستوى الحساب لمنع حدوث هذه النتيجة مستقبلاً.

قالت Priya: "أهم شيء حول نتائج GuardDuty أنها ليست تنبيهات — إنها فرضيات. كل نتيجة تقول 'هذا النمط يبدو شاذاً.' تتحقق، تحقّق، تستجيب. بعضها سيكون إيجابيات زائفة. معظمها لن يكون."

**ربط الخدمات الثلاث**

Shield وWAF وGuardDuty تعمل على طبقات مختلفة وتُكمل بعضها:

| الخدمة | الطبقة | تحمي من | الإجراء |
|--------|---------|---------|---------|
| AWS Shield | الشبكة/النقل (L3/L4) | فيضانات DDoS | تمتصّ/تخفّف الهجمات |
| AWS WAF | التطبيق (L7) | OWASP Top 10، روبوتات، كاشطات | تسمح أو تحجب أو تعدّ الطلبات |
| GuardDuty | السلوكي (جميع السجلات) | الشذوذات، بيانات الاعتماد المخترقة، البرمجيات الخبيثة | تكتشف وتُنبّه |

Shield يوقف الفيضان. WAF يُرشّح الماء. GuardDuty يراقب السباكة للأنماط غير العادية. Macie تدقّق ما هو مخزّن في الخزانات. Security Hub هي غرفة التحكم حيث كل لوحات التحكم مرئية دفعةً واحدة.

نمط فشل كل واحدة يشرح لماذا تحتاجها جميعاً:

- فيضان SYN بخمسين جيجابت/ث ليس طلب ويب. WAF لا يستطيع فحصه. GuardDuty قد تلاحظ أحداث CloudTrail المرتبطة. Shield يوقفه.
- طلب حقن SQL واحد ليس فيضاناً. Shield يتجاهله. GuardDuty لا تعرف محتوى طلبات HTTP. WAF يلتقطه.
- مستخدم AWS شرعي يستخدم بيانات اعتماده الخاصة لتسريب البيانات ببطء — لا DDoS، لا حقن، HTTP صالح — Shield وWAF لا يريان شيئاً غير عادي. GuardDuty تلاحظ أن بيانات الاعتماد تُستخدم من بلد جديد الساعة 3 صباحاً.
- مطوّر يرفع عرضياً بيانات عملاء إلى دلو قابل للوصول العام لا يولّد أي سلوك شاذ بتاتاً. GuardDuty ليس لديها ما تُعلّمه. Macie تفحص الدلو وتجد المعلومات الشخصية.

كل خدمة لها نقطة عمياء. المجموعة تغطّي تلك النقاط العمياء.

**CloudTrail: الأساس**

تعتمد جميع الخدمات الثلاث على السجلات. **AWS CloudTrail** هي خدمة التسجيل التي تلتقط كل استدعاء API في حسابك على AWS — من استدعاها، من أين، متى، وما النتيجة.

CloudTrail مُفعَّلة افتراضياً لسجل 90 يوماً في لوحة التحكم. للاحتفاظ بالسجلات على المدى الطويل:

1. إنشاء مسار يكتب إلى دلو S3
2. اختيارياً، الإرسال إلى سجلات CloudWatch للتنبيه الفوري
3. تفعيل التحقق من ملف السجل (للكشف عن التلاعب بالسجلات)

GuardDuty وAWS Config وSecurity Hub ومحلل وصول IAM يقرأون جميعاً من CloudTrail. بدون سجلات CloudTrail، هذه الخدمات ليس لديها ما تُحلّله.

سألت Priya: "ماذا لو حاول أحد تعطيل CloudTrail؟ إذا حصل مهاجم على وصول مسؤول، قد يكون أول إجراء له تعطيل التسجيل — إخفاء آثاره."

قال Leo: "هذا ما تمنعه SCP من الفصل 14. لا أحد في هذا الحساب يمكنه تعطيل CloudTrail، حتى المسؤولون."

**Amazon Macie: البيانات الحساسة في S3**

سألت Priya: "هل فكّرنا فيما يحدث إذا رفع أحدهم عرضياً ملفاً بأرقام بطاقات ائتمان عملاء إلى S3؟ ليس بخبث — مجرد مطوّر يُصدّر بيانات للتصحيح ويرفع الملف الخطأ؟"

**Amazon Macie** هي خدمة أمان بيانات تستخدم تعلم الآلة لاكتشاف وحماية البيانات الحساسة في S3 تلقائياً. تفحص دلوات S3 باستمرار وتُحدد:

- المعلومات الشخصية (PII): الأسماء، عناوين البريد، أرقام الهواتف، تواريخ الميلاد
- البيانات المالية: أرقام بطاقات الائتمان، أرقام الحسابات المصرفية
- بيانات الاعتماد: كلمات المرور، مفاتيح الوصول، المفاتيح الخاصة المُضمَّنة في الملفات
- المعلومات الصحية: سجلات المرضى، التشخيصات

تُنشئ Macie نتائج حين تكتشف بيانات حساسة في أماكن لا ينبغي أن تكون فيها — أو حين يكون لدلوات S3 ضبط وصول متساهل أكثر من اللازم.

**AWS Security Hub: لوحة التحكم**

إذا كنت تُشغّل حسابات AWS متعددة أو تحتاج إلى رؤية موحّدة للنتائج الأمنية، تُجمّع **AWS Security Hub** النتائج من GuardDuty وInspector (تقييم الثغرات) وMacie (خصوصية البيانات) وConfig وFirewall Manager في لوحة تحكم واحدة.

كما يتحقق من تكوينك مقابل أفضل ممارسات الأمان (معيار AWS Foundational Security Best Practices) ومعيار CIS AWS Foundations Benchmark.

Security Hub هو الإجابة على "كيف أرى كل نتائجي الأمنية في مكان واحد دون التبديل بين خمس وحدات تحكم مختلفة؟" حين تُنشئ GuardDuty نتيجة، تظهر في GuardDuty وفي Security Hub. حين تجد Macie بيانات حساسة في دلو S3، تظهر في Macie وفي Security Hub. حين تكتشف قاعدة Config ضبطاً خاطئاً، تظهر في Config وفي Security Hub.

لفريق بحساب واحد، يضيف Security Hub قيمة هامشية — إنه وحدة تحكم أخرى للتحقق منها. تظهر قوته على نطاق واسع: ثلاثة حسابات، عشرة حسابات، خمسون حساباً. كل النتائج من كل الحسابات تتجمّع في Security Hub لحساب الإدارة. فريق واحد يراقب لوحة تحكم واحدة. مجموعة تنبيهات واحدة. لا فحص سجلات حساباً بحساب.

بالنسبة لـ Nimbus: لم يكن Security Hub ضرورياً بعد. حين ينمو إلى ثلاثة حسابات (تطوير، تجريب، إنتاج)، سيصبح أساسياً.

قالت Soo-Jin في أسبوعها الثالث: "أعدّه الآن. يستغرق تفعيله خمس عشرة دقيقة. ويستغرق ثلاثة أشهر لتتمنّى لو فعلته مبكراً."

**Amazon Inspector: تقييم الثغرات**

بعد أسبوع من تفعيل Macie، نُشر CVE لإصدار OpenSSL العامل عبر أسطول إنتاج Nimbus. قرأت Priya الإرشاد على القهوة.

قالت: "نحتاج إلى معرفة أي من نسخنا متأثرة."

قال Leo: "يمكنني تشغيل فحص يدوي."

قالت Priya وهي تفتح وحدة تحكم Inspector: "لتسع نسخ، بالتأكيد. لتسعين؟ للحاويات؟ هذا ما يوجد Inspector من أجله."

**Amazon Inspector** هي خدمة تقييم ثغرات آلية. حيث تراقب GuardDuty السلوك — ما تفعله بنيتك التحتية الآن — ينظر Inspector إلى ما هو موجود قابل للاستغلال.

- **نسخ EC2:** يفحص Inspector نظام التشغيل والحزم المثبَّتة مقابل NVD (قاعدة بيانات الثغرات الوطنية) — الكتالوج المرجعي لـ CVEs المعروفة. إذا كنت تُشغّل OpenSSL 1.1.1 واستهدف CVE ذلك الإصدار، يُعلّمه Inspector.
- **صور حاويات ECR:** يفحص Inspector صور الحاويات في Elastic Container Registry قبل نشرها. حزمة ضعيفة في صورة أساس تظهر كنتيجة قبل تشغيل الحاوية أبداً في الإنتاج.
- **حزم دوال Lambda:** يُحلّل Inspector التبعيات المُجمَّعة في دوال Lambda — حزم Python، وحدات Node، تبعيات Java — بحثاً عن ثغرات معروفة.

الفرق الحاسم عن الفحص لمرة واحدة: يعمل Inspector **باستمرار**. لا يفحص نسخك مرة واحدة فقط حين تُفعّله ويعلن نظافتها. حين يُنشَر CVE جديد، يُعيد Inspector تقييم مواردك الموجودة تلقائياً مقابل الثغرة الجديدة. حين تتغير نسخة EC2 — حزمة جديدة مثبّتة، AMI مُحدَّث — يُعيد Inspector فحصها. أسطول EC2 الخاص بـ Priya أُعلِم بـ CVE الخاص بـ OpenSSL خلال دقائق من تفعيل Inspector، لا لأنها طلبت منه الفحص، بل لأن ذلك ما يفعله.

النتائج مُصنَّفة بالخطورة: حرجة، عالية، متوسطة، منخفضة، إعلامية. تتدفق إلى Security Hub جنباً إلى جنب مع نتائج GuardDuty وMacie. لوحة تحكم واحدة. ثلاث عدسات.

قال Leo وهو يقرأ نتائج Inspector: "ثلاث نسخ متأثرة. الست الأخريات على إصدار مُصحَّح."

قالت Priya: "صحّح تلك الثلاث هذا الأسبوع."

"ماذا عن صور الحاويات؟"

نظرت Priya إلى نتائج ECR في Inspector. صورتا أساس في سجل حاوياتهم بهما ثغرات معروفة — إصدارات أقدم من حزم صُحّحت منذ ذلك الحين. علّمتهما لإعادة البناء.

قالت Priya: "الشيء المهم أننا وجدنا هذا قبل استغلاله. لا بعده."

**نموذج العدسات الثلاث**

GuardDuty وInspector وMacie كلٌّ تراقب شيئاً مختلفاً:

- **GuardDuty** سلوكية. تسأل: *ما الذي يحدث الآن ويبدو خاطئاً؟* استدعاءات API من مواقع غير متوقعة، نسخ EC2 تتصل بخوادم أوامر وتحكم، بيانات اعتماد تُستخدم في ساعات غير عادية. تلتقط التهديدات النشطة والشذوذات.
- **Inspector** هيكلية. تسأل: *ما الموجود في بيئتنا القابل للاستغلال؟* حزم غير مُصحَّحة، تبعيات ضعيفة، أنظمة تشغيل قديمة. تلتقط الظروف التي تجعل الهجمات ممكنة.
- **Macie** عن البيانات. تسأل: *ما المعلومات الحساسة الموجودة في دلوات S3 لدينا التي لا ينبغي أن تكون هناك؟* المعلومات الشخصية، السجلات المالية، بيانات الاعتماد المتروكة في الملفات. تلتقط التعرّض الذي لا يولّد سلوكاً شاذاً — مجرد بيانات في المكان الخطأ.

اختراق يتضمن CVE معروفاً قد يظهر في الثلاثة: Inspector كان سيُعلّم الثغرة قبل الهجوم. GuardDuty ستُعلّم السلوك الشاذ أثناء الهجوم. Macie ستُعلّم البيانات المُسرَّبة بعد هبوطها في S3.

ثلاث عدسات مختلفة، ثلاثة آفاق زمنية مختلفة، لا واحدة منها بديل عن الأخريات.

**AWS Network Firewall: مفتّش الزيارات**

متخصص آخر يستحق الذكر قبل إغلاق صندوق الأدوات. مجموعات الأمان وNACLs (الفصل 15) تُرشّح الزيارات بحسب IP والمنفذ والبروتوكول — يمكنها قول *من* قد يتحدث مع *ماذا*، لكن لا يمكنها النظر داخل المحادثة. **AWS Network Firewall** هو جدار حماية مُدار ذو حالة تنشره على مستوى VPC. يُجري فحص رزم عميقاً: ترشيح بحسب اسم النطاق (السماح بالصادر فقط إلى `*.eatnimbus.com` ومستودعات حزمك)، حجب الزيارات المطابقة لتوقيعات الاختراق (IDS/IPS، متوافق مع قواعد Suricata)، وفحص التدفقات التي ستمرّرها مجموعات الأمان ببساطة لأن رقم المنفذ بدا سليماً.

قال Leo: "إذن إنها مجموعة أمان بعقل."

قالت Priya: "إنها الجهاز الذي ستشتريه من بائع جدران حماية، لكن مُدار، يتوسع تلقائياً، ومنشور في شبكته الفرعية الخاصة بحيث تُوجَّه كل الزيارات داخل وخارج VPC عبره."

إشارات الاختبار: "فحص أو ترشيح الزيارات بحسب اسم النطاق أو الحمولة"، "كشف/منع الاختراق (IDS/IPS) لـ VPC"، أو "ترشيح خروج مركزي للزيارات الصادرة" ← Network Firewall. مجموعات الأمان وNACLs هي الإجابة للسماح/الرفض على مستوى النسخة والشبكة الفرعية بحسب المنفذ وIP؛ Network Firewall هو الإجابة حين يتطلب السؤال فحصاً *داخل* الزيارات. وحين يسأل السؤال كيف تُدير قواعد WAF وShield Advanced ومجموعات الأمان *و*سياسات Network Firewall باتساق عبر حسابات كثيرة — فتلك **AWS Firewall Manager**، طبقة إدارة السياسات في الأعلى.

## نقاط القوة والقيود

**AWS Shield**:

- Standard: مجاني وتلقائي — لا سبب لعدم استخدامه
- Advanced: ممتاز للأهداف عالية الملف الشخصي؛ مكلف للفرق الصغيرة
- Standard يمتصّ هجمات الطبقة 3/4 (فيضانات SYN، فيضانات UDP، تضخيم DNS) تلقائياً
- Advanced يضيف حماية الطبقة 7، وإشعارات آنية، وفريق Shield Response

**AWS WAF**:

- مجموعات القواعد المُدارة تُبسّط الإعداد بشكل كبير — حماية OWASP Top 10 ببضع نقرات
- القواعد المخصصة تتطلب فهم أنماط هجوم HTTP
- تحديد المعدل ميزة قوية كثيراً ما تُهمَل — فعّالة ضد الكاشطات والقوة الغاشمة
- WAF ليس بديلاً لكود تطبيق آمن — إنه طبقة دفاع معمّق
- ابدأ في وضع العدّ، تحقّق، ثم انتقل إلى الحجب

**GuardDuty**:

- جهد منخفض جداً للتفعيل (بضع نقرات، تجربة مجانية 30 يوماً)
- النتائج تتطلب مراجعة بشرية وإجابة — GuardDuty تكتشف، لا تُصلح
- تحدث إيجابيات زائفة — بعض النشاط المشروع يبدو شاذاً لنماذج ML
- مستويات الخطورة (منخفض/متوسط/عالٍ) تساعد على ترتيب أولوية الاستجابة
- تتكامل مع Security Hub وEventBridge وLambda لسير عمل استجابة آلية

**Amazon Inspector**:

- فحص ثغرات مستمر وآلي — ليس تحققاً لمرة واحدة
- يُعيد الفحص تلقائياً حين تُنشَر CVEs جديدة أو حين تتغير الموارد
- يغطّي نسخ EC2 (حزم نظام التشغيل والتطبيق)، صور حاويات ECR، وحزم دوال Lambda
- النتائج تتدفق إلى Security Hub؛ تصنيفات الخطورة تساعد على ترتيب أولوية التصحيح
- لا يحجب الهجمات — يُظهر الظروف التي تجعل الهجمات ممكنة

**Amazon Macie**:

- تكتشف البيانات الحساسة تلقائياً (المعلومات الشخصية، بيانات الاعتماد، البيانات المالية) في S3
- تلتقط تعرّض البيانات الذي ليس له نمط سلوك شاذ — GuardDuty ستفوّته
- تجربة مجانية 30 يوماً؛ تدفع لكل دلو شهرياً بعد ذلك
- الأكثر قيمة للفرق ذات الدلوات الكثيرة ومستويات الحساسية المتفاوتة

**AWS Security Hub**:

- تُجمّع النتائج من GuardDuty وMacie وInspector وConfig وFirewall Manager
- تتحقق من التكوين مقابل معايير الأمان (CIS، NIST، PCI-DSS)
- الأكثر قيمة على نطاق متعدد الحسابات
- فعّله مبكراً، حتى لو كان لديك حساب واحد فقط — سجل النتائج تراكمي

## الملخص

خمس خدمات، خمس طبقات. كل واحدة تعالج نوعاً مختلفاً من التهديد — ولا واحدة منها تحل محل الأخريات. هجوم DDoS يتجاوز WAF وGuardDuty. محاولة حقن SQL تتجاوز Shield. بيانات اعتماد مخترقة تُستخدم ببطء وحذر قد تتجاوز Shield وWAF تماماً — لكن GuardDuty سترى الشذوذ. مطوّر يرفع عرضياً معلومات شخصية لعملاء إلى دلو S3 للتصحيح يتجاوز الثلاثة — لكن Macie تلتقطه.

- **AWS Shield Standard**: حماية مجانية وتلقائية من DDoS في الطبقة 3/4. دائماً مُفعَّلة. امتصّ فيضان SYN بخمسين جيجابت قبل وصوله إلى موازن تحميل Nimbus.
- **AWS Shield Advanced**: حماية DDoS مميزة مع وصول SRT وحماية التكلفة. حالة استخدام المؤسسات.
- **AWS WAF**: جدار حماية طبقة التطبيق. فحص وترشيح طلبات HTTP. الإرفاق بـ CloudFront أو ALB أو API Gateway. استخدام مجموعات القواعد المُدارة لحماية OWASP Top 10. قواعد قائمة على المعدل لدفاع الكاشطات.
- **Amazon GuardDuty**: كشف التهديدات السلوكية. مصادر البيانات الأساسية: أحداث CloudTrail، سجلات تدفق VPC، سجلات DNS. حمايات موسّعة اختيارية تضيف أحداث S3، مراقبة وقت تشغيل EKS/ECS، أحداث تسجيل دخول RDS، ونشاط شبكة Lambda. تُنشئ نتائج مُصنَّفة للنشاط الشاذ. خمسة أنواع نتائج رئيسية: UnauthorizedAccess (تسجيل دخول وحدة التحكم)، CryptoCurrency (تعدين)، Recon (تحسّس منافذ)، Trojan (زيارات C2)، Policy (ضبط S3 خاطئ).
- **Amazon Inspector**: تقييم ثغرات آلي. يفحص نسخ EC2 وصور حاويات ECR وحزم دوال Lambda بحثاً عن CVEs معروفة. يعمل باستمرار ويُعيد التقييم حين تُنشَر ثغرات جديدة. النتائج تتدفق إلى Security Hub.
- **Amazon Macie**: اكتشاف البيانات الحساسة في S3. تكتشف المعلومات الشخصية وبيانات الاعتماد والبيانات المالية. تلتقط التعرّض الذي ليس له نمط سلوك شاذ.
- **AWS Security Hub**: تُجمّع النتائج من كل خدمات الأمان في لوحة تحكم واحدة. تُتيح المراقبة المركزية عبر حسابات متعددة.
- **CloudTrail**: أساس كل تسجيل أمان AWS. فعّل مساراً يكتب إلى S3 للاحتفاظ على المدى الطويل. كل خدمة أمان تقرأ منه.

## نصائح الاختبار

*SAA-C03 المجال: تصميم معماريات آمنة (المجال الأول، المهمة 1.2)*

- **Shield Standard مقابل Advanced**: Standard مجاني وتلقائي. Advanced يكلف مالاً ويضيف SRT وحماية التكلفة وكشفاً أفضل. إشارات الاختبار لـ Advanced: "DDoS واسع النطاق"، "ضمان SLA أثناء الهجمات"، "الحماية المالية من ارتفاع تكاليف DDoS."
- **إشارات حالة استخدام WAF**: "حجب حقن SQL"، "حجب سكريبت عبر المواقع"، "تحديد معدل استدعاءات API"، "حجب عوامل مستخدم محددة"، "حماية OWASP Top 10" ← WAF.
- **إشارات GuardDuty**: "كشف نشاط API غير عادي"، "تحديد بيانات اعتماد مخترقة"، "الإبلاغ عن اتصالات EC2 الشبكية الشاذة"، "معلومات التهديد" ← GuardDuty.
- **إرفاق WAF**: يمكن إرفاقه بـ CloudFront (عالمي)، ALB (إقليمي)، API Gateway (إقليمي)، AppSync.
- **مصادر بيانات GuardDuty**: ثلاثة مصادر أساسية — أحداث CloudTrail، سجلات تدفق VPC، سجلات DNS. مصادر اختيارية موسّعة تشمل أحداث بيانات S3، سجلات تدقيق EKS، أحداث تسجيل دخول RDS، نشاط شبكة Lambda، ووقت تشغيل ECS. قد يسأل الاختبار أي مصدر بيانات ذو صلة بسيناريو كشف محدد: "تسجيلات دخول RDS شاذة" ← حماية RDS في GuardDuty؛ "تهديدات وقت تشغيل الحاويات" ← مراقبة وقت تشغيل EKS/ECS في GuardDuty.
- **Macie مقابل GuardDuty**: مُشتت اختبار شائع. **Macie** تستخدم ML لكشف البيانات الحساسة في S3 (المعلومات الشخصية، بيانات الاعتماد، البيانات المالية). **GuardDuty** تكتشف التهديدات والشذوذات في السلوك. Macie عن المحتوى. GuardDuty عن السلوك.
- **Inspector مقابل GuardDuty مقابل Macie:** ثلاث عدسات مختلفة، لا واحدة بديلة عن الأخريات. **Inspector** = فحص ثغرات — CVEs على نسخ EC2، وصور الحاويات في ECR، وحزم دوال Lambda. يعمل باستمرار ويُعيد الفحص حين تُنشَر CVEs جديدة. **GuardDuty** = كشف تهديدات سلوكي — ما الذي يحدث الآن ويبدو شاذاً. **Macie** = اكتشاف بيانات حساسة في S3 — معلومات شخصية وبيانات اعتماد وبيانات مالية لا ينبغي أن تكون هناك. مُحفِّز الاختبار: "تحديد ثغرات غير مُصحَّحة على EC2" أو "فحص صور الحاويات بحثاً عن CVEs" ← Inspector. "كشف استدعاءات API غير عادية أو بيانات اعتماد مخترقة" ← GuardDuty. "إيجاد معلومات شخصية أو بيانات حساسة في S3" ← Macie.
- **Security Hub**: تُجمّع النتائج الأمنية من خدمات وحسابات متعددة. سيناريو الاختبار: "شركة لديها حسابات AWS متعددة وتريد رؤية واحدة لكل النتائج الأمنية" ← Security Hub.
- **القواعد القائمة على المعدل في WAF**: تُستخدم لتحديد الطلبات لكل IP ضمن نافذة زمنية. مختلفة عن مجموعة القواعد الأساسية (التي تطابق أنماط الهجوم). يستخدم الاختبار القواعد القائمة على المعدل لـ "منع محاولات تسجيل الدخول بالقوة الغاشمة" أو "تخفيف الكشط."
- **CloudTrail + GuardDuty + Security Hub**: هذه الثلاثة معاً تُشكّل جوهر رصد أمان AWS. فعّل CloudTrail أولاً (GuardDuty وSecurity Hub يعتمدان عليه)، ثم GuardDuty، ثم Security Hub لتجميع النتائج.

## تمارين

**تمرين 1 — استرجاع**

اشرح الفرق بين AWS WAF وAmazon GuardDuty. ما الذي تحمي منه كل خدمة، وعلى أي طبقة تعمل كل منها؟

*(تلميح: فكّر في WAF كمرشّح على الطلبات الواردة، وGuardDuty كمحلل سلوكي يراقب سجلاتك.)*

**تمرين 2 — سيناريو SAA-C03**

*سيناريو*: موقع شركة تجزئة يتعرض لهجوم من شبكة روبوتات ترسل ملايين الطلبات في الساعة إلى API البحث عن المنتجات. تبدو الطلبات مشروعة (سلاسل User-Agent صالحة، كوكيز جلسة صالحة) لكنها لا تُفضي إلى مشتريات — إنها تكشط أسعار المنتجات. الهجوم يُسبّب تجربة استجابة بطيئة للعملاء الشرعيين.

أي مجموعة خدمات تعالج هذا التهديد على أفضل وجه؟

A) AWS WAF بقواعد تحديد المعدل وCloudFront  
B) AWS Shield Advanced وCloudFront  
C) Amazon GuardDuty وAWS Shield Standard  
D) NACLs تحجب نطاقات IP لشبكة الروبوتات

**تلميح 1**: الطلبات على مستوى HTTP (طبقة التطبيق). أي خدمة تعمل على طبقة HTTP؟

**تلميح 2**: تستخدم شبكات الروبوتات عناوين IP مختلفة كثيرة — حجب نطاقات IP محددة في NACL غير فعّال ضد شبكات روبوتات كبيرة.

**تلميح 3**: تحديد المعدل بحسب عنوان IP يمكنه إبطاء الكشط حتى لو لم تتمكن من حجبه كلياً.

**الإجابة**: A

**الشرح**: يمكن لـ AWS WAF تحديد معدل الطلبات لكل عنوان IP، مما يُقلل تأثير الكشط الكبير الحجم من أي مصدر واحد. CloudFront توزّع الزيارات الواردة عبر شبكة حافة AWS، تمتصّ الحجم وتحمي الأصل. يمكن لقواعد WAF أيضاً مطابقة أنماط الطلبات (طلبات متسلسلة سريعة لنفس نقطة نهاية API) للتعرف على سلوك الكشط.

**لماذا ليس B؟** Shield Advanced يحمي من فيضانات DDoS (الطبقة 3/4). السيناريو يصف كشطاً على مستوى التطبيق (طلبات HTTP الطبقة 7)، التي لا يفحصها Shield.

**لماذا ليس C؟** تكتشف GuardDuty الشذوذات في سلوك حسابك على AWS — لا تحجب طلبات HTTP الواردة. Shield Standard لا يتعامل مع هجمات طبقة التطبيق.

**لماذا ليس D؟** تستخدم شبكات الروبوتات الكبيرة آلاف عناوين IP من مصادر موزّعة. حجب نطاقات محددة نهج لا جدوى منه ضد شبكات الروبوتات المتطورة.

*SAA-C03 المجال: تصميم معماريات آمنة — المهمة 1.2*

**تمرين 3 — تحدي المعمارية** *(اختياري)*

Nimbus تفكّر في نموذج تهديدها استعداداً للتعامل مع بيانات بطاقات الائتمان. تراجع امتثال PCI-DSS يتطلب:

- الحماية من هجمات DDoS على طبقة الشبكة
- ترشيح طبقة التطبيق للاستغلالات المعروفة على الويب
- تسجيل جميع استدعاءات API في مخزن مقاوم للتلاعب طويل الأمد
- كشف أنماط وصول غير عادية لخدمة الدفع

عيّن كل متطلب إلى خدمة AWS محددة أو تكوين. هل Shield Standard كافٍ، أم يُشير سياق PCI-DSS إلى Advanced؟ أين ستُرفق WAF؟

*(لا توجد إجابة صحيحة واحدة. الهدف التدرب على تعيين متطلبات الامتثال إلى خدمات AWS.)*
