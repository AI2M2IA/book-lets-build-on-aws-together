# الفصل الحادي والعشرون: حاويات الشحن للكود

"إنه يعمل على جهازي."

تعلَّم Leo ألا يقول هذا بصوت عالٍ. لم يكن دفاعاً — كان تشخيصاً. والتشخيص هذه المرة كان EC2 instance الإنتاج رقم ثلاثة، التي تلقَّت تصحيحاً للمكتبة قبل ستة أسابيع لم يوثِّقه أحد، ولم تتلقَّه الـ instances الأخريان، وكان يُسبِّب الآن خطأً موجوداً فقط هناك، في تلك الـ instance الواحدة، غير مرئي في أي مكان آخر.

أمضى ثلاث ساعات الليلة الماضية في تتبُّعه.

"في كل مرة نُنشِر فيها"، قال في صباح اليوم التالي، "نُنسِّق بين instances متعددة. إصدار جديد، تبعيات مختلفة. يعمل في التجهيز، يتعطل في الإنتاج لأن البيئات انحرفت."

"لأن شخصاً ما حدَّث حزمةً على instance ثلاثة دون تحديث الأخريين"، قالت Priya. بلا قسوة.

"كنت أحتاج إصداراً محدداً من—"

"أعرف"، قالت. "والآن لدى instance ثلاثة تاريخ مختلف عن instance واحد واثنين. هذا انجراف التكوين. هادئ حتى يتوقف عن ذلك."

أصلحت Lambda مشكلة الخادم الخامل بالنسبة لخدمات Nimbus الأصغر. لكن الـ API الأساسي — الذي يحمل كل حركة مرور الطلبات — كان لا يزال على EC2. وinstances الـ EC2، خلافاً للدوال، تتراكم لها تاريخ.

"ما الحل الفعلي؟" سألت Maya.

"توقَّف عن معاملة الخوادم كأشياء دائمة تُضبَط"، قالت Priya. "وابدأ في معاملتها كوحدات يُمكن التخلص منها تُستبدَل."

هناك تشبيه يُفسِّر هذا بدقة شديدة لدرجة أنه يظهر في كل تفسير تقريباً لحاويات البرمجيات. يعود إلى عام 1956، وليس له علاقة بالبرمجيات. الجواب، حين سأل شخص أخيراً "ما الحل لشحن البضائع بشكل موثوق عبر ناقلات مختلفة؟"، كان: توحيد الحاوية. اشحن الصندوق، وليس فقط المحتويات.

**ما الحاوية؟**

**الحاوية** وحدة خفيفة وقابلة للنقل تُغلِّف تطبيقك مع كل ما يحتاجه للتشغيل: runtime (Python 3.11، Node.js 20، Java 17)، المكتبات والتبعيات، ملفات التكوين، وكود التطبيق نفسه.

خلافاً للآلة الافتراضية (التي تُحاكي جهاز كمبيوتر كاملاً بما في ذلك نواة نظام التشغيل)، تُشارك الحاوية نواة نظام تشغيل المضيف مع إبقاء كل شيء آخر معزولاً. هذا يجعل الحاويات سريعة الإقلاع (ثوانٍ، أحياناً مللي ثواني) وصغيرة (ميغابايت، لا غيغابايت).

أكثر تقنيات الحاويات شيوعاً هي **Docker**. صورة Docker هي المخطط — لقطة للتطبيق وبيئته. حاوية Docker هي instance عاملة من تلك الصورة.

الخاصية الأساسية: **الثبات**. صورة مبنية اليوم ستعمل بشكل متطابق على أي مضيف يدعم Docker — جهاز محمول، أو EC2 instance، أو خادم في مركز بيانات مختلف. البيئة مُدمَجة. انجراف التكوين مستحيل.

"إذن بدلاً من القلق حول ما هو مثبَّت على EC2 instance"، قال Leo، "نبني صورةً تحتوي على كل شيء. تعمل الصورة بنفس الطريقة في كل مكان."

"وإذا أردت اختبارها محلياً، تُشغِّل الصورة نفسها"، أضافت Priya. "لا مزيد من 'إنه يعمل على جهازي'."

**Amazon ECS: المُنسِّق**

تشغيل حاوية واحدة أمر بسيط. تشغيل عشرات الحاويات عبر مضيفين متعددين، وتوجيه حركة المرور بينها، وإعادة تشغيل الحاويات الفاشلة، ونشر إصدارات جديدة دون توقف — هذا يتطلب **مُنسِّقاً**.

**Amazon ECS (Elastic Container Service)** هو خدمة تنسيق الحاويات المُدارة من AWS. تُعرِّف:

- **تعريف المهمة (Task definition)**: صورة الحاوية التي ستعمل، مقدار CPU والذاكرة، متغيرات البيئة، المنافذ التي ستُعرَض
- **الخدمة (Service)**: عدد نسخ المهمة التي ستعمل، كيفية معالجة الأعطال والنشر
- **الكتلة (Cluster)**: البنية التحتية للحوسبة الأساسية

تتولى ECS الباقي: وضع المهام على السعة المتاحة، إعادة تشغيل المهام الفاشلة، تصريف الاتصالات خلال النشر، تسجيل المهام الصحية مع موازن التحميل.

بالنسبة لـ Nimbus، انتقل الـ API من EC2 instances مع عمليات نشر تُدار يدوياً إلى ECS. كل نشر جديد دفع صورة Docker جديدة إلى **Amazon ECR (Elastic Container Registry)** — سجل الحاويات المُدار من AWS — وطرحتها ECS عبر جميع المهام دون توقف.

**Fargate مقابل نوع الإطلاق EC2**

يمكن لـ ECS تشغيل الحاويات في وضعين:

**نوع الإطلاق EC2**: تدير instances الـ EC2 الأساسية. أنت مسؤول عن تصحيح الـ instances، ضبط حجمها الصحيح، وضمان وجود سعة كافية لحاوياتك. مزيد من التحكم، مزيد من المسؤولية.

**Fargate (حوسبة serverless للحاويات)**: يدير AWS البنية التحتية الأساسية بالكامل. تُحدِّد CPU والذاكرة لكل مهمة؛ يُوفِّر Fargate السعة المناسبة تلقائياً. لا instances EC2 لإدارتها. تدفع لكل vCPU-ثانية وGB-ثانية من الذاكرة.

Fargate هو نموذج "حاويات serverless" — تحصل على عزل بيئة الحاويات دون إدارة الخوادم. المقايضة: تحكم أقل في تكوين الـ instance الأساسية وتكلفة أعلى قليلاً لكل وحدة.

بالنسبة لـ Nimbus: Fargate لخدمة الـ API. لم يريدوا إدارة EC2 instances للحاويات.

**Amazon EKS: حين تحتاج Kubernetes**

**Kubernetes** نظام تنسيق حاويات مفتوح المصدر — المعيار الصناعي الفعلي لإدارة الحاويات على نطاق واسع. قوي، قابل للتوسع، ومعقد.

**Amazon EKS (Elastic Kubernetes Service)** هو خدمة Kubernetes المُدارة من AWS. تُشغِّل مستوى تحكم Kubernetes (طبقة الإدارة) نيابةً عنك، بينما تدير عُقد العمل (أو تستخدم Fargate لتلك أيضاً).

متى تستخدم EKS مقابل ECS؟

**استخدم ECS** إذا:

- كنت بشكل رئيسي على AWS وتريد تجربة أبسط وأكثر تكاملاً مع AWS
- لا يمتلك فريقك خبرة Kubernetes موجودة
- تريد تقليل الحمل التشغيلي

**استخدم EKS** إذا:

- تحتاج ميزات محددة لـ Kubernetes (Custom Resource Definitions، مخططات Helm، نظام Kubernetes البيئي)
- يعرف فريقك Kubernetes بالفعل
- تعمل في بيئة هجينة (بعضها محلي، بعضها في AWS) وتريد طبقة تنسيق متسقة
- لحمل العمل متطلبات تتناسب مع قابلية توسع Kubernetes

"أيهما يجب أن نستخدم؟" سألت Maya.

"ECS"، قالت Priya فوراً. "ليس لدينا خبرة Kubernetes. تفعل ECS كل ما نحتاجه. إضافة Kubernetes الآن ستضيف تعقيداً تشغيلياً دون فائدة عملية."

"يمكننا دائماً الانتقال إلى EKS لاحقاً إذا تجاوزنا ECS"، أضاف Leo.

هذه إجابة صحيحة كبار المهندسين: اختر الأداة الأبسط التي تناسب احتياجاتك الحالية.

**كيف تُغيِّر الحاويات عمليات النشر**

قبل الحاويات، كان نشر إصدار جديد من Nimbus API يعني:

1. الدخول بـ SSH إلى كل EC2 instance
2. سحب أحدث كود من Git
3. تثبيت/تحديث التبعيات
4. إعادة تشغيل عملية التطبيق
5. التحقق من الصحة
6. الانتقال إلى الـ instance التالية

كان هذا عُرضةً للأخطاء وبطيئاً. تطلَّب تنسيقاً. إذا فشلت الخطوة 3 على instance رقم 4، كان لديك نشر مختلط مع بعض الـ instances تعمل بالإصدار القديم وبعضها تفشل في تشغيل الإصدار الجديد.

مع ECS والحاويات:

1. بناء صورة Docker جديدة (مؤتمتة في خط أنابيب CI/CD)
2. الدفع إلى ECR
3. تحديث خدمة ECS لاستخدام إصدار الصورة الجديد

تتولى ECS النشر المتدرج: تبدأ مهام جديدة بالصورة الجديدة، تنتظر حتى تكون صحية، ثم توقف المهام القديمة. نشر بدون توقف، مؤتمت.

إذا فشل الإصدار الجديد في فحوصات الصحة، توقف ECS النشر ويستمر الإصدار القديم في خدمة حركة المرور.

## نقاط القوة والقيود

**الحاويات**:

- تُزيل تناقض البيئة ("إنه يعمل على جهازي")
- تُتيح نشراً سريعاً وموثوقاً
- ثابتة — الصورة نفسها تعمل بشكل متطابق في كل مكان
- كفؤة — أخف من الآلات الافتراضية، إقلاع أسرع

**ECS**:

- أبسط من Kubernetes لأحمال العمل المتمركزة حول AWS
- تكامل محكم مع AWS (IAM، ALB، CloudWatch، Secrets Manager)
- خيار Fargate يُزيل إدارة EC2 بالكامل

**EKS**:

- توافق كامل مع Kubernetes — استخدم النظام البيئي بالكامل
- أفضل للبيئات الهجينة أو الفرق التي لديها خبرة Kubernetes
- أكثر تعقيداً في الإعداد والتشغيل من ECS

**أين يصبح الأمر معقداً**:

- يجب بناء صور الحاويات وإصدارها — يتطلب خط أنابيب CI/CD
- تصحيح الحاويات يتطلب أدوات مختلفة عن تصحيح العمليات التقليدية
- الحاويات ذات الحالة (قواعد بيانات في الحاويات) تتطلب تكوين تخزين ثابت دقيق
- الشبكات بين الحاويات (الاتصال بين الخدمات) يتطلب فهم مفاهيم شبكات الحاويات

## الملخص

- **الحاويات** تُغلِّف كود التطبيق والـ runtime والتبعيات معاً — تعمل بشكل متطابق في أي مكان.
- **Docker** تقنية الحاويات المعيارية. الصور هي المخططات؛ الحاويات هي الـ instances العاملة.
- **ECR (Elastic Container Registry)** سجل Docker المُدار من AWS — خزِّن صورك وإصداراتها هنا.
- **ECS (Elastic Container Service)** تُنسِّق الحاويات. تُعرِّف المهام والخدمات؛ تدير ECS الوضع ودورة الحياة.
- **Fargate** حوسبة serverless للحاويات — لا instances EC2 لإدارتها.
- **EKS (Elastic Kubernetes Service)** Kubernetes مُدار — للفرق التي تحتاج ميزات Kubernetes أو توافقه.
- اختر ECS للبساطة على AWS؛ اختر EKS لتوافق نظام Kubernetes البيئي.

## نصائح الاختبار

*نطاق SAA-C03: تصميم بنيات مرنة (النطاق 2، المهمة 2.1)*

- **إشارات ECS مقابل EKS**: سيناريوهات الاختبار التي تذكر "Kubernetes"، "Helm"، "خبرة Kubernetes موجودة"، أو "تنسيق حاويات متعدد السحابة" → EKS. كل شيء آخر → ECS.
- **Fargate مقابل نوع الإطلاق EC2**: "لا نريد إدارة EC2 instances للحاويات"، "حاويات serverless"، "لا إدارة بنية تحتية" → Fargate. "نحتاج أنواع instances محددة"، "أحمال عمل GPU"، "تحكم دقيق في الـ instance" → نوع الإطلاق EC2.
- **أدوار مهام ECS**: مثل أدوار EC2 instance، لدى مهام ECS أدوار IAM. كل مهمة يمكن أن يكون لها أذونات مختلفة. سيناريو الاختبار: "الحاوية تحتاج قراءة من S3" → إرفاق دور IAM بتعريف المهمة.
- **فحص صور ECR**: يمكن لـ ECR فحص صور الحاويات بحثاً عن ثغرات معروفة (CVEs). إشارة الاختبار: "فحص الحاويات بحثاً عن ثغرات أمنية" → فحص صور ECR.
- **نشر Blue/Green**: تدعم ECS نشر blue/green عبر تكامل CodeDeploy. نشر بدون توقف مع التراجع التلقائي. نمط الاختبار: "النشر بدون توقف مع التراجع التلقائي" → ECS + CodeDeploy blue/green.
- **Auto Scaling لخدمة ECS**: قياس عدد المهام بناءً على CPU أو الذاكرة أو مقاييس CloudWatch المخصصة. يعمل مع ALB لتوجيه حركة المرور إلى العدد الصحيح من المهام العاملة.

## التمارين

**التمرين الأول — الاستذكار**

اشرح الفرق بين صورة Docker وحاوية Docker. اشرح الفرق بين ECS وECR.

*(تلميح: الصورة للحاوية كالوصفة للطبق المطبوخ. ECR يُخزِّن الصور؛ ECS تُشغِّلها.)*

**التمرين الثاني — تدريب على الاختبار**

*السيناريو*: شركة لديها تطبيق microservices يعمل حالياً على EC2 instances تُدار يدوياً. يعاني الفريق من نشر غير متسق — instances EC2 مختلفة لها إصدارات مكتبات مختلفة، مما يتسبب في أخطاء يصعب إعادة إنتاجها. يريدون توحيد النشر مع تقليل الحمل التشغيلي لإدارة الخوادم الأساسية. الفريق ليس لديه خبرة Kubernetes.

أي حل يلبِّي هذه المتطلبات على أفضل وجه؟

أ) النشر على EC2 مع AWS Systems Manager Patch Manager للحفاظ على اتساق الـ instances
ب) تحويل التطبيق إلى حاويات مع Docker؛ استخدام Amazon ECS مع نوع الإطلاق Fargate
ج) تحويل التطبيق إلى حاويات مع Docker؛ استخدام Amazon EKS مع مجموعات عُقد self-managed
د) استخدام AWS Elastic Beanstalk لإدارة النشر وتكوين الـ instance تلقائياً

**تلميح 1**: الحاويات تحل مشكلة "البيئة غير المتسقة" مباشرةً. أي الخيارات تستخدم الحاويات؟

**تلميح 2**: "تقليل الحمل التشغيلي لإدارة الخوادم" → Fargate (لا إدارة EC2) مقابل عُقد self-managed (لا تزال تدير EC2).

**تلميح 3**: "لا خبرة Kubernetes" → EKS أكثر تعقيداً تشغيلياً من ECS.

**الإجابة**: ب

**الشرح**: تحويل التطبيق إلى حاويات مع Docker يضمن أن كل نشر يستخدم الصورة نفسها بنفس التبعيات — مما يُزيل انجراف التكوين. ECS مع Fargate يعني لا instances EC2 لإدارتها. يركِّز الفريق على كود التطبيق وتعريفات الحاويات، لا صيانة الخوادم. ECS (وليس EKS) مناسب للفرق التي ليس لديها خبرة Kubernetes.

**لماذا ليس أ؟** Patch Manager يُبقي EC2 instances محدَّثةً لكنه لا يحل تناقض إصدار المكتبة بين التطبيقات. المشكلة الأساسية (بيئات كود مختلفة على instances مختلفة) تبقى.

**لماذا ليس ج؟** EKS مع عُقد self-managed يتطلب إدارة instances EC2 *وتعلُّم* Kubernetes. كلاهما لا يتوافق مع المتطلبات.

**لماذا ليس د؟** Elastic Beanstalk يدير نشر التطبيق على EC2 لكنه لا يحل التناقض الجوهري في البيئة ما لم تُستخدم الحاويات. Beanstalk لا يستخدم صور Docker افتراضياً (رغم إمكانية تكوينه لذلك).

*نطاق SAA-C03: تصميم بنيات مرنة — المهمة 2.1*

**التمرين الثالث — تحدي البنية** *(اختياري)*

تقوم Nimbus بتقسيم الـ API المتكامل إلى ثلاثة microservices: خدمة الطلبات، خدمة القائمة، وخدمة الإشعارات. لكل خدمة متطلبات توسع مختلفة (تتوسع خدمة الطلبات مع حركة المرور؛ خدمة القائمة للقراءة بشكل رئيسي ومستقرة؛ وخدمة الإشعارات لديها طفرات غير منتظمة).

صمِّم بنية ECS لهذه الخدمات الثلاث. كيف ستتعامل مع الاتصال بين الخدمات؟ هل ستستخدم كتلة ECS واحدة أم ثلاثاً؟ كيف ستُكوِّن Auto Scaling بشكل مختلف لكل خدمة؟

*(لا توجد إجابة صحيحة واحدة. الهدف هو ممارسة بنية microservices على ECS.)*

## مشهد ما بعد النهاية

كان نشر الحاوية الأول سلساً تماماً.

إصدار جديد من الـ API: بدون توقف. طرحته ECS، اجتازت فحوصات الصحة، تصرَّفت المهام القديمة، وتولَّت المهام الجديدة. راقب Leo حالة المهمة في وحدة التحكم بشيء يقترب من عدم التصديق.

"لقد نجح الأمر فحسب"، قال.

"هذه هي الفكرة"، قالت Priya.

"بدون SSH. بدون توقف. بدون 'انتظر حتى يُعيد التشغيل'."

"الصورة هي artifact النشر"، قالت. "البيئة ثابتة. عملية النشر إعلانية. هكذا يجب شحن البرمجيات."

حدَّق Leo في وحدة التحكم لحظةً أخرى.

"أمضيت ثلاث سنوات في تنسيق نشر EC2"، قال. "تنسيق سكريبتات SSH. كتابة دفاتر تشغيل النشر."

"كنت تحل مشكلة"، قالت Priya، "الحاويات تحلها بالتصميم."

لم يقل شيئاً بعد ذلك. لكن في صباح اليوم التالي، بدأ في كتابة وثائق عملية بناء الحاوية، حتى لا يضطر أحد آخر إلى قضاء ثلاث سنوات لاكتشافها.

في الفصل التالي: مخطط التدفق الذي يُشغِّل نفسه — ويتذكر أين توقف.
