**Классы хранилищ S3: полный спектр**

В главе 5 S3 Standard был представлен как основной класс хранилища. На самом деле у S3 семь классов хранилищ, каждый разработан для разных паттернов доступа:

**S3 Standard**: для часто запрашиваемых данных. Малая задержка (миллисекунды). Наибольшая стоимость. Нет минимального срока хранения. Используйте для активных данных: текущие фотографии меню, сегодняшние заказы, недавние логи.

**S3 Standard-Infrequent Access (S3 Standard-IA)**: для данных, к которым обращаются реже раза в месяц. Такое же миллисекундное извлечение, как у Standard, но более низкая стоимость хранения + плата за ГБ при извлечении. Используйте для данных, которые нужны немедленно при доступе, но к которым редко обращаются: старые квитанции о заказах, экспорты аналитики 6-месячной давности.

**S3 One Zone-Infrequent Access (S3 One Zone-IA)**: то же, что S3 Standard-IA, но хранится только в одной зоне доступности (а не в трёх). Менее надёжен (если в этой AZ случится катастрофа, данные могут быть потеряны), но на 20% дешевле. Используйте для данных, которые можно воссоздать в случае потери: кэш миниатюр, временные результаты обработки.

**S3 Glacier Instant Retrieval**: архивные данные, к которым периодически нужен доступ. Извлечение в миллисекунды. Очень низкая стоимость хранения, более высокая стоимость извлечения за ГБ. Минимальный срок хранения 90 дней. Используйте для данных, к которым обращаются раз в квартал или реже: квартальные отчёты о соответствии требованиям, резервные снимки 12-месячной давности.

**S3 Glacier Flexible Retrieval**: глубокий архив, извлечение занимает от минут до часов. Ниже стоимость, чем у Glacier Instant Retrieval. Используйте для архивных данных с меньшей срочностью.

**S3 Glacier Deep Archive**: самый дешёвый вариант. Извлечение занимает 12 часов. Минимальный срок хранения 180 дней. Используйте для данных, которые необходимо хранить для соответствия нормативным требованиям, но к которым никогда не ожидается доступ: 7-летние налоговые записи, 10-летние журналы аудита.

Паттерн: по мере снижения частоты доступа стоимость снижается, но время извлечения увеличивается (и стоимость извлечения возрастает). Выбирайте класс, соответствующий вашему паттерну доступа.

**Политики жизненного цикла S3: автоматизированная система хранения**

Ручное перемещение файлов между классами хранилищ подвержено ошибкам и требует много времени. **Политики жизненного цикла** S3 автоматизируют это на основе определённых вами правил.

Правило жизненного цикла имеет два компонента:

**Фильтр**: к каким объектам применяется правило (все объекты, объекты с определённым префиксом, объекты с определёнными тегами).

**Действия**: что делать и через сколько дней.

Пример политики жизненного цикла для квитанций о заказах Nimbus:

```
Перейти в S3 Standard-IA через 90 дней
Перейти в S3 Glacier Instant Retrieval через 365 дней
Перейти в S3 Glacier Deep Archive через 2555 дней (7 лет)
Удалить через 2920 дней (8 лет)
```

Эта единственная политика обеспечивает:

- Активные квитанции (< 90 дней): S3 Standard, быстрый доступ
- Недавние квитанции (90–365 дней): Standard-IA, дёшево, но мгновенно доступно
- Исторические квитанции (1–7 лет): Glacier, очень дёшево, редко нужны
- Просроченные квитанции (> 8 лет): автоматически удаляются

**S3 Intelligent-Tiering: самоорганизующийся класс**

Что если вы не знаете, как часто будете обращаться к своим данным?

**S3 Intelligent-Tiering** отслеживает паттерны доступа для каждого объекта и автоматически перемещает его между уровнями доступа:

- **Уровень частого доступа**: для объектов, к которым недавно обращались
- **Уровень нечастого доступа**: объекты, к которым не обращались 30 дней
- **Уровень мгновенного архивного доступа**: объекты, к которым не обращались 90 дней
- **Уровень архивного доступа**: объекты, к которым не обращались 90–730 дней (опционально)
- **Уровень глубокого архивного доступа**: объекты, к которым не обращались 180–730+ дней (опционально)

S3 Intelligent-Tiering взимает небольшую плату за мониторинг за каждый объект в месяц ($0,0025 за 1 000 объектов), но не берёт плату за извлечение для уровней частого и нечастого доступа.

Используйте Intelligent-Tiering когда:

- Паттерны доступа непредсказуемы или меняются со временем
- У вас есть смесь горячих и холодных данных, которые сложно классифицировать
- Объекты больше 128 КБ (для маленьких объектов плата за мониторинг превышает экономию)

Используйте явные классы хранилищ (с политиками жизненного цикла) когда:

- Паттерны доступа предсказуемы
- Вы хотите минимизировать плату за мониторинг каждого объекта
- Объекты маленькие (< 128 КБ)

**Многочастная загрузка: для больших объектов**

У S3 есть ограничение на одиночную загрузку в 5 ГБ. Для больших объектов необходимо использовать **многочастную загрузку**: разбить объект на части, загрузить каждую параллельно, и S3 их соберёт.

Преимущества:

- Более быстрые загрузки (параллельные)
- Можно возобновить прерванные загрузки (повторно загружать только упавшие части)
- Обязательна для объектов > 5 ГБ

Совет по правилу жизненного цикла: установите правило жизненного цикла для удаления незавершённых многочастных загрузок через 7 дней. Если загрузка не завершилась и не была очищена, частично загруженные части хранятся и тарифицируются — без собранного объекта в результате.

**Репликация S3: копирование данных между бакетами**

S3 может автоматически реплицировать объекты из одного бакета в другой:

**Репликация в том же регионе (SRR)**: копирование объектов в пределах одного региона. Используется для соответствия требованиям (хранение отдельной копии в другом аккаунте), агрегирования логов из нескольких бакетов или создания тестовых сред из производственных данных.

**Кросс-региональная репликация (CRR)**: копирование объектов в другой регион. Используется для аварийного восстановления (избыточность данных в разных регионах), соответствия требованиям (данные должны находиться в определённой географии) и снижения задержки для глобальных пользователей.

Репликация — не решение для резервного копирования: если вы удаляете объект в исходном бакете, он удаляется и в реплике (если только репликация маркеров удаления не отключена). Для резервного копирования используйте AWS Backup или версионирование с блокировкой объектов.

**S3 Object Lock: неизменяемость для соответствия требованиям**

Некоторые нормативные требования предписывают, чтобы данные были **неизменяемыми** — после записи их нельзя изменять или удалять в течение определённого периода.

**S3 Object Lock** реализует хранилище WORM (Write Once, Read Many — запись однократно, чтение многократно):

**Период хранения**: объекты нельзя удалять или перезаписывать в течение указанного срока.

**Юридическое удержание**: объекты нельзя удалять, независимо от периода хранения, до тех пор, пока юридическое удержание явно не снято.

Используйте S3 Object Lock для регулируемых отраслей: финансовые записи (SEC Rule 17a-4), медицинские записи (HIPAA), архивы для соответствия требованиям.

## Преимущества и ограничения

**Почему классы хранилищ S3 важны**:

- Значительное снижение затрат без потери надёжности или доступности для реально запрашиваемых данных
- Политики жизненного цикла автоматизируют весь процесс — нет операционной нагрузки
- S3 Intelligent-Tiering устраняет необходимость прогнозировать паттерны доступа

**Где возникают сложности**:

- К классам Glacier применяются минимальные сроки хранения (90 дней для Glacier Instant, 180 дней для Deep Archive) — раннее удаление всё равно взимает минимальную плату
- Плата за извлечение может неприятно удивить, если часто обращаться к архивным данным
- Переходы жизненного цикла занимают время — объекты не перемещаются мгновенно после срабатывания правила
- Плата за мониторинг Intelligent-Tiering накапливается для бакетов с миллионами маленьких объектов

## Резюме

- У S3 семь классов хранилищ: Standard, Standard-IA, Intelligent-Tiering, One Zone-IA, Glacier Instant Retrieval, Glacier Flexible Retrieval и Glacier Deep Archive.
- **Политики жизненного цикла** автоматизируют переходы между классами хранилищ в зависимости от возраста — задаёте один раз, S3 выполняет бесконечно.
- **S3 Intelligent-Tiering** автоматически перемещает объекты между уровнями на основе реальных паттернов доступа — используйте для непредсказуемых нагрузок.
- **Многочастная загрузка** обязательна для объектов > 5 ГБ и рекомендуется для всего > 100 МБ.
- **Репликация S3** (SRR и CRR) копирует объекты между бакетами и регионами — для аварийного восстановления, соответствия требованиям или агрегирования.
- **S3 Object Lock** обеспечивает хранилище WORM для сценариев соответствия требованиям.

## Советы к экзамену

*SAA-C03, область: проектирование архитектур с оптимизацией затрат (область 4, задача 4.1)*

- **Признаки выбора класса хранилища**:
  - «Часто запрашивается» → Standard
  - «Запрашивается раз в месяц, нужно мгновенное извлечение» → Standard-IA
  - «Может допускать часы задержки извлечения, редко запрашивается» → Glacier Flexible Retrieval
  - «Соответствие нормативным требованиям, хранение 7+ лет, никогда не запрашивается» → Glacier Deep Archive
  - «Неизвестные или меняющиеся паттерны доступа» → Intelligent-Tiering
- **Паттерны экзаменационных вопросов о политиках жизненного цикла**: «автоматически снижать затраты на хранение по мере старения данных», «перейти в архив через 90 дней» → политики жизненного цикла.
- **Плата за мониторинг Intelligent-Tiering**: небольшая плата за объект. Для большого числа маленьких объектов она может превысить экономию. Экзамен может проверять это.
- **Требования к CRR**: версионирование должно быть включено как на исходном, так и на целевом бакетах. Источник и назначение должны быть в разных регионах.
- **S3 Object Lock**: «WORM», «неизменяемый», «SEC 17a-4», «нельзя удалять или изменять» → Object Lock. Режим governance (может быть переопределён администраторами). Режим compliance (не может быть переопределён никем, включая root).
- **Восстановление из Glacier**: объекты в Glacier недоступны мгновенно. Необходимо «восстановить» копию в S3 Standard для доступа. Восстановленная копия временна (вы задаёте продолжительность). Оригинал остаётся в Glacier.

**Упражнение 2 — Подготовка к экзамену**

*Сценарий*: Компания ежедневно генерирует 500 ГБ журналов приложений. Журналы активно запрашиваются в течение первых 7 дней (отладка и мониторинг). После 7 дней журналы редко запрашиваются, но должны быть доступны в течение 30 минут при необходимости. После 1 года журналы должны храниться для соответствия требованиям, но никогда не запрашиваются. Компании нужно минимизировать затраты на хранение при соблюдении этих требований.

Какая политика жизненного цикла S3 наилучшим образом отвечает этим требованиям?

A) Хранить в S3 Standard 7 дней; перейти в S3 Glacier Deep Archive через 7 дней; истечь через 365 дней  
B) Хранить в S3 Standard 7 дней; перейти в S3 Standard-IA через 7 дней; перейти в S3 Glacier Flexible Retrieval через 365 дней  
C) Хранить все журналы в S3 Intelligent-Tiering с первого дня  
D) Хранить в S3 Standard 7 дней; перейти в S3 Glacier Instant Retrieval через 7 дней; перейти в S3 Glacier Deep Archive через 365 дней

**Подсказка 1**: «Доступны в течение 30 минут» — какой класс хранилища исключается?

**Подсказка 2**: Deep Archive занимает 12 часов для извлечения — не соответствует требованию 30 минут для дней 7–365.

**Подсказка 3**: После 365 дней время извлечения не важно (никогда не запрашиваются), поэтому применяется самый дешёвый вариант.

**Ответ**: D

**Пояснение**: S3 Standard на 7 дней обеспечивает частый доступ. Glacier Instant Retrieval предоставляет миллисекундный доступ для дней 7–365 — соответствует требованию 30 минут при значительно меньшей стоимости, чем Standard-IA. После 365 дней Glacier Deep Archive — самый дешёвый вариант для данных, к которым никогда не обращаются.

**Почему не A?** Glacier Deep Archive занимает 12 часов для извлечения — не соответствует требованию «доступность в течение 30 минут» для дней 7–365.

**Почему не B?** Standard-IA после 7 дней работает, но Glacier Instant Retrieval значительно дешевле. Standard-IA более уместен, когда нужен мгновенный доступ, но запросы редкие — здесь данные практически не запрашиваются после 7-го дня, что делает Glacier более экономичным.

**Почему не C?** У Intelligent-Tiering есть плата за мониторинг каждого объекта, и он может не перемещать журналы в архивные уровни так же агрессивно, как явные правила жизненного цикла. Для большого объёма журналов с предсказуемым паттерном доступа явные правила жизненного цикла более экономичны.
