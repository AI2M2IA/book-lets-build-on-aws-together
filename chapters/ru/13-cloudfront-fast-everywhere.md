**Аналогия с предварительно заполненным складом**

Представьте ритейлера Amazon, а не облачную компанию. У них есть огромный склад в одном месте с каждым товаром. Если бы они отправляли каждый заказ с этого одного склада, покупатели в дальних городах ждали бы дни.

Вместо этого у Amazon есть фулфилмент-центры рядом с крупными населёнными пунктами. Когда товар популярен, они предварительно заполняют эти местные склады. Когда покупатель в Сиэтле заказывает книгу, её отправляют с местного фулфилмент-центра, а не из другого конца страны.

Это **Сеть доставки контента (CDN)**: сеть географически распределённых серверов, которые кэшируют копии вашего контента рядом с вашими пользователями.

Когда пользователь в Бостоне запрашивает вашу главную страницу, CDN обслуживает её с сервера в Бостоне. Не из Орегона. Запрос никогда не пересекает страну.

**Знакомьтесь: CloudFront**

Amazon CloudFront — это CDN AWS. Он работает через глобальную сеть **граничных узлов** — кэширующих серверов, расположенных в городах по всему миру. На момент написания этой книги существует более 750 точек присутствия в 100+ городах.

Когда вы настраиваете CloudFront, вы указываете **источник**: источник вашего фактического контента. Вашим источником может быть:

- Бакет S3 (статические файлы: изображения, CSS, JavaScript, PDF)
- Application Load Balancer (динамический контент из вашего приложения)
- Экземпляр EC2
- HTTP-сервер где угодно в интернете

CloudFront стоит перед вашим источником. Запросы поступают на ближайший граничный узел. Если на узле есть кэшированный контент, он немедленно возвращает его. Если нет (*промах кэша*), он загружает с вашего источника, кэширует и возвращает.

**Как работает кэширование CloudFront**

Первый запрос на любой контент всегда является промахом кэша — он идёт к источнику. Каждый последующий запрос попадает в кэш на граничном узле.

Для Nimbus, фотографии меню — идеальные кандидаты для CloudFront. Фотографии ресторанов меняются редко (возможно, когда ресторан обновляет свой профиль). С CloudFront:

1. Пользователь в Бостоне запрашивает `images.eatnimbus.com/restaurant-047/photo.jpg`
2. CloudFront проверяет граничный узел в Бостоне — ещё не кэшировано (промах кэша)
3. CloudFront загружает из S3 в us-west-2 (~80 мс)
4. CloudFront сохраняет фотографию на граничном узле в Бостоне
5. Следующий пользователь в Бостоне запрашивает то же фото
6. CloudFront обслуживает из локального граничного кэша (~5 мс)

То же наказание в 80 мс для первого запроса. Но тысячный запрос из того же города — 5 миллисекунд.

Заголовки **Cache-Control** и **настройки TTL** в CloudFront определяют, как долго контент остаётся в кэше на граничном узле. Файлы изображений можно кэшировать часами или днями. HTML-страницы (которые меняются чаще) могут кэшироваться минутами или секундами.

Возможно, вы задаётесь вопросом: почему просто не разместить всё приложение в нескольких регионах вместо использования CDN? Если данные в Орегоне, почему не поместить полную копию в Нью-Йорк, Токио и Сан-Паулу? Можно. Но это означает поддержание синхронизации нескольких баз данных, управление развёртываниями в регионах одновременно, обработку сценариев split-brain, где регионы расходятся во мнениях. CDN — гораздо более простой ответ для статического и полустатического контента: один источник, много кэшированных копий на границе. Вы добавляете сложность нескольких регионов только тогда, когда вам действительно нужны вычисления или операции базы данных рядом с пользователем — для большинства контента граничного кэширования достаточно.

«Подождите — но *почему* мы делали бы это именно так?» — спросила Майя. «Зачем размещать кэш на границе вместо того, чтобы просто добавить более крупный кластер ElastiCache в Орегоне?»

«Потому что физика по-прежнему проблема», — сказала Прия. «Даже если Орегон отвечает за одну миллисекунду, этому ответу всё равно нужно добраться до Бостона. Время приёма-передачи — минимум 70 миллисекунд — скорости света всё равно, насколько быстры наши серверы. Граничное кэширование перемещает ответ ближе к вопросу».

**Динамический контент: CloudFront для большего, чем кэширование**

«Но что насчёт наших API-ответов?» — спросил Лео. «Они динамические — меняются для каждого пользователя, каждого запроса. Нельзя кэшировать страницу истории заказов».

Верно. Но CloudFront всё равно помогает с динамическим контентом.

Даже когда контент нельзя кэшировать, CloudFront маршрутизирует запрос с граничного узла к источнику через частную опорную сеть AWS — высокоскоростное волокно, соединяющее инфраструктуру AWS глобально. Это быстрее и надёжнее, чем маршрутизация через публичный интернет, где трафик может прыгать через нескольких операторов.

Результат: динамические запросы через CloudFront всё равно на 20-40% быстрее, чем прямое обращение к источнику через публичный интернет. Не из-за кэширования, а из-за сетевого пути.

«Это не сходится», — сказала Майя. «Если API-ответу всё равно нужно добраться из Орегона к границе, а затем в Бостон, как это быстрее, чем напрямую из Орегона в Бостон?»

«Две причины», — сказала Прия. «Первая, частная опорная сеть AWS быстрее и надёжнее, чем публичный интернет. Трафик публичного интернета маршрутизируется через нескольких операторов, каждый добавляет свою задержку и изменчивость. Опорная сеть — это прямое волокно с низкой задержкой. Вторая, завершение SSL происходит на границе. Пользователь устанавливает TLS-соединение с ближайшим граничным узлом CloudFront — рукопожатие быстрое. CloudFront затем держит постоянное, предустановленное соединение с источником. Два соединения на короткие расстояния вместо одного на дальнее».

«Значит, даже для некэшированного контента CloudFront сокращает время на накладные расходы соединения», — сказал Лео.

«Обычно от десяти до сорока процентов. Не так драматично, как кэширование. Но реально».

Кроме того, CloudFront обеспечивает:

**Завершение SSL/TLS**: CloudFront обрабатывает HTTPS на граничном узле. Соединение между пользователем и CloudFront зашифровано. CloudFront может подключаться к вашему источнику по HTTP внутренне (снижая нагрузку на источник) или по HTTPS (для сквозного шифрования).

**Защита от DDoS**: CloudFront интегрирован с AWS Shield Standard. Распределённый трафик по сотням граничных узлов означает, что атаки поглощаются на граничном уровне, а не обрушиваются на ваш источник.

**Гео-ограничения**: Блокировать доступ из конкретных стран. Если Nimbus лицензирован только для работы на определённых рынках, CloudFront может это принудительно применять на граничном уровне без того, чтобы запрос достигал ваших серверов.

**А что, если кто-то попытается взломать через CDN?** — спросила Прия. «Отравление кэша — что, если кому-то удастся внедрить плохой контент в граничный кэш?»

«У CloudFront есть элементы управления ключом кэша», — сказал Лео. «Вы определяете точно, какие атрибуты определяют, получат ли два запроса один и тот же кэшированный ответ. Заголовки, строки запроса, куки. Атакующий не может внедрить другой кэшированный ответ без совпадения точного ключа кэша».

«А Origin Access Control означает, что бакет S3 не будет обслуживать ничего, что не приходит через CloudFront», — сказала Прия. «Одна поверхность атаки вместо двух».

**Поведения CloudFront: тонкие правила кэширования**

Дистрибутив CloudFront может иметь несколько **поведений** — правил маршрутизации на основе URL-паттернов.

Для Nimbus:

- `/images/*` → Кэшировать на граничном узле 7 дней (фотографии меняются редко)
- `/static/*` → Кэшировать на граничном узле 30 дней (CSS и JavaScript с версионированными именами файлов)
- `/api/*` → Не кэшировать; пересылать напрямую к балансировщику нагрузки
- `/*` → Кэшировать 5 минут (HTML-страницы)

Это позволяет CloudFront быть умным: агрессивно кэшировать стабильное, пропускать динамическое.

Поведения сопоставляются от наиболее конкретного к наименее конкретному. `/images/hero.jpg` совпадает с `/images/*` прежде, чем совпадёт с `/*`. Универсальное `/*` внизу — это значение по умолчанию — оно применяется ко всему, что не совпадает с более конкретным паттерном.

«Что, если мы хотим разное кэширование для аутентифицированных и неаутентифицированных пользователей?» — спросила Прия. «Один и тот же URL может возвращать разный контент в зависимости от того, вошёл ли пользователь в систему».

«Тогда вы включаете куку сессии в ключ кэша», — сказал Лео. «Но это означает, что каждый вошедший пользователь получает свою собственную запись кэша. Ваш процент попаданий рушится для аутентифицированного контента».

«Вот почему вы разделяете аутентифицированный контент от публичного контента на уровне URL», — сказала Прия. «Всё, требующее аутентификации, идёт на `/app/*` и не кэшируется. Публичный контент идёт на `/browse/*` и кэшируется агрессивно. Одна чёткая граница».

Урок: CloudFront работает лучше всего, когда ваша структура URL отражает намерение кэширования. URL, указывающие на полностью публичные, статические данные, должны выглядеть иначе, чем URL, возвращающие персонализированные, динамические данные. Если они выглядят одинаково для CloudFront, либо кэш сломан, либо обслуживается неправильный контент.

Лео реструктурировал схему URL Nimbus за выходные. Конечные точки просмотра переехали на `/browse/`. API-конечные точки переехали на `/api/`. Аутентифицированный UI приложения переехал на `/app/`. Три поведения, три чёткие политики кэширования, ноль двусмысленности.

«Это немного рефакторинг», — сказал он.

«Это правильная структура», — сказала Прия. «Тебе она в итоге понадобилась бы».

**Origin Access Control: защита S3 с CloudFront**

Если ваш бакет S3 содержит приватный контент, который должен обслуживаться только через CloudFront (не напрямую), вы можете использовать **Origin Access Control (OAC)**, чтобы S3 отклонял запросы, не исходящие от CloudFront.

Таким образом:

- `d1234abcd.cloudfront.net/image.jpg` → Обслуживается (CloudFront имеет разрешение)
- `nimbus-assets.s3.amazonaws.com/image.jpg` → Заблокировано (прямой доступ к S3 запрещён)

Ваш контент доступен только через ваш дистрибутив, с применёнными вашими правилами кэша и настройками безопасности.

**Инцидент с устаревшим фото**

Ресторан 112 — колумбийское заведение на Истсайде — написал в поддержку в четверг утром. Клиент пожаловался, что главное фото ресторана всё ещё показывает старую витрину, хотя владелец загрузил новую два дня назад.

Лео открыл настройки дистрибутива CloudFront.

У поведения для `/images/*` был TTL семь дней. Портал партнёра-ресторана загрузил новое фото два дня назад, заменив файл по тому же ключевому пути S3: `restaurant-112/hero.jpg`. Старый файл исчез из S3. Но CloudFront всё ещё обслуживал его из кэша на каждом граничном узле, который загрузил его за последние семь дней.

«Мы изменили контент на источнике», — сказал Лео. «Но CloudFront об этом не знает. У него есть кэшированная копия, и он не будет проверять семь дней».

«Я уже задеплоил это — ой». Он предположил, что замена файла S3 автоматически обновит кэш CloudFront. Это не так. У CloudFront нет механизма обнаружения того, что контент по ключу S3 изменился — он просто обслуживает то, что закэшировал, пока TTL не истечёт.

Два варианта:

**Вариант первый: аннулирование.** Отправьте CloudFront запрос на аннулирование для `/images/restaurant-112/hero.jpg`. CloudFront помечает этот путь устаревшим на всех граничных узлах. Следующий запрос для этого пути загружает свежий контент из S3. Стоимость: первые 1 000 путей аннулирования каждый месяц бесплатны; сверх того $0,005 *за путь*. Для одного файла бесплатно. Для аннулирования тысяч файлов во время массового обновления затраты накапливаются.

**Вариант второй: версионированные имена файлов.** Вместо `hero.jpg` назовите файл `hero-v2.jpg`. Обновите ссылку в базе данных. У CloudFront нет кэшированной записи для `hero-v2.jpg` — первый запрос загружает его из S3, и пользователи видят его немедленно. Старый `hero.jpg` остаётся в кэше, но больше нигде не упоминается. Он истекает естественным образом через семь дней.

«Для контента, загружаемого пользователями», — сказала Прия, — «версионированные имена — правильный паттерн. Добавьте хэш или метку времени к имени файла. Каждая новая загрузка — это новая запись кэша. Никакой стоимости аннулирования, никакого устаревшего контента».

Лео обновил портал партнёра. Новые загрузки теперь будут храниться как `hero-{timestamp}.jpg`. Запись базы данных была обновлена новым путём. Старый кэшированный путь стал неактуален.

«А что насчёт случая развёртывания?» — спросила Майя. «Когда мы выпускаем новую версию приложения, и JavaScript меняется?»

«Тот же принцип», — сказала Прия. «Инструменты сборки, как Webpack, выдают хэшированные имена файлов: `app.a3b9c2d4.js`. Разверните новую версию, и хэш меняется: `app.f7e1b3c5.js`. CloudFront обслуживает оба из кэша — старые пользователи получают старый файл, новые пользователи получают новый файл. Никакого аннулирования, никакой проблемы координации».

«HTML-страница ссылается на текущий хэш», — сказал Лео. «Так что новые пользователи получают новый HTML с новым хэшем JS, и CDN обслуживает правильный файл».

«Стандартная практика», — подтвердила Прия.

«Улучшение наибольшее там, где проблема физики хуже всего», — заметил Том. «Сан-Паулу до Орегона — более двухсот миллисекунд. Это более четверти секунды, просто чтобы начать разговор».

«И контент никогда не достигает Сан-Паулу во второй раз», — сказал Лео. «Первый пользователь в Сан-Паулу загружает из Орегона и кэширует локально. Каждый пользователь после этого получает тридцать пять миллисекунд».

«Первый пользователь в Сан-Паулу оплачивает стоимость», — сказал Том. «Все остальные выигрывают».

«Так работают CDN», — сказала Прия. «Первый запрос заполняет кэш. Каждое попадание в кэш после этого почти бесплатно».

Следствие для глобальных продуктов значительно. Без CloudFront пользователь в Токио, ждущий 260 миллисекунд вашего главного изображения, ждёт из-за физики — оптоволоконных кабелей и скорости света. С CloudFront вы помещаете копию этого изображения в Токио, и проблема физики по сути исчезает.

---

**Несколько источников: ALB и S3 вместе**

«У нас изображения на S3 и API на балансировщике нагрузки», — сказала Майя. «Нам нужны два дистрибутива CloudFront?»

«Нет», — сказал Лео. «Один дистрибутив, несколько источников».

Один дистрибутив CloudFront может маршрутизировать разные URL-паттерны к разным источникам. Это паттерн с несколькими источниками:

```
eatnimbus.com/*         → Источник: ALB в us-west-2 (динамический контент)
eatnimbus.com/images/*  → Источник: бакет S3 (статические изображения)
eatnimbus.com/static/*  → Источник: бакет S3 (CSS, JS, шрифты)
```

CloudFront оценивает поведения в порядке конкретности. Запрос к `/images/hero.jpg` совпадает с поведением `/images/*` и идёт в S3. Запрос к `/api/orders` совпадает с универсальным `/*` и идёт к ALB.

Выгода: один домен, один SSL-сертификат, один дистрибутив CloudFront, несколько бэкендов. Пользователи видят единый домен. Маршрутизация для них невидима.

Одна операционная деталь, которая также является гарантированным фактом для экзамена: этот SSL-сертификат поступает из AWS Certificate Manager (ACM), и **сертификат, используемый CloudFront, должен быть запрошен или импортирован в `us-east-1`** — независимо от того, где живут ваши источники. CloudFront — глобальный сервис, чья плоскость управления живёт в us-east-1; сертификат, находящийся в us-west-2, просто не появится в выпадающем списке дистрибутива. (Для региональных сервисов, как ALB, сертификат живёт в собственном регионе ALB.)

«А ALB не ориентирован на публичную сторону?» — спросила Прия.

«Только CloudFront разговаривает с ALB», — сказал Лео. «Мы ограничиваем группу безопасности ALB управляемым списком префиксов CloudFront. Прямые соединения с ALB из интернета заблокированы».

«Значит, единственный способ достичь приложения — через CloudFront».

«Что означает, что правила WAF, завершение SSL и защита от DDoS применяются ко всему трафику, прежде чем он достигнет нас».

**CloudFront Functions против Lambda@Edge**

«Мы думали о том, что бы мы делали, если бы нам нужно было переписать URL на границе?» — спросила Прия. «Или добавить заголовок безопасности к каждому ответу?»

«Разве мы не можем сделать это в приложении?» — спросил Лео.

«Можем. Но если это происходит на границе — до того, как CloudFront обслуживает из кэша — мы экономим путь туда-обратно к источнику».

CloudFront поддерживает два механизма для запуска кода на границе:

**CloudFront Functions** — это лёгкие JavaScript-функции, которые выполняются на каждом граничном узле. Они выполняются за суб-миллисекундное время, обрабатывают миллионы запросов в секунду и предназначены для простых преобразований: переписывание URL, манипуляция заголовками, нормализация строк запроса, простые редиректы. Они могут запускаться на запросах зрителя и ответах зрителя (до и после кэша, с точки зрения пользователя). Они не могут делать сетевые вызовы. Стоимость: $0,10 за миллион вызовов.

**Lambda@Edge** запускает настоящие функции Lambda на региональных граничных узлах CloudFront (не на каждой точке присутствия, но на десятках крупных глобально). Lambda@Edge может делать сетевые вызовы, обращаться к базам данных, генерировать динамические ответы, выполнять сложную логику аутентификации. Она запускается на запросах зрителя, запросах источника, ответах источника и ответах зрителя — давая вам четыре точки вмешательства в жизненном цикле запроса. Стоимость: выше, чем у CloudFront Functions, оплачивается за запрос и длительность.

Ментальная модель:

| Случай использования | Инструмент |
|---|---|
| Переписать `/old-path` в `/new-path` | CloudFront Functions |
| Добавить заголовок `Strict-Transport-Security` | CloudFront Functions |
| Нормализовать строки запроса перед поиском в кэше | CloudFront Functions |
| A/B-тест: назначить тестовую куку на запросе зрителя | CloudFront Functions |
| A/B-тест: маршрутизировать 10% пользователей к другому источнику | Lambda@Edge (запрос источника — CloudFront Functions не могут менять источник) |
| Аутентифицировать токен JWT (требует криптобиблиотеку) | Lambda@Edge |
| Получить персонализированный контент из базы данных на границе | Lambda@Edge |
| Генерировать миниатюру изображения по запросу на границе | Lambda@Edge |

Для Nimbus: они использовали CloudFront Function для добавления заголовков безопасности к каждому ответу — `Strict-Transport-Security`, `X-Content-Type-Options`, `X-Frame-Options`. Две дюжины строк JavaScript. Суб-миллисекундное выполнение. Не нужен путь туда-обратно к источнику.

«Заняло бы дольше объяснить заголовки джуниор-инженеру», — сказал Лео, — «чем написать функцию».

**Ценовые классы: выбор граничных узлов**

«Мы думали о том, во что это обходится в масштабе?» — спросил Том, прокручивая страницу с ценами CloudFront.

«Сколько это стоит в месяц?» здесь технически было двумя вопросами. Первый: сколько берёт CloudFront? Второй: нужны ли вам все граничные узлы в мире?

Ценообразование передачи данных CloudFront варьируется по регионам. Трафик, обслуживаемый с граничных узлов в Северной Америке и Европе, самый дешёвый. Трафик из Южной Америки, Азиатско-Тихоокеанского региона, Австралии и Индии дороже — потому что инфраструктура там стоит дороже.

AWS позволяет выбрать **ценовой класс** для вашего дистрибутива:

- **Price Class All**: Использует все граничные узлы глобально. Лучшая производительность везде. Самая высокая стоимость передачи данных для регионов за пределами Северной Америки и Европы.
- **Price Class 200**: Использует большинство граничных узлов (Северная Америка, Европа, Азия, Ближний Восток, Африка). Исключает самые дорогие южноамериканские и некоторые океанийские узлы.
- **Price Class 100**: Использует только граничные узлы Северной Америки и Европы. Самый дешёвый. Пользователи в Сан-Паулу, Токио и Сиднее всё равно обслуживаются — но с североамериканского или европейского граничного узла, не с ближайшего к ним.

«Значит, если мы выбираем Price Class 100», — сказал Том, — «пользователь в Сан-Паулу обслуживается из... Майами? Нью-Йорка?»

«Где бы ни был ближайший включённый граничный узел. Может быть, 50 миллисекунд вместо 230 миллисекунд напрямую к Орегону», — сказала Прия. «Всё равно значимое улучшение. Не такое хорошее, как Price Class All».

«А разница в стоимости?»

«Передача данных из Южной Америки стоит примерно вдвое больше, чем из Северной Америки. Для стартапа, всё ещё наращивающего трафик, Price Class 200 — разумный компромисс — вы получаете Азию и Европу по более низкой цене, чем Price Class All, и большинство ваших пользователей покрыты».

«Начнём с 200», — сказал Том. «Когда у нас будут реальные данные о трафике из каждого региона, мы решим, стоит ли All того».

Правильный ценовой класс зависит от того, где ваши пользователи. Если у вас нет пользователей в Южной Америке, платить за южноамериканские граничные узлы — чистая трата. Если двадцать процентов вашей выручки приходит из Бразилии, улучшение производительности от Price Class All, вероятно, окупается.

**Проектирование ключа кэша**

«Мы думали о том, что произойдёт, когда два разных пользователя запрашивают один и тот же URL, но получают разный контент?» — спросила Прия.

Лео подумал об этом. «Персонализированные страницы».

«Или страницы для конкретного языка. Или мобильные против десктопных версий. Или страницы, которые варьируются по куке».

По умолчанию CloudFront использует только путь URL в качестве ключа кэша. Два запроса к `/browse` получают один и тот же кэшированный ответ, независимо от языковых предпочтений пользователя, типа устройства или куки сессии.

Если ваше приложение обслуживает разный контент на основе строк запроса, заголовков или куки — и вы хотите, чтобы CloudFront кэшировал эти вариации отдельно — вам нужно включить эти атрибуты в **ключ кэша**.

Для Nimbus:

- `/browse?city=miami` должен кэшироваться отдельно от `/browse?city=boston` — разные списки ресторанов. Включите строки запроса в ключ кэша.
- Мобильные пользователи могут получить другой макет. Включите нормализованный тип устройства (полученный из заголовка `User-Agent`) в ключ кэша.
- Заголовок `Accept-Language` определяет, на каком языке отрисовывается страница. Включите его в ключ кэша.

Однако будьте осторожны. Каждый атрибут ключа кэша, который вы добавляете, создаёт больше вариаций кэша. Если вы включаете всю строку `User-Agent` (которая варьируется по версии браузера, версии ОС и уровню патча), вы фактически ломаете кэширование — у каждого пользователя немного разный User-Agent, так что каждый запрос — это промах кэша.

Дисциплина: нормализуйте перед кэшированием. Сведите «iPhone 15 Pro Safari 17.4.1» к «mobile». Сведите все принятые языки к двум-трём, которые вы действительно поддерживаете. Включайте только то, что действительно меняет ответ.

«Чем конкретнее ваш ключ кэша», — сказал Лео, — «тем хуже ваш процент попаданий».

«А чем более общий», — сказала Прия, — «тем более вероятно, что вы обслуживаете неправильный контент неправильному пользователю».

«Значит, проектирование ключа кэша — тот же компромисс, что и всё остальное в кэшировании».

«Да», — сказала Прия. «Это всегда тот же компромисс».

## Когда CloudFront — не ответ: Global Accelerator

У мобильного приложения Nimbus была функция, за которой Том тихо наблюдал два месяца: статус заказа в реальном времени. Когда клиент размещал заказ, приложение оставалось подключённым через WebSocket, и экран управления заказами кухни обновлялся в реальном времени. Никакой кнопки обновления. Никакого опроса. Живое соединение, которое отправляло обновления в момент, когда кухня помечала блюдо готовым.

«Это использует WebSocket», — сказал Том, глядя на метрики задержки одним утром. «От пользователей в Сан-Паулу установление соединения занимает 340 миллисекунд. Что-то не так».

«CloudFront не кэширует WebSocket-соединения», — сказал Лео. «Он проксирует их — пропускает к источнику. Никакой выгоды от кэширования».

«Верно. Так почему он всё равно медленный?»

«Потому что WebSocket всё равно путешествует из Сан-Паулу к нашим серверам в Орегоне через публичный интернет», — сказал Лео. «CloudFront помогает, потому что он завершает TLS-рукопожатие на границе, а затем использует опорную сеть AWS к источнику. Но для постоянного WebSocket-соединения это всё равно соединение на дальнее расстояние».

«Есть сервис именно для этой проблемы», — сказала Прия.

**AWS Global Accelerator** — это не CDN. Он ничего не кэширует. Он не обслуживает контент с граничных узлов. Что он делает, так это даёт вам два статических Anycast IP-адреса, которые глобально анонсируются со всех граничных узлов AWS одновременно — а затем маршрутизирует трафик ваших пользователей через частную опорную сеть AWS вместо публичного интернета.

Когда клиент в Сан-Паулу открывает приложение Nimbus, его устройство подключается к ближайшему граничному узлу AWS (который может быть в самом Сан-Паулу). С этого граничного узла трафик путешествует к серверам Nimbus в Орегоне через частную, отслеживаемую, оптимизированную оптоволоконную сеть AWS — не через публичный интернет, где пакеты прыгают через непредсказуемых операторов и маршрутные прыжки.

Публичный интернет не спроектирован для задержки. Он спроектирован для отказоустойчивости — пакеты могут идти любым доступным путём. Опорная сеть AWS спроектирована иначе: она прямая, с низкой загруженностью и под операционным контролем AWS.

Том измерил разницу.

| Маршрут | Задержка (Сан-Паулу до Орегона) |
|---|---|
| Публичный интернет | 340 мс |
| Через Global Accelerator | 180 мс |

Снижение на 47%. Не от кэширования — от лучшего сетевого пути.

«Тогда почему бы нам просто не использовать CloudFront для всего?» — спросила Майя. «CloudFront уже маршрутизирует через опорную сеть AWS для динамического контента».

«CloudFront — только HTTP и HTTPS», — сказала Прия. «WebSocket работает с CloudFront, но только через HTTP-апгрейд. А некоторые наши протоколы — данные датчиков IoT, например — это чистый TCP или UDP. CloudFront их не обрабатывает. Global Accelerator не зависит от протокола. TCP, UDP, WebSocket, что угодно. Он перемещает пакеты, а не HTTP-запросы».

Была ещё одна разница, которую Прия отметила в своей документации по безопасности.

«Global Accelerator даёт нам два статических Anycast IP», — сказала она. «Эти IP никогда не меняются. Это означает, что мы можем добавить их в нашу политику безопасности, добавить их в белые списки партнёров, добавить их в правила файрвола. IP-адреса CloudFront меняются со временем — они управляются AWS и не фиксированы».

«А что насчёт переключения при сбое?» — спросил Лео.

«Мгновенное», — сказала Прия. «Если у нашего приложения в us-west-2 проблема, Global Accelerator может переместить трафик на резерв в us-east-1 менее чем за 30 секунд — не меняя IP-адрес, к которому подключаются пользователи. DNS-переключение через Route 53 занимает 60-300 секунд в зависимости от TTL. Global Accelerator быстрее».

**CloudFront против Global Accelerator — ментальная модель:**

CloudFront улучшает доставку через кэширование. Он построен для HTTP/HTTPS, и выгода наибольшая, когда контент можно кэшировать рядом с пользователями — статические файлы, изображения, JavaScript. Когда контент нельзя кэшировать, CloudFront всё равно помогает через маршрутизацию по опорной сети, но улучшение меньше.

Global Accelerator улучшает доставку через маршрутизацию. Он не перемещает контент. Он ничего не кэширует. Выгода применяется к каждому пакету — кэшированному или нет, HTTP или нет, статическому или динамическому. Два статических IP работают глобально. Переключение при сбое почти мгновенно. Случаи использования, где CloudFront недостаточен — WebSocket в реальном времени, протоколы на основе UDP, не-HTTP-трафик, глобальные приложения, требующие фиксированных IP — это там, где Global Accelerator — правильный инструмент.

Том обновил мобильное приложение Nimbus, чтобы оно подключалось к конечной точке Global Accelerator для функции статуса заказа в реальном времени. Установление WebSocket-соединения в Сан-Паулу упало с 340 мс до 180 мс. Обновления кухни всё равно ощущались мгновенными — потому что теперь, для пользователей за пределами Северной Америки, они действительно были такими.

## Сильные стороны и ограничения

**Почему CloudFront мощный**:

- Более 750 точек присутствия в 100+ городах — большинство пользователей получают контент за <20 мс
- Статический контент обслуживается в однозначное число миллисекунд после первого кэша
- Значительно снижает нагрузку на источник (повторный трафик никогда не достигает ваших серверов)
- Интегрирован с AWS Shield, WAF и Certificate Manager
- Никакого планирования ёмкости не нужно — CloudFront масштабируется автоматически
- Дистрибутивы с несколькими источниками маршрутизируют разные пути к разным бэкендам из одного домена
- CloudFront Functions обрабатывают лёгкую граничную логику с суб-миллисекундной задержкой

**Где всё усложняется**:

- Кэшированный контент может устаревать — аннулирование кэша стоит денег ($0,005 за путь после первых 1 000 бесплатных путей каждый месяц). Используйте версионированные имена файлов вместо этого.
- Заголовки Cache-Control должны быть правильно установлены на источнике — ошибки вызывают устаревший контент
- Динамический контент получает выгоду от оптимизации маршрутизации, но не от кэширования
- Отладка поведения кэша (что где кэшировано, как долго) требует понимания нескольких уровней: заголовки источника, настройки TTL CloudFront, правила поведения
- Передача данных через CloudFront стоит денег, хотя и меньше, чем стандартная передача данных
- Проектирование ключа кэша требует тщательного обдумывания — слишком конкретный ломает кэширование, слишком общий обслуживает неправильный контент

## Итоги

CloudFront не изменил физику. Свет по-прежнему путешествует с той же скоростью. Но он изменил, где живёт ответ — и для большинства пользователей ответ теперь был в нескольких миллисекундах, а не в нескольких сотнях. Процент попаданий в кэш после развёртывания: 83%. Это означало, что 830 000 из каждого миллиона запросов вообще не достигали серверов источника. Пользователи в Сан-Паулу ушли с 290 миллисекунд до 35 миллисекунд. Пользователи в Токио — с 260 до 28.

- **CDN** кэширует копии вашего контента на граничных узлах рядом с вашими пользователями — снижая задержку и нагрузку на источник.
- **CloudFront** — CDN AWS, с 750+ точками присутствия глобально.
- Промахи кэша загружают из **источника** (S3, ALB, EC2). Попадания в кэш обслуживаются с граничного узла — миллисекунды, а не сотни миллисекунд.
- **Поведения** позволяют устанавливать разные правила кэширования для разных URL-паттернов. Один дистрибутив может обслуживать `/images/*` из S3 и `/*` из ALB.
- Динамический контент не кэшируется, но CloudFront всё равно улучшает производительность через частную опорную сеть AWS.
- **Избегайте устаревшего контента**, используя версионированные имена файлов (например, `hero-v2.jpg`) вместо аннулирований — дешевле и надёжнее.
- **CloudFront Functions** обрабатывают лёгкую граничную логику (манипуляция заголовками, переписывание URL) с суб-миллисекундной скоростью. **Lambda@Edge** обрабатывает более тяжёлую обработку, требующую сетевых вызовов.
- **Ценовые классы** позволяют контролировать, какие граничные узлы обслуживают ваш трафик — и, следовательно, вашу стоимость передачи данных.
- **Проектирование ключа кэша** определяет, какие атрибуты запроса создают отдельные кэшированные вариации. Более конкретные ключи = более низкий процент попаданий. Менее конкретные = риск обслуживания неправильного контента.

## Советы по экзамену

*Домен SAA-C03: Проектирование высокопроизводительных архитектур (Домен 3, Задача 3.4)*

- **CloudFront + S3**: Классический паттерн экзамена для глобального обслуживания статических сайтов. Бакет S3 как источник, CloudFront как CDN, Origin Access Control для предотвращения прямого доступа к S3.
- **Граничные узлы против регионов против AZ**: Граничных узлов больше, и они существуют только для кэширования/CDN. Они не равны AZ (которые запускают ваши вычисления).
- **Аннулирование кэша**: Создаёт аннулирование `/images/*`, чтобы принудить CloudFront загружать свежий контент. Стоит денег — экзамен может спросить об экономически эффективной альтернативе: версионированные URL (`image-v2.jpg` вместо `image.jpg`), которые естественным образом обходят кэш.
- **Управление TTL**: `Cache-Control: max-age=3600` на источнике устанавливает TTL кэша в 1 час. CloudFront соблюдает эти заголовки. Минимальный TTL, максимальный TTL и TTL по умолчанию также можно установить в поведении дистрибутива.
- **CloudFront Functions против Lambda@Edge**: CloudFront Functions выполняются на границе для лёгкой манипуляции запросами/ответами (суб-миллисекунда). Lambda@Edge запускает ваш код Lambda на региональных граничных узлах для более тяжёлой обработки. Экзамен различает их по сложности случая использования. CloudFront Functions не могут делать сетевые вызовы; Lambda@Edge может.
- **Подписанные URL и подписанные куки**: Контролируют, кто может получить доступ к контенту через CloudFront. Подписанные URL дают доступ к конкретным файлам; подписанные куки дают доступ к нескольким файлам. Экзамен использует их для «контента для платных подписчиков».
- **Ценовой класс**: Экзамен может спросить, какой ценовой класс выбрать для глобальной аудитории против аудитории Северной Америки/Европы. Price Class All = лучшая производительность, самая высокая стоимость. Price Class 100 = только Северная Америка и Европа, самая низкая стоимость.
- **Ключ кэша**: Ключ кэша по умолчанию — это URL. Добавление строк запроса, заголовков или куки в ключ кэша создаёт отдельные кэшированные вариации — но увеличивает частоту промахов кэша. Экзамен может представить сценарий, где контент варьируется по параметру запроса, и спросить, как настроить кэширование.
- **Переключение при сбое источника**: CloudFront поддерживает группу источников с основным и вторичным источником. Если основной источник возвращает ошибку 5xx, CloudFront автоматически повторяет попытку с вторичным. Отличается от переключения Route 53 — это в пределах одного дистрибутива CloudFront.
- **Поведения с несколькими источниками**: Один дистрибутив может маршрутизировать `/images/*` в S3 и `/*` в ALB. Экзамен может представить это как «как обслуживать статический и динамический контент из одного домена без двух дистрибутивов».
- **CloudFront против Global Accelerator:** CloudFront = CDN для HTTP/HTTPS, кэширует контент на граничных узлах, снижает нагрузку на источник, лучше всего для статического и кэшируемого контента. Global Accelerator = любой протокол TCP/UDP, ничего не кэширует, маршрутизирует трафик через частную опорную сеть AWS, предоставляет 2 статических Anycast IP, поддерживает почти мгновенное региональное переключение при сбое. Триггер экзамена: «улучшить задержку для не-HTTP трафика» или «статический IP для глобального приложения» или «производительность WebSocket для глобальных пользователей» или «более быстрое региональное переключение при сбое, чем DNS» → Global Accelerator. «Обслуживать статические файлы глобально с низкой задержкой» → CloudFront.

**Упражнение 2 — Сценарий SAA-C03**

*Сценарий*: Программная компания распространяет большие файлы установщиков (~2 ГБ каждый) из бакета S3 клиентам по всему миру. Скорость загрузки медленная для клиентов в Азии. Команда хочет улучшить производительность без репликации бакета S3 в несколько регионов. Им также нужно гарантировать, что только платящие клиенты могут загружать установщики.

Какое решение НАИЛУЧШИМ образом отвечает этим требованиям?

A) Включить S3 Transfer Acceleration на бакете и генерировать подписанные URL для платящих клиентов  
B) Использовать CloudFront с бакетом S3 в качестве источника, включить Origin Access Control и использовать Подписанные URL CloudFront для платящих клиентов  
C) Создать бакет S3 в каждом регионе AWS и использовать маршрутизацию по геолокации Route 53 для направления клиентов к ближайшему бакету  
D) Использовать Application Load Balancer в каждом регионе с экземплярами EC2, которые обслуживают файлы установщиков

**Подсказка 1**: Требование — улучшить глобальную производительность *без* репликации бакета. Какой вариант не требует нескольких бакетов?

**Подсказка 2**: Какой сервис конкретно контролирует, кто может получить доступ к контенту, обслуживаемому через CloudFront?

**Подсказка 3**: S3 Transfer Acceleration оптимизирован для дальних загрузок *в* S3. Для доставки контента *из* S3 пользователям глобально CloudFront — правильный инструмент.

**Ответ**: B

**Объяснение**: CloudFront кэширует файлы установщиков на граничных узлах глобально после первой загрузки. Последующие загрузки из того же региона поступают с граничного узла — значительно быстрее, чем пересекать Тихий океан из S3 в us-west-2. Origin Access Control гарантирует, что бакет S3 доступен только через CloudFront. Подписанные URL ограничивают доступ платящим клиентам.

**Почему не A?** S3 Transfer Acceleration оптимизирован для дальних загрузок *в* S3 — не для распространения контента *из* S3 глобальной аудитории. Для этого CloudFront — правильный инструмент. Подписанные URL контролируют доступ, но не улучшают глобальную производительность.

**Почему не C?** Создание бакета S3 в каждом регионе действительно работает для производительности, но противоречит требованию не использовать репликацию. Это также требует стратегии синхронизации данных между бакетами.

**Почему не D?** Экземпляры EC2 за балансировщиком нагрузки в каждом регионе значительно дороже CloudFront и требуют управления серверами в нескольких регионах.
