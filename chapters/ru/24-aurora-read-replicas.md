**Реплики для чтения: распределение трафика чтения**

Большинство веб-приложений читают данные гораздо чаще, чем пишут. Клиент, просматривающий меню, выполняет десятки запросов SELECT. Размещение заказа создаёт несколько запросов INSERT/UPDATE. Соотношение обычно составляет 10:1 или выше.

**Реплика для чтения** — это дополнительный инстанс RDS, который получает копию всех записей от основного и делает их доступными для запросов SELECT.

Как это работает:

1. Операции записи приложения (INSERT, UPDATE, DELETE) направляются к основной базе данных
2. Основная реплицирует эти изменения асинхронно к репликам для чтения
3. Операции чтения (SELECT) приложения распределяются между репликами для чтения
4. Реплики делят нагрузку — каждая обрабатывает долю общего трафика чтения

В результате: основная база данных обрабатывает только записи (и опционально часть чтений). Реплики для чтения несут нагрузку по чтению. При соотношении чтение/запись 10:1 добавление одной реплики примерно вдвое снижает общую нагрузку на основную.

**Важное ограничение**: репликация **асинхронная**. Есть задержка репликации — обычно миллисекунды, но может достигать секунд под нагрузкой. Чтение из реплики может видеть данные, немного отстающие от основной. Для большинства операций чтения (просмотр меню, просмотр истории заказов) это приемлемо. Для «прошёл ли мой заказ?» — читайте из основной.

**Реплики для чтения: подробности**

- У одной основной RDS может быть до 5 реплик для чтения
- Реплики для чтения могут находиться в том же регионе или в другом регионе (кросс-региональные реплики)
- Реплики для чтения могут сами иметь реплики (цепочка)
- Реплики для чтения — отдельные конечные точки: приложение должно направлять чтение к конечной точке реплики
- Реплики для чтения могут быть повышены до самостоятельных баз данных (полезно для аварийного восстановления)

- Операции записи → конечная точка основной
- Просмотр меню, история заказов → конечная точка реплики

**Amazon Aurora: переосмысление движка базы данных**

Aurora — собственный движок реляционных баз данных AWS, совместимый с MySQL и PostgreSQL. Он был разработан с нуля для облачных нагрузок, переработав принцип работы уровня хранилища реляционной базы данных.

В традиционной конфигурации RDS (MySQL, PostgreSQL) хранилище и вычисления тесно связаны. Движок базы данных управляет файлами данных. Репликация копирует данные от основной к реплике. Реплика должна повторно выполнять каждую операцию записи.

Aurora разделяет хранилище и вычисления. Она использует распределённый, отказоустойчивый уровень хранилища, который автоматически реплицирует данные в шести копиях по трём зонам доступности. Уровень вычислений (инстансы базы данных) располагается поверх этого уровня хранилища.

**Что это меняет**:

**Реплики для чтения**: репликам Aurora не нужно реплицировать данные — они уже разделяют один уровень хранилища. Это означает:

- До 15 реплик для чтения (против 5 для обычного RDS)
- Задержка репликации обычно менее 100 миллисекунд (против секунд для RDS под нагрузкой)
- Реплики могут быть повышены до основной менее чем за 30 секунд (против нескольких минут)

**Переключение при сбое**: поскольку реплики разделяют хранилище, переключение происходит гораздо быстрее — повышение не требует передачи данных, только перенаправления записей.

**Хранилище**: Aurora автоматически масштабирует хранилище с шагом 10 ГБ, до 128 ТБ. Вам никогда не нужно заранее выделять хранилище.

**Производительность**: Aurora утверждает в 5 раз большую пропускную способность, чем стандартный MySQL, и в 3 раза больше, чем стандартный PostgreSQL, для эквивалентных типов инстансов.

**Ценообразование Aurora: вопрос Tom**

— Сколько это стоит? — спросил Tom.

Ценообразование Aurora отличается от RDS:

**Цена инстанса**: аналогична ценам на инстансы RDS по типу.

**Цена хранилища**: $0,10 за ГБ в месяц (платите за то, что хранится, автоматически масштабируется).

**Цена I/O**: Aurora взимает плату за каждый I/O-запрос (чтение/запись в хранилище). Это может быть существенным для нагрузок с большим количеством записей.

— Подождите, — сказал Tom. — Мы платим за I/O отдельно?

— Aurora Serverless v2 и Aurora I/O-Optimized меняют эту модель ценообразования, — сказал Leo. — Aurora I/O-Optimized не взимает плату за I/O, но выше цена хранилища и инстанса. Лучше для нагрузок с большим объёмом I/O.

Tom посмотрел на компромисс. Для Nimbus с интенсивным чтением (много запросов меню, мало записей) Aurora I/O-Optimized может стоить дороже. Стандартное ценообразование Aurora может подходить больше.

Это реальное решение по стоимости, которое принимают старшие инженеры: нужно знать паттерны I/O вашей нагрузки, чтобы выбрать правильно.

**Aurora Serverless: масштабирование без мыслей об инстансах**

**Aurora Serverless v2** — это конфигурация, которая автоматически масштабирует вычислительные мощности в зависимости от фактической нагрузки на базу данных. Вместо выбора фиксированного размера инстанса (db.r6g.large) вы задаёте минимальные и максимальные мощности в единицах Aurora Capacity Units (ACU).

Aurora Serverless v2:

- Масштабируется вверх за секунды при росте нагрузки
- Масштабируется вниз почти до нуля в периоды простоя
- Стоимость: $0,12 за ACU-час (плюс хранилище и I/O)

Для нагрузок с переменным трафиком — пиковые нагрузки в пятницу у Nimbus против тихого воскресного утра — Serverless v2 снижает затраты в непиковые периоды и справляется с пиковыми нагрузками без предварительного выделения ресурсов.

— Значит, во время пика в пятницу, — сказал Leo, — Aurora автоматически масштабируется вверх. В воскресенье утром, когда трафика почти нет, масштабируется обратно до минимума.

— И мы платим только за мощности, которые используем, — сказал Tom.

— Верно.

У Tom был вид человека, который нашёл именно то, что искал.

**Aurora Global Database: чтение из нескольких регионов**

**Aurora Global Database** распространяет Aurora на несколько регионов AWS:

- **Один основной регион** обрабатывает все записи
- **До пяти вторичных регионов** обслуживают чтение с обычно менее чем 1 секундой задержки репликации
- Вторичные регионы могут быть повышены до основного менее чем за 1 минуту (для сценариев аварийного восстановления)

Для глобального расширения Nimbus Aurora Global Database позволит партнёру-ресторану в Лондоне запрашивать своё локальное меню из реплики для чтения в EU, тогда как все заказы (записи) по-прежнему проходят через основную в US.

**RDS и Aurora: когда выбрать каждый**

| Фактор              | RDS (PostgreSQL/MySQL)           | Aurora                                                        |
|---------------------|----------------------------------|---------------------------------------------------------------|
| Стоимость           | Ниже для небольших нагрузок      | Выше базовая, но лучше масштабируется                         |
| Совместимость       | Полная                           | Совместима с MySQL/PostgreSQL (с незначительными различиями)  |
| Макс. реплики       | 5                                | 15                                                            |
| Задержка репликации | Может достигать секунд           | Обычно <100 мс                                                |
| Хранилище           | Фиксированное выделение          | Авто-масштабирование до 128 ТБ                                |
| Время переключения  | 60–120 секунд                    | <30 секунд                                                    |
| Бессерверный вариант| Ограничен                        | Aurora Serverless v2                                          |
| Лучше подходит для  | Стабильные, предсказуемые нагрузки | Переменный трафик, высокий объём чтения, нужно быстрое переключение |

## Преимущества и ограничения

**Преимущества Aurora**:

- Значительно более быстрое переключение при сбое, чем у стандартного RDS
- До 15 реплик для чтения с минимальной задержкой
- Авто-масштабируемое хранилище
- Serverless v2 для переменных нагрузок
- Global Database для развёртывания в нескольких регионах

**Ограничения Aurora**:

- Более высокая стоимость для небольших, стабильных нагрузок
- Ценообразование за I/O может быть существенным для нагрузок с большим объёмом записей (используйте I/O-Optimized для этого)
- Незначительные отличия в совместимости MySQL/PostgreSQL могут потребовать изменений кода
- Холодные старты Serverless v2 (с почти нулевого уровня) могут вызывать всплески задержки

## Резюме

- **Реплики для чтения** распределяют трафик чтения от основной. Асинхронная репликация — незначительная задержка приемлема для большинства операций чтения.
- **Aurora** переосмысляет уровень хранилища: распределённый, разделяемый между репликами, авто-масштабируемый.
- Aurora предлагает: 15 реплик для чтения, задержку репликации <100 мс, переключение при сбое <30 с, авто-масштабируемое хранилище до 128 ТБ.
- **Aurora Serverless v2**: авто-масштабирует вычислительные мощности в зависимости от нагрузки. Хорошо для переменного трафика.
- **Aurora Global Database**: основная в одном регионе, реплики для чтения в до пяти регионах.
- Выбирайте RDS для небольших, стабильных, предсказуемых нагрузок. Выбирайте Aurora, когда нужно масштабирование, быстрое переключение при сбое или обработка переменного трафика.

**Ответ**: B

**Пояснение**: Aurora MySQL с репликами Aurora обеспечивает почти нулевую задержку репликации (миллисекунды, а не секунды) для стабильной производительности чтения под нагрузкой. Aurora Serverless v2 авто-масштабирует вычисления при всплесках трафика без избыточного выделения ресурсов. Хранилище Aurora авто-масштабируется по мере роста данных. Переключение Aurora (повышение реплики) завершается менее чем за 30 секунд — соответствует требованию RTO.

**Почему не A?** Переключение RDS Multi-AZ занимает 60–120 секунд — не соответствует RTO < 30 секунд. Задержка стандартной реплики RDS для чтения может достигать секунд под нагрузкой — «стабильную» задержку чтения труднее гарантировать.

**Почему не C?** Вертикальное масштабирование (инстанс большего размера) увеличивает мощность, но не распределяет нагрузку чтения. База данных остаётся единой точкой отказа для чтений.

**Почему не D?** DynamoDB — NoSQL: миграция с MySQL на DynamoDB требует перепроектирования модели данных и запросов приложения, что далеко выходит за рамки данной задачи по улучшению производительности.
