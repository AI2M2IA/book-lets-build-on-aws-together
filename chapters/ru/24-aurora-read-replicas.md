# Глава 24: База данных, которая растёт вместе с вами

Представьте библиотеку, которая начиналась с двух полок и одного библиотекаря. Какое-то время этого хватало. Библиотекарь знал, где что лежит. На запросы отвечали быстро. Затем библиотека выросла: десять полок, двадцать, сорок. Тот же библиотекарь, тот же стол, тот же карточный каталог. Теперь найти что-либо означает ждать. Библиотекарь не медлителен — просто библиотеки стало больше, чем один человек может обслуживать в прежнем темпе.

Решение — не более быстрый библиотекарь. Это библиотека другого рода.

«Есть два подхода», — сказал Лео. «Реплики для чтения или Aurora».

«В чём разница?»

Когда библиотека становится популярной, образуется очередь. Решение: нанять больше библиотекарей — но только для ответов на вопросы. Приём книг всё равно идёт через основную стойку».

«Это реплика для чтения», — сказала Прия.

«Именно. Aurora идёт на шаг дальше — она переделывает саму систему стеллажей, чтобы каждый библиотекарь делил одни и те же полки и всегда видел одни и те же книги без задержки. Никакого ожидания, пока обновления просочатся от одной стойки к другой».

**Реплики для чтения: распределение трафика чтения**

Большинство веб-приложений читают данные гораздо чаще, чем пишут. Клиент, просматривающий меню, выполняет десятки запросов SELECT. Размещение заказа создаёт несколько запросов INSERT/UPDATE. Соотношение обычно составляет 10:1 или выше.

**Реплика для чтения (read replica)** — это дополнительный экземпляр RDS, который получает копию всех записей с основного (primary) и делает эти записи доступными для запросов SELECT.

Как это работает:

1. Записи приложения (INSERT, UPDATE, DELETE) идут на основную базу данных
2. Основная база асинхронно реплицирует эти изменения на реплики для чтения
3. Чтения приложения (SELECT) распределяются по репликам для чтения
4. Реплики для чтения разделяют нагрузку — каждая обрабатывает долю общего трафика чтения

Результат: основная база данных обрабатывает только записи (и, опционально, некоторые чтения). Реплики для чтения обрабатывают нагрузку чтения. Для соотношения чтения/записи 10:1 добавление одной реплики для чтения примерно вдвое снижает общую нагрузку на основную.

**Важное ограничение**: репликация **асинхронна**. Есть задержка репликации — обычно миллисекунды, но под нагрузкой могут быть секунды. Чтение с реплики может увидеть данные, слегка отстающие от основной. Для большинства чтений (просмотр меню, просмотр истории заказов) это приемлемо. Для «прошёл ли мой заказ?» — читайте с основной.

**Реплики для чтения: детали**

- У вас может быть до 15 реплик для чтения на один основной экземпляр RDS (MySQL, PostgreSQL, MariaDB)
- Реплики для чтения могут быть в том же регионе или в другом регионе (кросс-региональные реплики)
- Реплики для чтения сами могут иметь реплики для чтения (цепочки)
- Реплики для чтения — это отдельные конечные точки — ваше приложение должно направлять чтения на конечную точку реплики
- Реплики для чтения можно повысить до автономных баз данных (полезно для DR)

Для Nimbus Лео добавил одну реплику для чтения. «Всё будет хорошо», — сказал он, когда Прия спросила, протестировал ли он логику маршрутизации чтения/записи приложения перед переключением трафика. Он обновил приложение так:

- Операции записи → конечная точка основной
- Просмотр меню, история заказов → конечная точка реплики

CPU на основной упал с 89% до 41% на пике.

**Проблема консистентности «чтение-после-записи»**

Через три дня после включения реплики для чтения пришёл тикет поддержки. Партнёр-ресторан обновил своё меню — удалил снятый с производства пункт — и затем позвонил подтвердить, что он удалён. Агент службы поддержки открыл меню из интерфейса Nimbus. Пункт всё ещё был там.

Двадцать секунд спустя его не стало.

Задержка асинхронной репликации. Запись (DELETE пункта меню) пошла на основную. Чтение агента службы поддержки пошло на реплику, которая ещё не получила изменение. Реплика отставала на 15 секунд в тот момент — не необычно, но заметно.

«А что, если кто-то попытается взломать через окно итоговой консистентности?» — спросила Прия. «Или просто — что, если заказ размещается на пункт меню, который только что удалили? Мы списали бы деньги с клиента, а у ресторана не было бы этого пункта».

Это была реальная проблема консистентности, а не просто неудобство UX.

Решение: определить, у каких чтений есть требования к консистентности, и направить их на основную.

**Чтения, которые могут идти на реплику** (итоговая консистентность приемлема):
- Клиент, просматривающий меню ресторана (устаревание на 1-2 секунды незаметно)
- Запросы истории заказов (пользователь, просматривающий свою историю заказов минутной давности)
- Чтения аналитического типа (топ ресторанов на этой неделе)

**Чтения, которые должны идти на основную** (требуется консистентность «чтение-после-записи»):
- Сразу после записи, когда приложению нужно подтвердить, что запись удалась
- Чтения статуса заказа сразу после размещения заказа
- Чтения меню, инициированные интерфейсом управления рестораном (ресторан только что изменил меню)

Приложение добавило подсказку маршрутизации в слой соединений с базой данных: если запрос пришёл из дашборда управления рестораном, направить на основную. Если он пришёл от просматривающего клиента, направить на реплику. HTTP-заголовок `X-Read-Consistency: strong` служил сигналом.

«Это не так трудно», — сказал Лео. «Нужно просто знать, каким чтениям это требуется».

«И задокументировать это», — сказала Прия. «Чтобы следующий человек, который добавит новую конечную точку, знал, какой пул использовать».

«Сколько это стоит в месяц?» — спросил Том. Это был его стандартный начальный вопрос для любого нового сервиса.

Реплика для чтения того же типа экземпляра стоит столько же, сколько основная. С $340/месяц до $680/месяц.

«Мы удвоили стоимость, чтобы примерно вдвое снизить нагрузку», — сказал Том.

«Да. Но альтернативой был переход на более крупный тип экземпляра, который тоже стоил бы дороже и не распределял бы нагрузку чтения».

Том сделал расчёты. Он кивнул, неохотно.

«А что, если основная упадёт?» — спросила Майя, прежде чем Том успел перейти к Aurora. «Что произойдёт с репликой для чтения?»

Лео объяснил повышение реплики.

**Если основной экземпляр RDS падает**, AWS автоматически переключается на резервную реплику в конфигурации Multi-AZ (другой вид реплики — синхронный резерв, а не реплика для чтения). Резерв Multi-AZ становится новой основной. Реплики для чтения продолжают обслуживать чтения, теперь реплицируясь с новой основной. С точки зрения приложения, DNS конечной точки основной меняется, указывая на бывший резерв, и приложение переподключается.

Переключение обычно занимает 60-120 секунд для RDS PostgreSQL. В течение этого окна записи проваливаются.

**Повышение реплики для чтения (read replica promotion)** — это отдельная операция и отдельный сценарий. Если вы хотите взять реплику для чтения и сделать её независимой, доступной для записи базой данных (для DR, для миграции в новый регион или потому что основная исчезла и вам нужно повысить, а не ждать переключения Multi-AZ), вы можете повысить реплику для чтения до автономной основной. Повышение занимает несколько минут, после чего реплика больше не реплицируется с оригинальной основной — это её собственная база данных.

«Подумали ли мы о том, что произойдёт, если основная в us-west-2 полностью упадёт?» — спросила Прия. «Не просто переключение на резерв Multi-AZ — весь регион».

«Если регион упадёт», — сказал Лео, — «резерв Multi-AZ тоже в us-west-2. Оба падают вместе».

«Так что для настоящего сценария регионального DR», — сказал Том, — «нам нужна была бы реплика для чтения в us-east-1, которую мы могли бы повысить».

«Да. Кросс-региональная реплика для чтения. У нас её пока нет».

«Сколько это стоит в месяц?» — спросил Том. Он уже знал, что ответ будет включать решение.

Кросс-региональная реплика для чтения db.r6g.large в us-east-1: $340/месяц (та же стоимость экземпляра). Плюс кросс-региональная передача данных для репликации: минимальная при объёме записи Nimbus. Итого: примерно $350/месяц за DR-реплику.

«Это $4200 в год», — сказал Том, — «чтобы защититься от сценария, который происходил с регионами AWS менее пяти раз за десять лет».

«А стоимость простоя Nimbus в течение 24 часов во время регионального события?» — спросила Прия.

Том посчитал. Он не ответил вслух. Но он добавил «кросс-региональная реплика для чтения» в бэклог DR.

«Что такое Aurora?» — спросил он.

**Amazon Aurora: переосмысление движка базы данных**

Aurora — это проприетарный реляционный движок базы данных AWS, совместимый с MySQL и PostgreSQL. Он был спроектирован с нуля для облачных нагрузок, переосмыслив то, как работает слой хранилища реляционной базы данных.

В традиционной настройке RDS (MySQL, PostgreSQL) хранилище и вычисления тесно связаны. Движок базы данных управляет файлами данных. Репликация копирует данные с основной на реплику. Реплика должна повторить (redo) каждую операцию записи.

Это создаёт потолок скорости репликации: реплика может применять записи только так быстро, как может обрабатывать журнал репликации. В период интенсивной записи — массовый импорт, флеш-распродажа, пакетное обновление — реплика может отстать. Задержка репликации — не изъян реализации; это следствие архитектуры.

Прия отметила это сразу же, когда Лео предложил реплики для чтения. «А подумали ли мы о том, что произойдёт, если задержка репликации подскочит до 30 секунд во время пятничного наплыва? Реплика отстаёт на 30 секунд. Клиент размещает заказ, кухонный слот резервируется в основной, но второй клиент, запрашивающий реплику, не видит резервирования. Два заказа, один слот».

«Это проблема консистентности инвентаря», — сказал Лео.

«Это именно проблема консистентности инвентаря», — подтвердила Прия. «Вот почему чтения инвентаря — „доступен ли ещё этот пункт?“ — должны идти на основную».

Архитектура Aurora адресует задержку напрямую.

Aurora отделяет хранилище от вычислений. Она использует распределённый, отказоустойчивый слой хранилища, который автоматически реплицирует данные по трём зонам доступности в шести копиях. Слой вычислений (экземпляры базы данных) располагается поверх этого слоя хранилища.

**Что это меняет**:

**Реплики для чтения**: репликам Aurora не нужно реплицировать данные — они уже делят один и тот же слой хранилища. Это означает:

- До 15 реплик Aurora (Aurora Replicas), которые делят том хранилища (обычный RDS тоже допускает до 15 реплик для чтения, но каждая — это полная копия данных)
- Задержка репликации обычно менее 100 миллисекунд (против секунд для RDS под нагрузкой)
- Реплики можно повысить до основной менее чем за 30 секунд (против минут)

**Переключение (failover)**: поскольку реплики делят хранилище, переключение намного быстрее — повышение не включает передачу данных, только перенаправление записей.

**Хранилище**: Aurora автоматически масштабирует хранилище шагами по 10 ГБ, до 128 ТиБ (256 ТиБ в недавних версиях движка). Вы никогда не выделяете хранилище заранее.

**Производительность**: Aurora заявляет 5-кратную пропускную способность стандартного MySQL и 3-кратную стандартного PostgreSQL для эквивалентных типов экземпляров.

Вы можете задаться вопросом: если все реплики делят одно и то же хранилище, не становится ли это хранилище единой точкой отказа? Слой хранилища Aurora автоматически реплицирует данные по шести копиям в трёх зонах доступности. Само хранилище более устойчиво, чем любая отдельная настройка RDS Multi-AZ — оно спроектировано пережить потерю целой AZ без потери данных и без необходимости переключения.

Второй распространённый вопрос: если Aurora совместима с MySQL/PostgreSQL, можно ли мигрировать с RDS PostgreSQL на Aurora PostgreSQL без изменения кода приложения? Почти. Совместимость Aurora PostgreSQL означает, что Aurora реализует протокол передачи (wire protocol) PostgreSQL и поддерживает подавляющее большинство синтаксиса и функций SQL PostgreSQL. Большинство приложений мигрируют с нулевыми изменениями кода. Крайние случаи: небольшое количество расширений PostgreSQL недоступны в Aurora, некоторые запросы к системному каталогу возвращают другие значения, а некоторые административные операции отличаются. Для продакшен-миграций тестируйте с параллельным трафиком чтения перед переключением записей.

Для Nimbus миграция с RDS PostgreSQL на Aurora PostgreSQL заняла один день. Приложение направили на конечную точку Aurora. Запрос меню — после того как Лео добавил индекс, на который Performance Insights указал как на главного потребителя нагрузки базы данных — выполнялся за 4 мс вместо 620 мс. Пул соединений больше не достигал 198 из 200. Задержка P95 упала до 28 мс.

«Это другой движок базы данных», — сказал Лео, — «который приложение считает тем же движком базы данных».

«А интересная часть?» — спросила Майя.

«Быстрое клонирование базы данных».

«Принято к сведению», — тихо сказал Сэм с другого конца комнаты, уже печатая. Сэм был бэкенд-инженером, который присоединился к команде несколькими неделями ранее, чтобы снять часть работы с базой данных с плеч Лео. Никто не спросил, что он делает.

**Цены Aurora: вопрос Тома**

Цены Aurora отличаются от RDS:

**Цена экземпляра**: похожа на цену экземпляра RDS по типу.

**Цена хранилища**: $0.10 за ГБ в месяц (вы платите за то, что хранится, автоматически масштабируется).

**Цена I/O**: Aurora взимает плату за запрос I/O (чтение/запись в хранилище). Это может быть значительным для нагрузок с интенсивной записью.

«Подожди», — сказал Том. «Мы платим за I/O отдельно?»

«Aurora Serverless v2 и Aurora I/O-Optimized меняют эту модель ценообразования», — сказал Лео. «Aurora I/O-Optimized не взимает плату за I/O, но имеет более высокую цену хранилища и экземпляра. Лучше для нагрузок с интенсивным I/O».

Том посмотрел на компромисс. Для Nimbus, у которого было много чтения (множество запросов меню, мало записей), Aurora I/O-Optimized могла бы стоить дороже. Стандартное ценообразование Aurora могло бы быть уместным.

Полезная эвристика: если ваши платы за I/O превышают примерно 25% от вашего общего счёта Aurora, I/O-Optimized, скорее всего, дешевле. Для нагрузки Nimbus с интенсивным чтением платы за I/O были низкими — применяется стандартное ценообразование. Для нагрузки с интенсивной записью, вроде системы логирования событий, I/O-Optimized мог бы значительно снизить затраты.

Это реальное решение о стоимости, которое принимают опытные инженеры: вам нужно знать паттерны I/O вашей нагрузки, чтобы выбрать правильно.

Если ваша нагрузка небольшая, стабильная и предсказуемая, RDS PostgreSQL проще и заметно дешевле — но если ваш трафик непредсказуем, ваш объём данных растёт за пределы того, что вы можете выделить заранее, или вам нужно автоматическое переключение менее чем за 30 секунд, модель общего хранилища Aurora оправдывает более высокую базовую стоимость.

**Aurora Serverless: масштабирование без размышлений об экземплярах**

**Aurora Serverless v2** — это конфигурация, которая автоматически масштабирует вычислительную мощность на основе фактической нагрузки базы данных. Вместо выбора фиксированного размера экземпляра (db.r6g.large) вы устанавливаете минимальную и максимальную мощность в единицах мощности Aurora (Aurora Capacity Units, ACU).

Aurora Serverless v2:

- Масштабируется вверх за секунды при росте нагрузки
- Масштабируется вниз в периоды простоя — и с конца 2024 года может авто-приостанавливаться вплоть до 0 ACU, когда нет соединений (возобновление занимает ~15 секунд; авто-приостановка не работает с RDS Proxy или другими прокси, удерживающими соединения)
- Стоимость: $0.12 за ACU-час (плюс хранилище и I/O)

Для нагрузок с переменным трафиком — пятничные всплески Nimbus против тишины утром в понедельник — Serverless v2 снижает затраты в непиковые периоды и справляется с пиками без предварительного выделения.

«Так что во время пятничного всплеска», — сказал Лео, — «Aurora автоматически масштабируется вверх. Воскресным утром, когда у нас почти нет трафика, она масштабируется обратно вниз до минимума».

«И мы платим только за мощность, которую используем», — сказал Том.

«Верно».

После месяца на Aurora Serverless v2 Лео открыл график ACU (Aurora Capacity Unit) за предыдущую неделю.

График показал два чётких паттерна. В течение недели база данных работала на 2-4 ACU — тихий гул фоновых запросов, проверки работоспособности ECS, ETL-задания Glue и тестирование разработки. В пятницу вечером между 18:00 и 22:00 число ACU росло:

```
Пятница 18:00  → 6 ACU
Пятница 19:00  → 14 ACU
Пятница 19:45  → 26 ACU  (пик — заказы пиццы подскакивают перед началом матча NFL)
Пятница 20:30  → 18 ACU
Пятница 21:00  → 12 ACU
Пятница 22:30  → 4 ACU
Суббота 02:00 → 2 ACU  (минимум)
```

Масштабирование было почти мгновенным — Aurora Serverless v2 масштабируется шагами по 0,5 ACU, и она может добавить мощность за секунды, а не за минуты, требуемые для выделения нового экземпляра RDS.

«Сколько стоил тот пятничный пик?» — спросил Том.

При $0.12 за ACU-час: пятничный пик был 4 часа в среднем по 18 ACU → $8.64 за пиковый период. Остаток недели при среднем 3 ACU × 164 часа × $0.12 = $59.04. Итого за неделю: $67.68.

Эквивалентный выделенный экземпляр для обработки пятничного пика (db.r6g.xlarge, 4 vCPU, 32 ГБ) стоил бы $0.937/час × 168 часов = **$157.42 за неделю** — независимо от того, материализовался ли когда-либо пятничный пик.

«Serverless v2 — это $67 за неделю. Выделенный экземпляр, рассчитанный на пик, — $157», — сказал Том. «Это снижение на 57%».

«На базе данных, которая законно использует 26 ACU в течение четырёх часов в пятницу и 2 ACU остаток недели», — сказал Лео. «Если ваша база данных работает на стабильно высокой нагрузке всю неделю, выделенный экземпляр дешевле. Экономия исходит из переменчивости».

Том медленно кивнул. Он добавлял это к паттерну в своих заметках: у каждой истории экономии в этом квартале была одна и та же форма. Вы платите за то, что используете, а не за то, что вам может понадобиться. Политики жизненного цикла S3 платили только за класс хранилища, который заслуживал каждый объект. Lambda платила только за время вызова. Fargate платил только за CPU и память задач. Aurora Serverless v2 платила только за ACU, которые база данных фактически потребляла.

У Тома было выражение лица человека, нашедшего именно то, что искал.

**Восстановление после плохой миграции: клоны, PITR и кнопка отмены**

Через две недели после перехода на Aurora Сэм запустил скрипт миграции базы данных в продакшене. Скрипт должен был удалить столбец `legacy_menu_format` из таблицы `menu_items`. Он запустил его без клаузы WHERE, которую, как он думал, включил.

Результатом было не удаление столбца. Это был оператор DELETE, который очистил 40 000 строк из таблицы `menu_items` — данные меню примерно 200 ресторанов, исчезли.

Алерт сработал в течение 30 секунд. Сбои заказов подскочили. Сервис меню начал возвращать пустые результаты для 200 ресторанов.

«Там должна была быть клауза WHERE», — сказал Сэм, уставившись на консоль.

Традиционный путь восстановления: восстановить из самого недавнего автоматизированного снимка резервной копии. Автоматизированные резервные копии запускаются раз в 24 часа, а полное восстановление-и-замена заняло бы 20-40 минут — в течение которых *все* рестораны были бы в темноте, а не только затронутые 200 — и каждый заказ, размещённый с момента резервной копии, был бы потерян.

Лео этого не сделал. Как и стандартный RDS, Aurora хранит непрерывные резервные копии для **восстановления на момент времени (point-in-time recovery, PITR)** — вы можете восстановить кластер на любую секунду в окне хранения резервных копий, а не только на последний ночной снимок. И, что критично, восстановление создаёт *новый* кластер; продакшен остаётся работать, пока вы восстанавливаетесь.

```bash
aws rds restore-db-cluster-to-point-in-time \
  --db-cluster-identifier nimbus-aurora-recovery \
  --source-db-cluster-identifier nimbus-aurora-cluster \
  --restore-to-time 2024-06-14T15:42:00Z
```

Временная метка: 15:42:00Z — за четыре минуты до того, как Сэм запустил скрипт миграции. Пока кластер восстановления раскручивался, остаток продакшена продолжал обслуживать незатронутые рестораны. Как только он стал доступен, Лео выгрузил строки `menu_items` для 200 затронутых ресторанов из кластера восстановления и вставил их обратно в продакшен. Общее время от алерта до полностью восстановленных меню: чуть меньше 40 минут — и поскольку он восстановил строки хирургически, а не заменял всю базу данных, ни один заказ, размещённый после 15:42, не был потерян. Кластер восстановления был удалён после; он выполнил своё назначение.

«Что мы потеряли?» — спросила Майя.

Шесть заказов, размещённых против ненадолго опустевших меню, провалились на оформлении — все они были в очереди SQS и могли быть воспроизведены. Никакие данные клиентов не были потеряны навсегда.

«И вот тут появляется **быстрое клонирование базы данных**», — сказал Лео, собирая команду после. Aurora может создать **клон** кластера за минуты, независимо от размера базы данных, используя копирование-при-записи (copy-on-write): клон делит слой хранилища оригинала, и только новые или изменённые страницы потребляют дополнительное место. Клон текущей продакшен-базы данных дёшев, быстр и полностью изолирован — записи в клон никогда не касаются продакшена.

«Что означает», — сказала Прия, глядя на Сэма, — «что скрипт миграции тестируется против клона продакшен-данных прежде, чем он когда-либо запустится в продакшене. Это новое правило».

Сэм кивнул. Он уже написал это на стикере.

Ещё один инструмент принадлежит этой картине. У Aurora MySQL — не Aurora PostgreSQL — есть **Aurora Backtrack**: функция, которая перематывает кластер *на месте* на конкретный момент времени, вообще без восстановления в новый кластер. Если бы кластер Nimbus был Aurora MySQL, Лео мог бы перемотать его на 15:42 менее чем за три минуты — хотя перемотка всего кластера также откатила бы горстку легитимных заказов, записанных после удаления, которые хирургический подход PITR сохранил.

«А что, если кто-то попытается взломать, используя Backtrack — или восстановление на момент времени?» — спросила Прия. «Может ли атакующий перемотать журналы аудита или данные комплаенса?»

Backtrack требует API-разрешения `rds:BacktrackDBCluster`, а восстановления требуют `rds:RestoreDBClusterToPointInTime` — отдельные IAM-действия от обычных операций базы данных. У стандартных ролей приложений нет этих разрешений. Только операционная команда, с явной IAM-политикой, позволяющей это, могла их использовать. Она добавила это в чек-лист обзора IAM-разрешений.

Важные оговорки: Aurora Backtrack доступен только для кластеров, совместимых с Aurora MySQL, не PostgreSQL. Окно Backtrack настраивается при создании кластера (от 1 до 72 часов, тарификация за час окна backtrack). И Backtrack влияет на весь кластер — вы не можете сделать Backtrack одной таблицы или одного набора строк. Для хирургического восстановления на уровне строк — на любом движке — подход PITR-во-временный-кластер, который использовал Лео, и есть инструмент.

**Aurora Global Database: мультирегиональные чтения**

**Aurora Global Database** расширяет Aurora на несколько регионов AWS:

- **Один основной регион** обрабатывает все записи
- **До пяти вторичных регионов** обслуживают чтения с задержкой репликации обычно <1 секунды
- Вторичные регионы можно повысить до основного менее чем за 1 минуту (для сценариев DR)

Для глобальной экспансии Nimbus Aurora Global Database позволила бы партнёру-ресторану в Лондоне запрашивать своё локальное меню из реплики для чтения в ЕС, в то время как все заказы (записи) по-прежнему идут через основную в США.

**RDS против Aurora: когда выбирать каждый**

| Фактор             | RDS (PostgreSQL/MySQL)            | Aurora                                                          |
|--------------------|-----------------------------------|----------------------------------------------------------------|
| Стоимость          | Ниже для небольших нагрузок       | Выше базовая, но лучше масштабируется                          |
| Совместимость      | Полная                            | Совместима с MySQL/PostgreSQL (с небольшими отличиями)          |
| Макс. реплик       | 15 (каждая — полная копия данных) | 15 (общий том хранилища)                                       |
| Задержка реплики   | Может быть секунды                | Обычно <100 мс                                                 |
| Хранилище          | Фиксированное выделение           | Авто-масштабирование до 128 ТиБ (256 ТиБ в недавних версиях)   |
| Время переключения | 60-120 секунд                     | <30 секунд                                                     |
| Опция Serverless   | Ограниченная                      | Aurora Serverless v2                                           |
| Лучше для          | Стабильные, предсказуемые нагрузки | Переменный трафик, высокий объём чтения, нужда в быстром переключении |

**За пределами реляционного: семейство специализированных баз данных**

В главе 9 были представлены DocumentDB (документы, совместимые с MongoDB), Neptune (графовые связи) и Keyspaces (широкие столбцы, совместимые с Cassandra), а в главе 10 — MemoryDB (долговечная основная база данных, совместимая с Redis). Ещё два имени дополняют семейство — вам не нужна глубина по ним, лишь способность распознавать, какая форма данных указывает на какой движок, потому что они постоянно появляются как варианты ответов:

- **Amazon Timestream**: данные **временных рядов (time-series)** — показания датчиков, метрики, телеметрия. Признак в экзамене: «измерения IoT во времени». (В реальном мире текущее предложение — Timestream for InfluxDB; оригинальный вариант «LiveAnalytics» закрылся для новых клиентов в 2025 году.)
- **Amazon QLDB**: вы всё ещё можете встретить его в старых вопросах как «неизменяемый, криптографически верифицируемый реестр (ledger)». AWS прекратил QLDB в 2025 году (рекомендуя вместо него Aurora PostgreSQL) — относитесь к нему как к устаревшему отвлекающему варианту, а не строительному блоку.

Правило, которое стоит написать на доске: **реляционные строки → RDS/Aurora; ключ-значение в масштабе → DynamoDB; документы → DocumentDB; связи → Neptune; время → Timestream; Cassandra → Keyspaces; долговечный Redis → MemoryDB.** Сопоставьте форму, и вопрос ответит сам на себя.

## Сильные стороны и ограничения

**Сильные стороны Aurora**:

- Значительно более быстрое переключение, чем у стандартного RDS
- До 15 реплик для чтения с минимальной задержкой
- Авто-масштабирование хранилища
- Serverless v2 для переменных нагрузок
- Global Database для мультирегионального развёртывания

**Ограничения Aurora**:

- Более высокая стоимость для небольших, стабильных нагрузок
- Цена I/O может быть значительной для нагрузок с интенсивной записью (используйте для этого I/O-Optimized)
- Небольшие отличия совместимости с MySQL/PostgreSQL могут требовать изменений кода
- Возобновление Serverless v2 после авто-приостановки (~15 секунд) и быстрое масштабирование вверх могут вызывать всплески задержки

## Итоги

Работа с жизненным циклом S3 в главе 23 снизила затраты, переместив данные на правильный уровень хранилища. Aurora делает эквивалент для вычислений: вместо выделения под пиковую нагрузку и оплаты её всё время, Serverless v2 масштабируется под спрос.

- **Реплики для чтения** распределяют трафик чтения от основной. Асинхронная репликация — небольшая задержка приемлема для большинства чтений. Направляйте чтения, требующие консистентности записи (чтения сразу после записи, чтения админ-интерфейса), на основную, а не на реплику.
- **Aurora** переосмысливает слой хранилища: распределённый, общий для реплик, авто-масштабируемый.
- Aurora предлагает: 15 реплик для чтения, задержку реплики <100 мс, переключение <30 с, авто-масштабируемое хранилище до 128 ТиБ (256 ТиБ в недавних версиях).
- **Performance Insights**: определите конкретные SQL-запросы, вызывающие нагрузку базы данных, прежде чем решать, как масштабировать. Отсутствующий индекс может устранить необходимость в более крупном экземпляре.
- **Метрики базы данных CloudWatch**: DatabaseConnections (близость к насыщению означает сломанный пулинг соединений приложения), CPUUtilization (устойчиво высокий CPU означает дорогие запросы), ReadLatency (деградация со временем часто означает растущую таблицу с отсутствующим индексом).
- **Aurora Serverless v2**: авто-масштабирует вычисления шагами по 0,5 ACU. Тарифицируется за ACU-час. Значительно дешевле выделенных экземпляров для нагрузок с высокой переменчивостью между пиком и не-пиком.
- **Восстановление на момент времени (PITR)**: восстановите кластер Aurora на любую секунду в окне хранения резервных копий — в *новый* кластер, так что продакшен остаётся работать, пока вы хирургически копируете потерянные строки обратно.
- **Быстрое клонирование базы данных**: клон кластера по принципу копирования-при-записи за минуты независимо от размера. Дёшев, изолирован — используйте его для тестирования миграций против продакшен-данных прежде, чем они запустятся в продакшене.
- **Aurora Backtrack** (только совместимый с MySQL — не PostgreSQL): перемотайте кластер на месте на момент времени без восстановления из резервной копии. Доступен для окон до 72 часов. Требует IAM-разрешения `rds:BacktrackDBCluster` — ограничьте для операционной команды.
- **Aurora Global Database**: основная в одном регионе, реплики для чтения в до пяти регионах.
- **Повышение реплики для чтения**: кросс-региональные реплики для чтения можно повысить до автономных основных для регионального DR. Балансируйте выгоду DR против стоимости запуска второго полного экземпляра.
- Выбирайте RDS для меньших, стабильных, предсказуемых нагрузок. Выбирайте Aurora, когда вам нужен масштаб, быстрое переключение или обработка переменного трафика.

## Советы по экзамену

*Домен SAA-C03: Проектирование высокопроизводительных архитектур (Домен 3, Задача 3.3)*

- **Реплика Aurora против реплики для чтения RDS**: реплики Aurora делят хранилище (почти нулевая задержка, переключение <30 с). Реплики для чтения RDS реплицируют данные (возможна задержка, минуты на переключение).
- **Aurora Serverless v2**: «авто-масштабировать мощность базы данных», «непредсказуемый или скачкообразный трафик базы данных» → Aurora Serverless v2. Осторожно: исторически только Serverless **v1** масштабировался до нуля; минимум v2 был 0,5 ACU до конца 2024 года, когда v2 получил авто-приостановку до 0 ACU. Старые вопросы экзамена могут всё ещё предполагать, что v2 не может масштабироваться до нуля.
- **Aurora Global Database**: «мультирегиональная база данных», «читать из ЕС с низкой задержкой от основной в США», «RTO < 1 минуты для регионального переключения» → Aurora Global Database.
- **Тайминг переключения**: Aurora < 30 секунд. RDS Multi-AZ 60-120 секунд. Знайте оба.
- **Специализированные базы данных по форме данных**: «социальный граф / рекомендации / кольца мошенничества» → Neptune. «MongoDB» → DocumentDB. «Cassandra» → Keyspaces. «временные ряды / телеметрия IoT» → Timestream. «*основная* база данных, совместимая с Redis (долговечная)» → MemoryDB (против ElastiCache = кеш). «Неизменяемый криптографический реестр» → QLDB в старых вопросах (прекращён в 2025 году).
- **Aurora I/O-Optimized**: более высокая стоимость хранилища и экземпляра, без платы за I/O. Используйте, когда стоимость I/O доминирует (интенсивная запись). Стандартная Aurora: ниже стоимость хранилища, плата за I/O. Используйте для интенсивного чтения.
- **Aurora Backtrack**: перемотайте базу данных на месте на конкретный момент времени без восстановления из снимка резервной копии. Доступен только для Aurora, совместимой с MySQL — для Aurora PostgreSQL ответ — восстановление на момент времени (в новый кластер) или быстрый клон. Признак в экзамене: «случайно удалённые данные, нужно быстро восстановить без восстановления полной резервной копии» + MySQL → Backtrack.
- **Быстрое клонирование базы данных Aurora**: клон по принципу копирования-при-записи за минуты, независимо от размера базы данных. Признак в экзамене: «протестировать против копии продакшен-данных быстро и дёшево» → клон, а не восстановление из снимка.

**Упражнение 1 — Запоминание**

Объясните разницу между репликами Aurora и стандартными репликами для чтения RDS. Почему задержка репликации Aurora обычно ниже?

*(Подсказка: ключевое отличие — общее хранилище против репликации данных. Подумайте о том, что должна делать каждая реплика, когда приходит запись.)*

**Упражнение 2 — Сценарий SAA-C03**

*Сценарий*: База данных MySQL платформы социальных сетей испытывает высокую задержку чтения из-за растущего трафика. Приложение интенсивно на чтение (95% чтений, 5% записей). Команде нужна консистентная задержка чтения, даже во время всплесков трафика. Им нужно автоматическое переключение с минимальным простоем (целевой RTO < 30 секунд). Объём данных растёт непредсказуемо.

Какое решение базы данных НАИЛУЧШИМ образом отвечает этим требованиям?

A) RDS MySQL Multi-AZ с пятью репликами для чтения  
B) Aurora MySQL с репликами Aurora и Aurora Serverless v2  
C) RDS MySQL с более крупным типом экземпляра (вертикальное масштабирование)  
D) DynamoDB с DynamoDB DAX для кеширования чтения

**Подсказка 1**: «RTO < 30 секунд» — какой сервис этого достигает? Проверьте тайминг переключения для каждого варианта.

**Подсказка 2**: «Консистентная задержка чтения во время всплесков» — у реплик какого сервиса почти нулевая задержка против потенциальных секунд задержки?

**Подсказка 3**: «Непредсказуемо растущий объём данных» — какой сервис авто-масштабирует хранилище?

**Ответ**: B

**Объяснение**: Aurora MySQL с репликами Aurora обеспечивает почти нулевую задержку репликации (миллисекунды, а не секунды) для консистентной производительности чтения под нагрузкой. Aurora Serverless v2 авто-масштабирует вычисления во время всплесков трафика без избыточного выделения. Хранилище Aurora авто-масштабируется по мере роста данных. Переключение Aurora (повышение реплики) завершается менее чем за 30 секунд — отвечая требованию RTO.

**Почему не A?** Переключение RDS Multi-AZ занимает 60-120 секунд — не отвечает RTO < 30 секунд. Задержка реплики для чтения стандартного RDS может достигать секунд под нагрузкой — «консистентную» задержку чтения сложнее гарантировать.

**Почему не C?** Вертикальное масштабирование (более крупный экземпляр) увеличивает мощность, но не распределяет нагрузку чтения. База данных остаётся единой точкой отказа для чтений.

**Почему не D?** DynamoDB — это NoSQL — миграция с MySQL на DynamoDB требует переархитектуры модели данных и запросов приложения, что выходит далеко за рамки этой задачи улучшения производительности.
