# Глава 26: Осмыслить всё

Данные — это сырьё: временны́е метки, клики, события, числа. Информация — это то, что получается, когда данные организованы, обработаны и снабжены контекстом. Пропасть между ними — это то, о чём эта глава.

И в растущих системах эта пропасть становится дорогой очень быстро.

Nimbus генерировал огромные объёмы данных. Каждый заказ: зафиксирован. Каждый просмотр меню: залогирован. Каждое обновление ресторана: захвачено. Каждое взаимодействие с клиентом: отслежено.

У Tom был вопрос.

— Какое наше самое загруженное время заказов в пятницу?

Leo посмотрел на него. — Этого нет на нашей панели.

— Можем добавить?

— Данные в DynamoDB. И в логах CloudWatch. И в S3 из задания ночного экспорта аналитики. — Leo сделал паузу. — В трёх разных местах, в трёх разных форматах.

Maya добавила: — И экспорт аналитики запускается только раз в ночь. Если вы хотите данные за пятницу, придётся ждать до субботнего утра.

Tom посмотрел на экран. — Значит, данные у нас есть. Мы просто не можем ими пользоваться.

Это предложение описывает половину современной аналитики.

Это проблема инженерии данных: у вас есть данные, но они не в той форме, которую можно анализировать в нужный момент.

**Три разные проблемы**

Проблема с данными у Nimbus имела три измерения:

**Потоковая обработка в реальном времени**: прямо сейчас размещаются заказы. Вы хотите видеть панель с объёмом заказов в реальном времени — сколько в минуту, по регионам, по ресторанам. Данные нужно обрабатывать по мере поступления.

**Преобразование данных**: данные в S3 из различных систем, в разных форматах (JSON, CSV, Parquet). Перед анализом их нужно нормализовать — единая схема, единый формат, очищенные, объединённые со справочными данными.

**Специализированный анализ**: как только данные организованы, вы хотите выполнять SQL-запросы к ним без предварительной загрузки в базу данных. «Дайте мне топ-10 ресторанов по выручке за последние 30 дней». Без загрузки данных в базу данных.

Каждое из них — отдельная проблема. AWS имеет специализированный сервис для каждой:

- **Amazon Kinesis**: потоковые данные в реальном времени
- **AWS Glue**: преобразование и каталогизация данных
- **Amazon Athena**: бессерверные SQL-запросы к S3

**Amazon Kinesis: тикер реального времени**

**Amazon Kinesis Data Streams** — сервис потоковой передачи данных в реальном времени. Производители отправляют записи данных в поток. Несколько потребителей могут читать из потока одновременно, каждый в своём темпе.

Представьте ленту тикера: котировки печатаются непрерывно, все могут читать ленту, и лента не замедляется ни для одного отдельного читателя.

Для Nimbus при размещении заказа приложение публикует событие в поток Kinesis: `{ "orderId": "ORD-7741", "restaurantId": "47", "total": 3200, "timestamp": "...", "region": "us-west-2" }`.

Потребители этого потока:

- Панель в реальном времени (читает события по мере поступления, обновляет метрики)
- Lambda для обнаружения мошенничества (ищет необычные паттерны заказов)
- Поток в S3 для постоянного хранения

**Концепции Kinesis Data Streams**:

- **Шард (shard)**: базовая единица мощности. Один шард обрабатывает 1 МБ/с записи, 2 МБ/с чтения.
- **Период хранения**: данные остаются в потоке 24 часа (по умолчанию) до 7 дней.
- **Порядковый номер**: каждая запись имеет порядковый номер. Потребители отслеживают свою позицию в потоке.

**Amazon Data Firehose** (ранее **Kinesis Data Firehose**): управляемый сервис доставки между потоковыми производителями и назначениями, такими как S3, Redshift и OpenSearch. Автоматически буферизует, сжимает, преобразует и доставляет данные.

Для Nimbus: Kinesis Data Streams → Amazon Data Firehose → S3 (формат Parquet, сжатый, разбитый по дате).

**AWS Glue: переводчик**

Данные в S3 — сырые. Перед эффективным анализом нужно:

- Обнаружить, что там есть и какая схема (какие столбцы, какие типы)
- Преобразовать в единый формат
- Объединить разные наборы данных
- Обработать плохие записи, изменения схемы, отсутствующие значения

**AWS Glue** — полностью управляемый сервис ETL (Extract, Transform, Load). Он имеет два основных компонента:

**Glue Data Catalog**: хранилище метаданных, описывающее ваши данные в S3 — какие таблицы существуют, какие у них столбцы, где находятся файлы данных. Это как карточный каталог для вашего Data Lake.

**Glue Crawlers**: автоматизированные агенты, сканирующие S3, определяющие схему и заполняющие Data Catalog. Запустите crawler на своём S3-бакете и через 10 минут у вас будет каталог всех ваших таблиц.

**Glue Jobs**: бессерверные задания Spark/Python, выполняющие фактическое преобразование. Вы пишете логику преобразования (или используете визуальный инструмент ETL Glue), и Glue запускает её на управляемой инфраструктуре.

Для Nimbus:

1. Glue Crawler сканирует данные о заказах в S3 → создаёт определение таблицы в Glue Data Catalog
2. Glue Job преобразует необработанные JSON-события заказов в чистый, разбитый на партиции формат Parquet
3. Преобразованные данные записываются обратно в S3 в оптимизированном для запросов виде

**Amazon Athena: библиотекарь**

**Amazon Athena** — бессерверный интерактивный сервис запросов, выполняющий SQL-запросы непосредственно к данным в S3. Нет базы данных для выделения, нет данных для загрузки. Вы определяете таблицу (или используете Glue Data Catalog), пишете SQL и Athena выполняет запрос к файлам в S3.

```sql
SELECT 
    restaurant_id,
    COUNT(*) as order_count,
    SUM(total) as revenue
FROM orders
WHERE year='2024' AND month='01'
GROUP BY restaurant_id
ORDER BY revenue DESC
LIMIT 10;
```

Ценообразование Athena основано на объёме данных, которые сканирует запрос. Во многих регионах стандартные SQL-запросы начинаются от $5 за сканированный терабайт. Использование формата Parquet (столбчатый) с обрезкой партиций (`WHERE year='2024' AND month='01'`) означает, что Athena сканирует только нужные файлы, что резко снижает стоимость.

— Мы можем запустить этот запрос для 30 дней данных, — сказал Leo, — и это может стоить удивительно мало, если мы хорошо храним данные.

— Для любого произвольного вопроса, который мы можем придумать? — спросил Tom.

— Любого вопроса, который мы можем выразить в SQL, для любых данных, которые мы хранили в S3.

У Tom был вид человека, пересчитывающего ценность всех данных, которые они выбрасывали.

**Архитектура Data Lake**

Эти три сервиса объединяются в то, что называется **архитектурой Data Lake** — централизованное S3-хранилище для всех ваших данных с инструментами для их обработки и запросов:

```
Приложения (заказы, меню, события)
    |
    | События в реальном времени
    ↓
Kinesis Data Streams ──→ Amazon Data Firehose ──→ S3 (сырые)
                                                   |
                                                   | Glue Crawler обнаруживает схему
                                                   ↓
                                              Glue Data Catalog
                                                   |
                                                   | Glue Jobs преобразуют
                                                   ↓
                                              S3 (чистые, Parquet, с партициями)
                                                   |
                                                   | SQL-запросы
                                                   ↓
                                              Amazon Athena
                                                   |
                                                   ↓
                                          Инструменты бизнес-аналитики
                                       (QuickSight, Tableau и т.д.)
```

Сырые данные всегда сохраняются (в исходном S3-бакете). Преобразованные данные доступны для запросов через Athena. Новые вопросы всегда можно ответить, запустив новые задания Glue на сырых данных.

**Amazon Redshift: когда Athena недостаточно**

Для некоторых случаев использования Athena слишком медленная или дорогая:

- Очень сложные запросы со множеством объединений
- Панели, запускающие один и тот же запрос тысячи раз в день
- Машинное обучение на структурированных данных
- Требование времени ответа менее секунды для инструментов BI

**Amazon Redshift** — полностью управляемое хранилище данных: столбчатая аналитическая база данных, разработанная для больших, повторяющихся аналитических нагрузок. В отличие от Athena, которая запрашивает данные там, где они хранятся в S3, Redshift загружает данные в оптимизированное хранилище и использует оптимизацию запросов, стратегии сортировки и распределения для ускорения сложной аналитики.

Redshift значительно быстрее для сложных аналитических запросов за счёт стоимости (выделенные мощности) и требования загрузить данные перед запросами.

**Redshift Serverless** устраняет необходимость в планировании мощностей — вы выполняете запрос, Redshift масштабируется. Стоимость за запрос.

Для Nimbus в их текущем масштабе: Athena достаточно. При пятикратном увеличении объёма данных и инструментах BI, запрашивающих одни и те же панели сотни раз в день, Redshift станет экономически обоснованным.

## Преимущества и ограничения

**Kinesis Data Streams**: используйте Kinesis, когда данные поступают непрерывно и порядок важен — потоки кликов, финансовые транзакции, телеметрия IoT. Kinesis сохраняет порядок записей внутри шарда и позволяет воспроизводить данные в течение настроенного окна хранения, что принципиально отличает его от SQS. Компромисс — операционная сложность: в режиме с выделенными ресурсами вы управляете мощностью шардов и поведением потребителей. Для простых очередей задач, где порядок не важен и воспроизведение не нужно, SQS — более простой выбор.

**AWS Glue**: Glue устраняет инфраструктуру традиционного ETL-кластера. Вы пишете логику преобразования; AWS управляет средой Spark. Это ценно, когда преобразования сложны или объёмы данных велики. Ограничение — стоимость и холодный старт: задания Glue имеют задержку запуска в несколько минут, что делает их непригодными для преобразований, близких к реальному времени. Для простого преобразования форматов файлов (CSV в Parquet) накладные расходы Glue могут не стоить того по сравнению с Lambda-функцией или лёгким скриптом.

**Amazon Athena**: Athena позволяет запрашивать данные S3 стандартным SQL без инфраструктуры для управления. Критическое ограничение — стоимость: Athena взимает плату за сканированный терабайт данных. Запрос к таблице на 10 ТБ, сканирующий всё, стоит значительно больше, чем тот же запрос к таблице в формате Parquet с партициями, сканирующий 200 ГБ. Всегда используйте столбчатые форматы (Parquet или ORC) и разбивайте данные на партиции перед использованием Athena в production. Без этих оптимизаций счета Athena могут удивить.

## Резюме

- **Amazon Kinesis**: потоковая передача данных в реальном времени. Производители пишут записи; потребители читают в своём темпе. Amazon Data Firehose затем может доставлять потоковые данные в S3, Redshift и другие назначения с меньшими операционными затратами.
- **AWS Glue**: ETL и каталогизация данных. Crawlers обнаруживают схемы; Jobs преобразуют данные; Data Catalog делает данные доступными для Athena и других инструментов.
- **Amazon Athena**: бессерверный SQL к S3. Запрашивайте любые данные в S3 стандартным SQL. Ценообразование за ТБ сканирования — используйте Parquet и партиционирование для минимизации стоимости.
- **Amazon Redshift**: управляемое хранилище данных для высокопроизводительной аналитики. Загрузите данные, оптимизируйте для повторяющихся аналитических запросов и быстро запрашивайте в масштабе хранилища.
- **Паттерн Data Lake**: сырые данные в S3 → Glue преобразует → Athena запрашивает → инструменты BI визуализируют.

## Советы к экзамену

*SAA-C03, область: проектирование высокопроизводительных архитектур (область 3, задача 3.5)*

- **Kinesis и SQS**: Kinesis = упорядоченная потоковая передача в реальном времени, несколько потребителей, воспроизведение в течение окна хранения. SQS = очередь задач, каждое сообщение обрабатывается один раз. «Несколько потребителей читают один и тот же поток одновременно» → Kinesis. «Один воркер на сообщение» → SQS.
- **Признаки Athena**: «бессерверный SQL к S3», «анализировать данные S3 без загрузки в базу данных», «оплата за запрос» → Athena.
- **Оптимизация стоимости Athena**: столбчатый формат (Parquet или ORC) + партиционирование резко снижает сканируемые данные и стоимость. Экзамен может спрашивать, как снизить затраты Athena.
- **Glue Crawler**: «автоматически обнаружить схему данных S3» → Glue Crawler.
- **Amazon Data Firehose**: «автоматически загружать потоковые данные в S3/Redshift/OpenSearch без управления потребителями» → Amazon Data Firehose. Старые материалы могут называть его Kinesis Data Firehose.
- **Redshift и Athena**: Redshift для высокочастотных, сложных запросов к фиксированному набору данных (панели BI). Athena для специализированных запросов к данным S3, которые часто меняются.
- **EMR (Elastic MapReduce)**: управляемые кластеры Hadoop/Spark. Экзамен использует это при упоминании «существующих нагрузок Hadoop/Spark» или «пользовательских фреймворков обработки данных». Glue — управляемая альтернатива для большинства случаев использования.

**Упражнение 2 — Подготовка к экзамену**

*Сценарий*: Компания по совместным поездкам хочет анализировать данные о поездках. Ежедневно совершается 1 миллион поездок. Записи о поездках хранятся в S3 в формате JSON (примерно 2 КБ каждая). Команда аналитики хочет выполнять специализированные SQL-запросы вроде «средняя продолжительность поездки по городу за прошлую неделю». Запросы должны завершаться менее чем за 2 минуты. Затраты на хранение должны быть минимизированы. Команда будет выполнять 20–30 запросов в неделю.

Какая архитектура наилучшим образом отвечает этим требованиям?

A) Ежедневно загружать данные о поездках в RDS PostgreSQL; запрашивать стандартным SQL  
B) Использовать AWS Glue для конвертации JSON в формат Parquet, разбитый по дате и городу; запрашивать с помощью Amazon Athena  
C) Использовать Amazon Data Firehose для доставки данных о поездках в Amazon Redshift; запрашивать с помощью Redshift  
D) Загрузить данные о поездках в DynamoDB и использовать PartiQL для SQL-запросов

**Подсказка 1**: 20–30 запросов в неделю — низкая частота. Какой сервис наиболее экономичен для нечастых запросов?

**Подсказка 2**: Формат Parquet + партиционирование резко снижает объём данных, сканируемых Athena, — и следовательно, стоимость.

**Подсказка 3**: 1 миллион поездок × 2 КБ = ~2 ГБ в день. За неделю ~14 ГБ. По $5/ТБ для Athena, даже без оптимизации, это доступно.

**Ответ**: B

**Пояснение**: Glue конвертирует JSON в Parquet (столбчатый формат резко снижает сканируемые данные), разбитый по дате и городу (обрезка партиций означает, что запросы «за прошлую неделю» сканируют только партиции за 7 дней). Athena запрашивает S3 напрямую стандартным SQL. Для 20–30 запросов в неделю Athena с оплатой за запрос чрезвычайно экономична по сравнению с постоянно работающим Redshift.

**Почему не A?** Ежедневная загрузка 2 ГБ данных в RDS, затем запросы, требуют постоянно работающего инстанса базы данных. Для 20–30 запросов в неделю это чрезмерно инженерировано и дорого.

**Почему не C?** Redshift экономичен для высокочастотных запросов (сотни в день к одному набору данных). Для 20–30 запросов в неделю постоянно работающий кластер Redshift стоит значительно больше, чем ценообразование Athena за запрос.

**Почему не D?** DynamoDB — хранилище ключ-значение/документов, оптимизированное для доступа по ключу, а не для специализированных аналитических запросов. PartiQL в DynamoDB не поддерживает агрегации GROUP BY, описанные в задаче.
