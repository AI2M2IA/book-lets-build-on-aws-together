**Три разные проблемы**

У проблемы данных Nimbus было три измерения:

**Стриминг в реальном времени**: заказы размещаются прямо сейчас. Вы хотите видеть живой дашборд скорости заказов — сколько в минуту, по региону, по ресторану. Данные нужно обрабатывать по мере поступления.

**Преобразование данных**: данные в S3 из различных систем, в разных форматах (JSON, CSV, Parquet). Прежде чем вы сможете их анализировать, нужно их нормализовать — одна схема, один формат, очищенные, объединённые со справочными данными.

**Спонтанный анализ (ad-hoc)**: как только данные организованы, вы хотите выполнять SQL-запросы по ним, не загружая их сначала в базу данных. «Дай мне топ-10 ресторанов по выручке за последние 30 дней». Без загрузки данных в базу данных.

Каждая из этих — отдельная проблема. У AWS есть специальный сервис для каждой.

**Поток в реальном времени: телетайпная лента для данных**

Представьте телетайпную машину — ту, что печатала биржевые котировки на непрерывном рулоне бумаги. Цены печатались по мере их изменения. Каждый, кто хотел текущую цену, мог прочитать ленту. Никому не приходилось ждать кого-либо ещё; лента продолжала печатать независимо от того, сколько людей её читали.

Это модель для стриминга данных в реальном времени. Производители отправляют данные по мере их возникновения. Несколько потребителей могут читать поток одновременно, каждый в своём темпе, каждый получая полную картину.

**Amazon Kinesis Data Streams** — это та машина для Nimbus. Когда заказ размещается, приложение публикует событие в поток Kinesis: `{ "orderId": "ORD-7741", "restaurantId": "47", "total": 3200, "timestamp": "...", "region": "us-west-2" }`.

Потребители этого потока:

- Дашборд реального времени (читает события по мере поступления, обновляет метрики)
- Lambda обнаружения мошенничества (ищет необычные паттерны заказов)
- Поток в S3 для постоянного хранения

**Концепции Kinesis Data Streams**:

- **Шард (shard)**: базовая единица мощности. Один шард обрабатывает 1 МБ/с запись, 2 МБ/с чтение.
- **Период хранения (retention period)**: данные остаются в потоке 24 часа (по умолчанию), расширяется до **365 дней** (1 год) с расширенным хранением данных (Extended Data Retention).
- **Порядковый номер (sequence number)**: у каждой записи есть порядковый номер. Потребители отслеживают свою позицию в потоке.

**Amazon Data Firehose** (ранее **Kinesis Data Firehose**): управляемый сервис доставки между стриминговыми производителями и назначениями вроде S3, Redshift и OpenSearch. Он буферизует, сжимает, преобразует и доставляет данные автоматически.

Для Nimbus: Kinesis Data Streams → Amazon Data Firehose → S3 (формат Parquet, сжатый, партиционированный по дате).

«Я уже развернул это — ой». Лео установил количество шардов в один, не рассчитав сначала пропускную способность записи. При объёме заказов Nimbus одного шарда было достаточно. Он подтвердил это прежде, чем кто-либо заметил, что он угадал.

**Переводчик: осмысление сырых данных**

Данные в S3 сырые. Прежде чем вы сможете эффективно их анализировать, вам нужно обнаружить, что там есть, преобразовать в консистентный формат, объединить разные наборы данных и обработать плохие записи и пропущенные значения.

Это работа для специального слоя перевода.

**AWS Glue** — это полностью управляемый сервис ETL (Extract, Transform, Load — извлечение, преобразование, загрузка). У него два основных компонента:

**Glue Data Catalog**: хранилище метаданных, описывающее ваши данные в S3 — какие таблицы существуют, какие у них столбцы, где находятся файлы данных. Это как карточный каталог для вашего озера данных.

**Glue Crawlers**: автоматизированные агенты, которые сканируют S3, выводят схему и заполняют Data Catalog. Запустите краулер на своём бакете S3, и через 10 минут у вас есть каталог всех ваших таблиц.

**Glue Jobs**: бессерверные задания Spark/Python, выполняющие фактическое преобразование. Вы пишете логику преобразования (или используете визуальный ETL-инструмент Glue), и Glue запускает её на управляемой инфраструктуре.

Для Nimbus:

1. Glue Crawler сканирует данные заказов в S3 → создаёт определение таблицы в Glue Data Catalog
2. Glue Job преобразует сырые JSON-события заказов в чистый, партиционированный формат Parquet
3. Преобразованные данные записываются обратно в S3 в оптимизированной для запросов раскладке

**Когда ETL ломается: проблема эволюции схемы**

Конвейер Glue работал чисто первые три недели. Затем партнёр-ресторан #412 добавил новое поле в свой экспорт меню: `allergen_tags`. Поле было массивом строк — `["gluten", "dairy", "nuts"]` — и оно появилось в ночном экспорте данных ресторана.

Схема задания Glue была строгой. Оно было написано в ожидании конкретных полей в JSON заказа. Когда оно встретило `allergen_tags` — поле, которого не было в схеме — задание Glue провалилось.

Шесть часов данных о заказах от 47 ресторанов (все использующие тот же формат экспорта меню, что и партнёр #412) накопились в S3 без обработки. Ночной запуск Glue, который должен был сделать вчерашние заказы запрашиваемыми к утру, вместо этого остановился в 2:47 ночи и записал запись об ошибке в CloudWatch.

Том нашёл это, когда попытался выполнить запрос Athena в 9 утра и получил `0 rows returned` за предыдущие 12 часов.

«ETL сломался, потому что изменились исходные данные?» — спросила Майя, когда Лео объяснил, что произошло.

«ETL сломался, потому что ETL не знал, как обработать изменение схемы», — сказал Лео. «Мы написали строгое задание, которое ожидало ровно эти поля. Когда появилось новое поле, оно запаниковало».

«А что, если кто-то попытается взломать через изменение схемы?» — спросила Прия. «Злонамеренный партнёр-ресторан, намеренно отправляющий неожиданные поля, чтобы обрушить конвейер?»

Вопрос стоил рассмотрения. ETL-конвейер, который обрушивается на неожиданный ввод, — это вектор отказа в обслуживании: отправьте необычный формат данных, обрушьте конвейер, и этот ресторан (и все другие, делящие формат) перестают обрабатываться.

Исправление имело две части:

**Эволюция схемы Glue**: динамический фрейм Glue поддерживает эволюцию схемы — поля, которых нет в ожидаемой схеме, пропускаются дальше, а не вызывают сбои. Включите это, используя DynamicFrames вместо DataFrames в скрипте задания, с `mergeSchema`, установленным в дополнительных опциях. Новые поля добавляются в схему автоматически при следующем запуске краулера.

```python
# До (строго, ломается на новых полях)
datasource = glueContext.create_dynamic_frame.from_catalog(
    database="nimbus_db",
    table_name="orders"
)

# После (эволюция схемы включена)
datasource = glueContext.create_dynamic_frame.from_catalog(
    database="nimbus_db",
    table_name="orders",
    additional_options={"mergeSchema": "true"}
)
```

**Оповещение о задании Glue**: сбой конвейера был тихим около шести часов, прежде чем Том заметил. Аларм CloudWatch на состоянии запуска задания Glue (`FAILED`) оповестил бы дежурного инженера в течение 5 минут. Стоимость аларма: десять центов в месяц — фактически бесплатно (сама метрика ничего не стоит, и первые десять алармов попадают под бесплатный уровень).

«Шесть часов данных лежали необработанными в S3», — сказал Лео, после ручного повторного запуска задания Glue, чтобы наверстать. «Ничего не было потеряно — но аналитика отставала настолько. Если бы у нас был аларм, задержка была бы 30 минут».

Более широкий урок: ETL-конвейеры, обрабатывающие внешние данные, должны изящно справляться с изменениями схемы. Внешние партнёры — рестораны, платёжные провайдеры, службы доставки — будут менять свои форматы данных. Конвейер не должен быть хрупким к этим изменениям.

**Слой запросов: SQL прямо на S3**

Теперь данные были в S3, в формате Parquet, партиционированные по дате. Финальный элемент: способ задавать вопросы по ним, не загружая их сначала в базу данных.

**Amazon Athena** — это бессерверный, интерактивный сервис запросов, выполняющий SQL-запросы прямо на данных S3. Никакой базы данных для выделения, никаких данных для загрузки. Вы определяете таблицу (или используете Glue Data Catalog), пишете SQL, и Athena выполняет запрос против файлов S3.

```sql
SELECT 
    restaurant_id,
    COUNT(*) as order_count,
    SUM(total) as revenue
FROM orders
WHERE year='2024' AND month='09'
GROUP BY restaurant_id
ORDER BY revenue DESC
LIMIT 10;
```

Цена Athena основана на том, сколько данных сканирует запрос. В us-east-1, us-west-2 и большинстве основных регионов стандартные SQL-запросы стоят $5 за просканированный терабайт. Использование формата Parquet (столбцового) с обрезкой партиций (`WHERE year='2024' AND month='09'`) означает, что Athena сканирует только нужные ей файлы, что драматически снижает стоимость.

«Мы можем выполнить этот запрос за 30 дней данных», — сказал Лео, — «и это может стоить удивительно мало, если мы храним их хорошо».

«Как это может стоить так мало?» — спросила Майя. «Если он сканирует терабайты данных, как это не дорого?»

Лео объяснил Parquet. В строковом формате (JSON, CSV) запрос, ищущий два столбца из двадцати, должен прочитать все двадцать. В столбцовом формате вроде Parquet он читает только два нужных. Для набора данных 50 ТБ хорошо оптимизированный запрос мог бы просканировать 200 ГБ. При $5/ТБ это один доллар.

«А что, если кто-то случайно запросит всю таблицу?» — настаивала Майя.

«Это реальный риск стоимости», — сказал Лео.

Вы можете задаться вопросом: если Athena взимает плату за просканированный терабайт, может ли один плохо написанный запрос сгенерировать большой неожиданный счёт? Да — и это происходит в реальных продакшен-средах. Запрос против неоптимизированной таблицы 50 ТБ может стоить больше, чем весь ваш месячный счёт за S3. Вот почему формат Parquet и партиционирование — не опциональные оптимизации — это и есть контроль стоимости. Athena также поддерживает лимиты сканирования запросов в рабочих группах, которые ограничивают, сколько данных одному запросу разрешено сканировать.

«Для любого произвольного вопроса, который мы можем придумать?» — спросил Том.

«Любого вопроса, который мы можем выразить в SQL, против любых данных, которые мы сохранили в S3».

Том сел за ноутбук Лео и написал первый запрос:

```sql
SELECT
    r.restaurant_id,
    r.restaurant_name,
    AVG(EXTRACT(EPOCH FROM (o.confirmed_at - o.notification_sent_at)) / 60) 
        AS avg_confirmation_minutes,
    COUNT(DISTINCT c.customer_id) AS unique_customers,
    COUNT(DISTINCT CASE WHEN c.order_count > 1 THEN c.customer_id END) 
        AS returning_customers,
    ROUND(
        COUNT(DISTINCT CASE WHEN c.order_count > 1 THEN c.customer_id END) * 100.0 /
        NULLIF(COUNT(DISTINCT c.customer_id), 0),
        2
    ) AS reorder_rate_pct
FROM orders o
JOIN restaurants r ON r.restaurant_id = o.restaurant_id
JOIN (
    SELECT customer_id, restaurant_id, COUNT(*) AS order_count
    FROM orders
    WHERE year >= '2024'
    GROUP BY customer_id, restaurant_id
) c ON c.customer_id = o.customer_id AND c.restaurant_id = o.restaurant_id
WHERE o.year = '2024'
  AND o.status = 'delivered'
GROUP BY r.restaurant_id, r.restaurant_name
ORDER BY avg_confirmation_minutes ASC
LIMIT 20;
```

Запрос выполнялся 11 секунд. Результат: 20 ресторанов, отсортированных по самому быстрому среднему времени подтверждения, с их уровнями повторных заказов рядом.

Том уставился на вывод.

Самые быстро подтверждающие рестораны — те, что подтверждали заказы в среднем за 3-4 минуты — имели средний уровень повторных заказов 41%. Самые медленно подтверждающие рестораны (среднее время подтверждения 18-22 минуты) имели уровень повторных заказов 13%.

«Рестораны, которые подтверждают быстро, получают втрое больше повторных заказов», — сказал Том.

«Это огромный разрыв», — сказала Майя. «Почему скорость подтверждения так сильно влияет на уровень повторных заказов?»

«Потому что клиент разместил заказ и затем сидел, уставившись в свой телефон», — сказал Лео. «Если подтверждение приходит за 3 минуты, он чувствует уверенность. Если оно приходит за 22 минуты — или никогда — он чувствует тревогу. Тревога — это провал продукта, даже если еда прибывает нормально».

«Это продуктовый инсайт», — сказала Майя. «Не просто аналитический инсайт. Нам следует показывать ресторанам их бенчмарк времени подтверждения по сравнению со средним по категории».

Запрос Athena просканировал 1,2 ГБ данных (два месяца заказов в формате Parquet, партиционированных по году и месяцу). Стоимость: $0.006.

Полцента. За бизнес-инсайт, который изменил то, как Nimbus будет проектировать онбординг ресторанов — какие рестораны приоритизировать для коучинга успеха, какие цели по времени подтверждения устанавливать как часть SLA партнёров.

У Тома было выражение лица человека, пересчитывающего ценность всех данных, которые они выбрасывали.

«А что, если кто-то попытается взломать через слой запросов?» — спросила Прия. «Или просто аналитик, который случайно экспортирует адреса клиентов из сырых данных заказов? PII клиентов, истории заказов, финансовые записи — кто контролирует, какие таблицы вообще видимы?»

Прежде чем она закончила вопрос, Лео также осознал операционную проблему: как остановить одну команду от выполнения катастрофического полного сканирования таблицы, генерирующего счёт Athena в $500 одним запросом?

**Рабочие группы Athena (Athena Workgroups)** решают обе проблемы одновременно.

Рабочая группа — это именованная конфигурация, которая группирует пользователей Athena и применяет общие настройки: расположение результатов запросов, шифрование и — что критично — лимиты сканирования данных на запрос.

```
Workgroup: analytics-team
  Лимит сканирования запроса: 10 ГБ на запрос
  Действие при превышении лимита: Отменить запрос

Workgroup: engineering-team
  Лимит сканирования запроса: 100 ГБ на запрос
  Действие при превышении лимита: Только предупредить

Workgroup: finance-reports
  Лимит сканирования запроса: 1 ГБ на запрос
  Действие при превышении лимита: Отменить запрос
```

Аналитик в рабочей группе `analytics-team` не может случайно просканировать 50 ТБ данных и сгенерировать плату Athena в $250. Запрос отменяется, когда он превысил бы 10 ГБ просканированных данных. Аналитик видит сообщение об ошибке и знает, что нужно добавить фильтр партиции.

Рабочие группы также обеспечивают отдельные расположения результатов на команду: результаты запросов команды инженеров идут в `s3://nimbus-query-results/engineering/`; результаты команды финансов идут в `s3://nimbus-query-results/finance/`. Никакого межкомандного доступа к результатам запросов.

IAM контролирует, какие пользователи могут использовать какую рабочую группу. Функция Lambda, выполняющая автоматизированные отчёты, использует рабочую группу `finance-reports` (жёстко ограниченную). Инженер, отлаживающий продакшен-проблему, использует рабочую группу `engineering-team` (более широкое ограничение, предупреждать, а не отменять). Доступ к таблице сырых событий (содержащей PII клиентов) ограничен рабочей группой `engineering-team` через IAM-условие на таблице Glue Data Catalog.

«Это не просто контроль стоимости», — сказала Прия. «Это контроль доступа. Рабочие группы — это точка обеспечения».

Это полностью ответило на её вопрос. Каждое обсуждение конвейера данных, пропускающее контроль доступа, в итоге становится инцидентом комплаенса — а здесь аналитическая команда видела только агрегированные таблицы заказов, в то время как сырые события с PII клиентов оставались за явной IAM-авторизацией. Glue Data Catalog был не просто каталогом схем. Он был границей контроля доступа.

«Это не дополнительная работа», — сказала Прия. «Это и есть дизайн».

**Архитектура озера данных**

Эти три сервиса объединяются в то, что называется **архитектурой озера данных (data lake architecture)** — централизованным репозиторием S3 для всех ваших данных, с инструментами для их обработки и запросов:

```
Приложения (заказы, меню, события)
    |
    | События в реальном времени
    ↓
Kinesis Data Streams ──→ Amazon Data Firehose ──→ S3 (сырые)
                                                   |
                                                   | Glue Crawler обнаруживает схему
                                                   ↓
                                              Glue Data Catalog
                                                   |
                                                   | Glue Jobs преобразуют
                                                   ↓
                                              S3 (чистые, Parquet, партиционированные)
                                                   |
                                                   | SQL-запросы
                                                   ↓
                                              Amazon Athena
                                                   |
                                                   ↓
                                          Инструменты бизнес-аналитики
                                       (QuickSight, Tableau и т. д.)
```

Сырые данные всегда сохраняются (в оригинальном бакете S3). Преобразованные данные запрашиваемы через Athena. На новые вопросы всегда можно ответить, запустив новые задания Glue на сырых данных.

**Amazon Redshift: когда Athena недостаточно**

Для некоторых сценариев использования Athena слишком медленна или слишком дорога:

- Очень сложные запросы со множеством объединений
- Дашборды, выполняющие один и тот же запрос тысячи раз в день
- Машинное обучение на структурированных данных
- Требования субсекундного времени отклика для BI-инструментов

**Amazon Redshift** — это полностью управляемое хранилище данных (data warehouse): столбцовая аналитическая база данных, спроектированная для больших, повторяющихся аналитических нагрузок. В отличие от Athena, которая запрашивает данные там, где они живут в S3, Redshift загружает данные в оптимизированное хранилище склада и использует оптимизацию запросов, стратегии сортировки и стратегии распределения для ускорения сложной аналитики.

Если ваш объём данных небольшой, а запросы выполняются нечасто (еженедельно или ежемесячно), Athena с хорошо организованными данными S3 достаточна и почти бесплатна — но если вы выполняете одни и те же аналитические дашборды сотни раз в день, предварительно оптимизированное столбцовое хранилище Redshift будет быстрее и в конечном итоге экономичнее, несмотря на требование предварительной загрузки данных.

Redshift значительно быстрее для сложных аналитических запросов за счёт стоимости (выделенная мощность) и требования загрузки данных перед запросом.

**Redshift Serverless** убирает бремя планирования мощности — вы запрашиваете, Redshift масштабируется. Стоимость основана на фактически использованной вычислительной мощности, измеряемой в **RPU-часах** и тарифицируемой посекундно (с минимумом 60 секунд на активацию), плюс управляемое хранилище за ГБ-месяц — и ничего за вычисления, пока склад простаивает. (Athena — это та, что тарифицируется за запрос: $5 за просканированный ТБ.)

Для Nimbus на их текущем масштабе: Athena достаточна. При пятикратном объёме данных и с BI-инструментами, запрашивающими одни и те же дашборды сотни раз в день, Redshift стал бы экономичным.

**Когда Athena — неправильный инструмент**

«Так в чём подвох?» — спросила Майя. «Почему нам не использовать Athena для всего? Она бессерверная, оплата за запрос, никакой инфраструктуры — звучит идеально».

Случаи, когда Athena — не правильный ответ:

**Высокочастотные дашборды**: обращённый к клиентам аналитический дашборд, обновляющийся каждые 30 секунд и выполняющий 50 запросов в минуту, — не хороший сценарий использования Athena. При $5/ТБ просканированного эти запросы должны быть чрезвычайно хорошо оптимизированы, чтобы быть экономичными на такой частоте. Redshift или предварительно агрегированная база данных (даже RDS) более уместны для дашбордов с требованиями субсекундного времени отклика.

**Операционные запросы с требованиями низкой задержки**: если агенту службы поддержки нужно найти конкретный заказ менее чем за 500 мс, Athena — не инструмент — поиск в DynamoDB или запрос RDS — да. Athena оптимизирована для аналитической пропускной способности, а не операционной задержки. Даже хорошо настроенный запрос Athena на небольшом наборе данных имеет накладные расходы холодного старта в 1-3 секунды.

**Транзакционные системы**: Athena только для чтения. Вы не можете делать INSERT, UPDATE или DELETE записей в Athena (кроме как через специфические интеграции вроде Lake Formation или формата таблиц Iceberg, у которых своя сложность). Для операционных нагрузок записи используйте транзакционную базу данных.

**Очень маленькие, часто меняющиеся наборы данных**: если ваш набор данных меняется каждую минуту и составляет всего 1 ГБ, загрузка его в RDS или DynamoDB и запросы там проще и быстрее, чем выполнение запросов Athena против файлов S3, которые могут быть устаревшими. Athena запрашивает файлы S3 по состоянию на момент запроса — если файлы были записаны 2 минуты назад, это та свежесть, которую вы получаете.

Возникающий паттерн: Athena превосходна для крупномасштабных, нечастых, спонтанных аналитических запросов против данных S3. Для всего операционного, транзакционного или требующего субсекундной задержки используйте подходящую операционную базу данных.

**Kinesis против SQS: проясняем путаницу**

Это вопрос, который всплывает в каждом обсуждении архитектуры данных. И Kinesis, и SQS имеют дело с сообщениями. Когда использовать каждый?

Путаница исходит из поверхностного сходства: оба принимают сообщения от производителей. Оба доставляют эти сообщения потребителям. Оба — управляемые сервисы AWS. Но их модели данных принципиально разные.

**SQS (Simple Queue Service)** — это очередь задач. Вы кладёте сообщение. Один потребитель забирает его и обрабатывает. Когда обработка завершена, сообщение удаляется. Если у вас десять потребителей, каждое сообщение идёт ровно одному из них. Сообщение исчезает после потребления.

**Kinesis Data Streams** — это журнал (log). Вы кладёте запись. Каждый потребитель читает каждую запись. Потребитель A читает их все. Потребитель B тоже читает их все, в своём темпе. Ни один потребитель не удаляет запись — она остаётся в потоке, пока не истечёт период хранения. Вы можете добавить третьего потребителя в любое время, и он может читать с начала потока (в пределах окна хранения).

«Когда вы реально захотели бы, чтобы каждый потребитель видел каждое сообщение?» — спросила Майя.

Ответ — это сценарии использования, где Kinesis блистает:

**Дашборд реального времени + обнаружение мошенничества + архив S3**: все три потребляют один и тот же поток событий заказов одновременно. Если бы вы использовали SQS, вам нужно было бы публиковать в три отдельные очереди — и тот, кто публикует, должен знать обо всех трёх потребителях. С Kinesis производитель публикует один раз; любое число потребителей может читать независимо.

**Повтор (replay)**: потребитель проваливается на 2 часа (достигнут лимит параллелизма Lambda, нижестоящий сервис недоступен). С SQS эти сообщения уже были удалены (или имеют определённый таймаут видимости). С Kinesis потребитель возобновляет с последней контрольной точки и обрабатывает 2 часа пропущенных записей. Данные были сохранены в потоке (до 365 дней с расширенным хранением данных).

**Порядок в пределах шарда**: записи с одним и тем же ключом партиции всегда идут в один и тот же шард, сохраняя порядок. Для системы биржевой торговли, где вам нужно, чтобы все сделки по символу `AMZN` обрабатывались последовательно, Kinesis это гарантирует. SQS FIFO обеспечивает порядок в пределах группы, но при более низкой пропускной способности (до 3000 сообщений/секунду на очередь с пакетированием в стандартном режиме — высокопроизводительный режим поднимает это до десятков тысяч — против 1 МБ/с или 1000 записей/с на шард у Kinesis, умноженных на столько шардов, сколько вам нужно).

Решающий вопрос: **Должно ли каждое сообщение быть потреблено ровно одним потребителем и затем отброшено?** → SQS. **Должно ли каждое сообщение быть увидено несколькими потребителями независимо, или вам нужна возможность повтора?** → Kinesis.

Для дашборда реального времени Nimbus: Kinesis. Несколько потребителей (дашборд, обнаружение мошенничества, архив S3) все читают один и тот же поток.

Для очереди обработки заказов Nimbus (заказ размещён → одна задача ECS его обрабатывает): SQS. Один потребитель, повтор не нужен, веерный разброс не требуется.

## Визуализация данных: Amazon QuickSight

Athena запрашивает данные. Glue их подготавливает. Но в какой-то момент кому-то нужно увидеть график — и не выполняя SQL-запросы в консоли.

«Нам действительно нужен ещё один сервис для этого?» — спросила Майя. «Не могу я просто экспортировать результаты Athena в таблицу?»

«Для одного запроса — да», — сказал Том. У него было выражение лица человека, который уже это пробовал. «Для дашборда, которым вы хотите делиться со всей командой, это новая таблица каждое утро».

**Amazon QuickSight** — это управляемый сервис бизнес-аналитики (BI) AWS. Он подключается напрямую к Athena, S3, RDS, Redshift и другим источникам и позволяет строить дашборды и визуализации без отдельного BI-сервера.

Ключевые функции:

- **SPICE** (Super-fast, Parallel, In-memory Calculation Engine): QuickSight может импортировать наборы данных в свой in-memory движок для субсекундной производительности запросов в масштабе, без повторного запроса Athena при каждой загрузке дашборда
- **ML Insights:** обнаружение аномалий и прогнозирование встроены — никакой data science не требуется
- **Встроенные дашборды:** вы можете встроить дашборды QuickSight в собственное веб-приложение через URL

Том подключил QuickSight к источнику данных Athena и за один день получил работающий дашборд, показывающий ежедневные заказы, выручку по ресторанам и воронку конверсии.

«Сколько это стоит в месяц?» — спросил он — затем ответил на собственный вопрос прежде, чем кто-либо другой успел. «QuickSight стоит около $24/месяц за автора — людей, строящих дашборды — и $3/месяц за читателя. У нас четыре человека, которые им пользовались бы».

«Так что около ста долларов в месяц», — сказала Майя.

«За BI-сервис, который иначе требовал бы запуска отдельного аналитического сервера», — сказала Прия. «Да».

Том опубликовал дашборд. На следующее утро, вместо выполнения запросов Athena, вся команда открыла URL.

> **Совет для экзамена — QuickSight**
>
> QuickSight — это управляемый сервис BI и визуализации AWS. Подключается к Athena, S3, Redshift, RDS. SPICE — это in-memory движок запросов, который ускоряет повторяющиеся запросы дашбордов. Триггер экзамена: «дашборд бизнес-аналитики в AWS» или «визуализировать данные из Athena/Redshift» → QuickSight.

## Управление озером: AWS Lake Formation

По мере роста озера данных Nimbus доступ к данным стал проблемой управления (governance).

«Кто может запрашивать сырые журналы транзакций?» — спросила Прия на следующем разборе архитектуры. «Кто может видеть PII клиентов? Кто может получить доступ к таблицам финансовых сводок?»

«У инженерии полный доступ», — сказал Лео. «У аналитической команды доступ к агрегированным таблицам. У финансов доступ к таблицам выручки».

«Сконфигурировано где?»

Лео сделал паузу. «В... нескольких разных местах. Политики бакетов S3, IAM-политики, разрешения каталога Glue».

«Три отдельные системы, все из которых должны быть консистентны», — сказала Прия. «Что произойдёт, когда мы добавим нового аналитика? Или когда мы решим ограничить доступ к конкретному столбцу — скажем, телефонным номерам клиентов — от аналитической команды?»

Этот вопрос обнажил пробел. Управление мелкозернистым доступом к данным через политики бакетов S3, IAM и Glue Data Catalog одновременно было хрупким.

**AWS Lake Formation** — это управляемый сервис, который централизует контроль доступа для вашего озера данных. Вместо управления политиками бакетов, IAM-политиками и разрешениями каталога Glue по отдельности, Lake Formation предоставляет единое место для выдачи разрешений на уровне столбца, строки и таблицы на ваши данные.

Ключевые функции:

- Располагается поверх S3 и Glue Data Catalog — миграция данных не требуется
- **Мелкозернистый контроль доступа:** выдавайте конкретным пользователям или ролям доступ к конкретным таблицам, столбцам или даже отфильтрованным строкам — эквивалент разрешений уровня базы данных на данных S3
- **Фильтрация данных:** когда пользователь запрашивает управляемую Lake Formation таблицу через Athena, Lake Formation автоматически отфильтровывает столбцы или строки, которые ему не разрешено видеть

Прия настроила Lake Formation с тремя уровнями разрешений, при этом Рафаэль составил правила уровня столбцов: роль инженерии видела все таблицы и все столбцы. Аналитическая роль видела агрегированные таблицы заказов, но не столбцы PII клиентов. Финансовая роль видела таблицы выручки с замаскированными идентификаторами клиентов.

«Так что аналитик выполняет тот же запрос Athena», — подтвердил Лео. «Но Lake Formation перехватывает его и убирает столбцы, которые им не разрешено видеть?»

«Верно. Фильтрация автоматическая. Аналитику не нужно знать, что это происходит — и они не могут обойти это, запрашивая сырые файлы S3 напрямую, потому что Lake Formation контролирует доступ на уровне каталога».

«Это не дополнительная работа», — сказала Прия. «Это и есть дизайн».

> **Совет для экзамена — Lake Formation**
>
> Lake Formation централизует контроль доступа для озера данных, построенного на S3 и Glue Data Catalog. Поддерживает мелкозернистые разрешения на уровне таблицы, столбца и строки. Триггер экзамена: «ограничить доступ к конкретным столбцам в озере данных S3» или «централизовать управление озером данных» → Lake Formation. Ключевое отличие от сырого IAM: Lake Formation обеспечивает фильтрацию на уровне столбцов и строк, которую IAM-политики сами по себе выразить не могут.

## Сильные стороны и ограничения

**Kinesis Data Streams**: используйте Kinesis, когда ваши данные поступают непрерывно и порядок имеет значение — потоки кликов, финансовые транзакции, телеметрия IoT. Kinesis сохраняет порядок записей в пределах шарда и позволяет повтор в течение настроенного окна хранения (24 часа по умолчанию, до 365 дней с расширенным хранением данных), что делает его принципиально отличным от SQS. Компромисс — операционная сложность: в выделенном режиме вы управляете мощностью шардов и поведением потребителей. Для простых очередей задач, где порядок не имеет значения и повтор не нужен, SQS — более простой выбор.

**AWS Glue**: Glue устраняет инфраструктуру традиционного ETL-кластера. Вы пишете логику преобразования; AWS управляет средой Spark. Это ценно, когда преобразования сложны или объёмы данных велики. Ограничение — стоимость и холодный старт — у заданий Glue задержка старта в несколько минут, что делает их непригодными для преобразований почти реального времени. Для простых конвертаций формата файлов (CSV в Parquet) накладные расходы Glue могут не стоить того по сравнению с функцией Lambda или лёгким скриптом.

**Amazon Athena**: Athena позволяет запрашивать данные S3 стандартным SQL без инфраструктуры для управления. Критическое ограничение — стоимость: Athena взимает плату за просканированный терабайт данных. Запрос против таблицы 10 ТБ, сканирующий её целиком, стоит значительно больше, чем тот же запрос против партиционированной таблицы в формате Parquet, сканирующей 200 ГБ. Всегда используйте столбцовые форматы (Parquet или ORC) и партиционируйте свои данные перед запуском Athena в продакшене. Без этих оптимизаций счета Athena могут вас удивить.

## Итоги

Сетевая работа в главе 25 сделала конвейер данных Nimbus возможным. Эта глава — о том, для чего этот конвейер: сделать все данные, которые Nimbus генерировал, реально видимыми и пригодными к действию.

- **Amazon Kinesis**: стриминг данных в реальном времени. Производители пишут записи; потребители читают в своём темпе. Amazon Data Firehose может затем доставлять стриминговые данные в S3, Redshift и другие назначения с меньшей операционной работой.
- **AWS Glue**: ETL и каталогизация данных. Краулеры обнаруживают схемы; задания преобразуют данные; Data Catalog делает данные обнаружимыми для Athena и других инструментов.
- **Amazon Athena**: бессерверный SQL на S3. Запрашивайте любые данные в S3, используя стандартный SQL. Тарифицируется за просканированный ТБ — используйте Parquet и партиционирование для минимизации стоимости.
- **Amazon Redshift**: управляемое хранилище данных для высокопроизводительной аналитики. Загрузите данные, оптимизируйте для повторяющихся аналитических запросов и запрашивайте быстро в масштабе склада.
- **Паттерн озера данных**: сырые данные в S3 → Glue их преобразует → Athena их запрашивает → BI-инструменты их визуализируют.
- **Эволюция схемы Glue**: ETL-конвейеры, обрабатывающие внешние данные, должны изящно справляться с изменениями схемы. Используйте DynamicFrames с `mergeSchema: true`, чтобы избежать сбоев конвейера, когда вышестоящие данные добавляют новые поля.
- **Рабочие группы Athena**: лимиты сканирования данных и расположения результатов на команду. Контроль стоимости и контроль доступа в одной конфигурации. Обязательны для любого многокомандного развёртывания Athena.
- **Kinesis против SQS**: Kinesis для веерного разброса нескольким потребителям и возможности повтора. SQS Standard для простых очередей задач; SQS FIFO для упорядоченной, дедуплицированной обработки задач. Решающий вопрос: должен ли каждый потребитель видеть каждое сообщение, или каждое сообщение идёт одному потребителю?
- **Когда Athena неправильна**: высокочастотные дашборды (используйте Redshift), операционные запросы (используйте RDS или DynamoDB), очень маленькие часто меняющиеся наборы данных (просто используйте базу данных).
- **Amazon QuickSight**: управляемый BI-сервис AWS. Подключается к Athena, S3, Redshift и RDS для построения дашбордов без запуска отдельного BI-сервера. SPICE — это in-memory движок, ускоряющий повторяющиеся запросы дашбордов.
- **AWS Lake Formation**: централизованный контроль доступа для озёр данных на S3 + Glue Data Catalog. Обеспечивает разрешения на уровне столбца, строки и таблицы — мелкозернистое управление данными, которое IAM сам по себе выразить не может.

## Советы по экзамену

*Домен SAA-C03: Проектирование высокопроизводительных архитектур (Домен 3, Задача 3.5)*

- **Kinesis против SQS**: Kinesis = упорядоченный, стриминг в реальном времени, несколько потребителей, повтор в пределах окна хранения (24 часа по умолчанию, до 365 дней). SQS = очередь задач, каждое сообщение обрабатывается один раз. «Несколько потребителей, читающих один и тот же поток одновременно» → Kinesis. «Один работник на сообщение» → SQS.
- **Признаки Athena в экзамене**: «бессерверный SQL на S3», «анализировать данные S3, не загружая их в базу данных», «оплата за запрос» → Athena.
- **Оптимизация стоимости Athena**: столбцовый формат (Parquet или ORC) + партиционирование драматически снижают объём просканированных данных и стоимость. Экзамен может спросить, как снизить затраты на Athena.
- **Цены Athena**: $5 за просканированный ТБ (us-east-1, us-west-2 и большинство основных регионов). Стоимость рассчитывается по просканированным данным, а не по возвращённым — всегда оптимизируйте формат хранения перед запуском продакшен-запросов.
- **Glue Crawler**: «Обнаружить схему данных S3 автоматически» → Glue Crawler.
- **Amazon Data Firehose**: «Автоматически загружать стриминговые данные в S3/Redshift/OpenSearch без управления потребителями» → Amazon Data Firehose. Старые материалы могут всё ещё называть это Kinesis Data Firehose.
- **Redshift против Athena**: Redshift для высокочастотных, сложных запросов на фиксированном наборе данных (BI-дашборды). Athena для спонтанных запросов на данных S3, которые часто меняются.
- **EMR (Elastic MapReduce)**: управляемые AWS кластеры Hadoop/Spark. Экзамен использует это, когда упоминаются «существующие нагрузки Hadoop/Spark» или «кастомные фреймворки обработки данных». Glue — управляемая альтернатива для большинства сценариев.
- **QuickSight:** управляемый BI и визуализация AWS. Подключается к Athena, S3, Redshift, RDS. SPICE = in-memory движок для быстрых повторяющихся запросов. Триггер экзамена: «дашборд бизнес-аналитики в AWS» → QuickSight.
- **Lake Formation:** централизованный контроль доступа для озера данных (S3 + Glue Data Catalog). Мелкозернистые разрешения: уровень таблицы, столбца и строки. Триггер экзамена: «ограничить доступ к конкретным столбцам в озере данных S3» или «централизовать управление озером данных» → Lake Formation.

**Упражнение 2 — Сценарий SAA-C03**

*Сценарий*: Компания совместных поездок хочет анализировать данные поездок. 1 миллион поездок завершается ежедневно. Записи поездок хранятся в S3 как JSON-файлы (примерно 2 КБ каждый). Аналитическая команда хочет выполнять спонтанные SQL-запросы вроде «средняя длительность поездки по городам на прошлой неделе». Запросы должны завершаться менее чем за 2 минуты. Затраты на хранение должны быть минимизированы. Команда будет выполнять 20-30 запросов в неделю.

Какая архитектура НАИЛУЧШИМ образом отвечает этим требованиям?

A) Использовать AWS Glue для конвертации JSON в формат Parquet, партиционированный по дате и городу; запрашивать с Amazon Athena  
B) Загружать данные поездок в RDS PostgreSQL ежедневно; запрашивать стандартным SQL  
C) Использовать Amazon Data Firehose для доставки данных поездок в Amazon Redshift; запрашивать с Redshift  
D) Загрузить данные поездок в DynamoDB и использовать PartiQL для SQL-запросов

**Подсказка 1**: 20-30 запросов в неделю — это низкая частота. Какой сервис наиболее экономичен для эпизодических запросов?

**Подсказка 2**: Формат Parquet + партиционирование драматически снижают объём данных, сканируемых Athena — и, следовательно, стоимость.

**Подсказка 3**: 1 миллион поездок × 2 КБ = ~2 ГБ в день. За неделю ~14 ГБ. При $5/ТБ для Athena, даже без оптимизации, это доступно по цене.

**Ответ**: A

**Объяснение**: Glue конвертирует JSON в Parquet (столбцовый формат драматически снижает объём просканированных данных), партиционированный по дате и городу (обрезка партиций означает, что запросы «прошлой недели» сканируют только 7 дней партиций). Athena запрашивает S3 напрямую стандартным SQL. Для 20-30 запросов в неделю Athena с оплатой за запрос чрезвычайно экономична против всегда работающего Redshift.

**Почему не B?** Загрузка 2 ГБ данных ежедневно в RDS, затем запросы, требует экземпляра базы данных, работающего 24/7. Для 20-30 запросов в неделю это чрезмерно переусложнено и дорого.

**Почему не C?** Redshift экономичен для высокочастотных запросов (сотни в день на одном наборе данных). Для 20-30 запросов в неделю всегда включённый кластер Redshift стоит намного больше, чем оплата за запрос Athena.

**Почему не D?** DynamoDB — это хранилище ключ-значение/документов, оптимизированное для доступа по ключу, а не для спонтанных аналитических запросов. PartiQL на DynamoDB не поддерживает описанный вид агрегаций GROUP BY.

## Послесловие к главе

Том выполнил первый запрос Athena.

«Топ-10 ресторанов по выручке за прошлый квартал», — сказал он.

12 секунд спустя появились результаты.

Он уставился на них.

«Ресторан 47 был первым», — сказал он. Это был семейный ресторан Майи — тот, где начался Nimbus.

«Конечно был», — сказала Майя. «Арепа настолько хороша».

Том выполнил ещё один запрос. И ещё. «Сколько это стоит в месяц?» — спросил Том, прежде чем Лео успел что-либо сказать. Лео проверил историю сканирования запросов. Три запроса, всего просканировано данных: 1,2 ГБ. Стоимость: меньше цента.

Через час у Тома была полная картина бизнеса Nimbus так, как никогда раньше. Какие категории ресторанов росли быстрее всего. Какие когорты клиентов удерживались дольше всего. Какие пункты меню приносили больше всего повторных заказов.

«Почему мы не построили это раньше?» — спросил он.

«У нас были данные», — сказал Лео. «У нас просто не было конвейера, чтобы их использовать».

«Данные всегда были тут», — сказала Майя тихо. «Мы просто не могли их видеть».

В следующей главе: теперь, когда мы можем видеть бизнес ясно, давайте поговорим о том, как платить за инфраструктуру, которая его запускает — более эффективно.
