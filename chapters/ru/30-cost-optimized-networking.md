# Глава 30: Скрытые затраты

У Том в комнате для совещаний была доска с тремя столбцами: вычисления, хранилище, сеть. Первые два были заполнены — числа, даты, названия завершённых оптимизаций. Он постоял у доски минуту, прежде чем написать что-либо в третьем столбце. Сетевые строки в счёте AWS разбросались по странице так, как другие не разбросались. У каждой было своё название, своя единица, своё обоснование того, почему деньги уходят.

Он снял колпачок с маркера.

**Краткое содержание: последнее неизвестное в счёте**

Аудит баз данных закрыл последнюю крупную статью счёта, над которой Том активно работал — $491/мес. возвращено, $5 892 в год. Добавьте EC2 Savings Plans, политики жизненного цикла S3 и очистку хранилища, и текущий итог составлял $34 092 ежегодной экономии за три месяца работы. Но Том заметил во время глубокого погружения в базы данных, что одна категория почти не изучалась. Затраты на хранилище отображались одной строкой: «S3: $198». Затраты на вычисления отображались одной строкой: «EC2: $2 340» — до того, как пришли скидки Savings Plan из главы 27. Сетевые затраты разбросались по дюжине записей с названиями вроде «Data Transfer Out», «NAT Gateway Processing», «VPC Peering Data Transfer» и «CloudFront Data Transfer». Он никогда не складывал их и не смотрел на сумму. Это была сегодняшняя работа.

Том открыл счёт. Нашёл раздел передачи данных. Сложил все строки.

Сетевые затраты в AWS похожи на городскую систему платных дорог: въезд в город бесплатен, но каждый туннель на выезде стоит денег, и поездка между районами тоже немного стоит. Большинство людей не думают о пошлинах, пока в конце месяца не получают счёт и не понимают, что каждый день проезжали через туннель, когда рядом всё время была бесплатная наземная дорога. Цель этой главы — понять каждый пункт оплаты — и решить, какие из них стоит платить.

$847/мес.

— Мы тратим $847 в месяц на передачу данных, — сказал он.

— Это много? — спросил Лео.

— Это ровно столько, сколько был наш счёт S3 до оптимизации. И я даже не знал, что у нас есть счёт за передачу данных такого размера.

Майя взглянула.

— Что именно такое передача данных?

— Это то, что AWS берёт за перемещение байт. Байты в AWS: обычно бесплатно. Байты из AWS в интернет: платные. Байты между сервисами в разных регионах: платные. Байты, проходящие через NAT Gateway: платные.

— Можете разбить подробнее?

Том мог. Но на этот раз он не остановился на консоли биллинга. Он включил VPC Flow Logs во всех их VPC и подал их в CloudWatch Logs Insights. Это позволило ему запрашивать фактические потоки трафика — не просто суммы в долларах, а какие источники отправляли данные куда и сколько.

Запрос выполнялся две минуты. В сочетании с ещё одним источником логов, который он вскоре подтянет, вывод был достаточно конкретным, чтобы действовать.

**Анализ трафика: что на самом деле генерирует счёт**

Топ-5 потоков трафика по объёму, по порядку:

1. EC2-серверы приложений → NAT Gateway → сервисы AWS (SSM, Secrets Manager, CloudWatch, SQS): 3,9 ТБ/мес.
2. EC2-серверы приложений → NAT Gateway → внешние API: 1,3 ТБ/мес.
3. Эндпоинт reader Aurora → EC2-серверы приложений (кросс-AZ): 0,4 ТБ/мес.
4. Аналитический конвейер → S3-бакет в us-east-1 (кросс-регион): 0,3 ТБ/мес.
5. CloudFront → источник S3 (промахи кэша): 0,2 ТБ/мес.

Первые четыре пришли прямо из Flow Logs. Пятый не мог: VPC Flow Logs видят только трафик, пересекающий сетевые интерфейсы внутри ваших VPC, а промах кэша CloudFront, забирающий из S3, вообще никогда не касается VPC — это CloudFront, общающийся напрямую с S3. Для этого потока Том вытянул стандартные логи доступа CloudFront и отфильтровал по полю `x-edge-result-type`: каждая запись, помеченная `Miss`, — это запрос, который CloudFront пришлось забрать из источника, и суммирование байт дало ему 0,2 ТБ. Один счёт, два инструмента — каждый слеп к тому, что видит другой.

— Поток номер четыре, — сказала Прия. — Почему наш аналитический конвейер общается с бакетом в us-east-1?

У Лео было выражение лица, которое Том узнал.

— Я уже его развернул — ох, — сказал Лео. — Полгода назад я тестировал, может ли наш аналитический конвейер веерно расходиться по нескольким регионам параллельно. Я поднял тестовый бакет в us-east-1, направил конвейер на него и запустил на неделю. Тест закончился, но я забыл убрать назначение us-east-1 из конфигурации конвейера.

— То есть пять месяцев, — сказал Том, — мы записывали копию каждого аналитического результата в бакет в Вирджинии.

— Сколько это стоит в месяц? — спросил Том.

Кросс-региональная передача из us-west-2 в us-east-1: $0,02/ГБ. 300 ГБ/мес. = $6/мес. за передачу. Плюс хранилище S3 для дублирующихся данных в us-east-1: 300 ГБ × 5 месяцев × $0,023/ГБ = $34,50 в хранимых данных.

— Не огромно, — сказал Лео.

— Не огромно в месяц, — сказал Том. — Но это работает уже пять месяцев, и никто не знал. Это непреднамеренная затрата. Вопрос не в том, имеют ли значение $6 — а в том, знаем ли мы, почему тратится каждый доллар.

Лео удалил тестовый бакет us-east-1 и убрал назначение из конфигурации конвейера.

Самой пригодной к действию находкой в выводе flow log был поток номер один: EC2-серверы приложений, вызывающие сервисы AWS через NAT Gateway.

Том вытянул конкретные записи логов для запроса CloudWatch Logs Insights, отфильтрованные, чтобы показать только трафик, направленный к диапазонам IP сервисов AWS:

```
fields @timestamp, srcAddr, dstAddr, bytes, protocol
| filter dstAddr like "52.94." or dstAddr like "54.239." or dstAddr like "52.46."
| stats sum(bytes) as totalBytes by srcAddr, dstAddr
| sort totalBytes desc
| limit 20
```

Вывод показал кое-что, чего он не ожидал: примерно 300 ГБ в месяц трафика S3 в том же регионе — отдельно от кросс-регионального потока к бакету Лео в us-east-1 — проходило через NAT Gateway. Но Том уже настроил S3 Gateway Endpoints месяцами ранее.

— У нас есть S3 Gateway Endpoint, — сказал Лео. — Почему трафик S3 всё ещё идёт через NAT?

Том посмотрел на таблицу маршрутизации. Gateway Endpoint был настроен — но только для VPC приложения. Аналитический конвейер работал в отдельном VPC, который был создан девять месяцев назад для изоляции данных. У этого VPC не было S3 Gateway Endpoint. Каждый вызов S3 от EC2-инстансов аналитического конвейера маршрутизировался через NAT Gateway этого VPC.

— 0,3 ТБ трафика аналитического конвейера × $0,045/ГБ = $13,50/мес., — сказал Том. — Только из-за отсутствующего эндпоинта во втором VPC.

— Сколько стоило бы добавить эндпоинт? — спросил Лео.

— Ноль, — сказал Том. — S3 Gateway Endpoints бесплатны. Это запись в таблице маршрутизации.

Добавление Gateway Endpoint в аналитический VPC заняло бы четыре минуты и срезало бы $13,50 с месячной платы NAT Gateway — небольшое абсолютное число, но находка была в принципе. Они добавили контроль затрат в одном VPC и забыли воспроизвести его при создании второго. Согласованность требовала процесса, а не только знания.

Том добавил в чек-лист развёртывания: при создании нового VPC добавлять S3 и DynamoDB Gateway Endpoints до присоединения каких-либо нагрузок.

Вторая конкретная находка из flow logs была дороже. Трафик от функций Lambda, выполнявших систему уведомлений о заказах — доступ к S3 для чтения файлов конфигурации ресторанов — шёл через NAT Gateway вместо эндпоинта S3. Функции Lambda работали внутри VPC (для доступа к RDS), а эндпоинт S3 этого VPC был настроен только для EC2-инстансов в подсети приложения. Функции Lambda в подсети Lambda маршрутизировались через NAT.

— Подождите — но *почему* нам делать это так? — спросила Майя. — У нас есть эндпоинт. Почему Lambda его не использует?

— VPC Gateway Endpoints применяются на подсеть на основе таблиц маршрутизации, — сказал Том. — Функции Lambda в своей собственной подсети со своей собственной таблицей маршрутизации. В этой таблице маршрутизации не было маршрута эндпоинта. Я добавил его для подсети приложения. Я пропустил подсеть Lambda.

Добавление маршрута эндпоинта S3 в таблицу маршрутизации подсети Lambda сэкономило бы ещё $41/мес. в сборах за обработку NAT Gateway, которые начислялись за вызовы S3, которые должны были быть бесплатными.

Анализ flow log окупил себя. Три часа времени на запросы, три конкретные находки: забытый эндпоинт аналитического VPC ($13,50/мес.), пробел в маршрутизации подсети Lambda ($41/мес.) и исходная крупная находка, которая стала основой для решений по Interface Endpoint. Общая дополнительная месячная экономия, выявленная анализом flow log: $54,50, поверх $78 от Interface Endpoints, которые анализ уже вскрыл. Эти два меньших исправления пошли в бэклог на следующий спринт; таблица экономии в конце этой главы учитывает только то, что было отгружено.

— Урок в том, что VPC endpoints — это не одноразовая конфигурация, — сказал Том. — Каждый новый VPC, каждая новая подсеть, каждый новый тип нагрузки требует той же проверки. Поведение по умолчанию для всего в частной подсети — маршрутизироваться через NAT. Проверка такая: вызывает ли эта нагрузка S3, DynamoDB или какой-либо из высокотрафиковых сервисов AWS? Если да, есть ли у неё маршрут эндпоинта?

— А мы думали об автоматизации этой проверки? — спросила Прия. — Правило AWS Config, которое оповещает, когда частная подсеть создаётся без маршрута эндпоинта S3?

— Это в списке, — сказал Том. — Сразу после оповещения об осиротевших томах.


И с этим у Том был ответ на вопрос, с которого начался анализ. Сетевые затраты были не единой проблемой. Это были пять разных проблем, каждая со своим решением.

**Как AWS начисляет плату за передачу данных**

Ценообразование AWS на передачу данных асимметрично:

**В AWS (входящий)**: бесплатно. Вы можете загружать сколько угодно данных.

**Из AWS в интернет (исходящий)**: платно. Первые 100 ГБ/мес. бесплатны. После:

- $0,09/ГБ за первые 10 ТБ/мес. (регионы US)
- $0,085/ГБ за следующие 40 ТБ
- Ниже при больших объёмах

**Внутри той же зоны доступности**: бесплатно. EC2-инстансы, взаимодействующие в той же AZ, ничего не платят.

**Между зонами доступности (один регион)**: $0,01/ГБ в каждом направлении. Небольшая, но реальная стоимость.

**Между регионами**: $0,02–0,08/ГБ в зависимости от регионов. Кросс-региональный трафик значительно дороже.

**NAT Gateway**: $0,045/ГБ обработки. Каждый байт, отправляемый вашим частным EC2-инстансом через NAT Gateway для выхода в интернет — и каждый байт, возвращающийся — тарифицируется.

**CloudFront**: более низкие тарифы на передачу данных, чем прямое AWS-в-интернет. $0,085/ГБ за первые 10 ТБ (немного меньше, чем прямая исходящая передача данных). CloudFront часто снижает общие затраты на передачу, потому что кэширование на граничных серверах означает, что источник отдаёт данные реже.

**Разбивка Том**

— Сколько это стоит в месяц? — спрашивал Том по каждой строке счёта по очереди. Он добавлял их в отдельную вкладку в таблице — не месячный итог, а каждую категорию по отдельности. Итог был менее полезен, чем понимание того, какая часть счёта была каким видом затрат.

После категоризации каждой строки счёта:

**Исходящие данные в интернет**: $214/мес.

- Ответы API клиентам по всему миру
- Ресурсы, всё ещё обслуживаемые напрямую из S3 и ALB клиентам, минуя CloudFront (заполнения кэша сами по себе — CloudFront, забирающий из источника AWS — бесплатны: AWS не взимает плату за передачу от источника к CloudFront)

**Обработка NAT Gateway**: $289/мес.

- Серверы приложений, вызывающие внешние API (платёжный процессор, сервис электронной почты, данные карт)
- Вызовы DynamoDB, проходящие через NAT Gateway (до настройки VPC endpoints для некоторых таблиц)

**Кросс-AZ передача данных**: $178/мес.

- Балансировщик нагрузки к EC2-инстансам (балансировщик в одной AZ, некоторые инстансы в другой)
- Сервер приложений к реплике RDS для чтения (в другой AZ)

**Кросс-региональная передача данных**: $166/мес.

- Репликация Aurora Global Database (основная в us-west-2, читатель в us-east-1)
- Кросс-региональная репликация S3 для резервных копий
- Забытый тестовый конвейер Лео ($6/мес. от этого итога)

**NAT Gateway: наибольший сюрприз**

$289/мес. в сборах за обработку NAT Gateway были самой большой статьёй. И анализ VPC Flow Log сделал её конкретной: главным потребителем были серверы приложений, вызывающие API сервисов AWS (SSM, Secrets Manager, CloudWatch Logs) через NAT Gateway.

В главе 11 Том настроил VPC Gateway Endpoints для S3 и DynamoDB. Они были бесплатными. Но он пропустил настройку Interface Endpoints для нескольких других сервисов:

- Systems Manager (SSM) для управления патчами
- Secrets Manager для получения учётных данных
- CloudWatch для отправки метрик и логов
- SQS для опроса сообщений

Каждый вызов к этим сервисам от частных EC2-инстансов проходил через NAT Gateway. Каждый вызов тарифицировался по $0,045/ГБ.

Вы можете задаться вопросом, почему AWS берёт плату за трафик, проходящий через NAT Gateway, когда вы уже внутри сети AWS. Ответ в том, что сам NAT Gateway — это управляемый сервис: его запуск стоит денег, и AWS перекладывает эту стоимость за гигабайт. VPC Endpoints устраняют посредника, поэтому они снижают счёт.

— Подождите — но *почему* нам делать это так? — спросила Майя, когда Том показал цифры. — Мы настроили Gateway Endpoints для S3 и DynamoDB. Почему мы не сделали то же для SSM и CloudWatch?

— Gateway Endpoints доступны только для S3 и DynamoDB, — сказал Том. — Для всего остального — SSM, Secrets Manager, SQS — нужны Interface Endpoints. Они не бесплатны, но дешевле, чем маршрутизация через NAT при объёме, который мы генерируем.

**Interface Endpoints** для этих сервисов: $0,01/час на AZ + $0,01/ГБ обработанных данных.

При объёме Nimbus SSM Interface Endpoint стоил бы около $25/мес. (почасовые сборы плюс обработка за ГБ) и экономил бы около $45/мес. в платах NAT Gateway (потому что SSM генерирует значительный объём данных для управления патчами и вызовов хранилища параметров).

Стоимость и экономия от эндпоинтов варьировались по сервисам и объёму. Том подсчитал, что настройка Interface Endpoints для четырёх высокотрафиковых сервисов — по две AZ каждый, плюс обработка $0,01/ГБ на 3,9 ТБ, которые они понесут — обошлась бы примерно в $97/мес. в совокупности и сэкономила бы примерно $176/мес. в обработке NAT Gateway.

Чистая экономия: $78/мес. только от настройки эндпоинтов.

— А что, если кто-то попытается взломать? — сказала Прия, когда разговор о VPC endpoint перешёл к реализации. — VPC endpoint означает, что трафик никогда не касается публичного интернета — это не только затраты, это сокращение поверхности угрозы. Нам следовало сделать это ради одной только пользы для безопасности.

— Согласен, — сказал Том. — Экономия затрат — это бонус.

Лео посмотрел на список сервисов, которые маршрутизировались через NAT.

— Я, возможно, настроил эндпоинты логирования CloudWatch, не проверив, есть ли для него VPC endpoint, — сказал он. — Пока всё будет нормально — но да, это шесть месяцев шло через NAT.

— Это в списке, — сказал Том. — CloudWatch — один из четырёх, которые мы исправляем.

**Расчёт PrivateLink: когда это имеет смысл**

Есть более сложная версия этого разговора, которая возникает по мере роста архитектур: использование AWS PrivateLink для обеспечения частного подключения к сервисам, размещённым другими клиентами AWS (или к вашим собственным сервисам в других VPC).

Interface Endpoints PrivateLink стоят $0,01/час на AZ плюс $0,01/ГБ. Для сервиса, генерирующего 1 ТБ/мес. трафика через эндпоинт:

- Стоимость PrivateLink: $0,01 × 2 AZ × 730 часов + $0,01 × 1 000 ГБ = $14,60 + $10 = $24,60/мес.
- Маршрутизация того же трафика через существующий NAT Gateway вместо этого: $0,045 × 1 000 ГБ = $45/мес. дополнительных сборов за обработку

Сравнение *приростное*, потому что NAT Gateway остаётся в любом случае — он по-прежнему обслуживает остальной трафик, направленный в интернет, поэтому его почасовая стоимость ($0,045 × 2 × 730 = $65,70) не исчезает, когда этот один сервис переходит на эндпоинт. Для этого объёма трафика PrivateLink экономит примерно $20/мес. Точка безубыточности — примерно 420 ГБ/мес. — ниже этого собственная почасовая стоимость эндпоинта перевешивает экономию за ГБ относительно обработки NAT.

— Подождите — но *почему* нам использовать PrivateLink вместо просто VPN или пиринга? — спросила Майя.

— VPC Peering проще и бесплатен для внутрирегиональных передач, — сказал Том. — Но пиринг создаёт полностью маршрутизируемое соединение между VPC — всё в VPC A потенциально может достичь всего в VPC B. PrivateLink более хирургичен. Эндпоинт раскрывает конкретный сервис, а не полный сетевой маршрут. Для архитектур, заботящихся о безопасности, эта конкретность важна.

**Кросс-AZ трафик: архитектурный вопрос**

$178/мес. кросс-AZ передачи данных было сложнее.

Часть была неизбежна: балансировщик нагрузки распределяет трафик по AZ, поэтому некоторые запросы поступают в одну AZ, и балансировщик направляет их к инстансу в другой AZ.

Часть была оптимизируема: приложение было настроено на запись к основной RDS (в us-west-2a) и чтение из реплики для чтения (в us-west-2b). Каждый запрос чтения пересекал границы AZ.

Для чтений одно решение: настроить приложение на предпочтение реплики для чтения в той же AZ, что и запрашивающий инстанс. Каждая AZ получает собственную реплику для чтения. Трафик остаётся локальным.

Компромисс: больше реплик для чтения = больше затрат. Если кросс-AZ трафик стоит $50/мес., а дополнительная реплика для чтения — $190/мес., AZ-локальная оптимизация не окупается.

Том рассчитал: при их текущем объёме запросов кросс-AZ трафик был всего $31/мес. от $178. Не стоит добавлять реплики ради этого.

Другие кросс-AZ затраты были от маршрутизации балансировщика нагрузки и межсервисной коммуникации — в значительной мере неизбежные на текущем архитектурном уровне.

**S3 Select: сокращение передачи данных в запросах**

Просматривая аналитический конвейер, Том нашёл ещё одну оптимизацию, специфичную для того, как команда аналитики запрашивала большие файлы S3.

Паттерн: каждое утро аналитическое задание скачивало файл Parquet объёмом 500 МБ из S3, чтобы отфильтровать его в памяти для данных заказов конкретного ресторана. Примерно 95% файла отбрасывалось после скачивания.

**S3 Select** позволяет получать только нужные строки и столбцы из объекта S3 (CSV, JSON, Parquet), не скачивая весь файл для фильтрации в вашем приложении.

> **Важное обновление**: в середине 2024 года AWS перестал предлагать S3 Select новым клиентам — существующие пользователи сохраняют его, но для новых архитектур это тупик. Принцип, которому учит этот раздел (фильтруй на уровне хранилища, не пересылай весь файл), вне времени; современный инструмент для этого — **Amazon Athena** (SQL напрямую над S3, включая объединения и агрегации, которых у S3 Select никогда не было). **S3 Object Lambda**, когда-то другая альтернатива, последовал за S3 Select в статус legacy: с 7 ноября 2025 года он тоже закрыт для новых клиентов (существующие нагрузки продолжают работать). На текущем экзамене «запрос данных на месте в S3» указывает на Athena. История ниже сохранена, потому что *рассуждение* — сначала измерь, перенеси фильтр к данным — это и есть урок.

Без S3 Select:
```python
# Скачать файл 500 МБ, обработать в памяти
data = s3.get_object(Bucket='analytics', Key='orders-2024.csv')
df = pd.read_csv(data['Body'])
result = df[df['restaurant_id'] == '47'][['order_id', 'total']]
```

С S3 Select:
```python
# Пусть S3 сначала отфильтрует, передать только совпадающие строки (~2 МБ вместо 500 МБ)
response = s3.select_object_content(
    Bucket='analytics',
    Key='orders-2024.csv',
    Expression="SELECT order_id, total FROM S3Object WHERE restaurant_id = '47'"
)
```

S3 Select сокращает объём данных, перемещаемых из S3 в ваше приложение. Для больших файлов с выборочными запросами это может дать снижение объёма данных в 10–100 раз — и, поскольку аналитический инстанс работает в том же регионе, что и бакет, выигрыш не в счёте за передачу (передача S3-в-EC2 в том же регионе бесплатна): это вычисления, память и время, потраченные на скачивание и фильтрацию данных, которые вы сразу выбрасываете.

**CloudFront: скидка на передачу данных**

Вот контринтуитивный факт: обслуживание данных через CloudFront, как правило, дешевле, чем обслуживание напрямую с EC2 или S3.

**Прямое EC2 в интернет**: $0,09/ГБ
**CloudFront в интернет**: $0,085/ГБ (немного дешевле)

Но реальная экономия не в ставке за ГБ — а в том, что CloudFront кэширует данные на граничных серверах. Если 1 000 пользователей запрашивают одну и ту же фотографию меню:

- **Без CloudFront**: 1 000 запросов покидают S3 напрямую в интернет × размер фото × $0,09/ГБ
- **С CloudFront**: клиенты получают фото с граничного сервера по тарифу CloudFront ($0,085/ГБ), а заполнение кэша — CloudFront, забирающий из S3 на 1 промахе — **бесплатно** (AWS не взимает плату за передачу от источника к CloudFront; вы платите только за GET-запросы к источнику)

Для Nimbus с 83% частотой попаданий в кэш (из главы 13) 83% запросов вообще никогда не касались источника — меньше запросов к источнику, меньше нагрузки на источник, и каждый байт тарифицируется по граничной ставке вместо интернет-ставки S3.

— CloudFront — это не только CDN для производительности, — сказал Том. — Это также оптимизация затрат на передачу данных.

## Преимущества и ограничения

**Затраты NAT Gateway**:

- Большие объёмы данных через NAT Gateway быстро накапливаются
- VPC Endpoints полностью устраняют часть затрат NAT
- Проверьте, какие сервисы вызывают ваши частные инстансы и доступны ли для них эндпоинты

**CloudFront для оптимизации затрат**:

- Частота попаданий в кэш напрямую определяет экономию
- Высокая частота попаданий = меньше запросов к источнику и меньше нагрузки на источник, плюс больше байт тарифицируется по более дешёвой ставке CloudFront на стороне зрителя (передача от источника AWS к CloudFront вообще не тарифицируется)
- Пропускайте всю доставку статических ресурсов через CloudFront

**Компромиссы кросс-AZ**:

- Устранение кросс-AZ трафика обычно требует архитектурных изменений, которые стоят дороже экономии
- Тщательно рассчитывайте перед оптимизацией

**S3 Select** (legacy — недоступен новым клиентам с 2024 года; используйте Athena вместо него. S3 Object Lambda теперь тоже legacy — закрыт для новых клиентов с ноября 2025 года, существующие нагрузки не затронуты):

- Принцип остаётся: фильтруйте на уровне хранилища вместо скачивания больших объектов S3 — экономия проявляется во времени вычислений, размере инстанса и длительности задания (передача S3 в том же регионе уже бесплатна)
- Не помогает, когда нужен весь файл

Том закрыл сетевой анализ числом на доске и более ясным пониманием того, чем на самом деле было последнее неизвестное в счёте. $847/мес. сетевых затрат не были загадкой некомпетентности — это была ожидаемая стоимость распределённой системы, которая охватывала зоны доступности, обслуживала глобальных пользователей и реплицировала данные между регионами. Большая часть этого стоила того, чтобы платить. Часть — нет. Ключевым продвижением была способность различать одно от другого.

- AWS взимает плату за **исходящие данные** (интернет: ~$0,09/ГБ), **кросс-AZ трафик** ($0,01/ГБ в каждом направлении), **кросс-региональный трафик** ($0,02–0,08/ГБ) и **обработку NAT Gateway** ($0,045/ГБ).
- **Входящие данные** бесплатны. **Трафик внутри AZ** бесплатен.
- **VPC Flow Logs** показывают, какие конкретные потоки трафика внутри ваших VPC генерируют каждую категорию затрат — необходимо для целенаправленной оптимизации. Потоки, которые никогда не пересекают сетевой интерфейс VPC (как CloudFront, забирающий из источника S3), нуждаются в собственных инструментах: стандартных логах CloudFront или логах доступа к серверу S3.
- **VPC Gateway Endpoints** (S3, DynamoDB): бесплатно. Устраняют затраты NAT Gateway для этих сервисов.
- **VPC Interface Endpoints**: тарифицируются за час плюс за ГБ. Дешевле NAT Gateway для высокообъёмных сервисов.
- **CloudFront** обслуживает данные по более низким тарифам, чем прямое EC2-в-интернет, и резко снижает объём передачи с источника через кэширование.
- Критический вопрос — не просто «сколько», а «преднамеренна ли эта затрата?» Непреднамеренные затраты — забытые тестовые конвейеры, маршрутизация по умолчанию через NAT — это там, где прячется реальная экономия.

## Советы к экзамену

*SAA-C03, область: проектирование архитектур с оптимизацией затрат (область 4, задача 4.4)*

- **NAT Gateway и VPC Endpoints**: сценарий экзамена: «EC2 в частной подсети часто вызывает S3/DynamoDB — как снизить затраты NAT Gateway?» → VPC Gateway Endpoints (бесплатно для S3 и DynamoDB).
- **Правила ценообразования на передачу данных**:
  - В AWS: бесплатно
  - Внутри AZ: бесплатно
  - Между AZ: платно
  - Между регионами: платно (по более высокой ставке)
  - Интернет: платно (значительная ставка)
- **CloudFront как оптимизация затрат**: «снизить затраты на передачу данных для глобальной доставки контента» → CloudFront. Уровень кэша снижает количество запросов к источнику.
- **S3 Transfer Acceleration**: ускоряет загрузки *в* S3 с использованием граничных серверов CloudFront. Выше стоимость, чем стандартный S3. Используйте для клиентов, загружающих большие файлы из географически удалённых мест.
- **Стоимость кросс-региональной репликации**: репликация данных между регионами влечёт затраты на передачу данных. Для S3 CRR вы платите и тариф на исходящую передачу, и стоимость запроса S3.
- **PrivateLink (VPC Interface Endpoints)**: обеспечивает частное подключение к сервисам AWS и к сервисам, размещённым другими клиентами AWS. Более безопасно, чем через NAT, часто дешевле для высокообъёмных сервисов. Точка безубыточности против обработки NAT Gateway — примерно 420 ГБ/мес. (с учётом собственной почасовой стоимости эндпоинта на AZ и при условии, что NAT Gateway остаётся для другого трафика).

## Упражнения

**Упражнение 1 — Воспроизведение**

Объясните разницу между VPC Gateway Endpoint и VPC Interface Endpoint. Для каких сервисов AWS доступен каждый и какова стоимость каждого?

*(Подсказка: Gateway Endpoints бесплатны, но только для S3 и DynamoDB. Interface Endpoints стоят за час, но работают для большинства других сервисов AWS.)*

**Упражнение 2 — Сценарий SAA-C03**

*Сценарий*: Приложение компании работает на EC2-инстансах в частных подсетях. Инстансы делают частые вызовы API к Amazon SQS и Amazon S3. В настоящее время весь трафик выходит через NAT Gateway. Команда хочет снизить затраты NAT Gateway. Безопасность данных должна сохраняться — никакой трафик не должен проходить через публичный интернет.

Какой подход НАИЛУЧШИМ образом отвечает этим требованиям с минимальными текущими затратами?

A) Создать Gateway Endpoint для SQS и Gateway Endpoint для S3  
B) Создать Interface Endpoints для SQS и S3  
C) Создать Interface Endpoint для SQS и Gateway Endpoint для S3  
D) Удалить NAT Gateway и использовать Internet Gateway напрямую для вызовов API

**Подсказка 1**: Gateway Endpoints доступны только для S3 и DynamoDB.

**Подсказка 2**: Interface Endpoints доступны для SQS и многих других сервисов (но стоят денег).

**Подсказка 3**: Internet Gateway в таблице маршрутизации частной подсети сделал бы её публичной — нарушая требования безопасности.

**Ответ**: C

**Пояснение**: S3 использует Gateway Endpoint (бесплатно). SQS требует Interface Endpoint (платный). Это сочетание устраняет затраты на обработку данных NAT Gateway для обоих сервисов. Весь трафик остаётся внутри частной сети AWS — без прохождения через публичный интернет.

**Почему не A?** Gateway Endpoints недоступны для SQS. Только S3 и DynamoDB имеют Gateway Endpoints.

**Почему не B?** Хотя это работает, использование Interface Endpoint для S3 (вместо бесплатного Gateway Endpoint) влечёт ненужные почасовые сборы. Всегда используйте бесплатный Gateway Endpoint для S3 и DynamoDB.

**Почему не D?** Добавление маршрута к Internet Gateway из частной подсети делает её публичной подсетью. EC2-инстансы в частных подсетях, как правило, не имеют Elastic IP, поэтому они не смогли бы фактически маршрутизировать через Internet Gateway без дополнительных изменений — и это подвергло бы их входящему интернет-трафику.
