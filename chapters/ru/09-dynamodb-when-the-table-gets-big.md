# Глава 9: Когда таблица становится большой

Кухня первого ресторана-партнёра Nimbus пахла чесноком и тёплым хлебом даже в десять утра. Майя была там на демонстрации, наблюдая, как повар проводит пальцем по приложению, чтобы зарегистрировать замену — рыба вместо креветок, временно закончились. Свайп произошёл. Меню обновилось. Клиент в другой части города увидел изменение в течение нескольких секунд.

Это казалось магией.

Вернувшись в офис, магия начала замедляться.

В таблице меню было 50 000 элементов.

Это были данные 287 ресторанов — число партнёров взлетело с сорока семи времён балансировщика нагрузки до почти трёхсот менее чем за год — каждый со своими ежедневными специальными предложениями, сезонными блюдами и региональными вариантами. У некоторых блюд были модификаторы — размер, уровень остроты, выбор белка. У некоторых были комбо-сделки, ссылающиеся на другие блюда. Некоторые появлялись в меню только в будни, или только во время обеда, или только в определённых городах.

SQL-запрос, извлекавший полное меню ресторана, раньше выполнялся за 200 миллисекунд.

Теперь это занимало четыре секунды.

Четыре секунды — это разница между тем, чтобы разместить заказ, и тем, чтобы закрыть приложение. Лео проанализировал план запроса. Том посмотрел на конфигурацию индексов. Прия увеличила количество реплик для чтения. Ни одно из этих действий не дало ощутимого результата.

И это изменило настроение в комнате.

**Первая попытка: больше индексов**

У Лео был открыт план запроса. Он внимательно проследил его.

«Проблема в этом соединении», — сказал он. «Когда мы извлекаем меню ресторана, мы соединяем таблицу menu_items с таблицей modifiers, затем с таблицей combos, затем с таблицей availability_windows. Четыре таблицы, три соединения, пятьдесят тысяч строк».

Он добавил индекс на `restaurantId` в каждую таблицу. Он снова запустил запрос. Две секунды. Лучше, но недостаточно хорошо.

Том где-то читал про хинты запросов. Он провёл целый день, настраивая их. Одна целая три десятых секунды. Всё ещё нехорошо.

«А что если денормализовать?» — спросил Лео. «Объединить модификаторы в JSON-столбец прямо в таблице menu_items. Меньше соединений».

Они попробовали. Ровно одна секунда. Это казалось прогрессом. Майя отправила сообщение партнёрам-ресторанам, что проблема со скоростью решена. Это был вторник.

К четвергу запрос снова вырос до 2,8 секунды. Их данные выросли. Подключилось больше ресторанов. Больше блюд на ресторан. Запрос, который казался решённым, решён не был.

«Подход с индексами справляется с сегодняшними данными», — сказала Прия. «Но мы добавляем сорок ресторанов в неделю. К следующему кварталу у нас будет вдвое больше элементов. Как тогда будет выглядеть запрос?»

«Минимум три секунды», — сказал Лео. «Вероятно, пять».

«Значит, мы выиграли себе несколько недель».

«Да».

Они посидели с этой мыслью. Исправление, у которого есть срок годности, — это не настоящее исправление.

**Вторая попытка: реплики для чтения**

Прия уже однажды увеличила количество реплик для чтения. Она попробовала снова — теперь две реплики, и приложение балансировало нагрузку между ними. Теория была здравой: распределить трафик чтения, каждая реплика выполняет меньше работы.

Это немного помогло. Пиковая нагрузка упала с 2,8 секунды до 2,2 секунды.

«Это потому, что узкое место — не количество чтений», — сказал Том, глядя на метрики базы данных. «Это сам запрос. Больше реплик означает больше серверов, выполняющих тот же медленный запрос. Запрос всё равно медленный».

«Во сколько это обходится в месяц?» — добавил он, потому что всегда спрашивал. «Две дополнительные реплики для чтения на db.r5.large — это около 350 долларов в месяц. За улучшение на две секунды».

Лео закрыл панель реплик.

«Значит, больше железа не исправляет плохой запрос», — сказала Майя.

«Когда проблема переживает индексирование, попытки кэширования и дополнительные реплики», — медленно сказал Лео, — «возможно, проблема не в конфигурации. Возможно, дело в форме системы».

Это стало началом более долгого разговора.

Проблема DBA — та, что раньше будила Лео по ночам, — была решена. Уровень управляемой базы данных был стабилен. Но стабильно не означало быстро, а быстро теперь было проблемой. Таблица меню начала упираться в пределы, которые не могли исправить дополнительные реплики. Сама форма данных была неправильной.*

**Проблема с подгонкой всего в таблицу**

Вот основное противоречие реляционных баз данных: они спроектированы для хранения *структурированных* данных в *фиксированных* формах.

Если бы каждый пункт меню имел одинаковые поля — название, цена, описание, категория — SQL был бы идеален. У вас была бы чистая таблица `menu_items`, строки для каждого элемента и запросы, которые имеют смысл.

Но реальные меню так не работают.

У одного блюда может быть модификатор «уровень остроты». У другого — «выбор белка». У третьего — вложенные комбо: «закажи семейный обед и получишь два основных блюда, два гарнира и напиток». Структура данных варьируется *для каждого элемента*.

В SQL у вас два варианта:

**Вариант 1**: Создать столбец для каждого возможного модификатора. Это приводит к очень широкой таблице, где большинство столбцов большую часть времени пусты.

**Вариант 2**: Создать отдельную таблицу модификаторов и соединить её с таблицей пунктов меню. Это работает, но сложные меню требуют нескольких соединений, и при пятидесяти тысячах элементов с большим объёмом чтения эти соединения становятся дорогостоящими.

«Есть третий вариант», — сказала Прия, которая тихо читала документацию в углу.

Она открыла новую вкладку. «Что если данным не нужно помещаться в таблицу?»

**Другой способ думать о данных**

Реляционные базы данных хранят данные как строки в таблицах. Каждая строка должна соответствовать схеме таблицы. Схема согласовывается заранее.

NoSQL-базы данных хранят данные по-другому. Один распространённый подход — *документная модель*: каждая запись хранится как самодостаточный документ (обычно JSON), и документы в одной коллекции не обязаны иметь одинаковые поля.

Пункт меню в документной модели может выглядеть так:

```json
{
  "itemId": "ITEM-001",
  "restaurantId": "NIMBUS-047",
  "name": "Shrimp Arepa",
  "price": 3200,
  "modifiers": [
    { "name": "Spice Level", "options": ["mild", "medium", "hot"] },
    { "name": "Protein", "options": ["shrimp", "fish", "mixed"] }
  ],
  "available": true,
  "seasonalUntil": "2024-03-31"
}
```

Другой элемент может выглядеть совершенно иначе:

```json
{
  "itemId": "ITEM-002",
  "restaurantId": "NIMBUS-047",
  "name": "Family Feast",
  "price": 9800,
  "includes": ["ITEM-010", "ITEM-011", "ITEM-015", "ITEM-020"],
  "servings": 4,
  "available": true
}
```

Разные формы. Одна коллекция. Никаких проблем.

«Значит, база данных больше похожа на картотечный шкаф, чем на таблицу», — сказала Майя.

«Именно», — сказала Прия. «Вы можете положить любой документ в любой ящик. Вам не нужно обрезать документ до фиксированного размера».

**Знакомьтесь: DynamoDB**

Amazon DynamoDB — это управляемый сервис NoSQL-баз данных AWS. Он хранит данные как элементы (не строки), а элементы собраны в таблицы (наименование похоже на SQL, но поведение отличается).

Каждый элемент в таблице DynamoDB должен иметь **первичный ключ**, который уникально его идентифицирует. Всё остальное гибко.

Первичный ключ может быть одной из двух форм:

**Только ключ раздела**: Единственный атрибут, который должен быть уникальным для всех элементов.

**Ключ раздела + ключ сортировки (составной первичный ключ)**: Два атрибута, которые *вместе* образуют уникальную комбинацию. Это позволяет иметь несколько элементов с одинаковым ключом раздела, различающихся ключом сортировки.

Для меню Nimbus:

- Ключ раздела: `restaurantId`
- Ключ сортировки: `itemId`

Это означает, что вы можете эффективно извлечь все элементы для конкретного ресторана — DynamoDB точно знает, в каком разделе искать.

«Почему это называется ключом раздела?» — спросил Том.

«А что, если кто-то попытается взломать?» — спросила Прия. «Если ключ раздела угадываем, может ли кто-то завалить один раздел записями и намеренно вызвать состояние горячей точки?»

«Да», — сказал Лео. «Это, по сути, вектор отказа в обслуживании для плохо спроектированных таблиц. Что является ещё одной причиной выбирать ключи с высокой кардинальностью».

Прия записала это.

**Как DynamoDB хранит данные внутри**

DynamoDB построен для горизонтального масштабирования до огромных размеров. Этого достигают через *разбиение на разделы* — данные разделяются по многим физическим машинам на основе ключа раздела.

Когда вы записываете элемент, DynamoDB хэширует значение ключа раздела и использует этот хэш для определения того, на каком физическом разделе (и, следовательно, на каком сервере) хранится элемент. Когда вы читаете элемент, DynamoDB делает то же вычисление, чтобы мгновенно его найти.

Думайте об этом как о почтовой системе. Если на каждом конверте есть почтовый индекс, почтовая служба не читает каждый конверт, чтобы выяснить, куда он принадлежит — она сортирует по почтовому индексу. DynamoDB сортирует по хэшу ключа раздела.

«Подождите — но *почему* мы делаем это именно так?» — спросила Майя. «Почему выбор ключа раздела так важен? Разве мы не можем просто взять что угодно?»

Это правильный вопрос. Ключ раздела — самое важное проектное решение в схеме DynamoDB. Вот почему:

Если вы выбираете ключ раздела с низкой кардинальностью — скажем, `available: true/false`, или `category: "main/side/drink"` — большинство ваших данных попадает на одни и те же несколько разделов. DynamoDB называет это «горячим разделом». Один сервер обрабатывает большинство трафика. Он перегружается. DynamoDB начинает ограничивать запросы. Пользователи начинают видеть ошибки.

- **Хорошо**: Высокая кардинальность, равномерно распределённые значения (`restaurantId` со многими ресторанами)
- **Плохо**: Низкая кардинальность (`true/false`, `category`) — большинство данных попадает на несколько разделов, создавая «горячие точки»

«Значит, если бы я использовал `available: true` в качестве ключа раздела», — медленно сказал Лео, — «все доступные элементы накапливались бы на одном разделе».

«И ваша база данных расплавилась бы во время ужинного наплыва», — подтвердила Прия.

Лео медленно закрыл ноутбук.

**Инцидент с горячим разделом**

Им не пришлось бы это воображать. Месяцами позже — на втором месяце работы с DynamoDB, до того как они по-настоящему усвоили правило, — они узнали бы это на горьком опыте.

Команда запустила новую функцию: значок «Рекомендуемые блюда». Партнёры-рестораны могли отметить до пяти блюд как рекомендуемые. Функция хранила атрибут `featured: true` на каждом блюде.

Лео решил, что было бы полезно запрашивать все рекомендуемые блюда по всем ресторанам — для виджета «популярные блюда» на главной странице. Он создал вторичный индекс для поддержки этого запроса. Индекс использовал `featured` в качестве ключа раздела.

«Всё будет нормально», — сказал он. «Сколько может быть рекомендуемых блюд?»

Около тысячи двухсот, распределённых по двумстам сорока ресторанам.

Но виджет «популярные блюда» загружался на каждой странице. Каждая загрузка страницы запускала запрос к индексу `featured`. Все тысяча двести элементов жили на двух разделах — `true` и `false`. Раздел `true` принимал каждый удар.

Вечер пятницы, ужинный наплыв. Восемь тысяч одновременных пользователей. Все загружают главную страницу.

Уровень ошибок DynamoDB подскочил до восемнадцати процентов. Некоторые пользователи получали пустой виджет популярного. Некоторые получали индикаторы загрузки. Некоторые получали ошибки, которые всплывали в процессе заказа.

Лео достал метрики. «Раздел индекса ограничивается», — сказал он. «Мы упираемся в предел пропускной способности одного раздела».

«Как?» — спросила Прия.

«У ключа `featured` всего два значения. Все тысяча двести рекомендуемых блюд живут на одном разделе. Каждая загрузка главной страницы бьёт по этому разделу».

Они отключили виджет популярного в течение трёх минут. Уровень ошибок упал до нуля.

«Значит, ключ раздела с двумя значениями ограничил нас в пятницу вечером», — сказал Том.

«Да», — сказал Лео.

«Во сколько нам это обошлось?»

«Около сорока минут ухудшенного опыта для восьми тысяч пользователей», — сказала Прия. «Влияние на выручку — вероятно, несколько сотен заказов».

Лео заменил индекс другим дизайном: выделенной таблицей DynamoDB под названием `featured_items` с `restaurantId` в качестве ключа раздела и запланированной Lambda — небольшим фрагментом кода, который AWS запускает для вас (глава 20), — которая обновляла её каждые пятнадцать минут из основной таблицы. Запрос превратился в сканирование маленькой изолированной таблицы вместо горячего раздела на основной.

«Сначала проектируйте паттерны доступа», — сказала Прия. «Потом выбирайте модель данных».

«Я знаю», — сказал Лео. «Теперь знаю».

**Чтение и запись в масштабе**

DynamoDB может обрабатывать миллионы запросов в секунду. Но ему нужно знать, какую мощность выделить.

Есть два режима ёмкости:

**Выделенная ёмкость**: Вы указываете, сколько единиц чтения и записи хотите. DynamoDB резервирует эту ёмкость для вас и ограничивает трафик, превышающий её. Предсказуемые затраты, более низкая цена за запрос.

Единицы имеют точные определения, и экзамен ожидает, что вы их знаете: одна **единица ёмкости чтения (Read Capacity Unit, RCU)** — это одно строго согласованное чтение в секунду элемента размером до 4 КБ — или два конечно-согласованных чтения того же размера. Одна **единица ёмкости записи (Write Capacity Unit, WCU)** — это одна запись в секунду элемента размером до 1 КБ. Более крупные элементы потребляют пропорционально больше: строго согласованное чтение элемента в 12 КБ стоит 3 RCU; запись элемента в 3 КБ стоит 3 WCU.

**Ёмкость по требованию**: DynamoDB автоматически масштабируется с вашим фактическим трафиком. Никакого регулярного планирования ёмкости не требуется. Более высокая цена за запрос и значительно проще в операционном плане, хотя внезапные пики, намного превышающие недавний паттерн трафика таблицы, всё равно могут вызвать ограничение, если они нарастают слишком быстро.

Для Nimbus меню читается значительно чаще, чем записывается. Клиент открывает приложение, просматривает меню — это много операций чтения. Партнёр-ресторан обновляет своё меню дважды в неделю — это редкие записи.

«Ёмкость по требованию имеет смысл пока», — сказал Том. «Мы ещё не знаем наших паттернов трафика. Лучше платить больше за запрос, чем недостаточно выделить и получить ограничения».

Нерешительная инфраструктурная мудрость. От Тома. Команда официально выросла.

«Во сколько это обходится в месяц?» — спросил Том, открывая калькулятор цен.

«При нашем текущем объёме чтения — около сорока тысяч чтений в день — по требованию выходит примерно двенадцать долларов в месяц», — сказал Лео. «Выделенная, если правильно настроить, ближе к четырём. Но нам пришлось бы устанавливать ёмкость вручную и рисковать ограничениями, если ошибёмся в догадках».

Том записал оба числа. Он всегда записывал числа.

**Согласованность: насколько свежи ваши данные?**

DynamoDB автоматически реплицирует данные по нескольким зонам доступности. Это отлично для долговечности, но это также означает, что вам нужно чётко думать о согласованности чтения.

Когда вы читаете из DynamoDB, у вас есть выбор:

**Конечно-согласованное чтение**: Это значение по умолчанию. Оно дешевле, и результат может кратко отставать от недавно завершённой записи.

**Строго согласованное чтение**: Для чтения из таблицы или локального вторичного индекса DynamoDB может вернуть последнее зафиксированное значение из успешных предыдущих записей. Это стоит больше мощности чтения и недоступно для глобальных вторичных индексов.

Для данных меню конечная согласованность нормальна. Пункт меню с задержкой в миллисекунду не имеет значения.

Для данных подтверждения заказа — «был ли размещён этот заказ?» — вам нужна строгая согласованность. Клиент не должен видеть сообщение «попробуйте ещё раз», когда его заказ только что был сохранён.

«Это как разница между проверкой баланса вашего счёта в приложении и звонком в банк напрямую», — сказала Майя. «В приложении данные могут быть на тридцать секунд позади. Звонок всегда актуален».

Возможно, вы задаётесь вопросом: если DynamoDB автоматически реплицирует данные по нескольким зонам доступности, почему режим согласованности вообще важен? Вот ответ: репликация занимает небольшое, но ненулевое время — обычно миллисекунды. Конечно-согласованное чтение может быть обслужено репликой, которая ещё не получила последнюю запись. Строго согласованное чтение всегда обращается к первичной копии данных. Для большинства сценариев использования (пункты меню, каталоги товаров, профили пользователей) задержка незаметна. Для сценариев, где корректность важна в момент чтения (подтверждение платежа, доступность товара на складе), вам нужна строгая согласованность.

**Вторичные индексы: запросы за пределами первичного ключа**

Что если вам нужно получить доступ к данным иначе, чем позволяет первичный ключ?

DynamoDB поддерживает **вторичные индексы** — альтернативные ключи, которые позволяют запрашивать те же данные по разным атрибутам.

**Локальный вторичный индекс (Local Secondary Index, LSI)**: Использует тот же ключ раздела, что и таблица, но другой ключ сортировки. Должен быть определён при создании таблицы и не может быть добавлен позже. Делит выделенную ёмкость таблицы. Поскольку LSI делят раздел, они поддерживают строго согласованные чтения.

**Глобальный вторичный индекс (Global Secondary Index, GSI)**: Полностью отдельный индекс со своим собственным ключом раздела и ключом сортировки — отличными от первичного ключа таблицы. Может быть добавлен или удалён после существования таблицы, что даёт вам гибкость. Имеет собственные настройки выделенной ёмкости, отдельные от таблицы.

Для Nimbus: если бы им нужно было запрашивать элементы по диапазону цен, GSI мог бы это поддержать — но с одним правилом в уме: ключ раздела принимает только сравнения на *равенство*, поэтому `price` (по которому вы хотите делать диапазон) должен быть **ключом сортировки**, с группирующим атрибутом, таким как категория или `cuisineType#region`, в качестве ключа раздела GSI. Именно такой индекс построен в разборе ниже.

Если вы выбираете LSI, вы получаете строгую согласованность и общую ёмкость, но вы заперты в этом дизайне при создании таблицы; если вы выбираете GSI, вы получаете гибкость добавить его позже и независимое масштабирование, но теряете возможность делать строго согласованные чтения по индексу.

---

**Разбор запроса к GSI**

Прия прошлась по конкретному примеру. Nimbus хотел поддержать функцию «просмотр по кухне»: показать все доступные блюда определённого типа кухни по всем ресторанам-партнёрам.

В основной таблице `restaurantId` является ключом раздела, а `itemId` — ключом сортировки. Вы не можете эффективно запросить «все элементы с cuisineType = Colombian» — это потребовало бы сканирования по каждому разделу.

Они создали GSI:

- Ключ раздела GSI: `cuisineType#region` (например, "Colombian#NYC", "Mexican#Chicago")
- Ключ сортировки GSI: `price`

GSI дублирует проекцию каждого элемента — только поля, необходимые для страницы просмотра, — в хранилище индекса. Теперь запрос к GSI с `cuisineType#region = "Colombian#NYC"` идёт напрямую в этот раздел индекса.

«Почему бы просто не использовать `cuisineType` отдельно?» — спросил Лео.

«Потому что cuisineType отдельно имеет низкую кардинальность», — сказала Прия. «Colombian, Mexican, Thai — всего двадцать значений. Снова горячие разделы. Добавление региона даёт нам Colombian#NYC, Colombian#Chicago, Colombian#LA. Больше разделов, лучше распределение».

«Это выглядит немного хакерски».

«Это стандартный паттерн DynamoDB. Он называется шардинг ключа раздела. Иногда приходится работать в рамках инструмента».

Запрос к GSI в коде выглядел так:

```python
response = dynamodb.query(
    TableName='menu',
    IndexName='cuisineType-price-index',
    KeyConditionExpression='#ct = :ct AND price BETWEEN :lo AND :hi',
    ExpressionAttributeNames={'#ct': 'cuisineType#region'},
    ExpressionAttributeValues={
        ':ct': {'S': 'Colombian#NYC'},
        ':lo': {'N': '1000'},
        ':hi': {'N': '2500'}
    }
)
```

Это возвращало все колумбийские блюда в Нью-Йорке по цене от $10 до $25, отсортированные по цене, примерно за 4 миллисекунды.

«Это быстрее старого SQL-запроса в тысячу раз», — сказал Лео.

«Потому что он касается только одного раздела одного индекса», — подтвердила Прия. «А не сканирует каждую строку в соединённой таблице».

**DynamoDB Streams: реакция на изменения**

«Мы думали о том, что происходит, когда пункт меню обновляется?» — спросила Прия однажды утром. «Партнёр-ресторан меняет цену. Нам нужно обновить поисковый индекс. Нам нужно инвалидировать запись в ElastiCache» — сервисе кэширования, с которым мы познакомимся в следующей главе, — «и нам нужно записать изменение для нашего аналитического конвейера».

«Мы могли бы делать всё это в обработчике API», — сказал Лео. «Когда происходит запись, запускать все нижестоящие обновления».

«А если одно из них не сработает?»

«Тогда... мы повторяем попытку».

«Что если экземпляр EC2 падает после записи, но до нижестоящих обновлений? Данные сохранены, но ничто не знает об изменении».

Лео задумался об этом.

«Нам нужно, чтобы обновление было гарантировано», — сказал он. «Даже если наш код приложения падает на полпути».

Это то, что решает **DynamoDB Streams**.

DynamoDB Streams захватывает упорядоченный во времени журнал каждой модификации элемента в таблице DynamoDB. Каждая вставка, обновление и удаление записываются в поток как событие. Поток хранит события в течение 24 часов.

Вы можете присоединить функцию Lambda к потоку. Каждый раз, когда элемент меняется, функция Lambda вызывается с состоянием элемента до и после. Lambda затем может:

- Обновить поисковый индекс (OpenSearch)
- Инвалидировать запись кэша в ElastiCache
- Отправить уведомление в другую систему
- Питать аналитический конвейер
- Реплицировать изменение в другую таблицу или базу данных

Критическое различие: Streams отделяют запись от нижестоящих эффектов. Запись в DynamoDB успешна независимо от того, успешна ли Lambda. Если Lambda не срабатывает, DynamoDB повторяет её. Если приложение падает после записи, событие потока всё равно там — Lambda обработает его, когда всё восстановится.

«Значит, мы пишем в DynamoDB», — медленно сказал Лео, — «и DynamoDB гарантирует, что нижестоящая обработка в конечном итоге произойдёт, даже если мы упадём».

«Именно», — сказала Прия. «Это разница между надеждой, что все ваши побочные эффекты выполнятся, и тем, чтобы база данных их гарантировала».

Для Nimbus они подключили DynamoDB Streams на таблице меню к Lambda, которая инвалидировала записи ElastiCache, когда пункты меню менялись. Кэш оставался согласованным с базой данных автоматически, без какого-либо кода приложения, управляющего инвалидацией.

«Во сколько обходится Streams?» — спросил Том.

«Вы платите за чтение из потока — каждый вызов Lambda читает из него. При нашем объёме, вероятно, два-три доллара в месяц».

Том одобрил это без дальнейших вопросов. Он научился понимать, когда два доллара в месяц того стоят.

**Компромисс: чего не может DynamoDB**

NoSQL не лучше SQL в абсолютном смысле. Это другой инструмент для другой работы.

Что DynamoDB теряет:

**Гибкие запросы**: В SQL вы можете фильтровать и сортировать по любому столбцу. В DynamoDB вы можете эффективно запрашивать только по первичному ключу. Запрос по произвольным полям требует *сканирования* (чтения каждого элемента в таблице), что дорого и медленно в масштабе.

**Соединения**: DynamoDB не делает соединений. Если вам нужны данные из двух таблиц, вы делаете два отдельных чтения в коде приложения.

**Транзакции**: DynamoDB поддерживает транзакции, но реляционные базы данных по-прежнему являются более естественным выбором для многих многосущностных рабочих процессов, систем с интенсивными отчётами и дизайнов с интенсивными соединениями.

**Знакомость**: Десятилетия инструментария SQL, навыков и ментальных моделей не переносятся напрямую.

В чём DynamoDB превосходит:

- Паттерны доступа по ключу-значению и документу
- Массивный масштаб (задержка в однозначном числе миллисекунд при любом размере)
- Бессерверный, никакого управления инфраструктурой
- Автоматическое масштабирование, репликация Multi-AZ, резервные копии
- Предсказуемая производительность независимо от объёма данных

«Значит правило», — сказала Майя, — «использовать DynamoDB, когда вы точно знаете, *как* вы будете получать доступ к данным. Использовать SQL, когда ещё не знаете».

Прия кивнула. «Сначала спроектируйте паттерны доступа. Потом выбирайте базу данных».

Это одна из самых зрелых вещей, которые может произвести разговор о базах данных.

**Когда DynamoDB — неправильный выбор**

У Тома, который взял на себя модуль финансовой отчётности, был вопрос.

«Мы разрабатываем финансовую отчётность», — сказал он. «Ежемесячные сводки выручки по ресторанам, налоговые расчёты, история счетов. Можем ли мы и это положить в DynamoDB?»

Команда переглянулась.

«Подождите — но *почему* мы делали бы это именно так?» — спросила Майя, прежде чем Прия успела.

Прия улыбнулась. Майя перенимала привычку.

«Проведите нас по запросам», — сказала Прия Тому.

Он открыл спецификацию. «Нам нужно: общая выручка по ресторану, сгруппированная по неделям. Самые продаваемые блюда по количеству заказов, по всем ресторанам. Выручка с разбивкой по типу кухни. Средняя стоимость заказа по городу. Сравнение год к году для отчётности партнёрам».

Лео прочитал список. «Каждый из них — это агрегация. Сумма, группировка, среднее, сравнение».

«У DynamoDB нет функций агрегации», — сказала Прия. «Никакого GROUP BY. Никакого SUM. Никакого AVG. Чтобы ответить на „общая выручка по ресторану за эту неделю“, вам пришлось бы просканировать каждый заказ за неделю, загрузить всё в память приложения и вычислить это самим».

«Звучит плохо», — сказал Том.

«В нашем масштабе это десятки тысяч записей, загружаемых в память на каждый запрос отчёта. Это было бы медленно и дорого. И каждый раз, добавляя новое требование к отчёту, мы писали бы новый код сканирования и вычисления».

«Так что мы используем?»

«Для финансовой отчётности? RDS. PostgreSQL с правильными индексами. Запросы, которые вы описали, — это именно то, для чего был спроектирован SQL. Они были бы десятью строками SQL. Они были бы двумястами строками кода сканирования DynamoDB».

DynamoDB неправильный выбор, когда:

- Вы не знаете ваши паттерны доступа заранее (отчётность по своей природе исследовательская)
- Вам нужны агрегации (SUM, GROUP BY, COUNT) по большим наборам данных
- Ваши данные имеют сложные отношения, и вам нужны соединения
- Вам нужна гибкость ad-hoc запросов — задавать вопросы, о которых вы ещё не думали
- Ваши данные имеют фундаментально реляционную структуру, которая не отображается естественно на ключ-значение

«Значит, выбор не „новая технология лучше“», — сказала Майя.

«Выбор — „какую форму имеют ваши данные и как вы будете к ним обращаться“», — подтвердила Прия. «DynamoDB действительно лучше для меню. Он был бы действительно хуже для финансовых отчётов. Оба утверждения верны одновременно».

Том построил финансовую отчётность на PostgreSQL. Первый запрос GROUP BY, который он написал, вернулся за 80 миллисекунд. Ему не пришлось написать ни единой строки кода сканирования.

---

**Когда что использовать**

| Ситуация                                              | Выбор                   |
|-------------------------------------------------------|-------------------------|
| Структурированные данные, сложные запросы, отчётность | RDS (PostgreSQL, MySQL) |
| Гибкие формы данных, доступ по ключу, массивный масштаб | DynamoDB              |
| Интенсивная запись со сложными отношениями            | RDS                     |
| Интенсивное чтение с предсказуемыми паттернами доступа | DynamoDB               |
| Нужны соединения и агрегаты                           | RDS                     |
| Нужна задержка в миллисекунды при миллионах запросов/сек | DynamoDB             |
| Транзакции по нескольким сущностям                    | RDS (обычно)            |
| Бессерверный / непредсказуемые пики трафика           | DynamoDB по требованию  |
| Финансовая отчётность, ad-hoc аналитика               | RDS или хранилище данных |
| Event sourcing, захват изменений, обработка в реальном времени | DynamoDB + Streams |

Неправильный ответ — всегда «всегда использовать одно или другое». Nimbus в итоге использовал оба: RDS для истории заказов и финансовых записей (структурированные, реляционные, требует отчётности), DynamoDB для меню (гибкая схема, большой объём чтения, доступ по ID ресторана).

## Правильная база данных для правильной нагрузки

Перенесёмся на шесть месяцев вперёд — уже после того, как миграция на DynamoDB устаканилась, — и у Nimbus на доске было три новых проекта. Майя провела команду по ним одним вторничным утром.

«Первый: рекомендательный движок. Мы хотим показывать клиентам блюда, которые они, вероятно, закажут, на основе их истории и того, что заказывали люди со схожими вкусами. Второй: мы переносим данные меню для поддержки более богатого контента — полные документы меню в JSON, разная структура для каждого ресторана, гибкая схема. Третий: мы вот-вот закроем сделку по приобретению Barato, и их команда данных управляет кластером Cassandra для данных о поведении клиентов. Они хотят перенести это в AWS без переписывания своих конвейеров».

Три проекта. Три очень разных требования к данным. Ни один из них не был очевидным кандидатом на DynamoDB.

«Им всем нужны разные базы данных», — сказала Прия.

«У нас есть DynamoDB», — сказал Лео.

«У нас есть право выбрать правильный инструмент», — сказала Прия.

**Amazon DocumentDB: когда ваша нагрузка говорит на MongoDB**

Второй проект — богатые JSON-документы меню с гибкими схемами для каждого ресторана — описывал документную базу данных. Nimbus уже использовал гибкую схему DynamoDB для меню, но по мере того как команда строила более сложные функции меню (вложенные модификаторы, ценообразование по времени, сложные структуры комбо), модель запросов DynamoDB показывала свои пределы. Команда хотела более богатых документных запросов: найти все пункты меню, где вложенный модификатор содержит конкретную опцию, фильтровать по произвольным полям внутри JSON-структуры.

«Это паттерн документной базы данных», — сказала Прия. «MongoDB».

«Мы могли бы запустить MongoDB на EC2», — предложил Лео.

«Или мы могли бы использовать DocumentDB», — сказала Прия.

**Amazon DocumentDB** — это управляемая документная база данных, совместимая с MongoDB. Она хранит данные как JSON-подобные документы с гибкими схемами — разные документы в одной коллекции могут иметь разные поля. DocumentDB поддерживает язык запросов, API и драйверы MongoDB. Если ваша нагрузка в настоящее время работает на MongoDB, DocumentDB говорит на том же языке. Путь миграции — это перемещение строки подключения, а не переписывание приложения.

DocumentDB полностью управляемая: никакого патчинга, автоматические резервные копии, высокая доступность Multi-AZ, реплики для чтения и хранилище, которое автоматически растёт по мере роста ваших данных.

«Значит, мы мигрируем меню в DocumentDB», — сказал Лео. «И запросы, которые у нас уже есть в синтаксисе MongoDB, просто работают?»

«С небольшим тестированием совместимости, да», — подтвердила Прия. «DocumentDB поддерживает большинство API запросов MongoDB. Проверьте матрицу совместимости, прежде чем предполагать полное покрытие, но для документных запросов и агрегаций это просто».

Экзаменационный сигнал для DocumentDB прост: **«совместимый с MongoDB»** или **«документное хранилище»**. Если сценарий упоминает MongoDB или документно-ориентированные данные, DocumentDB — это управляемый ответ AWS.

**Amazon Neptune: когда отношения — это и есть данные**

Рекомендательный движок был более сложной проблемой.

Вопрос был не «что заказал этот клиент?» — это был простой поиск в DynamoDB. Вопрос был: «у каких клиентов профили вкусов схожи с этим клиентом, и какие блюда понравились этим клиентам, которые этот клиент ещё не пробовал?»

Это графовая проблема. Модель данных — это не таблица строк или коллекция документов. Это сеть отношений: клиенты, связанные с блюдами (заказаны, оценены, просмотрены), блюда, связанные с ресторанами и типами кухни, рестораны, связанные с районами и городами. Рекомендация не в точках данных — она в путях между ними.

«Нам нужна графовая база данных», — сказала Прия.

**Amazon Neptune** — это полностью управляемая графовая база данных. Она поддерживает две графовые модели: **граф свойств** (запрашивается языком обхода Gremlin) и **RDF** (запрашивается SPARQL). Вы выбираете на основе вашего существующего графового стека или предпочтения команды; обе работают на одной и той же инфраструктуре Neptune.

Графовые базы данных специально созданы для нагрузок, где отношения между точками данных так же важны, как сами данные: социальные сети (кто с кем связан), рекомендательные движки (что понравилось похожим пользователям), обнаружение мошенничества (какие транзакции разделяют подозрительные паттерны между счетами) и графы знаний (как связаны концепции).

Для рекомендательного движка Nimbus: клиенты и блюда стали узлами в Neptune. События заказов стали рёбрами. Обход Gremlin мог найти, в одном запросе, все блюда, которые клиенты со схожими историями заказов высоко оценили, отсортированные по силе связи — без сложных цепочек JOIN, которые потребовались бы в реляционной базе данных, или множественных запросов туда-обратно, которые понадобились бы в DynamoDB.

Экзаменационный сигнал для Neptune: **«социальная сеть», «рекомендательный движок», «граф знаний», «обнаружение мошенничества»** или **«обход графа»**. Если сценарий описывает данные, где связи имеют такое же значение, как сами данные, Neptune — это ответ.

**Amazon Keyspaces: Cassandra без операций**

Приобретение Barato привнесло в картину кластер Cassandra. Cassandra — это широкостолбцовая NoSQL-база данных, спроектированная для очень высокой пропускной способности записи и горизонтальной масштабируемости, обычно используемая для временных рядов, журналов активности пользователей и телеметрии IoT. Команда данных Barato использовала её для отслеживания поведения клиентов: какие элементы были просмотрены, какие добавлены в корзину, какие брошены.

Миграция Cassandra в AWS имела два варианта: запустить её на EC2 (операционные накладные расходы на управление кластером, обновления, масштабирование) или использовать управляемый вариант.

«Amazon Keyspaces», — сказала Прия.

**Amazon Keyspaces** — это бессерверная управляемая база данных, совместимая с Cassandra. Она поддерживает язык запросов Cassandra (CQL) — тот же язык запросов, который уже использовали конвейеры Barato. Как DocumentDB для MongoDB, Keyspaces — это управляемый путь: оставьте код приложения как есть, направьте его на эндпоинт Keyspaces вместо самостоятельно управляемого кластера и позвольте AWS управлять инфраструктурой.

Keyspaces масштабируется автоматически с трафиком, не требует планирования ёмкости и является бессерверной — вы платите за чтения и записи, которые фактически выполняете. Для данных отслеживания поведения Barato это была правильная модель: чрезвычайно переменный объём (ужинный наплыв против 3 утра), широкостолбцовая схема, высокая пропускная способность записи.

Экзаменационный сигнал: **«совместимый с Cassandra», «широкостолбцовый», «CQL»** или **«нагрузка Cassandra»**.

**Выбор правильной базы данных: справочная таблица**

К этому моменту в истории ландшафт баз данных Nimbus выглядел совершенно иначе, чем в седьмой главе. Правильный инструмент для каждой нагрузки:

| Триггерная фраза | База данных |
|---|---|
| «Совместимый с MongoDB» или «документное хранилище» | DocumentDB |
| «Графовые отношения», «социальная сеть», «рекомендательный движок» | Neptune |
| «Совместимый с Cassandra» или «широкостолбцовый» | Keyspaces |
| «Ключ-значение в любом масштабе», «задержка в однозначное число миллисекунд» | DynamoDB |
| «Реляционный + бессерверный», «автомасштабируемый SQL» | Aurora Serverless |
| «Структурированные данные, сложные запросы, отчётность» | RDS (PostgreSQL, MySQL) |

«Это будет продолжать расти?» — спросил Лео, глядя на список.

«Да», — сказала Майя. «Потому что у разных проблем разные формы. И использование неправильной формы стоит вам либо производительности, либо времени разработчиков, либо и того, и другого».

«Правильный вопрос не „какую базу данных нам использовать“», — добавила Прия. «Это „какую форму имеют наши данные и как мы будем к ним обращаться?“ База данных следует из ответа».

Это была самая важная вещь, которую она сказала о базах данных за два года.

## Сильные стороны и ограничения

**Почему DynamoDB мощный**:

- Задержка в однозначном числе миллисекунд при любом масштабе
- Полностью управляемый — никакого патчинга, настройки репликации, окон обслуживания
- Автоматическая репликация Multi-AZ (долговечность встроена)
- Масштабирование по требованию — нулевое планирование ёмкости
- Нативная интеграция с Lambda, API Gateway, Streams
- Восстановление на момент времени (аналогично автоматическим резервным копиям RDS)
- DynamoDB Streams — захват каждого изменения как события (полезно для обработки в реальном времени)

**Где DynamoDB усложняется**:

- Проектирование паттернов доступа обязательно — ошибки дорого исправлять
- Сложные запросы требуют вторичных индексов (добавляет стоимость и сложность)
- Сканирования дороги — избегайте их в продакшене
- «Ограничение размера элемента» — 400 КБ — большие элементы нуждаются в другом хранилище
- Ценообразование может удивить, если вы не понимаете стоимость единиц чтения/записи
- Горячие разделы — тихие убийцы — никаких ошибок, пока не начнётся ограничение

## Итоги

Редизайн схемы занял два дня и много места на доске. Выбор NoSQL-базы данных — это не просто техническое решение, оно полностью меняет то, как вы думаете о данных. Но результатом стала таблица меню, которая могла расти до любого размера, не замедляясь. Не менее важно: команда узнала, где находятся границы DynamoDB, и к каким специализированным базам данных обращаться, когда проблема меняет форму.

- DynamoDB — это управляемый сервис NoSQL-баз данных AWS. Элементы — это гибкие документы, без фиксированной схемы. Каждый элемент должен иметь **первичный ключ**: ключ раздела отдельно или ключ раздела + ключ сортировки. Выбирайте ключ раздела для равномерного распределения — горячие разделы вызывают ограничение.
- **По требованию** ёмкость автомасштабируется; **выделенная** ёмкость дешевле для предсказуемого трафика. **Конечно-согласованные** чтения дешевле; **строго согласованные** чтения всегда актуальны, но недоступны для GSI.
- **DynamoDB Streams** захватывают изменения на уровне элементов в реальном времени — используйте их для управления инвалидацией кэша, обновлений поискового индекса и аналитических конвейеров.
- DynamoDB — неправильный выбор для отчётности, сложных соединений и ad-hoc запросов — используйте RDS для них.
- **DocumentDB** (совместимый с MongoDB), **Neptune** (графовая база данных) и **Keyspaces** (совместимый с Cassandra) — это управляемые AWS-альтернативы для нагрузок, которые не вписываются в модель ключ-значение DynamoDB.

## Советы по экзамену

*Домен SAA-C03: Проектирование высокопроизводительных архитектур (Домен 3, Задача 3.3)*

- Знайте правила ключа раздела: **высокая кардинальность, равномерное распределение**. Горячие разделы — распространённая ловушка экзамена.
- **По требованию vs выделенная**: по требованию для непредсказуемого трафика; выделенная (с Auto Scaling) для предсказуемых нагрузок.
- **DynamoDB Streams**: фиксирует изменения на уровне элементов в реальном времени. Распространённый сценарий экзамена: «запустить функцию Lambda при изменении записи».
- **Global Tables**: мульти-региональная, мульти-активная репликация для глобально распределённых приложений и сценариев аварийного восстановления. На экзамене это сильный сигнал, когда нагрузка требует локальных чтений и записей в более чем одном регионе.
- **DynamoDB TTL (Time to Live)**: установите атрибут с меткой времени истечения на элементах, и DynamoDB удаляет их автоматически после истечения — **бесплатно**, не потребляя ёмкость записи. Триггер экзамена: «данные сессии/временные элементы должны удаляться автоматически после N часов с наименьшими затратами» → TTL, никогда не запланированное сканирование Lambda. Истёкшие элементы могут также поступать в DynamoDB Streams для архивации.
- **DAX (DynamoDB Accelerator)**: уровень кэширования в памяти для DynamoDB. Уменьшает задержку чтения от миллисекунд до микросекунд. Экзамен использует это, когда реплики для чтения RDS не помогут (потому что это кэш, специфичный для DynamoDB).
- **Составной первичный ключ**: ключ раздела + ключ сортировки позволяет гибкие запросы внутри раздела. Пример: получить все заказы для клиента между двумя датами — `customerId` является ключом раздела, `orderDate` — ключом сортировки.
- **GSI vs LSI**: GSI можно добавить после создания таблицы; LSI — нельзя. LSI поддерживает строго согласованные чтения; GSI — нет. LSI делит ёмкость таблицы; GSI имеет свою собственную.
- Знайте, когда НЕ использовать DynamoDB: сложные соединения, ad-hoc отчётность, транзакции по нескольким сущностям → RDS обычно является ответом.
- **Выбор специализированной базы данных** — экзамен часто представляет сценарий и спрашивает, какая база данных подходит. Используйте это как быстрый справочник: «совместимый с MongoDB» → DocumentDB. «Граф/социальная сеть/рекомендательный движок/граф знаний» → Neptune. «Совместимый с Cassandra/широкостолбцовый» → Keyspaces. «Ключ-значение в любом масштабе/миллисекундная задержка» → DynamoDB. «Реляционный/сложные запросы/отчётность» → RDS или Aurora.

**Упражнение 2 — Сценарий SAA-C03**

*Сценарий*: Глобальная игровая компания хранит профили игроков в DynamoDB. Каждый профиль включает такие поля, как имя пользователя, уровень, достижения и инвентарь. У некоторых игроков 10 предметов инвентаря; у других — несколько сотен — профили различаются по форме, но каждый остаётся комфортно ниже ограничения размера элемента DynamoDB в 400 КБ. Компании нужна задержка чтения в однозначное число миллисекунд для поиска профилей во время активного геймплея.

Какой подход проектирования НАИЛУЧШИМ образом поддерживает это требование?

A) Использовать DynamoDB с `playerId` в качестве ключа раздела и хранить весь профиль как один элемент  
B) Перейти на RDS Aurora с репликами для чтения в каждом регионе  
C) Использовать DynamoDB с `level` в качестве ключа раздела для группировки игроков схожего уровня  
D) Использовать ElastiCache перед RDS для достижения суб-миллисекундной задержки

**Подсказка 1**: Паттерн доступа — «найти конкретного игрока по ID». Какой ключ делает это эффективным?

**Подсказка 2**: Один вариант создаёт ужасную горячую точку. Какой атрибут имеет очень низкую кардинальность?

**Подсказка 3**: DynamoDB уже нативно обеспечивает задержку в однозначное число миллисекунд.

**Ответ**: A

**Объяснение**: Использование `playerId` в качестве ключа раздела равномерно распределяет данные по разделам и обеспечивает мгновенные поиски по ID игрока — именно тот паттерн доступа, который описан. Гибкая документная модель DynamoDB обрабатывает разные размеры инвентаря без изменений схемы.

**Почему не B?** RDS Aurora с репликами для чтения добавляет сложность и всё равно не является первым естественным выбором для этого типа поиска профиля по ключу в игровом масштабе.

**Почему не C?** Использование `level` в качестве ключа раздела создаёт серьёзные горячие точки — большинство трафика идёт на уровень 1 (новые игроки) или максимальный уровень (активные ветераны), оставляя другие разделы простаивать.

**Почему не D?** Вопрос описывает DynamoDB, а не RDS. Добавление ElastiCache перед RDS вводит два новых сервиса, когда DynamoDB один решает проблему.
