# Глава 9: Когда таблица становится большой

В таблице меню было 50 000 элементов.

Это были данные 287 ресторанов, каждый из которых имел ежедневные специальные предложения, сезонные блюда и региональные варианты. Некоторые блюда имели модификаторы — размер, уровень остроты, выбор белка. Некоторые были комбо-сделками, ссылающимися на другие блюда. Некоторые появлялись в меню только в будни, или только во время обеда, или только в определённых городах.

SQL-запрос, извлекавший полное меню ресторана, раньше выполнялся за 200 миллисекунд.

Теперь это занимало четыре секунды.

Четыре секунды — это разница между тем, чтобы разместить заказ, и тем, чтобы закрыть приложение. Лео проанализировал план запроса. Том посмотрел на конфигурацию индексов. Прия увеличила количество реплик для чтения. Ни одно из этих действий не дало ощутимого результата.

И это изменило настроение в комнате.

Когда проблема переживает индексирование, попытки кэширования и ещё одну реплику — люди перестают думать, что решение будет умным.

Иногда решение в том, что форма системы неправильная.

«Проблема», — сказал Лео, — «в форме данных. SQL хочет, чтобы всё было в строках и столбцах. У нашего меню нет фиксированной формы».

Это стало началом более долгого разговора.

**Проблема с подгонкой всего в таблицу**

Вот основное противоречие реляционных баз данных: они спроектированы для хранения *структурированных* данных в *фиксированных* формах.

Если бы каждый пункт меню имел одинаковые поля — название, цена, описание, категория — SQL был бы идеален. У вас была бы чистая таблица `menu_items`, строки для каждого элемента и запросы, которые имеют смысл.

Но реальные меню так не работают.

У одного блюда может быть модификатор «уровень остроты». У другого — «выбор белка». У третьего — вложенные комбо: «закажи семейный обед и получишь два основных блюда, два гарнира и напиток». Структура данных варьируется *для каждого элемента*.

В SQL у вас два варианта:

**Вариант 1**: Создать столбец для каждого возможного модификатора. Это приводит к очень широкой таблице, где большинство столбцов большую часть времени пусты.

**Вариант 2**: Создать отдельную таблицу модификаторов и соединить её с таблицей пунктов меню. Это работает, но сложные меню требуют нескольких соединений, и при пятидесяти тысячах элементов с большим объёмом чтения эти соединения становятся дорогостоящими.

«Есть третий вариант», — сказала Прия, которая тихо читала документацию в углу.

Она открыла новую вкладку. «Что если данным не нужно помещаться в таблицу?»

**Другой способ думать о данных**

Реляционные базы данных хранят данные как строки в таблицах. Каждая строка должна соответствовать схеме таблицы. Схема согласовывается заранее.

NoSQL-базы данных хранят данные по-другому. Один распространённый подход — *документная модель*: каждая запись хранится как самодостаточный документ (обычно JSON), и документы в одной коллекции не обязаны иметь одинаковые поля.

Пункт меню в документной модели может выглядеть так:

```json
{
  "itemId": "ITEM-001",
  "restaurantId": "NIMBUS-047",
  "name": "Креветочная арепа",
  "price": 3200,
  "modifiers": [
    { "name": "Уровень остроты", "options": ["мягкий", "средний", "острый"] },
    { "name": "Белок", "options": ["креветки", "рыба", "ассорти"] }
  ],
  "available": true,
  "seasonalUntil": "2024-03-31"
}
```

Другой элемент может выглядеть совершенно иначе:

```json
{
  "itemId": "ITEM-002",
  "restaurantId": "NIMBUS-047",
  "name": "Семейный пир",
  "price": 9800,
  "includes": ["ITEM-010", "ITEM-011", "ITEM-015", "ITEM-020"],
  "servings": 4,
  "available": true
}
```

Разные формы. Одна коллекция. Никаких проблем.

«Значит, база данных больше похожа на картотечный шкаф, чем на таблицу», — сказала Майя.

«Именно», — сказала Прия. «Вы можете положить любой документ в любой ящик. Вам не нужно обрезать документ до фиксированного размера».

**Знакомьтесь: DynamoDB**

Amazon DynamoDB — это управляемый сервис NoSQL-баз данных AWS. Он хранит данные как элементы (не строки), а элементы собраны в таблицы (наименование похоже на SQL, но поведение отличается).

Каждый элемент в таблице DynamoDB должен иметь **первичный ключ**, который уникально его идентифицирует. Всё остальное гибко.

Первичный ключ может быть одной из двух форм:

**Только ключ раздела**: Единственный атрибут, который должен быть уникальным для всех элементов.

**Ключ раздела + ключ сортировки (составной первичный ключ)**: Два атрибута, которые *вместе* образуют уникальную комбинацию. Это позволяет иметь несколько элементов с одинаковым ключом раздела, различающихся ключом сортировки.

Для меню Nimbus:

- Ключ раздела: `restaurantId`
- Ключ сортировки: `itemId`

Это означает, что вы можете эффективно извлечь все элементы для конкретного ресторана — DynamoDB точно знает, в каком разделе искать.

«Почему это называется ключом раздела?» — спросил Том.

**Как DynamoDB хранит данные внутри**

DynamoDB построен для горизонтального масштабирования до огромных размеров. Этого достигают через *разбиение на разделы* — данные разделяются по многим физическим машинам на основе ключа раздела.

Когда вы записываете элемент, DynamoDB хэширует значение ключа раздела и использует этот хэш для определения того, на каком физическом разделе (и, следовательно, на каком сервере) хранится элемент. Когда вы читаете элемент, DynamoDB делает то же вычисление, чтобы мгновенно его найти.

Думайте об этом как о почтовой системе. Если на каждом конверте есть почтовый индекс, почтовая служба не читает каждый конверт, чтобы выяснить, куда он принадлежит — она сортирует по почтовому индексу. DynamoDB сортирует по хэшу ключа раздела.

Вот почему важен хороший выбор ключа раздела:

- **Хорошо**: Высокая кардинальность, равномерно распределённые значения (`restaurantId` со многими ресторанами)
- **Плохо**: Низкая кардинальность (`true/false`, `category`) — большинство данных попадает на несколько разделов, создавая «горячие точки»

Горячая точка означает, что один раздел получает большую часть трафика. Этот раздел становится узким местом. DynamoDB начинает ограничивать запросы. Пользователи начинают видеть ошибки.

«Значит, если бы я использовал `available: true` в качестве ключа раздела», — медленно сказал Лео, — «все доступные элементы накапливались бы на одном разделе».

«И ваша база данных расплавилась бы во время ужинного наплыва», — подтвердила Прия.

Лео медленно закрыл ноутбук.

**Чтение и запись в масштабе**

DynamoDB может обрабатывать миллионы запросов в секунду. Но ему нужно знать, какую мощность выделить.

Есть два режима ёмкости:

**Выделенная ёмкость**: Вы указываете, сколько единиц чтения и записи хотите. DynamoDB резервирует эту ёмкость для вас и ограничивает трафик, превышающий её. Предсказуемые затраты, более низкая цена за запрос.

**Ёмкость по требованию**: DynamoDB автоматически масштабируется с вашим фактическим трафиком. Никакого планирования ёмкости не требуется. Более высокая цена за запрос и значительно проще в операционном плане, хотя внезапные пики, намного превышающие недавний паттерн трафика таблицы, всё равно могут вызвать ограничение, если они нарастают слишком быстро.

Для Nimbus меню читается значительно чаще, чем записывается. Клиент открывает приложение, просматривает меню — это много операций чтения. Партнёр-ресторан обновляет своё меню дважды в неделю — это редкие записи.

«Ёмкость по требованию имеет смысл пока», — сказал Том. «Мы ещё не знаем наших паттернов трафика. Лучше платить больше за запрос, чем недостаточно выделить и получить ограничения».

Нерешительная инфраструктурная мудрость. От Тома. Команда официально выросла.

**Согласованность: насколько свежи ваши данные?**

DynamoDB автоматически реплицирует данные по нескольким зонам доступности. Это отлично для долговечности, но это также означает, что вам нужно чётко думать о согласованности чтения.

Когда вы читаете из DynamoDB, у вас есть выбор:

**Конечно-согласованное чтение**: Это значение по умолчанию. Оно дешевле, и результат может кратко отставать от недавно завершённой записи.

**Строго согласованное чтение**: Для чтения из таблицы или локального вторичного индекса DynamoDB может вернуть последнее зафиксированное значение из успешных предыдущих записей. Это стоит больше мощности чтения и недоступно для глобальных вторичных индексов.

Для данных меню конечная согласованность нормальна. Пункт меню с задержкой в миллисекунду не имеет значения.

Для данных подтверждения заказа — «был ли размещён этот заказ?» — вам нужна строгая согласованность. Клиент не должен видеть сообщение «попробуйте ещё раз», когда его заказ только что был сохранён.

«Это как разница между проверкой баланса вашего счёта в приложении и звонком в банк напрямую», — сказала Майя. «В приложении данные могут быть на тридцать секунд позади. Звонок всегда актуален».

**Компромисс: чего не может DynamoDB**

NoSQL не лучше SQL в абсолютном смысле. Это другой инструмент для другой работы.

Что DynamoDB теряет:

**Гибкие запросы**: В SQL вы можете фильтровать и сортировать по любому столбцу. В DynamoDB вы можете эффективно запрашивать только по первичному ключу. Запрос по произвольным полям требует *сканирования* (чтения каждого элемента в таблице), что дорого и медленно в масштабе.

**Соединения**: DynamoDB не делает соединений. Если вам нужны данные из двух таблиц, вы делаете два отдельных чтения в коде приложения.

**Транзакции**: DynamoDB поддерживает транзакции, но реляционные базы данных по-прежнему являются более естественным выбором для многих многосущностных рабочих процессов, систем с интенсивными отчётами и дизайнов с интенсивными соединениями.

**Знакомость**: Десятилетия инструментария SQL, навыков и ментальных моделей не переносятся напрямую.

В чём DynamoDB превосходит:

- Паттерны доступа по ключу-значению и документу
- Массивный масштаб (задержка в однозначном числе миллисекунд при любом размере)
- Бессерверный, никакого управления инфраструктурой
- Автоматическое масштабирование, репликация Multi-AZ, резервные копии
- Предсказуемая производительность независимо от объёма данных

«Значит правило», — сказала Майя, — «использовать DynamoDB, когда вы точно знаете, *как* вы будете получать доступ к данным. Использовать SQL, когда ещё не знаете».

Прия кивнула. «Сначала спроектируйте паттерны доступа. Потом выбирайте базу данных».

Это одна из самых зрелых вещей, которые может произвести разговор о базах данных.

**Когда использовать каждую**

| Ситуация                                                | Выбор                          |
|---------------------------------------------------------|--------------------------------|
| Структурированные данные, сложные запросы, отчётность   | RDS (PostgreSQL, MySQL)        |
| Гибкие формы данных, доступ по ключу, массивный масштаб | DynamoDB                       |
| Интенсивная запись со сложными отношениями              | RDS                            |
| Интенсивное чтение с предсказуемыми паттернами доступа  | DynamoDB                       |
| Нужны соединения и агрегаты                             | RDS                            |
| Нужна задержка в миллисекунды при миллионах запросов/сек| DynamoDB                       |
| Транзакции по нескольким сущностям                      | RDS (обычно)                   |
| Бессерверный / непредсказуемые пики трафика             | DynamoDB по требованию         |

Неправильный ответ — всегда «использовать одно или другое». Nimbus в итоге использовал оба: RDS для истории заказов и финансовых записей (структурированные, реляционные, требует отчётности), DynamoDB для меню (гибкая схема, большой объём чтения, доступ по ID ресторана).

## Сильные стороны и ограничения

**Почему DynamoDB мощный**:

- Задержка в однозначном числе миллисекунд при любом масштабе
- Полностью управляемый — никакого патчинга, настройки репликации, окон обслуживания
- Автоматическая репликация Multi-AZ (долговечность встроена)
- Масштабирование по требованию — нулевое планирование ёмкости
- Нативная интеграция с Lambda, API Gateway, Streams
- Восстановление на момент времени (аналогично автоматическим резервным копиям RDS)
- DynamoDB Streams — фиксировать каждое изменение как событие (полезно для обработки в реальном времени)

**Где DynamoDB усложняется**:

- Проектирование паттернов доступа обязательно — ошибки дорого исправлять
- Сложные запросы требуют вторичных индексов (добавляет стоимость и сложность)
- Сканирования дороги — избегайте их в производстве
- «Ограничение размера элемента» — 400 КБ — большие элементы нуждаются в другом хранилище
- Ценообразование может удивить, если вы не понимаете стоимость единиц чтения/записи

## Итоги

- DynamoDB — это управляемый сервис NoSQL-баз данных AWS.
- Элементы хранятся как гибкие документы — фиксированная схема не требуется.
- Каждый элемент должен иметь **первичный ключ**: ключ раздела отдельно или ключ раздела + ключ сортировки.
- Ключ раздела определяет, на каком физическом разделе хранится элемент. Выбирайте его для равномерного распределения.
- Ёмкость **по требованию** автомасштабируется; **выделенная** ёмкость дешевле, если ваш трафик предсказуем.
- **Конечно-согласованные** чтения дешевле и быстрее. **Строго согласованные** чтения всегда актуальны.
- DynamoDB превосходит в доступе по ключу в массивном масштабе. Он хуже справляется с ad-hoc запросами и соединениями.
- Используйте RDS для реляционных данных. Используйте DynamoDB для данных документа/ключа-значения. Используйте оба, когда ситуация требует.

## Советы по экзамену

*Домен SAA-C03: Проектирование высокопроизводительных архитектур (Домен 3, Задача 3.3)*

- Знайте правила ключа раздела: **высокая кардинальность, равномерное распределение**. Горячие разделы — распространённая ловушка экзамена.
- **По требованию vs выделенная**: по требованию для непредсказуемого трафика; выделенная (с Auto Scaling) для предсказуемых нагрузок.
- **DynamoDB Streams**: фиксирует изменения на уровне элементов в реальном времени. Распространённый сценарий экзамена: «запустить функцию Lambda при изменении записи».
- **Global Tables**: мульти-региональная, мульти-активная репликация для глобально распределённых приложений и сценариев аварийного восстановления. На экзамене это сильный сигнал, когда нагрузка требует локальных чтений и записей в более чем одном регионе.
- **DAX (DynamoDB Accelerator)**: уровень кэширования в памяти для DynamoDB. Уменьшает задержку чтения от миллисекунд до микросекунд. Экзамен использует это, когда реплики для чтения RDS не помогут (потому что это кэш, специфичный для DynamoDB).
- **Составной первичный ключ**: ключ раздела + ключ сортировки позволяет гибкие запросы внутри раздела. Пример: получить все заказы для клиента между двумя датами — `customerId` является ключом раздела, `orderDate` — ключом сортировки.
- Знайте, когда НЕ использовать DynamoDB: сложные соединения, ad-hoc отчётность, транзакции по нескольким сущностям → RDS обычно является ответом.

**Упражнение 1 — Запоминание**

Объясните разницу между ключом раздела и ключом сортировки. Когда вы будете использовать оба?

*(Подсказка: подумайте о меню Nimbus — почему использование restaurantId в качестве ключа раздела и itemId в качестве ключа сортировки делает получение полного меню ресторана эффективным?)*

**Упражнение 2 — Практика для экзамена**

*Сценарий*: Глобальная игровая компания хранит профили игроков в DynamoDB. Каждый профиль включает такие поля, как имя пользователя, уровень, достижения и инвентарь. У некоторых игроков 10 предметов инвентаря; у других — 5 000 пользовательских конфигураций. Компании нужна задержка чтения в однозначное число миллисекунд для поиска профилей во время активного геймплея.

Какой подход проектирования НАИЛУЧШИМ образом поддерживает это требование?

А) Перейти на RDS Aurora с репликами для чтения в каждом регионе  
Б) Использовать DynamoDB с `playerId` в качестве ключа раздела и хранить весь профиль как один элемент  
В) Использовать DynamoDB с `level` в качестве ключа раздела для группировки игроков по схожему уровню  
Г) Использовать ElastiCache перед RDS для достижения суб-миллисекундной задержки

**Подсказка 1**: Паттерн доступа — «найти конкретного игрока по ID». Какой ключ делает это эффективным?

**Подсказка 2**: Один вариант создаёт ужасную горячую точку. Какой атрибут имеет очень низкую кардинальность?

**Подсказка 3**: DynamoDB уже нативно обеспечивает задержку в однозначное число миллисекунд.

**Ответ**: Б

**Объяснение**: Использование `playerId` в качестве ключа раздела равномерно распределяет данные по разделам и обеспечивает мгновенные поиски по ID игрока — именно тот паттерн доступа, который описан. Гибкая документная модель DynamoDB обрабатывает разные размеры инвентаря без изменений схемы.

**Почему не А?** RDS Aurora с репликами для чтения добавляет сложность и всё равно не является первым естественным выбором для этого типа поиска профиля по ключу в игровом масштабе.

**Почему не В?** Использование `level` в качестве ключа раздела создаёт серьёзные горячие точки — большинство трафика идёт на уровень 1 (новые игроки) или максимальный уровень (активные ветераны), оставляя другие разделы простаивать.

**Почему не Г?** Вопрос описывает DynamoDB, а не RDS. Добавление ElastiCache перед RDS вводит два новых сервиса, когда DynamoDB один решает проблему.
