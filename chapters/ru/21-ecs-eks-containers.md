**Что такое контейнер?**

**Контейнер** — это лёгкая переносимая единица, упаковывающая ваше приложение вместе со всем необходимым для его работы: средой выполнения (Python 3.11, Node.js 20, Java 17), библиотеками и зависимостями, конфигурационными файлами и кодом самого приложения.

В отличие от виртуальной машины (которая эмулирует весь компьютер, включая ядро операционной системы), контейнер разделяет ядро ОС хоста, сохраняя при этом изоляцию всего остального. Это делает контейнеры быстрыми в запуске (секунды, иногда миллисекунды) и небольшими (мегабайты, а не гигабайты).

Наиболее популярная технология контейнеров — **Docker**. Образ Docker — это схема (blueprint): снимок приложения и его среды. Контейнер Docker — это запущенный экземпляр этого образа.

Ключевое свойство: **неизменяемость**. Образ, собранный сегодня, будет работать одинаково на любом хосте с поддержкой Docker — на ноутбуке, EC2-инстансе, сервере в другом дата-центре. Среда встроена в образ. Дрейф конфигурации невозможен.

— Значит, вместо того чтобы беспокоиться о том, что установлено на EC2-инстансе, — сказал Leo, — мы собираем образ, в котором есть всё. Образ работает одинаково везде.

— И если вам нужно протестировать его локально, вы запускаете тот же образ, — добавила Priya. — Больше никакого «у меня работает».

**Amazon ECS: оркестратор**

Запустить один контейнер — просто. Запустить десятки контейнеров на нескольких хостах, маршрутизировать трафик между ними, перезапускать упавшие контейнеры, развёртывать новые версии без простоев — для этого нужен **оркестратор**.

**Amazon ECS (Elastic Container Service)** — управляемый сервис оркестрации контейнеров от AWS. Вы определяете:

- **Определение задачи (task definition)**: какой образ контейнера запускать, сколько CPU и памяти выделить, какие переменные среды использовать, какие порты открыть
- **Сервис (service)**: сколько копий задачи запускать, как обрабатывать сбои и развёртывания
- **Кластер (cluster)**: базовая вычислительная инфраструктура

ECS берёт на себя остальное: размещает задачи на доступных мощностях, перезапускает упавшие задачи, завершает соединения во время развёртываний, регистрирует работоспособные задачи в балансировщике нагрузки.

Для Nimbus API переехал с EC2-инстансов с ручным управлением развёртыванием на ECS. Каждое новое развёртывание отправляло новый образ Docker в **Amazon ECR (Elastic Container Registry)** — управляемый реестр контейнеров AWS — и ECS разворачивал его на всех задачах без простоев.

**Fargate и тип запуска EC2**

ECS может запускать контейнеры в двух режимах:

**Тип запуска EC2**: вы управляете базовыми EC2-инстансами. Вы отвечаете за обновление инстансов, правильный подбор их размера и обеспечение достаточной мощности для ваших контейнеров. Больше контроля, больше ответственности.

**Fargate (бессерверные вычисления для контейнеров)**: AWS полностью управляет базовой инфраструктурой. Вы указываете CPU и память для каждой задачи; Fargate автоматически выделяет нужные мощности. Никаких EC2-инстансов для управления. Вы платите за vCPU-секунду и ГБ-секунду памяти.

Fargate — это модель «бессерверных контейнеров»: вы получаете изоляцию среды контейнеров без управления серверами. Компромисс: меньше контроля над настройкой базового инстанса и несколько более высокая удельная стоимость.

Для Nimbus: Fargate для API-сервиса. Они не хотели управлять EC2-инстансами для контейнеров.

**Amazon EKS: когда нужен Kubernetes**

**Kubernetes** — система оркестрации контейнеров с открытым исходным кодом, фактически отраслевой стандарт для управления контейнерами в масштабе. Мощная, расширяемая и сложная.

**Amazon EKS (Elastic Kubernetes Service)** — управляемый сервис Kubernetes от AWS. Он запускает за вас плоскость управления Kubernetes (уровень управления), а вы управляете рабочими узлами (или используете для этого Fargate).

Когда использовать EKS, а когда ECS?

**Используйте ECS** если:

- Вы преимущественно работаете в AWS и хотите более простой, нативный для AWS опыт
- Ваша команда не имеет опыта работы с Kubernetes
- Вы хотите меньше операционных накладных расходов

**Используйте EKS** если:

- Вам нужны специфические функции Kubernetes (Custom Resource Definitions, Helm charts, экосистема Kubernetes)
- Ваша команда уже знает Kubernetes
- Вы работаете в гибридной среде (часть инфраструктуры локально, часть в AWS) и хотите единый уровень оркестрации
- Ваша нагрузка предъявляет требования, соответствующие расширяемости Kubernetes

— Что нам использовать? — спросила Maya.

— ECS, — немедленно сказала Priya. — У нас нет опыта работы с Kubernetes. ECS делает всё, что нам нужно. Добавление Kubernetes сейчас означало бы увеличение операционной сложности без практической пользы.

— Мы всегда можем перейти на EKS позже, если перерастём ECS, — добавил Leo.

Это правильный ответ опытного специалиста: выбирайте более простой инструмент, соответствующий вашим текущим потребностям.

**Как контейнеры меняют развёртывание**

До контейнеров развёртывание новой версии Nimbus API означало:

1. Подключиться по SSH к каждому EC2-инстансу
2. Получить последний код из Git
3. Установить/обновить зависимости
4. Перезапустить процесс приложения
5. Проверить работоспособность
6. Перейти к следующему инстансу

Это было подвержено ошибкам и занимало много времени. Требовалась координация. Если шаг 3 завершался ошибкой на четвёртом инстансе, возникало смешанное развёртывание: некоторые инстансы работали со старой версией, другие не могли запустить новую.

С ECS и контейнерами:

1. Собрать новый образ Docker (автоматизировано в CI/CD-конвейере)
2. Отправить в ECR
3. Обновить ECS-сервис для использования новой версии образа

ECS обрабатывает плавное развёртывание: запускает новые задачи с новым образом, ждёт, пока они станут работоспособными, затем останавливает старые задачи. Развёртывание без простоев, автоматизированное.

Если новая версия не проходит проверки работоспособности, ECS останавливает развёртывание и старая версия продолжает обслуживать трафик.

## Преимущества и ограничения

**Контейнеры**:

- Устраняют несоответствие сред («у меня работает»)
- Обеспечивают быстрое, надёжное развёртывание
- Неизменяемы — одинаковый образ работает одинаково везде
- Эффективны — легче виртуальных машин, быстрее запускаются

**ECS**:

- Проще Kubernetes для нагрузок, ориентированных на AWS
- Тесная интеграция с AWS (IAM, ALB, CloudWatch, Secrets Manager)
- Опция Fargate полностью устраняет управление EC2

**EKS**:

- Полная совместимость с Kubernetes — используйте всю экосистему
- Лучше для гибридных сред или команд с опытом Kubernetes
- Сложнее в настройке и эксплуатации, чем ECS

**Где возникают сложности**:

- Образы контейнеров нужно собирать и версионировать — требуется CI/CD-конвейер
- Отладка контейнеров требует других инструментов, чем отладка традиционных процессов
- Контейнеры с состоянием (базы данных в контейнерах) требуют тщательной настройки постоянного хранилища
- Взаимодействие между контейнерами (межсервисная коммуникация) требует понимания концепций сетей контейнеров

## Резюме

- **Контейнеры** упаковывают код приложения, среду выполнения и зависимости вместе — работают одинаково в любом месте.
- **Docker** — стандартная технология контейнеров. Образы — это схемы; контейнеры — это запущенные экземпляры.
- **ECR (Elastic Container Registry)** — управляемый реестр Docker от AWS — храните и версионируйте свои образы здесь.
- **ECS (Elastic Container Service)** оркеструет контейнеры. Вы определяете задачи и сервисы; ECS управляет размещением и жизненным циклом.
- **Fargate** — бессерверные вычисления для контейнеров — никаких EC2-инстансов для управления.
- **EKS (Elastic Kubernetes Service)** — управляемый Kubernetes — для команд, которым нужны функции Kubernetes или совместимость с ним.
- Выбирайте ECS для простоты в AWS; выбирайте EKS для совместимости с экосистемой Kubernetes.

## Советы к экзамену

*SAA-C03, область: проектирование отказоустойчивых архитектур (область 2, задача 2.1)*

- **Признаки ECS и EKS**: сценарии экзамена с упоминанием «Kubernetes», «Helm», «существующий опыт Kubernetes» или «оркестрация контейнеров в нескольких облаках» → EKS. Всё остальное → ECS.
- **Fargate и тип запуска EC2**: «не хотим управлять EC2-инстансами для контейнеров», «бессерверные контейнеры», «без управления инфраструктурой» → Fargate. «Нужны конкретные типы инстансов», «нагрузки с GPU», «тонкий контроль над инстансами» → тип запуска EC2.
- **Роли задач ECS**: как и роли инстансов EC2, задачи ECS имеют IAM-роли. Каждая задача может иметь разные разрешения. Сценарий экзамена: «контейнеру нужно читать из S3» → прикрепить IAM-роль к определению задачи.
- **Сканирование образов ECR**: ECR может сканировать образы контейнеров на известные уязвимости (CVE). Признак в экзамене: «сканировать контейнеры на уязвимости безопасности» → сканирование образов ECR.
- **Сине-зелёные развёртывания**: ECS поддерживает сине-зелёные развёртывания через интеграцию с CodeDeploy. Развёртывание без простоев с автоматическим откатом. Паттерн в экзамене: «развернуть без простоев с автоматическим откатом» → ECS + CodeDeploy сине-зелёное.
- **Auto Scaling сервисов ECS**: масштабировать количество задач на основе CPU, памяти или пользовательских метрик CloudWatch. Работает с ALB для маршрутизации трафика к нужному числу запущенных задач.

**Упражнение 2 — Подготовка к экзамену**

*Сценарий*: Компания имеет микросервисное приложение, работающее на EC2-инстансах, управляемых вручную. Команда испытывает трудности с непоследовательными развёртываниями — на разных EC2-инстансах разные версии библиотек, что вызывает труднопроизводимые баги. Они хотят стандартизировать развёртывания, минимизируя операционные накладные расходы на управление базовыми серверами. Команда не имеет опыта работы с Kubernetes.

Какое решение наилучшим образом отвечает этим требованиям?

A) Развернуть на EC2 с AWS Systems Manager Patch Manager для поддержания согласованности инстансов  
B) Контейнеризировать приложение с Docker; использовать Amazon ECS с типом запуска Fargate  
C) Контейнеризировать приложение с Docker; использовать Amazon EKS с самоуправляемыми группами узлов  
D) Использовать AWS Elastic Beanstalk для автоматического управления развёртываниями и конфигурацией инстансов

**Подсказка 1**: Контейнеры напрямую решают проблему «несогласованности сред». Какие варианты используют контейнеры?

**Подсказка 2**: «Минимизировать операционные накладные расходы на управление серверами» → Fargate (без управления EC2) в сравнении с самоуправляемыми узлами (всё ещё управление EC2).

**Подсказка 3**: «Нет опыта Kubernetes» → EKS создаёт больше операционной сложности, чем ECS.

**Ответ**: B

**Пояснение**: Контейнеризация с Docker гарантирует, что каждое развёртывание использует одинаковый образ с одинаковыми зависимостями — устраняя дрейф конфигурации. ECS с Fargate означает отсутствие EC2-инстансов для управления. Команда сосредотачивается на коде приложения и определениях контейнеров, а не на обслуживании серверов. ECS (не EKS) подходит для команд без опыта Kubernetes.

**Почему не A?** Patch Manager поддерживает EC2-инстансы в актуальном состоянии, но не решает проблему несоответствия версий библиотек между приложениями. Фундаментальная проблема (разные среды кода на разных инстансах) остаётся.

**Почему не C?** EKS с самоуправляемыми группами узлов требует управления EC2-инстансами *и* изучения Kubernetes. Ни то, ни другое не соответствует требованиям.

**Почему не D?** Elastic Beanstalk управляет развёртыванием приложений на EC2, но не решает фундаментальную проблему несоответствия сред без использования контейнеров. Beanstalk не использует образы Docker по умолчанию (хотя может быть настроен для этого).
