**Две проблемы: хранение секретов и шифрование данных**

Безопасность вокруг конфиденциальной информации имеет две отдельные проблемы:

**Хранение учётных данных** (пароли баз данных, API-ключи, строки соединения): Где они живут? Кто к ним имеет доступ? Как вы их ротируете, не перезапуская приложение?

**Шифрование данных** (информация о клиентах, платёжные записи, персональные данные): Как обеспечить, что даже если кто-то получит несанкционированный доступ к вашей базе данных или бакету S3, они не смогут прочитать данные?

AWS имеет специализированный сервис для каждой проблемы:

- **AWS Secrets Manager**: Хранит учётные данные и управляет ими безопасно
- **AWS KMS (Key Management Service)**: Управляет ключами шифрования для шифрования и дешифрования данных

**AWS Secrets Manager: никаких жёстко закодированных учётных данных больше**

Secrets Manager — это безопасное хранилище для секретов: учётные данные базы данных, API-ключи, OAuth-токены, SSH-ключи или всё конфиденциальное.

Вместо того чтобы ваше приложение читало пароль из переменной среды или конфигурационного файла, оно вызывает Secrets Manager API при запуске (или по необходимости) и получает секрет. Секрет никогда не касается диска. Он никогда не появляется в вашем коде. Его нет в ваших переменных среды.

Вот как выглядит поток:

**Старый способ**:
```
DB_PASSWORD=supersecretpassword123  # в файле .env или переменной среды
```

**Способ Secrets Manager**:
```python
import boto3
client = boto3.client('secretsmanager')
secret = client.get_secret_value(SecretId='nimbus/production/db-password')
password = json.loads(secret['SecretString'])['password']
```

Экземпляру EC2 нужна IAM-роль с разрешением вызывать `secretsmanager:GetSecretValue` для этого конкретного секрета. Никакой другой сервис не может его прочитать. Секрет никогда не попадает в код.

**Автоматическая ротация: настоящая мощь**

Главная функция Secrets Manager — не хранение секретов, а их автоматическая ротация.

Вот сценарий: каждые 30 дней Secrets Manager генерирует новый пароль базы данных, обновляет его в RDS, обновляет сохранённый секрет, и ваше приложение получает новый пароль в следующий раз, когда он ему нужен. Никакого ручного вмешательства. Никакого развёртывания. Никакого «мне нужно помнить об этом».

Ротация реализована как Lambda-функция. AWS предоставляет шаблоны для баз данных RDS (MySQL, PostgreSQL, Aurora). Вы можете настроить функцию для любого типа учётных данных.

**AWS KMS: фабрика замков**

AWS KMS (Key Management Service) управляет **криптографическими ключами** — секретными значениями, используемыми для шифрования и дешифрования данных.

Аналогия: KMS похож на компанию по изготовлению замков, которая хранит мастер-ключ. Ваши данные (содержимое коробки) зашифрованы. Только тот, у кого есть разрешение использовать KMS-ключ, может их расшифровать. KMS логирует каждое использование каждого ключа в CloudTrail.

**Customer Master Keys (CMK)** — теперь называемые KMS-ключами — бывают двух типов:

**Управляемые AWS ключи**: AWS создаёт ключ и управляет им автоматически для сервисов таких как S3, EBS, RDS. Вы не контролируете ключ напрямую, но можете видеть, что он используется. Бесплатно.

**Управляемые клиентом ключи**: Вы создаёте ключ в KMS и управляете каждым его аспектом: кто может его использовать, когда он ротируется, кто может им управлять. Вы можете включить автоматическую ежегодную ротацию. Стоимость: $1/месяц за ключ плюс плата за API-вызов.

**Шифрование в сервисах AWS: интеграция с KMS**

Большинство сервисов AWS интегрируются с KMS для шифрования:

**S3**: Включите «серверное шифрование с KMS» для бакета. Каждый объект зашифрован в состоянии покоя KMS-ключом. Чтение объекта требует разрешений как к бакету S3, *так и* к KMS-ключу.

**RDS**: Включите шифрование при создании. Хранилище базы данных, резервные копии и снимки — всё зашифровано KMS-ключом. Примечание: шифрование нельзя включить на существующем незашифрованном экземпляре RDS — нужно сделать снимок, скопировать снимок с включённым шифрованием и восстановить.

**EBS**: Шифруйте тома с помощью KMS. Новые тома, созданные из зашифрованных снимков, автоматически зашифрованы.

**DynamoDB**: Шифрование в состоянии покоя с помощью KMS включено по умолчанию для всех таблиц.

**ElastiCache Redis**: Шифрование в состоянии покоя с KMS для конфиденциальных кэшированных данных.

Принцип: данные должны быть зашифрованы в состоянии покоя (хранящиеся на диске) и при передаче (движущиеся по сети). KMS обрабатывает шифрование в состоянии покоя. TLS/SSL (предоставляемый автоматически сервисами AWS) обрабатывает шифрование при передаче.

**Конвертное шифрование: как KMS на самом деле работает**

Вот деталь, которая помогает понять поведение KMS и вопросы экзамена.

KMS в большинстве случаев не шифрует ваши данные напрямую. Он использует **конвертное шифрование**:

1. KMS генерирует **ключ данных** (уникальный симметричный ключ)
2. Сервис использует ключ данных для локального шифрования ваших данных (быстро — симметричное шифрование)
3. Сервис просит KMS зашифровать сам ключ данных (используя ваш KMS-ключ)
4. Хранятся как зашифрованные данные, так и зашифрованный ключ данных
5. Ваши фактические данные никогда не покидают сервис — только ключ данных идёт в KMS для шифрования/дешифрования

Когда вы читаете данные:

1. Сервис просит KMS расшифровать ключ данных
2. KMS проверяет разрешения, расшифровывает ключ данных, возвращает его
3. Сервис использует расшифрованный ключ данных для локального дешифрования ваших данных

Это означает, что KMS может обрабатывать очень большие данные, не отправляя их все через KMS API. Только маленькие ключи идут в KMS. CloudTrail логирует каждый KMS API-вызов — каждую операцию шифрования и дешифрования.

**Secrets Manager против Parameter Store**

AWS также имеет **Systems Manager Parameter Store**, который хранит конфигурационные значения (не только секреты). Parameter Store дешевле — бесплатно для стандартных параметров. Он также может хранить зашифрованные параметры с помощью KMS.

Для секретов, которым нужна ротация: Secrets Manager.

Для конфигурационных значений и несекретных параметров: Parameter Store (бесплатный уровень очень щедрый).

Для конфигурации приложения (номера портов, флаги функций, настройки для конкретной среды): Parameter Store.

## Сильные стороны и ограничения

**AWS Secrets Manager**:

- Автоматическая ротация секретов без изменений кода
- Тонкий IAM контроль доступа по каждому секрету
- Версионирование (доступ к предыдущей версии во время ротации)
- Аудит через CloudTrail
- Стоимость: ~$0,40/секрет/месяц + API-вызовы

**AWS KMS**:

- Централизованное управление ключами с полным журналом аудита
- Автоматическая ежегодная ротация ключей для управляемых клиентом ключей
- Тонкие IAM-разрешения по каждому ключу (политики ключей + политики IAM)
- Поддержка аппаратного модуля безопасности (HSM) — ключи никогда не покидают HSM
- Стоимость: $1/месяц за ключ + $0,03 за 10 000 API-вызовов

**Где всё усложняется**:

- Политики KMS-ключей отдельны от (и оцениваются вместе с) политиками IAM — может быть запутанно в отладке
- Шифрование в состоянии покоя нужно планировать — нельзя зашифровать существующий незашифрованный экземпляр RDS на месте
- Удаление ключа в KMS имеет период ожидания 7-30 дней (механизм безопасности — потерянные ключи означают потерянные данные)
- Затраты Secrets Manager масштабируются с количеством секретов и API-вызовов в масштабе

## Итоги

- Никогда не храните учётные данные в коде, переменных среды или конфигурационных файлах, коммиченных в систему контроля версий.
- **Secrets Manager** хранит учётные данные безопасно и ротирует их автоматически. Приложения получают секреты через API.
- **KMS** управляет ключами шифрования. Большинство сервисов AWS интегрируются с KMS для шифрования в состоянии покоя.
- **Шифрование в состоянии покоя** (данные, хранящиеся на диске) использует KMS-ключи, управляемые AWS или вами. **Шифрование при передаче** использует TLS.
- **Конвертное шифрование**: KMS шифрует ключ, а не данные напрямую. Сервис шифрует данные, используя локальный ключ данных.
- **Управляемые клиентом KMS-ключи**: полный контроль над ротацией, доступом и аудитом. **Управляемые AWS ключи**: автоматические, никакой конфигурации не нужно.
- **Parameter Store** — более лёгкая альтернатива Secrets Manager для несекретных конфигурационных значений.

## Советы по экзамену

*Домен SAA-C03: Проектирование безопасных архитектур (Домен 1, Задача 1.3)*

- **Secrets Manager против SSM Parameter Store**: Secrets Manager для учётных данных, которым нужна автоматическая ротация; Parameter Store для общей конфигурации. Экзамен различает их по требованию ротации и чувствительности к стоимости.
- **Политики KMS-ключей**: KMS-ключ имеет собственную политику ключа (политику на основе ресурса). Одних политик IAM недостаточно для доступа к KMS-ключу — политика ключа должна явно разрешать это.
- **Шифрование RDS**: Нельзя включить шифрование на существующем экземпляре RDS. Стандартный процесс: создать снимок → скопировать снимок с включённым шифрованием, используя управляемый клиентом KMS-ключ → восстановить из зашифрованного снимка → перевести трафик на новый экземпляр.
- **Шифрование EBS**: Новые тома могут быть зашифрованы. Снимки зашифрованных томов всегда зашифрованы. Незашифрованные тома нельзя напрямую зашифровать — снимок + копирование + восстановление.
- **CloudTrail + KMS**: Каждый KMS API-вызов логируется в CloudTrail. Это ключевая функция соответствия требованиям.
- **Мультирегиональные KMS-ключи**: Реплицировать материал ключа в несколько регионов, чтобы дешифрование происходило без кросс-региональных API-вызовов. Экзамен использует это для мультирегионального аварийного восстановления с зашифрованными данными.
- **KMS против CloudHSM**: KMS является мультиарендным (управляется AWS). CloudHSM — это выделенный аппаратный модуль безопасности, который контролируете только вы. Сигналы экзамена: «FIPS 140-2 Level 3», «выделенный HSM», «криптографические операции, управляемые клиентом» → CloudHSM.

**Упражнение 2 — Практика для экзамена**

*Сценарий*: Финансовые услуги хранят конфиденциальные данные клиентов в базе данных RDS MySQL. Новое требование соответствия предписывает:

1. Все данные должны быть зашифрованы в состоянии покоя
2. Все использования ключей шифрования должны быть проверяемы
3. Ключи шифрования должны быть управляемыми клиентом (не управляемыми AWS)
4. Пароль базы данных должен ротироваться автоматически каждые 90 дней

База данных была создана шесть месяцев назад без шифрования. Какой набор действий НАИЛУЧШИМ образом отвечает всем четырём требованиям?

А) Включить шифрование RDS на существующей базе данных; создать управляемый клиентом KMS-ключ; настроить Secrets Manager с 90-дневной ротацией  
Б) Создать снимок существующей базы данных; скопировать снимок с шифрованием, используя управляемый клиентом KMS-ключ; восстановить из зашифрованного снимка; настроить Secrets Manager с 90-дневной ротацией  
В) Создать новый зашифрованный экземпляр RDS с управляемым AWS ключом; перенести данные со старого экземпляра; настроить Secrets Manager с 90-дневной ротацией  
Г) Включить шифрование RDS в состоянии покоя на существующей базе данных, используя управляемый AWS ключ; настроить Secrets Manager с 90-дневной ротацией

**Подсказка 1**: Нельзя включить шифрование на существующем незашифрованном экземпляре RDS напрямую.

**Подсказка 2**: «Управляемые клиентом» ключи означают управляемые клиентом KMS-ключи, а не управляемые AWS.

**Подсказка 3**: Процесс копирования снимка — стандартный путь миграции на зашифрованный RDS.

**Ответ**: Б

**Объяснение**: Шифрование RDS нельзя включить на существующем экземпляре. Стандартный подход: сделать снимок существующего экземпляра → скопировать снимок с включённым шифрованием, используя управляемый клиентом KMS-ключ (удовлетворяет требованиям 1, 2 и 3) → восстановить из зашифрованного снимка. Управляемые клиентом KMS-ключи автоматически логируют всё использование в CloudTrail (аудит) и держат ключи шифрования под вашим контролем. Secrets Manager обрабатывает автоматическую 90-дневную ротацию пароля (удовлетворяет требованию 4).

**Почему не А?** Нельзя включить шифрование на существующем незашифрованном экземпляре RDS на месте.

**Почему не В?** Управляемые AWS ключи не удовлетворяют требованию «управляемые клиентом» (требование 3).

**Почему не Г?** Та же проблема, что и у А (нельзя включить на месте), плюс управляемый AWS ключ не удовлетворяет требованию 3.
