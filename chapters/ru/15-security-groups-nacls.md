**Два уровня сетевой безопасности**

В VPC у вас есть два отдельных инструмента для контроля сетевого трафика:

**Группы безопасности**: Виртуальные файрволы, прикреплённые к отдельным ресурсам (экземплярам EC2, базам данных RDS, балансировщикам нагрузки, функциям Lambda в VPC). Они работают на уровне ресурсов.

**Сетевые ACL (NACL)**: Правила файрвола, прикреплённые к подсетям. Они работают на границе подсети — до того, как трафик достигает любого ресурса в этой подсети.

Понимание обоих требует понимания одного критического различия: **с состоянием против без состояния**.

**С состоянием: группы безопасности**

Группа безопасности является **stateful** (с состоянием).

Когда вы разрешаете входящий трафик на конкретном порту, ответный трафик автоматически разрешается исходящим, даже если для него нет явного исходящего правила.

Когда вы разрешаете исходящий трафик к назначению, ответный трафик, возвращающийся обратно, автоматически разрешается.

Думайте об охраннике с состоянием в офисном здании. Вы показываете пропуск при входе. Позже вы выходите. Охраннику не нужно проверять вас снова при выходе — система знает, что вас впустили, и вам разрешено выйти.

**Правила группы безопасности для EC2-экземпляра API Nimbus:**

- **Входящий — TCP 8080 — от Load Balancer SG** → Принимать API-трафик от ALB
- **Входящий — TCP 22 — от Bastion Host SG** → SSH только с бастионного хоста
- **Исходящий — TCP 5432 — к RDS SG** → Подключаться к PostgreSQL
- **Исходящий — TCP 6379 — к ElastiCache SG** → Подключаться к Redis
- **Исходящий — TCP 443 — к 0.0.0.0/0** → HTTPS к внешним API

Обратите внимание: нет явного исходящего правила для порта 8080. Входящее правило имеет состояние — ответный трафик (ответ API балансировщику нагрузки) автоматически разрешается.

Также обратите внимание: правила группы безопасности ссылаются на *другие группы безопасности*, а не на IP-адреса. «Разрешить входящий от группы безопасности балансировщика нагрузки» означает «разрешить трафик от любого ресурса, к которому прикреплена эта группа безопасности». Это более гибко и поддерживаемо, чем отслеживание IP-адресов.

**Поведение по умолчанию:**

- По умолчанию весь входящий трафик запрещён
- По умолчанию весь исходящий трафик разрешён
- Все правила оцениваются (группы безопасности не имеют упорядоченных правил — применяются все совпадающие правила)
- Группы безопасности могут только **разрешать** трафик — нельзя создавать явные правила запрета

**Без состояния: сетевые ACL**

NACL является **stateless** (без состояния).

Когда вы разрешаете входящий трафик на порту 8080, это покрывает только входящее. Ответ (исходящий трафик на эфемерных портах) должен быть явно разрешён исходящим правилом.

Думайте о металлодетекторе. Вы проходите через него на входе. Металлодетектор не знает, что вы уже проходили — вам нужно пройти снова на выходе.

**Правила NACL нумерованы и оцениваются по порядку.** Первое совпадающее правило побеждает. Правило 100 оценивается раньше правила 200. Если правило 100 запрещает трафик, а правило 200 его разрешает, трафик запрещён.

NACL может явно **запрещать** трафик — в отличие от групп безопасности, которые могут только разрешать. Это делает их полезными для блокировки конкретных IP-диапазонов.

**Поведение NACL по умолчанию:**

- NACL по умолчанию (создаётся с вашим VPC) разрешает весь входящий и исходящий трафик
- Пользовательский NACL запрещает весь трафик по умолчанию (вы должны явно разрешить то, что хотите)

**NACL для публичной подсети (упрощённо):**

*Входящие правила (оцениваются по порядку — первое совпадение побеждает):*

- Правило 100: TCP 443, от 0.0.0.0/0 → **Разрешить** (HTTPS)
- Правило 110: TCP 80, от 0.0.0.0/0 → **Разрешить** (HTTP)
- Правило 120: TCP 1024–65535, от 0.0.0.0/0 → **Разрешить** (эфемерные обратные порты)
- Правило \*: Весь трафик → **Запретить**

*Исходящие правила:*

- Правило 100: TCP 443, к 0.0.0.0/0 → **Разрешить** (HTTPS)
- Правило 110: TCP 80, к 0.0.0.0/0 → **Разрешить** (HTTP)
- Правило 120: TCP 1024–65535, к 0.0.0.0/0 → **Разрешить** (эфемерные обратные порты)
- Правило \*: Весь трафик → **Запретить**

Правило 120 (порты 1024-65535) разрешает эфемерные порты — временные порты с высокими номерами, используемые для обратного TCP-трафика. Поскольку NACL без состояния, вы должны явно разрешать их исходящими, иначе ответы вашего сервера не пройдут.

**Когда использовать что**

«Подождите — но *почему* мы делали бы это именно так?» — спросила Майя. «Зачем иметь два отдельных инструмента — группы безопасности *и* NACL — если группы безопасности уже работают? Какой смысл в лишней сложности?»

Ответ в том, что они работают на разных уровнях и имеют разные возможности. Группы безопасности защищают отдельные ресурсы и могут только разрешать трафик. NACL защищают целые подсети и могут явно запрещать. Наличие обоих означает, что вы можете применять детализированные разрешающие правила на уровне ресурсов и широкие запрещающие правила на уровне подсети — без того, чтобы один мешал другому.

Используйте **группы безопасности** для основного уровня контроля доступа. Ими проще управлять, они с состоянием (меньше шансов случайной блокировки из-за забытых эфемерных портов) и поддерживают ссылки на другие группы безопасности.

Используйте **NACL** для элементов управления на уровне подсети, особенно:

- **Явные правила запрета**: Заблокировать конкретный IP-адрес или диапазон от достижения целой подсети
- **Экстренная блокировка**: IP активно атакует — добавьте правило запрета NACL для блокировки всей подсети до того, как она достигнет любого ресурса

Возможно, вы задаётесь вопросом: если группы безопасности с состоянием и блокируют весь входящий трафик по умолчанию, когда вам вообще понадобятся NACL? Группы безопасности хорошо справляются с большинством случаев. Но есть одна вещь, которую они не могут сделать: явно запретить. Группа безопасности может только разрешать трафик — если правило не совпадает, трафик запрещён по умолчанию. Вы не можете добавить правило, которое говорит «заблокировать этот конкретный IP». Для этого нужен NACL: нумерованное правило запрета, которое останавливает конкретный диапазон адресов до того, как он достигнет любого ресурса в подсети. NACL наиболее полезны для экстренного реагирования (блокировка активного злоумышленника) и для обеспечения границ на уровне подсети, которые не должны зависеть от конфигурации отдельных ресурсов.

«Значит, группа безопасности — это тонкий контроль», — сказала Майя, — «а NACL — широкий мазок?»

«Группы безопасности защищают отдельные ресурсы», — подтвердила Прия. «NACL защищают целые подсети. Когда вы хотите заблокировать IP от достижения чего-либо в вашей сети — NACL. Когда вы хотите разрешить только балансировщику нагрузки достигать API-сервера — группа безопасности».

«Мы думали о том, что произойдёт, если злоумышленник вернётся с другим IP?» — сказала Прия. «NACL блокирует один диапазон. Они переключаются на другой».

«Для этого и нужен GuardDuty», — сказал Лео. «Поведенческое обнаружение. Если тот же скрипт запускается с нового IP, паттерн трафика выглядит так же».

«Мы до этого дойдём», — сказала Прия. «Сначала главное».

«Сколько всё это стоит в месяц?» — спросил Том.

Сами группы безопасности и NACL бесплатны. AWS не взимает плату за количество групп безопасности, количество правил или количество записей NACL. Соображение стоимости косвенное: более жёсткие исходящие правила групп безопасности могут направлять меньше трафика через NAT Gateway, снижая плату за обработку данных.

«Значит, элементы управления безопасностью бесплатны», — сказал Рафаэль. «Стоимость — это инфраструктура, которая их поддерживает».

«Верно. NAT Gateway для высокой доступности. Интерфейсные VPC Endpoints для сервисов, которые иначе шли бы через NAT. У этого есть стоимость. У самих правил групп безопасности — нет».

**Соберём всё вместе: эшелонированная оборона**

После инцидента Прия нарисовала уровни обороны Nimbus на доске:

```
Интернет
  ↓
CloudFront + Shield (поглощение DDoS)
  ↓
WAF (фильтрация на уровне приложения)
  ↓
Internet Gateway
  ↓
NACL на публичной подсети (правила уровня подсети, экстренная блокировка)
  ↓
ALB Security Group (HTTPS откуда угодно)
  ↓
NACL на приватной подсети приложения
  ↓
EC2 API Security Group (порт 8080 только от ALB SG)
  ↓
NACL на приватной подсети данных
  ↓
RDS Security Group (порт 5432 только от API SG)
```

«Каждый уровень предполагает, что предыдущий может отказать», — сказала она. «База данных не доверяет тому, что сетевой уровень остановил злоумышленника. Экземпляр EC2 не доверяет тому, что ALB остановил злоумышленника. Каждый уровень обеспечивает свои собственные правила независимо».

«Эшелонированная оборона», — сказала Майя.

«Эшелонированная оборона. Злоумышленник, прошедший один уровень, всё ещё сталкивается со следующим. Ни одна отдельная неправильная конфигурация не катастрофична. Это означает, что один уровень отказывает, а другие держатся».

Лео посмотрел на диаграмму. Злоумышленник скомпрометировал один экземпляр EC2. Они прошли уровень учётных данных. Но каждый последующий уровень удержался.

Вот как выглядела эшелонированная оборона на практике.

**Инцидент: что перехватили слои**

Возвращаясь к атаке румынского IP:

**Что произошло**: Злоумышленник использовал скомпрометированный ключ развёртывания для загрузки скрипта сканирования на один экземпляр EC2. Скрипт пытался подключиться к другим сервисам.

**Что их остановило**:

- Группа безопасности RDS разрешала только входящий трафик на порту 5432 от группы безопасности API EC2. Скрипт не мог достичь базы данных с инструмента сканирования — он не прикреплял правильную группу безопасности.
- Группа безопасности ElastiCache разрешала только входящий трафик на порту 6379 от группы безопасности API EC2.
- Другие экземпляры EC2 разрешали SSH только от группы безопасности бастионного хоста.

**Что их не остановило**:

- Исходящие правила экземпляра EC2 разрешали HTTPS к 0.0.0.0/0 (нужен для загрузки пакетов). Скрипт использовал это для исходящих соединений с сервером злоумышленника.

После инцидента Прия добавила:

- Правило NACL, блокирующее румынский IP-диапазон
- Более ограничительное исходящее правило на экземплярах EC2 (разрешало только конкретные известные-хорошие назначения)
- Проверку того, что **IMDSv2 был принудительно включён** (`HttpTokens=required`) на каждом экземпляре — скрипт работал *на* экземпляре, что означало, что он мог запросить сервис метаданных на временные учётные данные роли экземпляра. IMDSv2 был включён ещё в главе 4; Прия проверила, что он по-прежнему требуется везде, потому что злоумышленник с выполнением кода плюс IMDSv1 равно украденным учётным данным AWS.

**Чтение логов потоков: что увидела Прия**

Расследование началось с логов потоков VPC. Прия открыла CloudWatch Logs Insights и выполнила запрос к группе логов потоков за последние 48 часов:

```
fields @timestamp, srcAddr, dstAddr, srcPort, dstPort, action
| filter srcAddr = "10.0.10.7"
| filter action = "REJECT"
| sort @timestamp asc
```

`10.0.10.7` был скомпрометированным экземпляром EC2. Фильтр REJECT показал попытки соединения, которые были заблокированы.

Результаты:

```
10.0.10.7 → 10.0.10.8  port 22    REJECT   # Другой экземпляр EC2 — SSH заблокирован
10.0.10.7 → 10.0.10.9  port 22    REJECT   # Ещё один EC2 — SSH заблокирован
10.0.10.7 → 10.0.20.8  port 5432  REJECT   # RDS — заблокирован группой безопасности
10.0.10.7 → 10.0.20.9  port 5432  REJECT   # Реплика RDS — заблокирована
10.0.10.7 → 10.0.20.11 port 6379  REJECT   # Redis — заблокирован
```

Сканирование задело каждый внутренний сервис. Каждая попытка была отклонена. Дизайн групп безопасности удержался.

Но была также исходящая запись ACCEPT:

```
10.0.10.7 → 185.220.101.55  port 443  ACCEPT   2847 bytes
```

Это была попытка эксфильтрации данных — 2,8 килобайта, отправленных на румынский IP по HTTPS. Группа безопасности разрешала исходящий HTTPS для легитимной загрузки пакетов. Злоумышленник использовал это правило.

«Группы безопасности остановили боковое перемещение», — сказала Прия, проводя команду через логи. «Но исходящее правило было слишком разрешающим. Мы разрешали HTTPS к любому назначению. Мы должны разрешать HTTPS только к известным конечным точкам AWS — CloudWatch, Secrets Manager, S3 — и к CDN репозиториев пакетов».

Она показала обновлённые исходящие правила группы безопасности:

```
TCP 443 → pl-63a5400a (префикс-лист gateway endpoint AWS S3)
TCP 443 → pl-02cd2c6b (AWS CloudWatch Logs)
TCP 443 → 54.239.0.0/18 (репозитории пакетов AWS — со временем сужается)
```

«Это устраняет общее исходящее правило HTTPS. Исходящий HTTPS теперь идёт только к известным-хорошим назначениям».

«А как насчёт функций Lambda, вызывающих сторонние API?» — спросил Лео.

«Они идут через NAT Gateway, у которого своё собственное выделенное исходящее правило», — сказала Прия. «Lambda не использует группу безопасности EC2. Другой сетевой интерфейс, другой набор правил».

---

**История отладки без состояния**

Через две недели после инцидента Рафаэль — всё ещё на своём первом месяце — помогал настраивать новый конвейер данных. Он включал функцию Lambda в VPC, которой нужно было вызвать внутренний API, работающий на EC2.

Функция Lambda истекала по таймауту. Каждый вызов истекал по таймауту.

Рафаэль проверил группы безопасности. Группа безопасности Lambda имела исходящее правило для TCP 8080 к группе безопасности EC2. Группа безопасности EC2 имела входящее правило для TCP 8080 от группы безопасности Lambda. Правила выглядели правильными.

Он повернулся к Лео. «Группы безопасности выглядят нормально. Почему оно истекает по таймауту?»

Лео посмотрел на конфигурацию подсети. Функция Lambda была в приватной подсети. У подсети был пользовательский NACL, который Прия применила во время усиления безопасности.

Он посмотрел на исходящие правила NACL:

```
Rule 100: TCP 443  → 0.0.0.0/0  ALLOW
Rule 110: TCP 5432 → 10.0.20.0/24 ALLOW
Rule *:   All      → 0.0.0.0/0  DENY
```

«NACL разрешает исходящий HTTPS и исходящий PostgreSQL», — сказал Лео. «Он не разрешает исходящий TCP 8080».

«Группа безопасности это разрешает», — сказал Рафаэль.

«NACL — нет. И NACL без состояния. Даже если группа безопасности функции Lambda разрешает исходящее соединение, NACL на границе подсети всё равно оценивает исходящий трафик. NACL блокирует вызов Lambda до того, как он покинет подсеть».

«Но если я добавлю ALLOW для исходящего TCP 8080 в NACL...»

«Тебе также нужно добавить ALLOW для входящих эфемерных портов», — сказал Лео. «Ответ от экземпляра EC2 возвращается на случайном порту между 1024 и 65535. Если входящие правила NACL их не разрешают, ответ блокируется на обратном пути».

Рафаэль обновил NACL:

```
Rule 100:  TCP 443       → 0.0.0.0/0      ALLOW  (исходящий)
Rule 105:  TCP 8080      → 10.0.10.0/24   ALLOW  (исходящий к подсети EC2)
Rule 110:  TCP 5432      → 10.0.20.0/24   ALLOW  (исходящий к подсети БД)
Rule *:    All           → 0.0.0.0/0      DENY
```

И на входящей стороне:

```
Rule 100:  TCP 1024-65535 from 10.0.10.0/24  ALLOW  (обратный трафик от EC2)
Rule *:    All                               DENY
```

Функция Lambda подключилась немедленно.

«Вот почему люди ненавидят NACL», — сказал Рафаэль.

«Вот почему вам нужно их понимать», — сказала Прия. «Баги, которые они создают, — это в точности те баги, которые они призваны предотвращать — неожиданные потоки трафика. Понимание модели без состояния говорит вам ровно, где искать, когда соединение загадочно отказывает».

«Группа безопасности с состоянием — обратный трафик автоматический. NACL без состояния — обратный трафик требует явных правил», — повторил Рафаэль.

«Говори это, пока оно не станет частью того, как ты думаешь», — сказала Прия.

---

**Экстренная блокировка NACL: правило /24**

После выявления диапазона исходного IP злоумышленника реакция Прии была немедленной: добавить правило запрета NACL.

Но она не заблокировала только один IP. Она заблокировала весь `/24` — подсеть из 256 адресов, из которой работал злоумышленник.

«Почему весь /24?» — спросил Лео.

«Потому что блокировка отдельных IP — проигрышная игра. Злоумышленники используют несколько IP в пределах диапазона, ротируя их, когда один блокируется. Блокировка /24 усложняет это — им пришлось бы переключиться на другой блок адресов, что стоит им времени и усилий».

Правило NACL:

```
Rule 90:  ALL from 185.220.101.0/24 → DENY
```

Правило 90 оценивается до любых разрешающих правил (которые начинаются с правила 100). Весь диапазон блокируется до того, как рассматривается любое разрешающее правило.

«И это применяется к каждому ресурсу в подсети?» — спросил Лео.

«К каждому ресурсу. В этом и смысл NACL — он применяется до того, как трафик достигнет группы безопасности любого отдельного ресурса. Запрет NACL на правиле 90 означает, что пакет никогда не доходит до оценки группы безопасности».

«Можем ли мы сделать это группой безопасности вместо этого?»

«Нет. Группы безопасности могут только разрешать трафик. Нет правила запрета. Если вы хотите заблокировать конкретный IP от достижения любого ресурса в подсети, NACL — единственный вариант».

Это основной случай использования правил запрета NACL: экстренное реагирование на активные атаки. Группа безопасности — основной механизм контроля. NACL — экстренный тормоз.

---

**Паттерны проектирования групп безопасности: ссылка по ID**

«Мы думали о том, что произойдёт, когда наши экземпляры EC2 будут заменены?» — спросила Прия. «Auto Scaling завершает старые экземпляры и запускает новые. Новые экземпляры получают новые приватные IP-адреса».

«Если правила групп безопасности ссылаются на IP-адреса», — медленно сказал Лео, — «нам пришлось бы обновлять правила каждый раз, когда экземпляр заменяется».

«Именно. Вот почему вы не ссылаетесь на IP-адреса в правилах групп безопасности для внутривпицевого трафика».

Группы безопасности могут ссылаться на другие группы безопасности вместо IP-адресов. Когда правило говорит «разрешить входящий от группы безопасности балансировщика нагрузки», это означает «разрешить трафик от любого ресурса, к которому прикреплена группа безопасности балансировщика нагрузки». Auto Scaling может запустить тысячу новых экземпляров с новым IP у каждого, и правило остаётся действительным.

Структура групп безопасности Nimbus:

```
nimbus-alb-sg (Балансировщик нагрузки)
  - Входящий: TCP 443 от 0.0.0.0/0
  - Входящий: TCP 80 от 0.0.0.0/0

nimbus-api-sg (Экземпляры API EC2)
  - Входящий: TCP 8080 от nimbus-alb-sg
  - Входящий: TCP 22 от nimbus-bastion-sg
  - Исходящий: TCP 5432 к nimbus-rds-sg
  - Исходящий: TCP 6379 к nimbus-redis-sg

nimbus-rds-sg (RDS)
  - Входящий: TCP 5432 от nimbus-api-sg

nimbus-redis-sg (ElastiCache)
  - Входящий: TCP 6379 от nimbus-api-sg

nimbus-bastion-sg (Бастионный хост)
  - Входящий: TCP 22 от <IP офисного VPN>
```

Никаких IP-адресов для внутреннего трафика. Только ID групп безопасности. Когда экземпляр заменяется, членство в группе безопасности автоматически переносится на новый экземпляр.

«А для микросервисов, которые мы планируем?» — спросил Рафаэль. «У нас в итоге будет дюжина сервисов. Каждому нужно общаться с некоторыми другими, но не со всеми».

«Каждый сервис получает свою собственную группу безопасности», — сказала Прия. «Группа безопасности сервиса A упоминается во входящих правилах каждого сервиса, который сервису A разрешено вызывать. Сервисы, которые не должны общаться, просто не ссылаются на группы безопасности друг друга».

Это **паттерн групп безопасности «звезда» (hub-and-spoke)** для микросервисов. Общая группа безопасности базы данных имеет входящие правила от пяти разных групп безопасности сервисов. Если шестому сервису нужен доступ к базе данных, вы добавляете его группу безопасности во входящее правило базы данных. Если доступ нужно убрать, вы удаляете ссылку. Никакого управления IP. Никаких устаревших правил, указывающих на выведенные из эксплуатации серверы.

«Группа безопасности — это идентичность», — сказала Прия. «IP-адрес — это случайность планирования».

---

**Файрвол наименьших привилегий: дисциплина**

«Мы думали о том, какова правильная позиция для исходящих правил?» — спросила Прия во время обзора после инцидента.

Большинство команд оставляют исходящие правила групп безопасности EC2 по умолчанию: разрешить весь исходящий. Это удобно — приложение может вызвать что угодно — но это не наименьшие привилегии.

Принцип Прии: исходящие правила должны быть такими же конкретными, как входящие правила.

Исходящие правила группы безопасности API Nimbus, после усиления:

```
TCP 5432 → nimbus-rds-sg       (PostgreSQL к RDS)
TCP 6379 → nimbus-redis-sg     (Redis к ElastiCache)
TCP 443  → префикс-лист s3.amazonaws.com    (gateway endpoint S3)
TCP 443  → конечная точка secretsmanager    (Secrets Manager)
TCP 443  → конечная точка logs              (CloudWatch Logs)
```

Никакого «разрешить весь исходящий». Каждое назначение названо.

«Это много обслуживания», — сказал Лео.

«Это больше обслуживания, чем разрешить-всё», — признала Прия. «Это меньше уборки, чем утечка данных. Злоумышленник, скомпрометировавший экземпляр EC2, мог бы эксфильтровать больше данных, если бы исходящие правила были открыты. Они использовали правило HTTPS-куда-угодно, потому что оно там было».

«А с конкретными исходящими правилами даже скомпрометированный экземпляр может отправлять данные только к одобренным назначениям».

«Именно. Группа безопасности становится последней линией сдерживания, а не только первой линией обороны».

## Сильные стороны и ограничения

**Группы безопасности**:

- С состоянием (нет головной боли с эфемерными портами)
- Могут ссылаться на другие группы безопасности (более гибко, чем IP)
- Только разрешающие правила — нет явного запрета
- Работают на уровне ресурсов — детализированно
- Правила применяются немедленно — нет упорядочивания, нет приоритета
- К одному ресурсу можно прикрепить несколько групп безопасности — правила всех объединяются

**NACL**:

- Без состояния (требует явных правил для обоих направлений, включая эфемерные порты)
- Могут явно запрещать — полезно для блокировки известных плохих IP
- Работают на уровне подсети — более широкий мазок
- Пронумерованные правила, оцениваемые по порядку — предсказуемо, но требует тщательного управления
- Применяются до того, как трафик достигнет любого ресурса в подсети — первая линия обороны
- Эффективны для экстренной блокировки IP по всей подсети

**Где подходит каждый инструмент**:

Используйте группы безопасности для всего по умолчанию. Добавляйте NACL, когда вам нужны явные правила запрета — блокировка диапазона IP, блокировка порта на уровне подсети независимо от конфигурации отдельного ресурса или обеспечение того, что подсеть данных никогда не сможет получать трафик от конкретного источника. NACL — не замена групп безопасности; они дополнение для ситуаций, где дизайн групп безопасности «только разрешать» недостаточен.

## Итоги

Инцидент с румынским IP был сдержан элементами управления безопасностью, которые уже были на месте — не по удаче, а по замыслу. Группы безопасности предотвратили боковое перемещение внутри VPC. После инцидента NACL добавили возможность явно заблокировать диапазон IP злоумышленника на границе подсети. Логи потоков VPC сделали атаку видимой. Два инструмента, два уровня, две разные работы — с логированием, чтобы доказать, что произошло.

- **Группы безопасности** — виртуальные файрволы с состоянием для отдельных ресурсов. Только разрешающие правила. Все правила оцениваются одновременно.
- **NACL** — файрволы без состояния для целых подсетей. Разрешающие и запрещающие правила. Правила оцениваются в числовом порядке — первое совпадение побеждает.
- **С состоянием** означает, что ответный трафик автоматически разрешён. **Без состояния** означает, что вы должны явно разрешать трафик в обоих направлениях, включая эфемерные обратные порты.
- Группы безопасности — ваш основной уровень контроля доступа. NACL — переопределение на уровне подсети, особенно для экстренной блокировки.
- Когда NACL разрешает входящий трафик, вы также должны разрешить исходящие эфемерные порты (1024-65535) для прохождения TCP-ответа.
- **Ссылайтесь на группы безопасности по ID**, а не по IP-адресу, для внутривпицевого трафика. Auto Scaling заменяет экземпляры; членство в группе безопасности переносится автоматически.
- **Конкретные исходящие правила** на экземплярах EC2 ограничивают, что может сделать скомпрометированный экземпляр — файрвол наименьших привилегий.
- Используйте логи потоков, чтобы видеть, что группы безопасности и NACL на самом деле делают. Правила — это теория. Логи — это доказательство.

## Советы по экзамену

*Домен SAA-C03: Проектирование безопасных архитектур (Домен 1, Задача 1.2)*

- **С состоянием против без состояния**: Это различие — наиболее часто проверяемая концепция в этой главе. Группы безопасности = с состоянием = ответ разрешён автоматически. NACL = без состояния = нужно явно разрешать ответный трафик.
- **Правила групп безопасности**: Нет явного запрета. Когда к экземпляру прикреплены несколько групп безопасности, применяется объединение всех правил. Все совпадающие правила оцениваются одновременно.
- **Порядок правил NACL**: Правила оцениваются от наименьшего числа к наибольшему. Правило 100 перед 200. Первое совпадение побеждает. Правило `*` (звёздочка) внизу — неявный запрет. Добавление правила запрета на правиле 90 блокирует до любого разрешающего правила на 100.
- **Эфемерные порты**: Классическая ошибка NACL — забыть разрешить исходящий трафик на портах 1024-65535. Если ваш NACL разрешает входящий HTTP (порт 80), но не разрешает исходящие эфемерные порты, пользователи могут отправлять запросы, но никогда не получат ответы. Это наиболее распространённый сценарий NACL на экзамене.
- **Ссылки на группы безопасности**: Вы можете разрешить трафик от другой группы безопасности (не только от IP). Это рекомендуемый паттерн для внутривпицевого трафика. Экзамен часто использует «разрешить входящий от группы безопасности ALB» как правильный ответ для ограничения доступа к EC2.
- **NACL по умолчанию против пользовательского NACL**: NACL по умолчанию разрешает весь трафик. Пользовательский NACL (который вы создаёте) запрещает весь трафик по умолчанию. Сценарий экзамена: «создали новый NACL, и теперь трафик заблокирован» → проверьте отсутствие разрешающих правил.
- **Блокировка IP злоумышленника**: Группы безопасности не могут блокировать конкретные IP (только разрешать). NACL могут явно запретить конкретный IP или CIDR. Сценарий экзамена: «заблокировать конкретный IP от достижения любого ресурса в подсети» → правило запрета NACL.
- **Отладка отказов соединения**: Проверяйте порядок: группа безопасности на источнике (исходящий) → группа безопасности на назначении (входящий) → NACL на подсети источника (исходящий + эфемерные порты) → NACL на подсети назначения (входящий). Большинство отказов соединения на экзамене вызваны отсутствующим исходящим правилом NACL или отсутствующим разрешением эфемерных портов.
- **Несколько подсетей и NACL**: Один NACL применяется ко всем подсетям, связанным с ним. Одна подсеть может быть связана только с одним NACL. Экзамен может спросить, какой NACL обновить, когда затронут трафик конкретной подсети.

## Упражнения

**Упражнение 1 — Запоминание**

Разработчик добавляет входящее правило к группе безопасности, разрешающее трафик на порту 443. Нужно ли ей также добавлять исходящее правило для разрешения ответа сервера? Почему да или почему нет?

Если вместо этого она добавляет входящее правило к NACL, разрешающее трафик на порту 443, нужно ли ей добавлять исходящее правило? Почему да или почему нет?

**Упражнение 2 — Сценарий SAA-C03**

*Сценарий*: Компания запускает веб-приложение на экземплярах EC2 в публичной подсети. Приложение принимает HTTPS-трафик (порт 443) из интернета. Пользователи сообщают, что могут подключиться к приложению, но не получают ответов — запросы зависают и прерываются по таймауту.

Группа безопасности EC2 имеет входящее правило, разрешающее TCP 443 от 0.0.0.0/0. NACL подсети имеет входящее правило (правило 100), разрешающее TCP 443 от 0.0.0.0/0, и исходящее правило (правило 100), разрешающее TCP 443 к 0.0.0.0/0.

Какова НАИБОЛЕЕ вероятная причина проблемы?

A) Группе безопасности не хватает исходящего правила для TCP 443  
B) У экземпляров EC2 нет Elastic IP-адресов  
C) Группе безопасности не хватает входящего правила для эфемерных портов  
D) NACL не хватает исходящего правила, разрешающего эфемерные порты (1024-65535)

**Подсказка 1**: Группы безопасности с состоянием — они автоматически разрешают ответы. NACL без состояния — нет.

**Подсказка 2**: Когда браузер подключается к веб-серверу на порту 443, ответ сервера путешествует обратно на случайном эфемерном порту (1024-65535), а не на порту 443.

**Подсказка 3**: NACL имеет исходящее правило для 443, но ответ не идёт на порт 443.

**Ответ**: D

**Объяснение**: NACL без состояния. Когда пользователи подключаются к серверу на порту 443, TCP-ответ сервера путешествует обратно на эфемерном порту (случайно выбранном из 1024-65535). Исходящее правило NACL разрешает только порт 443, поэтому ответ блокируется правилом запрета по умолчанию. Добавление исходящего правила NACL, разрешающего TCP 1024-65535, исправило бы это.

**Почему не A?** Группы безопасности с состоянием — ответный трафик разрешается автоматически, независимо от исходящих правил. Исходящее правило группы безопасности не нужно.

**Почему не B?** Elastic IP влияют на то, имеют ли экземпляры публичные IP, а не на возможность получать ответы при установленных соединениях.

**Почему не C?** Эфемерные порты предназначены для исходящего ответного трафика, а не входящего. Входящее соединение от пользователей поступает на порт 443, который уже разрешён.
