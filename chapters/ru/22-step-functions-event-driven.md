# Глава 22: Блок-схема, которая выполняется сама

Подтверждение заказа в Nimbus требовало пяти последовательных шагов: списать деньги с карты, отправить письмо с подтверждением, уведомить ресторан, обновить инвентарь и записать транзакцию для бухгалтерии. Если третий шаг завершался ошибкой — если уведомление ресторана не проходило — первый и второй шаги уже были выполнены. С клиента списали деньги. Письмо отправлено. Но ресторан не знал о существовании заказа.

Leo дал название этой категории ошибок: частичный успех. «Всё сработало, — говорил он, — кроме той части, которая имела значение».

— Сколько раз это происходило? — спросила Maya.

— Одиннадцать раз за последние две недели. Большинство мы обнаружили из-за злобных звонков в ресторан. Два нашли в логах — постфактум.

— Значит, у нас нет никакой координации, — сказала Priya. — Пять шагов, выполняемых скриптом, без гарантии, что все они завершатся.

— Или что завершатся в правильном порядке.

— Или что мы знаем, какой из них не сработал.

Leo вывел код на проектор. Это была функция на Python: пятьдесят строк, пять последовательных вызовов API, один блок try/except вокруг всего. «Если что-то здесь бросит исключение, мы получим 500 и клиент увидит ошибку. Но списания и письма не откатываются».

— Нам нужен рабочий процесс, — сказала Maya. — Что-то, что отслеживает каждый шаг.

**AWS Step Functions: оркестрация рабочих процессов**

**AWS Step Functions** — бессерверный сервис оркестрации, координирующий шаги приложения в виде визуального рабочего процесса. Каждый шаг — это **состояние** в **машине состояний**.

Вместо скрипта Python, который выполняется сверху вниз и падает, вы определяете рабочий процесс как машину состояний на JSON/YAML:

```json
{
  "StartAt": "ValidateLicense",
  "States": {
    "ValidateLicense": {
      "Type": "Task",
      "Resource": "arn:aws:lambda:us-east-1:123456789012:function:validate-license",
      "Next": "ImportMenu",
      "Catch": [{"ErrorEquals": ["*"], "Next": "OnboardingFailed"}]
    },
    "ImportMenu": {
      "Type": "Task",
      "Resource": "arn:aws:lambda:us-east-1:123456789012:function:import-menu",
      "Next": "SetupPayments",
      "Retry": [{"ErrorEquals": ["*"], "MaxAttempts": 3, "IntervalSeconds": 5}]
    },
    ...
  }
}
```

Каждое состояние может:

- **Выполнить Lambda-функцию** (наиболее распространённый паттерн)
- **Выполнить задачу ECS** (для длительной работы)
- **Ожидать заданного времени** или **события** (приостановить рабочий процесс до наступления внешнего события)
- **Выбрать путь** на основе условий (логика if/else)
- **Запустить параллельные ветки** одновременно
- **Повторять попытку при ошибке** с настраиваемым экспоненциальным отступом
- **Перехватывать ошибки** и направлять к состояниям обработки ошибок

Step Functions управляет состоянием выполнения надёжно. Если третий шаг не выполняется, выполнение приостанавливается на третьем шаге. Вы можете проверить упавшее выполнение в консоли, исправить проблему и перезапустить с третьего шага — без повторения первого и второго.

**Типы состояний: строительные блоки**

**Task (задача)**: выполнить действие — вызвать Lambda-функцию, запустить задачу ECS, вызвать API. Здесь происходит реальная работа.

**Choice (выбор)**: ветвление на основе условий во входных данных. Как if/else в коде.

**Parallel (параллельное)**: запустить несколько ветвей одновременно и ждать завершения всех.

**Map (отображение)**: применить набор состояний к каждому элементу списка. Обработать 50 позиций меню ресторана параллельно.

**Wait (ожидание)**: сделать паузу на заданное время или до метки времени. Полезно для запланированных задержек.

**Pass (передача)**: передать входные данные на выход без выполнения работы. Используется для преобразования данных и тестирования.

**Succeed/Fail (успех/неудача)**: конечные состояния, завершающие выполнение.

Для подключения ресторана Leo спроектировал рабочий процесс:

1. ValidateLicense (Task → Lambda)
2. ImportMenu (Task → Lambda, с 3 попытками)
3. Параллельная ветка:
   a. SetupPayments (Task → Lambda)
   b. CreateIAMRole (Task → Lambda)
4. SendWelcomeEmail (Task → Lambda, ждёт завершения параллельных задач)
5. NotifySalesTeam (Task → Lambda)

Шаги 3a и 3b выполняются параллельно — они не зависят друг от друга, и их одновременное выполнение экономит время.

**Стандартные и экспресс-рабочие процессы**

Step Functions предлагает два типа рабочих процессов:

**Стандартные рабочие процессы**:

- Максимальная продолжительность: 1 год
- Выполнения долговечны — состояние сохраняется, может быть проверено и проаудировано
- Выполнение не менее одного раза (каждая задача выполняется хотя бы раз)
- Цена за переход состояний
- Лучше всего подходят для длительных, важных рабочих процессов (обработка заказов, подключение клиентов, платёжные потоки)

**Экспресс-рабочие процессы**:

- Максимальная продолжительность: 5 минут
- Более высокая пропускная способность — до 100 000 в секунду
- Выполнение не менее одного раза или не более одного раза (настраивается)
- Цена за продолжительность (как Lambda)
- Лучше всего подходят для высокообъёмных, кратковременных рабочих процессов (обработка событий в реальном времени, приём данных IoT)

Для подключения ресторанов в Nimbus: стандартные (это важно, долговечно, может занять несколько часов при наличии ручных шагов).

Для обновления статуса заказов в Nimbus в реальном времени: экспресс (большой объём, короткая продолжительность, менее критично).

**Событийно-управляемая архитектура: более широкая картина**

Step Functions — лишь один элемент более широкого паттерна: **событийно-управляемой архитектуры**. Вместо того чтобы сервисы вызывали друг друга напрямую (тесная связанность), сервисы генерируют события, а другие сервисы реагируют на них.

Мы видели это на протяжении всей книги:

- Размещение заказов → SNS публикует событие → очереди SQS доставляют его потребителям
- Загрузка файла в S3 → Lambda запускается для его обработки
- Изменение записи DynamoDB → DynamoDB Streams → Lambda обновляет кэш

**Amazon EventBridge** (ранее CloudWatch Events) — продвинутая шина событий для этого паттерна. Она направляет события от сервисов AWS и ваших собственных приложений к целям (Lambda, SQS, Step Functions и т.д.) на основе правил.

EventBridge обеспечивает слабую связанность на архитектурном уровне: сервис заказов публикует события `order.placed`, не зная, кто их слушает. Сервис аналитики, сервис уведомлений и сервис баллов лояльности — все слушают независимо. Добавление нового слушателя не требует изменения сервиса заказов.

**Когда Step Functions — правильный инструмент**

Step Functions превосходит других, когда у вас есть:

**Многошаговые рабочие процессы**, требующие отслеживания прогресса по шагам

**Процессы с участием человека** — Step Functions может ждать сколь угодно долго внешнего события (например, одобрения человека) и затем продолжать

**Обработка ошибок в масштабе** — встроенная логика повтора, перехвата и запасных вариантов для множества шагов

**Аудируемые процессы** — каждое выполнение записывает каждый переход состояний. Вы можете точно видеть, что произошло и когда.

**Сложная параллельная или последовательная логика** — визуальный рабочий процесс облегчает рассуждение по сравнению с эквивалентным кодом

Step Functions избыточен для простых двухшаговых процессов. Используйте его, когда сама координация имеет ценность, а сценарии сбоев важны.

## Преимущества и ограничения

**Почему Step Functions мощен**:

- Визуальная история выполнения — видите точно, где находится рабочий процесс (или где он упал)
- Встроенные повторы и обработка ошибок — нет пользовательского кода для повторов
- Долговечное состояние — выполнения переживают перезапуски и сбои сервисов
- Прямые интеграции с 200+ сервисами AWS (не только Lambda)
- Визуальный рабочий процесс документирует себя сам

**Где возникают сложности**:

- Стандартные рабочие процессы тарифицируются за переход состояний — сложные рабочие процессы со многими состояниями могут стать дорогими в масштабе
- Формат JSON на языке ASL (Amazon States Language) имеет кривую обучения
- Максимальный размер полезной нагрузки — 256 КБ: большие данные должны передаваться через S3, а не напрямую через рабочий процесс
- Длительные рабочие процессы со многими ручными шагами требуют тщательной настройки тайм-аутов

## Резюме

- **Step Functions** оркеструет многошаговые рабочие процессы в виде машин состояний.
- Каждое **состояние** может запустить Lambda-функцию, выполнить задачу ECS, ждать, ветвиться или запускать параллельные шаги.
- **Повторы и перехват** встроены в каждое состояние — нет необходимости в пользовательском коде повторов.
- **Стандартные рабочие процессы**: длительные (до 1 года), долговечные, выполнение не менее одного раза. Для критичных бизнес-процессов.
- **Экспресс-рабочие процессы**: краткосрочные (до 5 минут), высокопроизводительные. Для высокообъёмной обработки событий.
- **Событийно-управляемая архитектура** использует такие сервисы, как SNS, SQS, Lambda и EventBridge, для развязки систем вокруг событий, а не прямых вызовов.
- Используйте Step Functions, когда координация шагов сама по себе сложна и когда важна аудируемость.

- **Признаки использования Step Functions**: «оркестрировать несколько Lambda-функций», «рабочий процесс с повторами и обработкой ошибок», «шаг одобрения человеком в автоматизированном рабочем процессе», «аудиторский след каждого шага рабочего процесса» → Step Functions.

- **SQS и Step Functions**: SQS для простых очередей задач (производитель/потребитель). Step Functions для многошаговых рабочих процессов со сложной логикой, повторами и отслеживанием состояний.
- **Признаки EventBridge**: «маршрутизировать события от сервисов AWS к целям», «событийно-управляемая интеграция между сервисами», «запланировать Lambda-функцию» → EventBridge (ранее CloudWatch Events).
- **Паттерн обратного вызова**: Step Functions может приостанавливать выполнение и ждать внешнего обратного вызова (токен задачи). Воркер вызывает обратно после завершения. Полезно для длительных задач ECS, где вы не хотите использовать 15-минутный лимит Lambda.
- **Прямые SDK-интеграции**: Step Functions может вызывать сервисы AWS напрямую (DynamoDB, S3, SQS и т.д.) без Lambda. Снижает стоимость и задержку для простых вызовов сервисов.

**Упражнение 2 — Подготовка к экзамену**

*Сценарий*: Компания по финансовым услугам обрабатывает заявки на кредит в несколько шагов: проверка кредитной истории, подтверждение дохода, проверка документов, проверка андеррайтером (вручную) и уведомление о решении. Каждый шаг может занимать от секунд (проверка кредитной истории) до дней (проверка андеррайтером). Компании нужен полный аудиторский след каждого шага для обеспечения соответствия требованиям. Упавшие автоматизированные шаги должны автоматически повторяться; ручные шаги должны приостанавливаться и ждать решения человека.

Какой сервис наилучшим образом отвечает этим требованиям?

A) Lambda-функции AWS, связанные через очереди SQS между каждым шагом  
B) Стандартные рабочие процессы AWS Step Functions с паттерном «Ждать обратного вызова» для шага проверки андеррайтером  
C) Экспресс-рабочие процессы AWS Step Functions для автоматизированных шагов и SQS FIFO для ручного шага  
D) Amazon EventBridge с правилами событий, маршрутизирующими Lambda-функции для каждого шага

**Подсказка 1**: Продолжительность «до нескольких дней» — какой тип Step Functions это поддерживает?

**Подсказка 2**: «Ожидать решения человека» — для чего предназначен этот паттерн Step Functions?

**Подсказка 3**: «Полный аудиторский след для соответствия требованиям» — какой сервис предоставляет историю состояний для каждого выполнения?

**Ответ**: B

**Пояснение**: Стандартные рабочие процессы Step Functions могут выполняться до 1 года, поддерживая шаг проверки андеррайтером, занимающий несколько дней. Паттерн «Ждать обратного вызова» приостанавливает выполнение на шаге андеррайтера с токеном задачи; когда андеррайтер принимает решение, он вызывает обратно с токеном для продолжения рабочего процесса. Стандартные рабочие процессы записывают каждый переход состояний — полный аудиторский след для соответствия требованиям.

**Почему не A?** Lambda, связанная через SQS, не предоставляет встроенного отслеживания состояний или аудиторского следа. Упавшие шаги требуют пользовательской логики повторов. Перезапуск с конкретного упавшего шага требует пользовательской реализации.

**Почему не C?** Экспресс-рабочие процессы имеют максимальную продолжительность 5 минут — несовместимо с шагом, который может занимать несколько дней.

**Почему не D?** EventBridge маршрутизирует события между сервисами, но не поддерживает состояние рабочего процесса и не предоставляет встроенных повторов/аудита. Построение на одном EventBridge требует пользовательского управления состоянием.
