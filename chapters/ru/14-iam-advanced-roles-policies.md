# Глава 14: Кому разрешено что делать

У Тома ключи доступа были открыты в текстовом файле, готовые для вставки.

«Что ты делаешь?» — спросила Прия.

«Экземпляру EC2 нужно читать конфигурационные файлы из S3. Я помещаю учётные данные в конфигурацию сервера».

Она несколько секунд смотрела на экран. «Закрой этот файл».

«Я просто хотел...»

«Если кто-то проникнет на этот сервер», — сказала она, — «они получат эти ключи. А эти ключи касаются всего, что IAM-пользователю разрешено касаться. Что, вероятно, больше чем просто S3».

Том закрыл файл.

«Есть лучший способ», — сказала она. «Сам сервер может иметь роль. Думай об этом как о должности — экземпляру не нужны учётные данные, потому что система уже знает, что он такое и что ему разрешено делать».

Том выглядел скептично. «Значит сервер аутентифицирует сам себя?»

«Да. Без пароля. Без ключей в конфигурационном файле. Без чего-либо, что может быть случайно закоммичено в git».

Последняя часть попала в цель. Том нашёл пароль базы данных в истории git две недели назад. Он открыл новую вкладку браузера.

**Пересмотр IAM: полная картина**

Глава 3 ввела IAM: пользователи, группы, роли и политики. Теперь время углубиться.

Политики IAM — это JSON-документы, которые указывают, какие действия разрешены или запрещены с какими ресурсами. Они выглядят так:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": [
        "s3:GetObject",
        "s3:PutObject"
      ],
      "Resource": "arn:aws:s3:::nimbus-assets/*"
    }
  ]
}
```

Эта политика разрешает чтение и запись объектов в бакете `nimbus-assets`, и ничего больше. Не удаление. Не перечисление бакетов. Не любая другая операция S3. Не любой другой сервис AWS.

Это правильный способ предоставлять разрешения: конкретные действия, конкретные ресурсы.

**Проблема с «Правами администратора»**

AWS Managed Policies, такие как `AdministratorAccess`, предназначены для быстрого старта. Они не предназначены для работы производственных систем с реальными членами команды.

`AdministratorAccess` предоставляет каждое действие для каждого ресурса. Если член команды с этой политикой делает ошибку — случайно удаляет бакет S3, завершает не тот экземпляр EC2, изменяет правила группы безопасности — AWS ничего не может сделать, чтобы их остановить. Разрешение было предоставлено.

Если учётные данные члена команды скомпрометированы (фишинговая атака, утёкший ключ доступа, кража ноутбука), злоумышленник имеет права администратора ко всему в вашем аккаунте AWS.

«Значит что должна иметь Су-Джин?» — спросил Лео.

«Что Су-Джин нужно делать?» — ответила Прия вопросом.

«Развёртывать API. Проверять логи. Больше ничего».

«Тогда она получает: возможность отправлять в конвейер кода, доступ на чтение к логам CloudWatch, и ничего больше».

«Это... очень конкретно».

«Да. В этом и смысл».

**IAM Roles: идентификаторы для сервисов**

Глава 3 ввела роли как способ для экземпляров EC2 получать доступ к сервисам AWS без хранения учётных данных. Давайте сделаем это конкретным.

Экземплярам EC2, запускающим API Nimbus, нужно:

- Читать из DynamoDB (меню)
- Записывать в DynamoDB (заказы)
- Помещать объекты в S3 (квитанции, загрузки)
- Записывать логи в CloudWatch
- Читать секреты из Secrets Manager

Вместо создания пользователя с ключом доступа и хранения этого ключа на экземпляре EC2 (кошмар безопасности — ключи доступа могут быть прочитаны любым, у кого есть SSH-доступ), вы создаёте **IAM Role** для экземпляра EC2 с именно этими разрешениями.

Экземпляр EC2 автоматически принимает роль. AWS предоставляет временные учётные данные через сервис метаданных экземпляра. Учётные данные ротируются автоматически. Нет ключа доступа для утечки.

«И если кто-то взломает экземпляр EC2?» — спросил Лео.

«Они смогут делать то, что разрешает роль EC2», — сказала Прия. «Что означает читать меню, записывать заказы и отправлять логи. Они не могут удалить бакет S3. Они не могут завершить экземпляры EC2. Они не могут трогать IAM».

«Потому что у роли EC2 нет этих разрешений».

«Именно».

**Принятие ролей: как сервисы становятся другими сервисами**

Роли могут быть приняты:

- **Сервисами AWS** (EC2, Lambda, задачи ECS и т.д.)
- **IAM-пользователями** в вашем собственном аккаунте (повышение роли — вы принимаете роль с большими разрешениями для конкретной задачи)
- **IAM-пользователями в других аккаунтах AWS** (кросс-аккаунтный доступ — аккаунт другой организации может принять роль в вашем)
- **Внешними провайдерами идентичности** (Google, Active Directory, Okta — федеративный доступ для человеческих пользователей)

Этот последний паттерн — **федерация идентичностей** — это то, как крупные организации дают своим сотрудникам доступ к AWS без создания индивидуальных IAM-пользователей для каждого человека. Active Directory вашей компании хранит ваши учётные данные. Когда вы входите в AWS, вы аутентифицируетесь против Active Directory, и AWS предоставляет вам роль.

**Границы разрешений: ограничение того, что могут предоставить роли**

Вот тонкая, но важная проблема: по умолчанию IAM не предотвращает предоставление пользователем разрешений, которых у него ещё нет.

Если у Су-Джин есть `iam:CreatePolicy` и `iam:AttachUserPolicy`, она может создать политику, предоставляющую доступ на запись в S3, и прикрепить её к себе — даже если её существующие политики разрешают только чтение S3. Этот класс уязвимости называется **повышением привилегий**, и именно поэтому существуют границы разрешений.

Но что если вы хотите делегировать создание IAM-разрешений руководителю команды, гарантируя при этом, что он не может предоставить больше, чем вы намеревались?

**Границы разрешений** устанавливают максимальные разрешения, которые могут быть когда-либо предоставлены идентификатору. Даже если прикреплённые политики идентификатора шире, эффективные разрешения ограничены границей разрешений.

Пример: Вы даёте руководителю команды политику, позволяющую создавать IAM-роли. Но вы прикрепляете границу разрешений, которая говорит: «Роли, созданные этим руководителем команды, никогда не могут иметь доступ на удаление S3». Даже если руководитель команды создаёт роль с полным доступом к S3, граница не позволяет удалению S3 вступить в силу.

Это продвинутая концепция, но она появляется на экзамене и отражает то, как организации делегируют управление IAM в масштабе.

**IAM Access Analyzer: аудит разрешений**

Прия потратила два дня на проверку IAM-настройки команды. Она обнаружила:

- Личный пользователь Лео имел права администратора (как было выявлено)
- Старая функция Lambda имела разрешения на чтение всех бакетов S3 (осталась от теста)
- Сервисная роль имела доступ на запись в таблицы DynamoDB, которые больше не существовали

Это нормально. Конфигурации IAM накапливают хлам со временем.

**IAM Access Analyzer** — это сервис AWS, который автоматически идентифицирует ресурсы (бакеты S3, IAM-роли, KMS-ключи, функции Lambda), которые разделяются с внешними сущностями. Он также идентифицирует излишне разрешительные политики.

Регулярные аудиты IAM должны быть частью ваших операций. Разрешения растут; они редко органически сокращаются. Access Analyzer помогает сделать невидимое видимым.

**Service Control Policies: организационные ограждения**

Если ваша среда AWS вырастет до нескольких аккаунтов (распространённый паттерн для больших команд — аккаунт разработки, аккаунт тестирования, производственный аккаунт), **AWS Organizations** позволяет управлять ими из центрального аккаунта.

В рамках Organizations **Service Control Policies (SCP)** применяют ограждения, влияющие на *каждую* IAM-сущность в аккаунте, включая администраторов.

Пример SCP: «Никто в аккаунте разработки не может создавать экземпляры EC2 в регионе eu-west-1».

Даже если у кого-то есть права администратора в аккаунте разработки, они не могут нарушить этот SCP. Он применяется на уровне организации, выше уровня аккаунта.

SCP не предоставляют разрешения — они ограничивают их. Они определяют максимальные разрешения, которые любая IAM-сущность в аккаунте может когда-либо иметь.

## Сильные стороны и ограничения

**Почему важны роли IAM и наименьшие привилегии**:

- Ограничивает радиус поражения при компрометации учётных данных
- Требует от злоумышленников эскалации через несколько систем, а не немедленного получения полного доступа
- Предоставляет журнал аудита — CloudTrail логирует, какая роль что делала
- Принуждает принимать осознанные решения об доступе — «что этому сервису действительно нужно?»

**Где всё усложняется**:

- Написание точных политик IAM требует понимания модели действий/ресурсов AWS для каждого сервиса (и у каждого сервиса десятки действий)
- Излишне ограничительные политики ломают приложения — отладка ошибок «access denied» по нескольким сервисам трудоёмка
- IAM распространяет изменения с небольшой задержкой (обычно секунды, иногда больше) — может вызывать запутанные проблемы с тайминговым выполнением
- Кросс-аккаунтные роли требуют тщательной настройки политики доверия

## Итоги

- Избегайте **прав администратора** в производстве — они для настройки, не для эксплуатации.
- Политики IAM указывают **Effect**, **Action** и **Resource** — будьте конкретны во всех трёх.
- Прикрепляйте политики к **группам** (для людей) и **ролям** (для сервисов).
- Экземпляры EC2, функции Lambda и другие сервисы AWS должны использовать **IAM Roles**, а не ключи доступа.
- **Границы разрешений** ограничивают максимальные разрешения любого идентификатора, независимо от прикреплённых политик.
- **SCP** (Service Control Policies) применяют общеорганизационные ограничения, которые даже администраторы не могут переопределить.
- **IAM Access Analyzer** идентифицирует излишне разрешительные политики и внешний доступ к ресурсам.

## Советы по экзамену

*Домен SAA-C03: Проектирование безопасных архитектур (Домен 1, Задача 1.1)*

- **IAM-роли для EC2**: Канонический ответ, когда EC2 нужен доступ к S3, DynamoDB, Secrets Manager или любому сервису AWS. Никогда не храните ключи доступа на экземпляре.
- **Логика оценки политик**: Когда IAM оценивает запрос, он использует иерархию явного разрешения/запрета. Явный **Запрет** всегда побеждает, даже против явного Разрешения. По умолчанию — Запрет.
- **Границы разрешений**: Используются при делегировании IAM-администрирования. Сценарий экзамена: «разрешить разработчикам создавать роли для их функций Lambda, но не позволять им предоставлять разрешения сверх того, что они имеют». → Границы разрешений.
- **SCP не предоставляют разрешения**: Они только ограничивают. Если SCP разрешает S3, но политика IAM запрещает его, S3 запрещён. Если SCP запрещает S3, но политика IAM разрешает его, S3 запрещён.
- **Политики на основе ресурсов**: Некоторые сервисы AWS (S3, SQS, Lambda) имеют политики на основе ресурсов — разрешения, прикреплённые к ресурсу, а не к идентификатору. Они работают вместе с политиками IAM.
- **Кросс-аккаунтный доступ**: IAM-роль в Аккаунте A с политикой доверия, позволяющей Аккаунту B принять её. Пользователь/роль Аккаунта B затем использует `sts:AssumeRole` для получения временных учётных данных в Аккаунте A.
- **IAM Users против Federated Access**: Для крупных организаций федеративный доступ (через IAM Identity Center или прямую федерацию с IdP) предпочтительнее индивидуальных IAM-пользователей.

**Упражнение 2 — Практика для экзамена**

*Сценарий*: Функции Lambda нужно читать из бакета S3 и записывать в таблицу DynamoDB. Разработчик дал функции Lambda роль с `AdministratorAccess` для простоты во время разработки. Перед переходом в производство команда безопасности хочет следовать принципу наименьших привилегий.

Какой из следующих подходов является НАИЛУЧШИМ?

А) Создать нового IAM-пользователя с разрешениями на чтение S3 и запись DynamoDB; сгенерировать ключ доступа; хранить ключ в переменных среды Lambda  
Б) Прикрепить встроенную политику к роли выполнения функции Lambda, предоставляющей `s3:GetObject` на конкретный бакет и `dynamodb:PutItem` на конкретную таблицу  
В) Сохранить `AdministratorAccess`, но добавить SCP, блокирующий все действия кроме S3 и DynamoDB  
Г) Создать IAM-группу с разрешениями на чтение S3 и запись DynamoDB и добавить функцию Lambda в группу

**Подсказка 1**: Функции Lambda используют роли выполнения, а не ключи доступа. Какой вариант это учитывает?

**Подсказка 2**: Наименьшие привилегии означают конкретные действия на конкретных ресурсах, а не широкие политики.

**Подсказка 3**: IAM-группы содержат пользователей, а не функции Lambda.

**Ответ**: Б

**Объяснение**: Роль выполнения Lambda должна иметь только конкретные разрешения, необходимые функции. Встроенные политики, ограниченные конкретными действиями (`s3:GetObject`) и конкретными ресурсами (ARN бакета, ARN таблицы DynamoDB), — это реализация наименьших привилегий.

**Почему не А?** Хранение ключей доступа в переменных среды Lambda является антипаттерном безопасности — ключи могут быть прочитаны любым, у кого есть доступ к консоли Lambda или через контекст выполнения. Функции Lambda используют роли выполнения с временными учётными данными от IAM.

**Почему не В?** SCP применяются на уровне Организации/аккаунта и не функционируют как контроль разрешений для каждой функции. AdministratorAccess с SCP — неправильный уровень.

**Почему не Г?** Функции Lambda не могут добавляться в IAM-группы. Группы предназначены только для IAM-пользователей.
